# One line = one (migration file, target table, pinned top-level statement

#
#     <basename>.sql <TAB> <schema.table> <TAB> <n> <TAB> # <anchor + consumer>
#
# Field 3 is `<n>` for an INSERT line (C1-C4). A C5 line (below) spells it
# `update:<n>` (replayed) or `decline:<n>` (accounted for, not replayed), and
# its field 4 is the REASON rather than a consumer; it is required all the same.
#

#    STATEMENT, not of a table. `public.strategies` is a DO-block fixture in

# ── THE CRITERION (C1-C4). A statement is reference data iff ALL FOUR hold ──
# C1  TOP-LEVEL — not inside a `DO $$…$$`, a `CREATE FUNCTION … AS $$…$$`, or a
#     `cron.schedule($cron$…$cron$)` body. Every fixture, probe and backfill in
#     this corpus lives in a body; every reference seed is bare.
# C2  LITERALS ONLY — `INSERT INTO t (cols) VALUES (…)` with no SELECT/FROM and
#     no identifier in the tuple beyond a cast, NULL/TRUE/FALSE, now() or
#     gen_random_uuid(). An `INSERT … SELECT` is a backfill of existing data by
#     construction: on an empty table it inserts nothing.
# C3  TARGET IN `public` — the restore drops ONLY `public` (the
#     `DROP SCHEMA public CASCADE` in the TXN_DROP heredoc of
#     scripts/restore-test-from-baseline.sh), so rows in other schemas
#     survive and need no replay.
#     ⛔ CITED BY SYMBOL, NOT BY LINE, ON PURPOSE. This read `:861` until
#     2026-09-09; that line had drifted to an unrelated census row within this
#     one PR, which added ~490 lines above it. C3 decides which schemas get
#     replayed, so its anchor must not rot. `storage.buckets` is OUT for this reason.
#     ⚠️ ONE NAMED EXCEPTION, and only one: `auth.users` in
#     20260515095804_teaser_anchor_strategy.sql. That row is the FK head of the
#     teaser trio and it SURVIVES the restore, so replaying it is a no-op via its
#     own `ON CONFLICT (id) DO NOTHING`. It is kept because `public.profiles` and
#     `public.strategies` below it do NOT survive, and keeping the head makes the
#     trio FK-self-contained on a lane that starts empty. The extractor accepts
#     `auth.users` and NO other non-public target; any other schema is refused by
#     name. A reviewer who reads C3 and then finds this line has not found a
#     contradiction — this paragraph IS the exception.
# C4  A CONSUMER READS THE ROW BY KEY — an FK, a CHECK, a slug lookup, or a
#     constant in application code. Human judgement; cite it in the entry.
#     Idempotence (`ON CONFLICT DO NOTHING`) is a strong SIGNAL and NOT a
#     criterion: `discovery_categories` has none and is unquestionably reference,
#     while a backfill in 20260408113028_disclosure_and_tenancy.sql:152-156
#     carries one and is not.
# C5  TOP-LEVEL LITERAL UPDATE ON A REPLAYED PUBLIC TABLE (Phase 164.9.2, added
#     2026-09-25). A separately pinned class, NOT a relaxation of C2. It admits
#     a top-level (C1) `UPDATE [ONLY] <target> [[AS] alias] SET …` whose target
#     is a `public` table some INSERT line above fills, and whose masked text
#     carries no FROM, USING, SELECT, RETURNING or WITH, no `$`, and no call but
#     `now()` (an IN list and AND/OR/NOT parentheses are not calls). Those
#     tables are empty after `DROP SCHEMA public CASCADE`, so such an UPDATE can
#     reach only rows the replay itself wrote. The extractor replays it inside
#     the same transaction, in (migration filename, byte offset) order, and its
#     block carries a `-- refdata-update:` trailer, never `-- refdata-expect:`,
#     so the restore's count floor stays INSERT-only.
#     ⛔ PUBLIC ONLY, NO auth.* EVER. The auth.users exception above is C3's and
#     is INSERT-only: auth.users SURVIVES the DROP, so a replayed UPDATE there
#     would mutate shared TEST's live row. A C5 line on any non-public target is
#     refused at parse. And because `--audit` accounts for every UPDATE on every
#     table an INSERT line fills, auth.users included, a future top-level UPDATE
#     of auth.users is refused outright: no line can account for it. Zero C5
#     statements on auth.* is therefore by design, not an accident of the corpus.
#     ⛔ DECLINE, NEVER SKIP (decision D-02). A top-level UPDATE on such a table
#     that is NOT literal (a join, a sub-select, a function call) gets a
#     `decline:<n>` line with its reason. (Since 164.9.2 review round 1 a
#     decline: count ALSO covers the writes a DO body runs on the table at apply
#     time — WR-02 / SFH-02; see the DO-body block at the foot of this file.)
#     It is emitted as nothing, counted in
#     the C5 census every run, and refused if the statement ever turns literal
#     ("a literal UPDATE is replayed, not declined"), so a decline can never hide
#     a replayable effect. The INSERT side's limitation 2 below (an unlisted
#     non-literal is skipped) is deliberately NOT carried over to C5.
#     `--audit` refuses a DELETE, TRUNCATE, MERGE or CTE-prefixed data-modifying
#     statement on such a table by name: C5 replays UPDATE only. At most one
#     `update:` and one `decline:` line per (file, table); a second line of one
#     kind is refused as a duplicate.
#     ⛔ CORRECTED 2026-09-25 (164.9.2 review round 2, WR-01 / SFH R2-01). "so a
#     decline can never hide a replayable effect" was FALSE for DO-body writes:
#     round 1 made every one declinable with any reason text, so a LITERAL
#     DO-body UPDATE of a seeded row, and a DO-body DELETE / TRUNCATE / MERGE /
#     COPY that is a hard refusal at top level, both passed under a decline:
#     line. The sentence above is kept as lineage. What a decline: line may
#     account for is now exactly three things, and each is scoped truthfully:
#       (1) a top-level NON-literal UPDATE, and (2) a NON-literal DO-body UPDATE.
#           For both, "it reaches no row the replay wrote" is a REVIEW judgement

#     Everything else is a HARD refusal that no line clears, at top level and in
