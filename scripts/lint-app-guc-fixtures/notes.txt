The successor `successor-not-sql.red.sql` points at — and why it is a .txt
===========================================================================

This file is the TARGET of that fixture's `successor:` field. It is plain text,
it is readable, and it is emphatically not a migration.

⛔ IT CONTAINS ZERO APP-GUC READS, AND THAT IS LOAD-BEARING — MEASURED
------------------------------------------------------------------------
The defect this fixture closes (164.7-REVIEW WR-06, threat T-164.7-02) is that
a successor merely had to EXIST and to hold zero app-GUC reads. Any file that
is not SQL trivially holds zero, so the second half of the old check was free
and `successor: notes.txt` PASSED.

So the fixture only demonstrates that closure if this file would have passed
the OLD check. If it carried a read-shaped line, the fixture would go red on
the CONTENT arm instead, and the red could not be attributed to the TYPE arm
at all.

MEASURED 2026-09-11, with an earlier draft of this file that did carry one:
disabling the type arm left `lint-app-guc.mjs --self-test` at `exit 0`, fully
GREEN — the fixture kept firing through the content arm and proved nothing
about the arm that had just been deleted. That is a control that cannot fail,
which is the exact defect class this phase exists to remove.

⛔ Do NOT add an app-GUC read to this file to make it "look like SQL". Doing so
re-creates that vacuity. The refusal must happen on the NAME, before this
file's bytes are ever read — which is also why the type arm short-circuits.

⚠️ This is a `.txt` and therefore outside `sqlFilesUnder`'s corpus and outside
the self-test's `*.red.sql` / `*.green.sql` sweeps. It is never scanned on its
own; it is read only as the successor of the fixture that names it, and under
the shipped check it is not even read that far. Its sibling
`unreadable-marker.txt` documents the conditions that cannot be a committed
`.sql` file at all.
