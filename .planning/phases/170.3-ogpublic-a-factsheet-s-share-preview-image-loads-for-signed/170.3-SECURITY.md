### T-170.3-01: no unpublished or other-tenant data through the now-anonymous route (high, CLOSED)

Three independent layers, each checked in code:

1. **Application predicate.** The only data read in the route is the `strategies` query. It is wrapped in `withPublishedOnly(` at `src/app/api/og/factsheet/[id]/route.tsx:100`, with `.eq("id", id)` at `:135` and `.maybeSingle()` at `:137`. `withPublishedOnly` (`src/lib/visibility.ts:81-93`) appends `.eq("status", "published")`. The `strategy_analytics` data arrives as an embed in the same query (`:134`), so it is gated by the same parent predicate. There is no second query, no service-role client and no `req` use: the handler's request parameter is `_req` (`:84`). The `?u=` query param is never read (`:165-170` comment, and no `searchParams` in the file). The client is `createClient()` (`:99`), which is the cookie-scoped anon-key client (`src/lib/supabase/server.ts:6-29`).
2. **RLS for anon.** `supabase/schema/baseline.sql:15681` `strategies_read` is `status = 'published' OR user_id = auth.uid()`. `:15677` `strategies_org_read` is permissive and adds org members only, and `auth.uid()` is NULL for anon. `:15091-15093` `analytics_read` requires the parent row to be published or owned. RLS is enabled on both tables (`:15666`, `:15689`). So an anonymous caller can never read a draft row even if the app predicate were dropped. The predicate also covers the case RLS permits: a signed-in org member or owner can read unpublished rows, but `withPublishedOnly` excludes them from this route.
3. **Failure path.** A read error, a not-found and an unpublished id all end at the same generic card. `data = res.data ?? null` (`route.tsx:146`) then `name = data?.name ?? data?.codename ?? "Strategy"` (`:154`). `res.error` sets `failed` and reports (`:142-145`), and the response is the image only. The error object goes to `console.error` and Sentry `extra`, never into the response body. A draft row therefore cannot appear on the failure path.

Test evidence (re-run green): `route.public-access.test.tsx` uses a fake that honours the recorded `.eq()` filters (lines 100-130, "Anonymous RLS: a row is visible only if it matches every predicate the route sent"). P1 renders a `draft` row and asserts none of its name, description or figures appear (`expectGenericCard`, lines ~225-238). P4 is the non-vacuity control with the same row published. P5 pins `["status","published"]` on `strategies` for unpublished, unknown, malformed and published ids. The author recorded neuter (a), the predicate replaced by a pass-through, as turning P1 and all four P5 cases RED, with a clean `cmp` restore (SUMMARY 01).

Residual disclosure on a published row: `name`, `codename`, `description` and three stored figures. This is the same set the already-public `/factsheet/[id]` page puts in its `<title>` and `og:description` for anonymous visitors (`src/app/factsheet/[id]/v2/page.tsx:257-272`, via the same `withPublishedOnly`). It is not a new exposure class. `name` takes precedence over `codename` on the card exactly as it does in that page's metadata.

### T-170.3-02: PUBLIC_ROUTES no wider than /api/og/factsheet (medium, CLOSED)

- `src/proxy.ts:18` adds exactly one string, `"/api/og/factsheet"`. `grep -o '"/api/og[^"]*"' src/proxy.ts` prints only that, and `grep -c '"/api/og"'` is 0. The two other `/api/og` hits in the file are comment lines.
- The matcher is `path === route || path.startsWith(route + "/")` (`src/proxy.ts:78`), so a sibling such as `/api/og/factsheetx` does not match.
- The only OG route in the tree is `src/app/api/og/factsheet/[id]/` (`ls -R src/app/api/og`), so no other card is exposed. A future OG route must opt in.
- `src/proxy.test.ts` pins the allowed `/api/og/factsheet/<uuid>` and four 307 cases: `/api/og`, `/api/og/other-card/abc-123`, `/api/og/factsheetx`, `/api/og/factsheetx/abc-123` (diff at `:239-245` and `:293-301`). Neuters (e) entry widened to `/api/og` and (f) `startsWith(route + "/")` loosened to `startsWith(route)` were recorded RED (4 and 17 failures).
- `e2e/og-public.spec.ts` carries an in-run control that `/api/portfolios/list` still 307s. The e2e job is advisory (`continue-on-error`), so `proxy.test.ts` is the blocking gate and it is in the green run.

### T-170.3-03: no per-viewer content under a public CDN cache (medium, CLOSED)

- Card content is a pure function of the published row: `id` (path), `name`, `codename`, `description`, `asset_class`, the analytics embed. Every one of those is read under the `status = published` predicate (`route.tsx:100-137`). Nothing in the file reads the session, `user_id`, owner, headers or cookies (`grep -n 'cookies\|headers\|getUser\|session\|owner\|user_id'` over `route.tsx` returns nothing). The signed-in and signed-out renders of one id are therefore the same image, so `public, s-maxage=86400, stale-while-revalidate=604800` (`:36`) is not keyed to a viewer.
- Org-member and owner visibility, which RLS grants, is cut off by the predicate, so there is no owner-only branch to leak.
- `?u=<unit>` affects only the cache key, never the content (the unit is re-read from the row, `:165-176`).
- The failure path sends `no-store` (`:40`, `:307`), so a degraded card is never publicly cached.
- P5 (`route.public-access.test.tsx:306-318`) pins the predicate on every case, so a future per-viewer read would need to drop it.

## Booked review item 170.3-OG-MALFORMED-ID: judgement

**Classification: an observability defect, with a low-severity security-adjacent edge. Not a security threat to this phase's register. Non-blocking.**

What is certain from the code:

- A non-uuid id reaches `.eq("id", id)` (`route.tsx:135`) with no `isUuid` check, so PostgREST answers 22P02. The route takes the failure path: `console.error`, `no-store`, a full render, and a `shouldCaptureNow("og-factsheet:read")` call (`src/lib/sentry-capture.ts:342-351`, 60 s window, per instance). The sibling public route `tearsheet.pdf/route.ts:163` already rejects a non-uuid id first.
- Confidentiality: not affected. The malformed-id response is the generic card, and the error object stays in logs and Sentry (T-170.3-01 section, failure path). Integrity: not affected.
- Availability: not meaningfully changed. A malformed id costs one cheap failed query plus one render. A valid-but-unknown uuid costs one indexed read plus one render at a distinct URL. An attacker gets no amplification over just iterating uuids, which T-170.3-04 already accepts. The one nuance is that T-170.3-04's premise "a not-found card is long-cached per URL" does not hold for malformed ids (they are `no-store`). That does not change the severity, since random valid uuids are uncached by URL in practice too.
- Detection: one anonymous request a minute per instance can occupy the single `og-factsheet:read` Sentry slot, so a real read failure (statement timeout, column drift) would go to logs only for that minute. That is a monitoring-evasion edge for one stage of one low-value route, with no data exposure, hence low. `compute` has its own slot and is not masked.

It is below `block_on: high`, so it does not count toward `threats_open`. It stays OPEN-non-blocking as an observability item, already tracked as `170.3-OG-MALFORMED-ID` in `TODOS.md` (line 9199), with the right fix (`isUuid` pre-check, not-found treatment, a separate valid-uuid error case to keep SFH-02 pinned). Recommendation: leave it with the booked owner and trigger. If someone wants to treat the detection-evasion edge as a security item, rate it low.

Booked sibling items `170.3-OG-NOTFOUND-CACHE` (a pre-publication blank card cached a day plus a week: freshness, not disclosure) and `170.3-OG-P3-STATUS-VACUOUS` (a test line that cannot fail) are not security threats. P3's cache-header assertion and `expectGenericCard` still fail on the behaviours they guard.
