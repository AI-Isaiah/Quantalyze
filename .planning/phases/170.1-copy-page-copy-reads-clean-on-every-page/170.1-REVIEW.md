### WR-01: Bespoke CSV rules render a false cause line: "Rule violated: This value does not pass a format check."

**Severity:** MEDIUM. **Class:** user-facing (wizard CSV upload and CSV submit).
**Files:**
- `src/lib/wizardErrors.ts:6416-6458` (`CSV_RULE_LABELS`, which has no entries for the four bespoke keys)
- `src/lib/wizardErrors.ts:6467-6472` (`csvRuleLabel` fallback)
- `src/app/(dashboard)/strategies/new/wizard/steps/CsvValidationEnvelope.tsx:237-246` (cause line)
- `src/app/(dashboard)/strategies/new/wizard/steps/CsvValidationEnvelope.tsx:289` (`<summary>`)

**Evidence: the trace.**
1. **Producer.** `analytics-service/services/csv_validator.py` emits four row-0 bespoke errors:
   - `empty` at `:663-668` ("No file uploaded") and `:742-747` ("No data rows found");
   - `parse_error` at `:681-686` and `:707-712` ("Could not parse CSV: …");
   - `too_many_rows` at `:755-765` ("CSV exceeds the 5000-row limit (got N rows).");
   - `date_format_ambiguous` at `:782-787`.

   `MAX_INGEST_ROWS = 5000` (`:85`) sits well under the 10 MB byte cap, so a CSV of 20 years of
   daily returns (about 7,300 rows) reaches `too_many_rows`.
2. **Wire.** The live upload path is `csv-validate/route.ts` → `/process-key`
   (`flow_type=csv`, `step=validate`) → `_run_validate_only`. That returns
   `_envelope_error(val.error_code, …, source_debug_context=val.debug_context)`, where
   `csv_adapter.py:159-179` carries `errors` as `violations`.
   `_forwarded_pandera_rows` (`process_key.py:414-450`) then projects them onto
   `debug_context.pandera_errors` as `{rule:"too_many_rows", row:0, message:"CSV exceeds …"}`.
   `CsvUploadStep.tsx:503-519` hands that `debug_context` to the envelope unchanged.
3. **Render** (`CsvValidationEnvelope.tsx`). `ruleCount === 1` and `realRowCount === 0`, so the
   cause line is `formatCsvRuleCauseFileLevel(csvRuleLabel("too_many_rows"))`, and
   `csvRuleLabel` misses and returns the fallback.

**Exact text a user sees for a 7,300-row upload:**

```
Your file failed validation
Rule violated: This value does not pass a format check. We checked the whole file, so no single row is at fault.
▸ This value does not pass a format check                       <- <summary>, collapsed
    • CSV exceeds the 5000-row limit (got 7300 rows).            <- only inside the closed <details>
```

The cause line is false for all four rules. No value failed a format check:
- the file is too long (`too_many_rows`);
- it has no data rows (`empty`);
- it is not parseable CSV (`parse_error`);
- its date order is ambiguous (`date_format_ambiguous`).

The one true sentence is hidden inside a collapsed `<details>`. Before plan 02 the same slot
printed the raw key ("Rule violated: too_many_rows."). That was ugly but not false. The change
replaced a raw identifier with a wrong explanation.

When two unlabelled rules co-occur, for example `date_format_ambiguous` beside another
unlabelled rule, the multi-rule line reads "Across 2 rule categories: This value does not pass
a format check, This value does not pass a format check." Two categories carry the same name.
The `mystery_rule` test (`CsvValidationEnvelope.test.tsx:766-781`) renders exactly that string
and asserts only `toContain("Across 2 rule categories:")`.

**Root cause.** R-3 says the bespoke messages "already read in plain words and render
verbatim", and plan 02 honoured that for the `<li>` only. UI-SPEC § Copy — CSV errors routes
the `<summary>` and the cause line through `CSV_RULE_LABELS[rule] ?? <fallback>`. Its fallback
row was written for unknown PANDERA rules, so the bespoke keys fell through a gap in the spec.
The executor's code is correct to the spec. The spec is wrong for these four keys.

**Fix.** Pick one, and confirm the wording with the founder: these are new user-facing
strings.
- (a) Preferred: label the four bespoke keys in `CSV_RULE_LABELS`, in the sentence-case voice
  of the existing labels. For example:

  ```ts
  too_many_rows: "Your file has more rows than the upload limit",
  empty: "Your file has no data rows",
  parse_error: "We could not read your file as a CSV",
  date_format_ambiguous: "The dates could be day-first or month-first",
  ```

  Then add an envelope test that drives the producer's real `too_many_rows` and `empty`
  messages and asserts the cause line and the `<summary>` text.
- (b) Alternatively: when the single rule's rows are all non-pandera-built
  (`!isPanderaBuilt(message)`) and there is exactly one row, use that row's `message` as the
  cause line in place of `formatCsvRuleCauseFileLevel(label)`.

Either way, de-duplicate the labels in the multi-rule cause line
(`[...new Set(humanizedKeys)]`) so that two fallback rules cannot print the same category
twice.

### R-1 (MEDIUM, data-integrity): F2 is still open when the Excel blank first row is narrower than the header. The exact repeat is accepted, and the user's second column is ignored without a word

**File:** `analytics-service/services/csv_validator.py:846-867` (`_raw_header_names`) and `:1001` (`... or list(df.columns)`)

**Repro (measured):**
```
,
date,daily_return,daily_return
2024-03-10,0.001,0.5
2024-03-11,0.002,0.5
2024-03-12,-0.001,0.5
```
`validate_csv(raw, "daily_returns")` returns `ok: True` with `errors: []`, and `daily_returns_series` is built from the FIRST column (0.001, 0.002, -0.001). The `0.5` column is dropped and the user is not told.

**Mechanism:**
1. `_raw_header_names` reads `header=None, nrows=header_row + 1`, so pandas fixes the field count from the 2-field blank row.
2. The 3-field header line then raises `ParserError`, which is swallowed (`return None`).
3. The caller falls back to `df.columns`, which pandas has already mangled to `daily_return`, `daily_return.1`.

The probes confirm this:
- a blank row as wide as the header (`,,`) or wider (`,,,,`) is caught;
- a narrower one (`,`) is not;
- the shipped test covers only the same-width shape (`test_an_exact_repeat_under_a_leading_blank_header_row_is_found_too`).

**Reach:** narrow. Excel writes every row to the used-range width. A narrower blank row comes from other tools or hand edits.

**Second defect, same lines:** the fallback is fail-OPEN by construction. Any raw-read failure silently restores the exact pre-F2 behaviour this round set out to remove.

**Fix:** read the header row with the stdlib `csv` reader, skipping empty records the way `skip_blank_lines` does, so no field-count inference is involved. Measured correct for the narrower, equal-width and wider blank rows, a leading empty line, a BOM, a quoted embedded comma and a quoted newline:
```python
import csv, itertools

def _raw_header_names(raw_bytes: bytes, header_row: int) -> list[str] | None:
    try:
        text = raw_bytes.decode("utf-8-sig")
        records = (r for r in csv.reader(io.StringIO(text)) if r)  # pandas skips blank lines
        return next(itertools.islice(records, header_row, None), None)
    except (UnicodeDecodeError, csv.Error):
        return None
```
Do NOT use `names=range(len(df.columns))`. It fixes the narrower case but misreads a wider blank row: the header comes back as `['daily_return', '', '']`, measured. When the raw read does return None, fail closed rather than fall back to the mangled names. A frame column whose name ends in `.N` and whose base name is declared and also present is ambiguous, so reject it with the same sentence. Add a red test for the narrower blank row.
