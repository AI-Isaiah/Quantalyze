## Summary

The round-2 lock design holds up. I traced each question in the brief and found no lock-order inversion, livelock or ownership-check defect. The one finding is that the worker does not handle the new 55P03 the way the migration's comment says it does.

### What I traced and found sound

- **Subtransaction rollback releases the block's row locks.** Every closure row is locked inside the `BEGIN … EXCEPTION WHEN SQLSTATE 'FI001'` block, so its `xmax` is the subtransaction's XID. When the subtransaction aborts, that XID leaves the backend's running-subxid set. A waiter in `XactLockTableWait` then sees it as not in progress and finds the tuple lock void. The failed job's own row was locked (`SELECT … FOR UPDATE`) and updated by the top-level XID before the block, so the rollback leaves it alone. PL/pgSQL variables are not rolled back, but `v_held` is reset to `'{}'` at the top of each outer attempt, so the stale value is never read.
- **No inversion with `mark_compute_job_done` or the enqueue.** Each path takes exactly one row lock outside the helper: the failed job, the done job, or nothing for the enqueue. Everything else goes through `_fan_in_lock_rows` in ascending (depth, id) order. The closure contains only strict `done_pending_children` descendants of a `running` root. So no other cascade's closure and no `mark_compute_job_done` child set can contain that root. An enqueue that names the root plus a lower-keyed row R holds only R while it waits, and R cannot be in the closure. `sync_strategy_analytics_status` takes no `compute_jobs` row locks, so the sorted advisory locks taken after the rows add no edge.
- **The re-read is complete.** A child of a locked row, or of the root, can only come from `_enqueue_compute_job_internal`, which share-locks every parent first. The other `parent_job_ids` writers listed in `supabase/schema/functions/` route through it. If such an enqueue commits before the lock is granted, the next statement-level snapshot (READ COMMITTED, assumption A1) sees its child.
- **Livelock is bounded.** A retry needs an enqueue to commit a new descendant inside the lock wait. Releasing on FI001 does let queued share-lockers through, but the bound of 10 stops the loop, so it cannot spin.
- **FI001 is private.** No PostgreSQL class `FI` exists. FI001 appears only in this migration, its function snapshot and the catalog anchor. The handler is inside the function and catches nothing else, so FI001 never escapes.
- **The cross-allocator check.** `match_decisions.allocator_id` and `bridge_outcomes.allocator_id` are both `NOT NULL`, so `IS DISTINCT FROM` cannot misfire on a NULL. All three `commit_scenario_batch` arms insert the decision and the outcome with the same `p_allocator_id`. The route sends only the caller's own `sent_as_intro` decision. The `compute_bridge_outcome_deltas` cron and `feedback_engine.py` never write `match_decision_id`. RLS pins `allocator_id = auth.uid()` in both `USING` and `WITH CHECK`, so a tenant cannot re-pair the row through `allocator_id`, which is outside the trigger's column list.
- **The route's 403.** supabase-js `PostgrestError` carries `code` and `hint` from PostgREST. TC10 pins the hint literal against the migration text and keeps a bare RLS 42501 as the generic 500.
- **Twins.** Every RED-UNDER-M `find` string for FL4, FL5, FL6, FL7, FC5, FC6 and OD8 matches exactly once in the migration (`grep -cF` = 1 each). FL6's twin exits the second read unchecked, and FL7 still passes under it because cascade 2 picks X up after cascade 1 commits. FL7's twin restores lock-on-top, and FL6 still passes under it because X is free, so the twins are not cross-scored WRONG-ARM. FL7 under its twin is a real 40P01: cascade 1 holds D and wants X, while cascade 2 holds X and wants D.

## Warnings

### WR-01 (MEDIUM, WARNING): the new 55P03 is not "left running for the watchdog". The worker's catch-all re-marks the job as `unknown`, which discards a permanent failure and its user-facing error kind.

**File:** `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql:934-938` (and the identical text in `supabase/schema/functions/mark_compute_job_failed.sql`); the raise is at `:955-960`. Consumer: `analytics-service/main_worker.py:991-997` and `:1008-1045`.

**Issue:** The migration says the bounded retry "fails loud, SQLSTATE 55P03 (never 55006, which the worker swallows …); the job stays `running` for the watchdog". The worker does not do that:

1. `dispatch_tick` calls `await _safe_mark(_mark_failed, …)` (`main_worker.py:991`) inside the `try:` opened at `:919`.
2. `_safe_mark` swallows only 55006 or the "preempted by watchdog reclaim" literal (`_is_serialization_failure`, `:410-415`). It re-raises the 55P03 `APIError`, and `db_execute` has no retry (`services/db.py:134`).
3. The 55P03 lands in the `except Exception as exc` at `:1008`, which handles a crash in `dispatch()`. That block calls `_mark_failed_fallback` (`:1025-1036`), which runs `mark_compute_job_failed` again with `p_error = str(exc)[:500]` (the 55P03 text) and **`p_error_kind = 'unknown'`**.

**Concrete failure scenario:** a job with `attempts < max_attempts` hits a permanent error (for example a revoked key). Its parents are listed, and enqueues keep committing children into its waiting closure until the retry hits the 10-attempt bound. The first RPC rolls back with 55P03, and the fallback then marks the job:

- **status:** `failed_retry`, not `failed_final`, because the kind is `unknown`;
- **`error_kind`:** `unknown`, not `permanent`;
- **`last_error`:** the 55P03 lock-attempt sentence, not the real error.

Three consequences follow:

- **No cascade runs.** Its waiting children keep their in-flight slots, and their strategies read `computing` until the retry fails again. That is the stranding D-01 exists to end, now delayed by the backoff schedule.
- **The real error is gone.** `Job … failed (permanent)` at `:999` is never reached, so the permanent error is never logged.
- **Retries on a permanent error.** The job is re-run up to `max_attempts` times.

If `attempts >= max_attempts`, the fallback does make it `failed_final` and the cascade runs. In that case every descendant inherits `error_kind = 'unknown'` through `fp.error_kind`, so the strategy owners' curated copy, which derives from `error_kind` alone (the migration says so), says "unknown" instead of what really happened. This is user-facing data, which is why it is MEDIUM and not LOW. It is latent today: PROD holds 0 parented jobs and no caller passes parents. The round-2 review's statement that an aborted `mark_compute_job_failed` "leaves its job `running` until the watchdog reclaims it" (REVIEW-R2 line 107) had the same blind spot.

**Fix:** pick one and make the comment say what actually happens.

- (a) **Worker side, preferred.** In `_safe_mark`, or in the FAILED branch, treat a 55P03 from `mark_compute_job_failed` as "the mark did not land, leave the job to the watchdog". Return without falling into the dispatch catch-all, and log at ERROR with the original `result.error_kind` and `result.error_message`:
  ```python
  except Exception as mark_exc:
      if _is_serialization_failure(mark_exc):
          ...  # unchanged
          return True
      if label.startswith("mark_failed") and getattr(mark_exc, "code", None) == "55P03":
          logger.error("MARK_FAILED_LOCK_BOUND: job %s: cascade lock retry bound hit; "
                       "job left running for the watchdog: %s", job_id, mark_exc,
                       extra={"event_type": "mark_failed_lock_bound", "job_id": job_id})
          return False  # caller must not run the generic fallback
      raise
  ```
  With this, the FAILED branch no longer reaches `except Exception as exc` at `:1008`. Pin it with a `main_worker` unit test in which a fake `mark_compute_job_failed` raises `code='55P03'` and the test asserts that no second `mark_compute_job_failed` call is made.
- (b) **SQL side.** Keep the worker as it is and rewrite `:934-938` and the header paragraph at `:105-108` to say that the worker re-marks the job as `unknown`/`failed_retry`. Book the loss of the permanent `error_kind` as a known limit in TODOS, against the first caller that passes parents.
