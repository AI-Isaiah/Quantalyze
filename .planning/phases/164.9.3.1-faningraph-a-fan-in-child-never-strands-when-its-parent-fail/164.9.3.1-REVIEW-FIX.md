### CR-01: the failure cascade locked level by level, so a deeper graph deadlocked (40P01)

**Status:** fixed: requires human verification (concurrency logic; the evidence below is executed, not read)
**Files modified:** `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql`, `supabase/schema/functions/mark_compute_job_failed.sql`, `supabase/tests/test_fan_in_lock_order_race.sql`, `supabase/tests/test_fan_in_failure_cascade.sql`
**Commits:** `51f1df169` (RED arms), `c61e2c25e` (fix)
**Applied fix:** `mark_compute_job_failed` now reads the whole waiting closure first (a recursive CTE seeded from every job failed so far, no locks), locks it with ONE `_fan_in_lock_rows(v_kids, TRUE)` call, and only then fails it level by level, each level restricted to the locked set (`c.id = ANY(v_kids)`) so every child still names its own failed parent (D-03). An outer loop re-runs only for children committed by a concurrent enqueue during the lock wait. The closure read skips every job already in `v_fail_set`, so termination does not lean on the status filter alone. New self-verify anchor `v_failed_closure_anchored` (recursive read, `@>` walk, exactly one helper call, the read precedes the lock); header text corrected to say one call per path.

**Deviation from the review's sketch:** the review suggested repeating read/lock/update for rows that appear after the lock wait. That is kept, but the seed of the second read is `parent_job_ids && v_fail_set` (all jobs failed so far), not only the root, so a child born under an already-failed row is found. A residual remains and is documented in the migration header: rows born DURING the cascade's own lock wait are locked in a second pass, after the first pass's rows. They are new rows that only their creator knows, no caller passes parents and PROD holds none (D-04 census), so the window is theoretical, but "no 40P01 anywhere" is true for every case except that one.

**RED/GREEN evidence (pg-lane, `scripts/pg-lane/run.sh`):**
- FL4 (review scenario B: F; A [F], B [A], D [F, B]; a permanent failure on F against an enqueue naming [B, D]) on the tip body: `TEST FAILED (FL4) ... the enqueue raised 40P01 (deadlock detected)`. GREEN after the fix.
- FL5 (review scenario A: F1 and F2 failing together over the same graph) on the tip body: `TEST FAILED (FL5) ... Cascade 1 raised 40P01 (deadlock detected), cascade 2 raised nothing, the roots read running and failed_final`. GREEN after the fix.
- Mutation twins, one per arm, DIFFERENT on purpose (the runner scores a twin by the file's first failing arm; one shared mutation scored FL5 `WRONG-ARM(FL4)` on the first attempt): FL4 makes the closure read non-recursive (`JOIN clo ON FALSE`), FL5 follows single-parent children only (`parent_job_ids = ARRAY[clo.id]`), both layered with `v_failed_closure_anchored` stood down. Runner: `arm FL4 exit 3 RED (identity ok)`, `arm FL5 exit 3 RED (identity ok)`.
- The FC4, FC5 and FC6 twins were re-pointed at the new text (FC5 stands down both loop exits, FC6 both status filters). The first FC6 twin hung for over 10 minutes: with both filters dropped the cascade looped forever. That is what the `v_fail_set` skip in the closure read now prevents.

### WR-01: a client could make the trigger write `former_match_decision_id` by attaching a decision and detaching it

**Status:** fixed: requires human verification (trigger logic)
**Files modified:** `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql`, `supabase/schema/functions/bridge_outcomes_sync_holding_ref.sql`, `supabase/tests/test_bridge_outcomes_decision_delete_cascade.sql`
**Commits:** `76b1d3c33` (RED arm), `023000835` (fix)
**Applied fix:** on an UPDATE that removes the link, the trigger records `OLD.match_decision_id` only when the decision row is gone (`IF EXISTS (SELECT 1 FROM match_decisions WHERE id = OLD.match_decision_id)` then NULL, else the old id). A voluntary detach is therefore a born-NULL row and meets the duplicate guard. New anchor `v_sync_detach_anchored` (the existence test precedes the copy). The three "cannot forge" comments (migration header, `COMMENT ON COLUMN`, `COMMENT ON FUNCTION`) now state the rule. OD1 and OD2, which delete real decisions, stay green, confirming the cascade's UPDATE runs after the parent row is invisible to the trigger.

**RED/GREEN evidence:**

OD1 to OD6 passed in the same run. GREEN after the fix.
