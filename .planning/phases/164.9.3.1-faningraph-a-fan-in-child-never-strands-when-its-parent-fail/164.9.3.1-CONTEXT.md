<decisions>
## Implementation Decisions

### The stranded or orphaned child (founder 2026-10-11, "Accept all")
- **D-01:** a fan-in child whose parent ends `failed_final` becomes `failed_final` itself, with an
  error naming the failed parent's job. It shows in the admin compute-jobs view like any failure and
  is never claimed again.
- **D-02:** the release is eager, inside `mark_compute_job_failed`, when the parent's last retry is
  spent, in the same transaction. No sweep.
- **D-03:** the release is transitive: each grandchild level fails, naming its own failed parent.
- **D-04:** research counts children already stranded on PROD (read-only). If any exist, the
  migration releases them once under the same rule and reports the count.

### The cascade 23505, the diamond deadlock and the lost release (founder 2026-10-11, "Accept all")
- **D-05:** the 23505 from a second `match_decisions` delete (the `ON DELETE SET NULL` cascade onto
  `bridge_outcomes_legacy_per_strategy_holding_when_md_null`) is fixed at its source after research
  proves what the index protects once the decision is NULL. Outcome rows are never deleted or merged
  to make room. Dropping or narrowing the index is allowed only if the planner shows the invariant
  it enforces no longer holds (SC-2).
- **D-06:** the diamond deadlock is prevented: every path that locks fan-in parents and children
  takes its locks in one global order (by job id). A 40P01 retry on the enqueue and mark paths is
  the fallback only if the planner proves the deadlock inherent (SC-3).
- **D-07:** the lost release is fixed by locking the child row and re-reading every parent's status
  inside `mark_compute_job_done`, so exactly one finishing parent releases it. Proven with two
  genuinely separate sessions; a single-client `Promise.all` cannot race.
- **D-08:** one migration PR carries all four fixes, each with a red-first lane test that fails on
  today's bodies. Migration-reviewer, rls-policy-auditor and silent-failure-hunter review it before
  merge, because a merge auto-applies to PROD. Every `CREATE OR REPLACE` re-bases on the latest
  definition found by a grep of all `supabase/migrations/**`.

### The outcome route's 42P10 (plan-level addition, 2026-10-15, coordinator relaying the founder's rule)
- **D-09:** the founder's rule of 2026-10-15 says user-facing and data-integrity defects are fixed, not booked
  ("Going forward, we should fix also the medium user facing and data integrity issues"). The booking
  `164.9.3.1-OUTCOME-ROUTE-42P10` was measured that day, read-only, on PROD after the marker query.
  `bridge_outcomes` has exactly three unique indexes: `bridge_outcomes_pkey (id)`,
  `bridge_outcomes_allocator_match_decision_unique (allocator_id, match_decision_id)`, and the md-NULL partial
  index. `EXPLAIN INSERT ... ON CONFLICT (allocator_id, strategy_id)` raises `42P10: there is no unique or
  exclusion constraint matching the ON CONFLICT specification`, so every `POST /api/bridge/outcome` returns
  500 on PROD today. The fix is at the root: the route's upsert targets `(allocator_id, match_decision_id)`.
  That is the existing constraint carrying the one-outcome-per-decision rule (migration 081 replaced 072's
  per-strategy unique with it), and the route always writes `match_decision_id = decision.id`. The fix needs a
  live-DB test seen RED (42P10) before GREEN. It is plan 11, and it adds no migration.
  `POST /api/bridge/outcome/dismiss` is unaffected: `bridge_outcome_dismissals` has a unique index on
  `(allocator_id, strategy_id)`.

### Research clarifications (2026-10-15, plan time; evidence in 164.9.3.1-RESEARCH.md)
These refine how D-05, D-06 and D-01..D-03 are carried out. None of them reverses a decision. Each is
flagged to the founder in the plan-time report. The decisions above are kept as written, as lineage.
- **On D-06 (the lock order).** A pure job-id order still deadlocks (40P01, reproduced on the lane for the
  diamond and for the transitive cascade). The cause is that a mark path learns a job's children only
  after it holds the job, so it must lock parent before child. D-06's "one global order" is carried
  out as **ancestor-first, with job id as the tie-break**: the key is (longest-ancestor-chain depth,
  id), and one private helper is used by every path. That order was run green on both interleavings.
  The deadlock is therefore not inherent, and the 40P01-retry fallback is not used.
- **On D-05 (the index fix).** D-05 lets the index be narrowed if research shows the invariant no longer
  holds. It does not hold for rows nulled by the cascade: a first-class admin delete turns a lawful
  state into a forbidden one (two outcomes for one allocator/strategy under two decisions are
  allowed by design). The index is narrowed only for that population. A nullable
  `former_match_decision_id` column is recorded by the sync trigger, and the SAME-named index is
  re-keyed on it. Born-NULL rows keep today's key and today's duplicate guard (option Y). The index
  is not dropped (that was option Z), and no outcome row is deleted or merged.
- **On D-01..D-03 (the second `failed_final` writer): NOT in this phase, open for the founder.** The
  hourly orphan reaper (the inline pg_cron job `retention_compute_jobs_orphaned_running`, last
  registered by `20260826140000`) also writes `failed_final` without going through
  `mark_compute_job_failed`, so it can still strand a fan-in child. It is latent, because no caller
  passes `parent_job_ids` and PROD holds 0 rows with parents. Covering it here would mean
  re-registering the cron job, which gives it a fresh PROD jobid and moves the retention gate's
  token counts and its RED-UNDER-M twins, invariant 7 of
  `retention-orphaned-running-terminalize.test.ts`, and the prober cron manifest. Alternatively it
  could be covered by a status trigger, which departs from D-02's "inside
  `mark_compute_job_failed`". Neither was discussed. This phase therefore keeps D-02's literal
  scope, books the reaper path in TODOS, and asks the founder.
  **FOUNDER DECISION (2026-10-15, AskUserQuestion "Book it, latent (Recommended)"):** keep
  `164.9.3.1-REAPER-STRAND` out of this phase. Its TODOS entry stays, with the trigger "the first caller that
  enqueues with parents, or any PROD compute_jobs row with parents".
- **On D-04.** The read-only PROD census on 2026-10-15 found 0 rows with parents and 0
  `done_pending_children` (2292 jobs in total). The migration owes no one-time release and carries
  no data-reading block.
