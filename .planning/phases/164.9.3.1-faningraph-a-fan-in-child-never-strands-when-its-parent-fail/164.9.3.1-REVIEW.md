## Critical Issues

### CR-01 (HIGH, BLOCKER): the failure cascade locks level by level, so its rows are not taken in ascending (depth, id) order and a deeper graph still deadlocks (40P01)

**File:** `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql:868-905` (the cascade loop; the helper is called at `:878` once per level). The claim it breaks is at `:70-74` and `:80-82`, and in the comment at `:854-855`.

**Issue:** `_fan_in_lock_rows` sorts by (longest-ancestor depth, id) only within ONE call. The cascade calls it once per BFS level:
- level k locks the done_pending_children whose parents overlap the level k-1 frontier;
- level k+1 then locks the next level.

A row reached at level 1 can have a LARGER depth than a row reached at level 2. That happens whenever a direct child of the failed job also hangs under a longer chain. So the transaction holds a deep row while it waits on a shallower one. Every other path ascends the key, so this is exactly the opposite-order pair the header says "none exists" (`:73-74`).

**Failure scenario 1: two concurrent cascades.**
- Graph:
  - F1 and F2 are running, depth 0.
  - A has parents [F1], depth 1.
  - B has parents [A, F2], depth 2.
  - D has parents [F1, B], depth 3.
  - A, B and D are `done_pending_children`.
- Run:
  1. Cascade 1 (F1 ends `failed_final`) runs level 1 and locks A and then D.
  2. Cascade 2 (F2 ends `failed_final`) runs level 1 and locks B.
  3. Cascade 1 runs level 2. Its plain SELECT still sees B as `done_pending_children`, so it waits on B.
  4. Cascade 2 runs level 2. Its plain SELECT still sees D as `done_pending_children`, so it waits on D.
- Result: a cycle, and SQLSTATE 40P01.

**Failure scenario 2: one cascade and one enqueue (one failing job suffices).**
- Graph: the same, but F2 is absent and B has parents [A].
- Run:
  1. Cascade 1 locks A and then D at level 1.
  2. A concurrent `_enqueue_compute_job_internal` naming parents [B, D] share-locks B (depth 2) and then waits for D (depth 3, held FOR UPDATE).
  3. Cascade 1's level 2 then wants B FOR UPDATE, which conflicts with the share lock.
- Result: 40P01.

The same inversion also deadlocks against `mark_compute_job_done` when a released node's children span levels of a concurrent cascade.

**Consequence:** the victim `mark_compute_job_failed` rolls back, so the job stays `running` until the watchdog reclaims it and re-runs it, or the enqueue gets a 500.

**Classification:**
- No data is corrupted, because the rollback is clean.
- It is **latent**: no caller passes `parent_job_ids`, and PROD holds 0 parented rows (D-04 census).
- It is a **phase-goal gap**. SC-3 and D-06 promise no deadlock on the fan-in lock graph, and the brief asks for diamonds AND deeper graphs.
- `test_fan_in_lock_order_race.sql` covers only one-level shapes (FL2: two rows; FL3: a depth-1 child), so no gate can see this.
- Not user-facing today; not data-integrity.

**Fix:** make the cascade take all of its row locks in ONE ascending pass.
1. Compute the descendant closure read-only.
2. Lock that whole set with a single `_fan_in_lock_rows` call.
3. Only then run the per-level UPDATEs.
4. Repeat the read/lock/update loop only for rows that appear after the lock wait (new children committed by an enqueue that held a share lock). Those rows can only have been created under rows this transaction now holds.

```sql
IF v_new_status = 'failed_final' THEN
  LOOP
    -- 1. read the whole waiting closure below the failed job (no locks)
    WITH RECURSIVE clo(id) AS (
      SELECT c.id FROM compute_jobs c
       WHERE c.status = 'done_pending_children'
         AND c.parent_job_ids && ARRAY[p_job_id]
      UNION
      SELECT c.id FROM compute_jobs c JOIN clo ON c.parent_job_ids @> ARRAY[clo.id]
       WHERE c.status = 'done_pending_children'
    )
    SELECT COALESCE(array_agg(id), '{}') INTO v_kids FROM clo
     WHERE NOT (id = ANY(v_casc_all));          -- rows not yet handled
    EXIT WHEN cardinality(v_kids) = 0;
    -- 2. ONE ascending lock pass over the whole set
    PERFORM public._fan_in_lock_rows(v_kids, TRUE);
    v_casc_all := v_casc_all || v_kids;
    -- 3. the existing level-by-level UPDATE ... RETURNING, restricted to
    --    c.id = ANY(v_kids), so each child still names its OWN failed parent (D-03)
  END LOOP;
END IF;
```

Add a gate arm with the scenario 2 shape: a level-1 child deeper than a level-2 child, and a dblink enqueue naming [shallow, deep]. It is RED on the current body and GREEN after the fix.

## Warnings

### WR-01 (MEDIUM, WARNING): a client can make the trigger write `former_match_decision_id` by attaching any existing decision and then detaching it, so the column is not "trigger-owned" in effect and the born-NULL guard is bypassable

**File:** `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql:1021-1022` (`ELSIF OLD.match_decision_id IS NOT NULL THEN NEW.former_match_decision_id := OLD.match_decision_id;`). The claims are at `:972-984`, in `COMMENT ON FUNCTION` at `:1110` ("so a client cannot forge it"), and in `COMMENT ON COLUMN` at `:1075`.

**Issue:** the trigger cannot tell the `ON DELETE SET NULL` cascade apart from an ordinary owner `UPDATE ... SET match_decision_id = NULL`. `bridge_outcomes_update_own` and `bridge_outcomes_insert_own` check only `allocator_id = auth.uid()`. The foreign key checks only that the decision exists, and the check runs with owner rights, so it can be any allocator's decision.

**Failure scenario:**
1. An allocator holds a born-NULL outcome R1 for strategy S.
2. They INSERT R2 with (S, `match_decision_id = D`), where D is any decision id they can name, for example one of their own outcomes' decision ids.
3. They UPDATE R2 with `SET match_decision_id = NULL`.
4. The trigger stores `former = D`, so R2 keys as (allocator, S, '', D) and escapes the born-NULL duplicate guard that option Y exists to keep (D-05).

**Impact:**
- `former_match_decision_id` now claims the outcome "was recorded under" a decision that was never deleted, and possibly one belonging to another allocator. The provenance meaning the column COMMENT documents is false for that row.
- The arms OD4, OD5 and OD6 do not cover this path.
- The impact is bounded. Equivalent evasions already exist: keeping R2 attached, and the booked `164.9.3.1-HOLDING-REF-DIRECT-UPDATE`.
- Data-integrity (provenance and guard); not user-facing.

**Fix:** record the former id only when the decision is really gone, which is the cascade case. Any voluntary detach then becomes born-NULL and meets the guard.

```sql
ELSIF OLD.match_decision_id IS NOT NULL
      AND NOT EXISTS (SELECT 1 FROM match_decisions WHERE id = OLD.match_decision_id) THEN
  NEW.former_match_decision_id := OLD.match_decision_id;   -- the ON DELETE SET NULL cascade
ELSIF OLD.match_decision_id IS NOT NULL THEN
  NEW.former_match_decision_id := NULL;                    -- an owner detach: born-NULL key
ELSE
  NEW.former_match_decision_id := OLD.former_match_decision_id;
END IF;
```

The RI action runs after the parent DELETE, so the deleted decision is no longer visible to the trigger's SELECT. Confirm this on the lane with OD1 and OD2, and add an OD7 arm: attach and then detach on a row whose decision still exists must collide 23505 with a born-NULL sibling. Correct the three comments to match.
