## Summary

All four defects are real and were reproduced on today's function bodies on a private pg-lane cluster. (1) A child whose parent ends `failed_final` stays `done_pending_children` forever, and its strategy stays "computing" in `strategy_analytics`; a prototype cascade inside `mark_compute_job_failed` fails the whole descendant closure in the same transaction and, once the child strategies are also pushed through the status bridge, flips them to `failed` with the curated sentence. (2) Deleting two `match_decisions` rows whose outcomes share `(allocator, strategy)` raises 23505 on `bridge_outcomes_legacy_per_strategy_holding_when_md_null` in all three shapes tried, including a single multi-row `DELETE` and the exact shape PROD holds today, because the sync trigger rewrites `original_holding_ref` to NULL on the `ON DELETE SET NULL` update, so every orphaned row lands on the key `(allocator, strategy, '')`. (3) The diamond deadlock reproduces deterministically (the enqueue gets 40P01). (4) The lost release reproduces deterministically with two backends (both parents `done`, child still `done_pending_children`, zero releases).

Two of the locked decisions need a precise reading, and both are decided by execution, not argument. **D-06 as worded ("one global order by job id") cannot be a deadlock-free order**: the mark paths only learn a finishing job's children after they hold the job, so they are forced to lock parent-before-child, and an id-only order deadlocks in the diamond (EXP-B) and in the transitive failure cascade (EXP-D) on the lane. The order that works, and that was executed green, is ancestor-first with job id as the tie-break, i.e. `ORDER BY (longest-ancestor-chain depth), id`. The deadlock is therefore not inherent and no 40P01 retry is needed (PostgREST 14 would retry 40P01 anyway). **D-05 does not require dropping the index**: re-keying it with a preserved former decision id fixes all three cascade shapes and keeps the born-NULL duplicate guard (which matters, because the `bridge_outcomes_insert_own` RLS policy lets an allocator insert md-NULL rows directly); dropping the index also works but removes that guard and rewrites a documented invariant.

**Primary recommendation:** one migration, newest timestamp above `20261022120000`, that (a) adds a private lock-order helper `_fan_in_lock_rows(uuid[], boolean)` ordered `(depth, id)`; (b) re-bases `_enqueue_compute_job_internal` (10-arg, only the parent-lock statement changes), `mark_compute_job_done` (lock children via the helper, then release in a later statement) and `mark_compute_job_failed` (transitive cascade + bridge every affected strategy in one sorted lock order); and (c) fixes the cascade 23505 by recording the former decision id on the orphaned outcome and re-keying the partial unique index (Option Y), with founder ratification of Y versus the cheaper drop (Z). Build the red-first lane gates first (waves below).

### Pattern 1: lock the children in one statement, release in a LATER statement (D-07)
**What:** take the row locks first, then decide, in a second statement.
**Why it works:** under READ COMMITTED each statement takes a fresh snapshot, but a single `UPDATE ... WHERE NOT EXISTS (parent <> 'done')` evaluates the subquery on the statement-start snapshot, which is exactly the bug: two parents each see the other as still running. With the lock taken in a previous statement, the second parent blocks on the child until the first commits, and its release statement starts after that commit.
**Example (executed on the lane, EXP-A; the fan-in section of `mark_compute_job_done`):**
```sql
-- Source: executed prototype, PG 16.13 pg-lane. Keep `parent_job_ids @> ARRAY[p_job_id]` (see Pitfall 6).
SELECT COALESCE(array_agg(c.id), '{}'::uuid[])
  INTO v_kids
  FROM compute_jobs c
 WHERE c.status = 'done_pending_children'
   AND c.parent_job_ids @> ARRAY[p_job_id]::uuid[];

IF cardinality(v_kids) > 0 THEN
  PERFORM public._fan_in_lock_rows(v_kids, TRUE);      -- statement 1: locks, (depth, id) order

  UPDATE compute_jobs c                                -- statement 2: fresh snapshot after the lock
     SET status          = 'pending',
         next_attempt_at = now()
   WHERE c.id = ANY(v_kids)
     AND c.status = 'done_pending_children'
     AND NOT EXISTS (
       SELECT 1 FROM compute_jobs p
        WHERE p.id = ANY(c.parent_job_ids)
          AND p.status <> 'done'
     );
END IF;
```
Measured (EXP-A2, `[VERIFIED: lane]`): today's body: `b_waited=f releases(dpc->pending)=0 ... child status=done_pending_children`; with the prototype: `b_waited=t releases(dpc->pending)=1 ... child status=pending`. The function must stay VOLATILE (the default) and the database READ COMMITTED (see A1).

### Pattern 2: the ancestor-first lock helper (D-06)
**What:** one private function, called by all three paths, so the order cannot drift between them.
```sql
-- Source: executed prototype (the ELSE branch is identical with FOR SHARE OF j). The cycle guard `lvl < 64` bounds a corrupt graph.
CREATE OR REPLACE FUNCTION public._fan_in_lock_rows(p_ids uuid[], p_for_update boolean)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
DECLARE r record;
BEGIN
  IF p_ids IS NULL OR cardinality(p_ids) = 0 THEN RETURN; END IF;
  IF p_for_update THEN
    FOR r IN
      WITH RECURSIVE walk(root, parents, lvl) AS (
        SELECT j.id, j.parent_job_ids, 0 FROM compute_jobs j WHERE j.id = ANY(p_ids)
        UNION ALL
        SELECT w.root, a.parent_job_ids, w.lvl + 1
          FROM walk w JOIN compute_jobs a ON a.id = ANY(w.parents) WHERE w.lvl < 64
      ), depth AS (SELECT root AS id, max(lvl) AS d FROM walk GROUP BY root)
      SELECT j.id FROM compute_jobs j JOIN depth ON depth.id = j.id
       ORDER BY depth.d, j.id
         FOR UPDATE OF j
    LOOP NULL; END LOOP;
  ELSE
    -- same query, FOR SHARE OF j
  END IF;
END
$$;
REVOKE ALL ON FUNCTION public._fan_in_lock_rows(uuid[], boolean) FROM PUBLIC, anon, authenticated;
```
`depth` = length of the longest chain of ancestors reached through `parent_job_ids`, so a parent always sorts before its child. The lock is acquired in output order because the `LockRows` node sits above the `Sort` node. The `REVOKE` is mandatory: Supabase's default-privilege event trigger grants EXECUTE on new public functions to anon/authenticated (`20260515130001` records it), and a callable lock helper is a queue-wide denial-of-service lever. Assert the denial in the migration's self-verify block with `has_function_privilege`.

### Pattern 3: transitive failure cascade, level by level (D-01..D-03)
See the "D-01..D-03" section for the full body. Each level is: plain `SELECT` of the next frontier, then `_fan_in_lock_rows(kids, TRUE)`, then one `UPDATE ... RETURNING` that becomes the next frontier. Do NOT write the descendant closure as one recursive-CTE `UPDATE`: a child enqueued by a transaction that holds a parent's share lock is invisible to the statement snapshot, which re-creates the strand. Lock level N, then read level N+1 in a new statement.

### Anti-Patterns to Avoid
- **Plain `ORDER BY id` anywhere in the fan-in locks.** Executed and refuted: it still deadlocks (EXP-B diamond, EXP-D transitive cascade). Pure id order is not a valid reading of D-06.
- **`min(uuid)`**: no such aggregate on PostgreSQL 16.13 (`42883 function min(uuid) does not exist`, hit in the first prototype). Pick the parent with `(SELECT x FROM unnest(...) x WHERE x = ANY(v_frontier) ORDER BY x LIMIT 1)`.
- **A sweep or cron for stranded children** (excluded by D-02), **a 40P01 retry loop** (excluded unless the deadlock were inherent; it is not), **deleting or merging outcome rows** (excluded by D-05).
- **Editing an older migration.** Existing mutation twins edit the byte text of `20260924230827_fanin_initial_status_10param.sql`, `20260926120000`, `20261001120000`, `20261003120000`; changing those files redden their gates. Add a new file.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Two parents releasing a child once | A counter column, a status flag, or application-side coordination | The child row lock + a later-statement re-read of the parents (Pattern 1) | The row lock is the serialisation primitive; a flag has the same read-skew |
| Deadlock avoidance | A 40P01 catch-and-retry in plpgsql, or a retry in the worker | One lock-order helper used by all three paths (Pattern 2) | Order is provable; retry is not, and PostgREST 14 already retries 40P01 unboundedly (`164.9.3.2-RESEARCH.md` lines 62, 239) |
| Descendant discovery for the cascade | One recursive CTE that selects and updates | Level-by-level lock-then-read (Pattern 3) | Snapshot staleness (see Pitfall 3) |
| Operator-visible failure text | A new error kind or a new column | `last_error` (operator) + inherited `error_kind` (drives user copy) | `computation_error_copy` derives all user copy from `error_kind`; `sync_strategy_analytics_status` is forbidden to read `last_error` (H1 anchor in `20260826120000`) |
| Observing "exactly one release" in a gate | Counting rows or timing | A gate-installed `AFTER UPDATE OF status` trigger logging `(id, old, new)` to a committed table, then `count(*) WHERE old='done_pending_children' AND new='pending'` | Deterministic and independent of timing |

**Key insight:** every defect here is a lock-protocol defect, and the repo already has the machinery to prove locks (dblink + `pg_locks` + gate-installed triggers). Do not invent timing-based tests.

## D-06: the diamond deadlock (Q4), proved and refuted by execution

**Concrete interleaving (EXP-B, deterministic, `[VERIFIED: lane]`).** Jobs: A running; B a waiting child of A with `id(B) < id(A)`; the enqueue of a new child C with parents `[B, A]`.
1. Backend m runs `mark_compute_job_done(A)`: `UPDATE` of A (holds A exclusively), then stalls (the gate parks it on a transaction-scoped advisory lock inside a gate-installed `AFTER UPDATE` trigger on A, so the stall is order-independent).
2. Backend e runs the enqueue: `FOR SHARE ... ORDER BY id` takes B (free) and then waits for A (held by m).
3. m resumes into its fan-in `UPDATE` of A's children and needs B, which e holds. Cycle. After `deadlock_timeout` one side dies: `EXP-B RESULT e=[40P01 deadlock detected]`.

**Why a single global order "by job id" is not achievable.** The mark paths discover a finishing job's children only AFTER they hold the job: a concurrent enqueue naming the job holds its share lock until commit and its child row becomes visible only then, so the child set is complete only once the job's own lock is held. The mark paths are therefore forced to lock parent-before-child, whatever the ids are. Any total order consistent with that has the parent before its child. A pure id order contradicts it for half of all random UUID pairs. Executed: with the helper switched to `ORDER BY j.id` the diamond still deadlocks (EXP-B: `e=[40P01 deadlock detected]`) and so does the transitive cascade (EXP-D: `e=[40P01 deadlock detected]`).

**The order that works, and why it is provably acyclic.** Key `(depth, id)`, depth = longest ancestor chain. Every path acquires its fan-in row locks in ascending key: enqueue locks its parent set in key order; `mark_compute_job_done` locks its own row (depth d), then its children (depth > d) in key order; `mark_compute_job_failed` locks its own row, then each BFS level (depth strictly increasing) in key order. A wait-for cycle needs two transactions that acquired a pair of rows in opposite order; all of them acquire ascending, so none exists. Advisory locks come strictly after all row locks; the bridge takes no row locks; claim, reclaim, reset and the reaper are `SKIP LOCKED`. Executed green: EXP-B on the prototype `e=[ok]`, EXP-D on the prototype (`m=[ok]`, B and D `failed_final` each naming its own parent, enqueue refused with 22023 because both parents are failed, no deadlock). So the deadlock is NOT inherent and the 40P01-retry fallback is not needed.

**Statement for the CONTEXT record (deviation policy).** D-06's mechanism is "one global order by job id". The executed finding is that the order must be ancestor-first with job id as the tie-break. Record this as a clarification of D-06 in CONTEXT.md and the ROADMAP section (CLAUDE.md global rule: a deviation is recorded where the project tracks decisions), because the planner's gate twins and the migration header will quote the key.

**Context that lowers urgency but not the fix.** PostgREST 14.x retries `40P01` (and `40001`) without bound, so a deadlock victim reached through PostgREST is re-run and converges [CITED: `.planning/phases/164.9.3.2-defer40001-.../164.9.3.2-RESEARCH.md` lines 62 and 239]. PostgREST 16 removed the retry, so after an upgrade a deadlock would surface as an HTTP 500 (`164.9.3.2.1-RESEARCH.md` line 62). And the in-database fan-out callers (pg_cron SQL functions that call `enqueue_compute_job`) are not behind PostgREST at all.

## Common Pitfalls

### Pitfall 1: a plain id order "fixes" nothing
**What goes wrong:** `ORDER BY id` in the helper still deadlocks (EXP-B, EXP-D).
**Why:** parent-before-child is forced on the mark paths (see D-06).
**How to avoid:** the key is `(depth, id)`; the gate twin that reverts the helper to `ORDER BY j.id` must go RED on the diamond arm.
**Warning signs:** a 40P01 in a gate or in `pg_stat_database.deadlocks` after the change.

### Pitfall 2: lock and decide in one statement
**What goes wrong:** the `NOT EXISTS` still reads the statement-start snapshot and the lost release returns.
**How to avoid:** lock in a prior statement (Pattern 1). Do not mark the function STABLE; do not run it under REPEATABLE READ.

### Pitfall 3: descendant closure in one recursive UPDATE
**What goes wrong:** a child inserted by a transaction that holds a parent's share lock is missing from the statement snapshot; the cascade misses it and re-creates the strand.
**How to avoid:** level by level, lock then read.

### Pitfall 4: forgetting the child strategy's bridge
**What goes wrong:** the child job is terminal but the strategy still reads "computing" (EXP-E on today's body). **How to avoid:** bridge every affected strategy, advisory locks in one sorted order.

### Pitfall 5: ACL on the new helper
**What goes wrong:** the default-privilege event trigger hands EXECUTE to anon/authenticated; a caller could take row locks and stall the queue. **How to avoid:** `REVOKE ALL ... FROM PUBLIC, anon, authenticated` and assert with `has_function_privilege` in the migration's verify block; no service_role grant is needed (only definer functions call it).

### Pitfall 6: existing gates that pin the mark body
`supabase/tests/test_compute_jobs_rpc_error_clear_and_fanin.sql` Part 1 (runs on the local-stack `sql-tests` lane against the FINAL bodies) asserts `v_done !~* 'parent_job_ids\s*@>\s*ARRAY\[\s*p_job_id'` raises and `v_done ~* 'FOR\s+v_child_id\s+IN'` raises (`:44-49`). Keep `c.parent_job_ids @> ARRAY[p_job_id]::uuid[]` in the new body and never name a loop variable `v_child_id` (the prototype uses `v_kids` and `r_b`). No gate in `supabase/tests` or `src/__tests__` pins `FOR SHARE` text.

### Pitfall 7: sorted-lock helper but unsorted advisory locks
Bridging more than one strategy in a cascade without sorting by the lock key re-introduces a deadlock on the advisory locks.

### Pitfall 8: data-reading verify block
The migration's `DO` block may read catalogs only (`pg_get_functiondef`, `pg_proc`, `pg_index`, `pg_constraint`, `has_function_privilege`, `to_regprocedure`); never `compute_jobs` or `bridge_outcomes` rows.

### Pitfall 9: `SET LOCAL` and transaction style
