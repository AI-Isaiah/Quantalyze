## Answers to the brief

### Does the 55P03 path leave the job recoverable?

**Yes.**

- **The 55P03 rolls back the whole RPC.** The RAISE at the bound is in the outer `LOOP` of `mark_compute_job_failed`, outside the `BEGIN … EXCEPTION WHEN SQLSTATE 'FI001'` block. It therefore aborts the whole top-level transaction, which includes the job's own `UPDATE … SET status = v_new_status`. The row stays `status='running'` with its `claimed_at` and `claim_token` unchanged. FL8 proves this on the real body: F reads `running` with a byte-identical `to_jsonb` image.
- **No lease or heartbeat is involved.** `reset_stalled_compute_jobs` selects on `status='running' AND claimed_at < now() - threshold` only. The worker's `_heartbeat` task (`main_worker.py` around line 950) writes `main_worker_healthz.LAST_TICK_AT` only, never the database, and it is cancelled before the mark. Nothing the worker keeps or drops affects reclaim. The row is reclaimed `claimed_at + threshold` after its claim: 10 minutes by default, and the per-kind override where `WATCHDOG_PER_KIND_OVERRIDES` sets one, for example 30 minutes for `derive_broker_dailies`. The reclaim nulls `claim_token` and resets the row to `pending`.

### Could the job re-hit the bound forever (livelock across reclaims)?

**No, not by construction.**

- Each reclaim cycle is at least one watchdog threshold apart, so the loop cannot spin.
- Each cycle trips the bound only if an enqueue commits a new descendant inside the lock window on 10 consecutive attempts.
- Neither the watchdog nor the cascade generates such enqueues. `_enqueue_compute_job_internal` is the only writer of `parent_job_ids`.
- `claim_compute_jobs_with_priority` does not gate on `max_attempts`, so the number of cycles has no hard cap. That holds only for a workload that keeps committing children under the same closure at sub-millisecond spacing, every cycle. Nothing in the tree does that.

**Recorded below the brief's threshold, as a design fact rather than a finding.** Recovery re-runs the handler from scratch after the stall window, and the strategy reads `computing` until then. A bounded in-worker retry of the same `_mark_failed` call (the claim token is still valid) would recover in seconds without a re-run. The path is a tripwire, and PROD holds no parented jobs, so I am not raising it.

### Is `exc.code` the right attribute?

**Yes.**

- `_is_lock_bound_failure` uses `getattr(exc, "code", None)`, the same shape as `_is_serialization_failure` (55006) and `_is_undefined_function_structured` (42883).
- `db_execute` runs the call in `_DB_EXECUTOR` and re-raises the `postgrest.exceptions.APIError` unchanged. It has no wrapping and no retry.
- PostgREST passes the RAISE's `ERRCODE` through as the JSON `code` string, so `"55P03"` compares equal as a string.
- The new test builds `APIError({"code": "55P03", …})`. I ran it from `analytics-service/` (`1 passed`), and it is not among the file's skipped tests.
- Under the pre-fix code the test would see two `mark_compute_job_failed` calls, so its `len(fail_calls) == 1` assertion can fail.

### Can another 55P03 be misrouted through this branch?

**Not to any wrong state.**

- The `try` wraps only `_safe_mark(_mark_failed, …)`, which issues the single `mark_compute_job_failed` RPC.
- That function and everything it calls (`_fan_in_lock_rows`, `pg_advisory_xact_lock`, `sync_strategy_analytics_status`) carries no `SET lock_timeout` and no `NOWAIT`. The `SET lock_timeout = '3s'` functions in `baseline.sql` (wizard, api-key delete and equity-snapshot RPCs) are not on this path, and `mark_compute_job_done` and the enqueue raise no 55P03.
- Suppose a role-level `lock_timeout` were ever added. Its 55P03 would also abort the whole RPC and leave the job `running`, so the handling would still be correct. Only the ERROR text ("lock-retry bound") would name the wrong cause.
- Any other SQLSTATE still reaches `raise` and the existing catch-all, which is unchanged behaviour.
- The dispatch-crash fallback (`_mark_failed_fallback`) is not routed through the new branch. A 55P03 there lands in the existing "mark_failed also raised" pair of ERROR lines and also leaves the job `running`.

### Does FL8 restore the real helper on every exit path?

**Yes, on every exit path that matters.**

- **Assertion failure (the arm's normal RED path, and its twin).** The restore `DO` block runs before the ASSERT block, so an assertion failure happens after the real helper is back.
- **Errors inside the mark.** The RACE block catches every mark error (`EXCEPTION WHEN OTHERS` around `dblink_get_result`) and stores it in `m_state`. A wrapper or dblink error inside the mark therefore also reaches the restore.
- **Errors before the restore.** These paths leave the wrapper installed:
  - the RACE block's `FL8-SETUP` RAISEs;
  - a failed `dblink_connect('fl_m')`;
  - a failure between the top-level `ALTER … RENAME` and the `CREATE FUNCTION` (two separate autocommit statements).

  In each case `psql -v ON_ERROR_STOP=1` (`scripts/pg-lane/run.sh` `psqlq`) stops the file at that statement. FL8 is the last arm before the epilogue, so no later arm in the file runs.
- **No leak to other files.** The file is LANE-ONLY (header line 123), so the local-stack `sql-tests` lane excludes it. Each mutation-runner lane is its own throwaway cluster: `runLane` spawns `pg-lane/run.sh` per invocation with a runner-allocated distinct port, and the cluster is torn down on EXIT. Concurrent lanes (`LANE_CONCURRENCY_CAP` 4) never share a database, so the rename cannot poison another file or a later arm leg.

### Is FL8 itself sound?

**Yes.**

- **Exactly 10 children.** The `FI001` subtransaction rollback releases the closure locks but not the child that dblink committed. Attempt k locks `{A, X1..X(k-1)}`, commits Xk and re-reads `{A, X1..Xk}`, so attempt 11 raises 55P03 with exactly 10 children born.
- **The twin bites.** Under the twin (`IF FALSE THEN`, with the anchor at `:1589` stood down), the 12 spare strategies run out. Attempt 13 then finds a stable closure, the cascade commits, and `m_state` is NULL, which reddens FL8 by name.
- **The find strings match once.** `grep -cF` returns 1 for both twin find strings in the migration.
- **The marking backend uses the wrapper.** The `fl_m` connection is a fresh backend, so its PL/pgSQL plan resolves `public._fan_in_lock_rows` to the wrapper. The restore drops the wrapper and renames the original OID back, which keeps its `REVOKE`.
