## Corrections to the brief (read before planning)

1. **The "orphan reaper function" is not a function.** It is an INLINE pg_cron job body, `retention_compute_jobs_orphaned_running`, registered by `cron.schedule(...)` with a `$cron$ ... $cron$` literal wrapping a `DO $sweep$ ... $sweep$` block. Earlier registrations: 20260719120000, 20260720120000, 20260817120000. There is no `supabase/schema/functions/*.sql` mirror for it, no signature, no `CREATE OR REPLACE FUNCTION`. "Re-basing" it means `cron.unschedule` + `cron.schedule` again (fresh jobid on every apply), and it drags in the consumers listed under "Reaper blast radius" below.
2. **`test_enqueue_race_loss_40001.sql` is NOT a dblink gate.** Its header says "One in-transaction `BEGIN; DO $$ ... $$; ROLLBACK;`, no dblink" (line 38). It is a single-session gate that induces a race with gate-installed triggers. Only TWO dblink gates exist in the corpus: `test_mark_rpc_bridge_advisory_lock.sql` and `test_sync_status_bridge_lock.sql`. Neither captures a REMOTE ERROR (they only wait on locks and call `dblink_get_result` bare), so gate B has no analog for catching 40P01 off a dblink backend (see "No Analog Found").
3. **One migration means every gate's apply list needs the whole chain.** The new migration does `ALTER TABLE public.bridge_outcomes ADD COLUMN ...`, re-creates the index, and re-bases the compute-job RPCs. So gates A, B and C ALL need fixture 40 (bridge_outcomes/match_decisions stand-in) plus the compute_jobs/bridge chain before the migration, not just gate C.
4. **Fixture number 40 is free** (`ls scripts/pg-lane/fixtures` ends at 39; note there are TWO `36-*` files, `36-fixture-compute-jobs-claim-token.sql` and `36-fixture-dblink.sql`, so numbers are not unique keys; re-check at execution).
