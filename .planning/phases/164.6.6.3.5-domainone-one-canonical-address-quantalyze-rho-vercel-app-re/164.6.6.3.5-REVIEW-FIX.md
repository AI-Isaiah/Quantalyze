### WR-01 / F1: a skipped founder email is recorded as not sent

**Commit:** `1728a5839` `fix(164.6.6.3.5): WR-01 a skipped founder email is recorded as not sent`

**What changed**

- `src/lib/email-skip.ts` (new): `EmailSkippedError`, an `Error` subclass carrying a `reason`
  (`resend_not_configured` or `platform_email_not_configured`). It lives in its own module so the
  route can `instanceof`-check it without importing `email.ts`, and so route tests that mock
  `@/lib/email` wholesale still see the real class.
- `src/lib/email.ts`: `send()` takes a new opt-in `throwOnSkip` (default `false`). Both skip
  branches (no Resend client, no `PLATFORM_EMAIL` sender) now throw `EmailSkippedError` when
  `throwOnFailure || throwOnSkip`. The message text is byte-identical to what `throwOnFailure`
  callers already received, so the approve routes see no change. `notifyFounderGeneric` takes
  `{ throwOnSkip }` as a third argument and passes it through. No default flipped; every other
  caller behaves as before.
- `src/app/api/for-quants-lead/route.ts`: both `notifyFounderGeneric` calls (`request_call` and
  `contact_form`) pass `{ throwOnSkip: true }`. The existing `catch` recognises
  `EmailSkippedError` and writes the fixed `notify_error` text
  `Founder email not sent: Resend or PLATFORM_EMAIL not configured`, leaves
  `notify_succeeded_at` unwritten, and reports to Sentry once per process with a module-scope
  `founderNotifySkipWarned` guard (mirroring `founderEmailMissingWarned`), as a
  `founder_notify_skipped` message. A skip does NOT go through the per-lead
  `captureException(…, "founder_notify")` path; real send failures still do. The client response is
  unchanged: `{ ok: true, status: "stored" }`.

**Tests** (RED first, then GREEN)

- `src/app/api/for-quants-lead/route.founder-skip.test.ts` (new, uses the REAL `email.ts` with Resend
  unset): RED **4 failed / 1 passed** against the old code (the one pass is the configured-send
  control, which must stay green). Covers `request_call` and `contact_form` with no Resend client,
  the no-`PLATFORM_EMAIL` branch, Sentry once across two leads with both rows still marked, the
  client response unchanged, and the configured send still writing `notify_succeeded_at`.
- `src/lib/email.test.ts`: one new case, `notifyFounderGeneric` is silent by default and throws
  `EmailSkippedError` with `throwOnSkip`, for both skip causes.
- GREEN: `src/app/api/for-quants-lead` + `src/lib/email*` = 4 files, 117 tests passed.

### D-17: unread badge on the admin sidebar entry

**Commit:** `38735bbf5` `feat(164.6.6.3.5): D-17 an unread badge on the admin For-quants leads entry`

**What changed**

- `src/lib/for-quants-leads-admin.ts`: `countUnprocessedForQuantsLeads(client?)`, a
  `select("id", { count: "exact", head: true }).is("processed_at", null)` through the existing
  service-role chokepoint. No row data is fetched. It returns `number | null`; any error, missing
  count or thrown client logs `[for-quants-leads-admin] unprocessed count …` and returns `null`,
  never `0`.
- `src/app/(dashboard)/layout.tsx`: after `isAdmin` is final (profile flag or claim-set check), and
  only then, reads the count; `null` becomes `undefined`. Non-admins never reach the read. Passed to
  `DashboardChrome` as `unprocessedLeadsCount`.
- `DashboardChrome.tsx` forwards it to the desktop `Sidebar` and to both `MobileSidebarDrawer`
  mounts (standard and full-bleed branches); `MobileSidebarDrawer.tsx` forwards it to its `Sidebar`.
- `Sidebar.tsx`: the existing `badge` mechanism on the `For-quants leads` item. Same pill classes as
  the flagged-holdings badge (`bg-accent`, `text-fixed-10`, white text, `rounded-sm`) and the same
  `99+` cap; a new optional `badgeLabel` gives the accessible name `N unprocessed lead(s)`
  instead of the hard-coded flagged-holdings wording. The entry lives in the ADMIN section, so a
  non-admin cannot see the badge even if handed a count. The mobile bottom nav carries no admin
  entries and is unchanged.

**Tests** (RED first, then GREEN)

- `for-quants-leads-admin.test.ts`: RED 5 failed (helper did not exist); GREEN 21/21. Pins the query
  shape (`from`, head count `select`, `is processed_at null`), 0, error, missing count and thrown
  client.
- `Sidebar.test.tsx` and `DashboardChrome.test.tsx`: RED 6 failed (4 + 2); the unknown-count,
  zero and non-admin cases pass trivially before the change, by design. GREEN: `src/components/layout`
  6 files, 117 tests passed.
- `src/app/(dashboard)/layout.unprocessed-leads.test.tsx` (new, real helper over a stubbed admin
  client): RED 5 failed / 1 passed (the non-admin case). Admin with N>0, admin with 0, claim-set
  admin, non-admin triggers no count read, failed read gives no count and logs, thrown admin client
  gives no count and logs. Neutered check: forcing the admin guard open turned the non-admin case
  RED; restored from a byte backup.

**Known limit:** a layout is not re-rendered on soft navigation, so the number updates on a full
load or `router.refresh()`. `ForQuantsLeadsTable` already calls `router.refresh()` after every
process/unprocess toggle, so working the queue keeps the badge honest. A lead that arrives while the
founder sits on one page appears at the next load. No polling was added (not asked for).
