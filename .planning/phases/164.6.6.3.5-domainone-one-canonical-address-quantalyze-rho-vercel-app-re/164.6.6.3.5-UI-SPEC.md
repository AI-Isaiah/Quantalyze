### Prefill (how the id reaches the form — D-02: both prefill AND paste)

- **Prefill.** `ref`, `draft` and `strategy` are each accepted only when they match `^[A-Za-z0-9_-]{8,64}$` (the charset `/api/for-quants-lead` already enforces on `wizard_session_id`; UUIDs and `cid-…` tokens match). A value that fails is dropped silently from the prefill (the field is not filled with it, nothing is echoed). This keeps the page from reflecting arbitrary text from a link.
- **Composition**, single-space separated, in this order, only the present parts: `<ref>`, `draft <draft>`, `strategy <strategy>`. Examples: `3f1c…` · `3f1c… draft 9a2e…` · `strategy 77b0…`.
- **Paste.** The Reference field stays editable. A user who arrived without a link, or whose prefill was dropped, pastes the id from the Diagnostics block. The Message field accepts a pasted "Copy diagnostics" block (2000 characters is above the block's usual size; if a block exceeds it, the `maxLength` stops the paste at 2000 and the server's "Message is too long" error never fires for a pasted block).
- The server re-validates: `reference` ≤ 200 characters, stored as text, rendered as React-escaped text in the CRM and HTML-escaped (`escapeHtml`) in the founder notification. It never renders as HTML.

### States

| State | Render |
|-------|--------|
| Idle, no params | Topic `General question`; all fields empty |
| Idle, from a pointer | Topic preselected; Reference prefilled in Geist Mono |
| Submitting | Button disabled, label `Sending...` (the existing `RequestCallForm` label); a second click is a no-op (ref gate) |

| Unreadable submission (400 with no `fieldErrors`, e.g. `Invalid JSON body`; 400 whose `fieldErrors` keys are ALL ones this form does not draw; or 413) | One fixed form-level alert (Copywriting row "Error — unreadable"); entries kept. Field notes for drawn fields, if any, still render |
| Form error (429 / 500 / 503 / network) | One `<p role="alert" class="text-caption text-negative">` directly above the button row; every entry kept; button re-enabled |
| Success | Rendered **only** when the route confirms a row was written (see **Success means stored**). The form is replaced in place (left-aligned, no icon, no tinted circle): H2 `Message received` (`tabIndex={-1}`, receives focus), body sentence, the reference echo when present, then secondary `Button` `Send another message` which restores an empty form with the same Topic. The success region is `role="status"` |

### Success means stored (binding)

Measured at HEAD: `for_quants_leads_email_day_uniq` (migration `20260604120000_for_quants_leads_email_day_unique.sql`) is unique on `lower(email)` + UTC day, and the route answers a 23505 with `{ ok: true }` and stores nothing. If contact messages shared that store unchanged, a second message the same day, any "Send another message", or a security report sent after a call request would all show `Message received` while nothing reached the CRM. That is a false success.

The contract:

1. **A contact-form submission is never deduplicated.** Every accepted contact message writes its own row. The mechanism is the planner's call (for example, scope the per-day unique index to request-a-call rows, or give contact messages their own table). Either way it is a **migration**, so the repo's migration-review gates (migration-reviewer + rls-policy-auditor clean before merge, apply-on-merge to TEST then PROD) apply. Before any `CREATE OR REPLACE` or index change, re-base on the latest definition across all migrations.
2. **The route tells the client what happened.** A response the client treats as success must be distinguishable as one of: `stored` (a row was written) or, for request-a-call only, `duplicate` (an earlier request from this email today is already on record). The exact field name is the planner's.
3. **`ContactForm` renders `Message received` only on `stored`.** Any other 2xx shape (including a bare `{ ok: true }`) is treated as the 500 case and shows `Error — server`, so a route regression cannot produce a false success.
4. **`RequestCallForm`** keeps its existing success view on `stored`. On `duplicate` it shows the verbatim **Request-a-call duplicate** copy below instead of claiming this submission was received.
5. **Honeypot.** A bot drop answers exactly like `stored` (same status, same body shape), so a bot cannot tell it was dropped. No human reaches that path: the `website` field is off-screen, `aria-hidden` and `tabIndex={-1}`. This is the only response shaped as `stored` that wrote no row, and it is deliberate.

## S2 — Pointer rendering rule (every surface)

One rule, applied everywhere: **a pointer is a sentence that contains the exact substring `contact form`, and that substring is a link to `contactHref(...)`.** No surface prints a URL or an address as text; no surface links any other words.

| Host | How the link is rendered | `href` | Opens |
|------|--------------------------|--------|-------|
| `ErrorEnvelope` `cause` and each `debug_context` bullet | `ContactPointerText` | `contactHref({ topic: "support", ref: envelope.correlation_id, draft })`, where `draft` comes from a new optional prop `contactDraftId?: string \| null` that wizard hosts pass (`strategyId`); other hosts omit it | new tab |
| Wizard steps (`MetadataStep` errors, `ConnectKeyStep` / `MultiKeyConnectStep` trust panel body) | `ContactPointerText` or a direct `<Link>` in JSX | `contactHref({ topic: "support", ref: wizardSessionId, draft: strategyId })` where available; trust panels use `contactHref({ topic: "security" })` | new tab |
| Status surfaces (S4) and key card (S5) | `ContactPointerText` over the copy constant (works for `before`/`after` segments too, so a remedy that already has an `edit page` link gains a second link without a new slot) | `contactHref({ topic: "support", strategy: strategyId })` | same tab |
| `/security`, `/legal/privacy`, `/pending-approval`, `/for-quants` | Direct `<Link>` / `<a>` in JSX, using the page's existing link class | `topic=security` (security, for-quants), `topic=privacy` (privacy), `topic=general` (pending-approval) | same tab |
| `RequestCallModal` and the lead route's error strings | No link (the user is already in a form) | — | — |

- **Why new tab for the envelope and the wizard:** those surfaces hold unsaved state (an open dialog, a wizard step). A same-tab navigation to `/contact` would discard it. Everywhere else the user loses nothing.
- **New-tab accessibility:** visually hidden ` (opens in a new tab)` inside the link, so the accessible name is "contact form (opens in a new tab)".
- **Fallback when no id exists:** `contactHref` omits the param; the sentence must not then promise an id. The copy shapes below are written so the same sentence is true with or without a prefilled reference ("the correlation id below" is always on screen in the envelope's Diagnostics block, so the paste path always works).
- `ErrorEnvelope` adds no button and no new row. The Diagnostics `<details>` stays collapsed and unchanged.

| Outcome | `ContactForm` | `RequestCallForm` |
|---------|---------------|-------------------|
