## ⭐ THE FINDING THIS BATCH BOUGHT — a stand-in can PREVENT the object under test from existing

`scripts/pg-lane/fixtures/02-fixture-sanitize-tables.sql:30` declares

```sql
CREATE TABLE IF NOT EXISTS user_notes            (user_id UUID);
```

Its purpose is honest — `sanitize_user` deletes from `user_notes`, so the stand-in gives that body a
target. But `supabase/migrations/20260412094453_user_notes.sql:31` creates the REAL table with
`CREATE TABLE IF NOT EXISTS` as well. With the stand-in applied first, the real statement is a
**no-op**, and the migration then dies at `:44` on `ERROR: 42703 column "content" of relation
"user_notes" does not exist`.

That failure is loud, so the lane never went green and nothing was annotated against a phantom
table. The point is what it generalises to: **plan 06 measured a stand-in that made an arm
unfalsifiable; this one would have made the object the arms name absent entirely** — and if the
migration's own first statement had been `ALTER TABLE … ADD COLUMN IF NOT EXISTS` rather than a

object a listed migration creates, ask which one wins. `IF NOT EXISTS` means the fixture does, and a
fixture written for a different subsystem's needs is not the object under test.

## ⭐ THE SECOND FINDING — an arm's conjunct can be shadowed by a DIFFERENT object's RLS

`funding_fees_read`'s predicate is `EXISTS (SELECT 1 FROM strategies s WHERE s.id =
funding_fees.strategy_id AND s.user_id = auth.uid())`. The obvious surgical mutation for Assertion 2
(cross-tenant read denial) is to drop the `AND s.user_id = auth.uid()` conjunct. **MEASURED: NO-RED.**

The reason is that the policy's sub-select on `strategies` is ITSELF subject to `strategies`' own
RLS, which already hides tenant B's DRAFT strategy from tenant A. The conjunct is the binding
constraint only for a strategy the reader can ALREADY see — i.e. a PUBLISHED one — and this gate
seeds only `status='draft'`.

So the twin replaces the whole predicate with `true`, which the arm CAN observe, and the measurement
is written into the arm's own prose. The residual — that the gate cannot distinguish
"`funding_fees_read` is owner-scoped" from "`strategies_read` is owner-scoped" — is a COVERAGE gap in
the gate, not a defect in the twin, and adding the seed that would close it is adding an arm, which
this phase may not do. Booked to `deferred-items.md`.

A third, smaller instance of the same shape: `test_user_notes_dashboard_scope.sql` Assertion 4's
forge is refused by the `user_notes_unique_multiscope` UNIQUE index BEFORE the INSERT policy's
`WITH CHECK` can be observed, because B forges at A's existing `(user_id, scope_kind, scope_ref)`

## Decisions Made

See `key-decisions` in the frontmatter. The three most consequential for later batches:

- **Ask which object a same-named fixture and migration produce.** `CREATE TABLE IF NOT EXISTS`
