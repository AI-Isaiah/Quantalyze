- **What is "an arm":** one `RED-UNDER-M` object per NAMED assertion group — the `"arm":"NAME"`
  field — matching the one annotated file today (31 `RED-UNDER-M` objects covering 104
  `TEST FAILED (` raises). NOT one per raise.

  `<code_context>` § Correction.** The rule itself stands; the planner must re-derive the
  denominator from the corrected measurement, not from the "44 files" figure quoted during discuss.
- **Batch order:** by file, largest arm-count first. Each plan lands its files **fully** proven —
  no file left half-annotated.
- **Out of scope:** no new arms, no assertion edits. Anything the backfill reveals is booked to
  `TODOS.md`.

#### Waivers & un-falsifiable arms

- **`WAIVED_CEILING` (today 0):** raise ONLY by measurement, +1 per accepted waiver, each with its
  reason pinned beside the value in `run.mjs` — the same discipline `ARMS_FLOOR` already uses.
  Criterion 4 requires waivers to be recordable, so a hard 0 would make the phase unlandable on the
  first mechanically-unmutatable arm.
- **Where the reason lives:** inside the `RED-UNDER-M` object itself (GRAMMAR "Shape 4 — waiver"),
  so the runner PRINTS it every run. A separate ledger drifts; a printed one cannot.
- **An arm that cannot fail AT ALL is the FINDING, not an exception.** Record it, book the fix to
  `TODOS.md`. Do NOT bury a dead assertion behind a waiver. Waivers are for arms that DO bite but
  cannot be mutated mechanically.
- **Waiver volume:** more than 5 total → STOP and escalate to the founder rather than ratchet the
  ceiling. A rising ceiling is the failure mode the ceiling exists to catch.

#### CI budget & the coverage floor

- **Full-corpus run per PR — MEASURE FIRST.** Today 30 arms; the phase ends near 260, each needing
  mutate → run → assert RED → restore → assert GREEN. If a full run exceeds ~20 minutes, PRs run
  CHANGED gate files and a scheduled full run enforces the floors. **The split is PRINTED, never
  silent** — a runner that quietly covers a subset is exactly what criterion 3 forbids.
- **Floor ratchet:** at the end of EVERY plan, to the measured value. Ratcheting once at phase end
  lets a mid-phase regression pass unnoticed.
- **Coverage output:** keep the printed aggregate, ADD a per-file breakdown so a file stuck
  half-annotated is visible in CI output.
- **Tally cross-check:** `arms:` vs `lane-invocations:` stays a HARD `MEASURE_FAIL` at the new
  scale. It is the v0.77.1.0 control that catches arms CLAIMED but never run.

## Summary

Every headline number in CONTEXT re-measures exactly at HEAD: **71** gate files, **1398** `RAISE EXCEPTION` occurrences (grep -a, comments included) in **all 71** files, **890** of them in the `TEST FAILED (` idiom across **44** files, **27** files with no idiom raise carrying **334** raw / **321** code-level non-idiom raises. But the CONTEXT's framing undercounts the reachability gap: at code level the corpus has **1342** raises of which **888** are idiom and **454** are not — **174** of the non-idiom raises sit *inside* the 44 idiom files, where they are just as unreachable by the runner (verdict `NO-IDENTITY`, `run.mjs:2037-2049`) and, worse, un-neuterable (`neuterArm` needle is `TEST FAILED (${arm})`, `run.mjs:544`).

The runner's "arm" unit, measured on the reference file, is neither a raise nor a distinct identity: `test_strategy_shares_rls.sql` raises **103 distinct identities** in **35 sections** (prefix+number groups such as `SHAPE 2` = `SHAPE 2a`+`2b`) and carries **30** twins — and **15 of its 35 sections have no twin at all**. Criterion 1 is therefore unmet even in the one "annotated" file. Under the section unit the 44 idiom files hold **355** sections (320 outside the reference); under the distinct-identity unit, **516** (413 outside). The CONTEXT's "~230 further arms" is a ratio guess (890 × 30/104); the measured range is 320–413 + the reference's 15 missing sections.

Two costs the CONTEXT does not name dominate the phase. (1) **Every newly annotated file needs a `RED-UNDER-SETUP` apply list that goes GREEN on a vanilla-PostgreSQL lane** — the runner refuses a file without one (`run.mjs:1808-1811`) and refuses arms against a red baseline (`:1836-1876`). Today's fixtures are hand-built stand-ins for exactly two migrations (`scripts/pg-lane/fixtures/01-*.sql` 75 lines, `02-*.sql` 41 lines); the real migration chain dies at migration **10 of 262** on `storage.buckets` (probe this session), and 37 migrations reference `cron.`, 4 `net.`, 38 `auth.users`. (2) **Three vitest hard pins go RED on the first new annotation** (`mutation-annotation-parser.test.ts:608-609` `armsSeen 30`/`stepsSeen 49`, `:1317-1319` `filesAnnotated 1`; `mutation-runner-floors.test.ts:184` `totalAnchored 30`, `:196` `annotated.length === FILES_FLOOR` exactly) plus the exact-value registry `gate-family-meta.test.ts:835-842` — every batch PR must move all of them in lockstep.

**Primary recommendation:** Scope this phase, ON THE RECORD, to arms already in the `TEST FAILED (` idiom (44 files, 355 sections incl. the reference file's 15 un-twinned ones), print the 27 excluded files by name from the runner, and book the 454 non-idiom raises as a successor phase whose single job is a message-only rename into the idiom (option a) — it is not an assertion edit, but it is 454 identities that must be *invented* (139 distinct prefixes cover 321 raises: `B5b:` alone heads 28), which is authoring, not transformation. Reject option (b): the literal is the ONE identity definition (`run.mjs:947`) spelled in ~150 places across runner, parser, grammar and tests, and generalising it buys no precision because the prefixes are not unique per raise. Before the first annotation plan, spend one timeboxed plan measuring the fixture strategy (per-file stand-ins vs a stubbed real chain), because that decision sets both the effort and the per-lane CI cost of everything after it.

### Option (b) — a declared per-file identity prefix in the runner

**What identity is, precisely, at HEAD:** three independent legs in `judgeBlock` (`run.mjs:1162-1256`), none of which is the literal. Leg (a) file, leg (b) chain length + F1 field-order, leg (c) source-line resolution. The forgery closure of 164.3.1 (nonce → source location; F1 message-embedded fields) is stated over *where the database printed from* (`GRAMMAR.md:217-263, 309-328`). A declared prefix would change **what text is extracted as an identity**, not where it must come from — so on paper it is orthogonal to the forgery closure.

**What it would actually weaken / cost:**
1. Rule 3a (parse-time refusal to inject/target the literal, `parse.mjs:136-140, 172-174`) becomes "refuse to inject text matching a pattern the SAME author declares". The author of a hostile annotation also authors the pattern. 3a is explicitly "not the closure" (`GRAMMAR.md:149`), so this is a weakening of the cheap early check, not of the closure.
2. Rule 3b's unit — "the exact text from the head of the branch enclosing a `TEST FAILED (` raise" (`GRAMMAR.md:173-176`, `run.mjs:1409-1413`) — must be re-derived per file from the declared pattern; today's `failureBranches()` is corpus-agnostic.
3. `gateAttributionRecords`, `neuterArm`, the neuter-missed check, `describeExpectedRaise`, the `--parse-only` walk, the count-recheck prose in ci.yml, 15 `--self-test` scenarios (`run.mjs:2494-2900`) and ~95 vitest sites (`mutation-annotation-parser.test.ts` ×42, `mutation-runner-neuter.test.ts` ×25, …) all spell the literal. This is the fourth re-opening of a control that was re-opened four times in 164.3.1 (`GRAMMAR.md:96-104`: "Rule 3 has been 'closed' in three consecutive review rounds and re-opened in each of them by a re-spelling").
4. **It buys no precision.** With prefix `B5b:` heading 28 raises, an annotation `{"arm":"B5b"}` is satisfied by *any* of the 28 firing first — the proof degrades from "this raise bites" to "something in this group bites". To get per-raise identity you still have to edit the messages, which is option (a).
5. The corpus's own idiom is uniform: **all 888 idiom raises are single-frame direct DO-body raises with P0001** (see § Authoring rule audit) — the runner's strictness is what makes attribution decidable; a per-file grammar adds a second parser to keep sound.

**Does it reopen the forgery hole?** Not the source-location one (3c is unchanged). It does reopen the *3a re-spelling* class in a new form (the pattern is attacker-declared), and it removes the 3b protection from every non-idiom branch until 3b is re-derived. Verdict: orthogonal to 3c, weakening to 3a/3b, no precision gain. **Reject.**

### Option (c) — scope to the idiom, exclude explicitly, book the rename as its successor

## Runner mechanics the planner must design around

- **Lanes per file = 1 baseline + N arms + 1 restore.** Baseline `run.mjs:1836-1876`, per-arm `:1881-2095`, restore per file `:2097-2122`. Restore is NOT per arm. `[VERIFIED]`
- **Every lane is a fresh cluster:** `initdb -D "$PGD/data" -U postgres --auth=trust -E UTF8` then `pg_ctl … -o "-p $PORT -c listen_addresses=127.0.0.1 -k ''"`, roles `CREATE ROLE anon NOLOGIN; CREATE ROLE authenticated NOLOGIN; CREATE ROLE service_role NOLOGIN BYPASSRLS;`, then `for f in "${applies[@]}"; do psqlq -q -f "$f"; done` `[VERIFIED: run.sh:252-266]`. Lane time is therefore boot + apply-list + gate, multiplied by arms.
- **A gate without `RED-UNDER-SETUP` is a `parse` defect** ("no RED-UNDER-SETUP line — the runner refuses to guess a corpus", `run.mjs:1809`); exactly one per file (`parse.mjs:339`).
- **Mutation targets must be in the setup list:** `bad-file-ref` — "step targets X, which is not in this gate's RED-UNDER-SETUP apply list" (`run.mjs:1819-1830`). A mutation may edit the gate file itself (it is appended to `corpusRels`, `:1813`) but rule 3b refuses any edit that changes a failure branch (`:1484`).
- **Occurrences are measured, not trusted:** `occurrence-mismatch` is a MEASURE_FAIL and the mutation is not applied (`run.mjs:1928`; GRAMMAR rule 2).
- **Neuters absorb only an exact `RESET ROLE;`** before the raise and refuse unclassifiable cleanup on either side (`run.mjs:520-580`; `GRAMMAR.md:526-556`).
- **`--file`/`--arm` never exit 0** (`run.mjs:13`, `:2206-2207`) — there is no passing subset mode to build the CONTEXT's >20-min fallback on; it would be new work in `run.mjs` and `ci.yml`.
- **Tallies:** `armsExecuted === laneInvocations` exact, `biting ≤ armsExecuted` (`run.mjs:1577-1600`, `absurdity` defect), re-parsed by the CI count-recheck (`ci.yml:1060-1174`).

## Architecture Patterns

### System flow (one annotated file, one arm)

```
supabase/tests/<gate>.sql ──parseFile──▶ prose/twins/setup ──parity, 3a──▶ annotations
        │                                                                     │
        │  RED-UNDER-SETUP.apply + gate  ──materialize──▶ scratch slot (copies only)
        │                                                                     │
        ▼                                                                     ▼
  baseline lane: initdb → roles → apply[] → gate ──exit 0?──▶ else `baseline` defect, file skipped
                                                                              │
   per arm: copy → neuter[] (gate copy) → apply steps (edit/insert-after, occurrences measured; 3b byte-identical branches)
            → lane(apply[], --post-apply <sql steps>, gate) ──psql verbose output──▶ attributeIdentities (3c legs a/b/c, F1)
            → verdict: RED (identity ok) | NO-RED | NO-IDENTITY | WRONG-ARM | SYNTHESISED | MEASURE-FAIL
                                                                              │
  restore lane (pristine copies) ──exit 0?──▶ else `restore` defect            ▼
  git status --porcelain before == after ──▶ else `dirty-checkout`     coverage / arms / biting / lane-invocations / waived: → floors → exit code
```

### Pattern 1: annotate a section (the reference's shape)
```sql
-- Source: supabase/tests/test_strategy_shares_rls.sql:415-417 (GRAMMAR Shape 1)
  -- RED-UNDER: change `generation BIGINT` back to `generation INTEGER` in the
  --            STEP 1 CREATE TABLE.
  -- RED-UNDER-M: {"arm":"SHAPE 1c","apply":[{"kind":"edit","file":"supabase/migrations/20260827120000_strategy_shares_generation_model.sql","find":"generation  BIGINT","replace":"generation  INTEGER","occurrences":1,"nth":1}]}
```
Discipline: measure `occurrences` with `grep -a -o -F '<needle>' <file> | wc -l` BEFORE writing the twin (rule 2); the twin's `arm` must equal an identity string inside `TEST FAILED (…)` in THIS file; prose first, twin on the next line; markers at comment line start (rule 1).

### Pattern 2: live-DB mutation with a shadowing arm neutered
```sql
-- Source: supabase/tests/test_strategy_shares_rls.sql (GRAMMAR Shape 2, :440-456)
  -- RED-UNDER-M: {"arm":"NONCE 1b","apply":[{"kind":"sql","stmt":"GRANT UPDATE (nonce) ON strategy_shares TO authenticated"}],"neuter":[{"arm":"SHAPE 3b"}]}
```
Use when the migration pins the state exactly and an edit would abort the apply. Neuters can only name idiom arms.

### Pattern 3: waiver (form only — corpus has none)
```sql
-- Source: GRAMMAR.md:480-483 (illustration)
  -- RED-UNDER: none — a deleted `nonce` aborts the apply, so this arm can
  --            never be the FIRST failure.
  -- RED-UNDER-M: {"arm":"<ARM>","waiver":"a deleted nonce column aborts the apply; no first-failure mutation exists"}
```
Each accepted waiver = `WAIVED_CEILING + 1` with the reason beside the constant (CONTEXT) — and the twin's reason is what the runner prints.

### Pattern 4: per-plan floor ratchet choreography (every batch PR)
1. Annotate the batch's files fully; add each file's `RED-UNDER-SETUP`.
2. `node scripts/mutation-runner/run.mjs` locally → read `coverage:`, `arms:`, `biting:`, `lane-invocations:`, `per-arm lane time:` off the RUN.
3. Raise `FILES_FLOOR`/`ARMS_FLOOR` (and `WAIVED_CEILING` if a waiver was accepted) to the measured values with a dated `MEASURED … COMMAND … SAMPLE SIZE` block within 80 lines above each constant.
4. Move the registry strings (`gate-family-meta.test.ts:835-842`), the exact pins (`mutation-runner-floors.test.ts:184`, `mutation-annotation-parser.test.ts:608-609, 1317-1319`), and the prose sites listed above; raise `ci.yml:854` if the run is within ~3 min of it.
5. `npx vitest run src/__tests__/mutation-*.test.ts src/__tests__/gate-family-meta.test.ts` serially; `git status --porcelain` empty.
6. PR; require `sql-mutation` GREEN on ubuntu (SHA-bound: re-read `headRefOid`, per `reference_ci_green_must_be_sha_bound`) before the next batch.

### Anti-Patterns to Avoid
- **Mutating a stand-in fixture** — proves the fixture, not production. Refuse by convention (grep twins for `scripts/pg-lane/fixtures/`).
- **Mutating the failure message or its guard** — refused (3a parse-time, 3b apply-time) and, if it slipped through, vacuous. Mutate the code under test.
- **Renaming an identity in the reference file** — breaks `vac06-mechanism-arms.test.ts:244` and VAC06-DEMOS.
- **Choosing floors by reading the finished artifact** — "A floor picked by reading the finished artifact always passes" (`run.mjs:120-121`); read them off the run log.
- **A twin per raise** — the CONTEXT locks one per named group; a per-raise twin count (516/837) more than doubles lanes for no additional proof.
- **`git checkout --` to undo a mutation experiment** — destroys uncommitted work; the runner only ever touches scratch copies, so nothing needs undoing.

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: the first annotated file reddens vitest, not just the runner
**What goes wrong:** `sql-mutation` goes green locally; the `frontend` aggregator goes red on `mutation-annotation-parser.test.ts:1318` (`filesAnnotated` 1) and `mutation-runner-floors.test.ts:196` (exact equality).
**Why:** the pins are deliberate lockstep controls (drift in EITHER direction fails).
**Avoid:** Pattern 4 above, in the same PR. **Warning sign:** a PR that touches only `supabase/tests/`.

### Pitfall 2: a red baseline is a skipped file that still looks like progress
**What goes wrong:** a file whose setup list does not reach GREEN gets a `baseline` defect and `continue` (`run.mjs:1858-1876`) — its arms are never judged. `filesAnnotated` still counts it (`scanCorpus` counts markers, not verdicts).
**Avoid:** the CONTEXT's per-file breakdown must print per-file `judged/annotated`, so a file with 0 judged and N annotated is visible; the ratchet must be read off `biting`, never off `annotated`.

### Pitfall 3: a non-idiom raise fires first
**What goes wrong:** verdict `NO-IDENTITY`; the natural fix — neuter it — is impossible (`neuterArm` only knows the idiom).
**Avoid:** choose a mutation the non-idiom raise does not observe; otherwise a waiver with the reason naming the shadowing raise's line. Batch the 7 mixed files last.

### Pitfall 4: `occurrences` measured with one space, needle has two
**What goes wrong:** `occurrence-mismatch` MEASURE_FAIL — the reference's `generation  BIGINT` story (`GRAMMAR.md:69-87`).
**Avoid:** measure with `grep -a -o -F` against the exact file named in `"file"`; `--parse-only` counts every step against the pristine repo and layered steps forward (`run.mjs:2329-2440`), so run it before the full run.

### Pitfall 5: CI green that belongs to an older SHA
**What goes wrong:** a batch is declared landed on a green board from an ancestor commit.
**Avoid:** the CONTEXT's "GREEN on ubuntu before the next batch" must be SHA-bound (`gh run view --json headSha` matches the PR head), per memory `reference_ci_green_must_be_sha_bound`.

### Pitfall 6: the setup list and the mutation target disagree
**What goes wrong:** `bad-file-ref` — the twin edits a migration the setup never applies; or the mutation edits a migration the setup applies but the gate reads a *different* copy of the object (a later migration re-creates it).
**Avoid:** the setup list must contain the migration that LAST defines the object under test; mutate that one. `CREATE OR REPLACE` chains (memory `⭐Re-base SQL fn before CREATE OR REPLACE`) make this non-obvious — grep all migrations for the function name and list them in order.

### Pitfall 7: reading the CONTEXT's numbers as facts
**What goes wrong:** "31 objects / 104 raises / ~230 arms / 44 armless files" — three of the four are off (30 / 103 / 320–413 / 0 armless).
**Avoid:** every plan quotes its own commands; the plan-anchor-verify job re-resolves `file:line` anchors (`ci.yml`, `plan-anchor-verify`) so stale integers in a PLAN are already a CI failure.
