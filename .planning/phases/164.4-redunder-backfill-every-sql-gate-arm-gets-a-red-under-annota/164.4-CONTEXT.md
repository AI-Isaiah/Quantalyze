# Phase 164.4: REDUNDER-BACKFILL — every SQL gate arm gets a RED-UNDER annotation that a machine PROVES bites - Context

**Gathered:** 2026-09-02
**Status:** Ready for planning
**Mode:** Smart discuss (autonomous) — 4 grey areas, all accepted as recommended

<domain>
## Phase Boundary

Every arm in `supabase/tests/*.sql` carries a `RED-UNDER` prose annotation and its
machine-executable `RED-UNDER-M` twin naming the exact mutation that reddens it, and the Phase
164.3 mutation runner (`scripts/mutation-runner/run.mjs`) PROVES each one bites — RED under its
own mutation, GREEN when restored. Coverage moves from 1 file to the whole corpus behind floors
that cannot regress.

This phase **annotates and proves what already exists**. Writing new gate coverage is explicitly
out of scope (ROADMAP, Phase 164.4).

</domain>

<decisions>
## Implementation Decisions

### Landing & branch strategy

- **Base branch:** ship `phase-164.3.1-sound-primitives` FIRST (PR → land), then branch 164.4
  from `main`. Measured 2026-09-02: that branch is **114 commits ahead of `main` with no PR**, and
  164.3.1's verification reads `stale`. Stacking 164.4 on top would produce a ~350-commit
  unreviewable PR and leave 164.3.1's gate unresolved.
- **PR granularity:** one PR per file-batch, landed ONE at a time. ~230 further arms across 43
  files is not one reviewable diff.
- **Gate between batches:** `sql-mutation` must be GREEN on the **ubuntu** CI host before the next
  batch starts. The job was first observed green on ubuntu only 2026-09-02 (workflow_dispatch run
  33620169220, `arms: 30/30/0`); scaling 30 → ~260 arms on an unobserved host is how a floor rots.
- **DB isolation:** throwaway pg-lane cluster (`scripts/pg-lane/run.sh`) only. Never shared TEST.

### Backfill scope & batching

- **What is "an arm":** one `RED-UNDER-M` object per NAMED assertion group — the `"arm":"NAME"`
  field — matching the one annotated file today (31 `RED-UNDER-M` objects covering 104
  `TEST FAILED (` raises). NOT one per raise.
- **Coverage floor basis:** `FILES_FLOOR` counts only files that actually carry arms. A coverage
  figure inflated by files nothing could redden is the same shape criterion 3 forbids — a runner
  reporting PASS while covering a fraction of the corpus.
  ⚠️ **The file split this rule was accepted against turned out to be wrong — see
  `<code_context>` § Correction.** The rule itself stands; the planner must re-derive the
  denominator from the corrected measurement, not from the "44 files" figure quoted during discuss.
- **Batch order:** by file, largest arm-count first. Each plan lands its files **fully** proven —
  no file left half-annotated.
- **Out of scope:** no new arms, no assertion edits. Anything the backfill reveals is booked to
  `TODOS.md`.

### Waivers & un-falsifiable arms

- **`WAIVED_CEILING` (today 0):** raise ONLY by measurement, +1 per accepted waiver, each with its
  reason pinned beside the value in `run.mjs` — the same discipline `ARMS_FLOOR` already uses.
  Criterion 4 requires waivers to be recordable, so a hard 0 would make the phase unlandable on the
  first mechanically-unmutatable arm.
- **Where the reason lives:** inside the `RED-UNDER-M` object itself (GRAMMAR "Shape 4 — waiver"),
  so the runner PRINTS it every run. A separate ledger drifts; a printed one cannot.
- **An arm that cannot fail AT ALL is the FINDING, not an exception.** Record it, book the fix to
  `TODOS.md`. Do NOT bury a dead assertion behind a waiver. Waivers are for arms that DO bite but
  cannot be mutated mechanically.
- **Waiver volume:** more than 5 total → STOP and escalate to the founder rather than ratchet the
  ceiling. A rising ceiling is the failure mode the ceiling exists to catch.

### CI budget & the coverage floor

- **Full-corpus run per PR — MEASURE FIRST.** Today 30 arms; the phase ends near 260, each needing
  mutate → run → assert RED → restore → assert GREEN. If a full run exceeds ~20 minutes, PRs run
  CHANGED gate files and a scheduled full run enforces the floors. **The split is PRINTED, never
  silent** — a runner that quietly covers a subset is exactly what criterion 3 forbids.
- **Floor ratchet:** at the end of EVERY plan, to the measured value. Ratcheting once at phase end
  lets a mid-phase regression pass unnoticed.
- **Coverage output:** keep the printed aggregate, ADD a per-file breakdown so a file stuck
  half-annotated is visible in CI output.
- **Tally cross-check:** `arms:` vs `lane-invocations:` stays a HARD `MEASURE_FAIL` at the new
  scale. It is the v0.77.1.0 control that catches arms CLAIMED but never run.

### Claude's Discretion

- Exact file-to-plan batching within the largest-first ordering.
- Mutation choice per arm, subject to the GRAMMAR's three annotation rules.
- Whether the per-file coverage breakdown is a new line or an extension of the existing one.

### ⚠️ Correction — the "27 armless files" premise is FALSE

During discuss I reported 27 files as having no arms, derived from `grep -c "TEST FAILED ("`.
Re-measured immediately after:

- `RAISE EXCEPTION` corpus-wide: **1398** occurrences, across **all 71 files — zero files have
  none**.
- Only **890** of those use the `TEST FAILED (` idiom.
- The 27 supposedly-armless files carry **334** `RAISE EXCEPTION` sites between them. They assert
  with their own message prefixes instead, e.g. `test_mt5_exchange_boundary.sql` raises
  `'MT5SRC-03 (1a): api_keys did not admit exchange=mt5'`; `test_claim_kind_filter.sql` raises
  `'FLIPRETRY-02: include predicate present % time(s)'`.

**This is a scoping question the planner MUST resolve, not inherit.** The runner's identity needle
is the `TEST FAILED (<arm>)` literal, so those 334 assertions are currently unreachable by it.
Either (a) they are renamed into the `TEST FAILED (<arm>)` idiom — which touches gate files and
brushes against this phase's "no assertion edits" boundary, or (b) the runner's identity grammar
generalises to a declared per-file prefix. Option (a) is a larger corpus edit than the phase was
scoped for; option (b) changes a control that 164.3.1 hardened against forgery. Neither is a
free choice and the phase cannot claim criterion 1 ("every arm carries a RED-UNDER") without
picking one on the record.

### Reusable assets

- `scripts/mutation-runner/run.mjs` — the runner; mutate → run → assert RED → restore → assert
  GREEN, plus floors, waiver handling and the two independent arm tallies.

- `scripts/mutation-runner/GRAMMAR.md` — the annotation grammar: three annotation rules, the

- `scripts/pg-lane/run.sh` — throwaway PostgreSQL cluster the `sql-mutation` job runs against.
- `test_strategy_shares_rls.sql` — the reference annotated file; every new file follows its shape.

### Established patterns

- Floors and ceilings are **pinned by measurement** with the derivation, sample size and date
  written beside the constant — never chosen. Follow this for every floor this phase raises.
- Neuter → observe RED → restore is the house proof that a control can fail
  (`feedback_every_test_must_be_able_to_fail`).
- CI integrity jobs (`sql-mutation`, `sql-gate-lint`, `plan-anchor-verify`) sit in the `frontend`
  aggregator's `needs:` list AND its result loop, so a failure fails the aggregate.

### Integration points

- `.github/workflows/ci.yml` — the `sql-mutation` job and the `frontend` aggregator.
- `scripts/mutation-runner/run.mjs` floor constants — raised at the end of every plan.
- `CLAUDE.md` § "SQL gate integrity jobs" — the measured `arms:` figure quoted there must be
  updated as the floors move, or it becomes a stale-integer claim.
