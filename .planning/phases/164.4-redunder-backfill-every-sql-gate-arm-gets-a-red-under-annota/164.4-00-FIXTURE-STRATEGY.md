### Probe 3 is TERMINAL for the stubbed-chain candidate — no stub can honestly remove it

`supabase/migrations/20260416201929_audit_log_hardening.sql:239-267` issues `SAVEPOINT
audit_log_probe;` and `ROLLBACK TO SAVEPOINT audit_log_probe;` **inside a PL/pgSQL `DO $$ … $$;`
body**. PL/pgSQL has no savepoint statements — its own `BEGIN … EXCEPTION` blocks are implemented
on top of them — so the body fails to PARSE. The error surfaces at `plpgsql_yyerror`
(`pl_scanner.c:542`), i.e. before a single statement in that block executes.

Probe `M1` reproduces it on an otherwise empty cluster from an 8-line DO body: same `42601 syntax
error at or near "TO"`. The failure is a property of the migration text and the PL/pgSQL grammar.
Nothing that can be applied BEFORE migration 51 changes either. This is the class the plan named in
advance — *"something no stub can honestly provide … it is a finding about the chain, not a reason
to widen the stub"* — so the iteration loop STOPPED here, at **3 of the 8 allowed iterations**,
with the chain at **51 of 262 migrations**.

⛔ Nothing under `supabase/migrations/` was edited to make the chain apply. A migration is
production; the stub was the only thing shaped.

DECISION: stand-ins

## Why

**Rule (i) failed TERMINALLY, so the rule decides without reaching rule (ii).** The stubbed real
chain reached **51 of 262 migrations at stub iteration 3 of the 8 allowed** and stopped on
`20260416201929_audit_log_hardening.sql:272`, `42601 syntax error at or near "TO"` — a `SAVEPOINT` /
`ROLLBACK TO SAVEPOINT` inside a PL/pgSQL `DO` body, which PL/pgSQL cannot parse. Probe `M1`
reproduced that from an 8-line DO body on an empty cluster, so it is a property of the migration
text and the PL/pgSQL grammar: **no stub applied before migration 51 can remove it**, and the only
other lever — editing the migration — is production and forbidden. The chain never reached a
baseline, so it has no lane time to compare: its three wall clocks (1.31 s / 1.24 s / 1.77 s) each
bought 10, 21 and 51 migrations respectively and are aborted-run numbers, not per-lane costs.

**The stand-in candidate is GREEN and timed:** 1.04 / 0.99 / 1.00 s over three runs,
**mean 1.01 s**, on `test_ledger_refresh_composite_arm.sql` with `ALL 10 ARMS EXECUTED (A-J)` and
no skip of its own. That is at the ubuntu-reference end of RESEARCH's model (ubuntu ran the
reference lane at 1.03 s where this box ran it at 1.65 s, ratio 1.6), i.e. this 10-file apply list
costs LESS on this box than the reference's 4-file list did — the apply list length is not the
dominant term at this scale; cluster boot is.

**Projected end-state CI wall clock for the winner**, by the plan's formula
`453 lanes x measured local mean / 1.6 + 65 s fixed`:
`453 x 1.01 / 1.6 = 286 s`, `+ 65 s` = **351 s ≈ 5.9 min** on ubuntu — comfortably under the
CONTEXT's ~20-minute threshold and under `ci.yml:854`'s `timeout-minutes: 15`, at THIS apply-list
size. Two caveats the batches must carry: the 453-lane figure is RESEARCH's scenario A and includes
the 71 sections that `[REDUNDER-PGCRON]` shows are un-runnable today, and per-lane cost must be
re-measured per batch — the threshold is crossed near ~2.5 s/lane on ubuntu.

**The stub file stays uncommitted.** `00-supabase-stubs.sql` lived only in the session scratchpad
and is NOT promoted to `scripts/pg-lane/fixtures/`, because the chain lost.

## Authoring rules carried into every batch

1. **No twin may target `scripts/pg-lane/fixtures/**`.** A mutation that edits a stand-in proves the
   fixture author's guess, not production. Targets must be a `supabase/migrations/**` file, the gate
   file itself, or a `sql` step. Measured at HEAD: 0 twins violate it, so the rule refuses nothing
   that exists. Plan 01 makes it a parse-time refusal — and it must key on the twin's `"file"`, NOT
   on a fixture's position in the apply list, because this plan measured that a stand-in cannot
   always be first (`04-fixture-compute-jobs-targets.sql` sits between two migrations).
2. **The apply list must contain the migration that LAST defines each object a twin mutates, and the
   twin must target THAT migration.** `CREATE OR REPLACE` chains re-base silently; a twin pointed at
   an earlier definition mutates text the running database never sees.
3. **Stand-ins prove that the DDL applies and that arms bite — not behaviour against the real
   schema.** The lane's own header says it, and it is quoted rather than re-litigated
   (`scripts/pg-lane/run.sh:44-51`):

   > ⚠️ WHAT IT DOES AND DOES NOT PROVE. fixtures/01-fixture-core.sql and
   > fixtures/02-fixture-sanitize-tables.sql are STAND-INS: they carry only the columns the
   > migrations' FKs, policies, RPCs and sanitize_user body actually name. The objects under test —
   > strategy_shares, its trigger, its grants, its policies, both RPCs — are the REAL ones from the
   > real migration files. So this proves the DDL applies, the self-verification blocks bite, and
   > the gate's arms pass and can fail. It does NOT prove behaviour against the real schema's own
   > RLS, constraints or triggers. That still belongs to the TEST hand-apply.
