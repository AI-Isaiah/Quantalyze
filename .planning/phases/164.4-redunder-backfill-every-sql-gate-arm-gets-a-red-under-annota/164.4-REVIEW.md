### WR-01: `gateNeedsPgCron` reads `'pg_cron'` off RAW statement text — a COMMENT can defer a file forever

**File:** `scripts/mutation-runner/parse.mjs:996-1002`

**Issue:** The classifier tests `pg_extension` against `stmt.executableText` (comments
masked) but tests the extension name against `stmt.text` (comments **not** masked):

```js
if (!PG_CRON_CATALOG_RE.test(stmt.executableText)) continue;
if (stmt.text.includes(PG_CRON_EXTENSION)) return true;
```

The asymmetry is deliberate (the literal `'pg_cron'` is blanked by `maskNonCode`), but it
opens a false-positive path the calibration pair does not cover: a gate with a **live**
`pg_extension` query for some *other* extension whose surrounding prose merely mentions
pg_cron classifies as `lane-blocked`. Such a file silently leaves `pending:` and joins a
deferral class that nothing will annotate. The fixture pair
(`lane-blocked-gate.sql` / `lane-blocked-comment-only-gate.sql`) only proves the *other*
direction — comment-only `pg_extension` → `pending`. There is no arm for
"live `pg_extension`, pg_cron only in prose".

`PG_CRON_CATALOG_RE` is case-insensitive while `.includes("pg_cron")` is case-sensitive,
which is a second, smaller asymmetry in the same two lines.

**Fix:** Narrow the second read to the statement with comments masked but literals
preserved, and add the missing calibration arm. Sketch:

```js
// parse.mjs — a projection that blanks comments only, not literals.
export function commentMaskedText(stmt) { /* mask `--` and block comments; keep literals */ }

export function gateNeedsPgCron(text) {
  for (const stmt of tokenizeStatements(text)) {
    if (!PG_CRON_CATALOG_RE.test(stmt.executableText)) continue;
    if (commentMaskedText(stmt).toLowerCase().includes(PG_CRON_EXTENSION)) return true;
  }
  return false;
}
```

plus, in `mutation-annotation-parser.test.ts`, a third member of the pair: live
`pg_extension WHERE extname = 'pgcrypto'` with `-- pg_cron` in a neighbouring comment,
asserting `gateNeedsPgCron(...) === false`.

### WR-02: the new per-file cross-sum arms agree with the aggregate BY CONSTRUCTION — they are not the independent control they are modelled on

**File:** `scripts/mutation-runner/run.mjs:2595-2624` (`absurdityViolations` relations 3/4),
`scripts/mutation-runner/run.mjs:3186-3189` and `:3203-3204` (the tally increments)

**Issue:** The doc-comment presents relations (3) and (4) as siblings of the
`armsExecuted === laneInvocations` check, whose whole value is that the two counters live
in different functions (`laneTally[leg] += 1` inside `runLane`, `armsExecuted += 1` inside
`runCorpus`). The per-file columns have no such independence — `tally.executed` is
incremented on the **line immediately after** `armsExecuted`, and `tally.unjudged` on the
line after `armsUnjudged`:

```js
armsExecuted += 1;
armsUnjudged += 1;
tally.executed += 1;
tally.unjudged += 1;
```

Both sides of `sum(perFile.biting) === biting` therefore derive from the same increments
and the same `defects` array. Tracing the verdict loop, exactly one non-biting defect can
be raised per executed arm and it always carries `file: gateRel` of a tally that was pushed
before any `continue`. The relation is consequently **unfireable in the current code**: it
can only trip if a future refactor keys a non-biting defect to a file the loop never
listed. That is a real (if narrow) guard, but it is not the control the comment claims,
and the same stub that severs the lane tally leaves these two relations perfectly
consistent.

**Fix:** Either (a) state the weaker guarantee in the comment — "these catch a defect
attributed to an unlisted file; they are NOT a second measurement of the arm count, unlike
relation (1)" — or (b) make one side genuinely independent, e.g. derive the per-file
`executed` column from `timings`/lane records keyed by gate rather than from a counter
incremented beside `armsExecuted`.

### WR-03: nothing statically detects a pg-lane stand-in NARROWER than production; the runner catches only half the class

**File:** `scripts/pg-lane/fixtures/10-fixture-strategies-rls-baseline.sql:7-31`,
`scripts/pg-lane/fixtures/16-fixture-user-notes-baseline.sql:5-18` (headers)

**Issue:** Both fixtures document a measured instance of the same defect — a stand-in
narrower than production made a gate print `ALL PASS` while its arms were satisfied by the
grant layer rather than by the object under test (fixture 10) or by an object the real
migration never got to create (fixture 16). Both were found **by hand**, and there is no
lint rule, no runner check and no self-test scenario for the class.

The mutation runner catches only the sub-case where the mutation *cannot* redden
(`no-red`). It cannot catch the sub-case where the arm reddens for a reason unrelated to
what the twin mutated: first-failure discipline checks the **arm identity**, never the
cause. That is exactly the shape fixture 10's header describes (`GUARD 6`/`GUARD 7`
catching a `42501` that came from a missing GRANT rather than from the trigger).

I ran the two obvious detectors by hand and both are clean at HEAD (see Summary), so this
is a missing control, not a live defect.

**Fix:** Add a fifth `sql-gate-lint` rule with red and green fixtures, over each gate's
`RED-UNDER-SETUP` apply list:

1. **Shadowing:** if a `scripts/pg-lane/fixtures/**` entry `CREATE TABLE IF NOT EXISTS X`
   and a *later* `supabase/migrations/**` entry in the same list also creates `X`, fail
   unless an intervening fixture carries `DROP TABLE IF EXISTS X` (the fixture-16 idiom).
2. **Fixture-vs-fixture shadowing:** the same rule for two fixtures in one apply list,
   unless the later one re-adds every column with `ADD COLUMN IF NOT EXISTS` (the
   fixture-20 idiom).

Both are ~20 lines and reproduce the two instances this phase fixed by hand.

### WR-05: `maskJsComments` is a hand-rolled JS lexer whose regex-literal and nested-template branches are uncalibrated

**File:** `src/__tests__/mutation-runner-floors.test.ts:112-197`

**Issue:** Several anti-prose wiring pins depend on this masker; if it ever fails to blank
a comment, those pins become satisfiable by a comment — the exact class the block above it
says it exists to close. Its calibration is three cases (trailing `//`, block comment,
`//` inside `"https://…"`). Two hand-written branches are uncovered:

- **Regex literals.** The `prev`-character heuristic treats `/` as a literal opener only
  after `[(,=:[!&|?{};+\-*%~^<>]`, so `return /a\/\/b/` is scanned as division.
- **Nested template literals.** `copyDelimited` closes on the first matching backtick, so
  `` `…${cond ? ` (x)` : ""}…` `` desyncs string-vs-code polarity for the span between the
  inner backticks. `run.mjs:2981` contains exactly this shape
  (`` …unverified${probe.measureFail ? ` (${probe.measureFail})` : ""} `` ). I confirmed
  the desync empirically; because nested templates always contribute an even backtick
  count, polarity resyncs at the end of the expression, and running the masker over the
  live `run.mjs` and `parse.mjs` yields **0 surviving `//` comment lines** and byte-length
  parity. So it is correct today and the dominant failure direction (over-masking real
  code) is loud.

**Fix:** Add two calibration arms beside the existing three:

```ts
expect(maskJsComments('const RE = /a\\/\\/b/; // logPerFileRows(x)'),
  "a `//` inside a regex literal must not be treated as a comment opener")
  .toContain("const RE = /a\\/\\/b/;");
expect(maskJsComments('const s = `a${c ? ` (b) ` : ""}d`;\n// logPerFileRows(x)\n'),
  "a nested template must not desync the mask past its own statement")
  .not.toContain("logPerFileRows");
```
