<objective>
Decide — by measurement, on the record — how every newly annotated gate file gets its baseline-GREEN
`RED-UNDER-SETUP` apply list: per-file STAND-INS (today's pattern, two fixtures for two migrations)
or a STUBBED REAL MIGRATION CHAIN (`auth`/`storage`/`cron`/`net` stubs + `supabase/migrations/*.sql`).
This is the phase's unpriced cost (RESEARCH § Fixture / setup authoring; PATTERNS § P2.5): the choice
sets both the authoring effort of every batch and the per-lane cost of ~453 CI lanes at phase end.
Batches must NOT start on an assumed strategy.

Measured facts to start from (RESEARCH, 2026-09-02): fixture-core + the real chain is mutually
exclusive (fails at migration 1, `relation "profiles" already exists`); a minimal `auth` stub +
`pgcrypto` + the chain reaches **10 of 262** then dies on `storage.buckets`; 37 migrations touch
`cron.`, 4 `net.`, 2 `storage.`, 38 `auth.users`. Nothing past migration 10 has ever been measured.

⭐ THE DECISION RULE, fixed here so the probes cannot be read to taste. Choose STUBBED-CHAIN only if
BOTH hold: (i) the stubbed chain reaches a GREEN baseline for
`supabase/tests/test_reconcile_dropped_enqueue_sweep.sql` within the timebox of **8 stub iterations**
(one iteration = read the first ERROR, add the smallest stub that removes it, re-run); AND (ii) the
measured stubbed-chain lane wall clock is **≤ 4.0 s on this box**. Derivation of 4.0 s: the
end-state corpus is ~453 lanes (365 arms + 44 baseline + 44 restore); the CONTEXT's ~20-minute
threshold minus the job's measured ~1.1 min fixed cost leaves ~2.5 s/lane on ubuntu; ubuntu ran the
reference lane at 1.03 s where this box ran it at 1.65 s (ratio 1.6), so 2.5 s ubuntu ≈ 4.0 s local.
Otherwise choose STAND-INS. Record BOTH candidates' numbers whichever wins.

⛔ Never contact a Supabase database and never run a `supabase` CLI command — this checkout's CLI is
linked to PRODUCTION. Every probe runs on `scripts/pg-lane/run.sh` with `--workdir` OUTSIDE the
repo (a workdir inside the checkout is the runner's `dirty-checkout` defect).

Purpose: turn an unpriced cost into a measured one before ~335 annotations are written against it.
Output: the decision record, the largest file's proven apply list, and any additive fixture it needs.
</objective>
