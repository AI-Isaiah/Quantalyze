## ⭐ THE FINDING THIS BATCH BOUGHT — a positive control needs a SILENT mutation

Six of these 48 arms are POSITIVE CONTROLS: they assert that something must still
WORK (`a self-owned own_capital strategy CAN become a position`; `the alias UPDATE
MUST succeed`; `a third-party unmarked strategy CAN become a position`). Their
statements are deliberately NOT wrapped in an exception handler — that is what
makes them positive controls.

**Measured consequence:** the drift each arm's prose NAMES makes that statement
RAISE, and an unhandled raise aborts the gate with no `TEST FAILED (…)` in the
output at all. The runner scores that `NO-IDENTITY` / `wrong-first-failure`, and
the arm is **not counted as biting** — so the literal drift cannot be used as its
twin.

First observed on this batch's own `test_scenario_shares_rls.sql`:

```
arm Assertion 7              exit   3  NO-IDENTITY
  wrong-first-failure  Assertion 7
      gate exited 3 but no "TEST FAILED (…)" in its output was ATTRIBUTABLE to a
      raise in …/test_scenario_shares_rls.sql — SIGHTINGS: none — the lane
      emitted no TEST FAILED (…) at all
```

**The resolution is a mutation, never a waiver.** Each such arm is twinned with
the SILENT form of the same drift — a write that is DROPPED rather than REFUSED —
which is exactly what the arm's own assertion measures (`got % rows`,
`alias=%`). Every one carries a ⚠️ at the annotation recording the measurement,
so the next author meets it as a contract rather than as a surprise:

| arm | literal drift (unusable) | the twin that bites |
|---|---|---|

## Decisions Made

See `key-decisions` in the frontmatter. The three most consequential for later batches:

- **A gate whose migration SELF-VERIFIES what the gate asserts can only be twinned with `sql` steps.** `test_create_wizard_strategy_for_key.sql` is the pure case: its migration's post-verify `(a)`-`(h)` covers nearly every arm, so any migration edit aborts the apply. All nine of its twins are `sql` steps or a gate-file edit — and that is not a workaround, it is the point of the gate: it re-reads the LIVE ACL and the LIVE body, catching drift the migration verified ONCE at apply time.
- **`neuter` ACCUMULATES.** `runCorpus` feeds each neuter's output into the next, so repeating an arm rewrites the NEXT surviving carrier. `Assertion 4` needed `Assertion 1` four times and `Assertion 2` twice to reach the fourth raise of a seven-raise arm. Plan 04 recorded neuter as "one raise per named arm"; it is one raise per ENTRY.
- **A single-line `find` on a GATE-FILE edit is self-defeating.** The needle is reproduced verbatim inside its own annotation's JSON, so an `occurrences` measured PRE-EDIT (correctly) becomes wrong the moment the twin is written — observed here as `MEASURE_FAIL: "  VALUES (port_a, strat_a_repoint, 500000);" occurs 2x … annotation claims 1x`. A needle spanning TWO lines is JSON-encoded with `\n` and never appears in the file.
