## R1 — Baseline currency guard (Area A, first deliverable)

**How the comparison is actually done** `[VERIFIED: scripts/restore-test-from-baseline.sh:309]`:
```
FRESHNESS_TS_CMD="${FRESHNESS_TS_CMD:-git log -1 --format=%ct --}"
```
and the comparator `[VERIFIED: scripts/restore-test-from-baseline.sh:652-662]`:
```
refuse_stale_baseline() {
  local b_ts m_ts
  b_ts=$($FRESHNESS_TS_CMD "$BASELINE_FILE" 2>/dev/null | head -1 | tr -d '[:space:]')
  m_ts=$($FRESHNESS_TS_CMD "$MIGRATIONS_DIR" 2>/dev/null | head -1 | tr -d '[:space:]')
  case "$b_ts" in ''|*[!0-9]*) fail "FRESHNESS_TS_CMD printed no epoch for ${BASELINE_FILE} (got '${b_ts}'). An unreadable timestamp is not a fresh one." ;; esac
  case "$m_ts" in ''|*[!0-9]*) fail "FRESHNESS_TS_CMD printed no epoch for ${MIGRATIONS_DIR} (got '${m_ts}'). An unreadable timestamp is not a fresh one." ;; esac
  if [ "$b_ts" -lt "$m_ts" ]; then
    fail "the baseline dump is STALE: ${BASELINE_FILE} last changed at epoch ${b_ts}, ${MIGRATIONS_DIR} at ${m_ts}. …"
  fi
  note "baseline freshness OK — baseline epoch ${b_ts} >= migrations epoch ${m_ts}"
}
```
So the comparison is **git commit timestamp** (`git log -1 --format=%ct -- <path>`, epoch seconds of the last commit that touched the path), applied identically to `supabase/schema/baseline.sql` and `supabase/migrations/`, comparing which was more recently committed. It is explicitly NOT filesystem mtime.

**Does this hold on a fresh/shallow CI clone?** No, and this repo already says so in its own comment, which is the strongest evidence available (an in-repo, dated, first-person statement, not an inference from behavior) `[VERIFIED: .github/workflows/test-restore-from-baseline.yml:216-219]`:
```
      # fetch-depth: 0 — BOTH the baseline freshness refusal (`git log -1 --format=%ct`
      # over supabase/schema/baseline.sql vs supabase/migrations) and the PROD-ledger
      # ancestry assert below need real history. A shallow clone makes the first read
      # the clone date and the second fail on an unknown object.
      - uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0  # v7.0.0
        with:
          persist-credentials: false
          fetch-depth: 0
```
`[VERIFIED: measured]` — reproduced the mechanism independently against a real shallow clone (`git clone --depth 1`, unrelated public repo, not this repo, to avoid any network operation against Quantalyze's own remote): `git diff --name-only origin/<missing-ref>...HEAD` printed nothing to stdout and `fatal: ambiguous argument … unknown revision or path not in the working tree.` to stderr, exit code 128 — confirming that a shallow/incomplete history does not resolve to "no changes," it resolves to a hard failure or (per the repo's comment) to the checkout timestamp standing in for history the clone never fetched. `git log -1 --format=%ct -- <path>` on a depth-1 clone has only the tip commit locally; if that lone commit is treated as having no parent, its diff against the empty tree includes every tracked file, so **every path's "last changed" epoch collapses to the clone's own commit time** — which is exactly what "read the clone date" means in the repo's own words. Comparing two paths that both report the clone's timestamp makes the freshness check pass vacuously regardless of the files' real history.

**Consequence for Area A's first deliverable.** `frontend-local-stack`, the job most likely to host `sql-tests` after the move (or any new dedicated currency-guard step), currently checks out with **no `fetch-depth: 0`** `[VERIFIED: measured — grep over .github/workflows/ci.yml:620-700 found the job's `actions/checkout` step at line 692 with only `persist-credentials: false`, no `fetch-depth` key present]`. Any implementation of the Area A currency guard MUST add `fetch-depth: 0` to whichever checkout step precedes it, or the guard will silently pass on stale schemas in CI even though it works correctly on a developer's full local clone — reproducing, in a new gate, the exact "gate named for staleness that measures integrity" defect Area A already names for `check-baseline-staleness.mjs`.

**Recommendation:** reuse `refuse_stale_baseline()` (or extract it to a standalone script sharing the `FRESHNESS_TS_CMD` seam) rather than writing a new comparator; add `fetch-depth: 0` to the hosting job's checkout; keep the check as its own named gate per Area A's "give the currency check its own named gate" forbidden-closure clause, rather than folding it into `check-baseline-staleness.mjs`.

## R3 — The subset rule (Area D)

**Reusable precedent — do not invent a second mechanism** `[VERIFIED: scripts/classify-changed-paths.mjs:273-297]`:
```
const baseRef = process.env.GITHUB_BASE_REF ? `origin/${process.env.GITHUB_BASE_REF}` : "origin/main";
let changedFiles;
try {
  changedFiles = git(["diff", "--name-only", "--no-renames", `${baseRef}...HEAD`])
    .split("\n")
    .filter(Boolean);
} catch (e) {
  console.error(`MEASURE_FAIL: could not read ${baseRef} — ${e.message}`);
  return 1;
}
```
This is the exact idiom Area D needs: a **three-dot** diff (`baseRef...HEAD`, i.e. against the merge base, not a two-dot direct diff) via `execFileSync` (argv-array form, never a shell string — the base ref is untrusted on a fork PR), wrapped in try/catch so a failed `git diff` (unresolvable ref) throws and is caught explicitly rather than silently producing an empty result.

**The `changed-paths` job's own checkout settings, and why they matter** `[VERIFIED: .github/workflows/ci.yml:150-153]`:
```
      - uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0  # v7.0.0
        with:
          persist-credentials: false
          fetch-depth: 0   # the classifier diffs against the base branch
```
`fetch-depth: 0` is mandatory here for the same reason as R1: `actions/checkout`'s default (`fetch-depth: 1`) fetches only the triggering ref; `origin/main` (or `origin/${GITHUB_BASE_REF}`) is not guaranteed to be present locally without a full or deepened fetch, and a missing ref makes the three-dot diff fail exactly as measured in R1's shallow-clone reproduction (`fatal: ambiguous argument …`, exit 128).

**Recommendation for `sql-mutation`'s subset rule:** either (a) add `needs: [changed-paths]` is already impossible per this job's own documented ban — `changed-paths` is explicitly exempted from the DB-touching jobs' "no new needs: edges" ban (`.github/workflows/ci.yml:127-135`, `[VERIFIED]`) because it shares no mutex and has no diverging `if:`, so `sql-mutation` CAN safely depend on it for a computed-files output — extend `changed-paths`'s job to also emit the changed-gate-files list (or the count) as a second output, reusing `judge()`'s sibling `git diff` call rather than `docs_only`'s boolean; or (b) give `sql-mutation` its own step calling `classify-changed-paths.mjs`'s underlying git command directly, scoped to `supabase/tests/**` and whatever other gate-file globs the mutation runner covers, with its own `fetch-depth: 0` checkout. Option (a) is preferred per the R3 instruction to "prefer reusing it over inventing a second mechanism" — it keeps exactly one script owning "diff against merge base."

## R4 — The vacuity fence (Area D)

**Missing-ref behavior, measured directly this session** `[VERIFIED: measured]`:
```
$ git diff --name-only origin/nonexistent-branch...HEAD
fatal: ambiguous argument 'origin/nonexistent-branch...HEAD': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'
exit=128
```
With `2>/dev/null` applied and the result captured via command substitution:
```
$ out=$(git diff --name-only origin/nonexistent-branch...HEAD 2>/dev/null); rc=$?
$ echo "captured='$out' rc=$rc"
captured='' rc=128
```
This confirms the exact idiom CONTEXT.md requires: `$?` after `out=$(cmd)` reflects the **substituted command's** exit status, not the assignment's — so checking `rc` (128, non-zero) correctly distinguishes "the diff failed" from "the diff succeeded and found nothing" (which would be `rc=0`, `out=''`). A pipeline into another command (e.g. `git diff ... | wc -l`) would lose this distinction, because `$?` after a pipe reflects the LAST command in the pipe (`wc -l`, which always exits 0), not `git diff`'s exit code — this is why the recommended shape captures via command substitution BEFORE any further processing, never pipes `git diff` directly into a counter.

**`grep -c` on zero matches, measured directly this session** `[VERIFIED: measured]`:
```
$ echo -n "" | grep -c foo; echo "rc=$?"
0
rc=1
$ printf "a\nb\n" | grep -c zzz; echo "rc=$?"
0
rc=1
```
`grep -c` prints `0` (a valid count) but exits `1` (its "no match" convention) — under `set -e`, an unguarded `grep -c` on a zero count aborts the script even though zero is a legitimate, expected value. This repo already has an established idiom for this exact trap, reused throughout `restore-test-from-baseline.sh` `[VERIFIED: scripts/restore-test-from-baseline.sh:1142-1145]`:
```
set +e; EXP_TABLES=$(grep -ac '^CREATE TABLE' "$BASELINE_FILE"); rc=$?; set -e
[ "$rc" -le 1 ] || fail "MEASURE_FAIL: could not count CREATE TABLE lines in ${BASELINE_FILE} (grep exited ${rc})."
```
i.e. disable `set -e` around the specific `grep -c`/`grep -ac` call, capture `rc`, then treat `rc <= 1` as valid (0 = matched, 1 = zero matches, both legitimate) and `rc >= 2` as a real error (bad pattern, unreadable file). **Recommendation:** reuse this exact `set +e; VAR=$(grep -c …); rc=$?; set -e; [ "$rc" -le 1 ] || fail …` idiom for `sql-mutation`'s subset computation, rather than `PIPESTATUS` — `[VERIFIED: measured]` `PIPESTATUS` has zero prior usages in this repo (`grep -rn "PIPESTATUS" scripts/ .github/workflows/` returned nothing), so introducing it would be a new, unprecedented idiom in a repo that already has a working, repeatedly-used alternative.

**Composing R3+R4 for the vacuity fence:** the subset step must (1) run the merge-base diff via `classify-changed-paths.mjs`'s pattern; (2) on a caught exception (missing ref / git failure), fail the job loud rather than defaulting to empty; (3) on a successful diff that legitimately narrows to a changed-file list, filter it to the gate-file glob (e.g. `supabase/tests/test_*.sql` and whatever else `sql-mutation` covers) using the SAME `grep -c`/`rc<=1` pattern above so a zero-match filtered result is distinguished from a filtering failure; (4) an EMPTY narrowed set after filtering must NOT short-circuit to success — CONTEXT.md's binding rule is explicit that this must run the full corpus or fail loud, never report "0 files changed, nothing to do" as a pass.

### Anti-Patterns to Avoid
- **Filesystem-mtime-based currency checks in CI:** every checked-out file gets the same checkout-time mtime on a fresh runner; only git-commit-time comparisons (with full history) are meaningful. `restore-test-from-baseline.sh` already made this choice; do not regress it.
- **Piping `git diff` directly into a counting command:** loses the diff command's own exit code behind the pipe's last command. Capture first, check `$?`, then process.
- **Treating an empty `grep -c` result as "nothing found, script continues cleanly" under `set -e`:** `grep -c` exits 1 on zero matches; use the `set +e; …; rc=$?; set -e; [ "$rc" -le 1 ]` idiom.
- **A second `git diff`-against-merge-base implementation living beside `classify-changed-paths.mjs`:** creates a second thing that must stay byte-identical in fetch-depth requirements, ref resolution, and error handling — this repo has a named, recorded defect class (`[164.7-CITATION-DRIFT-01]`) for exactly this kind of unintentional divergence between two copies of "the same" logic.

## Common Pitfalls

### Pitfall 1: Adding a currency guard without `fetch-depth: 0`
**What goes wrong:** the guard runs, prints a freshness-OK note, and is meaningless — both `baseline.sql` and `supabase/migrations/` report the shallow clone's own checkout timestamp.
**Why it happens:** `actions/checkout`'s default `fetch-depth: 1` is invisible in the guard's own output; nothing about a "PASS" line signals that history was too short to be trustworthy.
**How to avoid:** always pair a `git log`-based currency/history check with `fetch-depth: 0` on the SAME job's checkout step; this repo's own `test-restore-from-baseline.yml` comment (quoted above) is the citable precedent.
**Warning signs:** the guard passes even immediately after a known-stale baseline regeneration gap; the guard's epoch outputs for two different paths are suspiciously identical.

### Pitfall 2: Confusing "zero changed files" with "diff failed" in the subset rule
**What goes wrong:** `sql-mutation` runs zero arms and reports success on a PR whose merge-base ref could not be resolved (e.g. a fork PR edge case, or a `GITHUB_BASE_REF` pointing at a ref not yet fetched).
**Why it happens:** a naive `files=$(git diff … 2>/dev/null); if [ -z "$files" ]; then echo "nothing to do"; exit 0; fi` collapses both cases into the same branch.
**How to avoid:** check `$?` from the command substitution explicitly (see R4); a non-zero exit is a hard failure, never a "zero files" reading.
**Warning signs:** `sql-mutation` runs suspiciously fast, zero arms logged, on a PR that plainly touched `supabase/tests/`.

### Pitfall 3: Moving `sql-tests` onto `pg-lane` because it is the "existing disposable Postgres lane"
**What goes wrong:** 47 of 75 test files reference `pg_net`, `vault.*`, `auth.uid()`/`auth.jwt()`, or the Supabase-platform roles; `pg-lane` only provisions three bare roles and `pg_cron`. Most of the corpus would fail with undefined-schema/undefined-function errors, not assertion failures.
**Why it happens:** `pg-lane` is the lane already wired into `sql-mutation` for gate-file mutation testing, making it look like the natural "already proven" choice — but it is proven for a DIFFERENT, narrower workload (individual gate files with declared `RED-UNDER-SETUP` dependencies), not the full `supabase/tests/test_*.sql` corpus run wholesale.
**How to avoid:** target `local-stack` (already proven for the ~284-test live-DB class per Area A) and falsify `vault`/`pg_net` availability on it before committing, per R2's recommendation.
**Warning signs:** a spike run against `pg-lane` failing with `relation "vault.secrets" does not exist` or `function auth.uid() does not exist` on files that are NOT LANE-ONLY-marked.
