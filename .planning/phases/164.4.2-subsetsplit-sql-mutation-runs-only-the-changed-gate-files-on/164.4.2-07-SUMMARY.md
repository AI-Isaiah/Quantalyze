**The mutation runner gained a `--subset-from` mode that exits 0 on a clean run while `--file`/`--arm` still exit 2. Every corpus run prints one `scope:` line. ## The `scope:` forms (plan 09 parses these)

```
scope: FULL <N>/<N> annotated files
scope: FULL <N>/<N> annotated files (subset fallback: <reason>)
scope: SUBSET <k>/<N> annotated files: <basename> <basename> …
scope: DIAGNOSTIC <file-or-arm>
```

Fallback reasons, verbatim shapes: `no listed file is annotated: <names>` and
`<u> of <n> listed file(s) not annotated: <names>`.
A SUBSET run also prints `ARMS_FLOOR: NOT compared — this SUBSET run covered <k> of <N> annotated
files; ARMS_FLOOR is compared by the full-corpus run (push to main).`. Its closing line ends
`NOT full-corpus coverage.`

**Derivation outputs** (`scripts/sql-gate-subset.mjs`, appended to `$GITHUB_OUTPUT` when set):
`sql_gate_mode=full|subset` and `sql_gate_files=<space-separated repo-relative paths>` (empty on
FULL). The human line is `sql_gate_mode=<mode> — <reason>[: <files>]`.

## Deviations from Plan

**1. [Rule 2 - Missing critical functionality] The derivation forces FULL when the mutation machinery changes**
- **Found during:** Task 2
- **Issue:** Every gate's RED-UNDER-SETUP apply list names `scripts/pg-lane/fixtures/*` and
  `supabase/migrations/*` files, and the runner itself decides every verdict. Take a PR that
  changes one of those plus one gate file. Under the behaviour table as written, only that gate
  would run, and every other gate's arms would go unexercised against the changed machinery.
  That is the vacuity class the fence exists to stop.
- **Fix:** `MACHINERY_PREFIXES` (`scripts/mutation-runner/`, `scripts/pg-lane/`,
  `supabase/migrations/`) forces FULL and names the paths. Self-test row 7 covers it. This does
  not reopen DECISION D, because D governs gate-file changes and says nothing about machinery
  changes. It also makes plan 09's expectation hold on this branch ("expect the plain FULL form
  on a pull request"), since the branch changes `run.mjs`.
- **Commit:** `f3a2a0e09`

**2. [Rule 3 - Blocking] The subset self-test is a separately counted `(subset) 1/6..6/6` block**
- **Issue:** Renumbering the 17 numbered scenarios would have broken
  `src/__tests__/gate-family-meta.test.ts`, which pins `SELF-TEST 9/17` and others by needle. That
  file is outside `files_modified`, and `ci.yml` (owned by plan 09) also mentions `17/17`.
- **Fix:** A new block with its own denominator. The numbered set is untouched.

**3. [Scope clarification] `--parse-only` and pre-run refusals print no `scope:` line**
- The truth "every runner run prints exactly one `scope:` line" holds for every run that reaches
  `runCorpus` (FULL / SUBSET / DIAGNOSTIC). `--parse-only` runs zero arms, so printing
  `scope: FULL` there would describe a static check as mutation coverage. A refused
  `--subset-from` exits 1 or 3 before any corpus run. Plan 09's assert should treat a missing
  `scope:` line as a failure only for the mutation step, which is what the plan intends.

**4. [Rule 2] `--subset-from` also refuses `--fixture-corpus`**. A `supabase/tests/` list does not
  belong with a fixture scope.

**5. [Environment] Tracer command adapted and plan ledger not written**
- The sandbox refuses `git` inside `bash -c`. So the tracer ran as a scratch script with the
  git common dir hard-coded to its measured value. Everything else matches the plan's
  `<automated>` command byte for byte, including the lock, the grep assertions and the echo.
- The sandbox also refused a write of the per-plan ledger file under the git dir. So
  `plan_head_before` is the dispatch base `8a62cb34`, and `commits: 3` was measured with
  `git rev-list --count 8a62cb34..HEAD` before this SUMMARY's own commit.

**6. [Ordering] The FULL "after" run was taken once, after Task 3, not after Task 1**
- Task 3 builds on Task 1's changes, so one run at the final state checks them both.
  A second ~10-minute cluster run added no evidence.
