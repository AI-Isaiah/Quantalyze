### The RED

CI run `35886515179`, head `25135a99`, job `sql-tests`, step `Run SQL self-tests against the local-stack lane`, exit 3:

```
psql:supabase/tests/test_analytics_service_settings_and_vault_tick.sql:766: ERROR:  TEST FAILED (T1): an authenticated NON-ADMIN TRUNCATEd public.system_settings — the statement was permitted …
```

The step stops at the first failing file. The local reproduction below shows that this file was **1 of 35**.

### Root cause (verified before relying on it)

- **PROD grants no TRUNCATE here.** `supabase/schema/baseline.sql` grants `authenticated` exactly `SELECT,INSERT,DELETE,MAINTAIN,UPDATE` on `public.system_settings`.
- **The dump sets its default privileges LAST.** It has 12 `ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" …` lines, all after every CREATE. It emits object GRANTs relative to `acldefault` (owner only). They can add privileges and never subtract.
- **The lane never cleared the image's defaults.** Measured on a fresh `up --no-schema` lane (PostgreSQL 17.6): `public` holds **0** relations, **0** functions and **0** types. `pg_default_acl` holds **6** rows on `public`, 3 for grantor `postgres` and 3 for grantor `supabase_admin`, covering `r`/`S`/`f`. Each grants ALL to `postgres, anon, authenticated, service_role`. The loading role `postgres` is not a superuser and is not a member of `supabase_admin`.
- **The TEST restore path is unaffected.** `scripts/restore-test-from-baseline.sh` runs `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` before the dump, which removes every `public` default-ACL row.
- **Consequence:** every table, sequence and function the dump created on the lane inherited ALL. The failure spans tables and functions. Before the fix, `test_csv_finalize_atomic_fold.sql` failed on `anon holds EXECUTE on finalize_csv_strategy_with_returns`, the function half of the same defect.

### Approach chosen: (a) reset the default ACLs, not (b) DROP SCHEMA + recreate

- (a) changes only what is wrong. The image's `public` is empty apart from these rows, so removing them gives the restore path's starting state.
- (b) would also change the schema's owner (`pg_database_owner` → the connecting role) and its ACL. PUBLIC `USAGE` would be lost, and the dump recreates neither, because it grants USAGE only to postgres/anon/authenticated/service_role. PROD's `public` keeps its standard owner and ACL. (b) would therefore trade one divergence for another.
- **Grantor roles, object types and grantees are derived** from `pg_default_acl` joined on `defaclnamespace = 'public'::regnamespace`. None is listed in executable SQL.
- **Superuser.** The reset needs the stack superuser (`supabase_admin`) because `postgres` may only alter its own defaults. The superuser DSN is the lane's own loopback DSN with the role swapped. A DSN that does not start with the `postgres` role is refused, not guessed at. ⚠️ **Not observed in CI yet.** Measured on local CLI 2.84.2; CI pins 2.98.2. If the image there authenticates the superuser differently, the boot goes FATAL loudly at the reset. It cannot pass silently.
- **Ordering.** Currency gate → DSN/psql → **reset** → dump → **ACL-fidelity gate** → reference data → replay. Replayed migrations still run after the dump's trailing default privileges, exactly as on PROD.

### The fix — commit `9dcaff12b`

- `scripts/local-stack/run.sh`
  - `reset_public_default_acls()`: runs the reset as the superuser, then recounts through the loading role's own connection. Every failure path exits 1.
  - `check_acl_fidelity()`: reads the catalogue and runs the gate. DRIFT or a read failure is FATAL.
  - Both are called inside `load_baseline()`.
- `scripts/local-stack/reset-public-default-acl.sql`: the derived reset. It RAISEs if any `public` row survives, and prints `acl-reset: removed N … (grantor roles: …); 0 remain`.
- `scripts/local-stack/acl-fidelity.mjs` and `acl-fidelity-catalogue.sql`: the ACL-fidelity gate.
  - **Expected ACL:** built per object as `acldefault(owner)` plus the dump's GRANT/REVOKE lines, applied in order.
  - **Compared with:** `aclexplode(relacl/proacl)` for every `public` table-class relation, sequence and function, and `pg_default_acl` on `public` against the dump's ALTER DEFAULT PRIVILEGES lines.
  - **Not compared:** column-level grants live in `attacl`, which default ACLs never touch, so they are counted and skipped.
  - **Exit codes:** an unparsed dump shape, an object the dump grants on but the lane lacks, or an empty catalogue each exit 2 (MEASURE_FAIL). Drift exits 1.
- `src/__tests__/local-stack-lane-wiring.test.ts`: two new arms, the structural pin and the gate's behaviour.

### Root cause (verified before relying on it)

- **The CLI pulls from ghcr.io.** `supabase/setup-cli` exports `SUPABASE_INTERNAL_IMAGE_REGISTRY: ghcr.io`, and the drift-check log prints that value in the env of every step after it. The VAC-04 step log then shows `17.6.1.104: Pulling from supabase/postgres`.

### Decisions

- **Login method: a plain `docker login`, not `docker/login-action`.** The step is `printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u "$GHCR_USER" --password-stdin`, run under `set -euo pipefail`. `GHCR_TOKEN` is `${{ github.token }}` and `GHCR_USER` is `${{ github.actor }}`, both passed through `env:` and never interpolated into the script. Why: ci.yml's C-0293 header exists to keep a write-capable token away from third-party actions. A shell step hands the token to no third party, and it adds no new SHA pin to keep current. The token goes in over stdin and is never printed. It is placed immediately after `setup-cli` in all five jobs, so it runs before any CLI command. In `restore` it also runs before the mutex acquire, so a failed login stops the job before it touches shared TEST.
- **Permissions.** Each of the five jobs gets its own `permissions:` block. A job-level block REPLACES the workflow-level one, so each block restates the workflow's scopes and adds only `packages: read`. That is `contents: read` + `packages: read` for the three ci.yml jobs and drift-check `check`, and `contents: read` + `actions: read` + `packages: read` for `restore`. No other scope was widened, and no workflow-level block changed.
- **Fork PRs: fail loudly.** Of the five, only the three ci.yml lane jobs run on fork PRs; drift-check is same-repo-gated, and restore is dispatch-only on `main`. A fork PR's token is read-only, and read-only still reads public packages, so a fork has no reason to fail the login. If one ever does, the step fails the job. There is no `continue-on-error` and nothing swallows the error. Why: a swallowed failure turns back into the anonymous pull, which trades a named red at the login step for an intermittent throttle-shaped red at the boot step.
- **D-18 kept.** ci.yml still holds 0 occurrences of the prober workflow's name. The ci.yml comments do not name it.

### Guard test: `src/__tests__/contracts/ghcr-login-before-image-pull.contract.test.ts`

For every `setup-cli` job, the test derives PULLING vs NOT PULLING from the job's commands. A command must begin a line, follow `run:` or sit inside `$(`, so an `echo` that only quotes one does not count. The derived sets must equal the two pinned rosters exactly, so a new setup-cli job forces a decision and a broken detector cannot pass on an empty set. For each pulling job, the test requires:

- a ghcr.io login before the first pulling step, using `--password-stdin`, `github.token` and `github.actor`, under `set -euo pipefail`;
- no `continue-on-error` and no `|| true`;
- job permissions exactly equal to the workflow block plus `packages: read`.
