## D-F's open sub-question, CLOSED FROM EVIDENCE by the planner (reversible; no checkpoint)

**The marker's form: a FULL LIST of carried migration basenames, not a frontier version.**
MEASURED at planning time: across `git log --diff-filter=A` of `supabase/migrations/`, **5**
timestamp-versioned migrations were committed AFTER a migration with a HIGHER version already
existed (e.g. `20260513094906_enable_pg_cron.sql` landed after
`20260515210400_commit_scenario_batch_high_hardening.sql`), and `supabase-migrate.yml` applies with
`db push --include-all`, which exists precisely to apply such files. A frontier ("the dump carries
everything up to version V") would classify such a file as carried, never replay it, and boot the
lane green on a schema missing it — this repo's signature defect. A full list cannot make that
mistake. It is also depth-independent: it reads files on disk, so the epoch guard's documented
shallow-clone vacuity (two identical commit times comparing equal) does not exist for it.

**Why the marker is bound to the dump's sha256.** DECISION F forbids inferring the carried set
from commit dates, and requires it to come from BASELINE.md's regeneration record or an equivalent
machine-readable marker. A list that can drift from the dump is not evidence of the dump. Binding
the list to `sha256(baseline.sql)` makes "the founder regenerated the dump but not the list" a
named, loud defect instead of a silent mis-replay.

**Bootstrap content, measured, not assumed.** BASELINE.md's `### Regenerated 2026-09-23` record
states the current dump (sha256 beginning `efe49c15`) was taken AFTER Phase 167's migration applied
to PRODUCTION on merge commit `2091fea6`, and names `20260922120000_api_keys_sync_status_sign_in_failed.sql`

## How a replayed file is applied — REVISED 2026-09-23 after plan-check (supersedes the earlier `--single-transaction` design)

The first draft of this plan ran each replayed file with `psql --single-transaction` together with
its ledger INSERT and claimed the two were atomic. MEASURED at `1ab74411` by the plan checker, and
re-counted by the reviser on this branch: **182** migrations carry a top-level `BEGIN;` / `COMMIT;`
pair, and **4** carry a top-level `CREATE INDEX CONCURRENTLY`
(e.g. `20260516170400_portfolio_analytics_computing_idx_concurrently.sql`, whose own header says
CONCURRENTLY cannot run inside a transaction block and the file is deliberately non-transactional).
Under `--single-transaction`, a file's own `COMMIT;` ends psql's outer transaction early, so the
ledger row is NOT atomic with the migration (the atomicity claim was false for two thirds of the
corpus), and a top-level CONCURRENTLY statement errors, making the lane FATAL and every lane job red
the first time such a migration is newer than the dump. The tracer probe (one bare `CREATE TABLE`)
exercised neither shape.

**The design now:** each replayed file is applied AS AUTHORED — `psql -X -v ON_ERROR_STOP=1 -f <file>`
in psql's default autocommit mode, with NO lane-added wrapper — so the file's own transaction control
governs it and a top-level CONCURRENTLY statement runs outside any transaction block, as its author
intended. Only when that psql exits 0 does a SEPARATE psql call write the file's ledger row. A
failure anywhere is FATAL and the EXIT trap tears the ephemeral stack down, so a partially applied
file can never be tested against. ⚠️ What this does NOT claim: byte-identical client-protocol
semantics with the Supabase CLI's own apply; it claims D-F's shape — each file in filename order, as
authored, ledger row after success. Recorded so the next reader does not re-add a wrapper "for
safety" and re-break CONCURRENTLY.

## Reference data vs replay — REVISED 2026-09-23 after plan-check

`load_reference_data` runs `scripts/extract-reference-inserts.mjs` in its emit mode, which slices the
statements named by `scripts/restore-test-refdata-allowlist.txt` out of `supabase/migrations/`, and it
runs BEFORE the replay. The CI `--audit` mode (its `audit-unlisted` arm) FORCES an allowlist line for
any new top-level reference INSERT into an allowlisted table — so a new migration seeding, say,
`public.compute_job_kinds` will be allowlisted in the same PR that adds it. If extraction still read
every allowlisted file, that statement would execute twice on the lane (once extracted, once in the
replay — plain `VALUES`, no `ON CONFLICT`), or once BEFORE the table it targets exists when the same
migration creates that table. Both are boot-FATAL. The ordering argument "reference rows predate a
migration newer than the dump" holds only for CARRIED migrations.

**The design now:** the gate's replay mode, which already owns the replay set, also writes a FILTERED
copy of the allowlist with exactly the lines whose first tab-separated field is a replay basename
removed (comment and blank lines kept), and prints how many it dropped and which. `load_reference_data`
passes that file to the extractor with `--allowlist`; the extractor itself is unchanged (it already
accepts `--allowlist`, and emit mode reads only the files the allowlist names). A replayed migration's
own statements then run exactly once, natively, in the replay, in filename order. The TEST restore
path does not use the lane and keeps reading the full allowlist. ⛔ Do NOT filter with a shell
`grep -F` over basenames (a replay basename quoted in a carried line's comment field would drop that
carried line) or with awk's `NR==FNR` idiom (with an EMPTY replay file — K=0, today's normal case — it
treats the allowlist as the key file and emits nothing).
