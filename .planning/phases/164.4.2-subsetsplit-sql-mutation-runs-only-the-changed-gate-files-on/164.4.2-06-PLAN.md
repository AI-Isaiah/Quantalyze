## D-F's open sub-question, CLOSED FROM EVIDENCE by the planner (reversible; no checkpoint)

**The marker's form: a FULL LIST of carried migration basenames, not a frontier version.**
MEASURED at planning time: across `git log --diff-filter=A` of `supabase/migrations/`, **5**
timestamp-versioned migrations were committed AFTER a migration with a HIGHER version already
existed (e.g. `20260513094906_enable_pg_cron.sql` landed after
`20260515210400_commit_scenario_batch_high_hardening.sql`), and `supabase-migrate.yml` applies with
`db push --include-all`, which exists precisely to apply such files. A frontier ("the dump carries
everything up to version V") would classify such a file as carried, never replay it, and boot the
lane green on a schema missing it — this repo's signature defect. A full list cannot make that
mistake. It is also depth-independent: it reads files on disk, so the epoch guard's documented
shallow-clone vacuity (two identical commit times comparing equal) does not exist for it.

**Why the marker is bound to the dump's sha256.** DECISION F forbids inferring the carried set
from commit dates, and requires it to come from BASELINE.md's regeneration record or an equivalent
machine-readable marker. A list that can drift from the dump is not evidence of the dump. Binding
the list to `sha256(baseline.sql)` makes "the founder regenerated the dump but not the list" a
named, loud defect instead of a silent mis-replay.

**Bootstrap content, measured, not assumed.** BASELINE.md's `### Regenerated 2026-09-23` record
states the current dump (sha256 beginning `efe49c15`) was taken AFTER Phase 167's migration applied
to PRODUCTION on merge commit `2091fea6`, and names `20260922120000_api_keys_sync_status_sign_in_failed.sql`
as the complete set added since the prior capture. MEASURED: `git ls-tree 2091fea6 supabase/migrations/`
lists **273** `*.sql` files, and they are exactly this branch's 272 plus that one. The bootstrap
marker is therefore those 273 basenames. Every basename measured matches `^[0-9]+_[a-z0-9_]+\.sql$`
(0 exceptions), and no two share a version prefix (0 duplicates).

**Why "dump carries a migration this checkout lacks" is a defect, not a warning.** The lane would
then test the checkout's code against a schema its own migrations do not produce. On a
`pull_request` CI runs the merge ref, so this arises only on a stale local branch; the remedy is
to bring the base branch in, and the message must say so. ⚠️ THIS BRANCH IS IN THAT STATE RIGHT
NOW (the dump carries the Phase 167 migration; the branch does not) — hence the precondition.

**Where the replayed migrations' ledger rows come from.** D-F says the replay has "the same
forward-apply shape `db push` performs", and `db push` writes one `supabase_migrations.schema_migrations`
row per applied migration, in the same transaction. The lane does the same. Carried migrations get
a row too, with a statements value saying they were carried by the dump and NOT executed on the
lane — the same provenance-sentence convention `scripts/restore-test-from-baseline.sh` uses. A
ledger holding only replayed rows would tell two corpus files
(`test_create_wizard_strategy_for_key.sql`, `test_get_verified_cohort_rank_gate.sql`, both of which
read that table as an applied-ness oracle and RAISE when it is absent) that 273 applied migrations
never ran. ⚠️ Whether the lane has that table at all today is UNMEASURED — the plan-04 capability
probe has no ledger class — so Task 1 measures it before changing anything.
