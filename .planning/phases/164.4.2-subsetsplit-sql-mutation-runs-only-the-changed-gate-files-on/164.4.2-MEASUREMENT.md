## Recipe

Run verbatim, reproducible at any later head with different run ids substituted.

**Step 1 — enumerate merge-push runs of `ci.yml`:**
```bash
gh run list --workflow=ci.yml --branch main --event push --json databaseId,headSha,createdAt,conclusion --limit 12
```
Take the most recent runs that CONCLUDED (`conclusion` non-empty; skip cancelled and in-progress
— an in-progress run reports `conclusion: ""`, not `null`). Use at least 5.

**Step 2 — per run id, pull per-step timings for the three mutex-holding jobs:**
```bash
gh api "repos/AI-Isaiah/Quantalyze/actions/runs/<run_id>/jobs?per_page=100" \
  -q '.jobs[] | select(.name=="sql-tests" or .name=="python" or .name=="e2e-seeded") | {name, started_at, completed_at, steps: [.steps[] | {name, started_at, completed_at}]}'
```

**Step 3 — per run id, pull the run's own wall-clock:**
```bash
gh api "repos/AI-Isaiah/Quantalyze/actions/runs/<run_id>" -q '{run_started_at, updated_at, status, conclusion}'
```

**Per run, per job, four quantities are derived from the step timestamps returned by Step 2:**
- **acquire-wait** — duration of the step whose name begins `Acquire shared-test-db mutex`
- **useful work** — duration of the job's own work step (`sql-tests`: `Run SQL self-tests against
  test Supabase project`; `python`: `Run pytest --cov=...`; `e2e-seeded`: `Run seed-gated specs
  (MA-8 / BLOCK-3)`)
- **job-total** — the job's own `started_at` → `completed_at` (top-level object from Step 2, not a
  step)
- **run-total** — the workflow run's own `run_started_at` → `updated_at` (Step 3)

Durations were computed with a small Node script (`new Date(b) - new Date(a)`, rounded to the
nearest second) rather than by hand, to avoid transcription arithmetic errors in a document that
stays in the repo.

If a job is absent from a run (a skip), it is recorded as ABSENT with the reason from its `if:` —
never as a zero. **No job was absent from any of the 6 runs captured below.**

## Refutation condition — decided in advance (DECISION E)

⛔ **The original text is kept here as lineage and MUST NOT be used:** *"if `sql-tests`'s
acquire-wait does not fall to approximately zero, the change did not work."* This was corrected
in `164.4.2-CONTEXT.md` on 2026-09-21, before any code in this phase existed, because the plan
removes `sql-tests`'s mutex-acquire step outright — its post-change acquire-wait is zero **by
construction, not by observation**, so a prediction the change cannot fail to satisfy measures
nothing (the vacuous-gate class this phase and Phase 164.9 both exist to remove).

**THE REPLACEMENT — copied verbatim from `164.4.2-CONTEXT.md` Area E, binding on this phase:**

**a. The run's critical path must fall.** Baseline is captured above, over 6 (>= 5 required)
concluded merge-push runs. If the post-change critical path does not move outside that baseline's
spread — for the non-degenerate band, **16m18s–18m50s** — the change did not work; say so and
re-measure.

**b. The win must not merely RELOCATE.** `sql-tests`'s acquire-wait is replaced by local-stack
BOOT time on the same job. Its own **job-total wall-clock** must fall, not just its wait. A job
that swapped 5m05s–8m01s of queueing (the BEFORE range above) for a comparable amount of booting
has moved the cost, not removed it, and must be reported as such. BEFORE `sql-tests` job-total
range: **8m31s–29m32s** (8m31s–9m23s on the non-degenerate runs).

**c. The REMAINING holders must not absorb the freed time.** `python`, `e2e-seeded`, and the new
`test-db-drift` job (created by plan 05, which still holds the shared key for the VAC-08 drift
check that used to live inside `sql-tests`) still contend for key `61616158`. If their combined
acquire-wait rises by roughly what `sql-tests` gave up, the queue simply redistributed and the
run did not get cheaper. BEFORE combined acquire-wait (python + e2e-seeded + sql-tests) on the
non-degenerate runs: **12m05s–14m56s**. Measure all four jobs in the AFTER table (plan 08), not
just the one that changed.

⭐ **One additional clause this plan adds on measured grounds, marked as such** (not part of the
original Decision E text, added per this plan's Task 2 instruction): after plan 05 the VAC-08
drift check lives in its own `test-db-drift` job that still holds the shared key — the AFTER
table (plan 08) MUST include that job by name, alongside `sql-tests`, `python`, and `e2e-seeded`.
⛔ A win that merely moved the wait into a new job is not a win, and reporting it as one would be
the measurement equivalent of a vacuous gate.

**d. A faster wall clock alone does NOT confirm it.** CI wall-clock varies with runner
availability and queue depth — the two 62-minute runs above prove this: their wall-clock inflation
comes entirely from cross-run/cross-workflow mutex contention, not from `sql-tests`'s own behavior.
The binding number is `sql-tests`'s own acquire-wait and job-total, because those are the
quantities the change acts on directly. A run that got faster while acquire-wait stayed high got
lucky, and recording that as success would be the measurement equivalent of a vacuous gate.

**Summary — four independently-falsifiable clauses, none satisfiable by construction:**
(a) critical path moves outside the BEFORE spread, (b) `sql-tests` job-total falls (not just its
wait), (c) the remaining three holders (`python`, `e2e-seeded`, `test-db-drift`) don't absorb the
freed time, (d) a faster wall clock alone is not read as confirmation. Any one of these can come
out wrong, and each must be checked independently against the tables above, at the same commit
range and with the same recipe, when plan 08 captures the AFTER measurement.
