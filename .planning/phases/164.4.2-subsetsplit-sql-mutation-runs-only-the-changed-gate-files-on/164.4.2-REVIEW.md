## Warnings

### WR-01: A git-quoted path under `supabase/tests/` bypasses the SUBSET vacuity fence

**File:** `scripts/classify-changed-paths.mjs` (`changedFilesAgainstBase`), consumed by `scripts/sql-gate-subset.mjs` (`judge`)
**Issue:** `git diff --name-only` quotes any path that contains a non-ASCII byte, a tab, a newline, a backslash or a double quote (`core.quotePath`). For example, it prints `"supabase/tests/test_\303\251.sql"`. The leading `"` means `p.startsWith(GATE_DIR_PREFIX)` is false. The path is therefore neither in `underGateDir` nor in `nonConforming`, so it is silently dropped. The `nonConforming` rule, which is documented to force FULL on any odd name under `supabase/tests/`, never sees it.

Reproduced in a scratch repo: one commit adding `test_ok.sql` and `test_é.sql` printed the second as a quoted escape. If the same PR also changes an annotated gate, the verdict is SUBSET over the ordinary file. The quoted file is a `*.sql` that the runner's full scan and `sql-tests` would pick up, and its arms go unmutated on the PR. For the docs-only classifier the same quoting fails safe (the file reads as code). For the subset derivation it fails open.
**Fix:** Read NUL-separated names so git never quotes:
```js
return git(["diff", "--name-only", "--no-renames", "-z", `${baseRef}...HEAD`])
  .split("\0")
  .filter(Boolean);
```
Or, at minimum, make `judge` return FULL for any changed path that starts with `"`.

### WR-02: `MACHINERY_PREFIXES` omits the gate-pattern module that the runner itself imports

**File:** `scripts/sql-gate-subset.mjs` (`MACHINERY_PREFIXES`)
**Issue:** `scripts/mutation-runner/run.mjs` imports `GATE_FILE_RE` from `scripts/sql-gate-subset.mjs`, and `readSubsetList` uses it to refuse a list. That makes the module part of the mutation machinery, but it sits outside `scripts/mutation-runner/`. A PR that edits `sql-gate-subset.mjs` (the pattern, `judge`, or the prefix list) and touches one gate file gets a SUBSET run. The machinery that decided the subset is then never exercised against the full corpus before merge. The same applies to `scripts/classify-changed-paths.mjs`, whose `changedFilesAgainstBase` is the one diff both callers share.
**Fix:**
```js
export const MACHINERY_PREFIXES = [
  "scripts/mutation-runner/",
  "scripts/pg-lane/",
  "supabase/migrations/",
  "scripts/sql-gate-subset.mjs",
  "scripts/classify-changed-paths.mjs",
];
```
Add a self-test row for each new entry, so `EXPECTED_ASSERTIONS` moves with the list.

### WR-03: A SUBSET run checks no arm floor at all, so a PR that deletes arms only goes red after merge

**File:** `scripts/mutation-runner/run.mjs` (`runCorpus`, the `if (subset)` branch that replaces the `ARMS_FLOOR` comparison), and `.github/workflows/ci.yml` (`sql-mutation` step `Assert the run PRINTED its coverage and cleared both floors`, the early `exit 0` for SUBSET)
**Issue:** Take a PR whose only change is to delete one or more `RED-UNDER` arms from a gate file, while keeping at least one arm. It gets a SUBSET of that file. `FILES_FLOOR` still holds and `ARMS_FLOOR` is not compared, so the PR is green. The regression surfaces only on the push to `main`. Project policy has branch protection off, so every gate is advisory at merge, and a red on `main` after merge is the only signal. The runner already scans the whole corpus in subset mode (the `scope:` denominator comes from it).

Deliberately not comparing the subset's *biting* count is correct: that count only covers the listed files. But a static necessary condition is available at no lane cost. Full-corpus annotated arms minus waivers is an upper bound on full-corpus biting arms. If that bound is already below `ARMS_FLOOR`, the push-to-main run is certain to fail.
**Fix:** In subset mode, parse every annotated file statically, as `--parse-only` does, and add a `floor` defect when `(annotated − waived) < armsFloor`. Print it as `ARMS_FLOOR (static upper bound): N annotated-unwaived >= floor F`. Keep the "biting NOT compared" line as it is.

### WR-04: The replay's meta-command refusal only catches a backslash at the start of a line

**File:** `scripts/check-baseline-currency.mjs` (`judgeReplaySet`, the `replay-meta-command` loop), which feeds `scripts/local-stack/run.sh` (`replay_migrations`, `psql -f` per file)
**Issue:** The check is `/^[ \t]*\\/`. psql recognises a backslash command anywhere on a line outside quotes, so `SELECT 1; \! cmd`, `SELECT 1 \i other.sql` or `COMMIT; \o /tmp/x` pass the gate and are executed by `psql -f` on the runner. The `sql-mutation` preflight on the same files already uses a mid-line form (`(^| )\\!`). The `sql-tests` preflight scans only `supabase/tests/test_*.sql`, so replayed migrations in `sql-tests`, `frontend-local-stack` and `frontend-live-db-lane` get only this narrower check. On `pull_request` the PR controls its own workflow, so this is not a trust boundary. It is still a refusal that promises "refuse any backslash-led line … before psql opens it" and misses the mid-line shape.
**Fix:** Scan a quote-aware masked text instead of raw lines. `maskSql` from `scripts/lint-sql-gates.mjs`, which `nonpublic-objects.mjs` already imports, blanks string and dollar-quoted content. Then refuse any `\\[A-Za-z!?]` left in code positions. At minimum, match `(^|\s)\\[A-Za-z!]` in the same way the `sql-mutation` preflight does.

### WR-05: The default-mode currency gate reads a shallow clone as fresh, contrary to its own header

**File:** `scripts/check-baseline-currency.mjs` (`readEpoch` / `main` default mode; the header paragraph that says a shallow clone "prints nothing")
**Issue:** In a `--depth 1` clone, HEAD is a grafted root commit that introduces every path. So `git log -1 --format=%ct -- <path>` prints HEAD's timestamp for both the baseline file and the migrations directory. The two epochs are equal, and equal counts as fresh.

Reproduced in a scratch repo:
- Full clone: baseline epoch < migrations epoch, so the verdict is `baseline-stale`.
- Depth-1 clone of the same history: both epochs are equal, so there are no defects.

The header says the opposite ("a shallow clone … prints nothing … Treating 'could not measure' as 'measured fresh' would let a CI runner with a shallow checkout pass this gate vacuously"). This mode's only caller is the restore path, and that workflow checks out with `fetch-depth: 0`, so the problem is latent today. Because the gate's protection is described but not implemented, a future caller without `fetch-depth: 0` passes it vacuously on a destructive path.
**Fix:** Refuse by name before reading epochs:
```js
const shallow = execFileSync("git", ["rev-parse", "--is-shallow-repository"], { encoding: "utf8" }).trim();
if (shallow !== "false") { /* push a named 'history-shallow' defect and return 1 */ }
```
Add the kind to `DEFECTS` with a self-test arm. Alternatively, correct the header so it no longer claims the refusal.

## Info

### IN-01: The default-ACL reset double-quotes an already-quoted role name

**File:** `scripts/local-stack/reset-public-default-acl.sql` (the `EXECUTE format('ALTER DEFAULT PRIVILEGES FOR ROLE %I …', r.defaclrole::regrole::text, …)`)
**Issue:** `regrole::text` already quotes an identifier that needs quoting, and `%I` quotes it a second time. The statement would then name a nonexistent role. Only roles that need quoting are affected; the roles present today do not, so the finding is latent.
**Fix:** Use `%s` with `r.defaclrole::regrole::text`, or `%I` with the unquoted `pg_roles.rolname`.

### IN-02: Self-tests print a raw `fatal:` git line into CI logs

**File:** `scripts/classify-changed-paths.mjs` (`git()`, used by `changedFilesAgainstBase`)
**Issue:** `execFileSync` inherits stderr. The deliberate unreadable-ref self-test arm (run by both `classify-changed-paths.mjs --self-test` and `sql-gate-subset.mjs --self-test`) therefore prints `fatal: ambiguous argument 'origin/gsd-self-test-no-such-base-ref...HEAD'` above a PASSED verdict in `changed-paths`. A reader triaging a red run can mistake it for the cause.
**Fix:** Pass `stdio: ["ignore", "pipe", "pipe"]` and include `e.stderr` in the `MEASURE_FAIL` message.

### IN-03: Extracted cron jobs are registered active and fire during corpus runs

**File:** `scripts/local-stack/nonpublic-objects.mjs` (`check` requires `active = t`), with `scripts/local-stack/run.sh` (`load_nonpublic_objects`)
**Issue:** The lane registers 15 jobs as the loading role, and the gate requires them to be active. Some run every 15 minutes or hourly (the stuck-computing reaper, the orphaned-running retention, the dropped-enqueue sweep). A corpus or live-DB run that crosses one of those wall-clock minutes has a real background writer touching `compute_jobs` and `strategy_analytics`. This matches PROD and shared TEST, and files that use a transaction are insulated. It is still a timing-dependent input that a flaky-test triage should know about.
**Fix:** Name it in the lane header. Optionally, have `sql-corpus-report.mjs` print the cron minutes the run spanned.

### IN-04: The prose in another workflow still names `sql-tests` as a lock holder

**File:** `.github/workflows/analytics-deploy-verify.yml` (the advisory-lock triage bullet). This file is outside the reviewed list, and the change here left it stale.
**Issue:** The bullet still lists `sql-tests` among the jobs that can go red on the shared-test-db advisory lock. After this phase, `sql-tests` holds no key, and `test-db-drift` does.
**Fix:** Replace `sql-tests` with `test-db-drift` in that bullet, or add a dated correction, as the runbook does.

A `cron.schedule(...)` inside a `CREATE FUNCTION … $$` body, or in an untaken DO branch, is registered on the lane anyway. The fidelity `check` rebuilds its expectation from the same fold, so it cannot see the error. Fix: refuse, loudly, any cron call inside a non-DO dollar body.
