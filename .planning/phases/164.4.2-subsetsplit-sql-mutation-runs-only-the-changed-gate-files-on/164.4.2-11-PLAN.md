**The loading roles, and why.** Evidence is repo-only. The tracer boot is the first observation,
and its SUMMARY records it.
- **cron registration runs as the loading role `postgres`** (the lane's `db_url`):
  - `cron.schedule` stamps `cron.job.username = current_user`.
  - All 16 rows of the PROD manifest carry `username: "postgres"`.
  - The corpus reads `cron.job` as `postgres`, which plan 08 measured is NOT a superuser.
    pg_cron's row-level security on `cron.job` shows a non-superuser only its own jobs, so jobs
    registered as `supabase_admin` would be invisible to the very files they exist for.
  - Registering as the superuser would also run every job with superuser rights, a catalogue
    WIDER than PROD's. That is the class of plan 08's ACL defect.
  - ⚠️ If the boot shows `postgres` lacks EXECUTE on `cron.schedule`, the boot FATALs loudly; it
    does not silently switch roles. The documented alternative is to register through the
    superuser with `cron.schedule_in_database(…, username => 'postgres')`. The row it yields is
    identical, and the gate checks `username`. Take it ONLY on that measured refusal, and record
    the refusal in the SUMMARY.
- **The `auth.users` trigger is created through the stack SUPERUSER DSN**, derived exactly as
  `reset_public_default_acls()` derives it (the lane's loopback DSN with the role swapped; a DSN
  not starting with the `postgres` role is refused):
  - `auth.users` is owned by the auth service role, and the `postgres` role's TRIGGER privilege
    on it on this image is unmeasured.
  - A trigger has no owner, so the object is identical whoever creates it.
  - `handle_new_user()` is SECURITY DEFINER and owned per the dump, so runtime behaviour does not
    change.

**Why the trigger loads AFTER reference data, not in PROD's chronological order.**
- The reference-data allowlist replays the teaser sentinel `auth.users` row, then its sentinel
  `public.profiles` row (`ON CONFLICT (id) DO NOTHING`).
- With the trigger already in place, `handle_new_user()` would create the profile first, with
  different values, and the allowlisted row would silently no-op.
- Loading after reference data reproduces the TEST restore's state, where `auth.users` survives,
  the sentinel insert no-ops and the profile gets the migration's explicit values. That is the
  state the corpus was historically green against, and it is plan 08's current 67-file baseline.

**How double registration is avoided (D-F × D-G).**
1. The extraction folds ONLY the gate's carried set. A replayed file's cron and trigger statements
   run once, natively, inside `replay_migrations`, exactly as `db push` runs them on PROD. This
   mirrors how the filtered reference-data allowlist keeps a replayed migration's INSERTs out of
   `load_reference_data`.
2. A replayed reschedule supersedes by name rather than appending. pg_cron's `cron.schedule`
   upserts by name, and `20260803120000_strategy_analytics_stamp_trigger_null_stamp_clock_start`
   asserts exactly that. All 20 calling files also use the house unschedule-if-exists pattern.
3. A replayed plain `CREATE TRIGGER` of an existing name FATALs the replay, as it would on PROD,
   which already carries the trigger. That is fidelity, not a lane defect.
4. The drift gate runs BEFORE the replay and compares against the carried fold. The reasoning is
   `check_acl_fidelity`'s, recorded as plan 08 deviation 1: a replayed migration may legitimately
   change these objects, so the dump plus the carried fold is the fixed point the gate can be exact
   about. Today's replay set is empty, so the carried fold IS the full declared set.

- **The `--file` contract.** `--file <path>` is repeatable and narrows the run. A `--file` path

  skip: a file can print `SKIP:` from an early `DO` block and then fail on a later statement, and
  calling that a SKIP would hide a real failure behind a status that reads as "nothing to test
  here". FAIL is the louder of the two, and the louder label wins. The precedence is therefore
  LANE-ONLY (decided before running) → FAIL → SKIP → PASS.
