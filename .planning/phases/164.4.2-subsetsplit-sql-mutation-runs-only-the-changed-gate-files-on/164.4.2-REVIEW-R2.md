## Warnings

### WR-01: The WR-04 lexer passes a meta-command that psql executes once a file sets `standard_conforming_strings = off` (WR-04 not closed)

**File:** `scripts/check-baseline-currency.mjs` (`psqlMetaCommandLines`, the `'…'` branch), consumed by `judgeReplaySet` and then by `scripts/local-stack/run.sh` (`replay_migrations`, `psql -f`)
**Issue:** The lexer always reads a plain `'…'` literal with standard-conforming rules: a backslash is ordinary and only `''` escapes a quote. psql's lexer does not work that way. It follows the server's `standard_conforming_strings`, which is reported back after every `SET`. A migration can switch it off and then write:

```sql
SET standard_conforming_strings = off;
SELECT 'a\'' ; \! touch <scratch>/PWNED #'
;
```

- **The lexer's reading:** one literal running from the first `'` to the last, so no backslash in code and `{"lines":[]}`.
- **psql's reading:** `'a\''` is the whole literal, so `\! touch … #'` is a shell command.

**Measured:** applied through `scripts/pg-lane/run.sh --apply`, which uses psql on a file as the replay does. The marker file appeared, and the lexer returns `{"lines":[]}` for the same bytes. The fix's header says the lexer is "psql's own lexer's view". That claim is false for this input.

As the round-1 review noted, a PR controls its own workflow, so this is not a trust boundary. It is still a refusal that promises more than it checks. None of the 273 migrations mention `standard_conforming_strings` today.

**Fix:** Refuse by name any replay file that changes string-escaping mode. It cannot be lexed statically once the mode is data-dependent:
```js
if (/\bstandard_conforming_strings\b|\bbackslash_quote\b/i.test(text)) {
  push("replay-meta-command", `${r} changes string-escaping mode, so where psql reads a backslash as a command cannot be proven statically.`);
  continue;
}
```
Add an R10 arm with the input above, and raise `EXPECTED_ASSERTIONS` by one.

### WR-02: The single loopback rule accepts a comma multi-host DSN whose first host libpq connects to (WR-08 not closed)

**File:** `scripts/local-stack/capability-probe.mjs` (`refuseNonLocalDsn`). Since the fix round it is the only guard in `run.sh` (`load_baseline`, `probe_function_denial_survives`), in the `ci.yml` `sql-tests` corpus step, and in `scripts/local-stack/sql-corpus-report.mjs`.
**Issue:** The two parsers split the authority at different `@` characters. `new URL()` splits at the LAST `@`. libpq splits at the FIRST `@`, then reads a comma-separated host list. Take this DSN:

```
postgresql://u@db.example.invalid,@127.0.0.1:54322/postgres
```

- **`new URL()`:** `hostname=127.0.0.1`, `port=54322`, empty search, so `refuseNonLocalDsn` returns `null` (accepted).
- **libpq (`PQconninfoParse`, measured offline):** `host='db.example.invalid,@127.0.0.1'`, `port=',54322'`. The first host is `db.example.invalid` on the default port, and libpq tries it first.

The round-1 finding was titled "one parse-based check". The fix removed the `*@127.0.0.1:*` glob everywhere and named this function as the rule that closes "userinfo smuggling". That makes this gap in the rule the gap in every lane DSN gate. It is not a regression (the old glob accepted the same string). But WR-08 is recorded as closed, and the guard exists so that "TEST is shared and PROD is PROD".

**Fix:** Reject any DSN whose authority libpq would read differently from WHATWG. That means more than one `@`, or a `,` anywhere in the authority:
```js
const authority = String(dsn).replace(/^[a-z]+:\/\//i, "").split(/[/?#]/)[0];
if ((authority.match(/@/g) ?? []).length > 1 || authority.includes(",")) {
  return "the handoff's DB_URL carries a second '@' or a host list, which libpq parses differently from a URL parser";
}
```
Add the DSN above to the `capability-probe.mjs` self-test refusals and to the WR-08 test table in `local-stack-lane-wiring.test.ts`.

### WR-04: a non-ASCII identifier character before `$tag$` opens a false dollar body in `psqlMetaCommandLines`
psql reads bytes `\200-\377` as identifier characters, so `é$a$` is one identifier. The lexer's check on the preceding character is ASCII-only, so it opens a body at `$a$` and hides a `\!` on the next line. The fix is to treat code points at or above U+0080 as identifier characters, both before the `$` and inside the tag, and to add a test arm with the reproducer.

### WR-05: the WR-07 SUBSET name check largely compares the input list with itself
`SQL_GATE_FILES` is the list the runner was given, so the check proves the runner mutated its input list, not that the derivation was right. Reword the error to "…than the list changed-paths handed it", or re-derive the list in the assert step.

### WR-07: the WR-01 quoted-path self-test cannot fail on a machine with `core.quotePath=false`
