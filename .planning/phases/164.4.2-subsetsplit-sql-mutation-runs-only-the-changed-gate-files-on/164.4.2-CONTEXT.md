## AREA B — Which jobs move, and is it all-or-nothing? **A TRACER FIRST, and `sql-tests` is it.**

The three mutex holders in `ci.yml` are `sql-tests`, `python` and `e2e-seeded`.

**DECISION B:** `sql-tests` moves first, alone, as the tracer. Reasons, in order:
1. **It has the worst measured ratio** — 8.02 min of waiting to do 0.78 min of work on a typical
   18.2-min run. The largest win per unit of risk.
2. **Its workload is the most self-contained** — it runs `supabase/tests/test_*.sql` against a
   database. It needs a schema, not a booted application, an authenticated browser session, or a
   Python worker.
3. ⚠️ `e2e-seeded` needs seeded rows AND a running app; `python` runs pytest with its own fixture
   surface. Moving all three at once changes three workloads and one lock in a single step, and a
   post-change measurement would not tell you which one moved the number.

⛔ **All-or-nothing is explicitly rejected**, and not because it is harder: with one job moved,
the mutex still exists and the remaining holders still serialise, so the tracer's win is
MEASURABLE IN ISOLATION against the same key. That is what makes Area E falsifiable.

## AREA D — Half A's subset rule, and the vacuity fence

**DECISION D:** On a `pull_request`, `sql-mutation` runs only the gate files whose content
changed against the PR's merge base. On a push to `main`, it runs the FULL corpus — a merge is
the moment the full picture is owed, and it is also the only place a subset could hide a
regression introduced by an interaction between two PRs.

⛔ **THE VACUITY FENCE IS NOT OPTIONAL, AND IT IS THE POINT OF THIS AREA.** This repo has a
MEASURED class of gates that PASS having measured nothing; **164.9 closed six of them.** A subset
runner is the most natural seventh. Binding rules:
- An EMPTY change set is **not** a pass. It either runs the full corpus or fails loud. ⛔ It never
  reports "0 files changed, nothing to do" as success.
- An UNREADABLE diff base is a **failure**, never an empty set. ⚠️ `git diff` against a missing
  ref exits non-zero and prints nothing; a naive pipeline reads that as "no files changed".
- The run must PRINT the narrowed scope and the corpus size it was narrowed FROM, every run.
- ⛔ A narrowed run must never be recorded, logged or reported as full coverage.
- ⛔ `FILES_FLOOR` / `ARMS_FLOOR` are computed against the FULL corpus and do not move because a
  subset ran. A subset run that "passes the floor" by narrowing the denominator is the exact
  defect this fence exists to prevent. Read all three BY SYMBOL from
  `scripts/mutation-runner/run.mjs`.

⛔ **Nothing in this phase raises `sql-mutation`'s `timeout-minutes`.** It is a declared ceiling
of 20 that has spent its one permitted raise (2026-09-05). The subset rule IS the answer to a
crossing.

## AREA E — How the win is FALSIFIED

⛔ **Decided BEFORE it is built, so the change cannot be graded on its own narrative.**

**The prediction (ROADMAP):** removing contention should land the typical run near **11–12 min**,
bounded by `sql-mutation` at 10.8.

**DECISION E — the falsifying measurement:**
1. **Baseline, captured BEFORE any change lands**: for the last N merge-push runs of `ci.yml`,
   record per job — `sql-tests`, `python`, `e2e-seeded` — the acquire-wait and the useful work,
   and the run's wall-clock critical path. ⚠️ Capture it from `gh` run/job timings, not from
   memory, and record the run ids.
2. **After the tracer lands**, re-measure the SAME quantities on merge-push runs at the new head.
3. ⛔ **THE REFUTATION CONDITION — ⛔ CORRECTED 2026-09-21, BEFORE ANY CODE WAS WRITTEN, because
   the original was UNFALSIFIABLE.**

   ⛔ **The original text is kept here as lineage and MUST NOT be used:** *"if `sql-tests`'s
   acquire-wait does not fall to approximately zero, the change did not work."*

   ⚠️ **Why it was wrong.** The plan removes `sql-tests`'s mutex-acquire step outright, so its
   post-change acquire-wait is zero **BY CONSTRUCTION, not by observation**. A prediction that
   the change cannot fail to satisfy measures nothing — it is the vacuous-gate class this phase
   and Phase 164.9 both exist to remove, and it was sitting in this document's own success
   criterion. Found by the plan-checker, as an INFO advisory, before a line of code existed.

   ⭐ **THE REPLACEMENT, and each clause can come out WRONG:**
   a. **The run's critical path must fall.** Baseline is captured in `164.4.2-MEASUREMENT.md`
      over >= 5 concluded merge-push runs. ⛔ If the post-change critical path does not move
      outside that baseline's spread, the change did not work — say so and re-measure.
   b. ⛔ **The win must not merely RELOCATE.** `sql-tests`'s acquire-wait is replaced by
      local-stack BOOT time on the same job. **Its own job-total wall-clock must fall**, not just
      its wait. A job that swapped 5m05s of queueing for 5m of booting has moved the cost, not
      removed it, and must be reported as such.
   c. ⛔ **The REMAINING holders must not absorb the freed time.** `python`, `e2e-seeded` and the
      new `test-db-drift` still contend for key `61616158`. If their combined acquire-wait rises
      by roughly what `sql-tests` gave up, the queue simply redistributed and the run did not get
      cheaper. Measure all four jobs, not the one that changed.
   ⚠️ **A faster wall clock alone still does not confirm it** (see 4 below) — but a critical path
   that does NOT fall now genuinely refutes, which the original condition could not.
4. ⚠️ **A faster wall clock alone does NOT confirm it.** CI wall-clock varies with runner
   availability and queue depth. The binding number is `sql-tests`'s own acquire-wait, because
   that is the quantity the change acts on. A run that got faster while acquire-wait stayed high
   got lucky, and recording that as success would be the measurement equivalent of a vacuous gate.

## AREA F — Migrations that land AFTER the baseline dump (added 2026-09-23, founder decision)

**The gap.** DECISION A makes the currency guard REFUSE a baseline older than
`supabase/migrations/`, and nothing in plans 01–09 keeps the baseline current. Consequences, once
`sql-tests` runs on the ephemeral lane:
- every migration merge makes the committed dump stale, and the lane stays red until the founder
  takes a fresh schema-only dump from PRODUCTION, which is legitimate only AFTER that migration
  has applied there (behind the `Production` reviewer gate);
- a PR that ADDS a migration cannot exercise its own gate on the lane at all, because the lane's
  schema is a PROD dump that predates it.
Surfaced by the founder on 2026-09-23, while Phase 167's migration
(`20260922120000_api_keys_sync_status_sign_in_failed.sql`) was about to merge ahead of this phase.

**DECISION F (founder, 2026-09-23): the lane REPLAYS the migrations newer than the baseline.**
`load_baseline()` loads `baseline.sql` and then applies, in filename order, exactly the
`supabase/migrations/*.sql` files the dump does not already carry — the same forward-apply shape
`db push` performs on PROD. A migration newer than the dump is then the NORMAL case, not a defect.
- The currency guard's job changes from "refuse" to "bound and name": it must print WHICH
  migrations were replayed on every run (never silent), and must still fail loud when the set
  cannot be determined, or when a replayed migration errors.
- Refreshing the dump becomes periodic upkeep that shrinks the replay set. It stops being a
  per-migration founder action.
- A PR's own new migration is replayed on the lane BEFORE merge, which also narrows the
  applied-ness coupling CLAUDE.md records as `[164.8-PUSH-RACE-VAC08]` (b) for `sql-tests`.
- ⛔ "Which migrations does the dump already carry?" must be MEASURED from the dump, never
  inferred from commit dates alone. BASELINE.md's regeneration record names the migrations each
  dump carries, and that record, or an equivalent machine-readable marker, is the source.
- ⛔ The rejected alternative, recorded so nobody reopens it without new evidence: keeping the
  refusal and re-dumping per migration. It turns every migration into a manual founder step and
  leaves the lane unable to test a PR's own migration.

**Sequencing.** Plan 05 was already executing when this was decided, and it is left to finish:
the replay is additive to the lane loader and does not change what plan 05 moves. DECISION F is
realised by a replan of the remaining plans (`/gsd-plan-phase 164.4.2`), BEFORE plan 06 executes.

## AREA G — PROD objects OUTSIDE `public` that the lane lacks (added 2026-09-23, founder decision)

**The gap, measured.** Plan 08's SHA-bound CI read (run `35886515179` at `25135a99`) failed
`sql-tests`. The first cause was a lane ACL defect, fixed in plan 08's checkpoint-RED section.
With that fixed, the whole corpus run on the local lane (continuing past failures) still leaves
**8 of 76 files failing**. All 8 fail because the lane has no PROD objects that live outside
`public`, which the schema-only dump of `public` does not carry:
- **the trigger on `auth.users`** that creates a profile for a new user (1 migration declares
  it): 0 non-internal triggers on `auth.users` on the lane; 3 files fail;
- **the `pg_cron` job registrations** (24 migrations call `cron.schedule`): 0 rows in `cron.job`
  on the lane; 5 files fail.

Plan 04's capability probe measured that the lane *hosts* `pg_cron` and the auth functions,
reported `SUFFICIENT`, and the founder chose PROCEED on that reading. It did not measure whether
the lane carries the *objects PROD registers* in those schemas. That is the gap this area closes.
Shared TEST never showed it, because the TEST restore drops and rebuilds only `public` and leaves
`auth` and `cron` in place.

**DECISION G (founder, 2026-09-23): the lane REPLAYS these objects from the migrations.**
After `baseline.sql` loads, and before the DECISION F replay of newer migrations, the lane applies
the non-public objects PROD carries, EXTRACTED from the migration files. This is the same pattern
the reference-data extractor already uses:
- the `auth.users` trigger, from the migration that declares it;
- every `cron.schedule` registration, taken from the migrations in the order they declare them,
  and superseded or unscheduled exactly as later migrations do.
- A check proves the lane carries exactly the set the migrations declare, can be seen failing,
  and fails the boot on drift. It is never a warning.
- ⛔ The 8 failing SQL files are NOT edited, marked LANE-ONLY, or excused. They are correct; the
  lane is incomplete.
- ⛔ Rejected alternatives, recorded so nobody reopens them without new evidence:
  (1) **widening the dump** to include `auth` triggers and `cron.job` rows. It is another manual
  PROD dump per change, and `cron.job` is data rather than schema.
  (2) **moving `sql-tests` back to shared TEST.** It reintroduces the shared-TEST contention this
  phase exists to remove.

**Sequencing.** Realised as a new plan in this phase, planned via `/gsd-plan-phase 164.4.2` and
executed BEFORE plan 08's CI checkpoint is re-read. Plans 09 and 10 stay behind it.
