## Fixed Issues

### WR-01: The replay lexer passed a meta-command once a file set `standard_conforming_strings = off`

**Status:** fixed (requires human verification: logic)
**Files modified:** `scripts/check-baseline-currency.mjs`
**Commits:** e10c64548, then c2d71b722 (a correction, measured)
**Applied fix:** `psqlMetaCommandLines` refuses, by name, any replay file that mentions one of these:
- `standard_conforming_strings`
- `backslash_quote`
- `client_encoding`
- `SET NAMES`

It goes wider than the review asked. `client_encoding` also changes psql's lexing: in an encoding that is not ASCII-safe, a lead byte swallows the next byte, and that byte can be a quote. The refusal comes back as "cannot be proven", a `replay-meta-command` defect. The header no longer claims to be "psql's own lexer's view" without qualification. It names the settings it assumes, and it names one **known limit**: a setting whose name is built at run time (concatenation, an `E'…'` escape, `chr()`, dynamic `EXECUTE`) is not seen. As the review said, this is a guard against accident, not a trust boundary.

⚠️ **Correction, found by measurement in this round.** e10c64548 also continued an `E'…'` literal across a newline in E mode. That follows the server's grammar, not psql's, and it opened a bypass. A `scripts/pg-lane/run.sh` run on psql 16 measured two shapes:
- **Shape 1:** `SELECT E'a'` followed by `'\' ; \! cmd #'` on the next line. psql closed the second literal at `'\'` and **ran `cmd`**, while the e10c64548 lexer flagged nothing.
- **Shape 2:** `SELECT E'a'` followed by `'\'' ; \! cmd #'`. psql ran nothing, and e10c64548 refused it wrongly.

psql reads its input one line at a time, so the literal on the next line is a new plain literal to psql. c2d71b722 removes the continuation logic and pins shape 1. With the same-mode continuation put back, that arm goes RED.

c2d71b722 also skips to the end of the line after it flags a backslash, because psql passes the rest of the line to the meta-command as arguments. This only makes the refusal detail more precise.

**Measured on psql 16, same pg-lane run:** each of these shapes ran its shell command:
- the reviewer's `standard_conforming_strings = off` reproducer;
- `é$a$`;
- a `$é$` tag;
- `1E'\'`.

**Tests:** R10 has 7 new arms, and `EXPECTED_ASSERTIONS` is now 47:
- the escaping-mode reproducer;
- `client_encoding`, `SET NAMES` and `backslash_quote`;
- the non-ASCII identifier (SFH WR-04);
- the non-ASCII tag;
- the next-line literal;
- a number or `$n` run straight into an identifier character;
- a CONTROL of valid shapes.

Before the fix, 6 of these arms were RED; the CONTROL passed on the old lexer too. Each guard went RED again when neutered on its own.

### SFH WR-04: A non-ASCII identifier character before `$tag$` opened a false dollar body

**Status:** fixed (requires human verification: logic)
**Files modified:** `scripts/check-baseline-currency.mjs`
**Commit:** e10c64548 (shared with WR-01)
**Applied fix:** The lexer now consumes identifiers whole, following psqlscan.l's `ident_start`/`ident_cont`. Those treat every code point at or above U+0080 as an identifier character, and `$` continues an identifier. So `é$a$` is one identifier.

Dollar tags accept non-ASCII characters and no longer have an 80-character cap. A number or `$n` run straight into an identifier character is refused, because psql's junk-token rules differ between versions. On psql 16, `1E'…'` measured as the junk token.

The reproducer was reshaped so it closes cleanly under the new reading. On the old lexer it returned `{"lines":[]}`; on psql 16 it ran its shell command.

⚠️ **The one failure, so it is not read as clean.** `ci-anti-skip-gate.contract.test.ts` > "refuses a handoff whose DB_URL is not loopback, before any file reaches psql" timed out at the 5000 ms default during the full-suite run. The load average was about 15. Run alone, the file passes 33/33, and that test takes 2654 ms.

The time comes from round-1 WR-10's non-vacuity control. It drives the gate over the real corpus once before the refusal run, which roughly doubles the test. This round added only string assertions to that test. The timeout was not relaxed, per the rules.

This is a **flake risk on a loaded CI runner**. One option is to point the control at a one-file corpus through `runGate`'s `cwd` argument. That was not done here, because it changes a round-1 test design outside these findings.

**Lane runs.** Only `scripts/pg-lane/run.sh` was used, under `gsd-164.4.2-dbrun.lock`, which was released afterwards. The runs measured how psql 16 treats the WR-01 / SFH WR-04 shapes and the next-line literal. No supabase or psql command was run against any remote, and uvicorn was never started.

**Not covered here:**
- No `scripts/local-stack/run.sh up` was run. This round did not edit `run.sh`: IN-03 changed only a test, and `run.sh` was neutered and restored byte-exact.
- `node scripts/mutation-runner/run.mjs --self-test` was not re-run, because `run.mjs` was not edited this round. The `ARMS_FLOOR` raise for IN-01 was temporary and was restored byte-exact.
- The psql measurements cover psql 16, the local pg-lane binary. The CI runner's psql may be a different major version. The lexer refuses shapes whose reading depends on the version (junk tokens) instead of guessing.

**Root-cause option, not taken.** The escaping-mode refusal is by name, so a name built at run time can get past it. The alternative that would close this in the replay itself: stop letting psql scan the file as a script. For example, send each replay file as one query (`psql -c`) so meta-commands are never parsed. That changes transaction semantics (an implicit transaction per file, which breaks `CREATE INDEX CONCURRENTLY`), and it needs a Docker-backed `run.sh up` to verify. It is recorded here for a decision and was not attempted in the final fix round.
