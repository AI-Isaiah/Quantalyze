## §1 — Area A: the currency guard

**The behaviour already exists exactly once**, inside `refuse_stale_baseline()` in
`scripts/restore-test-from-baseline.sh`:

```bash
refuse_stale_baseline() {
  local b_ts m_ts
  b_ts=$($FRESHNESS_TS_CMD "$BASELINE_FILE" 2>/dev/null | head -1 | tr -d '[:space:]')
  m_ts=$($FRESHNESS_TS_CMD "$MIGRATIONS_DIR" 2>/dev/null | head -1 | tr -d '[:space:]')
  case "$b_ts" in ''|*[!0-9]*) fail "FRESHNESS_TS_CMD printed no epoch for ${BASELINE_FILE} ..." ;; esac
  case "$m_ts" in ''|*[!0-9]*) fail "FRESHNESS_TS_CMD printed no epoch for ${MIGRATIONS_DIR} ..." ;; esac
  if [ "$b_ts" -lt "$m_ts" ]; then
    fail "the baseline dump is STALE: ${BASELINE_FILE} last changed at epoch ${b_ts}, ${MIGRATIONS_DIR} at ${m_ts}. ..."
  fi
}
```
(symbol `refuse_stale_baseline`, `scripts/restore-test-from-baseline.sh`; config lines
`BASELINE_FILE="${BASELINE_FILE:-supabase/schema/baseline.sql}"`,
`MIGRATIONS_DIR="${MIGRATIONS_DIR:-supabase/migrations}"`,
`FRESHNESS_TS_CMD="${FRESHNESS_TS_CMD:-git log -1 --format=%ct --}"` — all three env-overridable, which
is exactly how the self-test injects fixture times without touching the real repo clock).

Two idioms to copy, from two different files:

1. **The comparison itself** — `git log -1 --format=%ct -- <path>` on both sides, `case` guards
   that refuse a non-numeric epoch BY NAME before the `-lt` comparison ever runs (`fail
   "FRESHNESS_TS_CMD printed no epoch..."` — an unreadable timestamp is never treated as fresh).
   This is the one behaviour to relocate or share; CONTEXT.md Area A is explicit that renaming
   `check-baseline-staleness.mjs` to match its weaker sha-only behaviour is a forbidden closure —
   the currency logic must move to (or be called from) BOTH `restore-test-from-baseline.sh` and
   `scripts/local-stack/run.sh`, not be re-derived twice.

2. **The "library + `--self-test`-able CLI" shape** for a NEW shared script — the cleanest
   full-file analog is `scripts/check-baseline-staleness.mjs` itself (a DIFFERENT concern —
   INTEGRITY not CURRENCY — but the EXACT shape this phase needs for the currency gate):
   - `export const DEFECTS = [...]` — named defect kinds, not booleans.
   - a **pure** `export function judge({...facts})` — all I/O happens in `main()`, `judge()` takes
     already-read facts and returns a defect array. This is what lets `--self-test` drive the real
     decision logic instead of a parallel copy of it.
   - `export const EXPECTED_ASSERTIONS = N` — the self-test's own assertion count is PINNED and
     checked at the end (`if (asserted !== EXPECTED_ASSERTIONS) { ...FAILED... }`), so a deleted
     arm cannot pass silently as a smaller green number.
   - `function invokedDirectly()` — realpath-safe main-module guard (`realpathSync(process.argv[1])
     === realpathSync(fileURLToPath(import.meta.url))`), the `[VAC04-C2]` lesson: a bare
     `import.meta.url` vs `file://${argv[1]}` compare no-ops on symlinked/space-bearing paths and
     silently turns a CLI into a library. Same idiom in `scripts/lint-app-guc.mjs` and
     `scripts/classify-changed-paths.mjs`.
   - `main(argv)` returns an exit code; the module only calls `process.exit()` under the
     `invokedDirectly()` guard, so a future importer (a vitest contract test, the way
     `scripts/classify-changed-paths.mjs`'s `judge()` is imported by
     `ci-docs-path-filter.contract.test.ts`) never gets killed at import time.
   - Prints one always-on summary line even on the clean path (`baseline=... bytes=... defects=0`)
     so "clean" and "did not run" never look alike.

   **`scripts/shared-test-db-keys.sh`** is the SHELL equivalent of this same "sourceable library +
   `--self-test` CLI" shape (`if [ "${BASH_SOURCE[0]}" = "${0}" ]; then ... --self-test ...; fi`,
   deliberately no `set -euo pipefail` at top level because it is meant to be sourced). Since the
   currency check must be called from a **bash** caller (`restore-test-from-baseline.sh`) AND
   plausibly from `scripts/local-stack/run.sh` (also bash), this is the stronger shape match for
   the currency guard specifically if it stays a `.sh`; `check-baseline-staleness.mjs`'s shape is
   the stronger match if it becomes a `.mjs` invoked via `node` from both bash callers (which is
   how `restore-test-from-baseline.sh` already treats `check-baseline-staleness.mjs`'s regex —
   "the SAME regex … its exported RECORDED_SHA_RE … A second opinion here would be a second
   drift"). Either concrete choice is a legitimate reading of CONTEXT.md's "library and a
   `--self-test`-able CLI" question; both idioms exist in this repo today, cited above.

**Wiring precedent** (how a shared script gets called from CI, both self-test and real mode, gated
on a path filter) — `sql-function-snapshot.yml`:
```yaml
- run: node scripts/check-baseline-staleness.mjs --self-test
- run: node scripts/check-baseline-staleness.mjs
```
with `paths:` filters naming `scripts/check-baseline-staleness.mjs` itself on both the `push` and
`pull_request` triggers. `test-restore-from-baseline.yml` runs the identical two-line pair. This is
the pattern for wiring the new currency guard into whichever job(s) end up calling it.

**The insertion point on the `local-stack` side** is `load_baseline()` in
`scripts/local-stack/run.sh`, immediately before its `FATAL: no schema baseline at ...` check and
the `psql ... -f "$BASELINE_FILE"` load — the exact position `refuse_stale_baseline` occupies in
`restore-test-from-baseline.sh`'s own call order (filesystem-only refusals fire before the first
connection).

## §2 — Area B: `sql-tests` off the shared mutex, onto its own database

**`sql-mutation`'s job-level shape in `ci.yml` is the target, not the local-stack jobs.** All three
— `sql-mutation`, `frontend-local-stack`, `frontend-live-db-lane` — share "no secret, no shared
resource, runs identically on a fork PR" and all three sit in the `frontend`/aggregator's **strict
default arm** (their own comments cross-reference each other on this point). But CONTEXT.md Area B
says `sql-tests`'s workload is "the most self-contained — it runs `supabase/tests/test_*.sql`
against a database. It needs **a schema, not a booted application**" — that rules out the
Supabase-CLI local-stack path (Postgres + PostgREST + GoTrue, booted via `supabase start`,
`timeout-minutes: 20-30`, needs `psql` installed as a separate step) as the analog, and points at
`scripts/pg-lane/run.sh` (bare disposable Postgres, no PostgREST/GoTrue, sub-second boot,
`--print-pgbin` / `--self-test` / `--tracer-proof` CLI contract) — the thing `sql-mutation` already
uses for exactly this reason.

**What to copy from `sql-mutation`'s job comment block** (`sql-mutation:` in `ci.yml`):
- The **aggregator classification argument itself**: "no secret, no repo variable, no shared
  resource, no `if:` — so this job runs identically on a fork PR ... and a `skipped` result is
  ALWAYS a real fault... takes the aggregator's STRICT default arm with NO tolerance... The
  DB-touching jobs' ban on new `needs:` edges does NOT apply here." A migrated `sql-tests` earns
  the identical argument once it drops the shared secret and the mutex, and the plan should quote
  this reasoning rather than re-derive it.
- **What does NOT change**: `permissions:` and `concurrency:` stay inherited from workflow level
  ("matching `sql-gate-lint` and every other job here... Restating them per-job would fork two
  sources of truth").

**What must be DELETED from `sql-tests`'s current shape when it moves** (so the plan can diff
against a known "before"): the `needs: [python, changed-paths]` mutex-ordering edge and its long
⛔ comment block, the `vars.E2E_TEST_DB_CONFIGURED` / fork-author `if:` gate, the "Wait for the TEST
schema apply to conclude" step (`bash scripts/wait-for-test-schema-apply.sh`), and the entire
"Acquire shared-test-db mutex" step (`pg_advisory_lock(61616158)` background holder, keepalive
params, `HOLDER-BACKEND-PID` marker). All of that machinery exists **only** because `sql-tests`
writes the shared TEST project; an ephemeral-DB `sql-tests` needs none of it, by the same argument
`sql-mutation`'s header already makes for itself.

**What must be KEPT, unchanged, from `sql-tests`'s current shape**: the "Preflight - reject psql
meta-commands in test files" step (Finding 6) — that preflight defends against a malicious commit
inside THIS repo, not against the shared-TEST threat model, so it applies identically to gate files
run against a throwaway lane. Keep it verbatim.

**Provisioning idiom** (how a job gets its own DB) — copy the shape from `sql-mutation`'s pg-lane
invocation (`scripts/pg-lane/run.sh --workdir <scratch> --apply <migrations...> --gate <gate.sql>`)
rather than the local-stack `up`/`down`/`--assert-teardown` triple. `pg-lane/run.sh`'s own header
states its CLI contract is "pasted VERBATIM into ci.yml... an A/B that changes invocation mode is
not an A/B" — treat that contract as fixed and drive `supabase/tests/test_*.sql` through it as a
`--gate`-equivalent run rather than inventing a new boot path. `sql-tests` needs the **full**
migration chain applied (all of `supabase/migrations/`), not the baseline-only load
`local-stack`/`pg-lane`'s mutation runner use for gate corpora — check `scripts/pg-lane/run.sh`'s
`--apply <file.sql> [<file.sql> ...]` contract against how many migrations it is asked to replay
per lane today (the mutation runner applies specific migrations per gate, not the whole chain) before
assuming it can be pointed at "every migration" unmodified — this is a real open question for the
plan, not a solved one, and CONTEXT.md's own precondition note under Area A applies here too: the
migration chain does NOT cleanly replay in this repo (`scripts/local-stack/REPLAY-SPIKE.md`: "262
migrations, 69 fail"). If `sql-tests` needs the true chain rather than a baseline snapshot, that
REPLAY-SPIKE finding is a live blocker for Area B and should be surfaced to the planner rather than
assumed away.

## §3 — Area D, part 1: the subset derivation ("which gate files changed")

**Strongest analog in the repo: `scripts/classify-changed-paths.mjs`.** It already solves the
generic shape of "which files changed against the PR's merge base, fail-closed on anything
ambiguous" that Decision D asks for, one directory below where the new subset runner would live:

```js
const baseRef = process.env.GITHUB_BASE_REF ? `origin/${process.env.GITHUB_BASE_REF}` : "origin/main";
changedFiles = git(["diff", "--name-only", "--no-renames", `${baseRef}...HEAD`])
  .split("\n")
  .filter(Boolean);
// on exception: `MEASURE_FAIL: could not read ${baseRef} — ${e.message}` + exit 1 (never "0 files")
```
(symbol `main`, `scripts/classify-changed-paths.mjs`). Copy directly:
- **`--no-renames` is called out as MANDATORY**, not stylistic — with rename detection a moved gate
  file would print only the destination path, silently losing "this file changed" for the source
  side. The same argument applies to a moved/renamed `supabase/tests/test_*.sql` file.
- **argv passed as an execFileSync ELEMENT, never shell-interpolated** — `GITHUB_BASE_REF` is
  attacker-controlled on a fork PR.
- **the exact fail-closed split CONTEXT.md Area D asks for is already this file's split**: an
  unreadable/failed `git diff` is a `MEASURE_FAIL` + exit 1 (never reported as zero changed
  files); a **successfully-read but EMPTY** diff is handled by the pure `judge()` — in
  `classify-changed-paths.mjs` empty ⇒ "CODE" (run everything), which is the direct precedent for
  Decision D's "an empty change set... either runs the full corpus or fails loud."
- **`judge(changedFiles)`** is a pure function tested via a `CASES` fixture table with a derived
  terminal count (`for (const c of CASES) ...`, count NOT hand-typed) — same self-test shape as
  §1's `check-baseline-staleness.mjs`, reusable almost verbatim for "is this changed file one of
  the annotated `supabase/tests/test_*.sql` gate files".
- **`emit(value, reason)`** writes one human-readable summary line AND appends to
  `$GITHUB_OUTPUT` when present, else no-ops — the shape for handing the derived subset from a
  preflight step to the step that invokes the mutation runner.

**Second analog, for the "derive, never hand-list, and floor it" half**:
`scripts/live-db-lane-corpus.mjs` — `export const CORPUS_FLOOR = 49` (symbol; read the LIVE value
off the file, this number is illustrative of the shape only) and:
```js
if (files.length === 0) { /* MEASURE_FAIL: EMPTY CORPUS ... */ return 1; }
if (opts.root === DEFAULT_ROOT && files.length < CORPUS_FLOOR) { /* MEASURE_FAIL: CORPUS COLLAPSED ... */ return 1; }
```
Its header states the argument for WHY derived-not-listed matters here too: "A static list goes
stale silently and in the ONE direction that reads as success... deriving from the gate symbol
means a newly gated spec is picked up by the next run, with nobody remembering anything" — same
shape as "a new annotated gate file must be picked up by the subset runner without a second list to
maintain." Its two-layer floor idiom — `CORPUS_FLOOR` in the derivation script bounds the LOWER
side, a vitest contract test re-derives and fails on the STALE-LOW direction — is the repo's
general answer to "a floor must move only in one direction," reusable for whatever ceiling/floor
Area D's own subset step ends up needing beyond `FILES_FLOOR`/`ARMS_FLOOR` themselves.

## §4 — Area D, part 2: the load-bearing finding — `--file` is NOT a gate mode

**This is the central technical fact the planner needs, and it contradicts the tempting shortcut
of "just call `run.mjs --file <changed file>` per changed gate file."**

`scripts/mutation-runner/run.mjs` already has a narrowed-scope mode (`--file <gate.sql>` /
`--arm <ID>`), but it is explicitly a **diagnostic** mode, deliberately incapable of a passing exit:

```js
const narrowed = Boolean(onlyFile || onlyArm);   // symbol `narrowed`, runCorpus()
...
if (narrowed) {
  log("");
  log("⚠️ NARROWED DIAGNOSTIC RUN (--file/--arm): coverage floors NOT enforced.");
  log("   This mode never exits 0, so it can never be mistaken for a passing gate.");
} else {
  if (corpus.filesAnnotated < filesFloor) { addDefect("floor", ..., "FILES_FLOOR regression..."); }
  if (bitingArms < armsFloor) { addDefect("floor", ..., "ARMS_FLOOR regression..."); }
  if (armsWaived > waivedCeiling) { addDefect("floor", ..., "WAIVED_CEILING exceeded..."); }
}
...
exitCode: defects.length > 0 ? 1 : narrowed ? 2 : 0   // symbol in same function
```
(both in `runCorpus`, `scripts/mutation-runner/run.mjs`). A green `--file` run exits **2**, never
0. It also accepts exactly **one** `--file` today (`parseArgs`/`main`'s `for` loop overwrites
`onlyFile` on a repeat flag rather than accumulating a list) — there is no multi-file narrowing at
all yet.

**Consequence for the plan:** the subset runner cannot be "wire the existing `--file` flag into
CI." It needs either (a) a genuinely NEW mode/flag on `run.mjs` (e.g. a `--files <list>` or
`--subset` argument) that is explicitly distinct from the diagnostic `--file`/`--arm` path — CAN
exit 0 when its narrowed set is clean, while still printing the CONTEXT.md-required "narrowed scope
and the corpus size it was narrowed FROM" line and while `filesFloor`/`armsFloor` stay computed
against the **full** corpus (`FILES_FLOOR = 48`, `ARMS_FLOOR = 423`, `WAIVED_CEILING = 0` — read
these three **by symbol** from `scripts/mutation-runner/run.mjs`, per CONTEXT.md's own instruction;
they have drifted from restated prose four times already) — or (b) a wrapper script that composes
`run.mjs`'s existing corpus-walk/annotation-parsing internals directly rather than shelling out to
the diagnostic CLI mode. Either way, `runCorpus`'s existing `filesFloor`/`armsFloor`/`waivedCeiling`
as **overridable named parameters** (`filesFloor = FILES_FLOOR, armsFloor = ARMS_FLOOR, waivedCeiling
= WAIVED_CEILING` — default parameters, `runCorpus` signature) is what already lets a caller pass
floors explicitly, which is the seam a new subset-run caller would use to say "enforce nothing
against this narrowed count, but still print what the full corpus's floors are" — never silently
comparing the narrowed run against a narrowed floor (CONTEXT.md's explicit forbidden closure).

**Vacuity-fence idioms to copy for the new subset step's CI wiring** (all inside `ci.yml`):
- **Non-empty-corpus preflight**, verbatim shape from `frontend-local-stack`'s `Preflight - the
  lane must have a non-empty test corpus` step: run the collector, `tee` to a file, `[ ! -s <file>
  ] && { echo "::error::..."; exit 1; }` — collect-only, no stack/lane needed yet.
- **Captured-stdout + named-line MEASURE_FAIL**, verbatim shape from `sql-mutation`'s own steps
  (`ci.yml`, search `lane-blocked:`/`lane-probe:`):
  ```bash
  the_line=$(grep -a -m1 -E '^some-marker: [0-9]+ ...' "$RUNNER_LOG" || true)
  if [ -z "$the_line" ]; then
    echo "::error::MEASURE_FAIL: the run printed NO 'some-marker: …' line, so <what we needed to know> is unknown."
    exit 1
  fi
  claimed=$(echo "$the_line" | sed -E '...')
  case "$claimed" in ''|*[!0-9]*) echo "::error::MEASURE_FAIL: could not read the count out of '$the_line'."; exit 1;; esac
  ```
  This is the exact shape for a step that asserts "the subset run printed the narrowed-scope line
  and the full-corpus-size-it-was-narrowed-from line" — both required by CONTEXT.md Area D — and
  refuses to pass if either is silently absent. Note the `|| true` after the `grep` is called out
  as LOAD-BEARING under `set -euo pipefail` (an empty-but-present count must not abort the step
  before the numeric guard runs) — copy that detail, it is a real footgun in this idiom.
- **`passWithNoTests: false`** — `vitest.livedb.config.ts` / `vitest.local-stack.config.ts` both
  set it; irrelevant if the subset runner never goes through vitest, but the general "a config-level
  belt alongside the preflight suspenders" idea is the same one CONTEXT.md's fence describes as
  multiple independent controls rather than one.

## §5 — Area E: before/after CI timing — no in-repo script analog

**Measured:** no file under `scripts/` wraps `gh api .../actions/runs` or `.../jobs` for per-job
acquire-wait / useful-work timing. `mutex-probe.yml` proves the mutex SERIALIZES (pairwise
non-overlapping hold windows) but does not measure or record wall-clock cost; it is a correctness
drill, not a timing tool. Every historical timing figure in this repo's own docs (the "8.02 min of
waiting to do 0.78 min of work," "81.6 min of pure acquire-wait across three jobs," the `python`
job's TTL-derivation comment) was pulled ad hoc via `gh` and recorded as prose in a PLAN/ROADMAP/
CONTEXT file, never committed as a reusable script.

The one committed idiom worth reusing is procedural rather than a script: this repo's own
`CLAUDE.md` names the SHA-bound counting discipline —
```bash
gh api "repos/AI-Isaiah/Quantalyze/actions/runs?head_sha=<sha>" -q '.workflow_runs | length'
```
— "count the checks and bind them to the head SHA," because a green board can under-report
(cancelled/skipped runs read as "no red," not as "did not run"). The planner should treat Area E's
deliverable as a **measurement recipe recorded in the plan/verification doc** (run ids + SHAs named
explicitly, per Decision E's own "capture it from `gh` run/job timings... record the run ids"),
not as a new permanent `scripts/` file — there is no existing precedent in this repo for a
committed CI-timing tool, and inventing one where none exists would be new surface without an
analog to justify its shape.

## Shared Patterns (cross-cutting, apply to every new/modified file in this phase)

### "Library + `--self-test`-able CLI"
**Sources:** `scripts/check-baseline-staleness.mjs` (JS: pure `judge()`, `EXPECTED_ASSERTIONS`
pin, `invokedDirectly()` realpath guard), `scripts/shared-test-db-keys.sh` (bash: sourceable,
`--self-test` only when executed directly), `scripts/classify-changed-paths.mjs` (JS variant with
a `CASES` fixture table and derived terminal count).
**Apply to:** the new Area A currency guard, and any new Area D subset-derivation script.

### Fail-closed on ambiguity, never silently empty
**Source:** `scripts/classify-changed-paths.mjs` — unreadable diff base ⇒ `MEASURE_FAIL` + exit 1;
successfully-read-but-empty diff ⇒ handled by `judge()`'s own explicit rule (here: run the full
corpus). **Apply to:** Area D's subset derivation, verbatim requirement from CONTEXT.md.

### Derive the corpus, never hand-list it; floor the derivation, never the floor
**Source:** `scripts/live-db-lane-corpus.mjs` (`CORPUS_FLOOR`, empty-corpus MEASURE_FAIL,
"stale-low direction caught one layer up by a vitest contract test"). **Apply to:** Area D.

### Captured-stdout, named-line MEASURE_FAIL
**Source:** `sql-mutation` job steps in `.github/workflows/ci.yml` (`lane-blocked:`/`lane-probe:`
grep-and-assert pattern, `|| true` under `set -euo pipefail` called out as load-bearing).
**Apply to:** any new CI step in Area D/B that must prove it actually measured something rather
than passing on an absent signal.
