### Why the books are still untrustworthy (evidence)

- The stored `degrade_reasons` of ranks 2 and 3 are the same before and after the deploy. The only blocking one is `dropped_key` (`no_anchor`, `stale_mark_carry` and `window_truncated` are benign).
- By the compose rule (`allocator_equity_compose.py`, `unanchored_return_keys`) a key that has a return series and a NULL anchor, and is not named native-unit or native-unpriced, yields `no_anchor` plus `dropped_key`. The stored inputs hold such keys: allocator 2 has 2 (one Deribit key of account 3 with anchor reason `dust` and 649 return days, and one MT5 key with reason `dust` and 357 days); allocator 3 has 1 (an MT5 key with reason `nonpositive` and 326 days); neither is the options-holding account.
- Reproduced in scratch with main's compose code on the stored post-deploy inputs: Deribit accounts 1 and 2 together give `trustworthy` (benign `stale_mark_carry` and `window_truncated` only); adding the account-3 key gives exactly `dropped_key, no_anchor, stale_mark_carry, window_truncated`, the stored set; the options-holding account alone gives no degrade reason at all. The MT5 keys were not replayed (no MT5 inputs were read), so the allocator-3 attribution to its MT5 key rests on the stored anchors and the rule, not on a replay.
- The same compose code of the pre-PR-2 build (`1f9a5e0fb`), run on the same stored inputs, gives `inception_unreconciled` for the options-holding account. That reproduces what the fix removed. It does not match the stored BEFORE books, which already lacked that token on 2026-10-11 although plan 05 recorded it on 2026-10-10. Something between those two derives (not PR-2, which had not run) removed the token from the stored books; the BEFORE readings did not capture flags and the old rows are gone, so the cause is unestablished. The claim made here is therefore the replay's (old code reads the token, new code does not, on identical inputs), not a stored before-to-after change of that token.
