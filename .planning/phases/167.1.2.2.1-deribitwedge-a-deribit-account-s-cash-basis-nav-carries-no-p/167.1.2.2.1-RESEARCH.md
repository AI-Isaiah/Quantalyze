## Summary

The refusal "non-positive reconstructed equity on 755 of 1200 day(s)" is reproduced exactly from the stored PROD inputs at the worktree HEAD (one counted Deribit key; replay with the repo's own `replay_key_equity`). Two independent defects stack (AND-gate, as the debug note says): a writer defect that plants a constant native BTC balance the account does not hold, and a compose rule that refuses a level that is exactly or nearly zero. Both are fixable in this phase. The third defect class the founder folded in (non-determinism, SC-6) is the same writer defect plus a second leak the debug note did not find: the unread `session_rpl`.

The writer defect is not only "`options_session_upl` is subtracted twice". Deribit's official identity is `equity = balance + futures (session UPL + RPL) + options mark value`, and `balance` "Does not include open futures PnL or options mark value". The cash_settlement wedge is `futures_session_upl + options_session_upl + options_value`, so the rolled terminal is `balance + futures_session_rpl - options_session_upl`: it carries one wrong term (`options_session_upl`, subtracted although `options_value` already contains it) and one missing term (`futures_session_rpl`, never read). Both move with live state. Measured on today's code with a hermetic perturbation matrix: an options mark drift changes 3 of 5 return days, a `session_rpl` accrual changes 3 of 5, a futures `session_upl` drift 0 of 5, a live index-price drift 0 of 5. The cleanest fix is to anchor the cash-basis terminal on the documented cash `balance` (wedge = `equity - balance`), which removes both terms and makes §5 reconcile the txn-log sum to the venue's cash balance directly.

On PROD the affected set is small and measured: 3 connected Deribit venue accounts (8 keys). One (3 keys, 1188 return days, option positions recorded) moves: its three sibling derives, run within about 40 minutes of each other, disagree on 371 to 373 of 1188 days (max |dr| 0.0060). The other two accounts' sibling derives are byte-equal on all 649 and 376 days. Two private composites also include one member from each account.

**Three findings change the plan's shape.** (1) With the compose fix alone, the refused allocator composes (755 emptied days, 2 stretches) but reads `inception_unreconciled` (blocking, untrustworthy) because its implied pre-deposit capital is +1.31% of the first-return-day level against a 0.01% band; removing the phantom offset makes it larger, not smaller (about +1.5%). So the headline "refused allocator reads a trustworthy v2 book" is NOT reachable by SC-1 + SC-3 alone; SC-5 is on the critical path. (2) SC-2's cap and SC-5 are coupled: if that residual is a native pre-history residual that `is_dust` currently absorbs, a cap turns the account's derive into a permanent `InceptionReconciliationError`. The cap must be sequenced behind a measurement. (3) D-03's capture and SC-1's identity read and SC-5's measurement are one additive change (store the account-summary snapshot and the native inception numbers in the `key_inputs` payload), so it ships first.

**Primary recommendation:** Ship in this order: (A) additive capture of the account-summary snapshot + native inception numbers into `key_inputs` (no value change) so the identity read and the SC-5 measurement arrive at the next 05:30 UTC derive; (B) the balance-anchored cash wedge (SC-1) + emptied-stretch compose rule (SC-3) + determinism tests (SC-6), all with RED-first fixtures; (C) the `is_dust` cap (SC-2) only after (A)'s reading shows the cap does not strand the account; (D) SC-5 fixed or routed by name per the reading; (E) hand the before/after method to Wave 5.

### Pattern 1: Anchor the realized terminal on documented cash, not on a reconstruction
**What:** Under cash_settlement the writer's NAV is a cash-balance NAV, so its terminal must be the venue's `balance`. Derive the wedge as `equity - balance` when `balance` is a finite number on the summary, else fall back to the component form with `options_session_upl` removed.
**When to use:** the cash arm of `build_deribit_native_ledger` only. The `mark_to_market` and `smoothed_mtm` arms keep `state.native_upnl` (their native_pnl excludes the current session's option move, so their identity is different and correct; pinned by Phase 131 REVIEW-FIX).
**Example:**
```python
# Source: deribit_ingest.py cash arm (today: lines 2463-2471) and docs.deribit.com get_account_summaries
def _cash_basis_wedge(summ_state: DeribitNativeAccountState, ccy: str) -> float:
    equity = summ_state.native_equity.get(ccy, 0.0)
    balance = summ_state.native_balance.get(ccy)        # NEW map; None when the field is absent
    if balance is not None and math.isfinite(balance):
        return equity - balance                           # = futures session UPL + RPL + options_value
    return (summ_state.native_upnl.get(ccy, 0.0)
            - summ_state.native_options_session_upl.get(ccy, 0.0)   # session move is already inside options_value
            + summ_state.native_options_value.get(ccy, 0.0))
```

### Pattern 2: Classify emptiness on a forward pass over the writer-basis levels
**What:** After the backward roll, walk the raw levels forward in time. A day is emptied iff a prior peak exists and the level is below 1% of it (D-01). The peak is the maximum over earlier non-emptied levels (D-02). Emptied days become exactly `0.0` in the returned series; the forward self-check runs on the RAW levels first.
**Example:** see Code Examples (SC-3).

### Pattern 3: Capture, don't re-read (D-03)
**What:** The derive already reads `get_account_summaries` once and threads `account_state` through (`build_deribit_native_ledger(..., account_state=...)`, the D5 one-read). Persist that same read as a stored input in the `key_inputs` payload. A replay constructs `DeribitNativeAccountState` from the stored JSON and passes it in; no second exchange read, and `tests/test_job_worker_deribit.py::test_deribit_branch_reads_summaries_once` keeps pinning that.

### Anti-Patterns to Avoid
- **A compose-side workaround for the phantom** (clamping, flooring negatives): D-18 forbids it; the compose would publish a curve built on a phantom balance.
- **Widening any inception tolerance** to make a key pass: `_INCEPTION_ZERO_START_BAND` is the founder's 0.01% and the code comment says do not loosen it. NAVBREACH (166.3.1) criterion 2 also forbids a widened tolerance.
- **Gating on a global assertion on shared TEST:** not applicable here (no TEST write), but unit tests assert about their own fixture only.

## Common Pitfalls

### Pitfall 1: The corrected wedge fixes `options_session_upl` but leaves `session_rpl`
**What goes wrong:** Subtracting only `options_session_upl` removes the options leak but the account still drifts on any day it realized futures PnL since the last 08:00 settlement.
**Why:** `equity` includes `futures_session_rpl`; the wedge never read it; it is not in the txn-log `change` until the settlement row. Measured on today's code: perturbation C changes 3 of 5 days.
**How to avoid:** anchor on `balance` (Pattern 1) and test both leaks.
**Warning signs:** sibling-key derives disagree after the fix on a trading account.

### Pitfall 2: The SC-2 cap strands the account whose derive it is meant to protect
**What goes wrong:** The cap makes `_assert_inception_reconciled` raise `InceptionReconciliationError` for the PROD account that holds options; the key-mode derive then fails permanent (`job_worker.py` deribit `except NavReconstructionError`, the disposition is FAILED / `error_kind="permanent"`), no returns refresh, the book goes stale.
**Why:** that account's pre-history residual is about 1.3% of its first-return-day level, about 1.8% of its terminal NAV, i.e. roughly 170 times the §5.2 tolerance (1e-4 of NAV). It passes today only because `is_dust` scales with gross lifetime throughput.
**How to avoid:** do not merge the cap until the stored snapshot shows the balance-anchored residual (Section 2.4, Section 6).
**Warning signs:** a post-deploy derive for any of the 8 keys ends `failed_final` with `native NAV reconstruction refused structurally`.

### Pitfall 3: Reading "the compose refuses" as "fixing the compose publishes a book"
**What goes wrong:** After SC-3 the refused allocator composes but is untrustworthy (`inception_unreconciled`, blocking). The reader (`queries.ts:3703-3708`) requires `is_trustworthy === true`, so the page still shows the rebuilding panel.
**How to avoid:** treat SC-5 as required for the headline outcome; say so in the plan's verification.

### Pitfall 4: A re-deposit smaller than 1% of the old peak never ends the stretch
**What goes wrong:** Under D-02 read literally, an account that re-funds with, say, 0.5% of its old peak is still "emptied" on every later day, so its real capital and real returns are dropped silently.
**Evidence:** on the PROD account the two re-deposits restore the level to 5.4% and 14.2% of the prior peak and the terminal is 8.1% of the global peak, all above 1%, so PROD does not hit it today.
**How to avoid:** implement literally (D-02 is the orchestrator's default, not the founder's) and surface a count flag; see Open Question OQ-4 for the recommended amendment.

### Pitfall 5: A data fault mid-history is silently reclassified as "emptied"
**What goes wrong:** Today a negative reconstructed level after a positive peak is a refusal that catches double-counted flows. The new rule turns that into zero capital with no error.
**How to avoid:** emit `emptied_stretch_days` and `emptied_stretches` flags (counts only) and, as hardening, require each stretch to begin on a day with a withdrawal flow or a stored dropped-day P&L, else keep refusing. Test it with a stretch that has no flow at its edge.

### Pitfall 6: Changing the self-check input
**What goes wrong:** Zeroing emptied levels before `_assert_forward_agreement` makes the forward identity fail at the stretch edges.
**How to avoid:** run the self-check on the raw levels, zero afterwards (Code Examples).

### Pitfall 7: Wedge change vs the byte-identity pins
**What goes wrong:** `tests/test_native_nav_sc4_identity.py` and `tests/test_cash_basis_series_sc4.py` pin cash byte-identity. Their fixtures carry no `options_session_upl`/`session_rpl` (only `test_deribit_ingest.py` and `test_smoothed_mtm_core.py` mention `options_session_upl`), so they should stay green; confirm by running them first. Perp-only accounts with `session_rpl != 0` change by design; say so in the CHANGELOG.

### Pitfall 8: Capture that adds a second read or leaks a magnitude into a log
**How to avoid:** reuse the one `account_state`; the snapshot goes to the DB payload only; logs carry counts and verdict booleans (T-115-05).

# 11..29 empty (r=0 gap-fill rows); day 30 re-deposits 50 (dropped day); 31..35 flat.
def _key(stretch_level):
    r = {**{_d(i): 0.01 for i in range(1, 10)},
         **{_d(i): 0.0 for i in range(11, 30)}, **{_d(i): 0.0 for i in range(31, 36)}}
    lvl9 = 100.0 * 1.01**9
    f10 = -lvl9

### 1.2 Deribit's official field semantics
All quoted verbatim from `https://docs.deribit.com/api-reference/account-management/private-get_account_summaries` and `.../private-get_account_summary`, fetched 2026-10-09 (the list endpoint the code calls carries the same fields; `[CITED]`).

| Field | Official text |
|-------|---------------|
| `equity` | "The account's equity in the selected currency: balance + futures (session UPL + RPL) + options mark value (plus any external/implied equity)." |
| `balance` | "The account's cash balance in the selected currency (deposits, withdrawals, transfers, option premiums, settlements/deliveries, corrections, costs, and insurance refills). Does not include open futures PnL or options mark value." |
| `session_upl` | "Unrealized profit and loss on open positions in the current trading session (since the last daily settlement)." |
| `session_rpl` | "Realized profit and loss accrued in the current trading session (since the last daily settlement). Resets at each daily settlement." |
| `futures_session_upl` | "Session unrealized profit and loss for open futures and perpetual positions." |
| `futures_session_rpl` | "Session realized profit and loss for futures and perpetual positions (resets at daily settlement)." |
| `options_session_upl` | "Session unrealized profit and loss for open options positions." |
| `options_value` | "Mark value of all open options positions in the selected currency. Under standard margin, margin_balance = equity - options_value." |
| `total_pl` | "Total profit and loss of all open positions since each position was opened (not limited to the current session). Differs from session_rpl + session_upl, which reset at daily settlement." |
| `margin_balance` | "Under standard margin (SM): equity - options_value (cash balance plus futures session UPL and RPL). Under portfolio margin (PM): equal to equity on a segregated account, and equity - outstanding_loan_amount on a cross account." |
| Key relationship | "Key relationships (standard margin): equity = balance + futures session PnL + options_value" |

Consequences:
- The cash-basis NAV the writer builds is a cash-balance NAV, so its terminal is `balance`, and `equity − balance = futures session PnL (UPL + RPL) + options_value` under standard margin.
- `session_upl` is not defined as futures-only or as a total. The code prefers `futures_session_upl` (documented as "required") and falls back to `session_upl` only if it is absent, which is right; keep that order and never add `options_session_upl` on top of a fallback `session_upl` without evidence (a third possible double count). `[ASSUMED]` that live responses always carry `futures_session_upl`; the stored snapshot will show it.
- "plus any external/implied equity", `margin_model` (example `"segregated_sm"`) and `cross_collateral_enabled` mean the identity may not hold for a portfolio-margin or cross-collateral account. `[ASSUMED]` PROD's account is standard margin; the identity read records `margin_model` and `cross_collateral_enabled` to settle it.
- cash_settlement versus the delivery/margin model: the writer's `pnl_basis="cash_settlement"` (default, `DEFAULT_PNL_BASIS`) books every option row at its full cash `change` on trade/delivery days, so an open option book carries no P&L in `native_pnl`; its mark lives only in `equity`. The other bases move the open book's change into `native_pnl` and so need the session leg in the wedge, which is why only the cash arm changes. Deribit's own session mechanics: futures PnL moves into `balance` at the daily settlement (08:00 UTC; txn-log field text: "since the last daily settlement at 08:00 UTC"), options settle in cash at delivery. `[CITED: docs.deribit.com private/get_transaction_log]`

## 2. SC-2, the `is_dust` inception allowance

### 2.1 What it is today
`native_nav._assert_inception_reconciled` (`native_nav.py:741-860`), per rolled bucket: `resid = balance[d0] − pnl[d0] − flow[d0]`; `throughput = Σ|pnl| + Σ|flow_qty|` (gross, lifetime, native units); `is_dust = abs(resid) <= INCEPTION_NATIVE_DUST_REL * throughput` (`:803-806`); a dust bucket contributes `0.0` to the USD sum, a non-dust one `abs(resid) * mark0` at the inception-day mark (`:807`); then `tol = max(INCEPTION_ABS_TOL_USD, INCEPTION_REL_TOL * abs(anchor_nav))` (`:847`) and a breach raises `InceptionReconciliationError`. Constants, verbatim: `INCEPTION_ABS_TOL_USD: float = 1.00` (`:179`), `INCEPTION_REL_TOL: float = 1e-4` (`:181`), `INCEPTION_NATIVE_DUST_REL: float = 1e-4` (`:200`). The comment at `:185-199` says tightening after more keys "is expected" and loosening "requires evidence".
The allowance is relative to gross turnover only. An options trader's gross premium throughput is large, so the allowance scales to dollars that no tolerance would accept. On PROD it is why the account reads `native_inception: reconciled` (the verdict is a single string written when the gate ran and passed, `job_worker.py` around 4274-4275).

### 2.2 Constraints on a cap (two pinned data points)
1. **Must stay green:** `tests/test_native_nav.py::test_inception_dust_relative_to_throughput_passes` pins the production dust shape: residual `0.000012 BTC` at `$88k` is about `$1.06`, against a terminal NAV of only about `$2.1`. So a NAV-relative cap at 1e-4 (or even 1e-3) fails the pinned shape: a pure NAV-relative cap is not an option.
2. **Must breach:** the measured offset. Valued at the inception mark it is about 24 times the §5.2 tolerance of the account and about 60 times a `$5` cap (ratios; this is a founder-owned PROD account).

### 2.3 Recommendation
`is_dust = abs(resid) <= INCEPTION_NATIVE_DUST_REL * throughput AND abs(resid) * mark0 <= INCEPTION_DUST_CAP_USD`, with `INCEPTION_DUST_CAP_USD = 5.0` as a named module constant beside the other three, with a comment that lifts the two pinned data points. Any value in `[~2, ~300)` satisfies both constraints; `5.0` keeps a 4x margin over the pinned dust. Do not make it NAV-relative. Fixture that fails today: `Σpnl` about 2000 BTC (dust allowance 0.2 BTC), residual `0.01 BTC` at a `30000` mark (`$300`), `full_history=True`: passes today, must raise after. Keep `test_inception_material_residual_above_dust_still_breaches` and the zero-throughput orphan test green.

## 6. SC-5, the +1.3% `inception_unreconciled` residual

### 6.1 What it is, measured on the stored inputs
- One opening flow on the day before the first return day; `implied_start / level_first_return = +0.01311` (the 1.3%). The same quantity equals the writer's own pre-history capital `prev0_usd` plus any compose-vs-writer drift (derivation: on the funding day the stored P&L is `NAV − prev0 − F`, so `L − F − P = prev0` when the backward roll is exact).
- It is the key's ONLY blocking reason after SC-3: prototype → `degrade_reasons = ['inception_unreconciled']`, `is_trustworthy = False`. The band is `_INCEPTION_ZERO_START_BAND = 1e-4` (`allocator_equity_derive.py:720`), 130 times smaller.

### 6.2 What it is not (each tested offline against the stored inputs and public BTC delivery prices)
1. **Not the terminal phantom.** The phantom's contribution at the opening day is −0.175% of the first-return level; removing it moves the implied start from +1.31% to about +1.49%. Fixing the wedge makes SC-5 slightly worse, not better.
2. **Not the phantom's quiet-day accumulation.** Summed over the 6 quiet runs (748 quiet days) it predicts −2.2e-4 of the account's peak, against a measured +1.43e-3: wrong sign and 16% of the size.
3. **Not generic coin-flow valuation.** Another account with 46 coin-valued flows reconciles inside the band. (`usd_signed` is the event-time value; the core values flows at day marks, `native_nav.py:521-533`; they use the same index precedence, so a systematic mismatch is not expected.)
4. **Not float rounding.** It is about 170 times the §5.2 tolerance.
