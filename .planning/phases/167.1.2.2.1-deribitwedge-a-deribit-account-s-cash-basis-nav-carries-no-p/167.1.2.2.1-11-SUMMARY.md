# Phase 167.1.2.2.1 Plan 11: the allocator compose rolls on the writer's stored flows and day P&L (D-06, compose half) Summary

**When a `key_inputs` row carries `composed_flows` and `composed_day_pnl`, the compose rolls that key's levels on the writer's own identity (`equity_{t-1} = equity_t - F_t - P_t`), so every level is the writer's NAV and the opening-run implied start is the writer's prev0; a stitched shared account takes the same basis at the account level, and a row that does not sit on the writer's calendar falls back to the unchanged roll with a blocking `key_inputs_mismatch`.**

`PLAN_BASE` is `3842272cbaebece9122850ae9902d5ec5b49475c`. `commits: 3` is measured with `git rev-list --count`, taken before this SUMMARY's own commit. `DW_SP` was a scratch directory outside the repo (`$HOME/.cache/quantalyze/deribitwedge-167.1.2.2.1`). Nothing is shipped; the code goes in PR-2.

## What was built

- **`replay_key_equity`** gains `writer_day_pnl` and `writer_flows` (together or `ValueError`). With a non-empty W the replayed days are the union of return days, writer flow days, dropped days and W. The mode applies only when every return day is in W or carries a stored `0.0` (gap-fill), every writer flow day is in W, and `realized_terminal` is on `max(W)`, the series' last day. Then the roll has no return factor, `_assert_forward_agreement` runs with an empty return map and W as its P&L map, the opening-run `implied_start` subtracts W's day P&L (the writer's prev0 on the funding day), and the flag `writer_basis` is `True`. Otherwise the existing roll runs on the event-time `flows` (exactly the call without the two arguments), `writer_basis_mismatch` is set and `KEY_INPUTS_MISMATCH` is added. An empty W is the legacy replay with no flag. A non-finite W amount is refused with a count-free message.
- **`compose_allocator_equity`** gains `writer_basis_by_key`. After the replay, a key whose flags carry `writer_basis` has its `anchored_flows` entry (which feeds the curve, ledger and MWR) set to its writer flows; a key that fell back keeps event-time flows everywhere.
- **The compose job** reads `read_writer_basis` for counted keys, departed keys and stitch sources (a `ValueError` goes through the block's permanent corrupt-input disposal). After the stitch, a non-stitched key with a non-empty W takes its own basis. A stitched kept key takes the members' bases joined by `stitch_dropped_day_pnl` (once over the P&L maps, once over the flow maps, the same day ownership `stitch_shared_account` applies to flows), only when every member has a basis; otherwise the account is byte-for-byte today's path. No new log line.
- No `DegradeReason` member was added: `len(DegradeReason)` is 17 at the plan base and 17 now.

## For plan 08's post-deploy reading

- **The fields exist only on rows a deployed derive writes.** Until each Deribit key's `derive_broker_dailies` has run on the deployed code, its row has no `composed_flows` / `composed_day_pnl` and the compose reads it exactly as before (`inception_unreconciled` for the PROD options-holding account). Read `writer_basis` in the equity_curve row's `flags` list to see that the mode ran; absence of `writer_basis` with `inception_unreconciled` present means the row has no fields yet (or the account is stitched with a member that lacks them), not that the fix failed.
- **A stitched account needs a basis on EVERY member** (each stitch source and the kept key). Earlier members are the eligible-but-not-working keys (for example `sync_status` `error`); if the derive is not re-run for such a key, its row never gains the fields and the account stays on today's path forever. Check this against the real account before reading the result: the plan 06 measurement was per key, and it was not recorded whether the 3 keys of the options-holding account are one stitched group.
- **A `writer_basis_mismatch` is not a flag token.** It is a bool in the key's replay flags, so it does reach the curve row's `flags` list (as `writer_basis_mismatch`) alongside the blocking `key_inputs_mismatch` reason. If the PROD read shows `key_inputs_mismatch` after deploy, the stored row and the stored returns come from different derive runs, or the returns carry a non-zero day the writer's NAV calendar does not hold, or the terminal day is not `max(W)`.
- **Series end:** when `max(W)` is one day past the last return day (plan 06 measured this for the account whose anchor is null, rank 3), the writer-basis series' last day is that terminal day, one day longer than the returns. That account has no anchor and is not replayed, so nothing changes today.
