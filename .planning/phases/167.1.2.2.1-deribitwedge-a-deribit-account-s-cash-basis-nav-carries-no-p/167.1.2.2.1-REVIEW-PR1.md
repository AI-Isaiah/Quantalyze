# Phase 167.1.2.2.1: Code Review Report, PR-1 (DERIBITWEDGE capture)

**Reviewed:** 2026-10-09T16:01:14Z
**Depth:** deep
**Files reviewed:** 9 source and test files plus the release files
**Status:** issues_found. The worst finding is MEDIUM. Nothing is CRITICAL or HIGH.

## Summary

PR-1 meets its central contract. It changes no computed NAV, return or gate verdict, and every new capture in `job_worker.py` is guarded so that it cannot fail a derive.

**Evidence that behaviour is unchanged (measured, not inferred):**

- **Refactor equivalence.** The `_roll_buckets`, `_union_calendar` and `_inception_reading` extraction was compared line by line against `origin/main`. The order is the same: roll, then gate, then the empty-rolled short-circuit, then the union calendar. The arithmetic and the orphan refusal site are identical. `tol` is now computed before the non-finite check, but `max(1.0, nan)` evaluates to `1.0` without raising, so the outcome is the same.
- **Differential test.** I ran a randomized differential (3000 random ledgers: mixed BTC, ETH, USDC and USDT; wedges; flows; missing marks; `full_history` both ways) through `reconstruct_native_nav_and_twr` on the old and the new module. The results:
  - 0 differences in the returns, compared by `repr` so NaN compares equal.
  - 0 differences in the exception class and the full exception message, which carries the currency list and the breach ratio.
  - Outcome mix: 2076 `InceptionReconciliationError`, 756 ok, 168 `UnmarkableCurrencyError`.
  - Script: `scratchpad/diff_test.py`.
- **Tests.** The new files, `test_native_nav`, `test_job_worker_deribit` and `test_allocator_equity_dropped_day_pnl` give 179 passed. mypy is clean on `native_nav.py` and `allocator_equity_derive.py`.
- **Whitelist.** The whitelist is complete against every `summ.get(...)` in `fetch_deribit_native_account_state` and `_combined_session_upl`. It holds no id, email, username, system name or type.
- **Digest.** The digest is deterministic. The sort key `(int ts, str(id), canonical line)` is a total order over strings, `json.dumps(sort_keys=True)` is stable, and every failure inside the build is caught onto the report.
- **Release files.** `VERSION` is `0.129.7.0`, 9 bytes, no trailing newline, and is byte-equal to the `package.json` version. `origin/main` is still `0.129.6.1` after `git fetch`. `CHANGELOG.md` has one unified entry.

**What is wrong:**

1. The new stored inputs exist only for derives that succeed (MEDIUM, MD-01). A derive that the §5 gate refuses, or that refuses for any other structural reason after the summaries read, stores nothing. That read stays the silent live input D-03 forbids, and those derives are the ones a diagnosis needs most.
2. The tolerance rule for the identity verdict can be wrong in both directions (MEDIUM, MD-02). A legitimate identity reads as broken when the fields have mixed precision, and a real 0.3-unit discrepancy reads as `identity_ok: true` when the values happen to be round.

The rest is LOW or INFO: robustness edges and an inaccurate CHANGELOG claim.

## Medium

### MD-01: The capture, the digest and the diagnostics are stored only when the derive succeeds, so a refused derive leaves its live read unrecorded

**Files:**
- `analytics-service/services/job_worker.py:4279` (`combine_native_ledger`, where the gate raises)
- `analytics-service/services/job_worker.py:4295-4370` (all three captures)
- `analytics-service/services/job_worker.py:4833-4858` (`except NavReconstructionError`, which returns `FAILED` without running the epilogue)

**Issue:** `account_summary`, `ledger_digest` and `native_inception_diagnostics` are all assigned after `combine_native_ledger(...)` returns. The diagnostics are also gated behind `_native_inception_verdict = "reconciled"`.

When `combine_native_ledger` raises (an `InceptionReconciliationError` from §5, an `UnmarkableCurrencyError`, a `LedgerValuationError`, or the C2 empty-ledger refusal), the handler at 4833 returns `FAILED/permanent`. `_run_key_mode_compose_epilogue` never runs, so none of the three fields is persisted, even though the one `get_account_summaries` read (4135) and the full crawl have already happened.

The consequences:

- **D-03 is not met for refused derives.** "Any live read … is captured as an input and stored. It is never read silently during a derive" holds only for derives that pass.
- **Plan 02's guarantee does not reach PROD.** Plan 02's behaviour "a ledger whose gate would raise yields a diagnostic" is true of the pure function, which the test checks, but it can never reach PROD storage. The breaching accounts the diagnostic exists to explain store nothing.
- **Plans 03 and 06 make it worse.** Once the wedge change (plan 03) or the cap (plan 06) lands, any account it pushes into refusal stops refreshing its stored reading. At that moment the evidence is needed most.
- **The scope cost already applies.** RESEARCH section 6 lists "a post-deploy derive for any of the 8 keys ends `failed_final`" as a warning sign, and that derive would leave no stored reading behind.

**Fix:** Compute the capture fields from `account_state` and `_completeness` as soon as they exist, before `combine_native_ledger`. Run the diagnostic on a path that does not depend on the gate passing (`native_inception_diagnostics` already never raises the inception refusal). Persist them on the refusal path too. A minimal shape:

```python
# right after build_deribit_native_ledger / assert_ledger_complete, before combine:
if is_key_mode and denominator_config is None:
    _account_summary_snapshot = _guarded(account_summary_payload, account_state, "account_summary")
    _ledger_digest = ...           # unchanged logic, moved up
    if native_ledger.full_history:
        _native_inception_diagnostics = _guarded(...)   # independent of the verdict
...
except NavReconstructionError as exc:
    # persist the additive fields onto key_inputs (merge, do not replace anchor fields)
    # before returning FAILED, so a refused derive still records what it read
```

If writing `key_inputs` on a failed derive is unacceptable (the compose reads that row), store the fields on a separate `key_capture:<api_key_id>` row instead. At the least, state in the CHANGELOG and in plan 05's preconditions that refused derives store nothing, so plan 05 does not read an absent field as "never derived".

### MD-02: The identity tolerance comes from the shortest `repr` of the finest field, which both falsely breaks and falsely passes

**Files:**
- `analytics-service/services/allocator_equity_derive.py:1223` (`places = min(max(_decimal_places(float(v)) for v in parts), _IDENTITY_PLACES_CAP)`)
- `analytics-service/services/allocator_equity_derive.py:1199-1235` (`_account_identity`)

**Issue:** `_decimal_places` reads the shortest round-trip `repr`, which strips trailing zeros. The tolerance `4 * 10**-d` uses the largest `d` among the parts. This has two failure modes, both measured against the shipped function:

- **False break.** The fields are reported at different precisions, which is typical when `options_value` is a computed mark. Measured: balance `1.0`, options_value `0.1234567891` (10 dp), equity `round(1.0 + ov, 8)` (Deribit's 8 dp). The identity holds to Deribit's own rounding, yet the result is `identity_ok: False, identity_resid_ratio: 2.25`. One finer field tightens the tolerance for every field.
- **False pass.** Every value happens to be round. Measured: `equity 100.0, balance 99.7` gives places = 1, so tol = 0.4, and the output is `identity_ok: True, ratio 0.75`. A 0.30 USDC unexplained difference reads as an identity that holds.
  - The test `test_identity_falls_back_to_session_upl_and_counts_missing_parts_as_zero` (`tests/test_deribit_account_summary_capture.py:201`) is an instance of this. With equity 1.5, balance 1.0 and session_upl 0.5, the tolerance is 0.4, so an equity of 1.8 would also pass. The test cannot detect a wrong fallback.

SC-1 decides the wedge anchor from this verdict (plan 05 reads `identity_ok`), so a wrong verdict in either direction misroutes that decision. The stored `identity_resid_ratio` does not help, because it is computed against the same tolerance.

**Fix:** Judge against the venue's documented precision, not the precision a value happens to show:

```python
# Deribit reports coin fields to 8 dp and USD-family fields to their own fixed precision;
# pin it per currency family instead of inferring it from repr.
_DERIBIT_FIELD_PLACES = {"default": 8}          # evidence-commented, overridable per ccy
places = _DERIBIT_FIELD_PLACES.get(ccy, _DERIBIT_FIELD_PLACES["default"])
tolerance = Decimal(len(parts)) * Decimal("0.5") * Decimal(10) ** -places
```

If inference is kept, also store `identity_resid_native` (the signed residual as a float) and `identity_places`, so plan 05 can re-judge offline from the stored snapshot without trusting this tolerance. Add a test with mixed precision and one with round values that pins both directions.

## Low

### LO-01: The capture code added inside `fetch_deribit_native_account_state` is unguarded, so "a capture never fails a derive" holds only by luck of types

**File:** `analytics-service/services/deribit_ingest.py:1709-1719` and `:1793-1796`

**Issue:** `_present_finite_number` calls `float(raw)` on any `int`. A very large JSON integer raises `OverflowError` (measured: `_present_finite_number(10**400)` raises `OverflowError`). This code runs on fields the derive never read before (`balance`, `total_pl`, `margin_balance`, `session_rpl`, `futures_session_rpl`, `options_session_rpl`), outside any try. The exception would escape the summaries read and fail the derive, which is the exact invariant PR-1 promises not to break. Deribit will not realistically send such a value. Even so, the guarantee is asserted, not enforced.

**Fix:** Catch `OverflowError` in `_present_finite_number` and return `None`. Alternatively, wrap the two capture lines in the loop so a failure leaves `summary_snapshot` empty, and record it as a capture error the worker turns into `account_summary_error`.

### LO-02: The balance-anchored wedge subtracts a present-only balance from a coerced equity, which fabricates `-balance` when equity is absent

**File:** `analytics-service/services/job_worker.py:4307-4312`, with `deribit_ingest.py:1797`

**Issue:** `native_equity[ccy] = float(summ.get("equity", 0.0) or 0.0)` turns an absent or null equity into `0.0`. `_alt_wedge` then stores `0.0 - balance` as the balance-anchored wedge, a value that was never read. That is the "absent is not zero" discipline this PR adds for `balance` and then breaks one line later for `equity`. Diagnostics only, but plan 05 decides from those numbers.

**Fix:** Build the alternative from the snapshot, where both fields are present-only:

```python
_alt_wedge = {
    c: s["equity"] - s["balance"]
    for c, s in account_state.summary_snapshot.items()
    if "equity" in s and "balance" in s
}
```

### LO-03: The diagnostic is all-or-nothing, so one failure in the alternative reading discards the current reading

**File:** `analytics-service/services/native_nav.py:1000-1079` (`native_inception_diagnostics`), `:1041`, `:1047`

**Issue:** There are two cases:

- `_roll_buckets(alt_ledger, ...)` re-runs `_build_buckets`. The alternative wedge can add a nonzero `terminal_upnl_native` for a currency that is UNMARKABLE or has no marks, so `_build_buckets` raises `UnmarkableCurrencyError`. The whole function then raises and the worker stores only `native_inception_diagnostics_error`, which loses the current-wedge reading that succeeded.
- When `cur is None` (`orphan_unvaluable`), `currencies` is `[]`, which drops the rows of every currency that could be valued.

**Fix:** Compute the alternative reading in its own try. On failure, set `*_balance_anchor` to null and add a `balance_anchor_error: <class name>` key. In the orphan case, emit the rows that could be valued, plus the flag.

### LO-04: The CHANGELOG and the `job_worker.py` comment say "the only broad except this phase adds", but there are four

**Files:**
- `CHANGELOG.md:26`
- `analytics-service/services/job_worker.py:4296`

**Issue:** This PR adds four `except Exception` blocks:

- `job_worker.py:4322` (diagnostics)
- `:4338` (the `account_summary` capture)
- `:4358` (the `ledger_digest` writer)
- `deribit_ingest.py:2426` (the digest inside the build)

The release note reads "The broad `except` is the only one this phase adds, around the diagnostic call". That statement is false, and this repo treats a CHANGELOG claim as a record. The plans contradict each other here: plan 01 asks for the guards and plan 02 says "ONLY".

**Fix:** Say "four broad excepts, each around an additive capture, each writing `<field>_error` plus one class-name WARNING", and list them. Correct the comment at 4296 the same way.

### LO-05: The snapshot drops numeric strings that the derive's own wedge read accepts, so the stored input can differ from the one used

**File:** `analytics-service/services/deribit_ingest.py:1709-1735` against `_combined_session_upl` (`float(raw)` accepts `"0.5"`)

**Issue:** `_combined_session_upl` and the `float(x or 0.0)` sibling reads accept numeric strings. `_present_finite_number` rejects anything that is not an `int` or `float`. If Deribit or ccxt ever delivered string numerics, the derive would compute with the values while the snapshot recorded them as absent, and the identity would read `null`. D-03's claim that the stored input is the read the derive used would then be false without anyone noticing.

**Fix:** Either parse finite numeric strings in `_present_finite_number`, the same way the derive does, or record a `non_numeric_fields: [names]` list in the snapshot so the divergence is visible.

### LO-06: The derive-level diagnostics tests mock the wrapper and ignore its positional arguments, so the real diagnostic never runs through `job_worker`

**File:** `analytics-service/tests/test_native_inception_diagnostics.py:342-355` (the `[(_args, kwargs)]` at 351 discards `_args`)

**Issue:** Every derive-level test patches `native_ledger_inception_diagnostics` with a `MagicMock` and asserts only on `alt_terminal_upnl_native`. No test checks that the worker passes the derive's own `native_ledger` and `_completeness.indexable_currencies`. With the stub ledger the real call raises `UnmarkableCurrencyError` (per the 02-SUMMARY), so every other mocked Deribit derive now silently stores `native_inception_diagnostics_error`. As a result:

- the success path through `job_worker` with a real diagnostic is untested;
- a wiring defect (for example, passing a different ledger) would stay green.

**Fix:** Assert `args == (native_ledger_used_by_combine, indexable)` (capture the ledger from the `build_deribit_native_ledger` stub). Add one derive test whose stub ledger carries marks, so the real wrapper runs and its output round-trips through `read_native_inception_diagnostics`.

## Info

### IN-01: `read_account_summary` accepts any unknown key as a number

**File:** `analytics-service/services/allocator_equity_derive.py:1314-1327`

The writer is whitelisted, but the reader does not enforce the whitelist: any extra key with a finite number passes. The reader also does not check that the `identity` keys match the `summaries` currencies, or that `identity_ok` agrees with `ratio <= 1`. **Fix:** Check against `ACCOUNT_SUMMARY_NUMERIC_FIELDS` (from a shared constant module, to keep the runtime import boundary) and cross-check the identity keys.

### IN-02: The error label in `_strict_finite_number` always says `account_summary`

**File:** `analytics-service/services/allocator_equity_derive.py:1273-1280`

It is reused by the diagnostics reader, so a corrupt diagnostics record reports itself as `key_inputs account_summary: …`. The 02-SUMMARY already notes this. **Fix:** Pass the payload name in.

### IN-03: The `session_upl` fallback in the identity mixes two definitions

**File:** `analytics-service/services/allocator_equity_derive.py:1216-1219`

On Deribit, `session_upl` is futures plus options. With an open option book whose `futures_session_upl` is absent, the fallback adds the options session P&L on top of `options_value`, which already contains the option marks, so the verdict reads as broken. This is the order the plan specifies. Record it in the docstring so plan 05 does not treat a fallback currency's break as evidence.

### IN-04: The CHANGELOG cites branch commit SHAs that will not exist on `main`

**File:** `CHANGELOG.md:6-8`, `:25`

A squash merge, and the `-pr` filter, rewrite them, so `5d9986f4e` and the other cited SHAs become dangling references. Name the PR number, or drop the SHAs.

### IN-05: The new tests import helpers from other test modules

**Files:** `tests/test_native_inception_diagnostics.py:42` (`tests.test_native_nav`), `tests/test_deribit_account_summary_capture.py:39`, `:292`, `:303`

Importing helpers from other test modules couples the files, so renaming a helper breaks unrelated files. Consider a `tests/_deribit_fixtures.py`.

## Checks that passed (no finding)

- **Behaviour unchanged.**
  - `_native_nav_levels`, `_assert_inception_reconciled` and `reconstruct_native_nav_and_twr` produce identical returns and identical exceptions, class and message, on 3000 random ledgers.
  - `INCEPTION_DUST_CAP_USD` is read only by `_readings_or_none`.
  - The gate passes `dust_cap_usd=None`.
- **Exception paths.** Each of the four worker-side and build-side guards writes `<field>_error` with the class name and logs class plus venue, never `str(exc)`. A test checks this with a message that carries a magnitude. `CancelledError` (a `BaseException`) is not swallowed.
- **Digest determinism.** The digest is independent of page order. Missing and mixed-type ids are safe. Equal `(timestamp, id)` rows are tie-broken on their content. No raw row value is stored. The `ROW_SCOPE_KEY` stamp enters the hash but is not stored.
- **Whitelist.** `summary_snapshot` stores only the 11 numeric fields, `margin_model` (str) and `cross_collateral_enabled` (bool). The writer re-checks finiteness, and the index snapshot is finiteness-checked.
- **Payload compatibility.** No Python or TS reader of `key_inputs` enforces an exact key set (`departed-history.ts` reads only `anchor_usd` and `anchor_null_reason`). The ccxt 5-key test still passes.
- **Type safety.** mypy is clean. `TYPE_CHECKING` keeps `allocator_equity_derive` free of a runtime import of `deribit_ingest`.
- **Test oracles.** They are hand-worked and do not import the module's constants:
  - 0.01 BTC, 30000, 4000, 300;
  - 1e-6 / 4e-8 = 25;
  - 0.499988 × 88000 / 4.4;
  - the digest is restated by hand.

  The exception is MD-02's fallback test, whose oracle is too loose to fail.
- **Release.** `VERSION` and `package.json` both read `0.129.7.0`, byte-equal (`xxd`: 9 bytes, no newline). That is one third-digit step from `origin/main`'s `0.129.6.1`.
