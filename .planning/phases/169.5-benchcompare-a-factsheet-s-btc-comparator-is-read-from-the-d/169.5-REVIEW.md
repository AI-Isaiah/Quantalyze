## Summary

Scope: `git diff de622a986 HEAD -- src` in the 169.5 worktree (branch `feat/169.5-benchcompare`). The
merge-in `8d8aa8a29` is out of scope. Per the founder rule, this report lists CRITICAL/HIGH and MEDIUM
findings only. LOW and INFO items are left out on purpose.

The core helper (`alignCoveredReturns`) matches the engine's `_interval_matched_benchmark` on the cases
I traced by hand: day one (D-05), both endpoints (D-04), the interior gap `count == expected` (WR-01), the
base close (D-07), and a dropped close inside the move. `buildComparatorBlock`, `readFactsheetBenchmark`
(the bounded read, the first-stored-date probe, the merge and trim, and the unavailable marker) and the
discovery LOCKSTEP call match D-54, D-58 as amended, D-59 as amended, and D-64(4) Amendments A and B. The
four core test files pass at HEAD (39/39).

Three defects remain. One is HIGH: a panel outside every comparator block still shows a fabricated BTC 0%,
and the new unavailable path causes it. The other two are MEDIUM.

**Excluded as instructed, not findings:**
- **D-65:** SignaturePanels, CrossSignaturePanels and BatchDPanels take null as 0. Phase 169.4 owns that.
- **D-52:** an honest "BTC prices unavailable" payload can be cached for the 1 h TTL.

**Weighed and left below the bar:**

  because `stress-windows.ts:89` already throws on a non-ISO first date.

**The executor's open question** (the weekday calendar is inferred from the bounded read window): it is
real, and it is reported as WR-02. It is a narrow corner. It needs a short record plus a real DB hole, but it
is a stated deviation from the engine rule D-64 mandates.

## Critical Issues

### CR-01: Stress Windows panel shows a fabricated "BTC +0.00% / DD 0.00%" whenever BTC is uncovered, and the new unavailable path causes it (HIGH)

**File:** `src/lib/factsheet/build-payload.ts:450` (with `nullAsZero` at `:185`). Rendered by `src/app/factsheet/[id]/v2/StressWindowsPanel.tsx:121-126`.

**Issue:** `deriveSeriesBundle` passes `nullAsZero(btcAl)` to `computeStressWindows`. That function compounds
`benchRet` over each named event window (`stress-windows.ts:136-145`) and emits `benchReturn` and
`benchMaxDD`. The panel renders both, colouring the return green when it is `>= 0`.

This is not covered by D-65. D-65 names only the api arm's allocator portfolios and event signatures, and
says outright that "SC3 and D-58 govern the comparator blocks; these synthesized panels are outside them."
`computeStressWindows` runs inside `deriveSeriesBundle` on EVERY arm (csv included) and every basis (cash,
MTM, smoothed, and the browser leverage re-derive through `basis-context.tsx`). The only record of stretching
the null-as-0 boundary to stress windows is a key-decision line in 169.5-01-SUMMARY ("stress windows take
BTC through the same named null-as-0 boundary as the D-65 api-arm panels"). It is an executor call, not a
locked decision.

**Failure scenario, measured:** I ran `buildFactsheetPayload` on a crypto strategy from 2024-07-01 to
2025-06-01 with `{ benchmarkPrices: { unavailable: true } }`, which is what the route produces on any BTC
read error or probe error. The result has `comparators.btc.summary === null`, so the picker says "BTC prices
unavailable". On the same page, `stressWindows.windows` holds
`{"name":"Aug 2024 unwind", ..., "benchReturn":0, "benchMaxDD":0}` and
`{"name":"Apr 2025 tariffs", ..., "benchReturn":0, "benchMaxDD":0}`. So on that page the Stress Windows
table tells an allocator that BTC was flat, with no drawdown, through the August 2024 carry unwind. Under
D-52 the payload is cached for an hour.

Before this phase the fixture always supplied real BTC closes for those dates, so this is a regression this
phase introduced. The same zero appears when a `dropped` close falls inside an event window (both days go
null and the move is lost). It also appears for any window before BTC's coverage starts: the FTX, 3AC and
TerraLuna rows of a crypto strategy with 2022 history, if the DB does not reach back that far. That last
case already existed under the fixture, but this phase's SC3 ("a gap is null, never 0") is the rule that
now condemns it.

**Fix:** Give stress windows the null-honest input rather than the D-65 boundary. That means one extra file,
`stress-windows.ts`, whose type the panel already renders with an em-dash elsewhere:

```ts
// build-payload.ts:450
stressWindows: computeStressWindows(dates, stratRet, btcAl.returns, "BTC", markets),

// stress-windows.ts: benchRet: ReadonlyArray<number | null>
let benchCovered = true;
for (let i = startIdx; i <= endIdx; i++) {
  stratCum *= 1 + stratRet[i];
  const b = benchRet[i];
  if (b == null) { benchCovered = false; } else { benchCum *= 1 + b; /* peak / DD as today */ }
}
// ... benchReturn: benchCovered ? benchCum - 1 : null, benchMaxDD: benchCovered ? benchMaxDD : null
```

Widen `StressWindow.benchReturn` and `benchMaxDD` to `number | null`, and render "—" in
`StressWindowsPanel.tsx:121-126` when they are null. Pin it with a unit case in which the unavailable marker
gives a null `benchReturn` for "Aug 2024 unwind", and a neuter that puts `nullAsZero` back. If the founder
prefers to keep D-65's boundary here, record it as a decision (a D-65 amendment), not a SUMMARY line.

## Warnings

### WR-01: `pastThrough` ignores the comparator's own calendar, so every SPX window (MTD, YTD, 3M, 6M, 1Y) goes null when a 7-day strategy ends on a weekend (MEDIUM)

**File:** `src/lib/factsheet/comparator-block.ts:83` (applied at `:124-128`). The caption has the same comparison at `src/app/factsheet/[id]/v2/ComparatorPicker.tsx:34`.

**Issue:** `pastThrough = aligned.through === null || lastDate > aligned.through` compares the comparator's
last close against the strategy's raw last date. A weekday comparator has no close on Saturday or Sunday by
construction. So a 7-day strategy whose last date is a weekend is always "past through" for SPX, even though
nothing is missing: the Friday close fully determines every window.

`align.ts` already treats the benchmark's own calendar as the definition of a gap (WR-01, `calendar[]`), so
this is a second, inconsistent reading of "missing" inside the same phase. The D-58 amendment puts
`compute()`'s windows on the SERIES rule (the move since the last close), not on a raw-date rule.

**Failure scenario, measured:** a crypto (7-day) strategy from 2025-01-01 to 2025-03-16, a Sunday, inside
SPX fixture coverage (fixture ends 2026-05-08). The payload has `comparators.spx.through = "2025-03-14"` and
SPX `mtd = ytd = p3m = null`. The picker shows "SPX prices through Mar 14, 2025" and all five SPX window rows
show "—", though SPX's data for the period is complete. A second probe ending 2025-06-01, also a Sunday,
gives the same result.

This affects roughly 2 in 7 crypto records that end inside SPX coverage. It becomes every weekend view of
every crypto factsheet as soon as SPX gets a live feed (the deferred item in CONTEXT). The same mechanism nulls
all five BTC windows when the strategy's last date is one day past the last stored BTC row (the refresh stores
completed UTC days only, at 00:10 UTC). That is the locked "past through" rule working as designed, and I
could not confirm that any strategy writer stamps a same-day return, so it is not claimed as a finding here.

**Fix:** measure "past through" against the benchmark's calendar. A comparator is past through only when a
date on its own calendar lies in `(through, lastDate]`. Expose that once from `alignCoveredReturns`, for
example a `coveredToEnd: boolean` computed with the same `calendar[]` it already builds. Use it in both
`comparator-block.ts:83` and the caption, so the two cannot drift:

```ts
// align.ts, after `through` and `calendar` are known
let coveredToEnd = through !== null;
if (through !== null) {
  for (let day = utcDay(through) + 1; day <= utcDay(lastStrategyDate); day++) {
    if (calendar[weekdayOfDay(day)]) { coveredToEnd = false; break; }
  }
}
```

Pin it with a 7-day strategy ending on a Sunday inside SPX coverage (SPX `mtd` non-null, no caption), plus a
neuter that restores the raw-date comparison.

### WR-02: The benchmark calendar is inferred from the BOUNDED window, not the benchmark's full series, so a short record can pair an interval the engine leaves unpaired (the executor's open question, confirmed) (MEDIUM)

**File:** `src/lib/factsheet/align.ts:115-116` (used at `:155`). The windowed input comes from `src/lib/factsheet/fetch-and-build-payload.ts:764` (the trim to `[from, to]`) and from `fixtureBenchmarkPrices` in `build-payload.ts`.

**Issue:** `calendar[]` is the set of weekdays on which the `prices` passed in carry a close. On the route,
those prices are trimmed to `[first strategy date - 1, last strategy date]`, and the no-opt path bounds the
fixture the same way. The engine infers `traded` from the benchmark series it receives
(`analytics-service/services/metrics.py:1283-1284`, `b.index.dayofweek`), which is the stored BTC history.

When every occurrence of a weekday inside the window is missing from the DB, TypeScript drops that weekday
from BTC's calendar. `expected` then shrinks to match the bridged `count`, and the interval is paired: the
exact M1 shape that WR-01 / `d1d1fc077` exists to reject.

**Failure scenario:** a weekday strategy with dates `2026-06-05 (Fri)`, `2026-06-08 (Mon)` and a few more
days that week. `MIN_FACTSHEET_SERIES_POINTS` is 2, so this is buildable. BTC's DB has no row for
`2026-06-06 (Sat)`, a hole 169.2 documents can happen. The window `[06-04, …]` holds no other Saturday, so
`calendar[6] = false`. For `(Fri, Mon]`, `expected = 2` (Sun, Mon), and `count = 2` (the Sunday point bridges
Fri→Sun, then Monday). So `paired = true`. The engine gives `expected = 3` and leaves it unpaired. Alpha, beta,
IR and ρ then include a two-day BTC move in a one-day slot, and the TypeScript and Python figures disagree.

The effect is bounded. It needs a record short enough that every Saturday (or other weekday) in its window is
missing, and on such a record the joint metrics are close to noise. But it breaks D-64's "the comparator
follows the engine's pairing rule" by construction, not by data.

**Fix:** do not infer the calendar from a trimmed window. BTC's calendar is known to be all seven days, so
pass the calendar as an input to `alignCoveredReturns` (for example `calendar: "7d" | "weekday"`, or a
7-element mask). Set it per comparator in `alignComparators` (BTC and ETH 7-day; SPX, GLD and IEF weekday),
which also makes it independent of fixture trimming. Alternatively, infer it from the untrimmed series
before the trim at `fetch-and-build-payload.ts:764` and carry it on `BenchmarkPricesOpt`, so the browser
re-derive sees the same calendar. Pin it with the Fri/Mon case above plus a neuter that restores window
inference.
