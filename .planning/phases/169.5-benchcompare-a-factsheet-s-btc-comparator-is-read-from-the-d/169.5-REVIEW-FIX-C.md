## Fixed Issues

### SFH-M-01: the catch in `readFactsheetBenchmark` covers computation code, and its log drops the message and all context

**Files modified:** `src/lib/factsheet/fetch-and-build-payload.ts`,
`src/lib/factsheet/fetch-and-build-payload.benchmark.test.ts`
**Commit:** `b813765e8`
**Applied fix:**
- The two DB calls (`readBenchmarkPrices` and the first-date probe) moved into a new private
  helper, `readBtcWithFirstStoredDate`, which holds the only `try`. The merge, trim and
  `alignCoveredReturns` code now runs outside it. A throw there is a code bug and propagates as
  a build error. It no longer renders "BTC prices unavailable" and no longer logs a DB failure.
- `benchmarkReadFailed` now logs `{ id, from, to, code, message }`. `message` comes from any
  error carrying one (Error instances and PostgREST error objects), otherwise `String(err)`.
  That tells the page-cap, cursor and "no data and no error" guards apart. `code` works as it
  did before.
- `readFactsheetBenchmark` gained an optional 4th parameter, `strategyId: string | null = null`,
  which is used for the log line only. The route call site (`buildFromResolved`) passes `id`.
- The docblock sentence "logged with one stable message and the error's code" was updated to
  match.

**Behaviour change to note:** a merge/align bug now throws instead of rendering "BTC
unavailable", and it lands on three surfaces:
- `src/app/factsheet/[id]/v2/page.tsx`, through `fetchAndBuildPayloadWithReason`: the throw
  leaves the `unstable_cache` callback, so nothing is cached and the error boundary renders.
- `src/app/factsheet-share/[token]/page.tsx:363`: this page awaits `fetchAndBuildPayload`
  directly, with no enclosing try, so the throw reaches the error boundary.
- `src/app/(dashboard)/discovery/[slug]/[strategyId]/page.tsx:288`: this page awaits
  `readFactsheetBenchmark` directly, with no enclosing try, so the throw reaches the error
  boundary.

This is the propagation the finding asked for. A DB read error or throw still gives the unavailable form,
logged and not captured (D-54 unchanged).

**Hand-off (outside this group's file set):** `src/app/(dashboard)/discovery/[slug]/[strategyId]/page.tsx:288`
calls `readFactsheetBenchmark(createAdminClient(), dailyReturns, buildOpts)` without the new
parameter. It compiles because the parameter is optional, but on that surface the log line
carries `id: null`. The fix is one line: pass the page's strategy id as the 4th argument. The
same file's comment block (about lines 277-286) says "A read error or throw is the unavailable
form". After M-01 that holds only for a throw from the DB calls, so the comment is now stale.
Both edits belong to whichever fixer owns that file, or to the orchestrator.

**Red-first evidence:** the tests were written first and run against the unfixed code. That run
was the neutered state, so no revert of uncommitted work was needed. RED lines:
- `the reader answers ok:false … logged, not captured`: `expected "error" to be called with arguments`
  (the payload lacked `id` / `from` / `to` / `message`)
- `the client throws …` and `the first-date probe answers an error …`: the same assertion,
  RED for the same reason
- `an align throw propagates as a build error …`: `promise resolved "{ unavailable: true }" instead of rejecting`
  (the wide `try` swallowed the simulated bug)

All four went GREEN after the fix. The align throw is simulated with a passthrough `vi.mock("./align")`
guarded by a hoisted flag. With the flag off it is the real function, so every other case is
unchanged.

### SFH-M-02: the two data-driven "unavailable" exits log nothing

**Files modified:** `src/lib/factsheet/fetch-and-build-payload.ts`,
`src/lib/factsheet/fetch-and-build-payload.benchmark.test.ts`
**Commit:** `5ade48b7b`
**Applied fix:** a new exported stable message, `BENCHMARK_UNAVAILABLE_MESSAGE`, is logged with
`console.warn` on both exits:
`{ reason, id, from, to, firstStored, readCount: read.prices.length, readThrough: read.through }`.
`reason` is `no_prices_in_window` for the `prices.length === 0` exit and `no_covered_interval`
for the `!anyCovered` exit. This is a separate line from the `console.error` read-failure line.
Behaviour on both exits is unchanged (D-09 / D-54), and there is no Sentry capture. The earlier
"no date on any axis" exit, which issues no query, is not part of the finding and was left
as is.

**Red-first evidence:** both cases failed against the unfixed code with
`expected "warn" to be called with arguments`. They were still RED after the M-01 fix landed
(`2 failed | 11 passed`), so what makes them fail is the missing M-02 fix itself. They went
GREEN after the M-02 fix. Each case also
asserts that `console.error` was NOT called, which pins that these exits are logged separately
from a read failure.

**Test-harness note:** `beforeEach` now clears the `console.warn` / `console.error` spies. A
repeated `vi.spyOn` returns the same spy with its earlier calls still recorded, so without the
clear a "not called" assertion picked up calls left over from earlier tests. This was measured:
the align case first failed on a leftover `readSingleKeyBasisOpts` error line.
