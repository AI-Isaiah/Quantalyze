## Summary

The root cause in CONTEXT reproduces exactly, and the fix direction is confirmed by measurement. The divergence is wider than `Math.pow(10, -4/-5)`, though. Node 22.22.1 (V8 12.4.254) and Playwright Chromium 153.0.8010.12 disagree on `Math.pow(10, n)` for n in {-29, -24, -23, -21, -20, -17, -5, -4, 26, 29}. They also disagree on `Math.log10`, `Math.log`, `Math.exp` and general `Math.pow`, by one ulp, on a few percent of inputs. Chromium's `Math.pow(10, n)` is exact for every n in -30..30. `Number("1e" + n)` returns the same exact value in both engines. `[VERIFIED: probe run this session, see Finding 1]`

A local before/after census settles Q3 and Q5. On a private local-stack lane (TEST and PROD untouched), all 26 seeded specs (209 tests) were run with a context-wide `weberror` recorder. **Before the fix: exactly one React #418 in the whole seeded suite**, on `/allocations?tab=overview` at 898 ms, inside `target-size.spec.ts`. **After a minimal fix to the six sites: 0 page errors in 209 tests**, and the EquityChart tap-rect test passed 10 of 10. So the #418 guard will not expose any other seeded page today. The `composite-factsheet-render` axe (cash basis) failure is **not** the hydration class: it fails 3 of 3 locally with **zero** page errors. The cause is that axe runs while the masthead `<h1>` is still inside React's hidden streaming segment `DIV#S:1[hidden]`. `[VERIFIED: lane census + instrumented probe, Findings 7 and 9]`

The differential sweep surfaces a conflict between two inputs the planner must honour, which Rule 7 says to surface rather than blend. CONTEXT's locked direction is "integer index times the step, rounded to the step's decimals", and the UI-SPEC repeats it as TK-1. Measured against what Chromium renders today, that construction **changes non-zero tick labels**: 2 of 4,400 linear cases, and **377 of 4,400 EquityChart cases** if applied to its walker. That violates TK-4 ("Labels and styles do not change"). A minimal construction meets every success criterion and TK-4 together: engine-independent exponent and power of ten, today's accumulation kept, a zero/baseline snap. It is engine-independent in all 4,400 cases. It changes **only** zero ticks (446 linear, 564 signature), never a non-zero label, value or tick count.

**Primary recommendation:**
- Add one pure module, recommended name `src/lib/chart-ticks.ts`, holding `pow10(n) = Number("1e" + n)` and `decimalExponent(x)`, which takes the exponent from `x.toExponential()` and calls no `Math.log10`. Add a shared "nice step" builder that keeps today's `v += step` loop and snaps a tick within `step * 1e-6` of 0 (or the baseline) to that exact value.
- Route all six sites through it.
- Add a seeded-e2e `pageerror` guard fixture, plus a vitest anti-drift check that every spec in the seeded list imports it.
- Land the guard in the same PR as the fix, or after it.
- **Blocking:** put the TK-1 vs TK-4 conflict to the founder before the helper plan executes (Finding 3). There is no default. The research recommends the minimal construction.

```ts
function niceLinearTicks(lo: number, hi: number, format: ChartValueFormat): { value: number; label: string }[] {
  if (!(hi > lo)) return [{ value: lo, label: formatValue(lo, format) }];
  const span = hi - lo;
  const rough = span / 5;
  const magnitude = Math.pow(10, Math.floor(Math.log10(Math.abs(rough)) || 0));
  const normalized = rough / magnitude;
  let nice: number;
  if (normalized < 1.5) nice = 1;
  else if (normalized < 3) nice = 2;
  else if (normalized < 7) nice = 5;
  else nice = 10;
  const step = nice * magnitude;
  const start = Math.ceil(lo / step) * step;
  const out: { value: number; label: string }[] = [];
  for (let v = start; v <= hi + step * 0.001 && out.length < 12; v += step) {
    out.push({ value: v, label: formatValue(v, format) });
  }
  return out;
}
```

```ts
// src/lib/chart-ticks.ts (name at Claude's discretion). Pure, no transcendental Math.*.
export function pow10(n: number): number {
  return Number(`1e${n}`); // spec-exact; equals Chromium's Math.pow(10, n) for n in -30..30 (measured)
}
export function decimalExponent(x: number): number {
  const s = Math.abs(x).toExponential(); // e.g. "2.986021615051442e-4"
  return Number(s.slice(s.indexOf("e") + 1)) || 0; // mirrors today's `|| 0` for 0 / non-finite
}
// Shared by niceLinearTicks (divisor 5, cap 12) and both niceTicks (divisor = count, cap 8).
export function niceStepValues(lo: number, hi: number, divisor: number, cap: number, anchor = 0): number[] {
  const rough = (hi - lo) / divisor;
  const magnitude = pow10(decimalExponent(rough));
  const normalized = rough / magnitude;
  const nice = normalized < 1.5 ? 1 : normalized < 3 ? 2 : normalized < 7 ? 5 : 10;
  const step = nice * magnitude;                    // keep `nice * magnitude` (Pitfall 5)
  const start = Math.ceil(lo / step) * step;
  const out: number[] = [];
  for (let v = start; v <= hi + step * 0.001 && out.length < cap; v += step) {
    out.push(Math.abs(v - anchor) < step * 1e-6 ? anchor + 0 : v); // snap; `+ 0` kills -0
  }
  return out;
}
```

Each caller keeps its own `!(hi > lo)` early return and its own formatter (TK-6, TK-4). `anchor = config.baseline` for growth charts (baseline 1) is the natural extension for TK-3. It was **not** separately swept: the sweep's linear cases used the percent format and an anchor of 0. Add it to the helper's test matrix.

### Finding 4: `decimalExponent` vs `Math.floor(Math.log10(x))`

For every n in -30..30 these two agree on `10^n` and on `10^n·(1+2^-52)`. They disagree only on the double **just below** each power of ten: e.g. `0.00009999999999999999`, where `floor(log10)` = -4 and `decimalExponent` = -5. Both engines produce the same list. `[VERIFIED: probe this session]`
- Consequence: an input sitting exactly one ulp under a power of ten picks `nice = 10, magnitude = 10^(n-1)` instead of `nice = 1, magnitude = 10^n`.
- The step is the same decimal value. It may differ by an ulp from today's browser output. It is still identical across engines.
- Probability: zero in the 4,400-case sweep, and measure-zero in practice. Record it in the helper's doc comment rather than special-casing it.

### Pattern 1: Auto fixture guard (SC-4)

```ts
// e2e/helpers/hydration-guard.ts
import { test as base, expect } from "@playwright/test";
export * from "@playwright/test";

const HYDRATION = [/Minified React error #418\b/, /Hydration failed because the server rendered/];

export const test = base.extend<{ hydrationGuard: void }>({
  hydrationGuard: [
    async ({ context }, use) => {
      const hits: string[] = [];
      context.on("weberror", (e) => {
        const msg = String(e.error()?.message ?? e.error());
        if (HYDRATION.some((re) => re.test(msg))) hits.push(`${e.page()?.url() ?? "?"}: ${msg.slice(0, 300)}`);
      });
      await use();
      expect(hits, "React hydration mismatch (#418) on a seeded page").toEqual([]);
    },
    { auto: true },
  ],
});
export { expect };
```

- Fail **after** `use()`, so the test's own assertions run first. The assertion fires in teardown, so a #418 that was swallowed by a race still turns the test red. That is "red, not flaky".
- Use `context.on("weberror")` or `page.on("pageerror")`; both are measured to receive #418.
- ⚠️ Keep `export * from "@playwright/test"` **before** `export const test`/`expect`, so that specs importing `type Page` or `Locator` from the same module still compile (several do, e.g. `composite-factsheet-render.spec.ts:58` imports `type Page`). A local export takes precedence over the star re-export.
- The scratch census fixture used exactly this shape and compiled against all 26 specs.

### Anti-Patterns to Avoid
- **Re-query or retry at `target-size.spec.ts:274`.** Forbidden (SC-5). Measured unnecessary: 10/10 after the fix.
- **Replacing `Math.pow` with `10 **`.** Measured identical to `Math.pow` in both engines (same four diffs).
- **Keeping `Math.log10` in the helper.** Engine-divergent (Finding 1). Use `toExponential`.
- **Normalising `nice = 10` → `nice = 1, e + 1`.** It changes `step` by an ulp vs today's `10 * magnitude` in some decades, which breaks byte-identity with today's browser (TK-4).

## Common Pitfalls

### Pitfall 1: `EquityChart.test.tsx` uses `Math.pow` as a recompute counter
**What goes wrong:** The two tests at `EquityChart.test.tsx:837-880` spy on `Math.pow` and assert `expect(afterMount).toBeGreaterThan(0)` (the comment at `:826` says the walker "calls Math.pow(10, p) for p in [-3..3] — seven calls per projection"). Removing `Math.pow` from EquityChart makes both fail for the wrong reason. `[VERIFIED: EquityChart.test.tsx:826-880]`
**How to avoid:** Retarget the counter in the same plan, keeping the intent (the projection memo does not recompute on hover). Recommended: `vi.mock("@/lib/chart-ticks", async (orig) => { const m = await orig<typeof import("@/lib/chart-ticks")>(); return { ...m, pow10: vi.fn(m.pow10) }; })` and count `pow10` calls. Update the `:826` comment. No other `spyOn(Math` touches in-scope files (the remaining hits are `Math.random` in `resilient-fetch.retry.test.ts`).

### Pitfall 2: A test that passes on today's code under vitest
**What goes wrong:** Node's inexact pow gives the server's exact 0, so "zero tick is 0" passes today (Finding 5).
**How to avoid:** Use the stub regimes, and show the test failing on today's code (red-before/green-after) in the plan's verification step.

### Pitfall 3: Negative zero
**What goes wrong:** `Math.ceil(-0.3) === -0`, so a start index or a snapped value can be `-0`. `(-0).toFixed(1)` prints `"0.0"`, and `-0 >= 0` is true, so labels survive. But TK-2 says positive zero, and `Object.is(-0, 0)` is false in tests.
**How to avoid:** Snap to `anchor + 0`. Assert with `Object.is(v, 0)`.

### Pitfall 4: Duplicate React keys after a snap
**What goes wrong:** Rows 1, 3 and 4 key on `` `y-${t.value}` ``, so two ticks snapping to the same value would collide (TK-5).
**How to avoid:** Keep the snap threshold far below the step (`step * 1e-6`). The sweep produced no duplicates or tick-count changes (0 shape changes beyond the zero label).

### Pitfall 5: Changing `step` arithmetic changes non-zero labels
**What goes wrong:** Finding 3. Rounding, index × step, or re-normalising `nice` shifts labels at `toFixed` half-way points. EquityChart is the worst case: 377/4,400.
**How to avoid:** Change only the magnitude source and add the snap. Keep `step = nice * magnitude` and the accumulation.

### Pitfall 6: Citing the UI-SPEC's golden census
The UI-SPEC's three-PNG claim is wrong at HEAD (Finding 8). Cite this research's 29-PNG census instead.

### Pitfall 7: The guard landing before the fix
It turns `target-size` deterministically red and blocks main CI, which makes Railway skip the analytics deploy. Same PR, or after.
