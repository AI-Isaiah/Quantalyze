## Summary

The diff range is `c0f9f2513...HEAD`. The review checked four things:

- the engine-independent tick helper;
- its five consumers;
- the hydration-guard Playwright fixture with its self-test and its anti-drift vitest;
- the composite axe visibility wait.

**The production fix holds, and no BLOCKER was found.** What was checked and found sound:

- **Tick values do not depend on the engine.** `niceStepValues` uses only these operations, each exactly specified in ECMAScript:
  - `toExponential()`, which gives the shortest round-trip exponent;
  - `Number("1e<n>")`, a correctly rounded parse;
  - IEEE `+ - * /`, `Math.ceil` and `Math.abs`.

  The step, start and accumulation are therefore bit-identical in Node and Chromium. The label formatters (`formatValue`, both `formatPct`) use `toFixed`, which is also exactly specified.
- **The snap cannot swallow a real tick.** Ticks sit one step apart. The anchors in use (`baseline` 0 or 1, from `chart-configs.ts`) are either on the step grid or at least step/2 from it. The snap window is step × 1e-6, so only the tick at the anchor can move.
- **-0 is never emitted.** Both branches of `chart-ticks.ts:89` add `+ 0`, and `-0 + 0 === +0`.
- **The `isBaseline` tolerance is consistent.** On the linear path a snapped tick equals the baseline exactly. On the log path the `1 × pow10(0)` candidate is exactly 1. `tickTolerance` returns 0 for a single tick, which reduces the check to exact equality.
- **The guard's message patterns match this stack.** In Next 16.3.6 with React 19.3.0, `throwOnHydrationMismatch` builds `formatProdErrorMessage(418, "text"|"HTML")` with no `cause`. Next's `onRecoverableError` passes it to `reportGlobalError`, which is `reportError`. The dev message starts with "Hydration failed because the server rendered", which the second pattern matches.
- **The listener is attached in time.** `hydrationGuard` is an auto fixture that depends on `context`, so it is set up before any navigation in the test body.
- **No seeded spec escapes the fixture.** None opens its own `browser.newContext()` or `browser.newPage()`. Every `beforeAll` takes no browser fixture.
- **The 25 import swaps are clean.** Each of the 25 seeded specs differs from base only by its `@playwright/test` → `./helpers/hydration-guard` import line. `composite-factsheet-render.spec.ts` also adds the h1 wait.

The findings are all in the **proof** layer, not the fix: places where a guard or test can pass when it should fail.

## Warnings

### WR-01: The guard asserts in teardown without waiting for hydration, so a late #418 is missed

**File:** `e2e/helpers/hydration-guard.ts:50-54`

**Issue:** `expect(hits).toEqual([])` runs as soon as `use()` returns. React reports a mismatch only after it hydrates the affected subtree and commits. That happens after scripts load, and for a streamed Suspense segment after its reveal.

Many seeded specs end straight after a server-text assertion or an axe scan. In those specs, the test can finish and the context can close before `onRecoverableError` fires. A real #418 on such a page never reaches `hits`, and the test stays green.

This is the "listener too late" class, but on the other end: the listener is attached in time, and the assertion runs too early.

**Fix:** before asserting, let every open page finish loading and go idle:

```ts
await use();
for (const p of context.pages()) {
  if (p.isClosed()) continue;
  await p.waitForLoadState("load").catch(() => {});
  await p
    .evaluate(() => new Promise<void>((r) => requestIdleCallback(() => r(), { timeout: 2000 })))
    .catch(() => {});
}
expect(hits, "...").toEqual([]);
```

### WR-02: The self-test's expected-failure cases accept a failure for any reason

**File:** `e2e/hydration-guard.self-test.spec.ts:31-47`

**Issue:** both biting cases call `test.fail()`. Playwright counts *any* failure as the expected one: a `waitForEvent` timeout, an exception thrown inside the guard's listener, or the `toBe(message)` check at `:27`.

The unrelated-error control case does catch failures that every case shares, such as `weberror` no longer firing or Chromium rewriting the message, because all three cases go through `reportPageError`. It does not catch a failure on the #418 path alone.

For example, suppose a refactor makes the listener throw while it formats `webError.page()?.url()` for a matching message. The two expected failures still go "red as expected", the control stays green, and the guard records nothing.

**Fix:** do not invert. Expose the collected hits through a test-scoped fixture, for example `hydrationHits: string[]` that `hydrationGuard` fills. Then assert in the positive:

```ts
test("records React #418", async ({ page, context, hydrationHits }) => {
  await reportPageError(page, context, "Minified React error #418; ...");
  expect(hydrationHits).toHaveLength(1);
  hydrationHits.length = 0; // let teardown pass
});
```

Keep one `test.fail()` case as well, so the teardown-throws path stays covered.

### WR-03: Nothing pins the self-test in CI, so the proof can be dropped silently

**Files:** `src/__tests__/e2e-seeded-hydration-guard.test.ts` (whole file) and `.github/workflows/ci.yml:6006`

**Issue:** the anti-drift test parses `ci.yml` and pins the 26 seeded specs. It never checks that `e2e/hydration-guard.self-test.spec.ts` is still in the unseeded `npx playwright test` line, the only place that proves the guard bites. A grep of `src/__tests__` for `hydration-guard.self-test` finds nothing.

If that one token is removed from line 6006, every check stays green and the guard can go blind unnoticed. This is the "anti-drift satisfied vacuously" class from the review focus.

**Fix:** add an assertion beside the seeded-list pin:

```ts
it("the guard's self-test runs in CI's unseeded e2e list", () => {
  const wf = readRepoFile(CI_WORKFLOW);
  expect(wf).toMatch(/npx playwright test [^\n]*\be2e\/hydration-guard\.self-test\.spec\.ts\b/);
});
```

### WR-04: The EquityChart memo test's "mount ran the walker" check can no longer fail

**File:** `src/app/(dashboard)/allocations/widgets/performance/EquityChart.test.tsx:851-858` (and `:880-884`)

**Issue:** this check was meaningful before the phase and is vacuous after it.

- **Before:** `vi.spyOn(Math, "pow")` made a fresh spy inside the test, so its count started at 0. `expect(afterMount).toBeGreaterThan(0)` therefore proved that this test's mount reached the walker.
- **After:** the spy is the module-level `vi.fn(actual.pow10)` from `vi.mock`. It is cleared only in the two tests' `finally` blocks.
- **Nothing clears it in between:** `vitest.config.ts` sets no `clearMocks`, `mockReset` or `restoreMocks`, and the file's top-level `beforeEach` (`:44`) does nothing.

Every earlier `describe` in the file renders `EquityChart` (`:67`, `:550`, `:607`, `:666`, `:759`, `:801`), so the count is already positive when the first memo test starts. A regression that stopped this mount from reaching the walker, or that moved the walker away from `pow10`, would still pass `toBeGreaterThan(0)`.

The 02-SUMMARY says "they were never sensitive to earlier calls". That holds for the relative-count assertion, not for this sanity pin.

**Fix:** clear the spy at the start of each test, not only in `finally`:

```ts
const powSpy = vi.mocked(pow10);
powSpy.mockClear();
```

### WR-05: The helper guard is a denylist, but its failure message promises an allowlist

**File:** `src/__tests__/chart-ticks-class-guard.test.ts:44` and `:190-196`

**Issue:** `HELPER_BANNED_RE` (`/Math\.pow\b|Math\.log10\b|Math\.log\(|Math\.exp\b|\*\*/`) bans only four functions and the exponent operator. Its failure message says the helper may use "only + - * /, Math.ceil and Math.abs", and the module header says the same (`chart-ticks.ts:15-19`).

These would all pass the guard while breaking the engine-independence contract: `Math.log2`, `Math.log1p`, `Math.expm1`, `Math.cbrt`, `Math.sin` and `Math.hypot` (all implementation-approximated). So would `Math.round`, which is exact but outside the stated contract.

There is also a second gap. `NATIVE_POW10_RE` (`:40`) matches only a literal `10`. `Math.pow(10.0, n)`, `Math.pow(1e1, n)`, `Math.pow(TEN, n)` and a destructured `pow(10, n)` all pass.

**Fix:** turn the helper check into a real allowlist that matches its own message:

```ts
const HELPER_BANNED_RE = /Math\.(?!ceil\b|abs\b)\w+|\*\*/;
```

Add one self-test sample, for example `Math.log2(x)`, so the widened rule is proven to fire.

## Info

### IN-01: The header's "known edge" claim is wrong for some decades

**File:** `src/lib/chart-ticks.ts:29-33`

**Issue:** the header says that when `toExponential()` picks the lower decade and `nice = 10`, "the step is the same decimal value". That is not true in general. IEEE-exact multiplication gives `10 * 1e-6 === 9.999999999999999e-6` (not `1e-5`) and `10 * 1e-11 === 9.999999999999999e-11` (not `1e-10`). The same holds for every `nice = 10` step at those magnitudes, not only the one-ulp edge.

This does not affect hydration: the product is identical in both engines, and the anchor snap absorbs it at the baseline. The documentation is still inaccurate.

**Fix:** reword to "the step is the same value in every engine (IEEE multiplication), though not always the decimal literal of the next power of ten".

### IN-02: The log-scale decade selection still uses native transcendentals

**File:** `src/app/factsheet/[id]/v2/TimeSeriesChart.tsx:1482-1485`

**Issue:** `Math.exp(lo)`, `Math.floor(Math.log10(eLo))` and the `eLo * 0.95` / `eHi * 1.05` candidate filter can, in principle, choose different candidates in the two engines. The same applies to the `niceLinearTicks(eLo, eHi, …)` fallback, which then produces different tick text.

This is excluded by the locked decision (RESEARCH Open Question 1, measured 0/4,400), and the class guard exempts it on purpose. It is recorded here so the exemption stays visible.

**Fix:** none in this phase. If it is ever revisited, take the decades from `decimalExponent(eLo)` and `decimalExponent(eHi)`.

### IN-03: The guard comment over-claims that retries cannot mask a #418

**File:** `e2e/helpers/hydration-guard.ts:25-27`

**Issue:** "A #418 is deterministic for a given pair of render engines" holds for the tick class, not for #418 in general.

- `playwright.config.ts` sets `retries: 2` in CI and has no `failOnFlakyTests`.
- A mismatch that depends on time or a race, such as text built from `Date.now()`, would show as "flaky" and exit 0.
- `EquityChart.tsx:1879` renders `formatRelativeTime(lastSyncAt, Date.now())` in its render body when the chart is stale. Whether this reaches a seeded page's SSR was not confirmed, so it is cited only as an example of the shape.

**Fix:** narrow the comment. Optionally, have the fixture call `testInfo.annotations.push(...)` when it records hits on a retry, so a flaky #418 stays visible.

### IN-04: The SSR tick test's engine stub is inert against the fixed code

**File:** `src/app/factsheet/[id]/v2/TimeSeriesChart.ticks.test.tsx:88-106`

**Issue:** after the fix, the linear tick path never calls `Math.pow`. The two regimes therefore run identical code, and the "byte-identical" test passes no matter how `Math.pow` is stubbed. It would catch only a return of `Math.pow(10, …)`, which the static class guard already catches. It would not catch a return of `Math.log10` in the builder, which is not stubbed here.

The real behavioural bite lives in `chart-ticks.test.ts:136-146`, the test where `Math.pow` and `log10` throw. This test is still a useful end-to-end pin on the "+0.0%" solid-baseline markup.

**Fix:** optional. Also stub `Math.log10` (one ulp off) in the Node regime, so the SSR test bites on both halves of the old idiom.
