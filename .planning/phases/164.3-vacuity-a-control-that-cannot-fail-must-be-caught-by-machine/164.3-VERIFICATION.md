### 2. Is any job in the aggregator's `needs:` but not in the result loop, or vice versa?

**No.** Mechanically compared: `needs` = 12, loop = 12, symmetric difference empty, and every loop
label matches the `needs.<job>.result` expression it reads (a mislabelled row would read another
job's result — checked and clean). The three new rows are wired in **both** places:

- `sql-gate-lint` — STRICT default arm, no tolerance. Correct: hermetic, no `if:`, cannot legitimately skip.
- `sql-mutation` — STRICT default arm, no tolerance. Correct: no secret, no repo variable, no `if:`, hosts its own clusters.
- `plan-anchor-verify` — the one row with a tolerance arm, and the reasoning is a **trigger**, not a credential: its `if: github.event_name == 'pull_request'` exists so a pending plan's drift on main cannot redden main CI and stall the Railway analytics deploy. On a `pull_request` the row is strict, fork or not. Sound.

The `sql-mutation` job additionally carries an assertion step that **re-reads the runner's printed
coverage and arm counts and compares them to `FILES_FLOOR`/`ARMS_FLOOR` imported from `run.mjs`**,
