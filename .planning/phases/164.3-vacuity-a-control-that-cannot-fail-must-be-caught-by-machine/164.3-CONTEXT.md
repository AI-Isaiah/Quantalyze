## Implementation Decisions

### Mutation runner (criterion 1)
- **D-01:** Runs over the **annotated** corpus only. It MUST print coverage as
  `files_annotated / files_total` on every run and enforce a ratchet floor, because a runner
  reporting PASS while covering 1.4% of the corpus is the same shape as the SKIP-that-reads-as-PASS
  on this phase's own defect list. Coverage today is 1/71; the floor starts there and only rises.
- **D-02:** For each annotated arm: apply the mutation named in its `RED-UNDER`, assert the file
  goes RED, restore, assert GREEN. An annotation whose mutation does not redden its arm is a defect.
- **D-09 (new):** **Both failure modes hard-fail with exit 1** — a `RED-UNDER` that does not bite,
  and coverage below the ratchet floor. Not advisory, not a warning.
  ⚠️ The floor is a RATCHET pinned at today's measured value (1/71), not an aspiration: it fails on
  REGRESSION, never "until 71/71". 164.4 raises it as it backfills.
  Rationale the founder chose this over report-only: branch protection is deliberately OFF here, so
  a non-zero exit is the *only* signal that exists. Softening it reproduces the status quo the phase
  exists to change — every mechanism this would catch was already GREEN in CI.

### Disposable-PostgreSQL lane (criterion 2)
- **D-03:** `PROC-01`'s implementation, promoted from the mid-phase script
  (`.planning/phases/164-.../pg-harness/run.sh`, 56 lines). Two defects its own reviewers hit are
  requirements, not anecdotes: it reused another agent's cluster and then `DROP SCHEMA public
  CASCADE`, and it enabled RLS on nothing but the table under test.
- **D-04:** ⚠️ A third defect, measured 2026-08-28 by reading the script: **it has no `pg_ctl stop`,
  no `trap`, and no `rm`.** Nothing in it ever stops what it starts. Consequence measured the same
  day: 27 orphaned Postgres volumes (904 MB) and a container up 10 days, contributing to a
  disk-exhaustion incident (8.2 GB free). The lane MUST stop and remove every cluster it starts,
  including on failure and on interrupt — `trap ... EXIT INT TERM`, not a cleanup line at the end.
- **D-07 (new):** **One script, two hosts — local AND a CI job, identical semantics.**
  ⛔ The mutation run may NOT use the shared TEST database: it deliberately breaks arms and restores
  them, and TEST sits behind an advisory-lock mutex shared with everyone else's CI. That is the same
  constraint that blocks Phase 159's items.
  Two portability fixes are in scope and both are measured, not guessed:
  * `PGBIN` defaults to `/opt/homebrew/opt/postgresql@16/bin` — macOS-only; it will not start on an
    ubuntu runner. Resolve from PATH / `pg_config`, with the homebrew path as a fallback.
  * The fixed default `PORT=55432` serialises concurrent agents (the collision guard correctly
    refuses rather than destroying a neighbour's cluster). Allocate a free port per run.
  — **Reversibility:** costly — once a CI job exists, the runner's invocation contract is depended on
  by 164.4's backfill oracle and by D-08's spec. Changing host semantics later means changing all
  three. ⚠️ An A/B that changes invocation mode is not an A/B (see
  `reference_gstack_evidence_wrapper_reddens_suite`).

### Criterion 4 — repo-vs-PROD body diff

⛔ **D-10 and D-11 below are SUPERSEDED by D-12/D-13 (founder ruling 2026-08-29, on facts that were not available when they were made). They are kept because the REASONING still binds: the check must be unskippable, and it must read PROD rather than TEST.**
- **D-10 (new):** **A CI job reading PROD through a dedicated least-privilege role.** Not a local
  manual step. A gate that only runs when a human remembers is the exact failure this phase exists
  to catch — `/gsd-pr-branch` is the in-repo proof that "nothing invokes it automatically" is a real
  failure mode, and DRIFT-02 (which nearly shipped a GDPR regression) was not caught by a manual step.
  ⛔ Diffing repo-vs-TEST instead was considered and REJECTED: that is DRIFT-01, a different finding.
  TEST agreeing with the repo says nothing about PROD's body, which is where the near-regression lived.
- **D-11 (new):** **Ship it wired and FAIL LOUD when the credential is absent — never skip.**
  If `PROD_BODY_READER_DSN` is unset the job must `exit 1` with an explicit error, not `exit 0` and
  not a skip. Shipping criterion 4 as a skip would be this phase committing `SKIP-01`, its own named
  defect. Accepted consequence: the board reads RED until the role exists. That is the honest state —
  the check genuinely is not running — and branch protection being off means it blocks nothing
  mechanically.
  🔴 **BLOCKING-HUMAN, once:** the founder creates a login role with **no table grants at all**
  (`pg_get_functiondef` needs none) and adds its DSN to CI secrets. I do not create roles or set
  secrets. Record this as a `gate: blocking-human` item in `164.3-VERIFICATION.md`.
- **D-05:** ⚠️ Any body assertion MUST strip `--` comments before matching. Measured live: PROD's
  7-param `_enqueue_compute_job_internal` reports 0 `INTO STRICT` in code but **1** including
  comments. Mechanism 2 on this phase's own defect list is exactly this shape.

- **D-12 (SUPERSEDES D-10/D-11):** **VAC-04 rides the EXISTING `migration-drift-check.yml` job and
  its existing credential.** No new secret, no new role, and **no blocking-human item** — the D-11
  gate is dissolved. Rationale the founder accepted: that secret is already in that job's blast
  radius on every migrations PR, so adding a step to a job that already holds it widens nothing,
  whereas a second prod credential would be a second copy of prod access rather than a smaller one.
  The unskippable requirement is UNCHANGED — an absent credential or an unreadable body still
  exits 1, never skips.
  📋 FOLLOW-UP BOOKED, not dropped: `[VAC-04-ROLE]` in TODOS.md — swap to a zero-table-grant
  read-only role (`pg_get_functiondef` needs no table privileges). A real hygiene win, off the
  critical path.
- **D-13 (new):** **VAC-04 is `pull_request`-triggered with a `supabase/migrations/**` paths filter
  — NOT main-push.** Two independent reasons. (a) It is the correct trigger on its own terms: the
  requirement is "no whole-body `CREATE OR REPLACE` **merges** without a diff", which is inherently
  pre-merge. (b) ⚠️ A consequence the discuss pass did not price: **Railway waits on main CI and
  SKIPS the analytics deploy when it is red.** The founder accepted a red board; they did not accept
  halted deploys. PR-triggering removes that coupling entirely.
- **D-14 (new, from RESEARCH — changes the runner's design):** **The 33 existing `RED-UNDER`
  annotations are PROSE, not machine-executable.** They span three shapes — migration-file edits,
  live-DB `GRANT` statements, and LAYERED compound mutations that require neutering OTHER arms
  first — plus two recorded waivers. A runner cannot apply them as written. The plan must introduce
  a STRUCTURED companion annotation with a per-file parity gate (every prose `RED-UNDER` has a
  machine form, or the file fails), and 164.4 inherits that schema.
  ⭐ And the assertion must be **first-failure identity**, not red-anywhere: mutate, then require
  that the FIRST `TEST FAILED (<ARM ID>)` names the intended arm. "The file went red" is satisfied
  by a mutation that breaks something else entirely — a vacuous check inside the vacuity detector.
- **D-15 (new, from RESEARCH — bounds VAC-07):** **VAC-07 cannot run on the bare `initdb` cluster.**
  `csv-finalize` and `withAuth` speak PostgREST/GoTrue through supabase-js, and the seed helper needs
  GoTrue admin. So there are TWO lanes, not one: the throwaway `initdb` cluster for SQL gates
  (VAC-01/02/06), and the Supabase CLI local stack for the app-level spec (VAC-07). Do not conflate
  them. ⚠️ Open risk, spike FIRST: whether the 263-migration chain replays cleanly. Fallback is a
  `db dump`.
- **D-16 (new, from RESEARCH — bounds VAC-03 honestly):** Of the five mechanisms, **1, 2 and 4 are
  statically lintable; 3 only narrowly; 5 is NOT.** Mechanism 5 (an arm made unreachable by an
  earlier arm covering the same state) is not detectable in SQL text — the runner's first-failure
  discipline is its detector. ⛔ Do NOT ship a rule for mechanism 5 to make the count look complete.
  A lint rule that cannot fire is precisely this phase's named defect, committed by the phase itself.
  Every rule that DOES ship must have a red fixture proving it fires.

- **D-17 (new, found while verifying D-12):** ⛔ **The job VAC-04 is joining CONTAINS a
  skip-that-reads-as-PASS.** `.github/workflows/migration-drift-check.yml:35-47` emits
  `configured=false` plus a `::notice::` when secrets are missing, and every later step carries
  `if: steps.check.outputs.configured == 'true'` — so an unconfigured run reports GREEN having
  checked nothing. That is `SKIP-01`'s exact shape, on the workflow guarding production migrations.
  ✅ **Classified honestly: LATENT, not live.** Measured 2026-08-29 on run 33167385035 — the job
  reaches its real conclusion (`Pending migrations match this PR's additions - no drift`), so the
  secrets ARE configured and the skip branch is dormant. It is a hole that opens the day a secret is
  rotated away, not one that is open now.
  **Two consequences for the plan:** (a) VAC-04's step must NOT inherit
  `if: configured == 'true'` — it does its own check and exits 1, per D-12. (b) Converting the
  existing skip into a hard failure is cheap and squarely in this phase's thesis; do it here rather
  than booking it. ⚠️ Verify before changing: confirm the vars/secrets are set for FORK PRs too, or a
  hard failure turns every fork PR red for a reason the contributor cannot fix.

### Criterion 5 (plan-anchor verification) — stays in this phase
- **D-06:** It is a different artifact (PLAN.md, not SQL) at a different execution point, and shares
  no code with the runner. Kept anyway: the phase is scoped by ROOT CAUSE — *the claim and the thing
  are never compared* — not by subsystem, and splitting would leave a one-criterion phase. Planned as
  its own wave so it can be lifted out if it bloats. Evidence it is real: both wave-3 plans were stale
  on arrival — `164-03` specified a two-argument `deriveShareToken` that would have minted links
  failing verification, and `164-04` anchored edits at `v2/page.tsx:563-573` in a file that had
  shrunk to 423 lines.

### Cross-phase — Phase 159's two blocked items
- **D-08 (new):** **Folded in. One spec on the new lane, in this phase.**
  Both 159 items (the concurrent-CAS race, and the 409 remedy) were marked blocked on 2026-08-28 on
  exactly the capability criterion 2 builds: request-level control over two `csv-finalize` POSTs
  carrying one `wizard_session_id`. A browser structurally cannot produce it — re-entering the wizard
  after a completed submit mints a FRESH session, observed live on production the same day — and TEST
  must not be raced.
  The spec: two concurrent finalize POSTs on one never-classified session; assert exactly one 2xx
  applied receipt, one honest raced refusal, and that `category_id` holds the winner.
  ⭐ The reason to do it HERE rather than after: it proves the lane against a REAL consumer instead of
  only against the gate corpus. A lane that can run `supabase/tests/*.sql` is not automatically one
  that can drive concurrent HTTP POSTs against an app talking to it — that is a different shape, and
  discovering it after the lane is fixed is how a cheap addition becomes rework.
  Bounded: one spec, no production code changes.
