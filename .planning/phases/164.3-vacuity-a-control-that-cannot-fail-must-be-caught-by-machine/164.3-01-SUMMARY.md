**`scripts/pg-lane/run.sh` — a throwaway-cluster lane with trap-based cleanup proven able to fail, portable PGBIN/port resolution, and a SHAPE 1c tracer that drives the real 103-arm gate mutate→RED(first-failure identity)→pristine→GREEN in ~5 seconds.**

## Accomplishments

- **The lane exists and cleans up.** The promoted script stops and removes every cluster it starts — on success, on a failing gate, on SIGTERM and on SIGINT. The mid-phase harness it replaces had **no `pg_ctl stop`, no `trap` and no `rm` anywhere**, which is what produced 27 orphaned Postgres volumes (904 MB) and contributed to a disk-exhaustion incident on 2026-08-28.
- **The cleanup was observed failing.** Neutering `trap cleanup EXIT` in a scratch copy turned the self-test RED with an orphaned cluster still listening. This is the phase's own standard applied to the phase's own tooling.
- **The tracer proves the phase's architecture end-to-end.** A machine-applied mutation of a *copy* of migration `20260827120000` (`generation` BIGINT → INTEGER) drives the real gate file to `TEST FAILED (SHAPE 1c)` **as the first failure**, and the pristine copies pass all 103 arms. The checkout is never touched.
- **The invocation contract is fixed and documented** (`README.md`), including the `--post-apply` hook plan 05's runner needs for live-DB `GRANT`-shape mutations, so plan 08's CI job can paste it verbatim.
- **Runtime budget measured, not guessed:** ~2 s per full lane run (boot + 2 fixtures + 2 migrations + 103-arm gate). 30 arms ≈ 1 minute of lane time.

## The final CLI contract

```bash
bash scripts/pg-lane/run.sh \
     --workdir <scratch-dir> \
     --apply <file.sql> [<file.sql> ...] \
     [--post-apply <file.sql>] \
     --gate <gate.sql>

bash scripts/pg-lane/run.sh                 # legacy demo (fixtures + both migrations + gate)
bash scripts/pg-lane/run.sh --self-test
bash scripts/pg-lane/run.sh --tracer-proof
```

Exit codes: `0` gate passed · `2` port collision refused · `130`/`143` SIGINT/SIGTERM · otherwise the failing step's own status (psql returns `3` on a gate `RAISE EXCEPTION` under `ON_ERROR_STOP=1`).

Environment: `PGBIN` and `PORT` override; **`PGD` deliberately does not** — it is derived from `--workdir` so cleanup owns exactly what the run created. The cluster lives at `<workdir>/pgd` and is removed on exit; the workdir itself belongs to the caller and is never removed.

## Decisions Made

- **Cleanup scope:** removes `<workdir>/pgd` only. The caller's workdir survives, so the mutation runner (plan 05) owns its own scratch lifetime and can inspect mutated copies after a run. Modes that allocate their own workdir (`legacy`) remove it via a separate `OWNED_WORKDIR` flag.
- **The occupied-port self-test squats with a REAL cluster.** A plain TCP listener was considered and rejected: `pg_isready` sends a startup packet and would never report such a socket as ready, so the guard would not have fired and check 1 would have been vacuous — a vacuous check inside the vacuity detector.
- **`--self-test` and `--tracer-proof` live in the same script, no wrapper.** Local and CI runs must be byte-identical in *mode*; a wrapper that changes invocation changes the result.
- **`REPO` resolves via git first, then a path fallback.** The fallback exists specifically so a scratch *copy* of the script — the anti-vacuity neuter harness — still runs outside a git repo.
- **Node fallback for port allocation.** Primary allocation binds port 0 via node; a random-high-port probe loop covers a host without node. The `pg_isready` guard remains in both paths for the TOCTOU window.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The specified SHAPE 1c mutation target does not exist where the plan says it does**

- **Found during:** Task 1 (tracer)
- **Issue:** The plan says "replace the first occurrence of `generation BIGINT` with `generation INTEGER`", and RESEARCH §Q3's example `RED-UNDER-M` says `{"find":"generation BIGINT","nth":1}`. Measured: that literal single-space string occurs **exactly once** in migration `20260827120000`, at line 828 — `RETURNS TABLE (generation BIGINT, nonce UUID)` — which is **not** the STEP 1 CREATE TABLE the arm's prose names. Mutating it trips the migration's *own* verification block at line 1181 (`create_strategy_share does not declare TABLE(generation bigint, nonce uuid)`) and **aborts the apply**, so the gate would never execute and no arm could be the first failure. The real column declaration at line 170 is `  generation  BIGINT      NOT NULL DEFAULT 1 CHECK (generation >= 1),` — two spaces.
- **Fix:** The tracer pins the real bytes of the line-170 declaration and asserts the occurrence count is exactly 1, emitting `MEASURE_FAIL` otherwise. Documented in the script, in `README.md`, and in the Task 1 commit body.
- **Files modified:** `scripts/pg-lane/run.sh`, `scripts/pg-lane/README.md`
- **Verification:** `--tracer-proof` passes; mutating line 828 instead was confirmed to be the apply-aborting path by reading the migration's verification block.
- **Committed in:** `c53a6354`
- **Why it matters beyond this plan:** this is the prose-locator hazard RESEARCH §Q3 predicted, arriving on the very first arm. It is direct evidence for plan 05 that `RED-UNDER-M` must carry executable bytes with an occurrence assertion, and that a runner which silently no-ops a find/replace would report "mutation applied, arm did not redden" — a false defect — or worse, mutate the wrong thing and read the resulting red as success.

**2. [Rule 3 - Blocking] `REPO` resolution aborted the neuter harness**

- **Found during:** Task 2 (anti-vacuity neuter step)
- **Issue:** `REPO=$(git -C "$SCRIPT_DIR" rev-parse --show-toplevel)` fails under `set -e` when the script is copied outside a git repo — which is exactly what the required neutered-copy run does.
- **Fix:** git first (worktree-correct), then a `$SCRIPT_DIR/../..` path fallback.
- **Files modified:** `scripts/pg-lane/run.sh`
- **Verification:** the neutered copy ran from the scratchpad and produced the required RED; `--tracer-proof` re-verified afterwards (git arm still used inside the repo).
- **Committed in:** `c53a6354`

**3. [Rule 2 - Missing Critical] Empty-array expansion hardening**

- **Found during:** Task 1
- **Issue:** `"${applies[@]}"` on an empty array aborts with "unbound variable" under `set -u` on bash < 4.4 — macOS `/bin/bash` is still 3.2 — turning a missing `--apply` into an opaque abort instead of the intended fail-loud argument error.
- **Fix:** `${applies[@]+"${applies[@]}"}` at the call site and an `if` guard when capturing, so a missing `--apply` produces `ERROR: --apply needs at least one file`.
- **Files modified:** `scripts/pg-lane/run.sh`
- **Verification:** covered by every self-test invocation (bash 5.3 locally); the guard is defensive for a bash-3.2 host.
- **Committed in:** `c53a6354`

## Issues Encountered

- **The neutered self-test RED'd earlier than the plan's wording anticipated.** With `trap cleanup EXIT` neutered, the first orphan assertion *reached* is check 1's squatter teardown, not check 2. Both use the same `no_orphan` helper. To discharge the plan's wording literally, a second neutered variant additionally bypassed check 1's teardown assertion so execution reached check 2, which was then observed RED (`SIGTERM mid-run: a postgres is STILL listening on 127.0.0.1:59794`). Both neutered copies were discarded, their leftover clusters stopped and their data dirs removed; `pgrep` afterwards shows only the developer's own long-running homebrew instance.
- **Signal timing is deferred, by design of bash.** A trapped signal is not handled until the running foreground command returns, so the kill checks wait (bounded, 20 s) for the run to exit before judging. Without the trap, bash's default disposition kills it immediately and the orphan survives — which is precisely the difference the check detects.
