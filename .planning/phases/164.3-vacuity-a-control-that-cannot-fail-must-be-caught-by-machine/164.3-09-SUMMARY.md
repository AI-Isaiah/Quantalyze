**A resolver that re-reads every `path:line` anchor, bound quote, opt-in symbol claim and `@`-reference a pending PLAN.md makes about the tree — with both of Phase 164's measured stale-plan failures as fixtures it must flag — wired into CI as a hermetic `pull_request` job that is strict in the `frontend` aggregator.**

## Accomplishments

- **The claim and the thing are now compared.** `scripts/verify-plan-anchors.mjs` re-resolves four kinds of claim and aggregates every miss with file, line, claim and reason (never first-miss-exit).
- **Both historical failures are fixtures, proven RED.** A file of exactly 423 lines anchored at `:563-573` (164-04), and a two-argument `deriveShareToken` quoted against a three-argument source (164-03). A green fixture passes in the same run.
- **The verifier cannot be silently blinded by a NUL byte.** Reads go through `node:fs`. The test file pins an anchor into a NUL-carrying fixture in BOTH polarities — a true claim resolves, a false one still fails — so a rewrite that reaches for `grep` reds the suite.
- **A CI job that can fail, on the event where it matters.** `plan-anchor-verify` runs `--self-test`, then the verbatim local `--pending` invocation, then an assertion that the scan printed its counts.

## The grammar this ships

| Kind | Shape | Fails when |
|---|---|---|
| `anchor-range` | `path:start[-end]` | path resolves to nothing / to >1 file, or the range exceeds the file's line count |
| `anchor-quote` | a backtick snippet on the anchor's line (after it) or the line below | the snippet is not in the range — the message says whether it moved (with the line) or is gone |
| `symbol-pragma` | `<!-- verify-symbol: <path> <symbol> -->` | the file is missing, or the symbol appears nowhere in it |
| `context-ref` | a line beginning `@<path>` | an in-repo target does not exist (`~`, `/`, `$`-prefixed refs are out of tree and ignored) |

## Decisions Made

1. **`pull_request`-scoped, not main-push** (the plan's instruction, and D-13's reasoning applied rather than re-decided). `.planning/` is tracked and plans merge to main before they execute, so a pending plan's anchor drifting on main would redden main CI — and **Railway waits on main CI and skips the analytics deploy when it is red**. Nothing is lost: a stale anchor matters at execute time, and execution happens on a branch. The aggregator row is strict on `pull_request` and tolerates `skipped` only on the events the job's `if:` excludes; the tolerance is a **trigger** carve-out, not a credential one, and the comment says so.
2. **`@`-reference checking was added to the grammar** (beyond the plan's three listed claim types). Without it the scan resolves **zero** claims on today's corpus — a gate that reads green having checked nothing, which is this phase's named defect. `@`-refs are GSD's own existing convention (no invented syntax), they are claims about the tree *now*, and an unresolvable one means the executor reads nothing and never notices. Cost: ~10 lines.
3. **Bare-symbol existence is opt-in via a pragma, not inferred.** A heuristic treating every backticked identifier near a path as an existence claim would fire on what plans mostly contain — names of code that does not exist yet.
4. **No claim-count floor in CI.** Zero claims is a legitimate measurement (a tree whose plans have all been executed). Inventing a floor would redden CI for an honest state; the self-test carries the "rules can still fire" burden instead.
5. **Extension allow-list on anchor paths.** Without it `164.3:450-519` — a phase number and a section range — parses as a path and the gate starts inventing failures. Stated as a limitation in the header rather than left to be discovered.

## Issues Encountered

- **`findQuoteLine` first reported the window's start line, not the match's line** (a quote at line 3 reported as line 1). Caught by the test that pins the "moved" message, which is the only reason it was noticed. Rewritten to flatten the file into an offset-mapped string and map the match offset back to the true line. Blank lines are dropped from the flattening rather than joined as empty, so a quote spanning a blank line still matches.

## Honest limitations (for `164.3-VERIFICATION.md`)

1. **The execute-time seam is a convention, not a mechanism.** The convention sentence future planners follow: ***each PLAN's first task invokes `node scripts/verify-plan-anchors.mjs <plan-path>` and halts on a non-zero exit.*** It is enforced socially and backstopped by the CI job. The installed gsd-core exposes no hook that could make it mechanical (`activeHooks: []`, measured), and gsd-core is out of scope. Saying otherwise would be a claim about a control that nothing compares to the thing.
2. **The job is `pull_request`-only by design.** A stale anchor that lands on main is caught on the next PR that touches the tree, not at merge. That is the deliberate price of not coupling the analytics deploy to plan hygiene (decision 1).
3. **Old-phase pending plans are in scope.** `159-01` and `160-07` have no sibling SUMMARY and are therefore scanned. They are green today. If such a plan is abandoned rather than executed, it could one day redden PRs for unrelated work — the remedy then is to summarize or delete it, not to exempt it, since "pending" is exactly the predicate that keeps the scan off the frozen archival corpus.
4. **Anchors with an extension outside the allow-list are not checked** (see decision 5). Stated in the script header.
5. **A quote is bound to an anchor by proximity** (same line after it, or the line below). A plan that puts its quote three lines away is not checked, and a plan that puts an unrelated backtick span directly after an anchor will have it checked. Misses print the claim verbatim, so a false positive is fixed by moving the quote or widening the range.
