## The two findings worth carrying forward

**1. Mechanism 4 and 5 are both cases where the file DID go red.** `SHAPE 5`'s mutation reddened `N1 2a`; `SANITIZE 1e`'s reddened `SANITIZE 1c`. A runner that accepted "the file went red" as proof would have reported both arms as proven-biting *while they were blind* — a vacuous check inside the vacuity detector. This is the strongest available evidence for D-14's first-failure identity rule, and it is why plan 06 could honestly ship no rule for mechanism 5: the identity assertion is a real detector, demonstrated here catching the real thing.

**2. Mechanism 1's re-introduction is green in CI.** `baseline … exit 0` and `arm TENANT 5b exit 0 NO-RED` in the same run: with the probe back inside the subtransaction the gate passes, exactly as it did for the two milestones the mechanism survived review. Only *breaking the thing the arm guards* distinguishes the defective arm from the repaired one — which is the entire argument for the runner existing.

## Decisions Made

1. **Re-introduce, don't merely re-demonstrate.** The plan's mechanism-1 wording (*"record the first-failure line proving the genuine defect is reported by the INTENDED arm"*) permits showing the repaired arm biting. That is the "before" half, and it is recorded — but the objective asks for the mechanism to be re-introduced and caught, so every mechanism here has both halves.
2. **No padding.** Mechanism 2 has no runner demonstration (it defeats a text-matching arm, whose repaired form is a normalizer, not an arm) and mechanism 5 has no lint rule (D-16). Each absence is stated in the record rather than filled with a second control that would make the table look symmetrical.
3. **The record is verified by execution, not by reading.** Mechanism 5's bash fences were parsed out of the committed markdown and run; they reproduced the recorded catch. A demonstration described but not run is the defect this plan exists to expose, and a *command* that only looks re-runnable is the same defect one level down.
4. **Linter demos use a throwaway copy in `supabase/tests/`, never an edit to a tracked gate file**, with the unmutated copy run first as the attribution control (`scanned 72 file(s); 0 finding(s)`). Every finding is therefore attributable to the re-introduction rather than to the corpus.
5. **The pin covers identity, not count.** `ARMS_FLOOR` already fails if an arm stops biting. It cannot see an arm that was *un-annotated*, because the runner tests the annotated corpus — an un-annotated arm is absent, not failing. That gap is exactly how a demonstration would rot, and it is what `vac06-mechanism-arms.test.ts` closes.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The first mechanism-3 re-introduction did not reproduce the mechanism**

- **Found during:** Task 1
- **Issue:** Reverting only the comparison to `gen_b_after IS DISTINCT FROM gen_pre_san + 1` left `N1 3a` biting correctly (`RED (identity ok)`, exit 2). PL/pgSQL short-circuits the `OR` on the leading `raised` term, which is TRUE in the failure case, so the comparison never evaluates. Recording that run as the demonstration would have been a claim about an overflow that did not happen — this phase's own defect, inside its own criterion 6.
- **Fix:** Re-introduced the mechanism at **both** sites the gate file's note names — the comparison AND the `RAISE`'s `expected %` argument slot. Observed `NO-IDENTITY`. Both runs are recorded, so the isolation is visible rather than asserted.
- **Verification:** two runner runs, exit 2 then exit 1.
- **Committed in:** `2f7080e9`
