### PRIMITIVE A — an ACCEPTED neuter still leaves `SET ROLE postgres;` live

`isBranchHead` (`scripts/mutation-runner/run.mjs:322-329`) classifies a line as a branch
head using two predicates that are not anchored against a preceding statement:

```js
/\b(THEN|LOOP)$/i.test(t)              // ← no start anchor
/^EXCEPTION(\s+WHEN\b.*)?$/i.test(t)   // ← `.*` swallows anything after WHEN
```

So a **compound line** — a real statement followed by a branch head on the same line — is
accepted as "structurally a branch head", the backward scan `break`s there, and everything
on and above that line is never classified. Measured at HEAD:

```
"  SET ROLE postgres; IF NOT ok THEN"                    -> isBranchHead = true
"  REVOKE ALL ON t FROM u; FOR r IN SELECT 1 LOOP"       -> isBranchHead = true
"  DROP TABLE t; WHILE ok LOOP"                          -> isBranchHead = true
"  EXCEPTION WHEN OTHERS THEN SET ROLE postgres;"        -> isBranchHead = true
```

`neuterArm(text, "X 1")` on

```sql
DO $$
BEGIN
  SET ROLE postgres; IF NOT ok THEN
    RAISE EXCEPTION 'TEST FAILED (X 1): boom';
  END IF;
  PERFORM later_arm();
END $$;
```

returns **`found: true`** and this text:

```sql
DO $$
BEGIN
  SET ROLE postgres; IF NOT ok THEN
-- NEUTERED(X 1)     RAISE EXCEPTION 'TEST FAILED (X 1): boom';
    NULL; -- neutered X 1 by the mutation runner
```

`SET ROLE postgres;` executes for the rest of the file. No defect kind, no log line — the
verbatim WR-07 / R2-C01 / R3-C01 outcome, fourth time.

The control is the same file with `SET ROLE postgres;` on its own line: `found: false`,
`neuter-missed`, loud. So the predicate is the difference, not the fixture.

**This shape is already in the corpus 164.4 backfills.** Scanning all 71 files under
`supabase/tests/` with the shipped `isBranchHead`, **7 lines** are accepted as branch heads

## Critical Issues

### R4-C01: PRIMITIVE A, fourth recurrence — `isBranchHead` accepts a COMPOUND line, so an accepted neuter leaves `SET ROLE postgres;` live

**File:** `scripts/mutation-runner/run.mjs:322-329` (`isBranchHead`), enforced at `:386`;
same predicate reused by `failureBranches` at `:672`

Full evidence in the PRIMITIVE RECURRENCE section above. Two independent leak arms:

1. `/\b(THEN|LOOP)$/i.test(t)` has **no start anchor**, so any statement followed by
   `IF … THEN` / `FOR … LOOP` / `WHILE … LOOP` on the same line is a "branch head".
2. `/^EXCEPTION(\s+WHEN\b.*)?$/i` — the `.*` swallows arbitrary code after `WHEN`, so
   `EXCEPTION WHEN OTHERS THEN SET ROLE postgres;` is a "branch head" **and** the leaking
   statement is on the head line itself, so it is never even reached by the classifier.

Measured leak (arm 1) and measured leak (arm 2) both shown above with the neutered text.
`supabase/tests/test_profiles_privileged_columns_locked.sql` already carries 7 lines of
shape 2 today.

The shipped oracle cannot catch this: `mutation-runner-neuter.test.ts` generates its inputs
by embedding `BRANCH_HEAD_WORDS` in `--` comments, block comments, string literals and
dollar-quoted bodies. It never generates a line that IS a branch head with a statement in
front of it, which is the one shape `isBranchHead` was written to accept.

**Fix:** a branch head is a line whose *executable* text contains no statement before the
keyword. Require the control keyword to start the line, and refuse a compound tail.

```js
export const isBranchHead = (line) => {
  const t = executableText(line).trim().replace(/;$/, "");
  // A head must not carry a statement of its own before/after the keyword.
  if (/;/.test(t)) return false;                        // compound line — never a bare head
  return (
    /^(BEGIN|DECLARE|ELSE|LOOP)$/i.test(t) ||
    /^EXCEPTION(\s+WHEN\s+[A-Za-z_ ,]+\s+THEN)?$/i.test(t) ||   // no arbitrary tail
    /^(IF|ELSIF|WHILE|CASE|WHEN)\b.*\bTHEN$/i.test(t) ||
    /^(FOR|FOREACH|WHILE)\b.*\bLOOP$/i.test(t)
  );
};
```

Then re-measure against the real corpus before shipping — I have already done the negative
half: with this predicate the 7 `test_profiles_privileged_columns_locked.sql` lines stop
being heads (they carry `;`), which turns them into `neuter-missed` refusals rather than
silent skips, i.e. the loud direction. Verify the 30-arm corpus still bites 30.

And make the oracle range over the class it names: quantify the "no accepted neuter may
leave a `SET ROLE` live" arm over `{statement}; {branch head}` and
`EXCEPTION WHEN OTHERS THEN {statement}` for every word in `BRANCH_HEAD_WORDS`, not only
over embeddings inside non-code regions.

### R4-C02: PRIMITIVE B, fourth recurrence — the identity nonce is forgeable by echoing `current_query()`; no file read, no superuser

**File:** `scripts/mutation-runner/run.mjs:487-537` (the nonce block, `stampIdentities`,
`firstFailureArm`, `unstampedIdentities`), consumed at `:964-988`

Full evidence, the accepted annotation and the control are in the PRIMITIVE RECURRENCE
section. Result: `RED (identity ok)`, `biting 1`, **no `synthesised-identity` defect**, for
an arm guarded by `IF FALSE`.

The design assumption in the header — "an annotation cannot produce a stamped identity
because it cannot know the nonce" — is false whenever server-side code can run *inside the
gate's own statement*. `current_query()` is available to every role; so are
`pg_stat_activity.query` for one's own backend and `RAISE … USING` re-emission. The runner
already permits `CREATE FUNCTION` / `CREATE TRIGGER` in `sql` steps, and the **real corpus
already uses both** (`zz_reproducible_nonce`), so the capability cannot be revoked without
refusing a shipped arm.

**Fix, two parts. Part 1 refuses the measured input; part 2 is the honest bound.**

1. **A stamped identity may only ever appear in RAISE POSITION.** The gate prints its
   identity in exactly one place: immediately after psql's `ERROR:  ` prefix. An echo puts
   it anywhere else. Assert that, and treat any other occurrence as synthesis:

```js
const STAMPED = (nonce) => new RegExp(`TEST FAILED \\(${nonce}\\|([^)]*)\\)`, "g");

/** Stamped identities NOT sitting immediately after psql's error prefix. */
export function echoedIdentities(output, nonce) {
  const out = [];
  for (const line of output.split("\n")) {
    for (const m of line.matchAll(STAMPED(nonce))) {
      if (!/^(ERROR|FATAL|FEHLER):\s+TEST FAILED \($/.test(line.slice(0, m.index + 13))) {
        out.push(m[1]);
      }
    }
  }
  return out;
}
// …beside the existing unstamped check:
const echoed = echoedIdentities(run.output, nonce);
if (echoed.length > 0) {
  addDefect("synthesised-identity", ann.arm, gateRel,
    `MEASURE_FAIL: the lane emitted a STAMPED identity (${echoed[0]}) outside RAISE position — ` +
    `the gate prints its identity only as an error message, so this is the gate's own text ` +
    `being ECHOED back (current_query(), pg_stat_activity, a re-raise). The mutation satisfied ` +
    `the DETECTOR instead of the arm.`);
  continue;   // do NOT count toward biting
}
```

   Verified reasoning against my measured input: the echoed `DO` block reproduces the raise
   as `    RAISE EXCEPTION 'TEST FAILED (<nonce>|FORGE 1): …';`, which is not in raise
   position, so this refuses it. Add it as self-test 9/9 with the fixture above.

2. **State the real residual, because part 1 is still a text rule.** An annotation that
   `regexp_replace`s the identity out of `current_query()` and re-raises it alone would land
   in raise position. Closing *that* needs the identity to stop being derivable from the
   query text — e.g. the runner replacing each arm's message with an opaque per-run token
   that maps back to the arm only in the runner's memory, and refusing any lane output in
   which more than one distinct token appears (an echo leaks every token in the block at
   once). Recommend booking it rather than shipping a fourth spelling-shaped answer, and
   update `GRAMMAR.md` + the `run.mjs:483-486` residual note, which currently understates the
   boundary by naming only `pg_read_file`.

### R4-C04: SP-I01's fix RE-OPENED the phantom-block hazard whose justification it deleted — a multi-line template literal containing `/*` blinds the audit-coverage detector for the rest of the file

**File:** `src/__tests__/audit-coverage.test.ts:159-178` (`unmatchedBlockOpen`),
consumed at `:180-205` (`stripBlockComments`)

The pre-SP-I01 code entered a block only on a line-LEADING `/*`, and its comment said why:

> Entering on any occurrence would let a string literal such as `"src/**/*.ts"` open a
> phantom comment and blank the rest of the file — a detector silently going blind, which is
> the failure this whole file exists to prevent.

Commit `4dfda654` deleted that sentence and asserted the risk "is closed properly instead of
avoided: `unmatchedBlockOpen` tracks quote state". It tracks quote state **per line, with
the state reset at every newline** — and multi-line template literals are legal TypeScript.

Driven against the file's own real bytes (transpiled slice of `MUTATOR_CALL_RE` …
`findMutations` plus `stripLineComment`, no retyping):

```
A: multi-line TEMPLATE literal containing /*        -> sites: []            ⛔
B: control, identical but no /* in the template     -> sites: [line 5]      ✅
C: single-line string /* (the shipped SP-I01 arm)   -> sites: [line 3]      ✅
```

Input A:

```ts
export async function POST() {
  const help = `
Usage: foo /*bar
`;
  const { error } = await supabase.from('trades').insert(batch);
  return Response.json({ ok: !error });
}
```

The `/*` on line 3 is inside a template literal that opened on line 2. `unmatchedBlockOpen`
sees line 3 with `quote = null`, opens a phantom block, and every line after it is blanked —
including the real `.insert()`. **The pre-fix code found that site.** The fix made the
detector blind on an input the pre-fix code handled correctly.

Live impact today: **none.** I A/B'd both strippers over all 194 non-test files under
`src/app/api` and the mutation-site sets are identical (`route files with a site-set
difference: 0`). The defect is latent — but a *missed* site is a DB write with no audit
event that the counted `ALLOWLIST` then certifies as covered, and the three shipped SP-I01
arms all use single-line strings, so nothing can catch it.

**Fix:** carry string state across lines, the same way `inBlock` already is.

```ts
function stripBlockComments(lines: string[]): string[] {
  const out: string[] = [];
  let inBlock = false;
  let quote: string | null = null;        // ← survives the newline
  for (const raw of lines) {
    /* …existing inBlock handling… */
    const code = stripLineComment(raw);
    const scan = scanLine(code, quote);   // returns { openAt, quoteAtEnd }
    quote = scan.quoteAtEnd;              // only ` can legally survive a newline
    if (scan.openAt >= 0) { inBlock = true; out.push(code.slice(0, scan.openAt)); continue; }
    out.push(code);
  }
  return out;
}
```

Only a backtick may legally span lines, so `quoteAtEnd` should be forced to `null` for `'`
and `"` (an unterminated one is a syntax error) — that keeps the runaway bounded exactly as
the original comment argued. Add the three-arm table above as the test, with B as the
calibration control so the arm cannot pass on a stripper that returns everything.

### R4-W01: a non-ASCII unqualified identifier is MANGLED by one reader and dropped by the other — VAC-04 then compares, or passes, the WRONG function name

**File:** `scripts/sql-function-names-naive.mjs:85` (`[A-Za-z0-9_$]`),
`scripts/sql-body-normalize.mjs` (same ASCII charset)

Postgres accepts unquoted non-ASCII identifiers. Measured at HEAD on
`CREATE OR REPLACE FUNCTION public.sanitize_üser(p uuid)`:

```
  lexer : (nothing)
  naive : sanitize_
```

Driven through the gate, this produces:

```
::warning::… the independent name reader found function definition(s) the normalizer's parser did not:
::warning::  sanitize_
  sanitize_: measured absent — not in the PROD source's 1-name index. Treated as a NEW function (pass).
GATE EXIT=0
```

The gate reports a *pass for a function that does not exist* and never looks at
`sanitize_üser`. Worse, if PROD happens to hold a real `sanitize_`, the gate compares that
function's body against `supabase/schema/functions/sanitize_.sql` and reports MATCH — a
clean result for the wrong subject, which is strictly worse than the silent pass SP-C05
removed. This is the same "maintainer-authored, therefore hardening" bar the fixer accepted
for SP-I07's traversal case, with a worse failure mode.

**Fix:** truncation must be impossible. Make the naive reader refuse rather than truncate,
and make the qualified/name output carry the refusal:

```js
const DEF_RE = /^[ \t]*CREATE[ \t]+(?:OR[ \t]+REPLACE[ \t]+)?FUNCTION[ \t]+(\S+)/i;
// …then validate the captured chain against the charset and FAIL LOUD if it does not
// fully match, instead of letting the chain regex stop at the first illegal byte.
if (!/^(?:"[^"]*"|[A-Za-z0-9_$]+)(?:[ \t]*\.[ \t]*(?:"[^"]*"|[A-Za-z0-9_$]+))*$/.test(chain))
  throw new Error(`sql-function-names-naive: refusing to read '${chain}' — it leaves bytes ` +
    `outside the unquoted-identifier charset, and a TRUNCATED name is compared against the ` +
    `wrong function. Quote the identifier in the migration.`);
```

Add the same guard to `extractFunctionDefs`. Both readers currently agree by *both* being

### R4-W02: SP-I03's per-job tolerance pin is spelled as one literal string, so an equivalently-written tolerance arm widens it silently

**File:** `src/__tests__/lint-sql-gates.test.ts:341-360`

The posture arm is the right design and the population is genuinely derived from `ci.yml`
(the "table covers EVERY job this phase added" arm reads job headers and matches on script
paths — I confirmed it fails if a fourth job appears). The `tolerance: null` half, however,
is only:

```ts
const arm = new RegExp(`\\[ "\\$name" = "${job}" \\]`);
expect(ci).not.toMatch(arm);
```

That is one spelling. `[ "${name}" = "sql-mutation" ]`, `case "$name" in sql-mutation)`,
`[[ $name == sql-mutation ]]`, or an `if:` on the job itself all install a tolerance the pin
cannot see. The existing three arms in `ci.yml` all use the pinned spelling, so this is a
future-drift hole rather than a live one — but "cannot silently widen" is the property the
fixer claimed, and it is not what is asserted.

**Fix:** assert over the *structure* of the loop instead of over one string. The aggregator's
result loop is a flat `if/elif` chain; extract it and range over its branch conditions:

```ts
const loop = ci.slice(ci.indexOf('name="${r%=*}"'), ci.indexOf('if [ "$fail" = "1" ]'));
const named = new Set([...loop.matchAll(/"\$\{?name\}?"?\s*(?:=|==)\s*"?([a-z0-9-]+)"?/g)].map(m => m[1]));
for (const { job, tolerance } of AGGREGATED_JOBS) {
  expect(named.has(job), `${job} has a per-job arm in the aggregator loop`).toBe(tolerance !== null);
}
expect(named.size, "no per-job arms parsed — this arm would be checking an empty set").toBeGreaterThan(2);
```

That covers every `$name` comparison spelling in the loop and carries its own non-vacuity
floor.
