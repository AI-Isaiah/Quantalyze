## The defect the runner found — in the runner, on its first real run

29 of 30 arms bit correctly on the very first full-corpus execution. `N1 3a` reported `wrong-first-failure: NO-DELETE 1`.

The cause was not the annotation. `neuterArm` replaced only the `RAISE`, leaving the failure branch's `RESET ROLE;` executing:

```sql
IF NOT raised OR err_msg NOT LIKE '%AT MOST ONE%' THEN
  RESET ROLE;                                    -- ← still ran
  RAISE EXCEPTION 'TEST FAILED (N1 1a): …';      -- ← neutered
END IF;
```

That branch *does* execute under the mutation — which is precisely why the arm needs neutering. The session fell from `authenticated` to the superuser session role for the rest of the file, and sixteen arms later `NO-DELETE 1`'s `DELETE FROM strategy_shares` succeeded because a superuser needs no grant.

**It was loud only by luck.** A leaked superuser makes every downstream GRANT arm pass for a reason unrelated to the grant — a silent vacuous PASS *inside the vacuity detector*, and Phase 164.4 would have inherited it across seventy more files. Fixed in `neuterArm` (absorbs an exact preceding `RESET ROLE;`, nothing else), documented in `GRAMMAR.md`, and pinned by `src/__tests__/mutation-runner-neuter.test.ts`.

## The CI job

`sql-mutation` hosts its own throwaway clusters and **never touches the shared TEST database** (D-07) — the run deliberately breaks arms, and TEST sits behind a mutex shared with everyone else's CI. It consumes no secret, no repo variable, has no `if:` and no mutex, so it runs identically on a fork PR and a `skipped` there is always a real fault: it takes the aggregator's **strict** arm with no tolerance, wired into **both** `needs:` and the result loop.

Two details worth their comments:

- **Mode identity by file redirect, not `| tee`.** The step's argv is byte-identical to the script header's (diffed mechanically). Its stdout goes to a file in `RUNNER_TEMP` and is `cat` back. A pipe would make `$?` the last command's status — the hazard that bit this plan's own `--self-test` measurement mid-execution — and a log written into the workspace would trip the runner's own `dirty-checkout` guard.
- **The preflight scans a superset** (all tests + all lane fixtures + all migrations, 335 files, 0 hits) rather than a list derived from `RED-UNDER-SETUP`, because a derived list is a second place for the corpus to drift. It uses `grep -a`: this repo has a measured NUL-blind file where a bare grep's exit 1 reads as "clean".

### Deliberate divergences from the plan text

- **`permissions:` / `concurrency:` are NOT restated per-job.** The plan's PATTERNS §3 asked for them. Its sibling `sql-gate-lint` — landed by plan 06 into this same file — carries an explicit comment saying they are inherited from the workflow level and that restating them forks two sources of truth. Matching the neighbouring convention (CLAUDE.md rule 11) beat matching the plan text. Both are present at workflow level.
- **No `npm ci`, no node_modules cache, no retry loop.** PATTERNS §3 Analog B prescribes them. `run.mjs` and `parse.mjs` import only node builtins, and an install the job does not need is an install that can fail and flake the gate — the same reasoning `sql-gate-lint` records.
- **`--parse-only` exits 0**, per the plan's verify, despite plan 05's "diagnostic modes exit 2" convention. It is a whole-corpus check, not a subset. The risk it creates — someone wiring it in as the gate — is closed by a *mechanism* rather than its banner: the CI job asserts an executed-arm count at or above `ARMS_FLOOR`, which this mode can never satisfy. Proven against that exact fixture.
