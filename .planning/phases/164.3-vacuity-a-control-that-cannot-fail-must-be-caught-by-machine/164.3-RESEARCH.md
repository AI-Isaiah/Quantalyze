# Phase 164.3: VACUITY — a control that cannot fail must be caught by machine - Research

**Researched:** 2026-08-28
**Domain:** CI/tooling — SQL mutation testing, disposable PostgreSQL, static gate linting, drift detection
**Confidence:** HIGH (repo facts measured this session; external facts cited; the few assumptions are logged)

## Summary

This phase builds machinery, not features: a mutation runner over annotated SQL gate arms, a
disposable-PostgreSQL lane, a five-shape static linter, a repo-vs-PROD body diff, plan-anchor
verification, and one e2e spec that closes Phase 159's two blocked items. Almost everything it
needs already exists in embryo in this repo and requires **zero new npm packages**: the 56-line
`pg-harness/run.sh` is the lane's seed, the ubuntu-24.04 runner ships PostgreSQL 16.15
preinstalled, `supabase/config.toml` + the locally-installed Supabase CLI 2.84.2 provide the app
consumer's stack, and the `frontend` aggregator + sentinel-floor patterns in `ci.yml` are the
wiring templates.

Two findings change how the planner must shape the work. **First (the single most important):
the 33 `RED-UNDER` annotations are prose written for humans, not machine-executable
instructions.** They name mutations in *three different shapes* — migration-file edits,
live-database SQL statements, and LAYERED compound mutations that require *neutering other arms
first* — and two arms carry recorded waivers. A runner that greps `RED-UNDER:` and tries to
"apply" the text cannot exist. The runner needs a structured, machine-readable companion
annotation added beside each prose annotation (in-file, so the claim and the executable mutation
can never drift apart), plus a parity gate that fails when a `RED-UNDER` lacks its structured
twin. **Second: the app under VAC-07 speaks PostgREST + GoTrue via `@supabase/supabase-js` — a
bare `initdb` cluster structurally cannot serve it.** The phase therefore has two throwaway-PG
shapes: the initdb lane (mutation runner, VAC-01/02/06) and the Supabase CLI local stack
(`supabase start`, Docker — VAC-07's consumer). Both are disposable, neither touches TEST, and
this is exactly the "different shape" risk D-08 predicted and folded the spec in to discover now.

**Primary recommendation:** Node scripts orchestrating a fixed bash lane script; mutations
applied to *copies* of migration files in scratch (never the checkout); first-failure asserted by
matching the uniform `TEST FAILED (<ARM ID>)` message; VAC-07 on the Supabase local stack via a
Playwright spec using `Promise.all` over `page.request.post`; VAC-04 as its own PR-triggered
check (NOT inside the `frontend` aggregator — see the Railway deploy-freeze pitfall).

### Q2 — One script on macOS and ubuntu (the lane, VAC-02)

`run.sh` read in full this session (56 lines). Verbatim, the two portability defects and proof of the missing cleanup:

```bash
PGBIN=${PGBIN:-/opt/homebrew/opt/postgresql@16/bin}   # line 24 — macOS-only
PORT=${PORT:-55432}                                   # line 28 — fixed port
```
and the file ends at line 56 with the last `psqlq -f` — **no `pg_ctl stop`, no `trap`, no `rm` anywhere** [VERIFIED: pg-harness/run.sh:1-56]. The collision guard (:36-42, refuses when `pg_isready` finds a listener) is correct and must survive (D-03). Also note `sleep 2` after `pg_ctl … start` (:47-48) is a race — replace with `pg_ctl -w` (waits for startup) plus a bounded `pg_isready` loop.

**PGBIN resolution chain (recommended):**
```bash
resolve_pgbin() {
  if command -v pg_ctl >/dev/null 2>&1; then dirname "$(command -v pg_ctl)"; return; fi
  if command -v pg_config >/dev/null 2>&1; then pg_config --bindir; return; fi
  for d in /usr/lib/postgresql/*/bin /opt/homebrew/opt/postgresql@*/bin; do
    [ -x "$d/pg_ctl" ] && { echo "$d"; return; }
  done
  echo "ERROR: no PostgreSQL server binaries found (need initdb/pg_ctl)" >&2; return 1
}
PGBIN=${PGBIN:-$(resolve_pgbin)} || exit 1
```
Measured locally this session: `pg_ctl`/`pg_config` are NOT on PATH but `/opt/homebrew/opt/postgresql@16` exists — the glob arm is what fires on this machine; on the runner the `/usr/lib/postgresql/*/bin` glob (or PATH) fires. [VERIFIED: `command -v` probes this session]

**Free port per run:** bind port 0 and let the OS choose, via node (guaranteed on both hosts):
```bash
PORT=${PORT:-$(node -e 's=require("net").createServer();s.listen(0,"127.0.0.1",()=>{console.log(s.address().port);s.close()})')}
```
Keep the existing `pg_isready` refuse-guard afterward — the bind-0 handoff has a small TOCTOU window and the guard is the measured protection against destroying a neighbour's cluster.

**Cleanup trap that survives `set -euo pipefail`:** register the EXIT trap BEFORE `initdb`, make INT/TERM route through EXIT, and only ever remove what this run created (the guard means we never attach to a foreign cluster):
```bash
CREATED=""
cleanup() {
  status=$?
  if [ -n "$CREATED" ] && [ -d "$PGD/data" ]; then
    "$PGBIN/pg_ctl" -D "$PGD/data" stop -m immediate -w >/dev/null 2>&1 || true
    rm -rf "$PGD"
  fi
  exit "$status"
}
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
# ... then:
mkdir -p "$PGD"; CREATED=1
initdb ...
```
Bash runs the EXIT trap on `set -e` failures and on exits initiated by trapped signals; it does not run on SIGKILL (nothing can). `pg_ctl stop -m immediate` is correct for a throwaway cluster (no durability requirement). [ASSUMED — standard bash/PostgreSQL semantics; the runner's self-test should include a kill-and-verify-no-orphan check, which also discharges D-04's "including on failure and on interrupt" verbatim.]

**Fixture-boundary note to preserve (run.sh header, :14-21, verbatim):** "01-fixture-core.sql and 02-fixture-sanitize-tables.sql are STAND-INS … It does NOT prove behaviour against the real schema's own RLS, constraints or triggers." The promoted script must keep saying this.

### Q3 — The mutation runner's mechanics (THE headline finding)

`supabase/tests/test_strategy_shares_rls.sql` (2564 lines) carries exactly **33** `-- RED-UNDER:` annotations; **1 file of 71** in `supabase/tests/` is annotated [VERIFIED: `grep -c` + file count this session — 33, 71]. The declared grammar, from the file header (:46-54, verbatim):

> `-- ⭐ PER-ARM RED-UNDER (standing requirement, founder-adopted 2026-08-27).`
> `-- Every arm added by the nonce change carries an adjacent`
> `` -- `-- RED-UNDER: <the exact mutation that reddens THIS arm>` comment, and each ``
> `-- of those mutations was performed individually on the throwaway cluster with`
> `-- that arm observed as the FIRST failure — not merely the batch observed red,`
> `-- which is how six structurally-unfailable arms entered this file across two`
> `-- earlier fix rounds. Where an arm could NOT be made the first failure, that is`
> `-- recorded at the arm instead of papered over (see SHAPE 1's note on a deleted`
> `` -- `nonce`, and NONCE 5c).``

**Verdict: the annotations are prose, NOT machine-parseable as-is.** They fall into three distinct mutation shapes, plus recorded waivers:

1. **Migration-file edits** — sometimes exact before→after, sometimes located only by prose:
   - `-- RED-UNDER: change `generation BIGINT` back to `generation INTEGER` in the` / `--            STEP 1 CREATE TABLE.` (:408-409) — mechanically applicable as a string replace, but "STEP 1 CREATE TABLE" is a prose locator.
   - `-- RED-UNDER: add a `token_hash TEXT` column to the STEP 1 CREATE TABLE in` / `--            migration 20260827120000.` (:369-370) — an *insertion* with no exact insertion point.
   [VERIFIED: test_strategy_shares_rls.sql:369-370, 408-409, read this session]
2. **Live-database SQL statements** (not file edits at all):
   - `-- RED-UNDER: `GRANT UPDATE (nonce) ON strategy_shares TO authenticated` on` / `--            the live database. ⚠️ SHAPE 3b's exact-set pin fires first on` / `--            ANY grant drift, so this arm was observed red with SHAPE 3b` / `--            neutered — at which point NONCE 1b is the first failure…` (:1533-1537) [VERIFIED, read this session]
   — note the **prerequisite neuter of a different arm** embedded in prose.
3. **LAYERED compound mutations** spanning migration + gate file:
   - `-- RED-UNDER: change the CREATE TRIGGER in migration 20260827120000 STEP 1b to` / `--            `BEFORE UPDATE ON strategy_shares`.` / `-- ⚠️ LAYERED: migration arm (v) tests the same bit and ABORTS THE APPLY, so` / `--    its `AND (t.tgtype & 4) = 4` term must be removed in the same mutation` / `--    or this file never runs.` (:661-665) [VERIFIED, read this session]
4. **Recorded waivers** — arms where no first-failure mutation exists (SHAPE 1's deleted-`nonce` note, NONCE 5c per the header). The runner's grammar needs an explicit, counted waiver form so these are visible, not silently skipped.

**Design consequence (this changes the runner completely, as suspected):** the runner cannot execute the prose. It needs a structured, machine-executable companion annotation. **Recommend in-file** (a sidecar manifest would recreate exactly the drift-by-distance this phase exists to kill — the claim and the executable mutation must sit on adjacent lines):

```
-- RED-UNDER: <existing prose, unchanged — the human claim>
-- RED-UNDER-M: {"arm":"SHAPE 1c","apply":[{"kind":"edit","file":"supabase/migrations/20260827120000_strategy_shares_generation_model.sql","find":"generation BIGINT","replace":"generation INTEGER","nth":1}]}
-- RED-UNDER-M: {"arm":"NONCE 1b","apply":[{"kind":"sql","stmt":"GRANT UPDATE (nonce) ON strategy_shares TO authenticated"}],"neuter":[{"arm":"SHAPE 3b"}]}
-- RED-UNDER-M: {"arm":"SHAPE 1","waiver":"<reason recorded in prose above>"}
```
(Exact key names are planner discretion; the required *capabilities* are: `edit` with byte-exact find/replace/insert-after, `sql` executed post-migration pre-gate, `neuter` naming another arm, `waiver`, and multi-step `apply` for LAYERED.)

Machine assertions the runner makes per arm:
- **Parity gate:** per file, `count(RED-UNDER) == count(RED-UNDER-M)`; a prose annotation without a structured twin is exit 1 (this is what keeps 164.4's backfill honest).
- **First-failure identity:** every arm's failure message uses the uniform format `TEST FAILED (<ARM ID>):` [VERIFIED: e.g. `'TEST FAILED (SHAPE 1c): …'` :414, `'TEST FAILED (NONCE 1b): …'` :1561]. The runner asserts the run went RED **and** the first `TEST FAILED (` occurrence names the annotated arm. Red-anywhere is not enough — first-failure identity is precisely the discipline that caught the six structurally-unfailable arms, and it is what detects mechanism 5.
- **Restore → GREEN:** rerun unmutated, expect exit 0.

**Never mutate the checkout.** Copy the migration + gate files into the scratch dir, mutate the copies, point the lane at the copies. This eliminates the stale-byte-backup class (`reference_byte_backups_go_stale_mid_edit`) and the shared-git-index race (`feedback_concurrent_agents_share_git_index_race`) by construction.

**Iteration cost:** 33 arms × (fresh schema + apply + gate). Recommend `initdb` once per run, then per-arm `createdb` from a pristine template database (fixtures + unmutated migrations applied once to the template; per-arm DBs get fixtures+mutated files applied fresh — or simply re-`psql` the four files per arm into a fresh DB; each apply is seconds). Budget minutes, not hours; measure in the first plan and record.

**Neuter semantics:** a `neuter` entry comments out the named arm's `RAISE EXCEPTION` (or its whole `IF` block) in the *copy* of the gate file. The neutered arm's ID must then NOT appear in output — assert that too, or the neuter itself can silently miss.

### Q5 — Reading PROD function bodies from CI (VAC-04)

**Privilege:** `pg_get_functiondef(oid)` and the `pg_proc` catalog are readable by every role by default — restricting them requires an explicit `REVOKE … ON pg_catalog.pg_proc FROM PUBLIC`, which is a documented *hardening customization*, not the default [CITED: postgresql.org docs 16 §catalog-pg-proc; postgresql.org mailing list "How to hide stored procedure's bodies"]. A login role with **zero table grants** therefore reads function definitions, needing only LOGIN and the default PUBLIC `CONNECT`. This confirms D-11's premise. Supabase does not revoke catalog access from custom roles by default [ASSUMED — verify once the founder's role exists; the job's first probe should be `SELECT pg_get_functiondef('public.sanitize_user'::regproc)` style and fail loud on empty].

**Comment stripping:** the in-repo idiom (`regexp_replace(body, '--[^\n]*', '', 'g')`) is the precedent and matches D-05's measured case (PROD's 7-param `_enqueue_compute_job_internal`: 0 `INTO STRICT` in code, 1 including comments). Two known limitations to document in the script: it also strips `--` inside string literals (rare in these bodies; acceptable, and symmetric when applied to BOTH sides), and it ignores `/* */` block comments — add a second pass `regexp_replace(…, '/\*.*?\*/', '', 'gs')` (apply to both sides identically). Normalize whitespace after stripping before diffing.

**Job design:**
- **Own workflow** (like `migration-drift-check.yml`), triggered on `pull_request` paths `supabase/migrations/**` — plus a plain scheduled or push-PR-wide variant is NOT recommended (see pitfall below). The DSN presence check is **unconditional and first**: `[ -z "$PROD_BODY_READER_DSN" ] && { echo "::error::PROD_BODY_READER_DSN is not configured — the repo-vs-PROD body gate CANNOT run (D-11: this is a hard failure, not a skip)"; exit 1; }` — before any work detection, so the job can never rationalize an exit 0 out of "nothing to do" while the credential is missing.
- **What to diff:** for each `CREATE OR REPLACE FUNCTION public.<f>` in the PR's changed migration files, fetch PROD's current `pg_get_functiondef` for that signature; strip comments + normalize both sides; diff against the migration's new body. A non-empty diff is *expected* (the migration IS a change) — the gate's target is DRIFT-02's shape: **a delta the migration does not claim**. Mechanizable claim protocol (planner discretion on details): the job prints the normalized diff's SHA-256 and fails unless the migration carries a matching `-- prod-diff-claim: <sha256>` pragma; the author obtains the hash from the failed job's log and pins it, which forces a human to have LOOKED at the diff. A function absent from PROD (new function) passes with a note.
- ⚠️ **Public-log redaction:** PROD bodies can contain surgical patches that exist nowhere in this public repo (that is DRIFT-02's whole point). The job must NEVER print raw PROD body text — print hunk counts, line numbers, and hashes only. The mutex step's redaction discipline (ci.yml:1237-1245) is the standing precedent.
- **Fork PRs:** secrets are withheld on forks, so the job would fail loud on every fork PR. Same-repo gating via the `sql-tests` `if:` precedent (`github.event_name == 'push'` OR same-repo PR, ci.yml:794-798) is the legitimate carve-out — a fork PR cannot merge a migration without a maintainer branch anyway.

## Common Pitfalls

### Pitfall 1: VAC-04 red-until-role-exists freezes Railway deploys if wired into main-push CI
**What goes wrong:** Railway waits on main CI and SKIPS the analytics-service deploy when it is red (`project_railway_analytics_deploy_wait_for_ci`). D-11 accepts a red *board*; it did not price a *deploy freeze*.
**How to avoid:** trigger VAC-04 on `pull_request` (paths `supabase/migrations/**`, same-repo) — the gate exists pre-merge where DRIFT-02b needs it; main-push CI stays green; the PR board is honestly red until the founder acts. Do NOT add it to the `frontend` aggregator until the credential exists. Surface this reasoning in the plan so nobody "fixes" it into a push-triggered job later without seeing the cost.

### Pitfall 2: A runner invocation that differs between local and CI is not the same runner
**What goes wrong:** wrapping a run changes its result (measured: 5/5 wrapped RED vs 3/3 direct GREEN — `reference_gstack_evidence_wrapper_reddens_suite`).
**How to avoid:** CI steps execute the exact commands the docs tell a developer to run — same entrypoint, same args, no wrapper. Write the invocation once in the script's header and paste it into ci.yml verbatim.

### Pitfall 3: Prose annotations silently drifting from executable mutations
**What goes wrong:** a sidecar manifest (or a runner that "interprets" prose) recreates the claim-vs-thing gap.
**How to avoid:** structured `RED-UNDER-M` lines adjacent to the prose, plus the per-file parity gate (`count(RED-UNDER) == count(RED-UNDER-M)`), plus waivers that are counted and printed. The runner prints coverage as `files_annotated / files_total` AND `arms_executed / arms_annotated / arms_waived`.

### Pitfall 4: The mutation reddening the WRONG arm reads as success
**What goes wrong:** "file went RED" passes even when an earlier arm (e.g. SHAPE 3b's exact-set pin) fired instead of the annotated one — the exact masking the annotations document (:1533-1537).
**How to avoid:** assert first-failure identity against `TEST FAILED (<ARM ID>)`, and execute declared `neuter` prerequisites first. Assert the neutered arm's ID does NOT appear.

### Pitfall 5: Orphaned clusters exhaust the disk
**What goes wrong:** measured 2026-08-28 — 27 orphaned volumes, 904 MB, a container up 10 days, 8.2 GB free (D-04); separately, 29 worktrees once drove the box to 230 MiB free (`reference_agent_worktrees_exhaust_disk`).
**How to avoid:** the EXIT/INT/TERM trap (Q2) registered before `initdb`; a runner self-test that kills mid-run and asserts no listener and no data dir remain; `supabase stop --no-backup` equivalently trapped in the VAC-07 lane.

### Pitfall 6: Node 22 vs 25 skew
**What goes wrong:** scripts pass locally on Node 25 and fail in CI on Node 22 (measured class: `reference_ci_node22_vs_local_node25`).
**How to avoid:** no Node-25-only APIs in the new scripts; local pre-push check via `PATH=/opt/homebrew/opt/node@22/bin:$PATH` when in doubt.

### Pitfall 7: Shell grep over repo files
**What goes wrong:** grep is silently blind past a NUL byte (measured: `src/lib/wizardErrors.test.ts`); exit 1 reads as "clean".
**How to avoid:** the linter and anchor verifier read files with node `fs`. Where shell is unavoidable, `grep -a` (ci.yml's own sentinel gate does this, :1579).

### Pitfall 8: PROD internals in a public Actions log
**What goes wrong:** printing `pg_get_functiondef` output or the raw diff publishes PROD-only surgical patches to a public repo's logs.
**How to avoid:** hashes, hunk counts, and line numbers only; never body text; never the DSN (redaction precedent ci.yml:1237-1245).

### Pitfall 9: The 263-migration replay wedging `supabase db reset`
**What goes wrong:** VAC-07's stack assumes the chain replays from `20260405061911_initial_schema.sql`; one non-idempotent or environment-coupled migration breaks the lane late.
**How to avoid:** make "prove the replay" the FIRST task of the VAC-07 plan (a spike with a recorded pass/fail); if it fails, the fallback is a schema snapshot (`supabase db dump` from TEST is read-only and allowed) loaded as the local stack's baseline — decide only on measurement.

## Open Questions

1. **Does the migration chain replay from scratch?** (A4) What we know: chain starts at `20260405061911_initial_schema.sql`, 263 files, TEST demonstrably received recent ones. What's unclear: whether every historical migration is environment-clean. Recommendation: first task of the VAC-07 plan is the replay spike; fallback is a read-only `supabase db dump` baseline.
2. **Exact `RED-UNDER-M` schema.** The capabilities are fixed by the corpus (edit / sql / neuter / waiver / multi-step / expect-first-failure); the key names and whether waivers get their own tag are planner calls. Constraint: 164.4 inherits this grammar for 70 more files — bias toward the simplest thing that expresses the 33 existing annotations.
3. **OPS-08-F8's full discharge.** The runner aggregates by design; converting the `sql-tests` first-failure loop is a separate, riskier edit to a live gate. Recommendation: runner design + explicit TODOS note if the loop conversion is deferred — do not silently claim the class closed.
4. **Where VAC-04's claim pragma lives** (`-- prod-diff-claim: <sha256>` in the migration vs a sibling file). In-migration keeps claim-beside-thing; but migrations are immutable post-apply — for a PR that iterates, the pragma churns the migration file. Planner decides; either satisfies DRIFT-02b.
