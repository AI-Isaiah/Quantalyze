<objective>
Criterion 7 (BASELINE-CONTENT-DRIFT): pin the committed baseline to the MIGRATION CHAIN, not
merely to its own changelog. Plan 02's co-edit gate fires on a byte change to `baseline.sql`; it
structurally CANNOT fire when a migration changes a function body and `baseline.sql` is left
untouched — which is exactly what Phase 164.7 just did.

Per D-04 this lands BEFORE any migration squash: collapsing 263 migrations onto an unpinned,
already-drifted baseline freezes the drift into the new floor permanently.

Purpose and route: `scripts/sql-body-normalize.mjs` ALREADY implements this comparison
(`--diff-bodies`). ⛔ Do not write a second normalizer. This plan writes a thin runner over
`diffFunctionBodies()` plus a dated allowlist, shaped like `scripts/lint-app-guc.mjs`.

⛔ **A full pg-lane replay is IMPOSSIBLE, not merely slow** — 69 of 262 migrations fail from
empty, with at least six independent root causes and one refusing BY DESIGN, and
`scripts/pg-lane/run.sh` takes curated `--apply` lists. The "applied migration chain" this gate
compares against is therefore the hermetic text-replay rendering in `supabase/schema/functions/*.sql`,
whose own currency is enforced by `dump-sql-functions.ts --check`. The gate must SAY this.

⛔ **THIS GATE IS RED AT HEAD.** Re-measured in-session at the planning tree, 0.12 s:
**114 MATCH, 6 DRIFT, 2 SNAPSHOT_MISSING**.

**P-03 — go-green route, decided here so no executor picks it: PRECEDENT B (a dated,
name-and-hash-pinned RATCHET), not Precedent A (a declared red interval).** Reasoning:

1. The alternative go-green is regenerating `baseline.sql` from PROD. That needs the PROD
   credential AND a secret re-scan AND it moves plan 02's recorded sha — three coupled acts on a
   credential-bearing surface. It is a separate REVIEWED act, not a step inside a hermetic plan.
2. Precedent A leaves the gate red for an interval. This phase exists because an artifact was
   "committed with NO staleness gate AND NO consumer"; shipping a gate that cannot block for an
   interval reproduces the same class in a smaller form.
3. Precedent B is strictly stronger here: it fails on ANY NEW drift immediately, AND it hard-fails
   when an allowlisted row stops being true ("the baseline may only shrink"), so the 8 rows can
   only leave.

⚠️ The allowlist rows pin the `snapshotHash`/`candidateHash` PAIR, not just the name — so a
DIFFERENT drift on an already-allowlisted function still fails. An entry keyed on the name alone
would be a mute button, and this repo names that as the defect.
</objective>
