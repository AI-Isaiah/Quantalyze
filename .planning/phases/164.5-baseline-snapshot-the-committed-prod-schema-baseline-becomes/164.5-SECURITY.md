## ⛔ The one blocking threat, and how it closed

| Threat ID | Category | Component | Severity | Status |
|---|---|---|---|---|
| T-164.5-01 | Information Disclosure | `.gitignore` — production dump path | registered `medium`, **re-graded `high`** | **CLOSED 2026-09-08** |

**What was actually wrong.** This was not "the branch is stale". The PR branch at `ac68bed2`
**deleted a control `main` already had**: `.gitignore`'s exclusion of
`scripts/local-stack/baseline.sql`, replaced by a comment asserting "the ignored path had no
consumer left". That assertion was **false on the same branch** —
`scripts/local-stack/REPLAY-SPIKE.md:156` still carried a runnable
`supabase db dump --db-url "$TEST_DB_URL" -f scripts/local-stack/baseline.sql`, and `:162`
is that document's own secret scan asserting the file can carry a DSN, host, project ref,
`\connect`, `ALTER DATABASE` or a JWT. A live-database dump path, un-ignored, with a runnable
command aimed at it, on a PUBLIC repo.

**The severity re-grade is stated, not slipped in.** The register graded this `medium` at plan
time for "deleting the rule normalises committing dumps". What was on the branch is stronger:
an existing public-repo information-disclosure control being *removed* while its documented
misuse path stayed runnable. The auditor graded the observed condition `high`, which is what
put it at the `block_on` threshold. ⚠️ At the plan-time `medium` the arithmetic would have read
`threats_open: 0` and this would have shipped. That is recorded because the near-miss is the
finding.

**How it closed — measured on the pushed branch `3bb3e699`, not asserted:**

|---|---|---|

| rule LINE deleted in the diff | none | **none** — every `-` line was comment text |
| `supabase/schema/baseline.sql` still tracked & NOT ignored | yes | **yes** |
| DROP migration absent from PR | 0 | **0** |
| pre-flight script absent from PR | 0 | **0** |
| deletion guard `main..PR -- .planning/` | empty | **empty** |
| `.planning/phases/` files added by the branch | 0 | **0** |

⚠️ **One auditor expectation was WRONG and is corrected here rather than satisfied.** It

branch and the PR branch, with the two files md5-identical. The constant was not inflated to

## Independent secret scan of the regenerated baseline

`supabase/schema/baseline.sql` was regenerated from PROD in `5c8d0fef` (449 changed lines) and
is committed to a PUBLIC repo. The auditor scanned the committed bytes itself rather than
trusting `BASELINE.md`:

- REPLAY-SPIKE pattern (`postgres://`, `@*.supabase.co`, `<ref>.supabase`, `\connect`,
  `ALTER DATABASE`, `eyJ…`) → **no matches**
- `^(INSERT|COPY|UPDATE|DELETE)` → **0** — schema-only, no data statements
- `CREATE ROLE` / `PASSWORD '` / `ENCRYPTED PASSWORD` / `vault.create_secret(` / `pgsodium` → **none**
- base64-ish runs ≥ 40 chars → **none**
- `gitleaks 8.30.1 detect --no-git` over the file → **no leaks found** (726 KB scanned)
- every `secret` / `password` / `api_key` hit is an identifier or a `COMMENT ON` body with no value

The dump path was **never** committed historically: `git log --all -- scripts/local-stack/baseline.sql`
is empty. So WR-05 was a live hazard, not a leak.
