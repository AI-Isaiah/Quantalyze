## The `up` log line is not the proof — here is the proof

`[local-stack] baseline loaded from …/supabase/schema/baseline.sql` is a claim the script
makes about itself. An independent oracle was run against the **live** lane database
before teardown (DSN read from the gitignored handoff, asserted local, never echoed):

```
--- ORACLE 1: DRIFT-04 function, defined by NO migration (baseline-only) ---
               proname               |                       args
-------------------------------------+---------------------------------------------------
 create_allocator_connected_strategy | p_user_id uuid, p_portfolio_id uuid, p_exchange text,
                                     | p_label text, p_strategy_name text,
                                     | p_api_key_encrypted text, p_api_secret_encrypted text,
                                     | p_passphrase_encrypted text, p_dek_encrypted text,
                                     | p_nonce text, p_kek_version integer
(1 row)

--- ORACLE 2: shape vs BASELINE.md provenance ---
 public_tables | public_policies | public_functions
---------------+-----------------+------------------
            61 |             152 |              121
(1 row)

--- ORACLE 3: the lane applied NO migration ledger rows ---
ERROR:  relation "supabase_migrations.schema_migrations" does not exist
```

Why each bites:

- **Oracle 1.** `create_allocator_connected_strategy` is DRIFT-04: `grep -rl` over
  `supabase/migrations/` returns **nothing**, and it appears **10** times in
  `supabase/schema/baseline.sql`. The lane starts with `[db.migrations]` disabled and no
  migrations directory, so no other step in the boot path can create it. Its presence — with
  the exact 11-arg signature CONTEXT recorded — can only come from the committed dump.
- **Oracle 2.** 61 / 152 / 121 matches `BASELINE.md`'s provenance row
  ("61 tables, 152 policies, 121 function statements") exactly.
- **Oracle 3.** The error IS the finding: no ledger table exists, so nothing replayed
  migrations. Reported honestly — the query failed under `ON_ERROR_STOP=1` (psql exit 3);
  the two oracles above had already returned.
