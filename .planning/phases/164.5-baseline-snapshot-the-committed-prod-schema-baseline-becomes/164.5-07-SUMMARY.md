## How the race is actually opened (and why a single client could not)

- **Two clients, two tokens.** `createClient()` twice, `signInWithPassword()` twice for the SAME
  user with distinct `storageKey`s and `persistSession: false`. `grep -c createClient` = 9,
  `grep -c signInWithPassword` = 4, `grep -c storageKey` = 2. A dedicated arm asserts
  `tokenA !== tokenB`, so the H-0033 / H-0036 precondition is itself a test rather than a
  comment.
- **Each request is bound to its own client** through a `node:async_hooks` `AsyncLocalStorage`.
  The route's `createClient()` (the SSR cookie-session factory, which has no cookies in a
  vitest process) is replaced by `laneCtx.getStore()`, and the two POSTs are fired as
  `Promise.all([laneCtx.run(clientA, …), laneCtx.run(clientB, …)])`. A module-level "current
  client" variable would have been racy by construction and would have re-created the very
  defect the spec exists to avoid; the mock THROWS a named error if a handler ever reaches it
  outside a context.
- **Different `category_id`s, identical everything else.** Identical categories could both
  answer 200 on the agreeing already-classified arm, which would make "exactly one 2xx"
  depend on timing. Differing ones make every ordering produce exactly one 2xx and one refusal.
  `asset_class` is held identical so `category_id` is the sole discriminator.
- **The loser is asserted by NAME.** `grep -c 'not.toBe(200)'` = **0**. The spec asserts the
  code is one of two named ones, then the exact status and sentence for that arm, and that
  `debug_context.strategy_id` equals the WINNER's id — which is also what separates the two
  raced arms from the `failClosed` read-failure arm, whose `debug_context` is empty.
- **Own-seeded invariants only.** Every count is scoped to this run's `user_id` +
  `wizard_session_id`; there is no global empty-state assertion anywhere.

### THE CARVE-OUT PARAGRAPH (the `needs:`-edge ban), written in both places

`ci.yml`'s DB-touching jobs carry an explicit ban on new `needs:` edges. That ban is stated at
its `sql-gate-lint` instance, which this plan re-resolved at execute time to **`ci.yml:2078-2083`**
(the PLAN cited `1939-1944`, correct when written; plan 06 and this plan's own ~165-line
insertion moved it — the PROSE is the durable anchor, the numbers a dated reading).

The carve-out reasoning now sits in TWO places — the job's own header and the aggregator's
header — and reaches the same verdict: **STRICT DEFAULT ARM, NO TOLERANCE.** Verified against
the shipped YAML rather than asserted:

```
frontend-local-stack keys: ['runs-on', 'steps', 'timeout-minutes']
has if:    False
has needs: False
in aggregator needs:      True
in aggregator result loop: True
has tolerance arm:        False
```

The reasoning, in short: the job references **no secret and no repository variable**, carries
**no `if:`** and **no `needs:`**, touches **no shared resource** (its Supabase stack is Docker
containers private to its own runner, and `run.sh` REFUSES any non-local DSN, so it can reach
neither shared TEST nor PROD), and **waits on no mutex**. It therefore runs identically on a
fork PR, a same-repo PR, a push and a `workflow_dispatch`; it has no legitimate skip; a
`skipped` result is ALWAYS a real fault. That is the `frontend-seam-redis` / `sql-gate-lint` /
`sql-mutation` shape and the OPPOSITE of `sql-tests` / `e2e-seeded`, whose tolerances exist only
because those jobs consume a repo variable a fork cannot see. The `needs:`-edge ban does not
reach it for the same reason it does not reach `sql-mutation`: that ban is about mutex-sharing
jobs whose `if:` conditions diverge, and this job shares nothing.

⭐ **This row is more than "one more gate", and the aggregator header says so.** The spec is
excluded from the sharded run on purpose, so this row is the ONLY place it executes. An
advisory row would leave the race asserted nowhere while reading as covered.

### `timeout-minutes: 20`, derived beside the value

MEASURED here: `run.sh up` 26–31 s, the spec 1–2 s, `down` 2–3 s ≈ **36 s of lane work** — with
all 13 images already cached. The UNMEASURED term is a **cold `supabase start` on a fresh
ubuntu runner**, which must pull those images, plus `npm ci` on a cache miss. 20 is therefore
**headroom over an unmeasured pull, not a measured total**, and the comment says exactly that
and instructs the next reader to replace it from the first green ubuntu wall clock rather than
widen it again.

## Limitations — stated, not implied

1. ⛔ **`frontend-local-stack` HAS NEVER RUN ON UBUNTU.** Everything above is a dated
   developer-box measurement on macOS/darwin-arm64 with all 13 images cached. Whether the job
   boots at all on a runner is UNMEASURED, and an unmeasured thing is not a passing thing.
2. ⚠️ **CLI version skew.** The boot used Supabase CLI **2.84.2**; the CI job pins **2.98.2**,
   matching every other workflow in this repo so there is ONE answer to "which CLI". Whether
   2.98.2 starts this stack and loads this dump is unmeasured. If the job's first run dies
   inside `supabase start`, that is the live hypothesis, and the job's own comment says so.
3. ⚠️ **`timeout-minutes: 20` is headroom, not a measurement** (derivation above). It should be
   replaced from the first green ubuntu wall clock.
4. ⚠️ **The race is probabilistic by nature.** Two `Promise.all`'d POSTs are concurrent but not
   barrier-synchronised. What makes the spec discriminating anyway is that BOTH orderings still
   yield exactly one 2xx *only when the fence exists* — which the mutation proved by producing
   two when it does not. The differing `category_id`s remove the one ordering (an agreeing
   already-classified echo) that could have produced a second 200 legitimately.
5. ⚠️ **`withAuth` is stubbed to a passthrough** in the spec, so the CSRF origin check and the
   approval gate are not exercised. The identity that the race depends on — `auth.uid()` inside
   the SECURITY DEFINER fold — is REAL, carried by the actual JWT on each per-request client.
   `after()` is a no-op, so no audit row is written and no compute job is enqueued; that is
   relied upon and documented, because it keeps `strategy_analytics` empty and so keeps the fill
   arm's clock-safety guard on its "nothing stored, nothing in flight" branch.
6. **Deliberately unchanged:** every existing CI job (the ci.yml diff has zero deletions), the
   lane script `scripts/local-stack/run.sh`, `supabase/schema/baseline.sql` (restored byte-exact),
   and all production code.
7. **Basis note for `actuals.tokens`.** 17 525 = 70 098 diff chars / 4 over the four commits,
   i.e. the realized diff. The plan's `estimate.tokens: 75000` is on a different
   (whole-file / working-set) basis; the two are not directly comparable and are not being made
