## ⛔ ONE VERDICT LINE IS MISLEADING, AND IT IS THE OPERATOR’S FAULT, NOT THE GATE’S

Assertion (c) printed:

> `EVIDENCE TAKEN. Calls WERE observed; the removal is a breaking change for whoever issued them.`

**No invocation was observed.** The `ALLOC_CALLS_CMD` used here matched any
`pg_stat_statements` entry whose TEXT contains the function name, which includes the DDL
that created it. All five entries were read individually and classified:

| entry | kind |
|---|---|
| `COMMENT ON FUNCTION create_allocator_connected_strategy IS …` | DDL |
| `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon` | DDL |
| `GRANT EXECUTE ON FUNCTION … TO authenticated` | DDL |
| `-- STEP 2: … RPC (SECURITY DEFINER)` + its `CREATE FUNCTION` | DDL |
| `-- STEP 3: self-verifying DO block` | DDL |

A second, narrower query filtering for invocation shape
(`create_allocator_connected_strategy[[:space:]]*\(`) returned ONE row, and its text was
inspected: the paren belongs to the `CREATE FUNCTION` statement inside the STEP 2 script.
**Zero invocations, confirmed by two independent queries.**

The gate is not wrong here — its STATED BOUND already says a reader is an operator
responsibility and that (c) speaks only to the current window. But the verdict SENTENCE
would mislead a reader who did not classify the rows, so it is recorded here rather than
left to be re-derived.
