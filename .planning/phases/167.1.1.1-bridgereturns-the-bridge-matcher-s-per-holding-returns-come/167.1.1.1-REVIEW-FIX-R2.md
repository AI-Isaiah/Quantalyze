# Phase 167.1.1.1: Review-fix report, round 2

**Branch:** feat/167.1.1.1-bridgereturns. **Commits:** `b5d829711`, `22b34cd8b`, `96779045e`, `cdc804f1d`.

## CR-01 (HIGH): this is a LIVE PRODUCTION DEFECT that predates this phase

The holding return series was indexed by plain `"YYYY-MM-DD"` strings, while every strategy and
candidate series reaches the engine through `records_to_series` as a tz-naive `DatetimeIndex`.
A string never equals a `Timestamp`, so the engine's date joins found no shared day. Phase 09's
string index (the deleted `reconstruct_symbol_returns` indexed by asof strings as well) never
joined the DatetimeIndex candidates once the universe moved to DatetimeIndex in 164.6.6.2.2. So
**the portfolio-fit axis (sharpe_lift, dd_improvement, corr_reduction, corr_with_portfolio; 40% of
the personalized score) was null for every book that holds a holding**, and a mixed
strategies-plus-holdings book also skipped every correlation-ceiling test and persisted a D-22
marker with `shared_days: 0` that blamed overlap for an index-type problem. This phase did not
introduce it, but its goal, its D-20 rationale and its D-22 marker all depended on the join
working, and none of the phase's tests could see it, because each built its candidate with a
string index of its own (which joined cleanly with the string-indexed holdings of the same test).

### Fix (commit `b5d829711`)

- `_load_holding_portfolio_context` builds each priced holding's series with
  `services.wealth_returns.records_to_series` (the converter `daily_returns_from_row` uses), so
  dtype family, tz-naive normalisation, sort, dedupe and name match the candidate side exactly. A
  `None` from the converter (unreachable for finite mark returns) raises `SeriesIndexError`.
- New `SeriesIndexError` and `assert_uniform_datetime_index(groups, allocator_id=...)`: every
  non-empty series across the groups must carry a `DatetimeIndex` of ONE tz-awareness. It runs in
  `_score_one_allocator` after the USD conversion and before `score_candidates`, over the
  converted book and the converted candidates, and the same guard runs inside `book_join_marker`,
  so the marker can never report `shared_days: 0` for a mixed index. It names the group, series
  ids and index types, never a value.
- `compute_holding_flags` and the marker read the same converted `portfolio_returns` the guard
  checked.
- `match_engine.py` and `window_alignment.py` were NOT modified; the guard needed no engine seam.

## WR-01 under D-23 (MEDIUM), commits `96779045e` and `cdc804f1d`

Founder D-23: when the matcher AUM is zero or below, the ticket is sized at the 0.5 add-weight
ceiling, consistent with D-21. Before the fix the context passed `portfolio_aum=None`, which
`score_candidates` reads as unknown AUM and sizes at a fixed 0.10, so a book that lost more
scored better on max weight and in total than the same book at +$100.

- **Seam (no engine change):** `_load_allocator_context` returns `aum_not_positive` (the same
  condition as the WARNING: AUM <= 0 for a book that holds holdings). `_score_one_allocator`
  then hands `score_candidates` `_AUM_NOT_POSITIVE_SCORING_AUM` (1e-6, used only for that call)
  when the fallback applies. The engine's own `_clamp(ticket / aum, 0.01, 0.5)` clamps to
  `_ADD_WEIGHT_CEILING` (0.5). `ctx["portfolio_aum"]` stays `None`, so the persisted AUM share
  stays null and `compute_holding_flags` is unchanged. `portfolio_aum` is read in exactly one
  place in the engine (the `add_weight` line), so the sentinel has no other effect.
- **Applies when it substitutes anything:** the engine's effective ticket (the preference merged
  with its default through `merge_with_defaults`, 50,000 when missing or null) is positive. An
  explicit zero ticket sizes at 0.10 whatever the AUM, so nothing is recorded.
- **Recorded on the batch** as a second book-level `holding_flags` entry beside the D-22 marker:
  `{"kind": "book", "holding_ref": null, "add_weight_fallback": "aum_not_positive_ceiling_0_5",
  "add_weight": 0.5, "flagged": false}`. Built by `add_weight_fallback_entry`. The dashboard
  reader keeps only `flagged` entries that carry a candidate, so it ignores it; the arm in
  `src/lib/queries.audit-2026-05-07.test.ts` now carries both book entries (`queries.ts` is
  unmodified, D-17 fence untouched).
- **WARNING text** now names the 0.5 add-weight ceiling and no longer says scoring is unaffected
  in a way that implied sizing was untouched (the scoring weights still are; the sizing is not).
- **Test** `tests/test_match_aum_not_positive_sizing.py`: real `_load_allocator_context`,
  `_score_one_allocator` and `score_candidates`, `max_weight` 0.1, ticket 50,000. AUM -4,000,
  -500 and 0 never score better than the same book at +$100 on the max-weight dimension or in
  total (the +$100 book scores `max_weight` 0.0 at the ceiling). Also: the entry is recorded and
  named in the WARNING; nothing is recorded at positive AUM or with an explicit zero ticket; a
  missing ticket counts as the engine default.
- **Neuter** (`scoring_aum` left at `None`): RED, 4 failed. Neuter (entry not appended): RED, 2
  failed. Restored with `cp`, `cmp` exit 0.
- **Scope note, for the caller to rule on:** the fallback is limited to books that hold holdings
  (the same condition as the `aum_not_positive` WARNING). A strategy-only book whose
  `allocated_amount` values are all missing also reaches the engine with `portfolio_aum=None`;
  that AUM is unknown rather than non-positive, so it keeps the engine's 0.10 default and is
  unchanged.
