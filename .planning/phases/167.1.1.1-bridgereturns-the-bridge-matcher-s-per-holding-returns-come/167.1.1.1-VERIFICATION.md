## Gaps (post-deploy, added 2026-10-16)

### GAP-01: a candidate whose overlap with the book is under 30 days gets a null portfolio fit with no reason

**Status:** failed (silent failure). **Found by:** the post-deploy SC4 reading on PROD (read-only, counts only).

**What was measured.** After deploy, 2 of 5 personalized Bridge candidates still carry null portfolio-fit components. Both rows are the same candidate strategy: its stored curve has 25 points, `daily_returns` is null, so the engine derives 24 returns, and those share only 8 and 9 days with each book's single eligible holding, under the engine's 30-day `min_overlap_days`. The null itself is CORRECT BY DESIGN: the axis cannot be computed on 8 days. The defect is that nothing says why.

**Where it goes silent (re-verified by symbol at the merge of origin/main, engine `v2.3.0`):**
- `services/match_engine.py` `_compute_portfolio_fit_components`, the `if not alignment.sufficient:` branch: returns `_empty_pf_components()` with no overlap count and no reason, although `alignment.overlap_days` is in hand (`services/window_alignment.py` `AlignmentMetadata`).
- The caller in `score_candidates`, `raw_components.append({...})` and the `score_breakdown["raw"]` dict carry nothing about it, so the persisted `match_candidates.score_breakdown.raw` cannot tell "too short to compute" from any other null.
- `corr_with_portfolio` (`_compute_corr_with_portfolio`, its own 10-day minimum) is null too on 8 days.
- `raw.data_completeness` reads `1.0` on that path. It measures how many book holdings survived the book's own join, not candidate overlap, so it reads "complete" beside a null fit.
- The book-level D-22 marker (`routers/match.py` `book_join_marker`, `book_join_too_short` + `shared_days`) names only the book's own join; the per-candidate case has no equivalent.
- No admin surface shows it: `src/components/admin/CandidateDetail.tsx` renders the Portfolio fit bar at 0 (null components normalise to 0.0) with no note.

**Done when:**
1. On the short-overlap path, the candidate's `score_breakdown.raw` carries the shared-day count and a named reason in the D-22 naming style (`fit_overlap_days`-style count plus a reason key, e.g. `fit_unavailable_reason: "overlap_below_min"`, and the minimum used), through the empty-components helper, `raw_components` and the persisted `raw`.
2. `raw.data_completeness` no longer claims completeness on a null fit (None on that path).
3. An admin can see the cause on the candidate (e.g. "Portfolio fit not computed: only 8 shared days with the book (needs 30)").
4. A candidate with exactly 30 shared days carries no reason key and keeps its computed components.
5. A test in `analytics-service/tests/` (beside `test_match_book_join_marker.py`) goes RED on the current code and GREEN after the fix: one-holding book with 60 days of returns, candidate with 24 returns of which 8 overlap the book; second arm at exactly 30 shared days.
6. `ENGINE_VERSION` moves to the next minor (the persisted `raw` shape changes, and trigger #2 re-scores cached batches so the PROD rows gain the marker without waiting for an input change), with every census that pins the version updated.

**Constraint found while re-verifying (a product-copy boundary, not a code detail).** The candidate's `reasons` list is NOT admin-only: `src/app/(dashboard)/recommendations/page.tsx` shows `reasons[0]` to the allocator as the card's primary pitch, `CandidateDetail.tsx` titles the list "Why this match", and `src/components/admin/SendIntroPanel.tsx` pre-fills the intro note from `reasons[0]`. A caveat line in `reasons` would reach the allocator and the intro note. So the admin-visible line is rendered from `score_breakdown.raw` in the admin `CandidateDetail.tsx` (beside the Portfolio fit bar), and `reasons` is left unchanged. `AllocatorMatchQueue.tsx` shows only `reasons[0]` per row and needs only its `raw` type extended.

```sql
WITH latest AS (
  SELECT DISTINCT ON (allocator_id) allocator_id, engine_version, computed_at, mode, holding_flags
  FROM match_batches ORDER BY allocator_id, computed_at DESC
)
SELECT engine_version, mode,
  (jsonb_array_length(coalesce(holding_flags,'[]'::jsonb)) > 0) AS has_holding_flags,
  count(*) AS allocators,
  sum(jsonb_array_length(coalesce(holding_flags,'[]'::jsonb))) AS entries,
  min(computed_at) AS oldest_latest, max(computed_at) AS newest_latest
FROM latest GROUP BY 1,2,3 ORDER BY 1,2,3;
```

```sql
WITH latest AS (
  SELECT DISTINCT ON (allocator_id) id, allocator_id, engine_version, mode, holding_flags
  FROM match_batches ORDER BY allocator_id, computed_at DESC

SELECT l.engine_version, l.mode,
  (jsonb_array_length(coalesce(l.holding_flags,'[]'::jsonb)) > 0) AS has_holding_flags,
  count(*) AS candidates,
  count(*) FILTER (WHERE c.score_breakdown->'raw'->>'sharpe_lift' IS NULL) AS sharpe_lift_null,
  count(*) FILTER (WHERE c.score_breakdown->'raw'->>'dd_improvement' IS NULL) AS dd_improvement_null,

FROM latest l JOIN match_candidates c ON c.batch_id = l.id AND c.exclusion_reason IS NULL
GROUP BY 1,2,3 ORDER BY 1,2,3;
```
