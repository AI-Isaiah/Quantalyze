## Summary

The price rule is sound and the two runtimes match. `holding_marks.py` and the adapter's
`classifySpotMarks` / `classifyDerivativeMarks` agree on everything this review checked:

- the pick: latest `updated_at` instant, ties to the smallest lowercase `api_key_id`, and gaps (marks <= 0) skipped before the pick;
- the contract checks, including real-calendar-date validation on both sides;
- adjacency, the sign taken from day i-1, flat or mixed days as gaps, and the -100% floor;
- option detection (`-C`/`-P` suffix in both runtimes);
- the ordering of the withheld-reason ladder.

`holding_equity_contribution` matches `holdingEquityContribution` except on the D-18 branch, and the fixture pins that difference. The matcher's history read is tenant-filtered (`.eq("allocator_id", ...)`), totally ordered `(asof, id)`, and capped. It raises instead of returning a partial series. Derivatives never put their notional into the AUM, the weights or `holding_flags`. A NULL P&L is never counted as 0. The phase's own pytest files pass at HEAD: 123 passed across the six new or rewritten matcher and mark test files.

The defects are in how the new AUM and weight basis reaches the engine. The engine assumes the book's joined weights sum to about 1. D-01 and D-16 now break that assumption on purpose, because withheld spot and derivative P&L are in the denominator. The code comment saying the score is unaffected is false. Measured on the real `_compute_portfolio_fit_components`, the same book gives a 4.3x different sharpe_lift (CR-01). The new P&L term also lets the AUM go to zero or below, or close to zero. In that case the flags persist a weight of 0.0 or an inflated weight (WR-01). D-20 counts returns but does not check that the counted returns overlap the rest of the book's (WR-02).

D-17 items (commit-route notional sizing, the writers' `or 0`) are out of scope and are not reported.

## Critical Issues (HIGH)

### CR-01: Withheld spot and derivative P&L in the weight denominator inflate the candidate's effective weight in portfolio-fit; the "score is unaffected" comment is false

**File:** `analytics-service/routers/match.py:999-1013` and `:1215-1221` (weights = value / AUM that includes withheld spot and derivative P&L); consumed at `analytics-service/services/match_engine.py:669-673` and `:718-721`

**Issue:** `_compute_portfolio_fit_components` builds the proposed book as follows:

```python
new_weights = {sid: w * (1 - add_weight) for sid, w in portfolio_weights.items()}
new_weights["__cand__"] = add_weight
w_new = np.array([new_weights.get(col, 0) for col in aligned.columns])
w_new = w_new / w_new.sum()
```

Only the joined columns survive into `w_new`. Let S be the sum of the joined holdings' weights. The candidate's effective share is then `a / (S·(1-a) + a)`, not `a`. Before this phase the holding weights were normalised over the eligible holdings only, so S was about 1. Now each priced spot weight is `value / (spot priced + spot withheld + derivative P&L)` (D-01, D-16), so S is the priced fraction of the AUM. PROD's `holding_flags` show stablecoins in 6 of 7 allocators' books. For a book that is 80% stablecoins, S = 0.2 and a 10% ticket is modelled as a 35.7% position. The current book (`w_arr`, normalised to 1 over the joined columns) and the proposed book are therefore on different bases. That changes `sharpe_lift`, `dd_improvement` and `corr_reduction`, which together carry 40% of the final score.

Measured with the real function at HEAD. One BTC series, the same candidate, `add_weight` 0.10:

| weights passed | sharpe_lift | dd_improvement |
|---|---|---|
| `{BTC: 1.0}` (S = 1) | 0.0907 | 0.0143 |
| `{BTC: 0.2, USDT(withheld): 0.8}` (S = 0.2) | 0.3931 | 0.0518 |

The joined return data is identical in both rows. Only a withheld holding with no series was added. The comment at `match.py:1000-1002` says "match_engine normalises the weights over the series it joins, so the score is unaffected". That is false for `new_port`. A positive derivative P&L lowers S, and a negative one raises it, in the same way. `test_e2_match_score_golden.py` and `match_engine_v2_golden.json` change only `engine_version`, so no golden book has a withheld or derivative weight, and nothing pins this.

**Fix:** Keep the AUM and the max-weight weights on the D-01/D-16 basis. Scale the joined weights to sum to 1 before applying `add_weight`, so the candidate's share is the ticket's share:

```python
# match_engine._compute_portfolio_fit_components
joined = [c for c in aligned.columns if c != "__cand__"]
base = np.array([portfolio_weights.get(c, 0.0) for c in joined])
base = base / base.sum() if base.sum() > 0 else np.full(len(joined), 1 / len(joined))
w_new = np.append(base * (1 - add_weight), add_weight)  # order matches aligned.columns
```

The alternative is to model withheld spot as an explicit zero-return leg. That needs a founder ruling. Either way, delete the false comment and add a test: adding a withheld weight with no series must not change `sharpe_lift`. That test fails today.

## Warnings (MEDIUM)

### WR-01: A negative derivative P&L can push the AUM to zero or below (equal weights invented, max-weight disabled, weight persisted as 0.0) or close to zero (weights > 1 persisted)

**File:** `analytics-service/routers/match.py:1004-1013`, `:1215-1229`, `:1246`, `:1342`, `:1355`, `:1417`

**Issue:** Before this phase the matcher's AUM was a sum of non-negative spot values. `total_aum` now adds each derivative's signed unrealized P&L (D-16). This is correct as an AUM. But the code downstream was written for a non-negative sum:

- If `combined_aum <= 0`, `_load_allocator_context` falls back to equal weights ("no AUM data available"). AUM data is available here; it is just non-positive. `portfolio_aum` becomes None, and `compute_holding_flags` then sets `weight = value / aum if aum else 0.0`. Every spot entry is persisted to `match_batches.holding_flags` with `weight: 0.0`, and the max-weight test silently does not run. A 0.0 standing in for an uncomputable figure breaks the never-invent rule. The figure should be null.
- If `combined_aum` is small and positive (spot value just above the loss), each spot weight is `value / aum`, far above 1. Every spot holding breaches `max_weight`. An eligible holding with a candidate scoring 50 or more is then persisted as `flagged: true` and shown on the dashboard's flagged-holdings panel with a weight like 1200%.
- `add_weight = ticket / portfolio_aum` (`match_engine.py:1005`) is clamped to 0.5 in the same case, and falls back to 0.10 when `portfolio_aum` is None.

None of the phase's tests build a book whose derivative loss exceeds or nearly cancels its spot value.

**Fix:** Decide the non-positive and near-zero AUM cases explicitly and test them. A minimal never-invent version:

- in `compute_holding_flags`, persist `"weight": None` and skip the max-weight test when `aum is None`, never 0.0;
- in `_load_allocator_context`, do not label the `combined_aum <= 0` branch "no AUM data". Log it at WARNING with the derivative P&L share.

Whether max-weight should divide by the spot-only total when derivative losses dominate is a founder question. Book it rather than pick silently.

### WR-02: D-20 counts adjacent returns but not their overlap with the rest of the book, so non-overlapping series still empty the shared-days join

**File:** `analytics-service/routers/match.py:963-966` (with the history read at `:877-889`)

**Issue:** D-20's stated purpose (the `_MATCHER_MIN_ADJACENT_RETURNS` comment, and the `test_match_book_join_overlap.py` docstring) is that one thin or gappy series must not empty `pd.DataFrame(portfolio_returns).dropna()`, null the portfolio-fit axis and silence every correlation-ceiling test. The gate checks `len(marks.returns) >= 30` over the whole 730-day window. The series is built from every day the allocator held the asset in that window, not from the current holding period. Two example books still pass the gate and empty the join:

- A holding traded for 60 days in the spring has 59 returns. If it was re-bought yesterday, it is admitted with returns that all predate another holding bought 40 days ago.
- A recent purchase with 31 adjacent returns is admitted. If another holding's marks failed for several days in that same month, the intersection is under 30 days, or empty.

In both cases `port_df` is empty, `portfolio_returns_series` is empty, every candidate gets `_empty_pf_components()`, and `compute_holding_flags` skips every correlation-ceiling test (`rest_df.empty`). Nothing names the cause, because the holdings are all "eligible". This is the failure D-20 was booked to prevent, reached by overlap rather than by count.

**Fix:** After the per-holding gate, check the joined overlap of the eligible holding series. If it is below `min_overlap_days` (30), withhold the holdings that shrink the intersection by name, for example a matcher-only `insufficient_book_overlap`. Or at least log the intersection length per allocator at WARNING so an empty join is never silent. Add a test with two holdings that each have 40 or more adjacent returns over disjoint date ranges; it should go RED today.
