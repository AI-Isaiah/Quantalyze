### MEDIUM-01: the fix's book-empty guard is unpinned; dropping it labels every candidate "no daily returns", and no test in the suite goes red

**File:** `analytics-service/services/match_engine.py:1087`; `analytics-service/tests/test_match_candidate_fit_overlap_marker.py` (no arm covers it)
**Classification:** WARNING (admin-only diagnosis integrity, the same class as SFH-R5 M1; ranking is unaffected)
**Evidence:** `mode` is `"personalized"` whenever `portfolio_strategies` is non-empty (`:929`). So
an allocator whose holdings have no joined returns (`portfolio_returns` empty, or a disjoint join,
which is D-22's `book_join_too_short` at 0 shared days) is personalized with an empty
`portfolio_returns_series`. In that state, `and not portfolio_returns_series.empty` is the only
thing that keeps the new `elif` from firing for EVERY candidate, including candidates that do
have returns. The first branch also requires a non-empty book, so those candidates fall through
to the `elif` too.

I measured this in a scratch copy of `analytics-service` (the worktree was not touched). I changed
the guard to `elif mode == "personalized":` and probed three personalized states:

| state | HEAD | neutered |
|---|---|---|
| holdings without returns, candidate HAS returns | `None` | `no_candidate_returns` |
| holdings without returns, candidate absent | `None` | `no_candidate_returns` |
| two holdings with a disjoint join, candidate HAS returns | `None` | `no_candidate_returns` |

With the guard neutered, the full analytics suite gave `52 failed, 10773 passed, 91 skipped`. The
unneutered copy gave the same 52 failures, as an identical sorted list. All 52 are repo-path or
git census tests that fail in any copy. **No test distinguishes the guard.** The fixer's neuter
table covered the other three guards (the `elif`, the empty-series return, the personalized
condition) and missed this one. CandidateDetail would then show "this strategy has no daily
returns to compare with the book" on every candidate of that allocator. That is a confident,
false cause in the place the admin reads, and it hides the real cause (the book), which is named
only in `match_batches.holding_flags`.
**Fix:** add one arm that pins the guard with a candidate that HAS returns, because that case
regresses most visibly:

```python
def test_arm_i_an_empty_book_join_names_no_candidate() -> None:
    # Personalized (a holding exists) but the book has no returns, so the D-22 batch marker names
    # it. No candidate, with or without a series, may carry the per-candidate marker.
    for cand_returns in ({"c1": _candidate_series("2026-01-01", "2026-03-01")}, {}):
        result = score_candidates(

            portfolio_strategies=[{"strategy_id": "p1"}],
            portfolio_returns={},
            portfolio_weights={"p1": 1.0},
            candidate_strategies=[_candidate("c1")],
            candidate_returns=cand_returns,
            portfolio_aum=1_000_000,
        )
        assert result["mode"] == "personalized"
        raw = json.loads(json.dumps(result["candidates"][0]["score_breakdown"]))["raw"]
        for key in REASON_KEYS:
            assert key not in raw
```

Prove it RED by dropping `and not portfolio_returns_series.empty` from a byte backup, then
restore and `cmp`.

### LOW-01: a series the USD conversion dropped is shown as "has no daily returns"

**File:** `src/components/admin/CandidateDetail.tsx:134-139`; `analytics-service/routers/match.py:1850-1853`
The router discards `convert()`'s second value, the dropped ids (`candidate_returns, _ = await
_usd.convert(...)`). So a BTC-unit strategy whose conversion came back empty (no price source,
or no priced interval) reaches the engine absent. It is labelled `no_candidate_returns`, and the
admin reads "this strategy has no daily returns". The strategy has returns. They could not be
converted to USD. SFH-R5 M1 listed this case as a source. The engine reason is accurate from the
engine's side (no series was given). The sentence overstates it. The drop is logged
(`native_to_usd.py:323-330`), so this is not silent. It is a misattribution, admin-only.
**Fix (book it):** pass the dropped ids into `score_candidates` (or tag them after the call) as a
distinct reason, e.g. `candidate_returns_unconvertible`. Alternatively, soften the sentence to
"no usable daily returns (none stored, or not convertible to USD)".

### LOW-02: an all-NaN candidate series is named as a short overlap of 0 days, not as no returns

**File:** `analytics-service/services/match_engine.py:703`, `:735-745`
`candidate_returns.empty` is False for a non-empty series of NaN, so the series reaches
`align_current_and_proposed`. The `dropna()` there yields 0 rows, so the candidate gets
`overlap_below_min` with `fit_overlap_days: 0`. The admin reads "only 0 shared days with the book
(needs 30)", while an absent series reads "no daily returns". The cause is equivalent, but the
labels are not. Pre-existing in kind (R5), and whether the router can emit such a series depends
on `daily_returns_from_row(..., keep_absent=True)`.
**Fix (book it):** test `candidate_returns.dropna().empty` at `:703` instead of `.empty`.
