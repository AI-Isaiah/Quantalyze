### Answers to the brief's questions

**MD-01: does any caller rely on the upsert refreshing an existing row?** No.
- **Same-day partial close later replaced by a final close.** That cannot happen and never could. `_completed_days_only` drops today from every fetch, and the read drops a stored today row before it reaches `by_date` (`benchmark.py:373-376`), so nothing in this code writes a partial close. Before this fix, a date already in `by_date` was also never rewritten, because of the `to_write` filter. The only "refresh" the old code could do was the accidental overwrite MD-01 described.
- **Correcting a wrong stored close.** No path exists in code, before or after the fix. That is now explicit rather than accidental (IN-R2-01).
- **Return value or count.** Not used. The `db_execute(...)` result is discarded. With `return=representation` and `resolution=ignore-duplicates`, PostgREST returns only the rows it actually inserted, so a consumer that counted the response would now under-count. There is no such consumer.
- **`require_persist`.** It is still meaningful and is not falsely tripped. A row that hits a conflict under DO NOTHING is a successful statement and raises nothing, so `BenchmarkCacheWriteError` still fires only on a transport or DB error. `routers/cron.py::benchmark_refresh` does not trust the write anyway. It reads the stored-through date back from the table (`_stored_through`) and returns 500 when that date is before yesterday. Under DO NOTHING, "already present" counts as current, which is correct.
- **Privileges.** DO NOTHING needs INSERT only (DO UPDATE needed UPDATE too), and the service-role client has both. No regression.

**SFH-01: consistency with the CSV run's flags.** The rule is the same: stale or None means unavailable. Whether the user sees why alpha and beta are blank:
- **The derive's own decision is not stamped.** The `derive_broker_dailies` pre-stamp (`job_worker.py:6977+`) writes no benchmark flag. The CSV run then sets `benchmark_unavailable` from its own `get_benchmark_returns` call. In the common case both calls see the same outage, so the stamp matches. When the benchmark state changes between the two calls, it does not match (LW-R2-01).
- **No factsheet surface renders the flag.** The only UI reader of `benchmark_unavailable` / `benchmark_note` is the wizard's `SyncPreviewStep.tsx:1776-1777`; `src/lib/types.ts:424` only declares it. On the factsheet, a null alpha or beta shows as a blank for EVERY basis, cash included, with no reason given. That predates 170.2 and is not introduced by this fix.

## Summary

No CRITICAL or HIGH findings. I tried to break the money and series paths and they held:

- **SC-5 `since` window.** `window_start = max(min(yesterday-(days-1), since-1), BTC_FIRST_DAY)` gives exactly the base close (`since-1`) that `_interval_matched_benchmark`'s index-0 pairing (166.4 D-07) needs. All five callers pass the first date of the series they pair, and every one of those series is a `DatetimeIndex`, so the `isinstance` guard never falls back to `None` in practice.
- **Keyset paging.** The loop cannot stop on a short page. It filters with `older`, so a double that ignores `.lt` terminates. It breaks once the oldest date read is at or before `window_start`. A cache hit needs the contiguous run that ends at the newest date to reach both `window_start` and `yesterday`. With `since=None` the result is identical to the old `days`-count contract.
- **CoinGecko.** The clamp to 365 is applied at the request. The `-1 day` shift, the midnight-only filter, the finite and positive price check and `_completed_days_only` together store exactly yesterday's close and never today's partial day.
- **Freshness on the fetch arm.** A result counts as fresh only when `run[-1] == yesterday and run[0] <= window_start`. Otherwise it comes back flagged stale, and the cron turns that into a 500.
- **Backfill script.** `--dry-run` is read-only. A run exits 1 on stale, on a short history and on an empty or uncounted read. Under a healthy read it is idempotent, and it prints no ids.
- **Cron.** Nothing else in the repo pins the old 00:10 minute. `*/15` crons imply Vercel Pro, which fires to the minute.
- **/compare.** `returns_series` really is the bridged level curve (`(1 + returns.fillna(0)).cumprod()` or `1 + Σr`). Gap days are therefore present at the carried level, and rebasing on the last level before `headlineCoversFrom` gives the suffix return. `extractAnalytics` passes the `twr_chain_broken` alias through. The service-role read is limited to rows the published-only read already returned, and it emits only a date.
- **SC-4.** `source` comes through the admin client, so no column-grant hazard. The conditional spread keeps non-CSV payloads byte-identical. The cache key moved from v12 to v13.
- **Layout.** `@3xl:` resolves against the `@container` scroller. React never overwrites the measured custom properties because `frameStyle`'s values do not change between renders.

Every finding below is a robustness gap at the edges.

## Medium

### MD-01: "The cache wins" holds only in memory. The DB write is a plain upsert, so a failed or partial cache read lets fetched closes (CoinGecko included) overwrite stored Binance closes

**File:** `analytics-service/services/benchmark.py:433-444` (and the read loop at `:357-389`)
**Confidence:** 6/10
**Issue:** `to_write` excludes only dates present in `by_date`. `by_date` holds what THIS call managed to read, and the write is `upsert(cache_rows)`, which is `ON CONFLICT DO UPDATE`. Three paths reach the write with an incomplete `by_date`:
1. The cache read raises `APIError` or `httpx.HTTPError` on page 1. It is logged and falls through to the fetch with `by_date == {}`.
2. Page 1 succeeds, page 2 or later raises, and `by_date` holds only the newest ~1000 rows.
3. Two compute jobs race during the Wave-5 recompute, both missing on the same cold window.

**Concrete scenario:** the 00:30 cron runs while PostgREST briefly answers 503 on the cache read, and Binance is also failing from Railway (the exact SC-2 condition). CoinGecko returns 365 shifted closes, and `to_write` becomes all 365 dates. The upsert overwrites a year of Binance-sourced closes with CoinGecko's start-of-day prices, which the research measured at about 0.05% apart. With `by_date` empty, `merged` covers only 365 days, so the result is stale and the cron returns 500. **The overwrite has already landed by then.**

Afterwards the cache is a mixed-source series, and nothing ever corrects it, because the cache wins on every later merge. Every benchmark-relative metric of every strategy then rests on a silently changed year of closes. The docstrings make this a stated invariant: `benchmark.py:427-431` says "a cached close ... is never re-written with a fetched one", and `backfill_btc_benchmark.py:15-16` says "A cached close is never overwritten, so re-running writes nothing new (idempotent)". The CHANGELOG Notes book half of this as "flagged, not fixed", but the code comments still claim it holds unconditionally.
**Fix:** enforce the invariant where the write happens, so it no longer depends on the read having succeeded:
```python
await db_execute(
    lambda: supabase.table("benchmark_prices")
    .upsert(cache_rows, on_conflict="symbol,date", ignore_duplicates=True)
    .execute()
)
```
This is `ON CONFLICT DO NOTHING`. It also closes the concurrent-writer race. Keep the `to_write` filter as the "nothing to write" short-circuit. Add a test that runs the cache read raising `APIError` together with a CoinGecko-only fetch and asserts the upsert carries `ignore_duplicates=True`, or that a pre-seeded close is unchanged in the fake table.

## Low

### LW-01: An empty or lagging Binance answer never reaches CoinGecko

**File:** `analytics-service/services/benchmark.py:63-69`, `:418-423`
**Confidence:** 4/10
**Issue:** `fetch_btc_daily_prices` falls back only when `_fetch_from_binance` raises. A Binance HTTP 200 with `[]` (for example a `startTime` Binance considers out of range, or an edge or proxy answering an empty body) produces an empty Series and no exception. `get_benchmark_returns` then raises `ValueError("benchmark source returned no completed days")` and goes to the stale-cache fallback. CoinGecko, which would have answered, is never tried. **Fix:** in `fetch_btc_daily_prices`, treat an empty Binance series as a failure (`if series.empty: raise ValueError(...)`) so the fallback runs. Optionally, on the fetch arm, when the merged run ends before `yesterday` and the source was Binance, try CoinGecko once before returning stale.

### LW-02: The stale-cache fallback (exception arm) bridges gaps, and its window is now up to about 3300 days wide

**File:** `analytics-service/services/benchmark.py:198` (`_stale_cache_fallback`), called at `:472-476`
**Confidence:** 5/10
**Issue:** `_stale_cache_fallback` takes `sorted(by_date)[-days:]` without a contiguity check, and `prices_to_returns` runs `pct_change` across any missing date. A multi-day move therefore becomes one daily return dated after the gap. `_interval_matched_benchmark` cannot tell a missing price row from a contiguous one (its own docstring says so), so a dense strategy's one-day interval is paired with a multi-day BTC move. That is an invented daily benchmark return feeding alpha, beta and R². The bug predates this phase, but 170.2 widens `days` here to `(yesterday - window_start).days + 1`, up to roughly 3300 for a 2017-floored `since`, and the paged read now loads up to 20,000 rows into `by_date`. A gap anywhere in years of history is far more likely to fall inside the served window. The fetch arm, by contrast, correctly uses `_contiguous_run_ending_at_newest`.
**Fix:** serve the stale fallback from `_contiguous_run_ending_at_newest(by_date)` trimmed to `>= window_start`, the same shape as the fetch arm.

### LW-03: The stale fetch-arm series is not trimmed to `window_start`

**File:** `analytics-service/services/benchmark.py:455-464`
**Confidence:** 5/10
**Issue:** When the merged run ends before `yesterday` (for example CoinGecko has not yet published, or Binance lags), the code returns `_series_for(run, merged, symbol)`. That is the whole contiguous run, which after the backfill reaches back to 2017-08-17 whatever `window_start` was. The hit arm and the fresh fetch arm both trim to `>= window_start`. The pairing helpers align by date, so metrics are mostly unaffected. But the cron's `points` count, and any consumer that uses the series length or its first date (log lines, a `since=None` caller expecting about 1000 points), now see a different window depending only on whether the result was stale.
**Fix:** `window = [d for d in run if d >= window_start]; return prices_to_returns(_series_for(window or run, merged, symbol)), True`.

### LW-04: /compare treats a string `"true"` flag as chain-broken. The factsheet treats only a boolean `true` as chain-broken

**File:** `src/lib/queries.ts:277` (`twr_chain_broken:data_quality_flags->>twr_chain_broken`), consumed at `src/app/(dashboard)/compare/page.tsx:187` and `src/components/strategy/CompareEquityOverlay.tsx:99`
**Confidence:** 4/10
**Issue:** `->>` renders both JSON `true` and the JSON string `"true"` as the text `true`. `singleKeyDataQuality` (`composite-read-path.ts`) deliberately accepts only a boolean `=== true` ("a string 'true' or 1 never prints the caveat", T-92-05). A row whose flag is the malformed string `"true"` reads clean on its factsheet and chain-broken on /compare. On /compare it then takes the service-role read and draws a suffix-only line, or none, beside a factsheet that draws the whole curve. That breaks the "chart and table always agree / one source" premise of D-07 for that row.
**Fix:** project the JSON type as well, for example `twr_chain_broken:data_quality_flags->twr_chain_broken` (the `->` operator returns JSON, so PostgREST yields a boolean), and coerce `=== true` in both places. Or document that only booleans are ever written and add a test pinning the string case.

### LW-05: The derive jobs throw away the stale flag, so MTM and smoothed basis metrics can be computed against a truncated benchmark with no flag

**File:** `analytics-service/services/job_worker.py:6829` and `:6920` (`_mtm_benchmark_rets, _ = ...`, `_smoothed_benchmark_rets, _ = ...`)
**Confidence:** 5/10
**Issue:** These two call sites gained `since` in this phase but still discard `is_stale`. Under 170.2 a stale result can be a SHORTER run than the requested window. Two examples: the cache still starts after `since` (before the backfill) while Binance is down, so `merged` = cache plus 365 CoinGecko days ends at the cache's oldest date; or there is a gap older than 365 days. The `mark_to_market` and `smoothed_mtm` alpha, beta and R² are then measured over a different, shorter window than the cash basis, which honours `benchmark_stale` in `analytics_runner.py`. Nothing in `data_quality_flags` records it. This is the silent-fallback class the brief asks about. It predates 170.2, but SC-5's premise is that metrics are measured over the full history.
**Fix:** keep the flag. When it is stale, either pass `None` (benchmark family null, the honest choice) or stamp the same benchmark-stale flag the cash basis carries.
