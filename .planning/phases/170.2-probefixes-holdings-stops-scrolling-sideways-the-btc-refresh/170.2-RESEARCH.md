## Summary

All six items are real and reproduce. The two layout items (SC-1, SC-6) share one measured mechanism family: a `display:grid` with an implicit `auto` track, or a sticky stack whose hard-coded offsets disagree with the cells' real widths. I rendered the real components (React Testing Library render of `HoldingsTabPanel`, the real `StrategyTable` inside the real `DashboardChrome`), compiled the repo's real Tailwind 4.3.3 CSS with the real fonts, and measured Chromium and WebKit. That harness reproduces the SC-1 overflow exactly and shows that the root-only fix suggested by CONTEXT is NOT enough (four nested grids must change). For SC-6 it reproduces the founder's "metrics read blank" symptom (at 360 px the pinned stack is 326 px wide inside a 326 px scroller, so every metric column has zero visible pixels at every scroll position). It does NOT reproduce the page-level sideways scroll (Q-5): the executor must name that offender with the existing `assertNoReflow` red run before touching anything.

The backend items hide three traps nobody had measured. (1) CoinGecko's free tier refuses `days` above **365** (measured: 365 answers 200, 366 answers 401 with `error_code` 10012), and the old code requests 1001. (2) The existing CoinGecko parser stamps each point with its own UTC date, but CoinGecko's daily stamp `D 00:00` is the price at the START of D, which equals Binance's close of `D-1` (measured on 7 days). Merging that series into the Binance-sourced cache without a one-day shift would write wrong, shifted closes. (3) `get_benchmark_returns` reads the cache with `.limit(days + 1)`, but PostgREST's `max_rows` is 1000, so the read can never return more than 1000 rows; Phase 169.2's "read in full" is true of the keyset-paged readers (`get_btc_closes`, TypeScript `readBtcCloses`) and false of `get_benchmark_returns`. On PROD today the cache holds 1155 contiguous BTC closes from 2023-08-10, and the oldest strategy starts 2023-04-26, so SC-5 also needs a Binance backfill of older history, not only a wider cache read.

The one finding that changes a design document: the UI-SPEC (M-3) keys the CSV masthead label on `payload.ingestSource === "csv"`. Measured on PROD, `strategy_analytics.daily_returns` is SQL NULL for every one of the 44 strategies, and `ingestSource` is derived from that column, so `ingestSource` is `"api"` for every real PROD strategy (composites are forced to `"csv"`, which is also wrong for this label). The label would never render in production while its render test passes on a synthetic payload. The truthful marker is `strategies.source = 'csv'` (27 PROD rows), which needs one new payload field and a payload-cache key bump.

**Primary recommendation:** Execute RED-first per criterion with the geometry/oracle tests named below; fix SC-1 with `grid-cols-1` on four grids (not one); fix SC-2/SC-5 together in `services/benchmark.py` (clamp CoinGecko to 365 days, shift its stamps by one day, merge with cache-wins, add `since` and a keyset-paged cache read, backfill older history from Binance); fix SC-3 by plotting stored levels over the D-07 suffix; add a `strategies.source`-derived field for SC-4 and amend UI-SPEC M-3; gate the Strategy-column pin on `@3xl:` and make pinned widths and offsets agree for SC-6.

### SC-2 — BTC refresh fallback

**`fetch_btc_daily_prices` and its fallbacks** (`analytics-service/services/benchmark.py`, HEAD):

- `fetch_btc_daily_prices(days=1000)` line 41: tries `_fetch_from_binance(days)`; on any exception logs and returns `_fetch_from_coingecko(days)`.
- `_fetch_from_coingecko(days)` line 92: GET `https://api.coingecko.com/api/v3/coins/bitcoin/market_chart` with `params={"vs_currency": "usd", "days": str(days), "interval": "daily"}`; indexes each `[ms, price]` point by `pd.Timestamp(ms, unit="ms").date()`.
- `get_benchmark_returns` line 276 calls `fetch_btc_daily_prices(days + 1)`, so the live request is `days=1001`.

**CoinGecko free tier, re-measured 2026-10-09** (one unauthenticated request per value to the public API):

| `days` | HTTP | Body |
|---|---|---|
| 365 | 200 | 366 points (365 midnight-aligned plus one intraday "now" point) |
| 366 | 401 | `error_code` 10012: "Your request exceeds the allowed time range. Public API users are limited to querying historical data within the past 365 days." |
| 400, 1000, 1001 | 401 | same |

[VERIFIED: live requests] Reproduced the failure end to end on old code: a scratch pytest drove `POST /api/benchmark-refresh` with Binance raising and a CoinGecko stub that refuses `days > 365`; old code requested `[1001]` and answered 500 `Benchmark refresh failed: no BTC series`, the same message as Sentry QUANTALYZE-1M/1N/1P. [VERIFIED: ran, then removed the scratch test]

**Defect found: the existing CoinGecko parse is one day off versus Binance.** CoinGecko's daily stamp `D 00:00 UTC` is the price at the start of day D, so it matches Binance's close of day `D-1`. Measured against a fresh Binance pull (`candle[4]`, open-time date), 2026-10-09:

| Binance close date | Binance close | CoinGecko stamp D+1 | CoinGecko stamp D (same date) |
|---|---|---|---|
| 2026-10-05 | 85,767 | 85,771 | 86,490 |
| 2026-10-06 | 85,550 | 85,540 | 85,771 |
| 2026-10-07 | 83,322 | 83,282 | 85,540 |

The same-date pairing is off by up to 2.6 percent; the shifted pairing by about 0.05 percent (different aggregate price). The existing parser (`benchmark.py` line 104: `dates.append(pd.Timestamp(point[0], unit="ms").date())`) uses the same-date pairing. [VERIFIED: measured] The CoinGecko docs state "The last completed UTC day (00:00) data is available 10 minutes after midnight (00:10 UTC)." [CITED: docs.coingecko.com/reference/coins-id-market-chart]

**Consequence for the cron.** `vercel.json` schedules `{ "path": "/api/cron/refresh-benchmark", "schedule": "10 0 * * *" }`, exactly at CoinGecko's publication boundary. On a Binance-down day the fallback may be one day short at 00:10:00 (the run answers 500 "did not reach yesterday", and the next run backfills). Moving the schedule to `30 0 * * *` removes the race; nothing in `src` or `tests` pins the string `10 0 * * *` (grep found only `vercel.json:15`), and Phase 169.2's CHANGELOG already says to revisit it ("If the first scheduled runs answer 500 on freshness, move the cron to about 00:30 UTC"). See Q-3.

**PROD cache state, measured** (marker first; the marker named PRODUCTION): 1155 `benchmark_prices` rows, symbol BTC only, 2023-08-10 to 2026-10-07, zero missing days in the span. All 1155 closes equal a fresh Binance `BTCUSDT` daily pull exactly (0 differences above 1e-9), so the CoinGecko fallback has never written to PROD. The newest stored close is 2026-10-07 at about 14:00 UTC on 2026-10-09: yesterday's close (2026-10-08) was not stored by the 00:10 UTC cron of 10-09. The failure is live. The cause on Railway's egress was not measurable here (Railway log retrieval returned nothing) [ASSUMED: Binance geo-block].

**Recommended pick: CoinGecko limited to 365 days, merged with the cache** (the ROADMAP's first option), because it is the only candidate measured end to end and needs no new dependency.

### Anti-Patterns to Avoid

- **Fixing only the root grid (SC-1).** Measured: leaves slop 382/134/40/93.
- **Reading a restated number as the floor (SC-5).** The window start must derive from `since`; do not raise `days` to a bigger constant.
- **Overwriting cached Binance closes with CoinGecko values (SC-2).** Cache wins; write only new dates.
- **Indexing CoinGecko by the stamp's own date.** One-day shift required.
- **Keying the CSV label on `ingestSource` (SC-4).** Always "api" on PROD (Finding F-1).
- **Asserting `position: sticky` to prove pinning (SC-6).** Assert occlusion geometry.
- **Stopping the cache read on a short page.** `max_rows` makes every page short.

## Common Pitfalls

### Pitfall 1: A green seeded spec that never measured a wide table
**What goes wrong:** the SC-1 spec passes because the seeded book is narrow.
**Why:** `seedAllocatorBook` seeds one spot row; the existing sweep is empty-state.
**How to avoid:** seed wide rows and assert each table's `scrollWidth` precondition inside the test.
**Warning signs:** the case is green on the old code.

### Pitfall 2: CoinGecko rows written to `benchmark_prices` one day early
**What goes wrong:** a fallback day writes the close of D-1 under date D and later Binance rows disagree.
**How to avoid:** shift stamps by one day, drop the intraday point, cache wins on overlap. Test with the measured pairs above.

### Pitfall 3: `max_rows` makes `.limit(n)` for n above 1000 a silent no-op
**How to avoid:** page; stop on empty or on reaching `window_start`, never on a short page. Keep the first page's chain unchanged so the pinned mocks hold.

### Pitfall 4: Adding `since=` breaks fixed-signature test fakes
Twelve-plus `_fake_benchmark(symbol)` fakes; update to `**kwargs` in the same plan.

### Pitfall 5: Cron at 00:10 races CoinGecko's own 00:10 publication
Covered by backfill-on-next-run; moving to 00:30 removes it (Q-3).

### Pitfall 6: Compare overlay on degenerate stored curves
Two PROD composite rows store levels around 2.1e6 with `cumulative_return` 0. They must hit C-5(c), not an auto-scaled chart.

### Pitfall 7: Un-prefixed `left-*` surviving on one of nine pinned cells
One missed cell (a placeholder row) keeps the defect for 170.7. Grep the file for any `left-14`/`left-0`/`left-[6.25rem]` not preceded by `@3xl:` as a test.

### Pitfall 8: A payload field without a cache-key bump
The public factsheet cache would serve v12 payloads without the field for up to the 3600 s TTL after deploy.

### Pitfall 9: Writing the label condition against fixtures only
Verify any new marker against PROD columns before trusting a render test (Finding F-1).

## Code Examples

### Pinned-occlusion probe (the proof for SC-6's second half)
Source: measured in this research; adapt into an e2e helper.

```ts
const rr = region.getBoundingClientRect();
const stackRight = pinned ? strategyCell.getBoundingClientRect().right : rr.left;
for (const sl of [0, 60, 150, 300, region.scrollWidth]) {
  region.scrollLeft = sl;
  for (const td of metricCells) {
    const b = td.getBoundingClientRect();
    const l = Math.max(b.left, rr.left, stackRight), r = Math.min(b.right, rr.right);
    if (r - l < 4) continue;                       // scrolled out or fully under the stack: not "visible"
    const top = document.elementFromPoint((l + r) / 2, b.top + b.height / 2);
    if (!(top && (top === td || td.contains(top)))) fail(`${label} covered at scrollLeft ${sl}`);
  }
}
```
