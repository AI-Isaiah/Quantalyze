# Phase 170.2 Plan 01: BTC refresh fallback (SC-2) Summary

When Binance fails, the daily BTC refresh now still lands yesterday's close: the CoinGecko fallback is clamped to the free tier's 365 days, stored under the right date, and merged over the cached history with the cache winning.

## What changed

- `COINGECKO_FREE_MAX_DAYS = 365` in `services/benchmark.py`, and `_fetch_from_coingecko` clamps its request to it. The old code asked for `days=1001`, which the free tier refuses.
- `_fetch_from_coingecko` stores a `D 00:00 UTC` stamp under `D-1`, because it is Binance's close of `D-1`. It drops a point whose millisecond stamp is not a whole UTC day (the intraday "now" point), a non-finite or non-positive price, and any malformed point.
- `get_benchmark_returns` merges the fetched closes over the cached ones (`{**fetched, **cached}`), upserts only dates absent from the cache, and skips the upsert when nothing is new. `require_persist` handling is unchanged.
- The merged series is served fresh only when its contiguous run ends on yesterday and reaches `window_start`. Otherwise it is served flagged stale with a warning naming the run's dates, and the cron answers 500. New private helpers: `_contiguous_run_ending_at_newest` and `_series_for`.
- `vercel.json` schedules `/api/cron/refresh-benchmark` at `30 0 * * *` (D-08). The route test's pinned clock moved to 00:30 UTC so its comment states the real schedule.

## Known limits (recorded, not fixed)

- If the cache READ fails (not a miss) and the fetch falls back to CoinGecko, `by_date` is empty, so every fetched date is upserted and could overwrite a cached Binance close with a fallback close. This is the same exposure the previous code had (it upserted everything fetched). A DB-side `ignore_duplicates` upsert would close it; it was outside this plan's scope. The cache-wins prohibition holds for every path where the cache read succeeded.
- A cold cache with Binance down is served stale on purpose, so the cron keeps answering 500 each day until Binance returns or the history is backfilled (SC-5 / plan 02 owns the older-history backfill). The rows are still written each run.
