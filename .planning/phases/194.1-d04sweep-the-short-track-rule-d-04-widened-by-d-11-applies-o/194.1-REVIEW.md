## Warnings

### WR-01: Returns route serves a full-series span for an unreadable record, so the composer shows a figure the rule withholds (MEDIUM)

**File:** `src/app/api/strategies/[id]/returns/route.ts:507-524, 601-603`
**Issue:** The route builds `record = recordFromScalars(analyticsRow, asset_class)` and serves `figure_span_days: record.spanDays`. The `unreadable` flag is dropped, and the plan forbade a fourth field. The doc comment at :509-512 says "the consumer sees a null span and withholds", and `194.1-SITES.md` (B8) says an unreadable record "reads as unknown (the stored figure shows)". Neither is true when the malformed date is `headline_since`. `figureSpan` ignores an unreadable `headlineSince` and measures from `seriesStart` (`src/lib/figure-gate.ts`, `figureSpan`). The span is therefore the generous full-series span, not null. The shared parity fixture proves this: case "headline_since present but not a date: unreadable" expects `span_days: 40` together with `unreadable: true`.

The consumer `parseConstituentRecord` then gets a concrete span and no flag. `gateAnnualized` judges a chain-broken record on its full series rather than its headline suffix. The drawer-added leg's CAGR and Sharpe show as cleared (`short`, or plain `full` with no `<1y`). Every other site withholds this record. The phase rule is "unreadable record → withhold". The route's test covers only an unreadable `series_end` (`route.test.ts` "reports an unreadable record once…", which asserts `figure_span_days` null), so this path is untested.
**Fix:** The minimal change, inside the plan's no-fourth-field constraint, makes the declared limit true. An unreadable record then really is unknown:
```ts
figure_span_days: analyticsRankable && !record.unreadable ? record.spanDays : null,
figure_observations: analyticsRankable && !record.unreadable ? record.observations : null,
```
Add a route test with `data_quality_flags.headline_since: "garbage"` (alias `headline_since: "garbage"`) asserting a null span. To truly withhold, which is the phase rule, add a `figure_unreadable: true` scalar. `parseConstituentRecord` would read it into `unreadable: true`. That is a founder-scoped change because plan 09 ruled the field out. Either way, correct the route comment and the SITES B8 limit to describe what the code does.

### WR-02: A withheld Bridge Sharpe chip with an unreadable failing record shows a bare dash with no reason (LOW)

**File:** `src/components/portfolio/ReplacementCard.tsx:172-177`
**Issue:** When `deltaState === "withheld"` and `parseWireFigureRecord` returns null, which covers the fail-closed out-of-set state and a malformed record, `withheldReason` is null. The chip prints `—` with no `title` and no sr-only text. The 194 precedent for the same wire shape, `PortfolioOptimizer.tsx:195-200`, falls back to `WITHHELD_GENERIC_REASON` ("Withheld: the record is too short to annualize.") in exactly this case. A `—` with no explanation reads to the allocator as "no data", which the UI-SPEC withheld idiom exists to prevent. The two Sharpe-delta cards now say different things for the same verdict.
**Fix:** Mirror the optimizer. Hoist `WITHHELD_GENERIC_REASON` into `figure-gate.ts` (or export it), then:
```ts
const withheldReason =
  deltaState === "withheld"
    ? failingRecord !== null ? widenedWithheldReason("delta", failingRecord) : WITHHELD_GENERIC_REASON
    : null;
```

## Info

### IN-01: Intro snapshot Top/Bottom 3 is ranked by a Sharpe the admin page then withholds

**File:** `src/lib/intro/snapshot.ts:230`, `analytics-service/services/job_worker.py:15089`
**Issue:** Both producers rank `top_3_strategies` / `bottom_3_strategies` by the raw stored Sharpe. `SnapshotMiniTable` now dashes a withheld Sharpe, so a 40-day strategy can sit at "Top 3 #1" with `—`. The ordering leaks the withheld figure's rank. That conflicts with the B7 rule this phase applied to the compare table ("a withheld column never wins"). Admin-only and frozen at intro time.
**Fix:** Either rank only cleared or unknown records (`record_clears(...) is not False` / `recordClears(...) !== false`) in both producers, or book it as a known limit beside B12c in SITES.

### IN-02: Recommendations asset-class read failure and missing rows log via `console.error` only

**File:** `src/app/(dashboard)/recommendations/page.tsx:320-338`
**Issue:** The fail-closed branch nulls every card's CAGR and Sharpe, and the missing-row branch nulls a card's figures. Both report only through `console.error`. `record-span-read.ts` notes that `console.*` does not reach Sentry in this repo, and the sibling read there reports through `captureToSentry`. A sustained RLS or projection fault would blank recommendation figures with no alert. This matches the file's existing `statusError` convention, so it is a consistency gap rather than a regression.
**Fix:** Add `captureToSentry(new Error("recommendations asset_class read failed"), { tags: { stage: "recommendations-asset-class" } })` beside the two `console.error` calls.

### IN-03: Python `record_clears` ignores `unreadable`, so callers must re-implement the check

**File:** `analytics-service/services/metrics.py:117`, `analytics-service/services/match_engine.py:897-905`
**Issue:** TS `recordClears` returns `false` for an `unreadable` record. The Python twin takes `(span, obs, crypto)` and cannot see the flag. `_generate_reasons` therefore checks `bool(sharpe_record.get("unreadable"))` inline. It is correct today, but the next Python caller that judges a `figure_record_from_scalars` dict through `record_clears` alone would show an unreadable record. That is a parity asymmetry on the "unreadable → withhold" rule.
**Fix:** Add a small `record_dict_clears(record: Mapping[str, Any]) -> bool | None` beside `figure_record_from_scalars` that applies the unreadable rule first. Use it in `_generate_reasons`.

### IN-04: Composer constituent values and record can come from different sources

**File:** `src/app/(dashboard)/allocations/lib/constituent-figure.ts:80-91` versus `ScenarioComposer.tsx` (`addedStrategyMetadataLookup`, `cagr: found?.strategy.strategy_analytics?.cagr ?? lazyPair?.cagr`)
**Issue:** The values use book-then-lazy per field (`??`). The record uses the book whenever the strategy is in the book. For a book leg whose `strategy_analytics` is null, the value comes from the lazy route and is judged on the book's scalars, which are null and so read as unknown. The figure then shows ungated even though the lazy entry carried its own record. This is an edge case.
**Fix:** Use the book record only when the book supplied the value, or document the precedence on `constituentFigure`.

### IN-05: `UNKNOWN_RECORD` literal duplicated across four files

**File:** `src/app/(dashboard)/admin/intros/page.tsx:55`, `src/app/(dashboard)/allocations/components/ScenarioCompareTable.tsx:89`, `src/app/(dashboard)/allocations/lib/constituent-figure.ts:40` (and pre-existing `src/app/factsheet/[id]/v2/MetricsColumn.tsx:617`)
**Issue:** The same `{ spanDays: null, observations: null, crypto: false }` is restated in each file. If `FigureRecord` gains a field, every copy must be found by hand.
**Fix:** Export one `UNKNOWN_FIGURE_RECORD` from `src/lib/figure-gate.ts` and import it.
