<objective>
Close `[253-CRON-MOVES-SEED-WHILE-BOUND-RPC-DOWN]` the way the founder ruled on 2026-11-28 ("Job's private record (Recommended)", quoted from CONTEXT). When the re-read bound RPC is down for a whole run, the run records its seed as a seed-hold mark in its own `compute_jobs.metadata` through plan 02's fenced merge RPC. The next run reads that mark as a further seed term. So a daily row stored meanwhile by `cron_sync`, `/fetch-trades` or any other writer cannot move the seed past the span the failed run never read.

Purpose: plan 01's persistent matrix arms, hand-off arms A and B and retry arms turn GREEN; the named residual (hand-off C, predicted to stay RED on a set column only) stays recorded RED.

Output: the reader in `services/trade_resume.py`, the read and write hunks in `run_sync_trades_job`, the mechanism pins and a parity pin. PROOF-01 neuters H1, H2, H3, H5, H6 and H7 are plan 05's (H4, the SQL fence, is plan 02's).

Planner addition to research's V3, flagged so the orchestrator can strike it: the claimed job's own metadata is also read as a seed term. A run can write its mark and then fail on the unguarded balance read. It is then re-claimed on the SAME row, and research's "latest `done` row" reader never sees that row's mark. Handlers already read `job.get("metadata")` (the claim RPC returns the whole row), so this costs no extra database call. Plan 01's retry arms are its gate.

Scratch: set `SCRATCH` in every shell call; commands read `${SCRATCH:?}`. Commands are relative; tracked text carries no home path.
