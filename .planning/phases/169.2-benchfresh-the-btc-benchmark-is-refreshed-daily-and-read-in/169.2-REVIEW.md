# Phase 169.2: Code Review Report

**Reviewed:** 2026-09-27T05:47:15Z
**Depth:** standard
**Files Reviewed:** 24
**Status:** issues_found

## Summary

Reviewed the phase diff (`origin/main...HEAD`): the paged `readBenchmarkPrices` reader and its
adoption by `/api/benchmark/btc`, the Python `POST /api/benchmark-refresh` endpoint, the
`/api/cron/refresh-benchmark` Vercel cron route, the new `benchmark-refresh` seam budget, and the
census/roster edits. The census edits are internally consistent (16 `SeamBudgetKey` members and 16
`SEAM_ROUTE_BUDGETS` rows, matching the REGISTRY counts). Auth ordering in the cron route (secret,
then limiter, then service) is correct, and the Python handler maps every non-success to 500.

The central defect is that the endpoint's 200 does not prove what the phase exists to guarantee,
namely that `benchmark_prices` was written. `services.benchmark.get_benchmark_returns` swallows a
failed cache upsert and still returns `(series, False)`, so the cron reports a successful refresh
while the table stays stale. That is the silent-staleness bug this phase is meant to close. The
endpoint also does not check that the series it got is current. Separately, the 60 s budget is
shorter than the fetcher's worst case, and on a deadline the seam records a failure on the global
breaker, which contradicts the W2 rationale in the new code. The newest-first offset paging can
return a duplicate row when a refresh writes during a read. The reader now bridges a dropped
corrupt close into a multi-day return that is labelled as one day, and the btc route test was
rewritten to accept this.

## Critical Issues

### CR-01: The refresh endpoint answers 200 when the cache write failed, so the cron reports success while `benchmark_prices` stays stale

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`), relying on `analytics-service/services/benchmark.py` (`get_benchmark_returns`, the `# Cache for next time` block)
**Issue:** `benchmark_refresh` treats `(series, is_stale=False)` from `get_benchmark_returns("BTC")`
as proof of a refresh. But `get_benchmark_returns` handles a cache miss by fetching, then doing the
upsert inside `try: ... except Exception as e: logger.warning("Benchmark cache write failed: ...")`,
and returns `returns, False` either way. If the write fails (a PostgREST error, a missing
service-role key, `get_supabase()` raising "not configured", an RLS or permission change, a
timeout), the handler answers 200 with a current `through`. The TS route then answers
`{ ok: true, through }` and Vercel Cron shows green, while nothing was written. The factsheet
reader (`readBenchmarkPrices` via `/api/benchmark/btc`) keeps serving the old newest day. This is
the "benchmark went stale silently" defect the phase docstring says it removes, and the phase does
not close it on this path. `test_benchmark_refresh.py` patches `get_benchmark_returns` wholesale,
so no test can see the case.
**Fix:** Make the endpoint verify the table rather than trust the fetcher's return. After the
call, read the newest stored BTC date and fail when it is older than yesterday (UTC):
```python
series, is_stale = await get_benchmark_returns("BTC")
...
supabase = get_supabase()
res = await db_execute(lambda: supabase.table("benchmark_prices")
    .select("date").eq("symbol", "BTC").order("date", desc=True).limit(1).execute())
stored = rows(res)
yesterday = (datetime.now(timezone.utc).date() - timedelta(days=1)).isoformat()
if not stored or str(stored[0]["date"])[:10] < yesterday:
    raise HTTPException(status_code=500,
        detail=f"Benchmark refresh did not persist: stored through {stored[0]['date'] if stored else 'none'}")
return {"symbol": "BTC", "through": str(stored[0]["date"])[:10], ...}
```
Report `through` from the table, not from the in-memory series. Add a test that runs the real
`get_benchmark_returns` with a failing upsert and asserts 500. The alternative is to make the cache
write failure propagate from `get_benchmark_returns` on the refresh path, for example with a
`require_persist=True` flag, because that function has other callers that must stay lenient.

## Warnings

### WR-01: A successful fetch whose data ends before yesterday still answers 200. Freshness is never checked against the calendar

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`, the `if is_stale:` arm); `src/lib/analytics-schemas.ts` (`BenchmarkRefreshResponseSchema`)
**Issue:** `is_stale` from `get_benchmark_returns` means only that "all sources failed and the
cached fallback was served". The fresh-fetch arm returns `False` for whatever the upstream sent.
With the cron at `10 0 * * *` (00:10 UTC), a lagging source (the CoinGecko fallback, or a Binance
daily candle not yet published) can return a series whose last completed day is the day before
yesterday. The handler reports it as `stale: False` with that older `through`, and the TS schema
only checks that `through` is date-shaped. The docstring's claim "200 ONLY for a non-empty,
non-stale series" therefore holds only for the fetcher's narrow meaning of stale.
**Fix:** In the handler, compare `through` against `yesterday` (UTC) and answer 500 when it is
older. CR-01's table read gives this for free if it reports the stored date. Consider moving the
schedule a little later, for example `30 0 * * *`, to leave room for upstream publication lag.

### WR-02: The 60 s budget is below the fetcher's worst case, and a deadline records a failure on the GLOBAL breaker, contradicting W2

**File:** `src/lib/resilient-fetch.ts` (`SEAM_BUDGETS["benchmark-refresh"]`, its `notes`, and the transport arm that calls `recordOnce(transportVerdict.breakerKey)`)
**Issue:** The budget comment and `notes` say the failure "pages through the cron's non-2xx without
touching the breaker". That holds only for a 500. On a cache miss, `fetch_btc_daily_prices(1001)`
issues up to 2 Binance requests on `httpx.AsyncClient(timeout=30)` (a 30 s limit per phase, per
request), then on failure a CoinGecko request with the same limit, plus a cache read and a
1001-row upsert. That adds up to well over 60 s. When the deadline fires, the transport arm
classifies the failure as `seamBreakerVerdict(null)` and records it against `BREAKER_KEY`
(`breaker:railway`), the residual global breaker that every dependency-less analytics call reads.
So a slow upstream price source counts against the analytics breaker, the exact coupling W2 set
out to prevent. It also produces a false 502 alarm while the Python handler (not cancelled on
client disconnect) may go on to finish and upsert.
**Fix:** Size the budget to the fetcher's worst case (for example 120 s, raising the route's
`maxDuration` to fit), or bound the Python side under the budget with
`asyncio.wait_for(get_benchmark_returns("BTC"), timeout=50)` so the service answers its own 500
first. Correct the `notes` text so it does not claim the breaker is never touched.

### WR-03: Newest-first OFFSET paging returns a duplicate row when the refresh writes during a read

**File:** `src/lib/factsheet/benchmark-source.ts` (`readBenchmarkPrices`, the `.order("date", { ascending: false }).range(offset, ...)` loop)
**Issue:** Paging is by offset over a descending order, and inserts land at the head. The table
holds more than 1000 BTC rows, so every read spans at least 2 pages. If the daily refresh upserts
a new newest date between page 1 and page 2, every row shifts down by one, and page 2 re-reads the
last row of page 1. The result then contains the same `date` twice. The btc route turns that into
a spurious `0` return stamped on a duplicated date, which feeds TE/IR/beta downstream. The comment
"pages can neither skip nor repeat a row" holds only for a static table.
**Fix:** Use keyset pagination, which is immune to head inserts:
```ts
let before: string | null = null;
// per page:
let q = client.from("benchmark_prices").select("date, close_price").eq("symbol", symbol);
if (opts.from) q = q.gte("date", opts.from);
if (opts.to) q = q.lte("date", opts.to);
if (before) q = q.lt("date", before);
const { data, error } = await q.order("date", { ascending: false }).limit(BENCHMARK_PAGE_SIZE);
// ... before = rows[rows.length - 1].date
```
At a minimum, dedupe by `date` before returning.

### WR-04: The reader silently bridges a corrupt close into a multi-day return labelled as one day, and the guarding test was rewritten to accept it

**File:** `src/lib/factsheet/benchmark-source.ts` (`readBenchmarkPrices`, `if (!Number.isFinite(close) || close <= 0) continue;`); `src/app/api/benchmark/btc/route.test.ts` ("skips a point with a non-positive CURRENT close")
**Issue:** Before this phase, a zero or negative close at day D made the route skip both the return
at D and the return at D+1, so no return was built across the bad row. Now the reader drops row D
before the pct-change loop, and the route emits `close(D+1)/close(D-1) - 1` stamped at D+1: a
two-day return presented as a daily one. The test's expectations changed from
`[{date: "2024-01-04"}]` to `["2024-01-03", "2024-01-04"]` to match. This weakens a data-integrity
guard on returns that feed beta/TE/IR, and it is not limited to missing days. A present but
corrupt row now vanishes silently with no log line.
**Fix:** Keep the invalid row out of the prices, but record the gap. Either return the dropped
dates (for example `dropped: string[]`) so the btc route can skip the return that spans them, or
keep the reader lossless and leave validity to each consumer. At a minimum, log or capture the
count of dropped closes. Restore the original test expectation.

### IN-02: The route's per-point positivity and finiteness guards are now unreachable

**File:** `src/app/api/benchmark/btc/route.ts` (`GET`, the `prevClose <= 0 || ... close <= 0` guard and the `Number(...)` re-coercion)
**Issue:** `readBenchmarkPrices` already coerces and drops every non-finite or non-positive close,
so the guard and the long comment explaining it describe a path that cannot run. That is
misleading for a reader trying to find where validity is enforced.
**Fix:** Delete the dead guard, or keep it as an explicit defensive assertion with a one-line
comment that the reader is the enforcer. Resolve this together with WR-04.

### IN-03: The class entry that named `/api/benchmark/btc` as the highest-risk unbounded select was not updated

**File:** `TODOS.md` (the "CLASS — unbounded `.select()` on unbounded-growth tables (8 remaining sites)" item)
**Issue:** This phase closes the site that entry calls highest risk, but the entry still lists it
as open and still says "8 remaining sites". The ledger and the code now disagree.
**Fix:** Mark the `api/benchmark/btc` site closed by Phase 169.2 (`readBenchmarkPrices`) and
decrement the count.

### IN-04: The refresh failure path discards all diagnostics except the exception type

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`, `except Exception` arm with `raise ... from None`)
**Issue:** The handler logs only `type(exc).__name__`, suppresses the chain, and sends nothing to
Sentry, and the TS side returns a static `{ ok: false }`. A daily page therefore tells the
operator only "RuntimeError", with no stack. The redaction rationale is valid for the message, but
a traceback carries no upstream payload.
**Fix:** Add `sentry_sdk.capture_exception(exc)` (Sentry scrubbing applies), or log with
`exc_info=True` at a scrubbed logger, while keeping the response detail type-only.
