## Summary

The round-1 critical is closed at the root for the case it described. `benchmark_refresh` now
reads the newest completed stored BTC day back from `benchmark_prices` (`_stored_through`, with
`lt(today)` mirroring `_completed_days_only`) and answers 500 unless it has reached yesterday
(UTC). It reports `through` from the table. A test drives the real `get_benchmark_returns` with
a failing upsert and asserts 500 (`test_failed_upsert_through_the_real_fetcher_answers_500`), and
a control test covers the success path. The reader now uses keyset paging with a strict-decrease
check. The btc route no longer builds a return across a dropped close, and its test expectation
is restored. The cron route checks `through` against the calendar and captures to Sentry. The
schema's refusal arms have tests that can fail, and they are exercised through the real seam.

Gates re-run by this reviewer at HEAD: vitest on the refresh route, the btc route, the reader,
`seam-constants.pin` and `seam-budgets.invariant` gave 5 files and 238 tests passed. pytest
`tests/test_benchmark_refresh.py` and `tests/test_limiter_route_coverage.py` gave 18 passed.

**Cross-topic contract (Python response vs `BenchmarkRefreshResponseSchema`):** consistent.
Python returns `{symbol:"BTC", through:<YYYY-MM-DD from the table>, stale:False,
points:int(len(series))}`, and the handler has already refused an empty series, so `points >= 1`
satisfies `z.number().int().positive()`. `through` is `str(date)[:10]`, which matches the regex.
No cross-language fixture pins this: the TS tests mock the body. That is acceptable for one
endpoint, but a Python rename would only show up as a daily 502.

**Budget:** 100 000 ms plus 12 750 ms of breaker-store time is 112 750 ms, inside
`maxDuration = 120`, and `seam-budgets.invariant` is green. The notes no longer claim that a
deadline leaves the breaker untouched.

The fix round introduced one regression-class issue (WR-01: unthrottled Sentry capture on a
public, cache-bustable route, amplified by the new no-store 503). Two round-1 themes are closed
only for the case that was named, not for their root (WR-02, WR-03).

## Warnings

### WR-01: The fix round added an unthrottled Sentry capture on a public, cache-bustable route, and removed the CDN cache that used to absorb the error arm

**File:** `src/app/api/benchmark/btc/route.ts` (`GET`, the `read.dropped.length > 0` arm and the `!read.ok` arm)
**Issue:** Two changes in `0b1ede45d` interact:
1. The new `dropped-closes` arm calls `captureToSentry(new Error(...), {level:"warning", extra:{dropped: read.dropped}})` on **every function invocation** while a corrupt row exists. That can be indefinitely, because nothing repairs a row the Python writer stored. The route is in `PUBLIC_ROUTES`, and its own docblock says an attacker can bust the CDN with `?x=rand` and reach the function on every request, bounded only by `publicIpLimiter` (10/min per IP, so unbounded across IPs). The message embeds the count, so the Sentry grouping key also changes whenever the count changes. `extra.dropped` is an unbounded array: a bulk corruption ships every date on every event.
2. The read-error arm is now `no-store` (SFH MD-05). That is correct for freshness, but during a PostgREST incident every request now reaches the function and fires `captureToSentry(read.error, ...)`. Before, the CDN served the cached response for an hour. The scenario-share page's `fetchBtcDaily` self-fetches on every anonymous render of a force-dynamic public page, so page views become one Sentry event each during an outage.

The repo already has the tool for this: `shouldCaptureNow(key)` in `src/lib/sentry-capture.ts`, a per-instance 60 s window whose docblock describes this exact failure ("burns the Sentry quota and DROPS OTHER ALERTS during the same incident"). `resilient-fetch.ts` and `ratelimit.ts` use it. This route does not.
**Fix:** Keep the console lines unconditional (per the `shouldCaptureNow` docblock), and gate only the remote capture. Use a stable message and cap the payload:
```ts
if (read.dropped.length > 0) {
  console.warn("[api/benchmark/btc] dropped unusable closes:", read.dropped.length);
  if (shouldCaptureNow("benchmark-btc:dropped-closes")) {
    captureToSentry(new Error("benchmark_prices holds unusable BTC closes"), {
      tags: { route: "api/benchmark/btc", stage: "dropped-closes" },
      level: "warning",
      extra: { count: read.dropped.length, dropped: read.dropped.slice(-20) },
    });
  }
}
// and the same shouldCaptureNow("benchmark-btc:read-error") gate on the !read.ok capture
```
Add a test that two consecutive GETs with the same corrupt table produce one capture.

### WR-02: The table read-back proves the NEWEST day only, so a refresh whose purpose was to repair a gap still answers 200 when its write failed

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`, `_stored_through`); relies on `analytics-service/services/benchmark.py` (`_cache_miss_reason`, the swallowed upsert in `get_benchmark_returns`)
**Issue:** CR-01 is closed for the case it named: the newest stored day is behind and the write fails, which now gives 500. But `_cache_miss_reason` also reports a miss for **gaps** and for **fewer than `days` cached rows**. In both cases the stored newest day can already be yesterday. The fetcher refetches, the upsert fails and is swallowed at warning level, `_stored_through` reads yesterday, and the handler answers 200 with `points` equal to the in-memory series length, not the stored count. The cron is green every morning. Every analytics compute is a cache miss and a live upstream refetch, and the gap stays in the table, where `/api/benchmark/btc` bridges it into a multi-day return (WR-03). The trigger is narrow: a gap can come from the CoinGecko fallback's irregular `interval=daily` series, or from a partial earlier write. But the failure is silent in exactly the class this phase exists to remove, and the upsert swallow, which is the root, is untouched.
**Fix:** Verify what the write was supposed to achieve, not only its newest row. The cheapest root fix is to make the refresh path see the write outcome, since the other callers must stay lenient:
```python
# services/benchmark.py
async def get_benchmark_returns(symbol="BTC", days=1000, *, require_persist: bool = False):
    ...
        except Exception as e:
            if require_persist:
                raise
            logger.warning("Benchmark cache write failed: %s", str(e))
# routers/cron.py
series, is_stale = await get_benchmark_returns("BTC", require_persist=True)
```
Keep `_stored_through` as the freshness check. Add a test: seed yesterday plus a mid-window gap, make the upsert raise, and assert 500.

### WR-03: The route still bridges a MISSING day into a multi-day return stamped as one day. `dropped[]` fixes one cause of that defect, not the defect

**File:** `src/app/api/benchmark/btc/route.ts` (`GET` pct-change loop, the comment "A day with NO stored row at all is still bridged"); `src/lib/factsheet/benchmark-source.ts` (the `dropped` bookkeeping)
**Issue:** Round-1 WR-04 and SFH MD-03 named the defect as "`close(D+1)/close(D-1) - 1` reaches the caller as a ONE-day return". The fix skips such a return only when the hole is a corrupt stored row. When the row is absent, the same two-day move is still emitted as one day and feeds TE/IR/beta. BTC trades every day, and the Python side (`_cache_miss_reason`) treats any calendar gap as a defect, so the two halves of the system disagree on what a gap means. SFH MD-03's fix text asked for the general rule ("skip any return whose two dates are not consecutive calendar days"). The narrower fix also added bookkeeping (the `dropped` array on `BenchmarkReadResult` plus a two-pointer walk in the route) that the general rule would make unnecessary for the route's purpose. The missing-row half is pre-existing, not a regression. It is the root, and WR-02 shows a path by which a gap can persist while the cron reports green.
**Fix:** In the route, skip any pair whose dates are not one UTC day apart. This covers corrupt and missing rows alike:
```ts
const DAY_MS = 86_400_000;
for (let i = 1; i < prices.length; i += 1) {
  const prev = prices[i - 1], cur = prices[i];
  if (Date.parse(`${cur.date}T00:00:00Z`) - Date.parse(`${prev.date}T00:00:00Z`) !== DAY_MS) continue;
  ...
}
```
Keep `dropped` for the Sentry visibility (throttled per WR-01), or drop it from the loop. Add a test with a missing middle row that asserts no return at the next day. If bridging missing days is a deliberate product decision, record it in CONTEXT and say why it differs from the Python rule.

## Info

### IN-01: The 100 000 ms budget is an estimate over a service that has no total bound

**File:** `src/lib/resilient-fetch.ts` (`SEAM_BUDGETS["benchmark-refresh"]` comment); `analytics-service/routers/cron.py` (`benchmark_refresh`)
**Issue:** "3 upstream requests x 30 s" understates the fetcher. `httpx.AsyncClient(timeout=30)` bounds each phase (connect, read-per-chunk, write, pool), not the whole request. `_fetch_from_binance` loops up to `max_pages = 20` when pages come back short. `db_execute` reads and upserts have no timeout. The comment already says so ("NO TOTAL bound today"). A deadline still gives a false 502, one global-breaker failure, and a Python handler that may finish the write afterwards.
**Fix:** Wrap the fetch in `asyncio.wait_for(get_benchmark_returns("BTC"), timeout=80)` in `benchmark_refresh` (mapped to the existing 500 arm), so the service always answers inside the TS budget and the breaker is never charged for a slow price source.

### IN-02: The handler reads the wall clock separately from the fetcher, bypassing the module's pin point, and the Python tests compute "yesterday" independently

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`, `today = datetime.now(timezone.utc).date()`); `analytics-service/tests/test_benchmark_refresh.py` (`_yesterday()`)
**Issue:** `get_benchmark_returns` takes its `today` from `services.benchmark._utc_today()`, which exists so tests can pin the clock. The handler takes a second, later reading with `datetime.now`. A run that crosses UTC midnight (not the 00:10 cron, but a manual POST at 23:59, or a slow fetch) has the fetcher cache through D-1 while the handler demands D, which gives a false 500. The tests call `_yesterday()` at setup and the handler recomputes it at request time, so a CI run that straddles 00:00 UTC flips several cases. The TS tests pin `Date`; the Python tests cannot, because the handler does not use `_utc_now`.
**Fix:** Use `benchmark_mod._utc_today()` (or a module-level `_utc_now` in `routers/cron.py`) in `benchmark_refresh`. Have the tests monkeypatch it to a fixed date instead of calling `datetime.now`.

### IN-03: The new `dropped-closes` capture is fire-and-forget on a serverless route

**File:** `src/app/api/benchmark/btc/route.ts` (`GET`, both `captureToSentry(...)` calls)
**Issue:** `captureToSentry` returns a promise that the route discards. The helper's docblock says "A site that needs the capture to survive a cold finish schedules it explicitly". The refresh cron `await`s its capture; this route does not, so the capture can be lost when the function freezes after responding. The read-error arm had the same shape before this phase. The dropped-close arm is new.
**Fix:** `after(captureToSentry(...))` from `next/server` (or `await` it), together with the WR-01 throttle.
