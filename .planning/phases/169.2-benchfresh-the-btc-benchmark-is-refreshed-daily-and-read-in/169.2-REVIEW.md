## Regression hunt (the brief's checks, with evidence)

- **Does `require_persist` change behaviour for any other caller?** No. There are five non-test call
  sites: `routers/portfolio.py`, `services/analytics_runner.py`, and three in `services/job_worker.py`.
  All call `get_benchmark_returns("BTC")` with the default. Only `_benchmark_refresh_once` passes `True`.
  Test doubles that patch the function (`AsyncMock` or `side_effect`) never receive the kwarg from those
  callers.
- **Does the new except-arm ordering still serve the stale-cache fallback for non-refresh callers?**
  Yes. With the default, a failed write logs at warning level and falls through to `return returns,
  False`, so `BenchmarkCacheWriteError` is never raised and its `raise` arm is unreachable. A failed
  fetch still reaches `except Exception` and `_stale_cache_fallback` exactly as before.
  `test_other_callers_keep_the_lenient_write` pins the default path through the real function.
- **Does `asyncio.wait_for` cancellation leave a half-written upsert or leak?** No half-write.
  `db_execute` is `loop.run_in_executor(_DB_EXECUTOR, fn)`. A cancel prevents a job that is still queued
  and cannot stop one that is running. The upsert is one PostgREST request (one statement, atomic), so
  it lands whole or not at all, possibly after the 500. The handler docstring records this. The Binance
  `httpx.AsyncClient` is an `async with`, so cancellation closes it. The executor is bounded
  (NEW-C12-08), so a zombie thread is capped and cannot accumulate without limit.
- **Does `after()` work in this route's runtime and in its tests?** Yes (see IN-03 above). No other
  importer of the btc route executes `GET`. `limiter-ordering`, `seam-log-coverage`, `seam-budgets` and
  `seam-ratelimit-posture` are source-scanning tests that Fix-C re-ran green.
- **Does the exactly-one-day rule break a consumer that expected bridged returns?** A grep for importers
  of `/api/benchmark/btc`, `benchmark-source`, `pricesToDailyReturns` and `mergeWithFixture` finds only
  two runtime consumers of the route's output: `ScenarioComposer` (the BENCH-01 mount fetch) and the
  scenario-share page (`fetchBtcDaily`). **No factsheet file imports the route or the module.**
  `mergeWithFixture` has no production caller. Both consumers feed the series to
  `ScenarioBenchmarkSection`, which inner-joins by date (`innerJoinByDate`), so the active-return
  metrics are correct under the new rule. Both also compound it into the chart overlay with
  `computeStrategyCurve`, and that is where behaviour changes (WR-01).
- **Tests that cannot fail:** none found among the new tests.
  - `test_too_few_rows_...` asserts only the status. It still discriminates: with `require_persist`
    neutered, the read-back sees yesterday and answers 200.
  - `test_deadline_sits_below_the_typescript_seam_budget` fails loudly (`assert match`) if the TS
    literal changes shape, rather than passing vacuously.

## Warnings

### WR-01: Skipping the return after a gap makes the BTC wealth overlay drift by the gap's whole move for every later date. The fix report describes the effect as a missing point only

**File:** `src/lib/factsheet/benchmark-source.ts` (`pricesToDailyReturns`). The consumers are
`src/app/(dashboard)/allocations/components/ScenarioComposer.tsx` (`btcWealth = computeStrategyCurve(btcDaily)`)
and `src/app/scenario-share/[token]/page.tsx` (`btcWealth = computeStrategyCurve(btcDaily)`), with
`computeStrategyCurve` in `src/lib/scenario.ts`.

**Issue:**
- **How the overlay is built:** `computeStrategyCurve` compounds whatever daily returns it receives:
  `c *= 1 + value`.
- **What the new rule changes:** since `fdbcc561d`, a missing or dropped `benchmark_prices` row
  produces no return at the next stored date. The move across the gap is therefore never compounded.
  For every date after the gap, the plotted BTC wealth curve is `close(D+1)/close(D-1)` away from
  BTC's real level. On a volatile two-day window that can be several percent. It shows on the
  logged-in composer and on the anonymous scenario-share page.
- **Before this round:** a missing row was bridged. The metrics then saw a two-day move stamped as one
  day (the defect WR-03 fixed), but the overlay kept its level.
- **The trade-off:**
  - Daily-return fidelity: the inner-joined TE/IR/beta in `ScenarioBenchmarkSection`, which now want
    and get no bridge.
  - Level fidelity: the cumulative overlay, which wants the bridged move and has now lost it.
- **Why the fix report matters here:** Topic C's human-verification note says "the one visible effect
  is that there is no point at the day after a gap". That wording would lead a verifier to approve
  something smaller than the actual change.
- **Why WARNING and not CRITICAL:**
  - The trigger needs a gap in `benchmark_prices`.
  - The Python refresh refills gaps and now pages when that refill write fails (round-2 WR-02, closed).
  - The pre-169.2 route already skipped the returns next to a corrupt row, so level drift already
    existed for that case.
  - The resolution is a design choice, not a one-line fix.
- **Not a reason to revert WR-03:** the round-2 review offered the general rule as option one, and the
  metrics side is now right.

**Fix:** a human decides. The discriminating question: should the scenario BTC overlay show BTC's
price level, or BTC's gap-free daily-return history? Options:
1. Let the overlay compound from prices, not from gap-skipped returns. For example, the route also
   serves `{date, close}` (or a bridged "level" return per point), and consumers build `btcWealth` from
   closes while the metrics keep `pricesToDailyReturns`.
   ```ts
   // one option: serve both, derive each from the right source
   return NextResponse.json({ returns: pricesToDailyReturns(prices), levels: prices.map(p => ({ date: p.date, value: p.close / prices[0].close })) }, ...)
   ```
   This changes the route's `[{date, value}]` contract and both consumers.
2. Accept the drift and record it in CONTEXT, with the argument that gaps should not persist because
   the refresh repairs them and pages when it cannot.

Either way, correct the human-verification item for WR-03 so it names the overlay drift, not only a
missing point.

## Info

### IN-01: The docblocks claim the one-day rule matches the Python side. That holds for the cache check but not for Python's own returns

**File:** `src/lib/factsheet/benchmark-source.ts` (module docblock "This is the same rule the Python
side applies"; `pricesToDailyReturns` docblock "mirroring `benchmark.py` `prices_to_returns`");
`src/app/api/benchmark/btc/route.ts` ("The Python side treats any calendar gap as a defect too").

**Issue:**
- **Where the claim holds:** `_cache_miss_reason` refuses to SERVE a gapped cache, which is true.
- **Where it does not:** `services/benchmark.py` `prices_to_returns` is plain `pct_change().dropna()`.
  On the fresh-fetch path it bridges any gap in the upstream series before returning it to the
  analytics compute. The CoinGecko fallback's `interval=daily` series is the plausible source of such
  a gap.
- **Effect:** TS and Python derive different returns from the same gapped prices. The prose asserts
  they do not. The Python behaviour is pre-existing; the docstrings overclaim parity.

**Fix:** narrow the wording ("the same rule the Python CACHE check applies; Python's fresh-fetch
`prices_to_returns` still bridges"), or book the Python half against whichever phase next touches
`prices_to_returns`.

### IN-02: `mergeWithFixture` says `through` is "the last REAL price date", but an all-corrupt DB returns the fixture's last date

**File:** `src/lib/factsheet/benchmark-source.ts` (`mergeWithFixture` docblock; test "an all-corrupt
DB still cuts the fixture at its first stored date", which expects `through: "2024-01-02"`, a fixture
date).

**Issue:** the prose and the behaviour disagree. The planned consumers (169-02, 169-03, 169.4-02) may
read `through` as benchmark freshness. In the all-corrupt case it names a bundled fixture date. The
empty-DB case already behaved this way. The function has no production caller yet.

**Fix:** reword the docblock to say "the last date in the merged series (a fixture date when the DB
holds no valid close)". Or return the DB's own `through` separately, so a consumer can tell DB
freshness from fixture coverage.
