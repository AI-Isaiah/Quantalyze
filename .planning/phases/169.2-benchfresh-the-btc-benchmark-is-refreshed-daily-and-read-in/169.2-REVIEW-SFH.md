# 169.2 BENCHFRESH — silent-failure review, round 1

Scope: `git diff origin/main...HEAD -- . ':!.planning'` on `feat/169.2`, plus the one pre-existing
function the new endpoint delegates to (`analytics-service/services/benchmark.py`
`get_benchmark_returns`), because the endpoint's success contract rests on it.

Each finding says whether the failing line is **phase-introduced** or **pre-existing**, so the
fix round can route it (revert / book / redesign).

---

## CRITICAL

### CR-01 — A failed cache upsert still answers 200 "refreshed": the cron reports success while `benchmark_prices` never moves

- **Location:** `analytics-service/services/benchmark.py` `get_benchmark_returns` (fresh-fetch arm,
  the inner `try` around `supabase.table("benchmark_prices").upsert(cache_rows)`), consumed by
  `analytics-service/routers/cron.py` `benchmark_refresh`, then `src/lib/analytics-client.ts`
  `refreshBenchmark`, then `src/app/api/cron/refresh-benchmark/route.ts` `handle`.
- **Origin:** the swallow is pre-existing; the phase made it load-bearing. `benchmark_refresh`'s
  docstring promises "200 ... ONLY for a non-empty, non-stale series" and the cron route's docstring
  promises "A 200 means the service reported a current series". Neither checks that anything was
  WRITTEN, and writing the table is the only thing this cron exists to do. Not separable: it belongs
  in this fix round.
- **Mechanism:** on a cache miss the fetcher pulls a fresh series, then
  `except Exception as e: logger.warning("Benchmark cache write failed: %s", ...)` and
  `return returns, False`. `benchmark_refresh` sees a non-empty, `is_stale=False` series and answers
  200 with `through` taken from the FETCHED series, not from the table. The TS schema accepts it,
  the cron answers `{ ok: true, through }`.
- **Realistic trigger:** a database incident. The cache read fails (`_CACHE_READ_ERRORS`, also
  warning level), the upstream fetch succeeds, the upsert fails (warning). Every link is
  warning-level, which the default Sentry `LoggingIntegration` records as a breadcrumb, not an
  event. Also: a revoked or rotated service-role key, an RLS/grant regression on the table, a
  constraint change. Every one of these repeats daily: the next run misses the cache again, fetches
  again, fails the write again, and reports 200 again.
- **Hidden errors:** `postgrest.APIError` (grant/RLS/constraint), `httpx` transport errors, a
  `get_supabase()` "not configured" `RuntimeError` (the write path calls `get_supabase()` directly,
  not `_benchmark_client`), any `TypeError` building `cache_rows`.
- **User impact:** exactly the defect the phase exists to remove. `/api/benchmark/btc` and every
  factsheet reader keep serving a benchmark that stops at the last successful write, while the
  cron log says "through yesterday" every morning. Nothing pages.
- **Test gap:** `analytics-service/tests/test_benchmark_refresh.py` monkeypatches
  `get_benchmark_returns` wholesale, so no test can go red on this path.
- **Fix (verify the effect, not the path):** after `get_benchmark_returns` returns, have
  `benchmark_refresh` read `max(date)` for `symbol='BTC'` from `benchmark_prices`
  (`.order("date", desc=True).limit(1)`) and answer 500 unless it is `>= through` (and, per HR-01,
  `>= yesterday`). Return `through` from the TABLE, not the fetched series. Optionally also raise
  the upsert swallow to `logger.error` + `sentry_sdk.capture_exception`, but the table re-read is
  the control; a log level is not.

```python
series, is_stale = await get_benchmark_returns("BTC")
...
table_through = await _stored_through("BTC")   # max(date) from benchmark_prices
yesterday = (datetime.now(timezone.utc).date() - timedelta(days=1)).isoformat()
if table_through is None or table_through < yesterday:
    logger.error("benchmark_refresh: table not refreshed (stored through %s)", table_through)
    raise HTTPException(status_code=500,
        detail=f"Benchmark refresh did not persist: stored BTC prices through {table_through}")
return {"symbol": "BTC", "through": table_through, "stale": False, "points": int(len(series))}
```

  Add a Python test where the fetch succeeds and the upsert raises: it must answer 500.

## HIGH

### HR-01 — Freshness is checked on neither layer for the fresh-fetch path; a lagging upstream is reported as a successful refresh

- **Location:** `analytics-service/services/benchmark.py` `get_benchmark_returns` (fresh-fetch arm
  returns `(returns, False)` unconditionally); `analytics-service/routers/cron.py`
  `benchmark_refresh` (trusts `is_stale`); `src/lib/analytics-schemas.ts`
  `BenchmarkRefreshResponseSchema.through` (a format regex only);
  `src/app/api/cron/refresh-benchmark/route.ts` `handle` (never compares `through` to today).
- **Origin:** fetcher behaviour pre-existing; the handler's reliance on it is phase-introduced.
- **Issue:** the cache-hit arm requires `window[-1] >= yesterday` (`_cache_miss_reason`). The
  fresh-fetch arm has no equivalent: whatever the upstream returned is `is_stale=False`. The
  Binance -> CoinGecko fallback in `fetch_btc_daily_prices` makes this reachable: a fallback
  source that lags, or a Binance pagination loop that stops early (`max_pages`, the
  `new_cursor <= cursor_ms` break), yields a series whose newest completed day is older than
  yesterday, and the endpoint answers 200 "stale: false".
- **Hidden errors:** upstream lag, a truncated upstream page, an upstream date-labelling change.
- **User impact:** a stale BTC comparator reported green by the job built to keep it current.
- **Fix:** CR-01's table re-read with `>= yesterday` closes this on the Python side. As a second,
  cheap guard, the cron route can refuse a `through` older than yesterday (UTC) and answer 502.

### HR-02 — Every TypeScript-side failure of the refresh reaches no Sentry event

- **Location:** `src/app/api/cron/refresh-benchmark/route.ts` `handle`, the `catch (err)` arm.
- **Origin:** phase-introduced.
- **Issue:** the catch arm is `console.error(..., scrubSeamError(err))` + 502, nothing else. The
  seam core (`src/lib/resilient-fetch.ts`) captures only breaker bookkeeping failures
  (`seam-breaker:check` / `seam-breaker:record`), and `parseResponse` in
  `src/lib/analytics-client.ts` only logs and throws. So these arms produce one function-log line
  and nothing remote:
  - the 60 000 ms `benchmark-refresh` budget expiring (service slow or hung);
  - the analytics service unreachable (deploy, crash, DNS);
  - the shared breaker open (the call never leaves Vercel);
  - a contract violation (a 200 carrying `stale: true`, a changed `through` format, a wrong
    `symbol`), i.e. the exact silent-200 drift the schema was written to catch.
  The Python-side failures DO reach Sentry (its `logger.error` calls are events under the default
  `LoggingIntegration`), but none of the above ever reaches Python.
- **Why this is HIGH, and what it does NOT assert:** the design rests on "Vercel Cron alarms on a
  non-2xx" (CONTEXT D-08, citing RESEARCH Pitfall 5). That is a planning claim, not a mechanism this
  repo carries or this review measured. The in-repo evidence is that sibling crons split:
  `src/app/api/cron/flag-monitor/route.ts` and `src/app/api/cron/founder-lp-report/route.ts` call
  `captureToSentry`; `reconcile-strategies` does not. The phase promises "refreshed daily"; the
  channel that proves a missed day should exist in-repo.
- **Fix:** keep the console line and the 502, and add a capture. `captureToSentry` scrubs
  unconditionally, so the seam redaction rule is preserved.

```ts
} catch (err) {
  console.error("[api/cron/refresh-benchmark] refresh failed:", scrubSeamError(err));
  captureToSentry(err, {
    tags: { route: "api/cron/refresh-benchmark", stage: "refresh" },
    level: "error",
  });
  return NextResponse.json({ ok: false }, { status: 502, headers: NO_STORE_HEADERS });
}
```

  Consider the same for the limiter-deny arm (a 503 misconfigured limiter also skips the day
  silently today).

## MEDIUM

### MD-01 — The `stale: z.literal(false)` guard has no test; it cannot fail

- **Location:** `src/lib/analytics-schemas.ts` `BenchmarkRefreshResponseSchema`;
  tests `src/app/api/cron/refresh-benchmark/route.test.ts`.
- **Origin:** phase-introduced.
- **Issue:** the schema's own comment says a 200 whose `stale` is not `false` "must fail the parse
  rather than report a refresh that did not happen". No test references the schema or a
  `stale: true` body (grep: zero hits outside the two source files). Neuter check: change the
  field to `z.boolean()` (or drop the `through` regex) and nothing goes red. The real-seam test
  only feeds the happy body.
- **Fix:** in the "through the REAL seam core" describe, feed `{symbol:"BTC", through:"2026-09-25",
  stale:true}` and a malformed `through` with status 200; assert `refreshBenchmark()` rejects,
  and that the route answers 502 for it. Neuter -> observe red -> restore.

### MD-02 — `benchmark_refresh` logs the exception class name only, `from None`, no stack

- **Location:** `analytics-service/routers/cron.py` `benchmark_refresh`, the
  `except Exception as exc` arm.
- **Origin:** phase-introduced.
- **Issue:** `logger.error("... raised %s", type(exc).__name__)` with no `exc_info`, then
  `raise HTTPException(...) from None`. Sentry gets an event whose whole content is a class name:
  a `KeyError` or `TypeError` from a future edit to the fetcher is undiagnosable. The stated reason
  ("an upstream message can carry URLs, headers") is handled at the chokepoint:
  `analytics-service/sentry_init.py` installs `before_send=_redact_before_send` with
  `include_local_variables=False`, and the in-file precedent in `benchmark.py`'s own cache-read arm
  already does `exc_info=True` + `sentry_sdk.capture_exception(e)`.
- **Hidden errors:** `ValueError` (symbol guard), any programming error that escapes the
  fetcher's own broad handlers.
- **Fix:** keep the type-only log line and the static `detail`, and add
  `sentry_sdk.capture_exception(exc)` before raising, so the stack reaches Sentry through the
  redacting `before_send`.

### MD-03 — The reader drops corrupt closes silently, and the route then bridges the gap into a multi-day return stamped as one day

- **Location:** `src/lib/factsheet/benchmark-source.ts` `readBenchmarkPrices` (the
  `if (!Number.isFinite(close) || close <= 0) continue;` loop); `src/app/api/benchmark/btc/route.ts`
  `GET` pct-change loop.
- **Origin:** phase-introduced behaviour change.
- **Issue (two halves):**
  1. A non-finite, non-positive or non-numeric `close_price` row is dropped with no count, no log
     and no signal in the result. A corrupt row in PROD is never noticed.
  2. Before this phase, the route skipped BOTH returns touching a bad close. Now the reader removes
     the row first, so the route's guards never fire and the next day's return is
     `close[i+1] / close[i-1] - 1`: a two-day move stamped as a one-day return, feeding TE, IR and
     beta. The route test was rewritten to bless this (`route.test.ts`, "skips a point with a
     non-positive CURRENT close": "treated exactly like a MISSING day — the same way the loop
     already bridges any gap"). That is a decision, but it contradicts the Python side, where
     `_cache_miss_reason` treats any date gap in BTC (a 7-day market) as a defect.
- **Fix:** return a `dropped` count (and the dropped dates) on `BenchmarkReadResult`, log it with
  `captureToSentry` when non-zero, and have the route skip any return whose two dates are not
  consecutive calendar days, instead of bridging. At minimum, restore the pre-phase semantics
  (skip the day after a dropped close) and record the choice in CONTEXT.

### MD-04 — Offset pagination under a concurrent upsert repeats a boundary row; the docstring says it cannot

- **Location:** `src/lib/factsheet/benchmark-source.ts` `readBenchmarkPrices` (`.range(offset, ...)`
  with `offset += rows.length`), and its module docstring ("pages can neither skip nor repeat a
  row").
- **Origin:** phase-introduced.
- **Issue:** the guarantee holds only for a static table. Reading newest-first, an insert of a new
  newest day between two page reads (the daily cron's upsert, or a compute's lazy refetch) shifts
  every row down one position, so page 2 starts with the last row of page 1 again. The result
  carries a duplicate date; the route emits a 0.0 return for it and a duplicated date key. Nothing
  checks strict date monotonicity, so it passes as data.
- **Fix:** keyset pagination: after the first page, `.lt("date", oldestDateSeen)` with
  `.limit(BENCHMARK_PAGE_SIZE)` instead of `.range()`. It is immune to inserts above the cursor and
  still stops on an empty page. Alternatively assert strictly-decreasing dates across the
  accumulated rows and return `{ ok: false }` on a repeat. Correct the docstring either way.

### MD-05 — A read error is served as a CDN-cached empty series for up to an hour (stale for a day)

- **Location:** `src/app/api/benchmark/btc/route.ts` `GET`, the `if (!read.ok)` arm calling
  `emptyResponse()`, whose headers are `public, s-maxage=3600, stale-while-revalidate=86400`.
- **Origin:** the error arm is pre-existing; the phase adds new error sources to it (the
  `BENCHMARK_MAX_PAGES` ceiling, and an error on any of several pages instead of one).
- **Issue:** one transient PostgREST error is pinned at the edge as `200 []` for the whole cache
  window, and a caller cannot tell "unavailable" (D-09) from "no data". The failure is captured
  server-side once, then every cached hit silently repeats it.
- **Fix (surgical):** give the error arm `Cache-Control: no-store` so the next request retries the
  read; keep the `200 []` body contract as it is.

### MD-06 — A short upstream fetch is a 200, then a cache miss forever

- **Location:** `analytics-service/services/benchmark.py` `get_benchmark_returns` fresh-fetch arm;
  `analytics-service/routers/cron.py` `benchmark_refresh` (`points` computed, never checked);
  `src/lib/analytics-schemas.ts` `BenchmarkRefreshResponseSchema` (strips `points`).
- **Origin:** fetcher pre-existing; the handler's acceptance of any non-empty series is
  phase-introduced.
- **Issue:** the cache-hit arm needs exactly `days` (1000) contiguous completed days. The fresh arm
  accepts any non-empty series, so an upstream that returns, say, 30 days yields a 200 today, and
  every later cron tick and every analytics compute is a cache miss and a refetch. The handler
  docstring ("refetches and upserts only on a miss") then describes a steady state that never
  recurs, and the only number that would show it (`points`) is dropped by the TS schema.
- **Fix:** have `benchmark_refresh` refuse (500) a series shorter than the fetcher's `days - 1`
  returns, or at least log it at error level; keep `points` in the TS schema and log it.

## LOW

### LW-01 — `.limit(days + 1)` against a `max_rows` of 1000

- **Location:** `analytics-service/services/benchmark.py` `get_benchmark_returns` cache read.
- **Issue:** `supabase/config.toml` sets `max_rows = 1000`, so the requested 1001 rows come back as
  1000. It works only because today's partial row is no longer cached; a single legacy row for
  today makes every read a miss. PROD's `max_rows` was not measured by this review.
- **Fix:** request `days` rows, or make the cache read tolerate one missing row, and pin PROD's
  `max_rows` in a test or a comment with its measurement date.

### LW-02 — The route's `prevClose` / `close` positivity guards are now unreachable

- **Location:** `src/app/api/benchmark/btc/route.ts` `GET` pct-change loop.
- **Issue:** `readBenchmarkPrices` already guarantees finite positive closes, so the guards (and
  the two tests named for them) no longer exercise the route; they exercise the reader. Harmless,
  but a reader looking for where bad closes are handled is sent to dead code.
- **Fix:** keep them as defence in depth, but say so in the comment; resolve together with MD-03.

### LW-03 — `data ?? []` treats a null body without an error as the end of the table

- **Location:** `src/lib/factsheet/benchmark-source.ts` `readBenchmarkPrices`.
- **Issue:** PostgREST should never return `{ data: null, error: null }` for a select, but if it
  does mid-read, the loop stops and returns a partial series as complete, the exact class the
  module exists to prevent.
- **Fix:** `if (data == null) return { ok: false, error: new Error("benchmark_prices page returned no data and no error") };`

## Done well

- `readBenchmarkPrices` stops on an EMPTY page (not a short one), advances by rows received, and
  turns the page ceiling into an error instead of a truncated success. The tests for the 2500-row
  table and the sub-page-size server cap would both go red on the "short page" bug.
- A read error is never replaced by the bundled fixture (D-09), and the route test asserts it.
- The Python handler answers exactly 500 (never 503) on every failure outcome, with a `!= 503`
  assertion, so a stale benchmark cannot trip the shared breaker.
- The cron route orders auth before the limiter before the service, and every failure arm is
  non-2xx with a static body and a scrubbed log line.
