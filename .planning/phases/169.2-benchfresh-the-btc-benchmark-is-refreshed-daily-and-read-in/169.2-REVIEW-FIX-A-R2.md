## Fixed Issues

### WR-02: a refetch for a gap or for too few rows could fail its write and still answer 200 (fixed: requires human verification)

**Files modified:** `analytics-service/services/benchmark.py`, `analytics-service/routers/cron.py`,
`analytics-service/tests/test_benchmark_refresh.py`

**Applied fix (the root):** the fix changes the swallowed upsert itself. A new flag on
`get_benchmark_returns`, keyword-only `require_persist`, controls it:

- **Default `False`, for every other caller:** behaviour is unchanged. A failed write is logged at
  warning level and the fresh series is returned.
- **`True`:** a failed write raises `BenchmarkCacheWriteError(f"... {type(e).__name__}") from e`.
  This includes `get_supabase()` "not configured" in the write arm. The message carries the type
  only, and the original error is `__cause__`.

`benchmark_refresh` is the only caller that passes `True`.

**A trap in the review's suggested snippet:** a bare `raise` inside the write arm does not leave
`get_benchmark_returns`. The write `try` is nested inside the fresh-fetch `try`, whose
`except Exception` serves `_stale_cache_fallback`. In the gap case that fallback is non-None,
because the cache already holds yesterday. So the lost write would have come back as `(fallback,
True)`: a 500 for the wrong reason ("stale"), with no Sentry capture of the real error. The
dedicated exception class and the `except BenchmarkCacheWriteError: raise` arm ahead of
`except Exception` are what let it escape. A neuter run proved this (below).

**In the handler:** the error reaches the handler's existing exception arm. That arm logs the type
only, calls `capture_exception(exc)` (the chained cause reaches Sentry), and answers 500, never
503. The `_stored_through` read-back is kept as the freshness check.

**Tests:**
- `test_gap_refetch_with_failed_upsert_answers_500` is the case the review named:
  - Setup: 1001 days are seeded through yesterday, then one middle day is deleted. A precondition
    assert proves that `_cache_miss_reason` returns the **gap** arm.
  - Asserts: 500, `!= 503`, and `BenchmarkCacheWriteError` in the body, with no canary message in
    the body or logs. `table.newest() == yesterday` and the hole is still missing, which shows this
    is a persist failure and not a freshness one. The capture receives a `BenchmarkCacheWriteError`
    whose `__cause__` is the raised error.
- `test_too_few_rows_refetch_with_failed_upsert_answers_500` covers the other miss arm.
- `test_other_callers_keep_the_lenient_write` shows that the default path still returns
  `(series, False)` when the write fails.
- `test_current_series_answers_200_with_through` now also asserts
  `mock.await_args.kwargs["require_persist"] is True`, so a later edit that drops the flag cannot
  pass the mocked cases silently.
- **Adjusted:** `test_failed_upsert_through_the_real_fetcher_answers_500` (round 1) now expects
  `BenchmarkCacheWriteError` in the body instead of the stored date, because the lost write is
  named before the read-back runs. The read-back itself stays pinned by
  `test_through_is_reported_from_the_table_not_the_series`.

**Neuter, then RED, then restore.** A backup of each file was taken first. Each neuter and
restore was an edit, and each restore was confirmed with `cmp` against the backup, which printed
`RESTORED-IDENTICAL`.

- **Neuter 1:** in `routers/cron.py`, `require_persist=True` changed to `False`.
  Result: `4 failed, 16 passed`. The failing tests were the gap test, the too-few test, the
  round-1 upsert test and the kwargs assertion.
- **Neuter 2:** in `services/benchmark.py`, the `except BenchmarkCacheWriteError: raise` arm was
  deleted. Result: `2 failed, 18 passed`, with
  `assert 'BenchmarkCacheWriteError' in '{"detail":"Benchmark refresh failed: no BTC series"}'`
  and the log line `All benchmark sources failed: Benchmark cache write failed: RuntimeError.`
  This is the trap described above, measured.

### IN-01: the refresh had no total time bound (fixed: requires human verification)

**Files modified:** `analytics-service/routers/cron.py`, `analytics-service/tests/test_benchmark_refresh.py`

**Applied fix:** the entire refresh (fetch, cache write, table read-back) moved into
`_benchmark_refresh_once(today)`. `benchmark_refresh` runs it under
`asyncio.wait_for(..., timeout=_BENCHMARK_REFRESH_DEADLINE_S)`, with the deadline set to 80 s.

- **Why 80 s:** the TypeScript budget is `SEAM_BUDGETS["benchmark-refresh"].timeoutMs` in
  `src/lib/resilient-fetch.ts`. This fixer read that file and did not edit it. 80 s leaves 20 s for
  the network hop.
- **Why only the deadline can land in the outer `except TimeoutError`:** every failure inside the
  inner coroutine is already an `HTTPException`. `CancelledError` is a `BaseException`, so the
  fetcher's `except Exception` arms cannot swallow the cancellation.
- **The timeout arm** works like the others: a log line, `capture_exception(exc)`, and a 500
  (never a 503) with detail `exceeded the 80s deadline`.
- **Documented in the docstring:** cancelling cannot recall a DB call that `db_execute` has already
  handed to its thread. A write can therefore still land after the 500, and the next run's
  read-back sees it.

**Tests:**
- `test_refresh_past_its_deadline_answers_500_and_captures`: the deadline is patched to 0.05 s and
  the fetch sleeps for 5 s. The test asserts 500, `!= 503`, "deadline" in the body and the log,
  and a capture that receives a `TimeoutError`.
- `test_deadline_sits_below_the_typescript_seam_budget`: reads the budget **by symbol** from
  `src/lib/resilient-fetch.ts` with a regex (tolerating `100_000`), then asserts
  `0 < deadline_ms <= budget_ms - 10_000`. If the TypeScript budget is lowered later, this test
  goes red in Python.

**Neuter, then RED, then restore:**
- `timeout=None` gave `1 failed` (the deadline test, which ran for 8.37 s).
- A deadline of `95.0` gave `assert 95000.0 <= (100000 - 10000)`, `1 failed`.

Both were restored, and `cmp` printed `RESTORED-IDENTICAL`.

**Applied fix:** `benchmark_refresh` now reads `today = benchmark_service._utc_today()` once, at the
top and before the fetch. It uses the module attribute, so a test that pins
`services.benchmark._utc_now` pins both the handler and the fetcher. It passes that `today` to
`_stored_through`. The `datetime.now(timezone.utc)` read in the handler is gone.

**Test changes:**
- The `table` fixture pins `benchmark_mod._utc_now` to a fixed **past** instant (`_NOW`).
  `_yesterday()` and `_prices_ending` now derive from `_TODAY` and no longer call `datetime.now`.

  unpinned handler computes a yesterday years after every seeded row.
- `test_today_is_read_once_before_the_fetch` (new): the mocked fetch moves the pinned clock forward
  one day **while it runs**, and the test asserts 200 with `through` = the original yesterday.

**RED evidence:**

## Skipped Issues

### LW-R2-03 (carried LW-01): `.lt("date", today)` and `.limit(days)` in the cache read

**File:** `analytics-service/services/benchmark.py` (`get_benchmark_returns`, the cache read)
**Reason:** not trivially safe, so it was left as documented.

- **What breaks:** adding `.lt` changes the query chain that 5 existing mock sites pin exactly.
  `tests/test_benchmark.py` wires `select.eq.order.limit.execute` at 4 sites, and
  `tests/test_benchmark_extras.py` builds the order/limit chain at 1 more. Those tests would fail
  or silently stop exercising the read, and the query shape would change for every caller.
- **What the change would buy:** the Python side already filters today's row
  (`str(row["date"])[:10] < today.isoformat()`). The refresh verdict is unaffected, because
  `_stored_through` filters `lt(today)`. The only effect left is the `max_rows` cap on a legacy row
  for today.

The clean fix stays as recorded: add `.lt("date", today)` and `.limit(days)`, and update those 5
mock chains in the same change.

**Original issue:** a request for `days + 1` rows comes back with 1000 rows under `max_rows = 1000`,
so a legacy row for today makes every cache read that day a miss.

### LW-R2-01 (MD-06 residue): a current but short upstream series answers 200

**File:** `analytics-service/routers/cron.py` (`benchmark_refresh`, the `points` value)
**Reason:** a floor cannot be shown to never false-alarm, so it was not implemented.

**How `_cache_miss_reason` defines too few:** fewer than exactly `days` (1000) completed days. Any
floor has to sit near that number to mean anything.

**What decides it, unmeasured:** how long a series the CoinGecko fallback actually returns for
`days=1001` on the unauthenticated tier.
- `fetch_btc_daily_prices` falls back to CoinGecko whenever Binance fails, and its own log line
  names geo-blocking as the expected cause.
- If that tier caps or refuses long windows, any floor above the cap fires every day the fallback
  serves. That would be a daily false page from an alarm meant to be rare.
- This fixer cannot measure PROD's live source or that tier's limit from here.

**Effect of leaving it:** the effect is still bounded, as SFH-R2 noted. The table keeps its older
rows, so readers lose no history. `points` is still in the 200 body and on the cron's info line.
Round 2 also removed one silent case: a short series whose write FAILS now pages (WR-02).

**What would unblock it:** a measured CoinGecko window length. With that, a floor derived from
`get_benchmark_returns`'s `days` default could go next to that default.

**Original issue:** a series much shorter than the window that still reaches yesterday answers
200, and its only signal is an info-level log line.
