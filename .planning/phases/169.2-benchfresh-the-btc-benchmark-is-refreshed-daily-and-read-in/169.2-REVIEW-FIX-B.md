### SFH HR-02: TypeScript-side refresh failures reached no Sentry event

**Applied fix:** `handle`'s one catch arm now does `await captureToSentry(err, { tags: { route:
"cron.refresh-benchmark", stage: "refresh" }, level: "error" })` after the scrubbed
`console.error`. It follows the one sibling cron that captures, `flag-monitor`
(`monitorReadFailed`): the call is awaited so the lambda stays up until the capture settles, and
the tag key is `route` with a `cron.` prefix. (`founder-lp-report` does not call
`captureToSentry` on this branch, so `flag-monitor` is the only precedent.) The capture receives
the original error, and `captureToSentry` scrubs it unconditionally. The limiter-deny arm is
**not** captured, and this is **left open for the orchestrator**. It was out of this finding's
scope (SFH wrote only "consider"). Measured: `checkLimit` in `src/lib/ratelimit.ts` returns
`reason: "ratelimit_misconfigured"` for a null limiter in production WITHOUT calling
`captureToSentry` (its captures are on the store-timeout arm). A misconfigured limiter therefore
reaches Vercel Cron as a 503, and nothing reaches Sentry.
**Test:** "captures the failure to Sentry exactly once, with the caught error and the route tag
(HR-02)", run for GET and POST. The 401, 429, 503 and 200 cases now also assert that the route
made no capture. The spy mocks only `captureToSentry` and keeps `shouldCaptureNow` real, because
`resilient-fetch` and `ratelimit` import that too.
**Neuter check:** replaced the capture with a no-op, and 5 tests went RED (HR-02 x2, stale-through
x2, real-seam route 502). Restored by re-edit, and all were GREEN again.

### REVIEW WR-01 / SFH HR-01 (TS half): a `through` older than yesterday UTC answered 200

**Applied fix:** after `refreshBenchmark()` resolves, the route computes yesterday in UTC
(`new Date(Date.now() - 86_400_000).toISOString().slice(0, 10)`). If `result.through` is older, it
throws. The throw goes through the same single failure arm as every other failure: scrubbed log,
Sentry capture, static 502. The comparison is a string comparison, which is chronological for
`YYYY-MM-DD` because the schema already enforces that shape. A comment says so, so that nobody
"fixes" it to `Date.parse`. The docblock line "A 200 means the service reported a current
series" now states the calendar rule.
**Tests:** every case runs on a pinned clock (`vi.useFakeTimers({ toFake: ["Date"] })` at
2026-09-26T00:10Z, the cron's schedule). Without the pin, the existing fixtures (`through:
2026-09-25`) would have gone red today and rotted a little more each day. New tests: the
day-before-yesterday case gives 502, a log naming both dates, and one capture. The boundary case,
`through` equal to yesterday, gives 200.
**Neuter checks:** flipping `<` to `<=` turned the boundary test RED (x2). Disabling the check
turned the stale-through test RED (x2). Both restored by re-edit.
**Status:** fixed, requires human verification of the logic (a calendar condition). The Python
half (the table re-read against yesterday) belongs to Topic A.

### REVIEW WR-02: the 60 s budget was below the fetcher's worst case, and a deadline hit the global breaker

**Root cause:** the row copied `process-key-sync`'s 60 000 ms instead of measuring the fetcher it
waits on.
**Measured worst case (read only, `analytics-service/services/benchmark.py`):** on a cache miss,
`get_benchmark_returns` calls `fetch_btc_daily_prices(days + 1)`. `_fetch_from_binance` runs on
`httpx.AsyncClient(timeout=30)` and makes 2 requests for 1001 days at `limit: 1000`. On failure,
`_fetch_from_coingecko` makes 1 more request on the same 30 s client. That is 90 s of
per-request read bound. The cache read and the upsert go through `db_execute` and have no timeout
of their own.
**Applied fix:** `SEAM_BUDGETS["benchmark-refresh"].timeoutMs` goes from 60 000 to **100 000**
(90 s of fetch plus 10 s for the DB). This stays inside `maxDuration = 120`, which is unchanged
and still the orchestrator's constraint. SC-4b charges 100 000 plus the failing-state store worst
case (3 x 4 250 = 12 750), for 112 750 ms against a ceiling of 120 000. That leaves room for the
`checkLimit` round, which SC-4b does not charge.
**Breaker decision, recorded in the row comment:** the core was not changed. CONTEXT D-08 / W2
concerns the stale-price **500**, and a 500 still never counts. Every seam records a deadline on
`BREAKER_KEY` through `seamBreakerVerdict(null)`, and there is no per-budget opt-out. Adding one
would change the closed dependency set across languages. Once the budget is above the fetcher's
worst case, a deadline no longer means "slow price source". It means the service did not answer
within its own maximum, which is the Railway degradation the breaker exists to count. One call a
day adds at most one failure, against `BREAKER_FAILURE_THRESHOLD` (5) inside `BREAKER_WINDOW`, so
this seam cannot trip the breaker alone. The false `notes` sentence ("without touching the
breaker") is rewritten.
**Pins moved, each re-measured and none edited in bulk:** `seam-constants.pin.test.ts`
(`"benchmark-refresh": 100_000`, with the hand computation in a comment). Two comments were
updated with the new arithmetic: the one over `maxDuration` in `route.ts`, and the one on the
`SEAM_ROUTE_BUDGETS` row in `resilient-fetch.ts`. A grep found no pin of the value in
`REGISTRY.md`, `seam-budgets.invariant.test.ts`, `vercel-cron-limits.test.ts` or
`limiter-ordering.test.ts`: the invariant reads the value from the table, and its "120 s ceiling"
comment carries no budget number. Those files are therefore unchanged. `maxDuration` did not
move, so `vercel-cron-limits.test.ts` did not need a change.
**Neuter check:** at `timeoutMs: 110_000`, both the literal pin and SC-4b's "failing state:
request budget + store round trips < maxDuration x 1000" for this route went RED. So 100 000 sits
near a real ceiling that is enforced. Restored by re-edit, and GREEN again.
**Status:** fixed, requires human verification. The worst case is realistic but not proven: the
service has **no total bound** (see the handoff below).

### SFH MD-01: the `stale: z.literal(false)` guard had no test

**Applied fix:** tests only, in the "REAL seam core" describe, where only the transport is mocked
and the real `resilientFetch` and schema run. Five 200 bodies must make `refreshBenchmark()`
reject: `stale: true`, a malformed `through`, `symbol: "ETH"`, no `points`, and `points: 0`. One
more test covers the route end to end: it points the route's mocked `refreshBenchmark` at the
real one, and a 200 carrying `stale: true` must produce 502, `{ ok: false }` and one route
capture.
**Neuter checks:** `stale: z.boolean()` turned 2 tests RED (the stale parse and the route-level
502). Loosening `symbol`, dropping the `through` regex and making `points` optional turned the
other 4 parse cases RED. Both restored by re-edit, and GREEN again.

### SFH MD-06: `points` was stripped by the schema

**Decision:** kept it. This was cheap, and it matches the contract: the `benchmark_refresh`
docstring and return line carry `points: int(len(series))`, and the existing real-seam fixture
already sent `points: 400`.
**Applied fix:** `BenchmarkRefreshResponseSchema` gains `points: z.number().int().positive()`. It
is at least 1 because the service refuses an empty series. The route logs `console.info(...
refreshed BTC through <date> (<n> points))`, which contains only dates and counts and no error
value, and echoes `points` in its 200 body. The refusal half (a 500 on a short series) belongs to
Topic A in Python.
**Test:** the 200 case asserts the body `{ ok, through, points }` and the log line. The "no
points" and "zero points" parse cases above cover the schema field.
