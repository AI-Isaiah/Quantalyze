# Phase 169.2 Plan 01: BENCHFRESH feed half Summary

**One paged, newest-first `benchmark_prices` reader behind `/api/benchmark/btc` (fixing the PostgREST `max_rows` truncation that served the oldest 1000 BTC days), and an analytics-service `POST /api/benchmark-refresh` that runs the existing `get_benchmark_returns("BTC")` and answers exactly 500, never 503, whenever the refresh did not produce a current series.**

## Accomplishments

- `src/lib/factsheet/benchmark-source.ts`: `readBenchmarkPrices(client, "BTC", {from?, to?})` selects only `date, close_price`, orders by `date` descending, reads `.range()` pages of 1000 until an EMPTY page, advances by the rows actually received, stops with an error after 50 pages, reverses to ascending, coerces numeric-string closes and drops non-finite or non-positive ones. It returns `{ok: true, prices, through}` or `{ok: false, error}` and never falls back to the fixture (D-09). `mergeWithFixture(db, fixture)` returns `{prices, through}` per D-09.
- `/api/benchmark/btc` reads through `readBenchmarkPrices` (DB only, no fixture merge). The rate limit, response shape, cache header, honest-empty degrade, server log and Sentry capture are unchanged.
- `analytics-service/routers/cron.py` `benchmark_refresh` (`POST /api/benchmark-refresh`): awaits `get_benchmark_returns("BTC")`, returns `{symbol, through, stale: false, points}` for a non-empty current series, and raises `HTTPException(500)` for None, an empty series, a stale series (the detail names `through`) or an exception (logged by type only). It sits behind the global `X-Service-Key` middleware beside `/api/cron-sync`.
- Limiter census: `routers.cron.benchmark_refresh` joins `NO_LIMITER_QUARANTINE` with a reason, classified like `cron_sync`. The coverage gate went red on the new route before the entry was added (`test_the_unlimited_partition_equals_the_quarantine`, `test_the_partition_is_total`), which shows the gate reads the route.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Existing route test pinned the defect's query shape**
- **Found during:** Task 1
- **Issue:** `queries benchmark_prices for symbol BTC ordered by date ascending` asserted `order("date", {ascending: true})` on the unranged read, which is the truncating read itself.
- **Fix:** It now asserts `{ascending: false}` and `range(0, 999)`. The fake client was rebuilt so every read (ranged or unranged) is capped at 1000 rows like `max_rows`; without that cap the new newest-day case would have passed on the unchanged route (an invalid RED).
- **Files modified:** src/app/api/benchmark/btc/route.test.ts
- **Committed in:** fd5d73a79

**2. [Rule 1 - Semantics change, surfaced] A corrupt close is now dropped by the reader**
- **Found during:** Task 1
- **Issue:** The plan's reader drops non-positive closes. The route's pct-change loop is unchanged. So the rows 100, 0, 110, 121 now yield returns at 01-03 (110/100 − 1, bridging the dropped day) and 01-04, where the old route yielded only 01-04. The existing test `skips a point with a non-positive CURRENT close` went red on its exact shape.
- **Fix:** The expected shape was updated. The test's protective intent is unchanged: no return built on a non-positive close reaches the response (`> -1` still asserted). A dropped corrupt day is now treated like a missing stored day, which the loop already bridges.
- **Files modified:** src/app/api/benchmark/btc/route.test.ts
- **Committed in:** fd5d73a79

**3. [Rule 3 - Blocking] TDD RED evidence needs TAP; pytest emits none**

- **Issue:** `check tdd-red-evidence` parses TAP (`# tests`, `not ok N - name`), and pytest has no TAP output in this venv. Installing a package is out of bounds.
- **Fix:** The RED run wrote pytest's built-in `--junitxml`. A stdlib-only script under the scratchpad transcoded that XML to TAP line for line, and the record was checked: `RED_EVIDENCE_OK`. The transcoder adds no test outcomes of its own.
