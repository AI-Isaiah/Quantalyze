## 2. New silent failures from the fix round

I checked each new catch arm, fallback and Sentry call:

- `benchmark_refresh` table-read `try/except Exception` catches `get_supabase()` "not configured", `APIError`, transport errors and a `KeyError` on a malformed row. All of them become 500 + `logger.error` + `capture_exception`. No success-shaped path. `rows()` drops non-dict elements, and an all-malformed response becomes `None`, which gives a 500 (fails closed).
- `_stored_through` / the `through < yesterday` comparison: plain `YYYY-MM-DD` string comparison on both sides, sliced `[:10]`. Nothing is swallowed.
- TS `handle` stale-through `throw`: it goes through the one catch arm and is not returned as success.
- `captureToSentry` awaited in the cron route: it never rejects, so it cannot turn the 502 into a 500 or into an unhandled rejection.
- `readBenchmarkPrices` null-page and order-violation arms: both return `{ ok: false }`. No partial series is returned as complete.
- `/api/benchmark/btc` dropped-close capture: `level: "warning"` with the dates. It is not awaited, which matches the repo convention (over 100 bare `captureToSentry(` calls under `src/app/api`). Not raised.

No CRITICAL or HIGH was introduced. The remaining items follow.

### MEDIUM

#### MD-R2-01: The `dropped` hole contract is enforced only in prose, and `mergeWithFixture` erases it

- **Location:** `src/lib/factsheet/benchmark-source.ts` `mergeWithFixture` (signature `(dbPrices, fixture) => { prices, through }`) and the module docstring ("any later consumer that derives returns from `prices` must honour `dropped` the same way").
- **Origin:** introduced by the fix round. Latent: `mergeWithFixture` has no production caller in this phase. It is data-integrity for the planned consumers (Phase 169 plans 169-02 / 169-03, Phase 169.4 plan 169.4-02).
- **Issue:** `dropped` lives only on `BenchmarkReadResult`. The one helper the planned consumers are told to use takes `DailyPrice[]` and returns `{ prices, through }` with no `dropped`. So a consumer that merges and then runs the standard pct-change bridges the hole, and `close(D+1)/close(D-1) - 1` reaches TE/IR/beta as a one-day return. This is the MD-03 defect in the next consumer. A second case: if the OLDEST stored row is the dropped one, `dbFirst` becomes the next valid date and the fixture fills the dropped date inside the DB window. That is a fixture/DB seam day, which the D-09 docblock ("no seam day inside the DB window") says cannot happen.
- **Hidden errors:** a corrupt stored close silently becomes a two-day return, or a fixture value is silently substituted for it.
- **Fix:** carry the contract in the type, not in prose. Either have `mergeWithFixture` take and return `dropped` and anchor the fixture cut at the first STORED date, not the first valid one:

```ts
export function mergeWithFixture(
  db: { prices: DailyPrice[]; dropped: string[] },
  fixture: DailyPrice[],
): { prices: DailyPrice[]; through: string | null; dropped: string[] } {
  const dbFirst = [db.prices[0]?.date, db.dropped[0]].filter(Boolean).sort()[0];
  ...
}
```

  Or export one `pricesToReturns(prices, dropped)` helper, which `/api/benchmark/btc` already implements inline, and make it the only way to derive returns. Add a test where the oldest DB row is dropped.

### LOW

#### LW-R2-01: A current but short upstream series still answers 200. The only signal is an info-level log line

- **Location:** `analytics-service/routers/cron.py` `benchmark_refresh` (`points` is computed and never checked); `src/app/api/cron/refresh-benchmark/route.ts` (`console.info`).
- **Issue:** the MD-06 refusal half was handed to Topic A and not done. A fresh fetch much shorter than the fetcher's window that still reaches yesterday gives a 200. Every later compute is then a cache miss and a refetch, and the only trace is a `console.info` that nothing alerts on. The effect is smaller than round 1 stated: the table keeps older rows, so readers do not lose history. That is why this is LOW.
- **Fix:** in `benchmark_refresh`, `logger.error` (a Sentry event) when `len(series)` is below a floor derived from the fetcher's `days` (for example `days - 7`). Or refuse with a 500, as round 1 proposed. Put the floor next to the fetcher's `days` default so the two cannot drift apart.

#### LW-R2-02: The limiter-misconfigured 503 arm still reaches no Sentry event

- **Location:** `src/app/api/cron/refresh-benchmark/route.ts` `handle`, the limiter-deny branch.
- **Issue:** carried from round-1 HR-02 ("consider"), and Fix-B handoff item 5 confirms it. A misconfigured limiter skips the day's refresh with a non-2xx and a console line, but nothing remote. Whether that is silent depends on Vercel Cron's alarming, which this repo does not show.
- **Fix:** `await captureToSentry(new Error("refresh-benchmark: limiter unavailable"), { tags: { route: "cron.refresh-benchmark", stage: "limiter" }, level: "error" })` on the 503 arm. Leave the 429 arm uncaptured.

#### LW-R2-03 (carried LW-01): the cache read's `.limit(days + 1)` against `max_rows = 1000`

- Skipped by Fix-A with reasons. It no longer affects the refresh verdict, because `_stored_through` filters `lt(today)`. The clean fix that Fix-A recorded (`.lt("date", today)` + `.limit(days)` in `services/benchmark.py`'s cache read) remains a candidate for whichever phase next touches that function.

## Done well

- The CR-01 fix checks the effect, not the code path: the handler reads back the table instead of trusting the fetcher's return. The test runs the REAL fetcher against an in-memory table whose upsert raises, so it would have been red before the fix.
- The TS freshness refusal throws into the one existing failure arm instead of adding a second arm with its own logging. Every "not refreshed" outcome therefore logs, captures and returns 502 the same way.
- Keyset paging plus a strict-order assertion replaces the prose guarantee ("cannot skip or repeat") with a check that returns an error.
