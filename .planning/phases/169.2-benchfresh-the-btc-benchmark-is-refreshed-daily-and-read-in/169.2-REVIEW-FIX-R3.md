## Fixed Issues

### WR-01: the one-day rule drifted the compounded BTC overlay off BTC's level after a missing day. Fixed, requires human verification

**Applied fix:** the rule is now `pricesToDailyReturns(prices, dropped)`. `dropped` is a required
parameter, so every consumer has to thread it.
- **A MISSING stored day is bridged again.** Adjacent stored closes give one return at the later
  date. This is the pre-phase behaviour, and it is what Python `prices_to_returns`
  (`pct_change().dropna()`) does.
- **A DROPPED close is still not bridged.** A pair yields no return when any `dropped` date `d`
  satisfies `prev.date < d < cur.date`. A forward pointer over the ascending `dropped` list finds it.
  Round-1 WR-04 / MD-03 therefore stays closed: a bad close at D gives no return at the next stored
  day.
- **The `DAY_MS` date-difference check is removed.**
- **The btc route `GET` now calls `pricesToDailyReturns(prices, read.dropped)`.** `mergeWithFixture`
  already passes `dropped` through, and its fixture cut is unchanged.
- **`ScenarioComposer` and the scenario-share page are unchanged.** A grep found no comment in either
  file that describes the one-day rule.

**Tests:**
- **Moved from "never bridges" to "bridges":**
  - The route test is now "BRIDGES a MISSING day". It expects `["2024-01-02","2024-01-04","2024-01-05"]`.
    It also asserts that the compounded served returns equal BTC's real level (`133.1/100`), which
    is the WR-01 property.
  - The helper test is now "BRIDGES a MISSING row".
- **Added:** the helper test "does NOT bridge a DROPPED close". It holds a dropped 01-03 and a
  missing 01-06 in one series and expects `["2024-01-02","2024-01-05","2024-01-07"]`.
- **Kept, with `dropped` threaded through:**
  - the route test "skips a point with a non-positive CURRENT close";
  - the merge test "a DROPPED oldest stored row is not filled by the fixture", which now calls
    `pricesToDailyReturns(merged.prices, merged.dropped)`.

**RED proofs.** Each neuter was restored by re-editing. `cmp` against a byte copy taken before the
neuters matched every time. Nothing was restored with `git checkout`, `git restore` or `git stash`.
- **Neuter A: the one-day check put back.** 3 tests went RED:
  - the route's missing-day test;
  - the helper's missing-row test;
  - the helper's dropped test, through its bridged 01-07.
- **Neuter B: the dropped check made never to fire (`&& false`).** 3 tests went RED:
  - the route's non-positive-close test;
  - the merge test's dropped-oldest assertion;
  - the helper's dropped test.
- **Neuter C: the route passes `[]` instead of `read.dropped`.** The route's non-positive-close test
  went RED. This proves the route really threads `dropped`.

**The fixture/DB seam, restated because round 2's statement no longer holds:** in a
`mergeWithFixture` series, a seam where the fixture's last date and the DB's first date are not
consecutive and no `dropped` date lies between them is now BRIDGED. That gives one return from a
fixture close to a DB close, stamped at the DB's first date. A seam with a dropped first stored row
between them is still not bridged, and the merge test pins that case. `mergeWithFixture` has no
production caller, so this is documentation and not a code change. The `pricesToDailyReturns`
docblock now states it.

**Test titles:** both "BRIDGES" tests cite `(review round 3 WR-01, narrowing round-2 WR-03)`.

**For a human:** this reverses round 2's missing-day behaviour, back to the pre-169.2 behaviour. The
known limit is stated in the docblocks: a bridged multi-day move is stamped at the later date as one
daily observation. The daily-return metrics (TE/IR/beta) therefore see it as one day. The
orchestrator books that limit separately.

### IN-01: the docblocks overclaimed parity with Python

**Applied fix:** every claim of a one-day rule or of Python parity is rewritten:
- the `benchmark-source.ts` module docblock;
- the `pricesToDailyReturns` docblock;
- the comment above the call in the btc route `GET`.

They now say:
- A missing day is bridged, as Python `prices_to_returns` does.
- A dropped close is not bridged.
- Known limit: a bridged move is stamped at the later date.
- The Python CACHE check `_cache_miss_reason` refuses to serve a gapped cache, but Python's own
  `prices_to_returns` also bridges, so neither side has a one-day rule.

The `BenchmarkReadResult.dropped` JSDoc now also names `pricesToDailyReturns` as a consumer.

### IN-02: the `mergeWithFixture` `through` docblock disagreed with the all-corrupt case

**Applied fix:** the docblock is corrected to match the code. It now says:
- `through` is the last date in the merged series, or null when that series is empty.
- `through` is NOT a DB-freshness signal. When the DB holds no valid close (the DB is empty, or
  every stored row was dropped), `through` is a bundled fixture date.

The docblock also tells a consumer to call `pricesToDailyReturns(merged.prices, merged.dropped)`.
There is no code change.
