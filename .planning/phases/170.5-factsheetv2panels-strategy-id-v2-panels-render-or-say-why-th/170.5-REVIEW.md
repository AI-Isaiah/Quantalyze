**Issue:** with a v2 context, an absent `btc_rolling_correlation_90d` reads "needs 91 days paired with BTC". A stored `[]` still reads `insufficientHistoryMessage("90-day BTC correlation", 250, n)`. The producer writes the key only when there are at least 90 paired days (`metrics.py:2573`). `_rolling_correlation` returns `[]` at that point only when every window is flat and `_finalize_rolling` drops them all. So `[]` means "no dispersion", not "short history".
**Failure scenario:** a flat or constant-yield strategy with 400 days of history reads "Insufficient history … (have 400 days, need 250)". The day count contradicts itself, and the 250 floor contradicts the 91 shown for the absent-key case. The malformed branch (`:189-199`) also still prints the bare "Benchmark correlation unavailable." on v2, which is the copy this phase set out to retire.
**Fix:** when `context` is present, route `[]` and the malformed case through `whyFromContext`. Optionally add a flat-series rung ("No dispersion in this record.", matching `greeksReason`).

### IN-02: [LOW] The live v2 joint and the factsheet's cached joint can briefly disagree, and their reasons can differ on an edge case

**File:** `src/lib/factsheet/v2-joint.ts:190`; `src/app/factsheet/[id]/v2/page.tsx:231` (`revalidate: 3600`)
**Issue:** (a) The factsheet payload is cached for up to an hour, keyed on `computed_at`. v2 computes live on every request. A `benchmark_prices` backfill or correction inside the strategy's date range, with no recompute, changes v2 at once and the factsheet up to an hour later. D-07 says "always match exactly". (b) The light path calls `readFactsheetBenchmark(admin, series, undefined, id)`, so its `anyCovered` check sees only the cash axis. The builder's check also sees the MTM and smoothed axes (`benchmark-read.ts:131-135`).
**Failure scenario:** for (b), an options strategy whose cash axis has no covered BTC interval but whose MTM axis does. The factsheet prints "Alpha and beta need at least 10 days paired with BTC; this record has 0." v2 prints "BTC benchmark prices are unavailable for this record." The values (all "—") agree. Only the reason differs.
**Fix:** (b) accept it and document it in the module header (the "Known differences" list is the right place), or pass the single-key MTM and smoothed axes. (a) Note it in the same list. It is transient, and the parity oracle covers it by construction.

### IN-03: [LOW] `RollingAlphaBetaChart` receives the raw untrusted arrays that the gate validated only partially

**File:** `src/components/strategy-v2/RollingMetricsPanel.tsx:128`, `:212-213`; `src/components/charts/RollingAlphaBetaChart.tsx:51-58`
**Issue:** `countFinitePoints` skips a non-array series, but the chart still receives `data?.rolling_alpha ?? []` unchanged. If one series is valid (2 or more points) and the other is a non-array object or holds a `null` element, `for (const p of alpha)` throws (not iterable, or `p.date` of null), and the panel crashes on the client. Separately, alpha and beta with one point each on different dates count as 2 and mount a chart with no visible segment.
**Fix:** filter both series with the same predicate `countFinitePoints` uses, and pass the filtered arrays to the chart. Gate on 2 or more points for at least one single series, not on merged dates.

### IN-04: [LOW] `greeksReason` blames correlation when a caller omits it

**File:** `src/lib/benchmark-why.ts:117` (the `isDash(values.correlation)` check inside the `computed` arm)
**Issue:** `correlation` is optional, and `isDash(undefined)` is true. A `computed` status with four finite figures and no `correlation` key therefore prints "Correlation reads — when either return series is flat." That is false. The current single caller always supplies the field, because `getStrategyDetailV2` and `withV2Joint` both set it, so this is latent.
**Fix:** make `correlation` required on `GreeksValues` and `StrategyV2Detail.panel7Inputs.benchmark_greeks` now that every producer sets it, and update the fixtures. Do not keep it optional for fixture convenience.
