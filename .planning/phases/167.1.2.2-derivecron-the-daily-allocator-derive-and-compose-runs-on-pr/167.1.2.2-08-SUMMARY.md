## What the plan assumed that was false

1. **Same-day reading.** The plan and runbook assume the D-06 reads happen on the first cron day. A read one day later finds the first day's freshness overwritten (the table is upserted by owner and kind), so the 24-hour window protects against counting the next day's rows but also reads 0 for the day it names. Plan 06's note should have said the first-cron-day freshness must be read before the next 05:30Z.
2. **Task 1's verify** (`awk` on NR==2 with `started_after_run_at == 1`) assumes the first cron day is the newest run; it fails a day late. Checked per day instead (the table above).
3. **The pass rule has no verdict for "composed, untrustworthy".** D-18(c) predicted the two owners would read `awaiting`/INCOMPLETE/REFUSED. They now read `rebuilding:derivation_rejected`, which the rule files under `other_shortfall`, so the rule returns FAIL with no pass path other than all six non-held owners trustworthy. That is the rule working as written, and it is the question below.
4. **Runbook `claim-census` has no upper bound**, so a read from the first RUN_AT also includes the second run's claims; a bounded variant was used for the per-window numbers above.
