## Phase Boundary

The daily allocator key-mode derive (`derive_broker_dailies` per eligible key) and its compose epilogue
(`derive_allocator_equity`) run on PROD again, safely, so every allocator book gets a version-2

rebuilt". Then 167.1.2's remaining browser UAT is completed. Spec: the `### Phase 167.1.2.2` ROADMAP

<decisions>
## Implementation Decisions

- **D-01 (founder 2026-10-07):** Own phase, Wave 1. Fix the trigger rather than changing the page's promise.
- **D-02:** The cron is registered through a runbook step, never a migration (164.7 rule:
  "A migration that schedules is a scope violation"). The registration is a PROD live op the orchestrator
  runs (PROD writes are authorized), marker query first, with the statement and its readback recorded.
- **D-03:** Before registering, the load the fan-out adds is MEASURED (eligible key count, per-job duration,
  what else the worker runs between 04:00 and 06:00 UTC) and the fan-out is shown unable to wedge the worker
  the way the July phase35 backfill did. If that needs code (a bound, a lane, a stagger), it ships first.
- **D-04:** The FLIP runbook's gating steps (dedicated backfill worker cutover, pilot, E2 gate) are
  re-evaluated against today's code, not assumed: research states for each whether it is still needed, already
  satisfied by later phases, or obsolete, with evidence. A step judged still needed is planned, not skipped.
- **D-05:** The ROADMAP and TODOS notes saying "Do NOT re-register the `derive-allocator-key-dailies` cron"
  (ROADMAP ~394, TODOS ~786) are amended with dated lineage notes, not deleted.
- **D-06:** Success is measured on PROD after the first 05:30 UTC run: counts of version-2 `equity_curve`
  rows vs eligible allocators, job outcomes, no worker backlog; then the browser check of My Allocation.

### Claude's Discretion
- Whether a one-off manual enqueue for today's books precedes the first scheduled run (through the
  product's own enqueue function, not hand INSERTs).
</decisions>
