## Summary

The daily fan-out has been absent from PROD `cron.job` since the v1.11 recovery, so no key-mode `derive_broker_dailies` job has ever run on a schedule and no version-2 `equity_curve` row exists (PROD, 2026-10-07: 2 `equity_curve` rows, both with no `version` field, both from 2026-07-20; 0 version-2). The census instrument built in 167.1.2 reads the baseline today as `owners_with_eligible_keys 7, ready 0, rebuilding:awaiting_derivation 6, rebuilding:duplicate_account 1`. A 05:30 run on PROD today would enqueue **23** key-mode `derive_broker_dailies` jobs (8 deribit, 8 mt5, 6 okx, 1 bybit; 7 owners) and each completed derive enqueues an allocator-scoped `derive_allocator_equity` compose job (between 7 and 23 of them, ~4 s each).

The July wedge is structurally closed for the interactive worker and PROD proves it: since the backfill service went live on 2026-10-02 every `derive_broker_dailies` / `derive_allocator_equity` claim came from 14 worker hosts that never claimed any other kind, and 17 other hosts claimed only other kinds. The Railway topology is read live: `quantalyze-analytics` has `WORKER_CLAIM_ROLE=interactive`, `quantalyze-analytics-backfill` has `WORKER_CLAIM_ROLE=backfill` with start command `python -m main_worker`, both 1 replica. Steps 0-3 of the FLIP runbook are therefore satisfied on PROD today; Step 4 (the E2GT-01 live gate) cannot run for this book (the harness does not support a Deribit key-mode allocator) and its premise (a legacy snapshot curve to fall back to) was removed by 167.1.2 plan 11; Step 5 is the fan-out itself; Step 6 is this phase.

The fan-out cannot wedge the interactive worker. It can still hurt the **backfill** worker in four bounded ways, none of which is a wedge of the July kind: (R1) a truly frozen backfill event loop is not restarted by anything, because Railway's healthcheck is deploy-time only; (R2) a batch of 5 claimed heavy jobs can exceed the 30-minute per-kind watchdog and cause a wasted re-crawl; (R3) the MT5 terminal lock is per-process and the backfill service is now a second process on the same gateway; (R4) onboarding derives queue behind the fan-out. The recommended plan is a one-off rehearsal tonight through the product's own fan-out function (off-hours, queue empty, measured), then registration, then the manifest re-capture in the same session.

**Primary recommendation:** Rehearse once now with `SELECT enqueue_derive_broker_dailies_for_allocator_keys();` (marker guard first, queue empty), read durations / reclaims / outcomes from `compute_jobs`, and only if clean register the cron with the Step 6 statement via `supabase db query --linked -f`, re-capture `scripts/prod-prober/cron-manifest.json` in the same session, and judge D-06 on `computed_at >= 05:30Z`, not on row existence.

### 1. What the fan-out enqueues today, which keys qualify, the compose chain

**Latest definition across all migrations.** `enqueue_derive_broker_dailies_for_allocator_keys` is defined exactly once, in `supabase/migrations/20260717233529_allocator_equity_derived_surface.sql`; no later migration re-creates it (`git grep -l` over `supabase/migrations`: only that file defines it; `supabase/schema/functions/enqueue_derive_broker_dailies_for_allocator_keys.sql` is the generated dump and names the same source migration). [VERIFIED: supabase/schema/functions/enqueue_derive_broker_dailies_for_allocator_keys.sql:5, :39-81]

The eligibility predicate, verbatim [VERIFIED: supabase/schema/functions/enqueue_derive_broker_dailies_for_allocator_keys.sql:56-62]:

```sql
      SELECT ak.id AS api_key_id
      FROM api_keys ak
      WHERE ak.is_active = TRUE
        AND ak.sync_status IS DISTINCT FROM 'revoked'
        AND ak.disconnected_at IS NULL
```

It is role- and venue-agnostic by design (pinned by `supabase/tests/test_derive_allocator_keys_fanout.sql` assertion 7: "this fan-out must stay exchange-agnostic"). Per key it calls `enqueue_compute_job(p_strategy_id := NULL, p_kind := 'derive_broker_dailies', p_idempotency_key := 'derive-dailies-' || key || '-' || today, p_api_key_id := key)` and swallows only `unique_violation` (lines 63-72). It takes a session advisory lock `hashtext('derive_broker_dailies_key_fanout')` and skips if held (lines 50-53). `REVOKE ALL ... FROM PUBLIC, anon, authenticated` (migration line 265); PROD: `has_function_privilege(...,'EXECUTE')` is true for the CLI role, function owner `postgres`, SECURITY DEFINER. [VERIFIED: PROD read-only SELECT 2026-10-07]

Behaviours that matter for planning:

- **`idempotency_key` is correlation only.** The queue migration says it is "NOT enforced at the DB level at all"; the only dedup is the in-flight partial unique index per `(api_key_id, kind)` over `pending`, `running`, `done_pending_children`. [VERIFIED: supabase/migrations/20260411144407_compute_jobs_queue.sql:163; supabase/schema/functions/_enqueue_compute_job_internal.sql:280-308] So the runbook sentence "one in-flight ... per key per day" (FLIP Step 5) is true only of in-flight rows: a second call after the first batch finished enqueues a second full crawl for every key. A one-off today followed by the cron tomorrow is two independent runs.
- **Priority is the column default `normal`.** `enqueue_compute_job` has no priority parameter (9 params, none for priority), so a fan-out job competes with interactive-class jobs on equal terms; the 123-RESEARCH recommendation "priority 'low' on the fan-out (defense in depth)" was never implemented. [VERIFIED: supabase/schema/functions/enqueue_compute_job.sql:25-33; supabase/migrations/20260428120836_compute_jobs_priority.sql: `priority TEXT NOT NULL DEFAULT 'normal'`]
- **All-or-nothing.** The loop runs inside one function call, so a non-`unique_violation` error (for example the `serialization_failure` "enqueue race lost" the internal function can raise) rolls back every enqueue of that run and shows up as a failed `cron.job_run_details` row. Probability is negligible at 05:30 (it needs a concurrent same-key enqueue that already finished), but the first-tick readback must check `status = 'succeeded'`. [VERIFIED: supabase/schema/functions/_enqueue_compute_job_internal.sql:410 `RAISE EXCEPTION 'enqueue race lost: ...' USING ERRCODE = 'serialization_failure'`]

**The compose chain and its refusal semantics** [VERIFIED: analytics-service/services/job_worker.py:11236 (`run_derive_allocator_equity_job`), the F1(b) block "INCOMPLETE compose", the empty-curve block, the upsert]:

- The compose reads the owner's eligible keys, per-key `csv_daily_returns` and `key_inputs:*` rows and calls `compose_allocator_equity`. - So the phase's success criterion is bounded by per-key derive success: an owner whose key fails permanently, or whose book is held earlier by `duplicate_account` / `key_not_syncing` / `account_identity_pending`, will not read `ready` from this phase alone. **Would today's daily fan-out wedge it? Verdict by worker.**

- **Interactive worker: no.** It excludes both derive kinds at claim time (`p_kind_exclude`), measured disjoint on PROD, and the 05:30 start is after the interactive window on 6 of the last 8 days. The only shared resources are the database (the fan-out SQL costs under 1 s) and the per-exchange API quota of keys that were polled ~90 minutes earlier.
- **Backfill worker: cannot reproduce the July wedge, but four residual risks exist.**
  - **R1, no automatic restart on a hard freeze.** The per-job heartbeat keeps healthz fresh while the loop turns, but Railway uses the healthcheck "only ... at the start of the deployment" and "does not monitor the healthcheck endpoint after the deployment has gone live". [CITED: docs.railway.com/deployments/healthchecks] That also explains the July "90 s auto-restart never fired": it never existed. The backfill service's restart policy is `ON_FAILURE`, max 3 retries, which covers process exit, not a frozen loop. A genuinely non-yielding hang would stall every derive job until someone restarts the service, and I found no automated alarm for backfill-queue staleness (absence not proven; treat as unknown, see A3). The mitigation inside this phase is the rehearsal plus the next-morning census; a recurring alarm is a follow-up.
  - **R2, batch-tail watchdog reclaim (code-read, not yet observed).** `dispatch_tick` claims 5 jobs at once (all stamped `claimed_at` = claim time) and runs them one after another. The per-kind watchdog resets any `running` `derive_broker_dailies` row whose `claimed_at` is older than 30 minutes, whether or not the worker has started it. Five deribit-sized jobs back to back are 5 x 472 s = 39 min, so the fifth can be reset while still waiting its turn; it then runs anyway, its `mark_compute_job_done` is ignored as preempted (`LATE_MARK_IGNORED`), and it is claimed and crawled again. Writes are idempotent so the result is correct but one full crawl is wasted and `attempts` climbs. All 23 jobs share one `next_attempt_at` (one transaction's `now()`), so the order inside the claim is unspecified. [VERIFIED: supabase/schema/functions/reset_stalled_compute_jobs.sql per-kind UPDATE `claimed_at < (now() - v_threshold)`; main_worker.py:358, :666, :804-821]
  - **R3, MT5 terminal serialization is per process, and there are now two processes on the one job gateway.** The terminal lease is an `asyncio.Lock` registry that "serializes the shared terminal only WITHIN one process's event loop", and the MT5 runbook pins the analytics service to a single replica because a second one "serializes nothing against the first". [VERIFIED: analytics-service/services/mt5_concurrency.py:257-274; docs/runbooks/mt5-go-live.md:131-146] The backfill service is such a second process: its `MT5_GATEWAY_HOST` / `MT5_GATEWAY_PORT` hash equal to the API service's (compared by sha, values not printed). The safety net is the login bracket (`assert_expected_login` before and after the read), which fails closed as a transient error, not silent corruption. Measured so far: 26 mt5 strategy-mode derives done and none failed on a login mismatch since the split; the 8 key-mode mt5 derives are a ~6 s each and run ~90 minutes after the interactive MT5 reads, but the API process's session monitor (a ~330 s cadence) can overlap them. Accept, and book it (TODOS currently carries only the D-33 replica note).
  - **R4, onboarding derives queue behind the fan-out.** A new key connected during the run enqueues its derive at the same priority and a later `next_attempt_at`, so it waits for all earlier jobs (up to ~1-2.6 h). Accepted, stated for the planner.

## Common Pitfalls

### Pitfall 1: the CLI hides the marker
**What goes wrong:** a marker query that is the first statement of a file is not shown; only the last statement returns. **How to avoid:** marker as a column of every read, a `DO` guard before every write, and a separate plain marker call recorded in the log. **Warning sign:** a transcript with no marker text.

### Pitfall 2: re-run is not idempotent after completion
**What goes wrong:** the "per-key per-day idempotency" in the runbook is only the in-flight index; a repeat after completion re-crawls every key. **How to avoid:** one rehearsal, then rely on the cron; do not repeat the function call casually. **Warning sign:** 46 derive rows in one UTC day.

### Pitfall 3: the first-run freshness trap
**What goes wrong:** after a rehearsal, v2 rows exist, so "count of v2 rows = owners" would pass without the cron ever having run. **How to avoid:** the `computed_at >= 05:30Z` filter. **Warning sign:** `v2_rows` > 0 with `v2_fresh_since_run` = 0.

### Pitfall 4: batch-tail reclaim
**What goes wrong:** the 5th job of a heavy batch is reset by the 30-minute watchdog before its turn, then crawled twice. **How to avoid:** read `reclaimed` in the rehearsal; take the batch-1 change if it is non-zero. **Warning sign:** `last_error = 'worker_stalled'`, `LATE_MARK_IGNORED` in the backfill logs.

### Pitfall 5: a frozen backfill worker looks fine until morning
**What goes wrong:** no automatic restart on a stale healthz (Railway healthchecks are deploy-time only). **How to avoid:** watch the queue and the claim census during the rehearsal and read the backlog query ~4 h after each run; restart the service by hand if open derive jobs stop moving. **Warning sign:** `oldest_open_age_s` growing with no new claims.

### Pitfall 6: version skew between the two services
**What goes wrong:** today the backfill service runs `239106dc5` while the API service's live container is `1af934872` with two newer deploys not yet live (one earlier deploy FAILED). Derive and compose code runs on the backfill service, so it carries the newer code; interactive code does not. **How to avoid:** P2 records both SHAs; do not rehearse while the API service is mid-deploy if that cannot be read as stable.

### Pitfall 7: drift noise between registration and manifest merge
Accepted by precedent, finite, and named; finish the same-session step.

### Pitfall 8: stale numbers in prose
CLAUDE.md bans restated constants; cite `BACKFILL_KINDS`, `TIMEOUT_PER_KIND` and `_BROKER_CRAWL_TIMEOUT_S` by symbol in the new runbook and re-read the values at execution.

### Job-outcome read (tested read-only)

```sql
SELECT (SELECT shobj_description(oid, 'pg_database') FROM pg_database WHERE datname = current_database()) AS which_database,
  kind, status, (api_key_id IS NOT NULL) AS key_mode, count(*) AS n,
  count(*) FILTER (WHERE last_error = 'worker_stalled' OR coalesce(reclaim_count,0) > 0) AS reclaimed,
  count(*) FILTER (WHERE last_error ILIKE '%wall-clock bound%' OR last_error ILIKE '%per-crawl%') AS crawl_bound_hits,
  coalesce(max(round(extract(epoch FROM (updated_at - claimed_at)))),0) AS max_run_s
FROM compute_jobs
WHERE kind IN ('derive_broker_dailies','derive_allocator_equity') AND created_at >= '<run start UTC>'
GROUP BY kind, status, (api_key_id IS NOT NULL) ORDER BY kind, status, 4;
```

### Backlog read (tested read-only)

```sql
SELECT (SELECT shobj_description(oid, 'pg_database') FROM pg_database WHERE datname = current_database()) AS which_database,
  (SELECT count(*) FROM compute_jobs WHERE status IN ('pending','running','failed_retry','done_pending_children')) AS open_jobs,
  (SELECT count(*) FROM compute_jobs WHERE status IN ('pending','running','failed_retry','done_pending_children') AND kind IN ('derive_broker_dailies','derive_allocator_equity')) AS open_derive_jobs,
  (SELECT coalesce(max(round(extract(epoch FROM (now() - created_at)))),0) FROM compute_jobs WHERE status IN ('pending','failed_retry')) AS oldest_open_age_s;
```

### Claim-census (role isolation proof, tested read-only)

```sql
WITH w AS (
  SELECT regexp_replace(claimed_by, '-[0-9]+$', '') AS host,
         bool_or(kind IN ('derive_broker_dailies','derive_allocator_equity')) AS ran_backfill_kind,
         bool_or(kind NOT IN ('derive_broker_dailies','derive_allocator_equity')) AS ran_other_kind,
         count(*) AS n
  FROM compute_jobs WHERE claimed_at > '<since>' AND claimed_by IS NOT NULL GROUP BY 1)
SELECT ran_backfill_kind, ran_other_kind, count(*) AS hosts, sum(n) AS jobs FROM w GROUP BY 1,2;
```
