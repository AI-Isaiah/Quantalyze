## Summary

Scope: the three code commits on `feat/167.1.2.2-derivecron`. They are the D-12 per-step self-check, the D-13/D-14 zero-start check with the new `inception_unreconciled` reason, and D-15, which stores the P&L of each dropped day in `key_inputs` and uses it in the compose replay. `src/` has no changes in this range. The phase test files pass at this sha (119 passed).

What holds, checked by reading the code and by re-running the code on synthetic books:

- **Backward roll with dropped-day P&L.** `equity[t-1] = (equity[t] - F_t - P_t)/(1+r_t)` (`allocator_equity_derive.py:967-969`) is the exact inverse of the writer's identity `NAV_t = NAV_{t-1}(1+r_t) + F_t` (`chain_linked_twr` puts the flow in the numerator, with end-of-day timing). On a dropped day `r_t` is absent, so the factor is 1 and the step is `NAV_{t-1} = NAV_t - P_t - F_t`. That matches `reconstruct_nav` and `level_day_pnl`. A pnl entry on a day that has a return row is ignored and counted, so nothing is counted twice.
- **The D-12 self-check is still a real check, but a narrow one.** It checks every step against the stored previous level (`:1143`). It catches a roll line that disagrees with the identity: a wrong-day flow, a wrong sign, or a missing P term. Removing the P term from either the roll or the check turns the D-15 level tests red. It cannot catch a wrong input, because both sides read the same `r`/`fbd`/`pnl` maps. See IN-02.
- **Opening invariant for a 2-day MT5 run.** `implied_start = equity[d0] - F[d0] - pnl[d0]`, where `equity[d0] = equity[d1] - F[d1] - pnl[d1]`. This is the capital before the first flow. A mutation that used the P&L of d1, or `opening_run[-1]`, turns `test_a_two_day_opening_run_reads_the_capital_before_its_first_flow` red.
- **Stitch ownership.** `stitch_dropped_day_pnl` uses the same rule as the flow branch of `stitch_shared_account`: `[own_first, next_first)`, plus the pre-window days of the first member. Both test clauses bite under mutation. The departed-key read sits inside the corrupt-input `try` (`job_worker.py:11789`), and so do all the other reads.
- **Payload compatibility.** An absent, `null` or empty field gives `{}`, and the replay is then byte-identical to D-13 (pinned). A malformed list, a bad day or a non-numeric amount raises an error the job disposes as permanent. Booleans and duplicate days do not raise (WR-02).
- **`FULL_HISTORY_VENUES` contains `mt5`.** The code supports it: `mt5_read.read_mt5_deal_ledger` fetches `history_deals_get` from epoch 0, and the combiner stamps `ledger_complete`. MT5 has no §5 gate, though, so this zero-start check is its only inception evidence. CR-01 shows the check does not measure inception on a key that holds an open position.
- **Oracles.** The `Book` fixture is built forward in exact `Fraction` arithmetic, and its guard rule is pinned against the real `chain_linked_twr`. The oracles are independent of the code under test. Every venue end-to-end test sets `account_equity == account_balance` / `terminal_upnl_native={}` and anchors on the last NAV day. That gap is where CR-01 lives.

**The executor's open risk is real, and it is a BLOCKER (CR-01).** I measured it. Take an account that started from exactly zero capital and holds an open position whose floating P&L is 0.01% of equity. It blocks as `inception_unreconciled`, on MT5 and on Deribit. On Deribit, a 1% index move between the last ledger day and the anchor read gives a residual of 3.1%.

## Critical Issues

### CR-01: The zero-start check compares the realized-basis roll against a full-equity anchor, so any open uPnL (and, on Deribit, any mark move after the last ledger day) reads as missing start capital

**File:** `analytics-service/services/allocator_equity_derive.py:956`, `:998-1009`; `analytics-service/services/job_worker.py:6116-6125`; writers at `analytics-service/services/nav_twr.py:898` and `analytics-service/services/native_nav.py:459`

**Issue:** The two writers do not roll from the same terminal level:

- **Writers (the stored returns and the stored dropped-day P&L).**
  - MT5 (`reconstruct_nav_and_twr`, `nav_twr.py:898`) rolls back from `terminal_nav = anchor - upnl`, which is the balance.
  - Deribit (`_roll_bucket`, `native_nav.py:459`) rolls back from `terminal_native - upnl_native` per currency, valued at the mark of the last ledger day.
- **Compose (the replay).**
  - The epilogue persists `anchor_usd = equity` (`job_worker.py:6116-6125`). On MT5 that is `account_info().equity`, which is balance plus floating uPnL. On Deribit it is `collapsed_equity_usd`, read now.
  - `replay_key_equity` pins that full figure on the last union day (`:956`) and rolls back through realized-basis returns.

Write `U` for the anchor mismatch: the uPnL wedge, plus on Deribit `E_native x (index_now - mark_last_ledger_day)` for coin held over a quiet tail. The replay then carries an error of `U / G(t->T)` at every level. With D-15 everything else is exact, so `implied_start` (`:998`) equals exactly that error at d0. The founder's 1e-4 band then judges the wedge, not the inception.

**Measured** with the test module's own zero-start oracle books, run through the real writers (`combine_mt5_deal_ledger` + `mt5_day_pnl`, `combine_native_ledger` + `native_ledger_day_pnl`) and the real `replay_key_equity`:

| book | U / equity | implied_start / L_first | verdict |
|---|---|---|---|
| funding+dominated, MT5 and Deribit (USDC) | 0 | -6.1e-16 | clean |
| same | 1e-5 | +3.4e-5 | clean |
| same | 1e-4 | +3.4e-4 | `inception_unreconciled` |
| same | 1e-2 | +3.4e-2 | `inception_unreconciled` |
| two-day-run, MT5 and Deribit | 1e-4 | +1.0e-4 | `inception_unreconciled` |
| BTC coin-margined (the test's own ledger) | uPnL 7.6e-5 of eq | +2.4e-4 | `inception_unreconciled` |
| BTC coin-margined, anchor index +1% vs last ledger mark | 0 | +3.1e-2 | `inception_unreconciled` |
| same, +10% | 0 | +2.4e-1 | `inception_unreconciled` |

Consequences:

1. **The check measures the wrong thing on both venues it was built for.**
   - On Deribit, D-15 makes `implied_start` equal `prev0_usd + U/G`. `prev0_usd` is what §5 already bounded, so the only new thing the compose check measures is the anchor mismatch.
   - On MT5 it is the only inception evidence, and it is dominated by `U`.
   - In the debug table, MT5 key F (+2.05%, no dropped interior day) and key E (+12.4%) fit a wedge at least as well as a funding-day P&L. D-15 will not unblock them if the cause is `U`.
2. **The verdict flaps.** It is a BLOCKING reason and depends on whether a position happens to be open at the moment of the derive. The same clean account reads trustworthy one day and untrustworthy the next, and the cron will re-derive daily.
3. **The levels are affected too.** Every early level is off by `U/G(t->T)` against the realized-basis NAV the writer used: 6,712 USD max at a 1% wedge on the funding+dominated book. This was true before D-15, but D-15's claim that the early levels are now exact holds only when `U = 0`.
4. **No test can see it.** Every end-to-end test passes `account_equity == account_balance` / `terminal_upnl_native={}` and anchors on the last NAV day.

**Fix:** Persist the writer's own terminal basis in `key_inputs` and roll the replay from it. Keep `anchor_usd` as the displayed current equity.

```python
# job_worker epilogue (key-mode, MT5 and Deribit NAV path), next to dropped_day_pnl:
_key_inputs_payload["anchor_realized_usd"] = float(nav_levels.iloc[-1])   # the level the writer rolled from
_key_inputs_payload["anchor_realized_day"] = nav_levels.index[-1].date().isoformat()
_key_inputs_payload["open_unrealized_usd"] = float(open_unrealized_usd)   # the wedge, for display/audit

# compose: replay from the realized terminal on its own day, then (optionally) add the
# wedge back on the curve's last point only. The zero-start check then reads prev0 exactly.
replay_key_equity(returns, flows, anchor_realized, history_reaches_inception=..., dropped_day_pnl=...)
```

Do this before treating any `inception_unreconciled` or `opening_flows_reconciled` verdict as evidence. The simpler alternative also works: have the derive persist its own `inception_residual_usd` (`prev0_usd` on Deribit, `NAV_d0 - pnl_d0 - F_d0` on MT5) and judge that against the band. Add an end-to-end test with `account_equity != account_balance` and one with `terminal_upnl_native != {}`. A book with a zero start must stay clean in both.

**File:** `analytics-service/services/allocator_equity_compose.py:189-197`, `:213-215`

- On 2026-02-03 (the flow-dominated day, P&L -700), the curve implies r = -0.3644%.

If the founder wants dropped days to stay non-returns in the KPIs, keep r = 0, but count those days under a named flag so the disagreement is visible. Pin it with a test asserting that `payload.returns` chained with the flows reproduces `payload.curve`.

### WR-02: `read_dropped_day_pnl` accepts boolean amounts and silently sums duplicate days

**File:** `analytics-service/services/allocator_equity_derive.py:1047-1052`

**Issue:** `float(row["pnl_usd"])` turns `true` into 1.0. `out[day] = out.get(day, 0.0) + amount` adds a duplicated day twice. **Fix:**

```python
out[day] = float(raw_amount)
```

Add both cases to `test_a_malformed_field_raises_rather_than_being_read_as_a_guess`.

### CR-01 - the replay rolls from the writer's realized terminal

Both routes the review named are the same fix here: the derive stores the writer's own terminal, and the replay rolls from it, so the inception residual `equity[d0] - F[d0] - pnl[d0]` is the writer's `prev0` rather than something the anchor can move. No separate residual field is stored (it would be derived data that could drift from the levels).

- **Stored (additive, key-mode MT5 and Deribit NAV paths only):** `realized_terminal_usd` and `realized_terminal_day`. MT5: the byte-identical `equity - (equity - balance)` that `reconstruct_nav_and_twr` rolls from, on the last NAV day of `mt5_day_pnl`. Deribit: the last USD NAV level of `_native_nav_levels` (`native_realized_terminal`, new, off the same levels as the returns), which is the native balance less terminal uPnL at the last ledger day's mark. `anchor_usd` is unchanged and stays the live equity. The open wedge is not stored: it is `anchor_usd - realized_terminal_usd` and storing it would only invite drift.
- **Replay:** `replay_key_equity(..., realized_terminal=(day, usd))`. When the day is the series' last day the roll starts from it; the forward self-check runs on the writer's levels; then the curve's last point is set to the live anchor. The wedge is therefore one step on the anchor day, never spread across history (the writers' own endpoint convention), and the zero-start verdict never sees it.
- **Old row (no fields):** behaves exactly as before (pinned). That behaviour is the defect, so it is pinned as what an old row does until the key's next derive rewrites it.
- **Terminal on another day than the series' last day** (the two writes are not atomic, so a compose between them can read a stale/fresh mix): the roll falls back to the anchor and the key degrades as `key_inputs_mismatch` (blocking), flag `realized_terminal_day_mismatch`.
- **Compose job:** reads the fields for live, departed and (not needed for) stitch-source keys; a malformed field is a permanent corrupt input like the neighbouring parses. A stitched account uses the counted (newest) key's terminal.
- **Known consequence, by the writers' own convention:** on the anchor day the curve moves by the wedge while `payload.returns` (the TWR) does not. The invariant "returns chained with flows reproduce the curve" therefore holds on every returned day except the final one when a position is open.
- **Cost:** a Deribit key derive now evaluates `_native_nav_levels` a third time (combine, day P&L, terminal). It is pure and vectorised; if it ever shows in a profile, the three can share one call.

### WR-01 - a dropped day is absent from `payload.returns`

`portfolio_returns` takes the per-key dropped days (a stored P&L on a day with no return row). That key-day sits out the day's sums, exactly as a key sits out the day it joins, and is counted under `missing_return_inside_coverage` (restored for dust and P&L-dominated days). A day on which no key has a defined return is absent, and is not counted as `skipped_nonpositive_denominator` (a different fact). The reader contract in `src/lib/queries.ts` (`extractTrustworthyDerivedSeries`: non-empty, strictly ascending, finite; no contiguity requirement) is unchanged, so no TS change was needed; the dashboard consumers read `{date, value}` arrays and a skipped day was already a possible shape.

**Decision recorded, for the founder to veto:** with several keys, a dropped key sits out and the day's book return is the capital-weighted mean over the keys that DO have a return, not an omitted day. The alternative (omit the whole book day if any key's return is undefined) loses more days in a multi-key book and skips the other keys' real move entirely. For a key whose dropped day is flow-dominated at a large prior level, the exclusion approximates; the key-day is counted and flagged either way.

The writer leaves key j's return on that day undefined, because `E_{j,t-1}` is not a base for that day's P&L (end-of-day flow convention: a deposit that dominates the prior NAV makes `P/E_{t-1}` meaningless). The two choices are:

- the other keys' TWR for that day, which drops only key j's P&L; or
- omitting the whole day, which drops every key's P&L.

The first is strictly less lossy. The next day's denominator does include key j's post-jump level, so nothing is double-counted. One consequence is real but recorded rather than hidden: the book's cumulative TWR leaves out key j's P&L for that day, under a non-blocking `missing_return_inside_coverage` flag. See R2-IN-01.

**Fixer judgment call 2: the last-day wedge step does not appear in `payload.returns`.** This is not a money-math defect for a reader of the curve. The curve's last point is the live equity, which is the correct current value of the money. The returns stay on the writer's realized TWR basis, which is the same basis as every venue factsheet's TWR. The factsheet KPIs and the Scenario own-book delta read the returns (`ScenarioComposer.tsx:4107-4120`), never curve ratios. So the KPIs are not moved by an open position that has not been realized, and that is the intended behaviour. What it does break is the invariant "returns chained with flows reproduce the curve" on the final day. None of the WR-01 tests exercises `realized_terminal`, so nothing pins it either way. See R2-IN-02.

#### R2-WR-01: KEY_INPUTS_MISMATCH has no self-heal when it comes from a read race (MEDIUM, confidence 6)

**Mechanism.**

- The derive writes `csv_daily_returns` (upsert, then reconcile delete), then the `key_inputs` row, then enqueues the compose (`job_worker.py:6535-6558` → epilogue `:6188` → `:6215`).
- The compose reads the csv rows first (`:11432`) and the `key_inputs` rows second (`:11539`).
- A compose that runs while a sibling key's derive is between those writes reads one half fresh and the other stale.
- After CR-01 this is detected on **every** derive that moves the last NAV day forward, which is nearly every daily derive. A stale row's `realized_terminal_day` is yesterday's last day while the csv already ends today, or the reverse. Either way `realized_terminal[0] != days[-1]` → `KEY_INPUTS_MISMATCH` (blocking).
- The sibling's own heal enqueue then hits `compute_jobs_one_inflight_per_kind_allocator`, whose predicate includes `'running'`. The enqueue is a benign no-op by design (`:6191-6196`).
- Take the case "old csv, new key_inputs": the sibling's `key_inputs` write lands inside the compose's t1..t2 read window, so its enqueue almost surely fires while the compose is still running. Nothing re-composes until the next derive of some key in that allocator. Under the daily cron that is the next 05:30 run.

**Why it matters here.**

- The book shows as untrustworthy, so the legacy fallback is used, for up to a day.
- D-06 judges success by counting version-2 trustworthy `equity_curve` rows within 24 h of the 05:30 run, and this race lowers that count.

Before round 1 the same race silently mis-levelled the curve and still read trustworthy. Blocking is the honest outcome, so the reason itself is right. What is missing is a way to recover from it.

**Fix (any one):**

- (a) When the only blocking reason is `KEY_INPUTS_MISMATCH`, end the compose job `transient`, with a bounded retry count, instead of persisting a blocking row. The queue's backoff then re-reads after the sibling's writes have landed. A truly structural mismatch still ends blocking once the retries run out.
- (b) Have the compose enqueue one follow-up compose after its own status leaves `running`.
- (c) Stamp one derive-run id into both the csv rows and the `key_inputs` payload, and have the compose re-read on disagreement.

Add a test that interleaves a sibling write between the two reads and asserts that the next compose is not dropped.

### R2-WR-01 - the compose no longer persists a blocking verdict for a read race

**Root cause.** Two non-atomic writes meet two non-atomic reads. The derive writes a key's returns, then its `key_inputs`; the compose read the returns, then the inputs; and when the pair disagreed the compose could not tell a derive that is mid-write from corruption, so it stored a blocking verdict whose only remedy (the sibling's compose request) is dropped while the compose is `running`. Round 1's CR-01 made the disagreement detectable on nearly every daily derive (the last NAV day moves), which is what turned a latent skew into a user-visible one.

**Fix, no migration, in two parts** (`analytics-service/services/job_worker.py`, `run_derive_allocator_equity_job`):

1. **Read order.** The `key_inputs` rows are read before the returns. The derive writes the returns first and the inputs last, so an inputs row that is visible to the compose implies its returns were already written when the compose reads them. The skew a race can leave is then one-sided: returns newer than the inputs. The opposite skew (inputs newer than the returns) can no longer come from a race, so it is a real inconsistency.
2. **Classification.** A counted key whose last stored return day is later than its `realized_terminal_day` is the mid-write state. On a non-final attempt the job ends `transient`: the queue's backoff (30 s, then 2 min) re-reads after the sibling's inputs have landed, no verdict is written and yesterday's stored curve row is left in place. On the last attempt (`attempts >= max_attempts`, default 3) the compose runs on what is stored and the replay's own check blocks it as `key_inputs_mismatch`, as before. Inputs newer than the returns are not retried and block at once.

**Why this and not the alternatives.**

- *(c) a derive-run id in both writes* needs the same two reads and a writer change in both the csv rows (a column, so a migration) and the inputs; the existing `realized_terminal_day` already is a version stamp of the only skew that matters here.
- *(b) a follow-up compose after the running one finishes* cannot be enqueued from inside the handler (the job is still `running`, so the in-flight index drops the request), and doing it right needs a dirty mark, which is a table or a column, so a migration. The retry achieves the follow-up through the queue instead: `failed_retry` is outside the predicate of `compute_jobs_one_inflight_per_kind_allocator`, so a request that arrives while this job waits is enqueued as its own pending twin (164.9.3, `20260927120000_claim_pair_pre_rank_exclusion.sql`) and is not lost.
- *(a) alone* (the reviewer's first option) would still leave the opposite skew reachable by a race, which is then indistinguishable from corruption and would be retried three times for nothing; the read order is what removes it.
- *Bound the returns by the terminal day and compose that* would silently publish a trustworthy book one day stale for that key and hide the mismatch; this repo's rule is to fail loud.

**A genuinely inconsistent pair still blocks**, and the tests show it: returns that stay newer than the inputs retry twice and then persist `key_inputs_mismatch` on the third attempt, and inputs newer than the returns persist it on the first.

**Recorded, not fixed (all pre-existing or outside the finding):**

- The race needs two workers touching one allocator. `derive_broker_dailies` and `derive_allocator_equity` are both in `BACKFILL_KINDS` and the backfill worker is one sequential process, so in steady state a compose and a sibling derive do not overlap; they can during a rolling deploy, a stalled-job reclaim, or a second worker started with role `all`. The finding's confidence of 6 is consistent with that. The fix costs nothing when there is no race.
- A key's very first derive (returns present, no `key_inputs` row yet) is the same family: the compose drops the key as `DROPPED_KEY` and the sibling's request can be dropped the same way. Retrying it would also retry every legacy key that has returns and never had an inputs row, so it was left as it was.
- A same-day re-derive that does not move the last NAV day can still leave a value-level skew between the returns and the inputs; nothing carries a version that would show it. It is unchanged from before CR-01.
- The general lost-update (a compose that read consistent but older data is `running` when a sibling's request arrives, so the request is dropped and that key is a day stale) is not closed. It does not make a book untrustworthy; closing it needs a dirty mark, so a migration, and was out of scope.
- A ccxt or sFOX key whose last NAV day has no stored return places its live anchor on an earlier day than it belongs to. That predates this round; the ccxt case now logs it.
- The retry consumes up to two of the job's three attempts, and a retried job shows as `failed_retry` for 30 s to 2 min with a counts-only message. No Sentry event is raised for it.
