## Summary

Scope: the three code commits on `feat/167.1.2.2-derivecron`. They are the D-12 per-step self-check, the D-13/D-14 zero-start check with the new `inception_unreconciled` reason, and D-15, which stores the P&L of each dropped day in `key_inputs` and uses it in the compose replay. `src/` has no changes in this range. The phase test files pass at this sha (119 passed).

What holds, checked by reading the code and by re-running the code on synthetic books:

- **Backward roll with dropped-day P&L.** `equity[t-1] = (equity[t] - F_t - P_t)/(1+r_t)` (`allocator_equity_derive.py:967-969`) is the exact inverse of the writer's identity `NAV_t = NAV_{t-1}(1+r_t) + F_t` (`chain_linked_twr` puts the flow in the numerator, with end-of-day timing). On a dropped day `r_t` is absent, so the factor is 1 and the step is `NAV_{t-1} = NAV_t - P_t - F_t`. That matches `reconstruct_nav` and `level_day_pnl`. A pnl entry on a day that has a return row is ignored and counted, so nothing is counted twice.
- **The D-12 self-check is still a real check, but a narrow one.** It checks every step against the stored previous level (`:1143`). It catches a roll line that disagrees with the identity: a wrong-day flow, a wrong sign, or a missing P term. Removing the P term from either the roll or the check turns the D-15 level tests red. It cannot catch a wrong input, because both sides read the same `r`/`fbd`/`pnl` maps. See IN-02.
- **Opening invariant for a 2-day MT5 run.** `implied_start = equity[d0] - F[d0] - pnl[d0]`, where `equity[d0] = equity[d1] - F[d1] - pnl[d1]`. This is the capital before the first flow. A mutation that used the P&L of d1, or `opening_run[-1]`, turns `test_a_two_day_opening_run_reads_the_capital_before_its_first_flow` red.
- **Stitch ownership.** `stitch_dropped_day_pnl` uses the same rule as the flow branch of `stitch_shared_account`: `[own_first, next_first)`, plus the pre-window days of the first member. Both test clauses bite under mutation. The departed-key read sits inside the corrupt-input `try` (`job_worker.py:11789`), and so do all the other reads.
- **Payload compatibility.** An absent, `null` or empty field gives `{}`, and the replay is then byte-identical to D-13 (pinned). A malformed list, a bad day or a non-numeric amount raises an error the job disposes as permanent. Booleans and duplicate days do not raise (WR-02).
- **`FULL_HISTORY_VENUES` contains `mt5`.** The code supports it: `mt5_read.read_mt5_deal_ledger` fetches `history_deals_get` from epoch 0, and the combiner stamps `ledger_complete`. MT5 has no §5 gate, though, so this zero-start check is its only inception evidence. CR-01 shows the check does not measure inception on a key that holds an open position.
- **Oracles.** The `Book` fixture is built forward in exact `Fraction` arithmetic, and its guard rule is pinned against the real `chain_linked_twr`. The oracles are independent of the code under test. Every venue end-to-end test sets `account_equity == account_balance` / `terminal_upnl_native={}` and anchors on the last NAV day. That gap is where CR-01 lives.

**The executor's open risk is real, and it is a BLOCKER (CR-01).** I measured it. Take an account that started from exactly zero capital and holds an open position whose floating P&L is 0.01% of equity. It blocks as `inception_unreconciled`, on MT5 and on Deribit. On Deribit, a 1% index move between the last ledger day and the anchor read gives a residual of 3.1%.

## Critical Issues

### CR-01: The zero-start check compares the realized-basis roll against a full-equity anchor, so any open uPnL (and, on Deribit, any mark move after the last ledger day) reads as missing start capital

**File:** `analytics-service/services/allocator_equity_derive.py:956`, `:998-1009`; `analytics-service/services/job_worker.py:6116-6125`; writers at `analytics-service/services/nav_twr.py:898` and `analytics-service/services/native_nav.py:459`

**Issue:** The two writers do not roll from the same terminal level:

- **Writers (the stored returns and the stored dropped-day P&L).**
  - MT5 (`reconstruct_nav_and_twr`, `nav_twr.py:898`) rolls back from `terminal_nav = anchor - upnl`, which is the balance.
  - Deribit (`_roll_bucket`, `native_nav.py:459`) rolls back from `terminal_native - upnl_native` per currency, valued at the mark of the last ledger day.
- **Compose (the replay).**
  - The epilogue persists `anchor_usd = equity` (`job_worker.py:6116-6125`). On MT5 that is `account_info().equity`, which is balance plus floating uPnL. On Deribit it is `collapsed_equity_usd`, read now.
  - `replay_key_equity` pins that full figure on the last union day (`:956`) and rolls back through realized-basis returns.

Write `U` for the anchor mismatch: the uPnL wedge, plus on Deribit `E_native x (index_now - mark_last_ledger_day)` for coin held over a quiet tail. The replay then carries an error of `U / G(t->T)` at every level. With D-15 everything else is exact, so `implied_start` (`:998`) equals exactly that error at d0. The founder's 1e-4 band then judges the wedge, not the inception.

**Measured** with the test module's own zero-start oracle books, run through the real writers (`combine_mt5_deal_ledger` + `mt5_day_pnl`, `combine_native_ledger` + `native_ledger_day_pnl`) and the real `replay_key_equity`:

| book | U / equity | implied_start / L_first | verdict |
|---|---|---|---|
| funding+dominated, MT5 and Deribit (USDC) | 0 | -6.1e-16 | clean |
| same | 1e-5 | +3.4e-5 | clean |
| same | 1e-4 | +3.4e-4 | `inception_unreconciled` |
| same | 1e-2 | +3.4e-2 | `inception_unreconciled` |
| two-day-run, MT5 and Deribit | 1e-4 | +1.0e-4 | `inception_unreconciled` |
| BTC coin-margined (the test's own ledger) | uPnL 7.6e-5 of eq | +2.4e-4 | `inception_unreconciled` |
| BTC coin-margined, anchor index +1% vs last ledger mark | 0 | +3.1e-2 | `inception_unreconciled` |
| same, +10% | 0 | +2.4e-1 | `inception_unreconciled` |

Consequences:

1. **The check measures the wrong thing on both venues it was built for.**
   - On Deribit, D-15 makes `implied_start` equal `prev0_usd + U/G`. `prev0_usd` is what §5 already bounded, so the only new thing the compose check measures is the anchor mismatch.
   - On MT5 it is the only inception evidence, and it is dominated by `U`.
   - In the debug table, MT5 key F (+2.05%, no dropped interior day) and key E (+12.4%) fit a wedge at least as well as a funding-day P&L. D-15 will not unblock them if the cause is `U`.
2. **The verdict flaps.** It is a BLOCKING reason and depends on whether a position happens to be open at the moment of the derive. The same clean account reads trustworthy one day and untrustworthy the next, and the cron will re-derive daily.
3. **The levels are affected too.** Every early level is off by `U/G(t->T)` against the realized-basis NAV the writer used: 6,712 USD max at a 1% wedge on the funding+dominated book. This was true before D-15, but D-15's claim that the early levels are now exact holds only when `U = 0`.
4. **No test can see it.** Every end-to-end test passes `account_equity == account_balance` / `terminal_upnl_native={}` and anchors on the last NAV day.

**Fix:** Persist the writer's own terminal basis in `key_inputs` and roll the replay from it. Keep `anchor_usd` as the displayed current equity.

```python
# job_worker epilogue (key-mode, MT5 and Deribit NAV path), next to dropped_day_pnl:
_key_inputs_payload["anchor_realized_usd"] = float(nav_levels.iloc[-1])   # the level the writer rolled from
_key_inputs_payload["anchor_realized_day"] = nav_levels.index[-1].date().isoformat()
_key_inputs_payload["open_unrealized_usd"] = float(open_unrealized_usd)   # the wedge, for display/audit

# compose: replay from the realized terminal on its own day, then (optionally) add the
# wedge back on the curve's last point only. The zero-start check then reads prev0 exactly.
replay_key_equity(returns, flows, anchor_realized, history_reaches_inception=..., dropped_day_pnl=...)
```

Do this before treating any `inception_unreconciled` or `opening_flows_reconciled` verdict as evidence. The simpler alternative also works: have the derive persist its own `inception_residual_usd` (`prev0_usd` on Deribit, `NAV_d0 - pnl_d0 - F_d0` on MT5) and judge that against the band. Add an end-to-end test with `account_equity != account_balance` and one with `terminal_upnl_native != {}`. A book with a zero start must stay clean in both.

## Warnings

### WR-01: The curve now carries the dropped-day P&L, but the D-06 book returns (which the factsheet KPIs read) still say r = 0 on that day

**File:** `analytics-service/services/allocator_equity_compose.py:189-197`, `:213-215`

**Issue:** D-15 adds each dropped day to the key's level series, and its P&L is inside the level jump. `portfolio_returns._return_on` still returns `0.0` for any day without a stored return row. Measured with `compose_allocator_equity` on the test's own funding+dominated book, single key:

- On 2026-02-03 (the flow-dominated day, P&L -700), the curve implies r = -0.3644%.
- `payload.returns` says `r = 0.0`.
- The payload reads `is_trustworthy: true`.

`src/lib/queries.ts:2894` documents that the factsheet KPIs and the Scenario own-book delta read `payload.returns`, "never ratios of `equityDailyPoints`". So the curve and the KPIs in one trustworthy payload now disagree, on exactly the days D-15 was written to fix.

There is a second effect on the dust and pnl-dominated dropped days that are not flow days. Before D-15 they had no level, so they were counted under `missing_return_inside_coverage` (`:213-215`). Now they have a level, so the flag no longer fires, and they are still read as r = 0. The one signal that marked those days is gone.

**Fix:** Pass the per-key dropped-day P&L into `portfolio_returns`. On a day with a level, no return row and a stored P&L, use `r = P_t / E_{t-1}`: this is the same end-of-day identity, and it is well defined whenever `E_{t-1} > 0`. If the founder wants dropped days to stay non-returns in the KPIs, keep r = 0, but count those days under a named flag so the disagreement is visible. Pin it with a test asserting that `payload.returns` chained with the flows reproduces `payload.curve`.

### WR-02: `read_dropped_day_pnl` accepts boolean amounts and silently sums duplicate days

**File:** `analytics-service/services/allocator_equity_derive.py:1047-1052`

**Issue:** `float(row["pnl_usd"])` turns `true` into 1.0. `out[day] = out.get(day, 0.0) + amount` adds a duplicated day twice. The docstring promises that a malformed field raises instead of being read as a guess. This repo already fixed the bool case on the flow channel (`_fold_mt5_deals` WR-01: "`float(True) == 1.0` ... silently folded"). The writer never emits a duplicate, so a duplicate is corruption, and it would move every earlier level by that amount.

**Fix:**

```python
raw_amount = row["pnl_usd"]
if isinstance(raw_amount, bool) or not isinstance(raw_amount, (int, float)):
    raise TypeError("key_inputs dropped_day_pnl: non-numeric amount")
if day in out:
    raise ValueError("key_inputs dropped_day_pnl: duplicate day")
out[day] = float(raw_amount)
```

Add both cases to `test_a_malformed_field_raises_rather_than_being_read_as_a_guess`.

### IN-02: The per-step self-check only tests the roll line against itself

**File:** `analytics-service/services/allocator_equity_derive.py:1141-1150`
**Issue:**
- The check rebuilds `vals[t]` from `vals[t-1]`, which the roll derived from `vals[t]` using the same maps. A wrong `_flows_by_day` or `_dropped_pnl_by_day` is invisible to it. The debug file accepts this.
- The teeth tests inject defects into a local `_roll`, not into `replay_key_equity`, and none of them covers the `P_t` term directly.
- The absolute floor of 1e-6 is below float cancellation once `|F_t|` reaches about 1e10 USD.
**Fix:** Add a teeth case with a wrong-day `P_t`. Consider scaling the band by `max(|vals[t]|, |vals[t-1]*(1+r)|, |F_t|)`.

### IN-03: A non-finite dropped-day P&L raises inside the epilogue after the series write

**File:** `analytics-service/services/job_worker.py:6138-6143` (called at `:6558`, after the `csv_daily_returns` upsert)
**Issue:** `dropped_day_pnl_payload` raises `NavReconstructionError` outside any typed disposition, so the per-key series is written while `key_inputs` stays stale. In practice this is unreachable, because the levels were already coerced. The flow channel's M1 pattern of skipping, counting and nulling the anchor is the house style.
**Fix:** Compute the payload before the series write, or null the anchor with a reason, as the flows do.

### IN-04: A stitched account mixes old and new `key_inputs` rows without saying so

**File:** `analytics-service/services/job_worker.py:11853-11858`
**Issue:** If a source member's row predates D-15, `source_dropped_pnl.get(k, {})` reads that member's owned dropped days, the account's funding day included, as flat, with no flag. The result fails toward blocking (`inception_unreconciled`), so it is not silent trust.
**Fix:** Count members with no `dropped_day_pnl` field in a flag.

### IN-05: A non-flow dropped day just before the first return day breaks the opening run

**File:** `analytics-service/services/allocator_equity_derive.py:1104-1115`
**Issue:** `_opening_flow_run` walks back over flow days only. A dropped day just before the first return day, for example a day below the dust floor, now carries a stored P&L that makes the zero-start check computable. It still turns the opening deposit into a BLOCKING `OUT_OF_WINDOW_FLOW`. This matches D-13 as written, and it is an edge case.
**Fix:** Walk over flow days and stored dropped-P&L days alike, or leave it as is and record the edge.
