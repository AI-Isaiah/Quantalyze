### WR-01 [MEDIUM, confidence 9]: `heal_series=False` on the new final-attempt stamp is not pinned by any test

**File:** `analytics-service/services/job_worker.py:5216-5218` (the call); `analytics-service/tests/test_mt5_derive_branch.py:706-746` (`test_unsettled_history_on_the_final_attempt_stamps_the_cause_sentence`)

**Issue:** The focus list names `heal_series=False`. CONTEXT and the arm's own comment justify it ("a late history is no reason to delete persisted basis series"). The default is `True`, and `True` makes `_heal_delete_basis_series` DELETE both `strategy_analytics_series` rows through `persist_basis_series(..., result=None)`. No test notices if the keyword is dropped:

- The final-attempt test asserts exactly one `strategy_analytics` upsert and no `csv_daily_returns` upsert. It never reads `capture["deletes"]`, even though `_build_ctx` records deletes at `test_mt5_derive_branch.py:273-274`.
- `TestF4CollapseDidNotAddDeletes` in `test_derive_silent_failure_f1_f4_f7.py` covers only the two pre-existing opt-out sites.
- `grep -rl heal_series analytics-service/tests src` finds that one file and nothing else.

**Measured:** In a scratch copy I changed the call to `heal_series=True` and ran `test_mt5_derive_branch.py`, `test_derive_silent_failure_f1_f4_f7.py` and `test_stamp_io_exhaustive.py`: **162 passed, 0 failed.**

**Failure scenario:** A later edit drops the keyword, which is easy to do because the call is two lines and the default sits on the closure signature. Then a re-sync of a published MT5 strategy whose history does not settle by attempt 3 deletes both persisted basis series. A `ledger-refresh-repair` run is deliberately unprotected by D-15, so a repair would delete them too. CI stays green. This is the destructive-DELETE class that F4 exists to fence, and the project rule says a data-integrity gate must be able to fail.

**Fix:** In the final-attempt test, assert the delete set:

```python
    assert "strategy_analytics_series" not in capture["deletes"], (
        "the history-unsettled stamp deleted persisted basis series; "
        "it must pass heal_series=False (F4)"
    )
```

Then run the neuter (`heal_series=True`), confirm RED by name, and restore from a byte backup. A better long-term fix is to add this site as a third case to `TestF4CollapseDidNotAddDeletes`, so the F4 census names every opt-out.

### WR-03 [LOW, confidence 5]: the final-attempt stamp also clears `metrics_json_by_basis` and overwrites `data_quality_flags` on a previously published, unmarked row

**File:** `analytics-service/services/job_worker.py:5216-5218`, which reaches the LOUD payload at `job_worker.py:3942-3958`

**Issue:** Before this phase the arm wrote nothing. A `failed_final` changed only what the bridge writes: `computation_status='failed'` plus `computation_error_copy`. Now the final attempt goes through the closure's LOUD path for any strategy that is not D-15 protected. That path is:

- a user-initiated re-sync of a live strategy, or
- a `ledger-refresh-repair` run, which is deliberately unprotected, or
- a marked refresh whose live-state read says not-present.

The LOUD path also writes `metrics_json_by_basis: None`, `computation_warned: False` and `data_quality_flags: {"csv_source": True}`, the last of which replaces the whole jsonb. `heal_series=False` keeps the series rows, but the by-basis metrics object and every other data-quality flag are lost until the next successful compute.

The arm's original rationale, kept as lineage, was "never a user-attributed 'failed' row for a fault that is neither the key's nor the strategy's". D-06 reverses that for the wizard. The collateral on already-published strategies is not mentioned in CONTEXT or in the plan 04 SUMMARY's Known limits.

**Failure scenario:** A funded, published MT5 strategy is re-synced from the account surface. Another key held the terminal in between, so the read is fresh, and the history does not settle within 3 attempts. The row loses `metrics_json_by_basis` and its non-CSV `data_quality_flags`. The bridge alone would have flipped only the status and the error text.

**Fix:** This is a design choice, so pick one of two options and record it:

- (a) Accept it and add a Known-limits line (plus a CONTEXT note under the deviation policy).
- (b) Pass a flag that skips the authoritative clear for this cause. Note that this widens the closure's CR-02 single-choke-point surface, which the publish-guard gates police, so (a) is the cheaper honest answer.

### WR-04 [LOW, confidence 4]: the GATE_HISTORY_NOT_SETTLED copy can be false where the history never settles

**File:** `src/lib/wizardErrors.ts` (`GATE_HISTORY_NOT_SETTLED`, around line 2968); `analytics-service/services/job_worker.py:342-346` (`_MT5_HISTORY_UNSETTLED_USER_SENTENCE`)

**Issue:** `Mt5HistoryUnsettledError` (`services/mt5_read.py:183-212`) is raised in two cases:

- the deal count is stable at zero under material equity, or
- the count does not hold equal across `_MT5_HISTORY_STABLE_INTERVALS` full intervals within the wait.

Neither case proves that the broker is "still sending". Two cases are recorded or plausible:

- **A funded account with a truly empty ledger.** This is D-16's accepted consequence, noted at `job_worker.py` in the same arm. A broker that archives old deals would produce it.
- **An actively trading account** whose deal count changes every poll interval, for example an EA.

Both fail every Retry identically. The card's title, "Your broker is still sending this account's history.", and "Nothing is wrong with your key" plus "Retry the sync in a few minutes" then promise a recovery that never comes. The second fix line ("If it fails again, send the correlation id…") limits the damage.

**Fix:** Soften the title to something true in every arm, for example "This account's history was not complete when we read it." Or name the repeat case explicitly in a fix line, for example "If it fails the same way twice, the history may not arrive on its own: send the correlation id …". Keep the Python and TypeScript sentences byte-equal; the parity pin enforces that.

### WR-05 [LOW, confidence 5]: "briefly busy … try again in a minute" is false in the documented persistent owed-scrub state

**File:** `src/lib/wizardErrors.ts` (`KEY_MT5_TERMINAL_BUSY`, around line 2050); `analytics-service/services/closed_sets.py:135-138` (`MT5_TERMINAL_BUSY_DETAIL`); emitter at `analytics-service/routers/exchange.py:1122-1142`

**Issue:** The owed-gate comment at `exchange.py` (the "Residue, stated" paragraph just above `if mt5_scrub_owed(...)`) records that while the scrub keeps failing, every wizard validation is refused here. Causes include the house credential being unset or wrong, or the terminal being unreachable. In that state:

- The title "briefly busy" and the fix "Try again in a minute" are false for as long as an operator has not acted.
- The code is deliberately not paged at the route.
- The only operator signal is `report_scrub_owed_refusal`. It emits ERROR plus a windowed capture only when no scrub was already pending, and a WARNING without a capture otherwise.

The plan 02 SUMMARY argues the copy is "true at both emitters" with respect to who holds the terminal. It does not test it against duration.

**Failure scenario:** The house credential is rotated without updating the analytics env. Every MT5 key a user submits gets "briefly busy, try again in a minute", indefinitely. Only the third-tier line ("If it is still busy after several tries…") points them anywhere.

**Fix:** Either make the title duration-neutral, for example "Our MetaTrader terminal could not take this check.", and keep "Try again in a minute" as the first remedy, or add a test that pins `report_scrub_owed_refusal`'s ERROR-plus-capture on a repeated scrub failure, so the stuck state is provably paged even though the card does not claim it.
