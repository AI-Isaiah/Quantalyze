## Summary

The three failures are cheap to separate on the Python side and the pins are all machine-checked, so the work is mostly mechanical and the existing 164.6.6.3 `MT5_SERVER_UNKNOWN` mint is a near-exact template. Three facts change the plan the ROADMAP implies, and the planner must start from them.

**(1) The "five emitters" is a cause count, not a raise-site count.** At HEAD `analytics-service/routers/exchange.py` has exactly FOUR `raise service_error(500, "MT5_GATEWAY_UNCONFIGURED", ...)` sites (an `ast` census, Finding 1). Three are env gaps and move to the new code; one (D-31 `undetermined`) stays. The "port-malformed" case is not a separate site: `read_env_validation_gateway_endpoint()` returns `None` for an unset host, an unset port, a non-integer port and a non-private host, and one raise site (`:533`) answers all four. Do not hunt for a fifth site. The worker twin raises a configuration `RuntimeError`, which is not a wire code and needs no change.

**(2) D-03's carrier does not reach the browser, so "copy only" is not yet buildable.** `compute_jobs.last_error` is redacted by the RPC the wizard's progress route uses (`NULL::TEXT AS last_error`), the route projects only `{jobStatus, stalled, memberProgress}`, the user-visible `computation_error` is one of four fixed per-kind sentences (and `transient` shares one sentence with `unknown`), and `SyncPreviewStep` sets `GATE_ANALYTICS_FAILED` for ANY `failed` status without reading anything else. The backfill half (`_MT5_BACKFILL_MESSAGES["history_unsettled"]`) has no wizard surface at all. A cause-specific carrier exists WITHOUT a migration and WITHOUT a new `error_kind` (the 164.2 provenance stamp, Option C2 below), but it needs a founder confirmation because 164.6.6.3 deliberately chose "no failed-analytics stamp". This is OQ-1.

**(3) The new env-gap code silently un-pages Sentry unless it joins `OUR_DEFECT_KEY_ERROR_CODES`.** The set pages on `SEAM_INTERNAL_FAULT`; moving three emitters onto a new wizard code drops them out of it. 164.6.5 recorded exactly this regression class. Also, the "we have been alerted" claim in D-01 is substantiated at two of the three env-gap emitters (an explicit alert / capture) and NOT at the IPC-inversion emitter (log only), so a capture must be added there or the copy lies at that arm.

**Primary recommendation:** Mint three Python/TS vocabulary items exactly as 164.6.6.3 minted `MT5_SERVER_UNKNOWN` (emitter, STATUS_CONTRACT row, contract fixture case, `VENUE_WIRE_CODE_TO_VERDICT` row, union + copy entry, three roster admissions, census pins, a test per emitter), keep the D-31 site and its four tests on `MT5_GATEWAY_UNCONFIGURED`, and get the founder's answer to OQ-1 before planning the history-not-settled task.

### Finding 3: the history-not-settled path, and why D-03's carrier has a gap

[VERIFIED by reading each file named.]

**Where the failure is produced.**
- Derive: `except Mt5HistoryUnsettledError as exc:` at `services/job_worker.py:5140` returns `DispatchResult(outcome=DispatchOutcome.FAILED, error_message=_MT5_HISTORY_UNSETTLED_MESSAGE, error_kind="transient")` (`:5176-5181`). The constant is at `:327`: `"derive_broker_dailies: the MT5 deal history had not settled within its wait budget — retrying"`. The arm logs at ERROR and makes NO failed-analytics stamp and NO terminal restart (comment `:5143-5162`).
- Backfill: `equity_reconstruction.py:3147` `return _fail("history_unsettled", "transient")`; message table `_MT5_BACKFILL_MESSAGES` at `:2751`, key at `:2783`: `"reconstruct_allocator_history: the MT5 deal history had not settled within its wait budget — retrying"`.

**What reaches a wizard, measured.**
1. `compute_jobs.error_kind` is `transient`; `mark_compute_job_failed` terminalises a transient only when `v_attempts >= v_max_attempts` (default `max_attempts INTEGER NOT NULL DEFAULT 3`, `supabase/migrations/20260411144407*.sql:122`). Before that the job is `failed_retry`, which the wizard treats as in-flight.
2. At `failed_final` the status bridge writes `strategy_analytics.computation_status = 'failed'` and `computation_error = computation_error_copy(error_kind)`. `computation_error_copy` has four distinct literals; `'transient'` and `'unknown'` SHARE `'Analytics could not complete after several automatic retries. Retry the sync, or contact support if it keeps failing.'` (`supabase/migrations/20260826120000_computation_error_curated_copy.sql:291-294`). It is defined only there (only that file and `20260826140000` match `FUNCTION computation_error_copy` / `get_user_compute_jobs` among the latest migrations).
3. The poller reads `computation_status, computation_error, computed_at` (`src/hooks/useStrategySyncPoller.ts:195`). `SyncPreviewStep.onTerminal` does `if (nextStatus === "failed") { ... setErrorCode("GATE_ANALYTICS_FAILED"); ... return "done"; }` (`src/app/(dashboard)/strategies/new/wizard/steps/SyncPreviewStep.tsx:1393-1401`) before any other read. This arm is shared by single-key and composite.
4. `gateFailureToWizardError("ANALYTICS_FAILED")` also returns `"GATE_ANALYTICS_FAILED"` (`wizardErrors.ts:4658-4659`). The copy is at `wizardErrors.ts:2829-2840`: `cause: "The analytics step failed for this draft. We cannot tell from here how much of the sync before it completed. The fault is in our pipeline, not at your exchange."`
5. `compute_jobs.last_error` (where `_MT5_HISTORY_UNSETTLED_MESSAGE` lands) is redacted by the only user-readable RPC: `NULL::TEXT AS last_error,   -- redacted` (`supabase/migrations/20260826140000_compute_jobs_error_kind_orphaned.sql:341`). The sync-progress route projects only `{ jobStatus, stalled, memberProgress[, otherJobInFlight] }` (`src/app/api/strategies/[id]/sync-progress/route.ts:298-300`). `error_kind` IS in the RPC row (`...140000.sql:315,342`) and `deriveComputeState` already coerces it to `{ state: "failed"; errorKind }` (`src/lib/compute-state.ts:437,550`), but neither the route nor `SyncPreviewStep` reads it.
6. The backfill message has no wizard consumer: `grep -rn reconstruct_allocator_history src` finds only a kind-check test (`src/__tests__/compute-jobs-kind-check-csv-2026-05-25.test.ts`). There is no wizard copy to write for it; it stays an operator-side message.

**The gap, stated plainly.** Neither the message nor the kind-plus-cause survives to the browser. `error_kind="transient"` alone is also emitted by timeouts, bridge blips and IPC faults, so a card saying "the broker is still sending your history" keyed only on `transient` would be false at those emitters, which is the exact defect class this repo's copy-honesty guard exists to stop (`wizardErrors.ts:940-946`: take the member "every one of whose claims is true at EVERY emitter").

## Common Pitfalls

### Pitfall 1: Moving D-31 by accident, or leaving an env gap behind
**What goes wrong:** the card says "not set up" for a terminal that ran and refused to classify, or an env gap keeps rendering `SEAM_INTERNAL_FAULT`.
**Why:** four sites share one literal and one detail string.
**How to avoid:** edit `:533`, `:573`, `:727` only. Keep `:1200`. Keep the four D-31 tests listed in Finding 4 on the old code; they are the control.
**Warning signs:** `BOTH SHAPES` assertion red (`derived.has("MT5_GATEWAY_UNCONFIGURED")` false).

### Pitfall 2: The env-gap code silently stops paging
**What goes wrong:** `OUR_DEFECT_KEY_ERROR_CODES` contains `SEAM_INTERNAL_FAULT`, which today covers E1-E3 (its member comment names `MT5_GATEWAY_UNCONFIGURED` explicitly, `wizardErrors.ts:5615-5618`). **How to avoid:** add the env-gap wizard code to the set, and clone the three `[164.6.5 WR-06]` route tests (`create-with-key/route.test.ts:3466`, `composite/add-key/route.test.ts:~1483`, `rotate-secret/route.test.ts:~740`) with `captureToSentry` asserted. Busy and history stay out: a held lease is contention, not our defect.
**Warning signs:** none automatic. Only the cloned tests catch it.

### Pitfall 3: "We have been alerted" is true at two env-gap emitters out of three
**What goes wrong:** E3 (`:727`) logs an ERROR and nothing else. Whether an ERROR log becomes a Sentry event depends on the SDK's default logging integration [ASSUMED: sentry-sdk's default `LoggingIntegration` turns ERROR logs into events; `sentry_init.py` only mentions it in scrubbing comments at `:267`, `:301`, and sets no `event_level`]. If the founder prefers not to touch E3, drop "we have been alerted" from the copy instead and drop the exemption.

### Pitfall 4: The three roster rows and the one pin that fails silently
