<domain>
## Phase Boundary

Two independent halves.

- **Code half.** Every standard-deviation divisor outside `services/metrics.py` that still tests for
  exact zero moves to Phase 166's relative dispersion floor, and so does every correlation site that
  divides by a leg's standard deviation without any guard. Each gets a red test built from a
  compounding-NAV constant yield.
- **Recompute half.** Every PRODUCTION `strategy_analytics` row that Phase 166 changes, and that was
  computed before the 166 worker deploy, is recomputed through the normal compute-job path, one
  strategy at a time, with a before/after check per row.

Out of scope: any migration; any change to `services/metrics.py` behaviour (it only re-imports the
moved floor); any TS change; `strategy_verifications.metrics_snapshot` rows (D-11).

⛔ **CORRECTED 2026-09-25 (plan-check revision, D-15).** "Any TS change" is no longer out of scope, and
the premise behind it was false. The TS side does NOT only read stored values: at least twenty sites
under `src/` compute a Sharpe, a correlation, a beta, an information ratio, a skew or kurtosis, a
diversification ratio or a risk share from daily returns behind a `> 0` / `!== 0` guard, or behind a
relative-only floor that misses the compounding-NAV residue (measured in Node 2026-09-25: residue sd
about 1.3e-16, Sharpe 1.5e12 to 3.5e14). They are in scope under D-15. What stays out of scope in TS
is any change to the CSV sentinel's rule name or label (D-04) and any change to how a renderer shows
a null. The sentence above is kept as lineage.

</domain>

### Code half

- **D-02 (2026-09-25, orchestrator, OQ1; reversible: a revert of one task).** The unguarded
  correlation sites are folded into plan 01 as their own task. Reason: the same root cause as the
  exact-zero guards (a ratio over a residue standard deviation), Phase 166 round 2 already fixed the
  `metrics.py` siblings for exactly this reason, and the repo rule is to close the whole class rather
  than park it. The research named six sites. The planner's re-grep of `.corr(` / `corrwith` over
  `services/` and `routers/` found **two more**, both `corrwith` matching sites
  (`strategy_matching.find_matched_strategy` and the `verify_strategy` matching block in
  `routers/portfolio.py`). They are the same class and are included. A dated note in ROADMAP
  `### Phase 166.1` records that criterion 3 now covers correlation sites too.
  ⭐ **Amended 2026-09-25 (plan-check revision, B3).** The correlation class C1-C8 is its own plan,
  `166.1-03`, in wave 2 after plan 01, instead of a task inside plan 01. Plan 01 was over budget with
  it. The scope is unchanged.
- **D-03 (2026-09-25, orchestrator, ratifying research A3; reversible).** One new leaf module,
  `analytics-service/services/dispersion.py`, holds Phase 166's floor as the single source:
  `DISPERSION_RESIDUE_REL`, `residue_floor`, `dispersion_is_residue` and `dispersion_is_real`, moved
  verbatim with their docblocks. `services/metrics.py` re-binds them under the old private names
  (`_DISPERSION_RESIDUE_REL`, `_residue_floor`, `_dispersion_is_residue`, `_dispersion_is_real`), so
  metrics behaviour and every existing test attribute stay byte-identical. Reason: `optimizer.py` is
  declared PURE, and `csv_validator.py`, `optimizer.py` and `allocated_capital.py` must not import
  quantstats and scipy through `services.metrics`. The same module carries the two small correlation
  helpers D-02 needs (a pairwise correlation that returns None unless both legs really disperse, and a
  `corrwith` restricted to dispersing columns), so the class has one implementation.
- **D-04 (2026-09-25, orchestrator, ratifying the researcher's S3 call; reversible: one conditional).**
  The CSV Sharpe sentinel keeps REJECTING a constant positive series, but no longer prints the
  fabricated ~1e15 number. A residue series with a mean above the risk-free rate gets the same
  `daily_sharpe_sentinel` rule with a message that names no number. A residue series at or below the
  risk-free rate gets no error (today's all-zero path). Real dispersion keeps today's code. No TS
  change: the rule name and its label are untouched. Reason: accepting the upload would flip a
  user-facing verdict; the number is the only fabrication.
- **D-05 (2026-09-25, orchestrator, ratifying research A2 row S7; reversible).**
  `portfolio_risk.compute_risk_decomposition` is in scope although the ROADMAP list omits it. It is an
  exact-zero guard of the same class and splits a residue portfolio volatility 48.6% / 51.4%.
- **D-06 (2026-09-25, orchestrator; reversible).** `optimizer.optimize_weights` is RE-POINTED to the
  shared floor. Its test is an honest PIN, not a red test: its old absolute `<= 1e-12` gate equals the
  new floor for any `|mean| <= 1`, so the test cannot go red against today's code. The drill neuters
  the gate to `== 0` instead, and the SUMMARY says so.
- **D-07 (2026-09-25, planner discretion; reversible).** The test invariant for every fixed site is:
  a compounding-NAV constant yield produces EXACTLY the output that an exactly-constant (all-zero)
  series of the same length produces today at that site. That makes each fix a statement about
  economics (no dispersion means no ratio), not about the implementation. A cent-rounded NAV (real
  quantisation dispersion) is the control on the other side of the floor, so widening the floor goes
  red. Because every fixed site then emits only an output shape it already emits for an exactly
  constant input, no new shape reaches any TS reader.

### Recompute half

- **D-08 (2026-09-25, orchestrator, OQ2; reversible per row: a later natural derive supersedes it).**
  Single-key broker strategies recompute through `compute_analytics_from_csv` ALONE, from the stored
  `csv_daily_returns`: no venue call, the input held fixed, so the before/after comparison is
  meaningful. Recorded residual: the `metrics_json_by_basis` mark-to-market PSR on those rows stays
  pre-fix until the strategy's next natural derive (persisted-only, no reader under `src/`).
- **D-09 (2026-09-25, orchestrator, OQ3; reversible).** A composite in the set (a strategy with any
  `strategy_keys` row) is recomputed ONLY through `stitch_composite`, never `compute_analytics_from_csv`
  (which NULLs `metrics_json_by_basis` on a composite). A composite with an untrusted member key
  (`sync_status` in `revoked` / `sign_in_failed`, or `disconnected_at` set) is not enqueued; it is a
  recorded residual.
- **D-10 (2026-09-25, orchestrator; one-way per enqueue, so every enqueue is a founder step).** No
  agent runs SQL against PROD, or any remote database. Every PROD statement is a founder step written
  out verbatim in plan 02, read-only except the enqueue. The database marker query from CLAUDE.md
  runs first. One tracer strategy is enqueued and watched to a terminal status with the full
  before/after check before any other; the rest go one at a time. Each enqueue carries the metadata
  `source` label `qstats-recompute-166.1`. The protected `ledger-refresh` marker is never used.
  Precondition: the Railway worker runs a commit at or after the 166 merge `bb31564f9`.
- **D-11 (2026-09-25, researcher, ratified; not reversible without rewriting an audit record, which is
  the reason it is not done).** `strategy_verifications.metrics_snapshot` is a point-in-time record of
  a verification run. A residue Sharpe captured there before the fix is historical and is NOT
  recomputed.
- **D-12 (2026-09-25, orchestrator; reversible).** The repo is public. `.planning/` records counts and
  anonymised row labels (R1..Rn) only, never strategy ids, names, key labels or metric values of
  private strategies. The founder keeps the before-snapshot locally.
- **D-13 (2026-09-25, orchestrator; reversible).** No migration. The recompute uses the existing
  `enqueue_compute_job` RPC and the existing worker.
- **D-14 (2026-09-25, planner discretion; reversible).** The release plan depends on the code plan
  only. The recompute is PROD operations and ships nothing, so the CHANGELOG entry records plan 02's
  state at release time, counts only, and does not block on it.
  ⭐ **Amended 2026-09-25 (plan-check revision).** "The code plan" is now five plans: 01 (Python
  variance sites), 03 (Python correlation sites), 04, 05 and 06 (TS sites, D-15). The release plan is
  `166.1-07` and depends on all five. It still does not depend on plan 02.

### Plan-check revision (2026-09-25)

- **D-15 (2026-09-25, ORCHESTRATOR DECISION, founder rule "close the whole class, not point-fixes";
  reversible per site).** The TS sites that compute a ratio over a daily-return dispersion behind a
  `> 0` / `!== 0` guard, or behind a relative-only floor, are IN SCOPE. The plan checker named four
  files (`holding-compare-adapter.ts`, `sample-basis-ratios.ts`, the Sharpe and correlation in
  `scenario.ts`, `diversification.ts`). The planner's re-grep found the rest of the class, listed in
  RESEARCH `### A5`. Every TS site gets the SAME floor as the Python helper, from ONE new TS module
  (`src/lib/dispersion-floor.ts`: `1e-12 * max(1, |mean|)`, NaN answers "not residue" and "not real"),
  a red test built from a compounding-NAV constant yield written first, and a neuter, RED, restore
  drill. The D-07 invariant holds in TS too: each fixed site emits exactly what it emits today for an
  exactly constant input at the same field (null, 0 or NaN, whichever that site already uses), so no
  renderer changes. Three TS plans, file-disjoint: 04 (the module plus the four named files), 05
  (correlation helpers, `portfolio-stats.ts`, the two scenario floors), 06 (`src/lib/factsheet/`).
  ⚠️ Coupling: `holding-compare-adapter.ts` is also edited on the unmerged `feat/167.1.2-hide` branch
  (it exports `reconstructAndAnalyze`). Plan 04 fetches `origin/main` first and rebases over that
  change if it merged; if it has not merged, plan 04 adds no export of its own.
- **D-16 (2026-09-25, plan checker finding B1, ratified by the orchestrator; reversible: one
  conditional).** `analytics_runner._compute_derived_trade_metrics`'s SQN block is site S8 of the
  variance class. Its guard is `var_r > 0` then `std_r > 0` over per-trade R-multiples. Measured
  2026-09-25 with the main checkout's venv: 21 identical losses of 7.7 give SQN -4.03e16, 37 give
  -5.40e16, while 21 identical losses of 1.0 give None (the sum is exact). SQN is rendered in
  `TradeAndPositionPanel`. It moves to `dispersion_is_residue(std_r, mean_r)`. The re-sweep that found
  it, and every hit it recorded as not in the class, is RESEARCH `### A2` addendum.
