## Warnings

### WR-01: `daily_sharpe_sentinel` label "Daily Sharpe > 10 looks unrealistic" now headlines every short constant-positive upload, whose Sharpe was never computed

**Files:**
- `analytics-service/services/csv_validator.py`: `_check_sharpe_sentinel`, the residue branch (about lines 250-258).
- `src/lib/wizardErrors.ts`: `CSV_RULE_LABELS.daily_sharpe_sentinel` (about line 6086) and `formatCsvRuleCauseSingle`.
- `src/app/(dashboard)/strategies/new/wizard/steps/CsvValidationEnvelope.tsx`: the `causeText` single-rule arm and the `<summary>` label.

**Issue:** D-24 (`d1b91d5d0`) sends an exactly-zero std into the residue branch. So a 2-, 3- or 5-row constant positive daily-returns CSV, which was accepted before, now gets `rule: "daily_sharpe_sentinel"`. Before D-24 it never reached the sentinel.

I traced the emission: `dispersion_is_residue(0.0, 0.001)` is True, `r.mean() - DEFAULT_RISK_FREE_DAILY > 0` is True, and the branch emits the rule with `row: 0`. I confirmed this by running `validate_csv` on a 5-row constant 0.001 body.

The wizard renders this rule, measured against `CsvValidationEnvelope.tsx`, as:

1. Headline: **"1 row failed validation"**. `errors.length === 1`, although this is a dataset-level rule with the absent-row sentinel `row: 0`.
2. Cause line: **"Rule violated: Daily Sharpe > 10 looks unrealistic. Expand below for the row-level breakdown."**
3. Collapsed `<details>` summary: the same label again.
4. Only inside the expanded bullet: the true cause, "Daily returns do not vary, so the Sharpe is unbounded; …".

Why the label misstates the cause:
- For sd = 0 the Sharpe is undefined, not a number above 10. The user is told a Sharpe was measured and judged too high, when the real problem is that the series never changes.
- The "row-level breakdown" pointer promises rows that do not exist.
- The sentinel also runs on the unvalidated frame after a `SchemaErrors` (`df_validated = df`). So a constant-return file with an unrelated schema error, such as the `bad-dates` body in `e2e/csv-upload-flow.spec.ts`, now shows two rule categories, one of them this misleading label.

**Why Warning and not Critical:**
- The verdict is correct and was a founder decision (D-24).
- The label is loosely true in the limit (an unbounded Sharpe is "> 10").
- The accurate sentence is one click away.
- No stored data is affected. I traced `validate_csv` callers: only `routers/csv.py` and `services/ingestion/csv_adapter.py`, both on raw upload bytes. Nothing re-validates stored `csv_daily_returns`, so 166.3's recompute does not flip existing rows.

**Reason the orchestrator may re-tier:** it is user-facing copy that misstates the cause on a path this phase created, and the repo's review policy lets user-facing defects block.

**Ownership:** D-04 locked "the rule name and its label are untouched, no TS change". D-24 changed which uploads reach that label without revisiting that clause, and D-23 moved every TS edit to 166.2. So this needs either a D-04 amendment in this phase or a named route to 166.2. It must not stay unowned.

**Fix (preferred):** emit a distinct rule key from the residue branch, so the label states the real cause and the Sharpe-number branch keeps its label:
```python
# csv_validator._check_sharpe_sentinel, residue branch
errors.append({
    "rule": "daily_returns_constant",
    "row": 0,
    "message": "Daily returns do not vary, so the Sharpe is unbounded; "
               "a constant positive return is not a realistic track record",
})
```
```ts
// wizardErrors.ts CSV_RULE_LABELS
daily_returns_constant: "Daily returns never change",
```
Also:
- Make `CsvValidationEnvelope` skip the "N rows failed validation" headline and the "row-level breakdown" pointer when every error has `row < 1`.
- Update the D-24 tests' `_sentinel_errors` filter to the new key.

**Minimal alternative** (keeps the key and changes TS only): relabel to "Sharpe unrealistically high or undefined (returns do not vary)".

### WR-02: the newly-None `_avg_corr` (C4) becomes a confident `0.0` "Correlation unchanged" in `simulate_add_candidate`, and a neutral `0.0` in `bridge_scoring`

**Files:**
- `analytics-service/services/portfolio_optimizer.py`: `_avg_corr`.
- Consumers outside the diff: `services/simulator_scoring.py` `simulate_add_candidate` (`corr_delta`), and `services/bridge_scoring.py` (`corr_delta = _delta(current_corr, new_corr)`).

**Issue:** C4 now returns None whenever any column's dispersion is residue, so a constant-yield candidate makes `proposed_avg_corr` None. `simulate_add_candidate` guards only `current_avg_corr is None` (the NEW-C11-02 guard). It then calls `_delta(current_avg_corr, proposed_avg_corr)`, and `_delta` coerces None to `0.0`.

**Measured:**
- Portfolio of two noisy legs plus a compounding 1e-4 constant-yield candidate: `deltas.corr_delta == 0.0`.
- An all-zero candidate: also `0.0`.

**Why it matters:** NEW-C11-02's own comment says the panel renders `0.0` as "Correlation unchanged (±0.000)", which is exactly the fabricated certainty that guard exists to prevent. The all-zero case was already wrong. This phase moves every constant-yield candidate (a stablecoin-lending shape) into that shape, where before it produced a residue number.

The same coercion hits `sharpe_delta` when the current or proposed blend is residue (S1 now returns None). In `bridge_scoring`, `_delta` makes the correlation axis silently neutral in `composite`. D-07 demands parity with the all-zero output, but parity with a known-wrong output is not a reason to widen it.

**Fix:**
```python
# simulator_scoring.simulate_add_candidate
corr_delta = (
    None
    if current_avg_corr is None or proposed_avg_corr is None
    else current_avg_corr - proposed_avg_corr
)
```
Apply the same "None on either side stays None" rule to `sharpe_delta` and `dd_delta` there, since the schema and panel already render None as "—". In `bridge_scoring`, keep `_delta`'s neutral `0.0` for ranking, but surface the axis as None in the returned `corr_delta` and `sharpe_delta`. Add a test with a constant-yield candidate asserting `corr_delta is None`.

### WR-03: two meanings of "average pairwise correlation"; one constant-yield sleeve voids the correlation axis in every scorer but not in the risk panel

**Files:**
- `analytics-service/services/portfolio_optimizer.py`: `_avg_corr`, the all-or-nothing `dispersion_is_real` gate.
- `analytics-service/services/portfolio_risk.py`: `compute_correlation_matrix` (C1 mask) and `compute_avg_pairwise_correlation` (skips None cells).

**Issue:** After C1, the portfolio page's average pairwise correlation masks the flat leg and averages the remaining pairs. After C4, `_avg_corr` returns None for the whole frame if any one column is flat.

`_avg_corr` feeds four scorers: `find_improvement_candidates`, `match_engine._compute_portfolio_fit_components`, `bridge_scoring` and `simulator_scoring`. So a real portfolio holding one constant-yield sleeve shows an average correlation on the risk panel, while every scorer drops the diversification axis for every candidate (`corr_reduction` None, or 0).

This is D-07-compliant (an all-zero column already gave None), but the two sites now answer the same question differently for the same input. The scorer behaviour silently disables one of three ranking axes for a common allocation shape.

**Fix:** decide one semantics and share it. The consistent choice is to mask non-dispersing columns and average only the defined pairs, as C1 plus `compute_avg_pairwise_correlation` already do:
```python
def _avg_corr(df):
    moving = [c for c in df.columns
              if dispersion_is_real(float(df[c].std()), float(df[c].mean()))]
    if len(moving) < 2:
        return None
    corr = df[moving].corr()
    n = len(corr)
    return _safe_float(float((corr.values.sum() - n) / (n * (n - 1))))
```
If "None when any leg is flat" is the intended rule, record it as a decision and make `compute_avg_pairwise_correlation` agree.

## Info

### IN-01: S8's structural divide guard became a predicate with a NaN hole

**File:** `analytics-service/services/analytics_runner.py`: `_compute_derived_trade_metrics`, the SQN block.

**Issue:** The old `if std_r > 0:` guaranteed a non-zero divisor. The new `if not dispersion_is_residue(std_r, mean_r):` relies on the floor comparison. With `mean_r` NaN (possible only if the `sum(r_multiples)` of finite values overflows to inf−inf), `residue_floor` is NaN, `0.0 <= NaN` is False, and `mean_r / 0.0` raises `ZeroDivisionError` on Python floats. The CHANGELOG notes that the function has no production caller since Phase 106, so this is Info.

**Fix:** `if std_r > 0 and not dispersion_is_residue(std_r, mean_r):`

### IN-02: C3's `else 0` arm is dead and type-inconsistent
