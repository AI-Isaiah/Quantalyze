Semantics (from the docblocks at `:571-586` and `:590-628`):

- The floor is `1e-12 * max(1, |mean|)`. It covers two residue scales: about `1e-16 * |mean|` for repeated floats (measured 4.35e-19 for 120 days of a constant 0.001), and about `1e-16` absolute for `pct_change` over a compounding NAV.

- `_dispersion_is_real` is the NaN-safe "does this leg vary" predicate.
- The smallest REAL dispersion pinned by a test is a cent-rounded compounding NAV: sd 4.1e-9 on a 1e6 start, and 4.0e-11 on a 1e8 start, which is 40× the floor. `test_q166r2_residue_floor_keeps_real_quantisation_dispersion` pins it.

from typing import Any
import numpy as np

DISPERSION_RESIDUE_REL = 1e-12

def residue_floor(mean: Any) -> Any:

def dispersion_is_real(sd: float, mean: float) -> bool:

### B3. Failure behaviour — why each enqueue is one at a time and watched

- Only the metadata marker `source = 'ledger-refresh'` (`LEDGER_REFRESH_SINGLE_KEY_SOURCE`, `job_worker.py:620`), together with a hop-1-minted `publish_status`, buys the D-15 non-destructive guard. ⛔ **Do not forge it.** It is a pinned four-end contract (`job_worker.py:584-604`), and the runbook's damage-attribution query keys on it (`docs/runbooks/ledger-refresh-go-live.md` §1).
- An unmarked `compute_analytics_from_csv` failure takes the LOUD path: publish state downgraded to `failed`, `data_quality_flags` rebuilt, persisted cash series DELETEd (`analytics_runner.py` CR-03/F1 block). That is acceptable ONLY because the input is unchanged math that computed successfully under the pre-166 code, it runs one row at a time, and a re-run after fixing the cause heals it (runbook §2/§4).
- **Marker.** Use a distinct, unprotected attribution label, e.g. `jsonb_build_object('source', 'qstats-recompute-166.1')`, so these jobs can never fall into the fan-out's population and are findable afterwards. It is the same pattern as the runbook's `ledger-refresh-repair`. No code reads it, so no gate or guard changes.
- **Interplay with the ledger fan-out.** The fan-out's 20-hour attempt cooldown counts ANY `derive_broker_dailies` or `compute_analytics_from_csv` job for the strategy (`enqueue_ledger_refresh_for_strategies` CTE). A recompute therefore suppresses that strategy's fan-out for 20 hours. That is harmless, since it was just recomputed. The in-flight guard makes `enqueue_compute_job` RETURN an existing in-flight job id instead of inserting, so confirm the returned id is a NEW row (count insertions, not calls — the fan-out's own rule).
- `enqueue_compute_job` requires exactly one of `p_strategy_id` / `p_allocator_id` / `p_api_key_id` (SQLSTATE 22023 otherwise). Pass `p_strategy_id` ALONE. It is granted to `service_role`, and the runbook's SQL-editor pattern (the postgres role, `auth.uid()` NULL) is the established founder route. The only kind it refuses by name is the retired `compute_analytics` (`_enqueue_compute_job_internal.sql:233`).
- Rows may self-heal before plan 02 runs. The daily cron sync enqueues `derive_broker_dailies` for strategies with new trades (`routers/cron.py:1136-1148`), and the ledger fan-out re-derives stale ledger strategies (`is_stale` = more than 4 days behind). The census filter `computed_at < T_DEPLOY` excludes those automatically. There is no reason to wait for them.

### Anti-Patterns to Avoid

- **`compute_analytics_from_csv` on a composite.** It destroys `metrics_json_by_basis` (B2).
- **Reusing `source: 'ledger-refresh'` to buy protection.** It is a forged contract marker and it pollutes the fan-out's damage attribution.
- **Batch-enqueueing all rows in one statement.** A systemic failure would then un-publish every row before anyone looks.
- **Importing `services.metrics` into `optimizer.py` / `csv_validator.py` for the floor.** It breaks the PURE contract and adds a heavy import chain.
- **Asserting "unchanged" after a path that re-fetched data.** The window moved, so the comparison is confounded.
- **Committing strategy ids or metric values to the repo.** The repo is PUBLIC; record counts only.

## Common Pitfalls

### Pitfall 1: A red test that cannot go red (S6)
**What goes wrong:** `optimizer.py`'s old `<= 1e-12` already equals the new floor, so a "RED first" claim would be false.
**How to avoid:** Call it a pin, and drill by neutering to `== 0`, as Phase 166 R2 recorded for its four already-caught fixtures.

### Pitfall 2: The floor moved, but a monkeypatch of the old symbol still "passes"
**What goes wrong:** After extraction, patching `services.metrics._DISPERSION_RESIDUE_REL` no longer changes `_residue_floor`.
**How to avoid:** Run the drill on `services/dispersion.py` source; state this in its docstring; grep tests for `monkeypatch.*DISPERSION` (0 today).

### Pitfall 3: A composite gets hop 2
See B2. This is a verification step in plan 02: C1's class column must be read before every enqueue.

### Pitfall 4: A confounded before/after
A derive, or a benchmark cache refresh, moves values the D-10 table says stay put. Gate each "unchanged" assertion on `series_end` / `series_n` equality, and check benchmark coverage when alpha/beta move.

### Pitfall 5: `enqueue_compute_job` returns an existing in-flight id
If another job for that strategy is in flight, the RPC returns ITS id and inserts nothing. Check `created_at`, or that the metadata `source` equals `qstats-recompute-166.1`, on the returned row before calling it "enqueued".

### Pitfall 6: Worker not yet on 166 code
A recompute on a pre-166 worker reproduces the old PSR and rolling alpha, and C2 then shows "no change" or a regression. Precondition: the worker's commit is at or after `bb31564f9`.

### Pitfall 7: Planning-hygiene leak
The SUMMARY must carry counts and anonymised row labels (R1…Rn), never strategy ids, key labels or home paths. Run `check-planning-hygiene` after every `.planning/` write.
