## (a) Round-1 HIGHs

### HIGH-1: closed

This was C3's `None` rendered as "reduce average correlation toward 0.00".

**Backend.** I probed `find_improvement_candidates` with a one-leg constant-yield
book and a noisy candidate. It returned `corr_with_portfolio: None,
sharpe_lift: None`, with a finite `dd_improvement` and `score`. The
`len(aligned) > 10 else 0` arm is gone. The score gives a missing lift an
explicit 0.0, and the sort key stays finite.

**Types and adapter.** `OptimizerSuggestionRow.corr_with_portfolio` and
`.sharpe_lift` are `number | null`, and `parseOptimizerSuggestionRow` no longer
applies `?? 0`.

**Every render site checks for null:**
- `WhatWedDoCard` drops the correlation clause and the Sharpe clause when the
  value is null. A null lift no longer hides the card, and it is no longer
  treated as a 0 lift.
- `PortfolioOptimizer`'s `MetricCell` renders null as "—" in `text-text-muted`
  through `formatMetric` and `liftClass`.
- `generate_narrative` guards `sharpe_lift is not None` before comparing it
  with 0.
- The live `/portfolio-optimizer` response model is `list[dict[str, Any]]`, and
  no zod schema on the TypeScript side rejects a null.

### HIGH-2: closed

This was the simulator and bridge deltas coercing `None` to 0.0, which rendered
as "unchanged".

**The fix.** Both `_delta` helpers return `None` when either operand is `None`.
The flat-leg guard `_leg_is_flat` covers the one case where two averages would
otherwise agree by construction.

**Probe results:**

| input | result |
|---|---|
| simulator, noisy book + flat candidate (constant yield and all-zero) | `corr_delta None` |
| simulator, flat book (one or two legs) + noisy candidate | `sharpe_delta None`, `corr_delta None` |
| simulator, mixed book with a flat leg + noisy candidate | `corr_delta None` when fewer than two legs disperse; a real number otherwise |
| bridge, flat incumbent | `corr_delta None` |
| bridge, flat candidate | `corr_delta None` |
| bridge, flat book | `sharpe_delta None`, `corr_delta None` |

In every case the other deltas stay finite, and `composite_score` is finite and
ranks through `_axis`.

**Frontend.** `BridgeCandidateSchema` makes the three deltas nullable.
`ReplacementCard` renders "— {label}" in `text-text-muted`.
`PortfolioImpactPanel` already rendered a null as "—" and "not computable",
and a new test pins that for the Sharpe and correlation deltas together.

**Other callers.** `match_engine._compute_portfolio_fit_components` applies the
same guard. Its `_normalize_min_max` already maps `None` to a 0 contribution.
The simulator's `insufficient_data` branch still emits `_zero_deltas()`, but
that is older code outside this diff, and the panel never renders deltas for
that status (`NonOkState`).

## (b) New silent failures introduced by the fix pass

I checked each shape the brief names:

- **`None` or NaN in arithmetic.**
  - Every `None` delta that reaches the bridge composite goes through `_axis`.
  - The optimizer score coalesces a `None` lift explicitly.
  - `generate_narrative` filters out risk rows with no `marginal_risk_pct` before

  (`avg_pairwise_correlation_pairs_used` and `_total`) are integers in JSONB.
  No zod schema or database constraint reads that object strictly, so the extra
  keys cannot fail a parse. The bridge and optimizer pydantic models are

- **Column lookups.** Each `_leg_is_flat` call reads a column that exists at its
  call site:

  - `"__cand__"` in match_engine;
  - `incumbent_strategy_id`, which is validated against `port_df.columns`, and

- **Tests that cannot fail.** None found. The new Python cases assert `is None`
  against inputs where the old code emitted 0.0. Each has a noisy-legs
  counterpart that asserts finite values. The fixer records a RED run for each
  under a neuter. The one draft case that could not fail was dropped.

## MEDIUM

### MEDIUM-1: the file-level cause line tells a ragged-CSV user that no row is at fault, when the parser names the line

- **Where:** `CsvValidationEnvelope` (the `ruleCount === 1` branch) together
  with `formatCsvRuleCauseFileLevel` in `wizardErrors.ts`, fed by the
  `parse_error` emitters in `csv_validator.validate_csv`.
- **Introduced by this fix pass (WR-01).** Any single-rule payload whose errors
  all carry `row: 0` now shows this primary cause line: "Rule violated: {label}.
  We checked the whole file, so no single row is at fault."
- **Where that is true.** I read every `row: 0` emitter in `csv_validator.py`.
  Most are genuine whole-file assertions: `empty`, `too_many_rows`,
  `date_format_ambiguous`, `daily_return_dollar_form_sentinel`, both Sharpe
  sentinels, and a pandera failure with no index.
- **Where it is false.** `parse_error` puts the pandas exception text into
  `message`. Measured on a three-row `daily_returns` body with one extra field,
  the error is `{"rule": "parse_error", "row": 0, "message": "Could not parse
  CSV: Error tokenizing data. C error: Expected 2 fields in line 3, saw 3"}`.
  `CsvUploadStep` passes `data.errors` straight into `pandera_errors`, so the
  panel shows:
  - the headline "Your file failed validation";
  - the cause line "Rule violated: parse_error. We checked the whole file, so no
    single row is at fault." The label is the raw key, because `parse_error` has
    no `CSV_RULE_LABELS` entry.
  - the line number, but only inside the collapsed `<details>`.
- **Why it matters.** Before this fix the cause line said "Expand below for the
  row-level breakdown", which sent the user to the detail. Now it tells them
  there is nothing row-level to find, on the most common malformed-CSV upload.
  `process_key`'s violation mapper also reports a row index that did not come
  back as `0`, so a row-scoped rule that lost its index gets the same sentence.
- **Why it is MEDIUM and not HIGH:**
  - The upload is still rejected loudly.
  - The exact parser message is still on the page.
  - Nothing is swallowed and no data is wrong. The problem is one misleading
    sentence of copy.
- **Recommendation.** Make the file-level sentence claim less, for example
  "This rule applies to the whole file." Or send `parse_error` to
  `formatCsvRuleCauseSingle`, or to a parse-specific sentence ("The file could
  not be read; the details below name the line."). Give `parse_error` a
  `CSV_RULE_LABELS` entry. Add an envelope test that renders a `parse_error`
  whose message names a line.

### MEDIUM-2: round-1 MEDIUM-1 is closed on the data side only; the subset average still renders without a hedge

- **Where:** `routers/portfolio._compute_portfolio_analytics` writes
  `avg_pairwise_correlation_pairs_used` and `avg_pairwise_correlation_pairs_total`
  to `data_quality`. A grep across `src/` finds no reader for either key.
- **What still renders:**
  - The "Avg Correlation" KPI.
  - `generate_narrative`'s sentence "Average pairwise correlation is X, which is
    well-diversified".
- **Why that misleads.** Both still describe a book in which a constant-yield
  sleeve was skipped, and neither says so. WR-03 also moved the scorers'
  `_avg_corr` from "None if any leg is flat" to the same subset rule. In a mixed
  book (for example two noisy legs, one flat leg and a noisy candidate), the
  simulator's `corr_delta` now compares two subset averages: 1 of 3 pairs
  against 3 of 6. Both averages skip the same flat leg, so the comparison is
  consistent. The rule is recorded in CONTEXT, and the fixer flagged it for
  human verification.
- **Recommendation.** When `pairs_used < pairs_total`, surface the count next to
  the KPI or hedge the narrative sentence. This is a recorded limit and does not
  need a fix round.
