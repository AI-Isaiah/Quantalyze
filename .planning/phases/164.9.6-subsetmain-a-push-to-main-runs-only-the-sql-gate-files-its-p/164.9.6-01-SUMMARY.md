# Phase 164.9.6 Plan 01: push-to-main SQL gate derivation Summary

A push to `refs/heads/main` now gets its own verdict from the pushed range, read through a lister it shares with the docs classifier. The possible verdicts:
- **SUBSET:** the changed gates plus the gates whose `RED-UNDER-SETUP` applies a changed migration, read through `parseAnnotations`.
- **`none`:** the D-09 verdict, when the range changes no gate, no migration and no machinery.
- **FULL with a printed reason:** every other case. The push path never exits non-zero.

## What was built

**Task 1, tracer (`349c3b53a`)**
- `classify-changed-paths.mjs`:
  - The range checks and the two-dot diff moved verbatim into `pushRangeFiles` (returns `{ok, sha, files}` or `{ok:false, reason}`, never throws).
  - The first-parent log read moved into `firstParentCommits` (throws on a git error).
  - `classifyPushRange` calls both. Its verdicts, reasons and order are unchanged.
  - `scratchRepo` is now exported.
  - **Proof of no change:** the classifier's `--self-test` output was diffed before and after the extraction, with shas normalised. The two outputs were IDENTICAL (19/19).
- `sql-gate-subset.mjs`:
  - `judge()` gains a push arm with the ref, range, single-commit and PR-merge checks.
  - `workflow_dispatch`, `schedule` and an unset event read FULL as D-02 requires.
  - `emit()` writes a third output, `sql_gate_reason`, sanitised by `oneLineReason`.
  - `derivePush` reads the repository at `process.cwd()` and turns every throw into FULL.

**Task 2 (`c4ffede5d`)**
- `PUSH_MACHINERY_PREFIXES` is derived from `MACHINERY_PREFIXES` by filtering out migrations, `ci.yml` and the floors file. The floors file joins the PR list, so a PR that raises a floor still runs FULL.
- `ciMutationSectionsChanged` decides when `ci.yml` counts as machinery on a push (D-10):
  - It compares the `changed-paths` and `sql-mutation` job sections, searched below `jobs:`.
  - A missing job counts as changed.
  - A compare error or a missing compare result reads FULL.
- `migrationLoaders` builds the D-03 map: migration to the gates that load it.
  - It reads every gate through `parseAnnotations`.
  - Any parse error throws, naming the file, and the push reads FULL.
- The D-09 `none` verdict.
- A changed migration that no gate loads, with no gate changed, reads FULL.

## Deviations from Plan

1. **[Rule 1 - Bug] The `oneLineReason` suffix and typographic characters.** The plan said to use a trailing ` …(truncated)` and to map every non-ASCII character to `?`. The `…` would break the must-have "one printable-ASCII line", and turning every existing em dash into `?` would garble every reason. Fix:
   - The suffix is ` ...(truncated)`.
   - The em dash and the ellipsis are spelled in ASCII first.
   - Everything else outside 0x20-0x7E still becomes `?`.
   - A self-test row asserts the newline and NUL mapping, the cap, and an all-ASCII result.
2. **[Rule 2 - Fail safe] Two extra FULL guards on the push arm.** (a) When `ci.yml` changed but no compare result was supplied, it reads "job sections were not compared". (b) When a migration changed but no loader map was supplied, the verdict is FULL. Neither input is assumed harmless when its evidence is missing. A self-test row covers (a).
3. **The empty-range reason on a push** reads `push range undeterminable (the range changed no files)`. This matches the classifier's wording for the same shape.
4. **The TDD commit shape.** The self-test lives inside the module it tests, so the RED rows were run and their failure captured (see Verify readings). They were committed together with the implementation in one `feat` commit rather than as a separate `test` commit. The plan is `type: execute`, so no plan-level TDD gate applies.
5. **The worktree pre-commit allow-list was not followed.** The protocol expects an `agent-*` branch, and this worktree is on `feat/164.9.6-subsetmain`, which the orchestrator pinned explicitly. HEAD was confirmed attached and not on a protected branch before each commit.
