## Summary

The mechanics are straightforward and mostly in place. `scripts/sql-gate-subset.mjs` has a pure `judge()` whose first statement returns FULL for any event other than `pull_request`. Its `MACHINERY_PREFIXES` includes `supabase/migrations/`, so any migration change is FULL. The push-range validation D-01 asks for exists in `scripts/classify-changed-paths.mjs` `classifyPushRange`: the before-SHA shape, all-zero, forced, `cat-file`, `--is-ancestor`, a two-dot `--no-renames -z` diff and a `--first-parent` commit log with `isPrMergeCommit`. It is inline, though, and returns only `{docsOnly, reason}`, never a file list. ⚠️ CONTEXT says "reusing `changedFilesAgainstBase`", but that function is the PR's three-dot merge-base diff and does not know about pushes. The right reuse is to **extract the push-range lister out of `classifyPushRange`** and have both callers use it, keeping the subset script's own "ONE DIFF, TWO CALLERS" rule. The lane applies **only** a gate's `RED-UNDER-SETUP` apply list plus the gate file, and `bad-file-ref` forces every arm's target into that list. So D-03's "gates whose setup loads a changed migration" is the **exact** set of gates whose verdict a migration can move. `parseAnnotations` in `scripts/mutation-runner/parse.mjs` imports only node builtins and can be reused without an import cycle.

**Two blocking findings come out of measurement, and they go to the founder rather than being designed around.** (1) The phase's own trigger push `98f04db16`, and `fb21ac20c` after it, changed only `.planning/` files. Both touch `.planning/ROADMAP.md`, which is in `TEST_READ_PLANNING_PATHS`, so they classify as code. Their changed set holds **zero gate files**, and the vacuity fence D-01 inherits turns that into **FULL**. The trigger would still run FULL against the 20-minute ceiling. (2) Of the last 200 first-parent `main` commits, only **5** would take a SUBSET under the literal rules. **30 of the 35** pushes that touch a gate or migration also touch machinery. A PR that adds arms ratchets `FILES_FLOOR`/`ARMS_FLOOR` in `run.mjs`, which is under `scripts/mutation-runner/`, and often edits `ci.yml` (`sql-tests` registry) or `scripts/pg-lane/fixtures/`. So the 164.5.2.1 migration PR, the first named consumer, will almost certainly merge FULL.

A third conflict comes from a cited source. `docs/runbooks/railway-worker.md` says Railway gates on **every workflow's check-runs** on the commit, which contradicts D-06's "does not affect Railway". A red nightly on `main` HEAD can block a Railway redeploy of that SHA. `analytics-deploy-verify.yml` deliberately exits 0 for exactly that reason. For the nightly's home, use a **new workflow file**: `nightly.yml` has concluded `failure` on every recent run (an accepted-red canary preflight), so a red there carries no signal.

**Primary recommendation:** Plan four parts. (a) Extract a shared `pushRangeFiles()` out of `classifyPushRange` and grow `judge()` with a push-on-main arm: single-squash check, migration loaders via `parseAnnotations`, and machinery minus `supabase/migrations/` on push only. (b) Widen the mutate-step guard and assert-step arm (2) to `pull_request` OR (`push` AND `refs/heads/main`). (c) Add `.github/workflows/sql-mutation-nightly.yml`, which copies the job's steps, holds a byte-equality vitest pin and runs a separate `always()` reporter job. (d) Before executing any of this, get founder answers on OPEN-1, OPEN-2 and OPEN-3. Without OPEN-1 and OPEN-2 the phase ships correctly but does not achieve its goal.

### Pattern 1: one push-range lister, two callers (D-01)

**What:** Lift the first half of `classifyPushRange` into an exported function. That half covers the SHA shape, all-zero, forced, `cat-file -e`, `merge-base --is-ancestor`, the two-dot diff and the first-parent log. It returns `{ ok: true, files, commits }` or `{ ok: false, reason }` and **never throws** (164.9.4's "fail safe to code, never to red"). `classifyPushRange` keeps its exact verdicts and reason strings by calling it, so its 164.9.4 self-test rows and the contract tests that mutate its source stay green.

**Verified source** [VERIFIED: scripts/classify-changed-paths.mjs:286-352, read this session]. The checks, verbatim:
```js
if (!/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/.test(sha)) return code(`before-SHA ${sha ? "is not an object name" : "is absent"}`);
if (/^0+$/.test(sha)) return code("before-SHA is all zeros, a branch-creating push");
if (String(forced ?? "").trim() === "true" || forced === true) return code("a forced push");
git(["cat-file", "-e", `${sha}^{commit}`], cwd);
git(["merge-base", "--is-ancestor", sha, "HEAD"], cwd);
files = git(["diff", "--name-only", "--no-renames", "-z", sha, "HEAD"], cwd)
commits = git(["log", "--first-parent", "--format=%H%x1f%ce%x1f%s%x1e", `${sha}..HEAD`], cwd)
```
⚠️ The ci.yml contract tests mutate `classifyPushRange` source by exact substring. One example from `ci-docs-path-filter.contract.test.ts`: `mutate("if (read.length > 0) return fullCorpus(", ...)`. Keep the docs-classifier-specific lines (test-read rule, `isPrMergeCommit` loop, predecessor gate) **inside** `classifyPushRange` byte-for-byte, and extract only the shared prefix. Run `npx vitest run src/__tests__/contracts/ci-docs-path-filter.contract.test.ts` after the extraction.

⚠️ **Wiring gap** [VERIFIED: ci.yml `changed-paths` job, steps `id: classify` and `id: sql_gate_subset`, read this session]. The `classify` step carries `env:` with `PUSH_BEFORE_SHA: ${{ github.event.before }}`, `PUSH_FORCED: ${{ github.event.forced }}` and `GH_TOKEN: ${{ github.token }}`. The following `- run: node scripts/sql-gate-subset.mjs --self-test` and `- id: sql_gate_subset` / `run: node scripts/sql-gate-subset.mjs` steps carry **no** `env:`. The subset step needs the same two values through `env:`, never interpolated into `run:`. It does **not** need `GH_TOKEN`, because the subset path makes no predecessor API call (see Pitfall 4).

### Pattern 2: the push arm of `judge()` (D-01, D-02, D-04)

**Current behaviour** [VERIFIED: scripts/sql-gate-subset.mjs:95-99]:
```js
if (event !== "pull_request") {
  return full(`event is '${event ?? "(unset)"}', not pull_request — the full corpus is owed`);
}
```
**Recommended shape:** keep `judge()` pure and give it more inputs. `main()` does all the I/O.
```js
// SKELETON, not shipped code. Names are proposals ([ASSUMED]).
export function judge({ event, ref, changedFiles, presentFiles, pushRange, migrationLoaders }) {
  const full = (reason) => ({ mode: "full", files: [], reason });
  if (event === "pull_request") return judgePullRequest({ changedFiles, presentFiles }); // body UNCHANGED
  if (event !== "push") return full(`event is '${event ?? "(unset)"}', neither pull_request nor push — the full corpus is owed`); // D-02
  if (ref !== "refs/heads/main") return full(`push to '${ref ?? "(unset)"}', not refs/heads/main`);
  if (!pushRange.ok) return full(`push range undeterminable (${pushRange.reason})`);
  if (pushRange.commits.length !== 1) return full(`the pushed range holds ${pushRange.commits.length} first-parent commits, not one PR squash`);
  const [[sha, email, subject]] = pushRange.commits;
  if (!isPrMergeCommit(email, subject)) return full(`commit ${sha.slice(0, 12)} is not a GitHub PR merge`);
  // machinery minus supabase/migrations/ (push only) -> FULL; bad names / absent gates -> FULL (same arms as PR)
  // selected = changed gate files ∪ migrationLoaders(changed migrations); empty -> FULL (fence) [OPEN-1]
}
```
- **Single-squash detection:** exactly one `--first-parent` commit in `before..HEAD`, **and** `isPrMergeCommit(committerEmail, subject)` true. `isPrMergeCommit` is already exported [VERIFIED: scripts/classify-changed-paths.mjs:365]. Optionally also require `git rev-parse HEAD^1 == before`. That is implied by "one first-parent commit and before is an ancestor", so it is a cheap redundant check.
- **`ref`:** read `GITHUB_REF`. `ci.yml` `on.push.branches: [main]` already limits pushes to main, but D-04 says "push to main", and the check costs nothing.
- **D-08 is NOT met today, on any event, and meeting it touches the runner.** D-08 asks for **one scope line** carrying mode, file count **and reason**. The current forms [VERIFIED: run.mjs `runCorpus`, the `scopeLine` assignments]: `` `scope: SUBSET ${targets.length}/${annotatedTotal} annotated files: ${targets.join(" ")}` `` (names, no reason), and `` `scope: FULL ${annotatedTotal}/${annotatedTotal} annotated files` `` with an optional ` (subset fallback: <reason>)` that appears **only** when the runner itself fell back. A FULL chosen by the derivation (`sql_gate_mode=full`) prints a bare FULL line with no reason. That holds on PRs and the nightly as well as on pushes. `emit()` prints `sql_gate_mode=<mode> — <reason>` but in the `changed-paths` job log, not on the scope line. What the plain reading costs:
  1. `run.mjs` accepts a reason (a new `--scope-reason <text>` flag or env var) and prints it on the scope line. On the nightly the reason is the event (`schedule: the nightly full corpus`).
  2. The assert step's FULL regex [VERIFIED: ci.yml assert step, `'^scope: FULL [0-9]+/[0-9]+ annotated files( \(subset fallback: .+\))?$'`] ends in `$` and must widen to admit the reason. Arm (1c) MEASURE_FAILs any line that matches neither form.
  3. ⚠️ **Parser collision on SUBSET.** The assert step counts SUBSET names with `grep -a -o -E '[A-Za-z0-9_]+\.sql'` over the **whole** scope line, and WR-07 takes the set as `${scope_line#*annotated files: }`. A D-03 reason naming a migration (`…_compute_jobs_queue.sql`), appended after the names, inflates the CLAIMS-vs-NAMES count and breaks set equality, which makes it a false MEASURE_FAIL. The reason therefore needs a **fixed, delimited position before the names**, for example `scope: SUBSET k/N annotated files [reason: …]: a.sql b.sql`, and the reason text must not contain `]:`. Alternatively both parsers change to read only after a terminal delimiter. Either way, every pin of the literal scope strings moves: 10 `scope: FULL`/`scope: SUBSET` occurrences in `mutation-runner-floors.test.ts` (GREEN_LOG, SUBSET_LOG, the fallback fixture and assertions), plus the runner's own self-test if it pins the format.
  4. The reason crosses jobs as a new `changed-paths` output (`sql_gate_reason`) through `env:` only. It can carry repo paths, which are `GATE_FILE_RE`-safe or machinery paths, never interpolated into `run:`.
  - **Cheaper alternative, which is a founder call (OPEN-4):** keep the scope line as is and print a second, mandatory `scope-reason: …` line that the assert step requires. That changes no existing regex and no fixture name parse, but it is "two lines", not "one scope line". Do not substitute it silently.

### Pattern 3: migration loaders via the runner's parser (D-03)

**Why it is exact, not a heuristic.** The lane applies only the setup list plus the gate:
- [VERIFIED: scripts/mutation-runner/run.mjs:5178,5214-5217] `const corpusRels = [...parsed.setup.apply, gateRel];` … `applyAbs: parsed.setup.apply.map((r) => baseMap.get(r)),`
- [VERIFIED: scripts/pg-lane/run.sh:408] `for f in "${applies[@]}"; do psqlq -q -f "$f"; done`
- [VERIFIED: scripts/mutation-runner/run.mjs:5186-5191] Every arm target must be in that list, or the runner raises `bad-file-ref`: `` `step targets ${step.file}, which is not in this gate's RED-UNDER-SETUP apply list` ``.

So a migration absent from a gate's setup **cannot** affect that gate's verdict in the lane, in a subset run **or** in the nightly. ⚠️ **Correction to the CONTEXT's "consequence to state honestly":** "a migration whose effect reaches a gate that does NOT list it … is caught only by the nightly" is not true of this lane. The nightly full run applies the same setup lists and cannot see that migration either. That gap belongs to the corpus (the setup list is a hand-kept model of production), not to the subset. The nightly's real backstop value is different: runner-host drift (ubuntu image, apt `pg_cron` version), flakiness, and **ARMS_FLOOR measured as real biting** rather than the static upper bound. The plan and CLAUDE.md should state it this way. D-03 itself is unchanged.

**Parser** [CITED: scripts/mutation-runner/parse.mjs, read via shell this session. Line 60 was opened with Read]:
- [VERIFIED: parse.mjs:60] `const SETUP_RE = /^[ \t]*--[ \t]*RED-UNDER-SETUP:[ \t]*(.*)$/;`
- [CITED: parse.mjs `parseAnnotations`] `export function parseAnnotations(text, { file = "<unknown>" } = {})` returns `{ file, setup, prose, structured, errors, parity }`, where `setup` is `{ apply: string[], line } | null`. Its `validateSetup` refuses any key other than `apply`, an empty `apply` and any non-repo-relative path.
- [VERIFIED: parse.mjs:47-48] `import { readFileSync, readdirSync } from "node:fs";` / `import { join } from "node:path";` are its only imports. Importing it from `sql-gate-subset.mjs` creates no cycle. `run.mjs` imports `GATE_FILE_RE` from `sql-gate-subset.mjs`, and `parse.mjs` imports neither.

**Loader map:** for every `supabase/tests/*.sql` matching `GATE_FILE_RE`, call `parseAnnotations` and map each `setup.apply` entry that starts with `supabase/migrations/` to the gate path. **Fail safe:** if any gate file reports `errors.length > 0`, or the read throws, return FULL with the reason. - **Reporter (D-06):** a separate job `report` with `needs: [sql-mutation-full]`, `if: always() && needs.sql-mutation-full.result != 'success'`, `permissions: { contents: read, issues: write }`, so the uplift is job-level only. Then it exits non-zero, which keeps the workflow red per D-06, subject to OPEN-3.
- ⛔ **Never quote credential-shaped text into the issue body.** The reading is runner output (counts, file basenames, `::error::` text) and contains no secrets. Truncate it to a bounded size, for example the last 60 lines plus the summary lines, since issue bodies are capped at 65,536 characters.

### Anti-Patterns to Avoid
- **A second diff implementation** in `sql-gate-subset.mjs` for pushes. Extract and share it.
- **A regex for `RED-UNDER-SETUP`** in the subset script. Use `parseAnnotations`.
- **Putting the nightly in `nightly.yml`.** Its standing red hides D-06.
- **Moving `sql-mutation` into a reusable workflow** in this phase. It breaks dozens of slice and execute pins for no behavioural gain.

- **Raising `timeout-minutes: 20`**, or adding an expression that lifts it on some event. Forbidden.

## Common Pitfalls

### Pitfall 1: the literal rule does not fix the trigger (BLOCKING → OPEN-1)
**What goes wrong:** `98f04db16` changed `.planning/ROADMAP.md`, `.planning/STATE.md` and one VERIFICATION file [VERIFIED: `git show --stat 98f04db16`]. ROADMAP is in `TEST_READ_PLANNING_PATHS`, so `docs_only=false` and `sql-mutation` runs. `judge()` sees zero gate files and returns `0 of N changed file(s) are gate files`, which is FULL.
**Measured (last 200 first-parent `main` commits, `77e003005..fb21ac20c`):** 10 docs-only short path (skipped) · 35 planning-only but touching a test-read path → FULL · 101 code with no gate/migration → FULL · 49 machinery → FULL · **at most 5 SUBSET**. The upper bound is loose: annotation status and the single-squash rule were not checked for those 5.
**How to avoid:** a founder decision (OPEN-1). Planning cannot resolve it without re-opening D-01's fence.

### Pitfall 2: floor ratchets and ci.yml edits make gate/migration pushes FULL (BLOCKING → OPEN-2)
**What goes wrong:** 30 of 35 gate/migration pushes in the window touch machinery: `scripts/mutation-runner/` (28), `ci.yml` (20), `scripts/pg-lane/` (16), with overlap. The cause is structural. A PR adding arms edits `export const FILES_FLOOR` / `export const ARMS_FLOOR` in `run.mjs` (seen in `985c26d12`, `5a88a165e`, `5ce71a986`) and often the `sql-tests` part of `ci.yml`, not the `sql-mutation` job.
**Why it matters:** 164.5.2.1, the first named consumer, will very likely merge FULL and can still cross 20 minutes.
**How to avoid:** OPEN-2 options. Whatever is chosen, the phase PR itself runs FULL, because it edits `sql-gate-subset.mjs` and `ci.yml`.

### Pitfall 3: every FULL on main still runs under the 20-minute ceiling
Every fallback path still runs FULL: dispatch (D-02), a multi-commit or direct push, a changed unannotated gate file (the runner fallback), machinery. Recent main FULL runs took 15.2-16.9 min and one exceeded 20 (CONTEXT). A timeout reds `main`, and Railway skips the deploy. The phase narrows the FULL population. It does not remove it. State this in the plan's success criteria rather than implying the ceiling risk is closed.

### Pitfall 4: the push subset must not call the predecessor API
`classifyPushRange` calls `predecessorVerdict` (`gh api`) on the docs short path only. The extracted lister must stop **before** the predecessor call. Otherwise the subset step needs `checks: read` and `GH_TOKEN`, and gains a network failure mode. No predecessor check is needed for a subset, because the PR run proved the tree. (Whether the PR's run was green is not checked here. That trust is D-03's own rationale.)

### Pitfall 5: the nightly's check runs land on `main` HEAD
Scheduled runs attach check runs to the HEAD SHA. (a) While a nightly is running or red on HEAD, the next docs-only push loses its short path, because `predecessorVerdict` counts every workflow. That cost was accepted in 164.9.4 IN-03 and is the safe direction. (b) Railway's gate is "every workflow's check on it must be non-red" [CITED: docs/runbooks/railway-worker.md, Recovery step 2], so a red nightly can block a redeploy of HEAD. See OPEN-3.

### Pitfall 6: wall-time growth toward 45 is invisible without the print
Local full runs already measured ~17 min in September (CLAUDE.md lineage). The nightly prints a wall-time line every run (D-05). Consider an `::warning::` once it passes about 80% of 45 min, so growth shows before a timeout. [ASSUMED: threshold is a suggestion]

### Pitfall 7: tests inherit the real event
`runCountRecheck` spreads `process.env`. In CI vitest runs with `GITHUB_EVENT_NAME=push` and `GITHUB_REF=refs/heads/main` on main. After widening, every count-recheck test that drives a SUBSET log must pass **both** `GITHUB_EVENT_NAME` and `GITHUB_REF` explicitly. Otherwise a RED arm ("SUBSET on push fails") passes on PRs and fails on main, or the reverse. The existing comment in `mutation-runner-floors.test.ts` already warns about this for the event.

## Code Examples

### Loader map (proposal, reuses the real parser)
```js
// SKELETON — names proposed, parser API verified (parse.mjs:391).
import { readdirSync, readFileSync } from "node:fs";
import { parseAnnotations } from "./mutation-runner/parse.mjs";
export function migrationLoaders(repoRoot) {
  const map = new Map(); // migration path -> Set(gate path)
  for (const name of readdirSync(join(repoRoot, GATE_DIR_PREFIX)).sort()) {
    const rel = GATE_DIR_PREFIX + name;
    if (!GATE_FILE_RE.test(rel)) continue;
    const p = parseAnnotations(readFileSync(join(repoRoot, rel), "utf8"), { file: rel });
    if (p.errors.length > 0) throw new Error(`MEASURE_FAIL: ${rel} has unparseable RED-UNDER annotations`); // caller -> FULL
    for (const a of p.setup?.apply ?? []) if (a.startsWith("supabase/migrations/")) {
      if (!map.has(a)) map.set(a, new Set());
      map.get(a).add(rel);
    }
  }
  return map;
}
```
⚠️ An unannotated gate has `setup === null` and is skipped, which is correct because it has no arms. ⚠️ `main()` must turn a throw into **FULL with the reason**, not a non-zero exit. A non-zero `changed-paths` exit skips every dependent and reds `main` (164.9.4 rationale), which is the same "fail safe to FULL, never to red" stance.

### Known threat patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Script injection via `github.event.*` in `run:` | Tampering | `env:` indirection only (the repo's existing rule for `PUSH_BEFORE_SHA`) |
| Crafted gate filename reaching shell | Tampering | `GATE_FILE_RE` (T-164.4.2-20). Loader paths come from the repo's own gate files and are re-checked by `GATE_FILE_RE` |
| Forged PR-merge commit shape to obtain a subset | Spoofing | `isPrMergeCommit` is a guard against accident, not an adversary. Anyone who can push to `main` can set the committer address. The nightly is the backstop |
| Issue body leaking secrets | Info disclosure | The reading is runner output only, bounded length, and never env dumps |
| Write-scoped token pivot in nightly | Elevation | `issues: write` only in a job that runs no repo code, only `github-script` on the downloaded text |
