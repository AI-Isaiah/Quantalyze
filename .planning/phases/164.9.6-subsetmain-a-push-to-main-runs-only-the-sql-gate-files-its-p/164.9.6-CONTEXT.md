# Phase 164.9.6: SUBSETMAIN - Context

**Gathered:** 2026-10-03
**Status:** Ready for planning

<domain>
## Phase Boundary

A push to `main` stops running the full SQL mutation corpus. It runs only the SQL gate files the
pushed (squash) commit changed, plus the gates that load a migration the commit changed. A new
nightly scheduled job runs the FULL corpus and is the place `FILES_FLOOR` / `ARMS_FLOOR` /
`WAIVED_CEILING` are enforced. Every run prints which scope it took and why.

Trigger (founder decision 2026-10-03): `sql-mutation` crossed its 20-minute ceiling on push
`98f04db16` (earlier main runs 15.2-16.9 min; push `fb21ac20c` took ~15 min). The push job's
`timeout-minutes: 20` is a declared CEILING and is NEVER raised again (CLAUDE.md, SQL gate
integrity jobs › Timeout). This phase is the `[REDUNDER-SUBSET-SPLIT]` answer that ceiling names.

Out of scope: pull-request behaviour (the 164.4.2 subset on PRs is unchanged), the runner's arm
semantics, and any floor value.
</domain>

<decisions>
## Implementation Decisions

### A. How a push to main picks its subset
- **D-01 (founder):** run the SAME `scripts/sql-gate-subset.mjs` derivation on the pushed range
  (`github.event.before..after`), reusing `changedFilesAgainstBase` as the docs classifier already
  does for pushes (164.9.4). Any doubt falls back to FULL with the reason printed: a zero or
  missing before-SHA, a forced push, a before-SHA not an ancestor, a multi-commit range that is not
  a single PR squash, or a git/API error. Never an empty scope read as a pass (the existing
  vacuity fence applies unchanged).
- **D-02 (founder):** a `workflow_dispatch` on `main` always runs FULL.
- **D-03 (founder):** a push that changes a migration runs the changed gate files PLUS every gate
  whose RED-UNDER-SETUP (setup list) loads a changed migration file — not FULL. Rationale: the PR
  run already covered the full corpus or its subset at that tree, and the nightly full run is the
  backstop. A change to the mutation MACHINERY itself (runner, pg-lane, fixtures) still forces
  FULL on main, as on PRs.
  - Consequence to state honestly: a migration whose effect reaches a gate that does NOT list it in
    its setup is caught only by the nightly run, up to ~24 h later.
- **D-04:** the `sql-mutation` step keeps refusing a subset on any event other than `pull_request`
  and a `push` to `main`; the refusal is widened by exactly one event, not removed.

### B. The nightly full run
- **D-05 (founder):** a new scheduled job runs the full corpus with its OWN `timeout-minutes: 45`.
  The push job stays at 20 and is never raised. The nightly prints its wall time so growth toward
  45 is visible.
- **D-06 (founder):** a red nightly (defect, floor or ceiling breach, timeout) fails the workflow AND
  opens a GitHub issue, or comments on the already-open one, carrying the failing reading. It does
  not affect Railway (which waits only on main CI).
- **D-07:** floors (`FILES_FLOOR`, `ARMS_FLOOR`, `WAIVED_CEILING`) are enforced on every FULL run,
  i.e. the nightly and any push/dispatch that falls back to FULL. A subset run keeps its existing
  `scope: SUBSET k/N` line so it never reads as full coverage. The vitest stale-low ratchet
  (`src/__tests__/mutation-runner-floors.test.ts`) is unchanged.
- **D-08:** every run prints one scope line (FULL or SUBSET, the file count, and the reason),
  on PRs, main pushes and the nightly alike.

### Claude's Discretion
- Whether the nightly lives in `nightly.yml` (existing `cron: "0 8 * * *"`) or its own workflow
  file, and the exact cron time.
- How the "gates that load a changed migration" set is derived (parse each gate's setup list via
  the runner's existing parser is preferred over a new regex).
- Whether the nightly holds the shared-TEST advisory key: it should not need it, since the
  mutation lane is a throwaway cluster (`scripts/pg-lane/run.sh`).
- The issue title/label used for D-06 dedupe.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `scripts/sql-gate-subset.mjs` (164.4.2 D-D): derivation, `GATE_FILE_RE` security allow-list,
  `--self-test` driving every verdict; currently hard-codes FULL for non-PR events and for any
  migration/machinery change.
- `scripts/classify-changed-paths.mjs`: `changedFilesAgainstBase()`, already push-range aware
  (`PUSH_BEFORE_SHA`, `PUSH_FORCED`) since 164.9.4, with fail-safe-to-code semantics.
- `scripts/mutation-runner/run.mjs --subset-from <list>`: prints `scope: SUBSET k/N` or
  `scope: FULL N/N (subset fallback: <reason>)`; refuses an empty list.

### Established Patterns
- `changed-paths` job in `.github/workflows/ci.yml` publishes `sql_gate_mode` / `sql_gate_files`
  outputs; `sql-mutation` consumes them and refuses subset on non-PR events in its own step.
- Red-path-first: every derivation has a `--self-test` run before the real one.
- Cite CI jobs by symbol (`grep -n '^  sql-mutation:'`), never by line number.

### Integration Points
- `.github/workflows/ci.yml` `changed-paths` and `sql-mutation` jobs; the `frontend` aggregator.
- `.github/workflows/nightly.yml` (schedule) or a new workflow.
- CLAUDE.md "SQL gate integrity jobs" section (timeout + floors prose must stay true; cite by
  symbol).
