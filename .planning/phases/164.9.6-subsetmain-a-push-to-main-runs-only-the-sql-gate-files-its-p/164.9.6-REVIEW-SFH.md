## The core question: can `sql-mutation` go green on a vacuous pass?

I found no path that does this today. Each failure mode in the brief was traced to code:

- **A missing or garbled output does not read as `none`.** The scope step writes `skip_lane=true` only on
  the literal `none` + `push` + `refs/heads/main` path, and only with a non-blank reason and an empty file
  list (`ci.yml` scope step). Every later step uses `!= 'true'`, so an absent or empty output boots the lane.
  An empty `SQL_GATE_MODE` reaches the mutate step's FULL command. `sql-mutation-scope-step.test.ts` pins
  this. Calibrations C and D prove the pin bites when a condition is deleted or flipped.
- **Derivation exceptions become FULL.** `derivePush` wraps the push path in a catch-all that returns
  FULL. `pushRangeFiles` never throws. A `firstParentCommits` throw, a `ci.yml` compare error and a
  loader-map parse error each map to a named FULL in `judgePush`. A `ci.yml` change with no compare result
  is treated as machinery.
- **`skip_lane=true` does not leak off main.** The event and ref are re-checked in the `sql-mutation` job
  itself. Calibrations A and B prove each check is read.
- **The assert step and the skipped lane.** Skipping both is the D-09 design. The job stays `success`,
  and the scope step prints both `scope: NONE` and `scope-reason:`. The strict `frontend` row is unchanged.
- **Floors on a FULL run.** Every FULL run, the runner's own subset fallback included, takes the
  `biting < arms_floor` arm. The floors come from `scripts/mutation-floors.mjs` through the runner's own
  import, and the assert step reads them the same way.
- **An empty SUBSET is never a pass.** An empty `SQL_GATE_FILES` gives an empty list, which
  `readSubsetList` and `runCorpus` both refuse. A list that names an unannotated gate falls back to FULL
  with every floor.
- **New tests.** None of them can pass vacuously that I could find. The real-history end-to-end test
  throws `MISSING OBJECT` on a shallow clone instead of skipping. The scope-step tests run the extracted
  `run:` body itself, so an empty extraction fails the `skip_lane=true\n` equality. Each nightly parity pin
  has its own calibration.

Three things are not vacuous today but can become silent. They follow.

## SFH-01 — MEDIUM (confidence 7): `migrationLoaders` silently drops any setup entry outside `supabase/migrations/` and matches paths as raw strings, so a lane input can change on a push with the lane skipped or its loader gate left out

**Location:** `scripts/sql-gate-subset.mjs:203-218` (`migrationLoaders`, and the `continue` at `:213`). It
feeds `judgePush` at `:324` (the D-09 `none` branch) and `:342` (`loading`).

**Issue.** The lane applies every `RED-UNDER-SETUP` `apply` entry of a gate. `materialize` in
`scripts/mutation-runner/run.mjs:2160` does `join(REPO_ROOT, rel)`. `validateSetup` / `isRepoRelativePath`
in `scripts/mutation-runner/parse.mjs:79,366` accept any repo-relative path without `..`. So both of these
are valid setup entries today, and the lane applies both:

1. **A non-canonical spelling of a migration**, such as `./supabase/migrations/X.sql` or
   `supabase/migrations//X.sql`. `join` normalises it, so the lane works. But `migrationLoaders` keys the map
   on the raw string, and `applied.startsWith("supabase/migrations/")` is false for `./…`. Git prints the
   canonical path, so `loaders.get(m)` misses. The push then:
   - selects the other changed gates and silently leaves out the gate that loads `X.sql`, or
   - if no gate changed, falls to FULL ("loaded by no gate"). This is the only safe outcome.
2. **A lane input that is neither a migration nor machinery**, such as `supabase/seed.sql`, a
   `supabase/schema/` file, or a future fixture directory outside `scripts/pg-lane/`. `migrationLoaders`
   skips it with `continue`. It is not in `PUSH_MACHINERY_PREFIXES` and not under `supabase/tests/`. A
   single-PR push that changes only that file therefore derives **`sql_gate_mode=none`**: the lane is
   skipped, the job is green, and the gate whose setup applies the changed file is never mutated.

**Hidden errors.** A setup list that names a lane input this module cannot see. The exception path at
`:209-211` covers only *parse* errors, not *unrecognised* entries.

**Impact.** This is latent. The census above shows the corpus uses only the two canonical prefixes today.
The first gate that applies a file from a third location, or spells a migration path differently, turns
D-09 into a vacuous green on `main`. Nothing would flag it before the nightly, and nothing at all if the
nightly happens to pass. The same blindness exists on the pull-request arm, where a changed gate plus a
changed non-machinery setup input gives a SUBSET without the loader. That is pre-existing. This phase
makes it reachable as a lane *skip*.

**Recommendation.** Fail toward FULL in `migrationLoaders`. Throw, naming the gate and the entry, for any
`apply` entry that:

- is not canonical (`posix.normalize(p) !== p`, or it starts with `./`), or
- is not under `MIGRATIONS_DIR_PREFIX` and not under a `PUSH_MACHINERY_PREFIXES` directory.

`derivePush` already turns the throw into `loaderError`, which gives FULL. Because `migrationLoaders` runs
only when a migration changed, also call it (or a cheaper `setupInputs(root)`) when **no** migration
changed, before D-09 returns `none`. Otherwise case 2 never reaches the check. Add two self-test rows:
`./supabase/migrations/…` throws, and `supabase/seed.sql` in a setup list throws.

```js
for (const applied of parsed.setup?.apply ?? []) {
  if (posix.normalize(applied) !== applied || applied.startsWith("./")) {
    throw new Error(`${rel}: RED-UNDER-SETUP entry ${JSON.stringify(applied)} is not a canonical repo path`);
  }
  if (!applied.startsWith(MIGRATIONS_DIR_PREFIX)) {
    if (PUSH_MACHINERY_PREFIXES.some((m) => m.endsWith("/") && applied.startsWith(m))) continue;
    throw new Error(`${rel}: RED-UNDER-SETUP applies ${applied}, a lane input the push derivation cannot track`);
  }
  …
}
```

## SFH-02 — MEDIUM (confidence 6): the nightly's filed issue cannot name a failure that only the assert step detected, and it tells the reader there was no `::error::`

**Location:** `.github/workflows/sql-mutation-nightly.yml:769-799` ("Capture the reading", the grep at
`:788`). It is filed by the `report` job at `:817-899`.

**Issue.** The reading greps `::error::` lines out of `$RUNNER_LOG` only. Every out-of-process MEASURE_FAIL
writes its `::error::` to the *assert step's* stdout, never into `$RUNNER_LOG`. That covers a missing or
duplicate `scope-reason:` line, the `arms:` and `lane-invocations:` disagreement, the per-file cross-sum,
the `unreachable:` and `lane-blocked:` counts, and the floor-read failures. When one of these is the cause,
the issue body says:

```
--- ::error:: lines ---
(no ::error:: line in the runner log)
...
job status: failure
```

That reads as "the runner was clean". It points triage at infrastructure rather than at the gate. Many
runner floor and defect lines do reach `$RUNNER_LOG`. The assert-only class does not.

**Impact.** The issue is filed, so this is not silent. But its one diagnostic section asserts something
false about where the failure was. A reader six months on has to open the run log to learn which assertion
fired, and its 14-day artifact and run logs can expire first.

**Recommendation.** Record which step failed in the reading. The assert block is pinned byte-equal to
`ci.yml`, so do not edit it. Instead, give the lane steps ids, pass their outcomes into the capture step,
and print them:

```yaml
      - name: Capture the reading
        if: always()
        env:
          MUTATE_OUTCOME: ${{ steps.mutate.outcome }}
          ASSERT_OUTCOME: ${{ steps.assert.outcome }}
        run: |
          …
          echo "--- step outcomes ---"
          echo "mutate: ${MUTATE_OUTCOME:-not run}  assert: ${ASSERT_OUTCOME:-not run}"
```

Also reword the empty-grep fallback to "(no ::error:: line in the runner log; an assert-step failure is
printed in the run log, not here)". Check whether adding `id:` breaks the parity parser before choosing
between this and the reworded fallback.

## SFH-03 — MEDIUM (confidence 5): nothing detects a nightly that never runs, yet both push-to-main shortcuts name it as their only backstop

**Location:** `.github/workflows/sql-mutation-nightly.yml:1-5` (`on: schedule` / `workflow_dispatch`) and
`:817-819` (`report` fires only on `needs.sql-mutation-full.result != 'success'`). The dependants are
`scripts/sql-gate-subset.mjs:324-333`, whose D-09 reason ends "FULL coverage is the nightly run's", and the
`ci.yml` SUBSET assert message ("ARMS_FLOOR … is compared by the nightly full-corpus run").

**Issue.** The reporter exists only inside a nightly run that started. These outcomes produce no run, no
red check and no issue:

- a schedule GitHub drops (scheduled events can be delayed or dropped under load),
- a workflow disabled in the Actions UI,
- a later edit that makes the YAML invalid (a scheduled workflow with a parse error simply does not run),
- the 60-day inactivity auto-disable.

While that lasts, every push to `main` keeps taking `none` (lane skipped) or a SUBSET (ARMS_FLOOR never
compared). A floor regression that only appears when two individually green PRs combine on `main` then
goes unseen indefinitely, where before this phase the next push's FULL run caught it.

**Impact.** This is a silent loss of the full-coverage guarantee that D-09 and D-04 were accepted on.

**Recommendation.** Add a liveness check on the consumer side, where the shortcut is taken. In the
`sql-mutation` scope step, before honouring `none`, and in the SUBSET branch: on a push to main, query the
latest completed `sql-mutation-nightly.yml` run on `main`
(`gh api repos/{owner}/{repo}/actions/workflows/sql-mutation-nightly.yml/runs?branch=main&status=completed&per_page=1`).
If none concluded within, for example, 36 hours, refuse the shortcut and boot FULL with a `::warning::`
that names the stale nightly. Refusing toward FULL keeps the fail-safe direction and needs only
`actions: read`.

The `pushRangeFiles` header records a design goal: "the subset path never makes a `gh api` call". If that
must hold, put the check in a separate small scheduled workflow that opens the same deduplicated issue when
the newest nightly is older than 36 hours. That is weaker, since it shares the scheduler it watches, but it
is better than nothing.
