# Phase 193 — UI Design Contract (QUIETVIEW)

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Shape of this phase.** Mostly removal. Three pieces of placeholder or foreign content leave the
factsheet, one interaction changes (a plain wheel stops zooming), one control is added (a reset
beside the range label that already exists), range persistence goes away, and the note surfaces
stop writing on open. The phase adds no new token, colour, font, icon or component file.
`DESIGN.md` governs everything below. Where this spec and `DESIGN.md` disagree, `DESIGN.md` wins
and the spec is wrong.

**Sources.** Locked decisions D-01 to D-10 in `193-CONTEXT.md`. ROADMAP Phase 193 success criteria
SC-1 to SC-4. REQUIREMENTS TRUST-02, TRUST-03 and TRUST-06. Code read at the worktree head on
2026-11-06. Line numbers are as read on that day; cite by symbol when planning, because they drift.

## Interaction Contract

### I-1 Wheel over a chart (D-01, SC-1, TRUST-02)

Applies to every wheel handler on the factsheet, measured 2026-11-06 with
`grep -rn 'onWheel\|"wheel"' src`. There are exactly two:
`src/app/factsheet/[id]/v2/TimeSeriesChart.tsx` (it changes the date range) and
`src/app/factsheet/[id]/v2/HistogramChart.tsx` (a local value-axis zoom). Both follow the same rule,
because D-01 says "a factsheet chart".

| Input over the chart | Result |
|----------------------|--------|
| Plain wheel (no modifier), any direction | **Nothing happens to the chart.** The page scrolls. No `preventDefault`. The date range, the KPI strip, the metrics rail and every other headline figure stay byte-identical. |
| Ctrl + wheel, or Cmd (`metaKey`) + wheel | Zooms exactly as today: anchored at the cursor, `exp(deltaY × 0.0012)` per tick, `WHEEL_SETTLE_MS` 150 ms settle hold. `preventDefault` is called, so the browser does not zoom the page while the pointer is over the chart. |
| Trackpad pinch (browsers report it as wheel + `ctrlKey`) | Zooms the chart. This is a consequence of D-01, and it is accepted. |
| Ctrl + wheel anywhere **outside** a chart | Untouched. The browser zooms the page as normal. |
| Shift + wheel / horizontal wheel (`deltaY === 0`) | Does not change the range. The existing early return stays. |

The non-passive native listener (`TimeSeriesChart.tsx` about :816–823, `HistogramChart.tsx` about
:203–207) must call `preventDefault` **only when a modifier is held**. Today it calls it on every
wheel, and that blocks page scrolling. This is the root cause of "plain scrolling must scroll the
page". Gating only the React `onWheel` body and leaving the native listener alone would still trap
the scroll.

These are unchanged, because each is a deliberate gesture or an explicit control (see assumption A-4):
drag inside the plot (pan), drag on the axes (scale), the MasterBrush, double-click (reset), keyboard
on a focused chart (arrows, `+`/`-`, Home/`0`/Esc), and a horizontal touch swipe (pan). Vertical
touch scroll already reaches the page through `touch-pan-y`.

No new visible hint is added to the time-series charts. There are 11 of them, so a hint on each
would be density noise. The MasterBrush is the visible range control.

### I-2 The narrowed-range label and its reset (D-03, SC-2)

1. **The label already exists. Do not add a second one.** `RangeEyebrow` sits directly above the KPI
   strip (`surface="strip"`) and at the top of the metrics rail (`surface="rail"`). Those are the two
   blocks whose figures follow the range. It prints the dates shown, from the same `RangeScope` as
   the figures (T-169-43). D-03's "labelled next to the figures it changes, the dates shown" is
   already met by this element. A second "Showing …" line beside it would put two strings on one
   fact, so the existing one is kept (see A-1 for the wording).
2. **Add the reset control inside `RangeEyebrow`.** Render it only when `scope.kind === "selected"`.
   With the full history in view, nothing is added and the row reads exactly as it does today.
3. **Layout.** Make the component's root a wrapper `div` with
   `flex flex-wrap items-center gap-x-3 gap-y-1`. The `className` prop moves to this wrapper, so the
   strip's `mt-6` is kept. The existing `<p data-testid="range-eyebrow-{surface}">` stays first,
   with its classes and **text content unchanged**. Existing tests pin `textContent` exactly
   (`FactsheetView.window-kpis.test.tsx`, `MetricsColumn.window.test.tsx`). The `<button>` comes
   second, left-anchored right after the text. No `ml-auto`, because a report is left-anchored. In
   the narrow rail it wraps onto its own line under the label.
4. **The control.**
   `<button type="button" data-testid="range-reset-{surface}">Reset to full history</button>`, with
   the ControlBar `Reset view` class string copied byte for byte. Add `factsheet-v2-no-print`, so
   the dated label prints and the button does not.
5. **What one click does.** It calls `resetXRange()` and nothing else. It does not touch the
   comparator, the collapsible sections, the per-chart Y override or the toggles. That set is what
   ControlBar `Reset view` does, and `Reset view` stays as it is. Then **focus moves to the label
   `<p>` of the same surface** (give the `<p>` `tabIndex={-1}`). The button unmounts once the range
   is full, and without this step keyboard focus would fall to `<body>`, which fails WCAG 2.4.3.
   With focus on the label, a screen reader then reads `Full history: <start> – <end>`, which is
   the result of the click.
6. **The result is the same from every route in.** A range reached by Ctrl/Cmd + wheel, the brush, a
   drag or the keyboard shows the same label and the same control.
7. The scenario composer and every other mount of the strip or rail get the control for free,
   because the component is shared. That is intended.

### I-3 Range persistence (D-02, SC-2)

- On load, the view opens on the **full history**, and the label reads `Full history: <start> – <end>`.
  This holds on every visit, every reload and every opened link.
- A `range=` value in the query string, or in an old `factsheet-v2:<id>` localStorage blob, is
  **ignored and deleted** on load. The URL is rewritten without `range=`, and the blob is rewritten
  without the range field, or removed (Claude's discretion in CONTEXT). Nothing flashes: the first
  painted range is the full history. A narrowed range is never painted and then reset.
- Narrowing a range writes nothing to the URL or to storage.
- Out of scope: the comparator and display-toggle persistence (`cmp`, `cb`, `reg`, `dark`). D-02
  names only the view range (see A-5).

### I-5 Note surfaces: opening writes nothing (D-09, D-10, SC-4, TRUST-06)

Measured 2026-11-06 with `grep -rln useNoteAutoSave src`: five note surfaces. Each one that writes
on open today is in scope.

| Surface | File | Today | After |
|---------|------|-------|-------|
| Strategy note | `src/components/notes/StrategyNoteCard.tsx` | An empty note opens in edit mode with `autoFocus`. On blur it saves the draft unconditionally. | Changed |
| Holding note row | `src/components/notes/HoldingNoteRow.tsx` | Same pattern (`setEditing(!c)` on load, `autoFocus`, unconditional blur save) | Changed |
| Bridge outcome note | `src/components/notes/BridgeOutcomeNoteSection.tsx` | Same pattern | Changed |
| Holding detail note | `src/app/(dashboard)/allocations/components/HoldingDetail.tsx` | Same pattern | Changed |
| Dashboard note | `src/app/(dashboard)/allocations/components/DashboardNoteCard.tsx` | No `autoFocus`. The blur is already dirty-checked. | **Unchanged.** It already writes nothing on open (Rule 3) |

The contract for each changed surface:
1. **Opening never moves focus.** Remove `autoFocus`. An empty note may still open with the textarea
   showing, with the existing placeholder and no focus. The page's focus order is not disturbed.
2. **An explicit "Edit" click moves focus into the textarea.** Do this in the click path (a ref plus
   focus after the textarea mounts), not with the `autoFocus` attribute, which also fires on the
   page-open mount. This keeps DESIGN.md's rule that focus moves to the control the user asked for.
3. **Blur saves only when the text changed and is non-empty** (D-09, literal). Compare the draft with
   the last content known to be persisted, which advances only on a confirmed `"saved"` state (the
   `DashboardNoteCard` idiom). If the draft is unchanged, there is no PATCH. If `draft.trim() === ""`,
   there is no PATCH.
4. **A blur that does not save leaves the card truthful.** If nothing is saved, the card shows what
   is actually stored: the saved note in read mode, or, when nothing is saved, the empty textarea
   with its placeholder. It never shows text the server does not hold as if it were saved. The
   status line (`NoteSaveStatus`) shows nothing for a skipped save: no "Saving…" and no "Note saved".
5. **Writing is unchanged.** Typing real text and blurring saves exactly as today, with the same
   status copy.
6. **D-10 test:** mount each changed surface with no saved note, focus and blur (or open and leave)
   without typing, and assert that `fetch` to `/api/notes` was **not** called. It must go RED
   against today's code. Add one positive arm per surface (type, blur, expect exactly one PATCH), so
   the guard cannot pass by never saving at all.

⚠ **Open question for the founder (see Q-1): clearing a saved note.** With "non-empty" read
literally, a user who deletes all the text of an existing note and blurs gets no save, and the note
comes back on reload. Point 4 makes the card show this honestly, but the user still cannot clear a
note. The "changed" half of D-09 on its own already fixes TRUST-06. The "non-empty" half only
affects clearing. ✅ **ANSWERED 2026-11-07: the founder chose "Allow clearing"** (recommended option): clearing a saved note saves `""`; see CONTEXT D-09 override.

## Assumptions (choices made where neither CONTEXT nor DESIGN.md decides)

- **A-1 — Label wording: keep `Selected range: <start> – <end>`, not `Showing <start> – <end>`.**
  CONTEXT leaves the label wording to Claude's discretion. The label D-03 describes already ships in
  two places, pinned by tests and by the Phase 169.1 contract (T-169-43). Its full-history pair is
  `Full history: …`, and switching between the two strings is itself the signal. Adding a "Showing"
  line next to it would print the same span twice, so one string is kept and nothing is blended in
