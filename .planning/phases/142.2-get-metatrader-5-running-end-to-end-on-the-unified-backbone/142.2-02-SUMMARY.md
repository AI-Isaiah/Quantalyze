# Phase 142.2 Plan 02: MT5 broker-server unmasking Summary

**MT5's broker-server input now renders as legible text via a per-venue `passphraseSecret` flag defaulted to `true`, so OKX's genuine passphrase credential stays dot-masked in both wizard steps — proven by three observed mutations.**

## Accomplishments

- The founder can now read the broker server name they typed, against helper copy that instructs "copy the server name exactly as it appears in your MT5 terminal" — an instruction that was literally unfollowable while the field rendered as dots.
- OKX's passphrase stays masked **by construction**: the flag defaults to `true`, so the OKX config entry is not edited and no hunk in the diff touches it. Every venue that omits the key — existing or future — renders exactly as it does today.
- `MultiKeyConnectStep.test.tsx` gained its first-ever assertion that the OKX passphrase renders masked at all. Before this plan that file had no such assert, so a future "unify the two venue arrays" refactor could have imported the new plumbing with the wrong default and unmasked a real credential with the whole suite green.

## Decisions Made

**1. The default carries D-03's "OKX `true`", not an edit.** PATTERNS.md identified the defaulted-read block (`:390-402`, every default being the OKX value) as the file's existing byte-identity mechanism. Adding `passphraseSecret: true` to the OKX entry would have produced the same runtime behaviour but a diff hunk inside the OKX object — and would have left the *next* venue to omit the key rendering unmasked. `?? true` makes the safe direction the one you get by doing nothing.

**2. Ternary polarity inverted rather than nested.** `passphraseSecret && !showSecret ? "password" : "text"` reads as "masked only when the venue says it's a secret AND the user has not asked to see it", which is the actual rule. The alternative (`passphraseSecret ? (showSecret ? "text" : "password") : "text"`) is behaviourally identical but restates the old ternary inside a new one.

**3. MT5's field ignores the Show/Hide toggle entirely.** A broker server name is not a credential, so there is nothing to reveal. The test asserts `type="text"` after toggling in *both* directions, which is what stops a later refactor from quietly re-coupling it.

**4. The MultiKey regression was written, not relocated.** VALIDATION.md row 2 assigned a byte-identity regression to `MultiKeyConnectStep.test.tsx`, and PATTERNS.md noted the file had no such assert. Since MT5-03 does not touch that component, the row could have been moved to ConnectKeyStep and declared satisfied. It was written instead (~30 lines) because the absence itself was the exposure.
