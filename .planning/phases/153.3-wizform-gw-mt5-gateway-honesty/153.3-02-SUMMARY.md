# Phase 153.3 Plan 02: bind `initialize()`, guard the whole class Summary

**One-liner:** `self._mt5.initialize()` now carries an explicit 20 000 ms ceiling taken from a
per-instance table that every timeout-carrying MT5 call must be registered in, the construction
guard iterates that whole table instead of `MT5_LOGIN_TIMEOUT_MS` alone, and the table's
completeness is derived from `mt5_client.py` on disk with a non-vacuity floor — so the inversion
that censored 9/9 production logins at the 30 s rpyc bound is fixed as a **class**, not an
instance.

## Task 1 — register the class, bind `initialize()`, make the chain per-instance

**`analytics-service/services/mt5_client.py:100-109`** — `MT5_INITIALIZE_TIMEOUT_MS =
int(os.getenv("MT5_INITIALIZE_TIMEOUT_MS", "20000"))`, minted beside `MT5_LOGIN_TIMEOUT_MS`
(`:98`). Its comment records the whole causal chain: MetaTrader5's vendor default for
`initialize(timeout=…)` is 60 000 ms, 2× the 30 000 ms rpyc bound; unset, the FIRST MT5 call of
every login is structurally incapable of answering before rpyc gives up; that is why all 9/9
correlated gateway↔worker failures on 2026-08-06/08 clustered at 30.1–31.0 s — a fixed ceiling,
not a latency distribution.

**`mt5_client.py:111-123`** — `MT5_IPC_TIMEOUTS_MS: dict[str, int]`, mapping each MT5 call that
carries its own `timeout=` to its default (`initialize` and `login` today). Its comment states the
rule in the imperative: **any MT5 call that carries its own timeout MUST appear here**, because
both the ordering guard and the source-derived completeness test read this table, and a call bound
outside it is unguarded *and* untested — which is exactly D-24.

**`mt5_client.py:232-240`** — `__init__` gained keyword-only `initialize_timeout_ms: int | None`
and `login_timeout_ms: int | None`. Resolution (`:242-259`) starts from `dict(MT5_IPC_TIMEOUTS_MS)`
and applies only non-`None` overrides, so:

- a construction with no overrides is byte-identical in resolved values to the module constants —
  `job_worker.py:969`, `services/ingestion/mt5.py:93` and `scripts/mt5_spike.py:439` all pass
  neither;
- a call newly added to the registry is carried on its default even before it earns a ctor
  override (resolution seeds from the registry, not from a hand-listed override tuple).

The resolved map is stored at `mt5_client.py:305` as `self._ipc_timeouts_ms`, on the **instance**,
so `restart()` cannot silently rebuild a shorter chain.

**`mt5_client.py:383`** — the root-cause fix:
`inited = self._mt5.initialize(timeout=self._ipc_timeouts_ms["initialize"])`.
**`:391-396`** — `login()` reads `self._ipc_timeouts_ms["login"]`, not the module constant; without
this a validate instance would log in under the worker's 20 s IPC ceiling and the "longer chain"
would be longer only at the top (the truncation EVIDENCE Correction C-3 describes).

**`mt5_client.py:355-381`** — `login()`'s docstring: the idempotency of `initialize()` is softened
from asserted fact to `[ASSUMED]` with the reason (our empirical observation, not a
MetaQuotes-documented guarantee — EVIDENCE Correction C-7; owner Phase 155), and the timeout
statement is added (both calls carry an explicit ms ceiling registered in the table and guarded at
construction).

**`restart()` (`:501-551`)** re-verified: it rebuilds via `self._connect(host=self._host,
port=self._port, timeout=self._request_timeout_s)` at `:541-543` — the INSTANCE value — and reads
no module constant. No code change was needed; the invariant is asserted in Task 2 instead.

## Task 2 — guard the class, and make the table non-vacuous

### (a) The guard — `mt5_client.py:261-290`

The single `if MT5_LOGIN_TIMEOUT_MS >= request_timeout_s * 1000` is replaced by an iteration over
the resolved per-instance table:

```python
request_timeout_ms = request_timeout_s * 1000
for call_name in sorted(ipc_timeouts_ms):
    ipc_ms = ipc_timeouts_ms[call_name]
    if ipc_ms >= request_timeout_ms:
        raise ValueError(
            f"MT5 {call_name}() IPC timeout must be strictly below the rpyc "
            f"request timeout ({ipc_ms}ms >= "
            f"{request_timeout_ms:.0f}ms) — this inversion reopens the "
            "v1.11 WEDGE-01 wedge class."
        )
```

The load-bearing tail — *"this inversion reopens the v1.11 WEDGE-01 wedge class."* — is verbatim.
The explanatory comment at `:261-279` is preserved and extended: it now records that the guard used
to check `MT5_LOGIN_TIMEOUT_MS` **alone** (the instance its author had in mind) while `initialize()`
ran unbound on the 60 000 ms vendor default, that this is what censored the 9/9 measured failures,
and that the contract suite derives the call set from the source file so a third one cannot land
unregistered. Iteration is `sorted()` so a multi-inversion always names the same call first.

It still fails **at construction**, not at a hung live login — the only posture that makes a bad
`MT5_INITIALIZE_TIMEOUT_MS` env value visible before production.

### (b) The source-derived completeness gate — `tests/test_mt5_client_contract.py:413-473`

`_timeout_carrying_mt5_calls(source)` strips whole-line comments, then for each
`self._mt5.<name>(` walks to the **matching close-paren** (a line-local regex would miss
`login(...)`, which spans four lines) and admits the name if the argument text matches
`\btimeout\s*=`. `test_every_timeout_carrying_mt5_call_is_registered` reads
`pathlib.Path(services.mt5_client.__file__).read_text()` and asserts:

1. `len(derived) >= 2` — the non-vacuity floor;
2. `"initialize" in derived` — the direct pin on the call that was un-timed;
3. `derived - set(MT5_IPC_TIMEOUTS_MS)` is empty.

The extractor itself is tested on synthetic source
(`test_timeout_call_extractor_ignores_comments_and_untimed_calls`, `:476-497`) so a commented-out
call can neither satisfy nor break the gate, and a multi-line call is provably seen.

### (c) Per-call ordering — `:500-527`

`test_every_registered_ipc_timeout_is_below_the_rpyc_bound` is parametrized over
`sorted(MT5_IPC_TIMEOUTS_MS)`, so a newly-registered call is checked the moment it is added.
Beside it, `test_shipped_timeout_chain_is_the_hand_typed_inequality` pins the shipped numbers as
**literals** — `MT5_IPC_TIMEOUTS_MS == {"initialize": 20000, "login": 20000}`,
`MT5_REQUEST_TIMEOUT_S == 30.0`, `20000 < 30 * 1000` — rather than recomputing the relation from
the table under test. The two pre-existing literal assertions at `:329-330` are untouched: one
catches the constants moving, the other catches the coupling breaking, and neither implies the
other.

### (d) `_FakeMt5` observes the timeouts — `:106-118`

`initialize(self, **kwargs)` now records `self.initialize_kwargs.append(dict(kwargs))`, mirroring
how `login` records its kwargs. `test_login_passes_initialize_ipc_timeout` (`:530-546`) asserts a
default construction passes `timeout == MT5_INITIALIZE_TIMEOUT_MS` — asserted against the recorded
kwargs on the double (test-the-wiring), not against the client's own constant expression.

### (e) Per-instance override tests — `:549-636`

## Deviations from Plan

**1. [Plan sequencing] Task 2(a) — the guard iteration — landed in Task 1's commit (`fe9e00e6`).**
- **Reason:** Task 1 introduces the per-instance table *and* the `initialize_timeout_ms` /
  `login_timeout_ms` ctor overrides. Leaving the old single `MT5_LOGIN_TIMEOUT_MS >=
  request_timeout_s * 1000` check in place for one commit would have shipped a tree in which an
  inverting `initialize_timeout_ms=30000` constructs happily — i.e. a knowingly-broken
  intermediate commit that re-ships the exact defect. Task 2's acceptance criteria were still all
  run and evidenced independently (above).

**2. [Rule 3 — blocking] Four test doubles outside the plan's `<files>` needed `initialize(**kwargs)`.**
- **Found during:** Task 1, the moment `initialize(timeout=…)` was bound.
- **Issue:** five in-tree doubles define `def initialize(self)` with no kwargs
  (`test_mt5_client_contract.py:94`, `test_ingestion_mt5.py:81`, `test_mt5_derive_branch.py:135`,
  `test_mt5_sync_path.py:68`, `test_allocator_positions_non_ccxt.py:556`). All five would raise
  `TypeError` on every login, so Task 1 could not be committed green with only the two files the
  plan lists.
- **Fix:** `**kwargs` added to all five, each with a one-line comment recording why. Only the
  contract double records the kwargs (Task 2); the other four ignore them, so no assertion in
  those suites changed. 108 tests across the four files pass.

**3. [Rule 2 — missing critical documentation] The module docstring's "Dual timeout" bullet
(`mt5_client.py:37-58`) was extended.**
- **Reason:** the plan mandates softening `login()`'s docstring only, but the module contract said
  "there are TWO independent timeouts" and described `MT5_LOGIN_TIMEOUT_MS` alone. Leaving it would
  have left the file's own contract asserting the very instance-shaped model this plan deletes.
  It now names `MT5_IPC_TIMEOUTS_MS`, the class-wide guard, the 60 000 ms/9-failure history, and the
  per-instance chain (D-25).

**4. [Rule 2] The source-derived extractor is itself under test.**
- **Reason:** the plan requires stripping comments and pinning a floor. Both defend against
  vacuity, but neither pins the *direction* of the comment rule. Without
  `test_timeout_call_extractor_ignores_comments_and_untimed_calls`, a future edit could make a
  commented-out call satisfy the gate (masking a deleted binding) and stay green. The extractor is
  the load-bearing mechanism of this whole plan; an untested extractor is a vacuous gate wearing a
  floor.

**5. [Anchor drift — for wave 3] `mt5_client.py` line anchors moved.** The new constants and the
guard iteration add lines above every cited anchor. Wave 3 (153.3-03) must re-derive; the current

## What stays UNVERIFIABLE offline — owner Phase 155 (MT5-VERIFY)

CI never installs `mt5linux`; every assertion above runs through the injected `_connect` double.
Three claims are therefore **unproven against a real terminal**, and one of them bounds what this
plan may be said to have achieved:

1. **That MetaTrader5 honours `initialize(timeout=<ms>)` the way `login(timeout=…)` is honoured.**
   The MQL5 docs state the parameter and the 60 000 ms default; that the terminal actually aborts
   the attach at our 20 000 ms is `[DOC]`-stated but not observed. `mt5linux` 0.1.9 evals
   `mt5.initialize(*args, **kwargs)`, so the kwarg reaches MetaTrader5 — the double proves the
   wiring, not the vendor's behaviour.
2. **⚠️ Binding `initialize()` guarantees an ANSWER, not a SUCCESS.** If a real attach genuinely
   needs more than 20 000 ms, validation still fails — but it now fails with MT5's own error code
   inside the rpyc bound (D-02's diagnostic-ordering property) instead of a bare
   `asyncio.TimeoutError` with `code=0`, which `mt5_client.py` emits identically from three
   different arms. So the honest claim for this plan is *"a verdict can now physically arrive"*,
   **not** *"validation now succeeds"*. Whether 20 000 ms is the right number is a data question:
   plan 153.3-05 instruments the real per-stage duration and **Phase 155** reads it.
   Consequently the three worker construction sites are behaviourally identical on the SUCCESS
   path and in the values they pass; their FAILURE mode changes from a censored rpyc abort at 30 s
   to an honest MT5 error at 20 s — which is the entire point of the fix, and is stated here rather
   than papered over as "byte-identical".
3. **Whether the terminal's `initialize()` is truly idempotent when already attached.** Now marked
   `[ASSUMED]` at `mt5_client.py:375-378` (EVIDENCE Correction C-7) instead of asserted as fact.
