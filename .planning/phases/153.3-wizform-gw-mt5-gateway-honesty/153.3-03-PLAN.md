**D-03 + D-02 + D-30.** Today `_MT5_PROBE_TIMEOUT_S` (35 s) is applied **separately** at
`routers/exchange.py:328` (connect), `:380` (probe) and `:456` (close), so the honest worst case

end-to-end deadline** (D-03) while preserving what the `+ 5.0` actually is — a **diagnostic
ordering margin** over the inner rpyc bound so the inner client timeout fires first and yields a

**D-30: `shutdown()` comes OUT of the request path.** `exchange.py:449-466` calls `close()` in
`finally:` on every validate, and `Mt5Client.close()` calls `self._mt5.shutdown()` (`:384`). Per
`153-EVIDENCE-mt5-platform.md` §A2 / Correction C-1, `mt5linux` serves every rpyc connection in
**one `ThreadedServer` process** sharing one `MetaTrader5` module instance — so `shutdown()` from
one request **tears down the IPC pipe for every concurrent caller**, who then observe
`-10004 No IPC connection`. It is a denial of service against ourselves. Attach once; do not tear
down per request.

⛔ **D-28 is SUPERSEDED by D-30** — with `shutdown()` off the request path there is no
per-request close to bound separately. Do NOT implement D-28. Its ONE surviving obligation, which
it shares with RESEARCH **Pitfall 6**, is carried here: **the `finally` teardown must still run on
every path, and must NEVER be wrapped inside the end-to-end deadline** — that would abandon the
RPyC session unclosed when the deadline fires, which is the session leak the `finally` block's
comment exists to prevent.

Purpose: separate "release the lease and our socket" from "shut down the terminal's IPC".
Output: one deadline, a preserved and extended ordering chain, and a request path that no longer
DoSes its neighbours.

Contract, to be written into its docstring citing D-30 and EVIDENCE §A2/C-1: **`release()` ends
OUR use of the terminal without ending anybody else's.** `mt5linux` serves every rpyc connection
from one `ThreadedServer` process over one shared `MetaTrader5` module instance holding one IPC
pipe to one terminal, so `mt5.shutdown()` from one request destroys that pipe for every
concurrent caller (`-10004`). `release()` therefore **never calls `shutdown()`**.

Behaviour:
1. Idempotent — return immediately if already closed/released; then set `self._closed = True`, so
   a later `close()` is structurally a no-op and **cannot** reach `shutdown()`. This ordering is
   the guarantee: after `release()`, the shutdown path is unreachable on that instance.
2. Best-effort close of the rpyc TRANSPORT. mt5linux 0.1.9 exposes no transport close, so reach
   the rpyc connection through the same name-mangled private attribute `_default_connect` already
   uses (`_MetaTrader5__conn`), via a defensive `getattr` chain, and call its `close()`. Carry a
   comment in the same "ponytail" register as `:154-156`, naming the 0.1.9 pin as what makes it
   stable.
3. If no transport close is reachable (the injected offline double, or a future transport shape),
   log a WARNING naming that fact and drop the reference. ⛔ Never silently no-op: a socket that
   is neither closed nor reported is a leak nobody can see.
4. Swallow any raise from the teardown with a logged WARNING, exactly as `close()` does at
   `:385-386` — a teardown failure must never mask the caller's verdict.

Leave `close()` **byte-unchanged**: the worker path (`services/exchange.py:924-938`,
`job_worker`) still uses it and is not in this sub-phase's scope.
