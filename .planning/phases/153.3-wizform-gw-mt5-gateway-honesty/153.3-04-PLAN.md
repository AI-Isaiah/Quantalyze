submissions therefore both call `login(...)` on the ONE shared Wine terminal; the code's own
comment at `exchange.py:352-372` acknowledges the race and mitigates it with a *detect-and-fail*
bracket rather than a queue, so concurrent user #2 does not wait — they make each other **fail**
(`153-EVIDENCE-mt5-latency.md` §4). Fix = take the same lease.

⭐ **The lease needs a BOUNDED acquisition timeout, distinct from the operation timeout.**
Today every `wait_for` sits *inside* the lock, so a queued caller's wait is unbounded and its own
timer starts only once it holds the lock. An interactive validation must be able to **give up
waiting for the terminal without waiting for the terminal**. The daily batch must NOT: it has all
day, and bounding it would convert patient queueing into failure.

⛔ **There is NO account cap.** MT5 binds one account per terminal *at a time* — a
**serialization** constraint, not a capacity one. A daily sync is sequential and latency-tolerant,
so one terminal cycles through hundreds of accounts across a day. The number of MT5 clients is
not architecturally limited. Do not plan, add, mention or test a cap on accounts.

Purpose: serialize the terminal honestly instead of racing it, and bound only the wait that a
human is sitting in front of.
Output: one lease helper on the ONE registry, taken by the validate path, with a refusal that
names an action and leaks no infrastructure.
