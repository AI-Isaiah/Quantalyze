┌───────────────────────────┬───────────────────────────┬───────────────────────────┐
│ RETURN                    │ RISK                      │ HOLDINGS                  │
│ YTD TWR                   │ SHARPE      MAX DD 12M    │ BOOK EQUITY   POSITIONS   │
│ +4.21%                    │ 1.37        -6.80%        │ $412,300      38          │

## Missing-data message (D-01, ROUTE-07, ROUTE-11 shape)

It replaces the generic `EquityHistoryRebuilding` panel and its four class headings, including "We are holding back your equity history" (`EquityHistoryRebuilding.tsx:139`). It sits directly under the at-a-glance panel.

**Shell:** a `<section aria-labelledby>` with the mono eyebrow `WHAT IS MISSING`, then one `<p>` per affected key (or one book-level line), `text-sm text-text-secondary`, left-aligned, `max-w-prose`, no fill, no glyph. Not `role="status"`: it is static at first render (the shipped rationale).

**Line template, per key (verbatim structure):**

`{key label}: no data for {day range}. {action}`

- `{key label}` comes from the ONE key-label rule (`apiKeyLabelById`: `Binance — Main`, or `Binance — ••••4f2a` when the key has no nickname), set at 600 weight in `text-text-primary`. CONTEXT D-01's example (`Binance key "Main"`) is illustrative, and the canonical label wins (OQ-4).
- `{day range}` comes from `formatUnpricedDays` (`Oct 3, 2026 – Oct 11, 2026`; separate runs are joined by `; `; every date is UTC). A single day reads `Oct 3, 2026`.
- `{action}` is chosen by the reason. It always names one place or one wait:

| Reason (producer) | Line |
|-------------------|------|
| key failing to sync (`key_not_syncing`, a `sync_failing` exit) | `{key}: no data for {range}. Reconnect the key on the Exchanges page or wait for the next sync.` |
| incomplete exchange read (`read_incomplete` exit) | `{key}: no complete data for {range}. Wait for the next sync, or reconnect the key on the Exchanges page if this persists.` |
| two keys on one account (`duplicate_account`) | `{key A} and {key B} read the same exchange account. Disconnect one of them on the Exchanges page and the history rebuilds.` |
| every key on one account failing (`shared_account_no_working_key`) | `{key labels}: no data for {range}. Fix or reconnect one of these keys on the Exchanges page.` |
| account identity pending (`account_identity_pending`) | `{key}: we are confirming which exchange account this key reads. Each daily sync checks it again.` |

Fallbacks. These are honest forms, never guesses:
- Day range unknown, key known: `{key}: no data since {day}.` when only the first missing day is known. When neither is known: `{key}: no complete history yet.` The action follows in both cases.
- Key unknown (the producer gives no key): the shipped unnamed sentence for that reason stays (for example "One of your keys is not syncing, …").
- Book-level reasons with no key: `awaiting_derivation` → `Book return and risk are recomputed once a day from each account's returns and cash flows. They appear after the next recompute.`; `derivation_rejected` → `The latest rebuild of your book's history did not pass its checks, so book return and risk are not shown.`; `history_read_failed` → `We could not load your book's history just now. Reload the page to try again.`; `shared_account_history_truncated` → the shipped sentence, unchanged.
- Order: lines are sorted by key label, with book-level lines last (the `FailingKeyExitNote` sort precedent).
- Scope rule (founder: a dead key affects only itself): a line names only its own key. It never says "your keys" or "your book" for a fault on one key. Holdings figures for other keys are never withheld because of it.
- The Scenario own-book sentence (`ScenarioComposer.tsx`, which classes reasons through `equityHistoryRebuildClass`) keeps reading the same class table, so the two surfaces cannot disagree.

Where per-key day ranges come from (the payload today carries a reason, not a range) is planner territory. The UI contract is the template and its fallbacks above.

## Dust (D-04, LEAN-06, SC-4)

- **Rule (verbatim from D-04):** a position worth under $50, or under 0.1% of the book, is dust. The test reads the row's printed USD value as a magnitude (spot: value; derivative: the notional the row prints). It compares strictly: `< 50`, and `< 0.001 × Book equity`.
- **Never dust (Assumed, OQ-8):** a row with no usable price ("No price" or `—`), and a row on an untrusted key (it already has its own `Show holdings from …` filter). When Book equity is not finite, only the $50 test applies.
- **Default:** dust rows are hidden in both the spot and derivatives tables. One control below the derivatives table governs both:
  - Collapsed: `Show {n} small positions` (`n` = dust rows across both tables; `Show 1 small position` when n = 1). `Button variant="ghost" size="sm"`, `aria-expanded="false"`, `aria-controls` set to both table ids.
  - Expanded: `Hide small positions`. Dust rows appear in their normal sort position with no special tint.
  - Under the control, in caption muted text: `Small positions are under $50 or under 0.1% of book equity.`
  - With n = 0, neither the control nor the caption renders.
- **Totals and counts include dust.** The at-a-glance `Positions` count, the Book equity and the Exposure figures are computed over every row. Hiding a row changes the view only, never a figure.
- **State:** the toggle is per page view (`useState`) and is not persisted. A reload hides dust again (D-04's "hidden by default").
- **A11y:** on toggle, `LiveRegion` announces `{n} small positions shown.` or `{n} small positions hidden.`

### Surface

Open and close animate over 250ms (enter ease-out, exit ease-in), with no animation under reduced motion. Esc and the backdrop close it. A close button `×` (`aria-label="Close without adding"`) sits top-right. Only one dialog is in the DOM at a time.

Header: the eyebrow `STEP 1 OF 2 · STRATEGY` or `STEP 2 OF 2 · AMOUNT AND DATE`, then the title `Add allocation`.

**Step 1 — pick a strategy (search)**
- Search input, autofocused: placeholder `Search by name or codename` (the Browse drawer's wording), `aria-label="Search strategies"`.
- Data: the same `/api/strategies/browse` read the Browse drawer uses, fetched once on open, filtered on the client. No new list endpoint.
- Rows: a listbox of 44px-minimum `<button>` rows, separated by hairlines. Each row shows the name (14px, 600), then a caption line: codename and manager (when present), the `TrustTierLabel`, `YoursChip` for an own strategy, and an `In your book` tag (muted neutral badge) for a strategy already held. - Choosing a row moves to step 2. Arrow keys move through rows, Enter selects, and focus moves to the Amount field.
- Footer (caption, muted): `Holding capital on an exchange already? Connect the key on the Exchanges page.` "Exchanges page" links to `/profile?tab=exchanges`. This keeps the connect-a-key path the old button served, without the manager wizard.

**Step 2 — amount and date**
- A strategy line at the top: name, `TrustTierLabel`, and a ghost button `Change strategy` that returns to step 1 with the search text kept.
- `Allocation (USD)`: `type="number"`, `inputMode="decimal"`, 44px. It uses the label `AllocateDialog` already uses, so one concept keeps one name.
- `Allocation date`: a date input that defaults to today (UTC). Allowed range: from 365 days ago up to today (the existing `ALLOCATED_FIELDS` rule; the planner confirms it against the write route it picks).
- Share line, caption muted, live as the user types: `≈ {p}% of your book equity ({Book equity}).` `{p}` is `formatPercent(amount / bookEquity, 1, { signed: false })`. It renders ONLY when Book equity is finite and above zero, and the amount parses. Otherwise no line renders, never a guess (OQ-2).
- Buttons, right-aligned: `Close without adding` (secondary) and `Add allocation` (primary). The primary is never disabled for validation (the `AllocateDialog` rule). It is disabled only while a request is in flight, and reads `Adding…` then.
- The write goes through an existing allocation route chosen by the planner (D-03: "reusing existing allocation APIs"). No new write endpoint. No optimistic row. The row on Holdings appears from the refreshed server data.

## Open questions

For the orchestrator to raise with the founder. Each has a recommended default, already written into this contract.

- **OQ-1 Scenario header button.** Should "+ Allocation" replace the Scenario tab's "+ Strategy" header button (which opens the model's Browse drawer)? Recommended: yes, one label and one action on every tab, per D-03 "on every tab" and SC-1. The composer's own "Browse strategies" button keeps the modelling path. Alternative: keep "+ Strategy" on Scenario only.
- **OQ-2 Amount unit and write route.** D-03 says "amount/date" and "reusing existing allocation APIs". The existing routes differ. `/api/portfolio-strategies/allocation` takes USD but only for the caller's own-capital strategies, and has no date. `/api/allocator/scenario/commit` `voluntary_add` takes `percent_allocated`, `size_at_decision_usd` and `effective_date`. `/api/bridge/outcome` takes percent and date, but only for introduced strategies. Recommended: the UI takes USD + date. The planner picks the route, and if the route needs a share of book, it is derived from Book equity. Then, when Book equity is not finite, the submit returns a field-level message (`We cannot size this allocation until your book equity is available.`), never a guessed percentage. This needs confirmation.
- **OQ-3 Already-held strategy.** Recommended: not selectable, with a pointer to Holdings, so a second position is never minted for one strategy (the `HoldingsTable` D-13 rule). Alternative: allow it and record an additional amount.
- **OQ-4 Key label format.** CONTEXT D-01's example reads `Binance key "Main"`. The app's one key-label rule reads `Binance — Main`. Recommended: the canonical rule (CLAR-04, one name).
- **OQ-5 Message tone.** Recommended: muted, matching the shipped key-scoped notes. Amber would also fit the "user-recoverable" gate, but it would make amber common on Overview.
- **OQ-6 Fold placement.** Recommended as in the fold table. The planner may move a section within its tab, but may not drop one.
- **OQ-7 Flagged holdings.** Recommended: a row chip and row action, so each position is listed once. Alternative: keep the separate list and accept a second listing of flagged positions.
- **OQ-8 Dust edges.** Derivative dust is tested on the printed notional's magnitude. Unpriced rows and untrusted-key rows are never dust. Recommended as stated.
- **OQ-9 Decimal places.** The Scenario strip prints YTD TWR at 2dp, while the DESIGN.md Numbers Contract asks for percentages at 1dp. CLAUDE.md Rule 7 says to pick one and not blend them. This contract picks byte-parity with Scenario (TRUST-04, the newer and tested rule) and flags the Scenario strip's 2dp for a later Numbers-Contract cleanup. It does not widen the glance panel's own rule.
- **OQ-10 Entry point.** `/allocations?add=<strategyId>` is recommended for Phase 196 to link to. The planner locks it, and Phase 196's plan uses the same string.
