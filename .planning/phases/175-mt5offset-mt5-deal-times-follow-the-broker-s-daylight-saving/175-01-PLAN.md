<objective>
Give the one MT5 server-time seam a broker clock that follows a daylight-saving rule, prove on the
reviewer's own numbers that a winter deposit made after a mark's read is no longer filed on the mark
day, and add the one fail-loud resolver every consumer will use.

Purpose: SC-2 ("MT5 deal day bucketing and D-23 instant placement use the offset in force on the
deal's date; tests go RED with the fixed `MT5_SERVER_UTC_OFFSET_S` across a DST change") and D-01
("A pure function gives the offset in force at a broker-clock instant; every MT5 deal day and instant
uses it ... an unknown or unset rule fails loud; a fixed-integer form stays for a no-DST broker. One
resolver replaces the scattered ... reads"). The consumers are wired in plans 03 and 05.

Reading of RESEARCH Open Question 1, stated here so the checker and the founder can object: D-01's
"unset rule" means NO clock configuration at all. The fixed-integer form IS a configured rule (the
form D-01 keeps for a no-DST broker), so `MT5_SERVER_UTC_OFFSET_S` alone resolves to the fixed clock.
What fails loud: neither variable set (today's silent `"0"` default is removed), an unknown rule id,
a rule id together with the integer (two answers, so neither wins), and a malformed or out-of-range
integer. Production carries only the integer today, so deploying this phase changes no derived
number; history re-buckets at the moment the rule id is set (plan 06). Rule ids are `eu` and `us`
only; there is no third id for the fixed form, because the integer alone already says it.

Output: `services/mt5_server_clock.py` (new pure leaf), the widened seam in `services/mt5_deals.py`,
`tests/test_mt5_server_clock.py` (new), extended `tests/test_mt5_deal_timing.py`.
</objective>

- Seam: `deal_utc_day(time_value: Any, server_utc_offset_s: int | Mt5ServerClock) -> str`, `deal_utc_instant_ms(deal, server_utc_offset_s: int | Mt5ServerClock) -> int | None` (parameter name kept, RESEARCH Open Question 2).

Algorithm (RESEARCH Pattern 1, validated at planning time against zoneinfo on 420,864 quarter-hours 2024-2029 with 0 mismatches, and the day-invariance property 2007-2099 with 0 violations):
- Standard offset 7200, daylight offset 10800 for both DST rules.
- Per rule and year, the UTC daylight window [start, end): `eu` = (last Sunday of March at 01:00 UTC, last Sunday of October at 01:00 UTC); `us` = (second Sunday of March at 07:00 UTC, first Sunday of November at 06:00 UTC). Memoize the window per (rule, year) with `functools.lru_cache`; never cache the env read.
- For a wall epoch w (the broker wall clock encoded as if it were UTC, the quantity a deal's `time` already is), the year is w's own calendar year; offset o in (10800, 7200) is a candidate iff (o == 10800) equals (start <= w - o < end). One candidate: unambiguous. Two: repeated hour. None: missing hour.
- `day_offset_s`: the first candidate, or 7200 when there is none (zoneinfo fold=0 semantics). `instant_offset_s`: the single candidate, else None. The fixed form returns `fixed_offset_s` from all three methods without computing a year.
- DST rules cover years 2007-2099 only (the US statute changed in 2007): outside that, or for an undatable epoch, the methods raise ValueError (or let OverflowError/OSError from the datetime conversion propagate). The seam maps all three to its existing out-of-range message.
