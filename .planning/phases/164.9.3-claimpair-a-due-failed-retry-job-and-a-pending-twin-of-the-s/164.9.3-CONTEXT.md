### C. The fix mechanism (ROADMAP criterion 2 leaves it to the planner, with evidence)

- **D-08: CLAIM-SIDE fix, applied BEFORE ranking; the enqueue side is unchanged.** In every claim
  body the candidate set (the `ranked` CTE's `WHERE`, i.e. before `row_number()`) drops a
  `failed_retry` job whose `(kind, partition key)` already holds a `pending` job - one clause per
  partition (portfolio, strategy, allocator, api_key), each matching its sibling
  `compute_jobs_one_inflight_per_kind_*` index predicate exactly (the strategy clause excludes
  `compute_intro_snapshot`, which that index does not cover). Placement:
  `claim_compute_jobs(integer, text)` re-based from `20260603120000`; the 5-arg
  `claim_compute_jobs_with_priority` re-based from `20260719073701`; the 2-arg
  `claim_compute_jobs_with_priority(integer, text)` re-based from `20260428190907` and ALSO given the
  existing C39 running / done_pending_children guard it lacks. The 2-arg overload is re-based, not
  dropped: every call form raises 42725 today, but dropping it makes VAC-04 fail
  `SNAPSHOT_MISSING` with no acknowledgment path.
  **Evidence (RESEARCH.md, measured on a throwaway pg-lane with the bodies copied from the
  baseline):** today, 8 of 8 cells (4 partitions x {`claim_compute_jobs`, 5-arg}) raise 23505, the
  whole batch aborts (an unrelated due job on another partition is not claimed), and 4 consecutive
  ticks all raise - it never self-clears. The ROADMAP-booked option (a), adding `'pending'` to the
  post-ranking C39 status list, turns the loud error into a SILENT permanent wedge (neither job ever
  claimed, 8 of 8 cells) and starves `compute_intro_snapshot` (0 of 3 claimed vs 3 of 3 today), so
  it is REJECTED. The pre-ranking clause: 0 raises on 8 cells, the unrelated job is claimed, the
  pending twin runs (at once if due, else when due), the retry runs after the twin finishes (no
  work lost), intro snapshot still claims 3 of 3, and a due retry plus a due twin in one batch is
  handled because the retry never enters the ranking.
  **Why not the enqueue side (option b):** it would not repair pairs that already exist on PROD,
  folding a new request into an older job can lose its payload, and it would break the text two
  existing mutation twins match on. The class is closed at the one place every writer's rows meet:
  the claim.
  **Recorded, not fixed (named in the migration header):** (i) the 5-arg throttle still counts a
  retry the new clause holds back, so a due retry beside a far-future twin can hold back
  low-priority jobs until the twin is due - C39 already over-counts the same way and it is strictly
  better than today's full wedge; (ii) a retry waits for a not-yet-due twin to run first;
  (iii) a claim racing a concurrent enqueue could still raise 23505 for one tick (reasoned, not
  measured).
  **D-05 consequence:** the migration edits NONE of `defer_compute_job`, `mark_compute_job_done`,
  `mark_compute_job_failed` or `_enqueue_compute_job_internal`, so there is no overlap with 164.9.3.2
  DEFER40001 or 164.9.3.1 FANINGRAPH, and no ordering constraint arises; the plan states this.

**D-08 RATIFIED 2026-09-27 (founder, AskUserQuestion "Planner's fix"):** the pre-rank claim-side exclusion ships; the ROADMAP-booked option (a) stays rejected on the lane evidence above.

**D-04 AMENDED 2026-09-27 (orchestrator decision, review round 1; reversible by the founder before merge):**
three independent reviewers measured the same defect on a throwaway pg-lane. The reviewers were the
code reviewer (WR-01), silent-failure-hunter (HIGH) and migration-reviewer (MEDIUM).

The defect is in the 5-arg `claim_compute_jobs_with_priority`, with the same shape in the 2-arg. The
throttle probe still counts a due `normal`/`high` `failed_retry` that the D-08 pre-rank clause holds
back. So a retry beside a `priority='low'` pending twin leaves NEITHER row claimable, on every tick,
and throttles every `low` job queue-wide. It raises no error: a silent permanent wedge where the old
23505 was loud. Residual (i) above called this "until the twin is due … strictly better", and that
is false for a low twin.

It is latent: no repo writer sets `low` today. But the column comment names `low` as the post-deploy
backfill class.

The fix belongs in this phase, not in a deferral. It is the same pre-rank exclusion, applied to the
throttle probe in both priority overloads, as its own marked block. It is still claim-side and still
before ranking, so D-08 as ratified stands. D-04's "no bytes outside the guard" now reads "no bytes
outside the marked CLAIMPAIR blocks", and the probe block is one of them. A red-first gate arm for
the low-twin cell precedes the code change (D-03). Residual (i) is restated in every file that
carries it.

**FOUNDER DECISIONS 2026-09-27 (AskUserQuestion, before merge; both resolve the two human items in 164.9.3-VERIFICATION.md):**

- **D-04 amendment RATIFIED (kept).** The `CLAIMPAIR PROBE EXCLUSION` blocks in both priority
  overloads ship. D-04 reads "no bytes outside the marked CLAIMPAIR blocks" from here on. The
  "orchestrator decision, reversible by the founder before merge" note above is closed: the founder

- **D-11: round-2 WR-01 is FIXED NOW, in this phase (not routed).** The throttle probe also skips a

  the same `(kind, partition)`. Every sibling test inside the marked PROBE EXCLUSION blocks widens

  layered mutation twin, and census pins moved by measurement (D-06). The migration header's
  residual (i) "What stays" sentence, the CHANGELOG entry and the TODOS closure are corrected to
  match. Still claim-side, still inside the marked blocks, so D-08 as ratified and D-04 as amended
  both stand.
- **D-11 refinement (orchestrator, 2026-09-27, from review iteration 3, measured on a pg-lane).** Read
  literally, "widen to `IN ('pending','running','done_pending_children')`" is not exact for the
  STRATEGY disjunct: the probe's strategy carve-out for `compute_intro_snapshot` would then also
  cover `running`/`done_pending_children` siblings, which C39 does drop (C39's strategy clause has
  no intro carve-out), so an intro retry beside a running intro sibling would still throttle every
  `low` job. The founder's intent is that the probe skips exactly what C39 holds back, so the
  strategy disjunct uses the split form (carve-out on the `pending` sibling only); the other three
  disjuncts widen literally. A second red-first arm (the intro `running` shape) tells the two forms
  apart.
