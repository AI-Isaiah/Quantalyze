## Decisions Made

- **Trap `WHEN OTHERS`, not `WHEN unique_violation`.** The plan's key_links names `unique_violation`. `OTHERS` keeps arm identity for every failure class, which lint R1 and the mutation runner's first-failure attribution both need. The handler holds only `GET STACKED DIAGNOSTICS`.
- **No literal `23505` in any RAISE text.** It appears only through the trapped `%` SQLSTATE, placed first in the message, so the census grep counts real collisions and nothing else.
- **Arms generated from one template** (a scratch generator, not committed), so the 14 non-tracer arms share the seed, trap and assertion shape byte for byte apart from partition, kind and entry point.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The replica-only seeding route fails at the claim with 23503; parents are now seeded too**
- **Found during:** Task 2, first census run.
- **Issue:** The plan's primary route is replica role for the INSERTs and `origin` before the claim, with no parent rows. It passes A1 as a capability but fails in use. W-INTRO, the only arm whose claim UPDATE gets past the unique indexes on the pre-fix tree, was RED with `23503`, and its message named `compute_jobs_strategy_id_fkey`. PostgreSQL re-checks a foreign key on an UPDATE of a row inserted in the same transaction, even when the key is unchanged. So the claim's own UPDATE checks the parents the replica seed skipped. The other 14 arms hid this behind their 23505. After plan 02's fix, every arm would have gone RED with 23503 and the census would have measured nothing.
- **Fix:** Every arm now also inserts a real parent row for each partition id it uses: `auth.users` (allocator), `api_keys`, `portfolios` or `strategies`, with only the parent's NOT NULL columns. These inserts run under the same replica role, so no parent trigger fires (for example `portfolios_seed_weight_snapshots_trigger` or `api_keys_stamp_first_added`) and nothing can enqueue a job onto an arm's partition. The claim still runs under `origin` with every compute_jobs trigger live. This is the plan's own named fallback ("real parent rows"), taken on measurement. It does not run the claim under the replica role, which would have dodged the check. The header now states the route and the reason. The Task 1 arm C-KEY was regenerated onto the same route in the Task 2 commit.
- **Files modified:** `supabase/tests/test_claim_compute_jobs_failed_retry_pending_pair.sql`
- **Verification:** W-INTRO GREEN. The scratch seed probe claimed 4 of 4, one per partition, and an in-transaction UPDATE to `done` succeeded. The census reads 14 RED with 23505 and 0 non-arm errors.
- **Committed in:** `f7ecd0159`
- **Finding, not an edit:** the replica-role recipe cited from the ROADMAP `### Phase 164.5.2` lineage repro is incomplete for any gate that claims or UPDATEs its own seeded rows in the same transaction. This is recorded here and was not changed in the ROADMAP.
