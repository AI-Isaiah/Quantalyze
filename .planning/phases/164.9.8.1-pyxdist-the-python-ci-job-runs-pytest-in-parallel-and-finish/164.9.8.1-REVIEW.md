**Round-2 WR-02: fixed, and the fixer found a real defect behind it.**

- The old ceiling was `asyncio.timeout(loop.time() + 30)`. `asyncio.timeout` takes a DELAY, so the ceiling was the loop clock's value in seconds: it never fired. My round-2 premise ("a 30 s ceiling expiry is indistinguishable from the aimed one") was therefore wrong in its mechanism. The real effect was worse: a never-reached rendezvous HUNG instead of passing.
- `asyncio.timeout_at` is correct on the pinned Python 3.12 (`ci.yml` `python-version: "3.12"`, `Dockerfile` `python:3.12-slim`).
- No other `asyncio.timeout(... time() ...)` misuse remains under `analytics-service/` (grep, `.venv` excluded).

**The `pytest.fail` inside a route's `wait_for` stand-in cannot be swallowed or remapped on any patched path.**
`pytest.fail` raises `Failed`, an `OutcomeException`, which is a `BaseException`
and not an `Exception`. I read every handler that wraps a stand-in `wait_for` in
the patched modules: `routers/exchange.py`, `services/ingestion/mt5.py`,
`services/mt5_terminal_scrub.py`, `services/mt5_relogin.py` and
`services/mt5_session_monitor.py`.

- They are all `except asyncio.TimeoutError`, `except asyncio.CancelledError` (which re-raises) or `except Exception`.
- Every `except BaseException` in those modules sits inside a LOGGING fallback with no `await` in its `try` (for example `mt5_terminal_scrub.py:577,627,680,702,790` and `mt5_session_monitor.py:399,494,513,539`). None encloses a stand-in wait.
- The `finally` blocks run more awaits (`client.release`, `close()`) but do not `return` or `raise`, so `Failed` keeps propagating. A second stand-in wait in a `finally` would add `Failed` as the context of a second `Failed`. It cannot turn the first into a pass.
- `mt5_terminal_lease` is an `@asynccontextmanager` and does not suppress.
- In the scrub test the wait runs inside a background task. `_drain_scrub_tasks` uses `asyncio.gather`, which re-raises the stored `Failed`.

I checked the helper semantics directly with a throwaway probe file (7/7 passed;
the file was removed afterwards, and `git status` is clean). The probe set the
ceiling to 0.3 s through the module global. It covered:

- the wrapper, never-reached: fails with the never-reached message;
- the wrapper, reached: passes;
- the wrapper, when the awaitable raises its own `TimeoutError` before the rendezvous: fails;
- the stand-in behind an `except asyncio.TimeoutError: return ...` / `except Exception: return ...` route: `Failed` propagates, and is not mapped;
- the stand-in when reached: maps to the timeout branch as before;
- nested never-reached stand-in waits: the outer ceiling fires first, the inner one sees only `CancelledError`, and the outer one fails;
- the stand-in inside a task drained by `gather`: fails.

**`_drive()`'s `finally` placement in `test_ingestion_mt5.py:640-645` is correct.**
`asyncio.run` runs `shutdown_default_executor()` after the main coroutine
finishes, and that joins the parked login thread. The release must therefore
happen inside the loop, before that join. The `finally` also runs when `Failed`
propagates, because `Failed` is stored on the main task (it is not
`KeyboardInterrupt`/`SystemExit`) and re-raised from `run_until_complete`, after
`_drive`'s `finally` has run.

**The session-monitor exemption** (`_tick_deadline_never_bites`, a never-set
Event) is unchanged in behaviour on the normal path. The heal completes well
inside 30 s, and each tick's `wait_for` starts a fresh ceiling, so a long-running
loop does not build up toward it. See IN-01: the "fails at the ceiling" branch
cannot be reached inside those tests.
