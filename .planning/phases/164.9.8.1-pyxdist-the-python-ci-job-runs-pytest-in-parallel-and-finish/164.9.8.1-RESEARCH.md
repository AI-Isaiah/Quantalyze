# Phase 164.9.8.1: PYXDIST — the python CI job runs pytest in parallel - Research

**Researched:** 2026-10-14
**Domain:** pytest-xdist scheduling, pytest-cov under xdist, Python test-isolation (sys.modules pollution), GitHub Actions CI wiring, vitest wiring pins
**Confidence:** HIGH. Both flakes were reproduced deterministically on this tree, and the mechanisms were read in the installed xdist and pytest-cov source. Only the CI wall-time projection is MEDIUM: it rests on local ratios.

## Summary

**The Phase 97 "fence flake" has a root cause that Phase 97 never saw: the `shared_test_db` xdist group has never existed.** `tests/conftest.py` adds the `xdist_group("shared_test_db")` marker in a plain `pytest_collection_modifyitems` hook. On every xdist worker, xdist's own `WorkerInteractor.pytest_collection_modifyitems` (which appends `@<group>` to the nodeid, the thing `--dist loadgroup` schedules on) is registered *after* the conftest. Pluggy calls the later registration first, so xdist reads the markers *before* the conftest adds them. The result: no nodeid ever gets the `@shared_test_db` suffix, and every live-DB test is its own scheduling unit. Measured on this tree under `-n 4 --dist loadgroup`, `test_compute_jobs_fencing.py`, `test_drain_semantics.py`, `test_transition_rpc.py`, `test_compute_similarity_sql.py` and `test_live_db_transport.py` ran on all of gw0..gw3, with **0** `@shared_test_db` suffixes. The fence tests all seed `sync_trades` rows and claim with `p_kind_include: ['sync_trades']`, batch 50, so concurrent fence tests on different workers claim each other's pending rows. That is exactly Phase 97's recorded symptom ("seeded row claimed out of the batch → None"). The fix is one decorator, `@pytest.hookimpl(tryfirst=True)`, on the existing conftest hook. With it, measured on the real tree, all 84 grouped tests ran on one worker in **exactly serial collection order, 3/3 runs**.

**The limiter-identity flake is order-dependent `sys.modules` pollution, reproduced deterministically.** `tests/limiter_stub.py::evict_module` pops `sys.modules[name]` **and deletes the `routers` package attribute**. Ten test files call it in fixture teardown and never restore the prior module. The victim resolves `routers.exchange` / `routers.portfolio` through the package attribute at call time, so it raises `AttributeError: module 'routers' has no attribute 'exchange'`. Serial runs never fail, because the victim always runs after its own sibling classes, which re-import the routers and heal the attribute. Under `--dist loadgroup` every ungrouped test is its own scope, so the victim can land right after a polluter test on the same worker. An exhaustive pairwise bisect (315 files, each run before the victim alone, serially) found 9 polluter files; a test-granularity pass found a 10th. The root-cause fix goes in the polluters: restore the exact pre-test module object and package attribute.

**Coverage and wall time.** pytest-cov combines worker data on the controller and evaluates `--cov-fail-under` only there. Measured on the same offline tree, the totals are identical (93.57%, 1559 of 24238 statements missed, serial and `-n 4`). A floor that cannot be met exits 1 under xdist. Locally (offline, 10-core Mac) the current command takes 429 s serial and 205 s at `-n 4`: a 2.1x speedup. CI today: job 18m12s-20m27s, pytest step 15m16s-17m13s, about 2m35s-2m49s of fixed pre-pytest overhead. Halving the job therefore needs the pytest step to run about 2.6x faster. xdist alone is projected to land near 55-60% of the job, not 50%. **The largest single cost is not parallelism: under coverage.py's default `ctrace` core on Python 3.12, four `test_qstats_gate.py` tests take 37-76 s each, versus 2-5 s without coverage.** With `COVERAGE_CORE=sysmon` the same suite takes 157 s serial and **69 s at `-n 4`**, with identical coverage. Switching the core is outside the locked command (D-06), so it is raised below as a founder decision, not planned.

**Primary recommendation:** Land three changes before the soak, each shown RED first: (1) add `tryfirst=True` to the conftest grouping hook, with a subprocess gate proving the group is real; (2) make every `evict_module` call site restore exactly what it evicted; (3) the D-06 command in `ci.yml` and the Makefile, plus the D-07 byte-identity vitest pin. Then run the D-01/D-02/D-11 soaks on the local-stack lane.

## Flake 1 — the Phase 97 global-claim fence flake (REPRODUCED as a mechanism; root cause found)

### What Phase 97 recorded
The original TODOS entry (`P3: analytics python CI parallelization deferred (#610 absorption)`, added in `be215b157`, 2026-07-12) said: "fail non-deterministically under xdist ordering even with every live-DB module pinned to one `shared_test_db` group — imperfect per-test `compute_jobs` cleanup pollutes a later global-`claim_compute_jobs_with_priority` assertion (tie-break picks a foreign row / `single()` → 0 rows / seeded row claimed out of the batch)" [VERIFIED: `git show be215b157 -- TODOS.md`]. ⚠️ **That entry no longer exists in `TODOS.md`.** It was dropped by the tracker consolidation `193afe818` (2026-07-23), which re-added nothing about xdist [VERIFIED: `git show 193afe818 | grep '^+.*\(xdist\|paralleli\|#610\)'` → no lines]. The `ci.yml:5594` pointer "(TODOS: v1.9.1 Phase-97 parallelization deferral)" is therefore DANGLING. The lineage survives only in `.planning/milestones/v1.9.1-ROADMAP.md:26,41` and `.planning/MILESTONES.md:214,219`.

### The actual mechanism: the group was never applied

1. The conftest adds the marker in a hook with NO ordering argument [VERIFIED: `analytics-service/tests/conftest.py:57-60`]:
   ```python
   def pytest_collection_modifyitems(config, items):
       for item in items:
           if _is_shared_db_module(str(item.fspath)):
               item.add_marker(pytest.mark.xdist_group("shared_test_db"))
   ```
2. On each worker, xdist builds the config first (`config = _prepareconfig(args, None)`, `xdist/remote.py:420`, which loads `tests/conftest.py` as an initial conftest). Only then does it create `interactor = WorkerInteractor(config, channel)` (`remote.py:426`), whose `__init__` runs `config.pluginmanager.register(self)` (`remote.py:122`) [VERIFIED: read in `.venv/lib/python3.12/site-packages/xdist/remote.py`].
3. The interactor's hook turns markers into the scheduling key [VERIFIED: `xdist/remote.py:236-254`]:
   ```python
   if config.getvalue("loadgroup"):
       for item in items:
           gnames: set[str] = set()
           for mark in item.iter_markers("xdist_group"):
               ...
           if not gnames:
               continue
           item._nodeid = f"{item.nodeid}@{'_'.join(sorted(gnames))}"
   ```
   Pluggy calls a later-registered implementation first, so this runs BEFORE the conftest's hook, finds no markers, and appends no suffix. `LoadGroupScheduling._split_scope` then returns the plain nodeid (`xdist/scheduler/loadgroup.py:55-59`), so every DB test becomes its own work unit.
4. **Measured on this tree** (offline, `-n 4 --dist loadgroup -v` over the five PostgREST live modules): tests spread across gw0, gw1, gw2 and gw3, and `grep -c "@shared_test_db"` gave **0**.
5. **Isolated reproduction** (scratch project, 6 "db" + 6 "off" tests, `-n 3 --dist loadgroup`): conftest hook without `tryfirst` → db tests on gw0/gw1/gw2. The same hook with `@pytest.hookimpl(tryfirst=True)` → all on gw0, nodeids suffixed `@shared_test_db`.
6. **The fix, validated on the real tree** (a scratch `-p` plugin carrying the same logic with `tryfirst=True`): `test_compute_jobs_fencing.py` (47), `test_drain_semantics.py` (6) and `test_live_db_transport.py` (30) all ran on gw0 and were GROUPED, while `test_account_identity.py` spread across gw1-gw3. The in-group execution order was **identical to serial collection order in 3/3 runs** (84 grouped tests, `cmp`).
7. The hook has had this shape since it was written: `be215b157`'s conftest carries `def pytest_collection_modifyitems` with no `hookimpl` decorator [VERIFIED: `git show be215b157:analytics-service/tests/conftest.py`]. **So the Phase 97 run had concurrent fence tests on different workers.** The "loadgroup-variable order" reading in `ci.yml:5586-5590` was wrong.

### Why concurrency produced exactly the recorded symptoms
- `test_compute_jobs_fencing.py` seeds `"kind": "sync_trades"` at 26 sites and claims through `_claim_one(... kind=...)`, which calls `claim_compute_jobs_with_priority` with `"p_batch_size": 50` and `"p_kind_include": [kind]` and returns only the row whose id matches the test's own job [VERIFIED: `tests/test_compute_jobs_fencing.py:842-849`]. When two fence tests run concurrently on different workers, one test's batch-50 claim moves the other's pending `sync_trades` row to `running`. The other test's `_claim_one` then returns `None` ("seeded row claimed out of the batch"). Before `want_job_id` scoping existed, the same race produced "tie-break picks a foreign row".
- The module also calls the GLOBAL watchdog `reset_stalled_compute_jobs` (5 sites) and `claim_compute_jobs` (1 site). `test_drain_semantics.py` claims `process_key_long` globally (4 sites), and `test_live_db_transport.py` writes `compute_jobs` (6 sites). Under the broken grouping, all of these interleave across workers.
- **Why the ROADMAP's two local `-n 4` passes did not exercise this:** they report 10009 passed, which equals the OFFLINE count (this session, offline: 10009 passed, 90 skipped). CI with the lane runs **10027 passed, 70 skipped, 2 xpassed**. The ~20 live tests skipped locally.

### Root-cause fix (in the polluters, per D-02)
Every eviction must be paired with an exact restore of (a) `sys.modules[name]` and (b) the package attribute, to the objects present before the fixture ran. Do this with ONE helper in `tests/limiter_stub.py` (the module that already owns `evict_module`), so all 20 `evict_module` call sites and the `routers.cron` evictions use the same mechanism. Illustrative skeleton (design is **[ASSUMED]**; names are the planner's call):
```python
_ABSENT = object()

@contextlib.contextmanager
def evicted(name: str):
    """Evict `name` for the duration, then restore EXACTLY what was there."""
    package_name, _, attribute = name.rpartition(".")
    package = sys.modules.get(package_name)
    prior_module = sys.modules.get(name, _ABSENT)
    prior_attr = getattr(package, attribute, _ABSENT) if package is not None else _ABSENT
    evict_module(name)
    try:
        yield
    finally:
        if prior_module is _ABSENT:
            sys.modules.pop(name, None)
        else:
            sys.modules[name] = prior_module
        if package is not None:
            if prior_attr is _ABSENT:
                if hasattr(package, attribute):
                    delattr(package, attribute)
            else:
                setattr(package, attribute, prior_attr)
```
⚠️ `monkeypatch.delitem(sys.modules, name, raising=False)` is NOT a drop-in: when the key is absent it records nothing, so a freshly imported stub module would survive teardown.
⚠️ The victim's assertion stays byte-identical (D-02). Do not "fix" it by re-importing inside the victim. That would hide the polluter.

### Anti-Patterns to Avoid
- **`--dist load` or `--dist loadfile`** to "simplify": `loadfile` would group the fence module with itself but not with drain/transport. Both break the cross-module serialization the sentinels define.
- **Re-importing the routers inside the victim.** That hides the polluter (D-02).
- **`-p no:xdist` for the live modules, or a second serial pytest invocation with `--cov-append`.** That is the Phase 97 TODO's suggested workaround, and D-04 forbids it.
- **Adding `psutil`** (Pitfall 4).

## Common Pitfalls

### Pitfall 1: Believing the group exists because the marker is visible
**What goes wrong:** `pytest --collect-only` and `item.iter_markers()` show `xdist_group` (the conftest adds it), but xdist's suffix was computed earlier.
**Warning signs:** under `-v` with `-n ≥2`, no result line ends `@shared_test_db`; DB tests appear on several `gw`.
**How to avoid:** the subprocess gate in Validation SC-1a asserts the suffix and the single worker on a REAL `-n 2` run.

### Pitfall 2: A green serial run "proves" isolation
**What goes wrong:** serial order hides both flakes: the victim's siblings heal the attribute, and the DB tests are sequential.
**How to avoid:** prove the fixes with the deterministic pair commands and `-n 1` orderings above, not with a full serial run.

### Pitfall 3: Offline soak counted as the D-11 soak
**What goes wrong:** with no lane, ~20 live tests skip (10009/90). The Phase 97 class is invisible.
**Warning signs:** pass/skip counts equal 10009/90 instead of ~10027/70/2 xpassed.

### Pitfall 4: `psutil` silently halves the worker count
`pytest_xdist_auto_num_workers` prefers `psutil.cpu_count(logical=False)` (PHYSICAL cores) when psutil imports (`plugin.py:26-33`). On a 4-vCPU VM exposing 2 cores × 2 threads, that is 2. Do not add psutil, and do not let a dependency bump drag it in. Check `created: 4/4 workers` in the CI log at ship.

### Pitfall 5: The D-04 handoff row moves but stays vacuous
`l.includes(firstDbStep)` over live lines. If the new substring also matches a COMMENT, `liveLines` already filters `#` lines, so this is safe. But make sure the substring cannot match the `Lane handoff` step text (it does not contain `pytest`).

### Pitfall 6: Stale `.coverage.*` files
An aborted xdist run leaves `analytics-service/.coverage.<host>.<pid>.<rand>` (not gitignored: only `.coverage` is). The next run's controller combines every `.coverage.*` in the directory, so stale data can inflate the TOTAL. `rm -f .coverage .coverage.*` before each soak run, and `git status --porcelain analytics-service` must be clean before commit.

### Pitfall 7: The key literal in new ci.yml comments
`critical-regressions.test.ts` (~`:2074`) reads `ci.yml` comments for the shared-test-db advisory key number. Write "the shared-test-db key" in prose.

### Pitfall 8: Coverage version drift
`coverage` is unpinned: 7.15.0 locally, 7.16.2 in CI. Compare TOTALs within one environment only (D-09 is about serial vs `-n auto` on the same tree and box).
