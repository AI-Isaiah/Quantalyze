## Findings (MEDIUM and above)

### SFH-01 - MEDIUM (confidence 5/10) - scroll cue is not re-measured when content width changes

`src/components/strategy/StrategyTable.tsx`, effect around lines 920-952 (`measure`, deps `[density, page, effectiveViewMode, paged.length]`).

The `ResizeObserver` observes only the scroll container's own box (`ro.observe(el)`). `scrollWidth` is driven by the table inside it, and that box does not resize when the table does. Content-driven width changes with an unchanged row count never trigger `measure`: web-font swap on a phone, a search or filter that keeps the same `paged.length` but changes cell text or sparkline width, `managerRows` or the star column toggling. If the first measurement ran before the table reached its final width, `hasMoreToScroll` stays `false`. The cue is hidden, no `scroll` event ever fires (the user has no reason to scroll), and `measure` is never retried.

Impact: D-01 removed the `More` disclosure, so the right-edge fade and "Scroll for more columns" hint are now the only visible sign that Volatility, 6 Month, AUM and both sparklines exist. A stale `false` fails silently with no log or error. The old `isOverflowing` gate had the same blind spot, but it was then backed by the per-row disclosure. This change removed that backup.

Scenario: a phone loads Discovery, the first measure runs against fallback-font metrics where the table fits (or nearly fits), the web font then swaps to a wider face, and the cue never appears.

Recommendation: also `ro.observe(el.firstElementChild)` (the `<table>`), or observe both. Alternatively re-run `measure` from a `document.fonts.ready` handler. The e2e and unit tests cannot catch this. The jsdom test stubs `ResizeObserver` as a no-op and sets `scrollWidth` by hand, and the e2e measures after a settled load.
