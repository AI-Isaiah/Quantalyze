## Implementation Decisions

### SC-1: phone table (founder "Accept", 2026-10-13)
- **D-01:** Every column is always rendered in the scrolling region.
  - The `@max-3xl:hidden` collapse on Volatility, 6 Month and AUM is deleted, and so are the two sparkline columns' collapse classes.
  - The per-row `<details><summary>More</summary>` is deleted, along with its `@3xl:hidden` "Details" header and cells.
  - The cells render the same single-source values (`volatilityText`, `sixMonthText`, `aumText`). Honest nulls stay "—", never 0.
  - Existing tests that pin the collapse (phase-52 Tests 2a-2c, the sticky-class pins) are rewritten to assert the new contract. They are never deleted without a replacement.
- **D-02:** The right-edge fade and its "Scroll for more columns →" hint show only while there is more to scroll (`scrollLeft + clientWidth < scrollWidth - ε`). Add a scroll listener to the existing ResizeObserver effect. Add a small trailing inset on the last column as a backstop. At the scroll end, Simulate Impact is fully visible and is the element at its own centre point.
- **D-03:** Name-column pinning below `@3xl` is unchanged. This phase does not revisit 170.2 D-05.
- **D-09 (founder, 2026-10-14, supersedes D-03):** Below `@3xl` the Strategy name column is PINNED. The PR-A code review (170.6.1-03-REVIEW.md WR-02) measured that the collapse D-01 removed was keyed to the container, so with the sidebar open laptops up to about a 1100 px viewport also show every column; without a pinned name, the scroll end shows Simulate Impact on a row whose name is off-screen. Founder answer: "Pin the name column". This reverses 170.2 D-05 for widths below `@3xl`. The scroll-cue checks (D-02) run at every viewport, not only phones.
- **Proof:** Playwright at 360, 375 and 390 CSS px, extending the existing `SC6-DISCOVERY` describes in `e2e/layout-narrow.spec.ts` and reusing its V360/V375/V390 constants. Every `thead` header has width > 0 and there is no `details`. At scroll end, the Simulate Impact rect sits inside the region, `elementFromPoint` returns the button, and the fade does not intersect it. The hint is asserted present at scroll start and absent at the end. A vitest structural pin is added beside it. Both must fail on today's markup.

### SC-2: venue label (founder "Accept", 2026-10-13)
- **D-04:** The key's venue wins.
  - A new published-only SECURITY DEFINER function, in the shape of `get_published_trust_signals(uuid[])`, returns `(strategy_id, exchange)` per strategy: the distinct lowercased `api_keys.exchange` reached through `strategies.api_key_id` and `strategy_keys`.
  - It has a pinned `search_path`, a `status='published'` gate and `RETURNS TABLE` as the column allowlist.
  - It **never returns a key id, label or encrypted field**. anon and authenticated get EXECUTE.
  - It is batched in `getStrategiesByCategory` next to the trust-signal call.
- **D-05:** The row's label and the "Trades fetched" tooltip name that venue.
  - When it disagrees with `supported_exchanges[0]`, the tooltip reads "Listed as {Listed}; trades come from {Venue}".
  - Several venues join, sorted and distinct, as "OKX, Bybit".
  - A strategy with no key (CSV or demo) keeps its listed exchange, with no mismatch cue.
- **D-06:** Scope is the Discovery table and its grid view (StrategyGrid, the same page's other view mode). The other SyncBadge mounts are booked as a follow-up and not changed: StrategyHeader, CompositionDonut, StrategyBreakdownTable and recommendations.
- **D-07:** Badge STATES are unchanged. `tradeFetchVenue` stays `null` on these mounts, so null-stamp rows do not start reading "No trade fetch recorded yet". Only the display label and tooltip change. Feeding `tradeFetchVenue` is a TRADESYNC state decision and is out of scope.
- **D-08:** The migration ships with:
  - a rollback;
  - a `supabase/tests` gate in house style with `RED-UNDER` arms: no key id in the result shape, non-published strategies excluded, and anon can call it;
  - every census a new gate file moves (grep them all: `lint-sql-gates.test.ts` "scanned N file", the mutation floors, gate-family-meta and the rest, using a recent gate-adding PR's file list as precedent);
  - the stamp picked against the PROD ledger tip at execution time (marker query first);
  - migration-reviewer and rls-policy-auditor clean before merge, because migrations auto-apply to PROD after TEST with no human gate.

### The flagged leak: anon CAN read `strategies.api_key_id` — YES, measured

- Grants: `has_table_privilege('anon','public.strategies','SELECT')` = true, and
  `has_column_privilege('anon','public.strategies','api_key_id','SELECT')` = true. anon's
  table-level grants on `strategies` are `DELETE, INSERT, REFERENCES, SELECT, UPDATE`, and
  `information_schema.column_privileges` lists `INSERT, REFERENCES, SELECT, UPDATE` on
  `api_key_id` for anon. These match the `strategies` grant line to anon in
  `supabase/schema/baseline.sql`.
- RLS is enabled on `strategies`. Two SELECT policies reach anon through the `public` role:
  `strategies_read` (`status = 'published' OR user_id = auth.uid()`) and `strategies_org_read`
  (the same published arm when `organization_id IS NULL`).
- Effective read, in a `BEGIN READ ONLY; SET LOCAL ROLE anon; … ROLLBACK;` transaction:
  anon sees 3 rows of `strategies`, and all 3 carry a non-null `api_key_id`. 3 of 3 published
  strategies have `api_key_id` set.
- Consequence: `getStrategiesByCategory` selects `*`, so the published row's `api_key_id` (an
  opaque key UUID, not the exchange, label or any credential) already reaches anonymous
  Discovery and /browse payloads. **Owned by Phase 170.6.1.1 ANONKEYID** (orchestrator security
  split, 2026-10-13; this superseded the planner's first draft, which booked it in TODOS.md from
  plan 03). It is NOT fixed in this phase: the
  fix changes a public table grant or the shared ranked projection, which no D-NN covers. The
  new function adds nothing to it: its `RETURNS TABLE` carries no key id (D-04), and plan 01's
  gate pins that.
