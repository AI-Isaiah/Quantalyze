## Warnings

### WR-01: The scroll cue is not re-measured when the table's own width changes, so "show while there is more to scroll" can go stale (MEDIUM, confidence 5/10)

**File:** `src/components/strategy/StrategyTable.tsx:920-953` (the effect; `ro.observe(el)` at :941, deps at :953)

**Issue:**

The cue is now contract-bearing in both directions (D-02): it must be OFF at the end and ON while content remains. It is measured only in four cases:
- on effect runs, keyed on `[density, page, effectiveViewMode, paged.length]`;
- on `scroll` events;
- on a ResizeObserver callback for the scroll container `el`;
- on window resize, where ResizeObserver is absent.

The ResizeObserver watches the container's box, not the table. A change in content width that leaves the container's size alone fires none of these. The cases that do this:
- a sort change on page 0 (`setPage(0)` from 0 is a no-op, and `paged.length` stays 20);
- a search or filter that still yields 20 or more rows (`setPage(0)` at :992 and :1018 while already on page 0);
- a late webfont swap after the first measure.

`scrollWidth` moves, and `hasMoreToScroll` keeps its old value.

Scenarios:
1. **Phone, stale off.** A phone user scrolls to the end, so the cue hides correctly. They re-sort by Sharpe, and the new first 20 rows carry a longer strategy name or badge set, so the content-sized table widens. There is now more to scroll, but the cue stays hidden until the next scroll event. This direction violates D-02.
2. **Laptop, stale off at the start.** A table that fit exactly at mount overflows after a sort or search by less than a column. The cue is off at `scrollLeft = 0`. Nothing invites a scroll, so no scroll event ever corrects it, and the right edge of Actions (Simulate Impact) is clipped with no hint.

The opposite direction (stale on) mostly self-heals. When content narrows past the current offset, the browser clamps `scrollLeft` and fires `scroll`.

The measurement gap existed for the old `isOverflowing` too. This phase made the cue's correctness a stated contract, D-02, so it now owns the gap. The fix is one line.

**Fix:** Also observe the table, so any change in content width re-measures. The `paged.length` / `page` deps then stop carrying correctness on their own.
```tsx
if (typeof ResizeObserver !== "undefined") {
  const ro = new ResizeObserver(measure);
  ro.observe(el);
  // The table's own box: sort / search / font-swap width changes do not
  // resize the scroll container, only its content.
  if (el.firstElementChild) ro.observe(el.firstElementChild);
  return () => {
    ro.disconnect();
    el.removeEventListener("scroll", measure);
  };
}
```
Pin it in `StrategyTable.phone-columns.test.tsx`. Capture the elements passed to `observe()` in the stubbed ResizeObserver, and assert that the `<table>` is one of them. Then, at the scroll end, raise `scrollWidth` and invoke the callback, and assert that the hint returns.

### WR-02: Removing the collapse changes laptop and tablet widths too, not just phones: up to about 1100 px of viewport the table now shows 12-15 columns with an unpinned name column, and nothing decides or tests that (MEDIUM, confidence 6/10)

**File:** `src/components/strategy/StrategyTable.tsx:264-286` (COLUMNS, `collapse` removed), `:1238-1240`, `:1590-1613`; the pinning rule stays `@3xl:`-gated at `:1114`, `:1123`, `:1153`, `:1375-1393`

**Issue:**

The collapse was keyed to the CONTAINER (`@max-3xl`, below 768 px of container), not to a phone viewport. Pinning of the rank, star and Strategy column is gated on the same `@3xl` step, and D-03 left it unchanged.

With the 260 px sidebar, the container stays below 768 px well past phone widths. The repo's own e2e places V768 and V1080 in the "SC6-DISCOVERY unpinned" describe, and starts the pinned describe at V1100. So on a 1024-1080 px laptop, or an iPad in landscape:
- **Before:** Rank, Strategy, Return %, CAGR, Sharpe, Max DD, More, Actions. That is about 8 columns, with modest horizontal scroll.
- **After:** all 12 columns, 13 with the star, and 15 in manager mode on `/strategies` and `/my-strategies`, where Status and Created are added. The Strategy name is NOT pinned and scrolls away.

At the scroll end, Simulate Impact or Edit sits on a row whose name is off-screen. The row's identity is recoverable only by counting rows. That is a desktop-class user-facing change on `/discovery`, `/browse`, `/strategies` and `/my-strategies`.

The CONTEXT frames D-01 and D-02 as phone decisions: "On a phone ... shows every column", and proof at 360/375/390 only. The CHANGELOG says the shared consumers change "below the container breakpoint", but does not say that this includes laptop viewports.

The new SC-1 e2e block is gated `if (vp.width <= 390)`. So V768 and V1080 run nothing that asserts or even logs the new column count or the hint-at-end contract at those widths. The change at those widths is unproven in either direction.

This is not a code defect against the letter of D-01, which says "every column is always rendered". It is an undecided consequence. Per the repo's rule, a decision whose blast radius was not stated must be surfaced and not shipped silently.

**Fix:** Pick one and record it in CONTEXT.md and ROADMAP:
- (a) **Founder confirms** that the laptop and tablet layout is intended. Then extend the SC-1 e2e block to V768 and V1080: drop the `vp.width <= 390` gate for the D-02 hint-start/hint-end and Simulate-Impact-clear checks, which are width-agnostic. Add a CHANGELOG line naming the laptop widths.
- (b) **Keep the phone outcome without the laptop cost.** Pin the Strategy column below `@3xl` once the table carries more than the old column set. That revisits 170.2 D-05, so it needs a founder call and is not something a fixer should do on its own.

Option (a) is the minimal one. In either case, the hint-at-end and Simulate-Impact-clear checks should not be phone-only, because the cue logic is identical at every width.
