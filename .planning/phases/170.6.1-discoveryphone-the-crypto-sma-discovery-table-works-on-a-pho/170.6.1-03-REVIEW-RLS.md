# 170.6.1 plan 03 - RLS / SECURITY DEFINER review

Scope: `supabase/migrations/20261019120000_get_published_trade_venues.sql` and its gate
`supabase/tests/test_get_published_trade_venues.sql` (with the rollback
`supabase/migrations/down/20261019120000-rollback.sql`, read for completeness).
Threshold: MEDIUM and above (HIGH conf >= 7, MEDIUM conf >= 8).

## What was checked, and the result

1. **Published gate equals anon's own visibility.** Both arms filter `s.status = 'published'`
   (migration lines 75 and 83). The baseline policies `strategies_read` and `strategies_org_read`
   (`supabase/schema/baseline.sql:15902`, `:15906`) already let anon read exactly the rows with
   `status = 'published'` (the `organization_id IS NOT NULL` branch needs org membership, but
   `strategies_read` is permissive and OR-ed, so published rows are anon-visible either way).
   `strategies_status_check` (`baseline.sql:12066`) admits draft / pending_review / published /
   archived / private; all four non-published values are excluded. The function therefore reveals
   a strategy's existence to nobody who could not already see that strategy.
2. **Column allow-list.** `RETURNS TABLE (strategy_id uuid, exchange text)` (migration line 65) and
   the two SELECT lists (lines 71-72, 78-79) return only the strategy id and `lower(k.exchange)`.
   `api_keys.exchange` is constrained by `api_keys_exchange_check` to six venue literals
   (`baseline.sql`, binance / okx / bybit / deribit / sfox / mt5), so the text channel cannot carry
   a label, owner or credential. No key id, owner id, `label`, `venue_account_id`, `attested_venue`
   or encrypted field is reachable. The catalogue self-verify (lines 123-125) and gate arm
   TV-shape pin the signature.
3. **search_path.** `SET search_path = public, pg_temp` (line 69): `pg_catalog` is implicitly first,
   `pg_temp` is explicitly last (the hardened position), and every relation is also schema-qualified
   (`public.strategies`, `public.api_keys`, `public.strategy_keys`). Same pin as the precedent
   `get_published_trust_signals` (`baseline.sql:6747`). The project convention text names
   `public, pg_catalog`; whether `public, pg_temp` is acceptable is migration-reviewer's call and is
   not duplicated here. Not a leak path.
4. **EXECUTE grants.** `REVOKE ALL ... FROM PUBLIC` then `GRANT EXECUTE ... TO anon, authenticated,
   service_role` (lines 93-94). Self-verify asserts anon and authenticated hold EXECUTE and that
   grantee 0 (PUBLIC) holds none (lines 127-139). Matches the precedent's grant set
   (`baseline.sql:16664-16667`). anon EXECUTE is the intended D-04 / D-08 behaviour and is
   justified in the header. No grant or RLS change on `api_keys` or `strategy_keys`.
5. **Input handling.** `p_strategy_ids` is only used as `s.id = ANY(p_strategy_ids)`. No dynamic SQL,
   no string concatenation, no `current_setting` / `auth.uid()` use. A NULL array or NULL elements
   yield zero rows. LANGUAGE sql, STABLE: a pure read, so no side-effect or write path from anon.
6. **Enumeration oracles.**
   - Probing unpublished ids: indistinguishable from nonexistent ids (both return zero rows);
     the gate arms TV-unpublished and TV-unpublished-composite pin it on both key paths.
   - "Does this published strategy have a key?" is revealed by the presence of a row. That is the
     intended product disclosure (D-04: the venue label), and it is bounded to published
     strategies, whose existence is already public. It does not widen what ANONKEYID (170.6.1.1)
     removes: `strategies.api_key_id` is an opaque UUID, whereas this function returns only a
     venue enum value and no key identity. After ANONKEYID lands, the venue label (and, for
     keyless strategies, its absence) is the only key-related signal left, which is the minimum
     the feature needs.
   - The function cannot be used to link two strategies to the same key (no key id; the
     UNION de-duplicates per strategy only), nor to learn which owner holds which key.
7. **Gate quality.** The gate runs behavioural arms as anon (the real public path), scopes every
   assertion to its own fixture ids, rolls back, and orders catalogue / grant arms before
   behavioural arms. Each RED-UNDER names a distinct way to break the gate (published predicate in
   each arm separately, UNION to UNION ALL, shape widening, secdef, search_path, each EXECUTE
   grant). Not an RLS finding, no gap that opens a leak.
8. **Cross-file pass.** No table gains RLS in this diff, so there is no enabled-RLS-with-no-policy
   risk. One SECDEF helper is added; its anon EXECUTE is explicit and justified. The rollback
   only drops the function.

## Observations below the reporting bar (not findings, for the record)

- The function returns the venue of every key row ever attached to a published strategy,
  including ended `strategy_keys` windows (`window_end` not null) and keys with
  `disconnected_at` set or `is_active = false`. So a manager who rotated from okx to bybit
  shows "okx, bybit". This is the intended "trades come from" reading (D-04, D-05), the value is
  one of six public venue names, and it adds no identity. Correctness / product question, LOW
  and confidence under 9, so discarded under the reporting bar.
- `p_strategy_ids` is unbounded in length, as in the precedent `get_published_trust_signals`.
  A very large array is a request-size / cost concern handled by PostgREST limits and the reader's
  batching, not a tenant leak. Below the bar.
