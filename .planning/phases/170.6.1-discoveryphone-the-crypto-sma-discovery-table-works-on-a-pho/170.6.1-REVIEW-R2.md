## Summary

Reported at MEDIUM and above only, as the brief asked.

**What holds up after tracing:**

- **WR-01 (Separator)** is correct. The visible text is "Venue unavailable · <sentence>" and a screen reader hears a comma, in all four states. The trailing space inside the flex item collapses, and the root `gap-1.5` provides the spacing. The real label path (D-05) is unchanged.

- **`queries.ts`** changed comments only, and they now agree with D-10.
- **`writeClipboardBounded`**:
  - The timer is cleared in `finally` on every path, including a missing `navigator.clipboard`, where the TypeError is thrown after the timer is armed.
  - `Promise.race` attaches handlers to both promises, so neither a late `writeText` rejection nor the timeout produces an unhandled rejection.
  - A late `writeText` resolution cannot act twice. The race has already settled, and nothing is chained on the original promise.
- **Revoke lifecycle**: a revoke clears `mintedUrl`. A failed mint returns before any `mintedUrl` write. `mintedUrl` cannot outlive a revoke within one mounted row, because `shareLive` and `mintedUrl` only go false/null together. The mint route is idempotent until a revoke (`mintShareUrl` docblock), so the URL kept for "Manage private link" is not stale while the link is live.
- **Focus ordering**: `Modal`'s `showModal` effect runs before the parent's focus effect in the same commit, as the comment says.

**Residual concerns:** the two findings below both sit in the "copy failed, URL is now on screen" path. That path is the one the fix exists for, and on a phone it is the path most users will reach.

## Warnings

### WR-01 (MEDIUM): the dialog the fix opens offers only a copy action that fails the same way, and it can wedge disabled

**Files:**
- `src/components/strategy/ShareableLink.tsx:380-398` (the dialog renders `OwnerUnpublishedPanel` beside the new URL field)
- `src/app/factsheet/[id]/v2/FactsheetView.tsx:2288-2316` (`mintAndCopy`)

**Confidence:** 6/10

**Issue:** The dialog opens only after both copy paths failed. The cause is usually lost or absent user activation: the row awaits a network mint before it writes to the clipboard. The only copy button in the dialog is the panel's `mintAndCopy`. That handler does the same thing again:

1. It awaits `mintShareUrl` over the network.
2. It then calls a bare `await navigator.clipboard.writeText(url)`. There is no bound and no `execCommand` fallback.

It does not copy the `mintedUrl` already on screen.

Two consequences:

- **(a) The copy fails again for the same reason.** Activation is consumed or expired across the fetch, and Safari is the strictest browser here. The user gets the panel's "failed" label inside the dialog whose text says to copy by hand.
- **(b) The button can wedge.** `writeText` can stay pending forever: a permission prompt nobody answers, or a focus-gated browser. That is the condition `CLIPBOARD_WAIT_MS` was introduced to bound. In that case `phase` stays `"working"` and the button stays `disabled={phase === "working"}` permanently. This is the same hang the row now bounds, re-exposed one click later inside the dialog the fix opens.

**Failure scenario:**
1. On a phone, the owner taps "Get private link".
2. The mint resolves, then `writeText` is refused. The dialog opens with the URL.
3. The owner taps the obvious "Copy link" button in the dialog instead of long-pressing the small mono field.
4. The re-mint plus clipboard write fails again (or hangs, and the button stays disabled until the row remounts). The only remaining route is manual selection, which is WR-02.

The code predates this fix, but this fix is what routes every failed copy into it. The test suite never clicks the panel's Copy while `mintedUrl` is shown.

**Fix:** When `mintedUrl` is set, give the field its own Copy button. It should copy the displayed string synchronously inside the click handler, so there is fresh activation and no await before the write, using the same bounded write and then the `execCommand` fallback:

```tsx
<Button size="sm" onClick={async () => {
  try { await writeClipboardBounded(mintedUrl); /* flash "Copied" */ }
  catch { urlFieldRef.current?.focus(); urlFieldRef.current?.select(); /* + execCommand fallback */ }
}}>Copy</Button>
```

Separately, `mintAndCopy` should use the same bound, so its button cannot stay disabled forever. Add a test: with `mintedUrl` shown and `writeText` hanging, the dialog's copy control returns to an enabled state.

### WR-02 (MEDIUM): "focused and pre-selected" is unverified on iOS Safari, the phase's own target

**File:** `src/components/strategy/ShareableLink.tsx:203-208` and `:370-377`

**Confidence:** 4/10. This is unmeasured: jsdom implements `select()` fully, so the GREEN test cannot detect it.

**Issue:** The fix promises a URL "ready for one Ctrl/Cmd-C". Two things stand in the way on iOS:

- **The field is `readOnly`.** Mobile WebKit has a long-standing record of ignoring `HTMLInputElement.select()` on inputs. The usual workaround is `setSelectionRange(0, value.length)`, and readonly inputs sometimes need even that toggled.
- **The focus call is programmatic and late.** `focus()` runs from an effect at least 3 s after the tap, outside any user gesture. iOS commonly declines programmatic focus outside a gesture.

The test asserts `selectionStart === 0` and `selectionEnd === MINTED_URL.length` in jsdom, which proves nothing about WebKit. This is DISCOVERYPHONE, so the phone is the reason the phase exists.

**Failure scenario:**
1. On an iPhone, the dialog opens.
2. Nothing is selected. The `text-caption font-mono` field shows a horizontally truncated slice of a long capability URL.
3. The owner must long-press, find "Select All" and then "Copy". Combined with WR-01, that is the only route that works.

Nothing is lost, because the URL is on screen. The stated "selected, ready to copy" outcome simply does not hold on the target device.

**Fix:**
- Use `el.setSelectionRange(0, el.value.length)` alongside `select()`, both in the effect and in `onFocus`.
- Keep the field's on-screen copy button (WR-01) as the primary affordance on touch.
- Verify once in real iOS Safari (or Playwright WebKit with a mobile device profile), not jsdom.
- Record the measurement in the review-fix record, the way WR-02 of round 1 was measured in Chromium.
