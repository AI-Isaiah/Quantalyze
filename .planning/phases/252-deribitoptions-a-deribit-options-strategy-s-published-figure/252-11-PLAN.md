## Design (settled at planning; the executor implements it as written)

1. **The seam stays where it is.** The smoothed pass keeps calling `_reconstruct_all(PNL_BASIS_SMOOTHED_MTM, structural_degrade=True, ...)` inside the same `asyncio.wait_for`, so every arm after it (budget refusal, timeout, `_PERMANENT_LEDGER_ERRORS`, the WR-01 / R2-WR-01 transient arm, the returned-`DispatchResult` branch, the divergence checks, the derive and its degrades, step 6c) is untouched and keeps its outcome by construction. Only the Deribit ledger SOURCE inside `_reconstruct_deribit` changes. Do not build the smoothed ledger inline in the cash pass: that would move the smoothed failures into the cash pass and rewrite every degrade arm.

2. **Retain in the cash pass.** Add a closure dict `member_cash_crawl: dict[int, tuple[CompletenessReport, DeribitNativeAccountState]]` beside `member_marked` (import both types in the function's local `services.deribit_ingest` import block). `_reconstruct_all` gains two explicit keyword parameters, `retain_cash_crawl: bool = False` and `reuse_cash_crawl: bool = False`, and passes them and the member `seq` to `_reconstruct_deribit` (new keyword-only `member_seq`). The cash-pass call passes `retain_cash_crawl=True`. On that pass `_reconstruct_deribit` adds `retain_raw_rows=True` to its existing `build_deribit_native_ledger` call. After `assert_ledger_complete(completeness)` passes, it stores `(completeness, account_state)` under the member's seq. Drive both modes by these parameters, never by comparing `basis` to a basis literal: `cash_pnl_basis` is `denominator_config.pnl_basis` on a configured composite and may itself be `mark_to_market` or `smoothed_mtm`. That case is still correct, because the crawl's raw rows do not depend on the basis and only the assembly does. The MTM second pass passes neither flag and is byte-unchanged.

3. **Rebuild in the smoothed pass.** The smoothed call passes `reuse_cash_crawl=True`. On that pass `_reconstruct_deribit` pops the member's entry from `member_cash_crawl`. A missing entry is a programming error: raise `ValueError` naming the member seq. Never fall back to a fresh crawl and never degrade silently; this is the same disposition `build_deribit_options_basis_ledger` gives a report without raw rows. It skips the account-state fetch and the native build. It calls `build_deribit_options_basis_ledger(ctx.exchange, report=<retained report>, account_state=<retained state>, pnl_basis=basis, exclude_spot_extraction=exclude_spot)` inside the same `asyncio.wait_for(..., timeout=_BROKER_CRAWL_TIMEOUT_S)`, so the `asyncio.TimeoutError` arm in `_reconstruct_all` still maps an overrun to a transient. It does not re-run `assert_ledger_complete`, because that gate already judged this same crawl's report in the cash pass (key-mode precedent). Then it runs the same `asyncio.to_thread(combine_native_ledger, ..., denominator_config=denominator_config)`. `has_option_activity` and the MED-01 `pre_mark_retention_option_dailies` bridge MUST read the report RETURNED by `build_deribit_options_basis_ledger`, never the retained cash report. The cash report never carries the retention list, so reading it would make P3 unable to fire, and that is the unsafe direction. In a `finally`, set the retained report's `raw_rows` to None (the key-mode idiom).
   - The per-member preflight still runs on the smoothed pass. It is cheap (no crawl), it provides the exchange handle the public chart and index reads use, and it keeps the WR-01 rule "a permanent preflight / unsupported-venue `DispatchResult` still returns, on every attempt".
   - `mark_seq` and `allocated_mark_seq` stay None on the smoothed pass, as today.
   - ccxt members are routed to `_reconstruct_ccxt_member` on the smoothed pass exactly as today: a live ccxt re-read, cash-only, with no Deribit transaction-log crawl to reuse. So the degraded-member divergence check and the R2-WR-01 `ccxt.NetworkError` arm keep their purpose. CONTEXT 2026-11-25 measured every PROD composite member as a Deribit key, so no PROD composite has a ccxt member today.

4. **The extraction mode.** `build_deribit_options_basis_ledger` hard-codes `exclude_spot_extraction=False` (key-mode NAV path), while the composite's smoothed member build today runs with `exclude_spot` (True on a configured composite). Add a keyword-only `exclude_spot_extraction: bool = False` to `build_deribit_options_basis_ledger` and pass it to `_assemble_deribit_native_ledger` in place of the literal. Update its docstring: key mode passes the default, and the composite stitch passes its configured mode so the rebuilt member ledger is assembled in the same mode as the crawl it replaced. Key mode passes no value, so its call is byte-unchanged. Nothing else in `deribit_ingest.py` changes.

5. **The account state.** The smoothed ledger now uses the cash pass's account-state read instead of a second live read. This follows the key-mode precedent: rows and anchor then come from ONE moment, so the cash and smoothed bases describe the same data, where today they could straddle transactions that landed between the two crawls. No founder checkpoint is needed for this.

6. **Release.** Retained rows hold instruments, sizes and amounts (`CompletenessReport.raw_rows` is `repr=False`; never log or persist them). Release each entry (set `raw_rows` None, drop it) as follows:
   - in the smoothed build's `finally`;
   - for every entry right after the cash pass when `smoothed_mtm_available(member_signals)` is False (so a perp-only composite does not hold them through its MTM crawl);
   - for every remaining entry once step 6b ends on any path (budget refusal, timeout, degrade, success). An early `return` releases them with the function frame.

7. **Budget decision.** The smoothed pass KEEPS its bounded timeout (`_smoothed_pass_timeout = _smoothed_remaining * _MTM_SECOND_PASS_BUDGET_FRACTION`) and its `_MTM_SECOND_PASS_MIN_SECONDS` refusal, with no constant changed. It still makes venue reads (the option daily marks and the dense index marks), so an unbounded pass could still overrun the outer dispatch wait. The founder chose reuse over a raise. The pass now does strictly less work under the same bound, and its remaining read time for these members is UNMEASURED. After the bounded `asyncio.wait_for` returns a tuple, emit exactly one INFO line, `run_stitch_composite_job: smoothed_mtm pass built from the cash pass's crawl in %.0fs of its %.0fs bound for strategy %s` (seconds and strategy id only, no amount, date or member id). The post-deploy reading uses it; a timeout keeps its existing warning. Do NOT reword any existing log line: tests match them.

8. **Comments.** Update the 6b comment block and the GLB-3(b) "BUDGET" paragraph to say the pass rebuilds each Deribit member from the cash pass's retained crawl (founder decision 2026-11-28), and name what remains bounded (preflight, option marks, index marks, combine, ccxt re-reads). Update the budget-refusal comment that says "a third full fan-out". `test_no_verification_or_publish_status_write_source_scan` scans the whole source of `run_stitch_composite_job`, comments included, for two banned words; read it before writing any comment.
