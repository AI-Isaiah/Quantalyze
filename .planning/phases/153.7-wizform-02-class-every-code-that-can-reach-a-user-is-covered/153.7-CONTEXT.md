<domain>
## Phase Boundary

Close the **class** behind WIZFORM-02 — the one requirement the Phase 153 span failed
(`153-VERIFICATION.md`, status `failed`, 5/6).

A server-classified failure currently reaches the user as `code: UNKNOWN`. The derived-roster
coverage law that was supposed to prevent this **works**, but its *reach* is wrong: its population
is scoped by directory and by syntactic shape rather than by "can this code reach a user".

This phase widens the population to every user-reachable code, and — the headline fix — makes a
code that is missing from **both halves** of the coverage law a **CI failure by name** instead of
a silent gap.

**IN:** the two scanner widenings (root + shape), the pinned-table re-cut, the both-halves
coverage assertion, the falsifiability proof, dispositions for the two known mt5-gateway codes,
the three code-less `finalize-wizard` rejections, and the `create-with-key` terminal arm that
discards the honest machine code.

**OUT:** WIZFORM-05 / the validate budget (explicitly — see decisions). Re-verifying 153.6.
Adding the two known codes as rows *without* the mechanism.

</domain>

<decisions>
## Implementation Decisions

### Boundary (LOCKED — the crux; reverse only with founder sign-off)
- The coverage law's boundary is **"every code that can reach a user-facing surface"**, NOT
  "codes emitted in a particular directory in a particular syntactic shape".
- Rationale, recorded: the present boundary is an artifact of *how the scanners were written*, not
  of any product rule. No one decided a 500 from `routers/` deserves less honesty than a 400 from a
  Next route, and the user cannot tell the difference. Both scanners already prove the mechanism
  works; only their reach is wrong.

### Scanner reach — TWO independent misses, both required
- Widen the Python scanner root from `analytics-service/services/**` to `analytics-service/**`
  (`seam-venue-vocabulary.invariant.test.ts`, `SERVICES_ROOT` :70).
- Teach it the **positional** shape `service_error(<status>, "<CODE>", …)` in addition to
  `error_code = "<CODE>"` assignments (`ASSIGNMENT_RE` :94).
- ⚠️ These are **independent**. Doing either alone still leaves `routers/exchange.py` invisible.
  Any plan that implements one without the other has not moved the needle.

### The both-halves assertion (the headline fix)
- A discovered code with **neither** a verdict row in `VENUE_WIRE_CODE_TO_VERDICT`
  (`wizardErrors.ts:2682-2730`) **nor** a recorded no-verdict in
  `VENUE_WIRE_CODES_WITHOUT_VERDICT` (`:2746-2795`) must **fail CI, by name**.
- ⭐ Today's live defect was silent *precisely because* the code was missing from both halves.
  That asymmetry is the actual defect, above any individual missing code.

### Pinned tables
- Re-cut the 153.1 `EXPECTED_TABLE_SIZE` family. **Never delete them.** The re-cut is the
  deliberate act that records the widening.

### Dispositions
- `MT5_GATEWAY_UNCONFIGURED` — permanent, operator-directed, not retryable.
  Emitters: `routers/exchange.py:465`, `:477`, `:620`, `:868`.
- `MT5_GATEWAY_UNREACHABLE` — transient, retryable. Emitter: `routers/exchange.py:628`.
- Each gets a wizard member OR an explicit `VENUE_WIRE_CODES_WITHOUT_VERDICT` row with a
  **measured** reason.

### Also in scope (from the verification's `missing` list)
- Three code-less `finalize-wizard` rejections (D-153.2-D: 500 draft-load, 500 finalize-RPC,
  502 upstream-shape) each need a copy member; `KNOWN_CODELESS_FINALIZE_REJECTIONS = 3`
  (`wizardErrors.invariant.test.ts:516`) moves accordingly.
- `src/app/api/strategies/create-with-key/route.ts:1057`, `:1094` — the terminal arm discards the
  honest machine code: `classifyKeyValidationError(err)` reads `err.seamCode` only through
  `VENUE_WIRE_CODE_TO_VERDICT`, falls through to a substring cascade over the human sentence, and
  answers `{ code: "UNKNOWN", status: 500 }`.

### Falsifiability (the phase's own gate)
- Add a new `service_error(...)` code in `routers/` with no verdict row and prove the gate **reds**.
- ⛔ **A fix that cannot fail this way has not closed the class.**

### Claude's Discretion
- Whether the two scanners converge into one shared discovery helper or stay separate with a
  shared matcher — as long as both roots and both shapes are covered and neither guard silently
  loses reach.
- The exact regex/AST strategy for the positional `service_error(...)` match, provided it is
  robust to multi-line calls and to `status` being a non-literal.
- Plan/wave decomposition and file-level task ordering.
- Copy wording for the new members, within DESIGN.md and the established wizard error voice.

</decisions>

<specifics>
## Specific Ideas

- ⭐ The mechanism is **proven**: mutating an emitted code literal in `finalize-wizard/route.ts`
  reds two assertions by name. This phase changes *reach*, not *design*. Do not rebuild the roster.
- ⚠️ **Do not blanket-sweep newly discovered codes into `WITHOUT_VERDICT` to make CI green.** Each
  newly discovered code needs a real disposition. A sweep reproduces the defect in its most general
  form: the law would cover everything and assert nothing.
- ⚠️ `analytics-service/**` is a wider root and may pull in test fixtures or scripts that mint
  codes no user can reach. Excluding them is legitimate; excluding them **silently** is not. Every
  exclusion is recorded with its reason.
- Live-relevance note: the code actually measured on PROD was `MT5_GATEWAY_UNCONFIGURED`, now less
  likely to fire since MT5 is configured. Its sibling `MT5_GATEWAY_UNREACHABLE` is exactly what the
  documented gateway wedges produce (three in one day), so the user-facing impact is live and
  recurring, not historical.

</specifics>
