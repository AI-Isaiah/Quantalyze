<objective>
CONTEXT Q6 item 2 (founder ruling 2026-11-25, as the coordinator relayed it): "A connect on the same broker with the wrong server must be refused at connect or validation time, because it cannot read anything. The gap plans confirm by measurement that the existing validation already refuses it (the MT5 login fails against the wrong server; the MT5 venue API docs are read too), and close any path that lets it through."

Why it must hold before PR-3: before migration B, the login-only index refuses a same-owner second key on one login whatever its server. After B, a wrongly admitted second server would be a second LIVE key on the same real account, and plans 14-16 would count it as a different account.

WHAT THE MT5 DOCS SAY (read 2026-11-25 with WebFetch; the plan relies on these and on nothing they do not say):
- https://www.mql5.com/en/docs/python_metatrader5/mt5login_py — `login(login, password=..., server=..., timeout=...)`. server is "Trade server name. Optional named parameter. If no server is set, the last used server is applied automatically." Return value: "True in case of a successful connection to the trade account, otherwise – False."
- https://www.mql5.com/en/docs/python_metatrader5/mt5initialize_py — when the server is omitted, "the server for a specified trading account saved in the terminal database is applied automatically". The page says nothing about a terminal that is already connected.
- https://www.mql5.com/en/docs/python_metatrader5/mt5accountinfo_py — `account_info()` returns a named tuple whose fields include `login` and `server` (example `server=MetaQuotes-Demo`), or None on error.
- https://www.mql5.com/en/docs/python_metatrader5/mt5lasterror_py — lists the error codes, among them an authorization-failed code. Its table was read through a summarising fetch, so this plan quotes no code from it; the repo's own constants in services/mt5_validation.py stay authoritative.
NOT documented: that a wrong server makes login() return False, and what login() does when the terminal already holds that login on another server. The repo's own observations fixture (tests/fixtures/mt5_login_rejection_observations.json) holds no measured pair yet, and its phrase tables are [ASSUMED].

WHAT THE CODE DOES TODAY (traced at HEAD; Task 1 and Task 3 pin it):
- The wizard router (routers/exchange.py) and the worker adapter (services/ingestion/mt5.py) both run the known-server pre-check (`assert_mt5_server_known`, curated list plus the house server) and then `run_probe`, which calls `client.login(login, investor_pw, server)`.
- `Mt5Client.login` passes `server=server` to MetaTrader5's login, so the server reaches the terminal, and a falsy return raises `Mt5LoginRefusedError`.
- The terminal lease is keyed by host:port (`mt5_terminal_key`), never by login, and there is no session cache: every validation logs in.
- The stored server is the validated passphrase (`normaliseConnectedVenueServer(passphrase)` in validate-and-encrypt and create-with-key).
- rotate-secret accepts no new server ("WITHOUT ever accepting a new login or broker server", its header).
THE GAP: after login, `run_probe` checks the session with `assert_expected_login`, which compares only the LOGIN. If login() ever reported success while the terminal stayed on that login's session on another server, which the docs do not rule out, the validation would accept a server the session never proved. Task 1 closes it with a server bracket.
