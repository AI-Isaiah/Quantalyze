<objective>
PR-2b-2, the Python twin. CR-01: once migration B admits one owner's same MT5 login on two servers, `account_identity_tokens` (analytics-service/services/allocator_equity_derive.py) unions the two keys on `(exchange, venue_account_id)` alone, `account_identity_collisions` finds two counted keys on one token, and the derive refuses the whole book with ACCOUNT_IDENTITY_COLLISION, with no end. CONTEXT Q6 (founder ruling 2026-11-25, as the coordinator relayed it) item 1: "Two keys with the same login on two different set servers are two different accounts. They never share an identity token". CONTEXT Q6 agent decision: "A key with no server joins its login's group only when that login has at most one distinct set server across the keys the reader sees. Otherwise the derive refuses with a named reason."

THE RULE, stated once and shared by the three twins (this plan, plan 15's TS, plan 16's SQL). It is a canonical identity per key, not a pairwise wildcard, because union-find is transitive (CR-01's warning: a NULL key unioned pairwise with servers a and b would merge a and b again):
- login = venue_account_id stripped, as today; a key with a blank login has no login identity (markers still apply).
- server = venue_server if it is a non-empty string, else none. Nothing is trimmed or folded here.
- For each (exchange case-blind, login), S = the set of distinct servers among the keys passed in.
- canonical server: the key's own server if set; else "" when S is empty; else the single member when S has one member; else NONE, and the key is AMBIGUOUS.
- Two keys share a token when their (exchange, login, canonical server) are equal. An ambiguous key takes part in no login union and is unknown (None) unless a share marker links it, exactly as a key with no login is today. Marker unions are unchanged.

PER-READER KEY SET (verified at HEAD by reading the selects): the derive's `_load_keys` (job_worker.py) and the match scorer (routers/match.py) both read EVERY key of the owner, live and disconnected, with no liveness filter. The TS readers in plan 15 and the SQL `owner_keys` in plan 16 read the same set. So "the keys the reader sees" is the same set in all three, and the rule has the same effect in each. PROD (orchestrator dispositions, 2026-11-25): 0 owner/exchange/login groups with two or more distinct set servers; 1 of 12 MT5 keys has no server and it is disconnected. So no current book changes grouping when this deploys.

THE AMBIGUOUS CASE, per reader (only the derive refuses):
- `account_identity_tokens` returns None for the ambiguous key (unknown), unless a marker link joins it to another key: the unchanged marker pass still unions it (the `marker-links-an-ambiguous-key` case), and `ambiguous_server_key_ids` still lists it.
- The derive refuses before composing, with the NEW token `account_server_ambiguous`.
- `departed_history_inclusion` reads None as account_unknown, so it excludes the key by default. The derive refuses anyway.
- The match scorer puts the key in its own `key:<id>` group. That is the scorer's existing treatment of an unknown key, and nothing it computes is persisted (its own docstring).
- Plan 15's TS and plan 16's SQL produce the same `key:<id>`.
Why this is safe: no figure is persisted from the ambiguous grouping (the derive refuses, the scorer is request-time, and the commit RPC only compares fingerprints that the TS and SQL twins compute identically). The answer is also the one the code already gives for any key whose account it cannot read.

REFUSAL TOKEN DECISION: a NEW `DeriveRefusal` member `ACCOUNT_SERVER_AMBIGUOUS = "account_server_ambiguous"`, not ACCOUNT_IDENTITY_COLLISION. Reasons:
(1) CONTEXT asks for "a named reason". The collision's definition, "Two live keys read one exchange account with no marker between them", is false here: the key with no server may read a third server.
(2) The collision maps to the reader line `duplicate_account`: "Two of your keys read the same exchange account. Disconnect one of them on the Exchanges page and the history rebuilds." That action does not clear the disconnected variant, because the ambiguous key is already disconnected and still counts.
(3) The enumeration audit at HEAD found the cost small.
    - No SQL CHECK, enum or column constrains a refusal token. `grep -a -rln 'compose_empty_blocked'` over supabase/ finds nothing.
    - The TS reader `untrustworthyRebuildReason` (src/lib/queries.ts) and the census CASE in scripts/accounttruth-census.mjs both map an unknown token to `derivation_rejected` by their ELSE arms.
    - So the change is the enum member, one `refusals` row in derive_refusal_rows.json (reader_reason `derivation_rejected`) and the derive code. The test set equality in test_derive_refusal_rows.py, src/lib/__tests__/derive-refusal-rows.test.ts and src/__tests__/accounttruth-census.test.ts pick the row up unchanged.
The owner then sees the existing `allocation.book.derivation-rejected` line ("…did not pass its checks… Use the contact form to have it checked."). That line is true in both variants, and it neither says wait nor names an action that would not work.
Exits from the refusal: a live ambiguous key gets its server written by its next successful poll (plan 12's backfill), and the next derive composes. A disconnected one clears only when that key is deleted (`delete_allocator_api_key`), because reconnect refuses a server-less key while a live sibling holds the login (migration B's wildcard).

Execution branch: the PR-2b branch cut from origin/main (see plan 13's objective). This plan ships in PR-2b-2 with plans 15, 16 and 17, after PR-2b-1 is applied on PROD. It needs no grant itself (the analytics service reads as service_role).

Output: the server-aware token and the ambiguity helper, the refusal, the two selects, the shared fixture's `tokens` section, and failing-first tests.
