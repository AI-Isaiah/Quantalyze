WHAT THE MT5 DOCS SAY (the venue API docs, read 2026-11-25 by plan 18's author and re-read by the PR-2c reviewer; this plan relies on nothing more): https://www.mql5.com/en/docs/python_metatrader5/mt5accountinfo_py — `account_info()` returns a named tuple whose fields include `login` and `server`, or None on error. https://www.mql5.com/en/docs/python_metatrader5/mt5login_py — `server` is "server name as it is specified in the terminal", optional ("the last used server is applied automatically"), and the return is True on a successful connection. Neither page says the server `account_info()` reports equals the name the login was given. That is what Task 3 measures. `Mt5Client.account_info` materialises every named-tuple field through `_materialize`, so the dict carries `server` whenever the terminal reports one.

THE NORMALISER IS ALREADY SHARED. `normalise_mt5_server` (trim, then case-fold) is on origin/main in services/mt5_probe.py, used today by the known-server pre-check and by services/mt5_server_clock_reading.py, and services/mt5_read.py already imports `assert_expected_login` from services.mt5_probe. PR-2c only ADDS `assert_expected_server`, which calls it. So this plan depends on nothing in PR-2c and needs no new module. The helper lives in services/mt5_read.py, not services/mt5_probe.py, because PR-2c's diff edits mt5_probe.py and mt5_client.py: touching neither keeps the two PRs free of a shared file, and PR-2c takes origin/main cleanly after this merges.

THE PREDICATE TO MIRROR (PR-2c, `git show origin/gsd/phase-225-pr2c:analytics-service/services/mt5_probe.py`, `assert_expected_server`): the reported server passes only when it is a `str`, its `strip()` is non-empty, and `normalise_mt5_server(reported) == normalise_mt5_server(requested)`. Here: those three hold → True; the first two hold and the third does not → False; the first or second fails → not_captured (PR-2c would refuse it as well).

ATTRIBUTION WITHOUT A SECRET. The line carries the lease site (the closed set in services/mt5_handover.py) and the lease holder through `normalize_mt5_holder`, the house precedent in that module: "A holder is a UUID api_key_id or one of four literals", and no account number, login, password, broker server, gateway host, port or terminal key may reach a row or a log line. With the holder, the orchestrator maps lines to keys, and keys to their stored servers, through one read-only PROD query. Per-server coverage is then determinable with no server value in any log line or tracked file.
