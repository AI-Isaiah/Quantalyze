<objective>
PR-2b-1: the owner may read their own key's broker server. CONTEXT Q6 item 1 (founder ruling 2026-11-25, as the coordinator relayed it) says two keys with the same login on two different set servers never share an identity token "in Python (`account_identity_tokens`), in TS (`accountIdentityTokens`) or in SQL (`commit_scenario_batch` `account_edges`)". Every TS caller of `accountIdentityTokens` reads `api_keys` as `authenticated` through the `API_KEY_USER_COLUMNS` allowlist, and `venue_server` is ungranted today. So the TS twin cannot become server-aware until the column is granted.

This plan reverses one posture of plan 01, and the plan says so. Plan 01 left the column ungranted on RESEARCH F-4's reason "no UI reads it", and gate arm `6v-no-grant` describes that as "founder ruling Q2". CONTEXT Q2 records only "The server name is stored in plaintext. Founder: yes, it is not a credential." The reason F-4 gave no longer holds once the TS twin reads the column. Task 1 puts the choice in front of a human before anything changes.

Ship order (departure from the orchestrator brief's single PR-2b, stated on purpose): the repo rule in `src/lib/constants.ts` ("PROD applied the GRANT before this list gained the columns, so no key list selects a column PROD lacks (42501 on every read)") forbids shipping the GRANT and the code that selects the column in one PR. Vercel deploys the code on merge while the migration applies to TEST and then PROD. So this plan alone is PR-2b-1. Plans 14 to 17 are PR-2b-2 and merge only after this migration is applied on PROD.

Execution branch: run on a branch cut from origin/main (for example `gsd/phase-225-pr2b`), never on `gsd/phase-225-oneaccountonce`, which carries plan 10 (migration B). PR-2b-1 is this plan's commits cherry-picked onto a fresh branch from origin/main, so migration B cannot ride in.
