<objective>
PR-2b-2, the TS twin. CONTEXT Q6 item 1 (founder ruling 2026-11-25, as the coordinator relayed it): two keys with the same login on two different set servers "never share an identity token, in Python (`account_identity_tokens`), in TS (`accountIdentityTokens`) or in SQL". CR-01 fix (a): "Every row type and select that feeds them must carry `venue_server`."

The rule is the one plan 14's objective states: a canonical (exchange case-blind, login stripped, canonical server) identity per key. A key's own server is used when set. With no server, the canonical server is "" when the login's keys carry no server, the single server when they carry one, and NONE (ambiguous, null token) when they carry two or more. Servers are compared as stored, with no trim or case-fold in the reader. Marker unions and the token format `account:<smaller id>` are unchanged. The TS answer for the ambiguous key is null: `keyAccountOf` gives `key:<id>`, and `departedHistoryInclusion` gives account_unknown. Only the Python derive refuses (plan 14). The dashboard shows the derive's refusal row through the existing reader.

Key set: every TS reader reads all of the owner's keys with no liveness filter (`fetchLatestHoldingsPerKey` and portfolio-exposure's `fetchHoldings` select KEY_IDENTITY_COLUMNS by user_id with the row cap; `getUserApiKeys` selects API_KEY_USER_COLUMNS by user_id). That is the same set as the Python derive, the scorer and the SQL `owner_keys`.

This plan also covers a fourth same-owner grouper the review did not list: `deriveKeyDataGapsField` (src/lib/queries.ts) builds `KeyAccountFact.accountId` from the bare login, and key-data-gaps' `accountGroups` groups on it to name keys in a `duplicate_account` gap line. After migration B it could name a key on another server. CONTEXT Q6 item 1 covers it ("two different accounts"), so it moves too. Cross-user readers (`src/lib/discovery/shared-account-partners.ts`, the fingerprint's cross-user use) stay login-only by the CONTEXT Deferred Ideas ruling and are not touched.

Precondition for the column: plan 13's GRANT (PR-2b-1) must be applied on PROD before this code merges, or every key list answers 42501 (src/lib/constants.ts's own rule). Local tests mock Supabase and run before that. Plan 17 Task 3 checks the PROD grant before PR-2b-2 merges.

Output: the server-aware TS twin, its fixture replay, the projections and types, and the callers' mappings.
