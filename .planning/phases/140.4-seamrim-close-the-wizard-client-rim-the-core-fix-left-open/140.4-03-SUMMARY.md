## The index, verbatim, with column order

```sql
CREATE UNIQUE INDEX IF NOT EXISTS strategies_user_wizard_session_source_uniq
  ON public.strategies (user_id, wizard_session_id, source)
  WHERE wizard_session_id IS NOT NULL;
```

- **`user_id` LEADS** — column 1 of 3. `wizard_session_id` is caller-supplied; a non-tenant-leading
  unique index over it is the C-08 cross-tenant leak that `20260726000225` exists to close.
- **Create-before-drop ordering, measured:** `CREATE UNIQUE INDEX` at **line 167**, `DROP INDEX` at
  **line 181**. Create precedes drop by 14 lines.
- **No NULL-distinctness hole:** `strategies.source` is `TEXT NOT NULL DEFAULT 'legacy'`
  (`20260411103316:36`), verified at source. A nullable third column would make every such row
  mutually distinct and the index inert.
- **The API guarantee is preserved exactly:** both API writers set `source='wizard'` — verified at
  `schema/functions/create_wizard_strategy.sql:88-97` and `add_wizard_composite_key.sql:70-80`. No
  migration in the tree ever `UPDATE`s `strategies.source`, so a row cannot migrate out of its own
  uniqueness bucket after insert.

### Self-verify assertions (STEP 4)

(a) column **list and order** from `pg_index` = `{user_id, wizard_session_id, source}`, index is
`indisvalid AND indisunique` · (a2) still partial on `wizard_session_id IS NOT NULL` ·
(b) `strategies_user_wizard_session_uniq` is gone · (b2) **exactly one** unique index on `strategies`
covers `wizard_session_id`, so a differently-named copy of the two-column shape cannot hide behind (b) ·
(c) `pg_get_functiondef` sliced **between `INSERT INTO strategies (` and `RETURNING id INTO
v_strategy_id`** contains both `wizard_session_id` and `p_wizard_session_id`. The slice is deliberate:
a whole-body `ILIKE '%wizard_session_id%'` is satisfied by the parameter declaration and by the
`strategy_verifications` INSERT, **both of which predate this migration** — i.e. the loose check passes
on the UNFIXED body and proves nothing.

### The cross-source control assertion, by name

**`Part 4` — "TEST FAILED (Part 4b/4c)"**, in `supabase/tests/test_csv_finalize_double_submit.sql`.
An abandoned `source='wizard'` draft carrying session `S` is created via the **real** API writer, then
a CSV finalize with the **same `S`** must succeed and mint its own strategy (2 rows for
`(uid_b, session_b)`, exactly 1 with `source='csv'`).

It carries its own **vacuity fence** (Part 4a): it first asserts the API draft really does carry
`source='wizard'` **and** the session id. Without that fence, an API writer that silently stopped
writing `wizard_session_id` would make Part 4 pass for the wrong reason and the control would report
agreement forever.
