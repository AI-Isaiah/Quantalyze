## ⭐ INHERITED DECISION 1 — `src/lib/ratelimit.ts`: ADDED to the roster

Plan 08 stated the problem exactly: `ratelimit.ts` "is a member of the … class by BEHAVIOUR and not
by TOPOLOGY" — it imports none of `analytics-client` / `resilient-fetch` / `process-key-client` and
is not a `route.ts`, so **no derivation in this programme will ever reach it** — "yet it holds the
one demonstrated credential leak of this whole work package" (plan 06 printed
`Bearer AX7zAAIncDEyMzQ1Njc4OTBhYmNkZWY` in full).

**Decision: ADD IT to the hand-typed lib half.** The reasons are written into the source beside the
roster; in short:

1. **The defended property is identical.** `@upstash/redis` puts
   `Authorization: Bearer <UPSTASH_REDIS_REST_TOKEN>` into an outgoing header that its transport
   error inlines, exactly as undici does with `INTERNAL_API_TOKEN`. Only *which secret* differs — a
   fact about the credential, not about whether this predicate applies.
2. **Leaving the one demonstrated leak outside the class guard on a topological accident is the
   instance-not-class shape this phase exists to close.** Its only backstop was one colocated case in
   `ratelimit.test.ts` — a real guard, but a per-file one, which is precisely the shape that left
   `create-with-key` and `composite/add-key` in the HI-02 gap.
3. **Adding a member is the safe direction.** It widens what is inspected and weakens nothing. It was
   measured at **0 offences under all three halves before it was added** (roster of 1: consoleSites 5,
   catchBindings 1, catch clauses 3, offences 0), so it lands on a green tree like the rest.

**The honest limit, stated in the source in these words:** this half is a **hand-typed roster —
coverage-law ROW 2, and therefore PARTIAL BY CONSTRUCTION**. A second `ratelimit.ts`-shaped file
would have to be added by hand and nothing in the repo would notice its absence. The ROUTE half is
row 1; this half is not.

## ⭐ INHERITED DECISION 2 — `status` / `seamCode`: DECLINED for `SAFE_PROPERTIES`

Plan 08 routed three provably-safe values (`err.status`, `err.seamCode` at `admin/match/eval:217`,
`admin/match/recompute:172`, `scenario/optimize:198`) through the scrub leaf rather than decide this.

**Decision: NO.** Four grounds, written into the `SAFE_PROPERTIES` docblock:

1. **Nothing is broken.** `scrubSeamError(424)` renders `"424"`; `scrubSeamError("SEAM_X")` renders
   `"SEAM_X"`. The scrub is a rendering no-op on both, no diagnosis is lost, and the only gain on
   offer is cosmetic.
2. **The list matches by NAME, not by type, in every rostered file, forever.** `status` is one of the
   most widely reused property names in the ecosystem; the entry would exempt `.status` on *any*
   caught value, including a future one where it is a **string** from a library we do not control.
   `code` earned its place with a narrow written justification (a five-character SQLSTATE); `status`
   cannot make the same argument.
3. **Routing through the leaf is coverage-law ROW 1** (a chokepoint); an entry here is ROW 2. This
   phase's own rule prefers the chokepoint, and the three sites already use it.
4. **Ordering.** This plan widens the roster from 8 files to 19. Enlarging the safe-property list in
   the same diff is the shape of the named warning sign.

`seamCode` alone is genuinely narrow and ground 2 does not bite it — it is declined anyway, because
it clears no site `status` does not also sit on, and a one-element relaxation of an absence guard
bought with no defect to fix is still a relaxation.
