<objective>
The read-only capture of our side (PARITY-03): ten SELECT-only statements, one per slice of `capture-contract.json` (created by plan 01). The orchestrator runs them through the Supabase MCP between two `bind.sql` runs, and `seal_capture` (plan 01) verifies their completeness witnesses.

Purpose: everything the engine (Gate A and Gate B) and the surface matrix (plan 09) compare on our side comes from persisted rows, never from a recompute. That covers the stored series and flags, the NAV marks, the key_inputs writer basis, the per-key and per-strategy daily returns, the book rows and the BTC closes.
Output: ten SQL files; the gate and README extended to cover them.

Design decision on parameterisation: the files are unparameterised. Each returns one row per MT5 key ordinal and runs once. If MCP truncates a result, seal_capture refuses it by witness. The orchestrator then re-runs that one file per ordinal through `render_per_ordinal` (plan 01), wrapped as `SELECT * FROM (...) AS q WHERE q.key_ordinal = 'kN';`. A committed file is never edited at run time, so the read-only gate always covers the bytes that run.
</objective>

Shape of every file: one output row per key ordinal (LEFT JOIN from the key CTE, so a key with no rows still prints `slice_rows = '[]'::jsonb` and `row_count = 0`), with the columns from the contract's `witness_columns` in that order:
- `key_ordinal`;
- `slice_rows`: `COALESCE(jsonb_agg(<row> ORDER BY <stable key>) FILTER (WHERE <row pk> IS NOT NULL), '[]'::jsonb)`;
- `row_count`: `count(<row pk>)`;
- `first_day`, `last_day`: min and max of the contract's day_column as text, NULL when the contract's day_column is null;
- then any extra_witness columns.
ORDER BY key_ordinal.

1. `capture-keymap.sql`. Row = `jsonb_build_object` with exactly the contract's keymap columns:
   - `api_key_id` = key.id, `allocator_id` = key.user_id, `label` = key.label, `account_currency`;
   - `strategy_id`, `strategy_status`, `asset_class` from a LEFT JOIN of public.strategies on api_key_id, so a key with no strategy yields one entry with NULL strategy fields;
   - `key_created_at` = key.created_at.
   The pk for FILTER is key.id, and the order is strategy created_at then id. This file is the only one that reads `label`, for the orchestrator's mapping file. It never reads the MT5 login column or any encrypted-secret or key-material column of api_keys.
2. `capture-strategy.sql`. Row = `to_jsonb(s.*)` for public.strategies s WHERE s.api_key_id = key.id. Order by s.created_at, s.id.
3. `capture-analytics.sql`. Row = `to_jsonb(sa.*)` for public.strategy_analytics sa joined to the key's strategies, ordered by sa.strategy_id. Extra witnesses, as arrays aligned with slice_rows in the same order:
   - `returns_series_len` = `jsonb_agg(CASE WHEN jsonb_typeof(sa.returns_series) = 'array' THEN jsonb_array_length(sa.returns_series) END ORDER BY sa.strategy_id) FILTER (WHERE sa.strategy_id IS NOT NULL)`;
   - `daily_returns_len`, built the same way from daily_returns.
   Both COALESCE to `'[]'::jsonb`.
4. `capture-series.sql`. Row = `to_jsonb(ss.*)` for public.strategy_analytics_series ss joined to the key's strategies, ordered by ss.strategy_id, ss.kind.
5. `capture-marks.sql`. Row = `to_jsonb(m.*)` for public.api_key_nav_marks m WHERE m.api_key_id = key.id, ordered by m.mark_day, m.id. first_day and last_day are min and max of m.mark_day.
