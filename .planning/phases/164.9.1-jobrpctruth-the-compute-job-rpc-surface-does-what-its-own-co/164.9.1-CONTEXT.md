<domain>
## Phase Boundary

The compute-job RPC surface does what its own comments and migrations say it does. Three
requirements, and nothing else:

1. `[164.9-FANIN-STATUS-NEVER-SET]` - a job enqueued through the public wrapper
   `public.enqueue_compute_job` WITH non-empty `p_parent_job_ids` must land in
   `done_pending_children`. Today it lands `pending`, because the wrapper routes all three modes to
   the TEN-arg `public._enqueue_compute_job_internal(uuid, uuid, text, text, uuid[], text, jsonb,
   uuid, uuid, timestamptz)`, whose `INSERT` omits `status`. Only the SEVEN-arg
   `public._enqueue_compute_job_internal(uuid, uuid, text, text, uuid[], text, jsonb)` computes
   `v_initial_status`, and nothing reaches it.
2. `[164.9-LIVEDB-RESIDUE-RPC-AND-INTENT]` - (a) the `{already_inflight, next_attempt_at}` shape of
   `public.request_allocator_holdings_sync(uuid)` is unreachable; (b) the
   `match-decisions-xor-rls` live-DB arm asserts an index migration 081 replaced.
3. `[164.9-TEST-ANALYTICS-URL-REARM]` - a restore of shared TEST re-seeds
   `system_settings.analytics_service_url` to a PROD-shaped value and nothing re-normalises it.

Out of the boundary: `[164.9-BASELINE-PRIVILEGES-ABSENT]` (K1/K2 ledger kinds - ROADMAP says do not
promote it without a new argument), any baseline re-dump, any `cron.schedule`, any change to the
restore's reference-data allowlist.

<decisions>
## Implementation Decisions

### A. Criterion 1 - proving the harm before any fix

- **D-01:** The harm probe runs FIRST, as its own plan in its own wave, on a **local database only**
  (`scripts/local-stack/run.sh` booted stack, or a `scripts/pg-lane/run.sh` throwaway cluster) -
  never shared TEST, never PROD. It enqueues through the PUBLIC wrapper (service_role path) a child
  with `p_parent_job_ids` naming a still-`pending` parent, then records (i) the child's landed
  `status`, (ii) whether `claim_compute_jobs` / `claim_compute_jobs_with_priority` hand the child to
  a worker while the parent is not done, (iii) what the fan-in advance in `mark_compute_job_done`
  does when the parent finishes. The probe's output is a verdict table (statuses and booleans, no
  ids) written into the plan SUMMARY.
- **D-02:** **Measured before this discussion, and binding on the probe's interpretation:** no
  production caller passes a non-empty `p_parent_job_ids`. Evidence at this worktree's HEAD:
  `grep -rn parent_job_ids analytics-service` (excluding `.venv`) returns ZERO hits in Python;
  every TypeScript hit outside tests is a type or schema declaration (`src/lib/database.types.ts`,
  `src/lib/types.ts`, `src/lib/analytics-schemas.ts`); the only SQL caller naming the parameter
  (`20260419061003_feedback_delta_enqueue.sql`) passes `'{}'`. So the production HARM is
  **latent** (no path reaches it today) even if the lane probe demonstrates the MECHANISM
  (a parented child claimable before its parent finishes). The SUMMARY must say "mechanism
  demonstrated / production harm latent" - never "harm observed in production".
- **D-03:** Whatever the probe shows, the fan-in defect is **FIXED, not dropped**. Per the
  ROADMAP's own rule a no-harm result drops the item to fix-or-drop; the fix is one computed column
  in one `INSERT`, the migration's own comment already states the intent, and the live-DB lane arm
  that proves it already exists. Fix-or-drop resolves to FIX. The phase stays a phase regardless,
  because item 2(a) is user-facing (the Queued pill) and item 3 is a credential-exposure hazard.

### B. Criterion 3 - the two overloads (named BY SYMBOL AND ARITY)

  (`'done_pending_children'` when `p_parent_job_ids` has at least one element, else `'pending'`)

  re-run the prior body.
  Evidence for rejecting DROP of the seven-arg: it is named by signature in at least
  `supabase/tests/test_enqueue_internal_destrict.sql`, `supabase/tests/test_compute_analytics_kind_retired.sql`,
  the mutation runner, `scripts/prod-body-drift-check.sh`, `scripts/test-ledger-drift-check.sh`,
  `scripts/sql-body-normalize.mjs` and `scripts/lint-sql-gates.mjs`; dropping it would remove gate
  arms (collides with the rule that no floor is lowered) and would destroy catalog COMMENTs this
  family's gates use as revert discriminators (see D-06).
- **D-05:** **Re-base on the LATEST ten-arg body, which is
  `supabase/migrations/20260826150000_destrict_enqueue_internal_10param.sql`** (newest `CREATE OR
  REPLACE` of that arity by timestamp, measured by grepping all of `supabase/migrations/**`). The
  planner must re-run that grep at execution time: if 164.4.2 or any other branch has landed a newer
  body, re-base on that one instead. Preserve verbatim: `SECURITY DEFINER`, `SET search_path =
  public, pg_catalog`, schema-qualified `public.` name, the 4-way XOR guard, the `p_kind` NULL guard,

- **D-06:** The new migration **re-issues the ten-arg ACL pair** (REVOKE from PUBLIC/anon/

- **D-07:** The migration's self-verify DO block is **catalog-only** (comment-stripped

### C. Criterion 4 - collision distinguishable from a fresh enqueue

- **D-09:** Fix at the CALLER whose contract promises the shape: a new migration `CREATE OR
  REPLACE`s `public.request_allocator_holdings_sync(uuid)` re-based on its LATEST body,
  `supabase/migrations/20260422122720_reconstruct_per_api_key_gate.sql` (migration 076), and
  restores migration 067's pre-enqueue in-flight look-up
  (`supabase/migrations/20260420103104_allocator_sync_queued_prefetch.sql`) in place of the dead
  `EXCEPTION WHEN unique_violation` handler around the poll enqueue. 076's per-api_key reconstruct
  gate is kept verbatim. **Reversibility:** reversible.
  **Root cause, measured:** 067 added the prefetch; 070
  (`20260420213754_allocator_equity_snapshots.sql`) was re-based on a body that predates 067 and
  silently re-introduced the dead handler the same day; 076 inherited 070's shape. A stale re-base,
  the exact class the re-base rule exists for.
- **D-10:** **Rejected:** changing `_enqueue_compute_job_internal`'s contract (raise
  `unique_violation`, or return a collision flag). Evidence: several callers rely on the
  idempotent return-the-existing-id behaviour by design - e.g. `analytics-service/routers/process_key.py`
  (the C-19 resume path) whose docstring cites it, pinned by
  `supabase/tests/test_enqueue_compute_job_dedupe_non_terminal.sql`. A return-type change also forces
  `DROP FUNCTION`, which destroys the D-06 comment marker. ROADMAP's "RPC change" is satisfied by the
  D-09 change to the user-facing RPC.
- **D-11:** Known, accepted limit, to be written into the migration comment: two concurrent calls
  that both pass the prefetch still collapse onto one row via the partial unique index, and the
  loser receives `{ok, job_id}` naming the winner's job. That race is the one 067 already tolerated;
  it is not closed here. ⛔ Do NOT close the arm by teaching the test to accept the current return
  (ROADMAP forbidden closure).
- **D-12:** The reconstruct-enqueue `EXCEPTION WHEN unique_violation THEN NULL` inside the same RPC
  is ALSO unreachable for the same reason, but it is benign (swallows nothing that can fire) and is
  kept verbatim. Touching it is out of scope (surgical-change rule).

### D. Criterion 5 - the migration-081 invariant

- **D-13:** **Written answer (record verbatim in the plan and in the test's header):** the CURRENT
  `bridge_outcomes` uniqueness invariant is two-part:
  (i) `bridge_outcomes_allocator_match_decision_unique UNIQUE (allocator_id, match_decision_id)` -
  one outcome per decision (migration 081); and
  (ii) `bridge_outcomes_legacy_per_strategy_holding_when_md_null` - a PARTIAL unique on
  `(allocator_id, strategy_id, COALESCE(original_holding_ref, ''))` `WHERE match_decision_id IS NULL`
  (migration 083, `20260426131721_commit_scenario_batch_race_fix.sql`), which restores 072's
  per-strategy guarantee only for rows whose decision was nulled out.
  Two strategy-sourced outcomes for the same (allocator, strategy) under two DIFFERENT decisions are
  therefore ALLOWED by design. The failing arm's expectation (a 23505 on that shape) describes
  migration 072's world and is wrong, not the schema.
- **D-14:** The arm is **rewritten, not deleted**, to assert the current invariant, and each
  assertion must be able to fail: (a) two different decisions, same (allocator, strategy) -> both
  INSERTs succeed; (b) a second outcome for the SAME `match_decision_id` -> 23505 AND the error
  names `bridge_outcomes_allocator_match_decision_unique`; (c) two outcomes with
  `match_decision_id` NULL and the same (allocator, strategy, holding) -> 23505 AND the error names
  `bridge_outcomes_legacy_per_strategy_holding_when_md_null`. Every other arm in the same
  `describe` block that still names the retired `bridge_outcomes_unique_per_strategy_holding` is
  re-pointed at the constraint that actually fires, and the `code === "23505" || message.includes(...)`
  disjunction (which makes the name check decorative) becomes a conjunction. Each tightened
  assertion is calibrated by neuter -> observe RED -> restore. Test-only change; no migration.
- **D-15:** The catalog COMMENT on column `bridge_outcomes.original_holding_ref` still says it
  "enables the widened bridge_outcomes_unique_per_strategy_holding index" (the index 081 dropped).
  It is fixed, not deferred (it is the written record criterion 5 asks for, and it is wrong):
  one `COMMENT ON COLUMN` statement, in its OWN small migration file (not mixed into the
  compute-jobs migrations), catalog-only self-verify. **Reversibility:** reversible.

### E. The REARM - `[164.9-TEST-ANALYTICS-URL-REARM]`

- **D-16:** The re-normalisation runs **inside the restore's own atomic transaction, after the
  reference-data replay**, so a PROD-shaped `analytics_service_url` is never COMMITTED on shared
  TEST, not even for the seconds between a commit and a follow-up workflow step. It is guarded by
  the database-identity marker the restore already reads first, and it is active only in
  `--mode restore` (in `--mode preflight` the transaction rolls back and it must write nothing).
  **Why not a separate post-restore workflow step running `scripts/test-only-normalize-analytics-url.sh`
  as-is:** that script takes `pg_try_advisory_xact_lock(61616158)` and REFUSES when another session
  holds the mutex (its guard 2) - and the workflow's `Acquire shared-test-db mutex` holder session
  holds exactly that lock for the whole job, so the script would always refuse there. The restore
  script uses the other idiom (it ASSERTS the mutex is held, `refuse_without_mutex`), which is the
  one that fits. **Reversibility:** reversible (workflow + script change, no schema).
  **Surfaced conflict (Rule 7):** the ROADMAP and the TODOS entry say "a post-restore step in
  `test-restore-from-baseline.yml`". This decision keeps the intent (the restore leaves TEST
  normalised, inside the held mutex, after the replay) and moves the location into the restore
  transaction because the measured commit window is the hazard. If the researcher finds the restore
  script's transaction cannot host it, the fallback is a workflow step that runs the normalisation
  in a mode that ASSERTS the held mutex (restore-script idiom) instead of trying to take it - never a
  mode that skips the mutex check.
- **D-17:** The normalisation SQL stays **single-sourced**: the restore path must reuse the
  target value and guards of `scripts/test-only-normalize-analytics-url.sh` (e.g. by the script
  emitting its SQL, or a shared fragment), not a second hand-typed copy of the loopback sink value.
  ⛔ Not closed by editing `scripts/restore-test-refdata-allowlist.txt` and not by a migration
  (both forbidden closures recorded in `TODOS.md`).
- **D-18:** Verification of D-16 is by the restore script's `--self-test` and the existing
  wiring test (`src/__tests__/test-restore-workflow-wiring.test.ts`) on disposable clusters, plus
  arm D1 of `supabase/tests/test_analytics_service_settings_and_vault_tick.sql`. A live dispatch of
  the restore against shared TEST is a FOUNDER CHECKPOINT (see FC-3) and does not gate this
  phase's completion - it is currently blocked anyway by the stale-baseline refusal recorded in
  `164.9-11-SUMMARY.md`.

### F. Cross-phase sequencing with 164.4.2 (not yet merged)

- **D-19:** **164.9.1 executes and merges AFTER 164.4.2.** Evidence: on `main` today
  `scripts/local-stack/run.sh` loads `supabase/schema/baseline.sql` and does NOT apply migrations
  newer than the dump (its header: "SCHEMA SOURCE: baseline, NOT migration replay"). 164.4.2's
  DECISION F adds the tail replay (`supabase/schema/baseline-carried-migrations.txt`,
  `scripts/check-baseline-currency.mjs --replay-set`). Without it, the live-DB lane in CI cannot see
  this phase's migrations, so criteria 2 and 6 cannot be proven in CI and the three ledger lines
  could not be removed without turning `frontend-live-db-lane` RED. Execution therefore starts by
  rebasing this branch onto a `main` that contains 164.4.2 (or onto its branch head, if the
  orchestrator sequences it that way). **Reversibility:** costly - a merge in the other order forces
  the ledger lines to stay and a follow-up reconciliation.
- **D-20:** **Re-measure, never copy, every 164.4.2-touched pin.** The live-DB execution ledger
  (`scripts/live-db-execution-ledger.txt`) is 18 entries / `ENTRY_CEILING = 18` on `origin/main` and
  10 / 10 on the 164.4.2 branch. This phase removes exactly the three K3 lines it closes
  (g10b P12, match-decisions-xor-rls, request-allocator-holdings-sync-queued) and lowers
  `ENTRY_CEILING` / `ENTRY_COUNT` by three IN THE SAME COMMIT, but the resulting numbers are READ
  from the rebased tree at execution time, not taken from this file. Same for the lane's pinned
  postgres image (17.6.1.113 on 164.4.2), the `sql-tests` / `test-db-drift` job split, and any
  `61616158` occurrence count. Whichever of the two phases merges second re-measures them.

### G. Gates, reviewers, and what reaches shared databases

- **D-21:** Every migration in this phase goes through `migration-reviewer` +
