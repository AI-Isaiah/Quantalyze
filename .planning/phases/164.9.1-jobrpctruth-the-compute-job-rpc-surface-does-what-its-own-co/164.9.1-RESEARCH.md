## Summary

The phase is three small production changes and one restore-script change. Each change rides on a thick layer of existing gates, and most of the planning risk sits in those gates rather than in the SQL.

The fan-in defect is exactly as reported. The latest 10-arg body (`20260826150000`) omits `status` from its INSERT, and the claim RPCs select `status IN ('pending','failed_retry')` with no parent check. So a parented child that lands `pending` IS claimable the moment it is inserted. The fan-in advance in `mark_compute_job_done` only touches rows with status `done_pending_children`, so it is a no-op for such a child. A second finding makes D-04 safe: a 7-argument call can never resolve against these overloads (measured 42725), so the seven-arg body is dead code and mirroring its status logic changes nothing that runs.

Most of the planning cost is gate choreography:
- every body change needs a regenerated snapshot plus an earned `-- prod-body-ack:` line (VAC-04);

**Verdict (by reading; the probe must confirm by execution):** a parented child that lands `'pending'` is claimable immediately, because its `next_attempt_at` equals `now()`, which satisfies `<= now()`. It is claimable while its parent is still pending or running. The fan-in advance is a no-op for it (its predicate is `status = 'done_pending_children'`). After M1, the child lands `done_pending_children`. It is excluded from claim, and it also blocks its own (kind, partition) through the C39 guard and the in-flight partial unique indexes. It is released to `pending` only when the LAST parent is marked done.

**Probe design (recommended: a vitest arm in the g10b file, run under the live-DB config against the booted local stack):**
- Seed a user and strategy with the existing helpers (`createTestUser`, `seedStrategy`, `insertComputeJob`, `mintClaimToken`, `fetchJob`, `cleanupLiveDbRow` in `src/__tests__/compute-jobs-audit-2026-05-07-g10b.test.ts`).
- Parent: `insertComputeJob` with `status: 'running'`, a minted `claim_token`, and kind `sync_trades`. A running parent is "not done", and a later `mark_compute_job_done` needs the token. This follows arm P15's seeding pattern.
- Child: `admin.rpc('enqueue_compute_job', { p_strategy_id, p_kind: 'reconcile_strategy', p_idempotency_key: null, p_parent_job_ids: [parentId] })`. This is P12's call. Use a different kind so the optimistic look-up and the partial index cannot collapse the child onto the parent.
- (i) Record `fetchJob(child).status`.
- (ii) Call `admin.rpc('claim_compute_jobs_with_priority', { p_batch_size: 1000, p_worker_id: '<probe>', p_unified_backbone_active: null, p_kind_include: ['reconcile_strategy'], p_kind_exclude: null })`. Record whether the child's id is in the returned set.
  ⚠️ Always pass `p_kind_include`. PROD also carries a 2-arg `claim_compute_jobs_with_priority(integer, text)` (`supabase/schema/baseline.sql` GRANT lines), so a 2-named-arg call is the same 42725 shape as Contradiction 3.
- (iii) Call `admin.rpc('mark_compute_job_done', { p_job_id: parentId, p_claim_token: tokenP })` and record the child's status afterwards. Post-fix, also re-run the claim and record whether the child is now claimed.
- Output: a table of statuses and booleans, with no ids. Expected pre-fix: `pending / claimed=true / fan-in no-op`. Expected post-fix: `done_pending_children / claimed=false / pending after parent done / claimed=true`.
- Assert only about the probe's OWN rows. The claim touches every eligible `reconcile_strategy` row on the lane, which is harmless on a private stack.
- Run one file with: `npx vitest run --config vitest.livedb.config.ts src/__tests__/compute-jobs-audit-2026-05-07-g10b.test.ts -t "P12"`.

The SQL-file alternative (psql against the lane DSN inside `BEGIN … ROLLBACK`, with `SET LOCAL ROLE service_role`) also works. `_assert_owner` returns early when `auth.uid()` is NULL (`supabase/schema/baseline.sql _assert_owner`). But a SQL probe needs auth-schema fixtures that the vitest helpers already solve. A pg-lane-only probe would need the claim and mark-done migrations layered onto fixtures, and was not measured. Not recommended.

### Q8 — REARM

**Can the restore transaction host it?** Yes. `build_transaction` writes one SQL file, `$RESTORE_OUT_DIR/restore.sql`. It starts with `BEGIN;` (heredoc `TXN_HEAD`) and appends, in order:
1. the census and closure;
2. the DROP and the dump;
3. `SET LOCAL search_path = public, pg_catalog;`;
4. `cat "$RESTORE_OUT_DIR/refdata.sql"`;
5. `TXN_REFDATA_TAIL` (path restore to `pg_catalog`);
6. the `TXN_REFDATA_GATE` DO block;
7. `TXN_LEDGER_DDL` plus the seed INSERTs;
8. the `TXN_ASSERT` DO block;
9. `COMMIT;` or `ROLLBACK;`.

It is run by `psql "$RESTORE_DB_URL" -X -q -v ON_ERROR_STOP=1 -f restore.sql` in `run_transaction`, with no `-v` variables. `[VERIFIED]`

**Placement:** directly after the `TXN_REFDATA_GATE` heredoc and before `TXN_LEDGER_DDL`. The row has been replayed and gated there. `src/__tests__/restore-test-from-baseline.test.ts` "L-01" pins the relative order of bracket → replay → path restore → gate → ledger DDL. Inserting a block between the gate and the ledger DDL keeps that order, and its calibrations still bite. Add a new order pin that places the fragment after `TXN_REFDATA_GATE` and before `TXN_LEDGER_DDL`. `search_path` is `pg_catalog` at that point, so every name must be schema-qualified. The existing normalize SQL already uses `public.system_settings`.

**Why the current `build_sql` cannot be reused as-is:**
- it wraps itself in `BEGIN;`/`COMMIT;`;
- guard 2 `pg_try_advisory_xact_lock(c_key)` REFUSES because the workflow's holder session owns the lock;
- guard 3 RAISEs on "already holds the sink", which would abort a restore;
- it takes the sink via psql `:'sink'` variables that the restore's psql call does not pass.

**Recommended single-source design (D-17):** refactor `scripts/test-only-normalize-analytics-url.sh` so one function emits the guarded statement body, parameterised by two policies:
- `mutex = try-take | caller-asserts-held`;

## Common Pitfalls

1. **Twin/apply-list desync (mutation runner).** When M1 supersedes 20260826150000, the dedupe gate's B1/B2 twins either go `no-red` (list extended, twins not re-pointed) or silently test the old body (list not extended). There is no automated detector for the latter. *Avoid:* extend the list and re-point the twins in one commit, then run `node scripts/mutation-runner/run.mjs` (or 164.4.2's subset for that file) and see `RED (identity ok)` for B1 and B2.
2. **VAC-08 red on the PR.** See Contradiction 4. Pre-declare it, bind it to the SHA, and check it clears after merge.
3. **Stranded fan-in children after M1 (latent, pre-existing design).** A `done_pending_children` child is released only by a parent's `mark_compute_job_done`. If every parent is already `done` at enqueue time, or a parent ends `failed_final`, or a parent id does not exist, the child never leaves DPC. It also blocks its (kind, partition) through the in-flight index, and the optimistic look-up keeps returning it. `mark_compute_job_failed` does not cascade (no `parent_job_ids` reference in its PROD body). `[VERIFIED: baseline read]` No caller passes parents today (D-02), so this is latent. D-04 mandates exact seven-arg parity. **Record the limit in M1's header and in the SUMMARY. Do not widen scope.** The optimistic look-up also ignores `p_parent_job_ids` when an in-flight job already exists; that is pre-existing and identical in the seven-arg.
4. **Backdated-migration policy.** `migration-policy.yml` fails any ADDED file whose 14-digit prefix is not newer than PROD's `MAX(version)`. VAC-08's header records that TEST re-stamps `version` at apply time. PROD's tip may be an apply-time stamp as well. *Avoid:* name files with the real UTC time at authoring, after the rebase, and re-check before merge if other migrations landed. `[ASSUMED: PROD tip semantics]`
5. **Frontier ceiling.** `FRONTIER_EXEMPT_CEILING=3`. Four or more new migrations, or a stalled `apply-test`, turns VAC-08's ledger half red. Three is the maximum.
6. **The 2-arg `claim_compute_jobs_with_priority(integer, text)` overload in PROD.** Any probe call with only `p_batch_size` and `p_worker_id` is ambiguous. Pass `p_kind_include`.
7. **Data-dependent DO block.** Any `FROM public.<table>` plus a RAISE on the result is refused by the linter. Keep reads to catalogs.
8. **A vacuous early return in the Queued arm.** `request-allocator-holdings-sync-queued.test.ts` has `if (!authed) return; // password-grant disabled — graceful skip`. It passes if sign-in fails. On the local stack sign-in works, since the arm currently fails on its assertion rather than returning. For criterion 6 calibration, the neuter → RED → restore must show the assertion firing, and the early return should become a hard failure. This is data-integrity/user-facing scope per the test-vacuity rule.
9. **Ledger STALE timing.** The ledger gate reds on STALE entries. D-20 removes all three lines and lowers the ceiling by 3 in one commit. Intermediate commits after a single fix are STALE-red if the lane runs on them. Either land the ledger commit together with the last fix, or remove each line with its own fix and lower the ceiling by 1 each time. Do not leave pushed commits red.
10. **164.4.2 not merged yet.** The rebase brings a new `refuse_stale_baseline` body, the ledger at 10/10, the `test-db-drift` job and the D-F replay. Every REARM, ledger and ci edit must be made on the rebased tree.
11. **Snapshot captures preceding comments.** `dump-sql-functions.ts` writes the comment block above each CREATE into the snapshot. VAC-04/08 strip comments, so they don't care, but the snapshot diff will show them.
