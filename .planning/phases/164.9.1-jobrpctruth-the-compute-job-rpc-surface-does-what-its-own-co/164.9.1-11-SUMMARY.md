### What each FIX did, and how it was proven

- **#10 HIGH-2 (M1).**
  - **The dead ends.** `mark_compute_job_done` releases a `done_pending_children` row only when every listed parent is `done`. Before this fix, three parent lists left a child stuck for good, holding its (target, kind) slot: a missing parent id, a parent already `failed_final`, and parents that are all already `done`.
  - **The change.** The body now locks the parents `FOR SHARE` in id order and then counts them. A NULL element, a missing parent or a `failed_final` parent is refused with 22023. A child whose parents are all done starts `pending`. Only a still-open parent makes it start `done_pending_children`.
  - **Why the lock.** It closes the race in which a parent commits `done` between the read and the INSERT: the parent's UPDATE waits on the lock, and its fan-in advance runs as a later statement that sees the child.
  - **Arm (m).** The new DO arm pins the lock, the `failed_final` count and both refusals. Each of the three was neutered on the lane and aborted the apply.
  - **Live-DB proof.** The new live-DB arm `P12-dead-end` was RED against the pre-fix body applied to the lane, with the first failing assertion reading `expected '<uuid>' to be null`. It is GREEN against the new body.
  - **Snapshot and ack.** The snapshot was regenerated. `--diff-bodies` against origin/main still gives the ten-arg `live` hash `ef92e416…`, which equals the pragma, so the ack is unchanged. origin/main's `supabase/` has not moved since the phase base.
  - **What is still open.** A parent that is still open at enqueue and later ends `failed_final` still strands its child. The header now says so, including the user-facing effect migration-reviewer INFO 3 asked for: a strategy then reads "computing" indefinitely. The harm stays latent because no caller passes parents (D-02).
- **#1 (M3).** The sync trigger nulls `original_holding_ref` for every md-NULL row it touches. Both comments now say that the md-NULL index is in effect per (allocator, strategy) among those rows. The DO block still passes. The comment text was read back from the lane. D-13's written answer is unchanged, because it quotes the index definition, which is correct.
- **#4 (M2 arm e).** The arm now matches the `SELECT EXISTS … INTO v_prior_reconstruct` for this key and the `IF NOT v_prior_reconstruct THEN`. Deleting that SELECT on the lane now aborts the apply; before, it passed. The function body is unchanged.
- **#6 (no-oracle).** A new live-DB arm: a non-owner who syncs someone else's disconnected key, with a job pinned, gets `42501 api_key_not_found_or_not_owned`, the same answer as for a missing key. On the lane, a mutant body with the refusal moved above the ownership check was RED, `expected 'P0001' to be '42501'`, and it is GREEN on M2 as written.
- **#9 HIGH-1 (UI).**
  - **Where the 409 goes.** A 409 from Sync now, Reconnect or Add key moves the row to Disconnected, clears the queued state and shows the route's own sentence. If the body is unreadable, a fallback with the same meaning is shown.
  - **The same class, closed.** Disconnected rows had no helper line, so the pre-existing "Reconnect failed — try again" was also never shown. They now carry the same aria-live helper line as active rows, and the styling matches `AllocatorSyncStatus`.
  - **Proof.** Five component arms were added. With the branches neutered, 3 and then 4 arms went RED. With the add-key branch neutered, 1 went RED. All are GREEN restored.
- **#14 M4 (route).** The branch now writes one `console.info` line, `refused: api key disconnected (409)`, with no user or key id. It still writes no error log and no audit event. The route test pins the call and that the line carries no identifier. With the line deleted, the test was RED: `expected "info" to be called 1 times, but got 0 times`.
- **#15 LOW-1 (UI merge).**
  - **The hold.** After an `already_inflight` answer, the merge keeps the optimistic `syncing` state until one of three things happens: the server reports anything but idle or complete, `last_sync_at` moves, or 2 minutes pass after the job's `next_attempt_at`.
  - **Proof.** Four arms were added. Each clause of `isQueuedHold` was neutered on its own, and each mutation turned exactly one arm RED.
  - **Why not the RPC.** It was deliberately not changed, for the reason given in key-decisions.
- **#11 and #12, M1 and M2 (restore).**

It counts with awk. The first draft used `grep -c … || true`, and the static suite's softening-token pin caught that as 4 to 8. The draft was rewritten, and the allowlist was not widened.
