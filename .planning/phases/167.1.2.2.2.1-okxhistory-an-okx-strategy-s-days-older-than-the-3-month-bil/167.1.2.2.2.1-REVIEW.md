## Summary

These parts hold up under adversarial reading:

- **The RPC.** `apply_okx_archive_rebuild` is SECURITY INVOKER with a pinned search_path, and only service_role can EXECUTE it. Its guards check for NULL explicitly and reject malformed input without casting it. It takes a FOR UPDATE row lock, then runs compare-and-set on both the stored gaps and the caller's narrowed gaps. Its INSERT uses ON CONFLICT DO NOTHING, and the ranges are derived from the rows the INSERT actually returned (RETURNING). It writes provenance once. The kind CHECKs are re-based on 20260717233529, which is still the newest declaration of both. The rollback mirrors the migration exactly.
- **The downloader.** It checks an exact-match allow-list that ships empty and refuses any answer that is not a public address. It pins the vetted IP and still verifies the certificate against the hostname through SNI. It refuses redirects, ignores proxies from the environment, and does not use the httpx client, whose request log would print the signed URL. Running counters enforce the size and ratio caps. No exception text carries the signed URL, and Sentry's `include_local_variables=False` keeps frame variables out.
- **The D-02 ordering.** `_check_keys`, which only reads the database, runs before `_allocator_key_preflight`, which decrypts the key. A refused key is never decrypted and never gets an exchange client.
- **The public sentence.** The D-06 text matches the founder's wording character for character.

The money path has one defect that can silently skew a published series (CR-01). It also has several places where a failure is reported as the wrong thing, or where something incomplete is reported as success.

## Critical Issues

### CR-01: The job treats the first live record as the live reach boundary. The partial boundary day then anchors the NAV roll for every rebuilt day, and the truncation detector cannot see the days it exists to check.

**File:** `analytics-service/services/okx_archive_job.py:1274-1374` (`first_realized_day=min(realized_by_day)`), `:1428-1446` (window start = `boundary + 1`), `:1855-1860` (`archive_only_in_live_reach` over `window_days`). Also `analytics-service/services/okx_archive_rebuild.py:245-290` (`live_first_day = live_returns.index[0]`; archive days only `< live_first_day`; the live realized/funding records of the boundary day are kept in the union).

**Evidence:**
- The live realized fetch is `fetch_daily_pnl(since_ms=None)`. It pages OKX `bills` and `bills-archive` newest-first, so its reach starts about 3 months back at an arbitrary time of day, or wherever the 100-page cap cut it (`exchange.py:1448-1560`).
- The job does not calculate that reach. It takes `min(realized_by_day)`, the day of the first *record*, and calls it "the reach boundary day, which is partial" (`:1269-1271`).
- The core it reuses explicitly forbids this: `combine_realized_and_funding` docstring, `broker_dailies.py:264-268`, "Never derive it from the first realized record".
- The plan specified "the live realized reach's first FULL day (the day after the reach boundary)" (08-PLAN `Window.`). RESEARCH Section 5 specified the window `[max(quarter start, run_date - 90 d), quarter end]` and said that archive activity inside live reach with no live row is "the persistent-truncation detector".

**Consequences, both silent:**
1. **The NAV anchor is biased.** `rebuild_union` prepends archive days strictly before `live_first_day` and keeps the live records *on* `live_first_day`. When that day is the partial reach-cut day, the backward roll is `nav[t-1] = nav[t] - pnl[t] - flows[t]` with a partial `pnl[t]`. Every rebuilt day's NAV, and therefore every rebuilt return, is then off by the P&L missing from that day. The archive holds the full day, but the code never uses it for that day. Nothing checks this day:
   - the reconciliation excludes it by design;
   - T-IDENT-1 excludes `live_vals[:1]`;
   - `first_live_day_differs` and `realized_balance_vs_rolled_nav` are information only.

   Today (reach starts about 07-17, first record 08-02 after a quiet stretch) the boundary may happen to be a full day. A run after about 2026-10-31 puts the 90-day cut inside active August days. So would any crawl that hit `OKX_BILLS_PAGE_CAP`.
2. **The truncation detector checks the wrong days.** If the live crawl was truncated, the first record is the truncation point. The window and `archive_only_in_live_reach` then both start after it, so by construction the days that were dropped are never compared. For the PROD accounts, the range 07-17..08-01 is exactly what RESEARCH said must be shown quiet before the `[167.1.2.2.2-OKX-PERSISTENT-TRUNCATION]` question counts as answered. The calibrate result cannot show it.

**Fix:**
```python
# 1. Derive the reach from the fetch window, not from the data:
reach_start_ms = now_ms - OKX_BILLS_ARCHIVE_REACH_MS        # or the begin bound actually sent
reach_day = ms_to_day(reach_start_ms)                         # partial by construction
first_full_day = reach_day + 1 day
# but if any instType hit the page cap (read _LAST_DQ_FLAGS["daily_pnl_truncated_okx"]),
# stop: the realized reach is unknown.
windows = _windows(quarters, first_full_day, today)           # compare 07-17.. not 08-03..

# 2. In rebuild_union, the archive must own every day < first_full_day, the partial
#    boundary day included. Drop the live realized/funding records dated < first_full_day
#    from the UNION call (and the live-only call used for T-IDENT-1), and prepend the
#    archive's full-day values for those days. Live days >= first_full_day are untouched,
#    so D-12 still holds for every stored live row.
```
Also add a gate, routed to the founder like D-10, on `realized_balance_vs_rolled_nav.diff`. It is the only reading that checks the anchor itself.

## Warnings

### WR-01: The archive's realized leg is narrower than the live definition it claims to reproduce. On gap days, where nothing reconciles, the difference is silently dropped.

**File:** `analytics-service/services/okx_archive_classify.py:201-204`, `:217-224`
**Issue:** The live path adds up `pnl + fee` for every non-type-8 bill in the four instTypes, whatever its subtype (`exchange.py:1588-1611`). The archive adds `pnl + fee` only for `REALIZED` subtypes. `NON_EXTERNAL` rows (110/111, 114/115, 16, 17) contribute nothing to realized. Only their `balChg` is collected, and `rebuild_union` never reads it. A NON_EXTERNAL row whose `ccy` is not USD skips the `non_usd_ccy` stop altogether, because of the `continue` at `:204`, which runs before the USD check. Inside the Q3 overlap, the reconciliation would expose the difference. On the 157 gap days, which have no live counterpart, a forced-repay or liquidation-transfer row carrying `pnl`/`fee` changes P&L relative to the live method, contrary to D-07 ("method identical"). Nothing reports it.
**Fix:** Either add `pnl + fee` of every non-funding row in `LIVE_REALIZED_INST_TYPES` to the realized leg, which is exactly the live rule, or stop loud (`unknown_subtype_nonzero` or a new class) when a NON_EXTERNAL row carries nonzero `pnl`/`fee` or is not in USD. Report the per-month NON_EXTERNAL `pnl+fee` beside `excluded_by_month`.

### WR-02: The NAV roll mixes two flow models at the junction, and the cross-check that would catch it never gates

**File:** `analytics-service/services/okx_archive_rebuild.py:267-290`; `okx_archive_job.py:1333-1355`, `:1864-1873`
**Issue:**
- Before `live_first_day`, the union uses archive **transfer bills** (types 11/12, trading-account flows). From `live_first_day` on, it uses ccxt **deposits/withdrawals** (funding-account, on-chain events).
- The anchor is the trading account's `totalEq`. One capital movement can therefore be counted twice. Example: a trading-to-funding transfer on day D < `live_first_day`, followed by the on-chain withdrawal on day >= `live_first_day`. The NAV of every earlier rebuilt day then shifts by the amount.
- In the other direction, a live-period transfer between funding and trading that never shows up as a ccxt deposit or withdrawal is not a flow at all for the roll.
- `flow_totals_overlap` and `realized_balance_vs_rolled_nav` measure exactly this, but both are "information, never a gate". The founder approves a fingerprint that deliberately excludes every live-anchored value (`:1698-1701`), and no check bounds the return values `apply` writes.

**Fix:** Gate `apply` on `realized_balance_vs_rolled_nav.diff` (and, preferably, on the archive-vs-live flow totals over the overlap) within a bound set by founder decision. Also make the preview carry the rebuilt values (or a digest of them), so the apply-time values can be compared with what the founder saw. At minimum, stop when the two diverge beyond a stated tolerance.

### WR-03: A failed live fetch is reported as `reconcile_miss window=none`, and the job ignores the live fetch's DQ flags

**File:** `analytics-service/services/okx_archive_job.py:1326-1328`, `:1442-1450`
**Issue:** `fetch_daily_pnl` catches every exception, including a 429 that outlasts its retries. It records `daily_pnl_fetch_error` in `_LAST_DQ_FLAGS` and returns `[]` (`exchange.py:2060-2075`). The job never reads those flags. An empty live series then becomes the permanent stop `reconcile_miss` with `window=none`. The runbook explains that stop as "the live reach no longer touches the quarter (Pitfall 9)", which can lead the founder to treat a transient venue error as the overlap having expired. The same blindness applies to `daily_pnl_truncated_okx`, which matters for CR-01. The handler's rate-limit deferral never triggers for this path.
**Fix:** After `fetch_all_trades`, read `exchange._LAST_DQ_FLAGS.get()`. Map `daily_pnl_fetch_error` with a rate-limit class to a deferral, other fetch errors to a transient failure, and `daily_pnl_truncated_okx` to a named permanent stop (for example `live_anchor_unusable live_realized=truncated`). Do this before `_reconcile` runs.

### WR-04: The wait has no bound independent of OKX's `ts`, whose meaning is unverified

**File:** `analytics-service/services/okx_archive_job.py:909-916`, `:930-940`
**Issue:**
- Every claim re-POSTs the apply first. If the answer is not `existing` and `age(answer.ts_ms) < 2 h`, the claim returns a wait **without reading the status**.
- The give-up bound is calculated only from that `ts`. RESEARCH marks the timings [ASSUMED] and calls `ts` both "the apply time" and "the first-request time".
- If OKX returns the time of the latest apply, every claim sees age about 0. It re-applies, defers one hour, and never reads the status or reaches the 8 h give-up. Deferral does not use up an attempt, so the loop has no end and keeps a row `pending` indefinitely. The same applies if the re-POST while `ongoing` restarts generation.

**Fix:** Add a backstop that does not depend on the venue: give up at `compute_jobs.created_at + N h`, which is readable without a write to metadata. Read the status on every claim after the first, whatever the age. Record `ts` (as a class: "advanced since last claim yes/no") in a log so the first real run measures its meaning.

### WR-05: A target with nothing to write is reported as `already_applied`

**File:** `analytics-service/services/okx_archive_job.py:1906-1934`
**Issue:** `_already_complete` is simply `not plan.rows and expected_after == stored_gaps`. Several cases satisfy it with nothing ever applied:
- the stored gaps lie entirely outside the ingested quarters;
- every gap day is NaN-guarded;
- the target has no stored gaps, for example a wrong strategy id or a strategy TRADESYNC never measured.

The result then records `rpc: {status: "already_applied"}` and the job ends `DONE`. The runbook reads `already_applied` as a successful re-run. The calibrate preview shows `insert_days: 0`, which softens this, but the apply record that is kept is wrong.
**Fix:** Only call a target `already_applied` when its `planned_dates` are non-empty and lie inside stored archive `reconstructed_ranges` carrying `_ARCHIVE_SOURCE`. Otherwise record `nothing_to_apply`. For an apply, stop when a target has no planned day at all.

### WR-06: One claim can exceed the 15-minute handler timeout, and the timeout comment says otherwise

**File:** `analytics-service/services/job_worker.py:676-680`; `okx_archive_job.py:2047-2067`, `:1323-1348`
**Issue:**
- The comment says "ONE claim covers a preflight, a status read, a download-and-parse, or a live crawl-and-reconcile". In fact a calibrate or apply claim does all of these:
  - two apply POSTs, paced at 11 s or more;
  - status reads;
  - up to two downloads at `TOTAL_TIMEOUT_S` = 300 s each;
  - parsing;
  - six live crawls in sequence, each bounded by `_BROKER_CRAWL_TIMEOUT_S` (810 s);
  - the rebuild;
  - the RPCs.
- All of that runs under a 900 s handler timeout.
- On a heavy account every claim is cancelled the same way. Each retry uses up an attempt and ends with a generic timeout error, never a stop class, after a fresh archive POST and download each time.
- Apply stays safe because each RPC is atomic and a re-claim resumes through rule 3. The failure itself is still opaque.

**Fix:** Give one claim a single budget: a monotonic deadline passed down, with each `wait_for` sized to `min(own_bound, remaining)`. Turn running out of budget into a named transient. Alternatively, raise the kind's timeout together with the watchdog override, and correct the comment.
