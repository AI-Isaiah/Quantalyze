# Phase 167.1.2.2.2.1: Code Review Report (plan 17, D-14 range-mismatch diagnostic)

**Reviewed:** 2026-10-22T09:42:33Z
**Depth:** deep (callers traced through `job_worker.dispatch`, `classify_exception`, `_allocator_key_preflight` and the parser)
**Files Reviewed:** 3
**Status:** issues_found
**Reporting threshold:** MEDIUM and above only, as the caller asked. LOW and INFO findings are not recorded.

## Summary

The code change does what D-14 asks. `_quarter_range_tokens` reads five fixed keys. Each date must
pass `_iso_day`, and the count must be a non-negative int that is not a bool. Everything else becomes
`unreadable`. `_parse_stop` appends the tokens only for the parser label `quarter_range_mismatch`, so
`empty_file` and every other label keep their text byte for byte. The stop class, its permanence,
the result-block-first order and the `from None` at the raise site are unchanged. No amount, billId
or file text can reach `last_error` through the new tokens.

Measured at `c0c709716`:
- `python3 -m pytest tests/test_okx_archive_job.py tests/test_okx_archive_apply.py tests/test_okx_archive_parse.py -q` gives `408 passed`.
- CI's mypy line gives `Success: no issues found in 121 source files`.
- The `job-result` form renders with `DRY=1` (rc 0) and emits `j.last_error,`.
- The Arabic-Indic poison is rejected because CPython's C `date.fromisoformat` refuses non-ASCII
  digits. `_ISO_DAY_RE`'s `\d` matches it, so `_iso_day` relies on that C check.

Two MEDIUM findings remain. The first is in scope: the runbook now prints `last_error` whole beside an
unconditional safety claim that the dispatcher does not honour. The second sits in the parser,
outside the three-file scope. It is a pre-existing crash path that skips the D-14 diagnostic for a
file whose timestamps are far out of range, which is exactly the kind of file this plan exists to
report on.

## Warnings

### WR-01: The `job-result` form now prints `last_error` whole and calls it contract-safe, but this kind's `last_error` is not always written by the job

**Severity:** MEDIUM (information disclosure into operator notes, T-167.1.2.2.2.1-44's accepted premise is false)
**File:** `docs/runbooks/okxhistory-go-live.md:487-490` (the claim) and `docs/runbooks/okxhistory-go-live.md:502` (the new `j.last_error,` column)
**Issue:** The "Read the result." paragraph now says the form shows "`last_error` whole (by the job
contract it carries dates, counts and closed-vocabulary classes only)". It contrasts this with
`member_progress`, which "is never pasted into a tracked file or a chat". That tells the operator the
new column is safe to transcribe. Step 2 then sends its dates to the founder.

The contract only covers text that `_finish_stop` / `_defer_job` build (`okx_archive_rebuild: <class> ...`).
At least two other writers put text into `last_error` for `kind = 'okx_archive_rebuild'`:

1. `run_okx_archive_rebuild_job` passes `_allocator_key_preflight`'s FAILED result through unchanged.
   `okx_archive_job.py` comments that this happens on a race with a concurrent key change. That result
   embeds the PROD api-key uuid:
   `error_message=f"{handler_name}: api_key {api_key_id} not found"` / `... is inactive`
   (`analytics-service/services/job_worker.py:1540`, `:1546`).
2. Any exception that escapes the handler reaches `dispatch`'s catch-all
   (`job_worker.py:14023`, `classify_exception`). Its final arms return `str(exc)[:500]`
   **unscrubbed** (`job_worker.py:1034`, `:1037`). That includes a ccxt `ExchangeError`, which ccxt
   renders as the venue's response body. It also includes a postgrest `APIError` from `_write_result`
   on the DONE path, which the handler deliberately lets propagate. Its `details` can echo row content.
   It also includes the parser `OverflowError` in WR-02.

None of these rows match `^okx_archive_rebuild: `, so the old form only ever showed them as a NULL
`error_class`, and the operator never saw the raw text. The new column puts that raw text in front of
the operator next to a sentence telling them it is safe. A uuid or venue text pasted into a note
violates the repo's "no PROD ids in tracked text" rule. This is a public repo.

**Fix:** Print only contract-shaped text, and say what to do with the rest:
```sql
       substring(j.last_error from '^okx_archive_rebuild: ([a-z0-9_]+)') AS error_class,
       CASE WHEN j.last_error ~ '^okx_archive_rebuild: ' THEN j.last_error END AS last_error,
       (j.last_error IS NOT NULL AND j.last_error !~ '^okx_archive_rebuild: ') AS last_error_uncontracted,
```
Then reword the paragraph: "`last_error` whole when it is the job's own stop text (`okx_archive_rebuild: ...`,
dates, counts and closed classes only). `last_error_uncontracted` true means the text came from the
dispatcher or the key preflight. Read it in `TS_SP` only, never paste it, and return to the founder."
(Alternatively keep the column but scope the claim to rows with a non-null `error_class` and give the
uncontracted rows the same never-paste rule as `member_progress`.)

### WR-02: A file with out-of-range timestamps crashes the parser before the range-mismatch stop is built, so the D-14 diagnostic never fires (out of scope, pre-existing, defeats this plan's goal)

**Severity:** MEDIUM (a range-mismatched file produces an unnamed `unknown` failure with no result block instead of the named, dated stop)
**File:** `analytics-service/services/okx_archive_files.py:247` (accepts up to 16 digits), `:179` (`_ms_to_day`), `:265-266` (called while building the `quarter_range_mismatch` detail). This file is outside the plan-17 scope list and was not changed in the range.
**Issue:** The parser accepts any `ts` of up to 16 ASCII digits. `_ms_to_day` computes
`_EPOCH + timedelta(days=ts_ms // _MS_PER_DAY)`. Any `ts >= 253402300800000` (after 9999-12-31,
15 digits) raises `OverflowError` there. A microsecond-unit `ts` (16 digits) is the most plausible
shape for a "wrong range" file, and it hits this. Measured at `c0c709716`: a one-row file with
`ts=1751328000000000` requested as 2026 Q3 raises `OverflowError: date value out of range` from
`parse_archive_csv`. It does not raise `ArchiveParseError("quarter_range_mismatch", ...)`.

The exception is not an `ArchiveParseError`, so `_ingest_quarter`'s `except` does not catch it, and
neither does the handler's `except _Stop`. It reaches `dispatch` → `classify_exception` →
`("unknown", "date value out of range")`. Three things follow:
- No result block is written, which breaks the result-block-first contract.
- `error_kind` is `unknown`, not `permanent`.
- `last_error` carries neither the class nor any of the five D-14 tokens.

The plan's `<done>` ("A calibrate that refuses a quarter file for its dates now says which days the
file held ...") does not hold for this input. `_quarter_range_tokens` already renders `unreadable`
for a missing day, so the job side would handle the fix cleanly.

The PROD Q2 file that triggered D-14 already produced the named stop, so the one planned re-run is
not expected to hit this. The finding is recorded because the diagnostic is meant to be the reading
for whatever mismatched file comes next.

**Fix (parser, minimal):** make `_ms_to_day` total for the detail, or bound `ts` to the range a
`date` can hold. For example:
```python
# okx_archive_files.py, in the quarter_range_mismatch detail
def _ms_to_day_or_none(ts_ms: int) -> str | None:
    try:
        return _ms_to_day(ts_ms)
    except OverflowError:
        return None
...
"observed_min_day": _ms_to_day_or_none(ts_min),
"observed_max_day": _ms_to_day_or_none(ts_max),
```
With this change the job renders `observed_max_day=unreadable` with the real `rows_outside` count. The
alternative is to tighten line 247 to `len(ts_text) > 13` so a non-millisecond `ts` is an
`unparseable_ts` stop. Either way, add a parser test with a 16-digit `ts` that asserts a named stop
rather than an exception. Route this to the orchestrator, because it touches a file outside plan 17's scope.
