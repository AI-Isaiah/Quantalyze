An empty window for every quarter means calibration cannot be taken: calibrate stops `reconcile_miss` with `window: null` and the runbook says the Q3 overlap expires around 2026-12-30 (RESEARCH Pitfall 9).

**Resumability (discretion, recorded; satisfies the plan-checker's partial-success property without changing Result shape v1 or the RPC).** Each `apply_okx_archive_rebuild` call commits on its own, so after target 1 commits and target 2 fails (a refusal, a timeout, a 5xx after the commit, a worker restart) target 1's rows and narrowed gaps are already stored. Three rules make a re-run finish the job instead of blocking it. (1) A target's PLANNED date set is covered ∩ finite ∩ ((stored `unrecovered_gaps` days that have no `csv_daily_returns` row) ∪ (days inside its stored `reconstructed_ranges` entries whose `source` is `okx_bills_history_archive`)). Before any apply it equals the row date set; after that target's RPC commits, the inserted days have moved from the first term to the second, so the set is unchanged. The fingerprint hashes the planned set, so a re-run after a partial apply matches the approved fingerprint when the archive and the live data have not moved. (2) `from_day` for `rebuild_union` is the earliest day across every target's stored gaps and archive `reconstructed_ranges`, so a committed target narrowing its own gap does not move the rebuild window, and the resumed target's rows (dates AND values) equal the preview's. (3) In apply, a target whose fresh row set is empty AND whose expected narrowed gaps equal the stored gaps it read is not sent to the RPC (the RPC refuses an empty `p_rows` with 22023 by contract, plan 01): it is recorded `rpc: {status: "already_applied", error_class: null}` with `insert_days` 0, and the loop continues with the next target. A target whose fresh row set is empty but whose expected narrowed gaps DIFFER from the stored gaps (live rows filled gap days since the read) cannot be expressed through the RPC; that is decided in evaluation, before the first RPC, and stops the whole apply with `rpc_refused` naming its position and writing nothing (D-11). An RPC that raises P0001 or 22023 is `rpc_refused` naming the position; any other RPC exception (timeout, connection, 5xx) is not a stop class: the handler first writes the result block with every target's `rpc` as it stands (committed targets `applied`, the failing one `{status: null, error_class: "rpc_transport"}`, later ones null), then re-raises so the worker's existing error classification retries it (the module docstring's table in `services/job_worker.py`: a timeout is transient, an unclassified exception is `unknown`, retried by default), and the re-claim resumes per rule (3); if the retries run out (`failed_final`), a fresh apply enqueued with the same `approved_fingerprint` resumes the same way. The `error_class` value is free text in Result shape v1 (string or null), so `rpc_transport` is a value, not a new key or stop class. "Nothing was written" is claimed only when no target's `rpc.status` is `applied`; otherwise the result names which positions were written.

**D-03 threshold (discretion, recorded).** A stored 0.0 day is a hit when the archive realized or funding sum for that day, rounded to the cent, is not zero.
