**Token format (planner's decision under D-14, recorded here so the executor does not re-derive it).**
- The five tokens use the parser's own detail key names, so the job adds no vocabulary of its own: `range_start`, `range_end_exclusive`, `observed_min_day`, `observed_max_day`, `rows_outside`. They come in that order, each as `key=value`, joined by single spaces and appended after `parse=quarter_range_mismatch` with one space. This matches the existing `quarter=<tag> parse=<label>` and `cause=<reason>` style.
- `range_start` and `range_end_exclusive` are the requested quarter as the half-open UTC calendar range the parser asserts. They are rendered verbatim, never converted to an inclusive last day, so the reader sees exactly the bound the code compared against.
- The parser's `requested` key (`2026 Q3`, with a space) is NOT emitted. `quarter=<tag>` already carries the same label, and a space inside a value would break key=value reading.
- A value that is not what the parser documents renders as the fixed literal `unreadable`. That word is already used for this purpose in this module's stop texts (`link=unreadable`, `age=unreadable`, `live_amount=unreadable`). Dates go through `_iso_day`, the count must be an int that is not a bool and is not negative, and a missing key also renders `unreadable` (never `KeyError`).
- An `empty_file` stop has no rows, so it has no observed day. Its text stays `quarter=<tag> parse=empty_file` exactly, and the `parse=` label is what tells it apart from a real range mismatch.
- No length cap exists downstream. `main_worker` passes `DispatchResult.error_message` to `mark_compute_job_failed` unclipped, and that function writes `p_error` (TEXT) into `last_error`. The bound is by construction: five fixed keys, and each value is a 10-character date, the literal `unreadable` or a row count.
