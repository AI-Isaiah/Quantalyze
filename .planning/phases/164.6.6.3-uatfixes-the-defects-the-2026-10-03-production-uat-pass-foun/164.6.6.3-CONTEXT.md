## Phase Boundary

This phase delivers ROADMAP items **0** and **9** of the 2026-10-03/04/05 UAT defect list, and
nothing else (D-01):

- **Item 0.** A fresh MT5 login on the jobs terminal reads its deal history before MT5 has
  downloaded it, so onboarding a new account fails permanently. The phase adds a bounded,
  fail-loud history wait. It also owns the `MT5-JOB-TERMINAL-TRADES-SCRUB-01` close-out and the
  `_JOB_TERMINAL_DELETE_TRADES` flip to 1.
- **Item 9.** An MT5 key on a broker server the terminals do not know hangs 45.6 s in `login()`
  and is reported as `KEY_SIGN_IN_FAILED`. The phase detects that case before login and names it.

**Measured at HEAD `c8e87b19` (2026-10-06, read-only scout; re-measure at plan time):**

- **Item 0 is still present.** `services/mt5_read.py::read_mt5_deal_ledger` runs `login()` →
  `account_info()` → the login bracket, then calls `history_deals_get(0, now+1d)` with no wait.
  - Callers: `job_worker.py` (~4957) and `equity_reconstruction.py` (~3053). Both are bounded by
    `asyncio.wait_for(..., _MT5_DERIVE_READ_TIMEOUT_S)` = 40 s (`mt5_concurrency.py:91`, request
    timeout 30 s + 10 s). A timeout of that bound restarts the terminal.
  - The refusal is stamped `error_kind="permanent"` ("material equity but <2 usable daily-return
    days", `job_worker.py` ~5262).
- **The flip is this phase's.** `_JOB_TERMINAL_DELETE_TRADES: Final[int] = 0` is on `origin/main`
  (`services/mt5_relogin.py:488`, used at ~1904 and ~2040). 164.6.6.1's pin test exists:
  `tests/test_mt5_relogin.py` `test_SCRUB_the_job_path_keeps_trades_until_MT5_JOB_TERMINAL_TRADES_SCRUB_01`,
  reading `TODOS.md` at run time through `_trades_scrub_entry_dictates`. The `TODOS.md` entry has
  no real `History wait shipped:` line yet, so 164.6.6.3 is the second merger and owns the flip.
- **Item 9 is still present.** Login goes through `Mt5Client.login` (`mt5_client.py:2564`), with a
  20 s IPC timeout (`MT5_LOGIN_TIMEOUT_MS`) inside the 55 s validate chain. A login-stage -10005 is
  routed to `SIGN_IN_FAILED` (`routers/exchange.py` ~850-900, 167 D-17), and an unknown server
  produces the same -10005.

### Scope and split (founder, 2026-10-06, smart discuss Area 1, "Accept all")
- **D-01.** The original 164.6.6.3 item list is split by topic into four phases.
  - **This phase (A) is MT5 onboarding: items 0 and 9.**
  - **B** is wizard wire codes: items 7 and 10, plus the wizard COPY for item 0's history-not-ready
    failure.
  - **C** is factsheet truth: items 2, 3 (with the two-sample KS fix), 4, 5 and 6b.
  - **D** is UI polish: items 1, 6a, 6c, 6d, 6e, 6f and 8.
  - B, C and D are booked as their own phases with `/gsd-phase --insert`, each carrying the
    scout's findings into its ROADMAP entry.
- **D-02.** Order: **A first** (item 0 blocks onboarding and owns the trades flip), then **D**
  (item 1 is a rename risk and every D item is small), then **B**, then **C** (the largest; it needs
  a PROD recompute).
- **D-03.** Item 9's headless-resolution spike is optional and founder-led, a task after item 0
  inside this phase. Item 0 must be able to ship even if the spike never runs.

### Item 0 — the history wait (founder, 2026-10-06, smart discuss Area 2, "Accept all")
- **D-04. Detection.** After a FRESH login (the account was not the terminal's previous holder),
  poll `history_deals_get` until the deal count is stable across consecutive reads. An account
  whose history is already cached pays no wait.
- **D-05. Bound.** About 30 s of bounded wait, inside an outer `wait_for` raised for this call only.
  The wait must never trip the existing 40 s bound's terminal-restart branch. Derive the outer bound
  from the symbols (wait budget + the read's own budget); never hand-pick it.
- **D-06. Expiry.**
  - Material equity with no settled deals when the bound expires is a **TRANSIENT, retryable**
    failure with its own `error_kind`, logged at ERROR. It is never stamped permanent.
  - Zero equity stays an honest empty result.
  - Never invent data.
  - The wizard copy for this failure belongs to phase B. Until B ships, this phase must not make
    the existing copy worse.
- **D-07. Tests and the flip.**
  - A failing-first race test: a fake whose history arrives after N reads goes RED on today's code
    and GREEN with the wait.
  - Then ONE commit, failing-first:
    - appends `History wait shipped: <date>, <sha>` to `TODOS.md` `MT5-JOB-TERMINAL-TRADES-SCRUB-01`;
    - flips `_JOB_TERMINAL_DELETE_TRADES` to 1, as 164.6.6.1's pin test requires.
  - The flip makes every account new to the jobs terminal after each `ipc_fault` recycle, so the
    wait is load-bearing for production syncs, not only for onboarding.

### Item 9 — a broker server the terminals do not know (founder, 2026-10-06, smart discuss Area 3, "Accept all")
- **D-08. Runbook, not headless.** The supported remedy is a runbook step that adds the server to
  both terminals. Headless resolution is unproven, and probing it needs the founder's credentials
  (see D-03).
- **D-09. Detection.** Before `login()`, pre-check the requested server against the terminals'
  known-server list. A miss returns a named outcome at once, with no 45.6 s hang.
  - ⚠️ **Open for research:** whether the terminals expose a readable known-server list (for
    example `servers.dat`, which `mt5_client.py` already mentions near line 1649) and how reliable
    it is. If no reliable source exists, research must say so and propose the next-best signal.
    Planning must not assume one exists.
- **D-10. User-facing outcome.** A distinct, recoverable wizard code, for example: "Our MT5
  terminals do not recognise server X yet. We have been notified." It is logged at ERROR and is
  Sentry-visible, so the founder can add the server.
- **D-11. 167 D-17 is unchanged for known servers.** A login-stage -10005 on a known server still
  means sign-in failed. The new branch fires only on a known-list miss.
