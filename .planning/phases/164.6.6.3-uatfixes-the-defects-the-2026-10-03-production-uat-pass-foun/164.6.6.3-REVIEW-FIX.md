### CR-01: A sub-interval tail sleep let two near-simultaneous reads compare equal

**Files modified:** `analytics-service/services/mt5_read.py`, `analytics-service/tests/test_mt5_read.py`
**Commit:** `6c7537c6a`
**Status:** fixed: requires human verification (logic fix; the loop's expiry arithmetic is semantic, not syntactic)
**Applied fix:** `_settle_deal_history` now checks `_clock() + _MT5_HISTORY_POLL_S > deadline` BEFORE each sleep and raises `Mt5HistoryUnsettledError(previous, material)` if a full interval does not fit. Every sleep is exactly `_MT5_HISTORY_POLL_S`; `min(poll, deadline - now)` is gone, and so is the post-read expiry check, which the pre-sleep check subsumes. A read can therefore only be compared with one taken a full interval earlier.

**RED to GREEN evidence.** New `_TimedGrowingTransport` (a history growing one deal per whole fake second, every read advancing the fake clock by `cost_s`) and `test_a_history_still_growing_never_settles_on_a_short_tail_interval`, parametrized over (read cost, growth offset) = (0.3, 0.0), (0.3, 0.5), (0.3, 0.75), (0.45, 0.0). The conftest clock makes reads cost 0 s, which is why the defect hid; this one makes them cost time.
- RED on the old loop: 4 failed. `(0.3, 0.5)` and `(0.3, 0.75)` fail with `DID NOT RAISE Mt5HistoryUnsettledError`, i.e. the loop returned `settled=True` on a still-growing history (the review's defect, reproduced). The other two raised but only after a short sleep (`sleeps=[..., 0.5999..]`, `[..., 0.1000..]`), caught by the `all(s == _MT5_HISTORY_POLL_S ...)` assertion.
- GREEN after the fix: all 4 pass. The test also asserts the key is not recorded as settled (`mt5_history_wait_due(...) is True`).
- Side effect, intended: with the pre-sleep check no read starts after `deadline`, which is the first option REVIEW WR-01's fix names. WR-01 itself (outer-bound budget, the tautological pin) is NOT addressed here.

### SFH-M1: `_MT5_TERMINAL_HISTORY_SETTLED[tk]` was never invalidated

**Source:** the silent-failure review's MEDIUM-1 (confidence 7). It is NOT in REVIEW.md; it was supplied in the fix brief. Quoted as briefed: "After settle -> `ipc_fault` scrub (deletes the trades cache, holder -> UNKNOWN) -> fresh read for K stamps holder=K -> wait EXPIRES unsettled -> K's next read sees holder K and a stale settled K, so `mt5_history_wait_due` returns False and reads an empty or partial cache as complete."
**Files modified:** `analytics-service/services/mt5_client.py`, `analytics-service/tests/test_mt5_read.py`
**Commit:** `190bd907a`
**Status:** fixed: requires human verification (state-handling logic)
**Applied fix:** in `_note_terminal_holder`, the one stamping door, the settled record for the terminal is popped whenever the holder being stamped differs from the key the record names (`if SETTLED.get(tk, holder) != holder: pop`). Re-stamping the SAME key keeps it.

**Why this is the smallest change that closes every path (and why not the other option).**
- The record is a claim about the deal cache sitting on the terminal's disk for ONE key. That claim is falsified exactly when the terminal is stamped for anyone else: a scrub with `terminated >= 1` stamps `HOLDER_UNKNOWN` (the scrub deletes only after a terminate, so a delete always comes with that stamp); a recycle stamps `HOLDER_UNKNOWN`; the house relaunch and heal stamp `HOLDER_HOUSE`; another key's login stamps its own id. All of them go through `_note_terminal_holder`, so one edit there covers every path, including a scrub that raised after crossing, because the owed relaunch debt forces a house relaunch (which stamps) before the terminal is used again.
- Dropping at "fresh read start" (the other option in the brief) was rejected as the single fix: it only helps if the later login for K happens through a settle-path read. A re-login of K through any other path after a scrub would still find holder == K and a stale record. Keying on the holder change does not depend on which caller logs in next.
- The epoch guard at the top of the door still applies: an abandoned thread's stamp returns before the drop, so it cannot invalidate a record owned by the lease that now holds the terminal. Dropping a claim is always the safe direction (it costs one re-wait), so no lock beyond the GIL is added.
- A restart already empties the registry (reads as fresh), so nothing more is needed there.

**RED to GREEN evidence.**
- `test_a_settled_record_does_not_outlive_the_holder_it_vouched_for`, parametrized over the three displacing events `scrub_or_recycle` (`HOLDER_UNKNOWN`), `house_relaunch` (`HOLDER_HOUSE`), `another_key`: settle K, displace, fresh read for K that expires unsettled (its login re-stamps K), assert `mt5_history_wait_due(tk, K) is True`. RED before the fix: 3 failed with `assert False is True` on `mt5_history_wait_due`. GREEN after.
- `test_a_re_stamp_of_the_settled_holder_keeps_the_record` guards against over-firing (a cached read's own login must not make it pay the wait). It passed before and after, as it must.

### WR-01: The fresh outer bound did not budget the trailing deal-history read (topic B)

**Files modified:** `analytics-service/services/mt5_concurrency.py`, `analytics-service/services/job_worker.py`, `analytics-service/services/equity_reconstruction.py`, `analytics-service/tests/test_mt5_concurrency.py`, `analytics-service/tests/test_mt5_read.py`, `analytics-service/tests/test_mt5_derive_branch.py`, `analytics-service/tests/test_equity_reconstruction.py`
**Commit:** `f5b5a803d`
**Status:** fixed: requires human verification (timing arithmetic)
**Applied fix:** new `mt5_derive_read_bound_s(*, read_s, wait_s, fresh)` and `_MT5_HISTORY_TRAILING_READ_S` (= `_MT5_REQUEST_TIMEOUT_S`, derived, not a literal) in `mt5_concurrency.py`. A cached read keeps `read_s`; a fresh read gets `read_s + wait_s + _MT5_HISTORY_TRAILING_READ_S`. With the defaults that is 40 + 30 + 30 = 100 s where it was 70 s. Both call sites (`job_worker` derive, `equity_reconstruction` backfill) call it, passing their own module's `_MT5_DERIVE_READ_TIMEOUT_S` and `_MT5_HISTORY_WAIT_S` at call time, so the existing per-module patch points still work. The trailing allowance is read from `mt5_concurrency` at call time.
**Why the formula is right.** Topic A's pre-sleep check means no settle read STARTS after the deadline, but the last one can start AT it and run a whole rpyc timeout. The settle deadline itself starts after login, PRE and the first read, so `read_s` (which already covers those and POST) plus the full wait plus one trailing read is the latest the helper can legally finish.

**Tests (the tautology is gone).** `test_history_wait_bound_is_derived` now asserts `fresh_bound >= read_s + wait_s + MT5_REQUEST_TIMEOUT_S` (the rpyc timeout imported from `mt5_client`, not read back from the new constant) and `cached_bound == read_s`; the `X + wait > wait` line was deleted. Added: `test_the_fresh_outer_bound_covers_a_trailing_read_that_starts_at_the_deadline` (`test_mt5_read.py`) drives the REAL `read_mt5_deal_ledger` through the slowest legal fresh run under the fake clock (read budget spent on login/PRE/first read, history never settles, the read that starts exactly at the deadline costs a full rpyc timeout) and requires the elapsed fake time to fit the bound; plus one wiring test per call site (`test_the_fresh_derive_bound_budgets_one_trailing_read`, `test_the_fresh_backfill_bound_budgets_one_trailing_read`), each of which fails if the trailing allowance is dropped. The four existing "wait zeroed" bound tests also zero `_MT5_HISTORY_TRAILING_READ_S` so they still measure their small bound.
**RED proof.** Neutered `mt5_derive_read_bound_s` back to `return read_s + wait_s` (byte backup in the scratchpad, restored with `cp`; no git checkout/restore/stash). All 4 new/replaced tests FAILED: the pin, the behavioural elapsed-vs-bound test, and both wiring tests (`FAILED` lines for all four). Restored, verified `return read_s + wait_s + _MT5_HISTORY_TRAILING_READ_S` is back, GREEN.
