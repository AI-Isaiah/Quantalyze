## Narrative Findings (AI reviewer)

None at MEDIUM or above. What was checked on each question asked:

**Settle loop (`services/mt5_read.py:163-193`).**

- The pre-sleep check `_clock() + POLL > deadline` means every sleep is a full interval. A read never starts after `deadline`, and with zero-cost reads the last one starts exactly at it (reads at t=2..30, 15 in all).
- `stable_intervals` counts only consecutive equal comparisons. Any change resets it to 0. An equal zero under material equity goes down the reset branch, so Finding C's protection holds.
- The raise passes `previous`, which by then is the count of the last read: the same value the old code reported.
- The stability window (2 × 2 s) fits the 30 s budget, and `test_history_wait_bound_is_derived` pins that.

**Outer bound (`mt5_concurrency.py:118-134`, `job_worker.py:4999`, `equity_reconstruction.py:3086`).**

- A cached read keeps `read_s`. A fresh read adds `wait_s + _MT5_HISTORY_TRAILING_READ_S`, and that allowance is read from the module global at call time, so the test patches bite.
- Both sites pass their own module's names, so the existing per-module patch points still work.
- The worst legal fresh run is login + PRE + first read (inside `read_s`), then the wall-clock settle window (≤ `wait_s`), then one read that starts at the deadline, then POST (inside `read_s`). The bound covers it.
- Sub-MEDIUM note, not booked: one `history_deals_get` is two to three separately rpyc-bounded crossings (the fetch, then `_materialize_rows`' `execute` and namespace call). So "one rpyc timeout" is a heuristic allowance, not a strict ceiling. A read that actually reaches the rpyc bound raises anyway, a healthy read measures in milliseconds, and `read_s` carries slack. No concrete failure scenario was found.

**Settled-record invalidation (`mt5_client.py:805-806`).**

- Every holder change goes through `_note_terminal_holder`: login, credentialed initialize, recycle (`HOLDER_UNKNOWN`), the scrub verb with `terminated >= 1`, the validation scrub's house re-stamp, and park (`HOLDER_HOUSE`).
- Nothing pops `_MT5_TERMINAL_HOLDERS` outside that door. The only bypass is the test reset at `:622`, which clears both registries.
- The drop sits after the epoch guard, so a zombie thread cannot clear a record it no longer owns.
- A zombie scrub whose stamp is refused still leaves relaunch debt, and the forced house relaunch stamps `HOLDER_HOUSE`, which drops the record.
- `get(tk, holder) != holder` keeps the record on a same-key re-stamp and drops it on any other holder, sentinels included.

**Sentry scope semantics (sentry_sdk 2.71.0, pinned in `requirements.txt`).**

- In 2.x, `new_scope()` forks the current scope and installs it as the current scope (a contextvar) for the `with` block.
- Top-level `sentry_sdk.capture_message` resolves `get_current_scope()`, so the event carries the tag and the tag dies with the scope. The real-sdk tests show both halves: the alert carries the tag and a later event does not.
- The existing `except Exception` still wraps the `with`, so a Sentry failure can never replace the verdict.
