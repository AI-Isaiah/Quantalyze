# 164.6.5 MT5VALIDATEWEDGE: silent-failure review, round 1

Files hunted: `analytics-service/services/mt5_client.py` (`recycle_terminal_process`,
`_REMOTE_TERMINAL_RECYCLE_SRC`), `services/mt5_relogin.py` (`_escalate_ipc_fault`,
`_capture_wedge_evidence`, `_classify_recycle_verdict`, `_heal_blocking`),
`services/mt5_session_episodes.py` (escalation gate), `services/mt5_validation.py`
(`is_ipc_transport_fault`), `services/mt5_probe.py`, `routers/exchange.py`, plus the
escalation tests in `tests/test_mt5_relogin.py` and `tests/test_mt5_client_contract.py`.
Nothing was run against the live gateway or any database.

**What is done well.** The never-raises property survives the new path. Every `Exception`
from the capture and from the recycle becomes `KIND_IPC_FAULT_RECYCLE_FAILED`, logged at ERROR,
and `Mt5SessionAbandoned` is re-raised deliberately. A test proves the recycle cannot escape via
`RuntimeError`. The recycle verb raises instead of returning a verdict when the transport
seam is missing or the remote JSON is malformed. The capture records `not_captured` WITH the
reason and never fills a gap by logging in. Debounced attempts are logged, not silent. The
`not_healed:` verdict stays byte-identical. None of the findings below is an empty catch or a
swallowed exception. They are cases where the escalation REPORTS something it did not measure,
or goes quiet while the outage continues.

## HIGH

### SFH-01: a recycle is labelled "recycled" (INFO, no Sentry event) without checking that anything was terminated

- **Where:** `mt5_relogin.py::_classify_recycle_verdict`
- **What:** the kind comes from `authorized` / `relaunch_code` alone. `matched`, `terminated`
  and `exited` are printed into the detail but have no effect on the kind or the level. Yet
  `deploy/mt5-gateway/railway-gateway.md` (D-05 caveats) says: *"treat a recycle verdict's
  `terminated` / `exited` counts as the only evidence the terminate landed"*. The
  Wine-side `TerminateProcess` path has **never run live**, and no test executes the remote
  source.
- **Failure scenario:** the remote source matches 0 processes. Causes could be an image-name or
  case difference under Wine, or an `OpenProcess` that is refused, which hits
  `if not handle: continue` with no `GetLastError` recorded. It could also match 1 and terminate 0.
  Either way no process was ended. If the relaunch probe's bare `initialize()` then happens to
  answer (a transient `-10005`, or a zombie releasing the pipe), the result is `ipc_fault_recycled`
  at INFO. The docstring glosses that kind as *"nothing for anyone to do; the terminal is back"*.
  If the probe does not answer, the result is `recycled_still_faulted`, which says *"the recycle
  ran and the terminal still does not answer"*. That points the operator at the VNC console for a
  recycle that never happened, and the gate stays disarmed for the rest of the run, so it is never
  retried. `matched=0` on every wedge would look like "the recycle doesn't cure this" rather than
  "the recycle verb is broken".
- **Tests that cannot fail:** the relogin double always returns `{"matched": 1, "terminated": 1,
  "exited": 1}` (`tests/test_mt5_relogin.py:153`). The contract test `_install_recycle_double`
  is used with `(1, 1, 1)`. No case exercises `matched=0`, `terminated<matched` or
  `exited<terminated`.
- **Fix:** add a kind before the relaunch branch, e.g. `ipc_fault_recycle_not_landed` at ERROR,
  whenever `matched == 0 or terminated < matched`. Treat `exited < terminated` as at least a
  WARNING qualifier. Pin it with a `(0,0,0)` + authorized-relaunch case that must NOT read
  `recycled`, and have the remote source return `GetLastError` for refused opens and terminates.

### SFH-02: the relaunch verdict is read too early, so a WORKING recycle is logged at ERROR as "a human is needed"

- **Where:** `mt5_client.py::Mt5Client.recycle_terminal_process` (step 2), consumed by
  `_classify_recycle_verdict` and by the level ladder in `_escalate_ipc_fault`.
- **What:** the relaunch is ONE bare `initialize()`, bounded by
  `MT5_INITIALIZE_TIMEOUT_MS` (default 20000). The only live measurement (D-05 record, run 1)
  shows a relaunch taking about 60 s from launch to authorized: the terminal appeared about 25 s
  after the kill and was authorized 86 s after the kill. The verb takes its single reading well
  inside that window.
- **Failure scenario:** the recycle works, but the 20 s probe reads `-10005` / `-10003` / `0`
  while the terminal is still starting. The result is `ipc_fault_recycled_still_faulted` at ERROR,
  which becomes a Sentry event (default `LoggingIntegration`, `sentry_init.py`), with the comment
  gloss *"A HUMAN is needed; a second automatic recycle is exactly what the debounce refuses"*. The
  next tick, 10 min later, reads authorized. On most successful recycles the operator gets a false
  alarm pointing at the VNC console. That trains them to ignore this exact ERROR, the only new loud
  signal this phase adds (see SFH-03). If the probe reads `-6` while the saved session is still
  loading, the run is labelled `recycled_no_account` instead.
- **Fix:** give the relaunch a bounded settle loop inside the budget, e.g. up to 90 s of
  `initialize()` polls with the round-trip count re-derived. Alternatively, record an
  intermediate kind such as `ipc_fault_recycled_pending` at WARNING and let the NEXT tick's first
  probe decide success or still-faulted, logging ERROR only then. Either way the kind must say
  "not yet known" rather than "still faulted".

### SFH-03: after the one escalation, a wedge that persists goes back to WARNING/INFO for as long as it lasts. The 4-day outage is only partly louder.

- **Where:** `mt5_relogin.py::_escalate_ipc_fault` (debounced branch, `logger.info(... is NOT
  repeated ...)`), the `heal_mt5_terminal_session` severity ladder (`not_healed:` → WARNING),
  and `mt5_session_episodes.py` blind-run escalation (WARNING).
- **Answer to "does this phase make the 2026-09-21 → 25 outage loud?"** Partly. Before this
  phase, a 4-day `-10005` wedge produced only WARNING/INFO lines on every tick, so no Sentry event
  at all. Now each run produces exactly ONE ERROR (`recycled_still_faulted` or `recycle_failed`),
  and then every later tick is back to the pre-phase shape: WARNING `not_healed:ipc_fault`, a
  blind-run WARNING, and an INFO "already attempted". A 4-day wedge that the recycle does not cure
  (Cause A, the persisted modal dialog, which the phase's own remedy says a recycle cannot fix)
  therefore yields one Sentry event at hour 0 and nothing for the next 96 hours. Under SFH-02,
  that one event may already have been dismissed as a known false alarm. Other cases produce no
  ERROR at all:
  - `-10004` (bridge detached). This path is never escalated and always logs WARNING.
  - `-10003` and `0`. The same as `-10004`.
  - A wedge whose ONE attempt came back `recycled` (SFH-01) or `recycled_no_account` (WARNING)
    and then re-wedged inside the same run (see SFH-05).
- **Fix:** keep the debounce on the ACTION, not on the ALARM. Record the monotonic time of the
  attempt. While the run continues, re-log at ERROR once per fixed window (for example hourly,
  matching the prober cadence) with the elapsed time: "ipc_fault persists N min after the one
  recycle; operator needed". Consider the same hourly ERROR for a persistent `-10004`. This is
  alarm cadence only and does not re-open the one-recycle-per-run decision.

## MEDIUM

### SFH-04: the wedge-evidence capture structurally cannot capture on the fault class it is gated to

- **Where:** `mt5_relogin.py::_capture_wedge_evidence`, and the claim beside it and in
  `TODOS.md` `MT5-SWITCH-WEDGE-CAUSE-01` / the runbook's Step 2b that the heal "records them
  first".
- **What:** the capture only runs after a bare `initialize()` has just failed with `-10005`.
  `terminal_info()` / `account_info()` go through the same dead terminal IPC (the MetaTrader5
  package does not serve them on a session whose `initialize()` failed). The test that models the
  realistic wedge,
  `test_ESCALATION_an_unanswered_capture_is_recorded_not_captured_and_still_recycles`, has the
  double answer `terminal_info` with `-10005`. That is the expected production shape. The
  happy-path capture test only passes because its double answers `terminal_info` DURING a wedge.
- **Failure scenario:** every real Cause B wedge logs
  `build=not_captured … (terminal_info failed: … code=-10005; account_info skipped)`, then
  recycles and erases the state. The line is honest, so nothing is hidden in the line. The
  failure is in the ledger: the TODOS item's close path ("unless something records the build and
  the servers before the recycle") now reads as covered, but the evidence it needs never arrives.
  The comment's reasoning, *"the per-field reads … are served by the BRIDGE, which is exactly the
  half this fault class says is alive"*, applies to the `_materialize` field reads and not to the
  `terminal_info()` call itself.
- **Fix:** say so in `TODOS.md` / the runbook: the automatic capture is best-effort and is
  expected to be `not_captured` on a true `-10005`. Also consider a bridge-side read that does not
  need the terminal IPC, such as the terminal64.exe file version from the install directory,
  read through the same committed-literal remote source as the recycle. That keeps the build half
  of D-03a capturable.

### SFH-05: the once-per-run gate can stay disarmed across a recovery it never observed

- **Where:** `mt5_session_episodes.py::claim_ipc_fault_escalation` / `rearm_ipc_fault_escalation`.
  The gate is re-armed only in `_heal_blocking`'s authorized and `-6` branches, and by a
  non-`-10005` first-probe code.
- **What:** the gate is re-armed only by a first probe that the monitor itself takes. A busy skip
  (`KIND_BUSY_SKIP`, common because `dispatch_loop` holds the lease), a budget abandon, a
  construction or connect failure, the credentials/gateway-not-configured returns and the kill
  switch all skip the probe, so none of them re-arms the gate.
- **Failure scenario:** the monitor reads `-10005` and recycles. The terminal recovers, but every
  tick for the next hours is a busy skip while jobs run. A later validate re-wedges the terminal
  (Cause B, the account-switch wedge). The monitor's next probe reads `-10005`. The gate is still
  disarmed, so it logs INFO "already attempted in this run" and never recycles the NEW wedge.
  The wedge then runs silently until an analytics-service redeploy (combine with SFH-03).
- **Fix:** also re-arm on a cooldown (for example, the attempt is older than the prober's 1 h
  window), or on evidence from other callers that the terminal answered (a successful lease-held
  MT5 call in the job path). Add a test: `-10005` → recycle → N busy skips → `-10005` must be
  either a recycle or an explicitly logged decision, never the INFO "same run" line after an
  unobserved recovery.

### SFH-06: a budget abandon mid-escalation discards the only evidence that the terminal was killed

- **Where:** `mt5_client.py::recycle_terminal_process` (the relaunch catches only
  `Mt5ClientError`), `_escalate_ipc_fault` (re-raises `Mt5SessionAbandoned`), and the
  `heal_mt5_terminal_session` `asyncio.TimeoutError` arm.
- **Failure scenario:** `wait_for` fires after the remote terminate has landed. The worst path
  is 8 × 30 + 10 = 250 s, so this needs a hang, or a Railway `MT5_RELOGIN_BUDGET_S` override
  still sized for the old 5-trip path (160 s). The lease then releases and bumps the generation.
  In the zombie thread the relaunch `assert_session_authorized()` raises `Mt5SessionAbandoned`
  from `_assert_live`, which is not an `Mt5ClientError`, so it propagates out of the verb. The
  `matched/terminated/exited` dict is discarded, `_escalate_ipc_fault` re-raises, and the future
  is never read. The only line logged is the generic `ABANDONED at the …s budget` ERROR, which says
  nothing about a terminal process having been ended and not relaunched by us. The gate stays
  disarmed. The terminal comes back only when the next caller's `initialize()` happens to launch
  it.
- **Fix:** in the verb, log the remote counts (INFO/WARNING, counts only) immediately after
  parsing them and before the relaunch, so they reach the log whatever happens to the relaunch.
  Alternatively, catch `Mt5SessionAbandoned` around the relaunch only, record
  `relaunch_code=None, relaunch_abandoned=True`, and re-raise after logging. Also confirm that no
  Railway override of `MT5_RELOGIN_BUDGET_S` sits below the new 250 s derivation. That check is
  for the operator; it was not run here.

### SFH-07: "recycled" / "authorized" after a relaunch does not say WHICH account, or whether the broker is connected

- **Where:** `recycle_terminal_process` (`authorized` = bare `initialize()` succeeded),
  `_classify_recycle_verdict`.
- **What:** the D-05 record measured that a relaunched terminal comes back on *"whichever
  account the last service call had logged in to"*, which in run 2 was a different account. A
  bare `initialize()` returning True also does not show that the terminal is connected to the
  trade server. The 4-day incident's own Journal reading was a terminal `disconnected` with no
  reconnect.
- **Failure scenario:** after the recycle, the terminal is up on a client's account, or up but
  `connected=False`. The escalation logs `ipc_fault_recycled` at INFO, and the monitor's next
  probe reads `already_authorized` and sends no credential. The heal's purpose, the house account's
  session, is not restored, and nothing says so. The capture already compares
  `session_server_matches_env` BEFORE the recycle but does nothing equivalent AFTER it.
- **Fix:** after a relaunch that answers, read `terminal_info().connected` and compare
  `account_info().login == env login` as a boolean only, never the number, in the same way the
  capture handles the server. Map "wrong account" or "not connected" to a distinct kind at WARNING.

### SFH-08: the validate path's MT5_TERMINAL_UNRESPONSIVE arm logs a shared-terminal outage at WARNING

- **Where:** `routers/exchange.py::_validate_mt5_key_probe`, the `is_ipc_transport_fault(e)`
  arm (`logger.warning("validate_key: MT5 terminal IPC transport fault (code=%s)")`).
- **What:** the same diff raises the trade-permission-off arm to ERROR because it means *"THE
  SHARED TERMINAL SERVING EVERY CLIENT"* is broken. An IPC-wedged terminal is the same class, with
  the same reach, and the user-facing copy says *"This needs an operator"*. Nothing notifies an
  operator. The line is WARNING, so it never becomes a Sentry event, and the validate path does not
  trigger the heal. A user hitting this during the 4-day window would have produced log lines only.
- **Fix:** log at ERROR (codes only, as now), matching the D-15 arm's reasoning. Alternatively,
  make the arm's docstring cite the monitor/escalation as the one alarm and state that it is.

## INFO

### SFH-09: the remote source records a refused open or terminate as a count, with no reason

`_REMOTE_TERMINAL_RECYCLE_SRC`: `if not handle: continue` and a false `TerminateProcess` add
nothing but a smaller `terminated`. Returning `ctypes.get_last_error()` for each refusal would
separate "access denied" from "process already gone" on the first live run, which D-05 names as
the measurement that closes its caveat. The source stays a committed literal; only its return
dict grows.

### SFH-10: a stale default figure in the cadence derivation

`mt5_session_monitor.py` cadence comment: *"the shipped defaults (600 / 2 / ~35) leave ~560 s of
headroom"*. The budget default is now 8 × 30 + 10 = 250 s, so the headroom is about 348 s. This
has no effect on behaviour, because the floor is derived from the ceilings, but it is a restated
number that has drifted.
