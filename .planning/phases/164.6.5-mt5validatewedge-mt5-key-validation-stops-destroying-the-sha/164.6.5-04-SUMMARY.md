## Accomplishments

- **A distinct, honest, non-recoverable wizard error code.** `KEY_MT5_TERMINAL_UNRESPONSIVE`
  states what is true — our terminal, not the user's key/password/broker server — never
  instructs a retry, and never promises a self-heal D-05 (a separate, concurrent plan) may not
  have shipped. `actions` carries no member of `RECOVERABLE_ACTIONS`, so the Retry control is
  suppressed structurally by `buildEnvelope`'s derivation, never by a component-level condition.
- **The Python side mints the wire code at the exact site the measured incident points to.** A
  new narrow predicate `is_ipc_transport_fault` (beside, not inside, `classify_mt5_login_error`)
  reuses `_IPC_TRANSPORT_CODES` and answers one question from the CODE alone. The new arm sits
  between the wrong-server branch and the generic transient tail in `_validate_mt5_key_probe`'s
  `Mt5ClientError` handler, raises `service_error(500, "MT5_TERMINAL_UNRESPONSIVE",
  dependency="mt5-gateway", retryable=False, ...)`, logs the scrubbed code only, and writes a new
  `terminal_unresponsive` trace outcome distinct from `transient`.
  `classify_mt5_login_error`'s own three-way contract is untouched.
  ⚠️ **This changes behavior for BOTH `-10004` and `-10005`**, not `-10005` alone — the predicate
  reuses the whole `_IPC_TRANSPORT_CODES` tuple, matching the plan's own instruction and that
  tuple's own docstring, which treats both as one infra-fault class with one remedy.
- **The two vocabularies agree member for member.** `VENUE_WIRE_CODE_TO_VERDICT` gained a row
  mapping `MT5_TERMINAL_UNRESPONSIVE` to the new wizard code at status 500 — written down beside
  the Python raise site's own status as a cross-reference comment so the two cannot silently
  disagree. `seam-venue-vocabulary.invariant.test.ts`'s arrival gate (`EXPECTED_EMITTED_CODES`)
  and `wizardErrors.invariant.test.ts`'s `[153.7 review W-153.7-1]` derive guard both confirmed
  RED before the fix and GREEN after, on both of `KNOWN_CREATE_WITH_KEY_CODES` and
  `KNOWN_ADD_KEY_CODES` — the two classifier-reachable rosters, verified by the guard itself
  rather than assumed by symmetry. `KNOWN_FINALIZE_CODES` and `KNOWN_SET_MEMBERS_CODES` correctly
  do NOT admit it (neither route reaches `classifyKeyValidationError` for this arm; the CLASSIFIER_STEPS
  derive guard only names the two that do).
- **The honest transport arm is proven intact, not merely left alone.** A new parametrized
  Python router test (`test_mt5_non_ipc_client_error_is_unchanged_the_d12_fence`) and a TypeScript
  unit test both assert, as EXECUTING assertions, that a non-IPC `Mt5ClientError` (and
  `KEY_NETWORK_TIMEOUT`'s copy) are byte-unchanged — this is the D-12 fence made falsifiable.
- **One pre-existing test's fixture necessarily moved.**
  `test_c5_mt5_transient_client_error_carries_a_machine_code` used `-10004` as its "transient"
  example; under this plan's change that code now leaves the venue-transient class. Re-cut to a
  non-IPC code (still the population C5 covers), and a new parametrized
  `test_c5b_ipc_transport_codes_leave_the_venue_transient_class` proves the class boundary
  explicitly at the live route.
- **Every new assertion was proven able to fail.** Four independent neuter passes against
  production code (the predicate forced `False`, forced `True`, the log line widened to include a
  submitted credential, and — in the TypeScript commit — the copy's `actions`, title, cause text,
  and verdict-row target each temporarily corrupted one at a time), each observed RED, each
  restored from a `cp` byte backup verified with `cmp`. See "Deviations from Plan" below for the
  full list with the exact RED observed.
