## Summary

The recycle verb is sound as a constant. `_REMOTE_TERMINAL_RECYCLE_SRC` is a plain
literal with no interpolation and takes no parameter. It is fenced by `_assert_live`
and crosses through `_guarded_read`. The one run-time value crosses as an int. A
malformed or absent transport raises and never reports success. Nothing in the diff
puts a credential, account number or broker server name on a log line: the evidence
line records the server only as an equality verdict, and the escalation detail
carries integer counts and codes. The offline suites are green at HEAD:
`pytest tests/test_mt5_relogin.py tests/test_mt5_client_contract.py tests/test_mt5_session_episodes.py -q`
gave `434 passed, 1 warning`.

The defects are in the **escalation's state machine** and in one decision the phase
records as in scope but never implemented:

- **CR-01.** The once-per-run gate is only re-armed by a first-probe reading. A
  recycle that WORKS does not re-arm it. So a terminal that re-wedges before the
  next monitor tick is never recycled again, and a human is needed. Avoiding that
  human is the goal of the phase.
- **CR-02.** D-17 says `KEY_MT5_TERMINAL_UNRESPONSIVE` joins the rotate-secret
  dialog's roster and is in scope for this phase. It is not in the roster, so the
  rotate dialog renders `UNKNOWN` with the Retry control that D-08 names as the
  harmful action.

**On the budget question.** Under the module's own counting rule, 8 is the minimum
for the path as it is written. That rule counts terminal-touching calls and treats
bridge-served calls as free. It is also the smallest value that keeps
`test_the_budget_covers_the_ESCALATION_path_too` green. But the same module counts
`last_error()`, a bridge-local call, at a full 30 s. It also does not count the
recycle's two extra rpyc crossings (`execute` and the namespace lookup). Counted
consistently, the path is 10 crossings: 10 x 30 + 10 = 310 s, which is over the
300 s ceiling. See WR-04.

**Known and not re-reported, as the brief asked:**
- the stale "algo trading re-cleared on every account change" wording in the
  `Mt5Client.terminal_info` docstring (`services/mt5_client.py`)
- the `Mt5GatewayMisconfigured` comment in `services/job_worker.py`
- the operator sentence in `scripts/prod-prober/arms/mt5.mjs`

IN-04 touches that last file only where it differs from the known item: the
"2.0 s" figure against the spike's own measurements.

## Critical Issues

### CR-01: A successful recycle never re-arms the escalation gate, so the next wedge is never healed

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault`,
`_heal_blocking`; `analytics-service/services/mt5_session_episodes.py` —
`claim_ipc_fault_escalation` / `rearm_ipc_fault_escalation`

**Issue:** `claim_ipc_fault_escalation()` disarms the gate on the first `-10005`.
The only call sites of `rearm_ipc_fault_escalation()` are:
- `_escalate_ipc_fault`'s non-reachable-code arm
- `_heal_blocking`'s `-6` arm
- `_heal_blocking`'s already-authorized arm

All three are FIRST-PROBE readings of a later tick. A recycle whose relaunch probe
reads `authorized=True` (`KIND_IPC_FAULT_RECYCLED`) or `-6`
(`KIND_IPC_FAULT_RECYCLED_NO_ACCOUNT`) has itself MEASURED the terminal answering
in a different class, but the gate stays disarmed.

**Failure scenario:**
1. At T+0 a client validation wedges the terminal (Cause B, an account switch —
   criterion 1 is still open, so this can recur).
2. The monitor tick at T+10m reads `-10005`. The gate is claimed, the recycle
   runs, and the relaunch reads authorized.
3. At T+12m the same client retries, or another client validates. The switch
   wedges the terminal again.
4. Every later tick reads `-10005` and is debounced: "is NOT repeated", logged at
   INFO.

No reading of a different class ever arrives, because the terminal stays wedged.
The gate never re-arms until the analytics service is redeployed. That is the
1h39m manual outage again, with an INFO line each tick saying the recovery was
deliberately withheld.

The same trap closes after `KIND_IPC_FAULT_RECYCLED_STILL_FAULTED` when the
terminal then comes up by itself (see WR-02) and re-wedges before a tick sees it
healthy.

`test_ESCALATION_re_arms_after_a_reading_of_a_different_class` only proves re-arm
through an intermediate authorized TICK, which is exactly what this scenario lacks.

**Fix:** Treat the relaunch probe as the reading it is. Re-arm when the escalation
proves the terminal answered:
```python
# in _escalate_ipc_fault, after kind is computed
if kind in (KIND_IPC_FAULT_RECYCLED, KIND_IPC_FAULT_RECYCLED_NO_ACCOUNT):
    # the relaunch probe MEASURED the terminal answering: this run is over
    rearm_ipc_fault_escalation()
```
Bound the cost separately if you need to, for example at most N recycles per rolling
hour, rather than by a gate that only a first-probe reading can open. Add a gate
test: wedge, recycle to authorized, wedge on the very next tick, and assert 2
recycles.

## Warnings

### WR-01: The gate is claimed before any work, so an abandoned escalation spends the one attempt with no recycle

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault`
(`claim_ipc_fault_escalation()` precedes `_capture_wedge_evidence` and
`client.recycle_terminal_process()`)

**Issue:** `Mt5SessionAbandoned` is re-raised from two places:
- the capture
- the recycle verb's first statement (`_assert_live("terminal_recycle")`), which
  raises before anything crosses

Either way the gate is already disarmed. Abandonment happens when the heal's
`wait_for` has fired and the lease has bumped the epoch. That is reachable whenever
the path overruns its budget, and WR-04 shows the budget does not cover the
consistently-counted path.

**Failure scenario:** The first escalation times out during the capture, or before
the recycle crosses. No process is terminated. The gate is disarmed. Every later
`-10005` is debounced, and the terminal stays wedged until a redeploy.

**Fix:** Re-arm on the abandoned arm when nothing crossed. The simplest form is to
move the claim to just before `client.recycle_terminal_process()`, and to re-arm if
that call raises `Mt5SessionAbandoned` from its fence (stage `terminal_recycle`)
rather than from the relaunch:
```python
except Mt5SessionAbandoned as exc:
    if getattr(exc, "stage", None) == "terminal_recycle":  # refused before crossing
        rearm_ipc_fault_escalation()
    raise
```

### WR-02: A working recycle is likely logged as `ipc_fault_recycled_still_faulted` at ERROR ("a human is needed")

**File:** `analytics-service/services/mt5_client.py` — `Mt5Client.recycle_terminal_process`
(the relaunch step); `analytics-service/services/mt5_relogin.py` —
`_classify_recycle_verdict`, `_escalate_ipc_fault` severity ladder

**Issue:** The relaunch is one `assert_session_authorized()`, bounded by
`MT5_INITIALIZE_TIMEOUT_MS` = 20 s. Plan 02's own spike measured a cold relaunch
reaching "logged in" 86 s after the kill (run 1), and the terminal reappearing
roughly 25 s after the kill. So on the evidence this phase holds, the relaunch probe
will usually time out while the terminal is still coming up.

It then reads an IPC code, is classified `KIND_IPC_FAULT_RECYCLED_STILL_FAULTED`,
and is logged at ERROR with the comment "a human is needed and no second automatic
attempt will come this run". Minutes later the terminal is authorized, and the next
tick reads `already_authorized`. Nothing links the two lines. That trains the
operator to ignore the ERROR, which is the WR-01-style severity inversion the
module fought, arriving from the other side. The plan-02 SUMMARY's "Issuing it in
the verb bounds the delay" bounds the WAIT; it does not make the relaunch succeed.

**Failure scenario:** The first live `-10005` after deploy recycles successfully. The
log says `ipc_fault_recycled_still_faulted` at ERROR, the operator is paged or goes
to VNC, and finds the terminal already healthy.

**Fix:** Handle a relaunch that has not answered yet in one of two ways:
- Poll the relaunch probe a bounded number of times inside the budget. Each poll
  costs round-trips, so re-derive the count.
- Or classify an IPC-coded relaunch as a distinct `recycled_relaunch_pending`
  (WARNING), and let the next tick's first probe deliver the verdict.

Neither should claim "human needed" before a later reading confirms it.

### WR-03: The verdict classifier ignores `matched` and `terminated`, so a recycle that ended nothing reads as a recycle

**File:** `analytics-service/services/mt5_relogin.py` — `_classify_recycle_verdict`

**Issue:** The classifier reads only `authorized` and `relaunch_code`. The remote
source deliberately COUNTS processes it could not open or terminate: `matched`
greater than 0 with `terminated` equal to 0 when `OpenProcess` or
`TerminateProcess` fails. It also returns `matched=0` when no `terminal64.exe`
exists. In all of these cases nothing was recycled, yet:
- with `authorized=True` the kind is `ipc_fault_recycled`, which claims the recycle
  healed it
- with an IPC code the kind is `ipc_fault_recycled_still_faulted`, which claims a
  recycle ran and did not help

**Failure scenario:** Wine denies `PROCESS_TERMINATE` on the terminal. The verdict is
`matched=1 terminated=0`. The relaunch `initialize()` attaches to the SAME wedged
process and reads `-10005`. The kind says the recycle ran and failed. The truth is
that the recycle never happened, and the gate is now disarmed (see CR-01), so it
never will.

**Fix:**
```python
if int(verdict.get("terminated") or 0) == 0:
    return KIND_IPC_FAULT_RECYCLE_FAILED  # or a new "recycle_ended_nothing" kind
```
Add gates for `matched=0` and for `matched=1, terminated=0`.

### WR-04: The budget arithmetic under-counts the recycle's rpyc crossings; honestly counted, the path exceeds the 300 s ceiling

**File:** `analytics-service/services/mt5_relogin.py` — `_MT5_RELOGIN_ROUND_TRIPS`
table; `analytics-service/services/mt5_client.py` —
`recycle_terminal_process._remote_call`; `analytics-service/tests/test_mt5_relogin.py`
— `_FakeRpycConn.execute` / `namespace`, `test_the_budget_covers_the_ESCALATION_path_too`

**Issue:** `_remote_call` makes THREE rpyc requests, each bounded only by
`sync_request_timeout` (30 s):
- `conn.execute(SRC)`
- `conn.namespace[FN]` (a netref `__getitem__`)
- the call itself

The table counts one. The double's `execute` and `namespace` append nothing to
`round_trips`, so the gate that is supposed to "count the path, never restate it"
counts 8 because the double under-reports.

The table's justification is that bridge-served calls are not terminal
round-trips. The same table counts `last_error()` at 30 s, and that is a
bridge-local read of the package's stored error, not a terminal call. The module's
own WR-03 lineage (D-32 EVIDENCE §1b, "a failed attempt paying a SECOND full 30 s
here") is the reason bridge crossings are counted. Counted consistently, the
worst path is 10 crossings: 10 x 30 + 10 = 310 s, over `_MT5_RELOGIN_BUDGET_CEILING_S`
= 300. Per the module's own record, that re-opens WR-03: the `wait_for` fires
mid-recycle, which also feeds WR-01.

**Answer to "is 8 the minimum?":** yes under the stated rule, no under the rule the
rest of the module applies.

**Fix:** Pick one of these:
- (a) Drop the `account_info()` read, which saves 2 and which the plan-05
  SUMMARY already offers. The honest count is then 8, at 250 s.
- (b) Merge the three crossings into one. For example, have the executed source
  also call the function (`conn.execute(SRC + "\n_qz_result = ...")`, then one
  read). ⚠️ This changes the committed-constant shape the tests pin, so it is a
  plan-level decision.

Either way, make the double record `execute` and the namespace lookup as round
trips so the gate measures what production does.

### WR-05: The new user copy states permanence for faults the phase itself makes transient, and for `-10004`

**File:** `src/lib/wizardErrors.ts` — `WIZARD_ERROR_COPY.KEY_MT5_TERMINAL_UNRESPONSIVE`;
`analytics-service/routers/exchange.py` — `_validate_mt5_key_probe`, the
`is_ipc_transport_fault` arm (detail "This needs an operator, not a retry.");
`analytics-service/services/mt5_validation.py` — `is_ipc_transport_fault`

**Issue:** The copy says *"it will not clear on a retry"* and *"nothing you do from
this screen can clear it"*. The arm fires for both `-10004` and `-10005`.

1. `-10004` is "bridge NOT ATTACHED". The prober's own `mt5-no-ipc` remedy calls it
   the gateway being "down or mid-redeploy", and says a redeploy fixes it.
2. This phase's own recycle creates a window of up to about 90 s (see WR-02) in
   which every validate reads `-10004` or `-10005` while the terminal relaunches.
3. D-05 has now shipped a heal that clears `-10005` within one monitor tick of 10
   minutes.

So a user who validates during a gateway redeploy, or during our own recycle, is
told nothing will help and to contact support. A retry a minute later would have
succeeded. That is the mirror of the `KEY_NETWORK_TIMEOUT` lie D-12 set out to
remove.

**Fix:** Word the copy as not-now-and-ours without asserting permanence. For
example: "It usually recovers on its own within a few minutes; if it is still
failing later, tell us." Update the router `detail` to match. Also consider minting
only on `-10005` and leaving `-10004` on the transient arm, which is the split the
heal already draws with `_RECYCLE_REACHABLE_IPC_CODES`.

### WR-08: A non-measuring `0` reading re-arms the gate, so a flaky bridge defeats the debounce

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault`
(`if code not in _RECYCLE_REACHABLE_IPC_CODES: rearm_ipc_fault_escalation()`)

**Issue:** Code `0` is the IN-02 sentinel. It means `last_error()` itself failed or
answered malformed, and in `_heal_blocking`'s own words it "measured nothing about
the session". The plan-05 SUMMARY states the rule that "non-measuring exits …
neither arm nor disarm", but the code re-arms on `0`. It re-arms on `-10003` too.

**Failure scenario:** During a wedge the bridge also intermittently times out
`last_error()`. The readings run `-10005`, `0`, `-10005`, `0`, and the terminal is
recycled every other tick (every 20 minutes). The debounce exists to prevent that
periodic outage of the shared terminal.

**Fix:** Re-arm only on readings that positively measured a different state:
authorized, `-6`, and arguably `-10004`. Leave `0` neutral, matching the stated
rule, and add a `-10005, 0, -10005` gate that asserts a single recycle.

(`headers.get(CORRELATION_HEADER) ?? mintWizardId()`)
**Issue:** `Headers.get` returns `""`, not `null`, for an empty value. So `""` is
sent and reported to `onCorrelationId`. The server then falls back to a fresh UUID,
and the displayed id is empty. No current caller does this.
**Fix:** Use `headers.get(CORRELATION_HEADER) || mintWizardId()`.
