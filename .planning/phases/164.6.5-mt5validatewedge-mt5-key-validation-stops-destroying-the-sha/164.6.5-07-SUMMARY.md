## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Stale-closure bug in the first CsvSubmitStep/CsvUploadStep draft, caught before commit**
- **Found during:** Task 3, writing the gate tests for `CsvSubmitStep.upstream-arm.test.tsx`
- **Issue:** The initial implementation captured the per-request id into a `useState` and read that state variable synchronously, later in the SAME async `handleSubmit`/`handleUpload` closure that had just called the setter — React does not make a `setState` update visible to the closure that called it until the next render, so the read silently saw the STALE (null, pre-attempt) value rather than the id `onCorrelationId` had just written.
- **Fix:** Replaced the `useState` pair with a plain `let requestCorrelationId: string | null = null;` local variable, assigned directly inside `onCorrelationId`'s callback. No React re-render is needed because `surfacedId` is computed synchronously within the same function, later in the same call.
- **Files modified:** `src/app/(dashboard)/strategies/new/wizard/steps/CsvSubmitStep.tsx`, `src/app/(dashboard)/strategies/new/wizard/steps/CsvUploadStep.tsx`
- **Verification:** The two new gate tests per file passed after the fix; the neuter-observe-restore proof (reverting the preference back to `correlationId` alone) reproduced RED on exactly those tests, confirming the fix is what makes them pass, not an unrelated pre-existing pass.
- **Committed in:** `34a1750b` (the bug never reached an earlier commit — found and fixed within Task 3's single commit)

**2. [Rule 3 - Blocking, worked around not fixed] `gsd_run check tdd-red-evidence` cannot classify this repo's vitest TAP output**
- **Found during:** Task 1, attempting to persist and verify the RED-phase evidence record per the TDD gate's stated mechanism
- **Issue:** The tool's TAP parser (`parseNodeTestSummary`) expects `node --test`'s `# tests N` / `# pass N` / `# fail N` summary footer, which vitest's `--reporter=tap` does not emit (confirmed absent by direct inspection of the raw output), and its failing-test-name regex (`^(?:not )?ok \d+ - (.+)$`) only matches un-indented lines, never vitest's indented nested subtests. Run against a genuinely RED test file, it returned `INVALID_RED` with reason `zero_tests_discovered` — a false negative, not a real classification of the RED phase's quality.
- **Fix (workaround, not a fix to the tool):** RED evidence was established by direct inspection — running the full test file and confirming each new-behavior test failed on the SPECIFIC intended assertion (never an import, syntax, or fixture-crash error) — combined with the neuter-observe-restore + `cp`/`cmp` "Proven-Able-to-Fail" ledger convention sibling plan `164.6.5-04` already used in this same phase for the identical purpose.
- **Files modified:** None (this is a process/tooling note, not a code change). Not a fix to `gsd-core`'s tooling — out of scope for this plan.
- **Verification:** Documented and reproduced (see the `check tdd-red-evidence` invocation and its `zero_tests_discovered` output during Task 1); logged to `.planning/WINDOWS.md` as a `deviation` entry so the gap stays visible for future TDD plans in this (vitest-based) repo.
