## Critical Issues

### CR-01: A wedge that recurs every tick is recycled every tick with no cap, and the persistence alarm is reset each time, so it never reaches ERROR

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault` (the `else:` arm's
`rearm_ipc_fault_escalation()` added for round-1 CR-01, and the level ladder's
`KIND_IPC_FAULT_RECYCLED -> logging.INFO`); `analytics-service/services/mt5_session_episodes.py` —
`rearm_ipc_fault_escalation` (now also clears `_IPC_FAULT_RUN_SINCE` and `_IPC_FAULT_LAST_ALARM_AT`)

**Issue:** Round 1's CR-01 fix re-arms the gate when the relaunch answered. In the same round,
SFH-03 made `rearm_ipc_fault_escalation` the one place that ENDS the persistence alarm's run:

```python
_IPC_FAULT_RUN_SINCE = None
_IPC_FAULT_LAST_ALARM_AT = None
```

Composed, one tick of a recurring wedge goes like this:

1. `note_ipc_fault_reading(now)` starts a fresh run at `now`, because the previous tick's
   re-arm cleared it.
2. The gate is armed, so the recycle runs.
3. The relaunch answers, so the kind is `ipc_fault_recycled`, logged at INFO. It is WARNING only
   if the post-relaunch reads degrade.
4. The `else:` arm re-arms, which clears both alarm stamps.

`ipc_fault_alarm_due` therefore never sees a run older than one tick, and the ERROR branches in
`_escalate_ipc_fault` are unreachable for this pattern. Each tick emits only these lines:

- the pre-recycle evidence (WARNING)
- the verb's counts line (WARNING)
- the escalation line (INFO)
- `not_healed:ipc_fault` (WARNING)

None of them is a Sentry event. `escalation_kind` is not persisted either (`HealOutcome` only;
`mt5_session_episodes` says "never an episode row"), so no durable record accumulates.

**Failure scenario.** This is Cause B as the runbook describes it: a client validation's account
switch wedges the terminal, and criterion 1 is still open.

1. Validations arrive faster than the 600 s cadence.
2. Every tick reads `-10005` and kills the shared terminal serving every client.
3. The terminal relaunches, "healed", at INFO, possibly on another account.
4. The next validation wedges it again.

This repeats indefinitely at up to 6 recycles an hour. The operator's only loud signal is the
per-validate page from WR-06, and that fires only for validations that land while it is wedged.
The fix report's "Recorded rather than done" says *"If the live logs show wedge -> recycle ->
wedge every tick, that pattern is the signal for Cause B"*. Nothing detects or raises that
pattern, so the recorded decision rests on a signal that is never emitted.

This is the fast-loop question the brief asked, and the answer is yes.

**Fix:** Keep the round-1 CR-01 re-arm, which is right for the ACTION. Stop it from erasing the
ALARM's memory of recent recycles. Two parts:

1. Record recycle timestamps in a small rolling window, independent of the run. Re-raise at ERROR
   when the window holds more than one recycle per `_IPC_FAULT_ALARM_INTERVAL_S`, for example:

   ```python
   # mt5_session_episodes
   _RECENT_RECYCLES: deque[float] = deque(maxlen=16)

   def note_recycle(now: float, window_s: float) -> int:
       _RECENT_RECYCLES.append(now)
       while _RECENT_RECYCLES and now - _RECENT_RECYCLES[0] > window_s:
           _RECENT_RECYCLES.popleft()
       return len(_RECENT_RECYCLES)

   # _escalate_ipc_fault, right after claim_ipc_fault_escalation(answers)
   recent = note_recycle(_clock(), _IPC_FAULT_ALARM_INTERVAL_S)
   if recent >= 2:
       level = max(level, logging.ERROR)  # "N recycles in the last hour: the wedge RECURS"
   ```

   This keeps "each recycle followed a measured recovery", with no cap on the remedy, while
   making the recurrence loud.
2. Decide explicitly whether a cap is wanted. Record that decision in CONTEXT, not only in the
   fix report.

Add a gate: three consecutive ticks of wedge -> recycle -> authorized must produce at least one
ERROR line. Neuter the window and observe RED.

## Warnings

### WR-01: A recycle the budget cannot afford returns before the persistence alarm, so a mis-sized `MT5_RELOGIN_BUDGET_S` silences the wedge again

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault`, the
`if not _affordable(deadline, _ESCALATION_RESERVE_CROSSINGS):` arm (`logger.warning(... NOT
attempted ...)` then `return None`)

**Issue:** That arm returns after the alarm bookkeeping (`note_ipc_fault_reading`) but before
either alarm branch, which sit only in the "not reachable" and "debounced" arms. So when the
recycle is never affordable, a persisting `-10005` never reaches ERROR, however long it lasts.

It is never affordable whenever `MT5_RELOGIN_BUDGET_S` sits below roughly
first-probe time + capture time + 5 x 30 s. Round 1's SFH-06 named that exact case: a Railway
override still sized for the old 160 s path. Realistically the first probe on a wedged terminal
spends the 20 s IPC timeout. At 160 s the check then needs 150 s left and finds about 138 s, on
every tick.

The result is the pre-phase four-day shape: a WARNING per tick, with no recycle and no ERROR.
The fixer recorded that the Railway variable was not checked.

**Fix:** In that arm, apply the same `ipc_fault_alarm_due(..., attempted=False)` /
`mark_ipc_fault_alarm` pair the other two arms use. Log it at ERROR on the first due reading and
name the variable, because this is a server misconfiguration that is preventing a recovery. Add a
test: set `MT5_RELOGIN_BUDGET_S=160`, run ticks of `-10005` over more than an hour, and assert at
least one ERROR.

### WR-02: The job-path answer re-arms the gate but does not end the alarm's run, so later alarms report a false elapsed time and a transient `-10004` can page on its first reading

**File:** `analytics-service/services/mt5_session_episodes.py` — `ipc_fault_escalation_armed`
(re-arms on a moved answer count and clears `_IPC_FAULT_ESCALATION_CLAIMED_AT_ANSWER`, but not
`_IPC_FAULT_RUN_SINCE` / `_IPC_FAULT_LAST_ALARM_AT`), versus `rearm_ipc_fault_escalation` (clears
all four)

**Issue:** SFH-05's answer count is the "the terminal answered" signal for the gate. The alarm's
run is ended only by `rearm_ipc_fault_escalation`, which is called only from the heal's own
probes. If the recovery was seen only by the job path, which is the SFH-05 premise (every tick a
busy skip), the run and the last-alarm stamp survive into the NEXT wedge. Two outcomes follow:

1. **False elapsed time.** A new `-10005` hours later recycles (the count moved, so the gate is
   armed). If it does not cure the wedge, the hourly alarm reads "PERSISTS 360 min into this
   run" for a wedge that is 60 min old.
2. **A transient `-10004` pages at once.** Take a gateway redeploy, a `-10004` shorter than an
   hour, which round 1 explicitly promised "stays quiet". It reaches the `attempted=False` branch
   with `_IPC_FAULT_LAST_ALARM_AT` still set from the old run. Once that stamp is an hour old,
   `ipc_fault_alarm_due` returns True on the FIRST reading, and the operator is told nothing
   automatic will clear a fault a redeploy is already clearing.

A related case is the WR-01 fence re-arm (`exc.stage == _RECYCLE_FENCE_STAGE`). It runs in the
zombie thread after the `wait_for` fired and goes through the same `rearm_ipc_fault_escalation`,
so a refusal that measured nothing ENDS the alarm run. That is the opposite error.
"Undo the claim" and "the terminal answered" are two different events that share one function.

**Fix:** Split the two events:

- `restore_ipc_fault_attempt()` undoes the claim only. The fence refusal and the WR-04 "not
  affordable" return use it.
- `end_ipc_fault_run()` handles the terminal being measured answering. It clears the claim AND
  both alarm stamps.

Have `ipc_fault_escalation_armed` call `end_ipc_fault_run()` when the answer count has moved.
Gates:

- `-10005`, then recycle `still_faulted`, then a job answer, then `-10004`: that `-10004` must
  not ERROR on its first reading.
- A fence refusal must not clear `_IPC_FAULT_RUN_SINCE`.

### WR-03: The WR-04 equality gate still under-counts crossings: a successful `terminal_info()` / `account_info()` is charged one crossing but materializes per field

**File:** `analytics-service/services/mt5_relogin.py` — `_CAPTURE_READ_CROSSINGS`, the
`_affordable(deadline, _CAPTURE_READ_CROSSINGS)` gates in `_read_post_relaunch_state`;
`analytics-service/services/mt5_client.py` — `_materialize` (and the comment above
`_REMOTE_MATERIALIZE_FN`: "`_materialize` costs ONE ROUND-TRIP PER FIELD");
`analytics-service/tests/test_mt5_relogin.py` — `test_the_budget_covers_the_ESCALATION_path_too`
(the `terminal_info_answers` shape feeds a LOCAL namedtuple)

**Issue:** Round 1's WR-04 set the rule that the unit is the rpyc crossing, each bounded by
`sync_request_timeout`, and that the double must record what production does. A successful
`terminal_info()` / `account_info()` returns a netref namedtuple. `_materialize` then crosses for
each of these:

- the `_asdict` lookup
- the call
- `.items()`
- each field's `next()`

That is dozens of crossings, per this module's own MT5DEAL-01 measurement. The double hands back
a local namedtuple, so it records one. The gate asserts EQUALITY "with every crossing at its full
ceiling", which is not true of the answering shapes.

The practical consequence falls on the post-relaunch reads. `_read_post_relaunch_state` gates
each read on 60 s left and reserves nothing after them. So a slow bridge can fire the `wait_for`
AFTER the recycle and relaunch, during materialization. Then:

- The escalation's own verdict line is never emitted.
- Round 1's CR-01 `else:` re-arm never runs, because the zombie's next fenced touch raises
  `Mt5SessionAbandoned` with a stage other than the fence.
- The operator gets only the generic "ABANDONED at the budget" line.

The count-based re-arm limits the gate damage, because the relaunch probe answered.

**Fix:** Pick one of these:

- Materialize these two reads bridge-side, as `_materialize_rows` already does for deals, so
  each is a bounded number of crossings.
- Or charge them honestly: a named `_ANSWERING_READ_CROSSINGS` equal to the field count plus 3,
  used in `_affordable`.

Either way, make the double return a netref-like object that records each crossing, and re-state
the equality gate over that.

### WR-04: SFH-07 is only half fixed: a relaunch on the wrong account or disconnected keeps the kind `ipc_fault_recycled`

**File:** `analytics-service/services/mt5_relogin.py` — `_escalate_ipc_fault` (`if degraded:
level = max(level, logging.WARNING)`; `kind` is unchanged)

**Issue:** SFH-07 asked that "wrong account" or "not connected" map to a DISTINCT KIND. The fix
raised the line's level to WARNING and kept `kind == KIND_IPC_FAULT_RECYCLED`. It also runs the
round-1 CR-01 re-arm, and it returns that kind as `HealOutcome.escalation_kind`. So every

The next tick's first probe then reads `already_authorized`, whichever account is up, so the heal

**Fix:** Add `KIND_IPC_FAULT_RECYCLED_DEGRADED`, or two kinds (`_other_account`, `_disconnected`).
Document them in the kinds block in `mt5_session_episodes`, and return them from
`_escalate_ipc_fault` when `degraded`. Pin the kind, not only the level, in the SFH-07 tests.

### WR-06: The remote recycle's runtime scales with the number of matched processes against one 30 s bound, and an overrun discards a terminate that landed

**File:** `analytics-service/services/mt5_client.py` — `_REMOTE_TERMINAL_RECYCLE_SRC` (per pid:
`file_version(pid)` + `TerminateProcess` + `WaitForSingleObject(handle, exit_wait_ms)`),
`_TERMINAL_EXIT_WAIT_MS = 5000`, `recycle_terminal_process._remote_call` under `_guarded_read`

**Issue:** The whole loop runs inside ONE rpyc request bounded by `sync_request_timeout` (30 s).
Each matched process can spend up to 5 s in the exit wait, plus a file-version read that round 1
added and that has never run under Wine. So six or more stray `terminal64.exe` processes can
overrun the bound, for example after repeated relaunch attempts or a duplicate launch (see
IN-01). Then:

- `_guarded_read` converts the timeout into `Mt5ClientError(0)`.
- The escalation logs `recycle_failed` ("whether the process was ended is not known").
- The SFH-06 counts line is never reached, because it is logged only after the JSON parses.

The terminates DID land, and the one piece of evidence round 1 added so an abandonment could not
lose them is lost by this route instead. IN-07 already records that the match is every
`terminal64.exe`.

**Fix:** Bound the loop's total wait, not only each wait. For example, pass a total budget and
shrink each `WaitForSingleObject` so the sum stays under about half of `sync_request_timeout`.
Or terminate every process first, then wait on all the handles once with
`WaitForMultipleObjects`. Pin it with an executed-source test using several processes whose
exit waits all time out, asserting that the modelled runtime stays under the rpyc bound.

## Info

### IN-01: The Win32 half of the remote source is exercised only against a faked `WinDLL`, so marshalling and Wine behaviour are unmeasured, including whether repeated relaunch polls can launch a second terminal

**File:** `analytics-service/services/mt5_client.py` — `_REMOTE_TERMINAL_RECYCLE_SRC`
(`file_version`, the `argtypes` blocks); `analytics-service/services/mt5_relogin.py` —
`_watch_relaunch`

**Issue:** The offline gates execute the literal with real `ctypes` structures. With a faked
`WinDLL`, though, assigning `argtypes` / `restype` is a no-op attribute write, so these are all
untested:

- argument conversion (LPWSTR buffer, `c_void_p` from a string buffer, `byref(DWORD)`)
- `restype` truncation
- Wine's answer to `PROCESS_QUERY_LIMITED_INFORMATION` and `GetFileVersionInfoW`

Separately, `_watch_relaunch` issues up to about four bare `initialize()` calls during the
terminal's startup window. The class docstring says the MetaTrader5 package's `initialize()`
LAUNCHES a terminal that is not running. Whether a poll during startup can launch a second
instance was not measured: the spike issued one `initialize()` after the kill. Round 1's fix
report already lists SFH-04 and SFH-09 for human verification.

**Fix:** Add both to the first-live-run checklist: the `file_versions` shape, the error ints, and
a process count after a watched relaunch.

### IN-02: `matched=0` with an answering relaunch is ERROR "needs a human", though it may be the strongest evidence of a real recovery

**File:** `analytics-service/services/mt5_relogin.py` — `_classify_recycle_verdict` (`if not
_recycle_landed(verdict): return KIND_IPC_FAULT_RECYCLE_NOT_LANDED`)

**Issue:** `matched=0` is ambiguous. Either:

- the image name did not match (the SFH-01 worry), or
- no `terminal64.exe` was running, and the verb's relaunch `initialize()` LAUNCHED a fresh one
  that answered.

The second is a genuine heal, yet it is logged at ERROR. Because `authorized is True`, it also
re-arms the gate through round 1's CR-01 `else:` arm. So a crashed-terminal recovery reads as a
broken verb.

**Fix:** Qualify `matched=0` plus an answering relaunch on the line, for example
`no_process_matched_relaunch_answered`, so the operator can tell the two apart. The level can
stay ERROR until the first live run shows which case it is.

### IN-03: `wizardPageLoadIdTag` trusts the repo's narrowed header type

**File:** `src/instrumentation.ts` — `wizardPageLoadIdTag(raw: string | undefined)` and the
`onRequestError` `request.headers: Record<string, string>` signature

**Issue:** Next's documented type for `request.headers` is `{ [key: string]: string | string[] }`
(`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/instrumentation.md`,
`dist/server/instrumentation/types.d.ts`: `NodeJS.Dict<string | string[]>`). An array value would
make `raw.trim()` throw inside the error hook and lose that capture. Node joins duplicate custom
headers into one string, so this does not happen today. The narrowed signature is what hides it.

**Fix:** Check `typeof raw === "string"` before trimming, or widen the parameter to Next's type.
