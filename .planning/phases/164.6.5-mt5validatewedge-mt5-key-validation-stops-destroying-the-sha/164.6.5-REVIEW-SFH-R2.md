## HIGH

### R2-SFH-01: a heal budget below the derived default skips the recycle at WARNING every tick, forever, and never reaches the persistence alarm

- **Where:** `mt5_relogin.py::_escalate_ipc_fault`, the
  `if not _affordable(deadline, _ESCALATION_RESERVE_CROSSINGS):` branch ("the terminal-process
  recycle was NOT attempted … The attempt is not spent; the next reading will try again").
- **What:** this is the only exit on the recycle-reachable (`-10005`) path that returns without
  consulting `ipc_fault_alarm_due`. The debounced branch and the never-escalated branch both
  check it; this one does not. "The next reading will try again" holds only if the next
  reading has more budget. It does not, because the budget comes from the same
  `MT5_RELOGIN_BUDGET_S` every tick. So the attempt is never spent and never made. Every tick
  logs:
  - the pre-recycle evidence WARNING
  - the "NOT attempted" WARNING
  - the `not_healed:ipc_fault` WARNING

  No ERROR is logged and no Sentry event is sent. This is the four-day outage shape SFH-03
  was meant to remove.
- **Why it is reachable, not theoretical:**
  - `_relogin_budget_s` accepts any value in `[_MT5_RELOGIN_BUDGET_FLOOR_S (30),
    _MT5_RELOGIN_BUDGET_CEILING_S (300)]` silently.
  - The reserve is `_ESCALATION_RESERVE_CROSSINGS` (5) × 30 s = 150 s, and it must still be left
    after the first probe and `terminal_info()`. On a real `-10005` those two readings each spend
    about the 20 s IPC timeout. So any override below roughly 190 s skips on every wedge.
  - Round 1's SFH-06 named exactly such an override: *"a Railway `MT5_RELOGIN_BUDGET_S`
    override still sized for the old 5-trip path (160 s)"*. It said that check "was not run
    here". REVIEW-FIX does not record it being run either.
  - The fix's own test, `test_WR04_a_recycle_the_budget_cannot_finish_is_never_started`, uses
    160. It asserts one WARNING and never asks what the next 47 ticks do.
- **Measured offline.** Setup: `MT5_RELOGIN_BUDGET_S=160`, a `-10005` wedge, 20 s per crossing,
  48 ten-minute ticks (8 h of fake time). Result: `recycles 0 errors 0 skips 48`.
- **Hidden:** a misconfigured knob (an operator fault) looks like a wedge the service is
  handling. The log line even guesses at the cause (`"… is set below its derived default?"`),
  but only at WARNING.
- **Fix, both halves:**
  1. **Route the skip through the alarm.** In that branch, call `ipc_fault_alarm_due(now,
     _IPC_FAULT_ALARM_INTERVAL_S, attempted=False)` and log an ERROR that names the knob and the
     elapsed time, as the never-escalated branch does. Better still, treat it as the
     configuration fault it is: `_log_configuration_fault_once` at ERROR naming
     `MT5_RELOGIN_BUDGET_S`, plus the hourly alarm.
  2. **Warn about the knob at read time.** Have `_relogin_budget_s` log once when the accepted
     value is below `_MT5_RELOGIN_ROUND_TRIPS * _MT5_REQUEST_TIMEOUT_S +
     _MT5_RELOGIN_CONNECT_SLACK_S`. That value can never run the escalation.

  Also pin a test: the 160 s scenario over more than one hour of ticks must produce an ERROR.
  Separately, an operator should read the Railway value of `MT5_RELOGIN_BUDGET_S` (read-only).
  This review did not.

## MEDIUM

### R2-SFH-02: the persistence alarm is an allowlist, so `-10001` / `-10002` and every other non-`-6` code stay at WARNING forever

- **Where:** `mt5_relogin.py::_IPC_FAULT_ALARM_CODES` is `_IPC_TRANSPORT_CODES` (`-10004`,
  `-10005`) plus `-10003`. `_escalate_ipc_fault` computes
  `since = note_ipc_fault_reading(now) if code in _IPC_FAULT_ALARM_CODES else None`.
- **What:** `_heal_blocking` labels every first-probe code other than `-6` as `KIND_IPC_FAULT`,
  so the verdict string reads `not_healed:ipc_fault:code=N` for all of them. But only three
  codes can ever reach ERROR. Two cases fall outside:
  - `services/mt5_validation.py` already lists `-10001` (RES_E_INTERNAL_FAIL_SEND) and `-10002`
    (RES_E_INTERNAL_FAIL_RECEIVE) as IPC-internal codes. For those, `since` is `None` and the
    branch returns before any alarm. The same holds for a persisting `-1` or any
    terminal-internal code.
  - A persisting `0` sentinel only feeds the blind-run escalation, which is WARNING.
- **Measured offline.** For each of `-10001`, `-10002` and `-1`: 48 ten-minute ticks, **0 ERROR
  records**.
- **Fix:** invert the set. Alarm the persistence of any first-probe code that is neither `-6`
  nor the `0` sentinel, and keep `_RECYCLE_REACHABLE_IPC_CODES` as the separate, narrow gate
  on the ACTION. Pin it with a parametrized persistence test over a code outside today's set.

### R2-SFH-03: a recovery seen only by the answered-count ends the recycle gate but not the persistence run, so the next IPC reading can alarm at once with a duration that spans the recovery

- **Where:** `mt5_session_episodes.py::ipc_fault_escalation_armed` re-arms the gate when
  `mt5_terminal_answer_count` has moved, but it leaves `_IPC_FAULT_RUN_SINCE` and
  `_IPC_FAULT_LAST_ALARM_AT` alone. Only `rearm_ipc_fault_escalation` clears them.
  `_escalate_ipc_fault`'s never-escalated branch (`-10003` / `-10004`) never reads the answered
  count at all.
- **Failure scenario:**
  1. A `-10004` blip at T0 starts a run.
  2. For the next two hours every monitor tick is a busy skip (`KIND_BUSY_SKIP`) while jobs
     succeed. Each job's `login()` bumps `_MT5_TERMINAL_ANSWERS`, but nothing that measures
     `authorized` reaches `rearm_ipc_fault_escalation`.
  3. A second, transient `-10004` then finds `now - _IPC_FAULT_RUN_SINCE >= 3600` and logs ERROR
     *"has PERSISTED for 120 min … an OPERATOR is needed"*. The terminal answered throughout.

  On the `-10005` side the gate re-arms correctly, but the stale `_IPC_FAULT_LAST_ALARM_AT` and
  `_IPC_FAULT_RUN_SINCE` carry over into the new run. Its elapsed minutes are then measured
  from the OLD run's start.
- **Why it matters here:** this is not a silent failure. It is a false loud one. Round 1's SFH-02
  reasoning applies: false alarms on this line train operators to dismiss it, and it is the one
  line that carries the persisting-wedge signal (see R2-SFH-05).
- **Fix:** add one check at the top of `_escalate_ipc_fault`, for every code: "has the terminal
  answered since the run started". Keep the answered count at the run's start, and when it has
  moved, call `rearm_ipc_fault_escalation()` (which ends both the gate and the run) before
  `note_ipc_fault_reading`. Add a test: `-10004`, then a job `login()`, then `-10004` more than
  one hour later gives no ERROR.

### R2-SFH-04: after the terminate has crossed, a parse failure or a remote raise is reported as "whether the process was ended is not known"; the counts are lost and nothing relaunches the terminal

- **Where:** `mt5_client.py::Mt5Client.recycle_terminal_process`. A single
  `try: … except (TypeError, ValueError, KeyError): raise Mt5ClientError(0, "… malformed verdict")`
  parses the essential counts (`matched` / `terminated` / `exited`) together with the round-1
  diagnostic fields (`open_errors`, `terminate_errors`, `file_versions`, `file_version_errors`).
  On the consuming side, `_escalate_ipc_fault`'s `except Exception` arm sets
  `KIND_IPC_FAULT_RECYCLE_FAILED`.
- **What:** by the time the payload is parsed, the remote function has already run to its
  `json.dumps`, so every `TerminateProcess` has happened. The new diagnostic fields come from
  Win32 code that has never run live. Any shape surprise in them fails the whole parse, and
  then three things follow:
  - **(a)** The SFH-06 WARNING counts line, which comes after the parse, is never logged.
  - **(b)** The verb's relaunch probe is never issued.
  - **(c)** The escalation logs `recycle_failed` with `exc_class=Mt5ClientError code=0`. The kind
    table glosses that as *"whether the process was ended is not known from here"*, although
    the process was ended.

  A remote raise after the first `TerminateProcess` (for example a `ctypes.ArgumentError` on
  a later pid) ends the same way through `_guarded_read`. The terminal then stays down until
  some later caller's bare `initialize()` launches it. The D-05 record measured about 4m45s for
  that in run 2. Nothing logs that the escalation left it down.
- **Fix:**
  1. Parse and log the three counts first, in their own `try`.
  2. Parse each diagnostic field tolerantly (an unparseable field becomes `"unparsed"` on the
     line, never a raise).
  3. In `_escalate_ipc_fault`'s `RECYCLE_FAILED` arm, take one budget-gated, credential-free
     detector reading (`_affordable(deadline, _DETECTOR_READING_CROSSINGS)`). That relaunches
     a terminal the failed verb may have ended, and lets the line say whether it answered.

  Pin it with a test where the remote payload carries a malformed `file_versions` entry: the
  counts must reach the log, and the kind must not claim the terminate is unknown.

### R2-SFH-05: whether the hourly re-raise reaches a human is unmeasured, because each re-raise is the same Sentry issue

- **Where:**
  - the three ERROR templates in `_escalate_ipc_fault`: "has PERSISTED for %d min", "PERSISTS %d
    min into this run", and the escalation line
  - `sentry_init.py`, whose default `LoggingIntegration` turns an ERROR record into an event
- **What:** each template is a fixed format string, so every hourly re-raise groups into ONE
  existing Sentry issue. A default issue alert ("a new issue is created") notifies on the first
  event only. An issue already marked ignored or archived, which is plausible for the
  escalation line after round 1's SFH-02 false alarms, notifies on none. So the SFH-03 fix
  guarantees events. It does not guarantee a notification. No alert rule lives in the repo
  (grep of `docs/` and `deploy/`: 0 hits).
- **Fix:** make this an operator check rather than a code change. Read the analytics project's
  alert rules (read-only) and confirm that one fires on event frequency for these messages,
  or add one. Record the result in the phase. Until that is done, "a persisting wedge now
  reaches an operator hourly" is a claim about Sentry configuration nobody has read.

## INFO

### R2-SFH-06: the remote source cannot tell a failed enumeration from "no terminal running"

`_REMOTE_TERMINAL_RECYCLE_SRC` has two paths that both produce `matched=0`:

- `Process32FirstW` returns false (for example, a `dwSize` the Wine kernel32 does not accept), so
  `more` is false and the loop never runs.
- The enumeration works and simply finds no `terminal64.exe`.

The outcome is loud (`recycle_not_landed` at ERROR). But it cannot be diagnosed, and on the
first live run this is the measurement SFH-09 set out to make. **Fix:** return an `enumerated`
count of all processes walked, and `ctypes.get_last_error()` when `Process32FirstW` fails,
both as ints.

### R2-SFH-07: `file_version`'s `except Exception` keeps only `-1`

In the remote loop, `except Exception: version, version_error = None, -1` drops which exception
it was. A missing `version.dll` under Wine (`OSError` from `WinDLL("version")`) and a ctypes
signature mismatch both read `-1` on every process. **Fix:** return the exception's class name.
It is a bridge-local Python class name, not remote free text. Otherwise, keep a distinct int
per stage.

### R2-SFH-08: the post-relaunch check degrades the level only on a definite mismatch

`_read_post_relaunch_state` sets `degraded` only for `connected=False` or a login mismatch.
These cases all leave `ipc_fault_recycled` at INFO:

- `post_relaunch=not_read` (budget)
- `terminal_info failed`
- `session_account_matches_env=not_captured`
- `session_server_matches_env=False`, which is never folded into `degraded`, although a login
  number is only unique per server

INFO is the level whose gloss is "nothing for anyone to do". **Fix:** WARNING when the check
could not be completed, and include a server mismatch in `degraded`.

### R2-SFH-09: `escalation_kind=None` covers three different outcomes

`_escalate_ipc_fault` returns `None` in three cases:

- the code is not recycle-reachable
- the attempt was debounced
- the budget skip (R2-SFH-01)

`HealOutcome.escalation_kind`'s docstring says `None` means *"this step never ran"*. In the
budget-skip case it ran and declined. The recorder does not read the field today, so this is
Info. A dedicated kind (for example `ipc_fault_recycle_skipped_budget`) would make R2-SFH-01
visible in any future consumer.

### R2-SFH-10: the rotate-secret route does not page `KEY_MT5_TERMINAL_UNRESPONSIVE`, and a comment says the Next-side key routes do

- `OUR_DEFECT_KEY_ERROR_CODES` is consulted only by `strategies/create-with-key` and
  `strategies/composite/add-key`. `keys/[id]/rotate-secret/route.ts` classifies the code and
  sends it only to `console.error`.
- Paging is not lost: the same probe's `logger.error` in `_validate_mt5_key_probe` is a Python
  Sentry event.
- But the comment beside that `logger.error` reads *"The Next-side key routes also page it"*,
  which is true for two of the three routes. **Fix:** narrow the sentence, or add the
  `OUR_DEFECT_KEY_ERROR_CODES` check to the rotate route's catch. Only the first fits a review
  fix; the second changes behaviour.

### R2-SFH-11: `wizard_page_load_id` records a malformed header the same way as an absent one

`wizardPageLoadIdTag` returns `null` for both. Not echoing a client-supplied value is correct.
A fixed sentinel such as `"malformed"` would separate "the client sent no header" (an old
bundle) from "the client sent a bad one" (a bug) without echoing anything. This is optional.
