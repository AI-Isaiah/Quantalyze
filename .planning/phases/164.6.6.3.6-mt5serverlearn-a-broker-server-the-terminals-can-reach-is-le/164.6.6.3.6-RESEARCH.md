## Summary

Plan 01 is a measurement, not a build. The research below gives the planner (1) the exact, evidence-backed shape of a one-off MetaTrader5 call on the validation gateway, (2) how the founder types credentials without argv or history exposure, (3) what MetaQuotes documents (and does not) for `host:port`, startup config and command-line keys, (4) how to read yes/no Journal evidence from inside the container, and (5) the safety envelope on the shared validation terminal, which changed since the 164.6.6 docs were written.

**Four findings change how plan 01 should be written.**
1. **The validation terminal is no longer "dark".** Since Phase 164.6.8 plan 06, the analytics session monitor runs a credential-free liveness probe against it on every tick (default 600 s), plus a scrub-row reader. `deploy/mt5-gateway/railway-gateway.md` step 11 still says it is dark; that text is stale. The probe does a bare `initialize()` (which RELAUNCHES a missing terminal as `terminal64.exe /portable`) under a bounded in-process lease the founder cannot hold. The founder-held gate therefore runs unlocked against a probe on a ~10 min cadence, and a scrub-owing validation would wreck it. There is no no-deploy pause; the mitigation is a quiet window plus timing each step between tick log lines.
2. **`mt5linux` 0.1.9 has a 30 s default rpyc sync timeout and `login()` interpolates the password into remote-evaluated source.** A naive one-off call times out at 30 s (before MT5's 45 s IPC ceiling) and would turn M1 into an artifact; a printed exception can carry the password. The protocol's script must set `sync_request_timeout` as `_default_connect` does, call `initialize()` before `login()` as `Mt5Client.login` does, and print only types, booleans and counts.
3. **MetaQuotes documents only `/login:`, `/config:`, `/profile:` and `/portable` as terminal command-line keys.** `/password` and `/server` are not documented (they come from one third-party README). The documented way to supply `Server=` is a `/config:` file whose `[Common]` section takes `Login`, `Password`, `Server` ("address and port number ... separated with a colon"). A custom config is read-only and replaces `common.ini`, so a terminal left running on it would lose the four `[Experts]` options the validation terminal needs (every validation would then be refused as undetermined). M3 must end with a kill and a credentialed house relaunch on the default config, then a `terminal_info()` read-back.
4. **The park must come from the analytics service container, not the gateway.** House credentials live only in the analytics service environment (D-00); the 164.6.6.1 S-04/S-11 precedent is a credentialed house `initialize` run from there with values read from the environment and never printed.

**Primary recommendation:** write plan 01 as (a) one protocol file in the phase directory (placeholders only) with steps S0–S9 below, (b) a founder checkpoint that is `human_needed` until the readings are pasted into CONTEXT `## Live verification`, and (c) a verdict line plus a `TODOS.md` `MT5-UNKNOWN-BROKER-SERVER-HANG-01` update. Build nothing. Keep the founder's session on the VALIDATION gateway via the bridge on loopback (Linux `python3` + `mt5linux` client, executing in the Wine `python.exe`), with the house park run from the analytics service container.

### Pattern 1: the one-off call (the evidenced shape)

**What:** an interactive `railway ssh --service <validation-gateway>`; inside it, write `/tmp/qz_gate.py` (no secrets inside; the container root filesystem, never `/config`), run it with `python3 /tmp/qz_gate.py`, then `rm` it. The script prompts for login, server and password on the tty and prints only a dict of booleans, a code, seconds and counts.

**Why this and not `python3 - <<EOF` or a one-liner:** with a heredoc on `python3 -`, stdin is the script, so `input()` reads EOF; writing the file first keeps stdin on the tty so `input()` and `getpass.getpass()` work. A one-liner puts the values in argv of the local shell history and the remote `ps`.

**Evidence the shape is right:**
- Bridge process tree and interpreter [VERIFIED: `deploy/mt5-gateway/railway-gateway.md:62-68`, from the 164.6.5 spike]: Linux side `python3 -m mt5linux --host 0.0.0.0 -p 8001 -w wine python.exe`; Wine side `python.exe /tmp/mt5linux/server.py --host 0.0.0.0 -p 8001`, "the interpreter the rpyc channel executes in"; terminal `C:\Program Files\MetaTrader 5\terminal64.exe`, `WINEPREFIX=/config/.wine`.
- A client on the gateway reaching the bridge on loopback [VERIFIED: `railway-gateway.md:304-307` `m=MetaTrader5(host="localhost",port=8001)`; `scripts/mt5-diag.sh` uses `MT5_DIAG_SERVICE=<gateway>` with host `127.0.0.1` as its fallback].
- Server is threaded: `mt5linux` 0.1.9 `__main__.py` default `--mode threaded` (`ThreadedServer`) [VERIFIED: wheel source read this session]. The `MetaTrader5` module is process-global inside that one Wine python, so a second connection shares the same IPC session. That is why the lease exists, and why a concurrent liveness-probe `initialize()` can interfere (see Safety envelope).
- Wine-prefix command form, if the direct-Wine alternative is ever needed [VERIFIED: `railway-gateway.md:295-297`]: `railway ssh --service <gateway> "s6-setuidgid abc bash -lc 'export WINEPREFIX=/config/.wine WINEDEBUG=-all ...; wine python -m pip ...'"`. `start.sh` itself runs `wine python --version` and `wine python -m pip install` [CITED: upstream `Metatrader/start.sh`; the running container's own copy at `/Metatrader/start.sh` was read by the 164.6.5 spike, `164.6.5-02-SUMMARY.md:73`].
- **No recorded evidence** that the 164.6.5 or 164.6.6.1 spikes ran a one-off MetaTrader5 call by launching `wine python` directly. The 164.6.6.1 spike drove the terminal from the analytics service over the private network (credentialed `initialize`, Reading B) and used Linux-side `kill`/`ps`/`ls` over `railway ssh` for the filesystem and process readings [VERIFIED: `164.6.6.1-CONTEXT.md:227-342`, S-02..S-11]. Say so in the protocol.

**What the script must do (each point is a measured trap):**
1. Build the client, then set the rpyc timeout on the private connection exactly as production does: `m._MetaTrader5__conn._config["sync_request_timeout"] = <seconds>` [VERIFIED: `analytics-service/services/mt5_client.py:1253-1257`]. mt5linux 0.1.9 has no `timeout=` constructor knob and rpyc's own default is 30 s [VERIFIED: `mt5_client.py:255-262`, `1231-1240`]. Without it, the call raises at 30 s, before MT5's 45 s IPC ceiling, and M1 reads as a different timeout than the 2026-10-05 one. Use `ipc_timeout_ms / 1000 + 25`.
2. Call `initialize(timeout=20000)` first, then `login(..., timeout=<ms>)`, as `Mt5Client.login` does [VERIFIED: `mt5_client.py:2702-2706, 2719-2746`: a bare `login()` without `initialize()` returns `-10004 'No IPC connection'`]. Record `init_ok` separately. Use `timeout=45000` for M1 to mirror the production validate ceiling [VERIFIED: `mt5_client.py:271-275`: "55s carries a 45 000ms IPC ceiling"].
3. Print only: `type(exc).__name__` on a raise, booleans, `last_error()[0]` (the code, never the text), seconds, and Journal counts. `mt5linux` builds `code=f'mt5.login(*{args},**{kwargs})'` and `eval`s it remotely, so a remote traceback can carry the password [VERIFIED: `mt5linux` 0.1.9 `__init__.py`, `login()`; repo corroboration `mt5_client.py:2691-2694` and `services/mt5_probe.py:857-859`, "mt5linux interpolates the password into the source it evaluates remotely (T-134-01)"].
4. "Authorized" means `account_info().login == <typed login>`, not `login()` returning True alone; after a failed login `account_info()` can still show the previous (house) account.

- switch: `'<account A>': disconnected` then `'<account B>': authorized` [VERIFIED: `docs/runbooks/mt5-go-live.md:367`]
- the 2026-10-05 control reading: "the disconnect from the house server and then no authorization attempt on the requested server at all" [VERIFIED: `TODOS.md:1673-1674`]

**Method:** record `(path, byte size)` of the newest log before the step, run the step, wait about 10 s, then read only the delta and count: lines containing `authorized on`; lines matching `authorization on .* failed`; lines containing the requested server string (the script holds it in memory; counted, never printed); lines containing the typed login. Strip NUL bytes then decode latin-1: that works whether the file is UTF-16LE or ASCII, so it needs no encoding assumption (MetaTrader logs are widely reported as UTF-16LE; [ASSUMED], and the control makes the reader self-checking). Do not run across 00:00 of the log's clock (a new file starts).

**The positive control is mandatory.** "No authorization attempt in the Journal" is an absence claim. It only means something if the same reader demonstrably sees a fresh `authorized on` line within the same ~10 s window on a known-good event. S2 therefore performs a house re-login (the park procedure, from the analytics container) and requires `j_authorized_on >= 1`. If the control reads 0, every "no attempt" reading is void (report "no observation", never "absent").

### Pattern 3: credential handling (answers Q2)

- Interactive session only: `railway ssh --service <validation-gateway>` with no command. Do not use `--session` (it runs inside tmux and "Installs tmux if not present", a change on the gateway) [VERIFIED: `railway ssh --help` locally; [CITED: https://docs.railway.com/cli/ssh]]. Piped stdin runs without a PTY [CITED: same page], so `getpass` would fail; keep the session interactive.

HOME=/config`; consistent with `/config` holding the usual home folders, `164.6.6-CONTEXT.md` S-07], so a bash history file written on exit would land on the PERSISTENT volume. - The demo investor password transits the rpyc channel inside an `eval` string. The same exposure exists on every production validation and is accepted (T-134-01); the gate adds no new surface. Whether the Wine-side rpyc server logs the eval source is [ASSUMED] not to happen; the founder should check the gateway's own log for the run window only if a leak is suspected.
- M3 writes a config file that contains the demo password. Create it under the Wine user (`s6-setuidgid abc`) with `umask 077` in `/tmp` (the Wine process must be able to read it, so a root-owned 0600 file will not work), delete it as soon as the terminal has started, and never place it on `/config`. A demo password is low-value, which is why the risk is accepted, but D-01 still forbids any tracked or argv exposure.

### Anti-Patterns to Avoid
- **Reaching for `python3 -c` with the password in the argument,** or a `railway ssh "<command with secret>"`. Argv leaks to local history and remote `ps`.
- **Printing `str(exc)` / a traceback / `last_error()` text.** The text can echo the server or the password.
- **Counting "no Journal line" without the positive control.** See Pattern 2.
- **Leaving the terminal on a `/config:` custom ini.** It runs that file read-only and bypasses `common.ini`'s `[Experts]` keys (see Pitfall 3).
- **Using the 2026-10-05 broker, any Vantage-family server (the house broker's family appears in `ROADMAP.md` Journal quotes), or the house broker as a "never seen" test.** D-03 and D-02.
- **Pausing anything by changing a Railway variable.** Every variable change redeploys the service (`mt5-go-live.md` Step 2d item 4), and the first validation after a deploy pays an owed scrub on this terminal.
- **Installing `xdotool` (or anything) on the gateway to make route (a) "work".** That is an image change; 164.6.5 D-05 rejected owning the image, and D-15 makes any new verb a posture decision after the gate.

## Common Pitfalls

### Pitfall 1: a validation (or its owed scrub) lands mid-gate
**What goes wrong:** the analytics process's scrub kills `terminal64.exe` and deletes `accounts.dat` and the `trades` caches, and a validation switches the account. The founder's measurement is clobbered. **Why:** the terminal lease is an in-process `asyncio.Lock` registry that "does not cross processes"; a founder session cannot hold it [VERIFIED: `services/mt5_concurrency.py:357-368`; `services/mt5_terminal_scrub.py` boot-mark docstring, "the lease and the probe-event registry do not cross processes"]. Scrub triggers are validations only (wizard `validate_wizard`, worker `validate_worker`), plus a boot mark that makes the FIRST validation after each analytics deploy pay an owed scrub [VERIFIED: `mt5_terminal_scrub.py:631-663`]. **Avoid:** quiet-window evidence in S0 (S-11's recipe: zero validate-site log lines for 10 min, zero open MT5 validation jobs, Reading A shows no validate-site row in the window) and do not let an analytics deploy happen during the gate. **Warning sign:** a `terminal64.exe` start time later than the step began; Reading A validate-site row.

### Pitfall 2: the liveness probe races the founder
**What goes wrong:** every tick, `probe_validation_terminal` does a bare `initialize()` on this terminal (credential-free, bounded lease, then `account_info`). The `MetaTrader5` module is one process-global session inside the Wine python, so a probe `initialize()` can land inside a 45 s M1 `login()`. Worse, with the terminal killed for M3, a probe `initialize()` RELAUNCHES `terminal64.exe /portable` with no `/config`, racing the founder's relaunch (two instances on one data directory). **Evidence:** probe is wired in the tick after the jobs heal [VERIFIED: `services/mt5_session_monitor.py:350-383`]; its probe is `assert_session_authorized` = `initialize(timeout=...)` [VERIFIED: `mt5_client.py:2781-2837`, `mt5_validation_liveness.py:133-157`]; `initialize()` launches a not-running terminal [VERIFIED: `railway-gateway.md:78-83`, "a recycle is: terminate the process, then call `initialize()`"; MetaQuotes [CITED: https://www.mql5.com/en/docs/python_metatrader5/mt5initialize_py]: "If required, the MetaTrader 5 terminal is launched"]. **Consequences are bounded:** readings only count toward an outage run; the page threshold is `ceil(3600 / interval)` consecutive not-measured readings, 6 at the default 600 s [VERIFIED: `mt5_session_episodes.py:502, 524-537`; `mt5_session_monitor.py:172`], and an `authorized` reading ends the run. A founder hold of a few minutes cannot page. **Avoid:** (a) read the tick phase from analytics logs (the probe writes `mt5 validation liveness: state=%s kind=%s code=%s` at INFO each tick [VERIFIED: `mt5_validation_liveness.py:201-206`]) and start each measured call about 60 s after a tick line, so the next tick is more than 8 minutes away; (b) do M3's kill-and-relaunch as ONE shell line so the relaunch gap is seconds; (c) there is no no-deploy pause (the kill switch `MT5_ENABLED` and `MT5_SESSION_POLL_INTERVAL_S` are Railway variables, so changing them redeploys). The actual production interval is [ASSUMED] to be the 600 s default (variables were not read).

### Pitfall 3: M3 leaves the validation terminal on a config with no `[Experts]` keys
**What goes wrong:** a terminal started with `/config:<file>` uses that file read-only and not `common.ini` [CITED: https://www.metatrader5.com/en/terminal/help/start_advanced/start: "Custom configuration files are used in the 'read only' mode"; the default configuration file is `common.ini`]. The validation terminal's four `[Experts]` options (Enabled, Account, Profile, Api) live in `common.ini` [VERIFIED: `164.6.6-CONTEXT.md` override item 8, "Enabled=1, Account=0, Profile=0, Api=0"; `railway-gateway.md:399-415` step 4a]. A terminal left on the gate's ini would answer every validation as undetermined (D-31) and `trade_allowed` would read false. **Avoid:** S5 ends with kill, credentialed house relaunch (the bridge's `initialize()` relaunches `terminal64.exe /portable` with no config, S-11: 2.1 s), then `mt5-diag.sh` read-back `connected: true`, `trade_allowed: true`, `tradeapi_disabled: false` (the Step 5 GATE-CHECK row `TERM`, `mt5-go-live.md:212-215`).

### Pitfall 4: a succeeding route teaches the terminal and contaminates the next
This is D-02's reason. Also: the broker search in M4 and a success in M2/M3 write `servers.dat`, and the production scrub never names `servers.dat` [VERIFIED: `railway-gateway.md:134-137`], so learned entries persist on the production validation terminal after the gate. That is harmless to production and is also the reason a broker can only be a first-contact test once. Run the never-seen check (S0) per broker.

### Pitfall 5: the rpyc sync timeout masquerades as the MT5 timeout
See Pattern 1 point 1. Record both `elapsed_s` and which side ended the call (`raised` type vs `login_returned`).

### Pitfall 6: a second `terminal64.exe` or a wrong process check
Under Wine the process name is the full Windows path, so `ps -eo comm | grep -cx terminal64.exe` can never match; the working form is `ps -eo args | grep -c '[t]erminal64.exe'` [VERIFIED: `164.6.6.1-CONTEXT.md:237-241`]. BusyBox `sed` is not case-insensitive [VERIFIED: `164.6.6.1-CONTEXT.md:367`]. The shell and userland on the gateway are therefore [ASSUMED] minimal until S1 inventories them.

### Pitfall 7: VNC left open
The only VNC access this repo has used is a temporary password-gated Railway domain, removed the same day [VERIFIED: `164.6.6-CONTEXT.md` S-08 / override item 4]. `railway-gateway.md:518-521` says "Preferred: `railway run` / port-forward ... [ASSUMED: exact Railway port-forward invocation]"; Railway CLI 5.64.1 has no port-forward command (full `railway --help` read locally), so that line is stale. Create with `railway domain --service <validation-gateway> --port 3000`, delete with `railway domain delete` (both from `railway domain --help`), then take L6.

```python
# Source: shape of Mt5Client.login (analytics-service/services/mt5_client.py:2688-2747)
#         + _default_connect timeout (mt5_client.py:1253-1257); mt5linux 0.1.9 login/eval.
import getpass, glob, os, re, time
from mt5linux import MetaTrader5

PORT = 8001
LOGDIR = glob.glob("/config/.wine/drive_c/Program Files/MetaTrader 5/[Ll]ogs")[0]

def newest_log():
    return sorted(glob.glob(os.path.join(LOGDIR, "*.log")))[-1]

def mark():
    p = newest_log()
    return p, os.path.getsize(p)

def journal_counts(base, server, login):
    p, off = base
    with open(p, "rb") as f:
        f.seek(off)
        text = f.read().replace(b"\x00", b"").decode("latin-1")
    lines = text.splitlines()
    return {
        "j_authorized_on": sum("authorized on" in s for s in lines),
        "j_auth_failed": sum(bool(re.search(r"authorization on .* failed", s)) for s in lines),
        "j_mentions_server": sum(server in s for s in lines),
        "j_mentions_login": sum(str(login) in s for s in lines),
    }

login = int(input("demo login: "))
server = input("server (name or host:port): ")
pw = getpass.getpass("investor password: ")
ipc_ms = int(input("ipc timeout ms [45000]: ") or "45000")

m = MetaTrader5(host="localhost", port=PORT)
m._MetaTrader5__conn._config["sync_request_timeout"] = ipc_ms / 1000 + 25
base = mark()
t0 = time.monotonic()
out = {}
try:
    out["init_ok"] = bool(m.initialize(timeout=20000))
    out["login_returned"] = bool(m.login(login, password=pw, server=server, timeout=ipc_ms))
    out["last_error_code"] = m.last_error()[0]
    a = m.account_info()
    out["authorized_for_typed_login"] = a is not None and a.login == login
except Exception as exc:
    out["raised"] = type(exc).__name__          # the type only, never the text
out["elapsed_s"] = round(time.monotonic() - t0, 1)
time.sleep(10)
out.update(journal_counts(base, server, login))
print("RESULT", out)
pw = None
```

### M3 sequence (shape; planner writes the exact lines and compile-checks any Python)
1. Under the Wine user, `umask 077`, write `/tmp/<ini>` from tty prompts: `[Common]` then `Login=`, `Password=`, `Server=`, `KeepPrivate=0`.
2. One shell line: collect the PIDs with `pgrep -f '[t]erminal64.exe'` (or the `ps -eo args` form), `kill` them, then launch `s6-setuidgid abc env WINEPREFIX=/config/.wine WINEDEBUG=-all DISPLAY=:1 wine 'C:\Program Files\MetaTrader 5\terminal64.exe' /portable '/config:Z:\tmp\<ini>' &`.
3. Poll the bridge (`initialize()` then `account_info()`) for up to ~60 s; record authorized for the typed login, seconds from launch, Journal counts.
4. `rm -f /tmp/<ini>` as soon as the terminal has started (after the first poll).
5. Restore: kill the config-launched terminal; run the park (Pattern 4), whose credentialed `initialize` relaunches `terminal64.exe /portable` with no config; then Reading B and `mt5-diag.sh` read-back.
