## Phase Boundary

The terminals should learn a broker server on its first successful validation, so nobody has to
hand-list it in `MT5_KNOWN_SERVERS`. That only happens if the criterion 1 GATE finds a headless
route. Measure the gate first, on the VALIDATION terminal only, never on the jobs terminal. If no
headless route exists, the phase closes with that measured verdict and builds nothing. The static
list and runbook Step 2d then stay the answer.

**Measured at HEAD `9014788bc` (2026-10-15; re-measure at plan time, symbols move):**

- **The pre-check.** `services/mt5_probe.py` holds three symbols.
  - `MT5_KNOWN_SERVERS_ENV`.
  - `read_env_known_mt5_servers()`: the env list plus the house `MT5_SERVER`, normalised by
    `normalise_mt5_server` (strip, then casefold).
  - `assert_mt5_server_known(server, *, site)`. A miss raises `Mt5ServerUnknownError`; an empty
    list raises `Mt5KnownServersUnconfigured`.
- **The two pre-check sites** (PARITY-01, 164.6.6.3 D-09). Both run before the lease and before
  any client exists.
  - `routers/exchange.py::_validate_mt5_key_probe` (`SITE_VALIDATE_WIZARD`).
  - `services/ingestion/mt5.py` `Mt5Adapter.validate` (`SITE_VALIDATE_WORKER`), after the
    validation-endpoint check.
- **`Mt5Client.login(login, password, server)`** passes `server` straight to
  `mt5.login(..., server=server, timeout=...)`. A `host:port` server string (route b) needs no new
  remote verb.
- **The rpyc channel carries only committed, named remote literals** (recycle, scrub; T-134-03
  posture, `deploy/mt5-gateway/railway-gateway.md`). Scripting route (a) or (c) in production
  would add a new remote verb, which is a posture change (D-15).
- **`TODOS.md` `MT5-UNKNOWN-BROKER-SERVER-HANG-01`** is open and human_needed. 164.6.6.3's SC4
  (Step 2d's live reading) is "not yet taken". The optional `servers.dat` / headless measurement
  was deferred on 2026-10-06 and never run.

## Implementation Decisions

All decisions below are the founder's, taken on 2026-10-15 by AskUserQuestion on the smart-discuss
proposals. A1+A2+A3 were answered as one: "You, railway ssh + demos (Recommended)". The Step 2d
question was answered "Not sure". A4 was answered "Accept it (Recommended)". B1–B3, C1–C4 and
D1–D2 were answered "Take all recommendations (Recommended)".

### Area A — the criterion 1 gate measurement
- **D-01 (A1). The founder runs it.** The session is a `railway ssh` into the VALIDATION gateway.
  It uses the bridge's own Wine `python.exe` with its MetaTrader5 package (the interpreter the rpyc
  channel executes in), plus VNC for route (a). It is the same method as the 164.6.5 spike, and no
  agent touches the gateway.
  - The protocol is written one founder step at a time, with placeholders only (`<Broker>-Demo`,
    `<validation-gateway>`, `<demo-login>`). It never names a real server, account, host or key id.
  - Nothing is deployed for the gate.
  - The founder types credentials. They never go into a tracked file, an argv the shell history
    keeps, or a pasted reading.
- **D-02 (A2). Demo accounts only.** Each route gets a fresh DEMO account at a DIFFERENT broker the
  validation terminal has never seen. The reason: a route that succeeds probably writes the broker
  into that terminal's `servers.dat`, which would contaminate the next route.
- **D-03 (Step 2d question, answered "Not sure").** The founder could not say whether Step 2d was run
  for the 2026-10-05 broker, so that broker is treated as possibly KNOWN on either terminal.
  - Its key is NOT used as a test case.
  - No demo account is opened at that broker.
- **D-04 (A3). Measure ALL routes, in this order.** For every route record: authorized yes/no,
  elapsed seconds, and whether the Journal shows an authorization attempt on the requested server.
  - **M1, control.** `login()` with the server NAME only, at a never-seen broker. It is expected
    to reproduce the 2026-10-05 reading: an about 45 s hang and no authorization attempt in the
    Journal.
  - **M2, route (b).** `login(server="host:port")`. Then retry the same account by NAME, to see
    whether the success taught the terminal the name.
  - **M3, route (c).** A startup config with `Server=`, or `terminal64.exe /portable /login
    /password /server` command-line flags. This route restarts the validation terminal.
  - **M4, route (a).** *File → Open an Account* broker search in VNC, stopping before an account
    is created, then `login()` by NAME. The run also records whether the search can be driven
    with no human (for example, keystrokes sent to the container display).
  - **Afterwards.** Park the validation terminal back on the house server and take the runbook's
    L6 reading (VNC torn down). The park itself is confirmed by Reading B against the validation
    terminal reading `house: yes`, as in L-H3b.
- **D-05 (A4). A pasted `host:port` is a valid server entry** if the gate shows route (b) works.
  Users type a NAME, and only the broker search turns a name into an address, so route (b) helps
  only when the user supplies the address (Pepperstone's own FAQ tells users to).

### Area B — the learned-server store (built only if the gate passes)
- **D-06 (B1).** The store is a new service-role-only table, with one row per normalised server per
  terminal role. It records when the server was resolved on the VALIDATION terminal and when on the
  JOBS terminal, because each terminal's store is its own (criterion 4).
  - `MT5_KNOWN_SERVERS` plus `MT5_SERVER` become the SEED.
  - The known set is the union of seed and table, computed at read time, at both pre-check sites.
- **D-07 (B2).** If the table read fails, the service falls back to the env seed only and logs ERROR.
  An unknown name then takes the bounded resolve path. It is never admitted blind.
- **D-08 (B3).** Nothing is forgotten automatically. An operator removes a row by hand.

### Area C — the unknown-server flow (founder direction 2026-10-06, (i)–(v))
- **D-09 (C1).** Direction (i) is followed literally. A validation on an unseen name enqueues a resolve
  job on the VALIDATION terminal, and the wizard says "checking a new broker server" and polls. It
  never logs in blind. The job's exact shape is fixed in the re-plan, from the gate's timings.
- **D-10 (C2).** A name no broker knows gets a NEW named, recoverable wire code. It is distinct from
  `MT5_SERVER_UNKNOWN` and is never `KEY_SIGN_IN_FAILED` (direction (v)).
- **D-11 (C3).** The resolve's bound is derived from the gate's measured route time, never
  hand-picked. A house park ALWAYS follows, so an unknown server never holds the shared validation
  terminal for the full 45 s or leaves it off the house server (criterion 3).
- **D-12 (C4).** The same resolve step runs under the JOBS-terminal lease before such a key's first
  sync. If it fails, the sync is refused by name, never by hanging (criterion 4).
- **D-13.** A server is learned only from an authorized session (`connected` true), never from a
  failed or timed-out attempt (criterion 3, restated so the re-plan cannot drop it).

### Area D — phase shape
- **D-14 (D1).** Plan ONLY plan 01 now: the gate protocol and its founder checkpoint. The build
  (criteria 2–5) is re-planned from the measured verdict ("if a spike disproves a plan set, replan,
  don't patch"). If no headless route exists, the phase closes with the verdict and builds nothing.
- **D-15 (D2).** Any new committed remote literal is a T-134-03 posture change. That covers a
  scripted GUI search (route a) and a config write or launch (route c). The founder ratifies each
  route's verb AFTER the gate shows that route works. Route (b) needs no new verb.

### Standing constraints carried in
- 164.6.6.3 D-14 stands: the SERVICE never reads or parses `servers.dat`. The terminal writes its
  own store through its own search. A founder looking at the file during the gate is measurement,
  not a service read.
- The jobs terminal is never used for the gate.
- Paste yes/no, counts, seconds and kinds only: never a server string, an account number, a
  password, a host or a key id. The repo is public.
