### CR-01: the scope-broadening probe skip branched on a column the key's owner could rewrite

**Files:** `supabase/migrations/20260810120000_lock_api_keys_exchange_column.sql` (new),
`supabase/tests/test_api_keys_exchange_not_user_writable.sql` (new), `TODOS.md`
**Commit:** `2d5d78da`

**⛔ NOT APPLIED TO ANY DATABASE.** The migration has **not** been run against
TEST or PROD. Merging `supabase/migrations/**` to `main` auto-applies to
production, and nothing here is pushed.

**Applied fix — root cause, per Rule 6.** `REVOKE UPDATE ON public.api_keys FROM
anon, authenticated`, table-level (a column-level `REVOKE UPDATE (exchange)` is a
documented no-op against a table grant — the trap migration 20260529150000's
header records), plus a **SECURITY INVOKER** `BEFORE UPDATE OF exchange` trigger
as defence-in-depth, plus the self-verifying DO blocks migrations 020/027/029
established.

**No re-grant, and that was audited, not assumed.** Every `from("api_keys")` /
`table("api_keys")` call site in `src/**`, `analytics-service/**`, `scripts/**`,
`e2e/**` and `supabase/migrations/**` was read. **There is no user-scoped UPDATE
anywhere.** The user-scoped client only SELECTs, INSERTs and DELETEs; every
UPDATE is either the Python worker on the service-role client or a SECURITY
DEFINER RPC running as the table owner (`disconnect_/reconnect_allocator_api_key`,
`advance_sync_cursor`, the circuit-breaker clock RPCs, the compute-jobs queue
RPCs). So there was no allowlist to grant back, and granting one would have been
speculative surface. INSERT and DELETE are deliberately untouched — both are live
client paths.

**Verified against a real PostgreSQL 16, not by reading.** A throwaway local
cluster was built with a faithful pre-fix fixture (Supabase-default `GRANT ALL`,
migration 027's SELECT allowlist, the `api_keys_owner` RLS policy, `auth.uid()`,
`service_role BYPASSRLS`). Measured:

| Check | Result |
|---|---|
| Exploit on the **pre-fix** state | **SUCCEEDS** — `PRE-FIX exploit result: exchange is now mt5` |
| Migration applies | clean; both self-verify blocks pass |
| Exploit **after** | `ERROR: permission denied for table api_keys` |
| Migration is idempotent | applied 3× clean |
| Self-verify block can fail | neutering the `REVOKE` line → `Migration … failed: role authenticated still holds UPDATE …` |
| `service_role` (the worker) | unaffected — can still write `api_keys`, incl. `exchange` |
| SECURITY DEFINER RPC under an `authenticated` caller | still succeeds (the disconnect/reconnect shape) |

All of the above were **re-run from scratch after the laptop crash** and
reproduced identically.

**The guard's mutation matrix (4 states, measured):**

| State | Guard says |
|---|---|
| Both protections live | 4/4 assertions OK |
| Trigger dropped, REVOKE kept | still green (still safe) — correct |
| UPDATE re-granted, trigger kept | **REDS assertion 3 by name**, while assertion 2 still passes → proves the trigger is load-bearing, not decorative |
| Both removed (= the live exploit) | **REDS by name**: `CR-01 REGRESSION (2): authenticated rewrote api_keys.exchange on its own row …` |

**⚠️ I changed the precedent's gate, deliberately.** The companion test in
`test_profiles_privileged_columns_locked.sql` gates its negative assertions on the
*trigger's existence*. Measured here: with the trigger dropped and the REVOKE left
in place, a trigger-keyed gate **SKIPS** — deleting one of the two protections
silently disarms the assertions guarding it. This test therefore gates on the
**column-comment marker** the migration stamps, which is not a control: removing
either protection leaves it intact, so both regressions re-arm as failures rather
than skips. The two positive controls (owner can still SELECT; owner can still
DELETE) run unconditionally, so the file can never be entirely inert.

**⚠️ FOUNDER PREMISE CORRECTED — please read.** The brief states *"`api_keys.exchange`
is set by the server at key creation after verification."* **It is not.** The
browser calls `/api/keys/validate-and-encrypt` and then performs the `api_keys`
INSERT **itself** (`ApiKeyManager.tsx:254`, `StrategyForm.tsx:140`,
`AllocatorExchangeManager.tsx:591`), choosing the `exchange` value independently
of what the server validated.

**Why the UPDATE lock still closes the harmful exploit, and the INSERT residue
does not.** The ciphertext is server-minted and only ever minted for a key the
server confirmed read-only (`validate-and-encrypt/route.ts:310`), so a broadened
key can only reach `api_keys` by being connected while read-only and broadened
afterwards — the row then carries its true venue, and the forgery **requires
UPDATE**. The reviewer's step 5 (PATCH the venue back so the key syncs normally
and the listing looks ordinary) is what makes it durable, and it is now
impossible. A forged INSERT can still mislabel a row, but with UPDATE revoked it
can never be corrected back, so that strategy's sync fails permanently and no
credible listing results — self-defeating, not harmful. Logged to `TODOS.md`
(Security) with the real remedy: move the INSERT server-side into
`validate-and-encrypt` and `REVOKE INSERT`, a three-component connect-flow
refactor deliberately outside this fix's blast radius.

**Server-side defence-in-depth: considered, deliberately not added.** There is no
server-owned provenance signal to corroborate the venue against, so any check
would have re-read the same column under a different name. Adding one would have
looked like a second layer while being the same layer. The reviewer's ⛔ was
respected: the fail-toward `?? true` default is untouched.
