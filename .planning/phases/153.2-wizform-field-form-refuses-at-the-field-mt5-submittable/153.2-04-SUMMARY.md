# Phase 153.2 Plan 04: MT5 declarable *and* submittable Summary

**MT5 is now a member of the set the wizard offers, preselected from the connected key and
rendered as an unremovable fact rather than a question asked twice — and the submit path
stops demanding a ccxt scope probe from a venue that has no scope surface, while the two
permanent failure conditions that used to arrive dressed as network blips with an impossible
Retry are finally told apart from a real one.**

## Accomplishments

### Task 1 — the narrow wizard set, and the pin re-cut in the SAME commit (`c9c51a0b`)

`WIZARD_ONLY_EXCHANGE_CODES` / `WIZARD_EXCHANGE_CODES` / `WIZARD_EXCHANGES` /
`canonicalizeWizardExchange` land in `closed-sets.ts`, composed **on top of**
`UI_EXCHANGE_CODES` rather than typed as a fifth literal, so the sFOX flag's behaviour stays
automatic instead of requiring four literals for two independent flags. `EXCHANGES`,
`UI_EXCHANGE_CODES`, `FUNDING_EXCHANGES` and `CRYPTO_EXCHANGES` are byte-unchanged and the
public marketing count does not move.

The `closed-sets.mt5-flag` pin was re-cut in that same commit — D-16's whole point, because a
widening that is unguarded for even one commit is what the pin exists to prevent. It **keeps**
both original negatives, **adds** the two it had always claimed in prose but never asserted
(`FUNDING_EXCHANGES`, `CRYPTO_EXCHANGES` — RESEARCH Table D's four-vs-two gap), and **adds**
the positive flag-ON assertion it lacked. A pin that asserts only absence cannot fail when the
flag turns on, which is the same defect class this plan audited elsewhere.

### Task 2 — the connected key's venue is a FACT (`18fa51fa`)

The chip group offers `WIZARD_EXCHANGES`; the venue of the key the strategy is built on
renders as a non-interactive `<span>` carrying the *selected* chip's tokens — visually
identical because it **is** selected, out of the tab order, and impossible to turn off.
⛔ Never a disabled `<button>`: a dead control is the exact failure mode this phase deletes.
A mono provenance eyebrow (`DETECTED FROM YOUR KEY`) sits beside the group label and a caption
interpolates the venue name (FLAG-2), so a second pinned venue cannot inherit a false sentence.

`withDetectedVenue()` unions the venue in at submit as well as at mount, closing the
resumed-draft path where `initial` carries a set that omits it — a strategy can never declare
a venue set that excludes its own key's venue. The rule is venue-generic throughout: a Bybit
key pins Bybit, and no venue name is compared anywhere in the file.

### Task 3 — the submit path stops asking a question that has no answer (`d6618b77`)

**One predicate, both call sites.** `runScopeBroadeningProbe` takes the venue and its first
statement is `if (!venueSupportsScopeProbe(venue)) return { ok: true };`. The single-key site
passes `apiKeyExchange` (already in scope for the asset-class stamp — no second lookup); the
composite site widened its member select to `api_key_id, api_keys ( exchange )` using the
`composite/members/route.ts` embed idiom and passes each member's venue. Gating both is what
makes it a class fix — leaving one ungated is the instance fix wearing a different hat.

**The gate fails TOWARD probing.** `venueSupportsScopeProbe` answers `true` for `null`, for an
unknown code and for an absent capability row. So a key whose `api_keys.exchange` read faulted
is still probed, and so is a composite member whose embed came back `null`. The justification
is written at the skip site in the MT5-13 comment's voice, all four points, including the
explicit ⛔ that this is a capability question and never an equality test — and the venue
literal is deliberately not spelled out even in the prose, because the acceptance grep proving
the route never names the venue runs over the comments too.

**Two permanent conditions stop being called temporary.** A body our own zod schema could not
read resolves to the module-scope `PROBE_PARSE_MISS` sentinel and now takes its own arm,
reached by reference identity (`livePerms === PROBE_PARSE_MISS`) — the only thing that can
separate it from a service that genuinely reported `probe_error: true`, since both carry the
same field. It answers `KEY_SCOPE_CHECK_UNAVAILABLE`; the service-reported arm keeps
`KEY_NETWORK_TIMEOUT` and its honest Retry. A missing `INTERNAL_API_TOKEN` gets its own
`ProbeMisconfiguredError` class, caught before the generic tail, answering `500
SEAM_MISCONFIGURED`. Both codes carry no recoverable action, so `buildEnvelope` derives
`recoverable: false` and **no Retry control renders at all** — the structural suppression, not
a prop. Both were verified present in `SubmitStep`'s `KNOWN_FINALIZE_CODES` at source before
committing. No retry, backoff or loop was introduced anywhere (D-07).

## Task 3 was inherited uncommitted — what the audit found

The previous executor's Task 3 work was in the working tree, unreviewed. It compiled and its
suites were green; that proved passage, not correctness, and certainly not falsifiability.
Three defects were found and fixed before the commit.

**1. A guard that could not fail (the defect class this phase exists for).** The re-cut
SEAMUX-07 row asserted `PROBE_FAILURE_ENVELOPE.code).not.toBe(PARSE_MISS_ENVELOPE.code)` — two
hand-typed constants declared thirty lines apart in the same test file. True the moment they
were typed, and unable to fail for **any** change to the route. Its comment claimed it made a
future collapse of the two arms "red by NAME"; it did no such thing. It now reads `body.code`
off the response the route actually returned, and runs **before** the broad `toEqual`, so a
collapse reports the explanation instead of `expected {…(2)} to deeply equal {…(2)}`. Mutation
M7 confirms the new form fires with its own message.

**2. A docblock that had become false at the exact site it describes.** `PROBE_PARSE_MISS`'s
docblock still read "so it lands on the EXISTING `probe_error` arm below" — which is precisely
what this change stopped being true. Rewritten to state the split, why identity is the only
separator, and ⛔ that it must stay a module-scope singleton, since a per-call object literal
would silently merge the two conditions again.

**3. A wrong claim about a runtime guarantee.** The new comment called the sentinel "one
frozen object". `as const` is a **type-level** freeze, not `Object.freeze` — the guarantee is
reference identity, not immutability. Corrected, with the distinction stated so the next
reader does not rely on a freeze that is not there.

**Audited and found sound:** the seam-absence assertion is paired with positive controls (a
binance row and an explicit sFOX row that both assert the probe DID run, and mutation M1 reds
the absence row); the class sweep's oracle is the capability registry with an anti-vacuity
floor (`nonProbing.length > 0` and `< SUPPORTED_EXCHANGES.length`); the truncation-detector
row hard-types `11` rather than importing `MAX_COMPOSITE_MEMBERS + 1`; `RF.lastCall` and
`INTERNAL_API_TOKEN` are both reset in `beforeEach`, so no row depends on leakage from its
neighbour; and no route-local scrubber was re-added — the existing `scrubSeamError` call
already covers the new throw, and `finalize-wizard/route.ts`'s own SEAMPROSE-01 citation row
is GREEN including every comment this plan added.
