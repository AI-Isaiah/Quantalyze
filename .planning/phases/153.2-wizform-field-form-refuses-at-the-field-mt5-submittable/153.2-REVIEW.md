## Critical Issues

### CR-01: The scope-broadening probe skip branches on a column the key's owner can rewrite — an ASVS V4 control the user can switch off

**File:** `src/app/api/strategies/finalize-wizard/route.ts:736-738` (the skip),
`:1129-1147` (where the venue comes from), `:1200` and `:1442` (both call sites);
`src/lib/closed-sets.ts:196-200` (`venueSupportsScopeProbe`)

**Issue:**

The submit-time probe is the defence against *a key broadened to trade/withdraw
between Connect and Submit* — the route's own comment calls it "the ASVS V4
scope-broadening defence". 153.2-04 gates it:

```ts
// route.ts:736
if (!venueSupportsScopeProbe(venue)) {
  return { ok: true };          // probe skipped entirely
}
```

`venue` is read straight off the database row:

```ts
// route.ts:1131-1146
const { data: keyVenueRow } = await assetClassAdmin
  .from("api_keys").select("exchange").eq("id", apiKeyId).single();
apiKeyExchange = typeof keyVenueRow?.exchange === "string" ? keyVenueRow.exchange : null;
```

`api_keys.exchange` is **writable by the row's owner**, verified at source in
this repo:

- `supabase/migrations/20260405061912_rls_policies.sql:22` —
  `CREATE POLICY api_keys_owner ON api_keys FOR ALL USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid());`
  `FOR ALL` includes `UPDATE`.
- `supabase/migrations/20260410225608_api_keys_column_revoke.sql` revokes and
  re-grants **SELECT only** (its own header states the table "inherits Supabase's
  default `GRANT ALL ON TABLE api_keys TO anon, authenticated`"). There is no
  `REVOKE UPDATE ON api_keys` anywhere in `supabase/migrations/`, and no
  `BEFORE UPDATE` trigger on the table (grepped).
- `supabase/migrations/20260723172032_mt5_exchange_boundary_checks.sql:69` —
  `CHECK (exchange IN ('binance','okx','bybit','deribit','sfox','mt5'))`. The
  exempt value is an **admitted** value of the constraint, in production today.
- `VENUE_CAPABILITIES` is deliberately **not** flag-gated
  (`closed-sets.ts:126-146`, "a capability is true whether or not the card is on
  screen"), so this skip is **live in production right now**, independent of
  `NEXT_PUBLIC_MT5_ENABLED` / `MT5_ENABLED`.

Exploit path, entirely within the user's own session and own rows:

1. Connect a read-only exchange key (passes the connect-time scope check).
2. Broaden that key at the exchange to trade/withdraw.
3. `PATCH /rest/v1/api_keys?id=eq.<own key>` with `{"exchange":"mt5"}` using the
   browser's own Supabase JWT. RLS allows it; the CHECK admits it.
4. Submit the wizard. `venueSupportsScopeProbe("mt5")` → `false` → **the probe
   never runs**, `runScopeBroadeningProbe` returns `{ok:true}`, and the strategy
   finalizes to `pending_review` with a key that holds trade/withdraw scope.
5. (Optional) `PATCH` the venue back afterwards.

The result is a strategy presented to allocators under a read-only-verified
claim that is false. The same rewrite also flips the `asset_class` stamp at
`:1169-1175` (√365 ↔ √252), which is a money-math boundary this repo pins
elsewhere as one — that half is pre-existing (MT5RECON-02), but 153.2-04 is what
turns the column into a **security** input.

Note what is *not* wrong: every fail-toward direction the plan argued for is
correct and is tested — `null`, `""` and unknown venues all still probe
(mutation-verified above), and both call sites are gated. The defect is one
level up: the gate's input is not trustworthy.

**Fix:** Take `exchange` out of the user's write surface. The in-repo precedent
is `supabase/migrations/20260529150000_lock_profile_privileged_columns.sql`
(revoke table UPDATE, grant back only the non-privileged columns) — a table-level
`REVOKE UPDATE (exchange)` is a documented no-op against an existing table-level
grant, so it must be done in that order:

```sql
-- new migration
REVOKE UPDATE ON api_keys FROM anon, authenticated;
GRANT UPDATE (label, is_active) ON api_keys TO authenticated;  -- audit the real
-- set of columns the app writes from the user-scoped client first.
```

Plus a SQL guard in `supabase/tests/` asserting `authenticated` has no
`UPDATE` privilege on `api_keys.exchange` (`has_column_privilege`), mirroring
migration 029's `has_column_privilege` self-verify.

If a full column lock is too wide a blast radius for this phase, the minimum
stop-gap is to stop trusting the column for the *security* decision: resolve the
probe-exemption venue from a source the user cannot write (e.g. re-derive it
inside the same SECURITY DEFINER surface that owns key provenance), and leave
`api_keys.exchange` governing only the display/annualization path. ⛔ Do not
"fix" this by removing the fail-toward default — that default is correct and is
the only reason the blast radius is bounded to venue-forgery rather than to
every unresolved venue.

### WR-01: A server field refusal on a field that is not currently rendered locks the form permanently — no message, no focus, no way to clear

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/MetadataStep.tsx:510-515`,
`:536-544`, `:704-713`, `:762-779`

**Issue:** `revealAndFocus` returns silently when the field's ref is unmounted:

```ts
function focusTargetFor(id) { const el = fieldRefs[id].current; if (!el) return null; ... }
function revealAndFocus(id) { const control = focusTargetFor(id); if (!control) return; ... }
```

but the refusal is still merged into `fieldErrors` (`:704-711`), so
`invalidFields` contains it and `handleSubmit` refuses **forever** at `:774`.
`messageFor` renders nothing (the control is not mounted), `noteFieldEdited` can
never fire (its only caller is the unmounted control's `onChange`), and the
summary at `:755-760` names a field the user cannot see:
*"1 field needs attention. The first is Whose capital is in this key?"*

`capitalOwnership` is the concrete instance: it renders only when
`showCapitalQuestion` (WizardClient `:1004`, `entryContext === "contribution"`),
yet it is an unconditional member of `MetadataFieldId`, `FIELD_ORDER`,
`clientFieldErrors` and `FIELD_BY_CODE`. Today it is not reachable — SubmitStep
only spreads `capital_ownership` when the draft carries it (`SubmitStep.tsx:263-265`)
and `initialDraft` never seeds it (`WizardClient.tsx:222-251`) — so this is
**latent, not live**. But it is the exact dead-end shape the phase exists to
delete, it is one prop change away from being live, and the test suite's
`capitalOwnership` row (`MetadataStep.test.tsx:1816`) passes
`showCapitalQuestion: true`, so nothing covers the other branch.

**Fix:** Make "no control to land on" a loud, clearable state rather than a
silent block. In `revealAndFocus`, when `focusTargetFor` returns `null`, drop the
server refusal instead of returning:

```ts
function revealAndFocus(id: MetadataFieldId) {
  const control = focusTargetFor(id);
  if (!control) {
    // The refusal names a field this surface does not render. Refusing forever
    // with no message and no control is the dead end this phase deletes — let
    // it escalate to the caller's envelope instead of silently blocking.
    setServerRefusal((prev) => (prev && prev.field === id ? null : prev));
    return;
  }
  ...
}
```

and add the negative row: mount with `serverFieldError={{field:"capitalOwnership", ...}}`
and `showCapitalQuestion` **absent**, then assert the submit still completes.

**Issue:** The change removes four page-level `max-w-[1920px]` caps on the

Six sites inside `isWide` trees still do exactly that. The four admin pages are

Scenario tab it stands in for is 1440-capped, widening the skeleton→page jump the

`max-w-[1440px]` from `ScenarioComposer`'s two shells so the tab honours the
fluid shell, or (b) narrow DESIGN.md's rule to name its carve-outs explicitly
(admin prose 1100, ScenarioComposer 1440) so the next reader inherits the
exception rather than a rule the codebase contradicts in six places.

### WR-03: `route.test.ts` mocks `isRateLimitMisconfigured` with a fabricated predicate over a fixture shape production never produces — and the comment claims the opposite

**File:** `src/app/api/strategies/finalize-wizard/route.test.ts:47-55`, `:3927-3941`

**Issue:**

```ts
vi.mock("@/lib/ratelimit", () => ({
  // "the real predicate's shape, not a stub that answers a constant"
  isRateLimitMisconfigured: (rl: { misconfigured?: boolean }) => rl?.misconfigured === true,

```

The real predicate (`src/lib/ratelimit.ts:246-252`) is:

```ts
return result.success === false && result.reason === "ratelimit_misconfigured";
```

503 row then drives it with `{ success:false, retryAfter:60, misconfigured:true }`

(the mock returns `true`, the 503 arm runs), so the assertion is not vacuous; but
the discrimination it demonstrates is one the test authored for itself, and the
comment asserting it is "the real predicate's shape" is false — the same
"a comment is a claim, not a witness" pattern this milestone has been paying for.
A future change that read `rl.reason` directly in the route would keep this row
green.

**Fix:** Use `importOriginal` for the predicate and drive it with the real
discriminator:

```ts
vi.mock("@/lib/ratelimit", async (importOriginal) => ({
```

### WR-06: The page-side of the "no px cap" invariant is unguarded — the skeleton is pinned, the page it stands in for is not

**File:** `src/app/(dashboard)/compare/loading.test.tsx:29-36` (guarded),
`src/components/layout/DashboardChrome.test.tsx:398-414` (shell guarded),
