### D-01 — The goal is the founder's (FOUNDER DECISION, 2026-09-26, recorded in the ROADMAP)

`python` and `e2e-seeded` no longer queue on the shared-TEST advisory lock; each runs against a
database private to its runner. This is the only founder answer this phase carries.

### D-02 — Neither job acquires key `61616158` (SC-1)

After the phase, `grep` of each job's body in `ci.yml` finds no `Acquire shared-test-db mutex`,
`Release shared-test-db mutex (best effort)` or `Verdict — shared-test-db mutex holder died mid-job`
step and no literal `61616158`, EXCEPT under D-07. The other takers of the key
(`supabase-migrate.yml`, `test-restore-from-baseline.yml`, `mutex-probe.yml`,
`analytics-deploy-verify.yml`) are NOT touched.
⭐ **CLARIFIED 2026-09-26:** "not touched" means their key TAKES (steps and behaviour). Dated prose
currency addenda in their comments or triage text that state the holder set or the key count are
permitted, as Phase 164.4.2.1 D-09 did.

### D-03 — The private database is the Supabase CLI local stack, `scripts/local-stack/run.sh` (SC-2)

Default: both jobs boot the precedent lane `scripts/local-stack/run.sh up`, the lane already used by
`sql-tests`, `frontend-local-stack` and `frontend-live-db-lane`. It pins its Postgres image
(`LANE_PG_VERSION`, never below `17.6.1.113`), replays migrations newer than the dump (Phase 164.4.2
DECISION F, `scripts/check-baseline-currency.mjs --replay-set`), runs the function-denial probe at
boot, and serves PostgREST + GoTrue, which supabase-js / supabase-py and the demo seeder need.
The bare `scripts/pg-lane/run.sh` cluster is allowed ONLY for a job the research MEASURES reaches the
database through raw SQL alone. Reason: SC-2 allows either; reuse the lane that already carries the
image pin, the replay and the loopback guard rather than building a third lane (Rule 2, Rule 7).
Each job that boots the lane also runs the lane's `Baseline currency - name the migrations the lane
replays on top of the dump` step, as `sql-tests` does.

### D-04 — Loopback-DSN guard, fail loud (SC-2)

Every DSN or Supabase URL the two jobs pass to their tests after the move must point at a loopback
host (`127.0.0.1`, `localhost`, `::1`). The job asserts it BEFORE the first DB-touching step and exits
non-zero on any other host. Reuse the guard the lane or `sql-tests` already has; do not invent a
second one. `src/lib/test-safety.ts` `assertNotProductionSupabaseUrl` stays in force and unmodified.

### D-05 — No drop in coverage or test counts (SC-3)

- The BEFORE numbers are MEASURED by the research from CI logs of a recent run on `main` (read-only
  `gh` API), per job: pytest passed / skipped / failed / xfailed counts and the `--cov` TOTAL %, and
  the Playwright seed-gated spec count (passed / skipped).
- AFTER, `pytest` keeps `--cov=services --cov=routers --cov=main_worker --cov-report=term-missing
  --cov-fail-under=80` byte-identical (and byte-identical with the `Makefile` `test:` target, as the
  job's own comment requires). The passed count may not drop and the skipped count may not rise.
- No test gains a `skip`, `xfail`, marker exclusion, `-k` / `--deselect`, or `test.skip` to make the
  move work. `CI=true`'s hard-fail branch (for example `_need_supabase()` in
  `analytics-service/tests/test_compute_jobs_fencing.py`) stays a hard fail.
- Any test that fails on the private database is FIXED at its root cause in this phase, or it falls
  under D-07. It is never skipped.

### D-06 — Nothing lowers a floor or widens an allowlist

No coverage threshold, `ARMS_FLOOR` / `FILES_FLOOR`, ratchet, `WAIVED_CEILING`, gitleaks allowlist,
live-DB ledger or lint allowlist moves in the permissive direction. A holder-set pin that shrinks
because a holder LEFT (the Phase 164.4.2.1 D-07 precedent) is not a relaxation; it moves by
measurement, in the same commit as the `ci.yml` change, with a dated reason, and every new or moved pin
is observed RED under a neuter before it is kept.

### D-07 — A test that genuinely needs shared TEST is named and stays on the key (SC-5)

If the research MEASURES that a specific test needs shared TEST (for example it asserts something
only a real hosted project serves, such as a Supavisor pooler or a real `pg_net` egress), that test
is named by file and test id, stays on the key in a job or step that still holds it, and states why
in a comment beside it and in the SUMMARY. "It currently uses TEST" is not a reason; the reason must be
something the local stack cannot serve. Default expectation, to be confirmed by measurement: zero such
tests.
⭐ **AMENDED 2026-09-26 (research):** zero is MEASURED for `python` (full suite run on the lane).

### D-14 — CSP remedy: option (b), derive the configured Supabase origin (ORCHESTRATOR DECISION, 2026-09-26; ✅ RATIFIED BY THE FOUNDER 2026-09-27)

⭐ **RATIFIED 2026-09-27.** The founder answered "Ratify D-14" to the orchestrator's AskUserQuestion in the session that runs this phase. The decision below stands as written and is no longer pending.

**Question (research Assumption A1):** `next.config.ts`'s `Content-Security-Policy` `connect-src`
allows only `'self' https://*.supabase.co wss://*.supabase.co https://plausible.io`, so a build
inlined with the lane's loopback URL has every browser-side sign-in refused (measured in Chromium
with the exact header). Option (a) sets `bypassCSP: true` for the seeded run; option (b) derives
the origin of `NEXT_PUBLIC_SUPABASE_URL` (plus its `ws:`/`wss:` twin) into `connect-src` at build time.
**Decision: (b).** Taken by the orchestrator in autonomous mode; no human was present. It is NOT a
founder answer and is surfaced for ratification.
**Reason:** (a) makes the seeded suite unable to fail on a CSP edit that breaks production login, a
user-facing gate turned vacuous, which this repo bans. Keeping `e2e-seeded` on the key under D-07 is
not allowed either: the reason would be the app's header, not a stack capability, and it would leave
`e2e-seeded` as the critical path, defeating D-01. (b) is the Rule 6 root-cause fix.
**Constraint that makes (b) safe:** the derived origin is appended ONLY when no existing
`connect-src` source already matches it. So the production build (an `https://<ref>.supabase.co`
origin) and `frontend-build` (the placeholder URL) emit a header BYTE-IDENTICAL to today's literal;
only a loopback build gains an entry. An unset or empty `NEXT_PUBLIC_SUPABASE_URL` yields today's
literal, does not throw at build, and never puts `undefined` into the header. The literal stays the
first string after `value:` so the `critical-regressions.test.ts` `[AUDIT-2026-05-07 #53]` Plausible
CSP pin still parses it. A contract test pins all three cases (prod-shaped URL equals today's literal;
loopback URL equals literal plus the loopback origin and its ws twin; unset or empty URL equals the
literal) and is observed RED under a neuter before it is kept. The planner reads
`node_modules/next/dist/docs/` for the headers API first (AGENTS.md).
**Reversibility:** reversible (a config edit; revert restores the literal). No `checkpoint:decision`.
**Recorded:** here AND as a dated note in the ROADMAP `### Phase 164.9.4` section.

### D-15 — The fence-test 40001 finding is booked, not fixed here

The research measured that a PostgREST call to `defer_compute_job` with a mismatched token hangs for
more than 25 s on an idle private lane (the RPC raises SQLSTATE 40001 and PostgREST retries it), so
the "flaky ReadTimeout under shared-TEST contention" attribution of the fence-test skips is wrong and
moving off TEST does not un-skip them. It touches the compute pipeline, so it may be data-integrity:
a plan books ONE evidence-only `TODOS.md` entry for it. It is not fixed in this phase and it changes
no count.

### D-16 — A push that touches a planning file a `frontend-test` assertion reads is CODE (FOUNDER DECISION, 2026-10-02)

**Why.** Review round 2 (WR-01) found that the round-1 push short path removed one of the two
backstops `[CI-DOCSPATH-01]` relied on. A docs-only PR skips `frontend-test` by design, and the entry
accepted that because the UNFILTERED merge push to `main` re-ran it. Once a `.planning/`-only push
took the short path too, a docs merge that broke `lint-sql-gates.test.ts` G3 or a
`verify-plan-anchors.test.ts` real-tree pin went GREEN on `main`, and the red surfaced on the next
unrelated code change, which then read it as its own.

**Decision.** The founder answered "Treat those 3 as code" to the orchestrator's AskUserQuestion on
2026-10-02. `scripts/classify-changed-paths.mjs` `TEST_READ_PLANNING_PATHS` lists the files, and
`classifyPushRange` classifies a push range that changes any of them as code (full corpus). The PR
path is unchanged.

⚠️ **The exact set is SIX files, not three.** The question named the review's three
(`.planning/REQUIREMENTS.md`, `.planning/ROADMAP.md`, Phase 159's `159-VERIFICATION.md`). Measured
against the two test files, `verify-plan-anchors.test.ts` G2 and its neighbours also read Phase
164.3's `164.3-07-DEFERRED.md` and `164.3-07-PLAN.md` by name, and creating the absent
`164.3-07-SUMMARY.md` ends the deferral those pins assert. All six are listed, because "identify
them exactly" was the instruction and a three-file list would leave the same gap for the other
three. The whole-corpus `--pending` scans are NOT listed: `plan-anchor-verify` runs the same scan
on every PR, docs-only PRs included, so that half is already caught on the PR board.
`ci-docs-path-filter.contract.test.ts` re-derives the list from the two test files in both
directions, so it cannot drift silently.

⛔ **CORRECTED 2026-10-02 (review round 3 CR-01): the exact set is SEVEN entries, not six.**
`src/__tests__/critical-regressions.test.ts` reads `.planning/config.json` from the real tree (the
two `workflow.use_worktrees` guards), and a config-only push took the short path because the
round-2 derivation scanned only the two test files the review had named. The rule the founder
approved, "files tests read count as code", covers it. The founder also confirmed on 2026-10-02
that the list may grow past the original three ("six files is fine"); that is approval for the

reads). It does not scan itself (its literals are fixtures), the classifier (the list's own home),
or the whole-tree walkers `check-planning-hygiene` and `verify-plan-anchors.mjs --pending`, which
always-on jobs (`frontend-lint`, `plan-anchor-verify`) already run on every event. The paragraph
above is kept as lineage.

**Same day, review round 2 SFH-04 (fixed, not a founder decision).** The short path is also taken
only when `before`'s own `frontend` check run concluded `success`, so a docs-only push can no longer

⛔ **CORRECTED 2026-10-02 (review round 3 WR-01 + SFH LOW-04; predicate decided by the
