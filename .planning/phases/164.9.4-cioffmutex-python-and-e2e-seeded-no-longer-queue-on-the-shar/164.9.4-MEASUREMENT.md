### Root cause of the `python` red — the D-15 40001 loop, which the lane stops masking

MEASURED 2026-09-27 on a private local-stack lane (not shared TEST):

1. **PostgREST retries an RPC that raises SQLSTATE 40001 without end, on BOTH the lane's image and
   PROD's version.** A throwaway lane-only function that bumps a sequence and then raises
   `serialization_failure` was called once through PostgREST. The sequence advanced 26,688 times in
   about 9 s on `postgrest:v14.5` (the version the linked PROD project reports) and 28,992 times on
   `postgrest:v14.7` (the lane's image). The client got no response (`HTTP 000`) on either. On
   the lane's own `v14.7` container the loop KEPT RUNNING after the client disconnected (the
   sequence went on climbing for at least 5 s more) and stopped only when that container was
   restarted; the `v14.5` container was removed straight after its reading, so this half is
   measured on `v14.7` only. Hosted PROD's behaviour is UNMEASURED here (no remote access), but it runs the same
   version.
2. **On shared TEST the test was always SKIPPED, never passing.** In comparand `36302599420` the
   fencing file's progress line reads `....................s.ss........sX.X.`; the lane run reads
   `....................F.ss........sX.X.`. Position 21 in collection order is
   `test_defer_compute_job_token_fence`, which is `s` on `main` and `F` on the lane. So the lane
   turned a SKIP into a FAIL, not a PASS into a FAIL.
3. **Why a skip on one side and a fail on the other: a 60 s timeout race.** `_rpc_retry_timeout`
   skips only when the exception text contains `timed out`. The admin client's httpx read timeout
   is 60 s. The lane's Kong gateway (`kong:2.8.1`, whose default upstream read timeout is also
   60 s; that default is read, not measured here) answers `504` with
   `The upstream server is timing out`, which supabase-py renders as `JSON could not be generated`,
   and that text does not contain `timed out`. When httpx fires first the test skips; when Kong
   answers first it fails. Run locally against the lane twice, httpx won both times:
   `SKIPPED … Last exception type: ReadTimeout` after 126 s and 131 s. In CI, Kong won.
4. **This is not the `tests/test_raw_5xx_census.py` 18≠12 failure** seen on PR #879. That file
   passed here; the only failure is the fence test.

**Not fixed in this phase, and why.** Every in-phase remedy is a waiver. Widening the skip match
to the 504 text re-hides the loop. Lengthening Kong's timeout so httpx always wins re-creates the
shared-TEST skip on purpose. Both are the green-that-measures-nothing D-05 forbids. The root-cause
fix is in the DB functions (`defer_compute_job`, and very likely `mark_compute_job_done` and
`mark_compute_job_failed`, which raise the same SQLSTATE on their stale-token paths). That is a
migration that auto-applies to PROD, and D-15 books it out of this phase as
`[164.9.4-DEFER-40001-RETRY-HANG]`. ⚠️ **D-15's premise "it changes no count" is contradicted by
this run:** it changed a skip into a failure. Routing this is a decision for the orchestrator
and the founder, not for this file.
