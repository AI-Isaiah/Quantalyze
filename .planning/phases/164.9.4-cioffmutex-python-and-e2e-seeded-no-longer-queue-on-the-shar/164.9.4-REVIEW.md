## Critical Issues

### CR-01: The predecessor gate dropped the `frontend` presence requirement, so a predecessor whose CI never ran or has not finished counts as proven

**File:** `scripts/classify-changed-paths.mjs:407-428` (`predecessorVerdict`), the doc comment at
`:321-339`, and the "proven" self-test rows at `:825-831`.

**Issue:**

The short path now needs only `runs.length >= 1` with every Actions check completed and in
{success, skipped, neutral}. Nothing requires that the **CI** workflow ran on `before`, or that it
finished. Measured with read-only `gh api` calls against this repository:

1. **Non-CI workflows attach checks to `main` SHAs.**
   - Commit `243219f0a9` carries check suites from six workflow runs:
     - `Contracts` (push);
     - `CI` (push);
     - `Nightly probes` (**schedule**), which produced its `npm-audit` and `preflight` checks;
     - `Main CI cancelled watcher` (**workflow_run**), three times.
   - Commit `53c3263037` likewise carries a `check` run from a suite created about 2.5 h after its
     CI.
   - `prod-prober.yml` and `phase-19-stability.yml` are hourly, so `main` HEAD routinely collects
     scheduled checks.
2. **The CI graph is not fully materialised mid-flight.**
   - In-flight commit `91f4239a19` returned 25 check runs, with `python` and `e2e-seeded`
     `in_progress`. `frontend` and `test-db-drift` were absent.
   - Completed siblings returned 27 to 33 runs.
   - A `needs:`-gated job has no check run until its dependencies finish.

**The fail-open sequences, each one returning `docsOnly: true`:**

- **(a) Skip trailer, measured to have happened in this repo.**
  1. Commit B merges with the skip trailer, so it gets no `CI` and no `Contracts` run. CLAUDE.md
     records this happening on 2026-09-17.
  2. An hourly scheduled workflow then runs green on B.
  3. A `.planning/`-only push C lands on B.
  4. `predecessorVerdict` sees one green Actions check, says
     `all 1 GitHub Actions check(s) non-red`, and C takes the short path.

  The result is a recorded green CI run on `main` over code that CI never ran. Under the round-2
  predicate this was `absent`, so the full corpus ran. **This pass regressed it.**
- **(b) The `needs:` race.**
  1. `before`'s CI has finished every job that exists. The last running dependency, such as
     `python`, has just completed.
  2. Its dependent (`test-db-drift`, then the `frontend` aggregator) has not been created yet.
  3. C's lookup lands in that gap and sees only green checks.
  4. C goes short. `test-db-drift`'s later VAC-08 red on `before` is then never re-checked by C's
     run.

  The window is seconds wide, but it is real.

**"It mirrors Railway" does not answer this.** CLAUDE.md (CI gate integrity, trap 1) records that
"Railway deploys anyway" when CI is absent, so a predicate that copies Railway's check-run gate also
copies that hole. The classifier's own header says the asymmetry is the whole argument: a wrong
`true` is "a gate-disable primitive". The self-test cannot catch this. Its "proven" row
`every Actions check green, one SKIPPED and one NEUTRAL` passes with no `frontend` present, so the
table pins the defect as correct.

**Fix:** keep "every Actions check non-red", and also require that CI ran to completion.
`frontend` is the `if: always()` terminal aggregator, it is a job name only in `ci.yml` (checked
with grep), and it is created only after every needed job finishes. A completed `frontend` check
run therefore proves that CI ran on `before` and finished. This still needs only `checks: read`.

```js
export const PREDECESSOR_REQUIRED_CHECK = "frontend"; // ci.yml's if: always() aggregator
// ...after the `runs.length === 0` guard:
if (!runs.some((r) => r.name === PREDECESSOR_REQUIRED_CHECK)) {
  return { ok: false, why: `absent: no '${PREDECESSOR_REQUIRED_CHECK}' check run, so CI has not run or not finished on that commit` };
}
```

Then update the self-test:

- Add `frontend` to the three "proven" rows.
- Add two "unproven" rows that expect code:
  - "green Actions checks but no `frontend`" (the mid-flight shape);
  - "only a scheduled workflow's checks" (the skip-trailer shape).
- Add a neuter leg that drops the presence check, and pin its FAIL line.
- Correct the doc comment's claim that "every Actions check run non-red" is sufficient.

## Warnings

### WR-01: A workflow run queued at the workflow level has no check runs, so a pending `supabase-migrate` on `before` is invisible

**File:** `scripts/classify-changed-paths.mjs:407-428`; trigger in `.github/workflows/supabase-migrate.yml`
(`on: push` with `paths: supabase/migrations/**`, and `concurrency: supabase-migrate-${{ github.ref }}`
with `cancel-in-progress: false`).

**Issue:**

- **The shape.** `supabase-migrate` serialises on one concurrency group for `main`. A migration
  merge B whose migrate run is queued behind an earlier, still-running migrate run has a workflow
  run but no jobs, so it has **no check runs**.
- **What the classifier sees.** If B's CI has finished green, a `.planning/`-only push C on B sees
  only green checks. C does not trigger `supabase-migrate`, because the path filter excludes it. So
  C goes short while `apply-test` has not run on B.
- **The self-test claims this case.** It names a red `apply-test` as a case the gate must refuse
  ("a RED check from ANOTHER workflow on the same commit"). A queued one passes.
- **Railway may be stricter.** The contracts registry entry for
  `analytics-deploy-tree-compare.contract.test.ts` records Railway "WAITING on the check-suite". So
  Railway may gate on check suites, which a queued workflow run does have. This is unmeasured
  live: I did not observe a concurrency-queued run's check-suite state.
- **Narrower than CR-01, and requires both:**
  - a migration merge;
  - an overlapping migrate run.

**Fix:** also read `repos/<repo>/commits/<before>/check-suites` (still only `checks: read`).
Require every `github-actions` suite to have `status == "completed"`, and treat a suite with
`latest_check_runs_count == 0` that is not completed as pending. Add a self-test row for it. If the
live shape cannot be measured, record that, and route the gap as a named limit in D-16 instead of
claiming "Railway's own gate".

### WR-02: The derivation's exclusion rules misdescribe one walker and add a second, global, unreasoned exclusion

**File:** `src/__tests__/contracts/ci-docs-path-filter.contract.test.ts:944-955` (prose), `:962`
(`NOT_SCANNED` entry), `:964-967` (`FIXTURE_COLLISIONS`), `:1031`.

**Issue:**

- **The prose is false for one walker.** The block comment says the excluded whole-tree walkers'
  "own always-on job already re-runs them on every event". That is false for
  `verify-plan-anchors.mjs`.
  - `plan-anchor-verify` carries `if: github.event_name == 'pull_request'` (`ci.yml`, the
    `plan-anchor-verify:` job).
  - It concluded `skipped` on push `53c3263037`.
  - On a push, nothing runs the `--pending` corpus except `frontend-test`, which a docs-only push
    skips.
  - The exclusion holds only because every first-parent `main` commit is a PR merge, and the PR run
    covers it. I measured 184 of 184 since 2026-09-01, none without a `(#N)` suffix.
  - That no-direct-push assumption is load-bearing, and it is written nowhere.
  - The classifier's own comment ("on every PR") is accurate. The contract file's ("on every
    event") is not.
- **A second exclusion mechanism.** `FIXTURE_COLLISIONS` exists alongside `NOT_SCANNED`, which
  contradicts "THE EXCLUSION RULE, kept in ONE place".
  - It drops `.planning/STATE.md` for **every** source, not only for the file whose fixture seeds
    it.
  - `STATE.md` is the planning file that changes most often. A future real reader of it in any
    test would be silently excluded, and the list would never learn it.
  - It is also not covered by the "still tracked" vacuity fence that `NOT_SCANNED` gets.

**Fix:**

- Reword the `NOT_SCANNED` reason for `verify-plan-anchors.mjs` to "plan-anchor-verify runs it on
  every PR (not on push); holds because every `main` commit is a PR merge". Put that assumption in
  D-16 too.
- Key the collision exclusion by `(source, path)`, i.e.
  `new Map([["src/__tests__/verify-plan-anchors.test.ts", ".planning/STATE.md"]])`, and give it a
  reason string.
- Fold it into `NOT_SCANNED`'s single place, or at least into its vacuity fence.

## Info

### IN-01: The derivation grammar has latent blind spots; none hides a reader today

**File:** `src/__tests__/contracts/ci-docs-path-filter.contract.test.ts:991-1056`

**Issue:** a grep across tracked JS, TS and Python found none of these in use today. Each would
hide a reader silently:

- **Literal shapes the scan misses.**
  - Backtick template literals, such as a path built inside a template string.
  - Literals where `.planning` does not start the literal, such as a `./` or `../` prefix, or a
    Python f-string that begins with a root placeholder.
  - A bare `.planning` root held in a variable and joined with a basename, or joined with a
    variable mid-path. Basename joins onto the root are deliberately skipped.
- **Python imports the closure walk misses.**
  - The import regex `from\s+([\w.]+)\s+import\s+([\w, ]+)` does not match the parenthesised form
    `from x import (`. 117 pytest files use that form, so those edges are dropped.
  - Relative imports are dropped too.
  - Re-running the walk with the parenthesised form fixed changed no `.planning`-mentioning file in
    the closure. So this is latent, not live.

**Fix:** make the scan fail closed. Any non-comment `.planning` occurrence in a scanned source that
does not resolve to a derived file should be a red, unless an allowlist entry gives a reason. Also
accept `\(?` in the Python import regex.

### IN-02: IN-02's "ONE name for every reader and writer" is true for `run.sh` only

**File:** `scripts/local-stack/run.sh:88-96`; `scripts/local-stack/sql-corpus-report.mjs:58`;
`scripts/local-stack/capability-probe.mjs:322`, `:444`

**Issue:** the lane has other readers of the handoff, and they do not honour `LANE_ENV_FILE`:

- `sql-corpus-report.mjs` hard-codes the default `.stack-env` path;
- `capability-probe.mjs` reads `STACK_ENV_FILE`.

If anyone does set `LANE_ENV_FILE` for `run.sh up`:

- the write, the guard and the teardown move together, as intended;
- those two readers still read the default path, and fail loud with "lane is not up".

No CI step sets it on `up` today, so nothing breaks.

**Fix:** narrow the comment to "every reader and writer in this script". Alternatively, have both
readers fall back through `LANE_ENV_FILE`.

### IN-03: Scheduled runs on `before` are a second, unstated cost of counting every workflow

**File:** `scripts/classify-changed-paths.mjs:321-339`; `164.9.4-REVIEW-FIX.md` "Consequence, accepted"

**Issue:**

- **The rule.** Every in-progress or red Actions check on `before` forces the full corpus, not only
  a red dispatch.
- **The cost.** The hourly `prod-prober` and `phase-19-stability` runs and the daily
  `Nightly probes` all attach to `main` HEAD. Measured: `Nightly probes` concluded `failure` on
  `243219f0a9`.
- **The effect.** A docs-only push landing while one of those is running, or after one went red,
  gets no short path. This is the safe direction, but the accepted-consequence note covers only
  dispatches.

**Fix:** extend the note, or, once CR-01's `frontend` requirement lands, consider scoping the
"every check non-red" half to suites whose event is `push` or `workflow_dispatch`. Record that as a
decision either way.
