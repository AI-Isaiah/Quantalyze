### CR-01: `TEST_READ_PLANNING_PATHS` missed `.planning/config.json`, and the contract scanned only two files

**Commit:** `f266de3b1`. Status: fixed. **Requires human verification** of the exclusion rule.

**What changed:**

- **The root cause.** The contract no longer hard-codes its sources. It now builds them from the
  whole tree:
  - every tracked `*.test.*` / `*.spec.*` file (vitest and Playwright);
  - every pytest file under `analytics-service/tests/`;
  - transitively, every tracked local module those files import (relative, `@/`, or a Python
    module under `analytics-service/`) or name by a `scripts/…` / `analytics-service/…` path
    literal (a spawned script).
- **The three read shapes it recognises.**
  - A full `.planning…` literal.
  - Adjacent literals joined by `,` or `/`, e.g. `join(ROOT, ".planning", "x")` and
    `ROOT / ".planning" / "x"`.
  - A non-root dir literal plus a basename literal from the same file. Basenames are never joined
    across files, and never onto the bare `.planning` or `.planning/` root.
- **It fails in both directions, naming the reading file.**
  - Calibrated: dropping `config.json` from the list goes RED, naming `critical-regressions.test.ts`
    as the reader.
  - Adding an unread `.planning/PROJECT.md` goes RED with `is on the list but no test reads it`.
  - The list was restored and `cmp`-checked after each run.
- **Vacuity fences.** At least 3 reader files and at least 6 derived paths. The walk must include a
  Playwright spec and a pytest file. Each import resolver must reach a known module:
  `scripts/check-planning-hygiene.ts` for JS and `analytics-service/scripts/phase12_kill_switch.py`
  for Python. Every excluded path must still be tracked.
- **The exclusion rule lives in one place, `NOT_SCANNED`, with a reason per entry:**
  - the contract file itself, whose literals are `judge()` fixtures;
  - the classifier, which holds the list itself, so scanning it would derive the list from the list;
  - `check-planning-hygiene` (test and script), a whole-tree walker that the always-on
    `frontend-lint` runs;
  - `verify-plan-anchors.mjs`, the `--pending` corpus walker that `plan-anchor-verify` runs
    unfiltered.
- **The measured result.** The derivation finds six real files across three reader files:
  - `config.json` from `critical-regressions.test.ts`;
  - `REQUIREMENTS.md` and `ROADMAP.md` from `lint-sql-gates.test.ts`;
  - `159-VERIFICATION.md`, `164.3-07-DEFERRED.md` and `164.3-07-PLAN.md` from
    `verify-plan-anchors.test.ts`.

  Together with the absent `164.3-07-SUMMARY.md` sibling, the list is **seven entries**. The
  self-test row is bumped from 6 to 7.
- **Documentation.** D-16 in CONTEXT.md, the ROADMAP 164.9.4 notes and the `[CI-DOCSPATH-01]`
  correction in TODOS.md all carry the count of seven. The founder's 2026-10-02 confirmation ("six

### WR-01 + SFH LOW-04: the predecessor gate read `frontend` only

**Commits:** `823d4f029`, then `af7a59618` and `bc0cca695`, both directed by the orchestrator. They
supersede the first commit's predicate. Status: fixed. **Requires human verification** that the live endpoint
behaves as below; that cannot be checked offline.

**Why the predicate mirrors Railway.** `docs/runbooks/railway-worker.md` (Recovery, step 2) records
that Railway gates on a commit's **check-runs**, not the combined status: "every workflow's check on
it must be non-red". The first commit read only the `CI` workflow's runs, so a red check from
another workflow on `before` was still invisible. The follow-up reads what Railway reads.

**What changed:**

- **The lookup.** `repos/<repo>/commits/<before>/check-runs?filter=latest&per_page=100`.
- **Which checks count.** Every check run with app slug `github-actions`, across all workflows and
  all events. `workflow_dispatch` is included because Railway counts those runs too. Non-Actions
  check runs, such as Vercel's, are ignored. **Every** Actions check run the lookup returns must be
  non-red. There is no cross-suite dedupe (`bc0cca695`, orchestrator decision): `filter=latest` already
  collapses re-run attempts inside a suite, and that is the only superseded case trusted. Whether
  Railway lets a newer suite hide an older red one is unmeasured, so it is not assumed.
- **The short path needs** at least one such check, and every one completed with a conclusion in
  {`success`, `skipped`, `neutral`}. Each of these runs the full corpus instead, with the reason
  printed:
  - pending;
  - `failure`, `cancelled`, `timed_out`, `action_required` or `stale`;
  - no Actions check run at all;
  - `total_count` greater than the returned page, which is refused rather than paged;
  - a check run for another commit;
  - no `check_runs` array;
  - a lookup that threw (a `gh` error or bad JSON).
- **Permissions.** `changed-paths` keeps `contents: read` + `checks: read`. The interim
  `actions: read` from `823d4f029` is gone. The contract pins the pair.
- **Self-test rows that must take the short path:**
  - all checks green, plus one `skipped` and one `neutral`;
  - a failed Vercel check, which is ignored;
  - an in-suite re-run (only the latest, green attempt is returned).
- **Self-test rows that must run the full corpus:**
  - a red `e2e` beside a green `frontend` (the shape of run `36892795002`);
  - a red check from another workflow;
  - a red dispatch check;
  - a newer red run superseding an older green one;
  - an older red run in another suite beside a newer green run of the same check;
  - each bad conclusion, pending, absent, Vercel-only, an API error, a malformed body, a truncated
    page and a foreign commit.
- **Updated in step with the code:** the fake-`gh` body and argv pin (the exact check-runs path),
  and neuter leg 5's expected FAIL lines.
- **Prose corrected**, as dated corrections with the originals kept as lineage:
  - the classifier doc comments;
  - the ci.yml comments in the job header and on the classify step;
  - the two ROADMAP `### Phase 164.9.4` notes;
  - D-16's SFH-04 paragraph;
  - the `[CI-DOCSPATH-01]` correction in TODOS.md.
- **Consequence, accepted.** If a dispatch on the predecessor SHA went red, every docs-only push on
  top of it runs the full corpus. A dispatch's full-history gitleaks scan does go red by
  construction (CLAUDE.md CI trap #2). That costs runner minutes and never opens a gap, because
  Railway would refuse that SHA too.

### SFH LOW-05: the self-test's in-process rows defaulted to the production `gh` reader

**Commit:** `3bfa656bc`. Status: fixed.

**What changed:**

- **The sentinel.** The default seam is now the module-level `defaultFetchCheckRuns`. `selfTest()`
  rebinds it to a sentinel that records the hit and throws, and restores it in `finally`.
- **Why the throw alone was not enough.** `predecessorVerdict` turns a throw into a code verdict,

  sentinel fails with the named line `self-test row reached the predecessor lookup without a seam (row N)`.
- **Calibration.** On a scratchpad copy with the ancestor guard dropped, the named FAIL appears for
  row 16. The contract's neuter leg 4 now asserts that line.

### IN-02: teardown deleted the default `ENV_FILE`, not the `LANE_ENV_FILE` the guard reads

**Commit:** `fe4ebfa02`. Status: fixed.

**What changed:**

- `run.sh` now resolves `ENV_FILE="${LANE_ENV_FILE:-${LANE_DIR}/.stack-env}"`. The `up` write,
  the `--assert-local-handoff` default, `down`, the failure trap and the self-test's
  "handoff survived teardown" check therefore all name one file.
- **Decision: the review's literal fix was not taken.** It suggested having `down` remove
  `${LANE_ENV_FILE:-$ENV_FILE}`. If the two paths diverged, that would stop deleting the file `up`
  actually wrote, which is the file the caller asked to have removed.
- `--assert-teardown`, the docker census, is unchanged.
- **Probed:**
  - `LANE_ENV_FILE` pointing at a loopback handoff passes the guard.
  - A missing one is a FATAL.
  - The default path is unchanged when the variable is unset, which is the case for every CI step
    today; each step that sets it uses the default value.
