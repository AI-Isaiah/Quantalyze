### The SFH-04 lookup against the real API

I ran these read-only checks against the repository's own data.

- **The endpoint and its response shape are right.** `commits/<sha>/check-runs?check_name=frontend`
  on the `origin/main` tip returns one `frontend` run, `completed` / `success`. That is the body
  shape `predecessorVerdict` parses.
- **Re-runs and multiple check suites are handled safely.**
  - On the most recently dispatched `main` SHA, the default filter and `filter=all` both returned
    TWO `frontend` runs from two check suites, one from the push and one from the
    `workflow_dispatch`. The default `latest` filter removes superseded re-run attempts within a
    suite. It does not collapse suites.
  - `predecessorVerdict` requires EVERY returned run to be `completed` and `success`. So a green
    dispatch cannot hide a red push `frontend`, and the reverse cannot happen either.
  - A failed attempt that was re-run green counts as green. That is an acceptable reading of
    "proven".
- **Pagination is not a risk.** The `check_name` filter leaves one run per suite, far below the
  default page size of 30.
- **The token is adequate.** The job-level block grants `checks: read`, which covers this endpoint.
  `contents: read` is restated. `GH_TOKEN` is set on the `classify` step only, and the contract test
  pins that.
- **A zero, forced, non-ancestor or absent `before` never reaches the API.** Branch creation and
  force pushes are refused before the lookup, and a self-test spy proves that.
- **Absent, pending and failed `frontend` all fail safe to code.**
  - **Absent:** the predecessor's CI has not created the aggregator's check run yet. The
    aggregator needs every other job, so this is the common state for most of the predecessor's
    run.
  - **Pending:** `status != completed`.
  - **Failed:** any conclusion other than `success`.

  Each is printed with its reason. `main()` exits 0 on every path. A 404 or a missing `gh` makes
  `execFileSync` throw, and the throw becomes `ok:false`.
- **The fake `gh` in the self-test is offline by construction.** It is first on `PATH`, it records
  its argv, and `finally` removes its temp dir.

### SFH-02's URL parse, edge by edge

`refuseNonLocalUrl`, which `assert_local` calls through `--refuse-nonlocal-url`:

| Input shape | Result | Why |
|---|---|---|
| userinfo, meaning the loopback host and port before an `@` with an external real host | refused | raw-authority `@` check, before any parser runs |
| a backslash in the authority | refused | raw-authority check |
| `localhost.<external>` or `127.0.0.1.<external>` | refused | hostname is not in the set |
| IPv6 `[::1]` | refused | not in the set; the old glob refused it too, and the lane never writes it |
| uppercase host or scheme | accepted | WHATWG lower-cases them, and the scheme strip regex is case-insensitive; still loopback |
| trailing-dot `localhost.` | refused | safe direction |
| port 80 | refused as "no port" | WHATWG drops a default port; safe direction, and the lane never uses 80 |
| numeric or short IPv4 forms (`127.1`, decimal) | accepted | they normalise to `127.0.0.1`, so the target is genuinely loopback |
| whitespace or control characters | refused | checked before parsing |

No refusal message echoes the URL, its host or its port. The executed matrix in
`local-stack-lane-wiring.test.ts` now has the userinfo row, built from parts. `LANE_DIR` is defined
before `assert_local` is reached.

## Critical Issues

### CR-01: `TEST_READ_PLANNING_PATHS` misses `.planning/config.json`, which `critical-regressions.test.ts` reads, and the contract that claims the list cannot drift scans only two files

**Files:**
- `scripts/classify-changed-paths.mjs:120-127` (`TEST_READ_PLANNING_PATHS`) and `:108-111` (the
  claim that the set was "measured against the two test files")
- `src/__tests__/contracts/ci-docs-path-filter.contract.test.ts`, describe
  `[164.9.4 WR-01] TEST_READ_PLANNING_PATHS matches the planning files the tests read`
  (`const SOURCES = ["src/__tests__/lint-sql-gates.test.ts", "src/__tests__/verify-plan-anchors.test.ts"]`)
- `src/__tests__/critical-regressions.test.ts:2896` and `:2911`, which run
  `JSON.parse(readText(".planning/config.json"))` against `REPO_ROOT`
- `TODOS.md` (the `[CI-DOCSPATH-01]` correction, which says "the six measured files")

**Issue:**

- **What the founder decided.** On 2026-10-02 the founder ruled that a push range touching a
  `.planning/` file that a `frontend-test` assertion reads is CODE.
- **The premise is bound.** `.planning/config.json` is tracked (`git ls-files`).
  `critical-regressions.test.ts` is in the node project (`vitest.node-env.ts:63`) under `INCLUDE`
  (`src/**/*.test.{ts,tsx}`). It runs only in `frontend-test`'s `npx vitest run --shard` (`ci.yml:463`),
  and that job carries `if: needs.changed-paths.outputs.docs_only != 'true'` (`:384`). No
  always-on job runs it.
- **What the fixer measured.** Only the two files the round-2 review happened to name. A grep for
  real-tree `.planning` reads across every `*.test.ts` under `src/` finds a third reader,
  `critical-regressions.test.ts`, with two assertions on `.planning/config.json`:
  - `workflow.use_worktrees stays true — a drive-by flip is a red PR, not a silent throughput loss`;
  - `the flag is a real boolean, so a stringified 'false' cannot pass as truthy`.
- **Measured at HEAD.**
  - `judge([".planning/config.json"])` returns `true`, so the path counts as docs-only.
  - `TEST_READ_PLANNING_PATHS.includes(".planning/config.json")` returns `false`.
  - So a push changing only that file takes the short path. `frontend-test` is skipped, and `main`
    records a green run on a commit whose own corpus is red. This is the exact misattribution
    WR-01 was fixed to stop: the red surfaces on the next unrelated code change.
- **The trigger is real.** That guard's own comment, and `git log -G use_worktrees`, record THREE
  unrelated flips of this flag. `.planning/config.json` is written by GSD tooling, so a
  config-only, `.planning/`-only commit is a natural shape.
- **The PR half of the same gap.** The PR filter also skips `frontend-test` on such a PR, so the
  guard whose stated purpose is "a drive-by flip is a red PR" bites on neither the PR nor the merge
  push.
- **Why the contract test cannot catch it.** The re-derivation that "cannot drift silently" reads
  only `SOURCES`, the same two files. A new real-tree reader in any other test file is invisible
  to it by construction. The fix report's "the exact set is SIX files" is therefore not a
  measurement of the class. It is a measurement of the two files that were already named.

**Fix:**
1. Add `".planning/config.json"` to `TEST_READ_PLANNING_PATHS`. Bump the self-test's
   `TEST_READ_PLANNING_PATHS.length === 6` row to 7, and update the doc comment, the TODOS
   correction and the ROADMAP sub-bullet ("six" becomes "seven").
2. Make the contract derive `SOURCES` from the tree rather than hard-coding it: every `*.test.ts`
   or `*.test.tsx` under `src/` whose text contains `.planning`. Then apply the existing literal
   and basename join, plus `FIXTURE_COLLISIONS`. Extend that set if a fixture-only literal in
   another file resolves to a real path; `check-planning-hygiene.test.ts`'s
   `.planning/phases/163/...` literals do not, because that path does not exist. Floor the derived
   SOURCES count at 3, so the contract fails if the scan stops finding readers.
   **Scope limits for the fixer:**
   - Exclude `ci-docs-path-filter.contract.test.ts` itself from `SOURCES`, so its own literals never
     feed the derivation.
   - Do not treat whole-tree walkers as readers of every planning file.
     `check-planning-hygiene.test.ts` runs `runCheck(process.cwd())` over every tracked file. It is
     excluded for the same reason the `--pending` scans are: `frontend-lint`, which is always on,
     runs the same hygiene script on every event.
   - The other root-level `readdirSync` walkers I found do not enter `.planning/`:
     `critical-regressions.test.ts:561` walks `.github/workflows`, `self-referential-oracle.test.ts:455`
     walks its own corpus dir, and `drift-check-scripts.test.ts` walks SQL snapshot dirs.

   The derivation:

```ts
const SOURCES = execFileSync("git", ["ls-files", "-z", "src/**/*.test.ts", "src/**/*.test.tsx"], { cwd: ROOT, encoding: "utf8" })
  .split("\0").filter(Boolean)
  .filter((f) => readFileSync(join(ROOT, f), "utf8").includes(".planning"));
expect(SOURCES.length, "vacuity fence: fewer real-tree .planning readers than measured").toBeGreaterThanOrEqual(3);
```

### WR-01: The SFH-04 predecessor gate reads `frontend` only, so a docs-only push still turns the board green over a red non-aggregated, docs-filtered job

**Files:**
- `scripts/classify-changed-paths.mjs:304-310` (`PREDECESSOR_CHECK_NAME = "frontend"` and its doc
  comment, which says it is "the one verdict that covers every gate on a push to main")
- `scripts/classify-changed-paths.mjs:361-376` (`predecessorVerdict`)
- `.github/workflows/ci.yml`: the jobs `e2e` (`if:` at `:5651`) and `lighthouse-mobile`
  (`:6675`). Each is `docs_only`-filtered, and neither is in the `frontend` aggregator's `needs:`
  (`:3556`). `knip` is also filtered and outside the aggregator, but its step ends in `|| true`
  (`:1424`), so it can never redden the run and is not part of this finding.

**Issue:**

- **What the fix assumes.** The rationale holds that a red `python` reaches `frontend` through
  `test-db-drift`'s skip arm. That is correct. But `frontend` is not the CI run's verdict. Two
  docs-filtered jobs that can fail sit outside it.
- **Measured.** CI run `36892795002` (a `workflow_dispatch` on `main`) concluded `failure`, its
  failing job was `secret-scan`, and its `frontend` concluded `success`. So `frontend: success` and
  "CI green" demonstrably diverge in this repo.
- **The bypass, for `e2e`.**
  1. Push A, a code commit, has `e2e` red and every aggregated job green. A's `frontend` is
     `success`, but A's CI run is `failure`.
  2. Push B, docs-only, sees `frontend: success` on A and takes the short path.
  3. `e2e` is skipped on B, so B's CI run concludes `success` over A's code.

  Whatever reads "main CI green" bound to HEAD's SHA, Railway included, is told yes. That is the
  SFH-04 shape on a narrower trigger.
- **Why this is a WARNING and not a BLOCKER.**
  - `e2e` and `lighthouse-mobile` are not merge gates. `lighthouse-mobile` is explicitly ADVISORY.
  - The four red `main` push runs I sampled all failed through `frontend`.
  - The earlier rounds disagree about whether Railway deploys a `.planning/`-only push.
- **Two statements are false regardless:** the doc comment's "the one verdict that covers every
  gate on a push to main", and the fix report's "Why `frontend` alone is enough".
- **Not new.** `secret-scan` is not docs-filtered, but it scans only the pushed range. So it never
  re-checks A on any event, and it never did. This is recorded as context, not as a regression.

**Fix:** pick one option. Each fails safe in the same way.

- **(a) Read the run, not the check.** Gate on the CI workflow run(s) for `before` with
  `event=push`:

  `gh api "repos/$GITHUB_REPOSITORY/actions/runs?head_sha=<before>&event=push"`

  Then require every run named `CI` to be `completed` with `success`. This needs `actions: read` on
  `changed-paths`. Update the contract pin to `actions: read`, `checks: read` and
  `contents: read`, or swap `checks` for `actions`.
- **(b) Widen the set of required checks.** Make `PREDECESSOR_CHECK_NAME` a set, `frontend` plus
  every docs-filtered job outside the aggregator that can fail the run (`e2e`, `lighthouse-mobile`). Derive that
  set in the contract test from `ci.yml` (filtered jobs minus aggregator needs), so it cannot lag.

With either option, correct the doc comment's "every gate" claim.

**Issue:** the comment says `cat-file -e` on a missing object "exit[s] 1 with no stderr". The code
calls `cat-file -e <sha>^{commit}`. Measured at HEAD, that form prints a `fatal: Not a valid object

**Fix:** reword the comment to say that `cat-file -e <sha>^{commit}` prints a `fatal:` line, and
that only `merge-base --is-ancestor` on a non-ancestor exits 1 with nothing.
