## SFH-01 (MEDIUM): build-guard arms (ii) and (iii) fail open on a grep error

**Location:** the `e2e-seeded` job, step `Verify build inlined real test-Supabase URL`, arms (ii)
`placeholder.supabase.co` and (iii) `https://[a-z0-9]{20}\.supabase\.co`. Both arms are new in this diff (D-09).

**Issue:** arm (i) is written `if ! grep -r -l ... .next/static .next/server > /dev/null 2>&1`, so
a grep error fails it closed. Arms (ii) and (iii) are written `if grep ...; then exit 1; fi`, so
exit status 2 (an error) reads exactly like exit status 1 (no match), and the step prints
"no placeholder or hosted-project URL". stderr goes to `/dev/null`, so nothing in the log shows that
the scan was partial.

GNU grep's documented exit status is 0 for a selected line, 1 for none and 2 for an error. A match
plus an error still returns 2 unless `-q` is given (`-s` only silences the messages). So if a
placeholder or hosted-project URL is present AND any read error happens in the same scan, the arm
passes.

**Hidden errors:** one of `.next/static` / `.next/server` missing (arm (i) can still pass on the
other directory); an unreadable file or a dangling symlink under `.next/`; any I/O error during
the scan. In each case the "this job builds against its own lane, never a shared or production
project" assertion stays green on a bundle that it never fully read.

**User impact:** reaching it requires a malformed build tree, so the likelihood is low. But this is
the one step that proves the seeded specs run against the lane and not a hosted project, and its
negative arms are the half of it that can fail without anyone noticing.

**Recommendation:** check that both directories exist, then treat rc 2 as fatal:

```bash
for d in .next/static .next/server; do
  [ -d "$d" ] || { echo "::error::$d missing after the build - cannot verify the inlined URL"; exit 1; }
done
rc=0; grep -r -l -F --include='*.js' --include='*.json' 'placeholder.supabase.co' .next/static .next/server > /dev/null || rc=$?
case "$rc" in
  0) echo "::error::(ii) the rebuild inlined the placeholder Supabase URL ..."; exit 1 ;;
  1) ;;
  *) echo "::error::(ii) grep could not scan the build output (rc=$rc) - refusing to call it clean"; exit 1 ;;
esac
```

(Same shape for (iii). Drop `2>&1` so the grep error itself reaches the log.)

## SFH-02 (MEDIUM): the D-04 API_URL guard is a prefix glob that admits a non-loopback host

**Location:** `scripts/local-stack/run.sh`, `assert_local` (pre-existing), which this phase reuses
through the new `assert_local_handoff` / `--assert-local-handoff` as the D-04 loopback guard for
both jobs' `Lane handoff - assert loopback, then export the URL and keys to later steps` step.

**Issue:** `assert_local` matches `http://127.0.0.1:*|http://localhost:*`. Measured:
a URL whose userinfo part is the loopback host and port and whose real host is an external domain (scheme, then `127.0.0.1:54321`, then an at-sign, then the external host) is ACCEPTED by that `case`, and `new URL()` resolves its
hostname to `evil.example.com`. The `127.0.0.1:54321` part is userinfo. This is the same class that
review 164.4.2 WR-08 removed from the DSN path. That is why `DB_URL` goes through
`capability-probe.mjs --refuse-nonlocal-dsn`, a parse-based check. The API_URL half of the D-04
guard still uses the glob WR-08 replaced.

It also chains into `next.config.ts`. `withConfiguredSupabaseOrigin` would derive
`http://evil.example.com` and `ws://evil.example.com` into `connect-src`, because that host passes
`DERIVED_CSP_HOST`. Both the build and the CSP would then point at a host the guard claimed was
loopback.

**Hidden errors:** a corrupted or tampered `.stack-env`, or a future CLI `status` format that emits
credentials in the URL. Either one passes the guard and reaches the seeder (which carries the
service key), the build and the browser.

**Honest exploitability:** the value comes from the lane's own boot (`supabase status`), and since
this phase neither job carries a secret. There is no realistic trigger today. I filed it at MEDIUM
because the guard is now the only thing that makes D-04 true for API_URL, and it can be bypassed by
construction.

**Recommendation:** parse it instead of globbing. Assert that `new URL(v).hostname` is in
{`127.0.0.1`, `localhost`, `[::1]`}, that `username`/`password` are empty and that `protocol` is
`http:`. The cleanest home is a `--refuse-nonlocal-url` sibling of `--refuse-nonlocal-dsn` in
`capability-probe.mjs`, called the same way, so the repo keeps ONE loopback parser per shape.

## SFH-03 (MEDIUM): the handoff guard checks one file and the step exports from another

**Location:** both jobs, step `Lane handoff - assert loopback, then export the URL and keys to later steps`.

**Issue:** the step runs `bash scripts/local-stack/run.sh --assert-local-handoff` with NO
argument, so `assert_local_handoff` reads run.sh's hard-coded `ENV_FILE="${LANE_DIR}/.stack-env"`.
The very next lines read the values they export from `${LANE_ENV_FILE}`, which comes from the
step's own `env:`. run.sh has no `LANE_ENV_FILE` seam (measured: 0 hits under
`scripts/local-stack/`). Today the two paths name the same file only because the YAML value happens
to equal run.sh's default. If either one moves, the guard asserts a file the job does not consume,
and the export reads an unasserted file. The `2>/dev/null ... || true` on the export's `sed`
reads would then also hide an unreadable file: the `-z` checks fire, but they name "no API_URL
line" instead of the real cause.

**Hidden errors:** a non-loopback URL in the exported file passes because the asserted file is
clean. A missing exported file is reported as a missing line.

**Recommendation:** assert exactly the file you export from:

```bash
lane_env_file="${LANE_ENV_FILE:-scripts/local-stack/.stack-env}"
bash scripts/local-stack/run.sh --assert-local-handoff "${lane_env_file}"
```
