## SFH-04 (HIGH, new): a docs-only push turns `main` green over a red code commit, and Railway deploys that code

**Location:**

- `scripts/classify-changed-paths.mjs:205`: `classifyPushRange`, which diffs only `before..HEAD`.
- `scripts/classify-changed-paths.mjs:602`: the `push` branch of `main()`.
- `ci.yml`, job `changed-paths`, step `id: classify` (`PUSH_BEFORE_SHA`, `:201`).
- `ci.yml`, job `frontend`, step `Verify all frontend-* jobs succeeded`: the uniform docs-only arm (`:3629`).

**Issue:** the push path judges only what the pushed range changed. It never asks whether the code
under that range was ever proven. Take two pushes to `main`:

1. Push A is a code commit, and its CI concludes red or is still running.
2. Push B is `.planning/`-only on top of A.

B's range `A..B` is docs-only, so B gets the short run: every filterable job is skipped and the
aggregator's uniform arm tolerates each skip. The result is `All frontend-* jobs succeeded.` on B's
SHA. Nothing in that run tested a byte of A's code, and the code on B is exactly A's.

Before WR-01 every push ran the full corpus, so a deterministic defect in A reddened B too.

**Why Railway turns this into a deploy, not just a misleading badge:**
`analytics-deploy-verify.yml:150` records a measurement from 2026-09-13. A merge that changed only
`.planning/` files did not cause Railway to decline the deploy. Railway QUEUED one and held it
on the check suite. So Railway deploys on docs-only pushes, gated only on that push's own suite.
B's short green suite releases a deploy of A's `analytics-service` tree, and that tree was red, or
never finished.

The "Railway SKIPS the deploy when main CI is red" protection (CLAUDE.md, the
`ci-docs-path-filter` contract's own message) is bypassed by the next docs commit.

**Likelihood:** high in this repo. A code merge followed minutes later by a
`docs(...): close <phase>` merge is the routine shape, for example #925 then #926, and #919
then #921. A red predecessor is not hypothetical either: the AFTER table in
`164.9.4-MEASUREMENT.md` records a red `python` on the lane.

**Hidden errors:** a genuine red on A, whether pytest, the seeded specs, VAC-08 or a coverage
drop. An A run that is still in progress when B's `changed-paths` runs. An A run that was
cancelled (`main-ci-cancelled-watcher.yml` files an issue, but B's green still releases the
deploy).

**User impact:** `main` HEAD reads green while its code is red. Anyone who checks "is main green"
bound to HEAD's SHA, as the repo's own rule asks, is told yes. Railway deploys code that CI
rejected.

**Fix:** make the short path conditional on the predecessor's verdict, still failing SAFE to code.

- In `classifyPushRange`, after the ancestor check, read the conclusion of the `frontend` check on
  `before`. For example, `gh api repos/{repo}/commits/{before}/check-runs?check_name=frontend`
  with `GH_TOKEN` and `checks: read` on the `changed-paths` job.
- Return `code("predecessor <sha12> has no successful frontend verdict (<conclusion|pending|absent>)")`
  for anything other than `success`. That covers red, pending, cancelled, absent and any API
  error.
- Add a self-test row for each of: a red predecessor, a pending predecessor and an API failure.
  The verdict should come through an injectable fetch seam, the same way `cwd` is injected for git.

That keeps the short path for the common case, where B lands after A has gone green, and it never
reddens `changed-paths`. A pending A costs B a full run, which is the safe direction.

If the founder prefers to accept the gap rather than fix it, record that decision. The
aggregator's uniform arm should then print the before-SHA, so the green line says which commit it
did not re-test.

## SFH-02 (MEDIUM, carried, now MEASURED): the D-04 API_URL guard accepts a userinfo-smuggled host

**The test gap:** the executed refusal matrix in `local-stack-lane-wiring.test.ts` (the `it` titled
`run.sh --assert-local-handoff refuses a non-loopback handoff and never echoes it`) has a
"loopback-prefixed API host" row, but no userinfo row. Adding one turns the file RED today.

**Fix:** as in round 1. Parse instead of globbing. Add a `--refuse-nonlocal-url` sibling to
`--refuse-nonlocal-dsn` in `capability-probe.mjs` that asserts these four things:

- `protocol === "http:"`
- an empty `username` and `password`
- `hostname` in {`127.0.0.1`, `localhost`, `[::1]`}

Call it from `assert_local`, which also covers `write_env_handoff`, and add the userinfo row to
the executed matrix. Describe the row in words in this file and in commit messages, never as a
literal URL (see `c5431f029`).

## SFH-03 (MEDIUM, carried, unchanged): the handoff guard asserts a default path and the export reads `LANE_ENV_FILE`

**Location:** both jobs, the same handoff step. `ci.yml:5175-5176` covers `python` and
`ci.yml:6174-6175` covers `e2e-seeded`.

**Issue:** this is unchanged from round 1. The guard is invoked with no argument, so it reads
`run.sh`'s `ENV_FILE`. The next line exports from `${LANE_ENV_FILE}`. The two paths agree today
only because the YAML value equals the default. If they diverge, the guard asserts one file and the
job exports another, unasserted one. The `2>/dev/null … || true` on the export's `sed` then reports
an unreadable file as "no API_URL line".

**Fix:** move the `lane_env_file=` line above the guard and call
`bash scripts/local-stack/run.sh --assert-local-handoff "${lane_env_file}"`. It is a one-line move
in each job. The order pin in `local-stack-lane-wiring.test.ts` still holds afterwards, because
the seam stays before the first `GITHUB_ENV` line.

## LOW-01: after any pre-boot failure, the lane teardown adds a second, misleading red

**Location:** step `Tear down the lane (and PROVE nothing survived)` in both jobs (`ci.yml:5249`,
`:6573`).

**Issue:** the step is `if: always()` and runs `run.sh down` under `set -euo pipefail`.
`cmd_down` calls `supabase stop` unconditionally, and `supabase/setup-cli` comes AFTER several
steps that can fail first:

- in `e2e-seeded`: npm ci, the Playwright install and the hydration self-test;
- in `python`: pip install and the mypy gate.

When one of those fails, teardown exits 127 on `supabase: command not found`. It is not silent,
but the second red step names the lane as broken when the lane never booted, which sends triage
the wrong way.

**Fix:** in the teardown step, run `run.sh down` only when `command -v supabase` succeeds.
Otherwise print `lane never booted (no supabase CLI on PATH), nothing to stop`. In both cases,
still run `--assert-teardown`, so the docker census stays the real proof.

## LOW-03: the push classifier's fail-safe arms drop git's stderr

**Location:** `scripts/classify-changed-paths.mjs:214` and `:229` (the `catch {}` arms of
`classifyPushRange`).

**Issue:** the direction is correct: each arm emits `docs_only=false` and exits 0. But the bare
`catch` discards the error that `git()` deliberately pipes into it (review 164.4.2 IN-02). So the
log names the class of failure ("git diff over the range failed") and not its cause. A recurring
cause would then quietly cost every docs-only push a full run, with nothing pointing at why.

**Fix:** `catch (e)` and append the first line of `e.stderr` (git's `fatal:` line, which names refs
and paths but no secret) to the reason.
