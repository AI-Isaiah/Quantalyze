## Summary

`python` is a clean move. Measured locally on the lane at this worktree's `analytics-service/` tree, which is byte-identical to the tree `main` CI measured at `35d1d412`: all nine live-DB modules run on `scripts/local-stack/run.sh up`, with 213 passed and 6 skipped. Those 6 skips are the same six reasons the suite skips anywhere. The full suite gave 6357 passed, 70 skipped, 2 xpassed and 1 failure, at 91.57% coverage. The failure is a 15 s subprocess timeout under host load 18-28 and does not touch the DB. The BEFORE for the same tree is 6356 passed, 72 skipped, 2 xpassed at 91.57%. The pytest step needs only two env values, `SUPABASE_TEST_URL` and `SUPABASE_TEST_SERVICE_KEY`, plus `CI`, and the lane's `.stack-env` supplies both. No python test needs shared TEST, so D-07's default of zero held.

`e2e-seeded` has one hard blocker, and it is the app, not the stack. `next.config.ts` ships a CSP whose `connect-src` allows only `'self' https://*.supabase.co wss://*.supabase.co https://plausible.io`. The login form is a `"use client"` component that calls `signInWithPassword` from the browser. So once the bundle is inlined with the lane's `http://127.0.0.1:<port>` URL, Chromium refuses every browser-side Supabase call. A probe measured this with the exact header string. Every seeded spec that logs in would then FAIL, not skip. The lane itself serves the rest: the demo seeder completed against it in 2 s, `discovery_categories` / `compute_job_kinds` / the sentinel profile are all replayed reference data, 40 back-to-back password sign-ins all returned 200, and no seeded spec touches storage, edge functions or pg_net.

**Primary recommendation:** One PR, five plans in four waves.
1. A BEFORE `MEASUREMENT.md` and a root-cause CSP fix run in parallel. The CSP fix derives an extra `connect-src` origin from `NEXT_PUBLIC_SUPABASE_URL` at build time. In production it only restates what the `*.supabase.co` wildcard already allows.
2. Then `python` moves.
3. Then `e2e-seeded` moves, with the holder-set pins re-subjected to an EMPTY `ci.yml` holder set in the same commits.
4. Then the docs and currency plan lands.

Every lane step is copied from `frontend-local-stack` / `sql-tests`, not abstracted.

### Pattern 1: copy the lane block, do not abstract it
**What:** each job carries its own copy of these five steps from `frontend-local-stack`:
1. `Baseline currency - name the migrations the lane replays on top of the dump` (`run: bash scripts/local-stack/run.sh --check-currency`)
2. `supabase/setup-cli` `version: 2.98.2`
3. `Log in to ghcr.io before the CLI pulls its images`
4. `Install psql client (the lane loads the baseline through it)`
5. `Boot the local-stack lane (Supabase CLI stack + committed baseline)` (`run: bash scripts/local-stack/run.sh up`)

It also carries the `Tear down the lane (and PROVE nothing survived)` step with `if: always()`.

**Why a copy:** `local-stack-lane-wiring.test.ts` "…all three lane-booting CI jobs run the currency seam before the boot" matches those exact `run:` lines per job, and that is precedent (Claude's Discretion answer).

**Job wiring:**
- Add `packages: read` to the job `permissions:` (ghcr step).
- Drop `actions: read`, which only the ordering wait used (D-08).

**`python`'s working directory:** its `defaults.run.working-directory: analytics-service` stays; `ci-mypy-strict-surface` reads that block. Give each lane step `working-directory: ${{ github.workspace }}` so its `run:` line stays byte-identical to precedent. `run.sh` also `cd`s to the repo root itself (`cd "$REPO_ROOT"`, run.sh after `REPLAY_SET_FILE`).

### Pattern 2: loopback assertion reusing the existing guards (D-04)
- **DB_URL:** `LOOPBACK_DSN="$db_url" node scripts/local-stack/capability-probe.mjs --refuse-nonlocal-dsn`. This is the ONE parse-based rule `run.sh load_baseline` and `sql-tests` already call; it exits 1 on refusal and never prints the DSN [VERIFIED: capability-probe.mjs:187-217, :357-362].
- **API_URL:** `run.sh`'s `assert_local` (the case `http://127.0.0.1:*|http://localhost:*`) is internal. Recommended: expose it through a new `run.sh` seam (e.g. `--assert-local-handoff`) that reads `.stack-env`, runs `assert_local` on `API_URL` and the probe on `DB_URL`, and prints no value. That REUSES the guard rather than inventing a second glob. Planner's discretion. The alternative is a verbatim `case` in each job, which D-04 discourages.
- **Where:** in the step that hands the values to the tests, before any DB-touching step.

**D-10 answer (asked explicitly by CONTEXT):** yes. ### Pattern 3: hand the lane's values to the tests without touching the pytest line
- A step reads `.stack-env` (same `sed -n 's/^API_URL="\{0,1\}\([^"]*\)"\{0,1\}$/\1/p'` idiom `sql-tests` uses) and asserts loopback.
- It emits `::add-mask::` for the keys. They are the CLI's public demo keys, but masking is free.
- It appends to `$GITHUB_ENV`:
  - `python`: `SUPABASE_TEST_URL`, `SUPABASE_TEST_SERVICE_KEY`.
  - `e2e-seeded`: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `TEST_SUPABASE_URL`, `TEST_SUPABASE_ANON_KEY`, `TEST_SUPABASE_SERVICE_ROLE_KEY`.
- The pytest step's `run:` stays byte-identical to the `Makefile` `test:` target. Its `env:` loses the `secrets.*` / `vars.E2E_TEST_DB_CONFIGURED` ternaries.
- **`CI`:** set `CI: 'true'` unconditionally, or drop the override so GitHub's default `CI=true` applies (`[ASSUMED]`, A3). Today `CI` is demoted to `''` when the var is unset. With the lane always present that demotion only weakens `_need_supabase()`'s hard-fail, so removing it is a tightening, not a widening.

### Anti-Patterns to Avoid
- **A composite action or reusable workflow for the lane.** It breaks the literal-`run:`-line pins and diverges from the three precedents.
- **Putting `run.sh up` into `python` without `working-directory`.** A bare relative `scripts/…` under `analytics-service` exits 127. This repo has a dated record of exactly that (`mutex-dead-holder-verdict.test.ts` Test 3b).
- **Keeping `vars.E2E_TEST_DB_CONFIGURED` in the python pytest env.** It no longer gates anything real.
- **Adding `-rs` or `--junitxml` to the pytest line to "measure" skips.** D-05 requires the line byte-identical.
- **Exporting the lane DSN as `TEST_SUPABASE_DB_URL`.** It silently un-skips 20+ psycopg modules (scope creep) and reuses the name of the shared-TEST secret.

## Common Pitfalls

### Pitfall 1: e2e-seeded goes red across the board on the CSP
**What goes wrong:** every login is refused by `connect-src`.
**How to avoid:** land the CSP remedy in an earlier wave than the `e2e-seeded` move.
**Warning signs:** `violates the following Content Security Policy directive` in the Next server or browser console; `loginAs` `waitForURL` timeouts.

### Pitfall 2: the python lane steps run from `analytics-service/`
**What goes wrong:** exit 127, or `run.sh` works but the literal-`run:` pins do not match.
**How to avoid:** step-level `working-directory: ${{ github.workspace }}` on every lane step.

### Pitfall 3: holder-set pins go vacuous instead of red
**What goes wrong:** `DB_JOBS = []` makes the `for` loops pass trivially.
**How to avoid:** replace them with an explicit empty-set pin, neuter it (put `61616158` back into one job), and observe RED.

### Pitfall 4: the verdict floor and Test 3b are edited "to pass"
**How to avoid:** re-measure with `grep -c` per `TARGET_FILES` entry after the move, and write the per-file breakdown into the dated comment (D-06).

### Pitfall 5: D-09's verify step prints a host
**What goes wrong:** the retargeted check must fail on a TEST or PROD host without naming one in a public log.
**How to avoid:** assert (i) the loopback `host:port` of `API_URL` IS inlined; (ii) `placeholder.supabase.co` is NOT; (iii) no `https://<20-char-ref>.supabase.co` shape is inlined. For (iii) use a regex and never echo the match. ⚠️ Whether the bundle contains a benign `supabase.co` string (for example from the supabase-js source) is UNMEASURED. Measure it on the first CI build before hardening (iii).

### Pitfall 6: CLI skew
**What goes wrong:** local measurements used CLI 2.84.2; CI uses 2.98.2. The `.stack-env` names the jobs consume (`API_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY`, `DB_URL`) are already consumed in CI under 2.98.2, but the rest of the local numbers are not CI-bound.
**How to avoid:** take AFTER numbers only from the SHA-bound CI run (D-11).

### Pitfall 7: `pg_cron` on the lane during a 15-min pytest
**What goes wrong:** the lane registers 15 cron jobs, including `match_engine_cron` (`0 * * * *`), which would `net.http_post` to the production analytics URL seeded in `system_settings`.
**Why it is safe today:** `match_engine_cron_tick()` first reads the vault key and `RAISE`s `'analytics_service_key missing from vault — refusing to send a null header'` when absent, and `vault.secrets` count on the lane = `0` [VERIFIED: `pg_get_functiondef` + `select count(*) from vault.secrets` on the lane].
