## Store-fault fallbacks judged safe (no finding)

- `begin_claim` -> None: the read becomes `_read_bybit_range` for the whole range, the pre-store
  read. It either returns a complete list or raises `TruncatedTradeRead`; it can never return a
  partial list, and it never defers or marks DONE on its own. Safe for integrity (see S-2 for the
  user-facing side).
- `load_window` -> None (malformed, mismatched count, wrong version, expired, or a client fault):
  the window is re-read live. `_meta_of` and `load_window` both demand every chunk 0..N-1, one
  `chunk_count`, one `window_end_ms`, the current version, an unexpired `expires_at`, and
  `len(trades) == n_trades`. A half-written window is never used.
- `save_window` -> False: the window's trades stay in this claim's output and the window is simply
  unstored. Progress is not recorded for it. A cancelled or crashed write leaves a chunk set whose
  length differs from `chunk_count`, which `_meta_of` rejects.
- `record_progress` / purges swallowed: worst case is a late purge (7-day expiry is the backstop)
  or a pessimistic stall count, both fail-closed (a job stops by name, nothing is written).
- `TradeReadDeferred` / `TradeReadStalled` ordering: both arms precede the generic `except
  Exception`; `_crawl_whole_account` handles both before its generic arm; nothing between
  `_fetch_bybit_trades` and the handler swallows them (`_fetch_trades_with_pagination` is awaited
  directly at the single call site).
- Store projection vs the replay: the replay reads `symbol, side, amount, price, cost, fee,
  timestamp` and `info.instType`, and the `info` read is bypassed for Bybit
  (`_resolve_perp_amt_base`, `venue != "okx"`), so dropping `id` / `info` does not change output.
- `asyncio.CancelledError` is not caught anywhere in the new code (`except Exception` only).
- Sweep: stamps the time before the purge, never stops the watchdog loop, logs class only.
- Probe: the new fields are validated by the closed-schema validators, and `run()` refuses
  (exit 2, stderr message) before any decrypt when the deployed rebuild lacks a name it reads.

## S-1 (MEDIUM, data integrity) - a window that ended on an uncertain stop is stored as complete and reused for up to 7 days

- Where: `analytics-service/services/equity_reconstruction.py:758-759` (empty page ends the
  window with a bare `return`), `:767-778` (full page with no cursor: one WARNING, window ends),
  and the unconditional save at `:979` (`if storable and await store.save_window(...)`).
- Hidden failure: `_read_bybit_window` returns `None` whether the window ended because the venue
  ran out of trades or because the last page was a FULL page that carried no `nextPageCursor`
  (the docstring itself says a truncated response and a legitimate final page of exactly 100 rows
  are indistinguishable there). Before this phase that was an accepted single-pass risk: the next
  rebuild re-read the venue and healed it. Now the same window is written to the store as
  "complete" and every later claim and every later job for the key within 7 days (the stall
  retry, the daily re-enqueue after a `TradeReadStalled`) loads it instead of re-reading. A window
  cut at a full page therefore stays short for the whole life of the read, and the allocator
  history written when the read finishes is missing those fills with no signal beyond the one
  WARNING already logged for it.
- Impact: wrong allocator equity history (positions and cash from missing fills) persisted as a
  whole rebuild; a retry cannot correct it until the 7-day expiry or the DONE purge.
- Minimal fix: have `_read_bybit_window` return a bool that is False on the full-page-no-cursor
  exit (True on every other normal exit), and store the window only when it is True:
  `ended_clean = await _read_bybit_window(...)` ... `if storable and ended_clean and await
  store.save_window(...)`. An unclean window is still read live and used in this claim exactly as
  layer 1 uses it, so no read is refused that was not refused before; it is only not frozen.

## S-2 (MEDIUM, user-facing) - a store fault on a big account silently reverts to the refusal this phase removes, under a misleading permanent token

- Where: `analytics-service/services/equity_reconstruction.py:937-938` (`state is None` ->
  `_read_bybit_range`), fed by `analytics-service/services/trade_read_store.py:531-537`
  (`begin_claim` catches every `Exception`, logs one WARNING, returns None).
- Hidden failure: for the account sizes this phase exists for, the layer-1 read raises
  `TruncatedTradeRead`, which is a `ccxt.BadRequest`, so `classify_exception` calls it permanent
  and the forced path refuses `account_key_read_failed` (unforced: FAILED permanent). So a
  transient store outage at claim start, or a persistent defect inside `_begin_claim` (a
  `TypeError`/`KeyError` on a malformed state row is inside the same `except Exception`), turns
  an account that would have been deferred and resumed into a permanent failure. The only trace
  is a WARNING with a class name; nothing separates it from a genuine venue truncation in the
  refusal token, the audit message or Sentry, and a forced rebuild is not re-crawled automatically
  (PD-I). The deploy-order case documented in the handler is the benign instance; the same path
  also fires for a real fault.
- Impact: a large account is stranded exactly as before the phase, with a refusal that blames the
  venue read. No wrong data is written (the failure is loud and nothing persists).
- Minimal fix: in the `state is None` branch, let the layer-1 read run but convert a
  `TruncatedTradeRead` it raises into a transient class, so the queue retries once the store is
  back instead of ending permanently:
  `try: return await _read_bybit_range(...)` /
  `except TruncatedTradeRead: raise ccxt.RequestTimeout("trade read store unavailable; retry") from None`
  (static message, no venue text). Small reads that finish under layer 1 are unaffected.

## Noted, below the reporting bar (not findings)

- `record_progress` swallowing a failed reset can make a progressing job count as stalled and
  stop by name after three claims (fail-closed, nothing written).
- A forced and an unforced job on the same key alternate `last_job_id` and can reset each
  other's stall count, bounded by the 24 h job-age backstop.
- `load_window` does not compare the stored `window_end_ms` with the expected grid end; the read
  version is the only guard, so Phase 173 must bump it as the module docstring already says.
