## Revert of S-2: does the restored store-fault behaviour leave a silent failure?

No. Each of the three outcomes is observable:

- Store fault: `begin_claim` returns None and has already logged once; the read then runs as
  layer 1 over the whole range (`:961-962`). No store call, no hidden state.
- Big book with the store down: no page or run budget, so the read ends on
  `_RECONSTRUCT_CRAWL_TIMEOUT_S`. The `asyncio.TimeoutError` arm (`:6039-6068`) logs a WARNING,
  emits the `reconstruct_failed` audit event, and returns FAILED/transient with static text that
  names the wall-clock bound. The attempts cap bounds the retries, so the end state is a FAILED
  job with a named cause, not a loop. Nothing is persisted. The message blames neither the venue
  nor the store, which is accurate: it is a timeout.
- `TruncatedTradeRead` stays permanent, store up or down. Each raise site logs a counts-only
  WARNING first (`bybit_no_advance`, `bybit_segment_ceiling`) and the persisted text is static.
  A genuine venue refusal is not relabelled as a store fault. The new parametrised test
  (`store_up` True/False) pins permanent, no persisted snapshot, and no signature in the message
  or log records.
