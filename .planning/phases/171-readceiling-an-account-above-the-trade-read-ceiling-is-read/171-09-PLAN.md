## Precedence decision (planner, Rule 7: one pattern chosen, the other recorded)

RESEARCH proposed deciding over all outcomes first: refusal > settled MT5 result > deferral > retryable > permanent. This
plan instead keeps today's key-order loop for every EXISTING outcome and decides a deferral LAST (remember it, keep
looping; after the loop, if nothing else decided, re-raise it). Why: it changes no existing outcome or pinned test (Rule
3); a refusal and a permanent failure are deterministic, so deferring on them would only burn claims (RESEARCH itself
ranked permanent below deferral, which this avoids); and the stored windows survive a FAILED claim, so a sibling's
retryable fault ending the claim transient (one attempt) loses no read progress. Record this in the SUMMARY.

- `_crawl_whole_account`'s outcome loop runs in key order: `ForcedRebuildRefusedError` (WARNING, raise), `DispatchResult`
  (an MT5 member's settled failure, WARNING, return), any other `BaseException` (WARNING with the class; classified

  account crawl reaches every member, and a binding set inside one member's crawl stays in that member's Task.
