### 5b. The second, independent argument — why the mechanism is a job-level condition

Even if protection were enabled, the shipped mechanism could not wedge it:

- A job **skipped by a conditional** still reports a result to the check board — `conclusion:
  "skipped"`, which GitHub reports to a required status check as **Success**. Measured above: all
  16 filtered rows are PRESENT on the docs board with a skipped conclusion.
- A workflow **skipped by a `paths:` filter** reports **nothing at all**. Its check row never
  appears, and a required check that never appears stays *pending forever* — the wedge the ROADMAP
  warns about.

That asymmetry is precisely why the locked mechanism is the job-level `if:` and why the rejected
workflow-level `paths-ignore` would have been the wedging one. Both halves of the asymmetry are
visible in this phase's own data: the 16 filtered `ci.yml` jobs report `skipped` rows, whereas the
five `paths:`-filtered workflows (§6) contribute no rows to a docs-only PR whatsoever.

### 5c. ⛔ The recorded conditional

**If branch protection or a ruleset is ever enabled on `main`, `changed-paths` MUST be added to the
required-checks list.** It is the single point of trust for sixteen gates — a wrong `true` skips
all sixteen at once — and an unprotected required list would leave it ungated. Booked here, in the
phase that created the dependency. (Threat `T-164.6.3-21`, disposition `accept`, is accepted only
because the measurement above shows there is currently nothing to register.)
