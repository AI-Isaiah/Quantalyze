### DECIDED 2026-09-09 — transcribed VERBATIM per success criterion 1

⛔ These are ANSWERS with the measurement or precedent they rest on. A planner RECORDS
them; it does not re-derive them and does not re-open them.

- **D1 — Registration lives in the RUNBOOK, never in a migration.** Basis: the 164.7 rule shipped in `20260907120000` (*"A migration that schedules is a scope violation"*), plus two in-tree precedents already following it (`ledger-refresh-go-live.md:412`, `flipretry-derived-equity-go-live.md:162`). The losing convention — Phase 164.5's old criterion 7 — is flagged for cleanup, not left to disagree silently.
- **D2 — What a rebuild-from-migrations produces: NO `match_engine_cron` job at all, plus one loud row.** MEASURED, not assumed: `20260408215026` skips scheduling whenever the two `app.*` GUCs are empty, and they are ALWAYS empty here because setting them returns 42501 on this platform. So a rebuilt database has no hourly job and one `cron_runs` row reading `error = 'GUC unset at migration 015'`, and the runbook registration is what creates the job. ⭐ This is the runbook convention working as designed — the migration fails CLOSED and leaves a trace — not a gap to be patched. ⛔ Therefore **no forward migration is written by this phase**, neither to schedule nor to unschedule. The window to name in the runbook is: *from a rebuild until the registration step is run, the hourly recompute does not fire, and `cron_runs` says why.*
- **D3 — The manifest re-capture is a SCRIPT, not hand work.** `scripts/prod-prober/` has no capture tool today. Criterion 3 already demands a pre-flight that ABORTS on a live-vs-manifest mismatch, which is code either way; the capture is the same read plus a write, and the drift arm compares by `command_sha256` and refuses a row without a valid one — so a hand-edited manifest is a defect waiting to happen. Write the small script, use it for the re-capture, commit both.
- **D4 — The PROD apply stays a HUMAN gate, and this block does not weaken it.** Criterion 5 is unchanged: three reviewers (`migration-reviewer`, `rls-policy-auditor`, `silent-failure-hunter`) before any production statement, and the founder runs or approves the live `cron.schedule`. Everything above removes *guesswork*, not *oversight*.

2026-09-12 and re-confirmed 2026-09-16: `export async function captureManifest({ seams,
outPath, log, functionsDir })` lives in `scripts/prod-prober/run.mjs` (resolve the SYMBOL,
not the line — it drifts). Criterion 2's re-capture CONSUMES this tool. The drift arm
compares by `command_sha256` and refuses a row without a valid one, so the sha is

⚠️ **The manifest is already at `ws-collapse-v2`** (captured 2026-09-11, run `34611594511`,

### Area 1 — Fail-closed kill switch (criterion 8)

- **The retry lives in `analytics-service/services/db.py` as a named seam** (e.g.
  `db_read_with_retry`), which `_engine_is_enabled()` consumes. Rationale: `db_execute`
  (`services/db.py:133`) is already the ONE seam every Supabase read in the kill switch,
  `cron_recompute` and `main_worker` passes through, and `classify_exception` already
  knows `transient`. ⛔ Do NOT retry inside `db_execute` itself — that silently changes
  timing semantics for every caller, including ones that must fail fast.
- **Budget: 3 attempts, exponential backoff with jitter (≈1/2/4s), total bounded strictly
  below the `statement_timeout` set in Area 2.** Idiom to copy, not invent:
  `_okx_bills_fetch_with_backoff` (`analytics-service/services/exchange.py:1296`) and the
  Deribit read-retry policy (`services/deribit_ingest.py`).
- **The closed state carries a DISTINCT status** — `kill_switch_unavailable`, never a silent
  `disabled` — logged at ERROR so Sentry fires. This is item 1's own ⚠️: a database outage
  must never be mistaken for the founder pressing the switch. Sentry `QUANTALYZE-1D`
  (5 events, 2026-09-12) is the dated production sighting this closes.
- **Fail-closed applies to `_engine_is_enabled_cached` too.** The cache NEVER serves a value
  produced by a failed poll: on exhaustion it invalidates and the caller sees the closed
  state. ⚠️ The mid-run re-check at `match.py:2029` deliberately uses the UNCACHED accessor
  (F1/MED8) — that stays.

### Area 2 — The gateway-ceiling inversion (criteria 7 and 9)

- **`service_role` gets `statement_timeout = 45s`**, set by FORWARD MIGRATION
  (`ALTER ROLE service_role SET statement_timeout`), ⛔ never by a console `ALTER ROLE` —
  that leaves no reproducible trace and is the exact class `CRON-DRIFT-01` exists because of.
  45s sits strictly below the gateway's 60s and above the measured 44.67s successful run;
  the remaining margin is what criterion 9's batching removes. Verified by reading
  `pg_roles.rolconfig` on PROD AFTER the apply and RECORDING the output, not the statement.
  ⛔ This makes nothing faster and must not be described as if it did — it converts an
  opaque gateway 504 into a catchable Postgres timeout.
- ⚠️ **This migration does NOT contradict D1 or D2.** D1/D2 forbid a migration that
  SCHEDULES or UNSCHEDULES (`20260907120000`: *"REGISTERS NO SCHEDULE and REMOVES NONE"*).
  `ALTER ROLE … SET statement_timeout` does neither. Recorded here so no reviewer reads the
  two as a conflict and no executor averages them.
- **`cron_recompute()` is batched with a cursor.** One request processes at most N
  allocators and returns `next_cursor` plus `status="partial"`; the remainder is picked up
  on the following tick. The uniform `_early_return` response shape (`status` + the four
  counters + `duration_s`) is PRESERVED — `TestCronResponseShape._REQUIRED_KEYS` asserts it.
  Rejected: a 202 + background task, which removes the duration from the measured path
  instead of shrinking it; and raising the timeout alone, which fixes nothing.
  The post-change duration is RECORDED against the measured `44.67s` baseline.
- **`_claim_priority` (`main_worker.py:651`) and `_reset` (`main_worker.py:1057`) are IN
  SCOPE**, consuming the same Area 1 retry seam. Criterion 9 permits deferring them to a
  NAMED phase; we do not take that option — they are the same defect through the same seam
  (Sentry `QUANTALYZE-11`, 14 events; `QUANTALYZE-X`, 3 events).

### Area 3 — Repoint, manifest re-capture and activation (criteria 1–6)

- **The pre-flight is a VERB in `scripts/prod-prober/run.mjs`, beside `captureManifest`** —
  same normalization, same `command_sha256` logic, no second notion of truth. It ABORTS
  non-zero WITHOUT writing on a live-vs-manifest mismatch, PROVEN by running it against a
  deliberately mismatched manifest (criterion 3: never infer from an absent measurement).
- **The residual Phase 164.8.5 left is the GATE, not the data:** nothing in CI fails when
  the arm's exported `NORMALIZATION` and the manifest's `normalization` key disagree. That
  mismatch was caught by an hourly PRODUCTION probe, not by CI — a control that silently
  stopped being able to find anything, which this repo ranks above ordinary correctness.
  Ship a contract test that goes RED on divergence, plus a `--self-test` arm proving it
  bites. ⛔ A note in the runbook alone does not satisfy this.
- **ONE runbook session, ONE re-capture at the end**, in this order:
  1. deploy Area 1 + Area 2 (kill switch, timeout, batching),
  2. repoint `match_engine_cron` at `public.match_engine_cron_tick()`,
  3. register `ledger_refresh_fanout`, flip `system_flags.ledger_refresh_enabled`,
  4. re-capture `cron-manifest.json` ONCE and commit it.
  ⛔ Two re-captures means two red prober runs. The ROADMAP names this coupling explicitly
  and it is part of why the activation was routed here.
- **Two waves, one phase.** Wave A = kill switch + timeout + batching (code + CI, mergeable
  on its own). Wave B = repoint + activation + re-capture (runbook, founder gate D4).
  ⛔ ORDER IS LOAD-BEARING: criterion 8 is not provable before Wave A lands, because proving
  a kill switch while it is fail-open verifies nothing.
