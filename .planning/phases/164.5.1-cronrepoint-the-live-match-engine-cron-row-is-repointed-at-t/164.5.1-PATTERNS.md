## Pattern Assignments

### `analytics-service/services/db.py` — `db_read_with_retry` (new)

**Primary analog:** `_okx_bills_fetch_with_backoff` (`analytics-service/services/exchange.py:1296-1336`)
**Secondary analog (exhaustion-signaling alternative):** `paginate_txn_log`'s inner retry block (`analytics-service/services/deribit_ingest.py:371-445`, `LedgerTruncatedError`)

**Which one to copy, and why:** copy `_okx_bills_fetch_with_backoff`'s SHAPE (bare re-raise on exhaustion, narrow exception-tuple gate, `for attempt in range(MAX_RETRIES)`), not `paginate_txn_log`'s named-exception idiom — CONTEXT.md's Area 1 already specifies the closed state is signaled by a **status value** (`kill_switch_unavailable`) at the call site, not by a raised exception type propagating out of the retry helper itself. A `LedgerTruncatedError`-style exception would just be caught immediately by `_engine_is_enabled`'s existing broad `except Exception` and converted to `True` today — the fix is precisely to stop doing that, so the retry helper should re-raise plainly and let each of the THREE call sites (kill switch, `cron_recompute`, `_claim_priority`/`_reset`) decide their own disposition, matching `_okx_bills_fetch_with_backoff`'s "let the caller decide" contract.

**Core pattern to copy** (`analytics-service/services/exchange.py:1296-1336`):
```python
OKX_BILLS_MAX_RETRIES = 4
OKX_BILLS_BACKOFF_BASE_S = 0.5

async def _okx_bills_fetch_with_backoff(
    exchange: ccxt.Exchange,
    method_name: str,
    params: dict[str, str],
    *,
    label: str,
    page: int,
) -> dict[str, Any]:
    method = getattr(exchange, method_name)
    for attempt in range(OKX_BILLS_MAX_RETRIES):
        try:
            result: dict[str, Any] = await method(params)
            return result
        except (ccxt.RateLimitExceeded, ccxt.DDoSProtection) as exc:
            if attempt == OKX_BILLS_MAX_RETRIES - 1:
                raise
            delay = OKX_BILLS_BACKOFF_BASE_S * (2 ** attempt) + random.uniform(0, 0.5)
            logger.warning(...)
            await asyncio.sleep(delay)
    raise RuntimeError("unreachable: _okx_bills_fetch_with_backoff")
```

**Where the sleep lives:** inside the `except` block, after computing `delay`, BEFORE the loop's next iteration — never a `finally`, never before the `try`. The re-raise on the last attempt happens BEFORE the sleep is computed (no wasted sleep after the final failure).

**How exhaustion is raised:** a bare `raise` (re-raises the original exception unchanged) — the caller sees the SAME exception type/shape it would have seen with zero retries, just later. This is the correct choice for `db_read_with_retry`: `_engine_is_enabled`'s existing `except Exception as err` catches whatever comes out and now must be changed to distinguish "not-transient" (unchanged behavior — CONTEXT.md doesn't touch that) from "transient, exhausted" (new: fail-closed).

**How it interacts with `asyncio.to_thread`:** `_okx_bills_fetch_with_backoff` is itself `async def` and calls `await method(params)` directly — it does NOT run inside `asyncio.to_thread`. This is the open structural question RESEARCH.md flags (Open Question 1): `_engine_is_enabled` today is `sync def` and is invoked via `asyncio.to_thread(_engine_is_enabled)`. `db_read_with_retry` as sketched in RESEARCH.md's code example is `async def` calling `await db_execute(fn)` (where `db_execute` itself does `loop.run_in_executor(...)` — see `services/db.py:133-159`, quoted below). Two shapes are possible:
  - (a) `_engine_is_enabled` becomes `async def`, calls `await db_read_with_retry(fn)` directly, and its ~3 call sites switch from `asyncio.to_thread(_engine_is_enabled)` to a plain `await _engine_is_enabled()`.
  - (b) `db_read_with_retry` stays sync, using `time.sleep` (not `asyncio.sleep`) for the backoff — correct ONLY because it already runs inside a thread-pool thread via `to_thread`, so blocking that thread is intended, not a bug — while `_engine_is_enabled` itself stays sync.
  Neither is "the pattern to copy" — this is a genuine decision the plan must make explicitly (RESEARCH.md's own Open Question 1); (a) is more consistent with `_okx_bills_fetch_with_backoff`'s async shape and is the recommended default absent a stronger reason for (b).

**`db_execute` itself** (`analytics-service/services/db.py:133-159`, the seam `db_read_with_retry` sits BESIDE, never inside):
```python
async def db_execute(fn: Callable[[], _T]) -> _T:
    """Run a synchronous Supabase call without blocking the async event loop. ..."""
    try:
        qsize = _DB_EXECUTOR._work_queue.qsize()
        if qsize > _DB_POOL_SIZE * 0.8:
            logger.warning("db_execute: thread pool near saturation ...")
    except AttributeError:
        pass
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(_DB_EXECUTOR, fn)
```

### Exception classification by `.code` — `_is_gateway_timeout` (new, in `db.py`)

**Analog for the `.code`-reading shape:** `_is_undefined_function_structured` in `analytics-service/main_worker.py` — confirmed by `Read` this session that the file's comment block (around line 511-521) describes it as the STRICTER structural check used for a permanent latch, contrasted with a loose message-substring fallback (`_is_undefined_function`) kept only for a one-shot per-tick attempt:
```python
if _is_undefined_function_structured(exc):
    return True
# Defensive: some PostgREST versions stash the SQLSTATE only inside the
# message string. Match on the canonical PostgreSQL phrase.
msg = str(exc) if exc is not None else ""
if "claim_compute_jobs_with_priority" in msg and "does not exist" in msg:
    return True
return False
```
`_is_undefined_function_structured` itself reads `getattr(exc, "code", None)` against SQLSTATE `42883` (not shown above but named identically by RESEARCH.md and CONTEXT.md, both citing the same symbol). The shape to copy for a `postgrest.exceptions.APIError` carrying `code: 504`:
```python
def _is_gateway_timeout(exc: BaseException) -> bool:
    code = getattr(exc, "code", None)
    return code in ("504", 504)  # [ASSUMED] wire type ambiguous — see RESEARCH.md A2
```
The dual `("504", 504)` check is NOT decorative — RESEARCH.md's Assumption A2 flags this as the one place a silent type mismatch would recreate the exact fail-open bug this phase exists to close, and recommends a calibration test against a REAL captured `APIError` shape rather than a hand-built mock.

**`classify_exception` in `services/job_worker.py:682`** (NOT `services/db.py` — RESEARCH.md's own citation confirms this at the top; there is no `classify_exception` in `services/db.py`): quoted above in full detail during this mapping session. It does **NOT** treat a bare `postgrest.exceptions.APIError` with `code == "504"` (or any 5xx) as transient by name — its `HTTPException` branch only matches FastAPI's own `HTTPException` type (checked BEFORE the ccxt hierarchy per comment `H-1113`), and a bare `APIError` falls through to the final catch-all `# Everything else ... return ("unknown", str(exc)[:500])`, which that module's own comment documents as "5xx -> falls through to 'unknown' below" (retried by default in THAT module's job-retry semantics — a different, higher-level concern than the low-level `db_read_with_retry` seam). **Conclusion for the plan: `db_read_with_retry` needs its OWN narrow predicate (`_is_gateway_timeout`, above) — do not delegate to or extend `classify_exception`, which lives in a different module (`job_worker.py`) serving a different call layer (compute-job retry, not raw Supabase reads).**
