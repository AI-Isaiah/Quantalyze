<objective>
Criterion 9: no single analytics request performs its whole unit of work inside one
gateway-bounded call.

Measured on PROD 2026-09-13: the one run in the observed window that SUCCEEDED reported
`duration_s: 44.67` against a 60 s gateway limit, and 5 of the 6 runs still inside pg_net's
retention window returned 500 — all with `timed_out: false` and `error_msg: null`, so pg_net
reached the service and the service itself errored. It is NOT database contention and NOT a slow
statement: 17 of 60 connections, 1 active, 0 idle-in-transaction, 0 waiting on a lock, and
`pg_stat_statements` returns ZERO rows with `max_exec_time > 20s`. The cron's AGGREGATE work is
what approaches the wall, and it worsens monotonically as allocator and strategy counts grow.

Plan 03's `statement_timeout` makes the failure LEGIBLE; this plan makes the request COMPLETE.

Locked decisions recorded and implemented here: CONTEXT.md **Area 2** — *"`cron_recompute()` is
batched with a cursor. One request processes at most N allocators and returns `next_cursor` plus
`status="partial"`; the remainder is picked up on the following tick. The uniform `_early_return`
response shape (`status` + the four counters + `duration_s`) is PRESERVED. Rejected: a 202 +
background task, which removes the duration from the measured path instead of shrinking it; and
raising the timeout alone, which fixes nothing."*

⚠️ The one thing CONTEXT.md leaves open beyond batch size is the PERSISTENCE LOCATION, and this
plan states it explicitly rather than treating it as a statement-level choice: the cursor lives in
`public.system_settings` (Phase 164.7's TEXT key/value table, already service-role-writable). ⛔ And
`public.system_settings` has ZERO Python consumers today — measured, no non-test hit anywhere in
`analytics-service/`. This plan writes the FIRST Python read/write path for that table. It follows
`db_execute`'s general shape because there is no table-specific pattern to follow; it does not
"consume Phase 164.7's mechanism" in any sense stronger than using the table 164.7 created.

⚠️ No migration is needed and none is written: `system_settings` already exists, the cursor is a
plain data row, and the first tick under the new code upserts its own. A dedicated state table
would be a forward migration needing its own justification against D2's (D-02) framing; it is not
taken.

Purpose: stop the hourly recompute from being a coin flip against a fixed wall.
Output: a bounded, resumable cron with its status vocabulary documented.
</objective>

## Edge-coverage assumptions

The consolidated 21-item table lives in `164.5.1-01-PLAN.md` § Edge-coverage assumptions; all 21
rows are `unresolved` and none is dropped. This plan owns no rows of its own, but three of the four
`164.5.1-GATEWAY-CEILING-INVERSION` rows bear directly on the batching and are restated here as
explicit assumptions rather than left to plan 02's context:

- **Row 19 (empty)** — "What is the result for empty, single-element, or null input?" **Assumed and
  implemented:** zero allocators still returns the existing `no_allocators` status, and one
  allocator with `CRON_BATCH_SIZE >= 1` returns a terminal status, never `partial`. Both are
  asserted.
- **Row 20 (ordering)** — "When elements compare equal, is output order specified and stable?"
  **Assumed and implemented:** allocators are ordered by `profiles.id`, which is a PRIMARY KEY and
  therefore unique — no two rows compare equal, so the keyset page has no tie to break. The probe
