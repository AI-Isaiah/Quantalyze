## Summary

Wave A hardens `/api/match/cron-recompute` ahead of a founder-run production repoint of
`cron.job` jobid 1. The retry seam (`services/db.py`) is narrow and correctly calibrated
(I verified the int-`code` arm is the REAL production shape: `postgrest`'s
`generate_default_error_message` sets `code = r.status_code`, an `int`, whenever the gateway
body fails `APIErrorFromJSON` validation — which is every Kong/Cloudflare 504). The kill-switch
tri-state and its cache-invalidation contract are correctly implemented and non-vacuously
tested. The prober verb, its fixture, the `[164.5.1-07]` oracle gate and the venue-vocabulary
arrival all pass (`--self-test` 82/82 exit 0; `vitest` 115/115; `pytest` 207/207 on the four
touched Python suites). I calibrated the batching suite by neutering `has_more` and it goes RED,
so it is not vacuous.

**But the batching cursor has a terminal state it cannot leave.** When the keyset page comes
back EMPTY while a cursor is set, `cron_recompute()` returns `no_allocators` and never writes
the wrap marker. The cursor stays pinned at the last allocator id forever and the match engine
stops recomputing every allocator, permanently and silently, with a status that reads as "there
was nothing to do". I reproduced it against the shipped code with the repo's own test doubles —
see CR-01. This is reachable on the very first production pass, because the elapsed-time budget
is measured from before the ~30k-row universe load and therefore trips on the LAST allocator of
the LAST page. Repointing jobid 1 at this code would trade a fail-open kill switch for a
fail-silent engine.

A cluster of secondary defects sits around the same new code path: the cursor write is
fire-and-forget (WR-03), an exhausted cursor READ escapes the route as a bare 500 despite a
docstring promising the caller decides (WR-02), and the only new user-facing wire code this
phase introduces (`KILL_SWITCH_UNAVAILABLE`, a 503 from `recompute()`) has zero tests, no
`STATUS_CONTRACT.md` row, and an exemption entry in `wizardErrors.ts` whose two "MEASURED"
claims are both wrong about which function emits it and which TypeScript consumer reads it
(WR-05, WR-06). The runbook still names the WITHDRAWN `service_role statement_timeout`
migration as a Wave B precondition (WR-07), and its stated alarm signal for a stuck batch
cannot observe the failure mode that actually exists (WR-08).

The `completed_at` → `updated_at` repair in `ledger-refresh-go-live.md` is CORRECT and I
verified it independently: `public.compute_jobs` in `supabase/schema/baseline.sql` has no
`completed_at` column, has `updated_at`, and carries
`compute_jobs_set_updated_at_trigger BEFORE UPDATE`, so `updated_at` really is the
terminal-status timestamp the prose claims.

## Critical Issues

### CR-01: The batching cursor has an absorbing state — an empty page with a live cursor never wraps, and the match engine stops forever

**File:** `analytics-service/routers/match.py:2159-2163`, `:2272-2275`, `:2325-2332`
**Severity:** BLOCKER

**Issue:**

```python
2159    has_more = len(_fetched_page) > CRON_BATCH_SIZE
2160    allocators = _fetched_page[:CRON_BATCH_SIZE]
2161    if not allocators:
2162        logger.info("match_engine cron: no allocators found")
2163        return _early_return("no_allocators")     # <-- cursor NEVER written
```

`_early_return("no_allocators")` is the ONLY return in `cron_recompute()` that can be reached
with a non-null cursor and writes nothing. Every other terminal path either wraps
(`_write_cron_cursor(None)`, :2352) or advances (`_write_cron_cursor(last_handled_id)`, :2332).

The state is reached on the ordinary happy path, not an exotic one. The elapsed-time bound is
evaluated **after every allocator, including the last allocator of the last page**:

```python
2272        last_handled_id = allocator_id
2273        if _duration() >= CRON_BATCH_BUDGET_S:
2274            budget_exhausted = True
2275            break
```

`_duration()` is measured from `overall_start` at the top of the route, so it already includes
`_read_cron_cursor`, the profiles page fetch and `_load_candidate_universe` (a full paginated
scan of every published strategy plus its `strategy_analytics` rows). Once cumulative elapsed
time crosses 25 s while handling the final allocator, `budget_exhausted` is `True` even though
`has_more` is `False`, line 2325 takes the `has_more or budget_exhausted` branch, and
`_write_cron_cursor(last_handled_id)` pins the cursor at the **maximum** `profiles.id`. The next
tick's `.gt("id", cursor)` (:2151) returns zero rows → `no_allocators` → no write → the state
repeats on every tick, forever.

Second, independent trigger: any allocator beyond the current page losing `role IN
('allocator','both')` (or being deleted) between two ticks also empties the page while the
cursor is live.

**Reproduced** against the shipped code, driving `cron_recompute()` through this repo's own
`_FakeProfilesQuery` and `_install_cursor_store` doubles (3 allocators, `CRON_BATCH_SIZE=10`,
`CRON_BATCH_BUDGET_S=0.0`, 8 consecutive ticks):

```
('partial', 1, 'a1')
('partial', 1, 'a2')
('partial', 1, 'a3')
('no_allocators', 0, 'a3')
('no_allocators', 0, 'a3')
('no_allocators', 0, 'a3')   # ... and every tick thereafter
```

Consequences, all silent:
- No allocator is ever scored again. `match_batches` stops growing; the admin match queue and
  every SSR surface fed by it serve a frozen batch whose own "Computed Nh ago" stamp is the
  only evidence.
- The retention sweep stops (`swept_allocator_ids` is empty on every tick).
- The status is `no_allocators` — documented in `docs/runbooks/match-engine.md` as a benign
  value, and *not* the `partial`-that-does-not-advance signal the same runbook tells the
  operator to alarm on (see WR-08). Nothing in the repo distinguishes "the platform genuinely
  has no allocators" from "the engine is wedged".
- `public.system_settings` carries `system_settings_admin_all FOR ALL TO authenticated` gated
  on `profiles.is_admin`, and no CHECK constraint covers this key. Any app-admin can PATCH
  `match_engine_cron_cursor` to `ffffffff-ffff-4fff-8fff-ffffffffffff` through PostgREST and
  wedge the engine permanently — which directly falsifies `_write_cron_cursor`'s own claim that
  an admin edit "restarts a pass and nothing worse" (WR-09).

The existing batching tests cannot catch this: `test_cron_batch_resume_wrap_and_restart_full_cycle`
only exercises the `has_more=False` exhaustion path (which *does* wrap), and
`test_cron_batch_budget_exhausted_returns_partial_after_one` calls `cron_recompute()` exactly
once. No test ever drives the cursor to the end of the set.

**Fix:** an empty page with a live cursor means "the pass is over", not "there is nothing to
do". Wrap and say so, and do not let the budget advance a cursor past the end of the set:

```python
    _fetched_page = rows(allocators_result)
    has_more = len(_fetched_page) > CRON_BATCH_SIZE
    allocators = _fetched_page[:CRON_BATCH_SIZE]
    if not allocators:
        if cursor is not None:
            # The pass ran off the end of the set (the tail was consumed, or the
            # remaining rows lost their allocator role). Wrap so the next tick
            # restarts — never leave a cursor that can only ever match zero rows.
            logger.info(
                "match_engine cron: keyset page empty past cursor %s — wrapping",
                cursor,
            )
            await _write_cron_cursor(None)
            return _early_return("wrapped", next_cursor=None)
        logger.info("match_engine cron: no allocators found")
        return _early_return("no_allocators", next_cursor=None)
```

and, at the budget check, only treat the bound as a batch boundary when work actually remains:

```python
        last_handled_id = allocator_id
        _is_last_of_page = allocator_id == allocators[-1]["id"]
        if _duration() >= CRON_BATCH_BUDGET_S and not (_is_last_of_page and not has_more):
            budget_exhausted = True
            break
```

Then add the regression test the suite is missing — drive `cron_recompute()` until the set is
exhausted and assert the cursor returns to the wrap marker and the following tick re-processes
the first allocator. Also add `"wrapped"` (or whichever status is chosen) to the runbook's
Metrics bullet, which `TestRunbookStatusVocabulary` will otherwise redden.

### WR-01: `last_handled_id` can still be `None` at the batch boundary, so a `partial` run writes the WRAP marker while it knows more work remains

**File:** `analytics-service/routers/match.py:2174-2185`, `:2325-2340`
**Issue:** the `if not allocators` guard at :2161 runs BEFORE the demo-allocator filter at
:2184 (`allocators = [p for p in allocators if p["id"] != _DEMO_ALLOCATOR_ID]`). If a page's
only non-trimmed member is the demo allocator, `allocators` becomes empty *after* that guard,
the loop body never executes, and `last_handled_id` stays `None`. Execution still reaches
:2325; with `has_more` true it calls `_write_cron_cursor(last_handled_id)` — i.e.
`_write_cron_cursor(None)` — which is the WRAP marker, resetting the pass to the beginning
while the run has just measured that more allocators exist. The response is
`{"status": "partial", "next_cursor": null}`, a self-contradiction (`partial` means "resume
after next_cursor"; `null` means "start over") that is byte-identical to the terminal `ok`
body's `next_cursor`. Every allocator ordered after that page is then never reached: the pass
loops over the same prefix indefinitely. Narrower trigger than CR-01 (it needs the demo seed's
`is_example` to have been reset, which the adjacent `logger.error` already alarms on) but the
same class of silent skip.
**Fix:** make the wrap explicit rather than implicit in a `None`:
```python
    if has_more or budget_exhausted:
        if last_handled_id is None:
            # Nothing completed this tick (e.g. the whole page was filtered out).
            # Do NOT write: writing None here would restart a pass that has not
            # finished, and writing a half-page id would skip the rest.
            logger.error(
                "match_engine cron: batch boundary with nothing handled "
                "(has_more=%s budget_exhausted=%s) — cursor left unwritten",
                has_more, budget_exhausted,
            )
        else:
            await _write_cron_cursor(last_handled_id)
```

### WR-02: an exhausted cursor READ escapes `cron_recompute()` as an unhandled 500 — the docstring's "the caller decides" is unimplemented at this call site

**File:** `analytics-service/routers/match.py:2136`, contract at `:2007-2029` and
`analytics-service/services/db.py:225-229`
**Issue:** `db_read_with_retry`'s docstring states "Each of the call sites that consume this
seam (the kill switch, `cron_recompute`, `_claim_priority`/`_reset`) decides its OWN
disposition on exhaustion". `_read_cron_cursor`'s docstring repeats it ("it propagates so the
caller decides"). The caller does not decide: `cursor = await _read_cron_cursor()` at :2136 sits
in no `try`, so an exhausted read propagates straight out of the route handler. FastAPI answers
a bare 500 with no `service_error` envelope — contradicting this file's own header rule
("every deliberate error in this file's seam-reachable arms goes through service_error so the
four status classes cannot drift apart site-by-site", :61-64) — and the whole tick, including
the retention sweep, is lost with no structured signal. `test_read_cron_cursor_exhausted_retries_raises_not_none`
pins the helper's propagation but nothing pins what `cron_recompute` does with it.
**Fix:** give it the disposition the kill switch already has, and test it:
```python
    try:
        cursor = await _read_cron_cursor()
    except Exception as err:
        logger.error(
            "match_engine cron: cursor read FAILED after exhausting retries — "
            "declining to run rather than silently restarting the pass: %s", err,
        )
        return _early_return("cursor_unavailable")
```
(Do NOT fall back to `cursor = None`: that is exactly the "a failed read must never be
indistinguishable from start-over" property `_read_cron_cursor` was written to preserve.)

### WR-03: `_write_cron_cursor` discards the upsert result — a silent no-op replays the same slice forever

**File:** `analytics-service/routers/match.py:2089`
**Issue:** `await db_execute(_write)` throws the response away. This file establishes the
opposite convention twice, explicitly and with reasons: the rollback DELETE inspects
`_del_result.data` because "an RLS/race no-op (`data=[]`) is distinguishable from a successful
cleanup" (A3-01), and the candidates insert inspects `_cand_insert.data` so "a silent FK/CHECK
violation cannot leave the batch claiming candidate_count > 0". The cursor write — the single
piece of state on which resume correctness depends — is the one new write that checks nothing.
A zero-row upsert leaves the cursor stale, and the next tick re-processes the identical slice;
with `_should_skip_allocator`'s 12 h age guard every allocator in that slice is then `skipped`,
so the counters look healthy while the pass never advances. `test_write_cron_cursor_upserts_value_and_updated_at`
only asserts the call ARGUMENTS (`upsert.call_args`), never the returned data, so it cannot
catch this.
**Fix:**
```python
    _res = await db_execute(_write)
    if not getattr(_res, "data", None):
        logger.error(
            "match_engine cron: cursor upsert for %s returned no rows — the "
            "cursor did NOT advance and the next tick will replay this slice",
            MATCH_ENGINE_CURSOR_KEY,
        )
```

### WR-04: `CRON_BATCH_BUDGET_S` does not bound the request, and the test that claims to pin it compares two constants

**File:** `analytics-service/routers/match.py:1985-1997`, `:2273`;
`analytics-service/tests/test_match_router.py` `TestCronBatchBoundsInvariants`
**Issue:** the module comment asserts "Three bounds keep one request inside the gateway window:
`CRON_BATCH_BUDGET_S` (25s) < the 60s API gateway ceiling". That is not what the code does. The
budget is a post-hoc check evaluated only BETWEEN allocators, so the request's actual wall time
is `universe_load + Σ(allocators until the crossing) + the full duration of the allocator that
crossed it`. One slow allocator (`_score_one_allocator` is pandas/numpy work over the whole
candidate universe, and the same runbook's own SLA line is "p95 < 30s per allocator") takes the
request past 60 s regardless of the 25 s constant. `test_batch_budget_strictly_below_gateway_ceiling`
asserts `match_mod.CRON_BATCH_BUDGET_S < 60.0` — a comparison of two literals that can never
fail for any reason connected to request duration. Compounding: `_duration()` starts before
`_load_candidate_universe`, so on a large universe the budget is already spent before allocator
#1, making `budget_exhausted` fire on every tick (which is what makes CR-01 near-certain rather
than theoretical).
**Fix:** either state the bound honestly in the comment ("a best-effort boundary checked
between allocators; it does not cap a single allocator's scoring time") or make it real by
starting the budget clock AFTER the universe load and adding a per-allocator
`asyncio.wait_for`. Either way, replace the constant-vs-constant test with one that drives
`cron_recompute()` with a slow `_score_one_allocator` double and asserts the observed
`duration_s`.

### WR-09: `_write_cron_cursor`'s docstring understates an admin-reachable denial of service

**File:** `analytics-service/routers/match.py:2064-2070`
**Issue:** *"The cursor is ENGINE-INTERNAL BOOKKEEPING even though the table's grants do not
distinguish it from operator-editable configuration — an admin hand-editing this row restarts a
pass and nothing worse."* `public.system_settings` carries
`system_settings_admin_all FOR ALL TO authenticated` gated on `profiles.is_admin = true`
(migration `20260907120000`), and the only CHECK constraint on the table is scoped to
`key = 'analytics_service_url'`. So any app-admin can PATCH this row through PostgREST, and
given CR-01 a high-valued UUID does not "restart a pass" — it stops the engine permanently.
Even once CR-01 is fixed, repeatedly setting a high cursor starves every allocator below it.
The one thing the code does get right here is that `_UUID_RE` (`:2002`) rejects a non-UUID
before it reaches `.gt("id", cursor)`, so there is no filter-injection route — worth keeping
and worth saying.
**Fix:** correct the sentence to name the real residual ("an admin who can write this row can
starve or stall the pass; the `_UUID_RE` guard bounds it to a valid-UUID DoS and forecloses
filter injection"), and consider a CHECK constraint pinning this key to
`value = '' OR value ~ '^[0-9a-f]{8}-…$'` so the fail-loud lives in the schema rather than only
in the reader.

### WR-10: `watchdog_tick`'s `_reset` is a WRITE RPC routed through a read-named retry seam, and a post-commit 504 makes the log under-report

**File:** `analytics-service/main_worker.py:1066-1080`
**Issue:** distinct call site from the `_claim_priority` finding already dispositioned at D4.
`reset_stalled_compute_jobs` mutates `compute_jobs`; a gateway 504 delivered AFTER the server
committed causes `db_read_with_retry` to re-invoke it, the second call finds nothing past the
10-minute staleness threshold, returns 0, and `reset_count = result.data or 0` suppresses the
`"Watchdog reclaimed %d stalled jobs"` WARNING entirely. The reclaim happened; the only record
that it happened is gone. The threshold makes a double-reset of a freshly re-claimed job
unlikely, so the correctness risk is low, but the observability loss is real and the seam name
(`db_read_with_retry`) now sits over two writes.
**Fix:** either rename the seam to `db_call_with_gateway_retry` and document that callers must
be idempotent, or leave `_reset` on `db_execute` and note that a lost watchdog tick is cheaper
than a lost audit line. If the retry is kept, log at WARNING when a retry occurred AND the
final `reset_count` is 0, so "reclaimed nothing" and "reclaimed then lost the receipt" are
distinguishable.

### WR-11: `CRON_BATCH_BUDGET_S` has no floor while `CRON_BATCH_SIZE` does, and a typo'd env var crashes the service at import

**File:** `analytics-service/routers/match.py:1996-1997`
**Issue:**

The `max(1, …)` floor was applied to the count knob and not to the time knob, so
`MATCH_ENGINE_CRON_BUDGET_S=0` (or a negative) trips `budget_exhausted` after every single
allocator — one allocator per tick, and straight into CR-01's wedge on the tail. There is also
no upper bound (a value above 60 defeats the stated purpose), and `TestCronBatchBoundsInvariants`
only asserts `< 60.0` and `>= 1`, never `> 0`. Separately, a non-numeric value for either var
raises `ValueError` at module import, i.e. the whole FastAPI app fails to start on an operator
typo with a traceback that names `int()`, not the variable.
**Fix:** mirror the existing floor and add a matching invariant test:
```python
CRON_BATCH_BUDGET_S = min(55.0, max(1.0, float(os.getenv("MATCH_ENGINE_CRON_BUDGET_S", "25.0"))))
```
and wrap both parses so a bad value logs the offending variable name and falls back to the
default rather than taking the service down.

### WR-12: nothing ties the batch bound to `RECOMPUTE_MIN_AGE_HOURS`, so a full pass can silently exceed the freshness window the engine promises

**File:** `analytics-service/routers/match.py:95` (`RECOMPUTE_MIN_AGE_HOURS = 12`) vs
`:1996-1997`, `:2193`
**Issue:** before this change the hourly cron walked every allocator each tick, so an
allocator crossing 12 h was recomputed within the hour. Now a full pass takes
`ceil(N / effective_slice)` ticks, and `effective_slice` is whatever the 25 s budget allows —
which, because `_duration()` includes `_load_candidate_universe` (a full paginated scan
re-executed from scratch on EVERY slice, :2193), can be one or two allocators. At two per hour
a 50-allocator platform needs 25 hours per pass, so batches routinely age past the 12 h
threshold the skip logic treats as the SLA. Nothing measures pass duration, nothing alarms on
it, and the runbook's "partial persisting across a full day" line is the closest thing to a bar
— which WR-08 shows is unobservable.
**Fix:** at minimum, log the pass age on wrap (`now() - system_settings.updated_at` at the
moment the cursor wraps) at WARNING when it exceeds `RECOMPUTE_MIN_AGE_HOURS`, so the
regression is visible. Structurally, hoisting the universe load out of the per-slice path (or
caching it across ticks with its own TTL) is what actually restores the throughput the bound
assumes.

### WR-13: the cron response shape is now inconsistent — `next_cursor` is present on four branches and absent on five

**File:** `analytics-service/routers/match.py:2098-2115` (`_early_return`), `:2336-2344`,
`:2355-2390`
**Issue:** `_early_return` builds "the uniform early-return response shape … so monitoring can
switch on one field instead of guessing at key presence", and `TestCronResponseShape._REQUIRED_KEYS`
enforces that uniformity. The phase added `next_cursor` to the `partial` return and to the
terminal `ok`/`degraded`/`total_failure` return, but not to `_early_return` and not to the
mid-run kill-switch return at :2336 — so `disabled`, `kill_switch_unavailable`,
`no_allocators`, `empty_universe` and the mid-run abort all omit it. A consumer reading
`body.next_cursor` gets `undefined`, which is indistinguishable from the terminal `null`
("wrapped"). That is the exact "guessing at key presence" the helper exists to prevent, and it
is also why CR-01's wedge cannot be seen from the response.
**Fix:** add `"next_cursor": None` to `_early_return`'s base dict and to the mid-run
kill-switch return, and extend `_REQUIRED_KEYS` to include it so the uniformity is enforced
rather than described.

### WR-14: `_is_gateway_timeout` is a private symbol imported across module boundaries to select between two near-identical log lines

**File:** `analytics-service/routers/match.py:52`, `:357-371`
**Issue:** `from services.db import _is_gateway_timeout` reaches across modules for a
leading-underscore name; `services/db.py` exports nothing declaring it part of the seam's
public surface. Its only use in `match.py` is to choose between two ERROR logs that share the

**Fix:** either promote the predicate (`is_gateway_timeout`, named in `services/db.py`'s seam

```python
        logger.error(
            "match_engine: kill switch check FAILED (%s) — engine STOPPED "
            "(kill_switch_unavailable): %s",
            "gateway timeout, retries exhausted" if is_gateway_timeout(err) else "non-retryable",
            err,
        )
```
