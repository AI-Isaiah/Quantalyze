Criterion 7: `service_role` carries an EXPLICIT `statement_timeout` strictly below the API gateway's
60 s ceiling, set by FORWARD MIGRATION.

Measured on PROD 2026-09-13: `pg_roles.rolconfig` gives `anon` 3 s, `authenticated` 8 s,
`authenticator` 8 s and `service_role` NULL — it inherits the 120000 ms database default while the
gateway gives up at 60 s. The ceiling that actually bites a service-role request therefore sits
BELOW the one Postgres enforces, so a slow read is answered `504 Gateway Timeout` by the gateway
while Postgres keeps working toward 120 s. The analytics service authenticates as `service_role`,
so every one of its reads runs under the only role in the project with no timeout of its own.

- **D2 (D-02)** says *"no forward migration is written by this phase"*. The ROADMAP's dated note of
  2026-09-16 scopes it: D1 (D-01) and D2 (D-02) forbid a migration that SCHEDULES or UNSCHEDULES
  (`20260907120000`: *"REGISTERS NO SCHEDULE and REMOVES NONE"*). An `ALTER ROLE … SET
  statement_timeout` does neither. Recorded here so no reviewer reads the two as a conflict and no
  executor averages them.
- **D4 (D-04)** stands: three reviewers (`migration-reviewer`, `rls-policy-auditor`,
  `silent-failure-hunter`) before ANY production statement. That gate is plan 09's
  `checkpoint:decision`; this plan writes the file and its static gate, and applies nothing.
- **Criterion 6 amendment (b)**: this migration's header carries NO forward pointer to the cron
  files, because it has no lineage relationship to them.
