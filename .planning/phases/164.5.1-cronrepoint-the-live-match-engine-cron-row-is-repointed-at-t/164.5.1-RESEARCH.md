## Summary

Every mechanism decision for this phase (D1-D4, plus Areas 1-3) is already locked in CONTEXT.md
and must be recorded, not re-derived. This research therefore focuses on the eight open
*implementation-shape* questions the discuss phase deliberately left to planning, plus three
requirement IDs (`[164.7-VAULT-ABSENT-RULE]`, `[VAULTTICK-EMPTYKEY-01]`, and the
`[164.8.5-MANIFEST-SIDE-LOOP-DEAD]`/`T-OPEN-03`/`T-OPEN-04` cluster) that the TODOS.md entries
describe as open but that measurement at HEAD shows are **already resolved or self-resolving** —
the plan should record this rather than re-open them as work items.

The two questions capable of changing the plan's shape:

1. **`ALTER ROLE service_role SET statement_timeout` is LOWER risk than CONTEXT.md's "single
   biggest risk to criterion 7" framing suggests.** All measured 42501s in this repo are against
   `app.*` **custom placeholder GUCs**, which Postgres treats as a superuser-only operation
   regardless of platform. `statement_timeout` is a **built-in** GUC, and Supabase's own current
   documentation shows `ALTER ROLE service_role SET statement_timeout = '10min';` as a normal,
   unrestricted operation with no superuser caveat — this is a materially different code path from
   the `app.*` failures. This is `[CITED: supabase.com/docs]`, not `[VERIFIED]` — nobody has run
   it against this project's PROD — so the plan should still gate the actual apply behind D4's
   human review, but should NOT plan a fallback-mechanism spike as if failure were the base rate.

2. **Cursor-batching `cron_recompute()` needs a genuinely NEW persistence idiom — there is no
   in-repo precedent for a cross-invocation resumable cursor**, because `match_engine_cron_tick()`
   fires the SAME parameterless `net.http_post` every hour; nothing in the pg_cron path carries
   state between ticks. The closest in-repo shapes (`paginate_txn_log`'s `continuation` and
   `_okx_bills_fetch_with_backoff`) both resume **within one call**, not across scheduled
   invocations. The plan needs to choose a persistence location; `public.system_settings`
   (Phase 164.7's TEXT key/value table, already service-role-writable) is a plausible reuse
   rather than a new table, but this is a genuine design choice for the plan to make explicitly,
   not an existing pattern to "consume."

**Primary recommendation:** treat Wave A (kill switch + timeout + batching) as ordinary
Python/SQL feature work following the cited house idioms below; treat Wave B (repoint +
activation) as a runbook-authoring task whose main risk is **not** technical but **operational**
— the P3-C pre-flight query is broken (wrong column name) and its last real reading failed the
freshness bar, so Wave B's plan must budget for a DEFER outcome, not assume activation completes
in one sitting.

### The retry seam — `db_read_with_retry`

**House idiom to copy** (confirmed by `Read` this session):

- `_okx_bills_fetch_with_backoff` (`analytics-service/services/exchange.py:1296-1336`): a `for
  attempt in range(MAX_RETRIES)` loop, catching a narrow exception tuple, computing
  `delay = BACKOFF_BASE_S * (2 ** attempt) + random.uniform(0, JITTER_MAX)`, `await
  asyncio.sleep(delay)`, re-raising on the last attempt. Only the named transient exceptions are
  retried; everything else propagates immediately.
- `paginate_txn_log`'s inner retry block (`analytics-service/services/deribit_ingest.py:412-445`)
  is the same shape with a named exhaustion exception (`LedgerTruncatedError`) instead of a bare
  re-raise — worth citing as the alternative "raise a named exception on exhaustion" idiom if the
  plan wants `db_read_with_retry` exhaustion to be distinguishable from an immediate failure.

**Exception classification for a Supabase gateway 504:** `postgrest.exceptions.APIError` exposes
`.code` as a string (confirmed via `analytics-service/services/audit.py:105`'s comment: *"APIError
shape is `{message, code, hint, details}`; `code` is the ... "*, and `main_worker.py`'s
`_is_undefined_function_structured` reads `getattr(exc, "code", None)` the same way for SQLSTATE
`42883`). **`classify_exception` in `analytics-service/services/job_worker.py:682` does NOT have
an explicit arm for `postgrest.exceptions.APIError` with `code == "504"` or any HTTP 5xx from
PostgREST** — that classifier's `HTTPException` branch only fires for FastAPI's own
`HTTPException`, and a bare `postgrest.exceptions.APIError` falls through to the final
`# Everything else ... return ("unknown", str(exc)[:500])` catch-all, which `job_worker.py`'s own
comment (line ~766-767) documents as "5xx -> falls through to 'unknown' below" (retried by
default in that module's job-retry semantics). This is `job_worker.py`'s compute-job-level
classifier, a **different, higher-level concern** than the low-level `db_read_with_retry` seam
this phase is building — `db_read_with_retry` should have its OWN narrow predicate (mirroring
`_is_undefined_function_structured`'s `getattr(exc, "code", None)` pattern) checking for `"504"`
structurally, not delegate to `classify_exception`. Recommended shape:

```python
def _is_gateway_timeout(exc: BaseException) -> bool:
    """postgrest.exceptions.APIError code '504' — Supabase's API gateway gave up
    before Postgres did. Retryable: a second attempt may land inside the window."""
    return getattr(exc, "code", None) == "504"
```

`[ASSUMED]` that `postgrest-py`'s `APIError.code` is populated with the literal string `"504"` for
a gateway timeout (as opposed to it being empty/None for a non-PostgREST-shaped 504 body, which is
plausible since a gateway timeout may not even be JSON). The ROADMAP's own cited CI sighting
(`postgrest.exceptions.APIError: {'message': 'JSON could not be generated', 'code': 504, ...}`)
supports this, but that is a `[CITED: ROADMAP prose, 2026-09-12 CI run PR #789]` secondhand
account, not something this research session re-ran. **Recommend the plan include a check of
`exc.code` at both string `"504"` and `int` `504` in `_is_gateway_timeout`, since the cited log
line shows `'code': 504` unquoted in a Python repr — ambiguous on the wire type — and a
`==` comparison against the wrong type silently never matches, which is exactly the fail-open
shape this phase exists to close.**

### Cursor batching for `cron_recompute()` — no in-repo precedent, a real design choice

**Confirmed absence:** grep across `analytics-service/` for `next_cursor`, `resume_from`,
`last_processed`, `watermark` returns zero hits outside unrelated exchange-pagination files
(`exchange_pagination.py`, `funding_fetch.py`, `sfox_read.py` — all *within-one-HTTP-call*
paginators against external exchanges, not cross-cron-tick state). `cron_recompute()` is invoked
by `net.http_post` inside `match_engine_cron_tick()` with a **fixed, parameterless** body
(`body := '{}'::jsonb`, confirmed by `Read` of `supabase/schema/functions/match_engine_cron_tick.sql`)
on every hourly tick — there is no channel for the PREVIOUS HTTP response to hand a cursor value
back INTO the next tick's request. **The cursor must therefore be persisted server-side by
`analytics-service` itself and read at the top of `cron_recompute()`.**

Candidate persistence locations, evaluated:

1. **Reuse `public.system_settings`** (`key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at,
   updated_by` — confirmed by `Read` of `supabase/migrations/20260907120000_...sql:167-172`).
   Store the cursor as a single TEXT row, e.g. `key='match_engine_cron_cursor'`,
   `value=<allocator uuid or empty string for "start over">`. Pro: table already exists,
   already service-role-writable, already the house mechanism Phase 164.7 established for
   non-secret operator config (its own comment calls it "the TEXT-valued sibling of
   system_flags"). Con: a single global row assumes ONE cron process; `cron_recompute()`
   already serializes per-allocator via `_get_recompute_lock`, so this is consistent with the
   existing single-writer assumption.
2. **A new dedicated table** (e.g. `match_engine_cron_state`). Pro: clean home, doesn't share a
   table designed for admin-editable config with an internal engine bookkeeping value an admin
   should never hand-edit. Con: a migration for a single-row table when `system_settings`
   already does the job is the kind of "don't hand-roll" the planner should weigh against
   D1/D2's "no forward migration is written by this phase" constraint — **this is worth flagging:
   if the plan wants a dedicated table, that IS a forward migration and needs its own
   justification against D2's "no forward migration" framing (D2 is about the SCHEDULE, not
   about state tables in general, so a state-table migration would not violate D1/D2's letter,
   but the planner should make that distinction explicit rather than let a reviewer discover it).**
3. **Deterministic re-derivation with no persisted cursor at all** — e.g. order allocators by
   `id`, and have each tick process a FIXED number starting from `(allocators_processed_so_far mod
   total) `, computed from a monotonic counter external to any row. Rejected as more complex than
   option 1 for no benefit — still needs a persisted counter somewhere.

**Recommendation for the plan: reuse `system_settings`, keyed pagination on `profiles.id`
(`WHERE id > cursor ORDER BY id LIMIT N`), wrapping to `NULL`/empty when a tick reaches the end of
the allocator set.** This is `[ASSUMED]` as the best shape — CONTEXT.md leaves "the exact batch
size N and cursor encoding" to Claude's Discretion, and this satisfies that framing, but the
planner should treat the PERSISTENCE LOCATION as a decision to state explicitly in the plan (not
merely the batch size), since — unlike batch size — it is not purely a "statement-level choice":
it determines whether `system_settings`' RLS/grants (already service-role-writable per Phase
164.7) are reused correctly or a new grant surface is opened.

**Downstream impact of `status="partial"` — confirmed SAFE, nothing reads it as a closed enum:**

- `TestCronResponseShape._REQUIRED_KEYS` (`analytics-service/tests/test_match_router.py:811-816`)
  is a **subset** assertion (`self._REQUIRED_KEYS <= set(body)`) with no closed-enum check on
  `status`'s VALUE — adding `"partial"` as a new value is additive-safe against this test.
- `docs/runbooks/match-engine.md:105-111` documents a `match_engine_recompute_total{status}`
  metric naming the closed set `ok`/`degraded`/`total_failure`/`disabled`/`skipped`/
  `no_allocators`/`empty_universe` — **but this metric name has ZERO hits anywhere in the repo
  outside this doc paragraph** (confirmed by grep across `*.py`/`*.ts`/`*.yml`/`*.json`); it is
  aspirational documentation, not a wired Prometheus/statsd counter. **The plan should update
  this runbook table to add `partial` to the documented status vocabulary** (a doc fix, not a
  code fix), and should note `partial` is a NORMAL completion of one batch slice, not a degraded
  state — it should not be conflated with `degraded`/`total_failure` in whatever external
  dashboard eventually reads these log lines.
- The prod-prober's `cron-obs.mjs` arm deliberately NEVER reads the JSON response body's
  `status` field (only `net._http_response`'s HTTP status code and `timed_out`/`error_msg`) —

### The retry seam skeleton (Area 1)

```python
# Source: house idiom from analytics-service/services/exchange.py:1296-1336
# (_okx_bills_fetch_with_backoff), adapted. Names/signature are Claude's Discretion.
import asyncio
import random


def _is_gateway_timeout(exc: BaseException) -> bool:
    """postgrest.exceptions.APIError surfacing a Supabase API-gateway 504.
    See RESEARCH.md 'The retry seam' for the [ASSUMED] str/int .code caveat."""
    code = getattr(exc, "code", None)
    return code in ("504", 504)


DB_READ_MAX_RETRIES = 3
DB_READ_BACKOFF_BASE_S = 1.0  # ~1/2/4s per CONTEXT.md's stated budget


async def db_read_with_retry(fn):
    """Retry a synchronous Supabase read with exponential backoff+jitter on a
    gateway timeout. NEVER wraps db_execute itself (CONTEXT.md Area 1) — this
    sits BESIDE it, called by the few read sites that need fail-closed
    semantics (kill switch, cron_recompute, _claim_priority, _reset)."""
    from services.db import db_execute  # avoid import cycle; confirm actual import shape in plan

    for attempt in range(DB_READ_MAX_RETRIES):
        try:
            return await db_execute(fn)
        except Exception as exc:
            if not _is_gateway_timeout(exc) or attempt == DB_READ_MAX_RETRIES - 1:
                raise
            delay = DB_READ_BACKOFF_BASE_S * (2 ** attempt) + random.uniform(0, 0.5)
            await asyncio.sleep(delay)
    raise RuntimeError("unreachable: db_read_with_retry")  # mirrors the house idiom's tail guard
```

This is illustrative, not a final shape — the sync/async boundary issue at `_engine_is_enabled`
(see "The retry seam is a NEW file/function" above) must be resolved by the plan before this
skeleton can be wired at all three call sites.

   under `asyncio.to_thread`?**
   - What we know: `_engine_is_enabled` is sync today and called via `asyncio.to_thread` at (at

     updated.

     to be discovered mid-implementation — see "The retry seam is a NEW file/function" above.
