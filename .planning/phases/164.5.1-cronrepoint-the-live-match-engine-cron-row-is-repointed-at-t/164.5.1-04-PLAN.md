Criterion 3: a pre-flight that ABORTS non-zero WITHOUT writing when the live jobid 1 command does
not match the committed manifest — proven by running it against a deliberately mismatched manifest,
not by inspection.

This is the gate that stands in front of plan 09's live `cron.schedule`. Without it, the Wave B
operator's only check that PROD is where the manifest says it is would be a human reading two
strings.

Locked decisions recorded and implemented here:
- **D3 (D-03)** — the manifest re-capture is a SCRIPT, not hand work — and D3 is ALREADY
  DISCHARGED: `export async function captureManifest({ seams, outPath, log, functionsDir })` lives
  in `scripts/prod-prober/run.mjs` (resolve by SYMBOL; the line drifts). ⛔ This plan does NOT write
  a second capture tool. It writes the SIBLING verb CONTEXT.md Area 3 specifies: "a VERB in
  `scripts/prod-prober/run.mjs`, beside `captureManifest` — same normalization, same
  `command_sha256` logic, no second notion of truth."
- **`[164.7-VAULT-ABSENT-RULE]`** is measured RESOLVED at HEAD and is NOT re-opened here. The rule
  was already redesigned by Phase 164.8.5: `cron-drift.mjs` asks "does this command REACH a Vault
  read that EXECUTES?" and `reachesVaultRead(spans, functionsDir)` resolves a function call against
  the committed snapshot directory `supabase/schema/functions/`, where
  `match_engine_cron_tick.sql` already exists carrying
  `FROM vault.decrypted_secrets WHERE name = 'analytics_service_key'`. So repointing jobid 1 to
  `SELECT public.match_engine_cron_tick();` should pass on the first try. ⛔ If it does not, that is
  a regression to investigate, NOT expected work, and NOT licence to widen the rule.

⚠️ And a repo-side reading never settles a production-side claim in this phase: the rule passing a
FIXTURE does not prove it passes against PROD's actual row. That is why the backstop truth above is
a backstop and is confirmed in plan 09, on live PROD, or not at all.
