# Phase 164.5.1.4 SYNCCURSOR — Round 2 Code Review

**Verdict: the fixes do NOT all hold.** WR-04 introduced a data-loss regression on
a path it was never meant to touch, and the unrequested test-anchor rewrite is what
made that regression invisible — the gate that detected it was retuned rather than
the code. Two further confirmed gaps: the CR-01 evidence conjunct is blind on Bybit
(the repo's primary cron-synced venue), and the migration's service_role grant rests
on a stated justification that is false.

All findings below were confirmed by execution, not by reading. Calibration was done
in memory (pytest `-p` plugins) and on an rsync'd scratch copy; the main checkout's
`routers/cron.py` and `tests/test_cron_router.py` were never modified.

## CRITICAL

### CR-01 (round 2): the WR-04 clamp is applied to the pre-phase key-cursor fallback, silently truncating catch-up for any key whose `last_sync_at` is older than the cap

**Where:** `analytics-service/routers/cron.py` — `_resume_floor_ms`, the clamp block
guarded by `MAX_MARKER_LOOKBACK_MS`.
**Disposition:** BLOCKER — data integrity, user-facing (missing trades → wrong analytics).

The constant's own derivation claims the cost is *"confined to the one strategy that
was already failing"* and that *"the capped worst case is a strict subset of the
pre-phase worst case."* Both are false. The clamp sits after the loop and applies to
whatever `floor` the loop produced — including the value produced by
`_strategy_resume_point`'s **key-cursor fallback**, i.e. the case where the strategy
has NO marker row at all and nothing has ever been held.

Measured directly against the shipped function, `now` fixed, key cursor 200 days old,
`strategy_cursors={}` (the exact state the migration lands in):

- eligible strategies present → floor clamped to exactly 30 days, and the warning
  names an innocent strategy as "holding" a resume point it never held
- no eligible strategies → unclamped (the branch the comment says is preserved)

So the two branches that were supposed to be identical pre-phase behaviour now
disagree, and the one that gets clamped is the common one.

This directly contradicts the shipped column comment in
`supabase/migrations/20260919120000_strategy_sync_cursors.sql`, which states that
state (1) "NO ROW for this strategy … is what makes this migration inert the moment
it lands." It is not inert: for any key whose `api_keys.last_sync_at` is older than
30 days, the fetch window is now truncated and the trades older than the cap are
fetched by no tick, ever.

**Reachable, not theoretical.** `api_keys.last_sync_at` is deliberately preserved
across a disconnect/reconnect cycle (`reconnect_allocator_api_key` — "last_sync_at is
preserved so 'last successful sync' history stays accurate"). It is also preserved
across the credential-failure `is_active=False` deactivation path. A key disconnected
or deactivated for more than 30 days and then reconnected used to catch up in full;
it now silently drops everything older than the cap. No strategy on that key was
failing. Nothing about that key is the scenario WR-04 was written for.

**Fix:** clamp only a floor that came from a per-strategy MARKER, never one that came
from the key-cursor fallback. Track provenance in the loop and gate on it:

```python
floor_from_marker = False
for sid in strategy_ids:
    resume_point = _strategy_resume_point(sid, strategy_cursors, key_cursor)
    ...
    if floor is None or parsed < floor:
        floor, floor_sid = parsed, sid
        floor_from_marker = sid in strategy_cursors   # membership, same rule as the resolver
...
if floor_from_marker and floor < oldest_allowed_ms:
    ...clamp...
```

That keeps WR-04's whole purpose (bounding an unclearable HOLD) while leaving the
pre-phase path byte-identical, which is what "purely additive" was supposed to mean.
The warning text must also stop naming a strategy when the floor came from the key
cursor.

### CR-02 (round 2): the test-anchor rewrite converted a true RED into a GREEN — the gate that caught CR-01 was retuned instead of the code

**Where:** `analytics-service/tests/test_cron_router.py` — `_ONE_TICK_AGO`, consumed as
`T0` by `TestSyncCursorPerStrategyResume`, `TestCronSyncDeliversStrategyCursorsToFanOut`,
`TestHeldStrategyMarkersAreNamedInTheEnvelope`.
**Disposition:** BLOCKER — a data-integrity gate was weakened to accommodate a new
defect. (Same defect as CR-01; listed separately because the remedy is different and
because the claim "no test's meaning changed" must be withdrawn.)

The claim under review was: *"every assertion is relative to `T0` so no test's meaning
changed."* **That claim is false for one gate, and it is the load-bearing one.**

`TestSyncCursorPerStrategyResume::test_partial_fanout_leaves_failed_strategy_window_refetchable`
carries this assertion, with this stated meaning:

> INERT ON ARRIVAL: with no marker rows yet every strategy is ABSENT from the mapping
> and must fall back to the key cursor (since_ms=…)

Its meaning is "with no marker rows, `since_ms` is byte-identical to
`parse_since_ms(key_cursor)`." After the anchor move that assertion is only ever
exercised for key cursors younger than the cap, so the property it names is no longer
pinned at all.

**Measured**, by restoring the pre-fix literal anchor purely in memory (a `-p` plugin
that rebinds the class attribute after collection — nothing on disk touched):

```
3 failed, 14 passed
FAILED …::test_partial_fanout_leaves_failed_strategy_window_refetchable
FAILED …::test_crashed_fetch_does_not_clear_an_existing_hold
FAILED …::test_failed_recompute_enqueue_holds_that_strategys_marker

E  AssertionError: INERT ON ARRIVAL: with no marker rows yet every strategy is
   ABSENT from the mapping and must fall back to the key cursor (since_ms=<t0>).
   Got since_ms=<t0 + ~218 days>.
```

The RED was not a stale literal reporting nothing. It was the inertness gate correctly
reporting CR-01. The anchor move made the report go away.

**Fix:** fix CR-01, then restore an anchor that is actually older than the cap for at
least the inertness arm — e.g. keep `_ONE_TICK_AGO` for the hold arms (where "one tick
ago" is the honest stand-in) and add a dedicated arm asserting
`_resume_floor_ms(ids, {}, key_cursor_older_than_the_cap) == parse_since_ms(key_cursor)`.
Without that arm CR-01 can be reintroduced at any time with a green suite.

## WARNINGS

### WR-01 (round 2): `fetch_degraded` is blind on Bybit — the CR-01 idle-disjunct fix does not cover the repo's primary cron-synced venue

**Where:** `analytics-service/routers/cron.py` (`fetch_degraded`) ×
`analytics-service/services/exchange.py::fetch_daily_pnl` (the Bybit branch's inner
`except Exception`).
**Disposition:** MEETS THE BAR — data integrity.

`fetch_degraded` is only as good as `daily_pnl_fetch_error`, and that flag is set by
`fetch_daily_pnl`'s OUTERMOST handler only. The Bybit branch wraps its entire body —
paging, dedup, daily aggregation, the terminal `daily_pnl.extend(...)` — in an inner
`except Exception` that re-raises only `ccxt.RateLimitExceeded`, logs a warning for
everything else, and falls through. The outer handler never sees it, so the flag is
never stamped.

**Measured** with a live probe against the real `fetch_daily_pnl` (no network, no DB):

| venue | rows returned on a venue `NetworkError` | `daily_pnl_fetch_error` |
|---|---|---|
| okx | 0 | **True** |
| binance | 0 | **True** |
| **bybit** | **0** | **False** |

Consequence on the cron path, which is exactly the loss CR-01's conjunct was written
to prevent, arriving by a different road: a Bybit 502/timeout returns `[]`,
`fetch_degraded` is False, `not trades` is True, and **every held marker on that key
advances to `now`**, discarding a hold of arbitrary age. That window is then fetched by
no later tick. Bybit is named in `cron.py`'s own comments as the cron-synced venue this
whole mechanism exists for.

The gate cannot see this: `_run_tick` stubs `get_and_clear_last_dq_flags` outright, so
it proves the router reads the flag and proves nothing about whether the flag is ever
set.

**Fix:** stamp `_record_dq_flag("daily_pnl_fetch_error", True)` in the Bybit inner
handler (it already declines to re-raise, so the flag is the only channel left), and
add an arm that drives the real `fetch_daily_pnl` with a failing Bybit client and
asserts the flag.

Related, same conjunct: a **partial** degraded fetch (`fetch_degraded` True with
`trades` non-empty) still advances any strategy whose store succeeded. That matches
pre-phase key-cursor behaviour so it is not a regression, but the conjunct's stated
intent — "only advance on evidence the fetch was complete" — is not what ships.

### WR-02 (round 2): the migration grants service_role nothing, on a justification that is factually wrong, and the new RLS gate has no arm that would catch it

**Where:** `supabase/migrations/20260919120000_strategy_sync_cursors.sql` (STEP 2) and
`supabase/tests/test_strategy_sync_cursors_rls.sql` (GRANT 1).
**Disposition:** MEETS THE BAR — the phase is inert in production if it is wrong.

At HEAD the migration ships `REVOKE ALL … FROM PUBLIC, anon, authenticated` and no
`GRANT` at all, justified in the file as:

> service_role is untouched — it reaches the table by BYPASSRLS at the role level, not
> through this grant.

`BYPASSRLS` is a **row-level** exemption and confers no object-level privilege.
service_role reaches this table only if Supabase's bootstrap
`ALTER DEFAULT PRIVILEGES … GRANT ALL ON TABLES` applied to the role that created it —
which nothing in this file establishes or checks, and which is keyed to grantor role
and schema. If it did not apply, every marker read and every marker write raises 42501
on every tick forever, the phase is inert, and per-strategy stranding continues
unchanged.

The nine-arm RLS gate closing WR-05 is entirely about DENIAL. It has no arm asserting
the positive capability the phase depends on — that the service-role writer can
actually INSERT/UPDATE/SELECT this table — and it repeats the same false BYPASSRLS
sentence in its own GRANT 1 failure message.

**Fix:** ship the explicit `GRANT SELECT, INSERT, UPDATE, DELETE ON
strategy_sync_cursors TO service_role;` and add a tenth arm that asserts service_role
holds it (calibrated by deleting the GRANT).

⚠️ An uncommitted working-tree edit at review time appears to be adding exactly this.
This finding is recorded against HEAD (`4f0ad37c`), which is what was submitted.

### WR-03 (round 2): `_is_missing_cursor_table` over-matches column-level faults on this table

**Where:** `analytics-service/routers/cron.py::_is_missing_cursor_table`, probe 3.
**Disposition:** BELOW THE BAR (log fidelity — the envelope field is still populated),
but it defeats the stated purpose of the conjunctive probe.

The probe is `table_name in blob and ("does not exist" in blob or "schema cache" in
blob)`. Measured against the shipped helper:

| error | classified "missing table" | correct? |
|---|---|---|
| `PGRST204` — could not find the `<col>` column of `<table>` in the schema cache | **True** | **no** |
| `42703` — column `<col>` of relation `<table>` does not exist | **True** | **no** |
| `42501` permission denied | False | yes |
| RLS `new row violates …` | False | yes |
| `23503` FK violation | False | yes |

A stale PostgREST schema cache right after the apply (the single most common
post-migration condition, since the reload is async) or any future column drift
produces PGRST204, which is now latched to one process-lifetime warning with no
traceback — and the marker write silently never persists while the log says "rollout
window." That is the class of misclassification the helper's own docstring says it
must not cause; it just guessed the wrong sibling error.

**Fix:** add `"column" not in blob` to the conjunct, or require the phrase to be
relation-shaped (`f'relation "{table}" does not exist'` / `f"the table '…{table}'"`).
Pin it with the two rows above.

### WR-04 (round 2): the cap's magnitude — the dial that decides how much history is abandoned — is pinned by nothing

**Where:** `analytics-service/routers/cron.py::MAX_MARKER_LOOKBACK_MS` and every arm
in `TestUnclearableHoldCannotWedgeTheWholeKey` (all read the constant rather than a
literal).
**Disposition:** BELOW THE BAR on its own (test coverage), but it is the direct
consequence of CR-02 and it is what would let CR-01 get worse unnoticed.

**Measured:** rebinding `MAX_MARKER_LOOKBACK_MS` in memory and re-running the file:

- `30 days → 1 hour`: **72 passed** — completely green
- `30 days → 1 minute`: 3 failed (only because it drops below the 15-minute anchor)

So the constant can be reduced by a factor of 720, permanently abandoning 30 days of
trade history per held strategy, with the suite reporting no change at all. Before the
anchor move the ~248-day anchor would have caught any cap below 248 days.

**Fix:** one arm asserting the shipped magnitude by measurement (a hold at
`cap - 1 day` is honoured, a hold at `cap + 1 day` is clamped, expressed against a
literal day count, not against the constant).

## INFO

### IN-01: the `_STRATEGY_CURSOR_ROW_RETRY_LIMIT` skip branch has no dedicated arm

The `skipped = strategy_cursor_rows[LIMIT:]` branch and its
`"not retried: per-row fallback limit (N) reached"` envelope wording are only reachable
at a fan-out above 25, which the code's own comment says will not occur. Confirmed
exercisable by forcing the limit to 0 in memory (one existing test then fails), so it
is not dead code — but nothing pins its envelope contract. The bound itself (25 serial
round-trips inside `KEY_SYNC_TIMEOUT`, on a path reached only after the `api_keys`
UPDATE has already committed) is a reasonable judgement call; the ordering risk it
creates is already documented in the block's own comment.

### IN-02: `_missing_cursor_table_warned` is unfixtured process-global mutable state

Two tests reset it by direct assignment. Any future test that trips the missing-table
classification without resetting will silently poison a later arm's latch expectation.
A `@pytest.fixture(autouse=True)` reset in the class would remove the hazard. In
production the latch never re-arms, so a table dropped after the rollout window is
silent in the log forever — documented and accepted, envelope field unaffected.
