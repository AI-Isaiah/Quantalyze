**What the key cursor is still load-bearing for**, and this is why "replaced" would have been the wrong word:

1. **It is the fallback for every strategy with no marker row.** That is the state of every strategy the moment the table lands, and the state of any strategy added later, and the state of every strategy on any tick where the marker lookup fails. `_strategy_resume_point` returns it by membership — `strategy_id in strategy_cursors` — precisely so "no row" resolves to the key cursor rather than to "re-fetch from the start of history".
2. **It still carries the key-level watermark on the same write as the balance.** `update_data` conditionally sets `last_sync_at` under the unchanged gate AND `account_balance_usdt` when a balance was fetched, in one `api_keys` UPDATE. The balance write is independent of the cursor gate (the code says so where a reader will ask), so touching the gate would have reached further than the cursor.
3. **It remains the only cursor for a key with no eligible strategies.** `_resume_floor_ms` parses the key cursor directly when `strategy_ids` is empty — today's behaviour on the five `private` keys, unchanged.

**What the marker took over:** the resume FLOOR for the fetch window (`_resume_floor_ms` takes the earliest resume point across a key's eligible strategies, because one `fetch_all_trades` call serves the whole key) and the per-strategy HOLD (a strategy that failed to store, or whose recompute enqueue raised, keeps its pre-tick resume point written down this tick).

**The test evidence, named:**

- **`TestC0198CursorOnlyAdvancesWhenStored` — 3 members, all passing with their bodies unchanged** (`test_C0198_zero_stored_does_not_advance_last_sync_at`, `test_C0198_partial_success_does_advance_last_sync_at`, `test_D03_empty_strategy_ids_with_trades_does_not_advance_cursor`). One docstring was corrected in plan 03; every assertion is byte-unchanged. These are the gates that would have reddened had the key-level discipline moved.
- **The consequence gate and its control** — `TestSyncCursorPerStrategyResume` pins the `since_ms` the NEXT tick asks the venue for, and its control asserts tick 1 really produced marker rows before asserting the window advanced, so it cannot pass for the right-looking wrong reason. Calibrated by neutering the marker READ with the WRITE left fully intact; the observed RED is quoted in `164.5.1.4-CALIBRATION.md` section 1.
- **The diff check over the protected region** — the `0` in the table above is re-derivable from `git diff origin/main..HEAD -- analytics-service/routers/cron.py` and is what fails if a later edit removes a line there.

⭐ **Why this is the correct disposition and not a compromise.** Replacing the key cursor would have meant deciding what happens to a key with no eligible strategies and re-deriving C-0198's advance semantics from scratch — and the backlog entry's own standing note says the symmetric defect (holding the whole key's cursor on any partial failure starves the succeeding strategies) is exactly what C-0198 chose to avoid. ## Verdict 2 — Phase 164.5.1.3 SYNCADMIT: unblocked **by the migration applying to PROD**, not by this branch merging

**The plain answer with its condition in it:** everything SYNCADMIT was blocked on is built, calibrated and committed on this branch — so it is unblocked as a matter of REPOSITORY state — but the protection SYNCADMIT needs does not exist in production until `20260919120000_strategy_sync_cursors.sql` has applied to PROD. A verdict reading simply "unblocked" would be true of the repo and false of production.

**What SYNCADMIT was blocked ON.** Admitting the owner-only status to `ALLOWED_STRATEGY_STATUSES` makes the five `private` production keys start fanning out to multiple strategies. Today those keys carry `strategy_ids == []` every tick, so the fan-out loop never runs and the stranding path is unreachable on them. The widening makes that path go live on precisely the keys the whole 164.5.1.x line exists to protect — which is why the founder re-ordered the queue so this phase lands first.

**What this phase shipped against it, named:**

- `strategy_sync_cursors` — the per-STRATEGY container (whole-PK `strategy_id`, cascading FK, nullable `last_sync_at`, deny-all RLS, `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, `GRANT ALL ... TO service_role`, 8-arm catalog-only self-verify on every apply).
- The membership-based read and the N-way resume floor.
- The marker write for **every** strategy in the fan-out, held or advancing, under `((not trades) and not fetch_degraded) or (stored > 0 and sid not in recompute_enqueue_errors)` — the `not fetch_degraded` conjunct added in round 2 (WR-01), without which a crashed venue fetch reads as an idle tick and clears a hold.

**Nothing shipped partially.** CONTEXT requires a partial remedy to be reported here rather than discovered by the next phase; both stranding halves — trade storage and recompute enqueue — have their own calibrated gate, so there is no partial to report on the code side.

**The condition, and where it is confirmed.** Both new Supabase paths **fail open** by design: a failed marker lookup gives every key an empty mapping (which *is* the absent-row semantics, so the tick degrades to today's behaviour rather than to a wrong window), and a failed marker write leaves markers behind so the next tick over-fetches — idempotent, because `sync_trades` deletes payload-window-scoped before re-inserting. That makes the deploy-order skew safe in **both** directions, and it is the same property that makes the fix inert while the table is absent.

So the thing to check is a **workflow run, not a file in the tree**: the `Supabase Migrate` run for the merge commit, with `apply-test` green against shared TEST and the `apply` job green behind the `Production` environment's human reviewer. Verified in the workflow itself rather than taken from the plan: it triggers on `push` to `main` with `paths: supabase/migrations/**`; `apply-test` runs in `environment: Test`; `apply` carries `needs: [plan, apply-test]` with `if: needs.plan.outputs.configured == 'true' && needs.apply-test.result == 'success'` and `environment: Production`.

⭐ **The recommendation that follows from the condition:** SYNCADMIT may be planned now and must not be **deployed** before that PROD apply has succeeded. The ordering the founder chose holds only if the migration lands first; a widening that reaches production ahead of the table re-opens the exact path this phase closed, silently, because the fail-open degradation is indistinguishable from normal operation.

### 3. The two decisions most likely to be challenged

Carried forward from plan 01's SUMMARY, each with its precedent, so the reviewer does not have to find them:

The reason is the table's posture: `allocator_holdings` HAS an owner-facing tier, so its service-role arm documents "service_role **in addition to** owners" — the wrong sentence for a table with no owners. Both forms rest on `service_role` bypassing RLS by default (ADR-0003); `USING (false)` is the strictly narrower **written** grant, since the `auth.role()` form would also admit any non-bypassing connection presenting that claim. - **The absence of a dedicated SQL gate file.** All 7 existing `*_rls.sql` gates are built around an owner-facing tier and reference `auth.uid()`; **zero** reference a deny-all policy, and the closest structural analog is named by zero gate files. What stands in its place is stronger on the axis that matters here: the migration's own catalog-only self-verify runs on **every apply** — the disposable lane, shared TEST on merge, and PROD — whereas a `supabase/tests` gate runs only when `sql-tests` runs.
