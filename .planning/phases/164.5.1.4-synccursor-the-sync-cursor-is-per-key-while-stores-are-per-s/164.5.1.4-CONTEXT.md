<domain>
## Phase Boundary

Stop a partial fan-out in `cron_sync` from permanently stranding the trade window of the strategies
whose `sync_trades` RPC failed. The resume cursor is per-KEY (`api_keys.last_sync_at`) while stores
are per-STRATEGY, so one succeeding sibling advances the cursor past every failing sibling's window.

**IN scope:** the per-strategy resume mechanism; the calibrated gate proving a partial fan-out no
longer strands; the accurate disposition of `SYNC-CURSOR-PER-KEY-STRANDS-STRATEGY-01`; a stated
verdict on whether 164.5.1.3 SYNCADMIT is unblocked.

**OUT of scope:** admitting `private` to `ALLOWED_STRATEGY_STATUSES` (that is 164.5.1.3, and it is
BLOCKED ON THIS PHASE); the position-poll predicate; `enqueue_ledger_composite_refresh`.

⛔ **This phase is the gate in front of 164.5.1.3.** The founder re-ordered the queue on 2026-09-19
so this lands first. If this phase ships only a partial remedy, say plainly that SYNCADMIT stays
blocked rather than letting the next phase discover it.

<decisions>
## Implementation Decisions

### Area 1 — Fix shape: the two candidate homes were MEASURED, and neither works

- ⛔ **`api_keys.last_fetched_trade_timestamp` (migration 045) is NOT the home, and this is settled by
  measurement rather than argument.** The brief asked to investigate it first. Measured at HEAD:
  `supabase/migrations/20260416125428_sync_checkpoints.sql` is `ALTER TABLE api_keys ADD COLUMN
  last_fetched_trade_timestamp` — **per-KEY**, exactly the granularity that causes this defect. It
  splits the checkpoint by PURPOSE (fetched-vs-stored), not by STRATEGY. Re-using it would reproduce
  the bug in a second column.
- ⛔ **`advance_sync_cursor` is not the home either.** `20260602173710_advance_sync_cursor_claim_token_fence.sql`
  takes `p_api_key_id` / `p_claim_token` / `p_job_id` — per-KEY, fenced to a JOB. Right mechanism,
  wrong axis.
- ⭐ **MEASURED: no per-strategy sync state exists anywhere in the schema today.** So the remedy
  requires NEW state keyed by strategy. There is no cheaper existing home to re-use, and the plan
  should not spend effort looking for one — record this measurement instead of repeating the search.
- **DECISION: a per-STRATEGY resume marker.** Keyed so that one strategy's failure cannot move
  another strategy's resume point. ⚠️ The precise shape (a column on a strategy-scoped table versus
  a `(api_key_id, strategy_id)` checkpoint table) is a planning call — the binding constraint is the
  KEY, not the container: it must not be per-`api_key_id` alone.
- ⛔ **`should_advance_cursor` is NOT touched.** Holding the whole key's cursor on any partial
  failure starves the SUCCEEDING strategies into permanent re-fetch — the symmetric defect, and the
  reason C-0198 chose to advance. The expression stays byte-identical.

### Area 2 — A second divergence found while measuring, and the plan must not trip over it

- ⭐ **There are TWO sync paths with DIFFERENT cursor discipline, and only one is in scope.**
  `services/job_worker.py::run_sync_trades_job` reads `preferred=ctx.key_row["last_fetched_trade_timestamp"]`
  and advances through the fenced `advance_sync_cursor` RPC. `routers/cron.py::_sync_single_key`
  reads `parse_since_ms(key_row.get("last_sync_at"))` and writes
  `update_data["last_sync_at"] = ...` **directly — no claim token, no fence, and it never touches
  `last_fetched_trade_timestamp` at all.**
- **The defect under repair lives in the cron path.** ⛔ Do NOT "harmonise" the two paths as a side
  effect — that is a much larger change, it is not what this phase was opened for, and the fenced
  path is not obviously wrong. If the divergence deserves attention, book it; do not absorb it.

### Area 3 — The recompute-enqueue stranding path (success criterion 4)

- ⭐ **DECISION: the remedy COVERS it, and covering it is nearly free given the shape chosen.**
- **Reasoning.** Both failures are the same statement — *"this strategy's window was not fully
  processed"*. A per-strategy marker that advances only when the strategy's window has been stored
  **and** its `derive_broker_dailies` job enqueued makes the next tick re-drive both. The code's own
  comment records the current behaviour: a failed enqueue is never re-driven because `last_sync_at`
  has already advanced.
- **Re-driving is SAFE, measured:** `sync_trades` does a payload-window-scoped delete (recorded in
  `_sync_single_key`'s own comments), so re-storing an already-stored window is idempotent; and
  `enqueue_compute_job` is dedup-safe via the partial unique index
  `compute_jobs_one_inflight_per_kind_strategy`. Neither re-drive duplicates anything.
- ⚠️ **It is user-facing, which is why it is not merely deferred.** The block's comment records the
  Phase-18 consequence of the analogous gap: cron-synced strategies were never recomputed and their
  dashboard KPIs froze until a user-triggered recompute.
- ⚠️ **If the marker shape chosen in planning does NOT make this cheap, it is fix-or-book, never
  silently dropped** — and in that case SYNCADMIT's exposure must be re-judged, because the five
  private keys would still acquire a live lag path.

### Area 4 — Migration discipline (this phase almost certainly ships one)

- ⛔ **3 reviewers BEFORE any apply** — `migration-reviewer`, `rls-policy-auditor`,
  `silent-failure-hunter` — then merge → `apply-test` → the PROD apply behind the `Production`
  human reviewer gate. Budget for it; it is the long pole.
- ⛔ **No data-reading `RAISE EXCEPTION` in the migration.** Shared TEST holds PROD's catalogue and
  never its data, so a count-asserting `DO` block can pass PROD and REFUSE TEST — and a refused TEST
  apply BLOCKS the PROD apply (`[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`).
- ⛔ No `cron.schedule(...)` inside a migration — that is a LIVE OP.
- **Backfill posture:** a new marker starts NULL for every existing row. The reader must treat NULL
  as "fall back to the key cursor" so the change is inert on day one and cannot strand anything
  during rollout. State that explicitly rather than leaving it to the reader.

### Area 5 — The calibrated gate (success criterion 2) — ⛔ ANTI-VACUITY BLOCKS HERE

- This is DATA INTEGRITY, so a gate that cannot fail is worse than none.
- **Method is non-negotiable:** neuter → observe RED → restore → verify byte-identical with `cmp` →
  record the OBSERVED failure text in the artifact. ⛔ Never `git checkout --` / `git restore` /
  `git stash` in the harness; `cp` byte backups, re-taken after EVERY edit.
- **The gate must pin the CONSEQUENCE, not the implementation's own formula:** a two-strategy key
  where one RPC raises must leave the failed strategy's window re-drivable on the next tick. A test
  that merely asserts the new column is written would pass against a marker nothing reads.
- ⛔ **All three `TestC0198CursorOnlyAdvancesWhenStored` members must still pass UNCHANGED**
  (`test_C0198_zero_stored_does_not_advance_last_sync_at`,
  `test_C0198_partial_success_does_advance_last_sync_at`,
  `test_D03_empty_strategy_ids_with_trades_does_not_advance_cursor`). ⚠️ The second one's docstring
  justifies the advance from the successful strategy's side and never names the cost to the failed
  one — if its BEHAVIOUR still holds, correct the DOCSTRING to state what is now recovered.

## Existing Code Insights

### Measured at HEAD (2026-09-19, main at 4844b495)

- `should_advance_cursor = (not trades) or synced_count > 0`, with
  `synced_count = sum(per_strategy_stored.values())` — aggregation across strategies is the defect's
  mechanism. CONFIRMED.
- `per_strategy_stored[sid] = stored` is written per strategy inside the fan-out. The per-strategy
  breakdown ALREADY EXISTS in memory — the gap is that nothing PERSISTS it.
- `recompute_strategy_ids` is built from `per_strategy_stored` entries with `stored > 0`, then one
  `enqueue_compute_job(p_kind="derive_broker_dailies")` per strategy.
- ⛔ `api_keys.last_fetched_trade_timestamp` and `advance_sync_cursor(p_api_key_id, p_claim_token,
  p_job_id, …)` are both per-KEY. Neither is a per-strategy home.
- ⛔ No per-strategy sync checkpoint table or column exists.

### Established patterns to follow

- Terminal sync statuses register in `SYNC_STATUS_SUMMARY_KEYS`; counters are DERIVED from it.
- Per-strategy failures are best-effort and surfaced in the result envelope (`strategy_errors`,
  `recompute_enqueue_errors`) so the summary alarm sees them rather than only Sentry.
- `sync_trades` deletes payload-window-scoped, so a re-drive is idempotent.

### Integration points

- `_sync_single_key` — the fan-out loop, the cursor gate, the `held` classification.
- The recompute tail — `recompute_strategy_ids` / `enqueue_compute_job`.
- `parse_since_ms` — how a resume point becomes a fetch window.
