## Summary

The defect lives entirely in `analytics-service/routers/cron.py::_sync_single_key`
(`[VERIFIED: analytics-service/routers/cron.py:195-671]`, read in full this session). One `api_keys`
row can back N `strategies` rows; `_sync_single_key` fetches ONE batch of trades per KEY
(`since_ms` computed once, before the per-strategy loop, at `cron.py:386`) and then calls the
`sync_trades` RPC once per linked strategy with the SAME trades payload
(`cron.py:401-402`). The only resume cursor that exists today, `api_keys.last_sync_at`, is written
once per key (`cron.py:526-531`) gated by `should_advance_cursor = (not trades) or synced_count > 0`
where `synced_count = sum(per_strategy_stored.values())` — a SUM across every strategy on the key.
A single succeeding sibling makes `synced_count > 0` true and advances the shared cursor past every
failing sibling's window, permanently (the shared cursor cannot express "advance for A, hold for
B"). `per_strategy_stored[sid]` is already computed in memory per strategy
(`cron.py:398, 423, 485`) — nothing persists it.

**Primary recommendation:** add a new per-strategy checkpoint table, `PRIMARY KEY (strategy_id)`
with `strategy_id UUID NOT NULL REFERENCES strategies(id) ON DELETE CASCADE` (matching every other
strategy-scoped table in this schema — `[VERIFIED: grep across supabase/migrations/*.sql]`, 13+
tables all use this exact FK shape), holding one nullable `TIMESTAMPTZ` watermark. Do NOT key it on
`(api_key_id, strategy_id)` — `strategies.api_key_id` is itself mutable (`ON DELETE SET NULL`,
`[VERIFIED: supabase/migrations/20260405061911_initial_schema.sql:51]`), so a strategy re-pointed to
a different key would orphan a composite-keyed row; keying on `strategy_id` alone means the cursor
travels with the strategy regardless of which key currently backs it. RLS: service-role-only
(`FOR ALL USING (auth.role() = 'service_role')`), no owner-select policy — this is internal
cron-operational state, and putting it in a NEW table (rather than a column on the publicly-SELECT-
able `strategies` table) avoids exposing an internal sync watermark to anonymous readers of
`published` strategies. Read path: compute the per-key fetch floor as the MIN of each eligible
strategy's marker (falling back to `api_keys.last_sync_at` when the marker is NULL), so the single
per-key fetch always covers the slowest linked strategy's outstanding window. Write path: advance
each strategy's own marker only when `(not trades) or (per_strategy_stored[sid] > 0 and the
strategy's `derive_broker_dailies` enqueue did not fail)` — this single condition closes both the
cursor-stranding defect (success criterion 2/3) and the recompute-enqueue stranding defect (success
criterion 4) with one write, per CONTEXT Area 3's own reasoning.

### Recommended container shape (Claude's Discretion in CONTEXT — this is the research
recommendation, not a locked decision)

**New table**, not a column on `strategies`:

```sql
CREATE TABLE IF NOT EXISTS strategy_sync_cursors (
  strategy_id           UUID PRIMARY KEY REFERENCES strategies(id) ON DELETE CASCADE,
  last_synced_trade_at  TIMESTAMPTZ,   -- NULL = never checkpointed; fall back to api_keys.last_sync_at
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Why a new table over a column on `strategies`:**
- `strategies` carries a public-read RLS policy — `[VERIFIED:
  supabase/migrations/20260405061912_rls_policies.sql:27-29]`: `CREATE POLICY strategies_read ON
  strategies FOR SELECT USING (status = 'published' OR user_id = auth.uid());` — so any column added
  to `strategies` is world-readable for every `published` strategy. Every other sync-cursor column in
  this schema (`last_sync_at`, `last_fetched_trade_timestamp`) lives on `api_keys`, which is
  owner-only (`[VERIFIED: supabase/migrations/20260405061912_rls_policies.sql:20]`:
  `CREATE POLICY api_keys_owner ON api_keys FOR ALL USING (user_id = auth.uid())`). A new table with
  no owner-select policy preserves that same "internal cursor state is never publicly readable"
  posture without needing a column-level `REVOKE`.
- **FK/cascade on strategy deletion:** every strategy-scoped table in this schema uses
  `strategy_id UUID NOT NULL REFERENCES strategies(id) ON DELETE CASCADE` — `[VERIFIED: grep -n
  "REFERENCES strategies" supabase/migrations/*.sql]` confirms this exact pattern on `trades`,
  `position_snapshots`, `weight_snapshots`, `positions`, `funding_fees`, `reconciliation` rows,
  `compute_jobs`, `deck_strategies`, `user_favorites`, and more (13+ occurrences, all `ON DELETE
  CASCADE` except two intentionally-nullable back-references). `ON DELETE CASCADE` on `strategy_id`
  is the established, unsurprising choice: deleting a strategy silently removes its cursor row with
  it, nothing orphaned.
- **Strategy re-pointed to a different key:** `strategies.api_key_id` is `UUID REFERENCES api_keys ON
  DELETE SET NULL` — `[VERIFIED: supabase/migrations/20260405061911_initial_schema.sql:51]`. It is
  mutable and nullable. Keying the marker on `strategy_id` alone (no `api_key_id` in the table at
  all) means a re-point is a non-event for the cursor: the strategy's resume point is a property of
  the strategy's own trade history, not of which key currently syncs it. A `(api_key_id,
  strategy_id)` composite key would need extra logic to migrate/merge rows on re-point and would
  silently strand the OLD composite row — avoid that complexity entirely by not including
  `api_key_id` in the table.
- **Index shape for the read path:** `PRIMARY KEY (strategy_id)` already gives an index on the exact
  column the read path filters by (`WHERE strategy_id IN (...)`) — no secondary index needed.

**RLS (service-role-only, no owner-select):**

```sql
ALTER TABLE strategy_sync_cursors ENABLE ROW LEVEL SECURITY;

CREATE POLICY strategy_sync_cursors_service_all ON strategy_sync_cursors FOR ALL
  USING (auth.role() = 'service_role')
  WITH CHECK (auth.role() = 'service_role');
```

This mirrors the explicit service-role policy pattern already used for `allocator_holdings`
(`[VERIFIED: supabase/migrations/20260420073003_allocator_holdings.sql:717-720]`: "Explicit
service_role FOR ALL policy (belt-and-suspenders; service_role also bypasses RLS by default per
ADR-0003, but an explicit policy documents intent...)"). ⚠️ **Deliberately NO owner-select policy** —
unlike `allocator_holdings`, nothing in CONTEXT.md asks for user-facing visibility into this cursor,
and the api_keys precedent (owner-only, not even that) argues for the narrower posture. If a future
phase wants to surface "last synced" in the UI, add the policy then — don't pre-grant unused
surface, which is exactly what `rls-policy-auditor` flags.

### Read path — per-strategy floor with per-key fallback

`parse_since_ms(last_sync_at, preferred=None)` (`[VERIFIED: analytics-service/services/exchange.py:
2744-2773]`, read in full) already supports a `preferred` override — that mechanism exists but is
currently used only by `job_worker.py`'s `preferred=ctx.key_row.get("last_fetched_trade_timestamp")`
call (`[VERIFIED: analytics-service/services/job_worker.py:1420-1422]`), never by `cron.py`.
`cron.py`'s `since_ms = parse_since_ms(key_row.get("last_sync_at"))` (`cron.py:386`) is a SINGLE call
computed once per key, BEFORE the per-strategy loop, and its result feeds ONE `fetch_all_trades`
call whose result (`trades`) is then handed identically to every strategy's `sync_trades` RPC. There
is no per-strategy fetch today — only a per-strategy STORE of the same fetched batch. This shapes the
read-path design: since the fetch is a single call per key, the "resume point" that matters is the
EARLIEST point any eligible strategy on the key still needs — fetching a WIDER window than a
caught-up sibling strictly needs is safe (idempotent re-store, see below), so there is no harm in
over-fetching for an already-current strategy.

```python
# In _sync_single_key, replacing the single line at cron.py:386
strategy_cursors: dict[str, str | None] = key_row.get("strategy_cursors") or {}
key_cursor = key_row.get("last_sync_at")

resume_points = [
    strategy_cursors.get(sid) if strategy_cursors.get(sid) is not None else key_cursor
    for sid in strategy_ids
] or [key_cursor]  # no eligible strategy on this key: unchanged, key-cursor-only behaviour

if any(rp is None for rp in resume_points):
    since_ms = None  # a never-synced strategy (or key) forces a full-history fetch
else:
    parsed = [parse_since_ms(rp) for rp in resume_points]
    since_ms = None if any(p is None for p in parsed) else min(parsed)

trades = await fetch_all_trades(exchange, since_ms=since_ms)
```

⚠️ This snippet is a **research design proposal**, not verified-working code — it has not been run.
It is offered as the shape that satisfies every locked constraint (NULL marker falls back to key
cursor; no strategy's window is ever skipped; `should_advance_cursor`/the key-cursor write path is
untouched). The planner should treat it as a strong starting point, not a drop-in patch.

**Fetching the markers themselves** (before the per-key loop, inside `cron_sync()`): reuse the
existing `_CRON_IN_LIST_PAGE_SIZE` chunked-`.in_()` pattern already established in this exact file
for the same class of problem — `[VERIFIED: analytics-service/routers/cron.py:936-944]`:

```python
_page = (
    supabase.table("portfolio_strategies")
    .select("portfolio_id")
    .in_("strategy_id", _chunk)
    .execute()
)
ps_data.extend(rows(_page))
```

Apply the identical chunking loop against `strategy_sync_cursors`, and wrap it in the same
fail-open try/except this file already uses for the recompute-lookup blip
(`[VERIFIED: analytics-service/routers/cron.py:973-979]`, comment: "A Supabase blip on the recompute
lookup must NOT lose the per-key sync results we already collected"). On a query failure here, treat
every strategy's marker as absent (`None`) — which is exactly the NULL/fallback semantics CONTEXT
requires, so a blip degrades to today's key-only behaviour rather than aborting the tick.

### Write path — one condition closes both success criteria 2/3 and 4

Per CONTEXT Area 3: *"A per-strategy marker that advances only when the strategy's window has been
stored **and** its `derive_broker_dailies` job enqueued makes the next tick re-drive both."* This is
NOT simply mirroring `should_advance_cursor`'s formula per-strategy — it must also gate on
`recompute_enqueue_errors`, which is populated in a LATER loop (`cron.py:596-613`) than
`per_strategy_stored` (`cron.py:398-485`). The marker write must therefore happen AFTER both loops:

```python
# After the existing recompute_enqueue_errors loop (cron.py:596-613)
now_iso = datetime.now(timezone.utc).isoformat()
marker_upserts = []
for sid in strategy_ids:
    stored = per_strategy_stored.get(sid, 0)
    recompute_failed = sid in recompute_enqueue_errors
    should_advance_this_strategy = (not trades) or (stored > 0 and not recompute_failed)
    if should_advance_this_strategy:
        marker_upserts.append({"strategy_id": sid, "last_synced_trade_at": now_iso})

if marker_upserts:
    supabase.table("strategy_sync_cursors").upsert(
        marker_upserts, on_conflict="strategy_id"
    ).execute()
```

`on_conflict="strategy_id"` mirrors the existing upsert convention in `job_worker.py`
(`[VERIFIED: analytics-service/services/job_worker.py:1908-1914]`:
`ctx.supabase.table("strategy_analytics").upsert({...}, on_conflict="strategy_id").execute()`).
`cron.py` itself does not yet use `.upsert()` anywhere (`[VERIFIED: grep '\.upsert(' cron.py` — zero
hits]) but this is a direct, unremarkable extension of a pattern already established 13+ times
elsewhere in the same Python codebase, and stays consistent with CONTEXT Area 2's instruction to
keep `cron.py`'s DIRECT-write style (no RPC/fence) rather than adopting `job_worker.py`'s fenced
`advance_sync_cursor` style.

⚠️ Using this SAME `now_iso` value for BOTH the key-level `last_sync_at` write (line 527) and every
per-strategy marker keeps semantics consistent: this repo's cursors are stamped "wall clock at sync
time," not "max trade timestamp in the payload" — `[VERIFIED: analytics-service/routers/cron.py:527]`:
`update_data["last_sync_at"] = datetime.now(timezone.utc).isoformat()`. Do not invent a different
semantic (e.g. deriving the marker from `MAX(trade timestamp)`) for the new per-strategy marker; it
would diverge from the one column it is meant to mirror.

## Idempotency evidence (read from source, not assumed)

**`sync_trades` re-store is safe.** Latest definition
(`[VERIFIED: supabase/migrations/20260510180535_sync_trades_date_range_scoped_delete.sql]`, confirmed
latest via `grep -rln "CREATE OR REPLACE FUNCTION sync_trades" supabase/migrations/*.sql` — 3 hits,
this file's timestamp `20260510180535` sorts last):

```sql
SELECT MIN((t->>'timestamp')::timestamptz), MAX((t->>'timestamp')::timestamptz)
  INTO v_min_ts, v_max_ts FROM jsonb_array_elements(p_trades) AS t;

IF v_min_ts IS NOT NULL AND v_max_ts IS NOT NULL THEN
  DELETE FROM trades
   WHERE strategy_id = p_strategy_id
     AND COALESCE(is_fill, false) = false
     AND timestamp >= v_min_ts AND timestamp <= v_max_ts;
END IF;

INSERT INTO trades (...) SELECT ... FROM jsonb_array_elements(p_trades) AS t;
```

The DELETE is scoped to `[MIN,MAX]` of the incoming payload's own timestamps, then the same payload
is re-inserted. Re-running this RPC with the identical `p_trades` array on a later tick deletes
exactly the rows it is about to re-create and produces the same net state — no duplication. This is
what makes "hold the marker and let the next tick re-fetch a wider window" safe.

**`enqueue_compute_job` dedup is safe.** Latest `_enqueue_compute_job_internal` definition
(`[VERIFIED: supabase/migrations/20260716090000_retire_compute_analytics_kind_rpc_guard.sql:
181-310]`, confirmed latest via `grep -rln "CREATE OR REPLACE FUNCTION _enqueue_compute_job_internal"
supabase/migrations/*.sql` — 6 hits, this file's timestamp sorts last): does an optimistic lookup
for an existing in-flight job (`status IN ('pending','running','done_pending_children')`) for
`(strategy_id, kind)` and returns its id if found; otherwise `INSERT ... ON CONFLICT DO NOTHING
RETURNING id`, falling back to a re-read of the winner's row if the insert lost the race. The
"final arbiter," per the function's own comment, is the partial unique index
`compute_jobs_one_inflight_per_kind_strategy` — latest definition
`[VERIFIED: supabase/migrations/20260416125430_contact_request_metadata.sql:156-160]`:
`CREATE UNIQUE INDEX compute_jobs_one_inflight_per_kind_strategy ON compute_jobs (strategy_id, kind)
WHERE strategy_id IS NOT NULL AND kind <> 'compute_intro_snapshot' AND status IN ('pending',
'running', 'done_pending_children')`. Re-attempting `enqueue_compute_job(kind='derive_broker_dailies')`
for a strategy that already has one pending/running is a guaranteed no-op returning the existing job
id — both CONTEXT claims are confirmed true from source, not assumed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Enqueue dedup for the recompute re-drive | A new "has this strategy already got a pending derive_broker_dailies job" check | The existing `enqueue_compute_job` RPC + `compute_jobs_one_inflight_per_kind_strategy` partial unique index | Already proven dedup-safe (verified above); re-inventing this check risks a race the existing index already closes |
| Large IN-list pagination for the marker read | A new chunking helper | The existing `_CRON_IN_LIST_PAGE_SIZE` constant + chunked `.in_()` loop pattern (`cron.py:936-944`) | Same file, same class of problem (unbounded id list from active keys × strategies), already solved and already citing the PostgREST 414/silent-truncation hazard |
| Marker write | A new SECURITY DEFINER RPC/fence mirroring `advance_sync_cursor` | A plain `supabase.table(...).upsert(...)` call, mirroring `job_worker.py`'s existing upsert convention | CONTEXT Area 2 explicitly forbids harmonising the two sync paths; `cron.py` already writes `api_keys` directly with no RPC/fence, so the new marker write should match its OWN file's established style, not `job_worker.py`'s |

**Key insight:** every mechanism this fix needs — chunked IN-list reads, dedup-safe enqueue,
idempotent re-store — already exists in this codebase and has already been proven safe by a prior
migration's own verification. The work is composition (persist what `per_strategy_stored` already
computes, and read it back with a fallback), not invention.

## Common Pitfalls

### Pitfall 1: Gating the marker advance on `stored > 0` alone (mirroring `should_advance_cursor`
verbatim) misses success criterion 4

**What goes wrong:** If the per-strategy marker advances whenever `per_strategy_stored[sid] > 0`
(exactly mirroring the key-level formula), a strategy whose trades stored fine but whose
`derive_broker_dailies` enqueue failed (`recompute_enqueue_errors[sid]` set) gets its marker
advanced anyway — the next tick fetches NEW trades only, never revisiting the window whose
recompute never fired. This reproduces the exact Phase-18 regression CONTEXT quotes (cron-synced
strategies "never recomputed... dashboard KPIs froze until a user-triggered recompute") through the
new marker itself.
**Why it happens:** `should_advance_cursor` was written before the recompute-enqueue tail existed in
its current form and only ever needed to protect trade STORAGE, not the downstream recompute
trigger.
**How to avoid:** the advance condition must be `(not trades) or (stored > 0 and sid not in
recompute_enqueue_errors)`, computed AFTER the recompute loop runs, not folded into the earlier
`should_advance_cursor` computation.
**Warning signs:** a calibrated gate that only stubs `sync_trades` failing (not
`enqueue_compute_job` failing) will pass even with the narrower, incorrect condition — the gate must
cover BOTH failure injections to catch this.

### Pitfall 2: A stuck strategy grows the WHOLE key's fetch window forever, not just its own

**What goes wrong:** Because the fetch is per-KEY (one `fetch_all_trades` call, `since_ms` computed
as the MIN across all eligible strategies), a single persistently-failing strategy on a multi-strategy
key (e.g. a strategy whose `enqueue_compute_job` keeps erroring for an unrelated reason) pins the
FETCH window for every OTHER sibling on that key too — every tick re-fetches a growing range even
for siblings that are otherwise healthy. This is not a new bug introduced by this phase; it is the
DIRECT structural consequence of fixing the per-key aggregation with a per-strategy marker while
keeping a single per-key fetch.
**Why it happens:** `fetch_all_trades` is not per-strategy — there is one exchange call per key, not
per strategy (see cron.py:386-388). A per-strategy STORE cursor cannot, by itself, give a
per-strategy FETCH.
**How to avoid:** this is the same accepted tradeoff the existing `held` status already documents at
the key level (`[VERIFIED: cron.py:126-136]`, comment: "the `fetch_all_trades` window grows every
tick" while `held`). Treat it as PRECEDENTED behaviour, not a new defect to fix in this phase — but
flag it explicitly in the plan/verification writeup so a future phase (or an alarm) can watch for a
strategy stuck across N consecutive ticks, since it now silently degrades its healthy siblings' fetch
efficiency (not their correctness — re-fetch is idempotent).
**Warning signs:** none observable from a single-tick test; would need a multi-tick simulation to see
the window growth, which is out of scope for this phase's calibrated gate (single-tick, per CONTEXT
Area 5).

### Pitfall 3: `strategies.api_key_id`'s `ON DELETE SET NULL` means "which key backs a strategy" is
NOT a stable join key over time

**What goes wrong:** A migration or read-path query that (wrongly) keys the marker on
`(api_key_id, strategy_id)` composite would silently orphan history the moment a strategy is
re-pointed to a different key or its key is deleted (FK sets `api_key_id` to NULL) — the read path
would then find no marker row for the new `(new_api_key_id, strategy_id)` pair and behave as if the
strategy had never synced, discarding the fact that it HAD.
**Why it happens:** the FK is deliberately `ON DELETE SET NULL`, not `RESTRICT` or `CASCADE` —
`[VERIFIED: supabase/migrations/20260405061911_initial_schema.sql:51]`.
**How to avoid:** key the marker table on `strategy_id` alone (see Architecture Patterns above).
**Warning signs:** a reviewer asking "what happens on re-point" during the 3-reviewer pass — this is
exactly the question CONTEXT asked research to answer, and the composite-key shape fails it.

### Pitfall 4: A migration-reviewer may ask "why isn't this write fenced like `advance_sync_cursor`?"

**What goes wrong:** without an explicit rationale comment in the migration header, a
`migration-reviewer` pass may flag the plain `.upsert()` write as inconsistent with the
`job_worker.py`/`advance_sync_cursor` fenced pattern and request it be harmonised.
**Why it happens:** this repo has TWO cursor-write disciplines living side by side (CONTEXT Area 2),
and a reviewer unfamiliar with that deliberate split will reasonably ask about it.
**How to avoid:** every recent migration in this repo carries an extensive rationale header
explaining scope and what it deliberately does NOT do (see the `advance_sync_cursor` migration's own
header, `[VERIFIED: supabase/migrations/20260602173710_advance_sync_cursor_claim_token_fence.sql:
1-70]`). The new migration's header should explicitly state: "this mirrors `cron.py`'s existing
direct-write style for `api_keys.last_sync_at`, not `job_worker.py`'s fenced
`advance_sync_cursor` — harmonising the two paths is out of scope (booked separately, see
164.5.1.4-CONTEXT.md Area 2)."
