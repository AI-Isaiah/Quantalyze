# Phase 164.5.1.4 Plan 01: The per-STRATEGY sync cursor container Summary

**`strategy_sync_cursors` ships as a deny-all, strategy-keyed resume table that applies, self-verifies on catalogs alone and re-applies on a throwaway PostgreSQL cluster — inert on arrival, because every strategy starts with no row and the read path is required to read that as "fall back to the key-level cursor".**

- **Duration:** ~41 min
- **Tasks:** 2/2
- **Commits:** 2

## Accomplishments

- **Built the container the rest of the phase reads and writes.** `strategy_sync_cursors` has exactly three columns: `strategy_id UUID PRIMARY KEY REFERENCES strategies(id) ON DELETE CASCADE`, `last_sync_at TIMESTAMPTZ` (nullable), `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. No surrogate `id` (the PK already indexes the column the read path filters on and is the upsert conflict target), no api-key column in any form, no `updated_at` trigger (single writer, sets it in its own payload).
- **Proved it on a real cluster rather than by review.** The same file was passed to the disposable pg-lane as both `--apply` and `--gate`, so it executed TWICE: applied, self-verified, applied again, exit 0. The lane `initdb`s its own cluster on loopback and is destroyed by an EXIT trap; nothing in this plan touched TEST or PROD.
- **Made the self-verify catalog-only, with six arms.** Relation exists in `public`; primary key column set is exactly `strategy_id`; a cascading FK to `strategies` exists (`confdeltype = 'c'`); RLS is enabled (`pg_class.relrowsecurity`); the named policy exists; and its `polcmd` is `*` (FOR ALL). MEASURED static counts over the comment-stripped file: `row_count_assertions=0`, `scheduled_job_calls=0`, `api_key_id_refs=0`, `raise_exception_arms=6`, `deny_all_policy=6`, `cascade=2`.
- **Wrote the header to answer the review question before it is asked.** The "WHAT THIS FILE DOES NOT DO" block carries all four items, and each was re-checked against the file as written: the file creates and alters only `strategy_sync_cursors` objects (measured statement census: 1 `CREATE TABLE`, 1 `ALTER TABLE`, 1 `DROP POLICY`, 1 `CREATE POLICY`, 5 `COMMENT ON`, 1 `DO`), and contains zero executable references to `last_fetched_trade_timestamp`, `should_advance_cursor`, `advance_sync_cursor`, `cron.`, `GRANT` or `REVOKE`.

## The two shape decisions the brief left open

Both were taken on evidence read this session, not defaulted into. Verdicts and counts only — no credential, connection string, project ref, key, path or identifier appears here.

### Decision A — the RLS shape: deny-all, following `compute_jobs_deny_all`

**Two shipped precedents were compared.**

| Precedent | Migration | Shape | Owner tier on that table? |
|---|---|---|---|
| `allocator_holdings_service_all` | `20260420073003_allocator_holdings.sql` | explicit `USING (auth.role() = 'service_role')` | YES — it is one arm of a 3-tier policy set with an owner-facing SELECT |
| `compute_jobs_deny_all` | `20260411144407_compute_jobs_queue.sql` | `USING (false) WITH CHECK (false)` | NO — operational infrastructure, no owner tier at all |

**Chosen: the `compute_jobs_deny_all` form**, on the table's own posture. `strategy_sync_cursors` has a single writer — the analytics service's service-role client in the cron fan-out — and no browser, `anon` or `authenticated` consumer exists or is planned. That is `compute_jobs`'s posture exactly, and it is NOT `allocator_holdings`'s: that table's service-role arm documents the intent "service_role **in addition to** owners", which would be the wrong sentence to write on a table with no owners.

**The property that makes the narrower form safe:** `service_role` **bypasses** RLS by default (ADR-0003, quoted verbatim in the `allocator_holdings` comment block: *"service_role also bypasses RLS by default per ADR-0003, but an explicit policy documents intent and survives any future RLS-hardening that might flip the bypass"*). Both forms rest on that same bypass. Given that, `USING (false)` is the strictly narrower **written** grant of the two, because the `auth.role()` form would additionally admit any non-bypassing connection that presents that role claim. Narrower wins on a table with zero user-facing consumers.

**Rejected addition, recorded so a later reviewer can see it was considered rather than missed: no `REVOKE` for `anon`/`authenticated` on top of the policy.** With a REVOKE in place the policy stops being the live control, and any assertion that a non-service caller is denied would start passing for the GRANT reason rather than the POLICY reason. That is the vacuity trap the existing gates warn about in their own words — `test_allocator_equity_derived_rls.sql` states it directly: *"Assertion 4 accepts EITHER 0 rows or a 42501, so without that grant it would pass on the missing privilege rather than on the absent anon POLICY — and no mutation of the policy could ever redden it."*

### Decision B — a dedicated `supabase/tests/*.sql` RLS gate: **NO**

Three legs, each measured at HEAD this session rather than asserted.

**Leg 1 — the PRECEDENT SPLIT (this is a reason).** There are **7** `*_rls.sql` gate files in `supabase/tests/`. **All 7** are built around an owner-facing tier: each references `auth.uid()` (`test_allocator_equity_derived_rls.sql` 3, `test_csv_daily_returns_perkey_rls.sql` 3, `test_funding_fees_rls.sql` 6, `test_scenario_shares_rls.sql` 8, `test_scenarios_rls.sql` 10, `test_strategy_keys_rls.sql` 5, `test_strategy_shares_rls.sql` 39). **Zero of the 7** reference a deny-all policy. And the closest structural analog to this table — `compute_jobs`, the shipped deny-all with no owner tier — is named by **zero** gate files: `compute_jobs_deny_all` appears in 0 of the 76 files in `supabase/tests/`. Five `compute_job*` gate files do exist, but they gate RPC behaviour (dedupe, fan-in, progress, error-kind parity), not the policy. The repo's own practice is that owner-facing tables with cross-tenant leak risk earn an RLS gate and deny-all internal tables do not.

⚠️ **Correction to the plan's own text, recorded rather than quietly absorbed.** The plan asserted "the **two** existing `*_rls.sql` gates in this repo". The measured count is **7**. The verdict is unchanged — it is strengthened, since 7/7 rather than 2/2 land on the owner-facing side — but the number in the plan was stale and this SUMMARY carries the measured one.

**Leg 2 — the ASSERTION SHAPE (this is the other reason).** With no owner tier there is no cross-tenant scenario to assert. The only assertion available is "a non-service caller gets zero rows", and that is precisely the assertion the existing gates warn passes for the GRANT reason rather than the POLICY reason unless `07-fixture-supabase-default-privileges.sql` is loaded first (33 gate files load it for exactly this reason). A gate whose single arm is a known vacuity risk, on a table whose leak surface is an internal wall-clock watermark, is not worth the file.

**Leg 3 — the COST (context, explicitly NOT the reason).** A new annotated gate file raises the annotated-file count and the biting-arm count above the floors pinned by symbol in `scripts/mutation-runner/run.mjs`: `FILES_FLOOR = 47`, `ARMS_FLOOR = 402`, `WAIVED_CEILING = 0`. `src/__tests__/mutation-runner-floors.test.ts` then fails in the stale direction — *"RATCHET STALE: N of M gate files are now annotated but FILES_FLOOR is still 47"* — and it also pins the arm count exactly (`expect(totalAnchored).toBe(402)`), so adding one gate file means editing pinned numbers in two places. The annotation burden itself is real: `test_funding_fees_rls.sql`'s `RED-UNDER-SETUP` line enumerates **6** apply files.

⭐ **This cost was NOT the reason for the verdict.** A ratchet raised to match a genuinely larger corpus is a TIGHTENING and would have been correct to take. Legs 1 and 2 are the reason; leg 3 is context. **No floor was raised, no ceiling widened and no exemption added by this plan.**

**What stands IN ITS PLACE — this is a substitution, not a gap.** The migration's own catalog-only self-verify block asserts that RLS is enabled on the relation and that the named deny-all policy is present and governs ALL commands. Unlike a `supabase/tests` gate, which runs only when `sql-tests` runs, this block runs on **every apply**: the disposable lane here, shared TEST on merge via `apply-test`, and PROD behind the human reviewer gate. An apply that lands the table without its policy raises and fails the apply.

## Handoff to plan 02

- The read path must distinguish **row absent** from **row present with NULL** by key MEMBERSHIP. A dictionary lookup returning `None` for both collapses "fall back to the key cursor" into "re-fetch from the start of history", which is a different and much more expensive behaviour. The column comment states the three states in the database itself.
- The upsert conflict target is `strategy_id`, and `updated_at` must be set by the writer in its own payload — there is deliberately no trigger.
- `last_sync_at` here means the same thing as `api_keys.last_sync_at`: wall clock at sync time, NOT the maximum trade timestamp in the payload.
