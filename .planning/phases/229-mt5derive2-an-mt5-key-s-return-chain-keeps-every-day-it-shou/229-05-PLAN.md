<objective>
The writer-basis gate compares per-day values as well as the calendar, and refuses a same-day re-derive pair whose values do not match (HOLD-03). CONTEXT "[Writer-basis values]" fixes the invariant: a key_inputs row and a returns set from two different derives that share the calendar are refused as the blocking key_inputs_mismatch, and a healthy pair is never refused, including a timed MT5 flow day (its stored return is a product of cohort returns and cannot be inverted) and a guard-NaN day (P&L with no return). The comparison and its tolerance were left to research.

Research chose a content stamp (RESEARCH "HOLD-03: the comparison, chosen"): the returns a derive wrote are themselves the returns-side stamp. The key_inputs row carries their per-day record, written in the same atomic upsert as the basis, and the compose compares each raw key series to it. The 2026-10-10 TODOS formula (r times L against the day P&L) is not used: it falsely refuses a timed day whose flows net to zero (measured), and `csv_daily_returns` has no column for an identifier without a migration.

Deliberate placement, recorded so a reader takes it as intended: ROADMAP SC-4 and the CONTEXT boundary name `read_writer_basis` and the writer-basis gate in `replay_key_equity`. The compare runs instead in the compose job's read loop, per raw key, before `stitch_shared_account` replaces a member's series, using new sibling helpers in allocator_equity_derive.py. Reasons: the replay sees the stitched series, not each member's own rows; and any change to `read_writer_basis` fires the open entry `167.1.2.2.1-WRITER-BASIS-EMPTY-READS-LEGACY`. The reader half still lives in allocator_equity_derive.py, beside the writer half (Pattern 3).

Wave 3: same files as plan 229-03 (whose reason row this extends) and `job_worker.py` with plan 229-02.

Output: the stamp writer, reader and compare, and their tests.
