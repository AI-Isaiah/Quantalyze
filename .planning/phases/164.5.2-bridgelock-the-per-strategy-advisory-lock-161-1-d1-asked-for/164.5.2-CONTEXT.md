- **D-01:** BOTH mark RPCs change in ONE migration. A half-applied lock discipline reads as

- **D-02:** The lock is TRANSACTION-scoped (`pg_advisory_xact_lock`) and uses the TWO-KEY
  namespaced form, so it cannot collide with the single-key
  `pg_advisory_xact_lock(hashtext(p_strategy_id::text))` that `sync_trades` and

  precedent `20260530120000_admin_role_mutate.sql`.*
- **D-03:** The lock is taken only when the job's `strategy_id` is non-NULL, mirroring however
  each RPC already gates its bridge PERFORM. `hashtext(NULL)` is NULL and
  `pg_advisory_xact_lock` is STRICT, so an unguarded call on a strategy-less job (portfolio,
  allocator) silently takes no lock rather than erroring. The researcher confirms the existing
  guard shape at the latest definition; the planner mirrors it exactly.
- **D-04:** Lock ORDER is part of the design, not an afterthought. The job row is already locked
  `FOR UPDATE` before the bridge; `mark_compute_job_done` also touches fan-in children and (since
  164.9.1) interacts with a `FOR SHARE` parent lock. The researcher states the full lock order on
  both paths and whether the new advisory lock can join a cycle with any existing lock; the
  migration header records the answer. A new 40P01 path is a data-integrity regression, not a
  footnote.

  `supabase/migrations/**` (at HEAD: `mark_compute_job_done` is defined in 9 files, newest

  PERFORMs the SQL bridge still yields an error-only Python write followed by a loud SQL status:
  the `computation_warned` residue, so a warned composite can read `complete_with_warnings`
  again at the next bridge call over a failed run. The single-key derive honour site in
  `run_derive_broker_dailies_job` carries the identical window; a fix is one change for both.
  Fix shape: in `sync_strategy_analytics_status`, either branch (b) clears `computation_warned`,
  or the protect/loud decision moves inside the bridge's transaction. The window's length was

  `[164.6-COMPOSITE-CLAIMTIME-SNAPSHOT]`, so the composite schedule waits on this phase.
- **`[164.6.7-RETRY-PLAIN-COMPLETE]`, quoted from `feat/164.6.7` `TODOS.md`:** a marked refresh
  whose marker re-read fails raises `RefreshMarkerRereadUnavailable` and retries. The move to
  `failed_retry` runs `mark_compute_job_failed`, whose bridge branch (a) keeps
  `complete_with_warnings` but rewrites a plain `complete` row to `computing`. On attempt 2
  `_read_entry_publish_state` reads `computing`, so no protection is granted and a recurring
  failure takes the loud, un-publishing path. Keeping state in job metadata cannot close it
  (branch (a) has already rewritten the row, and on the final attempt the bridge decides in SQL
  with no Python running). Root fix: the non-terminal branch keeps a healthy publish state for a
  job carrying a refresh marker. Latent today (dated reading: 0 plain `complete` rows in the
  live ledger cohort).
