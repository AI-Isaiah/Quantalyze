I tried to break each of the following, and each held up:

- **Re-base (D-05).** I re-grepped every `CREATE ... FUNCTION` / `ALTER FUNCTION` /
  `COMMENT ON FUNCTION` / `GRANT` / `REVOKE` on both RPCs across all of
  `supabase/migrations/**`. The newest definitions are still `20260603120000` (done) and
  `20260529180000` (failed). Later files mention the RPCs only in probes or prose. I extracted
  each function body from its latest migration and from `20260926120000` and ran `diff`. Each
  diff is exactly ONE added line, the `PERFORM pg_advisory_xact_lock(...)` statement. Nothing
  newer was reverted. The only SQL caller outside the worker
  (`20260826140000`, the F-3 probe) uses a random uuid and never reaches the bridge.
- **Key collision space (D-02).** I grepped every `pg_advisory*` / `pg_try_advisory*` use in
  `supabase/migrations/**` and in `supabase/schema/baseline.sql`. PROD's catalogue could carry
  a lock user that no migration created, which is why I checked the baseline too. The only
  other two-integer user is `admin_role_mutate`, and the migration's DO block arm (0) checks
  the inequality at apply time. Every strategy-keyed user is single-key (`sync_trades`,
  `positions_atomic_rebuild`), and so are `alloc:`, `sanitize_user:`, `wiz*:` and the cron
  fan-out locks. A two-integer key reports objsubid 2, so the key spaces are disjoint.
  `analytics-service` takes no advisory lock directly. A `hashtext` collision between two
  strategy ids inside the namespace costs only extra serialization, never a cycle.
- **Lock order / deadlock (D-04, D-24).** The worker calls each RPC as its own PostgREST
  transaction (`main_worker.py`, `_mark_done` / `_mark_failed`). No SQL function calls a mark
  RPC more than once per transaction. ADV is taken after the job-row and fan-in child-row
  locks. After ADV, the only writes are the bridge's `strategy_analytics` upserts. The
  triggers on that table are BEFORE-UPDATE triggers that assign NEW columns and write no
  other table. So a holder of ADV can wait only on the SA row, or on an FK key-share, and no
  ADV waiter holds either of those. Nobody takes ADV while holding a child row lock that
  another ADV holder waits for, so the 164.9.1 FOR SHARE diamond is not made worse. The
  header's lock-order paragraph is accurate.
- **Does the lock actually close 161.1-D1 for mark-vs-mark?** Yes. B blocks on ADV until A
  commits. B's next statement (the bridge PERFORM) then takes a fresh READ COMMITTED
  snapshot, which includes A's terminal status. So the last bridge to run decides from
  committed state. Without the lock, B's upsert waits on A's SA row but applies a verdict it
  computed from stale reads, which is the RESEARCH Q3 observation.
- **Gate arms can fail.** L1 and L2 assert `locktype = 'advisory'`, never merely "b waits".

## Warnings

### WR-01: The gate never exercises the FAILED RPC's lock key or namespace, nor a done-vs-failed pair (MEDIUM, recorded limit)

**File:** `supabase/tests/test_mark_rpc_bridge_advisory_lock.sql`, arms L2, L3 and L4
**Issue:** L2 is the only arm that runs `mark_compute_job_failed`, and it asserts only
`locktype = 'advisory'`. L3 (namespace and two-integer form) and L4 (per-strategy keying)
both run `mark_compute_job_done` on both sides. So under a twin that stands down
`v_failed_lock_anchored`, all four arms stay GREEN for each of these mutations, confined to
the FAILED lock:
- rewrite it to the single-key `hashtext(v_strategy_id::text)` (shares key space with
  `sync_trades`);
- give it a different namespace string (done and failed would no longer serialize against
  each other);
- key it on a constant (every failure mark in the system would serialize).

No arm pairs a done mark with a failed mark on one strategy either. That is the most common
real shape of 161.1-D1: two sibling jobs of different kinds, one succeeding and one failing.
**Why only MEDIUM:** the migration's `DO $verify$` applies ONE shared `c_lock_re` to BOTH
bodies. That regex pins the guard, the two-integer form, the `'mark_compute_job_bridge'`
namespace, the `v_strategy_id::text` key and the placement before the bridge. None of the
mutations above can reach TEST or PROD without also editing that anchor. The gap is in
mutation coverage, not in shipped behaviour.
**Fix (optional, on a later touch of this gate):** add an arm L5, with a in `mark_compute_job_done`
and b in `mark_compute_job_failed` on the same strategy. Assert b's ungranted row is
`advisory`, `classid = v_ns` and `objsubid = 2`. Give it a twin that changes ONLY the
failed lock's namespace string and stands down `v_failed_lock_anchored`. Place L5 after L4 so
it cannot pre-empt their first failures. That moves `ARMS_FLOOR` and the parser, floors and
GREEN_LOG pins by grep, with the calibration offsets kept.

### WR-02: Pre-existing, not introduced, not closed by this lock: the concurrent fan-in "lost release" in `mark_compute_job_done` (MEDIUM, needs routing)

**File:** `supabase/migrations/20260926120000_mark_compute_job_bridge_advisory_lock.sql`,
`mark_compute_job_done`, the set-based fan-in `UPDATE compute_jobs c ... AND NOT EXISTS (...)`.
This body is carried byte-for-byte from `20260603120000`.
**Issue:** a child C in `done_pending_children` whose `parent_job_ids` holds two parents, P1
and P2, can be stranded when both parents mark done concurrently:
1. P1's mark flips P1 to `done` and evaluates the fan-in. At READ COMMITTED it still sees P2
   as `running`, because P2's flip is uncommitted, so NOT EXISTS is false and C is not
   matched.
2. P2's mark does the same and sees P1 as `running`.
3. Both commit. No UPDATE ever matched C, so no row lock or EvalPlanQual recheck saves it.

I found no sweep over `done_pending_children` in the repo (`claim_compute_jobs*` only guard
against it), and no TODOS entry naming this interleaving. D-12 item 1 is a different cause
(a parent ending `failed_final`). This phase deliberately takes ADV after the fan-in
(D-24), so it neither introduces nor closes the race. Moving the lock before the fan-in
would only cover same-strategy parents, and it would invert the D-04/D-24 no-cycle argument
(ADV would be held while waiting on child rows). That is a redesign, not a fix.
**Fix:** record it rather than patch it here. Add a TODOS entry, routed through
`/gsd-phase --edit` to the D-12 second planning pass in this phase or to 164.5.2.1, since it
is data-integrity: a stranded child never computes. Candidate remedies to evaluate there:
- re-evaluate the release in each parent after its own commit, via a deferred or sweeper pass
  over `done_pending_children` whose parents are all `done`;
- serialize by child through a per-child advisory lock taken in parent-id order.

## Info

### IN-01: The deployed bridge's own comment now contradicts the shipped behaviour (LOW)

**File:** `supabase/schema/baseline.sql` and the latest `sync_strategy_analytics_status`
definition (`20260906120000`), in the bridge's read-ORDER comment block.
**Issue:** the comment says the callers are not serialized per strategy: "neither it nor
mark_compute_job_done takes pg_advisory_xact_lock(hashtext(strategy_id)) before its PERFORM of
this function". After this migration that is false for the two mark RPCs. It is still true
for every non-mark caller, and this phase's header lists those. A reader who reasons from
the bridge alone will under-count the protection.
**Fix:** 164.5.2.1 BRIDGERESIDUE already re-bases this function (D-07). Have it rewrite the
sentence in the same migration: terminal marks are serialized by the two-integer
`mark_compute_job_bridge` lock since `20260926120000`, and the listed non-mark callers are not.

### IN-02: The new gate declares no completion sentinel (LOW)

**File:** `supabase/tests/test_mark_rpc_bridge_advisory_lock.sql`, end of file
**Issue:** the gate has no `RAISE NOTICE '... ALL 4 ARMS EXECUTED (L1-L4)'` line. The
`sql-tests` static half would count-check that line against the roster and the RAISE-site
bound, even for a LANE-ONLY file. Without it, an arm deleted along with its twin is caught
only by the `ARMS_FLOOR` and parser pins, not by the file itself. The sentinel is optional
in this corpus, and the mutation runner covers every arm, so this is defence in depth only.
**Fix:** append a final `DO` block with
`RAISE NOTICE 'mark-rpc-bridge-lock gate: ALL 4 ARMS EXECUTED (L1-L4)';`.
