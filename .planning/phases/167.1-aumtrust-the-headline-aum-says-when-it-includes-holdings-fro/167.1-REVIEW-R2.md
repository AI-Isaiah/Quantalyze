## Warnings

### WR-01: the composer's manager-side derivation, the half of the WR-01 fix plan 05 inherits, can be removed with no test failing

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx`, the
`managerSideApiKeyIds` `useMemo` and its pass-through into `summarizeLiveHoldings`.

**Issue:** The WR-01 fix has two halves. The helper's skip is pinned by the D-20 unit case. The
composer's derivation (`eligibleApiKeyIds` minus `allocatorEligibleApiKeyIds`) is pinned by
nothing, because `excludedUntrusted` renders nowhere, so no component test can observe it.
Measured: I replaced the argument with `managerSideApiKeyIds: []` and ran all of
`src/app/(dashboard)/allocations`. It printed **1969 passed, 0 failed**. The file was restored
from a byte backup and `cmp`-verified.

A reversed difference (allocator-eligible minus eligible), a wrong source array or a dropped
argument would therefore ship green. Plan 05 under D-06 option (b) wires this exact value into a
money-adjacent disclosure. It would inherit an untested input and assume it was verified, because
the fix report says WR-01 is "fixed".

**Fix:** Pin the derivation where it is written. The cheapest option is to extract it as a pure
exported helper next to `summarizeLiveHoldings`, for example
`managerSideKeyIds(eligible, allocatorEligible)`, and unit-test it with a hand-listed fixture in
which the two sets differ in both directions. The composer then calls that helper. Alternatively,
expose `excludedUntrusted` to a test seam, but a pure helper is simpler. The neuter above must
then turn RED.

### WR-02: `holdingEquityIsReported`'s NaN-derivative and non-finite-spot branches are unpinned, so its "cannot disagree" claim is untested

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `holdingEquityIsReported`.

**Issue:** The docblock says it has the "Same branches as that function, so the two cannot
disagree about which holdings were defaulted". Only the null-derivative branch is exercised
(`H_SIGN_IN_FAILED_NO_PNL`, and the composer's `derivPnlUsd: null`). Measured: I rewrote the body
to `derivative → pnl != null`, `spot → true`. That drops both the `Number.isFinite` check on the
derivative and the whole spot check. The helper and composer suites stayed **368/368 green**. The
file was restored from a byte backup and `cmp`-verified.

So a NaN P&L on an untrusted derivative, or a non-finite `value_usd` on an untrusted spot
holding, can silently fall back to presenting a defaulted 0 as a known figure. That is exactly
what WR-03 set out to stop. The Open Positions footer does pin NaN (`pos-u-nan`), so the two
surfaces are guarded unevenly.

**Fix:** Add two unit cases to `live-holdings-summary.test.ts`. The first is an untrusted
derivative with `unrealized_pnl_usd: Number.NaN`. The second is an untrusted spot holding with
`value_usd: Number.NaN`. Each expects `unavailable: 1` and an unchanged `total`. Better still, add
a table-driven case that asserts `holdingEquityIsReported(h) === false` exactly when
`holdingEquityContributionLocal(h)` substituted its 0, across null, NaN and ±Infinity for both
holding types. That makes the lockstep claim executable.

### WR-03: the D-20 residual is stated as "a revoked manager-side key", but every manager-side key outside `eligibleApiKeyIds` escapes the narrowing

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, the
`LiveHoldingsSummary.excludedUntrusted` docblock. The same wording appears in `167.1-06-PLAN.md`
(the `### Notes` known-limits list: "a revoked manager-side key may be counted in the excludes
figure").

**Issue:** `managerSideApiKeyIds` is `eligibleApiKeyIds` minus `allocatorEligibleApiKeyIds`, and
`isPerKeyDailiesEligibleKey` requires `is_active && sync_status !== "revoked" && disconnected_at
== null`. So a manager-side key is invisible to the narrowing whenever it fails any of those three
conditions, not only when it is revoked. A soft-disconnected or inactive manager-side
`sign_in_failed` key still has its holdings counted in `excludedUntrusted`.

The direction is safe: it over-discloses and never hides. But the docblock is the one definition
plan 05 reads, and the release-notes known limit is the one public statement of the residual.
Both name a strict subset of the population that can inflate `$Y`.

**Fix:** In both places, word the residual by its predicate rather than by one status. For
example: "a manager-side key outside `eligibleApiKeyIds` (revoked, soft-disconnected or inactive)
cannot be told apart, so its untrusted holdings may be counted. That over-discloses and never
hides." Consider adding a unit case with a manager-side key absent from `managerSide` to pin that
it is counted.

### IN-01: when both parts are present, the combined "(value unavailable for N …)" reads as belonging to the unknown-status part only

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx`, `buildUntrustedAumClause`.

**Issue:** `unavailable` is `untrusted.unavailable + unknownStatus.unavailable`, but it is
appended after the last joined part. With both parts present it renders as "…needing attention
and $Z from keys with an unknown sync status (value unavailable for 1 holding)". That reads as
qualifying `$Z` even when the defaulted holding is an untrusted one. The UI-SPEC WR-05 table does
not list this combination, and no test renders it. It is reachable only on the degrade branch,
which production cannot reach with book mode.

**Fix:** Either attach each part's own `unavailable` count to that part, or add a row to the
UI-SPEC table and a typed-string pin that accepts the combined form deliberately.

## Silent-failure-hunter findings, round 2 (same round, 2026-09-24)

No CRITICAL and no HIGH. It overlaps WR-01 (the composer wiring of `managerSideApiKeyIds` is untested), WR-02 (the spot branch of `holdingEquityIsReported` is untested) and IN-01 (the merged unavailable suffix). It adds:

### WR-04: the WR-05 `console.error` reaches no operator
`src/instrumentation.ts` runs Sentry without `captureConsoleIntegration`, so a browser `console.error` is seen only in the user's devtools. The fix follows `ScenarioCommitDrawer.tsx`: capture a warning-level Sentry event tagged `reason: "holding_key_missing_from_key_list"` carrying the count only, no key id. Keep the console line for local dev, and pin it with a test that the Sentry call carries no key id.

### WR-05: the Holdings tab still reads a missing key as trusted, so two surfaces disagree
`HoldingsTabPanel.tsx` (`keyStatusById`, `spotHoldingRows`, `openPositionRows`) maps both a missing key and a present-but-null status to `"unknown"`, which is trusted. The composer names the unknown-status holding, and the tab it points the user to shows nothing. The fix: keep present-but-null as trusted, give a missing key its own marker, and have `OpenPositionsTable` count it as a separate unknown-status part using the composer's wording. The no-key-id rule applies.

### WR-06: a missing payload field makes `managerSideApiKeyIds` hide holdings from $Y
In `ScenarioComposer`, `payload.allocatorEligibleApiKeyIds ?? []` with `eligibleApiKeyIds` present marks every eligible key as manager-side, which hides rather than over-discloses. If either field is undefined, return `[]`. Covered by the same pure-helper extraction as WR-01.

### IN-04: a missing-key holding excluded by the narrowing is left out of $Y without trace
Either add an `excludedUnknownStatus` part to `summarizeLiveHoldings`, or state the exclusion in the `excludedUntrusted` docblock so the D-06 answer covers it.

### IN-05: attach the unavailable suffix to each part
Round-2 IN-01 and the silent-failure-hunter's LOW-3 describe the same issue. Render "(value unavailable for N …)" after the part it belongs to.

### IN-06: test hygiene
The WR-05 composer tests use a payload SSR cannot emit (`bookEntryGateSatisfied: true` with an empty `contributingApiKeyIds`); say in their docblock that this is a guard that production cannot reach. Remove the redundant `.not.toBe(71_110)`, which cannot fail on its own.
