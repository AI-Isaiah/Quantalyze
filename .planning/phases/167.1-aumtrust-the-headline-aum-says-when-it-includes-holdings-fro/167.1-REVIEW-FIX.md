### WR-01: `excludedUntrusted` is not D-20's `$Y`

**Files modified:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `src/app/(dashboard)/allocations/lib/live-holdings-summary.test.ts`, `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx`

**Status:** fixed: requires human verification (logic)
**Applied fix:** The narrowing option. `summarizeLiveHoldings` takes a new argument, `managerSideApiKeyIds`. The composer derives it as `eligibleApiKeyIds` minus `allocatorEligibleApiKeyIds`. Both sets come from the payload, and neither predicate is re-derived on the client. Holdings from those manager-side keys no longer enter `excludedUntrusted`.

The docblock now states D-20's definition:

A new unit case pins 15,555 and 2 holdings, and asserts the result is not 71,110. It went RED when the guard was neutered. Plan 05 was not executed, and no "excludes" copy renders.

### WR-02: the State A disclosure is not tied to the AUM input

### WR-03: "Includes +$0" claims a known zero when the P&L is unknown

**Files modified:** `OpenPositionsTable.tsx`, `untrusted-key-status.surfaces.test.tsx`, `live-holdings-summary.ts`, `live-holdings-summary.test.ts`, `ScenarioComposer.tsx`, `ScenarioComposer.test.tsx`, `167.1-UI-SPEC.md`
**Commit:** e58ed56fe
**Status:** fixed: requires human verification (logic and copy)
**Applied fix:** The totals are unchanged, and defaulted rows still sum as 0. What changed is that each surface now counts the untrusted rows it defaulted:
- **Open Positions:** the footer's single pass appends `(P&L unavailable for N position(s))`.
- **Helper:** each disclosed part becomes a `LiveHoldingsPart { amount, count, unavailable }`. The `unavailable` count comes from `holdingEquityIsReported`, which uses the same branches as `holdingEquityContributionLocal`.
- **Composer:** the single clause builder appends `(value unavailable for N holding(s))` in both State A and State B.
- **Known zero:** a real zero keeps the bare wording.

The finding suggested "(P&L unavailable for N)". I adapted that to the UI-SPEC's voice: the noun comes from the constant, the amount comes from the host renderer, the note is muted, and it has no role. The composer says "value", because a spot holding's missing figure is not a P&L. The UI-SPEC's "+$0" row is kept as lineage under a dated SUPERSEDED note.

Each of the three new guards went RED when neutered.

**Files modified:** `live-holdings-summary.ts`, `live-holdings-summary.test.ts`, `ScenarioComposer.tsx`, `ScenarioComposer.test.tsx`, `167.1-UI-SPEC.md`
**Commit:** 6a8dd2635
**Status:** fixed: requires human verification (logic and new copy)
**Applied fix:** A summed holding whose key is absent from the status map now goes into a new `unknownStatus` part. The check uses `.has`, so a key that is present with a null status stays trusted. The total is unchanged. The untrusted part still uses only the shared predicate as its membership test.

The composer's single builder adds a sibling part with its own noun: `includes $X from keys needing attention and $Z from keys with an unknown sync status`. It is never folded into `UNTRUSTED_KEY_SET_NOUN`, because the Holdings filter would not find those rows under that noun. The marker's gate widens to either count, and the composer calls `console.error` on the anomaly. No key id is logged.

Only the degrade branch can sum such a holding. The UI-SPEC records the new part and warns that plan 05 must compose its "excludes" clause through the same builder. The helper branch, the gate and the log each went RED when neutered.
