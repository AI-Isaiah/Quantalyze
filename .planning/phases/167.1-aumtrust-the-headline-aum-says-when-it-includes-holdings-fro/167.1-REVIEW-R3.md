## Warnings

### WR-01: the excludes clause is silent for dropped holdings whose key is missing from the key list, the one production-reachable path of that class

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `summarizeLiveHoldings`
(the `narrowToModelledBook && !contributing.has(...)` arm); consumed by `buildUntrustedAumClause` in
`ScenarioComposer.tsx`

**Scenario.** `getUserApiKeys` validates `exchange` at the trust boundary and drops a row whose
exchange is not in the supported union. The holdings for that key still arrive in
`holdingsSummary`. `contributingApiKeyIds` is a subset of the `apiKeys` ids, so in production (the
narrowing is always on, because `bookEntryGateSatisfied === contributingApiKeyIds.length > 0`) such
a holding always takes the narrowing arm. There, `isUntrustedKeySyncStatus(undefined)` is false, so
the holding lands in no part:

- not in `total`;
- not in `untrusted`;
- not in `unknownStatus` (that part is reachable only in the degrade branch);
- not in `excludedUntrusted`.

So the review WR-05 unknown-status disclosure covers only a path that cannot happen in production.
The path that can happen is the one with no disclosure. After D-06 (b), the marker now says
"Excludes $Y from keys needing attention." A reader reasonably takes $Y as the full account of what
the modelled book leaves out. The missing-key dollars disappear with no sentence, which is the
"nothing silently disappears" failure that D-06 (b) was chosen to end.

The same asymmetry shows up if `payload.apiKeys` is absent. `statusByKeyId` is built from `?? []`.
The includes side fails open (every summed holding becomes `unknownStatus` and is disclosed). The
excludes side fails closed (every dropped holding becomes unknown and vanishes from `$Y`).

This is not a BLOCKER. The field's code comment records it as IN-04, and the founder scoped (b) to
"keys needing attention" (D-20). But nothing in CONTEXT or UI-SPEC records that the D-06 answer
leaves it open. The comment's own condition ("A D-06 answer that wants it named needs its own
`excludedUnknownStatus` part") has now been decided without anyone saying so.

**Fix.** Pick one:

1. Add an `excludedUnknownStatus` part in the same narrowing arm, using the same `.has` test as
   WR-05:
   ```ts
   if (narrowToModelledBook && !contributing.has(h.api_key_id)) {
     if (untrusted && !managerSide.has(h.api_key_id)) addTo(out.excludedUntrusted, h, equity);
     else if (!args.statusByKeyId.has(h.api_key_id)) addTo(out.excludedUnknownStatus, h, equity);
     continue;
   }
   ```
   Then compose it in `buildKeyTrustClause` with `UNKNOWN_KEY_STATUS_SET_NOUN` (split form), and
   add it to the gate and to the Sentry count.
2. Record in CONTEXT `<known_limits>` and UI-SPEC § 3 that D-06 (b) deliberately leaves
   missing-key exclusions undisclosed, dated, with IN-04 cited, so the omission is a decision
   rather than an artefact.

### WR-02: the `untrusted.unavailable === 0` term of `oneNoun` is untested, and deleting it silently drops a WR-03 count

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `buildKeyTrustClause`
(`oneNoun`); tests in `live-holdings-summary.test.ts`, describe `buildKeyTrustClause — D-06 (b) …`

**Scenario.** Delete `untrusted.unavailable === 0 &&` from `oneNoun`. Given
`untrusted = {amount: 0, count: 1, unavailable: 1}` and `excluded = {amount: 8000, count: 1, unavailable: 0}`,
the builder then returns `includes $0 and excludes $8,000 from keys needing attention`. That drops
the "(value unavailable for 1 holding)" qualifier, so a defaulted $0 reads as a known figure, which
is exactly what review WR-03 fixed.

No test catches it:

- The only builder case with any `unavailable` on the includes-and-excludes path is
  `part(12_345, 1), NONE, part(8_000, 3, 2)`. There `excluded.unavailable === 2` already forces
  the split form.
- No composer M3 fixture carries an unreported value.

The `unknownStatus.count === 0` term is pinned (the WR-05 builder case goes RED without it), and
`excluded.unavailable === 0` is pinned by the case above. This third term is the only
`oneNoun` conjunct with no test.

**Fix.** Add the missing oracle, typed literally:
```ts
expect(buildKeyTrustClause(part(0, 1, 1), NONE, RENDER, part(8_000, 1))).toBe(
  "includes $0 from keys needing attention (value unavailable for 1 holding), and excludes $8000 from keys needing attention",
);
```
Then neuter the term, watch the case go RED, and restore it.

### IN-02: `hintShowsLive` is true where no live total is shown

**File:** `ScenarioComposer.tsx`, `hintShowsLive`

**Issue.** The flag is `sanitizedManualAum === undefined && liveHoldingsSum <= 0`. That also holds
in blank mode, and in book mode with no marker. In both cases the hint names no live total. The
gate stays correct only because `showUntrustedMarker` also requires `entryMode === "book"`, and
the sentence renders only under `showUntrustedMarker`. The name claims more than the predicate
guarantees, so a future reader who reuses `hintShowsLive` alone as "the live total is on screen"
would be wrong.

**Fix.** Rename it `hintShows` (or `fieldBlankHintShows`), or add a comment: "the hint renders;
it names the live total only when `showUntrustedMarker`".

### IN-03: the State 6 fix covers only exact float equality

**File:** `ScenarioComposer.tsx`, `fieldShowsLive` / `overrideNoteShowsLive`

**Issue.** State 6 requires `sanitizedManualAum === liveHoldingsSum`. The live total is a float
sum of custody values (the code's own example is `39963.1076231`), while a typed manual value is an
integer. The common case, an allocator who types the rounded live figure, therefore lands in State
B: "Overrides live-holdings total $39,963, which includes …", next to a field that shows 39963.
That copy is true, and the behaviour is pre-existing (review [9] chose it deliberately). But the
IN-06 fix is reachable in practice only when every summed value is an integer, or when a bottom-up
resize happens to match the sum. The D-18 reopen's promise is met, just more narrowly than the
SUMMARY implies.

**Fix.** None required. Record the narrowness in the UI-SPEC § 1 state 6 row so nobody plans
against it as the common case.
