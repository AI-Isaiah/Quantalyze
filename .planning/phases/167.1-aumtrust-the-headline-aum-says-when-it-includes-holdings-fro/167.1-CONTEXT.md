## Phase Boundary

**This phase adds a DISCLOSURE to a money figure. It changes no money figure.**

The standing founder decision (2026-09-22, recorded in the ROADMAP entry for this phase) is binding
and is not re-litigated here: **keep the total and flag it.** The headline AUM keeps including
holdings sourced from keys whose sync is untrusted (`isUntrustedKeySyncStatus`: `revoked`,
`sign_in_failed`) and says so, naming how much of it comes from those keys. Excluding them was
rejected because a password rotation would then read as an AUM loss. Nothing silently disappears,
and the figure stays reconcilable with the holdings table.

⛔ **PREMISE CORRECTION, measured during this discussion (see D-01).** The ROADMAP goal says "the
allocator KPI strip's headline AUM". **The KPI strip has had no AUM cell since Phase 64
PRESENT-01** (`KpiStrip.tsx` docblock: "return-form only — the AUM cell is gone (4 cells)"), and the
SSR field the review finding pointed at, `liveBaselineMetrics.aum`, **is not rendered anywhere**.
The holdings-derived headline dollar figure an allocator actually SEES is the Scenario composer's
**PORTFOLIO AUM (USD)** field, seeded in book mode from `liveHoldingsSum`, and the
`scenario-aum-override-note` that quotes that same live total. That is where the flag lands.

**In scope:**
- A marker next to the displayed live-holdings total in the Scenario composer (book mode) that names
  the dollar amount contributed by holdings whose source key is untrusted.
- Unit + component tests that can fail (data-integrity / user-facing — D-15).
- Correcting the comments that still describe a "headline AUM" consumer that does not exist
  (`src/lib/closed-sets.ts` block above `UNTRUSTED_KEY_SYNC_STATUSES`), and the ROADMAP goal's

- Closing `.planning/WINDOWS.md` entry 66 at ship.
- The release commit (VERSION + CHANGELOG), per the repo's CHANGELOG discipline.

**Out of scope:**
- Any change to the computed value of `emptyLiveBaselineMetrics`, `liveBaselineMetricsFromPerKeyDailies`,
  `liveHoldingsSum`, `scenarioAum`, or the commit route's server-side AUM (D-03).
- Re-adding an AUM cell to `KpiStrip` (reverses Phase 64 PRESENT-01 — a new capability, not this
  phase).
- Changing `isPerKeyDailiesEligibleKey` (a mirror of the Python backfill; cross-language SoT).
- The strategy-level `total_aum` surfaces (`PortfolioKpiPanel`, the factsheet `CapacityChip`,
  `portfolio-pdf`) — they read `portfolio_analytics.total_aum`, which the analytics service sums from
  strategy AUMs, not from allocator holdings by key.

## Implementation Decisions

### Where the flag lands

- **D-01: The flagged figure is the composer's live-holdings total, not a KPI-strip cell.**
  Evidence at 9fd60115:
  - `src/app/(dashboard)/allocations/components/KpiStrip.tsx` — 4 return-form cells (YTD TWR,
    Sharpe, Max DD 12m, Avg |ρ|); the docblock records "Phase 64 / PRESENT-01: return-form only — the
    AUM cell is gone".
  - `liveBaselineMetrics` has exactly one reader in `src/app`: `liveBaselineToComputedMetrics` in
    `ScenarioComposer.tsx`, which maps `ytdTwr/sharpe/maxDd/avgRho/equity` and **drops `aum`**.
    Inside `liveBaselineMetricsFromPerKeyDailies`, `totalAum` also scales the drawdown series, but
    `deriveSnapshotDrawdowns` (`allocations/lib/drawdown.ts`) returns `(value - peak) / peak`, which
    is scale-invariant — so no rendered number depends on the value of `liveBaselineMetrics.aum`
    beyond its `> 0` gate.
  - The rendered holdings-derived dollar total is `liveHoldingsSum` in `ScenarioComposer.tsx`: it
    seeds the `scenario-aum-input` field (book mode, no manual override) and is quoted verbatim by
    `scenario-aum-override-note` ("Overrides live-holdings total $X.").
  The researcher MUST re-run this enumeration (every rendered dollar total derived from
  `holdingsSummary` / `allocator_holdings` on an allocator surface) and report any site this list
  missed; a missed site is a plan gap, not a footnote. Known non-sites, measured:
  `allocations/lib/mandate-gates.ts` (`minAumGate` sums `value_usd`) has **no production caller**
  (`deriveMandateGates` is imported only by its own test); `src/app/(marketing)/page.tsx` sums
  `strategies.aum`, not holdings.
  — **Reversibility:** reversible — the marker is additive UI.

- **D-02: Keep the total and flag it — FOUNDER DECISION 2026-09-22, honoured verbatim.** The
  displayed total keeps its current value; beside it a marker states the untrusted contribution in
  dollars, in the shape the founder gave: "includes $X from keys needing attention". The collective
  noun is the existing constant `UNTRUSTED_KEY_SET_NOUN` (`src/lib/closed-sets.ts`, value
  `"keys needing attention"`) — the same noun the holdings-table filter toggle and hidden-row footer
  already use, so a reader can find the rows the marker is talking about. Do not restate the noun as
  a literal; derive the copy from the constant.

### Money math

- **D-03: No money number changes.** `emptyLiveBaselineMetrics`, `liveBaselineMetricsFromPerKeyDailies`
  (`src/lib/queries.ts`), `liveHoldingsSum` / `scenarioAum` (`ScenarioComposer.tsx`) and the commit
  route's `serverAumUsd` / `serverEquityAumUsd` (`src/app/api/allocator/scenario/commit/route.ts`)
  produce byte-identical values before and after this phase. The disclosure is a SEPARATE derived
  quantity computed alongside the total, never subtracted from it. A test must go RED if an
  untrusted holding is dropped from the total (that is the rejected alternative, and it must not be
  reachable by accident).

- **D-04: The flagged amount is a strict subset of the displayed total — reconcilable by
  construction.** `$X` is summed over EXACTLY the holdings `liveHoldingsSum` sums (same
  `toggleByScopeRef` iteration, same `holding:` prefix, same `narrowToModelledBook` /
  `contributingApiKeyIds` filter, same equity basis `holdingEquityContributionLocal`), restricted to
  those whose source key's `sync_status` satisfies `isUntrustedKeySyncStatus`. The key status comes
  from `payload.apiKeys[].sync_status` joined on `api_key_id` — already in the SSR payload and
  allocator-scoped, so no new read. The two sums must come from ONE pass (or one shared helper) so
  they cannot drift apart; ⛔ never a second hand-kept copy of the loop. ⛔ No local equality on the
  status column — `isUntrustedKeySyncStatus` is the only membership test (167 D-16's rule).

- **D-05: Which untrusted statuses can actually reach the total today, and why that is NOT changed
  here.** `isPerKeyDailiesEligibleKey` (`src/lib/queries.ts`) excludes `sync_status === "revoked"`
  but not `sign_in_failed`. `contributingApiKeyIds ⊆ allocatorEligibleApiKeyIds ⊆ eligibleKeyIds`,
  so in book mode a `revoked` key's holdings are ALREADY excluded from `liveHoldingsSum`, while a
  `sign_in_failed` key with a per-key series is included. The marker therefore fires, in practice,
  for `sign_in_failed`. It must still be written against the whole predicate (both members), so a
  future change to eligibility cannot silently put a `revoked` contribution in the total unflagged.
  The eligibility predicate is not touched (it mirrors the Python backfill — a cross-language SoT).

### OPEN — the founder's call

- **D-06 ⛔ OPEN (checkpoint:decision) — a `revoked` key's holdings are silently ABSENT from the
  composer's book-mode AUM.** Per D-05 the composer's total already excludes `revoked` keys, and so
  does the "Models N of M keys" note (`allocatorEligibleCount` is built on the eligible set, which
  excludes `revoked`). That is precisely the "a password rotation reads as an AUM loss" outcome the
  founder rejected — but for the venue-rejected state, and inside the composer, whose AUM was
  deliberately narrowed to the MODELLED book by Phase 151 review F2 so the per-row dollars reconcile.
  The founder's stated criterion "nothing silently disappears" and F2's reconciliation rule pull in
  opposite directions here, and choosing between them changes what the headline money figure MEANS.
  Options for the founder:
  - **(a) Leave the exclusion, record it.** The composer AUM stays "the modelled book"; no new copy.
  - **(b) Disclose the exclusion (recommended).** Keep the total unchanged and add the mirror
    sentence "excludes $Y from keys needing attention", with `$Y` summed on the same equity basis
    over the allocator's holdings whose key is untrusted and not in the summed set. Additive and
    reversible; F2's reconciliation is untouched.
  - **(c) Include revoked holdings in the total and flag them.** Matches D-02 literally, but breaks
    F2 (the rows the composer renormalizes would no longer add up to the AUM they are sized from).
  **Planning instruction:** the D-02/D-04 marker must NOT wait on this answer. Plan D-06 as a
  separate, independent task or plan behind a `checkpoint:decision` carrying option (b) as the
  recommendation, so the rest of the phase executes regardless of when the founder answers.
  — **Reversibility:** reversible for (a)/(b); costly for (c) — (c) redefines the composer AUM that
  the commit sizing, the per-row size gate and the commit refusal (`scenarioAum <= 0`) all read.

### Rendering rules

- **D-07: When the marker renders.** Book mode only (blank mode has no live sum —
  `holdingsSummary` is `[]` there by construction). It renders iff at least one holding in the summed
  set (D-04) has an untrusted source key — NOT iff `$X > 0`: a derivative's equity contribution can
  be zero or negative and is still sourced from a key whose numbers are not current. The amount is
  rendered with the composer's existing whole-dollar renderer `formatUsd`
  (`src/lib/dollar-validation.ts`), signed as it comes. With no untrusted holding in the set, the
  marker is absent (no "$0" claim).

- **D-08: One marker, attached to whichever element shows the live total.** With no manual override
  the live total is the field's value, so the marker sits beside the field. With a manual override
  the live total appears only inside `scenario-aum-override-note`, so the marker qualifies that
  note instead. Never two markers for one number. Exact placement, wording beyond D-02's shape, and
  tone are fixed by the UI-SPEC (D-09).

- **D-09: Visual treatment is the UI-SPEC's to fix, constrained by DESIGN.md.** DESIGN.md reserves
  amber for recoverable states and a re-added key IS user-recoverable; the sibling disclosures in the
  same row (`scenario-aum-override-note`, `scenario-aum-modelled-note`) use the muted
  `text-xs text-text-muted` voice. The UI-SPEC chooses between them with a stated reason, reuses an
  existing treatment, and adds no new component or token.

## Known limits (recorded 2026-09-24, code review round 1)

Recorded from `167.1-REVIEW.md` (the code reviewer plus the silent-failure-hunter section). None of
these changes a locked decision above; each is carried into the release notes' `### Notes` by
plan 06.

- **The disclosure holds only AFTER the latest-asof holdings collapse (routed, not fixed here).**
  `holdingScopeKey` (`src/lib/keys.ts`) omits `api_key_id`, so the latest-asof collapse merges two
  accounts on the same venue holding the same asset, and one key's position silently vanishes from
  every total and from the marker. It predates this phase, it is data-integrity, and it is booked
  for the founder as a proposed phase of its own. Every guarantee this phase makes (D-03, D-04,
  D-07) is about the rows that survive that collapse.
- **Whether a soft-disconnected key counts as "needing attention" is the founder's call (not in
  scope).** A key with `disconnected_at` set and `sync_status` complete does not satisfy
  `isUntrustedKeySyncStatus`, so its holdings are not disclosed. The review booked the question
  for the founder. This phase does not answer it and does not widen the predicate.
- **Review WR-04, not fixed: the marker is absent when the live total is ≤ 0 (UI-SPEC state 4).**
  When untrusted holdings push the live total to ≤ 0 the field is blank, "Required to size and
  commit." shows, and nothing says that part of the (non-positive) live total comes from keys
  needing attention. D-18 locks "in every other state the marker is absent" and UI-SPEC U-04
  settles state 4 as absent, so a clause on the hint needs a decision that re-opens D-18. It is
  surfaced for that decision, not worked around.
- **Review IN-06, accepted as a D-18 exception: manual equal to live shows no marker (UI-SPEC
  state 6).** With a committed manual value equal to the live total, neither the override note
  nor State A renders, although the number on screen is then the live total. D-18 (ii) requires
  "the two differ", so this is recorded as accepted rather than changed. The reviewer preferred
  showing State A here; that is the same D-18 re-opening as WR-04.
- **Review IN-05, kept by UI-SPEC U-05: the two surfaces sign the amount differently.** The
  composer prints `formatUsd` (`-$1,235`, no `+`), Open Positions prints `formatPnl` (`+$300`,
  `−$1,235`). U-05 decides each disclosure uses the renderer of the figure it qualifies, so a
  part and its whole share one sign convention. Both forms are pinned by typed-string tests.
