## Warnings

### WR-01: `excludedUntrusted` is not D-20's `$Y`, but its docblock and the D-06 unit pin present it as the D-06 measure

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, the `LiveHoldingsSummary.excludedUntrusted` field docblock and the `narrowToModelledBook && !contributing.has(...)` branch of `summarizeLiveHoldings`. The pin is the "D-06: a revoked key outside a non-empty contributing set…" case in `live-holdings-summary.test.ts`.

**Issue:** The field counts every toggled-on holding whose key fails the predicate and sits outside
`contributingApiKeyIds`. That set is wider than the thing the docblock says it measures ("the
`revoked` exclusion") and wider than CONTEXT D-20's definition of `$Y`. D-20 says a
`sign_in_failed` manager key "is recognisable from the payload and excluded".

`src/lib/queries.ts` builds `contributingApiKeyIds` from `allocatorEligibleApiKeyIds`, which
subtracts `strategyLinkedKeyIds` (the manager-side keys). The holdings of those keys stay in
`holdingsSummary`. So `excludedUntrusted` also picks up two other groups:

- (a) a manager-side `sign_in_failed` key's holdings, which are not the allocator's book, and
- (b) an allocator-eligible `sign_in_failed` key that simply has no return series yet (the
  "not yet contributing" population).

Nothing renders this field today, so no user-facing number is wrong at this HEAD. But the field is
named and documented as the D-06 quantity, and a unit test pins it. If plan 05 under option (b)
wires `excludedUntrusted.amount` straight into "excludes $Y from keys needing attention", it will
over-state `$Y` by the untrusted manager-side holdings. That is a money-adjacent disclosure
carrying dollars that are not in the allocator's book. The field is also computed on every toggle
and read by nothing in production, which is speculative surface under the simplicity rule.

**Fix:** Pick one of these before plan 05 consumes it:

- **Narrow the field to D-20's definition.** Pass the manager-side key set in (for example,
  `eligibleApiKeyIds` minus `allocatorEligibleApiKeyIds`), skip `sign_in_failed` holdings from
  those keys, and add a unit case that shows the manager-side holding is excluded.
- **Or rename and re-document it.** For example, call it `untrustedOutsideContributing`, state
  plainly that it is a superset of D-20's `$Y`, and leave the narrowing to plan 05. In that case
  the plan-05 brief must name this gap.

A sketch of the first option:

```ts
// args: + managerSideKeyIds: ReadonlySet<string>  (eligible minus allocator-eligible)
if (narrowToModelledBook && !contributing.has(h.api_key_id)) {
  // D-20: a manager-side key whose status the payload identifies is not the
  // allocator's book; only the indistinguishable remainder may over-disclose.
  if (untrusted && !args.managerSideKeyIds.has(h.api_key_id)) {
    out.excludedUntrusted.amount += equity;
    out.excludedUntrusted.count += 1;
  }
  continue;
}
```

In that sketch, any status test must still go through the shared predicate, never an inline
literal, per 167 D-16.

### WR-02: the State A disclosure is not programmatically tied to the AUM input

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx`, the `scenario-aum-input` `<input>` and the State A `scenario-aum-untrusted-note` span (and the State B `scenario-aum-override-note`).

**Issue:** The phase exists because "a headline money figure may not change meaning silently". But
the input carries no `aria-describedby`. A screen-reader or keyboard user who tabs to the
PORTFOLIO AUM field hears the label and the value, for example 492345, and nothing more. The
sentence saying part of that figure comes from keys needing attention is only reachable in
linear reading order, never on focus. For assistive-technology users, the disclosure is exactly
the silent change in meaning the phase set out to prevent.

The sibling notes (`scenario-aum-override-note`, `scenario-aum-modelled-note`) have the same gap,
so this repeats an existing pattern rather than creating a new one. It is still the one element
whose whole purpose is to qualify the value of that input.

**Fix:** Give the State A span and the override note stable ids, and set
`aria-describedby` on the input to whichever of them is rendered. No visual change, and no new
role or `aria-live` region (so D-09's no-role rule still holds):

```tsx
<input id="scenario-aum" aria-describedby={[
  showUntrustedMarker && fieldShowsLive ? "scenario-aum-untrusted-note" : null,
  overrideNoteShowsLive ? "scenario-aum-override-note" : null,
].filter(Boolean).join(" ") || undefined} … />
```

Add a component assertion that the input's accessible description contains the typed disclosure
string in State A.

### IN-02: the disclosed amount can exceed the figure it qualifies

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `summarizeLiveHoldings` (and the State A span in `ScenarioComposer.tsx`).

**Issue:** Take a trusted derivative with a large unrealized loss next to an untrusted spot
holding. For example, a trusted derivative at -4,000 and an untrusted spot holding at 5,000 give
a live total of 1,000. The field then shows `1000` beside "Includes $5,000 from keys needing
attention." The arithmetic is correct, and CONTEXT D-07 explicitly accepts that
`amount <= total` is not an invariant. But a reader sees a part larger than its whole, with no
explanation. No test covers this rendered case.

**Fix:** None is needed for correctness. If it should be explained, that is copy work for the
UI-SPEC. At minimum, add a component case that pins the current rendering, so a later "clamp"
change is deliberate.

### IN-03: the D-06 component pin gives a `revoked` key the `AT_KEY_SIGN_IN_FAILED` identifier

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.test.tsx`, the "D-06 (component pin, decision OPEN)" case.

**Issue:** The key id constant is named for `sign_in_failed`, but the fixture sets
`status: "revoked"`. The fixture self-proof then asserts that `AT_KEY_SIGN_IN_FAILED` is absent
from the eligible sets. Plan 05 has to edit this test deliberately, and the identifier misleads
whoever does that edit.

**Fix:** Add an `AT_KEY_REVOKED` constant (a synthetic id) and use it in this case.

### IN-04: an unknown key status fails open to "trusted" inside the helper

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `isUntrustedKeySyncStatus(args.statusByKeyId.get(h.api_key_id))`.

**Issue:** A summed holding whose `api_key_id` is missing from `payload.apiKeys` resolves to
`undefined`, the predicate treats that as trusted, and the holding goes undisclosed. On the
narrowed branch this cannot happen, because `contributingApiKeyIds` is derived from `apiKeys`. On
the degrade branch, which the code documents as unreachable in production, it can. For a
disclosure, failing open under-states the untrusted part.

**Fix:** Optional. Add a one-line note in the helper's docblock that an absent status counts as
trusted, and why that is safe (the contributing set is a subset of the `apiKeys` ids). Or add a
unit case that pins the degrade-branch behaviour for an unknown key.

## Silent-failure-hunter findings (same review round, 2026-09-24)

### WR-03: "Includes +$0" states a known zero when the untrusted P&L is unknown
In the `OpenPositionsTable` footer pass and in `holdingEquityContributionLocal` → `buildUntrustedAumClause`, null or non-finite P&L defaults to 0. When any untrusted row's amount was defaulted, the marker must not claim a zero. Count those rows (`untrustedUnknownCount`) and word it without a figure, e.g. "includes N position(s) with unknown P&L from keys needing attention", or pair the amount with "(P&L unavailable for N)". Apply the same in `summarizeLiveHoldings`. Re-pin the null-P&L test to the honest wording.

### WR-04: the marker disappears when untrusted holdings push the live total to ≤ 0
In `ScenarioComposer`, `showUntrustedMarker` depends on `liveHoldingsSum > 0`. When `untrusted.count > 0 && liveHoldingsSum <= 0`, the field is blank and the reason is silent. Extend the "Required to size and commit." hint with the untrusted clause. Re-pin absence state 4 accordingly.

### WR-05: a holding whose key is missing from `apiKeys` reads as trusted
In `summarizeLiveHoldings`, `statusByKeyId` returns `undefined` for keys that `getUserApiKeys` dropped, e.g. an unsupported exchange, and the predicate treats them as trusted. Treat a missing key as a distinct "status unknown" case: count it, disclose it with the untrusted clause or a sibling clause, and `console.error` it. `allocator_holdings.api_key_id` is NOT NULL, so undefined means dropped, never "no key". This supersedes IN-04.

### IN-05: sign conventions differ between the two surfaces
The composer uses `formatUsd`, giving "-$1,235" with no "+". Open Positions uses `formatPnl`, giving "+$300" and "−$1,235". The same fact should read the same way. Pick one convention for the disclosure clause on both surfaces and pin it.

### IN-06: manual equals live hides both the note and the marker (state 6)
This was a deliberate D-18 call. Either record it as an accepted exception in the phase's Known limits, or show State A's standalone sentence when manual equals live, since the number on screen is then the live total. Prefer showing it: the phase's premise is that a number including untrusted dollars says so.

Whether a soft-disconnected key (`disconnected_at` set, `sync_status` complete) counts as "needing attention" is booked for the founder.
