## S2 — Zoomed benchmark covered-span note (item 5, D-05)

**Where.** The existing `benchNote` paragraph in `MetricsColumn`, rendered at both of its sites
with `data-testid="bench-figure-gate-note"` and class `mb-2 text-fixed-10 italic text-text-muted`.
Both sites print the **identical** string. No new component, no new test id.

**When (all must hold).**
1. A range is selected (`selected`).
2. A benchmark is shown with annualized cells (`bn != null` and `hb != null`).
3. The strategy gate is not `withheld`. D-05 adds no withholding, and a withheld record shows no benchmark note.
4. The benchmark's covered span is shorter than the window on at least one side:
   - **Starts after:** a benchmark-calendar day exists in `[window start, first covered date)`. Judge it on the benchmark's own calendar, mirroring `isPastCoverage`. A weekday comparator against a window that starts on a weekend is **not** "starts after".
   - **Ends before:** the existing end-side rule (`isPastCoverage` / `coveredToEnd`).

**Precedence (one line, never two).**
1. The benchmark's covered span is unreadable: the existing sentence `${bn}: ${withheldReason("record", {...record, unreadable: true})}`. Unchanged.
2. Otherwise, a selected range whose benchmark coverage is short: the D-05 sentence below.
3. Otherwise, full history with a covered span under a year: the existing `${bn}: ${shortTrackNote("record", n)}`. Unchanged.
4. Otherwise nothing.

**Copy (the three variants, verbatim).** `{bn}` is the benchmark's display name as already used in
`benchNote` (for example `BTC`). `{from}` and `{through}` are the first and last covered dates
formatted by `isoToMonthDay` (for example `Mar 3, 2026`). The separator is a spaced en dash ` – `.

| Case | Sentence |
|------|----------|
| Starts after the window start only | `{bn} compared over {from} – {through} (its data starts after this range).` |
| Ends before the window end only | `{bn} compared over {from} – {through} (its data ends before this range).` |
| Both | `{bn} compared over {from} – {through} (its data starts after and ends before this range).` |
| One covered day inside the window (`from` equals `through`) | `{bn} compared on {from} only (its data starts after this range).`, with the same parenthetical rule as above (`starts after` / `ends before` / `starts after and ends before`) |
| No covered day inside the window | **No D-05 note.** There is no span to name, and `isoToMonthDay` would print `—`. The vs-benchmark cells follow their existing no-overlap handling (`—` per the Numbers Contract). The note must never print `—` in place of a date |

The string comes from ONE helper beside `shortTrackNote` in `src/lib/figure-gate.ts`, so a test can
pin every variant and no call site concatenates the sentence. The helper takes the benchmark name
and the two dates **already formatted**. `MetricsColumn` formats them with `isoToMonthDay` before
the call, because `isoToMonthDay` lives in `MetricsColumn.tsx`, which imports `figure-gate`, and
`figure-gate` must not import it back.

**Figures.** The vs-benchmark figures stay computed on the overlap and keep their normal formatting
and tone (D-05). The note qualifies them and never dashes them.

**Print.** The note is document content, not chrome. It prints with the rail (no
`factsheet-v2-no-print`).

**Decision UD-03 [derived]: `isoToMonthDay` over `formatIsoDay`.** RESEARCH proposed `formatIsoDay`
(`2026-03-03`). The note sits in the rail directly under the `RangeEyebrow`, which prints the window
as `Selected range: Mar 3, 2026 – Nov 9, 2026` through `isoToMonthDay`. With the same formatter
the reader can compare the two spans character for character. D-05's own example ("Mar 3 – Nov 9")
is month-day as well. The year is kept because a range can cross a year boundary.

## S3 — Print-view equity figure fits its card (item 7)

**Contract (layout invariant, not a redesign).** On `/factsheet/[id]/tearsheet` (the
`FactsheetView printView`) the equity figure renders through `ResponsiveChartFrame` and carries no
fixed pixel width. Its rendered SVG never extends past its containing card:
`svg.getBoundingClientRect().right <= card.getBoundingClientRect().right` (and the same on the left).

- Viewport the pin measures: **1470px** (the UAT reproduction). A search of `e2e/` on 2026-11-10 did not find a spec that opens the tearsheet, so expect the pin to be new. The planner re-checks at plan time. This contract does not assert other viewports for the print view, because none has been measured.
- No `<Sparkline … width={N}>` or other intrinsic-pixel chart may return to the tearsheet tree. The fixed 620px `Sparkline` was deleted by Phase 196 (`f4a2ab4ce`), and RESEARCH A2 records that the premise appears closed.
- Printed (A4 and Letter): the figure scales to the printable width with the rest of the print view. No clipping at the right margin.
- If the re-measure still shows overflow, the fix goes in the print-view container's width chain, never into a new fixed width.

No copy, colour, type or spacing changes on this surface.

## S4 — Record length reads the same on every page (item 8, D-02)

**Rule.** One strategy prints one record length N on discovery, the factsheet, the print view,
Holdings and the Scenario leg. N is 194 D-20 `coveredDays`: first to last return date, both ends
counted. The record's first date is the stored curve's first point. That is the addendum's
confirmed cause: the factsheet's curve inversion drops day 0, so it read one day fewer than the
lists. This contract names no specific number; the addendum shows the figure moves with each daily
derive.

**Copy (existing, unchanged, via helper).** No string is edited. Only the N fed to these changes:

| String | Producer |
|--------|----------|
| `CAGR, volatility, Sharpe, Sortino and Calmar are annualized from {N} days of record, under one year.` | `shortTrackNote("record", N)` |
| `Annualized from {N} days of record, under one year.` | `shortTrackMarkerTitle(N)` (the `<1y` marker's `title` and sr-only text) |
| `{N} days of record, {start} to {end}.` | `StrategyTable` Track-cell `title` (its `{start}` is `recordStartDay(...)`, so it moves with the same rule) |

N uses thousands separators, as DESIGN.md requires for integer counts. The factsheet's displayed
equity and metric series are **not** changed. Only the record's start (and so N and the gate) is.

### Entry point A: factsheet viewer bar (`ViewerBar` → `RequestIntroButton`)

New Viewer-State Matrix row (extends 196's matrix; other rows unchanged):

| Viewer | Header actions |
|--------|----------------|
| Signed in, role `allocator` or `both`, approved, **not attested** (attestation read succeeded, no row), not the owner | **Request intro** (primary, the bar's one accent fill). "Add to my allocation" stays hidden until the allocator has attested (D-07, founder 2026-11-10; `canAllocate` keeps its meaning, today's behaviour unchanged) |
| Same viewer, attestation **read error** | none (back link only). The failure is already reported to Sentry. Accepted limit: no prompt on a read error, because it could ask an attested user to re-attest and the upsert would overwrite `attested_at` |

Interaction:
1. The unattested allocator clicks **Request intro**. The attest modal opens, titled "Attest to request introductions". No request is sent.
2. Confirm label: **Confirm and request intro**.
3. On success the attest modal closes and the existing **Request an introduction** modal opens in its place, with focus on its message textarea. Nothing is sent until the user presses **Send request**. This completes the original action without leaving the page (D-04).
4. `router.refresh()` re-resolves the viewer, so "Add to my allocation" appears beside Request intro. The intro control must sit in a **stable tree position** across both viewer states (one client component that takes a `needsAttestation` prop), so its open state survives the refresh.
5. **Reactive branch.** This applies when `POST /api/intro` answers 403 `code: "attestation_required"`, for example on a stale page.
   - **One dialog at a time.** The request modal's body is replaced by the attest step inside the same `Modal`, whose title becomes "Attest to request introductions". The state the user typed (message and mandate fields) is kept in component state, not discarded.
   - **Confirm succeeds.** The body switches back to the request form with the typed state intact, and the request is re-submitted automatically (`Sending…`). On success the existing sent state shows.
   - **Close without confirming.** The body switches back to the request form with the typed state intact. Nothing is sent, and no error line shows. The user can close the modal or press Send request again, which reaches the same refusal.
   - **Re-submit fails.** The error shows in the request form's existing error line (`text-sm text-negative mb-4`, above the buttons) with the typed state intact. The copy follows the table below.
   - **Check failed.** If the route answers 500 `code: "attestation_check_failed"`, the same error line reads: `We could not check your attestation. Try again in a minute.`

Key the prompt off the new `needsAttestation` field, **never** off `!canAllocate`. Otherwise
unapproved users and managers would see it (RESEARCH pitfall 5).

### Entry point B: Bridge ReplacementCard on `/allocations`

1. The unattested allocator clicks the existing **Request Intro** button.
2. The card does not show an error line. It opens the attest modal ("Attest to request introductions").
3. Confirm label: **Confirm and send intro request**.
4. On success the modal closes and the card re-fires `handleIntro`: `Requesting...`, then `Intro Requested`. The click's original action completes in place (D-04).
5. `Close without confirming` returns the card to `idle` with no error line.
6. A 500 `attestation_check_failed` sets the card's existing error line (`mb-2 text-caption text-negative`, `role="alert"`) to `We could not check your attestation. Try again in a minute.`, and the button reads `Retry Intro`.
7. Branch on `code` **before** the generic 401/403 copy ("You don't have permission to request this intro."), which stays for the non-attestation 403s.

Decision UD-05 [derived]: the reactive branch alone satisfies this contract. On the first click a
refused POST has no side effect, and the user sees the attest step either way. Threading an
`introAttested` prop from `allocations/page.tsx` through `InsightStrip` → `BridgeTrigger` →
`ReplacementPanel` → `ReplacementCard` would save one round trip. It is permitted, not required,
and the planner decides. If it is threaded, the visible behaviour is the same: the click opens the
attest step before any POST. **Dependency:** UD-05 holds only if the route refuses an unattested
caller **before** `checkLimit(userActionLimiter, intro:…)`, which RESEARCH places right after the
allocator-role check. Otherwise each refused click burns one of the user's intro rate-limit tokens.
If the planner puts the attestation read after the limiter, the prop threading becomes required.

Decision UD-04 [derived]: the entry button keeps its request label ("Request intro" / "Request
Intro") instead of becoming "Attest to request introductions". The attest is a step inside the
request (D-04 says "step"), so the button's label stays true to what the click finally does, and an
attested and an unattested allocator see the same CTA. D-04's phrase appears verbatim as the attest
modal's title.
