## Critical Issues

### CR-01: [HIGH] Holdings and the Scenario book-held leg still start a curve-derived record at the SECOND curve date (D-02 / item 8 not closed)

**File:** `src/lib/queries.ts:2000` (producer `figureRecordScalars`, line 1986). Callers at
`src/lib/queries.ts:2193` (`getOwnCapitalStrategies`) and `src/lib/queries.ts:6372`
(`getMyAllocationDashboard`, whose series is built at `:6186`). Consumers:
`src/app/(dashboard)/allocations/components/HoldingsTable.tsx:375` and
`src/app/(dashboard)/allocations/lib/constituent-figure.ts:86`.
**User-facing and data-integrity; phase-goal gap.**

**Issue:** `figureRecordScalars` builds the record from `seriesStart: series[0]?.date`. Both callers
pass `resolveDailyReturnSeries(daily_returns, returns_series, method)`. For a curve-derived row
(`daily_returns` null), that is `equityCurveToDailyReturns`, which never emits day 0
(`resolve-series.ts:96`, `for (let i = 1; ...)`). The Holdings record therefore starts at
`returns_series[1].date`. Plan 05 fixed exactly this cause for the factsheet only
(`recordSeriesStart`). Every other reader takes `returns_series->0->>date`: the SQL aliases, the
owner arm `shapedRecordScalars`, `get_verified_cohort_rank`, and the lazy
`/api/strategies/[id]/returns` route through `recordFromScalars`.

The parity test does not catch it. `figure-parity-pages.test.tsx:1064` feeds `toStrategyRows`
`figure_span_days: spanOfSeries(CURVE)`, the raw curve's span. Its header (`:969-972`) says the
producer "reads `series[0].date` too" and that the owner-arm `shapeRowAnalytics` case stands for
it. It does not: `shapedRecordScalars` reads the raw `returns_series`, while `figureRecordScalars`
reads the inverted series. The SUMMARY's line "reads one record length on discovery, the factsheet,
the print view and Holdings" is false.

**Failure scenarios:**
1. The PROD UAT strategy from item 8 (194 days on the factsheet after this phase) shows a Holdings
   Sharpe `<1y` marker titled "Annualized from 193 days of record, under one year." The same
   one-day split item 8 was opened to remove is still there, on a different page.
2. A crypto strategy whose stored curve covers exactly 90 days: discovery, the factsheet and the
   tearsheet clear D-15 (90 >= 90) and show CAGR, Sharpe and Sortino. Holdings computes 89 and
   withholds the Sharpe. In the Scenario composer, the book-held leg reads `figure_span_days` 89
   and is withheld, while the same strategy added from the drawer reads 90 through the lazy route
   and shows. One strategy gets two verdicts on one screen.

**Fix:** give the producer the same record start the factsheet uses. Pass the stored curve's first
point when the series is curve-derived, with the same predicate as `curveRecordStart`, rather than
the inverted series' first date:

```ts
// queries.ts — figureRecordScalars input gains the raw columns (or a precomputed start)
function figureRecordScalars(input: {
  series: readonly DailyPoint[];
  recordSeriesStart?: string | null; // returns_series[0].date when daily_returns does not normalize
  ...
}) {
  const record = figureRecord({
    seriesStart: input.recordSeriesStart ?? series[0]?.date ?? null,
    seriesEnd: series[series.length - 1]?.date ?? null,
    ...
  });
```

Share one helper between `fetch-and-build-payload.ts` and `queries.ts` (move `curveRecordStart` to
`resolve-series.ts`) so the two producers cannot drift. Then add a parity case that runs the
PRODUCER, either through `getOwnCapitalStrategies` / `getMyAllocationDashboard` with a mocked
client or by exporting `figureRecordScalars`, and asserts 194 against a hand-typed expectation.
Neuter it by passing `series[0].date` and see the case read 193.

## Warnings

### WR-01: [MEDIUM] A malformed earliest date crashes the factsheet and tearsheet build before any unreadable gate runs

**File:** `src/lib/factsheet/benchmark-read.ts:100-109` (`isoMinusOneDay(min)`, defined at `:45`).
Called from `src/lib/factsheet/fetch-and-build-payload.ts:945` (native build) and `:1183` (USD
build).
**User-facing, not data-integrity.**

**Issue:** `readFactsheetBenchmark` takes the lexicographic minimum date across the cash,
mark-to-market and smoothed axes, then runs
`new Date(Date.parse(\`${min}T00:00:00Z\`) - 86_400_000).toISOString()`. When that minimum is not
parseable, `toISOString()` throws `RangeError: Invalid time value`. Measured with node: `""`,
`"2025-1-5"`, `"2025-13-01"` and `"2025-02-32"` all throw, while rollover days such as
`"2025-02-30"` do not. An empty string always sorts first, as does any date with a leading
non-digit or a short month. The throw is outside the guarded `try`, by design (169.5 SFH-M-01), so
it reaches `src/app/factsheet/[id]/error.tsx`.

Plans 01 and 05 wired `firstUnreadableDate` and the `record_start` axis into `buildFactsheetPayload`,
but the build never gets that far, so the named `figure-record-unreadable` Sentry report never
fires either. Plan 02 recorded this and deferred it, and plan 05 carried it again. The
`194-MALFORMED-DATES-ABSENT` closing wording reads "every date axis ... treat a malformed date as
unreadable, not absent". An error page is neither. The unit tests pass only because they call the
builder directly and skip `fetchAndBuildPayload`'s benchmark read.

**Failure scenario:** a CSV-derived strategy whose stored `daily_returns` holds one element dated
`"2025-13-01"` (a day/month swap) or `""` as its earliest key. Opening `/factsheet/<id>` or its
tearsheet renders the route error boundary ("Try again") instead of a factsheet with annualised
figures withheld under the unreadable reason. Retrying cannot recover it, because the stored data
is the cause. The same applies to an MTM or smoothed axis whose earliest date is malformed.

**Fix:** bound the read on readable dates only, so the gate downstream sees the malformed date and
withholds:

```ts
for (const axis of axes) {
  for (const r of axis) {
    if (!r || typeof r.date !== "string" || !isReadableDay(r.date)) continue;
    if (min === null || r.date < min) min = r.date;
    if (max === null || r.date > max) max = r.date;
  }
}
```

Apply the same guard in `build-payload.ts:190` (`isoMinusOneDay`, the fixture bound) for the
browser path. Add an end-to-end case through `fetchAndBuildPayload` with an earliest date of
`"2025-13-01"` that asserts the payload builds with `figureRecord.unreadable === true`, and see it
throw RED before the guard.

### WR-02: [MEDIUM] A present non-string record date is read as "absent" in TS, but as unreadable by the SQL twin

**File:** `src/lib/queries.ts:900-910` (`shapedRecordScalars` `day` / `dateAt`), `src/lib/queries.ts:275` (`percentileRecord` `day`), `src/lib/queries.ts:2000-2005` (`figureRecordScalars` `since` check), `src/lib/factsheet/fetch-and-build-payload.ts:196-202` (`curveRecordStart`).
**Data-integrity (found by silent-failure-hunter).**

**Issue:** each site keeps a date only when `typeof v === "string" && v.length > 0` and nulls everything
else. A PRESENT non-string value in `returns_series[0].date` or `headline_since` (a number, an object, a
boolean) is therefore read as ABSENT, which the gate treats as "unknown" and SHOWS. The SQL arm in
migration `20261110120000` reads the `->>` text of that value, which fails `^\d{4}-\d{2}-\d{2}$`, so it
is UNREADABLE and the strategy is dropped from cohorts. One stored record gets two verdicts.

**Fix:** treat any present, non-null value that is not a non-empty string as verbatim-unreadable
(`String(v)`), matching SQL. An empty string and null stay absent on both sides.

### WR-03: [MEDIUM] `reportUnreadableOnce` dedups before the send, so a throwing send mutes that record for the process lifetime

**File:** `src/lib/queries.ts:245-256`.
**Observability of a data-integrity gate (found by silent-failure-hunter).**

**Issue:** the key is added to `reportedUnreadable` before `send()` runs. If `send()` throws, the key stays,
and every later read of that record skips the report, so the one signal that an annualised figure left the
peer sets stays silent until the process restarts.

**Fix:** add the key only after `send()` returns without throwing.
