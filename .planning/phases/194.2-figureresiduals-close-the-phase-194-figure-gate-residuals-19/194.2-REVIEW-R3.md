## Warnings

### WR-01: [MEDIUM] New in 247d46f72. The USD view withholds a record whose native view shows its figures, because `recordSourceDates` includes absent days the native build drops

**File:** `src/lib/factsheet/fetch-and-build-payload.ts:1131-1135` (the `nativeSeries` read with
`keepAbsent = true`) and `:1165` (`recordSourceDates: nativeSeries.map((p) => p.date)`). The native
build reads `resolveDailyReturnSeries(...)` at `:482-486` with the default `keepAbsent = false`.
**User-facing (figure gate).**

**Issue:** `equityCurveToDailyReturns(..., keepAbsent = true)` (`resolve-series.ts:87-119`) keeps
every unusable curve day as a `NaN` placeholder at its stored date. Those are days with a null or
non-finite level, a non-positive geometric level, or the day after such a level. The native build
drops them. So a malformed date on such a day is not in the native build's dates. The native
record reads as readable. The USD build scans the same malformed date through
`recordSourceDates` and withholds. R2 WR-01 was "one record, two verdicts" (native withheld, USD
short). This fix flips which side is wrong, for a different input. It does not remove the split.

**Measured:** a 400-point BTC-native curve on the api arm, with full BTC closes. One interior
point has a malformed date and `value: null`:

| curve[200] | native `figureRecord.unreadable` | USD `figureRecord.unreadable` |
|---|---|---|
| `{date: "2024-07-3", value: null}` | false (figures shown) | **true (withheld)** |
| `{date: "2024-07-31x", value: null}` | false (figures shown) | **true (withheld)** |

**Failure scenario:** a native-unit strategy's stored curve holds one corrupt element, such as a
bad date with a null level, in the interior. The point after a zero or null level triggers it the
same way: `equityCurveToDailyReturns` marks it absent too. That follows from the code; I did
not probe it separately. The native factsheet, the Holdings producers, the list and the
percentile readers (`->0` / `->-1` only) all show
CAGR, Sharpe and Sortino. The viewer clicks USD. The same page now withholds them under "the
record's dates could not be read". The USD build also sends a `figure-record-unreadable` Sentry
event with axis `record_source`, and the native build sends none.

**Fix:** have the USD verdict read exactly the dates the native build judged. Pass the native
build's own series, or drop the placeholders:

```ts
// fetch-and-build-payload.ts, buildUsdView usdOpts
// The native build judges readability over its keepAbsent=false series; read the same dates.
recordSourceDates: nativeSeries.filter((p) => Number.isFinite(p.value)).map((p) => p.date),
```

A sturdier option is to thread the native payload's `figureRecord.unreadable` into
`buildUsdView` and OR it into the USD record. Then the two verdicts are equal by construction,
not by scanning the same list twice. Add a parity case through `fetchAndBuildPayload` with the
`value: null` element above. It should assert native and USD agree. Neuter the fix and see it go
RED.

### WR-02: [MEDIUM] 80d43fa7a keys the stress withheld form to the bundle's first date, not the record's verdict, so the USD toggle prints a stress table the native view withholds

**File:** `src/lib/factsheet/build-payload.ts:657-660` (`dates.length > 0 && !isReadableDay(dates[0])
? { ..., unreadable: true } : computeStressWindows(...)`). The converter that drops the date is
`src/lib/factsheet/native-to-usd.ts:57` (`for (let k = 1; ...)`, which never emits the native
series' day 0). **User-facing.**

**Issue:** the withheld line says "Stress windows are not shown: the record's dates could not be
read." That is a claim about the record. The predicate behind it is `dates[0]` of whichever
series this build received. The USD series never contains the native series' first date:
`convertNativeReturnsToUsd` starts at `k = 1`, and a malformed date never pairs with a close
anyway. So when the native view shows the withheld line, the USD view of the same record computes
and prints windows from the converted series. 247d46f72 made the USD **record** follow the native
dates through `recordSourceDates`. It did not do the same for the stress block, which still reads
only the USD build's own `dates[0]`. The same predicate also prints a full stress table under a
withheld record whenever the unreadable date is anywhere but first. The panel's sentence is tied
to "first date unreadable", not to "record unreadable".

**Measured:** a BTC-native curve starting 2024-02-28 with `curve[1].date = "2024-02-30"`, so the
native series' `dates[0]` is `"2024-02-30"`. `Date.parse` accepts that string, so the api-arm
build does not throw (compare WR-03).

| view | `figureRecord.unreadable` | `stressWindows` |
|---|---|---|
| native | true | `unreadable: true`, 0 windows: "Stress windows are not shown: the record's dates could not be read." |
| USD | true | **`unreadable` absent, 1 window: "Aug 2024 unwind 2024-08-02..2024-08-09"** |

**Reach today:** only first dates that `Date.parse` rolls over, such as day 30 or 31 of a
shorter month. Any other unreadable first date throws on the api arm before this guard (WR-03).
Fixing WR-03 widens WR-02 to every unreadable first date.

**Failure scenario:** a native-unit factsheet whose series' first date is calendar-invalid. In BTC
the stress panel says the record's dates could not be read. One click on USD and the same panel
prints a strategy return and drawdown for the Aug 2024 unwind. Both views carry the same
withheld record verdict.

**Fix:** derive the stress withholding from the record's verdict, the same one every figure gate
reads, not from the bundle's first date. In `buildFromBuildableSeries`, after `totalRecord` is
known (`build-payload.ts:~962`), replace the bundle's `stressWindows` with the withheld form when
`totalRecord.unreadable`. Keep the `dates[0]` guard only as the throw-avoidance for
`computeStressWindows`. That covers the USD view (its record now carries `record_source`) and an
interior unreadable date with one rule. If an interior unreadable date should still show
windows, keep the panel's sentence. But then the USD build needs the native first-date fact
passed in, as `recordSourceDates` does for the record. Add a USD-view case to
`StressWindowsPanel.unreadable.test.tsx` or the parity suite.

### WR-03: [MEDIUM] On the `api` arm the build throws `RangeError` for an unparseable first series date before the stress guard is reached. The R2 test's own inputs throw there, and the page renders an error

**File:** `src/lib/factsheet/allocator.ts:170` (`level.push({ date: isoDayBefore(dates[0]), close: 1 })`).
`isoDayBefore` at `:112-114` calls `.toISOString()` on `NaN`. It is reached from
`src/lib/factsheet/build-payload.ts:1192-1193` (`portfolioFigures` → `alignBlend`) inside
`if (ingestSource === "api")` at `:1164`. Nothing on the way out catches a `RangeError`:
- `fetchAndBuildPayload`'s only catches rethrow anything that is not a `CompositeSeriesReadError`
  (`fetch-and-build-payload.ts:528-534`, `:674-677`).
- The `unstable_cache` callback (`page.tsx:199-205`) adds no catch.
- The page rethrows any non-`FactsheetReadError` (`src/app/factsheet/[id]/v2/page.tsx:699-707`,
  `if (!(err instanceof FactsheetReadError)) throw err;`).

So the route error boundary `src/app/factsheet/[id]/error.tsx` renders. On a stale cache entry,
background revalidation keeps the old entry. On a miss, which is any new `computed_at`, every
request errors. **User-facing: the public factsheet errors.**

**Issue:** round 1's WR-01 was "the builder no longer throws for a malformed date". It was closed,
and round 2 confirmed it, on the default `csv` arm only (`build-payload.ts:923`,
`strategy.ingestSource ?? "csv"`). The Phase 170.2 `source:` comment in
`fetch-and-build-payload.ts` (the `strategyArg` block) records that `ingestSource` "reads 'api'
for every PROD strategy". On that arm, any `dates[0]` that `Date.parse` rejects throws in `alignBlend`.
Examples: `""`, `2023-13-01`, `2023-02-32`, `2024-1-5`. 80d43fa7a's withheld stress form exists
for exactly an unreadable first date, so on PROD it renders only for the narrow set `Date.parse`
rolls over, such as `2024-02-30`. `StressWindowsPanel.unreadable.test.tsx:16-31` never sets
`ingestSource`, so it pins the `csv` arm only.

**Measured:** `buildFactsheetPayload` called with the test file's own fixture
(`payloadWithFirstDate`):

| first date | default / `csv` arm | `api` arm |
|---|---|---|
| `"2023-13-01"` | `stressWindows.unreadable: true` | **throws `RangeError: Invalid time value`** |
| `"2023-02-32"` | `unreadable: true` | **throws** |
| `""` | `unreadable: true` | **throws** |

The same throw happens through the real series chain (`resolveDailyReturnSeries` →
`buildFactsheetPayload`, api arm): a curve with an unpadded
`"2024-01-1"` that sorts to the native series' first position (curve starting 2024-01-09). The
native build throws and the factsheet errors. The USD build for the same curve succeeds, because
the converter dropped the date.

**Failure scenario:** a PROD (curve-derived, api-arm) strategy whose stored curve has a malformed
date in its second sorted position. The record is unreadable, and the phase intends that to
withhold the figures and report it. Instead `/factsheet/<id>` fails with an unhandled error for
every visitor, through `error.tsx`. No withheld reason shows. The build's Sentry
`figure-record-unreadable` report does fire, because it runs at `build-payload.ts:~962`, before
the api arm at `:1164`. But the viewer gets the error page, not the withheld record.

**Fix:** `alignBlend` must not do date math on an unreadable first date. Either skip the
allocator blends when `totalRecord.unreadable` (they are record-derived figures), or guard the
base level:

```ts
// allocator.ts alignBlend
if (dates.length > 0 && Number.isFinite(Date.parse(`${dates[0]}T00:00:00Z`))) {
  level.push({ date: isoDayBefore(dates[0]), close: 1 });
  ...
}
```

The first option matches the phase's rule that an unreadable record withholds its figures. Add
`ingestSource: "api"` cases to `StressWindowsPanel.unreadable.test.tsx`, and a parity case through
`fetchAndBuildPayload` for an api-arm curve whose second point is `"2024-01-1"`. Each should
assert a payload with `figureRecord.unreadable === true`, not a throw.
