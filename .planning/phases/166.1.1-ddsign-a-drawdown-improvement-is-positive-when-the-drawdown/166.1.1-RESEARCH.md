## Summary

Three scorers compute the drawdown delta as `current_max_dd - new_max_dd`. `_max_drawdown` returns a value <= 0 (`drawdown.min()`), so that expression is NEGATIVE when the new book is shallower and POSITIVE when it is deeper. The bridge (`bridge_scoring`) was corrected under H-1065 to `new - current`. Nothing since has touched the three sites: `git blame` dates the three expressions to 2026-04-07, 2026-04-16 and 2026-06-03, and neither WEALTHRETURNS (#973) nor BENCHALIGN changed a drawdown line (`git diff d9c173346 HEAD` over the three files shows only an import reformat for `_max_drawdown`).

The fix is a one-token swap at each site, and it is safe to centralize: all four scorers (the three sites plus the bridge) already import from `services.portfolio_optimizer`, where `_max_drawdown` lives. A single `drawdown_improvement(before, after)` helper there, returning `after - before` or `None`, removes the chance of a fifth drift. I prototyped it in a scratch copy: all 654 existing tests in the 14 relevant files still pass (no existing test pins the old sign), the 10 new oracles pass, and `mypy --strict` is clean.

Every TS renderer already assumes positive = improvement. None negates or takes `abs()` (D-03 finds nothing to correct, only comments to update). On stored values (D-04): `match_candidates` rows are re-scored every cron pass (`RECOMPUTE_MIN_AGE_HOURS = 12`, retention keeps the newest 7 batches) and ARE bounded. The one persisted value that is never recomputed on its own is `portfolio_analytics.optimizer_suggestions` (carried forward verbatim into every new analytics row; refreshed only when someone runs the optimizer). Measured read-only on PROD 2026-10-09: **0 of 6 `portfolio_analytics` rows hold suggestions, and 0 `match_candidates` rows carry a `dd_improvement`**, so no wrong-sign stored value exists today and no founder question is needed before the fix.

**Primary recommendation:** add `drawdown_improvement(before_max_dd, after_max_dd) -> Optional[float]` beside `_max_drawdown` in `services/portfolio_optimizer.py`, route all four scorers through it, write the failing oracles first (they are given below), fix the now-false docstring/comment text (`simulate_add_candidate` docstring, `types.ts` `SimulatorDeltas` block), and ship as a Python behaviour fix with a CHANGELOG entry. Do NOT bump `ENGINE_VERSION`.

## The Three Sites At HEAD

All three read and quoted from the files this session (HEAD `ca2413d19`). `_max_drawdown` is the shared input.

**The input** `[VERIFIED: analytics-service/services/portfolio_optimizer.py:361-367]`:
```python
def _max_drawdown(returns: pd.Series) -> Optional[float]:
    if returns.empty:
        return None
    cumulative = (1 + returns).cumprod()
    running_max = cumulative.cummax()
    drawdown = (cumulative - running_max) / running_max
    return _safe_float(float(drawdown.min()))
```
So max drawdown is a **negative fraction (<= 0)** at every site. `None` only for an empty series.

The bridge's own comment states the convention in words (`[VERIFIED: bridge_scoring.py:176-181]`): "H-1065: _max_drawdown returns <= 0, so a shallower (better) new drawdown means new_dd > current_dd. ### Construction (hand-computable, independent of the code under test)

`_max_drawdown` starts its running max at the first cumulative value, so the series must put the shock AFTER day 0 (see Pitfall 1).

**Case A (the ROADMAP's -0.464 -> -0.236):**
- Book `s1` = `[0.0]*10 + [-0.464] + [0.0]*29` -> max DD exactly **-0.464**.
- Candidate `c1` = `[0.0]*10 + [-0.008] + [0.0]*29`, `add_weight=0.5`, `weights={"s1": 1.0}` -> blend shock day = `0.5*(-0.464) + 0.5*(-0.008) = -0.236` exactly -> proposed max DD **-0.236**.
- Oracle: improvement = **+0.228**. HEAD returns **-0.228** at all three sites.

**Case B (constant-yield book whose drawdown got worse):**
- Book `s1` = `[0.001]*40` (constant yield: max DD 0.0; `current_sharpe` None).
- Candidate `c1` = `[0.0]*20 + [-0.096] + [0.0]*19`, `add_weight=0.10` -> blend shock day = `0.9*0.001 + 0.1*(-0.096) = -0.0087` -> proposed max DD **-0.0087**.
- Oracle: improvement = **-0.0087**. HEAD returns **+0.0087** at all three sites (the ROADMAP's "improve drawdown by 0.87%").

### Ranking oracles (SC-2)

Constant-yield one-strategy book makes `sharpe_lift` and `corr_reduction` `None` for EVERY candidate, so the drawdown is the only axis that can order them (this isolates the axis without patching the normalizer).
- `mild` = Case B candidate (blend DD -0.0087); `deep` = `[0.0]*20 + [-0.5] + [0.0]*19` (blend DD `0.9*0.001 + 0.1*(-0.5) = -0.0491`).
- **Optimizer** (`find_improvement_candidates`, `add_weight=0.10`): HEAD order `['deep','mild']` with `dd_improvement` `[+0.0491, +0.0087]`. After fix `['mild','deep']` with `[-0.0087, -0.0491]`.
- **Match engine** (`score_candidates`, `preferences={"target_ticket_size_usd": 10.0}`, `portfolio_aum=100.0` -> `add_weight = 0.10`, one `portfolio_strategies` entry): HEAD order `['deep','mild']`, scores `deep 57.5 / mild 49.5`. After fix `['mild','deep']`, scores `mild 57.5 / deep 49.5`. The 8.0 gap is exactly `100 * W_PORTFOLIO_FIT * W_DD_IMPROVEMENT * (1.0 - 0.0)`.

## D-04: Stored Values

**Finding 1, bounded and recomputed (no action):** `match_batches` / `match_candidates`. ## Shared-Helper Opportunity (CONTEXT Discretion: yes)

All four scorers already import from `services.portfolio_optimizer`: `simulator_scoring.py:33`, `match_engine.py:37`, `bridge_scoring.py:18`. So one function beside `_max_drawdown` adds no import edge and no cycle.

```python
# analytics-service/services/portfolio_optimizer.py, immediately above _max_drawdown
def drawdown_improvement(
    before_max_dd: Optional[float], after_max_dd: Optional[float]
) -> Optional[float]:
    """Signed drawdown improvement: POSITIVE when ``after`` is shallower.

    ``_max_drawdown`` returns <= 0, so shallower means closer to 0 and the
    improvement is ``after - before`` (-0.236 - -0.464 = +0.228). None when
    either side is None: a delta against a drawdown that does not exist does
    not exist either (166.1 D7).
    """
    if before_max_dd is None or after_max_dd is None:
        return None
    return after_max_dd - before_max_dd
```

Call sites (all executed in the scratch copy):
- simulator: `dd_delta = drawdown_improvement(current_max_dd, proposed_max_dd)`
- optimizer: `dd_improvement = drawdown_improvement(current_max_dd, new_max_dd)` and `+ w3 * (dd_improvement if dd_improvement is not None else 0.0)` in the score
- match engine: `dd_improvement = drawdown_improvement(current_max_dd, new_max_dd)`
- bridge: `dd_delta = drawdown_improvement(current_dd, new_dd)` (behaviour-identical to `_delta(new_dd, current_dd)`; routing it through the helper makes the reference and the three fixed sites share ONE definition)

Prototype result: 568 existing tests in the 10 closest files pass, the 10 oracles pass, `mypy --strict --follow-imports=silent --config-file=pyproject.toml` is clean on the four modules. Name the helper in tests by symbol, and add a tiny unit test of the helper itself (`(-0.464, -0.236) -> +0.228`; `(0.0, -0.0087) -> -0.0087`; either side `None` -> `None`). The behaviour tests at each site remain the per-site gates required by D-02; the helper test is additive.

### Pattern: sign defined once, named for what it means
**What:** one helper whose name says "improvement" and whose docstring states "positive = shallower".
**When:** any code subtracting two `_max_drawdown` values.
**Anti-pattern:** a bare `a - b` on two drawdowns at the call site. Four of these existed; two directions were in use for eight months.

### Anti-Patterns to Avoid
- **Negating or `abs()` in the renderer to fix the display.** Wrong tier: it would leave the match score ranking inverted, which is the larger harm. D-03 confirmed no renderer does this.
- **Editing `bridge_scoring._delta` or the shared `_delta` in `simulator_scoring`.** They serve other axes (Sharpe, correlation, concentration) with the opposite or neutral order; changing them shifts those chips.
- **Backfilling `optimizer_suggestions` or `match_candidates`.** Locked out by D-04.
- **Bumping `ENGINE_VERSION`** (see above) or touching `WEIGHTS_VERSION`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Signed drawdown delta | a fourth/fifth inline subtraction | `drawdown_improvement` | the four copies disagreed for months |
| Max drawdown of a returns series | a new cummax loop | `_max_drawdown` | already shared by all scorers; changing it moves the Sharpe-adjacent metrics |
| Min-max normalization | a custom scaler | `_normalize_min_max` | its single-value clamp and all-equal -> 0.5 rules are tested and relied on |
| Wire/schema change | a new field `dd_improvement_v2` | keep `dd_delta` / `dd_improvement` | the contract is a nullable fraction; only the sign of the value changes |

**Key insight:** this is a convention bug, not a math bug. The cheap, durable fix is to give the convention one definition and one test per consumer.

## Common Pitfalls

### Pitfall 1: A first-day loss is not a drawdown in `_max_drawdown`
**What goes wrong:** a fixture whose shock is the FIRST return reads a much shallower max DD than intended. I hit it: a candidate with `[-0.5, 0.0, ...]` at weight 0.5 reported -0.232 instead of ~-0.424.
**Why:** `running_max = cumulative.cummax()` starts at `cumulative[0]` (already post-loss), never at 1.0.
**How to avoid:** put every shock after at least one non-negative day (the oracles above use day 10 or 20). Assert the precondition `_max_drawdown(series) == approx(expected)` in the test.
**Warning signs:** an oracle that matches the ROADMAP number only when the shock moves by one day. (Out-of-scope quirk, booked under Open Questions.)

### Pitfall 2: Using `approx` against the wrong magnitude
**What goes wrong:** `0.5*(-0.464) + 0.5*(-0.008)` is `-0.236` only to float precision (`-0.22799999999999998` observed). Use `pytest.approx`, never `==`.

### Pitfall 3: Testing the ranking with real Sharpe/correlation noise
**What goes wrong:** two random candidates differ on all three axes, so a flipped drawdown sign may not flip the order.
**How to avoid:** the constant-yield one-strategy book (above) makes `sharpe_lift` and `corr_reduction` `None` for all candidates, leaving drawdown as the only ordering axis. Assert order AND the 57.5 / 49.5 pair.

### Pitfall 4: Forgetting the docstring/comment text that asserts the old formula
**What goes wrong:** the code is fixed but `simulate_add_candidate`'s docstring and `types.ts` still say `current - proposed`; the next reader copies the wrong formula (this is how the bridge and the three sites diverged).
**How to avoid:** the change set above lists them; a plan task should grep for `current_max_dd  - proposed_max_dd` and `current  - proposed  (less drawdown` and expect 0 hits.

### Pitfall 5: A shared helper that shifts the optimizer's `None` semantics
**What goes wrong:** the helper returns `None` where the old line returned `0` (unreachable today, see per-site nuances). If the score line is left as `+ w3 * dd_improvement`, a future `None` raises `TypeError` in the ranking.
**How to avoid:** keep the `if ... is not None else 0.0` guard in the score (as the prototype does). The emitted `dd_improvement` then follows 166.1 D7 (`None`, not a fabricated `0`).

### Pitfall 6: zsh does not word-split `$VAR`
**What goes wrong:** `T="a b"; pytest $T` passes one argument in zsh. Run multi-file pytest through `bash -c` or list the files inline (cost me a false "identical" earlier).

### Pitfall 7: CHANGELOG / ship mechanics
`CHANGELOG.md`, `VERSION`, `package.json` move together in the `chore(release)` commit; enumerate every branch commit and map each to a bullet (the repo's cross-check rule); do not write the CI skip tokens anywhere; a squash merge concatenates every branch commit message. A Python behaviour fix deploys through Railway after main CI is green; confirm `/health` `git_sha`.
