<domain>
## Phase Boundary

Fix the sign of the drawdown-improvement number at the three Python sites named in the ROADMAP (`simulate_add_candidate` `dd_delta`, `find_improvement_candidates` `dd_improvement`, `match_engine._compute_portfolio_fit_components` `dd_improvement`), so a shallower max drawdown is a POSITIVE improvement everywhere, the match score rewards the shallower book, and every renderer's copy ("Positive = shallower", "improve drawdown by") stays true.

</domain>

<decisions>
## Implementation Decisions

- **D-01 (convention):** shallower-is-positive, matching the bridge's existing convention (H-1065). With max drawdown stored as a negative fraction, improvement = new_dd - old_dd (e.g. -0.236 - (-0.464) = +0.228). The research confirms the bridge's exact formula and copies it; it does not invent a second one.
- **D-02 (tests):** one test per site that fails on the old sign (the ROADMAP's measured cases: -0.464 → -0.236 must read +0.228; the constant-yield book whose drawdown got worse must read negative), plus a ranking test proving the match order flips back to the shallower book. Neuter → RED → restore from a byte backup.
- **D-03 (renderers):** every TS renderer of these fields is audited; any renderer that compensated for the wrong sign (negating, abs()) is corrected in the same phase, with a test. Copy is unchanged unless it becomes false.
- **D-04 (stored values):** no backfill. Simulator and optimizer results are computed on request; match candidates are re-scored by the next match run. If research finds a persisted score that is never recomputed, it names it and the founder is asked before anything is rewritten.

### Claude's Discretion
- Shared helper vs three local fixes: one shared helper if the three sites compute the same quantity, so the sign cannot drift again.

</decisions>
