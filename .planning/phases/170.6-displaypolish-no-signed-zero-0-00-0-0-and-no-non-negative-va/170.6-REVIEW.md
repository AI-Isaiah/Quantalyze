## Summary

The core is sound. `display-sign.ts` reads the sign from `Number((v*scale).toFixed(dp))`, the same expression whose digits it prints. So within one call, text and tone cannot disagree. NaN, null, undefined and ±Infinity all return the dash with no tone. `-0` prints `0.00`. I traced every changed call site where a tone and a text sit side by side, and each pair reads the same dp and scale. That includes KpiStrip (scale 1 for Sharpe and Avg |ρ|, 100 otherwise), OutcomesWidget, VaR/ES, StressWindows, the EoY delta (`ppDelta(s,b)` against `signTone(s-b)`), HeatmapPanels' YTD and reveal, TimeSeriesChart's bars and pit labels, ReplacementCard, PortfolioImpactPanel, AttributionBar, StrategyTable and EditorialHero.

- **`metricColor` callers:** all 16 use the default 2 dp, which matches `formatPercent` and `formatNumber`.
- **`formatNumber` against `signTone` near zero:** at the zero boundary (±0.005 at 2 dp) Intl and `toFixed` agree, so the detect-only `formatNumber` cannot disagree with `metricColor(…, "ratio")` on whether a figure is zero. I measured Intl and `toFixed` side by side at ties.
- **D-07:** applied in the single builder (`buildComparatorBlock.summaryOf`). The full payload, the dated suffix (`summarySince`), the basis bundles and `windowView` all go through it. The only remaining reader of the comparator's `ann_vol` is the vol-match scale, which reads `benchSummary` directly, and that is intended.
- **D-08:** the two factsheet callers pass a `comparatorPartialThrough` date, `formatAbsoluteDate` formats in UTC, and full coverage leaves the sentence unchanged.
- **Tests:** all 42 changed test files pass (899 tests).

**The two matcher narrowings.** Narrowing 2 (skip an operand named `length`, `size` or `count`) is safe. The lookbehind needs a word boundary and lowercase, so `tradeCount`, `discount` and `netCount` are still scanned. Narrowing 3 (drop bracketed JSX groups in R7) hides nothing in today's tree. I ran an un-narrowed R7 over all of `src`. The only hits were RiskAttribution's `share >= 0` validity guard, `hasScenario` (a length check), `isRateLimited` and an admin `holdingsEmpty`. But narrowing 3 does open a hole the guard cannot see (WR-04).

**The 74 allowlist entries.** I read every R6 `toFixed` pin and the R5 pins that sit near figures, and none hides a signed figure: ScenarioComposer's 8, PortfolioImpactPanel's aria magnitude (an early `unchanged` return covers a rounded zero), MetricsColumn's win/|loss|, BatchD's KS and p-value, TailRisk's P1 (always at or below -2% when it renders) and WorstDrawdowns' `MIN_DEPTH_PCT`.

**What the guard does miss is outside its scope.** It does not scan `src/lib`, except two files. It has no token for `bg-positive` or `bg-negative`. Because of those gaps, one user-facing signed zero and one second implementation of the rule ship under a green guard (WR-01, WR-02, WR-03).

## Warnings

### WR-01: The correlation-regime insight prints a signed zero ("to -0.00") on /allocations and /demo. Confidence 7

**File:** `src/lib/portfolio-insights.ts:156`
**Issue:** `computeRegimeChange` builds its sentence with a bare `best.prior.toFixed(2)` and `best.recent.toFixed(2)`. Both are averages of rolling correlations, which are signed. The insight fires when |recent − prior| ≥ 0.15, so the case that matters is one leg collapsing to about zero.
**Failure scenario:** prior = 0.62, recent = −0.003 gives "Correlation regime shift: pairwise correlation loosened from 0.62 to -0.00 between two strategies in your portfolio." That is the exact `-0.00` that D-02 says "never appears". O-1 and O-7 made D-02 global, and `InsightStrip` renders this sentence on `/allocations` (`AllocationDashboardV2.tsx:218`) and `/demo` (`demo/page.tsx:310`).
**Why the guard passes it:** `src/lib/portfolio-insights.ts` is outside `SCAN_DIRS`/`SCAN_FILES`, so its R6 `toFixed` count is never taken.
**Fix:**
```ts
import { formatFixedSigned } from "@/lib/factsheet/display-sign";
// …
sentence: `Correlation regime shift: pairwise correlation ${direction} from ${formatFixedSigned(best.prior, { dp: 2 })} to ${formatFixedSigned(best.recent, { dp: 2 })} between two strategies in your portfolio.`,
```
Then add `src/lib/portfolio-insights.ts` to `SCAN_FILES`, with an R6 pin of 0 at this line. Add a test with hand-typed prior 0.62 and recent −0.003 that expects "to 0.00".

### WR-02: A second implementation of the rounded-sign rule ships beside display-sign (`signAtCents` / `formatUsdSigned`), which D-05 forbids. Confidence 6

**File:** `src/lib/dollar-validation.ts:77-106`. Consumers: `src/app/(dashboard)/allocations/components/OpenPositionsTable.tsx:116-121, 280, 298` and `src/app/(dashboard)/allocations/components/HoldingsTable.tsx:741`.
**Issue:** `signAtCents` is `Number(n.toFixed(2))` compared with 0, which is `roundForDisplay` plus `signTone` at dp 2. `formatUsdSigned` chooses `+` / `−` / nothing from it, which is `formatFixedSigned` with `minus: "−"`. Both modules' docblocks call themselves the "ONE" decision. Today they agree on output, so nothing displays wrongly yet. But D-05 says the rule lives in `display-sign.ts` and "nowhere else", and the guard file states "CI fails the next private one". This private one passes for three reasons:
- `dollar-validation.ts` is not scanned.
- R4 only looks for a `metricColor` declaration.
- `pnlColor`'s `if (sign === "positive") return "var(--color-positive)"` is not a comparison with zero, so R2 cannot see it.

**Failure scenario:** a later change to display-sign's zero or rounding rule leaves the P&L columns on the old one. For example, the Intl tie difference I measured (`toLocaleString` rounds `1.005` to `1.01`, `toFixed` to `1.00`) breaks `formatUsdSigned`'s own docblock claim that the two "apply the same rule". Allocations would then disagree with the factsheet on the same rule, and no test would fail.
**Fix:** implement `signAtCents` as `signTone(n, 2) ?? (n == null || !Number.isFinite(n) ? null : "zero")`. Build `formatUsdSigned`'s glyph from the same call, keeping the Intl currency digits as `formatNumber` does. Add `src/lib/dollar-validation.ts` to `SCAN_FILES`. Extend R4, or add an R9, to flag any `Number(x.toFixed(` compared with 0 outside `RULE_FILE`.

### WR-03: The ScenarioComposer risk-contribution row tags a hedge and paints a green bar from the raw sign, beside a figure that prints "0.0%". Confidence 6

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:6053`, `6077-6084`, `6091`, `6097`
**Issue:** `const isHedge = pcr < 0;` drives two things:
- the "RISK-REDUCING" tag (`isHedge && (…)`);
- the bar's `bg-positive` (green) against `bg-accent`.

Plan 12 changed the printed figure to `formatPcrPercent(pcr)` (1 dp, unsigned at a rounded zero), so text and marks now disagree. That is a D-03 violation ("red and green follow the sign of the ROUNDED value, never the raw one").
**Failure scenario:** a strategy whose percent contribution to risk is −0.0003 shows "0.0%" with a green bar and a "RISK-REDUCING" chip. The reader sees a claim the figure next to it does not support. The bar is about 0.03% wide, but the chip is fully visible.
**Why the guard passes it:**
- `TONE_TOKEN_RE` has no `bg-positive` or `bg-negative`.
- R7's use pattern only matches `name ?`, never `name &&`.
**Fix:**
```ts
const isHedge = signTone(pcr, 1, 100) === "negative";
```
Add `bg-(positive|negative)` (and `border-…`) to `NEG_TOKEN`/`POS_TOKEN`, and let R7's use regex accept `&&` as well as `?`.

### WR-04: Matcher narrowing 3 (`dropJsxGroups`) lets a raw-sign boolean choose between toned JSX branches with no rule firing. Confidence 6

**File:** `src/__tests__/display-sign-single-source.test.ts:264-297, 428`
**Issue:** R7 now blanks every bracketed group in the ternary tail that contains a JSX element, so it only sees colours the boolean picks directly. Neither backstop the summary cites covers the gap:
- **R2:** only fires when the comparison is in the ternary's own condition.
- **R5:** treats a negative token as conditional when an earlier ` ? ` is on the same line, and never counts positive tokens at all.

**Failure scenario:** a new cell written as
```tsx
const up = delta >= 0;
… {up ? (<span className="text-positive">{txt}</span>) : (<span className="text-negative">{txt}</span>)}
```
passes R1 to R8. At delta = −0.0004 it renders red beside "0.00%", which is exactly the defect class the guard exists to stop. Today's tree has no such site; I ran an un-narrowed R7 over all of `src` and listed the hits in the summary. But the narrowing was made to clear one validity-guard false positive (`RiskAttribution.tsx` `assessable = … share >= 0`) by weakening the rule for every file. The guard already has a mechanism for that: a pinned, reasoned count.
**Fix:** revert narrowing 3. Pin RiskAttribution under a new two-sided R7 allowlist count, with its reason ("`assessable` is a validity guard; the colour comes from `overweight`"). Add a red self-test for the parenthesized-JSX form above.

### WR-05: Two D-59 basis tests lost their hand-typed oracle. The expected values are now computed by the code under test. Confidence 5

**File:** `src/lib/factsheet/build-payload.benchmark-opt.test.ts:292-328`
**Issue:** to clear the new 90-day floor, plan 11 lengthened the windows and replaced the literals with `coveredOracle(block.dailyReturns!, …)`. Those literals were `0.23196458527486924`, `0.4445740025160893`, `0.3295726382836115` and `-3.2996046778540213`. The replacement is `compute()` run over the block's own aligned output. CONTEXT's "Claude's Discretion" says expected values "must be typed by hand, never computed by the code under test".
- **What the tests still pin:** the 252-versus-365 basis, through `not.toBeCloseTo(on365.ann_vol)`.
- **What they no longer pin:** the aligned returns and the summary values. A regression in `alignCoveredReturns` or `compute` now moves the oracle and the actual together, so these cases cannot fail on it. The same applies to the D-58 case's `cov` index list, which is now derived (`filter((i) => i !== 2 && i !== 3)`).

**Failure scenario:** an alignment change that pairs Monday with the wrong close passes both D-59 tests, because `block.dailyReturns` feeds both sides.
**Fix:** measure the new windows once and paste the four values as literals, beside a comment naming the seed and window. Keep the `on365` inequality as the basis pin.
