<objective>
Make the read-retry seam treat an httpx `ReadTimeout` as transient, as D-02 and D-02a decide. Then a
single slow response no longer fails the worker's claim (QUANTALYZE-2C, 18 events) or watchdog reset
(QUANTALYZE-2B, 7 events) on the first attempt.

Purpose: SC-2 for the sites that already consume `db_read_with_retry`.
Output: one new predicate, helper and consumer tests that were RED first, a corrected worst-case
statement, and log classifications that name the real class.

**The decision this plan implements, quoted from 166.5.1-CONTEXT.md (D-02a, founder 2026-10-21,
AskUserQuestion "A: helper + move 4 reads (Recommended)"):** "supersedes D-02's 'applies only where
the helper is already used'. Retry httpx `ReadTimeout` wherever `db_read_with_retry` is already used,
the job claim `_claim_priority` (2C) and the idempotent watchdog reset (2B) included (a timed-out
claim cannot double-claim: its batch waits for the watchdog, as today), and move the four pure reads
Sentry named onto the helper. [...] No retry is added to any other write." This plan does the first
half. Plan 166.5.1-04 moves the four reads.

**Measured worst case (2026-10-21).** `get_supabase()` builds the PostgREST httpx session with
`Timeout(timeout=120)`, so the read timeout is 120 s per attempt. Neither `create_client` nor
`_force_http1` overrides postgrest's `DEFAULT_POSTGREST_CLIENT_TIMEOUT`, and the session's timeout
printed `Timeout(timeout=120)` when built with dummy credentials.
- **Per helper call:** a ReadTimeout on every attempt now costs 3 x 120 s plus at most about 4 s of
  backoff (1 s + 2 s base, plus up to 0.5 s jitter on each of the two sleeps). That is about 364 s,
  roughly 6 minutes, where one 120 s attempt cost before. The helper docstring's "strictly below the
  60s API gateway window" holds for a gateway 504 only.
- **Claim:** `dispatch_tick` stamps healthz only after the claim returns, and `STALE_THRESHOLD` is
  90 s. A claim hanging on a ReadTimeout already left healthz stale before this phase (one 120 s
  attempt); now it can stay stale for up to about 6 min.
- **Watchdog:** `watchdog_tick` can block `watchdog_loop` for up to about 6 min before
  `report_orphaned_capped_reconstructs` runs. Plan 04 adds a second helper read there, so one
  iteration can take up to about 12 min before its sleep.
- **Request handlers:** the `routers/process_key.py` reads that use the helper can hold a request up
  to about 6 min instead of 2 before failing.
These are recorded consequences of D-02a, not new decisions.
</objective>
