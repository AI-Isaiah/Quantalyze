<objective>
Make the read-retry seam treat an httpx `ReadTimeout` as transient (D-02), so the worker's claim
(QUANTALYZE-2C, 18 events) and watchdog reset (QUANTALYZE-2B, 7 events) stop failing a whole tick on
one slow response. Before any code changes, the plan settles a classification question that D-02's
wording does not answer.

Purpose: SC-2 for the sites that already consume `db_read_with_retry`.
Output: one new predicate, helper and consumer tests that were RED first, and corrected log
classifications.

**Why this plan opens with a decision (measured while planning, 2026-10-21, code at the phase branch head).**
CONTEXT root cause B lists `_claim_priority`, `_reset`, `_sel` and "the cron-recompute reads" as the
sites where a ReadTimeout propagates. D-02 then says the fix "applies only where the helper is
already used: read sites and the idempotent-by-filter watchdog reset". Three facts in the code do not
fit that sentence:
1. `_claim_priority` uses the helper, but it is not a read. `claim_compute_jobs_with_priority` is an
   UPDATE that sets status, `claimed_at` and `claim_token` and adds 1 to `attempts`.
   - A retry cannot claim a row twice: the claim matches only claimable rows, under
     `FOR UPDATE SKIP LOCKED`.
   - A first attempt that committed but timed out on the response leaves its batch `running` and
     unreported. That happens whether or not the call is retried, and the watchdog reclaims the batch.
   - So a retry adds no double run. It does make SC-2's sentence "no retry is added to a write" true
     only in that sense.
2. Neither `_sel` in services/job_worker.py (QUANTALYZE-2E, 8 events) uses the helper. Both go through
   the fail-fast `db_execute`: one in `_capture_history_reconstruct_capped`, one in
   `report_orphaned_capped_reconstructs`. Both are pure SELECTs.
3. Among the cron's reads, only the kill switch (`_engine_is_enabled`) and the cursor read
   (`_read_cron_cursor`) use the helper. Both catch their own failure and log it without a traceback.
   The reads that can raise a bare ReadTimeout out of `/api/match/cron-recompute` (QUANTALYZE-2D, 2F,
   2G) go through `db_execute` or `asyncio.to_thread` instead:
   - the allocator page query, a synchronous `.execute()` inside the async handler;
   - `_load_candidate_universe`;
   - `_should_skip_allocator`'s read;
   - the per-allocator `_score_one_allocator`, which also writes.
   The planner cannot read the groups' culprit frames: there is no Sentry access in this run.
</objective>
