## Summary

The phase made three fixes. (A) The demo allocator is now excluded in the cron's allocator query. (B) The read-retry helper treats an httpx `ReadTimeout` as transient, a sync twin was added, and four reads moved onto the helpers. (C) `derive_allocator_equity` got a 20-minute watchdog override. The five touched test files pass at HEAD (`286 passed`, run from `analytics-service/` with the Supabase env vars unset).

I checked each point the brief asked about against the code and the SQL.

- **Claim and watchdog-reset retry (D-02a).** I found no defect. In migration 20260927120000, `claim_compute_jobs_with_priority` only selects `status IN ('pending','failed_retry')` and uses `FOR UPDATE SKIP LOCKED`. So a retried claim can never take a row an earlier attempt already moved to `running`, even if that attempt is still executing on the server. A claim that committed but lost its response leaves its batch `running` (with `attempts + 1`) until the watchdog resets it. That was already true before this phase: `dispatch_loop` re-claimed on the next 30 s tick after a raised ReadTimeout, so the retry adds no new stranding mode. `reset_stalled_compute_jobs` (migration 20260516104201) filters on staleness with `SKIP LOCKED`, so a concurrent or repeated reset is idempotent. No double-claim and no lost job.
- **The `RuntimeError` that replaced the nothing-handled branch.** I found no defect. `allocators` is non-empty after the `if not allocators` early return, and an empty universe returns before the loop. The loop's first iteration can do one of four things: (1) `break` on the mid-run kill switch, which returns before the boundary block; (2) raise out of `_should_skip_allocator`, which escapes the handler; (3) catch a `_score_one_allocator` failure; or (4) succeed. Cases 3 and 4 both reach `last_handled_id = allocator_id`. So the raise cannot be reached.
- **Cursor correctness in `cron_recompute`.** I found no defect. `.neq("id", _DEMO_ALLOCATOR_ID)` sits in the keyset query beside `.gt("id", cursor)` and `.order("id")`. `has_more` is computed from that already-excluded page, and no earlier code wrote the demo id as a cursor, because the old filter dropped it before handling. `_DEMO_ALLOCATOR_ID` is a constant literal (`routers/match.py:226`), so the `neq` value can never be empty.
- **Whether the sync twin blocks the event loop.** I found no defect. `_load_allocator_context` is called only through `asyncio.to_thread` (`routers/match.py:1805`, `services/job_worker.py:11785`). `read_native_unpriced_days` is called from `_load_holding_portfolio_context` (only through `_load_allocator_context`) and from `services/equity_reconstruction.py:2250` inside `db_execute`. No async caller reaches the twin directly.
- **Whether the override or the invariant can let a real run be reset.** Yes. See WR-01.
- **Tests that cannot fail.** The new retry tests and the D-01 tests are RED on the old code (I read their assertions against the old paths). The D-03 "reproduction" test is weak, as recorded under WR-01.

## Warnings

### WR-01: The 20-minute `derive_allocator_equity` override is sized from a right-censored measurement and ignores batch arithmetic, so SC-3's "never run twice" is not met (data-integrity)

**File:** `analytics-service/main_worker.py:366-381` (override and comment); `analytics-service/main_worker.py:708-712` (`p_batch_size: 5`); `analytics-service/tests/test_main_worker.py` (`test_derive_allocator_equity_run_at_measured_claim_age_is_not_reset_under_the_runner`, `test_every_backfill_kind_has_an_explicit_watchdog_override`)

**Classification:** data-integrity. It also leaves a phase-goal gap: ROADMAP SC-3 says the race is "fixed at its source … so a finished job is never lost or run twice".

**Issue:**

1. **The measurement is censored at the old threshold.** The 14-day PROD sample (max 10:03.9, p95 8:14.8) was taken while the 10-minute default was resetting any `derive_allocator_equity` run that passed 10 minutes. A reset nulls `claimed_at` (migration 20260516104201), and the job is then re-claimed with a fresh `claimed_at`. So a run that exceeded the threshold never shows up as a long claim-to-done; only its later re-run is measured. The maximum is 10:03.9, within one 60 s `watchdog_loop` interval of the 600 s threshold. That is what a distribution truncated by the watchdog looks like, not the real tail. The comment's rationale, "20 minutes is about twice the measured maximum", therefore rests on a number the old bug capped. QUANTALYZE-2A/A firing at all (4 events in 7 days) is direct evidence that real runs went past the censoring point.
2. **The batch arithmetic bounds the claim age far above 20 minutes.** The comment states the mechanism correctly. `_claim_priority` claims `p_batch_size: 5` with one `claimed_at = now()` for the whole batch, and `dispatch_tick` runs the batch one job after another. On the backfill worker the batch-mates are `derive_broker_dailies` jobs, each with a 15-minute handler timeout. A `derive_allocator_equity` job fifth in a batch can therefore reach a claim age of up to 4 × 15 + 5 = 65 minutes before it finishes, and two slow broker-dailies batch-mates are enough to pass 20 minutes. If the PROD worker that claims these kinds runs `WORKER_CLAIM_ROLE=all` rather than `backfill`, the batch-mates can be any kind, including `process_key_long` at 30 minutes. I did not measure PROD's role from this worktree, and the comment assumes `backfill`. Past 20 minutes, the watchdog sets the row back to `pending` with `claim_token = NULL`. The claim's C39 exclusion no longer sees a `running` row for that allocator, so the job is claimable again, by another worker at once or by this worker after its batch. The original runner still finishes its work. The job runs twice, and the first runner's mark is refused (2A/A). The comment calls this a "RESIDUAL", but it is the same mechanism the phase set out to close, not an edge case.
3. **The tests cannot catch either point.**
   - The reproduction test does not run the reset or the mark. It re-implements the SQL threshold rule in Python and checks a single claim age of 604 s, which is the censored maximum. It passes for any override of 10:05 or more, so it adds nothing beyond `assert overrides["derive_allocator_equity"] == "20 minutes"`, which `test_calls_rpc_with_overrides` already makes.
   - The new invariant `test_every_backfill_kind_has_an_explicit_watchdog_override` only checks that the key exists. An override of `"11 minutes"` would pass it, even though its own failure message names the batch-serial mechanism as the reason the default is unsafe.

**Fix:** pick one of these and record the choice as a decision.

- **(a) Minimal fix that closes the mechanism at its source.** Give the backfill role a claim batch of 1, so each job's claim-age clock measures only its own runtime. This touches `_claim_priority` only:
  ```python
  "p_batch_size": 1 if WORKER_CLAIM_ROLE == "backfill" else 5,
  ```
  A 20-minute override is then four times the 5-minute handler bound. Throughput drops to one backfill claim per tick, with no per-tick wait between jobs. Weigh that against the D-06 cap comment at `main_worker.py:690-693`.
- **(b) Keep the batch of 5 and size the override from the batch bound.** The override must exceed `(p_batch_size - 1) × max(TIMEOUT_PER_KIND[k] for k in BACKFILL_KINDS) + TIMEOUT_PER_KIND["derive_allocator_equity"]` (65 min today). Make the invariant compute that bound from `TIMEOUT_PER_KIND`, `BACKFILL_KINDS` and the claim batch size, rather than only checking the key exists. That also exceeds `MAX_RATIO` 4.0 and will need the cap revisited. `derive_broker_dailies` at 30 minutes has the same exposure.

Either way:
- Re-measure on PROD with the censoring removed: count `derive_allocator_equity` rows that ever carried `last_error = 'worker_stalled'` or `attempts > 1` over the window, not only claim-to-done of the final claim.
- Replace the 604 s reproduction with an assertion on the batch-bound claim age.
- If the founder keeps 20 minutes with the residual, record SC-3 as partially met. As written, ROADMAP SC-3 claims "never … run twice", and this change does not deliver that.
