## Implementation Decisions

Founder accepted all four recommended answers on 2026-10-21 ("Accept all").

### Root causes measured 2026-10-21 (code read at origin/main; PROD read-only, marker first)
- **(A)** `analytics-service/routers/match.py` cron fetches allocators with `.in_("role", ["allocator", "both"])` only; nothing excludes `_DEMO_ALLOCATOR_ID`, so the M-3 guard after it fires `logger.error("match_engine cron: demo allocator %s appeared in allocators list …")` on every run. Its advice ("Verify profiles.is_example=true") names a column that does not exist: PROD `profiles` has no `is_example` column (42703).
- **(B)** `db_read_with_retry` (`analytics-service/services/db.py`) retries only `_is_gateway_timeout`-shaped exceptions; an httpx `ReadTimeout` propagates on the first attempt at `_claim_priority`, `_reset`, `_sel` and the cron-recompute reads.
- **(C)** `WATCHDOG_PER_KIND_OVERRIDES` in `analytics-service/main_worker.py` has no entry for `derive_allocator_equity`, so `reset_stalled_compute_jobs` uses the default `10 minutes`. PROD, last 14 days, 110 `derive_allocator_equity` jobs: p95 claim-to-done 8:14.8, max 10:03.9. A run past 10 minutes is flipped back to `pending` while its runner still works; its `mark_compute_job_done` / `mark_compute_job_failed` then refuse (P0002), which is QUANTALYZE-2A / A.

### Fixes
- **D-01 (A):** exclude `_DEMO_ALLOCATOR_ID` in the cron's allocator query itself, so the demo allocator is never fetched. Remove the error log and correct the stale M-3 comment (it names a non-existent `profiles.is_example`). A test pins the filter (RED on the old query). The demo boundary at scoring time stays as it is.
- **D-02 (B):** treat httpx `ReadTimeout` as transient in the read-retry helper, under the existing bounded budget (`DB_READ_MAX_RETRIES`, backoff and jitter unchanged). It applies only where the helper is already used: read sites and the idempotent-by-filter watchdog reset. No retry is added to any other write. A test goes RED on first-attempt propagation of a `ReadTimeout`.
- **D-03 (C):** add a `derive_allocator_equity` watchdog override strictly above its handler timeout (set from its measured runtime and handler budget, like the other long kinds). Extend the existing headroom invariant (`test_watchdog_threshold_exceeds_handler_timeout` / `test_every_kind_has_watchdog_headroom`) so a long-running kind without an override fails. Reproduce the reset-then-mark sequence in a test first. The mark functions' refusals stay loud.
- **D-04:** after deploy, read each group's event rate from Sentry over 48 h; resolve the fixed groups there.

- **D-02a (founder 2026-10-21, AskUserQuestion "A: helper + move 4 reads (Recommended)"):** supersedes D-02's "applies only where the helper is already used". Retry httpx `ReadTimeout` wherever `db_read_with_retry` is already used, the job claim `_claim_priority` (2C) and the idempotent watchdog reset (2B) included (a timed-out claim cannot double-claim: its batch waits for the watchdog, as today), and move the four pure reads Sentry named onto the helper. Top in-app frames read from Sentry 2026-10-21: 2E `services/job_worker.py` `report_orphaned_capped_reconstructs` → its `_sel` read (via `db_execute`); 2F `routers/match.py` `_should_skip_allocator` → the latest `match_batches` read (`.eq("allocator_id", …).order("computed_at", desc=True).limit(1)`); 2D `routers/match.py` `_load_allocator_context` → the `allocator_preferences` `.maybe_single()` read; 2G `services/allocator_positions.py` `read_native_unpriced_days` → its marker read (called from `match._load_holding_portfolio_context`). No retry is added to any other write.
