# Phase 164.2.1 Plan 01: SESSIONID-FENCE Summary

An abandoned wizard draft over key A no longer lends its `wizardSessionId` to a
wizard opened over key B: `deriveWizardResumeOverrides` now compares the key the
payload was written under against the key the mount will submit with, and
`WizardClient` stamps that key at every save site with the connect result rather
than a stale closure value. The partial unique index is untouched and remains
the guarantee — this is trigger removal on the terms the file's own doctrine set.

## Deviations from Plan

### [Rule 3 - Blocking] The component harness needs explicit storage doubles, not the preselect spec's guarded clear

- **Found during:** Task 1, on the first run of the new file.
- **Issue:** SC-1d failed. The plan and RESEARCH both said to copy
  `ContributionWizardOverlay.preselect.test.tsx`'s `window.localStorage?.clear?.()`
  idiom. A probe printed the real cause:
  `[wizard] saveWizardState failed: TypeError: window.localStorage.setItem is not a function`.
  Node 25 shadows jsdom's `window.localStorage` with an implementation whose
  `setItem` does not exist; `writeWizardState` catches storage failures, warns and
  returns, so **the seed silently never existed**. SC-1c was passing for the wrong
  reason — the exact vacuity this phase exists to prevent — and SC-1d, which
  demands a RESTORE, is what exposed it. The preselect spec is unaffected because
  it only ever writes; this file is the first in that directory that reads back.
- **Fix:** copied `installStorage()` verbatim from
  `WizardClient.csv-burn-persistence.test.tsx` (RESEARCH's own "Don't Hand-Roll"
  row prescribes exactly this), replaced the guarded clear with a per-test
  `localStore = {}; sessionStore = {}; installStorage();`, and added an
  APPLIED-NESS PROBE to the seed helper — `expect(await loadWizardState()).not.toBeNull()`
  with a message naming the storage doubles — so this failure can never again be
  silent. CI is Node 22, where jsdom's implementation works; the doubles make
  both boxes read the same.
- **Files modified:** `ContributionWizardOverlay.sessionid-fence.test.tsx`
- **Commit:** `40166edc`

### [Bookkeeping] Task 1's `= 25` grep tripwire reads 33 from Task 2 onward

Not a defect and not a deviation from intent — an artifact of the plan putting
the count check only in Task 1's verify while Task 2 deliberately adds eight
four-arg calls to the same file. It was `25` when Task 1's verify ran and was
recorded. The guarantee it stood for is carried from Task 2 onward by the
append-only diff (0 removed lines against the pinned base `45218594`), which is
strictly stronger: it proves no existing call was edited, not merely that the
total is unchanged. `git show <base>:…localStorage.test.ts | grep -c` still
reads **25** for the pre-existing region.

No other deviations. No architectural (Rule 4) decisions were needed.
