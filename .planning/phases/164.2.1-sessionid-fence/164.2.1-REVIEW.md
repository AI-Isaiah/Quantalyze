### WR-02: "constant `null` on the CSV branch" is not guaranteed by the code — the gate runs on a branch where it has no contract

**File:** `src/app/(dashboard)/strategies/new/wizard/WizardClient.tsx:609-610` (autosave effect comment) and `:452` (call site); `src/lib/wizard/localStorage.ts:158` ("that branch has no key at all"), `:487-488` ("write `apiKeyId: null` explicitly"), `:540` (`sessionKeyMatches` docblock: "the CSV branch (no key exists)"); `src/lib/wizard/localStorage.test.ts:1005`
**Issue:** Five comments assert that on the CSV branch the stored key is `null`
and the incoming key is `null`. Neither is enforced:

1. The 13 CSV sites stamp the `apiKeyId` **state**, not a literal `null`. That
   state seeds from `initialDraft?.api_key_id ?? preselectKey?.id ?? null`
   (`:285-286`).
2. The call site passes the same expression as the incoming key regardless of
   `source` (`:452`).
3. `ContributionWizardOverlay.tsx:302` passes `preselectKey={activePreselect}`
   unconditionally and the "CSV upload" pill (`:252-256`) is rendered whether
   or not a preselect is active.

Concrete path, user-reachable today: owner clicks "Finish setup →" on key B
(preselect B) → clicks "CSV upload" → `WizardClient` remounts with
`source="csv"`, `preselectKey=B`, `apiKeyId` state = `B`. If a CSV payload
sits in storage at `csv_upload` (the manager-route CSV wizard writes one on
every keystroke), `deriveWizardResumeOverrides` restores `step=csv_upload`, the
upload step renders, and the autosave stamps `apiKeyId: "bbbbbbbb-…"` on a CSV
payload. On that same mount the gate compared incoming `B` against stored
`null` and **declined the CSV session id together with any
`failedCsvSubmitSig` riding on it** (pinned as intended behaviour by the unit
test "does NOT restore the burn either when the key declines the session id").

Why this is more than a false sentence: on the CSV branch the key comparison
has no meaning — CSV submissions carry no key — so the only effect the gate
can ever have there is to strip a live CSV session id and its RT-3 burn. That
is the exact hazard RT-3 closed (a fresh id with the burn gone, resubmitting
content a failed attempt already spent). The SOURCE gate never had this shape
because a cross-source payload carries no CSV burn. Reachability needs a
failed CSV submit, a back-nav to upload, then the preselect + CSV-toggle
sequence — narrow, and the server-side equality refusal is the operative
fence, which is why this is a Warning and not a Blocker.

**Fix (preferred — make the comments true by construction):** on the CSV
branch the caller makes no key claim, so say so in code rather than in prose.
At the call site:
```ts
        // Phase 164.2.1 — the key THIS mount will submit under. `null` on the
        // CSV branch by construction: that branch carries no key, so it makes
        // no claim and the gate must not act on it.
        source === "csv"
          ? null
          : (initialDraft?.api_key_id ?? preselectKey?.id ?? null),
```
and stamp the literal `null` at the 13 CSV sites (`apiKeyId: null`), which
also lets the four CSV hook dep arrays drop the `apiKeyId` entry added in this
phase. The API-branch stamp (`persistPointer`) is untouched, the neuter proofs
are unaffected (both neuters target the API-branch helper clause and call
site), and the unit pin on the CSV decline still holds as a pure-helper
contract. **Fallback (prose only):** reword all five comments to "the CSV
wizard's key state, which is `null` unless the overlay was opened over a
preselect and toggled to CSV" — but then the gate still strips CSV burns on
that path, so the code gap stays open.

## Info

### IN-01: `apiKeyId` docblock overstates the bound rule and reuses a fingerprint constant for a key id

**File:** `src/lib/wizard/localStorage.ts:175-176`, `:494`
**Issue:** "Bounded at FINGERPRINT_MAX_LEN by the load-time validator, as every
other optional string on this payload is." `strategyName` is bounded at 80
(`:462`), not `FINGERPRINT_MAX_LEN` (64). Separately, `FINGERPRINT_MAX_LEN` is
documented as the `csvSubmissionFingerprint` output bound (`:66`); using it
for an `api_keys.id` couples two unrelated limits so a future fingerprint
resize silently moves the key bound.
**Fix:** `const API_KEY_ID_MAX_LEN = 64;` beside `FINGERPRINT_MAX_LEN` (a UUID
is 36), use it at `:494`, and reword the docblock: "Bounded (64) by the
load-time validator, like every other optional string on this payload."

### IN-02: the composite connect arm stamps `""`, outside the field's documented domain

**File:** `src/app/(dashboard)/strategies/new/wizard/WizardClient.tsx:952` via `steps/MultiKeyConnectStep.tsx:1755` (`apiKeyId: first.apiKeyId ?? ""`)
**Issue:** `handleConnectSuccess` is also `MultiKeyConnectStep`'s `onSuccess`
(`:1289`), whose success shape coalesces a null member key to `""`. The new
field is documented as "the `api_keys.id` … or `null` on the CSV branch";
`""` is neither, and the validator accepts it (string, length 0). Functionally
inert today: a composite draft has `api_key_id = null`, the overlay never
offers one under a preselect, so its incoming key is always `null` and `""` is
never compared. Recorded so the domain stays honest.
**Fix:** normalise at the single API-branch writer:
`apiKeyId: keyId || null` in `persistPointer`, with a one-line comment naming
the composite `?? ""` sentinel as the reason.

### IN-03: the load effect's "run once" comment no longer names everything it captures

**File:** `src/app/(dashboard)/strategies/new/wizard/WizardClient.tsx:480-482`
**Issue:** The `eslint-disable-next-line react-hooks/exhaustive-deps` is
justified by "`source` and `initialDraft` come from props/URL and are stable".
The effect now also captures `preselectKey` (`:452`). It IS stable — the
overlay's remount key includes `activePreselect?.id`
(`ContributionWizardOverlay.tsx:297`) and the manager route never passes one —
but the sentence that licenses the disable should say so, since a future
caller that changes `preselectKey` in place would silently compare against
the wrong key.
**Fix:** "`source`, `initialDraft` and `preselectKey` come from props/URL and
are stable for the lifetime of this instance (the overlay remounts on a
preselect change via its `key`)."

### IN-04: the residual incoming-`null` arm — recorded as the answer to focus 1, no action

**File:** `src/lib/wizard/localStorage.ts:554` (`if (incoming === null) return true;`)
**Issue:** By D-01 an incoming `null` restores unconditionally. The one
production path that yields `null` on the API branch with a stored key-A token
is the manager route when `page.tsx:108-110` offers no draft (the user's latest
draft is on the other branch, so the same-device payload would normally be
CSV and the SOURCE gate declines; cross-device only). The user then enters
credentials for key B carrying `S_A`. Traced: the credentials arm's
`(user_id, wizard_session_id)` fence returns draft A before validating the new
credentials — a silent resume onto key A, not a 23505, and pre-existing
behaviour this phase did not change. Not the dead end the phase closes; noted
so the next reader does not re-derive it.
**Fix:** none required for this phase. If it is ever closed, the honest fix is
in the credentials arm (validate the submitted key against the fenced draft's
`api_key_id`), not in this gate.
