# Phase 164.2.1: SESSIONID-FENCE — the stale wizardSessionId root cause - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the FUNCTIONAL dead end Phase 162 shipped honest copy about but did not remove: an
abandoned wizard draft over key A lends its `wizardSessionId` to a preselect for key B, the
submission takes 23505 on `strategies_user_wizard_session_source_uniq`, and re-pressing
Continue can never clear it because the stored id is stable.

The fix is TRIGGER REMOVAL, not a new guarantee — the partial unique index stays exactly as it
is and remains the guarantee. This phase removes the second trigger that reaches it.

⛔ OUT OF SCOPE: the `DRAFT_ALREADY_EXISTS` copy split (Phase 164.2 criterion 5, already
shipped there). This phase removes the dead end; 164.2 made the sentence describing it true.

</domain>

<decisions>
## Implementation Decisions

### Gate shape
- `deriveWizardResumeOverrides` takes a FOURTH positional parameter,
  `incomingApiKeyId: string | null` — the ROADMAP deliverable verbatim.
- NOT an options-object refactor. Criterion 5 requires the existing `localStorage.test.ts`
  pins to "still pass unmodified", and a signature change modifies all ~35 of them. An
  optional 4th parameter leaves every existing call site valid.
- The call site (`WizardClient.tsx`, the single post-mount `loadWizardState` effect) passes
  `initialDraft?.api_key_id ?? preselectKey?.id ?? null` — the SAME expression that already
  seeds the `apiKeyId` state, so the gate compares against exactly the key the submission
  will carry.

### Back-compat when the stored key is absent
- A payload with NO `apiKeyId` (every payload written before this ships) meeting a PRESENT
  incoming key ⇒ **DECLINE** the session-id restore. Absent key means we cannot prove the
  same key, and this phase exists because an unprovable case was assumed safe once already.
- Deliberately NOT mirroring the `source ?? "api"` back-compat idiom directly above it.
  That idiom defaults to the common case; here the defaulting population is precisely the
  set of drafts that currently carry the dead end.
- COST, accepted and stated: a draft saved before this ships loses its token once.
  `WizardClient` seeds `newWizardSessionId()` on mount, so the user keeps the draft and the
  resume banner — only the idempotency token is fresh, which is what a distinct submission
  should carry anyway (the file documents declining as safe).

### Write semantics for the new payload field
- `apiKeyId` is written EXPLICITLY at every `saveWizardState` call site from the existing
  `apiKeyId` state variable, which is already in scope at all 14 non-test sites (all in
  `WizardClient.tsx`).
- NOT the RT-3 `failedCsvSubmitSig` sticky carry-forward. `setApiKeyId(result.apiKeyId)`
  changes the key mid-wizard; a sticky field would hold the OLD key while the token moved
  on, inverting the comparison this phase adds.
- The field is OPTIONAL on `WizardLocalState` and the load-time validator must accept its
  absence (legacy payloads) and reject a non-string present value, matching how `source`
  and `strategyName` are validated.

### Test level
- BOTH a unit test and a component test.
- UNIT (`src/lib/wizard/localStorage.test.ts`): the gate logic on the pure helper.
- COMPONENT (`WizardClient` test): criterion 1 says verbatim "seeds localStorage with key
  A's payload, MOUNTS THE WIZARD with a key B preselect, and asserts the emitted session
  id". A helper-only test mounts nothing and cannot satisfy that sentence.
- Rationale beyond the wording: a correct helper the call site never passes the key to would
  still pass a unit-only suite. Testing the wiring, not just the helper, is the standing rule.

### Claude's Discretion
- Exact test file placement for the component test (new file vs. an existing
  `WizardClient.*.test.tsx`), naming, and fixture shape.
- Whether the same-key comparison lives inline in the gate or in a small named helper.

</decisions>

## Specific Ideas

- The file's own doctrine, applied literally (`localStorage.ts:524-530`): "THIS IS TRIGGER
  REMOVAL, NOT THE GUARANTEE … This line removes the one known trigger; if a second one is
  ever found, the DB still holds." This IS that second trigger. The fix removes it and leaves
  the index alone.
- Criterion 2 requires the fix be SHOWN to fail when neutered: remove the new pointer gate,
  observe RED, restore byte-identically (`shasum -a 256` before == after, never
  `git checkout --`, which destroys uncommitted work in a neuter/restore harness).
- ⛔ Criterion 1 carries its own warning: "INSPECTION IS NOT EVIDENCE — this exact item was
  declared 'already satisfied' once on a read, and the read was wrong."
