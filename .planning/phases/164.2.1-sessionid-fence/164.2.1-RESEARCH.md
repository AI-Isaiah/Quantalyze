### Locked Decisions

**Gate shape**
- `deriveWizardResumeOverrides` takes a FOURTH positional parameter, `incomingApiKeyId: string | null` — the ROADMAP deliverable verbatim.
- NOT an options-object refactor. Criterion 5 requires the existing `localStorage.test.ts` pins to "still pass unmodified", and a signature change modifies all ~35 of them. An optional 4th parameter leaves every existing call site valid.
- The call site (`WizardClient.tsx`, the single post-mount `loadWizardState` effect) passes `initialDraft?.api_key_id ?? preselectKey?.id ?? null` — the SAME expression that already seeds the `apiKeyId` state, so the gate compares against exactly the key the submission will carry.

**Back-compat when the stored key is absent**
- A payload with NO `apiKeyId` (every payload written before this ships) meeting a PRESENT incoming key ⇒ **DECLINE** the session-id restore. Absent key means we cannot prove the same key, and this phase exists because an unprovable case was assumed safe once already.
- Deliberately NOT mirroring the `source ?? "api"` back-compat idiom directly above it. That idiom defaults to the common case; here the defaulting population is precisely the set of drafts that currently carry the dead end.
- COST, accepted and stated: a draft saved before this ships loses its token once. `WizardClient` seeds `newWizardSessionId()` on mount, so the user keeps the draft and the resume banner — only the idempotency token is fresh, which is what a distinct submission should carry anyway (the file documents declining as safe).

**Write semantics for the new payload field**
- `apiKeyId` is written EXPLICITLY at every `saveWizardState` call site from the existing `apiKeyId` state variable, which is already in scope at all 14 non-test sites (all in `WizardClient.tsx`).
- NOT the RT-3 `failedCsvSubmitSig` sticky carry-forward. `setApiKeyId(result.apiKeyId)` changes the key mid-wizard; a sticky field would hold the OLD key while the token moved on, inverting the comparison this phase adds.
- The field is OPTIONAL on `WizardLocalState` and the load-time validator must accept its absence (legacy payloads) and reject a non-string present value, matching how `source` and `strategyName` are validated.

- BOTH a unit test and a component test.

- COMPONENT (`WizardClient` test): criterion 1 says verbatim "seeds localStorage with key A's payload, MOUNTS THE WIZARD with a key B preselect, and asserts the emitted session id". A helper-only test mounts nothing and cannot satisfy that sentence.
- Rationale beyond the wording: a correct helper the call site never passes the key to would still pass a unit-only suite. Testing the wiring, not just the helper, is the standing rule.

## Summary

The mechanism is confirmed exactly as the ROADMAP states: `deriveWizardResumeOverrides` (`localStorage.ts:493-497`, signature `(loaded, source, initialDraftId)`) restores `wizardSessionId` on the source gate alone (`:536`), while the API-branch step restore is pointer-gated (`:566`). The file has zero preselect awareness. The fix is small and the code is already shaped for it; the research value is in three hazards the locked decisions do not mention:

1. **A stale-closure hazard at the most important save site.** `handleConnectSuccess` calls `setApiKeyId(result.apiKeyId)` (`WizardClient.tsx:904`) and then `persistPointer("sync_preview", result.strategyId)` (`:922`) in the same tick. `persistPointer` is a `useCallback` closing over `[wizardSessionId]` (`:806`). Reading `apiKeyId` state inside it writes the PRE-connect key (null on the credentials arm) into the first API-branch payload — the one this phase exists to stamp. `persistPointer` must take the key as an argument.
2. **The CSV branch writes `null`, not a string.** `apiKeyId` state is `string | null` (`:285`). Nine of the 14 sites are CSV-branch; "write explicitly from state" means they write `apiKeyId: null`.
   ⚠️ **SUPERSEDED 2026-09-07 (code review WR-01, at execution):** the count "nine" is WRONG — MEASURED **13 of 14**.
   Exactly one site, `persistPointer`, is API-branch. The sentence is retained as the dated record of what this
   research pass believed; the two SOURCE comments that repeated it were corrected in commit `52161f70`. Nothing
   else in this item changes: the `failedCsvSubmitSig` validator shape was and remains the right call, and it is
   MORE load-bearing at 13 sites than at 9, not less.
 A validator that "rejects a non-string present value" as `source`/`strategyName` do (`:428-437`) would then reject EVERY CSV payload. The validator must follow the `failedCsvSubmitSig` shape (`:438-447`: absent OR null OK, else string) — this is a refinement of decision 3's last sentence, not a departure.
3. **The 4th param must default to `null` and `null` must mean "no key claim".** 25 existing three-arg calls in `localStorage.test.ts` and every CSV mount (no draft, no preselect ⇒ incoming `null`) require that a `null` incoming key leaves today's behaviour intact. Decision 2 is scoped to a PRESENT incoming key; this research recommends the gate fire only when `incomingApiKeyId !== null`.

**Primary recommendation:** add `incomingApiKeyId: string | null = null` as the 4th param; gate `out.wizardSessionId` on `(source matches) && (incomingApiKeyId === null || loaded.apiKeyId === incomingApiKeyId)` where a stored absent/null key with a present incoming key falls to DECLINE; give `persistPointer` a third `keyId` argument; write `apiKeyId` at all 14 sites; validate as `failedCsvSubmitSig` is validated; prove at unit level in `localStorage.test.ts` and at component level in a NEW file modelled on `ContributionWizardOverlay.preselect.test.tsx`, which is the only harness that mounts the REAL `WizardClient` + `MultiKeyConnectStep` + `ConnectKeyStep` with a preselect and captures the `wizard_session_id` actually POSTed.

## Q2. HMAC / serialization surface

`writeWizardState` (`:330-368`) builds `payload = { ...state, savedAt, failedCsvSubmitSig: burn }`, then `payloadJson = JSON.stringify(payload)` and signs **that whole string**: `envelope = { v: 2, p: payloadJson, h: HMAC(payloadJson, tabNonce) }` `[VERIFIED: localStorage.ts:342-356]`.

- **Adding a field does NOT invalidate previously-stored payloads.** `loadWizardState` (`:378-450`) verifies `h` against the stored `p` string as-is (`:404-409`) — the schema of `p` is irrelevant to verification. An old payload (no `apiKeyId`) verifies exactly as before, provided the same tab nonce is still in `sessionStorage` (survives reload, dies on tab close — `:21-29`).
- **After verification, the validator runs field-by-field** (`:411-447`): required `strategyId/wizardSessionId/step/savedAt` (`:411-420`), `step` in `WIZARD_STEP_KEYS` (`:425`), `source` absent or `"api"|"csv"` (`:430`), `strategyName` absent or string ≤ 80 (`:434-441`), `failedCsvSubmitSig` absent or null or string ≤ 64 (`:438-447`). An old payload has no `apiKeyId` → with a validator written as "absent ⇒ OK" it passes and reaches `deriveWizardResumeOverrides` with `loaded.apiKeyId === undefined`.
- **Therefore decision 2's "absent stored key" case IS reachable** — old payloads are not rejected wholesale. It is reached by: same tab, page reload after deploy, key-B preselect. `[VERIFIED]`
- **`JSON.stringify` drops `undefined` values** — a site that omits `apiKeyId` writes no key at all; there is NO sticky carry-forward for any field but `failedCsvSubmitSig` (`:336-340`), so decision 3's "explicit, not sticky" holds by default `[VERIFIED: :336-346]`.
- **`null` survives `JSON.stringify`.** The CSV sites will write `"apiKeyId":null`. The validator MUST accept `null` (see Summary hazard 2). Recommended validator, mirroring `:438-447`:
  ```ts
  // 164.2.1 — optional; absent (legacy) or null (CSV branch / no key) is OK, anything else must be a string.
  if (obj.apiKeyId !== undefined && obj.apiKeyId !== null && typeof obj.apiKeyId !== "string") {
    return null;
  }
  ```
  Type on `WizardLocalState`: `apiKeyId?: string | null;` (same shape as `failedCsvSubmitSig?: string | null`, `:154`). Length bound: a UUID is 36 chars; a bound of 64 mirrors `FINGERPRINT_MAX_LEN` and is cheap — optional, Claude's discretion.
