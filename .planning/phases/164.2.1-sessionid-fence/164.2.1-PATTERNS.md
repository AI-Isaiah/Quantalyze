### 1. `WizardLocalState.apiKeyId?` — optional payload field

**Analog:** `src/lib/wizard/localStorage.ts`, interface `WizardLocalState` (`:104-155`)

The two precedents, verbatim:

**`source?` (`:119-123`)** — declared with its back-compat meaning-when-absent stated in the docblock:
```typescript
  /**
   * Phase 15: discriminator for resume-banner branching. Absent ⇒ 'api'
   * (back-compat with v1 payloads written before the CSV branch shipped).
   */
  source?: "api" | "csv";
```

**`strategyName?` (`:124-130`)** — declared with the phase tag, WHERE it is present vs absent, and the bound the validator enforces:
```typescript
  /**
   * Phase 15 cross-AI revision 2026-04-30: user-typed strategy name on the
   * CSV branch — preserved across back-navigation and tab refresh. Absent
   * on the API branch (the API path uses a different name-source: the
   * metadata step). Bounded at 80 chars to match the UI input cap.
   */
  strategyName?: string;
```

There is also a third, heavier precedent — `failedCsvSubmitSig?: string | null` (`:131-154`) — whose docblock carries a `⚠️ DEFENSE IN DEPTH ONLY` paragraph naming the OPERATIVE fence elsewhere, a `STICKY:` paragraph, and the bound. CONTEXT.md explicitly rejects the sticky semantics for `apiKeyId`, so this is NOT the template for write semantics, but its "name the operative fence, say what this field is NOT" paragraph IS the template for the docblock's warning register.

**Which is the better template and why:** `strategyName?` is the better template for the DECLARATION. It is a plain optional string (same type as `apiKeyId`), it states which branch writes it and which does not (apiKeyId: written from the `apiKeyId` state on every save; meaningful on the API branch, `null` on the CSV branch), and it names the validator rule beside the field. `source?` is the better template for the ONE sentence about absence — "Absent ⇒ …" — but CONTEXT.md decision "Back-compat when the stored key is absent" inverts its meaning (absent ⇒ cannot prove same key ⇒ decline), so the docblock must state that inversion explicitly rather than borrow `source`'s "defaults to the common case" idiom. Pattern to copy: `strategyName`'s shape + a `failedCsvSubmitSig`-style "what this is NOT" paragraph pointing at the partial unique index as the guarantee.

**Ordering convention:** optional fields are appended at the END of the interface in phase order (`source` → `strategyName` → `failedCsvSubmitSig`). Append `apiKeyId?` after `failedCsvSubmitSig` (`:154`).

**`failedCsvSubmitSig` arm (`:445-457`)** — string-or-null + bound, with a five-line WHY comment. Note `!== undefined && !== null` because that field's contract admits `null`:

Conventions the new arm must match:
- Placement: after the `failedCsvSubmitSig` arm (`:457`), before `return parsed as WizardLocalState;` (`:458`). Arms are in field-declaration order.
- Access via `obj.<field>` where `const obj = parsed as Record<string, unknown>;` (`:423`); the cast `(obj.x as string)` only where a string method is needed.
- `return null;` is the ONLY rejection form — no `console.warn` on shape failures (warnings are reserved for the HMAC arms at `:392`, `:402`, `:408`).
- Whether `apiKeyId` admits `null` (the `apiKeyId` React state is `string | null`, `:285-286`) is a planner call — if it does, the `failedCsvSubmitSig` two-clause predicate is the exact shape; if the writer normalises to `undefined`, the `strategyName` shape is exact. - Bounds precedent: every optional string on this payload is length-bounded by the validator (`80`, `FINGERPRINT_MAX_LEN`), with the constant declared near the top (`FINGERPRINT_MAX_LEN` at `:58-66` with a docblock stating why that number).

**Storage doubles — required because the real `loadWizardState` HMAC-verifies against a sessionStorage nonce (`:187-224`).** The docblock explains the Node 25 shadowing reason; copy `installStorage()` verbatim:
```typescript
/**
 * Explicit storage doubles. Node 25 shadows jsdom's `window.localStorage` with
 * its own experimental implementation, which has no `clear()`; wiring these
 * also makes the reload boundary explicit — `localStore` and `sessionStore`
 * are the ONLY state that crosses the unmount, which is precisely what a
 * browser reload preserves.
 */
let localStore: Record<string, string>;
let sessionStore: Record<string, string>;

function installStorage() {
  const mk = (get: () => Record<string, string>, set: (v: Record<string, string>) => void) =>
    ({
      getItem: (k: string) => (k in get() ? get()[k] : null),
      setItem: (k: string, v: string) => {
        get()[k] = v;
      },
      removeItem: (k: string) => {
        delete get()[k];
      },
      clear: () => set({}),
      key: () => null,
      length: 0,
    }) as unknown as Storage;
  Object.defineProperty(window, "localStorage", { value: mk(() => localStore, (v) => (localStore = v)), configurable: true });
  Object.defineProperty(window, "sessionStorage", { value: mk(() => sessionStore, (v) => (sessionStore = v)), configurable: true });
}
```
