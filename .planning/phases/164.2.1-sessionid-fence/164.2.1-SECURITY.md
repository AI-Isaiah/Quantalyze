## Trust Boundaries

| Boundary | Description |
|---|---|

| `WizardClient` → `create-with-key` POST | the emitted `wizard_session_id` is a client-owned idempotency token; the partial unique index `strategies_user_wizard_session_source_uniq` is the guarantee, not this code. |

## Threat Register — disposition and EVIDENCE

| ID | Category | Severity | Disposition | Status | Evidence observed |
|---|---|---|---|---|---|
| T-164.2.1-01 | Tampering — forged `apiKeyId` to force a restore for another key | low | mitigate | **CLOSED** | The field rides INSIDE the signed payload: `writeWizardState` spreads `...state` into `payload`, `JSON.stringify`s it, and signs that exact string (`computeWizardHmac(payloadJson, nonce)`) before wrapping as `{v, p, h}`. A tampered `apiKeyId` fails HMAC like any other field. The validator additionally rejects a non-string present value (`localStorage.ts:526`), pinned by a forged-envelope unit test with an in-bound positive control. ⭐ Note the direction: the gate can only DECLINE more often, never grant more — a forged value cannot manufacture a restore that was not already permitted. |
| T-164.2.1-02 | DoS — attacker forces a decline to deny resume | low | **accept** | **CLOSED (accepted)** | A decline refreshes only the idempotency token. The draft, the resume banner and the server-side draft row are untouched — `WizardClient` seeds `newWizardSessionId()` on mount. An actor able to do this could simply clear localStorage, which is strictly stronger. |
| T-164.2.1-03 | Info disclosure — `apiKeyId` persisted in localStorage | low | **accept** | **CLOSED (accepted)** | `api_keys.id` is a UUID, not credential material, and the same value already appears in the server draft row the overlay reads and in the `reuse_api_key_id` POST body. Bounded on load so the field cannot carry a serialized payload. ⚠️ CORRECTION: the plan's text said `FINGERPRINT_MAX_LEN`; the shipped bound is its own constant `API_KEY_ID_MAX_LEN = 64` (`localStorage.ts:77`, applied `:526`), introduced by review finding IN-01 precisely because reusing the fingerprint bound overstated a shared rule. The mitigation holds; the plan's constant name did not. |
| T-164.2.1-04 | Repudiation — stale `persistPointer` closure stamps the wrong key | medium | mitigate | **CLOSED** | `persistPointer` takes an explicit third `keyId` argument and the connect call passes the RESOLVED key: `persistPointer("sync_preview", result.strategyId, result.apiKeyId)` (`WizardClient.tsx:998`) — not the closure's pre-connect `apiKeyId`. Proven by the WIRE test, whose responder returns an id deliberately distinct from the preselect id; reverting to the closure form was observed RED. ⚠️ This threat was REAL, not theoretical: on the reuse arm the stale value coincidentally equals the preselect id, so it is invisible in exactly the preselect scenario. |
