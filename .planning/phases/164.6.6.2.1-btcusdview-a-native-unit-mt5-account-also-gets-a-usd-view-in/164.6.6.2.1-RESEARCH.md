## Summary

164.6.6.2 (BTCNATIVE, merged as #969) already built almost all of the conversion machinery, for **returns**: `convert_native_returns_to_usd` / `UsdSeriesConverter` / `native_units_by_id` (`analytics-service/services/native_to_usd.py`), its TypeScript twin `convertNativeReturnsToUsd` (`src/lib/factsheet/native-to-usd.ts`), the DB-only price readers `get_btc_closes()` (`analytics-service/services/benchmark.py:326`) and `readBtcCloses` (`src/lib/factsheet/benchmark-source.ts:305`), and a shared oracle fixture. Those four places all skip a native key by name today. So this phase is: (a) one small pure levels/scalar converter beside the existing returns converter, (b) four writers switched from "skip" to "convert, or omit by name when unpriced", (c) the factsheet BTC/USD toggle, (d) a chip, (e) two correlation fixes, (f) one MTD fix.

Three findings change the ROADMAP's framing. **First**, `bridge_scoring.find_replacement_candidates` is already fixed at its only call site: `portfolio_bridge` converts the incumbent and every candidate to USD before the call (`analytics-service/routers/portfolio.py:2195-2201` and `:2305-2308`) and two tests pin it (`tests/test_portfolio_router_logic.py:791`, `:815`, both pass at HEAD). Only a regression pin is owed there. **Second**, there is a **third, unnamed correlation-only consumer** that still reads candidate series raw: the inline matching block in `verify_strategy` (`routers/portfolio.py:2680-2711`). **Third**, today's PROD price table is **one completed day behind** (newest stored BTC close is 2 days old at 14:00 UTC, so yesterday's close is missing), which is exactly the "missing day stays null" case D-02 describes and is caused by the unfixed 170.2 SC-2 refresh bug. **Primary recommendation:** add `convert_native_levels_to_usd` (+ a one-day scalar helper) to `native_to_usd.py` over `get_btc_closes()`, with the rule "value on day D needs the stored close for D, else absent"; make the daily derive the single writer of the USD balance, key-mode inputs, and (backfill) snapshot rows; ship the factsheet toggle as a **second server-built payload** (`usdView`) selected client-side, never as a client recompute and never overlaying the persisted BTC scalars; fix the two (three) correlators by converting candidates through the existing `UsdSeriesConverter`; sequence the `StrategyTable` change after 170.2.

### 2. The conversion: series, fixing time, per-day join, missing day -> null, 170.2 interaction

**Series.** `benchmark_prices` (`date` date NOT NULL, `symbol` text NOT NULL, `close_price` numeric NOT NULL, PK `(date, symbol)` - `supabase/schema/baseline.sql:11484-11489`, `:13263-13264`), `symbol = 'BTC'`. Use the **same stored rows the benchmark metrics use, through the already-existing DB-only readers** - `get_btc_closes()` (Python, pages the whole table, drops non-finite / non-positive closes) and `readBtcCloses(client)` (TS). Do **not** reuse `get_benchmark_returns(days=...)`: it returns *returns* over a trailing window and is the function 170.2 SC-5 will re-window.

**Fixing time.** One value per **UTC calendar day**, labelled by the day's date. Primary source `_fetch_from_binance`: symbol `"BTCUSDT"`, `"interval": "1d"`, `closes.append(float(candle[4]))  # Close price` with the label `pd.Timestamp(candle[0], unit="ms").date()` (`benchmark.py:64-87`) - i.e. the close at the end of UTC day D. MT5 NAV days are `deal_utc_day(time, MT5_SERVER_UTC_OFFSET_S)` (`job_worker.py:5728`), also UTC calendar days, so "NAV at end of day D x close of D" is a like-for-like end-of-day pairing and it is the same pairing `convert_native_returns_to_usd` already uses (`(1 + r_k) * (P(d_k) / P(d_{k-1})) - 1`). Today's row is never stored (`_completed_days_only`, `benchmark.py:154`).
- `[ASSUMED]` caveat A2: the fallback `_fetch_from_coingecko` (`"interval": "daily"`) stamps points at 00:00 UTC (CoinGecko docs: `"daily" (00:00 UTC)`; the price type is unspecified there), so a CoinGecko-sourced row labelled D is roughly the close of D-1. `benchmark_prices` has no source column, so mixed-source rows cannot be told apart. This pre-dates the phase and already affects every benchmark metric; 170.2 SC-2 ("stays within the free-tier window and merges with cached history") may add more fallback rows. The planner should record the caveat, not engineer around it.
- Quote currency is USDT, not USD (`BTCUSDT`); the benchmark metrics make the same USD ~= USDT assumption. `[ASSUMED]` A4.

**Per-day join (the one rule, both runtimes).** Build `closes = {UTC-midnight day -> float}` from only finite, positive closes (this is exactly `_usable_closes`, `native_to_usd.py:83`). For a **level or balance on day D**: USD = native x `closes[D]`; if `D not in closes` the day is **absent** (no row, `None`, "—"). For **returns**, reuse `convert_native_returns_to_usd` unchanged: day k needs every calendar day in `[d_{k-1}, d_k]` in `closes` (stricter than the level rule; 164.6.6.2 D-18, T-164.6.6.2-41). Never `ffill`, never `0`, never the nearest close. A level `ffill` of the *native* realized balance across quiet days is legitimate (the existing `_mt5_rows_from_levels` does it); a **price** `ffill` is not.

**Missing day stays null (D-02) - measured today.** PROD at 14:00 UTC: `btc_bench_days_behind_today_utc = 2`, `btc_bench_row_for_today = 0`, `btc_bench_calendar_gaps_in_range = 0`; the one PROD BTC strategy has 356 series points, 355 with a stored close, and the 1 without lies **after** the newest stored close. The refresh cron is `{ "path": "/api/cron/refresh-benchmark", "schedule": "10 0 * * *" }` (`vercel.json:15`); 170.2's evidence (2) records it failing when Binance fails (CoinGecko 401 at `days=1000`). Consequences the plan must carry: (i) between 00:00 and 00:10 UTC, and on any failed refresh, "yesterday's close" is absent; (ii) a live-balance USD figure priced at D-1 is `NULL` on PROD **right now**; (iii) the post-deploy acceptance reading (D-16 style) must be conditioned on a close existing, not on the code.

**Interaction with 170.2 SC-2 / SC-5** (170.2 and 170.7 are **unplanned**: their phase directories are empty at HEAD).

It does not change the table's shape or `get_btc_closes()`. It *improves* coverage (fewer null days) and may introduce CoinGecko-labelled rows (caveat above). No code dependency; a data dependency only.

- **File collision:** both live in `analytics-service/services/benchmark.py`. Put new helpers in `native_to_usd.py` (pure), not in `benchmark.py`, and import `get_btc_closes` only. If 170.2 renames `_benchmark_client` / `_CACHE_READ_ERRORS` (which `get_btc_closes` uses), the fix is theirs to carry; flag it in the 170.2 plan-check.

## Common Pitfalls

### Pitfall 1: Pricing "now" with a close that does not exist yet
**What goes wrong:** the live balance (read at time T on UTC day D) has no close for D, and on PROD today not even for D-1. **Why:** daily close is end-of-day; refresh runs 00:10 UTC and can fail. **How to avoid:** price at the close of the latest completed day **only if stored**, else NULL (D-02), and test the NULL path. **Warning signs:** a "latest close" helper with a `max(date)` fallback.

### Pitfall 2: Interior price holes silently shrink USD cumulative returns
**What goes wrong:** the converter drops the unpriced day *and the next one*; compounding what remains omits two days of P&L without any null being shown. **How to avoid:** the factsheet `usdView` is built only when the conversion left no interior hole (otherwise disabled with the count); a test with one missing interior close asserts no `usdView`.

### Pitfall 3: Persisted BTC scalars bleed into the USD payload
**What goes wrong:** `buildFactsheetPayload` overlays persisted cash scalars (`overlayBasisScalars`, `build-payload.ts:652`) from `singleKeyOpts.metricsByBasis`. **How to avoid:** build the USD payload without `singleKeyOpts`; assert `cagr` equals the hand-computed USD value, not `strategy_analytics.cagr`.

### Pitfall 4: A "comfortable" security pin quietly weakened
`queries.test.ts:403` exists to keep `data_quality_flags` off anon responses. Narrow it to the bare column only, and add the positive alias pin, in the same commit.

### Pitfall 5: Two writers of `account_balance_usdt`
The fenced RPC uses `COALESCE`; the derive writes directly. If both write a native value they can disagree for a day. One writer (the derive) for native keys.

### Pitfall 6: The compose already treats a hole as a flat day
A key day inside coverage with no return and no flow is carried at `r = 0` under a benign flag (`_MISSING_RETURN_INSIDE_COVERAGE`, `allocator_equity_compose.py`). Feeding it a USD series with holes would invent flat days inside the composite. Prefer omitting an unpriced key by name (Open Question 1).

### Pitfall 7: Shared TEST / migration hazards
If the key card path adds a GRANT (Open Question 5), PROD applies the migration with no human stop and the `API_KEY_USER_COLUMNS` allowlist must not select a column PROD lacks: migration PR first, code PR after (the 20260920120000 / 20260925120000 precedent), and no data-reading `DO` block.

### Pitfall 8: `process_key` becoming async-aware
`find_matched_strategy` becomes `async`; its sole caller is async, but `tests/test_process_key.py:1541` patches the symbol with a sync stub and the C8 harness calls it synchronously - both must change in the same commit.

### Pitfall 9: Worktree has no test environment
`node_modules` and `analytics-service/.venv` are absent here (the main checkout has them; its Python is 3.12.13 and runs this worktree's tests - verified).

## Code Examples

### Levels/scalar conversion (Python, pure; sits beside `convert_native_returns_to_usd`)
```python
# Source: derived from analytics-service/services/native_to_usd.py:83-141 conventions
def convert_native_levels_to_usd(
    levels: pd.Series, unit: str | None, btc_closes: pd.Series | None
) -> pd.Series:
    """USD level on day D = native level x stored close of D. A day with no usable
    close is ABSENT: never 0, never carried, never the nearest close."""
    if unit is None:
        return levels                      # a USD row: the SAME object
    if btc_closes is None:
        return pd.Series([], index=pd.DatetimeIndex([]), name=levels.name, dtype=float)
    closes = _usable_closes(btc_closes)
    out: dict[pd.Timestamp, float] = {}
    for ts, v in levels.items():
        day = pd.Timestamp(ts).normalize()
        v = float(v)
        if day in closes and math.isfinite(v):
            out[day] = v * closes[day]
    return pd.Series(out, name=levels.name, dtype=float).sort_index()
```
Hand oracle for the test: levels `{d1: 1.0, d2: 1.1}`, closes `{d1: 60000, d2: 66000}` -> `{d1: 60000.0, d2: 72600.0}`; the same pair through the returns converter gives `0.21` (`(1.1 x 66000)/(1.0 x 60000) - 1`), so levels and returns agree.

1. **How does an unpriced day behave in the composite allocator book?** (Highest-risk planning question.)
   - Known: a USD `key_inputs` anchor/flows/returns for a BTC key reuses the compose unchanged (`flow_drop` already handles an unpriced flow day: the anchor goes null). The converter drops the unpriced day and the next, and the compose carries a hole inside coverage at `r = 0` under a benign flag.
   - Unclear: whether a key whose series ends one day early (yesterday unpriced), or has one interior hole, should (a) be **omitted by name** (a new benign flag, mirroring `native_unit_key_omitted`), (b) end its series early with `realized_terminal` on its own last priced day, or (c) degrade the whole book. Today's omission flips the allocator total on/off with the cron's timing.
   - Recommendation: (a) for any interior hole or an unpriced terminal, with a distinct reason token (not `native_unit`, not in `_NO_CAPITAL_ANCHOR_REASONS`), plus copy in `departed-history.ts`; (b) for a tail-only gap if the spike (A6) shows the compose accepts it. Founder question only if the flapping is unacceptable (it is D-02-honest, but visible).

2. **Interior hole in the factsheet USD view: refuse or break the curve?**
   - Recommendation: refuse (`usdView` absent, USD segment disabled with the count), because a broken curve plus compounded-over-the-hole metrics would be a quiet understatement. Alternative: render the USD series with a visible coverage gap; it needs the 169.5 comparator-coverage machinery.

3. **Scope of the correlation fix:** the ROADMAP names two consumers; one is already fixed and a third exists (`verify_strategy` inline match, `routers/portfolio.py:2680-2711`). Recommendation: fix `find_matched_strategy` and the inline block together (same helper), pin the bridge as a regression, and correct the ROADMAP/CONTEXT wording.

4. **`getOwnCapitalStrategies`: convert or label?** Recommendation: convert to USD (matches the positioned half and the dashboard's USD rule, D-01); alternative is to carry `returns_unit` and render the MTD with the unit chip (then the table mixes BTC and USD MTDs in one column). Founder-confirmable; either way PROD has no exemplar.

5. **Where does `nativeAmount` get its first caller, and does it need a migration?** No public surface shows a native amount (D-21). The one natural place is the key card's balance line (`AllocatorExchangeManager.tsx:1346`, and the strategy-key card), e.g. "Balance 0.0123 BTC" beside the USD value. That needs `account_currency` and `account_balance_native` granted to `authenticated` (migration + `API_KEY_USER_COLUMNS_ARR` + `ApiKey` type + `api-key-runtime-guard.test.ts` + a two-PR deploy order). Alternatives: (i) `nativeAmount` in the Holdings table's quantity cell for the BTC row (needs the row's unit, not exposed), (ii) defer the formatter again (ROADMAP says it "inherits `nativeAmount` ... with its first caller"). Recommendation: the key card with the migration, as its own plan, last in the sequence; confirm with the founder because it exposes a live native balance to the owner (already true of the USD balance).

6. **Chip scope beyond `StrategyTable`:** `StrategyGrid`, `CompareTable`, `StrategyBreakdownTable`, recommendations, `browse/[slug]/[strategyId]`, `HoldingFactsheet`, admin match queue. Recommendation: `StrategyTable` + `CompareTable` (side-by-side return comparison is where unit mixing misleads most); list the rest in the plan as explicit non-goals.

7. **Live-balance pricing tolerance:** strict "close of D-1 or NULL" gives NULL on PROD today and a visible "—" for minutes each night.
