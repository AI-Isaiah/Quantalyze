## Critical Issues

### CR-01 (HIGH, confidence 8): an unpriced day leaves YESTERDAY'S priced BTC holding row in place as the latest, so holdings and AUM keep a stale-close value while the note says "left out of holdings"

**File:** `analytics-service/services/allocator_positions.py:1155-1172` (with `persist_allocator_holdings` at `:1593-1630`, the poll handler at `analytics-service/services/job_worker.py:10486`, and the read `fetchLatestHoldingsPerKey` in `src/lib/queries.ts` at the `getMyAllocationDashboard` projection)

**Issue:** When the latest completed UTC day has no stored close, `_fetch_mt5_account_rows` returns `([], MT5_NATIVE_UNPRICED_NOTE)`. Three facts in the code combine here:

- `persist_allocator_holdings` only upserts what it is given. On an empty list it returns 0 and deletes nothing.
- The dashboard reads each key's rows at that key's own latest `asof` (Phase 167.1.2 D-16).
- The scenario commit audit sums `value_usd` over the same latest rows (`src/app/api/allocator/scenario/commit/route.ts:829-859`).

This file already documents the exact hazard 40 lines above the new branch (Review [1] on WR-01): *"emitting nothing froze the last POSITIVE equity in place forever"*.

**Failure scenario:**
1. Oct 9: the poll prices 0.4213 BTC at the Oct 8 close and writes a row with `asof=2026-10-09` and `value_usd` of about $26,100.
2. Oct 10: the Oct 9 close is late (PROD is a day behind, as CONTEXT D-08 records). The poll returns `[]` and the note "No BTC close stored for Oct 9 yet; left out of holdings."
3. The Holdings tab, the AUM total and the commit audit all still read the `asof=2026-10-09` row, a value priced at the Oct 8 close.

The account is not left out. It is carried at a stale close, which is what D-02, D-08 and D-17 forbid. The user-visible note contradicts the number beside it. If the closes refresh stays broken, the stale row persists indefinitely.

**Fix:** Do the omission on the read side, keyed on stored facts rather than on the absence of a row. One option:

```python
# allocator_positions.py: write today's row anyway, quantity in its own unit, with NO price
if one_unit is None:
    ...
    return ([{**row_base, "quantity": equity_usd, "quantity_unit": unit.code,
              "mark_price": None, "value_usd": None}], note)   # needs value_usd/mark_price NULLable
```

If `value_usd` must stay NOT NULL, the alternative is a scoped delete in the poll handler, run only for this key and only when the unpriced note fires:

```python
# job_worker.py poll handler, before persist, ONLY for a native-unpriced warning:
supabase.table("allocator_holdings").delete() \
    .eq("allocator_id", allocator_id).eq("api_key_id", api_key_id) \
    .eq("venue", exchange_name).lt("asof", today_str).execute()
```

Either way, add a test that seeds a priced row for day N, runs an unpriced poll on day N+1, and asserts the dashboard read (`fetchLatestHoldingsPerKey` -> `derivePhase07Fields`) carries no `value_usd` for that key. The current tests only assert the fetcher's return value, so this defect cannot fail them.

### CR-02 (HIGH, confidence 9): in the USD view the Terms panel loses the trust tier ("Data source: —" for an API-verified strategy) and can falsely mark a live record as backtest

**File:** `src/app/factsheet/[id]/v2/FactsheetView.tsx:253-256` (`SelectedPayloadProvider`), `src/lib/factsheet/fetch-and-build-payload.ts:967`, consumer `src/app/factsheet/[id]/v2/MandatePanels.tsx:64-93` (`TermsPanel`), overlays at `src/app/factsheet/[id]/v2/page.tsx:752` and `src/app/(dashboard)/discovery/[slug]/[strategyId]/page.tsx:90`

**Issue:** The USD payload is built with `strategyArg.trustTier: null`. Both pages overlay the real tier onto the OUTER (native) payload only: `{ ...payload, trustTier }` does not reach `payload.usdView.payload`. D-19 keeps the masthead on the native payload, but `SelectedPayloadProvider` hands `usdView.payload` to `FactsheetProvider`, so every `usePayload()` consumer in the body reads the USD payload. `TermsPanel` is one of them:

- `const tier = payload.trustTier;` gives `null` in the USD view, so **Data source** renders `—` instead of `API-verified`. That is a provenance claim on the institutional document, and it changes when the viewer clicks a units toggle.
- `recordStart = payload.strategyMetrics.start` is the USD series start. The USD series always starts at least one native date later (day 0 is dropped), and later still with a leading hole (D-22). When `startDate` is set and the native series' second date is more than one day after its first (an MT5 weekend gap, or any leading price hole), `hasBacktestGap` becomes true. The panel then prints "observation window starts {usdStart}; portion before live date is backtest" about a record that is live. The native view of the same strategy says nothing.

**Failure scenario:** An API-verified BTC MT5 strategy with `start_date` equal to its first trading day (a Friday) has a native second date on Monday. A viewer toggles to USD. The Terms panel switches from "Data source: API-verified" to "Data source: —" and adds a backtest warning. No test covers this: `FactsheetView.usd-toggle.test.tsx` and `usd-view-withholdings.test.tsx` never render `TermsPanel` with a tier.

**Fix:** Two changes:
1. Make the identity facts view-independent at the source. Overlay the tier onto both payloads wherever it is overlaid today, with a helper so the two sites cannot diverge:
   ```ts
   const withTrust = (p: FactsheetPayload, tier: TrustTierKind | null): FactsheetPayload =>
     p.usdView ? { ...p, trustTier: tier, usdView: { ...p.usdView, payload: { ...p.usdView.payload, trustTier: tier } } }
               : { ...p, trustTier: tier };
   ```
2. In `TermsPanel`, take `trustTier`, `startDate` and the `hasBacktestGap` record start from `useUnitView()?.nativePayload ?? payload`, as `FactsheetHeader` already does. They are facts about the strategy, not about the unit (the panel's own SFH R2-1 comment makes the same argument for basis).

Add a toggle test that asserts the Terms "Data source" text and the absence of the backtest clause are identical in both views.

### WR-01 (MEDIUM, confidence 6): departed and stitch-source BTC keys skip `read_native_key_inputs`, so their interior price holes replay UNSPLIT and reproduce the M3 mis-scaled levels with no `key_inputs_mismatch`

**File:** `analytics-service/services/job_worker.py:12363-12405` (the departed branch and the stitch-source branch each `continue` before the native block at `:12430-12484`), compose `analytics-service/services/allocator_equity_compose.py` (the I2 split loop reads only `unpriced_days_by_key`)

**Issue:** Only a counted, eligible key reaches `read_native_key_inputs`. A BTC key that departs, or that is a stitch source of a shared account (several logins on one account are intended, per project memory), keeps its `unpriced_days` and `segment_terminals` in `key_inputs` but never hands them to the compose. Its returns still have interior holes, because the writer converted them identically. The compose finds no entry in `unpriced_days_in`, does not split the key, and does not raise `KEY_INPUTS_MISMATCH`. The rollback then applies the post-hole return to the pre-hole level. That is MEASUREMENT M3's STALE-CARRY defect (+2833 / +2691 / +2940 on levels of about 60k), which this phase built the I2 mechanism to remove.

**Failure scenario:** A BTC key had a 2-day close outage in July and was disconnected in September (an included departed history). Every pre-July level of its departed history is mis-scaled, the curve is shown as `ready`, and no flag fires.

**Fix:** Read the native fields for a departed key in the departed branch, and for a stitch source in the source branch, through the same helper. Populate `unpriced_days_by_key` / `segment_terminals_by_key` for them, or fail closed with `KEY_INPUTS_MISMATCH` when a departed native key carries `unpriced_days`:

```python
_departed_native = read_native_key_inputs(departed_payload)  # same try/except as the counted path
if _departed_native is not None and _departed_native.unpriced_days:
    unpriced_days_by_key[api_key_id] = _departed_native.unpriced_days
    segment_terminals_by_key[api_key_id] = dict(_departed_native.segment_terminals)
```

Add a compose-job test with a departed BTC key that has one interior hole. It should assert the pre-hole levels equal the writer's `segment_terminals`. This test is RED today.

### WR-02 (MEDIUM, confidence 6): a malformed native `key_inputs` row drops the key from the total with NO dashboard note, because the payload names it with `day: null`, which the reader discards

**File:** `analytics-service/services/job_worker.py:12436-12447`, `analytics-service/services/allocator_equity_compose.py:904-907`, `src/lib/queries.ts:3837-3860` (`readUnpricedNativeAccounts`, the `typeof day !== "string"` drop at `:3856`)

**Issue:** The compose records `interior_hole_days[k]` for every unpriced day between a key's first and last priced event, over the key's whole series. Every compose then lists that key with `day: None`, for as long as the hole stays in the series. The TS reader throws away `hole_days` and `reason`, so both cases render the same text: "The total leaves out BTC desk on the days it cannot be priced in USD."

- **Interior hole:** a two-day closes outage in July puts this note on the dashboard indefinitely. The note sits above a headline total that does include the account today. Before this fix the flag was raised, but no entry was listed and no note shown. The note is new behaviour, and nothing ever clears it.
- **Malformed native row (`day_unknown`):** the account is out of every day, including today. The sentence understates that as "on the days it cannot be priced". Round-1 WR-02's fix asked for "cannot be priced in USD right now".

Two different facts get one sentence, and for each case the sentence is wrong in a different direction. D-20 needs the note to explain a drop, and it explains neither drop accurately.

**Failure scenario:** A BTC MT5 key had a 2-day stored-close gap on 2026-07-14 and 2026-07-15. Its current anchor is priced. From this head onward, every ready dashboard render carries "The total leaves out BTC desk on the days it cannot be priced in USD." The headline total is the full book.

**Fix:** Carry the distinction through the reader and render it:

```ts
// queries.ts readUnpricedNativeAccounts: keep the kind of omission
type UnpricedAccount = { apiKeyId: string; label: string; day: string | null;
  kind: "dated" | "whole" | "history" };   // reason === "day_unknown" -> "whole"; hole_days only -> "history"
```

- `"whole"`: "...is left out of the total: it cannot be priced in USD right now."
- `"history"`: name the account against the curve, not the total, for example "The equity history leaves out BTC desk on N days with no stored BTC close". You could also bound it to holes inside the displayed window, or omit it once the hole is outside the window.

Add a `queries.test.ts` case for each kind, asserting the distinct sentence.
