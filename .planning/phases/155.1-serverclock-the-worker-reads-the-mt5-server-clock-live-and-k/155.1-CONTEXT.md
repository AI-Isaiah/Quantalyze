# Phase 155.1: SERVERCLOCK — the worker reads the MT5 server clock live and keeps every reading - Context

**Gathered:** 2026-11-13
**Status:** Decisions locked. Planning waits on the live gateway spike (see `<spike>`).

<domain>
## Phase Boundary

Inside every leased MT5 derive (`derive_broker_dailies` in `analytics-service/services/job_worker.py`),
the worker takes one live server-clock reading through one narrow, tick-time-only `Mt5Client` method,
asserts it against the configured `Mt5ServerClock` rule (Phase 175's `MT5_SERVER_TIME_RULE` stays the
carrier), and persists the reading write-once. A mismatch refuses that key's persist and raises an
`ops_alert`. Each reading carries a hashed server label, so the readings show per key whether MM2,
MM3 and FX-AI_V share one server. Requirement: MT5-06.

Out of scope: a per-server clock (a Future requirement; it is brought forward only if the readings
show a split, and then as its own phase), any harness gateway call (Phase 155 never touches the
gateway), any publishing or advertising change, and writing the reading back as configuration.

</domain>

<decisions>
## Implementation Decisions

### Binding milestone decisions (REQUIREMENTS.md, cited by id)
- D-A..D-E are binding. D-D: one named, tick-time-only `Mt5Client` method is admitted; the
  forbidden list in `test_read_only_surface_no_trade_methods` stays, including `symbol_info_tick`,
  and the exception is pinned by a test after the `terminal_info` precedent (153.3 / D-31).

### Founder decisions, 2026-11-13 (locked; asked through the coordinator via AskUserQuestion)
- **D-01 Clock mismatch: "Refuse + alert".** When a reading disagrees with the configured rule,
  that key's persist is refused with a named error and an `ops_alert` is raised, so a mis-bucketed
  day is never written. This follows the Phase 175 fail-loud precedent (175 / D-04).
- **D-02 Shared server: "Not sure, measure it".** Each reading records the account's server as a
  hashed label only, never the name. If the servers differ, a per-server clock comes before parity;
  check the parked MT5SERVERLEARN branch (`feat/164.6.6.3.6-mt5serverlearn`) when that happens.
- **D-03 Publishing: "No change".** No surface, copy or badge changes in this phase; the MT5
  advertising ban stands until 155.2 passes.

### The tick-time method (Claude's recommendation, accepted under the autonomous default)
- D-04 One public method, named for what it returns, never `symbol_info_tick` (that attribute stays
  forbidden). Working name `server_tick_times`. It returns tick TIMES only (`time_msc` per symbol, or
  the newest one); bid, ask, last and volume are never materialised or returned.
- D-05 Symbol set per research conflict C3: STACK's set, the visible Market Watch symbols (they
  reproduce MQL5 `TimeCurrent`), not the account's own deal symbols, and never `symbol_select`
  (that changes terminal state). Whether the visible set is enumerable inside the same one method
  is a spike question (see `<spike>`); if it is not, the planner re-decides from the spike result.
- D-06 Placement per C3: ARCH's, inside the leased derive, after login and the account check and
  before the first persist, on the same session. Never a second process against the gateway.
- D-07 It goes through the existing read discipline (`_assert_live`, `_guarded_read`, `_timed`,
  `_materialize`, `_raise_last` on `None`), exactly like `terminal_info` and `account_info`.
  `test_public_surface_is_exactly_the_contract` gains the name with a dated comment.

### The reading and its assertion
- D-08 Measured offset = newest tick wall time minus the worker's UTC now, rounded to 900 s (C3).
  The rounding residual and the newest tick's age are recorded with the reading.
- D-09 Expected offset = the configured clock's offset at that wall instant
  (`Mt5ServerClock.instant_offset_s`). In a repeated or skipped broker hour, where that is `None`,
  the reading is recorded as unassertable and is not a mismatch.
- D-10 Three verdicts: `match`, `mismatch`, `unmeasured`. `unmeasured` covers no fresh tick (a
  closed market, a session break, the weekend) and a residual past the refusal bound. An
  `unmeasured` reading is persisted with its reason and does NOT refuse the persist: refusing on a
  closed market would fail every weekend derive. Only `mismatch` refuses (D-01). The freshness and
  residual bounds come from the spike, never picked to make a run green.
- D-11 Mismatch error: a named error (working name `Mt5ServerClockMismatchError`). The derive fails
  before any `nav_marks` / dailies persist for that key, with an `ops_alert`, and the message carries
  the rule id and the two offsets only. Error kind follows 175 / D-04: `transient`, so retries are
  bounded and a corrected rule heals on the next derive.
- D-12 The reading is never written back as configuration (Anti-Pattern 3); `MT5_SERVER_TIME_RULE`
  stays the only carrier.

### Persistence (migration)
- D-13 One new table, working name `public.mt5_server_clock_readings`, created by a pure-DDL
  migration: table, constraints, indexes, RLS enabled, grants, and a write-once guard. No data-reading
  `DO` block (it auto-applies to TEST, whose tables are empty, then to PROD with no human gate).
- D-14 Write-once: INSERT only. UPDATE and DELETE are refused (revoked grants plus a refusing
  trigger), so a reading cannot be edited after the fact.
- D-15 RLS on with no policy for `anon` or `authenticated`: the worker writes with the service role,
  and nothing user-facing reads it in this phase (D-03). migration-reviewer and rls-policy-auditor
  must both be clean before the PR.
- D-16 Columns (planner may refine): key id, job id, read-at UTC, measured offset s, expected offset
  s (nullable), configured rule id, verdict, reason (nullable), residual s, newest tick age s,
  symbols counted, server label hash. The key FK does not delete readings when a key is
  disconnected (keep data; disconnect, never delete).
- D-17 The server label is a hash of `account_info().server`, computed in the worker. The name never
  reaches a log, an error message, tracked text or the table.

### Criterion 5 (near-midnight deal)
- D-18 One real near-midnight deal from the divergence week 2026-10-25..11-01 is preselected by a
  PROD read through the Supabase MCP (marker query first). The test pins its broker wall time and
  expected UTC day as a literal, with no ids, logins, amounts or server names, and goes RED under the
  wrong rule (`eu` against `us`). The last leg, the terminal-displayed time, is read by the founder
  in the 155.2 session, so this phase's verification reads `human_needed` for that leg by design.

### Claude's Discretion
- Exact method, error, table and column names; module placement of the assertion (a pure function
  beside `Mt5ServerClock` is preferred, so it stays network-free and testable).

The agent may not touch the PROD gateway. Founder-supervised run, before 157 rotates
`MT5_SPIKE_INVESTOR_PASSWORD`, outside the derive window and away from the session-monitor tick
(the lease is in-process only; a second login can fail the nightly with `Mt5AccountMismatchError`).

the points below, so the spike needs a small new tick leg.

1. Does `symbol_info_tick(symbol)` answer through mt5linux on Wine under an investor login, for a
   visible Market Watch symbol, and for a symbol not in Market Watch without `symbol_select`?
2. Can the visible set be enumerated read-only (`symbols_get` / `symbols_total` / `symbol_info().visible`)?
3. Is the tick's `time` / `time_msc` in the deal `time` encoding (broker wall clock as if UTC)?
   Expected now: newest tick minus UTC now is about +7200 s, within seconds.
4. What an investor session's Market Watch holds (count only; no names in tracked text).
5. Newest-tick age in market hours, in a daily session break, and at the weekend. This sets the
   freshness bound and confirms the 900 s rounding. The weekend case can ride the founder's D-E
   sitting (2026-11-14/15); the market-hours case needs a weekday.

<specifics>
## Specific Ideas

- Measured 2026-11-13 from `mt5_server_clock.py`: `eu` and `us` use the same offsets (+2 h standard,
  +3 h daylight) and differ only in transition dates. Both autumn moves are past, so a live reading
  returns +2 h under either rule until 2027-03-08. The readings therefore cannot show a RULE split
  before the 155.2 session; the server-label hash (D-17) is what shows a SERVER split (criterion 4),
  and criterion 5's divergence-week deal is what tests the rule. The continuous reading earns its keep
  at the 2027-03 transitions.
- Account labels only (MM2, MM3, FX-AI_V) in tracked text.

</specifics>
