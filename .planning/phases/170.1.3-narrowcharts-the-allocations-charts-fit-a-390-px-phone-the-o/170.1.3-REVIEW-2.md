### The three questions you asked

- **Will the fixture hold on Linux CI?** Almost certainly not. See HI-01. The date anchors are
  fine, the Monte Carlo is seeded (`mulberry32`, `MC_SEED_DEFAULT`), and both lanes use the same
  benchmark data. The problem is fonts. The spec comment says "attributes do not [depend on
  fonts]". That is false for every Recharts `interval="preserveStartEnd"` axis in the fixture.
- **Does `padLeft` change desktop for normal data?** No. A label of 7 characters or fewer needs
  42 + 6 = 48, which rounds to 48 and stays under `PAD.left = 50`. Only charts with a label of 8
  or more characters change, and those labels were the ones being clipped. The committed reading
  shows just one such chart, the Overview Rolling Sortino, which moves from 50 to 56. D-04 tests
  svg width and the tick set, and neither moves. A LOW, not raised: `yDomain` re-fits to the
  visible `xRange`, so panning across an 8-character threshold (for example "+900.0%" to
  "+1000.0%") moves the plot 6 units mid-drag.
- **Does the `anchorMs` seed change affect other specs?** No. The default is still `Date.now()`.
  The only other callers (`layout-narrow.spec.ts:367`, `:1367`, `target-size.spec.ts:255`) do not
  pass it, so their book does not change. The holdings row still uses today's date, and
  `equityHistoryReadiness` does not read dates, so the Overview still mounts with a past-anchored
  curve.

Unit tests for the changed files pass (51/51) and `tsc --noEmit` is clean.

## Critical Issues

### HI-01: The committed desktop fixture encodes macOS font metrics, so the V1280 reading cases will very likely be red on every Linux `e2e-seeded` run [neither — CI gate integrity]

**File:** `e2e/layout-narrow.spec.ts` (the `C-5 desktop unchanged` describe comment,
`compareDesktopReading`, `V1280 ${surface}: desktop reading`),
`e2e/fixtures/narrowcharts-desktop-1280.json` (composer readings #18 to #20)

**Issue:** The spec says it compares `<text>` attributes rather than rendered boxes because
"boxes depend on the machine's fonts, attributes do not". That holds for TimeSeriesChart, whose
attributes come from arithmetic. It does not hold for the Recharts axes.

- **How Recharts picks the visible ticks.** With `interval="preserveStartEnd"`, Recharts chooses
  both which ticks to show and where the tail sits (`tickCoord`). It does this with
  `getStringSize`. That function sets `{fontSize, letterSpacing}` on a `<span>` appended to
  `<body>` and reads `getBoundingClientRect().width`. The span inherits the body font, DM Sans,
  so the width depends on how the host rasterises that font.
- **What we measured on macOS.** The probe loaded the DM Sans latin woff2 in local Playwright
  Chromium 1.64.1. The scratchpad has `mac-w.json` and `probe-js/sim.cjs`, which is the
  `getTicksStart` loop transcribed. With those widths, the simulation reproduces the committed
  rolling-chart reading exactly: all 19 labels, and every x from `01-18@65` to `09-19@766.72`.
  It also gives the tail `tickCoord` 843.07, which `EdgeFitXTick` clamps to 840 as committed.
  So the model is right.
- **How sensitive the pick is.** The smallest decisive margin in that walk is **0.097 px**, and
  the next ones are 0.177, 0.198 and 0.200 px. If any label measures about 0.2 px wider or
  narrower, one pick moves by a day. Every later label then changes text and moves 2.88 px,
  well past `DESKTOP_SLOP_PX = 0.5`.
- **What Linux probably does.** Linux headless Chromium at device scale factor 1 does not use
  subpixel positioning by default, so glyph advances are hinted to whole pixels. macOS reports
  fractional advances (for example `01-31` = 29.2500, `02-05` = 36.7969). A difference of 0.2 px
  or more on at least one of about 275 candidate labels is expected. If it happens, readings
  #18 to #20 of the composer reading differ in strings and x on every run.

The fixture was generated on macOS only, and no CI run exists for `7d4146a50`. The GitHub API
returns 0 workflow runs for that SHA. The repo already knows this class of problem: the SVG
goldens are baked on the Linux runner through the `bake_svg_goldens` dispatch for exactly this
reason.

*Not measured:* the Linux widths themselves. Pulling `mcr.microsoft.com/playwright:v1.64.1-noble`
and `node:22-bookworm` failed repeatedly with TLS and short-read errors. So "red on Linux" is a
strong inference, not an observation. One `e2e-seeded` run on the branch will settle it.

**Fix (root cause, which also closes MD-02):** stop letting Recharts measure the rolling-chart
labels in DOM text. Compute the tick list in arithmetic and pass it to the three rolling charts
as `ticks={...}` with `interval={0}`. Use `estLabelWidth(label, 12)`, which gives the true Geist
Mono width of 36 for "MM-DD", plus a fixed gap, keeping the first and last ticks. That is the
same approach as the EquityChart's `thinXTicks` (C-2). The tick set and positions then no longer
depend on any font, so the macOS fixture holds on Linux.

If you do not take that fix, then either:
- generate the fixture on the ubuntu runner (a dispatch that uploads it as an artifact, like
  `bake_svg_goldens`) and record one green `e2e-seeded` run at the head SHA before merging; or
- leave out of the x/y comparison any text that Recharts placed by measurement, and keep only
  the strings and arithmetic positions.

## Warnings

### MD-02: Rolling-chart x labels still overlap on about 30 % of data windows; the new overlap gate checks one window that happens to be clean (WR-01 / M3 narrowed, not closed) [user-facing]

**File:** `src/components/charts/EdgeFitXTick.tsx:79-80`; `src/components/charts/RollingMetrics.tsx:147-153`,
`RollingVolatilityChart.tsx:32-38`, `RollingSortinoChart.tsx:32-38`; gate at
`e2e/layout-narrow.spec.ts` (`${vp.id} composer: rolling x labels do not overlap`, 260 days, V390/V640)

**Issue:** Recharts sizes each label in DM Sans: "MM-DD" at 12 px measures 29.25 to 37.47 px,
per the probe above. `EdgeFitXTick` then draws it in Geist Mono, which is exactly 36.00 px
(also measured). Recharts spaces labels at measured width plus a 5 px `minTickGap`. Wherever the
DM Sans width is under 31 px, two adjacent mono labels can overlap.

The same transcribed walk was run with the measured widths over 341 series lengths (60 to 400
daily points) at chart widths 340, 590 and 858:

| width | windows with any overlapping x labels | worst | tail pair, with the clamp | tail pair, centred (no clamp) |
|---|---|---|---|---|
| 340 | 93 / 341 | 5.32 px | 7 / 341, 3.80 px | 4 / 341, 0.73 px |
| 590 | 112 / 341 | 5.41 px | 19 / 341, 3.78 px | 4 / 341, 0.71 px |
| 858 | 104 / 341 | 5.82 px | 14 / 341, 5.82 px | 2 / 341, 2.75 px |

- **Interior overlaps.** These come from the font mismatch and predate this phase. The old
  `tick={CHART_TICK_STYLE}` drew the same mono font over the same DM Sans measurement.
- **Tail overlaps.** The clamp adds them. It pulls the end label left by its real overflow, about
  3 to 8 px depending on the DM Sans width, into space Recharts reserved for a narrower label.
  That is far better than the old `end` flip (round 0 estimated about half of all windows at up
  to 18 px), but it is not zero.

The phase goal is that the charts fit at 390 px with legible labels, and `D-03b` names the
rolling charts. A 4 to 6 px collision between two date labels is visible to a user. The new gate
cannot catch it in general. It seeds one 260-day window, which the fixer chose because it was red
under the old flip. Most windows are clean, so a gate on one window passes by luck of the window,
not by rule.

The chart widths 340 and 590 are approximations of the V390 and V640 rolling-chart widths. The
model reproduces the committed 1280 reading exactly (see HI-01).

**Fix:** use the same root-cause fix as HI-01. Pass deterministic `ticks` thinned with the width
the label is actually drawn at (`estLabelWidth(label, 12)` = 36) plus a gap, and `interval={0}`.
Then no pair can overlap by construction, at any width or OS, and the clamp only has to keep the
end label inside the svg. Keep the e2e overlap case, and add a unit test that sweeps series
lengths through the tick-thinning function (pure, no DOM) and asserts no overlap. A single
e2e window cannot fail representatively. A sweep can.
