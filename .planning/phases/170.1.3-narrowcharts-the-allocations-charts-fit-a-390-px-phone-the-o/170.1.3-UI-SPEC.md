# Phase 170.1.3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This is a **geometry-only** phase. It adds no colour, no font, no copy and no component. It
changes only (a) how wide the Overview equity chart's `<svg>` is below 400 px, (b) how many
x-axis ticks that chart draws below 400 px, and (c) where an edge tick label is anchored when its
box would cross its own `<svg>`. Everything else is DESIGN.md as it stands.

Sources: decisions D-01..D-04, D-03a and D-03b are quoted from `170.1.3-CONTEXT.md` (founder, "Accept all",
2026-10-21). Code facts were read at the head of `feat/170.1.3-narrowcharts` on 2026-10-21 and are
cited by symbol, not by line.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| EquityChart x tick label (DM Sans) | 12px | 400 | single-line SVG text, n/a |

| Factsheet v2 tick / reference labels in the composer (Geist Mono) | their existing viewBox literals, desktop and mobile arms unchanged (e.g. `MasterBrush` `yearTickFont` 9 / 15, `DistributionPanels` `refLabelFont` 9 / 16, `TimeSeriesChart` ticks 10) | 400 | n/a |

Two weights only (400, 600), both existing. Labels are never shrunk, truncated or hidden to fit
(D-02: "Labels are not hidden"). Thinning the EquityChart x ticks below 400 px (D-01) removes
whole ticks, never shortens a label.

**Label-width estimate (used by the rules below; deterministic, SSR-safe, no `getBBox`):**
`estWidth(label, fontSize) = label.length × fontSize × 0.6`. Geist Mono's advance is 0.6 em, so
this is exact for the mono labels and an over-estimate for DM Sans x labels, which only makes the
rule anchor inward slightly earlier. Never measure with the DOM to decide a rendered label
position: server and browser must emit the same markup (React #418, the Phase 169.1.1 HYDRATIONTICKS
lesson that `src/lib/chart-ticks.ts` exists for).

## Layout and Interaction Contract (the substance of this phase)

### C-1 Overview equity chart width (D-01)

File: `src/app/(dashboard)/allocations/widgets/performance/EquityChart.tsx`, the ResizeObserver
effect that today calls `setWidth(Math.max(400, Math.floor(cr.width)))`.

- The `<svg width>` equals `Math.floor(contentRect.width)` of the chart's wrapper at **every**
  width. The `Math.max(400, …)` floor is removed. No new floor is introduced (the narrowest
  supported viewport is 390 px; a card that narrow still yields `chartW = width - 72 > 0`, and
  the existing `Math.max(1, …)` guard on `chartW` stays).
- The initial `useState(960)` and the jsdom fallback stay, so the server render and the first
  client render are identical; the narrow width arrives only through the ResizeObserver, after
  hydration. No hydration-mismatch surface is added.
- Hover / tap index math (`handleMove`, `useTapPin` `padL`) already reads the same `width`, so it
  follows automatically. It must not keep a private 400 assumption anywhere; the plan greps for
  `400` in the file and accounts for every hit.
- Result: at 390 x 844 the SVG's bounding box sits inside its card's content box (measured
  2026-10-20: card clips at 334 px; target SVG width is therefore at most 334 px).

### C-2 Fewer x ticks when narrow (D-01, Claude's discretion: the count rule)

Applies **only when `width < 400`**. At `width >= 400` the tick list is byte-identical to today,
which is what makes D-04 true by construction (every width at or above 400 was already rendered
exactly this way, because the floor forced it).

- `chartW = width - pad.l - pad.r` (existing). `maxTicks = max(2, floor(chartW / 64))`.
  Worked values: width 334 -> chartW 262 -> 4 ticks; width 319 -> chartW 247 -> 3 ticks.
- If the tick list built by the existing two branches (month ticks when `n > 90`, else the
  `target = 7` "MMM D" walk) has more than `maxTicks` entries, keep every `k`-th entry with
  `k = ceil(ticks.length / maxTicks)`, **counted back from the newest tick**, so the most recent
  date always keeps its label (the "MMM D" branch already walks from `n - 1`; the month branch is
  thinned from its end the same way).
- The 64 px pitch is the widest DM Sans 12 px label in use ("Oct 20", estWidth 43.2 px) plus
  the 8 px clear gap on each side, rounded to the 4 px ladder. The pitch is a
  target, not a proof: edge anchoring (C-3) moves the first and last boxes inward, and partial-month
  ticks are unevenly spaced, so the gate is C-6's browser measurement of no overlapping x labels.
- Implement as a pure function (input: tick list, `width`, `pad`; output: tick list) so a unit
  test can drive it without a DOM. It does not touch y ticks, `niceStepValues` or anything else in
  `src/lib/chart-ticks.ts`; y-tick values stay engine-independent exactly as Phase 169.1.1 left them.

### C-3 Edge tick labels drawn whole (D-02, Claude's discretion: reuse a helper)

No existing label-fit helper was found (`grep -rln -E "anchorFor|labelAnchor|fitLabel|clampLabel|edgeAnchor" src`
returned nothing on 2026-10-21). Add **one** pure helper next to the tick helpers,
`src/lib/chart-ticks.ts`, and call it from every emitter listed in C-4:

```
fitTickLabel(x, label, fontSize, minX, maxX, anchor = "middle")
  -> { x, textAnchor }
```

- With the label's box computed from `estWidth` for the given `anchor`:
  - box left edge < `minX` -> `textAnchor: "start"`, `x` unchanged (label starts at its tick).
  - box right edge > `maxX` -> `textAnchor: "end"`, `x` unchanged (label ends at its tick).
  - otherwise the caller's anchor and `x`, unchanged.
- `minX = 0`, `maxX` = the SVG's own coordinate width (`width` for EquityChart, `VB_W` for the
  viewBox charts). Units are the SVG's user units, so the rule is identical whether the SVG is
  pixel-sized (EquityChart) or viewBox-scaled (factsheet v2).
- This is the "inward" anchoring D-02 asks for: the first label left-aligns and the last label
  right-aligns **when, and only when, centred they would cross the SVG edge**. A label that
  already fits keeps its centred position, which is what keeps desktop rendering unchanged (C-5).
- Right-axis labels on EquityChart (`textAnchor="start"` at `width - pad.r + 4`): `pad.r` stays
  64 whenever every y label satisfies `width - pad.r + 4 + estWidth(label, 12) <= width`; when one
  does not, `pad.r = ceil(max estWidth) + 8`, rounded up to a multiple of 4. At 12 px mono, 60 px
  of label room holds 8 characters (57.6 px; labels at or above 10% print with no decimal, so even
  "+12345%" is 7), so 64 is expected
  to hold at every width; the rule exists so a long label grows the gutter instead of clipping.
- Never hide, truncate, rotate or shrink a label to make it fit.

### C-4 Scope (D-03)

In scope, by the evidence named in D-03:

| Chart | Emitter | Evidence | Rule |
|-------|---------|----------|------|
| /allocations Overview equity chart | `EquityChart.tsx` x labels, y labels | SVG 400 px wide in a 334 px card; "0%" to "-3.5%", "Oct" hidden | C-1, C-2, C-3 |
| Composer timeline brush | `src/app/factsheet/[id]/v2/MasterBrush.tsx` year ticks (`yearTicks`, first year tick sits at `PAD.left` = 6) | "2025" reads "025" at 390 px | C-3 |
| Composer distribution panel | `src/app/factsheet/[id]/v2/DistributionPanels.tsx` "P5 …" / "P95 …" reference labels | "P95 +0.1%" cut | C-3 |
| Composer rolling charts (D-03b) | Recharts XAxis end-date ticks (`tickFormatter={(d) => d.slice(5)}`, `interval="preserveStartEnd"`) in the shared `src/components/charts/RollingMetrics.tsx`, `RollingVolatilityChart.tsx`, `RollingSortinoChart.tsx`, mounted by the composer directly and by strategy pages | "10-20" / "10-19" cut | C-3, through one custom XAxis `tick` renderer whose width comes from Recharts' layout state (`useChartWidth()`), never a DOM read |

Correction (2026-10-21, plan-check revision 1, status stays approved): this row first named
`src/app/factsheet/[id]/v2/TimeSeriesChart.tsx` as the "10-20" / "10-19" emitter. That was wrong:
its `makeXTicks` emits only years, `Q3 25`-style quarters or month names. The founder then decided
D-03b (fix the shared rolling charts once). `TimeSeriesChart` stays a D-03a shared component and
is fixed only if the closing measurement finds one of its own labels cut.

**Closing the list by measurement, not by this table.** The plan's first measurement task loads
the composer and the Overview at 390 x 844 and 640 x 800 and lists every `svg text` whose
`getBoundingClientRect()` extends beyond its own `<svg>`'s rect by more than 0.5 px. That list is
the closed set of emitters this phase fixes. A cut label found in a composer chart not named above
(for example `src/app/(dashboard)/allocations/components/MonteCarloBandChart.tsx`, which renders
with `overflow-visible`) is in scope only if that sweep finds it cut; record it either way. For an svg whose
computed overflow is `visible`, "cut" is measured against the padding box of its nearest
overflow-clipping ancestor (or the viewport), so such a label is gated, not merely recorded.

**Shared-component consequence, surfaced and not averaged (Rule 7).** `MasterBrush`,
`DistributionPanels` and `TimeSeriesChart` are the `/factsheet/[id]/v2` components; the composer
mounts them through `ScenarioFactsheetChart` -> `FactsheetBody`. Fixing their labels therefore
also fixes the same labels on the factsheet v2 page, which D-03 lists as deferred ("Charts on
other pages are deferred"). This contract fixes the shared emitter once and does **not** add a
composer-only prop to fork the behaviour: a fork would leave a known-cut label on the factsheet on
purpose and add a code path for a single caller. The effect on the factsheet page is the same
geometry rule and is only visible where a label was already cut. The founder decided this on
2026-10-21 ("Fix shared once (Recommended)", CONTEXT D-03a). The same reasoning and the same
founder answer cover the shared Recharts rolling charts, which strategy pages also mount (CONTEXT
D-03b); other charts in `src/components/charts/` stay deferred unless the closing measurement finds
them cut on the Overview or the composer.

Out of scope: every other SVG chart on any other page (D-03 deferred); items (1), (3) and (4) of
TODOS `[170.1-SC5-SCENARIO-NARROW-DEFECTS]`.

### C-5 Desktop unchanged, proven by measurement (D-04)

- At 1280 x 800, before and after the change, record for the Overview equity chart and for every
  composer chart in the C-4 closed set: the `<svg>` width (`getBoundingClientRect().width`) and the
  ordered list of tick label strings. Both must be identical before and after.
- EquityChart: the tick set is identical by construction above 400 px (C-2 gate); the measurement
  proves it. C-3 runs at every width, so the permitted anchor difference below applies here too.
- EquityChart and viewbox charts: the tick **set** is untouched by C-3. The only permitted desktop difference is
  `text-anchor` on a label whose estimated box already crossed its SVG at 1280 (that is, a label
  that was already cut on desktop, such as a first-year brush tick at `x = 6`). The measurement
  lists every such label by text; any other anchor change at 1280 is a regression.
- The before reading is taken on the branch base before the first code commit and kept in the
  phase directory as the measurement artifact the verifier compares against.

### C-6 Viewports

| Viewport | Why | Must hold |
|----------|-----|-----------|
| 390 x 844 | Narrowest supported (Phase 170 LAYOUT, 2026-09-27) | C-1 SVG inside card; C-2 no overlapping x labels; C-3 every `svg text` inside its `<svg>` |
| 640 x 800 | Desktop at 200% zoom | Same as 390 (EquityChart is >= 400 here, so C-2 is inactive; C-3 still applies) |
| 1280 x 800 | Desktop reference | C-5 before/after equality |

375 px was in the 2026-10-20 evidence but is below the supported floor; it is not a pass/fail
viewport. The rules have no 390-specific constant, so 375 is expected to pass as a side effect.
