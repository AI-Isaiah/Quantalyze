## Warnings

### WR-01: EdgeFitXTick's end flip runs past the gap Recharts reserved, so the end-date label can overlap the label before it, desktop included [user-facing]

**File:** `src/components/charts/EdgeFitXTick.tsx:76` (renders for `RollingMetrics.tsx`, `RollingVolatilityChart.tsx`, `RollingSortinoChart.tsx`)

**Issue:** The rolling charts use `interval="preserveStartEnd"`. In Recharts 3.10.1
(`es6/cartesian/getTicks.js`, `getTicksStart` with `preserveEnd`), Recharts measures the tail
label as a CENTRED box. It shifts the tail's `tickCoord` inward so that the box fits, then
hides every earlier label whose box reaches past `tail.tickCoord - (tailSize/2 + minTickGap)`.
`CartesianAxis` passes `x = tickCoord`, the already-shifted value and not the data coordinate.

`EdgeFitXTick` then switches that label to `text-anchor="end"` at the same `x`. This moves the
label's left edge from `x - w/2` to `x - w`, a further `w/2` (18 px for "10-19" at 12 px
Geist Mono) into space Recharts did not reserve. The penultimate visible label is placed by a
forward walk over hundreds of daily candidates, so its position relative to that boundary is
effectively arbitrary.

Using the measured overflow (3.13 px, which implies a Recharts size of about 29.7 px against a
true 36 px), the two labels overlap whenever the penultimate label's centre lies within about
19 px of the reservation boundary. That is roughly half of all data windows. The flip fires at
every width: MEASUREMENT records `"10-19" middle -> end` at 1280 on all three rolling charts. So
this is a desktop change as well as a mobile one.

Two further points:
- Because `x` is the shifted `tickCoord`, the end-anchored label ends about 15 px left of the
  last data point. The docblock says "the tick position `x` never moves". That is true of the
  number but not of the data point the label belongs to.
- No gate catches the overlap. `e2e/layout-narrow.spec.ts` checks overlap only for the equity
  chart at V390. The rolling-chart cases check clipping only. In jsdom every tick is kept, so
  `EdgeFitXTick.test.tsx` accepts several adjacent `end` labels.

**Fix:** Keep Recharts' anchor and clamp the centred box into the svg. The label then moves only
by its real overflow (about 3 px), which stays inside the gap Recharts reserved. Add an x-label
overlap assertion for the three rolling charts to the NARROWCHARTS describe at V390 and V1280.
```tsx
let drawX = x;
if (chartWidth !== undefined && typeof tickX === "number" && Number.isFinite(tickX) && typeof size === "number" && Number.isFinite(size)) {
  const half = estLabelWidth(label, size) / 2;
  drawX = Math.max(half, Math.min(tickX, chartWidth - half));
}
return <Text {...rest} x={drawX} fontSize={fontSize} textAnchor={textAnchor}>{label}</Text>;
```

### WR-02: `fitEndLabelX` moves a long y label onto the plot; the gutter never grows [user-facing]

**File:** `src/lib/chart-ticks.ts:157-167`, used at `src/app/factsheet/[id]/v2/TimeSeriesChart.tsx:892`

**Issue:** `fitEndLabelX` returns `x = w` when `x - w < 0`. The label then ends at `w`, whatever
the plot boundary is. In TimeSeriesChart, `PAD.left = 50`, labels end at `PAD.left - 6 = 44`,
and the font is 10, so each character is 6 viewBox units wide:
- An 8-character label ends at 48. It sits 2 units from the plot instead of 6. This is the
  measured "+1000.00" Sortino case.
- A 9-character label ends at 54, which is 4 units inside the plot. It overlaps the gridline
  start and the data. This affects every chart, desktop included, because the viewBox is fixed.

Real data reaches this. The Overview fixture's Sortino already prints "+3000.00", so a ratio of
10,000 or more prints "+10000.00". A Sortino with near-zero downside deviation can do that. The
growth format's log ticks print `+14900.0%` at 150x.

The docblock says the label "never flips onto the plot", but the label can still cross onto the
plot without flipping. UI-SPEC C-3's rule for a right-axis gutter is "a long label grows the
gutter instead of clipping", and that rule was not applied here. Nothing checks the plot edge:
`edge-tick-labels.test.tsx` pins only the 8-character case, and the e2e gate checks the svg
edge, not the plot edge.

**Fix:** Grow the left gutter from the widest tick label, as `ReturnQuantiles` and `rightAxisPad`
already do, and keep `x = padLeft - 6`. Because `PAD` is module-level, make `padLeft` a value
derived from `yTicks` and thread it through `X`, the gridlines and the Y-pull hit test. A
smaller interim fix is to cap the shift so the label ends at or before `PAD.left - 1`. That
cap would also make the remaining clip visible rather than silent.

### WR-03: The SC-3 "desktop unchanged" comparison never runs in CI and ignores label position [neither]

**File:** `e2e/layout-narrow.spec.ts` (`compareDesktopReading`, and the `V1280 ${surface}: desktop reading` cases)

**Issue:** `compareDesktopReading` runs only when `NARROWCHARTS_DESKTOP_BEFORE` is set. Nothing
in `.github/workflows/ci.yml` sets it. In CI the desktop-reading cases therefore assert only
that some svg text exists, which cannot fail on a desktop regression.

Even when the comparison runs, it compares svg count, width, ordered strings and `text-anchor`,
but not the `x`/`y` of a text. Three kinds of desktop change pass it unseen:
- a moved label (`fitEndLabelX`; MEASUREMENT itself notes the 44 -> 48 move "which the
  comparator does not report")
- a label whose baseline moved (`fitBaselineY`)
- a grown gutter (`rightAxisPad`, the ReturnQuantiles `padLeft`)

SC-3 / D-04 rests on a one-off local reading (`170.1.3-DESKTOP-BEFORE.json` /
`-AFTER.json`). After merge, no repeatable gate guards it.

**Fix:** Either commit the BEFORE reading as a fixture and point the CI case at it, or drop the
env opt-in and compare against a committed path by default. Also record each text's rect
(already read as `t.rect`) relative to its svg, and compare `x`/`y` within 0.5 px. Report a
change only for texts the BEFORE reading marked as overflowing, as the anchor rule already does.
