<objective>
DBACC-02 step 3 (PR-3 in CONTEXT's delivery): the insert fence. A BEFORE INSERT trigger on `api_keys` refuses any insert whose `current_user` is not `postgres` or `supabase_admin`. Only the audited postgres-owned writer functions, migrations and SQL fixtures can then insert. With plan 05's `user_id` immutability trigger, that is the two-part backstop the founder chose.

**Ships in PR-C, after PR-B is merged AND deployed.** PR-B moved the route, every seed and every live test to `insert_api_key`. A fence applied before the route's RPC call is live would refuse every connect-a-key on PROD, because the migration applies on the merge push in parallel with the Vercel build.

Decisions implemented (CONTEXT cited by heading and date; no D-NN ids):
- CONTEXT `### DBACC-02` ⭐ FOUNDER DECISION 2026-11-26, candidate 1, part (ii): "A BEFORE INSERT check refuses any insert made outside a sanctioned SECDEF writer function". Reversibility: one-way, settled there, so no checkpoint is added.
- Same section, ⛔ MECHANISM CORRECTED 2026-11-26: the fence is a `current_user` check, NOT a transaction-local GUC (migration `20260515114310` removed the GUC shape as forgeable). "A catalogue arm pins the exact set of functions whose body inserts into `api_keys`, so a new SECDEF inserter cannot appear silently."
- Same section, ⭐ Polarity (phase agent, 2026-11-27): an ALLOW-list, deny by default. An insert passes only when `current_user IN ('postgres', 'supabase_admin')`.
- Same section, the last constraint bullet: the trigger function is hardened per migration-reviewer (pinned `search_path`, REVOKE from PUBLIC/anon/authenticated). The deletion-path sanitize exemption does not apply: this is an INSERT-only trigger, and `sanitize_user` deletes.
- RESEARCH pitfall 6: a BEFORE INSERT trigger fires on `INSERT ... ON CONFLICT` before conflict resolution. That is why PR-B removed every upsert of `api_keys`.

**Correction to RESEARCH's gate census, re-derived at plan time.** Two existing gates insert into `api_keys` as a client role and would go RED on the local-stack `sql-tests` corpus once the fence replays:
- `test_api_keys_insert_not_client_writable.sql` arm 2: a direct `service_role` INSERT, which the brief names.
- `test_api_keys_exchange_not_user_writable.sql` arm 5c's "scrub half": a temporary `GRANT INSERT ... TO authenticated` followed by an authenticated INSERT, so the scrub trigger's non-privileged branch stays covered. The brief does not name it.

Both are handled here. Every other client-role `api_keys` INSERT in `supabase/tests` is refused at the privilege check before any trigger fires, so its asserted message does not change.
