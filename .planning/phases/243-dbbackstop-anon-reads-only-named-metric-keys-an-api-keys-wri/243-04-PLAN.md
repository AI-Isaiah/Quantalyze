<objective>
DBACC-01 half (a), OG side: move the share-card route, the only anon-reachable reader of `metrics_json_by_basis` (RESEARCH census), off any anon reference to that column. Then plan 09's anon column revoke cannot take the card down.

**Ships in PR-A.** This is the reader plan 09's revoke waits on. Plan 09's precondition requires PR-A to be merged AND deployed: a migration applies to PROD on the merge push in parallel with the Vercel build, with no ordering between them (the O-1 rule of `20261022120000_strategies_anon_api_key_id_revoke.sql`).

Decisions implemented (CONTEXT cited by heading and date; no D-NN ids):
- CONTEXT `### DBACC-01: anon metric reads` (2026-11-26): "If any anon reader needs it, that reader moves to the named aliases first, or (b) narrows to the keys it needs." CONTEXT `### DBACC-02` (Delivery, accepted by main 2026-11-26): "DBACC-01's anon column revoke ships only after its single anon reader, the OG route, has moved to the named aliases."
- The planning brief: the 21-alias projection goes in the payload builder AND the OG route, one path (plan 03's module).

⚠ CORRECTION TO RESEARCH, surfaced and not averaged. RESEARCH (C2 and `### Census of anon-client reads`) and PATTERNS assumed that moving the OG route to named `->` aliases makes it safe under plan 09's revoke. It does not. A PostgreSQL column privilege covers every reference to the column, including `metrics_json_by_basis->'cash_settlement'->'sharpe'`, so after the revoke an anon session read of even one alias answers 42501. "(b) narrows to the keys it needs" is not available either: a column grant cannot narrow to JSON keys.
So the reader moves to the named aliases read through a role that holds the grant. The session read drops the column entirely. A second read through the admin client, scoped to the id the published-only session read already returned and itself wrapped in `withPublishedOnly`, selects exactly `BY_BASIS_ALIASES`.
This is the CONTEXT rule implemented as written ("moves to the named aliases first"), with the mechanism corrected. It is reversible TypeScript, and it is the same trust pattern `resolveFactsheetInputs` already uses (admin client behind an explicit visibility predicate). The consequence for the SC-1 wording: after plan 09, an anonymous REST request reads NONE of the column directly. The anonymous visitor's card and factsheet read exactly the 21 named keys, server-side.

Purpose: unblock DBACC-01 half (b) without degrading the card.
Output: the OG route on the fragment, and its seven test files updated.
