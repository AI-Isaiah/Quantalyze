<objective>
DBACC-02 step 1 (additive): create the audited writer `public.insert_api_key`, which mirrors the `validate-and-encrypt` route's insert, and make `api_keys.user_id` immutable for every role. Neither depends on any caller changing.

**Ships in PR-A.** The migration is additive. Nothing in PR-A calls the RPC, and nothing legitimate updates `user_id`, so it is safe in either order against the Vercel deploy that fires on the same merge. PR-B (plans 06 to 08) moves every caller to the RPC. Its plans' preconditions require this migration in the PROD ledger, because a deploy that calls a function the database lacks answers PGRST202.

Decisions implemented (CONTEXT cited by heading and date; no D-NN ids):
- CONTEXT `### DBACC-02` ⭐ FOUNDER DECISION 2026-11-26 (candidate 1), part (i): "A BEFORE UPDATE trigger makes `api_keys.user_id` immutable for every role, BYPASSRLS included." Part (ii) prerequisite: "The `validate-and-encrypt` insert moves into an RPC, and the e2e and seed inserts move to the same RPC." Reversibility recorded there: one-way, settled by the founder, so no `checkpoint:decision` is added.
- Same section, Delivery (accepted by main 2026-11-26): "PR-1: the new writer RPC plus the `user_id` immutability trigger."
- Same section: "the trigger function is SECDEF-hardened per migration-reviewer (pinned `search_path`, REVOKE from PUBLIC/anon/authenticated)", and "any deletion-path guard exempts `quantalyze.sanitize_in_progress='on'`". Neither new object fires on DELETE, and `sanitize_user` only DELETEs `api_keys`, so no exemption is needed. The local-stack run of `test_cleanup_orphaned_api_keys_sweep.sql` (its CLEAN-02 Part 3 sanitize arm) is the proof that sanitize completes with the trigger present.
- `### Claude's Discretion`: names. The RPC is `insert_api_key`, the trigger is `api_keys_user_id_immutable`, and the trigger function is `enforce_api_keys_user_id_immutable`.

Decisions taken here, with reasons (RESEARCH Open Question 2 and the immutability shape):
- **`p_id uuid DEFAULT NULL`** (row id = `COALESCE(p_id, gen_random_uuid())`). `scripts/seed-full-app-demo.ts` and the three `scenario-commit-*` live tests key later rows on a caller-chosen key id, and an UPDATE cannot give a row its id after the fact. The signature is frozen once PR-A applies (one-overload rule), so it is decided now. The route never passes it. A colliding id is a PK 23505, never an overwrite.
- **Optional trailing ciphertext parameters** (`p_api_secret_encrypted` through `p_venue_server` default NULL, `p_kek_version` NULL meaning 1), so seed callers pass only the NOT NULL columns, exactly as their direct inserts do today.
- **The immutability trigger has NO column list** (`BEFORE UPDATE ... WHEN (OLD.user_id IS DISTINCT FROM NEW.user_id)`, not `BEFORE UPDATE OF user_id`). A column list is checked against the statement's SET list only, so an earlier BEFORE trigger rewriting `NEW.user_id` would slip past it. Without the list, and named so it sorts after every existing `api_keys` BEFORE UPDATE trigger, it judges the final row. The `WHEN` clause keeps same-value assignments (upserts) passing (RESEARCH pitfall 5). The function raises unconditionally, so removing the `WHEN` fails closed.

Purpose: SC-2, the UPDATE half in full, and the writer the INSERT half (plan 10) admits.
Output: one migration, its rollback file, two gates, two generated function dumps, raised floors.
