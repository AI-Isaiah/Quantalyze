composite whose `csv_daily_returns` read fails transiently is cached as a null payload on the public
factsheet for up to the `unstable_cache` TTL, because `readCompositeFactsheet` turns that error into an
empty series and the resolve stage then answers `composite_unbuildable`, a fact about the row, which the
cached callback stores. The single-key path already throws out of the cache on `read_error`
(`FactsheetReadError`, 167.2.1 WR-02); the composite path cannot, because the error is gone by the time
the resolve stage sees the series.

while discovery, recommendations and /strategies show it as live, which is the cross-page disagreement
SC4 forbids. The fix is at the one source: the reader keeps the error, the resolve stage names it
`read_error`, and 167.2.1's existing throw does the rest.

page's catch; four red-first test seams (reader, resolve-stage parity, public page, discovery page), each
with a neuter; the three stale comments corrected.
