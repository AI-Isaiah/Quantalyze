<objective>
Make the holdings writer ready for D-10 before the index changes, so the migration can apply to PROD with
no window in which polls fail.

D-10, quoted from CONTEXT (founder 2026-10-11): "D-08 holds end to end, ingestion included.
`allocator_holdings`' unique index on `(allocator_id, venue, symbol, asof)` and the
`persist_allocator_holdings` upsert on that key ... keep ONE row when two live keys on one venue hold one
symbol on the same day. The index and the upsert's conflict target gain `api_key_id`, so every key keeps
its own row."

Purpose (why this is its own plan and ships in the FIRST pull request): a migration merged to `main`
auto-applies to PROD (`supabase-migrate.yml`, no human gate since 2026-09-23), while the analytics service
redeploys on Railway only after main's CI is green. If the index changed first, the running worker's
`on_conflict="allocator_id,venue,symbol,asof"` would match no unique index and every holdings poll would
fail with 42P10 until the new worker deployed. Shipping this tolerant writer first (PR 1, plans 01-08),
verifying it on Railway, and only then merging the migration (PR 2, plan 09) removes that window.
Output: the writer change and its test.
</objective>
