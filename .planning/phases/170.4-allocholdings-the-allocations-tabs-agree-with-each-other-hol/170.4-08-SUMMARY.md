# Phase 170.4 Plan 08: Holdings writer with the 42P10 fallback Summary

`persist_allocator_holdings` now upserts on `allocator_id,venue,symbol,asof,api_key_id` and retries once on `allocator_id,venue,symbol,asof` only when Postgres refuses with SQLSTATE 42P10, so the deployed worker keeps writing on either side of migration 170.4-09.

## What changed

- `analytics-service/services/allocator_positions.py`: constants `HOLDINGS_CONFLICT_TARGET` and `HOLDINGS_CONFLICT_TARGET_PRE_D10`; the upsert catches `postgrest.exceptions.APIError`, reads only `.code`, and on 42P10 logs once at INFO (naming the fallback target) and retries once with the same rows. Everything else, including a 42P10 on the retry, propagates unchanged. `APIError` import follows the `account_identity.py` idiom. Docblock records D-10 and that the fallback is deploy-window only (removal booked by the PR 2 release plan).
- New `tests/test_persist_holdings_conflict_target.py` (8 tests): constants, per-key first attempt + row stamping, 42P10 retry (same rows, one INFO log), 23505 / 42501 / non-APIError propagate after exactly one call, 42P10-on-fallback propagates with no third call, empty holdings returns 0 with no call.
- `test_allocator_positions.py` and `test_allocator_positions_non_ccxt.py`: their old-target assertions now use `HOLDINGS_CONFLICT_TARGET` (their mocks never raise 42P10), intent comments kept.
