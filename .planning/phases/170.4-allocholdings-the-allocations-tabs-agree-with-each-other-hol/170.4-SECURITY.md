**2. The commit AUM never reads owner-writable `audit_log`.**
- `route.ts:843-848` calls the reader with `{ auditEvidence: false }`. In the reader, both `audit_log` selects are replaced by a resolved no-op (`latest-holdings-per-key.ts:326-337`, `:340-350`), and `partialReads` stays empty.
- The route file names no `audit_log` table read (`grep` finds only comments and the audit emit).
- Forged-audit pin: `route.test.ts` "CR-01: a user-forged audit event cannot change the audit AUM, and the audit log is never read for it". Compared with the base commit (`73c8693c5`), the test body is byte-identical except that the fixture row gains an `updated_at` (the new NOT NULL contract); the forged event, the `toBeCloseTo(33_049.7675, 6)` assertion and `expect(tablesRead).not.toContain("audit_log")` are unchanged. The test passes.

**3. Trust basis of the markers and the identity columns.**
- `allocator_equity_derived`: RLS enabled and FORCED; exactly two policies, `owner_select` (SELECT, `allocator_id = auth.uid()`) and `service_all` (`auth.role() = 'service_role'`) (migration 20260717233529 lines 93-118). No later migration adds a policy to it. An authenticated INSERT or UPDATE has no matching policy, so RLS refuses it whatever the table grants say. The marker is service-written; the owner cannot forge it.
- `api_keys` UPDATE: `REVOKE UPDATE ON public.api_keys FROM anon, authenticated` with no re-grant (migration 20260810120000 line 104). INSERT: `REVOKE INSERT ... FROM anon, authenticated` (migration 20260823120000 line 156). Re-grant sweep over every migration: the only later `GRANT ... ON api_keys` statements are column-level SELECT grants (`venue_account_id`, `account_share_kind`, `account_shared_with_api_key_id`, `history_inclusion`, native balance columns). No UPDATE or INSERT grant exists. So `venue_account_id`, `account_share_kind` and `account_shared_with_api_key_id` are service-written; the owner reads them and cannot set them. Caveat: the revocations are table-level, so a `SECURITY DEFINER` RPC that updates these columns would still be the only writer path; the sweep found none exposing them to the caller in this phase's diff.

**4. The writer's 42P10-only fallback.** Closed (T-19 row). The `except` catches `APIError` only; any other exception class is not caught at all.

**5. No other allocator's rows on any surface.** Every read in the diff is owner-filtered (Checks 1); the RPC path is unchanged; the payload only reaches the page via `getMyAllocationDashboard(user.id)` with `user.id` from `supabase.auth.getUser()` (`page.tsx`), and `getMyAllocationDashboard` has no other caller. The commit route's `supabase` is the user-scoped client (`route.ts:536`).

**6. `HoldingsReadTruncated` and `HoldingsUpdatedAtError` leak nothing.**
- `HoldingsReadTruncated` (`match.py:576`, raised at `:642` and `:669`): the only request path is `POST /recompute`, whose `except Exception` returns a fixed `SCORING_FAILED` body with a correlation id and logs the text server-side (`match.py:2011-2037`). `test_s15_truncated_holdings_read_is_a_logged_500_with_a_correlation_id` asserts the body carries none of the exception text. The cron loop only logs and counts (`:2709-2713`).
- TS cap errors (`"... reached the row cap"`) carry no data and are `assertOk`'d into a thrown error; production RSC masks the message and `error.tsx` shows the digest only.
- `HoldingsUpdatedAtError` (message embeds the offending `updated_at` string, the owner's own column value): in the commit route it is caught into `holdingsLookupErr`, which reaches `console.warn` and Sentry only (`route.ts:895-906`); `holdingsLookupErr.message` appears nowhere else in the file. In the dashboard it throws to `error.tsx` (digest only).
