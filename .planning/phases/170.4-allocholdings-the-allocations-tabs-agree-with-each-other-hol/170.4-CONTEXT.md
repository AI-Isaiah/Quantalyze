## Phase Boundary

The `/allocations` tabs agree with each other about what the allocator holds now and about whether
history is rebuilding. Seen on PROD on 2026-10-03:

- The Exposure panel showed 3 Deribit positions (185.1K gross), while Holdings read "No holdings to

<decisions>
## Implementation Decisions

### One source for "what I hold now"
- **D-01:** Exposure's current snapshot (ExposureByClass and anything else that shows "now") reads
  the same per-key latest holdings as Holdings and Open Positions: `fetchLatestHoldingsPerKey`
  (src/lib/latest-holdings-per-key.ts), with its supersession rules. Those rules drop a key at a
  newer `native_unpriced` marker, at a newer clean `allocator.holdings.sync_completed` poll, or when
  a newer key on the same exchange account read later. The three surfaces then agree by
  construction. Exposure does not get its own copy of these rules (the alternative was rejected).
- **D-02:** for a book with no spot rows but open derivatives, the Holdings tab no longer reads
  "No holdings to display". It says there are no spot holdings and points to the N open positions
  shown below. A truly empty book keeps an honest empty state.
- **D-03:** the over-time charts (NetExposureChart, AllocationOverTime) are unchanged. They are
  history. Only the current snapshot moves to the per-key source.

### Empty, rebuilding and "connect a key" states
- **D-04:** while equity history is not ready, Overview shows the same `EquityHistoryRebuilding`
  panel, with the same reason, that Risk shows. The rebuilding state takes precedence over
  Overview's empty-holdings card (`AllocationDashboardV2.tsx`'s `holdingsSummary.length === 0`
  early return).
- **D-05:** Scenario says "connect a key" only when the allocator has no eligible key. With
  eligible keys and an empty book, it says the connected accounts hold no open positions yet.
- **D-06:** the Diversification Optimizer says "connect a key" only when no key is eligible. With
  eligible keys but no portfolio or portfolio analytics, it names that reason instead. No portfolio
  is created automatically.
- **D-07:** one shared server-side "has an eligible key" predicate feeds every tab. It is the
  existing `hasConnectedKeys = apiKeys.some(isPerKeyDailiesEligibleKey)` (src/lib/queries.ts),
  carried in the payload, so no tab derives "has a key" from holdings or from `portfolios`.

### Founder decisions after planning (2026-10-11)
- **D-08 ("One Key is One Strategy", founder 2026-10-11):** holdings from different API keys are
  never merged. The `holdingsSummary` collapse in `src/lib/queries.ts` (one row per
  `holdingScopeKey` = venue:symbol:type, keeping the latest `asof`) drops all but one key's row
  when two live keys on the same venue hold the same symbol. That makes Holdings understate today,
  and under D-01 it would make Exposure understate too. Each key's position stays its own row,
  scoped by `api_key_id`. Departed and superseded keys are already removed by
  `fetchLatestHoldingsPerKey`, so no cross-key dedup is needed. Holdings, Open Positions and
  Exposure carry every live key's position, and their totals equal the sum over keys. This answers
  the rule Phase 167.1.1 HOLDINGKEYSCOPE booked ("two accounts on one venue holding the same asset
  never merge") on this surface. Asked as "fix in 170.4 vs book it"; the founder's answer selects
  the in-phase fix, keyed per key.
- **D-09 (founder 2026-10-11, Recommended):** with NO eligible key, Overview and Risk both show the
  connect-a-key card; with an eligible key, the rebuilding panel wins over the empty card on both.
  This refines D-04 consistently with D-05..D-07.

- **D-10 (founder 2026-10-11, Recommended):** D-08 holds end to end, ingestion included.
  `allocator_holdings`' unique index on `(allocator_id, venue, symbol, asof)` and the
  `persist_allocator_holdings` upsert on that key (analytics-service/services/allocator_positions.py)
  keep ONE row when two live keys on one venue hold one symbol on the same day. The index and the
  upsert's conflict target gain `api_key_id`, so every key keeps its own row. Keys that share one
  exchange account stay de-duplicated by the existing same-account grouping (167.1.2). This is a
  migration that auto-applies to PROD on merge, so migration-reviewer and rls-policy-auditor must
  be clean BEFORE the merge. PROD on 2026-10-11 has allocators with 2-4 live keys on Deribit, OKX
  and MT5, so the collision is reachable today. This supersedes the Phase Boundary's "any change to
  how holdings are ingested" exclusion for this one key change only.

- **D-11 (founder 2026-10-11, Recommended, "Fix in PR 2"):** once PR 2's per-key index lands, two keys
  that read ONE exchange account each keep a same-day row, and the over-time charts' reader
  (`fetchHoldings` in src/lib/portfolio-exposure.ts, feeding NetExposureChart and AllocationOverTime)
  sums every row per `asof`, so that account would count twice. PR 2 makes that reader apply the same
  one-key-per-account-day rule (D-10, plan 11's shared rule) per `asof` day, with tests. D-03 keeps its
  meaning: the charts' history semantics are unchanged; only the double count is prevented. Found by
  plan 09's reader census; PROD on 2026-10-11 has 1 live marked same-account pair.

### Claude's Discretion
- The exact copy for the D-02, D-05 and D-06 states, following DESIGN.md and the curated-copy
  conventions already used on this page.
- Whether `getLatestExposureSnapshot` is re-implemented over `fetchLatestHoldingsPerKey` or
  removed in favour of the payload's holdings, provided D-01 holds and Exposure fails loud, never
  showing an invented zero, when the read fails.
- (Planner, 2026-10-11, plan-checker round 5; NOT a founder decision.) How D-10's "Keys that share
  one exchange account stay de-duplicated" picks the one key once two keys of an account both hold
  same-day rows: PER HOLDING TYPE (review WR-01, round 1), the key whose rows OF THAT TYPE carry
  the latest `updated_at` instant (compared as parsed microseconds, never as strings), ties broken
  by the smallest lowercase `api_key_id`. The winner is picked per (account, holding_type), not per
  account, so a later spot-only poll by one key does not erase the derivative rows another key of
  the account wrote that day; each type still comes from exactly one key, so nothing is counted
  twice. It applies to dollar totals only, never to the Scenario fingerprint, which keeps the commit RPC's
  contributing row set. It is one rule in both runtimes (plan 11), and the commit's server AUM
  applies it over service-written evidence only (plan 12).
