# Phase 164.1.1: Code Review Report

**Reviewed:** 2026-09-18T10:13:20Z
**Depth:** deep
**Files Reviewed:** 18
**Status:** issues_found

## Summary

This phase adds a PROD-side pg_cron observer (`public.prod_prober_cadence_check()`), the HTTP
endpoint it posts to (`POST /api/prober-cadence-alert`), and a large mutation-tested SQL gate plus
supporting wiring/floor pins. The SECURITY DEFINER hardening is genuinely solid: `search_path` is
pinned, EXECUTE is revoked from PUBLIC/anon/authenticated and granted only to `service_role`, the
migration self-verifies its own grants in a `DO` block, the NULL-contact leg is handled explicitly
(refusing the "NULL compared to NULL reads as healthy" trap), the destination allow-list is
re-tested in-body as a second layer independent of the CHECK constraint, and a missing/blank Vault
key raises rather than building a header over `NULL`. The 7-arm SQL gate (`G1/S1/O1/A1/U1/V1/N1`)
is unusually rigorous — every arm is proven RED by its own mutation twin, arm ordering is
carefully reasoned about shared `now()`/transaction-start-time hazards, and the destination/key
guards are each independently exercised rather than assumed. The Python route
(`prober_cadence_alert`) logs unconditionally before the rate-limited Sentry escalation, never
logs or echoes the request's own `X-Service-Key`, and is confirmed (by a test driving the real
`main.app` stack) to sit behind the existing `SERVICE_KEY` middleware with no carve-out. Floor
moves (`FILES_FLOOR` 46→47, `ARMS_FLOOR` 395→397→402) are consistent across `run.mjs`,
`mutation-annotation-parser.test.ts`, `mutation-runner-floors.test.ts` and `gate-family-meta.test.ts`,
and the only touched migration file is the new one — no applied migration was edited.

The review turned up no blockers. It did turn up a real coverage gap that sits exactly where the
phase's own charter says the highest scrutiny belongs — "any way this new alarm can itself fail
silently is the defect this phase exists to remove, reappearing one layer down" — plus three
smaller warnings and three low-severity items. None of them are user-facing or data-integrity
defects under the project's severity-scoping rule, so none are classified as blockers; the primary
finding (WR-01) is nonetheless the most important thing in this report and should be read first.

## Warnings

### WR-01: The new alarm's own outbound delivery is not watched by anything — `cron-obs` does not cover it, and the runbook's phrasing could be read as claiming it does

**File:** `analytics-service/routers/cron.py:1210-1230` (docstring), `docs/runbooks/prod-prober-cadence-go-live.md:261-280`, `scripts/prod-prober/arms/cron-obs.mjs:97-112` (unchanged, pre-existing)

**Issue:** `public.prod_prober_cadence_check()` fires `net.http_post` on a stale tick and never
checks the response — deliberately, per its own comment: "a raise here rolls back the observer
row written in step 4, so a tick that could not deliver leaves NO row." That's a reasonable
design for the *observer's own* liveness, but it means the only automated place in this repo that
could ever notice this new POST getting a non-2xx (the exact CRON-DRIFT-01 shape: a stale
`analytics_service_key` producing silent 401s behind a green history) is the `cron-obs` prober
arm, which reads `net._http_response`. That arm's query is hardcoded to a single job name:

```js
// scripts/prod-prober/arms/cron-obs.mjs — unchanged by this phase
export const CRON_OBS_SQL = `WITH j AS (
  SELECT jobid FROM cron.job WHERE jobname = 'match_engine_cron'
), ...`;
```

It will never fire for a `prod_prober_cadence_check` job, registered or not (registration itself
is deferred to plans 05/06, out of this branch). Yet `routers/cron.py`'s own docstring reads:

> "An operator can see whether the database's OWN post succeeded via `net._http_response` on the
> PROD side — never via `cron.job_run_details.status`, which is the distinction the `cron-obs`
> prober arm exists to make."

That sentence is true as a *general statement about the distinction cron-obs models*, but it
reads as though `cron-obs` is the answer for *this* function's own posts — it is not, and the
runbook's "Watching it" section (line 274 onward) tacitly concedes this by routing "was the alert
actually received" to a manual Sentry-triage check instead of a `net._http_response` query. The
net effect: if `analytics_service_key` goes stale the same way it did historically, the new
cadence alarm can enqueue a 401 that nothing polls for, and the only backstop is a human running
`SELECT ... FROM net._http_response ...` by hand — which is the "nobody looks" property this
phase's whole subject is about, one level down.

**Fix:** Either (a) extend `cron-obs.mjs`'s `CRON_OBS_SQL` (or add a sibling arm) to also watch
`jobname = 'prod_prober_cadence_check'` once it is registered, closing the gap with the same
mechanism already proven for `match_engine_cron`, or (b) if that is deliberately deferred to a
later plan/phase, soften the docstring in `cron.py` so it does not read as though `cron-obs`
already covers this function's posts, and add an explicit disclosed-residual entry (in the style
of `[PGCRON-LIVENESS-UNWATCHED-01]`) naming this specific gap so it isn't rediscovered as a
surprise later.

### WR-02: The Sentry escalation rate-limit window is a single global, not scoped by `cron_name`

**File:** `analytics-service/routers/cron.py:1156, 1183-1198`

**Issue:** `_last_prober_cadence_alert_at` is one module-level variable shared across every
`cron_name` the route ever receives:

```python
_last_prober_cadence_alert_at: float | None = None
...
def _escalate_prober_cadence_gap(alert: ProberCadenceAlert) -> None:
    global _last_prober_cadence_alert_at
    ...
    if (_last_prober_cadence_alert_at is not None
        and (now - _last_prober_cadence_alert_at) < _PROBER_CADENCE_ALERT_WINDOW_S):
        return
```

Today there is exactly one caller (`prod_prober_cadence_check`, `cron_name='prod_prober'`), so
this is currently harmless. But `ProberCadenceAlert.cron_name` is an unconstrained string and the
route's name (`prober_cadence_alert`, generic, not `prod_prober_cadence_alert`) invites reuse for
a second cadence source later. If that happens, an in-window alarm for cron A would silently
suppress the Sentry escalation for a genuinely different, concurrently-stale cron B — each
occurrence is still logged (the unconditional `logger.error` is correctly ordered before the
window check), so it is not a silent *loss* of signal, but it is a silent *downgrade* from
Sentry-paged to log-only for an unrelated source.

**Fix:** Key the window by `alert.cron_name` (e.g. a `dict[str, float]`) now, before a second
caller exists — cheap to do today, and avoids a defect report years from now.

### WR-03: The `NO_LIMITER_QUARANTINE` exemption overstates its own claim

**File:** `analytics-service/tests/test_limiter_route_coverage.py:341-348`

**Issue:** The added quarantine entry says the route is "invoked ONLY by
`public.prod_prober_cadence_check()`'s own `net.http_post`... never a browser or a user session."
That is not actually enforced anywhere — `POST /api/prober-cadence-alert` accepts any caller that
presents a valid `X-Service-Key` header, which is the same shared secret several other parts of
the stack hold (the Next.js frontend's `ANALYTICS_SERVICE_KEY`, for one). Nothing scopes the
caller to PROD's own SECURITY DEFINER function specifically. This mirrors the existing
`routers.cron.cron_sync` entry's phrasing immediately above it, so it is not a new pattern this
phase invented, but "invoked ONLY by" is stronger than what the guard actually proves.

**Fix:** Soften the comment to match what is actually true ("gated by the same shared service key
as `cron_sync`; no additional caller restriction"), or, if the narrower claim matters, add an
actual constraint (e.g. reject a `cron_name` outside an allow-list) so the comment describes
enforced behavior rather than an assumption about who currently holds the key.

### WR-04: `sql-mutation`'s local wall-clock keeps closing on its 20-minute CI ceiling, unactioned across two plans in this phase

**File:** `.github/workflows/ci.yml:1540-1572` (comment block added by this phase)

**Issue:** The phase's own comments record the trend without acting on it: plan 01 measured
~975s/~16.25min locally, plan 02 (same phase) measured ~1020s/~17.0min — both explicitly flagged
as "closer to the ceiling than the prior reading" and both deferred with "flagged, not acted on."
This is consistent with the documented policy (the rule fires on a *measured ubuntu* run, not a
local projection), so it is not a process violation, but two consecutive plans in the same phase
both moved the needle toward a hard 20-minute CEILING with no other lever than
`[REDUNDER-SUBSET-SPLIT]` once it's crossed. `TODOS.md`'s `[REDUNDER-SPLIT-CI]`-style entry (the
one this same diff cites) was reassigned to Phase 164.4.2 SUBSETSPLIT on 2026-09-18, per this same
branch's `TODOS.md` diff, so there is now a named owner — but that owner is not this phase, and
nothing here checks in a scheduled ubuntu run to see how close the real number actually is.

**Fix:** No action required in this phase (correctly out of scope, per its own routing decision),
but worth surfacing here since this phase's own two plans are the most recent contributors to the
trend, and the next PR that adds a SQL gate arm should capture the real ubuntu number before
assuming there is still headroom.

## Info

### IN-01: `detected_at` is validated but never surfaces in the log line or the Sentry message

**File:** `analytics-service/routers/cron.py:1132-1146, 1184-1191, 1199-1205`

**Issue:** `ProberCadenceAlert.detected_at` is a required field (a body missing it is rejected with
4xx), but `_escalate_prober_cadence_gap` never reads it — the log line and Sentry capture carry
`cron_name`, `gap_minutes` and `ceiling` only. An operator reading either signal cannot tell when
the DB-side function actually detected the gap versus when the log line itself was emitted (the
two can diverge under queueing/retry). Not a bug — the field's presence is still useful as a
producer-contract check — just a missed diagnostic opportunity.

**Fix:** Include `alert.detected_at.isoformat()` in the log format string and/or the Sentry
message body.

### IN-02: Module-global rate-limiter state is per-process, not per-deployment

**File:** `analytics-service/routers/cron.py:1156`

**Issue:** `_last_prober_cadence_alert_at` is a plain module global with no cross-process
coordination. Under a multi-worker Uvicorn/Gunicorn deployment this "once per hour" window is
actually "once per hour per worker process," so N workers could each independently escalate to
Sentry within the same hour. This is an inherited pattern (cloned deliberately from
`_alert_kek_unavailable` in `routers/internal.py`, which has the same property), not something
this phase introduced net-new, so it is informational rather than a regression.

**Fix:** None required for this phase specifically; if the underlying pattern is ever hardened
(e.g. moved to a shared store), this call site should move with it.

### IN-03: The migration's `⛔ FORWARD MIGRATION ONLY` comment references `cron.schedule(...)` registration as owned by "plans 05/06 of this phase," but nothing in this branch registers it

**File:** `supabase/migrations/20260918120000_prod_prober_cadence.sql:12-17`

remains: the live registration itself... owned by plan 06") and the runbook

branch, confirming the function ships un-scheduled as documented. No fix needed.
