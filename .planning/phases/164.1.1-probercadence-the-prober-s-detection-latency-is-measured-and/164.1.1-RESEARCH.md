# Phase 164.1.1: PROBERCADENCE — Research

**Researched:** 2026-09-18
**Domain:** PROD-side PostgreSQL observability (`pg_cron` + `pg_net` + `cron_runs`), GitHub Actions
scheduling reliability, and the alarm-delivery channels genuinely reachable from PROD Postgres
in this repo.
**Confidence:** MEDIUM — the repo-side mechanism (what exists, what is dormant, what is dead) is
HIGH confidence (read from source, migrations, and a captured PROD manifest). The PROD-side
runtime state of two candidate delivery channels (whether `SENTRY_DSN` is actually set on the
Railway analytics-service, whether `RESEND_API_KEY` is set in Vercel prod) could NOT be verified
from the repo and is flagged LOW/ASSUMED below — this is exactly the class of claim CTX-03 warns

## Summary

CTX-03 asked three measurement questions before any channel is locked. All three now have
repo-side answers, and one of them reverses part of the premise written into CONTEXT.md.

1. **`cron_runs` is NOT dormant.** It has a real, currently-running PRODUCTION writer:
   `analytics-service/services/mt5_session_episodes.py`, invoked from an `asyncio.create_task`
   registered in `analytics-service/main.py`'s lifespan (`mt5_session_monitor_loop`, not a test).
   It writes rows under `cron_name = 'mt5_session_episode'`. There is also a **direct,
   founder-approved precedent** (Phase 164.6.4, decision D-5) for adding a brand-new
   `cron_name` to this same table **with no migration at all** — the exact shape CTX-01 proposes
   for `cron_name = 'prod_prober'`. This precedent is reusable almost verbatim.
2. **The documented "36h stale alert" is dead — confirmed, not merely suspected.**
   `latest_cron_success(p_cron_name)` has **zero callers** anywhere in the tree (grepped Python,
   TypeScript, and SQL — including `.rpc(...)` call sites). It exists only as a generated RPC
   signature in `src/lib/database.types.ts`; nothing invokes it, no dashboard reads it, no cron
   job calls it. The `COMMENT ON TABLE` describing a "36h stale alert" describes a mechanism that
   was apparently never wired to anything a human reads. This is a **finding to report**, per
   CTX-03's own instruction — do not route around it, and do not reuse `latest_cron_success` as
   this phase's read path without first deciding whether to wire it for real or replace it.
3. **PROD's outbound-reachable surface is narrower than CONTEXT.md's premise stated, but it is
   NOT the placeholder URL.** The placeholder `https://<your-railway-host>` CONTEXT.md cites is
   from the *original* (2026-04-08) migration and is stale. Phase 164.7's settled mechanism
   (`public.match_engine_cron_tick()`, re-based by 164.8.6) reads a **real, seeded** Railway host
   — `system_settings.analytics_service_url = 'https://quantalyze-analytics-production.up.railway.app'`
   — through a two-layer allow-list (a `CHECK` constraint on the table plus a byte-identical
   regex re-test inside the function body), and fires `net.http_post` at it. This is a live,
   reviewed, currently-registered pattern (PROD `cron.job` jobid 1 runs exactly this function
   hourly, per the captured 2026-09-17 manifest). **This is the one channel a new PROD `pg_cron`
   job can reach without inventing new infrastructure or a new migration-gated allow-list entry.**
   Whether that HTTP hop ultimately reaches a human depends on what analytics-service does with
   the request — see Open Question 1 below, which is NOT resolvable from the repo.

**Primary recommendation:** Reuse `cron_runs` under `cron_name = 'prod_prober'` (CTX-01, now with
a directly reusable precedent), have the prober write it via a plain `psql` `INSERT` added to its
existing PROD session-pooler connection (CTX-02), and have a NEW PROD-side `pg_cron` job call a
NEW `SECURITY DEFINER` function that (a) checks the gap, (b) writes its OWN `cron_runs` row so the
check's own liveness is observable the same way, and (c) reaches analytics-service through the
ALREADY-ALLOWED `system_settings.analytics_service_url` + `net.http_post` pattern — but do NOT
assume that HTTP hop currently pages anyone. Confirm what analytics-service does with the request
(or route it through Sentry capture, which has a documented, currently-used human triage runbook)
before treating "alarm fires" as "a human is paged." Retire or explicitly repurpose
`latest_cron_success()` in the same phase rather than leaving two "is this cron alive" answers in
the schema.

### Finding 4 — `pg_cron` job registration in this repo is a LIVE OP, never a migration [VERIFIED: .planning/phases/164.5.1-cronrepoint-the-live-match-engine-cron-row-is-repointed-at-t/164.5.1-PROD-SESSION.md:340,569; supabase/migrations/20260907120000_analytics_service_settings_and_vault_tick.sql:52]

```
164.5.1-PROD-SESSION.md:340 (verbatim, the actual command that was run against PROD):
  SELECT cron.schedule('match_engine_cron', '0 * * * *', $$SELECT public.match_engine_cron_tick();$$);
164.5.1-PROD-SESSION.md:343:
  Returned `schedule = 1` — `cron.schedule` UPSERTs on `(jobname, username)` and PRESERVED …
```

The migration comment states this directly: *"analytics_service_url — NOT a secret, and it has
NO consumer anywhere … `docs/runbooks/ledger-refresh-go-live.md`: the registration statement lives
THERE and never in a migration."* This repo's settled convention (established across 164.5,
164.5.1, and the ledger-refresh activation) is: a **migration** creates the SQL function(s) and
any supporting table/index/constraint changes; the actual `cron.schedule(...)` call that touches
the LIVE PROD `cron.job` catalog is run as a **separate, documented, founder-gated live operation**
against the linked-to-PROD Supabase CLI, following a runbook pattern (see
`docs/runbooks/ledger-refresh-go-live.md` as the template — 799 lines, already exists for the
ledger case).

**Design implication:** this phase's plan should NOT attempt to `cron.schedule(...)` a new job
from inside a migration file. It should (a) ship the checking function + any table changes as a
forward migration, reviewed by the three required reviewers
(`migration-reviewer`/`rls-policy-auditor`/`silent-failure-hunter` per CLAUDE.md), then (b) ship a
short runbook (or extend an existing one) describing the exact `cron.schedule(...)` statement, and
(c) treat the actual registration against PROD as a live op — almost certainly a `checkpoint`
task, since CLAUDE.md's "no clients → take decisions autonomously" note applies to *decisions*,
not to *executing an irreversible write against a linked PROD database*, which this repo's own
constraints elsewhere gate behind explicit review.

⚠️ **Consequence for criterion 4's sibling gate — `cron-drift`.** The prober's existing
`cron-drift` arm (`scripts/prod-prober/arms/cron-drift.mjs`, see `scripts/prod-prober/run.mjs`)
diffs live PROD `cron.job` against the **committed** `scripts/prod-prober/cron-manifest.json`. The
moment a new job is registered live against PROD, that arm will read it as an UNCOMMITTED
manifest drift (a real defect it exists to catch) **unless** the plan also updates
`cron-manifest.json` to include the new job (jobid, jobname, schedule, command, command_sha256) in
the same change. This is a required task, not an optional cleanup — the existing `cron-drift` arm
would otherwise immediately regress on this phase's own output.

### Finding 5 — the prober's SQL arms are deliberately READ-ONLY today; the new write (criterion 1) needs a distinct code path [VERIFIED: scripts/prod-prober/run.mjs:1423-1454 (scenario text quoted), :218-220]

```

  scenario("a psql failure is a measure-fail on the SQL arm, never a cron verdict");
scripts/prod-prober/run.mjs:218-220 (verbatim):
  "Set PROBER_POOLER_URL to the PROD Supabase SESSION POOLER URL (port 5432, IPv4) WITHOUT a

  "Set the existing GitHub Actions secret SUPABASE_DB_PASSWORD on the prod-prober workflow's job.

```

The prober already carries a live PROD session-pooler credential and shells out to `psql -At` for
its `cron-obs` and `cron-drift` arms. Its self-test explicitly enforces a **SQL-read-only**
invariant for arms (`cron-obs.mjs`'s own header: *"THIS ARM THEREFORE NEVER SELECTS

literally forbidding all writes, but the whole arm design assumes read-only SQL). Adding an
`INSERT INTO cron_runs (...)` for CTX-02's "the prober writes its own contact row" requirement is
straightforward from a credentials/connectivity standpoint (same pooler URL, same PGPASSWORD) but
should be implemented as a **step separate from the four existing arms** — e.g. a final
"record contact" step that runs regardless of arm pass/fail (so a red arm still gets its contact
row written, which is exactly what CTX-02's rationale requires: "measure prober runs, not request
health") — rather than folded into an arm's own read-only SQL surface, to avoid perturbing the
arms' self-test invariants or requiring a new DEFECT_KIND for what is not a probe result.

### Finding 7 — this repo's anti-vacuity SQL-gate machinery is the natural home for criterion 3 [VERIFIED: supabase/tests/ naming convention; TODOS.md VAC-01..08 entries in REQUIREMENTS.md read above; project memory `project_test_becomes_real_preprod.md`]

Criterion 3 requires the alarm be **observed RED with a stale/absent contact row and GREEN with a
fresh one** — explicitly framed by the phase as "exactly the vacuity class this milestone ranks
above ordinary correctness." This repo already has a purpose-built, CI-enforced mechanism for
exactly this shape: `supabase/tests/test_*.sql` gate files carrying `RED-UNDER` mutation
annotations, exercised by the mutation runner (`scripts/mutation-runner/run.mjs`, the `sql-mutation`
CI job) on a disposable pg-lane. This is the SAME mechanism VAC-01/02/06 built and VAC-06/VAC-07
reused. **Recommendation: express criterion 3 as a new `supabase/tests/test_prod_prober_cadence_*.sql`
gate file**, following the existing convention (RED-UNDER annotation on the arm that asserts
"stale row → alarm predicate is TRUE / RAISEs", proven by mutation; a paired GREEN arm for a fresh
row). This reuses machinery the plan-checker, mutation runner, and `sql-gate-lint`'s seven rules
already understand, rather than inventing a bespoke calibration harness. ⚠️ It does NOT, by
itself, prove the HTTP hop to analytics-service is reachable or that a human receives anything —
only that the PROD-side PREDICATE (stale vs. fresh) is correctly computed. A separate, live smoke
(closer to how the `cron-obs` arm checks `net._http_response` rather than trusting
`cron.job_run_details.status`) is the honest way to prove delivery, not just detection — name this
gap explicitly if the plan cannot close it within this phase's budget.

### Finding 8 — the turtle (criterion 5): nothing in this repo watches `pg_cron`/Postgres itself [VERIFIED: grep of `cron.job_run_details` across supabase/migrations, supabase/tests, scripts/ — all hits are either comments noting it is "rarely scraped" or SQL gates scoped to OTHER jobs' behavior, none is a meta-monitor of pg_cron's own liveness]

`cron.job_run_details` is pg_cron's own native execution log — several migrations reference it as
"operator-visible" but one comment states plainly it is *"rarely scraped"*
[CITED: supabase/migrations/20260516170200_match_decisions_constraint_validate.sql:7]. No
mechanism in this repo (SQL, Python, or TypeScript) periodically checks whether `pg_cron` itself
is still executing jobs, whether the extension is enabled, or whether PROD Postgres is reachable
at all, independent of any specific job's own body. If PROD Postgres or the `pg_cron` extension
stopped entirely, the new staleness-check job proposed here would also stop firing — it shares
the exact failure mode being guarded against, one level up.

**This is the unexamined turtle criterion 5 requires be named, not solved.** Two honest options
for the plan, consistent with how this repo already treats other unclosable residuals (e.g. the
`FANOUT-FAILBRANCH-UNEXERCISED-01` and VAC-08 residuals in TODOS.md):
1. **Accept it as a named residual**, documented in the phase's own artifacts and in TODOS.md,
   on the grounds that a total PROD Postgres outage is already a whole-application incident with
   many other symptoms (every request fails, not just this alarm) — i.e. the residual is narrow
   (silent pg_cron-only degradation while the rest of Postgres works) rather than broad.
2. **Partially cover it** by having the GitHub-hosted prober's own arms (which already run,
   however unreliably) include a check of `cron.job_run_details` recency for the alarm job itself
   — this does NOT close the gap (the prober shares GitHub's own unreliability, which is this
   phase's entire premise) but it is strictly better than nothing and costs little, since the
   prober already runs SQL arms against PROD.
Neither is free; CTX and the ROADMAP both anticipate this and require only that the choice be
**stated**, not that it be solved.

### Pattern: Vault-backed PROD `pg_cron` → `pg_net` function (the settled 164.7 shape)
**What:** a `SECURITY DEFINER` function that resolves a secret from `vault.decrypted_secrets` and
a destination from `system_settings`, re-validates the destination against the SAME regex the
table's `CHECK` constraint enforces, and fires `net.http_post`.
**When to use:** any new PROD `pg_cron` job in this repo that needs to reach an external HTTP
endpoint.
**Example (the exact function to model against, read in full):**
```sql
-- Source: supabase/schema/functions/match_engine_cron_tick.sql (Phase 164.7, re-based 164.8.6)
SELECT count(*), max(decrypted_secret) INTO v_cnt, v_key
  FROM vault.decrypted_secrets
 WHERE name = 'analytics_service_key';
-- ... null/empty guards ...
SELECT s.value INTO v_url FROM public.system_settings s WHERE s.key = 'analytics_service_url';
-- ... null/empty guard, THEN re-test against c_url_allowed regex ...
SELECT net.http_post(
         url := v_url || '/api/match/cron-recompute',
         headers := jsonb_build_object('Content-Type', 'application/json', 'X-Service-Key', v_key),
         body := '{}'::jsonb,
         timeout_milliseconds := 60000
       ) INTO v_req;
```

### Anti-Patterns to Avoid
- **Scheduling a new `cron.job` row inside a migration file.** This repo's established convention
  (Finding 4) treats live PROD `cron.job` registration as a separate, runbook-driven op — a
  migration doing this would be a deviation from every prior instance in this repo.
- **Trusting `cron.job_run_details.status` as evidence the alarm's HTTP call landed.** Every arm
  and function in this repo that touches `net.http_post` explicitly rejects this (the `cron-obs`
  arm's entire reason for existing is that `net.http_post` is async and `job_run_details` only
  proves the call was *enqueued*). The new check function's own success/failure must be judged the
  same way this repo already judges `match_engine_cron`'s.
- **Echoing a secret or an offending URL value in a `RAISE`.** `match_engine_cron_tick()` names
  the SETTING, never its value, specifically because `RAISE` text lands in `cron.job_run_details`,
  Postgres logs, and downstream log shippers — and this repo is public (`.planning/` is tracked).
  Follow the same discipline in the new check function.
- **Introducing an unfiltered `COUNT(*)` or scan over `cron_runs`.** The migration that owns the
  table explicitly forbids this in its own comments (Finding 1) because several existing SQL gates
  are narrowed by `cron_name` filters and an unfiltered read is both a perf and a coupling risk.

## Common Pitfalls

### Pitfall 1: assuming the workflow header (criterion 4) still needs editing
**What goes wrong:** the plan re-does work already shipped in commit `126517a8`, wasting a task
slot or, worse, stomping the already-correct 27%/3.28h/7.13h language with a re-derived (possibly
inconsistent) restatement.
**Why it happens:** the phase's own ROADMAP/TODOS text still narrates the defect in present tense
("declares hourly and delivers 27%") without flagging that the fix already landed.
**How to avoid:** Finding 6 — verify with a one-line `Read` of the workflow file before scoping
any task here.

### Pitfall 2: treating `latest_cron_success()` as free infrastructure
**What goes wrong:** the plan calls `latest_cron_success('prod_prober')` assuming it is a working,
tested "is this alive" read, when it has never been called by anything and its comment describes
a dead alert.
**Why it happens:** the function LOOKS purpose-built for exactly this ("Monitored by
latest_cron_success() for the 36h stale alert").
**How to avoid:** Finding 2 — either wire it for real (with its own proof) or write a dedicated
check; do not assume "it compiles and returns a timestamp" means "it is proven correct in this
role."

### Pitfall 3: forgetting the `cron-drift` arm will flag the new job as an uncommitted drift
**What goes wrong:** CI (or the next scheduled prober run that actually fires) reports a fresh
regression the moment the new job is live-registered against PROD.
**Why it happens:** `cron-drift` diffs live PROD against a COMMITTED manifest; live registration
and manifest-commit are two different actions that must land together.
**How to avoid:** Finding 4 — update `scripts/prod-prober/cron-manifest.json` (jobid, jobname,
schedule, command, `command_sha256`) in the same change that registers the job.

### Pitfall 4: conflating "the alarm predicate is provably correct" (criterion 3) with "a human receives it" (the phase's actual goal)
**What goes wrong:** the plan ships a SQL gate that proves RED-under-stale/GREEN-under-fresh (a
real, valuable, machine-checkable proof) and treats criterion 3 as fully closed, while the HTTP
hop to a human-facing channel is never actually confirmed to deliver anything.
**Why it happens:** the SQL-gate proof is the easy, machine-checkable 80%; the delivery proof
needs either a live PROD smoke or an honest recorded gap, and this repo's own culture (Finding 7)
makes the easy 80% look like the whole job.
**How to avoid:** treat "predicate correctness" and "delivery reachability" as two separate
claims in the plan's verification section, and if delivery cannot be smoke-tested within this
phase's budget, name that explicitly as a residual (mirroring Finding 8's treatment of the
turtle) rather than letting the SQL gate's green stand in for it.
