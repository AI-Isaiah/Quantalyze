### Auto-fixed Issues

**1. [Rule 1 - Bug] O1's RED-UNDER-M narrowed to avoid colliding with G1's own existing assertion**
- **Found during:** Task 1, first mutation-runner verification pass
- **Issue:** The plan's literal example for O1 ("delete the observer's own INSERT") also breaks G1's own pre-existing fresh-branch self-row assertion (established in plan 01), so under that mutation G1 — which runs before O1 — became the first failure instead of O1 (`WRONG-ARM(G1)`).
- **Fix:** Narrowed O1's mutation to hardcode only the status CASE expression (`CASE WHEN v_stale THEN 'error' ELSE 'ok' END` → `'ok'`), which leaves the fresh branch's row correct (unaffected, since G1's own scenario already reads 'ok') and wrong only on the stale branch, which no arm but O1 reads.
- **Files modified:** supabase/tests/test_prod_prober_cadence.sql

- **Committed in:** 165173b0 (Task 1 commit)

**2. [Rule 1 - Bug] N1's RED-UNDER-M narrowed and its execution position moved to LAST, to avoid corrupting or being corrupted by shared transaction-time state**
- **Found during:** Task 1, second and third mutation-runner verification passes
- **Issue:** Two related defects. First: the plan's literal example for N1 ("drop the cron_name predicate to `WHERE TRUE`") makes an unfiltered scan pick up ANY prior arm's own self-observability row — which shares N1's deliberately-fresh fixture's exact transaction-start `now()` timestamp — so once N1 ran anywhere after G1, S1 (which runs immediately after G1 and needs the read to conclude stale) became the first failure instead of N1, regardless of N1's own position. Second: placing N1 FIRST (to dodge that) instead broke G1's and S1's OWN plan-01 twins, because both mutate the shared staleness comparison every arm's call depends on, and G1/S1 must be the first two arms for their own twins to self-attribute.
- **Fix:** Narrowed N1's mutation to admit a second REAL producer by name (`WHERE cron_name IN ('prod_prober', 'mt5_session_episode')`) rather than dropping the predicate entirely — this never admits `prod_prober_cadence_check`, so it is immune to every arm's own self-observability row — and moved N1 to run LAST, after every arm whose twin touches the shared staleness math, with its own N1-SETUP restoring the Vault key (V1 removed it) and destination (U1 pointed it at a foreign host).
- **Files modified:** supabase/tests/test_prod_prober_cadence.sql
- **Verification:** `node scripts/mutation-runner/run.mjs --file supabase/tests/test_prod_prober_cadence.sql` reports all 7 arms `RED (identity ok)`, 0 defects
- **Committed in:** 165173b0 (Task 1 commit)

**3. [Rule 1 - Bug] O1's tick-2 row read fixed for a same-`now()` tie**
- **Found during:** Task 1, baseline (pristine) gate run
- **Issue:** `now()` inside a single `BEGIN...ROLLBACK` gate file is transaction-start time, not per-statement time, so O1's fresh and stale ticks write self-observability rows with an IDENTICAL `started_at`. `ORDER BY started_at DESC LIMIT 1` could then return either row non-deterministically, and the baseline gate failed on its own pristine run (`the stale-tick self-observability row reads status=ok`).
- **Fix:** Capture the fresh tick's row id, then read the stale tick's row as "the row whose id is NOT that one" — deterministic regardless of the timestamp tie, since O1 never carries more than two rows for this cron_name.
- **Files modified:** supabase/tests/test_prod_prober_cadence.sql
- **Verification:** baseline (pristine) gate run exits 0, all 7 arms pass, `ALL 7 ARMS EXECUTED` notice prints
- **Committed in:** 165173b0 (Task 1 commit)
