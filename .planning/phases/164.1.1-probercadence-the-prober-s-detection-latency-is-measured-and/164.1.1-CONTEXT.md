<decisions>
## Implementation Decisions

Settled 2026-09-18 via smart-discuss, one grey area, all four proposals accepted by the founder.

### CTX-01 — Reuse `cron_runs`, do not invent a second record

Last-prober-contact is recorded as a `cron_runs` row with `cron_name = 'prod_prober'`.
`supabase/migrations/20260408113029_cron_heartbeat.sql` already ships that table
(`cron_name`, `started_at`, `completed_at`, `status IN ('running','ok','error')`, `error`,
`metadata`), both its indexes, and a `latest_cron_success(cron_name)` helper whose own
`COMMENT ON TABLE` says it is *"Monitored by latest_cron_success() for the 36h stale alert"*.

**Why:** the reuse ladder — an existing helper in this repo beats a new one. A second table
answering "when did this last run" would need its own migration, its own indexes, a rebuilt
helper, and would leave two places to ask one question.

### CTX-02 — The PROBER writes the row, at the end of every run

It is the thing whose contact is being measured, and it already holds PROD database access for
the arms it runs. A PROD-side trigger on incoming requests was considered and rejected: it would
measure REQUESTS, not prober runs, and would go on reporting healthy while the prober was dropped
by GitHub — the exact failure this phase exists to close.

### CTX-03 — ⛔ MEASURE THE CHANNEL BEFORE CHOOSING IT. Do not hard-wire one at plan time.

The first plan task establishes, by measurement rather than by reading the comment:
1. Does anything WRITE `cron_runs` in production today? (grep found only test-file writers —
   `analytics-service/tests/*`. If no live writer exists, the table is dormant and that changes
   the design.)
2. Is the documented **"36h stale alert"** wired to anything that a human actually receives, or is
   it prose describing an intention? Nobody currently knows.
3. What outbound channels does PROD genuinely have? (`pg_net` exists; the only `http_post` URL
   found in migrations is the placeholder `https://<your-railway-host>`.)

⭐ **Rationale, and it is the phase's own subject:** an alarm on a channel nobody reads is exactly
the vacuity class this repo ranks above ordinary correctness — and adding a second channel beside
a first one that may already be dead would double the ambiguity instead of resolving it.
⚠️ A dead 36h alert is a FINDING to report, not a thing to quietly route around.

### CTX-04 — The ceiling is DERIVED from the distribution, never a tidy number

Measured 2026-09-18 over 273.4 h, twice independently: delivery 27 % (75 of 273 expected hourly
ticks), median gap 3.28 h, max gap 7.13 h, two gaps over six hours. The committed ceiling carries
its sample size and its date beside it, so the next reader can tell a measurement from a guess.
⛔ A round number chosen because it looks tidy is refused.

### Claude's Discretion

Everything not named above — file layout, helper naming, test structure — is at Claude's
discretion, consistent with existing repo conventions.
</decisions>

<specifics>
## Specific Ideas

- ⛔ **Do NOT "fix" the cadence by shortening the cron.** Under the same GitHub throttling
  `*/15` buys more attempts, not a bounded gap — a louder claim rather than a measured one.
- ⛔ **A GitHub-hosted watchdog cannot close this by construction.** If GitHub drops the prober
  run it drops the watchdog run too. The observer lives where a scheduler that actually fires
  does: PROD's own `pg_cron`.
- ⭐ **Criterion 3 is the anti-vacuity criterion:** the alarm must be OBSERVED red with a stale or
  absent contact row and green with a fresh one. A staleness gate never seen red has not been met.
- ⭐ **Criterion 5 forbids an unexamined turtle:** name what happens if PROD `pg_cron` itself
  stops, and either cover it or record it as an accepted, named residual.

<deviations>
## Workflow deviations taken at ship time (2026-09-18, v0.77.51.0)

Both are recorded here AND in `.planning/ROADMAP.md` per the CLAUDE.md deviation policy.

**D-SHIP-01 — the `track_shipping` step of `ship.md` was not run as written.**
That step writes a CI skip trailer into the ship-note commit message. CLAUDE.md forbids writing
that token in any commit message or PR body, *not even to deny it*, because GitHub honours it
anywhere in the message and a squash merge concatenates every branch commit message into the merge
body — so the token would ride into `main` and suppress CI there. Measured precedent: 2026-09-17,
zero workflow runs for the SHA, and a board that read "clean" with two Vercel checks. The ship-note
is therefore written without the trailer. The repo rule outranks the global workflow file, which
`/gsd-update` overwrites anyway.

**D-SHIP-02 — the `verification.status` ship gate was waived, not satisfied.**
`query verification.status` returns `missing`. This is structural, not an oversight: VERIFICATION.md
covers the phase goal, the phase goal is only reachable once Plan 06 registers the live
`cron.schedule(...)`, and Plan 06 cannot run until this migration has applied to PROD — which
happens on merge. The gate cannot be satisfied before shipping, by construction. Waived with the
reason stated in the PR body rather than re-planning a phase whose work is done and has passed four
review gates plus a security audit. VERIFICATION.md is owed immediately after Plan 06 executes.
</deviations>
