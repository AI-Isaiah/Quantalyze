## Summary

This phase's real subject is not the breaker; it is that **the breaker's tests cannot fail.** Ten
simultaneous semantic mutations to the seam core produced `8859 passed | 287 skipped` — byte-identical
to the number Phase 140 certified. The mechanism is fully explained by three source facts read this
session, not by an inference:

1. Every budget assertion reads its expected value out of the table under test
   (`src/lib/resilient-fetch.test.ts:473`, `:485` — `toHaveBeenCalledWith(mod.SEAM_BUDGETS.bridge.timeoutMs)`).
2. Every breaker loop bound is `mod.BREAKER_FAILURE_THRESHOLD`
   (`resilient-fetch.test.ts:260, 274, 330, 345, 374, 409, 423, 434, 443`), so a threshold of 5 or of
   30 produces the same green.
3. The fake limiter harvests its threshold **from production's own constructor argument**:
   the test's `Ratelimit` double does `fakeRatelimitFor(shared.ctx.store, opts.limiter.tokens)`
   (`resilient-fetch.test.ts:108`), and `opts.limiter.tokens` is whatever
   `Ratelimit.slidingWindow(BREAKER_FAILURE_THRESHOLD, BREAKER_WINDOW)` was called with
   (`resilient-fetch.ts:399`). The oracle is literally the thing under test, two layers deep.

The second half of the phase is that **the fake models the wrong algorithm.** The deployed limiter is
`@upstash/ratelimit@2.0.8`'s single-region sliding window: epoch-aligned buckets, **weighted carry-over
from the previous bucket**, and **no increment on denial**. The fake
(`src/test/helpers/upstash-breaker.ts:165-186`) is a fixed window anchored at first-call time with a
plain `count <= threshold`. Reading the deployed Lua at
`node_modules/@upstash/ratelimit/dist/index.mjs:206-247` reproduces A-08's recovery-latency finding
exactly: after a trip, the counter is never cleared, so the *first* failure in the next epoch bucket
re-trips whenever the carry-over lands at `threshold - 1`. Real recovery latency is **30s–60s**,
alignment-dependent, against a docblock (`resilient-fetch.ts:100-107`) that says 30s.

Three defects found at source this session are load-bearing for the plan and are stronger than the
findings doc states them:

- **A-09 is exact and reproducible from library source.** `@upstash/ratelimit`'s `timeout` defaults to
  **5000 ms** (`index.mjs:743`) and its timeout sentinel resolves
  `{success: true, limit: 0, remaining: 0, reset: 0, reason: "timeout"}` (`index.mjs:905-916`). The
  breaker's trip test is `if (success && remaining > 0) return;` (`resilient-fetch.ts:455`). A hung
  Upstash therefore **trips the breaker on ONE failure** — the fail-open sentinel is read as counter
  exhaustion, and it is a hard code path, not a theoretical one.
- **A-04 is exact.** `Redis.fromEnv()` (`resilient-fetch.ts:364`) takes SDK defaults of **6 attempts**
  and `Math.exp(i)*50` backoff with **no signal** (`@upstash/redis@1.38.0`
  `chunk-2X4SLXT7.mjs:125-190`). Cumulative backoff ≈ **4 290 ms**, and each of the 6 `fetch` calls has
  no deadline at all. `Redis.fromEnv(config)` **does** accept `retry` and `signal`
  (`node_modules/@upstash/redis/nodejs.mjs:222-232`), so bounding it is a config change, not a rewrite.
- **`isBreakerOpen` can be made 1 RTT and atomic** by storing the expiry inside the value instead of a
  second `ttl()` call, which closes A-24 (the get/ttl race) and half of A-26 (store cost) in the same edit.

**Primary recommendation:** treat `SEAMCORE-07` (literal pins) and `SEAMCORE-09` (real Redis) as
**Wave 0** — build the falsifiable oracle and the real-Redis lane *before* changing any semantics,
so that every subsequent behaviour change in this phase is provable. Then land the semantic changes
in dependency order: recording window (SEAMCORE-02) → attributability + per-dependency keying
(SEAMCORE-01) → store bounding (SEAMCORE-03/04/05) → structural guards (SEAMCORE-08) → SC7/TS-04.

### 3.2 The fake models the wrong algorithm (explains D-01, A-08, A-14)

### 4.3 The discriminator shape (contract-mandated — do not invent a variant)

STATUS_CONTRACT §2.1 prescribes the branch verbatim. **Reading `body.detail.code` unconditionally
yields `undefined` on both flat shapes** and falls through to UNKNOWN — the exact dead end PYAPIFIX2-01
exists to kill, reintroduced at the consuming layer.

```ts
// `detail` is an OBJECT  => the nested service_error envelope (STATUS_CONTRACT §2)
// `detail` is a STRING   => one of the two flat shapes            (STATUS_CONTRACT §2.1)
const code =
  body?.detail !== null && typeof body?.detail === "object"
    ? body.detail.code          // nested: also carries dependency + retryable
    : body?.code;               // flat:   also carries recoverable (or ok/human_message)

const human =
  typeof body?.detail === "string" ? body.detail : body?.detail?.detail;
```

`dependency` exists **only** in the nested branch — the flat shapes are 4xx and name none. That
asymmetry is the contract, not an omission.

### 4.4 Four hard requirements the discriminator must satisfy

1. **It must reach a verdict from the STATUS LINE ALONE** for the bodyless `500 text/plain` case
   (O-4 / TRAP-2). Concretely: decide *counts / does-not-count* on `res.status` **before** any
   `res.json()`, and use the body only to refine the **key**. A discriminator that must parse a body
   is undefined on the single most common 5xx.
2. **It must not consume the body the caller needs.** `Response.body` is a one-shot stream. Either
   `res.clone()` before reading (an extra buffer of the whole body) or read once in the core and hand
   the parsed value forward. **This is a real design decision the planner must make** — today the core
   returns an unread `Response` and both clients read it themselves
   (`analytics-client.ts:177,184,196`; `process-key-client.ts:300,307`;
   `permissions/route.ts:146,152`; `finalize-wizard/route.ts:133`). It interacts directly with
   SEAMCORE-02 (§5).
3. **It must key on `dependency`, never globally** (O-2 / OB-8) — and the OB-8 acceptance criterion is
   testable: *with `breaker:mt5-gateway` open, a call that can only be blocked by `breaker:supabase`
   still reaches Railway.*
4. **A `424`'s `dependency` must never become a key** (STATUS_CONTRACT §4). The cleanest structural
   guard: only read `dependency` on the `503` arm; ignore the field entirely on every other status.

### 4.5 ⚠️ The unresolved design problem: per-dependency keying vs. check-before-fetch

`isBreakerOpen()` runs **before** the request (`resilient-fetch.ts:524`), which is the property worth
protecting — but at that moment **the dependency that will fail is unknown.** Three viable resolutions,
with their costs:

| Option | Mechanism | Store cost | Assessment |
|---|---|---|---|
| **A — call-site dependency sets** | Each `SEAM_BUDGETS` row declares the dependencies it can be blocked by (e.g. `validate-key: ["mt5-gateway","egress-proxy"]`, `keys-permissions: ["kek","supabase"]`). Check only those. | 1 `mget` = **1 RTT** (`@upstash/redis` supports `mget`, `chunk-2X4SLXT7.mjs:3423`) | **Recommended.** Turns SEAMCORE-01 and SEAMCORE-10/A-17 into the *same* row-per-call-site refactor, and makes the declaration reviewable. Risk: a wrong/stale declaration silently under-protects — so pin each row with a literal. |
| B — check all keys always | `mget` of the 4 service keys + the global | 1 RTT | Simpler, but re-creates a partial A-01: an `egress-proxy` trip would block `/api/simulator`, which cannot touch it. |
| C — global check + per-dependency record | Keep one `breaker:railway` gate; only the *counter* is per-dependency | 1 RTT | **Fails OB-8's acceptance criterion outright** — one dependency's trip still suppresses everything. Do not ship this. |

Whatever is chosen, the residual **transport-failure** key stays global (`breaker:railway`): a
connection that never completed names no dependency, and that is genuine Railway degradation.

## 5. SEAMCORE-02 — the recording window and the body read

### 5.1 Exactly where the window ends today

```
resilient-fetch.ts:530   try {
resilient-fetch.ts:535     res = await fetch(`${ANALYTICS_URL}${path}`, { ...requestInit,
resilient-fetch.ts:537       signal: AbortSignal.timeout(timeoutMs) });
resilient-fetch.ts:539   } catch (err) { ... await recordSeamFailure(); throw err; }
resilient-fetch.ts:560   ^^^ THE TRY CLOSES HERE
resilient-fetch.ts:562   if (res.status >= 500) await recordSeamFailure();
resilient-fetch.ts:572   return res;               // ← the body has NOT been read
```

`AbortSignal.timeout` aborts the **response stream**, not just the header exchange. With a stalling
upstream — headers fast, body slow, which is the modal Railway degradation — `fetch` **resolves**, the
`try` closes, `res` is returned, and the rejection happens later inside the caller's `res.json()`.
`recordSeamFailure()` is therefore **never called** on that path.

The docblock at `resilient-fetch.ts:502` (*"breaker check → budgeted fetch → classified failure
recording"*) is **false** for this case (C-23 class). The `>= 500` branch at `:562` is likewise the
only status-based recording, and it never sees a body.

## 6. SEAMCORE-03 / SC5 — how a degraded store holds a lambda past its budget, and how to bound it

### 6.1 The exact arithmetic (all figures read from library source this session)

**`@upstash/redis@1.38.0` defaults** — `node_modules/@upstash/redis/chunk-2X4SLXT7.mjs:125-190`:

- `retry.attempts = config.retry?.retries ?? 5` (`:129`) with the loop `for (let i = 0; i <= attempts; i++)`
  (`:168`) ⇒ **6 `fetch` attempts**.
- `backoff = config.retry?.backoff ?? (i => Math.exp(i) * 50)` (`:130`), slept when `i < attempts`
  (`:187-189`) ⇒ sleeps for `i = 0..4` = `50 + 135.9 + 369.5 + 1004.3 + 2729.9` ≈ **4 289.6 ms**.
- `signal: config.signal` (`:107`, `:142`) — **`undefined` by default**, so each of the 6 `fetch`
  calls has **no deadline whatsoever**. Fail-open covers *rejections*; a **hang is not a rejection**.
- Retries fire only on a **thrown** fetch (`:171-176`), not on a non-`ok` response.

**`@upstash/ratelimit@2.0.8`** — `node_modules/@upstash/ratelimit/dist/index.mjs`:

- `this.timeout = config.timeout ?? 5e3` (`:743`) — so `breakerLimiter.limit()` **is** bounded at 5 s,
  by a race, not by an abort: the underlying request keeps running.

**Per-`resilientFetch` store cost, by state** (this is the table SC5 asks the invariant to account for):

| Breaker state | Store calls, in order | Bounded? | Added wall-clock when Upstash is degraded |
|---|---|---|---|
| **closed, request succeeds** | `GET breaker:railway` | ✗ unbounded | up to ≈4.3 s of backoff + N unbounded fetches |
| **open** | `GET` then `TTL` — **2 sequential RTTs** (`:420`, `:422`) | ✗ ✗ | ≈8.6 s |
| **closed, request fails** | `GET` + `EVALSHA limit` + `SET nx ex` | only the middle one (5 s race) | ≈4.3 + 5 + 4.3 ≈ **13.6 s** |

**None of this appears in `SEAM_ROUTE_BUDGETS` or in the SC-4b arithmetic**

### 6.2 The fix is a config change, not a rewrite — `[VERIFIED@src]`

`Redis.fromEnv(config)` forwards `retry` and `signal` to the `HttpClient`
(`node_modules/@upstash/redis/nodejs.mjs:222-232`), and `signal` may be a **function**, in which case
the client calls it per request (`chunk-2X4SLXT7.mjs:143`, `:151`) — which is exactly what is needed,
since a single `AbortSignal` instance would be already-aborted on the second call.

```ts
// Bounded breaker store. Every number here must be pinned to a literal (SEAMCORE-07)
// and must appear in the SC-4b arithmetic (SEAMCORE-03).
const BREAKER_STORE_TIMEOUT_MS = 1_000;   // per attempt
const BREAKER_STORE_RETRIES    = 1;       // attempts = retries + 1
const redis = configured
  ? Redis.fromEnv({
      retry: { retries: BREAKER_STORE_RETRIES, backoff: () => 100 },
      signal: () => AbortSignal.timeout(BREAKER_STORE_TIMEOUT_MS),
    })
  : null;
```

⚠️ **Read `chunk-2X4SLXT7.mjs:173-183` before choosing between a function-signal and a plain signal.**
The two branches behave *differently on abort*: with `isSignalFunction` the abort **rethrows**; with a
plain signal the client fabricates a `200` `Response` whose body is `{"result": <reason>}`. The
fabricated-200 path would make an aborted `GET` look like a *successful read of a value that is not
`"open"`* — i.e. **fail-open, silently**. That is the desired direction for `isBreakerOpen`, and the
**wrong** direction for `recordSeamFailure` (a swallowed record is an unarmed breaker). A plan must
choose deliberately and pin the choice with a test; do not let the default decide.

### 6.3 The A-09 sentinel — a hung store TRIPS the breaker today

`index.mjs:900-925` (`applyTimeout`) resolves, on timeout:
`{ success: true, limit: 0, remaining: 0, reset: 0, pending: Promise.resolve(), reason: "timeout" }`.
The library's intent is unambiguous — `success: true` means *let traffic through*.

`resilient-fetch.ts:448-462` reads it as:
```ts
const { success, remaining } = await breakerLimiter.limit(`${BREAKER_KEY}:failures`);
if (success && remaining > 0) return;   // ← sentinel: success=true, remaining=0 ⇒ FALLS THROUGH
await redis.set(BREAKER_KEY, "open", { ex: BREAKER_COOLDOWN_S, nx: true });  // ← TRIPS
```

⇒ **one recorded failure + one slow Upstash = a full global trip.** The fix must read `reason` (or
`limit === 0`, which no real limit ever is) and treat the sentinel as *"store unavailable, do not
trip"* — the fail-OPEN direction the locked decision already mandates. This is SEAMCORE-05's *"the
store's fail-open sentinel is never read as counter exhaustion"* and it is a **live defect**, not a
hardening nicety.

### 6.4 What SC5's invariant must assert

Extend `seam-budgets.invariant.test.ts`'s SC-4b arithmetic to:

with `storeWorstCaseMs` derived from the **literal** store constants (attempts × per-attempt timeout +

## 7. SEAMCORE-04 — breaker-state self-consistency (A-24)

`isBreakerOpen()` (`resilient-fetch.ts:414-431`) has two independent defects, both in nine lines:

```ts
const state = await redis.get<string>(BREAKER_KEY);      // :420  RTT 1
if (state !== "open") return { open: false };
const ttl = await redis.ttl(BREAKER_KEY);                // :422  RTT 2 — NOT atomic with RTT 1
return { open: true, retryAfterS: ttl > 0 ? ttl : DEFAULT_RETRY_AFTER_S };  // :423
```

1. **Healed circuit still denies.** If the lock expires between `:420` and `:422`, `ttl` returns `-2`,
   the ternary falls back to `30`, and the function **still returns `{open:true}`** — a recovered
   Railway is denied for another 30 s.
2. **Known-open state discarded.** If `ttl` throws while `get` returned `"open"`, the catch at `:424`
   returns `{open:false}` — contradicting `DEFAULT_RETRY_AFTER_S`'s own docblock (`:109-113`), which
   names exactly that case as the reason the fallback exists.

**The recommended fix removes both defects and one RTT at the same time:** store the expiry *inside the
value* — `SET breaker:<dep> "open:<expiryEpochMs>" EX <cooldown> NX` — and derive `retryAfterS` from a
single `GET`. Then:
- one RTT instead of two (halves the open-state store cost in §6.1);
- atomic by construction (there is no second read to race);
- a value whose parsed expiry is in the past is **treated as closed**, which is the correct
  fail-forward direction;
- and the `nx` idempotency property is unchanged.

An alternative — a small `EVAL` returning `[value, ttl]` atomically — also works (`redis.eval` is
available; `safeEval` uses it at `index.mjs:147-155`) but adds a second Lua script to own. Prefer the
value-encoding.

⚠️ **A-25 composes with A-24 and is separate.** `recordSeamFailure` has **no is-open guard**
(`:445-469`): a call admitted at `t=0` under a 60 s budget fails at `t≈60`; the lock armed at `t=0`
expired at `t=30`, so `nx` succeeds and arms a **fresh** 30 s window for a request that was already
doomed before the first trip. One wave of long-budget calls holds the breaker open 90 s+ with no new
traffic attempted. Fix shape: record the failure only if the request **started** after the current
lock was armed, or skip the trip write when the breaker is already open.

## Common Pitfalls

### Pitfall 1 — Pinning the plumbing and calling the value pinned
**What goes wrong:** `expect(timeoutSpy).toHaveBeenCalledWith(mod.SEAM_BUDGETS.bridge.timeoutMs)` looks
like a budget test. It is a *plumbing* test.
**Why:** the assertion's expected value is read from the object under test.
**Avoid:** every tuning value needs **two** assertions — plumbing (table → primitive) and value (table
→ literal). Delete neither.
**Warning sign:** a test whose `expect(...)` argument contains `mod.` or an import from the module under test.

### Pitfall 2 — Building the negative control on the false `vi.mock` premise
**What goes wrong:** a control that never fires, so the positive test's green is meaningless.
**Why:** `vi.mock` factories do **not** re-run on `vi.resetModules()` (measured, vitest 4.1.10).
**Avoid:** hang per-context setup off `Redis.fromEnv()`; assert class identity against the same module
registry. Better: use the real-Redis lane, where none of this applies.
**Warning sign:** a comment asserting factories re-run, or `instanceof` against a statically imported class after `resetModules()`.

### Pitfall 3 — A "recover faster" cooldown tweak that produces a permanent outage
**What goes wrong:** dropping `BREAKER_COOLDOWN_S` below `BREAKER_WINDOW` means the counter has not
decayed when the lock expires ⇒ ONE failure re-trips ⇒ the breaker flaps forever.
**Why:** counter and lock are separate keys with independent lifetimes, and the counter is never cleared.
**Avoid:** assert `cooldownMs >= windowMs` from literals (A-14), and prove recovery latency against real Redis (R-7).
**Warning sign:** any change to `:98` or `:107` that does not redden a test.

### Pitfall 4 — Fixing A-21 and A-22 in separate passes
**What goes wrong:** A-21 moves the body read **into** the try; A-22 moves the URL/signal construction
**out** of it. Two passes over the same `try` block reintroduce each other's bugs (TRAP-8, receipted).
**Avoid:** one task, one commit, both assertions RED first.

### Pitfall 5 — "Route the health warmer through the core" as a cleanup
**What goes wrong:** a cold `/health` probe failing is NORMAL ⇒ the warmer trips the breaker ⇒ the
breaker blocks its own recovery probe. **Self-sustaining outage, zero tests fail.**
**Avoid:** §10.1(c)'s membership guard. ESLint will not object (the paths are allowlisted).

### Pitfall 6 — Recording a caller fault as Railway degradation
**What goes wrong:** a malformed `ANALYTICS_SERVICE_URL` throws before a packet leaves, is logged as
*"network failure reaching the analytics service"*, and after 5 requests opens the global breaker —
permanently, from a config typo, with the log pointing ops at Railway.
**Avoid:** construct the URL and the signal **above** the try; validate `timeoutMsOverride` at entry.
**Warning sign:** the log line at `:553` firing with zero corresponding Railway ingress.

### Pitfall 7 — Under-enumerating a class (TRAP-5, receipted 4×)
**What goes wrong:** "every log site" delivered 3 of 5; "all error classes from the leaf" 5 of 7 routes.
**Avoid:** this document enumerates 10 log sites (§9.2), 9 body-read sites (§5.2), 13 budget keys with
their call sites (§2.1), 5 `resilientFetch` invocations (§1.2). **A plan must copy the lists, and the
plan-checker must reproduce the counts by its own search.** Enumerate by BEHAVIOUR, state the count,
say how you searched.

### Pitfall 8 — A green real-Redis job that ran nothing
**What goes wrong:** the store is unreachable, a `skipIf` fires, the job is green, the gate is fiction.
**Avoid:** fail loud in `beforeAll`; assert an executed-case count against a literal; wire the job into
the `frontend` aggregator's strict result loop.
