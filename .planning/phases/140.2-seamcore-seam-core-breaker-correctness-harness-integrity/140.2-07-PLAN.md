<objective>
Stop the breaker's own store from becoming the outage.

Purpose: `SEAMCORE-03`, `SEAMCORE-04`, `SEAMCORE-05` / ROADMAP SC5.

Four defects, all read at source, all live:

  **A-04 — the store is completely unbounded.** `Redis.fromEnv()` takes SDK defaults of SIX fetch
  attempts with `Math.exp(i)*50` backoff (≈4 290 ms cumulative) and **`signal: undefined`**, so each
  of the six fetches has no deadline whatsoever. Fail-open covers REJECTIONS; a hang is not a
  rejection. Per-call cost when Upstash is degraded: ≈4.3 s closed-and-succeeding, ≈8.6 s open (two
  sequential round trips), ≈13.6 s closed-and-failing. **None of it appears in the budget
  arithmetic**, which sums only `timeoutMs × calls × (1 + retries)`.

  **A-09 — a slow store TRIPS the breaker today.** `@upstash/ratelimit`'s `timeout` defaults to
  5000 ms and its timeout sentinel resolves `{success: true, limit: 0, remaining: 0, reason:
  "timeout"}`. The library's intent is unambiguous: `success: true` means LET TRAFFIC THROUGH. The
  core's trip test is `if (success && remaining > 0) return;` — so the sentinel falls THROUGH and
  trips. One recorded failure plus one slow Upstash equals a full trip. This is a live defect, not a
  hardening nicety.

  **A-24 — the state read is neither atomic nor self-consistent.** Two sequential reads of the
  breaker state: if the lock expires between them the retry-after falls back to the default and the
  function still returns open, so a recovered Railway is denied for another cooldown; and if the
  SECOND read throws after the first returned open, the catch returns closed — discarding a
  KNOWN-open state, which is precisely the case `DEFAULT_RETRY_AFTER_S`'s own docblock says the
  fallback exists for.

  **A-25 — an expired lock can be re-armed by a doomed request.** `recordSeamFailure` has no
  is-open guard. A call admitted at t=0 under a 60 s budget fails at t≈60; the lock armed at t=0
  expired at t=30, so `nx` succeeds and arms a FRESH 30 s window for a request that was already
  doomed before the first trip. One wave of long-budget calls holds the breaker open 90 s+ with no
  new traffic attempted.

⚠️ **Fail-OPEN stays.** Every failure mode of the breaker's own store resolves to "closed, proceed",
in ALL environments including production. This is a deliberate inversion of `src/lib/ratelimit.ts`'s
fail-closed and must NOT be harmonised: a silently-disabled rate limiter removes a regulatory cap,
whereas a breaker that blocks traffic because ITS OWN store is misconfigured has become the outage
it exists to prevent.
</objective>
