**The one message, byte-for-byte in both clients:**

```
Analytics seam returned an unusable response (HTTP <status>, content-type <media-type>). The upstream did not answer with the JSON contract.
```

`<media-type>` is the header's media type only — lower-cased, parameters stripped, capped at 64
chars (the raw header is upstream-controlled) — or the literal `absent` when there is none.

**Why 502 and not the observed status.** `AnalyticsUpstreamError.status` is contractually the code
route handlers FORWARD (`simulator/route.ts` forwards 4xx verbatim). Forwarding 204 or 304 would
have moved the identical `Response constructor: Invalid response status code` crash into the
route's own `NextResponse.json`; forwarding 200 would have shipped an error payload under a success
code. So the routable status is 502 — the gateway answered, unusably — and the observed status
lives in the message where an operator reads it. In `process-key-client` the user-facing envelope is
the EXISTING `UPSTREAM_NETWORK_ERROR` 502 with its existing copy: zero new codes, zero new
user-facing copy (140.3's fence). The observed status and content-type appear only in the operator
log line.

**Breaker verdict untouched.** A 2xx is not a service fault and neither is a 304. `seam-discriminator.ts`
was not edited; SEAMCORE-01's table is unchanged. This plan changed only what the CLIENTS do.

## Decisions Made

1. **502 as the routable status, observed status in the message.** See the enumeration above. The alternative — carrying the observed status on `AnalyticsUpstreamError.status` — reproduces the crash inside the routes that forward it, and ships an error payload under a 200 for the maintenance-page case.
2. **`{ ok: false, response }`, never a throw, in `process-key-client`.** Plan 140.2-05 widened that function's `try` specifically to keep it non-throwing for five caller routes with no catch; closing A-27 with a throw would have undone that in the same file. Asserted by "STILL never throws".
3. **Refuse, do not clamp, and use `Number.isInteger`.** The plan asked for "the shape `AnalyticsUpstreamError` already uses", and that shape is `!Number.isInteger(x)` plus a range check. `Retry-After` is RFC-7231 delta-seconds, so a fractional value is as malformed as a NaN. Production never produces one: `isBreakerOpen` returns `Math.ceil((expiresAtMs - now) / 1000)` guarded by `expiresAtMs > now`, i.e. always a positive integer — checked before shipping the validation, so this cannot turn a live breaker trip into a crash.
4. **The message builder is duplicated, and the duplication is guarded.** It cannot be shared: neither client may import from the other (sixteen route test files replace one or the other wholesale with a full factory, under which a cross-client import is `undefined` — the same argument that homes `CircuitOpenError` in the leaf), and it cannot go in the leaf because `seam-errors.purity.test.ts` pins that leaf's exported surface to a hand-typed TWO-member set which this plan does not change. So both files carry it, both state the outcome in a comment, and a comment-stripped cross-file check asserts the builder line is byte-identical in both.
