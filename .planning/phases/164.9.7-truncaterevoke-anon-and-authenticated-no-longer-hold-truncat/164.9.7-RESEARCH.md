## Summary

anon and authenticated hold TRUNCATE because **Supabase's platform bootstrap default privileges** grant `ALL` on every new `public` table to `postgres`, `anon`, `authenticated` and `service_role`. The migration chain never grants it: the chain contains no `ALTER DEFAULT PRIVILEGES` statement and no `GRANT TRUNCATE`; its only `GRANT ALL` statements are `service_role` grants (5 lines, listed below). Every table the repo ever created inherited TRUNCATE at creation, and each later hardening migration removed it from one table at a time (`system_settings`, `cron_runs`, `strategy_shares`, `strategy_sync_cursors`, `compute_jobs`, ...). This phase is the class fix. [VERIFIED: PROD `pg_default_acl` reading 2026-10-07 and `supabase/schema/baseline.sql:17166-17169`]

⛔ **The ROADMAP/CONTEXT counts (anon 56 of 63, authenticated 59 of 63) are RELATIONS, not tables.** Measured 2026-10-07 on PROD: of 63 base tables, **anon holds TRUNCATE on 53 and authenticated on 56**; three of the four `public` VIEWS (`compute_jobs_admin`, `public_profiles`, `verification_requests`) carry the privilege in their ACL too, which is exactly 53+3 and 56+3. `baseline.sql` agrees (51 `GRANT ALL` + 5 explicit-TRUNCATE lines = 56 for anon). TRUNCATE on a view is not executable, so the three view entries are hygiene, but `REVOKE ... ON ALL TABLES IN SCHEMA public` removes them for free and the self-check should cover the same set the REVOKE covers.

The mechanism was proven on a scratch PG 16.13 cluster: `REVOKE TRUNCATE ON ALL TABLES IN SCHEMA public FROM anon, authenticated` plus `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE TRUNCATE ON TABLES FROM anon, authenticated` leaves existing and future `postgres`-created tables without TRUNCATE for both roles, and `service_role`/`postgres` untouched. The grantor on every TRUNCATE ACL entry on PROD is `postgres`, and every `public` relation is owned by `postgres`, so the silent grantor-mismatch trap (measured in `20260911130000`) does not apply today; the self-check stays mandatory because the failure is silent.

**Primary recommendation:** ONE migration `20261009120000_revoke_truncate_anon_authenticated.sql`: a single `DO` block that (1) counts `service_role` TRUNCATE holders, (2) `REVOKE TRUNCATE ON ALL TABLES IN SCHEMA public FROM anon, authenticated`, (3) `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE TRUNCATE ON TABLES FROM anon, authenticated`, (4) verifies from `pg_class`/`pg_default_acl` only that no relation of kind r/p/v/m/f still lets either role TRUNCATE, that postgres's default ACL for tables carries none, and that `service_role` holders did not move. One new gate file, one rollback file, and the census edits listed below.

**Which role owns the default-privilege entries, and what the migration can reach.**
- Every one of the 63 tables and 4 views in `public` is owned by `postgres`; every TRUNCATE ACL entry for anon/authenticated has grantor `postgres`; zero entries have grantee PUBLIC; zero have another grantor. `[VERIFIED: PROD read 2026-10-07]`
- The `postgres` default-ACL row is the one that governs every table a migration creates. It is what D-01's `ALTER DEFAULT PRIVILEGES` must change, and it must be written `FOR ROLE postgres` explicitly: it is the creating role, and an unqualified statement targets `current_user`, which is not guaranteed to be `postgres` when the apply connects through a login role that is a member of it (PROD shows a `cli_login_postgres` member of `postgres`). `[VERIFIED: PROD pg_auth_members read]`
- ⛔ **The `supabase_admin` default-ACL row CANNOT be altered by any migration.** On PROD `postgres` is `rolsuper=false` and `pg_has_role('postgres','supabase_admin','member') = false`; PostgreSQL refuses `ALTER DEFAULT PRIVILEGES FOR ROLE <non-member>` with `permission denied to change default privileges` (reproduced on the scratch cluster, which raises that exact error for a role the session user is not a member of). Do NOT add a `FOR ROLE supabase_admin` statement: it would abort the apply on TEST and PROD. The residual is a table created by `supabase_admin` inside `public`; none exist today (all 67 relations are `postgres`-owned, 0 extension-owned). See Open Question 4.
- On TEST the `supabase_admin` row is gone anyway: `DROP SCHEMA public CASCADE` in the restore removes schema-scoped default ACLs and the dump re-adds only the `postgres` rows. `[ASSUMED]` A3 below (derived from the restore design, not read from TEST this session).

### Migration shape (verified skeleton)

House style (read: `supabase/migrations/20261008120000_for_quants_leads_contact_source.sql`, `20260911130000_ledger_fanout_grantees_and_dormancy.sql:1296-1313,1700-1752`): a long header (why, caller impact, access, "deliberately no data-reading DO block, the self-check reads the CATALOG only"), `-- STEP n` banners, a closing self-verifying `DO $...$` raising `migration <version> failed: ...`, no `BEGIN/COMMIT` in the up file, no `SET lock_timeout` in the up file.

Recommended single-DO form (the before/after `service_role` comparison needs both sides in one block, and one statement is atomic even under the lane's autocommit replay). Run on a scratch PG 16.13 cluster this session: success path printed `ok: service_role holders 3, anon/authenticated 0`; with `GRANT TRUNCATE ON public.b TO PUBLIC` planted it raised `TRUNCATE still held (relation/role): b/anon, b/authenticated`. `[VERIFIED: scratch run]`

```sql
DO $verify$
DECLARE
  v_sr_before int; v_sr_after int; v_held text; v_default text;
BEGIN
  SELECT count(*) INTO v_sr_before FROM pg_class c
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege('service_role', c.oid, 'TRUNCATE');

  REVOKE TRUNCATE ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
    REVOKE TRUNCATE ON TABLES FROM anon, authenticated;

  SELECT string_agg(c.relname || '/' || r.rolname, ', ' ORDER BY c.relname, r.rolname) INTO v_held
    FROM pg_class c CROSS JOIN (VALUES ('anon'), ('authenticated')) AS r(rolname)
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege(r.rolname, c.oid, 'TRUNCATE');
  IF v_held IS NOT NULL THEN
    RAISE EXCEPTION 'migration 20261009120000 failed: TRUNCATE still held (relation/role): %. REVOKE removes only grants made by the current user or a role it is a member of and prints nothing on a grantor mismatch (MEASURED, 20260911130000); find the grantor with aclexplode(relacl) and re-run the REVOKE under SET ROLE <grantor>', v_held;
  END IF;

  SELECT string_agg(d.defaclrole::regrole::text || '->' || a.grantee::regrole::text, ', ') INTO v_default
    FROM pg_default_acl d CROSS JOIN LATERAL aclexplode(d.defaclacl) a
   WHERE d.defaclnamespace = 'public'::regnamespace AND d.defaclobjtype = 'r'
     AND d.defaclrole = 'postgres'::regrole AND a.privilege_type = 'TRUNCATE'
     AND a.grantee IN ('anon'::regrole, 'authenticated'::regrole);
  IF v_default IS NOT NULL THEN
    RAISE EXCEPTION 'migration 20261009120000 failed: the postgres default ACL on public tables still grants TRUNCATE (%)', v_default;
  END IF;

  SELECT count(*) INTO v_sr_after FROM pg_class c
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege('service_role', c.oid, 'TRUNCATE');
  IF v_sr_after <> v_sr_before THEN
    RAISE EXCEPTION 'migration 20261009120000 failed: service_role TRUNCATE holders moved % -> %', v_sr_before, v_sr_after;
  END IF;
END
$verify$;
```

Decisions this encodes (all within CONTEXT's discretion):
- **`ON ALL TABLES IN SCHEMA public`, not a `pg_tables` loop.** It also covers views, matviews, foreign tables and partitions (a `pg_tables` loop would miss the 3 views and need `format('%I.%I')` plumbing). And it fails LOUD when the executing role is not the owner: scratch PG 16.13, a non-owner running it got `ERROR: permission denied for table t1`, aborting the apply. `[VERIFIED: scratch run]` On PROD every relation is `postgres`-owned, so that path is not live.
- **Self-check scope = REVOKE scope** (relkind `r,p,v,m,f`), via `has_table_privilege`, which also sees PUBLIC grants and role inheritance. `has_table_privilege` returns true for a VIEW whose ACL lists TRUNCATE (PROD: `views_trunc` read) so the view entries are detected, not ignored. `[VERIFIED: PROD read]`
- **`FROM anon, authenticated` only**, as D-01 states. PROD has zero PUBLIC-grantee entries; if one ever appears the self-check names it and the TEST apply fails first. See Open Question 5.
- **Catalogue only**, so TEST (schema-only, data-less) behaves like PROD. Reads `pg_class`, `pg_default_acl`, `aclexplode` — no table is scanned.
- **Do not write a `FOR ROLE supabase_admin` statement** (aborts the apply; see above).
- Timestamp: **`20261009120000`**. Latest migration on `origin/main` is `20261008120000` (DOMAINONE, `239106dc5`); across every local worktree branch and remote ref, no other branch carries a migration newer than `20261008120000`. `[VERIFIED: git ls-tree over all refs, 2026-10-07]` Re-check at plan time; other phases are in flight.
- Down file convention: `supabase/migrations/down/<version>-rollback.sql` (32 exist; latest `20261008120000-rollback.sql`), a manual file off the auto-apply path, `BEGIN; SET lock_timeout = '5s'; ... COMMIT;`, a header stating what it restores and that the ledger row is left in place plus the marker-query warning. `[VERIFIED: read of the DOMAINONE rollback]` ⛔ A blanket `GRANT TRUNCATE ON ALL TABLES ... TO anon, authenticated` rollback would OVER-grant: anon never held it on 10 tables and authenticated on 7 (system_settings, cron_runs, strategy_shares, strategy_sync_cursors, compute_jobs, ...). Restore the exact pre-state from `git show origin/main:supabase/schema/baseline.sql` (it equals PROD for this metric) and say so in the header.

## Common Pitfalls

### Pitfall 1: silent grantor mismatch
**What goes wrong:** `REVOKE` removes only grants made by the current user or a role it is a member of; on a mismatch it prints `REVOKE`, exits 0, and the privilege stays.
**Why:** measured on PG 16.13 on 2026-09-12 (`20260911130000`), superuser included.
**Avoid / detect:** the catalogue self-check (mandatory). Today every grantor is `postgres` `[VERIFIED: PROD read]`, so this is a guard, not a live fault.

### Pitfall 2: views, partitioned tables, matviews, foreign tables
`has_table_privilege` is true for a view whose ACL lists TRUNCATE (PROD: 3 views). `ON ALL TABLES` revokes on all of them; a self-check restricted to `relkind = 'r'` would pass while the ACL entry survives, and a `pg_tables` loop would never touch them. PROD has 0 partitions/matviews/foreign tables today; the sweep names `p,m,f` so a future one is covered without edits. Sequences and functions keep their `ALL` defaults (out of scope; no TRUNCATE concept).

### Pitfall 3: tables created by other roles or extensions
`ALTER DEFAULT PRIVILEGES FOR ROLE postgres` covers tables created BY `postgres` only (every migration, and the dashboard). A table created by `supabase_admin` inherits that role's row, which the migration cannot alter (non-member, measured). PROD has 0 such tables and 0 extension-owned `public` relations. An extension created as `postgres` inherits the (now clean) postgres default. Residual accepted; see Open Question 4.

### Pitfall 4: `apply-test` runs on a schema-only TEST
The self-check reads `pg_class`/`pg_default_acl`/`relacl` only, so an empty TEST cannot refuse it (`[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`). Do NOT add any `SELECT count(*) FROM <table>` or row-dependent guard. TEST's catalogue is a copy of PROD's dump (`baseline.sql` plus the replayed migrations), so the TEST holder counts equal the baseline counts; `[ASSUMED]` A3 (not read from TEST this session). If the TEST apply fails, the PROD apply is blocked and, with no human stop, the remedy is to revert the merge, never to edit `supabase-migrate.yml`.

### Pitfall 5: baseline, carried marker, replay
- Do not edit `supabase/schema/baseline.sql` or `supabase/schema/baseline-carried-migrations.txt`. The marker lists what PROD had when the dump was taken (it ends at `20261007120000`); `20261008120000` is already a replayed migration and the new one will be a second. The lane (`sql-tests`, `frontend-local-stack`, `frontend-live-db-lane`, `python`, `e2e-seeded`) loads the dump, then applies each uncarried file in filename order, one `psql` call per file in autocommit. A single `DO` is one statement, so it is atomic there, while a top-level `REVOKE` followed by a failing `DO` would leave the REVOKE committed on the lane. `[VERIFIED: scripts/local-stack/run.sh:610-700]`
- `scripts/baseline-content-drift-check.mjs` compares FUNCTION BODIES only (its header says "no grants"), so a grants-only migration does not create the tolerated stale-baseline red. The post-apply bot/manual re-dump will simply carry the new ACLs. Its `ALTER DEFAULT PRIVILEGES` lines will list explicit privileges (`SELECT,INSERT,REFERENCES,DELETE,TRIGGER,MAINTAIN,UPDATE ... TO "anon"`), a shape `scripts/local-stack/acl-fidelity.mjs` already parses (`DEF_RE` accepts a privilege list; a default-privilege REVOKE would be a MEASURE_FAIL, which pg_dump does not emit for a schema-scoped row). `[VERIFIED: acl-fidelity.mjs:93-117]`
- `restore-test-from-baseline.sh` still REFUSES a dump older than the migrations (default currency mode); a TEST restore between the PROD apply and the re-dump would refuse. Not caused by this phase; do not dispatch a restore in that window.

### Pitfall 6: the three "gate" lanes disagree about what exists
pg-lane (mutation) is PG 16 with fixtures; local-stack (`sql-tests`) is PG 17.6.1.113 with the dump plus replay; TEST is PG 17 schema-only. The gate must read only the catalogue and tables it creates itself, because the three catalogues differ. `supabase_admin` default rows exist on none of the lanes.
