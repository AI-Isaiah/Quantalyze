# Phase 164.9.7: TRUNCATEREVOKE - Context

**Gathered:** 2026-10-07
**Status:** Ready for planning

<domain>
## Phase Boundary

anon and authenticated no longer hold TRUNCATE on public tables. Measured read-only on PROD
2026-10-03: anon held it on 56 of 63 tables and authenticated on 59, `api_keys` included. RLS never
covers TRUNCATE, so any holder can empty a table regardless of policies. One migration revokes it and
the default privilege. Gates: migration-reviewer and rls-policy-auditor clean before merge (PROD
auto-applies after `apply-test`, no human stop).
</domain>

<decisions>
## Implementation Decisions (founder 2026-10-07, AskUserQuestion)

- **D-01 (scope):** Revoke TRUNCATE from `anon` and `authenticated` on EVERY table in `public`, and
  `ALTER DEFAULT PRIVILEGES` so tables created later never grant it to either role. `service_role` and
  `postgres` keep it.
- **D-02 (proof):** The migration carries a self-check that fails the apply if anon or authenticated
  still holds TRUNCATE on any public table afterwards. The self-check must not depend on table DATA
  (TEST is schema-only; CLAUDE.md `[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`), only on the catalogue.
- **D-03 (gate):** A SQL gate in `supabase/tests` asserts no public table grants TRUNCATE to anon or
  authenticated, shown RED once against a re-grant, and every census the new file moves is updated.
- **D-04 (measure):** Before and after PROD readings (marker query first) of the per-role TRUNCATE
  holder counts, counts only, recorded in the phase.

### Claude's Discretion
- Whether the revoke loops over `pg_tables` or issues `REVOKE ... ON ALL TABLES IN SCHEMA public`; check
  that nothing in the app or CI relies on anon/authenticated TRUNCATE (grep tests and fixtures).
### Accepted residual (orchestrator, planning 2026-10-07; recorded here per the deviation policy, ROADMAP carries it too)
- Accepted residual (CONFIRMED by the founder 2026-10-07, before merge; was provisional pending plan 04 Task 2): the `supabase_admin` default-ACL row on `public` still grants TRUNCATE to anon and authenticated on tables that role creates. `postgres` cannot alter it (not a member), no such table exists today, and this phase records it rather than gating it.

### Founder decisions (2026-10-07, AskUserQuestion, after review round 1)
- **D-05:** the `supabase_admin` residual is ACCEPTED, and a read-only PROD detector is booked: it flags any `public` relation not owned by `postgres`, and any non-`postgres` `pg_default_acl` row on `public` that grants TRUNCATE to anon or authenticated. Plan 04 Task 2's confirmation step is therefore already satisfied.
- **D-06:** the same RLS-exempt class with a larger blast radius goes to a NEW phase inserted after 164.9.7, not into this migration. The class is TRIGGER held by anon and authenticated (RLS audit HIGH: a client role can make a BYPASSRLS writer run its code) plus MAINTAIN (PG17: lock, VACUUM FULL, i.e. outage). TRUNCATE on `storage.*` and `net.*` is recorded as an accepted platform residual (not revocable by `postgres`). 164.9.7 ships unchanged.
</decisions>
