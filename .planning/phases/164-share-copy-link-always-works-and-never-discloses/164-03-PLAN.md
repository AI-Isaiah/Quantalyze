<objective>
The owner-side write lanes: mint-or-reuse and revoke, as API routes under the strategies namespace,
in the house route discipline — the fix for the founder-hit defect where a verbatim scenario-share
port would revoke-on-mint and silently kill the recipient's existing link (D-02's reuse payoff:
because the token re-derives from the stored counter, re-minting returns the SAME url).

**Response contract (shared verbatim with plan 164-04, which builds the UI against it):**
- POST /api/strategies/{id}/share → 200 `{ url }` where url = NEXT_PUBLIC_APP_URL +
  "/factsheet-share/" + token; 401 unauthenticated; 400 invalid id; 404 not-owner-or-unknown;
  429 with Retry-After; 503 limiter-misconfigured. All responses carry NO_STORE_HEADERS.
- POST /api/strategies/{id}/share/revoke → 200 `{ revoked: true }`; 404 when nothing was active
  (convergence — the client treats it as success); same auth/validate/limiter/error arms.

Purpose: SHARE-01 (Copy Link always yields a working URL — the mint half) and SHARE-03 (the revoke
control's backend).
Output: two routes + colocated tests, both under the audit law.
</objective>

<revision_note>
⛔ **REVISED 2026-08-28. This plan was written before the storage layer was finished, and parts of
it were WRONG rather than merely incomplete.** Read this block before the tasks.

**What would have broken.** The plan specified `deriveShareToken(strategyId, generation)`. The token
gained a third input — a per-row `nonce` — during 164-02's fix rounds. A route built to the original
spec mints links that **fail verification on the recipient route**, and the failure looks like a
revoked link rather than a bug. Corrected in Task 1 steps 5 and 6.

**Why the nonce exists**, so nobody removes it as noise: without it, `service_role` could DELETE a
share row and re-INSERT it, landing back on generation 1 and reproducing a byte-identical HMAC for a
link the owner had already revoked — including one killed by a GDPR erasure. MEASURED, twice, by two
different reviewers.

**What is now closed at the database level**, so the routes must NOT re-implement it:
- **N1** — an owner could drive `generation` to the bigint ceiling and wedge both revoke and their
  own Art. 17 erasure. A bounded-increment rule now caps every UPDATE at +1, so overflow is
  unreachable by construction. The route needs no guard.
- **N2** — ⛔ **founder ruling: NOT a defect.** Both RPCs are single statements; three interleavings
  across two concurrent sessions all converge. **Do not add `SELECT … FOR UPDATE`, retries, or
  advisory locks to these routes.** `revoked_at IS NULL` is the convergence contract, and the
  measured evidence is that the prescribed "fix" would have CREATED a counter-inflation bug.
- **R3** — a client-chosen starting counter on INSERT, closed by a trigger that covers `service_role`
  and BYPASSRLS roles the column grants never reach.

**Still true and still load-bearing:** everything about B15 ordering, 404-not-403, redacted
envelopes, soft-revoke-never-DELETE, and 404-as-convergence. Those were right when written and are
right now.

⚠️ **`F7`, inherited and now bounded.** `checkLimit` fails **OPEN** outside production
(`src/lib/ratelimit.ts` — gated on `VERCEL_ENV === 'production'`), so a preview deployment can mint
without limit. That was a live concern when this plan was written; per-environment
`SHARE_TOKEN_SECRET` (shipped 2026-08-28) means a preview-minted token **cannot** open a production
factsheet. Residual: unlimited minting against the preview's own data. Accepted, not fixed here.
</revision_note>
