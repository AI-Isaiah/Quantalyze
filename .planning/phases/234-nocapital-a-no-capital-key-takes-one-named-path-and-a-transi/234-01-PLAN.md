## Counting rules (one count per key per run)

- A key is counted at selection only if it would otherwise be a candidate: NULL anchor, a token in `_NO_CAPITAL_ANCHOR_REASONS`, a return day (`last_return_day`), and not in `departed_end_by_key`. Then: no stored terminal counts `no_stored_terminal`; a terminal level above `DUST_NAV_FLOOR` counts `funded_terminal`; otherwise the key becomes a candidate. A read-failure token is never counted (RESEARCH Pitfall 3).
- A candidate refused in the apply loop is counted there (`consumes_more_than_dust`) and nowhere else.
- A candidate that falls back in the compose is counted by the compose, once per owner key (a segmented key's units are one key).
- A whole-compose `NavReconstructionError` with candidates in play counts `compose_reverted` once per candidate in play (`len(no_capital_exit_by_key)`). The first compose's own counts are discarded with its payload; the stored-input compose has no candidates, so it adds none.
