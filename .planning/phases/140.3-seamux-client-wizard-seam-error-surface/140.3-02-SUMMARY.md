## Task 3 — TS-15, and the leak it exposed

### The forwarding, with three deliberately different failure directions

| Route | Direction | Why |
|---|---|---|
| `csv-finalize` (pre-existing) | fail **CLOSED** (401) | its SECURITY DEFINER RPC cannot run without `auth.uid()` |
| `keys/sync` (new) | **best-effort** | caller already authenticated, ownership already proven — an unreadable session must not fail a resync at the money-onboarding chokepoint |
| `verify-strategy` (new) | **public**: forward if a session exists, otherwise **nothing** | a fabricated value on an unauthenticated flow is elevation of privilege (T-140.3-02-02), asserted negatively |

### 🔴 THE FINDING — a live credential leak in the seam core, and a correction to 140.2-08's count

The plan required proving scrub coverage **by execution**, not by inferring it from the leaf's
existence. Driving a token-bearing transport error through the route produced **two** log lines:

```
[resilient-fetch] process-key-sync: network failure reaching the analytics service:
  Error: connect ECONNREFUSED … {"Authorization":"Bearer <redacted>",
  "X-User-Access-Token":"eyJhbGciOiJIUzI1NiIs…"}        ← LEAKING
[verify-strategy] /process-key upstream fetch threw:
  connect ECONNREFUSED … {"Authorization":"Bearer <redacted>",
  "X-User-Access-Token":"<redacted>"}                   ← correct (140.2-08)
```

The core's own transport arm called `scrubSeamError(err)` with **no per-request secrets**, so it
redacted `Authorization` (an env-list member) and shipped the JWT in the clear — **while its comment
claimed it removed "every credential undici inlined into the message."**

**This was LIVE, not latent, and it predates this plan.** `strategies/csv-finalize` has forwarded that
JWT through this exact core since Phase 19.1. 140.2-08's enumeration was of the **client's** log
sites and never reached the core's — the same syntax-vs-behaviour enumeration defect this programme
keeps hitting. Recorded in the TS-15 ledger row as a correction to that plan's count.

**Fixed as a CLASS, not a point fix.** `credentialHeaderValues()` **derives** the per-request secrets
from the outgoing headers the core was asked to send, so any credential-bearing header is scrubbed
whichever caller supplied it. A caller-declared `secrets: []` option would be convention — and a
caller who forgets is silently back to leaking, which is the exact failure mode this programme exists
to close.

**Examined and rejected as a class member, with the reason recorded rather than left implicit:**
`instrumentBody`'s body-read log site. It never receives `requestInit`, and a body-read rejection
carries no outgoing headers. Threading secrets into it would be a core-signature refactor with no
demonstrated leak behind it.

### Scrub coverage proven at BOTH routes

`keys/sync` already had `route.seam.test.ts` (real client + real core). `verify-strategy` had none —
its `route.test.ts` mocks the client wholesale on every case that reaches the seam, so TS-15's claim
is *unprovable* there. `src/app/api/verify-strategy/route.seam.test.ts` was created on the keys/sync
pattern. **Both halves of TRAP-1 are asserted at both routes**: the JWT is gone **and** `ECONNREFUSED`
survives. A one-sided assertion would ship an over-redacting scrubber green.
