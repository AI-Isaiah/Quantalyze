nested `service_error` envelope is structurally unreachable there (the branch requires `code` at the

grep for `detail ??` — the recurring defect class of this programme. Executing it as written would
import a leaf into a `"use client"` component for a body that can never be a seam envelope: dead code,
a new bundle edge, and a falsely-closed obligation.

**C-3 — `PortfolioImpactPanel.tsx` IS a real, uncovered member, and it is the OPPOSITE of a template.**

`{}` via `const body = parsedError.success ? parsedError.data : {}`, and `error`, `retryAfter` and

`undefined`, the component logs `"unrecognized error body shape"` and throws ``new Error(`HTTP
${res.status}`)``. On the exact envelope this plan exists to render, the named template throws away the
whole error body. **Copying its shape propagates the defect.**

The correct fix shape is the leaf itself applied to the **RAW** parsed JSON *before* any narrowing
schema — not a hand-rolled `typeof` branch, and not this panel's current shape.

`ErrorResponseSchema` has **exactly one production consumer** (`PortfolioImpactPanel.tsx`; verified —
the only other hits are its own declaration and type alias), so fixing the site closes the class
without touching the schema. Do **not** widen `errorSchema.ts` here: narrowing an *error*-body schema
is the documented Pitfall-3 hazard and the schema's `{}` fallback is correct for its own purpose.

**Both false claims are repeated in `analytics-service/docs/STATUS_CONTRACT.md` §2.1** (it names the
drawer as a site that "will render `[object Object]`" and names `PortfolioImpactPanel` as "the
