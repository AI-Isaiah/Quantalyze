<interfaces>
**TS-02 — the sharpened remedy.** Re-point the duplicate branch at `code === "WIZARD_DUPLICATE"`
ALONE, dropping the `queued` conjunct. That conjunct is now provably wrong in BOTH directions:
TS-01 established that `queued: true` and `WIZARD_DUPLICATE` co-occur on the resumed-wedge reply, so
`queued === false &&` silently SKIPS the duplicate branch on exactly the case that most needs it.
Deleting the branch outright is acceptable ONLY if resync is confirmed structurally unable to emit
the code (PYAPI-09d); re-pointing is the safer of the two and costs the same. Do not leave it
asserting a dead contract.

**TS-12** — branch on `upstream.ok === true` instead of sniffing `verification_id`. The rejection no
longer reaches the sniff at all (it returns at the `!result.ok` guard above), so the
`"Verification service returned an invalid response"` 502 rejection case is DEAD — delete it.

**TS-13** — same pattern in `csv-finalize`: branch on `ok`. **KEEP the `isUuid` check** — it is
defence in depth, not redundancy.

**M-6 (fold-in from the 140.1 code review) — the reason TS-14 is an `ok`-branch and not a status
branch.** `validate-only` answers **200 with `ok:false`** where `_scope_rejected` answers **403**, on
the IDENTICAL `not val.valid` predicate. It was judged a deliberate carve-out, but it contradicts the
contract and `STATUS_CONTRACT.md` records the exception nowhere. A consumer branching on STATUS is
therefore wrong on one of the two paths no matter which status it picks. Branching on `ok` is correct
on both. Record this provenance in the SUMMARY so the next reader does not "simplify" it back to a
status check.

**TS-14** — every consumer of the synchronous `/process-key` path (`teaser`, `csv`-with-strategy_id,
`internal_report`) must handle the envelope by `ok`, not by status, because ordinary validation
failures moved to 403 alongside the scope arms.

**TS-15 — the two routes that do NOT forward the user token today.** `csv-finalize` forwards it
(locate by `const userAccessToken = session?.access_token;` and the `userAccessToken,` argument);
`keys/sync` and `verify-strategy` do not. Forwarding makes a user-scoped, RLS-enforcing Supabase
pre-check possible on the Python side, so PYAPI-01's explicit ownership filter becomes
belt-and-braces rather than the only belt.

**TS-16 — RECORD only.** Treat `400` as CALLER unconditionally. It is the first status arriving from
a condition that used to be a 503, so a discriminator special-casing "was this previously an outage?"
would be wrong. Also `body.detail.correlation_id` now exists on three sites; SURFACING it is TS-20
and belongs to a later 140.3 plan, not this one.
