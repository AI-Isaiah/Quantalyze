## Summary

The race-loss RAISE is reachable deterministically. On a throwaway pg-lane cluster running the REAL 10-param body (the dedupe gate's apply list, which ends in `20260924230827`), the D-01 trigger pair made the call raise `40001` with `enqueue race lost: the winning job already advanced past the in-flight statuses`. The competitor was inserted once and flipped once. A second call then returned a fresh `pending` id, with exactly one in-flight row left. A generalized four-target version reached the same RAISE on an `api_key` target. **One correction to the CONTEXT's sketch is load-bearing.** The one-shot arm must be a SEQUENCE (`nextval` is non-transactional). A control table or a counter row is rolled back with the failing transaction on every retry. It would then re-arm the trigger on every PostgREST retry and manufacture an infinite loop that says nothing about the code.

PostgREST 14.x wraps every request in hasql-transaction's retrying transaction. That transaction re-runs the WHOLE transaction (BEGIN..COMMIT) on `40001` or `40P01`, immediately, with no bound and no backoff. The parent phase measured that loop on v14.5 and v14.7. PostgREST 16.0 removed the retry: PR #4222's test asserts a 40001 now comes back as HTTP 500 with `code` `40001`. Under 14.x, therefore, the race-loss raise is retried server-side, and the real-world retry converges because the winner is terminal. So the expected outcome of D-02 is "converges, keep 40001". It must still be MEASURED through the lane's PostgREST with K-shot arming. With K shots, PostgREST should answer HTTP 200 with a new id after exactly K+1 executions. The sequence counts those executions exactly, which is a stronger measurement than counting log lines.

Under PostgREST 14, the app-side helper (`retryOnceOnSerializationFailure`) never sees a 40001 from this site, because PostgREST absorbs it. The helper becomes live on PostgREST ≥ 16, where the 40001 reaches supabase-js as `error.code === "40001"`. That is the true reason it must stay (D-04). The CONTEXT's "a direct-Postgres caller can still get a 40001" is true for the SQL callers (pg_cron fan-outs that catch `serialization_failure`). It is not a reason for the TS helper, because supabase-js always goes through PostgREST.

**Primary recommendation:** Plan 01 replays the measured mechanism on the local-stack lane: psql first, then a K-shot PostgREST probe with K=1 and K=3 on `enqueue_compute_job`, which is csv-finalize's exact call. Add a negative control (unbounded arm) as the last probe, then `down`. Record the raw numbers (D-03). On "converges", plan 02 adds a both-lanes SQL gate `supabase/tests/test_enqueue_race_loss_40001.sql` with layered mutation twins against `20260924230827`, moves the census pins from one measured run, and corrects the comments in the TS helper and the two routes. No migration.

## Q2 — Deterministic induction (MEASURED on pg-lane)

### Postgres semantics, answered

| Question | Answer | Evidence |
|---|---|---|
| Does a competing row inserted by a BEFORE ROW trigger in the same transaction make `ON CONFLICT DO NOTHING` skip? | **Yes.** The BEFORE ROW trigger runs before the arbiter pre-check, and the pre-check sees the transaction's own uncommitted tuples. | MEASURED: `CALL1 state=40001`. The outer row was not inserted, so `v_new_id` was NULL and the path reached the RAISE |
| Does the statement-level AFTER INSERT trigger fire when DO NOTHING inserts 0 rows? | **Yes.** | [CITED: postgresql.org/docs/17/trigger-definition.html] "a statement that affects zero rows will still result in the execution of any applicable per-statement triggers". MEASURED `flips=1` |
| Does the re-read run after the AFTER statement trigger? | **Yes.** "Statement-level AFTER triggers fire at the very end of the statement" [CITED: same page], and the plpgsql re-read is a later statement with a fresh snapshot. | MEASURED: the re-read missed, so the RAISE fired |
| Can the flip happen inside the BEFORE trigger instead? | **No.** A row inserted and then updated to `done` by the same transaction before the pre-check leaves no live in-flight version, so the INSERT succeeds and nothing conflicts. The flip must come after the conflict check, which is why both triggers are needed. | Reasoned [ASSUMED]; consistent with the measurement |
| Recursion guard needed? | **Yes, on BOTH triggers.** The competitor INSERT fires the BEFORE trigger again, and its own end-of-statement fires the AFTER STATEMENT trigger, both at `pg_trigger_depth() = 2`. Without the guard on the AFTER trigger, the competitor would be flipped to `done` BEFORE the outer INSERT's conflict check, and the INSERT would simply succeed. | Guards `IF pg_trigger_depth() > 1` in both; MEASURED working |
| Does the partial index predicate match? | **Yes** for a competitor with `status 'pending'` and the same target and kind (any kind other than `compute_intro_snapshot` for strategy targets). | baseline.sql:13469 |
| Isolation sensitivity? | **None measured.** The same result was observed under REPEATABLE READ. The own-transaction competitor is exempt from ON CONFLICT's serializability visibility check. | MEASURED (RR variant: identical CALL1/CALL2/KSHOT lines) |
| Through PostgREST the retry re-runs the WHOLE transaction | so a transactional arm re-arms each time. **Use a SEQUENCE**: `nextval` survives ROLLBACK. | MEASURED: `shots` advanced 1 → 2 across a caught 40001 whose subtransaction rolled back the competitor |

### The induction objects (lane-only; Code Example 1)

- One schema `enq40001_probe`, not exposed to PostgREST, holding:
  - two sequences: `shots`, the one-shot counter, consumed only for armed targets; and `flips`, which proves the AFTER trigger ran;
  - an arm table `(target uuid, kind text, shots int)`, committed BEFORE the probe;
  - two trigger functions (SECURITY INVOKER; they run as `postgres`, the owner of the SECDEF enqueue function);
  - two triggers on `public.compute_jobs`.
- K-shot arming: the trigger induces while `nextval('shots') <= K`. So a call through PostgREST 14 should run K+1 times and then succeed. After the call, `shots.last_value = K+1` exactly, which counts executions. `flips` is also a sequence, so it survives every rollback too: expect `flips.last_value = K`, one flip per induced attempt.
- ⛔ **Reset both counters before EVERY probe** (`SELECT setval('enq40001_probe.shots', 1, false), setval('enq40001_probe.flips', 1, false);`), or read every counter as a before/after delta. The sequences are global across targets. Without a reset, a K=3 probe run after a K=1 probe starts at `nextval` 3, races once instead of three times, and still ends at `shots=4`. That counter would match its expectation by coincidence, and only the log count (1 instead of 3) would show the error.
- Removal: `DROP SCHEMA enq40001_probe CASCADE` drops the functions and, through dependency, both triggers. The lane `down` destroys everything anyway.

## Q3 — PostgREST 14 behaviour on SQLSTATE 40001

- **Retry semantics** [CITED: hasql-transaction `Sessions.hs` at 2a9a710, via the parent RESEARCH §"The retry source", lines 301-317, and the PostgREST issue #3673 body]: `inRetryingTransaction` is `fix $ \retry -> ...`. On SQLSTATE `"40001"` or `"40P01"` it calls `retryOrThrow`, which restarts from BEGIN. There is **no retry limit, no backoff, no sleep**, and the whole transaction re-runs.
- **Measured:** 164.9.4 run `36304648008` saw about 27k re-runs in about 9 s on v14.5 and about 29k on v14.7 (ROADMAP.md:3291-3292). 164.9.3.2-01 measured about 2,700-4,100 re-executions per second on v14.7, continuing after the client disconnected [VERIFIED: 164.9.3.2-01-SUMMARY.md].
- **Client view under 14.x:** the client never sees the 40001 while the loop runs. It sees HTTP 200 if a retry succeeds, and no answer if the condition never clears. If the retry eventually fails with a non-40001 error, it sees that error.
- **Fixed in 16.0** [VERIFIED: PostgREST CHANGELOG.md line 87 under `## [16.0] - 2026-08-07`: "Fix automatic transaction retries on `40001 (serialization_failure)` errors to prevent replication lag by @laurenceisla in #3673"]. The closing PR #4222 ("fix: do not retry transactions on `40001` SQL error", merged 2026-04-27) adds a test asserting `response.json()["code"] == "40001"` and `response.status_code == 500` [CITED: github.com/PostgREST/postgrest/pull/4222 files, test/io/test_replica.py]. So on ≥16 there is no retry at all, and the client gets HTTP 500 with `code: "40001"`. The 40* → 500 mapping matches the v14 docs table [CITED: docs.postgrest.org/en/v14/references/errors.html, "40\* | 500 | transaction rollback"].
- No `## [14.x]` entry through 14.18 (2026-09-10) mentions the fix. That rests on changelog silence, so "no 14.x carries the fix" is [ASSUMED] in general. It is measured only for 14.5 and 14.7.
- **Isolation:** PostgREST runs an RPC in READ COMMITTED unless the function sets one. No enqueue function does [ASSUMED for the default]. The RR variant above showed the same behaviour, so this does not matter.
- **Expected outcome of the measurement (prediction, not yet a fact):** K=1 should give HTTP 200, a uuid body, `shots=2`, one `enqueue race lost` ERROR line in the db log, wall time under 1 s, and one in-flight row for the target whose id equals the body. K=3 should give the same with `shots=4` and 3 log lines.
- **Negative control:** set K very large, for example `2147483647`. That should give `http=000` at the 20 s bound with `shots` still climbing after the client disconnects. It proves the probe can see a non-converging retry, and that the loop is the gateway's. It must be the LAST probe in a session, followed by `down`.

## Common Pitfalls

### Pitfall 1: a transactional one-shot arm manufactures the loop
**What goes wrong:** the arm is a control-table row or a counter UPDATE. PostgREST's retry rolls it back, the trigger re-arms, and the call loops forever. That looks exactly like "does not converge" and would wrongly trigger Branch B.
**How to avoid:** arm with `nextval()` on a sequence. Assert `shots.last_value = K+1` after an answered call.
**Warning signs:** `http=000` with K=1, or `shots` far above K+1.

### Pitfall 2: missing depth guard on the AFTER STATEMENT trigger
**What goes wrong:** the competitor's own INSERT ends its statement inside the BEFORE trigger. Its AFTER STATEMENT trigger flips the competitor to `done` before the outer INSERT's conflict check. The INSERT succeeds and nothing is induced.
**How to avoid:** `IF pg_trigger_depth() > 1 THEN RETURN NULL; END IF;` in the AFTER trigger, and `RETURN NEW` in the BEFORE trigger.

### Pitfall 3: a false-positive 40001
**What goes wrong:** a different 40001 source (a real serialization conflict) or an unrelated error is taken as the race-loss.
**How to avoid:** assert the SQLSTATE AND the `enqueue race lost` message prefix AND `flips=1`. Count db-log lines on the exact message, not on `40001`.

### Pitfall 4: probing a wrapper whose own guard answers first
**What goes wrong:** `_assert_owner` and the XOR guards refuse before the INSERT. 164.9.3.2 hit this with A2 (22023 in 3 ms).
**How to avoid:** use a real seeded strategy and csv-finalize's exact call shape: `enqueue_compute_job` `{p_strategy_id, p_kind:"compute_analytics_from_csv", p_metadata:{source:"enq40001-probe"}}` with the service-role key. `_assert_owner` short-circuits for service role (dedupe gate comment, lines ~147-150).

### Pitfall 5: lane poisoning and public-repo leaks
**What goes wrong:** the negative control keeps looping after curl gives up, and probe output carries machine paths.
**How to avoid:** run the negative control last, then `run.sh down`. Hold the host lane lock (`$LANE_LOCK` from the orchestrator) for the whole session. Paste only `http=`, `real=`, counters and log counts. Strip `psql:<path>:` prefixes.

### Pitfall 6: a stale gate when the rest image moves to 16
**What goes wrong:** a CI-wired PostgREST assertion fails on a CLI bump.
**How to avoid:** keep the PostgREST probe out of CI (above), and record the image tag (`docker ps --format '{{.Image}}'` filtered to postgrest) beside every measurement.

## Code Examples

### 1. Lane-only induction objects (measured on pg-lane; psql as `postgres`, COMMITTED for the PostgREST probe)

```sql
-- Source: this research's pg-lane probe (generic four-target version, measured)
CREATE SCHEMA enq40001_probe;
CREATE SEQUENCE enq40001_probe.shots;      -- non-transactional one-shot counter
CREATE SEQUENCE enq40001_probe.flips;
CREATE TABLE enq40001_probe.arm (target uuid NOT NULL, kind text NOT NULL, shots int NOT NULL,
                                 PRIMARY KEY (target, kind));

CREATE FUNCTION enq40001_probe.before_ins() RETURNS trigger LANGUAGE plpgsql AS $f$
DECLARE v_shots int;
BEGIN
  IF pg_trigger_depth() > 1 THEN RETURN NEW; END IF;
  SELECT a.shots INTO v_shots FROM enq40001_probe.arm a
   WHERE a.target = COALESCE(NEW.strategy_id, NEW.portfolio_id, NEW.allocator_id, NEW.api_key_id)
     AND a.kind = NEW.kind;
  IF NOT FOUND THEN RETURN NEW; END IF;
  IF nextval('enq40001_probe.shots') > v_shots THEN RETURN NEW; END IF;
  INSERT INTO public.compute_jobs (strategy_id, portfolio_id, allocator_id, api_key_id, kind, status, metadata)
  VALUES (NEW.strategy_id, NEW.portfolio_id, NEW.allocator_id, NEW.api_key_id, NEW.kind, 'pending',
          '{"enq40001_probe":"competitor"}');
  RETURN NEW;
END $f$;

CREATE FUNCTION enq40001_probe.after_stmt() RETURNS trigger LANGUAGE plpgsql AS $f$
DECLARE n int;
BEGIN
  IF pg_trigger_depth() > 1 THEN RETURN NULL; END IF;
  UPDATE public.compute_jobs SET status = 'done'
   WHERE metadata->>'enq40001_probe' = 'competitor'
     AND status IN ('pending','running','done_pending_children');
  GET DIAGNOSTICS n = ROW_COUNT;
  IF n > 0 THEN PERFORM nextval('enq40001_probe.flips'); END IF;
  RETURN NULL;
END $f$;

CREATE TRIGGER enq40001_probe_bi BEFORE INSERT ON public.compute_jobs
  FOR EACH ROW EXECUTE FUNCTION enq40001_probe.before_ins();
CREATE TRIGGER enq40001_probe_ai AFTER INSERT ON public.compute_jobs
  FOR EACH STATEMENT EXECUTE FUNCTION enq40001_probe.after_stmt();
```
In the SQL gate, the same objects are created inside the gate's `BEGIN ... ROLLBACK`, so nothing survives. Column values used above (`'pending'`, `'done'`, `'done_pending_children'`, `'running'`) are verbatim from `compute_jobs_status_check` [VERIFIED: baseline.sql:1407].
