## The shape this file forced into the open

Fourteen of the 25 sections live in Parts 2 and 3, which run **after** Part 1's
twenty-odd textual assertions over the same deployed body. So a Part-2 twin must
preserve every count Part 1 makes while changing what a real tick WRITES. Two
devices carry that:

- **branch the SET expression.** `error_kind = CASE WHEN TRUE THEN 'unknown'
  ELSE 'orphaned' END` leaves `'orphaned'` in the body exactly twice — so Part 1
  and migration `20260826140000`'s own STEP 5 (d) both stay satisfied — while the
  row is written with `'unknown'`. That is precisely the gap the gate's own
  comment describes: *"Part 1 proves the deployed TEXT says orphaned, this proves
  a real tick actually WROTE it."* The same device on `last_error` writes NULL
  while the fixed audit literal stays in the body.
- **arithmetic on the literal, never the literal.** `interval '4 hours' / 4` and
  `interval '48 hours' / 48` keep both window counts at 1 while collapsing the
  thresholds, so only a seeded row at the boundary can tell.

`2/arm C/JOB-05` is worth calling out: this file's own HONESTY note says arm C is
dominated by arm B for any MONOTONE threshold, and that a body taking C but not B
must be age-INVERTED, which fails arm A first. Its twin is the third possibility
the note does not name — a NON-monotone predicate (`claimed_at < now() -
interval '4 hours' OR claimed_at > now() - interval '1 minute'`) — under which
the century-old claim and the 3h tail both behave and only the row claimed this
instant moves. The note is now checkable rather than merely stated.

## ⛔ THE BLOCKER: `3/JOB-05` has no first-failure mutation

This is the plan's one incomplete item and it is a **founder decision**, not
something to be worked around.

`test_retention_orphaned_running.sql` carries **three copies of one registration
guard** — Part 1's `1/JOB-05`, then `2/JOB-05`, then `3/JOB-05` — each dominated
by the one before it. For the third to be the FIRST failure, Part 2 must PASS
(so `cron.job.command` was non-NULL when it read) while Part 3 reads NULL. That
requires `cron.job` to change between two reads separated only by a transaction
Part 2 **rolls back**. Two routes were driven on real lanes:

| route | measured |
|---|---|
| unschedule the job + `neuter` Part 1's dominators + `neuter` `2/JOB-05` | Part 1 passes, and Part 2 then reaches its oracle call: `psql:…:932: ERROR: 22004: query string argument of EXECUTE is null`. A raw driver error that names no arm — scored `NO-IDENTITY`. `2/JOB-05` is not a duplicate raise; it is Part 2's **precondition**. |
| a cron body that unschedules ITSELF (no `DELETE` keyword, so Part 1's ban does not see it) | Part 2 goes fully green (`Part 2 OK` printed), but the unschedule is transactional: Part 3 reads the row back and its second tick dies on `XX000: could not find valid entry for job 'retention_compute_jobs_orphaned_running'`. |

Adding a `RETURN` after Part 2's RAISE to fix the control flow under a neuter is
refused by the runner itself, deliberately — `neuterArm` (`run.mjs:1658-1674`)
will not neuter a branch carrying a statement after its RAISE, because in the
original file that statement is unreachable and neutering would make it execute.

`2/JOB-05` itself DOES bite, with a nine-entry `neuter` chain read off the
runner's own first-failure report rather than reasoned out: five entries walk
`1/JOB-05`'s repeated raise sites (`neuterArm` suppresses the FIRST raise
carrying an identity, so reaching a later one means repeating the entry) and
three walk `1/JOB-05/D-19`'s, which fires because `regexp_matches(NULL, …)`
returns zero rows and the `LIMIT 100` count comes back 0.
