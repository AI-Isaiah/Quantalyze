## Summary

The phase turns on one question — **real pg_cron or a shim** — and the measurement answers it
unambiguously in favour of **real pg_cron**. Three findings carry the phase:

1. **The majors AGREE.** `ubuntu-24.04` runners ship **PostgreSQL 16.15**
   `[VERIFIED: actions/runner-images Ubuntu2404-Readme.md via gh api]`; this box has **16.13**
   `[VERIFIED: pg_config --version, this session]`. Same MAJOR — so the CI job and the authoring
   box measure the same corpus, which is success criterion 1. The `brew info pg_cron` scare in
   CONTEXT is real but **routes around**, not blocks: Homebrew's formula builds only against
   `postgresql@17` and `@18`, but pg_cron 1.6.7 **compiles and installs cleanly against
   `postgresql@16` from source**, which I did and then loaded.
2. **The preload cost is ZERO within noise.** Measured A/B on this box, 5 iterations each, same
   harness: **without preload mean 0.737 s/lane, with `shared_preload_libraries=pg_cron` mean
   0.746 s/lane** — a +0.009 s delta whose ranges overlap. `-o` on the single `pg_ctl` start is
   sufficient; no restart, no `postgresql.conf` edit, no initdb-time step.
3. **The timing risk is the ARM COUNT, not pg_cron.** The five files add ~105 sections and 5 files
   ⇒ ~455 legs, projecting **~10.3 min at the worst observed 1.07 s/leg**. That crosses the
   ci.yml comment's own "raise only when a MEASURED run reaches ~10 minutes" rung. `timeout-minutes`
   almost certainly moves 15 → 20 in this phase, and 20 is the recorded CEILING — the next step
   after that is the subset-mode split, not another raise. **Plan for that explicitly.**

One finding contradicts a premise in the ROADMAP fallback. The five gates do **not** merely probe
`pg_extension`; three of them read **`cron.job.command` as an ORACLE** for the deployed job body. A
shim would therefore have to implement `cron.schedule()` writing a faithful `cron.job` row — not
"the `cron` schema and a few catalog rows". Since the real extension costs nothing measurable, the
shim's only remaining argument is gone.

**Primary recommendation:** take **real pg_cron**. Thread
`-c shared_preload_libraries=pg_cron -c cron.database_name=postgres` into the existing `-o` string
at `scripts/pg-lane/run.sh:255`; install `postgresql-16-cron` via apt in the `sql-mutation` job;
document a source-build step for macOS because Homebrew cannot serve `@16`.

## Q1 — Version matching and availability

### macOS (authoring box)

`[VERIFIED: brew info pg_cron + the formula source, this session]` Homebrew `pg_cron` is **stable
1.6.7**, and its formula declares:

```ruby
depends_on "postgresql@17" => [:build, :test]
depends_on "postgresql@18" => [:build, :test]
depends_on "libpq"
```

It installs one `.so` per dependency into `lib/postgresql@17` and `lib/postgresql@18`. **There is no
`@16` artifact.** CONTEXT's warning is confirmed and is not a version-drift artefact — it is what
the formula says.

⚠️ Note the deps are `:build, :test` only, so `brew install pg_cron` would **not** uninstall or
unlink `postgresql@16` — it is safe under the system-install policy. It would simply be **useless**:
an `.so` built for PG17/18 will not load into a 16.13 postmaster.

**The route that works, MEASURED.** pg_cron 1.6.7 builds against `postgresql@16`:

```bash
PGC=/opt/homebrew/opt/postgresql@16/bin/pg_config
SDK=$(xcrun --show-sdk-path)
CPP=$($PGC --cppflags | sed 's|-isysroot [^ ]*||')
LDF=$($PGC --ldflags  | sed 's|-isysroot [^ ]*||')
make install PG_CONFIG=$PGC PG_LDFLAGS=-lintl \
     CPPFLAGS="$CPP -isysroot $SDK" LDFLAGS="$LDF -isysroot $SDK"
```

Result: `pg_cron.dylib: Mach-O 64-bit bundle arm64`, installed, loaded, `CREATE EXTENSION pg_cron`
succeeded and `cron.schedule(...)` inserted a `cron.job` row `[VERIFIED: this session]`.

⚠️ **Three non-obvious build facts the plan must carry, each measured as a failure first:**

- `PG_LDFLAGS=-lintl` is required on macOS (pg_cron issue #269) — the Homebrew formula sets it too.
- **The keg's `pg_config` reports a STALE SDK.** It emits
  `-isysroot /Library/Developer/CommandLineTools/SDKs/MacOSX26.sdk`, which **does not exist on this
  box** (present: `MacOSX.sdk`, `12.1`, `14.5`, `14`, `15.5`, `15`). Both `CPPFLAGS` and `LDFLAGS`
  must be sanitised — overriding only one gets you past compile and then fails at link with
  `ld: library 'System' not found`. `COPT=` does **not** work: the stale flag comes from `CPPFLAGS`,
  which clang sees last, and last `-isysroot` wins.
- ⛔ **PostgreSQL 16 has no `extension_control_path` GUC** (that is PG18). The `.control` file
  **must** live in the real sharedir, so the macOS install necessarily writes into the
  `postgresql@16` keg. A scratch-prefix install is NOT viable for the control file on 16. The
  `.dylib` alone could be preloaded by absolute path, but `CREATE EXTENSION` could not run — and
  the gates need the extension, not just the worker.

## Q2 — Does `-o` suffice, or is a restart needed?

**`-o` suffices. MEASURED.** `[VERIFIED: this session]`

```
pg_ctl -D $D/data -o "-p $P -c listen_addresses=127.0.0.1 -k '' \
   -c shared_preload_libraries=pg_cron -c cron.database_name=postgres" -w start
```

then, in that same cluster:

```
CREATE EXTENSION pg_cron;                              -- succeeded
SELECT extname FROM pg_extension WHERE extname='pg_cron';   -- 1 row
SELECT cron.schedule('probe-job','35 * * * *','SELECT 1');  -- succeeded
SELECT jobname, schedule, command FROM cron.job;
--  probe-job | 35 * * * * | SELECT 1
```

Why no restart is needed: `shared_preload_libraries` requires a restart only because it cannot be
changed in a *running* cluster. The lane starts its postmaster **exactly once per invocation**
(`run.sh:255`), so the value is present at the only start that ever happens. No `postgresql.conf`
edit, no initdb-time step, no second `pg_ctl` cycle.

**On `cron.database_name`:** it names the database the background worker connects to for its job
table. `postgres` is the lane's database, so the default is already correct — but state it
explicitly rather than rely on the default, because pg_cron's default *is* `postgres` today and a
silent default is exactly the class of claim this phase family exists to refuse.

**On what the worker's presence alone buys:** ⚠️ nothing the gates need. The bgworker starting does
**not** create the extension, and `CREATE EXTENSION pg_cron` is what puts the row in `pg_extension`
that four of the five gates probe. The extension **must** be CREATEd — which means it belongs in
each gate's `RED-UNDER-SETUP` apply list (or a lane-level bootstrap), not merely in the `-o` string.
Conversely, `CREATE EXTENSION pg_cron` **fails** without the preload (pg_cron refuses to load
outside `shared_preload_libraries`), so both halves are required.

**Also required, and easy to miss:** `cron.schedule()` writes to `cron.job`, and the three
oracle-reading gates need those rows. So the apply list must include the *migrations that schedule
the jobs* — `20260816140000_reconcile_dropped_enqueue_sweep.sql` (`PERFORM cron.schedule(` at :711),
`20260802120000_strategy_analytics_stuck_computing_reaper.sql`,
`20260719120000_retention_orphaned_running_compute_jobs.sql` and their successors
(`20260819130500`, `20260819150000`, `20260720120000`, `20260803130000`) `[VERIFIED: grep -rln
'cron.schedule' supabase/migrations/, this session]`. Those migrations also carry
self-verification blocks that RAISE if the schedule is wrong — they are part of the apply cost, and
the plan should expect apply-list discovery to be the real work per file, exactly as the 164.4-00
spike found.

1. ⛔ **No gate exercises cron SCHEDULING BEHAVIOUR.** The single `cron.job_run_details` mention is

holds whatever the migration in the apply list just scheduled — the oracle and the subject share a
source. The arms still **prove falsifiability** (which is all this phase claims), but they prove
less about deployment drift on the lane than on TEST. Say so in the annotations rather than let a
future reader infer otherwise.

## Q5 — Ordering constraint for success criterion 3

**The mechanism, read at HEAD** `[VERIFIED: scripts/mutation-runner/run.mjs:2881-2930, this
session]`: `logCorpusClassification` prints `lane-blocked:` from `corpus.laneBlockedFiles`, then —
only when `laneProbe !== null` — prints
`lane-probe: pg_cron AVAILABLE — lane-blocked class is STALE` on `laneProbe.available === true`.
`"lane-blocked-stale"` is a registered GATE defect kind `[VERIFIED: run.mjs:1082, quoted: "the lane
CAN host pg_cron while idiom files are still classified `lane-blocked`"]`, so the run exits 1.

Critically, classification applies to **UNANNOTATED** files `[VERIFIED: parse.mjs:1055-1060, quoted:
"Which of four idiom classes an UNANNOTATED gate file falls in"]`. So **annotating the four files
empties `laneBlockedFiles` by itself** — no classifier edit is needed to clear the tripwire.

**That gives a genuine ordering problem:** the interval between "pg_cron available" and "four files
annotated" is a state in which `sql-mutation` **exits 1**. Landing that interval as a commit reddens
the aggregator; collapsing it into one commit means the tripwire is never observed, which fails
criterion 3.

**Recommended resolution — make the observation PERMANENT rather than momentary:**

- **Task A (evidence, not a red main).** Add a **runner self-test arm** that drives
  `logCorpusClassification` / the defect path with a synthetic corpus
  (`laneBlockedFiles` non-empty, `laneProbe.available === true`) and asserts exit 1 naming
  `lane-blocked-stale`. This EXERCISES the tripwire on every push, forever — which is stronger than
  a one-shot observation and matches the house pattern the phase family already uses (red/green
  fixture pairs, `lint-sql-gates.mjs:37-40`). ⭐ **This is the durable answer to criterion 3.**
- **Task B (the dated observation).** In the SAME PR, capture a **local** run of the real corpus in
  the intermediate state — pg_cron available on the lane, the four files not yet annotated — showing
  the `lane-probe: … AVAILABLE` line, the `lane-blocked-stale` defect and exit 1. Commit that log as
  a fixture / quote it in the plan's evidence. This is the "shown to fire" half, obtained without
  ever pushing a red commit.
- **Task C.** Land the preload (`run.sh`) + CI install + the annotations of the four
  `lane-blocked` files, so `lane-blocked: 0` and the run is green at the PR head.
- **Task D.** `test_compute_jobs_error_kind_copy_parity.sql` — the `pending:` one — with the parser
  pin updated to the newly MEASURED set (locked decision 4: deliberately, measured, never loosened
  to "any set"). If the set becomes empty, the pin must assert **empty as a measured fact**, not be
  deleted.

⚠️ Ordering hazard to name in the plan: **Task C's `run.sh` change alone flips the probe**, so any
commit that lands the preload without the annotations is red. Keep the preload and the annotations
in one commit, with A and B carrying the proof.

## Q6 — `[REDUNDER-LANEBLOCKED-BLIND]`, honestly costed

`gateNeedsPgCron(text)` scans only the gate's own statements for a `pg_extension` probe naming
pg_cron `[VERIFIED: parse.mjs:1043-1049, quoted: `if (!PG_CRON_CATALOG_RE.test(stmt.executableText))
continue;`]`. It is blind to the `RED-UNDER-SETUP` apply list, which is why the fifth file printed
under `pending:`. Its tripwire is the parser test's "names the 4 lane-blocked files EXACTLY" arm,
which flips the day either half resolves.

| Option | What it is | Cost | Verdict |

## Common Pitfalls

### Pitfall 1: `.so` major mismatch reads as "extension not found"
**What goes wrong:** `brew install pg_cron` succeeds, then `CREATE EXTENSION pg_cron` fails with a
control-file error — because the artifacts landed under `lib/postgresql@17`, not `@16`.
**How to avoid:** assert `pg_config --version` major and the install path in the same step.
**Warning sign:** `Could not open extension control file ".../postgresql@16/.../pg_cron.control"` —
byte-identical to the "not installed at all" message TODOS `[REDUNDER-PGCRON]` records.

### Pitfall 2: the stale-SDK build failure looks like a broken toolchain
**What goes wrong:** the keg's `pg_config` emits `-isysroot .../MacOSX26.sdk`, absent on this box.
**How to avoid:** sanitise BOTH `CPPFLAGS` and `LDFLAGS` (§ Q1). Fixing only one gets you a
compile-clean, link-broken `ld: library 'System' not found`.

### Pitfall 3: preloading without CREATE EXTENSION (or vice versa)
**What goes wrong:** the bgworker starts, `pg_extension` stays empty, gates still RAISE. Or
`CREATE EXTENSION` fails because pg_cron refuses to load outside `shared_preload_libraries`.
**How to avoid:** both halves, always. Assert the `pg_extension` row, not the worker.

### Pitfall 4: the tripwire reddens `main` between commits
**What goes wrong:** landing the preload before the annotations. § Q5.
**How to avoid:** self-test arm + local log fixture for the observation; preload and annotations in
one commit.

### Pitfall 5: pinning a floor from prose
**What goes wrong:** the ~105 in § Q4 is a crude `sort -u` count, and this file says so.
**How to avoid:** ratchet `FILES_FLOOR`/`ARMS_FLOOR` to the runner's own `coverage:`/`arms:` lines.

### Pitfall 6: the macOS install is invisible provisioning
**What goes wrong:** it works on this box because I installed it by hand today. A fresh clone has
nothing.
**How to avoid:** ship the build as a scripted, documented step and have the lane **fail loud** with
a named diagnosis when pg_cron is absent — never silently degrade.

  vacuity shape this phase family exists to refuse.
- **§ Q1:** the macOS/ubuntu split that would have justified a shim **does not exist**. Both are

**What was NOT obtainable, stated plainly:** I could not execute
