### CR-01: `2/JOB-04`'s recorded "no production mutation can make this raise fire first" is FALSE — measured on a real lane

**File:** `supabase/tests/test_reconcile_dropped_enqueue_sweep.sql:769-787` (prose + twin), raise at `:788`

**Issue.** The arm's `RED-UNDER` prose states, as a measurement:

> *"So no production mutation can make this raise fire first, and the honest falsifier is
> the one that breaks the precondition it asserts."*

and on that basis the twin at `:786` mutates **the gate file's own oracle lookup**
(`jobname = 'reconcile_dropped_enqueue_sweep'` → `'reconcile_dropped_enqueue_sweep__no_such_job'`).
That mutation has no production preimage: no change to any migration, schema object or
deployed body produces it. The arm is nevertheless counted as biting and is folded into
`ARMS_FLOOR = 363`.

The recorded measurement tried exactly two routes (renaming the `cron.schedule` call in
`20260819150000`, and short-circuiting that migration's STEP 2). It did **not** try the
route that this phase's own plan 03 used, three plans earlier, for the structurally
identical guard `2/JOB-05` in `supabase/tests/test_retention_orphaned_running.sql` — a
live-DB `sql` step plus a `neuter` of the dominating Part 1 arm:

```json
{"arm":"2/JOB-05",
 "apply":[{"kind":"sql","stmt":"DELETE FROM cron.job WHERE jobname = 'retention_compute_jobs_orphaned_running'"}],
 "neuter":[{"arm":"1/JOB-05"}, … ]}
```

**Measured refutation, 2026-09-05, real pg-lane, PostgreSQL 16.13 + pg_cron 1.6.** I copied
the gate to a scratch dir, commented out the 15 `RAISE EXCEPTION 'TEST FAILED (1/JOB-04)…'`
statements (exactly what the runner's `neuter` primitive does), built the apply list from
the file's own `RED-UNDER-SETUP`, and ran `scripts/pg-lane/run.sh` with a `--post-apply`
containing one statement — the production-shaped regression the arm's own message names
("the job was unscheduled out of band"):

```sql
DELETE FROM cron.job WHERE jobname = 'reconcile_dropped_enqueue_sweep';
```

Result — lane exit 3, and the FIRST and only failure is this arm, raised directly from the
gate's own DO body:

```
psql:<scratch>/gate.sql:1280: ERROR:  P0001: TEST FAILED (2/JOB-04): the
reconcile_dropped_enqueue_sweep cron job is missing while pg_cron is installed.
A missing sweep is a red gate, never a skip.
```

So an honest, production-shaped first-failure mutation exists, is already the idiom in this
corpus, and was never tried. The gate-self-mutation is an unnecessary weakening of an arm
that could carry a real one.

The prose also cites *"Same class as the S-2 seed-integrity precedent in
test_strategy_analytics_stuck_computing_reaper.sql (plan 164.4.1-04)"*. That citation is
wrong: `4a/seed`'s twin mutates `supabase/migrations/20260802120000…` and
`…20260803120000…` — two migrations — not the gate. It is not the same class.

**Failure scenario this leaves open.** Migration `20260816140000` (or a later rewrite of the
`cron.schedule` call) stops registering `reconcile_dropped_enqueue_sweep` under that exact
name. `2/JOB-04` is the assertion nominally responsible for noticing at Part 2 — but the
only mutation ever proven to make it bite is one that breaks the test's own SELECT, so the
corpus has never demonstrated that this arm reacts to anything in production. Meanwhile the
biting count that `ARMS_FLOOR` protects is +1 for it.

**Fix.** Replace the gate-self twin with the measured one (arm names in `neuter` repeat once
per raise carrying that identity, as `2/JOB-05` already does — 15 raises carry `1/JOB-04`):

```json
-- RED-UNDER-M: {"arm":"2/JOB-04","apply":[{"kind":"sql","stmt":"DELETE FROM cron.job WHERE jobname = 'reconcile_dropped_enqueue_sweep'"}],"neuter":[{"arm":"1/JOB-04"}, … x15 ]}
```

and rewrite the prose: the two routes it recorded as failing did fail, but the conclusion
drawn from them ("no production mutation can make this raise fire first") does not follow
and is now measured false. Re-run the file; `biting` should stay 39.

Then update the two per-file rows and floors in
`src/__tests__/mutation-runner-floors.test.ts` and `src/__tests__/gate-family-meta.test.ts`.

Separately, and worth a founder call rather than an executor edit: reclassification and

### WR-04: `PGBIN_CHECKED` is an undocumented env-var bypass of the install script's safety guard, and the guard false-refuses when `PGBIN` is set explicitly

**File:** `scripts/pg-lane/install-pg-cron-macos.sh:81-92`

**Issue, two halves.**

1. `if [ -z "${PGBIN_CHECKED:-}" ] && command -v pg_ctl …` — `PGBIN_CHECKED` is set nowhere
   in the repo (`grep -rn PGBIN_CHECKED .` → this line only), appears in no `--help` text and
   in no comment. It is a silent kill switch for the one guard standing between "installed
   pg_cron" and "installed pg_cron next to binaries the lane never boots" — the exact
   silent-degrade shape the phase exists to remove.
2. The guard fires even when the caller set `PGBIN` explicitly. `scripts/pg-lane/run.sh:252`
   honours `PGBIN` first (`if [ -z "${PGBIN:-}" ]; then PGBIN=$(resolve_pgbin)`), so with
   `PGBIN` exported the lane and this script agree by construction and there is nothing to
   refuse. The comment at `:77-80` describes only the `PGBIN`-unset case.

**Failure scenario.** A fresh macOS box with Homebrew's default `postgresql` (18) linked onto
PATH and keg-only `postgresql@16` beside it. The operator does the correct thing —
`PGBIN=/opt/homebrew/opt/postgresql@16/bin bash scripts/pg-lane/install-pg-cron-macos.sh` —
and is refused, with remediation text telling them to set `PGBIN` to the PATH directory,
which then trips the `REQUIRED_MAJOR=16` refusal at `:96-103`. The documented escape is an
env var they cannot discover.

**Fix:** scope the guard to the case it reasons about, and document the override:

```bash
if [ -z "${PGBIN_EXPLICIT:-}" ] && [ -z "${PGBIN_ORIGINAL:-}" ] && command -v pg_ctl >/dev/null 2>&1; then
```

i.e. record whether `PGBIN` came from the environment before `resolve_pgbin` runs, skip the
guard when it did, and either delete `PGBIN_CHECKED` or list it in the `--help` header.

### IN-04: CI picks the HIGHEST PostgreSQL major, the lane picks the FIRST

**File:** `.github/workflows/ci.yml:1003` vs `scripts/pg-lane/run.sh:86`

`major=$(ls -d /usr/lib/postgresql/*/bin | awk -F/ '{print $5}' | sort -n | tail -1)` takes
the highest major; `resolve_pgbin`'s glob fallback takes the first match (lexical, so the
lowest). On a runner image carrying both 16 and 17 the provisioning step would install
`postgresql-17-cron` and MEASURE_FAIL on `!= 16`, while the lane would have booted 16. The
disagreement fails loud rather than silently, so it is Info — but the two selectors should
be one. **Fix:** have the CI step resolve through the same rule (`| sort -n | head -1`) or,
better, print `PGBIN`'s own `pg_config --version` and key the apt package off that.
