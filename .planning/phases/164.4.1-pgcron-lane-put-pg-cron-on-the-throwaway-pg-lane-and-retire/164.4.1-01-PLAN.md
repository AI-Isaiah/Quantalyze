This plan is the substrate half of the phase and it leads with the tracer: ONE lane, preload threaded through the ONE `pg_ctl -o` string, `CREATE EXTENSION pg_cron` from the repo's own enabling migration, one `cron.schedule`, one `cron.job` read-back — end to end on the real script. **D-06 is settled by RESEARCH's measurement and this plan records it, not re-argues it:** real pg_cron, because the isolated A/B measured the preload at +0.009 s/lane (0.737 → 0.746 s, ranges overlapping) and § Q3 showed three gates read `cron.job.command` as an oracle, which a shim would have to reimplement by the same hand as the claim. Task 1 re-measures per-lane cost BEFORE and AFTER on this box so the decision is dated at this commit, not inherited from prose.

**Where `CREATE EXTENSION` lives (RESEARCH Open Question 2, decided):** in the gates' `RED-UNDER-SETUP` apply lists, via the repo's REAL migration `supabase/migrations/20260513094906_enable_pg_cron.sql` (`CREATE EXTENSION IF NOT EXISTS pg_cron;` at `supabase/migrations/20260513094906_enable_pg_cron.sql:17`). Not a lane-level bootstrap and not a new fixture: the corpus discipline is that a gate declares what it needs, the migration is the platform's own record of enabling the extension, and a fixture doing it would be a stand-in for something the repo already carries for real. The lane itself carries ONLY the preload GUCs — shared_preload_libraries cannot be set after start, so it is the one thing that must be substrate.

**Why `cron.max_running_jobs=0` joins the two RESEARCH GUCs (Claude's discretion, measured):** pg_cron 1.6.7 declares the GUC with minimum 0 (`DefineCustomIntVariable("cron.max_running_jobs", …, 0, MaxConnections, …)` in its `pg_cron.c`), and at 0 the launcher never starts a job. Without it a lane whose apply list schedules a `*/15 * * * *` reaper and happens to straddle :00/:15/:30/:45 would run that job body concurrently with the gate; the gates tolerate live ticks on TEST by design, but a mutation gate whose whole verdict is FIRST-failure identity should not carry a 1-in-900-per-lane nondeterminism it can delete for free. `cron.schedule` still inserts the `cron.job` row the gates read.
