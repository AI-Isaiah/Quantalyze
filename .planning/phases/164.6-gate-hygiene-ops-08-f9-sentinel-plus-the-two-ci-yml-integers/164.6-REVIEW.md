## Warnings

### WR-01: The Python parity oracle ignores any marker added to `LEDGER_REFRESH_JOB_SOURCES` beyond the two named constants

**File:** `src/lib/ledger-refresh-marker.test.ts` — `PYTHON_LEDGER_REFRESH_JOB_SOURCES`, and the
"the TS marker set equals the set Python honours" case.

**Issue:** The oracle captures the `frozenset(...)` body, but it only checks that both constant
NAMES appear in it. It then returns `new Set([single[1], composite[1]])`, built from the two
single-line constants. It never enumerates what the union actually contains. The TS JSDoc
promises "a marker added on one side cannot silently go unretracted on the other", and that is
exactly the case the pin misses.

**Scenario, measured with the test's own regexes against `job_worker.py`:** I rewrote the union to
`{LEDGER_REFRESH_SINGLE_KEY_SOURCE, LEDGER_REFRESH_COMPOSITE_SOURCE, "ledger-refresh-mt5"}`. The
captured body contains the third member, but the oracle still returns
`['ledger-refresh', 'ledger-refresh-composite']`. So the parity case, and the
`.size).toBe(2)` anti-vacuity case, both stay green. Python would honour a third marker, but
`retractInheritedRefreshMarker` would not retract it. That puts a stale factsheet over a failed
user resync, which is the data-integrity class 161.1-D13 exists for. A test that cannot fail for
its stated purpose is a false pin on a data-integrity gate.

**Fix:** Derive the oracle from the union's MEMBERS, and fail on anything the parser cannot
resolve:

```ts
const body = union[1].replace(/[{}\s]/g, "");
const consts = new Map<string, string>();
for (const m of py.matchAll(/^(LEDGER_REFRESH_\w+_SOURCE): Final\[str\] = "([^"]+)"$/gm)) {
  consts.set(m[1], m[2]);
}
const members = body.split(",").filter(Boolean).map((tok) => {
  const lit = /^"([^"]+)"$/.exec(tok);
  if (lit) return lit[1];
  const v = consts.get(tok);
  if (v === undefined) throw new Error(`161.1-D13 parity oracle: unresolvable union member ${tok}`);
  return v;
});
return new Set(members);
```

Keep the `size`/`has` anti-vacuity case. Add a red demo that appends a third member to a copy of
the source and asserts that the oracle's size becomes 3.

### WR-02: The runbook's "did a candidate fail this tick?" query has no time window, so "Expected: zero rows" stops being true after the first failure, permanently

**File:** `docs/runbooks/ledger-refresh-go-live.md`, subsection "Did a candidate fail to enqueue
this tick? (Phase 164.6, OPS-08-F2)".

**Issue:** The query filters only on `cron_name` and `error`, orders by `completed_at DESC`, and
applies `LIMIT 5`. `cron_runs` has no purge (migration-reviewer LOW). So once any tick in PROD
history has written a failure row, the query returns rows forever. The heading asks about "this
tick", but the query cannot answer that, and "Expected: zero rows" becomes false for a healthy
system. The sibling query directly above it ("enqueued_this_tick") does bound itself with
`created_at > now() - INTERVAL '65 minutes'`. The new query breaks that convention.

The bullet also says a failing tick writes "**exactly one**" row. A failed instrument INSERT
(MIGRATION-REVIEW MEDIUM-1) writes zero rows. In that case the query shows a healthy reading while
candidates failed. Until MEDIUM-1 is fixed, the runbook must say that zero rows is not proof of
health.

**Fix:**

```sql
 WHERE cron_name = 'ledger_refresh_fanout'
   AND error = 'candidate_enqueue_failed'
   AND completed_at > now() - INTERVAL '65 minutes'
```

Reword "Expected" to "zero rows in the last tick's window". Keep a separate unbounded variant,
labelled as history. Add one line: a failure-row write that itself failed leaves only a Postgres
`WARNING` ("failure instrument write failed"), so zero rows is not proof of health until
MEDIUM-1 lands.

### WR-03: Three runbook bullets in a public doc promise behaviour the fix round has not shipped, and nothing forces them to be updated

**File:** `docs/runbooks/ledger-refresh-go-live.md`, the "**Current behaviour. Each point below
changes in the 164.6 review fix;**" bullet and its three "*(Changes in the 164.6 review fix.)*"

**Issue:** The doc asserts that three future changes will happen: an alert (HIGH-1), a cooldown
for a failed candidate (HIGH-2), and separate 40001 counting (MEDIUM-2). Only the 164.6-05

No check ties the two together. The fix round may take a different remedy or defer one item. For
example, HIGH-1's observer could be routed to another phase instead of shipped here. In that case

operator who reads "changes in the review fix" may assume an alert exists.

**Fix:** Write the present tense only, e.g. "Nothing alerts on this row", with no promise. Have
the fix round change each bullet in the same commit as the change it describes. If a bullet must
point forward, cite a `TODOS.md` id or a ROADMAP phase instead of "the review fix".

### IN-04: The keys/sync retraction adds two unbounded round trips to the synchronous 202 path

**File:** `src/app/api/keys/sync/route.ts`, the composite branch's
`retractInheritedRefreshMarker(admin, rpcData, correlation_id)` await.

**Issue:** Python runs its twin inside a worker job. The TS site awaits a read and, when a marker
is present, an UPDATE, all before answering the user's 202. Neither call has a timeout. An UPDATE
waiting on a row lock held by a claiming worker delays the user's sync kickoff, even though the
result is best-effort and never changes the response.

finalize-wizard's call sits inside `after()` and is not affected.

**Fix:** Accept this and record it in the route comment. Alternatively, move the retraction into
`after()`, as finalize-wizard does. Note that a retraction landing after the response widens the
post-claim window that `[164.6-COMPOSITE-CLAIMTIME-SNAPSHOT]` already blocks on, so whichever is
chosen should be a recorded decision.
