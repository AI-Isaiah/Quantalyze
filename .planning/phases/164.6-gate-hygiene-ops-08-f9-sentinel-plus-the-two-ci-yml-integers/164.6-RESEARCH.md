## Summary

All three criteria are code-and-SQL work with **no new packages**. The two TypeScript criteria are small, well-precedented edits to four route handlers whose test harnesses already mock exactly the seams needed (a hoisted `adminRpcMock` in csv-finalize, a hoisted `mockRpc` in holdings sync, a table-branching admin `from()` mock in keys/sync and finalize-wizard). And finalize-wizard's admin mock **throws** on an unknown table, so every composite test breaks until a `compute_jobs` branch is added.

Criterion 3 is the heavy one, and its cost is not the SQL. The new migration's `CREATE OR REPLACE` supersedes the bodies that **every edit-kind mutation twin in both ledger gates currently mutates**: 20 twins target `20260917120000_…`, 16 target `20260911130000_…`, and 3 target view/constraint migrations that do not move. Appending the new migration to both `RED-UNDER-SETUP` lists without re-pointing those twins **in the same commit** turns every one into `no-red`, which cannot be absorbed because `WAIVED_CEILING` is 0. This is TRAP E / C-02, and it has happened three times already (see the fan-out gate's header). Because the new file holds BOTH bodies, the fan-out gate's `occurrences: 1` twins become `occurrences: 2, nth: 1` wherever their needle appears in both bodies. The composite gate's twins keep `nth: 2`. Every count must be **measured with grep on the new file**, never predicted.

The pin fan-out of "one new arm per gate" was grepped, not counted, and is listed in §Q3. It covers `run.mjs` `ARMS_FLOOR`, two parser-test pins plus the needle census, about a dozen `mutation-runner-floors.test.ts` values (including deliberate off-by-one calibrations), the value-keyed `gate-family-meta.test.ts` row, the `ci.yml` sentinel table and `ARMS_FLOOR=213`, the `drift-check-scripts.test.ts` literal `ARMS_FLOOR=213`, and the Python gate `analytics-service/tests/test_ledger_refresh_gates.py`. ### Pattern 1: retry once on 40001 (D-03, D-05, D-06)
**What:** a factory-taking helper. A supabase-js builder is a thenable, and a factory makes the second call an unambiguous second request.
**When:** exactly the two named sites.

### Pattern 2: best-effort retraction (D-15, D-18, D-19)
**What:** read → decide → write, each error surfaced to the caller, which logs `console.error` and calls `captureToSentry` under a distinct tag without changing the response. Place it **after** the successful enqueue and **before** `logAuditEventAsUser`, awaited. In keys/sync that means before the 202. In finalize-wizard it means inside the `enqueue_sync_trades_job` side effect, wrapped in its own try/catch so a retraction failure does not reject the side effect.

### Pattern 3: counted-row instrument outside the lock
Mirror the dormancy instrument: assignments in the handler, the write outside it, the write wrapped `BEGIN … EXCEPTION WHEN OTHERS THEN RAISE WARNING … END;`. The write goes after `pg_advisory_unlock` so no failure path holds the lock.

### Pattern 4: poisoned-candidate gate arm
A `pg_temp` trigger function keyed by fixture name, `BEFORE INSERT ON compute_jobs`, dropped after the call. The call is wrapped so any escape becomes the arm's own identity.

### Pattern 5: the same-commit twin re-point
Append the migration to the apply list, re-point every edit twin, and re-measure `occurrences`/`nth`. Prove with `--parse-only` (static) and then `--file` for both gates (both must print `No defects in the narrowed scope.`).

### Anti-Patterns to Avoid
- **Raising at tick end when failures occurred.** It rolls back the good enqueues (D-10).
- **Putting the failure `INSERT` inside the per-row handler.** That is R1's shape, and the write would be rolled back with the failed subtransaction anyway.
- **Counting all `cron_runs` failure rows in a gate.** Arm R now writes one too. Narrow by your own target id.
- **Awaiting a retraction inside `Promise.allSettled` without its own try/catch.** A retraction failure would mark the `enqueue_sync_trades_job` side effect rejected, and the Sentry tag would then read as an enqueue failure. Use a distinct tag (D-18).
- **Editing an applied migration** (20260826150000, 20260911130000, 20260917120000) to fix prose. It's history (D-08).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Forcing one candidate's enqueue to fail on a lane | a new fixture table or a mocked RPC | arm R's `pg_temp` BEFORE INSERT trigger | proven biting, R1-clean, invisible to other arms once dropped |
| Proving an arm can fail | a hand neuter | a `RED-UNDER` + `RED-UNDER-M` twin, `run.mjs --file` | the runner asserts first-failure identity and restores |
| Body-hash acks | `sha256sum` of the snapshot file | `node scripts/sql-body-normalize.mjs --diff-bodies`, `live` column | VAC-04 greps exactly that token |
| Function snapshots | hand edits under `supabase/schema/functions/` | `npm run schema:functions` | the files are `@generated`, and `--check` gates currency |
| Correlation id | reading `x-correlation-id` by hand | `getCorrelationId()` | shape-checked, CR/LF-safe fallback |
| Marker parity | a TS literal with only a comment | a vitest parity test that reads `job_worker.py` and throws on parse failure | the house anti-vacuity shape |

**Key insight:** in this repo the expensive failures are the **silent** ones: a twin that no longer mutates the live body, a count that reads 0 because nothing wrote, a pin nobody moved. Every choice above keeps a failure loud.

## Common Pitfalls

### Pitfall 1: the existing 40001 test flips RED
**What goes wrong:** `mockResolvedValueOnce(40001)` plus a retry means the second call succeeds, so no placeholder is written. **Avoid:** convert it to 40001 twice (two `mockResolvedValueOnce` calls) and assert exactly 2 calls. Add the 40001→success case separately.

### Pitfall 2: Sentry captured twice
Capture only after the retry is exhausted (D-06). Assert `captureToSentry` is called exactly once on 40001×2 and 0 times on 40001→success.

### Pitfall 3: retrying a builder instead of a call
Pass `() => admin.rpc(...)`, not the builder object. Assert the call count at the **mock** level (`adminRpcMock`/`mockRpc` = 2).

### Pitfall 4: twins left on the superseded migration (TRAP E / C-02)
**What goes wrong:** all 36 superseded-file twins report `no-red`, and `WAIVED_CEILING` is 0. **Avoid:** re-point in the same commit as the apply-list entry, then run `--parse-only` and `--file` on both gates. **Warning sign:** `no-red` on arms A/B/C/… that were green yesterday.

### Pitfall 5: `occurrences` predicted, not measured
The new file holds both bodies, so needles that were unique in 20260917120000 occur twice (for example `v_cause := 'flag_row_invisible_or_absent';`, `INTERVAL '20 hours'`, `WHERE lrs.is_stale`, `AND ak.sync_status IS DISTINCT FROM 'revoked'`, `AND COALESCE(ak.is_active, TRUE)`, `AND ak.disconnected_at IS NULL`, the in-flight status list, and `IF v_existing = 0 AND v_job_id IS NOT NULL THEN`). Header prose can add more. **Avoid:** `grep -c -F` every needle on the final file bytes. The runner fails `occurrence-mismatch` otherwise.

### Pitfall 6: a verify needle that a twin mutates
The apply then aborts, the gate never runs, and the runner scores a defect (GRAMMAR rule 2's recorded instance). **Avoid:** needle only what no twin touches, and concatenate needles.

### Pitfall 7: the new arm placed before arm R
It steals R's first failure under R's twin. Place it last.

### Pitfall 8: the failure write inside the lock-holding block
An INSERT error goes to the outer handler: unlock, `RAISE`, and the whole tick rolls back. Place it after the unlock, wrapped.

### Pitfall 9: sentinel prose left at the old count
CI reads the FIRST `ALL N ARMS EXECUTED` in the file, which sits in a comment hundreds of lines up. This was measured on 2026-09-17 when a stale 15 made the gate fail. Move all three mentions.

### Pitfall 10: blanket N→N+1 across the floors test
It breaks the deliberate gap-of-one calibrations. Re-derive each and **run** `npx vitest run src/__tests__/mutation-runner-floors.test.ts src/__tests__/mutation-annotation-parser.test.ts src/__tests__/gate-family-meta.test.ts src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts src/__tests__/drift-check-scripts.test.ts`.

### Pitfall 11: expecting sql-gate-lint and sql-tests green on the PR
`baseline-content-drift` (2 findings) and the shared-TEST `sql-tests` run (cause (v) applied-ness) are red by construction until the post-merge apply and, for the first, the founder's baseline regeneration. Don't "fix" either by an allowlist or a skip.

### Pitfall 12: the composite gate's leftover published cohort
Arm H's five stay published. Park them in the new arm or the LIMIT 2 is consumed.

### Pitfall 13: finalize-wizard's throwing admin mock
Unknown `from(table)` throws, so add the `compute_jobs` branch before anything else, or dozens of composite tests fail at once.

### Pitfall 14: `getCorrelationId()` under vitest
`headers()` throws outside a request scope. Mock `@/lib/correlation-id` in finalize-wizard's test.

### Pitfall 15: a retraction failure masquerading as an enqueue failure
In finalize-wizard the enqueue runs inside `Promise.allSettled` with Sentry tag `side_effect: "enqueue_sync_trades_job"`. Catch retraction errors locally and capture under their own tag.

### Pitfall 16: a single-value marker check
Mirror the UNION (D-15). A test per marker value (`"ledger-refresh"` and `"ledger-refresh-composite"`) proves it.

type PgResult = { error: { code?: string | null } | null };
export async function retryOnceOnSerializationFailure<T extends PgResult>(
  call: () => PromiseLike<T>,
  onRetry: (first: T) => void, // caller logs console.warn (D-06); never Sentry

  const first = await call();
