## Warnings

### WR-01: HIGH-2 is recorded as fixed, but the all-fail RAISE rolls back the cooldown row in the exact scenario HIGH-2 named

**File:** `supabase/migrations/20260924120000_ledger_fanout_failure_count.sql`. The
all-candidates-failed `RAISE EXCEPTION` in both `enqueue_ledger_refresh_for_strategies` and
`enqueue_ledger_composite_refresh`, together with the failed-attempt-cooldown `NOT EXISTS (… FROM
public.cron_runs cr …)` conjunct in each candidate CTE. Snapshots are in
`supabase/schema/functions/`. `164.6-REVIEW-FIX.md` marks HIGH-2 as "fixed".

**Issue.** The cooldown reads the failure row. The raise at the end of an all-fail tick rolls back
that same tick's failure row. So the cooldown can engage only when some other candidate in the
same tick enqueued successfully. HIGH-2's own words were *"two per venue starve that venue, two
composites starve the whole composite cohort"*. Both of those are all-fail ticks by construction:

- **Single-key.** The per-venue cap is `venue_rank <= 2`. The runbook's "Expected" bullet records
  that PROD's backlog is single-venue: *"the four-strategy single-venue backlog (the per-venue cap
  of 2 binds)"*.

  Scenario:
  1. The two stalest strategies on that venue are poisoned, and no other venue has a stale
     candidate.
  2. Every tick selects the same two, both fail, and the tick raises.
  3. The raise erases the row, so the next tick selects the same two again.
  4. Every healthy strategy on that venue stays unrefreshed indefinitely.
- **Composite.** `LIMIT 2` has no partition, so two poisoned composites mean every tick is
  all-fail. The composite header measures the cohort at one. With a cohort of one, ANY failure is
  all-fail, so the composite cooldown can never engage.

Arm T passes only because its tick carries healthy siblings. It never exercises the scenario that
motivated it. The trade is loud, since the prober alerts every hour. But "fixed" is the wrong
status: the user-facing starvation HIGH-2 described still ships. REVIEW-FIX's residual line
("All-fail tick: no cooldown") understates it as a cooldown gap and does not mention the
starvation.

**Fix:** remove the need for the raise, not the cooldown.

1. Drop the `IF v_enqueued = 0 AND v_failed > 0 THEN RAISE EXCEPTION …` block from both bodies.
   Every failure row then survives, and the cooldown engages on every tick, all-fail included.
2. Keep the MEDIUM-1 re-raise, arm V2. That path has no row to lose.
3. Give cron-obs a second read, of `public.cron_runs`. The prober already writes this table
   (`CONTACT_INSERT_SQL`), so it can read it. Read counts only:

```sql
SELECT count(*) FILTER (WHERE metadata->>'function' = 'enqueue_ledger_refresh_for_strategies'),
       count(*) FILTER (WHERE metadata->>'function' = 'enqueue_ledger_composite_refresh')
  FROM public.cron_runs
 WHERE cron_name = 'ledger_refresh_fanout'
   AND error = 'candidate_enqueue_failed'
   AND completed_at > now() - interval '3 hours';
```

4. Raise `cron-ledger-fanout-failed` when either count is above zero, and keep the
   `return_message` read for errors raised by the body itself.

This one change closes four things:

- HIGH-1, and it also alerts on partial failures.
- HIGH-2 in both scenarios.
- REVIEW-FIX's residuals "Partial-failure tick: no alert".
- REVIEW-FIX's residual "CONTEXT line in PROD is unmeasured". The row read does not depend on
  pg_cron's message format.

Re-point arms U and R to assert that the row exists and nothing is raised.

If the raise is kept as a decision, correct `164.6-REVIEW-FIX.md` from HIGH-2 "fixed" to "partially
fixed". Also state the starvation, not just "no cooldown", in the migration header and in the
runbook bullet "A failed candidate is skipped for 20 hours".

### WR-02: the new cron-obs step's constants are pinned to nothing, and zero runs reads as healthy

**File:** `scripts/prod-prober/arms/cron-obs.mjs`, covering `LEDGER_FANOUT_JOB`,
`LEDGER_FANOUT_FUNCTION`, `LEDGER_FANOUT_SQL` and step (4) of `run`. Also `scripts/prod-prober/run.mjs`
`fixtureSql`.

**Issue:**

1. **The self-test cannot fail on the SQL.** `fixtureSql` routes on
   `q.includes("job_run_details") && q.includes("ledger_refresh_fanout")` and returns canned
   counts, so nothing in the SQL predicate is ever executed or pinned. I found no test tying either
   constant to its source of truth:
   - `LEDGER_FANOUT_JOB` should match the manifest entry `"jobname": "ledger_refresh_fanout"` in
     `scripts/prod-prober/cron-manifest.json`.
   - `LEDGER_FANOUT_FUNCTION` should match that entry's `"command"` and the SQL function the raise
     text leads with.

   `git grep LEDGER_FANOUT_FUNCTION` hits only the arm and a migration comment. Two failure paths
   follow:
   - A typo, or a future rename of the SQL function (a `_v2` re-base, say), makes `errored` read 0
     on PROD forever, and the self-test stays green.
   - A typo in `LEDGER_FANOUT_JOB` makes `runs` read 0 as well.
2. **Zero runs passes.** The arm's own header rule says *"⛔ ZERO RUNS IN THE WINDOW IS A DEFECT, NOT
   A PASS. The job is hourly; three hours with nothing is itself the failure."* The new step logs
   `0 run(s) in the last 3h` and adds no defect. `cron-drift` cannot stand in for this, because it
   checks the manifest against `cron.job` and never reads this step's constants. The job is
   `active: true` and hourly in the manifest, so 3 runs are expected in the window.

**Fix:**

- In `prod-prober-wiring.test.ts`, assert the following:
  - the manifest entry with `jobname === LEDGER_FANOUT_JOB` exists, and its `command` contains
    `public.${LEDGER_FANOUT_FUNCTION}()`;
  - `LEDGER_FANOUT_SQL` contains both constants' quoted literals;
  - the migration's all-fail message begins with `${LEDGER_FANOUT_FUNCTION}:`. Read the migration
    file, as the parity oracle does.
- In `run`, treat `counts.runs === 0` as `cron-no-observation`, with subject `LEDGER_FANOUT_JOB`.
- Add a red fixture, `ledger-fanout-no-runs.json` with `{runs:0, errored:0}`. That is one more
  scenario, so bump `SELF_TEST_SCENARIOS` 84 → 85 together with its wiring pin.

### WR-03: the composite fan-out now raises for an observer that does not watch it, and the runbook says it does

**Files:**

- `scripts/prod-prober/arms/cron-obs.mjs`: `LEDGER_FANOUT_FUNCTION` is the single-key name only.
- `docs/runbooks/ledger-refresh-go-live.md`:
  - "Did a candidate fail to enqueue this tick?", which opens with "Both fan-outs write it"
    beside "The prod prober's cron-obs arm reports such a run as `cron-ledger-fanout-failed`";
  - the bullet "**What is watched.** A tick in which every candidate failed is a failed run, which
    the prod prober's cron-obs arm reports";
  - the `[164.6-COMPOSITE-CLAIMTIME-SNAPSHOT]` precondition list.

**Issue.** `enqueue_ledger_composite_refresh` got the same all-fail raise, in the same round, with
the same justification in its body: the raise exists *"so the scheduler records this run as
FAILED … which the prod prober's cron-obs arm reads"*. cron-obs reads only the job
`ledger_refresh_fanout` and only the single-key function name.

The composite is dormant today. However its schedule gets registered, nothing observes it:

- **Its own job name.** cron-obs never reads that job.
- **A second statement in the `ledger_refresh_fanout` command.** pg_cron runs a multi-statement
  command as one implicit transaction. A single-key raise would then roll back the composite's
  enqueues, and a composite raise would roll back the single-key's.

The runbook's "What is watched" bullet is unqualified. The precondition list that gates the
composite schedule (items 1–5) says nothing about the observer. An operator scheduling the
composite after 164.6.7 ships would reasonably believe an alert exists.

**Fix:**

- Qualify the runbook bullets to "the single-key fan-out's failed runs".
- Add a precondition item 6: *"cron-obs watches the composite job: `LEDGER_FANOUT_*` becomes a list
  of `{job, function}` pairs covering the composite's own job name. Schedule it as its own job,
  never as a second statement of `ledger_refresh_fanout`."*
- If WR-01's `cron_runs` read is adopted, it covers both functions already, via
  `metadata->>'function'`.

### IN-05: the runbook overstates what 40P01 means, and persistent lost races are silent

**File:** `docs/runbooks/ledger-refresh-go-live.md`, the bullet "**A lost enqueue race is not a
failure.** SQLSTATE `40001` … and `40P01` (deadlock) mean another writer is already serving the
strategy." Also the `WHEN serialization_failure OR deadlock_detected` branch in both bodies.

**Issue.**

- **40001 claim: true.** The enqueue RPC raises it when another writer won the in-flight race.
- **40P01 claim: not true.** A deadlock victim's other party can be any lock holder, for example a
  worker updating the row. Nothing then guarantees an in-flight job exists for the strategy.
- **The consequence.** A recurring deadlock never names the candidate and never cools it down.
  It never writes a row and never raises. It retakes the slot every tick, silently.

**Fix:**

- Reword to "40001 means another writer won the enqueue race; 40P01 is lock contention and is
  counted with it".
- Either count 40P01 as a failure, or raise the tick when `v_lost_race > 0 AND v_enqueued = 0`
  across two consecutive ticks. Alternatively, record the trade as a residual.
