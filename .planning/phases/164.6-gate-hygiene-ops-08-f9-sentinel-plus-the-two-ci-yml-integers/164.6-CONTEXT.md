## Implementation Decisions

### Scope
- **D-01:** Scope is criteria 2, 3, 4 exactly as pruned on 2026-09-17. Criterion 17
  (`[164.6.2-KILLSWITCH-COMMENT-DRIFT]`) was routed IN on 2026-09-14 and then listed among the
  DROPPED criteria by the later 2026-09-17 prune; the later founder decision governs, so it is
  NOT planned here. Evidence: ROADMAP `### Phase 164.6`, "What was dropped, by criterion: … 17".
- **D-02:** Criterion 2 names two call sites and this phase retries at those two only. A census
  found six further TS `enqueue_compute_job` callers (`keys/sync` ×1, `finalize-wizard` ×2,
  `intro`, and two crons). Extending the retry to them is recorded as a deferred idea, not done,
  because the criterion's text ("add the retry at BOTH call sites") is the founder's scope and the
  prune was explicit.

### 40001 retry (criterion 2)
- **D-03:** Retry **exactly once**, **only** when the PostgREST error's `code === "40001"`, with
  **no sleep**. Evidence: TODOS `[OPS-08-TS]` ("retry once before falling through to the 500"); the
  40001 is raised only when the lost race's winner has ALREADY advanced past the in-flight
  statuses (mig `20260826150000` header), so an immediate re-enqueue does not collide with an
  in-flight row, and a wait buys nothing.
- **D-04:** When the retry is exhausted, each site's CURRENT failure behaviour is kept exactly:
  csv-finalize writes `ENQUEUE_LOST_RACE_USER_COPY` through the placeholder and captures to
  Sentry; holdings sync answers its existing 500. Every non-40001 error takes the existing path
  with NO retry.
- **D-05:** One small shared helper under `src/lib/` (name at the planner's discretion) wraps
  "call, and on 40001 call once more". Two call sites with two different clients justify it; it
  must not grow options nobody uses.
- **D-06:** A 40001 that is retried is logged (`console.warn`) but NOT sent to Sentry; only a
  final failure is captured, as today. A retried race is an expected MVCC outcome and alerting on
  it would be noise.
- **D-07:** Tests per site (vitest, mocked client): 40001 then success → the success outcome and
  exactly two RPC calls; 40001 twice → the existing failure outcome and exactly two calls; a
  non-40001 error → one call. ⛔ Anti-vacuity: neuter the retry at each site in turn and observe
  that site's test go RED, then restore byte-identically (byte backup + `cmp`).
- **D-08:** Correct the TS prose that now becomes false — the `ENQUEUE_LOST_RACE_USER_COPY`
  JSDoc and the `enqueueLostRace` comment in csv-finalize say "nothing in this repo retries a
  40001". The user copy itself ("Retry the sync, or contact support if this persists.") STAYS: it
  is only written after the retry is exhausted, where it is still true. ⛔ Applied migration files
  are history and are NOT edited even where their headers say the same thing.

### Fan-out failure count (criterion 3)
- **D-09:** Delivered as ONE new forward migration that re-bases BOTH functions on their latest
  bodies (`supabase/schema/functions/enqueue_ledger_refresh_for_strategies.sql`, source
  `20260917120000`; `supabase/schema/functions/enqueue_ledger_composite_refresh.sql`, source
  `20260911130000`) with `CREATE OR REPLACE`. Signature, `SECURITY DEFINER`, `search_path`, ACL and
  `RETURNS INTEGER` are unchanged. — **Reversibility:** one-way — merging `supabase/migrations/**`
  auto-applies to PROD, and the single-key fan-out is LIVE there (scheduled as `ledger_refresh_fanout`
  since Phase 164.5.1, per `167-CONTEXT.md`).
- **D-10:** The return value keeps meaning "jobs actually INSERTED this tick" — the founder reads
  it back per `docs/runbooks/ledger-refresh-go-live.md`. The failure count is surfaced BESIDE it,
  not instead of it. REJECTED: changing the return type (needs `DROP FUNCTION`, breaks the
  scheduled command and every gate reading the integer); RAISE-ing at the end of a tick with
  failures (rolls back the enqueues that DID succeed, turning one poisoned row back into a lost
  tick — the exact thing the per-row handler exists to prevent).
- **D-11:** Mechanism, following the dormancy instrument already in both bodies: the per-row
  `EXCEPTION WHEN OTHERS` handler does ASSIGNMENTS only (count + append `{strategy_id, sqlstate}`
  to a local), keeping the shape lint rule R1 argues for. After the loop, when the count is
  non-zero, ONE `public.cron_runs` row is written: `cron_name = 'ledger_refresh_fanout'`,
  `status = 'error'`, `error` = one fixed cause string distinct from the two dormancy causes, and
  `metadata` = `{function, cause, failed_count, enqueued_count, failed_targets}`. The write is
  best-effort-wrapped exactly like the dormancy write, and the advisory lock is released on every
  path. The final `RAISE NOTICE` names the failed count too. A tick with zero failures writes
  nothing (same "healthy writes nothing" precedent as the dormancy instrument).
- **D-12:** The failed target's `strategy_id` goes ONLY into `cron_runs.metadata`, NEVER into
  RAISE text — the T-161.1-10 RAISE discipline is kept as-is. Recording the id is the founder's
  own criterion text ("record the failed target id"). The rls-policy-auditor must confirm who
  can read `cron_runs` before this ships.
- **D-13:** Proof on the pg-lane (`scripts/pg-lane/run.sh`, never a remote): new arms in
  `supabase/tests/test_ledger_refresh_fanout.sql` and `supabase/tests/test_ledger_refresh_composite_arm.sql`
  force ONE candidate's enqueue to raise and assert a `cron_runs` row with `failed_count >= 1`
  naming that target, while the other candidates still enqueue. Arms carry `RED-UNDER`
  annotations so the mutation runner covers them. Floors (`FILES_FLOOR`, `ARMS_FLOOR`) may only
  RISE, read by symbol from `scripts/mutation-runner/run.mjs`; `WAIVED_CEILING` stays 0.
- **D-14:** Before push: three reviewers (migration-reviewer + rls-policy-auditor +
  silent-failure-hunter) and every finding fixed. `npm run schema:functions` regenerates the
  function snapshots in the same commit as the migration.

### Composite marker retraction (criterion 4)
- **D-15:** The TS retraction mirrors Python's `_retract_refresh_marker_on_reuse` semantics
  exactly: with the job id the enqueue returned, read `compute_jobs.metadata`; if
  `metadata.source` is one of the ledger-refresh markers, write back the metadata WITHOUT
  `source`, plus `refresh_marker_retracted = <old marker>` and `correlation_id = <this
  request's>`. The UNION of both markers, not only the composite one — Python's docstring argues
  that retraction is the loud direction, so widening it is safe.
- **D-16:** The TS marker set is a constant mirroring Python's `LEDGER_REFRESH_JOB_SOURCES`
  (`analytics-service/services/job_worker.py`), pinned by a static parity test that reads the
  Python file. This is the repo's existing parity pattern (compare the `computation_error_copy`
  gate in `csv-finalize/route.test.ts`).
- **D-17:** `finalize-wizard`'s composite enqueue currently discards the RPC's `data`. It must
  capture the returned job id.
- **D-18:** Failure policy is best-effort, same as Python: a failed retraction does NOT fail the
  user's request (the enqueue succeeded), but it is LOUD — `console.error` plus `captureToSentry`
  under a distinct tag. It is never silent.
- **D-19:** The read-modify-write residual Python records (161.1-D12) is inherited and stated in
  a comment; the real closure (a merge arm in `enqueue_compute_job`, 161.1-D11) is out of scope.
- **D-20:** Tests per site: an enqueue returning an id whose row carries each marker → an update
  with the retracted metadata; a row without a marker → no update; a failing retraction → the
  request still succeeds AND Sentry is called. ⛔ Anti-vacuity: neuter the retraction at each site
  and observe RED, restore byte-identically.
