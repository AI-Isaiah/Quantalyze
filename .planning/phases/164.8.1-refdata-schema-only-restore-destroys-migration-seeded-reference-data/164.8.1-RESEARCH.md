## Summary

The restore (`scripts/restore-test-from-baseline.sh`) assembles one psql transaction: `DROP SCHEMA public CASCADE` → the filtered `baseline.sql` dump → survivor DDL → a TRUNCATE-and-reseed of `supabase_migrations.schema_migrations` from the repo file list → a `DO $restore$` shape assertion → `COMMIT`/`ROLLBACK` (`:860-978`). The dump carries **zero** data statements (`BASELINE.md:3`, `:55`), so every row a migration INSERTed is gone after the restore while the ledger says the migration applied. The fix the founder locked is a replay of the reference INSERTs inside that same transaction, followed by a gate.

The research finding that matters most: **"reference table" is the wrong unit — reference-ness is a property of a STATEMENT, not a table.** `strategies` is a fixture table 20 times and a required application singleton once (`20260515095804_teaser_anchor_strategy.sql:78-90`, consumed by `src/lib/phase-19-constants.ts:21` and `analytics-service/routers/process_key.py:1121`). A per-table allowlist would either replay 20 files of fixtures or lose the sentinel the teaser flow writes FK rows against. So the allowlist must be keyed by **(migration file, table)** with a pinned statement count, and the classification criterion is mechanical: *top-level* (not inside any dollar-quoted body), `INSERT INTO <t> … VALUES (<literals only>)`, no `SELECT`/`FROM`, terminated by `;`. Every candidate that passes that criterion is one of six tables in seven files; every other INSERT in the corpus fails it for a reason a machine can name (inside a `DO`/function body, `INSERT … SELECT`, or a schema the restore does not drop).

Extraction should be a small Node script that reuses the lexer already in `scripts/lint-sql-gates.mjs:334` (`maskSql`, which blanks comments and string literals while preserving offsets, and `statements()` at `:533`, which splits on top-level `;`). Classification runs on the masked text; the emitted SQL is sliced from the ORIGINAL text by offset, so nothing is rewritten. The script refuses loudly on every shape it cannot prove safe, and an `--audit` mode fails when a migration gains a top-level literal INSERT into an allowlisted table that has no allowlist line — the drift direction a static allowlist otherwise cannot see.

**Primary recommendation:** (file, table, count)-keyed allowlist file + offset-preserving extractor with refuse-by-default + `SET LOCAL search_path = public, pg_catalog` around the replay + a `DO $refdata$` gate that names the empty table + `refdata:` rows in the census + three new self-test arms (`EXPECTED_ARMS` 21 → 24), one of which is a scratch-copy neuter that proves the gate bites.

## 1. The allowlist — criterion, then applied

### The criterion (human-applicable, machine-re-checkable)

A statement is **reference data** iff ALL of:

| # | Test | Why it discriminates | Machine check |
|---|------|----------------------|---------------|
| C1 | It is a **top-level** statement — not inside a `DO $$…$$`, a `CREATE FUNCTION … AS $$…$$`, or a `cron.schedule($cron$…$cron$)` body | Every fixture/probe/backfill in this corpus lives in a `DO` self-verify block or a function body; every reference seed is bare | masked-statement text begins with `INSERT` (a `DO` block is one statement beginning with `DO`) |
| C2 | It is `INSERT INTO <t> (cols) VALUES (…)` with **literals only** — no `SELECT`, no `FROM`, no identifiers in the tuple beyond casts and `now()`/`gen_random_uuid()` | `INSERT … SELECT FROM profiles` is a backfill of existing data by construction; on an empty table it inserts nothing, so replaying it is a no-op that a non-empty gate would then fail | masked text contains no `SELECT`/`FROM` token; tuple tokens are string/number/`::type`/`NULL`/`TRUE`/`FALSE`/`now()` |
| C3 | The target table lives in `public` | The restore drops ONLY `public` (`restore-test-from-baseline.sh:861` `DROP SCHEMA public CASCADE`); `storage.buckets` and `auth.users` rows survive and need no replay (exception: the teaser file's `auth.users` row, replayed for lane-correctness only — see A5) | schema prefix absent or `public.` |
| C4 | Something in the running system **reads the row by key** — a FK, a `CHECK`, a slug lookup, a constant in app code | Distinguishes a seed from a leftover | human: cite the consumer |

Idempotence (`ON CONFLICT DO NOTHING`) is a strong *signal* (15/15 live `compute_job_kinds` statements carry it) but NOT a criterion: `discovery_categories` has none (`20260405061911_initial_schema.sql:146-151`) and is unquestionably reference, while `INSERT … SELECT FROM profiles … ON CONFLICT DO NOTHING` (`20260417031851_user_app_roles.sql:223-238`) carries it and is a backfill.

**Err-toward-exclusion rule applied:** anything failing C1 or C2 is OUT regardless of how "reference-shaped" the table name looks.

## 2. Extraction — what the statements look like, and the approach

### What the corpus actually contains (read this session)

- All 15 live `compute_job_kinds` statements: one or two physical lines, `INSERT INTO compute_job_kinds (name) VALUES ('x')\n  ON CONFLICT (name) DO NOTHING;` — unqualified table name, no comments inside the statement (`20260416081039:176-177` et al.).
- `discovery_categories`: a 6-line multi-row VALUES with `'…'` strings containing periods and commas, no embedded quotes (`20260405061911:146-151`).
- `system_flags`/`system_settings`/`feature_flags`: 1–3 lines, `public.`-qualified in the 2026-09 files, unqualified in the April file.
- Teaser file: three multi-line `INSERT (…) VALUES (…)` with `::uuid` casts, preceded by `BEGIN; SET lock_timeout = '3s';` at top level (`20260515095804:44-46`) — the file manages its own transaction; only the three INSERTs are taken.
- Three `compute_job_kinds` "hits" are comments (`20260420073003:18`, `20260510175507:6`, `20260717233529:47`) — a raw grep over-counts them; the masked lexer does not.
- Commented-out `DELETE FROM compute_job_kinds` rollback notes exist (`20260420073003:1122`, `20260420213754:680`) — comments only; no live DELETE/UPDATE touches any allowlisted table `[VERIFIED: grep -niE "(delete from|update)\s+(public\.)?(compute_job_kinds|discovery_categories|feature_flags|system_flags|system_settings)" → only those two comment hits]`. So "replay the INSERTs" reproduces the full DML history for these tables; no retired kind is resurrected.

### Why not regex in bash

A `sed -n '/INSERT INTO t/,/;/p'` cannot tell a top-level INSERT from one inside `DO $$ … $$` (the `strategies` case: 35 of 37 occurrences are in bodies), cannot see that `:18` is a comment, and will stop at the first `;` inside a string literal. The fragility the CONTEXT warns about is real for this corpus.

### Recommended approach — reuse the repo's lexer, refuse by default

`scripts/extract-reference-inserts.mjs` (new; name at planner's discretion):

1. Read the allowlist; refuse (exit 1, naming the line) on malformed lines, unknown basenames (must be in `MIGRATIONS_DIR`), or a table outside `public.`/`auth.users` (C3).
2. For each file: `maskSql(src)` → `statements(code)` (both from `lint-sql-gates.mjs:334`/`:533`; export them — two `export` keywords, no behaviour change. `maskSql` returns `{error,line}` on an unterminated quote/dollar-tag, which is itself a refusal). Masking blanks comments and string interiors while **preserving offsets** (`:326-327`), so `src.slice(start, end+1)` yields the original statement byte-for-byte.
3. A span qualifies iff masked text matches `^\s*INSERT\s+INTO\s+(public\.)?<table>\b` (C1 comes for free: a `DO` block is one span starting with `DO`).
4. **Refuse** (exit 1, `file:line table reason`) when: the span contains `SELECT` or `FROM` tokens (C2); the tuple contains an identifier that is not a cast/`NULL`/`TRUE`/`FALSE`/`now()`/`gen_random_uuid()` (C2); the span is the trailing unterminated remainder (no `;`); the per-line count ≠ pinned count; any allowlisted (file, table) yields zero spans; or the emitted text contains a `$` dollar-tag (defensive — keeps the transaction's replay section body-free, matching the redaction rule at `:1173-1176`).
5. Emit, in **allowlist order = filename order**, each original statement followed by a `-- refdata: <basename>:<line> <table>` provenance comment, then a single `-- refdata-expect: <table>=<n-statements>` trailer per table the script can parse back (used for the census/gate list).
6. `--audit` mode: scan **every** migration for qualifying spans into any allowlisted table and exit 1 on a (file, table) pair with no allowlist line. Wire it into `test-restore-from-baseline.yml` next to `check-baseline-staleness.mjs` (`:462-469`) and into `ci.yml`'s `sql-gate-lint` job so a new `*_kind.sql` migration cannot merge without its allowlist line.
7. `--self-test` with red+green fixtures per rule, the `lint-sql-gates.mjs` convention (`:112 FIXTURE_DIR`).

**Candidates where extraction cannot be made safe:** none in the current allowlist — every statement is a bare literal VALUES. If a future reference INSERT is authored inside a `DO` block (e.g. guarded by `IF NOT EXISTS`), the extractor will refuse it under C1; the remedy is to author reference seeds at top level with `ON CONFLICT DO NOTHING` (as all 15 kinds already are), never to teach the extractor to descend into bodies.

**How the bash side consumes it (LOCKED placement):** in `build_transaction()` after `cat "$RESTORE_OUT_DIR/survivors.sql" >> "$out"` (`:876`) and before the ledger DDL (`:881`):


## 4. The gate — recommend non-empty + one derived invariant + visible counts

**Recommendation: non-empty per allowlisted table, table NAMED in the exception, plus one table-specific invariant that costs nothing and is not a pin.**

In a new `DO $refdata$` block appended right after the replay (separate from `DO $restore$` at `:904` so its message is its own anchor):

```sql
-- Source: shape of the existing DO $restore$ block, restore-test-from-baseline.sh:904-963
DO $refdata$
DECLARE t text; v_n bigint; v_missing text;
BEGIN
  FOREACH t IN ARRAY ARRAY[${refdata_tables_csv}]::text[] LOOP
    EXECUTE format('SELECT count(*) FROM %s', t) INTO v_n;
    IF v_n = 0 THEN
      RAISE EXCEPTION 'restore aborted: reference table % is EMPTY after the replay — the ledger would say its seed migration applied while its rows are gone (Phase 164.8.1)', t;
    END IF;
  END LOOP;
  -- compute_jobs_kind_check lists every admitted kind; the registry must contain all of them.
  SELECT string_agg(k, ',') INTO v_missing
    FROM unnest(regexp_matches(pg_get_constraintdef(c.oid), '''([a-z_]+)''', 'g')) AS m(k)
    JOIN pg_constraint c ON c.conname = 'compute_jobs_kind_check'
   WHERE NOT EXISTS (SELECT 1 FROM public.compute_job_kinds WHERE name = m.k);
  IF v_missing IS NOT NULL THEN
    RAISE EXCEPTION 'restore aborted: compute_jobs_kind_check admits kind(s) % that compute_job_kinds does not carry — a partial replay', v_missing;
  END IF;
END
$refdata$;
```

(`regexp_matches` inside `unnest` needs the usual lateral form; the planner writes it properly — the point is the invariant, not the syntax.)

Why not count pins in the DB: a count pin drifts on every new kind (the CONTEXT's objection) and, worse, it moves the number OUT of the migration that adds the row. The **statement** count per file in the allowlist is the stable place for a pin.

**What non-empty cannot catch:** a partial replay (3 of 16 kinds) in any table that has no derived invariant; a wrong literal (`'crypto_sma'` for `'crypto-sma'`). ## Common Pitfalls

### Pitfall 1: `search_path` is `pg_catalog` where the replay runs
The dump leaves `set_config('search_path', '', false)` in force (`:868-870`), and `TXN_MID` sets `pg_catalog` (`:872-875`). Twelve of the allowlisted statements are unqualified (`INSERT INTO compute_job_kinds …`). Without `SET LOCAL search_path = public, pg_catalog` the replay fails with `relation "compute_job_kinds" does not exist` — and would fail the same way on the lane, so arm 22 catches it. Restore `pg_catalog` afterwards so the ledger DDL and `DO $restore$` behave as before.

### Pitfall 2: `FORCE ROW LEVEL SECURITY` on `compute_job_kinds` + `SET row_security = off`
`baseline.sql:9578` forces RLS on the kinds table and its only policy is SELECT (`:13012`); the dump preamble sets `row_security = off` (`baseline-fixture.sql:44` mirrors it). Under those two, an INSERT by a role that RLS applies to raises an error instead of filtering. It works today only because the restoring role bypasses RLS — hosted Supabase's `postgres` is `rolbypassrls = TRUE` `[CITED: supabase/migrations/20260816140000_reconcile_dropped_enqueue_sweep.sql:375 comment]`, and the pg-lane runs as a superuser. The self-test therefore cannot prove this on TEST — record it beside `:98-103` ("IT DOES NOT PROVE THAT THE REAL DUMP APPLIES"). Assumption A1.

### Pitfall 3: the tail after `:1090` never runs on TEST today
The extension guard fails on the real TEST (CONTEXT `<specifics>`, Phase 164.9). Anything after it is unmeasured. Put the gate in the transaction and the counts in the census; nothing new below `:1090`.

### Pitfall 4: `set -e` and grep exit codes
`grep -c` exits 1 on zero matches; the script's `set +e; …; rc=$?; set -e` idiom (`:648-664`) must wrap the extractor call and any count read, or a legitimately-zero pre-census `refdata:` row aborts the script.

### Pitfall 5: the three exact summary-line greps
Arms 9/12/18 match `restore: tables=2 policies=1 functions=2 ledger_rows=3 survivors=… filtered=1 mode=restore` verbatim (`:1731`, `:1801`, `:1907`). Adding `refdata=` to that line silently breaks three arms; keep it out.

### Pitfall 6: `system_settings.analytics_service_url` is the PROD Railway host
The seed literal is `https://quantalyze-analytics-production.up.railway.app` (`20260907120000:295`). Replaying it is faithful — the same migration seeded the same value on TEST when it applied, and the CHECK at `baseline.sql:10880` admits only `*.up.railway.app` or `http://127.0.0.1:9` — but it means TEST's `match_engine_cron_tick()` targets PROD's analytics service exactly as before the restore. Not this phase's to change; flag it in RESEARCH → planner → founder as Open Question 1 rather than silently "fixing" it in the allowlist.

### Pitfall 7: `20260515095804` manages its own `BEGIN`/`COMMIT`
Extracting only its three INSERTs is correct; extracting the file wholesale would put a `COMMIT` inside the restore transaction. The extractor's "INSERT spans only" rule is what prevents that — make it a red fixture in arm 24 or the extractor's self-test.

### Pitfall 8: the allowlist only sees tables it names
`--audit` closes "new kind migration without allowlist line". It cannot see a new reference TABLE. State it in the script header, the way `:75-103` states the self-test's limits.
