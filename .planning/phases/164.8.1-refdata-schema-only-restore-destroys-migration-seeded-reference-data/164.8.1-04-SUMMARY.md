# Plan 04 — the replay run for real

## What happened

`--mode preflight` ran the WHOLE transaction against hosted TEST and rolled it back:
post-census byte-identical to pre-census, no `relation … does not exist`, no
`violates row-level security`, no `permission denied`, no ERROR line. `--mode restore`
then ran the same statement stream and committed. Every step of the restore job was
green, including `Post-verify with the Supabase CLI — ledger SHAPE`, which had never
executed before — the 2026-09-08 run failed ahead of it.

Full censuses, gate lines and run ids are in `164.8.1-04-RESTORE.log`. It carries names
and counts only; `.planning/` is tracked and this repo is public.

## The measurement this plan existed for

RESEARCH A1 asked whether the connecting role can INSERT into `public.compute_job_kinds`
on hosted TEST. That table carries FORCE ROW LEVEL SECURITY with a SELECT-only policy,
so FORCE removes the owner exemption and an INSERT without BYPASSRLS aborts with 42501.
The self-test lane structurally CANNOT answer it: its `postgres` is initdb's superuser,
so the assertion is satisfied there for the wrong reason. Only a full transaction against
hosted TEST measures it.

It ran. 23 statements, 15 of them into that table, no RLS error. **A1 holds — measured.**

## The proof, which is not the script's word for itself

CI run `34329426898` on sha `a622df27` was RED before the restore. Its failed jobs were
re-run AFTER it — same commit, same tests, only the database changed in between:

| job | before | after | why it was red |
|---|---|---|---|
| `python` | failure | **success** | 27 failures: 26 `compute_jobs_kind_fkey` violations, 1 `PGRST116 … 0 rows` |
| `e2e-seeded` | failure | **success** | `discovery_categories row for slug='crypto-sma' not found` |

⚠️ Coverage was never implicated — `Required test coverage of 80% reached. Total
coverage: 90.97%`. The job was red purely from the 27 test failures, and every one of
them was a missing PRECONDITION rather than a defect in the logic under test.

⛔ **This is why the rows were not hand-seeded while CI was red and shared TEST was
blocking other teams.** Hand-seeding would have turned CI green and destroyed the
pre-census that makes the replay provable — the tables would have been non-empty for the
wrong reason, and the gate would have shipped without anyone seeing it work. The
allowlist forbids it in writing and so does the seeder's own message.

## What the restore revealed — a finding, not damage

With `python` green, `sql-tests` ran for the FIRST time in this sequence (`P1956` appears
ZERO times in the 2026-09-08 log, which died earlier at the ledger stage) and
`test_commit_scenario_batch_p1956_range.sql` failed. It asserted that
`bridge_outcomes.percent_allocated` REJECTS 100 and 0, citing mig-059's inline CHECK —
which `20260528223200_drop_stale_bridge_outcomes_percent_inline_check.sql:53` DROPPED in
May, its own filename calling it stale.

The test had stood green for four months because nothing applies migrations to shared
TEST, so TEST still carried the dropped constraint. **The test was measuring a database
the migration chain no longer describes.** Same disease as the empty reference tables,
from the other side: there the ledger lied about effects, here the database lied about
constraints.

Fixed and shipped as v0.77.28.0 (PR #765), with a new leg at `100.01` so that flipping
two legs to ACCEPT does not leave `-1` as the only rejecting arm — a one-sided boundary
test cannot tell a correct `[0, 100]` from a CHECK that lost its ceiling. All four
boundaries were evaluated read-only against the live predicate before committing. Full
CI green afterwards, with the test executing rather than being skipped.

## Deviations from the plan

* **The plan's Task 1 said `/gsd-ship`.** It halted at its own preflight:
  `verification.status: missing`, and only `passed` may ship. The gate is correct in
  general and wrong for this phase — plan 04's Task 1 IS the merge, because the restore
  workflow only runs on `--ref main`, so the code must land before the phase's last step
  can execute at all. PR #764 was merged directly (`gh pr merge --squash`) after
  confirming the merge carried ZERO files under `supabase/` and therefore applies no
  migration to PROD. Founder decision, recorded here rather than left implicit.
* **The merge happened on a RED board, deliberately and with the reason named.** `python`
  and `e2e-seeded` were red BEFORE the merge and for the condition the merge was about to
  fix. Proven pre-existing rather than assumed: commit `7798f865` on the same branch,
  before the review fixes, shows the identical pytest tally — `27 failed, 5421 passed,
  69 skipped, 2 xfailed`.
