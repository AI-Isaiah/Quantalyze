## What was found that the plan did not predict

### 1. ⭐ The flat app-global 429 envelope **cannot arrive** at this route — so "keep some flat" was vacuous

The plan says to *"keep genuinely-app-global cases flat with `main.py`'s REAL
literals"*. **There are none.** Predicate, re-runnable: the upstream is
`@router.post("/keys/{key_id}/permissions")` in `routers/internal.py`, which
carries **no `@limiter.limit(...)` decorator**, and the process's single canonical
`Limiter` (`services/rate_limit.py:215`) is built as
`Limiter(key_func=default_platform_key)` with **no `default_limits`**. slowapi
never raises `RateLimitExceeded` on this path, so `main.py`'s handler is
unreachable from here.

All seven fixtures were therefore re-homed onto shapes that *can* arrive: the
**nested** envelope for the three cases modelling our own per-key throttle
(including `:777`, whose `Retry-After: 60` **is** `int(_RATE_LIMIT_WINDOW_S)`),
and the **scalar-`detail`** shape for the three modelling a throttle above our
service. `:870` (non-JSON edge/WAF, no payload) was already truthful and untouched.

### 2. ⭐ `VenueTransientHTTPException` is **FLAT, not nested** — the plan's 424 instruction was wrong

The plan asks for *"the upstream's real **nested** `VenueTransientHTTPException`
424 body"*. That class's docstring opens with **"A classified venue verdict on
`/api/validate-key`: FLAT, not nested"**, and `main.py`'s dedicated handler
serialises `{detail: <scalar str>, code, recoverable}` — a deliberate, documented
departure kept so the three TS `error.detail ??` sites keep working. Writing the
planned fixture would have re-committed the very defect class this task removes.

Worse for a copy-paste: **the two 424 producers emit different shapes.**
`/process-key` returns `_envelope_error`'s `{ok, code, human_message,
debug_context, correlation_id, recoverable}`; `/api/validate-key` returns the flat
`{detail, code, recoverable}`. The landed test's docblock warns the next author.

### 3. ⭐ **TEN unconditional skips, not six** — and the plan's count failed for the reason the guard exists

The first cut of `offencesIn` scanned **line by line**. Measured against the real
sites it **would have caught 1 of 5**, because prettier wraps the construct:

```
test.skip(
  true,
  "reason",
);
```

Four of the five were written that way. Switching to whole-file matching (line
numbers recovered from the match index) found **four more**:
`e2e/strategy-v2-chart-parity.spec.ts:47` and `e2e/sync-analytics-flow.spec.ts`
`:72`, `:154`, `:214`. This is **DEF-16-2 in a second form** — a line-based
scanner silently returning zero on a wrapped construct — reached by a different
route than the comment-blindness case, and it is why the planner's enumeration
(itself derived from the line-based `ci.yml` regex shape) was short.

### 4. A behavioural hole the fabricated 500 fixture was hiding

See **OPEN (b)** below.

### 5. `SEAM_DEGRADED` appears **nowhere** in `analytics-service`

`grep -rn 'SEAM_DEGRADED' analytics-service` → **no matches**, while 12 TS files
use it and `wizardErrors.ts` documents it as a *wire* code. The three corrected
