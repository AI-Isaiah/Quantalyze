## Design decisions (technical; recorded here so the checker and the founder can see them)

- **T-A1 (RESEARCH A1).** "Starting NAV" (D-03) is the base the day's return is divided by: in `apply_marks` the mark's `base` (the previous level plus the gap days' flows). A gap-day deposit therefore counts in the base.
- **T-A2 (RESEARCH A2).** The window is the 30 calendar days t-30 through t-1, inclusive. It always contains t-1, so a key's own first measured day has a ratio of at most 1 and is never tiny.
- **T-LM (checker revision 1).** The level map the marks are judged against is built from every mark's level always, plus the S-1 level `level_s1` (the value `base0` held before the existing `usable(base0)` check nulls it) whenever it was computed and is finite. An S-1 level at or below `dust_floor` cannot make a later usable base tiny (that base exceeds it, so it exceeds 5% of it), so including it never adds a false tiny day; leaving the map empty when `base0` is None, the first draft of this plan, left marks-only and unusable-S-1 series unjudged.
- **T-OQ4 (RESEARCH Open Question 4), decided here, implemented by plan 03, differently from RESEARCH on purpose.** RESEARCH proposed an optional `prior_levels` keyword filled by the writer-chain callers. Plan 03 computes the pre-start part of the window INSIDE `apply_marks` (`_pre_start_levels`), rolled from `level_s1`: the writer chain rolls back through its own day P&L and flows (the identity `_writer_level_before` already uses); a wallet caller rolls back through the input returns and flows with the compose's convention (`L(d-1) = (L(d) - F_d) / (1 + r_d)`, an absent day is r = 0, a NaN day uses the day P&L when given, else the roll stops). Why: no call-site change in `job_worker.py` (186), the two composite `apply_marks` call sites follow automatically, and wallet venues are covered too instead of documented as a limitation (plan 03 records the narrower remainder as KL-3).
- **T-OQ5 (RESEARCH Open Question 5), decided differently from RESEARCH, on purpose.** The compose does NOT recompute the rule from its replayed levels. The derive decides, in the key's own unit, and stores the day's P&L; the compose follows that through code that already exists. Why: (a) the compose's levels are USD, the derive judges a native-unit (BTC) MT5 key in BTC, so a compose recompute could disagree at the 5% boundary; (b) one decision point per key, no second definition of "which days"; (c) `allocator_equity_compose.py` stays untouched for 186. The cost: a stale row stays measured until that key's next derive (the nightly re-derives every key; plan 11 reads after it).
- **Precedence.** A mark with no usable base (non-finite, or at or below `dust_floor`) keeps today's "no row, the next mark covers it" outcome; only a usable base is then judged tiny.
