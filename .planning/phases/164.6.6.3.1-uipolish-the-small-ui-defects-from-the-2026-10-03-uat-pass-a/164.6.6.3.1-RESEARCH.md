## Summary

All seven items are small repairs inside files that already exist; **no new package, token, font size, colour or primitive is needed**. Every claim below was read at file:line or executed. Two throwaway experiments (a symlinked `node_modules` and a headless Chromium probe, both removed afterwards) turned four UI-SPEC assumptions into measured facts, and three of them change what the plan should say:

1. **Item 8's layout class string, as written in the UI-SPEC, does not wrap the action cluster.** `flex-1 min-w-0` gives the left block `flex-basis: 0%`, so the line-breaking step sees a zero-width item and never wraps the actions to a new row; the left block is squeezed instead. Measured in Chromium at a 420 px card: left block 63 px, nickname 80 px tall (one word per line), exactly the defect. `flex-[1_1_14rem] min-w-0` (or `flex-auto min-w-0`) wraps the whole action row as intended at every width tested (1100 to 320 px).
2. **Item 6d: wrapping the glyph in a `<span>` breaks six existing tests** in two files (`FactsheetBody.joint-floor.test.tsx` x3, `FactsheetBody.basis.test.tsx` x3), because they locate the cell by `getByText("α vs SPX")` / `getAllByText(/α vs/)`, which match an element's OWN text nodes. `first-letter:normal-case` on the label `<p>` (only when the label starts with α) gives "α VS BTC" in Chromium with **zero DOM change** and zero collateral test edits. ## Answers to the six open implementation questions

### Q1. Item 6f revoke sync: the minimal optional prop

`OwnerUnpublishedPanel` (`src/app/factsheet/[id]/v2/FactsheetView.tsx:893-935`) holds `const [shareLive, setShareLive] = React.useState(hasActiveShare);` at `:908` and passes the raw state setter as `onShareLiveChange={setShareLive}` to BOTH `ShareLinkButton` (`:920`) and `ShareRevokeControl` (`:925`). Both children already call `onShareLiveChange?.(...)`: `ShareLinkButton.mintAndCopy` calls `onShareLiveChange?.(true)` after a successful mint, `ShareRevokeControl.confirmRevoke` calls `onShareLiveChange?.(false)` after a 2xx or 404 revoke (404 = convergence) and NOT on a failed revoke. So the whole change is one optional prop and one wrapper on the panel:

```tsx
// FactsheetView.tsx, OwnerUnpublishedPanel (additive; absent prop = today's behaviour)
export function OwnerUnpublishedPanel({
  strategyId, hasActiveShare = false, shareNote, onShareLiveChange,
}: {
  strategyId: string;
  hasActiveShare?: boolean;
  shareNote?: string;
  /** 164.6.6.3.1 D-05: lets a host keep its own label in step with the panel's shareLive. */
  onShareLiveChange?: (live: boolean) => void;
}) {
  const [shareLive, setShareLiveState] = React.useState(hasActiveShare);
  const setShareLive = React.useCallback(
    (live: boolean) => { setShareLiveState(live); onShareLiveChange?.(live); },
    [onShareLiveChange],
  );
  // ...unchanged JSX, but pass setShareLive (not the raw setter) to both children
}
```

Why this shape: (a) the parent callback is invoked from the event handler path, never inside a state updater (a parent `setState` inside a child updater is a React anti-pattern); (b) with the prop absent, `onShareLiveChange?.(live)` is a no-op and the rendered DOM is identical, which a test can pin as `innerHTML` equality with and without a `vi.fn()` prop; (c) nothing is read in an effect, so there is no mount-time call. The panel's two existing callers (`page.tsx:636`, `FactsheetView` internals) and its two test files (`page.owner-compute-state.test.tsx:935`, `FactsheetView.share-affordance.test.tsx:598,614`) pass no such prop and are untouched. [VERIFIED: FactsheetView.tsx:893-935 read this session]

### Q2. Does the Modal close itself after a successful revoke?

**Recommendation: yes, close it on the live-to-not-live transition, and keep it open on a failed revoke.** Grounding:
- The repo's dialogs close on success: `RenameStrategyDialog.tsx:203` calls `onClose()` then `router.refresh()`; `MarkOwnershipDialog.tsx:194` calls `onClose()`; `ApiKeyManager` closes its delete confirm only after the awaited delete.
- The UI-SPEC's own sentence says "once the panel's state flips to not-live and the Modal closes".
- A failed revoke never reaches the callback (`ShareRevokeControl` sets `failed` and returns), so the modal stays open with its `role="alert"` "Couldn't revoke this link. Try again." The link stays live, so row and modal still agree.
- Staying open would leave a modal reading "Create share link" over a row reading "Get private link", i.e. two mint entry points and no confirmation the user can see; closing leaves the row label itself as the confirmation.

Implementation lives in `ShareableLink`, in the callback it passes: `(live) => { setShareLive(live); if (!live) setPanelOpen(false); }`. The panel unmounts in the same tick; `ShareRevokeControl` sets `setConfirming(false)` BEFORE it calls `onShareLiveChange?.(false)`, so it never sets state after unmount. **Shape (derivation mirrors `factsheet/[id]/v2/page.tsx:485-504`, `hasActiveShare = !!shareRow && shareRow.revoked_at === null`):**

```ts
// 164.6.6.3.1 D-05/D-06: ONE read, UNPUBLISHED rows only (a published row's button never reads this).
const unpublishedIds = (strategies ?? [])
  .filter((s) => !isPublishedStatus(s.status))
  .map((s) => s.id);
let liveShareIds = new Set<string>();           // FALSE-by-default is the fail-closed value (D-06)
if (unpublishedIds.length > 0) {
  const { data: shareRows, error: shareError } = await (supabase as unknown as SupabaseClient)
    .from("strategy_shares")
    .select("strategy_id, revoked_at")          // ⛔ never nonce / generation: MAC inputs (factsheet page.tsx:456-463)
    .in("strategy_id", unpublishedIds);
  if (shareError || !Array.isArray(shareRows)) {
    const message = shareError?.message ?? "the active-share read returned no rows array and no error";
    console.error("[strategies/page] active-share read failed", message);
    captureToSentry(new Error(message), { tags: { route: "strategies/page", stage: "active-share" } });
  } else {
    liveShareIds = new Set(
      (shareRows as { strategy_id: string; revoked_at: string | null }[])
        .filter((r) => r.revoked_at === null)  // derive in code, as the factsheet does, so a revoked row is testable
        .map((r) => r.strategy_id),
    );
  }
}
// ...then in the row: <ShareableLink ... hasActiveShare={liveShareIds.has(s.id)} />
```

`strategy_shares.strategy_id` is `NOT NULL UNIQUE` (migration `:168`), so there is at most one row per strategy and `.in()` returns at most N rows. With zero unpublished rows no query is issued (UI-SPEC "zero-one-many"). Failure falls back to an empty set, so every unpublished row reads "Get private link", and the failure is both logged and captured (the log line in the UI-SPEC's Copywriting Contract is `console.error("[strategies] active-share read failed", { error })`; using the page's existing `[strategies/page]` prefix is the better match to its own greps and is within the contract's "e.g."). **Do not add a visible note** (UI-SPEC: "no visible colour at all").

### Q6. D-04: how to measure the ~20 s key-list read on PROD, read-only (DO NOT RUN in this phase's research)

Evidence of the symptom is one line in the 164.6.6.3 ROADMAP entry: "edit pages flash 'No API keys connected.' for about 20 s while loading". The read is the browser-client `from("api_keys").select(API_KEY_USER_COLUMNS).order("created_at", { ascending: false })` at `ApiKeyManager.tsx:441-444`, on a table whose policy is the trivial `api_keys_owner ... USING (user_id = auth.uid())` [VERIFIED: supabase/migrations/20260405061912_rls_policies.sql:22]. A trivial policy makes a 20 s DB-side cost unlikely, so the measurement must first separate client-side stall from server time. Three steps, cheapest and most discriminating first:

1. **Browser timing (founder's own session; writes nothing).** On a strategy edit page, in DevTools console immediately after load:
   `performance.getEntriesByType("resource").filter(e => e.name.includes("/rest/v1/api_keys")).map(e => ({ startedAt: Math.round(e.startTime), stalledBeforeRequest: Math.round(e.requestStart - e.fetchStart), ttfb: Math.round(e.responseStart - e.requestStart), total: Math.round(e.responseEnd - e.startTime) }))`
   Repeat on 3 cold loads. Reading: large `startedAt` or `stalledBeforeRequest` with a small `ttfb` means the delay is before the request leaves (hydration, or the Supabase browser client waiting on its auth lock or a token refresh); a large `ttfb` means PostgREST/DB.
2. **Server side, only if `ttfb` is large.** Run the marker query first (CLAUDE.md: `SELECT shobj_description(oid, 'pg_database') AS which_database FROM pg_database WHERE datname = current_database();`, and a NULL answer means stop). Then a read-only file via `supabase db query --linked -f <file>` (no leading `--` comment; PROD reads are authorized, writes unnecessary): `BEGIN READ ONLY; SET LOCAL ROLE authenticated; SELECT set_config('request.jwt.claims', json_build_object('sub', '<owner-uuid>', 'role', 'authenticated')::text, true); EXPLAIN (ANALYZE, BUFFERS) SELECT <the API_KEY_USER_COLUMNS list> FROM public.api_keys ORDER BY created_at DESC; ROLLBACK;`. The owner uuid is the founder's own account id, supplied at run time and never written into a tracked file. Also read PostgREST latency from the Supabase API logs (service `api`, path `/rest/v1/api_keys`, `response_time`), and `pg_stat_statements` if that extension is present (`calls, mean_exec_time, max_exec_time` for statements on `public.api_keys`).
3. **Decision rule (recommended, `[ASSUMED]` threshold):** "real" = reproduces at or above 5 s on three consecutive cold loads. If real: add a `TODOS.md` entry (owner, trigger, the step-1 numbers, which half stalls) and do not fix it here. If it does not reproduce: record the three numbers in the phase SUMMARY and book nothing. Either way the "Loading keys…" caption (D-03) is what makes a slow read honest.

## Common Pitfalls

### Pitfall 1: Three page test doubles THROW on the new table
**What goes wrong:** `page.share-affordance.test.tsx:174`, `page.wizard-draft-banner.test.tsx:156` and `page.key-pill.test.tsx:314` each build a Supabase double whose `from(table)` throws `Unexpected table: <name>` for anything off an allow-list; a new `from("strategy_shares")` turns all three files red (their rows are mostly `draft`, so the read is issued).
**How to avoid:** Wave 0 (before the page edit): extend each double to answer `strategy_shares` with an empty `{ data: [], error: null }` by default; the share-affordance and key-pill files also need a seedable rows/error path for the new tests. `key-pill`'s `state.calls` is filtered by `c.table`, so a new table does not disturb its existing call-count assertions (`:493`, `:587`, `:617`, `:622`).
**Warning signs:** "Unexpected table: strategy_shares" in the first red run.

### Pitfall 2: The UI-SPEC's `flex-1` never wraps the key-card actions
See Item 8 table. Test by class tokens in jsdom (no layout there) AND keep the founder re-read, because jsdom cannot see the failure: an existing repo comment records the same limit ("mutating the controls' wrapper to `className="hidden"` left all three arms GREEN, because jsdom does no layout").

### Pitfall 3: `getByText` matches an element's own text nodes only
Any change that splits a label into child elements silently breaks `getByText`/`getAllByText` lookups (6d measured: 6 failures). Prefer CSS-only changes on the element that owns the text. For 6c the label moves into a `<span>`: `getByText("My Allocation")` now returns the span, which is fine for `MobileNav.test.tsx`, and `getByRole("link", { name })` is unaffected (verified green).

### Pitfall 4: `Modal` children are always in the DOM
See Item 6f. Conditional mount, and note a closed `<dialog>` is not guaranteed hidden to jsdom queries.

### Pitfall 5: Item 1's trap in the edit page, not the form
`strategies/[id]/edit/page.tsx` also prints `Edit: ${strategy.name}` and a breadcrumb from the server row. Nothing there needs a change, but a test that renders only `StrategyForm` will never catch a name-display regression; keep the form-level DOM assertion.

### Pitfall 6: The direct client update bypasses the rename route's rules (pre-existing, out of scope)
`api/strategies/[id]/name` enforces trim, a 1-to-80 character bound and a `private|draft` status gate (D-17); the form's browser update enforces none of them. A deliberate pick from `STRATEGY_NAMES` is an allow-listed value so the bound is moot, but the status gate is not applied. Do not widen this phase to fix it; mention it in the SUMMARY if the founder asks why the form can still rename a published row.

### Pitfall 7: Release mechanics
Per CLAUDE.md, every ship writes a CHANGELOG entry plus a `VERSION`/`package.json` bump (byte-equal 4-digit strings) in one `chore(release)` commit, and the executor must NOT mark 164.5.3 closed (D-10: only after the founder re-read). A `TODOS.md` entry is created only if D-04's measurement shows the read is real.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Reading another owner's share state (IDOR) | Information disclosure | Request-scoped client + `created_by = auth.uid()` policy + the list is already owner-filtered |
| Leaking share material to the client | Information disclosure | Select `strategy_id, revoked_at` only; pass a boolean to the client; the modal prints no URL (D-05) |
| False reassurance ("Get private link" over a live link, or "Manage" over a dead one) | Spoofing/Repudiation (honesty) | Fail closed to today's label on read failure (D-06); one state shared by row and panel |
| Share URL or token in logs/analytics | Information disclosure | Log lines carry only the error message; the panel's `trackFactsheetEvent` carries `strategy_id` only and is suppressed on share paths |
| Rename of a published row through the form | Tampering | Out of scope (Pitfall 6); D-02 narrows when `name` is sent |
