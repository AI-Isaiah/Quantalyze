## Narrative Findings (AI reviewer)

## Summary

I reviewed the changed hunks in `12eb8479..HEAD` and their immediate callers: `Modal`,
`OwnerUnpublishedPanel`, `ShareLinkButton`, `ShareRevokeControl`, `dataSourceLabel`,
`formatAbsoluteDate`, `DashboardChrome`, the `strategy_shares` migration (RLS and grants) and the
factsheet's own share-state read. I ran the 51 affected test files locally and all of them passed
(221 + 894 tests).

I checked each focus item against the code:

- **The `strategy_shares` read on /strategies is correct.** It is one `.in()` read over the
  unpublished ids only, on the request-scoped client. The owner policy (`created_by = auth.uid()`)
  and the table-level `GRANT SELECT` cover `strategy_id, revoked_at`. An error or a non-array
  answer leaves `liveShareIds` empty, which is the fail-closed outcome. Only a boolean crosses into
  the client component. Live is decided by `revoked_at === null`, matching the factsheet's rule.
  The table has `UNIQUE(strategy_id)` and no expiry column.
- **The Modal state machine cannot show a link as live when it is not.** A failed mint returns
  before `setShareLive(true)`. A failed revoke never calls `onShareLiveChange`. A 2xx or 404
  revoke flips the row and closes the Modal. A revoke that finishes after the Modal was closed
  still reaches the row's setter through the retained closure.
- **The key card's loading flag is set by every path that finishes a read.** No failed read can
  fall through to "No API keys connected."
- **D-01 and D-02 behave as specified.** An off-list name is added to the options and preselected,
  and `name` is sent only for create or when the picker changed.
- **The batch chip checks for a valid timestamp before formatting it.** "Invalid Date" cannot
  appear for any value from the database.
- **The disclaimer census has a positive control.** `DashboardChrome` renders the footer once in
  each of its two layout branches.
- **The α eyebrow uses `first-letter:normal-case` only on labels that start with α.** Tailwind
  4.3.3 ships that variant.
- **Each bottom-nav cell has `min-w-0` and the label wraps.** It adds up to exactly the 64 px
  reservation.

I found no blockers. The four warnings are about robustness when the factsheet chunk fails to
load, an unneeded type cast whose comment is false, an unsequenced catch, and timer-based tests
that can flake.

## Warnings

### WR-01: A failed lazy load of the factsheet chunk takes down the whole /strategies page

**File:** `src/components/strategy/ShareableLink.tsx:455-464` (and the mount at `:559-582`)
**Issue:** `OwnerUnpublishedPanel` is loaded with `next/dynamic(() => import("@/app/factsheet/[id]/v2/FactsheetView"))`.
That import is the entire factsheet client module, with its charts, contexts and panels. If the
chunk fails to load, the loader rejects and the dynamic component throws while rendering. This can
happen after a deploy, when a page served earlier asks for a chunk hash that no longer exists. It
can also happen on a flaky mobile connection. Nothing inside the `Modal` catches the error, so it
travels up to `src/app/(dashboard)/strategies/error.tsx`. The user clicked "Manage private link"
and the whole strategy list is replaced by the route error screen. The dynamic import exists only
to avoid a static import cycle (`FactsheetView.tsx` imports `mintShareUrl` and
`shareAffordanceMode` from this file). So this new risk comes from where the panel is kept, not
from anything the feature needs.
**Fix:** Remove the cause rather than adding a guard. Move `OwnerUnpublishedPanel`,
`ShareLinkButton`, `ShareRevokeControl`, `OwnerUnpublishedNotice` and `shareButtonLabel` into a
small module such as `src/components/strategy/OwnerSharePanel.tsx`. It would depend only on
`@/lib/share-affordance`, `mintShareUrl` and `trackFactsheetEvent`. Import it statically from
both `FactsheetView.tsx` and `ShareableLink.tsx`. The cycle goes away and so does the
`dynamic()`. If moving the code is ruled out, wrap the dynamic panel in a local error boundary
inside the Modal that renders a muted retry line instead:
```tsx
<PanelErrorBoundary fallback={<p role="alert" className="text-caption text-negative">Couldn&apos;t load the link controls. Close and try again.</p>}>
  <OwnerUnpublishedPanel … />
</PanelErrorBoundary>
```

### WR-02: An unneeded `as unknown as SupabaseClient` cast whose comment is false turns off column checking on the share read

**File:** `src/app/(dashboard)/strategies/page.tsx:77-84, 94`
**Issue:** The comment says "The generated types predate `strategy_shares`". That is not true:
`src/lib/database.types.ts:2781` has `strategy_shares` with `strategy_id`, `revoked_at` and
`created_by`. Because the cast erases the schema type, PostgREST row inference is lost. The
second cast at `:94` (`shareRows as { strategy_id: string; revoked_at: string | null }[]`) then
asserts a shape the compiler never checked. Suppose a column is renamed or mistyped, for example
`.select("strategy_id, revoked")`. The code still compiles, `r.revoked_at` becomes `undefined`,
`undefined === null` is false, and every row quietly reads "Get private link". This read exists
specifically to detect that state, and here it would go undetected with no log. The page tests
mock the client, so they would not catch it either.
**Fix:** Drop both casts and the false comment, and let the generated types check the select
string:
```ts
const { data: shareRows, error: sharesError } = await supabase
  .from("strategy_shares")
  .select("strategy_id, revoked_at")
  .in("strategy_id", unpublishedIds);
…
for (const r of shareRows) if (r.revoked_at === null) liveShareIds.add(r.strategy_id);
```

### WR-03: The mount-time `.catch` in ApiKeyManager does not check the read sequence, so a superseded read's throw can paint the error card over a good list

**File:** `src/components/strategy/ApiKeyManager.tsx:506-518`
**Issue:** Every other path in `loadKeys` is guarded by `keysReadSeqRef` and
`appliedKeysReadRef`, so an out-of-date read never overwrites a newer one. The new `.catch` runs
outside that guard. The effect runs again whenever `loadKeys` changes identity, and that happens
when `currentKeyId` changes after a `router.refresh()`. Suppose the earlier read throws after the
newer read has already finished cleanly. The catch then calls `setLoadError(...)`, and the card
shows "Couldn't load your API keys … connection problem" above a list that just loaded
correctly. The comment calls this a "first read" catch, but nothing restricts it to the first
read. The chance is low, because supabase-js usually returns `{ error }` instead of throwing.
Still, this phase's own goal is "a failure is never misreported", and the guard is missing.
**Fix:** Put the throw path inside `loadKeys`, behind the same sequence check:
```ts
let data, keysErr;
try {
  ({ data, error: keysErr } = await supabase.from("api_keys").select(API_KEY_USER_COLUMNS).order("created_at", { ascending: false }));
} catch (err) {
  keysErr = { message: err instanceof Error ? err.message : "The key list read failed." };
}
if (seq < appliedKeysReadRef.current.seq) { … return newer outcome … }
// existing error arm then handles it, and sets firstReadSettled
```
After that, the effect goes back to a plain `void loadKeys()`. The Retry button (`:1653`) and the
`onUpdated` re-read (`:1942`) also get thrown-read handling; today both leave an unhandled
rejection.

### WR-04: The new ShareableLink tests wait on real 2 s and 4 s timers with only 2 s of slack

**File:** `src/components/strategy/ShareableLink.test.tsx` (new `describe("ShareableLink — Manage private link")`, the "successful row mint flips…" and "a failed mint never claims a live link" cases)
**Issue:** Both tests wait for the component's own real `setTimeout(…, 2000)` and
`setTimeout(…, 4000)` to clear, with `waitFor` limits of 4000 ms and 6000 ms. On a loaded CI
shard (the coverage-instrumented vitest shards), the margin between timer and limit is easy to
use up. The result is an intermittent red that has nothing to do with the code. The second test
also takes over 4 s of wall-clock time by itself.
**Fix:** Use `vi.useFakeTimers({ shouldAdvanceTime: true })` and step past the windows with
`await act(() => vi.advanceTimersByTimeAsync(2000))` and `(4000)`. Then assert the label
directly instead of polling.

## Info

### IN-01: The batch chip shows no year, so a year-old batch reads like today's

**File:** `src/components/strategy/FreshnessBadge.tsx:410-413`; `src/lib/utils.ts:103-109`
**Issue:** `formatAbsoluteDate` prints `month: "short", day: "numeric"`. A batch from 2025-10-06
seen on 2026-10-06 reads "Batch: Stale · Oct 6". The chip is meant to say which batch this is,
and here it points at the wrong year. The UI-SPEC (line 142) chose this formatter on purpose, so
I am recording it rather than calling it a defect.
**Fix:** If it matters, add the year only when it differs from the current year, inside the
`showDate` branch.

### IN-02: `toTimestamp` lets through finite numbers outside Date's range, and `toISOString()` throws on them

**File:** `src/components/strategy/FreshnessBadge.tsx:385-392, 410-413`
**Issue:** A numeric `computedAt` beyond ±8.64e15 passes `Number.isFinite`. `new Date(ts).toISOString()`
then throws a `RangeError` and breaks the server render. Strings are safe, because `Date.parse`
returns NaN when out of range, and every current caller passes a string.
**Fix:** Check `Number.isFinite(new Date(ts).getTime())` instead of `Number.isFinite(ts)`.

### IN-03: After a mint, the row button's click opens the Modal while its label still shows the copy feedback

**File:** `src/components/strategy/ShareableLink.tsx:519, 533-542, 255-268`
**Issue:** `setShareLive(true)` runs before the clipboard write, so `managing` becomes true while
"Link copied!" or "Copy failed — copy the URL manually" is still on screen. A click in that window
opens the dialog, and the label does not say so. The "copy the URL manually" advice also has
nowhere to point. The row never shows the URL, and under D-05 the Modal deliberately does not
print it either. That advice was already there before this phase; this phase removes its last
possible way out.
**Fix:** Drive `onClick` and `aria-haspopup` from `managing && !copied && !copyFailed`. Separately,
reword the copy-failed label for the minted case, for example "Copy failed — use Manage private
link to retry".

### IN-04: The "Private link" dialog has no accessible name

**File:** `src/components/ui/Modal.tsx:23-30` (an existing component, newly used here)
**Issue:** The `<dialog>` has no `aria-labelledby`, so a screen reader announces it without the
"Private link" title. The new `aria-haspopup="dialog"` on the trigger is correct.
**Fix:** Give the `h2` an id from `useId()` and set `aria-labelledby` on the `<dialog>`.

### IN-05: On a successful revoke, the focused element is removed before `dialog.close()` runs

**File:** `src/components/strategy/ShareableLink.tsx:565, 575-578`
**Issue:** The confirm "Revoke" button has focus. `setPanelOpen(false)` takes the panel out of the
tree (`{panelOpen && …}`) in the same commit, and only after that does Modal's effect call
`dialog.close()`. So focus has already fallen to `<body>` before the dialog's focus-restore steps
run. Whether those steps still return focus to the row button depends on how the browser
implements the modal case of the "previously focused element" rule. The tests spy on `close()`
but never check `document.activeElement`, and the jsdom polyfill does not model focus at all.
**Fix:** Keep the panel mounted until the dialog has closed: render it under `modalMounted` and
let the Modal hide it. Or hold a ref to the row button and call `buttonRef.current?.focus()` in
`onClose`. Add a check that `document.activeElement` is the row button.

### IN-06: The disclaimer census scans only `src/app/(dashboard)`

**File:** `src/__tests__/dashboard-disclaimer-once.test.ts:22-25, 133-142`
**Issue:** A shared component under `src/components/` that renders `<Disclaimer variant="footer" />`
and is mounted on a dashboard page would print a second footer, and this census would stay green.
None exists today: the only components that render a `Disclaimer` are `StrategyV2Shell`, with the
`strategy` variant, and the landing page's `VerificationResults`.
**Fix:** Optionally, also scan `src/components/**` for the `footer` variant and allowlist
`DashboardChrome`.
