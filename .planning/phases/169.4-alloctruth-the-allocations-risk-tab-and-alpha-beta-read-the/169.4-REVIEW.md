## Summary

I checked the phase against D-64 (the pairing rule), D-65 and D-70 (null honesty), D-67 (the route
swap), D-71 (the cache key), D-75 (key labels) and D-77 (the reader move). Most of it holds:

- **Pairing vs D-64.** `pairScenarioWithBtc` and `computeBookAlphaBeta` both call 169.5's
  `alignCoveredReturns` on `COMPARATOR_CALENDARS.btc` and keep `paired[i] && value !== null`, which
  is the comparator block's filter. So day one, the unpaired interior gap and the first-stored-close
  base all hold by construction. `portfolio_daily_returns` is built from a sorted `commonDates`
  (`src/lib/scenario.ts:411`), so the helper's strictly-ascending precondition holds on both Scenario
  surfaces. The alpha/beta widget and the Overview use one normaliser, calendar and basis (365), and
  a parity test pins it.
- **Cache key.** `factsheet-v2-payload-v10` is the only `unstable_cache` key over a built payload.
  It covers the 169.4-05 and 169.4-06 shape changes (nullable allocator figures, `through`,
  null-honest signatures, multi_asset on 252). The allocator Overview payload is built per request
  and is not cached. The factsheet PDF route's CDN cache is keyed per deployment, not by a key this
  phase would need to move.
- **Deleted route.** `src/app/api/benchmark/btc/route.ts` and its test are gone. No `src` caller is
  left. The `/api/benchmark/btc` `PUBLIC_ROUTES` entry is kept on purpose because it is the prefix
  that makes `/prices` public. The limiter-ordering and node-env registries name only
  `prices/route.ts`. What remains is prose: docs, TODOS, and the `benchmark-source.ts` docblock that
  D-67 keeps.
- **Key labels.** `apiKeyLabelById` is the one rule, and both the composer and the Risk tab use it.
  `CorrelationMatrix` keys rows and columns by `strategy_id` and uses the full name as text and
  title.
- **D-77.** `readFactsheetBenchmark` in `benchmark-read.ts` matches the pre-move body byte for
  byte. It uses only an `import type` of the admin client.

Three user-facing problems remain. One is new to this phase, a null that now renders as a
fabricated 0% trajectory under a false "0 wins · 0 losses" count. The other two are carry-forward
items: the Scenario BTC overlay is not anchored to the scenario's start, and the allocator tail
figures print 0 when there are no stress windows.

## Critical Issues

### CR-01: A missing BTC series renders as "0 wins · 0 losses" over flat 0% benchmark panels, beside populated equity panels (carry-forward item 1, now reachable by default)

**Files:**
- `src/lib/factsheet/event-signatures.ts:44-46` (`aggregate([])` returns six all-zero series)
- `src/lib/factsheet/event-signatures.ts:169-170` (`winCount: winBench.length`, `lossCount: lossBench.length`)
- `src/lib/factsheet/build-payload.ts:602,820,825`
- `src/app/factsheet/[id]/v2/SignaturePanels.tsx:58,64`
- `src/app/factsheet/[id]/v2/CrossSignaturePanels.tsx:91,97`

**Issue:** 169.4-05 (D-70(1)) drops a benchmark trace whose 28-day window reads a BTC null. The
equity trace of `eventSignatures` checks `stratRet`, the strategy's own series, which is never null,
so it is kept. The title counts are still `winBench.length` / `lossBench.length`, which count
BENCHMARK traces only, and an empty trace set aggregates to all-zero arrays instead of an absence.

Failing scenario: the BTC read fails (`readFactsheetBenchmark` answers `{ unavailable: true }`, and
D-52 lets that form be cached for the whole TTL). Or BTC's last stored close is more than 14 days
before the strategy's last date. Then `apiAl.btc` is null and `btcAligned` is all null
(`build-payload.ts:602`). Every `bTrace` is null, and every `eTrace` is built. The api-arm
factsheet then shows three contradictory things:
- "Returns Signatures for 7 Days Horizon (0 wins · 0 losses)" (`SignaturePanels.tsx:58`, and `:64`
  for 1 day);
- "Win Event · of BTC" and "Loss Event · of BTC" drawn as a flat 0% mean, median and band, which is
  a fabricated benchmark trajectory;
- "Win Event · of Accumulated Capital" fully populated from the hundreds of events the title says do
  not exist.

`CrossSignaturePanels` (`benchEventSignatures`, `stratRet = btcAligned`) shows "0W · 0L" and four
flat-zero panels. Before this phase, `nullAsZero` kept the counts equal to the equity panels (the 0
was wrong in a different way). So 169.4 turned a wrong-number panel into a panel that contradicts
itself. Interior BTC gaps cause the same count mismatch at a smaller scale, because each missing or
dropped close silently removes up to 28 events from the title and the benchmark panels only.

**Fix:** Count each view by its own traces, and render an absence for an empty trace set, never an
all-zero series.
```ts
// event-signatures.ts: an empty trace set is an absence
function aggregate(traces: number[][]): EventSignature | null {
  if (traces.length === 0) return null;
  ...
}
// computeHorizon: counts per view
return {
  horizonDays,
  winCount: winEquity.length, lossCount: lossEquity.length,           // the equity panels' N
  benchWinCount: winBench.length, benchLossCount: lossBench.length,   // the benchmark panels' N
  eligibleWinCount, eligibleLossCount,
  winOfBenchmark: aggregate(winBench), ...
};
```
Then in `SignaturePanels` / `CrossSignaturePanels`: a null `EventSignature` renders the DESIGN.md
em-dash state ("No BTC trajectory: BTC prices unavailable over these windows"), not a chart. Each
pair of panels names its own N. When the BTC comparator is unavailable (`payload.comparators.btc`
carries the unavailable form), do not render `CrossSignaturePanels` at all. This changes the payload
shape, so move the cache key to v11 in the same change (the D-71 pattern).

## Warnings

### WR-01: The Scenario BTC overlay is not anchored at the scenario's first date, so BTC starts several times above the 1.0 portfolio line (both Scenario surfaces)

**Files:**
- `src/app/(dashboard)/allocations/lib/scenario-benchmark.ts:145-149` (`btcLevelsFromCloses`: `close / prices[0].close`)
- `src/app/api/benchmark/btc/prices/route.ts:136` (`mergeWithFixture(read, BTC_DAILY)`: `prices[0]` is the fixture's 2023-04-26 close whenever the DB starts later)
- `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:2252-2256`, `src/app/(dashboard)/allocations/widgets/performance/scenario-factsheet-payload.ts:453-463`
- `src/app/scenario-share/[token]/page.tsx:295`, `src/app/(dashboard)/allocations/widgets/performance/EquityChart.tsx:615-627`

**Issue:** The overlay is `close / first close` of the WHOLE served series. Neither consumer
re-bases it to the scenario's window:
- The composer's `ScenarioFactsheetChart` copies the levels verbatim into `comparators.btc.cumulative`
  (`scenario-factsheet-payload.ts:460`). `resolveSeries` never re-bases a comparator
  (`chart-configs.ts:271-289`), and re-bases the strategy only when zoomed.
- The share page's `EquityChart` runs `anchorFromFirstPositive(benchmark)`, which anchors at the
  benchmark's OWN first point, not at the composite's first date (`EquityChart.tsx:619`).

Failing scenario: a scenario whose portfolio returns start on 2026-01-05, and a BTC series whose
first served close is 2023-04-26 (about $28k; the fixture prefix D-67 now prepends). At the
scenario's first date the portfolio line reads 1.0 and the BTC line reads close(2026-01-05) / 28k,
about 3 to 4 times higher. The comparison is visually meaningless: the default-zoom chart implies
BTC gained 200-300% before the portfolio's first day, and the Y-domain flattens the portfolio line.
The same un-anchored construction existed before (compounded from the DB's first stored date). 169.4
made it worse by moving the base to the fixture's first close, and its overlay tests use series
whose first close is the scenario's first date, so they cannot see this.

**Fix:** Base the level on the last close on or before the portfolio's first date. That is the
anchor the factsheet comparator block has by construction (`cumEq` over the covered window).
```ts
export function btcLevelsFromCloses(
  prices: readonly DailyPrice[],
  fromDate?: string,
): DailyPoint[] {
  let i0 = 0;
  if (fromDate !== undefined) {
    // the last close on or before fromDate is the base (level 1.0)
    let j = -1;
    for (let k = 0; k < prices.length && prices[k].date <= fromDate; k++) j = k;
    i0 = j >= 0 ? j : 0;
  }
  const base = prices[i0]?.close;
  if (base === undefined) return [];
  return prices.slice(i0).map((p) => ({ date: p.date, value: p.close / base }));
}
// callers: btcLevelsFromCloses(btc.prices, portfolioDaily[0]?.date)
```
Add a test whose closes begin well before the scenario and assert that the overlay equals 1.0 at
the scenario's base date.

### WR-02: An allocator blend with zero stress windows prints "+0.00%" / "+0.00%" / "0%" for mean, median and windows-positive (carry-forward item 2; conflicts with D-65/D-70's em-dash rule)

**Files:**
- `src/lib/factsheet/allocator.ts:329-338` (`tailMean`, `tailPos`, `tailMedian` seeded to 0)
- `src/lib/factsheet/allocator.ts:351-354` (emitted as numbers)
- `src/app/factsheet/[id]/v2/BatchDPanels.tsx:367-378`

**Issue:** When `tailMm.length === 0` (a measurable blend where the portfolio never drew 5% or more
in any 21-day window, or every window was dropped for a null under D-70(2)), `buildAllocatorMetrics`
returns `tail_count: 0` with `tail_mm_mean: 0`, `tail_mm_median: 0` and `tail_mm_pos: 0`. The
BatchDPanels renderers em-dash null values only, so the panel reads "MultiMarket mean return
+0.00%", "MultiMarket median return +0.00%" and "Windows MM was positive 0%". The caption right below
says there were no stress windows. A mean and median of an empty set do not exist, and "positive 0%
of the time" claims every window was negative.

Failing scenario: the SPX/GLD/IEF fixtures end 2026-05-08, so for most live api strategies the
60/40 and multi_asset blends now keep only a few pre-May weekday windows. D-70 made "no window
survives" more common, not rarer.

**Fix:**
```ts
const hasTail = tailMm.length > 0;
...
tail_count: tailMm.length,
tail_mm_mean: hasTail ? tailMean : null,
tail_mm_median: hasTail ? tailMedian : null,
tail_mm_pos: hasTail ? tailPos : null,
```
`AllocatorMetrics` already types these as `number | null`, and `pctSigned2` / `pctRound` already
em-dash null, so no renderer change is needed. The payload shape changes, so this rides the same
cache-key move as CR-01.
