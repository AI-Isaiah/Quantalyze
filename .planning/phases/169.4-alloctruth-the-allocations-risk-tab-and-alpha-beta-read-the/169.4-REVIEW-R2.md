## Critical Issues

### CR-01: Both signature sections label BTC data with the ACTIVE comparator's name, and fix B carried the wrong name into the new per-panel titles and empty-state reasons (pre-existing, widened this round)

**Files:**
- `src/lib/factsheet/build-payload.ts:827` (`computeEventSignatures(stratRet, btcAligned, …)`) and `:832` (`benchEventSignatures` built from `btcAligned`): both payloads are ALWAYS BTC.
- `src/app/factsheet/[id]/v2/SignaturePanels.tsx:44,64,70` (`benchName={cmp.shortName}` from `useActiveComparator()`), `:104-116` (titles `of ${benchName}` and the new `emptyReason` strings `…window of ${benchName} prices`), `:157` (the new `· N events` title)
- `src/app/factsheet/[id]/v2/CrossSignaturePanels.tsx:39,54,57,64` (subtitle and `benchName` from the active comparator), `:99` (legend `${benchName} events`), `:105-121` (titles, `view={`${benchName} prices`}`), `:181,186` (the new `no ${benchName} event` reason and the `${benchN} ${benchName} events` title)
- `src/app/factsheet/[id]/v2/ComparatorPicker.tsx:13` (`KEYS = ["btc", "spx"]`); `factsheet-context.tsx:328` also sets the comparator from the URL.

**Issue:** open any api-arm factsheet and click SPX in the comparator picker, or load it with the SPX
URL parameter. The Signatures section then reads "Win Event · of SPX · 86 events" and "Loss Event · of
SPX". The Cross-Signatures section reads "SPX events" in its legend and "…vs SPX-indexed mean (muted)" in
its subtitle, and titles each panel "… 86 strategy / 90 SPX events". Every one of those lines plots BTC:
BTC trajectories around the strategy's events, and BTC's own up and down days as the "SPX events". A
reader comparing the strategy's behaviour around SPX moves is shown BTC. That is a fabricated attribution
on a document surface.

The mislabel is older than this phase: the titles used `cmp.shortName` at `32494ba25`. The CR-01 fix
widened it. The per-panel counts (`… · 90 SPX events`) and the new em-dash reasons now name SPX as well.
So with BTC unavailable and SPX active, the empty state says *"Not measurable: no win event has a complete
±14-day window of SPX prices."* It blames SPX, whose fixture is intact, for a BTC read failure. With BTC
active, the same reason still describes an outage as missing windows ("no … complete ±14-day window of
BTC prices"). That is the wrong-cause class that fix A removed from `BatchDPanels` under SFH MEDIUM-2.
Round 1's fix text proposed the outage copy ("BTC prices unavailable over these windows").

**Fix:** the payload's benchmark is BTC by construction, so label it BTC, and name the outage when the
BTC alignment has no close:
```tsx
// SignaturePanels.tsx / CrossSignaturePanels.tsx — the signatures are BTC-only (build-payload.ts:827,832)
const SIG_BENCH = "BTC";
const btcUnavailable = payload.comparators.btc.through === null; // unavailableAlignment(): through null
...
benchName={SIG_BENCH}
emptyReason={btcUnavailable
  ? "BTC prices are unavailable right now"
  : `no win event has a complete ±14-day window of ${SIG_BENCH} prices`}
```
An alternative is to render both sections only when `cmpKey === "btc"`. That hides the section when SPX
is picked instead of mislabelling it. Either way, add a test that mounts the section with `activeComparator:
"spx"` and asserts that no rendered string contains "SPX". Confirm that `comparators.btc.through` is the
marker the unavailable form carries before relying on it (`build-payload.ts:176-178` sets `through: null`
on the alignment).

## Warnings

### WR-01: "Stress windows in sample 0" is printed when no window could be examined (the WR-02 class, left in the count)

**Files:**
- `src/lib/factsheet/allocator.ts:393` (`tail_count: tailMm.length`, which is `0` whenever `tailWindows === 0`)
- `src/app/factsheet/[id]/v2/BatchDPanels.tsx:371` (`p.tail_count === null ? "—" : String(p.tail_count)`)

**Issue:** fix A nulled the mean, median and positive share for an empty stress set, but left the count at
`0` when nothing was examined. A blend is measurable (`own.length >= 2`) when it has 2 to 21 blend dates.
In that case the tail loop (`for (let i = TAIL_WINDOW; i < n; i++)`) never runs, so `tail_windows` is 0
and `tail_count` is 0. The panel then shows "Stress windows in sample **0**" directly above the new
caption *"No 21-day window with every leg priced, so no stress window could be measured."* The table
states a measured zero, and the caption says right below it that nothing was measured.

Failing scenario: any api-arm strategy whose first date is after roughly 2026-04-08. The SPX, GLD and IEF
fixtures end 2026-05-08, so its 60/40 and Multi-Asset blends have fewer than 22 common weekdays. That
covers every strategy connected in the last five months, and the Overview of any allocator whose book
started then. The same happens for a blend in which every window holds a dropped close.

**Fix:** a count over zero examined windows is an absence, like the mean.
```ts
// allocator.ts
tail_count: tailWindows > 0 ? tailMm.length : null,
```
```tsx
// BatchDPanels.tsx:377 — the caption no longer needs tail_count to be non-null for the zero-window case
{p.tail_windows !== null && (
  <p …>{tailCaption(p.tail_count ?? 0, p.tail_windows, p.tail_mm_pos)}</p>
)}
```
Update the test that pins `['0', '—', '—', '—']` for this case to `['—', '—', '—', '—']`, and keep the
`tail_windows > 0, tail_count === 0` case at `'0'`. There a zero is measured.

### WR-02: D-70(2)'s definition of a blend date was changed in code but not amended in CONTEXT.md or the ROADMAP

**Files:**
- `src/lib/factsheet/allocator.ts:148-164` (`blendDates = calendarDates.filter(d => closeSets.every(c => c.has(d)))`), `:190-204` (`through` is now read from the legs' prices against the last calendar date, not from the alignment)
- `.planning/phases/169.4-…/169.4-CONTEXT.md` D-70(2) and D-70(4): not touched in `4145f48be..HEAD` (`git log` on the file is empty)

**Issue:** D-70(2) defines the blend as *"built on its legs' COMMON calendar (the strategy dates falling on
a weekday every leg carries …) … A blend index is null when any leg is null"*. The code now also requires a
close from every leg on the date. So a US holiday, a date past a fixture's last close, a BTC gap and a
dropped close are no longer null blend dates. They are not blend dates at all. That changes what `tail_windows`,
`cum_ret`, `ann_vol` and `through` mean, and it moved snapshot figures (fix-A report: `multi_asset.cum_ret`,
`sixty_forty.tail_count`). The change is sound, because it removes HIGH-1's lost BTC move. But the decision
the verifier reads still describes the old rule. A verifier checking D-70(2) literally will find the code
out of spec. A later planner re-basing the blend on D-70 will re-introduce the holiday null.
CLAUDE.md's deviation policy requires the record in the phase's CONTEXT.md and in the ROADMAP, not only in
a fix report.

**Fix:** no code change. Add a dated amendment under D-70 in `169.4-CONTEXT.md`, and a matching line in
the ROADMAP's 169.4 entry. The amendment should say: "blend dates are the calendar-shared strategy dates on
which every leg has a non-dropped close; the day after a holiday is unpaired for the weekday legs;
`through` is each leg's last close on or before the last calendar-shared date (review round 1, SFH HIGH-1)".
Keep the original sentence as lineage.
