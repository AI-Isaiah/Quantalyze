### D-66: SC11 is met by pairing, not by changing the returns rule (planner, revision 2026-09-30)
- **Why.** SC11 (TODOS `[169.2-BTC-GAP-RETURN-STAMP]`) asks for the overlay from closes and the metrics
  from exactly-one-day returns. `pricesToDailyReturns` must keep bridging a missing day (169.2 reverted
  its skip-every-gap attempt because the overlay drifted), so the fix is in the consumers.
- **Decision.** (1) The Scenario and scenario-share BTC overlay is the close level
  (`close / first close`) at each stored close date, never compounded returns. Measured fact, stated so
  no test pretends otherwise: across a plain missing day the two constructions give the same level; they
  differ across a DROPPED (corrupt) close, where the compounded curve loses the move for good. The
  overlay tests therefore pin both: no point on the missing day or the dropped date, and every later
  level equal to `close / first close` (the dropped-close case is the one that goes red under
  compounding). (2) The benchmark-relative metrics pair through D-68, so a return that bridges a missing
  stored day is never paired as one observation: a paired interval needs every date of BTC's own
  calendar inside it (169.5 D-64(2), 166.4 review WR-01). For a 7-day portfolio that is exactly the
  one-day rule SC11 states. For a sparser portfolio the paired BTC move spans the portfolio's own
  interval (166.4 D-A, founder); where SC11's literal "exactly-one-day" and D-A differ, D-A wins,
  because the founder ruled the engine's pairing governs every surface (2026-09-27).
- `pricesToDailyReturns` and `benchmark-source.ts` are not edited.
- **Reversibility:** reversible.

### D-67: The Scenario surfaces read BTC CLOSES from a new public route; the returns route is removed (planner, revision 2026-09-30)
- **Why.** The Scenario composer (a client component, fetch on mount) and the scenario-share page
  (server, self-fetch with the WR-03 timeout) read `/api/benchmark/btc`, which serves bridged RETURNS.
  D-66 and D-68 need closes plus the `dropped` list. The route's body is cached
  `public, s-maxage=3600, stale-while-revalidate=86400`, so changing the body at the same URL lets a new
  client read an old-shape body for up to a day.
- **Decision.** A new route `GET /api/benchmark/btc/prices` answers
  `{ prices, dropped, through }`: `readBenchmarkPrices(client, "BTC")` UNBOUNDED, merged with
  `mergeWithFixture(read, BTC_DAILY)` so the fixture fills only dates strictly before the DB's first
  stored date (D-09, the factsheet's rule). An unbounded read's first row is the DB's true first stored
  row (dropped rows included), so the one-row probe of 169.5 D-64(4) Amendment B is not needed here; this
  is the 169.2 reader `readFactsheetBenchmark` wraps, so no second read is written. Same rate limiter,
  same cache headers, a read error is a 503 with `no-store` (169.2 SFH MD-05). It is public through the
  existing `/api/benchmark/btc` entry of `PUBLIC_ROUTES` (`proxy.ts` matches `route + "/"`). Both
  clients validate the body's shape; a body that is not that shape is "unavailable", never a partial
  series. Once no in-repo consumer reads it, 169.4-04 deletes the returns route and its test (⛔ amended
2026-09-30, plan-check round 1: 169.4-08, split out of 169.4-04, deletes them in wave 3, and removes the
test's `vitest.node-env.ts` entry; the bare-path check excludes `benchmark-source.ts`, whose two
docblock sentences are the route's history and are not edited under D-66): it serves
  the exact bridged-returns shape SC11 names, and keeping it invites a new consumer. A stale browser tab

### D-70: D-65's panels are null-honest: blends on the legs' common calendar, windows break on a null (planner, revision 2026-09-30; applies 169.5 D-65)
- **Why.** Measured at `f1ca32b56`: the SPX, GLD, IEF and ETH fixtures end 2026-05-08 to 2026-05-11, so
  every api-arm panel (and the allocator Overview, whose payload is `ingestSource: "api"`) today reads
  about 140 days of those legs as 0% days, and SPX, GLD and IEF are null every Saturday and Sunday
  against a 7-day book (the D-58 series rule). "Break on the first null" would therefore empty every
  panel with a weekday leg, and plain compaction on the strategy's dates would drop BTC's weekend moves
  from the multi-asset blend (a new wrong number, the class the D-58 amendment rejected).
- **Decision.** (1) Event signatures (`computeEventSignatures`, feeding SignaturePanels and
  CrossSignaturePanels): an event whose verdict reads a null is skipped, and a benchmark or equity trace
  whose 29-day window touches a null is dropped, like an edge event today; `benchEventSignatures` gets
  the same rule on BTC's own nulls. (2) Allocator portfolios (`blend` / `buildAllocatorMetrics`, feeding
  BatchDPanels): each blend is built on its legs' COMMON calendar (the strategy dates falling on a
  weekday every leg carries, from `COMPARATOR_CALENDARS`), every leg aligned on those dates through
  `alignCoveredReturns`, and the book aligned the same way from its own level series (level 1 dated the
  day before its first return, then the compounded level at each date; that base level is the
  definition of a return series, not an invented close). A blend index is null when any leg is null and
  paired when every leg is paired. Own-series figures (vol, cumulative return, drawdown) use the
  non-null indices; the correlation and the sleeve scan use the paired ones; a 21-day tail window
  containing a null is dropped. (3) Basis: the blend's calendar frequency, which is the smaller of its
  legs' `annualizationPeriods` (169.5 D-59's rule). 60/40 stays 252 and crypto_book stays 365;
  **multi_asset moves 365 -> 252. This supersedes #597 BLEND-02's "any crypto leg -> 365" for that one
  panel**: BLEND-02 assumed the joined series is calendar-daily, and once weekend nulls are honest it is
  weekday-frequency, where 365 inflates vol about 1.2x (the error class D-59 fixed). Surfaced to the
  founder in the planner's return. ⭐ **Founder ruling, 2026-09-30 (AskUserQuestion): "Allow 252 here".**
  A narrow exception to #597 BLEND-02 for the multi_asset allocator-portfolio panel only, because its
  points are weekdays once weekend gaps are no longer 0-filled. The 60/40 blend stays 252 and the
  crypto_book blend stays 365; BLEND-02 stands everywhere else. The basis is computed from an explicit
  leg -> asset class map through `annualizationPeriods` (169.4-06), since `COMPARATOR_CALENDARS` maps a
  key to a calendar only. (4) A blend with fewer than 2 usable observations has `metrics: null`
  and a `through` date; BatchDPanels renders the em-dash (DESIGN.md) with a dated "prices through
  <date>" caption, never a figure. (5) The null-as-0 helper in `build-payload.ts` and its five named
  locals are deleted.
- ⛔ **AMENDED 2026-09-30 (round-1 review SFH HIGH-1, fix `d74aa4af7`; recorded per round-2 review WR-02).**
  (2)'s blend calendar is narrowed: a blend date is a strategy date on every leg's calendar WHERE EVERY
  LEG ALSO HAS A STORED CLOSE. A US-market holiday (a weekday with no SPX/GLD/IEF close) is therefore
  not a blend date, and dates past a fixture's end are dropped rather than nulled; the next common date
  carries each leg's full close-to-close move, so BTC's move across the holiday is kept (under the
  original wording a holiday nulled the whole blend and BTC's move into it was lost: 20 moves,
  about -10% of BTC over 2024-25). Consequence, by design: the day after a holiday is unpaired for the
  weekday legs, so the correlation and sleeve scan skip about 10 days a year. Tail windows now run over
  the common-calendar series and report how many were examined (`tail_windows`); with no stress window
  the tail figures are null, never 0. The basis ruling in (3) is unchanged. The text above is lineage.
- Rejected: break on the first null (empties every weekday-leg panel); compaction on the strategy's
  own dates (drops BTC's weekend moves from multi_asset); keeping 365 for multi_asset (1.2x vol).
- **Reversibility:** reversible (TypeScript only; no stored value).
