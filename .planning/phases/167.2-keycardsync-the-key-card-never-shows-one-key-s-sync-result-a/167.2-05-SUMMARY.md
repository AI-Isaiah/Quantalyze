# Phase 167.2 Plan 05: the key card bounds the link update and the enqueue, and an expiry says what it could not confirm Summary

**The link update and the `/api/keys/sync` enqueue each have a client-side bound now: 15 s for the link and 180 s for the enqueue. When one expires, the attempt ends in a new amber `unconfirmed` state. The link case reads "Sync not started" and no enqueue is ever sent. The enqueue case reads "Sync not confirmed", with a sentence saying the sync may still be running. Neither line says "failed", and neither panel has a Retry. An answer that lands after its bound is logged and dropped: a late 202 starts no poll. The panel's status label is now its one polite live region, so these states are announced when they arrive.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - plan inconsistency] The late answer is awaited after an expiry, so the guard is the thing that drops it**
- **Found during:** Task 1
- **Issue:** The action text says to race the enqueue "exactly like the TERMINAL_REREAD_BOUND_MS race" and to handle expiry. A literal race-and-return leaves the function at the bound, so a late 202 would never reach `if (attemptRef.current !== attempt) return`. The must-have "neutering the late-answer guard turns LATE-202 RED" could then never be met, because that neuter would stay GREEN. The plan's own words, "the guard below handles it", show that it expects the late answer to reach the guard.
- **Fix:** After the timed-out branch ends the attempt, it awaits the original promise. A late success logs a `console.warn` and then meets the guard. A late rejection reaches the existing catch, where `endAttempt` answers false and the existing "failed after its attempt ended" warn runs. The link race does the same, but it `return`s after the late answer, so it never goes on to the baseline read.
- **Files modified:** `src/components/strategy/ApiKeyManager.tsx`
- **Verification:** N1b and N2b above
- **Committed in:** `f916c78e1`, `2fea0ad9a`

**2. [Process] Task 2 committed as test then feat, and two extra neuters**
- The RED tests went into their own commit before the implementation, so Task 2 has two commits where the plan asks for one per task. I also ran N2b and N2c beyond the one neuter Task 2 requires, so the late-link return and the live region each have a bite recorded.
