# Phase 167.2 Plan 06: composite key card and applied-read retirement Summary

**A composite strategy's key card can no longer rewrite `strategies.api_key_id` (no Resync, Use & Sync or Add Key, and the handlers refuse), an unreadable member count fails closed on those controls while keeping Update password and Delete, and a success judged beside an untrusted key is retired at that moment so no later re-read, including another tab's fix or delete, can bring it back.**

## Accomplishments

- KCS-23: the edit page head-counts `strategy_keys` on the request client (`countCompositeMembers`) for API-key strategies only, and passes `keyShape` to `ApiKeyManager`. The card's `linkControlsAllowed` (`keyShape === "single"`) gates the header `Add Key`, the `ApiKeyForm`, and every key's `Resync` / `Use & Sync`; `handleSyncTrades` and `handleAddKey` return, and `handleLinkKey` throws, when it is false. A composite shows `COMPOSITE_CARD_NOTE` directly under the header. Avatar, label, exchange line, MT5 account line, `Update password`, `Delete` and the `AllocatorSyncStatus` block are unchanged.

- KCS-04: `loadKeys` resolves `{ ok, subjectStatus }` (`KeysReadOutcome`) from the rows it applied, and `appliedKeysReadRef` carries the applied subject status so a WR-04-dropped read answers with it. The terminal arm sets the success only when the re-read is `ok` and the subject is trusted, else lands on idle. `retireWithheldSuccess(subjectUntrusted = panelSubjectUntrusted)` gains its new call site in `loadKeys`, still one helper with its functional updater. `lastAttemptedKeyIdRef` mirrors the subject for the memoised `loadKeys`. `withholdPanelSuccess` stays as a render backstop; no effect watches it (`useEffect` count 2 before and after).
