# Phase 167.2 — UI Design Contract

> Visual and interaction contract for Phase 167.2 (KEYCARDSYNC — a status the owner reads is
> about the thing it names, and never promises an outcome that is not coming).
>
> ⛔ **THIS IS A COPY-AND-STATE SPEC, NOT A LAYOUT SPEC.** Every surface already exists. The phase
> adds truthful state lines to them. It introduces **NO new component, NO new page, NO new colour,
> NO new token and NO new font weight**. Two existing components gain one OPTIONAL prop each
> (`ApiKeyForm`, `OwnerUnpublishedPanel`), and `SyncProgress` gains UI-only states. Each is named
> below with the reason. Restyling anything else is out of scope (CLAUDE.md Rule 3).
>
> **Autonomous run (`--auto`, founder asleep).** No question was asked. Every choice below is
> taken from `DESIGN.md`, the shipped components, `167.2-CONTEXT.md` (KCS-01..KCS-23; section E's
> KCS-18..KCS-23 SUPERSEDE the clauses they name) and `167.2-RESEARCH.md`. `DESIGN.md` is not
> deviated from.
>
> **Carried forward unchanged from `167-UI-SPEC.md`:** the `AllocatorSyncStatus` locked copy table
> (`Key revoked`, `Sign-in failed`, `REVOKED_HELPER`, `CREDENTIAL_FAILED_HELPER`, `Syncing…` with
> U+2026, the U+2014 em-dash strings), its `PILL_STYLES` map, S1b's placement and R1..R6 (except
> where KCS-01 replaces R6's post-add clause and KCS-04 replaces R2's "withheld" by "retired",
> KCS-05). This spec rewords none of them.
>
> **Public repo.** Every example below uses synthetic placeholders (`{keyLabel}`, `{n}`, `{m}`,
> `{id}`, `Bybit`, `OKX`). No real strategy name, id, token or path appears.

### Visual anchor per surface

The one element the eye lands on first, and the question it answers. No anchor is created by
size or weight; each is an existing slot, and the anchor is won by position and tone.

| # | Visual anchor | Why it is read first |
|---|---------------|----------------------|
| S1 | the disabled `Connect Key` button | it is the control the owner reached for; the `KCS01-*` line sits directly above it in the caption slot and is tied to it by `aria-describedby` |
| S2 | the panel's status row (icon + label) | the only 14px/500 text in the panel; on `unconfirmed` it is also the only amber on the card. The detail line beneath is the second read |
| S3 | the `KCS23-COMPOSITE` line | first line under the `Exchange API Keys` header, above every key card, so the absence of controls is explained before it is noticed |
| S4 | the `AllocatorSyncStatus` pill | the only filled, coloured mark in the row card; the left caption names which key it is about |
| S5 | none of its own | a muted caption at the end of the footer band; it answers a secondary question and must not compete with the row name or an S4 pill |
| S6 | the **Computation status state line** | read BEFORE the share panel for the founder's test ("is anything happening, and do I need to do something?"): see below |
| S7 | the panel's existing uppercase heading (unchanged) | the new `shareNote` is its last, muted child |
| S8 | the H1 (strategy name), then the single sentence | only one sentence exists, so there is nothing to rank |
| S9 | the `EmptyStateCard` heading (unchanged component) | the card's own hierarchy |

**S6: the state line is the anchor, and the share panel is read as a frame around it.** The
panel's DOM-first position is LOCKED by an earlier checker-approved spec (the disclosure precedes
any document content), so this phase does not move it. It is a bordered, `bg-surface-subtle` box
of 12–13px muted captions under a small uppercase heading, which reads as page chrome. Below it
the large serif H1 names the strategy, and the state line is the first sentence of the document
body directly beneath the H1, the only text on the page that carries amber or red when something
is wrong. The founder's question is answered in ONE read of two adjacent lines: the state line
says whether anything is happening, and the remedy line directly under it (`mt-3`) says whether
the owner needs to do something. ⛔ No state or remedy content goes into the share panel, and the
S7 note says only what a recipient sees, so the two blocks never answer the same question.

surface family, not by preference: the app chrome (key card, `/strategies`) already sets its

|------|-----------------------|------|--------|-------------|----------------------|

| State line | `text-fixed-13` | 13px | 400 | Tailwind default (1.5 on DM Sans body) | S6 state line, S8 public sentence |
| App caption | `text-xs` | 12px | 400 | Tailwind default (1rem) | S1 blocked reason, S2 detail, S3 note, S4 caption, S5 share note |
| Factsheet caption | `text-fixed-12` | 12px | 400 | Tailwind default | S6 remedy line (existing slot), S7 share note |

- ⛔ **`text-caption` is NOT used by anything this phase authors.** It is fluid (clamp 12→13px).
  S7's note takes `text-fixed-12`, so it renders a fixed 12px even though the notice body above it
  (unchanged `OwnerUnpublishedNotice`) is `text-caption`. The ≤1px difference is accepted: the
  note is its own paragraph after the control row, and a fixed size keeps the role one token.
- **Declared sizes new copy lands in: 12, 13, 14, plus S9's inherited `text-micro` (fluid
  10→11px, unchanged `EmptyStateCard` body, not chosen here).** Four sizes.
- **Weights this phase authors: exactly two, 400 and 500.** 400 for every new sentence, 500 only
  on the S2 panel label (the slot's existing `font-medium`). **600 is inherited, not chosen**: it
  comes from the unchanged `EmptyStateCard` heading (S9) and the unchanged
  `OwnerUnpublishedNotice` heading (S7). Every new content block carries at most two weights (S2:
  500 label + 400 detail; S9: 600 inherited heading + 400 body; every other block: 400 only).
  ⚠️ Measured 2026-09-23: some host surfaces' EXISTING chrome already carries more than two
  weights (the key card has a 600 section heading, a 700 avatar initial and 500 `Button` labels;
  the owner pending page has a 600 notice heading and 500 share buttons). This phase adds no weight
  to any surface and restyles none of that chrome (Rule 3).
- ⛔ `no-raw-font-px` is repo-wide `error`: no raw `text-[Npx]`.
- **Numbers inside prose stay in the body voice.** `key {n} of {m}`, `12 minutes`, `2 minutes`,
  `3 minutes`, `15 seconds`, `30 seconds` are thresholds and counts inside a sentence, not figures
  in a column, so they are DM Sans, not `.font-metric`. House precedent: `Usually takes 15–30
  seconds`, `Drafts expire after 30 days`.
- **Length budget.** S2 detail and S6 lines are prose in wide containers (≤ 760px article, full
  panel width) and may wrap to two lines. S4's caption must stay one line at 1024px and wrap
  cleanly at 320px (see § UI Considerations). No string interpolates unbounded text except

## Copywriting Contract

⛔ **Every string in this section is LOCKED VERBATIM** (KCS-14, the 167 D-11 house convention):
unit tests pin each one character for character. Conventions for every new string:

- Apostrophe is ASCII `'` (U+0027), as in the shipped `CREDENTIAL_FAILED_HELPER` and `isn't ready yet`.
- `—` is U+2014 (only where marked). `·` is U+00B7. No `…` is authored.
- Sentence case, declarative, active voice, terminating period. No exclamation, no adjective where
  a number exists, a limit states its threshold (DESIGN.md § Voice).
- `{…}` marks an interpolation slot. Nothing else varies.
- Numeric thresholds are rendered FROM the named constants (`STALL_THRESHOLD_MS`,
  `POLL_MAX_ATTEMPTS` × poll interval, the KCS-03 bound constants). If the planner chooses a
  different bound value, the rendered number changes with it in the same commit and the pin moves
  with it. The values below are the researched ones (RESEARCH Q2: link 15 s, enqueue 180 s).

### A. Key card (S1–S3)

#### KCS-01 — Add Key blocked while an attempt is live (S1)

Rendered in `ApiKeyForm`, in the caption slot directly above the button row (`mt-3`, the slot the
form's `error` line uses; `error` renders above it when both are present), as
`<p id="…" className="text-xs text-text-muted mt-3">`. The `Connect Key` submit is `disabled`
(existing `Button` disabled style, label unchanged) and carries `aria-describedby` pointing at the
line. The Enter-key path inside the form's `handleSubmit` is blocked the same way.

| ID | Condition | Copy |
|----|-----------|------|
| `KCS01-BLOCKED` | form open AND a tracked attempt is live AND the attempt's key has a non-empty label | `Wait for the sync of "{keyLabel}" to finish before connecting another key.` |
| `KCS01-BLOCKED-NOLABEL` | same, label empty | `Wait for the current sync to finish before connecting another key.` |

- `"` is ASCII U+0022 (house precedent: the `/strategies` draft banner quotes a name the same way).
- The header `Add Key` button stays enabled: opening the form and filling it in is harmless; only
  submission is blocked. When the attempt ends, the line unmounts and the submit enables.
- **P7, the reverse overlap:** while an add is in flight (`Validating...` on the submit), every
  key's `Resync` / `Use & Sync` is `disabled` in the existing style. **No new copy**: the
  `Validating...` label already says what is happening.
- With no attempt live, the post-add sync RUNS AS the tracked attempt: the S2 panel appears in its
  existing `syncing` → `computing` states and its outcome is judged like any Resync. No new copy.

#### KCS-03 — client-side bounds (S2, new UI state `unconfirmed`)

| ID | Condition | Label (panel status row) | Detail (`<p className="text-xs text-text-secondary mt-1 ml-6">`) |
|----|-----------|--------------------------|------------------------------------------------------|
| `KCS03-LINK` | the link update did not answer within the link bound (15 s) | `Sync not started` | `This sync did not start: linking the key to this strategy did not answer within 15 seconds. Reload this page to check which key is linked before you sync again.` |
| `KCS03-ENQUEUE` | the enqueue did not answer within the enqueue bound (180 s) | `Sync not confirmed` | `We could not confirm this sync started: the request did not answer within 3 minutes, so it may still be running. Reload this page to see the latest status before you sync again.` |

- Panel treatment: `bg-warning-bg`, label + `WarningIcon` in `text-warning`. **No Retry button**
  in either row (KCS-22: a re-POST while a job may be live can insert a second job). The key's
  `Resync` / `Use & Sync` re-enables when the attempt ends, which is the path the detail names.
- ⛔ Neither string contains `failed` or `error`. `Sync not started` is used only for the link
  bound because there, and only there, the card KNOWS no enqueue was sent: after the link bound
  expires the enqueue is never sent, and a late link or enqueue answer writes nothing to the panel
  (`if (attemptRef.current !== attempt) return`, RESEARCH P5).

#### KCS-22 — the poll budget runs out (S2, new UI state `no_result`)

| ID | Condition | Label | Detail (same block as KCS-03: `text-xs text-text-secondary mt-1 ml-6`) |
|----|-----------|-------|--------|
| `KCS22-CAP` | the panel's poll cap (40 polls × 3 s) expires with no accepted terminal | `No result yet` | `This panel stopped checking after 2 minutes. The sync may still be running: reload this page later to see its result.` |
| `KCS22-NOROW` | the missing-row grace (10 polls × 3 s) expires with no analytics row | `No result yet` | `This panel stopped checking after 30 seconds with nothing recorded yet. The sync may still be running: reload this page later to see its result.` |

- Panel treatment: muted, like `idle` (`bg-page`, `IdleIcon`, label `text-text-secondary`). **No
  Retry.** The existing `Analytics computation timed out. Please retry or contact support.` sentence
  is no longer reached from either give-up path.
- If the planner removes the separate missing-row give-up (so a missing row just keeps polling to
  the cap, which KCS-02 permits), `KCS22-NOROW` is deleted and `KCS22-CAP` is the only string.
  Record which.
- **`Sync failed` renders only from evidence:** an accepted `failed` status (KCS-02 evidence gate)
  or a non-2xx / non-enqueued `/api/keys/sync` answer (existing `syncFailureMessage` copy,
  unchanged). A give-up of the panel's own is never a failure.

#### KCS-02 / KCS-18 / KCS-04 — no new copy, render rules only

| Rule | Visible contract |
|------|------------------|
| KCS-02 | A terminal read without this attempt's evidence renders nothing new: the panel stays on `Computing analytics...` (existing label) and keeps polling. |
| KCS-18 | A terminal SUCCESS (`Up to date` / `Synced with warnings`) renders only after one `sync-progress` read shows no factsheet-chain job in flight. Until then the panel stays on `Computing analytics...`. A failed or degraded read keeps it there. |
| KCS-04 | When the terminal success's subject key is untrusted, the success is RETIRED at that moment: the panel returns to `idle` and unmounts. No later re-read (another tab's `Update password` / `Delete`, the load-error Retry) re-shows it. The key's own `AllocatorSyncStatus` pill is the truthful signal and clears on the next read. |

#### KCS-23 — a composite strategy's key card (S3)

On a composite strategy the card renders **no `Resync`, no `Use & Sync`, and no `Add Key`**
control. Every other part of each key's `Card` is unchanged: avatar, label, exchange line, MT5
account line, `Update password`, `Delete`, and the S1b `AllocatorSyncStatus` block.

What replaces them is ONE line directly under the `Exchange API Keys` header, in the same
`space-y-4` stack: `<p className="text-xs text-text-muted">`.

| ID | Condition | Copy |
|----|-----------|------|
| `KCS23-COMPOSITE` | the strategy is a composite | `This composite strategy reads from every key below. Keys are not linked or synced from this card: contact support@quantalyze.com to change which keys it uses or to re-run its computation.` |

- **Why a line and not nothing:** removing the controls without a word leaves an unexplained
  absence (DESIGN.md § Voice: state the limitation). **Why no control:** `handleLinkKey` writes
  `strategies.api_key_id` unconditionally, so `Use & Sync` would silently make a composite a
  single-key strategy (RESEARCH P14).
- ✅ **`Add Key` is included in the removal, per CONTEXT KCS-23's 2026-09-23 clarification.**
  `handleAddKey` performs the same unconditional `strategies.update({ api_key_id })` link, so
