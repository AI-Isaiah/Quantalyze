## Summary

Every question the CONTEXT asked research to settle has an answer from code and migrations. The
important one is KCS-02's fast-fail case. **(a)+(b) DO close it.** `mark_compute_job_failed` always
`PERFORM`s `sync_strategy_analytics_status`, and the bridge's failed branch (b) writes
`computed_at = now()`. So a job that fails before any handler writes `computing` still moves
`computed_at` (evidence b), even though `computing` itself is never observable. **No third
evidence arm is needed for that case.**

The trace also turned up four facts the plans have to absorb, because they change what "correct"
means for KCS-02, KCS-07 and KCS-09:

1. **Warned rows never show `computing` while jobs are running.** The bridge's branch (a) keeps a
   row at `complete_with_warnings` (or with `computation_warned` set) while it bumps `computed_at`.
   So with (a)+(b), a resync of a warned strategy ends at the first job hop and shows "Synced with
   warnings" while the chain is still running. That is better than today, which ends at the first
   poll, but it is still an early terminal. Closing it needs job-state evidence.
2. **KCS-02 turns a stale "Up to date" into a timeout on slow fetches.** The panel's poll budget is
   120 s. The analytics row does not move until the first job hop finishes, and that hop can take
   minutes. So a healthy long crawl now reaches "Analytics computation timed out".
3. **`done_pending_children` is not terminal.** It is a child job waiting on its parents. The SQL
   bridge counts it as non-terminal and the in-flight unique index includes it. KCS-07's
   "finished (`done` / `done_pending_children`)" mapping, and the same claim in
   `src/lib/sync-progress.ts`, disagree with the SQL.
4. **"No job row" does not mean "never started".** Retention crons delete `done` jobs after 30 days
   and `failed_*` jobs after 90 days. On top of that, recurring cron kinds (`reconcile_strategy`,
   `sync_funding`) can be the strategy's latest job, which would hijack the route's
   "latest of any kind" fallback.

**Primary recommendation:** Put the KCS-02 evidence gate in `SyncProgress`, which already filters
statuses before forwarding them, and key it per attempt. Pass `computed_at` as a third `onStatus`
argument from the hook's interval arm only. Lift the sync-progress selection plus a kind
classification into one dependency-free `@/lib` module. That module takes the job rows, reports
whether the read was exhaustive, and maps `done_pending_children` to `queued`.

### Q1 — KCS-02: is the fast-fail case observable? (settled: YES, via evidence (b))

**Trace, single-key resync** (`ApiKeyManager.handleSyncTrades` → `POST /api/keys/sync`):

1. The route's unified arm calls `postProcessKey({ flow_type: "resync" })` (`unifiedKeysSyncHandler`, `src/app/api/keys/sync/route.ts`). The Python side (`analytics-service/routers/process_key.py`, block `# 3) Long-fetch dispatch (BACKBONE-09)`) calls `enqueue_compute_job` with `"p_kind": "process_key_long"` and metadata `{correlation_id, verification_id, flow_type, source}`. It then returns `{"ok": True, "queued": True, "verification_id": …}` [VERIFIED: analytics-service/routers/process_key.py, `_is_long_fetch` dispatch block].
2. **Nothing writes `strategy_analytics` at enqueue or at claim.** In SQL, only `mark_compute_job_done` / `mark_compute_job_failed` `PERFORM sync_strategy_analytics_status` (the baseline dump shows exactly two `PERFORM` sites). In Python, the only extra caller is `services.job_worker.dispatch`, for the `DEFERRED` outcome only. The `COMMENT ON FUNCTION sync_strategy_analytics_status` confirms it: *"Called post-flip by mark_compute_job_done / mark_compute_job_failed (in-RPC PERFORM) and, for the DEFERRED outcome only, by services.job_worker.dispatch."* [VERIFIED: supabase/schema/baseline.sql, `COMMENT ON FUNCTION "public"."sync_strategy_analytics_status"`; analytics-service/services/job_worker.py `dispatch`]. `run_process_key_long_job` (`services/ingestion/long_fetch.py`) does not write `strategy_analytics`. So the **previous run's row is what the poll reads for the entire first hop**. This confirms the ROADMAP's "likely on MOST resyncs".
3. **Fast fail:** the handler returns `FAILED` (or raises, which `dispatch` catches into `FAILED`) → main_worker calls `mark_compute_job_failed` → `PERFORM sync_strategy_analytics_status(v_strategy_id)`. ### Pattern 1: KCS-02 evidence gate lives in `SyncProgress`, keyed per attempt
**What:** `ApiKeyManager` reads the baseline immediately before the enqueue and passes it as a prop, e.g. `evidenceBaseline: { computedAt: string | null } | "unknown"`. `SyncProgress` holds a `sawComputingRef` and forwards a terminal only when `sawComputing || (baseline !== "unknown" && computedAt !== baseline.computedAt)`. Mount it with `key={attemptSeq}` so the ref resets per attempt: the panel stays mounted from `error` into a Retry, so without a key a stale `sawComputing` would carry over.
**Why here and not in `handleSyncStatusChange`:** `ApiKeyManager.test.tsx` mocks `./SyncProgress` and drives `capturedOnStatusChange("complete")` at about 16 sites. With the gate in `SyncProgress`, those tests keep meaning "a status the panel forwarded is this attempt's". The real gate is then exercised in `ApiKeyManager.poll.test.tsx` and `SyncProgress.poll.test.tsx`, which use the real poller. `SyncProgress` already owns the surface filter (`toSyncStatus` idle-drop), and `ApiKeyManager` keeps "only the attempt ends itself".
**Hook change:** in the interval arm only, `onStatusRef.current(data.computation_status, data.computation_error ?? null, data.computed_at ?? null)`. The ladder arm's select (`"computation_status, computation_error"`) and its call are byte-unchanged. No test asserts `onStatus` arity (`grep` for `onStatus).toHaveBeenCalledWith` finds 0).

### Pattern 3: lane-local owner read that cannot crash the page
Call `supabase.rpc("get_user_compute_jobs", { p_strategy_id: id, p_limit: 100 })` inside `try` in the `!payload && lane === "owner"` branch. On `{error}`, or on a throw (the owner-lane test mock has no `rpc`), log with `console.error` + `captureToSentry`, the same shape as the share-state read, and render the neutral "claims no state" sentence. The result goes into a local variable passed only to JSX, never to `fetchAndBuildPayload` or the payload object.

### Pattern 4: retire at the applied re-read (KCS-04)
`loadKeys` resolves `{ ok, subjectStatus }` computed from the rows it actually applied. The terminal arm sets `idle` rather than the success when `isUntrustedKeySyncStatus(subjectStatus)`. Every applied read also calls `retireWithheldSuccess(isUntrustedKeySyncStatus(subjectStatus))`.

### Anti-patterns to avoid
- **Evidence from the client clock** (comparing `Date.now()` with `computed_at`): forbidden by the ROADMAP.
- **Selecting `metadata` whole on the share page**: it carries `source`, `correlation_id`, `verification_id`. Project `metadata->>member_progress_at` only.
- **Changing Lane B's select embed** to add `computation_status`: it breaks the owner-lane test 9 substring pin (P13).
- **A `useEffect` that watches `withholdPanelSuccess`**: the component deliberately runs retirement from event handlers only ("it is not an effect").
- **Reusing `syncStatus: "error"` for the KCS-03 expiry**: `SyncProgress`'s `STATUS_CONFIG.error.label` is `"Sync failed"`, which is exactly the claim KCS-03 forbids (P5).

## Common Pitfalls

### P1: A warned strategy's resync still ends early (KCS-02 residual)
**What goes wrong:** Branch (a) of the bridge keeps a `complete_with_warnings` / `computation_warned` row at `complete_with_warnings` and bumps `computed_at` on every hop, so evidence (b) accepts a mid-chain row as the terminal.
**How to avoid:** Either record it as a named limit, or add the job-state arm for this status only (Open Question 1). Test shape: baseline `complete_with_warnings` T0 → poll `complete_with_warnings` T1 while the chain job is `pending`.

### P2: KCS-02 turns a false "Up to date" into a false "timed out" on long fetches
**What goes wrong:** `POLL_MAX_ATTEMPTS = 40` × 3 s = 120 s. The row does not move until the first hop's mark, and `TIMEOUT_PER_KIND["process_key_long"]` is 30 min ("supports 90-day OKX archive backfill"). A healthy crawl longer than 2 min now reaches `"Analytics computation timed out. Please retry or contact support."`, and Retry then enqueues on top of a live job (the in-flight unique index dedups `pending` / `running`, but not `failed_retry`).
**How to avoid:** The planner should decide the budget-exhaustion copy for the key card, e.g. a non-failure "still running, this panel stopped watching" line, rather than inheriting the timeout sentence. Treat it like KCS-03's expiry: do not claim failure without evidence.

### P3: Baseline race with recurring cron jobs
Take the baseline read **after** the link update and immediately before the enqueue fetch. Document the residual window.

### P4: The baseline read is a new unbounded await, and a pre-enqueue analytics read
Bound it. On error or expiry, use `"unknown"` (evidence (a) only) and log. ⚠️ `ApiKeyManager.poll.test.tsx` pins `expect(readsBeforeEnqueue).toBe(0)`, counting `.single()` analytics reads. Use `.maybeSingle()` for the baseline (absent row ⇒ `null`, a legit value) so the mock can tell it apart from polls, and **move** the pin to "exactly one baseline read, zero polls, before the enqueue". Its reason stays: no *poll* before the enqueue. The mock's `eq()` currently exposes only `single`, so add `maybeSingle`. The CONTROL "a terminal read AFTER the enqueue still ends the attempt" feeds `computed_at: null` with no `computing` poll first, so under KCS-02 it must gain evidence (a `computing` tick or a changed `computed_at`).

### P5: KCS-03 expiry has no truthful panel state today
`STATUS_CONFIG.error` renders "Sync failed" plus Retry. Add a UI-only `SyncStatus` member (e.g. `"unconfirmed"`). `STATUS_CONFIG` is `Record<SyncStatus, …>`, so the compiler forces its entry. `toSyncStatus`'s `assertNever` covers only DB statuses and is unaffected. Also: **after a bound expires, the late 202 must not write the panel.** Today `attempt.enqueued = true; setSyncStatus("computing")` runs with no liveness check, and only the `catch` asks `endAttempt`. Add `if (attemptRef.current !== attempt) return;` before those writes.

### P6: `ApiKeyForm` is shared with the allocator surface
Any new prop must be optional and default to today's behaviour. `AllocatorExchangeManager` must render byte-identically.

### P7: The reverse overlap (Resync clicked during an in-flight add)
Disabling Add Key while an attempt is live does not stop an attempt from *starting* during the add's awaits. Disable Resync / Use & Sync while the add is in flight too, and pin it.

### P8: Recurring cron kinds hijack "latest of any kind"
`reconcile_strategy` (active keys, synced in the last 24 h) and `sync_funding` (active perp keys) are enqueued for ordinary strategies. A `done` reconcile after a `failed_final` chain would read as `finished` ("the last run finished…"), which is false. Filter the non-stitch fallback to chain kinds (Q3).

### P9: `done_pending_children` is waiting, not finished
It is a child whose parents are not all `done`. `mark_compute_job_done` flips it to `pending` when the last parent finishes. The bridge counts it non-terminal, and the in-flight unique index includes it. KCS-07 and `src/lib/sync-progress.ts`'s comment call it terminal-success. Map it to `queued` (Open Question 2). A 2026-05-26 migration comment said no worker passes `parent_job_ids`; that is a dated claim, not re-measured.

### P10: Retention makes "no row" ambiguous
`retention_compute_jobs_done` deletes `done` rows older than 30 days, and `retention_compute_jobs_failed` deletes `failed_final` / `failed_retry` rows older than 90 days (`supabase/migrations/20260515113853_retention_crons_safe.sql`). Author the `never_started` owner copy so it is **true in both cases**, for example "No sync is running and none is on record for this strategy". Also emit `unreadable` rather than `never_started` when the read was not exhaustive.

### P11: `p_limit` window
The route uses `p_limit: 20`. Once the fallback is chain-filtered, 20 rows of daily cron jobs can hide a failed chain. Use a larger limit for the state derivation (the RPC default is 100, the cap 1000), and treat a full window with no chain job as `unreadable`.

### P12: Owner-lane and share tests have strict mocks
The owner-lane request mock has no `rpc`. The share `page.test.tsx` and the cache-isolation `mockAdmin` throw on unexpected tables. The strategies page tests (`page.share-affordance.test.tsx`, `page.wizard-draft-banner.test.tsx`) throw `Unexpected table: …` for anything but `strategies` / `contact_requests`, and have no `rpc`. The owner and share reads must sit only in the `!payload` branch and catch throws (fail closed to the neutral sentence or arm (b)). Extend the two strategies-page test doubles **deliberately**, with the new tables and an `rpc` stub. Do not weaken their throws.

### P13: Owner-lane test 9 pins the Lane B select string by substring
`"strategy_analytics ( computed_at )"` must remain a substring of the Lane B select. Do not widen that embed.

### P14: The Resync advice is wrong for composites and CSV strategies
On `/strategies/[id]/edit`, `ApiKeyManager` receives `currentKeyId={strategy.api_key_id}`. For a composite that is `null`, so no key shows **Resync**. Every key shows **Use & Sync**, which runs `handleLinkKey`, writes `strategies.api_key_id`, and would turn the composite into a single-key strategy. CSV strategies (`source === "csv"`) render `CsvStrategyEditNote` and have no Resync at all. KCS-09's "the `Resync` control on the edit page" advice is therefore true only for single-key API strategies (Open Question 4).

### P15: The public sentence must avoid "failed" and "error"
V2 asserts that the lower-cased public placeholder text contains neither word.
