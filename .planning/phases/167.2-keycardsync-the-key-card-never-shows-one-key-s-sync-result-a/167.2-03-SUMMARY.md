# Phase 167.2 Plan 03: a sync attempt shows a result only when the server proves it is this attempt's Summary

**The key card's sync panel now forwards a terminal status only with evidence that it belongs to the current attempt. The evidence is either a `computing` read seen by this attempt's panel, or a `computed_at` that differs from the value read just before the enqueue. Both are server-written values. A resync can no longer end at its first poll with the previous run's "Up to date" or "Sync failed".**

A clean read returns `{ computedAt }`, and an absent row gives `null`. An error, a throw or an expiry returns `"unknown"` and logs `console.error` with the bound or the strategy. `handleSyncTrades` calls it after `handleLinkKey` and right before the enqueue `fetch` (P3), then checks `if (attemptRef.current !== attempt) return;`. The panel mounts as `<SyncProgress key={attemptSeq} evidenceBaseline={evidenceBaseline} …>`. `endAttempt`, `enqueued`, `settling`, `TERMINAL_REREAD_BOUND_MS` and R1–R5 are unchanged (KCS-05).

## Decisions Made

- The gate sits in `SyncProgress` (RESEARCH Pattern 1), so "only the attempt ends itself" stays in `ApiKeyManager` without change.
- An unknown baseline admits a terminal only after a `computing` read. A moved `computed_at` means nothing without something to compare it with.
- The baseline goes back to `"unknown"` when an attempt registers, before any await. The previous attempt's baseline therefore never reaches the new panel.
- The `ApiKeyManager.test.tsx` mock answers `maybeSingle` only for `strategy_analytics`. It is not a catch-all, so a baseline read aimed at the wrong table would throw, and the new case would fail.
