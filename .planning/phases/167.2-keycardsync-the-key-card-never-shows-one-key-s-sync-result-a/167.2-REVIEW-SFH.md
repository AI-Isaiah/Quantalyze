# 167.2 KEYCARDSYNC — silent-failure hunt

**Scope:** `git diff $(git merge-base HEAD origin/main)..HEAD -- . ':!.planning'` on `feat/167.2-keycardsync` (33 files, production code read in full for every changed symbol below).
**Method:** static read. No DB command, no server started. Every finding is cited by file + symbol.
**Totals:** 0 Critical · 3 High · 7 Medium · 4 Low.

What is done well, and stays that way: `deriveComputeState` fails closed on `readError`, on an out-of-domain status and on a full window. `readShareComputeState` and `readOwnerPendingStatus` both fold a PostgREST error, a non-array answer and a throw into `unreadable`, and never into an in-progress claim. `countCompositeMembers` never throws and treats a null count as `ok: false`. The poller's KCS-22 rule (`sawRow` plus `cleanRead`) correctly refuses to say "nothing recorded" when the read failed. The KCS-18 job-state read (`jobQueueSaysChainSettled`) fails closed on 429, 5xx, a bad body and `degraded`.

---

## HIGH

### H-1 — `/strategies` list: the query this phase widened discards its error, so any embed failure renders "No strategies yet"
- **Where:** `src/app/(dashboard)/strategies/page.tsx`, `StrategiesPage`, the `strategies` select (`const { data: strategies } = await supabase.from("strategies").select("…, strategy_analytics ( computation_status )")`).
- **Failure scenario:** KCS-12 added a `strategy_analytics ( computation_status )` embed to the list query, but `error` is still not destructured. The embed adds new ways to fail: a column grant revoked on `computation_status` (42501), or a second FK between the tables that makes the embed ambiguous (PGRST201). Either one fails the WHOLE query. `data` is null and the page takes the `(!strategies || strategies.length === 0)` branch: **"No strategies yet. Create your first strategy."** An owner with live strategies is told they have none. That is the H-0395 class the key card already fixed for itself. Nothing is logged and nothing reaches Sentry. The discard itself predates this phase, but the phase widened what it hides.
- **Fix:** destructure `error`. On error, `console.error` it plus `captureToSentry(error, { tags: { route: "strategies/page", stage: "list" } })`, then render a distinct load-failure card, never the empty state. Keep the embed only if its failure is survivable. An alternative is to read `computation_status` in a separate `strategy_analytics` query whose failure only drops the share notes, in the fail-closed direction (note shown).

### H-2 — Key card: an unreadable member count silently removes every sync control, with no copy and no Sentry
- **Where:** `src/app/(dashboard)/strategies/[id]/edit/page.tsx`, `EditStrategyPage` (the `memberCount.ok === false` arm → `keyShape = "unknown"`); `src/components/strategy/ApiKeyManager.tsx`, `linkControlsAllowed`, the header's `keyShape === "composite"` note, and the `keys.length === 0` empty state.
- **Failure scenario:** a transient `strategy_keys` error makes the shape `"unknown"`. The card then renders no Add Key, no Resync and no Use & Sync, and says nothing about why. The explanation line renders for `"composite"` only, and the comment says "an 'unknown' shape gets no copy". With zero keys, the empty state still says *"Add a read-only exchange key to import your trading data"* above a card that has no Add Key button. The owner hits a dead end. The only trace is a server `console.error`: no `captureToSentry`, unlike the owner factsheet page's identical read (`readOwnerPendingStatus` captures `stage: "strategy-shape"`). Failing closed on the destructive write is right. Failing closed *silently* is the defect.
- **Fix:** (1) in `EditStrategyPage`, add `captureToSentry(new Error(memberCount.message), { tags: { route: "strategies/edit/page", stage: "strategy-shape" } })` beside the log. (2) In `ApiKeyManager`, render one line for `keyShape === "unknown"`, e.g. "We couldn't confirm how this strategy's keys are set up, so syncing is paused on this page. Reload to try again." This is new copy, so it needs a UI-SPEC row (house rule D-11). (3) Suppress or reword the empty-state sentence when `!linkControlsAllowed`.

### H-3 — `/strategies` list: a failed key-status or member read renders every row as healthy
- **Where:** `src/app/(dashboard)/strategies/page.tsx`, `StrategiesPage`, the `api_keys` read (`if (keysError) console.error(...)`) and the `strategy_keys` read (`if (membersError) console.error(...)`); `untrustedKeyLines`.
- **Failure scenario:** on this page, the healthy state is the *absence* of a pill. When the `api_keys` read errors, `keysById` stays empty, `untrustedKeyLines` returns `[]` for every row, and every strategy looks trusted, including one whose key's sign-in failed. That is the exact state KCS-06 exists to surface. When the `strategy_keys` read errors, a composite is judged on `api_key_id` alone, which is usually null for a composite, so a composite with an untrusted member also shows no mark. The code comment calls this "truthful, partial". To the owner it reads as "all keys fine", and both paths are console-only.
- **Fix:** on either error, (a) `captureToSentry` with `stage: "key-status"` / `stage: "strategy-keys"`; (b) render one page-level muted line such as "Key status could not be checked right now; open a strategy to see its keys." (new UI-SPEC row), so that an absent pill stops meaning "healthy" during an outage.

## MEDIUM

### M-1 — A late enqueue or link answer is dropped to `console.warn`; a definitive failure never reaches the panel
- **Where:** `ApiKeyManager.tsx`, `handleSyncTrades`: the `enqueueOutcome === "timed_out"` arm (`await enqueued` then `console.warn`), the `linkOutcome === "timed_out"` arm, and the outer `catch` (`if (!endAttempt(attempt)) { console.warn("…sync failed after its attempt ended:", err); return; }`).
- **Failure scenario:** the enqueue exceeds `ENQUEUE_BOUND_MS` (180 s), and the panel says *"Sync not confirmed … it may still be running."* At 200 s the route answers 503 (breaker) or 401. The rejection reaches the catch, `endAttempt` returns false, and the only output is a `console.warn`. The panel keeps promising "may still be running" about a sync the server has since refused. The reverse case also happens: a late 202 means a job IS running, but no poll starts and the user is invited to "Reload … before you sync again". A late answer is the one piece of evidence the `unconfirmed` state was waiting for, and it is discarded.
- **Fix:** in the late-answer path, when no newer attempt exists (`attemptRef.current === null`, `lastAttemptedKeyIdRef.current === keyId`) and the panel is still `unconfirmed`, apply the answer. On rejection, `setSyncStatus("error")` with the route's own message (`syncFailureMessage`). On a stamped 2xx, show a "sync started" line, or re-register as the tracked attempt. Add `captureToSentry` at `level: "warning"` for any late answer, because a 180 s enqueue is a wedged route.

### M-2 — Overlapping interval reads plus the sticky evidence (a) can admit an out-of-order STALE terminal
- **Where:** `src/hooks/useStrategySyncPoller.ts`, interval arm (`setInterval(async () => { … await supabase…single(); if (cancelled) return; … })`: no in-flight guard, no sequence number); `src/components/strategy/SyncProgress.tsx`, `onStatus` (`sawComputingRef.current = true` … `if (!sawComputingRef.current && !changed) return;`).
- **Failure scenario:** reads are issued every 3 s whether or not the previous one has returned. Read R1 is issued before the worker writes `computing`, and it is slow. R2 is issued after, returns first with `computing`, and sets `sawComputingRef`. Then R1 lands carrying the PREVIOUS run's terminal row, and evidence (a) admits it. A previous `failed` is forwarded as this attempt's *"Sync failed"* with the old run's `computation_error`. The error arm skips the KCS-18 job-state check. A previous `complete` is only saved by KCS-18. This is exactly the wrong-run attribution KCS-02 exists to prevent, and it re-enters through response ordering.
- **Fix:** give each tick a monotonically increasing sequence number and drop any response older than the newest one applied (the `keysReadSeqRef` pattern `loadKeys` already uses), or skip a tick while a read is in flight. Do it in the interval arm only, so the ladder arm stays byte-unchanged as KCS-02 requires.

### M-3 — Give-up copy says "may still be running" without consulting the job queue, even when the baseline read failed or every read errored
- **Where:** `ApiKeyManager.tsx`, `readEvidenceBaseline` (returns `"unknown"` on error, throw or bound); `SyncProgress.tsx`, `onStatus` (`changed` is false whenever the baseline is `"unknown"`) and `onError` → `no_result`; `key-card-copy.ts`, `PANEL_STOP_COPY.poll_cap` / `missing_row`.
- **Failure scenario A:** the baseline read errors, so the baseline is `"unknown"` and only evidence (a) remains. The job then fails fast before any handler writes `computing` (the case CONTEXT KCS-02 asked to be measured). Nothing is ever admitted, the cap fires, and the panel says *"No result yet … The sync may still be running."* The job is `failed_final`.
- **Failure scenario B:** the session expires mid-poll. Every read errors (logged 40 times to the console), the cap fires, and the owner sees the same "may still be running" text. The panel did not stop because the sync was slow. It stopped because it could not read anything.
- **Fix:** before choosing give-up copy, make one `jobQueueSaysChainSettled`-style read of `/api/strategies/[id]/sync-progress`. `failed_final` → forward `error`. In flight → keep `poll_cap`. Unreadable → keep `poll_cap`. Track "every read in this activation errored" in the hook and pass a distinct reason, e.g. `"unreadable"` (needs copy along the lines of "This panel could not check the sync's status"). Also send `captureToSentry` at level warning when the baseline read fails, because that silently disables evidence (b).

### M-4 — `/api/strategies/[id]/sync-progress` answers IDLE for three "could not tell" cases, and the key card reads IDLE as settled
- **Where:** `src/app/api/strategies/[id]/sync-progress/route.ts`, `GET`: `const jobRows = Array.isArray(rows) ? rows : []` → `IDLE`; no `rows.length >= COMPUTE_STATE_READ_LIMIT` check; `jobStatus = (latest.status ?? null) as StitchJobStatus | null` (unvalidated). Consumer: `SyncProgress.tsx` `jobQueueSaysChainSettled` → `!isFactsheetJobInFlight(read.jobStatus)`.
- **Failure scenario:** (1) the RPC answers neither rows nor an error. The route returns `IDLE`, not `DEGRADED`, and the key card's KCS-18 gate reads `jobStatus: null` as "no chain job in flight", so a mid-chain `complete_with_warnings` row is admitted as "Synced with warnings". (2) A full 100-row window with no chain row is `IDLE` here, but `deriveComputeState`, which lives in the module this route now imports, calls the same input `unreadable`. The route breaks its own module's rule. (3) A status outside the six-value domain passes through, and `isFactsheetJobInFlight(unknown)` is false, so it also reads as settled. `deriveComputeState` calls that `unreadable` too.
- **Fix:** return `DEGRADED` (plus `console.error` / `captureToSentry`) when `rows` is not an array. Return `DEGRADED` when the window is full and `selectFactsheetJob` found nothing. Return `DEGRADED` when `latest.status` is outside the domain (export the status predicate from `compute-state.ts`). The wizard already handles `degraded`.

### M-5 — A full-window `unreadable` is derived silently on every surface, and its remedy cannot fix it
- **Where:** `src/lib/compute-state.ts`, `deriveComputeState` (`row === null && !readExhaustive` → `unreadable`, which cannot be told apart from `readError`); callers `readOwnerPendingStatus` (`factsheet/[id]/v2/page.tsx`), `readRecipientArm` (`strategies/page.tsx`), `readShareComputeState` (`factsheet-share/[token]/page.tsx`).
- **Failure scenario:** a strategy whose newest 100 `compute_jobs` rows are recurring kinds (`reconcile_strategy`, `sync_funding`, RESEARCH P8) derives `unreadable` on every render, deterministically. The owner reads *"The computation status for this strategy could not be read. Reload this page to try again."* Reloading can never help. None of the three callers logs this case, because they log only `error` / non-array / throw, so the condition is invisible in Sentry and in logs. Retention (P10) makes it less likely, but nothing measures whether it happens.
- **Fix:** have `deriveComputeState` expose why (e.g. `{ state: "unreadable", reason: "read_error" | "window_full" | "bad_status" }`) and have every caller log plus capture `window_full`. On the share page the admin read can drop the window problem completely: add `.in("kind", [...FACTSHEET_CHAIN_KINDS, "stitch_composite"])` to the `compute_jobs` query. That keeps the security bound (the strategy id) and adds no column. On the RPC callers, re-ask with `p_limit: 1000` (the RPC's cap) once when the first window is full.

### M-6 — The client bound expiries and the server compute-state failures reach the console only
- **Where:** `ApiKeyManager.tsx`: `handleSyncStatusChange` (terminal re-read timed out / threw), `readEvidenceBaseline` (three arms), `handleSyncTrades` (link bound, enqueue bound, late answers); `SyncProgress.tsx`: `jobQueueSaysChainSettled`'s `onUnreadable` (`console.warn`, once per attempt); `strategies/page.tsx`: `readRecipientArm`; `factsheet-share/[token]/page.tsx`: `readShareComputeState`; `strategies/[id]/edit/page.tsx` (see H-2).
- **Failure scenario:** each of these is an operational signal: a wedged `/api/keys/sync`, a PostgREST read hanging for 15 s, a sync-progress route answering 429/5xx for a whole attempt (which turns a verified success into a `no_result`), or a compute-state read failing on the public share page. None of them reaches Sentry, so production sees none of them. `readOwnerPendingStatus` does call `captureToSentry` for the same read that `readRecipientArm` and `readShareComputeState` only log, so the three surfaces the phase built to agree do not agree on observability. `captureToSentry` is client-safe (`src/lib/sentry-capture.ts` is imported by client components). The `readShareComputeState` log also carries only `message`, while the neighbouring pending-page `console.warn` logs `strategyId`, so a share-page failure cannot be tied to a strategy.
- **Fix:** add `captureToSentry` with a `stage` tag at each site (level `warning` for the bounds, `error` for the read failures), and add `strategyId` to the `readShareComputeState` log context.

### M-7 — `countCompositeMembers` reads an RLS-filtered zero as "not a composite", which enables the destructive link write
- **Where:** `src/lib/strategy-shape.ts`, `countCompositeMembers` (`count: "exact", head: true` on the request client); consumers `EditStrategyPage` (`memberCount.count > 0 ? "composite" : "single"`) and `resolveStrategyShape`.
- **Failure scenario:** RLS denial on SELECT does not produce an error. It produces zero rows. If `strategy_keys_owner` ever regresses, or the session's `auth.uid()` does not resolve, a composite counts `0` with `ok: true`, the card gets `"single"`, and `Use & Sync` / `Resync` write `strategies.api_key_id` on a composite. That silently turns it into a single-key strategy, which is the outcome KCS-23 exists to prevent. The module header promises "fail closed on an unknowable count", but a filtered count is unknowable and still reads as `ok`.
- **Fix:** cross-check with a signal RLS cannot hide from the owner. For example, when `count === 0` and `strategies.api_key_id` is null for a non-CSV strategy, treat the shape as `"unknown"` rather than `"single"`, because a genuinely unlinked single-key strategy has no current key to Resync anyway. Or move the composite guard server-side into the link write.

## LOW

### L-1 — A terminal re-read that times out erases a completed sync with no lasting trace
- **Where:** `ApiKeyManager.tsx`, `handleSyncStatusChange` (`outcome === "timed_out"` → `setLoadError(...)`, then `setSyncStatus("idle")` in `finally`); `loadKeys` (`setLoadError(null)` on the late clean read).
- **Scenario:** the sync finished. The re-read takes more than 15 s, the panel lands on idle ("Ready to sync") and the load-error banner shows. When the stalled read finally resolves, `loadKeys` clears the banner. What is left is an idle panel and nothing saying a sync just completed or that its result was withheld.
- **Fix:** when a success is withheld for an unverified list (not for an untrusted subject), keep a small note on the panel ("This sync finished; reload to confirm the key's status") that the late read does not clear.

### L-2 — A subject missing from the re-read, or `data: null` with no error, counts as "trusted"
- **Where:** `ApiKeyManager.tsx`, `loadKeys` (`data?.find(...)?.sync_status ?? null`; `appliedKeysReadRef.current = { seq, ok: true, subjectStatus }` even when `data` is null), and the terminal arm (`subjectTrusted = reread !== null && !isUntrustedKeySyncStatus(reread.subjectStatus)`).
- **Scenario:** the subject key was deleted in another tab, or the read returned neither rows nor error. `subjectStatus` is null, `isUntrustedKeySyncStatus(null)` is false, and the panel shows "Up to date" for a key the list no longer holds. `data: null, error: null` is also recorded as `ok: true`.
- **Fix:** treat `data == null` as `ok: false`. Treat a subject absent from the applied rows as not-trusted for the purpose of *showing* a success (land on idle).

### L-3 — `get_user_compute_jobs` answers `[]` with no error when `auth.uid()` is null, and the derivation reads that as `never_started`
- **Where:** RPC body (`IF v_auth_uid IS NULL THEN RETURN; END IF;`, latest definition `20260826140000_compute_jobs_error_kind_orphaned.sql`); callers `readOwnerPendingStatus`, `readRecipientArm`.
- **Scenario:** today both callers run only after `getUser()` returned a user, so the path is guarded upstream. But the RPC's empty answer for "no session" and for "no jobs" are the same bytes. A future caller without that guard, or a JWT that `getUser` accepted but PostgREST did not, would render *"No computation is running for this strategy, and none is on record"* with a Resync remedy. The callers' own comment ("error-absent ≠ legit-absent") does not cover this case.
- **Fix:** document the precondition at each call site, and ideally treat an empty answer for a strategy that has analytics or a linked key as suspect. No migration is needed for the note (KCS-15).

### L-4 — A throw from the post-enqueue `loadKeys` reports "Sync failed" for a sync that WAS enqueued
- **Where:** `ApiKeyManager.tsx`, `handleSyncTrades`: after `attempt.enqueued = true; setSyncStatus("computing")`, `await loadKeys({ lastSyncedKeyId: keyId })` is inside the same `try`, and the outer `catch` sets `error` with the thrown message.
- **Scenario:** `loadKeys` itself rarely throws (supabase-js returns errors), but `createClient()` or a network-layer throw would end a live, enqueued attempt as *"Sync failed"* and stop its poll. The path predates this phase, but it now also covers the post-add sync (KCS-01).
- **Fix:** move the post-enqueue list refresh out of the enqueue `try`, or wrap it in its own `try` that logs and keeps the attempt in `computing`.
