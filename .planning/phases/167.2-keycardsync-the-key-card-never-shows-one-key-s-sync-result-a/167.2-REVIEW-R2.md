**Measured, not assumed.** The 48 test files for the key card, the poller, compute-state,
strategy-shape, the edit page and the sync-progress route pass locally: 849 tests, 0 failed. The
`node_modules` symlink was removed afterwards. CR-01 below was reproduced with a throwaway `tsx`
script that called the real `readOwnerComputeJobs` → `compositeHistoryOf` → `resolveStrategyShape`
with a fake 100-row RPC answer. It printed
`{"ok":true,"exhaustive":false,"hist":"unreadable","shape":"unknown"}`. The script was deleted, and
no source file was modified.

The panel's use of the same read is also sound:

- The M-3 give-up: `giveUpStartedRef` stops a second read. A late forward is dropped by the

Other fixes check out:

The tests for the gate and the read-back are real. `CR01-OTHER-KEY-REFUSED`,
`WR06-RESYNC-REFUSED`, `GATE-UNREADABLE` and `WR04-LINK-*` each assert that no link and no enqueue

## Critical Issues

### CR-01: M-7 turns every unlinked strategy with 100+ job rows into `unknown`, which removes Add Key: "delete the failed key, add a new one" dead-ends

**File:** `src/lib/strategy-shape.ts` — `compositeHistoryOf` (`return read.readExhaustive ? "none" : "unreadable"`); `src/lib/compute-jobs-read.ts` — `readOwnerComputeJobs` (re-asks at `COMPUTE_STATE_READ_LIMIT_MAX` only when `isWindowFullWithoutFactsheetJob`); `src/app/(dashboard)/strategies/[id]/edit/page.tsx` — the M-7 block (`if (members.keyIds.length === 0 && !strategy.api_key_id)`); also `src/app/factsheet/[id]/v2/page.tsx` — `readOwnerPendingStatus` (`compositeHistory: compositeHistoryOf(jobsRead)`)

**Issue:** `readOwnerComputeJobs` widens to 1000 rows only when the first 100 rows contain NO
factsheet-chain row. If the newest 100 rows include one, it does not re-ask. It returns the 100 rows
with `readExhaustive: false`. `compositeHistoryOf` finds no stitch among them and answers
`"unreadable"`, so `resolveStrategyShape` returns `"unknown"`. That is deterministic: a reload gives
the same answer. Reproduced with the real functions (see Summary).

Scenario:
1. A mature single-key strategy has been syncing for weeks and has 100+ `compute_jobs` rows,
   including recurring `sync_trades` / `compute_analytics` chain rows.
2. Its key shows "Sign-in failed". The card's documented remedy is `Delete` / `Add Key` for a
   re-add (see the comment block above `AllocatorSyncStatus` in `ApiKeyManager`).
3. The owner deletes the key. `strategies_api_key_id_fkey ... ON DELETE SET NULL` clears
   `strategies.api_key_id`, and `handleDeleteKey` calls `router.refresh()`.
4. The edit page re-renders. There are zero members and no linked key, so M-7 runs, and the shape
   comes back `unknown`.
5. `linkControlsAllowed` is false. Add Key, Resync and Use & Sync are gone. The card shows
   `KCS-SHAPE-UNKNOWN` ("… Reload this page to try again"), and a reload cannot help.

The strategy can no longer be re-keyed from the product. It is a user-facing dead end, and it was
introduced by this fix round: before M-7, this strategy resolved to `unlinked`, i.e. `single`. The
owner factsheet takes the same helper, so its remedy also resolves against `unknown`.

No test can catch it. The M-7 edit-page tests (`M7-STITCH-HISTORY`, `M7-HISTORY-UNREADABLE`,
`M7-NO-HISTORY`, `M7-LINKED-NO-READ`) all use a one-row RPC answer, and `strategy-shape.test.ts`
has no `compositeHistoryOf` case at all.

**Fix:** The history question is "is any `stitch_composite` row on record?". It needs its own
widening rule, not the chain-selection one. Either always ask the RPC cap for the history read, or
re-ask whenever the first window is not exhaustive. Then call it `unreadable` only when the 1000-row
window is itself full with no stitch:
```ts
// edit page (and readOwnerPendingStatus), M-7 arm only
let jobs = await readOwnerComputeJobs(client, strategy.id);
if (jobs.ok && !jobs.readExhaustive && !jobs.rows.some((r) => r?.kind === "stitch_composite")) {
  jobs = await readOwnerComputeJobsAtCap(client, strategy.id); // p_limit: COMPUTE_STATE_READ_LIMIT_MAX
}
compositeHistory = compositeHistoryOf(jobs);
```
Add a test that fails today: 100 rows, a chain row among them, no stitch, zero members, no linked
key. Expect `"single"`, plus a second RPC call at `p_limit: 1000`. Also add a direct
`compositeHistoryOf` unit case for each of its three answers.

## Warnings

### WR-01: A deterministic `unknown` shape tells the owner "Reload this page to try again"

**File:** `src/components/strategy/key-card-copy.ts` — `SHAPE_UNKNOWN_CARD_NOTE`; `src/lib/strategy-shape.ts` — `resolveStrategyShape` (the `compositeHistory !== "none"` arm)

**Issue:** `KCS-SHAPE-UNKNOWN` was authored for H-2's transient case, a member-count read that
failed. M-7 added two DETERMINISTIC ways to reach the same shape, and on both of them the copy is
false:
- `"seen"`. A strategy converted from a composite to a single key before KCS-23 keeps its stitch
  rows for their 30/90-day retention, which IN-03 itself documents. Once its key is deleted
  (`api_key_id` → null), it is `unknown` on every render until retention expires.
- The non-exhaustive arm of CR-01.

The owner is told to reload, reloads, and gets the same dead end. There is no support pointer, and
the card offers no action. That is the "false remedy" class this phase removes on other surfaces.

**Fix:** Pass the reason through, so the card can tell them apart. For example, `keyShape: "unknown"`
plus `unknownReason: "read_failed" | "history"`. Keep the "Reload" copy for `read_failed` only.
Author a new UI-SPEC row for `history`, e.g. "We could not confirm whether this strategy is a
composite, so keys are not linked from this card. Contact support@quantalyze.com to link a key."
Pin it in `key-card-copy.test.ts`.

### WR-02: The WR-05 Delete refusal has no owner-side exit: an archived composite's member key can never be deleted, and a draft's refusal names only support

**File:** `src/components/strategy/ApiKeyManager.tsx` — `handleDeleteKey` (`if (memberships.length > 0) { … setError(DELETE_COMPOSITE_MEMBER_COPY); return; }`); `src/components/strategy/key-card-copy.ts` — `DELETE_COMPOSITE_MEMBER_COPY`; the card-level `{error && …}` line (`text-negative`)

**Issue:** The refusal is unconditional. It covers a membership in ANY composite, whatever its
status (`draft`, `pending_review`, `published`, `archived`, `private`). Consequences:
1. **Permanent trap.** A key whose only membership is an `archived` composite keeps its
   `strategy_keys` row, because the strategy is not deleted. The owner can never delete their own
   exchange credential, not even after revoking it at the exchange. The only path is support.
   Before this round, only the PUBLISHED case was refused (by the DB guard).
2. **False remedy for drafts.** For a draft composite, membership is owner-editable through
   `/api/strategies/composite/set-members`, but the copy says "Contact support@quantalyze.com".
3. **Discovered after the fact.** The owner clicks Delete, reads "This will permanently remove this
   API key", confirms, and only then is refused. Nothing on the card said the key was locked. On a
   single-key card, the copy does not say which strategy holds the key.
4. **Tone.** The refusal renders in the card-level `text-negative` line. DESIGN.md §Color reserves
   red for "permanent / negative only (a realized loss, a hard error …)". A policy refusal is not an
   error. When the Add Key form is open, the line is hidden and the refusal appears inside
   `ApiKeyForm`'s `error` slot instead, as if it were a form-validation failure.
5. **Unbounded read.** The membership read is not raced against a bound, unlike every other read
   on this card. A hang leaves the confirm modal open with Delete clickable.

**Fix:**
- Read memberships for the listed keys with `loadKeys` (one `strategy_keys … .in("api_key_id", ids)`
  read on the RLS client), so the lock is known before the click.
- On a member key, render Delete disabled with a muted line naming the reason.
- Scope the lock to statuses where a silent shrink is the harm (`draft`, `pending_review`,
  `private`; `published` is already refused by the DB).
- Let an `archived` composite's member be deleted, behind a composite-specific confirm.
- For drafts, point at the composite's own editor rather than support.
- Bound the read like `readLinkedKeyId`.

This changes the KCS-23 amendment, which is already in the founder UAT queue, so it needs a dated
UI-SPEC row either way. A test must show a key in an archived composite is deletable, or explicitly
pin the trap as a founder decision.

### WR-03: The 15 s bound, the gate's only "cannot hang" guarantee, is unpinned

**File:** `src/components/strategy/chain-job-state.ts` — `CHAIN_JOB_READ_BOUND_MS`, `readChainJobState`'s `Promise.race`; tests `ApiKeyManager.test.tsx` (mocks the module wholesale), `ApiKeyManager.poll.test.tsx`, `SyncProgress.poll.test.tsx`

**Issue:** The bound is the whole reason the gate cannot freeze the card. The attempt is registered
(`syncingKeyId` set, every Resync / Use & Sync / Connect Key disabled, spinner shown) before
`await readChainJobState`. A sync-progress request that never settles would hold all of that until
a reload. `grep -rn CHAIN_JOB_READ_BOUND_MS src` finds only the module itself. No test stubs a
never-settling `/sync-progress` fetch. The two never-resolving stubs in `ApiKeyManager.poll.test.tsx`
are the baseline read and the link. So deleting the `Promise.race` leaves every test green: a guard
that cannot fail its test, on a user-facing lock. The same goes for the panel's KCS-18 / WR-03 /
M-3 reads. Before this round they were unbounded, and `jobCheckInFlightRef` would stay held.

**Fix:** In `ApiKeyManager.poll.test.tsx` (real module, fake timers), answer
`/api/strategies/*/sync-progress` with `new Promise(() => {})`, click Resync, and advance
`CHAIN_JOB_READ_BOUND_MS`. Then expect `data-stop-reason="chain_unreadable"`, no link update, no
enqueue, and Resync enabled. Check that the test goes RED with the race removed, then restore it.

## Info

### IN-01: "No key id and no strategy id in any capture" holds for the payload, not the Sentry event

**File:** every `captureToSentry` site added in `538668fb8` (`ApiKeyManager`, `SyncProgress`, `strategies/page.tsx`, the edit page, the route)
**Issue:** The message and tags are id-free, and the tests assert that. But the same client event
also carries Sentry's console breadcrumbs, and the neighbouring `console.error` / `console.warn`
lines embed `[strategy_id=…]` and `[key_id=…]`. It also carries the fetch breadcrumb for
`/api/strategies/<id>/sync-progress` and the page URL `/strategies/<id>/edit`. The route's server
capture carries the request URL. `scrubSentryEvent` in `src/instrumentation.ts` scrubs share-token
shapes, not UUIDs. These ids are owner-internal and not secret, so this is not a leak. But the
REVIEW-FIX claim ("tags only: no key id and no strategy id in any capture") is broader than what
the code guarantees.
**Fix:** Narrow the claim to "no id in the capture's message or tags". If ids must be kept out of
Sentry, add a UUID scrub to the breadcrumb pass of `scrubSentryEvent`.

### IN-02: `KCS-GATE-INFLIGHT` says "a sync for this strategy is still running" for states that are not a running sync

**File:** `src/components/strategy/key-card-copy.ts` — `PANEL_STOP_COPY.chain_in_flight`
**Issue:** The gate refuses on any in-flight chain job: `pending` (queued, not running), a
`failed_retry` backoff (a failed run waiting to retry), or a recurring `compute_analytics` /
`derive_broker_dailies` row that the owner never started. "A sync … is still running" is therefore
inexact for most of those states.
**Fix:** Reword to something true in every in-flight state, e.g. "This sync did not start: this
strategy still has a sync or computation in progress. Try again once it has finished." Re-pin the
string.

### IN-03: `/strategies` still renders "No strategies yet" for `data: null` with no error

**File:** `src/app/(dashboard)/strategies/page.tsx` — the `strategiesError ? … : (!strategies || strategies.length === 0)` branch
**Issue:** H-1 routes a destructured `error` to `KCS-LIST-UNREADABLE`. But `data: null, error: null`
still takes the empty-state branch. That is the same class L-2 fixed in `loadKeys`, where "null
data is not a clean read".
**Fix:** Treat `strategies === null` as unreadable: `strategiesError || !Array.isArray(strategies)`.

### IN-04: A deterministic DEGRADED route answer refuses every attempt with "Try again in a moment"

**File:** `src/app/api/strategies/[id]/sync-progress/route.ts` — the `read.windowFull` → `degrade("compute-jobs-window-full", …)` arm; `key-card-copy.ts` — `PANEL_STOP_COPY.chain_unreadable`
**Issue:** Since M-4, a 1000-row window with no chain row is DEGRADED on every call, and the gate
reads DEGRADED as `unreadable`. That strategy's Resync / Use & Sync is refused on every click, with
copy promising that a moment will help. It is rare, because it needs 1000+ non-chain rows inside
retention, and it is captured (`compute-jobs-window-full`). But it has no owner-side exit.
**Fix:** Have the projection carry a reason (`degradedReason: "window_full"`), map it to its own
`PanelStopReason` whose copy names support, or record it as an accepted residual in the UI-SPEC row.

### IN-05: IN-03's `preferStitch` rides on an RLS-scoped count, so the M-7 class reaches the route too

**File:** `src/app/api/strategies/[id]/sync-progress/route.ts` — `preferStitch: !(memberCount.ok && memberCount.count === 0)`; the same on `factsheet/[id]/v2/page.tsx`
**Issue:** A regressed `strategy_keys_owner` policy counts a real composite as `0` with `ok: true`.
Stitch preference is then dropped, and a member chain row newer than the stitch answers for the
composite: no member progress, and the KCS-18 gate reads that chain row instead of the stitch. This
is the exact failure mode M-7 guards against on the edit page, but here it is left unguarded. It
needs a policy regression, so it is Info.
**Fix:** Reuse the M-7 cross-check once CR-01 is fixed: a zero count with a stitch on record keeps
`preferStitch` true. Only a proven zero with no stitch history drops it.
