<domain>
## Phase Boundary

Three surfaces, one family: **a status the owner reads must be about the thing it names, and must
not promise an outcome that is not coming.**

1. **The key card (`ApiKeyManager` on `/strategies/[id]/edit`).** A sync result is only ever shown
   about the key it came from, and a success withheld beside a "Sign-in failed" pill cannot
   reappear through a re-read. This closes the four residuals Phase 167 routed here
   (`167-CONTEXT.md` D-18, "Two residuals, named and NOT fixed" and "Two limits of the attempt
   scoping"): (1) the post-add sync outside the tracked slot, (2) another tab's change re-showing a
   withheld success, (3) a stale terminal read after the enqueue, (4) an enqueue that never returns.
2. **The `/strategies` list (167 D-19).** Each strategy row whose feeding key is untrusted
   (`isUntrustedKeySyncStatus`) carries the same key-level pill. No causal claim.
3. **The "still computing" surfaces (2026-09-23 widenings).** The OWNER lane of the pending
   factsheet states the strategy's real compute state; the share page and the owner's share
   affordance tell a running compute apart from one that failed, stalled or never started, and
   never promise "a few minutes" for a terminal failure.

**Out of scope:** new job states (ROADMAP fence); any change to what the worker writes, to
`compute_jobs`, to `strategy_analytics`, or to any SQL function (KCS-15: no migration); the
Deribit `assignment` classification itself (Phase 168); the allocator KPI strip (Phase 167.1);
`HoldingsTabPanel`'s `keyStatusById` (named out of scope by 167 D-18); email/push notification
(167 D-14).

## Implementation Decisions

### A. The key card — residuals routed from Phase 167

- **KCS-01: While a tracked sync attempt is live, the card does not start a second sync. `Add Key`'s
  submit is disabled for that window, key-scoped copy says why, and with no attempt live the
  post-add sync RUNS AS the tracked attempt** (it takes the marker, it is polled, its subject is the
  new key, and its failure reaches the panel). This closes residual (1) in both halves: (a) a
  post-add failure reaching only the console, and (b) the post-add outcome never being polled.
  **Evidence for the shape:** 167 D-18 R4 and R5 already close the same kind of overlap by
  disabling a control while an attempt is live (`Update password` and `Delete`, key-scoped on
  `syncingKeyId`), and R4's lineage records the lesson that the window exists only if two
  operations overlap, so preventing the overlap is cheaper and more robust than recording which
  attempt owns which result. A queued second attempt was rejected: it needs a queue the card does
  not have, and a queued sync that starts after the user has left the page is invisible.
  ⚠️ This changes the add flow the `SEAMUX-05` describe block in
  `src/components/strategy/ApiKeyManager.test.tsx` pins. Those pins MOVE deliberately in the same
  change (the ROADMAP names this cost); they are not deleted, and each moved pin keeps its reason.
  — **Reversibility:** reversible — client-only, one component.

- **KCS-02: An attempt accepts a terminal status only with evidence that the status belongs to
  THIS attempt (residual 3).** Evidence is either (a) this attempt has itself observed `computing`,
  or (b) the row's `computed_at` differs from the value read BEFORE the enqueue. Both are
  server-written values compared with each other; ⛔ no client clock is compared with a server
  clock (ROADMAP). A terminal read with neither piece of evidence is not shown as the attempt's
  result; the attempt keeps polling.
  ⚠️ **The researcher MUST measure one case before the planner commits to (a)+(b) alone:** a job
  that fails fast, before any handler writes `computing` to `strategy_analytics`, on a strategy
  whose previous run also failed. If neither `computing` nor a new `computed_at` is observable
  there, (a)+(b) cannot end that attempt and it runs out its budget into the timeout copy. If so,
  the planner adds a third evidence arm from data the owner can already read — the latest
  `compute_jobs` row through `get_user_compute_jobs` (the RPC `/api/strategies/[id]/sync-progress`
  already calls), compared by job identity or by server `created_at` against a server value read
  before the enqueue — and records which arm closes the case. `useStrategySyncPoller` already
  selects `computed_at` and does not pass it on; the ladder (wizard) arm must stay byte-unchanged
  unless the planner shows the wizard has the same defect.
  — **Reversibility:** reversible — client poll logic.

- **KCS-03: The link update and the enqueue each get a client-side bound (residual 4).** On expiry
  the attempt ends with copy that does NOT say the sync failed, because it may have been enqueued:
  it says the card could not confirm the sync started and what to do next. The bound is chosen
  with evidence, not as a round number: it must sit below the route's `maxDuration = 300`
  (`src/app/api/keys/sync/route.ts`) and above the slow-but-successful enqueue durations the
  167-06 review rounds used (36 s and 126 s, 167 D-18 R4 lineage). `TERMINAL_REREAD_BOUND_MS` is
  the in-file precedent for a named bound constant.
  — **Reversibility:** reversible.

- **KCS-04: A withheld success is retired at the moment it is withheld (residual 2).** Today R2
  withholds the render and R3/R5 retire it on this tab's own actions, so a re-read after another
  tab's `Update password` or `Delete` can lift the withhold and re-show it. The fix the ROADMAP
  names is taken: when the terminal success is withheld because its subject key is untrusted, the
  panel's success state is retired then, so no later re-read can resurrect it. Consequence,
  accepted: if another tab has since fixed the key, this tab shows no "Up to date" for that
  attempt; the key's pill clears on the next read, which is the truthful signal. `retireWithheldSuccess`
  stays the one retirement helper (167 D-18 R5); this is a new CALL SITE for it, not a second
  mechanism.
  — **Reversibility:** reversible — redesign of one render rule, client-only.

- **KCS-05: The 167 D-18 R1–R6 rules stay in force unless a decision above replaces one by name.**
  KCS-01 replaces R6's "while an attempt is live the post-add catch reaches the console only"
  (there is no post-add sync while an attempt is live). KCS-04 replaces R2's "withheld" with
  "retired". Every other rule, and every neuter-pinned test behind it, is kept.

### B. The `/strategies` list pill (167 D-19)

- **KCS-06: A strategy row is marked when ANY of its feeding keys is untrusted.** Feeding keys are
  `strategies.api_key_id` plus the composite's `strategy_keys` members (owner-scoped RLS on both:
  `api_keys_owner`, `strategy_keys_owner`). The mark reuses the existing key-level pill (the
  `AllocatorSyncStatus` pill or the `untrustedKeyChipLabel` chip; the UI-SPEC picks one and says
  why) with the existing copy; no new colour, token or copy family. When two keys are untrusted
  with different statuses, each distinct status shows once. The row states what the pill is
  about (a key) and makes no claim about the strategy's numbers (167 D-02, D-03). The row's
  existing name link already goes to `/strategies/[id]/edit`, where the remedy lives (167 D-18).
  ⛔ The read is owner-scoped on the request client and never touches a factsheet path (167 D-04).
  — **Reversibility:** reversible — additive UI.

### C. The compute-state surfaces (2026-09-23 widenings)

- **KCS-07: One pure derivation decides the compute state, and every surface in this section calls
  it.** Input: the rows `get_user_compute_jobs` (or, on the share page, an equivalent admin read
  bounded by the matched strategy id, KCS-11) returns. Output: exactly one of the existing states,
  named in owner terms — `queued` (`pending`), `retrying` (`failed_retry`), `running` (with, for a
  `stitch_composite`, "key N of M" from `metadata.member_progress`), `stalled` (the EXISTING
  `stalled` rule only: a running stitch whose heartbeat is older than `STALL_THRESHOLD_MS`),
  `failed` (`failed_final`, carrying `error_kind`), `finished` (`done` / `done_pending_children`)
  and `never_started` (no row). ⛔ **No new job states are invented** (ROADMAP fence): each output
  maps one-to-one to a `compute_jobs.status` value or to the absence of a row, except `stalled`,
  which is the rule `sync-progress` already ships. ⛔ **A non-stitch job is never `stalled`**:
  `/api/strategies/[id]/sync-progress` records why (its `claimed_at` never moves, so a long healthy
  single-key crawl would read as stalled and push users to abort healthy work). The route and the
  new surfaces share the derivation rather than re-implementing it, so the job-selection rule
  (stitch-preferring, latest by `created_at`) is written once.
  — **Reversibility:** reversible.

- **KCS-08: "Fetching trades" versus "computing" is decided by the job's `kind`, from the closed
  `compute_jobs_kind_check` set.** Fetch kinds (the planner enumerates them from the constraint,
  e.g. `process_key_long`, `sync_trades`) say the service is reading trades from the exchange;
  derivation and analytics kinds say it is computing. An unrecognised kind gets a neutral "working
  on it" line, never a guess. For a composite the stitch job's member progress supplies "key N of
  M"; for a single key no N of M is shown because no writer publishes one.

- **KCS-09: The OWNER lane of the pending factsheet (`src/app/factsheet/[id]/v2/page.tsx`, the
  `!payload` branch with `lane === "owner"`) reads the strategy's latest compute job and states its
  real state in authored copy.** Failed renders an authored reason keyed on `error_kind`
  (`permanent`, `transient`, `unknown`, `orphaned`, anything else), consistent in meaning with the
  SQL's curated `computation_error_copy` and `get_user_compute_jobs.user_message` (retry-positive
  for `orphaned`, "retrying alone will not resolve it" for `permanent`), and ⛔ never raw exception
  text (`last_error` is operator-only and the RPC already redacts it to NULL). `stalled` and
  `never_started` say what the owner can do (the `Resync` control on the edit page; contact
  support for a `permanent` failure). `finished`-but-no-payload says the last run finished but the
  factsheet could not be built from its results, without naming an internal gate (164.2
  criterion 9). The sentence "Some strategies stay in this state, and this page is all there is
  until one has been computed." is removed.
  ⛔ **D-04 still binds:** the read runs on the request-scoped client, inside the owner branch,
  lane-local like `ownershipMark` and `hasActiveShare`, and never enters `FactsheetPayload`,
  `fetchAndBuildPayload` or `buildFactsheetPayloadCached`. `phase-148-owner-lane-cache-isolation`
  and `page.owner-lane.test.tsx` stay green unedited. A read error degrades to a neutral sentence
  that claims no state, logged server-side (Rule 12), and never to a false "computing".
  — **Reversibility:** reversible — request-scoped render only.

- **KCS-10: The PUBLIC lane placeholder names no internal state, and it stops claiming one.** The
  public lane cannot read owner job state and must not (ROADMAP fence; 164.2 criterion 9). Today
  its first paragraph asserts "still computing … once the analytics service finishes the first
  compute pass", which is false for a failed or never-started strategy, the same false promise the
  share-page widening forbids. It becomes one neutral sentence that is true in every state and
  promises no timing. The "Some strategies stay in this state" sentence goes on this lane too (it
  is the same element today, not lane-gated). The criterion-9 rendering test keeps binding to the
  anonymous render and keeps failing if the developer-facing sentence returns.
  — **Reversibility:** reversible — copy.

- **KCS-11: The share page (`src/app/factsheet-share/[token]/page.tsx`) tells an in-progress
  compute from a terminal one, in neutral copy.** Two viewer-facing arms only:
  (a) `queued` / `retrying` / `running` (not stalled): the link works and the data is being
  prepared (the existing card, which may keep "try again later" but must not promise a number of
  minutes unless the copy can defend it); (b) `failed`, `stalled`, `never_started`, `finished`
  without a payload, or an unreadable state: the link works, the factsheet is not available yet,
  and nothing promises it will appear on its own. ⛔ No internal cause, job state name, error kind
  or owner action is shown to the recipient (164.2 criterion 9; the viewer has no console and no
  remedy). An unreadable state falls to arm (b), never to "being computed" (fail closed on the
  promise).
  ⛔ **The added read is bounded exactly as the SECURITY BOUNDARY header demands:** by the matched
  strategy id, on the admin client, projecting only the columns the derivation needs (`status`,
  `kind`, `error_kind`, `created_at`, `claimed_at`, the heartbeat and member-progress keys of
  `metadata`). ⛔ Never `last_error`, never owner identity, `api_keys`, holdings or AUM, and never
  through `buildFactsheetPayloadCached` (SL-1: the module must still have no cache reach, and
  `page.no-cache-reach.test.ts` / `page.cache-isolation.test.tsx` stay green).
  ⛔ **A plan that touches this route earns a `checkpoint:decision`** per 167 D-04 ("a plan that
  touches … the share route"), unless the planner shows the read is bounded as above and adds no
  cache reach; record which.
  — **Reversibility:** reversible — but the read is on a public route, so the projection is the
  reviewed surface.

- **KCS-12: CREATING A SHARE LINK BEFORE THE FIRST SUCCESSFUL COMPUTE STAYS ALLOWED. The owner's
  share affordance says what a recipient will see.** This is the ROADMAP's open question, decided
  on evidence:
  1. Phase 164 built the valid-token-but-no-payload arm on purpose. The share page's own comment:
     *"'still computing' is exactly when an owner is most likely to have shared it"*, and the
     owner-lane placeholder carries the share notice for the same reason (`page.tsx` WR-02). The
     affordance is a shipped, tested design, not an accident.
  2. The founder's complaint is the false promise (*"a promise that will not come true"*) and the
     confusion (*"can already post or copy a link but can't see it"*), both of which are copy
     defects KCS-11 and this decision close. Neither asks for the capability to be removed.
  3. The token re-derives from the stored `(nonce, generation)` pair and mint is idempotent, so a
     link handed out early becomes a working factsheet the moment a compute succeeds, with nothing
     to re-send. A refusal would only delay the owner's own onboarding.
  4. A refusal would be a new server gate on the mint route (a new analytics read under a
     csrf→auth→validate→limiter→ownership ordering pinned by `share/route.test.ts`) plus new
     refusal copy, and it would still not cover the case that matters most here: a strategy that
     computed once and then failed, whose link already exists.
  5. It is reversible: a later gate can be added to the mint route at any time without touching a
     link already issued.
  **What changes instead:** where the owner gets the link for a strategy with no computed
  factsheet, the affordance states, beside the control, what the recipient will see now: the
  "being prepared" page while a compute runs, or the "not available yet" page when it failed,
  stalled or never started. Surfaces: the owner-lane pending factsheet (its `OwnerUnpublishedPanel`
  sits above the KCS-09 state block) and each `/strategies` row's `ShareableLink`. On `/strategies`
  the row reads the state through the same KCS-07 derivation, only for rows without a computed
  factsheet; the planner decides the exact "has a computed factsheet" predicate from the columns
  the page can read owner-scoped (`strategy_analytics.computation_status` / `computed_at`) and
  records it. `ShareableLink`'s mint path and label logic are unchanged.
  — **Reversibility:** reversible.

### E. Amendments after research (2026-09-23, orchestrator, autonomous) — these SUPERSEDE the clauses they name

`167.2-RESEARCH.md` surfaced five open questions; two contradicted locked decisions above. Per
Rule 7 each is resolved here, not averaged, and the superseded clause is named. All are
reversible, client- or route-level, and need no migration.

- **KCS-18 (amends KCS-02) — the warned-row early terminal is CLOSED in this phase with a job-state
  arm.** Measured by research (RESEARCH P1): on a row already at `complete_with_warnings`, the SQL
  bridge keeps that status while jobs run but still moves `computed_at`, so (a)+(b) accept a
  mid-chain row as the attempt's result. Research also settled KCS-02's fast-fail case: (b) closes
  it, because the failed branch of the latest `sync_strategy_analytics_status` writes
  `computed_at = now()`, so no third arm is needed THERE. **Decision:** before an attempt accepts a
  terminal SUCCESS (`complete` or `complete_with_warnings`), it reads
  `/api/strategies/[id]/sync-progress` once and accepts only when no factsheet-chain job is in
  flight (not `pending`, `running`, `failed_retry` or `done_pending_children`); otherwise it keeps
  polling. A `failed` terminal needs no job-state read. A degraded or failed read of that route
  does not accept the success (fail closed on the claim, keep polling). Existing route and limiter
  only.

- **KCS-19 (amends KCS-07) — `done_pending_children` is IN PROGRESS, not finished.** Measured
  (RESEARCH P9; the job-insert function in `supabase/schema/baseline.sql` starts rows with
  unfulfilled parents as `done_pending_children`, and the in-flight unique index and the bridge
  both count it non-terminal). It maps to `queued`. The comment on `StitchJobStatus` in
  `src/lib/sync-progress.ts`, which calls it terminal-success, is corrected in the same change.

- **KCS-20 (amends KCS-07) — job selection is restricted to FACTSHEET-CHAIN kinds, in the route
  too.** Measured (RESEARCH P8): recurring cron kinds (`reconcile_strategy`, `sync_funding`) can
  be a strategy's latest job, so "latest of any kind" can describe a job unrelated to the
  factsheet. Selection is the latest `stitch_composite`, else the latest job whose kind is in the
  chain set RESEARCH Q3 enumerates. `/api/strategies/[id]/sync-progress` adopts the same
  selection, so its `jobStatus: null` now means "no factsheet-chain job visible" (a deliberate
  behaviour change on an internal route, recorded here; `route.test.ts` gains cases for it; the
  stitch-preferring arm and the PIN-COMPOSITE-* pins are unchanged). **`never_started` is also
  worded as a claim retention cannot falsify** (RESEARCH P10: finished jobs are deleted after 30
  days, failed ones after 90): the copy says no computation is running or recorded, never that
  none ever ran.

- **KCS-21 (amends KCS-09) — the owner's remedy is keyed on strategy SHAPE.** Measured (RESEARCH
  P14): a composite's edit page passes `currentKeyId = null`, so no key shows `Resync`, and CSV
  strategies render `CsvStrategyEditNote` with no sync control. So: single-key API strategy → the
  `Resync` control on the edit page; composite → contact support (no safe self-serve re-run
  control exists on its card, see KCS-23); CSV → the CSV path the edit page already names, else
  contact support. The UI-SPEC locks the table.

- **KCS-22 (amends KCS-02) — running out of poll budget on the key card is NOT a failure line.**
  Measured (RESEARCH P2): with stale terminals ignored, the panel's poll cap can expire during a
  long, healthy exchange fetch, and the current cap copy says the computation timed out. On cap
  expiry the panel shows a non-failure line (the sync may still be running; the factsheet updates
  when it finishes), and no Retry is offered while a job may be live (a re-POST during
  `failed_retry` inserts a second job, per the F-3 note in `src/lib/sync-progress.ts`).

- **KCS-23 (NEW, folded in) — on a COMPOSITE strategy the key card offers no control that rewrites
  `strategies.api_key_id`.** Measured (RESEARCH P14; `ApiKeyManager`'s `handleLinkKey` does an
  unconditional `update({ api_key_id })`): every key on a composite's card shows `Use & Sync`,
  which would re-link the composite to one key and silently make it a single-key strategy. That is
  a data-integrity defect on the exact component this phase owns, so it is fixed here rather than
  deferred (data-integrity items are fixed or phased, never left implied). The card learns the
  strategy's shape from its page (the edit page already reads the strategy) and, for a composite,
  renders no `Use & Sync` / link control; the key list, pills, `Update password` and `Delete`
  behave as before. — **Reversibility:** reversible — client-only; no data moves.
  **Clarified 2026-09-23 after UI-SPEC:** `Add Key` is ALSO a link control — `handleAddKey` writes
  the same unconditional `api_key_id` link — so on a composite card `Add Key` is not offered either.
  This card offers no change of composite membership; the wizard's composite members route is
  scoped to drafts, so for a submitted composite the UI-SPEC names support as the path.
