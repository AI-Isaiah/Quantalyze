**Q1, which keys are the account's keys.**
- `_allocator_has_other_api_keys` counts EVERY api_keys row of the user other than the job's key, "whatever its
  is_active, sync_status (revoked and NULL included) or disconnected_at", because the history a departed key wrote "is
  still in the allocator's rows".
- Stored rows are NOT attributed to a key. There is one row per (allocator_id, asof) with a per-SYMBOL breakdown. The
  reconstruct writes it first-writer-wins; the daily refresh writes one row summing every counted exchange account.
- So a key's share cannot be separated and kept: "preserve" is impossible, and each exchange account must be rebuilt or
  the whole rebuild refuses.
- A departed key is covered only when a WORKING key reads the same exchange account (`account_groups`).

**Double counting.**
- services/account_identity.py's module docstring: "One exchange account behind two live keys is summed twice by every
  consumer that adds keys together."
- Both allocator writers count each `account_groups` group once, and both hold when
  `identity_pending_venues(key_rows, VENUES_WITH_ACCOUNT_ID - {"deribit"}) > 0`: the refresh in
  `_fetch_latest_holdings_per_eligible_key`, the derive through its blocking ACCOUNT_IDENTITY_PENDING.
- The rebuild reuses those exact helpers and adds none.

**Q2, mixed venues.**
- bybit and binance: the ccxt crawl with require_anchor=True (plans 01/02/05).
- mt5: `_mt5_fetch_window`, the full deal ledger, no anchor (plan 05 PD-H's exclusion).
- okx CAN NEVER complete a forced rebuild. `_fetch_trades_with_pagination` sets hit_okx_terminus whenever since is older
  than OKX_TRADE_TERMINUS_DAYS. That is always true for a BACKFILL_CAP_DAYS (730) window, and plan 05 refuses a forced
  curve with hit_terminus.
- sfox: no reconstruct crawl.
- deribit contributes $0 to the stored aggregate. The reconstruct's deribit arm refuses every Deribit reconstruct, and
  `run_refresh_allocator_equity_daily_job` skips holdings whose venue is 'deribit' (Phase 71 SC-3). So it is counted as 0,
  never crawled and never refused (PD-T).

Planner decisions (continuing PD-A..PD-J of plans 01-05):

**PD-K (selection).** `def _select_account_crawl_keys(account_keys, job_api_key_id) -> tuple[list[Mapping[str, Any]], int]`.
For each group of `account_groups(account_keys)`, in order:
- The members' lower-cased exchanges must form one venue; more than one gives account_key_venue_unsupported.
- deribit: skip the group and count it.
- A venue outside `_ACCOUNT_REBUILD_VENUES` = {bybit, binance, mt5}: account_key_venue_unsupported.
- No member passes `working_holder_predicate`: account_key_not_working.
- Otherwise select the job's own key when it is a working member, else the working member with the smallest id.

After the loop, `identity_pending_venues(account_keys, VENUES_WITH_ACCOUNT_ID - {"deribit"}) > 0` gives
account_identity_pending (the refresh's exact call). Returns (the selected keys in group order, the number of Deribit
exchange accounts skipped).

**PD-T (Deribit counts as 0).** `_ACCOUNT_ZERO_CONTRIBUTION_VENUES = frozenset({"deribit"})`, with a comment citing the
reconstruct's deribit arm and the refresh's Deribit skip. A Deribit group is never crawled, never refused, and adds
nothing to any summed row.

**PD-L (revised: the summed curve, never invented).** `def _sum_account_rows(per_account_rows) -> tuple[list[dict[str, Any]], int]`:
- The day set is the INTERSECTION of the accounts' row days. days_incomplete = the size of the union minus the
  intersection.
- Per day: value_usd = round(sum, 2).
- breakdown = the per-entry sum (rounded 2dp) of the numeric, non-bool entries of the contributing rows, with
  `__truncated__` True when any contributing breakdown carries it, passed through `_cap_breakdown`; None when no
  contributing row has a dict.
- source = the one source all contributing rows share, else "mixed". pre_terminus_balance_unknown = any.
- Rows sorted by asof. A single account's rows come back with the same days.

WHY no zero-fill: a day an exchange account has no row is either a day it held nothing (not yet funded, or emptied) or a
day its replay could not price, and nothing the crawl returns tells the two apart. The breakdown's STARTING_BALANCE entry
is the anchor offset (`anchor - last_value`) spread over every row; it is nonzero for any replay residual, so it is not a
pre-window-balance signal. A left-out day that the allocator already has stored is never deleted silently: plan 09's
check refuses that replace.

**PD-U (telemetry merge).** `def _merge_account_telemetry(parts) -> dict[str, Any]`:
- sorted unions of skipped_symbols, unknown_perp_symbols, inverse_perp_symbols and anchor_partial_ticker_symbols (each
  read with `.get(key, [])`);
- concatenated ctval_drift_warnings;
- `any` of pre_terminus_balance_unknown, anchor_offset_implausible and anchor_replay_unreliable;
- the rounded sum of anchor_offset_skipped_usd.
Read everything with defaults: mt5 telemetry omits the anchor keys on purpose.

**PD-R (one closed refusal vocabulary).**
- `FORCED_REBUILD_ANCHOR_REASONS` = plan 05's six.
- `FORCED_REBUILD_ACCOUNT_REASONS` = account_state_unreadable, account_identity_pending, account_key_venue_unsupported,
  account_key_not_working, account_key_read_failed, account_key_no_rows, account_sum_empty, account_keys_changed,
  history_predates_window, history_days_unreproduced.
- `FORCED_REBUILD_REFUSAL_REASONS` is their union (16).
- `def _forced_refusal_message(reason: str) -> str` returns, for an anchor token, EXACTLY the text plan 05's refusal arm
  builds today, and otherwise "forced rebuild refused (<reason>): the account's stored history could not be rebuilt in
  full and replaced in one step, so nothing was written and the stored curve is unchanged (Phase 167.2.1.1 D-04)".
- Every refusal is error_kind "permanent" (PD-I).
