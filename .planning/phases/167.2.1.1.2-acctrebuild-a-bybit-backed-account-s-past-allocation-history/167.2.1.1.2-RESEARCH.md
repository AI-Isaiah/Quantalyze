## Summary

UPNLVENUES shipped on main (`9630f6aa1`) the **sole-key** forced rebuild only. `run_reconstruct_allocator_history_job` honours `metadata.force_rebuild` JSON `true`, crawls with `require_anchor=True`, and replaces through the existing `replace_allocator_equity_snapshots` RPC. For any user with a second `api_keys` row it refuses `multi_key` (or `sibling_lookup_failed`) before the crawl. The plan-checked design inputs 07-11 were **never executed and are not in the tree**; the `167.2.1.1-*` phase directory on main holds only a `.gitkeep`. They are a starting design, not code: this phase builds the whole-account crawl from scratch against the shipped handler.

The four design questions resolve as follows.
1. **Compose.** Window length is one number for the whole account: 90 calendar days when any crawled exchange account is OKX, otherwise the existing 730. Every venue's crawl takes that one `start_date`, because the stored row is the SUM across exchange accounts and a day only one venue can supply cannot be a correct row. OKX needs `start_date = end_date - 89 days`, not 90, or `_fetch_trades_with_pagination` flags the terminus and the forced path refuses.
2. **Scoped replace needs a migration.** The existing RPC DELETEs every row of the allocator; re-sending older rows through it would reset their `reconstructed_at`, overwrite each row's `history_depth_months` with the one `p_depth_months`, and race the daily refresh. Add a new function (new name, no overload) that deletes only `asof >= p_window_start`.
3. **Boundary date.** `allocator_equity_snapshots` has no metadata column. Recommended store: one row of the existing `allocator_equity_derived` table, `kind = 'snapshot_rebuild_boundary'`, written by the new function in the same transaction. No schema change to that table (its `kind` has no CHECK). **Critical finding (for the planner and founder, section Open Questions OQ-1):** no chart or return on screen is built from `allocator_equity_snapshots` today; the Allocations curve and returns come from the derived `equity_curve` row.
4. **Race.** Yes, the stored-days check moves into the new function, as a check on exactly the rows its own DELETE removed (`DELETE ... RETURNING`, raise on any not in the payload, the raise rolls the delete back). That closes the race the shipped handler names ("ACCEPTED RACE ... ACCTREBUILD 167.2.1.1.2 owns the in-transaction version").

**Primary recommendation:** unify the forced path (1..N keys) into one account path that computes one window, crawls each exchange account once with `require_anchor=True`, sums over shared days, and calls one new SECURITY DEFINER function that replaces `asof >= window_start`, refuses (in SQL, counts only) on any unreproduced stored day in the window, and upserts the boundary row. Treat a refusal as an expected, valid SC-3 outcome: the 90-day replay starts at zero cash, so many accounts will refuse `history_days_unreproduced` or `account_key_no_rows` (see Pitfall 2).

## Answers to the four questions

### Q1. How the OKX 90-day crawl composes with the other venues

**Recommendation: one window for the whole account. `window_days = 90` iff any selected (crawled) exchange account is on OKX, else 730. Every venue's crawl receives the same `start_date`.**

Evidence:
- The stored row is one aggregate per `(allocator_id, asof)` with a per-symbol breakdown, not attributed to a key; first-writer-wins ON CONFLICT DO NOTHING in `persist_equity_snapshots` (`:1370-1377`, `on_conflict="allocator_id,asof", ignore_duplicates=True`), and the daily refresh writes through the same function (`:4917`). A day only some exchange accounts can supply is not a correct row, so mixed windows would produce either shared-days-only rows (dropping every Bybit-only day past 90) or short rows. One window is the only consistent reading.
- OKX history fetcher: `_fetch_trades_with_pagination` (`:578`): for venue `okx` it fans out across `OKX_INSTRUMENT_TYPES` and `OKX_TRADE_TERMINUS_DAYS: int = 90` (`:102`) bounds it: `hit_okx_terminus = since_ms < okx_terminus_ms` with `okx_terminus_ms = now_ms - OKX_TRADE_TERMINUS_DAYS * 24 * 60 * 60 * 1000`. Transfers are clamped to the same terminus when hit (`:2802-2805`). OHLCV is per symbol, `_fetch_ohlcv_daily` (`:680`). Daily equity reconstruction DOES exist for OKX (replay in `_compute_daily_equity`), and the anchor is OKX's raw `totalEq` via `fetch_okx_total_equity_usd` (`:3149-3154`, "totalEq already includes open-position unrealized PnL"), so no open-uPnL double count.
- **Why 89, not 90.** `start_ms` is midnight UTC of `start_date`; `now_ms` is read inside `_fetch_and_price_window` (`:2792`). With `start_date = end_date - 90 days`, `start_ms = M - 90d < now - 90d` for any `now > M`, so `hit_terminus` is always True, the anchor is skipped, and on the forced path `if hit_terminus: _refusal = "anchor_skipped_okx_terminus"` (`:3019-3020`) refuses. With `start_date = end_date - (OKX_TRADE_TERMINUS_DAYS - 1)` days, `start_ms = M - 89d >= now - 90d` iff `now - M <= 1 day`: True for the whole UTC day [derived from the code above]. That window is exactly 90 calendar days inclusive of today. State "90 days" as `window_start = today - 89d` in the audit and handoff. **Residual edge:** a job that crosses 00:00 UTC mid-crawl would refuse `anchor_skipped_okx_terminus` (permanent); the handoff must avoid enqueue near midnight UTC and a re-run clears it.
- Non-OKX window is unchanged: `start_date = end_date - timedelta(days=BACKFILL_CAP_DAYS)` with `BACKFILL_CAP_DAYS: int = 730` (`:103`, `:4100`).
- **MT5 provides** the full deal ledger (`history_deals_get` "is a FULL-HISTORY fetch with no retention terminus", `:3447-3449`), clipped by `_mt5_rows_from_levels` to `[start_date, end_date]`, dense across quiet days by forward-fill, and "days inside the window but BEFORE the account's first ledger event get NO ROW AT ALL". It is realized-basis, no anchor, `breakdown` NULL, `source` `'exchange_primary'`, `pre_terminus_balance_unknown` False. Clipping to 90 days is exact for MT5 (it carries its pre-window balance forward). `_mt5_telemetry()` omits the four `anchor_*` keys on purpose.
- **Deribit counts as zero:** `run_reconstruct_allocator_history_job` refuses every Deribit reconstruct (`:4031-4046`) and the daily refresh skips holdings with `(h.get("venue") or "").lower() == "deribit"` (`:4744`). A Deribit exchange account is neither crawled nor refused.
- **sFOX / any other venue:** no snapshot reconstruct crawl (only mt5 has a venue branch; everything else goes to the ccxt path). Keep `account_key_venue_unsupported` for sfox and unknown venues only. **OKX leaves the unsupported set.**
- **Is the shared-days sum with no zero fill still correct inside a 90-day window?** Correct as a no-invention rule, but it behaves differently. `_compute_daily_equity` emits a row only on a day with a non-empty breakdown or non-zero total (`if breakdown or total:`, `:1262`), and the replay starts at `quantities={}` at `start_date`. Inside a clipped window an exchange account that held assets before the window but traded/transferred nothing until day k has NO rows for days before k (and an account idle for the whole window has no rows, so `account_key_no_rows`). The anchor offset is added only to rows that exist (`:3001-3008`). So the sum drops those days and D-02 refuses whenever a stored day sits there. This is the honest outcome under D-02, not a bug; do not zero-fill (nothing in the crawl separates "not funded" from "unknown").
- Account-selection rules to carry from design 07 (all verified present): group with `account_groups`; deribit skipped and counted; one working key per group (job key preferred, else smallest id); no working member -> `account_key_not_working`; `identity_pending_venues(account_keys, VENUES_WITH_ACCOUNT_ID - {"deribit"}) > 0` -> `account_identity_pending` (the refresh's exact call, `:2311`).

### Q2. Can `replace_allocator_equity_snapshots` do a window-scoped replace?

**Answer: no, it needs a scoped variant, which is a migration.**

Reject.

**Recommended minimal shape** (a NEW name, never an overload: PostgREST resolves RPCs by name and argument names, and an overload of the same name risks ambiguity):

```
replace_allocator_equity_snapshots_window(
  p_allocator_id  UUID,
  p_rows          JSONB,     -- same element shape as today
  p_depth_months  INTEGER,
  p_window_start  DATE
) RETURNS INTEGER            -- rows inserted, like the original
SECURITY DEFINER, SET search_path = public, pg_temp, SET lock_timeout = '3s'
```

2. Shape guard: `p_rows` is a non-empty array and no row has `asof < p_window_start` (22023).

WHERE allocator_id = p_allocator_id AND asof >= p_window_start RETURNING asof)`; if any `del.asof` is not among the payload's `asof` values -> `RAISE EXCEPTION` (P0001, message token `history_days_unreproduced`, DETAIL a count only). ### Q4. Does the stored-days check move inside the replace transaction?

**Yes, and it should be the only implementation.** The shipped check (`_allocator_snapshot_asofs` -> paged read -> `<= {r["asof"] for r in rows}`) runs as a separate round-trip before the RPC, so a row the daily refresh writes (its `persist_equity_snapshots` takes NO advisory lock) between the read and the DELETE is removed unseen; that is the accepted race the handler comment names. Doing the check in SQL as `WITH del AS (DELETE ... RETURNING asof)` and comparing `del.asof` against the payload's days checks exactly what was deleted, in the same statement and transaction; a raise rolls the delete back. This forces the migration route (already forced by Q2). Consequences:
- Drop `_allocator_snapshot_asofs` from the forced path and the Python pre-read; the old tokens `history_outside_replay` and `multi_key` / `sibling_lookup_failed` go with the unified path. `test_the_stored_history_guard_reads_past_the_response_row_cap` loses its subject (SQL has no row cap); its intent moves to the SQL test.
- The worker maps a refusal by the message token. Precedent: `services/okx_archive_job.py` (around `:2282`) handles `apply_okx_archive_rebuild` P0001 messages `gaps_changed` / `gaps_after_mismatch`, tested with a `_PgError("P0001", "apply_okx_archive_rebuild: gaps_changed")` fake (`tests/test_okx_archive_apply.py:381`). [ASSUMED: the PostgREST error surface for the new function matches; the planner should read `okx_archive_job.py` around that line and reuse its mapping.] The RAISE message must carry no id or amount.

## Architecture Patterns

### System flow

```
enqueue_compute_job (service role, metadata.force_rebuild = true, one job per account)
   -> run_reconstruct_allocator_history_job
        forced? -> _read_account_keys -> _select_account_crawl_keys (account_groups; deribit = 0; sfox -> refuse)
                -> window_start = today-89d if any selected venue is okx else today-730d
                -> concurrent _crawl_account_key per exchange account (same start_date, require_anchor=True; mt5 via _mt5_fetch_window)
                -> _sum_account_rows (shared days only)  -> account_sum_empty if none
                -> re-read key ids -> account_keys_changed on mismatch
                -> replace_equity_snapshots_window RPC  (delete asof >= window_start RETURNING; raise if any not in payload;
                                                          insert; upsert/delete boundary row)  -- one transaction
                -> mark keys, audit (window_days, counts)
   refusal anywhere before the RPC, or a raise inside it -> reconstruct_failed / permanent / "forced rebuild refused (<token>)" / nothing written
```

### Recommended structure
Extend `services/equity_reconstruction.py` in place (the handler, wrapper and helpers live there today); new test module `tests/test_reconstruct_whole_account.py`; one migration + one `supabase/tests/test_*.sql`; one TS parser + query field + test.

### Anti-patterns
- Re-sending kept rows through the old RPC. Zero-filling a missing exchange-account day. Setting window to 90 days back (terminus flag). Writing the boundary row from Python after a committed replace. A second implementation of the stored-days check in Python.

## Common Pitfalls

1. **Window = 90 days back flags the terminus.** See Q1: `start_date = end_date - 89 days`; add a test that fails with 90. Midnight-UTC crossing refuses `anchor_skipped_okx_terminus`.
2. **Expect many refusals, and that is correct.** Zero-cash replay at window start leaves days before an account's first in-window activity empty; the shared-days sum drops them; D-02 refuses where a stored day exists there. The unforced OKX reconstruct, by contrast, flags `pre_terminus_balance_unknown` and skips the anchor (`:2947-2960`). A clipped-window rebuild sets that flag False (no terminus hit) and anchors. See OQ-2.
3. **Test fake vs SQL drift.** `FakeSupabaseClient.rpc` (`tests/test_equity_reconstruction.py:315`) is a hand-written Python copy of the SQL. A green Python test proves the mapping only; the SQL semantics (window-scoped delete, refusal rollback, boundary upsert) must be proven by the `supabase/tests` file and its mutation twins.
4. **Old rows' metadata.** The only way `reconstructed_at` and `history_depth_months` of kept rows survive is never touching them. Assert byte-identity in both the SQL and the Python test.
5. **Rows exactly at the window start** belong to the window (replaced, must be reproduced).
6. **Do not unify with the unforced path.** The unforced sole-key replace and the DO-NOTHING multi-key persist stay as they are (default unchanged).
7. **`pre_terminus_balance_unknown`:** the function projects it per row; MT5 rows carry False, ccxt rows carry the crawl's `hit_terminus`.
