<objective>
Close the gap the plan checker found. `replace_allocator_equity_snapshots` deletes every stored row of the allocator.
Plan 07's summed curve (PD-L, shared days only) can legitimately lack a day the allocator already has, and so can any
rebuild that starts after the stored history begins. Without a check, that day is deleted silently.

D-04 says a forced rebuild "replaces that account's history in one atomic step, or refuses and writes nothing". So both
forced replace paths now refuse, with a named token, when the replace would delete a stored day the rebuild does not
reproduce. This plan also closes the sole-key path's fall-through to first-writer-wins when a sibling appears mid-job
(PD-Q), and makes the closed vocabulary exact.

Purpose: SC-3 ("recomputed or recorded"): a refused account is recorded by token, never half-rebuilt. SC-2, because the
sole-key anchored rebuild of plans 04/05 gets the same guard.
Output: the check and the PD-Q refusals in `services/equity_reconstruction.py`; tests in
`tests/test_reconstruct_whole_account.py`; the equality pin in `tests/test_reconstruct_force_rebuild.py`.
</objective>

Measured by the planner at HEAD 0da7c814e (cite by symbol, never by line):
- The handler sets `end_date` to today (UTC) and `start_date = end_date - timedelta(days=BACKFILL_CAP_DAYS)` (730).
  Both crawls cover [start_date, end_date] and emit a row only on a day with a nonzero value or breakdown, so a rebuilt
  curve starts at its first activity, possibly after start_date.
- `replace_allocator_equity_snapshots` (latest body: migration 20260602183000) DELETEs every row of the allocator and
  INSERTs the payload ON CONFLICT DO NOTHING. Its only guard on deletion is the Python one in `replace_equity_snapshots`
  for an EMPTY payload (`EmptyReplaceRefusedError`). A non-empty payload deletes any day it lacks.
- The test fakes support everything the check needs. `_FakeTable` has `lte`, `gte`, `limit` (a no-op) and
  `select(count="exact")`, and the RPC emulation deletes and inserts like the SQL. `_RecordingTable` fails only the HEAD
  api_keys select when `fail_sibling_lookup` is set, so `_read_account_keys` (a non-head select) is unaffected.
- The marker-writer crawl (`_crawl_exchange`) produces rows on END_DATE minus 0..9 days, the same ten days
  `_seed_sentinel_rows` seeds. A rebuild over those sentinels therefore covers every stored day, and an extra stored row
  on any other day is not reproduced.

Planner decisions:

**PD-P (revised after the plan check; was "pre-window rows only").**
`async def _refuse_if_replace_drops_stored_days(supabase, allocator_id: str, start_date: date, rows: Sequence[Mapping[str, Any]]) -> None`.
- rebuilt = the set of `str(row["asof"])[:10]`.
- Read 1, through `db_execute`: `allocator_equity_snapshots` asof where allocator_id matches and
  `asof <= (start_date - 1 day)`, limit 1. Any row raises history_predates_window: no crawl can rebuild a day before its
  window.
- Read 2, through `db_execute`: asof with `count="exact"` where allocator_id matches and `asof >= start_date`.
  - If the response's count is not an int equal to the number of rows returned, raise account_state_unreadable
    (fail-safe against a truncated page; at most 731 days fit in one page).
  - If any stored day (`str(asof)[:10]`) is not in rebuilt, raise history_days_unreproduced.
- Either read raising: one WARNING with the exception class and `scrub_freeform_string` text, then
  account_state_unreadable from None.
- Every token is passed as a literal.

WHY refuse and never delete. A stored day the rebuild lacks is one of two things:
- a day one key's value was stored first-writer-wins (staggered key histories), or
- a day the account held something the replay cannot price.
Deleting it changes the user's history with no rebuilt value in its place. Keeping it beside rebuilt rows mixes two
readings in one curve. The founder decides whether either is acceptable (Founder decisions, and plan 11's ledger entry);
until then the safe default is to refuse.

**Placement.**
- Whole-account path: in the persist half, after PD-M's key-set comparison and immediately before
  `replace_equity_snapshots`.
- Sole-key path: when `forced` and `rows` is non-empty, immediately before `replace_equity_snapshots` in the
  `not sibling_check.has_siblings` branch. An empty forced replay keeps the existing EmptyReplaceRefusedError handling,
  which already writes nothing.
- The unforced path is not touched.

**PD-Q (a forced job never falls through to first-writer-wins).** In the non-account branch of the persist half, when
`forced`, right after the existing `allocator.equity.sibling_lookup_failed` audit emit:
- `sibling_check.lookup_failed` raises account_state_unreadable. It is checked FIRST, because a failed lookup also
  reports has_siblings True (fail-safe).
- Otherwise `sibling_check.has_siblings` raises account_keys_changed: `_read_account_keys` saw one row, so a sibling
  arrived during the crawl.
Both raise inside the persist try, whose first arm (plan 08) returns `_forced_refusal_result`.
