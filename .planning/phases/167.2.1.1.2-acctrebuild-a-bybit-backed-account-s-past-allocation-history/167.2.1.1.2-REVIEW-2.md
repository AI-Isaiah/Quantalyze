The rollback restores both old bodies and the old `replace_allocator_equity_snapshots` comment byte for byte.
- **The definer DELETE under FORCE RLS on the user path.** `delete_allocator_api_key` runs with an authenticated JWT, so the `service_all` policy does not admit it. The DELETE succeeds because the function owner, `postgres`, has BYPASSRLS on Supabase. The repo records this (`06-VERIFICATION.md`: "runs as `postgres` (BYPASSRLS=t)"), and BYPASSRLS overrides FORCE. Arm 13 exercises the authenticated path.
- **No other whole-history wiper exists.** No application code and no live function DELETEs every `allocator_equity_snapshots` row of an allocator other than the two that were patched. The DELETE in `20260529160000` belongs to a superseded definition.
- **The keep-earliest-seam rule.** I traced five cases and each is correct:
  - A forward re-run on a later UTC day keeps S1.
  - A wider window that deletes S1 takes the new seam, because `old < v_seam` is false.
  - When the payload starts after `p_window_start`, D-02 has already refused any stored day in `[W, v_seam)`.
  - The ELSE delete fires only when no stored row precedes W, which implies none precedes S1.
  - The correlated `EXISTS` inside `DO UPDATE SET` sees the same function's earlier DELETE and INSERT.
  - `v_seam` cannot be NULL on the upsert path, because `p_rows` is a non-empty array and every row is inserted.
- **Session cleanup.** A transient re-raise from the preflight loop or the gather loop still runs the `finally` that closes the opened sibling sessions.
- **Ordering in the gather loop.** It is key order. A transient at an earlier key masks a refusal at a later key, and the retries surface the refusal. That costs bounded extra crawls and loses nothing.
- **Tests.** `tests/test_reconstruct_whole_account.py` and `tests/test_reconstruct_force_rebuild.py` both pass (89 passed). The worktree was clean after my probes.

## Warnings

### WR-01 (MEDIUM, information disclosure, regresses this phase's T-167.2.1.1.2-24): a sibling's venue text reaches `compute_jobs` and the audit unscrubbed

**File:** `analytics-service/services/equity_reconstruction.py:4556` and `:4590` (the new re-raises). The sink is the handler's generic arm at `:4831-4855` and the rate-limit arm at `:4790-4802`.

**Issue:** T-167.2.1.1.2-24 is a `mitigate` threat. Its text is "venue error text (a planted signature) reaching the job error, the audit or the log". Its mitigation is that the gather converter logs the exception class only and raises `from None`. The fix now re-raises every transient-classified sibling exception unchanged. The handler then builds both `DispatchResult.error_message` (written to `compute_jobs`) and the audit's `sanitized_message` from `classify_exception(exc)`, which returns `str(exc)[:500]` unscrubbed. Only the log line goes through `scrub_freeform_string`.

The transient class is mostly `ccxt.NetworkError` and its subclasses, which are exactly the exceptions that carry the request URL. Measured with a scratch edit to the new parametrized test, now restored, using `ccxt.NetworkError("... ?apiKey=PUBKEY123&signature=deadbeefcafe ...")` on the sibling:

```
error_message = "fixture: GET https://api.bybit.com/v5/x?apiKey=PUBKEY123&signature=deadbeefcafe connection reset"
audit reconstruct_failed metadata.sanitized_message = (the same string)
```

The new test `test_a_transient_fault_on_one_account_ends_the_job_transient_and_writes_nothing` has no planted-signature assertion. The other sibling pins all have one, so this path is now uncovered. The own-key arms always behaved this way, but this phase explicitly mitigated the sibling path, and the fix reopened it.

**Fix:** Do not re-raise the venue exception. In `_crawl_whole_account`:
1. Log the class only.
2. Raise a phase-owned transient from `None` with static text, for example a small `_AccountCrawlTransient(exc_class_name)`.
3. Catch it in the handler ahead of `except ccxt.RateLimitExceeded`, and emit one `reconstruct_failed` with `error_kind` set to the classified kind and a static message naming only the exception class.

Add the planted-signature assertion, on the error, the audit and caplog, to the parametrized transient test. That arm also fixes WR-02 below, because it does not stamp.

### WR-02 (MEDIUM, operational; test weakened to hide it): a rate-limited sibling also stamps the job's own healthy key

**File:** `analytics-service/services/equity_reconstruction.py:4590` (re-raise), `:4790-4791` (`await _stamp_429(ctx.supabase, ctx.key_row, exc)`). The test is at `analytics-service/tests/test_reconstruct_whole_account.py:1005`.

**Issue:** `_crawl_account_key` stamps the sibling, which is correct. Its `RateLimitExceeded` is then re-raised out of the gather loop and lands in the handler's `except ccxt.RateLimitExceeded` arm. That arm stamps `ctx.key_row`, which is the job's own key, and that key was never rate-limited.

Measured by printing the stamp list in `test_a_rate_limited_sibling_is_stamped_and_ends_the_job_transient`:

```
stamped = ['...0002' (sibling), '...0001' (job's own key)]
```

`_stamp_429`'s own docstring says the stamp parks "every sibling job on this api_key behind the circuit breaker". So every job on the healthy key is deferred for the exchange cooldown, including the daily derive and syncs, along with the forced job's own retry. Round 1 pinned the invariant as `stamped == [{"p_api_key_id": API_KEY_ID_2}]` with the docstring "its own key, and only its own, is stamped". The fix weakened it to `API_KEY_ID_2 in stamped` and changed the docstring, so the regression passes silently. That is a Rule 9 failure: the test can no longer fail on the behaviour it was written to guard.

**Fix:** Do not route a sibling's rate limit through the handler's own-key stamp arm. The WR-01 fix (a phase-owned transient with its own handler arm and no stamp) removes it. Then restore the exact-equality assertion: `stamped == [{"p_api_key_id": API_KEY_ID_2}]` when the sibling is limited. Add the mirror case: when the OWN key is limited, the own key is stamped exactly once.

### WR-03 (MEDIUM, audit-trail integrity, breaks the SC-3 handoff read): an MT5 sibling failure leaves the job's key with no terminal audit

**File:** `analytics-service/services/equity_reconstruction.py:4500-4501` and `:4587-4588` (the `DispatchResult` pass-through), and `:4736-4740` (the handler returns it). The handoff text is in `.planning/phases/167.2.1.1.2-acctrebuild-a-bybit-backed-account-s-past-allocation-history/167.2.1.1.2-09-SUMMARY.md:192-193`.

**Issue:** `_mt5_fetch_window` is called with `api_key_id=str(key_row["id"])`, the MT5 sibling. Its `_fail` writes the one `reconstruct_failed` under that sibling's id. The fix then drops the job's own refusal audit. The result for one forced job, measured by printing `audit.call_args_list` in `test_an_mt5_account_that_fails_its_read_leaves_one_failure_audit`:

```
reconstruct_started  entity_id=...0001  (job key, forced_rebuild: true)
reconstruct_failed   entity_id=...0002  (MT5 sibling)
```

The job's key has a `reconstruct_started` and nothing after it. Plan 09's B'5 reads exactly that key (`entity_id` = the chosen key, `created_at >= t0`) and takes the terminal audit "after it". Census accounts (1) and (2) hold 5 and 2 MT5 keys, so for them B'5 finds no terminal event.

There are two further effects:
- The permanent MT5 arms (`auth`, account mismatch, post-read verification, `non_finite`, `deal_unclassifiable`, `nav_structural`, `negative_nav`, `kill_switch`) now end a forced job FAILED/permanent with neither the `forced rebuild refused (` prefix nor a refusal token. B'5's (iii) and "token outside the 15" rules cannot classify that outcome.
- The test asserts exactly one failure audit but never which key it is on, so it passes with the audit on the wrong key.

The handoff notes (b) "A 429 ... ends the job FAILED with the permanent `account_key_read_failed` token" and (c) "An MT5 window-fetch failure writes two failed audits" now describe behaviour the code no longer has. An orchestrator following them will misread the run.

Round 1 offered "skip the second audit" as one option. That option was under-specified: it should have said that the surviving audit must sit on the job's key.

**Fix:** Keep the single audit, but put it on the job's key. Give `_mt5_fetch_window` a keyword (for example `emit_audit: bool = True`), and pass `False` from `_crawl_account_key`. In the handler, when `_account_outcome` is a `DispatchResult` that is not DEFERRED, emit one `reconstruct_failed` on `api_key_id` with that result's `error_kind`, its message and `venue: "mt5"`. In the test, assert the audit's entity is `API_KEY_ID_1`. Then update the 09-SUMMARY handoff notes (b) and (c), and add a B'5 rule for a FAILED MT5 member outcome that has no refusal prefix.

### WR-04 (MEDIUM, operational; residual of round-1 WR-02 part 1): "unknown"-classified venue faults still become permanent refusals

**File:** `analytics-service/services/equity_reconstruction.py:4590-4601` (only `== "transient"` escapes, and everything else becomes `account_key_read_failed`). The same pattern is at `:4556`.

**Issue:** `classify_exception` returns `unknown` for every `ccxt.BaseError` leaf outside the network, auth and bad-request families. That includes `ExchangeError` and `InvalidNonce`, plus HTTP 5xx `HTTPException` and every plain Python exception. I checked the ccxt mapping in the worker's venv: bybit retCode `10016` maps to `ExchangeError` and `10002` maps to `InvalidNonce`. Its module table states "everything else -> unknown (retried by default)".

Round 1 named "an exchange 5xx" in WR-02. Body-level venue server faults reach the worker as `ExchangeError`, not as `ExchangeNotAvailable`: ccxt's bybit map sends retCode `10016` (internal server error) to `ExchangeError`, and a recv-window clock skew to `InvalidNonce`. Before AR-7 these went through the handler's generic arm as `unknown` and were retried. Through the account path they are still the permanent `account_key_read_failed`. So the round-1 finding is fixed only for HTTP-level 5xx (`ExchangeNotAvailable`, which is a `NetworkError`).

The existing test `test_a_failed_sibling_crawl_refuses_the_account_without_its_text` pins `ExchangeError` → permanent refusal, which is the behaviour round 1 objected to.

The impact is bounded: B'5 re-enqueues `account_key_read_failed` once. Outside the handoff, though, a single Bybit 10016 on any account now needs a manual re-enqueue.

**Fix:** Treat any kind other than `permanent` as non-final, so the test becomes `classify_exception(outcome)[0] != "permanent"`. Route it through the same scrubbed, phase-owned transient as WR-01, preserving the classified kind (`unknown` stays `unknown`). Keep `account_key_read_failed` for the `permanent` class and for non-`Exception` `BaseException`s. Re-point the ExchangeError test at a permanent class such as `ccxt.AuthenticationError`, and add an `ExchangeError` case to the transient parametrization that expects `error_kind == "unknown"`.
