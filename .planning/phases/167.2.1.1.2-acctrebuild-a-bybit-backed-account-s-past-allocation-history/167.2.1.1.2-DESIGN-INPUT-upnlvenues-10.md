Measured by the planner at HEAD 0da7c814e (cite by symbol, never by line):
- **Depth.**
  - `VENUE_HISTORY_DEPTH_MONTHS` holds binance 24, okx 3 and bybit 24, with no mt5 entry, so
    `history_depth_months_for_venue("mt5")` is None.
  - The handler today derives depth from the JOB key's venue only, and the RPC applies its one `p_depth_months` to every
    exchange_primary row.
  - So a forced job on an MT5 key of an MT5-plus-Bybit account would store NULL depth on rows that Bybit's 24 months
    limit.
- **MT5 rows.** `_mt5_fetch_window` returns `(rows, False, _mt5_telemetry())` with breakdown None and source
  "exchange_primary" on success. `_mt5_telemetry()` omits the anchor keys on purpose, and plan 07's
  `_merge_account_telemetry` reads them with defaults.
- **Markers.**
  - The marker ladder stamps only the job's key, through `_mark_api_key_history_reconstructed`, when
    `_reconstruct_outcome_completes_the_key` allows it; a stamp error fails the job transient.
  - An unmarked key is what the daily fan-out (and `_owed_reconstructs_for_zero_snapshot_book`) treats as owed. Its
    unforced reconstruct on a multi-key allocator persists first-writer-wins, which fills any day the rebuilt book lacks
    with that key's value alone.

Planner decisions:

**PD-S (depth of a summed row).** `def _account_history_depth_months(venues: Iterable[str]) -> int | None`: the minimum
of `history_depth_months_for_venue(v)` over the venues that return an int, None when none does. In the persist half, when
the account branch ran, `depth_months` comes from it over the lower-cased exchanges of `account_keys` outside
`_ACCOUNT_ZERO_CONTRIBUTION_VENUES`, instead of from the job key's venue. Every such venue was crawled, because
otherwise the job refused. The account path never reports hit_terminus (okx refuses), so the terminus override does not
apply to it.

**PD-O (every active key of a rebuilt account marked).** When the account branch ran and the completes-the-key rule
allows the stamp, stamp every key of `account_keys` whose `is_active` is True and whose lower-cased exchange is not in
`_ACCOUNT_ZERO_CONTRIBUTION_VENUES`, in id order (the job key among them), inside the existing marker try; the existing
except arm handles any failure.
- Inactive keys are not touched: no reconstruct can run for them (the preflight fails an inactive key permanently).
- Deribit keys are not touched: their history is counted as 0, not rebuilt, so a marker would claim a rebuild that never
  happened.
