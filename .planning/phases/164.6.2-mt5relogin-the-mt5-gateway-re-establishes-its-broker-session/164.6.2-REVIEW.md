# Phase 164.6.2 (MT5RELOGIN): Code Review Report

**Reviewed:** 2026-09-14

## Summary

The heal itself is carefully built: the single lease is taken by key before any client
exists, the client is constructed inside the `to_thread` body so the untimed
`rpyc.classic.connect` is actually bounded, the `-6` branch is correct, the non-`-6`
classification does not re-collapse the 164.1 distinction, `client.close()` is on a
`finally` and is structurally incapable of raising (`_teardown_transport` swallows
`Exception`), and the zombie-thread path is correctly fenced by the lazy `_epoch` bind
(a timed-out heal's in-flight credentialed `initialize` is refused by `_assert_live`
before it can touch the terminal under the next holder's lease). `main.lifespan`'s wiring
matches D-08. `pytest tests/test_mt5_relogin.py tests/test_mt5_concurrency.py
tests/test_mt5_client_contract.py` → **186 passed**.

Two defects are **reproduced, not hypothesised**, and both land on the two properties the
phase declared load-bearing.

1. **The by-value credential redaction does not cover the form `mt5linux` actually
   produces when the password contains an escapable character.** I ran the shipped
   `_redact_credential_values` against the shipped `mt5linux` kwargs-repr shape: the login
   and the server are redacted, and the **password survives verbatim** whenever it
   contains `\`, a quote pair, a tab or any control character. This is the exact
   disclosure class the phase exists to close, and the test corpus cannot fail on it.
2. **A typo in either of the two new tuning variables takes the whole analytics service
   down at startup.** `_MT5_RELOGIN_BUDGET_S` / `_MT5_RELOGIN_LEASE_WAIT_S` are
   `float(os.getenv(...))` at module scope, and `main.lifespan` imports the module
   unguarded before `yield` — which is precisely the uvicorn-abort outcome D-08's own
   comment says the design avoids.

I checked, and **cleared**, three things the brief flagged as likely: `asyncio.Handle`/
`functools.partial` reprs do **not** render the `to_thread` positional arguments (measured);
`parse_mt5_credentials` raises only `Mt5ValidationError` and never embeds a credential in its
message; `Mt5Client` stores no credential on the instance, so no default `repr` can leak one.
`Mt5Client.login` is byte-unchanged, the per-session heal is correctly absent, and the
`create_task` shape is correct — none of those are reported.

## Critical Issues

### CR-01: `_redact_credential_values` misses the password whenever `repr()` escapes it — the credential the phase exists to protect reaches the log verbatim

**Symbols:** `services/mt5_client.py::_redact_credential_values`, consumed by
`Mt5Client.initialize_with_credentials` (both failure arms) and logged by
`services/mt5_relogin.py::heal_mt5_terminal_session`'s top-level handler.

**Issue.** The loop redacts three *raw* literals:

```python
for literal in (str(login), password, server):
    if literal:
        safe = safe.replace(literal, "[REDACTED]")
```

`mt5linux` 0.1.9 builds the remote call as source text — `f'mt5.initialize(*{args},**{kwargs})'`
— so the kwargs reach the traceback as a **`repr()` of a dict**, not as a raw literal. Two
measured consequences:

* **`scrub_freeform_string` contributes nothing at all on that shape.** Its
  `SENSITIVE_KEY_VALUE` pattern requires `key` immediately followed by `\s*[:=]+`, and the
  repr form puts a closing quote between them (`'password': 'VALUE'`). Measured:
  `scrub_freeform_string("mt5.initialize(**{'login': …, 'password': 'VALUE', …})")` returns the
  input **unchanged**. The by-value pass is therefore the *sole* control on the production shape,
  not a second layer over a first.
* **`repr()` escapes, and the by-value pass matches only the unescaped form.** A password
  containing `\`, a tab/newline, or a quote that forces escaping is rendered with a different
  byte sequence, so `str.replace` never fires.

**Reproduction (run against the shipped function, `analytics-service/`):**

```python
from services.mt5_client import _redact_credential_values
pw = "pa\\ssw0rd"                      # a single backslash in the password
kwargs = {"login": LOGIN, "password": pw, "server": SERVER}
raw = "rpyc remote error while eval'ing mt5.initialize(**%r)" % (kwargs,)
print(_redact_credential_values(raw, LOGIN, pw, SERVER))
```

Observed output (login and server redacted, **password intact**):

```
rpyc remote error while eval'ing mt5.initialize(**{'login': [REDACTED],
  'password': 'pa\\ssw0rd', 'server': '[REDACTED]'})
```

Same result for `pa'ss"w0rd` and for a password containing a tab. The clean case
(`n0t-a-real-pw`) redacts correctly, which is why the suite is green.

**Failure scenario.** `MT5_PASSWORD` is a broker-generated password containing a backslash.
The terminal is at `-6` at boot. `initialize(login=…, password=…, server=…)` raises an rpyc
remote error → `_redact_credential_values` runs → the password survives → the typed
`Mt5ClientError` propagates to `heal_mt5_terminal_session`'s catch-all → `logger.warning("…
scrubbed=%s", scrub_freeform_string(str(exc)))`, which is shape-only and also misses it → the
plaintext broker password is written to the Railway log, and to any CI job that exercises the
path on a public Actions log. The escaping is trivially reversible.

**Fix.** Redact every *rendering* of each literal, not just the literal:

```python
def _credential_forms(literal: str) -> set[str]:
    forms = {literal}
    forms.add(repr(literal)[1:-1])          # the repr-escaped body mt5linux embeds
    forms.add(json.dumps(literal)[1:-1])    # the JSON-escaped body, for good measure
    return {f for f in forms if f}

safe = scrub_freeform_string(str(text))
for literal in (str(login), password, server):
    for form in _credential_forms(literal):
        safe = safe.replace(form, "[REDACTED]")
return str(safe)
```

**⛔ The gate cannot currently fail on this class — state it plainly.** Every credential
fixture in the corpus is escape-free: `test_mt5_client_contract.py`'s `_FAKE_PASSWORD =
"not-a-real-password-42"` and `test_mt5_relogin.py`'s `_FAKE_PASSWORD = "n0t-a-real-password"`
contain only `[A-Za-z0-9-]`. The redaction gate is therefore not vacuous in general (it does
bite on the clean shape) but it is **blind to the escaping class by construction of its
corpus**. The lever that would prove the fix: parametrize the signature-derived redaction
gate with at least one password containing `\`, one containing both `'` and `"`, and one
containing a tab, and assert each literal absent individually — the existing gate already
asserts per-literal, so only the corpus needs widening. Observe it RED before the fix.

### CR-02: the two new tuning variables are parsed at import time, and `main.lifespan` imports the module unguarded — a malformed value aborts uvicorn startup and takes the whole analytics service down

**Symbols:** `services/mt5_relogin.py::_MT5_RELOGIN_BUDGET_S`,
`services/mt5_relogin.py::_MT5_RELOGIN_LEASE_WAIT_S`, and the
`from services.mt5_relogin import heal_mt5_terminal_session` statement inside
`main.py::lifespan`.

**Issue.** Both constants are `float(os.getenv(...))` evaluated at module import. The import
sits in `lifespan`'s body, before `yield`, outside any `try`. A `ValueError` there propagates
out of the lifespan context manager and aborts uvicorn startup.

**Reproduction:**

```
$ MT5_RELOGIN_BUDGET_S="45s" python3 -c "import services.mt5_relogin"
IMPORT RAISED: ValueError could not convert string to float: '45s'
```

**Failure scenario.** An operator sets `MT5_RELOGIN_BUDGET_S=45s` (or `60 ` with a stray
character, or leaves it as an empty string) in the Railway variables while tuning the heal.
On the next deploy, `lifespan` raises before `yield`; FastAPI's startup fails; the API never
binds; `restartPolicyType ON_FAILURE x3` burns its three attempts and the analytics service
stays down — **the dispatch loop, the watchdog, the enqueue loop and `/health` all gone**, for
a best-effort heal of a gateway nobody needed. That is verbatim the outcome the D-08 comment
in `main.lifespan` says the `create_task` shape exists to prevent; the unguarded import
defeats it one line above the task.

The asymmetry is the tell: **every other misconfiguration in this module is handled by
log-once-and-return (D-02)** — absent `MT5_LOGIN`, an unparseable credential triple, a
non-numeric `MT5_GATEWAY_PORT` all skip the heal and leave the service up. Only the two
knobs that exist purely to tune the heal are fatal.

**Fix.** Read and coerce them per call, inside the guard, with the same posture as the
credential readers — a bad value logs once and falls back to the derived default:

```python
def _relogin_budget_s() -> float:
    return _env_float("MT5_RELOGIN_BUDGET_S", _MT5_REQUEST_TIMEOUT_S + 10.0)

def _relogin_lease_wait_s() -> float:
    return _env_float("MT5_RELOGIN_LEASE_WAIT_S", 2.0)

def _env_float(name: str, default: float) -> float:
    raw = (os.getenv(name) or "").strip()
    if not raw:
        return default
    try:
        value = float(raw)
    except ValueError:
        _log_configuration_fault_once(
            f"{name}_not_numeric",
            "mt5 boot heal: %s is set but is not a number; using the derived "
            "default. This is a SERVER misconfiguration.", name,
        )
        return default
    if not (0.0 < value < _MT5_RELOGIN_MAX_BUDGET_S):   # see WR-06
        _log_configuration_fault_once(...)
        return default
    return value
```

Per-call reading also restores the property `read_env_mt5_credentials`'s docstring already
argues for at length ("a go-live variable flip must take effect without a reimport") — these
two knobs are the only env reads in the module that violate it.

Note honestly: `mt5_client.py` and `mt5_concurrency.py` carry the same import-time
`float(os.getenv(...))` idiom, so this is a repo class rather than an invention of this phase.
What is new is that this phase adds two knobs on the *boot* path of a module whose entire
design premise is that it cannot take the service down.

## Warnings

### WR-01: `_heal_blocking` throws away the already-scrubbed failure detail, and reports every non-heal verdict at INFO

**Symbols:** `services/mt5_relogin.py::_heal_blocking` (the `not_healed:ipc_fault` return),
`heal_mt5_terminal_session` (`logger.info("mt5 boot heal: %s", verdict)`).

**Issue.** On the non-`-6` arm the function returns `f"not_healed:ipc_fault:code={err.code}"`
and discards `str(err)` — which is *already* scrubbed and safe to log, since
`Mt5ClientError.__init__` scrubs at construction. Two consequences:

* **Failure scenario (unactionable log).** The rpyc round-trip raises (connection reset mid-
  `initialize`, an rpyc timeout, a wedged pipe). `assert_session_authorized`'s broad arm
  converts it to `Mt5ClientError(0, <scrubbed transport text>)`. `_heal_blocking` sees
  `code == 0 != -6` and returns `not_healed:ipc_fault:code=0`. The operator's only artefact
  is the literal string `mt5 boot heal: not_healed:ipc_fault:code=0` — it names neither the
  transport class nor the reason, and `code=0` is the sentinel `_raise_last` also uses for
  "unknown" and "malformed `last_error` shape", so three distinct faults are indistinguishable.
* **Failure scenario (severity inversion).** The terminal is wedged behind a modal login
  dialog (`-10005`). The heal cannot help; the line `mt5 boot heal:
  not_healed:ipc_fault:code=-10005` is emitted at **INFO** — while a merely-unset
  `MT5_GATEWAY_PORT` is emitted at **WARNING** by `_log_configuration_fault_once`. A real
  gateway outage is logged one level *below* a config typo, in a milestone whose stated
  purpose is removing silent failure.

**Fix.** Carry the detail and split the level:

```python
except Mt5ClientError as err:
    if err.code != _MT5_NO_AUTHORIZED_ACCOUNT_CODE:
        return f"not_healed:ipc_fault:code={err.code}:{err}"   # already scrubbed
...
if verdict.startswith("not_healed"):
    logger.warning("mt5 boot heal: %s", verdict)
else:
    logger.info("mt5 boot heal: %s", verdict)
```

### WR-02: the `healed` verdict is not measured — nothing re-probes, so the operator-facing line asserts something the module's own doctrine says it cannot know

**Symbols:** `services/mt5_relogin.py::_heal_blocking` (`_VERDICT_HEALED`),
`Mt5Client.initialize_with_credentials`.

**Issue.** `_heal_blocking` returns `_VERDICT_HEALED` on the sole basis that
`initialize_with_credentials` did not raise. Both the module docstring and the method
docstring state, twice and emphatically, that "the oracle for 'is the session authorized' is
the NEXT probe, never this call's own boolean". **There is no next probe.** Nothing in this
module, in `main.lifespan`, or on the boot path re-runs `assert_session_authorized` after the
heal. The verdict token is therefore named after exactly the signal the design refuses to
trust, and it is the only thing an operator sees.

**Failure scenario.** The broker accepts the connection but rejects the account (rotated
password that was rotated again, a server rename). `initialize(login=…)` returns truthy —
which is the documented-as-untrustworthy case — `initialize_with_credentials` returns without
raising, and the log reads `mt5 boot heal: healed`. The gateway is still down; the operator
reads a green line and looks elsewhere. This reproduces the silent-UNKNOWN class the milestone
has spent four phases closing, at the one site built to close it.

**Fix.** The credential-free probe already exists, is cheap, is already inside this lease and
this budget, and takes one line:

```python
client.initialize_with_credentials(login, password, server)
try:
    client.assert_session_authorized()
except Mt5ClientError as err:
    return f"not_healed:still_unauthorized:code={err.code}"
return _VERDICT_HEALED
```

If the re-probe is rejected for cost or for the `[ASSUMED]` idempotence caveat, then rename
the token to something that does not claim success (`credential_sent`), so the log line and
the doctrine agree.

### WR-03: the whole-heal budget is derived from ONE round-trip but the path makes an unbounded connect plus up to THREE bounded round-trips

**Symbol:** `services/mt5_relogin.py::_MT5_RELOGIN_BUDGET_S`.

**Issue.** The budget is `MT5_REQUEST_TIMEOUT_S + 10.0` → **40 s** by default. The work it
must cover, from the module's own docstring ("the rpyc connect plus at most two bounded
round-trips"), is actually:

| step | ceiling |
|---|---|
| `rpyc.classic.connect` in `Mt5Client.__init__` | **no bound of its own** — this `wait_for` is the only one |
| `assert_session_authorized` → `initialize()` | 20 s MT5 IPC / 30 s rpyc |
| `_raise_last` → `last_error()` (on the `-6` path) | 30 s rpyc, and D-32's own EVIDENCE §1b records a failed attempt paying a *second* full 30 s here |
| `initialize_with_credentials` → `initialize(login=…)` | 20 s MT5 IPC / 30 s rpyc |

Worst case is ~80 s+ against a 40 s ceiling. The docstring undercounts by one round-trip:
`last_error()` is a full remote call and is on the `-6` path by construction.

**Failure scenario.** The terminal is genuinely at `-6` and the Wine bridge is slow (the
condition under which a heal is most needed). The probe takes its full 20 s IPC ceiling to
answer; `last_error()` takes several more seconds; the credentialed `initialize` starts around
t=28 s and needs its own 20 s. At t=40 s the `wait_for` fires **mid-`initialize`**. The
coroutine unwinds, the lease releases and bumps the generation, the zombie thread's
credentialed `initialize` is left in flight against the shared terminal, and the operator sees
`mt5 boot heal did not complete`. The heal that was working is abandoned, and whether the
session came up is now unknowable from the log.

**Fix.** Derive the budget from the number of round-trips the path actually makes rather than
from one, e.g. `float(os.getenv("MT5_RELOGIN_BUDGET_S", str(3 * _MT5_REQUEST_TIMEOUT_S + 10.0)))`,
and update the docstring's "at most two bounded round-trips" to three. Re-read the
`_MT5_RELOGIN_LEASE_WAIT_S` trade-off alongside it: a longer hold makes WR-06's starvation
window longer, which is an argument for re-probing cheaply (WR-02) rather than for a bigger
ceiling.

### WR-04: the structural never-raises gate does not forbid `finally:` / `else:` on the guard, and does not cover the handler body — two of the three escape routes the phase itself names

**Symbol:** `tests/test_mt5_relogin.py::test_the_heal_body_sits_entirely_inside_one_top_level_except_exception`.

**Issue.** The gate asserts: one non-docstring top-level statement, it is an `ast.Try`, it has
exactly one handler, that handler's type is the bare `Name` `Exception`, and the kill-switch
read is inside. It does **not** assert `body[0].finalbody == []` or `body[0].orelse == []`.

**Failure scenario.** A future author adds a cleanup `finally:` to the guard — a metric flush,
a `_LOGGED_CONFIGURATION_FAULTS` bookkeeping line, a `logger.info` that formats a value that
is `None` on the early-return paths. The `finally` body sits outside the handler, so a raise
there escapes `heal_mt5_terminal_session`, reaches `main.lifespan`'s `_crash_handler`, and
`SHUTDOWN.set()` stops the dispatch, watchdog and enqueue loops behind a green `/health` — the
exact silent analytics outage this test is the control for. **The test stays green.** Same for
an `else:` clause.

Separately, the gate says nothing about the handler body, which evaluates
`type(exc).__name__` and `scrub_freeform_string(str(exc))` *before* calling `logger.warning`,
with no guard of its own (see IN-01's sibling, IN-06).

**Fix.** Two lines, plus a mutation to prove they bite:

```python
assert body[0].finalbody == [], (
    "the guard grew a `finally:` — its body sits OUTSIDE the handler, so a raise "
    "there reaches _crash_handler and stops the worker loops behind a green /health"
)
assert body[0].orelse == [], "the guard grew an `else:` — same escape route"
```

Prove them: splice a `finally: raise RuntimeError()` into a source copy in a calibration test
(the file already uses that mutant idiom in
`test_the_criterion_1_predicate_reds_on_a_mutant_with_the_entry_excised`) and assert the
predicate reds.

### WR-05: `password` is not on `redact.DENYLIST_EXACT`, so Sentry's frame-`vars` scrub does not cover the three new frames that now hold the plaintext password

**Symbols:** `services/redact.py::DENYLIST_EXACT` / `_is_denylisted_key`,
`sentry_init.py::_redact_before_send`, and the new locals `password` in
`heal_mt5_terminal_session`, `_heal_blocking` and `Mt5Client.initialize_with_credentials`.

**Issue.** `sentry_sdk.init` here sets neither `include_local_variables=False` nor
`default_integrations=False`, so local variables are captured for every frame of an event and
`LoggingIntegration` turns any `logger.error(..., exc_info=…)` into an event.
`_redact_before_send` scrubs `…frames[*]['vars']` via `scrub_pii`, which redacts **denylisted
keys** — and measured, `_is_denylisted_key("password")` is **False**:

```
>>> scrub_pii({'login': …, 'password': 'n0t-a-real-pw', 'server': 'Broker-Demo-2'})
{'login': …, 'password': 'n0t-a-real-pw', 'server': 'Broker-Demo-2'}
```

`password` appears only in `_FREEFORM_KEY_ALTERNATES`, which is a *string* pattern for
`key=value` shapes, not a key denylist — so a `vars` dict whose key is `password` passes
through untouched.

**Failure scenario.** Any future `logger.error(..., exc_info=exc)` anywhere on this call stack —
`_crash_handler` already has exactly that shape, and the obvious remediation for WR-01 is to
raise the heal's failure log to ERROR — ships the plaintext MT5 password to Sentry as a frame
variable. This is the phase's own disclosure class arriving through the observability
pipeline instead of through the log line the phase fenced.

**Fix.** Both, and neither alone:
1. add `"password"` (and `"investor_password"`, which `Mt5Session` already uses as a field
   name) to `DENYLIST_EXACT` in `services/redact.py` — note the TS mirror
   `src/lib/admin/pii-scrub.ts` must move with it, per that module's byte-for-byte contract;
2. pass `include_local_variables=False` to `sentry_sdk.init`, since no frame variable in this
   service is worth a credential.

### WR-06: the two new knobs get no range validation — `0` silently disables the heal forever, `inf` holds the terminal lease indefinitely and starves the batch

**Symbols:** `_MT5_RELOGIN_BUDGET_S`, `_MT5_RELOGIN_LEASE_WAIT_S`.

**Issue.** Any value `float()` accepts is used verbatim as an `asyncio.wait_for` timeout.

**Failure scenario A (silent disable).** An operator sets `MT5_RELOGIN_BUDGET_S=0` while
trying to turn the heal off (there is no dedicated off switch other than `MT5_ENABLED`, which
also disables the rest of MT5). `wait_for(timeout=0)` cancels immediately; the heal logs
`mt5 boot heal did not complete` on every boot forever and never runs. The only signal is a
line that is indistinguishable from a transient gateway problem.

**Failure scenario B (terminal starvation).** `MT5_RELOGIN_BUDGET_S=inf` parses cleanly and
removes the bound entirely. The heal holds `mt5_terminal_lease` for as long as a wedged rpyc
connect lasts. Every batch caller — `run_derive_broker_dailies_job`,
`_fetch_mt5_account_balance`, `_fetch_mt5_account_rows` — acquires with `wait_s=None`, i.e.
**unbounded**, so the daily derive queues behind the boot heal until its own 15-minute
dispatch ceiling fires. A best-effort heal takes out the batch.

**Fix.** Validate on read (folded into CR-02's `_env_float`): reject non-finite values and
anything outside `0 < value <= <a declared ceiling>`, log once, fall back to the derived
default. The ceiling for the budget should be stated in the same place WR-03's derivation is.

## Info

### IN-01: `except Mt5ClientError: raise` in `initialize_with_credentials` is an unredacted pass-through

**Symbol:** `Mt5Client.initialize_with_credentials`, first except arm.

Its sibling `except Exception` arm redacts by value; this one re-raises untouched. It is
unreachable today — nothing inside `self._timed("initialize_credentialed", lambda: …)` can
construct an `Mt5ClientError`, since `_timed` only re-raises and `self._mt5.initialize` is the
mt5linux proxy. It is worth a comment saying *why* the asymmetry is safe (the same file
already comments the `Mt5SessionAbandoned` arm to that standard), because if a future
`_timed`/transport wrapper ever wraps a raw remote traceback into an `Mt5ClientError`, that
message reaches the log with the shape-scrub only — which CR-01 shows is a no-op on the
mt5linux form.

### IN-02: the `-6` detection silently declines whenever `last_error()` itself fails

**Symbols:** `Mt5Client._raise_last`, `_heal_blocking`'s code comparison.

`-6` is only ever observable through `last_error()`. If that round-trip raises, or returns a
falsy/malformed shape, `_raise_last` produces `code=0`, and `_heal_blocking` classifies the
fault as an IPC fault and heals nothing. The fail-closed direction is the right one (never
send a credential on a guess), but it means the single fault this module exists for is
undetectable whenever the second round-trip is the one that is broken — worth stating in the
`_heal_blocking` docstring's branch table, which currently reads as though `-6` is always
observable.

### IN-03: `_reset_relogin_log_throttle_for_tests` ships in production code

**Symbol:** `services/mt5_relogin.py::_reset_relogin_log_throttle_for_tests`.

A test-only mutator of module state living in a `services/` module. It is underscore-prefixed
and documented as test-only, and `mt5_client` already ships `_reset_mt5_epochs_for_tests`, so
this matches the house convention — recording it only so the convention stays a decision.

### IN-04: the heal refuses to queue behind real work, but real work queues behind the heal

**Symbols:** `_MT5_RELOGIN_LEASE_WAIT_S` (2 s, bounded) vs the three job call sites'
`wait_s=None` (unbounded).

The asymmetry is deliberate on one side and unexamined on the other. Concretely: the worker
boots, `dispatch_loop` claims a `derive_broker_dailies` job within a second or two, and the
heal has already taken the lease — the job then waits inside its own unbounded acquire for up
to the whole budget (40 s today, more if WR-03 is fixed by raising it). Harmless against a
15-minute dispatch ceiling, but it is the direction the docstring's argument ("a busy terminal
is a terminal somebody is already using") does not cover, and it gets worse in proportion to
any budget increase.

### IN-05: the lease-roster scanner is blind to `main.py`, and only a comment stands between that and a silent hole

**Symbol:** `tests/test_mt5_concurrency.py::_PRODUCTION_LEASE_SITES` /
`_production_python_files`.

The re-cut to six is correct and the new site is genuinely a `services/` module, so the `==`
assertion still means what it claims. The scope gap is documented honestly in the new comment.
It remains true that a `mt5_terminal_lease` taken in `main.py` (or in `main_worker.py`) would
never appear in the walk and the `==` would stay green over an incomplete roster. The cheap
close is to add `main.py` and `main_worker.py` to `_production_python_files`' glob and
re-measure the roster; the comment is a record of the hole, not a guard against it.

### IN-06: the never-raises handler body is itself unguarded

**Symbol:** `heal_mt5_terminal_session`'s `except Exception` body.

`type(exc).__name__` and `scrub_freeform_string(str(exc))` are evaluated as arguments, i.e.
before `logger.warning` is entered and outside any guard — stdlib `logging` swallows
formatting errors during emit, but not the evaluation of its arguments. `str(exc)` on an
exception whose `__str__` misbehaves, or a `RecursionError`/`MemoryError` arriving at an
already-exhausted stack, escapes the guard and reaches `_crash_handler`. The tail is narrow,
but the phase's declared standard is "structurally incapable", not "unlikely". A nested
`try/except BaseException: logger.warning("mt5 boot heal did not complete (detail
unavailable)")` around the handler body, or a `_safe_str` helper, would make the claim
structural. Pair it with the WR-04 gate extension so the property is asserted rather than
remembered.
