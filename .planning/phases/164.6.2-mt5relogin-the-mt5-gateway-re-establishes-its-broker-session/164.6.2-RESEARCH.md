## Summary

This phase is smaller than it looks in one way and much larger than it looks in another.

**Smaller:** nothing needs to be built from nothing. `Mt5Client.login(login, password, server)`
exists in `analytics-service/services/mt5_client.py`, carries the timeout ordering, the scrubbing
and the by-value credential redaction, and is already called from four production sites. The
credentials are already Railway-variable-shaped. `MT5_ENABLED=true` and the gateway host/port are
already set on the analytics service — measured this session.

**Larger:** the deliverable as written does not work, and two of the three proposed call sites are
structurally unsafe. Three findings, each measured at HEAD:

1. **`Mt5Client.login()` cannot heal a `-6`.** Its FIRST statement is a credential-less
   `initialize()`, and `initialize()` is precisely the call that returns `False` with `-6` when the
   terminal has no authorized account. The method then raises before it ever reaches the
   credentialed `login()`. Probed live against the production gateway today: the terminal is in the
   `-6` state right now, and `initialize()` returns `false`. The env credentials must therefore be
   passed to **`initialize()`**, which mt5linux 0.1.9 supports and MetaQuotes documents.
2. **An env login inside `_make_mt5_session` re-opens the defect `WIZFORM-ABANDON / D-36 AMENDED`
   exists to prevent.** `_make_mt5_session` runs in PREFLIGHT, outside and before the terminal
   lease. `Mt5Client._epoch` binds on FIRST TOUCH. A touch in preflight stamps the generation
   early, so any unrelated lease release in the window between preflight and the handler's own
   lease makes a legitimate derive read fail with `Mt5SessionAbandoned` — a false refusal that
   classifies transient and loops. The client's own docstring names `_make_mt5_session` as the
   reason the bind is lazy.
3. **Question THREE's hazard is REFUTED by a dated in-repo measurement — and the repo contradicts
   itself about it in code that shipped today.** `156-LIVE-ACCEPTANCE.md` records that on
   2026-08-13 the founder "unticked both auto-disable boxes" and that `trade_allowed` read true
   before a real `login()` and "still true after it, proving the fix survives a `login()` — the
   `Account=1` re-disable loop is broken." Meanwhile the `-6` remedy text shipped in
   `scripts/prod-prober/arms/mt5.mjs` on 2026-09-13 still tells the operator that a login re-clears
   those options. Both cannot be current. The state cannot be re-measured today because
   `terminal_info()` returns `null` while `-6` is in force.

**Primary recommendation:** keep D-00 and D-03. Replace D-01's call site with **worker startup
only, on its own throwaway `Mt5Client`, under the lease, behind `MT5_ENABLED`, wrapped so nothing
propagates** — and make the healing verb `initialize(login=…, password=…, server=…)` rather than
`Mt5Client.login()`. Leave `_make_mt5_session` untouched. That shape satisfies criterion 1's
"performs login from the env vars at its own startup", is the only shape that can actually clear a
`-6`, and costs the phase nothing except the words "AND whenever it opens an MT5 session" — which
the planner should route to the founder as an amendment, not silently drop.

## VERDICTS — the five research questions

### ⛔ VERDICT ZERO (unasked, and it outranks the rest): `Mt5Client.login()` is the wrong verb

`Mt5Client.login` opens with a credential-less `initialize()` and refuses on a falsy return, verbatim
from `analytics-service/services/mt5_client.py`, symbol `Mt5Client.login`
[VERIFIED: read at HEAD this session]:

```python
        inited = self._timed(
            "initialize",
            lambda: self._mt5.initialize(
                timeout=self._ipc_timeouts_ms["initialize"]
            ),
        )
    …
    if not inited:
        self._raise_last()
```

`_raise_last` reads `last_error()` and raises `Mt5ClientError(code, text)`.

Probed **live against the production gateway, 2026-09-13**, with the repo's own read-only
diagnostic `scripts/mt5-diag.sh` (it calls `initialize()` + `terminal_info()` and never `login()`),
output verbatim [VERIFIED: live probe, this session]:

```
PROBE {"initialize": false, "last_error": [-6, "Terminal: Authorization failed"], "terminal_info": null}
```

`-6` is `RES_E_AUTH_FAILED` [CITED: mql5.com/en/docs/python_metatrader5/mt5lasterror_py].

So in the exact state this phase exists to heal, `Mt5Client.login(env_login, env_pw, env_server)`
raises `Mt5ClientError(-6)` from the `initialize()` arm and **never attempts the credentialed
login**. Implemented literally, criterion 1's deliverable is a no-op against its own target fault.

**What does work.** MetaQuotes documents three call forms for `initialize()`, one of which carries
the account [CITED: mql5.com/en/docs/python_metatrader5/mt5initialize_py]:

> "login=LOGIN — [in] Trading account number. Optional named parameter. If not specified, the last
> trading account is used."

That "last trading account is used" is the mechanism of the `-6`: bare `initialize()` tries to
authorize the terminal's saved account, and that is what the broker is refusing.

mt5linux 0.1.9 passes kwargs straight through. From the pinned wheel
(`mt5linux-0.1.9-py3-none-any.whl`, `mt5linux/__init__.py`, methods `MetaTrader5.initialize` and
`MetaTrader5.login`), verbatim [VERIFIED: downloaded and read from PyPI this session]:

```python
        code=f'mt5.initialize(*{args},**{kwargs})'
        return self.__conn.eval(code)
```
```python
        code=f'mt5.login(*{args},**{kwargs})'
        return self.__conn.eval(code)
```

Two consequences, both load-bearing:

- `initialize(login=…, password=…, server=…, timeout=…)` reaches the real MetaTrader5 module
  unchanged. This is the verb that can clear a `-6`.
- ⛔ **The f-string is the T-134-01 credential-disclosure surface, and it applies to `initialize`
  the moment a password is passed to it.** Today `Mt5Client.login`'s `initialize` except-arm scrubs
  but does **not** redact by value; only the `login` arm runs the
  `for literal in (str(login), password, server)` replacement loop. Moving credentials into
  `initialize()` without moving that loop is a straight regression of a shipped security control.

### ONE — worker startup ordering. VERDICT: nothing runs at boot today; a boot login CAN take the worker down; `MT5_ENABLED` does NOT gate the transport connect.

**(a) What the worker does today when the gateway is down.**

Production does **not** run `main_worker.main()`. `analytics-service/main_worker.py`'s own module
header says so verbatim [VERIFIED: read at HEAD]: *"PRODUCTION DOES NOT RUN THIS ENTRYPOINT. There
is no separate worker service and has not been since April 2026; the dispatch/watchdog/enqueue
loops were merged into the FastAPI process."* The worker's startup is therefore
`analytics-service/main.py`'s `lifespan`. **`main.py` contains no MT5 reference of any kind** except
one unrelated logging comment — grepped at HEAD. ⭐ **There is no boot-time MT5 path to modify;
this is entirely new surface.**

Down the job path, `job_worker._make_mt5_session` constructs `Mt5Client(host, int(port_raw))`, and
`Mt5Client.__init__` performs a **blocking connect**: `self._mt5 = connect(host=host, port=port,
timeout=request_timeout_s)`. `_default_connect` builds `mt5linux.MetaTrader5(host, port)`, whose
constructor is, verbatim from the pinned wheel [VERIFIED]:

```python
        self.__conn = rpyc.classic.connect(host,port)
        self.__conn.execute('import MetaTrader5 as mt5')
```

⚠️ **`rpyc.classic.connect(host, port)` takes no timeout.** `MT5_REQUEST_TIMEOUT_S` is applied
*after* the socket is up, by writing `sync_request_timeout` onto the private connection — the
`_default_connect` docstring says exactly that, and 0.1.9's ctor confirms it. So the TCP/DNS
connect is bounded only by the OS. A refused port fails fast; a blackholed mesh address does not.

`_make_exchange_client` is called from `_exchange_preflight` with **no try/except** around it, so a
connect failure propagates into the handler, is classified by `classify_exception`, and fails
**that job**. It does not touch the worker. [VERIFIED: read `_exchange_preflight` and
`_make_exchange_client` at HEAD.]

**(b) Does `MT5_ENABLED` gate the path?** Partially, and the repo already records the gap.
`services/closed_sets.py`, symbol `mt5_enabled_server`, verbatim [VERIFIED]:

```python
    return (os.getenv("MT5_ENABLED") or "").strip().lower() == "true"
```

Fail-closed, read per call. But the gate sits **after** the transport is opened. `job_worker`'s own
WR-08 note says so verbatim [VERIFIED]: *"`_exchange_preflight` has ALREADY decrypted the
credentials and built the session (`_make_exchange_client` → `_make_mt5_session` → `Mt5Client`,
whose `__init__` opens the RPyC transport) by the time control reaches here. What this gate stops
is every terminal READ — login / account_info / history_deals_get — not the transport connect."*
`TODOS.md` carries the same as **WR-08 residual**.

⇒ A new startup login **must consult `mt5_enabled_server()` BEFORE constructing the client**, not
after. That is a one-line requirement and it is the difference between honouring the kill switch
and re-opening WR-08 at a second site.

**(c) Could a failed boot login take the worker down? YES — and hard.**

`lifespan` is a plain `@asynccontextmanager`. An exception raised before its `yield` aborts
uvicorn's startup and the process exits. `analytics-service/railway.toml`, verbatim [VERIFIED]:

```toml
[deploy]
healthcheckPath = "/health"
healthcheckTimeout = 120
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 3
```

So an unguarded boot login that raises three times leaves the **entire analytics service down** —
API, dispatch loop, watchdog, daily enqueue — for a gateway nobody needed. That is precisely the
outcome D-02 forbids, and today's code does not prevent it because today's code does nothing at
boot.

⚠️ A second, subtler boot hazard that is NOT covered by a try/except: the connect is **synchronous
and unbounded** (see (a)). Called directly in `lifespan`, it blocks the event loop, so `/health`
cannot answer while it hangs — against a 120 s `healthcheckTimeout`. **The boot login must run off
the loop** (`asyncio.to_thread`) **and under an `asyncio.wait_for` of its own**, or it converts a
gateway outage into an analytics outage by a second route.

**Railway boot ordering.** Railway's CLI exposes no service-ordering primitive (`railway --help`
read at HEAD: no `depends-on`/ordering verb). [ASSUMED] that Railway offers no start-order
guarantee between sibling services. ⭐ **It does not matter, and the planner should not spend a
checkpoint on it:** even a guaranteed order would not help, because the gateway can restart at any
later moment. The design must be order-independent. Treat "the gateway is not up at boot" as the
NORMAL case, not the exception — log once, continue, and let the next heal attempt cover it.

### TWO — the `initialize()` idempotence assumption. VERDICT: the exposure is real but SMALL, and it is now better understood than the docstring states.

The docstring's `[ASSUMED]` marking is correct and the official documentation confirms the silence.
Asked directly of the primary source [CITED: mql5.com/en/docs/python_metatrader5/mt5initialize_py]:
the page documents `initialize()` as *"Establish a connection with the MetaTrader 5 terminal"* and
*"If required, the MetaTrader 5 terminal is launched to establish connection"*, and **says nothing
about calling it repeatedly on an already-connected session**. Same for `login()`
[CITED: mql5.com/en/docs/python_metatrader5/mt5login_py]: *"True in case of a successful connection
to the trade account, otherwise – False"*, silent on re-authentication.

⚠️ Per the absent-evidence rule, that silence is **not** evidence either way. It is why the claim
stays `[ASSUMED]` and cannot be promoted by a documentation read.

**What actually breaks if it is false.** Four scenarios, ordered by blast radius:

| If `initialize()` on an attached terminal… | Consequence today | Consequence with this phase |
|---|---|---|
| returns `False` | every existing `Mt5Client.login()` already raises — this is ALREADY the live failure mode (`-6`) | identical; the phase does not widen it |
| detaches/reattaches the IPC pipe | a concurrent holder's in-flight read could fail | ⚠️ slightly worse: one more attach per heal attempt. Mitigated entirely by taking the LEASE |
| re-authorizes the saved account | harmless | ⭐ this is the behaviour the phase WANTS |
| counts as an account change | see question THREE | see question THREE |

⭐ **The honest reframing: this phase makes the assumption LESS load-bearing, not more.** The
recommended shape passes credentials to `initialize()`, so the heal path no longer depends on a
bare `initialize()` doing something useful when already attached — it depends on
`initialize(login=…)` doing what MetaQuotes documents it does. The `[ASSUMED]` idempotence remains
load-bearing only for the four EXISTING per-account call sites, which this phase does not touch
(D-03).

**Cheap defensive shape, and it is genuinely cheap:** attempt the heal, and treat *any* outcome —
`True`, `False`, or a raised `Mt5ClientError` — as "logged, continue". Never assert on the return.
The oracle for "did it work" is the next `terminal_info()`/prober tick, never this call's boolean.
Combined with the lease and the throwaway client, a false idempotence assumption degrades the heal
to a no-op; it cannot corrupt a concurrent read.

⛔ Phase 155 (MT5-VERIFY) still owns the assumption. This document reports exposure and does not
propose to fix it.

### FOUR — cheap "already logged in" detection. VERDICT: yes, and it is already in the tree — but the answer changes what you would use it FOR.

Given finding ZERO, the question is no longer "avoid a redundant login" but "avoid a pointless
heal". Both are answered by the same read.

| Probe | What it costs | What it tells you | Already used by |
|---|---|---|---|
| `initialize()` return + `last_error()` | one round-trip, no credential | `False` + `-6` ⇒ **no account is authorized**. This IS the detector. | `scripts/mt5-diag.sh`, `prod-prober/arms/mt5.mjs`, `Mt5Client.login`'s own first statement |
| `Mt5Client.terminal_info()` | one round-trip, no credential | `None` while `-6`; otherwise `connected` / `trade_allowed` | `mt5_probe.read_terminal`, both validate paths |
| `Mt5Client.account_info()` | one round-trip | the account the terminal is ON (`info["login"]`) | the MT5CONC-02 bracket in `job_worker` and `allocator_positions` |

**What `mt5_probe` reads.** `mt5_probe.run_probe` calls `client.login(...)`, `account_info()` and
`order_check()`; `mt5_probe.read_terminal` calls `terminal_info()`. [VERIFIED: read at HEAD, and
independently pinned by `tests/test_mt5_probe_parity_roster.py`'s `PROBE_VERB_UNITS_IN_HOME_FLOOR`,
whose comment records *"exactly two units in `services/mt5_probe.py` call a probe verb —
`read_terminal` (`terminal_info`) and `run_probe` (`login`, `account_info`, `order_check`)"*.]

**The cheapest correct gate, and it needs no new verb:**

```
bare initialize()  ->  truthy   =>  a session exists. STOP. Do not heal.
                   ->  falsy    =>  read last_error(); -6 => heal with credentials.
                                    -10003/-10005 => an IPC fault, NOT ours to heal — log and stop.
```

⭐ This is worth more than avoiding a redundant login: it keeps the heal **narrow**. Healing on a
`-10005` (a modal dialog blocking IPC, per the prober arm's header) would be the wrong remedy
applied to the wrong fault, which is the exact confusion Phase 164.1 built the `-10004`/`-10005`
split to prevent.

⚠️ `initialize` and `login` are the **only two** calls carrying an explicit per-call ms ceiling —
`MT5_IPC_TIMEOUTS_MS` holds exactly `{"initialize": …, "login": …}`, defaults `20000` each against
`MT5_REQUEST_TIMEOUT_S` default `"30"`. `account_info()` and `terminal_info()` ride the rpyc
`sync_request_timeout` only. Prefer `initialize()` + `last_error()` as the detector: it is the one
probe that is both credential-free AND explicitly bounded.

### Pattern 1 — the heal, as a shape

**What:** one function, one throwaway client, one lease, credential-free detection then credentialed
heal, every outcome swallowed.
**When:** at `lifespan` startup, and at whatever additional trigger the founder amendment allows.

```python
# Source: composed from verbs verified in this repo at HEAD. NOT copied from any
# external example. Illustrative shape for the planner, not a finished task action.

async def heal_mt5_terminal_session() -> None:
    """Re-establish the gateway terminal's broker session from the env triple.

    ⛔ NEVER raises. NEVER blocks the event loop. NEVER fails a boot (D-02).
    """
    # 1. The kill switch FIRST — before any construction (WR-08's residual is a
    #    gate consulted AFTER the transport opened; do not repeat it here).
    if not mt5_enabled_server():
        logger.info("mt5.heal: skipped — MT5_ENABLED is not true")
        return

    # 2. The env triple, parsed through the ONE fail-closed offline seam.
    #    Absent => log ONCE and continue (D-02). Never a raise, never a warning storm.
    raw = (os.getenv("MT5_LOGIN"), os.getenv("MT5_PASSWORD"), os.getenv("MT5_SERVER"))
    if not all(raw):
        logger.info("mt5.heal: skipped — MT5_LOGIN/MT5_PASSWORD/MT5_SERVER not all set")
        return
    try:
        login, password, server = parse_mt5_credentials(*raw)
    except Exception:                      # scrubbed by the seam; never echo raw
        logger.warning("mt5.heal: skipped — the env credential triple did not parse")
        return

    host, port_raw = os.getenv("MT5_GATEWAY_HOST"), os.getenv("MT5_GATEWAY_PORT")
    if not host or not port_raw:
        logger.info("mt5.heal: skipped — gateway host/port unset")
        return

    # 3. Off the loop AND bounded. The rpyc connect carries NO timeout of its own
    #    (mt5linux 0.1.9 ctor), so this wait_for is the only ceiling there is.
    async with mt5_terminal_lease(f"{host}:{port_raw}"):
        try:
            await asyncio.wait_for(
                asyncio.to_thread(_heal_blocking, host, int(port_raw),
                                  login, password, server),
                timeout=_MT5_HEAL_BUDGET_S,
            )
        except Exception:                  # incl. TimeoutError
            logger.warning("mt5.heal: did not complete; continuing (D-02)")
```

⚠️ The lease key must be derived the same way `Mt5Client.terminal_key` derives it. Read that
property rather than re-spelling `host:port` — a second spelling is the "two registries" class
`mt5_concurrency`'s module header forbids.

### Pattern 2 — detect, then heal, then stop

```python
def _heal_blocking(host, port, login, password, server) -> None:
    client = Mt5Client(host, port)         # fresh, throwaway, ONE lease only
    try:
        # DETECT: credential-free, explicitly ms-bounded, cannot leak a secret.
        if client.is_session_live():       # bare initialize() truthy?  -> nothing to do
            logger.info("mt5.heal: a session is already authorized; no action")
            return
        # HEAL: the ONLY form that can clear a -6.
        client.initialize_with_credentials(login, password, server)
        logger.info("mt5.heal: re-established the terminal's broker session")
    finally:
        client.close()                     # D-41-exempt; never leave the socket
```

### Anti-patterns to avoid

- **⛔ A terminal touch inside `_make_mt5_session`.** Pitfall 2. The client's own `_assert_live`
  docstring names this function as the reason the epoch bind is lazy.
- **⛔ Re-using one `Mt5Client` across two lease acquisitions.** Refused on the second with
  `Mt5SessionAbandoned`, classified transient, so it loops. Pitfall 3.
- **⛔ Passing the password to `initialize()` without moving the by-value redaction loop with it.**
  Pitfall 1.
- **⛔ Asserting on the heal's return value.** Question TWO. The oracle is the next probe.
- **⛔ Healing on a `-10003`/`-10005`.** Wrong remedy, wrong fault; re-collapses the distinction
  Phase 164.1 built.
- **⛔ Making the prober or `mt5-diag.sh` log in.** D-06 rejected it; 164.8.3 criterion 5 fences
  `mt5-diag.sh` read-only.

## Common Pitfalls

### Pitfall 1 — moving credentials into `initialize()` silently drops a shipped security control

**What goes wrong:** `Mt5Client.login`'s `initialize` except-arm is
`raise Mt5ClientError(0, scrub_freeform_string(str(exc))) from None` — shape-based scrubbing only.
The by-value redaction (`for literal in (str(login), password, server): safe = safe.replace(literal, "[REDACTED]")`)
exists **only** in the `login` arm. [VERIFIED: read `Mt5Client.login` at HEAD.]
**Why:** today `initialize()` carries no credentials, so by-value redaction there was pointless —
the docstring even says *"initialize() carries no credentials, but its transport text is scrubbed on
the same fail-loud path for safety."* The moment credentials are passed, that sentence is false.
**How to avoid:** the credentialed-initialize path must run the by-value loop. Prefer a shared
private helper over a copy.
**Warning signs:** a new `initialize(` call with a `password=` kwarg and no `[REDACTED]` loop in its
except-arm.

### Pitfall 2 — ⛔ an env login inside `_make_mt5_session` re-opens WIZFORM-ABANDON / D-36

**What goes wrong:** `Mt5Client._assert_live` binds the terminal generation on FIRST TOUCH, not at
construction. `_make_mt5_session` runs in preflight, **outside and before** the lease. A touch there
stamps the generation early; an unrelated lease release before the handler's own acquisition then
refuses a legitimate read.
**Why:** the client's own docstring states the mechanism verbatim [VERIFIED]:

> `⭐ LAZY BIND, and it is load-bearing. job_worker._make_mt5_session builds its client in PREFLIGHT — outside and before the lease — so a generation stamped at construction would go stale merely because an UNRELATED lease released in that window, and a legitimate derive read would be refused.`

**It is reachable, not theoretical.** The validate path (`routers/exchange.py::_validate_mt5_key_probe`)
takes the same lease **in the same process** — the worker loops are merged into the FastAPI process.
A user connecting an MT5 key between a job's preflight and its lease is enough.
**Consequence:** `Mt5SessionAbandoned`, classified transient (D-40) — "a permanent-looking retry
loop, on a path that plainly HELD the lease", which `test_mt5_concurrency.py` calls *"the most
confusing failure this subsystem can produce"*.
**How to avoid:** ⛔ do not touch the terminal in `_make_mt5_session`. Heal from a site that owns
its own client and its own single lease.

### Pitfall 3 — the lease roster is a HAND-TYPED frozenset asserted with `==`

**What goes wrong:** `tests/test_mt5_concurrency.py::test_no_production_function_holds_two_terminal_leases`
asserts `set(sites) == _PRODUCTION_LEASE_SITES`. A new `async with mt5_terminal_lease(...)` anywhere
under `services/` or `routers/` **reds this test** until the literal is re-cut in the same diff.
Verbatim [VERIFIED: read at HEAD]:

```python
_PRODUCTION_LEASE_SITES: frozenset[tuple[str, str]] = frozenset(
    {
        ("services/allocator_positions.py", "_fetch_mt5_account_rows"),
        ("services/ingestion/mt5.py", "validate"),
        ("services/job_worker.py", "_fetch_mt5_account_balance"),
        ("services/job_worker.py", "run_derive_broker_dailies_job"),
        ("routers/exchange.py", "_validate_mt5_key_probe"),
    }
)
```

⚠️ **And a gap worth naming:** the walk is `_production_python_files()`, which globs `services/` and
`routers/` only. `analytics-service/main.py` is in NEITHER. A lease taken in `lifespan` is invisible
to this roster — so if the heal lands in `main.py`, the pin does not cover it and the planner should
say so in the plan rather than discover it in review. (Putting the heal function in `services/` and
calling it from `main.py` keeps it inside the roster's scope, which is the better shape.)
**How to avoid:** budget a task for re-cutting the roster, and read the test's own failure message —
it prescribes the check ("does the new site touch an `Mt5Client` that was ALREADY touched under a
different lease?").

### Pitfall 4 — a boot-time heal that raises takes the whole analytics service down

**What goes wrong:** an exception before `lifespan`'s `yield` aborts uvicorn startup; `railway.toml`
carries `restartPolicyType = "ON_FAILURE"` / `restartPolicyMaxRetries = 3`, so three failures leave
the service down.
**How to avoid:** a bare `except Exception` around the whole heal, plus the `mt5_enabled_server()`
gate and the absent-vars early return. D-02 is not a nicety here; it is the difference between an
MT5 outage and an analytics outage.
**Warning signs:** any `await` in the new startup path that is not inside a `try`.

### Pitfall 5 — a boot-time heal that BLOCKS takes the service down by a second route

**What goes wrong:** `rpyc.classic.connect(host, port)` has no timeout — verified verbatim from the
0.1.9 wheel. `MT5_REQUEST_TIMEOUT_S` is applied only *after* the socket is up. Called synchronously
in `lifespan`, an unreachable gateway blocks the event loop against `healthcheckTimeout = 120`.
**How to avoid:** `asyncio.to_thread` + `asyncio.wait_for`. A try/except alone does NOT fix this.

### Pitfall 6 — `-6` makes the terminal unreadable, so "it did not work" and "it is not measurable" look identical

**What goes wrong:** the live probe this session returned `"terminal_info": null` alongside the `-6`.
Every capability flag is unreadable while a session is missing.
**How to avoid:** sequence the D-06 measurement so the `trade_allowed` readings are taken **after**
the first successful heal, never before. A `null` before the heal is not a measurement of anything.

### Pitfall 7 — `MT5_ENABLED` is three different variables

**What goes wrong:** `TODOS.md` records the trap: the worker's `MT5_ENABLED`, Vercel's server-side
`MT5_ENABLED`, and Vercel's build-time-inlined `NEXT_PUBLIC_MT5_ENABLED` are distinct. Only the
first is this phase's.
**Measured this session:** on the `quantalyze-analytics` production service,
`MT5_ENABLED=true`, `MT5_GATEWAY_HOST=mt5-gateway.railway.internal`, `MT5_GATEWAY_PORT=8001`; no
`MT5_LOGIN` / `MT5_SERVER`. [VERIFIED: `railway variables --service quantalyze-analytics
--environment production --kv`, filtered to non-secret keys only.]

### Pitfall 8 — a new `.login(` under `services/` may trip a roster (this one is a false alarm, stated so it is not re-investigated)

`tests/test_mt5_probe_parity_roster.py` scans **only** `routers/exchange.py`,
`services/ingestion/mt5.py` and `services/mt5_probe.py` (its `UNIT_FLOORS` keys). `job_worker.py`
and a new heal module are outside it. [VERIFIED: read `UNIT_FLOORS` and `_ROOT` at HEAD.] ⚠️ But
`test_mt5_abandon_roster.py` pins the *guarded-method* count at seven on `Mt5Client` itself — a NEW
public method on `Mt5Client` (e.g. `initialize_with_credentials`) must carry the `_assert_live`
fence or re-cut that floor deliberately.

## Open Questions

1. **⛔ Does criterion 1's "whenever it opens an MT5 session" survive Pitfall 2?**
   - What we know: `_make_mt5_session` is the only "session open" seam, and a terminal touch there
     re-opens D-36. Startup-only satisfies the criterion's other half exactly.
   - What is unclear: whether the founder accepts narrowing criterion 1, or wants the per-session
     half relocated INSIDE the lease (technically possible, but it adds an account change per read
     and directly pressures D-03).
   - **Recommendation:** plan startup-only; raise the narrowing as an explicit ROADMAP amendment via
     `/gsd-phase --edit` with this document's Pitfall 2 as the evidence. ⛔ Do not silently drop the
     clause and do not silently implement the unsafe version.

2. **⛔ UNVERIFIED — does a same-account login clear `[Experts] Enabled` today?**
   - What we know: MetaQuotes documents the trigger as "when the account is changed"; the repo says
     yes in three shipped places and no in one dated acceptance record; `terminal_info()` is `null`
     while `-6` is in force so it cannot be read now.
   - **What would settle it:** `scripts/mt5-diag.sh` before and after the first real `login()`
     post-heal. Free, read-only, no VNC, no credential. Fold into D-06's procedure.

3. **What closes the window after a gateway restart, if the analytics service does not restart?**
   - What we know: nothing in the current design restarts analytics when the gateway restarts.
   - **Recommendation:** treat "unbounded until the next analytics deploy" as the LIKELY measured
     answer and pre-write the D-06 finding accordingly. That outcome is what the keepalive follow-up
     phase exists for, and D-06 explicitly refuses to design it before the measurement.

4. **Is the env account the same account as the only connected MT5 key?**
   - What we know: the gateway carries one `Vantage_investor_password_*` variable; the MT5CONC-02
     bracket asserts strict equality between `account_info()["login"]` and the key's login.
   - Why it matters: if they differ, a heal that leaves the terminal on the env account and a job
     that logs into a user account are two account changes per cycle rather than one.
   - **Recommendation:** the planner need not resolve this — the bracket already fails loud on a
     mismatch and the heal runs under the lease. Record it as an observation for D-06.

### Known threat patterns for this stack

| Pattern | STRIDE | Standard mitigation |
|---|---|---|
| Broker password echoed in an rpyc remote traceback (T-134-01) | Information disclosure | Scrub + **by-value** redaction on EVERY arm that has credentials in scope. ⛔ Pitfall 1. |
| A production filesystem path or account number reaching a PUBLIC Actions log | Information disclosure | The prober arm already projects only `connected`/`trade_allowed`. ⛔ Never widen it, and never paste a `mt5-diag.sh` `path`/`build` field into `.planning/`. |
| Env credentials placed on the GATEWAY instead of the worker | Elevation / expanded blast radius | ⛔ D-00 rejected this explicitly. They go on **quantalyze-analytics**. |
| Unauthenticated RPyC = arbitrary remote code | Elevation of privilege | Private mesh only. Unchanged by this phase; re-state it in the plan so nobody "simplifies" the heal by exposing a port. |
| A heal that mutates from an instrument (prober / `mt5-diag.sh`) | Tampering | ⛔ D-06 + criterion 5 + 164.8.3 criterion 5 all forbid it. |
