## Decisions Made

- **No shared redaction helper was extracted out of `Mt5Client.login` (the plan's `<the_one_decision_this_plan_takes>`, honoured).** `_redact_credential_values` is a NEW module function used only by the new verb; `login`'s own copy of the loop is byte-unchanged. The new helper exists because the new verb needs the loop on TWO arms and writing it twice inside one method would be silly — it is not a refactor of anything shipped.
- **The falsy arm unwraps the typed error's own prefix before re-wrapping** (`str(err).removeprefix(f"MT5 client error (code={err.code}): ")`) so the message reads once rather than twice. `removeprefix` degrades to a no-op if that format ever changes — a doubled prefix, still fully redacted. The redaction never depends on a string shape.
- **The falsy arm catches `Mt5ClientError` and NOT `Exception`, and the transport arm carries an explicit `except Mt5SessionAbandoned: raise` ahead of its broad arm.** `_raise_last` opens with its own `_assert_live`, so a session-abandoned refusal can genuinely arise on that line and must escape untouched — D-42's whole point is that an our-infrastructure refusal can never be re-classified as a user credential fault. The narrow arms make that structural rather than remembered.
- **Stage names are distinct from `login`'s** (`session_authorized`, `initialize_credentialed`), so the boot heal's round-trips do not pollute the `initialize` duration population Phase 155 reads.

### 2. [Rule 1 — the plan's driver instruction does not hold at HEAD] the scenario key is derived from the credential-carrying CALL, not driven "both at once"

- **Found during:** Task 2.
- **Issue:** The plan's `<action>` (d) says to *"drive both scenario keys at once in a single scenario dict so whichever attribute the method reaches, it raises"*. **Measured at HEAD, that would have redded shipped code.** `Mt5Client.login` reaches the transport TWICE — a credential-LESS `initialize()` first, then the credentialed `login()`. Setting `initialize_raises` too makes `login()` fail on its FIRST call, whose arm is shape-scrubbed only and correctly so (no credential is in scope there). The gate would then have reported a disclosure on unchanged, shipped `login` — which is exactly the outcome the plan's own ⛔ forbids two paragraphs later (*"asserting by-value redaction there would red on shipped, unchanged code and the remedy would be a `login()` edit D-07 forbids"*). The instruction contradicts its own constraint because it assumed one transport attribute per method.
- **Fix:** The scenario key is derived one level deeper and is MORE derived, not less: `_credential_carrying_transport_calls` finds the `self._mt5.<name>(...)` call inside the method that is handed one of the credential PARAMETERS, and the key is `f"{name}_raises"`. Nothing is hand-mapped; a third credentialed verb is still fenced automatically. The gate additionally asserts exactly one such call per drivable method and says so by name if a future verb has two.
- **Verification:** the derivation prints `login -> ('login',)` and `initialize_with_credentials -> ('initialize',)` against the real source; the classifier self-test pins the `login` shape on synthetic source precisely so that the SECOND (credential-carrying) call is the one selected; lever 1 confirmed the gate still bites on the new verb while leaving `[login]` green.
- **Committed in:** `f7558d36`.

### 3. [Rule 2 — missing coverage the change itself created] two new stages added to the D-42 roster

- **Found during:** Task 1.
- **Issue:** `test_session_abandoned_message_carries_no_classifier_token` claims in its own docstring to hold *"for EVERY stage name the fence can carry"*. Two new fenced stages would have left that sentence false.
- **Fix:** Added `session_authorized` and `initialize_credentialed` to the parametrization. Both are near-misses by construction (`auth`, `credential`), which is the shape D-42 exists to keep out of the message. The existing entries are untouched.
- **Committed in:** `e89e04d1`.
