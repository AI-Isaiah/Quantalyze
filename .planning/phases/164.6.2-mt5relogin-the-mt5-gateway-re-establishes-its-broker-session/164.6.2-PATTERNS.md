## Pattern Assignments

### 1. The env-credential read — `MT5_LOGIN` / `MT5_PASSWORD` / `MT5_SERVER`

**Analog A (the idiom to copy): `services.closed_sets.mt5_enabled_server`.**
A tiny module-level function that reads `os.getenv` **PER CALL, never a module-load constant**, with
a `.strip().lower()` normalisation and a fail-CLOSED default. Its own module comment states the
reason explicitly: read per call so a go-live env change or a test `monkeypatch.setenv` takes effect
without a reimport. Copy: the per-call read, the single-purpose helper, the docstring naming the
fail-closed default.

**Analog B (how "configured vs not" is represented): `main._platform_secret_is_set` and
`main._degraded_platform_secrets`.** Note the load-bearing lesson in `_platform_secret_is_set`'s
docstring — it reads `SERVICE_KEY` from the MODULE GLOBAL, **not** `os.getenv`, precisely because
the gate that consumes it captured the value at import; reading `os.getenv` for the report while the
gate reads a stale global is the "silent disagreement" class (C-11). **Copy the principle, not the
global:** whatever reports "MT5 credentials configured" must read through the SAME accessor the
login path calls. Since Analog A's idiom is a per-call read, the natural shape is one accessor
returning a triple-or-`None`, used by both the caller and any report.

**Analog C (server-misconfig vs user-fault posture): the `MT5_GATEWAY_HOST`/`MT5_GATEWAY_PORT` block
inside `routers.exchange` (the `validate_key` gateway-config guard) and the same block inside
`job_worker._make_mt5_session`.** Both treat unset gateway env as a SERVER misconfiguration,
deterministic and non-retryable, logged **secret-free** and explicitly "never a credential failure".
Copy that framing verbatim in the new reader's message.

**⛔ What NOT to copy:**
- **Do NOT copy `routers.exchange`'s `service_error(500, "MT5_GATEWAY_UNCONFIGURED", retryable=False)`
  raise.** That is a request-scoped fail-closed for a user-initiated validation. D-02 says absent
  `MT5_LOGIN`/`MT5_PASSWORD`/`MT5_SERVER` must LOG ONCE AND CONTINUE — a raise at the startup hook
  would take analytics down for a deployment nobody configured for MT5.
- **Do NOT copy `job_worker._make_mt5_session`'s `raise RuntimeError(...)` for the NEW credentials.**
  The existing raise covers HOST/PORT and stays exactly as it is; the new env triple is optional and
  its absence must fall through to today's per-account behaviour.
- **Do NOT reuse `main.REQUIRED_PLATFORM_SECRETS` / `config_degraded_secrets`.** ⚠️ This is the most
  dangerous available analog. `main.health`'s own comment records T-140.1-24: Railway's
  `healthcheckPath` is `/health`, and the tuple is named *REQUIRED*. Adding MT5 names to it turns an
  unset optional variable into a red `config_ok` and re-opens exactly the restart-loop argument that
  comment exists to close. If the phase wants an MT5 configured/not signal on `/health`, it must be
  a **separate, non-required key** that never moves `status` and never moves `config_ok`. The rule
  to copy is the one already written there: *"`status` stays the WORKER-heartbeat verdict and
  `config_ok` stays the SECRET verdict; crossing them is the bug."*

**⚠️ "Log once and continue" — no exact analog. This is NEW.** The closest three:
- `sentry_init.init_sentry` — reads `os.getenv("SENTRY_DSN")`, returns early and **silently** when
  unset. Right control flow, wrong observability: silent is the defect class this milestone exists
  to remove.
- `main._capture_secret_misconfig` — a real THROTTLE: a module-level `_secret_capture_last_at:
  dict[str, float]` keyed `"<fault>:<secret name>"` against `time.monotonic()`, plus
  `_SECRET_CAPTURE_MIN_INTERVAL_S`, with the whole emit wrapped in try/except so an alerting
  failure never becomes a 500. It also documents WHY (an unthrottled per-request capture is its own
  outage) and states it **never holds a secret value** — only NAMES. This is the nearest thing in
  the service to "say it once, not on every call", and the shape to copy if the log sits on a hot
  path.
- `main_worker.daily_enqueue_loop`'s startup-gate arm — logs and **proceeds** when its gate check
  fails ("proceeding with startup enqueue (fail-safe)"). That is the D-02 posture in this repo's own
  voice: degrade loudly, never abort the boot.

Recommended synthesis: a module-level boolean/`dict` flag beside the reader (`_capture_secret_misconfig`'s
throttle shape, simplified to once-per-process), emitting NAMES of the absent variables only.

### 2. The session-open call site — `job_worker._make_mt5_session`

**Analog: itself.** `_make_mt5_session(api_key, api_secret, passphrase) -> Mt5Session` already does
exactly the four things the new code needs, in order: lazy runtime imports of `Mt5Client` and
`parse_mt5_credentials` (keeping the module-import-does-not-require-`mt5linux` contract intact), the
offline fail-CLOSED credential parse, the `MT5_GATEWAY_HOST`/`MT5_GATEWAY_PORT` guard, and the
`Mt5Session(...)` construction. Copy: the lazy-import placement, the env guard position (before
construction), and the docstring convention of naming the defect id the function serves.

**Where the new login naturally sits — and the constraint that decides it.** The existing per-account
login is NOT here; it is at the READ sites, inside the bounded off-loop bracket:
- `job_worker` — the derive/balance bracket built around `_assert_expected_login`, which calls
  `session.client.login(session.login, session.investor_password, session.server)` then
  `account_info()` and asserts **STRICT equality** of `info["login"]` against `session.login`, raising
  `Mt5AccountMismatchError` on a mismatch or a MISSING field (the MT5CONC-02 login bracket).
- `services.allocator_positions` — the same bracket, its own `_assert_expected_login`, same strict
  equality, same off-loop `_MT5_DERIVE_READ_TIMEOUT_S`-style ceiling.
- `services.mt5_probe` — the operator-fault path (`Mt5GatewayMisconfigured`, `curated_gateway_detail`).

⛔ **This is the single most important constraint in the phase and it has no prose anywhere else:**
an env-credential login performed *inside or after* those brackets would authenticate the TERMINAL
to the env account and then the very next `_assert_expected_login` would see a login that is not
`session.login` and raise `Mt5AccountMismatchError` — a correct-by-design guard turned into a
manufactured failure. D-03 ("per-account login is UNCHANGED") is therefore not merely a scoping
statement; it is a *sequencing* requirement. The env login belongs in the CONSTRUCTION path
(`_make_mt5_session`, before the `Mt5Session` is handed out and before any lease/bracket), not in
the read path, and every per-account `client.login(...)` must still run afterwards.

**What already happens on a failed connect:** the construction path raises `RuntimeError` on unset
gateway env; the read brackets classify via `services.mt5_validation.classify_mt5_login_error` and
the `_WRONG_SERVER_TOKENS`/`_AUTH_TOKENS` substring tables, routing to user-attributed `auth` /
`wrong_server` verdicts. ⚠️ **Copy the defensive lesson from `Mt5SessionAbandoned`'s docstring:** it
is deliberately a PLAIN `Exception`, not an `Mt5ClientError`, so an OUR-INFRASTRUCTURE refusal can
never be absorbed into a user-attributed verdict and blame a working key. A *terminal* re-login
failure is our infrastructure. If the new path raises at all, it must not raise an `Mt5ClientError`
into the classify arms — best-effort, logged, swallowed, per D-02.

**⛔ NOT to copy:** the `mt5_terminal_lease` / occupancy-token machinery. `_make_mt5_session` builds
its client in PREFLIGHT — outside and before the lease — and several tests
(`tests/test_mt5_client_contract.py`, `tests/test_mt5_abandon_roster.py`,
`tests/test_mt5_abandon_fence.py`) pin exactly that: it holds no lease and carries no occupancy
token. Adding a lease acquisition there would red those roster tests.

### 3. The worker-startup hook

⛔ **MEASURED, and it contradicts the obvious reading of D-01: `main_worker.main` IS NOT THE
PRODUCTION PATH.** Its own docstring block records the verification (Phase 143, 2026-08-17):
*"PRODUCTION DOES NOT RUN THIS ENTRYPOINT… the loops were merged into the FastAPI process"* after
the 2026-04-20 "jobs queued but never processed" incident. A startup login added ONLY to
`main_worker.main` would never run in production and would look green in every test.

**Analog: `main.lifespan`.** It is the real once-at-boot hook. Its established ordering is
`validate_kek_on_startup()` → `assert_platform_secrets_configured()` → log "Startup validation
complete" → lazy `import main_worker` → `assert_worker_not_aimed_at_prod_off_platform()` →
`asyncio.create_task(...)` for `dispatch_loop`, `watchdog_loop`, `daily_enqueue_loop`,
`_bridge_healthz`. Copy: the lazy import of anything MT5-shaped (same reason `main_worker` is
imported lazily — unit tests import `main.py` without env vars), and the comment convention naming
WHY a step sits where it does.

**Placement: put the re-login in the TASK region, not the validation region.** The validation region
is synchronous and boot-blocking; a call there that reaches the RPyC gateway would hold the pod's
startup on a network round-trip and could crash the boot. D-02 forbids that. The correct analog for
"once at startup, but tolerant, and after the loops are up" is `main_worker.daily_enqueue_loop`'s
startup tick: it lives INSIDE a loop task, runs once at boot subject to a gate, logs and proceeds
when the gate check fails, and its docstring states it runs on EVERY worker startup with a redundant
run explicitly accepted as the safe direction. That is exactly the D-02 posture and it answers the
CONTEXT research question: **the boot cannot be made to depend on gateway reachability, and today it
does not — nothing at startup touches MT5 at all.**

⚠️ **Railway boot ordering, for criterion 2's window:** the API/worker pod and the mt5-gateway
service start independently. A startup login may therefore fire while the gateway is still
unreachable. That is a *measurement input for D-06*, not a bug to engineer around in this phase —
record it, do not add a retry loop.

**Standalone parity:** mirror the same call into `main_worker.main` beside `validate_kek_on_startup`
so `python -m main_worker` behaves identically. The lifespan already documents this
merged-vs-standalone duplication as deliberate ("the merged-worker path of the same hard stop
`main_worker.main()` applies").

### 4. The test shape

**Analog: `tests/test_mt5_client_contract.py` — `_FakeMt5`, `_FakeRpycConn`, `_FakeNamedTuple` and
the `_make(scenario)` helper.**

How MT5 is doubled today (copy all of it):
- A scenario-dict-driven in-memory double injected through the `_connect` seam —
  **explicitly never a `MagicMock`**. The module docstring gives the reason: the double is shaped
  like the real bridge so the kwarg wiring is asserted for real (test-the-wiring lesson, P115), not
  against the impl's own formula.
- `_FakeMt5.login(self, login, **kwargs)` appends `(login, kwargs)` to `self.login_calls`, and
  `initialize(**kwargs)` appends to `self.initialize_kwargs` and increments `initialize_calls`.
  `self.call_order` records the sequence. **This is the mechanism that proves a call was MADE with
  particular arguments** — assert against `login_calls` / `call_order`, exactly as the existing
  timeout-ordering cases do. The new criterion-1 test asserts `fake.login_calls` contains the values
  taken from the monkeypatched env.
- The autouse `_reset_terminal_state` fixture calling
  `mt5_concurrency.reset_terminal_state_for_tests()` — process-wide MT5 state must be reset around
  every test or a leaked epoch bump fences another test's client under `-n auto --dist loadgroup`.
  Any new test module touching MT5 needs the same fixture.

How credentials are faked: **literal, obviously-fake strings** — `password="s3cr3t-pw"`,
`server="Broker-Demo"` / `"MyBroker-Live"`, `host="mt5-gw.internal"`, port `18812`. ⛔ D-04: keep
exactly this register; never a real credential, never the real broker server string, never the
account number.

How env is faked: `monkeypatch.setenv("MT5_GATEWAY_HOST", "mt5-gw.internal")` /
`monkeypatch.setenv("MT5_GATEWAY_PORT", "18812")` as used throughout `tests/test_ingestion_mt5.py`,
and `monkeypatch.setenv("MT5_ENABLED", "true")` in `tests/test_allocator_positions_non_ccxt.py`.
Copy that verbatim for `MT5_LOGIN` / `MT5_PASSWORD` / `MT5_SERVER`. ⚠️ Because the reader is a
per-call `os.getenv` (Analog A above), `monkeypatch.setenv` works without a reimport — this is the
whole reason that idiom was chosen; do not convert it to a module-level constant or the tests
silently bind to import-time state.

**⛔ NOT to copy:** the live-credential skip idiom (`@pytest.mark.skipif(not
os.environ.get("SFOX_SANDBOX_KEY"))` in `tests/test_sfox_client_live.py`). A test that skips when a
credential is absent is a test that never runs in CI — D-04 says doubles only, so there is nothing
to gate on and nothing to skip.

**D-05 falsifier:** remove the login call → observe RED → restore from a byte backup verified with
`cmp`. ⛔ Never `git checkout --` (it restores to HEAD and destroys the uncommitted edit). The
neuter must APPLY — a neuter that does not apply reads as GREEN.

### 5. Credential-safety analogs — what must NOT be weakened

**`Mt5Client.login` (the by-value redaction).** Its except arm runs
`safe = scrub_freeform_string(str(exc))` and then, because the credential values are in scope,
additionally `safe = safe.replace(literal, "[REDACTED]")` for each of `str(login)`, `password`,
`server`. The docstring states why: `mt5linux` f-string-interpolates the password into remotely-
eval'd code, so a raw rpyc remote traceback is a real credential disclosure (T-134-01). The new
caller passes env-sourced values through this same method — **the redaction covers them for free and
must not be bypassed.** ⛔ Do not add a new code path that logs the exception before `login()` wraps
it, and do not log the env values at the call site.

**`services.redact.scrub_freeform_string`.** Five-pass shape-based redaction (URL userinfo →
key=value → `scrub_pii` JWT → embedded JWT → transitive re-walk), with a fast-path that returns
early when the string carries no `:`, `=` or `.`. ⚠️ It is SHAPE-based, so it would not on its own
catch a bare password echoed as prose — which is exactly why `login()` layers the by-value pass on
top. Any new log line must rely on the by-value layer, not on this alone.

**`Mt5Session`'s `field(repr=False)` on `login`, `investor_password` and `server`.** The dataclass
auto-`__repr__` would otherwise emit the plaintext investor password into any `%r`/f-string/structlog
serialization. If the phase adds a field carrying env credentials to any dataclass, it carries
`repr=False` too — the invariant is STRUCTURAL here, not call-site discipline, and it must stay that
way.

**Existing tests that pin the redaction — the regression fence for this phase.** In
`tests/test_mt5_client_contract.py`: `test_login_failure_raises_typed_error_no_secret` (falsy return
→ typed `Mt5ClientError` carrying the `last_error()` code, password absent from the message) and
`test_login_transport_raise_is_scrubbed_and_typed` (a transport RAISE whose text embeds the
interpolated credentials → scrubbed and typed; asserts the password, the server AND the login string
are all absent). There is also a `capture_logs()` sweep over the stage-event emissions with an
explicit non-vacuity assertion (`"the sweep is vacuous — no stage event was captured at all"`, plus
a check that a FAILED-stage event was captured). ⛔ All of these must stay green unchanged; if the
phase makes any of them need editing, that is the signal that the redaction is being weakened.

## Shared Patterns

### Per-call env read, never a module-load constant
**Source:** `services.closed_sets.mt5_enabled_server` (and its module comment).
**Apply to:** the new credential reader.
Rationale is written there: a go-live env change or a test `monkeypatch.setenv` must take effect
without a reimport. `tests/test_phase12_kill_switch.py` carries a dated note about an
`int(os.getenv(...))` read at import breaking unrelated callers.

### Fail-CLOSED normalisation
**Source:** `mt5_enabled_server` / `sfox_enabled_server` — `.strip().lower() == "true"`.
**Apply to:** any boolean-shaped env this phase reads. Unset / `""` / `"1"` / `"on"` all mean OFF.

### Secret NAMES in logs, never values
**Source:** `main._capture_secret_misconfig` (tags carry `config_secret` = the NAME) and
`main.health`'s comment that `/health` is unauthenticated so an echo would be a public disclosure.
**Apply to:** the D-02 "log once and continue" line, and anything added to `/health`.

### Server-misconfig framing, never a user-credential blame
**Source:** the gateway-config guards in `routers.exchange` (`validate_key`) and
`job_worker._make_mt5_session` — *"This is a server misconfiguration, never a credential failure."*
**Apply to:** the absent-env message.

### Our-infrastructure refusals are PLAIN exceptions
**Source:** `Mt5SessionAbandoned` (and its siblings `Mt5AccountMismatchError`,
`Mt5TerminalBusyError`, `_Mt5PostReadVerificationError`).
**Apply to:** any new exception this phase introduces — it must not subclass `Mt5ClientError`, or it
can be absorbed into a user-attributed `auth`/`wrong_server` verdict and blame a working key.
