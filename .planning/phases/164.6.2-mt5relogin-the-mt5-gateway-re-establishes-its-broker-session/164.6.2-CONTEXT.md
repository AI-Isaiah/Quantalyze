<domain>
## Phase Boundary

The MT5 terminal's broker session is re-established **without a human**. Today it is established
ONCE, BY HAND, over VNC, and NOTHING re-establishes it — so any rotation, expiry or volume event
takes MT5 down silently.

⛔ **IN scope:** the env-credential caller. `MT5_LOGIN`/`MT5_PASSWORD`/`MT5_SERVER` become Railway
variables, and the analytics WORKER calls the EXISTING `Mt5Client.login()` from them on session
open and once at its own startup.

⛔ **NOT in scope, and named so nobody re-acquires it:**
- **Entering any credential.** The founder sets the Railway variables. The phase is BUILT and
  tested against doubles with no real credential; it CLOSES only after the founder sets them.
- **Changing what the gateway READS.** This removes the need to repeat a hand login; it does not
  widen access. Investor credentials suffice — only equity and positions are read.
- **The `-6` defect vocabulary.** That was deferred to Phase 164.8.3 PROBERAUTH, which ✅ SHIPPED
  2026-09-13 in v0.77.42.0 (PR #796). What the prober SAYS about a lost session is settled there;
  what the gateway DOES about one is here.
- **Clearing the CURRENT outage.** Run `34758502223` (2026-09-13) still reports `-6`. This phase
  stops the NEXT one being silent and hand-repaired; it does not substitute for the founder's
  one-time credential setup.

⛔ **THE PHASE'S ORIGINAL PREMISE WAS WRONG AND IS CORRECTED IN THE ROADMAP — do not restore it.**
Criterion 1 and the goal both said *"the GATEWAY performs `login()` at startup"*. MEASURED
2026-09-13: the Railway mt5-gateway is a PREBUILT THIRD-PARTY image, `gmag11/metatrader5_vnc:2.3`,
deployed straight from Docker Hub (`deploy/mt5-gateway/railway-gateway.md`). The only environment
variables it reads are `CUSTOM_USER`, `PASSWORD` (both VNC) and `mt5server_port`; its `start.sh`
launches only the RPyC bridge. There is no auto-login hook and no build of ours to add one to.
⚠️ A planner who "fixes" this by adding a Dockerfile is re-opening a founder decision, not closing
a gap — see D-00.

<decisions>
## Implementation Decisions

### Founder decisions (smart discuss, 2026-09-13)

- **D-00 — Worker-side re-login, NOT an image fork.** The alternative was building our own
  Dockerfile FROM `gmag11/metatrader5_vnc:2.3` with an auto-login entrypoint. Rejected on cost:
  we would own and maintain an image whose MetaTrader binary self-updates from the broker anyway,
  and the broker password would move into the container environment. The worker-side shape puts
  the login where the credentials, the scrubbing and the tests already live.
- **D-06 — MEASURE the healing window; do not close it in this phase.** Restart the gateway,
  record how long the prober stays red and what closes it. If the window is acceptable, the phase
  closes. If not, book a keepalive as a NAMED follow-up phase. ⭐ The reasoning is explicit: a
  keepalive designed before any measurement is an interval tuned against a guess. ⛔ Rejected
  alternative: having the prober perform the login when it sees `-6` — that makes the instrument a
  mutator and widens what the prober is credentialed to do, against criterion 5 and Phase 164.1's
  design.

### Founder decisions added 2026-09-13 AFTER research (both overturned an earlier decision)

- **D-07 — A NEW credentialed-initialize method, NOT a change to `Mt5Client.login()`.** Research
  proved `login()` cannot heal a `-6`: it opens with a credential-less `initialize()` and raises
  before reaching its own credentialed `login()`. The heal is `initialize(login=…, password=…,
  server=…)`. It lands as a new method because `login()`'s four per-account callers are shipped and
  working, and a regression there would land on live job processing.
  ⛔ **ORDERED SECURITY PRECONDITION:** the by-value redaction loop must be on the `initialize` arm
  BEFORE any credential flows through it. Today only the `login` arm has it. `mt5linux`
  f-string-interpolates arguments into remotely-eval'd code (T-134-01) — this is a shipped control
  and routing credentials past it is a REGRESSION, not an omission.
- **D-08 — Startup-only; D-01's "on session open" is STRUCK.** `Mt5Client._epoch` binds on first
  touch and `_make_mt5_session` runs in preflight OUTSIDE the lease, so a login there can refuse a
  legitimate derive read with `Mt5SessionAbandoned`. The heal lives in `main.lifespan` — the
  production path — and nowhere else. ⚠️ This lengthens the healing window, which D-06 already
  requires to be measured rather than guessed.

- **D-09 — the stale `Account=1` sentence in the shipped `-6` remedy is folded INTO this phase.**
  Phase 164.8.3 owns that file's vocabulary but is COMPLETE and SHIPPED (4/4, `5dead88a`,
  v0.77.42.0), so it cannot receive the work. Folded here because this phase already produces the
  measurement that settles it — criterion 2's heal run reads `trade_allowed` before and after.
  ⛔ Rejected alternatives, and why: Phase 164.8.4 would be a THIRD outside item against a fence
  re-armed hours earlier; a new phase is a full cycle for one sentence.
  **The contradiction, both verified at HEAD:** the remedy says *"a login is an ACCOUNT CHANGE, and
  MT5 re-clears those options on every account change"*, while `156-LIVE-ACCEPTANCE.md` records
  from a LIVE run the same day that the founder unticked both auto-disable boxes and
  `trade_allowed` stayed **true** across a real `login()` — *"the `Account=1` re-disable loop is
  broken"*.
  ⭐ **STALE, not FALSE** — the sentence is true while `Account=1` is ARMED, and the 2026-08-13
  unticking disarmed it. Cost is one wasted operator step. ⛔ Do not plan it as a bug fix.
  ⛔ **MEASURE FIRST:** unmeasurable today (`terminal_info` is `null` while `-6` is in force). "No
  change needed, here is the evidence" is a legitimate outcome.

### Claude's discretion (proposed, not founder-reviewed)

- **D-01 — Call site.** ⛔ **SUPERSEDED BY D-08 — struck, not amended.** It proposed `_make_mt5_session`; research showed that site is unsafe. Kept here as the record of a proposal that measurement overturned.
- **D-02 — Absent env vars: log once, continue.** ⛔ NEVER fail the worker's boot. MT5 is one arm
  of many; a hard failure would take analytics down for a service nobody configured for MT5.
- **D-03 — Per-account login is UNCHANGED.** `job_worker` and `allocator_positions` keep passing

- **D-04 — Doubles only in tests.** Assert the call is MADE with values taken from env; never a
  real credential. The existing `scrub_freeform_string` + by-value redaction already covers the
  failure path and must not be weakened.
- **D-05 — The criterion-1 test is a FALSIFIER.** Remove the login call, observe RED, restore from
  a BYTE BACKUP verified with `cmp`. ⛔ Never `git checkout --`.

<code_context>
## Existing Code Insights

⭐ **The login path EXISTS — this phase adds a caller, it does not build a login.**
`Mt5Client.login(login, password, server)` in `analytics-service/services/mt5_client.py` (cited BY
SYMBOL, per `[164.7-CITATION-DRIFT-01]`) already:
- calls `initialize()` FIRST, because the MT5 Python API needs the IPC pipe attached before any
  call — without it `login()` returns `-10004 'No IPC connection'` against a real terminal;
- carries explicit millisecond ceilings on BOTH calls from `_ipc_timeouts_ms`, each strictly below
  the rpyc request timeout so MT5 fails its own pipe first;
- scrubs transport text AND redacts the credential values by value, because `mt5linux`
  f-string-interpolates the password into remotely-eval'd code — a raw rpyc traceback is a real
  credential disclosure (T-134-01).

**Existing callers, all per-account:** `job_worker`, `allocator_positions`, `mt5_probe`, plus the
`mt5_spike`/`mt5_soak` scripts.

⚠️ **A load-bearing ASSUMPTION is recorded in that docstring and is NOT a MetaQuotes guarantee:**
that a bare `initialize()` is idempotent — a no-op `True` when already attached. It is an empirical
observation (EVIDENCE Correction C-7), owned by Phase 155. This phase adds a call path that relies
on it; if the measurement in D-06 shows unexpected behaviour, that assumption is the first suspect.

⚠️ **The prober's arm is a DIFFERENT path.** `scripts/prod-prober/arms/mt5.mjs` runs a
credential-less `initialize()` and never logs in. That is deliberate and stays that way — it is why
criterion 2's observation is meaningful, and why D-06 rejected letting the prober self-heal.
</code_context>
