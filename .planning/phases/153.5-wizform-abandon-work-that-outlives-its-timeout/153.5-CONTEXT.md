# Phase 153.5: WIZFORM-ABANDON — Work that outlives its timeout - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning

<domain>
## Phase Boundary

No `asyncio.to_thread` work can keep touching the MT5 terminal after its `wait_for` fired
and its caller released the lease.

ONE defect with three faces, all introduced in the Phase 153.3 diff and all deliberately
deferred by that phase's `/code-review high`. Work handed to `to_thread` outlives its
`asyncio.wait_for`; the `wait_for` raises, the caller unwinds and releases the terminal
lease, and the abandoned thread keeps driving the same process-global MT5 session.

| # | Site (locate by MECHANISM — see below) | Symptom |
|---|---|---|
| 5 | `services/mt5_concurrency.py` `_mt5_bounded_restart` | abandons at its ~10s bound; the one permitted `mt5.shutdown()` can fire **after** the lease is released, under the next holder |
| 6 | `routers/exchange.py` connect stage (+ `services/ingestion/mt5.py`) | a connect-stage timeout orphans an `Mt5Client` the thread then constructs — `client` was never assigned, so the Pitfall-6 `finally` releases nothing and the rpyc session leaks |
| 7 | `routers/exchange.py` end-to-end probe deadline | the deadline fires; the abandoned probe keeps issuing rpyc calls, so D-29's serialization does not hold on the timeout path |

⚠️ **The line numbers in ROADMAP.md and TODOS.md have DRIFTED.** They were recorded against
the 153.3 diff. Verified 2026-08-11: `routers/exchange.py:689` now lands in unrelated
`order_check` commentary. Locate all three sites by mechanism, never by the quoted line.

### Why this phase is load-bearing beyond its three findings

D-35 (Phase 153.3, plan 06) removed `mt5.shutdown()` from `Mt5Client.close()` and left
exactly ONE surviving teardown: `Mt5Client.restart()`'s, the deliberate heal of a wedged
pipe (MT5CONC-01). TODOS records that survivor as safe **"because every call site holds
the terminal lease."** Finding #5 is precisely the case where that premise is false. This
phase is therefore not three loose ends — it is the repair of the safety argument the
previous phase's fix rests on.

<decisions>
## Implementation Decisions

### D-36: The sink is a generation/epoch counter on `Mt5Client` (ACCEPTED)

- **`Mt5Client` carries a generation. The lease bumps it on release. Every method that
  touches the MT5 session checks it FIRST and refuses on a stale epoch.** Fixes #5, #6
  and #7 at one sink with zero call-site edits — the same fix-at-the-sink shape D-35
  already used successfully in this exact module.
- **The refusal must be LOUD** — raise a named error (e.g. `Mt5SessionAbandoned`), never a
  silent no-op. A zombie thread discovering it has been fenced is a real event; swallowing
  it reproduces the silent-UNKNOWN class this milestone has spent four phases closing.
- **An ast roster test is required, modelled on `tests/test_mt5_shutdown_roster.py`** —
  derive the set of session-touching methods from source, assert each carries the guard,
  with a vacuity floor and self-tests. Without it the guard is correct today and forgotten
  by the next method written. (This is the static complement to guard #16; it does NOT
  replace the runtime assertion.)
- ⛔ **REJECTED — "refuse to release the lease until the worker confirms it stopped."**
  Correct in isolation, wrong in system: it blocks the lease for as long as the hung
  thread, which is exactly the **WEDGE-01** class D-25 forbids (`mt5_client.py:79-81` — a
  hung terminal must not wedge the SEQUENTIAL worker past the ~90s healthz budget). This
  project has already paid for that class once (PR #632, heavy pandas on the shared loop
  froze healthz). The hang would propagate from one job to every subsequent lease waiter.
- ⛔ **REJECTED — "cancellation-aware wrapper" as a standalone remedy.** Python threads
  cannot be interrupted; `to_thread` offers no cancellation. Such a wrapper discards the
  RESULT while the thread keeps issuing rpyc calls against the same session — it makes the
  caller tidier and changes nothing about the defect. If the wrapper also gates the
  session, it *is* D-36 under a different name.

### D-37: Guard #16 is a deterministic barrier + fake-session spy (ACCEPTED)

- **The AST lease-roster CANNOT catch this class** — its enclosure proof is *lexical*, so
  it reads the `shutdown` as inside the `async with` and passes while the runtime escapes.
  Guard #16 must be a **runtime** assertion.
- **Shape:** a fake MT5 session records every touch as `(method, epoch, at_time)`. The test
  owns a `threading.Event` the worker thread blocks on, so the abandonment is *scheduled by
  the test*, not by the scheduler: worker blocks → `wait_for` fires → caller unwinds, lease
  releases, epoch bumps → test sets the Event → zombie proceeds → assert no post-release
  touch carries a live epoch and the zombie's calls raise.
- ⛔ **NO sleep-ordered concurrency test.** This repo already carries four documented flake
  mechanisms in its shared-DB suite and a `--no-file-parallelism` workaround for local
  vitest; a timing-ordered race would buy a fifth, and would pay the real bound on every
  run.
- The guard must be **falsifiable**: remove the epoch check, the post-release touch lands,
  the test reds. Observe that red, do not predict it.

### D-38: Scope stays ONE class (ACCEPTED)

- **IN:** findings #5, #6, #7 — the abandoned-`to_thread` mechanism, fixed at the sink.
- **OUT — the structlog processor-chain freeze** (8 module-level `get_logger` proxies bind
  before `configure_logging()` runs in the lifespan, bypassing the PII `_redact_processor`).
  A real defect and a real redaction bypass, but it shares only a *directory* with this
  phase, not a mechanism. It also carries its own unresolved decision in TODOS ("triage
  before fixing all eight — exposure is NOT uniform") plus a preferred class fix (drop
  `cache_logger_on_first_use`, or configure logging at import). That is a phase-sized
  decision, not a rider. Stays in TODOS with its own owner.
- **OUT — finding #8** (the 60s per-stage ceiling wraps SIX round-trips whose own ceilings
  are 45 000ms IPC / 55s rpyc, so "innermost fires first" holds per round-trip but not per
  stage) and **finding #10** (the 20s interactive lease wait is smaller than the worker's
  40s read + 10s restart hold, so an interactive validate can never wait out one in-flight
  derive). Both are **deferred to Phase 155** because both need the live latency data D-32
  made collectable. ⛔ Do NOT guess these numbers.
- **OUT — cross-replica serialization.** The terminal lease is an `asyncio.Lock`, which is
  single-event-loop and serializes nothing across replicas. That is why **D-33** pins the
  gateway to a SINGLE replica. Owner: D-33. A scale-up is a correctness change, not a
  capacity knob.

### Claude's Discretion

- Where the epoch lives (module-level registry keyed by `terminal_key`, mirroring
  `_mt5_terminal_lock_for`, vs. an attribute) — pick whichever survives the
  `_make_mt5_session` builds-a-fresh-client-per-job trap that MT5CONC-02's docstring warns
  about. A per-instance counter that a fresh instance resets would fence nothing.
- The exact exception type/name and whether #6's orphaned client is additionally closed by
  the fence or merely refused.
- Plan count and wave structure.

## Existing Code Insights

### Reusable Assets
- `services/mt5_concurrency.py` — `mt5_terminal_lease` (`@asynccontextmanager`, line ~207)
  is the natural place to bump the generation on release; `_mt5_terminal_lock_for` (~182)

  reinvent.
- `Mt5Client` already accepts `request_timeout_s` as a constructor argument, so per-path
  chains exist without touching the module constant.

### Established Patterns
- **Fix at the SINK, not at N call sites.** D-35 closed the `shutdown()` class with zero
  call-site edits and is the precedent this phase is explicitly told to follow. The
  milestone has paid for the instance-not-class mistake sixteen times.
- **Roster tests derive from source via ast**, never a hand-edited list.
- Bounded work runs off the event loop under a ceiling precisely so a hung gateway cannot
  wedge FastAPI/healthz (WEDGE-01) — any fix must preserve that non-blocking posture.

### Integration Points
- `services/mt5_concurrency.py` (lease + bounded restart), `routers/exchange.py` (connect
  stage + end-to-end probe deadline), `services/ingestion/mt5.py` (the worker's client
  construction), `services/mt5_client.py` (the sink itself), `analytics-service/tests/**`.
