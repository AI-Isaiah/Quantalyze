## Summary

The four defect sites are all one shape: `asyncio.wait_for(asyncio.to_thread(f), t)`. When
`t` expires, `wait_for` cancels the *asyncio* future; the OS thread running `f` is not
touched and keeps running. The caller unwinds, the `async with mt5_terminal_lease(...)`
releases, and `f` keeps driving the process-global MT5 session. **This is verified, not
assumed**: `asyncio.futures._copy_future_state` opens with `if dest.cancelled(): return`, so
the zombie's eventual result *and its eventual exception* are silently discarded
[VERIFIED: CPython `asyncio/futures.py`, read in-session]. That discard has a direct design
consequence — D-36's "LOUD refusal" cannot be loud by raising alone. The sink must **log**
at the moment it fences, because on three of the four sites there is no longer anybody to
catch the raise.

Three structural facts govern where the epoch can live. First, `services/mt5_concurrency.py`
imports `services/mt5_client.py` (line 36, a runtime import of one constant) and
`mt5_client` imports only `services.redact` — the dependency is strictly one-way, so
**`Mt5Client` cannot read a registry that lives in `mt5_concurrency`** without a circular
import. The epoch registry therefore belongs in `services/mt5_client.py`, and
`mt5_terminal_lease` imports the bump — the same direction the existing constant import
already travels. Second, the epoch must be **module-level and keyed by `terminal_key`**,
because `mt5_terminal_lease(terminal_key: str, ...)` receives *only a string* — it holds no
reference to any client and structurally cannot bump an instance attribute. Third, two of
the four `Mt5Client` construction sites (`job_worker._make_mt5_session` →
`_make_exchange_client` → `_exchange_preflight` / `_allocator_key_preflight`) build the
client **outside and before** the lease, so an epoch captured at construction and compared
strictly would false-positive on every legitimate derive/holdings job that races an
unrelated lease release. The client must therefore bind its epoch **lazily on its first
session touch**, not at construction.

The honest gap: **the method-level fence does not fix finding #6.** In #6a and #6b the
abandoned thread is inside `Mt5Client.__init__`'s blocking connect and makes *no further
session call* — the lambda returns and the thread's work ends. There is no method for a
guard to sit in front of. #6 is a resource leak (an rpyc socket to the gateway that nobody
will ever close), not a correctness hazard, and the only sink-side mechanism that closes it
is a **construction-time self-disposal**: snapshot the epoch before the connect, re-read it
after, and if it moved, tear down the socket we just opened and raise. That is a *different*
mechanism in the same sink, it carries a small false-positive risk against the two unleased
preflight constructions, and CONTEXT.md's claim that D-36 "fixes #5, #6 and #7 at one sink"
is only true once the constructor participates. This is the single most important thing this
research can hand the planner.

**Primary recommendation:** put `_MT5_TERMINAL_EPOCHS: dict[str, int]` + `_mt5_epoch_for()` /
`_bump_mt5_epoch()` in `services/mt5_client.py`; bump inside `mt5_terminal_lease`'s existing
`finally`, **before** `lock.release()`; give `Mt5Client` a lazily-bound `self._epoch: int |
None` and a private `_assert_live()` as the first statement of the seven session-touching
methods plus a second check immediately before `stale.shutdown()` inside `restart()`; treat
#6 as its own task with its own decision (see §Open Questions Q-1).

## Q1 — Where must the generation live so it actually fences?

### Finding 1.1 — It cannot live in `services/mt5_concurrency.py`

[VERIFIED: ast import walk over both modules, run in-session]

```
services/mt5_client.py       →  services.redact                    (line 123)   -- only in-tree import
services/mt5_concurrency.py  →  services.mt5_client                (line 36)    -- RUNTIME import of MT5_REQUEST_TIMEOUT_S
services/mt5_concurrency.py  →  services.mt5_client.Mt5Client      (line 39)    -- TYPE_CHECKING only
```

`mt5_concurrency`'s module docstring states the invariant explicitly (lines 20-24): *"this
module MUST NEVER import `services.job_worker`, nor anything that does. Its only in-tree
import is one constant from `services.mt5_client` — itself a leaf over `services.redact`."*

⛔ **Therefore: if the epoch registry lives in `mt5_concurrency`, `Mt5Client` must import
`mt5_concurrency` to read it, and that is a circular import.** A lazy import inside
`_assert_live()` would "work" and would sit on the hot path of every MT5 round-trip while
inverting the documented leaf ordering. Do not do this.

✅ **The registry belongs in `services/mt5_client.py`.** `mt5_terminal_lease` then imports
`_bump_mt5_epoch` alongside the constant it already imports — the same direction, no new
edge in the module graph, leaf invariant preserved.

### Finding 1.2 — It must be keyed by `terminal_key`, module-level

[VERIFIED: `services/mt5_concurrency.py:207-273`]

```python
async def mt5_terminal_lease(terminal_key: str, *, wait_s: float | None = None) -> AsyncIterator[None]:
```

The lease receives **a string and nothing else**. It holds no client, no session, no
reference to anything the fence could stamp. An instance attribute is structurally
unreachable from the place D-36 says the bump happens. This is a stronger argument than the
MT5CONC-02 fresh-client-per-job argument the CONTEXT flags, and it is decisive on its own.

The existing precedent to mirror is verbatim `services/mt5_concurrency.py:179-187`:

```python
_MT5_TERMINAL_LOCKS: dict[str, asyncio.Lock] = {}

def _mt5_terminal_lock_for(terminal_key: str) -> asyncio.Lock:
    return _MT5_TERMINAL_LOCKS.setdefault(terminal_key, asyncio.Lock())
```

`terminal_key` is `f"{self._host}:{self._port}"` (`services/mt5_client.py:911-924`, a
`@property`). Every lease call site derives the identical string from the same env
(`routers/exchange.py:796`, `services/ingestion/mt5.py:198`) or reads the property directly
(`job_worker.py:364`, `job_worker.py:3572`, `allocator_positions.py:656`). The epoch keyed
the same way is contended by the same set.

### Finding 1.3 — Capture at construction is WRONG; bind lazily on first touch

[VERIFIED: `services/job_worker.py:944-973` and `:976-1003`; `services/allocator_positions.py:599-613`]

`_make_mt5_session` builds `Mt5Client(host, int(port_raw))` (`job_worker.py:969`) and is
reached from `_make_exchange_client` (`:1002`), which both preflights call. Both preflights
run **before** the `async with`. The code says so itself at `allocator_positions.py:601-606`:

> *"By the time this runs, `_allocator_key_preflight` has already decrypted the credentials
> and built the client through `job_worker._make_exchange_client` → `_make_mt5_session` →
> `Mt5Client(...)`, whose `__init__` opens the RPyC transport."*

and again at `job_worker.py:3478-3482`.

⚠️ **The false-positive this creates, spelled out:**

1. Derive preflight constructs `Mt5Client`. Epoch for `mt5-gw:18812` is `7`. Client stamps `7`.
2. An interactive validate finishes and its lease releases → epoch becomes `8`.
3. The derive job acquires the lease and calls `login()` → `7 != 8` → **a perfectly
   legitimate read is refused.**

The two leased construction sites (`routers/exchange.py:513-524` and
`services/ingestion/mt5.py:207-210`) do not have this problem. The two unleased ones do.

✅ **Lazy binding removes it entirely.** `self._epoch: int | None = None` at construction;
the first session touch binds it to the *current* epoch; every subsequent touch compares. In
the sequence above, `login()` is the first touch, it happens under the held lease, it binds
`8`, and the read proceeds. The zombie cases still fence, because in every one of them the
first touch happened under the lease that later released.

### Recommended shape

```python
# services/mt5_client.py — beside MT5_IPC_TIMEOUTS_MS

_MT5_TERMINAL_EPOCHS: dict[str, int] = {}

def _mt5_epoch_for(terminal_key: str) -> int:
    """The CURRENT lease generation for one terminal. `dict.get` with a default —
    never `setdefault` — so a read cannot mint an entry and diverge from the bump."""
    return _MT5_TERMINAL_EPOCHS.get(terminal_key, 0)

def bump_mt5_terminal_epoch(terminal_key: str) -> int:
    """Called by mt5_terminal_lease on EVERY release. Public (no underscore) because
    it crosses a module boundary — mt5_concurrency imports it."""
    nxt = _MT5_TERMINAL_EPOCHS.get(terminal_key, 0) + 1
    _MT5_TERMINAL_EPOCHS[terminal_key] = nxt
    return nxt
```

```python
# class Mt5Client

    self._epoch: int | None = None     # in __init__, UNBOUND

    def _assert_live(self, stage: str) -> None:
        current = _mt5_epoch_for(self.terminal_key)
        if self._epoch is None:
            self._epoch = current          # first touch under a held lease — bind
            return
        if self._epoch != current:
            logger.warning(               # ⭐ the loudness that actually reaches an operator
                "Mt5Client: refusing %s — this session was abandoned by its caller "
                "and the terminal has since been handed to another holder "
                "(WIZFORM-ABANDON / D-36).", stage,
            )
            raise Mt5SessionAbandoned(stage)
```

⚠️ **`_assert_live` runs on a WORKER THREAD** (every session touch is inside a
`to_thread` body). `_MT5_TERMINAL_EPOCHS` is therefore read cross-thread while the event-loop
thread writes it. A `dict.get` and a `dict.__setitem__` on a plain `int` value are each a
single bytecode under the GIL, so neither can tear and neither can observe a half-written
state. There is no atomicity requirement beyond that: the fence needs "did the value change",
not "which value exactly". ⛔ Do NOT reach for a `threading.Lock` here — it would be held on
the hot path of every round-trip and would introduce a lock-ordering question against the
terminal lease that does not currently exist.

## Q3 — Where the lease releases, and whether that is the right place to bump

`mt5_terminal_lease` is `services/mt5_concurrency.py:207-273`. Structure, verbatim:

```
239   lock = _mt5_terminal_lock_for(terminal_key)
242   if wait_s is None:
243       await lock.acquire()
245-258 else: wait_for(lock.acquire(), wait_s)  →  TimeoutError → raise Mt5TerminalBusyError
261   try:
262-270   [threshold log]
271       yield
272   finally:
273       lock.release()
```

### Every exit path is covered

| Exit | Reaches `finally`? |
|------|--------------------|
| Body returns normally | ✅ generator resumes at `yield`, `finally` runs |
| Body raises (`HTTPException`, `Mt5ClientError`, `service_error`, …) | ✅ `__aexit__` → `gen.athrow` → `finally` |
| Body's task is CANCELLED | ✅ `CancelledError` is thrown into the generator at `yield`; `finally` runs |
| **Acquisition timed out** (`Mt5TerminalBusyError`) | ✅ **correctly NOT reached** — the raise at `:256` is *before* the `try:` at `:261`, so nothing is released and nothing may be bumped. The docstring pins exactly this (`:232-236`). |

✅ **The bump belongs in that same `finally`.** It inherits the release discipline the
docstring already documents and `tests/test_mt5_concurrency.py` already pins, and it cannot
fire for a caller that never held the terminal.

### Bump BEFORE `lock.release()`

```python
    finally:
        bump_mt5_terminal_epoch(terminal_key)
        lock.release()
```

Today the order is immaterial: `Lock.release()` schedules the waiter's wake with
`call_soon`, and no `await` separates the two statements, so no other coroutine can run
between them. Bump-first is nonetheless the right order, because it makes the invariant
*"no new holder can exist while the old generation is still current"* true by construction
rather than true by the absence of an `await` a future author might insert.

### Re-acquisition by the next holder, and a NEW client constructing during the zombie's lifetime

Walk it with the lazy-bind design (§Q1):

| t | Event | epoch | zombie's `_epoch` | new client's `_epoch` |
|---|-------|-------|-------------------|------------------------|
| 0 | Holder A acquires | 4 | — | — |
| 1 | A's client first touch (`login`) | 4 | **binds 4** | — |
| 2 | A's `wait_for` fires; thread abandoned | 4 | 4 | — |
| 3 | A unwinds; lease `finally` → bump, release | **5** | 4 | — |
| 4 | Holder B acquires; constructs a client (or reuses a preflight one) | 5 | 4 | `None` |
| 5 | B's first touch | 5 | 4 | **binds 5** |
| 6 | **Zombie's next touch** | 5 | 4 ≠ 5 → **`Mt5SessionAbandoned`** ✅ | 5 = 5 ✅ |

And the low-contention case, which is the one that kills a bump-on-*acquire* design:

| t | Event | epoch | zombie |
|---|-------|-------|--------|
| 3 | A releases; **nobody else ever acquires** | **5** | 4 |

## Q4 — `restart()` and the one surviving `mt5.shutdown()`

`Mt5Client.restart` is `services/mt5_client.py:824-909`. The body that matters:

```
880   def _reconnect_then_dispose_stale() -> None:
881       stale = self._mt5
883-885   self._mt5 = self._connect(host=..., port=..., timeout=...)     # WR-01: reconnect FIRST
886       self._closed = False
891-896   try: stale.shutdown()          ⭐ THE ONE PERMITTED shutdown
907       self._teardown_transport(stale, who="Mt5Client.restart", stage=None)
909   self._timed("restart", _reconnect_then_dispose_stale)
```

### A restart cannot fence itself

The legitimate heal runs **inside** the lease. The bump happens on lease **release**.
Therefore the epoch is unchanged for the whole duration of any restart that completes within
`_MT5_RESTART_TIMEOUT_S` (~10s). An entry check reads `epoch == self._epoch` and passes. ✅
The recovery path is not broken.

`tests/test_mt5_shutdown_roster.py:393-417` already proves from source that all four
`restart` call sites (`allocator_positions.py` ×2, `job_worker.py` ×2) are lexically inside
an `async with` lease — so "restart is only ever invoked under the lease" is an existing,
enforced property, not a hope.

### An entry check ALONE does not fix finding #5

Finding #5 is precisely the case where the check has already passed and the *damage happens
later*. `_mt5_bounded_restart` (`mt5_concurrency.py:104-126`) gives the restart ~10s and then
abandons it; the caller returns a transient `DispatchResult`, the lease releases (epoch
bumps), and the zombie — still inside `_reconnect_then_dispose_stale` — reaches `stale.shutdown()`
at `mt5_client.py:892`. Because `mt5linux` serves every rpyc connection from ONE
`ThreadedServer` over ONE `MetaTrader5` instance holding ONE IPC pipe
(`153-EVIDENCE-mt5-platform` §A2 / C-1, cited at `mt5_client.py:68-72`), that late shutdown
destroys the pipe for the **next holder**, who observes `-10004 No IPC connection`.

⭐ **The load-bearing check is a SECOND one, immediately before `stale.shutdown()`.**

### Recommended ordering inside `restart()`

```python
def _reconnect_then_dispose_stale() -> None:
    # (1) ENTRY — an already-abandoned restart must not open a socket nobody will close.
    self._assert_live("restart")                      # raises before any I/O

    stale = self._mt5
    self._mt5 = self._connect(...)                    # WR-01 preserved: reconnect FIRST
    self._closed = False

    # (2) THE LOAD-BEARING CHECK — between the reconnect and the shared teardown.
    if self._epoch != _mt5_epoch_for(self.terminal_key):
        logger.warning(
            "Mt5Client.restart: this restart was abandoned by its caller and the "
            "terminal has been handed on — SKIPPING the shared-IPC shutdown() "
            "(it would -10004 the next holder). Disposing our own sockets only."
        )
        # ⛔ Our OWN sockets are always ours to close (D-35). Dispose BOTH:
        #    the stale one, and the fresh one nobody will ever use.
        self._teardown_transport(stale,     who="Mt5Client.restart(abandoned)", stage=None)
        self._teardown_transport(self._mt5, who="Mt5Client.restart(abandoned)", stage=None)
        self._closed = True                          # restore the latch we cleared at :886
        raise Mt5SessionAbandoned("restart")

    try:
        stale.shutdown()
    except Exception:
        logger.warning("Mt5Client.restart: stale shutdown() raised; swallowing.")
    self._teardown_transport(stale, who="Mt5Client.restart", stage=None)
```

Three things the planner would otherwise get wrong here:

1. ⚠️ **Skipping the shutdown must NOT skip the socket close.** `mt5_client.py:897-906`
   already documents that the two are separate concerns and that a raising shutdown must not
   skip the socket close. The fenced path must honour the same rule, or every abandoned
   restart leaks a socket — trading one leak for another.
2. ⚠️ **`self._closed = False` at line 886 must be undone on the fenced path.** Otherwise a
   client the caller has already given up on is left latched-open with a live fresh socket,
   and `aclose_exchange`'s `client.close()` (which is exempt from the fence, and may already
   have run) will never close it. This is a *new* leak the fence itself would introduce.
3. ⚠️ **The fresh connection opened at line 883-885 must be disposed on the fenced path.**
   WR-01 forces reconnect-before-dispose; on the fenced path that reconnect is dead weight.

### Interaction with `_mt5_bounded_restart`'s swallow

`mt5_concurrency.py:121` is `except (asyncio.TimeoutError, Exception)` — it swallows
everything with a WARNING. So an `Mt5SessionAbandoned` raised from a restart that is still
being awaited is already handled and produces no new caller-visible behaviour. On the
abandoned path nobody is awaiting at all and the raise is discarded by asyncio (§Q5/§Q7). In
both cases **the WARNING log is the only signal that reaches an operator** — which is why
the fence must log, not merely raise.

### Consequence for the existing shutdown roster

`PERMITTED_SHUTDOWN_SITES` (`test_mt5_shutdown_roster.py:59-61`) is `{("services/mt5_client.py",
"restart")}` and the derivation reports the OUTERMOST enclosing def, so moving the
`stale.shutdown()` call inside an `if`/`else` within the same closure changes nothing there.
✅ No roster edit required. `TEARDOWN_BARE_REFERENCE_SITES` is also unaffected — no new bare
`.shutdown` / `.restart` reference is introduced by the shape above.

pins the 5.x line as load-bearing wire compatibility with the Wine-side mt5linux server).
Downloaded and read in-session. [VERIFIED: rpyc 5.2.3 source]

### What `sync_request_timeout` actually bounds

```python
# rpyc/core/protocol.py:480-489
def sync_request(self, handler, *args):
    timeout = self._config["sync_request_timeout"]
    _async_res = self.async_request(handler, *args, timeout=timeout)
    return _async_res.value
```

```python
# rpyc/core/async_.py — AsyncResult.wait()
while not (self._is_ready or self.expired):
    self._conn.serve(self._ttl)
if not self._is_ready:
    raise AsyncResultTimeout("result expired")
```

`AsyncResultTimeout` is `rpyc.lib.compat.TimeoutError`, which on Python ≥ 3.3 **is the
builtin `TimeoutError`** (`rpyc/lib/compat.py`). Note that `asyncio.TimeoutError` is also an
alias of builtin `TimeoutError` on Python ≥ 3.11 — so an rpyc expiry inside a `to_thread`
body is `isinstance(exc, asyncio.TimeoutError)`. It is nonetheless caught and converted by
`Mt5Client._guarded_read` into a scrubbed `Mt5ClientError` before it can reach any caller's
`except asyncio.TimeoutError` arm, so no existing arm is mis-routed today. ⚠️ Worth knowing
before anyone "simplifies" `_guarded_read`.

### Q5.a — Does an abandoned in-flight rpyc call complete server-side?

**Yes.** `set_expiry` sets a purely *client-side* TTL on the wait loop. Nothing in
`AsyncResult`, `Connection.sync_request` or `Connection._async_request` sends a cancellation
to the peer; there is no cancel opcode in `rpyc/core/consts.py`'s handler set for an
in-flight request. The `ThreadedServer` thread that picked up the `MSG_REQUEST` runs the
remote `eval` to completion regardless of what our side does.

⭐ **Consequence for the design: the epoch fence cannot un-send a call that is already on the
wire.** In finding #5, if the zombie has *already dispatched* `stale.shutdown()` when the
lease releases, the pipe dies for the next holder and no fence can prevent it. The fence
prevents the far more common case — the zombie sitting on an earlier round-trip and reaching
the shutdown *after* the release. That is a real, honest limit and the plan should say so
rather than claim the class is 100% closed. It is also the reason the existing
`_assert_expected_login` login-bracket must stay: prevention is not a licence to delete the
detection (`routers/exchange.py:599-605`).

### Q5.b — Does closing the transport under a running call raise on the zombie thread?

**Yes — but only for a call already in flight, and it is not sufficient.**

```python
# rpyc/core/protocol.py:191-207  Connection.close()
self._closed = True
self._async_request(consts.HANDLE_CLOSE)
finally: self._cleanup(_anyway=True)        # → self._channel.close() → stream.close()
```

```python
# rpyc/core/stream.py  SocketStream.close()
self.sock.shutdown(socket.SHUT_RDWR)
self.sock.close()
self.sock = ClosedFile                      # ClosedFile.fileno() raises EOFError
```

A thread parked in `Connection.serve()` → `channel.poll()` → `Stream.poll()` → `self.fileno()`
either (a) is woken by the `SHUT_RDWR` and then hits `ClosedFile` on `recv()`, or (b) calls
`fileno()` after the swap and gets `EOFError("stream has been closed")` directly. Either way
`serve()`'s `except Exception` re-raises it, and `sync_request` propagates `EOFError`.

⛔ **This does NOT make the epoch redundant.** Three independent reasons:

1. **#6a and #6b have no transport to close.** The zombie is *inside* `Mt5Client.__init__`'s
   blocking connect. The socket it will leak does not exist at the moment of abandonment —
   `routers/exchange.py:486` still holds `client = None`, and the `finally` at `:935` guards
   on exactly that. You cannot close a socket that has not been opened yet.
2. **`restart()` deliberately swaps in a FRESH connection before disposing the stale one**
   (`mt5_client.py:880-885`, the WR-01 ordering). Closing "the client's transport" from
   outside would close the *fresh* one and leave the zombie driving `stale` — the exact
   inverse of the intent.
3. **The damage in #5 is server-side, not socket-side.** `mt5.shutdown()` is a request that
   executes on the shared `MetaTrader5` instance. Closing our socket a microsecond later
   does not un-execute it.

Conversely, the epoch alone is not sufficient to fix #6's leak either (§Q-1). The two
mechanisms are complementary, and neither subsumes the other.

### Q5.c — rpyc classic is not concurrent-request-safe

`Connection.serve_threaded`'s own docstring (`protocol.py:435-444`) records the caveat:
*"using non-immutable types that require a netref to be constructed to serve a request, or
invoking anything else that performs a sync_request, may timeout due to the sync_request
reply being received by another thread serving the connection … issue #345."* Replies are
routed by `seq` to `_request_callbacks`, so a reply reaches the *right* `AsyncResult`, but
the thread that happened to serve it may then expire waiting for its own. `Mt5Client.restart`
already cites this at `:838-840`. The fence reduces exposure by keeping a zombie off the
connection for its second and subsequent calls; it does not eliminate it.

## Q7 — What can this break

The fence introduces a new refusal path with a **plain `Exception` subclass**. Following the
codebase's own thrice-stated rule (`Mt5TerminalBusyError` at `mt5_concurrency.py:190-204`,

`services/ingestion/mt5.py:326-340` already shows an author deliberately dodging those words
in a message that might get classified. Keep `Mt5SessionAbandoned`'s message free of them
— "abandoned … terminal" contains `terminal`.

## Common Pitfalls

### Pitfall 1: Putting the epoch registry in `mt5_concurrency.py`
**What goes wrong:** circular import, or a lazy import on the hot path of every round-trip.
**Why:** the dependency is one-way `mt5_concurrency → mt5_client` (`:36`), pinned by
`mt5_concurrency`'s own leaf-module docstring.
**Avoid:** registry in `mt5_client.py`; `mt5_terminal_lease` imports the bump.
**Warning sign:** an `import` statement inside a `Mt5Client` method body.

### Pitfall 2: Stamping the epoch at construction
**What goes wrong:** the derive and holdings jobs build their client in preflight, outside
the lease. An unrelated lease release between preflight and acquire fences a legitimate read.
**Avoid:** `self._epoch: int | None = None`; bind on first touch.
**Warning sign:** `self._epoch = _mt5_epoch_for(...)` appearing in `__init__` for the method
fence (as opposed to the separate, deliberate `__init__` snapshot for the #6 leak — different
mechanism, different variable; do not conflate them).

### Pitfall 3: Bumping on acquire instead of release
**What goes wrong:** the zombie is fenced only when somebody else happens to acquire; in the
uncontended case (the common one) it keeps driving the terminal indefinitely.
**Avoid:** bump in the lease's `finally`, before `lock.release()`.

### Pitfall 4: Fencing `close()` / `release()` / `_teardown_transport`
**What goes wrong:** the release path in `routers/exchange.py:935-948` and the `finally` in
`services/ingestion/mt5.py:384-389` stop closing their sockets — an rpyc leak, a Pitfall-6
regression, and a WEDGE-01-adjacent failure.
**Why it is safe not to fence them:** since D-35 they touch nothing shared; they close OUR
socket only (`mt5_client.py:754-793`).
**Warning sign:** the ast roster reporting `close`/`release` as unguarded and someone
"fixing" it.

### Pitfall 5: Checking the epoch only at `restart()` entry
**What goes wrong:** finding #5 is not fixed — the entry check passes and the late
`stale.shutdown()` still lands under the next holder.
**Avoid:** the second check immediately before `stale.shutdown()` (§Q4).

### Pitfall 6: A fenced restart that skips the socket close, or leaves `_closed = False`
**What goes wrong:** two new leaks introduced by the fix (§Q4, items 1-3).

### Pitfall 7: `Mt5SessionAbandoned` subclassing `Mt5ClientError`
**What goes wrong:** `classify_mt5_login_error` absorbs it into `auth` / `wrong_server` and a
working key is told its credentials or broker server are wrong — the exact accusation class
`Mt5TerminalBusyError`'s docstring exists to make structurally impossible.

### Pitfall 8: Forgetting the epoch registry in the five test-reset fixtures
**What goes wrong:** a leaked epoch fences a later test's legitimate client under
`-n auto --dist loadgroup` — a sixth flake mechanism.

### Pitfall 9: Patching a re-exported constant
**What goes wrong:** the test is a silent no-op and pays the real bound while still passing.
**Avoid:** patch the module that READS it (§Q6 table). This is a documented past defect
(`test_mt5_derive_branch.py:869-877`).

### Pitfall 10: An unbounded `Event.wait()` in a D-37 test
**What goes wrong:** `asyncio.run` joins the default executor for up to `THREAD_JOIN_TIMEOUT
= 300` seconds. A five-minute CI stall instead of a red.

### Pitfall 11: Assuming the raise is loud
**What goes wrong:** `asyncio.futures._copy_future_state` discards a cancelled future's
exception, so a fenced zombie raises into the void. D-36's "LOUD" requirement is only met by
logging at the fence.

### The fence, in the sink

```python
# services/mt5_client.py

class Mt5SessionAbandoned(Exception):
    """WIZFORM-ABANDON / D-36 — this client's caller gave up on it (its
    `asyncio.wait_for` fired) and the terminal lease it was operating under has
    since been released. Touching the shared session now would drive a terminal
    that belongs to somebody else.

    Deliberately a PLAIN ``Exception``, NOT an ``Mt5ClientError`` subclass — the
    same discipline as ``Mt5TerminalBusyError`` and ``Mt5AccountMismatchError``,
    and for the same structural reason: the credential classify/stamp arms match
    on ``Mt5ClientError``, so an abandoned session that inherited from it could be
    absorbed into a USER-ATTRIBUTED verdict and blame a working key for our own
    abandonment.

    ⛔ Its message names a STAGE and nothing else — no host, port, terminal key,
    login, password or broker server, and none of
    ``mt5_validation._WRONG_SERVER_TOKENS`` / ``_AUTH_TOKENS``, so that even a
    future caller that mis-routes it into ``classify_mt5_login_error`` cannot
    produce a user-blaming verdict.
    """

    def __init__(self, stage: str) -> None:
        self.stage = stage
        super().__init__(f"MT5 session abandoned before {stage}")
```

```python
    def _assert_live(self, stage: str) -> None:
        """D-36 — refuse a session touch whose caller has already unwound.

        ⭐ The epoch is bound LAZILY, on the FIRST touch, not at construction.
        `job_worker._make_mt5_session` builds the client in PREFLIGHT — outside and
        before the lease — so a construction-time stamp would be compared against a
        generation that an unrelated holder may legitimately have bumped in between,
        and a perfectly good derive read would be refused. The first touch always
        happens under the held lease; that is the generation this client belongs to.

        ⭐ It LOGS as well as raising. `asyncio` discards the exception of a thread
        whose future was already cancelled (`asyncio.futures._copy_future_state`
        returns early on a cancelled destination), so on the abandoned path the
        raise reaches nobody. The WARNING is the only signal an operator ever sees.
        """
        current = _mt5_epoch_for(self.terminal_key)
        if self._epoch is None:
            self._epoch = current
            return
        if self._epoch == current:
            return
        logger.warning(
            "Mt5Client: refusing %s — this session was abandoned by its caller and "
            "the lease has since been handed on (WIZFORM-ABANDON / D-36).", stage,
        )
        raise Mt5SessionAbandoned(stage)
```

Each fenced method then opens with one line, e.g.:

```python
    def account_info(self) -> dict[str, Any]:
        self._assert_live("account_info")
        info = self._guarded_read(self._mt5.account_info, stage="account_info")
        ...
```

⚠️ **Placement matters for the roster and for telemetry.** Put `_assert_live` *outside*
`_timed`/`_guarded_read` — a refusal is not a round-trip and must not enter the D-32
`duration_ms` population, or Phase 155's histograms acquire a spike of ~0ms events that were
never MT5 calls.

### ⭐ Q-1 (✅ RESOLVED 2026-08-11 — founder-approved): how to close finding #6

> **Resolution: NEITHER of the two options below — a third mechanism.** `CONTEXT.md`
> § *D-36 AMENDED 2026-08-11* records the founder-approved answer: a **lease-occupancy
> `ContextVar`** fences CONSTRUCTION. `asyncio.to_thread` copies the caller's
> `contextvars.Context` at spawn, so an abandoned thread carries the OLD occupancy token
> while the registry moves on; a preflight build holds no lease, therefore carries no
> token, therefore is exempt **structurally** — which removes the false positive that made
> the construction-time epoch snapshot (recommended below) need two opt-in call-site edits
> and a hand-typed pin. Implemented by plan 01 Task 1 (the ContextVar + helpers) and
> plan 02 Task 2 (`__init__`'s participation); plan 02's `must_haves.truths` cites this as
> "Open Q-1 RESOLVED". ⛔ The `fence_construction=True` opt-in below is REJECTED.
> ⚠️ The honest residue is recorded in plan 02's objective: a construction that COMPLETES
> between the `wait_for` firing and the lease's bump passes both checks and still leaks one
> socket. The fence narrows the window; it does not close it to zero.

**What we know:**
- The method-level epoch fence **does not** fix #6. The abandoned thread is inside
  `Mt5Client.__init__` and makes no subsequent session call; there is no method for a guard
  to sit in front of. `routers/exchange.py:486` (`client = None`) and `:935`
  (`if client is not None:`) are the exact reason the router's `finally` releases nothing;
  `services/ingestion/mt5.py:200-210`'s own comment says the connect sits outside the
  close-`finally` because *"there is no client to close yet."*
- The harm is a **leaked rpyc socket** (an accepted connection + a server thread + a
  `MetaTrader5` reference on the gateway), not a correctness hazard. Slow FD exhaustion.
- The only sink-side mechanism that closes it is **construction-time self-disposal**:
  snapshot the epoch before `connect(...)` (`mt5_client.py:457`), re-read after, and if it
  moved, `_teardown_transport(self._mt5, ...)` and raise.
- ⛔ A caller-side "publish the client into a mutable holder from the worker thread" fix does
  **not** work: the caller's `finally` runs immediately on timeout, seconds before the
  zombie could append. Ruled out, mentioned only so nobody re-proposes it.

**What's unclear — the tradeoff, honestly:**
The two *unleased* preflight constructions (`job_worker._make_mt5_session:969`, reached from
both preflights) would be refused if any lease released during their connect window. The
worker is sequential and the router is interactive, so an interactive validate finishing
during a worker preflight connect is entirely plausible. Cost of a false positive: **one
retried job** (`classify_exception` → `"unknown"` → retried; no user-blame stamp). Cost of
not taking the check: **a permanent socket leak on every connect-stage timeout**, forever.

**Recommendation (mine, for the planner to accept or overturn):** take the
construction-time check and pay the rare retry — a retry is cheap and self-healing, a leak is
neither. But make it a **separate task with its own test and its own line in the plan**, so
the false-positive tradeoff is a recorded decision rather than a side effect.

**The alternative worth putting on the table:** an explicit opt-in — `Mt5Client(...,
fence_construction=True)` passed only at the two *leased* construction sites
(`routers/exchange.py:515` and `services/ingestion/mt5.py:100`). Zero false-positive risk,
two one-keyword call-site edits, and it needs a pin so a third leased site cannot forget it.
⚠️ **That pin cannot be a lexical enclosure predicate**: `routers/exchange.py`'s construction
lives inside `_connect_and_probe`, a *nested* coroutine, while the `async with
mt5_terminal_lease` is in the enclosing function — and `_Scan._visit_function`
(`test_mt5_shutdown_roster.py:194-203`) resets lease depth at every function boundary. The
scanner would (correctly, conservatively) report it as NOT lease-enclosed. So the pin must
be a hand-typed `(relpath, enclosing def)` set with a vacuity floor, in the shape of
`PERMITTED_SHUTDOWN_SITES`. That is more machinery, and it is the machinery-vs-false-positive
axis the planner is choosing on.
