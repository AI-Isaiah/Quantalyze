**D-03 — the criterion-3 freshness column is `max(date)` inside `strategy_analytics.returns_series`,
conjoined with `computation_status`.** Measured, with every rejected candidate measured too:

| Candidate | Verdict | Measurement |
|---|---|---|
| `api_keys.last_sync_at` | REJECTED | advanced daily by key-scoped jobs even with zero trades — the liar that hid this bug |
| `strategy_analytics.computed_at` | REJECTED | `sync_strategy_analytics_status` writes `computed_at = now()` in ALL arms including the `failed` arm (`20260710150000` :125/:179/:199) — reproduces the same lie one column over |
| `strategy_analytics.computing_started_at` | REJECTED | stuck-row reap anchor; cleared to NULL on exit (`job_worker.py:2594`) |
| `strategy_analytics_series.computed_at` | REJECTED **as the freshness signal**, ADOPTED as plan 02's attempt-cooldown input | written only by `upsert_strategy_analytics_series_batch` (`20260428120919:218-223`), so no status transition moves it — but it is a *write* timestamp: it advances when a run completes even if the run produced no new day |
| **`max((e->>'date')::date)` over `strategy_analytics.returns_series`** | **ADOPTED** | written only by the analytics runner's metrics payload (`metrics.py:1467`, `analytics_runner.py:1595`); the status bridge writes only `computation_status`/`computation_error`/`computed_at`; the terminal-failure stamp (`job_worker.py:2588-2602`) writes status columns and `metrics_json_by_basis`, never `returns_series`. It advances if and only if a real analytics run persisted a later day. |

`returns_series` shape is `[{date:'YYYY-MM-DD', value:float}, …]` (`metrics.py:910-913`) and
`cap_data_points` truncates keeping the most recent (`transforms.py:395-399`), so the tail is the
newest day.

**D-04 — status success set is `('complete','complete_with_warnings')`.** All 5 live ledger rows
are `complete_with_warnings` (CONTEXT census); `status = 'complete'` alone marks every healthy
ledger strategy broken.

**D-05 — the view is the SINGLE SQL home of the ledger venue literal set.** Plan 02's fan-out
selects from this view and declares no venues of its own; plan 02's drift gate pins this one list
against `_LEDGER_BACKED_SOURCES` (`long_fetch.py:63`) and separately asserts the fan-out file
contains no venue literals at all. Per D-02 (CONTEXT D2) the set is scoped off ledger-backed-ness,
never off absence from `EXCHANGE_CLASSES` — deribit is in `EXCHANGE_CLASSES`, so absence-scoping
silently drops it.

**D-06 — the view resolves venue via BOTH `strategies.api_key_id` AND `strategy_keys`.** Measured
at `finalize-wizard/route.ts:1177,1388-1392`: a multi-key composite has `api_key_id = NULL` and a
strategy with `api_key_id` set is definitively single-key — the two are mutually exclusive. A view
joining only `api_key_id` is therefore blind to every composite, and the ONLY deribit strategy in
PROD is a composite: deribit would be invisible in the very surface built to observe it.

Define `public.ledger_refresh_staleness`, one row per ledger-backed strategy, with these columns:
`strategy_id`, `is_composite`, `exchanges` (sorted distinct TEXT[] of the strategy's venues),
`has_mt5_member`, `computation_status`, `analytics_computed_at`, `series_written_at`,
`last_return_date`, `days_since_last_return`, `is_stale`, `stale_reason`.

Venue resolution per D-06: build the `exchanges` array as the sorted distinct union of the venue
of `strategies.api_key_id` (when set) and the venues of that strategy's `strategy_keys` members
(when present). `is_composite` is TRUE iff the strategy has at least one `strategy_keys` row.
`has_mt5_member` is TRUE iff mt5 appears in `exchanges`. Restrict the view's rows to strategies
whose `exchanges` array OVERLAPS the ledger venue literal array — this array is the single SQL
home of the venue set per D-05, and it must carry a comment naming
`analytics-service/services/ingestion/long_fetch.py` as the constant it mirrors and naming the
plan-02 drift gate that fails CI on divergence.

`last_return_date` per D-03: a CROSS JOIN LATERAL taking the max of the `date` field over
`jsonb_array_elements` of `strategy_analytics.returns_series`. Two mandatory guards, both
fail-toward-stale: normalise a non-array `returns_series` to an empty array inside a CASE before
handing it to `jsonb_array_elements` (a set-returning function on a scalar raises and would break
the view for every reader), and filter elements whose `date` does not match a four-two-two digit
date pattern before casting (a garbage element must not raise; dropping it makes the row look
staler, never fresher).

`series_written_at` is the `strategy_analytics_series` row's own write timestamp for the
`daily_returns_grid` kind. It is INFORMATIONAL here — label it in a column comment as the
attempt-recency signal plan 02 uses for its cooldown, explicitly NOT the freshness verdict.
`analytics_computed_at` is likewise informational and its column comment must say it is re-stamped
on every job transition and is why this phase does not key on it.

`is_stale` is TRUE when ANY of: no `strategy_analytics` row exists; `computation_status` is not in
the success pair from D-04; `last_return_date` IS NULL; `last_return_date` is older than the
staleness threshold. `stale_reason` returns which of those fired, as a short text token, so a
fresh-but-failed row is visibly distinct from a genuinely fresh one.

Staleness threshold: 4 days. Write the derivation in a header comment — ledger dailies land one
row per calendar day, but MT5 is a traditional venue with no weekend bars, so a Friday close read
on a public-holiday Monday is legitimately 3 days old; 4 days is the smallest whole-day value that
cannot false-alarm on that gap. The live cohort sits at 21 and 36 days (CONTEXT census), so
detection has a wide margin.

Access control: the `public` schema in this project carries default privileges that grant new
relations to `anon` and `authenticated`, and this view enumerates strategies across tenants.
REVOKE ALL on the view from PUBLIC, anon and authenticated, and GRANT SELECT to service_role only.

Self-verifying DO block (house style — RAISE EXCEPTION, never a silent NOTICE-skip): assert the
view exists; assert `information_schema.role_table_grants` returns zero rows for anon and for
authenticated on it; assert the view's row count query executes (SELECT count(*) into a variable)
so a broken lateral or cast is caught at apply time rather than at first read. The block must NOT
mutate anything.
