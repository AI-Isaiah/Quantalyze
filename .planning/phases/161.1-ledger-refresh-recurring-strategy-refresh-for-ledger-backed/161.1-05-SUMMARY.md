## ⛔ A defect in the plan, found by plan 02's executor and FIXED here rather than shipped

Plan 05 defines the FUNCTION BODY as "the text between the fan-out function's dollar-quote
delimiters" and then asks **gate 7** to assert that body "pins `search_path`". It cannot.
`SET search_path` is part of the `CREATE FUNCTION` **declaration** and sits OUTSIDE the
`$fanout$` delimiters, as it does in every SECDEF function in this repo. Written as
specified, gate 7 would have been **RED against a perfectly correct file**.

**Fix:** a fifth region — the **DECLARATION PRELUDE**, `CREATE … FUNCTION …` through
`AS $fanout$` — with its own floor (80 chars) and its own sentinel (the function's own
name). Gate 7 reads that.

**Both directions proven, as the orchestrator required:**

| Direction | Observation |
|---|---|
| GREEN on a correct file | the full 21-test run passes at HEAD with the migration untouched |
| RED when the thing is actually gone | N6 — `SET search_path = public, pg_catalog` deleted from the declaration ⇒ `the fan-out is SECURITY DEFINER without a pinned search_path` |

### The four observations that are load-bearing rather than routine

**N2a and N2b are the whole point of the file.** In both, gate 6's *negative* assertion
(`test_verdict_rejects_every_write_timestamp`) failed **with the anti-vacuity floor's
message**, not with a green tick. That is the property the plan demanded and the one that
is easy to claim without checking: an absence assertion over an empty string passes, and
a file of absence assertions with a broken extractor is 21 green tests proving nothing.

**N9 is the reason gate 3a asserts a match-count FLOOR before it scans.** With the glob
matching zero files, the loop iterates over nothing and "no file contained a schedule"
reads exactly like success. The floor fired instead.

**N8 is the reason gate 3b exists at all.** N7 (a schedule inside the fan-out migration)
was caught by 3a and **3b stayed silent** — correctly, since the file count is still 1.
N8 (a schedule from a migration whose filename lacks the phase token) was caught by 3b and
**3a stayed silent** — correctly, since that file is outside its glob. The two scans are
genuinely complementary, and neither alone would have covered the other's case. This is
also the concrete demonstration that D-18's "never enumerate filenames" is not pedantry:
an enumeration of the two known files would have missed N8 exactly as 3a did.

**N13 is the subtle one.** Lowering `LIMIT` to `2` leaves `test_per_tick_limit_is_bounded`
**GREEN** (2 ≤ 4). Only `test_limit_is_strictly_greater_than_the_cap` fires. Had the
strict comparison been written `>=`, the neutering would have gone entirely green and
plan 02's behavioural arm G would have silently stopped discriminating the cap from the
limit — a bound pinned only by a test that cannot fail.

### Auto-fixed issues

**1. [Rule 1 — Bug in the plan's own specification] Gate 7 was specified against a region that cannot contain what it asserts**

- **Issue:** see the defect section above. Gate 7 as written would be RED on a correct file.
- **Fix:** the DECLARATION PRELUDE region, with its own floor and sentinel.
- **Verification:** GREEN at HEAD; RED under N6.
- **Committed in:** `a6171709`

**2. [Rule 2 — Missing critical functionality] The verdict region's own rule is wider than the plan's two tokens**
- **Found during:** Task 1, reading the marker comment plan 01 wrote.
- **Issue:** the plan bans "the two rejected timestamp columns" from the is_stale expression. The region's own marker comment states the rule as *"No write timestamp of any kind may appear below until the END marker"*, and plan 01's D-03 rejects a **third** candidate for the same reason: `series_written_at` advances whenever a run COMPLETES even if it produced no new day. Keying the verdict on it is the Phase-106 janitor bug in its third form, and the plan's two-token ban would not have caught it.
- **Fix:** `_REJECTED_FRESHNESS_TOKENS` carries all three. `computed_at` covers both `strategy_analytics.computed_at` and the view's `analytics_computed_at` alias.
- **Committed in:** `a6171709`

**3. [Rule 3 — Blocking] A naive statement terminator truncated the VIEW BODY to prose**
- **Found during:** Task 1, while probing the extractors before writing any assertion.
- **Issue:** locating the CREATE VIEW statement's end with `text.find(";")` stops at *"catches single-key strategies;"* — a semicolon inside a **comment**, 584 characters in. The extracted "view body" was almost entirely prose: the venue array was still inside it (so gate 1 would have passed), but the status-set regex found **zero** matches and the verdict markers were absent. Gate 9 and gate 6 would have been broken. **Measured, not theorised** — this is what the first probe returned.
- **Fix:** `_scan_sql()`, a comment-aware scanner that also skips single-quoted literals (with `''` escapes) and dollar-quoted blocks, so neither a `;` in prose nor a `;` in a string can terminate a statement early. The same scanner produces the comment-stripped text.
- **Note:** the anti-vacuity floor would have caught this had it slipped through — the truncated body is 584 characters against a 1200 floor. That is the floor doing its job on a real defect rather than a hypothetical one.
- **Committed in:** `a6171709`

### Non-fix design choices worth recording

**Positive assertions read comment-STRIPPED text; negative assertions read RAW text.** The
repo rule is *prose must neither satisfy nor trip a mechanical gate*. Stripping comments
for positives means a sentence can never satisfy a gate; keeping raw text for negatives
means a venue name or a schedule call cannot hide in a comment. The asymmetry is safe in
both directions: a broken strip yields an empty string, on which a positive assertion
**fails** (never silently passes), and the negatives are region-scoped precisely because
plan 01 and plan 02 engineered their files for it — the view's rejected timestamps live
OUTSIDE the verdict markers, and the fan-out's whole D-01/D-05/D-09 narrative lives in the
file HEADER, outside the dollar quotes.

**The guard region ends at the first following line indented `<=` the `async def`.** The
plan says "the next sibling definition at the same indentation", but what actually follows
`_stamp_strategy_analytics_failed` is an annotated assignment (`denominator_config: … =
None`), not a `def`. The indentation rule is exact and does not depend on what kind of
statement follows; measured, it yields 7685 characters ending exactly at that comment.

**Gate 2's ban list is derived, not hand-typed.** `_banned_venue_names()` is
`_LEDGER_BACKED_SOURCES | {"binance", "okx", "bybit"}`, so adding a fourth ledger venue
extends the ban automatically instead of leaving a hole a hand-typed tuple would have.

**Gate 8 carries a second assertion the plan did not ask for.** The guard must reference
`STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES` by name. A status list inlined inside the
guard would be a *third* spelling of the success set, and neither gate 9 (which compares
the view against the constant) nor the view's own predicate could see it drift.

**Gate 2's failure message is written from D-17 and carries no false claim.** It cites the
ROADMAP fence and the measured hand-copied-mirror incident, and states explicitly that it
does **not** rest on `src/lib/strategyGate.invariant.test.ts` banning venue literals across
TS — because measured at HEAD, that file's `BANNED_VENUE_LITERALS` is scoped to
`src/lib/strategyGate.ts` alone (`:64`).

## The self-exclusion trick, and why it must survive review

The pg_cron search tokens and the fan-out's function name are assembled by **runtime
concatenation** (`"cr" + "on" + "." + "sched" + "ule"`), with a comment saying so. This is
deliberate and load-bearing, not an obfuscation:

- gate 3b **counts files** containing the fan-out's name. A self-match would be
  indistinguishable from a real second definition — and the fix a future reader would
  reach for is "exclude the test file", which then also excludes any real offender that
  happens to live nearby.
- any future widening of gate 3a from `supabase/migrations/` to the repo, or any reviewer
  grepping "is there a schedule anywhere?", would otherwise hit the very file whose job is
  to prove there is none.

The comment above the constants says **⛔ KEEP THE CONCATENATION. Do NOT "clean this up".**
