<planning_decisions>
**D-07 — the recurring unit is `derive_broker_dailies` in strategy-mode, not `process_key_long`.**
Criterion 1 says "via the strategy-keyed `process_key_long` chain"; `JOB_CHAIN_FOLLOW_ON`
(`job_worker.py:521-529`) is this repo's canonical name for that chain and its ledger-backed edge
is `JOB_CHAIN_FOLLOW_ON["process_key_long"][0]` = `derive_broker_dailies`, which auto-chains to
`compute_analytics_from_csv`, which stamps `strategy_analytics`. Enqueuing the chain HEAD instead
is a provable no-op: `long_fetch.py:154` returns DONE on `status == "published"` and `:193` returns
DONE on the whole advanced-status set, and every onboarded strategy is `published` — it would ship
a green job, a fresh `compute_jobs` row, and an untouched `strategy_analytics`. The head also
decrypts and re-encrypts credentials and mints a `published` verification row per cycle into a
provenance table. Strategy-mode derive is also documented as the arm that DOES stamp
`strategy_analytics` (`job_worker.py:2384-2388` records key-mode as the arm that does not).

**D-08 — two locks, both with real readers.** Lock A: this migration contains zero pg_cron
registration calls; activation is one founder LIVE op per the WORKER-03 precedent
(`flipretry-derived-equity-go-live.md:171`), because `supabase/migrations/**` auto-applies to PROD
on merge and a silently-skipped worker deploy then recreates the v1.11 wedge verbatim. Lock B: the
function's first statement reads the `app.ledger_refresh_enabled` database setting and returns 0
unless it is exactly `true` — fail-closed on unset, matching the fail-closed idiom in
`services/closed_sets.py` and the existing `app.*` setting convention.
⚠️ RESEARCH proposed Lock B as a Python `ledger_refresh_enabled()` helper in `closed_sets.py`. That
is REJECTED here: with a SQL enqueue there is no Python code path to read it, and this repo has
already been bitten by a flag nothing reads (`computation_status='stale'`, and the inert
`process_key_unified_backbone` row) — "a mechanism that looked like one". Lock B lives where the
enqueue lives.

**D-09 — the bound, derived not guessed.** Worst case one `derive_broker_dailies` job is 900 s
(`job_worker.py` per-kind ceiling, mirrored at `:261`); the worker claims in batches of 5 but
dispatches sequentially (`main_worker.py:606,647,742`). At an hourly tick, n × 900 s must stay
under 3600 s or backlog grows monotonically ⇒ **n = 4** per tick. Per-venue cap **k = 2** because
MT5 serialises on ONE terminal registry (`services/mt5_concurrency.py`) — without the partition an
MT5-heavy book spends every tick on one serialised venue and starves deribit/sfox. Do NOT copy the
reconcile sweep's LIMIT 25: that sweep's follow-on is pure-DB. Cooldown **20 hours** on prior
attempt: the data granularity is daily, so one refresh per strategy per day is the correct steady
state, and an attempt-based cooldown (unlike a success-based one) also bounds a permanently-failing
strategy to ~1 job/day instead of 24. `compute_jobs` terminal-row retention is 30 days
(`20260515113853:198`), comfortably longer than the cooldown, so the cooldown cannot silently void.
⚠️ Per CONTEXT the live cohort is 5 strategies — these bounds are shape, not volume. Do not
over-engineer them further.

**D-10 — no `FOR UPDATE SKIP LOCKED` in the candidate CTE.** Postgres refuses `FOR UPDATE`
alongside a window function, and the per-venue cap needs `row_number() OVER (PARTITION BY …)`.
Concurrency is already covered by the advisory lock plus `enqueue_compute_job`'s in-flight dedupe
plus the `compute_jobs_one_inflight_per_kind_strategy` partial unique index. Say so in a comment so
a later reader does not "restore" a lock clause that cannot compile.
</planning_decisions>
