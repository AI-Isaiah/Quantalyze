**D-11 — the composite arm is a SEPARATE function, not a second branch inside the single-key
fan-out.** Three reasons, each measured: the kinds differ (`stitch_composite` versus
`derive_broker_dailies`); the CHAIN SHAPES differ, not merely the ceilings — `stitch_composite` is
chain-terminal (`JOB_CHAIN_FOLLOW_ON`, `job_worker.py:528`) so one enqueue costs one 20-minute
handler ceiling (`TIMEOUT_PER_KIND`, `:502`) and nothing more, whereas plan 02's
`derive_broker_dailies` (15 minutes, `:501`) chains a `compute_analytics_from_csv` hop after it
(10 minutes, `:490`; the edge is at `:526`), so the two arms' bounds are NOT one formula with a
different constant and copying plan 02's integer would import a derivation that does not apply
here; and separate functions mean the founder can schedule, bound and roll back one without
touching the other, which matters because the composite path carries per-member exchange crawls and
was the subject of the stitch-composite crawl-bounding incident.

**D-12 — `stitch_composite` is the right unit and already exists.** It is a registered
strategy-scoped kind (`20260710130000`, admitted by both compute_jobs CHECKs), it fans over
`strategy_keys` members by seq, and it writes the headline `strategy_analytics` row DIRECTLY in one
atomic upsert (`job_worker.py:5350`, `:7177`) rather than chaining — `JOB_CHAIN_FOLLOW_ON` records
it as chain-terminal. So it reaches `strategy_analytics`, which is what criterion 1 requires.

**D-13 — the mt5 exclusion is on MEMBERSHIP, not on the strategy's headline venue.** A composite
with any mt5 member is excluded, because D-01's deferral is about the MT5 path, and a mixed
composite would drag the MT5 terminal into the composite crawl. The staleness view already exposes
a has-mt5-member flag for exactly this (plan 01, D-06).

**D-14 — the composite handler DOES write `strategy_analytics.returns_series`, which is the only
reason task 3's PASS criterion is reachable. Traced at HEAD, not assumed.** This plan's whole
premise is that a `stitch_composite` run can move `last_return_date`. Plan 01's D-03 table names
the analytics-runner payload as the writer of `returns_series` and reads as exhaustive — it is
not. `run_stitch_composite_job` is a SECOND writer, and if it were not, task 3 could never pass and
this entire arm would be theatre. Each hop measured at HEAD:

| hop | site | what it carries |
|---|---|---|
| 1 | `job_worker.py:6450` | `cash_metrics_json = dict(_cash_basis_result.metrics_json)` |
| 2 | `basis_series.py:296` | `BasisSeriesResult(metrics_json=metrics.metrics_json, …)` — it IS the `MetricsResult` dict, passed through unchanged |
| 3 | `metrics.py:265-269` | that dict is documented to hold the above-the-fold series, `returns_series` named first among them |
| 4 | `job_worker.py:7083` | `headline_payload.update(cash_metrics_json)` spreads it into the headline payload |
| 5 | `job_worker.py:7177` | one `strategy_analytics` upsert on `strategy_id` persists that payload |

⚠️ The in-file comment at `job_worker.py:7071-7072` says that spread carries "metric SCALARS only".
That claim is true only for the narrow thing it was written to defend — the spread cannot clobber
the sibling `series_completeness` key — and false as a description of what is spread. Do not quote
it as evidence that the composite path leaves `returns_series` alone. Plan 01 is being updated
separately to add this row to its D-03 table; do NOT edit plan 01 from here.
