## Summary

The defect is real and its mechanism is exactly as the roadmap describes for **two of the three** ledger venues. `strategy_analytics` for a keyed strategy is only ever written at the end of a `compute_analytics_from_csv` job, and the only edges that reach it are `sync_trades → derive_broker_dailies → compute_analytics_from_csv` (ccxt fill path) and `process_key_long → derive_broker_dailies → compute_analytics_from_csv` (ledger path). `process_key_long` is enqueued in exactly two places, both inside the onboard/resync request handler (`analytics-service/routers/process_key.py:765` and `:1517`) — there is no recurring enqueuer of it anywhere in the tree. The two daily Vercel strategy crons both gate on `FUNDING_EXCHANGES` (`binance`/`okx`/`bybit`), and `cron_sync` defers any venue absent from `EXCHANGE_CLASSES`. mt5 and sfox therefore have **no recurring path to `strategy_analytics` at all**.

**The material disagreement with the roadmap text: `deribit` IS in `EXCHANGE_CLASSES`.** So deribit is *not* deferred at `routers/cron.py:182` — it falls into the ccxt branch of `_sync_single_key`, which fetches fills and, for strategies that received new trades, enqueues `derive_broker_dailies`. deribit therefore has a *partial* recurring path, gated on a predicate that is wrong for a ledger venue (`stored > 0` — deribit returns are settlement cash deltas, not fills, so a deribit account can move materially with zero new fills and never recompute). The three "ledger-backed" venues are asymmetric, and any design that treats them as one deferred branch will silently miss deribit. This changes the shape of the fix and the planner must not inherit the roadmap's uniform framing.

The second load-bearing finding is a trap: **re-enqueuing `process_key_long` for an existing strategy does nothing.** The handler short-circuits on any non-`draft` verification status (`services/ingestion/long_fetch.py:189-198`) and returns `DONE` without running the pipeline. A recurring `process_key_long` would have to mint a fresh `strategy_verifications` draft per cycle, which re-runs a live credential probe (an MT5 terminal login per key per cycle), re-encrypts credentials, and writes one `published` verification row per strategy per cycle into a table that feeds trust/provenance surfaces. The correct recurring unit is the chain's **strategy-keyed tail**, `derive_broker_dailies` in strategy-mode — which is the value `JOB_CHAIN_FOLLOW_ON["process_key_long"]` names as the ledger-backed follow-on, and which auto-chains to `compute_analytics_from_csv`.

**Primary recommendation:** ship a **strategy-scoped SQL fan-out function in a migration with NO `cron.schedule` call**, enqueuing `derive_broker_dailies` (strategy-mode) for ledger-backed keyed strategies whose `strategy_analytics.computed_at` has aged past a derived threshold, bounded by an hourly-cadence × per-tick `LIMIT` × per-venue partition cap; dormancy is two locks (no schedule registered anywhere in the repo + a fail-closed env flag on the worker); activation is one founder `SELECT cron.schedule(...)` LIVE op plus one env flip, documented in a new `docs/runbooks/ledger-refresh-go-live.md` modelled on `sfox-go-live.md`.

### Pattern 1 — Enqueue the chain's **tail**, not its head

**What:** the recurring unit is `derive_broker_dailies` in strategy-mode (`p_strategy_id`, no `p_api_key_id`), which is `JOB_CHAIN_FOLLOW_ON["process_key_long"][0]` — the ledger-backed tail the onboard handler itself selects.

**When to use:** always, for a *refresh*. `process_key_long` is an *onboarding* unit: it validates credentials live, re-encrypts them, and drives a verification state machine.

**Why this satisfies criterion 1 as written:** the criterion says "via the strategy-keyed `process_key_long` chain". `JOB_CHAIN_FOLLOW_ON` is the repo's canonical name for that chain and its ledger edge is `derive_broker_dailies`. Strategy-mode "does NOT enqueue compute_analytics_from_csv and does NOT stamp strategy_analytics" is *key-mode's* documented limitation (`job_worker.py:2385-2388`); strategy-mode is explicitly the arm that does both. The fill path is never touched: strategy-mode derive dispatches by venue and the mt5/sfox/deribit arms are ledger reads, not `fetch_raw_trades`.

⚠️ **Planner must record this reading explicitly** as a decision, because "the `process_key_long` chain" could be misread as "enqueue `process_key_long`". That misreading produces a mechanism that provably does nothing (Pitfall 1).

### Pattern 2 — Two-lock dormancy (the SFOX_ENABLED / WORKER-03 composite)

The repo has two distinct dormancy mechanisms and this phase should use **both**, because each alone has a documented failure mode.

| Lock | Mechanism | Failure mode it closes |
|---|---|---|
| **Lock A — no schedule** | The migration ships the FUNCTION and the VIEW and contains **zero** `cron.schedule` / `cron.unschedule` calls. Activation is one founder statement. | Auto-apply-on-merge cannot start work. This is literally the WORKER-03 rule (`flipretry-derived-equity-go-live.md:171`) and satisfies "the schedule is NOT registered" verbatim. |
| **Lock B — fail-closed env flag** | A `ledger_refresh_enabled()` in `services/closed_sets.py`, byte-shaped like `sfox_enabled_server()`. If the enqueue is ever moved into a Python surface, or if a scheduled tick must be muted without touching pg_cron, this is the kill-switch. | A registered schedule cannot be un-registered fast under incident pressure without a DB op; an env flip + redeploy is the rollback shape both go-live runbooks already use. |

**⛔ Do NOT** put the `cron.schedule` in the migration "but inactive" via `cron.alter_job(active := false)`. It still registers a row, still diverges git from live the moment anyone toggles it, and still fails criterion 2's literal wording.

**Migration safety under auto-apply:** a function with zero callers plus a read-only view changes no prod behaviour on merge. The repo convention (every migration carries a self-verifying `DO` block that RAISEs) is satisfiable without invoking the function. ⚠️ The self-verify block must **not** call the fan-out function as a smoke test — that would enqueue real jobs at merge time.

### Pattern 3 — Staleness observed on `computed_at`, with the known caveat handled

Criterion 3 mandates `computed_at`. It is the right column *for this defect* (a strategy with no jobs at all never advances it), and `last_sync_at` is exactly the liar — it is advanced by `advance_sync_cursor` on the key-scoped path even when zero trades landed, and MT5's `sync_trades` arm reaches that epilogue with `trades = []` by design (`job_worker.py:1416-1418`).

⚠️ **But `computed_at` is not "when analytics were last computed".** `sync_strategy_analytics_status` sets `computed_at = now()` in all three of its arms — including the arm that resolves to `failed`. So a strategy whose refresh jobs keep failing shows a FRESH `computed_at`. The staleness predicate must therefore be:

```
age(now(), sa.computed_at) > <threshold>
  OR sa.computation_status = 'failed'
  OR sa.strategy_id IS NULL          -- no analytics row at all
```

…and the *observability* view should surface `computation_status` beside the age so a fresh-but-failed row is visibly distinct from a genuinely fresh one. Stating this in the plan is what stops the phase shipping a check that is green while the thing it watches is broken.

**Where it lives — the ranked recommendation:**

1. **A read-only SQL view/function in the same migration** (`ledger_refresh_staleness`), returning `(strategy_id, exchange, computed_at, age, computation_status)` for ledger-backed keyed strategies. Zero side effects, safe under auto-apply, queryable by the founder immediately, and the fan-out predicate and the check then read *the same* definition — so the check cannot drift from the mechanism.
2. **Surfaced on an admin route** — `src/app/api/admin/compute-jobs/` is the existing admin operational surface and is triple-gated (same-origin → authed → `isAdminUser`). Founder-visible, not user-visible.
3. **⛔ NOT `/api/health`** — it is public and unauthenticated by design.
4. **A CI gate is necessary but insufficient**: a `supabase/tests/*.sql` arm runs against the TEST project in CI and can never observe PROD staleness. It pins *the shape* of the check (see Pattern 4), not the live condition.

### Pattern 4 — The refresh set is DERIVED from one constant, and pinned by a drift gate

`_LEDGER_BACKED_SOURCES` (`long_fetch.py:63`) is the single authoritative definition. There is deliberately **no TypeScript mirror** — `strategyGate.invariant.test.ts` bans venue literals from the gate precisely because a hand-copied mirror drifted (TS at one venue, Python at three) and cost a funded MT5 account its publish path.

A SQL fan-out necessarily writes the venues as a literal. The repo's answer to exactly this problem is a **cross-language drift gate**, and one already exists: `STRATEGY_ANALYTICS_REAP_THRESHOLD` is a Python constant whose value is embedded in a pg_cron body, and `job_worker.py:534-537` records `the drift gate (plan 142-04) fails CI if the SQL literal and this constant diverge. Change it HERE first.`

**LEDGER-04's pin should therefore be a matched pair:**
- **Positive arm** — read the migration file, extract the venue list from the function body, assert set-equality with `_LEDGER_BACKED_SOURCES`. Falsifiable by deleting `"mt5"` from either side.
- **Behavioural arm** — a `supabase/tests/*.sql` case seeding one stale strategy per venue and asserting three rows are enqueued, plus a **negative control** (a fresh strategy is NOT enqueued). ⚠️ The positive arm alone passes under a body that enqueues *everything*; the negative control alone passes under a body that enqueues *nothing*. Only the pair pins a bound that is present and not over-tight — the exact reasoning `20260819150000` gives for its C5/C5b pair.

⚠️ **Anti-vacuity floor required.** A file-reading gate is green if the file is missing, renamed, or the extraction returns `""`. `strategyGate.invariant.test.ts` handles this with a hand-typed character floor; mirror it.

### Anti-Patterns to Avoid

- **Re-enqueuing `process_key_long`** — returns `DONE` without work (Pitfall 1).
- **Defining the set as "venues absent from `EXCHANGE_CLASSES`"** — silently drops deribit.
- **A second TS venue list** — the MT5-12 drift class.
- **Adding the schedule to the migration** — the WORKER-03 / v1.11 wedge class.
- **A `cron_runs`-only or Sentry-only staleness signal** — the reaper's own migration argues detection of a *writer* bug belongs in a static gate, not a runtime alert; the inverse holds here: detection of a *missing recurring path* belongs in a runtime query, because no static gate can see that prod stopped ticking.
- **Enqueuing for composite strategies** — they need `stitch_composite`, not strategy-mode derive. Exclude via the `strategy_keys` NOT EXISTS conjunct.

## The Fan-Out Bounding Decision

The risk shape named in the invocation is real but its *mechanism today* is not concurrency — it is **queue depth and interactive starvation**.

**Measured topology:**
- The worker claims `"p_batch_size": 5` and dispatches **sequentially** (`for job in jobs:`), one job at a time per process.
- `derive_broker_dailies` has a fixed outer ceiling of 900 s (15 min).
- MT5 serialises on one terminal registry; the batch path queues **unbounded on purpose** (`wait_s=None`), because "bounding it would convert serialization into batch FAILURE".
- With `WORKER_CLAIM_ROLE` at its default `"all"`, a single worker process means terminal contention is already serialised by the dispatch loop — **but it also means a ledger batch and a user's onboarding share one queue.** That is the v1.11 shape: not a crash, a *wait*.

**Decision — four bounds, composed, in this order of importance:**

1. **Staleness gate (primary).** Only enqueue strategies whose analytics have aged past the threshold. This makes the mechanism self-idling: after the first catch-up, steady state is roughly *N strategies per refresh period*, not *N per tick*. It is also the bound that ties the mechanism to criterion 3 — the same predicate that detects the bug drives the repair.
2. **Cadence × per-tick `LIMIT` (the ceiling).** Adopt the sweep's shape: hourly, oldest-first, `FOR UPDATE SKIP LOCKED`, `LIMIT n`. **Derive `n`, do not guess it** — the Phase-106 janitor was reverted for an underived number. The derivation the planner must write down: worst-case one job = 900 s, dispatch is sequential, so `n × 900 s` must stay under the tick interval or backlog grows monotonically. At an hourly cadence that yields `n ≤ 4` in the worst case; a value of `n` with headroom (the sweep chose 25 against a *pure-DB* follow-on, which is why its number is much larger — do not copy the integer, copy the method).
3. **Per-venue partition cap (the MT5 clause).** Because MT5 binds one account per terminal at a time, cap mt5 rows per tick independently — `row_number() OVER (PARTITION BY ak.exchange ORDER BY sa.computed_at) <= k`. Without it, a book that is 90 % MT5 spends every tick on one serialised venue and starves deribit/sfox refresh indefinitely. This is fairness, not safety.
4. **Overlap lock (belt-and-braces).** `pg_try_advisory_lock(hashtext('ledger_refresh_fanout'))`, released on both the normal and exception paths — verbatim shape from `20260717233529:229-258`. Cheap; makes a slow tick unable to double-fan.

**Explicitly considered and NOT chosen:**

| Option | Why not |
|---|---|
| Fixed-hour daily fan of the whole set | This *is* the risk shape named in the invocation. One hour, N jobs, sequential worker, onboarding behind it. Rejected. |
| Random jitter / stagger inside one tick | Adds nondeterminism to a mechanism whose whole value is being observable and testable; a small hourly `LIMIT` achieves the same spreading deterministically. |
| Bounding the MT5 terminal wait | Directly contradicts the in-code decision at `mt5_concurrency.py`: it converts serialisation into batch failure. Do not touch `wait_s`. |
| Relying on `WORKER_CLAIM_ROLE=backfill` isolation | `derive_broker_dailies` **is** in `BACKFILL_KINDS`, so this works *if activated* — but the default is `"all"` and the two-worker cutover (WORKER-01) is a founder op whose live status is unverified. **Name it as a runbook activation-order gate, never as a shipped mitigation.** |
| Queue-depth backpressure only | Good addition, weak alone: it caps concurrent depth but not the *rate* of arrival across a day. Fold it in as a fifth conjunct if cheap (`NOT EXISTS` more than K non-terminal `derive_broker_dailies` rows), but the LIMIT is the real ceiling. |

**Tradeoff, stated honestly:** an hourly small-`LIMIT` cadence means the *first* activation tick does not catch up the whole book — a backlog of B strategies takes `B / n` hours to clear. That is the correct trade (a slow, observable catch-up beats a wedge), but the runbook must say so, and the founder must expect the staleness view to drain over hours rather than minutes.

## Common Pitfalls

### Pitfall 1 — "Recurring `process_key_long`" is a mechanism that provably does nothing
**What goes wrong:** the obvious reading of criterion 1 produces a cron that enqueues `process_key_long` with the strategy's existing `verification_id`. Every job returns `DONE` in milliseconds. The queue looks healthy, the cron log looks healthy, `strategy_analytics` never moves.
**Why:** `run_process_key_long_job` short-circuits on `status == 'published'` *and* on any of `{validated, metrics_captured, encrypted, report_queued, published}`. Every onboarded strategy's verification is `published`.
**How to avoid:** enqueue the chain **tail** (Pattern 1). If the planner nonetheless wants the head, it must mint a fresh `draft` verification per cycle — and then own a live credential probe per key per cycle, credential re-encryption, and one new `published` row per strategy per cycle in a table that feeds provenance surfaces.
**Warning signs:** job durations near zero; `process_key_long.already_published_skip` / `advanced_status_skip` in the worker log.

### Pitfall 2 — Defining the refresh set by "not in `EXCHANGE_CLASSES`"
**What goes wrong:** deribit — the venue the entire ledger pipeline was built for — is excluded from the fix.
**Why:** `EXCHANGE_CLASSES` contains `"deribit": ccxt.deribit`; ledger-backed-ness and ccxt-availability are orthogonal.
**How to avoid:** derive the set from `_LEDGER_BACKED_SOURCES` only.
**Warning signs:** a test fixture list of two venues; any grep of the plan showing `EXCHANGE_CLASSES` in the predicate.

### Pitfall 3 — Scheduling from a migration
**What goes wrong:** merge auto-applies to PROD; if the same merge's worker deploy is silently skipped (Railway skips on red main CI), a schedule starts fanning jobs at a worker that cannot serve them.
**Why:** documented verbatim at `flipretry-derived-equity-go-live.md:171`; it is the v1.11 wedge.
**How to avoid:** Lock A. The migration contains the function and the view and **no** `cron.schedule`.
**Warning signs:** any `cron.schedule` / `cron.unschedule` token in the phase diff. Make this a mechanical gate in the plan, not a review note.

### Pitfall 4 — Treating `computed_at` as "when analytics were computed"
**What goes wrong:** a strategy whose refresh keeps failing shows a fresh `computed_at`; the staleness check reads green while the strategy is broken.
**Why:** `sync_strategy_analytics_status` writes `computed_at = now()` in all three arms, including the `failed` arm.
**How to avoid:** conjoin `computation_status` into both the predicate and the view (Pattern 3).
**Warning signs:** a check that selects only `computed_at`; a view with no status column.

### Pitfall 5 — Enqueuing for a composite strategy
**What goes wrong:** strategy-mode derive requires a single `strategies.api_key_id`; a composite's refresh unit is `stitch_composite`. A wrongly-routed composite is the "silently orphaned" failure the finalize-wizard route already guards against.
**How to avoid:** copy the sweep's exclusion conjunct verbatim (`NOT EXISTS … strategy_keys`).
**Warning signs:** no `strategy_keys` reference anywhere in the predicate.

### Pitfall 6 — A vacuously-green regression pin
**What goes wrong:** LEDGER-04's pin reads a migration file; if the filename moves or the extraction regex misses, it returns an empty set and every absence assertion passes.
**How to avoid:** anti-vacuity floor + matched positive/negative behavioural pair + demonstrate RED by deleting one venue and by neutering the enqueue.
**Warning signs:** a single assertion; no observed-RED evidence in the plan's verification steps.

### Pitfall 7 — Pointer hygiene on a re-registered cron
**What goes wrong:** the repo's convention is that any file naming a cron's registering migration must move in the same commit; a stale pointer keeps a gate green while it guards a body pg_cron no longer runs (`20260819150000` header; `_SWEEP_MIGRATION_NAME`, `_REAPER_MIGRATION_NAME`).
**How to avoid:** because Lock A means **this phase registers nothing**, there is no pointer to maintain at merge — but the *runbook* becomes the pointer, and it must name the migration whose function body the founder's `cron.schedule` will invoke.

## Rejected Alternatives (with reasons)

### A. Vercel cron → new TS route (`/api/cron/refresh-ledger-strategies`)
Structurally the `reconcile-strategies` twin, and the most familiar shape. **Rejected because** it requires a TypeScript ledger-venue list, which is the drift class `src/lib/strategyGate.invariant.test.ts` exists to ban — that file's own header records the incident: the Python set widened to three, TypeScript stayed at one, and a funded MT5 account landed on an unwinnable gate. It also weakens dormancy: a `vercel.json` crons entry is live at deploy, so criterion 2's "schedule NOT registered" would have to be satisfied by *omitting* the entry — making activation a code change and a redeploy rather than a founder LIVE op.
*Revisit if:* the founder wants the Vercel-cron uniformity and accepts a TS drift gate as the mitigation.

### B. Extend `cron_sync`'s deferred branch (`routers/cron.py:182`)
Superficially the root-cause fix, and it has the best answer to criterion 5 (the branch can `import _LEDGER_BACKED_SOURCES` directly). **Rejected because** (i) the deferred branch does not cover deribit, so the fix would need *two* insertion points in the same function for one behaviour; (ii) nothing in the repo registers a schedule for `/api/cron-sync`, so the mechanism's cadence is unverified — building on it means building on an assumption; (iii) extending an already-scheduled tick means dormancy rests on the env flag alone, failing criterion 2's literal "schedule NOT registered"; (iv) a 15-minute cadence is the wrong clock for a 15-minute-ceiling job, forcing the staleness gate to carry the entire bound.
*Revisit if:* OQ-1 confirms `cron-sync` is live and the founder accepts single-lock dormancy — the code delta is genuinely the smallest of the three.

### C. New FastAPI endpoint on analytics-service, scheduled by pg_cron + pg_net
The best answer to criterion 5 (imports the constant; no drift gate needed) and gives the richest bounding options. **Rejected as primary because** activation requires pg_cron **and** pg_net **and** two DB GUCs (`app.analytics_service_url`, `app.analytics_service_key`), whose live configuration is unverified at HEAD — turning a one-statement founder op into a multi-part one with three failure modes, in a phase whose whole point is a safe founder-gated activation. Both in-repo migrations that use this path guard it with `RAISE NOTICE … skipping` when the GUCs are absent, which is the silent-skip convention the newer migrations explicitly reject.
*Revisit if:* OQ-3 confirms both GUCs and pg_net are live on PROD — then C becomes strictly better than the recommendation on criterion 5, and the recommendation's drift gate can be deleted.

### D. Enqueue `process_key_long` recurrently
**Rejected on measurement** — see Pitfall 1. It is not a tradeoff; it is a no-op unless a fresh verification is minted per cycle, and that variant carries a live MT5 login per key per cycle plus provenance-table pollution.

## Open Questions

1. **OQ-1 — Is `/api/cron-sync` scheduled in PROD, and at what cadence?**
   - Known: no migration registers it; ADR-0008 lists it as "Triggered by Mechanism 3"; a code comment says every 15 min; a CHANGELOG line mentions "a Railway probe hitting the path".
   - Unclear: whether a live pg_cron job, a Railway cron, or nothing calls it.
   - Recommendation: founder runs `SELECT jobid, jobname, schedule, active FROM cron.job ORDER BY jobname;` on PROD. Resolves OQ-1, A3, and (with a GUC read) A4 in one op. **Blocking for alternative B only; the recommendation stands either way.**

2. **OQ-2 — Re-measure the staleness census at HEAD.**
   - Known: the roadmap figure is dated 2026-08-24.
   - Recommendation: founder-run read-only query over ledger-backed keyed strategies returning `computed_at` age and `computation_status`. This doubles as the acceptance evidence for criterion 3 and as the sizing input for the `LIMIT` derivation. ⚠️ Report counts only in `.planning/` — no ids.

3. **OQ-3 — Are pg_net and the two `app.*` GUCs live?** Only gates whether alternative C is reconsidered.

4. **OQ-4 — Composite (multi-key) ledger strategies: in scope or explicitly deferred?**
   - Known: strategy-mode derive cannot serve them; their unit is `stitch_composite`; the reconcile sweep excludes them explicitly.
   - Recommendation: **explicitly defer**, with the exclusion conjunct present in the predicate and a comment naming the deferral, so a future reader sees a decision rather than an oversight. Founder call — a composite of MT5 keys would be equally stale.

5. **OQ-5 — The sibling defect: ccxt strategies with no new fills also never recompute.**
   - Known: `cron_sync` enqueues `derive_broker_dailies` only for strategies with `stored > 0`. A flat trading day for a ccxt strategy produces no recompute either.
   - Recommendation: out of scope for 161.1 (different venue class, different mechanism), but **file it** — a staleness-gated fan-out is trivially generalisable to it later, and the view built for criterion 3 would surface it for free if the planner chooses not to venue-filter the *view* (only the *enqueue*).

6. **OQ-6 — Does the staleness signal need a surface beyond the view, and which?**
   - Options: founder-run query only (cheapest, satisfies "observable"); an admin panel row (`src/app/(dashboard)/admin/compute-jobs`); an addition to the daily `alert-digest` cron (founder email — note `RESEND_API_KEY` is recorded as unset in Vercel prod, so an email path may be silently dead).
   - Recommendation: ship the view in this phase; treat any UI/email surface as a separate, optional plan so criterion 3 is not hostage to a UI task.

7. **OQ-7 — What cadence and `LIMIT` does the derivation actually yield?** The method is given above; the numbers depend on OQ-2's book size and A5's worker topology. This must be *written down with its derivation* in the plan, not chosen in review.

### Known Threat Patterns

| Pattern | STRIDE | Mitigation |
|---|---|---|
| Cross-tenant enqueue via a SECDEF function | Elevation of Privilege | No parameters; no caller input reaches the predicate; `REVOKE ALL` from `anon`/`authenticated` |

| Information disclosure through a staleness surface | Information Disclosure | Admin-gated route only; ⛔ never `/api/health` (public); ⛔ never ids in `.planning/` |
