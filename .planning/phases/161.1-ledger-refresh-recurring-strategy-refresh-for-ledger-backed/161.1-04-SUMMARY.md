## ⛔ The finding this plan exists to have caught

**`run_stitch_composite_job`'s `_stamp_failed` is a second D-15-class destructive stamp, and plan
02's guard does not reach it.** The plan asked me to "check whether your arm needs the marker guard
extended to it, and say either way". The answer is **yes**, and it is not a close call.

Measured at HEAD before anything was written (`job_worker.py:5557-5606` pre-edit):

| What the composite stamp does | Verdict |
|---|---|
| merges rather than overwrites `data_quality_flags` (M-2) | already safe |
| never writes `metrics_json_by_basis` | already safe |
| writes `computation_status = 'failed'` | **the un-publish** |

| calls `_heal_delete_basis_series()` | **no** — that helper has no call site in this handler |

`src/lib/strategyGate.ts` carries `ANALYTICS_FAILED` as a gate failure code, and plan 01's census
records every live ledger row as `complete_with_warnings`. So that status flip is precisely the
harm D-15 exists to prevent — on a path **this plan makes recurring**, against the venue whose only
live strategy IS a composite. A cohort of one, and no redundancy.

**Why it was fixed rather than filed.** The stopping rule for this repo blocks on user-facing or
data-integrity harm, and this is both. The realistic recurring failure mode is not exotic: the
composite path's PERMANENT failures include `LedgerCompletenessError` / `LedgerValuationError`
arising from new data, which is the "structural mark-hole fails the WHOLE job" shape this codebase
already has history with. Filing it as a TODO would have shipped an arm whose first bad tick takes
deribit's factsheet dark.

**Why the extension is consistent with the existing design rather than a change to it.** The
closure's own docstring gives the reason for the flip: *"Terminal 'failed' stamp so the wizard
poller reaches a gate instead of an infinite 'computing' spinner"*. That reason is real and is
untouched — a user-initiated stitch still flips the status, loudly. A background maintenance refresh
has **no wizard poller watching it**, so the flip buys nothing and costs a live factsheet. Keying
the exemption on the fan-out's marker is exactly D-15's mechanism, spelled the same way, applied to
the second arm.

## The partition, and why arm D is the arm this plan turns on

`is_composite = TRUE` is the SOLE conjunct separating this arm's cohort from plan 02's. The trap the
plan warned about is mechanical: `is_composite` is TRUE iff the strategy has ≥1 `strategy_keys` row,
and a single-key strategy has ZERO, so **any** conjunct spelled as a bare `EXISTS (SELECT 1 FROM
strategy_keys …)` performs the partition a second time and makes the mandated neutering
unfalsifiable.

The member-health conjunct is therefore written in two halves:

```
NOT EXISTS (any strategy_keys row for this strategy)     -- member-less rows PASS here
OR EXISTS  (a strategy_keys row whose key is active, not revoked, not disconnected)
```

**ANY eligible member, not ALL** — decided and commented at the point of use: a composite whose
members are partly disconnected is still refreshable over its remaining declared windows, and an
all-members rule would silently drop a live composite the day one member is revoked. **Arm B pins
that**: its fixture carries one eligible member and one REVOKED member, and it asserts the revoked
member is present, so arm B's return value of 1 IS the measurement of ANY-vs-ALL rather than an
incidental pass.

Arm D asserts **six eligibility facts about its own fixture before it asserts the exclusion** —
`is_stale`, `is_composite = false`, `has_mt5_member = false`, lifecycle status, zero
`strategy_keys` rows, zero `compute_jobs` rows. Each is an INPUT read from the view and the tables,
not a re-implementation of the predicate. Without those, a green arm D could be the staleness gate
or the lifecycle conjunct talking, and neutering 2 below would not have fired.

The plan's two prohibitions were followed and written into the file: the "n × ceiling fits in a
tick" formula is false because (a) this arm does not own the tick — the same sequential worker is
draining the other arm's 1500 s chains — and (b) at n = 3 it lands on 3600 s, an **equality** with an
hourly tick, which is not a bound. The cap is set at 2: strictly above the measured cohort of 1, so
it never binds today, and low enough that a grown cohort adds at most 2400 s to a shared tick.

**No per-venue partition**, stated as a decision rather than omitted: the cohort is one strategy, so
a partition would rank a set of one and pin nothing. Ordering is oldest-first so a future larger
cohort cannot starve a tail.
