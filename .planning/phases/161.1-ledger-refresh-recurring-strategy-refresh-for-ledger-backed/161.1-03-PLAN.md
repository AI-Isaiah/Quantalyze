Write the runbook. Its audience is the founder at a PROD SQL prompt, months from now, under time
pressure. Prefer exact statements over prose.

Sections, in order:

**What this activates.** One paragraph: after onboarding, ledger-backed strategies were never
recomputed; this registers an hourly, staleness-gated, bounded fan-out that enqueues the chain tail
for stale ledger strategies. Name both migrations by filename — the staleness view and the fan-out
function — and state plainly that the founder's registration statement will invoke the function
body defined in the latter. That pointer must move if the migration is ever superseded; say so,
because this phase's research records a stale pointer keeping a gate green while it guarded a body
nothing ran.

**Blast radius — read before the pre-flight, not after it.** Open the runbook's operational half
with what a wrong activation costs, because every gate below only makes sense once this is known.
State it as measurement, citing `analytics-service/services/job_worker.py:2582-2604` by path and
line: when a derive job fails terminally, the worker does not merely record a failed job — it
upserts onto that strategy's `strategy_analytics` row `computation_status='failed'`,
`computation_warned=false`, `computing_started_at=NULL`, a scrubbed `computation_error`, and
`metrics_json_by_basis=NULL`. That last one is an authoritative clear of a live column on a row that
was healthy a second earlier. Per the CONTEXT census all 5 live ledger rows are currently
`complete_with_warnings` — a success status — so there is no already-broken row to fail; every
strategy the fan-out touches is one it can only downgrade.

Therefore: activating while `MT5_ENABLED` is false does not degrade the rollout, it downgrades the
whole MT5 cohort at once, on the FIRST tick, before anyone reads a log line. Say the number for the
current cohort explicitly, and say that these are funded, published strategies. Add that this is not
a hypothetical ordering slip: the MT5 gateway is on record wedging into `-10005` IPC timeouts three
times in a single day, so a correctly-flagged activation against a wedged terminal produces the
identical stamp. The flag gate reduces the exposure; it does not remove it — which is why the
remediation procedure below is a required part of this runbook and not an appendix.

One thing survives, and the whole recovery hangs off it: that stamp never writes `returns_series`.
The historical daily series stays on the row. So the damage is confined to the status columns and
`metrics_json_by_basis`, both of which a later successful run rewrites wholesale — and the surviving
`returns_series` is what the detection query keys on. State this survival explicitly as the reason
the incident is recoverable.

**Pre-flight, all blocking. Any item that does not return its expected answer is an ABORT, not a
note-and-continue.** A checklist, each item with the exact query or command and the expected answer:
  - The A7 tracer (plan 01 task 3) passed. If it did not, stop — the path is unproven.
  - Both migrations are applied to PROD: assert the view and the zero-argument function both exist.
  - ⛔ **Venue enable flags — the hard gate.** Assert `MT5_ENABLED` is true on the worker BEFORE any
    mt5 strategy can be fanned, and `SFOX_ENABLED` likewise before any sfox strategy exists. Give
    the exact command that reads the live worker's value and the exact expected string; a value read
    from a dashboard the founder believes is current does not satisfy this item, and neither does a
    variable set without the redeploy that publishes it — cross-reference the mt5 and sfox go-live
    runbooks by path for the redeploy requirement. If the assertion does not return the expected
    value, STOP: do not run step 1, do not run step 2. The derive handler fails closed on a disabled
    venue, and per the blast-radius section a fail-closed derive is a destructive write, so
    proceeding costs the cohort's analytics state — not a retry.
  - Baseline census: run the staleness view and record the row count, the per-venue counts, the
    per-row `computation_status`, and the maximum days-since-last-return. Record it somewhere
    outside the SQL session. This is both the number the founder watches drain AND the pre-incident
    snapshot the remediation step compares against — a remediation with no BEFORE cannot tell a row
    the fan-out broke from a row that was already failing.
  - Worker health: confirm the worker is live and consuming, and note the WORKER_CLAIM_ROLE value.
    If it is the default all-kinds value, the ledger batch and interactive onboarding share one
    queue — that is a wait, not a crash, and it is the shape the v1.11 incident took. State it as a
    known condition of activation, never as a mitigation already in place.

**Step 1 — the activation setting (LIVE op 1 of 2).** The exact database-level SET statement for
the activation setting whose name plan 02 recorded in its SUMMARY. Then the verification: open a
NEW session and read the setting back — it does not apply to sessions already open. If the role
lacks privilege for the database-level form, document the role-level fallback and re-verify the
same way. Catching a privilege failure here, before anything ticks, is why this step comes first.

**Step 2 — the schedule (LIVE op 2 of 2).** The exact statement that registers the hourly job,
naming the job, invoking the zero-argument function, and using a minute offset that avoids the
quarter-hour reaper grid and the occupied 03:30 / 04:00 / 04:15 / 05:00 / 05:30 UTC daily slots.
Give the verification query against the job registry (name, schedule, active). State once more, in
bold, that this statement lives HERE and never in a migration, and why: migrations auto-apply on
merge, and a merge whose worker deploy is silently skipped starts a schedule against a worker that
cannot serve it.

**First tick.** What to expect: the function returns a count; at the per-tick and per-venue bounds
plan 02 recorded, a backlog of B strategies takes roughly B divided by the per-tick bound in hours
to clear. State the number for the current cohort explicitly. Say the trade honestly — a slow,
observable catch-up was chosen over a fast one because a fast one is the wedge.

**Watching it.** The staleness view query to re-run, and the compute_jobs query showing the kind,
status and duration of the last tick's jobs. Success is the stale count going down and the maximum
days-since-last-return going down. Warn explicitly: a job reaching a green terminal status is NOT
success — the defect this phase fixes wore a green badge for weeks. Check the view.

**Rollback, part 1 of 2 — stop the bleeding.** Two levels, fastest first:
  - FAST: reset the activation setting. The schedule keeps firing but the function returns 0 and
    enqueues nothing. No schedule operation, no deploy, effective for every new session.
  - FULL: unschedule the job by name. Give the exact statement and the verification query.
  - Note that neither rollback cancels already-queued jobs; give the query to inspect non-terminal
    rows and state that the existing orphan-terminalizer and stuck-row reaper own them from there.
    Do not add a third mechanism racing them.
  - End this part with an explicit hand-off sentence: stopping the schedule stops FUTURE damage and
    repairs nothing. If any tick already ran, part 2 is mandatory.

**Rollback, part 2 of 2 — remediation: find and repair what the fan-out already downgraded.**
This section is the reason the rollback is a rollback. Three steps, in order:

  1. **Detect.** Give the exact query that lists the affected rows. It joins `compute_jobs` to
     `strategy_analytics` on `strategy_id` and selects rows where ALL of these hold: the
     `compute_jobs.metadata` carries the fan-out's source token (use the token plan 02 recorded in
     its SUMMARY — quote it verbatim in the runbook, and note that the A7 tracer used a different
     token so tracer jobs cannot be swept in by accident); the job reached a failed terminal status;
     the strategy's `strategy_analytics.computation_status` is `failed`; and its `returns_series` is
     a non-empty array. Explain each conjunct in one clause, because a reader who does not
     understand the last one will drop it: the surviving `returns_series` is what distinguishes a
     row the fan-out knocked down from a row that never had analytics at all. Order the output by
     the job's completion time. Have the founder diff this list against the pre-flight BEFORE census
     and treat only rows whose recorded BEFORE status was in the success pair as fan-out damage —
     the census is what makes this a diff rather than a guess.
  2. **Repair.** State the fix in the only order that works: correct the cause FIRST — set the venue
     flag true and redeploy the worker, or clear the wedged gateway per its own runbook — and
     re-assert the pre-flight flag gate before enqueuing anything. Then, for each affected strategy,
     re-run the chain by hand exactly as the A7 tracer did: ONE `derive_broker_dailies` job, one
     strategy at a time, carrying a remediation-specific metadata source token so the repair jobs
     are distinguishable from both the tracer and the fan-out. Give the exact enqueue statement with
     the id as a placeholder. Do not batch, and do not re-enable the schedule to do the repair for
     you — a schedule against an uncorrected cause re-runs the damage.
  3. **Verify the repair, per row.** For each repaired strategy re-read the staleness view and the
     `strategy_analytics` row and assert all three: `computation_status` is back in the success pair
     from D-04, `metrics_json_by_basis` is non-null again, and `last_return_date` advanced. Say why
     all three and not just the first — the status alone flipping green is the exact shape of defect
     this phase exists to eliminate, and `metrics_json_by_basis` is the column the failure stamp
     cleared, so a green status over a still-null by-basis column is a half-repair that looks whole.
  4. **When the repair cannot succeed.** If the venue is still down, the row stays `failed`. Say
     plainly that this is an accepted, recorded state and that the founder must NOT hand-edit
     `strategy_analytics` to restore a success status or re-populate `metrics_json_by_basis` by
     hand: a status not produced by a real run is a fabricated green badge, which is the precise
     failure mode this phase was opened to remove. Record the affected count and date in TODOS.md
     and re-run the repair when the venue returns.

**What this deliberately does not cover.** Reference the composite disposition and the ccxt sibling
defect by their TODOS.md entry numbers from task 2.
