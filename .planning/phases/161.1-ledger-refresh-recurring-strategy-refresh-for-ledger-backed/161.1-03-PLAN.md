Sections, in order:

**What this activates.** One paragraph: after onboarding, ledger-backed strategies were never
recomputed; this registers an hourly, staleness-gated, bounded fan-out that enqueues the chain tail
for stale ledger strategies. Name both migrations by filename — the staleness view and the fan-out
function — and state plainly that the founder's registration statement will invoke the function
body defined in the latter. That pointer must move if the migration is ever superseded; say so,
because this phase's research records a stale pointer keeping a gate green while it guarded a body
nothing ran.

**Pre-flight, all blocking.** A checklist, each item with the exact query or command and the
expected answer:
  - The A7 tracer (plan 01 task 3) passed. If it did not, stop — the path is unproven.
  - Both migrations are applied to PROD: assert the view and the zero-argument function both exist.
  - Venue enable flags FIRST. MT5_ENABLED must be true on the worker before mt5 strategies are
    fanned; SFOX_ENABLED likewise before any sfox strategy exists. Order matters: the derive
    handler fails closed on a disabled venue, so activating the fan-out first would mint terminal
    failed jobs for every mt5 strategy in the cohort. Cross-reference the mt5 and sfox go-live
    runbooks by path.
  - Baseline census: run the staleness view and record the row count, the per-venue counts, and the
    maximum days-since-last-return. This is the number the founder watches drain.
  - Worker health: confirm the worker is live and consuming, and note the WORKER_CLAIM_ROLE value.
    If it is the default all-kinds value, the ledger batch and interactive onboarding share one
    queue — that is a wait, not a crash, and it is the shape the v1.11 incident took. State it as a
    known condition of activation, never as a mitigation already in place.

**Step 1 — the activation setting (LIVE op 1 of 2).** The exact database-level SET statement for
the activation setting whose name plan 02 recorded in its SUMMARY. Then the verification: open a
NEW session and read the setting back — it does not apply to sessions already open. If the role
lacks privilege for the database-level form, document the role-level fallback and re-verify the
same way. Catching a privilege failure here, before anything ticks, is why this step comes first.

**Step 2 — the schedule (LIVE op 2 of 2).** The exact statement that registers the hourly job,
naming the job, invoking the zero-argument function, and using a minute offset that avoids the
quarter-hour reaper grid and the occupied 03:30 / 04:00 / 04:15 / 05:00 / 05:30 UTC daily slots.
Give the verification query against the job registry (name, schedule, active). State once more, in
bold, that this statement lives HERE and never in a migration, and why: migrations auto-apply on
merge, and a merge whose worker deploy is silently skipped starts a schedule against a worker that
cannot serve it.

**First tick.** What to expect: the function returns a count; at the per-tick and per-venue bounds
plan 02 recorded, a backlog of B strategies takes roughly B divided by the per-tick bound in hours
to clear. State the number for the current cohort explicitly. Say the trade honestly — a slow,
observable catch-up was chosen over a fast one because a fast one is the wedge.

**Watching it.** The staleness view query to re-run, and the compute_jobs query showing the kind,
status and duration of the last tick's jobs. Success is the stale count going down and the maximum
days-since-last-return going down. Warn explicitly: a job reaching a green terminal status is NOT
success — the defect this phase fixes wore a green badge for weeks. Check the view.

**Rollback.** Two levels, fastest first:
  - FAST: reset the activation setting. The schedule keeps firing but the function returns 0 and
    enqueues nothing. No schedule operation, no deploy, effective for every new session.
  - FULL: unschedule the job by name. Give the exact statement and the verification query.
  - Note that neither rollback cancels already-queued jobs; give the query to inspect non-terminal
    rows and state that the existing orphan-terminalizer and stuck-row reaper own them from there.
    Do not add a third mechanism racing them.

**What this deliberately does not cover.** Reference the composite disposition and the ccxt sibling
defect by their TODOS.md entry numbers from task 2.
