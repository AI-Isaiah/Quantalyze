### Threshold comparison — strictly `> 4`, and why it is not `>= 4`

The plan derives 4 days from "a Friday close read on a public-holiday Monday is legitimately
3 days old". That scenario stops one step early. Walk it out: Friday's bar carries date F;
Sat/Sun produce none; a holiday Monday produces none; the next bar is Tuesday. A read on
Tuesday **before** that day's derive has run sees F at an age of exactly **4**. So 4 is the
largest *healthy* age and the alert must fire strictly above it. Keying `>=` off the plan's
derivation would false-alarm every holiday Tuesday. Same constant, corrected comparison —
and Arm F now pins it at **both** edges (age 4 fresh, age 5 stale) so it cannot drift silently
in either direction. Detection is unaffected: the live cohort sits at 21 and 36 days.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The mandated date guard does not deliver its own stated property**
- **Found during:** Task 1
- **Issue:** The plan specifies filtering elements "whose `date` does not match a four-two-two
  digit date pattern before casting", justified as "a garbage element must not raise".
  A regex does not achieve that. `'2026-02-31'` matches `^[0-9]{4}-[0-9]{2}-[0-9]{2}$` exactly
  and still raises SQLSTATE **22008** on cast, which would break the view for every reader whose
  result set includes the corrupt row — the precise failure T-161.1-04 exists to prevent.
- **Fix:** Kept the regex as a cheap pre-filter *and* routed the cast through
  `public.ledger_refresh_parse_series_date`, which traps exactly `invalid_datetime_format` (22007)
  and `datetime_field_overflow` (22008) and returns NULL. NULL drops the element from the `max()`,
  so corruption can only make a row read **staler**, never fresher. Named conditions rather than
  `WHEN others`, so it can never swallow a query cancel or a permission error.
- **Verification:** Measured both codes empirically before writing the function, then built the
  regex-only variant and observed the view raise on `'2026-02-31'` (observation 5a). Arm E3 pins it.
- **Committed in:** `2291feb1`

**2. [Rule 1 — Bug] Threshold comparison off by one against the worst legitimate gap**
- **Found during:** Task 1
- **Issue:** The plan's derivation of the 4-day constant stops at a Monday read (3 days) and so
  under-counts the real worst-case legitimate age by one day. Implementing `>= 4` from that
  wording would false-alarm on every holiday Tuesday.
- **Fix:** Strictly `> 4`. Full walk-through written into the migration header, explicitly flagging
  where the plan's derivation stops short.
- **Verification:** Arm F pins both edges (age 4 fresh, age 5 stale).
- **Committed in:** `2291feb1`

**3. [Rule 2 — Missing critical functionality] Grant assertions strengthened beyond the plan**
- **Found during:** Task 1
- **Issue:** The plan specifies asserting zero rows in `information_schema.role_table_grants` for
  anon/authenticated. That view reports a grant made to `PUBLIC` under grantee `PUBLIC`, not under
  `anon`, so the specified check alone can miss a live cross-tenant read path. It also does not
  assert that `service_role` retained SELECT, and the broad `REVOKE ALL` can remove it by accident —
  which would ship an observability surface nobody can read.
- **Fix:** Kept the specified check and added `has_table_privilege` probes for `anon` and
  `authenticated` (these resolve PUBLIC grants and role inheritance), a positive
  `has_table_privilege('service_role', …)` assertion, and a `security_invoker=true` assertion so
  the view can never become an RLS bypass on the base tables (T-161.1-05).
- **Verification:** Confirmed the underlying risk is real — a probe view created in `public`
  returned `t|t` for anon/authenticated before any REVOKE, so these assertions are non-vacuous.
- **Committed in:** `2291feb1`

**4. [Rule 2 — Missing critical functionality] Two unpinned properties given their own arms**
- **Found during:** Task 2
- **Issue:** The plan's five arms leave two load-bearing properties untested. Nothing pinned the
  ledger-venue **cohort scope** — deleting the venue filter entirely would still pass all five
  arms — and nothing pinned the **staleness threshold**, so the constant could drift silently.
- **Fix:** Added Arm G (a non-ledger okx strategy must be ABSENT; plus a count assertion that all
  10 seeded ledger strategies are present) and Arm F (threshold edges). Also ordered every series
  fixture newest-first, so an implementation reading the array tail instead of taking `max()` fails.
- **Verification:** Arm G observed RED under a dropped cohort filter (observation 5b).
- **Committed in:** `5f3e8456`
