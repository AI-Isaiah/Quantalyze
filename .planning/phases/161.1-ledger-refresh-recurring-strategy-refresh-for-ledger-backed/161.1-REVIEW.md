## Summary

The dormancy machinery, the freshness verdict, the cohort scoping and the SQL hygiene
are genuinely well built and I could not break them. Independently verified at HEAD:

- **Invariant 1 — zero `cron.schedule`.** `grep -rniE "cron\.|schedule"` over the three new
  migrations returns comment prose only; no `cron.` call site anywhere. Gate 3a
  (`*ledger_refresh*.sql` glob + a floor of 3 known files) and gates 3b/10c (function-name
  count over ALL `*.sql` == 1) both hold and are non-vacuous.
- **Invariant 2 — dormancy is real.** `current_setting('app.ledger_refresh_enabled', TRUE)`
  is genuinely the first statement of both function bodies, compared by exact string
  equality, with a `RETURN 0` before any read of the cohort
  (`20260825130000:253-257`, `20260825140000:220-224`).
- **Invariant 3 — `enqueue_compute_job` exactly-one-of.** Both call sites pass
  `p_strategy_id` alone (`20260825130000:392-399`, `20260825140000:375-382`). Traced
  `_assert_owner` (`20260516131500:205-210`): `auth.uid()` is NULL in a pg_cron session, so
  it returns early — no silent 42501 that would make the fan-out a no-op.
- **Invariant 4 — the verdict.** `max(ledger_refresh_parse_series_date(e.elem->>'date'))`
  conjoined with `NOT IN ('complete','complete_with_warnings')`; both rejected columns appear
  only *outside* the `LEDGER_REFRESH_VERDICT_BEGIN/END` markers as documented informational
  columns, which is correct and I did not flag.
- **Invariant 6 — cohort scope.** `_LEDGER_BACKED_SOURCES` is `{deribit, sfox, mt5}`
  (`long_fetch.py:63`); gate 1 pins the SQL array against it by set equality plus a
  cardinality floor of 3. `python3 -m pytest tests/test_ledger_refresh_gates.py` → **35 passed**;
  the three non-destructive/scoped-update suites → **23 passed**.
- **Invariant 8 — public repo.** Diff scan for emails / UUIDs / URLs / project refs is clean
  (only the standard zero `instance_id` and `@quantalyze.test` fixtures).

The defects are all on one axis: **the D-15 non-destructive guard does not actually hold
end-to-end.** It was built and tested at the level of one Python closure, and the closure is
not where the publish state is decided. Three independent paths route around it, and the
phase's own PROD tracer observed the exact outcome the guard is supposed to prevent —
`161.1-04-SUMMARY.md` attributes that to "the guard is not merged yet", which is a
misdiagnosis: merging the guard would not have changed the observed AFTER state.

Because migrations auto-apply and the fan-outs are dormant, none of this is live today. All
three CRITICALs are **go-live blockers, not merge blockers** — but they must be fixed (or
consciously re-scoped by the founder) before LIVE op 1 in
`docs/runbooks/ledger-refresh-go-live.md`, because activation with them present converts a
latent defect into a permanent live outage on a funded account (CR-01 scenario 2).

## Critical Issues

### CR-01: The D-15 guard is overwritten by the SQL status bridge on the job's own terminal transition

**File:** `analytics-service/services/job_worker.py:2654-2708` and `:5648-5686`
**Also:** `supabase/migrations/20260529180000_fix_mark_compute_job_failed_error_kind_column.sql:135-138`,
`supabase/migrations/20260802120000_strategy_analytics_stuck_computing_reaper.sql:374-399`

**Issue:** Both D-15 guards skip the Python `computation_status = 'failed'` upsert and then
return. The handler still returns `DispatchResult(outcome=FAILED, error_kind="permanent")`
(both new test files assert exactly this — `test_ledger_refresh_nondestructive.py:164`,
`test_ledger_refresh_composite_nondestructive.py:126-127`). `main_worker` then calls
`mark_compute_job_failed`, which sets the row to `failed_final` and, in the same transaction,
`PERFORM sync_strategy_analytics_status(v_strategy_id)`. That function's branch (b) fires on
**any non-superseded `failed_final`** and writes:

```sql
INSERT INTO strategy_analytics (strategy_id, computation_status, computation_error, computing_started_at)
VALUES (p_strategy_id, 'failed', v_latest_error, NULL)
ON CONFLICT (strategy_id) DO UPDATE
   SET computation_status = EXCLUDED.computation_status, ...
```

The refresh job *is* the latest job of its kind, so it is not superseded. `computation_status`
lands on `'failed'` regardless of the guard. `src/lib/strategyGate.ts` maps `failed` →
`ANALYTICS_FAILED`, so the funded account's factsheet goes dark — which is the entire harm
D-15 exists to prevent.

Two concrete failure scenarios:

1. **Single-key / MT5.** First tick after activation lands on a wedged MT5 gateway →
   permanent failure → `failed_final` → all four live MT5 strategies read `ANALYTICS_FAILED`
   until a later refresh succeeds (≥20 h away, per the cooldown).
2. **Composite / deribit — permanent.** The sole live deribit composite is already
   unstitchable (`breach_ratio=436`, ~118 days). Once the composite arm is scheduled it will
   re-attempt every 20 h and fail every time, so that account reads `ANALYTICS_FAILED`
   **indefinitely**. Today the row is `complete_with_warnings` and renders. The pre-existing
   data defect is known and accepted; converting it into a permanent live outage is new and
   is introduced by this phase.

**Evidence this is not theoretical:** `161.1-04-SUMMARY.md:544-576` records the PROD tracer
producing precisely this AFTER state — `computation_status: complete_with_warnings → failed`,
with `returns_series`, `metrics_json_by_basis` and all 11 basis-series rows surviving. That is
exactly the signature of the SQL bridge acting alone. The SUMMARY's conclusion ("the guard
lives on this branch, not merged, so the live worker ran the UNGUARDED code") is incomplete:
the guarded code produces the same final status.

What the guard *does* buy, and should be kept: it leaves `computation_warned` set, so branch
(c) of the bridge restores `complete_with_warnings` on the next successful run without an
analytics re-run. That is real, but it does not close the dark window.

**Fix:** the exemption has to be visible to the thing that decides publish state — the
`compute_jobs` aggregate — not only to the Python stamp. Two workable shapes:

```sql
-- Option A (preferred): teach the bridge to ignore a marked maintenance refresh.
-- Re-base sync_strategy_analytics_status on 20260802120000 (its LATEST definition)
-- and narrow branch (b)'s failed_final scan:
  SELECT count(*) INTO v_failed_count
    FROM compute_jobs f
   WHERE f.strategy_id = p_strategy_id
     AND f.status = 'failed_final'
     -- Phase 161.1 / D-15: a MARKED background maintenance refresh must not
     -- poison an already terminal-SUCCESS row. Scoped to the two refresh
     -- markers only; every user-initiated job still poisons loudly.
     AND NOT (
           f.metadata ->> 'source' IN ('ledger-refresh', 'ledger-refresh-composite')
       AND EXISTS (SELECT 1 FROM strategy_analytics sa
                    WHERE sa.strategy_id = p_strategy_id
                      AND (sa.computation_status IN ('complete','complete_with_warnings')
                           OR sa.computation_warned))
     )
     AND NOT EXISTS ( ... existing supersession subquery ... );
```

Option B (smaller blast radius, worse fidelity): have the marked-refresh path return
`DispatchOutcome.DEFERRED` instead of `FAILED` so no `failed_final` is written — but that
loses the attempt row the fan-out's cooldown reads, so it needs a compensating attempt record.
Option A is the one that keeps every existing invariant.

Whichever is chosen, add a regression test that exercises **handler → mark RPC → bridge**, not
just the closure. Every current D-15 test mocks Supabase and stops at the upsert payload, so
this bug is invisible to all 23 of them.

### CR-02: Three sibling terminal-`failed` stamps in the same handler are unguarded — one of them deletes the live basis series

**File:** `analytics-service/services/job_worker.py:2490-2510`, `:4672-4697`, `:4755-4773`

**Issue:** D-15 was applied to exactly one of the four terminal-failure stamp sites inside
`run_derive_broker_dailies_job`. The other three write the destructive payload directly and
never consult `job['metadata']['source']`:

| line | site | writes | also destroys |
|---|---|---|---|
| 2490 | `_dispose_broker_nav_error` | `status='failed'`, `computation_warned=False`, `metrics_json_by_basis=None`, `data_quality_flags={'csv_source':True}` | — |
| 4672 | `_mark_insufficient` (<2 daily-return days) | same payload | **`_heal_delete_basis_series()` at :4697 — DELETEs both `cash_settlement` and `mark_to_market` series rows** |
| 4755 | `_stamp_verdict_failed` (MT5-12 series-completeness refusal) | same payload | — |

`_mark_insufficient` is the worst and the most reachable: it fires whenever the crawl comes
back with fewer than two days of combined realized+funding returns. An MT5 gateway that has
lost its terminal login and returns an *empty* deal history (the `-10004` state recorded in
this repo's operational history) produces exactly that. On a live funded strategy with years
of history, one refresh tick then NULLs `metrics_json_by_basis` and deletes both persisted
basis-series rows — the precise harm the D-15 comment at `:2695-2699` names as "the half that
is easy to miss".

`_stamp_verdict_failed` is MT5-specific (the MT5-12 seam) and MT5 is 4 of the 5 live ledger
strategies.

**Fix:** hoist the guard out of the closure into one predicate evaluated once per job, and
consult it at every stamp site:

```python
# near the top of run_derive_broker_dailies_job, after strategy_id/is_key_mode resolve
_job_meta = job.get("metadata") or {}
_refresh_marked = (
    isinstance(_job_meta, dict) and _job_meta.get("source") == "ledger-refresh"
)

async def _publish_state_is_protected() -> bool:
    """D-15: True iff this is a MARKED refresh AND the row is terminal-success.
    Fail-safe: any read failure returns False -> the LOUD destructive path."""
    if not _refresh_marked or is_key_mode:
        return False
    try:
        status = await db_execute(_read_existing_status)
    except Exception:
        return False
    return status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES
```

Then gate `_dispose_broker_nav_error`, `_mark_insufficient` (including its
`_heal_delete_basis_series()` call) and `_stamp_verdict_failed` on it, each with the
error-only upsert. Add a static gate to `test_ledger_refresh_gates.py` that counts
`"computation_status": "failed"` occurrences inside `run_derive_broker_dailies_job`'s source
region and asserts every one of them is inside a `_publish_state_is_protected()` branch —
otherwise the next stamp site added will silently reopen this.

### CR-03: The chained `compute_analytics_from_csv` hop is enqueued with no metadata, so the second half of every refresh is unmarked

**File:** `analytics-service/services/job_worker.py:5344-5350`

```python
def _enqueue_csv_analytics() -> None:
    ctx.supabase.rpc(
        "enqueue_compute_job",
        {"p_strategy_id": strategy_id, "p_kind": _csv_analytics_kind},
    ).execute()
```

**Issue:** The fan-out's own migration header (`20260825130000:144-150`) is explicit that a
refresh is a **two-hop chain**: `derive_broker_dailies` auto-chains to
`compute_analytics_from_csv`, and the D-09 bound is derived from that. But the follow-on job
carries no `metadata`, so `metadata->>'source'` is NULL on hop 2. Any D-15-style guard —
today's or a fixed one — is structurally blind to it.

Hop 2 is where the factsheet is actually compiled, and `analytics_runner.py` writes
`"computation_status": "failed"` at five separate sites (`:1316`, `:1682`, `:1725`, `:1778`,
`:1814`). So: derive succeeds, analytics hop fails, funded account un-published — with the
D-15 guard fully working and the marker contract fully in sync. The 20-hour cooldown even
counts `compute_analytics_from_csv` (`20260825130000:319`), which shows the phase reasoned
about hop 2 as part of the refresh everywhere *except* the guard.

**Fix:** propagate the marker through the chain edge.

```python
def _enqueue_csv_analytics() -> None:
    _payload: dict[str, Any] = {
        "p_strategy_id": strategy_id, "p_kind": _csv_analytics_kind,
    }
    # Phase 161.1 / D-15: the follow-on hop is part of the SAME refresh. Without
    # the marker, a hop-2 failure un-publishes a funded account while every
    # hop-1 guard reads green.
    _src = (job.get("metadata") or {}).get("source") if isinstance(job.get("metadata"), dict) else None
    if _src is not None:
        _payload["p_metadata"] = {"source": _src, "chained_from": "derive_broker_dailies"}
    ctx.supabase.rpc("enqueue_compute_job", _payload).execute()
```

…and then apply the guard inside the CSV analytics runner's terminal stamps too, or accept
CR-01's Option A (which covers hop 2 automatically, since it keys on the `compute_jobs` row).
Option A is the reason to prefer it.

### WR-01: A load-bearing comment states the composite exclusion is "REDUNDANT" — it is not, and the file contradicts itself twelve lines later

**File:** `supabase/migrations/20260825130000_ledger_refresh_fanout_dormant.sql:112-117`
(repeated in the in-body comment at `:290-293`), contradicted at `:129-136`

At `:112-117`:

> ⚠️ The `is_composite = FALSE` conjunct is, under the LEFT join described below, otherwise
> REDUNDANT: the key-eligibility conjuncts would drop a NULL-key row anyway.

At `:129-136`:

> For the same reason every key-eligibility conjunct below is written NULL-TOLERANTLY. …
> A NULL-intolerant conjunct here would quietly become a SECOND composite-exclusion mechanism.

**Issue:** the second statement is the correct one and the first is false. Evaluate the actual
predicate for a composite (`ak` all NULL under the LEFT join):

- `ak.sync_status IS DISTINCT FROM 'revoked'` → `NULL IS DISTINCT FROM 'revoked'` → **TRUE**
- `ak.disconnected_at IS NULL` → **TRUE**
- `COALESCE(ak.is_active, TRUE)` → **TRUE**

All three pass. `lrs.is_composite = FALSE` (`:294`) is therefore the *only* thing excluding
composites — the opposite of redundant. The file tells a future editor the line is dead code
while a separate paragraph forbids removing it; the misleading half is the one printed
directly above the predicate.

**Failure scenario if acted on:** delete `:294` and every stale composite is enqueued for
`derive_broker_dailies`, which resolves its key through `strategies.api_key_id` (NULL on a
composite) and cannot serve one — a guaranteed terminal failure that (per CR-01) un-publishes
the deribit composite on every tick. Arm D of `supabase/tests/test_ledger_refresh_fanout.sql`
would catch it, but only after merge (see WR-03).

**Fix:** replace `:112-117` with the true statement, e.g.

```sql
-- ⚠️ The `is_composite = FALSE` conjunct is LOAD-BEARING, not decorative. Under the
-- LEFT join, every key-eligibility conjunct below is NULL-TRUE for a composite
-- (NULL IS DISTINCT FROM 'revoked' -> TRUE; NULL IS NULL -> TRUE; COALESCE(NULL,TRUE)
-- -> TRUE), so this line is the ONLY thing excluding composites. That is deliberate:
-- it keeps the exclusion falsifiable (arm D of the behavioural gate reddens when it is
-- deleted) instead of hiding it in a join or a key predicate.
```

and fix the same claim at `:290-293`.

### WR-02: The deferred-venue literal `'mt5'` in the staleness view is the only venue literal in the phase with no drift gate

**File:** `supabase/migrations/20260825120000_ledger_refresh_staleness_view.sql:206`

```sql
  ('mt5' = ANY (sv.exchanges))            AS has_mt5_member,
```

**Issue:** every other venue literal in this phase is pinned. Gate 1
(`test_ledger_refresh_gates.py:620-650`) matches only
`ARRAY\[([^\]]*)\]::TEXT\[\]\s+AS\s+venues` — it does not see this second literal. Gate 10b2
pins that the *consumer* (`has_mt5_member = FALSE`, `20260825140000:258`) is present, and gates
2/10b ban venue literals in the function bodies, so `'mt5'` here is the one hand-copied venue
name in the whole phase that nothing compares against `_LEDGER_BACKED_SOURCES`.

**Failure scenario:** the MT5 venue token changes or gains a sibling (`mt5_demo`, a rename in
`api_keys.exchange`). Gate 1 forces the `venues` array to be updated; `has_mt5_member`
silently evaluates FALSE for the affected rows; the composite arm's D-01/D-13 exclusion stops
excluding; an MT5-member composite is enqueued for a stitch that drags the single shared MT5
terminal registry (`mt5_concurrency.py`) into a composite crawl. That is a silent
mishandling — precisely what CONTEXT D-01 says must never happen.

**Fix:** derive the flag from the same array so one gate covers both, e.g.

```sql
-- inside ledger_venue_set
SELECT ARRAY['deribit','sfox','mt5']::TEXT[] AS venues,
       'mt5'::TEXT                          AS deferred_venue
...
  (lv.deferred_venue = ANY (sv.exchanges))  AS has_mt5_member,
```

then extend gate 1 to assert `deferred_venue` is a member of the extracted `venues` set (a
two-line addition that reddens the moment the two spellings diverge).

### WR-03: All three behavioural SQL gates are guaranteed to SKIP on the PR that introduces the migrations they guard

**File:** `supabase/tests/test_ledger_refresh_staleness.sql:76-82`,
`supabase/tests/test_ledger_refresh_fanout.sql:100-108`,
`supabase/tests/test_ledger_refresh_composite_arm.sql:108-116`

**Issue:** each file opens with a presence gate that `RAISE NOTICE 'SKIP: …'; RETURN;` when the
migration is absent. `supabase/migrations/**` auto-applies to the shared TEST project **on
merge to main**, so on the PR branch the three functions/views do not exist there and all
three files return green having executed zero assertions. The CI step
(`.github/workflows/ci.yml:1322-1340`) reads only the exit code.

This is established repo convention (17 of 66 files use the same pattern) and I am not
proposing to change the convention. It is a WARNING here because of the specific combination:
the SQL files are the **only** executed coverage of the fan-out predicates — the Python gates
are pure static text scans, and the two non-destructive suites mock Supabase entirely — and
the migrations auto-apply straight to PROD at merge. Net effect: three
`SECURITY DEFINER` cross-tenant enqueue functions reach production with their SELECT
predicates never having been executed anywhere except an executor's local session.

Note WR-01's exposure rides on this: arm D is what would catch the deletion the comment
invites, and arm D cannot run on the PR that lands the comment.

**Fix:** either (a) run the three files against a locally-applied `supabase db reset` shadow
in CI before the merge gate, or (b) at minimum, have the CI step grep each file's output for
its own `ALL N ARMS EXECUTED` sentinel and fail when a `SKIP:` line is printed on a PR that
touches `supabase/migrations/**`:

```bash
out="$(psql "$TEST_SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f "$f" 2>&1)"; echo "$out"
if echo "$out" | grep -q '^NOTICE:.*SKIP:'; then
  echo "::error file=$f::gate SKIPPED — it asserted nothing this run"; exit 1
fi
```

The files' own headers already say "read the notice, do not infer it from the exit code";
nothing mechanically does.

### WR-04: Five of the eight anti-vacuity region sentinels are tautological

**File:** `analytics-service/tests/test_ledger_refresh_gates.py:294-316` (`_assert_region`),
consumers at `:328-334`, `:369-399`, `:419-457`, `:460-485`, `:505-545`

**Issue:** `_assert_region`'s docstring states the design rule: *"Length alone is not enough —
a region could be long and still be the wrong text — so each region also carries a hand-typed
sentinel proving the extraction landed where it was aimed."* For five of the eight regions the
sentinel is a substring of the locator that found the region, so the assertion cannot fail:

| region | locator | sentinel | falsifiable? |
|---|---|---|---|
| VIEW BODY `:333` | regex `…VIEW public.ledger_refresh_staleness` | `"ledger_refresh_staleness"` | **no** |
| DECLARATION PRELUDE `:398` | regex embeds `_FANOUT_FUNCTION_NAME` | `_FANOUT_FUNCTION_NAME` | **no** |
| COMPOSITE PRELUDE `:484` | regex embeds `_COMPOSITE_FUNCTION_NAME` | `_COMPOSITE_FUNCTION_NAME` | **no** |
| GUARD REGION `:456` | line `startswith("async def _stamp_strategy_analytics_failed")` | `"_stamp_strategy_analytics_failed"` | **no** |
| COMPOSITE GUARD `:544` | line `startswith("async def _stamp_failed")` | `"_stamp_failed"` | **no** |
| FUNCTION BODY `:415` | `$fanout$…$fanout$` | `"enqueue_compute_job("` | yes |
| COMPOSITE BODY `:501` | `$composite$…$composite$` | `"enqueue_compute_job("` | yes |
| IS_STALE `:365` | `VERDICT_BEGIN…END` | `"last_return_date"` | yes |

Those five regions are protected by the character floor alone. Concretely: if
`_scan_sql`'s dollar-quote or literal handling regressed and the VIEW BODY extraction
terminated at the wrong `;` — still returning >1200 characters of the *header prose*, which is
what `_scan_sql`'s own docstring says happened once during development — the sentinel would
still be present (the phrase appears throughout the header) and gate 6's negative assertions
would pass over the wrong text.

**Fix:** give each of the five a sentinel drawn from the region's *tail*, which the locator
cannot supply:

```python
# VIEW BODY            -> "WHERE sv.exchanges && lv.venues"
# DECLARATION PRELUDE  -> "AS $fanout$"        (COMPOSITE: "AS $composite$")
# GUARD REGION         -> "_heal_delete_basis_series()"
# COMPOSITE GUARD      -> "on_conflict=\"strategy_id\""
```

Each proves the extraction reached the end of the intended region, and each reddens under a
truncating extraction bug.

### IN-01: The `v_existing` pre-count is unreachable-as-non-zero on the normal path

**File:** `supabase/migrations/20260825130000_ledger_refresh_fanout_dormant.sql:374-378`
(and `20260825140000:354-358`)

**Issue:** the candidate CTE already excludes any strategy with a job in
`('pending','running','done_pending_children','failed_retry')` (`:336-341`), which is a
superset of the three statuses the pre-count queries. So within a tick `v_existing` is 0 for
every candidate except under a concurrent externally-committed enqueue landing between the CTE
snapshot and the loop iteration (the advisory lock only serialises fan-outs, not the API). The
comment presents the pre-count as the primary defence against "counting CALLS not INSERTIONS";
in practice the in-flight conjunct is. It is harmless and fail-safe (it can only undercount),
but the surrounding narrative overstates it, and no test can drive it non-zero.

**Fix:** keep the pre-count, trim the comment to say what it actually is — a race-window
backstop over the in-flight conjunct, not the mechanism.
