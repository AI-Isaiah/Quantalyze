<objective>
SC-3's worker half: the store D-05 asks for, wired into the price resolution so a moved flow's price is read from
Deribit once, written once, and read back from the database on every later derive.

D-05 verbatim from CONTEXT: "Each resolved price is stored once and reused on later derives, so the source never needs
to be re-read for an old flow." Why it matters here (RESEARCH Pitfall 4): every derive re-applies ALL marks from the
first one, so without the store each night would re-read every historical moved flow and its price would only be as
stable as Deribit's 1-minute history.

Order inside `resolve_moved_flow_prices` (RESEARCH Pattern 3): (1) the wanted moved INDEXED instants from the shared
predicate; (2) read the key's stored prices for their `(instrument, minute_ms)` keys; (3) group only the MISSING keys by
(currency, read day) and read each group once; (4) write every newly read price once and re-select, so the stored row,
not the local read, is what the index uses; (5) build the index from stored rows. Zero store calls and zero chart calls
when nothing is wanted. Writing before the apply is deliberate: a price read correctly is a permanent fact, kept even if
the derive later refuses for an unrelated reason, so a retry costs no second chart request.

In this plan a store error (`FlowPriceStoreError`, including the table being absent because the worker deployed
before the migration applied) propagates out of the crawl to the existing transient handling: loud, never a price
used without the store. Plan 04 turns it into the named `store_fault` capture that keeps the day's mark.

Purpose: SC-3 (stored once, reused). Output: the store module, its fake mirror and unit tests, the live probe, the
wiring, and the roundtrip store cases.
</objective>
