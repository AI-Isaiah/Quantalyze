<objective>
The storage half of D-05: the table each resolved at-instant price is written to once and read back from, so an old
moved flow is never re-read from Deribit. Nothing writes to it until plan 03's worker code deploys.

D-05 verbatim from CONTEXT: "Each resolved price is stored once and reused on later derives, so the source never needs
to be re-read for an old flow. Storing needs a migration. It must have: service-role-only access (RLS forced, no
anon/authenticated grants) unless research shows a UI reads it; an erasure path (ON DELETE CASCADE from api_keys, or a
justified reason it holds no personal data); migration-reviewer and rls-policy-auditor clean before merge; a CREATE OR
REPLACE re-base on the latest definition of anything it touches. PROD auto-applies after TEST. The planner decides the
shape: key, currency, minute, price and source."

Shape decided here (planner's call inside D-05; the orchestrator settled RESEARCH Open Questions 6, 7 and 9 and will
surface them to the founder at hand-back, so each is one header line and easy to change):
- FP-1 Per key (`api_key_id` only), not global and not per owner: the set of stored minutes is the timing of a user's
  deposits and withdrawals, so it must erase with the key and the account; every derive path already holds the key id.
- FP-2 `instrument` stores what was read (`{CCY}_USDC-PERPETUAL`), `minute_ms` the candle's tick (a multiple of 60000),
  `price` the candle `open` as NUMERIC, `source` a closed set with one member, `deribit_perp_1m_open` (D-04).
- FP-3 Write-once is the GRANT (SELECT, INSERT to service_role only) and the primary key is the conflict arbiter for the
  worker's `ON CONFLICT DO NOTHING`; no other index, no surrogate id, no expiry column, no cron.
- FP-4 Not exported in the GDPR Art. 15 export (Open Question 7): a derived cache of a public market price keyed by an
  api key only, like Phase 171's store; plan 07 confirms the coverage hook still exits 0 with no edit.
- FP-5 No retention bound (Open Question 9): rows live until the key or account cascade removes them; a TTL would bring
  back the re-read the store exists to avoid.
- FP-6 The rollback renames the table aside and keeps every row (keep-data rule).
- Nothing is backfilled: the first derive after deploy that moves a flow writes the rows it needs.

Purpose: SC-3 (the database half). Output: the migration, its manual rollback, the 8-arm SQL gate with measured twins.
</objective>
