# Phase 167.2.1.1 Plan 03: Bybit uPnL live probe Summary

**A read-only Railway-worker probe that records, per active Bybit key, only booleans, counts and 3-significant-figure ratios for whether equity minus wallet balance equals open uPnL and whether ccxt's real `parse_balance` total follows the wallet balance, built and proven on fakes without touching any venue or database.**

## Performance

- **Duration:** about 25 min (start time was not captured at execution start; this is an estimate)
- **Completed:** 2026-10-22
- **Tasks:** 3
- **Files modified:** 2 (both new)

## Accomplishments

- `scripts/bybit_upnl_probe.py`: per key, one wallet-balance read (UNIFIED, then CONTRACT only after a bad-request or exchange error or an empty list) and one linear-USDT position-list read through `ReadOnlyBybitProxy`; ccxt's real `parse_balance` is run on a credential-free client over the same raw response; the record and a count-only summary go to stdout through `emit_record` only.
- `tests/test_bybit_upnl_probe.py`: 47 tests, none skipped. `run()` is driven end to end on stub clients, a fake Supabase chain and patched `services.*`.
- Read-only is enforced three ways: the wrapper (two GET endpoints, once each per distinct request, `AttributeError` for everything else including `close`), the source test (no write or preflight literal), and the single-SELECT test.
- A flat key (zero uPnL) is recorded as non-informative and the summary counts informative keys, so a run of idle keys cannot read as confirmation.

## How the record maps to D-01

D-01 says: "The check records only whether equity minus wallet balance equals the open uPnL (a boolean or a ratio per key), never an amount, a key id or an account number."

- D-01's measurement is `coin_equity_minus_wallet_equals_upnl` together with `upnl_ratio`.
- `record`, `key` and `run_date` are labels (the literal `key`/`summary`, the `k1..kN` label in `created_at` order, and the run date with no finer timestamp).
- Each of the other eleven key-record fields is a non-amount interpretive attribute of that same measurement: `read_ok`, `positions_read_ok` and `failure_class` say whether the read happened; `account_type` and `ccxt_total_equals_wallet` say which account shape and parser it went through; `account_equity_minus_wallet_equals_perp_upl`, `upnl_nonzero`, `borrow_present`, `non_usdt_coins_present`, `non_usdt_upnl_present` and `positions_upnl_matches_totalperpupl` say whether the identity is informative or what explains a mismatch. None carries an amount, a key id or an account number.
- Every summary count (`keys`, `keys_read`, `keys_informative`, `keys_identity_holds`, `keys_ccxt_total_is_wallet`) is likewise a count over those attributes.
