Bybit and Binance account equity is read one way on every path (the derive anchor in `exchange.py`, the reconstruct anchor in `equity_reconstruction.py`, the holdings poll in `allocator_positions.py`), so open-position profit is neither double-counted nor dropped. <decisions>
## Implementation Decisions

All three answered by the founder via AskUserQuestion on 2026-10-22.

### D-01 Evidence: code plus one live read
"Code + one live read (Recommended)". Settle the question from the pinned ccxt version's Bybit (V5 unified) and Binance balance parsing and Bybit's V5 wallet-balance docs. Then confirm on the live Bybit keys with a read-only check run on the Railway worker. The check records only whether equity minus wallet balance equals the open uPnL (a boolean or a ratio per key), never an amount, a key id or an account number. The live read waits for Railway deploys to resume, so it is a post-deploy step.

### D-02 Stored data: recompute affected
"Recompute affected (Recommended)". After the fix deploys, re-run the derive and the reconstruct for every Bybit-backed strategy and allocator. Record each one's before/after as counts and the size of change, with no amounts in tracked files. Use the product's own job paths (enqueue the existing compute kinds), not hand SQL writes.

### D-03 Binance: fix code, test only
"Fix code, test only (Recommended)". Make every path read Binance the same way, pinned by tests built from ccxt fixtures. No PROD step, because there are no Binance keys.

### D-04 Multi-key accounts: rebuild the whole account
Founder 2026-10-22, AskUserQuestion: "Rebuild whole account (Recommended)". PROD census (2026-10-22, marker first): all 6 active Bybit keys belong to users who hold other api_keys rows, so the sole-key forced rebuild (plans 04/05) would recompute none of them. Allocator snapshots are one aggregate row per (allocator_id, asof). A forced rebuild of an account with several keys rebuilds all its keys together and replaces that account's history in one atomic step, or refuses and writes nothing. Covered by tests before any PROD step. Supersedes the "recorded, not recomputed" handling of `[167.2.1.1-MULTIKEY-RECOMPUTE]`.

### Claude's Discretion
- Which side of the contradiction is right is the research question, not a decision. Plans must derive it from the pinned ccxt source and docs, and must show a test going RED on the wrong reading.
- Whether the fix is in the anchor, the wedge, or both follows from that finding.

</decisions>
