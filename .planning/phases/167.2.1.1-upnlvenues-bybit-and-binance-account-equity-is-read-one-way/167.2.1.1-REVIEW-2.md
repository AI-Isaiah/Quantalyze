## Round-1 findings: verdicts

### CR-01 [HIGH]: a forced rebuild on a multi-key allocator gap-fills the aggregate curve. **FIXED**

`equity_reconstruction.py:4104-4113`: a forced job calls `_allocator_has_other_api_keys` inside the guarded `try`, before the mt5 branch and before the crawl.

- `lookup_failed` raises `ForcedRebuildRefusedError("sibling_lookup_failed")`.
- `has_siblings` raises `ForcedRebuildRefusedError("multi_key")`.

Both reach the existing FAILED/permanent arm, which writes nothing and leaves the marker untouched. Both tokens are in `FORCED_REBUILD_REFUSAL_REASONS`, and the closed-set test pins them.

The new test seeds 9 of 10 days with a sibling row. It asserts no crawl and exactly 9 rows afterwards, so an insertion is now visible, which the round-1 test could not see. Handoff B3b now enqueues forced jobs for sole-key allocators only, and B3c counts any forced row on a multi-key key as a STOP. D-04/D-05 are respected: multi-key accounts are recorded as owned by ACCTREBUILD 167.2.1.1.2.

### WR-01 [MEDIUM]: a sole-key forced replace deletes stored days the replay does not cover. **FIXED** (option 1, refuse)

`equity_reconstruction.py:4160-4176`. After the crawl, a forced job refuses `history_outside_replay` unless every stored `asof` is a day the replay emits. `_allocator_snapshot_asofs` (`:1519-1532`) pages through `paginated_select` with a total order (`asof` ascending under the `(allocator_id, asof)` key), so the PostgREST row cap cannot truncate the set. A failed read bubbles to the generic arm as FAILED, never a pass.

Both sides use the same format: replay rows are `date.isoformat()` and the stored `date` column comes back as `YYYY-MM-DD`. The replay loop runs `while cur <= end_date`, so today's refresh row is a replay day, and the guard does not refuse every job.

The check-then-replace race is documented as accepted at the guard. In practice it bites only when the crawl crosses UTC midnight, and then the refresh row would have carried the same day the replay writes.

Handoff B5(iii) makes `history_outside_replay` a founder STOP. B5(v) now STOPs on any added or removed row.

### WR-02 [MEDIUM]: the forced anchor can silently miss part of the open uPnL. **FIXED** (for Bybit, as the round-1 fix proposed)

`equity_reconstruction.py:3259-3294`. When `refuse_unread_positions` is set on an additive venue, the forced path now refuses `positions_unreadable` in four cases:

- (a) 200 or more position rows, a possibly truncated read.
- (b) An open position (`contracts` nonzero or unparseable) whose `unrealizedPnl` is missing or non-numeric. A flat one is still skipped.
- (c) On Bybit, `balance["info"]["result"]["list"][0]["totalPerpUPL"]` is absent or unparseable.
- (d) On Bybit, the summed position uPnL differs from `totalPerpUPL` by more than `max(1 USD, 0.5% × wallet figure)`.

Check (d) is what closes the USDC-settled and inverse gap that `[167.2.1.1-BYBIT-POSITIONS-USDT-LINEAR-ONLY]` books. Every refusal stays inside the existing `except ForcedRebuildRefusedError: raise`, so the blanket arm cannot swallow it into `anchor_unreadable`. The unforced path is unchanged apart from SFH-3's flag. Binance has no aggregate cross-check (see the notes below).

## Notes below the reporting bar (LOW, not counted, no fixer action)

These are recorded so they are not lost. Each is below MEDIUM: either fail-closed, or caught by the handoff.

1. **The persist half still re-runs the sibling lookup** (`equity_reconstruction.py:4321`). A forced job that passed the pre-crawl check can still end DONE without replacing anything in two cases: the second lookup fails transiently, or a key row is added during the crawl. The job then takes the DO-NOTHING persist, finishes as `reconstruct_complete` with `atomic_replace: false`, and inserts only replay days that are not stored. The WR-01 guard keeps the stored set inside the replay, so that is almost always none. Handoff B5(vi) STOPs on `atomic_replace` false, so it is not silent. A one-line close: on the forced path, refuse when this second result reports `has_siblings` or `lookup_failed`.
2. **The `totalPerpUPL` tolerance scale contradicts its own comment** (`:3083-3092`). The comment says the drift "follows notional", but the tolerance scales with the wallet figure. On a leveraged book a few seconds of price movement can exceed 0.5% of the wallet and refuse falsely. This fails closed: `positions_unreadable` is re-enqueued once under B5(iii).
3. **Binance has no aggregate uPnL cross-check.** Coin-M positions are never requested, so a forced Binance anchor can still omit them. No Binance key exists (`[167.2.1.1-BINANCE-FUTURES-WALLET-UNREAD]`), and the handoff enqueues no Binance forced job.
4. **Two TODOS readings are now stale.**
   - `[167.2.1.1-ANCHOR-POSITIONS-READ-FAILURE]` still says the unforced wallet-figure anchor carries "no data-quality flag". SFH-3 now records `anchor_positions_unread` in the completion audit. It is still not an `EquityDQ` key, so the entry stays open, but its Reading should say this.
   - `[167.2.1.1-BYBIT-POSITIONS-USDT-LINEAR-ONLY]` does not say that the forced path now refuses on a `totalPerpUPL` mismatch.
5. **The `day-the-replay-does-not-emit` test case seeds a future date** (`END_DATE + 3`), not a gap day inside the window. The guard is a set comparison, so this is equivalent for the code under test, but the case name overstates what it models.
