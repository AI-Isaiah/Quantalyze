**Part B' — D-02 recompute for every Bybit account, multi-key included (product RPC only; no hand INSERT, UPDATE or
DELETE).**
- Reversibility: one-way for stored rows. The whole-account or sole-key replace rewrites the allocator's
  `allocator_equity_snapshots` in one transaction. This is settled by D-02 and D-04 (founder, 2026-10-22), so there is no
  new checkpoint.
- What plans 05 and 07-10 guarantee: a forced job either writes, in one replace, the per-day sum of every exchange
  account's anchored curve (each counted once, a Deribit one as 0, over the days they all share, and only when every
  stored day is reproduced), or it writes nothing and fails with a named token.

B'0. Marker query first, in every SQL file run through `supabase db query --linked -f <scratch file>`:
`SELECT shobj_description(oid, 'pg_database') AS which_database FROM pg_database WHERE datname = current_database();`
- It must name PRODUCTION. NULL means re-set the marker; never proceed on a guess.
- No leading `--` comment line.

B'1. Census (read-only, counts only), per a-label:
- that user's api_keys rows by exchange, split working or not (working: is_active, disconnected_at NULL, sync_status NULL
  or not in revoked / sign_in_failed / error);
- and split stamped (venue_account_id set), marked (account_share_kind duplicate or composite_member) or neither;
- the TOTAL count of that user's api_keys rows (any status);
- the count of that user's `allocator_equity_snapshots` rows dated before current_date minus 730 days.
Predict each account's outcome by the code's rules:
- any key on okx or sfox -> account_key_venue_unsupported;
- deribit keys count as 0 (neither crawled nor refused);
- an exchange account with no working key -> account_key_not_working;
- two or more unstamped, unmarked working keys on one of bybit / binance / okx -> account_identity_pending;
- any pre-window row -> history_predates_window;
- otherwise "rebuildable unless history_days_unreproduced" (that token depends on the replay and cannot be predicted from
  the database).
A one-key user takes the sole-key path. Record the prediction per a-label. If every account is predicted to refuse,
still run B'2-B'5 (each refusal writes nothing and is the deployed proof), then ask the founder under
[167.2.1.1-ACCOUNT-REBUILD-BLOCKERS].

B'2. Before (read-only, scratchpad only), as plan 06 B2:
- `allocator_equity_snapshots (allocator_id, asof, value_usd)` for the Bybit accounts;
- `csv_daily_returns` for the active Bybit keys and the Bybit-backed strategies;
- `allocator_equity_derived (allocator_id, kind, computed_at, md5(payload::text))` for the Bybit accounts.

B'3a. In-flight pre-check (read-only): one query, with targets selected inside the SQL, returning:
- `now() AS t0`;
- the count of `compute_jobs` rows of kind `reconstruct_allocator_history` for EVERY api_keys row of the Bybit accounts,
  with status in ('pending', 'running', 'done_pending_children', 'failed_retry');
- the count of key-mode `derive_broker_dailies` rows for the active Bybit keys, and of strategy-mode ones for the
  Bybit-backed strategies, with status in ('pending', 'running', 'done_pending_children').
Keep t0 in the scratchpad. If any count is above 0, poll until 0, then re-run B'3a for a fresh t0.
`_enqueue_compute_job_internal` returns an existing non-terminal job's id instead of inserting, so a pending unforced
reconstruct would absorb the forced request.

B'3b. Enqueue through the product's RPC, with targets selected inside the SQL, printing only counts. Re-read the latest
`enqueue_compute_job` definition first.
- ONE forced reconstruct per Bybit account, on its earliest-created active Bybit key
  (`DISTINCT ON (user_id) ... ORDER BY user_id, created_at, id`):
  `public.enqueue_compute_job(p_strategy_id := NULL, p_kind := 'reconstruct_allocator_history', p_api_key_id := <that key>, p_metadata := jsonb_build_object('force_rebuild', true))`.
- Never a second forced job for the same account: two would race the same replace.
- The derive enqueues are as plan 06 B3b: per active Bybit key in key mode, and per Bybit-backed strategy in strategy
  mode.
- A returned id is not proof of a new job.
- A `serialization_failure` means a lost race: re-run B'3a, then B'3b.
- The flag literal is `force_rebuild`, pinned by `test_force_rebuild_key_spelling_is_the_handoff_literal`.

B'3c. New-job proof (read-only, right after B'3b). Per a-label: does a `reconstruct_allocator_history` row exist for its
chosen key with `created_at >= t0` and `metadata -> 'force_rebuild' = 'true'::jsonb`? Print the two counts.
- An account without one was absorbed: wait for that job to end, then repeat B'3a-B'3c for that account only.
- Likewise count the derive rows created at or after t0, per kind.

B'4. Wait until every enqueued job is terminal (status counts by kind for these targets, created at or after t0).
- A forced job may be DEFERRED by an exchange cooldown on ANY key of its account. It returns to pending and is claimed
  again, so keep waiting.
- A failed job is recorded by `error_kind` count, never hand-fixed.
- If waiting stops while an account's forced job is not terminal, that account is "not shown (job not terminal)".

B'5. After. Per a-label, read the chosen key's audit trail inside the SQL (`audit_log`, `entity_type = 'api_key'`,
`entity_id` = that key, `created_at >= t0`), printing labels and counts only.
- FORCED START = the latest `allocator.equity.reconstruct_started` row with
  `metadata -> 'forced_rebuild' = 'true'::jsonb`.
- TERMINAL AUDIT = the first row after it of `reconstruct_complete`, `reconstruct_failed`, `reconstruct_no_data`,
  `reconstruct_partial_unsupported` or `reconstruct_unexpected_noop`.
Apply in order:

(i) No forced start: not shown. Re-enqueue once through B'3a-B'3c; if still not shown, record "not shown" and ask the
founder. Never recomputed.

(ii) A `reconstruct_complete` with `reason = already_reconstructed_for_api_key` after t0: STOP and ask the founder (the
flag did not reach the handler).

(iii) The terminal audit is a `reconstruct_failed` whose `metadata ->> 'sanitized_message'` starts with
`forced rebuild refused (`: NOT recomputed. Record the token and compare it with B'1's prediction; a mismatch is
recorded and the founder asked.
- Re-enqueue ONCE through B'3a-B'3c after B'4 for these 6: positions_unreadable, anchor_unreadable,
  anchor_skipped_partial_ticker, account_state_unreadable, account_key_read_failed, account_keys_changed. If it refuses
  again, record "recorded, not recomputed (<token>)".
- Record-only, no re-run, for these 10: anchor_skipped_okx_terminus, anchor_skipped_unreliable_replay,
  anchor_skipped_implausible, account_identity_pending, account_key_venue_unsupported, account_key_not_working,
  account_key_no_rows, account_sum_empty, history_predates_window, history_days_unreproduced.
- Note positions_unreadable and anchor_unreadable on [167.2.1.1-ANCHOR-POSITIONS-READ-FAILURE], and each account-level
  record-only token's count on [167.2.1.1-ACCOUNT-REBUILD-BLOCKERS].
- A token outside the 16: STOP (deploy mismatch).
- Any other `reconstruct_failed`: record by `error_kind`, not recomputed.

(iv) A `reconstruct_complete` with a non-empty `anchor_partial_ticker_symbols`, or with `anchor_offset_implausible`,
`anchor_replay_unreliable` or `okx_terminus_hit` true: STOP and ask the founder.

(v) RECOMPUTED only when ALL of these hold:
- the terminal audit is `reconstruct_complete` with no `reason` key and none of (iv)'s flags;
- the account's forced job (its B'3c row) has status `done`;
- `atomic_replace` is true;
- EITHER the account is multi-key by B'1, `account_rebuild` is true and `account_key_count` equals B'1's total key count
  for that user, OR it is one-key by B'1 and the audit has no `account_rebuild` key.
Then compare B'2 with a re-read in the scratchpad, per account: rows before and after; rows changed (absolute difference
above 0.005); rows added and removed; the max relative change to 3 significant figures; and the audit's
`account_exchange_accounts`, `account_zero_contribution_accounts` and `account_days_incomplete`.
Expected:
- a level move of about the summed open uPnL at the rebuild day;
- for an account whose stored history was first-writer-wins (one key's value per day), a move of up to the other
  exchange accounts' equity on earlier days. Record the size; do not judge it.
- An account whose key was informative in Part A but shows 0 changed rows is recorded "informative at A, unchanged at
  B'5", not silently.

(vi) Everything else is NOT recomputed and is recorded with its cause:
- a multi-key completion with `atomic_replace` false or without `account_rebuild` is a STOP (the deployed code is not
  D-04's);
- `reconstruct_unexpected_noop`, `reconstruct_no_data` or `reconstruct_partial_unsupported` is "recorded, not recomputed
  (<kind without the prefix>)", with the B'2-versus-after row counts beside it, and the founder is asked if any row
  changed;
- no terminal audit while the job is terminal is "not shown (no terminal audit)" with the row counts, and the founder is
  asked;
- anything else is "not shown (<cause>)".
Per key and strategy, whatever the reconstruct outcome: derive rows changed beyond 1e-12, expected 0 apart from days that
legitimately moved (the derive is realized-basis and this phase did not change it).

B'6. Record B'1 (with the predictions), B'3c and B'5 in the phase VERIFICATION/UAT as counts, ratios and per-label
outcomes: recomputed / recorded, not recomputed (<token or kind>) / not shown (<cause>) (SC-3). Delete the scratchpad
readings.
