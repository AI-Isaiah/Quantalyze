## Summary

The Bybit anchor reading holds up. I checked it against ccxt's real `bybit.parse_balance` in the installed venv (`account['total'] = safe_string(coinEntry, 'walletBalance')`), and `fetch_positions()` with no symbols defaults to `category=linear`, `settleCoin=USDT`, `limit=200`. The resulting state is consistent across paths:

- The reconstruct anchor (wallet + position uPnL) now matches the holdings AUM (USDT spot row + derivative uPnL).
- The derive anchor stays at the wallet figure with a structural 0.0 wedge.
- The cross-path test ties all three to one real-parsed payload.

The D-01 probe never writes. It makes one SELECT and two GET reads through a proxy that allows only those calls, and the emitter is a whitelist. I found nothing in it at MEDIUM or above.

The defects are in the `force_rebuild` path (plans 04 and 05):

- On a multi-key allocator it does not just "keep first-writer-wins". It **inserts this key's single-key replay value into any day the aggregate curve is missing**. I measured this on the branch's own fixtures. Per D-04, every active Bybit key is multi-key, and those are exactly the keys the post-deploy handoff (plan 06 B3b) enqueues.
- On a sole-key allocator the "anchored or nothing" contract does not cover what the atomic replace deletes.
- The forced-path guarantee ("anchored including open uPnL") has holes that let a position's uPnL drop out silently.
- Half the refusal arms have no test that can fail.

## Critical Issues

### CR-01: [HIGH] A forced rebuild on a multi-key allocator writes single-key values into the aggregate curve's missing days

**File:** `analytics-service/services/equity_reconstruction.py:3990` (flag bypass), `:4246-4250` (multi-key persist), `analytics-service/tests/test_reconstruct_force_rebuild.py:253-295`

**Issue:** `forced` skips the marker short-circuit for every key, sibling or not. The persist half then takes the multi-key branch, `persist_equity_snapshots(...)`, which is `upsert(on_conflict="allocator_id,asof", ignore_duplicates=True)`. That is ON CONFLICT DO NOTHING, which is not the same as "write nothing". Every `asof` in the replay that has no aggregate row gets an INSERT carrying **this one key's** replayed equity.

`allocator_equity_snapshots` is one aggregate row per (allocator_id, asof) across all keys (CONTEXT D-04). So any day where the daily refresh did not write (a worker outage or a skipped refresh) becomes a dip to the Bybit-only value, wedged between aggregate neighbours.

Measured on this branch: a scratch copy of `test_forced_rebuild_cannot_overwrite_a_multi_key_allocators_rows` with one of the ten sentinel days removed ended with 10 rows. Nine were the 12345.0 aggregate sentinels and one was a new row at **1250.5** (the Bybit key alone) on the missing day. The scratch file was deleted afterwards and the tree is clean.

Why this matters now:

- **No benefit.** CONTEXT D-04 says all 6 active Bybit keys sit on multi-key users, and D-05 moved their recompute to ACCTREBUILD 167.2.1.1.2. A forced job on them cannot change any existing row, so it has no upside.
- **The handoff runs it on all of them.** Plan 06's handoff B3b enqueues `force_rebuild: true` for "each active Bybit key".
- **Nothing stops it.** B5(vi) records multi-key outcomes as "recorded, not recomputed (multi_key)" with "expected 0 changed rows", but has no STOP when rows were added.
- **The existing test cannot catch it.** It only counts surviving sentinels, and its crawl yields exactly the ten seeded days, so it can never see an insertion.

**Fix:** Refuse a forced rebuild on any allocator with another api_keys row until ACCTREBUILD owns it. Check before the crawl, which also avoids a 730-day venue crawl for nothing, and add a seventh reason to the closed set:

```python
forced = _job_requests_force_rebuild(job)
if forced:
    sibling = await _allocator_has_other_api_keys(ctx.supabase, allocator_id, api_key_id)
    if sibling.has_siblings or sibling.lookup_failed:
        # D-05: multi-key accounts are ACCTREBUILD 167.2.1.1.2's; a forced
        # DO-NOTHING persist would gap-fill the aggregate curve with one key's value.
        raise/return the existing ForcedRebuildRefusedError arm with reason "multi_key"
```

Add `"multi_key"` to `FORCED_REBUILD_REFUSAL_REASONS`. Add a test that seeds a multi-key book with a missing day and asserts that **no** row is added (row count and values unchanged), not only that the sentinels survive. Then drop multi-key keys from handoff B3b, or have B5 STOP on any added row.

## Warnings

### WR-01: [MEDIUM] A sole-key forced rebuild deletes stored history the new replay does not cover, and the audit cannot show it

**File:** `analytics-service/services/equity_reconstruction.py:4240-4243` (replace call, `purged = count`), `:2995-3008` (the refusal contract), `:1262-1284` (row emission)

**Issue:** Plans 04/05 describe the forced path as "writes a curve anchored to today's venue equity, or writes nothing". On a sole-key allocator it calls `replace_allocator_equity_snapshots`, which runs `DELETE FROM allocator_equity_snapshots WHERE allocator_id = p_allocator_id` and then inserts only the replay rows. Rows outside the replay are lost:

- **(a) Rows older than `today - BACKFILL_CAP_DAYS`.** A key first reconstructed months ago had its window start months earlier, so those days are deleted and nothing replaces them.
- **(b) Days the replay does not emit.** `_compute_daily_equity` appends a row only when `breakdown or total`, so days before the first in-window event, or where the replay sums to 0, are deleted.
- **(c) Daily-refresh rows.** Every `refresh_allocator_equity_daily` row since the first reconstruct (live holdings marks, `source='exchange_primary'`, indistinguishable by source) is overwritten by trade-replay estimates.

Before this phase, a marked key never re-entered the replace, because of the short-circuit. The `force_rebuild` flag opens that route. The completion audit sets `stale_snapshots_purged = count`, the INSERTED count, so no record anywhere says how many rows were deleted. Handoff B5(v) does compare rows before and after, but only after the one-way write has happened.

**Fix:** Pick one of these:

- **Bound the replace (narrowest).** On the forced path, refuse (reason `history_outside_replay`) when the allocator holds any snapshot dated before `rows[0]["asof"]`. Or pass the replay's date range to a scoped replace, which needs a migration.
- **Book it.** Record the deletion as an accepted consequence of D-02 in CONTEXT and TODOS, and add the pre-replace row count to the `reconstruct_complete` metadata as `rows_deleted`, so the loss shows up in the audit.

Either way, add a test that seeds a row dated before the replay's first row and asserts what happens to it.

### WR-02: [MEDIUM] The forced path can silently anchor without part of the open uPnL, contradicting PD-H's guarantee

**File:** `analytics-service/services/equity_reconstruction.py:3201-3216`

**Issue:** `refuse_unread_positions=True` refuses only when `fetch_positions()` raises or returns a non-list. Inside a readable list, three cases still drop uPnL silently:

- A position whose `unrealizedPnl` is `None` or non-numeric is skipped with a bare `continue`. ccxt's `bybit.parse_position` uses `safe_number('unrealisedPnl')`, and ccxt's own sample response for this endpoint shows `"unrealisedPnl": ""`, which parses to `None`.
- USDC-settled linear positions are never requested, because the default is `settleCoin=USDT`.
- Inverse positions are never requested either.

In every case the forced job writes a curve whose anchor leaves out some open uPnL, and on a sole-key allocator it replaces the stored curve in one write. That is the exact outcome PD-H exists to refuse. `[167.2.1.1-BYBIT-POSITIONS-USDT-LINEAR-ONLY]` books the coverage gap for the default path, but nothing on the forced path stops on it.

**Fix:** When `refuse_unread_positions` is set on an additive venue:

- Raise `ForcedRebuildRefusedError("positions_unreadable")` for any position with nonzero `contracts` whose `unrealizedPnl` is missing or unparseable.
- For Bybit, cross-check the summed position uPnL against the account `totalPerpUPL` already present in `balance["info"]["result"]["list"][0]`, and refuse when they disagree beyond rounding. That one comparison also catches the USDC and inverse cases.

Add a test for each case.

### WR-03: [MEDIUM] Three of the six refusal arms that guard a destructive replace have no test that can fail

**File:** `analytics-service/services/equity_reconstruction.py:2995-3008`, `analytics-service/tests/test_reconstruct_force_rebuild.py:405-480`

**Issue:** End-to-end tests cover `positions_unreadable`, `anchor_unreadable` and `anchor_skipped_partial_ticker`. Three arms have no test that drives them:

- `anchor_skipped_okx_terminus`
- `anchor_skipped_unreliable_replay`
- `anchor_skipped_implausible`

`test_forced_rebuild_refusal_reasons_are_a_closed_set` only compares the frozenset to a literal set, so deleting any of those three `elif` arms leaves the whole suite green. Plan 05's SUMMARY D4 records this as `human_judgment`. But the unreliable-replay arm is the one a Bybit account with inverse or unknown-ctVal perps hits. If that arm is gone, a forced sole-key rebuild atomically replaces the stored curve with an **unanchored** zero-cash replay, the failure PD-H exists to prevent. Under this repo's rule that data-integrity gates must be able to fail, that is a gap, not a judgment call.

**Fix:** Add one parametrized forced-path test per remaining reason, each asserting FAILED/permanent, the exact `forced rebuild refused (<reason>)` message, and the seeded rows unchanged:

- An OKX key with `hit_terminus` true.
- A replay that records an inverse perp fill (non-empty `inverse_perp_symbols`).
- A replay whose last value makes `abs(offset) > 5 * last_value`.

Show each one going RED with its arm removed.
