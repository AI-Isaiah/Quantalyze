## Summary

**The founder's question is settled: yes, D-02 requires `commit_scenario_batch`'s SQL copy to move, in a migration shipped in the same merge.** The fingerprint the commit RPC compares is NOT built from the commit route's `{ auditEvidence: false }` read. It is built from the dashboard's read (audit evidence ON): the browser hashes `holdingsFingerprintRows`, a by-product of `getMyAllocationDashboard`'s default-mode `fetchLatestHoldingsPerKey` call, and the RPC recomputes the same set in SQL from `audit_log`. If TS hides a key's same-day rows and the SQL does not, the client fingerprint lacks tokens the server still counts, and every book-mode commit of that allocator is refused with `portfolio_fingerprint_stale` (HTTP 409 "Refresh to load the latest holdings", a remedy no refresh satisfies) until the key's next written rows or the next UTC day. It is a loud refusal, not a silent mismatch. This is exactly the SFH-R2-01 / T-170.4-38 class that migrations `20260929120000` and `20261011120100` were written to close.

The route's `{ auditEvidence: false }` read (route.ts:843-848) feeds only the persisted audit sizing (`size_at_decision_usd`, `serverAumUsd`). It never touches the fingerprint. D-02 does not change that read at all (neither `audit_log` query is issued in that mode), but it widens an already-accepted, test-pinned difference: the dashboard hides a same-day-emptied key's rows while the commit's persisted AUM still counts them.

The rest of the phase is small and well-precedented. D-04 is a one-line gate change plus a type-union removal (`connected_empty` has exactly one production consumer). D-05 is a sibling of an existing pure function and one JSX block. D-01/D-03 are records. The main planning risks are procedural: the migration plan pulls in a full SQL-gate ritual (new annotated gate file, floors ratchet, snapshot regeneration, rollback file, parity test, retargeting the existing unpriced gate), and a census test (`complete-status-scan.test.ts`) forbids a new `=== "complete"` comparison in any non-test `src` file.

**Primary recommendation:** ship D-02 as TS reader change + `CREATE OR REPLACE` migration re-based on `20261011120100` (adds a `newest_meta` read and a `same_day_empty` flag that flips `has_rows`, nothing else), gated by a new annotated SQL gate with PARITY-FINGERPRINT literals bound to a new TS parity test; do D-04, D-05 and the records as independent TS-only plans in the first wave.

   `[VERIFIED: src/lib/queries.ts:5024-5028]` — built BEFORE `oneKeyPerAccountDay` narrows the dollar rows, because the RPC keeps every tied key. A key the reader hid contributes no row and therefore no token.

### What breaks if TS changes and SQL does not
- Hidden key K (same-day clean empty poll): client tokens omit K's tokens; SQL still counts K's rows (poll_day == latest_day is not `>`). Server set is a strict superset unless another contributing key holds the same `symbol:venue:type`. Result: `portfolio_fingerprint_stale`, HTTP 409, on every book-mode commit by that allocator until K writes newer rows or the next UTC day's poll (which passes the strict `>` on both sides). It is not silent: the user sees a refusal whose copy ("Refresh to load the latest holdings") cannot be satisfied.
- If K's rows were the whole book, the client fingerprint is `""`, the route sends null, and the precondition is skipped. So the failure appears exactly for partially-hidden books, which is the realistic case (one key flat, another not).
- Reverse skew (SQL deployed, TS not yet): the server drops K, the client still sends K's tokens: same refusal in the other direction. Migration and app deploy in one merge; a minutes-long skew window is the same one `20260929120000` accepted. `[ASSUMED]` deploy ordering (apply-test, then PROD apply, then app deploy) is as CLAUDE.md describes; no PROD access was used.

### The route's `{ auditEvidence: false }` read is not the other side of the comparison
- `route.ts:843-848` passes `{ auditEvidence: false }`; the reader then substitutes `Promise.resolve({ data: null, error: null })` for both audit reads (latest-holdings-per-key.ts:349, 358-382). Its rows feed `serverAumUsd`, `serverEquityAumUsd` and the per-row `size_at_decision_usd` audit figures only. It never produces or checks a fingerprint.
- Consequence for D-02: the persisted AUM figure will still include a same-day-emptied key's rows (service-written evidence only). This is the already-accepted rule stated in the reader's docblock: "ACCEPTED DIFFERENCE, pinned by a test: on the dashboard a newer clean empty poll ends a key's older rows; in the commit's mode it cannot ... The display may supersede; the persisted figure may not." `[VERIFIED: src/lib/latest-holdings-per-key.ts:284-287]` D-02 extends "newer" to "newer or same-day empty". The docblock (lines 275-290), the route comment (~790-797) and the KNOWN LIMIT test (latest-holdings-per-key.test.ts:869 and route.per-key-aum.test.ts:364) should be extended to say so; no behaviour change in the commit path.

1. **SQL twin reads `audit_log`; the TS commit path does not.** The fingerprint twin follows the dashboard reader (audit evidence on); the commit route's sizing read has audit evidence off. ## Poll events and the D-02 edge cases

**Event shape.** `run_poll_allocator_positions_job` emits, after persist and the status update:
```
"allocator.holdings.sync_completed",
{ "row_count": count, "holding_type_counts": {...}, "final_status": final_status, "asof": today_str }
```
with `final_status = "complete_with_warnings" if warning else "complete"` `[VERIFIED: analytics-service/services/job_worker.py:10984, 11051-11066]`. `count` is `len(rows)` returned by `persist_allocator_holdings`, which returns 0 for an empty list and otherwise upserts (never deletes) `[VERIFIED: analytics-service/services/allocator_positions.py:1664-1707]`. `asof` is `today_str`, fixed at handler start, so a poll crossing 00:00 UTC has `created_at` on the next day but `asof` on the start day (the `R3-WR-01` comment). Failures are different actions (`sync_failed`, `persist_failed`), so "the newest poll of any outcome" (`newestPollRes`, action = `sync_completed` only) is the newest COMPLETED poll of either status; a failed or still-running poll is invisible to it.

**How the reader already reads it.** `newestPollRes` (latest-holdings-per-key.ts:372-382) selects `metadata` from `audit_log` filtered by `user_id`, `action = POLL_COMPLETED_ACTION`, `entity_type = "api_key"`, `entity_id = key.id`, `order("created_at", { ascending: false }).limit(1)`; `partialPollDay(newestPollRes.data?.[0]?.metadata ?? null)` is computed at line 401. `pollRes` (358-369) is the same query plus `.eq("metadata->>final_status", "complete")`. The SQL `ORDER BY al.created_at DESC` puts NULL `created_at` first, as PostgREST does (`audit_log.created_at TIMESTAMPTZ DEFAULT NOW()` is nullable; `[VERIFIED: 20260407075303_portfolio_intelligence.sql:67-75]`).

**Recommended TS change (no new query; the audit-read count stays 2).** `queries.my-allocation.test.ts` asserts `expect(pollReads).toHaveLength(2)` for the dashboard, so a third `audit_log` read would break a pin. Inside the per-key reading, after the existing strict `cleanPollAsof > latestAsof` branch and before the final return, add:

### Known Threat Patterns (STRIDE) for the read-path changes
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Owner forges a clean empty poll to hide their own key's rows | Spoofing / Tampering | `log_audit_event` refuses `allocator.holdings.sync_completed` (D-18, arm D2); no INSERT policy for `authenticated`; display-only effect, no row deleted |
| Cross-tenant event read | Information disclosure | reader filters `user_id` and `entity_id`; RLS owner read; SQL scoped on `p_allocator_id` |
| TS/SQL skew causes unsatisfiable 409 refusals | Denial of service (self) | one PR, parity literals, gate arms; remedy is reversible (next poll) |
| Hidden rows read as "position closed" when the poll mis-parsed (funded account read empty) | Tampering (integrity of display) | known limit, display-only and reversible; Python refresh keeps its stricter two-part proof; recorded, not fixed |
| Hidden positions leak into persisted figures | Tampering | commit sizing uses `auditEvidence:false` (service-written evidence only); unchanged |
| Disclosure through the new line | Information disclosure | shows the owner's own key label, venue and symbols, all already visible in the tables; no PROD ids |
| Repudiation of a hide | Repudiation | n/a: the poll events remain in `audit_log` (immutable: UPDATE/DELETE revoked) |
| Elevation via the new migration | Elevation of privilege | SECURITY DEFINER with `SET search_path = public, pg_catalog`, ACL re-issued, `_assert_no_public_execute`; rls-policy-auditor and migration-reviewer must be clean |
