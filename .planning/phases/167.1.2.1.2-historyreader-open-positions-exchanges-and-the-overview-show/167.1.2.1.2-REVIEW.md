## Warnings

### WR-01 (RESOLVED in round 2, a69359349): The account-sibling consequence of D-02 is pinned on neither side, so the SQL twin can drift from the reader without a red gate [data-integrity]

**File:** `supabase/tests/test_commit_scenario_batch_fingerprint_sameday_empty.sql` (all five arms put key-k and key-l on separate accounts); `src/lib/fingerprint-sameday-empty-parity.test.ts:85-88` (KEYS: two exchanges, no shared `venue_account_id`); `src/lib/latest-holdings-per-key.test.ts` Case I (both siblings' rows at the same day D)

**Issue:** Both runtimes keep the hidden key in account grouping at its own day: SQL through `key_day.day`'s unchanged `ELSE p.latest_day`, TS through `reading: { day: latestAsof, hasRows: false }`. The migration header and the TS comment call this load-bearing ("so a sibling key on the same account still counts at that day"). The reverse consequence matters just as much. Take a sibling on the same account whose newest rows are from day D-1. The emptied key at D moves the account's newest day to D, so the sibling's D-1 rows must drop out.

No test exercises that shape:
- The SQL gate has no shared-account fixture.
- The parity fixture uses two unrelated exchanges.
- TS Case I puts both siblings at the same day D, where the rule holds whether or not the hidden key keeps its day.

Two mutations would pass all five SQL arms, the parity test and Case I:
- adding `WHEN r.same_day_empty THEN NULL` to the `day` CASE;
- filtering `account_newest` to `WHERE d.has_rows`.

Either one makes the server count the sibling's D-1 tokens while the browser's fingerprint drops them. Every book-mode commit of that book is then refused `portfolio_fingerprint_stale` (409), and no refresh fixes it. This is the SFH-R2-01 / T-167.1.2.1.2-12 class that this migration exists to prevent. PROD auto-applies migrations with no human gate, so this gate is the only stop.

**Fix:** Add a sixth SQL arm and its parity twin. Two keys share one account (same exchange, same non-blank `venue_account_id`):
- key-a: rows at 2026-10-10, newest poll clean, `row_count` 0, `asof` 2026-10-10;
- key-b: rows at 2026-10-09 only.

The reader's fingerprint is the always-kept third key's token alone. Assert that fingerprint is NOT refused and that one carrying key-b's token IS refused. Put the `PARITY-FINGERPRINT(sameday-empty-sibling-older)` literal in the gate and have the parity test read it. Annotate it with `RED-UNDER-M`, for example an `edit` that replaces `ELSE p.latest_day END AS day` with `WHEN r.same_day_empty THEN NULL ELSE p.latest_day END AS day`. Mirror it in `latest-holdings-per-key.test.ts` as a Case I' with key-b at D-1, expecting no rows. Moving FILES/ARMS floors and censuses follow the usual ratchet.
