# Phase 141.2 Plan 04: Retry-After parse-not-presence Summary

`hasContractualWait` now delegates to the shared `parseRetryAfterSeconds` (B20), so a 503
carrying `Retry-After: 0`, an empty value, garbage or a negative retries instead of
short-circuiting — while the parsed number is still discarded and never reaches a sleep.

## What changed

**`src/lib/resilient-fetch.ts`** — one line of behaviour and a rewritten docblock:

```ts
return parseRetryAfterSeconds(res.headers) !== null;   // was: res.headers.get("Retry-After") !== null
```

The 503 short-circuit and the capability check are unchanged. The docblock names the old
presence-only claim, says why it was unsound (it asserted the emitter's contract without
verifying the responder is bound by it), states the delegation, and states that the
platform-edge trigger is **unverified** — no prose anywhere claims it is observed.

**`src/lib/resilient-fetch.retry.test.ts`** — a new `[SEAM-06 / D-06]` describe with seven
cases, all driven through the real `resilientFetch` loop. The oracle is the **fetch count**
(with the returned status as a second, independent witness), never the predicate: the defect
lives in the relationship between the header value and the loop's fail-fast exit, so a
helper-level assertion could have been green while the loop still short-circuited. Two new
fixtures (`rawRetryAfterResponse`, `rawRetryAfterThenOkFetch`) exist because the existing
`retryAfterResponse` takes a `number` and therefore cannot type any of the finding-9 values.

**`docs/runbooks/seam-breaker.md`** — only the `### The Retry-After fail-fast` section, now
carrying a value→behaviour table and the operator line that matters: *"the response had a
`Retry-After`" is not enough to explain a single-attempt 503 in the logs — read the value.*
The trip-count table and the retry-count prose were **not** touched (plan 06 owns them); the
write-side corruption sentence and the one-sidedness note added by plan 01 are untouched and
sit outside this section.

## A6 disposition — resolved, unchanged

The `[SEAM-06]` per-attempt-latch case asserts **2** recorded failures against
`statusSequenceFetch(503, 503)`. Read the fixture: `statusSequenceFetch` resolves
`{ ok, status } as Response` — a **bare literal with no `headers` property at all**. The
capability check therefore degrades it to "no hint" both before and after this change, the
retry stays armed, and the 2-failures assertion **stays valid as written**. Confirmed green
throughout (including under the SC-J mutation). This also matters to plan 06: SC-M's ledger
row nominates exactly this case as the site where its mutation must be observed, and nothing
here moved it.

## Rule 7 resolution, on the record

**Reused `parseRetryAfterSeconds`; RESEARCH §4.4's hand-rolled `Number(raw.trim())` +
`Number.isInteger` shape rejected.** PATTERNS named the helper as the *exact* analog for this
file, and the repo already carries a `no-raw-retry-after-parse` contract entry
(`src/__tests__/contracts/REGISTRY.md`) that bans `Number()`/`parseInt()` of a `Retry-After`
outside `src/lib/retry/**` — so the researcher's recommendation would have needed a sanctioned
exception to ship at all. The researcher simply missed the helper. The helper's HTTP-date arm
is a capability, not a gap: the "state the HTTP-date gap in the docblock" instruction was
dropped rather than restated, because after delegation there is no gap.

## Deviations from Plan

1. **[Rule 3 — plan/tree drift, prose only] Runbook section coordinates.** The plan cites the
   `Retry-After` fail-fast section at `~:156-168`; on this tree it is at `:170-185`. The
   section is unique by heading, so the intent was unambiguous. No behaviour change.

2. **[Rule 3 — scope] Test 5 (non-503 scope control) discharged by the existing case, not
   duplicated.** `[SEAM-06 / D-01]`'s *"a counting 502 carrying a STRAY Retry-After still
   retries"* already drives a non-503 whose header parses to a **positive** value, so after
   this change only the status short-circuit can be preventing the fail-fast — which is
   precisely what Test 5 asks to pin. It was verified GREEN under the SC-J mutation and at the
   final tree. Writing a second copy would have added a duplicate, not a pin.

3. **[Rule 2 — kept a guard the delegation could have absorbed] The local
   `typeof res.headers?.get !== "function"` check stays.** `parseRetryAfterSeconds` defends
   with `headers?.get?.(…)`, which covers absent/undefined but would still throw on a `get`
   that is present and *not callable*. A throw here lands inside the classification window and
   would replace the real upstream error with a bookkeeping one — the docblock's own stated
   reason for the check. Kept, and the docblock now says it is the belt in front of the
   helper's braces rather than a duplicate of it.

4. **[Rule 11 — import spelling] `./retry/retry-after`, not `@/lib/retry`.** The plan offered
   either. Every other import in `resilient-fetch.ts` is a relative sibling (`./seam-errors`,
   `./seam-discriminator`, …), and the direct path avoids pulling `wait.ts` and
   `rate-limit-gate.ts` into this module's graph for no benefit.

**No hand-offs.** Nothing in this plan needed a fix that belongs to another plan's files.
