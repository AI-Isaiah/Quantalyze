## The through-line

141.1 re-derived the retry-safety audit's evidence and repaired the alert that watches
the seam. The review found that **both** re-derivations were wrong in the same direction:
they describe an intended state rather than the reachable one.

- The `onboard` retry-safety evidence assumes an idempotency key the handler does not
  always send.
- The flag-monitor denominator's docblock asserts "`correlation_id` is minted once per
  client `postProcessKey` call, above the retry loop, so a retried call reuses it" —
  true on the TypeScript side, false end-to-end, because the Python handler re-mints a
  `uuid4()` whenever the inbound id is not a bare UUID, and `wizardFetch` sends
  `wizard:<uuid>` on both retry-eligible flows.

So the phase's real subject is **claims that hold at one layer and break at the seam**.
Any fix that is verified only on the side of the seam it was written on repeats the defect.

### D-01 — `onboard`: no idempotency key ⇒ no retry (finding 1, BLOCKER)

`finalize-wizard/route.ts:1589` uses a conditional spread, so `wizard_session_id` is
absent from the context whenever `strategies.wizard_session_id` is NULL — nullable by
design (migration `20260728120000`: "NULL for legacy/admin strategies ONLY").
`process_key.py` then evaluates `idempotent_by_session` to False, skips the duplicate
pre-check, and mints a server-side `uuid4()` for the NOT-NULL SV column, so the unique
constraint cannot collide and attempt 2 inserts a second row.

**DECISION: the retry verdict for `onboard` must become conditional on the presence of a
usable idempotency key, not fixed by `flow_type` alone.**

⚠️ **Scope corrected 2026-08-01 (pattern-mapper C-1). This is NOT "a conditional at one
call site" as I first wrote.** `finalize-wizard` reaches the seam through `postProcessKey`,

That is an API change to a shared seam client, not a one-liner, and it must be planned as
one: every caller updated, and the default for a caller that says nothing must be the SAFE

has not earned.

Rejected: minting a client-side stable key to always populate the field. It is the better
end state but changes the cross-seam contract and the SV uniqueness semantics, which is a

### D-02 — flag-monitor: ATTEMPT grain on both sides, revert the dedup (findings 2, 3, 4, 7)

Four findings are one rewrite. The D-16 denominator is attacker-steerable (dedup key is
the inbound `X-Correlation-Id`, reachable via the UNAUTHENTICATED `/api/verify-strategy`),
silently truncating (unbounded `.select()` vs PostgREST `max_rows=1000`, HTTP 200 /
`error: null`), and collapses nothing on the only two flows it targets. Its stated
premise is false.

**DECISION: revert the denominator to `.select("id", { count: "exact", head: true })`
and make the ratio explicitly ATTEMPT-grained on both sides.**

Rationale: the Sentry numerator counts EVENTS, which are per-attempt. Audit rows are
written per handler invocation, which is per-attempt. Attempt-grain on both sides is
therefore internally consistent and needs **no dedup at all** — which removes the
truncation, the wire-controllable key, and the grain mismatch in one move, and restores
two properties the pre-D-16 code had: uncapped at any volume, and impossible to influence
from the wire.

The cost D-16 was chasing is real but must be stated honestly rather than engineered
around: retries inflate the denominator, so the rate biases DOWNWARD (quieter) when the
seam retries. That is the safer direction than the D-16 failure modes, which include
false pages and attacker-controlled silence. Note it in the docblock and in TODOS as the
known limitation; a true per-request rate needs a server-minted request id the retry
reuses, which is a separate piece of work.

⚠️ Both the docblock AND `docs/runbooks/seam-breaker.md` currently describe the D-16
semantics. Prose must move with the code or this phase recreates the drift it is closing.

### D-06 — `Retry-After` presence-only test (finding 9)

`hasContractualWait` returns true for any non-null header, so `Retry-After: 0` — which
means "retry now" — and an empty value both DISABLE the retry.

**DECISION: parse the value; treat it as a contractual wait only if it parses to a
positive number.** Keep the existing safety property that the value never drives sleep
timing; this changes only the boolean. Zero, empty, and unparseable all fall through to
the normal backoff path.

### D-07 — limiter double-spend (finding 8): re-measure, do not pre-engineer

A retried call spends two tokens of the platform-wide `500/hour` `/process-key` ceiling,
and 429 is classified non-counting so the breaker structurally cannot contain it —
draining it refuses the anonymous teaser and CSV flows that never retry.

**DECISION: no limiter code change in this phase.** D-01 and D-03 remove most retry
volume, so re-measure the worst case after they land. If the arithmetic still reaches the
ceiling, record it in the registry's cost note and raise as a separate decision. Do not
add a limiter-aware retry path speculatively.

### D-09 — `admittedAtMs` is captured once above the retry loop (finding 5, CONFIRMED)

**Added 2026-08-01. This finding had no decision and would have been dropped** — see the
correction note under D-03. It is CONFIRMED and user-facing, so it is in scope.

`resilient-fetch.ts:2099` captures `admittedAtMs` once, before the retry loop. The A-25
guard then judges attempt 2's failure with attempt 1's admission timestamp, so a failure
that is genuinely new evidence (attempt 2 was admitted AFTER the lock armed) is discarded
as stale. On the 30 s `optimize-weights` budget the deadline exactly equals
`BREAKER_COOLDOWN_S`, so the whole retried wave is suppressed identically: `/api/scenario/optimize`
keeps issuing full 60 s double attempts at a dead upstream instead of short-circuiting, and
allocators wait 60 s per click for a 502/504 rather than getting an immediate
`CIRCUIT_OPEN` 503 with `Retry-After`.

**DECISION: re-capture the admission timestamp per attempt**, so the A-25 guard compares
the attempt's own admission against the lock. The exact in-repo analog is the **per-attempt
latch reset** already at `resilient-fetch.ts:2124`/`:2199` (pattern-mapper) — follow that
shape rather than inventing a second mechanism.

The pin must drive a two-attempt sequence where the lock arms BETWEEN admissions and assert
the breaker re-arms. A test that only checks single-attempt behaviour cannot see this.
