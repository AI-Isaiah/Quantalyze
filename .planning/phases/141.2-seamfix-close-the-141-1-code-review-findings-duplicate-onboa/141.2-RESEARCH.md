## §3 — The breaker cluster (findings 5, 10, 11)

### 3.1 Finding 5 — `admittedAtMs` is captured once. CONFIRMED. **No decision exists (§0.2).**

`const admittedAtMs = Date.now();` sits at `src/lib/resilient-fetch.ts:2099`, **above** the
`for (let attempt = 0; attempt <= retries; attempt++)` loop that begins at `:2153`. `recordOnce`
(`:2125-2129`) closes over it and passes it to `recordSeamFailure`, whose A-25 guard is
`if (admittedAtMs <= existing.armedAtMs) return;` (`:1429`).

The loop *does* re-check the breaker before attempt 2 (`isBreakerOpen` at `:2179`), so attempt 2 is
independently ADMITTED at a later instant — but that instant is never captured. On the 30s
`optimize-weights` budget with `BREAKER_COOLDOWN_S = 30`, attempt 1's deadline exactly equals the
cooldown and the 250–500 ms backoff pushes the re-check just past lock expiry, so attempt 2 fires,
fails at t≈60.4s, and is judged against `admittedAtMs = 0` versus `armedAtMs = 200` — suppressed.

**Recommended fix (minimal):** make `admittedAtMs` a `let` and reassign it immediately after each
successful pre-attempt breaker re-check (i.e. inside `if (attempt > 0) { … }` after the
`reBreaker.open` throw). `recordOnce` closes over the binding, so the last attempt's admission
instant is what reaches `recordSeamFailure` — which is exactly right, including for the
post-return `instrumentBody` closure. This preserves A-25's stated predicate ("was this request
already in flight when that lock was armed") for each attempt individually, which is what the guard
means.

**Pin must drive the whole loop.** A helper-level test cannot see this: the defect is the
*relationship* between the loop and `recordSeamFailure`. Drive `resilientFetch` on a retry-enabled
budget with a lock armed between admission and attempt 2, and assert the store shows a re-armed
lock. Mutation: revert to a single capture ⇒ RED.

### 3.2 Finding 10 — corrupt-but-present lock ⇒ `SET NX` ⇒ the breaker can never arm. CONFIRMED, and it is a 141.1 REGRESSION (§0.1).

The exact path:

```
resilient-fetch.ts:1407  const existing = decodeBreakerLock(await redis.get<string>(breakerKey));
resilient-fetch.ts:1436  if (existing === null) {
resilient-fetch.ts:1446    written = await redis.set(breakerKey, value, { ex: ttlS, nx: true });   // refused
resilient-fetch.ts:~1497 if (written) emitBreakerTransition("open", …)                            // skipped
```

`decodeBreakerLock` collapses **two different states** — "key absent" and "key present but
undecodable" — into one `null`. Only the first justifies `nx: true`.

**Recommended fix (minimal, zero extra round trips):** capture the raw value and branch on ITS
presence, not on the decoded result.

```ts
const rawLock = await redis.get<string>(breakerKey);
const existing = decodeBreakerLock(rawLock);
…
if (rawLock === null) {           // key genuinely absent → nx is correct
  written = await redis.set(breakerKey, value, { ex: ttlS, nx: true });
} else {                          // key present (live lock, tombstone, OR corrupt) → SET…GET
  const displaced = decodeBreakerLock(await redis.set(breakerKey, value, { ex: ttlS, get: true }));
  written = displaced === null || displaced.expiresAtMs <= now;
}
```

This is correct on the `else` side too: a corrupt displaced value decodes to `null` ⇒ `written =
true` ⇒ the transition is emitted, which is truthful (this call DID arm the circuit). It also
composes with the finding-11 fix (§3.3): an implausible lock becomes self-healing on the next
recorded failure rather than permanently jamming the write path.

**Pin must drive `recordSeamFailure` with the corrupt value present.** CONTEXT D-04 already demands
this. The existing G2 case in `resilient-fetch.test.ts` exercises only `isBreakerOpen` plus one
successful fetch, which is why nothing reddened.

### 3.3 Finding 11 — span-only bound admits absurd absolute epochs. CONFIRMED by executed arithmetic.

The guard is purely relative (`src/lib/resilient-fetch.ts:1052-1053`):
```ts
const spanMs = expiresAtMs - armedAtMs;
if (spanMs <= 0 || spanMs > MAX_BREAKER_LOCK_SPAN_MS) return null;
```
Executed in Node [VERIFIED: `node -e`]:
```
Number('100000000000030000') - Number('100000000000000000') === 30000   (isInteger: true)
Math.ceil((1e17 + 30000 - Date.now())/1000) === 99998214430587          (isInteger: true)
```
So `open:100000000000000000:100000000000030000` decodes cleanly, `isBreakerOpen`
(`:~1120`) returns `retryAfterS = 99_998_214_430_587`, `CircuitOpenError`'s A-15 guard
(`src/lib/seam-errors.ts` — `Number.isInteger(retryAfterS) && retryAfterS >= 0`) accepts it, and both
seam clients emit it as `Retry-After: 99998214430587` — including to the anonymous teaser. The
`TODOS.md` sentence "A `Retry-After` of 1e17 can no longer be minted" is false.

**Recommended fix:** add a ONE-SIDED absolute bound — a live lock cannot expire further into the
future than its own maximum span.

```ts
export function decodeBreakerLock(
  value: unknown,
  nowMs: number = Date.now(),
): { armedAtMs: number; expiresAtMs: number } | null {
  …
  if (spanMs <= 0 || spanMs > MAX_BREAKER_LOCK_SPAN_MS) return null;
  if (expiresAtMs > nowMs + MAX_BREAKER_LOCK_SPAN_MS) return null;   // NEW — absolute plausibility
  return { armedAtMs, expiresAtMs };
}
```

Why one-sided: a lock in the far PAST is already handled — `isBreakerOpen` treats
`expiresAtMs <= now` as a tombstone and calls `announceBreakerClosed` (`:~1113`). Adding a
past-side bound would break tombstone semantics. The optional `nowMs` parameter keeps the decoder
deterministically testable without a fake-timer dependency, matching the module's existing style.
This also closes the *reachable* production variant the finding names: a writer instance an hour
ahead on the clock arms a legal-span lock, and every reader currently tells users to wait ~3600 s
instead of 30.

**Prose that must move with this fix:** the `decodeBreakerLock` docblock
(`resilient-fetch.ts:1016-1040`, specifically the ⚠️ PARSEABLE IS NOT THE SAME AS PLAUSIBLE
paragraph and the "The rejection direction is `null` … corruption still fails forward, **unchanged**"
sentence, which finding 10 shows is the opposite of unchanged on the write side), the runbook line
in `docs/runbooks/seam-breaker.md` that says corruption "decodes to `null` and reads CLOSED", and the
`TODOS.md` DISCHARGED entry (§0.1).

### 4.4 ⚠️ One refinement D-06 as written leaves open

D-06 says "treat it as a contractual wait only if it parses to a positive number." RFC 9110 §10.2.3
permits **two** forms: `delay-seconds` and `HTTP-date`. Under D-06's literal rule,
`Retry-After: Wed, 21 Oct 2026 07:28:00 GMT` — a legitimate contractual wait — parses to no number
and would be retried. The repo's own contract-bound emitter only ever produces delay-seconds
(`str(retry_after)` over an int), so the practical exposure is nil.

**Recommendation:** implement the delay-seconds parse with the module's existing A-15 discipline —

```ts
function hasContractualWait(res: Response): boolean {
  if (res.status !== 503) return false;
  if (typeof res.headers?.get !== "function") return false;
  const raw = res.headers.get("Retry-After");
  if (raw === null) return false;
  const seconds = Number(raw.trim());              // "" → 0 (falls through, correct)
  return Number.isInteger(seconds) && seconds > 0; // NaN / "0" / garbage → retry
}
```

— and state the HTTP-date gap **in the docblock**, rather than silently inheriting it. `Number("")`
is `0` and `Number("0abc")` is `NaN`, so empty, zero and garbage all fall through to the normal
backoff exactly as D-06 intends. `Number.isInteger` mirrors `CircuitOpenError`'s A-15 guard, which is
the repo's established shape for "a value that goes on, or comes off, the wire".

The existing safety property survives verbatim: **the value still never drives sleep timing.** Only
the boolean changes. Say so in the docblock, replacing the current sentence *"Only presence is
tested, so a malformed or hostile value cannot influence timing or logs"* (`:1932`), which will no
longer be accurate about presence.

### Pattern 1: Distinguish "absent" from "present but unparseable" (findings 10, 12)

**What:** Never let a decoder's `null` / a query's `error` collapse into the same branch as a
legitimately empty result.
**When to use:** Any store read whose result drives a conditional write, and any query whose zero
result has a distinct operational meaning.
**Repo precedent:** `src/lib/portfolio-exposure.ts:225-232` — *"an empty result and a query error
are distinct states; never collapse an error into `[]`"*. Global Rule 12 (fail loud) says the same.
Findings 10 and 12 are the same violation on two different data types.

### Pattern 2: A cross-seam predicate must be written identically on both sides

**What:** When TypeScript gates on a condition Python also evaluates, write the *same* predicate,
not an equivalent-looking one.
**Example:** Python `bool(context.get("wizard_session_id"))` ⇒ TS `Boolean(args.context.wizard_session_id)`.
Not `!== null` (diverges on `""`), not `typeof === "string"` (diverges on `""`).
**Why:** This is the phase's entire subject. A claim that holds at one layer and breaks at the seam
IS the defect class.

### Pattern 3: Prose moves with code, in the SAME commit

**Sites this phase must keep in sync:** the module docblock, `docs/runbooks/seam-breaker.md`,
`TODOS.md`, and the evidence strings in `seam-retry-registry.ts` (which are themselves runtime
values, so they are code). §0.1 and §0.3 list the specific lines.

### Anti-Patterns to Avoid

- **`git revert` for D-02.** It restores finding 12's silent form and would also revert the numerator
  repair if scoped by commit rather than by function (§0.4, §2.6).
- **Multi-line `retriesOverride` expression.** Reds `resilient-fetch.wiring.test.ts` for a reason
  unrelated to the change (§5.1).
- **Line-number citations in registry evidence strings.** `seam-retry-registry.test.ts:424-458` reds
  on `file.ext:NN` (§5.2).
- **A pin that restates a constant.** Finding 13's whole subject. If the assertion's inputs are all
  pinned literals, the assertion cannot fail.
- **Testing a helper instead of the wiring.** Findings 4 and 5 both passed their unit tests. The
  route.test.ts fixtures at `:250-252` assert `Set` behaviour on `{correlation_id:'cid-A'}` twice —
  a shape production never produces (§2.3).

### Pitfall 1: Reverting `getDenominator` by commit rather than by function

**What goes wrong:** 141.1-08 changed BOTH the numerator (removing the dead `path:` term, adding

### Pitfall 2: A D-01/D-03 pin that passes against a broken wiring

### Pitfall 3: Making `decodeBreakerLock` time-dependent without a seam for tests

**What goes wrong:** Adding a bare `Date.now()` makes the decoder untestable without fake timers and

**What goes wrong:** After D-03 moves `resync` out of the YES map,

### Finding 11 — one-sided absolute plausibility bound

```ts
// src/lib/resilient-fetch.ts:1042 — decodeBreakerLock
// Source: executed arithmetic (§3.3) proving open:1e17:1e17+30000 currently decodes.
export function decodeBreakerLock(
  value: unknown,
  nowMs: number = Date.now(),
): { armedAtMs: number; expiresAtMs: number } | null {
  if (typeof value !== "string") return null;
  const parsed = /^open:(\d+):(\d+)$/.exec(value);
  if (!parsed) return null;
  const armedAtMs = Number(parsed[1]);
  const expiresAtMs = Number(parsed[2]);
  const spanMs = expiresAtMs - armedAtMs;
  if (spanMs <= 0 || spanMs > MAX_BREAKER_LOCK_SPAN_MS) return null;
  // ONE-SIDED, deliberately: a lock in the PAST is a tombstone and `isBreakerOpen`
  // depends on decoding it to announce the close. Only the FUTURE side is implausible.
  if (expiresAtMs > nowMs + MAX_BREAKER_LOCK_SPAN_MS) return null;
  return { armedAtMs, expiresAtMs };
}
```

### Finding 9 / D-06 — parse, don't presence-test

```ts
// src/lib/resilient-fetch.ts:1935 — hasContractualWait
// Source: error_contract.py:116-117 (a 503's Retry-After is always > 0),
//         seam-errors.ts CircuitOpenError A-15 (the Number.isInteger discipline).
function hasContractualWait(res: Response): boolean {
  if (res.status !== 503) return false;
  if (typeof res.headers?.get !== "function") return false;
  const raw = res.headers.get("Retry-After");
  if (raw === null) return false;
  const seconds = Number(raw.trim());          // "" → 0; "0abc" → NaN; both fall through
  return Number.isInteger(seconds) && seconds > 0;
  // RFC 9110 §10.2.3 also permits an HTTP-date. `error_contract` only ever emits
  // delay-seconds, so a date form falls through to the normal backoff — ONE extra
  // attempt, bounded. Stated here rather than silently inherited.
}
```

### Finding 12 + D-02 — counting form WITH error capture

// src/app/api/cron/flag-monitor/route.ts:213 — getDenominator

async function getDenominator(args: {
