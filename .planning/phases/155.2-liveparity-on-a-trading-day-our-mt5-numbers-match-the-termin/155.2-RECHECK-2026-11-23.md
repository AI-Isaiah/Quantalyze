The hypotheses of a near-midnight placement (the 2026-10-30 03:00:00 reading), a clock-rule difference, a deal-type difference and window start-day selection are all refuted for both findings: the same harness, clock and window give 0 once the ledger and the Report are the same account.

**Classification.**
- Not a product money-math defect. Nothing in the shared backbone is implicated, and no fix is proposed there.
- Harness defect: nothing checks that a label's ordinal and its Report are the same account. `bind_report` binds the Report bytes to the worksheet, never to the key. In `docs/runbooks/mt5-parity/census-accounts.sql`, `keys_sharing_login` counts `venue_account_id` equality, so a key marked `duplicate` (whose `venue_account_id` is NULL) reads 0. That 0 hid this case (k2 0, k1 1).
- Founder ruling needed on which ordinal is MM3. k10 holds the MM3 account. k2 is a second key on MM2's account and carries the name MM3.

**Scope.** Every MM3 Gate A reading so far (2026-11-19, and the 2026-11-22 recapture above) measured MM2's ledger against MM3's Report. MM3's Gate A is therefore unjudged, not failed, until the binding is settled. The MM3 rows of the data-layer findings table above read k2, so they also describe MM2's account under a second key. This addendum records the reading and changes no exit state.

**Proposed fix shape (not applied).**
1. Harness: refuse a label by name (a new not-measurable reason such as `oracle_account_mismatch`) instead of bucketing it `unexplained`. Refuse when the label's key carries `account_shared_with_api_key_id`, or when the key's login is not the Report header's login. Compare the two logins in-process and never print them.
2. Census: count the `account_shared_with_api_key_id` link in `keys_sharing_login` as well.
3. After the founder rules: relabel MM3 to k10 in a fresh capture and re-run Gate A. The scratch run above predicts all five legs at 0.
