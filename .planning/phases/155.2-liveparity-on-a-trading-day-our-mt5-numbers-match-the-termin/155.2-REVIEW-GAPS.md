## Warnings

### WR-01: A curve whose head the normalizer drops gets a fabricated day-0 return (both runtimes; measured in Python)

**File:** `analytics-service/services/wealth_returns.py:312-317` (with `records_to_series` at `:109`, `curve_to_daily_returns` at `:219`); `src/lib/factsheet/resolve-series.ts:39-50, 126-129`
**Issue:** `from_base` / `fromBase` assumes the first level that SURVIVES normalization is the curve's first stored level `1 + r0`. The normalizers silently drop elements:
- Python `records_to_series` drops non-dict records, missing dates and unparseable dates. It logs "skipped N malformed records".
- TS `normalizeCurve` drops non-objects and non-string dates.

When the dropped element is the head, the second stored level is read against 1.0. Before this change that level had no predecessor and was absent, which is the house ABSENT-never-invent rule. Now it is a booked return worth two days of compounding. Measured at HEAD:

```
returns_series = [{'date':'2026-04-30x','value':1.02},{'date':'2026-05-01','value':1.0302},{'date':'2026-05-02','value':1.040502}]
daily_returns_from_row(row, name='s')  ->  2026-05-01 0.0302, 2026-05-02 0.0100
# true 2026-05-01 return is 1.0302/1.02 - 1 = 0.0100; 0.0302 is invented
# same output with a None head element
```

TS keeps the `"2026-04-30x"` string, so for this input it reads `0.02 @ 2026-04-30x, 0.01 @ 2026-05-01`. The two runtimes now disagree by a fabricated value rather than by an absent day. With a `null` head, TS fabricates the same 0.0302. The repo treats malformed heads as possible: `figure-parity-pages.test.tsx` seeds `"2026-04-30x"` and `"2026-04-3"` heads on purpose. That test passes only because the TS path keeps the string date and flags the record unreadable. The Python surfaces (portfolio compute, simulator, match, `mt5_parity_capture`) flag nothing and carry the invented day into Sharpe and correlation.
**Fix:** Read day 0 only when the curve's first STORED element is the first normalized point. Otherwise fall back to the old pairing, the same rule as a cut curve. Python, in `daily_returns_from_row`:

```python
first = raw_curve[0] if isinstance(raw_curve, list) and raw_curve else None
head_intact = (
    isinstance(first, dict)
    and levels is not None and len(levels)
    and pd.to_datetime(first.get("date"), format="ISO8601", errors="coerce") == levels.index[0]
)
derived = curve_to_daily_returns(levels, method, keep_absent=keep_absent and native,
                                 from_base=from_base and bool(head_intact))
```

TS, in `resolveDailyReturnSeries`: pass `fromBase && headIntact`, where `headIntact` checks that `raw[0]` is an object whose string `date` equals the first sorted point's date. Add one oracle case, "dropped head reads with the old pairing", that both runtimes read.

### WR-02: The "venue-agnostic" re-entry is silently scoped to {deribit, sfox, mt5} by the staleness view, and the binance test case asserts behaviour production cannot exhibit

**File:** `analytics-service/services/job_worker.py:4340-4357` (the `ledger_refresh_staleness` read); `supabase/migrations/20261114151700_ledger_staleness_closed_composites.sql` (`SELECT ARRAY['deribit','sfox','mt5']` and the final `WHERE sv.exchanges && lv.venues;`); `analytics-service/tests/test_key_mode_linked_strategy_recompute.py:42, 193-195` (the `_Read` double)
**Issue:** Plan 16 switched the last-return-date read from `strategy_analytics.returns_series` to `public.ledger_refresh_staleness` to satisfy the census (SUMMARY Deviation 1). That view emits rows only for strategies whose exchanges overlap the ledger venue set. For a binance, okx or bybit strategy, `.maybe_single()` returns None, `raw_end` is not a str, and the helper `continue`s with no log. Three claims are therefore false in production:
- The plan's must-have: "The rule is venue-agnostic: the tests run it for an mt5 key and a binance key and get the same enqueue decision."
- The test module's docstring: "never venue-scoped".
- The SUMMARY: "for every venue".

The test passes only because its `_Read` double returns a row for any strategy id (`self.db.analytics.get(...)`), which the real view never does for binance. In practice, binance, okx and bybit get `cron_sync`'s daily strategy derive. The surviving gap for those venues is a lag of up to one day between the 05:30 key fan-out and the next cron derive. Nothing documents that, and the G4-1 (b) ruling ("enqueue the analytics recompute after a key-mode derive") is not implemented for them. Under the repo's fail-loud rule, a scope narrowed silently and proven by a test double is the defect, more than the narrowing itself.
**Fix:** Choose one, state it, and re-pin the test to the real behaviour:
- (a) Accept the scoping. Name it in the helper docstring ("the view is ledger-venue-scoped; binance/okx/bybit are refreshed daily by `cron_sync`"). Make the `_Read` double honour the view's venue filter, and turn the binance parametrization into an assertion that no enqueue happens, with that reason in the test.
- (b) Keep it venue-agnostic. Read the date from a source with no venue filter. The census already allows `services.wealth_returns`: add a `last_curve_date(row)` helper there and select `returns_series` through it. Or use a dedicated service-role RPC or view whose only predicate is the `lr` lateral.

Either way, correct the SUMMARY's "for every venue".

### WR-03: The cooldown is not the fan-out's clock: the founder's weekly caps and the any-kind / `failed_retry` in-flight guard are missing

**File:** `analytics-service/services/job_worker.py:4265-4275` (`_LINKED_RECOMPUTE_COOLDOWN` and its "the two refreshers share one clock" comment), `:4362-4376`; compare `supabase/migrations/20261114152300_ledger_fanout_no_advance_weekly_cap.sql` (the `CASE ... THEN INTERVAL '7 days' ELSE INTERVAL '20 hours'` admission and the `cj2.status IN ('pending','running','done_pending_children','failed_retry')` guard)
**Issue:** The fan-out admission the helper says it mirrors has three conjuncts the helper drops:
1. **Weekly cap.** The window is 7 days when `marks_trailing_since` is 3 or more days old (Phase 174 D-01/D-04, "Re-admit weekly"). It is also 7 days when a completed derive and compute could not move a `series_behind` strategy (Phase 214 FRESHTRUTH, founder Q1 = A, "Weekly cap, never exclude"). The helper always uses 20 hours. A strategy whose strategy-mode refresh cannot advance while its key-mode series does is exactly the per-key-ahead shape this helper fires on, and FX-AI_V's own lag cause is still unexplained in RULINGS. Such a strategy is re-derived every day, which re-opens the cost the founder capped at weekly.
2. **In-flight guard, any kind.** The fan-out refuses a strategy holding any in-flight job of any kind, `failed_retry` included. Its comment calls two concurrent derives for one strategy "exactly what the venue that serialises on a single shared terminal registry cannot absorb". The helper covers derive and compute jobs created in the last 20 hours only. `enqueue_compute_job`'s dedup covers (strategy, kind) over pending, running and done_pending_children, not `failed_retry`. A `failed_retry` derive older than 20 hours, or an in-flight job of another kind, does not stop a second derive.

The comment "so a nightly key fan-out adds at most one chain per strategy per day and the two refreshers share one clock" is therefore only half true.
**Fix:** Mirror the fan-out's admission rather than one arm of it. Simplest: add the in-flight read (any kind, the four statuses, no age bound). Then either (i) compute the 7-day window with the same two predicates, or, better, (ii) express the whole admission once in SQL. Option (ii) is a small service-role function or view returning "admit / hold" for a strategy id, which both the fan-out and this helper read, so the clock really is single-sourced. If a migration is ruled out for this phase, implement (i) and cite both migrations' line ranges beside the constant.
