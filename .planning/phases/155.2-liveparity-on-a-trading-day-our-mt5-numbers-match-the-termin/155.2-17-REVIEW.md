### What was measured, not assumed

- **G5-3 rounding is correct.** `Decimal(x).quantize(Decimal("0.001"), ROUND_HALF_UP)` was compared with Node's `Number(x.toFixed(3))` on about two hundred thousand values. The set included random doubles, values snapped to exact half-thousandths, and hand-picked decimal ties that are not exact in binary (one, eight and zero plus or minus half a thousandth, positive and negative). **0 mismatches.** `toFixed` rounds the exact binary value, ties away from zero, and `Decimal(float)` with HALF_UP does the same. `-0.000 == 0.000` holds as Decimals. The matrix Sharpe values (`src/__tests__/mt5-parity-surfaces.test.ts`) come from the product's own producers: the factsheet payload, `computeOgHeadline`, `toStrategyRows`, `liveBookFigures` and the scenario composer. Grepping those producers finds no `toFixed` or `Math.round` on Sharpe, except the scenario's own 3-decimal store. So no surface hands the comparison a 2-decimal value, and 3 decimals cannot raise false rows from display rounding.
- **The `Account:` parser works on the real build 5830 Reports.** `report_account_matches` was run locally on the real Reports in the gitignored capture directory, printing only shapes and booleans. All three parse. Each has exactly one `Account:` row, shaped as two `th` cells with colspans 4 and 10. After the collector collapses whitespace, the cell holds 6 tokens, and the extracted token is all digits followed by ` (`. The raw markup inside the cell (any `<b>` wrapper, the exact separator character) was not inspected. With a dummy hash the call returns `False`, which means it parsed and compared, not `None`. A fourth HTML file there is refused by `parse_report` with `EmptyDeals` and has no `Account:` row (`None`). No login, filename or server name was printed.
- **No login leaks on any surface checked.** No login reaches an exception message, a log, the verdict JSON, the markdown, stdout or stderr. `report_account_matches` keeps the token in a local variable, returns only a bool or None, and raises nothing of its own. `reason` is `oracle_account_mismatch:<arm>`. No script serialises keymap rows into tracked output. The only `load_capture` callers in `scripts/` are the runner and `mt5_parity_records.py findings`. `findings` reads only labels and analytics rows (`_analytics_row`), and it writes markdown that is rendered and passed through `_write_scanned`. Neither reads the keymap's hash column.
- **The gate cannot fail open.** `oracle_account_check` returns None only when `report_account_matches` returns True. That needs exactly one `Account:` row whose token sha256 equals the captured hash. `evaluate_windows` is called only from the runner (`grep`: one non-test caller), so no other path skips the gate by passing the default `None`.

## Info

### IN-01 (LOW): The Sharpe tie test cannot tell exact-binary rounding from decimal-repr rounding

**File:** `analytics-service/tests/test_mt5_parity_findings.py:775`
**Issue:** The docstring and `_stored_sharpe` (`services/mt5_parity_findings.py:547`) claim exact-binary rounding, but the only tie under test is exact in binary. A mutant `Decimal(repr(x)).quantize(...)` passes all 84 tests. On the double nearest to one plus half a thousandth (`1 + 5e-4`), it rounds up to the next thousandth, while JS `toFixed(3)` keeps it at one because that double sits just below the tie. A later "simplification" to `Decimal(str(x))` would ship unnoticed.
**Fix:** Add `assert _sharpe_findings(1 + 5e-4, 1.0) == []` (JS stores both as one). The `repr` mutant would raise a finding there.

### IN-02 (LOW): Two parser arms in `report_account_matches` are untested

**File:** `analytics-service/services/mt5_parity_report.py:533`, `:539`
**Issue:** Each of these mutants passes every test:
- `len(found) != 1` relaxed to `not found`, which would accept a Report with two `Account:` rows by reading the first.
- The `break` at the Deals marker removed.

Neither shape occurs in the measured real Reports (exactly one row, before Deals), so this is a pinning gap only.
**Fix:** Add two parametrised cases: two `Account:` rows give `None`, and an `Account:` row placed after the Deals marker is ignored.

### IN-03 (INFO): The capture-side absent arm is shadowed for a null hash; only its rows-disagree branch is unpinned

**File:** `analytics-service/services/mt5_parity.py:1249-1250`
**Issue:** Dropping `if not rows or shared != {False} or len(hashes) != 1` passes every test. For a null hash that mutant is equivalent, because `report_account_matches(..., None)` returns None, which also gives `account_identity_absent`. What stays unpinned is the rest of the arm: empty rows (which, without the arm, would make `next(iter(set()))` raise an uncaught `StopIteration`), a non-bool `account_shared`, and per-key rows that disagree. The committed SQL produces none of these. The capture is a file across a trust boundary, so this is not a necessity finding.
**Fix:** Optional: one direct `oracle_account_check` test on a capture whose keymap rows carry two different hashes.

### IN-04 (LOW): D17-3 describes the hash's exposure too narrowly

**File:** `docs/runbooks/mt5-parity/capture-keymap.sql:9`, `analytics-service/services/mt5_parity_capture.py:128`
**Issue:** The code comment says "the login itself is never captured", and D17-3 says the hash "lives only in capture directories". Neither is quite true:
- `capture-keymap.sql` runs through the Supabase MCP (runbook README: "The phase orchestrator only, through the Supabase MCP"), so the unsalted sha256 also enters the orchestrator transcript.
- The hash is written for every mt5 key in the table, not only the label's key.
- A short numeric login inverts from that hash by brute force in seconds.

This is inherent to an offline check, because the harness needs everything required to recompute the hash. D17-3 accepted it as a limit. The finding is that the record understates where the hash goes.
**Fix:** Amend D17-3 and the `_KEYMAP_COLUMNS` comment to name the MCP transcript and to say the hash is equivalent to the login for privacy purposes. Never quote `raw/capture-keymap.json` into tracked text.

### IN-05 (LOW): The stderr line overstates two of the three arms

**File:** `analytics-service/scripts/mt5_parity_run.py:307`
**Issue:** Every mismatch prints "the label's key is not the Report's account", but two arms do not prove that:
- `account_identity_absent` means the binding is unverified, not that it is wrong.
- `account_shared` also fires for `account_share_kind = 'composite_member'`. The comment in the `api_keys_account_identity` migration calls that pair "legitimate and not a duplicate", so such a key can be the Report's own account.

Both cases still refuse, so nothing fails open. The wording can send the founder to relabel a binding that was correct.
**Fix:** Word it by arm: "is not verified as the Report's account" for `account_identity_absent`, and "is marked as sharing another key's account" for `account_shared`.

### IN-06 (LOW): Other refusals can pre-empt the named mismatch, and red-proof never names it on stderr

**File:** `analytics-service/scripts/mt5_parity_run.py:236-260`
**Issue:**
- `oracle_account_check` runs, but its result is only acted on after `propose_windows(...)` (line 248) has read the wrong account's capture against the Report. Any `ValueError` raised there exits through `_refuse` with that message, and no verdict naming `oracle_account_mismatch` is written.
- `red-proof` on a mismatched bundle was measured: exit 3, stderr `expectation failed for reclassify_balance, clock_shift_1h, drop_oldest_deal`. The mismatch shows up only as a `note:` in the markdown.

Both are fail-closed.
**Fix:** In `_prepare`, act on the mismatch before calling `propose_windows`. For example, emit the mismatch verdict for the fixed or run-day windows, or have `_cmd_red_proof` refuse up front with the arm name.

### IN-07 (LOW): The committed real-shape fixture does not carry the measured real header shape

**File:** `analytics-service/tests/fixtures/mt5_parity/report_realshape_synthetic.utf8.html` (unchanged by this plan); test cell at `analytics-service/tests/test_mt5_parity_account_binding.py:36`
**Issue:** The real Reports carry `Account:` as two `th` cells, colspans 4 and 10, and the second cell's collapsed text is a digit login, a space and a parenthesised group (6 tokens in all). The raw markup inside the cell was not inspected. Every committed fixture and test uses an invented `th` plus `td` row with colspans 2 and 12. The parser does handle the real shape (measured above), but nothing in the repo pins it. That is the same class as the 2026-11-19 Deals-header defect, where the synthetic fixture had invented a shape.
**Fix:** Make the real-shape fixture's header row match the real structure with synthetic values, e.g. `<th colspan="4">Account:</th><th colspan="10">0 (USD, Synthetic-Srv, real, Hedge)</th>`. Copy any inner markup (bold, separator) from the real file's structure without its values, and run one binding test against it.

### IN-08 (LOW): The census undercounts keys that share one holder

**File:** `docs/runbooks/mt5-parity/census-accounts.sql:9-11`
**Issue:** When K2 and K3 both carry `account_shared_with_api_key_id = K1` and both logins are NULL, K2 and K3 are not linked to each other. Each reads `keys_sharing_login = 1` while K1 reads 2. Every member still reads non-zero, so G5-2's purpose (no hidden duplicate) holds. The value just is not "keys sharing this login".
**Fix:** Optional: add `o.account_shared_with_api_key_id = ak.account_shared_with_api_key_id` (non-null on both sides) to the `IN` list, with an exec seed of two duplicates of one holder.

### IN-09 (LOW): The login comparison ignores the broker server

**File:** `analytics-service/services/mt5_parity_report.py:519-542`
**Issue:** MT5 logins are unique per server, not globally. A key holding login N on broker A passes against a Report for login N on broker B. This is inherited from the product identity, which stores the login without the server (TODOS A-3 and the `mt5_venue_account_id` docstring). Real collisions are unlikely, but the check proves login equality, not account equality.
**Fix:** Record it as a known limit beside D17-4. If the capture ever carries a server, compare the Report's server token as well.

### IN-10 (INFO): `contract_version` stays 1 although the keymap column set changed

**File:** `docs/runbooks/mt5-parity/capture-contract.json:2`
**Issue:** An older capture is still refused, by the exact-column check ("rows do not carry the contract columns"), so this is cosmetic. Bumping the version would let that refusal name the cause.
**Fix:** Optional: bump to 2 together with the test that pins it.

### IN-11 (INFO): `_stored_sharpe` raises `decimal.InvalidOperation` for |x| >= 1e25

**File:** `analytics-service/services/mt5_parity_findings.py:547`
**Issue:** Quantizing to 0.001 in the default 28-digit context overflows from 1e25 up (measured). A degenerate Sharpe of that size would crash `classify_matrix` with an untyped error instead of producing a finding. This is not realistic.
**Fix:** None needed, or guard with `localcontext(prec=60)`.

### IN-12 (INFO): Import order and list order

**File:** `analytics-service/services/mt5_parity_findings.py:27`, `src/__tests__/mt5-parity-capture-sql.test.ts:111-113`
**Issue:** `from decimal import ...` sits before `from collections.abc import ...` (out of isort order; ruff is not in CI). The three new `ALLOWED_CALLS` entries are placed above an otherwise alphabetical list.
**Fix:** Reorder both.
