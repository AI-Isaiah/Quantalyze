# Phase 155.2 Plan 16: key-mode derive re-enters the linked strategy's derive chain Summary

**A key-mode `derive_broker_dailies` that runs ahead of a directly linked strategy's analytics now enqueues that strategy's own strategy-mode derive chain head (carrying the `ledger-refresh` marker, once per 20 hours at most), at both key-mode exits, for the ledger venues the staleness view serves (deribit, sfox, mt5), not for every venue.** Corrected after review WR-02: the helper reads `public.ledger_refresh_staleness`, whose final `WHERE sv.exchanges && lv.venues` emits no row for a binance, okx or bybit strategy, so those get no re-entry from this path. That is by design, since `cron_sync`'s daily strategy derive serves them; the residual lag for those venues is at most the day between the nightly key fan-out and that cron. The helper's docstring names the scope.

## What the "analytics recompute" is (the founder-facing paragraph)

The per-key series runs ahead of the strategy analytics. On the sealed capture, FX-AI_V's per-key series ended 2026-11-18 while its strategy series ended 2026-11-15. The cause is a refresher gap. The nightly key fan-out derives every eligible key in key mode, which never enqueues `compute_analytics_from_csv`. The daily strategy-mode re-entry is `routers/cron.py` `cron_sync`, but `_sync_single_key` defers any key whose exchange is not in `EXCHANGE_CLASSES` (binance, okx, bybit, deribit) or not in `DAILY_PNL_VENUES` (okx, binance, bybit), so an mt5, sfox or deribit strategy never gets that daily derive. The only other strategy-mode refresher for those venues is the single-key ledger fan-out, which admits a strategy only once `ledger_refresh_staleness` reads it stale (a series older than 4 days). A lag of 1 to 4 days was invisible to every refresher.

Why this plan does not enqueue `compute_analytics_from_csv` alone: `run_csv_strategy_analytics` reads the STRATEGY-keyed `csv_daily_returns` rows, while a key-mode derive writes only `api_key_id`-keyed rows. Compute alone would re-publish the same stale strategy rows and close nothing. The repo's own name for the broker recompute is `_recompute_kind = "derive_broker_dailies"` in `cron_sync`: the strategy-mode derive rewrites the strategy-keyed rows and chains `compute_analytics_from_csv`. This plan enqueues that kind, as `cron_sync` does, carrying the single-key fan-out's refresh marker. It is the ruling's recompute expressed through the chain head, not a different fix.

## What was built

- `_enqueue_linked_strategy_recompute(supabase, *, api_key_id, per_key_last_day) -> list[str]` beside `_enqueue_allocator_compose` in `analytics-service/services/job_worker.py`, with `_LINKED_RECOMPUTE_COOLDOWN` (20 hours, citing migration 20261114152300's `INTERVAL '20 hours'`) and `_LINKED_RECOMPUTE_ATTEMPT_KINDS`.
- Called at BOTH key-mode exits (the at-least-2-day exit and the under-2-day short-circuit), BEFORE `_run_key_mode_compose_epilogue`, each inside its own outer try that logs `logger.exception` and cannot skip the epilogue, reach its `NavReconstructionError` handler, or change the DONE outcome. After review SF-01 each call is also bounded by `asyncio.wait_for(..., timeout=_LINKED_RECOMPUTE_TIMEOUT_S)` (30 s), with an `asyncio.TimeoutError` branch that logs the api key, so a stalled read can never spend the job budget and skip the epilogue. The two call sites are inline (not a closure) so the plan's call-count criterion reads 1 definition plus 2 calls.
- Enqueue rule: `per_key_last_day` is not None; the strategy is selected by `strategies.api_key_id = <this key>` (never a payload id) with status in `routers.cron.ALLOWED_STRATEGY_STATUSES` (function-local import); the strategy's `ledger_refresh_staleness.last_return_date` is not NULL (so it already has an analytics row with a dated point) and is earlier than `per_key_last_day`; and no `derive_broker_dailies` or `compute_analytics_from_csv` `compute_jobs` row was created inside the cooldown. After review WR-03 the cooldown is the fan-out's whole admission and not only its 20-hour arm: the window is 7 days when the marks have been paused 3 or more days (Phase 174 D-04, `marks_trailing_since`) or when a completed refresh could not move a `series_behind` strategy 8 or more days old (Phase 214 Q1 = A), and a strategy holding any in-flight job of any kind (`pending`, `running`, `done_pending_children`, `failed_retry`, no age bound) is never given a second derive. No SQL function or view column exposes that admission, so it is restated in the helper, with the migration cited beside the constants (no migration was added). The RPC payload is `{p_strategy_id, p_kind: 'derive_broker_dailies', p_metadata: {source: LEDGER_REFRESH_SINGLE_KEY_SOURCE, enqueued_at}}`, no correlation_id.
- Per-strategy failure isolation: `logger.exception` naming the key, the strategy and the exception class, then the next strategy.
- Docstring key-mode paragraph and the inline "dark until Phase 36" comment rewritten to the new contract; a comment beside `JOB_CHAIN_FOLLOW_ON` names the re-entry as not a chain edge (dict entries byte-unchanged).
- `analytics-service/tests/test_key_mode_linked_strategy_recompute.py` (the decision cases run for an mt5 key; after review WR-02 the `_Read` double honours the view's venue filter and one test pins a binance strategy to NO enqueue; driving the real `run_derive_broker_dailies_job`; the mt5 key runs through an offline transport double over the canonical deal fixture).

## Exclusions (named in code and here)

- Composites (`strategy_keys` members) get no strategy enqueue from this path. A composite's recompute is `stitch_composite`, which re-crawls every member itself, and the composite fan-out already refuses MT5-member composites ("on mt5 no composites"). A key that is only a composite member backs no strategy directly, so its strategies read is empty. Test: a composite-member key enqueues no `stitch_composite` and no derive, and the helper never reads `strategy_keys`.
- Allocator-only keys (back no strategy) get nothing new here, because the allocator compose epilogue already serves them. Test: no strategy enqueue, compose epilogue still runs exactly once.

## Side effects (no code)

- The derive carries the single-key refresh marker, so it gets the fan-out's Phase 161.1 D-15 protection. The bridge's branch (a) still shows a plain `complete` row as `computing` while the job is in flight, exactly as the fan-out's refresh does, but a failure keeps a published factsheet published (branch b-prime) instead of un-publishing it. A dedup onto an in-flight unmarked job loses the marker, which the existing REUSE-01 warning logs.
- It counts as an attempt for the ledger fan-out's 20-hour and weekly cooldowns.
- MT5 sessions stay serialised by `mt5_concurrency`.
- Added cost: at most one strategy derive chain per directly linked strategy per day.
