# Phase 155.2 Plan 08: G3 convention decomposition and G4 freshness lag Summary

Every G3 finding left after plan 07 is decomposed on the sealed capture and has a measured cause: three are the first-day return that the curve reader never emits (a CONVENTION, one ruling question), and three are the same three-day staleness window as the G4 findings (disposed of by the G4 ruling question). No code changed, no tolerance moved, no bucket was invented, and no DEFECT or UNEXPLAINED row exists.

## Method (capture side, untracked)

Two stdlib-only scratch scripts, run with `python3 -I`, live in the capture directory's `scratch/` folder. `g3_decompose.py` re-runs each surface's own recipe (the `computeScenario` recipe: sample sd, 252 for a traditional strategy, calendar days, compound cumulative, 3-decimal Sharpe and 5-decimal cumulative rounding) on that surface's own series and compares it with the factsheet cell. It applies every candidate change singly and in pairs and reports the smallest set that reproduces the factsheet figure (cumulative return within `MT5_PARITY_TOLERANCE`, Sharpe equal at 3 significant figures). Candidates: the five the plan names (population sd, active days, 365, simple cumulative, no rounding) plus two series-shape changes the stored series force (the first-day return, the series end day). It writes `derived/g3-decomposition.json` (one key per G3 finding id), `derived/g3-factsheet-reproduction.json`, and `g4_lag.py` writes `derived/g4-lag.json`.

Checks that the decomposition is sound: each recipe reproduces its surface's matrix figure exactly (`recipe_reproduces_surface` true on all six); the stored factsheet Sharpe is reproduced exactly by sample sd, 252, calendar days on the full daily series on all three labels, so the persisted scalar's convention is known and not assumed; the decomposition keys equal the six ids plan 07's table marks present (the plan's key check exits 0, and exits 1 when I drop one key from a copy, so it can fail).
