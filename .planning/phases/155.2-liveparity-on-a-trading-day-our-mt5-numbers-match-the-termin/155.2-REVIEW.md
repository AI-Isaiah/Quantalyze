An absent, empty or unknown exchange returns `null`, and `blendPeriodsPerYear` (closed-sets.ts:695-702) reads `null` as 365. So an unwired caller cannot move a crypto book to 252. All three call sites pass the map:

The maps come from the allocator's full `apiKeys` list, which is a superset of `contributingApiKeyIds`. So no contributing key falls back to `null` by accident. There are no `asset_class: "crypto"` literals left in a per-key builder.

## Warnings

### WR-01: A verdict can be judged on the wrong server clock silently, and it does not record which clock it used

**File:** `analytics-service/scripts/mt5_parity_run.py:153-158` (the `--clock-rule` default `"us"`), `:233-234`, `:274`. The verdict serialization does not carry the rule.

**Issue:** The phase widened `--clock-rule` "so each account is judged on the clock its derive used" (module docstring, lines 14-15). The new CLI tests say a wrong clock "would force a verdict on the wrong day placement, which is a silent parity miss, not a refusal" (test_mt5_parity_cli.py, header of the `--clock-rule forms` block).

But the flag still defaults to `us`. `resolve_mt5_server_clock` (mt5_server_clock.py:185-196) notes that "production carries only the integer until the rule is set", so an operator who leaves out `--clock-rule` gets the US DST clock on a fixed-offset account. Deal times then land on different days, and the `day_placement` and level legs are judged on that placement.

Nothing in `verdict.json` or the markdown names the clock: `verdict_to_json` has no clock or rule field. A reviewer reading the artifact cannot tell a right-clock verdict from a wrong-clock one. A wrong clock usually reads RED (a refusal-by-failure). But on a window with no flows or deals near midnight it can read GREEN on a placement the derive never used.

**Fix:** Make the rule required, or record it in the verdict, or both:
```python
parser.add_argument(
    "--clock-rule",
    type=_clock_rule_arg,
    required=True,  # no silent default: the operator names the derive's clock
    help="the server clock the derive used: eu, us, utc or fixed:<seconds>",
)
```
Then carry `clock_rule` into `Verdict` / `verdict_to_json`, and print it on the `verdict:` stdout line, so every sealed verdict names the clock it was judged on.

### WR-02: The Gate A unit guard is fail-open by default and never reads the currency the Report itself states

**File:** `analytics-service/services/mt5_parity.py:738-748` (`_unit_mismatch`), `:762` (`account_currency: str | None = None`); `analytics-service/services/mt5_parity_report.py:441-505` (`parse_report`)

**Issue:** There are two gaps in the guard that stops a non-USD Report being compared against USD books.

1. **Fail-open default.** `gate_a_legs(..., account_currency=None)` is the default, and `_unit_mismatch(..., None)` returns `False` when the marks carry no `native_unit`. That is the case for every pre-native-unit mark and every Deribit-shaped row. So any caller that leaves out the keyword, or a worksheet that lacks the reading, gets the money legs measured with no unit check. Both production callers pass it today (lines 276 and 1173), and the CLI enforces `require_complete`. The safety still depends on every future caller remembering an optional keyword. `None` means "unknown", which should refuse, not pass.

2. **The Report's own `Currency:` row is discarded.** The real-shape Report states its currency in its header block (fixture line 9: `<th colspan="2">Currency:</th><td colspan="12">USD</td>`), but `parse_report` never reads it. The guard therefore rests only on the hand-transcribed worksheet reading `account_currency` (provenance `terminal_reading`). The `_unit_mismatch` docstring calls it "a Report currency reading", which overstates what is checked. A transcription slip ("USD" typed for a EUR Report) passes a EUR deal ledger as USD money. The Report is sha-bound to the worksheet, so the cross-check costs one parse and no trust.

**Fix:**
```python
def gate_a_legs(..., *, account_currency: str | None) -> ...:  # required keyword
    ...
def _unit_mismatch(capture, ordinal, account_currency):
    if account_currency is None:
        return True  # unknown currency: refuse, never measure
    ...
```
Also have `parse_report` capture the `Currency:` header cell into `ParsedReport.currency`. Then refuse in `_prepare` (or in `bind_report`) when it differs from the worksheet's `account_currency` reading.

### IN-01: Comments still say per-key legs carry asset_class 'crypto'

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:3750-3752`; `src/app/(dashboard)/allocations/lib/scenario-compare.ts:384`
**Issue:** Both say "Per-key units carry asset_class 'crypto' (84-01), so every real book blend derives 365". After G2 that is false: a pure-mt5 book derives 252. The next reader of the money-math basis gets the retired premise.
**Fix:** Reword to "per-key units carry the class `assetClassForExchange` derives from the key's exchange (155.2 G2)".

### IN-02: The CLI re-implements the worker's fixed-offset parser and imports its private bound

**File:** `analytics-service/scripts/mt5_parity_run.py:66-72, 114-128`
**Issue:**
- `_clock_rule_arg` duplicates `_parse_fixed_offset_s` (mt5_server_clock.py:172-182) and imports the private `_MAX_FIXED_OFFSET_S`. The two can drift.
- It also refuses `EU` / `US`, which the worker accepts because it lower-cases.
- It accepts `utc`, which the worker does not take, so "the forms the worker takes" (docstring line 14) is not accurate.

**Fix:** Call the worker's own parser (catch `Mt5ServerClockConfigError` and re-raise it as `ArgumentTypeError`), or promote it to a public helper.

### IN-03: The api_key_id → exchange map is built in three places

**File:** `src/lib/queries.ts:5905`; `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:3145-3151`; `src/app/(dashboard)/allocations/AllocationsTabs.tsx:1180-1182`
**Issue:** There are three identical `Object.fromEntries(apiKeys.map(k => [k.id, k.exchange]))` copies. The phase's own invariant is "both surfaces annualize one book on one clock". If one copy later filters or normalizes differently, the composer and the compare columns disagree again. That is the T-66-08 drift class.
**Fix:** Add one exported helper (for example, `exchangeByApiKeyId(apiKeys)` in closed-sets.ts or the adapter), or ship the map once on the SSR payload.

### IN-04: The 252 clock for a pure-MT5 book assumes weekday-only observations, and nothing in this phase measures that

**File:** `src/lib/closed-sets.ts:627-635` (`assetClassForExchange`), and how it is used through `blendPeriodsPerYear`
**Issue:** The project rule is "risk by frequency". 252 is correct only if an MT5 per-key series posts returns on weekdays only. The derive's native basis is described as "the level identity on every calendar day from the key's first NAV day" (job_worker.py:4321-4322), and I found no weekend drop on the per-key writer path. The synthetic capture (k1: 10 rows, 0 weekend) cannot tell either way. If real MT5 per-key rows include weekend zero-return days, √252 on a calendar-daily series understates vol and Sharpe. This is a judgment call, not proven.
**Fix:** Count weekend rows in a real MT5 key's `csv_daily_returns` from the capture before the founder signs off on G2. If there are any, either drop them for traditional legs or keep 365 for those keys.

### IN-05: A USD-family deposit currency other than USD can never be measured in Gate A

**File:** `analytics-service/services/mt5_parity.py:722-748`
**Issue:** The marks migration stores `native_unit 'USD'` for every USD-family read (USDT, USDC and the rest; `20261029120000_api_key_nav_marks.sql:33-35`). `_is_writer_unit` accepts only the literal `USD`, so a broker account whose `account_currency` reads `USDT` is `not_measurable:unit_mismatch` on every leg, permanently. This fails closed, which is correct for money. But such an account can never reach a Gate A pass, and no message says why beyond `unit_mismatch`.
**Fix:** Decide explicitly, as a founder or phase decision, whether USD-family stablecoin deposit units are comparable at par. Record the decision beside `WRITER_BASIS_UNIT`.

### IN-06: Duplicated test helper in the surfaces suite

**File:** `src/__tests__/mt5-parity-surfaces.test.ts`. The `perKeyRows` / `nudge` closures are copied verbatim into the two `155.2-04` cases ("decomposition: a 1e-12 per-key gap..." and "cross_store tolerance: ...").
**Issue:** Two copies of the bundle-mutation helper. If one is edited, the other test can silently stop exercising the same mutation.
**Fix:** Hoist both to one `describe`-scope helper.
