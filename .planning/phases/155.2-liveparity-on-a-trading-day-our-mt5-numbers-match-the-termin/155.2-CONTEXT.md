## Implementation Decisions

### Report parser fix (the measured finding)
- Real MT5 build 5830 writes the Deals header as `<td nowrap><b>Time</b></td>` cells, not `<th>`, and adds a `Cost` column carrying `class="hidden"` before Commission. Deal rows carry 15 cells with the same hidden cell; the Deals marker, the totals footer and the next section marker span 14, the visible width. The synthetic fixture invented `<th>` headers and has no hidden column. Measured 2026-11-19 on the three real files (counts only): the unpatched parser refuses all three with `RowShapeRefused` at `_canonical_headers`.
- Fix at the root in `analytics-service/services/mt5_parity_report.py`, three parts: (1) `_canonical_headers` accepts a header row whose cells all share ONE tag (`th` or `td`) with colspan 1, and still refuses a mixed or spanned row; (2) `Cost` joins `REPORT_KNOWN_HEADERS` as a known, non-required header, and stays out of the money math (the unknown-header refusal is kept, so a hidden column is named, never dropped blind); (3) the collector records the `hidden` class token per cell and `parse_report` detects a footer or next marker by the VISIBLE width (header columns minus hidden ones), while a deal row must still match the full header width.
- The evidence that excluding `Cost` is right is the existing balance-continuity check passing on the real files. `BALANCE_CONTINUITY_ABS_TOL` is not touched; a refusal there is a finding, not a tolerance change. A scratch run of exactly this patch parsed all three real files to completion (deal counts only recorded in the capture directory).
- The test is built from the REAL shape with synthetic values only: a `td`+`<b>` header, the hidden `Cost` cell in header and rows, a span-14 totals row and a following `th` section marker. The existing `th`-header fixture stays green. The new test is shown RED by neutering the fix in a byte copy and restored from a byte backup (never git checkout/restore/stash).

### Real-file run and Gate A
- After the parser fix, the three real Reports are parsed locally and Gate A is judged per account. Outcomes (counts, pass/fail per gate per account, buckets) go ONLY into the capture directory; the tracked record holds labels, buckets, day counts and ratios to 3 significant figures, never amounts, logins, server names or account numbers.
- Gate A needs a sealed PROD capture. PROD reads go through the Supabase MCP only, run by the phase orchestrator (executors have no MCP and never use the CLI or Keychain against PROD), marker query first, per the README run order. The plan carries this as an orchestrator checkpoint; the executor writes the code and the local run commands, the orchestrator drops raw MCP results into the capture directory.
- The intake refuses a worksheet missing any required reading, and the weekend and statement readings do not exist yet. Do not add placeholder readings, do not mark the worksheet synthetic, and do not loosen the intake. If the CLI has no Gate-A-only path, Gate A is judged by calling the engine's `gate_a_legs` from a scratch script outside the repo and recorded as "Gate A only, Gate B unjudged".
- Any Gate A discrepancy is fixed at its root in shared money-math, never scoped to `exchange === 'mt5'`, or surfaced to the founder as a named-bucket ruling question. It is never guessed into a bucket.

### Discrepancies and flags (criterion 4, MT5-10 / MT5-15)
- Each finding F-155-01..29 in `155-FINDINGS.md` is root-caused: cross_store (series vs per-key return rows), last_return_date (series ending on different days across surfaces), Sharpe/CAGR/cumulative/max-drawdown gaps between `allocations_live_baseline`, `scenario_composer_book`, `scenario_composer_route` and the factsheet cell. A root cause in shared code is fixed there with a test that can fail; a difference that is legitimately a different convention or a staleness window becomes a named-bucket question for the founder, never a silent pass.
- `csv_source` (F-155-04..06) is classified from the code that writes it (`services/analytics_runner.py`) into explained-and-acceptable, defect or unknown. Explained-and-acceptable still needs the founder's written acceptance, which is a human_needed item.
