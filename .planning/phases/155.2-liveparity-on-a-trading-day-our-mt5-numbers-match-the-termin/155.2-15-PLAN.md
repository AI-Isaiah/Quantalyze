<objective>
Close founder ruling G3-1 (a), recorded verbatim in `155.2-RULINGS.md`: "align the route to include the first-day return. This is a gap-closure fix in shared code, covering both the TS reader and its Python twin, with a test that can fail."

The gap (F-155-14, F-155-19, F-155-29): the composer returns route derives daily returns from the stored cumulative curve and drops day 0, so its Sharpe runs on n-1 observations while the persisted factsheet Sharpe runs on n. RULINGS measured that adding the first-day return closes all three at 3 significant figures. The same missing first point is the remaining G1 cross_store day on F-155-02 and F-155-03 (MM2, MM3) and one of the four missing days on F-155-01 (FX-AI_V), per `155.2-FINDINGS.md`. The other three F-155-01 days belong to plan 155.2-16. Plan 12's recapture is the closure evidence for all six rows.

Why the fix goes in the ROW-LEVEL readers and not in the raw curve function (evidence read during planning):
- `services/metrics.py` writes `returns_series` from `cumulative = (1 + returns_for_chart).cumprod()` (geometric) or `1.0 + cumsum` (simple), with no base point. So the stored curve's first level is `1 + r0` and day 0 is exactly `w0 - 1` on both methods. That holds for a STORED strategy curve only.
- The raw function `equityCurveToDailyReturns` is also called directly on curves with no 1.0 base. One is `buildAllocatorPortfolioFactsheetPayload`, on the allocator's blended equity (its own comment warns against dollar-level ratios). The others are both `ReturnHistogram` calls: a scenario blend's histogram series, and a benchmark curve. Emitting day 0 there would fabricate a return.
- A curve whose head was cut has no base either: `_trim_returns_series` in `routers/portfolio.py` (verify-strategy correlation) and the writer's `cap_data_points` (5000 points, `services/transforms.py`). Read against 1.0, their first level would be a multi-year cumulative return booked as one day.

Never scoped to `exchange === 'mt5'` (success criterion 4): every stored-curve reader of every venue gains day 0.

Ship order: this plan ships as its own PR after the plans 01-10 PR lands and before plan 155.2-12, so the recapture in plan 12 sees it. Plan 12's `depends_on` names this plan.

Purpose: MT5-09 (surfaces agree) and MT5-10 (the discrepancy is fixed at its root in shared code).
Output: the day-0 read in both runtimes, the extended shared oracle, the caller census in the SUMMARY.
