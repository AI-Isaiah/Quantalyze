## Summary

The phase has two halves with one finding that changes how SC-2 must be planned. **Part A** (rule + SC-3) is Python-only and mechanical: state one price rule in a small pure module, apply it on the 15 paths that value an open position (most already conform; five need a code change: the CoinGecko fallback, the unbounded on-or-before carry, the poll's `$0` on a failed ticker, the anchor's silent `$0` on a `None` last, and the legacy refresh's run-day label), close the two NAVMTM leftovers (the `replay_key_equity` step when the day's mark is refused, and the moved-flow price of REVIEW-3 IN-02), and delete the dead `EquityCurveBuilder` return scalars. **Part B** (D-01) moves the legacy poll and refresh next to the mark window and labels the legacy row by the UTC day that closed. The cron move is an operator step from a runbook modelled on `docs/runbooks/navmtm-chain-move-go-live.md`, not executor work.

**R-1 (the finding SC-2 hangs on).** The legacy snapshot and the stored mark do not differ only by price rule and clock. For an OKX account with open USDT-margined perpetuals the legacy refresh counts the open profit twice: ccxt's OKX `fetch_balance()["total"]` is the raw `eq`, which the recorded OKX balance payload in the repo shows is `cashBal + upl`, and the refresh then adds each derivative row's `unrealized_pnl_usd` on top. A cross-curve test written only against price-rule fixtures would pass while PROD stays about one open-profit apart on OKX. The test fixtures must come from a real-shaped OKX payload, and the OKX spot-row basis (wallet `cashBal`, not `eq`) must be settled inside this phase. See "R-1".

**Primary recommendation:** Plan four Python-only plans in Wave 1 (rule+history/CoinGecko+anchor; poll gap + refresh price-gap hold; SC-3 deletion; derive/compose residual + IN-02), then Wave 2 for Part B code (closed-day label, OKX `cashBal` basis, cross-curve test) and the runbook, then a non-autonomous Wave 3 where the orchestrator moves the two crons (before 04:00Z on the cut-over day), re-captures the manifest and takes the post-deploy reading. N = 7 days (the repo's own `CARRY_AGE_CAP_DAYS`). No migration.

### Gap semantics (research question 2)

How a gap is represented and who consumes it today:

| Where | Representation | Consumer |
|---|---|---|
| History replay | `skipped_symbols` set, then telemetry `skipped_symbols` in the `reconstruct_complete` audit | Operators only; the day's `value_usd` omits the symbol |
| Anchor | `_AnchorPartialSet` (a set subclass with `wallet_total_usd`, `positions_unread`) | Reconstruct skips the anchor (`_anchor_skipped_partial_ticker`); the Bybit/Binance mark read refuses `wallet_unpriced` |
| Marks | `MARK_REFUSAL_TOKENS`, no row written (NAVMTM D-05) | `apply_marks` `mark_gap_days` / `covered_days`; `marks_trailing_since` shown on the chart |
| Native balance | `NativeUnpricedNote` + service-written `native_unpriced:<key>` marker | `_fetch_latest_holdings_per_eligible_key` counts `native_unpriced_accounts` and leaves the account out |
| Holdings marks | `mark_price <= 0` | `holding_marks` (skipped before the per-day pick; a missing day breaks the return chain) |
| Poll today | **none** (`$0` is written as a measurement) | the refresh sums it |

**The decision to pin (assumption A1, needs founder confirmation at plan review).** D-02 reads "a missing price is a named gap, never $0 ... a gap longer than a stated N days is named and skipped, not carried." Research reading: *history* valuation carries the last close for at most N days (the carry is what `_price_on` does today without a bound) and names it; beyond N the symbol is named and skipped (`skipped_symbols`). The *live* poll has no earlier close to carry, so a live gap is never filled: it is stored as a gap row and **the refresh holds the day** (precedent: 167.1.2.1.1 D-01, "a total that cannot be right is not written. The snapshot is first-writer-wins, so a day persisted short would stay short"). The existing hold ladder is `never_polled_working`, `carry_over_age`, `identity_pending` in `_refresh_hold_reason`; add `price_gap` with its `_HOLD_SENTRY_OUTCOME` entry (`held_price_gap`) and an audit count, same closed-set, counts-only discipline.

**N = 7 days.** Defensible from the repo itself: `CARRY_AGE_WARN_DAYS = 3` and `CARRY_AGE_CAP_DAYS = 7` in `equity_reconstruction.py` (quote: `CARRY_AGE_CAP_DAYS = 7`, comment "past a week an account's last marks no longer describe the book"), a founder-set cap (167.1.2.1.1 D-02/SC-5) for exactly this question (how stale may a carried mark be). Reuse the value, name it `PRICE_GAP_MAX_DAYS` in `price_rule.py`, and add one test asserting `PRICE_GAP_MAX_DAYS == CARRY_AGE_CAP_DAYS` so the two cannot drift apart silently. BRIDGERETURNS is N = 0 because a return is a ratio of adjacent days; a *level* may be carried because a level persists, a return does not. State that difference in the module docstring.

### Pattern 1: one rule module, imported by every path
**What:** `price_rule.py` holds the docstring that *is* the documented rule (CONTEXT: "one documented rule"), `PRICE_GAP_MAX_DAYS: Final[int] = 7`, and one helper `close_on_or_before(days, closes, day, max_gap_days) -> tuple[float, int] | None` (price and age in days, `None` for a gap). `_price_on` (both branches) and the CoinGecko lookup call it; `allocator_positions` imports only the constant and the gap predicate (`last` finite and `> 0`).
**When:** every path in rows 1-9.
**Example (shape, not final code):**
```python
# Source: this research; rule from CONTEXT D-02, N from equity_reconstruction.CARRY_AGE_CAP_DAYS
PRICE_GAP_MAX_DAYS: Final[int] = 7

def usable_price(value: object) -> float | None:
    """A price is usable only if finite and > 0 (BRIDGERETURNS: a mark <= 0 is a gap)."""
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        return None
    return float(value) if math.isfinite(value) and value > 0 else None
```

### Pattern 2: closed-day label through the NAVMTM function
Use `nav_marks.mark_day_for(now)` for the refresh label; do not re-derive "UTC date minus one" (the NAVMTM tests already pin it, and D-01 says "the same label as the mark").

### Pattern 3: neuter-to-RED per path
Every new test gets a drill: byte backup of the source file, break the rule at exactly the changed line, run the named test, see RED, restore, `cmp` exit 0 (see Validation Architecture).

### Anti-Patterns to Avoid
- **Zero-fill or forward-fill a live price.** A live `last` gap is a stored gap and a held day, never yesterday's price.
- **Editing `supabase-migrate.yml` or adding a migration to move the crons.** The move is `cron.alter_job` behind a marker guard, hand-run (NAVMTM precedent, and "a PROD migration auto-applies with no human stop").
- **Labelling holdings rows by the closed day.** `allocator_holdings.asof` stays the poll day (user polls overwrite the same-day row; BRIDGERETURNS picks the latest `updated_at` per day). Only the *snapshot* label moves.
- **Making the cross-curve test read its expected level from the code under test.** Hand-type every level.
- **Reading TEST's `statements` column as evidence** (CLAUDE.md currency note) and quoting any PROD id in tracked text.

How the files classify a row (read this before reading a number):
- **`bulk_written`**: a snapshot row sharing its `reconstructed_at` with more than 5 other rows of the same allocator. A history reconstruct or a window rebuild writes all its rows in one transaction (one `now()`), the daily refresh writes one. Rows that are `bulk_written` are anchored once and are NOT suspect. [ASSUMED] threshold and inference (A14); it is robust to the label cut-over, unlike a "written on its own day" test.
- **`suspect`**: a refresh-written (not bulk) snapshot row, on a day the allocator has an OKX holdings row group with at least one derivative row with a non-null `unrealized_pnl_usd` summing to a non-zero figure. The estimated overcount is that sum; it ignores a refresh row that carried an OKX key's holdings from an earlier day (`refresh_days_with_no_okx_holdings_that_day` counts the days where that could hide). When several OKX keys share a day the sum may count an account twice (`suspect_days_with_several_okx_keys`).
- **After the plan 04 deploy** the refresh rows written from then on are correct but still read as `suspect` (the SQL cannot know the deploy day). Take the BEFORE census before the poll fix is live if possible; for the AFTER census subtract the rows dated on or after the deploy day (the `last_suspect_asof` column makes the tail visible).

```sql
  SELECT k.user_id AS allocator_id,
         row_number() OVER (ORDER BY min(k.created_at), k.user_id) AS label_no
    FROM public.api_keys k
   WHERE lower(k.exchange) = 'okx'

okx_day AS (
  SELECT h.allocator_id,
         h.asof,
         count(DISTINCT h.api_key_id) AS okx_keys,
         count(*) FILTER (WHERE h.holding_type = 'derivative'
                            AND h.unrealized_pnl_usd IS NOT NULL) AS derivative_rows,
         coalesce(sum(h.unrealized_pnl_usd) FILTER (WHERE h.holding_type = 'derivative'), 0) AS okx_upnl_usd
    FROM public.allocator_holdings h
    JOIN okx_account a ON a.allocator_id = h.allocator_id
   WHERE lower(h.venue) = 'okx'
   GROUP BY h.allocator_id, h.asof
),
snapshot_day AS (
  SELECT a.label_no,
         s.allocator_id,
         s.asof,
         s.value_usd,
         (count(*) OVER (PARTITION BY s.allocator_id, s.reconstructed_at) > 5) AS bulk_written,

    FROM public.allocator_equity_snapshots s
    JOIN okx_account a ON a.allocator_id = s.allocator_id
),
joined AS (
  SELECT sd.*,
         d.okx_keys,
         d.derivative_rows,
         d.okx_upnl_usd,
         (NOT sd.bulk_written AND d.derivative_rows > 0 AND d.okx_upnl_usd <> 0) AS suspect,
         abs(d.okx_upnl_usd) / nullif(abs(sd.value_usd), 0) AS overcount_share
    FROM snapshot_day sd
    LEFT JOIN okx_day d
      ON d.allocator_id = sd.allocator_id AND d.asof = sd.asof
)
SELECT CASE WHEN GROUPING(label_no) = 1 THEN 'all' ELSE 'a' || label_no END AS account_label,
       count(*) AS snapshot_days,

       count(*) FILTER (WHERE NOT bulk_written AND okx_keys IS NULL) AS refresh_days_with_no_okx_holdings_that_day,
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY overcount_share) FILTER (WHERE suspect)::numeric, 5) AS median_overcount_share,
       round(max(overcount_share) FILTER (WHERE suspect)::numeric, 5) AS max_overcount_share,
       round(sum(abs(okx_upnl_usd)) FILTER (WHERE suspect)::numeric, 2) AS sum_abs_overcount_usd,
       round(max(abs(okx_upnl_usd)) FILTER (WHERE suspect)::numeric, 2) AS max_abs_overcount_usd
```

### D-06: the dust floor on the gap hold

#### Where an unpriced balance is detected

| Layer | Where | What it can know |
|---|---|---|
| Poll | `allocator_positions._fetch_spot_rows`: `mark_price = float(t.get("last") or 0.0)` and the per-symbol fallback `tickers[sym] = {"last": 0.0}` today; plan 04 turns them into a gap row (`mark_price` 0.0, `value_usd` 0.0, `raw_payload["price_gap"] = True`) | the quantity and the missing price. No account level (the derivative rows come from a second call) and no earlier price |
| Refresh | `_fetch_latest_holdings_per_eligible_key`, right after `_sel_rows` returns one account group's rows and before `rows.extend(one_key_per_account_day(...))`. The columns it already reads are `_REFRESH_HOLDINGS_COLUMNS = ("symbol, quantity, mark_price, value_usd, " "unrealized_pnl_usd, venue, holding_type, api_key_id, updated_at")` (`equity_reconstruction.py:2750-2753`), which is everything the gap test needs | the whole account's rows (so its USD level), and by one extra read an earlier priced row of the same key and symbol |
| Display | the Holdings tab (D-07), from `mark_price_usd` already in the payload | nothing about size; every gap row reads "no price" regardless of size |

The poll must NOT drop a dust row: the UI labels every gap row (D-07), and sizing needs data the poll lacks. The decision lives in the refresh, per account group.

#### What "size" can mean for a balance with no price

A balance with no usable price has no USD value by definition. The only evidence is an **earlier priced row of the same key and symbol**: estimated size = `quantity x that row's mark_price`, looked back at most `PRICE_GAP_MAX_DAYS` (7) days before the row's `asof` (the same N as D-04, so one stated carry bound serves both). The account's USD level is the sum, over the group's counted rows, of the AUM contribution (`services/holding_equity.holding_equity_contribution`, the AUM basis: spot `value_usd`, derivative `unrealized_pnl_usd`, a missing P&L counts 0 here).

| Case | Disposition | Why |
|---|---|---|
| estimated size known, `size < DUST_FLOOR_SHARE x level` (strict) | **dust**: left out of the day, named | D-06 |
| estimated size known, `size >= floor` or `level <= 0` | **hold** the day (plan 05's `price_gap` hold, with its WORKING-key / failing-key split) | D-04 |
| no priced row within 7 days (**unsizable**: never priced, or last priced longer ago than the carry bound) | **recommended: left out and named**, not held | continuity: such a balance has contributed $0 to every earlier legacy row since the poll started (today's silent `$0`), so leaving it out keeps the series comparable, whereas a hold would freeze the allocator's legacy store for a token that may never get a ticker. Founder question F2; `[ASSUMED]` A15 |

- **The named note** has the precedent of 167.1.1.2 D-07: `__pnl_missing__` is a structured `{count, symbols}` record stamped onto the stored snapshot's `breakdown` (`breakdown_to_store["__pnl_missing__"] = {...}`, `equity_reconstruction.py:6335`), protected from truncation by `_BREAKDOWN_PROTECTED_KEYS: tuple[str, ...] = ("STARTING_BALANCE", "__truncated__", "__pnl_missing__")` (`:554`) and not summed by `_sum_breakdowns` (non-numeric entries do not survive; pinned in `tests/test_reconstruct_whole_account.py` near line 378).
```sql
WITH gap AS (
  SELECT h.allocator_id, h.api_key_id, h.venue, h.symbol, h.asof, h.quantity
    FROM public.allocator_holdings h
   WHERE h.holding_type = 'spot'
     AND h.quantity > 0
     AND h.mark_price <= 0
),
sized AS (
  SELECT g.*,
         g.quantity * p.mark_price AS estimated_usd,
         (g.asof - p.asof) AS price_age_days
    FROM gap g
    LEFT JOIN LATERAL (
      SELECT q.mark_price, q.asof
        FROM public.allocator_holdings q
       WHERE q.allocator_id = g.allocator_id
         AND q.api_key_id = g.api_key_id
         AND q.symbol = g.symbol
         AND q.holding_type = 'spot'
         AND q.mark_price > 0
         AND q.asof < g.asof
         AND q.asof >= g.asof - 7
       ORDER BY q.asof DESC
       LIMIT 1
    ) p ON true
),
account_level AS (
  SELECT h.api_key_id,
         h.asof,
         sum(CASE WHEN h.holding_type = 'spot' THEN h.value_usd
                  ELSE coalesce(h.unrealized_pnl_usd, 0) END) AS level_usd
    FROM public.allocator_holdings h
   WHERE EXISTS (SELECT 1 FROM gap g WHERE g.api_key_id = h.api_key_id AND g.asof = h.asof)
   GROUP BY h.api_key_id, h.asof
),
latest AS (
  SELECT api_key_id, max(asof) AS latest_asof
    FROM public.allocator_holdings
   GROUP BY api_key_id
),
scored AS (
  SELECT s.*,
         (s.asof = l.latest_asof) AS is_latest_day_of_its_key,
         CASE
           WHEN s.estimated_usd IS NULL THEN '1 unsizable: no priced row within 7 days'
           WHEN coalesce(al.level_usd, 0) <= 0 THEN '2 account level not positive'
           WHEN s.estimated_usd / al.level_usd < 0.0001 THEN '3 below 0.01 percent'
           WHEN s.estimated_usd / al.level_usd < 0.001 THEN '4 0.01 to 0.1 percent'
           WHEN s.estimated_usd / al.level_usd < 0.01 THEN '5 0.1 to 1 percent'
           ELSE '6 at least 1 percent'
         END AS size_bucket
    FROM sized s
    JOIN latest l ON l.api_key_id = s.api_key_id
    LEFT JOIN account_level al ON al.api_key_id = s.api_key_id AND al.asof = s.asof
)
SELECT CASE WHEN GROUPING(is_latest_day_of_its_key) = 1 THEN 'all days'
            WHEN is_latest_day_of_its_key THEN 'latest day of each key'
            ELSE 'earlier days' END AS scope,
       size_bucket,
       count(*) AS unpriced_balance_rows,
       count(DISTINCT api_key_id) AS keys,
       count(DISTINCT symbol) AS symbols,
       count(DISTINCT asof) AS days
  FROM scored
 GROUP BY GROUPING SETS ((is_latest_day_of_its_key, size_bucket), (size_bucket))
 ORDER BY GROUPING(is_latest_day_of_its_key), is_latest_day_of_its_key DESC, size_bucket;
```

**File `unpriced-balances-current.sql`** (the current unpriced rows one by one: venue, symbol, quantity, last priced mark, share of the account level; scratchpad only because it carries amounts. The `USDE`, `PYUSD` and `USDB` symbols, which plan 04 will value at 1.0, appear here as the legacy stable-value zeros):

```sql
WITH latest AS (
  SELECT api_key_id, max(asof) AS latest_asof
    FROM public.allocator_holdings
   GROUP BY api_key_id
),
gap AS (
  SELECT h.allocator_id, h.api_key_id, h.venue, h.symbol, h.asof, h.quantity
    FROM public.allocator_holdings h
    JOIN latest l ON l.api_key_id = h.api_key_id AND l.latest_asof = h.asof
   WHERE h.holding_type = 'spot'
     AND h.quantity > 0
     AND h.mark_price <= 0
)
SELECT g.venue,
       g.symbol,
       g.asof,
       g.quantity,
       p.mark_price AS last_priced_mark,
       (g.asof - p.asof) AS last_priced_days_ago,
       g.quantity * p.mark_price AS estimated_usd,
       (g.quantity * p.mark_price) / nullif(lv.level_usd, 0) AS share_of_account_level
  FROM gap g
  LEFT JOIN LATERAL (
    SELECT q.mark_price, q.asof
      FROM public.allocator_holdings q
     WHERE q.allocator_id = g.allocator_id
       AND q.api_key_id = g.api_key_id
       AND q.symbol = g.symbol
       AND q.holding_type = 'spot'
       AND q.mark_price > 0
       AND q.asof < g.asof
       AND q.asof >= g.asof - 7
     ORDER BY q.asof DESC
     LIMIT 1
  ) p ON true
  LEFT JOIN LATERAL (
    SELECT sum(CASE WHEN r.holding_type = 'spot' THEN r.value_usd
                    ELSE coalesce(r.unrealized_pnl_usd, 0) END) AS level_usd
      FROM public.allocator_holdings r
     WHERE r.api_key_id = g.api_key_id AND r.asof = g.asof
  ) lv ON true
 ORDER BY share_of_account_level DESC NULLS FIRST, g.venue, g.symbol;
```

## Common Pitfalls

### Pitfall 1: the cross-curve test passes while OKX is wrong (R-1)
**What goes wrong:** price-rule fixtures with `total` set to a wallet value hide the `eq = cashBal + upl` identity. **Why:** ccxt parses `eq`, tests typed it as cash. **Avoid:** build the OKX leg through the real `parse_balance`; add a RED drill that reverts the poll to `eq`. **Warning sign:** the OKX leg's expected legacy level equals the mark exactly.

### Pitfall 2: `ignore_duplicates=True` makes the CoinGecko fix a no-op
**What goes wrong:** corrected close-labelled prices are inserted with DO NOTHING; old open-labelled rows for the same `(symbol, asof)` survive and are read. **Avoid:** new `source` tag, updating upsert, source-filtered read (row 3).

### Pitfall 3: a `price_gap` row looks like a measured zero to everything except `holding_marks`
**What goes wrong:** the Holdings tab and `holdingEquityIsReported` treat a finite `value_usd` of 0 as reported, so the AUM still shows `$0` for the asset. **How to avoid (CORRECTED 2026-10-27 by D-07, SC-5; the first-pass advice "the Holdings display stays as is and is booked as follow-up" is withdrawn):** the refresh holds the day (so the *curve* is honest), AND the Holdings tab labels the row as unpriced and the AUM note says it excludes the row. Keep the AUM *number* unchanged (a gap row contributes 0 on both runtimes already): D-07 changes what the screen says about that 0, not the sum. Do NOT widen `holding_equity_contribution_cases.json` (its schema is "ONE expected per case, three fields"); add a sibling fixture for the new predicate (Delta, D-07).

### Pitfall 4: holding the day silently
**What goes wrong:** a held day is a missing legacy day with no one told. **Avoid:** the Sentry `held_price_gap` outcome, one event from the leader job only, counts only (copy the `carry_over_age` branch), plus the audit count.

### Pitfall 5: the label change and the cron move are one event
**What goes wrong:** deploying the label alone lags the curve a day; moving the clock alone mislabels (run-day label at 01:00Z). **Avoid:** the cut-over section above; the runbook states the order and the collision outcome.

### Pitfall 6: moved flows change a second counter
**What goes wrong:** `flow_moves` is applied symmetrically by the stored-flows code; repricing only the `+` side leaves the `-` side on the old number. **Avoid:** report both amounts and test the stored flows too (the `held_out` and `flow_moves` assertions of the NAVMTM round-2 verdicts).

### Pitfall 7: deleting scalars trips three census tests
**What goes wrong:** `test_e1_sharpe_twr_parity::test_caller_census_matches_pinned_inventory` goes red on the *missing* side. **Avoid:** shrink the pin in the same commit; run `test_e1_delete_gate.py` and `test_dispersion_floor_sites.py` in the plan's verify command.

### Pitfall 8: stale tests that encode the behaviour being changed
`test_stale_last_mark_does_not_anchor` (row 14) and any `_price_on` test relying on a 400-day carry (the v0.15.4.3 pagination test uses a monotonic stub, check it). Name each oracle move in the plan.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A poisoned or erroring third-party price becomes a measured value | Tampering | `usable_price`; gap row + hold instead of a zero or a carried price |
| User-visible `sync_error` echoing venue text or symbols | Information disclosure | fixed copy constant keyed by status/venue (`sync_error_copy` contract) |
| Runbook leaking PROD identifiers into a public repo | Information disclosure | jobs named by `jobname`, never `jobid`; the renderer reads the marker from the manifest; counts only |
| Operator write on the wrong database | Tampering | marker query first, compare-and-set guard that raises, read-back with `marker_is_prod` |
| A read-only census file edited into a write (or carrying an id) before an operator runs it | Tampering / Information disclosure | one statement per file, static vitest guard (drill D-N20), marker query first, `supabase db query --linked -f <file>` from the main checkout only |
| The D-05 rewrite replaces a stored day the rebuild cannot reproduce | Tampering | the window function refuses inside its own transaction (`history_days_unreproduced`) and writes nothing; older rows are kept byte-for-byte; one forced job per account (two would race the same replace) |
| A price-gap row presented as a measured $0 to the user | Repudiation | D-07: the row reads `—` and "no price", the AUM note says it is excluded; the number is unchanged and the fixture pins the predicate in both runtimes |
