## Warnings

### WR-01 (MEDIUM, data integrity / money math): OKX `cashBal` override drops open profit from the book whenever the derivative read fails

**File:** `analytics-service/services/allocator_positions.py:708-724` (override) with `:1698-1745` (derivative arm partial success)

**Evidence:** `_fetch_spot_rows` now always replaces OKX spot quantities with `cashBal` (= `eq - upl`), on the premise that "the derivative rows already carry `upl` as `unrealized_pnl_usd`". But `fetch_allocator_holdings` runs the spot read first and, when `_fetch_derivative_rows` raises a retryable error, returns the spot rows alone with `DERIVATIVE_FETCH_FAILED_NOTE` (partial success, `complete_with_warnings`). In that case the stored book for the day is `cashBal` only: the open profit is in neither the spot rows (stripped by the override) nor the derivative rows (absent). The refresh reads only rows at `latest` (`.eq("asof", latest)`, `equity_reconstruction.py` `_sel_rows`), so it sums `cashBal` and writes the legacy row short by the whole `upl`, with no hold reason (`_refresh_hold_reason` has no arm for a failed derivative arm). The live AUM (`summarizeLiveHoldings`) is short by the same amount. Before this phase, `eq` made this exact failure path correct (it was only the success path that double counted).

**Why it matters:** A transient OKX positions error now silently writes a first-writer-wins legacy row below the venue's equity by the open profit, and the D-01 cross-curve agreement fails for that day (the derived curve's mark uses `totalEq`). The only signal is the generic "positions will retry" sync note.

**Suggested minimal fix:** Apply the `cashBal` override only when the derivative read succeeded. For example, have `fetch_allocator_holdings` pass a flag (or re-derive the OKX spot rows from ccxt `total`) when `_fetch_derivative_rows` failed, so the failure path keeps `eq` (open profit counted once, inside spot) and the success path keeps `cashBal`.

### WR-02 (MEDIUM, data integrity): a material price gap holds the day for 7 days, then is silently reclassified "unsizable" and left out

**File:** `analytics-service/services/equity_reconstruction.py:3329-3376` (`_judge_price_gaps`, window `read_day - PRICE_GAP_MAX_DAYS .. read_day - 1`), `:3238-3275` (hold vs leave-out), `analytics-service/services/price_rule.py:126-146` (`gap_disposition`), `:76` (`UNSIZABLE_GAP_HOLDS = False`)

**Evidence:** A gap row is sized only from priced rows of the same account and symbol inside the last 7 days. For a material balance whose ticker stops answering: days 1-7 find a priced row, judge `hold`, and the whole allocator's legacy day is held (never back-filled, first-writer-wins). On day 8 the window holds no priced row, `estimated_usd` is None, `gap_disposition` answers `unsizable`, `gap_holds_the_day` is False, and the account's gap row is dropped and the day is WRITTEN without that balance. The only trace is the `__price_gap_left_out__` breakdown record and the `price_gap_unsizable_rows` audit count. A once-material position therefore produces up to 7 missing days followed by a step down equal to its full value.

**Why it matters:** This contradicts CONTEXT D-04 ("past that the price is a named gap, and a legacy daily row whose holdings carry a gap is held") and D-06 (only a balance BELOW the floor is left out). The "unsizable left out" choice (D-09, F2) was recorded for a balance that "cannot be sized"; here the balance was sizable a day earlier and is reclassified only because the sizing window equals the carry window. The cross-curve tolerance (D-01) fails on every such day, because the derived curve's mark (venue `totalEq`) still contains the balance.

**Suggested minimal fix:** Decouple the sizing look-back from the carry cap. Size from the newest priced row of the account and symbol at any age (drop the `.gte("asof", window_start)` bound, or use a much longer bound), so a balance that was ever material keeps judging `hold`, and only a balance that was never priced is `unsizable`. If the founder prefers a bounded hold, make the transition an explicit, named outcome (a distinct audit reason and Sentry event) rather than the dust/unsizable leave-out path.

### WR-03 (MEDIUM, data integrity): reconstruct treats any non-empty CoinGecko cache as complete; with the new 7-day cap a cache gap now drops the symbol instead of carrying it

**File:** `analytics-service/services/equity_reconstruction.py:3736-3750` (`if not cached:`), with `_price_on` / `close_on_or_before` at `:1296-1311`

**Evidence:** In `_fetch_and_price_window`, CoinGecko is fetched only when `_read_cached_prices` returns nothing for the window. Any close-tagged rows at all (written by an earlier reconstruct with a shorter window, or by the flow pricer `job_worker.py:2931-2958`, which caches only the days it needed) count as full coverage. Before this phase that gap was masked because `_price_on` carried a CoinGecko close on-or-before without limit. The phase caps the carry at `PRICE_GAP_MAX_DAYS` = 7, so every reconstructed day more than 7 days past the newest cached close now SKIPS the symbol (`skipped_symbols`) and the day's equity drops by that holding. The flow pricer next door already does the right thing (`if days - set(closes): ... fetch`).

**Why it matters:** A forced rebuild or first-connect reconstruct for an account holding a BadSymbol-only asset writes legacy history with false drawdowns (the asset vanishes for days or weeks), then recovers when a cached day reappears. The rows are written through the window replace, so they persist; the only signal is a symbol name in the reconstruct audit.

**Suggested minimal fix:** Fetch when the cache does not cover the window, mirroring the flow pricer: compute the expected close days `[start_date, end_date - 1]`, and call `_fetch_coingecko_daily_closes` (and cache) when any are missing, merging fetched closes over cached ones.

### WR-04 (MEDIUM, silent fallback / user-facing): a ticker that answers `last` 0 or None now blocks the Bybit UTA mark and the reconstruct anchor, with no dust floor, and keeps a "will retry automatically" warning up forever

**File:** `analytics-service/services/equity_reconstruction.py:4043-4064` (`_price_wallet_totals`), `:4369-4371` (`_read_bybit_uta_mark` returns `wallet_unpriced` on any partial), `:4124` (`_fetch_current_equity`); `analytics-service/services/allocator_positions.py:1747-1751` (`SPOT_PRICE_GAP_NOTE`)

**Evidence:** The phase reverses the documented premise that a ticker answering 0 or None is "a genuine zero" (old NEW-C01-02 comment): such an asset now joins `partial_unpriced`. `_read_bybit_uta_mark` refuses the whole account's NAV mark on any member of that set (`if partial: return "wallet_unpriced"`), and the reconstruct anchor is skipped the same way. The D-06 dust floor is applied only in the legacy refresh, so a worthless dust token that has a market but no usable `last` (an illiquid or wound-down pair) refuses every daily mark for that Bybit account indefinitely, and the derived curve then has no new marks. On the holdings side, `fetch_allocator_holdings` appends `SPOT_PRICE_GAP_NOTE` ("Couldn't read a price for some {venue} balances — sync will retry automatically.") on every poll, so the key sits in `complete_with_warnings` permanently with copy that promises a retry that never succeeds. (The legacy refresh itself is fine here: a never-priced token is `unsizable` and left out by name.)

**Why it matters:** One dust balance can stop the marked-NAV path for a real account, which is the opposite of the phase goal (one rule on every path, curves agreeing while positions are open), and the user is shown a transient-failure message for a permanent condition.

**Suggested minimal fix:** Apply the same dust judgement on the mark/anchor path before refusing. Bybit reports a per-coin `usdValue` in the `coin` entries `_read_bybit_uta_mark` already iterates (`entry["coin"]`): treat an unpriced coin whose venue-reported `usdValue` is below `DUST_FLOOR_SHARE x totalWalletBalance` as dust (excluded from `our_wallet` and from the partial set) rather than refusing the mark. For the poll note, emit it only for a gap that the refresh would hold (or only when a priced row exists within the window), so a never-priced asset does not keep the key in a retry state.

#### WR-05 (MEDIUM, data integrity): the WR-02 sizing read is now unbounded and silently truncated at PostgREST's 1000-row cap, turning a material gap back into "unsizable, left out"

**File:** `analytics-service/services/equity_reconstruction.py:3360-3381` (`_judge_price_gaps._sel_priced` and the `newest` loop)

**Evidence:** With the age bound removed, `_sel_priced` selects every spot row of the account's keys for every gap symbol up to the day before the read day, priced or not (`mark_price` is `NOT NULL` in the schema, so every earlier gap row is stored with `mark_price` 0 and comes back too; only `usable_price` in Python filters them). There is no `.gt("mark_price", 0)`, no `.limit`, and no page loop. `supabase/config.toml` sets `max_rows = 1000`, which this codebase treats as a hard response clamp elsewhere (`benchmark.py:54`, `job_worker.py:13390`, `nav_marks.py:468`, `position_reconstruction.py:819`). Because the read is ordered `asof DESC`, truncation drops the OLDEST rows, which is exactly where a long-stuck balance's last priced row lives. With one row per (key, symbol, day) (unique index `allocator_holdings_owner_venue_symbol_asof_api_key_key`), the newest priced row falls off once `keys_in_group x gap_symbols x days_since_last_price > 1000`, e.g. one key with ten never-priced airdrop tokens plus one stuck material coin: about 90 days; three keys sharing one account and five gap symbols: about 66 days. Cross-symbol crowding does the same thing even with a price filter: a gap symbol priced daily until yesterday contributes up to 1000 newer priced rows that push another symbol's older last price out of the response. Past that point the material balance's `estimated_usd` is `None`, `gap_disposition` answers `unsizable`, and the account's gap row is dropped and the day written short by its full value: the WR-02 defect again, only later. The docstring now promises "at ANY age ... only a never-priced balance is `unsizable`", which the read cannot keep. Latent today (plan 10 measured 0 unpriced rows on PROD), but the read is the one that decides whether a balance is left out of a first-writer-wins legacy row.

**Why it matters:** A silent truncation decides between "hold the day" and "write the day without this balance". The SF-M1 leader event now fires on the leave-out, but it names it as an unsizable (never-priced) balance, which is the wrong diagnosis.

**Fix:** Read the newest priced row per gap symbol directly, the idiom this module already uses for the newest holdings day (`.order("asof", desc=True).limit(1)` at `:3132-3138`):
```python
def _sel_newest_priced(symbol: str) -> Any:
    return (
        supabase.table("allocator_holdings")
        .select("symbol, mark_price, asof")
        .eq("allocator_id", allocator_id)
        .in_("api_key_id", ids)
        .eq("symbol", symbol)
        .eq("holding_type", "spot")
        .gt("mark_price", 0)
        .lte("asof", window_end)
        .order("asof", desc=True)
        .limit(1)
        .execute()
    )
```
One read per gap symbol per account, only on an account that has a gap; keep `usable_price` as the Python-side check on the returned row.

#### WR-06 (MEDIUM, residual of WR-04): the Binance mark and every non-Bybit anchor still refuse on one unpriced dust coin, with no dust floor

**File:** `analytics-service/services/equity_reconstruction.py:4673-4682` (`read_marked_equity_usd`, Binance branch: `if partial: return "wallet_unpriced"`), `:4170-4174` (`_fetch_current_equity`, dust drop gated on `venue.lower() == "bybit"`), `:3807-3811` (the reconstruct anchor's two callers)

**Evidence:** WR-04 named the mark AND the reconstruct anchor. The fix applies the dust floor only when the venue is Bybit, because only Bybit's balance carries a per-coin `usdValue`. The Binance NAVMTM mark goes through `_fetch_current_equity(..., refuse_unread_positions=True)` and returns `wallet_unpriced` on any member of the partial set, and the anchor for Binance (and OKX when the raw `totalEq` read fails) is skipped the same way. A Binance account holding one coin whose `<ASSET>/USDT` ticker answers without a usable `last`, which this phase newly counts as unpriced (D-02 reversed NEW-C01-02's "genuine zero"), therefore refuses every daily mark indefinitely and the derived curve stops gaining marks for that key. Part of this is older: a ticker read that RAISES (a delisted pair, the usual Binance dust case) already refused before this phase. The answered-without-`last` case is new with this phase and has the same effect.

**Why it matters:** It is the WR-04 failure (one worthless balance stops a real account's marked NAV) on the venue the fix did not reach, and it reads as resolved in the round-1 table unless this is recorded.

**Fix:** Binance's `fetch_balance` has no venue USD per coin, so the Bybit mechanism does not port. Smallest honest options, founder's call: (a) size Binance unpriced coins from the newest priced `allocator_holdings` row of the key and symbol (the refresh's own sizing source, using the per-symbol read from WR-05) and drop the coins whose sum is dust against the wallet total; or (b) record the Binance limit as a named TODOS entry and in the runbook, so the residual is booked rather than implied fixed. At minimum, the WR-04 status in the phase records should say "Bybit only".
