## Decisions Made

- The `state` form carries the facts the pre-flight needs as extra columns (open legacy jobs, `pg_cron` version and `cron.alter_job`, snapshot rows labelled yesterday and today), so P3, P4 and P7 are tracked SQL and not a hand-typed statement at run time. The plan's rule is that no operator SQL is written at run time; this keeps the form set at the nine names the guard pins.
- `move` also refuses when either NAVMTM job is absent (count not 2), not only when one is still at its old schedule: "the mark read this move sits beside must exist".
- Readings that need a day name compute it inside the form from the database clock (`now() AT TIME ZONE 'UTC'`), so a reading run on the wrong day reads that day and says so in its `run_day` column.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The cut-over rule "Step B before 04:00Z" leaves a one-day hole when the chosen slot is earlier**
- **Found during:** Task 2, writing "Cut-over timing" and P6.
- **Issue:** the plan and RESEARCH say Step B runs before 04:00Z on D0 so the old pair never runs on D0 and the new pair labels D0 - 1. That assumes the new slot has not yet passed. With the candidate poll at 01:00Z, a Step B at 02:00Z is "before 04:00Z" yet after the new slot: D0 would get neither the old pair (moved away) nor the new pair (already gone by), and the label D0 - 1 would never be written (a gap in a curve nothing can backfill).
- **Fix:** P6 and "Cut-over timing" require Step B before 04:00Z AND before the chosen poll slot, and say why. The plan's wording is a subset of this rule, not a contradiction of it.
- **Files modified:** `docs/runbooks/marksource-legacy-chain-move-go-live.md`
- **Commit:** `4d0e2da5a`

**2. [Rule 2 - Missing critical functionality] The `state` form and `move` guard carry more than the plan listed**
- **Issue:** the plan's pre-flight P3, P4 and the D0 - 1 snapshot read (cut-over outcome) had no tracked form among the nine, which would have meant hand-written SQL at run time, against the orchestrator rule.
- **Fix:** extra columns on `state` (above) and the NAVMTM-pair existence check in `move`. Neither adds a form name; the guard's pinned set is unchanged.
- **Commit:** `4d0e2da5a`

## Issues Encountered

- **The SQL was never executed.** No database command is permitted to an executor, and no offline SQL parser exists in the toolchain (`sqlglot`, `pglast` and `sqlparse` are all absent), so the forms were checked by the static rules and by careful reading only. Plan 08's first catalogue run is the first parse; a form that errors there is routed back here as a fix, never hand-edited at run time. Two spots deserve an eye on that first run: `reading-c`'s `log()` rounding to 3 significant figures, and the correlated `d.run_day` references inside scalar subqueries in `reading-a` and `reading-e`.
- The audit metadata keys the readings cast to integers (`price_gap_*`, `native_unpriced_accounts`, `*_failing_accounts`) were read from `_refresh_audit_counts` at this branch's HEAD, not from a PROD row.
