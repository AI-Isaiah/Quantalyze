## PROD-write guards (the brief's focus)

| Form | Where | Verified |
|------|-------|----------|
| `move` | `docs/runbooks/marksource-legacy-chain-move-go-live.md:276` | Opens with `DO $guard$`. Raises on `shobj_description(...) IS DISTINCT FROM __MARKER__` (a NULL marker refuses). Then a compare-and-set on both legacy jobs' schedule and command, and a check that the NAVMTM chain exists and has moved. Then one `cron.alter_job` statement and a read-back that selects `marker_is_prod` first. |
| `rollback` | same file, `:648` | Same guard and a compare-and-set on the moved schedules. |
| `enqueue` | `docs/runbooks/marksource-okx-history-correction.md:376` | Opens with `DO $guard$` and `IS DISTINCT FROM __MARKER__`. Its only call is `public.enqueue_compute_job`. It skips an account that has a job in `pending`, `running`, `done_pending_children` or `failed_retry`, or a job created at or after `__T0__`. |

The vitest guard pins all three. Each write form must start with `DO $guard$\n`, contain `RAISE EXCEPTION` and contain
`IS DISTINCT FROM __MARKER__`. The set of forms is pinned in both runbooks, so an added form fails until reviewed. The `enqueue` form must call only `enqueue_compute_job` and may contain no write keyword.

Read forms (`state`, `reading-*`, the history-correction readings, the seven census files) are each a single `WITH`/`SELECT`
statement. Each has exactly one `;`, no `--` line, no uuid-shaped literal and no whole-word `INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/GRANT/COPY/CALL`.
`state` and every `reading-*` form have `m.marker_is_prod` as the first column of their one top-level SELECT. All of this is enforced by the same test file (108 passing).
The only `--` in the runbooks is the trailing `-- WRITE` annotation on the guarded `move` and `rollback` write lines, which is correct.
The marker is never typed: `form.mjs` reads `database_marker` from `scripts/prod-prober/cron-manifest.json` and wraps it in `$m$...$m$`.

Residual, procedural, non-blocking: the seven census files do not select `marker_is_prod` themselves.
They rely on `marker.sql` run first as its own call, because the CLI returns only the last statement. That is the T-26 design, and it holds for reads only.
