## Critical Issues

### CR-01: A3's trim drops unbounded P&L and flows, so a key that lost money composes into a TRUSTWORTHY book with the loss erased

**File:** `analytics-service/services/job_worker.py` (lines 12775-12790, candidate qualification; 12967-13021, walk-back, trim and pad) and `analytics-service/services/allocator_equity_compose.py` (lines 802-808, the fallback test)

**Issue:**

**A2 checks the wrong number.** It tests only `_nc_terminal[1] <= DUST_NAV_FLOOR`, which is the
stored terminal LEVEL. A3 then walks that level back across `(L, P]`. Every flow and dropped-day
P&L in that range is "consumed": none of it is booked. Separately, the trim
`flows_by_key[_k] = [f for f ... if f.utc_day_iso <= _nc_end]` silently drops every flow dated
after the exit day, including flows after `P` when `P == L`.

**Nothing bounds what is consumed or dropped.** Neither the job nor the compose fallback checks
the size of those amounts. The compose fallback only looks at the replay's own blocking reasons.
Once the walked-back level is the anchor and `(L, level_L)` is the realized terminal, the replay
is self-consistent by construction and raises nothing.

**The rule's own shape lets real money disappear.** The writer drops a day's return when the
day's flow dominates the prior NAV (`FLOW_DOM_RATIO = 1.0`) or the prior NAV is dust. On such a
day the P&L can be several times the prior NAV and still not trip `PNL_DOM_RATIO = 10`. The exit
seam then books `−level_L` as an outflow (`_departure_seams`), so the erased loss reads as a
withdrawal.

**Reproduced, run 1: a margin call followed by a liquidation.** An MT5 key is `dust`, with flat
returns on days 1-3 (L = day 3). Day 4 carries a +10000 deposit and −14500 of P&L. Its terminal is
500, which is under the floor, so the key qualifies under A2. The walk-back gives
`level_L = 500 − 10000 + 14500 = 5000`.

```
trust True ['classified_rotation', 'window_truncated']
curve {d1..d3: 105000.0, d4..d5: 100000.0}
returns {.. d4: 0.0 ..}   scalars {'mwr': ~8e-15, 'dietz': 0.0}
```

The book reads trustworthy with a 0.0 return on day 4. The 14500 loss and the 10000 deposit are
in neither the curve, the returns, nor the MWR/Dietz figures. The key's exit reads as a 5000
withdrawal. Today's code marks this book `dropped_key`, which is untrustworthy, and that is the
honest answer.

**Reproduced, run 2: a deposit after the terminal day.** A dust key has `P == L` (day 3), a stored
terminal of 600 and a +50000 flow dated on day 5. It reads `is_trustworthy: True` and is named in
`no_capital_exited_keys`, and the 50000 is gone. On `origin/main` this flow is a blocking
`OUT_OF_WINDOW_FLOW`. The trim converts it into nothing.

**This is the D-02 class: a gate weakened by construction.** The `out_of_window_flow` reason the
SC-5 decision record measured as blocking is removed for every amount, not just dust-sized ones.
The founder's D-08 record justified A3 with "the dust deposit and the P&L of the final day … are
named by the exit", which is a dust-scale premise. The code does not enforce that premise.

**Fix:** decide A2 on everything the exit consumes or drops, not on the terminal level alone. When
a check fails, the candidate keeps today's `dropped_key`. Both checks below cost nothing on the
measured PROD inputs: `flows_after_terminal_day_removed` was 0 on all three keys, and both
consumed final days were dust-scale.

```python
# in the candidate apply loop, before rebinding anything for _k
_after_p = [f for f in flows_by_key[_k] if f.utc_day_iso > _nc_p] or [
    d for d in dropped_pnl_by_key[_k] if d > _nc_p
]
if _after_p:
    continue  # something dated after the writer's last NAV day: not an exit, keep dropped_key
if _nc_p > _nc_last:
    _consumed_pnl = sum(v for d, v in _nc_pnl_by_day.items() if _nc_last < d <= _nc_p)
    if abs(_consumed_pnl) > DUST_NAV_FLOOR:
        continue  # a material P&L would be erased by the exit; keep dropped_key
```

To keep the original candidate set intact, do the `continue` before `no_capital_exit_by_key`,
`anchors_by_key` and the other maps are touched. Better still, move both checks into the
qualification block at lines 12775-12790, so a key that fails them is never named.

Add two job-level tests that are RED on the current tree: the run-1 margin-call fixture and the
run-2 post-terminal-deposit fixture. Each must assert `dropped_key` and `is_trustworthy is False`.

### WR-01: A3 replaces the realized terminal with the walked-back level, which disables the `realized_terminal_day_mismatch` detector and reads unaccounted days in (L, P] as zero P&L

**File:** `analytics-service/services/job_worker.py` (lines 12942-13021) and `_no_capital_level_on_last_return_day` (lines 12067-12091)

**Issue:**

**What the detector normally does.** For any other key, a realized terminal dated after the last
return day is a blocking `KEY_INPUTS_MISMATCH`, raised by `replay_key_equity` at
`allocator_equity_derive.py:1417-1418`. It catches a returns/inputs disagreement.

**How A3 bypasses it.** A3 treats every `P > L` as "the writer dropped the last day(s)". It walks
back through `(L, P]` and writes `realized_terminal_by_key[_k] = (L, level_L)`. A day in that
range with no flow entry and no P&L entry contributes 0. A day with a flow but no stored P&L
(either a row written before D-15, or returns that are simply missing) contributes the flow and
assumes zero P&L. The resulting level is invented, and the replay can no longer see it, because
the anchor is now that same level.

**Only some venues have a backstop.** The inception check (`FULL_HISTORY_VENUES` =
deribit, mt5) may catch a large error. Every other venue has no backstop, and A3 does not
restrict venue.

**Reproduced.** A binance `dust` key has returns on days 1-2 only and a terminal of 500 on day 5.
It has a −8000 flow on day 4 and no stored dropped-day P&L. The book reads `is_trustworthy: True`
and composes the key at an invented 8500 on days 1-2. A writer would not drop day 3 (no flow,
prior NAV above dust), so this row is internally inconsistent, and today's detector exists
precisely to block a row like this.

**Fix:** apply A3 only when `(L, P]` is evidenced as writer-dropped days. Every day in that range
that carries a flow must also carry a stored dropped-day P&L, or a writer-basis day P&L for a
writer-basis key, because D-15 always stores one for a dropped day. The row must also carry the
D-15 field at all (`dropped_day_pnl` present in the payload). Otherwise skip the candidate so it
keeps `dropped_key`.

```python
_unaccounted = [d for d in _nc_flow_by_day if _nc_last < d <= _nc_p and d not in _nc_pnl_by_day]
if _unaccounted or "dropped_day_pnl" not in <the key's payload>:
    continue  # keep dropped_key: (L, P] is not proven to be the writer's dropped days
```

Add a RED-first test with the binance fixture above.

### WR-02: The compose-level fallback does not compose a segmented candidate "exactly as today": its pre-hole segments stay in the book

**File:** `analytics-service/services/allocator_equity_compose.py:779-830`

**Issue:**

**Why only part of the key falls back.** Interior-hole segmentation (D-09/I2) runs before the
replay loop and splits key `k` into `k#hole0 … k`. The fallback tests `k in no_capital_exit`,
which only the LAST unit's id matches. When that unit blocks, only it is removed. The earlier
units keep their segment terminals, their `departed_end` and their exit seams, and stay
composed.

**Why that contradicts the docstring.** The docstring (lines 562-567) and the test file both claim
the candidate "is composed exactly as an unanchored key with returns is today". Today a NULL
anchor never reaches segmentation, so the whole key is absent.

**Reproduced with a direct `compose_allocator_equity` call.** B has a hole on day 3, a segment
terminal on day 2, and a realized terminal mismatched to day 4, so the last segment blocks.

```
fallback: dropped_key, no_anchor ... curve {d1: 100600, d2: 100600, d3..d5: 100000}
today:    dropped_key, no_anchor     curve {d1..d5: 100000}
```

**Severity.** The book stays untrustworthy, so the trust bit is not wrong. But the displayed curve
of an untrustworthy book differs from today's, and the key is half-in. The plan 09 premise ("a
candidate is never allowed to make a book worse than today") and its docstring are false for this
shape. Reaching it needs a native BTC key that carries a `dust` or `nonpositive` token and an
interior unpriced hole.

**Fix:** fall back by PARENT, not by unit id. When a candidate's unit falls back, remove every
unit `u` with `parent[u] == k` (from `anchored_keys`, `anchored_returns`, `anchored_flows`,
`departed_end`, `hole_exit_units` and `reentry_units`, and drop `interior_hole_days[k]`).
Alternatively, have the job skip naming a key in `unpriced_days_by_key` as a candidate. Add a
compose-level test that is RED on the current tree.

### WR-03: The WR-01 bypass survives when (L, P] holds no flow at all: a stored terminal dated days after the last return reads TRUSTWORTHY, the history is rescaled to that terminal, and `realized_terminal_day_mismatch` is never raised

**Severity:** WARNING (MEDIUM). **File:**
`analytics-service/services/job_worker.py`, `_no_capital_exit_consumes_only_dust`, final
`return all(day in pnl_by_day for day in flow_by_day if last_return_day < day <= terminal_day)`.

**Issue:**

**Why the rule is vacuous here.** Rule 3 proves that (L, P] is the writer's own dropped days only
on days that carry a flow. When the window has no flow and no stored P&L, the `all(...)` is over
an empty set and returns True. The window sum is 0, so rule 2 also passes.
`_no_capital_level_on_last_return_day` then returns the stored terminal unchanged as the level on
L, the anchor becomes that level, and the replay's `realized_terminal_day_mismatch` detector
(`allocator_equity_derive.py:1417-1418`) can no longer fire.

**What the detector would otherwise have caught.** A writer drops a no-flow day only when the prior
NAV is dust. It also stores a P&L row for each dropped NAV day that has one
(`dropped_day_pnl_payload`, `allocator_equity_derive.py:1494-1515`). So an empty window is what a
returns/inputs disagreement looks like, which is exactly the row the detector exists for. The
inception backstop covers deribit and mt5 only.

**Reproduced.** A binance `dust` key has returns on days 1-2 (L = day 2) and a stored terminal of
500.0 on day 5. It has no flow and no `dropped_day_pnl` field:

```
P1 no-flow gap: trust True ['classified_rotation', 'window_truncated']
                exited [{'api_key_id': 'key-E', 'reason': 'dust', 'day': '2026-06-07'}]
                curve {06: 100500.0, 07: 100500.0, 08..10: 100000.0}
```

Before NAVBREACH, this key was `dropped_key` and the book was untrustworthy. Now the key's whole
history is composed at whatever level the terminal names. If the gap is missing returns rather
than dust days, the key's real capital through days 1-2 is replaced by 500 and the book reads
trustworthy.

**Fix:** when P > L, require every day in (L, P] to carry a stored P&L on the basis being walked
back, not only the flow days. Do the check before any map is touched, exactly like the other three
rules. On plan 08's PROD inputs this costs nothing: all three keys pass both "P has a stored P&L"
and "every day in (L, P] has a stored P&L".

```python

window_days = pd.date_range(last_return_day, terminal_day).strftime("%Y-%m-%d")[1:]
if any(day not in pnl_by_day for day in window_days):

```

### WR-04: The compose fallback leaves a segmentation-level `key_inputs_mismatch` behind, so a candidate with an unsplittable hole is not composed "exactly as today"

**Severity:** WARNING (MEDIUM). **File:**
`analytics-service/services/allocator_equity_compose.py`, segmentation block: the
`if any(e not in terminals for e in ends):` branch adds `DegradeReason.KEY_INPUTS_MISMATCH` to
the book-level `reasons` and composes the key unsplit. The block is read together with the
fallback loop that follows it.

**Issue:**

**Why today never carries this reason.** Today an unanchored key never reaches segmentation,
because `anchored_keys` excludes a NULL anchor. A no-capital candidate arrives anchored, so it can
trip the missing-segment-terminal branch. That branch writes `KEY_INPUTS_MISMATCH` straight into
the book's `reasons`, not into the key's replay reasons.

**Why the fallback leaves it behind.** When the candidate then falls back, the fallback removes
every unit of the key, but nothing removes that book-level reason or its warning line. fixB's
docstring promise ("leaving today's result for an unanchored key with returns") is false for this
shape.

**The second consequence.** When the unsplit candidate's own replay is clean, it does not fall
back at all. It is composed across an unpriced hole and named in `no_capital_exited_keys`, while
the book holds a blocking reason that only its candidacy caused.

**Reproduced.** `_hole_candidate_book(last_terminal=(DAYS[4], 600.0))` with
`segment_terminals_by_key={"B": {}}`:

```
F1  fallback reasons: ['dropped_key', 'key_inputs_mismatch', 'no_anchor'] trust False
F1  today    reasons: ['dropped_key', 'no_anchor']                        trust False
F1  payload equal to today: False
F1b (clean last terminal) reasons: ['classified_rotation', 'key_inputs_mismatch', 'window_truncated']
    trust False, exited [{'api_key_id': 'B', 'reason': 'nonpositive', 'day': '2026-06-09'}]
```

**Severity.** The trust bit is False either way, so the book does not become wrongly trustworthy.
What is wrong is that the stored `degrade_reasons` of an untrustworthy book name a cause belonging
to a key that is not in it. Reaching it needs a native-unit candidate whose row lacks a segment
terminal before an interior hole.

**Fix:** make a candidate's own segmentation failure a candidate failure. In the
