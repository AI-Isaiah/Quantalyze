## Summary

**The breach is raised by the native-unit core's inception gate, and the gate is doing its job: the venue anchor it is handed does not equal the ledger it is rolled against.** `_assert_inception_reconciled` (`analytics-service/services/native_nav.py:661-780`) rolls each currency's balance backward from `terminal_native_equity − terminal_upnl_native` through the whole ledger and requires the pre-history residual to be ~0 (tolerance: the larger of $1 and 1e-4 of anchor NAV, after a per-currency dust allowance of 1e-4 of that currency's throughput). The anchor is the live `get_account_summaries` `equity`. Deribit's own documentation defines `equity` as `balance + futures (session UPL + RPL) + options mark value`, and the ledger's `change` column books session PnL only at the daily 08:00 UTC settlement. Our wedge strips `session_upl` (futures plus options) and `options_value`, and never reads `session_rpl` at all. So whenever the account has realized-but-unsettled session PnL at crawl time, the anchor exceeds the ledger by exactly that amount, and the gate (correctly) refuses.

**The PROD evidence says the residual is session-dependent, not a permanent hole in the ledger.** The same three venue accounts, with an unchanged ledger history, produced: a breach on 2026-08-25 (ratio 436), a clean stitch on 2026-09-27 (two jobs), identical breaches on 2026-10-01 (three jobs on two strategies, ratio 26.1 each, all inside one 08:00-to-08:00 session), and clean results on 2026-10-02 (a stitch and a single-key derive). A missing historical row would breach every time. Only member 3 (the third key, the only one whose account is demonstrably funded and live) ever raises. Most telling, the three stored stitched series of the same history agree to the last digit for members 1 and 2 and disagree on 116-117 days of member 3's window, by up to 3.4 percentage points on one day. The same ledger, rolled from a different anchor each time, is a time-of-run-dependent track record. That is a data-integrity defect in its own right, independent of whether a run happens to breach, and the fix removes it.

**D-04 is a different mechanism and is certain.** Python never writes `strategy_analytics.computed_at` on a failure; the SQL bridge does. `sync_strategy_analytics_status` branch (b) ends `computed_at = now()` (`supabase/migrations/20261003120000_sync_status_bridge_residues.sql:950`), and the failed stitch's `mark_compute_job_failed` calls it. PROD shows the signature: the row's `computed_at` equals the failed job's `updated_at` to the microsecond. It can be fixed WITHOUT editing `sync_strategy_analytics_status`, using a table trigger, which is the repo's own precedent for exactly this class and avoids both the concurrent STATUSBRIDGE edit and about 50 mutation twins that pin the current bridge text.

**Primary recommendation:** Wave 0 takes one read-only live measurement on the worker (the raw summary fields and the identity `balance` vs `equity − wedge` vs `Σchange`, relative figures only). If it confirms `futures_session_rpl` as the residual, fix the anchor decomposition in `fetch_deribit_native_account_state` / `build_deribit_native_ledger` (strip the unbooked futures session RPL, leave every tolerance constant untouched), prove it with a test that is RED on today's code, and fix D-04 with a narrow BEFORE UPDATE trigger on `strategy_analytics`. If the measurement shows the residual is NOT explained by the summary fields, it is venue data and the phase stops for a founder decision (CONTEXT discretion rule).

### Pattern 1: What the gate reads, exactly (question 1)
**Where raised:** `InceptionReconciliationError` is defined at `native_nav.py:137-155`; its message is `native_nav inception reconciliation breached venue={venue} currencies=[{codes}] breach_ratio={ratio:.3g}`. The PROD error text carries the trailing `breach_ratio=` (the ROADMAP evidence line omitted it). It is raised at `native_nav.py:776` (the breach), with two refusal siblings at `:745` (a value-carrying un-rolled orphan with no usable mark) and `:763` (a non-finite residual or anchor).
**The reconciliation:** per rolled bucket, `resid = balance[0] − pnl[d0] − flow[d0]`, where `balance` was rolled backward from `terminal_native = terminal_native_equity − terminal_upnl_native` (`_roll_bucket`, `native_nav.py:449-459`; `nav_twr.reconstruct_nav`, `nav_twr.py:357-385`). So `resid = (equity − wedge) − Σ(native pnl) − Σ(flows)`. [VERIFIED: native_nav.py:449-459, 688-727]
**Tolerance** (verbatim, `native_nav.py:178-199`):
```python
INCEPTION_ABS_TOL_USD: float = 1.00
INCEPTION_REL_TOL: float = 1e-4
INCEPTION_NATIVE_DUST_REL: float = 1e-4
# :726  is_dust = abs(resid) <= INCEPTION_NATIVE_DUST_REL * throughput
# :727  resid_usd = 0.0 if is_dust else abs(resid) * mark0     # mark0 = INCEPTION-day mark
# :767  tol = max(INCEPTION_ABS_TOL_USD, INCEPTION_REL_TOL * abs(anchor_nav))
# :768  if resid_usd_total > tol: raise InceptionReconciliationError(... breach_ratio=resid_usd_total / tol)
```
`throughput = Σ|pnl| + Σ|flowqty|` of that currency. So `breach_ratio = 26.1` means the offending currency's non-dust residual, valued at the inception-day mark, was 26.1 times the tolerance. [VERIFIED: native_nav.py:178-199, 722-727, 767-780]
**"member ledger unrecoverable":** the literal prefix is built at `job_worker.py:8380-8381` in the `except _PERMANENT_LEDGER_ERRORS` arm (`:8359`); `_PERMANENT_LEDGER_ERRORS` (`job_worker.py:7772-7779`) includes `NavReconstructionError`, the parent of `InceptionReconciliationError`. The arm calls `_stamp_failed(...)` and returns `DispatchResult(FAILED, error_kind="permanent")`, so the queue never retries. The message text is the scrubbed exception string, so only codes and the relative ratio reach `compute_jobs.last_error`. [VERIFIED: job_worker.py:7772-7779, 8359-8385]

### Pattern 2: The anchor and the ledger are different quantities (the root cause)
The anchor handed to the core is `terminal_native_equity = summary["equity"]` and `terminal_upnl_native` is, for the default `cash_settlement` basis, `native_upnl + native_options_value` (`deribit_ingest.py:2461-2470`), where `native_upnl` is `futures_session_upl` (or the legacy `session_upl`) plus `options_session_upl` (`_combined_session_upl`, `deribit_ingest.py:1452-1480`). The ledger side is Σ of the txn-log `change`, and the in-repo module header pins what `change` is: "for settlement: session PNL and perpetual funding", and `cashflow` is "Realized SESSION PnL since last settlement ... 0 at fill time for perps" (`deribit_txn.py:12-25`).
Deribit documents `equity` as `balance + futures (session UPL + RPL) + options mark value`, `balance` as the cash balance (deposits, withdrawals, transfers, option premiums, settlements/deliveries, corrections, costs), and `session_rpl` as "Realized profit and loss accrued in the current trading session (since the last daily settlement)". [CITED: docs.deribit.com/api-reference/account-management/private-get_account_summary and private-get_account_summaries, fetched 2026-10-07]
A 2026-07 repo research note already recorded the formula ("`equity = balance + session_upl + session_rpl`") and then took only `session_upl` into the wedge, tagging the field choice `[ASSUMED]` and noting it "needs live confirmation" (`.planning/milestones/v1.8-phases/77-upnl-basis-reconciliation/77-RESEARCH.md:91-95`). No source or test file under `analytics-service` reads `session_rpl`, `futures_session_rpl` or `session_funding`, and every `get_account_summaries` stub in `tests/test_deribit_ingest.py` sets `equity = Σledger + session_upl (+ options_value)` with no realized term (see `_open_book_paginate` and the `h1_*` tests, `:3495-3560`). The existing tests therefore encode the blind spot: they can only ever pass.

### Hypotheses

**H1 (our code; MEDIUM-HIGH, one live measurement from HIGH): the anchor wedge omits the futures session RPL (and may over-strip the options session UPL).** `equity = balance + futures(session UPL + RPL) + options_value`; the ledger books session PnL at the 08:00 UTC settlement; the wedge strips session UPL and options value only. Residual = unbooked futures session RPL, constant within a session (realized PnL on closed trades does not move until the next settlement), different across sessions, and zero on a session with no closing trades. That matches all of: three identical 26.1 readings across about nine hours on two strategies; clean results at other times; a different ratio in the August code era; only the funded member; run-to-run series drift on that member only. A synthetic replay with the real core (scaled, anonymous numbers, scratchpad only) shows the gate passes when the unbooked amount is under the dust floor and breaches above it, with the ratio rising linearly (4 at 0.004 BTC, 39.9 at 0.04 BTC on a ~10 BTC account). [VERIFIED mechanism: synthetic replay with `services.native_nav`; CITED venue semantics: Deribit docs; ASSUMED for the real account until OQ-1]
**H1b (our code, same family): the cash-basis wedge adds `options_session_upl` on top of `options_value`.** Per the documented `equity` formula the options mark value already contains the options unrealized move, so adding `options_session_upl` to a wedge that also strips `options_value` over-strips by that term. This only matters when an option position is open with nonzero session UPL (the composites carry an `unsmoothed_options_book` MTM-gating flag, so an options book exists somewhere in their history; whether member 3 holds one now is unknown). The repo's own comment records that the open-book field layout "is not verifiable at the probe account's flat terminal" and that "the first live open-options anchor is watched at §5" (`deribit_ingest.py:1443-1450`). [CITED + VERIFIED code; ASSUMED effect]
**H2 (our code; LOW, secondary): anchor-versus-crawl skew.** `account_state` is read at `job_worker.py:7802`, but `end_ms = _now_ms()` is taken at `deribit_ingest.py:1152` after scope enumeration, currency enumeration and the per-currency index probes (paced about 1 request per second). Rows booked in that gap are in the ledger but not the anchor. On an active account this yields a run-to-run random residual. ## Common Pitfalls

### Pitfall 1: "It passes now, so it is fixed" (or "it fails now, so it is a venue problem")
**What goes wrong:** the same accounts pass and fail depending on the session's unbooked realized PnL.
**Why it happens:** the residual is time-dependent, so a single run is a coin flip.
**How to avoid:** SC-1 evidence is the test that is RED on today's code; D-03 evidence is a successful recompute PLUS the Wave 0 probe showing the identity closes at an instant when the unbooked term is nonzero.
**Warning signs:** a recompute that succeeds with the probe's `futures_session_rpl` at zero proves nothing.

### Pitfall 2: Fixing the gate's symptom by loosening dust
**What goes wrong:** `INCEPTION_NATIVE_DUST_REL` already exempts a residual up to 1e-4 of throughput; raising it would hide this class entirely.
**How to avoid:** assert all three constants verbatim; add a negative-control test where a genuinely missing ledger row of the same size still breaches after the fix.

### Pitfall 3: Fixing the cash pass but not the MTM and smoothed passes
**What goes wrong:** the stitch reconstructs three bases (`cash_settlement`, MTM, smoothed) from the same state; the wedge differs by basis (`deribit_ingest.py:2453-2470`). A fix applied only to the cash branch can leave the other two breaching on the same session.
**How to avoid:** the reproducing test parametrizes the basis; the smoothed book-channel guard (`_assert_smoothed_book_channel`, which reconciles against `options_value − options_session_upl`) must be re-run.

### Pitfall 4: The D-04 trigger swallowing the runner's stamp (Phase 166.5)
**What goes wrong:** a trigger that holds `computed_at` whenever the row is not complete would block the runner-side stamp Phase 166.5 plans to write while the row is still `computing`.
**How to avoid:** hold ONLY when `NEW.computation_status = 'failed'`. The runner never stamps while writing a failed row.

### Pitfall 5: Forgetting the censuses a new SQL gate moves
**What goes wrong:** a new `supabase/tests` file shifts `FILES_FLOOR`, the live-DB execution ledger, CI step lists and `test_sql_gate_scoped_updates.py`.
**How to avoid:** grep for the sibling's name (`test_sync_status_bridge_residues`) across `CHANGELOG.md`, `TODOS.md`, `scripts/mutation-floors.mjs`, `.github/workflows/ci.yml`, `analytics-service/tests/test_sql_gate_scoped_updates.py` and update every hit; read the floors by symbol from `scripts/mutation-floors.mjs`, never from prose.

### Pitfall 6: A plan premise that is stale
**What goes wrong:** CONTEXT cites `TODOS.md` item 0.2 for the breach. At HEAD item 0.2 is the ccxt flat-day recompute gap (`TODOS.md:821`); the breach is recorded in the `assignment` entry (`TODOS.md:895-905`) and item 0.3 (`:914`).
**How to avoid:** cite those two, not 0.2. (Re-measured this session.)
