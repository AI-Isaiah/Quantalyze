## ⭐ Coexistence with `SyncProgress`: the contract, derived from measurement

**What `SyncProgress` is.** It is a LOCAL state machine (`SyncStatus`: idle, syncing, computing, complete, complete_with_warnings, error). It is driven by `handleSyncTrades` and by the panel's own `strategy_analytics` poll. It is fed from component state and never from `api_keys.sync_status`. It carries NO `aria-live` and NO `role` (measured: 0 in `SyncProgress.tsx`).

**Why its success can contradict the key card.**
- `run_sync_trades_job`'s MT5 branch makes the daily-PnL fetch an explicit no-op. Its balance read is best-effort.
- So a resync of an MT5 key whose password is wrong can still end `complete` and render "Up to date". That is a claim about an analytics run, and it is NOT evidence that the credential works.
- Nothing on the `/api/keys/sync` path writes `api_keys.sync_status`. The re-read status after a resync is therefore the same server fact it was before.

The rules:

- **R1: the card, per key.**
  - The persisted-status block is MOUNTED if and only if `isUntrustedKeySyncStatus(key.sync_status)`.
  - While `syncingKeyId === key.id` (this key's sync is in flight), the DISPLAYED status is overridden to `syncing`.
  - That produces exactly UI-SPEC S1's declared retry-in-flight cell: a neutral `Syncing…` pill with a silent helper. No credential claim sits under a spinner.
  - The block stays mounted across the transition, so its one live region is stable. When the server-read state returns, it is announced politely rather than silently re-inserted.

- **R2: the panel.** `SyncProgress` renders exactly as today, except in one case. When its state is a terminal SUCCESS (`isComputedAnalytics(syncStatus)`) AND its subject key (`lastAttemptedKeyId`) is untrusted in the loaded `keys`, the panel is not rendered.
  - Reason: the server-read credential failure is the only evidence about the credential, and a success line beside it is the false confidence this phase exists to remove.
  - The panel's ERROR render is kept. It agrees with the pill (something failed) and carries that attempt's own message.
  - ⛔ The panel is NEVER withheld while in flight (syncing or computing). Its poll is what drives `handleSyncStatusChange`, and unmounting it mid-flight would strand `syncingKeyId`. Every Resync button would then stay disabled until a reload.

- **R3: a withheld success is retired, never re-shown.** Added in plan revision 1, from the checker's `key_links_planned` warning.
  - **The hole R2 leaves.** R2's withhold reads the key's CURRENT status. After `Update password` succeeds, `rotate-secret`'s validated write sets that status to `idle`, and the withhold lapses. Without R3 the panel re-mounts with the terminal success of the attempt made under the replaced password. The user would see "Up to date" right after fixing the credential, from a run that never used the fix.
  - **The rule.** Replace the dialog's `onUpdated` with a handler that does two things. First, only while R2 is withholding the panel (the panel's subject key is untrusted in the loaded `keys`), it calls `setSyncStatus` with a FUNCTIONAL updater. That updater maps a terminal success (`isComputedAnalytics`) to `idle` and returns every other value unchanged. Second, it calls `loadKeys()` exactly as today.
  - **Why this shape, not the checker's other one.** The alternative ties the withhold to the attempt. That needs a new piece of state recording the attempt's credential, and this plan forbids state that mirrors other state. R3 is one guarded update in an event handler. It adds no effect and no state.
  - **How R3 cannot disturb an in-flight sync.**
    1. The updater returns `syncing` and `computing` unchanged. The in-flight panel stays mounted, its poll still reaches `handleSyncStatusChange`, and `syncingKeyId` is still cleared (T-167-06-04).
    2. The updater is FUNCTIONAL, so it reads the state committed when it runs, not the closure's copy. `UpdateMt5SecretDialog` calls `onUpdated` only after awaiting `rotate-secret`, and the panel's poll can move `syncStatus` during that await.
       - After R4, the only sync that can be in flight during that await belongs to a DIFFERENT key from the one being rotated. If that sync's terminal success lands during the await, this updater retires it, but nothing on screen shows it: R2 reads that other key's own status, which the rotation does not change, so the panel is withheld either way.
       - Plan revision 2 therefore declined the optional during-await case. Under a closure-reading neuter it would still pass, and this repo does not keep a test that cannot fail. The functional form stays because the next value depends on the previous one.
    3. `error` is also returned unchanged. The error render agrees with a failed attempt, and its Retry is now useful with the new password.
    - Pinned by the in-flight-remedy case and neuter N11. That case rotates a second MT5 key while the current key syncs, because R4 makes the syncing key's own `Update password` unclickable.
  - **Why it is guarded by the withhold.** Without the guard, rotating any MT5 password would retire any terminal success, including a truthful one about a healthy key. With it, healthy behaviour stays identical. Pinned by the control case and neuter N12.
  - The one case R3 cannot reach, a rotation that completes while the rotated key's own sync is still in flight, is closed by R4 below.

- **R4: a key's password is never replaced while that key's own sync is in flight.** Added in plan revision 2, from the checker's `scope_reduction` warning.
  - **The window.** R3 must leave an in-flight sync running. Suppose `Update password` for key K succeeds while K's own sync is in flight. When that sync completes, K's re-read status is already `idle`, so R2 does not withhold, and the panel shows the success of a run made under the replaced password. At `c8d4e131` this was reachable: the `Update password` button carried no `disabled` prop (measured).
  - **The rule.** `Update password` takes `disabled={syncingKeyId === key.id}`, derived in render. `handleSyncTrades` sets `syncingKeyId`; `handleSyncStatusChange`'s terminal arms and `handleSyncTrades`' catch clear it. It is the same in-flight marker `Resync` already reads. No state, no effect, no copy, no colour: `Button`'s existing disabled style.
  - **The reverse order is already impossible.** `Modal` opens its native `<dialog>` with `showModal()`. That makes the rest of the document inert in a browser, so no `Resync`, `Use & Sync` or panel Retry can start a sync while a rotation dialog is open. The `rotate-secret` await happens while the dialog is still open, because `onUpdated` runs before `onClose`. Together the two facts mean one key's attempt and its rotation never overlap.
    - jsdom implements no `showModal`. The test file's polyfill toggles the `open` attribute and does not model inertness. So a unit case can pin that the dialog opens MODALLY (a `showModal` spy, N15), but not the browser's inertness itself.
  - **Why key-scoped, not `!!syncingKeyId` like `Resync` and `Use & Sync`.**
    - Those two take `!!syncingKeyId` because the component owns ONE sync slot: `syncingKeyId`, `lastAttemptedKeyId`, `syncStatus` and one `SyncProgress`. A second sync of ANY key would overwrite the first one's slot and strand its poll. That rule stops two syncs running at once.
    - `Update password` occupies none of that slot. R2 and R3 judge the panel by its SUBJECT key's status, and a rotation changes only the rotated key's status. Rotating key K while key J syncs leaves J's status, and so J's withhold, untouched. An untrusted J's success is still withheld, and a healthy J's success is still truthful.
    - A global disable would therefore buy no truth. It would block the one remedy the pill asks for, fixing K, for the whole length of an unrelated sync, up to the panel's `POLL_MAX_ATTEMPTS` cap. Pinned by N14.
  - **Why not also condition it on the key being untrusted.** `handleSyncTrades` re-reads `keys` mid-flight, and the daily poll can stamp a key between reads. A disable conditioned on the status could therefore flip during one attempt, and a user could open the dialog while it was off. The in-flight marker cannot flip mid-attempt.
    - The cost is one of the plan's two healthy-key behaviour changes: a healthy MT5 key's `Update password` is also disabled during that key's own sync, exactly as its `Resync` already is. R5's `Delete` disable is the other. The `<done>` list and S1b state both.
  - **The correction, recorded as lineage.** Plan revision 1 said closing this window "needs the attempt-tied record that R3 was chosen over". That reasoning was WRONG. The window exists only if one key's attempt and its rotation overlap in time. The overlap can be prevented from state that already exists, and when the two can never overlap, nothing about the attempt's credential has to be recorded. So no residual is recorded for it.
  - Pinned by the rotation-blocked case and neuters N13 (drop the prop), N14 (widen it to every key), N15 (open the dialog non-modally) and N16 (a disable that never lifts, which would dead-lock the remedy).

- **R5: every other in-tab action that removes the panel's subject, or moves it, retires a withheld success the same way, and `Delete` takes R4's disable.** Added in plan revision 3, from an issue the orchestrator surfaced; the checker did not raise it.
  - **The hole, measured at `12bf825c`.** `handleDeleteKey` awaits the `api_keys` delete, then filters the row out of `keys` locally. It never touches `syncStatus`. R2 answers a missing subject row as "not untrusted", so a success withheld beside a failed sign-in re-appears once its key is deleted. That is R3's hole reached through `Delete`, and deleting and re-adding the key is exactly what the `revoked` helper tells the user to do.
  - `handleAddKey` reaches the same hole a third way. After the link succeeds it moves `lastAttemptedKeyId` to the new key, so R2 then judges the new, healthy key, and the success withheld beside the old key's failure re-appears.
  - **The rule.** R3's retirement becomes one shared helper, `retireWithheldSuccess`, in the component body. Only while the render's panel-subject derivation (Task 2 Step 3) says the subject is untrusted, it calls `setSyncStatus` with R3's functional updater: a terminal success becomes `idle`; `syncing`, `computing` and `error` come back unchanged. Three event handlers call it:
    1. the dialog's `onUpdated` (R3);
    2. `handleDeleteKey`, after its error return and before the row is filtered out;
    3. `handleAddKey`, after the link succeeds and before `setLastAttemptedKeyId` moves the subject.
    A failed delete or a failed add leaves the row and the subject where they were. The withhold still holds, so nothing is retired there.
  - **Why the guard reads the pre-change list.** Each handler reads the derivation from the render the user clicked in. For `Delete`, that render still holds the row. The list cannot move during the delete await either: the confirm is open, and it opened modally. Re-deriving the guard from the list with the row filtered out would answer false for the deleted subject, and the success would re-show. Pinned by N18.
  - **`Delete` takes R4's disable, `disabled={syncingKeyId === key.id}`, for R4's reason.** Deleting a key during its own attempt removes the subject while the updater must leave `computing` alone. The attempt's later success would then land with no row left to withhold it.
    - The reverse order is closed as R4's is. The Delete confirm renders through `Modal`, which opens it with `showModal()`. `handleDeleteKey` awaits the delete before it clears `confirmDelete`, so the await happens while the dialog is still open.
    - It is key-scoped for R4's reason: deleting key K changes only K's row, so another key's withhold is untouched.
  - **Healthy behaviour.** The guard keeps a never-withheld success through a `Delete` of another key and through an `Add Key`, exactly as at HEAD. Pinned by two control cases and N12. A healthy key's `Delete` is disabled during that key's own sync, the plan's second healthy-key change, matching its `Resync`.
  - Pinned by the remedy-by-Delete case (N17, N18, N21), the Delete-blocked case (N19, N20, N21) and the remedy-by-Add-Key case (N22).

- **R6: every transition of the panel to `error` clears the in-flight marker.** Added in plan revision 3. R4's and R5's disables read `syncingKeyId`, so they are only as sound as the paths that clear it.
  - **The gap, measured at `12bf825c`.** `handleSyncTrades`' catch and `handleSyncStatusChange`'s error arm each set `error` and clear the marker together. `handleAddKey`'s background catch sets `error` and does NOT clear it.
    - That post-add sync is not registered in the one sync slot, and the Add Key form is not modal. So it can fail while another key's sync is in flight.
    - Its `error` then stops that attempt's poll, because `SyncProgress` polls only while syncing or computing. `handleSyncStatusChange` never runs, and the marker stays set.

  - **The rule.** The background catch also calls `setSyncingKeyId(null)`, as the other two error paths do. When no sync is in flight the marker is already null, so healthy behaviour outside the race is unchanged. Once the marker is clear, the abandoned attempt cannot show a success, because nothing polls it any more.
  - Pinned by the marker case and N23.

- **Subjects that differ do not contradict.** If the panel's subject is key J and key K is untrusted, K's card keeps its pill while the panel reports J. `handleSyncTrades` links J to the strategy first, so the panel is truthfully about the strategy's CURRENT key.

  - `handleAddKey` moves the subject to the new key while another key's attempt may still be polling. That attempt's terminal success is then judged against the new key, and reads as being about it.
  - It happens identically between two healthy keys, as a premature `Up to date`, so it does not depend on credential trust.
  - R6 closes its dead-lock half, which R4 and R5 rely on. Closing the subject half means routing the post-add sync through the tracked slot, which changes the add flow that the `SEAMUX-05` describe block pins.
  - Surfaced to the orchestrator for routing at plan time.

- **Named, not planned: a change made in another tab.** R3 and R5 retire on THIS tab's own actions.
  - Another tab's `Update password` or `Delete` reaches this tab only through a re-read: the load-error banner's `Retry`, or the re-read in the terminal-success arm. Either can lift R2's withhold if the other tab fixed or deleted the subject key in between.
