## ⭐ RESEARCH OPEN QUESTION 2, CLOSED: the manager's key card is the surface

167-RESEARCH Open Question 2 asked which surface counts as "the surface where they notice the symptom". No plan answered it. The verifier found the consequence: the only render sits behind an allocator-only tab. **This plan closes the question with the reasoning below. Task 3 records it as CONTEXT D-18 so it lives where decisions live.**

**The answer: the key card in `ApiKeyManager`, on the strategy's own edit page (`/strategies/[id]/edit`).**

1. **Who has the symptom.**
   - A manager owns the factsheet whose staleness is the symptom.
   - `profiles.role` defaults to `manager`, so a manager-role owner is the common case, not an edge.
   - The daily poll stamps that owner's key, and before this plan no page they can reach rendered it.

2. **Where the manager meets the key.** The edit page is gated by ownership only.
   - The page reads the strategy with `.eq("user_id", user.id)`. It reads nothing from `profiles` (measured: 0 occurrences in the page source).
   - The dashboard layout reads `role` only to choose nav chrome.
   - `src/proxy.ts` gates admin routes only.
   - The page mounts `ApiKeyManager` with `currentKeyId = strategy.api_key_id`. The key that feeds THIS strategy is therefore shown on THIS strategy's page, marked by its `Resync` control. Every other key shows `Use & Sync`.

3. **The remedy is on the same card.** The helper's imperative names an action the card can actually perform:
   - `Update password` for MT5. It goes to `rotate-secret`, whose validated write sets `sync_status` to `idle`, the only place the column is cleared.
   - `Add Key` and `Delete` for a ccxt re-add, which is what the `revoked` helper asks for.

4. **Why not the factsheet.**
   - D-04 is rated one-way. It forbids the cause entering `fetchAndBuildPayload`'s id-keyed cache, and the owner lane shares that payload. Touching it earns a `checkpoint:decision`.
   - A strategy-level causal sentence would also need the staleness conjunct (D-03). `ledger_refresh_staleness` exposes that only to `service_role` (D-12).
   - 167-UI-SPEC §4 binds S1 to claim only what was written for the key.

5. **Why not open the `/profile` Exchanges tab to managers.**
   - That tab is the allocator's holdings-and-balance surface. Its `Sync now` drives the holdings poll.
   - Un-gating it changes a role boundary on an unrelated surface. That is a larger change than the gap needs.
   - It would still not be the page where a manager manages a strategy's key.
   - `ProfileTabs` and the profile page stay byte-unchanged.

⚠️ **THE RESIDUAL, NAMED RATHER THAN HIDDEN.** The rendered sentence names the credential and the remedy. It does NOT say "your factsheet stopped updating because…".
- The tie to the factsheet is carried by PLACEMENT: the strategy's own page, with its current key marked. It is not carried by copy.
- No signal ties a strategy's staleness to a key's failure (D-02, D-03, UI-SPEC §4), and authoring one here would be exactly the inference this phase forbids.

## ⭐ Coexistence with `SyncProgress`: the contract, derived from measurement

**What `SyncProgress` is.** It is a LOCAL state machine (`SyncStatus`: idle, syncing, computing, complete, complete_with_warnings, error). It is driven by `handleSyncTrades` and by the panel's own `strategy_analytics` poll. It is fed from component state and never from `api_keys.sync_status`. It carries NO `aria-live` and NO `role` (measured: 0 in `SyncProgress.tsx`).

**Why its success can contradict the key card.**
- `run_sync_trades_job`'s MT5 branch makes the daily-PnL fetch an explicit no-op. Its balance read is best-effort.
- So a resync of an MT5 key whose password is wrong can still end `complete` and render "Up to date". That is a claim about an analytics run, and it is NOT evidence that the credential works.
- Nothing on the `/api/keys/sync` path writes `api_keys.sync_status`. The re-read status after a resync is therefore the same server fact it was before.

The rules:

- **R1: the card, per key.**
  - The persisted-status block is MOUNTED if and only if `isUntrustedKeySyncStatus(key.sync_status)`.
  - While `syncingKeyId === key.id` (this key's sync is in flight), the DISPLAYED status is overridden to `syncing`.
  - That produces exactly UI-SPEC S1's declared retry-in-flight cell: a neutral `Syncing…` pill with a silent helper. No credential claim sits under a spinner.
  - The block stays mounted across the transition, so its one live region is stable. When the server-read state returns, it is announced politely rather than silently re-inserted.

- **R2: the panel.** `SyncProgress` renders exactly as today, except in one case. When its state is a terminal SUCCESS (`isComputedAnalytics(syncStatus)`) AND its subject key (`lastAttemptedKeyId`) is untrusted in the loaded `keys`, the panel is not rendered.
  - Reason: the server-read credential failure is the only evidence about the credential, and a success line beside it is the false confidence this phase exists to remove.
  - The panel's ERROR render is kept. It agrees with the pill (something failed) and carries that attempt's own message.
  - ⛔ The panel is NEVER withheld while in flight (syncing or computing). Its poll is what drives `handleSyncStatusChange`, and unmounting it mid-flight would strand `syncingKeyId`. Every Resync button would then stay disabled until a reload.

- **Subjects that differ do not contradict.** If the panel's subject is key J and key K is untrusted, K's card keeps its pill while the panel reports J. `handleSyncTrades` links J to the strategy first, so the panel is truthfully about the strategy's CURRENT key.
</scoping_decision>
