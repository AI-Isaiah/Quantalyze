## ⭐ THE HIGHEST-LEVERAGE SCOPING QUESTION, CLOSED ON A MEASUREMENT

167-RESEARCH's Open Question 1 asks whether this phase must add a `sync_status` write boundary to
the STRATEGY-level pipelines (`run_sync_trades_job`, the ledger fan-out), since those are what feed
the factsheet and they write nothing to `api_keys`. 167-PATTERNS records that **no analog exists**
for such a boundary, so building one would be INVENTION.

**It is not needed, and here is the measurement that settles it.**

`scripts/prod-prober/cron-manifest.json`, captured from PRODUCTION, carries jobid **15**,
`poll-allocator-positions`, schedule `0 4 * * *`, `active: true`, running
`SELECT enqueue_poll_allocator_positions_for_all_keys();`. That function's body
(`supabase/migrations/20260420073003_allocator_holdings.sql`) loops
`SELECT id FROM api_keys WHERE is_active = true AND sync_status IS DISTINCT FROM 'revoked'`.

⇒ **Every active, non-revoked key is polled DAILY, and that poll is the existing write boundary.**
The ROADMAP's own headline evidence confirms it end to end: the MT5 key sat at `sync_status: error`
with `MT5 terminal unreachable — sync will retry automatically.` for 17 days — that row was
WRITTEN, by this job, repeatedly. The defect was never a missing signal; it was a signal carrying
the wrong cause and an impossible promise.

⇒ **NO new write boundary is added. This plan corrects the boundary that already fires.**

⚠️ **THE RESIDUAL, NAMED RATHER THAN HIDDEN — and it is a real limit on what this phase delivers.**
The daily poll writes a fact about a KEY, and it surfaces on the account-wide keys surface. It does
NOT attach a cause to a specific STRATEGY's factsheet, because the factsheet-feeding pipelines
still write nothing to `api_keys`. 167-UI-SPEC §4's copy contract already binds that: S1 may claim
only what was actually written for that key, and the factsheet's own chip claims nothing new. The
strategy→key attribution gap is therefore a KNOWN, bounded limit of this phase — record it in the
SUMMARY so the next reader does not mistake it for an oversight.
</scoping_decision>
