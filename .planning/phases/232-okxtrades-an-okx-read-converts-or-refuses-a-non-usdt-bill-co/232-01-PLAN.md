<objective>
VREAD-08: `api_keys.last_fetched_trade_timestamp` never reads ahead of the newest stored trade, and a
key found ahead has its skipped days re-read.

Purpose: the epilogue of `run_sync_trades_job` stamps the fills cursor with wall-clock now whenever the
fills list is empty, which covers a raised fetch, an empty read, the MT5 arm and every run with
`USE_RAW_TRADE_INGESTION` off (CONTEXT PROD reading: 5 active keys ahead of their newest stored fill).
The read side trusts that cursor. This plan makes the writer stamp a stored-through mark, holds it on
any refused or partial read, clamps the read to the stored fills high-water, and anchors a bootstrap
refusal at its read start (rulings Q1, Q7; Phase 231 `dependency-232`, WR-03 gap 1).
Output: one helper in `services/trade_resume.py`, two spans of `run_sync_trades_job`, a new gate file,
three test flips, PROOF-01 records and the hand-offs.

## Decisions this plan applies (quoted from CONTEXT and its orchestrator rulings)

- Stamp: "A stored-through mark: the newest timestamp among the fills this run persisted; when the run
  persisted no fill, the column is left untouched (NULL param). It never stamps wall-clock now."
- Gate: "Only when Phase 2 ran, did not raise and persisted, and Phase 1 did not fail: gate
  `advance_fetched_cursor` on `not phase2_failed` as the 231 hand-off asks." Ruling Q7: "Hold the fills
  cursor also when any `sync_truncated_*` flag is true."
- Seed, ruling Q1 (it replaces RESEARCH design step 2 and PATTERNS section 5 where they say "no stored
  fill, ignore the column"): "`fills_since_ms = min(column, newest stored fill if one exists else daily_since_ms)`;
  a NULL column keeps today's seed (`daily_since_ms`)." A failed fills high-water read is treated as
  "no stored fill known" (the same min with the daily seed), so the column is never used unclamped.
- Bootstrap anchor, ruling Q1: "When `fetch_raw_trades` raised AND the column was NULL at read time AND
  the run had a non-NULL seed, the epilogue passes that seed as `p_last_fetched_ts`." Planner refinement
  (reversible, surfaced in the return): the same anchor on a partial persist failure, because it leaves
  the same unstored span under the same flag. The epilogue reads only `phase2_failed`, so no edit lands
  in the fetch except arm that Phase 222 re-bases over.
- No migration and no RPC change: the RPC's CASE already makes a lower value a no-op, so only a direct
  UPDATE can repair a column that is already ahead (coordinator, after merge).
- Gap 3 (Phase-1 persist ordered after the Phase-2 walk), the Phase-1 store under flags and the
  never-cleared public `daily_pnl_*` flags are NOT fixed here: they are routed by name to Phase 222.
