91 passed). I traced the following and found no defect in them:

- **AllocationOverTime tooltip (plan 05 deviation).** The lookup resolves. Each `<Area>` has
  `dataKey={venueKey(venue)}` = `"v:" + venue`. `TouchTooltip` passes `{...props}` straight
  to Recharts `<Tooltip>`, whose formatter gets the series entry with that `dataKey`.
  `String(item.dataKey).slice(VENUE_KEY_PREFIX.length)` gives back the raw `venue`, which is
  exactly the key `buildAllocationChartData` writes into `usd[v.venue]`. `allocator_holdings.venue`

  - `/api/admin/match/eval`: CSRF, then auth (401), then admin (403), then the rate limit run
    before the name reads. Only `id, display_name` and `id, name` are selected. The `missed`
    list is capped at 50 upstream (`match_eval.py:377`), so the `.in()` lists are bounded.
  - partner-pilot: reads only `id, display_name` from `profiles`, and a read error throws.
  - compute-jobs page: the explicit column list on `compute_jobs_admin` excludes `user_email`
    and `claim_token`. The view itself has no `claim_token`, and the admin client is used
    behind `isAdminUser`.
- **AUMBASIS / HISTORYREADER.** In `HoldingsTable`, `OpenPositionsTable` and
  `AllocatorExchangeManager`, the diff only changes venue rendering. `holdingEquityIsReported`,
  `pnlMissingSentence` and `renderDepartedHistory` are untouched.
- **Badge.** Every `type="status"` caller passes a strategy or contact-request status, so none
  falls into the new "Unknown status" fallback.

The phase-gate sweep (plan 10) reports no label or id leak beyond two residuals. That is not

## Critical Issues

### CR-01 (HIGH): The census-freshness test reds CI on the next migration that touches any of 19 constraints, and its stated fix cannot be done

**File:** `src/lib/display-labels.test.ts:295-328` (offender loop at `:321`, message at `:326`)

**Issue:** The test fails whenever a migration newer than `baseline-carried-migrations.txt`
mentions one of the census constraint names. It fails even when the TS map was correctly
extended in the same PR. Its remedy is "re-dump the baseline in that commit", but
`supabase/schema/BASELINE.md` says the dump is taken from PROD after the apply ("Regenerating
BEFORE the apply would have recorded a PROD that did not yet exist"). Under Decision F a
migration newer than the dump is "the normal case, not a red".

`compute_jobs_kind_check` alone appears in 12 migrations (most recently
`20261026120000_okx_archive_rebuild.sql`), so this will fire.

**Failure scenario:** a PR adds a compute-job kind. It edits the migration and
`COMPUTE_JOB_KIND_LABELS`. The `frontend` vitest shard goes red on the PR. Merging it reds
`main`, and the next pushes stay red until a separate post-apply re-dump PR lands. The only way
to get green is to not touch the constraint, which is the opposite of the census's intent.

**Fix:** resolve each constraint newest-wins across `baseline.sql` plus the uncarried
migrations, the way `src/__tests__/contracts/check-zod-db-check-parity.test.ts` does
(`resolveColumnCheck`, a named `ADD CONSTRAINT ... CHECK` with the newest file winning). Then
compare the TS keys to that set. A new migration is then judged on its values, never on its
existence:

```ts
function latestCheckSet(name: string): string[] {
  const re = new RegExp(`CONSTRAINT\\s+"?${name}"?\\s+CHECK\\s*\\(\\(?"?[a-z_]+"?\\s*(?:=\\s*ANY\\s*\\(ARRAY\\[|IN\\s*\\()([^\\])]*)`, "g");
  for (const f of newerMigrations.slice().reverse()) {          // newest first
    const hits = [...stripSqlComments(read(f)).matchAll(re)];
    if (hits.length) return [...hits.at(-1)![1].matchAll(/'([^']+)'/g)].map((m) => m[1]);
  }
  return checkSet(name);                                          // the dump
}
```

### CR-02 (HIGH, SC-2 failure): The portfolio PDF's correlation table prints raw strategy UUID fragments, and the strategy table prints "Unknown"

**File:** `src/app/portfolio-pdf/[id]/page.tsx:329`, `:338`, `:150`

**Issue:** `correlationKeys` are the keys of `portfolio_analytics.correlation_matrix`.
`strategyNameById` is built only from the portfolio's current `portfolio_strategies` rows
(`:191-195`). A matrix computed before a strategy left the portfolio still carries the departed
strategy's id, so the code renders `(strategyNameById.get(k) ?? k).slice(0, 10)`: a 10- or
14-character UUID prefix as a column or row header. A name does exist for that strategy in
`strategies`. Separately, `name: s?.name ?? "Unknown"` (`:150`) is a non-specified fallback,
where SC-2 requires "Unnamed strategy".

This document is HMAC-rendered, printed and emailed off the platform (see the STALE-01 comment
at `:126-131`), so the leak lands in a file the recipient keeps. The gate SUMMARY records it
and leaves it unfixed, but SC-2 is marked `requirements-completed` by plan 10.

**Failure scenario:** an allocator removes strategy B after the last portfolio-analytics
compute. They download the report. The correlation matrix header reads `3f9a1c2e-4`, and the
row label reads `3f9a1c2e-4b7d`.

**Fix:** use the departed strategy's real name where it exists, and "Unnamed strategy" only on
a true miss. Look up the missing keys with the admin client already in scope:

```ts
const missingIds = correlationKeys.filter((k) => !strategyNameById.has(k));
if (missingIds.length) {
  const { data, error } = await admin.from("strategies").select("id, name").in("id", missingIds);
  if (error) throw error;
  for (const r of data ?? []) if (r.name) strategyNameById.set(r.id, r.name);
}
// render
{strategyNameById.get(k) ?? "Unnamed strategy"}            // CSS truncate, never .slice on an id
// and :150
name: s?.name ?? "Unnamed strategy",
```
