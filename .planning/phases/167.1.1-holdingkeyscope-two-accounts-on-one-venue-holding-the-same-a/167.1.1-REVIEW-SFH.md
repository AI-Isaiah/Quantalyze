# 167.1.1 silent-failure review

Scope: `git diff aea86620c..HEAD -- src analytics-service supabase`. MEDIUM and above only. Read-only; no database queried.

Checked and found sound (no finding): the adapter's query error path logs the message only and throws `HoldingCompareLoadError`; the page ceiling throws rather than returning a partial series; a bad `updated_at` throws (only for rows that reach the per-day pick); the invalid-mark skip happens BEFORE the per-day pick so a later `0.0` sentinel cannot eclipse a valid mark; no zero-fill or forward-fill; `analyzePriceSeries` returns null (not 0) for vol/Sharpe with fewer than 2 adjacent-day returns; `api_keys.disconnected_at` is in `API_KEY_USER_COLUMNS` and the payload type, so it is selected; `summarizeLiveHoldings` lands every toggled-on row in `total` or one `excluded*` part, and a key absent from the key list still reaches `unknownStatus`.

## SFH-01 (MEDIUM, user-facing) A non-crypto spot holding silently vanishes from /compare

Location: `fetchHoldingCompareItem` (`if (!isCryptoExchange(parsed.venue)) return null;`) and the item merge in `src/app/(dashboard)/compare/page.tsx` (`holdingItemsRes.filter(x => x !== null)`, then `items.length === 0` -> "This comparison isn't available.").

Evidence: the adapter reads the rows first (so the holding provably exists and is owned), then returns `null` for an MT5 `ACCOUNT-<hex>` row. `null` is the same value D-15 uses for "unowned or nonexistent". The page drops a null item without a trace: in a mixed comparison (strategy + MT5 holding) the holding is simply absent from the table; alone, the allocator reads "This comparison isn't available", which is false and gives no cause.

Impact: an allocator who owns the holding (it is on their Holdings tab) sees it disappear from a comparison they built, with no reason. The "uncomputable is null" rule is met for the number, but the item itself is converted into a non-existence claim. Nothing is logged, so support cannot tell this from an RLS miss.

Suggested fix: do not collapse this case into the D-15 null. Return a ready-shaped item with `historyState: "rebuilding"` and `analytics: null` (the factsheet already has a withheld-note slot; add a dedicated "this venue carries no asset price" note), or return a typed marker the page renders as a named note. D-15 is preserved because this branch is reached only after rows were found (owned rows only), so no existence leak. If the founder prefers dropping, at least render a per-id notice on the page.

## SFH-02 (MEDIUM, user-facing) A ready factsheet with em-dash metrics gives no reason, and its basis line overstates what was computed

Location: `HoldingFactsheet` (`tooFewPricedDays`, the `holding-factsheet-price-basis` paragraph) and `analyzePriceSeries` (`returns.length >= 2` gate, adjacency rule).

Evidence: with 30 or more priced days that are not on adjacent calendar days (a holding priced on alternating days, or a poll outage), `cumulative_return` and `max_drawdown` are numbers while `vol` and `sharpe` are null (fewer than 2 adjacent-day returns). The card then prints `Computed from 30 days of <symbol>'s daily price...` under two numbers and two em-dashes. Nothing says why two cells are blank, and "30 days" is a count of priced days, not a span: the cumulative return can span 700 calendar days of which 30 are priced. `tooFewPricedDays` is inferred from "all four metrics null", not from `priced_days < HOLDING_COMPARE_MIN_PRICED_DAYS`, so the two sources of truth can disagree if the adapter ever returns partial nulls below the minimum.

Impact: a blank cell reads as "missing data" to the allocator and as "zero risk" to a skimmer; the basis sentence implies a continuous series it is not.

Suggested fix: derive the below-minimum state from `analytics.priced_days < HOLDING_COMPARE_MIN_PRICED_DAYS`. When Sharpe or vol is null but priced_days is at or above the minimum, add a clause ("Volatility and Sharpe need at least 2 consecutive priced days; this holding has gaps"). Consider carrying the first/last `asof` so the line can say "N priced days between X and Y".

## SFH-03 (MEDIUM, data-integrity) A malformed mark or day is skipped with no log, so a schema or driver change reads as "not enough priced days"

Location: `dailyMarkPrices` (`typeof m !== "number" || ...` and the `ISO_DAY` skip), consumed by `fetchHoldingCompareItem`.

Evidence: `mark_price` is `numeric NOT NULL`. The only legitimate skips are the writer's `0.0` sentinel and non-positive numbers. A mark that arrives as a string (a PostgREST or client change in numeric serialisation) or a non-ISO `asof` hits the same silent `continue` as the sentinel. If every row is skipped, the item is `ready` with `priced_days: 0` and the copy "Only 0 priced days of X so far", a confident data-quality verdict about a holding whose rows were present and unreadable. The `ISO_DAY` guard cannot fire for a `date` column and so is unreachable cover that would mask a real change the same way.

Impact: a type regression turns every spot holding on /compare into a plausible "not enough history" message, with no error, no log and no Sentry signal. This is the exact shape of failure the repo rule "fail loud" exists for.

Suggested fix: separate the two skip classes. A number that is not above 0 stays a silent gap (documented sentinel). A non-number mark or a non-`YYYY-MM-DD` `asof` is a contract violation: `console.error` with the count and holding ref (no payload) and throw `HoldingCompareLoadError`, the same way a bad `updated_at` already does. Also log once when `rows.length > 0` and `points.length === 0`.

## SFH-04 (MEDIUM, data-integrity) The disconnected-key input is optional on the row types, so an omitted field reads a disconnected key as connected

Location: `keyNeedsAttention` / `KeyAttentionInput` in `src/lib/closed-sets.ts`; `HoldingRow.source_key_disconnected_at?`, `OpenPositionRow.source_key_disconnected_at?`, `DesignProps.disconnectedAtByHoldingId` (defaults to `{}`) in `HoldingsTable.tsx` / `OpenPositionsTable.tsx`.

Evidence: `summarizeLiveHoldings` made `disconnectedAtByKeyId` REQUIRED with the stated reason "a caller cannot omit it and silently read a soft-disconnected key as connected (a fail-open)". The other money surfaces do the opposite: the field is optional, `KeyAttentionInput` documents that a missing `disconnected_at` "reads as connected / no status, never as a throw", and the design-mode table defaults the map to `{}`. Both production builders (`HoldingsTabPanel` spot and derivative rows) pass the field today, so nothing is wrong yet. But a future builder, or a payload projection that drops the column, makes a soft-disconnected key's dollars render as current, un-struck-through, outside the "keys needing attention" footer and count, with no error and no failing type.

Impact: the disclosure D-02 exists to guarantee silently disappears on the surface where the omission happens, and the three surfaces now disagree on whether omission is allowed.

Suggested fix: make `source_key_disconnected_at` required (`string | null`) on `HoldingRow` and `OpenPositionRow`, and `disconnectedAtByHoldingId` required on the design props, so TypeScript rejects an omitted field the way it does for the composer. Keep `KeyAttentionInput` optional only if a census test pins that every production call site passes both fields (the census test file already exists; extend it).
