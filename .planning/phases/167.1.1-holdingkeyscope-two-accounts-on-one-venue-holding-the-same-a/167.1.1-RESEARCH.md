### Soft-disconnected keys (founder, 2026-10-15, AskUserQuestion: "Count, disclose (Recommended)")
- **D-02:** a soft-disconnected key's holdings stay IN the total. They are disclosed as "keys needing attention" the same way an untrusted key's are: the "needing attention" predicate is widened to cover a key with `disconnected_at` set, whatever its `sync_status`. This answers SC 3 and founder queue item 11's second question. It is the question 167.1's CONTEXT (`## Known limits`) and 167.1-REVIEW booked for the founder.
  - The rule matches the per-key reader's existing rule: every key the allocator owns counts, departed ones included (`src/lib/latest-holdings-per-key.ts` docblock). Anything not trusted goes into a disclosed part and is never hidden.
  - PROD on 2026-10-15 (read-only, marker = PRODUCTION): 13 soft-disconnected keys with sync status `complete` hold 146 `allocator_holdings` rows from the last 30 days, so the case is reachable today.

### /compare per-holding metrics (founder, 2026-10-15, AskUserQuestion: "Price-based, spot only (Recommended)")
- **D-03:** each holding's return, Sharpe, max drawdown and vol are computed from that holding's daily PRICE change (mark price day over day), never from its dollar value. That way buying, selling or moving more of an asset is not read as a gain or loss.
  - Spot holdings go `"ready"` once that source exists.
  - Derivative holdings stay `"rebuilding"` until a signed basis is defined.
  - A test fails on the dollar-ratio read: the value-level ratio over `allocator_equity_snapshots.breakdown` in `reconstructAndAnalyze` (`src/app/(dashboard)/compare/lib/holding-compare-adapter.ts`).
  - PROD on 2026-10-15: 26 of 36 spot holdings (per key and asset) have at least 30 priced days. For derivatives it is 141 of 2025.

## Summary

Most of the phase as booked already shipped in Phase 170.4. At HEAD the headline collapse is fixed: `derivePhase07Fields` keys by `${r.api_key_id}|${holdingScopeKey(r)}` (`src/lib/queries.ts:4950`), the ingestion index carries `api_key_id`, and `getLatestExposureSnapshot` is gone (`grep` over `src` and `analytics-service` finds no hit). What remains is four pieces of work: (1) one cross-surface test that goes RED when the `${r.api_key_id}|` prefix is removed; (2) a census test that pins every consumer of the `holding:venue:symbol:type` key shape; (3) widening the "needing attention" predicate to cover `disconnected_at`; (4) replacing `/compare`'s dollar-ratio per-holding read with a price read and flipping spot to `"ready"`.

**Four findings change what the planner should assume.** (a) The headline test already has a home: `HoldingsTabPanel.exposure-agreement.test.tsx` already runs the real read -> `derivePhase07Fields` -> `HoldingsTabPanel` path with a two-live-keys describe; it just lacks the derivative rows, the revoked key and the composer total, so SC 1 *extends* it. (b) D-02 needs **no payload, query or column-grant change**: `disconnected_at` is already selected by the user-scoped `getUserApiKeys` (`API_KEY_USER_COLUMNS`) and already typed on `payload.apiKeys`; the work is client-side wiring plus one new predicate. (c) For D-03, **`allocator_holdings.mark_price` is `NOT NULL` but a failed ticker is written as `0.0`, and MT5 account rows are written with `mark_price = 1.0`** (both read in `allocator_positions.py`), so "no price" is a zero sentinel the adapter must treat as a gap, and an MT5 spot row would show a flat 0% "return". (d) The census must also catch a second key shape that the `holding:` grep misses: `computeHoldingsFingerprint` builds `${symbol}:${venue}:${holding_type}` (`scenario-state.ts:253`).

**Primary recommendation:** Extend `HoldingsTabPanel.exposure-agreement.test.tsx` for SC 1 (neuter `queries.ts:4950`); add `src/__tests__/holding-scope-key-census.test.ts` on the `display-sign-single-source` pattern (derive population from disk, count-pinned allowlist with reasons); add `keyNeedsAttention` / `keyAttentionChipLabel` to `closed-sets.ts` and thread `disconnected_at` from `payload.apiKeys` into the rows and into `summarizeLiveHoldings` as a new REQUIRED argument; rewrite `fetchHoldingCompareItem` to read `allocator_holdings` marks per holding (paged `.range()`, 730 days, invalid mark = gap), pick one mark per day deterministically, and feed the unchanged metric kernel.

2. ## Common Pitfalls

### Pitfall 1: Equal-`asof` neuter fixture is non-deterministic
**What goes wrong:** with `perKeyMap` keyed on scope alone, two rows at the same asof keep whichever the reader returned first; the "RED" depends on input order.
**How to avoid:** give the revoked key an OLDER asof than the trusted key (fixture above).
**Warning signs:** the new arms go RED on some runs only.

### Pitfall 2: Pin 5 silently stops proving anything
**What goes wrong:** `summarizeLiveHoldings` calls `keyNeedsAttention`, which calls the real `isUntrustedKeySyncStatus` internally; the `vi.mock("@/lib/closed-sets")` double of `isUntrustedKeySyncStatus` is never consulted; either pin 5 goes RED or (if edited carelessly) it passes vacuously.
**How to avoid:** double `keyNeedsAttention` (delegate to real unless `WIDEN`) and keep the control arm that `error` is trusted under the real module.

### Pitfall 3: A zero mark read as a price
**What goes wrong:** a failed ticker writes `mark_price = 0.0`; treating it as a price yields a -100% then +inf return.
**How to avoid:** the validity filter (`> 0`, finite, number) before the per-day pick; test with a `0` row between two valid days.

### Pitfall 4: MT5 account rows show a confident flat 0%
**What goes wrong:** `ACCOUNT-xxxxxxxx` rows carry `mark_price 1.0`; the card would print `0.00%`, `—`, `0.00%` under a caption claiming a price basis.
**How to avoid:** Open Question 1.

### Pitfall 5: `priced_days` required field breaks fixtures
**What goes wrong:** adding a required `priced_days` to `HoldingCompareAnalytics` breaks `tsc` (not vitest) in `HoldingFactsheet.test.tsx`, `strategy.signed-zero.test.tsx`, `compare/page.test.tsx`, the adapter tests and the RLS test.
**How to avoid:** update every fixture in the same plan; run `npx tsc --noEmit` (the repo's CI type-check) after.

### Pitfall 6: Census counts drift on unrelated edits
**What goes wrong:** a count-pinned allowlist trips when a file legitimately gains a second mention.
**How to avoid:** key entries by (file, matcher) and give each a one-line reason; that is the intended two-sided pin, not a bug.

### Pitfall 7: Paging by `.range()` while rows are inserted
**What goes wrong:** the daily poll upserts mid-read; offset paging can skip or repeat a row.
**How to avoid:** group by `(asof, api_key_id)` after collecting and let the per-day pick be order-independent (it is: max `updated_at`, deterministic tie-break). Repeats collapse; a skipped row can only change which same-day mark wins, never invent a price.

### Pitfall 8: `showRevoked` default vs UI-SPEC
See D-02 section. Assert the shipped default.

## Code Examples

### Per-day price pick (D-03)
```typescript
// Source: composed from holdings-account-day.ts (writtenAtMicros) and the rule above. [ASSUMED: names]
import { writtenAtMicros } from "@/lib/holdings-account-day";

type MarkRow = { asof: string; mark_price: unknown; updated_at: string; api_key_id: string };

const validMark = (m: unknown): m is number =>
  typeof m === "number" && Number.isFinite(m) && m > 0;

export function dailyPrices(rows: readonly MarkRow[]): Array<{ asof: string; price: number }> {
  const best = new Map<string, { price: number; at: number; key: string }>();
  for (const r of rows) {
    if (!validMark(r.mark_price)) continue;            // a gap, never a zero
    const at = writtenAtMicros(r.updated_at);          // throws HoldingsUpdatedAtError on a bad instant
    const key = r.api_key_id.toLowerCase();
    const cur = best.get(r.asof);
    if (!cur || at > cur.at || (at === cur.at && key < cur.key)) {
      best.set(r.asof, { price: r.mark_price, at, key });
    }
  }
  return [...best.entries()]
    .sort(([a], [b]) => (a < b ? -1 : 1))
    .map(([asof, v]) => ({ asof, price: v.price }));
}
```
