## Summary

The D-02 predicate (`keyNeedsAttention` / `keyAttentionChipLabel`) is wired correctly into every
money surface the orchestrator scoped it to. `summarizeLiveHoldings` (composer), the legacy and design
`HoldingsTable` filter, hidden counter and chip, and the `OpenPositionsTable` footer pass and chip all
use it. On the Holdings and Open Positions surfaces each dollar still lands in exactly one part, and
no total moves. `HoldingsTabPanel` gets `disconnected_at` from the full `getUserApiKeys` projection
through the payload, and `keyStateMapsOf` builds both composer maps from a single pass. No money
surface still asks only for the sync status. The key-management call sites (`ApiKeyManager`, the
`/strategies` pill) keep `isUntrustedKeySyncStatus` on purpose, as the CONTEXT reading says.

D-03 is mostly sound. The paging uses a total order (`asof`, `id`), and the page ceiling throws
instead of returning a partial series. A mark that is not a finite number above 0 is treated as a
gap. Returns are taken only between adjacent days. The minimum counts priced days. Annualization is
crypto 365. RLS plus the `allocator_id` filter keeps D-15 intact.

One defect is user-facing. The D-03 "ready" gate admits holdings whose `mark_price` is a constant the
writer hard-codes (stablecoins), not an observed price. The phase withholds MT5 for exactly this
reason. Three MEDIUMs: two concern whether the new tests can fail, and one concerns D-02 fidelity on
the composer AUM.

Tests run: `holding-scope-key-census`, `holding-compare-adapter`, `HoldingFactsheet` and
`closed-sets.untrusted-key-status` all pass (4 files, 117 tests). This proves they are green. It does
not prove they can fail (see WR-01 and WR-02).

## Critical Issues

### CR-01 (HIGH): /compare shows confident 0% figures computed from a hard-coded $1 "price" for stablecoin holdings, and the caption calls that constant "daily price"

**Classification:** user-facing. The figure shown is not a measurement.
**File:** `src/app/(dashboard)/compare/lib/holding-compare-adapter.ts`, symbols `holdingCompareHistoryState` and `fetchHoldingCompareItem` (the `isCryptoExchange` gate is the only venue/asset exclusion). Rendered by `src/components/strategy/HoldingFactsheet.tsx`, State R caption (`"Computed from … of ${symbol}'s daily price, so buying, selling…"`).

**Evidence:**
- Writer: `analytics-service/services/allocator_positions.py` `_fetch_spot_rows` sets `mark_price = 1.0` for any asset in `STABLECOINS` *"without a ticker call"*. The sFOX builder writes `"mark_price": 1.0` for every row it keeps (stablecoins only). `STABLECOINS` (`analytics-service/services/closed_sets.py`) is `{"USDT","USDC","DAI","BUSD","TUSD","FDUSD","USD"}`.
- Gate: `holdingCompareHistoryState("spot")` returns `"ready"`, and the only further exclusion is `!isCryptoExchange(parsed.venue)`. `binance`, `okx`, `bybit` and `sfox` all pass it. A `holding:binance:USDT:spot` (or any sFOX holding) with 30 or more poll days therefore gets `analyzePriceSeries` over a constant 1.0 series. The result is `cumulative_return = 0`, `max_drawdown = 0`, and `vol = 0` (`dispersion` reports a residue sd as exactly 0, and `vol` is not nulled on 0). It renders as `0.00%`, `0.00%`, `0.00%`, `—`, with the caption "Computed from N days of USDT's daily price".
- The phase's own orchestrator reading (CONTEXT, "MT5 account rows under D-03") withholds MT5 because its `mark_price` is `1.0` and "a price-based return there would print a confident 0%, which is an invented number". Stablecoin rows have the same mechanism: a writer constant, not an observed price. They are admitted anyway. No test covers a stablecoin symbol.

**Why it matters:** The repo rule is "never invent data: uncomputable metrics are null". The card claims the figures come from a daily price, but no price was ever read. A depeg would be invisible, and the 0.00% vol and drawdown would still print. USDT/USDC collateral is common in allocator books (see the Bybit UTA fallback in the same writer), so this is reachable on day one of the "ready" flip.

**Fix:** Treat a holding whose marks are the writer's cash convention like MT5, with no item and no numbers. Prefer a shared closed set over a local list. Mirror `STABLECOINS` into `src/lib/closed-sets.ts`, or reuse an existing TS twin if one exists, and gate on it:
```ts
if (!isCryptoExchange(parsed.venue)) return null;
// D-03: a cash-convention asset's mark is the writer's constant 1.0, not a price.
if (isStablecoinSymbol(parsed.symbol) || parsed.venue.toLowerCase() === "sfox") return null;
```
If the founder would rather show a "no price is observed for this asset" note, add a State for it instead of returning null. Either way, add a red test: `holding:binance:USDT:spot` with 40 rows at `mark_price: 1` must not render any `0.00%`.

## Warnings

### WR-01 (MEDIUM): The SC 2 census cannot see composite keys built as a tuple, a `.join`, or from destructured variables, so a new key-merging consumer passes unclassified

**Classification:** data-integrity (the guard the phase relies on to stop the next silent cross-key merge)
**File:** `src/__tests__/holding-scope-key-census.test.ts`, `MATCHERS` (M1–M7) and the `KNOWN LIMITS` docblock

**Evidence:**
- M5 matches only template literals that interpolate a property access (`${x.venue}:${x.symbol}`). These shapes produce no hit from any matcher:
  - `${venue}:${symbol}:${holding_type}` (destructured)
  - `[h.venue, h.symbol, h.holding_type].join(":")`
  - a `Map` keyed by `JSON.stringify([...])`
  - a Python tuple key `(r["venue"], r["symbol"], r["holding_type"])`
- The repo already holds a live, uncaught instance of the Python idiom: `analytics-service/routers/match.py` `_load_holding_portfolio_context`, `key = (counted["venue"], counted["symbol"], counted["holding_type"])`. That tuple is the summing key that actually merges keys. The census classifies `match.py` only through its M4 f-strings, so the tuple line is not what the pin counts. If it were deleted or duplicated in another function, no pin would move.
- The `KNOWN LIMITS` block names only `"holding" + ":"` and `new RegExp(...)`. It does not mention the tuple, join or destructured shapes, which are the common idioms for the collapse SC 2 is guarding.

**Why it matters:** SC 2 is "a test that ... fails when a new one appears unclassified". The 170.4 D-08 collapse class of bug is a dict or Map keyed by `(venue, symbol, type)` without `api_key_id`. That is exactly the shape that is invisible here, so the census stays green on the defect it exists to catch.

**Fix:** Add two matchers, each with a red/green self-test sample. Python: `\(\s*\w+\[["']venue["']\]\s*,\s*\w+\[["']symbol["']\]` (and the `symbol`-first order). TS: a `[...venue..., ...symbol...].join(` form plus a destructured `\$\{venue\}:\$\{symbol\}` form. Then pin `match.py`'s tuple line with its `merges-on-purpose` verdict. At minimum, name these shapes in `KNOWN LIMITS` so the guard does not overclaim.

### WR-02 (MEDIUM): The SC 1 "narrowed branch" test asserts a state production cannot produce, so the narrowed path with an untrusted second key is never exercised

**Classification:** data-integrity (test reliability for the composer AUM marker)
**File:** `src/app/(dashboard)/allocations/HoldingsTabPanel.exposure-agreement.test.tsx`, describe `"167.1.1 SC-1: two keys, one venue and asset, …"`, `it("the 167.1 marker, narrowed branch: the same total and the same part")`

**Evidence:**
- The test calls `markerArgs(book, ["key-a", "key-b"])` with `key-b` revoked. In production `contributingApiKeyIds ⊆ allocatorEligibleApiKeyIds ⊆ eligibleKeyIds` (`src/lib/queries.ts`, the `contributingApiKeyIds` build). Eligibility is `isPerKeyDailiesEligibleKey`: `is_active && sync_status !== "revoked" && disconnected_at == null`. A revoked key is never contributing.
- In the real narrowed branch, `key-b`'s rows go to `excludedUntrusted` (and are left out of `total`), not to `untrusted`. Neither SC 1 assertion checks `excludedUntrusted`. So the two-keys-one-ref case on the path the composer actually takes in book mode (`narrowToModelledBook` is always true there; see the function's own comment) is not pinned. The test's "narrowed" case is the degrade-branch arithmetic again, run through an impossible fixture.

**Why it matters:** SC 1 is meant to prove the marker keeps both keys' rows. Under the booked key (scope key without `api_key_id`), the production-shaped failure is `excludedUntrusted.count` dropping from 2 to 0 while `total` is unchanged. No SC 1 assertion would see that.

**Fix:** Replace the fixture with the production shape, and assert the excluded part:
```ts
const m = summarizeLiveHoldings({ ...markerArgs(book, ["key-a"]), eligibleApiKeyIds: ["key-a"] });
expect(m.total).toBe(41200);                 // 40000 + 1200, key-a only
expect(m.excludedUntrusted.amount).toBe(24700); // key-b: 25000 + -300
expect(m.excludedUntrusted.count).toBe(2);
```
Re-run the byte-backup neuter of the scope key, and record that this assertion goes RED.

### WR-03 (MEDIUM): D-02 says a soft-disconnected key's holdings "stay IN the total", but the composer AUM always leaves them out in production, and the new JSDoc says otherwise

**Classification:** user-facing (the composer's PORTFOLIO AUM figure). A founder decision is needed, or the doc must be corrected.
**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts`, `LiveHoldingsSummary.untrusted` JSDoc (*"or since 167.1.1 D-02 a soft-disconnected key whatever its status, whose dollars stay IN `total`"*) and `summarizeLiveHoldings`'s narrowed branch. Consumed by `ScenarioComposer.tsx` (`keyStates` / `liveHoldingsSummary`).

**Evidence:**
- A soft-disconnected key is never in `eligibleKeyIds` (`disconnected_at == null` is required), so it is never in `contributingApiKeyIds`. Book mode requires `contributingApiKeyIds.length > 0`, so `narrowToModelledBook` is always true in production. The function's comment says the degrade branch "is unreachable there".
- The phase's own composer test says so outright: *"Its dollars never leave the total on this path (the narrowed branch never summed them)"*. It asserts the AUM field equals the trusted key's value alone and the note reads *"Excludes $3,300 from keys needing attention."*
- What D-02 actually changed on the composer is only the noun: `excludedNotConnected` → `excludedUntrusted`. The JSDoc on `untrusted` describes a path that never runs for a disconnected key, and the CONTEXT decision text ("stay IN the total") holds for Holdings and Open Positions but not for the AUM figure.

**Why it matters:** CONTEXT presents D-02 as the founder's answer to "do a soft-disconnected key's dollars count". A reader of the JSDoc or the phase report would conclude that the composer AUM now includes them, and it does not. The 13 PROD keys named in D-02 hold dollars that the AUM excludes, disclosed as "Excludes". That may well be the right call, since the D-20 narrowing keeps the AUM in agreement with the modelled book. But it is a different answer from the one recorded, and it was made without the founder.

**Fix:** Either (a) record in CONTEXT/ROADMAP that on the composer D-02 is met as "disclosed in the Excludes clause, not summed" (D-20 narrowing wins), and correct the `untrusted` JSDoc to say a soft-disconnected key reaches `untrusted` only in the degrade branch, or (b) if the founder wants them summed, change the narrowing so a needs-attention key's equity is added to `total` and flagged. That is a number-moving change and needs its own decision.
