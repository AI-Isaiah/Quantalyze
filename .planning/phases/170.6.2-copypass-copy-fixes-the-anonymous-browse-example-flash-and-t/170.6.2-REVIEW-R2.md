### WR-01: the e2e hydration signal is real again (fixed, confidence 9)

- `StrategyTable.tsx:649-654` sets `data-strategy-table-prefs-applied` on `<html>` only from a
  `useEffect`. Effects do not run under SSR, so the server HTML cannot carry the attribute. The
  effect runs after the hydration commit, so `onChange` on the "Hide examples" input is attached
  by the time the attribute is set. `StrategyFilters` is not behind a Suspense or `dynamic()`
  boundary inside `StrategyTable` (grep returns nothing), so the input is hydrated in the same
  commit.
- Anonymous `/browse` (full-flow): `useDiscoveryPrefs` runs with `enabled: false`, so
  `prefsHydrated` is true from the first render. The mark goes on after the first client commit.
- Signed-in `/discovery` (discovery-hide-examples-default): `isHydrated` flips to true after the
  storage read, and the mark is set in the commit that follows. The prefs-mirror effect's
  `setShowExamples(!prefs.hide_examples)` can still be pending when the mark lands. That is not
  a race, for two reasons. First, the initial `showExamples` state (`:516-518`) already equals the
  DEFAULTS outcome, so for a fresh allocator the update is a no-op. Second, the toggle handler is
  a functional update (`setShowExamples((v) => !v)`, `:980`), so it composes with any queued
  mirror update instead of reading a stale closure.
- Default-mounts byte fixture: `grep -c prefs-applied` on
  `__fixtures__/strategy-table-default-mounts.json` returns 0. The attribute is on
  `documentElement`, outside the `container.innerHTML` the fixture pins, and the RTL unmount
  removes it through the cleanup.
- Multiple mounts clearing each other's mark: every mount site
  (`browse/[slug]/page.tsx`, `discovery/[slug]/page.tsx`, `strategies/page.tsx`,
  `MyStrategiesSection.tsx`) renders exactly one `<StrategyTable>`. On a keyed client navigation,
  React runs passive-unmount cleanups before passive-mount effects in the same commit, so the old
  table's `removeAttribute` cannot follow the new table's `setAttribute`. The shared-flag design
  would break if a future page mounted two tables, but nothing does today. That is below MEDIUM
  and is not reported.
- Test bite: arm A (`renderToString` under jsdom, then `document.documentElement.hasAttribute`)
  goes red if the write moves into render. Arm B goes red if the effect is removed. Arm C goes
  red if the cleanup is removed. All three can fail.

### SFH-1: fetchKinds no longer swallows a failure or clears the list (fixed, confidence 9)

- `ComputeJobsTable.tsx:139-165`: the catch path now runs `console.error` with the status and the
  error, keeps `kinds`, and sets a message string that carries `(HTTP <status>)` when a status
  exists. The `setKinds([])` on failure is gone.
- Request-sequence guard: `requestId` is taken before the `await`. Both the success path (after
  parsing, before `setKinds`) and the failure path (after logging, before `setKindsError`) return
  early on `requestId !== kindsRequestRef.current`, so a response that lands late, good or
  failed, cannot overwrite a newer one. A stale failure is still logged, which is acceptable
  diagnostic output.
- Test bite, traced against the pre-fix code: K5 goes red on the old `setKinds([])`. K7 and K7b
  go red without the guard (the late failure would show the line; the late good read would put
  `stale_kind` back). K6 and K6b go red without the log. K3 and K3b pin the message with and
  without a status.
