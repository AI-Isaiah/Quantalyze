<objective>
Make the admin Compute Jobs Kind filter list every kind that has jobs (SC-4, D-07). Today the select offers a
hardcoded three kinds, so an admin cannot filter to, say, `derive_allocator_equity`. The list now comes from a
distinct-kinds read on the existing admin route. It is behind the same gate and the same client, and it is its
own query, so it never depends on which page of jobs is loaded.

Purpose: an admin can filter to any kind that is actually in the queue.
Output: a `?facets=kinds` branch on the route, a Kind select fed by it, tests on both, and a neuter proof.
</objective>

Discretion taken (CONTEXT "Claude's Discretion", the facet's API shape): a `?facets=kinds` branch of the same
route, returning `{ kinds: string[] }`, sorted ascending. NOT an extra field on the page payload. The page
response is a bare `ComputeJobAdminRow[]`, and wrapping it would break its contract and every existing route
test for no gain.

Why per-kind probes and not one `select("kind")`: PostgREST has no DISTINCT. A bare `select("kind")` returns
rows, not kinds, and is capped by the API's max-rows, so it can silently miss a rare kind. That is the same
defect as the hardcoded list. `compute_jobs.kind` carries a foreign key to `compute_job_kinds.name`
(`supabase/schema/baseline.sql`, constraint `compute_jobs_kind_fkey`), so the registry is a complete, small
superset of the present kinds. One `limit(1)` probe per registered kind, run in parallel, is exact. The
probes read the `compute_jobs_admin` view, the same relation the list filters with `.eq("kind", …)`. So
"listed" means exactly "selecting it returns rows". No migration.

Next.js note (AGENTS.md): the route is an App Router route handler using `NextRequest.nextUrl.searchParams`,
as it already does. No new Next API.

Environment: Node 22 (`PATH=/opt/homebrew/opt/node@22/bin:$PATH`). vitest runs one file per invocation.
