### Pattern 1: The reusable capture-count-WITHHOLD idiom (Area 1)

**What:** Redirect a psql call's stderr to a per-run temp file, count its lines with a
never-blank fallback, and report the COUNT (never the content) in the failure message.

**When to use:** Any psql (or other credential-bearing process) invocation whose stderr must
never reach a public log but whose absence-of-diagnosis would itself be a defect.

**Where it already exists, verbatim (`scripts/test-ledger-drift-check.sh`, the `ledger_rows` arm):**
```bash
local ledger_rows matched ledger_rows_rc=0 err_lines
local ledger_rows_err="${tmp}/ledger_rows.err"
set +e
ledger_rows="$(run_ledger_query ledger_rows "$names_csv" 2>"$ledger_rows_err")"
ledger_rows_rc=$?
set -e
# THE `2>/dev/null` HERE IS CORRECT — the braces matter: `wc … || echo '?'` must
# be grouped BEFORE the pipe, or `tr` succeeds on nothing and the fallback never fires.
err_lines="$( { wc -l < "$ledger_rows_err" 2>/dev/null || echo '?'; } | tr -d '[:space:]' )"
if [ "$ledger_rows_rc" -ne 0 ]; then
  fail "MEASURE_FAIL: could not read the TEST ledger row count (the ledger_rows query exited ${ledger_rows_rc}; ${err_lines} line(s) of stderr captured and WITHHELD — it can carry a DSN, host or username). …"
fi
```

**The defective call site to fix (same file, `missing` direction):**
```bash
local missing_file="${tmp}/missing.txt"
run_ledger_query missing "$names_csv" > "$missing_file" \
  || fail "the ledger presence query failed (output withheld — it can carry connection detail)."
```
Stderr here is **bare** — no `2>` redirect at all — so on a psql connect/auth/DNS failure it
streams straight to the job's own stderr = the public Actions log, contradicting the `fail`
message's own claim that output is "withheld." The fix is to apply the exact same idiom: redirect
to a `${tmp}/missing.err` file, count lines with the `{ wc -l … || echo '?'; } | tr -d
'[:space:]'` idiom, and include the count (never the content) in the `fail` message.

**Test idiom already established for this file** (`src/__tests__/drift-check-scripts.test.ts`):
tests inject a fake `LEDGER_QUERY_CMD` (overriding `run_ledger_query`'s default psql call) via env,
scaffolded with `scaffoldLedgerCase()`. A new test for the `missing` direction should follow the
same shape as the existing `ledger_rows`-direction MEASURE_FAIL tests: inject a stub that writes a
known marker string to stderr and exits non-zero for the `missing` direction, then assert (a) the
marker string does NOT appear in the gate's stdout, and (b) the failure message contains a
non-blank line count and the word `WITHHELD`.

### Pattern 2: ONE redaction definition, referenced from every site (Area 2)

**What was found, byte-verified this session (see Assumptions Log A1 for full methodology):**

| File | Sites | Expression sets in use |
|------|-------|------------------------|
| `ci.yml` | 3 (three separate jobs' mutex-acquire retry blocks) | All 3 use the SAME 2-expression set: `postgres(ql)?://` URL-userinfo mask + `server at "…"` mask + `for user "…"` mask (3 expressions total per block) |
| `test-restore-from-baseline.yml` | 5 | Vary: 3-expression (mutex-acquire, marker check) / 4-expression (activity gate — adds `could not translate host name "…"`) / 5-expression (dry-run push, and the `id: redact` loop — add `host=` and `user=` masks) |

**⚠️ Critical finding not stated in CONTEXT.md:** No single existing block covers ALL SIX
expression shapes seen across the 8 sites. The activity-gate block (CONTEXT's "the correct target
form") has 4 of 6 — it is missing `host=`/`user=`. The `id: redact` loop and the dry-run-push block
have 5 of 6 — both are missing the DNS-hostname expression. **The new shared definition must be
the UNION of all 6 expressions observed across every site, not a copy of any one existing block.**

**Recommended carrier — one file, referenced everywhere:**
```
scripts/redact-psql-stderr.sed
------------------------------
s#(postgres(ql)?://)[^@]*@#\1***@#g
s#(host=)[^ "]*#\1***#g
s#(user=)[^ "]*#\1***#g
s#(server at )"[^"]*"( \([^)]*\))?#\1"***"#g
s#(could not translate host name )"[^"]*"#\1"***"#g
s#(for user )"[^"]*"#\1"***"#g
```
Every call site becomes:
```bash
sed -i -E -f scripts/redact-psql-stderr.sed "${file}"       # in-place
# or, for the stream form (dry-run push style):
sed -E -f scripts/redact-psql-stderr.sed "${raw}" > "${out}"
```
`sed -E -f <scriptfile>` applies extended-regex mode to every substitution command read from the
file — `-E` and `-f` compose normally in GNU sed. This collapses all hand-copied `-e` chains to a
single reference, satisfying the locked decision ("ONE definition, referenced N times — not N
corrected copies") without inventing a bash-function-sharing mechanism across workflow files
(ruled out — see Alternatives Considered).

### Pattern 3: The scanner-gate + `calibrate()` idiom for "no NEW unredacted site" (SC-1)

**Where it already lives:** `src/__tests__/test-restore-workflow-wiring.test.ts` already loads all
three files this phase touches as raw-text constants at module scope:
```typescript
const WF_PATH = ".github/workflows/test-restore-from-baseline.yml";
const CI_PATH = ".github/workflows/ci.yml";
const SCRIPT_PATH = "scripts/restore-test-from-baseline.sh";
const read = (rel: string): string => readFileSync(join(ROOT, rel), "utf8");
const WF = read(WF_PATH);
const CI = read(CI_PATH);
const SCRIPT = read(SCRIPT_PATH);
```
and already provides a mutation-calibration helper:
```typescript
function calibrate(
  label: string,
  mutate: (s: string) => string,
  predicate: (s: string) => boolean,
  text: string = WF,
): void {
  const mutant = mutate(text);
  expect(mutant, `CALIBRATION ${label}: … produced an identical string`).not.toBe(text);
  expect(predicate(text), `${label}: the predicate is FALSE on the real file`).toBe(true);
  expect(predicate(mutant), `CALIBRATION ${label}: … did NOT flip on the mutant`).toBe(false);
}
```
This is the idiomatic home for the new SC-1 gate. The predicate should assert something like: "no
`sed -E` redaction expression (`server at "`, `for user "`, `could not translate host name "`,
`(host=)`, `(user=)`) appears in `CI` or `WF` text OUTSIDE of `scripts/redact-psql-stderr.sed`
lines" (an inline-survivor scan), AND "every psql invocation whose combined output is captured to
a file (`> ".../[a-z._-]+" 2>&1` shape) is followed, before any `cat`/`echo` of that file, by an
invocation of the shared redaction script" (an unredacted-echo scan, closing the third leak
shape). `calibrate()` proves each by inserting exactly that violation into a mutated copy of `CI`
or `WF` and asserting the predicate flips from true (clean) to false (caught) — this is what
"FAILS on a NEW unredirected/unredacted site" requires structurally, not a count assertion.

### Pattern 4: Extending `arm_redaction_subject()` / arm 14 for the shared definition (Area 2 calibration)

**What exists (`scripts/restore-test-from-baseline.sh`, `--self-test` harness):** `run_arm()`
captures every arm's output to a file and runs a redaction check over it BEFORE deciding
pass/fail — protecting the *self-test harness's own log*, not the production artifact:
```bash
local leaked=0
if grep -aqE 'postgres(ql)?://' "$out" || grep -aqE '\$[A-Za-z_0-9]*\$' "$out"; then leaked=1; fi
```
Arm 14 (`arm_redaction_subject()`) builds a **scratch copy** of the script with a deliberately
injected leak (`echo "$RESTORE_DB_URL"` spliced in via `awk`, anchored on a stable text needle,
asserted present before use) and asserts `run_arm`'s own grep FIRES on it — i.e. it is a
self-test's self-test: "the redaction check has a SUBJECT."

**This is a DIFFERENT mechanism from the production `sed -E` redaction blocks** in the two
workflow YAML files — it only guards the harness's own stdout/stderr capture during
`--self-test`, using a narrower 2-pattern grep (raw DSN shape, dollar-quoted SQL) that does not
include the `server at "…"` / `for user "…"` / DNS-hostname shapes at all.

**Extend, per the locked decision, rather than invent a second harness:** add a new arm (e.g.
`arm_redaction_subject_connfail`) whose scratch copy deliberately emits a *connect-failure-shaped*
string (e.g. echoing a synthetic `could not translate host name "…"` line — never a real value)
instead of a raw DSN, and extend `run_arm`'s leak grep (or add a second, named check reusing the
production `scripts/redact-psql-stderr.sed` expressions) so the calibration proves the SAME shared
definition that redacts production output also catches this shape in the self-test harness. This
keeps calibration and production redaction anchored to one definition rather than two
independently-drifting regex sets.

### Pattern 5: Deriving the channel allowlist from producer source text (Area 4 / SC-3)

**Current mechanism** (`.github/workflows/test-restore-from-baseline.yml`, staging step):
```bash
for c in census.err ledger.err marker.err refdata.err dump.log transaction.out; do
  if [ -f "${outdir}/${c}" ]; then
    cp -p "${outdir}/${c}" "${stage}/"
  fi
done
```
This list is hand-typed and duplicated in a prose comment above it. It agrees with the two
producers TODAY (verified this session — `restore-test-from-baseline.sh` writes `census.err`,
`marker.err`, `refdata.err`, `transaction.out` to `$RESTORE_OUT_DIR/*`; the workflow's own steps
write `ledger.err` and `dump.log` directly to `${outdir}/*`; `RESTORE_OUT_DIR` is exported as
`"${RUNNER_TEMP}/test-backup"` — the SAME path as `outdir` — at the point the script is invoked),
but nothing enforces that agreement going forward.

**Recommended derivation mechanism, staying default-DENY:** add a step (or inline block within the
staging step, since both source files are already checked out on the runner) that:
1. Greps `scripts/restore-test-from-baseline.sh`'s own text for its declared write targets
   (`$RESTORE_OUT_DIR/<name>.(err|log|out)` shape) → the script's writer set.
2. Greps the WORKFLOW's own text (`.github/workflows/test-restore-from-baseline.yml`, its own
   file, read from the checked-out repo) for `${outdir}/<name>.(err|log|out)` write-target shapes
   in its OTHER `run:` steps → the workflow's writer set.
3. Unions both sets, sorts, and uses THAT as the `for c in …` list — computed at run start, not
   hand-typed.

This satisfies "a newly written channel reaches the artifact with no list edited" (a new
`$RESTORE_OUT_DIR/foo.err` write in the script is picked up automatically) while staying
default-DENY (an **undeclared** stray file that happens to land in `${outdir}` — e.g., a debug
artifact — is never in either producer's declared-write-target text, so it is never enumerated and
never staged; the mechanism scans SOURCE for declared intent, not the runtime directory by glob).
**⛔ Do not glob `${outdir}/*.err` at runtime** — that is exactly the `[164.8.2-REFUSAL-STILL-
PUBLISHES]`-class mistake the locked decision names as closed and forbidden to reopen.

**Test this by** committing a scratch/mutated copy of the script or workflow with one new declared
write target and no corresponding edit to the (now-derived, not hand-typed) staging list, and
asserting the channel appears in the derivation's output — the `calibrate()` idiom applies here
too, at the derivation-logic level rather than the workflow-execution level (a pure-text-scan unit

### Pattern 6: The `HAS_LIVE_DB` inheritance guard (Area 3 / SC-2)

**What exists (`src/lib/test-helpers/live-db.ts`):**
```typescript
export const LIVE_DB_URL = process.env.NEXT_PUBLIC_SUPABASE_URL;
export const LIVE_DB_SERVICE_ROLE_KEY = process.env.SUPABASE_SERVICE_ROLE_KEY;
export const HAS_LIVE_DB = Boolean(LIVE_DB_URL && LIVE_DB_SERVICE_ROLE_KEY);
```

This is a **module-load-time** snapshot of `process.env` — it becomes `true` the instant those two
vars are present in the environment, regardless of WHY they are present.

**Where the bootstrap already captures env at the right moment** (`src/test-setup.ts`, module
scope, i.e. inside `setupFiles`, which vitest fully awaits before any test module imports):
```typescript
const INHERITED_ENV: NodeJS.ProcessEnv = { ...process.env };
```
This line runs before any test file's imports execute — the same point `HAS_LIVE_DB` is first
evaluated (since `live-db.ts` is itself imported by test files, its module-scope const runs on
first import, which for any live-DB test is after `test-setup.ts` has already run per vitest's
`setupFiles` ordering).

**How CI legitimately sets these two vars, verified this session (`ci.yml`):** the `frontend-test`
job deliberately sets PLACEHOLDER values (`https://placeholder.supabase.co` /
`placeholder_service_role`) with an explicit comment "DO NOT add NEXT_PUBLIC_SUPABASE_URL /
SUPABASE_SERVICE_ROLE_KEY env to this job" nearby — i.e. CI's OWN workflow `env:` blocks are the
only place these vars should carry a value in a job that is not intentionally live-DB. Jobs that
ARE meant to run live-DB tests set REAL values via `secrets.TEST_SUPABASE_URL` /
`secrets.TEST_SUPABASE_SERVICE_ROLE_KEY` explicitly in their own `env:` block. **In neither case
does CI load a dotenv file** — GitHub Actions has no dotenv auto-load step; the leak is
LOCAL-invocation-only (bun's dotenv auto-load inside `gstack-evidence`'s wrapper).

**Recommended guard shape** (repo-side, in `src/test-setup.ts`, not in `live-db.ts` — the module
that OWNS the skip gate must stay untouched per the locked decision):
- Add an explicit, single, narrowly-scoped sentinel env var that ONLY an intentional live-DB test
  invocation sets (e.g. `VITEST_LIVE_DB_INTENDED=1`, set by a new/existing intentional-run
  invocation path — check for one before inventing it; `[ASSUMED — no existing sentinel of this
  shape was found in this session's search of package.json's test scripts; a planner should
  re-confirm no such marker already exists under a different name before adding one]`).
- In `test-setup.ts`, at module scope (same point `INHERITED_ENV` is captured): if `HAS_LIVE_DB`
  is `true` AND `process.env.CI !== 'true'` AND the sentinel is absent, **throw** (fail loud,
  before any test runs) rather than let the suite proceed silently against shared TEST.
- This does not touch `it.skipIf(!HAS_LIVE_DB)` anywhere (49 files reference `HAS_LIVE_DB`,
  unmodified) and does not touch `HAS_LIVE_DB`'s own definition — it adds a NEW check at the one
  point every suite passes through before any test executes.
- **Provenance distinction, answered directly:** a repo-side guard CANNOT reliably distinguish
  "this env var's value came from a dotenv file bun auto-loaded" from "this env var's value was
  genuinely exported by the operator's shell" by inspecting `process.env` alone — `process.env`
  carries no provenance metadata. The sentinel-var approach sidesteps this by not trying to
  detect PROVENANCE at all; it requires explicit INTENT instead, which a dotenv auto-load can
  never accidentally satisfy (a `.env.local` file would have to ALSO define the sentinel var,
  which is a much narrower coincidence than merely defining two commonly-present Supabase vars).
  `[ASSUMED — this design reasoning was not cross-checked against gstack-evidence's actual

## Common Pitfalls

### Pitfall 1: Copying the "activity-gate" block as "the correct form"
**What goes wrong:** CONTEXT.md's Reusable Assets section calls the activity-gate's 4-expression
block "the correct target form." Copying it as the new shared definition would ship a redaction
still missing `host=` and `user=` masking (present in the dry-run-push and `id:redact` blocks but
absent from the activity-gate block).
**Why it happens:** The activity-gate block is the only one with the DNS-hostname expression, which
makes it look complete when only compared on that one axis.
**How to avoid:** Build the shared `.sed` file as the UNION of all 6 distinct expressions found
across all 8 measured sites (see Pattern 2), not a copy of any single existing block.
**Warning signs:** A new redaction test that passes on the DNS-hostname fixture but has no fixture
for `host=`/`user=` masking.

### Pitfall 2: Asserting a specific count (12, 8, or any number) in the new gate
**What goes wrong:** A test asserting "exactly N redaction blocks exist" is a count-pinning arm —
explicitly named as the "widened count over an unwidened scan" overclaim success criterion 9 (of
the original, now-mostly-dropped list) forbids, and it also directly contradicts SC-1's own text
("not assert today's count of 12").
**Why it happens:** Counting is the easiest thing to assert and the temptation is strong once a
specific number has been measured (whether 8 or 12).
**How to avoid:** Assert the STRUCTURAL invariant only — "no inline redaction expression survives
outside the shared definition" / "every captured-output echo passes through the shared
definition first" — proven via `calibrate()`'s mutation-flip, never via a literal count comparison.
**Warning signs:** A test with a magic number like `expect(blockCount).toBe(8)`.

### Pitfall 3: `grep` going silently blind on `src/lib/wizardErrors.test.ts`
**What goes wrong:** This repo carries a deliberate NUL byte in that file; plain `grep` (without
`-a`) treats the file as binary and reports "no match" — a false green.
**Why it happens:** Habit — `-a` is easy to omit.
**How to avoid:** Every shell-level grep in this phase's new gates and scripts must use `grep -a`
(or `grep -aE`/`grep -aq` as appropriate), matching the discipline already visible throughout
`test-ledger-drift-check.sh` and `restore-test-from-baseline.sh`.
**Warning signs:** A gate that reads clean immediately after being written, with no RED
calibration ever observed.

### Pitfall 4: Neutering the wrong occurrence, or restoring with `git checkout --`
**What goes wrong:** Anti-vacuity calibration for this phase's gates requires neuter → observe
RED → restore byte-identically. `git checkout --` / `git restore` / `git stash` in a live
neuter-and-restore harness can silently destroy uncommitted work elsewhere in the tree (this
repo's own recorded pitfall class).
**Why it happens:** `git checkout --` is the reflexive "undo my edit" command.
**How to avoid:** `cp` byte backups before every edit, re-taken after every edit, verified with
`cmp` before proceeding to the next mutation.
**Warning signs:** Any restore step in a plan that does not name `cmp` as its verification.

### Pitfall 5: Publishing a specimen while proving a redaction works
**What goes wrong:** A calibration or a RESEARCH/PLAN document that quotes the REAL TEST pooler
host, IP, DB user, or a real connection string — even as a "before" example — publishes exactly
what the redaction is supposed to prevent, in the one place (a tracked, public-repo `.md` file)
that has no redaction step at all.
**Why it happens:** It is natural to want to show a concrete "before/after" example when writing
up a fix.
**How to avoid:** Use synthetic placeholders only (`<host>`, `<ip>`, `<user>`, `example.invalid`),
matching `test-restore-workflow-wiring.test.ts`'s own pattern of assembling a DSN-shaped fixture
string at runtime (`const SCHEME = \`${"postgres"}${"ql://"}\`;`) specifically so the literal
never appears whole in the source.
**Warning signs:** Any real-looking hostname, IP, or 8+ char alphanumeric project-ref string in a
tracked file.

### The `calibrate()` idiom to extend (Area 2 / SC-1)
```typescript
// Source: src/__tests__/test-restore-workflow-wiring.test.ts (verbatim, already in repo)
function calibrate(
  label: string,
  mutate: (s: string) => string,
  predicate: (s: string) => boolean,
  text: string = WF,
): void {
  const mutant = mutate(text);
  expect(mutant, `CALIBRATION ${label}: the mutation produced an identical string, so the twin proves nothing`).not.toBe(text);
  expect(predicate(text), `${label}: the predicate is FALSE on the real file`).toBe(true);
  expect(predicate(mutant), `CALIBRATION ${label}: the predicate did NOT flip on the mutant — it cannot fail, so it is not evidence`).toBe(false);
}
```
