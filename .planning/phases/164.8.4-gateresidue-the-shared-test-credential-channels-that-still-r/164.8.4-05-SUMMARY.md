## Accomplishments

- `scripts/derive-restore-channels.sh` makes the staging step's own comment executable: it scans `scripts/restore-test-from-baseline.sh` and `.github/workflows/test-restore-from-baseline.yml` for their declared write targets into the shared output directory (anchored on the `RESTORE_OUT_DIR` / `outdir` variable names both use), restricts to the three diagnostic extensions (`.err`/`.log`/`.out` — `.sql`/`.ok` targets are gated by a separate scan-verdict path), unions and sorts the result. Over the two real producers this yields exactly the six names the hand-typed list carried — `census.err dump.log ledger.err marker.err refdata.err transaction.out` — clean by coincidence before this plan, by construction after. Default-DENY: an absent/unreadable producer or an empty derivation fails loud with measured per-producer match counts; embeds no known channel name anywhere, comments included (caught and fixed a self-check comment that initially leaked all six names before the first commit).
- The staging step in `test-restore-from-baseline.yml` now computes `derived_channels` once, near the top of the step (before the outdir-exists branch), and its `for c in ${derived_channels}; do` loop iterates that set. A failed or empty derivation denies every channel, prints a named `MEASURE_FAIL`, and sets the same deferred wiring-fault flag the unreadable-`REDACT_OUTCOME` guard already uses — the staged manifest still prints and the reversal recipe still uploads. Used the repo's own `cmd || rc=$?` idiom (not `set +e`/`set -e`) because `set +e` is a token this job's own softening-token gate forbids outright.
- Rewrote the comment block above the staging step and the "WHAT STAYS" enumeration to describe the channels as DERIVED (naming the script) rather than hand-typed, without restating the six names as documentation — a list in a comment is still a second source of truth.
- Added `"[164.8.4-05] the staged channel set is DERIVED from the producers, not hand-typed"` — a pure text-and-process describe block in the wiring test file with three arms: (1) the shipped derivation agrees with an INDEPENDENTLY-written regeneration over the two real producers, asserting non-empty on both sides first so a double-broken scan cannot agree vacuously; (2) SC-3's own calibration — a scratch copy of one producer with one new declared diagnostic target arrives in the derived set with nothing else edited, AND a file present in a scratch output directory but declared by neither producer is absent (the default-DENY half, closing the door on `[164.8.2-REFUSAL-STILL-PUBLISHES]` re-opening); (3) the staging step's extracted script body references the derivation script and holds no literal channel name, calibrated by re-introducing a literal list and observing the predicate flip. No arm asserts a count.

## Decisions Made

See `key-decisions` in frontmatter — summarized: the derivation's write-target scan anchors on the two known output-directory VARIABLE names (`RESTORE_OUT_DIR`, `outdir`) rather than any bash variable at all, because a fully generic scan picked up ~45 unrelated self-test scratch paths and per-job diagnostic files that never land in the staged directory; this is "the existing comment's two greps, made executable" and is a different kind of embedded knowledge than the forbidden six channel names. Both patterns are checked against both producer arguments so the derivation is order-independent. The channel set is computed once, unconditionally, near the top of the staging step (before the outdir-exists branch), matching the plan's "computed once, at the start of the staging step's script" instruction.

**Discretionary scope call, recorded rather than silently decided:** the backup step's `README.txt` heredoc (staged inside the artifact itself, `test-restore-from-baseline.yml` lines ~1279-1415) also names the six channels individually, each with its own one-line description (e.g. "census.err — stderr of the pre-drop catalogue census query"). This is NOT the staging step's own comment block (which I did rewrite) — it is a separate, downstream, human-facing document shipped INSIDE the artifact for whoever downloads it, written by an earlier phase (WR-01), and its per-channel descriptions carry information a generic "see the derivation script" pointer cannot replace. I left it unchanged: Task 2's `<files>` and its `<action>`'s explicit "comment block above it" scoping point at the staging step's own comment, not this heredoc; none of the plan's actual `<verify>` automated commands check it; and editing it is genuine scope expansion beyond SC-3 (the STAGING MECHANISM, which no longer depends on this text in any way). The plan's `<verification>` section's closing bullet ("no comment carries the list") is read here as a compact restatement of the staging-step-comment requirement already satisfied, not a new requirement reaching every heredoc in the file. Flagging this explicitly so a verifier can independently judge it.
