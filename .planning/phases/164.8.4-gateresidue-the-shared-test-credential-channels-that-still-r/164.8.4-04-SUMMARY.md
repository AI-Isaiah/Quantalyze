# Phase 164.8.4 Plan 04: Fail-loud vitest bootstrap guard against inherited live-DB credentials Summary

**A module-scope guard in `src/test-setup.ts` that aborts every vitest run before any test module loads when both live-DB credentials are present without an explicit `VITEST_LIVE_DB_INTENDED=1` sentinel, closing `[164.8.2-EVIDENCE-DOTENV-LEAK]`.**

## Accomplishments

- **Task 1 — the guard itself.** `src/test-setup.ts` now imports `HAS_LIVE_DB` from `src/lib/test-helpers/live-db.ts` (never recomputes the underlying two-variable boolean) and, as the first module-scope statement after the import block, calls `assertLiveDbWasIntended(HAS_LIVE_DB, process.env)`. The function throws unless `process.env.VITEST_LIVE_DB_INTENDED === "1"`, with a named remedy message (`LIVE_DB_INHERITANCE_REMEDY`) that names `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` by name only — never their values — and gives both exits (unset the vars, or set the sentinel). `src/lib/test-helpers/live-db.ts` and all 49 `it.skipIf(!HAS_LIVE_DB)` call sites are byte-unchanged (verified: `git diff --quiet` on the file passes). The in-file comment records why there is no `CI` escape hatch: measured 2026-09-19 that none of the four vitest-invoking `ci.yml` jobs (`frontend-test`, `frontend-coverage`, `frontend-seam-redis`, `frontend-local-stack`) set both live-DB variables near their vitest step; the jobs that DO set both are non-vitest (a Next build, a Playwright e2e run, a `tsx` seed script).
- **Task 2 — both polarities independently falsifiable.** The guard's decision is exported as a pure function, `assertLiveDbWasIntended(hasLiveDb, env)`, so it is drivable from a test without mutating real `process.env` mid-suite. New file `src/test-setup.live-db-guard.test.ts` (following `src/test-setup.leak-canary.test.ts`'s docblock-with-ledger-rows shape) asserts four independently-named legs, each with its own reddening mutation recorded in the docblock: credentials + no sentinel throws naming both variables; credentials + sentinel does not throw; a partial environment does not throw; and the thrown message contains neither credential value (only the key names) — using synthetic placeholder values (`https://example-project-ref.supabase.co`, `synthetic-service-role-key`) assembled at runtime, never a real host or key.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Narrowed `assertLiveDbWasIntended`'s `env` parameter type**
- **Found during:** Task 2 (writing the guard test)
- **Issue:** The function was typed `env: NodeJS.ProcessEnv` in Task 1. `NodeJS.ProcessEnv` requires `NODE_ENV` and the rest of the ambient process-env shape, so every test-constructed environment object in Task 2 failed `tsc --noEmit` with "Property 'NODE_ENV' is missing" even though the function never reads that property.
- **Fix:** Narrowed the parameter to `Record<string, string | undefined>` — the function only ever reads `env.VITEST_LIVE_DB_INTENDED`, and `process.env` (passed at the real call site) is structurally assignable to that type, so the module-scope call site required no change.
- **Files modified:** `src/test-setup.ts`
- **Verification:** `npx tsc --noEmit -p tsconfig.json` clean; both test files green.
- **Committed in:** `7204fb82` (part of Task 2 commit)
