## Medium

### MR-01: a new book whose keys have a balance but no return day yet now reads "held back, did not pass its checks" (USER-FACING)

**File:** `analytics-service/services/job_worker.py:run_derive_allocator_equity_job` (the B2 split, `if not (payload.get("curve") or [])`), together with `src/lib/queries.ts:untrustworthyRebuildReason` (case 5).

**Evidence:**
- A key with fewer than two days of history takes the key-mode short-circuit. It writes a `key_inputs` row with a real anchor and no csv returns: the "<2-day / never-traded idle key" in `allocator_equity_compose.py`.
- `compose_allocator_equity` puts such a key in `anchored_without_returns`, which adds `MISSING_SERIES` and the blocking `DROPPED_KEY`. Reproduced at HEAD:
  ```
  compose_allocator_equity({}, {'k1': []}, {'k1': 1000.0}, {})
  -> curve [] , degrade_reasons ['d3_missing_series','dropped_key','no_anchored_keys'], is_trustworthy False
  refusal_payload('compose_empty_blocked', extra_reasons=blocking_degrade_tokens(...))['degrade_reasons']
  -> ['compose_empty_blocked', 'dropped_key']
  ```
- F1b does not catch this case, because the key is in `key_inputs_ids`. The compose comes back empty and untrustworthy, so the B2 split persists `compose_empty_blocked` + `dropped_key`. The reader maps that to `derivation_rejected`, class `held_back`. The Overview then shows:
  - heading: "We are holding back your equity history";
  - line: "The latest rebuild of your history did not pass its checks, so it is not shown."
- Before this phase the row was deleted, so the reader said `awaiting_derivation`: "Your equity history is being rebuilt … recomputed … once a day". For this state that line is true: the key gains a return day on the next daily derive and the book composes.
- This hits exactly the onboarding population: a single-key book, or a book whose keys are all new, on its first day or two. RESEARCH row 6b ("every key `dropped_key`") was treated as a blocking cause, and this wait shape was not separated from it.
- The same shape inside a NON-empty compose already read `derivation_rejected` before this phase, so this is a regression only on the empty-curve path. That path is the common one for a brand-new book.

**Fix:** In the B2 split, tell this wait apart from a real blocker before choosing the token. Persist `compose_empty`, which maps to `awaiting_derivation`, when both of these hold:
- the compose's only blocking token is `dropped_key`;
- every dropped key is an anchored key with no return rows, meaning its anchor is non-null and the key is absent from `returns_by_key`.

Keep `compose_empty_blocked` for a null-anchor or read-failure key, and for an unanchored key with returns. Add a RED-first derive test (one anchored key with no returns gives `compose_empty`) and a fixture row in `derive_refusal_rows.json`, so the TS reader and the census pin the line. If the planner reads D-04 as forbidding that split, route it to the founder: as shipped, the line is false for a wait.

## Low

### LR-01: the leader may be a key whose refresh job never reaches the Sentry code, so a hold stays Sentry-silent for that book

**File:** `analytics-service/services/equity_reconstruction.py:_fetch_latest_holdings_per_eligible_key` (`job_key_is_leader`, smallest ELIGIBLE id).

**Evidence:** The leader is drawn from every eligible key, failing keys included. There are two cases where its job never gets to the hold or left-out capture:
- **The preflight raises before the fetch.** `_allocator_key_preflight` re-raises when the decrypt or client build fails. For example, `parse_mt5_credentials` refuses a structurally invalid MT5 slot.
- **The job is never enqueued.** On a zero-snapshot book, the refresh fan-out (`20261021120000`, arm 2) does not enqueue a key linked to a strategy. A hold then keeps the book at zero snapshots, so that leader is never enqueued.

The hold still writes its audit row from every other job, so the trace exists. Only the D-01/D-02/D-12 Sentry event is lost. Both triggers are narrow.

**Fix:** Elect the leader among WORKING eligible keys. Every hold reason implies at least one: `never_polled_working`, over-age with a working key, or two working unknown keys. Fall back to the smallest eligible key only for the left-out events. Pin it with a test where the smallest id is a failing key.

### LR-02: refusal rows that are waits now raise a reader Sentry warning and a `console.error` on every load

**File:** `src/lib/queries.ts` (the `allocator_equity_derived` read in `getMyAllocationDashboard`, `derivedPayloadRejection(row.payload)` → `"untrustworthy"`).

**Evidence:**
- Before this phase, a `compose_incomplete` or `compose_empty` book had no row, so the read logged nothing.
- Now the row is "untrustworthy", which brings two signals:
  - `console.error("… row rejected (untrustworthy) …")` on every dashboard load;
  - a `derived_row_rejected` Sentry warning per allocator per 6 h per instance.
- Both fire for states the reader itself names as a wait (`awaiting_derivation`), such as the backfill window. The noise is bounded, and it dilutes the issue that real refusals report into.

**Fix:** In the capture branch, skip both the log level and the capture when `untrustworthyRebuildReason(row.payload) === "awaiting_derivation"`. Log at `warn` instead, as the `not_version_2` branch does.

### LR-03: the SC-6 refresh hold has no Deribit exemption, although Deribit adds $0 to the refresh total

**File:** `analytics-service/services/equity_reconstruction.py:_fetch_latest_holdings_per_eligible_key` (`pending_venues = identity_pending_venues(key_rows, VENUES_WITH_ACCOUNT_ID)`).

**Evidence:**
- `VENUES_WITH_ACCOUNT_ID` includes `deribit`.
- The D-13 exemptions for never-polled and over-age accounts rest on the fact that "Deribit rows add $0 to the refresh total". The breakdown loop skips `venue == 'deribit'` rows.
- Two unstamped, working Deribit keys therefore hold the whole book's legacy snapshot, although they cannot double-count anything in it.
- It is transient, because the Deribit stamper reads `info.id` after the first successful poll. The derive half of SC-6 is correct to include Deribit, because Deribit returns do enter the derive.

**Fix:** In the refresh only, pass `VENUES_WITH_ACCOUNT_ID - {"deribit"}` to `identity_pending_venues`, with a comment tying it to D-13. Add a test for two unstamped working Deribit keys and no hold. D-03's wording names `VENUES_WITH_ACCOUNT_ID`, so record the narrowing as a technical choice.

### LR-04: the SC-7 count field is lost on the empty-compose path, while the Sentry event still fires

**File:** `analytics-service/services/job_worker.py:run_derive_allocator_equity_job` (`if departed_unavailable_counts:`, placed before the B2 check).

**Evidence:** `payload["inputs"].update(departed_unavailable_counts)` runs and the Sentry event fires. Then the B2 branch persists `refusal_payload(...)`, whose `inputs` is `{n_keys, anchor_asof, composed_at}`. The `departed_history_unavailable_*_keys` counts are dropped, so the stored row and Sentry disagree.

**Fix:** Pass the counts through to `refusal_payload`, for example with an `inputs_extra` argument. Alternatively, move the SC-7 block after the B2 branch and run it on both outcomes.

### LR-05: SC-3 counts as disagreement a flow the newer member lists before the oldest member's first return day

**File:** `analytics-service/services/allocator_equity_derive.py:stitch_flow_disagreement_days` / `_stitch_owned_window`.

**Evidence:**
- Member 0's window is `(None, firsts[1])`, so it "owns" every day before its own first return day.
- Suppose the newer key's crawl reaches further back than the older key's, for example because the older key was reconstructed with a smaller depth. Every flow the newer key lists on those pre-window days then counts as a disagreement, since the older key lists nothing there. The result is the blocking `shared_account_flows_disagree`, which reads as "history not shown".
- The stitch itself drops those flows either way, so this is a stricter flag than the D-03 wording requires ("a day the older member owns"). It could block a healthy book permanently.

**Fix:** Compare only days at or after `firsts[0]` for member 0. Or treat a later member's listing on a day before the owner's first return day as out of window. Pin it with a test.

### LR-06: two unstamped working keys hold the refresh with no escape when the stamper can never read an id

**File:** `analytics-service/services/equity_reconstruction.py:_refresh_hold_reason` (`identity_pending`).

**Evidence:**
- If the stamper returns no id for a key, for example a Bybit UTA parse miss (HISTORYREADER item 3), two such working keys hold every day's snapshot indefinitely.
- D-01 and D-12 were built so that "a dead key never freezes the owner's snapshot store", but SC-6 has no equivalent valve.
- This follows D-03's literal wording ("until the stamper groups them"), so it is LOW here. It is worth a sentence in the HISTORYREADER handoff, which owns the parse miss.

**Fix:** None in this phase beyond recording it. HISTORYREADER's item 3 fix (group the key, or flag the miss) is the release.
