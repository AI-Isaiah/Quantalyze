## MEDIUM

### M-1 Leader-only Sentry event depends on one job that can die before the hold (data-integrity visibility)
- File: `analytics-service/services/equity_reconstruction.py`, `_fetch_latest_holdings_per_eligible_key` (`job_key_is_leader`) and `run_refresh_allocator_equity_daily_job` (hold branch).
- Evidence: the leader is the smallest id among ALL eligible keys (`eligible_ids[0]`), which includes failing (`sign_in_failed`/`error`) keys, Deribit keys and strategy-linked keys. The Sentry event is raised only `if latest.job_key_is_leader`, after `_allocator_key_preflight`. That preflight (`job_worker.py` `_allocator_key_preflight`) returns a circuit-breaker DEFERRED before the handler body, and re-raises a credential decrypt or client-build failure (FAILED job, `refresh_failed` audit, no hold audit, no Sentry). A failing key is exactly the kind whose preflight fails. When the leader job dies or defers, every other job still writes a `refresh_held` audit row, but nothing reaches Sentry, so the hold the phase exists to make loud is audit-only. The same dependency covers both left-out events (`left_out_never_polled_failing`, `left_out_carry_over_age_failing`).
- Hidden failures: breaker cooldown from a strategy-side 429 on the leader's exchange (contagion is accepted by design), bad KEK/decrypt on one key, ccxt construct error, a key flipped to revoked between fan-out and run.
- Fix: do not tie the event to a fixed key. Either (a) elect among keys that can run (working, non-Deribit, active), or better (b) make the event idempotent per (allocator, day, outcome): the first job to write its `refresh_held` audit row that finds no earlier `refresh_held` row for the allocator today raises the event (one extra read, still one event per hold). Add a test where the smallest-id job is FAILED at preflight and another job's hold still raises exactly one event.

### M-2 "Left out" Sentry events never fire on the paths where the book has no day written (data-integrity visibility)
- File: `equity_reconstruction.py`, `run_refresh_allocator_equity_daily_job`.
- Evidence: the `left_out_*` loop sits after `persist_equity_snapshots`. The `no_holdings_today` early return (`not breakdown and not book_emptied`) and the `refresh_held_for_reconstruct` return come first and emit only the audit. A book whose every eligible account is a never-polled-failing or over-age-failing account (the D-01/D-12 "left out, with a Sentry event" case) has `holdings == []`, takes `no_holdings_today`, writes no snapshot at all, and raises no event. That is the worst case of "left out": the whole day is missing and the only trace is an audit row. The counts are in `_refresh_audit_counts`, but D-01/D-12 promise a Sentry event.
- Fix: raise the left-out events (via the M-1 mechanism) before the `no_holdings_today` and `refresh_held_for_reconstruct` returns, or move the loop up beside the hold decision so it runs for every non-held outcome. Add a test with an all-failing book that asserts the event.

### M-3 `identity_pending` hold counts Deribit keys although the refresh sums Deribit as $0, and the hold has no bound (data-integrity, user-facing)
- Files: `analytics-service/services/allocator_equity_derive.py` `identity_pending_venues`; `equity_reconstruction.py` `_refresh_hold_reason`.
- Evidence: `VENUES_WITH_ACCOUNT_ID` is `{okx, bybit, binance, deribit}`. The refresh skips `venue == deribit` rows when summing (`equity_reconstruction.py` ~L4399) and the same function exempts Deribit-only accounts from the never-polled and over-age holds. `identity_pending_venues` has no such exemption, so two unstamped WORKING Deribit keys (PROD has Deribit keys that never write rows) hold the legacy snapshot write, though they cannot double-count anything in that total. Nothing in the hold ages out or escalates: if the stamper never reads the ids (venue schema drift, the case its own ERROR path describes), the allocator's `allocator_equity_snapshots` stops for good, with one audit row and one Sentry warning a day, and first-writer-wins means the missed days stay missing for `/compare` and the dashboard per-holding returns. D-03 asks for the hold "until the stamper groups them", which assumes the stamper succeeds.
- Hidden failures: unstamped pair on Deribit, or any venue whose stamper is failing.
- Fix: for the refresh, count only candidates that contribute to the refresh total (pass a `stamping_venues` set minus `deribit`, or filter in `_fetch_latest_holdings_per_eligible_key`), keeping the derive's call unchanged. Add a bound: after N days of the same `identity_pending` hold (read `refresh_held` audit rows), escalate to an ERROR-level Sentry event so a stuck stamper is not a daily warning. Add a test: two unstamped working Deribit keys do not hold the refresh.

## LOW

### L-1 Refusal row drops the SC-7 departed counts
`job_worker.py` writes `departed_unavailable_counts` into `payload["inputs"]` only on the non-empty compose. On the empty-compose branch `_persist_refusal` stores a fixed `inputs` object, so the count is lost. The Sentry event still fires (it sits before the empty branch), so this is only a readability gap. Fix: pass the counts into `refusal_payload(..., inputs_extra=...)` or accept and document it.

### L-2 `polled_no_rows` is "any `sync_completed` event ever" (equity_reconstruction.py `_sel_polled`)
An account with one old completed poll and no rows is neither held, carried, nor counted by any Sentry path, and the 7-day cap cannot see it because the cap needs rows. In practice a later successful poll writes rows, so this is an edge case, but a persist failure after a completed poll (`allocator.holdings.persist_failed`) leaves exactly that shape. Fix: bound the event by age (for example within `CARRY_AGE_CAP_DAYS`), or exclude accounts whose newest `persist_failed` is newer than the newest `sync_completed`.

### L-3 SC-6 detects "two unknown working keys", not "one unknown key beside a stamped sibling"
`identity_pending_venues` needs two unstamped keys on a venue. One unstamped working key on a venue that already has a stamped key can read that same account and be counted twice. The reader holds the Overview for any unstamped eligible ccxt key (`identityStillPending`), so the curve is covered. The refresh writer is not, and first-writer-wins fixes the double-count for that day. This matches D-03's wording, so it is recorded, not a defect against the decision. Consider a founder call.

### L-4 SC-3 reads silence as agreement
`stitch_flow_disagreement_days` ignores a later member that lists nothing on a day the owner lists flows. A newer crawl that reaches back over the owner's window but misses a withdrawal the owner lists is indistinguishable from one that does not reach back. Accepted in the docstring (assumption A1); recorded here because the fix would be a coverage test (does the later member's listed range cover the day?) rather than a sum compare.

### L-5 Reader noise from benign refusal rows
`derivedPayloadRejection` returns `untrustworthy` for the `compose_empty` row (which is a wait, not a fault). `getMyAllocationDashboard` then runs `console.error` on every load and a Sentry warning once per (allocator, rejection) window, for every allocator whose compose is empty. Before this phase that state was "no row" and silent. Not a silent failure, but a real signal can drown in it. Fix: log `compose_empty`/`compose_incomplete` waits at `console.warn` and skip the capture, the way `not_version_2` is handled.

### L-6 Tests that cannot distinguish what they claim
- `test_refresh_allocator_equity_carry_forward.py` `_sentry_calls`/`_tags` merge `set_tag` calls from one shared mock scope, so with two events in a run the tags of one cannot be told from the other's. The single-event tests are fine; a test with two events would pass on wrong tags.
- `writer_residual_resolution.json` has cells for SC-2 and SC-6 only. SC-3 (`shared_account_flows_disagree`) has no cross-runtime cell, and the "covers every derive-side token" test asserts only two tokens.
- No test covers M-1 (leader job fails or defers) or M-2 (Sentry on `no_holdings_today`).
- `capture_message.call_count == 0` assertions in the no-hold cases are only meaningful because the default job key is the leader; they would pass vacuously if the leader flag were broken. Pair them with a positive control (the same fixture with one more failing key raises one event).
