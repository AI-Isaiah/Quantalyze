## Warnings (MEDIUM)

### MR-FR-01: a new book that also has a dust, native-unit or native-unpriced key still reads "held back" (MR-01 only partly fixed)

**File:** `analytics-service/services/job_worker.py:run_derive_allocator_equity_job` (B2 split, the `all(a is not None and k not in returns_by_key for k, a in anchors_by_key.items())` clause)
**Class:** user-facing. **Introduced by this round:** no. It is a residual of MR-01 that this round left in place.

**Evidence:** The clause needs EVERY key in `anchors_by_key` to have a non-null anchor. The compose drops some null-anchor keys silently or by name, with no `DROPPED_KEY` from them:
- `dust`;
- `native_unit` and `native_unpriced` (`allocator_equity_compose.py`: the `null_anchor_without_returns` dust `continue`, and `omitted_by_name`).

Such a key is in `anchors_by_key` with `None`, so `all()` is False. The book then persists `compose_empty_blocked` + `dropped_key` even though its only blocking cause is the brand-new anchored key. Reproduced at the fix head with the project venv:

```
compose_allocator_equity({}, {k: [] ...}, {'k1': 1000.0, 'k2': None}, {'k2': 'dust'})
  -> curve [], degrade_reasons ['d3_missing_series','dropped_key','no_anchored_keys'], blocking ['dropped_key']
same with {'k2': 'native_unit'} -> identical
```

So this book reads "We are holding back your equity history … did not pass its checks" on its first days. The cases are a new funded key next to an empty sub-account key, or next to a BTC-unit MT5 key. That is the same onboarding regression MR-01 describes, for a subset of the same population. MR-01's own fix text says to keep `compose_empty_blocked` for "a null-anchor or read-failure key". That means a key the compose DROPPED, not a key it omits.

**Fix (minimal, same clause):** skip the keys the compose omits without a drop:
```python
and all(
    k not in returns_by_key
    and (a is not None or null_anchor_reasons.get(k) in ("dust", "native_unit", "native_unpriced"))
    for k, a in anchors_by_key.items()
)
```
At least one anchored key must remain, or there is no `dropped_key`. Add one parametrized refusal case (new anchored key + `dust` key -> `compose_empty`).

### MR-FR-02: a book whose only keys never trade now reads "being rebuilt … once a day" permanently

**File:** `analytics-service/services/job_worker.py:run_derive_allocator_equity_job` (same clause); the source of the state is `run_derive_broker_dailies_job`'s key-mode `int(returns.notna().sum()) < 2` short-circuit (`job_worker.py`, "Brand-new / inactive account").
**Class:** user-facing. **Introduced by this round:** yes, by the condition MR-01 prescribed. Before this phase the row was deleted and read `awaiting_derivation`, so this round brings that pre-phase line back for this population.

**Evidence:** The condition treats "anchored, no return rows" as "brand new, the next derive adds a day". The short-circuit that produces that state also fires for a funded key with fewer than two interpretable return days that will never get more:
- a key with no realized or funding activity (a hold-only account);
- the empty-deal-history case the same block documents.

For such a key every daily derive writes the same anchored `key_inputs` row and no csv returns, and nothing ends the state. The book then persists `compose_empty` every day. The reader maps it to `awaiting_derivation`: "Your equity history is being rebuilt … recomputed … once a day". That line promises progress that never comes. The previous `compose_empty_blocked` line was not accurate either, but it did not promise a rebuild. The condition cannot tell the two apart, because the per-key derive stores no "insufficient history since" marker.

**Fix:** this is a founder call, not a code fix inside the minimal-fix rule. Either accept and record it as a known limit of the MR-01 split, or bound it with data the derive already has. One option is to treat the anchored no-returns key as a wait only while it is younger than N days. The key's `created_at` is on `key_rows`, so this needs no new column. Record the decision in the phase's CONTEXT and ROADMAP entries.

## Round 2 re-review (e72caff18)

**Scope:** `git show e72caff18` only (`analytics-service/services/job_worker.py:run_derive_allocator_equity_job` B2 split, plus two parametrized refusal cases in `analytics-service/tests/test_derive_allocator_equity_job.py`). MR-FR-02 is a founder call and out of scope.
**Result:** 1 MEDIUM. 0 CRITICAL, 0 HIGH. MR-FR-01 is fixed for omitted keys with no return rows. It is not fixed for `native_unit` / `native_unpriced` keys that have return rows.

### What was checked and holds

- **Reason strings match the writer.** `dust`, `native_unit` and `native_unpriced` are the exact tokens the key-mode epilogue stamps (`job_worker.py`, the `_anchor_null_reason` ladder). They also match the malformed-native path in the key_inputs loop, which sets `native_unpriced`, and the compose constants `_NATIVE_UNIT_REASON` / `_NATIVE_UNPRICED_REASON` plus the literal `"dust"` in `allocator_equity_compose.py:compose_allocator_equity`. The clause reads the same `null_anchor_reasons` dict the compose receives.
- **Every such key without returns is omitted with no `DROPPED_KEY`.** `native_unit` / `native_unpriced` with a NULL anchor go into `omitted_by_name`. That set is excluded from both `unanchored_return_keys` and `null_anchor_without_returns`. A `dust` NULL-anchor key with no returns hits the `continue` in the fourth bucket. A `dust` key WITH returns lands in `unanchored_return_keys`, which raises `DROPPED_KEY`, and the clause correctly rejects it on `k not in returns_by_key`.
- **The widening does not turn a real blocker into a wait.** When `all(...)` passes, the only `DROPPED_KEY` source left in the compose is `anchored_without_returns`:
  - `unanchored_return_keys` needs a key in `returns_by_key`. Every such key is in `anchors_by_key` because of the `anchors_by_key.setdefault(k, None)` loop, so `all` fails on it.
  - A non-dust, non-omitted NULL key fails the reason test.
  - A no-capital `fell_back` candidate needs `last_return_day`, so it is in `returns_by_key`.
  - A job-level blocking `degrade_reasons` entry makes `_blocking != [dropped_key]`.
  - The no-capital re-compose path reads the mutated maps. The mutated keys all carry returns, so `all` fails either way.
  - A book whose only keys are omitted ones raises no `DROPPED_KEY` at all, so the clause cannot match it.
- **The new tests bite.** In a throwaway worktree, with `job_worker.py` reverted to `e72caff18^`, `compose_empty_new_book_beside_dust` and `compose_empty_new_book_beside_native_unit` both FAIL. With the fix in place the file passes 143/143.

### MR-R2-01 (MEDIUM): a new book beside a `native_unit` / `native_unpriced` key that HAS return rows still persists `compose_empty_blocked`

**File:** `analytics-service/services/job_worker.py:run_derive_allocator_equity_job` (the B2 `all(...)` clause)
**Class:** user-facing. **Introduced by this commit:** no. It is the part of MR-FR-01 this commit leaves unfixed, not a regression. The clause it replaced failed this case too.

**Evidence:** The compose omits a NULL-anchor `native_unit` / `native_unpriced` key by name whether or not it has returns. `unanchored_return_keys` excludes `omitted_by_name`, and the compose docstring expects a native key to have a series ("e.g. one written before the key-mode skip existed"). The new clause still requires `k not in returns_by_key` for every key, the omitted ones included. Both cases are reachable:
- `native_unpriced` with returns: a priced BTC key whose live close is missing, when the T1 path does not re-anchor it (stored terminal not on `priced_through`), or the malformed-native path, which nulls the anchor but leaves the csv returns.
- `native_unit` with returns: legacy rows written before the skip.

Measured in a throwaway worktree with a probe: key-A anchored at 50000 with no returns, and key-Z NULL with reason `native_unit` (or `native_unpriced`) and four csv return rows. Both reasons persisted `refusal: compose_empty_blocked` with `degrade_reasons: [compose_empty_blocked, dropped_key]`. The compose's only blocking cause is the new key-A, so this is the same wait MR-FR-01 describes, labelled as blocked until key-A's first return day.

**Fix (minimal, same clause):** only `dust` needs the no-returns test. The compose already drops a dust key that has returns.
```python
all(
    (a is not None and k not in returns_by_key)
    or (a is None and null_anchor_reasons.get(k) in ("native_unit", "native_unpriced"))
    or (a is None and k not in returns_by_key and null_anchor_reasons.get(k) == "dust")
    for k, a in anchors_by_key.items()
)
```
Pass `csv_daily_returns` rows for `key-Z` in `_new_book_beside_omitted_key` for the native reasons, so the case covers a key with returns.
