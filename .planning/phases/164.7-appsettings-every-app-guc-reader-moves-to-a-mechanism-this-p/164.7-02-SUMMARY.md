# Phase 164.7 Plan 02: analytics_service_* settings and the vault tick — Summary

**The repository now describes the match-engine mechanism production has been running since 2026-09-01 — key from Vault, url from a table an operator can UPDATE, a loud RAISE on either absence — and it describes it in a migration that schedules nothing and in a 7-arm gate every one of whose arms was watched failing before it was allowed to pass.**

## Accomplishments

- **DRIFT-02 is closed for both `analytics_service_*` settings.** The two April migrations wrote a job row that read four settings this platform does not let a migration set; PROD's live row was hand-repaired onto Vault a week ago and the repo never caught up. `20260907120000` now carries the mechanism verbatim: the manifest's own `SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = 'analytics_service_key'` idiom, the manifest's own RAISE text, and the manifest's own URL literal — the last of which moves into `public.system_settings` because it is not a secret and an operator should not need secret-management privileges to change a hostname.
- **The scope fence held and is measured, not asserted.** Zero schedule-registration tokens and zero app-GUC reads in the file, comments included. Repointing the live row stays Phase 164.5 item (7).
- **The RAISEs are proven, not inspected.** Arms V1 and U1 remove the value on a real cluster and call the real function; arm C1 is the discriminator that refuses a callable which raises unconditionally. Without C1, a function whose entire body was one RAISE would pass V1 and U1 and post nothing forever — the CRON-DRIFT-01 outage with the sign reversed.
- **Two planned twins were measured unfalsifiable and replaced with evidence** rather than argued away (below). One of them, the `DROP POLICY <t>_service_all` shape, is a finding about the whole repository, not about this table.
- **A vault stand-in now exists for the pg-lane**, so any future run-time Vault reader's failure paths are provable there.
