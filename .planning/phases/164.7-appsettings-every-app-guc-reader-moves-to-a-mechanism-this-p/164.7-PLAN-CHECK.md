## 3. Plan 02 Task 1's `;` — SOUND, stays as is

Shape: `A && … && rm -rf "$S" && mkdir -p "$S" && printf … && bash run.sh … > "$S/out.log" 2>&1; rc=$?; grep applied && grep OK && test "$rc" = "0" && …`

Why the literal "one `&&` chain" rule does not apply here: the `;` boundary's status is CAPTURED (`rc=$?`) and then ASSERTED (`test "$rc" = "0"`), and every assertion before the `;` participates in that status. Enumerated and demonstrated:

- an assertion fails BEFORE `rm -rf "$S"` → the chain short-circuits, `rc=1`, a stale `out.log` may survive and the two greps PASS — then `test "$rc" = "0"` fails. Measured: greps printed the stale lines, **exit 1**.
- a failure AFTER `rm -rf` → `out.log` absent, greps fail.
- `run.sh` itself fails → `rc≠0`, exit 1 (measured with `exit 3`: no stale read, **exit 1**).
- `rc=0` is only reachable when the whole chain including this run's `run.sh` succeeded, i.e. the log is fresh.

Nothing after the `;` is anything but `&&`. Not vacuous; no edit needed.
