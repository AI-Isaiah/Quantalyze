<decisions>
## Implementation Decisions

### D-01 — `ledger_refresh_enabled` moves to the EXISTING `system_flags`, not a new table

Rationale: a second settings table would be a second answer to a question this repo
answered in April, and Rule 7 (surface conflicts, don't average them) says pick the
one that is more tested. `system_flags` has RLS, an admin route, a fail-closed
consumer and a passing red-team test. A new table would have none of that on day one.

⚠️ **The read must fail CLOSED.** `current_setting(…, TRUE)` cannot raise; a table
read can (missing table, permission denied, connection fault). 161.1's whole design is
fail-closed, and its comment says the guard is "FIRST statement in the body,
deliberately". So the replacement must return 0 (dormant) on ANY failure, not just on
`enabled = false`, and must stay the first statement. Model it on
`send-intro/route.ts:96-102`, which already does exactly this and has the test to prove it.

⚠️ Exact-equality semantics survive: `enabled BOOLEAN NOT NULL` is strictly better than
the string comparison it replaces (the original comment enumerates `'1'`, `'on'`,
`'TRUE'`, `'true '` as things that must NOT open the flag; a boolean column makes that
class unrepresentable rather than merely rejected).

### D-02 — `analytics_service_key` -> Vault (`vault.decrypted_secrets`)

Per ROADMAP. It is a secret, and Vault is the only mechanism PROVEN working on this
project — PROD's jobid 1 was hand-repaired onto it on 2026-09-01.

### D-03 — `analytics_service_url` -> the settings table, NOT Vault

`system_flags.enabled` is `BOOLEAN NOT NULL`, so a TEXT value does not fit it.
Decision: a sibling table (`system_settings(key TEXT PK, value TEXT NOT NULL, …)`)
carrying the SAME RLS shape as `system_flags`, rather than widening `system_flags`
with a nullable `value` column — widening makes every existing row's contract
ambiguous (is this row a flag or a setting?).

**Considered and rejected:** putting the URL in Vault alongside the key, so that one
mechanism serves both. It is genuinely tempting — the two are read side by side at
`:144/:145` and `:45/:46`, so splitting them is more code, not less. Rejected because
it puts a non-secret behind Vault access, meaning an operator changing a URL needs
secret-management privileges. Recorded here so the planner does not re-litigate it.

### D-04 — `app.admin_email` is ANNOTATED, not migrated and not deleted ⚠️ SCOPE AMENDMENT

Criterion 2 offers two dispositions: "either migrated or DELETED with the evidence
that nothing reads it." Measurement says neither is right.

- **Migrating is meaningless.** The block already ran. Pointing it at a new mechanism
  changes the behaviour of code that will never execute again.
- **Deleting is worse.** An applied migration file is the record of what was applied
  to PROD. Editing it so the repo no longer describes the statements that ran trades a
  cosmetic grep win for a lie in the permanent record.

**Disposition: a dated, commented lineage block** — the exact exemption criterion 1
already defines. The evidence that nothing reads it is recorded WITH the annotation.

⛔ This is a THIRD option the criterion does not list, so it is a scope amendment and
must be written into ROADMAP criterion 2, this file, and the SUMMARY — not one of them.
A scope amendment touching one file is incomplete; the refused claim survives in the
others.

### D-05 — the CI gate counts comments, and the lineage block is the only exemption

### C-01 — the `analytics_service_*` sites are TWO different kinds, and the section above got it wrong

`<code_context>` above treats all 8 as if they were live readers, and `<decisions>`
D-02/D-03 speak of re-pointing "the analytics cron function(s)". **There is no
function.** Measured in both files:

| Kind | Sites | What it is | Live? |
|---|---|---|---|
| Preflight | `cron_heartbeat` `:144,:145`; `schedule_match_cron_hourly` `:45,:46` | plain plpgsql inside a one-shot `DO $$` block | **No** — ran once at apply time. `cron_heartbeat:148`'s own NOTICE says "re-run this DO block". |
| Cron command text | `cron_heartbeat` `:167,:170`; `schedule_match_cron_hourly` `:70,:73` | inside a `$cron$ … $cron$` literal passed to `cron.schedule()` | **Yes** — stored verbatim as `cron.job.command` and evaluated at EVERY TICK |

The `$cron$` form is deliberate and commented: *"do NOT bake v_url/v_key into the
body via format(%L, …). Resolve them inside the cron body so the secret never lands
in cron.job.command."* The migration does not execute those two lines; it WRITES them
into a cron row that then executes them hourly forever.

⛔ **This is why the phase must not treat them as dead.** Both GUCs are unsettable
here (42501), so the stored command resolves `url := NULL || '/api/…'` → NULL on every
tick. That IS `CRON-DRIFT-01` — seven days of 401s behind a green cron history. If a
planner annotates `:167/:170` as lineage on the belief that they are one-shot, the
migration keeps writing a broken cron command on every future fresh apply and the
defect is papered over rather than fixed.

⚠️ **`20260408215026` SUPERSEDES `20260408113029`.** Same `jobname`
(`match_engine_cron`), unschedules then reschedules daily → hourly. Only the later
one describes the row that exists. The earlier one is lineage.

**Consequence for the scope fence (unchanged, now better grounded):** 164.7 changes
what the MIGRATION TEXT writes; 164.5 item (7) repairs the LIVE `cron.job` row, which
PROD already had hand-repaired onto Vault on 2026-09-01. 164.7 must not call
`cron.schedule`.

### C-02 — the mutation twins: right mechanism, wrong count, and the breakage is CONDITIONAL

Claim was "22 existing RED-UNDER-M twins (12 fanout / 10 composite) … the new
CREATE OR REPLACE overwrites them, so every one stops biting."

**Measured by parsing the `RED-UNDER-M` JSON objects, not by eyeballing:**

| Gate | Migration it mutates | edit-kind twins |
|---|---|---|
| `test_ledger_refresh_fanout.sql` | `20260825130000_ledger_refresh_fanout_dormant.sql` | **14** |
| `test_ledger_refresh_composite_arm.sql` | `20260825140000_ledger_refresh_composite_arm.sql` | **12** |
| `test_ledger_refresh_composite_arm.sql` | `20260825120000_ledger_refresh_staleness_view.sql` | 2 |

**28 edit-kind twins, not 22.** Of these, exactly **2** target the GUC guard text D-01
rewrites (`find: "IF v_enabled <> 'true' THEN"`, one per gate).

⚠️ **"Every one stops biting" is not automatic — it is conditional on the APPLY LIST.**
A new migration's `CREATE OR REPLACE` does not alter the old migration's text. The
twins mutate the OLD file and the apply list re-applies it. They stop biting only once
the gate's apply list is extended to include the NEW superseding migration, because
then the mutated old body is overwritten before the assertions run. That extension is
unavoidable (the gate must test current behaviour), so the risk is real — but the
planner must reason about the apply list, not about `CREATE OR REPLACE` alone.

**Live floors, read off the symbols in `scripts/mutation-runner/run.mjs` (never from
prose, which drifts):** `FILES_FLOOR = 45`, `ARMS_FLOOR = 369`, `WAIVED_CEILING = 0`.
A silent regression here is a fall from 369, and `WAIVED_CEILING = 0` means it cannot
be absorbed by waiving. Precedent for the fix: `test_sync_status_curated_sentence_survives.sql`
(phase 164.2 plan 07) re-points its twins at the superseding migration; re-point,
re-measure each twin's `occurrences`, and re-prove on the lane.

### C-03 — do NOT copy the `send-intro` flag read wholesale; one of its branches is fail-OPEN

D-01 above cites `send-intro/route.ts:96-102` as the fail-closed model. That citation
is correct for the branch it names — the `flagErr` branch returns 503. But the block
continues:

```ts
if (flagRow && flagRow.enabled === false) { … 503 … }
```

A **missing row** (`flagRow === null`) falls through to ALLOW. That is deliberate and
documented in the comment above it ("Row missing (brand-new project before migration
011) → treat as enabled=true").

⛔ For `ledger_refresh_enabled` that rule is INVERTED: a missing row must mean
**dormant**, not enabled. 161.1's guard is fail-closed by design and its comment calls
the first-statement placement deliberate. Copy the error branch and the
`enabled = false` branch; explicitly reject the missing-row branch, and pin the
rejection with an arm that seeds NO row and asserts the fan-out returns 0.
