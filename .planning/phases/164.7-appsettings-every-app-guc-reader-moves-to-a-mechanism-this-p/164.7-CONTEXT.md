<decisions>
## Implementation Decisions

### D-01 — `ledger_refresh_enabled` moves to the EXISTING `system_flags`, not a new table

Rationale: a second settings table would be a second answer to a question this repo
answered in April, and Rule 7 (surface conflicts, don't average them) says pick the
one that is more tested. `system_flags` has RLS, an admin route, a fail-closed
consumer and a passing red-team test. A new table would have none of that on day one.

⚠️ **The read must fail CLOSED.** `current_setting(…, TRUE)` cannot raise; a table
read can (missing table, permission denied, connection fault). 161.1's whole design is
fail-closed, and its comment says the guard is "FIRST statement in the body,
deliberately". So the replacement must return 0 (dormant) on ANY failure, not just on
`enabled = false`, and must stay the first statement. Model it on
`send-intro/route.ts:96-102`, which already does exactly this and has the test to prove it.

⚠️ Exact-equality semantics survive: `enabled BOOLEAN NOT NULL` is strictly better than
the string comparison it replaces (the original comment enumerates `'1'`, `'on'`,
`'TRUE'`, `'true '` as things that must NOT open the flag; a boolean column makes that
class unrepresentable rather than merely rejected).

### D-02 — `analytics_service_key` -> Vault (`vault.decrypted_secrets`)

Per ROADMAP. It is a secret, and Vault is the only mechanism PROVEN working on this
project — PROD's jobid 1 was hand-repaired onto it on 2026-09-01.

### D-03 — `analytics_service_url` -> the settings table, NOT Vault

`system_flags.enabled` is `BOOLEAN NOT NULL`, so a TEXT value does not fit it.
Decision: a sibling table (`system_settings(key TEXT PK, value TEXT NOT NULL, …)`)
carrying the SAME RLS shape as `system_flags`, rather than widening `system_flags`
with a nullable `value` column — widening makes every existing row's contract
ambiguous (is this row a flag or a setting?).

**Considered and rejected:** putting the URL in Vault alongside the key, so that one
mechanism serves both. It is genuinely tempting — the two are read side by side at
`:144/:145` and `:45/:46`, so splitting them is more code, not less. Rejected because
it puts a non-secret behind Vault access, meaning an operator changing a URL needs
secret-management privileges. Recorded here so the planner does not re-litigate it.

### D-04 — `app.admin_email` is ANNOTATED, not migrated and not deleted ⚠️ SCOPE AMENDMENT

Criterion 2 offers two dispositions: "either migrated or DELETED with the evidence
that nothing reads it." Measurement says neither is right.

- **Migrating is meaningless.** The block already ran. Pointing it at a new mechanism
  changes the behaviour of code that will never execute again.
- **Deleting is worse.** An applied migration file is the record of what was applied
  to PROD. Editing it so the repo no longer describes the statements that ran trades a
  cosmetic grep win for a lie in the permanent record.

**Disposition: a dated, commented lineage block** — the exact exemption criterion 1
already defines. The evidence that nothing reads it is recorded WITH the annotation.

⛔ This is a THIRD option the criterion does not list, so it is a scope amendment and
must be written into ROADMAP criterion 2, this file, and the SUMMARY — not one of them.
A scope amendment touching one file is incomplete; the refused claim survives in the
others.

### D-05 — the CI gate counts comments, and the lineage block is the only exemption

Criterion 1's wording already settles this. Consequence: `cron_heartbeat.sql:113` gets
a lineage block. The gate ships with a RED fixture proving it fires when an
unannotated `current_setting('app.` is reintroduced — a gate that cannot fire is this
milestone's named defect, so the fixture is not optional.

### D-06 — the PROD activation (criteria 3 and 4) is a USER GATE, not an executor step

Criterion 3 requires throwing the 161.1 switch on PROD and observing
`ledger_refresh_staleness.days_since_last_return` go down; criterion 4 requires
observing a flipped switch enqueue 0 on a live tick. Both are production writes.

⚠️ **A production read was already attempted during this discuss and was denied by the

⚠️ Criterion 3's own warning stands: a green `compute_jobs` row is NOT success. Check

### D-07 — three reviewers before any migration applies

migration-reviewer + rls-policy-auditor + silent-failure-hunter, per project rule.
Merging `supabase/migrations/**` to `main` auto-applies to PROD. silent-failure-hunter
is load-bearing here rather than routine: D-01 converts an infallible read into a
fallible one.

This phase writes a genuine forward migration, so its PR is the first real chance for
