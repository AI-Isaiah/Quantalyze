## Open — BLOCKING (severity ≥ `high`)

### T-164.7-08 — Repudiation / absent secret → null header → silent 401s / **high** / mitigate

**Declared mitigation:** *"explicit RAISE on NULL/empty (arms V1/U1); async note points at cron-obs"*.

**What is present:** `20260907120000:324-326` —
`IF v_key IS NULL OR v_key = '' THEN RAISE EXCEPTION 'analytics_service_key missing from vault — refusing to send a null header';`
with executable arm V1 and its twin at `test_analytics_service_settings_and_vault_tick.sql:224-255`.

**Why it is not closed.** Two proven input paths reach the *exact* outcome the threat names — a
non-empty-looking key in the `X-Service-Key` header, a 401 from the analytics service, and an async
`net.http_post` whose return value looks identical either way:

1. **`[VAULTTICK-EMPTYKEY-01]`** — the guard tests `v_key = ''`, not `btrim(v_key) = ''`. A
   whitespace-only secret passes the guard and is posted as the header. Confirmed by execution in
   `164.7-REVIEW.md:60`; booked at `TODOS.md:7769`.
2. **WR-01** — `SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = …`
   (`:321-323`) carries no `STRICT`, no cardinality check. A duplicate secret name (the shape a
   `vault.create_secret` re-run rather than `vault.update_secret` leaves) makes plpgsql take an
   arbitrary row and post the **retired** key. `164.7-REVIEW.md:306-350`; booked at `TODOS.md:7799`.
   The migration header at `:66-73` reasons carefully about the zero-row case and never mentions
   the many-row case.

The guard is present and bites for the NULL case; it does not close the threat. **This is
bit-for-bit the seven-day silent outage `CRON-DRIFT-01` documents and that this function was
written to end.** Owner: Phase **164.8.6 VAULTTICKFIX**.

### T-164.7-07 — Info disclosure / secret in `cron.job.command` or in a RAISE / **high** / mitigate

**Declared mitigation:** *"key read at run time inside the body, never baked; RAISE texts carry no
values; **cron-drift hygiene rules stay in force**"*.

**Clauses 1 and 2 verify.** The key is read at call time (`:321-323`), never baked. No RAISE echoes
a value — `:325`, `:332`, and `:348`, whose reasoning is stated at `:341-346`: *"echoing an
attacker-chosen string there writes their collector's hostname into every downstream reader of this
project's logs."* Arm C3 (`:436-444`) has an executable twin that reddens if the refusal is made to
echo `v_url`.

**Clause 3 is falsified by execution.** `164.7-REVIEW.md:164-221` (CR-03) proves the ten hygiene
rules return **zero** violations on a command inlining a live service key:

- **(b) unfixed at HEAD** — `scripts/prod-prober/arms/cron-drift.mjs:267` still reads
  `singleQuotedLiterals(text, quoteIdx, text.length)[0]`, i.e. only the FIRST literal, and fires at
  `HEADER_LITERAL_MIN = 16` (`:186`). `'sk_live_' || 'AAAABBBBCCCCDDDDEEEE'` presents an
  8-character first literal, and both fragments sit under `HEADERS_LITERAL_MAX = 32` (`:189`) so
  `long-literal-in-headers` misses them too.
- **(c) unfixed at HEAD** — `singleQuotedLiterals` (`:223`) has no dollar-quote awareness, although
  the file's own comment says `cron.job.command` is *"frequently a multi-line `DO $$ … $$` block"*.
  A lone apostrophe inside `$q$don't$q$` desyncs the scanner and flips `long-literal-in-headers`
  from RED to CLEAN.
- **(a) is fixed on this branch only** — `stripSqlComments` is applied to `vault-absent` at `:354`.
  That fix is in commit `84b21cb5` and is **not on `origin/main`**, so on main the comment-satisfies-
  the-grep hole is live as well.

This is the detective control named in the register's own mitigation plan, guarding the one shape
that actually happened on this project. Booked at `TODOS.md:7791` as
`[164.7-CR03-HYGIENE-BYPASS]`. Owner: Phase **164.8.5 PROBERPARSE**.
