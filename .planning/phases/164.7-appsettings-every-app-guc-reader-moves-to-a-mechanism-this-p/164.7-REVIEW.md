## Summary

This is a post-merge AUDIT, not a merge gate. All five files are live on PROD.

The prose in these files is unusually good and the SQL guards are, on the whole, correctly
fail-closed. The defects cluster in one place and they cluster hard: **the gates that are supposed
to prove things are the weakest code in the phase.** `scripts/prod-prober/arms/cron-drift.mjs`
collects six fields per cron row and compares three of them; it reads the CLAUDE.md-mandated
database marker, null-checks it, logs it, and throws it away without ever comparing it to the
marker the oracle records; and its ten-rule secret scanner returns **zero violations** on a command
that inlines a live service key, which I demonstrated by running it. Two of the migrations' own
`DO $verify$` needles are satisfiable by their own error messages.

Five of the six Critical/Warning findings against `cron-drift.mjs` are **proven by execution**, not
argued — the exact probe commands are inlined with each finding so the next reader can re-run them
rather than trust this file.

The five original reviewer findings are confirmed, not re-raised (see the confirmation table). One
of them — `[164.7-VAULT-ABSENT-RULE]` — turns out to have a much worse twin in the *opposite*
direction, which is CR-03 below.

⚠️ **Nothing here is exploitable by an unauthenticated user.** The EXECUTE surface on all three
SECURITY DEFINER functions is correctly closed to `anon` and `authenticated`, and asserted. The
Critical findings are all **detection failures**: controls that cannot fail. Per this project's own
elevation rule ("any assertion, guard or gate that CANNOT FAIL outranks a correctness bug"), that is
the right severity — but the forward-fix grading below says plainly which ones actually justify
touching production.

## Critical Issues

### CR-01: `compareManifest` collects `username`, `database` and `jobid` and compares none of them — a cron job repointed to another execution role is invisible

**File:** `scripts/prod-prober/arms/cron-drift.mjs:576-582` (the `changed` list); collected at `:111`, `:396-404`; recorded in the oracle for all 14 rows.
**Grade:** FORWARD-FIX-NOW (cheap, self-contained, no production write)

`CRON_JOB_SQL` selects seven columns. `parseCronJobRows` parses all seven. `cron-manifest.json`
stores `jobid`, `database` and `username` on **every one of its 14 rows** (measured). And the
comparison is exactly three lines:

```js
if (String(m.schedule ?? "").trim() !== String(p.schedule ?? "").trim()) changed.push("schedule");
if (Boolean(m.active) !== Boolean(p.active)) changed.push("active");
const prodSha = sha256Hex(normalizeCommand(p.command));
if (m.command_sha256 !== prodSha) changed.push("command");
```

`username` is the pg_cron column that decides **which role the command executes as**. A job silently
repointed from `postgres` to a different (or more privileged) role is not drift to this arm. Neither
is a job moved to a different `database`, nor a jobid change. `jobid` is even *printed* at `:574` —
collected, displayed, never tested.

Proven:

```
node --input-type=module -e "import {compareManifest,sha256Hex,normalizeCommand} from './scripts/prod-prober/arms/cron-drift.mjs';
const cmd='select 1 -- vault.decrypted_secrets';
const man={schema_version:1,normalization:'ws-collapse-v1',jobs:[{jobname:'match_engine_cron',schedule:'0 * * * *',active:true,username:'postgres',database:'postgres',command_sha256:sha256Hex(normalizeCommand(cmd)),command:cmd}]};
const prod=[{jobid:'99',jobname:'match_engine_cron',schedule:'0 * * * *',active:true,database:'attacker_db',username:'supabase_admin',command:cmd}];
console.log(compareManifest(man,prod).defects);"
→ []
```

username `postgres` → `supabase_admin`, database changed, jobid 1 → 99: **zero defects.**

**Fix** — in `compareManifest`, beside the three existing tests:

```js
for (const f of ["username", "database"]) {
  if (m[f] === undefined) continue;               // pre-schema-1 rows; see CR-05's fix for the durable answer
  if (String(m[f]).trim() !== String(p[f] ?? "").trim()) changed.push(f);
}
if (m.jobid !== undefined && String(m.jobid) !== String(p.jobid)) changed.push("jobid");
```

and extend the headline the same way `schedule`/`active` already are, so the defect names the old
and new role. Add a `prod-username-changed.json` fixture beside the existing
`prod-active-flipped.json` so the new arm has a red control.

### CR-02: the live database marker is read, null-checked, logged — and never compared to the marker the oracle was captured from

**File:** `scripts/prod-prober/arms/cron-drift.mjs:663-688` (live read) vs `:489-490` and `:591` (manifest's recorded marker)
**Grade:** FORWARD-FIX-NOW

The file's own docstring at `:99-103` states the rule: *"the hand-set `COMMENT ON DATABASE` marker
CLAUDE.md requires before trusting ANY reading against a Supabase project: `current_database()` is
`postgres` on both PROD and TEST and proves nothing."*

What ships implements exactly half of that. `run()` reads the marker into a local at `:677`, refuses
an empty one at `:678`, logs it at `:688` — and the local **dies there**. It is never passed to
`compareManifest`. Meanwhile `compareManifest` reads `manifest.database_marker` at `:490` and
interpolates it into the drift headline at `:591`.

So: point the prober at any database that carries *a* marker, and the arm will compare that
database's `cron.job` against PROD's oracle and stamp every defect line with
`(marker ⛔ PRODUCTION — real customer data. …)` — the marker of a database it did not read.
That is worse than not checking: the report actively asserts a provenance it did not verify.

The null-check is the only thing here that can fail, and it fails on the one case
(`COMMENT ON DATABASE` lost) that is far less likely than the case CLAUDE.md actually warns about
(you are on the wrong project). Grep confirms zero comparisons anywhere:
`grep -rn database_marker scripts/prod-prober/` returns three hits — a self-test string assertion, a
capture-time write, and the headline interpolation.

**Fix** — thread the measured marker into the comparison and make disagreement a `measure-fail`:

```js
// run():
const { defects, lines } = compareManifest(manifest, prodRows, { liveMarker: marker });

// compareManifest(), immediately after the schema/normalization validation:
if (opts.liveMarker !== undefined && manifest.database_marker !== opts.liveMarker) {
  defects.push({ kind: "measure-fail", subject: "database marker",
    detail: `the oracle was captured from a database whose marker reads ${JSON.stringify(manifest.database_marker)}, `
          + `but this reading came from one marked ${JSON.stringify(opts.liveMarker)}. Two different databases were compared; `
          + `no statement about drift can be made from this run.` });
  return { defects, lines };
}
```

### CR-03: the ten hygiene rules return ZERO violations on a command that inlines a live service key — the exact pre-2026-09-01 outage shape

**File:** `scripts/prod-prober/arms/cron-drift.mjs:263-271` (`headerCarriesLiteral`), `:328-333` (`vault-absent`), `:370-379` (`long-literal-in-headers`)
**Grade:** FORWARD-FIX-NOW

Two independent weaknesses compose into a full false GREEN:

1. **`vault-absent` is a substring test over raw command text** (`!text.includes("vault.decrypted_secrets")`),
   so a `--` comment naming the table satisfies it. This is "a grep matching its own comment,"
   the named anti-vacuity shape.
2. **`headerCarriesLiteral` only inspects the FIRST quoted literal** after the header name and only
   fires at `content.length >= 16`. A key split across a `||` concatenation — `'sk_live_' || 'AAAA…'` —
   presents an 8-character first literal. The two fragments are then each below
   `HEADERS_LITERAL_MAX = 32`, so `long-literal-in-headers` misses them too.

Proven — this is the command, and this is the result:

```
node --input-type=module -e "import {hygieneViolations} from './scripts/prod-prober/arms/cron-drift.mjs';
console.log(hygieneViolations('match_engine_cron',
  \"DO \\\$\\\$ BEGIN -- resolves from vault.decrypted_secrets\n perform net.http_post(url:='https://x', headers:=jsonb_build_object('X-Service-Key','sk_live_'||'AAAABBBBCCCCDDDDEEEE')); END \\\$\\\$\"));"
→ []
```

Zero of ten rules fire. The same command with the key un-split fires two
(`x-service-key-literal`, `vault-absent`). The file's own docstring at `:8-12` says this arm exists
because *"PROD `cron.job` jobid 1 carried a hardcoded URL and an INLINE SERVICE KEY in its `command`
text for MONTHS."* The rule set does not catch that key if it is written with a `||` and a comment.

A third, separate bypass in the same parser: **it has no dollar-quote awareness**, and this file's
own comment at `:116-117` says `cron.job.command` is *"frequently a multi-line `DO $$ … $$` block."*
A lone apostrophe inside a `$q$…$q$` literal desyncs `singleQuotedLiterals`:

```
$q$don't$q$  in the headers list → long-literal-in-headers CLEAN
$q$dont$q$   same command        → long-literal-in-headers FIRES
```

**Fix**, three parts, all local to this file:

```js
// (a) vault-absent must test EXECUTABLE text, not raw text.
const stripSqlComments = (t) => String(t).replace(/--[^\n]*/g, "").replace(/\/\*[\s\S]*?\*\//g, "");
if (name === "match_engine_cron" && !stripSqlComments(text).includes("vault.decrypted_secrets")) { … }

// (b) headerCarriesLiteral must consider the whole concatenation chain, not literal [0].
//     Sum the contents of every literal joined by `||` before the next `,` at depth 0,
//     and compare the SUM to HEADER_LITERAL_MIN. A key split into n pieces still sums to a key.

// (c) teach matchingParen / singleQuotedLiterals about $tag$ … $tag$, skipping such a
//     region wholesale. Ship a red fixture row for each of the three shapes above —
//     `hygiene-red.json` currently proves each rule CAN fire, not that it cannot be dodged.
```

⛔ Do not "fix" (b) by lowering `HEADER_LITERAL_MIN`; the docstring at `:256-261` correctly explains
why the threshold exists, and lowering it would fire on the green Vault-backed shape.

### CR-04: a manifest row that omits `active` silently accepts a DISABLED production cron job

**File:** `scripts/prod-prober/arms/cron-drift.mjs:466-482` (oracle row validation) and `:578`
**Grade:** FORWARD-FIX-NOW

The oracle validation is thorough about `jobname`, `command_sha256` and the withhold pair, and says
nothing about `active` or `schedule`. The comparison then does `Boolean(m.active) !== Boolean(p.active)`.
`Boolean(undefined)` is `false`. So a manifest row with no `active` key **agrees** with a PROD job
that has been switched off.

Proven:

```
manifest row omits `active`, PROD job is DISABLED, everything else identical → defects: []
```

That is the failure this whole arm was built for: `CRON-DRIFT-01`, "a PROD cron job 401'd hourly for
seven days behind a green cron history." A deactivated jobid 1 produces no job-run rows at all — even
quieter than a 401 — and this arm would report it clean.

`schedule` fails the other way (`String(undefined ?? "")` is `""`, which mismatches any real cron
expression and reports drift), so only `active` has the silent direction. The committed manifest
carries `active` on all 14 rows today, so this is latent — but it is one hand-edit or one
capture-format change away, and the oracle is a hand-reviewed file by design.

**Fix** — make the oracle validation total over the fields the comparison consumes:

```js
if (typeof row.active !== "boolean") {
  return invalid(`cron manifest row ${row.jobname} has no boolean \`active\`. Boolean(undefined) is false, so an omitted `
               + `flag would silently AGREE with a deactivated PROD job — the quietest form of the outage this arm exists for.`);
}
if (typeof row.schedule !== "string" || row.schedule.trim().length === 0) {
  return invalid(`cron manifest row ${row.jobname} has no schedule.`);
}
```

Apply the same treatment to `username` and `database` when CR-01's fix lands.

### WR-01: the Vault read is not single-row-safe — a duplicate secret name silently selects an arbitrary row

**File:** `supabase/schema/functions/match_engine_cron_tick.sql:29-31`
(= `20260907120000:321-323`)
**Grade:** FORWARD-FIX-LATER — fold into the same forward migration as `[VAULTTICK-EMPTYKEY-01]`

```sql
SELECT decrypted_secret INTO v_key
  FROM vault.decrypted_secrets
 WHERE name = 'analytics_service_key';
```

No `STRICT`, no `LIMIT`, no `ORDER BY`, no count assertion. The migration header at `:66-73` reasons
carefully about the **zero-row** case (`SELECT … INTO` without STRICT sets NULL and does not raise)
and never mentions the **many-row** case, where plpgsql silently takes whichever row the scan
returns first and discards the rest without warning.

Why it matters here specifically: the realistic route to two rows named `analytics_service_key` is a
botched rotation — an operator running `vault.create_secret` again instead of
`vault.update_secret`. The tick would then have a ~50% chance of posting the **retired** key,
producing a 401 against the analytics service, against an async `net.http_post` whose return value
looks identical either way. That is bit-for-bit the seven-day silent outage `CRON-DRIFT-01`
documents and that this function was written to end — reached through the one input path the guards
do not cover.

**Fix** — assert the cardinality rather than picking a winner:

```sql
DECLARE v_keys INTEGER;
…
SELECT count(*) INTO v_keys FROM vault.decrypted_secrets WHERE name = 'analytics_service_key';
IF v_keys <> 1 THEN
  RAISE EXCEPTION 'analytics_service_key resolves to % vault row(s), expected exactly 1 — refusing to guess which one is current. Two rows is the shape a re-CREATE (rather than an UPDATE) of the secret leaves behind, and posting the retired one produces a 401 behind a green cron history', v_keys;
END IF;
SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = 'analytics_service_key';
IF v_key IS NULL OR btrim(v_key) = '' THEN   -- btrim closes [VAULTTICK-EMPTYKEY-01] in the same edit
  RAISE EXCEPTION 'analytics_service_key missing or blank in vault — refusing to send an empty header';
END IF;
```

⛔ Do **not** fix this with `ORDER BY … LIMIT 1`. Picking deterministically still picks silently, and
the wrong key is what the failure looks like.

### WR-02: `service_role` keeps EXECUTE on all three SECURITY DEFINER functions, and both verification blocks stop at `anon`/`authenticated`

**File:** `20260907120000:385` and `:492-497`; `20260907130000:470-471`, `:735-736`, `:852-857`
**Grade:** FORWARD-FIX-LATER

```sql
REVOKE ALL ON FUNCTION public.match_engine_cron_tick() FROM PUBLIC, anon, authenticated;
-- The scheduler runs as superuser; no additional GRANT is required.
```

`service_role` is absent from the revoke list and from every check. This repo's own model of the
Supabase bootstrap — `scripts/pg-lane/fixtures/07-fixture-supabase-default-privileges.sql:22` —
grants `ALL ON FUNCTIONS TO anon, authenticated, service_role`, so `service_role` retains EXECUTE by
default privilege. `public` is a PostgREST-exposed schema, which makes
`POST /rpc/match_engine_cron_tick` reachable by any holder of the service key: CI jobs, the
analytics service, Vercel functions, and anyone who obtains the key.

The comment at `:386` already establishes that nothing needs a grant, so removing it costs nothing.
This is defence-in-depth, not a live bypass — the service key is already a high-value credential —
but a network-reachable, unauthenticated-at-the-function-level trigger for the whole match-engine
recompute, with no rate limit, is a strictly larger surface than the design intends. The check at
`:495` is what makes it a *review* finding rather than a taste one: its message says
"A browser-reachable SECURITY DEFINER function that posts the analytics service key is an
unauthenticated trigger for the whole match engine", and the check cannot fail for the one role that
can actually reach it over the network.

**Fix:**

```sql
REVOKE ALL ON FUNCTION public.match_engine_cron_tick() FROM PUBLIC, anon, authenticated, service_role;
```

and in check 3, add `service_role` to the `has_function_privilege` triple with a message naming the
PostgREST `/rpc/` route. Same two edits for both fan-outs in `20260907130000`.

### WR-03: `20260907130000`'s comment-strip false-pass analysis is inverted for its own check 6

**File:** `supabase/migrations/20260907130000_ledger_refresh_switch_to_system_flags.sql:880-885`
and `:893`, `:912-916`
**Grade:** LATENT-ONLY (documentation + gate hygiene; no PROD behaviour)

The header states, as a closed argument:

> *"The other direction is safe by construction — a `--` inside a string literal makes the strip eat
> real code, which can only cause a FALSE FAILURE, and a false failure is loud."*

That holds for checks 4 and 5, which are **presence** assertions. It does **not** hold for check 6,
which is an **absence** assertion:

```sql
IF position(v_guc_needle IN v_def) <> 0 THEN   -- "the retired app-namespace read is GONE"
```

For an absence check, the strip eating real code is precisely the **false-PASS** direction. A body
containing `RAISE NOTICE 'a -- b'; PERFORM current_setting('app.ledger_refresh_enabled');` on one
line would have the GUC read stripped away, and check 6 would report the read gone while it is
still there and still executing. The `/*…*/` residual the header *does* record is the reverse for
check 6 (loud false failure) — so the file records the harmless direction and misses the harmful one.

Neither body contains a `--` inside a string literal today (measured), so this is latent. But the
header is the artifact a future editor reasons from, and it currently licenses exactly the edit that
breaks check 6.

**Fix** — split the argument by check polarity, and give check 6 a strip-independent second arm:

```sql
-- check 6 runs on BOTH texts: a needle absent from the stripped body AND absent from the raw one.
IF position(v_guc_needle IN v_def) <> 0 OR position(v_guc_needle IN v_def_raw) <> 0 THEN
```

(That is safe: the raw body's prose deliberately never spells the call out — the DECLARE at `:776-783`
already concatenates the needle for exactly this reason.)

### WR-04: an unreadable or invalid oracle disables the live credential scan entirely

**File:** `scripts/prod-prober/arms/cron-drift.mjs:643-661` (`run`) and `:443-487` → `:511-522`
**Grade:** FORWARD-FIX-LATER

Two short-circuits, both ahead of PROD hygiene:

* `run()` at `:652-660` returns as soon as the manifest file cannot be read or parsed — before the
  `cron.job` query is even issued. No PROD row is ever examined.
* `compareManifest`'s `invalid()` at `:443-446` returns immediately, and the `prodHygiene` loop at
  `:511-522` sits **below** every validation gate.

So a manifest that is missing, has a bumped `schema_version`, or has one malformed row means the arm
never asks whether a live cron command carries a credential. The header at `:38-41` explicitly makes
the opposite claim as a design property: *"why they run on BOTH sides of the comparison, and why a
PROD command failing them is `cron-secret-in-command` EVEN WHEN ITS SHA MATCHES THE MANIFEST."* The
hygiene scan is presented as independent of the comparison and is implemented as downstream of it.

`manifest-invalid` is itself a loud defect, so this does not fail silently — but it *masks* a
higher-severity finding behind a lower-severity one, and a stale schema bump is a mundane way to get
there.

**Fix** — hoist the PROD scan above the oracle:

```js
// run(): read cron.job FIRST, then the manifest.
const prodRows = parseCronJobRows(res.stdout);
for (const row of prodRows) {
  const v = hygieneViolations(row.jobname, row.command);
  if (v.length) addDefect("cron-secret-in-command", "cron-drift", `prod:${row.jobname}`, …);
}
// only then: manifest validation + compareManifest, which skips its own prod-hygiene pass.
```

### WR-05: `parseCronJobRows` silently drops any record with fewer than seven fields

**File:** `scripts/prod-prober/arms/cron-drift.mjs:395`
**Grade:** FORWARD-FIX-LATER

```js
const f = rec.split(CRON_JOB_SEPARATORS.fieldSep);
if (f.length < 7) continue;
```

This is the one path in the arm where a PROD cron row disappears with **no** `measure-fail`, in a

A dropped row surfaces indirectly as "job missing from PROD" (loud) *if* it is in the manifest — but
an extra, unreviewed PROD job that gets dropped by the parser vanishes with no trace at all, which
is precisely the case `:555-562` ("an EXTRA job is drift too — nobody reviewed what it runs") exists

**Fix** — make it a measurement failure rather than a `continue`:

```js
if (f.length < 7) {
  malformed.push(rec.slice(0, 40));
  continue;
}
// …and return { rows, malformed } so run() can raise a measure-fail naming the count.
// A row the parser could not read is NOT a row that is not there.
```

### WR-06: `lint-app-guc`'s successor check is satisfied by any readable file, of any type, anywhere reachable by relative traversal

**File:** `scripts/lint-app-guc.mjs:471-504`
**Grade:** FORWARD-FIX-LATER

```js
const successorAbs = join(dirname(absPath), header.successor);
```

`header.successor` is free text from the annotated file. Nothing constrains it to a `.sql`
migration, to the corpus directory, or to a timestamp later than the annotated file's. The only test
applied is "contains zero app-GUC reads," which every non-SQL file trivially satisfies.

Proven — both of these pass with **zero findings**:

```
successor: notes.txt          (a plain text file beside the migration)  → []
successor: ../out/escaped.md  (a file outside the migrations directory) → []
```

The `header-not-allowlisted` check does force the string to also appear in `LINEAGE_ALLOWLIST`, so a
reviewer sees it — which is why this is a Warning and not a Critical. But the *machine* check named
`successor-invalid`, whose message is "A lineage header that points nowhere is an exemption with no
forwarding address," is satisfied by an empty text file. It proves nothing about the mechanism having
moved.

**Fix:**


### WR-10: two of the three dormancy causes never reach even a WARNING — the fan-outs cannot tell "closed by design" from "invisible to the definer"

**File:** `20260907130000:250-261` and `:509-520`
**Grade:** LATENT-ONLY

Distinct from the booked `[APPGUC-WARNING-UNINSTRUMENTED-01]` (which is about the `RAISE WARNING`
reaching no instrument). This is about the two cases that never produce a WARNING at all.

The guard collapses three materially different states into one `RAISE NOTICE` and `RETURN 0`:

1. read raised → `RAISE WARNING` then dormant — distinguishable in the log (if anything reads it);
2. **row genuinely FALSE** → NOTICE "dormant";
3. **row present but invisible** (definer lost RLS exemption) → `SELECT INTO` yields NULL → NOTICE
   "dormant", byte-identical to (2).

The migration's check 2b at `:817-845` reasons about case (3) *at apply time* and calls it "safe and
silent, i.e. indistinguishable from 'nothing was stale' … the wedge shape this phase removes." The
apply-time check catches the state as it exists on the day of the apply. Nothing catches it if the
exemption is lost afterwards — a role change, a `ALTER ROLE … NOBYPASSRLS`, a restore under a
different owner — and the runtime symptom is a NOTICE that says the flag is closed while an operator
looking at `system_flags` sees `enabled = TRUE`.

**Fix** — make the guard report *which* dormancy it is, so the three are separable in a log:

```sql
BEGIN
  SELECT sf.enabled INTO v_enabled FROM public.system_flags sf WHERE sf.key = 'ledger_refresh_enabled';
  GET DIAGNOSTICS v_found = ROW_COUNT;
EXCEPTION WHEN OTHERS THEN
  RAISE WARNING '…: activation flag read failed (SQLSTATE %); treating as dormant', SQLSTATE;
  v_enabled := NULL; v_found := -1;
END;
IF v_enabled IS DISTINCT FROM TRUE THEN
  IF v_found = 0 THEN
    RAISE WARNING '…: dormant because NO ROW for ledger_refresh_enabled was VISIBLE to this function. The row may exist and be hidden by row security — check the definer''s RLS exemption before re-seeding';
  ELSE
    RAISE NOTICE '…: dormant (system_flags.ledger_refresh_enabled is FALSE); enqueued 0';
  END IF;
  RETURN 0;
END IF;
```

(This shares the instrumentation gap of `[APPGUC-WARNING-UNINSTRUMENTED-01]` — closing that one
should close both.)

### WR-11: a manifest row's `command` text is not bound to its own `command_sha256` — the withhold-procedure's stated guarantee is false

**File:** `scripts/prod-prober/arms/cron-drift.mjs:466-482` (row validation) and `:499-510` (manifest-side hygiene), `:606-613` (the printed diff)
**Grade:** FORWARD-FIX-LATER

The docstring at `:49-60` makes an explicit promise about the reviewer's withhold procedure:

> *"The sha stays machine-produced by `captureManifest`, so this is a REDACTION, not authorship — a
> reviewer can hide text they do not want in a public repo **without being able to invent an
> oracle**."*

That is true of the *withhold* path (delete `command`, set `command_withheld`). It is **not** true of
the ordinary path, because nothing anywhere re-derives `sha256Hex(normalizeCommand(row.command))` and
compares it to `row.command_sha256`. `captureManifest` (`run.mjs:2519`) computes the sha once at
capture; after that the two fields float free.

Consequences, both proven in one run:

* **manifest-side hygiene is defeated.** `manifestHygiene` at `:501` scans `row.command`, so a hand-cleaned
  `command` reports clean while the sha it sits beside still matches a dirty PROD command.
* **the printed diff is a fiction.** `:611` prints `normalizeCommand(m.command)` as the "manifest"
  side of a unified diff whose *actual* comparison was sha-based.

```
manifest.command  = "... jsonb_build_object('X-Service-Key', vault_key) -- vault.decrypted_secrets"   (hand-written, clean)
manifest.command_sha256 = sha of a PROD command that inlines a live key
prod.command      = the inlining command
→ defects: [ 'cron-secret-in-command:prod:match_engine_cron' ]   # prod side only
→ no 'manifest:' defect, no drift: the sha agrees, so the fabricated text is never questioned
```

Graded Warning rather than Critical because PROD-side hygiene still runs on live text and the sha
still detects drift correctly — the damage is to evidence integrity and to the manifest-side arm, not
to the primary comparison.

**Fix** — one clause in the existing row-validation loop, which already runs before any comparison:

```js
if (typeof row.command === "string") {
  const derived = sha256Hex(normalizeCommand(row.command));
  if (derived !== row.command_sha256) {
    return invalid(`cron manifest row ${row.jobname} carries a command whose own sha (${derived.slice(0,12)}) `
      + `is not the command_sha256 it publishes (${String(row.command_sha256).slice(0,12)}). The two fields describe `
      + `different text, so the printed diff and the manifest-side hygiene scan are about a command that was never `
      + `captured. Re-capture rather than hand-editing; to hide text, use the withhold procedure.`);
  }
}
```
