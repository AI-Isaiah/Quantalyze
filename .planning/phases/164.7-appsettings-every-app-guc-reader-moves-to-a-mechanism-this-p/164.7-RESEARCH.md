## Q1 — VAULT: how it is read, by whom, and what happens when the secret is absent

### The hand-written PROD form IS in the repo — verbatim

CONTEXT and 164.1-RESEARCH both say the repo never recorded jobid 1's Vault command. That was true on 2026-09-05 and is no longer true: Phase 164.1 plan 06 captured it from PROD into `scripts/prod-prober/cron-manifest.json` (jobname `match_engine_cron`, `jobid: 1`, `username: "postgres"`, `schedule "0 * * * *"`, `active: true`). The `command` field, quoted verbatim `[VERIFIED: scripts/prod-prober/cron-manifest.json, jobid 1 entry, read this session]`:

```sql
DO $body$ DECLARE v_key text; BEGIN SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = 'analytics_service_key'; IF v_key IS NULL OR v_key = '' THEN RAISE EXCEPTION 'analytics_service_key missing from vault — refusing to send a null header'; END IF; PERFORM net.http_post( url := 'https://quantalyze-analytics-production.up.railway.app/api/match/cron-recompute', headers := jsonb_build_object( 'Content-Type', 'application/json', 'X-Service-Key', v_key ), body := '{}'::jsonb, timeout_milliseconds := 60000 ); END $body$;
```

Three things this text settles:
1. **The reading idiom this project already uses** is `SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = '<name>'` inside a `DO`/plpgsql body, followed by an explicit `IS NULL OR = ''` check that RAISES. Reuse it byte-for-byte in the new callable.
2. **The role that reads it is `postgres`** (`username: "postgres"`), and the read WORKS on PROD: TODOS `CRON-DRIFT-01` records the re-scheduled job returning `200 {"status":"ok","processed":14,…}` at `net._http_response` id 3485 on 2026-09-01 `[VERIFIED: TODOS.md, "### CRON-DRIFT-01 / CRON-OBS-01" section]`. So whatever grant `postgres` holds on `vault.decrypted_secrets`, it is sufficient on PROD.
3. **The URL is a hardcoded literal in the command.** D-03 moves it to `system_settings`; the value to seed is exactly the literal above (already public in the committed manifest, so committing it in a migration leaks nothing new).

The cron-drift arm's hygiene rules constrain the SHAPE of any future jobid-1 command `[VERIFIED: hygieneViolations() in scripts/prod-prober/arms/cron-drift.mjs]`:
- `app-guc`: fires on `/current_setting\s*\(\s*'app\./i` anywhere in the command text (comments included — it runs on raw text).
- `vault-absent`: fires when `name === "match_engine_cron" && !text.includes("vault.decrypted_secrets")` — the command TEXT must literally contain `vault.decrypted_secrets`. ⚠️ This means a 164.5 repair that repoints jobid 1 at `SELECT public.<tick_fn>()` would FAIL this rule unless the rule is amended in the same change. Recorded as Open Question 2; it is 164.5's problem, but the planner should not design a callable whose only legal invocation trips the manifest gate.
- `x-service-key-literal`, `long-literal-in-headers`, `jwt-shape`, `service-role`, etc. — a header value must be an expression (`v_key`), never a quoted literal ≥ 32 chars.

### Official-docs corroboration

- Supabase's own pg_cron example reads Vault inline in the cron command: `url:= (select decrypted_secret from vault.decrypted_secrets where name = 'project_url') || '/functions/v1/function-name'` and `'apikey', (select decrypted_secret from vault.decrypted_secrets where name = 'publishable_key')` `[CITED: supabase.com/docs/guides/functions/schedule-functions via Context7 /websites/supabase]`. So "a cron command reading `vault.decrypted_secrets`" is the vendor-documented pattern, not a local hack.
- Vault docs: `vault.decrypted_secrets` exposes `id, name, description, secret, decrypted_secret, key_id, nonce, created_at, updated_at`; "anyone that has access to the view has access to decrypted secrets", and the docs suggest "the `postgres` user explicitly granting access to the vault table" as the control `[CITED: supabase.com/docs/guides/database/vault]`. Create/update: `vault.create_secret('value', 'unique_name', 'description')`, `vault.update_secret(id, value, name, description)` `[CITED: same page]`.
- ⚠️ The docs do NOT state which grants `postgres` holds by default on a hosted project, and say nothing about SECURITY DEFINER + Vault. `[ASSUMED — A1]`: a SECURITY DEFINER function OWNED BY `postgres` reads Vault exactly as the `DO` block does, because the effective role is identical. This is very likely but was not measured; it is cheap to falsify on TEST (see Validation Architecture). Note the fan-out migration already REQUIRES the owner to be superuser or `rolbypassrls` (the RAISE in the verification `DO` block of `20260825130000` at the `v_owner` check, quoted in CONTEXT) — that owner is `postgres` on Supabase, which is the same role jobid 1 runs as.

### Failure mode when the secret is absent

- A plpgsql `SELECT … INTO` with no `STRICT` sets the target "to nulls if the command returned no rows" and does not raise `[CITED: postgresql.org/docs/current/plpgsql-statements.html, "Executing a Command with a Single-Row Result"]`. So a missing/renamed secret yields `v_key IS NULL`. Without the explicit check, `jsonb_build_object('X-Service-Key', NULL)` sends a null header → the service answers 401 → pg_cron still logs `succeeded` because `net.http_post` is async — the exact 7-day silent outage `CRON-DRIFT-01` documents. **Therefore the `RAISE EXCEPTION` on NULL/empty is load-bearing and must be kept** in the new callable; it converts "absent secret" into a failed `cron.job_run_details` row, which the `cron-obs` arm can see.
- On a database with NO `vault` schema at all (the pg-lane: `grep -rni vault scripts/pg-lane/` is empty `[VERIFIED]`), the read raises `42P01 relation "vault.decrypted_secrets" does not exist` at execution (plpgsql resolves at run time). That is the correct fail-loud behaviour for the match-engine callable — but it also means **no `supabase/tests` gate for the Vault read can run on the pg-lane without a `vault` stand-in fixture**, and `sql-tests` on shared TEST needs the secret to exist there, which is UNKNOWN (Open Question 3).

## Q2 — FAIL-CLOSED CONVERSION: the plpgsql idiom, and every gate it moves

### The repo's own idiom

The fan-out body already uses `BEGIN … EXCEPTION WHEN OTHERS THEN … END;` twice `[VERIFIED: supabase/migrations/20260825130000_ledger_refresh_fanout_dormant.sql, per-candidate handler at the `RAISE WARNING 'enqueue_ledger_refresh_for_strategies: one candidate failed to enqueue (SQLSTATE %); continuing'` line and the outer handler that `pg_advisory_unlock`s then `RAISE`s]`. Phase 164.4 plan 09's resync-retry gate uses the same construction for the mirror reason (`test_resync_retry_single_job.sql`, comment beginning "The INSERT is wrapped in the SAME `BEGIN ... EXCEPTION WHEN unique_violation` idiom") `[VERIFIED]`. There is no need to invent anything. The guard, as the FIRST statement of the body:

```sql
-- Source: the repo's own EXCEPTION idiom (20260825130000 per-candidate handler) +
-- plpgsql SELECT INTO semantics (no STRICT => NULL on zero rows, postgresql.org docs).
DECLARE
  v_enabled BOOLEAN;     -- was TEXT; the column is BOOLEAN NOT NULL
  …
BEGIN
  -- ---- Lock B: the fail-closed activation switch (FIRST statement, deliberately) ----
  -- ANY failure of this read — table missing, permission denied, planner fault —
  -- lands in the handler and leaves v_enabled NULL, which the comparison below
  -- treats as dormant. A missing row is ALSO dormant: SELECT INTO without STRICT
  -- sets the target to NULL on zero rows. This is the opposite default from
  -- send-intro/route.ts (missing row => enabled) ON PURPOSE: 161.1 is dormant-by-default.
  BEGIN
    SELECT sf.enabled INTO v_enabled
      FROM public.system_flags sf
     WHERE sf.key = 'ledger_refresh_enabled';
  EXCEPTION WHEN OTHERS THEN
    v_enabled := NULL;
  END;
  IF v_enabled IS DISTINCT FROM TRUE THEN
    RAISE NOTICE 'enqueue_ledger_refresh_for_strategies: dormant (system_flags.ledger_refresh_enabled is not TRUE); enqueued 0';
    RETURN 0;
  END IF;
```

Why `IS DISTINCT FROM TRUE` and not `<> TRUE` / `NOT v_enabled`: with `v_enabled` NULL both alternatives evaluate to NULL and the `IF` falls through as false — i.e. they would OPEN the flag on the failure path. `IS DISTINCT FROM TRUE` is true for NULL and for FALSE, which is the fail-closed truth table. (This is the boolean analogue of the original comment's "a truthiness test would open the flag on half of that list".)

⚠️ Put nothing but the assignment inside the handler. `lint-sql-gates.mjs` rule `R1-exception-handler-probe` flags DML or `SELECT … INTO` inside an `EXCEPTION WHEN` block; it scans `supabase/tests` only, but the gate files that exercise this guard will copy the shape, so keep it clean at the source.

⚠️ `send-intro/route.ts` semantics differ and the planner must not copy them blindly: that route treats a MISSING row as `enabled = true` (its comment: "Row missing (brand-new project before migration 011) → treat as enabled=true") and only a READ ERROR as 503 `[VERIFIED: src/app/api/admin/match/send-intro/route.ts, system_flags lookup block]`. `analytics-service/routers/match.py` is fail-OPEN on exception ("kill switch check FAILED (fail-open, engine still running)") `[VERIFIED]`. Neither is the model for a dormant-by-default switch; only the "error ⇒ closed" half transfers. Recommend the migration SEEDS `('ledger_refresh_enabled', false)` so the activation op is an `UPDATE` (matching `kill-switch/route.ts`, which UPDATEs and 503s on a missing row) and a missing row is never the normal state.

### RLS: no policy needed for the guard read
CONTEXT's reasoning holds and was re-read: the function is `SECURITY DEFINER`, `SET search_path = public, pg_catalog`, and its migration RAISES unless the owner is `rolsuper` or `rolbypassrls` `[VERIFIED: the `IF NOT (COALESCE(v_bypassrls, FALSE) OR COALESCE(v_super, FALSE))` RAISE in 20260825130000's verification block]`. The `system_flags` read inside it bypasses RLS by construction. The EXISTING `system_flags` policies (`system_flags_match_engine_public_read` scoped to `key = 'match_engine_enabled'`, `system_flags_admin_all`, `system_flags_service_all`) `[VERIFIED: 20260407164606_perfect_match.sql, RLS section]` already let an admin session or the service role UPDATE the new row; no new policy is required for the flip either. ### The exemption, made falsifiable

The tension the planner must see: D-04 says applied migrations are the permanent record and must not have executable statements deleted — so the 11 executable `current_setting('app.` sites STAY in the tree as text. 3. The header itself does not count as an occurrence only if it does not contain the regex — write it as `app.* GUC` prose, never as `current_setting('app.`.

### Anti-Patterns to Avoid
- **`SET app.… ; SELECT …` in the cron command** — rejected by the founder; it holds a fail-closed guard open by its own caller (ROADMAP).
- **`IF NOT v_enabled` / `v_enabled <> TRUE`** — NULL-unsafe; opens the flag on the failure path.
- **Editing the executable text of an applied migration** — D-04; add headers/comments only.
- **Reading `api_keys.last_sync_at` as freshness** — the lie 161.1 was written against; read the view.
- **A schedule in a migration** — auto-applies to PROD with no deploy step (runbook, gate 3a).
- **Widening the `system_flags` public-read policy to the new key** — nothing browser-side needs it.

## Common Pitfalls

### Pitfall 1: The mutation twins still edit the dead body
**What goes wrong:** arm A twins point at `20260825130000/140000`; after the new `CREATE OR REPLACE` the mutated text is overwritten on the lane, so the arm cannot redden → `no-red`.
**How to avoid:** re-point `file`/`find` at the new migration and re-measure `occurrences` with `--parse-only`.
**Warning signs:** `no-red` naming arm A in either ledger file.

### Pitfall 2: Gate 3a's window and token scan
**What goes wrong:** a `202609…` migration naming `enqueue_ledger_refresh_for_strategies` fails the "escaped the window" floor; once the window is widened, any `cron.schedule` text — even a rollback comment — fails the dormancy scan.
**How to avoid:** widen the window and `_PHASE_MIGRATION_NAMES` in the same commit; keep `cron.` tokens out of the new files entirely.

### Pitfall 3: Pasting the VAC-04 ack
**What goes wrong:** a pragma written on sight silences DRIFT-02's shape.
**How to avoid:** the 164.2 recipe — verify origin/main snapshot sha == PROD sha locally first, write both hashes and the run id beside the pragma.

### Pitfall 4: A `sql-tests` red misread as a coupling regression
**What goes wrong:** the new migration is not on shared TEST, so VAC-08 and the ledger gates go red BY DESIGN.
**How to avoid:** name the expected reds by arm in the SUMMARY and a TODOS entry before the PR opens; never hand-apply to TEST without the founder (shared DB).

### Pitfall 5: Activation stalls at P3, or trips cron-drift
**What goes wrong:** MT5 auth failure (#747) makes P3-C abort; the new cron row makes the prober report drift.
**How to avoid:** say so in the SUMMARY; schedule the manifest re-capture as the last step of the founder gate.

### Pitfall 6: NULL-unsafe boolean comparison
**What goes wrong:** `IF NOT v_enabled` with `v_enabled` NULL falls through and opens the flag exactly when the read failed.
**How to avoid:** `IS DISTINCT FROM TRUE`; a Python gate asserting that exact text; a SQL arm that renames the table in a savepoint and expects 0.

## Code Examples

### The match-engine callable (shape; body text to be finalised by the planner)
```sql
-- Source: manifest jobid-1 command (verbatim idiom) + D-03 settings read
CREATE OR REPLACE FUNCTION public.match_engine_cron_tick()
RETURNS BIGINT LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_catalog
AS $tick$
DECLARE v_key TEXT; v_url TEXT; v_req BIGINT;
BEGIN
  SELECT decrypted_secret INTO v_key FROM vault.decrypted_secrets WHERE name = 'analytics_service_key';
  IF v_key IS NULL OR v_key = '' THEN
    RAISE EXCEPTION 'analytics_service_key missing from vault — refusing to send a null header';
  END IF;
  SELECT s.value INTO v_url FROM public.system_settings s WHERE s.key = 'analytics_service_url';
  IF v_url IS NULL OR v_url = '' THEN
    RAISE EXCEPTION 'analytics_service_url missing from system_settings — refusing to post to a null url';
  END IF;
  SELECT net.http_post(
    url := v_url || '/api/match/cron-recompute',
    headers := jsonb_build_object('Content-Type', 'application/json', 'X-Service-Key', v_key),
    body := '{}'::jsonb, timeout_milliseconds := 60000) INTO v_req;
  RETURN v_req;
END $tick$;
REVOKE ALL ON FUNCTION public.match_engine_cron_tick() FROM PUBLIC, anon, authenticated;
```
⚠️ `vault-absent` requires the literal `vault.decrypted_secrets` in the cron COMMAND text (Open Question 2) — 164.5 decides between amending that rule and keeping a `DO` wrapper.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Null header after secret rotation (7-day silent 401) | Repudiation/DoS | explicit RAISE on NULL/empty key; `cron-obs` arm reads `net._http_response` |
| Fail-open on read error | Elevation | `EXCEPTION WHEN OTHERS ⇒ NULL` + `IS DISTINCT FROM TRUE`; arm L |
