## 2. Regression hunt: what I checked and found sound

- **False RECOVERED while still down, across a restart:** none found. The durable recovery is reached only when `reading_state == STATE_AUTHORIZED`. A busy skip, a budget abandon and a dark reading all fall through, and the test `test_only_a_measured_authorized_reading_recovers_a_page_from_before_a_restart` pins this. The scrub restart path fires only when the newest row is `scrubbed` and this process holds no outstanding page.
  - The relaunch-debt restart settle relies on `_MT5_TERMINAL_RELAUNCH_DEBT` being process-local (`mt5_client.py`, "IN-PROCESS ONLY"). Its only writer is the scrub verb (`mt5_client.py:3678`), so a fresh process cannot owe a debt it did not create. The settle is skipped while THIS process has paged a debt.
- **Races between the window stamp and the done-callback:** `_release_window` deletes only when the stored stamp equals its own. So a recovery that cleared the key in between, or a newer page that re-stamped it, is never undone. The test `test_a_released_window_is_not_released_over_a_newer_page` would fail without that check. `page()` has no `await` between `_admit_through_window` and scheduling the email task, so a monitor-tick cancellation cannot land between the stamp and the delivery.
- **Duplicate restart recoveries:** two concurrent first-healthy readings (boot heal and monitor tick) can both pass the `_DURABLE_CHECKED` test and both read the row. The second `recovered` is still suppressed, because a recovered of the same source is already inside the window.
- **Tick time bound:** every new sink call is held to 5 s by `asyncio.wait_for`, and the outer `PROBE_TICK_BOUND_S` / `READ_TICK_BOUND_S` / heal `wait_for` bounds still cap the tick. The I/O is also one-shot:
  - the read happens once per source per process;
  - the record happens once per incident (it stops once `recorded=True`);
  - the close happens once per recovery.

  So a steady healthy or sustained-down tick adds no round trip. With a degraded sink, the work can be truncated by the outer bound: the 5 s slack in `PROBE_TICK_BOUND_S` was sized for a page that does not await. That fails toward a retry (record) or a repeat notice (close), never toward a hang. Not reported.
- **`cron_runs` readers that do not filter `cron_name`:** none. Every reader is narrowed by name:
  - `latest_cron_success` (by name and `ok`);
  - `prod_prober_cadence_check` (`prod_prober`);
  - `ops_staleness_check` (`cron_sync`);
  - `enqueue_ledger_*` (`ledger_refresh_fanout`);
  - the prober `cron-obs` arm (`ledger_refresh_fanout`);
  - `_read_newest_scrub_row` (`mt5_terminal_scrub`);
  - the episode reader (`mt5_session_episode`).

  Nothing in `src/` reads the table: there is only the generated type. No retention job or sweeper DELETEs or UPDATEs `cron_runs` in migrations or the cron manifest, so a long-open `ops_alert_open` row is neither reaped nor counted.
- **Tests that cannot fail:** the conftest autouse store has the same semantics as the real module (setdefault-idempotent record, pop-on-close, raise-on-read-failure). `test_ops_alert_open.py` tests the real functions, captured at import before the fixture patches them. The SFH-F2 tests cover every no-channel arm (502, raise, unset key, raising Sentry, unschedulable task) and both one-channel arms. None of them would pass with the release removed or made unconditional.

## 3. Findings

### WR-R2-01: A RECOVERED notice that reaches no channel is lost for good: the run is consumed and the durable record is closed whether or not delivery happened

**Severity:** MEDIUM. **Confidence:** 6/10.
**Files:**
- `analytics-service/services/mt5_outage_alert.py:252`: `run = _RUNS.pop(role, None)` consumes the run before delivery.
- `analytics-service/services/mt5_outage_alert.py:354-377`: `_send_request` closes the record right after `page()` returns.
- `analytics-service/services/mt5_outage_alert.py:557-572`: the debt settle does the same.
- `analytics-service/services/mt5_validation_liveness.py:440-450`: the scrub reader does the same.
- `analytics-service/services/ops_alert.py:319-341`: `_settle_window`.
- `analytics-service/services/ops_alert_open.py:46-48`: the "at-least-once, never lost" claim.

**Issue:** The SFH-F2 fix rests on "the window is not spent and **the next reading retries**", and `_settle_window` logs that sentence. That holds for an OUTAGE, because every later qualifying reading calls `page()` again. It is false for a RECOVERED. Every recovered path is one-shot:
- the tracker pops the run;
- the scrub reader clears `outstanding_cause`;
- the debt settle zeroes `_DEBT`.

All of these happen before `page()`. The new durable record, the one mechanism that could re-send, is then closed unconditionally. `page()` returns `None` before the email task has even run, so `_send_request` cannot know that delivery failed.

**Failure scenario:**
1. The jobs terminal is paged OUTAGE.
2. It recovers. `_advance_run` pops the run and `page(... "recovered")` runs. Sentry yields no event id (no DSN, or `before_send` dropped it), and the founder email POST returns 502 (a Resend blip) or 401 (a key rotation on one side).
3. `_settle_window` releases the window and logs "the next reading retries".
4. Meanwhile `_send_request` has already called `close_open_page`. The row is `ok`, and `_DURABLE_CHECKED` holds the source.
5. No later reading or restart re-sends the notice. The founder's last message stays OUTAGE for a terminal that is healthy.

This is the WR-01 end-state, reached through delivery instead of a redeploy. The log line that claims a retry is false, and so is the module docstring's "never lost". Impact is limited because it needs both channels to fail at once, and it fails toward a stale alarm, not a silent outage.

**Fix:** Close the durable record only once a channel has the notice, and let the durable path be the retry.
- Have `page()` return the delivery outcome to callers that need it. For example, return the email task (or `None` when suppressed) together with `sentry_ok`, or accept an `on_settled` callback.
- In `_send_request`, in the debt settle and in the scrub reader, call `close_open_page` only when a channel succeeded.
- On a no-channel RECOVERED, leave the row open and `discard` the source from `_DURABLE_CHECKED` (for the scrub reader, set `restart_checked = False`). The next measured authorized reading then finds the row and re-sends through `_durable_recovery_request`, which already exists.
- Add a test: recovered with `capture_message -> None` and an email 502. Assert that the row stays open and that the next authorized reading sends a second recovered.
- Until then, at minimum, correct the `_settle_window` log text and the `ops_alert_open` docstring so they do not promise a retry that does not exist for RECOVERED.

### WR-R2-02: A failed close is never retried within the process, so the stale `running` row outlives the incident, is inherited by the next incident's record, and sends a mis-dated RECOVERED after the next deploy

**Severity:** MEDIUM. **Confidence:** 5/10.
**Files:**
- `analytics-service/services/mt5_outage_alert.py:335`: `_DURABLE_CHECKED.add(source)` runs on the boot read even when nothing is open.
- `analytics-service/services/mt5_outage_alert.py:375-377` and `:570-572`: a False close leaves the set untouched.
- `analytics-service/services/mt5_validation_liveness.py:405`: `restart_checked = True` on the boot read; `:447-450` is the close.
- `analytics-service/services/ops_alert_open.py:166-168`: `_record` keeps any existing open row.
- `analytics-service/services/ops_alert_open.py:228-246`: `_close` never reads the UPDATE's affected count.

**Issue:** `_DURABLE_CHECKED` (and `restart_checked`) is set by the first successful boot read, which normally finds nothing. From then on, the durable path is never consulted again in this process. Take an in-process recovery whose `close_open_page` fails: a 5 s timeout, a transient PostgREST error, or an UPDATE that matched nothing, which `_close` reports as success because it ignores the result. The failure is logged at WARNING and nothing retries it. The `running` row then lives until the next process start. Two consequences:

1. **The next incident inherits the stale row.** `_record` returns True when any open row exists for the source, so a new incident's record keeps the OLD row's `cause` and `since`. If a redeploy then ends the new incident, the restart RECOVERED names the old cause and an old `since`, with a `duration_min` that spans both incidents and the healthy gap between them.
2. **With no new incident, the next deploy sends a spurious RECOVERED.** The first authorized reading after a routine redeploy, possibly days later, sends a recovered notice for an incident the founder already saw end.

Neither leaves the founder believing a down terminal is up. It is noise and mis-dated evidence on the channel D-05 is trying to keep trustworthy, and the brief asked specifically about rows left `running`.

**Fix:**
- On a False `close_open_page`, `discard` the source from `_DURABLE_CHECKED` (for the scrub reader, set `restart_checked = False`). The next measured healthy reading then re-reads and re-closes. The window already suppresses a duplicate notice within the hour.
- In `_close`, request `count=CountMethod.exact`, as `mt5_session_episodes._close_row` does. Treat "rows were selected as open but none was updated" as a failure rather than success.
- Alternatively, have `_record` treat an open row whose `since` predates the current run's `since` as stale: close it and insert a fresh one. That way a new incident never inherits an old one's identity.
