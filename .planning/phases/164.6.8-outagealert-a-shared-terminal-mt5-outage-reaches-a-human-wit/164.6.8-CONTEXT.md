<decisions>
## Implementation Decisions

### Paging channel
- **D-01:** The page is a Sentry event plus a Sentry alert rule that fires on frequency, not only on a new issue, AND a founder email through `notifyFounderGeneric`. The Python service reaches it through a small authenticated server-side Next.js route.
- **D-02:** Delivery is proven by an early founder step that records the Sentry rule type (as go-live runbook L-H2 does), plus a test per source that fails first when its reader is removed.
- **D-03:** Whether the alarm watches its own delivery (`PROBER-ALERT-DELIVERY-UNVERIFIED-01`) stays explicitly out of scope. The founder left it unrouted on 2026-09-18.
- **D-15 (founder 2026-10-14, plan 09 drill, deviates from D-01):** **Sentry is the only live paging channel for now.** The PROD drill at 19:50:49 UTC (pg_net request 4530, HTTP 200) reached Sentry: the `ops_alert source=drill` event fired, and the founder confirmed the rule "Ops alert: outage (164.6.8)" notified them without opening Sentry. The founder-email channel did NOT deliver. `POST /api/cron/ops-alert` answered 502 because Vercel production has no Resend key (`EmailSkippedError: [email] Resend not configured`). The route failed loud, as designed. Founder call: "Sentry only for now". The email code stays shipped and loud, and the email half of D-01 is booked as `164.6.8-OPS-ALERT-EMAIL-UNCONFIGURED`. It is not a defect in the shipped code.
- **D-16 (founder 2026-10-14, after verification, follows from D-15):** **Under D-15, a RECOVERED notice counts as delivered once its Sentry capture succeeds.** The verifier found that `ops_alert.py` credits a recovered notice only on a 2xx from the founder email (WR-R3-01). With email unconfigured, a recovered notice could never be credited and would retry on every healthy reading: a Sentry warning, an ERROR log and a failing email POST each time, until Resend exists. Founder call: "Credit recovery via Sentry". Email still sends whenever Resend is configured. This ships as a gap-closure plan in this phase before it closes. ⭐ **Amended 2026-10-15 (founder: "Widen the rule to recovered"):** the Sentry rule "Ops alert: outage (164.6.8)" now also notifies on `ops_alert_event=recovered`, in a second action group sending the same email to the issue owners. A credited recovered notice therefore reaches the founder, rather than sitting in Sentry unseen. This is a live Sentry setting and no repo file holds it.

### Thresholds, dedupe, recovery
- **D-04:** An MT5 outage pages at the existing `blind_run_escalation_threshold(poll_interval_s)` (`mt5_session_episodes.py`). The escalation raises to ERROR with a tagged Sentry capture and sends the founder email. No new number is invented.
- **D-05:** Re-alert at most once an hour per cause (the `_PROBER_CADENCE_ALERT_WINDOW_S` pattern, keyed per cause), with `_DECIDED_BLIND_KINDS` suppressed.
- **D-06:** Recovered means the first MEASURED healthy reading closes the episode (`_clear_blind_run`) and sends one "recovered" notice. A busy skip or `code=0` is `not_measured` and never counts as recovered.
- **D-07:** One GitHub issue per incident instead of the forever-open #773. The prober workflow stays exit-0 by design, because Railway's wait-for-CI otherwise skips deploys.

### Scope
- **D-08:** MT5 (both terminals), cron-sync staleness and backfill staleness are all in, split by topic into plans.
- **D-09:** The validation terminal is in (`MT5-VALIDATION-TERMINAL-COVERAGE-01`, both halves: (a) the gateway is monitored, (b) `mt5_terminal_scrub` `cron_runs` rows get a reader).
- **D-10:** The cron-sync and backfill reader is one SECURITY DEFINER function plus one pg_cron registration, posting to the existing alert route. The registration is a live PROD op (marker query first), and the migration needs migration-reviewer and rls-policy-auditor clean before merge. Never edit `supabase-migrate.yml` to ship it. No data-reading DO block that RAISEs (TEST holds schema without data).
- **D-11:** Cron-sync pages when its `cron_runs` heartbeat is older than 2 days, or on two consecutive `error` rows (the TODOS gate values).

### Wedge evidence
- **D-12:** `MT5-PROBER-WEDGE-CALIBRATION-01` and `MT5-SWITCH-WEDGE-CAUSE-01` are booked as live-gated human items, so the phase closes without waiting for a wedge. A hand-written fixture is never a close.
- **D-13:** The MT5 alert path snapshots wedge evidence at page time, before any recycle (the heal can recycle in about 10 min), and scrubs account digits, broker server name and machine paths.
- **D-14:** The ROADMAP SC-2 text is corrected to HEAD (the lease-busy ERROR exists and is pinned). The longer lease wait while a relaunch debt is owed (`MT5-RELAUNCH-DEBT-LEASE-WAIT-01`, founder "Book a fix", D-15 of 2026-10-08) is taken in this phase.
