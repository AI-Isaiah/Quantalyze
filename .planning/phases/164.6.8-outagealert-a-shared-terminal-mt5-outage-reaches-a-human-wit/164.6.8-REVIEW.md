## Summary

The channel itself is sound. `page()` never raises, and the Sentry capture carries a stable per-(source, cause, event) fingerprint. The founder rule filters on `ops_alert_event = outage`, so the un-tagged LoggingIntegration events do not fire it. The email POST is held to an allow-listed https origin with redirects off, and the route fails closed on auth and on an empty recipient. The prober incident logic does what D-07 asks. The SQL backfill ceilings match the watchdog (`claimed_at`-based reclaim, 30 min for `derive_broker_dailies`, `next_attempt_at NOT NULL`).

The defects are in incident lifecycle state, not in delivery:
- recovery notices are lost across a redeploy, and one can be lost within a tick;
- the dedupe key is per reading-cause, not per incident;
- the alert-path failures themselves log below the Sentry event level;
- the go-live runbook still registers the SQL reader at the minute O-1 rejected;
- the cron_sync error arm pages on per-key client faults.

## Warnings (MEDIUM)

### WR-01: A paged MT5 outage never gets its RECOVERED notice when a redeploy happens before recovery

**Severity:** MEDIUM. **Confidence:** 8/10.
**Files:**
- `analytics-service/services/mt5_outage_alert.py:121` (`_RUNS`) and `:135` (`_DEBT`)
- `analytics-service/services/mt5_outage_alert.py:215-220`
- `analytics-service/services/mt5_validation_liveness.py:259` (`_SCRUB_STATE`, the same shape)

**Failure scenario:**
1. The jobs terminal goes dark and the tracker pages: the founder gets `[OUTAGE] mt5_jobs_terminal: dark`.
2. A fix is merged and Railway redeploys the analytics service. Redeploying is the most likely way an MT5 incident ends.
3. The new process starts with empty `_RUNS`. Its first measured `authorized` reading reaches `_advance_run`, and `run = _RUNS.pop(role, None)` returns `None`, so the function returns `None`.
4. No RECOVERED email or Sentry event is ever sent. The founder's inbox ends on OUTAGE.

The relaunch-debt page (`_DEBT`) behaves the same way. The accepted risk T-164.6.8-20 (plan 04 SUMMARY) covers only "delays a page by at most one threshold". The lost recovery is not in that acceptance.

**Fix:** Make "a page is open" durable. Options:
- Write one `cron_runs` row (for example `cron_name='ops_alert_open'`, with source and cause) when an outage page is sent, and one when it recovers. On the first measured `authorized` reading after boot, read the open row and send the recovered notice.
- At minimum, have the first authorized reading after boot send a "service restarted; terminal measured healthy" notice whenever the durable marker says a page is open.

### WR-02: Dedupe is keyed on (source, cause, event), not on the incident, so a re-outage goes silent and one incident pages once per reading kind

**Severity:** MEDIUM. **Confidence:** 7/10.
**Files:**
- `analytics-service/services/ops_alert.py:292-297`
- `analytics-service/services/mt5_outage_alert.py:235-251`

**Failure scenario (a), a silent re-outage:**
1. T+0: the jobs terminal is paged `outage/dark`.
2. T+10: the first authorized reading sends RECOVERED.
3. T+20: the terminal goes dark again, and the run reaches the threshold about 30 min later (2 readings per heal tick).
4. `_last_alert_at[(mt5_jobs_terminal, dark, outage)]` is still inside 3600 s, so `page()` returns silently. The Sentry capture and the email are both suppressed.
5. The last thing the founder was told is RECOVERED, while the terminal has been down again for up to an hour.

A terminal that flaps (down about 30 min, up about 5 min) produces one OUTAGE and one RECOVERED per hour and otherwise looks healthy.

**Failure scenario (b), one incident paging several times an hour:** `cause` is the CURRENT reading's kind, and it changes within one run (`ipc_fault`, `busy_skip`, `budget_abandoned`, `tick_deadline`). Each new kind is a fresh window key and a fresh Sentry fingerprint, so one wedge can send 3 or 4 founder emails plus 3 or 4 Sentry-rule emails in the same hour. The RECOVERED cause is then `recovered_from_<whichever kind came last>`.

**Fix:**
- Fix the page's cause per run: use the cause at the threshold crossing, stored on `_Run`, and page later readings with that run cause.
- When a run ends with a RECOVERED notice, clear that source's `outage` window entry, or key the window on `(source, run_since)`. A new incident then pages immediately, while a sustained one still re-pages at most hourly.

### WR-03: The relaunch-debt RECOVERED notice depends on a same-tick check, so a debt paid outside that window leaves the page open forever with stale state

**Severity:** MEDIUM. **Confidence:** 5/10.
**Files:**
- `analytics-service/services/mt5_relogin.py:2876` (`debt_owed_at_start`)
- `analytics-service/services/mt5_relogin.py:3058-3059`
- `analytics-service/services/mt5_outage_alert.py:354-361` and `:391-402`

**Failure scenario:**
1. A debt-owed busy tick pages, which sets `_DEBT.debt_paged=True` and `since`.
2. A later tick wins the lease. Its `_heal_blocking` thread pays the debt (`clear_mt5_relaunch_debt`).
3. `record_mt5_heal_outcome` makes several unbounded Supabase round trips. The monitor's outer `asyncio.wait_for(heal, timeout=interval)` (`mt5_session_monitor.py`, the heal `wait_for`) cancels the coroutine before line 3058. The budget-abandon `return` at `:3005` likewise skips the check.
4. On every later tick `debt_owed_at_start` is `False`, so `note_relaunch_debt_settled` is never called. No RECOVERED is sent.
5. `_DEBT` keeps `debt_paged=True`, the old `since` and the accumulated `busy_ticks`. The NEXT debt incident then pages with the previous incident's `since` and an inflated tick count.

**Fix:** Decide the settle from state, not from the tick. At the start of every heal tick (before the lease), run `if _DEBT.debt_paged and not mt5_relaunch_debt(terminal_key): await note_relaunch_debt_settled()`. Expose a predicate from `mt5_outage_alert` so the lock stays internal.

### WR-05: Failures of the alert path itself are logged at WARNING, below the Sentry event level, so a broken reader or tracker stays silent

**Severity:** MEDIUM. **Confidence:** 6/10.
**Files:**
- `analytics-service/services/mt5_outage_alert.py:278-289`: `note_outage_reading` handler, WARNING.
- `analytics-service/services/mt5_outage_alert.py:370-381` and `:417-428`: relaunch-debt page and settle handlers, WARNING.
- `analytics-service/services/mt5_validation_liveness.py:396-407`: scrub-row reader handler, WARNING.
- `analytics-service/services/mt5_validation_liveness.py:208-219`: probe handler, WARNING.
- `analytics-service/services/mt5_session_monitor.py:364-370` and `:377-382`: probe and reader tick bounds, WARNING.

**Failure scenario:** `sentry_init.py` keeps the default LoggingIntegration, which turns ERROR into a Sentry event and leaves WARNING as a breadcrumb. These are the handlers that catch a failure of the PAGING path, and they log at WARNING. Two examples:

- **The scrub reader stops reading.** Suppose `_read_newest_scrub_row` raises or times out on every tick: a PostgREST schema-cache error, a renamed column, or degraded Supabase past `_READ_TIMEOUT_S`. Then D-09 (b) has no reader. A later `refused` or `failed` scrub row, meaning a client's login may still be on the terminal, never pages. The only trace is a WARNING line every 10 minutes that no rule sees.
- **The validation probe never counts.** If the probe's outer `PROBE_TICK_BOUND_S` ever bites, `note_outage_reading` is never called for that tick. Nothing is counted, so a validation terminal that always hangs that way never reaches the threshold and never pages. It leaves only a WARNING.

D-03 keeps delivery self-monitoring out of scope. This is different: these failures happen inside the service, before delivery is attempted.

**Fix:**
- Log these handler arms at ERROR, so a persistent failure becomes Sentry events.
- Better, for the reader and the probe, record a counted reading on the failure:
  - the probe's outer `TimeoutError` should feed `note_outage_reading(ROLE_VALIDATION, STATE_NOT_MEASURED, KIND_TICK_DEADLINE, None, ...)`;
  - the reader should count consecutive failures and page `mt5_terminal_scrub` / `reader_failed` at `blind_run_escalation_threshold(interval)`.

### WR-06: The cron_sync `two_consecutive_errors` arm pages on per-key client faults and re-pages hourly with no recovery notice

**Severity:** MEDIUM. **Confidence:** 5/10.
**Files:**
- `supabase/migrations/20261015120000_ops_staleness_check.sql:138-160`
- `analytics-service/routers/cron.py`: `_cron_sync_heartbeat_row`, `_cron_sync_error_counters`, `_NON_OK_STATUSES` (`:169-176`)

**Failure scenario:** The heartbeat row is `status='error'` whenever ANY key's status is in `_NON_OK_STATUSES`: `transient_failure`, `partial`, `held`, `timeout`, `error` or `key_revoked`. That is a statement about one client's key, not about whether the cron ran.

`key_revoked` deactivates the key (`is_active=False`), so it does not persist. `transient_failure` and `held` do. Take one venue whose API is flaky for two days, or one key whose cursor is held. Then:
- two consecutive daily rows are `error`;
- `ops_staleness_check` (hourly) pages `cron_sync / two_consecutive_errors` every hour, by Sentry and by founder email, for at least a day, until an `ok` row lands;
- by design, no RECOVERED is ever sent.

D-11 names "two consecutive `error` rows" as the gate value. The defect is that `error` here does not mean "the trade sync is stale". This is the alert-fatigue shape that gets a channel muted, and a muted channel cannot report a real outage either.

**Fix:** Page the `two_consecutive_errors` arm only on rows that mean the RUN failed:
- `error LIKE 'cron_sync aborted%'`;
- `no_strategy_backed_keys`;
- `no_key_synced`;
- or a metadata ratio such as `synced = 0`.

Leave per-key non-ok counts to the existing per-strategy surfaces. Alternatively, record the founder's explicit acceptance of per-key faults paging hourly.

## Checked and found sound (not findings)
