# Phase 164.6.8 Plan 06: OUTAGEALERT validation terminal liveness Summary

The session-monitor tick now measures the validation gateway with a credential-free probe and feeds the shared outage tracker under the validation role, and it reads the newest `mt5_terminal_scrub` row and pages once per row that is not `scrubbed`. Both halves of `MT5-VALIDATION-TERMINAL-COVERAGE-01` (D-09 (a) and (b)).

## Instrument-choice scope statement

The in-process session monitor is the liveness instrument that pages: it already runs on a cadence and already owns the threshold. Not done, on purpose:

- The prod-prober's mt5 arm is NOT extended to the validation service. It would need a new Railway service secret in GitHub, and its output is a GitHub issue, which is not the paging channel.
- The boot heal and the ipc-fault recycle are NOT extended to the validation terminal. The 164.6.6.1 scrub already ends and relaunches that terminal after each validation, and a second recycler on it would race the scrub. The new module only reads the terminal and pages.

## What was built

- `services/mt5_validation_liveness.py` (new).
  - `probe_validation_terminal(*, poll_interval_s)`: endpoint reader (absent -> counted `gateway_not_configured`), then `mt5_terminal_lease(mt5_terminal_key(host, port), wait_s=_MT5_RELOGIN_LEASE_WAIT_DEFAULT_S, holder=HOLDER_VALIDATION, site=SITE_VALIDATION_LIVENESS)`, then `_probe_blocking` off the loop under `MT5_REQUEST_TIMEOUT_S` plus the heal's connect slack. Busy -> `busy_skip`; the thread bound -> `budget_abandoned`; any other raise -> `probe_failed`. The reading goes through `classify_reading` into `note_outage_reading(ROLE_VALIDATION, ...)`. One INFO line per probe with state, kind and code only.
  - `read_unscrubbed_validation_terminal()`: one bounded read (`_READ_TIMEOUT_S` = `_SCRUB_RECORD_TIMEOUT_S`) of the newest `cron_runs` row for `mt5_terminal_scrub`, selecting `id,completed_at,metadata` only. Pages `ops_alert.page("mt5_terminal_scrub", cause=<kind or unrecognised>, event="outage", since=completed_at, detail=...)` once per row id; the first `scrubbed` row after a page sends one `recovered_from_<cause>`. The detail is built from closed fields (site through `_normalize_site`, relaunch status against `_RELAUNCH_STATUSES`, counts only when an int) and goes through `scrub_alert_detail`.
- `run_mt5_session_monitor_tick`: after the jobs heal's `wait_for` (success or timeout), the probe then the reader, each under its own `asyncio.wait_for` (`PROBE_TICK_BOUND_S`, `READ_TICK_BOUND_S`). Neither runs when the kill switch is off. `_MT5_SESSION_POLL_INTERVAL_FLOOR_S` is untouched; a tick stretches by at most the two bounds, and the module docstring says why that is safe (sequential loop, call after the heal cannot pre-empt its abandon arm).
- `SITE_VALIDATION_LIVENESS` added to the closed handover site set.
- Lease roster: `_PRODUCTION_LEASE_SITES` gained `("services/mt5_validation_liveness.py", "probe_validation_terminal")` with a dated re-cut note answering the roster's question (fresh client inside the thread, no reuse) and the steal question. Roster size is now **9** (read from the literal).
- Routing pin: the validation-endpoint reader allowance gained one named entry, kept out of `_VALIDATE_SITES`.

## Behaviours worth the next reader's attention

- A redeploy forgets the reader's paged row id, so the newest non-scrubbed row re-pages once after a deploy (docstring says so).
- A non-scrubbed row stays one page forever if no later row appears; only the helper's hourly window and the single outage page apply.
- The reader's cause is the row's kind, so `skipped_probe_in_flight` and `skipped_no_house_credentials` page under those names, not the write-time alert's `probe_in_flight` / `house_credentials_unset`.
- The probe does not honour a scrub relaunch debt: on a validation terminal left account-less by an unverified relaunch, a bare probe reads an ipc fault or times out, which is a true reading of that terminal.
- A tick-level timeout of the probe (lease or page hanging past its inner bounds) is a WARNING log only, not a counted reading.
- Monitor tests have the known 0.0 s cadence race under `-n 4` (plan 04 deviation 3). One neutered run saw `test_CRITERION_2...` fail once; six consecutive un-neutered runs were clean.
