## Findings

### R3-SFH-01 - MEDIUM (confidence 7): the delivery outcome waits for the founder email even when Sentry already took the notice, so a slow email route blocks the reading path and is then logged as "reached no channel"

Location: `analytics-service/services/ops_alert.py` `page` (the `email_task.add_done_callback(functools.partial(_settle_window, ...))` wiring, ~line 513) and `_settle_window` (`finally: delivered.set_result(outcome)`); `await_delivery` / `_DELIVERY_WAIT_S` (~lines 98, 389-406). Callers: `analytics-service/services/mt5_outage_alert.py:_send_recovered`, `analytics-service/services/mt5_validation_liveness.py:_close_after_recovered`.

`delivered` is resolved only from the email task's done-callback (or immediately when no task exists). `sentry_ok` is known synchronously before that, yet a page with `sentry_ok=True` still resolves only when the email POST finishes. `_post_founder_email` uses `httpx.AsyncClient(timeout=10.0)`, which is a PER-PHASE timeout (connect, read, write, pool), so one POST can legitimately run past `_DELIVERY_WAIT_S` (15 s).

Failure scenario: Sentry takes the RECOVERED notice (event id returned) and the founder-email route is slow (cold Next.js function, 12-20 s).
1. `await_delivery` times out at 15 s and answers False although a channel already has the notice.
2. `_send_recovered` logs ERROR "reached no channel ... stays open", calls `mark_open_page_stale`, and unmarks the source. The ERROR is false (Sentry has it) and pages anyone watching Sentry-logging for ERROR.
3. The wait is inline: `note_outage_reading` is awaited from `record_mt5_session_reading` BEFORE the reading is recorded (`mt5_session_episodes.py` ~1374), and for the debt path from `note_relaunch_debt_settled` inside the heal. Every healthy reading in the re-check cycle blocks 15 s (the shielded holder future is still pending) plus up to 5 s for the close. If a surrounding bound cancels it (`READ_TICK_BOUND_S` for the scrub reader, any heal budget), the healthy reading that should close the episode is not recorded. A healthy measurement is lost with only a warning-level trace.
4. The row is only closed once the email finally settles and a later reading finds the held future resolved True.

Hidden errors: a slow or hung email route; a cancelled tick; a stale flag on a row whose notice was in fact delivered (a new incident then closes and replaces a row for no reason).

Recommendation: resolve `delivered` as soon as the outcome is decidable. When `sentry_ok` is True, `delivered.set_result(True)` right after the capture (the email result is then irrelevant to the one rule "a channel has it"); keep the callback only for the `sentry_ok=False` case. Separately, make the wait for the email case not inline in the reading path (schedule the close as a held background task, as the page itself is), or at minimum size `_DELIVERY_WAIT_S` above the real worst case of the POST (connect+read+write+pool) and keep the log honest ("no outcome yet" for a timeout, "no channel" only for a False outcome).

Example:
```python
# in page(), after the Sentry capture
if sentry_ok and not delivered.done():
    delivered.set_result(True)
# _settle_window: set_result only `if not delivered.done()` (already guarded)
```
