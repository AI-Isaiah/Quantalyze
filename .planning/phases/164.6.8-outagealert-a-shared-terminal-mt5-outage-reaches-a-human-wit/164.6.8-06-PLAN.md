<objective>
Close both halves of `MT5-VALIDATION-TERMINAL-COVERAGE-01`, per D-09. (a) The validation gateway
(`MT5_VALIDATION_GATEWAY_HOST` / `MT5_VALIDATION_GATEWAY_PORT`) is measured on every session-monitor tick by the same
credential-free liveness probe the jobs terminal gets, and an outage on it pages through plan 04's tracker. (b) The
`mt5_terminal_scrub` `cron_runs` rows Phase 164.6.6.1 writes get a reader: a non-`scrubbed` row pages.

Purpose: today a wedged or logged-out validation terminal is noticed only when a user's validation fails, and a
skipped scrub leaves a client's saved login on the terminal with nothing reading the row (TODOS gate: "a check that
only runs when someone validates a key" is not a close).

Instrument choice (Claude's discretion, recorded): the in-process session monitor is the liveness instrument that
pages; it already runs on a cadence and owns the threshold. The prod-prober's mt5 arm is NOT extended to the
validation service here: it would need a new Railway service secret in GitHub, and its output is a GitHub issue,
which is not the paging channel. The boot heal and the ipc-fault recycle are not extended to the validation terminal
either: the 164.6.6.1 scrub already ends and relaunches that terminal after each validation, and a second recycler on
it would race the scrub. The SUMMARY records this scope statement.

Sizing note: the estimate (120k) is above the 100k target. Both halves live in one new module and two calls in the
same monitor tick; splitting them would make two executors edit `run_mt5_session_monitor_tick` and its tests in
sequence for little saving, so they stay together.
</objective>
