## Findings

### F1 - MEDIUM, confidence 8 - NEW
The migration does not assert that its SECURITY DEFINER owner is exempt from row security, although the backfill arm reads a FORCE-RLS table.

- File: supabase/migrations/20261015120000_ops_staleness_check.sql:349-430 (verify block, missing check), reads at :171-194.
- Table: public.compute_jobs carries `FORCE ROW LEVEL SECURITY` (supabase/schema/baseline.sql:1412) and a `USING (false)` deny-all policy (20260411144407_compute_jobs_queue.sql:233-238). FORCE is the one clause under which owning a table is not an exemption. The definer reads it three times (max(claimed_at), the `v_bf_waiting` EXISTS, the `v_bf_stuck` EXISTS).
- Precedent: 20260911130000, 20260917120000 and 20260924120000 each assert `rolsuper OR rolbypassrls` for the definer role and RAISE otherwise (e.g. 20260924120000:1639-1655), precisely because the failure is silent. This migration's header says it follows the sibling hardening, but its DO block checks only overloads, arg count, SECDEF, search_path and the EXECUTE grantee set.
- Failure scenario: the function's owner at apply time is a role with neither rolsuper nor rolbypassrls (a non-Supabase owner, or a PROD owner whose attribute was changed). Every compute_jobs read then returns zero rows. `v_bf_waiting` and `v_bf_stuck` are FALSE, `v_bf_last_claim` is NULL, so the backfill arm reports healthy forever while the worker is dead. That is the "silent healthy" shape this phase exists to remove, and the DO block says "verified". The pg-lane gate (supabase/tests/test_ops_staleness_check.sql) runs as a superuser, so it cannot catch it. On current PROD the owner is `postgres` (BYPASSRLS), so this is latent today, not live.
- Leak scope: none (fails closed to silence, reads nothing extra).
- Recommended fix: add a fourth check to the verify block that joins pg_proc.proowner to pg_roles and RAISEs unless `COALESCE(rolbypassrls,false) OR COALESCE(rolsuper,false)`, copied from 20260924120000:1639-1655. Do not edit applied migrations; this migration is not yet applied, so the edit is in place before merge.

### F2 - MEDIUM, confidence 8 - PRE-EXISTING (copied guard, booked)
The destination allow-list accepts any `*.up.railway.app` host, and the row it tests is writable by service_role as well as admins. The service key is posted to whatever that row names.

- File: supabase/migrations/20261015120000_ops_staleness_check.sql:128-129 (pattern) and :263 (re-test), header :56-62 declares it a copy of cron_sync_tick() / match_engine_cron_tick(). Origin: 20260907120000_analytics_service_settings_and_vault_tick.sql:217, :318, :429.
- Failure scenario: anyone who can write `public.system_settings` (policies `system_settings_admin_all` and `system_settings_service_all`, so any admin session or any service_role holder, i.e. every Next.js `createAdminClient()` route) sets `analytics_service_url` to `https://attacker.up.railway.app`, which any Railway user can register. The next tick sends `X-Service-Key` (the live analytics key, which is also this app's Bearer for `/api/cron/ops-alert`) to that host. This function adds a third outbound caller of the same gate.
- Leak scope: platform-wide service credential, not tenant rows.
- Status: this is `[167.1.2.2.2-CRON-TICK-RESIDUALS]` item 1; the migration deliberately does not re-fix one copy. Not a blocker for this merge. Fix belongs in the booked forward migration that fixes all sibling functions plus the CHECK constraint together (exact host match, or the host pinned in the row).
