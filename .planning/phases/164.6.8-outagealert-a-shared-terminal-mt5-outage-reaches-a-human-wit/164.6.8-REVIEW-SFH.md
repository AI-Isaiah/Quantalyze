## F1 - MEDIUM/HIGH - an outage that re-opens inside an hour never pages (and neither does the second recovery). Confidence 8
ops_alert.py:233-238 (`key = (source, cause, event)`; `_last_alert_at[key] = now` is never cleared).
Scenario: jobs terminal goes down, pages `(mt5_jobs_terminal, ipc_fault, outage)` at T. A measured authorized reading at T+10m pops the run and sends `recovered_from_ipc_fault` (a different key). The terminal wedges again at T+25m: `_advance_run` opens a fresh run, reaches the threshold, calls `page`, and the (source, cause, outage) key is still inside the 3600 s window, so it returns after the logger.error line: no Sentry capture, no email. The founder was just told "recovered" and is never told it broke again. A flapping terminal is the usual shape of this outage. The same flaw applies to a second recovery inside the hour, to `mt5_relaunch_debt` (note_relaunch_debt_lease_busy) and to the scrub reader, whose "one page per row" is overridden by the window when two non-scrubbed rows with the same cause land within an hour (mt5_validation_liveness.py `_advance_scrub_state` marks the row paged even when `page` suppresses it).
The only test (test_ops_alert.py:240) covers outage then recovered, not outage, recovered, outage.
Fix: when `page` sends an event "recovered", delete the window entries for that source (every cause, event "outage"); or key the window with a run id supplied by the tracker (`_Run.since`). Add the test outage, recovered, outage inside the window and assert the second outage captures and posts.

## F2 - MEDIUM - the window is spent before delivery is attempted, so a failed delivery silences the retry for an hour. Confidence 8
ops_alert.py:237 sets `_last_alert_at[key]` before the Sentry capture and before the email task is even scheduled; `_post_founder_email` (ops_alert.py:170-200) only logs on a non-2xx, a missing SERVICE_KEY, a refused URL or an exception.
Scenario: the first page of a sustained outage lands while the Next.js route returns 502 (Resend blip) or 401 (key rotated on one side, a documented operation in this repo) and Sentry has no DSN. Every following reading is suppressed by the window. The only trace is logger.error lines. The outage that began with a transient delivery failure stays unreported for the whole hour, and then the next page may hit the same fault.
Fix: have `_post_founder_email` report success to the caller (or a done-callback) and delete the window key when neither channel succeeded; at minimum, on a failed email, shorten the key's lifetime (store `now - OPS_ALERT_WINDOW_S + 60`). Treat a Sentry no-op (F3) as a failed channel for this purpose.

## F3 - MEDIUM - the Sentry half silently no-ops with no DSN or a dropped event, and the page then relies on the email alone. Confidence 6
ops_alert.py:240-256; analytics-service/sentry_init.py:355-357 (`init_sentry` returns with no log when SENTRY_DSN is unset).
`capture_message` returns None when the SDK is not initialised or `before_send` drops the event; the code ignores the return value, so "Sentry capture sent" is never established. The module docstring admits delivery is unverified, but nothing logs it at the moment of the page. With the DSN missing, the ops channel is one hop (email) with no signal that it is one hop.
Fix: after `capture_message`, if `event_id is None` (or `not sentry_sdk.is_initialized()`), `logger.error("ops_alert: sentry capture produced no event; email is the only channel")` and feed that into the F2 window decision. Also emit one ERROR at startup when SENTRY_DSN is unset in the production environment.

## F4 - MEDIUM - the relaunch-debt page can be left paged forever, with no recovered notice and stale state on the next episode. Confidence 6
mt5_relogin.py (the `debt_owed_at_start and not mt5_relaunch_debt(terminal_key)` block after `record_mt5_heal_outcome`); mt5_outage_alert.py `_DEBT`, `note_relaunch_debt_settled`.
`clear_mt5_relaunch_debt` is also called from `scrub_and_relaunch_as_house` (the validation scrub path) and `_boot_accountless_relaunch` (mt5_relogin.py:1710, 2402), not only from a heal tick. If the debt is paid outside a tick, the next heal starts with `debt_owed_at_start == False`, the settled notice is never sent, `_DEBT.debt_paged` stays True, `since` and `busy_ticks` keep growing, and the next debt episode's page claims a `since` from the earlier incident. The founder sees "lease busy with relaunch debt" and never sees it end. The settled call also sits after `record_mt5_heal_outcome` inside the one try, so any earlier exception in the tick skips it too.
Fix: decide the recovered notice from `_DEBT.debt_paged and not mt5_relaunch_debt(terminal_key)` at the top of every tick, not from `debt_owed_at_start`; or call `note_relaunch_debt_settled` from `clear_mt5_relaunch_debt`'s callers. Add a test where the debt is cleared between two ticks.

## F5 - MEDIUM - the SQL reader's own delivery failure and absence are unobserved. Confidence 6 (acknowledged as out of scope by D-03, so this is a residual to book, not a surprise)
ops_staleness_check.sql, pg_net calls and the observer row (migration lines for `net.http_post ... INTO v_req` and the INSERT into cron_runs); header comment "that absence is itself the next tick's evidence".
`net.http_post` is async and the function returns `v_posts` without reading `net._http_response`, so a 401 (rotated SERVICE_KEY), 5xx or timeout from the analytics service is invisible: the tick is green, `cron_runs` says 'error' with the cause name, and the `/prober-cadence-alert` route returns `acknowledged: True` even when its own page could not be delivered. A RAISE (missing Vault key, bad url) rolls the observer row back and lands in cron.job_run_details, which nothing reads. The comment's claim that the missing row is "the next tick's evidence" is false: no code reads it. Net effect: the alert for "sync stopped for 2 days" can itself stop and nobody is told.
Also note, as a release gate rather than a defect: the migration schedules nothing, so until plan 09 registers the job in PROD no staleness page can fire. The runbook should be the gate on closing the phase, not the merge.
Fix: add a cheap dead-man check in the existing prober or the same function: on each tick, read the previous tick's `net._http_response` status for request ids stored in the observer row's metadata and RAISE (red tick) on non-2xx; and add `ops_staleness_check` itself to the prober's cadence list so a missing observer row pages. Remove or correct the "next tick's evidence" sentence.

## F6 - MEDIUM - the scrub-row reader misses failures and hides its own read errors at WARNING. Confidence 6
mt5_validation_liveness.py:`_read_newest_scrub_row` (limit(1)), `_advance_scrub_state`, `read_unscrubbed_validation_terminal` except branch.
(a) Only the newest row is read each tick. A `failed`/`refused` scrub followed by a `scrubbed` row inside one monitor interval is never seen: state has no outstanding cause, so the newer row returns None and the failure (a client's login possibly left on the terminal at that moment) is never paged. (b) A read that raises or times out is logged at WARNING only. WARNING is below the Sentry event level the phase itself calls out in mt5_session_episodes.py, so a persistently failing read (DB down, bad column, RLS/key change) leaves the reader dead with no human signal, the exact class this phase exists to remove. The "no row exists" case also returns None silently, so a reader pointed at the wrong cron_name looks healthy forever.
Fix: select rows newer than the last seen `completed_at` (or limit 10) and page for any non-scrubbed one; count consecutive read failures and call `ops_alert.page("mt5_terminal_scrub", "reader_failed", ...)` at a small threshold; log ERROR, not WARNING, once the count passes it.
