# Phase 164.6.8: Code review of the D-16 gap closure (plan 10)

Reporting threshold: MEDIUM and above only (caller instruction).

## Summary

The decision under review, quoted from CONTEXT:

- D-15: "**Sentry is the only live paging channel for now.**"
- D-16: "**Under D-15, a RECOVERED notice counts as delivered once its Sentry capture
  succeeds.** ... Email still sends whenever Resend is configured."

The change is `sentry_counts = sentry_ok` (was `sentry_ok and event_n == "outage"`)
in `ops_alert.page`, plus docstrings and tests. It implements D-16 as written:

- No path credits a recovered notice without an event id. `sentry_ok` is True only when
  `capture_message` returns non-None; a raise or a None leaves it False, and
  `_settle_window` then releases the window (WR-R3-01 Sentry half kept, pinned by the
  parametrised `test_wr_r3_01_a_failed_sentry_capture_does_not_credit_a_recovered_notice`).
  The suppressed-with-no-held-future `set_result(True)` branch at `ops_alert.py:481` is
  unreachable: admission writes `_last_alert_at` and `_delivery_by_key` together with no
  await between, and `_release_window` pops both together. It is pre-existing.
- The email is still scheduled for every admitted page. Its failure logs ERROR inside
  `_post_founder_email`. Because the window is now spent on a credited recovery, that
  happens at most once per window.
- Window and holder interplay: a credited recovery stamps the recovered key for the hour.
  A repeat recovered reading inside the hour (for example after a failed
  `close_open_page`) is suppressed and gets the holder's resolved-True future, so the
  close is retried with no second capture or email. That is the intended behaviour.
  A fresh outage cannot be suppressed after a recovery, because the recovery drops every
  outage entry of its source. The admitted outage then drops the recovered entries, so
  the next recovery is admitted. Stale `_delivery_by_key` entries are consulted only
  through a holder key that is live in `_last_alert_at`, and that key's future is always
  the one written at its own admission. No stale-future leak changes an outcome.
- The tests encode WHY (they quote D-15/D-16 and name the reversed WR-R3-01 direction).
  Each one fails under the pre-D-16 rule (the old code returns False / keeps the record
  open). Every count assertion follows `_drain_ops_alert_tasks_for_tests()` and, in
  the caller tests, `_drain_recovery_tasks_for_tests()`. 198 tests passed in the three
  files at `124e14ead`.

One MEDIUM: D-16 moves the recovery close onto the caller's path, and a bound
derivation that assumed the close ran in a held task is now wrong.

## Narrative Findings (AI reviewer)

### Warnings

#### WR-D16-01 (MEDIUM, confidence 5): `PROBE_TICK_BOUND_S` and its comment still assume the recovery close runs in a held task; D-16 makes it inline, so the bound is now short by one or two open-page round trips

**File:** `analytics-service/services/mt5_validation_liveness.py:120-130` (bound and
comment). The pin is `analytics-service/tests/test_mt5_validation_liveness.py:787-805`.
The cause is in `analytics-service/services/ops_alert.py:528-533` together with
`analytics-service/services/mt5_outage_alert.py:461-473`.

**Issue:** The comment reads: *"a recovered notice's wait for its outcome runs in a
held task, so what the tracker awaits is ONE durable open-page read (a healthy reading)
or ONE write (an outage reading)"*. On that basis `PROBE_TICK_BOUND_S` budgets one
`_OPEN_PAGE_TIMEOUT_S` (5 s) for the tracker.

Before D-16, a recovered outcome was never decided when `page` returned, because only
the email could decide it. `_send_recovered` therefore always took the held-task branch.
After D-16, a Sentry-credited recovery resolves `delivered` before `page` returns. That
is now the normal production path, since the DSN is set. `_send_recovered` then takes the
`else` branch and awaits `_finish_recovered` inline, which awaits `close_open_page`, a
second bounded 5 s DB round trip.

On the restart path the tracker does `_durable_recovery_request` (read, 5 s) and then
the inline close (5 s). That is two open-page round trips against a budget of one. On
the in-process path the close is an extra round trip the derivation does not count.
`test_the_tick_bounds_cover_the_recovery_work_they_wrap` pins the old one-round-trip
sum, so it stays green on an under-budgeted bound. The plan's SUMMARY records only that
the held wait "now arises only when the Sentry capture fails". It does not carry that
fact through to this bound.

**Failure scenario:** A degraded Supabase (each open-page call near its 5 s cap)
coincides with a validation probe that also uses a large share of its lease wait and
thread bound. `wait_for(probe_validation_terminal, PROBE_TICK_BOUND_S)` fires during
the inline `close_open_page`. `_finish_recovered`'s `finally` marks the row stale and
discards `_DURABLE_CHECKED`, so the close is retried next tick (the suppressed repeat
returns the held True), but:

- the monitor logs "the validation terminal probe did not complete inside its bound",
  which blames the probe for a delay that came from the alert bookkeeping;
- under sustained DB slowness every tick re-reads and re-closes, and gets cut off again,
  until the hourly window expires. The next admitted recovery then sends a second Sentry
  capture and email for the same incident.

This is the R3-SFH-01 class ("a bound smaller than that sum cancels the very work it
wraps") coming back through the decided-inline branch.

**Fix:** Pick one of two options and make the comment and the pin agree with it.

1. Keep the close off the probe's path. In `_send_recovered`, always schedule
   `_finish_recovered` as a held task, so the "decided" case is no longer special and
   the derivation's premise becomes true again:
   ```python
   delivery = await ops_alert.page(source, cause, event="recovered", since=since, detail=detail)
   task = asyncio.get_running_loop().create_task(_finish_recovered(source, delivery))
   _RECOVERY_TASKS.add(task)
   task.add_done_callback(_RECOVERY_TASKS.discard)
   scheduled = True
   ```
2. Or budget for the inline close and fix the text:
   ```python
   #: ... A Sentry-credited recovered notice is decided at capture time (D-16), so its
   #: close runs INLINE: the worst case is the restart path's open-page read plus the
   #: close.
   PROBE_TICK_BOUND_S: Final[float] = (
       _MT5_RELOGIN_LEASE_WAIT_DEFAULT_S
       + _PROBE_THREAD_BOUND_S
       + 2 * ops_alert_open._OPEN_PAGE_TIMEOUT_S
   )
   ```
   Then raise the pin in `test_the_tick_bounds_cover_the_recovery_work_they_wrap` to
   `2 * open_s`, so the test can fail on this regression.
