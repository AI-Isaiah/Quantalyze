# 164.6.8 OUTAGEALERT - Silent-failure re-review, round 4 (SFH)

Scope: `git diff fcad37fed..44a410284 -- analytics-service/` (fixD). Round-3 findings
(R3-SFH-01, WR-R3-01, WR-R3-02, WR-R3-03) were checked against the diff.

## Round-3 fixes verified (no finding)

- Exception inside the held task: `_finish_recovered` (`services/mt5_outage_alert.py`) catches
  `Exception` around the wait and the close, logs class only, and its `finally` marks the record
  stale, un-marks the source and records a resend reason. A raise out of that `finally` is not
  reachable (a set add and a lock). A held task therefore cannot die with an unretrieved error,
  and the missing done-callback logger is not a gap.
- Cancelled task: `CancelledError` is not caught, so it reaches the `finally`; `closed` is False,
  so the record is marked stale, the source is un-marked and a reason is set (`delivered` picks
  the wording). A cancel that lands mid-close (UPDATE possibly committed) errs toward one extra
  read that finds no row. Same shape in `_close_after_recovered` (`services/mt5_validation_liveness.py`).
- `wait_for` timeouts: `await_delivery` turns a timeout into False, so the record stays open, is
  marked stale and is re-sent. Not treated as success. The 15 s wait exceeds the 10 s total POST
  deadline, so a slow-but-successful email is not mis-read as a failure.
- Recovered notice dropped silently: no path found. Every non-closing exit leaves the open record
  and removes the source from `_DURABLE_CHECKED`, so the next measured healthy reading re-sends.
  A task lost to process shutdown leaves the durable record open, so the next process re-sends
  (duplicate-safe direction).

## Findings (MEDIUM and above)

### F1 - MEDIUM (confidence 5/10): the in-process recovery path has no in-flight guard, so readings during the held wait re-enter recovery

- Where: `services/mt5_outage_alert.py` `_send_recovered` (the `create_task` branch) with
  `_durable_recovery_request` (guard at the top, `if source in _DURABLE_CHECKED`) and
  `note_outage_reading` (healthy branch).
- Scenario: a run ends on a healthy reading. `_advance_run` pops the run and returns the
  recovered request; `_send_recovered` sends the notice and holds the wait in a task. The source
  was never added to `_DURABLE_CHECKED` on this path (only the durable path adds it, at dispatch).
  While the held task waits (up to 15 s on a slow founder email), the next healthy reading for
  the same role finds no run, then calls `_durable_recovery_request`. The source is unchecked and
  the record is still open, so it builds a SECOND recovered request whose detail carries the
  default `_REASON_RESTART` text ("after the analytics service restarted"). That is false here,
  because no restart happened. It starts a second held task. Before fixD the wait was inline and
  serialized the role's readings; the held task removed that serialization without adding a
  guard. Most reachable for `ROLE_JOBS`, which is fed per session reading (not a fixed slow
  tick).
- Hidden/lost: the window suppresses a second recovered email for the hour, so the usual outcome
  is only noise. Second task closes a row the first already closed: `close_open_page` returns False
  and logs "an UPDATE matched no open row", marks the source stale with no row behind it, and
  sets `_RESEND_REASON` to the "close failed" wording. If the first email fails and releases the
  window before the second reading, the founder gets a recovered email with the wrong cause
  ("restarted").
- Fix: mark the source in `_DURABLE_CHECKED` (under `_LOCK`) at the start of `_send_recovered`,
  before `page`, so an in-flight recovery is never re-derived. `_finish_recovered` and the
  not-scheduled `finally` already un-mark on every non-closing exit. Add a test: two healthy
  readings while the first delivery future is pending produce one `page` call and one task.

## Observations below the reporting bar

- Behavior from WR-R3-01 (intended): a recovered notice is credited only on a 2xx email. With
  `SERVICE_KEY` unset or the route down, each healthy reading re-captures a recovered Sentry
  event and logs ERROR (loud, not silent), and the record never closes until email works.
- A new incident that records within the held window (needs a full blind run, so minutes of
  readings) would have its fresh row closed by the older task. Not reachable at current
  thresholds.
- Jobs-role healthy path can await two open-page reads (own source, debt source), each bounded
  at 5 s, under a tracker bound that now budgets one. A cancel there drops the healthy episode row
  only when the 5 s reads both time out; the reads existed before this diff.

Verdict: 1 findings (MEDIUM and above)
