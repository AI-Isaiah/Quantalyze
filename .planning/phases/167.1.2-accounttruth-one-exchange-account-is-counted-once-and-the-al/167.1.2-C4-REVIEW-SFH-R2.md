## Part 2: silent failures at HEAD

### HIGH

#### SFH-R2-01: every book-mode scenario commit returns a 409 that no refresh can clear (D-16, widened by the K1 fixes)

- **Location:**
  - `supabase/schema/baseline.sql:2250-2259` (`commit_scenario_batch` step 3b). The server builds the fingerprint from `DISTINCT ON (venue, symbol, holding_type) ... ORDER BY ... asof DESC` over **every** `allocator_holdings` row the allocator has ever had.
  - `src/app/(dashboard)/allocations/hooks/useScenarioState.ts:169-172`. The client builds its fingerprint from `holdingsSummary`, and a book draft carries it (`ScenarioComposer.tsx:4655-4659`).
  - `src/lib/queries.ts:4223` and `src/lib/latest-holdings-per-key.ts:179-309`. Since C4, `holdingsSummary` holds only each key's rows at its own latest reading. After K1 it also drops a key that a newer reading on the same account superseded (SFH-C4-01), and a key whose newer clean poll read nothing (SFH-C4-02).
- **Scenario:** an allocator once held BTC-PERP on Binance and closed it. BTC-PERP's last row (an older `asof`) is still in `allocator_holdings`, because persist only upserts and nothing deletes. Since D-16 the client's token set leaves `BTC-PERP:binance:derivative` out. The server's set keeps it. The allocator builds a scenario in book mode and commits. The RPC finds the two sets differ and returns `portfolio_fingerprint_stale`. The route turns that into a 409: "Your holdings were updated after you opened this scenario. Refresh to load the latest holdings, then re-apply your changes." (`src/app/api/allocator/scenario/commit/route.ts:713`). A refresh rebuilds the same client set, so every retry is refused the same way.
- **Before C4** the client collapsed over every date (the removed `.order("asof", …)` read with its all-rows collapse), so both sides produced the same set. D-16 opened the divergence. K1's SFH-C4-01 and SFH-C4-02 fixes widen it: each drops more triples on the client and none on the server.
- **Hidden path:** this is the 151 CR-01 class, "a remedy copy no refresh can satisfy". CR-01 closed it for blank mode. It now returns for book mode. The two fingerprint readers that the K1 report lists under WR-02 (the RPC fingerprint and the route's audit recompute) were checked only for the missing `api_key_id`, not for the per-key latest rule. There is no test pairing the SQL fingerprint with `holdingsSummary`.
- **Who is hit:** any allocator with at least one current holding and at least one triple that is no longer current. After a book has traded for a while, that is almost every allocator. An allocator whose book is now empty is not hit, because `""` becomes `null` and the RPC skips the check.
- **User impact:** the phase's scenario commit is a dead end for a live book. The error says the portfolio changed, and that is false. The logs show nothing wrong: the route answers with a handled 409.
- **Recommendation:** make the RPC's token set follow the D-16 rule, in the same release as the reader: each key's rows at its own latest reading, with the account-supersede and clean-poll rules. Alternatively, have the client send a fingerprint built by the same SQL rule. Then add a SQL gate in `supabase/tests/test_commit_scenario_batch_fingerprint_precondition.sql` whose fixture has a triple closed on an earlier `asof`, and assert the precondition passes with the reader's set. Until that ships, the PR text must say book-mode commits are refused for allocators with closed positions.

### MEDIUM

#### SFH-R2-02: the WR-01 line clears on the next FAILED poll, while the positions stay missing

- **Location:** `src/app/(dashboard)/allocations/HoldingsTabPanel.tsx:151-168`. The filter is `k.sync_status === "complete_with_warnings"`. The failure arm, `job_worker.py` `run_poll_allocator_positions_job`, stamps `_map_exception_to_sync_status(exc)`, and it writes no rows.
- **Scenario:** on day 5 a Binance poll is `complete_with_warnings`. The derivative read failed, and spot rows were written at day 5. On day 6 the poll fails outright, for example with a 429 or a venue error. That stamps a status other than `complete_with_warnings` and writes nothing. The key's latest rows are still day 5 spot only. Its newest clean poll is day 4 or earlier, which is older than the rows, so the SFH-C4-02 branch does not fire. Open Positions shows none of the key's derivative positions, and the WR-01 line is gone, because it reads the key's current status. The read-day note (SFH-C4-08) cannot fire either, because the key contributes no derivative rows to date.
- **Hidden path:** the docblock says "the line clears when a sync reads the positions again". It also clears when a sync reads nothing at all. It likewise disappears while the next sync is `syncing`, which is transient.
- **User impact:** open perps disappear from Open Positions with no sentence on the tab. The only trace is the key card's sync error on the Exchanges page.
- **Recommendation:** decide from the rows, not from the current status. The key's latest rows came from a poll whose event says `complete_with_warnings`, which is readable the same way `cleanPollDay` reads the event. Alternatively, keep the line while the key's newest successful event is `complete_with_warnings` and no clean event is newer. Add the "warnings, then a failed poll" arm to the test.

#### SFH-R2-03: SFH-C4-08's age note never fires for a one-key book, or for a book where every key is equally stale

- **Location:** `HoldingsTabPanel.tsx:96-124`. `newest` is the newest `asof` among the rows shown (`:107-110`), and a row is dated only when `r.asof < newest` (`:113`). `OpenPositionsTable` chips only `revoked` and `sign_in_failed`.
- **Scenario:** an owner has one Bybit key. It has failed with `error` for three weeks, or the owner disconnected it and nothing newer read the account. Its rows are the newest in the book, so no note is written, and neither status gets a chip. Open Positions shows three-week-old positions and marks as current. This is round 1's exact scenario ("a key failing with `error` for three weeks"), and the most common book shape.
- **User impact:** the fix covers only the multi-key case. The single-key owner, who has no newer row to compare against, still gets undated stale positions.
- **Recommendation:** date against the calendar rather than against the newest row, since the dashboard already knows today. Alternatively, date every row whose key is not live or whose last sync failed. Add a one-key arm to the test.

### LOW (recorded, routed nowhere)

- **SFH-R2-04: a same-day clean empty poll does not hide rows written earlier that day.**
  `latest-holdings-per-key.ts:225` requires `cleanPollAsof > latestAsof`. Persist only upserts
  (`allocator_positions.py` `persist_allocator_holdings`). So when a position is closed after the
  04:00 poll and the owner then syncs by hand the same day, the closed position stays shown until
  the next day's poll. A partial close behaves the same way, because the earlier row at the same
  `asof` is never removed. This is bounded to one day and existed before C4. It is still not what
  the owner expects after "I closed it, then synced".
- **SFH-R2-05: the reason precedence names a connected key when a departed key is the real bound.**
  `job_worker.py:10723-10734` and `departed-history.ts:258-268` check `live_firsts` before
  `covered` and `successor`. Example: departed A (Jan 1 to Jan 31), departed B (Feb 1 to Mar 1),
  live L (first day Apr 1), all on one account. A is included until Jan 31, but its card says
  "From the next day a key you still have connected reads this account". B reads February, not L.
  A COVERED key on an account that also has a live key likewise says "a key you still have
  connected reads the same exchange account over these days", when an earlier departed key reads
  them. The numbers are right; only the named cause is wrong. The precedence predates the fixes.
  SFH-C4-07 extends it to the covered case.
- **SFH-R2-06: an explicit `is_active: null` diverges between the twins.** Python
  `_is_live_key` (`job_worker.py:10498`) uses `row.get("is_active", True)`, which keeps an explicit
  `None`, and `bool(None)` makes the key departed. TS `isLiveKey` (`departed-history.ts:83`) reads
  `null ?? true`, which makes it live. The column is `NOT NULL`, so this cannot happen today. The
  new truth-table parity test has no null arm, so it would not catch the split.
- **SFH-R2-07: the Holdings notes are keyed by their own text.** `HoldingsTabPanel.tsx:476` and
  `:485` use `key={note}`. Two unlabelled keys on one venue produce the same sentence ("the Binance
  key"). React then warns about duplicate keys, and the two lines read as one key. Separately,
  `CCXT_POSITION_VENUES` (`:133-138`) is a hand copy of "every venue outside `NON_CCXT_VENUES`". A
  new ccxt venue would silently get no WR-01 line.
- **SFH-R2-08: the departed-history disclosure appears only on the Overview.** The Scenario
  composer and the other widgets (`ScenarioComposer.tsx`, `widgets/performance/*`) render the same
  ready curve from the same payload without the line.
  `grep -rn departedHistoryUnavailable src/app` finds only `AllocationDashboardV2.tsx`.

  dependency the daily refresh already accepts.

  (`latest-holdings-per-key.ts:199-304`). The `audit_log` read uses `idx_audit_log_entity`

- **INFO-3:** the Overview's `holdingsEmpty && !hasSyncing` early return
  (`AllocationDashboardV2.tsx:133`) also hides the new departed-history line. That return is the

  empty), and the line goes with it.
- **INFO-4:** `_utc_day` now returns None without logging (`job_worker.py:10511-10512`), and the key
  falls back to its last returns day. Postgres never produces a malformed `timestamptz`, and the
  fallback never adds a day past the key's own returns. A malformed stamp would still be invisible
  if it ever appeared, so a DEBUG line would cost nothing.

## Checked and clean

- **The `audit_log` read's failure modes.** An error on either per-key read returns `error` and
  never falls back to rows (`latest-holdings-per-key.ts:221-222`, `:236-237`). The read is scoped by
  `user_id`, `action`, `entity_type` and `entity_id`. RLS `audit_log_owner_read`
  (`user_id = auth.uid()`) matches the writer's `user_id=allocator_id` (`job_worker.py:1421`).
  `final_status` is filtered in the query and checked again in `cleanPollDay`. A malformed
  `row_count` or `asof` counts as no evidence. There is no cap to hit, because every read is
  `.limit(1)`.
- **`_utc_day` returning None never counts or drops a day beyond the key's own returns.**
  `end = _utc_day(...) or last` (`job_worker.py:10631`), then `until = min(end, last)`. It is the
  only parse site on the derive path (`grep disconnected_at` finds `:10631` alone). Liveness is
  decided from the presence of `disconnected_at`, never from parsing it.
- **The derive's split WARNING.** A departed key's row with a null anchor is recorded under its
  reason, or `unstamped` when it has none. A missing row is the remainder. Both leave the book as
  before (`job_worker.py:11294-11328`). The count arithmetic is exact.
- **The Overview flag.** `derivedPayload` is `derivedRow.payload`, and the compose writes `flags` at
  the payload's top level (`allocator_equity_compose.py:562`). The reader gates on
  `equityHistoryState === "ready"`, and the renderer on `!isRebuilding`. The two agree.
- **`departedHistoryCard`.** The switch is ON only when the decision is included and the key is
  anchored. It is disabled in every state where flipping it cannot change the book. A failed
  returns-day or anchor read shows `HISTORY_LOAD_FAILED` with the switch disabled, not a guess.
  `allocator_equity_derived_owner_select` allows the anchor read, so an RLS-empty result cannot
  pass for "missing".
- **The new reasons.** `same_account_as_earlier_key` and `same_account_as_connected_key_pending`
  have their own sentences in the not-included branch (`departed-history.ts:381-386`). Neither can
  be included: a covered or pending key is bounded to `0000-00-00`, so `countedUntil < first`. The
  included branch's default ("History included until X.") therefore never meets them. No other
  reader consumes the reason tokens (`grep` over `src/`, `analytics-service/services`,
  `routers` and `supabase/migrations` finds only the two twins).
- **rotate-secret's gate.** The pre-read error returns 500, and a missing row returns 404, before
  the gate runs. `is_active` is `NOT NULL`. The reset is decided once and reused by the WR-02 retry.
