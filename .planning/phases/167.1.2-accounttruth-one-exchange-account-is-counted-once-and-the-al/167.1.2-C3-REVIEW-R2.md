## Warnings

### WR-01: The paginated returns read is not a snapshot, so a concurrent key derive can make it skip or duplicate a row

**File:** `analytics-service/services/job_worker.py:10388-10395` (`_load_returns`), using `services/db.py:388-405` (`paginated_select`: OFFSET `range()` per page, one statement per page)

**Issue:** The read it replaced was one SELECT, so it saw one MVCC snapshot. That snapshot was truncated, but it was consistent. `paginated_select` issues a separate `range(start, end)` statement per page with no shared snapshot and no keyset. If a row is inserted or deleted, between two page reads, at a position that sorts before the next page's offset, every later row shifts by one:

- an insert shifts them back, and a row is read twice;
- a delete shifts them forward, and a row is never read.

That writer exists and runs at the same time, by design:

- The 05:30 UTC cron (`enqueue_derive_broker_dailies_for_allocator_keys`) fans out one `derive_broker_dailies` per key of the same allocator.
- The first key to finish enqueues this compose (`job_worker.py:5675-5690`).
- The other keys are still upserting today's `csv_daily_returns` row (an insert when the day is new) and running the ranged reconcile delete.
- The order is `api_key_id` first, so a write to a key that sorts earlier shifts every later page.

Consequences:

- **Skipped row:** a day inside a key's coverage with no return row. `portfolio_returns` carries the level with `r = 0` (`allocator_equity_compose.py:124-128`), which is the "a day with no sync read as zero" class this phase exists to remove. The curve can still be marked trustworthy.
- **Duplicated row:** `pd.Series(..., index=[dates])` (`job_worker.py:10620-10624`) accepts a duplicate index silently, and the compose gets one day twice.

**Why it does not heal quickly:** the later key's own compose enqueue collides with `compute_jobs_one_inflight_per_kind_allocator` while this compose is `running` (`baseline.sql:13290`: `status IN ('pending','running','done_pending_children')`). So the torn curve can stand until the next day's compose.

**Scope and severity:** this only affects allocators whose rows span more than one page (more than 1000 rows; 6 allocators in PROD, one with 2804, per fix D), and only when a write lands between page reads. The pre-fix read was strictly worse for those allocators: it was always wrong, not wrong only under a race. This is therefore a Warning on the fix, not a reason to revert it. The non-snapshot read is still a new shape of wrong data that the old read could not produce, and nothing detects it.

**Fix (pick one):**
- **Keyset pagination** on the total order, which inserts and deletes cannot shift. `or=(api_key_id.gt.<k>,and(api_key_id.eq.<k>,date.gt.<d>))` with `.not_.is_("api_key_id", "null")`, since the consumer drops NULL-key rows anyway (`:10429-10432`).
- A post-read guard that detects the duplicate half and retries, so the job stays transient rather than composing:
  ```python
  seen: set[tuple[Any, Any]] = set()
  for r in csv_rows:
      key = (r.get("api_key_id"), r.get("date"))
      if key[0] is not None and key in seen:
          raise RuntimeError("csv_daily_returns page shift: duplicate (api_key_id, date); retrying")
      seen.add(key)
  ```
  This does not catch the skip half.
- Read in one statement through a SECDEF RPC that returns a single `jsonb_agg` row. One row stays under `max_rows` and keeps one snapshot.

Whichever option is chosen, add a fake-backed test that inserts a row between page 1 and page 2 and asserts the compose either sees every row exactly once or does not compose.

### WR-02: The classifier's "rebuilding" class tells a wait for two reasons that the C2 decisions say are not waits, and the new test pins it

**File:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:60-76` (class doc and table); `ScenarioComposer.tsx:891-897` (the "being rebuilt" line); `ScenarioComposer.test.tsx:17178-17187` (`REASON_CLASSES` pins both rows)

**Issue:** The class doc (`:62-63`) says the `rebuilding` class is "a wait on a running job, or a hold no owner action heals in this release. The generic 'being rebuilt' copy is true for these." The `OWN_BOOK_REBUILDING_LINE` doc (`ScenarioComposer.tsx:883-890`) says "only a real wait says 'being rebuilt'". Two members contradict both statements, and the contradiction is in this repo's own recorded decisions:

- **`derivation_rejected`.** `queries.ts:3817-3819` (Review C2 SFH-05 / SFH-06): "a v2 row the reader rejected, or a read that failed, must not be shown as a wait". The Overview comment at `EquityHistoryRebuilding.tsx:129-130` repeats it: "is not a wait on the daily recompute, so neither line names one." The Scenario now tells exactly this book "Your book's own history is being rebuilt".
- **`shared_account_history_truncated`.** `EquityHistoryRebuilding.tsx:135-138`: "No action is named because none heals it in this release". Nothing is being rebuilt. The Overview line says the history "is not shown", and the Scenario says it "is being rebuilt".

The fixer followed round 1's recommendation, which listed `derivation_rejected` as passive. That recommendation conflicted with the C2 rule, so SFH-C3-01 is closed as specified and this finding is new. It is not a regression: before the fix, all 8 reasons said "being rebuilt". But the fix added a written claim that the sentence is true for these reasons, plus a test that locks the class in. A later reader will take both as settled. Mitigation: the Overview heading still reads "Your equity history is being rebuilt" for every reason (pre-existing, recorded by round-1 SFH as "Related"), so the two surfaces agree at heading level.

**Fix:** Add a fourth class, for example `held`, covering `derivation_rejected` and `shared_account_history_truncated`, with a Scenario sentence that states no wait:
```tsx

  <>
    Your book&apos;s own history is not shown right now, so the comparison
    with your current book is not shown. The Overview says why.
  </>

```
Move the two rows in `REASON_CLASSES`, and correct the class doc so it no longer claims "being rebuilt" is true for a hold. This is new user-facing copy, so it needs the founder's call (DESIGN.md Voice). Alternatively, keep the class and correct the two doc comments so they stop asserting the sentence is true there.

### IN-01: The Overview's `REASON_LINE[reason]` lookup is still unguarded, while the new classifier guards the same key

**File:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:261-268`

**Issue:** `equityHistoryRebuildClass` refuses prototype and unknown keys with `Object.hasOwn`, and the fix-B tests pin that on the Scenario (`"constructor"`, `"some_later_reason"`). The Overview branch next to it still does `reason ? REASON_LINE[reason]`:

- For `"constructor"`, that renders `Object`'s constructor function as a React child: nothing is shown, and a dev warning fires.
- For an unknown string, it renders an empty `<p>`.

This behaviour predates the fix, and the producer is server-side and typed, so it is not reachable today. The two surfaces now fail closed differently for the same input.

**Fix:** Guard the lookup the same way, e.g. `reason && Object.hasOwn(REASON_LINE, reason) ? REASON_LINE[reason] : null`, or route it through the classifier. Mirror the Scenario's fail-closed arms against `EquityHistoryRebuilding`.

### IN-02: The warm-up test's copy binding assumes the writer's N-1 relationship through its own fixture

**File:** `src/app/(dashboard)/allocations/AllocationDashboardV2.warmup.test.tsx:63-76`, `:152-175`

**Issue:** `readyShape` builds returns as `equityDailyPoints.slice(1)`, which hard-codes "one return per curve day after the first". The binding test derives "three" from the builder's threshold applied to that fixture. So a change to the builder's `< 2`, or to the copy, fails the test, as fix A measured. A change on the writer side does not: for example, `portfolio_returns` emitting a first-day return, or a reader change that trims returns. After such a change the copy is wrong and the test stays green. The copy's number depends on three layers, and the test binds two of them.

**Fix:** Optional. Pin the writer half in Python with a `portfolio_returns` test asserting `len(returns) == len(union) - 1` for a gap-free single key, cross-referenced from the JSDoc. This would also cover IN-05's missing Python pin.
