## SFH-01: a FAILED reconstruct counts as "bootstrapped", so the refresh closes the gate and the backfill is lost for good (HIGH, data integrity)

**Evidence.**

- The migration defines a BOOTSTRAPPED book as one where no qualifying key "lacks a compute_jobs
  row of kind reconstruct_allocator_history **in any status**". This is the `bk*` subquery in the
  refresh loop of `enqueue_refresh_allocator_equity_for_all`. A `failed_final` reconstruct row
  therefore marks the book as bootstrapped.
- `run_refresh_allocator_equity_daily_job` never looks at how the reconstruct ended. It reads the
  latest `allocator_holdings` rows (`_fetch_latest_holdings_per_eligible_key`) and persists a row
  for today whenever `breakdown` is non-empty. The holdings come from the poll jobs, which succeed
  or fail independently of the 30-minute reconstruct crawl.
- `run_reconstruct_allocator_history_job` has several routine ways to end `FAILED`:
  - `classify_exception` returns `permanent` for auth, permission, bad-request and invalid-token
    errors.
  - The crawl hits `_RECONSTRUCT_CRAWL_TIMEOUT_S` (transient). After `max_attempts` (default 3) a
    transient failure also ends `failed_final`.
  - The MT5 failure arms.
- **The sequence that loses the history:**
  1. The bootstrap enqueues a reconstruct.
  2. The reconstruct fails.
  3. The book counts as bootstrapped, so the same run or the next run enqueues the refresh.
  4. The refresh writes today's row, so `EXISTS (SELECT 1 FROM allocator_equity_snapshots aes …)`
     becomes true.
  5. From then on the book is a "book WITH snapshots". Arm N5 forbids sending such a book a
     bootstrap reconstruct.
  6. After 90 days `retention_compute_jobs_failed` deletes the `failed_final` row.

  After step 6 nothing in the database records that this key was never backfilled. The allocator's
  curve starts on the day of the first refresh, and a reader cannot tell it apart from a genuinely
  short history. The only trace is an `allocator.equity.reconstruct_failed` audit event.
- The same thing happens to a two-key book when one sibling's reconstruct succeeds and the other's
  fails. The successful sibling's rows close the gate on the failed one.
- The plan's register says this case is mitigated, and it is not:
  - **T-167.1.2-58** says "no first snapshot row closes the gate before every qualifying key's
    reconstruct **exists**". The threat is a key stranded at zero history, and a reconstruct that
    merely exists does not prevent it.
  - **T-167.1.2-42** and the migration header's "REPEAT BEHAVIOUR" say a book whose reconstruct
    "ends done or failed with no rows written is re-enqueued once that compute_jobs row is reaped".
    That holds only while the book stays at zero snapshots. It stops holding as soon as the refresh
    writes a row, and the refresh writes one whenever holdings exist.
- **Arm N4 locks the defect in.** It seeds a `failed_final` reconstruct on a zero-snapshot book and
  asserts `v_ref = 1`: the refresh MUST be enqueued. That refresh is the enqueue that closes the
  gate.
- **The two paths disagree (Rule 7).** `request_allocator_holdings_sync` treats only
  `status IN ('done','pending','running','done_pending_children')` as a prior reconstruct, so a
  failed reconstruct is retried on the next user sync. The cron path treats `failed` and
  `failed_final` as final.

**Fix.**

- In the "bootstrapped" test, count only a reconstruct row in an in-flight or `done` status. That
  matches the RPC's own gate. A book whose qualifying key's latest reconstruct ended
  `failed`/`failed_final` then stays un-bootstrapped: it gets no refresh, so no row closes the gate.
- Apply the same change to the book-selection (`bqj`) and per-key (`rkj`) copies, so that a failed
  key is re-enqueued under the cap. Choose one of two bounds:
  - add a re-enqueue back-off (for example, the latest failed row is older than N days), so a
    permanently refused key does not re-crawl every day; or
  - stop refreshing that book and surface it (see SFH-03). Do not refresh past a failed backfill.
- Re-write arm N4 so that it asserts the chosen semantics: no refresh for a zero-snapshot book whose
  only reconstruct failed. Add a sibling arm for a two-key book where one reconstruct is `done` and
  the other is `failed_final`.
- Correct T-167.1.2-42 and T-167.1.2-58 in the plan so that neither claims what the code does not
  do.

## SFH-02: an error in the new bootstrap loop now cancels the existing daily refresh for EVERY allocator, and the one race error that can occur is not the one caught (HIGH, user-facing)

**Evidence.**

- The bootstrap loop is placed inside the same `BEGIN … EXCEPTION WHEN OTHERS THEN
  pg_advisory_unlock(...); RAISE; END` wrapper, and BEFORE the refresh loop. Any error raised in the
  bootstrap loop unwinds the whole function, and the refresh loop never runs. Before this migration
  the refresh loop depended only on its own statements. After it, every allocator's
  `refresh_allocator_equity_daily` for that UTC day depends on the new code as well. Errors that
  can reach it:
  - the triple anti-join hitting `statement_timeout`;
  - a trigger or CHECK on `compute_jobs`;
  - a 40001.
- **The swallowed exception is the wrong class.** `_enqueue_compute_job_internal` inserts with
  `ON CONFLICT DO NOTHING`, so it never raises `unique_violation`. On a lost race whose winner has
  already moved past the in-flight statuses, it raises `serialization_failure` (40001), and its
  comment calls that the retry-safe signal. Both loops catch only `unique_violation`:
  - In the bootstrap loop, `EXCEPTION WHEN unique_violation THEN NULL; -- a racing first-connect
    call landed first; benign` is dead code.
  - A real 40001 falls through to `WHEN OTHERS` and aborts the run.
  - The gate's own header (lines 102-105) concedes that the swallow is inert: "removing the
    fan-out's unique_violation swallow … is inert".
- `compute_jobs.idempotency_key` is documented in `baseline.sql` as "NOT enforced at the DB level at
  all". So the header's reason for the swallow ("the cron path and the user path name one job; a
  unique_violation is swallowed as the RPC does") rests on a premise that does not hold.

**Fix.**

- Wrap each key's enqueue in both loops in its own sub-block that catches
  `unique_violation OR serialization_failure`. Emit `RAISE WARNING` with the key id and `SQLSTATE`,
  and continue.
- Wrap the whole bootstrap loop in a sub-block whose `WHEN OTHERS` does two things: emit
  `RAISE WARNING` (with `SQLSTATE` and `SQLERRM`) and record a failure (see SFH-03). Then fall
  through to the refresh loop.
- This isolation is safe by construction. A book whose reconstructs were never enqueued is not
  bootstrapped, so the refresh loop still withholds its refresh.
- Add an arm that forces the bootstrap loop to raise, for example with a fixture trigger on
  `compute_jobs` that refuses `reconstruct_allocator_history` for one seeded key. The arm asserts
  that a snapshot-book key in the same call still gets its refresh.
- Correct the header comments: the swallow guards nothing, and the idempotency key is a correlation
  label only.

## SFH-03: a failed or partial fan-out run leaves no trace anyone reads (MEDIUM)

**Evidence.**

- The function reports nothing about what it did:
  - no count of books bootstrapped, keys enqueued, or books deferred beyond `v_bootstrap_cap`;
  - on a lock collision, only `RAISE NOTICE '… another run holds the lock; skipping'`, and the cron
    run is still recorded as a success.
- `scripts/prod-prober/arms/cron-obs.mjs` watches `match_engine_cron` and the ledger fan-out only.
  `cron-manifest.json` jobid 17 `refresh-allocator-equity` (`SELECT
  enqueue_refresh_allocator_equity_for_all();`, `0 5 * * *`) is unwatched.
- A run that raises (SFH-02) is therefore visible only as a `cron.job_run_details` row, and nothing
  alerts on that row for this job.
- A backlog of zero-snapshot books larger than the cap drains at 25 keys a day, and nothing reports
  how long it is.
- The repo already has a precedent for this signal. `20260924120000_ledger_fanout_failure_count.sql`
  writes `candidate_enqueue_failed` rows, and the prober alarms on them.

**Fix.**

- End each run with one line:
  `RAISE NOTICE 'enqueue_refresh_allocator_equity_for_all: bootstrapped % book(s) / % key(s), deferred % book(s) beyond cap, enqueued % refresh(es), % bootstrap error(s)'`.
  This line lands in `return_message`.
- On any caught per-key or bootstrap-block error, write a failure row in the ledger fan-out's shape.
- Add jobid 17 to `cron-obs`. At minimum it should check "a run completed in the last 26 hours and
  its message names the function". Better, it should alarm on the failure rows.
- Also surface keys whose reconstruct ended `failed_final` on a zero-snapshot book (SFH-01).

## SFH-04: the qualifying predicate spends cap slots on keys whose reconstruct cannot succeed (MEDIUM)

**Evidence.**

- Qualifying excludes only `sync_status = 'revoked'`. `api_keys_sync_status_check` also admits
  `sign_in_failed`, `error` and `rate_limited`.
- A `sign_in_failed` key is enqueued a 30-minute reconstruct. The reconstruct fails `permanent` on
  the credential error, uses one of the 25 slots, and then feeds SFH-01: the book is bootstrapped
  by a failed row.
- Arm N2's matched-pair design covers `revoked` only.

**Fix.**

- Decide the eligible set explicitly, for at least `sign_in_failed`. The recommendation is to exclude
  it from QUALIFYING and leave it in the refresh population, so the user's re-sign-in goes through
  the RPC, which does enqueue the reconstruct.
- Write the decision in the header and pin it with an arm.

## SFH-05: residual R-12-1 is a data-integrity gap with no owner (MEDIUM)

**Evidence.**

- `167.1.2-12-SUMMARY.md` and the migration header record R-12-1 as "UNROUTED". The gap: a key added
  to a book that already has snapshots, whose first sync collided with an in-flight poll, never gets
  a backfill.
- Nothing signals it. The key's history is silently missing from the aggregated legacy curve.
- The repo's deferral rule says a data-integrity residual must name a phase. A PR-description
  sentence is not a queue.

**Fix.** Route R-12-1 to a phase with `/gsd-phase --edit` before PR C merges, and cite that phase in
the migration header in place of "unrouted". An alternative, cheaper and closer to the root cause:
move `request_allocator_holdings_sync`'s reconstruct gate AHEAD of its `already_inflight` early
return, so a colliding connect still enqueues the reconstruct. This is a narrower change than
"re-base the RPC", and it removes the residual.

## SFH-06: comments claim a dedup and a race guard the code does not provide (LOW)

**Evidence.** Three places:

- The migration header edit (3) says the reused `-initial` idempotency key makes "the cron path and
  the user path name one job".
- Arm Z2's message says the same.
- The inline comment on the swallow reads "a racing first-connect call landed first; benign".

Dedup is actually done by `compute_jobs_one_inflight_reconstruct_per_api_key`, the in-flight partial
unique index, together with the enqueue helper's in-flight pre-check. `idempotency_key` is not
enforced. Arm Z2 bites (it reads the stored string), but what it protects is a correlation label.
It does not protect job identity. A future editor who trusts the comment could remove the any-status
`NOT EXISTS` and expect the key to dedup a `done` or `failed` row, and it would not.

**Fix.** Rewrite the three comments to say what the code does: the in-flight index dedups, the
any-status `NOT EXISTS` blocks re-enqueue, and the key is a correlation label. Either reword Z2's
failure text to match, or drop Z2's claim about job identity.

## SFH-07: a regression in ONE per-key (`rk*`) copy passes the whole gate (LOW)

**Evidence.**

- The mutations for N1, N2, N3, N3b, N3c and N6 edit several copies at once. Every negative-control
  book holds only the excluded key, so the book-selection copy (`bq*`) keeps that book out of the
  loop whether or not the per-key copy (`rk*`) filters.
- No fixture pairs a qualifying key with an excluded key on the same zero-snapshot book, so the
  `rk*` copies are never the only filter. Each of these single-copy deletions leaves every arm
  green:
  - `rk.disconnected_at IS NULL`
  - `rk.sync_status IS DISTINCT FROM 'revoked'`
  - either `rk*` strategy-link term
  - `lower(rk.exchange) <> 'deribit'`
- Group B's target book is the one mixed book: an `okx` key plus a `deribit` key. It asserts only
  `k_td`'s refresh, not that `k_td` has no reconstruct.
- The result would be a 30-minute reconstruct for a disconnected, revoked, manager-linked or Deribit
  key. The gate claims to pin exactly this ("each mutation names ONE copy … so an edit of one copy
  is never inert").

**Fix.**

- Add one mixed-book group: a qualifying `okx` key plus one each of disconnected, revoked, live-linked
  and Deribit keys, all on one zero-snapshot book. Assert that exactly one reconstruct is enqueued
  and that it belongs to the qualifying key.
- Give each `rk*` term its own single-copy RED-UNDER-M.
- Alternatively, extend group B to assert `k_td` has zero reconstruct rows, which covers the Deribit
  copy.

## SFH-08: minor items, no action required for merge (INFO)

- **The self-verify reads fixed strings only (acknowledged in its header).** It passes on a body
  whose bootstrap loop is dead (for example `EXIT WHEN TRUE` before the enqueue), because it checks
  only for the `'reconstruct_allocator_history'` and `v_bootstrap_cap` strings. That is acceptable
  only because the gate's arms carry the behaviour. Keep the gate mandatory in `sql-tests`.
- **Rollback: `SET lock_timeout` is session-scoped.** The rollback runs `SET lock_timeout = '3s'`
  inside `BEGIN`, not `SET LOCAL`, so the setting outlives the transaction on that session. This is
  harmless for a one-shot psql run.
- **Rollback: the post-verify checks less than the migration's self-verify.** It does not assert
  that `service_role` keeps EXECUTE, and it does not check that the three roles exist, as the
  migration's self-verify does.
- **Rollback behaviour change: revoked keys are refreshed again.** The rollback restores 075's body
  verbatim, and that body refreshes revoked keys every day. The migration fixed this as its edit
  (1). The rollback header should say so, so a revert does not silently restore it.
- **Pre-existing: a lock-collision skip counts as a success.** The skip path returns success to
  pg_cron, so a stuck `daily_equity_refresh` lock cannot be seen. SFH-03's summary line would make
  the skip visible.
