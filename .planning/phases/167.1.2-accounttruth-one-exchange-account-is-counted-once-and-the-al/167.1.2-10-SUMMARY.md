# Phase 167.1.2 Plan 10: Legacy daily refresh carries quiet keys and counts one account once Summary

**`run_refresh_allocator_equity_daily_job` now sums each eligible key's holdings at that key's own latest `asof` on or before today. A key that has not polled yet is carried, not read as $0. A key marked as a duplicate of a working holder, or as a composite member of an eligible holder, is left out, so one exchange account is counted once. The persisted row is the same whichever key's job writes first.**

## Accomplishments

- `_fetch_latest_holdings_per_eligible_key(supabase, allocator_id, today_iso)` loads the allocator's `api_keys` (`id, is_active, sync_status, disconnected_at, account_share_kind, account_shared_with_api_key_id`) and keeps the keys that pass `eligible_key_predicate`, imported from `services.allocator_equity_derive` rather than copied. For each counted key it reads that key's latest `asof <= today` and then that key's rows at exactly that `asof`. It returns the rows plus `eligible_keys`, `carried_keys` and `excluded_shared_keys` counts. There is no staleness horizon. A key is carried for as long as it is eligible.
- `_counted_through_holder` applies the D-01/D-04/D-11 exclusion in one place, inside the helper.
- The summation below the read is unchanged: the Deribit skip, the derivative uPnL rule, `perp_upnl_missing`, `_cap_breakdown` and `persist_equity_snapshots` are all untouched. The snapshot table, its unique key and every reader of the store are also untouched.
- The `refresh_complete` audit metadata (both the written and the `no_holdings_today` branches) and the log line carry the three counts. They never carry a USD figure or a key id beyond the job's own key, which was already there.

## Known limitations (recorded, not fixed here)

- **Per-key attribution is only approximate when two live keys share a venue.** `persist_allocator_holdings` upserts on `(allocator_id, venue, symbol, asof)`, so a holdings row's `api_key_id` belongs to whichever key polled last. If two keys write the same venue and symbol on one day, the later one claims the row. The earlier key's latest `asof` then covers only the symbols the later key did not overwrite. This is the unique-key defect that D-08 re-scopes into Phase 167.1.1. Plan 10 does not touch the holdings writer or its index.
- **The provisional working-holder definition leaves one gap.** A holder with `is_active = false` that is neither disconnected nor revoked counts as working for a `'duplicate'`, so its duplicate is left out. But that holder is not eligible, so neither key's holdings reach the sum. The COMMENT marks this definition PROVISIONAL, and plan 04 decides it with the founder. This plan follows the COMMENT so that every reader of the marker agrees.
