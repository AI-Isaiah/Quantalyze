## Findings

### RLS-R2-01 — INFO — The new bootstrap sub-block and per-key handlers widen no privilege and leak no row

Evidence: the fix round added three things to the body:
- a nested `BEGIN ... EXCEPTION WHEN OTHERS` around the bootstrap loop;
- a per-call `EXCEPTION WHEN unique_violation OR serialization_failure` in both loops;
- a `coalesce(<alias>.sync_status, '') NOT IN ('sign_in_failed', 'error')` term in every QUALIFYING copy.

None of them changes who can call the function, which role it runs as, or which rows it reads. The
function still takes no arguments and returns VOID. From a tenant angle, the swallowing sub-block fails
safe. A bootstrap error rolls back that run's reconstruct rows to the sub-block savepoint. The refresh
loop's bootstrapped test (`bk`/`bkj`) then finds that owner's book NOT bootstrapped, so the loop cannot
write a first snapshot row for it. A swallowed error cannot make one owner's book be enqueued under
another owner's key: every enqueue still passes the loop key's own `api_keys.id`.
Fix: none.

### RLS-R2-02 — INFO — The new WARNING text names an api_keys.id, and only privileged roles can read it

Evidence: the fix round added three RAISE WARNING statements:
- `reconstruct enqueue skipped for api_key % (SQLSTATE %)` in the bootstrap loop;
- `refresh enqueue skipped for api_key % (SQLSTATE %)` in the refresh loop;
- `the bootstrap loop failed and was rolled back ... (SQLSTATE %: %)`, which interpolates `SQLERRM`.

What reaches the text:
- The key id is an opaque UUID, not a credential. No `api_key_encrypted`, label, exchange, balance or
  email is interpolated.
- `SQLERRM` carries only the message, never `PG_EXCEPTION_DETAIL`, so row images from a constraint
  violation do not reach it.
- The enqueue helper's own RAISE texts (`enqueue_compute_job`) interpolate at most UUIDs
  (strategy, allocator and api-key ids, and `auth.uid()`).

Where the text goes:
- The server log. On Supabase, only project members can read it.
- The calling session. Only `postgres` (pg_cron) and `service_role` hold EXECUTE, and anon and
  authenticated are refused by the ACL above.

PostgREST does not relay notices or warnings to HTTP clients. No anon or authenticated read path to the
text exists.
Fix: none. If a later edit interpolates `PG_EXCEPTION_DETAIL`, or any `api_keys` column other than `id`,
into these messages, re-audit.

### RLS-R2-03 — INFO — RLS-03's owner term is intact in all eight copies, and still no arm pins it

Evidence: every discriminator copy keeps `<strategy alias>.user_id = <key alias>.user_id` (count 1 each,
listed above). The fix round added no arm that mutates it. The arms that touch the discriminator
(`N3`, `N3b`, `N3c`, `M3`, `M4`, `E`) neuter the link halves or the archived term. None of them seeds a
`strategy_keys` or `strategies` row owned by a DIFFERENT user that names the key. REVIEW-FIX recorded
RLS-01 to RLS-05 as "not fixed (INFO; no action asked)", so this matches the brief and is not a
regression.
What stays open: the `strategy_keys_owner` policy's WITH CHECK does not constrain `api_key_id`, so an
authenticated user B can still insert a `strategy_keys` row naming user A's key. Today the owner term
neutralises that row, so it cannot suppress A's bootstrap or refresh. A future edit that drops the term
from any copy would not turn the gate red, and B could then suppress A's reconstruct and refresh (an
availability and integrity effect on A's equity book, not a read leak).
Fix (optional, test-only): add one arm. Seed user B's non-archived strategy plus a `strategy_keys` row
naming user A's unlinked key on a zero-snapshot book. Assert A's key still gets exactly one reconstruct
and one refresh. Pair it with a RED-UNDER-M edit that replaces each `<s>.user_id = <k>.user_id` with
`TRUE`, in all four `strategy_keys` copies, or in one copy per arm as `M3`/`M4` do.

### RLS-R2-04 — INFO — The fixture trigger is confined to the gate's transaction and to the gate's own key

Evidence: the gate opens with `BEGIN;` (after the RED-UNDER-SETUP header) and closes with `ROLLBACK;`
as its last statement, and contains no COMMIT, SAVEPOINT release or `END;` at top level. Groups X1, X2
and X3 each:
- create `public._fanout_boot_refuse()`, which is SECURITY INVOKER and has no grants;
- create a `BEFORE INSERT` trigger on `public.compute_jobs` whose `WHEN` clause matches only
  `NEW.api_key_id = <that group's own freshly generated key>` and one `kind`;
- call the fan-out inside a caught sub-block;
- then run `DROP TRIGGER` and `DROP FUNCTION` before their assertion.

If an assertion RAISEs, the transaction aborts and the DDL rolls back with it. No other tenant's insert
can match the `WHEN` clause, and no other session can see the uncommitted trigger. The one side effect:
`CREATE TRIGGER` takes a SHARE ROW EXCLUSIVE lock on `compute_jobs` and holds it until the ROLLBACK, so
on a SHARED database other writers to `compute_jobs` would block for the rest of the file. `sql-tests`
now runs on its runner-private local stack, so this is not reachable in CI. It is recorded for anyone who
runs the file by hand against shared TEST.
Fix: none needed for CI. Do not run this file against shared TEST or PROD by hand.
