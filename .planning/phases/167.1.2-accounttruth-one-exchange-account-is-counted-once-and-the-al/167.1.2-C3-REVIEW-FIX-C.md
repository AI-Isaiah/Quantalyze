### IN-05: a trustworthy v2 row with a one-point curve and no returns reads `derivation_rejected`

**Files modified:** `src/lib/queries.test.ts`
**Commit:** `12d4241af`
**Applied fix:** test only. The IN-05 arm in `derived-row outcomes` pins the current behaviour. The arm:
- sends `{version: 2, is_trustworthy: true, curve: [1 point], returns: []}`
- asserts `derivedPayloadRejection` gives `"malformed"`, the state is `rebuilding`, the reason is `derivation_rejected`, and both arrays are empty
- adds a contrast with the `v2()` fixture (one point, one return), which is `ready`

The comment cites the writer by symbol.

**Status: unreachable from the HEAD writer, so the current mapping stays.** The row is persisted by `job_worker.py` (`run_derive_allocator_equity_job`) and `allocator_equity_compose.py`. `allocator_equity_derive.py` provides the math only. The chain, read at `e9050c346`:
1. In `job_worker.py`, the key-mode branch of `run_derive_broker_dailies_job` has an `int(returns.notna().sum()) < 2` gate. A key with fewer than 2 interpretable days writes no `csv_daily_returns` rows. It writes only its `key_inputs`, and the compose classes it as DROPPED_KEY, which is untrustworthy. The later ranged reconcile delete covers only a span that has at least 2 rows. So every per-key series the compose reads has at least 2 days.
2. `replay_key_equity` keeps every return day and adds flow days. It returns `None` on zero days, never a one-point series.
3. `allocator_equity_curve` sums over the union of the anchored keys' days, so the curve has at least 2 days.
4. `portfolio_returns` looks at the union's second day. The key that opened on the first day has a positive level on both days, since non-positive equity raises. So `returns` is non-empty whenever the curve is.
5. The B2 branch of the compose handler deletes the row when the curve is empty.

So this shape means the writer broke its own contract. That is the case `derivation_rejected` and its Sentry capture exist for. Mapping it to `awaiting_derivation` would hide that anomaly behind a "wait for the recompute" line that no recompute would change.

**Neuter → RED → restore → cmp:**
- I made a byte backup of `queries.ts`.
- Neuter: the producer mapping sent `rejection === "malformed"` to `awaiting_derivation`.
- The arm went RED: `expected 'awaiting_derivation' to be 'derivation_rejected'`.
- I restored the file from the backup. `cmp` was clean and `git diff --quiet` was clean, and the arm passed again.

**Residuals, recorded and not fixed:**
- *Unmeasured:* a `csv_daily_returns` key row written before the `< 2` gate existed, with exactly one row, would give this shape for a single-key book. The code cannot rule that out. Only a PROD count can.
- *Out of scope, reported for the orchestrator, possibly data-integrity:* the compose's `_load_returns` in `job_worker.py` reads `csv_daily_returns` for an allocator with a bare `.select().eq().execute()`. There is no pagination and no order. `TODOS.md` records a PROD measurement where an unbounded select returned exactly 1000 rows from a 7351-row table (PostgREST `max_rows`). `supabase/config.toml` sets `max_rows = 1000`. For an allocator with more than 1000 rows, the compose would get an arbitrary subset of each key's series, and the curve would be wrong without any error. This does NOT reach the IN-05 shape: that needs every counted key to arrive with at most one row. But it is a separate reading of the writer that someone should measure. I did not verify it against the live table and did not touch the file (read-only for this fixer).
