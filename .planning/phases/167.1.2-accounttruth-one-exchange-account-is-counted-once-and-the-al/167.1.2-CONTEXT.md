## Phase Boundary

Two defects, one surface ("My Allocation"):

1. **Account identity.** Nothing stops two api keys that read the SAME exchange account from both
   counting in an allocator's book. `api_keys.venue_account_id` is NULL for every ccxt venue, so the
   existing fence `api_keys_user_exchange_venue_account_uniq` never fires for them.
2. **Equity history.** The curve on My Allocation is the legacy `allocator_equity_snapshots`
   patchwork (first-writer-wins, a non-polling key read as $0), and its returns are recomputed from
   $-levels, so deposits and keys joining or leaving read as returns ("Sharpe 1.44 beside −42.8%").

**In scope:** capture the venue account id at connect for OKX, Bybit, Binance and Deribit; refuse a
second live key on an account already connected; a named cleanup path for duplicates that already
exist; hide the broken curve first; rebuild the history as a per-account, flow-neutral series with
KPIs read from its returns; keep departed accounts' history up to their departure day, with an
include/exclude toggle; fix the legacy daily refresh's $0 defect; the scenario honesty fixes and the
three small fixes of success criterion 5; a read-only PROD census and the recompute after merge.

**Out of scope:** keying holdings per key in `holdingScopeKey` or the `allocator_holdings` unique
index (Phase 167.1.1, re-scoped after this phase per D-08); retiring the `allocator_equity_snapshots`
store (it still has readers: match.py, compare, GDPR export, SQL cron); sFOX account identity (D-10).

- **D-04 (orchestrator, research OQ2): measure in code whether two live composite members can sit

  and the refusal. Never a silent DROP+CREATE of `add_wizard_composite_key`. If a DROP is

  the stitch accepts it.
  (c) Nothing disconnects a member whose declared window has closed, so both member keys stay live
  (`disconnected_at IS NULL`) and both are polled by the role-agnostic poll fan-out.
  (d) The composite add route's own 23505 arm calls the venue-identity collision "unreachable" only
  because the RPC writes no identity. That stays true after this phase.
  **Therefore:** the exemption token is `composite_member`. It applies when the key and the live
  holder of its account id are both members of one composite strategy with disjoint declared
  windows. The stamper records the pair (`account_share_kind = 'composite_member'`) instead of a
  duplicate. The refusal path is exempt by construction (the composite RPC stays untouched and still

  `20260814120000` does not arise. A standalone key on an account that a composite member already
  holds is a real duplicate and is refused or marked like any other. — Reversibility: reversible.

- **D-06 (orchestrator, research OQ4): returns are the exact return of the summed book, with
  dynamic capital weights.** `r_t = Σ_k E_{k,t−1}·r_{k,t} / Σ_k E_{k,t−1}` over the keys present on
  both `t−1` and `t`, where `E` is the replayed per-key equity and `r_k` the key's own flow-adjusted
  return (0 on a carried day). This is flow-neutral: deposits, withdrawals, a key joining and a key
  leaving are never returns. Over the surviving set S (keys present on both days) it equals
  `Σ_{k∈S}(E_{k,t} − F_{k,t}) / Σ_{k∈S} E_{k,t−1} − 1`, because `E_{k,t} = E_{k,t−1}(1 + r_{k,t}) +
  F_{k,t}`. That identity is pinned as a test. **Phase 115's static D1 weights (`_current_equity_weights`,
  today's anchor share) are REJECTED for the book curve**, with this reason: they weight every
  historical day by today's capital mix, so a key that held 5% of the book in March and 60% today
  drives March's return at 60%. That is not the return the allocator earned, and on a book whose
  capital moved between keys it produces exactly the Sharpe-vs-cumulative contradiction the
  founder saw. D1 stays in place for any other caller of `blend_concurrent_returns`; only the book
  curve's persisted `returns` use D-06. KPIs read `payload.returns`, never
  `equityCurveToDailyReturns(curve)`. — Reversibility: reversible (a payload field).

- **D-07 (orchestrator, research OQ5): fix `run_refresh_allocator_equity_daily_job` in this
  phase — carry forward and never count a non-polling key as $0.** Reason: same defect, same

### Planner decisions (recorded with evidence)

- **D-09: "departed" means soft-disconnected OR credential-revoked, and each has an end day.** A
  disconnected key ends on the UTC day of `disconnected_at`; a revoked key (`sync_status =
  'revoked'`, never disconnected) ends on its last `csv_daily_returns` day, because that is the last
  day its data is real. Revoked keys are not polled (`enqueue_poll_allocator_positions_for_all_keys`
  skips them) and are not "disconnected" in the founder's word, but their data stops the same way.
  Both get the toggle.
  **Default inclusion (the founder's words set the default to "included"):** a departed key is
  included up to its end day UNLESS the compose cannot show it is a DIFFERENT account from a key
  already in the book. Three cases:
  (1) its `venue_account_id` is known and no other COUNTED key holds it: INCLUDED. "Counted" means
  the live keys AND the departed keys already included, never the live keys only. Otherwise two
  departed keys on one account would both count on the same days (plan check B4, 2026-09-25);
  (2) its id equals another counted key's id, live or departed (a rotation on one account): the keys
  sharing that id are ordered by first returns day (then last returns day, then id). Each is
  INCLUDED only for days BEFORE the next key's first returns day, because that key carries the
  account's history from then on. The last key in the group runs to its own end day. The successor's
  day is its first `csv_daily_returns` day in BOTH the compose and the overview, never `created_at`
  (plan check W5). On no day do two counted keys share a known account; the compose checks this
  over the whole counted set and fails closed;
  (3) its id is NULL (it departed before this phase stamped anything, so identity can never be read
  again from a revoked or disconnected credential): EXCLUDED BY DEFAULT, shown in the overview with
  the reason, and the owner can include it.
  Case (3) is the one place the default departs from "included". The reason: an unknown-identity
  departed key that read the same account as a live key would silently double-count that account
  again, which is the defect this phase exists to remove. The owner, who knows which account it
  was, decides. The owner's 'include' overrides only this case (3) default. It never re-opens the
  overlapping days of a known shared id in case (2). 'exclude' always excludes.
  **FOUNDER-CONFIRMED 2026-09-25 (AskUserQuestion during plan revision):** a departed key whose
  account identity is unknown is EXCLUDED by default, shown in the overview with its reason, and the
  owner can include it. Case (3) is therefore a founder decision, not only a planner default. A hard-deleted key's rows no longer exist and cannot be shown. Plan 09 measures
  what `delete_allocator_api_key` removes and, if it removes history, the Delete confirm says so.
  — Reversibility: reversible.
