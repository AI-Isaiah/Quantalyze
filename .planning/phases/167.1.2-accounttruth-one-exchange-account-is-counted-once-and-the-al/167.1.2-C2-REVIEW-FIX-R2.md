### R2-CR-01: CR-04's emptiness proof was judged on the key's CURRENT status

**Files modified:** `analytics-service/services/job_worker.py`, `analytics-service/services/equity_reconstruction.py`, `analytics-service/tests/test_refresh_allocator_equity_carry_forward.py`, `analytics-service/tests/test_allocator_positions.py`
**Commit:** `1b7f9e4c2`
**Status:** fixed: requires human verification

**Applied fix.**
- The proof is now the proving poll's own recorded outcome, as the orchestrator decided.
- **Where the outcome lives.** `compute_jobs` records no outcome, because `mark_compute_job_done` takes none. The only fenced metadata writer, `set_compute_job_progress`, hard-codes `member_progress`, and a migration is out of scope. So the record used is the `allocator.holdings.sync_completed` audit event that the poll handler already emits on its success path.
- **Writer.** That event now carries `final_status` (`complete` / `complete_with_warnings`) beside the existing `row_count`.
- **Reader (`_polled_empty_since`).** It reads `audit_log` for that action, keyed by `entity_type = 'api_key'` and the ccxt members' ids, with `created_at` on or after the day after the latest `asof`. The `(entity_type, entity_id)` index serves it. The read is bounded to 200 events, newest first.
- **The proof rule.** There must be at least one event with `final_status == 'complete'` and `row_count == 0`, and no event with `row_count > 0`.
- **Removed:** the current-status gate. **Kept:** the ccxt-venue gate. "No proof ⇒ carry" and "read error ⇒ raise" are unchanged.

**Test evidence.**
- RED (8 failed): both arms of `test_account_polled_empty_after_its_last_row_contributes_zero`, and all 6 arms of the new `test_proven_empty_account_stays_zero_whatever_the_keys_current_status`. The arms cover current status `complete`, `rate_limited`, `syncing`, `idle`, `complete_with_warnings` and `error`, each over a clean empty poll from yesterday.
- GREEN: 142 passed across the refresh and allocator-positions suites.
- The no-proof guards now cover:
  - no recorded poll;
  - a poll on the rows' own day;
  - an outcome of `complete_with_warnings`;
  - a `sync_failed` event;
  - a poll that wrote rows;
  - a pre-change event without `final_status`;
  - MT5.
- `test_run_poll_allocator_positions_job_emits_sync_completed_audit_on_done` pins `final_status` in the event.

**What it changes, stated plainly.**
- **The proof no longer expires with the 30-day `compute_jobs` retention.** Hot `audit_log` keeps rows for 2 years.
- **Deploy-day transition.** Events written before this deploy have no `final_status`, so they prove nothing. An account proven empty under round 1 is therefore carried at its last balance again until its next poll writes a new-shape event (the 04:00 poll, one day at most).
- **A dropped audit row** (`_emit_audit` never fails the poll) also means no proof, so the account is carried. That is the safe direction.
- **Nothing else parses that event's metadata.** `git grep sync_completed` over `src`, `scripts`, `supabase/migrations`, `analytics-service/services` and `analytics-service/routers` finds only the action literal (`src/lib/audit.ts`, `services/audit.py`), its entity-type map and test, and this writer and reader. No strict schema reads the metadata, so the added `final_status` key breaks no consumer.

### R2-CR-02: an unmarked credential rotation was counted twice by the refresh

**Files modified:** `analytics-service/services/equity_reconstruction.py`, `analytics-service/tests/test_refresh_allocator_equity_carry_forward.py`
**Commit:** `81210273c`
**Status:** fixed: requires human verification

**Applied fix.** The orchestrator's rule, applied per account group:
- A group is **not carried forward** when all three hold:
  1. none of its eligible keys is working under D-18;
  2. none of its keys (departed ones included) carries a `venue_account_id`;
  3. every eligible key is on a venue that stamps one (`VENUES_WITH_ACCOUNT_ID` from `services/account_identity.py`: okx, bybit, binance, deribit).
- Only its same-day rows count, which is main's pre-C2 behaviour for such a key.
- The refresh now selects `venue_account_id`.
- The count goes to the new `identity_unknown_not_carried`, in both `refresh_complete` audit arms and in the INFO log line.
- The derive is unchanged. The reader already holds that cell under `key_not_syncing`, per the review's matrix.

**What this trades away (the orchestrator's decision, pinned by a test).** A genuinely separate account behind a failing key that was never stamped drops out of the day's row on a day it has no rows, exactly as on main. Nothing can tell it apart from the old half of a rotation. `test_a_separate_account_behind_a_failing_unstamped_key_drops_out_on_a_quiet_day` asserts this, and the audit counts it, so the drop is not silent.

**Kept deliberately (the venue gate).**
- A failing MT5 or sFOX key is unstampable by design, not "unknown", so it keeps its carry.
- Without this gate, an MT5 key in `error` would have left the legacy series on every day it failed. The MT5 gateway's `-10005` wedge makes that common.

**Test evidence.**
- RED (7 failed). The reviewer's rotation measured **2000.0** where the account holds 1000, for both `error` and `sign_in_failed`.
- GREEN: 153 passed (refresh and equity_reconstruction). All 287 refresh-related tests passed.
- Arms:
  - the rotation (2000 → 1000);
  - the separate-account trade;
  - a working unstamped key, still carried;
  - a failing stamped key, still carried;
  - a failing MT5 key, still carried;
  - same-day rows of an identity-unknown failing key, still counted.

**Residual, not in the orchestrator's scope.** Two WORKING keys on one account, both unmarked with at least one id NULL (a stamp that came back `no_id` / `skipped_no_budget`, or the day before the first post-C1 poll), can still both be carried while that state lasts. The review names this. The stamper normally closes it within a poll.

### SFH-R2-03 (high) / R2 IN-01: working-first dropped a failing key's older history under a benign flag

**Files modified:** `analytics-service/services/allocator_equity_derive.py`, `analytics-service/services/allocator_equity_compose.py`, `analytics-service/services/job_worker.py`, `analytics-service/tests/test_derive_allocator_equity_job.py`
**Commits:** `bb9a152e1` (fix); `3d1821f8e` (a test that pins the not-stitched case of a working key with no returns)
**Status:** fixed: requires human verification

**Applied fix: STITCH, not drop.**
- **New pure helper, `stitch_shared_account(links)`,** in `allocator_equity_derive.py`. It orders the members by first return day, with the counted (kept) member last, which is D-09 case (2) ordering:
  - each older member owns the days from its own first return day up to, not including, the next member's first day;
  - the kept member owns every day from its own first day on.
- **Flows follow the same ownership.** A day's flows come from the member that owns that day, and the first member keeps its pre-window flows. So a newer key whose crawl reaches back over the older key's days cannot double a deposit.
- **The derive** records, per group, the non-kept eligible members whose returns start before the kept key's. It loads their returns and their `key_inputs` flows (both were skipped before) and replaces the kept key's series and flows with the stitched ones.
- **Unchanged:** the kept key's anchor still ends the replay, and the account is still ONE counted key (`n_keys` 1).
- **New benign flag:** `shared_account_history_stitched`.

**When the join cannot be made honestly (the orchestrator's fallback).** The kept key stays alone and the new **BLOCKING** degrade reason `shared_account_history_truncated` makes the curve untrustworthy. It is also logged at WARNING, with counts only. Three cases trigger it:
- an older series ends before the day before its successor starts, which leaves a gap nobody's returns cover;
- the older member has no `key_inputs` row, so its flows are unknown;
- that row's `anchor_null_reason` is `flow_drop`, meaning its flows were cut as non-finite and cannot level those days.

**The new kwarg.** `compose_allocator_equity` gained a `degrade_reasons` kwarg for reasons the caller finds, a sibling of `benign_flag_tokens`.

**Not stitched, on purpose.**
- **A kept key with no returns yet.** Its anchor is today's equity, and hanging it on an older member's last day would misdate it. The compose already drops such a key as `DROPPED_KEY` (untrustworthy). This is the case the SFH reviewer named as a hidden error. `test_a_working_key_with_no_returns_yet_is_not_stitched_and_the_book_is_not_trustworthy` (`3d1821f8e`) pins it: untrustworthy, `dropped_key`, no stitched flag. It pins a decision, so no RED was shown.
- **Departed (not eligible) members.** They are plan 09's domain (D-05 / D-09), not this path.

**Test evidence.**
- RED (6 failed). The reviewer's measurement (H `sign_in_failed`, returns 2026-05-01 to 2026-06-03; M working, from 2026-06-01) gave a first day of `2026-06-01`, for both kinds.
- GREEN: 53 passed in `test_derive_allocator_equity_job.py`. A run over every derive and compose file also passed.
- The stitched curve is compared **point by point** against `replay_key_equity` over the expected series:
  - H's 0.001 returns in May;
  - M's 0.002 from June 1;
  - H's overlap-day returns set to 0.5, so that using them would visibly change the curve.
- The flows test gives both keys the same May deposit, plus a stray June flow on H. The curve matches only when each day's flows come from the owning key.
- The three untrustworthy arms are gap, missing `key_inputs` and `flow_drop`.
- `test_composite_pair_keeps_the_key_whose_history_starts_first` (the round-1 WR-01 test) stays green.
