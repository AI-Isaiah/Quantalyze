### SFH-05 (reader half) / SFH-06: rejected rows and failed reads were shown as a daily wait

**Files modified:** `src/lib/queries.ts`, `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx`, `src/lib/queries.test.ts`, `src/lib/queries.my-allocation.test.ts`, `src/app/(dashboard)/allocations/AllocationDashboardV2.rebuilding.test.tsx`
**Commit:** `66bc4c6e5`
**Applied fix:**
- `derivedPayloadRejection(payload)` returns `not_version_2`, `untrustworthy` or `malformed`, or null when the row is accepted.
- The derived-row read returns `DERIVED_ROW_READ_FAILED` on any error, `PGRST205` included (it was swallowed silently before). It logs the true consequence (the old text claimed a legacy fallback that plan 11 removed) and reports to Sentry with tag `reason: derived_row_read_failed`.
- A present row the reader rejects is logged and reported with its token only (`reason: derived_row_rejected`, `rejection: <token>`). The level is warning for `not_version_2` and `untrustworthy`, and error for `malformed`. No curve value reaches the log, and a test pins that.
- `equityHistoryReadiness` takes a `missingSeriesReason`. No row gives `awaiting_derivation`. A rejected row gives `derivation_rejected`. A failed read gives `history_read_failed`. Key-list reasons still win.
- `derivePhase07Fields` and `equityHistoryReadiness` stay pure: all logging is at the read site.
- The stale "legacy fallback" comments are corrected.
- The dashboard test harness's `maybeSingle` now honours an injected table error, as its `then` already did.

**RED → GREEN:** the unit arms read `awaiting_derivation` and the dashboard arms had no Sentry capture. All pass after the change (`queries.test.ts`, `queries.my-allocation.test.ts`, rebuilding test: 196/196).
**Recorded decision:** a pre-v2 row now reads `derivation_rejected` until the next key refresh recomposes it as v2. That is true, and transitional for books whose keys refresh. For ledger venues that never re-derive, it is more honest than "recomputed once a day". Expect the Sentry volume to match: ledger-venue keys are never re-enqueued after creation, so a book whose only keys are on such venues and which holds a v1 row from the earlier backfill will send a `not_version_2` warning on every dashboard load, permanently. That is SFH-05 surfacing a history that will never become ready, not noise to silence.
**Out of scope, recorded:** the writer half of SFH-05 is Python. The writer should persist its refusal (a tombstone row instead of a silent delete). Until it does, a refused-and-deleted curve still reads `awaiting_derivation`.
**Status:** fixed
