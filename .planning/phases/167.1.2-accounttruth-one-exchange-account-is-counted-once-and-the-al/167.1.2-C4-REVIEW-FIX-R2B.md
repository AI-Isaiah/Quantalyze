## Fixed Issues

### WR-R2-02: an unanchored covering key zeroes the key it covers, so the account's days count nowhere

**Commit:** b8c5e638a
**Status:** fixed: requires human verification (a logic change to the D-09 rule)

**Files modified:**
- `analytics-service/services/job_worker.py`: `departed_history_inclusion` and
  its caller in `run_derive_allocator_equity_job`
- `src/lib/departed-history.ts`: `departedHistoryInclusion`, `DepartedHistoryKey.anchored`
- `src/components/exchanges/AllocatorExchangeManager.tsx`: the card's reader
- `analytics-service/tests/fixtures/departed_history_inclusion.json`: the shared spec
- `analytics-service/tests/test_allocator_equity_departed.py`
- `src/components/exchanges/AllocatorExchangeManager.departed-history.test.tsx`

**Root cause.** The rule chose the carrier of a known account before the job knew
which departed keys could be levelled. The job then dropped every included key with
no anchor. A dropped carrier took the covered key's days with it.

**Applied fix. Availability is decided before the rule, in both twins.**
- **Rule (both languages):** a new optional input `anchored` (default true).
  - A departed key with `anchored` false is left out of every OTHER key's
    `counted_departed` ordering, the same way an excluded key is. So it covers
    nothing and bounds nothing, and the chain re-forms around the keys that can be
    levelled.
  - Its own decision is taken against those keys, with itself added. So
    `included`/`until` on it still say whether it would carry days that no
    levelled key carries.
  - The change is one filter clause in each twin.
- **Derive caller:**
  - The `key_inputs` read moved ahead of the rule.
  - One pass over those rows builds `departed_anchored` and
    `departed_null_anchor_reasons`. The test for "anchored" is byte-identical to
    the old drop condition (`anchor_usd is not None`). IN-R2-10 was not touched.
  - `departed_unavailable` is now the set of included keys that are not anchored.
    `departed_end_by_key` holds anchored keys only.
  - So an unanchored key never reaches the collision gate, the returns grouping or
    the compose.
  - The old after-the-fact deletion loop is gone. The `departed_history_unavailable`
    flag, its WARNING and the counts-apart log (SFH-C4-06) are unchanged in meaning.
- **Card reader:**
  - `historyKeys` carries `anchored` from `anchorById`.
  - A card now renders only once every departed key on its account has its anchor
    state loaded. Without that, a covering key would read as anchored for one
    render, and the covered key would show the old false sentence.

**A side effect, not a separate fix:** in the finding's shape, key B's card now reads
"History included until …" instead of "an earlier key read the same exchange
account over all of these days". Nothing was added for the separate LOW.

### Rule sentence for the D-09 amendment in CONTEXT (orchestrator to paste)

> A departed key whose saved balance is missing or unusable (no `key_inputs` row,
> or a null `anchor_usd`) neither covers nor bounds any other key: it is left out of
> every other key's ordering, as an excluded key is, so the account's history
> re-forms around the keys the book can count. Its own decision is taken against
> those keys with itself added, so `included` on it means it would carry days no
> levelled key carries; the derive then leaves it out under
> `departed_history_unavailable`, and its card says its history is not available.

## Tests (written first, observed RED, then green)

**New and changed tests:**
- Fixture rows, run by both twins:
  - 21: an unanchored earlier key does not cover the later key.
  - 22: an unanchored later key does not cut the earlier key's tail. The WR-R2-02
    fix text asked for this row. It is the shape the review called the predecessor
    tail (IN-01); whether IN-01 is closed is the reviewer's call.
  - 23: the chain re-forms around an unanchored middle key.
- `inputs` documents `anchored`, and a new `rule` line states the contract.
- `test_no_day_of_a_known_account_is_dropped` is extended. It models the job's
  drop: only anchored keys count, and every day an anchored key read must be
  counted exactly once by an anchored key. So a dropped key can never leave a gap
  that a counted key would have filled.
- `test_no_two_counted_keys_share_a_known_account_on_any_day` now looks at
  anchored keys only, because those are the keys the book counts.
- `_fixture_supabase` omits the `key_inputs` row for an `anchored: false` key.
  `test_the_job_passes_the_rules_end_days_to_the_compose` expects only anchored
  included keys, so it covers rows 21 to 23 at the job level.
- New job-level test
  `test_an_unanchored_departed_key_does_not_zero_the_key_it_would_have_covered`,
  with two arms: `no_row` and `null_anchor` (balance_error).
  - A (June 1 to 15, unanchored) would cover B (June 5 to 10, anchored).
  - It asserts that B's levels are in the curve on June 5 to 10 and that the curve
    is live-only after that.
  - It asserts that both flags are present, the book is trustworthy, and there is
    one WARNING with the right counts.
- New card test: B reads "History included until 2026-06-10." with the switch ON,
  and A reads "History not available:".

**The caller's early strip is also pinned.** The late loop now reads
`float(payload["anchor_usd"])` unconditionally for every key in `departed_end_by_key`.
If the strip regressed, the `null_anchor` arm would end FAILED and the `no_row` arm
would compose an untrustworthy book. The job-level test asserts DONE and trustworthy
on both arms. The card's widened `loaded` wait is defensive and has no test of its
own: the mock returns every anchor in one batch.

the rule, property and job-spy tests) and 4 vitest failures (rows 21 to 23 and the
card test).

**Bite proof:**
