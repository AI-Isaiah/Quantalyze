## Critical Issues

### CR-01: The `allocator_holdings` read measures "the daily poll ran", not "the allocator Exchanges page connected it", so true orphans answer KEY_VENUE_ALREADY_CONNECTED and the Finish-setup remedy is hidden again

**File:** `src/app/api/strategies/create-with-key/route.ts:311-330` (`resolveOtherKeyUse`, the `allocator_holdings` read), `:1604-1621` (the `held` race branch); copy and rationale at `src/lib/wizardErrors.ts` (the `⛔ CORRECTED 2026-09-27` paragraph above `KEY_ORPHANED`, and the `KEY_ORPHANED.cause`)

**Issue:** The fix treats "an `allocator_holdings` row exists for this key" as proof that the allocator Exchanges page connected the key. The poll that writes that table polls every live key, not only allocator keys:
- `enqueue_poll_allocator_positions_for_all_keys` (baseline) selects every `api_keys` row where `is_active = true AND sync_status IS DISTINCT FROM 'revoked' AND disconnected_at IS NULL`. It has no role filter and no strategy filter.
- `_allocator_key_preflight` (`analytics-service/services/job_worker.py`, near line 1288) loads any key by id and never checks for a strategy. Neither does `run_poll_allocator_positions_job`.
- The handler writes holdings with `allocator_id = ctx.key_row["user_id"]`. That is exactly the value the new read filters on (`.eq("allocator_id", userId)`).

So the population `KEY_ORPHANED` exists for answers `held` after its first daily poll, if the account has any balance. That population is the live key of the caller's with no strategy row:
- a key added on the manager key card through the `keys/validate-and-encrypt` persist arm;
- a key left behind when `delete_api_key_if_unreferenced` failed during a draft delete.

`KEY_ORPHANED` is then reachable only on the key's first day, or for an empty account.

What the owner sees instead is `KEY_VENUE_ALREADY_CONNECTED`:
- Its `actions` are `["request_call", "expand_log"]`, and its third bullet sends them to email.
- Its remedy text never names My Strategies → "No strategy yet" → "Finish setup". That is the one path that resolves an orphan with no support ticket. The reuse-arm docblock in the same file calls the loop it closed "unwinnable, measured".

This is a regression the fix round introduced, not a gap it left open. Before round 1, these keys correctly answered `KEY_ORPHANED`.

The fixer's recorded residual therefore points the wrong way. The dominant misroute is not "a new allocator key reads as an orphan". It is "every aged orphan reads as held". The `KEY_ORPHANED` copy rewrite, the CORRECTED docblock paragraph and the route docblock all rest on the wrong model.

A second, supporting defect: `allocator_holdings` is unique on `(allocator_id, venue, symbol, asof)`, and `api_key_id` is not part of that key. For a user with two keys on one venue, the `api_key_id` on a row is whichever key wrote it last. The per-key read is unreliable in both directions.

The tests cannot see any of this. `keyHoldingsLookupMock` defaults to empty, so the existing orphan pin never meets a polled orphan.

**Fix:** Remove the `allocator_holdings` read, and keep the `strategy_keys` read:
- Composite membership is the one case where "no strategy uses it" is false.
- An Exchanges-page key with no strategy is correctly described by the new `KEY_ORPHANED` cause ("…or connected it on another page"), and Finish setup can adopt it through the reuse arm.

```ts
async function resolveOtherKeyUse(/* … */): Promise<VenueIdentityResolution> {
  const { data: member, error: memberErr } = await supabase
    .from("strategy_keys")
    .select("api_key_id")
    .eq("owner_id", userId)
    .eq("api_key_id", liveKeyId)
    .limit(1)
    .maybeSingle();
  if (memberErr) { /* log scrubbed, as now */ return UNRESOLVED; }
  return member ? HELD : ORPHANED;
}
```

Also make these changes:
- Drop the `allocator_holdings` branch from `makeSelectBuilder`, drop `keyHoldingsLookupMock`, and drop the "ALLOCATOR key … allocator_holdings" test.
- Add a regression test named for this defect: a live key with no `strategies` row and no `strategy_keys` row answers `KEY_ORPHANED`. Its purpose is to pin that no poll-written table may make that answer `held`.
- Rewrite the route docblock, the `held` docblock, the `wizardErrors.ts` CORRECTED paragraph and the `KEY_VENUE_ALREADY_CONNECTED` second-emitter note so that each says composite membership only.
- The 409 set stays at 6, because `held` still emits the code for composite members.

## Warnings

### WR-01: The stamper's ERROR line says "a retry will not clear this" for failures a retry does clear

**File:** `analytics-service/services/account_identity.py:445-454` (`_RETRYABLE_FAILURES`), `:505-512` (the ERROR arm)

**Issue:** The SF-M3 split sends every class outside `_RETRYABLE_FAILURES` to ERROR, with the text "a retry will not clear this, so the key is not checked for a duplicate until it is fixed". The docstring files "a holder or key that moved mid-step" under WARNING. The tuple covers that case only when it surfaces as `_HolderVanished` or `_MarkerNotWritten`. It does not cover these cases:
- **The holder departs between `_find_live_holder` and the marker UPDATE.** The same-owner trigger (migration 20260925120000) raises `ACCOUNT_SHARE_HOLDER_NOT_LIVE` (SQLSTATE 55000) or `ACCOUNT_SHARE_HOLDER_NOT_FOUND` (23503). Each reaches the client as an `APIError`, so it lands at ERROR. The next poll self-heals by stamping, which makes it the textbook retryable race.
- **A Supabase gateway 504.** It surfaces as an `APIError`, and `services/db.py` already has `_is_gateway_timeout` because it recurs. It lands at ERROR, and since `_error_code` returns `None` for an int code, the line reads `code=None`.
- **A statement timeout (57014), a serialization failure (40001) or a deadlock (40P01).** Each is an `APIError` and lands at ERROR.

Each one sends a Sentry event that claims permanence for a condition the next poll clears. That is the alert fatigue SF-M3 was meant to prevent, pointed the other way. The line's promise that nobody is checking for a duplicate is also false for these cases.

**Fix:** Classify with a predicate rather than a bare tuple, and stop the ERROR line from asserting that the failure is permanent:
```python
_RETRYABLE_SQLSTATES: Final = frozenset({"55000", "23503", "57014", "40001", "40P01"})

def _is_retryable(exc: BaseException) -> bool:
    if isinstance(exc, _RETRYABLE_FAILURES):
        return True
    if _is_gateway_timeout(exc):          # services.db
        return True
    return _error_code(exc) in _RETRYABLE_SQLSTATES
```
Then:
- Use `except Exception as exc:` with `if _is_retryable(exc): warning … else: error …`.
- Log `code` with `getattr(exc, "code", None)` passed through `str()`, so an int 504 is not lost.
- Add parametrised WARNING cases for 55000, 23503 and a 504 `APIError`.
- If 23503 is too broad, narrow it to the `ACCOUNT_SHARE_HOLDER_NOT_FOUND` / `ACCOUNT_SHARE_HOLDER_NOT_LIVE` message tokens, which `.message` carries safely.

### IN-01: The faulted-holder-read test pins only what the answer is not

**File:** `src/app/api/strategies/create-with-key/route.test.ts` (the `it.each` "a faulted %s read answers neither KEY_ORPHANED nor KEY_VENUE_ALREADY_CONNECTED")

**Issue:** An `unresolved` from the new reads falls through to the byte-identical `DRAFT_ALREADY_EXISTS` 409. That is the sentence the empty draft read has just disproved, and 161-05 removed it from the orphan path. Falling through is the accepted 154.1 posture for a dark read, and the fixer recorded it. The problem is the test: it asserts only `not KEY_ORPHANED` and `not KEY_VENUE_ALREADY_CONNECTED`, so a future change that returns 500, or anything else, passes unnoticed. It also doubles the number of reads that can produce this fall-through, although CR-01's fix halves that again.

**Fix:** Pin the actual code (`DRAFT_ALREADY_EXISTS`) and the `console.error` label, so that a posture change is a deliberate edit.

### IN-02: `KEY_ORPHANED.cause` still says a new strategy "cannot be created over that key" while its second bullet offers Finish setup, which does exactly that

**File:** `src/lib/wizardErrors.ts` (`KEY_ORPHANED.cause` and `fix[1]`)

**Issue:** The rewritten cause keeps "A new strategy cannot be created over that key, and it does not clear on its own." The next bullet tells the owner that "Finish setup" on My Strategies "builds the strategy from the key already stored". The sentence means "not from this wizard with these credentials", but it reads as a flat contradiction. This round re-authored the cause and pinned it byte for byte, so this is the moment to make it true.

**Fix:** For example: "…A new strategy cannot be created over that key from here, and it does not clear on its own." Update the byte pin in `wizardErrors.test.ts` in the same commit.

### IN-03: `_audit_duplicate` now holds a bounded `db_execute` pool slot for the audit RPC, and a timed-out step keeps it after the poll has returned

**File:** `analytics-service/services/account_identity.py` (`_write_marker_and_audit`)

**Issue:** This follows from the chosen design, and the design is correct for SF-M2. Once `wait_for` fires, the handler returns `DONE` and closes the exchange. The marker-and-audit thread still holds one of the fixed-size `_DB_EXECUTOR` slots until the audit RPC returns. That is the zombie-thread accounting `db_execute`'s own docstring warns about. It is recorded so the next reader does not look for it. No change is needed unless pool-saturation warnings start naming this path.

**Fix:** None required. Optionally note it in the `_write_marker_and_audit` docstring beside the residual the fix report already records.
