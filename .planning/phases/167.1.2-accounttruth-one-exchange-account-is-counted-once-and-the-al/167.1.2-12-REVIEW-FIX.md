### SFH-01: what changed, and the residual that remains

### ⚠️ Routed, one class: "durable per-key history-reconstructed marker". Routed to Phase 167.1.2.1 RECONMARKER (founder decision D-20)

Round 3 correction (SFH-R3 L-3 and M-2). This heading read "UNROUTED, founder decision" when

These gaps have one root cause: no durable per-key fact that a key's history was
reconstructed. `compute_jobs` rows are reaped after 30 days (done) or 90 days (failed).

1. **R-12-1** (plan 12): a key added to a book that already has snapshots, whose first sync
   collided with a poll, gets no backfill.
2. **R-13-1** (plan 13): a sole-key REPLACE with non-empty rows deletes the history of the
   book's disconnected keys.
3. **The two-key sibling** (SFH-R2-01): on a zero-snapshot book with two qualifying keys,
   one key's reconstruct ends `done` and writes rows while the other's ends `failed_final`.
   The book has snapshots, so the failed key is never bootstrapped again.
4. **The fast-fail ordering** (a known limit of the hold as briefed): the same-run
   reconstruct reaches `failed_final` before the refresh job is claimed. This can happen
   with a permanent-class failure early in the job. The refresh then sees no in-flight
   row, writes the first row, and the key is stranded.

   **Reach, corrected in round 3 (SFH-R3 M-2).** The trigger is "the reconstruct reaches
   `failed_final` before the refresh is claimed", not only a co-claim. Every row one fan-out
   call inserts shares one transaction `now()` as `next_attempt_at`, so

   bounds it: only a `permanent`-class failure goes straight to `failed_final`; `transient`
   and `unknown` pass through `failed_retry`, which the hold covers; and `InvalidToken` fails
   the refresh's own preflight too.

   (`claim_compute_jobs_with_priority` gives both rows the same transaction `now()`)".

### SFH-R2-03: one book at a time

- **The per-book block.** Each book of the bootstrap loop is enqueued in its own inner
  block. Any error other than a per-key `unique_violation` or `serialization_failure` does
  four things:
  1. rolls back that book's enqueues;
  2. RAISEs a WARNING naming the key being enqueued (`v_boot_key`, NULL when the per-key
     query failed before the first key) and the SQLSTATE;
  3. writes a durable row (below);
  4. continues with the next book.
- **Why skipping is safe.** A skipped book has no reconstruct row, so its refresh stays
  withheld and the next run takes it again.
- **The sub-block stays** as the outer safety net.
- **X2, reworked.** The old X2 mutation (sub-block `RAISE;`) is inert now. X2 seeds an older
  zero-snapshot book taken after the refused one and asserts it still gets its reconstruct.
  Its mutation re-raises from the per-book block.
- **X1, reworked.** The 40001 now falls to the per-book block under X1's mutation, so X1 gains
  a sibling key in the refused key's own book. The sibling's reconstruct is what tells a
  per-key catch from a per-book one.
- **Finds.** The Z2, X1 and S finds follow the new indentation.

### SFH-R2-02 + MIG-R2-01: a durable row, and why `cron_runs`, not `audit_log`

- **Where the rows go.** Both handlers write one `public.cron_runs` row. All rows carry
  `cron_name 'equity_refresh_fanout'` and `status 'error'`. The `error` value is one of two:
  - `bootstrap_book_skipped`: per skipped book, with the owner id, key id, SQLSTATE and
    message in `metadata`;
  - `bootstrap_loop_failed`: from the sub-block, with the SQLSTATE and message.
- **Why the two writes differ.** The per-book write is deliberately not wrapped, so a sink
  that refuses it escalates to the sub-block. The sub-block's write is wrapped
  (`WHEN OTHERS` then a WARNING), so a refusing sink can never cancel the daily refresh.
- **⚠️ Deviation from the brief's letter (Rule 7: surfaced, not averaged).** The brief says
  "an `audit_log` row" and names the ledger fan-out's `candidate_enqueue_failed` as the
  precedent. That precedent is a `public.cron_runs` write
  (`20260924120000_ledger_fanout_failure_count.sql`), not an `audit_log` write. `cron_runs`
  was chosen, for these reasons:
  - `audit_log.entity_id` is `NOT NULL uuid`, and the sub-block failure has no entity.
  - `audit_log_owner_read` plus the `authenticated` SELECT grant would show the allocator an
    internal SQLSTATE and message.
  - `cron_runs` is readable only by platform admins and service_role.
  - `cron_runs` has a lane stand-in, `scripts/pg-lane/fixtures/33-fixture-cron-runs.sql`,
    now added to the gate's RED-UNDER-SETUP list before the migration.
  - `cron_runs` has a prober precedent that counts rows of exactly this shape.
  - `cron_runs` has no CHECK on `error`, so no schema change was made. The rollback stays
    075 verbatim, and the brief's STOP clause was never reached.
- **Arms.**
  - **X2t** asserts the per-book row for the refused key (owner, key, SQLSTATE `P0001`).
    Its mutation deletes that INSERT.
  - **X4** is a new group. A fixture trigger refuses one key's reconstruct, and a second
    trigger on `cron_runs` refuses that key's per-book row, so the error reaches the
    sub-block. X4 asserts that the call raises nothing, that a snapshot book is still

    mutation deletes the sub-block INSERT.
- **Still open.** No prober arm reads `cron_name 'equity_refresh_fanout'` yet. That half of
  round-1 SFH-03 remains: the rows are durable, not watched.
