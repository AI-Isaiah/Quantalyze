**Applied fix:** `_normalise(value, venue)` now enforces `MAX_VENUE_ACCOUNT_ID_LENGTH = 128`, a named and exported constant whose comment cites `src/lib/analytics-schemas.ts`. An over-long id becomes `None`, and a WARNING names the venue and the cap, never the value. The venue is threaded through from `venue_account_id_from`.

**Parity with zod, measured and not assumed:**
- The schema is `.trim().min(1).max(128)`, so the value is trimmed before it is measured.
- zod measures a JS string's `.length`, which counts UTF-16 code units, so the service counts them too.

The module docstring's contract list now states the cap and the one logging side effect.

**Where it lands.** On the validator path (`services/exchange.py`, `services/key_permissions.py`) an over-long id now connects the key without an id, as it would for a venue that reports none. On the stamper path it surfaces as the existing `no_id` outcome, whose WARNING names schema drift. That is the right reading for an id past the cap.

**Red → green:**

### SF2-M2: a retryable failure or `skipped_no_budget` that recurs daily never escalated

**Files modified:** `analytics-service/services/account_identity.py`, `analytics-service/tests/test_account_identity_stamper.py`
**Commit:** 1c2fa48b0
**Status:** fixed: requires human verification (the threshold is a judgment call)

**Applied fix:** `UNSTAMPED_ESCALATION_DAYS = 3` is a named, exported module constant. When a retryable failure or `skipped_no_budget` hits a key that has been unstamped too long (`_unstamped_for_too_long`), the same line is logged at ERROR and ends "key unstamped for >3 days; duplicate check not running". The retryable line keeps "stamp failed", and the budget line keeps `budget_s`. A key counts as unstamped too long only if all of these hold:
- its venue is in `VENUES_WITH_ACCOUNT_ID`. This check matters because `skipped_no_budget` is decided before the venue check, so without it an sFOX or MT5 key would escalate every day for a check that never runs by design;
- `venue_account_id` is NULL;
- `created_at` is more than 3 days old.

**`key_row` carries `created_at`, measured.** The column is `NOT NULL` on `api_keys` (the baseline), and the poll loads the key with `select("*")` in `job_worker._allocator_key_preflight` (the `_load_key` inner function), so the field is already present. No query changed. A missing or unparseable value answers "no escalation", and the docstring says why: it is a fixture artefact, not a production state. A value without an offset is read as UTC, and a `Z` suffix parses (Python 3.12).

**Tests, on both sides of the threshold:**
- 2 days → WARNING and 4 days → ERROR, for both the retryable arm and the no-budget arm.
- A `Z`-suffixed timestamp escalates.
- The constant is pinned at 3.
- Five no-escalation cases at 30 days: sFOX, MT5, an already-stamped key, a NULL `created_at`, and an unparseable one.
- The `_key_row` fixture now carries a fresh `created_at`, so every pre-existing WARNING case also pins the un-escalated side.
- The 4-day cases, the `Z` case and the constant pin failed before the fix.

**A limit, recorded rather than fixed.** The age is measured from `created_at`, not from the first failed stamp. A key that was stamped, then had its `venue_account_id` cleared, would escalate at once. Nothing in the service clears the id: the stamper only writes a value, and the self-heal keeps it NULL until a stamp lands. So this is not a live path today.
