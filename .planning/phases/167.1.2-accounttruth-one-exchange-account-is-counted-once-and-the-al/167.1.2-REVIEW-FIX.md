### IN-04 / SF-M2: a timeout between the marker UPDATE and the audit lost the audit for good; a 0-row UPDATE was audited

**Files modified:** `analytics-service/services/account_identity.py`, `analytics-service/tests/test_account_identity_stamper.py`
**Commits:** bd9707964 (shared with SF-M5, because both change `_audit_duplicate`), then 28f20035a (widens the timeout test's margins)
**Status:** fixed: requires human verification (it changes when the audit fires)
**Applied fix:** a new synchronous `_write_marker_and_audit` runs the marker UPDATE, checks that it returned a row, and emits the duplicate audit. All of this is ONE callable handed to `db_execute`.
- `asyncio.wait_for` can cancel the await, but it cannot split a synchronous callable running in its thread. So a marker that lands is always audited, even when the step has already answered `error`.
- The audit RPC no longer runs on the event loop (IN-04's first half). It runs in the same bounded `db_execute` pool rather than `asyncio.to_thread`. The effect is the same: it is off the loop.
- A 0-row UPDATE raises the new `_MarkerNotWritten`. The step then answers `error` and announces nothing.

**Design chosen over the alternative.** The alternative was to treat "the marker equals but no audit row exists" as an audit still owed. That would need an `audit_log` read on every daily poll of every marked key. The retention cron also archives rows to `audit_log_cold`, so an archived event would re-fire the audit once per retention cycle. It would also have forced fixtures into every existing "not re-audited" test. The one-thread-task design closes the gap without either cost.

**Red → green:**
- The timeout case (the marker fake `time.sleep`s against the budget, records the write, and the second call carries the marker) counted 0 audits. It now counts exactly 1, naming the holder. The test waits on a `threading.Event` for at most 3 s.
- The red was observed at a 0.4 s sleep against `timeout_s=0.1`. Follow-up 28f20035a widened that to 1.5 s against 0.5. Three thread hops (the refused stamp, the holder read and the `strategy_keys` read) must finish inside the budget before the marker write begins. At 0.1 s, a loaded machine could cancel the step before the marker was issued, and the test would fail for a reason unrelated to the defect it pins. The logic under test is unchanged.
- The 0-row case answered `marked_duplicate`. It now answers `error`, with no audit.

**Residual:** if the worker process dies after the UPDATE commits and before the audit RPC returns, the audit is still lost. No design short of a single database transaction covers that. It is the same exposure every fire-and-forget audit in the service has.
