## Accomplishments

- The compose keeps a departed key's history. It takes `departed_end_by_key`, replays the key on its full series, clips it to its end day, and rotates it out after that day. On the next day the key is out of the $-curve and out of both sums of `payload.returns`. The day's return is the remaining keys' own return, and the curve steps down by the departed key's last level.
- The frozen core's math is unchanged. The exit uses the core's own rotated-out rule, fed through the `seams` argument of `allocator_equity_curve`. The ledger books the exit as an outflow.
- The D-09 rule is written once per language: `departed_history_inclusion` (Python) and `departedHistoryInclusion` (TS). Both are tested against every row of `analytics-service/tests/fixtures/departed_history_inclusion.json` (17 cases). The job then checks B4 over the whole history set and fails closed.
- The orphan cleanup deletes only rows of keys that no longer exist, so the owner's switch stays reversible.
- On the Exchanges page, every departed key card shows one sentence and a switch. The Disconnected section has these cards, and so does a revoked or inactive key that was never disconnected. The Delete confirm now says that deleting removes the history. rotate-secret now resets `history_inclusion`.

## Decisions Made

See `key-decisions` above. Two more:

- **Carry-in #2 (one shared seam list) is kept for every rotation.** The curve gets `seg.seams` plus the exit seams, and the ledger gets `seg.seams`. The ledger's seam formula `F = next_eq − prev_eq·(1+r_next)` books a redeployment into `next_keys`. An exit is not a redeployment: with `next_keys=(L,)` it would book the live key's whole balance as a deposit. So the exit is booked as its own outflow of the departed key's last level, on the next union day. In a flat book with a departure, the Modified-Dietz return is 0 and not a loss (tested). `allocator_equity_curve`'s MEDIUM-6 guards still hold. Every exit seam's keys are anchored, and the passed seams are a superset of the internal rotations. No core file was edited.
- **Error tone (DESIGN.md semantic gates).** A 55006 "recompose running" is a transient state that recovers on its own, so its line uses the alert shape in amber. Other refusals use the Disconnect error line's red shape. Plan 09 asked for "the error line the card already uses for Disconnect failures". The shape is reused and DESIGN.md decides the tone.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] A marker link is a known account identity (both languages, and the B4 gate)**
- **Found during:** Task 1. The existing test `test_duplicate_of_an_inactive_holder_counts_on_its_own` failed with `2 == 1`.
- **Issue:** The plan groups by non-NULL `(exchange, venue_account_id)` only. The stamper leaves a marked key's `venue_account_id` NULL because the holder already holds the unique index slot. Take a departed holder with a live marked key: the holder looked like a distinct account and was included, so one account was counted twice. The collision gate could not see it. The reverse case is the common D-01 path: the owner disconnects the marked duplicate. That key read as "unknown", the card would ask the owner to include it, and including it would double-count again. Plan line 177 (a marked key whose holder departed counts in its own right) needs the same identity.
- **Fix:** `account_identity_tokens` / `accountIdentityTokens` build a union-find over venue-id edges and marker edges. The D-09 rule and the B4 gate both use the token. The fixture gains the optional inputs `account_shared_with_api_key_id` and `account_share_kind` (cases 10 and 11). Both languages still read one set of inputs, the same one.
- **Commit:** `9cd0e3466`, `f4cab7b3f`

**2. [Rule 2 - Missing Critical] A departed key with no usable anchor is left out, not dropped**
- **Found during:** Task 1 orientation. `git log -S orphan_kinds` shows the orphan cleanup has existed since 115.1 (`d8f6ca993`).
- **Issue:** Every key that departed before this plan has had its `key_inputs` row deleted by any later compose. A departed key is never derived again. Composing it would drop it as DROPPED_KEY, which is blocking, and hold the book "rebuilding" forever. That is worse than D-22's accepted omission.

**3. [Decision] "Departed" is the job's own ineligibility (inactive included), and inputs grow by optional `is_active`**

**4. [Decision] `until` = min(end day, last returns day), plus a `no_returns` reason**
- The plan's fixture rows name end days only. A disconnected key whose returns stopped before its disconnect day has no data after that day. A key with no returns on or before its end day is excluded as `no_returns` (cases 12 and 15).

**5. [Decision] A live key on the account with no returns yet bounds a departed key to zero days (case 13)**
- Treating it as an open-ended overlap would fail the book closed during every rotation's backfill window. The next compose re-bounds the departed key once the new key has returns.

## Known limits (recorded, not fixed here)

- **This plan restores departed history only for keys whose `key_inputs` row still exists.** On PROD that is every key that departs after this code deploys.
