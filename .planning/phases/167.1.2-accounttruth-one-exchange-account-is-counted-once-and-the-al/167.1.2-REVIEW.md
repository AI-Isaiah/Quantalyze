# Phase 167.1.2 (PR C1): Code Review Report

**Reviewed:** 2026-09-27T19:30:00Z

## Summary

Scope: the PR C1 hunks (`git diff origin/main...HEAD`) for plans 02 (capture the venue account id at connect), 04 (poll-time identity stamper, duplicate marker, key-card note, reconnect refusal copy) and 16 (the D-18 working-holder rule in `set_departed_key_history_inclusion` and `isWorkingHolder`), read against CONTEXT D-01, D-04, D-09, D-10, D-11 and D-18.

The core mechanics hold up when traced:
- The stamper never raises. It is bounded by `min(20 s, TIMEOUT_PER_KIND − elapsed − 10 s)`, and it only writes the three identity and marker columns.
- Its UPDATE runs as `service_role`, so the INSERT-only scrub trigger never touches it.
- The unique index predicate (`venue_account_id IS NOT NULL AND disconnected_at IS NULL`) matches `_find_live_holder`'s filter.
- The poll handler's try/finally restructure keeps every early return inside the `finally` that closes the session.
- D-18 is expressed identically in SQL (with the explicit NULL leg; `is_active` is NOT NULL, so there is no three-valued hole there) and in `isWorkingHolder`.
- The rollback is guarded and self-checking.
- Census pins move by measurement, and origin/main still carries `ARMS_FLOOR = 491`, as the SUMMARY states.

No finding corrupts stored data, crosses a tenant boundary or leaks a credential, so there are no Critical items. The defects are in what the owner is told, and in one data-integrity direction that C2 will inherit:
- The manager key card's duplicate note names a control that card does not have. It also renders on keys that are themselves already disconnected.
- The wizard's orphan refusal now reaches four more venues with a sentence that is false when the holder is an allocator or composite key.
- During the backfill window, the stamper marks the older key, the one that carries the history, as the duplicate of a newer one.

## Warnings

### WR-01: Manager key card tells the owner to "Disconnect" on a surface that has no Disconnect control

**File:** `src/lib/account-share-note.ts:85`, rendered at `src/components/strategy/ApiKeyManager.tsx` (the `accountShareNote(key, keysById)` block inside `listedKeys.map`)
**Issue:** `accountShareNote` returns one fixed sentence: "This key reads the same exchange account as X. Disconnect one of them." That fits `AllocatorExchangeManager`, where active rows carry a Disconnect button. `ApiKeyManager` has no Disconnect control; a grep for `Disconnect` in that file returns nothing, and its own new test asserts the control beside the note is `Delete`. So the manager is told to take an action the card does not offer. D-01 says the note sits "beside the existing Disconnect and Delete controls", which holds on only one of the two cards. This is user-facing copy that points at a missing control.
**Fix:** Let the caller name the verb, or use a verb that is true on both cards:
```ts
export function accountShareNote(
  key: AccountShareNoteKey,
  keysById: ReadonlyMap<string, AccountShareNoteKey>,
  action: "Disconnect" | "Delete" = "Disconnect",
): string | null {
  // ...
  return `This key reads the same exchange account as ${label}. ${action} one of them.`;
}
// ApiKeyManager: accountShareNote(key, keysById, "Delete")
```
Pin it with an ApiKeyManager test asserting the sentence's verb matches a button that exists in the same card.

### WR-02: The duplicate note renders on a marked key that is itself disconnected or inactive, and it never clears

**File:** `src/lib/account-share-note.ts:75-86`; `src/components/strategy/ApiKeyManager.tsx` (the `listedKeys` derivation and render)
**Issue:** `accountShareNote` checks only whether the holder is working. It never checks the marked key. `AllocatorExchangeManager` avoids the problem only because it renders the note inside `activeKeys` (and even there an `is_active = false`, still-connected row gets it). `ApiKeyManager` lists every key the RLS read returns, including disconnected ones; there is no `disconnected_at` or `is_active` filter in the file.

A key marked `duplicate` and then disconnected by its owner, which is exactly the action the note asks for, is never polled again. `_allocator_key_preflight` skips inactive keys, and the stamper runs only inside a successful poll. So the marker is never cleared, and the card shows "…Disconnect one of them." on an already-disconnected key permanently. The owner is left with a remedy they have already applied. The SUMMARY's claim "The note renders on active rows only" holds for one of the two cards.
**Fix:** Gate on the marked key inside the shared function, so both cards inherit it:
```ts
if (key.account_share_kind !== "duplicate" || holderId === null) return null;
if (!isWorkingHolder(key)) return null; // a departed/failing duplicate asks nothing
```
(or at minimum `key.disconnected_at === null && key.is_active`), and add the disconnected-duplicate and inactive-duplicate cases to `account-share-note.test.ts` and `ApiKeyManager.test.tsx`.

### WR-03: During the backfill window the OLDER key (the one with the history) is marked as the duplicate of a NEWER key, and D-01's refusal does not fire

**File:** `src/app/api/keys/validate-and-encrypt/route.ts:772-774` and `src/app/api/strategies/create-with-key/route.ts:1261-1263` (connect-time stamp); `analytics-service/services/account_identity.py:327-370` (`_stamp` / `_find_live_holder`)
**Issue:** Every key connected before this PR has `venue_account_id` NULL, and the partial unique index cannot see NULL. Consider an owner whose old key K_old (NULL, months of history) is live when they add K_new on the same account after deploy:
1. The connect route stamps K_new, and the INSERT succeeds. D-01's "refuse a second key" does not fire.
2. On K_old's next daily poll the stamper hits the index. It marks K_old `duplicate` with `account_shared_with_api_key_id = K_new`.

The marker's direction is therefore decided by which key was stamped first. During the backfill window that is systematically the newer key. The COMMENT's reader contract says the book "counts that account once, through the holder". If the C2 readers (plans 05 and 10) apply that literally, the account's history before K_new's first returns day is lost from the book, even though K_old carried it. The key card also points the owner at the senior key ("This key [K_old] … Disconnect one of them"). The marker persists, so this is data-integrity-relevant for C2, not just a transient gap in D-01.
**Fix:** Pick one and record it in CONTEXT/SUMMARY:
- (a) Before connect-time stamping is relied on, run the stamper once as a backfill over all live ccxt keys (a one-shot job or a dispatch). Then the senior key holds the slot and the connect route refuses K_new as D-01 intends.
- (b) Explicitly bind the C2 replan to NOT assume holder = senior key. For a live `duplicate` pair, order by first returns day, as D-09 case (2) already does for departed keys.

Either way, add a stamper test for "old unstamped key + newer stamped key" that asserts the chosen direction.

### WR-04: KEY_ORPHANED ("nothing uses it … draft was deleted") is now reachable for ccxt venues and is false when the holder is an allocator or composite key

**File:** `src/app/api/strategies/create-with-key/route.ts:1484-1540` (race arm), `:273-367` (`resolveStrategiesForKey`); copy at `src/lib/wizardErrors.ts:2461-2481`
**Issue:** The race arm resolves the colliding live key through `resolveStrategiesForKey`, which reads only `strategies.api_key_id`. It returns `orphaned` when no strategy row points at the key. Two kinds of live key legitimately have no such row:
- a key added on the allocator Exchanges page (`validate-and-encrypt` persist arm), for a user whose role is `both`;
- a composite member key, linked through `strategy_keys`, not `strategies.api_key_id`.

Before this PR only MT5 could reach this arm. Now OKX, Bybit, Binance and Deribit can. A manager who connects, in the wizard, an account their own allocator key or composite member already reads is told "This key is already stored, but nothing uses it. These credentials were saved in an earlier session whose draft was deleted…". That is false, and it points them at a "Finish setup" path built for orphans. The new test `an ORPHANED key on the same account → 409 KEY_ORPHANED` pins only the true-orphan case. The defect predates this PR (it already applied to MT5), but this PR widens its reach.
**Fix:** Before answering `orphaned`, check the other two holders. If a `strategy_keys` row references `liveKeyId`, or the key has holdings or allocator usage, answer the venue-neutral `KEY_VENUE_ALREADY_CONNECTED` refusal (already re-authored for ccxt in this PR) instead of `KEY_ORPHANED`:
```ts
const { data: member } = await supabase.from("strategy_keys")
  .select("strategy_id").eq("api_key_id", liveKeyId).limit(1).maybeSingle();
if (member) return { kind: "connected", strategyName: null };
```
Add a race-arm test for an allocator-held key and one for a composite-member-held key.

### WR-05: `deduped` on a ccxt collision silently discards the credential the user just entered

**File:** `src/app/api/strategies/create-with-key/route.ts:1491-1502`; pinned by `route.test.ts` "[167.1.2 / D-01] … an own DRAFT on the same account → 200 deduped with the EXISTING ids"
**Issue:** For MT5, "same login" effectively meant "same credential", so resuming the existing draft lost nothing. For a ccxt venue two different API keys on one account are routine; rotation is the common case. When a user starts a new wizard session with a freshly created key K2, on an account whose draft already holds K1, the route answers 200 with K1's `api_key_id`. K2 is validated, encrypted and then dropped without a word. If K1 was deleted on the exchange (the usual reason to make a new key), the resumed draft syncs with a dead credential. The user sees a revoked or failed sync right after entering a working key, with nothing telling them their new key was ignored. The test shows this was intended, so it is a design consequence to confirm, not an accident.
**Fix:** Confirm the intent with the founder and record it. If a silent discard is not acceptable, either:
- answer a named 409, e.g. reuse `KEY_VENUE_ALREADY_CONNECTED` with a "resume your draft" action, so the user chooses; or
- when the existing draft's key is revoked or failing (the D-18 not-working set), refuse with copy telling the user to replace the draft's key rather than resuming onto it.

### IN-02: Zod caps `venue_account_id` at 128 characters; the service has no cap, so an over-long id fails the whole validation

**File:** `src/lib/analytics-schemas.ts:44`; `analytics-service/services/account_identity.py:63-67`
**Issue:** `_normalise` returns any non-blank str or int. If a venue ever returns an id longer than 128 characters, `parseResponse(ValidateKeyResponseSchema, …)` throws and the connect fails. That contradicts the stated contract "A missing id is None and NEVER fails validation" (`services/exchange.py:1331-1334`).
**Fix:** Apply the same bound in `_normalise` (return `None` above 128 characters, with a venue-named warning), or make the TS field fail soft, for example with `.catch(null)`.

### IN-03: The holder label is lowercase for Deribit (and MT5 or sFOX) because `EXCHANGE_LABELS` lists only three venues

**File:** `src/lib/api-key-label.ts:20-24`
**Issue:** The duplicate note can now fire for Deribit (`VENUES_WITH_ACCOUNT_ID`). With no nickname the note reads "…as deribit — ••••abcd.", while other venues get a capitalised name.
**Fix:** Add `deribit: "Deribit"` (and `mt5: "MT5"`, `sfox: "sFOX"` for completeness) to `EXCHANGE_LABELS`.

### IN-04: A synchronous audit call inside the bounded stamp, and a lost audit on a cancelled write

**File:** `analytics-service/services/account_identity.py:262-284, 321-323, 400-402`
**Issue:**
- `_audit_duplicate` calls `log_audit_event`, a synchronous network call, from inside the `asyncio.wait_for` that claims to bound the step. A slow audit RPC blocks the event loop, so the timeout cannot preempt it, and it can stall other jobs on the same worker. This is the same pattern as `_emit_audit`, but here it sits inside the bound that is meant to protect the poll's timeout.
- If `wait_for` times out while `db_execute(_q)` in `_mark_shared` is running in its thread, the UPDATE can still commit after the step has returned `error`. The next poll then sees the same holder and kind and skips the audit. The transition into `duplicate` is recorded in the table and never in the audit log.
**Fix:** Run the audit through `asyncio.to_thread`. Treat "marker equals, but no audit row exists" as eligible for one audit, or emit the audit before the marker write.

### IN-05: create-with-key's outer catch scrub list omits `venueAccountId`

**File:** `src/app/api/strategies/create-with-key/route.ts:1728-1731`
