Most of the risk sits in the two Python writers. Both still apply the pre-D-18 holder rule (CR-01, lead 1, confirmed by running it). Plan 10's per-key carry-forward reads a key's rows by the `api_key_id` stamped on them. The holdings table is last-writer on `(allocator_id, venue, symbol, asof)`, so for a duplicate pair the counted holder can be carried at months-old holdings (CR-03). The fixes interact, and CR-01 must not be fixed on its own. If the D-18 predicate goes into the Python writers alone, a holder that fails (`error` / `sign_in_failed`) but is still eligible stays counted next to the now-ordinary marked key. The derive has no collision to catch this, because the marked key's `venue_account_id` is NULL (SF-M1). The book would then compose a double-counted curve. Today the TS reader hides it only because of CR-02's false "pending" state. Fix CR-01, CR-02 and CR-03 together (see each Fix).

## Critical Issues

### CR-01: Both Python writers apply the pre-D-18 holder rule, so an inactive or failing holder drops the account from the refresh and the curve from the derive (lead 1)

**File:** `analytics-service/services/job_worker.py:10245-10252` (`_holder_is_working`), `analytics-service/services/equity_reconstruction.py:1818-1845` (`_counted_through_holder`)
**Issue:** D-18 (founder, 2026-09-27) and the column COMMENT from migration `20260927180000` say a marked key counts through its holder only while that holder is WORKING. That means `is_active` is true, `disconnected_at IS NULL`, and `sync_status` is NULL or not in (`revoked`, `sign_in_failed`, `error`). CONTEXT's "D-18 home" says C2's plans 05 and 10 "are written against the new rule". They are not. Both functions test only `disconnected_at IS NULL AND sync_status <> 'revoked'`, and `_counted_through_holder`'s docstring still cites the superseded migration `20260925120000`. Measured:

```
is_active  sync_status      _holder_is_working  _counted_through_holder(dup)
False      complete         True                True
True       error            True                True
True       sign_in_failed   True                True
```

Effects, per holder state:
- **Holder inactive** (`is_active=false`, not disconnected, not revoked). The holder fails `eligible_key_predicate`, so the refresh does not count it, and the refresh also drops the healthy marked key. The account is counted by **nobody** and the persisted legacy snapshot loses its whole balance. D-18 exists to prevent exactly this, and first-writer-wins keeps the short row for the day. The derive meanwhile deletes the curve (`account_duplicate`). The TS reader sees no working-holder duplicate and shows "recomputed ... once a day" for as long as the pair exists.
- **Holder `error` / `sign_in_failed`, still active.** The derive deletes the curve. The refresh counts the account through the failing holder's carried (stale) holdings, never through the healthy key.
- The composite branch has the same gap: `composite_member` is judged by `eligible_key_predicate`, which admits `error` / `sign_in_failed`. The COMMENT's reader contract applies to "a marked key" of either kind.

No test covers any of the three D-18 states. The derive tests cover only revoked and disconnected holders (`test_derive_allocator_equity_job.py:1541-1637`), and so does the refresh (`test_refresh_allocator_equity_carry_forward.py:230`).

**Fix:** Add ONE Python predicate beside `eligible_key_predicate` in `services/allocator_equity_derive.py`, mirroring `NOT_WORKING_SYNC_STATUSES` in `src/lib/account-share-note.ts`. Use it in both writers for both kinds, and re-cite `20260927180000`:

```python
NOT_WORKING_SYNC_STATUSES: Final = frozenset({"revoked", "sign_in_failed", "error"})

def holder_is_working(holder: Mapping[str, Any] | None) -> bool:
    """D-18 (migration 20260927180000 COMMENT). Twin of isWorkingHolder."""
    if holder is None:
        return False
    return (
        holder.get("is_active") is True
        and holder.get("disconnected_at") is None
        and holder.get("sync_status") not in NOT_WORKING_SYNC_STATUSES
    )
```

This swap on its own opens a double count. A failing holder is still eligible and still in `counted_ids` / `counted`. Once the marked key is ordinary, both are summed, and the derive's collision gate cannot fire because the marked key's id is NULL (CR-02). So when a marked key reads through a holder that is **not working**, drop the **holder** from the counted set for that account, and let the healthy key read it. Better, apply CR-03's account-group read, which counts the group once whichever member is working. Add tests for the three D-18 states in both writers, including "failing but eligible holder + healthy marked key ⇒ counted once, by the healthy key". Add a parity test that pins the Python status set to the TS set, as `account-share-note.test.ts` already does against the SQL tuple.

### CR-02: A working key behind a live but non-working holder keeps a NULL account id forever, and plan 11 holds the book in `account_identity_pending` with a promise that never comes true (lead 2, C1 SF-M1)

**File:** `src/lib/queries.ts:3732-3737` (`identityStillPending`), `src/lib/queries.ts:3745-3759` (`equityHistoryReadiness`), `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:46-47`
**Issue:** The chain, verified link by link:
1. `_find_live_holder` (`account_identity.py:241`) treats any key with `disconnected_at IS NULL` as the holder, including one that is inactive, revoked, `error` or `sign_in_failed`.
2. The index `api_keys_user_exchange_venue_account_uniq` is `WHERE venue_account_id IS NOT NULL AND disconnected_at IS NULL` (`20260812083206:465-467`). That holder therefore keeps the slot until it is **disconnected**.
3. `_mark_shared` writes the marker and leaves the working key's `venue_account_id` NULL (its docstring: "succeeds once the holder has left").
4. In the TS reader, `countsAsDuplicate` correctly returns false (the holder is not working under D-18). But `identityStillPending` sees an eligible ccxt key, `account_share_kind = 'duplicate'` (not `composite_member`) and a NULL id, so it returns `account_identity_pending`.

The book is held in "rebuilding" for as long as the dead holder stays connected. The line shown is "We are confirming which exchange account each key reads. This happens on the next daily sync.", which is false: no sync will stamp that key. No remedy is named either, because the Exchanges-page note also stays silent when the holder is not working. C1 routed this constraint to C2 in so many words: readers "must not treat 'known but blocked by a not-working holder' as unknown identity". Plan 11 does not handle it.

The TS unit test that should catch this pins an unreachable state instead (WR-05).

**Fix:** In `identityStillPending`, a marked key whose holder is present in the key list and has a known id is identity-KNOWN. Its account is the holder's account:

```ts
function identityStillPending(key: EquityHistoryKey, byId: ReadonlyMap<string, EquityHistoryKey>): boolean {
  if (!isPerKeyDailiesEligibleKey(key)) return false;
  if (!ACCOUNT_IDENTITY_EXCHANGES.has(key.exchange.toLowerCase())) return false;
  if (key.account_share_kind === "composite_member") return false;
  if (knownVenueAccountId(key.venue_account_id)) return false;
  const holder = key.account_shared_with_api_key_id ? byId.get(key.account_shared_with_api_key_id) : undefined;
  return !(key.account_share_kind === "duplicate" && holder && knownVenueAccountId(holder.venue_account_id));
}
```

Update the call site to match: `if (apiKeys.some((key) => identityStillPending(key, byId)))` in `equityHistoryReadiness` (`byId` is already built there). Do this only together with CR-01's "drop the non-working holder" half (see "Fix coupling" above). Otherwise this change marks ready a book whose derive (after CR-01) sums both keys. An alternative worth weighing is to have the stamper record the measured id on the marked key in a separate column. Either way, add a readiness test built from the realistic shape: a marked key with a NULL id, and a holder with the shared id in each of inactive, revoked, `error` and `sign_in_failed`.

### CR-03: Plan 10's per-key read counts a duplicate pair through the holder's OWN-NAMED rows, but the holdings table attributes each row to whichever key polled last, so the holder is carried at stale holdings

**File:** `analytics-service/services/equity_reconstruction.py:1894-1936` (`counted` plus the per-key `_sel_latest_asof` / `_sel_rows`)
**Issue:** `persist_allocator_holdings` upserts on `(allocator_id, venue, symbol, asof)` (`allocator_positions.py:1534`, index `allocator_holdings_owner_venue_symbol_asof_key`). There is no `api_key_id` in the key. A duplicate pair H/D reads one account, so both keys write the same symbols every day, and the key that polls LAST owns every row for that day. Plan 10 excludes D and then reads H's rows via `.eq("api_key_id", H)` at H's latest `asof`. On any day D polled after H, H's "latest" is the last day H happened to win the race. That can be days or months back if D reliably polls later. The refresh then persists that stale total as today's snapshot.

Before plan 10, the today-only read merged the pair's rows correctly: one row per symbol, whichever key owned it (RESEARCH line 28: "for ONE account behind several keys it merges CORRECTLY"). So plan 10 turns a correct merge into a stale count in exactly the case it was written for. The 10-SUMMARY (line 194) records the approximation but routes it to 167.1.1 as the index defect. That routing does not cover this regression, which plan 10's read shape creates. The same applies to `composite_member` pairs.

**Fix:** Read by ACCOUNT GROUP, not by key. Build groups from the markers: a holder plus every key that points at it through `account_shared_with_api_key_id`. For each group with at least one counted member, take the group's latest `asof` over `.in_("api_key_id", group_ids)` and sum that day's rows once. This also resolves CR-01's direction question, because the group is counted once whichever member is working. Add a test where D's job overwrote H's rows today and H's own-named rows are older. The persisted total must equal today's merged rows.

### CR-04: The carry-forward keeps an EMPTIED account's last balance forever, because an empty account writes no holdings row

**File:** `analytics-service/services/equity_reconstruction.py:1915-1932` (`if not asofs: continue` / `latest = max(asofs)` with no staleness horizon)
**Issue:** The ccxt spot builder keeps only `float(qty) > 0` (`allocator_positions.py:597`), and `persist_allocator_holdings` writes nothing for an empty list (`allocator_positions.py:1518`). It never zeroes or deletes yesterday's rows. Take a key whose account was fully withdrawn or closed and which stays connected. It keeps polling successfully and writes no row. Plan 10 then reads that key's latest `asof` (the last day it had money) and carries that balance into every future daily snapshot, "for as long as `eligible_key_predicate` admits it". Before plan 10 the today-only read counted $0, which is correct for this case. This is the defect `allocator_positions.py:1047-1058` already documents and fixed for MT5 ("emitting nothing froze the last POSITIVE equity in place forever"), now reintroduced for every ccxt venue in a persisted money figure. `match.py`, compare, the GDPR export and the SQL cron all read `allocator_equity_snapshots`.

**Fix:** Carry a key only when it has NOT completed a successful poll since its latest holdings day. A key whose last successful poll is newer than its latest `asof` has an empty account and contributes $0. One way is to read the key's last successful poll day with the key row (`last_sync_at` with a success `sync_status`; check first that the allocator poll stamps it for ccxt keys, since memory records `last_sync_at` as unreliable for ledger venues). A more robust way is to make the poll persist an explicit empty marker, the MT5 approach. Add a test: key polled today, zero rows today, rows three days ago ⇒ contributes $0.

### WR-01: The derive keeps the composite HOLDER's series whatever the stamp order, and a benign flag hides the dropped history (C1 WR-03)

**File:** `analytics-service/services/job_worker.py:10326-10341`, `analytics-service/services/job_worker.py:10560-10564`
**Issue:** A `composite_member` non-holder is removed from `counted_ids` whenever its holder is eligible. The marker's direction depends on which key was stamped first. During the backfill window that is systematically the NEWER key (C1 WR-03). If the dropped member is the older key, its earlier per-key returns leave the book. `benign_flag_tokens=["composite_shared_account_counted_once"]` then keeps `is_trustworthy` true, so a shortened curve renders as trustworthy with no signal. C1 routed "must not assume holder = senior key" to exactly this code.
**Fix:** For a composite pair, keep the member whose returns start earliest (D-09 case (2) ordering), or stitch by the declared `strategy_keys` windows. Add a test where the holder's series starts after the non-holder's.

### WR-02: A ccxt key that is failing and was never stamped holds the book in `account_identity_pending` indefinitely, under the same false copy

**File:** `src/lib/queries.ts:3732-3737`, `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:46-47`
**Issue:** `identityStillPending` uses `isPerKeyDailiesEligibleKey`, which excludes only `revoked`. The stamper runs only after a SUCCESSFUL poll (`job_worker.py` poll epilogue). A key in `error` or `sign_in_failed` with a NULL id (every key connected before C1, until its next good poll) never stamps. The whole book stays rebuilding, and the text says "This happens on the next daily sync." The same holds for a persistent `no_id` or `skipped_no_budget` stamp outcome. Holding the book may be right (the identity really is unknown), but the copy promises a timer that is not running, and D-15 forbids exactly that.
**Fix:** Judge pending only over WORKING keys (the D-18 predicate), or give the non-working case its own reason and line, such as "One of your keys is not syncing. Fix it on the Exchanges page." Pin both with tests.

### WR-03: `excludedTrusted` names DISCONNECTED keys' dollars as "connected keys with no return history yet"

**File:** `src/app/(dashboard)/allocations/lib/live-holdings-summary.ts:281`, `:312`
**Issue:** `holdingsSummary` is not filtered by key eligibility (`queries.ts` collapses every `allocator_holdings` row to the latest per venue/symbol/type, departed keys included). A soft-disconnected or inactive key whose `sync_status` is `complete`, `error` or NULL is not untrusted (`UNTRUSTED_KEY_SYNC_STATUSES` is only `revoked`, `sign_in_failed`), is not manager-side, and is not contributing. Its toggled-on holdings therefore land in `excludedTrusted`, and the composer says they are "from connected keys with no return history yet". Both halves are false for a disconnected key that has history. This is user-facing copy on a money figure.
**Fix:** Split the part: route holdings whose key is not eligible (`isPerKeyDailiesEligibleKey` false, key present in `payload.apiKeys`) to their own part with honest copy (for example "from disconnected keys"). Keep `excludedTrusted` for eligible, non-contributing keys. Extend the conservation test's generator to include a disconnected key.

### IN-02: The bootstrap cap counts enqueues that were skipped or rolled back
