# 167.1.2 C3: silent-failure review (plan 14, D-15)

## Verdict

No CRITICAL or HIGH findings. The change does what D-15 asks. Both surfaces gate
on `equityHistoryState !== "ready"` and stay fail-closed: a missing, null, empty
or unknown state still reads as rebuilding. No readiness reason now falls through
to the warm-up note or to a "no data yet" reading. The IN-01 branch is removed,
not kept beside the new code. The Overview's per-reason arm covers all 8 members
of `EquityHistoryRebuildReason` across 3 history shapes. Re-adding a count or
source condition would turn it RED.

There are three MEDIUM findings. (1) The Scenario disclosure ignores the reason,
so it calls a failed history read a rebuild. (2) The payload contract in
`queries.ts` still says two consumers read `equityCurveSource`, but plan 14
removed both. (3) The ready-branch warm-up note shows its "two days" timer only
when two days are already on screen, and the new test locks that state in.

passed (371 skipped by the filter).

## SFH-C3-01 — MEDIUM — The Scenario calls a failed history read (and every reason that needs the user to act) "being rebuilt"

**Location:** `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:5521-5529`
(copy at :5526-5527). The reason is never destructured in the composer
(`grep equityHistoryRebuildReason ScenarioComposer.tsx` returns 0 hits).

**Issue.** The disclosure reads the state alone, and its one sentence says
"Your book's own history is being rebuilt, so the comparison with your current
book is not shown." For the same payload, the Overview
(`EquityHistoryRebuilding.tsx`) picks the line by reason. So the two surfaces now
agree on WHETHER something is withheld but disagree on WHY:

| reason | Overview line | Scenario line |
|---|---|---|
| `history_read_failed` | "We could not load your history just now. Reload the page to try again." | "being rebuilt" |
| `duplicate_account` | "Disconnect one of them on the Exchanges page" | "being rebuilt" |
| `key_not_syncing` / `shared_account_no_working_key` | "Check it on the Exchanges page" | "being rebuilt" |

**Why plan 14 makes it worse.** Under a failed derived read, `derivedPayload` is
null, so `curveForSource` is null and `equityCurveSource` is always `"legacy"`
(`src/lib/queries.ts:4119-4128`). Before plan 14, a read-failed book with 0
legacy snapshots got NO Scenario disclosure. That was a silent gap, but not a
false claim. After plan 14 it gets "being rebuilt". This is a new
false-cause state for that book on this surface.

**Failing scenario.** The `allocator_equity_derived` read errors for one request
(transient PostgREST or pooler error → `DERIVED_ROW_READ_FAILED` →
`history_read_failed`). The allocator is on the Scenario tab in book mode and
reads that the history is "being rebuilt". That sentence describes a background
process that is not running. They wait instead of reloading, and one reload
would have fixed it. A `duplicate_account` owner likewise reads a passive wait,
but nothing rebuilds until they disconnect a key.

**Hidden errors.** A failed history read (network, RLS, timeout) is shown in the
Scenario as a scheduled rebuild.

**Recommendation.** Thread `equityHistoryRebuildReason` into the composer.
- `history_read_failed`: use the Overview's read-failure line, or a Scenario
  variant such as "We could not load your book's history just now, so the
  comparison is not shown. Reload the page to try again."
- The action-needed reasons (`duplicate_account`, `key_not_syncing`,
  `shared_account_no_working_key`): point to the Overview panel or the Exchanges
  page rather than implying a wait.
- Keep the current sentence for the passive reasons: `awaiting_derivation`,
  `account_identity_pending` and `derivation_rejected`.

Add a Scenario test arm per reason class, mirroring `REASON_LINES` in the
Overview test, so the two surfaces cannot drift apart again.

```tsx
{isOwnBookRebuilding && !isBlankMode && (
  <p data-testid="scenario-ownbook-rebuilding" className="mt-2 text-fixed-11 text-text-muted">
    {equityHistoryRebuildReason === "history_read_failed"
      ? "We could not load your book's history just now, so the comparison with your current book is not shown. Reload the page to try again."
      : NEEDS_ACTION.has(equityHistoryRebuildReason)
        ? <>Your book's own history is on hold until a key is fixed, so the comparison is not shown. See the Overview for what to do.</>
        : "Your book's own history is being rebuilt, so the comparison with your current book is not shown."}
  </p>
)}
```

**Related (pre-existing, outside the C3 diff; recorded only).** On the Overview,
a `history_read_failed` book still gets the heading "Your equity history is being
rebuilt". The body under it gives a double-count / no-sync-day cause, and neither
of those is why the history is missing. Plan 14 now sends 0-snapshot read-failed
books to this panel instead of the warm-up note. That is a better outcome than
before, but it does mean more users reach this copy.

## SFH-C3-02 — MEDIUM — The payload contract still says the warm-up gate and the Scenario disclosure read `equityCurveSource`; plan 14 removed both

**Location:** `src/lib/queries.ts:2899-2904` (JSDoc on the
`MyAllocationDashboardPayload.equityCurveSource` field: "the warm-up / disclosure
gates still read it … The Overview warm-up gate and the Scenario disclosure
do."), `src/lib/queries.ts:4119-4128` (producer comment: "The Overview warm-up
gate and the Scenario disclosure still do, so keep the pre-167.1.2 curve gate in
that state."), and `src/lib/queries.ts:3627` (`equityCurveSource` still uses it).

**Issue.** After `08a998ffe` and `2b8e11d74`, nothing reads `equityCurveSource`
while the book is rebuilding. Its only remaining consumer is `EquityChart`
(`widgets/performance/EquityChart.tsx:2038`), and that mounts only in the
`"ready"` branch. The producer still computes a rebuilding-state `"derived"` /
`"legacy"` split whose sole purpose was the IN-01 and WR-02 gates, and the
payload type, which every consumer reads, still describes those gates as live.
`queries.ts` was not in plan 14's `files_modified`, so this is a leftover of the
superseded pattern. D-15 says of that pattern "REMOVED, not kept beside a new
one" (Rule 7).

**Failing scenario.** A later reviewer or fixer reads the field's contract, finds
it says the Scenario disclosure depends on `equityCurveSource`, and "restores" the
source condition. That brings back exactly the gate D-15 forbids, and a derived
curve would once again change whether a rebuilding book is disclosed. The
"Do NOT restore" lineage comments sit only in the test files. The contract a
consumer actually reads points the other way.

**Recommendation.** Rewrite the three comments to say that no consumer reads
`equityCurveSource` while the book is rebuilding (D-15). Then either stamp
`"legacy"` under rebuilding, or keep the computation and state that it is kept
only for the pinned union and the ready-branch chart. Name D-15 in the note.

## SFH-C3-03 — MEDIUM — The ready-branch warm-up promises "two days" in exactly the state where two days are already on screen, and the new test locks it in

**Location:** `src/app/(dashboard)/allocations/AllocationDashboardV2.tsx:220-223`
(ready fallback) and :235-263 (`FactsheetWarmupNote`, whose JSDoc now claims "its
timer is true"). Test: `AllocationDashboardV2.rebuilding.test.tsx`, arm
"ready + a curve too short for a factsheet …".

**Issue.** Ready requires a v2 series, and `extractTrustworthyDerivedSeries`
rejects `returns.length === 0` (`src/lib/queries.ts:3674`). The writer emits one
return per union day after the first (`allocator_equity_compose.py:portfolio_returns`,
`for index in range(1, len(union))`), so a ready curve has at least 2 days and at
least 1 return. The factsheet builder returns null iff `dailyReturns.length < 2`
(`src/lib/factsheet/allocator-portfolio-payload.ts:49`). So in the typical case,
the ONLY reachable ready-plus-warm-up state is a 2-day curve with 1 return. There
the chart shows two days, and the note says panels "appear once at least two days
of blended equity history are available". That condition is already met on
screen, so the page reads as broken. The new test renders exactly this case,
`equityDailyPoints.slice(0, 2)`, and asserts that copy, so the contradiction is
now locked in as correct.

The count line in the same note reads `snapshotCount`, which is the LEGACY
snapshot count. It does not count the derived curve shown above it, so "1
snapshot recorded so far" can sit next to a chart of a different length, and a
book with no legacy rows gets no count at all.

**Failing scenario.** A new book's first v2 compose writes 2 curve days and 1
return, and the book turns ready. The Overview shows a two-point curve, and under
it: "Aggregated factsheet panels appear once at least two days of blended equity
history are available." The panels actually need a third day.

**Recommendation.** This is not a D-15 regression: plan 14 was told not to change
the copy. But the JSDoc's "its timer is true" claim is wrong. Fix the copy to
match the builder's threshold (two daily returns, which means three days of
history), or base the threshold on curve days. Base the count on
`equityDailyPoints.length` in the ready branch, not on the legacy
`snapshotCount`. Change the test to assert the corrected copy against the same
2-point fixture.

## SFH-C3-04 — LOW — The Scenario comment claims more parity with the Overview than the code gives

**Location:** `ScenarioComposer.tsx:5517-5520` ("so a book with no snapshot yet
reads here as it does on the Overview's rebuilding panel").

**Issue.** The Overview shows the panel for any non-ready book that has holdings
or `hasSyncing`. The Scenario shows its disclosure only in book mode, and book
mode requires `hasLiveBook && bookEntryGateSatisfied`
(`ScenarioComposer.tsx:969,978-980`). The first-connect book used by the
rewritten IN-01 Overview arm (no holdings, `hasSyncing`) is FORCED into blank
mode in the Scenario and gets no disclosure there. The same happens to a book
with holdings but no per-key series yet. Blank mode draws no own-book line, so
nothing false is rendered. But the comment and the SUMMARY claim "one book read
the same way" without that qualification.

**Recommendation.** Scope the comment: "…reads here as it does on the Overview
whenever book mode is available. A book forced into blank mode (no live book, or
no per-key series) has no own-book comparison to disclose." No code change.

## SFH-C3-05 — LOW — Blank-mode `it.each` title fills its slots with the wrong fields

**Location:** `ScenarioComposer.test.tsx`, the arm
`"blank mode + equityHistoryState %s (%s snapshots, %s source): no disclosure"`.

**Issue.** Each row is `[label, state, snapshotCount, source]`, and the three
`%s` placeholders take label, state and snapshotCount. The rendered titles read
"… rebuilding (rebuilding snapshots, 0 source)". A red run would then report
misleading test names. The assertions themselves are sound: the book-mode arms
above act as the positive control that the fixture does render the disclosure.

**Recommendation.** Use `%s (%s, %s snapshots, %s source)` or `$`-named
interpolation.

## Checked and clean

- **Fail-closed state.** Both `isRebuilding` (`AllocationDashboardV2.tsx:86`) and
  `isOwnBookRebuilding` (`ScenarioComposer.tsx:1009`) compare against `"ready"`
  only. The existing fail-closed arms (missing, null, "", "partial") still assert
  the disclosure in book mode.
- **No reason reaches the warm-up note.** The `isRebuilding` branch renders
  `EquityHistoryRebuilding` unconditionally, and `FactsheetWarmupNote` is
  reachable only through `!isRebuilding && factsheetPayload === null`.
- **The no-holdings EmptyState early return is unchanged**
  (`AllocationDashboardV2.tsx:136-160`). An allocator with nothing connected and
  no sync in flight never sees the panel, as D-15 requires.
- **The tests can fail.** The Overview `REASON_LINES × HISTORY_SHAPES` arm
  asserts each reason's line and the absence of `/appear once/`. Restoring the
  IN-01 `snapshotCount === 0 && source !== "derived"` branch fails the
  "0 snapshots, legacy source" shape for all 8 reasons. The Scenario
  "0 snapshots on the legacy source" arm fails under the old
  `snapshotCount > 0 || equityCurveSource === "derived"` conjunct.
- **`REASON_LINES` is typed** `satisfies ReadonlyArray<[NonNullable<…RebuildReason>, string]>`.
  This stops a wrong reason name from compiling. It does NOT force a newly added
  reason into the table, because a missing row still compiles. The renderer side
  is covered: `REASON_LINE`'s `Record<Exclude<…>>` fails to compile when a new
  reason is added.
