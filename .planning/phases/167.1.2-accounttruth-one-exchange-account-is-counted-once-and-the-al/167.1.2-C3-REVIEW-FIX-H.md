## The defect

Two `csv_daily_returns` writers made the stored rows match a fresh rebuild by deleting first and upserting after. The two were separate PostgREST statements with no transaction:
- the dailies derive (`run_derive_broker_dailies_job`, strategy mode and key mode);
- the composite stitch (`run_stitch_composite_job`).

A reader landing between the two statements saw every rebuilt day absent. Every consumer reads an absent day as a 0% day or a chain break. C3 fixes D, E and F made the readers page-consistent. No read can close a hole that the writer opens.

## Fixed Issues

### Item 1: the dailies derive upserts first, then deletes only the span days the payload lacks

**Files modified:** `analytics-service/services/job_worker.py`, plus tests (listed below)
**Commit:** `c81c43547`

**End state, unchanged.** Inside the authoritative span `[returns.index.min(), returns.index.max()]`, the stored series ends exactly equal to the fresh payload:
- a day the new derive refuses (NaN, so skipped) ends ABSENT;
- rows older than `span_start` (the retention-windowed "out-of-scope history" rule) are never named by the delete;
- the scope filter is the same as before (`api_key_id` in key mode, `strategy_id` in strategy mode).

**New order.**
1. The chunked `_upsert_dailies` runs first. `ON CONFLICT (…, date) DO UPDATE` keeps each row present.
2. Then `_reconcile_span_delete` runs once per batch. Its filters:
   - `.gte("date", span_start).lte("date", span_end)`;
   - `.in_("date", batch)`;
   - `.eq(<same scope>)`.

**The NOT IN problem, and the form chosen.** A span can be thousands of days wide. supabase-py puts a delete's filters in the URL query string, so a `not.in.(…payload…)` list is unbounded. The chosen form sends the complement instead:
- **The span's calendar days minus the payload dates**, computed client-side by the new module-level `_calendar_days_absent_from`.
- **Sent in `in.(…)` batches** of at most `_RECONCILE_DELETE_IN_BATCH = 200` dates. 200 ISO dates is about 2.4 KB of query string, well under common gateway request-line limits of 8 to 16 KB. A ten-year span refused whole is 19 statements.

Why this form:
- **The end state is exact.** `csv_daily_returns.date` is a DATE, so every stored row inside the span is one of those calendar days. Deleting exactly that list removes the same rows the old ranged delete plus re-insert removed.
- **No read of the table is needed.** A read-then-delete would add its own statement and its own race window.
- **The delete keeps the `gte/lte` span bound as well.** That is defense in depth, so the delete can never leave the span even if the list were wrong.
- **An empty complement sends no delete at all.** That is the common case: a clean series covers its whole span.

**Why not the alternatives:**
- **A ranged delete per contiguous gap run.** Scattered refused days would then cost one statement each.
- **Read the stored dates, then delete the difference.** It needs an extra read, and the result is only as fresh as that read.

**Partial failure changes shape, stated honestly.**
- Before: a worker death between the two statements left the span EMPTY.
- Now: a death after the upsert leaves the refused day's STALE row present until the retry heals it.
- A death partway through the upsert leaves some days rewritten and others still old. None is absent.

**Comments updated so they no longer say the opposite of the code:**
- the MT5-12 verdict placement block, whose rule is unchanged but whose stated reason had inverted;
- the MEDIUM-HIGH reconcile block;
- the `_load_allocator_daily_returns` docstring, which named this writer window as its unclosed residual.

### Item 2: the composite stitch upserts first, then deletes what the payload lacks

**Files modified:** `analytics-service/services/job_worker.py`, plus tests (listed below)
**Commit:** `c81c43547`

**New order.**
1. The upsert runs first.
2. Then `_reconcile_full_delete` issues two scoped deletes:
   - `.eq("strategy_id", S).lt("date", first_payload_day)`;
   - `.eq("strategy_id", S).gt("date", last_payload_day)`.
3. Then `_reconcile_gap_delete` deletes the in-span calendar days the payload lacks, in the same bounded `in.(…)` batches, also scoped and bounded `gte/lte`.

Together these delete exactly the strategy's rows that the payload does not carry. That is the same end state as the old whole-series delete plus re-insert. So F5(a) holds: full-series ownership, and a shrinking re-derive stays idempotent. The stitched series is sparse (inter-member gaps, guarded days), so its in-span complement is real and can be long, and the batching applies here too.

The Phase 105 D5 "honest boundary" comment was updated to describe the new order.

### Item 3: `_load_series` in the CSV analytics runner pages by keyset on `date`

**Files modified:** `analytics-service/services/analytics_runner.py`, plus tests (listed below)
**Commit:** `5fe8525d4`

**The read.** New module-level `_load_strategy_daily_returns(supabase, strategy_id, *, page_size=1000, hard_cap_pages=1000)`, modelled on C3 fix E's `_load_allocator_daily_returns`:
- each page is `eq("strategy_id") [+ gt("date", cursor)] + order("date") + limit`;
- the read stops on the first EMPTY page, not a short one;
- past the cap it raises `PaginatedSelectTruncated` with the byte-same hint (`csv_daily_returns strategy_id=<id>`), so the runner's typed truncation arm and its row-cap sentence are unchanged.

`(strategy_id, date)` is UNIQUE (`csv_daily_returns_strategy_date_key`), so with the strategy fixed by `eq`, the `date` cursor is a total order.

**Wiring.** `_load_series` keeps its name, because a WR-03 test keys its `db_execute` side effect on `fn.__name__ == "_load_series"`. It now just calls the helper. `paginated_select` stays imported: it is still used at `analytics_runner.py:399`.

## Known limits

- **Fakes, not PostgREST.** The fakes compare `date` as ISO strings, and apply `in` / `lt` / `gt` in Python. For `YYYY-MM-DD` values the order matches Postgres DATE.
  - The real `in.(…)` URL length was not measured against the PROD gateway. The 200-date cap is a reasoned bound, not a measured one.
  - `ON CONFLICT (strategy_id, date) DO UPDATE` and `ON CONFLICT (api_key_id, date) DO UPDATE` now actually take the UPDATE arm on a re-derive. Before, the delete emptied the span first, so the upsert inserted.
    - The conflict targets and unique indexes are unchanged: `csv_daily_returns_strategy_date_key` and `csv_daily_returns_api_key_date_key`, both non-partial.
    - The `csv_daily_returns_owner_coherence` trigger fires on UPDATE as well as INSERT, for key-mode rows, with the same owner values.
    - This path was not exercised against a live database here.
- **`created_at` and `updated_at` on an overwritten row.** An overwritten row now keeps its original `created_at` and `id`. `updated_at` is not bumped (no trigger does it, and the payload does not carry it), where before the fix every rebuilt row was a fresh insert. No Python reader uses either column. A SQL or TS reader was not checked.
- **Tests the old order bound only indirectly.** The existing stitch and parity suites do not distinguish the old order from the new one (N2 above). `test_h2_…` is the only guard on the composite's order.
- **Pre-existing staleness, not changed here.** Staleness from an absorbed follow-up compose (fix E's Residual 2) is unchanged.
