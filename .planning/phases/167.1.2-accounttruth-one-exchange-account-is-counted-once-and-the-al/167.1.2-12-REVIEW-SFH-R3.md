## The three fix-introduced risks the brief asked about

### (b1) A failed probe read fails the job: not a new failure class

- All three probe reads go through `db_execute`. `db_execute` does not swallow errors, and the
  PostgREST client raises on an HTTP error. A raise reaches the existing
  `except Exception` in `run_refresh_allocator_equity_daily_job`, which calls `logger.exception`,
  emits the `refresh_failed` audit and returns `FAILED` with a `classify_exception` kind.
- A transient read error becomes `failed_retry` and is claimed again. This is the same contract
  the `_fetch_latest_holdings_per_eligible_key` reads above it already had. The fix adds one
  round-trip per refresh job (the snapshot-existence read) on the common path, and three on a
  zero-snapshot book.
- A failed probe never falls through to the write. The tests pin this: 3 failure cases each
  assert `FAILED` and no row.
- **Verdict: no new CRITICAL/HIGH.** One LOW about fail-open on a *successful* but empty
  response is L-2.

### (b2) The unwrapped per-book `cron_runs` write escalating: bounded, LOW

See L-1. The write can only escalate when the sink refuses a row that satisfies its one CHECK.
`SECURITY DEFINER` as owner bypasses the table's RLS, and no migration creates a trigger on the
table.
The realistic trigger is therefore a future schema change, not a data condition. The cost when
it does fire is real, though, so it is recorded.

### (b3) A book held forever: no

The hold lasts only while a `reconstruct_allocator_history` row for one of the owner's keys is
in `pending`, `running`, `done_pending_children` or `failed_retry`. Each of those statuses
ends on its own:

- `running` is terminalised by the hourly orphaned-running reaper (`20260826140000`).
- `failed_retry` runs out of attempts and ends `failed_final`.
- `pending` is claimed. The claim's per-kind partitions never block across kinds.
- `done_pending_children` is set only for a job whose `parent_job_ids` is non-empty
  (`20260510180226`). The fan-out's `enqueue_compute_job` call passes no parents.

A key under a persistent 429 cooldown defers its reconstruct indefinitely, which keeps the
hold on. The refresh goes through the same `_allocator_key_preflight` circuit-breaker check,
though, so that book would not have been written before the fix either. That is not a
regression.

A held job ends `DONE`. The next fan-out enqueues a new refresh, because the idempotency key
is per day and the dedupe checks only in-flight rows. After a `done` reconstruct, the next
refresh writes.

## Findings

### M-1 (MEDIUM, routing): the fast-fail race is routed in CONTEXT only, not in the queue

- **Location.** `.planning/ROADMAP.md` `### Phase 167.1.2.1: RECONMARKER` (on `origin/main`,
  from #889), compared with `167.1.2-CONTEXT.md` D-20.
- **Issue.**
  - D-20 routes five items to RECONMARKER, including "the fast-fail `failed_final` race
    recorded in 167.1.2-12-REVIEW-FIX Round 2".
  - RECONMARKER's ROADMAP **Evidence** list and its six **Success Criteria** cover R-12-1,
    R-13-1, the two-key sibling path and the `request_allocator_holdings_sync` `failed_retry`
    list. **None of them names the same-run fast-fail race.** Criterion 5 is about the RPC's
    status list, not this cron path.
  - The ROADMAP is the queue a planner reads. So the phase can close with all six criteria
    green while this path stays open. A per-key marker would close it in principle, but no
    criterion requires a test that fails on the old behaviour for it.
  - This is the "a scope amendment touching ONE file is incomplete" class.
- **User impact.** The failure is a data-integrity loss with no user signal: a key's pre-connect
  equity history is never backfilled, and the only trace is the `failed_final` row, which is
  reaped after 90 days.
- **Recommendation.** Add a seventh evidence bullet and success criterion through
  `/gsd-phase --edit 167.1.2.1`. Suggested criterion: "a zero-snapshot book whose same-run
  reconstruct reaches `failed_final` BEFORE its refresh job is claimed is still retried. A
  test fails on the old behaviour."

### M-2 (MEDIUM, understated reach): the fast-fail race is wider than "both claimed at once"

- **Location.** `167.1.2-12-REVIEW-FIX.md` Round 2, "⚠️ Routed", item 4.
- **What is stated.** The race can happen "when both jobs are claimed at once
  (`claim_compute_jobs_with_priority` gives both rows the same transaction `now()`)".
- **What the code does.**
  - `claim_compute_jobs_with_priority` orders by priority, then `next_attempt_at`, then `id`.
  - `next_attempt_at` defaults to `now()`, and so does every row one fan-out call inserts. That
    covers every bootstrap reconstruct and one refresh per eligible key of **every** book that
    has snapshots, all sharing one transaction timestamp.
  - `id` is `gen_random_uuid()`, and the worker claims 5 at a time (`p_batch_size`,
    `main_worker.py`).
  - So within one fan-out burst, a book's reconstruct and its refresh are claimed in random
    order, usually in different batches. The race window runs from the reconstruct's claim to
    the refresh's claim, which can be up to the drain time of the whole burst. It is not
    limited to a co-claim.
- **What still bounds it.**
  - Only a `permanent`-class failure goes straight to `failed_final`, and it has to happen
    early in the crawl.
  - `transient` and `unknown` failures pass through `failed_retry`, and the hold covers that
    status.
  - `InvalidToken` fails the refresh's own preflight too (both call `decrypt_credentials`), so
    neither job writes and the book is retried.
  - The reachable population is a reconstruct that fails permanently on an exchange call (for
    example a credential rejected by the venue) while the key's DB holdings rows still let the
    refresh write. The refresh makes no exchange call.
- **Is it silently worse than stated?** In reach, yes: the trigger is "the reconstruct ends
  permanently before the refresh is claimed", not "both claimed at once". In class, no: it is
  the same failure mode, and it is strictly narrower than the pre-fix state, where every
  failure path stranded the key. This finding does not reopen SFH-R2-01. It corrects the
  trigger condition the routing record carries.
- **Recommendation.** Restate item 4 of the fix report, and the new RECONMARKER bullet from
  M-1, as "the reconstruct reaches `failed_final` before the refresh is claimed. Claim order
  within one fan-out burst is by random UUID, batch 5, so the window is up to the burst's
  drain time". Any fix belongs to RECONMARKER.
  - A cheap interim control could live in the worker: also hold when the owner's newest
    reconstruct row is `failed_final` **and** was created in the same fan-out run as this
    refresh. That is not recommended here, because it moves toward SFH-R2-05's give-up
    policy, which is not a fixer's call.

### L-1 (LOW): a refusing sink turns one poisoned book back into "every book rolled back"

- **Location.** `enqueue_refresh_allocator_equity_for_all`, the per-book `EXCEPTION WHEN OTHERS`
  handler's `INSERT INTO public.cron_runs`, which is deliberately not wrapped.
- **Issue.**
  - When the per-book INSERT raises, the error reaches the sub-block handler. That rolls back
    **every** book's enqueues from this run, including books that were enqueued cleanly before
    the poisoned one, and every per-book row already written.
  - The sub-block then writes its own row to the **same** sink. Whatever refused the first row
    will most likely refuse this one too, and its wrapped handler reduces it to a WARNING.
  - So in the only case the design exists for (the sink refuses), the result is the pre-SFH-R2-03
    outcome: every book's bootstrap is cancelled, every day, and the only trace is a WARNING in
    the server log. The stated rationale, "a skip is never left with no trace at all", holds
    only when the sink refuses the first row and accepts the second.
- **Hidden errors.** A future CHECK or trigger on `cron_runs`, or a schema change to it. The
  pg-lane X4 fixture is exactly this shape: a trigger that refuses one key's row. X4 pins that
  the refresh survives, not that the other books' bootstraps survive.
- **Why LOW.** It needs two independent faults: a key whose enqueue always fails, and a sink
  that refuses a row satisfying `cron_runs`' only CHECK. The refresh loop still runs, and
  withheld books stay withheld, never wrongly written.
- **Recommendation (optional).** Wrap the per-book INSERT the way the sub-block's write is
  wrapped, with `WHEN OTHERS` and then a WARNING naming the owner, the key and both SQLSTATEs.
  A refusing sink then costs one book's trace, not every book's bootstrap. X4 would move to
  asserting that the older book is still bootstrapped.

### L-2 (LOW): the probe fails OPEN on a successful-but-empty key read

- **Location.** `_inflight_reconstructs_for_zero_snapshot_book`, the `key_ids` list and the
  `if not key_ids: return 0` branch. Also the `count is None` fallback to
  `len(data or [])`.
- **Issue.**
  - `allocator_id` is `ctx.key_row["user_id"]`, and the job's own `api_key_id` belongs to it.
    So a legitimate `api_keys` read can never come back empty.
  - An empty `data` (or `data=None` on a 2xx) is therefore an anomaly. The helper reads it as
    "nothing in flight", returns 0, and the caller writes the first row. That is the exact
    write the hold exists to prevent.
  - The same holds when `count` is absent and `data` is `None` on the in-flight read.
  - Both need a malformed success response, because an HTTP error raises. Hence LOW.
- **Recommendation.** Seed `key_ids` with the job's own `api_key_id` (pass it in), or raise on
  an empty key list. On the in-flight read, raise when both `count` and `data` are `None`.
  Either way the fail direction becomes "hold or FAILED", never "write".

## Known and not re-raised

These were raised in earlier rounds and not re-raised here:

- SFH-R2-05: no back-off or give-up.
- The `bootstrap_*` `cron_runs` rows are durable but unwatched. No prober arm reads
  `cron_name 'equity_refresh_fanout'`. This is the remaining half of round-1 SFH-03.
- `query_canceled` is uncaught by design.
- `v_bootstrap_enqueued` counts skipped keys.

One more point: a book with a key whose enqueue always fails is now skipped for good,
with one `bootstrap_book_skipped` row per day. That is correct and traced, but no one watches
it. The same unwatched-rows gap covers it.

## Well done

- The probe's docstring and the call-site comment both state the fail direction (raise, then
  `FAILED`, never write), and the tests pin it.
- The hold emits a counts-only audit with a new action kept in parity across
  `services/audit.py`, `AllocatorEquityAction` and `src/lib/audit.ts`. No DB CHECK on
  `audit_log.action` exists that could drop it. `_emit_audit` swallows with a WARNING by its
  documented P907 contract, so a dropped audit never fails the job.
- `v_boot_key` is reset for each book, so a per-book row never names the previous book's key.
