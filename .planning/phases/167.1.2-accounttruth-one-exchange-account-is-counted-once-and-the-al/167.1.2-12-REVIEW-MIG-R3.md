Notes on each:

- **SFH-R2-01.** The probe reads three things: the book's snapshot existence, the
  owner's key ids, and the in-flight reconstruct count. It runs AFTER the
  `no_holdings_today` return and INSIDE the job's `try`, so a raising read lands
  in the `except Exception` handler: the job is `FAILED` with a `refresh_failed`
  audit, and no row is written. The hold returns `DONE` with no upsert.
  - No day-one gap: `run_reconstruct_allocator_history_job` sets its `end_date`
    to today (UTC), so a held refresh loses no day that the reconstruct does not
    write itself.
  - `_RECONSTRUCT_IN_FLIGHT_STATUSES` is the migration's in-flight-or-done list
    minus `done`, which is right: a `done` reconstruct has written what it could.
  - A reconstruct stuck in `running` would hold the refresh indefinitely. The
    existing `reset_stalled_compute_jobs` reaper bounds that, and the SQL bootstrap
    already treats `running` as in flight, so the hold adds no new stuck state.
  - The pinning test file `test_refresh_holds_for_inflight_reconstruct.py` carries
    the controls the report claims: `test_done_reconstruct_on_zero_snapshot_book_still_writes`,
    `test_book_with_snapshots_writes_despite_inflight_reconstruct`,
    `test_no_holdings_path_is_unchanged_by_the_hold`, and
    `test_a_failed_probe_read_fails_the_job_and_writes_nothing`.
  - The new audit action is added to both `services/audit.py` `AuditAction` and
    `services/job_worker.py` `AllocatorEquityAction`. The TS side is outside this
    review's scope; the report says `test_action_literal_matches_ts_union` passes.
- **SFH-R2-03.** Each book's key loop is wrapped in its own `BEGIN ... EXCEPTION
  WHEN OTHERS`. On the refused book, the per-key `unique_violation OR
  serialization_failure` catch still skips one key only. Any other error rolls
  back that book's savepoint and the outer `FOR v_book` continues. The outer
  cursor's portal belongs to the enclosing subtransaction, so it survives the
  inner rollback. X2 (an older book is still bootstrapped after the refused one)
  measures exactly that. `v_boot_key` is reset to NULL per book, so the WARNING
  and the row never name the previous book's key.
- **SFH-R2-02 and MIG-R2-01.** See (b) for whether the sink accepts the rows. The
  sub-block handler copies `SQLSTATE` and `SQLERRM` into `v_loop_state` and
  `v_loop_msg` BEFORE its nested `BEGIN`. That is necessary, because inside the
  nested handler `SQLSTATE` would name the INSERT's error, not the loop's. It is
  done correctly.
- **SFH-R2-04.** N4r's mutation removes `failed_retry` from the `bqj` and `rkj`
  status lists only and leaves the bootstrapped subquery's `bkj` intact. The arm
  still bites: the book is re-selected, and the enqueue helper's narrower
  in-flight list does not see the `failed_retry` row, so a second reconstruct
  row appears.

Checked for the `public.cron_runs` writes:

- **CHECKs and defaults.** `cron_runs_status_check` admits `'error'`. There is no
  CHECK on `error` or `cron_name`. `started_at` defaults to `now()` and is the
  only other NOT NULL column besides `id` (defaulted). Both INSERTs name every
  required column.
- **Row security and ownership.** RLS is ENABLED, not FORCED, and the table is
  owned by `postgres`. The function is SECURITY DEFINER; a CREATE OR REPLACE
  keeps the 075 owner, `postgres`. So the INSERT is exempt from row security by
  ownership, exactly as the ledger fan-outs' `candidate_enqueue_failed` writes
  already are in PROD. No grant change is needed or made. The existing guard
  comments across the ledger fan-outs and `mt5_session_episodes` already forbid
  FORCE on this table.

  narrows by name: `prod_prober_cadence_check` (`prod_prober`),
  `latest_cron_success` (its parameter, and `status = 'ok'`),

- **Metadata.** Only UUIDs, the SQLSTATE and SQLERRM, never

## INFO (below the reporting bar)

- **INFO-1: compound fault on the unwrapped per-book write.**
  - **The fault.** Suppose the sink refuses the `bootstrap_book_skipped` row (a
    future FORCE, a CHECK on `error`, a trigger). Then the error leaves the
    per-book handler, and the sub-block rolls back every book's bootstrap for that
    run. The sub-block row is the same table and near the same shape, so it is
    very likely refused too, and the run leaves a WARNING only.
  - **The comment's claim is conditional.** The inline comment says "a skip is
    never left with no trace at all". That holds only if the sink accepts one row
    shape and refuses the other.
  - **Why it is only INFO.** It takes two independent faults, a book that always
    fails AND a sink that refuses. The blast radius is the pre-migration state (no
    bootstrap), never worse, and the daily refresh still runs.
  - **Optional tightening.** Soften the comment's wording. No code change is
    needed.
- **INFO-2: the sub-block row loses the original cause.** When the per-book INSERT
  is what escalates, `bootstrap_loop_failed` records the INSERT's SQLSTATE, not the
  enqueue error that made the book skip. That is acceptable, because the cause is
  the sink.
- **INFO-3: the rows are durable but not watched.** No prober arm reads
  `cron_name 'equity_refresh_fanout'` yet. This is the still-open half of
  round-1 SFH-03, and the fix report already states it.
- **INFO-4: the fix report's routing is now stale.** The round-2 fix report calls
  the "durable per-key history-reconstructed marker" class (R-12-1, R-13-1, the
  two-key sibling, the fast-fail `failed_final` ordering) UNROUTED. Two places now
  route it to Phase 167.1.2.1 RECONMARKER:
  - `167.1.2-CONTEXT.md` decision D-20 does, and it also adds the RPC's
    `failed_retry` status-list gap;
  - main's ROADMAP carries that phase.

  The migration header still says "UNROUTED, founder decision". Updating that
  prose to name the phase would keep the header honest. It is a comment-only edit,
  but it moves nothing the gate reads only if no RED-UNDER find string spans
  those lines, so check that first.
