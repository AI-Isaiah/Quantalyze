## Fixed Issues

### SFH-C3R2-X1: the dashboard's per-key `csv_daily_returns` read silently dropped the newest rows past 1000

**Files modified:** `src/lib/drain-by-id.ts` (new), `src/lib/drain-by-id.test.ts` (new), `src/lib/queries.ts`, `src/lib/queries.my-allocation.test.ts`
**Commit:** `37e16b80d`

**The defect.** `getMyAllocationDashboard` read the rows in ONE request:
`.order("date", asc).limit(20000)`. PostgREST caps every response at `max_rows`
(1000 on PROD), whatever limit the client asks for. It still answers HTTP 200
with `error: null`, and because the order was ascending the rows it dropped
were the newest. The orchestrator's read-only PROD measurement (2026-09-29)
found one allocator with 2348 rows inside the 730-day window, so that
dashboard was reading only its oldest 1000 rows.

**Applied fix.**
- **A new helper, `src/lib/drain-by-id.ts` (`drainById`).** `src/lib` had no
  shared pagination helper. There were two inline patterns:
  - `portfolio-exposure.ts` `fetchHoldings`: offset `.range()`, stops on a
    short page.
  - `factsheet/benchmark-source.ts` `readBenchmarkPrices`: keyset, stops on an
    empty page, has a page ceiling, checks the cursor is monotone.

  The helper generalises the benchmark-source discipline, which is the newer
  and stricter of the two. It works like this:
  - **Keyset on the `id` bigint PK.** Each request is `id > cursor`, ordered by
    `id`, with `.limit(1000)`. `id` alone is a total order.
  - **It stops on an EMPTY page, never on a short one.** A server cap below the
    page size makes every page short, so a short-page stop would truncate.
  - **Ids must strictly increase across pages.** A repeat or an out-of-order id
    is an ERROR.
  - **A page with neither data nor an error is an ERROR.**
  - **At 100 pages it returns an ERROR** instead of a partial read.
  - **Natural-key duplicates collapse to the larger id.** One can arise when a
    delete then re-upsert lands in the middle of a drain.
  - **The rows come back sorted by the natural key.**
  - **Why `id` and not the natural key `(api_key_id, date)`.** The writers
    delete a span and then re-upsert it, and a re-inserted row gets a larger
    id. An id cursor still reaches that row later in the same drain. A
    natural-key cursor that had already passed its `(key, date)` would skip
    it. Offsets would skip a row whenever a delete lands between pages.
  - **Failure is returned as a value, not thrown.** The result is
    `{ data, error }`, the shape supabase-js resolves to.
- **`queries.ts`.** The read is now an async IIFE, matching the
  `allocator_equity_derived` member of the same `Promise.all`, and it calls
  `drainById` with:
  - `.select("id, api_key_id, date, daily_return")`;
  - `.eq("allocator_id", userId)`;
  - `.not("api_key_id", "is", null)`;
  - `.gte("date", <730d>)`;
  - a natural key of `${api_key_id}|${date}`.

  Other details:
  - A drain failure resolves `{ data: null, error }`. The existing
    `assertOk(phase36PerKeyDailiesRes, "csv_daily_returns")` then logs and
    throws, which is the dashboard's existing read-failure path. There is never
    a silent partial series.
  - The rows are sorted by `(api_key_id, date)`. That is the per-key date
    order `buildPerKeyReturnsByApiKeyId` relies on, so its contract is
    unchanged.
  - NULL `api_key_id` rows (strategy-scoped rows) are excluded at the query.
    The consumer already dropped them, and without the filter they would
    collide on the natural key.
  - The false "flat SAFETY CEILING … without truncating recent data" comment is
    rewritten.

**Status: fixed. Requires human verification of one semantic point:** the
dedupe keeps the larger id. That is correct only if the larger id is always the
newer write. It is for a GENERATED ALWAYS identity column, which
`csv_daily_returns.id` is (baseline.sql, `ADD GENERATED ALWAYS AS IDENTITY`).

### SFH-C3R2-X1 sweep: the wizard's composite series read (`SyncPreviewStep.tsx`, was ~:1442)

**Files modified:** `src/app/(dashboard)/strategies/new/wizard/steps/SyncPreviewStep.tsx`, `SyncPreviewStep.composite.render.test.tsx`, `SyncPreviewStep.own04-link.test.tsx`
**Commit:** `9a6eb2a6e`

**The defect.** This was the same single `.order("date", asc).limit(20000)`
request, under a "Flat safety ceiling" comment that cited the queries.ts read
as precedent. A stitched composite with more than 1000 days (about 2.7 years)
reached the preview with only its oldest 1000 days. That corrupted what the
composite arm computes:
- `csvRowCount` was wrong.
- The `compositeSparkline` fallback ended early.
- `composite.series` fed the attribution table and the gantt without its
  newest days.
- The R2-4 reconciliation caption epsilon-checks the series against the
  server's `cumulative_return`, so it could not reconcile.

The 7-row floor comparison is a lower bound, so the cap did not corrupt it.

**Applied fix.** The series now drains through `drainById`, with natural key
`date`, which is unique per strategy (`csv_daily_returns_strategy_date_key`).
The result is deduplicated and sorted by date.
- A drain failure resolves `{ data: null, error }` and throws through the
  existing `composite series read failed` branch into `heavyFetchErrorsRef`.
- The `id` cursor column is stripped before the series enters the snapshot, so
  the snapshot shape is unchanged.

## Residuals (recorded, not fixed)

- **No snapshot across pages.** Each page is a separate request. A key's span
  deleted and re-upserted in the middle of a drain is still read completely,
  because re-inserted rows get larger ids and the drain reaches them. Two
  windows can still break this:
  - **Rows written after the drain's final empty page are not read.** That is
    the same freshness a single request has.
  - **A day deleted before the drain reads it, and not re-inserted before the
    drain ends, is absent.** The writer's own delete-then-upsert window shows
    this regardless of pagination.

  This is the TypeScript twin of SFH-C3R2-01, now narrowed. It is MEDIUM or
  lower, so no fix round is owed.
- **`composite-read-path.ts:228` still carries the defect** (see the sweep
  table). Phase 169 owns it.
- **One extra round trip per read, accepted.** The drain ends only on an
  EMPTY page. So a dashboard allocator with 1 to 999 rows now costs 2
  sequential requests on its `Promise.all` member instead of 1, and every
  composite terminal poll costs one extra request too. This is the price of
  not trusting a short page: a server cap below the page size would make
  every page short. `benchmark-source.ts` accepted the same trade.
- **Two SyncPreviewStep test fakes are not yet drain-aware.**
  `SyncPreviewStep.stale-refusal.runtime.test.tsx` and
  `SyncPreviewStep.readfailure.runtime.test.tsx` have no `gt` and serve
  composite rows without an `id`. They pass legitimately:
  - stale-refusal's composite case (T3b) seeds `HEAL_DELETE_ROWS = 0`, so the
    first page is empty and the real R2-5 empty-series repoll runs;
  - readfailure drives single-key runs only (`composite: false`).

  A future test that seeds composite rows in either file must serve an `id`
  and honour `gt`, as the `pagedSeries` fake in the two updated files does.
  Otherwise the drain refuses the rows as `row without an integer id`, and
  that failure is tolerated as a heavy fault that repolls, which looks like
  the waiting state.
