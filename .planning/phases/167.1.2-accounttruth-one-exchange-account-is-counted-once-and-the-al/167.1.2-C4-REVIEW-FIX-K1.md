### SFH-C4-02: a key that closes its last position keeps showing it (HIGH)

**Deviation from the brief, on purpose.** The brief asked for a "polled, empty" marker
row on the ccxt and Deribit paths, like MT5's `$0` row. That was not done. The fix is on
the read side and uses a marker the poll already writes.

Why not a marker row:
1. **It would silently break the daily refresh's emptiness guard.** In
   `equity_reconstruction.py` `_polled_empty_since`, any event with `row_count > 0` vetoes
   the proof, and the refresh then takes the group's rows at the latest asof. A marker row
   makes `row_count = 1`. On a parse-empty day (the Bybit UTA case that C2 round 3,
   SFH-R3-01, cross-checks against the key's live equity read), the refresh would read the
   marker, publish `$0` for a funded account, and keep it (the snapshot is
   first-writer-wins). Fixing that means editing `equity_reconstruction.py`, which is
   outside K1.
2. **It reaches readers K1 does not own.** A marker row would also reach
   `portfolio-exposure.ts`, the scenario commit route's audit recompute and its SQL RPC,
   `match.py`, `notes/scope-ref.ts` and the GDPR export. The brief's own clause, "make
   sure every reader treats the marker as no position", would require editing all of
   them. Under the brief's rule, that is a stop-and-report for the marker route.

What was done instead:
- The poll already records "polled, and what it read". The success arm emits
  `allocator.holdings.sync_completed` with metadata `{final_status, row_count, asof}`
  (`job_worker.py`, `run_poll_allocator_positions_job`). This is the same evidence the
  refresh's proof reads.
- `audit_log_owner_read` lets the user-scoped client read it.
- `fetchLatestHoldingsPerKey` now reads each key's newest event with
  `final_status = complete`, scoped by `user_id`, `action`, `entity_type` and
  `entity_id`. If that poll read the key on a day after the key's latest rows, those rows
  are not current and the key contributes nothing.
- None of these count as evidence: a poll with warnings, an event with no `asof` (from
  before C2 round 3), an event on the rows' own day, a malformed `row_count`, and a
  missing event. In each case the key keeps its latest rows.

**The same rule covers WR-02's failure on the read side.** Suppose a clean poll wrote
rows, but another key's upsert later relabelled them. The key's latest asof then falls
back a day, while its poll record says it read on the later day. The key's older rows no
longer come back.

**Known limit, recorded in the docblock.** This shows what the poll read. Suppose a poll
reads a funded account as empty (the Bybit UTA parse miss). The key then shows flat until
its next poll. That is transient on the display. The refresh's `$0` would be permanent,
which is why the refresh keeps its stricter proof. The D-16 docblock line "a quiet key
still shows its last poll, never flat" was reworded to "a key that has not polled".

**Follow-up `5010706fc`.** The SI-01 census (`complete-status-scan.test.ts`) counts an
exact comparison to the complete status anywhere in `src/`, comments included. The first
commit's docblock spelled one out, so the prose was reworded. The code keeps
`!== "complete"` deliberately: `complete_with_warnings` proves no emptiness.

**Tests** (`src/lib/latest-holdings-per-key.test.ts`):

- The newest clean poll decides.
- Five no-evidence arms.
- The WR-02 not-worse arm.
- Another user's events are never read.
- A poll-outcome read error is returned as an error.

### SFH-C4-01: a closed position shows across a key rotation (HIGH)

`fetchLatestHoldingsPerKey` now reads each key's identity columns: `exchange`,
`venue_account_id`, `account_share_kind` and `account_shared_with_api_key_id`. All of them
are in `API_KEY_USER_COLUMNS`.

The keys are grouped with `accountIdentityTokens`, the D-09 identity. It is imported
read-only from `src/lib/departed-history.ts` and was not modified there. Only the keys
holding the account's newest reading, with rows on that day, have their rows read. A
clean empty poll (SFH-C4-02) counts as a reading.

This is the account grain the Python plan-10 reader already uses ("a departed member's
rows are still that account's"). It settles every case with one rule, not a second
departed-vs-live rule:

| Case | Result |
|---|---|
| Live key has a newer reading | the departed key's rows leave |
| Live key has a newer clean empty poll, even with no rows ever | the departed key's rows leave |
| A marker link joins a key that has no venue id | same account |
| Live key never polled | the departed key's rows stand |
| Live key's last reading is older | the departed key's rows stand, the live key's leave |
| Different account | both stand |
| Unknown identity | each key is its own account |

Dropping superseded rows moves no dollars out of a disclosure. The newer reading is the
account's current value. `queries.ts`'s collapse comment now says so.

**Tests:**
- Seven arms in `latest-holdings-per-key.test.ts`.
- One end-to-end arm in `queries.my-allocation.test.ts`: a rotation through
  `getMyAllocationDashboard`.
- The owner-filter test now pins the identity select and the `audit_log` read's scoping.

**Neuter:** making every key its own account turned 5 helper arms and the end-to-end arm
RED.

**Residual, not fixable on the reader.** Take a rotation whose old key was never stamped
and never marked, such as a pre-C1 departure on a ccxt venue. Nothing ties the two keys
together, so the old key stays its own account and its rows stand. SFH-C4-08 now dates
those rows, so the reader can see how old they are. The same limit applies to the book
(D-09 case 3).

### WR-01: a partial poll hides all of that key's derivative positions (WARNING)

**Choice: surface it, rather than stop the per-key latest from advancing.** Holding a
key's latest read back to an older complete day would also show a stale spot book. Under
repeated derivative failures it would show an arbitrarily old one. It would also need
day-binding of each poll's outcome in the reader, when the only discriminator today is the
event's `final_status`.

How the poll records the failure:
- On a ccxt venue (binance, okx, bybit, deribit), `fetch_allocator_holdings` has exactly
  one warning source: a failed derivative-side read. It keeps the spot rows and returns
  `DERIVATIVE_FETCH_FAILED_NOTE`.
- A spot failure raises instead.
- The handler turns the warning into `sync_status = complete_with_warnings`.

What the Holdings tab now shows:
- One line per connected ccxt key in that state, under Open Positions: "Open positions
  from the Binance key Main could not be read on its last sync. Any it holds are missing
  below until a sync reads them."
- MT5 and sFOX warnings mean something else, so those keys get no line.
- Departed keys are not polled, so they get no line either.
- The line reads the key's current `sync_status`, which moves on with the next sync, so it
  clears when a sync reads the positions again.

**Tests:** 6 arms.

**Neuter:**
- A never-matching status turned the naming arm RED.
- Dropping the live-key and venue gates turned the 4 exclusion arms RED.

### SFH-C4-04: a "ready" book is silently missing a departed account's history (HIGH)

- The flag is `departed_history_unavailable`, the writer's name, unchanged. It sits in the
  payload's sorted `flags` list (`allocator_equity_compose.py:562`, raised from
  `job_worker.py` `benign_flag_tokens`).
- The producer in `derivePhase07Fields` reads it defensively (`Array.isArray` plus
  membership), and only when `equityHistoryState === "ready"`. It exposes it as
  `departedHistoryUnavailable`, and both payload branches carry it through `...phase07`.
- `AllocationDashboardV2` renders one `role="status"` line under its banners on a ready
  curve: "This curve leaves out the history of at least one disconnected account, because
  the balance that history is measured from is not available."
- The line is not a blocker, as the writer's comment requires.

**The count N is not available.** The payload flag is a presence token with no count.
The line therefore says "at least one" rather than inventing N. To say N, the writer
needs a count field, for example `departed_history_unavailable_count`. That field belongs
in `job_worker.py`, which is K2a's file and was not edited. **Route:** a writer-side count
field plus the reader's copy change.

The copy says "is not available" rather than "was deleted". SFH-C4-06 shows the null
anchor can also be a failed balance read, so "deleted" could be false.

**Tests:**

  rebuilding; no row.
- 3 render arms in `AllocationDashboardV2.departed-history.test.tsx`.

**Neuter:**

### WR-02: the holdings unique index lacks `api_key_id` (WARNING)

This needs a migration. Migrations auto-apply to PROD, so none was written here.
**Route it** with this record:

- **Index:** `allocator_holdings_owner_venue_symbol_asof_key`, UNIQUE on
  `(allocator_id, venue, symbol, asof)`. See `supabase/schema/baseline.sql:13226`.
- **Writer:** `persist_allocator_holdings` in
  `analytics-service/services/allocator_positions.py` upserts with
  `on_conflict="allocator_id,venue,symbol,asof"`. The real fix changes the index to
  `(allocator_id, api_key_id, venue, symbol, asof)` and the writer's `on_conflict` in the
  same release.
- **Existing workaround in the writer:** MT5's account-scoped symbol
  `ACCOUNT-{api_key_id[:8]}` (`_fetch_mt5_account_rows`), written for exactly this
  collision (151-RESEARCH Pitfall 1).
- **Other readers that assume one row per `(venue, symbol, asof)`,** which the migration
  must check:
  - the scenario commit route's audit recompute and its `commit_scenario_batch` RPC
    fingerprint;
  - `portfolio-exposure.ts`;
  - `equity_reconstruction.py`'s refresh. Its docblock already records the "167.1.1 index
    defect" residual.
- **What the reader can and cannot do.** The reader cannot repair a relabelled row. It
  now does not make the defect worse: a key whose clean poll read it after its latest rows
  no longer brings back its older rows (SFH-C4-02's rule). A relabelled row still shows
  under the key that took it, and Open Positions' venue:symbol:type collapse still keeps
  one of two same-symbol positions on two different accounts of one venue.
