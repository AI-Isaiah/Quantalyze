## Point 1: coupling matrix (refresh persists / derive writes / page shows)

H = holder with the stamped id. M = marked key with a NULL id, which is the production shape. "Once" means the account's rows are read once for the group, at the group's latest `asof`. Page results come from the tsx probe over `equityHistoryReadiness`, with a v2 series present. Derive results come from reading `run_derive_allocator_equity_job:10354-10450` and are cross-checked against fixer A's tests.

**`duplicate`**

| H \ M | M working | M `error` / `sign_in_failed` | M inactive / revoked / disconnected |
|---|---|---|---|
| H working | once / REFUSE (row deleted) / `duplicate_account` | once / REFUSE / `duplicate_account` | once via H / H / ready |
| H `error` / `sign_in_failed` | once / M (H dropped) / ready | once, `no_working_accounts` += 1 / earliest-start key, flag `shared_account_no_working_key` / ready | once via H / H / ready |
| H inactive / revoked / disconnected | once / M / ready | once, carried / M / ready | not counted anywhere (no eligible member) / not composed / ready (other keys) |

**`composite_member`**: every cell except "H working" is identical to `duplicate`. With H working, the derive never refuses. It keeps the earliest-start member (M working), or H (M failing or not eligible), and the page reads ready.

**Unmarked pair (not in the brief, and the one cell that disagrees).** A (`error`, NULL id, never stamped) + B (working, stamped), one account: the refresh persists the account **twice** / the derive composes BOTH (the NULL id hides the pair from the collision gate) / the page shows `key_not_syncing`. The screen is held, so no "ready over a double count" cell exists. The legacy store is wrong (R2-CR-02).

No cell renders "ready" while a writer double-counts or drops an account.

## Critical Issues

### R2-CR-01: CR-04's emptiness proof is judged on the key's CURRENT status, so a proven-empty account goes back to its old balance on any refresh that sees `rate_limited` or `syncing`

**File:** `analytics-service/services/equity_reconstruction.py:2002-2009` (`candidate_ids` requires `r.get("sync_status") == "complete"`), used at `:1955-1959`

**Issue.** Fixer A's proof is "a done `poll_allocator_positions` job claimed after the group's latest `asof`". The candidate filter, though, reads the key's status at REFRESH time, not the outcome of the poll that supplies the proof. That status moves independently of the proof:
- A 04:00 poll that hits a 429 writes `rate_limited` (`job_worker.py` 429 arm).
- A manual `request_allocator_holdings_sync` writes `syncing` (`baseline.sql:8029`), which a circuit-breaker DEFERRED keeps in place.

On such a day, yesterday's done-and-empty poll is ignored, and the account is carried at its last positive `asof`: a balance the proof has already superseded. The row is written `ON CONFLICT (allocator_id, asof) DO NOTHING` and never rewritten. Measured with the refresh fixture (emptied bybit account with BTC 500 three days ago, done poll claimed yesterday, live okx key 1000 today):

```
status=complete      persisted 1000.0  emptied_accounts=1
status=rate_limited  persisted 1500.0  emptied_accounts=0
status=syncing       persisted 1500.0  emptied_accounts=0
```

The legacy series therefore flaps between $0 and the stale balance, depending on transient key state. This is the CR-04 defect class (a persisted wrong money figure in the store that match.py, compare and the GDPR export read), with a narrower trigger. The guard tests (`test_account_without_proof_of_emptiness_is_carried`) cover `complete_with_warnings`, `error`, MT5 and a running poll, but no transient status.

**Fix.** Make the proof a property of the poll that ran, not of the key now:
- Read the outcome recorded with that job. Either stamp `final_status` and the row count into `compute_jobs.metadata` in `_update_ok`'s success path, or read the `allocator.holdings.sync_completed` audit event's `row_count` for the same key after the claim. Admit the proof when that poll's own status was `complete` and it wrote 0 rows.
- Drop the current-status gate. Keep the ccxt-venue gate.
- Add `rate_limited`, `syncing` and `idle` arms asserting the account stays at $0 once proven empty.

```python
# _polled_empty_since: select the done job's own outcome, not api_keys.sync_status
.select("id, metadata")
.eq("kind", "poll_allocator_positions").eq("status", "done")
.in_("api_key_id", ccxt_member_ids)
.gte("claimed_at", f"{next_day}T00:00:00+00:00")
# ...and require metadata->>'final_status' == 'complete' and metadata->>'row_count' == '0'
```

### R2-CR-02: The refresh counts one account twice when its two keys were never stamped as a pair, the pre-C1 credential rotation (plan 10 lineage)

**File:** `analytics-service/services/equity_reconstruction.py:1923-1971` (a group of one per unmarked key, each carried at its own-named rows), `analytics-service/services/allocator_equity_derive.py:245-286` (`account_groups` leaves unmarked keys ungrouped by design)

**Issue.** Take the realistic rotation that SFH-01 describes, where the old key stopped working before C1's stamper existed:
- Key A is the old credential, now `error` or `sign_in_failed`. It was never stamped, so its id is NULL. The stamper runs only after a successful poll, so A will never be stamped.
- Key B, the new credential, polled successfully. The stamper found no live holder with that id, because A's id is NULL, so B was stamped plainly and left unmarked.

`account_groups` makes A and B two groups. A is eligible, so the refresh carries A at its last own-named rows, without limit, beside B's rows for today. Measured with the refresh fixture (okx, one account worth 1000, A's rows 5 days old, B's rows today):

```
UNMARKED ROTATION persisted: 2000.0
```

On `origin/main` the today-only read merged the account's rows and gave 1000, so plan 10's per-key carry turned a correct day into a doubled one. The doubling is also permanent: every day's row is doubled, first-writer-wins, until A is disconnected. The only signal is the `max_carry_age_days` WARNING, which does not say "counted twice".

- **Derive:** it also composes both keys, because the NULL id hides the pair from `account_identity_collisions`.
- **Page:** it is held under `key_not_syncing` (probe), so the doubled curve does not render.

That makes this a data-integrity defect in the legacy store, the same class and store as round-1 CR-03. It was not introduced by the fix round: CR-03's group read covers MARKED pairs only.

The same doubling happens, for as long as the state lasts, when two working keys on one account are both unstamped: the stamp came back `no_id` / `skipped_no_budget`, or the day before the first post-C1 poll.

**Fix.** The minimum honest fix mirrors the reader. A book with an eligible, identity-unknown ccxt key is not counted by carry:
- Hold the day's write the way the plan 12 hold does, audited as `refresh_held_for_identity`, whenever an eligible ccxt key with a NULL `venue_account_id` and no marker would be carried (its latest `asof` < today) while another counted account sits on the same venue.
- At the least, count such carries (`identity_unknown_carried_keys`) in the audit and log, so the doubling is not silent.
- Add a test: A `error` / NULL id / rows 5 days old + B stamped / rows today ⇒ no doubled row.

### R2-CR-03: A pre-v2 derived row now reads "did not pass its checks" and fires a Sentry warning on every dashboard load. On deploy day that is every book, and it is false

**File:** `src/lib/queries.ts:3964-3968` (the `missingSeriesReason` ternary maps every rejection to `derivation_rejected`), `src/lib/queries.ts:4324-4346` (`captureToSentry` at level `warning` for `not_version_2`), `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:60-61`

**Issue.**
- **Every existing row is pre-v2.** `version: 2` is new in this PR. `origin/main`'s `allocator_equity_compose.py` writes no `version` key (`git show origin/main:…` has 0 hits; the C2 writer sets it at `allocator_equity_compose.py:420`). So from deploy until each book's next compose, every allocator whose book has a derived row sees "The latest rebuild of your history did not pass its checks, so it is not shown."
- **Every dashboard load then sends a Sentry `warning` tagged `derived_row_rejected` / `not_version_2`.** The load is proportional to active allocators on deploy day.
- **The sentence is false for this row.** The row passed every check the writer ran. What changed is the reader's contract.
- **Fixer B's premise does not hold.** The recorded decision says ledger books "never re-derive", but that describes the dormant strategy-mode ledger refresh. Allocator keys are re-derived daily by `enqueue_derive_broker_dailies_for_allocator_keys`, scheduled `30 5 * * *` as `derive-allocator-key-dailies` (`supabase/migrations/20260717233529…sql:269-285`; later migrations call it jobid 9, "never unschedule it"). That fan-out selects every eligible key whatever its venue, and each key-mode derive enqueues the compose (`job_worker.py:5650-5673`).
- **So a pre-v2 row is exactly the case the daily recompute answers.** For it, the round-1 line ("recomputed … once a day") was TRUE, and fixer B replaced it with a false one. This is a user-facing regression introduced by the fix round.
- **The copy also breaks DESIGN.md Voice.** It states a limitation with no unlock condition. The rule is "the reader learns exactly what unlocks it."

**Fix (minimal, honest).**

```ts
// derivePhase07Fields
const rejection = derivedRow !== null ? derivedPayloadRejection(derivedRow.payload) : null;
const missingSeriesReason: MissingSeriesReason = derivedReadFailed
  ? "history_read_failed"
  : rejection === null || rejection === "not_version_2"
    ? "awaiting_derivation"          // no row, or a pre-v2 row the daily compose rewrites
    : "derivation_rejected";          // untrustworthy / malformed
```

At the read site, do not `captureToSentry` a `not_version_2` row. Log it as a breadcrumb only, or capture it only when `computed_at` is older than about 36 h, which means the daily compose did not rewrite it. Keep `warning` for `untrustworthy` and `error` for `malformed`. Update `queries.test.ts:1461,1494,1538`, `queries.my-allocation.test.ts:3153-3179` and `AllocationDashboardV2.rebuilding.test.tsx:368`, which currently pin the false mapping.

Residual to name, not fix here: a book in which every key's `derive_broker_dailies` fails before the compose enqueue never gets rewritten. With the fix above, that book reads `awaiting_derivation` indefinitely. The stale-`computed_at` capture is what surfaces it.
