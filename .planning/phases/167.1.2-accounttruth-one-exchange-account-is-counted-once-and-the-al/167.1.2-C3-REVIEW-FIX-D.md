## Fixed Issues

### SFH-R3-07: the derive's returns read is unpaginated

**Files modified:** `analytics-service/services/job_worker.py`, `analytics-service/tests/test_derive_allocator_equity_job.py`
**Commit:** `c50137dc6`
**Status:** fixed. The ordering and the disposition below are judgment calls, stated so they can be checked.

**The defect, as read at `fb0a6d983`.** `_load_returns` in `run_derive_allocator_equity_job` read
`csv_daily_returns` with `.select("api_key_id,date,daily_return").eq("allocator_id", …).execute()`.
It had no ORDER BY and no pagination. PostgREST returns at most 1000 rows per response
(`supabase/config.toml` `max_rows = 1000`), so for the 2804-row allocator the job read an
arbitrary 1000 rows and raised no error. After C2 round 2, three things consume that read:
- `first_return_day` picks the kept key of a shared account.
- `stitch_sources` picks which older members get stitched in.
- `returns_by_key` feeds the compose.

A partial read therefore gave the wrong kept key, the wrong stitch, and a shortened series, and
the curve could still be marked trustworthy.

**Applied fix.**
1. `_load_returns` now reads through `services.db.paginated_select`, which calls `.range()` page
   by page. The order is `(("api_key_id", False), ("date", False), ("id", False))`:
   - `(api_key_id, date)` is unique for every row this job uses (`csv_daily_returns_api_key_date_key`,
     `supabase/schema/baseline.sql`).
   - `id` is the primary key (`csv_daily_returns_pkey`). It makes the order total even if a
     `NULL`-`api_key_id` row carries this `allocator_id`. The CHECKs do not rule that out:
     `csv_daily_returns_per_key_allocator` only forces an `allocator_id` when there IS an
     `api_key_id`.
   - `truncation_hint` is `csv_daily_returns allocator_id=<id>`. Per the `PaginatedSelectTruncated`
     docstring it is a log-only triage string.
2. **How a `PaginatedSelectTruncated` is handled.** It is caught at the read site and ends as
   `DispatchResult(FAILED, error_kind="permanent")`, after `_delete_equity_curve_row()`.
   - Why not let it propagate: `classify_exception` has no arm for it. It would fall into the
     final `("unknown", str(exc))` catch-all and retry forever against the same rows. That is the
     T-74-02 poison-retry class that `_permanent_corrupt_input` exists to prevent.
   - Why delete the curve row: every other permanent path in this job does (F2). A stale row left
     in place would keep rendering as trustworthy. With the row gone, the book shows the
     rebuilding panel.
   - Why not reuse `_permanent_corrupt_input`: it is defined later in the function, its message
     says "corrupt persisted input" (wrong here), and it redacts numbers (which would hide the row
     cap).
   - What gets logged where: `logger.error` records the allocator id, `page_count`, `page_size` and
     the hint. At ERROR it also reaches Sentry as an event. The job's `error_message` names only
     the row cap: no allocator id, no hint, no USD.
3. `PaginatedSelectTruncated` and `paginated_select` were added to the module's existing
   `from services.db import …` line, now wrapped one name per line.

**Tests added** (in `tests/test_derive_allocator_equity_job.py`):
- **Fake support.** The fake PostgREST gains three things:
  - a chainable `order()` that actually sorts, recorded in `fake.orders`;
  - an inclusive `range()`;
  - an opt-in `max_rows` response cap on `_FakeSupabase`. It defaults to `None`, so the 56 older
    tests in the file are unchanged.
- **`test_sfh_r3_07_returns_read_drains_past_the_response_cap`.** Seeds one working key with 1500
  consecutive days, stored newest-first, under `max_rows=1000`. It asserts:
  - the curve starts on the first stored day (2022-01-01) and ends on the last;
  - the curve holds at least 1500 distinct days;
  - the `csv_daily_returns` read was ordered by exactly `api_key_id, date, id`.
- **`test_sfh_r3_07_returns_read_truncation_is_permanent_and_deletes_curve`.** Patches
  `services.job_worker.paginated_select` to raise. It asserts:
  - the job ends FAILED with `error_kind == "permanent"`;
  - the message does not contain the allocator id;
  - exactly one `(allocator_id, equity_curve)` delete happened;
  - no curve was upserted.
