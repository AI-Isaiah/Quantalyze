## What was checked, and against what

### 1. Who can read the new `cron_runs` rows

- The table (baseline `CREATE TABLE ... "public"."cron_runs"`) has `ENABLE ROW LEVEL
  SECURITY` without FORCE. It carries exactly two policies, and no later migration touches
  them. `cron_heartbeat` created both, and the only later mention is a comment in
  `20260924120000_ledger_fanout_failure_count.sql`.
  - `cron_runs_admin_read` is FOR SELECT, USING an EXISTS over `profiles` where
    `p.id = auth.uid() AND p.is_admin = true`.
  - `cron_runs_service_role` is FOR ALL, with USING and WITH CHECK
    `auth.role() = 'service_role'`. It is symmetric.
- Neither policy has a `TO` clause, so both apply to `anon` too. For anon, `auth.uid()` is
  NULL, so the admin read is false. The JWT role is not `service_role`, so the second policy
  is false as well.
  - The table-level grants to `anon` and `authenticated` (SELECT, INSERT, UPDATE, DELETE)
    are pre-existing and wide. Row security closes them: a non-admin reads zero rows, and
    no tenant can forge or alter a row.
- `profiles.is_admin` cannot be set by its own user. The column is outside the per-column
  UPDATE grant allowlist, and the `profiles_lock_privileged_cols` trigger backstops that.
- The two SECDEF readers of `cron_runs` are pre-existing and not granted to
  anon or authenticated:
  - `latest_cron_success` has REVOKE FROM PUBLIC and a grant to service_role only.
  - `prod_prober_cadence_check` has REVOKE FROM PUBLIC.

  The two ledger fan-out readers filter on `cron_name = 'ledger_refresh_fanout'`. No view
  selects from `cron_runs`.
- **Leak scope: none.** Only platform admins and service_role can read the rows. That
  includes the owner id, the api_key id, the SQLSTATE and SQLERRM.

### 2. The claim "audit_log would expose SQLSTATE and the message to the allocator": verified

- On `audit_log`, `audit_log_owner_read` is FOR SELECT, USING `user_id = auth.uid()`, with
  no `TO` clause. `authenticated` holds a table-level SELECT grant.
- A per-book row written the natural way, with `user_id` set to the book's owner, would
  therefore be readable by that allocator. So would its `metadata.sqlstate` and
  `metadata.message`. The reasoning in `167.1.2-12-REVIEW-FIX.md` is correct.
- `audit_log.entity_id` is `uuid NOT NULL`, which confirms the second reason. The
  `bootstrap_loop_failed` row has no entity to name.
- One precision note, which does not change the choice. The exposure depends on writing
  `user_id` = owner. A NULL `user_id` would avoid it, but the row would then be readable by
  no one except service_role, because the hot `audit_log` has no admin-read policy (only
  `audit_log_cold` does). `cron_runs` is still the better sink. It is admin-readable, it is
  the ledger fan-outs' existing precedent, and the prober counts rows of this shape.

### 3. The write itself runs under the definer, not the caller

- The function is SECURITY DEFINER and owned by `postgres`, per the baseline's
  `ALTER FUNCTION ... OWNER TO "postgres"`. `cron_runs` is also owned by `postgres` and has
  no FORCE.
- The INSERT is therefore exempt from row security by ownership alone. Neither policy
  admits the definer role, and neither needs to. This matches the mechanism the two ledger
  fan-outs document in their own bodies.
- The caller does not matter here: pg_cron and `service_role` hit the same path. The gate
  calls the function as the session superuser, which is equivalent because SECDEF fixes the
  executing role.

### 4. search_path, grants and REVOKEs

- `SET search_path = public, pg_catalog` is unchanged, matching the project convention.
- The self-verify reads `pg_proc.proconfig` for the exact value. It does not match on the
  body text.
- Both new INSERTs schema-qualify `public.cron_runs`, and the CREATE is schema-qualified.
- Grants:
  - Migration: `REVOKE ALL ... FROM PUBLIC, anon, authenticated` and `GRANT ALL ... TO
    service_role`.
  - Asserted twice: by the migration's `has_function_privilege` self-verify, and by the
    gate's arm G.
  - The rollback restores the baseline's own pair, REVOKE FROM PUBLIC and GRANT to
    service_role. The baseline carries no anon or authenticated grant for this function,
    so the rollback re-exposes nothing.
- No new SECDEF was added. The gate's fixture functions `public._fanout_boot_refuse` are
  SECURITY INVOKER trigger functions. They are created, used and dropped inside the gate's
  single `BEGIN ... ROLLBACK`.

### 5. Tenant scope of the rest of the round-2 diff

- The body's reads are unchanged in shape from round 1: `api_keys`, `strategies`,
  `strategy_keys`, `compute_jobs` and `allocator_equity_snapshots`. Every one of them
  correlates on the owner, through `user_id` or `allocator_id`, or on the key being
  processed. No book's decision reads another tenant's rows.
- The Python hold's new audit action `allocator.equity.refresh_held_for_reconstruct` is
  written against the book's own allocator:
  - The allocator can read it through `audit_log_owner_read`.
  - Its metadata holds a reason, the venue and two counts. It carries no USD figure, no
    key id and no error text.
- The hold's probe, `_inflight_reconstructs_for_zero_snapshot_book`, runs as service_role
  (BYPASSRLS). It is explicitly scoped by `.eq("allocator_id", ...)` and
  `.eq("user_id", ...)`, which is the ADR-0022 explicit-scope shape.

## INFO notes (no action asked)

- **RLS-R3-01 (INFO). The FORCE coupling is not written in this body.** Both new INSERTs
  depend on `cron_runs` having no FORCE ROW LEVEL SECURITY. If a future hardener adds FORCE:
  - the per-book INSERT, which is deliberately not wrapped, would raise;
  - that would escalate a one-book skip into the sub-block;
  - the sub-block rolls back every bootstrap enqueue of the run;
  - and then its own wrapped INSERT fails too, leaving only WARNINGs.

  That would be a daily whole-run bootstrap loss with no durable row. The daily refresh
  would survive, which is what X4 pins. The ledger fan-outs carry an explicit comment
  warning about exactly this clause. This body does not. X2t would go RED on a lane that
  replays such a FORCE migration, so the gate catches it, and a comment would only help the
  hardener see it before the gate does.
- **RLS-R3-02 (INFO). What admins can see.** The per-book row puts `owner_id`, `api_key_id`
  and `SQLERRM` in front of platform admins. SQLERRM excludes `PG_EXCEPTION_DETAIL`, so
  constraint-violation row values are not copied. The one path that could put arbitrary text
  into the message is a RAISE from a trigger on `compute_jobs`, and the audience is admins
  only. RLS-R2-02's re-audit condition is still not triggered.
- **RLS-R3-03 (INFO). The pre-existing grants are wide.** `anon` and `authenticated` hold
  INSERT, UPDATE and DELETE on `cron_runs` at table level, and row security is the only
  thing refusing them. This predates this plan, and ADR-0001 accepts RLS as the primary
  gate. It is recorded here because this round made `cron_runs` carry per-tenant ids for
  the first time under this cron_name.

Verdict: 3 findings (0 critical, 0 high)
