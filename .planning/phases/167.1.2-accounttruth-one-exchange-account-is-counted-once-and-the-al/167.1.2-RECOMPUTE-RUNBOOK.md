# Phase 167.1.2: the PROD recompute runbook (plan 08, success criterion 6)

**Written:** 2026-10-02, plan 08 Task 1. Adapted from RESEARCH `## Recompute Plan (SC-6), for after the merge`.
**Runs after:** PR C (topic PRs C1 to C4) is merged and deployed, SHA-bound.

## Rules for every step

- Nothing is enqueued by hand. Nobody writes a row by hand: no UPDATE, no DO block, no ad-hoc RPC.
  The stamp, the derive and the compose run on their normal schedule. The one allowed speed-up is
  the existing `request_allocator_holdings_sync` RPC, called on the founder's own keys, and only with
  the founder's approval (T-167.1.2-39).
- The census is read-only. Run the marker query first. Any answer other than `database_marker` in
  `scripts/prod-prober/cron-manifest.json` stops the step (I2). TEST carries a marker too, so a
  non-NULL answer is not enough.
- Output is counts only. The repo is public, so a tracked file may carry a census figure only as an
  aggregate count. No key id, user id, label, email or USD value goes into one (T-167.1.2-38).
- Row-level security must not shrink a count. `allocator_equity_derived` is
  `FORCE ROW LEVEL SECURITY`, and `api_keys` and `csv_daily_returns` have RLS enabled. A role that
  RLS applies to sees fewer rows and gets no error. The census would then print plausible, wrong
  counts.
- Two read paths, one SQL source:
  - **Live mode** (needs `PROBER_POOLER_URL` and `PGPASSWORD`): `node scripts/accounttruth-census.mjs`.
    It sets `default_transaction_read_only=on` and `row_security=off`, and reads both back. It runs
    the `rls` probe, and refuses before any census query unless the role bypasses RLS.
  - **Print mode** (touches no database): `node scripts/accounttruth-census.mjs --print-sql=<label>`.
    This prints one statement, a lone SELECT, for the operator to run through the read path they hold
    (`supabase db query --linked`). **Submit one label per call, in this order:** `marker`, which must
    equal the manifest's PROD marker; `rls`, which must answer `bypasses_rls`; then `a` to `f`.
    Batched together, the marker would gate nothing.
    This path has no read-only transaction behind it. Its barrier is the static guard in
    `src/__tests__/accounttruth-census.test.ts`, so run only statements printed at a commit where
    that test is green.

## Census sections

| | What it counts | The bucket a gate reads |
|---|---|---|
| (a) | live keys by exchange; live keys with `venue_account_id` NULL; the subset the stamper has not resolved (no share marker, or a marker whose holder has departed or holds no index slot) | `<venue>.live_keys_unstamped_unmarked` |
| (b) | keys marked `duplicate` / `composite_member`; duplicates whose holder is working | `duplicate.blocking` |
| (c) | owners with eligible keys; those lacking `csv_daily_returns` or a `key_inputs` row | `owners_missing_either` |
| (d) | `equity_curve` rows by payload version and `is_trustworthy`; `degrade_reasons` tokens | `version=2,is_trustworthy=true` (a GROUP BY bucket: at 0 it prints as `0 (absent: a GROUP BY bucket with no rows)`, never as a missing line) |
| (e) | owners whose `equityHistoryState` would be ready, else the reason | `ready` |
| (f) | departed keys by their D-09 default outcome; departed keys with no `key_inputs` row | `departed_key_inputs_row_gone` |

⚠️ (b) also prints the raw `duplicate.marked` count. That count does not reach 0 after a cleanup,
because the marker is never cleared when a key departs (D-18). The cleanup gate reads
`duplicate.blocking`, which follows the reader's `countsAsDuplicate` rule.

⚠️ The census prints PROD-wide counts. It never prints an owner, and it never narrows to one by id.
A gate about the founder's book is settled by a PROD-wide 0. Above 0, the founder's own key cards say
whether any of those owners is him.

## Steps

### 1. Census (before anything moves)

- **Gate:** founder go (plan 08 Task 2, answered "run"). PR C is merged and deployed, SHA-bound.
- **Do:** run the census: live mode, or `marker`, `rls`, then `a` to `f`, one label per call.
- **Done reads as:** the marker equals the PROD marker, `rls` answers `bypasses_rls`, then six sections
  of counts. Record the counts in the plan 08
  SUMMARY. A refused marker or an unreadable section stops here. It never means "0".

### 2. Stamp (identity backfill)

- **Gate:** step 1 recorded. The founder decides whether to wait or speed up.
- **Do:** nothing. The identity stamper runs inside the next scheduled holdings poll. If the founder
  approves a speed-up, call the existing `request_allocator_holdings_sync` once per founder key.
  Never call it on anyone else's key.
- **Done reads as:** a successful poll has run for every live key. The `already_inflight` answer is a
  wait, not an error.

### 3. Re-census (a) and (b)

- **Gate:** step 2 done.
- **Do:** run `marker`, `rls`, `a`, `b`, one label per call (or live mode).
- **Done reads as:** in (a), the per-exchange `<venue>.live_keys_unstamped_unmarked` buckets for
  binance, okx, bybit and deribit read 0. (b) shows any duplicates the stamper marked.
  ⛔ CORRECTED 2026-10-03 (debug `unstamped-venue-account-id`): this line used to read the
  `<venue>.live_keys_venue_account_id_null` buckets, and those cannot fall while a duplicate is
  live. A key the stamper marks keeps `venue_account_id` NULL by design, because the unique index
  refuses its id. Measured on PROD: 14 NULL, 12 of them marked duplicates (deribit 7, okx 5), and
  `<venue>.live_keys_unstamped_unmarked` was 0 for every ccxt venue. The NULL buckets fall only at
  step 4, once a duplicate is disconnected and its sibling's next poll stamps it.
  ⛔ CORRECTED 2026-10-03 (167.1.2-08 review WR-01 / SFH M-2): a marker counts as resolved only
  while its holder, in the same owner's keys, still has `disconnected_at` NULL, which is the
  unique index's own condition. A marker is never cleared when its holder departs (D-18). A key
  marked against a departed holder is no longer refused by the index, but it stays NULL until its
  own next successful poll, so the bucket now counts it as unresolved. Before this correction the
  bucket counted only keys with no marker at all, and could read 0 with such keys left behind. A
  revoked holder that is still connected keeps its slot, so its marked sibling still counts as
  resolved. The 2026-10-03 PROD reading above was taken under the old rule. Re-read it at step 3
  with the corrected statement.
  ⛔ CORRECTED 2026-10-03 (167.1.2-08 review round 2, IN-R2-03): the holder must also HOLD the
  slot, which means it is on the same exchange as the marked key and carries a `venue_account_id`.
  The index is `(user_id, exchange, venue_account_id)`, partial on a non-NULL id and a NULL
  `disconnected_at`, so a connected holder with no id, or one on another exchange, blocks nothing,
  and a key marked against it counts as unresolved. No current writer produces such a marker, so
  this tightens an edge and is not expected to move the PROD reading.
  ⛔ CORRECTED 2026-10-03: sFOX stays NULL by design (D-10). **MT5 is NOT covered by D-10.** An MT5
  key gets its login stamped at connect or rotate (the Next routes), but nothing backfills an MT5
  key connected before the column existed (2026-08-12). On PROD that leaves 2 MT5 keys unstamped
  and outside the duplicate check. See the debug session for the open decision.
  ⭐ RESOLVED 2026-10-03 (founder Option B, code on branch, NOT yet deployed): the poll stamper now
  stamps an MT5 key from the login text its session already carries, through the same index
  refusal -> 'duplicate' marker -> one audit path as ccxt. After deploy and one poll cycle,
  `mt5.live_keys_unstamped_unmarked` is expected to read 0, and one of the two pre-column MT5 keys is
  expected to carry a 'duplicate' marker (they measured as one broker account). Until that is
  measured on PROD, treat MT5 as open.

### 4. Founder cleanup

- **Gate:** (b) `duplicate.blocking_owners` > 0, and the founder's key cards show the duplicate note.
- **Do:** the founder disconnects the flagged duplicates with the key card's existing Disconnect
  control. The key keeps its history (D-05). Nothing is deleted.
- **Done reads as:** no key card shows the duplicate note.

### 5. Re-census (b)

- **Gate:** step 4 done.
- **Do:** run `marker`, `rls`, `b`, one label per call.
- **Done reads as:** PROD-wide `duplicate.blocking_owners` is 0. If it is above 0, none of the
  founder's key cards shows the duplicate note. Record the count in the SUMMARY.

### 6. Derive

- **Gate:** step 5 is done.
- **Do:** nothing. The daily `enqueue_derive_broker_dailies_for_allocator_keys` writes the per-key
  dailies. Its per-key epilogue enqueues `derive_allocator_equity`, which writes the version-2
  `equity_curve` payload.
- **Done reads as:** one daily run has passed since step 5.

### 7. Re-census (c) to (f)

- **Gate:** step 6 done (plan 08 Task 3, item 1).
- **Do:** run `marker`, `rls`, `c`, `d`, `e`, `f`, one label per call.
- **Done reads as:** (c) `owners_missing_either` is explained or 0. (d) the rows are version 2. (e)
  `ready` covers the founder's book, or the reason it prints is named on his Overview. (f)
  `departed_key_inputs_row_gone` is recorded. Those keys show "History not available" on their cards.

### 8. Browser verification

- **Gate:** step 7 recorded.
- **Do:** the orchestrator checks the founder's book in the logged-in browser (plan 08 Task 3, items
  2 to 5).
- **Done reads as:** My Allocation shows either the rebuilding panel with a named reason, or a curve
  whose KPIs agree in sign with its cumulative return. The Scenario shows no flat +0.00% line. No
  raw key id appears.

## Known limits of the census

- (e) mirrors `equityHistoryReadiness` and `extractTrustworthyDerivedSeries` (`src/lib/queries.ts`).
  `history_read_failed` happens on the page and has no SQL twin.
- (f) mirrors `departedHistoryInclusion` (`src/lib/departed-history.ts`) and its Python twin. The
  shared fixture `departed_history_inclusion.json` was replayed on a throwaway local cluster at
  plan 08 Task 1, and every expected decision matched. That fixture's unreadable-`disconnected_at`
  case was not replayed, because a `timestamptz` column cannot hold that value.
  ⛔ CORRECTED 2026-10-03 (167.1.2-08 review SFH M-3): the replay harness is now committed.
  `src/__tests__/accounttruth-census.test.ts` section (6) boots a throwaway local cluster (the
  binaries `scripts/pg-lane/run.sh --print-pgbin` names, socket-only, never TEST or PROD), replays
  every case of that fixture except the unreadable-`disconnected_at` one, which it excludes by name,
  and runs the whole census through the real runner. So a rule change that moves the TS and the
  Python but not the SQL now fails in CI. The same section executes (a) and (b) on seeded rows.
- The population of (c) and (e) is every owner with an eligible key, whatever their role. That
  matches `enqueue_derive_broker_dailies_for_allocator_keys`.
