## Warnings

### WR-01: The SF2-M2 escalation fires on every marked key, whose `venue_account_id` stays NULL by design, and says "duplicate check not running" when the check ran and found the duplicate

**File:** `analytics-service/services/account_identity.py` (`_unstamped_for_too_long`, and the two call sites in `stamp_account_identity`). Test gap: `analytics-service/tests/test_account_identity_stamper.py` (`test_no_escalation_where_no_duplicate_check_is_missing`).

**Issue:** `_unstamped_for_too_long` treats "ccxt venue, `venue_account_id` NULL, `created_at` more than 3 days old" as "should have been stamped by now and is not". That misses the design in `_mark_shared`'s docstring:
- A key that shares an account with a live holder, whether a `duplicate` or a `composite_member`, is marked, and **its `venue_account_id` stays NULL** until the holder leaves (D-01, the self-heal).
- The daily poll re-runs `stamp_account_identity` on it (`job_worker.py`, the `stamp_account_identity` call at the end of `run_poll_allocator_positions_job`).

So every marked key older than 3 days is in the escalation population permanently. Any transient failure on it, or any `skipped_no_budget`, is logged at ERROR, which reaches Sentry, with "key unstamped for >3 days; duplicate check not running". Examples of transient failures: a ccxt `NetworkError`, a rate limit, a gateway 504, the `wait_for` timeout.

For these keys that sentence is false: the duplicate check did run, and the marker is its result. The population includes legitimate composite members sharing one account, which is steady state rather than a fault.

I measured it on this tree. A 30-day-old `okx` row with `account_shared_with_api_key_id` set and `account_share_kind='duplicate'`, passed to `stamp_account_identity(..., timeout_s=0.0)`, logged:

```
ERROR account_identity: api_key k (venue okx) outcome=skipped_no_budget budget_s=0.0 — key unstamped for >3 days; duplicate check not running
```

That is the alert fatigue WR-01/SF-M3 were fixing, re-introduced by SF2-M2. The fixer's recorded limit mentions only a stamped key whose id is later cleared, "not a live path today". The marked-key path is live on every daily poll. The no-escalation `parametrize` covers sFOX, MT5, already-stamped and bad `created_at`, and has no marked-key case, so the suite cannot see this.

**Fix:** A marked key is not "missing its duplicate check". Exclude it in the predicate and pin it:

```python
def _unstamped_for_too_long(key_row: Mapping[str, Any]) -> bool:
    if key_row.get("exchange") not in VENUES_WITH_ACCOUNT_ID:
        return False
    if key_row.get("venue_account_id") is not None:
        return False
    # A marked key stays unstamped BY DESIGN while its holder is live (D-01,
    # the self-heal): its duplicate check ran and the marker is the result.
    if key_row.get("account_shared_with_api_key_id") is not None:
        return False
    ...
```

Add two cases to `test_no_escalation_where_no_duplicate_check_is_missing`:
- `pytest.param({"account_shared_with_api_key_id": HOLDER_ID, "account_share_kind": "duplicate"}, id="marked-duplicate")`
- the `composite_member` twin of that case.

**What this does not cover, stated as a limit:** a marked key whose holder later departs and whose self-heal stamp then fails every day would no longer escalate. If that residual matters, escalate a marked key only when a cheap read shows its holder is not live. Do not escalate every marked key.

### WR-02: The one remaining `held` signal ignores the W-4 archived rule, so a key held only by an archived composite answers KEY_VENUE_ALREADY_CONNECTED while My Strategies lists it under "No strategy yet"

**File:** `src/app/api/strategies/create-with-key/route.ts:300-322` (`resolveOtherKeyUse`). Compare `src/lib/queries.ts`, `deriveStrategyLinkedKeyIds` and `deriveStrategylessKeys`.

**Issue:** After CR-01, composite membership is the only `held` signal. The read answers `held` on any `strategy_keys` row of the owner's for the key, whatever the linked strategy's status. The repo's other reader of the same question, `getStrategylessActiveKeys`, works differently:
- It applies W-4, "archived ≠ coverage". A `strategy_keys` link whose strategy is archived is dropped, so the key reappears as a "No strategy yet" row with "Finish setup".
- Its docblock says the helper exists so that no caller can "quietly grow a third link form or a different archived rule".
- Archiving does not delete `strategy_keys` rows. The composite member RPC refuses to touch a non-draft composite's members, per the comment in migration 20260712120000.

The result: a manager whose only use of a key is an archived composite re-enters that account in the wizard and gets KEY_VENUE_ALREADY_CONNECTED.
- Its remedies are "use the key you already have", "create a key on a different account" and "email security@".
- It never names "Finish setup", the route My Strategies is showing them for that same key.
- KEY_ORPHANED is the code whose copy is true here: no live strategy is built on the key.

This is the same class as CR-01, where a "held" answer suppresses the orphan remedy, in a narrower population. Round 1 introduced the read and round 2 kept it, so it is in scope.

**Fix:** Apply the archived rule in the route's read, so the two readers agree:

```ts
const { data: member, error: memberErr } = await supabase
  .from("strategy_keys")
  .select("api_key_id, strategies!inner(status)")
  .eq("owner_id", userId)
  .eq("api_key_id", liveKeyId)
  .neq("strategies.status", "archived")
  .limit(1)
  .maybeSingle();
```

The alternative is a second read of the linked `strategy_id`'s status. Either way:
- Add a route test: an `archived`-composite member answers KEY_ORPHANED, and a live-composite member still answers KEY_VENUE_ALREADY_CONNECTED.
- Keep the read-set pin's table list honest if an embed changes what it captures.

Note: the `connected` arm (`resolveStrategiesForKey`'s owner read, which has no status filter) has the same divergence for an archived direct strategy. That arm predates this PR, so it is recorded here and not assigned to this PR.

## Info

### IN-01: Over-long ids now land on `no_id`, which never escalates, so SF2-M1 and SF2-M2 together leave that key unchecked at WARNING forever

**File:** `analytics-service/services/account_identity.py` (`_normalise`, and the `no_id` arm of `stamp_account_identity`)

**Issue:** On the stamper path, an id over 128 units becomes `None`, which gives `no_id`. That is a daily WARNING, plus `_normalise`'s own WARNING. SF2-M2's escalation covers retryable failures and `skipped_no_budget` only, so this key's duplicate check never runs and nothing ever reaches ERROR. That is the silent-forever shape SF2-M2 was opened for. No venue is known to send an id this long today.

**Fix:** Optionally route `no_id` through `_unstamped_for_too_long` as well. Venue schema drift that persists for 3 days is exactly the condition that should reach Sentry.

### IN-02: The escalation age is `created_at`, so on the first poll after deploy every pre-existing ccxt key's first transient failure is an ERROR

**File:** `analytics-service/services/account_identity.py` (`_unstamped_for_too_long`)

**Issue:** Keys connected before plan 02/04 are older than 3 days and unstamped at deploy. On the first backfill poll, one network blip or budget miss on any of them logs "key unstamped for >3 days" at ERROR, though no stamp has yet been attempted. This is a one-off burst, not a steady state. The fix report records a different age limit (a cleared id) but not this one.

**Fix:** None required. Record it next to the existing limit so the deploy-day Sentry burst is expected rather than triaged.

### IN-03: `account_identity` imports the private `services.db._is_gateway_timeout`

**File:** `analytics-service/services/account_identity.py` (import line)

**Issue:** This is a cross-module dependency on an underscore name. Its docstring says "iff APIError", but it matches `code in ("504", 504)` on any exception. That is harmless here, since ccxt and httpx exceptions carry no `.code`, but it is a contract the helper does not state.

**Fix:** Optionally make it public, for example `is_gateway_timeout` with the old name kept as an alias, or add an `isinstance(exc, APIError)` guard at the call site in `_is_retryable`.
