### WR-01 / SFH-C3R2-01: the paginated returns read is not a snapshot, so a concurrent key derive can make it skip or duplicate a row

**Files modified:** `analytics-service/services/job_worker.py`, `analytics-service/tests/test_derive_allocator_equity_job.py`
**Commits:** `391b86866`, `e7f6cfbe2`
**Status:** fixed. This is a concurrency fix. The tests below drive the exact race through a fake writer, but the approach choice is a judgment call, so it is stated here for a reader to check.

**The defect, as read at `0f2c6d116`.** `_load_returns` in `run_derive_allocator_equity_job` used `paginated_select` over `csv_daily_returns` filtered by `allocator_id`, ordered `(api_key_id, date, id)`, and paged by OFFSET (`.range(start, end)`). Each page is a separate PostgREST request with its own snapshot. At the same time, the key-mode `derive_broker_dailies` for a sibling key deletes its key's span (`_reconcile_span_delete`) and then upserts it back in chunks. If that write changes the row count of a key that sorts before the next page's offset, every later row shifts by one:
- a day is appended, so a row is read twice;
- a refused day is removed, so a row is never read.

**Approach chosen: keyset pagination on `(api_key_id, date)`, run as one key per loop.** For each key id, the read issues `eq("allocator_id", A).eq("api_key_id", k).gt("date", cursor).order("date").limit(1000)`. The cursor is the last date read, and the loop stops on the first empty page. This IS keyset pagination on the total order: the outer column is fixed by the `eq`, and the inner column is the cursor. It is a new module-level function, `_load_allocator_daily_returns`, which `_load_returns` calls.

What this guarantees, and why:
- **No `(api_key_id, date)` pair is read twice.** Within a key the cursor strictly increases, and the keys are read one after another.
- **Every row present for the whole read is read.** No page's start depends on how many rows sort before it, so a write to another key, or to earlier days of the same key, cannot move a page.

Why not the alternatives:
- **Why not the reviewer's `or=(api_key_id.gt.K,and(api_key_id.eq.K,date.gt.D))` form?** It gives the same guarantee. But it needs a PostgREST `or` filter string built from row values, plus a `not.is.null` on every page. The per-key form needs neither: the `eq` already excludes NULL keys.
- **Why not per-key reads plus an exact-count check and bounded retry?** The count is one more separate statement. It can agree with a torn read, or disagree with a clean one. It adds retry machinery and a new transient path, and it closes nothing that keyset leaves open.
- **Why not a single-statement SECDEF RPC?** It needs a migration, and PROD migrations auto-apply on merge. It is also outside this topic's file scope.

Choices made inside the fix:
- **`id` is deliberately NOT in the cursor.** `(api_key_id, date)` is unique (`csv_daily_returns_api_key_date_key`, `supabase/schema/baseline.sql`), so a tie on it can only be the same day deleted and re-inserted with a new `id`, which is the writer's own shape. An `id > I` arm would re-read that day, which is exactly the duplicate this fix removes. The brief's wording "(api_key_id, date, id)" was the total order for OFFSET pages, and it does not carry over to a cursor.
- **Only the keys the derive already read from `api_keys` are read.** Semantics are unchanged, as checked in the code:
  - `first_return_day` is consulted only through `.get(row["id"])` for rows of `key_rows`;
  - `_grouped` admits only `counted_ids ∪ stitch_source_ids`, and both are subsets of `key_rows` ids;
  - NULL-`api_key_id` rows were skipped by both consumers, so they are no longer read at all.
- **The read stops on an EMPTY page, not a short one.** PostgREST clamps `limit` to `max_rows`. A short-page stop would silently end each key after its first page if that cap ever sat below 1000. The empty-page stop costs one extra request per key. `e7f6cfbe2` pins this.
- **Topic D's disposal is kept byte for byte.** Past `_DAILY_RETURNS_HARD_CAP_PAGES` (1000) non-empty pages, the read raises `PaginatedSelectTruncated`, with the same hint string as before. The unchanged `except PaginatedSelectTruncated` arm then deletes the curve row and ends the job permanent. Only one comment in that arm changed, because it named `paginated_select`. A count landing exactly on the cap is read whole, which matches `paginated_select`'s boundary-peek semantics.
- **Housekeeping.** `paginated_select` was dropped from the `services.db` import because nothing in the module uses it any more. `Iterable` was added to the `collections.abc` import.

**Cost.** The number of requests goes from about ⌈rows/1000⌉ to about Σ over keys of (⌈key rows/1000⌉ + 1). Each allocator has a handful of keys.

## Residuals this fix does not close (not fixed, stated so they are not read as closed)

1. **The writer's own delete-then-upsert window. This is pre-existing, and the read side cannot close it.** `_reconcile_span_delete` (job_worker `run_derive_broker_dailies_job`, key mode) deletes a key's whole span, then upserts it in 1000-row chunks as separate statements with no transaction. A read that lands inside that window, even a single-statement snapshot read, sees the key's rows absent or partly re-inserted. The pre-topic-D single SELECT had the same exposure. What changed here: the read can no longer be torn by a write that lands BETWEEN two of its pages. The window is milliseconds to seconds wide.
   - **The follow-up is a writer change, not made here.** Upsert first (`ON CONFLICT (api_key_id, date) DO UPDATE` keeps the row), then delete only the span dates absent from the new payload. With that ordering, no present day is ever absent.
   - **Why it was not made here:** it changes a different job's write path, which has its own tests (`test_derive_broker_dailies_*`), and it is outside the brief.
   - **Routing** is for the orchestrator. It is data-integrity, so under the deferral policy it needs a phase if booked.
2. **The absorbed follow-up compose.** This is pre-existing, as the reviewer described. A sibling key that finishes writing while this compose is `running` has its epilogue enqueue absorbed by `compose_jobs_one_inflight_per_kind_allocator`. So its newest day can be missing from today's curve until the next compose. Keyset does not change that. It is staleness, not a torn read.
3. **Correction to the review's premise (measured, not a fix).** WR-01 says a duplicated row is "accepted silently" by `pd.Series(..., index=[dates])`, and that the compose gets the day twice. Under Neuter 1 the duplicate did not compose. `portfolio_returns` (`allocator_equity_derive.py:480`, `float(series_by_key[k].get(day, 0.0))`) raised `TypeError`, because `.get` on a duplicated index returns a Series. That exception is not in the derive's `(ValueError, TypeError, KeyError)` parse guard, which covers only the Series construction. It escapes the compose's own catch, so it would reach `classify_exception` as an unclassified exception and retry. That is a loud failure, not a wrong curve. After this fix no duplicate can be produced by the read. The observation is recorded so the review's severity reasoning is not reused as fact.

## Known limits

- The fake orders and compares `date` as an ISO string, and applies `gt` by string comparison. PostgREST compares the `date` type. For `YYYY-MM-DD` values the two orders agree.
- PROD's effective `max_rows` was not measured. The read no longer depends on it being at least the page size.
- The race tests drive the write BETWEEN reads, so they prove the page-shift half. They do not, and cannot, prove the write-window half (Residual 1).
