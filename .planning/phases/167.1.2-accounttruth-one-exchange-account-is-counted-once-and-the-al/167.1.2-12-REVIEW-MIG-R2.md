## Exception-block and advisory-lock semantics (the fix round's main change)

Traced every exit of `enqueue_refresh_allocator_equity_for_all` against the session-level
`pg_try_advisory_lock(hashtext('daily_equity_refresh'))` taken BEFORE any sub-block:

| Path | What happens | Lock |
|---|---|---|
| lock not acquired | `RETURN` before any block | not held |
| per-call 40001 / 23505, either loop | the inner per-call subtransaction rolls back one enqueue, WARNING, loop continues | held; released by the trailing unlock |
| any other error in the bootstrap loop (for example P0001, 42501, 55P03 from `lock_timeout`) | bootstrap sub-block `WHEN OTHERS` rolls back every bootstrap enqueue, WARNING, falls through to the refresh loop | held; released by the trailing unlock |
| any other error in the refresh loop | outer `WHEN OTHERS` unlocks, re-raises | released |
| normal completion | trailing unlock | released |
| `query_canceled` / `assert_failure` (not matched by `WHEN OTHERS`) | propagates past both handlers without the unlock | leaks for the SESSION only; inherited verbatim from 075's wrapper, and a pg_cron run ends its session, which frees it. Not a finding |

A subtransaction rollback never releases a session-level advisory lock, and the lock is not
taken inside any sub-block, so no handler can drop it early. The bootstrap rollback is also
safe for the refresh loop by construction: a book whose reconstructs were rolled back has no
in-flight-or-done row, so its `bk*` subquery keeps its refresh withheld (arm X2 pins this: the
refused zero-snapshot key gets 0 refreshes while a snapshot book still gets 1).

The helper's real lost-race signal is confirmed: `_enqueue_compute_job_internal`
(`supabase/schema/functions/_enqueue_compute_job_internal.sql`) inserts `ON CONFLICT DO NOTHING`
and raises `USING ERRCODE = 'serialization_failure'` when the re-select finds no in-flight row.
Catching 40001 per call is safe here because it is a synthetic RAISE, not an SSI abort, and
pg_cron runs at READ COMMITTED.

## Fixture trigger containment

- All three `_fanout_boot_refuse` function + `compute_jobs` trigger pairs are created and
  DROPPED inside their own DO block (X1, X2, X3), before that arm's assertion, inside the
  file's single `BEGIN;` (after the setup header) ... `ROLLBACK;` (last line). A RAISE aborts
  the transaction, and psql with `ON_ERROR_STOP=1` exits, so the uncommitted catalogue rows
  never become visible to another session on any path.
- Each trigger's `WHEN` clause matches only that arm's own random `k_refused` id, so even
  within the transaction it cannot touch a foreign key's enqueue.
- The name is re-used three times; each block drops it before the next creates it, so no
  `42710` duplicate on a clean run.
- Side effect, not a finding: `CREATE TRIGGER` / `DROP TRIGGER` take `ShareRowExclusive` /
  `AccessExclusive` on `compute_jobs` and hold them until the file's `ROLLBACK`. On the private
  lanes that run this corpus (`sql-tests` local stack, the mutation runner's throwaway cluster)
  that blocks no one. `supabase/tests/test_api_keys_account_identity.sql` already puts a
  fixture trigger on `compute_jobs` the same way, so this is the corpus's precedent, not a new
  shape. Anyone following the file's `Usage:` line against shared TEST would stall the worker's
  `compute_jobs` traffic for the tail of the file (X1 through G, a few calls).

## Findings

### MIG-R2-01 (MEDIUM): the bootstrap sub-block turns a bootstrap failure from a failed cron run into a log-only WARNING

**Evidence.** The new sub-block's `EXCEPTION WHEN OTHERS THEN RAISE WARNING ...` swallows every
non-40001/23505 error in the bootstrap loop. Before the fix round, such an error failed the whole
call, so `cron.job_run_details` recorded the run as failed. Now the call returns normally and the
run records `succeeded`; the only trace is a WARNING in the Postgres log. A PERSISTENT cause (for
example a later re-base of `enqueue_compute_job` that changes its signature or refuses the
`reconstruct_allocator_history` kind) would disable the bootstrap every day with a green cron,
and books would sit at zero snapshots, which is exactly the defect this migration exists to fix,
returning silently. The trade (keep the refresh alive for every allocator) is the right call
for SFH-02; the observability half is what `167.1.2-12-REVIEW-SFH.md` SFH-03 asks for and the
fix report records as not fixed. This finding sharpens SFH-03: the fix round made the D-17
failure mode silent BY CONSTRUCTION, where before it was loud.

**Fix.** Not required for this merge (MEDIUM, no fix round on its own per policy). Route with
SFH-03: either have the sub-block's handler record a durable signal (a row a prober reads) or add
a prober arm that counts zero-snapshot books with a qualifying key and no reconstruct row older
than one cron cycle. At minimum, state in the header's edit (4) that a bootstrap failure is
visible only in the Postgres log.

### MIG-R2-02 (INFO): a key skipped by the per-call handler still spends a cap slot

**Evidence.** In the bootstrap loop `v_bootstrap_enqueued := v_bootstrap_enqueued + 1` runs
after the per-call `BEGIN ... EXCEPTION ... END`, so a key whose enqueue was skipped by a caught
40001 still counts toward `v_bootstrap_cap`. The cap only becomes more conservative (fewer books
per run), the skipped key has no reconstruct row so its book stays un-bootstrapped and is
re-taken the next day, and a 40001 needs a concurrent winner that already went terminal. No
correctness effect.

**Fix.** None. Recorded so it reads as reviewed.
