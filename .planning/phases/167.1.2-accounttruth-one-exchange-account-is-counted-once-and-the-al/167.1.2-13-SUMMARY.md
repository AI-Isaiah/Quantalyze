# Phase 167.1.2 Plan 13: empty sole-key reconstruct never wipes existing history Summary

**An empty sole-key reconstruct no longer calls `replace_allocator_equity_snapshots` when the book already has legacy rows, or when that existence lookup errors. The job stays DONE and says so on the existing `reconstruct_no_data` audit.**

## Accomplishments

- `replace_equity_snapshots` refuses an empty payload before the RPC when `allocator_equity_snapshots` has rows for the allocator, or when the head count itself errors (fail-safe: keep the rows).
- `run_reconstruct_allocator_history_job` catches `EmptyReplaceRefusedError` ahead of the generic handler, leaves the outcome DONE, and adds `purge_refused`, `existing_history` and `snapshot_lookup_failed` to `allocator.equity.reconstruct_no_data` only then.
- A book with no snapshots still sends `p_rows: []` once. The non-empty E4 path is unchanged.

## What a refused purge means next

The outcome is DONE, so the worker records this key's `reconstruct_allocator_history` row as `done`. `_api_key_already_reconstructed` then reads true for this key until `retention_compute_jobs_done` deletes `done` rows at 30 days (ADR-0024). Plan 12's bootstrap does not fire for this book: `enqueue_refresh_allocator_equity_for_all` bootstraps only a zero-snapshot book, and `_inflight_reconstructs_for_zero_snapshot_book` returns 0 once any snapshot row exists. The rows were kept, so the book is not empty.
