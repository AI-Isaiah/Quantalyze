Measured: `tests/test_account_identity_stamper.py` 79 passed (run from `analytics-service/`, no

Summary: no CRITICAL. The MT5 branch reuses the ccxt UPDATE -> 23505 -> holder -> `_mark_shared`
-> audit path unchanged, and every exception inside `_stamp` reaches the `stamp_account_identity`
boundary, which logs it (WARNING / ERROR, with the escalation). A collision cannot go unmarked
without a log line. The census gates (exact PROD marker, read-only read-back, `row_security=off`,
RLS role probe, id-shaped bucket refusal) are sound. The gaps are where the stamp step never runs
at all, or ends in an outcome the escalation ignores, plus one census bucket that undercounts the
unresolved keys.

## HIGH

### H-1 — An MT5 key whose poll does not reach DONE is never stamped, and nothing logs that (confidence 7)

`analytics-service/services/job_worker.py:9558` (the only `stamp_account_identity` call site) runs
after persist on the DONE path. The rate-limited, transient, permanent and persist-failure branches
of `run_poll_allocator_positions_job` all `return DispatchResult(...)` first, and a decrypt or
`_make_mt5_session` failure raises out of `_allocator_key_preflight` (`job_worker.py:~1365`) before
a session exists.

- **Hidden failure:** the SF2-M2 escalation ("key unstamped for >3 days; duplicate check not
  running", `account_identity.py` `_unstamped_for_too_long`) lives INSIDE `stamp_account_identity`.
  A key that never reaches DONE never reaches the escalation either, so a pre-column MT5 key whose
  poll keeps failing (gateway -10005 wedge, `sign_in_failed`, persistent 429, a decrypt error)
  stays unstamped. No `account_identity:` line is ever written for it. The poll failure itself is
  logged, but nothing says the duplicate check is not running.
- **Why it matters for MT5 in particular:** the MT5 stamp needs NO terminal call (it reads the
  login text from the decrypted credentials), yet it is gated on the terminal answering. The MT5
  gateway is the least reliable venue this service talks to. The last-good holdings of a key in
  `rate_limited` / transient state still count in the book, so a duplicate MT5 pair where one key's
  polls keep failing keeps summing twice with no ERROR.
  `queries.ts` `ACCOUNT_IDENTITY_EXCHANGES` excludes MT5 too, so the page shows no
  `account_identity_pending` either.
- **What catches it today:** only a human running census (a) `mt5.live_keys_unstamped_unmarked`.
  That is the runbook gate, not an alarm.
- **Recommendation:** for MT5, stamp from the decrypted login independently of the fetch result,
  for example in a `finally`-adjacent step once the session exists. Or run the escalation check (no
  stamp) on the non-DONE return paths, so a stamped-venue key unstamped for more than
  `UNSTAMPED_ESCALATION_DAYS` logs the same ERROR whatever the poll's outcome. Pin it with a test
  that drives an MT5 poll down the transient or permanent branch and asserts the escalation record
  (or the stamp).

## MEDIUM

### M-1 — `no_id` never escalates, and for MT5 it is a wiring defect logged as "schema drift?" (confidence 8)

`account_identity.py` `stamp_account_identity`, the `elif outcome == "no_id"` arm, and
`_mt5_account_id`. `mt5_client.py:2768` declares `venue_account_id: str | None = field(default=None, ...)`.

- **Hidden failure:** the escalation is applied only to retryable errors and `skipped_no_budget`.
  `no_id` is always WARNING, every day, forever, and never reaches Sentry. For MT5, `no_id` means
  the session carried no `venue_account_id`. `parse_mt5_credentials` already refuses a blank login,
  so the only way to get there is an `Mt5Session` built without the field. The `default=None` makes
  that silent: a future second construction site, or a refactor of `_make_mt5_session`, compiles,
  passes mypy, and leaves every MT5 key unstamped with a misleading
  "the venue answered without an account id (schema drift?)" WARNING.
- **Recommendation:** (a) apply `_unstamped_for_too_long` to `no_id` as well (it is the same
  "duplicate check not running" state). (b) For MT5, log `no_id` at ERROR with its own text
  ("the poll session carries no login; this is a construction defect"), or make the field required
  (no default) so a constructor that omits it fails at build time. (c) Add the missing test: an MT5
  session with `venue_account_id=None` yields `no_id` and, past 3 days, an escalation record.
  No current test covers `_mt5_account_id` returning `None`.

### M-2 — `live_keys_unstamped_unmarked` hides marked keys whose holder has left (confidence 7)

`scripts/accounttruth-census.mjs:137` and `:144` (`... AND k.holder_id IS NULL`).

- **Hidden undercount:** a key marked `duplicate` against a holder that has since departed is NOT
  counted as a duplicate (`duplicate.blocking` requires `h.working`, as `countsAsDuplicate` does).
  It is also NOT counted as unstamped, because its marker is non-NULL. Its `venue_account_id` stays
  NULL until a poll stamps it (`_mark_shared` docstring: the self-heal), and per H-1 that poll may
  never reach DONE. Such a key is unresolved, counts in the book, and is invisible to the bucket
  the runbook's stamp gate reads. The gate can read 0 while keys are still unresolved.
- **Recommendation:** count `eligible AND NOT venue_known AND (holder_id IS NULL OR the holder is
  not eligible)`, or add a separate `live_keys_marked_holder_departed` bucket per exchange and name
  it in the runbook gate. Update the static test in section (5) of the census test to pin it.

### M-3 — Census SQL semantics are never executed by any test (confidence 8)

`src/__tests__/accounttruth-census.test.ts` (whole file). Every assertion runs against string
shape (the read-only guard, regex over `UNION ALL` arms) or canned `fixtureSqlRunner` answers. No
test runs (a)–(f) against a Postgres with seeded rows. The header comment on
`DEPARTED_DECISION_CTES` says a local harness can compare it with
`tests/fixtures/departed_history_inclusion.json`, but no such harness exists in the repo (grep:
the symbol appears only in the script).

- **Consequence:** a wrong predicate (a NULL-propagating `CASE`, a join that drops a row, an `e`
  readiness branch that diverges from `equityHistoryReadiness`) prints plausible counts with exit 0.
  The tests cannot fail on a semantic regression, only on a textual one. This is the class the
  census exists to rule out, and its numbers feed recompute gates on PROD.
- **Recommendation:** add a pg-lane (`scripts/pg-lane/run.sh`) or local-stack test that seeds a
  handful of `api_keys` / `csv_daily_returns` / `allocator_equity_derived` rows covering NULL
  `sync_status`, a marked key with a departed holder, an sFOX key, and an MT5 key, and asserts the
  exact bucket counts. At minimum, run `DEPARTED_DECISION_CTES` against the shared D-09 fixture as
  the comment claims.

### M-4 — An empty section, or a missing bucket, prints and exits 0 (confidence 6)

`scripts/accounttruth-census.mjs:689` (`if (parsed.rows.length === 0) out("  (no rows)")`).

- Sections (a), (b), (c) and (e) are built from un-grouped aggregates and a fixed `VALUES` list, so
  they ALWAYS return rows by construction. Zero rows from them means the read did not run the
  statement the script thinks it ran (a pooler or proxy answering oddly, a runner bug, a hand-edited
  fixture). The script prints `(no rows)` and exits 0. Nothing checks that the buckets the runbook
  gates on (`<venue>.live_keys_unstamped_unmarked`, `duplicate.blocking`, `ready`) are present, so
  an operator who reads an absent line can read it as 0.
- **Recommendation:** per section, declare the required bucket set (the fixed ones) and exit 1 with
  "(x) answered without bucket <name>" when one is missing. Treat `(no rows)` as a measure failure
  for (a), (b), (c) and (e). The `greenFixture` in the test already omits most required buckets,
  which shows how easily a partial answer passes.

## LOW

### L-1 — The read-only and row-security read-back is a sample, not a per-statement guarantee (confidence 5)

`accounttruth-census.mjs:652-664` and `realSqlRunner` (one psql process per statement). The
`READ_ONLY_PROBE_SQL` read-back proves only that ITS session got the PGOPTIONS. Each census
statement is a new psql session through the pooler. If the pooler applied startup options
inconsistently across backends, a later session could run with `row_security` on, and the RLS
role probe is what then prevents silent filtering. Acceptable because the role probe is
role-scoped (constant across sessions) and the statements are SELECTs. A one-line improvement:
prefix each section's run with the same read-back in the same `-c` invocation (two statements in
one session), or note the assumption.

### L-2 — Per-exchange buckets silently drop an exchange outside the fixed `VALUES` list (confidence 5)

`accounttruth-census.mjs:126`. A venue the `api_keys_exchange_check` admits later is counted in
`all.*` but in no per-exchange line, and the runbook gate reads per-exchange lines. Add an
`other.live_keys*` arm (`exchange NOT IN (...)`) so the totals reconcile on the printout.

### L-3 — Python `strip()` and JS `trim()` disagree on a few code points (confidence 4)

`mt5_validation.py` `mt5_venue_account_id` claims byte-equality with the connect route's
`api_key.trim()`. Python strips `\x1c`–`\x1f` and JS does not; JS strips U+FEFF and Python does
not. `int()` accepts a login padded with `\x1c`, so `parse_mt5_credentials` lets such a slot
through, and the poll would stamp a value connect never stored. It is unreachable through the
wizard in practice, but the docstring overstates the guarantee. Either restrict the strip to the
ASCII set `btrim`/`WS` uses in the census, or soften the claim.

### L-4 — Partial PROD key ids in a tracked planning file (confidence 6, disclosure rather than silent failure)

`.planning/debug/unstamped-venue-account-id.md` (`next_action`, `human_verify`) names two PROD
`api_keys` id prefixes. The repo is public, and the census itself refuses to print ids
(T-167.1.2-38). Consider replacing them with role names ("the older / newer pre-column MT5 key").

## Questions asked of the new code

- **Can the pre-fetch MT5 stamp mask or alter the poll?** No. `stamp_account_identity` catches
  `Exception` at its boundary and returns a token. A `CancelledError` (the worker's `wait_for`)
  propagates with `identity_attempted` already True, so the `finally` does not add a false
  "not attempted" line, and `aclose_exchange` still runs. Its budget at that point is the full
  `_IDENTITY_STAMP_TIMEOUT_S` (20 s of the 180 s envelope), so it cannot come back
  `skipped_no_budget`.
- **Can `escalate_if_unchecked` in the `finally` mask the original exception, or be skipped?** It
  is synchronous, so a cancel cannot interrupt it halfway. Its body is wrapped in
  `except Exception -> logger.exception`, so it cannot replace an in-flight exception. It is
  skipped only when the preflight returned a `DispatchResult` before the `try` (see R2-L1) or
  raised (covered by the build-failure arm). Nothing between the preflight and the `try` can
  realistically raise.
- **Does `escalate_session_build_failure` swallow or rewrite the error?** No. It logs only the
  class (the test proves the exception text stays out of the log) and is called inside the
  `except` before a bare `raise`. It catches `Exception` only, so a `BaseException` passes
  straight through.
- **Does any census section still print and exit 0 on an empty or partial answer?** No, for
  every bucket in `required`. The one exception is (d)'s gate. That is deliberate, and see R2-L2.

## LOW

### R2-L1 — A key behind a repeatedly DEFERRED poll never reaches either escalation (confidence 4)

`job_worker.py:1379-1381` (preflight `_check_circuit_breaker`) and `job_worker.py:9235-9238`
(the handler returns the `DispatchResult` before the `try`). A circuit-breaker DEFERRED returns
before `identity_attempted` exists, so neither `escalate_if_unchecked` nor the build-failure arm
runs. The breaker cools down, and a DEFERRED job is retried rather than dropped, so this matters
only if a venue's breaker keeps tripping across every daily window. If it does, an unstamped key
on that venue is silent until a human reads census (a). Fix if cheap: call
`account_identity.escalate_if_unchecked(key_row, cause="poll_deferred")` on the poll handler's
DEFERRED return. It is age-gated, so it adds no noise on a fresh key.

### R2-L2 — (d)'s gate line is omitted rather than printed as 0, while the script tells the operator "an absent line is not a 0" (confidence 5)

`accounttruth-census.mjs:613` (`gateMayBeAbsent: true`) and `:814` (the print loop prints only
the rows it got). When `version=2,is_trustworthy=true` is 0, the printout has no line for it. The
runbook's section table names that bucket as (d)'s gate. In the same run, the M-4 error text
teaches the operator that an absent line is not a 0, so the two rules contradict each other on
one printout. Recommendation: for each `gate` bucket marked `gateMayBeAbsent` and absent from the
rows, print `  <bucket>: 0 (absent: a GROUP BY bucket with no rows)`, so every gate the runbook
reads appears explicitly.

### R2-L3 — The D-09 replay passes on nothing if the fixture loses its cases (confidence 4)

`src/__tests__/accounttruth-census.test.ts:938`. The only size assertion is
`cases.length - replayed.length === D09_NOT_REPLAYABLE.size`. If the shared fixture were cut down
to the one excluded case, or its cases' `expected` maps emptied, `replayed` would be `[]`, the
decision query would return no rows, and `expect(got).toEqual({})` would pass. Add a floor tied to
the fixture (for example `expect(replayed.length).toBeGreaterThanOrEqual(<measured count>)`) and
`expect(Object.keys(got).length).toBe(replayed.length)`.

### R2-L4 — The poll-level escalation text overstates for a marked key whose holder is live (confidence 5)

`account_identity.py:594` (`_duplicate_check_missing`), used by `escalate_if_unchecked` (`:634`)
and `escalate_session_build_failure` (`:664`). Python treats "venue_account_id is NULL" as "the
duplicate check is missing". A key marked `duplicate` against a live, connected holder also has
NULL by design (12 of the 14 NULL keys on PROD, per the debug session), and the census now counts
it as **resolved** (M-2's rule). If such a key's poll fails for more than 3 days, or its session
cannot be built (no age gate on that one), it logs ERROR "duplicate check not running". The check
did run, and its marker stands. This is not a silent failure. It is a misleading alarm that
erodes trust in the real ones, and the census and the escalation now hold two definitions of
"unresolved". Recommendation: in `_duplicate_check_missing`, also return False when
`account_shared_with_api_key_id` is non-NULL (the holder's liveness is not on `key_row`, so a
marked key is the conservative "resolved" choice), or keep it and change the text to "not
re-checked this poll" for a marked key. Either way, write down which definition is intended.

## INFO (not defects)

- **Docstring cadence claim.** `_allocator_key_preflight` says the build-failure ERROR is "one line
  per key per day". The fanout is daily (`'0 4 * * *'`), but the arm fires on every attempt,
  including any dispatcher retry of the FAILED job. Not silent. If retries apply, it is a little
  noisier than the docstring claims.
- **The login-only MT5 identity has a cross-server collision.** The pre-column backfill (TODOS A-3
  addendum) stamps from the login alone. Two different broker accounts with the same login on
  different servers, under one owner, therefore collide, and the newer one is marked `duplicate`
  and held out of the book. It is surfaced (a key-card note plus an `account_duplicate_detected`
  audit event), the founder chose it (Option B), and TODOS records it. It is not silent. It is a
  wrong-number risk, and it is booked.
