# Phase 167.1.2 Plan 04: stamp existing keys, mark duplicates, name them on the card Summary

**The daily allocator poll now stamps each live OKX, Bybit, Binance or Deribit key's venue account id
with one venue call on the session it already holds. A key whose account a live sibling of the same
owner already holds is marked, never disconnected or deleted. The mark is `'duplicate'`, or
`'composite_member'` for a rotation inside one composite (D-04). A new duplicate is audited once, and
both key cards name the holder beside the controls that already exist. A reconnect into an occupied
account is refused in words.**

## What was built

- **`services/account_identity.py`**
  - `read_venue_account_id` makes the one call the validator already makes:
    - okx: `private_get_account_config`
    - bybit: `private_get_v5_user_query_api`
    - binance: `fetch_balance()` info
    - deribit: `fetch_balance({"extended": True})` info
  - `stamp_account_identity` works as follows:
    - It skips a non-ccxt venue and an already-stamped key.
    - It writes `venue_account_id` with the marker cleared, `WHERE id = key AND venue_account_id IS NULL`.
    - On a 23505 whose message names `api_keys_user_exchange_venue_account_uniq`, it looks up the live
      same-owner holder and marks the key.
    - It never raises, and is bounded by `asyncio.wait_for`. `CancelledError` is not caught.
    - It logs key id, venue, a token and on failure the exception class and SQLSTATE. It never logs the
      id value.
  - Tokens: `skipped_not_ccxt`, `skipped_already_stamped`, `skipped_no_budget`, `stamped`,
    `marked_duplicate`, `marked_composite_member`, `no_id`, `error`.
- **`COMPOSITE_MEMBER_SHARED_ACCOUNT`** reads both keys' `strategy_keys` rows in one query. If one
  strategy holds both keys with windows that do not overlap by `stitch_composite.windows_overlap`
  (imported, not re-implemented), the kind is `composite_member`. Any other shape is `duplicate`.
- **`run_poll_allocator_positions_job`** calls the stamp after persist, the success audit and
  `stamp_first_sync_success`, just before the DONE return. Its token is not read.
- **`API_KEY_USER_COLUMNS`** gains the three columns. `ApiKey`, `ApiKeyRowSchema` (`.strict()`) and
  the runtime-guard fixture were updated with it.
- **`accountShareNote`** (src/lib/account-share-note.ts) is the one non-test source of the sentence.
  It is imported by both cards. The allocator card renders it in amber on the active row beside
  Disconnect. The manager card renders it beside Delete. The holder is looked up in the whole key
  list.
- **Reconnect:** `rpcErr.code === "23505"` shows "This exchange account is already connected through
  another of your keys. Disconnect that key first, then reconnect this one." It goes through the
  existing M2 revert and `helper_override`, so it shows on the disconnected row's helper line, and no
  sync request follows. Any other code keeps "Reconnect failed — try again".

## Open question from the plan: which job re-runs the stamper, per venue?

The daily cron `poll-allocator-positions` runs at 04:00 UTC, scheduled by migration
`20260420073003`. It calls `enqueue_poll_allocator_positions_for_all_keys()`, which selects EVERY
exchange's keys with `is_active = true AND sync_status IS DISTINCT FROM 'revoked' AND disconnected_at
IS NULL`. It is role-agnostic and venue-agnostic. "Sync now", Add Key and Reconnect also enqueue a
poll for one key. The stamper acts only for okx, bybit, binance and deribit, so:

- **Every live key on those four venues is re-evaluated at least daily.** A marked key whose holder
  is disconnected self-heals on its next poll.
- **A key that is revoked or `is_active = false` is never polled again**, so its marker (and its NULL
  identity) is never re-evaluated. For those keys "until the stamper re-evaluates them" in the column
  COMMENTs means never. The reader rule is the only thing that keeps their account counted correctly.
  - **Revoked holder:** its marked sibling stays marked, and is re-polled daily but keeps hitting the
    index, because revoked is still live for it. The reader rule counts the sibling on its own. This
    is pinned by `test_a_revoked_holder_does_not_self_heal_its_duplicate`.
- sFOX and MT5 are polled daily and skipped by the stamper by design (D-10, and MT5 identity is the
  login stamped at connect).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The exchange session is closed before the plan's stamp site**
- **Found during:** Task 1
- **Issue:** `run_poll_allocator_positions_job` closed `ctx.exchange` in the `finally` right after the
  fetch. Persist and DONE ran after the close, so a stamp there would call the venue on a closed ccxt
  session. Async ccxt re-opens a session lazily, and that session then leaks.
- **Fix:** The success tail (persist through the DONE return) moved inside the outer `try`, so the
  existing `finally` closes the session after the stamp. The move is whitespace-only
  (`git diff -w` shows only the `finally` block moving).
- **Verification:** `test_poll_stamps_a_null_identity_key_while_its_session_is_open` asserts the venue
  call saw an open session and the session was then closed. The poll suites passed (448 passed,
  2 skipped).
- **Committed in:** `1c8879491`

**2. [Rule 2 - Correctness] The stamp is bounded by the handler's remaining budget**
- **Found during:** Task 1
- **Issue:** The worker wraps the handler in `wait_for(TIMEOUT_PER_KIND[...])`. An unbounded venue
  call after persist could time out a poll that had already persisted and written `complete`, which
  changes the DispatchResult (Pitfall 4).
- **Fix:** The stamp budget is `min(20 s, ceiling − elapsed − 10 s)`. A budget at or below zero skips
  the step with a new token, `skipped_no_budget`.
- **Verification:** `test_a_hanging_venue_is_cut_off_by_the_budget`,
  `test_no_budget_left_skips_the_step_without_a_venue_call` and
  `test_a_poll_near_its_timeout_skips_the_stamp` all pass.
- **Committed in:** `1c8879491`

**3. [Rule 3 - Blocking] `ApiKey`, `ApiKeyRowSchema` and the runtime-guard fixture move with the projection**
- **Found during:** Task 1
- **Issue:** `ApiKeyUserView = Pick<ApiKey, ApiKeyUserColumn>` requires every projected column on
  `ApiKey`. `ApiKeyRowSchema` is `.strict()`, so a row carrying the new columns would be dropped.
  This is the same sync that migrations 066, 068, 075 and 20260920120000 each did.
- **Fix:** Three typed fields were added to `ApiKey` and the schema, plus
  `ApiKeyAccountShareKind = "duplicate" | "composite_member"`. The fixture carries the fields.
- **Files modified:** src/lib/types.ts, src/__tests__/api-key-runtime-guard.test.ts
- **Committed in:** `1c8879491`

**4. [Rule 3 - Blocking] "The card's existing label builder" did not exist on either card**
- **Found during:** Task 3
- **Issue:** The plan's label (`exchange — nickname or masked tail`) is `dataSourceLabel`, a private
  function in ScenarioComposer.tsx. Importing it from that 7000-line client component into a lib and
  two cards is the wrong dependency direction.
- **Fix:** `dataSourceLabel` and its `EXCHANGE_LABELS` moved byte for byte into
  `src/lib/api-key-label.ts`, and ScenarioComposer imports it. The only other change is an added
  comment on the move. `EXCHANGE_LABELS` was not widened, so a deribit holder reads "deribit — …" as
  the Scenario rows do.
  - Plan 07's instruction "import it; never re-implement `dataSourceLabel`" now has a real module to
    import from.
- **Files modified:** src/lib/api-key-label.ts (new), src/app/(dashboard)/allocations/components/ScenarioComposer.tsx
- **Verification:** 54 test files under `allocations/components` passed (1093 tests).
- **Committed in:** `b0bc05d3c`

**5. [Scope] sec-005 tests: no "expected lists" existed**
