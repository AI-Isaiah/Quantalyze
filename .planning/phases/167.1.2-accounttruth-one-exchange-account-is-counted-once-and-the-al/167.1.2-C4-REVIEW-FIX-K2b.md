### CR-01 (= SFH-C4-03): rotate-secret erases the owner's history choice on a key that stays disconnected

**Files modified:** `src/app/api/keys/[id]/rotate-secret/route.ts`, `src/app/api/keys/[id]/rotate-secret/route.test.ts`
**Commit:** `1d9f9c6b2`
**Status:** fixed: requires human verification (a logic condition, so the tiers below prove the
branch and not the rule)

**Applied fix:**
- The ownership pre-read now selects `disconnected_at, is_active`. Neither is written.
- The reset is decided by `returnsKeyToLive = isLiveKey({ is_active, sync_status: "idle",
  disconnected_at })`. It imports `isLiveKey` from `src/lib/departed-history.ts`, which has no imports
  of its own and is the predicate the key card and the derive job read. That avoids a fifth copy of
  the predicate (SFH-C4-10). The route's write sets `sync_status = 'idle'` and never touches
  `disconnected_at` or `is_active`, so this is the key's liveness after the write. The pre-read
  `sync_status` drops out of the rule.
- The payload spreads `history_inclusion: null` only when `returnsKeyToLive` is true. The spread
  sits inside `attemptPersist`, so the WR-02 retry without `venue_account_id` makes the same
  decision.
- An already-live key also takes the reset. It is live after the write, and a stale non-NULL value
  would otherwise carry into its next departure, which the column COMMENT forbids.
- The test comment that said "the route does not even SELECT this column" was false after this
  change. It now says the column is selected to make the decision and is never written.

**Tests:** the test that pinned the unconditional reset was replaced by four:
1. A revoked key (`disconnected_at` NULL, active) is reset.
2. A disconnected key keeps its choice. The payload has no `history_inclusion` key, still has
   `sync_error: null` and `sync_status: 'idle'` and the ciphertext, and still has no `disconnected_at`.
3. An inactive key keeps its choice.
4. The pre-read's columns include `disconnected_at` and `is_active`.

**Known limits (recorded in the route comment, not fixed here):**
1. **No recompose is enqueued.** A revoked key whose non-NULL choice is reset gets no recompose.
   The key is live after the write, so the next derive for this owner composes it as a live key.
   This route does not take the recompose serialisation that `set_departed_key_history_inclusion`
   takes. Queuing one would need that RPC's lock and job path, which is outside this topic's
   files. The reviewer allowed "enqueue (or document)", and this is the document.
2. **The liveness fields are read before the broker probe.** If a Disconnect lands during the
   probe, the reset follows the pre-read state. In that window a key that was just disconnected
   could still have its choice reset. The window is one probe long.

### SFH-C4-09: the manager-card Delete cascades a key's history without the warning

**Files modified:** `src/components/strategy/ApiKeyManager.tsx`, `src/components/strategy/ApiKeyManager.test.tsx`
**Commit:** `4e16b67fe`

**Applied fix:**
- New module constant `DELETE_REMOVES_HISTORY = "Deleting also removes this account's history."`.
- It is rendered in the "Delete API Key" confirm as its own line: amber `text-warning`,
  `role="status"`, `data-testid="delete-history-warning"`. It is separate from the composite
  `deleteCheck` warning, and the Delete button is never disabled by it.

**Deviations from the brief and the review:**
- **The wording is the first sentence only.** AllocatorExchangeManager's copy continues
  "Disconnect instead to keep it." This card has no Disconnect (its own comment, 167.1.2 REVIEW
  WR-01). Repeating that sentence would send the owner to a control that is not on this card. The
  test asserts the warning does not mention Disconnect.
- **The warning shows on every Delete.** The brief said to show it "only when the delete path
  hard-deletes". This path is always `.from("api_keys").delete()`, a hard delete that cascades
  `csv_daily_returns`, so the brief's condition always holds. SFH-C4-09 suggested showing it only
  when the key has per-key dailies. That would need a new read before the confirm, and I did not
  take it. A key with no dailies therefore also gets the sentence, which then has nothing to
  delete.
