## Summary

**The defect is exactly as recorded, and it lives on one line.** In `run_stitch_composite_job`, the `_stamp_failed` closure decides "protected background refresh or loud user failure" from `job.get("metadata")` [VERIFIED: analytics-service/services/job_worker.py:6225-6240, `_job_metadata = job.get("metadata") or {}` … `if ( _job_source == "ledger-refresh-composite" and existing_status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES ):`]. That dict is the row the claim RPC returned. Nothing in the composite handler reads `compute_jobs` again. The single-key derive path already closed the same window with `_refresh_marker_still_on_row` [VERIFIED: job_worker.py:2591-2622]. It calls that helper at three honour sites (`:3040`, `:5852`, `:5916`). The composite twin never got the call. This is the only composite honour site: the marker literal appears once in the handler, and nothing forwards it down a chain edge.

**The fix is a Python-only change of about ten lines, and it needs no migration.** At decision time, and only when the snapshot would otherwise grant protection, re-read the live row with the existing helper. If the marker is gone, take the loud path. This mirrors `:3040` exactly. The SQL end (`is_protected` in `sync_strategy_analytics_status`) already reads `f.metadata ->> 'source'` from the live row whenever `mark_compute_job_failed` PERFORMs the bridge [VERIFIED: supabase/schema/baseline.sql:6776 `PERFORM sync_strategy_analytics_status(v_strategy_id);`, :9043-9047]. No SQL change is needed to make the two layers agree.

⚠️ **The harm is narrower than the runbook's wording, and criterion 1 exists to measure it.** The runbook says a post-claim retraction "suppresses the user's failure". Reading the bridge says that is not the final STATUS on the common path. `_stamp_failed` runs only before `error_kind="permanent"` returns, so the job goes `failed_final`. With the marker retracted, `is_protected` is FALSE, so branch (b) writes `computation_status='failed'` anyway. The layers really do disagree, and the disagreement is observable, in two places:
- **H2, `computation_warned` residue.** The stale Python path never writes `computation_warned=False`, while the loud path does [VERIFIED: job_worker.py:6291]. The bridge's branch (b) does not touch `computation_warned`. Its branches (a) and (c) turn any row carrying `computation_warned` back into `complete_with_warnings` [VERIFIED: baseline.sql bridge body, `WHEN strategy_analytics.computation_status = 'complete_with_warnings' OR strategy_analytics.computation_warned THEN 'complete_with_warnings'`]. So a failed user resync on a warned composite reads `failed` until the next bridge call that has a job in flight, then silently reads terminal-success again.
- **H3, another job in flight at failure time.** Branch (a) runs first. It preserves the untouched `complete_with_warnings` and NULLs `computation_error`. The user's poller reads terminal-success over a failed run. The loud path would have written `failed` with warned FALSE, which branch (a) turns into `computing`.

**Primary recommendation:** Three plans in three sequential waves. Plan 01 runs a harm probe that drives the REAL handler against the local-stack lane, pre-fix. Plan 02 adds the live re-read and a unit regression observed RED under neutering, then re-runs the same probe post-fix as the criterion-2 agreement proof. Plan 03 restates the runbook precondition and updates TODOS and CHANGELOG. There is no migration, and no file overlaps with 164.9.1.

### Pattern 1: Narrow-only live re-read at the honour site (copy `:3040`)

**What:** Keep the snapshot comparison as the first filter, so an unmarked job pays nothing. Only when protection would be GRANTED, ask the row. If the row no longer carries the marker, log a warning and take the loud path.
**Constraints the shape must satisfy (all verified in tests this session):**
- **Gate 11** needs exactly ONE `_job_source == "<marker>"` comparison inside the `_stamp_failed` closure, and it compares that literal to the SQL arm's [VERIFIED: tests/test_ledger_refresh_gates.py:2404-2440, `re.findall(r'_job_source\s*==\s*"([^"]*)"', composite_guard_region())` then `assert len(python_markers) == 1`]. So do NOT write the literal a second time. Pass `_job_source` or `LEDGER_REFRESH_COMPOSITE_SOURCE` as `expected`.
- The closure region must still reference `STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES`, and its sentinel `"data_quality_flags": merged_flags` must stay beyond the 1500-char floor [VERIFIED: test_ledger_refresh_gates.py:405 `_COMPOSITE_GUARD_REGION_MIN_CHARS: Final[int] = 1500`, :478 `_COMPOSITE_GUARD_REGION_SENTINEL: Final[str] = '"data_quality_flags": merged_flags'`].
- The **M-3 source scan** fails if the whole `run_stitch_composite_job` source contains the substring `published` or `verification_status`, COMMENTS INCLUDED [VERIFIED: tests/test_stitch_composite_job.py:2914-2922, `assert "verification_status" not in src` / `assert "published" not in src`]. New comments and log strings must say "live", never that word.
- Use the handler-local `supabase` (from `get_supabase()`), not a `ctx` object. The composite handler has no `ctx.supabase` at closure scope.

**Example (recommended shape; the planner may adjust the wording):**
```python
# Source: mirrors job_worker.py:3040-3051 (derive arm, REUSE-01)
_honour_marker = (
    _job_source == "ledger-refresh-composite"
    and existing_status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES
)
if _honour_marker and not await _refresh_marker_still_on_row(
    supabase, job.get("id"), LEDGER_REFRESH_COMPOSITE_SOURCE
):
    logger.warning(
        "stitch_composite: the refresh marker on compute_job %s has been "
        "RETRACTED since the claim; a user-initiated request inherited this "
        "job, so taking the LOUD terminal path for strategy %s.",
        job.get("id"), strategy_id,
    )
    _honour_marker = False
if _honour_marker:
    ...  # the existing error-only branch, unchanged
```

### Anti-Patterns to Avoid
- **Replacing the snapshot compare with the live read.** It costs a read on every loud failure and loses the "narrow only" property. Keep both, in the order above.
- **A test that retracts BEFORE the handler runs.** That test is green against the bug, because the snapshot would already lack the marker. Every loud assertion must drive a job dict that STILL carries the marker against a live row that does not. This is the same discipline as `test_ledger_refresh_reuse_collision.py`'s header [VERIFIED: that file, lines 42-50].
- **Stopping at the Python payload.** 161.1 recorded that a guard which is green on the payload can be red at the bridge (`test_sync_status_marked_refresh_protected.sql` header). Criterion 2 requires reading `strategy_analytics` AFTER `mark_compute_job_failed`.
- **Pointing the probe at anything but loopback.** `services/db.get_supabase()` reads `SUPABASE_URL`/`SUPABASE_SERVICE_KEY` from the environment [VERIFIED: services/db.py:72-78]. `main.py`/`main_worker.py` call `load_dotenv()`, but importing `services.job_worker` does not. The probe must set both variables from `.stack-env` and assert a `127.0.0.1`/`localhost` host before it imports anything.

## Migration verdict

**Not needed.** Reasons:
1. The SQL end already decides on the live row. `is_protected` is computed inside the bridge from `f.metadata ->> 'source'` at `mark_compute_job_failed` time [VERIFIED: baseline.sql:9043-9047 quoted: `COALESCE( (f.metadata ->> 'source') IN ('ledger-refresh', 'ledger-refresh-composite') AND f.kind IN ('derive_broker_dailies', 'compute_analytics_from_csv', 'stitch_composite'), FALSE ) AND v_publish_healthy AS is_protected,`].
2. `set_compute_job_progress`, the only other writer of this job's metadata during the run, MERGES (`COALESCE(metadata,'{}') || jsonb_build_object('member_progress', …, 'member_progress_at', …)`). It cannot bring back a retracted `source` [VERIFIED: baseline.sql:8240-8262].
3. A migration here would auto-apply to PROD on merge and force a baseline regeneration that collides with 164.9.1's `baseline.sql` and `baseline-carried-migrations.txt` edits.

**Residual after the fix, to be stated rather than hidden.** A retraction that lands between the Python re-read and `mark_compute_job_failed` (milliseconds) still produces an error-only Python write followed by a loud SQL status. That is the same H2 residue, over a far smaller window. The derive arm (`:3040`) has the identical residual. Closing it would take a SQL change: branch (b) clearing `computation_warned`, or the decision moving inside the bridge's transaction. That would be a migration to a bridge every kind shares. Recommendation: record it as a known limit in the SUMMARY and the runbook. Do not open a phase for it unless the lane shows it matters.

## Common Pitfalls

### Pitfall 1: The existing suppression tests go RED after the fix, for the wrong reason
**What goes wrong:** Tests 1-3 in `tests/test_ledger_refresh_composite_nondestructive.py` drive a marked job with NO `id` against `_FakeSupabase`. That fake's select returns `data=None` for any table it does not know, `compute_jobs` included [VERIFIED: tests/test_stitch_composite_job.py:166-190, fallthrough `return SimpleNamespace(data=None)`; nondestructive `_run` builds `job = {"strategy_id": _STRATEGY_ID}`]. After the fix, `_refresh_marker_still_on_row` answers FALSE (no id, or no row), so the protected arm turns loud.
**How to avoid:** Extend `_FakeSupabase` with an optional `live_job_metadata` (default: absent, which is the current behaviour) that the `compute_jobs` select serves as `{"metadata": …}`. Give `_run` a `job_id` and a `live_metadata` defaulting to the snapshot's metadata (not retracted). Tests 1-3 then keep their meaning. Default-absent keeps every other `_FakeSupabase(` construction (104 across `tests/`, measured) byte-unchanged.
**Warning signs:** Tests 1-3 fail with a loud payload right after the one-line fix.

### Pitfall 2: Gate 11 or M-3 go RED from prose
Covered under Pattern 1. Writing the literal a second time, or using "published" in a new comment, fails the gate with no behaviour change.

### Pitfall 3: A probe that proves nothing
**What goes wrong:** Seeding `computation_warned = FALSE` makes the H2 difference vanish, because a failed row with warned FALSE goes to `computing` on either path. That reads as "no harm".
**How to avoid:** Seed the analytics row as the composite success path writes it. The success path writes `"computation_status": composite_status, "computation_warned": member_warned` [VERIFIED: job_worker.py:7882-7885]. Run the probe for BOTH `computation_warned` TRUE and FALSE, and record both. Whether live composite rows carry TRUE is UNMEASURED [ASSUMED]. The SUMMARY must say so and must not claim a production cohort.

### Pitfall 4: Starting a worker
Never run `main_worker`/`uvicorn`. The probe calls `run_stitch_composite_job(claimed_row)` directly, then calls `mark_compute_job_failed` itself, as `main_worker.py:959-970` does. The zero-member composite is the earliest permanent failure and does no exchange I/O. The nondestructive test file already uses it as its driver.

### Pitfall 5: Treating `.planning` or TEST as the lane
Python's existing `*_live.py` tests target shared TEST through `TEST_SUPABASE_DB_URL`. Do not reuse them. The probe reads only `scripts/local-stack/.stack-env`.
