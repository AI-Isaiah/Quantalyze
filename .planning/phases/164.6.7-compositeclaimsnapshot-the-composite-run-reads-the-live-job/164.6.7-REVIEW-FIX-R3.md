### SFH-R3-01 (HIGH) / WR-03: a failed composite stamp read erased the curated cause

**Files modified:** `analytics-service/services/job_worker.py`,
`analytics-service/tests/test_ledger_refresh_composite_nondestructive.py`
**Commit:** `59bafa62f`
**Applied fix:** In `run_stitch_composite_job` → `_stamp_failed`, the
`db_read_with_retry(_read_existing_failed_row)` call is wrapped. Any failure, whether a 504
past the budget or any other error on the first attempt, now:
- logs one ERROR carrying `_read_failure_text(exc)` and the scrubbed cause (with the scrubbed
  `detail` appended when present);
- makes one capture tagged with the job id;
- raises `RefreshMarkerRereadUnavailable("stitch_composite: the stamp's status read failed
  (<Class>: <msg>), so no terminal stamp was written for: <scrubbed>")`, which
  `classify_exception` files TRANSIENT.

Nothing is written. The read failure text is capped at 120 characters and placed before the
cause, so the cause cannot be pushed past `classify_exception`'s 500-character cut. A test
with a 2000-character read error pins that.

The round-2 test that pinned the erasure, `test_a_persistent_504_still_fails_and_suppresses_nothing`,
is replaced by `TestAFailedStampReadKeepsTheCause`. It covers a marked persistent 504, a marked
non-504 first failure, an unmarked user stitch with a non-504 failure, and the long read error.
Each case asserts TRANSIENT, the curated cause and the read's kind in `last_error`, the cause at
ERROR, one capture, the job tag, and no write.

`_stamp_strategy_analytics_failed` needed no equivalent arm. Its first I/O on the marked path is
the marker re-read, because `existing_status` is the entry snapshot (SFH-R3-01 checked this, and
I confirmed it in the source).

**Deliberate asymmetry with item 2.** This arm catches every exception, programming errors
included, and files them TRANSIENT. The orchestrator scoped the programming-error exclusion to
the entry arm. The difference is that here there is a curated cause to keep in `last_error`,
while the entry read has none. `unknown` and `transient` retry the same way in

### WR-02 / SFH-R3-03: the runbook's alert-volume bound was stale

**Files modified:** `docs/runbooks/ledger-refresh-go-live.md`
**Commit:** `f4964a5c5`
**Applied fix:** The bullet is kept as lineage under a dated correction and a table re-counted
from the round-3 code. An event is one `logger.error` (the default `LoggingIntegration`:
`init_sentry` in `sentry_init.py` passes `integrations=[StarletteIntegration(),
FastApiIntegration()]` without disabling the defaults) or one `capture_exception`.

| path, per attempt | ERROR | captures | events |
|---|---|---|---|
| D-15 protected (`PRESENT`) | 0 | 0 | **0** |
| marker `READ_ERROR` at either stamp | 2 | 1 | **3** |
| composite stamp status read fails | 1 | 1 | **2** |
| chain edge `READ_ERROR` | 2 | 1 | **3** |
| entry read fails | 1 | 1 | **2** |
| entry read programming error | 1 | 1 | **2** |
| marked, `RETRACTED` / `OTHER_SOURCE` → loud stamp | 1 | 0 | **1** |
| marked, `NO_ID` / `NO_ROW` → loud stamp | 2 | 0 | **2** |
| tail mirror `READ_ERROR` (on a DONE attempt) | 2 | 1 | **3** |

**Derivation.** Every read failure except the tail mirror's raises and ends the attempt. No
attempt reaches two rows, because the three reads run in a fixed order:
- the entry read runs before the crawl;
- the chain edge runs before the tail mirror;
- the composite status read runs before its marker re-read.

So an attempt produces at most 3 events. With the default `max_attempts` of 3, a job produces at
most **9**, for example two chain-edge `READ_ERROR`s and then a DONE attempt whose tail read
fails. A protected failure produces none.

Compared with round 2, the per-job bound is the same number, but it is now true. At HEAD before
this round it was 12, and each protected failure added 1. The scope sentence says the handler
arm's own failure logging and the worker loop's WARNING are outside the count.
