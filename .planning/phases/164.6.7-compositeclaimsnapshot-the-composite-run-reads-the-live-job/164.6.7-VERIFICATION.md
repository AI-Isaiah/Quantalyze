### Known limits (recorded, not fixed, from REVIEW-R5, R6 and R7)

1. **SFH-R5-06 (INFO).** A `_READ_PROGRAMMING_ERRORS` member in a stamp call is filed `unknown`
   with its own text, so `last_error` lacks the curated cause (it is on the ERROR line only). The
   split is a heuristic: a client library parsing an odd gateway body can raise `KeyError` /
   `TypeError` / `IndexError`. Only the label moves; budget and user copy are the same. A comment
   now says so.
2. **SFH-R5-07 (INFO).** The WR-01 plain-`complete` exposure across a transient retry is unchanged
   by round 4. Routed as `[164.6.7-RETRY-PLAIN-COMPLETE]` (deferred above).
3. **SFH-R5-02 / R5 IN-01 / R6-03, residual blind spots of the scan.** It cannot see a method call,
   a function defined outside `services/`, or I/O reached only through a passed callable (for
   example `upsert_or_drop_provenance`'s write). The discovery test cannot see off-thread calls.
   `NO_ID` and a `detail`-bearing stamp have no driving scenario (the scan covers them).
4. **SFH-R5-01 caveat.** The executor thread behind a cancelled stamp write keeps running, so that
   write can still land after the job is filed `transient`.
5. **R6-05 sibling.** `services/analytics_runner.py` has its own `_read_existing_flags` in
   `run_csv_strategy_analytics`, still `dict(... or {})`. Outside this phase's diff; it fails
   loud (the job raises and retries), not silent.
6. **R6-06 (INFO).** `_refresh_marker_still_on_row` now has log-only semantics for programming
   errors; a future caller that needs a raise must call `_refresh_marker_live_state` directly.
   R6-07 (the cancel arm re-raises) and R6-08 (the 500-character test is sound) are confirmations.
7. **R7 LOW.** The runbook's round-6 derivation assumes the 3-attempt retry budget without citing
   it by symbol. Sourced here: `max_attempts INTEGER NOT NULL DEFAULT 3` in
   `20260411144407_compute_jobs_queue.sql`, and `job.get("max_attempts", 3)` in the worker's
   failure path in `job_worker.py`.
