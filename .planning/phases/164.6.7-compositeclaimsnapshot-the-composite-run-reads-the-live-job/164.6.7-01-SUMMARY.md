# Phase 164.6.7 Plan 01: Composite claim-time harm probe Summary

A local-lane probe drives the real `run_stitch_composite_job` through the real enqueue, claim RPC
and `mark_compute_job_failed`. On the pre-fix tree it shows the Python stamp taking the
error-only branch while the SQL bridge reads the same live job as unprotected, for every
retracted arm. The marker-present control agrees.

## What was built

`analytics-service/scripts/probe_composite_claimtime.py` is a standalone script. It is not
collected by pytest. Each arm does the following, in order:

1. Seeds its own user, a zero-member strategy and a `strategy_analytics` row at
   `complete_with_warnings`, with the arm's `computation_warned` seed.
2. Enqueues a marked `stitch_composite` job with `enqueue_compute_job`.
3. Claims it through `claim_compute_jobs_with_priority` (five named args) on the handler's own
   service-role client.
4. Optionally retracts the marker on the live row, using the TypeScript helper's write shape,
   after the claim.
5. Awaits the handler on the unmodified snapshot and reads the branch it took from what it wrote.
6. Recomputes the bridge's `is_protected` over the live rows.
7. Marks the job failed with its claim token, then reads the end state.
8. Reads the end state again after one more bridge call.
9. Cleans up its own rows.

Safety:
- `.stack-env` is parsed with one quote pair stripped. Both `API_URL` and `DB_URL` must name a
  loopback host before any service import.
- `SUPABASE_URL` is re-asserted after the import.
- Handler records go to the `--handler-log` file only.
- The lane's live bridge definition is checked for `AS is_protected` and the marker IN-list
  before any arm runs.
- Nothing imports or spawns a worker or web server.

### End state per retracted arm (lane only)

- **retracted-warned:** The failure mark left the row `failed` (branch (b), because the bridge saw
  no marker). The next bridge call, with an unmarked composite pending, turned it back into
  `complete_with_warnings`. The stale error-only Python write never cleared `computation_warned`.
  This is H2, measured on the lane.
- **retracted-unwarned:** The row went `failed`, then `computing` on the next bridge call. That is
  the same end state the loud path would reach. The DECISION still disagreed
  (`layers_agree=false`).
- **retracted-warned-inflight (modelled):** With one other job in flight, the failure mark routed
  the bridge to branch (a). The row read `complete_with_warnings` straight after the failed run, so
  a poller sees terminal success over a failed run. This is H3. It is **modelled** on the lane. A
  production path to this shape is unmeasured (research A2). This SUMMARY does not describe
  observed production behaviour.

**Production cohort: UNMEASURED.** Whether live composite `strategy_analytics` rows carry
`computation_warned = TRUE` is unmeasured (research A1). No remote database was read in this
phase, so no production cohort is claimed. Every statement above is scoped to the loopback lane.

  The judge bites.

  `HARM-PROBE refused: the lane's sync_strategy_analytics_status no longer carries the marker IN-list; the probe's predicate would drift`.

- **Parser:** a quoted `API_URL` passes the loopback check. A value containing `=` survives intact.
  A missing `SERVICE_ROLE_KEY` is refused by name, and a non-loopback `API_URL` is refused by name.
- **Cleanup:** after the runs, the lane held 0 probe strategies, 0 probe users and 0 jobs claimed
  by the probe worker id.

## Deviations from Plan

**1. [Rule 2 - Missing critical functionality] A generic exception arm keeps database error text off the stream**
- **Found during:** Task 1.
- **Issue:** An unexpected psycopg or PostgREST error would print a traceback to stderr, and its
  text can name a row id.
- **Fix:** `main()` catches any other exception. It logs the traceback to the handler log and
  prints only the exception type as a `HARM-PROBE error:` line.
- **Commit:** `707e4a27e`.

**2. [Advisory applied] Scratch dir and TMPDIR**
- Scratch dir S is under the session scratchpad instead of `$TMPDIR`, and every probe run used
  `env -u TMPDIR`, as the orchestrator directed.
- The `subprocess` acceptance grep was anchored to an import statement. It prints nothing.
- No job id constant was introduced. The worker id and the correlation id are not uuid-shaped.

**3. [Additive output line]** The probe prints one extra `HARM-PROBE next-bridge:` line with the
method and the in-flight kind, so the SUMMARY can record both from the run itself. It does not
match `^HARM-PROBE verdict: arm=`, so the four-line count is unaffected.
