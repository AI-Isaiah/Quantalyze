## HIGH

### SFH-R4-01 — D-15 protected path: when the error-only write fails, the curated cause is recorded nowhere (SFH-R3-01, one write later)

**Location.** Both stamp closures, on the `PRESENT` arm:
- in `run_derive_broker_dailies_job` → `_stamp_strategy_analytics_failed`, the
  `await db_execute(_upsert_error_only)` inside the second
  `if existing_status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES:`;
- in `run_stitch_composite_job` → `_stamp_failed`, the `await db_execute(_upsert_error_only)`
  inside the second `if _honour_marker:`.

Neither write has a handler, and no cause line precedes either one.

**Scenario, measured.** A marked refresh fails permanently on a published row, and the live
re-read answers `PRESENT`. The handler's error-only upsert then fails: a 504 (`db_execute` is
not `db_read_with_retry`, so the first one counts), a 42501, a PostgREST 4xx, or a transport
error. `upsert_or_drop_provenance` re-raises every error that does not refuse a marker, unchanged.
The write's exception leaves the closure, and the handler's `return DispatchResult(...)` never
runs. The probe ran the composite zero-member stamp with the write raising `permission denied
for table strategy_analytics`:

| | marked, `PRESENT` | unmarked (`main` behaviour) |
|---|---|---|
| `last_error` (`error_message`) | `permission denied for table strategy_analytics` | same |
| ERROR lines | **0** | 0 |
| cause in any ERROR line | **no** | no |
| cause in any WARNING line | **no** (the only earlier line is `if detail:`) | no |
| `capture_exception` calls | **0** | 0 |
| error kind | `unknown` (retries) | `unknown` |

**Checked against SFH-R3-01's criteria.**

| R3-01 criterion | R4-01 |
|---|---|
| The cause is replaced in `last_error` by the failing I/O's text | yes (measured) |
| A no-detail stamp's cause is logged nowhere | yes (measured) |
| A detail-bearing stamp logs it only at WARNING | yes (the `if detail:` line) |
| A permanent failure is reported as retryable | yes (`unknown`, measured) |
| Generic copy replaces the curated sentence on exhaustion | yes. No stamp landed, so branch (b-prime) writes the per-kind generic (the `_upsert_error_only` comment says so itself) |
| A persistent non-gateway error triggers it on attempt 1 | yes. Even a 504 does, because this is not a retried read |

Two things narrow it compared with R3-01:
- It fires only on the protected path. The row stays published.
- The failed write itself produces no Sentry event. The only trace is the worker loop's `Job %s
  failed` WARNING in `main_worker.py`, so the operator gets less signal here than R3-01 gave.

One thing broadens it: the protected path is the RECURRING one. Once the schedule is on, every
refresh tick that lands on a wedged venue takes it for every marked strategy. It sits on the
same database, a moment after the reads round 3 hardened, and fails for the same reasons.

The rating is **HIGH, the same as R3-01**. Every R3-01 criterion holds, the failure it hides is
HONEST-01's user-facing sentence, and the new comment claims that this exact gap is closed. The
defect is **pre-existing on `main` and re-exposed by the round-3 fix**. The phase did not
introduce it.

**The alert-volume table is not wrong. It shows the silence.** Its "D-15 protects (`PRESENT`)
→ **0** events" row is still 0 when the protected write fails, and that zero is this finding.

**Fix.** Wrap each `await db_execute(_upsert_error_only)` the same way the composite status read
is now wrapped:

```python
try:
    await db_execute(_upsert_error_only)
except Exception as _write_exc:  # noqa: BLE001 — reported, then re-raised
    logger.error(
        "<site>: could not record the protected failure for strategy %s on "
        "compute_job %s (%s). Nothing was recorded for: %s.",
        strategy_id, job.get("id"), _read_failure_text(_write_exc), _cause,
    )
    _capture_read_failure(_write_exc, job_id=job.get("id"))
    raise RefreshMarkerRereadUnavailable(  # or a sibling typed exception
        f"<site>: the protected error-only write failed "
        f"({_read_failure_text(_write_exc)}), so nothing was recorded for: {scrubbed}"
    ) from _write_exc
```

Before choosing a type, decide the disposition. TRANSIENT through `RefreshMarkerRereadUnavailable`
matches the reads, but that type's name and docstring describe a read. A sibling type, such as
`RefreshStampWriteUnavailable` mapped to TRANSIENT in `classify_exception`, keeps the name
accurate. Then add a row for this path to the runbook's alert-volume table: 1 ERROR + 1 capture
= 2, which keeps the per-attempt bound at 3. Correct the "exactly where it is at risk" block
comment in both closures.

**Pin.** For each closure, make `_upsert_error_only` raise on the `PRESENT` path. Assert that
the cause reaches an ERROR line and `error_message`, and assert `log.error.call_count == 1` and
`capture_exception.call_count == 1` (the table-row pin idiom). To neuter, remove the `try`. The
test should go RED on the error count.

**Out of scope, recorded.** The unmarked LOUD `_upsert` in both closures fails the same way (the
right-hand column above). That path is byte-unchanged from `main` and is not this phase's
defect. It is the same class, so if the fix is shaped as a helper, the helper may cover both
writes at no extra cost. Covering only the protected write is enough to close SFH-R4-01.

## LOW

### SFH-R4-02 — `_READ_PROGRAMMING_ERRORS` is honoured at one of the three read handlers

**Location.** `_READ_PROGRAMMING_ERRORS` is checked only in the `except Exception as
_entry_exc` arm of `run_derive_broker_dailies_job`. Two other handlers still map the same types
(`AttributeError`, `TypeError`, `KeyError` and the rest) to TRANSIENT:
- the new `except Exception as _stamp_read_exc` arm in the composite `_stamp_failed`, through
  `RefreshMarkerRereadUnavailable`;
- the `except Exception as exc` arm in `_refresh_marker_live_state`, through `READ_ERROR`. That
  covers both stamp re-reads, the chain edge and the tail mirror.

The constant's own comment gives the SFH-R3-02 rationale: labelling a code defect TRANSIENT
reports it as "the database was busy". That applies identically at these handlers. It is not
silent: each logs at ERROR with the class name and captures. The only difference is the error
kind. **Fix.** Apply the same `isinstance(..., _READ_PROGRAMMING_ERRORS)` split in both handlers,
or state in the constant's comment why the entry read is the only site that needs it. In
`_refresh_marker_live_state`, a programming error would then propagate out of the helper, so
check that the tail mirror, which runs after its enqueue, still behaves as intended.

### SFH-R4-03 — The two stamp-site `READ_ERROR` raises still drop the read's failure kind from `last_error`

**Location.** `_stamp_strategy_analytics_failed` and the composite `_stamp_failed` both call
`_refresh_marker_still_on_row`. That wrapper discards the text that `_refresh_marker_live_state`
was added to return. Their `raise RefreshMarkerRereadUnavailable("… the live re-read of the
refresh marker failed, so no terminal stamp was written for: {scrubbed}")` therefore does not
name the read's failure. The chain edge (`({_read_failure_out})`), the entry read and the
composite status read all do. This is the SFH-R3-02 remedy applied at three of five `last_error`
raise sites. The kind still reaches the helper's ERROR line and the tagged capture, so nothing
is lost, only missing from the first place an operator looks. **Fix.** Call
`_refresh_marker_live_state` at both stamp sites, and put the text before the cause, as the
composite status read does, so the 500-character cut cannot drop the cause.

## INFO

- **I-R4-1, programming-error `last_error`.** On the entry arm's `raise` path, `classify_exception`
  writes `str(exc)`. For a `KeyError` that is only the quoted key, with no class name. The ERROR
  line uses `_read_failure_text` and the tagged capture names the class, so this is a
  readability point about `last_error` only.
- **I-R4-2, the `else: raise ValueError` in `_log_marker_not_confirmed`.** Only a future
  `MarkerLiveState` member can reach it. At the tail mirror it would run after the hop-2 enqueue,
  and the retry re-runs the derive. The comment says exactly this. Accepted.
- **I-R4-3, `_capture_read_failure`.** `with sentry_sdk.new_scope() as scope:` forks the current
  scope, sets the `compute_job_id` tag and captures. The tag does not leak out of the `with`.
  It is valid on the pinned 2.64.0. The helper cannot raise in a way that would replace the
  exception it reports.
- **I-R4-4, raw text in two pre-existing ERROR lines.** The ERROR lines in
  `_refresh_marker_live_state` and in the entry arm's TRANSIENT branch interpolate the raw
  exception, not `_read_failure_text`. This predates round 3 and PostgREST errors do not carry
  credentials, so it is not flagged. The newer lines in the same code use the scrubbed form.

## The six questions in the brief, answered

1. **`_capture_read_failure` and `new_scope`.** Sound; see I-R4-3. Every call sits inside an
   `except` that re-raises or returns `READ_ERROR`, so the capture never replaces a return.
2. **`_refresh_marker_live_state`.** It returns the failure text only on `READ_ERROR` and `None`
   on every other state, so the chain edge's `({_read_failure_out})` cannot print `None` on a
   read failure. Its residue is SFH-R4-03: the stamp sites do not use it.
3. **`_READ_PROGRAMMING_ERRORS` without `ValueError`.** Correct for the installed `postgrest`
   2.31.0. Its malformed-body path raises `APIError` through `ValidationError`, a `ValueError`
   subclass, so leaving `ValueError` out keeps infrastructure answers TRANSIENT. I found no
   postgrest path where a database answer surfaces as one of the listed types. Residue:
   SFH-R4-02, since the constant is honoured at one site.
4. **Removing the unconditional pre-read ERROR: can a real failure now log nothing?** Yes, one:
   SFH-R4-01, a failed protected write. Every READ failure still logs its cause at ERROR: the
   stamp re-read `READ_ERROR` through the site's `_log_marker_not_confirmed` line, and the
   composite status read in its own arm. A definitive not-marked answer logs through the new
   "no longer protects it" line.
5. **Leaving the ERROR off unmarked first computes: does the cause still reach
   `computation_error` and `last_error`?** Yes, whenever the stamp's write succeeds. The
   destructive `_upsert` writes `scrubbed` to `computation_error`, and the arm then returns its
   `DispatchResult`, whose `error_message` becomes `last_error`. The worker loop logs the failed
   job at WARNING. The path is byte-unchanged from `main`, and leaving it at WARNING is the WR-01
   decision, not a silent failure. The exception is a failed write on that path, which loses
   the cause the same way SFH-R4-01 does. That is pre-existing, and I recorded it out of scope
   under SFH-R4-01.
6. **The alert-volume table against the code.** Every row matches its emitters:
   - the ERROR levels in `_log_marker_not_confirmed`: `RETRACTED` and `OTHER_SOURCE` at WARNING;
     `READ_ERROR`, `NO_ID` and `NO_ROW` at ERROR;
   - the one capture per read failure through `_capture_read_failure`;
   - the new "no longer protects it" ERROR lines.

   The derivation holds: every read failure except the tail mirror's raises, walk 2 shows no
   attempt stamps twice, and no stamp follows the chain edge. So the per-attempt bound is 3 and
   the per-job bound is 9 at `max_attempts` 3. The one gap is SFH-R4-01's path, a zero that is
   silence rather than a miscount. Once that is fixed, the table needs a row for the protected
   write failure (2 events).
