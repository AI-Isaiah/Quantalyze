### SFH-R2-05 / IN-01: Sentry noise, recorded, config unchanged

**Files:** `docs/runbooks/ledger-refresh-go-live.md` (composite precondition item 2)
**Commit:** `905ac27fe`
**Fix:** a dated "Alert volume, a known property" bullet. Each `logger.error` is an event under
the default `LoggingIntegration`. A failed re-read at a stamp site or the chain edge produces 3
events. A failed entry publish-state read produces 2, counted from fixer A's working diff at the
time. Each failure ends its attempt, so a job with `max_attempts` of 3 produces at most 9 events,
multiplied across the marked refreshes in flight. The exception event carries no job tag. Global
Sentry config is unchanged. The bullet also says to re-count the bound if the deployed commit
adds an ERROR line.
**Reported to fixer A, not edited (their file):** the stale rationale is the assertion message
in `analytics-service/tests/test_ledger_refresh_composite_nondestructive.py`,
`TestTransientReReadFailureRetries.test_a_raising_reread_writes_nothing_and_fails_transient`, on
the `sentry.capture_exception.call_count == 1` assert: *"the re-read failure did not reach
Sentry. A WARNING is a breadcrumb, not an event, so without this nobody is told …"*. The line is
ERROR now, so the capture's real job is carrying the traceback. It is still present at
`777c7e0bb`. The similar sentence in `test_ledger_refresh_reuse_collision.py` (on the
`log.error.call_count == 1` assert) is CORRECT: it justifies ERROR over WARNING. Leave it.
