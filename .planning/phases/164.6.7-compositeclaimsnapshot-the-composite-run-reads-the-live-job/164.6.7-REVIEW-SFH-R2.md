# 164.6.7 — Silent-failure review, round 2

Cited by symbol, not by line. Nothing was run against any remote database and no worker was
started. Evidence came from reading source and migrations and from one throwaway AST walk. The
walk listed every call to `_stamp_failed`, `_stamp_strategy_analytics_failed`,
`_dispose_broker_nav_error` and `_stamp_429` with each enclosing `try` and its handler types.

## Verdict

Round 1 is closed at the sites it named. Every round-1 finding has a fix in the diff, and I
confirmed each one against the code (see "Round-1 closure" below). The AST walk agrees with the
fix report's caller trace. No broad `except Exception` / bare `except` / `except BaseException`
sits in a `try` BODY between any stamp call and `dispatch`. `_PERMANENT_LEDGER_ERRORS` holds
six typed ledger errors and no base class, so the smoothed pass's degrade catch cannot swallow
`RefreshMarkerRereadUnavailable`. `mt5_terminal_lease` re-raises. `classify_exception` maps
the exception to TRANSIENT, and nothing up the stack catches it before `dispatch`.

The fixes add one new silent failure. The retry **erases the failure it postponed**
(SFH-R2-01). They also leave the round-1 root cause open at a third read (SFH-R2-02): a failed
read becomes a destructive stamp. That is the same D-09 class, one screen above the site that
was fixed. Two further gaps are conditional (SFH-R2-03, SFH-R2-04).

⛔ **Two of these need an orchestrator decision, not a fixer's call:** SFH-R2-02 (does D-09
extend to the entry publish-state read?) and SFH-R2-04 (the chain-edge forward on
`READ_ERROR`, which the round-1 fixer surfaced and left open).

## HIGH

### SFH-R2-01 — The transient retry replaces the handler's original failure reason, and for a stamp with no `detail` that reason is recorded nowhere

**Location:** `_stamp_failed` in `run_stitch_composite_job` and `_stamp_strategy_analytics_failed`
in `run_derive_broker_dailies_job`, at their `MarkerLiveState.READ_ERROR` arm, plus the
`RefreshMarkerRereadUnavailable` arm of `classify_exception`.

**Scenario.** A handler reaches a permanent failure, for example "Composite strategy has no
member keys." or a structural ledger error, and calls the stamp. Every caller of either closure
follows the stamp with `return DispatchResult(FAILED, error_kind="permanent",
error_message=<the specific cause>)`. I spot-checked all 12 direct single-key call sites and the
composite ones. On `READ_ERROR` the closure now raises BEFORE that return:
- `classify_exception` writes `str(exc)[:500]` into `compute_jobs.last_error`. That is the
  re-read failure text ("the live re-read of the refresh marker failed…"), not the handler's
  cause.
- Both closures log `message` only `if detail:`. A stamp with no detail (the no-members stamp,
  `_mark_insufficient`, the malformed returns-denominator stamp, and others) never logs the
  cause at all. When a detail is present, it goes out at WARNING, which is a breadcrumb and not
  a Sentry event.
- The Sentry capture is the READ exception, with no job or strategy tag (see SFH-R2-05).
- On retry exhaustion the bridge's protected branch (or its `'failed'` branch for a retracted
  job) writes `computation_error_copy('transient')`, the generic "automatic retries exhausted"
  sentence. It replaces the curated, specific `message` that HONEST-01 exists to show. The
  account holder is told a permanent failure was a retryable one.
- When the raise happens inside a typed `except` arm, Python sets `__context__` to the original
  exception, but nothing reads it: `classify_exception` sees only the outer one.

It gets worse when the read failure is persistent and not a gateway error: a 42501 on
`compute_jobs`, a PostgREST 406, or an `AttributeError` after a supabase-py API change.
`db_read_with_retry` re-raises those on the first attempt. Each attempt re-crawls the venue,
which is the full derive or composite fan-out. After `max_attempts` the job is `failed_final`
with a `last_error` that names only the symptom. The real cause is gone from every surface. In
this repo the operator's triage reads `compute_jobs.last_error` first.

**Hidden errors.** Every permanent handler failure that coincides with a re-read failure. That
includes the whole programming-error class, which now reads as "transient".

**Fix.**
1. In both closures, log `message` (scrubbed) at WARNING before the re-read, whether or not
   there is a detail. That gives the cause one durable record even if the read then fails.
2. Carry the cause into the exception, so `last_error` names both:
   ```python
   raise RefreshMarkerRereadUnavailable(
       "stitch_composite: the live re-read of the refresh marker failed while "
       f"stamping a terminal failure ({scrubbed}); no stamp written, retrying the job"
   )
   ```
   The derive closure gets the same treatment. `scrubbed` is already computed at the top of
   both closures.
3. Test: in `TestTransientReReadFailureRetries` and in the single-key
   `test_an_unreadable_row_writes_nothing_and_fails_transient`, assert that
   `result.error_message` contains the curated stamp sentence. Neuter: drop the cause from the
   raise, and confirm the test goes RED.

### SFH-R2-02 — The D-09 class is not closed: a failed ENTRY publish-state read still sends a single-key refresh down the destructive path, at WARNING, with no retry and no Sentry

**Location:** `_read_entry_publish_state` and its `except Exception as _entry_exc` arm near the
top of `run_derive_broker_dailies_job`, which feeds `_refresh_publish_status`, which the stamp
closure reads as `existing_status`. The same value feeds the hop-2 forward's
`_metadata_out["publish_status"]`.

**Scenario.** A marked (`ledger-refresh`) derive starts. The entry read of
`strategy_analytics.computation_status` hits a gateway timeout, an httpx transport error, or a
5xx. The arm logs a WARNING that says so plainly ("this refresh takes the LOUD terminal-failure
path at BOTH hops") and sets `_entry_row = {}`. `_refresh_publish_status` stays `None`. If the
derive then fails, `existing_status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES` is false,
and the closure stamps `failed` + `computation_warned=False` over a live factsheet. If the
derive succeeds, the chain edge forwards no `publish_status`, so a hop-2 failure is
destructive too.

This is exactly the shape SFH-01 named, and exactly what D-09 decided against: "a transient
re-read failure must NOT make the destructive un-publishing stamp". It is pre-existing and not
in this diff. But the round-1 root cause was "a failed read becomes a destructive stamp", and
the fixes closed two of that class's three doors. It is also the weakest of the three: it uses
bare `db_execute` (no 504 retry), logs at WARNING (a breadcrumb, never an event), and does not
call `capture_exception`. Nobody is paged.

**Why the fix is cheap here.** This read runs BEFORE any crawl. Raising
`RefreshMarkerRereadUnavailable` (or a sibling that `classify_exception` maps the same way) at
this point costs one queue retry and wastes no work. That is cheaper than either site the round
fixed, because both of those raise after a full crawl.

**Fix (orchestrator decision: does D-09 extend here?).** Read through `db_read_with_retry`. On
exhaustion, log at ERROR, `capture_exception`, and raise the transient exception, gated on the
marker exactly as the read already is. Pin it with a dispatch-driven test (raising entry read ⇒
`FAILED`/`transient`, zero `strategy_analytics` writes). Neuter it by restoring the `_entry_row
= {}` fallback, and confirm the test goes RED.

**Sibling, LOW:** `_read_existing_failed_row` inside the composite `_stamp_failed` also uses bare
`db_execute`. Its failure propagates, and `classify_exception` falls through to `unknown`, which
retries. So it is not destructive. It is inconsistent with the 504 retry now wrapped around the
read that follows it.

## MEDIUM

### SFH-R2-03 — The transient retry is non-destructive only for `complete_with_warnings` / warned rows; for an unwarned `complete` row the retry itself sets up the un-publish

**Location:** the interaction between `RefreshMarkerRereadUnavailable` → `mark_compute_job_failed`
(`failed_retry`) and `sync_strategy_analytics_status`'s non-terminal branch (latest body:
`20260906120000_computation_error_provenance.sql`).

**Scenario.** `mark_compute_job_failed` PERFORMs the bridge on EVERY transition, including
`failed_retry`. With a non-terminal job present and no protect-hold, the bridge's non-terminal
branch writes `computation_status = CASE WHEN status = 'complete_with_warnings' OR
computation_warned THEN 'complete_with_warnings' ELSE 'computing' END`. For a marked refresh of
an UNWARNED `complete` strategy:
1. Attempt 1: the re-read returns `READ_ERROR`, so the job raises transient and goes to
   `failed_retry`. The bridge flips the row to `computing`.
2. Attempt 2: the composite re-reads `existing_status` live, and the derive re-reads it at
   entry. Both see `computing`, which is not in `STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES`.
   So `_honour_marker` / `existing_status` fails, and a repeat of the handler's failure stamps
   `failed` loudly.
3. Alternatively the retries exhaust. At `failed_final`, `v_publish_healthy` is false (status
   is `computing`), so the job is unprotected and the bridge writes `failed`.

Either way the retry D-09 chose "instead of un-publishing" un-publishes. This is pre-existing
for EVERY transient failure of a marked refresh, and the D-15 comment records that every live
PROD ledger row is `complete_with_warnings`. So it is latent, not live. But the fix's own text
states the guarantee without that condition: the `MarkerLiveState` block comment, the
`RefreshMarkerRereadUnavailable` docstring, runbook item 2, and CONTEXT D-09.

**Fix.** At minimum, qualify the guarantee in runbook item 2 and in the block comment: it holds
while the row is `complete_with_warnings` or `computation_warned`. The root fix makes the
bridge's non-terminal branch keep a healthy publish state for a job carrying a refresh marker.
That is a migration. Merging `supabase/migrations/**` auto-applies to PROD, so it needs the
three-reviewer pre-merge pass. Name it and route it. Do not patch it here. A lane assertion
(seed `complete`/unwarned, fail the marked job transient, read the status) would measure it.

### SFH-R2-04 — Chain-edge forward on `READ_ERROR` still drops the marker, so a read blip followed by a hop-2 failure un-publishes

**Location:** the `_refresh_source_out == LEDGER_REFRESH_SINGLE_KEY_SOURCE` block before
`_enqueue_csv_analytics` in `run_derive_broker_dailies_job`.

**Scenario.** Hop 1 succeeds. The forward's live re-read fails and returns `READ_ERROR`. The site
logs, sets `_refresh_source_out = None`, and enqueues hop 2 with no marker and no
`publish_status`. If hop 2 (`compute_analytics_from_csv`, which honours only the snapshot it is
handed) then fails, it stamps loudly and the factsheet goes dark. It takes two independent
failures, and the read is reported at ERROR and to Sentry, so this is not silent. But the end
state is the one D-09 forbids. The round-1 fixer surfaced it and left it to the orchestrator.

**Fix (orchestrator decision).** Re-deriving to retry the forward is the expensive option,
because hop 1 has already crawled and persisted. The cheaper and more accurate option moves the
decision to where it is needed. On `READ_ERROR`, forward the marker together with a key such as
`refresh_marker_unverified_from: <hop-1 job id>`. Hop 2's stamp site then runs the same
`_refresh_marker_still_on_row` against hop 1's row at the moment it would stamp, with the same
`READ_ERROR` → transient rule. Hop 2 does no crawl, so its retry is cheap. This needs the
snapshot-only honour at hop 2 to accept the key. That key reaches the bridge's `is_protected`
only through `source`, so check that the SQL side is unaffected.

**Sub-item, LOW:** on `READ_ERROR` the consequence string "so hop 2 fails LOUDLY" states as fact
that hop 2 will fail. It should say "hop 2 would fail LOUDLY if it fails".

## LOW

### SFH-R2-05 — Three Sentry events per `READ_ERROR` attempt, none tagged with the job

`sentry_init` passes no `default_integrations=False` and no `LoggingIntegration(...)`. With
sentry-sdk 2.64 the default `LoggingIntegration(event_level=ERROR)` is active, so every
`logger.error` is an event. One `READ_ERROR` at a stamp site emits:
1. the helper's `logger.error` (a message event with no `exc_info`),
2. `sentry_sdk.capture_exception(exc)` (an exception event with no job, strategy or site
   tag or extra),
3. `_log_marker_not_confirmed`'s `READ_ERROR` `logger.error` (a third event).

With the default `max_attempts` of 3 that makes nine events per job per blip. A gateway outage
across N marked refreshes multiplies it by N. Meanwhile the one event that carries the stack
cannot be tied to a job. **Fix:** keep one event: `capture_exception` with
`scope.set_tag("job_id", …)` / `set_extra("strategy_id", …)`, or a single `logger.error(...,
exc_info=exc)`. Downgrade the site line to WARNING (it becomes a breadcrumb on that event).
The composite test asserts `capture_exception.call_count == 1` and would still hold.

### SFH-R2-06 — `_log_marker_not_confirmed` would log a false cause if ever handed `PRESENT`

The docstring says "Never called with `PRESENT`", but the final `else:` treats every remaining
state as NO_ID/NO_ROW. If a caller passed `PRESENT`, the log would say "no live row … invariant
breach", which is the SFH-02 class (a confident, wrong cause). All four current callers guard
correctly. **Fix:** make the `else` explicit (`elif state in (NO_ID, NO_ROW)`) and `raise
ValueError` for `PRESENT`.

### SFH-R2-07 — The retrying read widens the window inside `_stamp_failed` under an outer `wait_for`

`db_read_with_retry` can spend up to three request timeouts plus about 3 s of backoff inside
the stamp. Under `dispatch`'s `asyncio.wait_for`, an overrun cancels the stamp between the
re-read and the write. The result is `asyncio.TimeoutError`, which is transient and writes
nothing, so it fails the same way as `READ_ERROR` and is not destructive. I checked the
smoothed third pass's own `wait_for` (whose `TimeoutError` DEGRADES to DONE): its only
`_stamp_failed` arm re-raises before stamping under `structural_degrade=True`, so a permanent
failure cannot be cancelled there into a green DONE. Recorded so the next reviewer does not
re-derive it. The one real cost is that this lengthens the unmeasured
`[164.6.7-COMPOSITE-REREAD-RESIDUE]` window on exactly the slow-gateway path, as the block
comment already says.
