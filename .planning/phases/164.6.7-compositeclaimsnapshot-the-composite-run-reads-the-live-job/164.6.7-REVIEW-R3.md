## Warnings

### WR-01: the pre-read cause line fires at ERROR on the D-15 suppression path, so every protected failure is now a Sentry event

**File:** `analytics-service/services/job_worker.py`. The `logger.error("... terminal failure for
strategy %s on marked compute_job %s — %s%s. Re-reading the refresh marker before choosing the
stamp.")` added by 777c7e0bb sits in two places:
- `_stamp_strategy_analytics_failed`, in `run_derive_broker_dailies_job`;
- `_stamp_failed`, in `run_stitch_composite_job`.

**Issue:** The line runs whenever `existing_status` is terminal-success, which in the composite
is `_honour_marker`. That is before the re-read, so it covers every marked refresh of a published
row, including the ordinary `PRESENT` outcome where D-15 suppresses the stamp.

The D-15 path deliberately reports its suppression at `logger.warning` ("a MARKED ledger refresh
failed … left the publish state … intact (D-15)"). A WARNING is a breadcrumb, not an event.
`init_sentry` keeps the default `LoggingIntegration`, so this new ERROR turns every suppressed
refresh failure into a Sentry event.

The case D-15 exists for is a venue wedge that fails the whole marked cohort on each refresh
tick. That is now one event per strategy per tick, on a path that needs no one's attention.

SFH-R2-01's fix text asked for this line at WARNING. Fixer A logged it at ERROR and flagged the
consequence as "literal compliance". The concern was only ever to keep a record on the path where
the read fails.

**Fix:** Record the cause at ERROR only where it is being postponed, which is the `READ_ERROR`
arm. `_refresh_marker_still_on_row` never raises; it returns `READ_ERROR` on any exception. So
that arm is always reached when the read fails, and the cause is recorded exactly there.

```python
if _live_state is MarkerLiveState.READ_ERROR:
    _log_marker_not_confirmed(
        _live_state, site=..., job_id=..., strategy_id=...,
        consequence=(f"Writing NO terminal stamp for: {scrubbed}; failing the job "
                     "TRANSIENT so the queue can retry it"),
    )
    raise RefreshMarkerRereadUnavailable(...)
```

Drop the pre-read `logger.error`, or make it a `logger.warning`. Keep the "cause logged at ERROR"
assertions in `TestReReadFailsSafe` and `TestTransientReReadFailureRetries`: they still hold,
because the site line now carries the cause. Add one assertion to a `PRESENT`-path test (for
example `test_control_an_unwatched_refresh_is_still_protected`) that `log.error.call_count == 0`.

### WR-02: the runbook's Sentry bound ("3 events at a stamp site, at most 9 per job") was already stale when it was written

**File:** `docs/runbooks/ledger-refresh-go-live.md`, composite precondition item 2, bullet
"Alert volume, a known property".

**Issue:** The bullet counts three events at a stamp site:
- the helper's ERROR;
- the `capture_exception`;
- the site's `_log_marker_not_confirmed` ERROR.

The pre-read cause `logger.error` (WR-01) landed in 777c7e0bb, the first round-2 fix commit. The
bullet landed later, in 905ac27fe, and fixer B's report says the count came "from fixer A's
working diff at the time". The bullet's own re-count trigger ("if the deployed commit adds an
ERROR line on this path, re-count the bound") had already fired when the bullet was committed.

Measured at HEAD, by symbol:

| path | events |
|---|---|
| stamp site `READ_ERROR` (either closure) | **4**: the cause `logger.error`, `_refresh_marker_still_on_row`'s `logger.error`, `sentry_sdk.capture_exception`, `_log_marker_not_confirmed`'s `READ_ERROR` `logger.error` |
| chain edge `READ_ERROR` | 3 |
| entry publish-state read failure | 2 (`logger.error` + `capture_exception`); the bullet is correct here |
| D-15 suppression (`PRESENT`) | **1** per suppressed failure, not in the bullet at all (WR-01) |

The per-job bound is therefore at most 12, not 9. An operator sizing alert rules from the
runbook will under-count.

**Fix:** If WR-01 is fixed as proposed, the stamp site returns to 3 events and the `PRESENT` path
to 0, and the bullet becomes true. Re-count against the deployed commit either way. If WR-01 is
not fixed, rewrite the bullet with the four rows above and the 12-per-job bound.

### WR-03: the composite stamp's flags/status read still erases the handler's cause on a non-gateway failure; f7db9543c narrowed it and its test pins the erasure

**File:** `analytics-service/services/job_worker.py`, `run_stitch_composite_job` → `_stamp_failed`
→ `existing_row = await db_read_with_retry(_read_existing_failed_row)`.
`analytics-service/tests/test_ledger_refresh_composite_nondestructive.py`,
`TestStampReadRetriesAGateway504.test_a_persistent_504_still_fails_and_suppresses_nothing`.

**Issue:** This is round 2's SFH-R2-01 class (rated HIGH there), one statement above the site
that round fixed. The read is unconditional: it runs before `_honour_marker` is computed, so it
covers unmarked first computes as well as marked refreshes.

`db_read_with_retry` retries only `_is_gateway_timeout`. Anything else raises on the first
attempt, for example a 42501, an httpx transport error, a PostgREST 406, or an `AttributeError`
after a client API change. An exhausted 504 also raises. The exception then leaves `_stamp_failed`:
- `classify_exception` falls through to `("unknown", str(exc))`;
- `mark_compute_job_failed` treats `unknown` like `transient` (`failed_retry` until
  `attempts >= max_attempts`), so each attempt re-runs the full composite fan-out;
- `compute_jobs.last_error` records the read's error text;
- the curated `message` (for example "Composite strategy has no member keys.") is logged nowhere.
  `_stamp_failed` logs `message` only `if detail:`, and then at WARNING. The new cause
  `logger.error` sits after this read, so it is never reached.

On exhaustion the bridge writes the generic retry copy over a failure that was permanent.

The new test asserts `expect_error_kind="unknown"` and no write, and describes this as "failure
semantics unchanged". It therefore pins the erasure as intended behaviour: a fix that preserves
the cause turns it RED on the error kind.

**Fix:** Record the cause before the read, and carry it through a read failure:

```python
try:
    existing_row = await db_read_with_retry(_read_existing_failed_row)
except Exception as exc:  # noqa: BLE001
    logger.error(
        "run_stitch_composite_job: could not read strategy_analytics to stamp "
        "strategy %s (%s: %s); no stamp written for: %s",
        strategy_id, type(exc).__name__, exc, scrubbed,
    )
    raise RuntimeError(
        f"stitch_composite: stamp read failed, no stamp written for: {scrubbed}"
    ) from exc
```

This keeps the `unknown` disposition, so nothing is suppressed and the retry is unchanged, while
`last_error` names the cause. Alternatively, use a typed exception that `classify_exception`
maps. Update `test_a_persistent_504_still_fails_and_suppresses_nothing` to assert
`"Composite strategy has no member keys." in result.error_message`, and add a non-gateway
(`RuntimeError`) case.

### IN-01: the entry-read and chain-edge `last_error` texts do not name what failed

**File:** `analytics-service/services/job_worker.py`, the `RefreshMarkerRereadUnavailable` raises
at the entry publish-state read and at the chain edge.

**Issue:** `classify_exception` records `str(exc)`. The entry-read text uses `from _entry_exc`,
but the chained exception's class and message are not in the string. The chain-edge raise sets no
cause at all. So `last_error` reads "the pre-refresh publish-state read failed …", with no hint
of whether it was a 504, a 42501 or a transport error. The ERROR line and the Sentry capture do
carry it.

**Fix:** Append `f" ({type(_entry_exc).__name__})"` to the text. At the chain edge, which has no
exception in scope, have `_refresh_marker_still_on_row` expose the class name alongside
`READ_ERROR`, or accept the gap as it stands.
