## The fix (D-05)

In the `_stamp_failed` closure of `run_stitch_composite_job`:

- The snapshot condition (`_job_source == "ledger-refresh-composite"` and a terminal-success
  prior status) is bound to `_honour_marker`. It is still the first filter.
- Only when `_honour_marker` is true, the closure awaits
  `_refresh_marker_still_on_row(supabase, job.get("id"), LEDGER_REFRESH_COMPOSITE_SOURCE)` on the
  handler-local client. A False answer logs a warning naming the job and strategy and clears
  `_honour_marker`.
- `if _honour_marker:` guards the unchanged error-only branch.

It can only narrow. An unmarked job and a non-terminal-success row never read the live row. A
missing id, no row, a non-dict metadata or a raised exception all answer "not marked", which
takes the loud path. No migration or SQL change (D-04).
