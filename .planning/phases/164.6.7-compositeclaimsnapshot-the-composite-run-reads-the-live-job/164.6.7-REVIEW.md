**Answers to the brief's key questions:**
1. *Does every failure path of the live re-read take the loud path?* Yes, for every `Exception`.
   However, the log line the new call site emits on those paths misattributes the cause (WR-02).

   has unbounded contributors (IN-06), and the deferral names no phase for a data-integrity

## Warnings

### WR-01: The probe's loopback guard is bypassable, because libpq connects to a host `urlparse` never sees

**File:** `analytics-service/scripts/probe_composite_claimtime.py`, `_read_stack_env` (the
`for key in ("API_URL", "DB_URL")` loop) and `_main_async` (`psycopg.connect(env["DB_URL"], ...)`)
**Issue:** The guard checks `urlparse(values["DB_URL"]).hostname` against `_LOOPBACK_HOSTS` and
then passes the unmodified string to `psycopg.connect`. libpq resolves the connection target
differently from `urlparse`. I reproduced this with the venv's `psycopg.conninfo.conninfo_to_dict`:

```
postgresql://u:p@127.0.0.1:54322/postgres?host=db.example.com
  urlparse.hostname -> 127.0.0.1   libpq -> host='db.example.com'
postgresql://u:p@127.0.0.1:54322/postgres?hostaddr=203.0.113.9
  urlparse.hostname -> 127.0.0.1   libpq -> hostaddr='203.0.113.9'  (connects there)
postgresql://u:p@127.0.0.1:54322/postgres?service=remote
  urlparse.hostname -> 127.0.0.1   libpq -> service='remote'
```

`PGHOSTADDR` in the calling shell has the same effect with no change to the DSN at all. libpq
uses `hostaddr` for the TCP connect whenever it is set. The probe then runs `INSERT INTO
auth.users`, `INSERT INTO public.strategies`, an `UPDATE` of `compute_jobs` and `DELETE`s over
that connection. This checkout's CLI is linked to PROD, so "a guard that reads the right-looking
string" is exactly the class this repo has no other automated stop for. The source file is
generated locally and gitignored, which keeps this a WARNING rather than a BLOCKER. Still, the
docstring's claim "BOTH `API_URL` and `DB_URL` must name a loopback host before ... any client
exists" is not what the code enforces.
**Fix:** Check what libpq will actually use, and check again after connecting, before the first
statement:

```python
from psycopg.conninfo import conninfo_to_dict

params = conninfo_to_dict(values["DB_URL"])
if "service" in params or os.environ.get("PGSERVICE") or os.environ.get("PGHOSTADDR"):
    raise ProbeError("DB_URL/env names a libpq service or hostaddr; refusing")
for part in ("host", "hostaddr"):
    for h in filter(None, str(params.get(part, "")).split(",")):
        if h not in _LOOPBACK_HOSTS:
            raise ProbeError(f"DB_URL {part} is not loopback; refusing")
...
with psycopg.connect(env["DB_URL"], autocommit=True) as conn:
    if conn.info.hostaddr not in {"127.0.0.1", "::1"}:
        raise ProbeError("connected peer is not loopback; refusing")
```

To be sure the guard works, neuter it, observe RED with a `?host=` DSN, restore, and observe GREEN.

### WR-02: The new warning says "RETRACTED since the claim — a user-initiated request was served" on paths where nothing was retracted

**File:** `analytics-service/services/job_worker.py`, `run_stitch_composite_job` → `_stamp_failed`,
the `logger.warning("stitch_composite: the refresh marker on compute_job %s has been RETRACTED since the claim ...")`
block
**Issue:** The line fires whenever `_refresh_marker_still_on_row` returns `False`. That covers
four cases: an actual retraction, `job.get("id")` missing, no live row (`data=None`), and a raised
read. Three of those four are not a retraction, and in none of them did a user-initiated request
own the job. When the read raises, the helper logs its own "could not re-read" warning first, so
an operator sees two lines that contradict each other. When there is no row or no id, the
retraction sentence is the ONLY record, and it asserts a cause that did not happen. That is a
silent mis-attribution on the path that un-publishes a funded composite. An operator triaging a
darkened factsheet will look for a resync that never existed. The single-key sites carry the same
wording, and this phase copied it.
**Fix:** Have the call site say what it knows, or have the helper return the reason:

```python
logger.warning(
    "stitch_composite: the refresh marker on compute_job %s is NOT confirmed on the live row "
    "(retracted since the claim, row missing, or the re-read failed; see any preceding "
    "re-read warning). Taking the LOUD terminal path for strategy %s.",
    job.get("id"), strategy_id,
)
```

A better fix is a tri-state return from `_refresh_marker_still_on_row`, such as
`"present" | "retracted" | "unknown"`. The retraction sentence is then logged only when the live
row was read and its `source` differs.

### WR-03: A single transient failure of the new re-read now un-publishes a funded composite on a background refresh, and nothing records that new trigger

**File:** `analytics-service/services/job_worker.py`, `_refresh_marker_still_on_row` (it reads via
`db_execute`) as newly called from `run_stitch_composite_job` → `_stamp_failed`
**Issue:** Before this phase, a marked composite refresh over a `complete_with_warnings` row had
only one way to reach the destructive stamp: the snapshot said so. Now any `Exception` from one
PostgREST read on the job row also routes there. That includes a gateway 504, a `RuntimeError`
from a saturated `_DB_EXECUTOR`, and a connection reset. The result is `failed` plus
`computation_warned = False`, which `strategyGate.ts` renders as `ANALYTICS_FAILED` on a
refresh nobody is watching. That is the exact harm D-15 exists to prevent. The fail-loud
direction is a locked decision (D-05), and this finding does not dispute it. The defect is
twofold. `services.db.db_read_with_retry` exists for precisely this 504 shape and is not used.
And neither the runbook's item 2 nor the TODOS entry records "a failed re-read darkens the
factsheet" as a consequence. The runbook presents it only as a safety property ("a re-read that
fails all take the loud path").
**Fix:** In `_refresh_marker_still_on_row`, read through `db_read_with_retry(_read_live_source)`.
It retries only on the structured 504 and propagates everything else on the first attempt, so
the exception still resolves to `False` and the direction is unchanged. Then add one sentence to
runbook item 2 stating that an unreadable job row takes the destructive stamp, by design. Note
the trade-off: retries lengthen the IN-06 window by up to the retry budget. If that is
unacceptable, keep `db_execute` and record the consequence instead. Either way, pick one and
write it down.

### WR-04: A data-integrity residue is deferred with no phase, and the runbook calls item 6 the only blocker while TODOS says to re-read before scheduling

**File:** `TODOS.md` `[164.6.7-COMPOSITE-REREAD-RESIDUE]` ("Owner: whoever next changes
`sync_strategy_analytics_status`"). `docs/runbooks/ledger-refresh-go-live.md`, the "What is NOT
watched" bullet ("it is the ONLY one still blocking") and item 5 ("blocked ONLY by item 6").
**Issue:** The entry describes a failed composite run that can read `complete_with_warnings`
again at the next bridge call. That is a data-integrity outcome on a funded account. The entry
states its reachability condition itself: "Re-read this line before the composite is scheduled."
Yet the runbook, which is the document an operator follows at scheduling time, twice states that
nothing but item 6 blocks, and mentions the residue only as a ⚠️ aside inside item 3. Two
documents give opposite readings of the same scheduling decision. The repo's standing deferral
rule is that a data-integrity or user-facing deferral must name a PHASE in the ROADMAP, not an
event-triggered owner. "Whoever next changes the function" has no date and no gate, and the
trigger may never fire, because nothing forces a change to that function before the schedule is
registered. CONTEXT D-03 locked "record it in TODOS with that owner". This finding surfaces the
conflict between D-03 and the deferral rule rather than averaging them.
**Fix:** Choose one of these and make both documents say the same thing:
(a) Add a runbook item 7 that is ⛔ BLOCKING until `[164.6.7-COMPOSITE-REREAD-RESIDUE]` is
closed, or explicitly accepted by the founder with a date. Also route the entry to a named phase
through `/gsd-phase --edit`.
(b) If the founder accepts the window for go-live, record that acceptance, with its date and a
reason, in runbook item 3. Remove "Re-read this line before the composite is scheduled" from
TODOS, because a scheduling-time instruction the runbook does not carry will not be read.

**Issue:** `probe_composite_claimtime.py` prints only `HARM-PROBE verdict:`, `HARM-PROBE

### IN-03: The probe claims every pending `stitch_composite` on the lane, never releases them, and leaks rows on a partial seed

**File:** `analytics-service/scripts/probe_composite_claimtime.py`, `_run_arm` (`p_batch_size:
1000`) and `_seed` (called outside the `try`/`finally`)
**Issue:** Any foreign pending `stitch_composite` job is claimed under `_WORKER_ID` and left
`running`. `foreign_rows_claimed` is printed but `_judge` does not act on it. Separately, if
`_seed` fails after the `auth.users` insert (autocommit), the `finally` cleanup never runs
because it only wraps what follows `_seed`. Both effects stay on the private lane.
**Fix:** Use `p_batch_size: 1`, or refuse (`ProbeError`) when `foreign_rows_claimed > 0`. Move
`_seed` into the `try` and make cleanup tolerate partially bound ids.

### IN-04: The handler-log location is unenforced, and a pre-configuration traceback reaches stderr

**File:** `analytics-service/scripts/probe_composite_claimtime.py`, `main` (`--handler-log`
help text: "kept outside the repo") and the `except Exception` arm
**Issue:** Nothing refuses a `--handler-log` path inside the repository. That file receives
every job and strategy id, and the repo is public with `.planning/` tracked. Also, if an
exception other than `ProbeError` is raised before `_configure_handler_log` runs (for example a
`UnicodeDecodeError` or `PermissionError` from `_read_stack_env`, or a failing `mkdir`),
`logger.exception` falls through to logging's last-resort stderr handler. That handler includes
the full traceback, with absolute paths.
**Fix:** Resolve the path and refuse it if `_REPO_ROOT` is among its parents. In the generic
`except`, log the traceback only when the file handler is installed.

### IN-05: No test pins the "narrow only" half of D-05

**File:** `analytics-service/tests/test_ledger_refresh_composite_nondestructive.py`,
`TestPostClaimRetractionTakesTheLoudPath`
**Issue:** Every new test seeds the marker on the snapshot. None seeds an unmarked snapshot with
a marked live row. So an implementation that honoured the LIVE marker alone, which widens
protection, would pass the whole class. That is the direction D-05 forbids ("It can only
NARROW").
**Fix:** Add a test with `metadata=None` (or a different source) and
`live_metadata={"source": _COMPOSITE_MARKER}`. It should assert the loud stamp. Optionally, also
assert that no `compute_jobs` select was issued.

### IN-06: The residue's "milliseconds" is asserted, not measured, and several contributors are unbounded

**File:** `TODOS.md` `[164.6.7-COMPOSITE-REREAD-RESIDUE]`; runbook item 3 ("in the milliseconds
between the live re-read and `mark_compute_job_failed`")
**Issue:** After the re-read, the window includes several further steps. There is the error-only
upsert. On the member-ledger-error and unsupported-venue paths there is also an
`aclose_exchange` network close, in a `finally` or immediately before the stamp. Then come the
heartbeat cancel in `main_worker`, and a `_safe_mark` → `db_execute` that can queue behind a
saturated `_DB_EXECUTOR`. The typical case may be milliseconds, but no reading was taken, and the
probe's zero-member driver exercises none of those contributors.
**Fix:** Say "a short window, typically sub-second and unmeasured", or measure it (log
monotonic deltas around the re-read and the mark on a lane run), and cite that reading.
