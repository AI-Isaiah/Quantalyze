## Assessment of the fixer's three recorded decisions

**(a) Loud-path ERROR scope: SOUND.** ERROR fires where the cause is at risk:
- `READ_ERROR`, through the site's `consequence`;
- a failed composite stamp status read;
- a marked terminal-success row stamped loud after a definitive not-marked answer (the new "no
  longer protects it" line).

It is withheld on `PRESENT`, where D-15 protects the row and nobody needs paging. It is also
withheld on an unmarked first compute, whose cause already lands in `computation_error` and
`last_error`, and which round 2's line never covered either: it was gated on
`existing_status in STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES` (single-key) and
`_honour_marker` (composite). So no path lost an ERROR it had before round 2. WR-01's volume
concern is closed, and SFH-R3-01's record requirement is met on every failure arm.

**(b) Programming errors report before they propagate: SOUND.** `dispatch` does not log a
handler's exception, and the worker loop logs a failed job at WARNING. Without the ERROR and
capture pair, a code defect in the entry read would have produced no Sentry event. Propagating
as itself keeps the class and text in `last_error` and files it `unknown`, which is the "needs a
human look" label.

One residual, not raised as a finding: `TypeError` / `KeyError` can also come from inside the
postgrest client on a malformed response body. Such a case would be filed `unknown` rather than
`transient`. Given the parity measured under (c), that difference is only a label.

**(c) Composite stamp-read arm files programming errors TRANSIENT: SOUND functionally,
inconsistent in its documentation (IN-02).** The claim that only the label differs holds, and it
can be re-checked at two SQL symbols:
- `mark_compute_job_failed` terminalises on the first failure only for `p_error_kind =
  'permanent'`, so `transient` and `unknown` both reach `failed_final` only through
  `v_attempts >= v_max_attempts`;
- `computation_error_copy` gives `'transient'` and `'unknown'` the identical user sentence.

I found no Python or app-side reader that branches on `transient` vs `unknown`: `src/lib/analytics-schemas.ts`
only enumerates the kinds. The `last_error` text still names the class (`AttributeError: …`), and
ERROR plus a tagged capture fire, so the defect is not hidden from an operator. The fixer's reason,
that a curated cause must survive, is real. But option (b)'s shape would have kept it too: log
the cause at ERROR, then bare `raise` for a `_READ_PROGRAMMING_ERRORS` member. So the asymmetry
was a choice, not a constraint.

## Info

### IN-01: the runbook says every alert-table row except the tail mirror's is count-pinned; the `OTHER_SOURCE` half is not

**File:** `docs/runbooks/ledger-refresh-go-live.md`, composite precondition item 2, the
"CORRECTED 2026-09-26" alert-volume table, and the sentence "Every row except the tail mirror's is
PINNED by an exact `log.error.call_count`".

**Issue:** The row "marked row, `RETRACTED` / `OTHER_SOURCE` → loud stamp" is pinned for `RETRACTED`
only. Both `test_the_loud_stamp_over_a_live_row_logs_its_cause_at_error` tests drive
`refresh_marker_retracted`. The composite `test_a_different_live_source_is_not_called_a_retraction`
asserts message content, not `log.error.call_count`. The count itself is right by code shape:
`OTHER_SOURCE` takes the WARNING arm of `_log_marker_not_confirmed`, then the shared "no longer
protects it" ERROR, the same as `RETRACTED`. So a future ERROR added to the `OTHER_SOURCE` arm
alone would not turn anything RED, and the sentence says it would.

**Fix:** Add `assert log.error.call_count == 1` to
`test_a_different_live_source_is_not_called_a_retraction`. Or narrow the sentence to "the
`RETRACTED` half of that row".

### IN-02: `_READ_PROGRAMMING_ERRORS`' block comment contradicts the composite stamp-read arm

**File:** `analytics-service/services/job_worker.py`, the comment above `_READ_PROGRAMMING_ERRORS`
("Labelling them TRANSIENT would hide a code defect behind 'the database was busy'") and the
`except Exception as _stamp_read_exc` arm in `_stamp_failed`.

**Issue:** The composite arm does exactly what the comment calls a hiding. The reasoning for the
asymmetry is recorded only in `164.6.7-REVIEW-FIX-R3.md` (under `.planning/`), not at either code
site. A reader of the comment will take the composite arm for a bug, or "fix" the entry arm to
match it.

**Fix:** Either add one sentence at both sites naming the asymmetry and its reason (the curated
cause, and `transient`/`unknown` parity in `mark_compute_job_failed` / `computation_error_copy`).
Or make the arms consistent: in the composite arm, after the ERROR line and the capture,
`if isinstance(_stamp_read_exc, _READ_PROGRAMMING_ERRORS): raise`. The cause is already on the
ERROR line in that case, and `last_error` would carry the bug's own text.

### IN-03: `RefreshMarkerRereadUnavailable` and its `classify_exception` comment no longer describe every raise

**File:** `analytics-service/services/job_worker.py`, `class RefreshMarkerRereadUnavailable` and
its arm in `classify_exception`.

**Issue:** Since round 3 it is also raised for the composite stamp's `strategy_analytics` status
read. That read is not a refresh-marker read, and it fires on unmarked user stitches. The class
docstring was updated to say so. The `classify_exception` comment still gives the rationale "The
handler could not tell whether a failure may be recorded without un-publishing a funded
account". That rationale does not apply to an unmarked 0-member stitch. This is naming and
comment drift only: the disposition (TRANSIENT, retry) is right for both.

**Fix:** Extend the `classify_exception` comment with the round-3 case's own reason (a cause
exists and cannot be recorded yet). Renaming the class is optional and out of proportion for
this phase.

### IN-04: the new `else: raise ValueError` in `_log_marker_not_confirmed` can be caught by an `except ValueError` arm that stamps again

**File:** `analytics-service/services/job_worker.py`, `run_stitch_composite_job`. The MTM
degenerate-length `_stamp_failed("Composite mark-to-market series has fewer than two
interpretable days …")` call sits inside the MTM `try` whose `except ValueError` arm (F-5) calls
`_stamp_failed` again with the "interior chain-break" message.

**Issue:** Round 3 added a second `ValueError` source inside `_stamp_failed`: the unknown-state
arm of `_log_marker_not_confirmed`. The `PRESENT` guard was the first. If a future
`MarkerLiveState` member reached it on that call, the F-5 arm would catch the `ValueError` and
re-run `_stamp_failed` under a misattributed cause. The second run would raise the same
`ValueError` from inside the handler, and it would propagate as `unknown`. So it is loud and
non-destructive, and it is reachable only by a future enum member.

**Fix:** None required now. If a member is ever added, give the refusal its own exception type
(not a `ValueError` subclass) so that no F-5-style `except ValueError` can intercept it.
