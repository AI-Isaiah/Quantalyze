## Warnings

### WR-01: The LANE-ONLY marker is a self-granted exemption; nothing technical verifies the named object is genuinely TEST/PROD-absent

**Class:** WARNING — this is a robustness/process gap on the mechanism whose whole job is
"impossible to grow silently" (per `164.1.1.1-CONTEXT.md`'s LOCKED decision), not a
data-integrity or user-facing defect today, and not a vacuous test — the checks that exist
(`FORWARD`/`REVERSE`/JSON-shape) are real and do fire (verified in mutation cycle #1 and by the
"fails loudly" JSON tests). It is flagged as a WARNING rather than a BLOCKER because the residual
gap is explicitly acknowledged in `164.1.1.1-CONTEXT.md`'s `<deferred>` section ("An optional
cross-check asserting the marker's named fixture also appears in the file's own RED-UNDER-SETUP
apply list") — this finding names precisely that gap so it does not fall out of view.

**File:** `.github/workflows/ci.yml:3217-3219` (`lane_only_marker()`), and
`src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:700-712` (FORWARD check)

**Issue:** The only technical requirements for a file to be excluded from `sql-tests` execution
are: (1) a `-- LANE-ONLY: {json}` line whose JSON parses and has string `object`/`fixture` keys,
and (2) that `object` string appears *anywhere* in the file's own non-`--`-comment text — which is
trivially satisfiable by pasting the object name into an unreachable branch, a `SELECT '...'`
literal, or any other cosmetic reference that has nothing to do with the file actually being
unrunnable on shared TEST. Nothing in `ci.yml` or the contract test confirms the named object
*really* exists only on the pg-lane (e.g., by cross-referencing the pg-lane fixture list, or by
requiring the marker's `fixture` field to also appear in the same file's own
`RED-UNDER-SETUP` apply list, which is the specific cross-check `164.1.1.1-CONTEXT.md` defers).
The register test (`LANE_ONLY_SITES`) forces the addition to be *visible in a diff* (someone has
to add both the marker and the register entry, or a test goes red) but does not force it to be
*legitimate*.

**Fix:** Land the deferred cross-check from `164.1.1.1-CONTEXT.md`: assert that every
`LANE_ONLY_SITES` entry's `fixture` value also appears in that same file's own `RED-UNDER-SETUP`
apply list (both are read from the same `.sql` file today, so this is a same-file, same-mechanism
addition — no new marker idiom needed). That at least ties the exclusion to a fixture the file
already declares it depends on, closing the "paste an unrelated substring" evasion without
requiring a live database round trip.

### WR-02: `stripSqlLineComments` only strips `--` line comments, not `/* ... */` block comments, weakening the FORWARD/REVERSE object-binding cross-checks

**Class:** WARNING — a robustness gap in the anti-growth guard itself (the mechanism this task
asked to be scrutinized hardest), not a data-integrity/user-facing defect; the practical exposure
is a false positive (over-strict, safe direction) rather than an under-detection, so it is not
promoted to BLOCKER.

**File:** `src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:643-649`

**Issue:** `stripSqlLineComments` filters out lines starting with `--` but does nothing for
`/* ... */` block comments, which do appear elsewhere in the corpus (confirmed:
`test_capital_ownership_column.sql`, `test_ledger_refresh_composite_arm.sql`,
`test_get_verified_cohort_rank_gate.sql`, and others all contain `/*`). Today's two files in
scope (`test_prod_prober_cadence.sql`,
`test_analytics_service_settings_and_vault_tick.sql`) use neither, so the FORWARD and REVERSE
checks are correct for the current corpus (both confirmed passing on the real repo). But the gap
means a future file that references a lane-only object *only* inside a block comment (e.g., a
`/* still queries net._lane_posts, see fixture 34 */` note) would be judged by REVERSE as "must
carry a marker" even though it makes no real query — a false alarm, not a silent hole. It is worth
closing so the check's actual coverage matches its stated intent ("the comment-stripping is
load-bearing").

**Fix:** Extend `stripSqlLineComments` (or add a sibling helper) to also strip `/* ... */` spans,
e.g. via a simple non-greedy regex pass before the line-based `--` filter, since SQL block
comments in this corpus do not nest.

### BL-01: `stripSqlComments`'s block-comment strip runs on RAW text before line-comment stripping, and demonstrably swallows real assertion code today — defeating the REVERSE cross-check's safety guarantee

**Class:** BLOCKER. This is the exact mechanism the brief asked to be scrutinized hardest, the
defect is reproduced against real, currently-committed corpus files (not a hypothetical future
file), and the failure direction is the dangerous one: REVERSE — the check whose entire job is to
catch a file that queries a declared LANE-ONLY object (today, `net._lane_posts`, i.e. real
outbound HTTP via pg_net — the register's own `why` field calls running that against shared TEST
"unsafe, not merely inconvenient") without declaring itself LANE-ONLY — can be silently defeated
by pre-existing, unrelated prose elsewhere in the same file. Round 1's WR-02 characterized this
regex gap as "the practical exposure is a false positive (over-strict, safe direction)"; that
characterization is wrong in the direction that matters, and this find corrects it rather than
narrows it further.

**File:** `src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:664-670` (`stripSqlComments`)

**Root cause:** `stripSqlComments` does `text.replace(/\/\*[\s\S]*?\*\//g, "")` — a non-greedy
block-comment strip over the **raw, unfiltered** file text — and only *afterwards* filters out
`--`-prefixed lines. The block regex has no notion of `--` line-comment context, so a literal
`/*` occurring as **prose inside an existing `--` line comment** (e.g. a sentence illustrating a
glob pattern) is matched as a real comment opener, and the regex then greedily-but-nongreedily
searches forward for the **nearest** `*/` anywhere later in the file — which may also be inert
prose inside a *different*, much later `--` line comment. Everything between those two accidental
tokens, including genuine SQL/PLpgSQL code, is deleted before the FORWARD/REVERSE checks ever see
it.

**Reproduced against real files, verified by running (not just reading):**
- `supabase/tests/test_ledger_refresh_fanout.sql` has 4 raw `/*` occurrences and 1 raw `*/`
  occurrence (measured with `python3 -c "re.finditer(...)"`), all four sitting inside `--` line
  comments (line 119 `-- ... supabase/tests/*.sql ...`, line 157 similar, line 414
  `` -- ... `/* … */` `` which is self-contained, line 416 similar). The first accidental `/*`
  (line 119) pairs, via nearest-match, with the `*/` embedded in line 414's own illustrative
  backtick text — a span of **295 lines**.
- Ran `stripSqlComments` against that file's actual raw text in Node: **21,070 bytes** (of
  131,980) are removed by the block-comment regex alone, versus **0 bytes** removed by the same
  regex once line-comments are stripped first (confirmed by reordering the two operations and
  re-measuring — the reordered version strips 0 extra bytes for this file).
- `supabase/tests/test_ledger_refresh_composite_arm.sql` shows the identical shape: 4 raw `/*` vs
  1 raw `*/`, **16,065 bytes** wrongly removed under the shipped order, 0 under the reordered one.
- **Direct proof of the safety hole:** copied the real `stripSqlComments` logic into a throwaway
  script, took `test_ledger_refresh_fanout.sql`'s actual content, and inserted a single new line
  `PERFORM net._lane_posts;` (a real, non-comment reference to the currently-declared LANE-ONLY
  object) at line 200 — squarely inside the erroneously-stripped 119→414 span. Ran
  `stripSqlComments(mutated).includes("net._lane_posts")` → **`false`**. The REVERSE test
  (`src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:742`) reads exactly this stripped
  text to decide whether an unmarked file must be flagged; with the reference invisible to it, the
  check would report **zero offenders** and CI would stay green while a file that now genuinely
  queries a pg-lane-only object runs unmarked against shared TEST.
- **Today's corpus is unaffected only by luck of content, not by the guard working:** neither
  `test_ledger_refresh_fanout.sql` nor `test_ledger_refresh_composite_arm.sql` currently contains
  the string `net._lane_posts` (confirmed by direct grep — 0 hits in each), and the one file that
  does carry the marker (`test_prod_prober_cadence.sql`) has 0 raw `/*`/`*/` occurrences of its
  own, so `vitest run` on the real repo today still reports 27/27 green. That is precisely the
  "suite stays green because the new code path is outside every existing gate by default" shape
  this round was warned to watch for — the bug is live in shipped code, not merely theoretical.

**Fix — reorder the two strip passes (line comments first, then block comments), confirmed
correct against the real corpus by running it:**
```ts
function stripSqlComments(text: string): string {
  const withoutLineComments = text
    .split("\n")
    .filter((l) => !l.trim().startsWith("--"))
    .join("\n");
  return withoutLineComments.replace(/\/\*[\s\S]*?\*\//g, "");
}
```
Verified: reordered against `test_ledger_refresh_fanout.sql` and
`test_ledger_refresh_composite_arm.sql`, 0 bytes are removed by the block-comment pass beyond what
line-comment stripping already removed (vs. 21,070 / 16,065 bytes under the shipped order); the
REVERSE offender list for the real corpus stays empty (`[]`) and the FORWARD check for
`test_prod_prober_cadence.sql` still holds (`stripped.includes("net._lane_posts") === true`). A
calibration test should also be added asserting a synthetic file whose real object-reference falls
between two unrelated same-file `--`-comment `/*`/`*/` mentions is still detected by REVERSE — the
injected-reference repro above is a ready template.

### IN-04: A non-object JSON marker payload (e.g. bare `null`) throws a raw, file-unnamed `TypeError` instead of the guard's own named-file error

**Class:** INFO — still fails loudly (no silent pass), so this does not meet the round-2 fix bar;
noted for completeness since the guard restructure was explicitly in scope.

**File:** `src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:638` (`const { object,
fixture } = payload;`)

**Issue:** `deriveLaneOnlySites` types `payload` as `Record<string, unknown>` but does not verify
the parsed JSON is actually a non-null object before destructuring. A marker line like
`-- LANE-ONLY: null` (valid JSON) parses successfully, then `const { object, fixture } = payload`
throws `TypeError: Cannot destructure property 'object' of 'payload' as it is null.` — confirmed
by running this exact destructure against `JSON.parse("null")` in Node. The step still fails the
test/CI run (verified: it throws, it does not swallow), so there is no silent-pass risk; the only
defect is that the error message loses the `${name}` file-naming and the tailored explanation the
other two throw sites provide, making a real failure marginally harder to triage.

**Fix (optional):** Guard the object-ness of `payload` before destructuring, e.g. `if (payload ===
null || typeof payload !== "object" || Array.isArray(payload)) { throw new Error(...) }`, reusing
the same named-file error message shape already used for the missing-key and unparseable-JSON
cases.
