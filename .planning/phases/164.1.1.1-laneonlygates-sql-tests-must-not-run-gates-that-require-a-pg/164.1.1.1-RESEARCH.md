# Phase 164.1.1.1: LANEONLYGATES - Research

**Researched:** 2026-09-18
**Domain:** CI SQL-gate integrity (GitHub Actions bash orchestration + PL/pgSQL gate corpus + vitest contract tests)
**Confidence:** HIGH — every claim below is either a direct `Read` of the source-of-truth file at HEAD (quoted verbatim) or a `grep`/`ls` measurement run this session. No package research, no external docs; this is a closed, in-repo problem.

## Summary

`sql-tests`' "Run SQL self-tests against test Supabase project" step globs
`supabase/tests/test_*.sql` unconditionally and runs every match against shared
TEST. One file in that corpus, `test_prod_prober_cadence.sql`, asserts against
`net._lane_posts` — a table that exists **only** inside the throwaway pg-lane
cluster `scripts/pg-lane/run.sh` builds for `sql-mutation`. It is `[VERIFIED:
scripts/pg-lane/fixtures/34-fixture-pg-net-stand-in.sql:23-27]` that this
object is "NEVER APPLIED TO TEST OR PROD" by the fixture's own header. The gate
is permanently red on `sql-tests` and permanently green on `sql-mutation`
(different lane, different assertions against the same migration), and because
`sql-tests` is `needs:`-blocking in the `frontend` aggregator, this one file
is what is currently keeping `POST /api/prober-cadence-alert` off production.

This is a single-file problem today: measured this session, `grep -l
'34-fixture-pg-net-stand-in\|net\._lane_posts' supabase/tests/test_*.sql`
returns exactly one match. The near-miss the ROADMAP names —
`vault.decrypted_secrets` / fixture 32 — is real but structurally different:
both `test_prod_prober_cadence.sql` and `test_analytics_service_settings_and_vault_tick.sql`
reference fixture 32 in their `RED-UNDER-SETUP` apply lists, but only the
prober file's own assertion bodies query an object (`net._lane_posts`) that
has **no real-schema counterpart at all**, and whose real analogue
(`net.http_post` against real `pg_net`) would additionally perform a live
outbound HTTP call from shared CI infrastructure if exercised for real —  a
second, independent reason it cannot be "fixed forward" into TEST. Vault's
stand-in is read-only and TEST carries the real `supabase_vault` view, so a
gate built on it can run for real there (with a different, already-documented
caveat about pre-migration-apply absence). This distinction is the reason "any
`scripts/pg-lane/fixtures/**` reference in the apply list" is **not** a safe
detector for the exclusion set — it would incorrectly also flag the vault
fixture's consumer.

The fix has three coupled parts, all of which change the same handful of
places: (1) a machine-readable exclusion marker inside the .sql file itself,
in the same "structured comment" idiom this repo already uses for
`RED-UNDER-SETUP`; (2) the `sql-tests` step's file-discovery loop filtering on
that marker and printing every exclusion, never silently; (3) the two floors
this file currently feeds — `SENTINEL_FLOOR`/`ARMS_FLOOR` in `ci.yml` (11/213
today) and the file-set/arm-table bijection in
`ci-anti-skip-gate.contract.test.ts` — both of which must move in the same
diff, and the contract test's own corpus-derivation loop must learn to apply
the identical exclusion filter, or it will assert a set `ci.yml` no longer
matches.

**Primary recommendation:** Add a `-- LANE-ONLY: {"fixture": "...", "reason":
"..."}` structured-comment marker to `test_prod_prober_cadence.sql`'s header
(same JSON-in-a-SQL-comment convention as `RED-UNDER-SETUP`), have the
`sql-tests` step's `files=(...)` discovery filter it out and print the
exclusion with its reason on every run, drop `SENTINEL_FLOOR` 11→10 and
`ARMS_FLOOR` 213→206 with the per-file table row removed, and update
`ci-anti-skip-gate.contract.test.ts`'s corpus-derivation loop to apply the
same marker filter so the bijection check keeps passing — plus a NEW pinned
test asserting the excluded-file SET (not a count) so a second exclusion or a
swapped one cannot land unseen.

### Alternatives Considered (for the exclusion-declaration mechanism — scope item 3)

| Option | Tradeoff |
|--------|----------|
| **A. Structured comment marker in the .sql file** (recommended) | Same tier that already declares `RED-UNDER-SETUP`; visible in the file diff; trivially greppable from bash without a JSON parser (the repo's existing `RED-UNDER-SETUP` extraction in `ci.yml` is itself plain `grep`, not `jq`). Con: a second place (the marker) must stay consistent with the file's own assertion bodies — mitigated by requiring the contract test to verify the marker's named fixture is genuinely one the file's `RED-UNDER-SETUP` apply list also carries. |
| **B. Explicit exclusion list hard-coded in `ci.yml`** | Simpler bash (`case "$f" in *test_prod_prober_cadence.sql*) continue ;; esac`), but this is exactly the class of "a number/list restated in this file" CLAUDE.md's own SQL-gate section names as the repeated defect (the `ARMS_FLOOR`/`FILES_FLOOR` history: stale FOUR times). A list of filenames in a workflow YAML is no different in kind from a stale constant — it is not derived from anything and nothing forces it to be re-examined when a new lane-only file is added. Rejected as the primary mechanism for this reason; may still be needed as an operational convenience (see Common Pitfalls) alongside A. |
| **C. Derivation purely from which fixture objects a file references** (no explicit marker at all — infer "lane-only" from "the file's assertion bodies name an object created by a `NEVER APPLIED TO TEST OR PROD` fixture") | Most "automatic," and it is what a first-pass reading of the ROADMAP's phrasing might suggest. **Rejected as the sole mechanism**, MEASURED this session: it does not discriminate the true class from the near-miss. Both `test_prod_prober_cadence.sql` and `test_analytics_service_settings_and_vault_tick.sql` reference `32-fixture-vault-stand-in.sql` — also headed "NEVER APPLIED TO TEST OR PROD" — in their `RED-UNDER-SETUP` apply lists, but only one of them is actually excludable; the other runs directly against the real `vault.decrypted_secrets` view on TEST (see `[VERIFIED: supabase/tests/test_analytics_service_settings_and_vault_tick.sql:40-46]`, quoted in full below). A purely fixture-reference-based rule would over-exclude. It IS useful as a **secondary, machine-checked cross-check** ("does the marked fixture appear in the file's own `RED-UNDER-SETUP` apply list, and does the file's body actually reference an object that fixture — and only that fixture — creates?") rather than as the primary declaration. |

### Pattern: Structured-comment declaration, read pre-execution, never at runtime
**What:** A machine-readable fact about a gate file's requirements, stated as a
single-line JSON-in-comment near the top of the file, extracted by `grep`
before `psql -f` ever opens the file.
**When to use:** Whenever a CI step must decide *whether to run* a file at
all — as opposed to the anti-skip nets, which decide whether a file that DID
run is honest about what it withheld.
**Example (existing precedent, quoted verbatim):**
```sql
-- Source: supabase/tests/test_prod_prober_cadence.sql:182 (RED-UNDER-SETUP is the mutation
-- runner's precedent for this comment-JSON idiom, not new to this phase)
-- RED-UNDER-SETUP: {"apply":["scripts/pg-lane/fixtures/01-fixture-core.sql","scripts/pg-lane/fixtures/02-fixture-sanitize-tables.sql","scripts/pg-lane/fixtures/07-fixture-supabase-default-privileges.sql","scripts/pg-lane/fixtures/12-fixture-profiles-is-admin.sql","scripts/pg-lane/fixtures/15-fixture-auth-role.sql","scripts/pg-lane/fixtures/32-fixture-vault-stand-in.sql","scripts/pg-lane/fixtures/33-fixture-cron-runs.sql","scripts/pg-lane/fixtures/34-fixture-pg-net-stand-in.sql","supabase/migrations/20260907120000_analytics_service_settings_and_vault_tick.sql","supabase/migrations/20260911120000_vault_tick_hardening.sql","supabase/migrations/20260918120000_prod_prober_cadence.sql"]}
```
A `LANE-ONLY` marker in the same family, naming the ONE fixture that makes the
file structurally inexecutable against real infrastructure (not the whole
apply list — most of that list is ordinary migration replay), is the smallest
addition consistent with this precedent.

### Anti-Patterns to Avoid
- **In-file `RETURN`-based skip:** LOCKED OUT by the phase's own constraint (WR-03). The fix must never make `test_prod_prober_cadence.sql` print a `RAISE NOTICE 'SKIP: ...'` and `RETURN` — that is the exact pattern NET1/NET2 exist to fail. The exclusion must happen in `ci.yml`, before `psql -f` is ever invoked on the file, not inside the file's own control flow.
- **Bare filename list in `ci.yml` as the sole record:** see Alternative B above — this repeats the "count/list restated in a file, drifts silently" class CLAUDE.md's own SQL-gate section is written to warn against.
- **Detecting "lane-only" purely by presence of any `scripts/pg-lane/fixtures/**` reference:** MEASURED false positive against the vault fixture (see Standard Stack, Option C).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Is this a whole-file bail-out?" | A new runtime `RAISE NOTICE`-based skip mechanism for this file | The existing pre-execution file-level exclusion pattern (structured comment, filtered before `psql -f`) | The phase's own LOCKED constraint forbids the runtime-skip shape; a new one would be the exact violation the phase exists to prevent. |
| "Which files declare a sentinel?" | A second, independent script/grep that lists sentinel-bearing files for the exclusion feature | The existing derivation already in `ci-anti-skip-gate.contract.test.ts` (`readdirSync(testsDir)` + sentinel regex) — extend it with one more filter | A parallel derivation is a second place for the corpus to drift, the exact class of bug CLAUDE.md's SQL-gate section names repeatedly (four historical staleness incidents on `ARMS_FLOOR` alone). |

**Key insight:** every mechanism this phase needs already exists in this repo in a slightly narrower form (`RED-UNDER-SETUP` comment declarations, file-level `grep -aoE` marker extraction, sentinel/arm floor re-derivation, SITES-not-a-COUNT bijection tests). The work is composition and extension, not invention — and inventing a parallel mechanism is itself the failure mode CLAUDE.md's own SQL-gate section catalogues at length.

## Common Pitfalls

### Pitfall 1: Excluding execution but forgetting the floors
**What goes wrong:** The `files=(...)` loop is filtered so `test_prod_prober_cadence.sql` never runs, but `SENTINEL_FLOOR`/`ARMS_FLOOR` are left at 11/213. Since the file no longer executes, `sentinels_declared` and `arms_declared` both undercount by 1/7 relative to the (unchanged) floors — the step now fails on EVERY run with `"only 10 test file(s) declare ... under the recorded floor of 11"`, a self-inflicted red.
**Why it happens:** The floors and the file-loop are two different pieces of the same step, edited independently; the derivation comment block that lists per-file counts (`test_prod_prober_cadence.sql 7` among the eleven rows, `[VERIFIED: .github/workflows/ci.yml:3589]`) must be edited in the SAME diff, or the arithmetic silently stops matching the corpus — the exact defect class the comment above the floors already warns about ("the sum falls below a number held outside every file it sums").
**How to avoid:** Drop `SENTINEL_FLOOR` 11→10 and `ARMS_FLOOR` 213→206 (213 − 7) in the same commit that adds the filter, and remove the `test_prod_prober_cadence.sql 7` row from the derivation table.
**Warning signs:** `ci-anti-skip-gate.contract.test.ts`'s bijection test (line-range `[VERIFIED: src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:396-449]`) is designed to catch exactly this — it will fail loudly if the table's declared total stops matching the sum of the (filtered) corpus's own sentinels, IF the contract test's OWN derivation loop is ALSO updated to apply the filter (see Pitfall 2).

### Pitfall 2: Updating `ci.yml` but not the contract test's independent corpus scan
**What goes wrong:** `ci-anti-skip-gate.contract.test.ts`'s bijection check (`[VERIFIED: src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:415-425]`, `for (const name of readdirSync(testsDir)) { ... if (!line) continue; actual.set(name, ...) }`) currently builds its "actual" sentinel-bearing file set from **every** file physically present under `supabase/tests/` that declares a sentinel — with no concept of lane-only exclusion. If `ci.yml`'s table drops the `test_prod_prober_cadence.sql` row but this loop is left unchanged, `actual` still contains the file (it is still on disk, still declares `ALL 7 ARMS EXECUTED`), and the `expect(...).toEqual(table.map(([f]) => f).sort())` assertion at line-range `[VERIFIED: src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts:427-432]` fails — the exact opposite direction of Pitfall 1, but the same root cause (two independent derivations of one set, edited in only one place).
**Why it happens:** The contract test was written before any exclusion concept existed; its corpus scan has no filter to apply.
**How to avoid:** The test's derivation loop must apply the identical LANE-ONLY filter the `ci.yml` step applies — ideally by extracting/reading the SAME marker convention from the same files, not a second hard-coded exception list inside the test.
**Warning signs:** `npx vitest run src/__tests__/contracts/ci-anti-skip-gate.contract.test.ts` failing with "the set of files declaring an 'ALL N ARMS EXECUTED' sentinel no longer matches ci.yml's derivation table" is this exact failure mode; it is the intended tripwire, not a false alarm.

### Pitfall 3: Treating the mutation-runner's floor as something that must also move
**What goes wrong:** Seeing `SENTINEL_FLOOR`/`ARMS_FLOOR` drop in `ci.yml`, an implementer might reflexively look for the "matching" move in `scripts/mutation-runner/run.mjs`'s `FILES_FLOOR`/`ARMS_FLOOR` (currently 47/402, `[VERIFIED: scripts/mutation-runner/run.mjs:893,1979]`) — because a comment in `ci.yml` explicitly documents that these two floors have moved together in lockstep historically (`[VERIFIED: .github/workflows/ci.yml:3562-3566]`, "the mutation runner's OWN ARMS_FLOOR moved 384 -> 392 in the same commit, also +8 ... the two agreeing is evidence each of the eight new arms got BOTH a sentinel and a biting twin").
**Why it happens:** That comment's own framing makes divergence look suspicious by default.
**How to avoid:** This phase is the FIRST case where the two floors should legitimately move in OPPOSITE directions — `ci.yml`'s floor drops (the file is removed from `sql-tests` execution) while the mutation-runner's floor is UNCHANGED (the file's 7 RED-UNDER-M arms keep running on the pg-lane exactly as before; this phase adds no new mutation coverage). The plan should add an inline comment at the `ci.yml` floor explaining this specific, deliberate divergence, so a future reader does not "fix" the mismatch.
**Warning signs:** A reviewer or a future audit flagging "these two floors disagree" without checking whether this phase's own reasoning already accounts for it.

### Pitfall 4: Scanning the excluded file in the wrong preflight step
**What goes wrong:** The meta-command preflight ("Preflight - reject psql meta-commands in test files", `[VERIFIED: .github/workflows/ci.yml:2891]`, `files=(supabase/tests/test_*.sql)`) is a SEPARATE step from the execution loop and uses its own independent glob. It is a pure text scan (no DB call), so there is no safety reason to exclude the lane-only file from it — but an implementer copying the execution loop's filter reflexively into this step too would be scope creep with no defect behind it.
**How to avoid:** Leave the preflight step's glob untouched; it is harmless and correct as-is for a file that is never executed against TEST.

## Code Examples

### The anti-skip step's file-discovery + loop entry point (what the filter must sit inside)
```bash
# Source: .github/workflows/ci.yml, "Run SQL self-tests against test Supabase project" step
echo "Discovering supabase/tests/test_*.sql files..."
shopt -s nullglob
files=(supabase/tests/test_*.sql)
# F11 — AN EMPTY GLOB IS AN ERROR, NEVER A QUIET PASS. ...
if [ ${#files[@]} -eq 0 ]; then
  echo "::error::No supabase/tests/test_*.sql files found. ..."
  exit 1
fi
```
The filter must run AFTER this empty-glob guard populates `files[@]}` from the
real corpus (so "corpus is empty" still means the corpus, not the
post-filter set) and BEFORE the `for f in "${files[@]}"; do` execution loop
begins — with every exclusion echoed (`::notice file=...::excluded from
sql-tests — <reason>`) so the F11 doctrine ("an empty glob is an error, never
a quiet pass") has its mirror: an exclusion is stated, never merely absent.

### The marker read pattern to extend (already proven at this file-scan layer)
```bash
# Source: .github/workflows/ci.yml:3363 (NET 1, existing pattern to model the new filter on)
markers="$(grep -aoE "RAISE NOTICE 'SKIP: [^'%]{0,60}" "$f" | sed "s/^.*RAISE NOTICE '//" | sort -u || true)"
```
A `LANE-ONLY` filter would use the identical `grep -a` (NUL-safe, per this
repo's own `wizardErrors.test.ts` lesson) against the **file itself**, not
against psql's runtime output — e.g. `grep -aq '^-- LANE-ONLY:' "$f"` as the
membership test, with the JSON payload extracted the same way
`RED-UNDER-SETUP` already is for the mutation runner.
