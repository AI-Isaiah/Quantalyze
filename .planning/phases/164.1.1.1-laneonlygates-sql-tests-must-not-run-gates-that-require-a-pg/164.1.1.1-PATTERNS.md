**Analog:** itself, `RED-UNDER-SETUP` header (same file, line 182)

**Existing marker idiom to copy** (`supabase/tests/test_prod_prober_cadence.sql:182`, quoted verbatim):
```sql
-- RED-UNDER-SETUP: {"apply":["scripts/pg-lane/fixtures/01-fixture-core.sql","scripts/pg-lane/fixtures/02-fixture-sanitize-tables.sql","scripts/pg-lane/fixtures/07-fixture-supabase-default-privileges.sql","scripts/pg-lane/fixtures/12-fixture-profiles-is-admin.sql","scripts/pg-lane/fixtures/15-fixture-auth-role.sql","scripts/pg-lane/fixtures/32-fixture-vault-stand-in.sql","scripts/pg-lane/fixtures/33-fixture-cron-runs.sql","scripts/pg-lane/fixtures/34-fixture-pg-net-stand-in.sql","supabase/migrations/20260907120000_analytics_service_settings_and_vault_tick.sql","supabase/migrations/20260911120000_vault_tick_hardening.sql","supabase/migrations/20260918120000_prod_prober_cadence.sql"]}
```

**Shape to reuse for the new marker:** single-line, `-- TOKEN: {json}` immediately readable by a plain `grep -a`/`grep -aoE`, sitting in the file's header block alongside the existing marker (not replacing it). A `LANE-ONLY` marker in the same family should:
- Name **one specific object**, not the whole apply list — the locked decision is that the detector keys on `net._lane_posts` (the object the assertion body queries: see `DELETE FROM net._lane_posts;` at line 212 and `SELECT count(*) INTO v_cnt FROM net._lane_posts;` at line 236, both quoted from this file), not on "any pg-lane fixture" (that over-excludes — see the vault near-miss below).
- Carry a `reason` string, because `ci.yml`'s exclusion print (see next section) needs something human-readable to emit — the same reason the fixture header itself (`scripts/pg-lane/fixtures/34-fixture-pg-net-stand-in.sql`) states "NEVER APPLIED TO TEST OR PROD" in prose, not just a boolean.
- Must NOT be an in-file `RAISE NOTICE 'SKIP: ...'; RETURN;` bail-out inside a `DO` block — that shape is exactly what NET 1/NET 2 in `ci.yml`'s step (see below) exist to fail (WR-03 doctrine, `ci.yml:3202-3234`).

**The near-miss to hold in mind while placing the marker** (why the detector cannot be "references a `scripts/pg-lane/fixtures/**` path"):
`supabase/tests/test_analytics_service_settings_and_vault_tick.sql` also names `scripts/pg-lane/fixtures/32-fixture-vault-stand-in.sql` in its own `RED-UNDER-SETUP` apply list, but that file's assertion bodies query `vault.decrypted_secrets`, which has a real counterpart on shared TEST (`supabase_vault` view) — it is NOT lane-only, and legitimately runs on both sides. The marker's object identity (`net._lane_posts`, unique to this file) is what discriminates the two, not fixture co-membership.

### `.github/workflows/ci.yml`, `sql-tests` job, "Run SQL self-tests against test Supabase project" step

**Analog:** the same step's own existing file-scan idioms — quoted from three points in the step, all `[VERIFIED]` at the line numbers below (cite by symbol/step-name for future drift, per `[164.7-CITATION-DRIFT-01]`; these numbers are HEAD-of-branch only).

**1. Where the filter must sit — after the empty-glob guard, before the loop body** (`ci.yml:3186-3198`, quoted verbatim):
```bash
echo "Discovering supabase/tests/test_*.sql files..."
shopt -s nullglob
files=(supabase/tests/test_*.sql)
# F11 — AN EMPTY GLOB IS AN ERROR, NEVER A QUIET PASS. ...
if [ ${#files[@]} -eq 0 ]; then
  echo "::error::No supabase/tests/test_*.sql files found. ..."
  exit 1
fi
echo "Found ${#files[@]} test file(s):"
printf '  - %s\n' "${files[@]}"
```
⛔ **ORCHESTRATOR CLARIFICATION — this sentence contradicted §4 below and is REPLACED.** As
originally written ("the filter belongs … before the `for f in` loop begins") it reads as PRUNING
THE `files` ARRAY. It must not be implemented that way: a pruned file never enters the loop, so the
static accounting block in §4 never runs for it, `sentinels_declared` falls to 10 and
`arms_declared` to 206, and BOTH FLOORS WOULD HAVE TO MOVE — the outcome CONTEXT.md and the
RESEARCH correction explicitly forbid.

**The correct split, and it is two separate things in two places:**

1. **BEFORE the loop — COMPUTE the set only.** Immediately after the empty-glob guard (so "corpus
   is empty" still means the real corpus), derive the lane-only SET by reading each file's marker
   with the §2 `grep -a` idiom, and PRINT every member (§5's never-silent obligation). Do **not**
   remove anything from `files` — the array stays whole, and `${#files[@]}` keeps reporting the real
   corpus size that `src/__tests__/lint-sql-gates.test.ts` pins at 74.
2. **INSIDE the loop — skip EXECUTION only.** For a file in that set, skip `psql -f "$f"` and the
   three `"$out"`-derived checks named in §4, then fall through to the static `"$f"`-only accounting
   exactly as every other file does.

Net effect: `sentinels_declared` stays **11**, `arms_declared` stays **213**, no floor moves, and
the derivation-table row stays. If a plan prunes the array, it has taken the branch this phase
exists to avoid.

**2. The marker-read pattern to model the filter on — NET 1, static extraction from file text, never from psql's runtime output** (`ci.yml:3363`, quoted verbatim):
```bash
markers="$(grep -aoE "RAISE NOTICE 'SKIP: [^'%]{0,60}" "$f" | sed "s/^.*RAISE NOTICE '//" | sort -u || true)"
```
The `-a` flag (NUL-safe) and reading straight out of `"$f"` rather than `"$out"` (psql's captured output) is the pattern to copy: a `LANE-ONLY` membership test is `grep -aq '^-- LANE-ONLY:' "$f"`, evaluated per-file inside (or just before) the same loop, using the identical `-a` convention this repo's own `wizardErrors.test.ts` lesson requires.

**3. The "never silent" printing convention — F11's own mirror requirement.** F11 is quoted above: "AN EMPTY GLOB IS AN ERROR, NEVER A QUIET PASS." The exclusion's mirror obligation (stated explicitly in RESEARCH.md's Code Examples section) is that every exclusion is `::notice file=...::` printed on every run — never merely absent from the loop. There is no existing `::notice::` emission in this exact step to quote (the step uses `::error::` throughout for failures), so this is the one place Claude's Discretion applies to exact spelling; model it on GitHub Actions' own `::notice file=<path>::<message>` annotation syntax, consistent with `::error file=$f::...` used elsewhere in this same step (e.g. `ci.yml:3358`, `3489`, `3518`).

**4. What must NOT move — the static accounting block, per the ORCHESTRATOR CORRECTION.** The per-file loop's static-analysis checks (sentinel declaration count, roster-vs-count self-consistency, `n_arms` ≤ non-comment `RAISE EXCEPTION` sites — all reading `"$f"`, lines ~3479-3514) must keep running for the excluded file. Only the `psql -f "$f"` execution itself and the three `"$out"`-derived checks (partial-skip census, block-terminating-skip hits, and the completion-sentinel-printed check at `ci.yml:3515` — `grep -aF "$sentinel" "$out"`) are skipped for a `LANE-ONLY` file. `SENTINEL_FLOOR=11` and `ARMS_FLOOR=213` (`ci.yml:3663-3664`) and the derivation-table row `test_prod_prober_cadence.sql 7` (`ci.yml:3654-3661` comment block) all **stay unchanged**.

**5. The preflight loop, explicitly OUT of scope for this filter** (`ci.yml:2872`, step "Preflight - reject psql meta-commands in test files", `files=(supabase/tests/test_*.sql)` at `ci.yml:2891`) — this is a pure text scan with no DB call and no safety reason to exclude the lane-only file; leave its glob untouched (Pitfall 4 in RESEARCH.md).
