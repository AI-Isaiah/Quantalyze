# 169.3 SMALLFIXES: silent-failure review

## SFH-01 [HIGH] A failed mandate read now HIDES the allocator's recommendations and says no mandate exists

**Location:** `src/app/(dashboard)/recommendations/page.tsx:77-89` (the read), `:259-263` (header copy), `:285-299` (the branch)

**What happens.** `const { data: preferences } = await supabase.from("allocator_preferences")...maybeSingle()` drops `error`. On any read failure (PostgREST timeout, 5xx, an RLS or grant fault, a column rename on `max_weight` / `preferred_strategy_types`), `preferences` is `null`, `deriveMandateIsSet(null)` returns `false`, and nothing is logged.

**Why this is the phase's defect, not only a pre-existing one.** The 04-SUMMARY records this under "Noted, not changed" as behaviour that "predates this plan". The *ignored error* predates it. The *consequence* does not. Before 169.3 the list rendered independently (`{candidates.length > 0 && (...)}`), so a failed read showed a spurious "Set your mandate" card above the real recommendations. After 169.3 the new single branch `!mandateSet ? <NoMandateState/> : ...` withholds the list entirely. The header description also switches to "No mandate is set yet." So an allocator with a mandate and a computed batch gets three false statements from one transient fault:
- the header says no mandate is set,
- the card says to set one,
- their recommendations are gone.

Nothing reaches the logs or Sentry, so an RLS or column regression on `allocator_preferences` would look like "allocators never set a mandate" indefinitely.

**Concrete scenario.** Migration drops or renames `max_weight` (or a GRANT on the column regresses). PostgREST returns 42703/42501 for every allocator. Every allocator sees "Set your mandate to see recommendations" and no list. `/allocations` for the same user throws, because `getOwnPreferences` checks the error, so the two surfaces the comment says share "the same rule" disagree.

**Hidden errors:** network/timeout, PGRST205 (table missing), 42703 (column missing), 42501 (grant revoked), RLS policy regression, `maybeSingle` multi-row PGRST116.

**Fix.** Read `error`, log it, and render a distinct degraded state. Do not fall into the no-mandate branch. Keep the page up rather than returning a 500, which is why the plan rejected `getOwnPreferences`:

```ts
const { data: preferences, error: preferencesError } = await supabase
  .from("allocator_preferences")
  .select("max_weight, preferred_strategy_types")
  .eq("user_id", user.id)
  .maybeSingle();
if (preferencesError) {
  console.error("[recommendations] allocator_preferences read failed:", preferencesError.code, preferencesError.message);
}
const mandateState: "set" | "unset" | "unknown" = preferencesError
  ? "unknown"
  : deriveMandateIsSet((preferences ?? null) as AllocatorOwnPreferences | null) ? "set" : "unset";
```

Render `NoMandateState` and the "No mandate is set yet" header only for `"unset"`. For `"unknown"`, render a "We couldn't load your mandate, refresh to try again" card with neutral header copy, and do not claim the mandate is absent. Add a `page.mandate-gate.test.tsx` case where the preferences mock returns `{ data: null, error: {...} }` and a batch with candidates exists. Assert that "Set your mandate" is NOT rendered. That test fails on HEAD.

## SFH-02 [MEDIUM] RPC failures render as affirmative "computing" / "nothing matched" states

**Location:** `src/app/(dashboard)/recommendations/page.tsx:103-114` (errors logged only), `:285-299` (branch rewritten this phase)

**What happens.** Both `get_allocator_latest_batch_meta` and `get_allocator_recommendations` errors are `console.error`-ed and then treated as empty. In the branch this phase rewrote:
- **recs RPC fails, batch meta succeeds** → `NoCandidatesState`: "We computed a batch but none of the current strategies matched your mandate. Try relaxing your filters". The allocator is told to loosen a mandate that did match, and may act on it by editing `/preferences`.
- **both fail** → `NoBatchState`: "Your mandate is set… your first batch will appear here after the next run". This is false for an allocator who has had batches for months.

The error-to-empty conflation predates the phase. But 169.3 rewrote this exact block, and its comment claims "ONE branch decides both the header copy above and what renders here". An error arm belongs in that one branch. It is MEDIUM rather than HIGH because the user-facing harm is a misleading empty state, and the one action it prompts (relaxing filters) is reversible.

**Fix.** Carry `batchMetaResult.error || recsResult.error` into the branch. When either is set and there are no candidates, render a "Recommendations could not be loaded, refresh to try again" card instead of `NoBatchState` / `NoCandidatesState`.

## SFH-03 [MEDIUM] "0 connected · Active Allocation auto-synced" when every remaining key is revoked or inactive

**Location:** `src/components/exchanges/AllocatorExchangeManager.tsx:1181` (`connectedCount`), `:1192-1199` (subtitle), header gate `activeKeys.length === 0` at `:1210`

**What happens.** The count moved to `activeKeys.filter(isLiveKey).length`, but two things were left on the old population:
- the gate choosing "No exchanges connected yet." vs the subtitle still reads `activeKeys.length`,
- the suffix still reads `hasHoldings` / `anySyncing`.

When an allocator's only non-disconnected key is revoked (`sync_status = 'revoked'`) or `is_active = false`, and `allocator_holdings` still holds that key's last positions, the header reads **"0 connected · Active Allocation auto-synced"**. Nothing is syncing, and the suffix asserts that a live pipeline keeps the book current. The book is frozen at the revoked key's last read, and the header tells the allocator the opposite. `anySyncing` also counts non-live keys, so an inactive key left in `syncing` produces "0 connected · first sync in progress".

**Hidden condition:** the revoked or inactive transition, which is exactly the case SC7 was written for.

**Fix.** Derive the suffix from the live set. With `connectedCount === 0 && activeKeys.length > 0`, render a neutral subtitle that asserts nothing about syncing, e.g. "No working connection". Compute `anySyncing` over `activeKeys.filter(isLiveKey)`. Add a liveness test: one revoked key with `hasHoldings === true` must not render "auto-synced".

## SFH-04 [MEDIUM] Two "is this key working" predicates disagree, so the "balance renders once" rule silently breaks for an erroring holder

**Location:** `src/components/exchanges/AllocatorExchangeManager.tsx:1244` (`showBalance = shareNote === null && isLiveKey(key)`), against `src/lib/account-share-note.ts:71-79` (`isWorkingHolder`) and `src/lib/departed-history.ts:86-92` (`isLiveKey`)

**What happens.** `showBalance` combines two predicates that do not agree:

| | `isWorkingHolder` (share note) | `isLiveKey` (balance) |
|---|---|---|
| `sync_status` values it rejects | `revoked`, `sign_in_failed` and `error` | `revoked` only |
| `is_active` | must be `=== true` | `?? true`, so a null counts as live |

Take a duplicate key B marked against holder A while A is in `error` or `sign_in_failed`:
- `accountShareNote(B)` returns `null`, because the holder is not working, so B shows the balance.
- A is still `isLiveKey`, so A also shows the balance.

The same account balance renders on both rows, which is the double-count SC7 set out to remove. The erroring holder's balance is also its last good read, with no date on the row. That is the reason the plan gave for hiding a departed key's balance, and here it goes unapplied. Nothing signals that the two rules diverged. This is a Rule 7 conflict between two predicates, blended rather than resolved.

**Fix.** Pick one predicate for "this row reads its account now", and use it for both the share note's holder test and `showBalance`. If `sign_in_failed` / `error` keys should keep a balance, the note should still suppress the duplicate row's balance while its holder exists and is not departed. Either way, add the `error`-holder case to `AllocatorExchangeManager.liveness.test.tsx` and assert exactly one `Balance` per account.
