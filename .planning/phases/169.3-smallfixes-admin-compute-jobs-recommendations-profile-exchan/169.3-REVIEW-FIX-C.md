### WR-02 / SFH-04 (residual): one account's balance still showed twice for a composite_member pair or two unmarked keys on one venue account id

**Files modified:** `src/components/exchanges/AllocatorExchangeManager.tsx`, `src/components/exchanges/AllocatorExchangeManager.liveness.test.tsx`
**Commit:** `37cf546ca`
**Status:** fixed. This is a logic change, so it needs human verification.

**Applied fix.**
- Group B's `balanceBearingKeyIds` followed `duplicate` pointers with its own walk. It is replaced by `balanceBearers(activeKeys, identity)`. `identity` is the `accountIdentityTokens(historyKeys)` map that the component already computes for the departed-history card. It covers every key the owner has, departed keys included, and it is the same D-16(a) / D-09 union-find that Open Positions uses in `latest-holdings-per-key.ts`. No second grouping was written. A key whose account is unknown is its own group (`key:<id>`, the fallback `latest-holdings-per-key.ts` uses).
- The order that picks the row is group B's, now applied per account group and only over live keys (`isLiveKey`):
  1. a working key (`isWorkingHolder`) before a live key that is failing,
  2. an unmarked key before one marked `duplicate` or `composite_member`,
  3. the lowest id.

  A revoked key never carries the balance. A group with no live key has no bearer, so its rows show neither a balance nor a note.
- Every other row in a group that has a bearer shows no balance, plus one line: `Balance shown on <bearer's key label>`. The label is the row title the user sees. The line uses `text-xs text-text-muted mt-0.5`, DESIGN.md's caption token (`#64748B`), and carries `data-testid="balance-shown-elsewhere"`. It deliberately has **no** `role="note"`, because the existing tests find the 167.1.2 share note by that role, and a second `note` would break them for the wrong reason.
- A working `duplicate` row whose holder is also working now shows both the share note and the new line. D-74 records that this is intended.
- The helper's docblock no longer says "Deliberately NOT grouped". It now cites D-74.

**Tests: 7 new cases in the `one balance per account identity (D-74)` block of the liveness file.**
- composite_member pair: the balance shows once, on the holder, and the member's row reads "Balance shown on Holder Binance"
- two unmarked keys on the same venue id: the balance shows once, on the lowest id, and the other row names it
- a working twin with a higher id wins over a twin in `error` with a lower id (working first)
- keys on a different venue id, and a key whose venue id is null: each keeps its own balance, and no note appears
- a revoked key on a live key's account: no balance ($7,000 absent), and its row names the live row
- a lone revoked key with a venue id: no balance and no note
- a working duplicate pair: exactly one balance, the share note unchanged, and the new line on the duplicate

**Existing tests changed: none.** All 179 existing exchanges tests passed after the fix without edits, including group B's 7 liveness cases, the 167.1.2 share-note tests, and `shows nothing for a composite_member pair` (`AllocatorExchangeManager.test.tsx`). That last test asserts no `role="note"`, and it still holds because the new line has no role. No test had pinned plan 03's composite_member choice.

**Neuter, recorded.** I took a byte backup to the scratchpad, then put group B's duplicate-only pointer walk back as `groupOf` inside `balanceBearers`, keeping the note rendering so the neuter isolates the grouping. The run gave `Tests 4 failed | 182 passed (186)`:

After I restored from the backup, `grep -c NEUTER` returned 0 and the suite gave `186 passed`. The 3 cases that stayed green under the neuter pin behaviour that should not change: a different account, a lone revoked key, and a duplicate pair, which group B's grouping already covered.
