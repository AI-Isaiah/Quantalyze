### D-76: Credential inputs opt out of saved-login autofill with `new-password` and vendor ignore attributes, and bulk-pasted whitespace is stripped by one shared client helper (planner, gap closure, 2026-09-30)
- **Asked:** `169.3-VERIFICATION.md` truths 12 and 13, the two `ROUTED IN 2026-09-27` items in the
  Phase 169.3 ROADMAP section that no plan claimed. Planned as `169.3-06` (gap closure). D-75 is
  169.4's, so this is D-76.
- **Autofill: what was measured.** `autoComplete="off"` was already on the dialog's key and secret
  (`ApiKeyForm.tsx`, since `6b09f96f0`) when a saved site login was seen filled into both. It is
  also on `ConnectKeyStep` and `MultiKeyConnectStep`. MDN (*Turning off form autocompletion*):
  "Many modern browsers do not support `autocomplete="off"` for login fields". A masked input with
  no usable autocomplete token makes the form a login form, and the text field before it becomes
  the username.
- **Autofill: the choice.** Every masked credential input (API secret, and the OKX passphrase slot)
  gets `autocomplete="new-password"`. Every credential input (key, secret, passphrase) gets
  `data-1p-ignore`, `data-bwignore`, `data-lpignore` and `data-form-type="other"`. The key
  (type=text) keeps `autocomplete="off"`: with no login-form password field beside it, no browser
  pairs it as a username. The passphrase slot must opt out too, even though it is excluded from
  the trim. A lone unmarked password field would turn the form back into a login form, and the key
  field would become its username again.
- **Sources, read 2026-09-30.**
  - Chromium `components/password_manager/core/browser/form_parsing/form_data_parser.cc` (main):
    a `new-password` field is parsed as `new_password` (sign-up), not as the `password` a saved
    login is filled into. That is the parse only. Chrome's resulting fill behaviour is inferred
    from it, not read, and the deferred browser check below confirms it.
  - Firefox `toolkit/components/passwordmgr/LoginManagerChild.sys.mjs` (main): "Not filling form,
    password field has the autocomplete new-password value" (autofill result
    `PASSWORD_AUTOCOMPLETE_NEW_PASSWORD`). Firefox's autofill of an `off` field is pref-gated
    (`signon.autofillForms.autocompleteOff`); the pref's default was not read.
  - MDN recommends `new-password` to prevent password-field autofill, and adds that it "is a hint
    to browsers; some may not comply with it."
  - 1Password developer docs (`1password.dev/web/compatible-website-design`): `data-1p-ignore`.
  - Bitwarden `bitwarden/clients` `apps/browser/src/autofill/services/collect-autofill-content.service.ts`:
    `data-bwignore`.
  - Dashlane SAWF (`dashlane.github.io/SAWF`): "you can set its `data-form-type` attribute to
    `other`".
  - ⚠️ `data-lpignore` is an **unverified vendor hint**: LastPass's support pages could not be read
    from here (certificate error, then a JS-rendered page). It is kept because it is inert
    everywhere else; nothing claims it is proven.
- **Rejected: `autocomplete="one-time-code"` on the secret.** Chromium's `IsNotPasswordField`
  honours it, which is cleaner there: no save prompt and no generation offer. But no handling for it
  was found in Firefox's password manager (the hits were in form autofill and tests, not
  `passwordmgr`), so it would be a Chrome-only fix.
- **Cost, accepted and to be observed.** A `new-password` field can prompt the browser to offer a
  generated password, or to SAVE the submitted key and secret as a login. Removing `off` also lifts
  Firefox's pref-gated save suppression (`signon.storeWhenAutocompleteOff`). The vendor attributes
  cover the extension managers. The browsers' own save prompt is not suppressed by any token found.
- **Whitespace: the rule.** `normalizeCredentialInput` in the new client-safe module
  `src/lib/credential-input.ts` removes one leading and one trailing run of JS `\s` or U+200B.
  That run covers space, tab, CR, LF, NBSP, U+2028/2029 and U+FEFF. Interior characters are left
  alone.
- **Why not share `trimCredential`.** It is module-private in `src/lib/analytics-client.ts`, and
  that module imports `node:crypto` through `tenant-claim.ts`, so a client component cannot import
  it. It also cannot be the same rule: `String.prototype.trim()` strips U+FEFF but NOT U+200B
  (measured with `node -e`). The server rule stays unchanged, as the brief requires. The client
  rule is a superset of it, and the only character the client strips that the server does not is
  U+200B.
- **Which input is normalized: the keystroke guard.** `readCredentialInput(event)` normalizes
  unless the native `inputType` is a keystroke (`insertText`, `insertCompositionText`, `delete…`).
  So paste, drop, autofill and programmatic changes are normalized, and typing is not. Why: an
  interior space the user types (say into an MT5 investor password, which rides the secret slot)
  is briefly trailing, and trim-on-every-change would silently delete it. The server trims the
  typed leading/trailing case anyway. One hook point (`onChange`); no separate `onPaste` copy of
  the rule.
- **Passphrase excluded from the trim** (ROADMAP, and `trimCredential`'s docblock: user-chosen,
  whitespace can be significant). It keeps its raw `onChange`, with a test per surface.
- **Scope.** The three named surfaces: `ApiKeyForm.tsx` (the `/profile` "Connect exchange" dialog,
  and also `ApiKeyManager.tsx`, which renders it), `ConnectKeyStep.tsx` and
  `MultiKeyConnectStep.tsx`. **Same defect class, outside the routed items, not touched here:**
  `src/components/strategy/StrategyForm.tsx`'s "Connect Exchange API Key" modal
  (`/strategies/[id]/edit`) and `src/components/strategy/UpdateMt5SecretDialog.tsx`'s password
  field. Both carry `autoComplete="off"` on masked credential inputs and have untrimmed
  `onChange`s. They are named for the orchestrator to route; this plan does not widen to them.
- ⛔ **CORRECTED 2026-09-30 (orchestrator decision, the founder's standing rule to close a defect
  class across its whole surface): the scope WIDENS to both surfaces named above.** The sentence
  before this line is kept as lineage. `169.3-06` Task 4 applies D-76 to
  `src/components/strategy/StrategyForm.tsx`'s "Connect Exchange API Key" modal
  (`/strategies/[id]/edit`) and `src/components/strategy/UpdateMt5SecretDialog.tsx`'s password
  field, through the same `src/lib/credential-input.ts` helper.
  - **StrategyForm modal: full rule.** The key gets `CREDENTIAL_KEY_INPUT_PROPS`, and the secret
    and OKX passphrase get `CREDENTIAL_SECRET_INPUT_PROPS`. Key and secret normalize bulk input
    through `readCredentialInput`, and the passphrase keeps its raw `onChange`. The modal posts to
    `/api/keys/validate-and-encrypt`, which trims through `trimCredential`, so this matches the
    three routed surfaces.
  - **UpdateMt5SecretDialog: attributes only, NO strip.** The password input gets
    `CREDENTIAL_SECRET_INPUT_PROPS` and keeps `setNewSecret(e.target.value)`. The attributes are
    needed: a lone masked field with no usable token is a saved-login target. The strip is excluded
    for the reason D-76 excludes the OKX passphrase. The strip on the other surfaces rests on "the
    server trims, so the field shows what is sent", and that premise is false here. The rotate
    path never trims. `src/app/api/keys/[id]/rotate-secret/route.ts` line 221 uses `.trim()` only
    as a presence check, line 227 binds the raw `body.new_secret` and line 312 forwards it, and
    `analytics-service/routers/internal.py` passes `req.new_secret` straight to validation (line
    739) and encryption (line 762). A client strip would change the stored password compared with
    today, and an MT5 password is user-chosen and may legitimately contain spaces.
  - **Recorded, not acted on:** the MT5 investor password is trimmed at creation (the wizard's
    secret slot, `create-with-key` → `validateKey` → `trimCredential`) and is not trimmed at
    rotation. That asymmetry predates this phase, and `169.3-06` leaves both server paths
    unchanged.
- ⛔ **WIDENED 2026-09-30 (plan-check round 1): VerificationForm on the landing page joins scope;
  server route unchanged.** Orchestrator decision, recorded here: it is a user-facing member of the
