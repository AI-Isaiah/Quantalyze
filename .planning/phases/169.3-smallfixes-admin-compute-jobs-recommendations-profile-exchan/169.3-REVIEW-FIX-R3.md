## Fixed Issues

### WR-01: Every inputType outside the keystroke list normalized the whole field, so undo and redo could delete a typed interior space

**Files modified:**
- `src/lib/credential-input.ts`
- `src/lib/credential-input.test.ts`
- `src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.credential-input.test.tsx`

**Commit:** `67dbe6764`

**Applied fix:** The rule is inverted. `isKeystrokeInputType` was a keystroke allow-list,
and every type outside it was trimmed. It is replaced by `isBulkInputType`, which trims
only these cases:

- the bulk types D-76 names, held in `BULK_INPUT_TYPES`: `insertFromPaste`,
  `insertFromPasteAsQuotation`, `insertFromDrop` and `insertReplacementText`
  (autofill or a password manager replacing the field);
- an absent or empty `inputType`, which is the autofill or programmatic fallback that
  was already trimmed.

Every other `inputType` now returns raw. That covers keystrokes, deletions,
`historyUndo`, `historyRedo`, `insertFromYank`, `insertTranspose`, and any unknown or
future type. The `readCredentialInput` docblock was rewritten to match. The public API
is unchanged (`normalizeCredentialInput`, `readCredentialInput` and the two prop sets),
and no caller was touched.

The OKX passphrase keeps its raw `onChange`, and `UpdateMt5SecretDialog` still sets the
attributes without stripping. Neither path calls the helper's reader, so the fix does
not reach them.

**Tests added:**
- `credential-input.test.ts`:
  - `historyUndo` returns raw
  - `historyRedo` returns raw
  - an unnamed type returns raw (`insertFromYank` and `someFutureInputType`)
  - `insertReplacementText` trims
  - `insertFromPasteAsQuotation` trims
  - The existing `insertFromDrop` trim case is kept. The describe title no longer says
    "keystroke guard".
- `MultiKeyConnectStep.credential-input.test.tsx`: a surface test on panel 1's secret.
  It types `pass w`, then fires an `input` event carrying `inputType: "historyUndo"` with
  the value `pass `, and asserts the controlled value stays `pass `.
  - A continuation (`user.type("word")` expecting `pass word`) was tried and dropped. The
    `fireEvent` bypasses user-event's own value tracking, so user-event appended to its
    stale `pass w` and produced `pass wword`. That is a harness artifact, not product
    behaviour.
