# Phase 169.3 Plan 01: Admin compute-jobs reads the admin view Summary

**GET /api/admin/compute-jobs now reads the `compute_jobs_admin` view with the service-role client after `isAdminUser`. It no longer calls the broken database function, which failed every call. A failed load in ComputeJobsTable no longer shows "No compute jobs found."**

## Accomplishments

- **The route reads the view.** `route.ts` keeps `assertSameOrigin`, the user read and the `isAdminUser` gate in place. After the gate it reads `compute_jobs_admin` on `createAdminClient()` with:
  - an explicit list of the 21 columns `ComputeJobAdminRow` consumes
  - one `.eq` for each `status`, `kind` or `exchange` param that is present
  - `.order("created_at", { ascending: false })` and `.range(offset, offset + limit - 1)`
  
  The limit and offset clamps, the 500 body and `NO_STORE_HEADERS` are unchanged. A comment says why the function is not used and names `[169-DEAD-ADMIN-JOBS-RPC]` (D-01).
- **No code path calls `get_admin_compute_jobs` now.** The function name is left in only two places: the explanatory comment and the generated `database.types.ts`. It is not dropped and there is no migration (D-01, D-14).
- **The empty row needs a successful load.** In `ComputeJobsTable`, the "No compute jobs found." row now also requires `!error`. This is the only change to the component; the alert copy is untouched.

## Decisions Made

- **The route-test mock records `rpc` as well as the builder methods.** The first RED run gave 9 `TypeError: admin.rpc is not a function` crashes. That is a load failure, not a behaviour RED. With `rpc` recorded, the RED became 6 assertion failures on the view read.
- **Filters use `if (param) query = query.eq(...)`.** An absent or empty param adds no filter. This matches the old `|| null` handling.
