## Summary

anon and authenticated hold TRIGGER and MAINTAIN for the same reason they held TRUNCATE: the Supabase platform bootstrap default ACL on `public` hands `arwdDxtm` to `postgres`, `anon`, `authenticated` and `service_role` on every new table, and this repo's migration chain never issues `GRANT ALL` to a client role. Phase 164.9.7 already removed `D` (TRUNCATE) from the `postgres` default row and from every existing relation; what remains on the `postgres` row for the client roles is `arwdxtm` (INSERT, SELECT, UPDATE, DELETE, REFERENCES, TRIGGER, MAINTAIN). This phase removes `t` and `m`. The proven recipe is 164.9.7's: ONE `DO` block that revokes on all tables in schema, revokes in the `postgres` default row, then proves it from the catalogue only. [VERIFIED: PROD pg_default_acl read 2026-10-08, see PROD reading]

Three findings change the plan relative to a pure copy of 164.9.7:

1. **MAINTAIN does not exist on PG16, and the `sql-mutation` pg-lane runs PG16.** `REVOKE ... MAINTAIN`, `ALTER DEFAULT PRIVILEGES ... REVOKE MAINTAIN` and `has_table_privilege(..., 'MAINTAIN')` all raise `unrecognized privilege type` on 16.13 (reproduced). The migration is applied on the pg-lane by the gate's `RED-UNDER-SETUP`, so every MAINTAIN statement and every MAINTAIN probe must sit behind `current_setting('server_version_num')::int >= 170000`. Consequence for the gate: a MAINTAIN assertion can execute on the local-stack lane (PG 17.6.1.113) but can never be shown RED by the machine-executable mutation corpus, and a section with no twin is refused by the 164.4-02 inclusion pin while `WAIVED_CEILING` is 0. The recommended resolution is in "The SQL gate" and Open Question 1.
2. **The "MAINTAIN = LOCK outage" premise in ROADMAP/CONTEXT is only partly true.** On PG17, `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` is permitted to any holder of MAINTAIN, UPDATE, DELETE or TRUNCATE. Measured on PG 17.6: `authenticated` holding UPDATE and DELETE but not MAINTAIN took ACCESS EXCLUSIVE successfully. So revoking MAINTAIN closes `VACUUM [FULL]`, `ANALYZE`, `CLUSTER`, `REINDEX` and `REFRESH MATERIALIZED VIEW` for the client roles, and does NOT close the lock-hold outage (UPDATE/DELETE stay, by design, behind RLS). The migration header, CHANGELOG and TODOS must not claim the lock outage is closed.
3. **Supabase withdraws default table grants on existing projects on 2026-10-30.** The platform change revokes `select, insert, update, delete` from `anon, authenticated, service_role` in the `postgres`/`public` default ACL. It does not mention TRIGGER, TRUNCATE, MAINTAIN or REFERENCES. This migration is unaffected (a default-ACL REVOKE of an absent entry is a no-op), but any NEW gate arm that asserts a freshly created probe table still grants `SELECT/INSERT/UPDATE/DELETE` to a role will redden on the first dump taken after the change (existing `TRUNC 3` and `TRUNC 4` already carry that exposure). Do not add more arms of that shape. [CITED: supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically]

**Primary recommendation:** one migration with a version-guarded single `DO` block (TRIGGER always, MAINTAIN iff `server_version_num >= 170000`), a manual exact-holder-set rollback, and an EXTENSION of `supabase/tests/test_truncate_revoke_anon_authenticated.sql` with a shared-verb-list arm family whose twins are all `sql` steps (TRIGGER-based, so they bite on the PG16 pg-lane), plus a recorded one-time RED of the MAINTAIN half on a PG17 database.

### Migration shape (skeleton RUN on PG 17.6 and PG 16.13)

House style: header (why / scope / caller impact / "deliberately no data-reading step" / accepted residual), `-- STEP` banner, one closing `DO $verify$` raising `migration <ts> failed: ...` with a SINGLE string-literal format (migration-reviewer invariant 21: no `||` in a `RAISE` format), no `BEGIN/COMMIT`, no session `SET` (invariant 14). One `DO` is one statement, so it is atomic even under the lane's autocommit replay (164.9.7 Pitfall 5).

```sql
DO $verify$
DECLARE
  v_maint     boolean := current_setting('server_version_num')::int >= 170000;
  v_verbs     text[];
  v_sr_before int;
  v_sr_after  int;
  v_held      text;
  v_default   text;
BEGIN
  v_verbs := CASE WHEN v_maint THEN ARRAY['TRIGGER','MAINTAIN'] ELSE ARRAY['TRIGGER'] END;

  SELECT count(*) INTO v_sr_before
    FROM pg_class c CROSS JOIN unnest(v_verbs) AS v(verb)
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege('service_role', c.oid, v.verb);

  REVOKE TRIGGER ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
    REVOKE TRIGGER ON TABLES FROM anon, authenticated;
  IF v_maint THEN   -- MAINTAIN is PG17+: on PG16 these statements raise `unrecognized privilege type`
    REVOKE MAINTAIN ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
    ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
      REVOKE MAINTAIN ON TABLES FROM anon, authenticated;
  END IF;

  SELECT string_agg(c.relname || '/' || r.rolname || '/' || v.verb, ', ' ORDER BY c.relname, r.rolname, v.verb) INTO v_held
    FROM pg_class c CROSS JOIN (VALUES ('anon'), ('authenticated')) AS r(rolname) CROSS JOIN unnest(v_verbs) AS v(verb)
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege(r.rolname, c.oid, v.verb);
  IF v_held IS NOT NULL THEN
    RAISE EXCEPTION 'migration <ts> failed: TRIGGER/MAINTAIN still held (relation/role/verb): %. REVOKE removes only grants made by the current user or a role it is a member of and prints nothing on a grantor mismatch; find the grantor with aclexplode(relacl) and re-run the REVOKE under SET ROLE <grantor>', v_held;
  END IF;

  SELECT string_agg(d.defaclrole::regrole::text || '->' || a.grantee::regrole::text || '/' || a.privilege_type, ', ') INTO v_default
    FROM pg_default_acl d CROSS JOIN LATERAL aclexplode(d.defaclacl) a
   WHERE d.defaclnamespace = 'public'::regnamespace AND d.defaclobjtype = 'r'
     AND d.defaclrole = 'postgres'::regrole AND a.privilege_type = ANY (v_verbs)
     AND a.grantee IN ('anon'::regrole, 'authenticated'::regrole);
  IF v_default IS NOT NULL THEN
    RAISE EXCEPTION 'migration <ts> failed: the postgres default ACL on public tables still grants (%)', v_default;
  END IF;

  SELECT count(*) INTO v_sr_after
    FROM pg_class c CROSS JOIN unnest(v_verbs) AS v(verb)
   WHERE c.relnamespace = 'public'::regnamespace AND c.relkind IN ('r','p','v','m','f')
     AND has_table_privilege('service_role', c.oid, v.verb);
  IF v_sr_after <> v_sr_before THEN
    RAISE EXCEPTION 'migration <ts> failed: service_role TRIGGER/MAINTAIN holders moved % -> %', v_sr_before, v_sr_after;
  END IF;
END
$verify$;
```

Evidence: ran on a Supabase PG 17.6.1.113 container as role `postgres` (non-superuser, as on PROD) over tables + a view + a matview: `ok: verbs {TRIGGER,MAINTAIN}, service_role holders 8, anon/authenticated 0`; the relacl for every relation read `anon=arwdx/postgres,authenticated=arwdx/postgres` afterwards and the default row read `{postgres=arwdDxtm/postgres,anon=arwdx/postgres,authenticated=arwdx/postgres,service_role=arwdDxtm/postgres}`. On a PG 16.13 cluster the same file ran clean (`verbs {TRIGGER}`). With `GRANT MAINTAIN ON public.a2 TO PUBLIC` planted first, PG 17.6 raised `TRIGGER/MAINTAIN still held (relation/role/verb): a2/anon/MAINTAIN, a2/authenticated/MAINTAIN`. [VERIFIED: scratch runs this session]

Decisions encoded (all inside CONTEXT discretion):
- **`ON ALL TABLES IN SCHEMA public`, not a loop**: covers views/matviews/partitions/foreign tables (sequences are excluded from ALL TABLES), and is loud for a non-owner (164.9.7 research). Same as 164.9.7.
- **TRIGGER and MAINTAIN in SEPARATE statements, MAINTAIN dynamic-free but behind an `IF`.** A combined `REVOKE TRIGGER, MAINTAIN` fails whole on PG16. A static `REVOKE MAINTAIN` inside the untaken branch of a `DO` parses and is never executed on PG16 (reproduced: printed the NOTICE, no error), so no `EXECUTE` string plumbing is needed.
- **Self-check scope = REVOKE scope** (relkind `r,p,v,m,f`) via `has_table_privilege`, which also sees PUBLIC grants and inheritance. `FROM anon, authenticated` only (PROD has 0 PUBLIC entries).
- **`FOR ROLE postgres` explicit; NO `FOR ROLE supabase_admin`**: reproduced `ERROR: permission denied to change default privileges` for `postgres` against the `supabase_admin` row (`postgres` is not a member of it) on the PG 17.6.1.113 image. Adding it aborts TEST and PROD.

- **Down file** `supabase/migrations/down/<ts>-rollback.sql` (manual, off the auto-apply path; may carry `BEGIN; SET lock_timeout = '5s'; ... COMMIT;`; 164.9.7 precedent). It runs only against PG17, so it needs no version guard. ## Common Pitfalls

### Pitfall 1: MAINTAIN on PG16
Any executed `MAINTAIN` token (REVOKE, ADP, `has_table_privilege`, aclitem text) errors on the pg-lane. The migration is APPLIED there by the gate's setup list, so an unguarded `REVOKE TRIGGER, MAINTAIN` makes the baseline leg fail and every arm report `baseline` defect. Guard on `server_version_num`, split the statements.

### Pitfall 2: the lock outage is not closed by this phase
`LOCK TABLE ... ACCESS EXCLUSIVE` needs MAINTAIN **or** UPDATE, DELETE or TRUNCATE [CITED: postgresql.org/docs/17/sql-lock.html: "If the user has `MAINTAIN`, `UPDATE`, `DELETE`, or `TRUNCATE` privileges on the table, any lockmode is permitted."]. Reproduced on PG 17.6: `authenticated` (UPDATE, DELETE, no MAINTAIN) took ACCESS EXCLUSIVE; `VACUUM` and `ANALYZE` as that role printed `permission denied to vacuum/analyze "<t>", skipping it` (WARNING, not ERROR), `REFRESH MATERIALIZED VIEW` raised `permission denied for materialized view`. Therefore the 164.9.7 REVIEW MD-01 statement and the ROADMAP goal sentence over-claim. Word the migration header, CHANGELOG and TODOS as "closes VACUUM/CLUSTER/REINDEX/REFRESH MATERIALIZED VIEW and the TRIGGER attach vector; the ACCESS EXCLUSIVE lock-hold remains reachable through UPDATE/DELETE" and book it (a statement/idle timeout on the client roles is the natural mitigation, `[ASSUMED]` A5).

### Pitfall 3: a behavioural VACUUM/ANALYZE arm cannot assert refusal
Those statements only WARN and skip, and `VACUUM` cannot run inside a DO/transaction. Do not write a MAINTAIN behavioural arm around them. If a PG17-only behavioural MAINTAIN probe is ever wanted, `REFRESH MATERIALIZED VIEW` raises 42501 but needs a matview in the lane (PROD has none).

### Pitfall 4: silent grantor mismatch
Same as 164.9.7: REVOKE removes only grants made by the current user or a role it is a member of. Every TRIGGER/MAINTAIN ACL entry on PROD has grantor `postgres` today, so this is a guard, not a live fault; the has_table_privilege sweep is mandatory because the failure is silent.

### Pitfall 5: `supabase_admin` default row
It grants TRIGGER and MAINTAIN (and TRUNCATE) to both client roles on any table `supabase_admin` creates in `public`. `postgres` cannot alter it (reproduced `permission denied to change default privileges`). All 67 relations are `postgres`-owned and 0 are extension-owned, so it is latent. The residual and its detector `TRUNCREVOKE-ADMIN-DETECTOR-01` (TODOS.md) currently name TRUNCATE only; its condition (b) must be widened to "grants TRUNCATE, TRIGGER or MAINTAIN". Do not fold the detector into this phase (it needs prod-prober work, which CONTEXT does not scope).

### Pitfall 6: Supabase default-grant withdrawal on 2026-10-30
See Summary item 3. After the next re-dump on a project that took the change, a new table postgres creates no longer inherits S/I/U/D, so any arm asserting that on a probe table (existing `TRUNC 3` service_role TRUNCATE is unaffected because TRUNCATE is not in the withdrawn set; `TRUNC 4` client SELECT IS in it) will redden on the lane. Keep new positive controls on EXISTING tables (as `VERB 4`) and do not widen the exposure; flag `TRUNC 4` to the founder as a pre-existing time bomb (Open Question 5). The migration itself is safe in either world. `[ASSUMED]` A2: how the platform applies the change to each project's `pg_default_acl` is not documented in the changelog.

### Pitfall 7: anti-skip and LANE-ONLY machinery
`sql-tests` fails a file that prints `NOTICE: SKIP:`, and `-- LANE-ONLY:` exclusions are a pinned register (`ci-anti-skip-gate.contract.test.ts`). Neither is the right tool for a PG-version guard: print a neutral "verbs evaluated" NOTICE and keep the arms in the executed set.

### Pitfall 8: edit of an applied migration
Never edit `20261009130000_revoke_truncate_anon_authenticated.sql` to add TRIGGER/MAINTAIN (migration-reviewer invariant 11). New migration only.

### Pitfall 9: rollback over-grant and TRUNCATE
Two verb lists, not one (holder sets differ by `cron_runs`/`system_settings`); and the rollback must not re-grant TRUNCATE.

### Pitfall 10: `TRUNC 1-SETUP` style anti-vacuity
164.9.7 REVIEW LOW-01/LOW-02 are still true of the existing file and worth a one-line fix while editing it (pin the setup check to the default-granted `cron_runs`; `TRUNC 6` probes a table that lost TRUNCATE earlier). They are LOW findings; per standing rule never fix LOW/INFO unless it is the file being edited anyway - leave a note in the plan rather than expanding scope.

### Pitfall 11: shared TEST is untested here
TEST holder/owner/grantor state was read by 164.9.7 on 2026-10-07 (no non-postgres owner/grantor, no PUBLIC entry, 3 default-ACL rows) but not re-read for TRIGGER/MAINTAIN this session. `[ASSUMED]` A1. A TEST refusal blocks the PROD deploy and the remedy is to revert the merge. Add a plan-time read through the TEST read-only SQL tool, marker first (names TEST).
