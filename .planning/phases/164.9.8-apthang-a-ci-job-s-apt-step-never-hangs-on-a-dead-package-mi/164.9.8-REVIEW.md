## Summary

The wrapper does what it says on the hang path. `timeout` runs inside `sudo`, so TERM and then KILL reach apt-get and the apt method children in its process group. Every network phase is capped inside one budget. The unpack runs `--no-download`, unwrapped and after the archives are cached. `set -euo pipefail` is on line 55, ahead of everything, and an unpack failure exits non-zero through errexit. No wrapper step carries `continue-on-error` or a custom shell.

Budget arithmetic, checked:
- Fail path: budget + kill-after + one sleep, so 413 s for the 400 s default and 373 s for pg_cron's 360 s.

The main defect is in the guard, not the wrapper. R1 is blind to the single-line `run: sudo apt-get install ...` form, which is the most common way a new workflow writes apt. ## Critical Issues

### CR-01: R1 misses `run: sudo apt-get install ...` on one line, and other common forms, so the guard passes a new raw apt step

**File:** `src/__tests__/contracts/ci-apt-bounded.contract.test.ts:198-208` (`CMD_POS`, `PREFIX`, `RAW_APT`). The false claim is at `:62-65`.

**Issue:** `CMD_POS` accepts only these as a command start:
- line start
- `&&`, `||`, `;` or `|`
- `then`, `else` or `do`
- `(`, `{` or `!`

`PREFIX` then accepts only `sudo|env|nohup|exec|command`, flags and `VAR=x`. A YAML single-line `run:` key is none of these. So in `        run: sudo apt-get install -y bar` or `      - run: sudo apt-get update`, the `run: ` text sits between the line start and `sudo`, and nothing in the pattern can consume it.

I extracted lines 78-374 of the test file unchanged and ran them under `node --experimental-strip-types`. I added an in-memory workflow with three steps:

```yaml
      - run: sudo apt-get update && sudo apt-get install -y libfoo   # flagged (only via the `&&`)
      - name: Install bar
        run: sudo apt-get install -y bar                             # NOT flagged
      - name: Install baz
        run: |
          sudo timeout 600 apt-get install -y baz                    # NOT flagged
```

Result: `r1` reported only the `&&` step. `r2` and `censusViolations` stayed `[]`. So a new workflow can add an unbounded, unlimited apt step and every rule and the census stay green.

A regex probe also showed these forms are missed:
- `run: apt-get install`
- `timeout 60 apt-get install` / `sudo timeout 60 apt-get install`
- `time sudo apt-get`
- `/usr/bin/apt-get install` / `sudo /usr/bin/apt-get install`
- `"$SUDO" apt-get install`
- `xargs sudo apt-get install`
- `sudo nice -n 10 apt-get install`
- `sudo -- apt-get install`

The KNOWN LIMIT comment at `:62-65` says a `timeout N apt-get` form "is a violation even when it happens to be bounded". The rule does not flag it, so the comment is false.

Why calibration never saw this: every R1 mutant (`R1a`/`R1b`/`R1c`, `:472-507`) is substituted into the indented body of a `run: |` block through `WRAPPER_PSQL_LINE`. None of them exercises the single-line `run:` key. The real tree passes only because none of its 16 workflows currently writes apt that way. The guard D-02 asks for ("fails when a new apt call lacks them") is not in place for the commonest new-workflow form.

**Fix:** Let the command position include a YAML `run:` key. Accept `timeout`/`time`/`nice`/`xargs` and path-qualified apt as prefixes. Add mutants for each form:

```ts
const CMD_POS = String.raw`(?:^(?:[ \t]*-)?[ \t]*run:[ \t]*|^|&&|\|\||;|\||\bthen\b|\belse\b|\bdo\b|[({!])`;
const PREFIX = String.raw`(?:(?:sudo|env|nohup|exec|command|time|xargs|nice|stdbuf)[ \t]+|timeout[ \t]+(?:-\S+[ \t]+)*\d+\S*[ \t]+|"?\$\{?SUDO\}?"?[ \t]+|--[ \t]+|(?:-u|--user|-g|--group|-n)[ \t]+\S+[ \t]+|-{1,2}[A-Za-z][\w-]*(?:=\S+)?[ \t]+|[A-Za-z_]\w*=\S*[ \t]+)*`;
const RAW_APT = new RegExp(`${CMD_POS}[ \\t]*${PREFIX}(?:\\S*/)?apt(?:-get)?[ \\t]+(?:${APT_OPT})*(?:${APT_VERBS})\\b`, "m");
```

Then add calibration cases that rewrite a whole step into each form. For example, replace mutex-probe's `run: |` block with `        run: sudo apt-get install -y postgresql-client`, and add `      - run: sudo apt-get update`. Each must make `r1` non-empty. Also correct the `:62-65` comment so it matches the rule.

## Warnings

### WR-01: The retry loop retries deterministic apt errors for the whole budget, then blames the mirror

**File:** `scripts/ci-apt.sh:167-200`

**Issue:** `net_phase` failures are not told apart by exit code. A cap kill exits 124 or 137. apt's own refusals exit 100. Some examples of the second kind:
- `E: Unable to locate package` (a typo, or a package dropped from the archive after the 26.04 / PostgreSQL 18 rollover);
- a dpkg frontend lock held by another process (apt-get does not wait by default);
- a malformed sources entry.

All of them return at once, and the loop goes to `sleep 3; continue`. With the 400 s budget that is roughly 130 attempts, each printing a `::warning::` and a forensics block. The step then ends with `::error::MEASURE_FAIL: ... A dead or trickling package mirror, not a repo defect.`

That final sentence is wrong exactly when the defect is in the repo, for example a wrong package name in a workflow. The failure is loud but misattributed, and it costs 6-7 minutes of log noise. It also hides the one apt error line that matters among about 130 repeats.

`--budget` below `APT_MIN_PHASE` is a related case (`bash scripts/ci-apt.sh install --budget 5 x` was measured). It makes no attempt at all and prints the same mirror-blaming MEASURE_FAIL.

**Fix:**
- Capture `rc` from `net_phase`.
- Treat 124 and 137 (wall-clock kills) as retryable.
- For any other non-zero code, cap the retries at a small number such as 2, then exit with a MEASURE_FAIL that names the apt exit code and says "apt refused (exit N); not a timeout, check the package name / lock / sources".
- Make `--budget` below `MIN_PHASE` a usage error (exit 2).
- Put the last exit code into the final MEASURE_FAIL line.

### WR-02: The forensics cannot name the stalled host, which is their only stated purpose (assumption A2)

**File:** `scripts/ci-apt.sh:100-104`

**Issue:** `ls -l /var/lib/apt/lists/partial` runs as the `runner` user. apt creates `partial/` as `_apt`-owned mode 0700 (`SetupAPTPartialDirectory`), so the listing fails. `2>/dev/null` then hides the failure and nothing is printed.

There are two further gaps:
- A fetch-phase stall leaves its partials in `/var/cache/apt/archives/partial`, which is never listed.
- `ss -tn` runs after `timeout` has already killed apt and its methods. The stalled connection is gone, or at best sits in TIME-WAIT among the runner's own sockets.

So RESEARCH A2 ("Forensics output answers it") stays unanswered on every occurrence, and nothing says so.

**Fix:**
- Use `sudo ls -l /var/lib/apt/lists/partial /var/cache/apt/archives/partial`.
- Capture the socket table while apt is still alive. One way: a background `sleep $((cap-5)); ss -tnp` inside `net_phase`. Another: run the phase with `-o Debug::Acquire::http=true -o Debug::Acquire::https=true` into a temp log and tail it on failure.
- Print a line when the listing is unreadable instead of discarding stderr.

### WR-03: The `--provides` skip checks neither version nor a working binary, so D-04's "at a version the step's consumer accepts" is not encoded

**File:** `scripts/ci-apt.sh:144-151`

**Issue:** The skip fires on `command -v` alone. `"${resolved}" --version ... || true` swallows a failing `--version`. On Ubuntu, `/usr/bin/psql` is the `pg_wrapper` symlink from `postgresql-client-common`. If no `postgresql-client-NN` is installed, the symlink still exists on PATH and exits non-zero with "You must install at least one postgresql-client-<version> package". The wrapper still prints `apt-skip:` and exits 0, and skips the install that would have repaired it.

Today every psql caller runs `psql --version` next under errexit, so the job fails loud, but it fails with the wrong diagnosis. The two mutex dead branches gate on `command -v psql` and so inherit the same blind spot.

The version D-04 talks about is printed but never asserted, and the measurement of record (plan 05) does not exist yet at this SHA. The wrapper encodes "present", not "present and acceptable".

**Fix:** Skip only when `"${resolved}" --version` exits 0. Otherwise fall through to the install, with a `::warning::` that names the broken binary. If a minimum psql major matters to the lane, add an optional `--min-major N` that `do_install` compares against the parsed version. At minimum, record in CONTEXT that version acceptance is enforced only by the plan-05 measurement.

### WR-04: The self-test cannot catch a regression in the two invariants the header leads with

**File:** `scripts/ci-apt.sh:288-332`

**Issue:** The five scenarios cover update-hang retry, update-hang budget, fetch-hang retry, skip and fall-through. Nothing fails if:
- the unpack is wrapped in `net_phase` (the "dpkg is never killed mid-unpack" invariant, header item 3, RESEARCH anti-pattern). The stub's unpack never hangs, and no assertion checks that the unpack call bypasses `timeout`;
- every fetch hangs (`fetch:all`): no scenario proves that the budget ends a fetch-only stall with MEASURE_FAIL and that no unpack runs;
- the unpack fails: the stub always exits 0, so `return $?` / errexit propagation is unproven. A future `|| true` on line 190 would pass.

R4 in the guard depends on this self-test, so these gaps are also gaps in the guard.

**Fix:** Add three scenarios:
- `STUB_HANG=fetch:all`: expect rc 1, MEASURE_FAIL, zero `unpack` lines.
- `STUB_FAIL=unpack` (the stub exits 100): expect rc 100 (non-zero).
- Wall-clock check on the unpack: `STUB_HANG=unpack:1` with `--fetch-timeout 2`, run under an outer `timeout 8`, expecting rc 124 from the OUTER timeout. That proves no inner cap killed the unpack. Alternatively, log `$PPID`'s comm in the stub and assert the unpack's parent is not `timeout`.
