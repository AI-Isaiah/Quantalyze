## Implementation Decisions

### Area 1 — The VAC-08 frontier exemption's ceiling (WR-02) — LOCKED
**A COUNT ceiling that is LOUD when crossed.** More than N exempted migrations (N small, ~3)
⇒ exit 1 naming the exempted versions.

Why this shape and not the others, so planning does not re-litigate it:
- It is **this repo's existing idiom**. `WAIVED_CEILING` in `scripts/mutation-runner/run.mjs` is
  exactly this form and sits at 0. Conform to the neighbour rather than invent a second shape.
- One migration above the tip is a normal timing artefact; five is a stuck apply. A count
  discriminates those two; the current unbounded exemption discriminates nothing.
- ❌ A TIME ceiling was rejected: it would make a green run on Friday red on Monday with no code
  change, and nothing in this repo's gates is clock-dependent today.
- ❌ Coupling the exemption to an open TODOS entry was rejected: it wires a SQL gate to parsing a
  Markdown file — a seam that does not exist here and can itself break silently.

⭐ The ceiling is a RATCHET: set it at or just above the measured reality and lower it when the
reality allows, never raise it to make a run pass.

### Area 2 — The world-readable artifact (WR-05) — LOCKED
**NARROW THE ARTIFACT to what it needs to be, rather than widening the redaction.**
Upload only what constitutes the reversal recipe (`ledger.csv`, the `.sql` files) plus the
diagnostic channels after redaction. Everything else the script writes does not enter the artifact
at all.

Why: it removes the CATEGORY instead of managing it. Every future file the script writes is then
out by default rather than in by default. Widening the globs (❌ rejected) is an
allowlist-by-omission — the next new extension is uncovered again, and that is precisely the shape
that produced this finding. Re-running the secret scan afterwards (❌ rejected) would report green
and leave the leak: `pre-census.txt` carries reconstructed `CREATE POLICY … USING (<qual>)` and
owner-named rows, which are not secrets in the scanner's sense.

⛔ **AMENDED 2026-09-09 — `survivors.sql` is the exception, and it was NOT foreseen when this
area was decided.** The locked phrase above says "upload only what constitutes the reversal recipe
(`ledger.csv`, the `.sql` files)". Measured afterwards: `survivors.sql` is built as
`awk '$1=="survivor" {print $4}' pre-census.txt` (`restore-test-from-baseline.sh:918-925`), and
column 4 is `pg_get_triggerdef(...)` plus a reconstructed `CREATE POLICY … USING (<qual>)`. So the
reversal recipe and the leak are THE SAME BYTES, and the original phrasing would have shipped the
policy DDL under a different filename while reading as a fix.

**FOUNDER DECISION 2026-09-09: the DDL appears exactly ONCE, in the file that needs it.**
`survivors.sql` STAYS in the artifact — without it an aborted restore is not reversible, and that
reversibility is something Phase 164.8 deliberately built. What leaves are the files carrying the
SAME DDL again with no such claim on it: `pre-census.txt`, `post-census.txt` and the two
`*-rollback-view.txt` files. That is the intent the script itself already booked as threat
`T-164.8-21` — *"print survivor KEYS here and leave the DDL in `survivors.sql` inside the
artifact"*. ❌ Dropping `survivors.sql` too was rejected (it removes a built capability);
❌ shortening `retention-days` was rejected (world-readable for 7 days is the same state as for 90,
and that line is byte-pinned anyway).

⚠️ The count in the review is wrong and the planner must not carry it: **10 of 18** files pass
through neither the secret scan nor the redaction, not seven. `pre-census.rollback-view.txt`,
`post-census.rollback-view.txt` and `README.txt` were missed. Regenerate the list rather than
trusting either number.

⛔ **The step's own ⚠️ SCOPE comment must be corrected in the same change.** It currently claims
"only the .err/.log/.out channels … ledger.csv and the two .sql files are … secret-SCANNED at the
point they are written", which is a scope the code does not have — the scan runs BEFORE these
files exist. A fix that leaves the comment standing hands the next reader the same false
assurance.

### Area 3 — The two twin-pair asymmetries (WR-03, WR-06) — LOCKED
**Bring both twins level, with SEPARATE constants per file. No shared helper.**

Why: this repo's wiring tests are deliberately self-contained. Phase 164.8 Plan 05 Task 2 states
it outright — *"reuse its slicing/calibration helpers by COPY (the repo's wiring tests are
self-contained files; say so in a comment rather than creating a shared helper nobody else
imports)"*. A shared helper (❌ rejected) would be a new abstraction with two consumers, against
the standing convention. Fixing only the destructive workflow (❌ rejected) would leave WR-03 open,
and WR-03 is what ARMS criterion 1 of this phase — without it a cleanup can delete the new
frontier arms and the self-test reports a smaller PASSED.

⭐ Each copied constant carries a comment naming its siblings and why the duplication is
deliberate, so the next reader does not "fix" it into a shared module.

⛔ **SCOPE AMENDED 2026-09-09, after the pattern-mapper measured it: it is a TRIPLET, not a twin
pair.** A THIRD byte-identical 5-token copy lives at `src/__tests__/prod-prober-wiring.test.ts:93`,
outside the review's file list and outside this phase's original criteria. The founder's decision
was about the CLASS — "one half of a twin pair hardened, the other left" — and fixing two of three
members leaves that class intact.

The amendment was taken WITHOUT a new founder question because it is measured to be free:
`prod-prober.yml` contains **0** occurrences of all four extra tokens (`2>/dev/null`, `|| :`,
`set +o pipefail`, `|| exit 0`), so widening its list 5 → 9 needs no allowlist and no triage.
For contrast, `test-restore-from-baseline.yml` carries **11** `2>/dev/null` sites — that triage is
WR-06's actual work and was always in scope; `supabase-migrate.yml` carries 6 and already ships
the 9-token list, so the planner must read HOW that file's twin tolerates them before copying.

⚠️ Counts measured 2026-09-09 with `grep -cF`; regenerate rather than trusting these numbers.
