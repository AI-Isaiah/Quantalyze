## F1 — HIGH — C-0331 stays vacuous on an EMPTY or reshaped `supabase migration list`, and its own new comment says so

**Location** `.github/workflows/supabase-migrate.yml:858-861` (TEST twin) and `:1158-1161` (PROD).
**Status** CONFIRMED by reading.

The phase added `-a` to both greps. That closes the *encoding* half of the vacuity (a NUL byte making
grep report clean). It does not close the *emptiness* half, and the check is purely negative:

```
supabase migration list --db-url "${dsn}" | tee "${RUNNER_TEMP}/test-migration-list.txt"
if grep -aEiq '(^|[[:space:]|])reverted([[:space:]|]|$)' "${RUNNER_TEMP}/test-migration-list.txt"; then
```

Failure scenario: the CLI exits 0 but prints an empty list, a header-only list, or a table whose
"Reverted" column has been reworded or re-cased between CLI versions. `grep -q` exits 1, the branch is
skipped, the group closes, `apply-test` goes green, and `apply`'s `needs.apply-test.result == 'success'`
green-lights the PROD apply. What the operator sees is a passing "Post-apply migration list
verification (C-0331 twin)" group. What is true is that nothing was verified.

`set -euo pipefail` *does* protect the adjacent case — a CLI that exits non-zero aborts the step at the
pipeline, so rc-2/unreadable-file is not a live path here. The live path is "exit 0, wrong or empty text".

The comment the phase added directly above the TEST twin states the defect and stops:

> This is a NEGATIVE check, so reading clean is indistinguishable from finding nothing — and this one
> green-lights the PROD apply.

The same phase's sibling check does it correctly. `.github/workflows/test-restore-from-baseline.yml:1333-1341`
pairs the negative grep with a **positive** one, with an explicit rationale ("this assertion is
deliberately positive so a wording change reddens instead of passing vacuously"):

```
if grep -aq 'Would push these migrations:' "${out}"; then ... exit 1; fi
if ! grep -aq 'Remote database is up to date.' "${out}"; then ... exit 1; fi
```

**Recommendation.** Give C-0331 a positive floor before the negative grep, both sites:

```
rows="$(grep -ac '[0-9]\{14\}' "${RUNNER_TEMP}/test-migration-list.txt")" || rc=$?
[ "${rc:-0}" -le 1 ] || { echo "::error::MEASURE_FAIL: could not read the migration list (grep exited ${rc})."; exit 1; }
if [ "${rows}" -eq 0 ]; then
  echo "::error::MEASURE_FAIL: 'supabase migration list' printed no migration version at all. An empty list is not a list with no reverted rows — the C-0331 check would pass without having read anything, and this check is what green-lights the PROD apply."
  exit 1
fi
```

## F2 — MEDIUM/HIGH — the `2>/dev/null` allowlist is a COUNT, not a set of sites; a one-for-one swap is invisible

**Location** `src/__tests__/test-restore-workflow-wiring.test.ts:309` (`const ALLOWED`) and `:311-328`
(`softeningOffenders`).
**Status** CONFIRMED by reading.

```ts

...
const n = live.split(token).length - 1;
const allowed = ALLOWED[token] ?? 0;
if (n === allowed) continue;
```

The scan is satisfied by *any* five `2>/dev/null` occurrences in the scannable restore block. Delete one
of the three benign probe suppressions (`:605`, `:607`, `:609` — a step that is non-fatal by design) and
add one on the marker step's psql, and the count is still 5, the scan reports zero offenders, and the
step whose stderr *is* the evidence that the wrong database was identified goes quiet. That is precisely
the mutation the file's own calibration at `:1416-1443` treats as the worst of the nine — it only detects
it because that mutation moves the count to 6.

Both calibrations move the count: `:1426` mutates to 6, `:1483-1493` mutates to 4. Neither exercises a
count-preserving swap, which is by construction the one shape a count cannot see.

Note the naming: the `it` at `:1469` is titled "the `2>/dev/null` allowlist is an exact set", and the
phase brief describes it as "an exact-set allowlist of the `2>/dev/null` sites". The exact set is over
**tokens** (`expect(Object.keys(ALLOWED)).toEqual(["2>/dev/null"])`), not over sites. The site list exists
only as a five-item prose enumeration in the doc comment at `:275-305`.

**Recommendation.** Pin the sites, not the count — the prose enumeration already names all five:

```ts
  "pg_config --bindir 2>/dev/null",
  "ls -d /usr/lib/postgresql/*/bin 2>/dev/null",
  ".../initdb /usr/lib/postgresql/*/bin/pg_ctl 2>/dev/null",
  'FROM supabase_migrations.schema_migrations;" 2>/dev/null',

```
then assert every live `2>/dev/null` line matches exactly one entry, and that every entry matches exactly
one line. That reds in both directions *and* on a swap, and it costs nothing this file is not already
carrying as prose.

## F3 — MEDIUM — the widened nine-token scan cannot see a step that simply never sets `-e`

**Location** `src/__tests__/test-restore-workflow-wiring.test.ts:236-246` (`SOFTENING_TOKENS`);
live instances at `.github/workflows/test-restore-from-baseline.yml:516`, `:557`, `:603`.
**Status** CONFIRMED by reading.

`set +e` is banned outright. `set -uo pipefail` — a `run:` block that never turns `-e` on in the first
place — is functionally the same softening over the whole step, contains none of the nine tokens, and is
invisible to the scan. Three live steps in the *scanned* restore job use it today and the scan reports
zero offenders.

All three of today's instances are defensible and I checked each: `:516` and `:557` are the extractor
self-test / audit census assertions, which capture `status=$?` explicitly and route every path to a named
`::error::` + `exit`; `:603` is the deliberately non-fatal PostgreSQL-binaries diagnostic echo. The
comment at `:509-512` says outright that omitting `-e` is what lets those steps avoid `|| true`. So this
is not a live defect — it is a gap in a control whose stated purpose is "the first five were not a class,
they were five spellings of a class". A new step written `set -uo pipefail` sails through.

**Recommendation.** Add a tenth, structural check to the same scan: every `run: |` block in the scannable
restore block must carry a live `set -e`/`set -euo pipefail` line, with the three current exceptions
named in an exact-set allowlist carrying the same per-site justification the `2>/dev/null` sites get.

## F4 — MEDIUM — `git merge-base --is-ancestor … 2>/dev/null` collapses rc 1 and rc ≥ 2, and discards the channel that separates them

**Location** `.github/workflows/test-restore-from-baseline.yml:413`; allowlist justification for
"site 1" at `src/__tests__/test-restore-workflow-wiring.test.ts:280-284`.
**Status** CONFIRMED by reading.

```
if ! git merge-base --is-ancestor "${APPLY_HEAD_SHA}" HEAD 2>/dev/null; then
  failed="${failed} ancestor(${APPLY_HEAD_SHA} is not an ancestor of this checkout's HEAD)"
```

`--is-ancestor` exits 0 (ancestor), 1 (not an ancestor) and **128** (bad object / not a commit).
The `case` above only checks that `APPLY_HEAD_SHA` is hex-shaped, never that the object exists. So a
sha that was force-pushed away, or that the `gh` query returned from a different ref, produces rc 128,
and the operator is told a *false statement about PROD's apply* — "is not an ancestor" — while git's
"Not a valid object name" is thrown into `/dev/null`.

The allowlist entry says "The exit code IS the answer and it is branched on". That holds for rc ∈ {0,1}
only. This is the identical shape IN-06 just fixed in the restore script (`-le 1` and not `-eq 0`,
because "an unreadable dump is not an empty one").

Mitigation, verified: the job checks out with `fetch-depth: 0` (`:222-225`), so the common shallow-clone
trigger is absent, and the step does fail loud either way — this is a misdiagnosis, not a silent pass.

**Recommendation.** The IN-06 shape:

```
rc=0
git merge-base --is-ancestor "${APPLY_HEAD_SHA}" HEAD 2>"${RUNNER_TEMP}/ancestry.err" || rc=$?
case "$rc" in
  0) ;;
  1) failed="${failed} ancestor(${APPLY_HEAD_SHA} is not an ancestor of this checkout's HEAD)" ;;
  *) failed="${failed} ancestor(MEASURE_FAIL: git exited ${rc} — the ancestry question was not answered: $(cat "${RUNNER_TEMP}/ancestry.err"))" ;;
esac
```

## F5 — MEDIUM — VAC-08's three count reads still use `|| true`, the exact shape IN-06 loudened elsewhere

**Location** `scripts/test-ledger-drift-check.sh:520` (`exempt_count`, added by this phase's WR-02 path),

**Status** CONFIRMED by reading.

Likelihood is low, and I want that on the record: all three files are created by the script itself a few
lines earlier (`: > "$exempt_file"`, `mv "$kept_file" "$new_file"`), so an unreadable one implies a
mid-run disk/permission fault. But the sibling script's IN-06 comment says of its own two sites "the two
now fail the same way", and these three are the same measurement in the twin gate, left on the old shape.

**Recommendation.** Same wrap, same bound, three sites:

`[ "$rc" -le 1 ] || fail "MEASURE_FAIL: could not count $new_file (grep exited $rc)."`

## F6 — MEDIUM (diagnosability) — every `MEASURE_FAIL` sentence the new self-test arms print is discarded by `run_arm`

**Location** `scripts/test-ledger-drift-check.sh` — `run_arm`'s `( "$@" ) >/dev/null 2>&1 || rc=$?`;
consumers `arm_frontier_ceiling_exceeded` (four distinct MEASURE_FAIL messages) and
`arm_harness_calibration` (two, plus its two `calibration, flip …` lines).
**Status** CONFIRMED by reading.

The exit-code contract is correct and I verified it: `arm_frontier_ceiling_exceeded` is declared
`want 1`, returns 1 only on the fully satisfied path, and `return 0` on every MEASURE_FAIL — which is
`!= want`, so `run_arm` reports `FAIL`. There is no false green here.

What is lost is the *reason*. The arm has four distinguishable causes — wrong exit code, no
`FRONTIER_EXEMPT_CEILING exceeded` string, a missing `::error::  exempt (above tip): <name>` for any of
four names — and the operator gets `FAIL frontier-ceiling-exceeded RED` and nothing else. The messages
were written to be read and cannot be.

This is the sibling script's existing `run_arm` convention, so it is pre-existing, not introduced here.
Flagged because the two new arms lean on printed diagnosis far more than the older ones do.

**Recommendation.** Capture rather than discard, and print on failure only:
`out=$( ( "$@" ) 2>&1 ); rc=$?` … and in the FAIL branch, `printf '%s\n' "$out" | sed 's/^/      /'`.

# Cleared suspicions — constructs that look like silent failures and are not

Each of these was read in full.

1. **IN-06's wrap is not re-enterable as a silent path.** I enumerated every read of `BASELINE_FILE`
   (`scripts/restore-test-from-baseline.sh:536, 539, 556, 874, 959, 961, 973, 1010, 1186`). Five are
   already rc-bounded with `MEASURE_FAIL` (`959/961/973/975/1010`), `536` is a `[ -f ]` refusal, `539`
   runs under `set -e` + `pipefail` behind that refusal, `556` discards stderr but refuses on any
   non-numeric result, and `874`'s `awk` sits inside `if !` so an unreadable file fails loud. No second
   unguarded read exists. The `-le 1` bound is the right one: `grep -v` exits 1 on "every line matched",
   which is legitimate, and an all-filtered-away dump is separately caught by the
   `EXP_TABLES -ge 1` refusal at `:978`.
2. **The restore workflow's dry-run pair is guarded.** `test-restore-from-baseline.yml:1333-1341` — the
   negative `grep -aq 'Would push these migrations:'` is backed by a positive
   `! grep -aq 'Remote database is up to date.'`, so an unreadable or empty `${out}` reds on the second
   check. This is the shape F1 asks C-0331 to adopt.
3. **The staging step fails closed, and it is proven by execution.** `trap 'rc=$?; rm -rf "${stage}"; …; exit 1' ERR`
   plus `if-no-files-found: error` on the upload; the `if [ -f ]` guards admit an aborted run's missing
   files without admitting a failed `cp`. `test-restore-workflow-wiring.test.ts` runs the extracted step
   with `cp` forced to `false` and asserts exit 1 with an empty/absent staging directory, and separately
   pins `REDACT < STAGE < UPLOAD` with three swap calibrations.
4. **`runStage`'s bare `catch { stageExists = false }`** (`test-restore-workflow-wiring.test.ts`, inside
   `runStage`) swallows any `readdirSync` error, including EACCES. It cannot produce a green: the
   positive test asserts an *exact* staged array, and the fail-closed test asserts
   `stageExists && staged.length > 0` is false, which a masked error only makes more true. Cleared.
5. **The IN-06 vitest arm is genuinely calibrated.** It asserts the `main "$@"` strip applied, asserts
   the sourced copy ends on a closing brace, asserts the `WRAPPED` needle occurs exactly once, asserts
   the neuter changed the text, and then asserts *both* directions (wrapped → exit 1 + named
   `MEASURE_FAIL`; bare → exit 2 + no message). The read failure is injected via a `grep()` shell
   function returning 2 only for `-*v*`, so it binds to the filter site and not to the count site — which
   the comment measured and explains. This is the opposite of the two failure modes named in the brief.
6. **IN-03 and IN-04 both convert a silent degradation into a loud one.** `suffix()` threw where
   `slice(indexOf(...))` used to degrade to `slice(-1)` (a byte-identity pin over a whole mutex protocol
   comparing one trailing newline); `applyJobBlock` bounds an unbounded slice-to-EOF. Both ship an
   executed calibration (`suffix("no anchor here")` throws; a fake `zz_after_apply` job is appended and
   the bounded slice is asserted not to contain it while the unbounded one does).
7. **The two new ratchets' second layers are sound.** `EXPECTED_ARMS` is checked *before* the pass check
   ("a run that lost an arm must not be able to print a success narrative at all"), the success line's
   denominator is the constant rather than `$total`, and `drift-check-scripts.test.ts` pins single/live/
   dated/compared with four applied mutations each. `FRONTIER_EXEMPT_CEILING` is read from the script by
   the tests (falling back to `0`, which every arm then refuses with a named message), so the driven arms
   cannot go vacuous if the ratchet is lowered.
8. **The `arm_harness_calibration` inversion is correctly scoped.** Both halves run `run_arm` inside a
   command substitution with `total`/`pass`/`results` re-initialised, so neither can leak into the real
   tally, and `ARM_FORCE_INVERT` is read as `${ARM_FORCE_INVERT:-0}` and set only in those subshells.
   `arm_calib_leg` reuses the gate's own `missing-ledger-row RED` mode, so its exit 1 is a measured
   property rather than an invented failure.
9. **The restore script's T-164.8-21 header does NOT misstate the STDOUT half.** The header claims the
   artifact half is closed and the stdout half is not; `run_restore` still does
   `cat "$RESTORE_OUT_DIR/pre-census.txt"` at `scripts/restore-test-from-baseline.sh:1549`, DDL column
   included. The header is accurate. Nothing to report there, per the brief's exclusion.
10. **The five allowlisted `2>/dev/null` sites, read individually.** Sites 2-4
    (`test-restore-from-baseline.yml:605/607/609`) each pair the suppression with an `|| echo '(…absent)'`
    inside a step documented as non-fatal, so the absence is printed either way — discarding stderr there
    cannot hide a failure. Site 5 (`:1227`) captures rc through a `pipefail` pipeline and the very next
    branch turns non-zero into `::error::` + `exit 1`; suppressing psql's connect stderr there is a
    deliberate redaction on a public log and the failure stays loud. Site 1 is F4 above — the only one
    whose justification does not hold for the full range of exit codes.
