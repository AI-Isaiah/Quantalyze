### 2. The five sites, named, with why each exit status is CHECKED rather than swallowed

Printed by the same script (`[file line ~N]` is a dated reading, not an anchor):

```
  [file line ~413]   if ! git merge-base --is-ancestor "${APPLY_HEAD_SHA}" HEAD 2>/dev/null; then
  [file line ~605]   echo "pg_config bindir: $(pg_config --bindir 2>/dev/null || echo '(pg_config absent)')"

  [file line ~609]   ls -l /usr/lib/postgresql/*/bin/initdb /usr/lib/postgresql/*/bin/pg_ctl 2>/dev/null \
  [file line ~1227]     -c "SELECT count(*) FROM supabase_migrations.schema_migrations;" 2>/dev/null | tr -d '\r' | tail -1)" || rc=$?
```

1. **`Assert PROD's apply ran on an ancestor of this checkout`** — the exit code IS the answer and it is branched on by `if !`; a non-ancestor appends to `failed` and the step exits 1. git's stderr here would only restate "not a valid object" for a sha the `case` above has already accepted as hex.
2-4. **`Probe - the runner image's PostgreSQL server binaries resolve`** — the whole step is a diagnostic echo, non-fatal *by design* (its own comment: pg-lane's four-step resolution chain owns the judgement, and a second divergent opinion about which layout is acceptable would be worse than none). Each swallowed channel is paired with an `|| echo '(absent)'` that prints the absence, so the log says what was not found either way.
5. **The backup step's ledger row count** — its rc IS captured (`… 2>/dev/null | … )" || rc=$?`) and the very next branch turns a non-zero into `::error::` + `exit 1`. psql's connect/auth stderr names the host, its IP and the DB user, and this job's log is PUBLIC — so here the suppression is a *redaction* and the failure is still loud.

The same justification block, dated `RE-MEASURED 2026-09-09`, sits above `ALLOWED` in the source.
