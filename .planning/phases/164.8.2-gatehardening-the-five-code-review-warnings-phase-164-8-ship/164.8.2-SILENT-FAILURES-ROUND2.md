## F-R2-01 — BLOCKER (data-integrity / information disclosure) — CONFIRMED

**The backup step's secret scan aborts on the FIRST hit, and the `if: always()` staging step
then publishes the file the scan never reached.**

**Location**
- `.github/workflows/test-restore-from-baseline.yml` — step `Back up TEST before any write
  (schema + ledger; NOT data)`, function `scan_for_secrets()` and its two call sites
  (`scan_for_secrets "${outdir}/ledger.csv" …` then `scan_for_secrets
  "${outdir}/schema-before.sql" …`).
- `.github/workflows/test-restore-from-baseline.yml` — step `Stage the public artifact
  (enumerated allowlist; default-out)` (`if: always()`), its `for f in ledger.csv
  schema-before.sql README.txt census.sql survivors.sql restore.sql refdata.sql` loop.
- `.github/workflows/test-restore-from-baseline.yml` — step `Upload the pre-restore backup`
  (`if: always()`, `retention-days: 90`, public repo).

**What is wrong.** `scan_for_secrets` ends its hit path with `rm -f "${f}"` followed by
`exit 1`. `exit` in a `run:` block ends the STEP, so the *second* call never runs. Sequence
on a hit in the first file:

1. `scan_for_secrets ledger.csv` matches → `rm -f ledger.csv` → `exit 1`.
2. `schema-before.sql` is on disk, **scanned by nothing**.
3. The backup step is red, so the restore script never runs — but `Redact…`, `Stage the
   public artifact` and `Upload…` are each `if: always()` and all three run.
4. The staging loop's `if [ -f "${outdir}/schema-before.sql" ]` is TRUE, so it is `cp`'d into
   `${RUNNER_TEMP}/test-backup-artifact` and uploaded for 90 days on a PUBLIC repo.

**Why this is not theoretical.** `schema-before.sql` is an unreviewed `supabase db dump` of a
live hosted database; the step's own comment says so. The precondition is "a credential shape
exists in database-derived material", which is exactly the condition under which the *other*
database-derived file most deserves to be read. The two files fail together far more often
than either fails alone.

**The control contradicts its own published claim.** The `README.txt` this same step writes
into the artifact says:

> Six of the files here were scanned for the same six classes **before this run was allowed
> to proceed to any write** … A hit **WITHHOLDS the file (rm -f)** and fails the run before
> any write, so the offending file does not reach this artifact.

On the path above, `schema-before.sql` was scanned zero times and reaches the artifact, while
the artifact's own README tells the reader it was cleared.

**And the twin does it correctly.** `scripts/restore-test-from-baseline.sh`'s
`refuse_credential_in_published_sql()` — written in FIX-D, for the same threat — accumulates
into `hits` across all four files and calls `fail` ONCE at the end, and then adds
`[ "$scanned" -eq "${#staged[@]}" ] || fail "MEASURE_FAIL: scanned ${scanned} of
${#staged[@]} …"`. The workflow twin has **neither** the accumulate-then-fail shape **nor** a
`scanned == 2` floor. This is the same "the negative check passed over a file it never
opened" argument FIX-D wrote out for the script, not applied to the workflow.

**Hidden failures this masks.** (a) a credential in `schema-before.sql` on any run where
`ledger.csv` also has one; (b) `schema-before.sql` being absent/empty entirely (its scan never
runs, so its absence is never a `MEASURE_FAIL`); (c) an operator reading the artifact's README
and treating an unscanned file as cleared.

**Recommendation.** Make the workflow scan the accumulating shape its own script twin already
uses:

```sh
hits=""; scanned=0
scan_for_secrets() {          # RECORD, never exit
  f="$1"; re="$2"; classes="$3"; rc=0
  [ -f "${f}" ] || return 0
  scanned=$(( scanned + 1 ))
  n="$(grep -acE "${re}" "${f}")" || rc=$?
  if [ "${rc}" -gt 1 ]; then rm -f "${f}"; hits="${hits}${hits:+, }$(basename "${f}") (UNREADABLE)"; return 0; fi
  if [ "${n}" != "0" ]; then rm -f "${f}"; hits="${hits}${hits:+, }$(basename "${f}") (${classes})"; return 0; fi
  echo "secret scan: $(basename "${f}") clean — 0 lines matched (${classes})."
}
scan_for_secrets "${outdir}/ledger.csv"        "${ledger_re}" "…"
scan_for_secrets "${outdir}/schema-before.sql" "${schema_re}" "…"
[ "${scanned}" -eq 2 ] || { echo "::error::MEASURE_FAIL: the secret scan read ${scanned} of 2 published files. A file this scan could not find is a file that ships UNSCANNED."; exit 1; }
[ -z "${hits}" ]      || { echo "::error::the secret scan matched in ${hits}. Every matching file has been WITHHELD (rm -f) and this run stops before any write. The match is not printed: this log is public."; exit 1; }
```

Every offender is removed before the `if: always()` staging step can see it, and the scan can
no longer report a verdict over a file it never opened.

## F-R2-02 — MEDIUM (fix-or-drop) — CONFIRMED

**The PROD-refusal grep in `Which database am I on` is fail-OPEN, and neither of that step's
two greps carries `-a` or is covered by the `-a` enforcement arm.**

**Location** — `.github/workflows/test-restore-from-baseline.yml`, step
`Which database am I on`, the two marker predicates:

```sh
if ! printf '%s' "${marker}" | grep -Eiq '(^|[^[:alnum:]_])test([^[:alnum:]_]|$)'; then  # refuse
if   printf '%s' "${marker}" | grep -Eiq 'prod'; then                                     # refuse
```

**What is wrong.**

1. **Direction.** The first predicate is fail-CLOSED only by accident of the leading `!`: any
   non-zero grep status (including ≥ 2, "could not read") refuses. The second is fail-OPEN —
   a grep that errors is indistinguishable, in the branch taken, from a marker that does not
   name prod, and the step goes on to print `which_database: OK — the marker names TEST and
   not PROD.` Every other measurement in this phase was given a `-le 1` bound for exactly this
   reason (`scripts/test-ledger-drift-check.sh` × 6, `refuse_credential_in_published_sql`,
   both C-0331 floors). This step did not get one.
2. **`-a`.** Both greps omit it. The same file's post-verify step calls `-a` "mandatory
   repo-wide", and `src/__tests__/test-restore-workflow-wiring.test.ts` enforces it — but the
   enforcement arm is scoped to **the post-verify step's greps only** (`bare` is computed from
   that step). The marker step is outside it. So is `grep -q 'MUTEX-ACQUIRED' "${log}"
   2>/dev/null` in the acquire step, which sits inside the region `scannableRestoreBlock()`
   deliberately slices out — nothing scans it either.

**Why it matters here specifically.** WR-06's own comment in
`src/__tests__/test-restore-workflow-wiring.test.ts` names this step as *"the worst of the
nine: `Which database am I on` is the gate standing between a dashboard-shaped mistake and a
DROP SCHEMA on the wrong database, and a run it cannot be undone."* The phase widened the
token scan to protect that step and left the step's own two predicates unbounded and
flavour-dependent.

**Inputs that make it fire.** A `grep` on the runner exiting ≥ 2 (a transient resource
failure, a future image where the alternation is rejected by the ERE engine, or a `grep`
binary substituted on PATH). Not observed; the point is the direction, which the rest of this
phase fixed everywhere else.

**Recommendation.** Bound both, and add `-a`:

```sh
rc=0; printf '%s' "${marker}" | grep -aEiq '(^|[^[:alnum:]_])test([^[:alnum:]_]|$)' || rc=$?
[ "${rc}" -le 1 ] || { echo "::error::MEASURE_FAIL: the TEST-marker predicate could not be evaluated (grep exited ${rc}). An unevaluated identity check is not a passed one."; exit 1; }
[ "${rc}" -eq 0 ] || { echo "::error::the database identity marker does not name TEST as a whole word. Refusing. The marker text is withheld: this log is public."; exit 1; }
rc=0; printf '%s' "${marker}" | grep -aEiq 'prod' || rc=$?
[ "${rc}" -le 1 ] || { echo "::error::MEASURE_FAIL: the PROD-refusal predicate could not be evaluated (grep exited ${rc})."; exit 1; }
[ "${rc}" -ne 0 ] || { echo "::error::the database identity marker names PRODUCTION. Refusing, loudly."; exit 1; }
```

And widen the `-a` enforcement arm from "the post-verify step" to "every live `grep` in the
scannable restore block", with the excluded mutex region covered by the byte-identity pin it
already has.

## F-R2-04 — LOW (fix-or-drop) — CONFIRMED

**The advisory `extra` ledger query fails completely silently, while the grep one line below
it was deliberately made to narrate.**

**Location** — `scripts/test-ledger-drift-check.sh`:

```sh
if run_ledger_query extra "$names_csv" > "$extra_file" 2>/dev/null; then
  …
  if [ "$extra_rc" -gt 1 ]; then
    echo "::warning::… could not count the advisory extra-ledger rows (grep exited ${extra_rc}). … it reported nothing because it could not read, not because there was nothing."
  fi
  …
fi
```

**What is wrong.** The `if` swallows the psql status AND the `2>/dev/null` swallows the
channel, so a failed `extra` query produces **no output at all** — not even the warning the
block's own sentence promises for the strictly narrower grep case. The two layers disagree:
the inner one insists an unreadable result must not read as "nothing to report", the outer one
makes an unreadable query indistinguishable from a clean one by producing zero lines.

**Impact.** Advisory direction only; no verdict changes and `bad` is untouched. The cost is
that the "advisory: N ledger row(s) have no repo file" line silently stops appearing, and a
reader diffing two runs' logs cannot tell a clean advisory from a dead one.

**Recommendation.**

```sh
extra_q_rc=0
run_ledger_query extra "$names_csv" > "$extra_file" 2>"${tmp}/extra.err" || extra_q_rc=$?
if [ "$extra_q_rc" -ne 0 ]; then
  echo "::warning::${GATE}: the ADVISORY extra-ledger query exited ${extra_q_rc} (stderr WITHHELD — it can carry a DSN, host or username). This direction is advisory, so the run continues — but this run printed no advisory line because it could not read, not because there was nothing."
else
  … existing body …
fi
```

## F-R2-05 — LOW (fix-or-drop) — CONFIRMED

**The one remaining unbounded `grep` in `check()` is the one that sets the frontier tip, and
its error direction widens the exemption window.**

**Location** — `scripts/test-ledger-drift-check.sh`, the frontier-tip loop:

```sh
for nm in "${repo_names[@]}"; do
  # Present == not on the measured-missing list.
  if grep -aqFx -e "$nm" "$missing_file"; then continue; fi
  ts="${nm%%_*}"
  …
done
```

**What is wrong.** F5 bounded **five** sibling `grep` reads in this same function on the
argument that rc 1 ("no match") and rc ≥ 2 ("could not read") must not collapse. This site
still collapses them: `if grep …` treats BOTH as false, so an unreadable `$missing_file`
reads as *"this migration is PRESENT"*. The consequences run the wrong way:

- a name wrongly treated as present can RAISE `frontier_tip`;
- a higher tip EXEMPTS more measured-missing migrations from NEW drift;
- a larger exempt set is capped by `FRONTIER_EXEMPT_CEILING`, but the widening itself is what
  removes findings — and every name that stops being NEW drift stops reddening the gate.

So the direction is toward `0 NEW drift` and the clean summary, which is precisely why F5
called the sibling sites "a gate reporting a pass it did not earn".

**Likelihood.** LOW — `$missing_file` was successfully counted by `grep -ac` a few dozen lines
earlier, so an rc ≥ 2 here requires the file to become unreadable mid-run. Reported because
the direction is wrong and the remedy is a five-line copy of an idiom already in the same
function.

**Recommendation.**

```sh
set +e; grep -aqFx -e "$nm" "$missing_file"; grep_rc=$?; set -e
[ "$grep_rc" -le 1 ] || fail "MEASURE_FAIL: could not test whether '${nm}' is on the measured-missing list (grep exited ${grep_rc} on ${missing_file}). An unreadable list is not a list this migration is absent from, and reading it as PRESENT RAISES the frontier tip and widens the exemption."
if [ "$grep_rc" -eq 0 ]; then continue; fi
```

## F-R2-07 — INFO — CONFIRMED

**The staging step's `REDACT_OUTCOME` wiring-fault guard is unreachable when the backup
directory is missing.**

**Location** — `.github/workflows/test-restore-from-baseline.yml`, step `Stage the public
artifact (enumerated allowlist; default-out)`.

`wiring_fault` is initialised to 0 before the `if [ ! -d "${outdir}" ]` branch, and every path
that can set it to 1 lives in the `else`. A run that dies before the backup step therefore
takes the README-only branch, never evaluates `REDACT_OUTCOME`, and exits 0. So on that path
`id: redact` can be gone, reordered or dropped from the `env:` block and the MEASURE_FAIL the
step's comment promises ("an empty (or unrecognised) outcome is a MEASURE_FAIL that EXITS 1")
does not fire.

Costs nothing on that path — there are no channels to stage — but the guard's comment states
the rule unconditionally, and a wiring regression introduced during a run that also failed
early would not be named. One-line fix: evaluate the `REDACT_OUTCOME` `case` before the
`if [ ! -d "${outdir}" ]` split, or repeat the empty/unrecognised check in the missing-dir
branch.
