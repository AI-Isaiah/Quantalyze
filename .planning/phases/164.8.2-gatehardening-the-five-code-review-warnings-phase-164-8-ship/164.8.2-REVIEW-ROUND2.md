#### WR2-01: The F1 sentinel guard has a reachable hole, and the variable that would catch it is measured and never branched on — REPRODUCED BY EXECUTION

**File:** `.github/workflows/test-restore-from-baseline.yml:449-458`
**Introduced by:** FIX-A (`git blame` → `eeb8e731`, 2026-09-10 — the fix round,
not the original plan work)
**Confidence: CONFIRMED by running the shipped shell.**

The step captures `sentinel_rc` and then never tests it:

```bash
sentinel_rc=0
printf 'ANCESTRY-PROBE-SENTINEL\n' > "${ancestry_err}" || sentinel_rc=$?
ancestry_rc=0
git merge-base --is-ancestor "${APPLY_HEAD_SHA}" HEAD 2>"${ancestry_err}" || ancestry_rc=$?
if [ ! -f "${ancestry_err}" ] || [ ! -r "${ancestry_err}" ] || grep -q 'ANCESTRY-PROBE-SENTINEL' "${ancestry_err}"; then
```

`sentinel_rc` appears **only inside the message of the branch that already fired**.
If the sentinel WRITE itself fails, the sentinel is never in the file, the guard
cannot see it, and the step falls through to the `ancestry_rc -eq 1` arm — which is
git's "not an ancestor" code AND bash's "could not open the redirection" code.

I ran the shipped logic against a pre-existing read-only `ancestry.err` holding
unrelated text:

```
sentinel_rc=1 ancestry_rc=1
VERDICT: ancestor(deadbeef… is not an ancestor of this checkout HEAD)
```

That is verbatim **the FALSE STATEMENT ABOUT PROD'S APPLY** that the comment three
lines above it says F4 exists to delete and that F1 says it re-closed — "the precise
FALSE STATEMENT F4 exists to delete, reintroduced through F4's own new file".
It is reintroduced again, through F1's own new probe.

The existing `chmod 0444` arm (`test-restore-workflow-wiring.test.ts:3529-3573`)
does **not** cover this: it injects `chmod` AFTER the sentinel write succeeds, so
the sentinel is present and the clause fires. The unwritable-BEFORE-the-write
ordering has no arm.

Reachability is low on a fresh GitHub-hosted runner (`${RUNNER_TEMP}/ancestry.err`
does not pre-exist) but is exactly the "a path this shell was not made to think of"
class the step claims to have closed, and the detector is already computed.

**Fix:** act on the measurement, and add the arm in the missing ordering.

```bash
sentinel_rc=0
printf 'ANCESTRY-PROBE-SENTINEL\n' > "${ancestry_err}" || sentinel_rc=$?
if [ "${sentinel_rc}" -ne 0 ]; then
  failed="${failed} ancestor(MEASURE_FAIL: the pre-probe sentinel write to ${ancestry_err} exited ${sentinel_rc} (RUNNER_TEMP='${RUNNER_TEMP}'), so the stderr channel was NOT armed and git's own redirection would fail the same way. rc below is bash's, not --is-ancestor's — this is not a 'no'.)"
else
  ancestry_rc=0
  git merge-base --is-ancestor "${APPLY_HEAD_SHA}" HEAD 2>"${ancestry_err}" || ancestry_rc=$?
  ...
fi
```

Then add the twin of the `chmod 0444` arm with the `chmod` injected **before** the
sentinel write, asserting the output does NOT contain `FALSE_VERDICT`.

#### WR2-02: WR-05's job-bound fix is a HALF-CLASS FIX — the pre-fix `NEXT_JOB_RE` survives verbatim in both sibling files, and over-reaches into a neighbouring job

**Files:**
- `src/__tests__/supabase-migrate-test-first.test.ts:107-114` (`jobBlock`)
- `src/__tests__/test-restore-workflow-wiring.test.ts:120-127` (`jobBlock`)
- Fixed copy for comparison: `src/__tests__/critical-regressions.test.ts:1099-1152`

**Confidence: CONFIRMED by execution.**

FIX-B commit `f79c2757` closed WR-05 by widening `NEXT_JOB_RE` and adding a throw —
in `critical-regressions.test.ts` only. Both siblings still carry the EXACT pre-fix
expression:

```ts
const next = after.match(/\n {2}[A-Za-z_][\w-]*:\n/);
return head + (next ? after.slice(0, next.index) : after);
```

Measured against the shipped `supabase-migrate.yml`: give the successor job key a
trailing comment (valid YAML) and `jobBlock(WF, "apply-test")` grows from
**44 341 → 48 718 bytes**, swallowing the whole `apply-test-verdict` job. On the
last recognised key it degrades all the way to EOF. No throw, no message — the
failure mode is a PASS, which is the whole reason IN-04 was raised and WR-05
re-opened it.

This matters more here than in the fixed file, because `jobBlock` is the workhorse
of `supabase-migrate-test-first.test.ts`: `liveLineCount(jobBlock(WF, VERDICT_JOB), wiring) === 1`
(`:1083`, `:1096`, `:1107`, `:1118`) and the `environment:`/`needs:`/`if:` pins
would then be satisfiable by a NEIGHBOURING job's text. That is the IN-04 shape, in
the file that gates the PROD apply.

This also contradicts the phase's own written standard. `test-restore-workflow-wiring.test.ts:93-95`
says of a different helper: *"IN-03 fixed one copy of one half, which is how this
became a half-class fix. Both halves, both files, throw now."* WR-05 got the
treatment IN-03 was criticised for.

**Fix:** lift the corrected pair into all three copies (restated per-file, matching
this repo's locked no-shared-helper convention for these structural gates):

```ts
const NEXT_JOB_RE = /\n {2}[A-Za-z_][\w-]*:[^\S\n]*(#[^\n]*)?\n/;
const ANY_JOB_KEY_RE = /\n {2}[A-Za-z_][\w-]*:/;
function jobBlock(text: string, job: string): string {
  const head = `\n  ${job}:\n`;
  const start = text.indexOf(head);
  if (start < 0) return "";
  const after = text.slice(start + head.length);
  const next = after.match(NEXT_JOB_RE);
  if (!next && ANY_JOB_KEY_RE.test(after)) {
    throw new Error(
      `${job}: a 2-space job key FOLLOWS it that NEXT_JOB_RE did not match, so this ` +
        "block would silently run to END OF FILE — the unbounded shape IN-04/WR-05 removes.",
    );
  }
  return head + (next ? after.slice(0, next.index) : after);
}
```

…and port the three-shape calibration (`"  k:"`, `"  k:  # c"`, `"  k: "`) into both
files. Note `jobBlock` also returns `""` on an absent job, which `softeningOffenders`
already guards but nothing else does — worth the same throw treatment.

#### WR2-03: `refuse_credential_in_published_sql` does not cover the abort paths that publish the same four files, and both the script's own `scanned 4 of 4` sentence and the in-artifact README claim otherwise

**Files:**
- `scripts/restore-test-from-baseline.sh:1631-1706` (the scan),
  `:1776-1780` (its call site)
- `.github/workflows/test-restore-from-baseline.yml:1788-1900` (the staging step,
  `if: always()`), `:1330-1390` (the README's claim)

**Introduced by:** FIX-D (`fff4e08d`)

The scan is called once, between `build_transaction` and `run_transaction`. The
workflow's staging step is `if: always()` and stages `census.sql`, `survivors.sql`,
`restore.sql` and `refdata.sql` by name whenever they exist. Every abort **after**
those files are written and **before** the scan therefore publishes them
**unscanned**, to a world-readable 90-day artifact on a public repo:

- `census_survivor_count` MEASURE_FAIL (`:1768`)
- `refuse_publication_row_without_table` (`:1771`)
- `derive_expected_shape` (`:1773`)
- `build_transaction`'s own refdata refusal (`:1237` — at which point
  `refdata.sql` holds whatever the extractor wrote before it failed, and
  `restore.sql` is partial)

The scan's positive floor says a short tally *"is its own MEASURE_FAIL rather than
a clean verdict over files it never opened"* — true only when the scan RUNS. The
README that ships **inside the artifact** repeats it: *"a tally short of `scanned 4
of 4` is its own MEASURE_FAIL rather than a clean verdict over files it never
opened."* On an abort path the tally is never taken at all, and the README does not
say so. That is precisely the "control weaker than the sentence next to it" this
phase exists to remove.

The wiring gate does not catch it either: `test-restore-workflow-wiring.test.ts:2114-2118`
derives `scanned` **only** from the workflow's `scan_for_secrets` calls and asserts
it equals `["ledger.csv", "schema-before.sql"]`, so it is structurally blind to
whether the script's scan ran.

**Fix (pick one, but say which in the README):**

1. Move the scan so it runs on every exit that leaves files behind — e.g. install it
   in the script's EXIT trap alongside `cleanup_out_dir`, guarded on
   `RESTORE_OUT_DIR` being populated; or
2. Have the staging step refuse to stage the four script `.sql` files unless the
   script emitted its `public .sql files carry no credential shape …` line, on the
   same default-DENY shape `REDACT_OUTCOME` already uses:

```bash
# in the staging step, beside the REDACT_OUTCOME guard
if grep -aq 'public .sql files carry no credential shape' "${outdir}/script.log"; then
  for f in census.sql survivors.sql restore.sql refdata.sql; do ...; done
else
  echo "::error::the restore script aborted before refuse_credential_in_published_sql ran — the four script .sql files are UNSCANNED and are NOT staged."
fi
```

Either way, correct the README sentence so it scopes the guarantee to runs that
reached the scan.

#### WR2-04: The new sentinel grep carries neither `-a` nor an rc bound, in the same fix round that was adding `-a` elsewhere for exactly this reason

**File:** `.github/workflows/test-restore-from-baseline.yml:453`

```bash
if [ ! -f "${ancestry_err}" ] || [ ! -r "${ancestry_err}" ] || grep -q 'ANCESTRY-PROBE-SENTINEL' "${ancestry_err}"; then
```

Two gaps, both in the **false-green** direction (the guard fails to fire and the
step falls through to the ancestry verdict):

1. **No `-a`.** Round 1's WR-04 was exactly this class, and the same fix round
   rewrote both `supabase-migrate.yml` C-0331 greps to `-aEiq` with a comment
   calling `-a` *"mandatory repo-wide (this repo tracks a file carrying a
   deliberate NUL byte)"*. This new grep reads a psql/git stderr channel — the one
   file class most likely to carry raw bytes — and did not get it.
2. **No rc bound.** `grep` exiting ≥ 2 (unreadable) is indistinguishable from
   "sentinel not found" inside an `if`. The `-r` clause covers the common case but
   not all of them, and the file's own sibling sites (`test-ledger-drift-check.sh`,
   `restore-test-from-baseline.sh:1685`) all bound with `-le 1`.

`grep -q 'MUTEX-ACQUIRED'` at `:858` and `supabase-migrate.yml:601` share the
missing `-a`, but those are pre-existing (blame `e6c76832`, 2026-09-08) and fail in
the **safe** direction — see IN-05.

**Fix:**

```bash
sentinel_rc=0
grep -aq 'ANCESTRY-PROBE-SENTINEL' "${ancestry_err}" || sentinel_rc=$?
if [ ! -f "${ancestry_err}" ] || [ ! -r "${ancestry_err}" ] || [ "${sentinel_rc}" -gt 1 ] || [ "${sentinel_rc}" -eq 0 ]; then
```

…and add the corresponding token to the wiring test's pinned line
(`test-restore-workflow-wiring.test.ts:3405`, `:4545`, `:4605`, which currently pin
the `-a`-less spelling verbatim and would otherwise red on the fix).
