<decision name="the email arm KEEPS KEY_INVALID_FORMAT">
None of the four split codes is true of "a present value is malformed": it is not missing, not
a venue property, not a length cap. `KEY_INVALID_FORMAT`'s own union comment reserves it for
"the only one of the twelve that was ever a format failure" — and a malformed email IS a
format failure. Retaining it here is the split landing CORRECTLY, not the split failing.

⚠️ The "exactly ONE emitter per route" rule in that comment is scoped to the two WIZARD connect
routes and their `api_secret.length < 8` ccxt check; `verify-strategy` is a different route with
different facts and is not bound by it. Do not force a false code to satisfy a rule written
about other routes. Record this reasoning at the arm.
</decision>

<decision name="F3 — the public arms move CODES only, and the disclosure boundary is proven unchanged">
161-UI-SPEC § Copy Spec WIZERR-08 requires that on anonymous `verify-strategy` the
sFOX-disabled gate "must NOT map to **copy** that names an unlaunched venue or reveals the
wider venue set (F3)". Read precisely, the constraint binds COPY. Three measurements settle how
to satisfy it:

1. **No public copy hop exists.** `src/components/landing/VerificationForm.tsx` (~:95-110)
   renders `human_message ?? error ?? "Verification failed"` and **never reads `code`**. On this
   route the code channel is machine-only, so re-coding an arm changes nothing an anonymous
   caller sees.
2. **The sentence is the disclosure surface** — so every sentence on this route stays
   byte-identical, and Task 2 pins that.
3. **The venue-disabled arm is already bounded by the offer.** The `UI_EXCHANGE_CODES` gate at
   `~:131` runs FIRST, so `~:144` is reachable only when the venue IS in the offered set (the
   documented `NEXT_PUBLIC_SFOX_ENABLED` / `SFOX_ENABLED` half-state). The arm cannot disclose
   a venue the landing form was not already offering.

Therefore `~:144` takes `KEY_VENUE_NOT_ENABLED`, which is TRUE of the fact, rather than
`KEY_UNSUPPORTED_VENUE`, whose copy ("We do not support that exchange") would be FALSE of a
venue we do support. Choosing a false code to guard against a hypothetical future copy hop
would trade a present falsehood for a future one — the wrong trade in a phase about false
sentences.

⚠️ **Latent hazard, recorded so a future consumer must re-decide rather than inherit:**
`KEY_VENUE_NOT_ENABLED`'s copy reads "This exchange is not open on Quantalyze yet." If any
anonymous surface ever starts mapping this route's codes to wizard copy, that copy WOULD leak a
coming-soon signal and F3 must be re-decided at that moment. Task 2 writes this into the route
as a comment at the arm and into the SUMMARY.
</decision>

<decision name="the 4th ROUTES row carries a roster (Open Question 1)">
`validate-and-encrypt` has four client consumers and no `KNOWN_*` roster today. Options were a
new shared roster constant or a roster-less union-membership row. **Decision: a shared roster
constant.** A roster-less row weakens the law's "a client can render it" half — and that half
is the entire reason this row exists: `STALE_CLIENT` shipped unregistered at a consumer, which
is the regrowth vector the row closes. A row that cannot catch that would be decoration.

Place the constant in a shared module rather than in any one of the four consumers, since four
consumers share it; state the chosen location and why in the SUMMARY.
</decision>
