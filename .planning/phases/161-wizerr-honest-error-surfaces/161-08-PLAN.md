<decision name="widen-the-forward, do not mint five members">
The recovered ledger left this open: widen the forward arm (one edit per route, closes all
five) versus minting per-code wizard members (five copy decisions). **Decision: widen.**
Rationale, each half measured:

1. **It is symmetrical with behaviour already accepted on these exact routes.** All five
   already answer `code: err.seamCode ?? "UNKNOWN"` on 4xx. The wire-code channel already
   carries server-chosen strings out of these handlers; the 5xx arm is the anomaly, not the
   4xx one.
2. **Pitfall 4 does not bite here.** The identity-admission trap is `code as WizardErrorCode`
   at a CONSUMER. This edit writes a wire token into a response body; nothing is cast into the
   copy union. Client recognition still runs through the explicit `SEAM_CODE_TO_WIZARD_CODE`
   table, and an unrecognized code still renders UNKNOWN copy. Nothing enters the copy
   vocabulary silently — Task 3 pins that.
3. **Collapsing is irrecoverable; forwarding is not.** A code discarded at the route cannot be
   recovered downstream. Forwarding preserves the discriminator and leaves the copy decision
   where it belongs.
4. **It closes the CLASS, not five instances** — the founder's standing rule. Minting five
   members would fix the five codes measured in Aug 2026 and leave the SHAPE intact for the
   next code.

Consequence accepted and recorded: response bodies on 5xx may now carry codes that have no
wizard copy entry. That is correct and is exactly what `UNKNOWN` copy is for; it is a
*rendering* fallback, which is legitimate, as distinct from a *classification* fallback, which
is the defect this phase closes.
</decision>
