<decision name="the routes grow code-first literals; the dialogs read the code">
UI-SPEC leaves this open per dialog. **Decision: all three routes emit a machine code alongside
their existing sentence, and the dialogs discriminate on it.** Three grounds, each measured:

1. **The law cannot see prose.** The coverage law's scanner derives its population from
   code-first literals. A dialog keyed on `body.error` is invisible to it, so "the coverage law
   reaches the dashboard dialogs" is unachievable without codes.
2. **The repo already ruled against prose-sniffing.** `validate-and-encrypt`'s SEAMUX-03
   comment states the intent verbatim: a machine code on every error arm "so a client
   discriminates the fault on a stable token instead of sniffing prose."
   `ROUTE_FIELD_ERRORS[body.error]` is that anti-pattern with a lookup table around it, and it
   silently breaks the moment a sentence is reworded.
3. **It is additive and therefore safe.** Adding a `code` key changes no existing sentence, so
   every other consumer of these three routes is unaffected — pinned per arm in Tasks 1-2.

Retire `ROUTE_FIELD_ERRORS` rather than keeping it beside the code path: two discriminators for
one decision is the divergence class this repo has already paid for twice.
</decision>

## ⚠ E5 — the phase's ONE unresolved UI consideration, and a MEASURED correction to its premise

161-UI-SPEC § UI Considerations carries exactly one ⚠ unresolved row, and it belongs to this
requirement: *"The three dialogs mount the envelope in a fixed-height body. A multi-bullet
`fix[]` list may overflow… The planner must make this an explicit check — if it clips instead of
scrolling, WIZERR-07's honest copy would be honest but unreadable, which is the same defect
wearing a different hat."*

**Measured at plan time: the premise is wrong.** `src/components/ui/Modal.tsx` renders a native
`<dialog>` (`~:26`) whose body is `<div className="bg-surface rounded-xl border border-border
shadow-elevated w-full max-w-lg p-6">` (`~:28`). There is **no `max-h-*`, no `overflow-*`, and no
fixed height** anywhere on that body. The dialogs do NOT mount the envelope in a fixed-height
container.

That does not dismiss the row — it re-aims it. The residual risk is the opposite shape: an
UNBOUNDED body relies on the user-agent stylesheet's `dialog` max-height for viewport
containment, and whether the overflowing content SCROLLS or CLIPS is a UA-resolved rendered
property. jsdom does not do layout, so it cannot answer this (161-VALIDATION.md already lists it
Manual-Only).

**Named assumption (carried, not resolved):** a tall envelope in these dialogs scrolls within
the viewport rather than clipping. **Split of the check** — the automatable half is automated in
Task 3, the genuinely-visual residue is the manual check below, and the two must not be confused
for each other.
