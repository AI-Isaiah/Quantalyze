## Summary

The phase needs three things the code does not have yet:

1. **A way to bring a terminated terminal back.**
2. **A rule that the service never brings one back credential-free.** Every relaunch the service performs goes straight to a credentialed house `initialize`.
3. **A committed remote-source verb** that deletes the saved-account database and the per-account deal caches while no terminal runs.

Everything else the scrub needs already ships: the one lease registry, the abandoned-thread epoch fence, the heal's crossing budget, the ipc-fault debounce and cap, the `probe_thread_done` gate that answers W-1, and the bridge-side `session_snapshot`.

**The restart path is NOT closed by the spike, and the planner must not treat it as closed.** CONTEXT's spike concluded "`initialize()` over the rpyc bridge does not launch a dead terminal". Three things contradict that, and the spike's own evidence for it is weakened.

The contradicting evidence:
- **The vendor documentation.** "If required, the MetaTrader 5 terminal is launched to establish connection when executing the initialize() call." `[CITED: mql5.com/en/docs/python_metatrader5/mt5initialize_py]`
- **The 164.6.5 live spike.** Twice, a killed terminal was relaunched as `terminal64.exe /portable` (ppid 1) by the bridge's next `initialize()` (`deploy/mt5-gateway/railway-gateway.md`, D-05 record).
- **A read taken this session on the production job gateway.** The running terminal is `C:\Program Files\MetaTrader 5\terminal64.exe /portable` with ppid 1 and 14 702 s elapsed at 14:55:27 UTC. That puts its start at 10:50:25, 13 s after the 164.6.5 recycle at 10:50:12, the one that terminated the old process (`164.6.5-VERIFICATION.md`). `start.sh` passes no `/portable`: it launches `$wine_executable "$mt5file" $MT5_CMD_OPTIONS &`, and `MT5_CMD_OPTIONS` is unset on both gateways (read this session). So the process that later showed the L7 Login dialog was launched by that recycle's bare `initialize()`. `[VERIFIED: railway ssh read of ps and /Metatrader/start.sh, 2026-10-04]`

Why the spike's own evidence is weaker than it reads:
- S-03(a) ran in run 1, where CONTEXT itself voids every process reading ("It printed 0 for 320 s while the full process list showed the terminal running").
- `accounts.dat` had just been deleted, so a launched terminal had no account to start with. A bare `initialize()` against an account-less terminal is exactly what S-03(b) measured hanging.
- The 30 s failure of `initialize(path=…, portable=True)` probably came from the vendor default timeout (60 s, per the same docs page) outrunning the 30 s rpyc bound. That is the D-24 inversion `Mt5Client.__init__` guards against, not proof that a launch is impossible.

**Primary recommendation:**
1. Terminate with the existing Toolhelp/`TerminateProcess` mechanism.
2. Delete `Config\accounts.dat`, plus the scrub targets.
3. Relaunch AND log in with ONE credentialed `initialize(login=, password=, server=, timeout=<below the rpyc bound>)`, which the vendor documents as launching the terminal.
4. Verify with `session_snapshot`.

All four steps run inside the one lease. Before any plan deletes a byte, Wave 0 measures this exact sequence on the validation gateway (cell **S-09**). The pre-decided fallbacks are a Wine-side launch verb (committed literal), then a Railway API restart.

Criterion 4 falls out of the same rule. A terminal launched with a stale saved house password opens a Login dialog that blocks IPC (L7). A terminal launched with NO `accounts.dat` accepted a credentialed `initialize` in 3.4 s (S-04). So the robust relaunch removes `accounts.dat` before it relaunches, rather than trusting the saved copy.

### Pattern 1: Every relaunch the service performs is credentialed, from a terminal with no `accounts.dat` (criteria 3 and 4)

**What.** Replace the recycle's credential-free relaunch (`recycle_terminal_process` step 2 → `assert_session_authorized`, then `_watch_relaunch`'s bare polls) with this sequence: terminate, delete `Config\accounts.dat`, `initialize_with_credentials(*read_env_mt5_credentials())`, `session_snapshot`. Deleting `accounts.dat` is what makes the saved house password irrelevant. A stale copy cannot pop a Login dialog if there is no copy.

**Evidence that it is the right shape.**
- L7 (`164.6.6-CONTEXT.md`): a relaunch with a stale saved house password opened a Login dialog, the probe read `-10005`, and the credential-free heal had no way past it.
- S-04: with no `accounts.dat`, a credentialed `initialize` authorized in 3.4 s.
- The validation gateway's `Config/accounts.dat` mtime is 14:46:08.877 UTC, matching S-04's credentialed call (Reading B at 14:46:19). So a credentialed API `initialize` re-creates `accounts.dat` and re-saves the house entry. `[VERIFIED: railway ssh stat, 2026-10-04]`
- Whether it saves the PASSWORD is unknown. That matters only for relaunches the service does NOT perform: a container restart or redeploy, which launch from `start.sh` with whatever `accounts.dat` holds.

**What still covers a non-service relaunch.** If a redeploy launches into a stale-password dialog, the monitor's next tick reads `-10005`, which is in `_RECYCLE_REACHABLE_IPC_CODES`, and the new credentialed recycle path heals it. Measure this as a live check; do not restart a gateway to find out.

**Why not "re-save the house password before any delete".** The ROADMAP offered "re-saving the house password from `MT5_PASSWORD` (or a credentialed relaunch) before any delete". A re-save requires a working login on a terminal that may be wedged, and it adds a crossing set. The credentialed relaunch from an `accounts.dat`-free terminal reaches the same end state with fewer moving parts. This is the "(or a credentialed relaunch)" branch.

**When to use it.** On EVERY path where this service ends a terminal process: the existing `ipc_fault` recycle, the job-terminal scrub and the validation-terminal scrub.

⚠️ **This collides with D-04 option (iii), and the founder must see it.** Deleting `accounts.dat` on every recycle IS an automated scrub of the jobs terminal's saved accounts, which (iii) rules out. Picking (iii) therefore removes the only mechanism this research found for criterion 4. The alternative, re-saving the house password before the terminate, needs a terminal that answers, and the L7 terminal did not. So D-04 is really choosing between (i)/(ii), which delete `accounts.dat` on each recycle and so fix criterion 4, and (iii), which leaves criterion 4 unmet unless a new mechanism is found. Data-history (`trades`) deletion is a separate, later choice gated on 164.6.6.3 (Pitfall 3).

### Pattern 2: The job-terminal scrub rides the existing `ipc_fault` escalation (D-04 (i)), inside the ONE heal lease

- **Ordering, inside `_heal_blocking` under `mt5_terminal_lease`:**
  1. First probe.
  2. `_capture_wedge_evidence` (before the terminate erases it). This keeps the 164.6.8 evidence. D-03 keeps the jobs terminal's `logs` anyway.
  3. An `_affordable` gate covering the scrub, the credentialed relaunch and the verify.
  4. The scrub verb.
  5. The credentialed relaunch.
  6. The verify.
- **Jobs and polls cannot interleave.** Every job read, the positions fetch and the heal take the same `asyncio.Lock` from `_MT5_TERMINAL_LOCKS` (`mt5_concurrency.py:248`). Batch callers wait unbounded, so they queue behind the heal, and nothing extra is needed.
- **Abandoned work is fenced.** `_assert_live` is the first statement of every verb, and the lease bumps the epoch on release, so a zombie thread from an earlier holder cannot scrub under a successor.
- **Budget.** `_MT5_RELOGIN_BUDGET_CEILING_S: Final[float] = 300.0` (`mt5_relogin.py:496`) is not to be raised. The moved plan 04 derived a total of 8 crossings by swapping the recycle (3) for the scrub (3) and the bare relaunch reading (2) for a credentialed one (2). Plans should DEFAULT to budget-gated credentialed polls and treat one crossing as the best case S-09 might show: in 164.6.5 run 1 about 60 s passed between the relaunching call and `authorized`. That arithmetic still holds IF S-09 shows the credentialed `initialize` launches AND authorizes within one rpyc crossing (30 s, `MT5_REQUEST_TIMEOUT_S` default "30", `mt5_client.py:262`). If S-09 measures longer, the relaunch needs budget-gated credentialed polls. Each poll reserves 2 crossings, and every poll must stay credentialed, never bare (see Pitfall 1).

### Pattern 3: The validation-terminal scrub runs AFTER the verdict, in its own lease on the validation terminal key

- **Why not in-request.** The wizard chain is `_MT5_VALIDATE_STAGE_TIMEOUT_S = MT5_VALIDATE_REQUEST_TIMEOUT_S + 5.0` (60 s), `_MT5_VALIDATE_DEADLINE_S = float(os.getenv("MT5_VALIDATE_DEADLINE_S", "75.0"))` and `_MT5_PARK_MIN_BUDGET_S = _MT5_VALIDATE_STAGE_TIMEOUT_S` (`routers/exchange.py:135,150,177`). The server worst case is already 105 s against a 120 s client ceiling. A cold relaunch (14 s by restart, unknown by `initialize`) plus 3.4 s of login plus the terminate cannot fit inside the 15 s the park floor leaves, and it cannot be added after the deadline without breaking the 120 s ceiling. The worker gets `_MT5_PROBE_TIMEOUT_S = MT5_REQUEST_TIMEOUT_S + 5.0` (35 s; `services/ingestion/mt5.py:108`).
- **Design.** The validation terminal serves only validations (D-02), so nobody waits on it except the next validation. After the response is decided, schedule a scrub that:
  1. waits, bounded, for `probe_thread_done`;
  2. acquires `mt5_terminal_lease(<validation key>)`;
  3. runs Pattern 1 with `delete_logs` per the founder's answer.
- **Use a supervised task.** Do not hang a raising task off `main.lifespan`. The repo records that a background-task raise reaches `_crash_handler` and stops dispatch (`mt5_concurrency.py` lease finally comment; `mt5_relogin.py` module docstring item 1). Wrap the scrub coroutine in a never-raises top-level `except Exception`, as `heal_mt5_terminal_session` does.
- **Scrub owed.** If the scrub cannot run (probe still in flight past the bound, lease busy, budget), record a per-terminal SCRUB OWED marker. The next validation consumes it before its probe, or the next scheduled scrub does. Alert with a named cause (reuse `report_park_skipped`'s closed-cause, never-raises shape).
- **Semantics change for the founder.** "After every validation" becomes "within seconds after every validation, before the next validation's probe". That is founder-visible; see Open Question 1.

### Anti-Patterns to Avoid
- **A bare `initialize()` anywhere between the terminate and the house login.** On an account-less terminal it hangs to the rpyc bound (S-03(b)), and the client turns that into code 0 (Pitfall 1).
- **Deleting while any `terminal64.exe` runs.** A running terminal can rewrite `accounts.dat` from memory (A4). The verb must refuse unless `exited == matched`, as the moved plan 02 specified.
- **Interpolating anything into the remote literal.** Keep the T-134-03 discipline: a plain constant with no brace, int-only arguments, an AST-pinned test (the recycle family at `tests/test_mt5_client_contract.py` ~4470-4540 is the model).
- **Deleting `Config\common.ini` or `Config\servers.dat`.** `common.ini` carries the `[Experts]` keys `Enabled`, `Account`, `Profile` and `Api` that 164.6.6 S-01 set and the founder confirmed. Losing them breaks trade-capability classification. `servers.dat` is the broker server list the credentialed login needs. (Key names read this session, values masked.)
- **Calling the Railway API from the analytics service as the routine relaunch.** It needs a new project-scoped token on the analytics service, and it restarts the container, which drops the bridge the caller is connected through and every other rpyc session. Use it as a manual fallback only.

## Common Pitfalls

### Pitfall 1: An account-less terminal goes SILENT. No heal, no recycle, no alarm.
- **What goes wrong.** After a scrub whose relaunch did not log in, the next session-monitor tick runs `_heal_blocking`'s first probe, `assert_session_authorized()`, a bare `initialize`. S-03(b) measured that call hanging to the rpyc bound on an account-less terminal. The broad arm turns the transport timeout into code 0: `except Exception as exc: … raise Mt5ClientError(0, scrub_freeform_string(str(exc))) from None` (`mt5_client.py:2196-2199`).
- **Why nothing then acts.** Code 0 is `_MT5_UNATTRIBUTED_CODE: Final[int] = 0` (`mt5_relogin.py:456`). It is a member of `_IPC_FAULT_ALARM_EXEMPT_CODES … frozenset({_MT5_NO_AUTHORIZED_ACCOUNT_CODE, _MT5_UNATTRIBUTED_CODE})` (`:468-469`). It is NOT in `_RECYCLE_REACHABLE_IPC_CODES … frozenset(_IPC_TRANSPORT_CODES) - {_MT5_IPC_BRIDGE_DETACHED_CODE}` (`:172-174`, with `_IPC_TRANSPORT_CODES: tuple[int, ...] = (-10004, -10005)`, `mt5_validation.py:93`). So the heal sends no credential (that path is only for `-6`, `:140`), does not escalate, and does not alarm. Every job then fails until a human looks. That is criterion 3's "logged out", with no signal.
- ⚠️ **Unmeasured.** The client passes `timeout=` `MT5_INITIALIZE_TIMEOUT_MS` (default "20000", `mt5_client.py:296`). The terminal may fail its own pipe at 20 s with `-10005` before rpyc gives up, which would route to the escalation instead. S-03(b)'s call most likely carried no timeout. This is Wave-0 cell **S-10**.
- **How to avoid it.**
  - (a) The invariant: **no lease is released with a terminal this service terminated and has not yet seen authorized as house.**
  - (b) A per-terminal **relaunch-debt marker** (an in-process dict keyed by `terminal_key`, beside `_MT5_TERMINAL_HOLDERS: dict[str, str] = {}` at `mt5_client.py:709`), set immediately before the terminate and cleared only by a house-verified `session_snapshot`. While it is set, the next heal tick goes straight to the credentialed relaunch whatever its first probe returned. That includes code 0 and an rpyc timeout, and skips the bare probe entirely. On the validation terminal, the next validation runs the credentialed relaunch before its probe.
  - (c) Alert at ERROR on every relaunch-failed outcome. That is in-process state only: a process restart loses it. The boot heal must then treat "first probe hung / code 0" with house credentials set as a reason to attempt a credentialed relaunch. This is a founder-visible widening of 164.6.2's "credential only on -6" rule, so put it to the founder (Open Question 3).
- **Warning signs.** `not_healed:ipc_fault:code=0` lines repeating at WARNING with no recycle.

### Pitfall 2: The spike's "initialize cannot relaunch" conclusion leads a plan to build restart infrastructure it may not need
- **What goes wrong.** A plan adds a Railway token, or a process-launch literal (a new command class on the unauthenticated channel), when the documented `initialize` launch may already do the job.
- **How to avoid it.** Run S-09 first, then follow the pre-decided branches (§Open Questions 2). Do not record "initialize launches" as VERIFIED until S-09 passes with the working process check `ps -eo args | grep -c '[t]erminal64.exe'` (CONTEXT's corrected form).

### Pitfall 3: Deleting the job terminal's `trades` caches recreates Finding C for every account
- **What goes wrong.** `services/mt5_read.py::read_mt5_deal_ledger` calls `login()` and then `history_deals_get()` with no wait for the history download (`164.6.6-CONTEXT.md` Finding C: deals read about 1 s after authorize, `derive_broker_dailies` failed permanently with "<2 usable daily-return days"). Today only accounts NEW to the job terminal hit it. After a `trades` scrub, EVERY account is new on its next derive. That is a user-facing permanent failure stamp on every MT5 strategy.
- **How to avoid it.** Make the job-terminal `trades` deletion a hard precondition on Phase 164.6.6.3's bounded history wait being shipped. 164.6.6.3 is ordered before this phase in the ROADMAP but has no phase directory yet, so it is not planned. `accounts.dat` deletion alone does not trigger it. The validation terminal does not read deal history, so it is unaffected.

### Pitfall 4: The validation terminal has no heal at all (D-06)
- **What goes wrong.** The session monitor, boot heal and recycle read only `MT5_GATEWAY_HOST`/`_PORT`. A failed validation-terminal relaunch is noticed only when the next validation fails (D-06 residue).
- **How to avoid it.** The SCRUB OWED / relaunch-debt marker (Pitfall 1(b)) is consumed at the start of the next validation, so the next validation self-heals before its probe instead of failing. Alert on every failed relaunch. The reader of the rows stays deferred to 164.6.8.

### Pitfall 5: Budget assumptions inherited from the moved plans
- **What goes wrong.** The moved plan 04's "credentialed relaunch reading = 2 crossings" assumes the launch and the login fit in one 30 s crossing. The only measured cold relaunch (164.6.5 run 1) took 86 s from kill to authorized, partly waiting for a caller (about 25 s). It was bare, and at the time of the next call the terminal reappeared.
- **How to avoid it.** W-2. Derive every budget from S-09's measured kill-to-authorized time. If it exceeds one crossing, use budget-gated credentialed polls (still under the unchanged 300 s ceiling, with `_RELAUNCH_SETTLE_S: Final[float] = 90.0` and `_RELAUNCH_POLL_INTERVAL_S: Final[float] = 10.0`, `mt5_relogin.py:430,435`). Never delete when the time left cannot cover the relaunch.

### Pitfall 6: A credentialed `initialize` racing the terminal's own auto-login
- **What goes wrong.** If `accounts.dat` is NOT removed, a launched terminal may try the saved (possibly stale) house password before the Python authorize arrives, and land in the L7 dialog.
- **How to avoid it.** Always delete `accounts.dat` before the relaunch on every path. The recycle path gains this too, which D-03's reversal "for saved accounts" covers.

### Pitfall 7: Measurement hygiene on Wine
- **What goes wrong.** `ps -eo comm | grep -cx terminal64.exe` never matches under Wine (CONTEXT). Bases sub-directory names are broker server names, and `trades` children are account numbers.
- **How to avoid it.** Use `ps -eo args | grep -c '[t]erminal64.exe'`. Count and mask in every live reading; never paste names. ⛔ Never print `terminal64.exe`'s arguments after a CREDENTIALED launch. Record yes/no flags only (see Open Question 2), because the launch command line has never been inspected and may carry the credential.
