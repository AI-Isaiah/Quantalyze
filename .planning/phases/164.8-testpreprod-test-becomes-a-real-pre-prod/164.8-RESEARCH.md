## Summary

Every question below was answered by reading the actual file or the actual CLI source at the CI-pinned version (`supabase/cli` **v2.98.2**, `supabase-migrate.yml:171,205`), never from memory. Two findings dominate the plan:

1. **`supabase db push` cannot run against TEST as the ledger stands today, and no flag makes it forward-only.** `FindPendingMigrations` (`pkg/migration/apply.go:21-54`) compares the *sorted `version` column* against local filename timestamps. Any remote version with no local file is `ErrMissingLocal` and a hard error **before** `--include-all` is consulted (`up.go:42-52`). TEST's ledger provably holds such rows — the latest `main` run's own VAC-08 shape diagnostic prints `version=20260828061901 name=20260827120000_strategy_shares_generation_model` (CI run 34202869035, job 101989517009). And when the ledger *is* consistent, `--include-all` applies **every** local file the remote lacks (`up.go:46-48`) — exactly the 31-file bulk apply Area 2 rejected. There is no "start from a version" or "skip these" flag (`supabase db push --help`, output pasted in §A). `migration repair` only inserts/deletes ledger rows, executing no SQL (`repair.go:58-88`). **So Area 2 Q1 (forward-only from a cut) is implementable only two ways:** (R1) a founder-approved one-shot ledger repair on shared TEST plus a filtered temp workdir handed to the CLI, or (R2) a small repo-owned applier that applies post-cut files with `psql` and writes the same ledger row the CLI writes. §A and §E argue R2.

2. **The pragma must be a machine-checkable *claim*, not prose, and its seam must be a node module both bash consumers call.** VAC-08 already shells out to node for the normalizer (`test-ledger-drift-check.sh:232,492`), and this repo's two annotation precedents (`RED-UNDER-M`, `APP-GUC-LINEAGE`) both refuse malformed headers, pin an exact count/object, and ship red fixtures per finding kind. Arm 3 ("stated reason is FALSE") is decidable only with a live catalog probe of TEST; the hermetic half is the *decision logic* behind an injectable `OBJECT_PROBE_CMD`, exactly VAC-08's existing `LEDGER_QUERY_CMD`/`BODY_FETCH_CMD` seam and its stated boundary (`:100-112`). §C names what is and is not decidable without a credential.

**Primary recommendation:** Build `scripts/migration-applicability.mjs` (one parser + `--self-test`, node, hermetic) and a repo-owned `scripts/test-apply-migrations.sh` (psql, cut-bounded, mutex-wrapped, stops at first failure by name, writes `INSERT_MIGRATION_VERSION`-shaped rows). Wire a `test-apply` job into `supabase-migrate.yml` that the PROD `apply` job `needs:`. Extend VAC-08 with a third partition (declared-not-applicable, probe-verified) and three new red arms in its `--self-test`. Do **not** attempt `supabase db push` against TEST until the ledger measurement in §E is taken and the founder rules on a repair.

### Locked Decisions

#### Area 1 — Apply pipeline: when, and what a failure blocks
- **The TEST apply runs on merge to `main`**, as a job that must succeed BEFORE the PROD
  apply job. Not on PR (a PR head is not the merge result) and not nightly (too late to
  gate anything).
- **A failed TEST apply BLOCKS the PROD apply.** Warn-only was considered and rejected:
  it makes the phase decorative, and "caught against a real Postgres instead of against
  customers" is the entire goal.
- **Same workflow** (`supabase-migrate.yml`), a new job the PROD job `needs:`. One place
  decides what reaches production; two workflows cannot order themselves.
- **A new GitHub Environment `Test`** carrying its own project ref and password,
  mirroring how the PROD job is already pinned by `environment: Production`
  (`supabase-migrate.yml:118`).

#### Area 2 — Bringing TEST current
- **Forward-only from a declared cut date.** ⚠️ This is a DELIBERATE SCOPE CUT, accepted
  knowingly: it does NOT bring TEST current in the sense of matching PROD. It declares
  the accumulated past out of scope and starts the discipline from the cut. Justified by
  measurement — 69 of 262 migrations do not replay from empty (`BASELINE.md`), and a full
  replay is precisely what hits `42883` on `20260908120000`.
- **The 31 baselined-absent migrations are NOT bulk-applied.** The list shrinks by
  founder decision, one at a time, as it already has once
  (`20260823120000_revoke_api_keys_insert`, 32 → 31). A bulk apply is 31 unreviewed
  schema changes on a database other people's CI uses.
- **The catch-up is a one-shot `workflow_dispatch`, founder-approved, never automatic** —
  it writes to a SHARED database.
- **A failure mid-catch-up STOPS and reports the failing migration by name.** Continuing
  past a failure leaves TEST in a state nobody can describe.

#### Area 3 — The unappliable-migration disposition (`[164.5-TEST-VAC08-DROP-UNAPPLIABLE]`)
- **The migration AUTHOR declares it; the gate does not infer it.** Inference means
  probing TEST for the object and staying silent when it is absent — which is
  indistinguishable from the genuine missing-apply the gate must still catch.
- **Shape: a dated header pragma** in the migration (e.g. `-- TEST-NOT-APPLICABLE: <reason>`),
  parsed by ONE piece of code that both consumers read. Conforms to the `RED-UNDER` and
  `APP-GUC-LINEAGE` idioms this repo already has.
- **One declaration exempts BOTH the TEST apply and VAC-08's drift verdict.** Two
  independent switches drift, and the apply pipeline would then abort on exactly the
  migrations VAC-08 had been told to forgive.
- **Anti-vacuity is a THREE-arm proof, not a pair:**
  1. RED — a genuinely unapplied migration with NO pragma still fails.
  2. GREEN — the pragma'd migration passes.
  3. RED — a pragma whose stated reason is FALSE (the object DOES exist on TEST) fails.
  ⛔ Arm 3 is what stops the pragma becoming a mute button. A disposition proven only in
  direction (2) is worse than the red it replaces.

#### Area 4 — Shared-TEST blast radius
- **No new isolation mechanism in this phase**, stated explicitly rather than left
  implicit. The ROADMAP already fences it.
- **`FANOUT-GLOBAL-01` stays deferred**, named in the phase as a known limit on any
  assertion made against TEST.
- **The apply step TAKES the existing shared-TEST advisory mutex** — the same one
  `ci.yml`, `analytics-deploy-verify.yml`, `main-ci-cancelled-watcher.yml` and
  `mutex-probe.yml` use. An apply racing a running `sql-tests` is the one collision that
  corrupts a reading rather than merely delaying it.
- **A foreign conflicting change surfaces as a LOUD apply failure.** We cannot lock a
  database we do not own, and a defence that cannot be tested is worse than a clear error.

#### ⚠️ ACCEPTED CONSEQUENCE — a coupling neither answer shows alone
Area 1 Q2 (a TEST apply failure BLOCKS the PROD apply) and Area 4 Q3 (the apply takes the
SHARED mutex) combine into: **a hung or slow mutex holder, owned by someone else's CI, now

TEST at all, so this is a NEW coupling to a resource this project does not control. It was
surfaced at decision time and accepted. ⛔ Planning must not discover this and quietly

a timeout on mutex acquire that proceeds with a loud warning, applying without the mutex,

### A.3 How `db push --include-all` decides what to apply, and mid-list failure `[VERIFIED: supabase/cli v2.98.2 source fetched raw this session into the scratchpad; paths below are repo-relative in github.com/supabase/cli]`

`internal/db/push/push.go:33` → `up.GetPendingMigrations(ctx, ignoreVersionMismatch, conn, fsys)` where `ignoreVersionMismatch` IS the `--include-all` flag. `internal/migration/up/up.go:33-53`, verbatim:

```go
func GetPendingMigrations(ctx context.Context, includeAll bool, conn *pgx.Conn, fsys afero.Fs) ([]string, error) {
	remoteMigrations, err := migration.ListRemoteMigrations(ctx, conn)
	...
	localMigrations, err := migration.ListLocalMigrations(utils.MigrationsDir, afero.NewIOFS(fsys))
	...
	diff, err := migration.FindPendingMigrations(localMigrations, remoteMigrations)
	if errors.Is(err, migration.ErrMissingLocal) {
		utils.CmdSuggestion = suggestRevertHistory(diff)
	} else if errors.Is(err, migration.ErrMissingRemote) {
		if includeAll {
			pending := localMigrations[len(remoteMigrations)+len(diff):]
			return append(diff, pending...), nil
		}
		utils.CmdSuggestion = suggestIgnoreFlag(diff)
	}
	return diff, err
}
```

`ListRemoteMigrations` runs `SELECT version FROM supabase_migrations.schema_migrations ORDER BY version` (`pkg/migration/history.go:24`, `list.go:19-31`) — **it reads `version` only, never `name`** (comment at `list.go:20`). `ListLocalMigrations` keeps files matching `^([0-9]+)_(.*)\.sql$` (`file.go:30`, `list.go:49-53`). `FindPendingMigrations` (`pkg/migration/apply.go:21-54`) is a two-pointer merge over the two sorted version lists:

```go
	for i < len(remoteMigrations) && j < len(localMigrations) {
		remote := remoteMigrations[i]
		...
		local := migrateFilePattern.FindStringSubmatch(filename)[1]
		if remote == local { j++; i++ }
		else if remote < local { missing = append(missing, remote); i++ }
		else { unapplied = append(unapplied, localMigrations[j]); j++ }
	}
	if j == len(localMigrations) { missing = append(missing, remoteMigrations[i:]...) }
	if len(missing) > 0 { return missing, errors.New(ErrMissingLocal) }
	if len(unapplied) > 0 { return unapplied, errors.New(ErrMissingRemote) }
	pending := localMigrations[len(remoteMigrations):]
	return pending, nil
```
with `ErrMissingRemote = "Found local migration files to be inserted before the last migration on remote database."` and `ErrMissingLocal = "Remote migration versions not found in local migrations directory."` (`apply.go:15-16`).

Consequences, each read off the code:
1. **A remote `version` with no local file of that exact timestamp is fatal** (`ErrMissingLocal` is returned before `ErrMissingRemote` is even considered, `:45-47`), and `--include-all` does not touch that branch (`up.go:43-44` only sets a suggestion). The suggested remedy is `supabase migration repair --status reverted <versions>` (`up.go:55-61`).
2. **`--include-all` = "apply every local file whose version the remote lacks, older ones first"** (`up.go:46-48`). It is a superset switch, not a selector.
3. **There is no flag to start at a version, skip a file, or bound the set.** `supabase db push --help` (2.84.2, pasted): flags are `--db-url`, `--dry-run`, `--include-all`, `--include-roles`, `--include-seed`, `--linked`, `--local`, `-p/--password`. `ListLocalMigrations` has a `filter` parameter (`list.go:33,55-59`) but nothing on the `db push` path passes one.
4. **`db push` reads `supabase/config.toml` `[db.migrations] enabled = true`** (`push.go:31`; `config.toml:53-55`) and, when pending is non-empty, `vault.UpsertVaultSecrets` runs before apply (`push.go:89`).
5. **Execution and mid-list failure** (`apply.go:56-77`, `file.go:75-115`): files are applied in order; for each, `RESET ALL`, then the file's statements plus the ledger `INSERT` are sent as ONE `pgconn.Batch` — "ExecBatch is implicitly transactional" (`file.go:87`). On error the loop **returns immediately** (`apply.go:72-73`) with `Applying migration <file>...` already printed to stderr (`:64`) and the message `At statement: <i>` plus the offending statement with a caret (`file.go:88-113`). Earlier files stay committed; the failing file's batch is rolled back as a unit (unless the file carries its own `BEGIN;…COMMIT;`, in which case statements after an inner `COMMIT` are in a fresh implicit transaction until Sync). **So the CLI already satisfies "stop and name the failing migration" — it stops at the first failure and every later file is untouched** (this is the WEDGE `[164.5-TEST-EXCEPT-DRIFT04]` warns about, `TODOS.md:1535-1540`).
6. **Ledger row written by the CLI** (`history.go:18`): `INSERT INTO supabase_migrations.schema_migrations(version, name, statements) VALUES($1, $2, $3)` with `version = <14-digit prefix>`, `name = <description after the first underscore>` (`file.go:44-45` — NOT the full basename), `statements = text[]` of the split statements. Table DDL: `version text NOT NULL PRIMARY KEY`, `statements text[]`, `name text` (`history.go:15-17`). ⚠️ This is VAC-08's "old rows" convention `version || '_' || name = basename` (`test-ledger-drift-check.sh:39-40,147`); the "recent" convention (`name = full basename`, `version` re-stamped, `:41-42`) is **not** what this CLI writes — those rows came from another applier (the Management API / MCP `apply_migration`), which is why TEST's ledger is CLI-inconsistent today.

### B.3 The `RED-UNDER` precedent — grammar shape, validation, falsifiability `[VERIFIED: scripts/mutation-runner/GRAMMAR.md:1-330; scripts/mutation-runner/parse.mjs:58-60,130-168,249-474, read this session]`

Shape: prose line + structured JSON twin on the NEXT line, never a sidecar (`GRAMMAR.md:28-37`):

  -- RED-UNDER-M: {"arm":"…", "apply":[{"kind":"edit","file":"…","find":"…","replace":"…","occurrences":1}]}

Recognised ONLY at comment-line start: `PROSE_RE = /^[ \t]*--[ \t]*RED-UNDER:/`, `STRUCTURED_RE = /^[ \t]*--[ \t]*RED-UNDER-M:[ \t]*(.*)$/`, `SETUP_RE` likewise (`parse.mjs:58-60`); rule 1 explains why (a header sentence *about* the marker inflated the count 30→33, `GRAMMAR.md:44-70`).

Validation (`parse.mjs:249-474`): `validateStep` normalises every step and throws a message string; `validateAnnotation` requires non-empty `arm` and an `apply` array; JSON parse failure is `fail("malformed JSON in RED-UNDER-M: …")` (`:441`); only one `RED-UNDER-SETUP` per file (`:416`); `refuseSelfSatisfying` (`:130`) refuses injecting the `TEST FAILED (` literal, `refuseRetargetingFailureLiteral` (`:168`) refuses needles naming it; paths must be repo-relative (`:79`).

What makes it **falsifiable** (the property the pragma must inherit):
- Every claim carries a **measured quantity** the machine re-measures: `occurrences` is required on every byte edit and a count mismatch is its own defect kind `occurrence-mismatch` — "could not locate the bytes" and "the arm did not redden" never share a code path (`GRAMMAR.md:74-99`).
- The claim is proven by **running the thing** and reading what the database printed, attributed by source location (rule 3c, `GRAMMAR.md:266-330`), not by trusting the annotation's spelling — three consecutive review rounds re-opened "closed" rules by re-spelling (`:118-126`).
- **Absence of proof is never a pass**: unparseable output is `MEASURE_FAIL` (`:309-311`).

For the pragma this translates to: the header must name **the object it claims is absent on TEST** in a form a query can check (kind + schema-qualified identifier + arity for functions), plus a date, plus a reason; the gate must **probe** that object; a probe that cannot run is `MEASURE_FAIL`; and a pragma with no checkable object is malformed, not lenient.

**Honest answer:** arm 3 as decided ("the object DOES exist on TEST") is **not decidable without a TEST connection**. What IS decidable hermetically is (a) that the gate's logic fails closed when told the object exists (O2), (b) that a probe error is `MEASURE_FAIL` rather than "absent" (O2), and (c) O4. The plan should ship O1+O2+O4 together: O2 and O4 in `--self-test` and vitest (no DB), O1 as the live path in `sql-tests` and in the applier. A calibration arm in the style of `test-ledger-drift-check.sh:610-612 --expect-inverted` should prove the new arms can fail. **Do not** present O2 alone as "arm 3 proven" — that is the "proven only in direction (2)" shape CONTEXT forbids restated one level up.

## D. THE SHARED MUTEX

### D.1 Mechanism `[VERIFIED: docs/runbooks/shared-test-db-mutex.md:20-63,75-140; .github/workflows/ci.yml:2510-2727,3263-3330]`

- **Lock key:** session advisory lock **`61616158`** on the TEST Postgres (`runbook:22-24`; `ci.yml:2610`). All TEST-writing jobs MUST take the same key — a private key "serializes this job only against itself" (`ci.yml:2395-2399`).
- **Where:** the **session-mode** DSN — derived from `TEST_SUPABASE_DB_URL` by rewriting `:6543/` → `:5432/` (`ci.yml:2537-2543`), because a session lock does not survive transaction-mode pooling (`runbook:44-49`). libpq keepalives appended (`:2555-2559`).
- **Acquire** (`ci.yml:2522-2727`): a BACKGROUND `psql` (`nohup … &`, pid recorded) runs, in order, `SET statement_timeout = 0;` → `SET client_connection_check_interval = '30s';` → `SELECT 'HOLDER-BACKEND-PID ' || pg_backend_pid();` → `SELECT pg_advisory_lock(61616158);` → `SELECT 'MUTEX-ACQUIRED';` → `SELECT pg_sleep(6000);` (`:2604-2612`). The foreground loop polls the log for `MUTEX-ACQUIRED` every 5 s up to a **3600 s cumulative cap** (`:2631-2670`); a DEAD session is retried up to 3 times with 5/10 s backoff (`:2629,2685-2695`); a cap exhaustion is NOT retried — that is contention (`:2672-2675`). `PGAPPNAME=ci-shared-test-db-mutex` identifies holders (`:2605`).
- **Timeout behaviour:** on cap exhaustion the step runs a bounded census (`PGCONNECT_TIMEOUT=15 timeout 20 psql … SET statement_timeout='10s' … count(*) FILTER (WHERE granted) … FROM pg_locks WHERE locktype='advisory' AND objid=61616158`, `:2721-2725`) and prints `::error::timed out after ${waited}s … Lock census: … TWO causes … (1) QUEUE DEPTH … (2) A WEDGED holder …` then `exit 1` (`:2726-2727`). The job `timeout-minutes: 90` (`:2362-2370`) is the TTL; holder `pg_sleep(6000)` > TTL is the invariant (`:2563-2573`).
- **Release** (`:3269-3330`, `if: always()`, never non-zero): `kill` the psql client; if the pid is already gone print `::error::mutex holder pid … died BEFORE this release step — the DB work after its death ran UNSERIALIZED` (annotation only, `:3287-3297`); then server-side `SELECT pg_terminate_backend(${backend}) FROM pg_locks WHERE locktype='advisory' AND objid=61616158 AND pid=${backend};` guarded so it is a no-op on a recycled pid (`:3314-3318`).
- **Wedged holder:** no reaper cron; TTL + `client_connection_check_interval='30s'` bound an orphan at ~30 s after its client dies (`runbook:77-113`); a session alive-but-wedged is the only human case — runbook §3 gives the `pg_stat_activity`/`pg_locks` census and `pg_terminate_backend(<pid>)` (`runbook:154-235`). Waiters are served in unspecified order (`runbook:34-42`).
- **Three coupled numbers** (`runbook:151-165`): acquire cap 3600 s, job TTL 90 min, holder sleep 6000 s — and a FOURTH in `analytics-deploy-verify.yml` (convergence window 4800 s, `runbook:166-176`): raising the cap requires raising that window.

### D.2 The acquire pattern to copy, and the pins that constrain it

- Copy the `Acquire shared-test-db mutex` step from `ci.yml:2522-2727` and the release step `:3269-3330` **byte-for-byte** into the new `test-apply` job. `critical-regressions.test.ts:1290-1312` asserts the THREE `ci.yml` acquire steps are pairwise byte-identical and carry keepalives, and `:1272` pins the four-line `SET…SET…HOLDER-BACKEND-PID…pg_advisory_lock` fragment; `:1367` pins the guarded terminate. Those pins are scoped to `ci.yml` job names, so a copy in `supabase-migrate.yml` is not asserted by them — the planner should add the same byte-identity assertion across files (a fourth site that drifts is the exact risk `:1312` names).
- `mutex-probe.yml:131-225` is the closest precedent for a mutex user OUTSIDE `ci.yml`: same DSN rewrite, same keepalives, same two `SET`s before `pg_advisory_lock`, `PGAPPNAME=ci-mutex-probe`. For the apply job use the `ci.yml` holder shape (background holder + release), not the probe's single-session shape, because the apply needs the lock held across several steps (marker check → applier → post-verify).
- The fork-PR `exit 0` branch (`ci.yml:2527-2530`) is **wrong for this job**: `supabase-migrate.yml` runs on push to `main`/dispatch, never on a fork PR, and an absent credential on a push must be `exit 1` (the same reasoning `supabase-migrate.yml:135-143` applies to PROD secrets). Replace that branch with a fail-loud.
- `timeout-minutes` for `test-apply`: derive from the runbook table — setup (~2 min) + acquire cap (60 min) + apply work (small) → the same 90 min shape, with `pg_sleep(6000)` kept above it. ⚠️ This is the accepted coupling in CONTEXT: a merge can now wait up to ~60 min behind other CI before PROD applies. Do not shrink the cap to soften it (locked).
- The mutex serializes the apply against `sql-tests`/`python`/`e2e-seeded` — it does NOT order them. On a push to `main`, `ci.yml`'s `sql-tests` (VAC-08) and `supabase-migrate.yml`'s `test-apply` start concurrently; whichever wins the lock runs first. If VAC-08 wins, it reads the ledger BEFORE the apply and reports the merge's new migration as NEW drift. See Pitfall 3.

## E. FORWARD-ONLY CUT DATE

### E.1 The numbers, and what they are made of `[VERIFIED: CI run 34202869035 log; scripts/vac08-ledger-baseline.txt; ls supabase/migrations]`
- Repo: **266** `*.sql` under `supabase/migrations/` (`Repo migrations: 266` in the log; `ls | wc -l` = 267 including the `down/` directory).
- TEST ledger: `rows_total=243 name_null=2 name_set=241`; **2** ledger rows have no repo file under any convention (`advisory: 2 …`).
- Absent: **31** baselined (`vac08-ledger-baseline.txt`, last entry `20260819151000_csv_finalize_fold_guard1_null_safe`) + **1** un-baselined (`20260908120000`) = 32. So 234 repo files match a ledger row; 243 − 2 = 241 matching rows > 234 means several migrations are ledgered twice (VAC-08 header `:16-17` "several applied twice", tolerated by `EXISTS`).
- The three most recent ledger rows (`20260906120000`, `20260907120000`, `20260907130000`) have `version == filename timestamp` and `name == full basename` — the hand-apply path used for `[164.2-TEST-APPLY-PROVENANCE]`/`[164.7-TEST-APPLY-APPSETTINGS]` wrote CLI-compatible versions but the "recent" name convention. Rows like `version=20260828061901 name=20260827120000_…` are re-stamped (not CLI-compatible).

### E.2 A defensible cut date
The cut must satisfy: every repo migration with `ts ≤ CUT` is either ledger-present, baselined (31, founder-owned), or pragma'd (1); every migration with `ts > CUT` is the pipeline's responsibility. Measured, the newest migration is `20260908120000` and everything up to `20260907130000` is present or baselined. **Recommended `TEST_APPLY_CUT = "20260908120000"`** (inclusive: files with `ts > CUT` are candidates), pinned as an exported constant in the seam module beside a dated comment, and mirrored by a vitest that re-derives the invariant "every repo file ≤ CUT is present ∪ baselined ∪ pragma'd" from the baseline file + pragma list (hermetic half) — the ledger-present half is VAC-08's live job. Choosing the newest existing migration as the cut means the catch-up dispatch (Area 2 Q3) has NOTHING to apply on day one — which is exactly the founder's "the past is out of scope"; the one-shot dispatch then exists for the day a baseline line is deleted (see E.3).

### E.3 Mechanical enforcement — how a later migration cannot pull in an earlier unapplied one
1. **Lower bound by construction (R2):** the applier's candidate set is `{repo files : ts > CUT}` minus ledger-present minus pragma'd. A file with `ts ≤ CUT` is never in the set, whatever its ledger state. (`--include-all` has the opposite property — `up.go:46-48` — which is why R2.)
2. **Backdating is refused upstream:** `migration-policy.yml:60-290` blocks any PR that ADDS a migration whose timestamp is below PROD's ledger tip unless allowlisted in `.github/migrate-backdated-allowlist.txt`. An allowlisted backdated file with `ts ≤ CUT` would be invisible to the applier AND absent from TEST → VAC-08 `NEW drift` red (`:386-403`) → loud, not silent. The two mechanisms partition the timeline with no gap.
3. **The 31 shrink only by a founder apply:** when the founder hand-applies one and deletes its baseline line, VAC-08's stale check (`:365,:376-385`) has already forced the deletion order (apply first, then delete — otherwise `NEW drift`). The applier never sees those files because `ts ≤ CUT`. If the founder instead wants the pipeline to apply a chosen old file, the mechanism is a founder-approved `workflow_dispatch` input naming the basename explicitly (Area 2 Q3 "one-shot, founder-approved, never automatic") — the applier applies exactly that file, in order, stopping at the first failure by name.
4. **Ledger row written by R2** must be CLI-compatible in `version` (= file timestamp) so that any future move to R1 does not re-break the CLI, and `name` = full basename (the "recent" convention VAC-08 already joins, `:146`).
5. **Pin both directions:** a vitest that (a) neuters the `ts > CUT` filter and observes a `≤ CUT` fixture file enter the candidate set (RED), and (b) confirms the real corpus yields an EMPTY candidate set at the cut on the day it ships (the measured number, printed).

## Common Pitfalls

### Pitfall 1: `supabase db push` refuses TEST outright
**What goes wrong:** `Remote migration versions not found in local migrations directory.` **Why:** `FindPendingMigrations` is version-keyed (`apply.go:21-54`) and TEST has re-stamped versions (log sample). **How to avoid:** R2; or R1 only after a founder-approved repair. **Warning signs:** the CLI suggests `migration repair --status reverted …` — do NOT run it from this checkout (linked to PROD).

### Pitfall 2: `--include-all` bulk-applies the 31
**What goes wrong:** exactly the rejected outcome. **Why:** `up.go:46-48`. **Avoid:** never call `db push --include-all` against TEST with the real migrations dir.

### Pitfall 3: the merge's own VAC-08 races the apply
**What goes wrong:** on a push to `main`, `ci.yml sql-tests` and `supabase-migrate.yml test-apply` contend for the same lock in unspecified order (`runbook:34-42`). If VAC-08 runs first it reports the just-merged migration as `NOT baselined` → red `sql-tests` → red `frontend` → Railway skips the analytics deploy (`runbook:65-70`, `migration-drift-check.yml:19-26`). **Also on every PR:** a PR that adds a migration is red on VAC-08 (and on any applied-ness-probe SQL gate) until it merges, because the apply is on-merge by locked decision — this is the `[164.2-TEST-APPLY-PROVENANCE]` shape made permanent for PR-time. **Avoid:** VAC-08 may scope "NEW drift" for files that are not on the base branch — on `pull_request`, exclude files added by the PR (`git diff --diff-filter=A base..HEAD`, `migration-policy.yml:116-124` idiom) and print them as `pending apply-on-merge: <name>`; on `push`, either (a) accept one possibly-red run and re-run, or (b) have `sql-tests` on push wait for the migrate workflow — a coupling of its own. **This is a founder-visible consequence of Area 1 Q1 and must be surfaced in the plan, not discovered.** ⚠️ Applied-ness probes inside `supabase/tests/*.sql` (`TEST FAILED (0)` shapes) cannot be scoped this way; they stay red on migration PRs.

### Pitfall 4: the pragma header spells a refused token
**What goes wrong:** `20260908120000`'s verify greps the whole file for the existence-tolerant / dependent-removing modifiers and for schema qualifiers it must not name (`:80-87,118-122`). **Avoid:** the header names the object and the reason without those words; add a vitest asserting the file still contains zero occurrences.

### Pitfall 5: a fourth mutex site that drifts
**Why:** `critical-regressions.test.ts:1290-1312` pins only `ci.yml`. **Avoid:** extend the byte-identity pin across files.

### Pitfall 6: `paths:` filter hides seam/baseline edits from the migrate workflow
**What goes wrong:** editing `scripts/migration-applicability.mjs` or the baseline never triggers `test-apply`; a broken seam is discovered on the next migration merge. **Avoid:** the seam's `--self-test` and vitest run in `ci.yml` on every PR (as `sql-gate-lint` does); and consider adding the seam paths to `supabase-migrate.yml`'s `paths:` — ⚠️ note `migration-drift-check.yml:38-47` documents the credential-exposure reasoning for such additions; the same reasoning applies to the `Test` credential.

### Pitfall 7: transaction-mode pooling for the apply
**Why:** `SET lock_timeout` and multi-statement files need one backend. **Avoid:** session DSN rewrite for the apply psql, as for the holder.

### Pitfall 8: the marker string is unknown to the repo
**Why:** `COMMENT ON DATABASE` is hand-set; nothing in-repo carries its value. **Avoid:** read it once (read-only) in the plan's first wave, pin it as a constant with the date, and refuse on mismatch OR NULL (CLAUDE.md).
