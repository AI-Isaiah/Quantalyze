## Summary

**Nothing has ever called `/api/cron-sync` on PROD, and the sync code is already built for it.** The route, the per-strategy cursor table (`strategy_sync_cursors`, 0 rows on PROD) and the vault tick pattern all exist. The phase is mostly wiring plus four traps the existing code sets for a first tick. All four were found by reading and, where cheap, by executing the repo code or measuring PROD.

The four traps, in order of damage. (1) **Seeding cursor rows does not recover a gap older than 30 days**: `_resume_floor_ms` clamps any marker-derived floor to `MAX_MARKER_LOOKBACK_MS` (30 days), executed here: a marker 156 days old yields a 30.0-day window. The fallback to `api_keys.last_sync_at` is the unclamped path, but that column is overwritten daily at about 04:05 UTC (executed here: a 9-hour-old `last_sync_at` yields a 9.0-hour window). The right fix is a data-derived fallback (the strategy's own newest stored daily-P&L row), not seed rows. (2) **A tick that is not at 00:00 UTC cuts the day's row**: `sync_trades` deletes and re-inserts the daily rows inside the payload's day range, and the fetch starts at the raw cursor instant, so the cursor day is re-written with only the post-cursor part of its bills. The fetch start must be floored to 00:00 UTC. (3) **`cron_sync` selects every `is_active` key**: 42 on PROD, of which 14 are disconnected and 28 have no eligible strategy. The first tick would read disconnected users' exchange accounts, write `account_balance_usdt` on allocator keys, count 5 revoked Bybit keys as `revoked` forever, and run for up to 9 sequential batches (about 9 minutes worst case) against Railway's 5-minute idle cut-off. It must be filtered to connected keys with at least one eligible strategy (4 keys on PROD). (4) **The first tick's follow-on derive can replace a published track record**: three of the four OKX strategies have 0 `csv_daily_returns` rows, and their stored `returns_series` (25 to 73 points) is a legacy artifact. `compute_analytics_from_csv` reads only `csv_daily_returns`, so a derive that writes only the venue-reachable window replaces that series.

**D-01 verdict (plain): it does not fit this phase; book it as a follow-on phase.** For OKX the "trades" the cron stores are already aggregated from account bills (`fetch_all_trades` is `fetch_daily_pnl`, which reads `/account/bills` and `/account/bills-archive`, last 7 days and last 3 months). So there is no separate trade-derived versus bills-derived pair on OKX; D-01 is really an extension of OKX's reach from 3 months to the quarterly `bills-history-archive` CSV download (since 2021-02-01, async, 2 to 3 hours to generate, 12 requests a day). Bybit needs nothing (closed-PnL and transaction-log both reach 2 years; its gap is 15 days). Three OKX strategies are affected, two of them published, one on a disconnected key. See Section 6.

**Primary recommendation:** ship the tick as a copy of the vault tick (`30 4 * * *` UTC, `timeout_milliseconds := 180000`, registered by runbook after a measured rehearsal), fix the resume fallback in `routers/cron.py` (not the poll writer), floor the fetch start to UTC midnight, filter the key selection, record the last successful fetch in a new nullable `strategy_analytics.trades_fetched_at`, and book the OKX history-archive reach as its own phase.

**Sync versus async (SC-5).** Facts:
- `match_engine_cron_tick` and the cadence check both use `timeout_milliseconds := 60000` (`20260911120000...:314`, `20260918120000...:199`). pg_net's own default is 5000 ms. [VERIFIED: migrations read]
- `net._http_response` retains rows for `pg_net.ttl = 6 hours` on PROD, so a rehearsal's body (which carries the route's `duration_s`) must be read within 6 hours. 6 rows, all 200, 0 timed out at read time. [VERIFIED: PROD read 2026-10-09]
- Railway closes an HTTP request after 5 minutes with no data transferred and after 15 minutes in any case. [CITED: https://docs.railway.com/networking/public-networking/specs-and-limits]
- `cron_sync` has no overall deadline: exchange groups run sequentially, each in batches of `BATCH_SIZE = 5` with `EXCHANGE_BATCH_DELAY = 2.0` s between batches and `KEY_SYNC_TIMEOUT = 60` s per key (`cron.py:78-82`, loop at `:1741-1758`). The portfolio recompute cascade runs inside the same request, up to 90 s per portfolio at concurrency 2 (`:86-93`).
- Unfiltered, today's selection is 42 active keys: okx 11 (3 batches), deribit 16 (4), bybit 6 (2), mt5 9 (2, deferred). Worst case is about 9 sync batches times 60 s = 9 minutes, which exceeds Railway's 5-minute idle cut-off. After the Section 5 filter the loop holds 4 keys (okx 3, bybit 1): two groups of one batch each, worst case about 120 s, plus 0 portfolios.
- **A full run is UNMEASURED.** Nothing has called the route on the current deployment (Railway HTTP log census in the debug doc: 0 requests, positive control present). The nearest measured proxies, from PROD `compute_jobs` for ccxt venues over the last 30 days (`updated_at - claimed_at`): `sync_trades` p50 44.8 s, p95 188 s, max 280 s (n=9, includes raw-fill backfill that the cron path does not do); `sync_funding` p50 4.2 s, p95 185.5 s (n=110); `reconcile_strategy` p50 9.7 s (n=130); `derive_broker_dailies` p50 19.4 s, p95 731 s (n=98). These bound a venue round-trip's order of magnitude only.

**Recommendation.** Keep the tick synchronous. Set `timeout_milliseconds := 180000` (above the 120 s filtered worst case, below Railway's 5-minute idle cut-off). Make the number a measured one: the go-live runbook has a REHEARSAL step that runs `SELECT public.cron_sync_tick()` once from the CLI behind the marker guard and reads `net._http_response` (status, `timed_out`, and `duration_s` inside the body) within the 6-hour TTL. Decision rule written into the runbook: if the rehearsal's `duration_s` exceeds 90 s, or any key reports `timeout`, do NOT register; switch to the async design (below). If the rehearsal fits, register with the measured margin recorded.

Async fallback (only if the rehearsal fails): make `/api/cron-sync` return 202 immediately and run the body as a background task guarded by a `cron_runs` row (`cron_name = 'cron_sync'`, status `running` then `ok`/`error`; the table, its index and RLS exist: `20260408113029_cron_heartbeat.sql`) so two runs cannot overlap. A restart loses an in-flight run, which is acceptable because cursors only advance on success (re-driven next day). The alternative fallback is the compute-jobs fan-out in "Alternatives Considered".

### 2. SC-2: the exact gap-skip path, and why seeding rows is the wrong repair

**The code path** (all [VERIFIED: analytics-service/routers/cron.py read this session]):
1. `cron_sync` loads every key `.eq("is_active", True)` (`:1594-1598`), then attaches per-strategy markers from `strategy_sync_cursors` by chunked `IN` (`:1661-1732`). A strategy with no row is ABSENT from `row["strategy_cursors"]`.
2. `_sync_single_key` captures `key_cursor_at_tick_start = key_row.get("last_sync_at")` (`:696`).
3. `_strategy_resume_point` (`:464-497`): `if strategy_id in strategy_cursors: return strategy_cursors[strategy_id]` (`:495-496`), else `return key_cursor` (`:497`).
4. `_resume_floor_ms` (`:500-668`): no eligible strategy -> `parse_since_ms(key_cursor)` (`:566-567`); otherwise the EARLIEST resume point across strategies; a floor that did NOT come from a marker is returned untouched (`:616`); a marker-derived floor older than the cap is replaced by `now - MAX_MARKER_LOOKBACK_MS` (`:631`, returned at `:668`).
5. `trades = await fetch_all_trades(exchange, since_ms=since_ms)` (`:890`), which is `fetch_daily_pnl` (`services/exchange.py:2835-2838`).
6. After a clean tick the key cursor is written `tick_now` (`:1065`) and a marker row is upserted for EVERY strategy in the fan-out (`:1311`), advancing to `tick_now` when `strategy_advances` (`:1227`) and holding at the pre-tick resume point otherwise.

**Executed proof on repo code** (run this session, `analytics-service/`, Python 3.14, `routers.cron` imported directly; `now` = real clock):

```
_resume_floor_ms(["sid-1"], {}, last_sync_at = now - 9h)
    -> floor age 9.0 hours            # newest stored trade is 156 days old: the gap is skipped
_resume_floor_ms(["sid-1"], {"sid-1": now - 156d}, last_sync_at = now - 9h, clamp_report={})
    -> floor age 30.0 days            # a SEEDED 156-day marker is clamped to the cap;
                                      # clamp_report keys: cap_days, floor_age_days,
                                      # floor_strategy_id, oldest_allowed_ms, truncated_strategy_ids
```

[VERIFIED: executed 2026-10-09]. The first line is the SC-2 "fails on today's code" case. The second line is the trap: **the roadmap's "seed `strategy_sync_cursors` at or before the newest stored trade" cannot recover any gap older than 30 days.** PROD's gaps are 15.6, 51.6, 139.6, 147.6 and 156.6 days (newest `daily_pnl` row per strategy; Section 5 table), so three of five would be silently cut to 30 days, with only an envelope field (`strategy_cursor_window_clamped`) and one warning line to show for it. The cap exists for a good reason (a stuck marker growing the key's window past `KEY_SYNC_TIMEOUT` and wedging the whole key, `cron.py:216-289`) and must not be lifted for this.

**Second trap in the same path: the fetch start is a raw instant, the store is day-aligned.** `fetch_daily_pnl` passes `begin = since_ms` straight to OKX (`exchange.py:1445`, `:1507`) and starts Bybit's window walk at `since_ms`, then aggregates by UTC day and stamps each row `YYYY-MM-DDT00:00:00+00:00`. `sync_trades` then deletes every non-fill row with `timestamp >= min(payload) AND <= max(payload)` and re-inserts the payload (`supabase/schema/functions/sync_trades.sql:100-115`). With a cursor at 04:30 on day D, the next tick builds day D's row from bills after 04:30 only, and the delete replaces the stored day-D row, which held the 00:00 to 04:30 part. The day's row loses that slice on every tick where any bill exists after the cursor. [VERIFIED: read exchange.py:1431-1624, 1801-1976 and sync_trades.sql; not executed against a database] Fix: floor `since_ms` to 00:00 UTC of its day before `fetch_all_trades`. Re-fetching a whole day is idempotent through the window-scoped delete.

**Recommended design (replaces seeding):**
- **Fallback source.** For a strategy with no marker row, use the strategy's own high-water mark: `max(trades.timestamp)` over `is_fill = false` rows (the daily-P&L rows the cron itself writes), floored to its UTC day. No such row -> `None` (full reach, the safe over-fetch direction, matching today's `None` semantics). The cron already knows the strategy ids before the loop (`_marker_strategy_ids`, `:1661`), so read the high-water beside the marker lookup, one small query per marker-less strategy (index `idx_trades_strategy_timestamp (strategy_id, timestamp)` exists, `baseline.sql:13986`). On a read error, fail OPEN to `None` and record it in the envelope, like `strategy_cursor_lookup_error`. This path is NOT marker-derived, so `_resume_floor_ms` returns it unclamped (`:616`), which is what the gap needs, and `TestKeyCursorFallbackIsNeverClamped` (`tests/test_cron_router.py:3891`) pins exactly that property for the old fallback; re-point the fixture, keep the property.
- **After the first successful tick** each strategy has a marker (`tick_now`), so the fallback runs exactly once per strategy.
- **The runbook "seeding" step becomes a guarded PRE-TICK PROOF**, not a write: marker first; per strategy the newest `daily_pnl` age, `strategy_sync_cursors` row count (0), and the computed fallback floor; after the rehearsal tick, rows = 4 (or 5), newest `daily_pnl` age at most 1 day, no `strategy_cursor_window_clamped`. The before/after counts the roadmap asks for are all there.
- If the founder wants literal seed rows anyway, they only help for strategies whose gap is at most 30 days (the Bybit one) and are redundant with the fallback. Record this as a deliberate SC-2 amendment in CONTEXT and ROADMAP together (CLAUDE.md deviation policy). [ASSUMED: A1, the amendment needs orchestrator or founder acknowledgement]
- **If literal seed rows are still wanted, this is the guarded form** (a runbook write behind the marker guard, idempotent, with before/after counts read as separate marker-first SELECTs on `strategy_sync_cursors`). It is safe but only effective for rows at most 30 days old, which on PROD today is the Bybit row alone (15.6 days); the OKX rows at 51.6 and 139.6 days would be clamped:
```sql
__GUARD__
INSERT INTO strategy_sync_cursors (strategy_id, last_sync_at, updated_at)
SELECT s.id, date_trunc('day', max(t.timestamp)), now()
  FROM strategies s
  JOIN api_keys k ON k.id = s.api_key_id AND k.is_active AND k.disconnected_at IS NULL
  JOIN trades t ON t.strategy_id = s.id AND NOT t.is_fill
 WHERE k.exchange IN ('okx', 'bybit')
   AND s.status IN ('draft', 'pending_review', 'published', 'private')
 GROUP BY s.id
ON CONFLICT (strategy_id) DO NOTHING; -- WRITE
```
  `ON CONFLICT DO NOTHING` so a re-run never rewinds a marker the tick already advanced. A seeded marker must never be NEWER than the data it claims (that would reintroduce the skip), hence `date_trunc('day', max(...))` of the stored rows and nothing later.

### 4. SC-4 / D-05..D-07: recording the last successful trade fetch, and what renders it

WHERE strategy_id = ...` (never an upsert, so no stub `pending` row appears), stamped `tick_now` ONLY when `strategy_advances` is true (`cron.py:1227`: fetch not degraded and either idle or stored without an enqueue error). Deribit has its own transaction-log ledger (`deribit_ingest.py`), irrelevant here.

**So, for the five PROD strategies:** Bybit's gap (15.6 days) is inside native reach, so the ordinary tick recovers it. OKX strategies 3 and 5 (139.6 and 156.6 days) are 47 and 64 days beyond the 3-month archive. Strategy 2 (51.6 days) is inside it. Strategy 4 is on a disconnected key. So D-01 touches exactly two connected OKX strategies (one published) plus one on a disconnected key, and the days at stake are the roughly 47 and 64 days between each strategy's last stored row and the archive horizon.

**How a bills-derived daily return is built, and what a rebuild needs.** The machinery exists. `trades_to_daily_returns_with_status` reads daily-P&L rows (`price` carries the dollar P&L, `side` the sign), anchors on TODAY'S account balance as terminal NAV, rolls NAV backward (`NAV_{t-1} = NAV_t - pnl_t`) and chain-links a time-weighted return (`transforms.py:100-200`); `combine_realized_and_funding` adds funding and external flows, derives the base as `current_equity - total_pnl`, and always stamps `series_completeness = fill_derived_unproven` (`broker_dailies.py` docstring and registry). A rebuild beyond the 3-month horizon therefore needs three streams over the longer window: realized (bills `pnl + fee`, excluding funding), funding (type 8), and external flows. Flows are the hard part: the code takes them from deposit/withdrawal history whose retention is OKX 90 days / Bybit 365 days (`nav_twr.py:111-113`, `job_worker.py:5834`), so beyond 90 days it would need OKX bills type 1 (transfer) and related transfer types as the flow source, which no code does today. Bills carry realized cash effects only: unrealized P&L is absent, so the reconstructed NAV drifts from truth the further back it goes ("reconstruction error accrues into the distant past", `broker_dailies.py` docstring). Transfers must be EXCLUDED from P&L and INCLUDED as flows; fees included; funding included as its own stream.

**D-03 (mark a rebuilt day) options.**
1. Per-range provenance in `strategy_analytics.data_quality_flags` (for example `reconstructed_ranges: [{from, to, source: "okx_bills_history_archive"}]`), stamped by the derive. No schema change; precedent in `flow_coverage_incomplete`. Per range, not per row. **Recommended.**
2. A `source` column on `csv_daily_returns`. Per row, but that table has many readers and writers (`job_worker.py:6623`, `:9177`, key-mode and composite writers) and a migration on it is the costly kind.
3. A new `series_completeness` value. Rejected: that registry is producer-only and the TypeScript admissibility allow-list is a hand-typed subset, so a new value would make the factsheets non-publishable by default.
`trades` cannot carry it: the table has no source column and `sync_trades` inserts a fixed column list without `raw_data` (`sync_trades.sql`).

**D-04 (overlap reconciliation).** Because OKX trade rows are already bills, the "both exist" comparison is bills against bills unless a second, independent source is used. The independent source on the 3-month overlap is the stored raw fills (OKX fills carry `fillPnl` and `fee`; `_trim_raw_data` may drop them, verify before relying on it). Reconcile per UTC day: `sum(bills pnl + fee, non-funding)` against `sum(fillPnl + fee)`; a disagreement beyond a tolerance that is CALIBRATED on the measured overlap (do not invent a number) fails the job loud with the date range and both totals, error kind permanent, and neither value is written. Trade-derived wins on a tie, per D-04.

**Verdict.** **D-01 does not fit this phase. Split it into its own follow-on phase** (CONTEXT: "splitting the bills rebuild into its own plan wave, or into a follow-on phase booked with `/gsd-phase --insert`, is allowed"). It is not dropped. Reasons, in order of weight:
1. It is an async two-phase job: apply, wait 2 to 3 hours, fetch a link valid for 5.5 hours, download, parse. That cannot run inside `/cron-sync` (60 s per key) or a 15-minute handler (`TIMEOUT_PER_KIND["derive_broker_dailies"] = 15 * 60`). It needs a durable job with a deferred second step; `compute_jobs.kind` is a CHECK-constrained set (`baseline.sql:1372-1420`), so a new kind is a migration, and the `compute_jobs_kind_target_coherence` constraint needs a matching arm.
2. It needs a new flow source (bills transfers) for any window beyond the 90-day deposit retention; without it the rebuilt NAV and every return built on it are wrong in a way the existing coverage-terminus flag would not describe.
3. It touches money-math that feeds published factsheets (two of the three affected strategies are published). D-01 itself records the reversibility as costly. That deserves its own verification gate and a founder review of the rebuilt numbers before they publish.
4. It is OKX-only and affects two connected strategies. The cron, cursor, badge and ADR work in this phase is independent of it and delivers the daily-sync fix to all four connected keys.
5. D-04 needs an independent second source and a calibrated tolerance, which needs measurement on real overlap data, not guesswork at plan time.

What THIS phase does instead for D-01/D-02: the runbook records, per strategy, the pre-tick high-water and the post-tick earliest new row (the named, dated gap); nothing is filled or interpolated; the badge and factsheet state what is current. The follow-on phase reads that pair as its work list. Suggested follow-on name: OKXHISTORY, booked with `/gsd-phase --insert 167.1.2.2.2`.

## Common Pitfalls

### Pitfall 1: seed rows are clamped, so a seeded gap silently shrinks to 30 days
**What goes wrong:** the planner follows SC-2 literally; three of five gaps are cut to 30 days. **Why:** `_resume_floor_ms` clamps marker-derived floors (`cron.py:631`). **Avoid:** data-derived fallback (Section 2). **Warning signs:** `strategy_cursor_window_clamped` in the envelope; floor age exactly 30.0 days.

### Pitfall 2: the cursor day is re-written with a partial day
**What goes wrong:** every tick loses the pre-cursor slice of the cursor day's P&L. **Why:** instant-aligned fetch, day-aligned delete-and-insert. **Avoid:** floor `since_ms` to 00:00 UTC. **Warning signs:** a day's stored P&L smaller than the venue's bills for that day by exactly the early-morning part. Test: cursor 04:30, assert the venue call's `begin` equals 00:00 of that day.

### Pitfall 3: the unfiltered selector
**What goes wrong:** disconnected accounts are read, allocator balances overwritten, `revoked` pinned at 5, 9-minute worst case beats Railway's idle limit. **Avoid:** Section 5 filter.

### Pitfall 4: the first derive replaces a published series
**What goes wrong:** for strategies with 0 `csv_daily_returns` rows (three of four OKX), `run_csv_strategy_analytics` reads only that table (`analytics_runner.py:1225-1276`, `:1328`), so the series after the first tick is whatever the venue still serves (about 3 months), and the 25 to 73 earlier published points disappear from `returns_series`. **Avoid:** a founder decision before the first tick (Open Questions). [ASSUMED: A5, not run end to end]

### Pitfall 5: rollout window
Code deploys on CI green; migrations apply separately. The stamp write and the tick must tolerate the column / function being absent (once-per-process warning, envelope field).

### Pitfall 6: TEST is empty of data
Both migrations verify shape only (no count-based `RAISE`), or a PROD deploy can be blocked by TEST.

### Pitfall 7: reading the wrong clock
Do not "fix" the badge by switching to `last_sync_at` (the poll's) or `last_fetched_trade_timestamp` (ahead of the data on PROD).

### Pitfall 8: pg_net visibility is six hours
The rehearsal body is purged after `pg_net.ttl = 6 hours`; read it in the same session.

### Pitfall 9: empty trades is not always idle
`strategy_advances` treats `not trades and not fetch_degraded` as "idle, advance". The Bybit arm previously swallowed errors without the degraded flag (`exchange.py:1990-2016`, now stamped). Keep the 164.5.1.4 tests green; do not add a new swallow.

```python
# routers/cron.py -- replaces "return key_cursor" as the ABSENT-marker fallback source
def _high_water_floor(iso_ts: str | None) -> str | None:
    """UTC-midnight of the strategy's newest stored daily-P&L row, or None (full reach)."""
    if iso_ts is None:
        return None
    dt = datetime.fromisoformat(iso_ts.replace("Z", "+00:00")).astimezone(timezone.utc)
```

```python
def _floor_to_utc_day_ms(ms: int | None) -> int | None:
    if ms is None:
        return None
    return ms - (ms % 86_400_000)
```

### Rehearsal read (SQL; counts and a duration only, marker first)
```sql
WITH m AS (SELECT (shobj_description(oid,'pg_database') LIKE '%PRODUCTION%')::int AS marker_is_prod
             FROM pg_database WHERE datname = current_database())
SELECT m.marker_is_prod, r.status_code, r.timed_out,
       (r.content::jsonb ->> 'duration_s') AS duration_s,
       (r.content::jsonb ->> 'total_keys') AS total_keys,
       (r.content::jsonb ->> 'revoked')    AS revoked
  FROM m LEFT JOIN net._http_response r ON true
 ORDER BY r.created DESC NULLS LAST LIMIT 1;
```
