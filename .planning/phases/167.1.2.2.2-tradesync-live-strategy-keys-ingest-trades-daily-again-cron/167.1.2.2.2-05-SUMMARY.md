# Phase 167.1.2.2.2 Plan 05: TRADESYNC resume window and trades_fetched_at stamp Summary

**A marker-less strategy now resumes from 00:00 UTC of its own newest stored daily-P&L day (unclamped, fills ignored, fail-open and recorded), the 04:00 poll's `last_sync_at` can no longer move any strategy's window, and `strategy_analytics.trades_fetched_at` is stamped for exactly the strategies whose trades the tick truly fetched.**

## What was built

`analytics-service/routers/cron.py`:

- `_load_strategy_high_waters(supabase, ids)`: one `trades` read per marker-less strategy (`select("timestamp")`, `.eq("strategy_id")`, `.eq("is_fill", False)`, `.order("timestamp", desc=True)`, `.limit(1)`), day-floored to ISO. A read or parse error maps that strategy to `None` (full reach), is logged with the traceback, and returns an error string. `cron_sync` attaches the result as `row["strategy_high_waters"]` beside `strategy_cursors` and surfaces `strategy_high_water_lookup_error` in the response.
- `_strategy_resume_point(strategy_id, strategy_cursors, strategy_high_waters)`: the three-state membership rule is unchanged (absent / present-NULL / present-timestamp); the absent state reads the high-water, and a strategy with no entry is full reach. The key cursor is not an input. `_resume_floor_ms` gained a keyword-only `strategy_high_waters`; its non-marker floor stays on the unclamped path, and its no-eligible-strategy branch still reads the key cursor (plan 06 owns making it unreachable).
- `_floor_to_utc_day_ms`, applied once to the value handed to `fetch_all_trades` (marker-derived and non-marker alike; `None` stays `None`).
- Held-absent rule in the hold-write: a strategy held on a tick where it was absent from `strategy_cursors` gets no row but stays in `held_strategy_ids`, so the envelope and the warning still name it. A present marker holds exactly as before.
- Stamp: after the marker write, one single-column `update({"trades_fetched_at": marker_now}).in_("strategy_id", advancing_ids)` on `strategy_analytics`, never an upsert, best-effort. Envelope: `trades_fetched_at_stamped` (rows RETURNED), `trades_fetched_at_unstamped` (shortfall, with a warning), `trades_fetched_at_stamp_error` (per key and aggregated at the top of the response). A code comment names `strategy_analytics_stamp_computing_started_trigger` and states the stamp is accepted on every row state.

`analytics-service/tests/test_cron_router.py`:

- `_make_mock_supabase_for_cron_sync` gained explicit capturing branches (PATTERNS correction 7): a `trades` fake that APPLIES the filters it is given (so a dropped `is_fill` filter changes the answer) and a STRICT `strategy_analytics` fake that supports `.in_` and nothing else. Captures: `trades_queries`, `strategy_analytics_updates`, `strategy_analytics_upserts`. `_make_key_row` gained `strategy_high_waters`.
- New classes: `TestFallbackIgnoresPollOverwrittenKeyCursor`, `TestFetchWindowFloorsToUtcMidnight`, `TestHighWaterIgnoresFillRows`, `TestHighWaterLookupFailsOpen`, `TestHeldFirstTickPreservesAbsentMarker`, `TestTradesFetchedAtStampedOnlyOnAdvance`. Instants are typed literals wherever the clamp allows (`1778112000000` = 2026-05-07T00:00Z, `1786492800000` = 2026-08-12T00:00Z); the two relative-date arms derive their expectation from the same datetime the input was built from, never from `routers.cron`.

## Residuals and not run

- **Not run:** the database trigger behaviour of the stamp (`computing`/NULL `computing_started_at`, stale stamp). Lane arm, owned by `[167.1.2.2.2-PROVENANCE-GATE-RESIDUALS]` item 5.
- **Not run:** anything against PROD or TEST (the plan required no read). The high-water query was exercised only against the fake `trades` table, which mirrors the filters but not PostgREST's timestamp formatting; the loader parses `fromisoformat` with a `Z`-to-offset replace and treats a parse failure as a failed read.
- **Residual, accepted and documented in the code comment:** a strategy whose store succeeds but whose recompute enqueue fails, with no prior marker, writes no hold row. Next tick its high-water is the newest stored day, and the floor is that whole day, so the day is re-fetched, re-stored and the enqueue re-attempted. This relies on the venue returning that day's row again; `sync_trades` and `enqueue_compute_job` are idempotent either way.
- **Plan 06 coupling:** the no-eligible-strategy branch of `_resume_floor_ms` still parses the key cursor; plan 06's selector filter and its test are what make it unreachable from the route.
- The per-strategy high-water reads are sequential synchronous calls (4 strategies on PROD today), matching the neighbouring marker lookup's style. They scale linearly with strategy count.
