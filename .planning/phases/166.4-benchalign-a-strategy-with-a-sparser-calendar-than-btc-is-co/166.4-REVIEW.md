## Summary

This round re-reviews the phase after the round-1 fix commits `d1d1fc077` (round-1 WR-01),

"round-1 WR-xx / IN-xx".

**Status of the round-1 findings**

- **Round-1 WR-01: closed for the production shape.** Production's benchmark comes only from
  `get_benchmark_returns("BTC")`, which serves the full naive 1000-day series, never sliced to the
  strategy's dates. Against that series, `traded` is all seven weekdays, so both the dropped

  `tests/test_benchalign.py`, `tests/test_metrics_parity.py`, `tests/test_qstats_gate.py` and
  `tests/test_metrics.py` give 418 passed. The fix has two new weaknesses outside the production
  shape. WR-01 and WR-02 below cover them.
- **Round-1 WR-02: closed.** `_benchmark_pair` maps a strategy ±inf to NaN once, and every fan-out
  metric, both r_squared helpers and the rolling leg read that output. **Correction to the fix
  report's record:** its note that "in `_rolling_greeks` the former inf row now reaches that
  function's existing frame `fillna(0)` as NaN" does not describe a behaviour change.
  `_rolling_greeks` already ran the strategy leg through `_prepared_returns_no_guess`, which does
  `replace([inf, -inf], NaN)` and then `fillna(0)`, before the fix. So the rolling values are
  unchanged.
- **Round-1 IN-01..IN-04:** these were outside the fix scope and are still open at HEAD. They are
  carried forward as IN-01..IN-04 below, each re-checked against the current source.

**D-A check.** The new rule adds no fill. It only unpairs more intervals, so D-A's "never
back/forward-filled across a gap" still holds everywhere. Both warnings are the other failure mode:
intervals that are silently unpaired (WR-01), or paired against the wrong calendar (WR-02), in
input domains the helper accepts but production does not reach today.

## Warnings

### WR-01: `expected` floors UTC-converted stamps to a day number, so a same-zone pair in a UTC+0/+1 DST zone loses intervals silently (regression from `d1d1fc077`)

**File:** `analytics-service/services/metrics.py` (`_interval_matched_benchmark`, the
`day_num` / `traded` block)
**Issue:** `_benchmark_pair` hands the helper a strategy index that `_tz_naive_like_qs` has
already converted to UTC and made naive. `_refuse_mismatched_day_labels` accepts a pair whose legs
share one zone, for example both `Europe/London`. In that zone, local midnight is 23:00 UTC on the
previous day under BST and 00:00 UTC under GMT. `day_num` is
`astype("datetime64[D]")`, which floors the stamp, so the day number jumps by 0 or 2 across each
DST change. `traded` is taken from the same floored `b.index.dayofweek`, so a London business-day
benchmark is read as trading Sunday to Friday. `count` comes from timestamp intervals and is not
affected. The result is `count != expected` on intervals where nothing is missing.

I compared this against the pre-fix module (`a7bc6da79`), same-zone pairs, 2025:

| zone | pair | pre-fix paired | post-fix paired |
|---|---|---|---|
| Europe/London | dense daily vs 7-day | 275/275 | 273/275 (both DST days) |
| Europe/London | weekday vs business-day | 250/250 | **202/250** (48 intervals, mostly Mondays) |
| Europe/Berlin, Asia/Tokyo, America/New_York | weekday vs business-day | 250/250 | 250/250 (the offset never crosses UTC midnight between seasons) |
| Europe/Berlin | dense daily vs 7-day | 275/275 | 275/275 |

No log line is written. The metrics are computed on a pair up to 19% shorter than the pre-fix
pair.

**Reachability:** not reachable from production today. The only production benchmark is the naive
BTC series from `get_benchmark_returns`, and `_refuse_mismatched_day_labels` refuses a naive BTC
leg against a non-UTC aware strategy. The helper's accepted input domain does include same-zone
aware pairs, though, and `_refuse_mismatched_day_labels`' docstring says so. That is why this is a
WARNING and not a CRITICAL.
**Fix:** Derive the day number from each stamp's local date, not from a floor of its UTC instant.
The root-cause option is to take `day_num` and the benchmark weekdays from the wall clock BEFORE
`_benchmark_pair` drops the zone (`tz_localize(None)` rather than `tz_convert("UTC")`), and pass
them into the helper. A smaller option is nearest-day rounding:
```python
day_num = (
    pd.DatetimeIndex(index).round("D").values.astype("datetime64[D]").astype("int64")
)
traded[np.unique(np.asarray(b.index.round("D").dayofweek))] = True
```
I checked `round("D")` against local dates in London (BST 23:00 of the previous day), Tokyo (15:00
of the previous day) and New York (04:00/05:00 of the same day), and it matches in all three. On
naive midnight stamps it is the identity, so SC4 is unaffected. It still fails for zones at about
±12h (for example `Pacific/Auckland`, +12/+13), where rounding lands on a different side between
seasons. That residual is why the wall-clock option is the better one. Add a same-zone London
business-day test that asserts no interval is lost.

### WR-02: The benchmark's calendar is inferred from whichever weekdays happen to appear, with no evidence floor and no log

**File:** `analytics-service/services/metrics.py` (`_interval_matched_benchmark`,
`traded[np.unique(np.asarray(b.index.dayofweek))] = True`)
**Issue:** The rule that closes round-1 WR-01 depends on `traded`, and `traded` is whatever
weekdays are present anywhere in `b`. Three probes, all silent, each against the current HEAD:

1. **The new rule does not catch a weekday-only slice of 7-day BTC (not caused by the fix).** The
   benchmark is 60 contiguous days with the weekend rows removed, against a weekday strategy.
   `traded` becomes Monday to Friday, every Monday is paired, and the paired value is BTC's
   Sunday-to-Monday DAILY return (`b4[monday] == full[monday]`), which is exactly the M1 pairing
   D-A supersedes. The pre-fix engine at `a7bc6da79` pairs it the same way (measured), so this is
   not a regression. A DECLARED seven-day calendar would have caught it (`expected=3, count=1`),
   and the inferred one cannot. The fix report already concedes that "a BTC window without any
   weekend date would be read as weekday-only".
2. **A business-day benchmark holiday unpairs a correct interval (regression from `d1d1fc077`).** The benchmark is
   `bdate_range` prices with Good Friday dropped, then `pct_change().dropna()`, and the strategy
   is on the same calendar. The (Thursday, Monday] interval gives `expected=2, count=1` and is
   unpaired. Its stored Monday return equals the true Thursday-to-Monday price ratio, and the
   pre-fix code paired it correctly.
3. **One stray weekend row flips the calendar for the whole series (regression from `d1d1fc077`;
   before the fix it was one more row to compound).** Adding one Saturday row to a
   business-day benchmark sets `traded[5]`, and from then on every (Friday, Monday] interval needs a
   Saturday return. The result is 100 of 124 weekday intervals paired, against 124 of 124 without
   that row.

**Reachability:** not reachable from production today. `get_benchmark_returns` raises for any
symbol other than BTC and always serves the 1000-day series, so `traded` is always all seven.
Probes 1 to 3 need a caller that slices BTC, or a non-BTC benchmark. The inference exists only to
keep the `pd.bdate_range` fixtures green (the golden pair and the `tests/test_metrics_parity.py`
pairs). A hard-coded seven-day calendar would unpair every Monday of those fixtures and break SC4.
So the code carries production-irrelevant inference that has its own failure modes.
**Fix:** The cheapest fix that stops the silence is to log the inferred weekday set at WARNING
whenever it is not all seven. That is what lets probe 1 surface, and it changes no values. The
stronger fix is to declare the calendar instead of inferring it (for example a
`benchmark_calendar_days: Literal[5, 7] = 7`). Be aware of its cost:
`tests/test_metrics_parity.py` enters through `compute_all_metrics(...)`, not through
`_benchmark_pair`, so a declared calendar would need a new keyword on the public compute function
that exists only for the business-day fixtures. Do not REFUSE on thin evidence: a raise inside the
fan-out `try` would blank every benchmark metric. Add a business-day test with a missing interior weekday (for
example, a Wednesday dropped inside a weekly strategy's interval), because the business-day branch
of the new rule is now pinned only indirectly by SC4 golden (see IN-06).

## Info

production entry point sorts (`derive_basis_series` hands a caller's `scalar_returns` through as
given)")
**Issue:** This is unchanged at HEAD. `compute_all_metrics` raises on a non-monotonic index before
any benchmark code runs, so no production caller reaches this function unsorted.

### IN-02: The "ONE pair" is still rebuilt independently four times per compute (carried from round-1 IN-02)

**File:** `analytics-service/services/metrics.py` (`compute_all_metrics` fan-out, `_r_squared`,
`_r_squared_pair_varies`, `_rolling_alpha_beta`)
**Issue:** Each site calls `_benchmark_pair(returns, benchmark_returns)` again. Round-1 WR-02 was
exactly this coupling failing: one site pre-processed a leg and the others did not. Moving the inf
mapping into `_benchmark_pair` repaired that instance, not the structure.
**Fix:** Build the pair once in `compute_all_metrics` and pass it down.

### IN-04: `strategy_calendar_is_sparse` still claims "exactly the condition", and an emptied pair is still silent (carried from round-1 IN-04)

### IN-05: The CHANGELOG entry does not describe the round-1 WR-01 behaviour change for sparse strategies

**File:** `CHANGELOG.md` (`## [0.108.0.0]`, the SC5 bullet "When BTC itself has a gap (the
stale-fallback path), the day after the gap is now unpaired")
**Issue:** That line covers dense series only. Since `d1d1fc077`, a SPARSE strategy's interval
that spans a BTC price gap is unpaired as well, even though `pct_change` over a price gap would
have telescoped correctly. The fix report deferred this line to the ship re-fold. This file is
outside the review's file list, so the finding is recorded but not graded.
**Fix:** Add one bullet at the ship re-fold: sparse intervals that contain any missing BTC date
are now unpaired, whether the date is missing as a price or as a return.

### IN-06: The business-day branch of the new interior-gap rule has no direct test

**File:** `analytics-service/tests/test_benchalign.py`
**Issue:** The only new test runs against a seven-day benchmark. The fix report explains the
adaptation with the claim that "a business-day pair still pairs its Mondays (expected 1, count 1)",
and that claim is pinned only indirectly, through SC4 golden parity. No test drops an interior
weekday from a business-day benchmark, and no test pins a same-zone tz-aware pair. Both gaps are
where WR-01 and WR-02 live.
**Fix:** Add both tests (see the fixes for WR-01 and WR-02).
