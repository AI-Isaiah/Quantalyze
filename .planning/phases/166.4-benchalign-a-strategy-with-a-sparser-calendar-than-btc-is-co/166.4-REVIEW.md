## Warnings

### WR-01: A missing benchmark RETURN inside a multi-day interval is compounded as if it were 0, which is a silent fill across a gap

**File:** `analytics-service/services/metrics.py` (`_interval_matched_benchmark`)
**Issue:** A sparse interval k is paired when t_{k-1} and t_k are both closes and no benchmark
value in the interval is non-finite. Nothing checks that the benchmark dates inside the interval
are complete. The docstring says the value "telescopes to price[t_k] / price[t_{k-1}] - 1 even if
BTC misses a day strictly inside the interval". That is true only when the move over the missing
day is carried by the next stored return (`pct_change` over a price gap). When a RETURN row is
missing instead, that move is silently dropped, which is the same as filling the gap with a 0
return. D-A forbids that ("a benchmark gap must be skipped, never back/forward-filled across").

Probe: 60 contiguous daily benchmark returns, one Saturday return row dropped
(`b.drop(sat)`), and a weekday strategy. The Monday interval is **paired** with 0.031027…, but the
true Friday-to-Monday move is 0.003428…. Nothing is logged.

This shape is reachable, and the SC2 tests treat it as a gap. The gap fixture of
`test_benchalign_gap_absent_close_unpairs_both_adjacent_intervals` drops a RETURN row
(`benchmark.drop(d)`). A dense strategy is protected by the both-endpoints rule, but no test puts a
missing row strictly inside a SPARSE interval. The same shape can also come from production. With
the pinned pandas 3.0.3, `prices_to_returns` (`pct_change().dropna()`, no fill) turns one NaN close
into two dropped return rows. If the NaN falls on a Saturday, the Monday return is Sunday-to-Monday
only, and a weekday strategy's Friday-to-Monday interval is paired with that one-day move. So a
dense strategy and a sparse strategy treat the same BTC gap differently: the dense one leaves it
unpaired, the sparse one pairs a partial move.
**Fix:** The helper takes returns, so it cannot tell a missing price from a missing return. Take
the conservative reading of D-A and treat any interior benchmark gap as a gap:
```python
# after computing `count` per interval:
span_days = np.zeros(n, dtype="int64")
span_days[1:] = ((index[1:] - index[:-1]) / pd.Timedelta(days=1)).astype("int64")
contiguous = count == span_days          # every calendar day in (t_{k-1}, t_k] carries a return
paired = is_close & ~any_nan & (count >= 1) & contiguous
```
(Check that this keeps SC4 dense parity. Every dense interval has span 1 and count 1, so it
should.) Alternatively, move the pairing onto BTC PRICES at the call site, which D-A's formula
allows ("Claude's Discretion"). Either way, add a test with a missing row strictly inside a
weekday interval, and correct the telescoping sentence in the docstring.

### WR-02: r_squared and correlation/beta read different rows when the strategy carries ±inf, so SC1 "r_squared = correlation²" does not hold

**File:** `analytics-service/services/metrics.py` (`_r_squared`, `_r_squared_pair_varies`, the
`compute_all_metrics` benchmark fan-out)
**Issue:** `_r_squared` and `_r_squared_pair_varies` map the strategy's ±inf to NaN and drop the
row (`r.replace([np.inf, -np.inf], np.nan)`, then `dropna()`). The fan-out feeds the raw
`aligned_returns` to `_greeks_no_guess`, `aligned_returns.corr(...)` and the excess series without
that step. `_benchmark_pair`'s docstring says it is "the ONE pair every benchmark-relative metric
reads", and `_r_squared`'s docstring says r_squared is "the squared correlation of the same pair
the persisted `correlation` is computed on". Probe: a 200-day dense strategy with one `+inf` day
gives `correlation=None`, `beta=None` and `r_squared=0.0268` with `r_squared_status="ok"`. The
persisted row says R² is defined while correlation and beta are not. The split existed before
166.4 (the old r_squared zero-filled the inf). This phase re-asserts the invariant in prose without
closing it.
**Fix:** Sanitise the strategy leg once, in `_benchmark_pair`, so every metric sees the same rows:
```python
r = _tz_naive_like_qs(returns).sort_index().replace([np.inf, -np.inf], np.nan)
```
Then drop the per-call `.replace(...)` in `_r_squared` and `_r_squared_pair_varies`. Add the ±inf
case to `test_benchalign_one_pairing_r_squared_is_correlation_squared`.

## Info

### IN-01: `_benchmark_pair`'s sort rationale names a path that cannot reach it unsorted

**File:** `analytics-service/services/metrics.py` (`_benchmark_pair` docstring)
**Issue:** The docstring justifies the sort with "`derive_basis_series` hands a caller's
`scalar_returns` through as given". But `derive_basis_series` calls `compute_all_metrics`, which
raises `ValueError` on a non-monotonic index before any benchmark code runs. `compute_qstats_scalars`
is called only from `compute_all_metrics`. The sort is a defensive guard with no production caller
that needs it, and the stated reason sends a reader looking for one.
**Fix:** Reword it as a defensive precondition for `np.searchsorted` (direct callers and tests)
and drop the `derive_basis_series` claim.

### IN-02: "ONE pair" is rebuilt independently four times per compute

**File:** `analytics-service/services/metrics.py` (`compute_all_metrics`, `_r_squared_pair_varies`,
`_r_squared`, `_rolling_alpha_beta`)
**Issue:** `_benchmark_pair(returns, benchmark_returns)` runs separately in the fan-out, in both
r_squared helpers and in the rolling leg. The four results match today only because each call site
passes the same raw inputs to a deterministic function. A future caller that pre-processes one leg
at one site (as WR-02's inf handling already does in two of the four) splits the "one pair"
silently. This is a structural coupling, not a performance note.
**Fix:** Build the pair once in `compute_all_metrics` and pass it to `compute_qstats_scalars`' R²
block and `_rolling_alpha_beta`, or have one private function return every derived view.

### IN-03: Test-module coupling contradicts the fixture module's own rule, and fixtures are duplicated

**File:** `analytics-service/tests/test_benchalign.py`, `analytics-service/tests/benchalign_fixtures.py`
**Issue:** `benchalign_fixtures.py` says "A test module imports fixtures from here, never from
another test module". `test_benchalign.py` imports `_q166_calendar_mismatch`,
`_q166_raw_pair_regression`, `_q166_windowed_regression`, `_Q166_ROLLING_WINDOW` and
`_Q166_WRITTEN_TOLERANCE` from `tests.test_metrics`. `_contiguous_btc` in `test_benchalign.py`
duplicates `_contiguous_benchmark` in the fixtures module, and `_dense_daily` duplicates `_daily`.
**Fix:** Move the shared `_q166_*` builders and constants into a fixtures module, import them from
there in both test files, and remove the duplicate builders.

### IN-04: `strategy_calendar_is_sparse` overstates "exactly the condition", and an emptied pair is silent

**File:** `analytics-service/services/metrics.py` (`strategy_calendar_is_sparse`, `compute_all_metrics`
fan-out)
**Issue:** The docstring says that, against a contiguous benchmark, the predicate is "exactly the
condition under which the 166.4 D-A interval pair differs from a daily inner join". An index stamped
at a non-midnight time is not sparse, yet it pairs to zero rows. Probe: the same dense strategy
shifted to 23:59 left every benchmark scalar absent and gave `r_squared_status="error"`. A sub-daily
index also breaks the claim. The empty or 1-row pair is not logged either: the fan-out skips on
`len(aligned_returns) > 1` without a WARNING, and `_r_squared_pair_varies` returns False, which
writes `error` with no log. Both behaviours existed before (the inner join was also empty), so this
is not a regression. But 166.3 will select on this predicate, and the sentence claims more than the
code guarantees.
**Fix:** Qualify the sentence ("for a midnight-stamped daily index"). Consider a DEBUG or INFO line
in the fan-out that gives paired versus strategy row counts when the pair is materially shorter
than the strategy, so a strategy whose benchmark metrics vanish has a signal.
