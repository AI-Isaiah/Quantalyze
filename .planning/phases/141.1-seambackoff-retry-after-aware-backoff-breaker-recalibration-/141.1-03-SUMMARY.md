## Accomplishments

- **Closed D-14c / SC-P.** `test_seam06_resync_dedups_on_strategy_scoped_draft_key` only ever asserted that `status='draft'` appears among the pre-check's filters — a *shape* assertion against a scripted double. It proves the filter is **sent**, not that it **matters**. The new pin proves it matters.
- **Named the defect the pin catches.** Removing `.eq("status", "draft")` makes the pre-check key on `(strategy_id, flow_type)` alone. Every strategy that has *ever* synced then carries a matching historical verification, so every future resync is answered `WIZARD_DUPLICATE` — and, because a `completed` row is not in `_RESUMABLE_VERIFICATION_STATUSES`, is not even re-enqueued (`queued: false`). The user's resync silently never runs. That is a total loss of the resync feature, and pre-141.1 it would have shipped green.
- **Made the pin non-vacuous** with a positive control that is byte-identical except for the seeded row's `status`.
- **Held the D-03 fence.** `git diff --stat` shows exactly one file, `analytics-service/tests/test_process_key.py`, purely additive.

## Decisions Made

**OQ-2 (owed at plan time) — RESOLVED: test files are outside the D-03 zero-Python fence.**
The D-03 fence exists to keep 141.1 from changing production service behaviour. A test file changes no service behaviour; Phase 141 itself shipped Python tests under the same constraint. The pin therefore lives in `analytics-service/tests/test_process_key.py` — the Python home SC-P names — rather than being deflected into an SQL gate where it could not exercise the FastAPI route at all. The fence is **verified, not assumed**: `git diff --stat` is an acceptance criterion and shows one test file.

**The pin runs against the stateful double, not the scripted one.** `_RecordingSupabase` (used by the neighbouring shape pin) replays scripted responses and cannot honour `.eq()`, so against it the `status` filter is unobservable by construction. Reusing `_StatefulSupabase` from `tests/test_resync_draft_dedup.py` was mandatory for the pin to have any teeth — and it was imported, not re-implemented, per the plan.

## Issues Encountered

**Potential vacuous-pass hazard, investigated and cleared.** `test_process_key.py` pops and re-imports `routers.process_key` at module scope, while the imported harness builds its client from `main.app`. If `main` had already bound the pre-pop module object, the `patch("routers.process_key.get_supabase")` in the new tests would target a module the running app does not use, and both new tests could pass without ever reaching the pre-check. Cleared two ways: (a) the positive control would fail if the patch had not taken — it passes; (b) the mutation was re-run with `main` deliberately imported first and still reddens. Recorded here so a future reader does not have to re-derive it.
