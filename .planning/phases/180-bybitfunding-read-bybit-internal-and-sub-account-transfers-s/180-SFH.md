## HIGH

### H-1 `services/ccxt_flow_fetch.py:104-115`: the Bybit cursor can be lost inside ccxt, and the loop then ends silently (partial list returned as complete)

Evidence. `_read_bybit_transfer_window` reads `nextPageCursor` from `row["info"]` of the PARSED page (`_bybit_next_cursor`, :40). ccxt (`add_pagination_cursor_to_result`, ccxt `bybit.py`) writes the cursor onto the FIRST RAW row only (`data[0]['nextPageCursor']`, the newest). `parse_transactions(data, currency, since, limit)` then sorts and runs `filter_by_since_limit`, which keeps a row only if `value and value >= since` (ccxt `base/exchange.py` `filter_by_since_limit`). Bybit's `parse_transaction` stamp is `createTime`, else `successAt`. A deposit row whose `successAt` is `"0"`/empty (any not-yet-successful or failed deposit, if Bybit returns them in the record list) has timestamp 0, is falsy, and is dropped. If that dropped row is the cursor carrier, the cursor is gone from the page, `_bybit_next_cursor` returns None and line 114-115 `return True` ends the window as "done" after page 1 (a window with rows past page 1 loses them). If every row of the page is dropped, `if not page: return True` (:104) does the same even though the raw page was full and carried a cursor. This is exactly the bug class D-02 fixes (a window silently cut after page 1), re-introduced through a different door, and it reaches every `fetch_ccxt_transfers` caller (derive broker dailies, stitch composite, nav marks).

I checked against the local ccxt 4.5.64; the repo pins 4.5.88, so re-confirm `add_pagination_cursor_to_result` and `filter_by_since_limit` there. Whether Bybit really serves `successAt: "0"` rows on the deposit record is a venue fact I could not measure here, so the trigger is probable, not proven.

The test double hides it: `_NewestFirstBybitTransfers` (`tests/test_ccxt_flow_fetch.py`) puts the cursor on `page[-1]` after the page is built, never filters, and never serves a stamp-0 row. And `test_a_bybit_page_without_a_cursor_ends_the_window` (`tests/test_ccxt_flow_fetch.py:213`) asserts that a 50-row page with no cursor out of 120 rows returns 50 rows and 1 call: it pins the silent truncation as the intended behaviour. That test cannot go red on the defect.

Hidden errors: a lost cursor, a stamp-0 row, a ccxt that stops attaching the cursor in a later version, a page of exactly 50 rows with no cursor, all read as "last page".

User impact: deposits/withdrawals missing from the flow-aware TWR base with no signal, the failure mode WR-04 was written to prevent.

Minimal fix. Do not rely on a row's `info` surviving ccxt's filter. Either (a) call the raw `private_get_v5_asset_deposit_query_record` / `private_get_v5_asset_withdraw_query_record` and read `result.nextPageCursor` directly, as `bybit_unified_flows.py` does, or (b) keep `fetch_deposits` but treat "page empty OR (len(page) >= 50 and no cursor)" as `TransferPageStalled`-style refusal, and flip the test above to assert the raise. Option (b) can falsely refuse a window holding exactly 50 rows if Bybit omits the cursor on the last page, so prefer (a).

## MEDIUM

### M-1 `services/ccxt_flow_fetch.py:93,122-131`: the 1000-page ceiling logs a warning and returns True (a truncated list reads as complete)

The helper's docstring and the function docstring say "it never returns a short list". The ceiling path does exactly that: `logger.warning(...)` then `return True`, and the caller moves to the next window. A cursor cycle of length 2 or more (A, B, A, B; `nxt == cursor` only catches an immediate repeat, :116) walks 1000 pages and then returns a truncated list. The generic path's identical warning-only ceiling is pre-existing, but this branch is new code that claims the stronger contract, and the sibling reader added in the same phase raises at its ceiling.
Fix: `raise TransferPageStalled(...)` at the loop exit (same static text style), and track all seen cursors (`seen_cursors: set[str]`) instead of only the previous one.

### M-2 `services/bybit_unified_flows.py:182-193` (with `services/exchange_pagination.py:228-233`): a FULL page with no cursor ends the window silently

`stop_on_short_page=False`, so the walker stops on an empty page or an empty cursor. A page of 50 rows whose `nextPageCursor` is `""`/absent (or the cursor lost by a venue/proxy change) ends the window as complete although the venue may hold more. The module docstring promises "never returns a short list" but this one case is trusted. `tests/test_bybit_unified_flows.py` has no test for it (the nearest, `test_an_empty_page_ends_the_window_even_when_its_cursor_repeats`, covers the opposite case).
Fix: in `_fetch_page`, `if len(items) >= BYBIT_LOG_PAGE_SIZE and not next_cursor: raise _refuse(log_type, "a full page came back with no cursor")`, plus a RED test. Trade-off to confirm against the venue: if Bybit returns `""` on an exactly-full last page this refuses a good read; the fail-loud rule prefers that to a silent cut.

### M-3 `services/bybit_unified_flows.py:159-166`: the failure log carries venue text through a scrub that does not scrub free text

`logger.warning(... scrubbed=%s, scrub_freeform_string(str(exc)))`. `scrub_freeform_string` returns a string unchanged when it contains none of `:`, `=`, `.` (fast path, `services/redact.py`), and otherwise only redacts URL userinfo, sensitive key=value pairs and JWT shapes. A ccxt Bybit error is `bybit {"retCode":...,"retMsg":"...","result":{...},"retExtInfo":{...}}`; `retMsg`, uids, order/transfer ids and amounts pass through. This module's own docstring and `equity_reconstruction.py:6385-6389` state the convention for the crawl path: "The exception CLASS only: the venue's text is never logged here ... T-167.2.1.1.2-24". The line also fires for every transient fault (rate limit, network), at WARNING, per page. No test captures the log (`caplog`), so nothing would catch a leak; the tests feed `"fake-venue-text"` and only assert on the raised text.
Fix: log `type(exc).__name__`, the type and the window only (drop `scrubbed=`), and add a `caplog` assertion that a `fake-venue-text` exception message is absent. (There is precedent for `scrubbed=` in the sibling-key preflight at `equity_reconstruction.py:6350`; that is the older pattern, not the rule the crawl path states.)

### M-4 `services/equity_reconstruction.py:4184-4189`: a forced refusal for the reader's own failure loses its cause, and the cause is never logged

`except (..., BybitUnifiedFlowReadError): raise ForcedRebuildRefusedError("account_flow_source_unreadable") from None`. The reader's four refusals (non-object answer, repeated cursor, wrong-type row, page ceiling, plus the row-field refusals) carry static, safe text, but it is dropped by `from None` and never logged: the venue-exception branch logs inside `_fetch_page`, the reader's own `_refuse(...)` paths do not. The only trace is the later `reason=account_flow_source_unreadable` line (`:6389-6395`). An operator reading the post-deploy handoff cannot tell "the key lacks permission" from "the venue served a repeating cursor" from "the window exceeds 200 pages", and the runbook's action (record only) is the same for all of them.
Fix: before raising the refusal, `logger.warning("bybit unified flow read refused venue=bybit reason=%s", str(exc))` for `BybitUnifiedFlowReadError` (text is static by contract) and `type(exc).__name__` for the ccxt classes. Keep `from None`.

### M-5 `scripts/allocator_history_probe.py:781-790,792-822` (+ `bybit_transfers_cause` :1091): `bybit_unified_state` reads `read` when the read was refused or interrupted

The recorder wraps only the venue call. It sees an exception raised by the call or the shape of the answer. It does not see (a) the reader's own refusals after the call returned (repeated cursor, ceiling, wrong-type row, bad amount, a non-object row inside `list`), nor (b) a `CancelledError` (a `BaseException`, not caught by `except Exception`) from the crawl bound or a timeout hitting mid-read. In both cases `unified_calls > 0`, `unified_failure == "none"`, `unified_malformed == 0`, so `unified_state()` returns `read`, while `bybit_transfers_cause` for the same record says `flow_source_unreadable` (case a, via the refusal token) or `read_incomplete` (case b, by inference from `trade_calls == 0`). A record carrying `bybit_unified_state=read` next to a shut gate and an unreadable cause is self-contradictory, and the founder reads these fields at SC-3. In case (b) `bybit_unified_in_rows` is also a partial count under a `read` label.
Fix: in `_probe_account`, after computing `member_refusal`, `if member_refusal == _FLOW_SOURCE_REFUSAL and unified_state == "read": unified_state = "malformed"`; in `_recorded_log`, add `except asyncio.CancelledError: self.unified_failure = self.unified_failure if self.unified_failure != "none" else "Timeout"; raise` (the crawl bound is the only canceller). Add a test per case.

### M-6 `scripts/allocator_history_probe.py:1140-1176,1929,2018`: `bybit_funding_explained` can claim `unexplained` from one member's evidence

`first_funding = dict(fundings[0])` takes the FIRST measured Bybit member's evidence, while `unified_in_rows` is summed over all Bybit members and `trades_read` over ALL members including non-Bybit ones (`sum(trades_read(r.calls) for r in results)`). For an account with two Bybit keys (a master and a sub, the very topic of this phase) where member 2's evidence was never taken (the generic-failure branch of `_probe_member` sets `funding = None`, so only some members carry evidence and only the first of those is used), the verdict can be `unexplained` ("a source still unnamed") although member 2's inflow sources were never asked. A mixed-venue account's OKX trades also satisfy `trades_read >= 1` for a Bybit account with none. `bybit_evidence_members` discloses the count but the token itself is the decision input for the founder's rebuild call.
Fix: pass `bybit_evidence_members` and the Bybit-only trade count in, and return `unmeasured` unless `bybit_evidence_members == bybit_members` and `trades_read` counts Bybit members only (`sum(trades_read(r.calls) for r in bybit_results)`).

### M-7 `scripts/bybit_funding_record.py:343` (+ walker): the evidence walk coerces a non-string cursor to `""` and ends on a full page without a cursor, and the source still reads `read`

`return items, cursor if isinstance(cursor, str) else ""`: a `nextPageCursor` of the wrong type (int, dict) becomes "no more pages", where `bybit_unified_flows.py:179` refuses the same answer. A 50-row page with no cursor also ends the window as complete. The state is `read`, and these counts feed `bybit_funding_explained` (`off_edge`/`unexplained`) and the oldest-age/older-365d columns. A truncated evidence read therefore can print `unexplained` or an `older_365d` of 0 with `state=read`.
Fix: `if cursor is not None and not isinstance(cursor, str): raise EvidenceShapeError("evidence cursor is not a string")`, and in `_read_source._fetch_page` raise `EvidenceShapeError` when `len(items) >= EVIDENCE_PAGE_SIZE` and the cursor is empty (state `malformed`, counts still lower-bounded). Add the two RED tests next to `test_a_malformed_page_is_named_and_counts_nothing`.

## LOW

### L-1 `scripts/bybit_funding_record.py:543-554,447-482`: a `Timeout`/failed source prints numeric partial counts beside the state

The module says a source past its bound "is the state `Timeout` and never a count of 0". The walk is newest-first, so a timeout loses the OLDEST windows, which are the ones `older_365d` and `oldest_age_bucket` are about; `older_365d` prints `0` (and `oldest_age_bucket` a young bucket) with `state=Timeout`. `depth_bucket` does disclose how far back it answered, and the census documents "lower bound", so this is a reading hazard rather than a hidden error.
Fix: when `state != "read"`, emit `older_365d` and `oldest_age_bucket` as `field-absent`, keep `rows`/`other_status_rows`/`depth_bucket`.

### L-2 `scripts/allocator_history_probe.py:685-697`: `_log_rows` drops non-object list entries without counting them

Docstring: "A list entry that is not an object is dropped." `unified_malformed` is not incremented, so the recorder under-counts flows with no state change. The rebuild itself would refuse such a row (see M-5), so the loss is covered only when the refusal token is present.
Fix: return None (malformed) if any entry is not a Mapping.

### L-3 `services/bybit_unified_flows.py:211-220`: silent de-duplication of repeated `(type, id)` rows

A row served twice is collapsed with no count and no log. The comment says windows cannot overlap, so a repeat is a venue anomaly (or an id collision across currencies) worth a debug-level count. Dropping a distinct row that shares an id would under-count a flow silently.
Fix: count the skipped rows and `logger.warning("... duplicate_rows=%d", n)` when n > 0 (counts only).

### L-4 `services/ccxt_flow_fetch.py:34-37` / `services/job_worker.py:1198-1207`: `TransferPageStalled` has no `classify_exception` arm

The sibling `BybitUnifiedFlowReadError` is classified permanent; `TransferPageStalled` (also deterministic, also static text) is a `RuntimeError` and falls to `unknown`, which the queue retries. The live derive/composite jobs will re-run the full multi-window crawl until the retry budget ends. Loud, not silent, but inconsistent with the reasoning in the arm's own comment.
Fix: add `TransferPageStalled` to the same `isinstance` arm (or document why live callers should keep retrying).

### L-5 `services/bybit_unified_flows.py:36-43`: the Earn/staking limitation has no runtime signal

Documented, and the probe's census counts the candidate types, but the forced rebuild writes a curve whose level can be off by the staked amount with nothing in the job result or log; only the 5x implausibility bound stands behind it. Within the decisions recorded (orchestrator reading 3), so informational only.
Fix (optional): none for this phase; keep the booked follow-up.
