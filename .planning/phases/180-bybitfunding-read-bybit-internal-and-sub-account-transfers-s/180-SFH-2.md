## HIGH

### F-1 `services/ccxt_flow_fetch.py:114-143`: an empty RAW Bybit page that still carries a cursor is not treated as the end of the window; a sticky cursor raises `TransferPageStalled` on a valid read

Evidence. The H-1 fix tests the PARSED page: `if not page and nxt is None: return True`. A raw page with zero rows and a non-empty `nextPageCursor` therefore continues, and an empty page that repeats the cursor it was sent hits `if nxt in seen_cursors: raise TransferPageStalled`. Every other cursor walk in this phase ends on an empty page before it looks at the cursor: `walk_paginated` (`services/exchange_pagination.py`, `if res.is_empty: break` precedes the cursor test), `bybit_unified_flows._fetch_page` (`if items and next_cursor == req.cursor`, pinned by `test_an_empty_page_ends_the_window_even_when_its_cursor_repeats`), and the evidence walk. That the venue serves a cursor beside an empty list is the premise those tests encode, and ccxt's own `add_pagination_cursor_to_result` guards on `dataLength > 0` for the same reason. The OLD code could never see such a cursor (it read it off a parsed row, which an empty page does not have); the new raw read can, so this is a behaviour the fix created.

Reproduced with the test double (`_NewestFirstBybitTransfers(rows(3), cursors=["off:3","off:3", ...])`): page 1 returns 3 rows and a cursor, page 2 is empty and answers the same cursor: `RAISED TransferPageStalled calls 2`. With a fresh cursor on the empty page the window costs one extra call and then ends (`rows 3 calls 3`). Repro script: `<scratchpad>/repro_f1.py`.

Hidden errors: a valid, fully read window is turned into a hard failure of the derive, stitch and nav-mark jobs. Not silent, but it is a false refusal on the shared path every Bybit allocator uses, and `TransferPageStalled` has no `classify_exception` arm (round-1 L-4), so the queue retries it as `unknown` until its budget ends. A window ending on an exact multiple of 50 rows would trigger it on Bybit's last page if the venue echoes a cursor there.

User impact: Bybit broker dailies and composite NAV marks stop computing for an account whose last window ends this way; the operator sees a stalled-cursor message for a read that was complete.

Minimal fix. Decide the end on the raw rows, which the loop already has in hand:

```python
raw_rows = exchange.add_pagination_cursor_to_result(response)
page = exchange.parse_transactions(raw_rows, None, window_start, _BYBIT_TRANSFER_PAGE_LIMIT)
nxt = _bybit_next_cursor(response)
if not raw_rows:          # an empty raw page ends the window, whatever cursor it carries
    return True
```

Keep `if nxt is None: return True` and the seen-cursor raise for non-empty raw pages. Add a RED test: raw-empty page with a sticky cursor returns the rows read and does not raise; raw-empty page with a fresh cursor makes no further call. The parsed-empty-but-raw-full case (the H-1 regression test) is unaffected.

## MEDIUM

### F-2 `services/ccxt_flow_fetch.py:121-126`: `parse_transactions` drops raw rows with no count and no log

Evidence. Confirmed with the real ccxt: a two-row deposit answer, one `successAt: "0"` (status 4), parses to one row (`raw 2 -> parsed 1`). `parse_transactions` also drops a row whose stamp is `None` (an unparseable `createTime`/`successAt`), a row older than `window_start` (the `since` filter), and anything past 50 (the `limit` slice). The branch now makes the call itself and holds both lists, but never compares them. The Unified reader's contract in this phase is the opposite: an unreadable row refuses the read and a row is never dropped.

Hidden errors: a credited deposit whose stamp field drifts to a non-numeric string; a venue that ignores `limit` and sends more than 50 rows (the oldest 50 are kept and the cursor then continues past the rest); a startTime filter on a different field than the one ccxt stamps from. All read as a clean list.

User impact: missing flows in the flow-aware TWR base with no trace. Most dropped rows today are legitimately uncredited deposits, which is why this is MEDIUM and not HIGH, but nothing distinguishes that case from a drift.

Minimal fix: `dropped = len(raw_rows) - len(page)`; when `dropped > 0`, `logger.warning("... kind=%s window_start_ms=%d dropped_rows=%d of=%d", ...)` (counts only, no venue text). If `len(raw_rows) > _BYBIT_TRANSFER_PAGE_LIMIT`, raise `TransferPageStalled`-style (the slice would otherwise discard rows silently). Test: one stamp-0 row in a page logs `dropped_rows=1`.

## LOW

### L-1 `services/ccxt_flow_fetch.py:40-50, 114-126`: a malformed answer reads as an empty window; a non-string cursor is stringified

`_bybit_next_cursor` returns `str(cursor)`, so an int or dict cursor is sent back to the venue (`{'a': 1}` becomes the text `"{'a': 1}"`). The Unified reader and the evidence walk refuse a non-string cursor. A 200 answer with no `result` object, or with its rows under an unknown key, makes `add_pagination_cursor_to_result` return `[]` and the window ends as empty (`safe_dict`/`safe_list_n` default to empty). ccxt did the same inside `fetch_deposits`, so this is not new behaviour, but the branch now owns the call and could match the Unified reader's strictness. Fix: `if not isinstance(response, dict) or not isinstance(response.get("result"), dict): raise TransferPageStalled(...)`, and `isinstance(cursor, str)` in `_bybit_next_cursor` (raise otherwise).

### L-3 `scripts/allocator_history_probe.py:2058, 2085`: the record prints member 1's evidence fields while `bybit_funding_explained` is decided over all members

### L-4 `services/ccxt_flow_fetch.py:206-214, 241-247` (pre-existing, found in passing): Bybit DEPOSIT rows carry no `id`, so the cross-window de-duplication never applies to them

Confirmed against ccxt: `parse_transaction` sets `id = safe_string_2(transaction, 'id', 'withdrawId')`, and a deposit row has neither (`id: None`, `txid: 'abc'`). `seen_ids` therefore never sees a deposit, and a deposit stamped on the exact boundary millisecond shared by two adjacent windows (window n+1 starts at window n's inclusive end) is counted twice. The module comment says "ccxt transfers always carry one", which is false for Bybit deposits. The test double hides it by putting an `id` on the raw rows, which the real endpoint does not. Probability per deposit is about one in 2.6 billion, so LOW and not introduced by this phase; fix is `_rid = row.get("id") or row.get("txid")` for the Bybit branch.

### L-5 `services/ccxt_flow_fetch.py` / `services/job_worker.py` `classify_exception` (round-1 L-4, still open)

`TransferPageStalled` is still a plain `RuntimeError` with no permanent arm, while its twin `BybitUnifiedFlowReadError` is permanent. The new ceiling and cycle raises make it more reachable, and F-1 would route a false positive through it. Not required by the fixer's brief (LOW), but cheap to close together with F-1.
