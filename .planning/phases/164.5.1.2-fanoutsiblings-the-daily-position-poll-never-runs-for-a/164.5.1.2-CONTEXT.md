## D-01 — ⭐ THE INVERTED DEPENDENCY IS NARROWER THAN THE ROADMAP CLAIMS, AND THIS IS THE PHASE'S KEY FINDING

**The ROADMAP says this phase depends on 164.5.1.1**, because the question *"does an owner-only
strategy share an `api_key` with a sibling whose status IS in `ALLOWED_STRATEGY_STATUSES`?"* was
handed to that phase's plan 04 PROD session. **Measured 2026-09-19: that question is UNANSWERED** —
164.5.1.1 plan 04 has no SUMMARY, the phase has no VERIFICATION (`missing`), and its
`PROD-SESSION.md` contains ZERO occurrences of `api_key`. The founder has deliberately ordered
this phase FIRST; that ordering stands.

⭐ **BUT THE DEPENDENCY DOES NOT BIND THE POLL-POSITIONS VERDICT AT ALL, and the reason is
structural, not statistical.** Traced at HEAD:

1. The poll predicate's second conjunct keys on the strategy's OWN id — `cj.strategy_id = s.id`.
2. `sync_trades` jobs are issued only by `/cron-sync`, whose `strategy_ids` list is built by
   filtering the key's related strategies through `ALLOWED_STRATEGY_STATUSES`, and the job carries
   an id **drawn from that filtered list**.
3. Therefore an owner-only strategy's OWN id **never** receives a `sync_trades` job — **whether or
   not a sibling shares its key.** A shared key means the SIBLING's id gets the job, not this one's.

⛔ **Consequence, and it must not be lost downstream:** the shared-key answer cannot change whether
an owner-only strategy is polled. It changes only whether the KEY is synced at all — i.e. whether
trades reach *anyone* on that key — which is a question about the sync constant's SCOPE, not about
the poll predicate.

**DECISION: split the dependency rather than inherit it whole.**
- **The poll-positions verdict is decided in this phase, unconditionally.** No PROD read needed.
- **The `ALLOWED_STRATEGY_STATUSES` verdict takes option (a): this phase requests the production
  read ITSELF**, as a `checkpoint:human-action`, rather than option (b)'s conditional verdict.
  **Why (a) over (b):** the founder's ordering puts 164.5.1.1 AFTER this phase, so a verdict
  "conditional on 164.5.1.1" would be conditional on work that has not happened yet and is not
  next — a dangling condition with no owner. The read is ONE read-only query.
  ⛔ **The founder enters credentials; no agent does.** The marker query runs FIRST and a NULL
  answer stops the session. ⚠️ If the founder declines or defers the read, the fallback is (b) —
  an explicitly conditional verdict naming exactly what it awaits — never an assumed answer.

⛔ **The verdict must NOT be reached by assumption or by inference from code.** A verdict resting
on an unrun query is the "dated CLAIM, not a fact" failure that collapsed two phases this week.

## D-02 — the poll-positions site: REFUSE the widening as INERT, and say why in the record

**Verdict: LEAVE the lifecycle conjunct alone. Do not widen it.**

**Evidence (PROD, 2026-09-17, marker read first — `⛔ PRODUCTION`):** the five `pending_review`
strategies **already pass** the lifecycle conjunct and have **still never been polled**. A status
that is admitted and still yields zero is direct evidence that the lifecycle set is **not the
binding constraint** — the exact OPPOSITE of what Phase 164.5.1.1 found for the ledger fan-out,
where it was the only one. ⛔ Widening this predicate alone would change nothing observable, and
shipping it as a fix would be **a change that cannot be falsified by its own outcome**.

⛔ **THE TRAP, named so no one re-proposes the widening later:** the binding constraint is the
`EXISTS (sync_trades in 30 days)` conjunct, which is starved upstream by
`ALLOWED_STRATEGY_STATUSES`. An owner-only strategy fails BOTH conjuncts. Per criterion 2, if the
lifecycle conjunct is ever widened, the 30-day conjunct is addressed **in the same decision**, or
the widening is refused as inert. This phase refuses it.

⚠️ **The harm is real and stays booked** — this is a refusal to apply the WRONG fix, not a finding
that nothing is wrong. Measured: no `private` strategy has ever been polled and **none has a single
position snapshot**, while every `published` one is current to today. 23 `poll_positions` jobs
exist in the last 30 days and **all belong to ONE published strategy**. `run_poll_positions_job`
fetches open positions from the venue and persists snapshots; for all six real, live, key-bearing
strategies there are none, ever. That is the user-facing half of this phase.
