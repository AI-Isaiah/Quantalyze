## § S — the sibling question (all statements RECORDED)

**The question, fixed before any reading:** does an owner-only (`private`) strategy share an
`api_key` with a sibling strategy whose status IS in `{draft, pending_review, published}`?

**Why it matters, and the narrow thing it decides.** Per CONTEXT D-01, this does **not** affect
whether a `private` strategy is polled — that is settled and structural: the poll predicate's
`EXISTS` keys on the strategy's OWN id, and `/cron-sync` draws the `sync_trades` `strategy_id`
from a list already filtered by `ALLOWED_STRATEGY_STATUSES`, so a `private` strategy's own id
never receives a `sync_trades` job whether or not a sibling shares its key. What the answer
decides is whether the KEY is synced at all — the SCOPE of the constant's harm.

**Pre-registered interpretation — written BEFORE the read so the number cannot be rationalised
afterwards:**

| `without_in_set_sibling = 0` | every `private` key is already synced via an in-set sibling; the constant's gap is narrower than the TODOS framing suggests, and widening would newly sync only the `private` strategy's own rows rather than unstarve a dark key |
