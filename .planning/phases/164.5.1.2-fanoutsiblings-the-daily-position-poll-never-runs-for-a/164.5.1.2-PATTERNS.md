## Pattern Assignments

### A. Recording a VERDICT — including "leave alone" — durably

**Analog:** `TODOS.md` §§ `FANOUT-COHORT-SIBLING-POLL-01`, `FANOUT-COHORT-SYNC-CONSTANT-01`,
`FANOUT-COHORT-SIBLING-COMPOSITE-01` (all booked 2026-09-17 by Phase 164.5.1.1 plan 03 — these
three entries are literally what this phase is closing).

**The idiom, extracted (each entry carries all five):**
1. **A heading naming the finding**, with a booked date: `### <ID> — <one-line finding> (booked
   YYYY-MM-DD)`.
2. **`Measured` paragraph** — what was actually read, from where, with the exact symbol/path, and
   an explicit statement of what a *partial* read would have gotten wrong (see
   `FANOUT-COHORT-SYNC-CONSTANT-01`'s correction of `164.5.1.1-RESEARCH.md`'s partial-body error —
   this phase's own D-04 inherits that correction verbatim and must not re-derive it).
3. **A "what a user/strategy gets" consequence paragraph** — stated as an *effect*, not a
   mechanism (compare `FANOUT-COHORT-SIBLING-POLL-01`'s "no `private` strategy has ever been
   polled, and none has a single position snapshot").
4. **`TRIGGER`** — the condition under which the entry comes due again, phrased so a future author
   cannot quietly re-propose the refused idea without tripping it. Example from
   `FANOUT-COHORT-SIBLING-POLL-01`: *"anyone proposes to widen this conjunct, or a phase proposes
   to widen `ALLOWED_STRATEGY_STATUSES`... Either one alone is inert; the pair is a real behaviour
   change and needs the measurement first."*
5. **`Destination` + `Owner`** — named phase, never a bare TODOS line. (Founder rule 2026-09-08,
   restated in every one of these entries: *"a TODOS line alone has none of the three [owner,
   trigger, phase]."*)

**For this phase specifically:** D-02's "leave alone, refused as inert" verdict should be written
back into `FANOUT-COHORT-SIBLING-POLL-01` as a **closure**, in the same voice as
`164.5.1.1-PROD-SESSION.md`'s closure of `FANOUT-COHORT-PRIVATE-01` — quote the measurement that
justifies "leave", not just assert it. D-03's verdict (fix-here vs book) should either close
`FANOUT-COHORT-SYNC-CONSTANT-01` (if fixed) or leave it open with a sharpened `TRIGGER` that now
names the cursor-lies defect specifically, distinct from the widening question it was originally
filed under — the two have different causes (CONTEXT.md D-03) and must not share one entry's
closure.

**Refusal-as-outcome precedent (closest thing to "why leave alone is written up, not just decided
in chat"):** `FANOUT-COHORT-SIBLING-COMPOSITE-01`'s handling of `164.5.1.1-RESEARCH.md`'s wrong
widening instruction — *"The premise is false... so the instruction is refused, and the refusal is
now written into the gate file itself beside the literal it protects."* A refusal gets written
where a future reader will trip over it, not only into a planning doc.

**B2 — Python site (`ALLOWED_STRATEGY_STATUSES`, `should_advance_cursor`).**

### C. The `checkpoint:human-action` PROD-read pattern (D-01's one read-only query)

**Analog:** `164.5.1.1-04-PLAN.md` Task 3 (`checkpoint:human-action`, `gate="blocking-human"`) +
its recording in `164.5.1.1-PROD-SESSION.md` §B. **This phase's read is a strict subset of that
task** — no natural-tick wait, no manual RPC invocation, no apply to watch — so borrow the
discipline, not the full task shape. The nearer-weight precedent for "one read, one write, one
report" is `161.1-01-PLAN.md` Task 3 ("A7 TRACER"), but even that carries a write (one manual
enqueue) this phase's D-01 read does not need — no repo task in this codebase is a **pure** single
read-only query with nothing else, so this is a role-match, not an exact one.

**What to copy verbatim (non-negotiable, repeated in every PROD session in this repo):**
1. **Marker-first, always.** `SELECT shobj_description(oid, 'pg_database') AS which_database FROM
   pg_database WHERE datname = current_database();` is the first statement of the session, its
   OUTPUT is recorded, and a NULL/non-TEST-non-PROD answer stops the session
   (`164.5.1.1-PROD-SESSION.md` §B: *"Marker first, every time"*).
2. **Record OUTPUT, never the query.** `164.5.1.1-04-PLAN.md`'s verify block fails loud on a
   session record that pastes a query instead of its result — *"Pasting a query instead of its
   result has satisfied a verification leg in this project before and was booked as a defect."*
3. **Truncate every identifier to 8 characters**, and the automated verify greps for full-length
   UUIDs and fails on any hit (`164.5.1.1-04-PLAN.md`'s `full_uuids` check). ⛔ Non-negotiable per
   this phase's own CONTEXT.md.
4. **The question the read answers must be a single sentence, decided before the read, not
   discovered during it.** D-01's question is already that sentence: *"does an owner-only strategy
   share an `api_key` with a sibling whose status IS in `ALLOWED_STRATEGY_STATUSES`?"* — the query
   is a join on `strategies.api_key_id` grouping by status membership, nothing else.
5. **The founder enters credentials; no agent does** — the `<action>` block names the ONE
   human-only step and everything else as automated, exactly as `164.6.2-03-PLAN.md` Task 2 does
   for a credential-set gate (a stricter analog for "agent must not touch the value," useful for
   phrasing the refusal list even though that task is a write, not a read).
6. **Record file:** create (or extend) a `164.5.1.2-PROD-SESSION.md` in this phase's directory,
   same two-marker + §-lettered structure as `164.5.1.1-PROD-SESSION.md` (`## § <letter> — <task
   name>`), not a subsection of CONTEXT.md or a chat transcript.

**Fallback per CONTEXT.md D-01(a):** if the founder declines or defers the read, CONTEXT.md
already names the fallback — option (b), an explicitly conditional verdict naming exactly what it
awaits. That fallback's own precedent is how `FANOUT-COHORT-SYNC-CONSTANT-01` was originally
written (conditional, before the read it named ever happened) — reuse ITS "the one question that
cannot be settled from code" framing verbatim if the read does not happen this phase.

## Shared Patterns

### PROD-write / SQL-migration apply path (applies ONLY if D-03 or a reopened D-02 lands as a `supabase/migrations/**` change)
**Source:** `164.5.1.1-04-PLAN.md` Task 1 + Task 2, `CLAUDE.md` §"Which database am I on?"
**Apply to:** any SQL file change, never a Python-only change.
- Three reviewers BEFORE any apply is requested: `migration-reviewer`, `rls-policy-auditor`,
  `silent-failure-hunter`, run against the **shipped diff**, not the plan.
- Apply path: merge → `apply-test` (shared TEST) → PROD `apply` behind the `Production`
  environment's human reviewer gate. A migration file on `main` proves nothing about what applied
  — record both run ids and both conclusions.
- ⛔ Never a data-reading `RAISE EXCEPTION` in the migration body (shared TEST holds PROD's
  catalogue, never its data — `[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`).
- ⛔ **This path does NOT apply to a `cron.py`-only fix.** `ALLOWED_STRATEGY_STATUSES` and the
  `should_advance_cursor` gate live in `analytics-service/routers/cron.py`, deployed via the
  Railway CI/CD path (pytest → merge → Railway auto-deploy waiting on green `main` CI), not the
  Supabase migration path. Do not route a Python-only D-03 fix through the 3-reviewer SQL gate —
  route it through the ordinary review/ship flow, with the C-0198-shaped pytest addition as its
  falsifiability proof (§B2 above).

### CHANGELOG + version-bump discipline
**Source:** `CLAUDE.md` §"CHANGELOG discipline", `164.5.1.1-04-PLAN.md` Task 2 instructions (a).
**Apply to:** any ship this phase produces, code or verdict-only.
- Enumerate every commit (`git log main..HEAD --oneline`), read the full diff, group by theme,
  write ONE unified entry, cross-check every commit maps to a bullet.
- `VERSION` and `package.json` byte-equal 4-digit strings, hand-edited, never `npm version`.
- ⛔ Never a CI skip trailer anywhere, not even to deny it — `164.5.1.1-04-PLAN.md`'s own verify
  step greps every branch commit message for the token class and fails on any hit.

### "Record verdicts, never specimens" / repo-is-public redaction discipline
**Source:** `164.5.1.1-04-PLAN.md` Task 3's verify block (the `full_uuids` grep), this phase's own
CONTEXT.md non-negotiables.
**Apply to:** the PROD-SESSION record (§C above) and any TODOS.md entry quoting a production read.
- Truncate every UUID to 8 characters.
- No credential, connection string, project ref, key, absolute home path, local username, MT5
  account number or broker server name, ever — including inside a sentence proving one is absent
  (`feedback_proof_of_absence_can_publish_the_thing_it_proves_absent.md`).

### `last_sync_at` cursor-advance guard — the file's own repeated idiom
**Source:** `analytics-service/routers/cron.py::_sync_single_key`, the `C-0198` comment block
(audit-2026-05-07) around `any_trades_to_store` / `should_advance_cursor`.
**Apply to:** any D-03 fix.
- The existing gate is a two-clause boolean deliberately kept legible: `any_trades_to_store` (was
  there anything to store at all) then `should_advance_cursor = (not any_trades_to_store) or
  synced_count > 0` (advance on a genuinely idle tick, or on any real success; never on a tick that
  fetched trades but stored zero for a reason internal to this tick). A D-03 fix is a third clause
  in this same shape distinguishing "no trades fetched" from "trades fetched but zero strategies
  eligible" — do not invent a new gate shape beside it.
- The file already logs the "held `last_sync_at` unchanged" case at `logger.warning` with the key
  id and count — mirror that log line's shape for the new branch rather than adding a silent skip.
