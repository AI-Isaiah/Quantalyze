## Decisions Made
- Reused `api_keys.venue_account_id` (D-01-PRIME) rather than adding a new column — its own migration COMMENT's "never echo to the browser" prohibition is deliberately overridden by the founder per CONTEXT.md's amendment; the forgery vector it warned about (an unauthenticated RPC call) was closed by Phase 156's revocation of `authenticated` EXECUTE on `create_wizard_strategy`.
- Migration modeled verbatim on migration 068 (`20260420103151_api_keys_last_429_at_grant.sql`), the one clean standalone GRANT+self-verify precedent, with one addition: a catalog-only guarded pre-check (`information_schema.columns`) since, unlike 068, this migration extends a GRANT on a column that already exists rather than adding one.
- `ApiKeyRowSchema` (not named in the plan's file list, since it lives in the same file as `ApiKey`) required the same field — its `.strict() satisfies z.ZodType<ApiKey>` constraint would otherwise fail to typecheck once `ApiKey` gained a non-optional `venue_account_id`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Added `venue_account_id` to `ApiKeyRowSchema` (src/lib/types.ts)**
- **Found during:** Task 1 (types.ts edit)
- **Issue:** `ApiKeyRowSchema` is a Zod schema in the same file as `ApiKey`, declared `.strict() satisfies z.ZodType<ApiKey>`. The plan's file list named only the `ApiKey` interface; adding the field there alone would leave the Zod schema missing a required property, which fails the `satisfies` constraint and would break `npm run typecheck`.
- **Fix:** Added `venue_account_id: z.string().nullable()` to `ApiKeyRowSchema`'s field list, matching the sibling `sync_error`/`disconnected_at` fields' style.
- **Files modified:** src/lib/types.ts
- **Verification:** `npm run typecheck` clean repo-wide (confirmed in Task 2's own verify step).
- **Committed in:** 3b68186e (Task 1 commit)
