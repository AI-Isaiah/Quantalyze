# Phase 164.5.3 Plan 02: Stamp venue_account_id and discriminate its 23505 on validate-and-encrypt Summary

**Closed the NULL-population gap on the founder-visible "Add Key" path by stamping `venue_account_id` at INSERT time and discriminating the newly-reachable venue-identity 23505 into an honest 409.**

## Accomplishments
- `validate-and-encrypt`'s persist arm now derives `venueAccountId = isMt5 ? api_key.trim() : null` (mirroring `create-with-key/route.ts` verbatim) and writes it as an explicit INSERT field — every MT5 key connected via "Add Key" (`ApiKeyManager.tsx` / `AllocatorExchangeManager.tsx`, both call this route with `persist: true`) is now identifiable on the card immediately, not just wizard-created ones.
- A new branch, positioned above the route's existing generic insert-failure fallback, catches a `23505` naming `api_keys_user_exchange_venue_account_uniq` (now reachable here for the first time) and answers `{ code: "KEY_VENUE_ALREADY_CONNECTED", error: "You already have a connected key for this account." }` at 409 — an honest, distinct fact rather than "couldn't be saved."
- Every non-MT5 create and every other pre-existing insert-failure arm is byte-unchanged, confirmed both by test and by reading the committed diff.

- Reused `exchangeNormalized` (already the route's own canonicalized MT5-branch value) to derive `isMt5` locally inside `legacyValidateAndEncryptHandler`, rather than threading POST's `isMt5` binding through as an extra argument — equivalent by construction, keeps one source of truth.
