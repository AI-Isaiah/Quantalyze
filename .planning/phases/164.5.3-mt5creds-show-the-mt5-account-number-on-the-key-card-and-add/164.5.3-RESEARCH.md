## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01 — A GENERAL display column, populated only by MT5 for now.** Add one nullable text column holding the venue's non-secret account identifier, named generically (not `mt5_login`). Only the MT5 path populates it initially. Refused: `mt5_login`; also refused: populating it for other venues this phase.
- **D-02 — No backfill migration. The column arrives NULL and the update path is itself the backfill.** The migration adds the column and extends the GRANT. Nothing reads data. Existing rows stay NULL until their next successful credential write (fresh create or the new update path).
- **D-03 — The update path accepts the PASSWORD ONLY.** It does not accept a new login, and it does not accept a new broker server. Changing account is what Delete + Add Key legitimately means.
- **D-04 — Re-validate against the broker BEFORE persisting. Always.** The update path validates the new credential against the live broker and persists only on success. A failed validation persists nothing and mutates nothing. This is a data-integrity and user-facing path, so its gates BLOCK.
- **D-05 — Clear the failure state only on a successful validation, never on submission.** On a validated, persisted update, clear `sync_error` and lift a soft `disconnected_at`. On a failed validation, leave every status field exactly as it was.
- **D-06 — UI follows DESIGN.md, with one deliberate, recorded deviation.** Key card is a **card** primitive (white surface, 1px `#E2E8F0`, 8px radius, subtle shadow) — not a data panel. Account identifier renders in **Geist Mono with `tabular-nums` via `.font-metric`**. Deviation: **no thousands separators** — an MT5 login is an identifier, not a quantity. Absent value renders `—` (em-dash, never `0`, never blank). Update failures render through **`ErrorEnvelope`**, sourcing copy via `buildEnvelope()`. No bespoke error UI.

### A correction to PATTERNS.md's own risk framing (CR-01) — re-measured at HEAD

PATTERNS.md flags a real residual named in the venue_account_id migration's own header: *"`authenticated` holds EXECUTE on `create_wizard_strategy`, which is SECURITY DEFINER and stamps `venue_account_id` FROM A CALLER-SUPPLIED PARAMETER WITH NO VALIDATION... any browser session can POST `.../rpc/create_wizard_strategy` directly... and that value is persisted."* PATTERNS.md cites this as a live reason to be cautious about reusing the column.

**This residual was closed two days after it was written, and PATTERNS.md's citation is stale.** `[VERIFIED: supabase/migrations/20260814120000_wizard_rpcs_revoke_authenticated.sql:439]` — `REVOKE ALL ON FUNCTION public.create_wizard_strategy(` (the statement block revokes `EXECUTE` from `PUBLIC`/`anon`/`authenticated` and grants it only to `service_role`; the migration's own stated purpose, per its header, is exactly the "Phase 156 (CONNECT-REFACTOR)" remediation the venue_account_id migration deferred). A repo-wide scan for every later migration mentioning `create_wizard_strategy` (`[VERIFIED: supabase/migrations/ — all files with timestamp > 20260814120000 grepped for the string]`) found exactly one hit, `20260826130000_create_wizard_strategy_for_key.sql`, which is a **different function** (`create_wizard_strategy_for_key`, 4-arg signature) that is *also* `REVOKE ALL ... FROM authenticated` / `GRANT ... TO service_role` only (`[VERIFIED: supabase/migrations/20260826130000_create_wizard_strategy_for_key.sql:257-260]`). No migration re-grants `authenticated` EXECUTE on the original `create_wizard_strategy`.

**Consequence:** at HEAD, `venue_account_id` is populated only by server code (`createAdminClient()`-backed `rpcAdmin.rpc("create_wizard_strategy", ...)` in `create-with-key/route.ts`) that itself ran `validateKey()` moments earlier and confirmed a successful read-only auth for that exact login. The "any browser can forge it" vector PATTERNS.md flags is closed. The residual risk that remains (see Common Pitfalls below) is narrower: a **duplicate-row edge case** where a founder has two live `api_keys` rows for the same MT5 login (possible via the non-wizard `validate-and-encrypt` create path, which has never checked the WIZCONT-02 dedup fence), and D-02's "populate on next successful write" could then collide with `api_keys_user_exchange_venue_account_uniq`.

### A correction to PATTERNS.md's primary route analog — the UPDATE grant is fully revoked on `api_keys`

PATTERNS.md recommends `src/app/api/strategies/[id]/name/route.ts` as the "primary analog" for the new route's ownership+update shape, and that route's shape (`.eq("id", id).eq("user_id", user.id)...select("id")`, branch on `updatedRows.length === 0`) is excellent and should be copied — **but not verbatim**, because that route runs through the **user-scoped client** (`[VERIFIED: src/app/api/strategies/[id]/name/route.ts:127,197-203]` — `const supabase = await createClient();` ... `await supabase.from("strategies").update({ name })...`), which only works because `strategies` still has table-level UPDATE granted to `authenticated` under RLS.

`api_keys` does not. `[VERIFIED: supabase/migrations/20260810120000_lock_api_keys_exchange_column.sql:104]` — `REVOKE UPDATE ON public.api_keys FROM anon, authenticated;` with **no re-grant anywhere** (`[VERIFIED: supabase/migrations/20260823120000_revoke_api_keys_insert.sql:23-25]`, quoted verbatim: *"SELECT / UPDATE — UPDATE was already withdrawn by 20260810120000"*). A repo-wide scan (`[VERIFIED: grep -n "GRANT.*UPDATE.*api_keys\|GRANT UPDATE ON.*api_keys" supabase/migrations/*.sql — zero hits]`) confirms nothing has re-granted it since.

**Consequence:** copying the `name` route's `.update()` call onto a user-scoped Supabase client against `api_keys` will fail at the GRANT layer with a bare PostgREST `42501`, not degrade gracefully to the intended `updatedRows.length === 0` → 404 behavior. The write must go through **either** a service-role client (`createAdminClient()`, the same helper `validate-and-encrypt`'s persist arm and `create-with-key`'s `rpcAdmin` already use) **or** a `SECURITY DEFINER` RPC that performs the ownership check internally (the only existing UPDATE precedent on this exact table — see below). The `.eq("id", id).eq("user_id", user.id)` ownership idiom itself is unaffected by this correction and should still be applied as an explicit WHERE-clause filter even under the admin client, because service-role bypasses RLS but PostgREST still applies `.eq()` filters as literal WHERE clauses.

   │  1. rate-limit (userActionLimiter, 5/60s — same bucket family as validate-and-encrypt)
   │  2. ownership read: user-scoped SELECT id,user_id,exchange WHERE id=:id → 404 if absent/foreign

### Pattern 1: GRANT-extension migration (068 shape — the correct template)

**What:** A standalone migration that extends migration 027's column allowlist by one column, with a self-verifying anti-leak check. PATTERNS.md independently identified this as the correct template (not 066/075, which are large bundled migrations where the GRANT is a sub-clause) — corroborated here by a full read of all three.

**When to use:** Any time a new/existing `api_keys` column needs to become readable by `authenticated`.

**Example (adapt column name; full file read at `supabase/migrations/20260420103151_api_keys_last_429_at_grant.sql`):**
```sql
-- Migration NNN: GRANT SELECT (venue_account_id) ON api_keys TO authenticated
-- Extends migration 027's allowlist (see also migration 068 STEP for the
-- last_429_at precedent) so the founder can see WHICH MT5 account a key
-- card belongs to. venue_account_id already exists (migration 20260812083206,
-- Phase 154/WIZCONT-02) — this migration ONLY changes its readability. No
-- column is added, no row is read or written.
--
-- After this migration, src/lib/constants.ts → API_KEY_USER_COLUMNS_ARR and
-- src/lib/types.ts → ApiKey must both add "venue_account_id". All three ship
-- together.
--
-- ROLLBACK: REVOKE SELECT (venue_account_id) ON api_keys FROM authenticated;
-- and remove "venue_account_id" from API_KEY_USER_COLUMNS_ARR + ApiKey.

GRANT SELECT (venue_account_id) ON api_keys TO authenticated;

DO $$
BEGIN
  IF NOT has_column_privilege('authenticated', 'api_keys', 'venue_account_id', 'SELECT') THEN
    RAISE EXCEPTION 'Migration NNN failed: authenticated lacks SELECT on api_keys.venue_account_id';
  END IF;
  IF has_column_privilege('anon', 'api_keys', 'venue_account_id', 'SELECT') THEN
    RAISE EXCEPTION 'Migration NNN failed: anon unexpectedly has SELECT (migration 027 REVOKE broken?)';
  END IF;
  RAISE NOTICE 'Migration NNN: authenticated can SELECT api_keys.venue_account_id.';
END
$$;
```

### Pattern 3: Ownership-scoped read via user-scoped client (unaffected by the UPDATE-grant correction)

### Pattern 4: The only existing UPDATE-on-`api_keys` precedent — `SECURITY DEFINER` RPC with in-body ownership check

**Example (full statement read, `supabase/migrations/20260422101911_api_keys_disconnected_at.sql:114-163`):**
```sql
CREATE OR REPLACE FUNCTION public.reconnect_allocator_api_key(p_api_key_id UUID)
RETURNS BOOLEAN LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_temp
AS $$
DECLARE v_owner UUID; v_already_disc TIMESTAMPTZ; v_uid UUID := auth.uid();
BEGIN
  IF v_uid IS NULL THEN RAISE EXCEPTION 'not_authenticated' USING ERRCODE = '42501'; END IF;
  SELECT user_id, disconnected_at INTO v_owner, v_already_disc FROM api_keys WHERE id = p_api_key_id;
  IF v_owner IS NULL OR v_owner <> v_uid THEN
    RAISE EXCEPTION 'reconnect_allocator_api_key: caller does not own api_key %', p_api_key_id USING ERRCODE = '42501';
  END IF;
  IF v_already_disc IS NULL THEN RETURN false; END IF;  -- idempotent no-op
  UPDATE api_keys SET disconnected_at = NULL, sync_error = NULL, sync_status = 'idle'
    WHERE id = p_api_key_id AND user_id = v_uid AND disconnected_at IS NOT NULL;
  RETURN true;
END; $$;

REVOKE ALL ON FUNCTION public.reconnect_allocator_api_key(uuid) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.reconnect_allocator_api_key(uuid) TO authenticated;
```
This is the **closest structural precedent** for D-05's "clear `sync_error`/lift `disconnected_at` atomically with success" — including the exact two fields D-05 names. It is also the ONLY existing evidence in this repo of how `api_keys` gets updated at all, given the table-wide UPDATE REVOKE. The planner should decide (Open Questions Q2) whether the new credential-update persist step is (a) a sibling RPC in this exact shape, extended with the ciphertext columns + `venue_account_id`, or (b) a direct `createAdminClient()` UPDATE from the Next.js route (the posture `validate-and-encrypt`'s persist arm and `create-with-key`'s `rpcAdmin` already use for writes to this table). Both are established idioms in this codebase for `api_keys`; neither is a locked decision.

### Anti-Patterns to Avoid
- **Copying the `strategies/[id]/name` route's `.update()` call onto a user-scoped client for `api_keys`.** It will 42501 at the GRANT layer (see the CRITICAL correction above). Ownership-check-then-update over a single filtered query chain is still the right *shape* — run it through `createAdminClient()` or a `SECURITY DEFINER` RPC instead.
- **Sending the new/old broker server (passphrase slot) or the old password to the browser at any point**, even transiently, to let the client re-submit the full triple. D-03 forbids accepting login/server from the client; the server must recover them itself (via decrypt), never round-trip them through the browser.
- **Treating a Python-side validation 4xx as a persist trigger.** D-04 requires the persist step to run only after the `_validate_mt5_key`/`_validate_mt5_key_probe` call returns a structural success (`read_only: true`), exactly the same gate `create-with-key` already applies at creation.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Credential encryption/decryption | A new Fernet wrapper, a TS-side crypto helper | `analytics-service/services/encryption.py`'s `encrypt_credentials`/`decrypt_credentials` (`[VERIFIED: analytics-service/services/encryption.py:57-124]`) | It is the ONE encryption implementation in the repo; the KEK, DEK-per-row envelope scheme, and `kek_version` bookkeeping all live here. A parallel implementation would fork the crypto surface. |

## Common Pitfalls

### Pitfall 1: The venue-identity unique index can reject a legitimate backfill write
**What goes wrong:** `api_keys_user_exchange_venue_account_uniq` (`[VERIFIED: supabase/migrations/20260812083206_api_keys_venue_account_id.sql:465-467]`, quoted verbatim: `CREATE UNIQUE INDEX api_keys_user_exchange_venue_account_uniq ON public.api_keys (user_id, exchange, venue_account_id) WHERE venue_account_id IS NOT NULL AND disconnected_at IS NULL;`) governs any row where `venue_account_id` becomes non-NULL. If a founder has **two** live MT5 `api_keys` rows with the same login — possible today because `validate-and-encrypt`'s direct-INSERT create path (used by `ApiKeyManager`/`AllocatorExchangeManager`'s "Add Key" UI) never checked the WIZCONT-02 dedup fence — then D-02's "populate on next successful write" could hit a `23505` on this constraint when the second row's identifier is finally set.
**Why it happens:** The dedup fence was built for the wizard path only (Phase 154); the non-wizard create path was never wired to it.
**How to avoid:** The update route's persist step must catch `23505` on this specific constraint (`pgConstraintName`-style discrimination, exactly as `composite/add-key/route.ts:562-589` already does for the same constraint name) and answer a distinct, honest error rather than a generic 500 — this is a genuinely new failure mode this phase's update path can surface for the first time.
**Warning signs:** A founder with duplicate MT5 keys (same login, two rows) attempting a password correction on either row.

### Pitfall 2: `UPDATE` on `api_keys` is fully revoked — a user-scoped client silently can't write here
**What goes wrong:** Any `.update()` call against `api_keys` through the standard `createClient()` (user-scoped) helper will fail with PostgREST `42501`, not a graceful "0 rows" — see the CRITICAL correction above.
**Why it happens:** Migration `20260810120000` revoked table-level UPDATE from `anon, authenticated` with no re-grant, and this is easy to miss because SELECT (a *different* grant, column-allowlisted) still works fine for reads on the same table.
**How to avoid:** Use `createAdminClient()` (service-role) or a `SECURITY DEFINER` RPC for the actual write; keep the `.eq("id", id).eq("user_id", user.id)` ownership filter regardless of which path is chosen.
**Warning signs:** A route test that mocks the user-scoped client's `.update()` and never exercises the real Postgres GRANT will pass while the live route 500s.

### Pitfall 3: Adding `venue_account_id` to `ApiKey` may break every existing test fixture that constructs a full row literal
**What goes wrong:** `ApiKeyManager.test.tsx`'s "M-0456 projection allowlist columns reach the UI" block (`[VERIFIED: src/components/strategy/ApiKeyManager.test.tsx:268-299]`) constructs a full mock row object with every current `API_KEY_USER_COLUMNS` field spelled out literally (`id`, `user_id`, `exchange`, ... `disconnected_at`) and no `venue_account_id`. `AllocatorExchangeManager.test.tsx` (1763 lines) almost certainly does the same at multiple call sites (not individually re-read this session — flag for the planner to grep, not verified).
**Why it happens:** These fixtures are hand-typed object literals, not derived from `ApiKeyUserColumn`, so a new required-looking field is a silent gap unless the mock's type is loose enough to accept an incomplete object.
**How to avoid:** Grep every `api_keys` row-shaped test fixture across `ApiKeyManager.test.tsx`, `AllocatorExchangeManager.test.tsx`, `route.test.ts` files under `src/app/api/keys/**` and `src/app/api/strategies/**`, and add `venue_account_id: null` (or a synthetic placeholder value, per the non-negotiable rule — never a real login) to each.
**Warning signs:** `npm run typecheck` failures on test files after the `ApiKey` interface edit, or (if the type is loose) tests passing vacuously with `venue_account_id: undefined` rendering as if it were correctly NULL.

### Pitfall 4: `code:`-first key order is load-bearing for coverage tooling, repo-wide
**What goes wrong:** Every coded rejection this new route emits must be written `{ code: "...", error: "..." }`, not `{ error, code }`. `keys/validate-and-encrypt/route.ts`'s own comments (`[VERIFIED: src/app/api/keys/validate-and-encrypt/route.ts:329-341]`) describe this exact defect: twelve rejection arms on that route were briefly invisible to every coverage law in the repo (`wizardErrors.invariant.test.ts`, `dialog-envelope.invariant.test.ts`) because they were written in the wrong key order.
**Why it happens:** JSON key order has no runtime meaning, so it is easy to write `{ error, code }` without anything failing locally.
**How to avoid:** `code:` literal first in every `NextResponse.json({...})` call on the new route, mirroring `strategies/[id]/name/route.ts`'s own explicit comment on this.
**Warning signs:** A repo-wide coverage/invariant test passing with an unexpectedly low count for the new route's codes.

### Pitfall 5: MT5 validation needs the broker server (passphrase slot) — and it is not stored in plaintext anywhere TS can read
**What goes wrong:** Calling the existing TS `validateKey()`/`encryptKey()` seam functions for the update route requires the (unchanged) login and broker server in plaintext, alongside the new password. Neither is available to the Next.js layer without a new decrypt capability — `venue_account_id` (once exposed) supplies the login, but the broker server exists ONLY inside the Fernet-encrypted blob.
**Why it happens:** `ValidateKeyRequest`/`EncryptKeyRequest` (`[VERIFIED: analytics-service/models/schemas.py:9-13, analytics-service/routers/exchange.py:171-175]`) always require raw `api_key`/`api_secret`/`passphrase` — there is no existing `key_id`-based "revalidate this stored key" variant on either `/validate-key` or `/encrypt-key`.
**How to avoid:** This is why the Architecture Patterns diagram above recommends a **new** Python-side endpoint that decrypts, validates, and re-encrypts in one server-side round trip, never handing plaintext login/server back to Next.js — mirroring `/internal/keys/{key_id}/permissions`'s existing "decrypt stays inside Python" posture (`[VERIFIED: analytics-service/routers/internal.py:184-274]`, which uses its own `get_supabase()` service-role client to load the row by `key_id`).
**Warning signs:** A plan that has Next.js decrypting the row itself, or passing the broker server through a browser round trip — both would widen the plaintext-in-Vercel-process exposure this repo has consistently minimized (SEAMCORE-06).

## Open Questions

1. **Reuse `venue_account_id` or add a genuinely new column?**
   - What we know: `venue_account_id` already satisfies D-01's stated shape (nullable, generic-named, MT5-only-for-now) almost exactly, and the specific forgery risk PATTERNS.md flagged against reusing it (CR-01) is closed at HEAD. What remains against reuse: extending its GRANT and its writer set couples this phase's display feature to the WIZCONT-02 dedup fence's partial unique index (Pitfall 1), which was scoped narrowly on purpose by its own migration.
   - What's unclear: whether the planner considers that coupling acceptable, or prefers a second, display-only column to keep the dedup fence's blast radius untouched (D-01's literal wording — "add one nullable text column" — more directly supports a *new* column).
   - Recommendation: reuse `venue_account_id` (less migration surface, satisfies D-02's "the update path is itself the backfill" naturally since the value is already the login the row was created/re-validated with) **provided** the planner adds the `23505`-on-venue-identity-constraint handling from Pitfall 1 to the update route. If the coupling is judged too risky, a second column is a straightforward, low-risk fallback — but name it distinctly from `venue_account_id` in the migration header so a future reader does not conflate the two (PATTERNS.md's own recommendation if Option 2 is chosen).

2. **Service-role admin client vs. a new `SECURITY DEFINER` RPC for the persist step?**
   - What we know: both are established idioms for writing to `api_keys` in this codebase (admin client: `validate-and-encrypt`'s INSERT, `create-with-key`'s `rpcAdmin`; RPC: `reconnect_allocator_api_key`'s UPDATE — the only existing UPDATE precedent).
   - What's unclear: which the planner prefers for a credential-adjacent write that must also call an external HTTP seam (Python) mid-flow — a `SECURITY DEFINER` RPC cannot make the broker call itself, so at minimum the *validate* step happens in the Next.js route (calling Python) and only the *persist* step is a candidate for the RPC form.
   - Recommendation: a `SECURITY DEFINER` RPC for the persist step alone (accepting the new ciphertext columns + optionally `venue_account_id`, doing the ownership-checked UPDATE + D-05's status-field clear in one atomic statement, mirroring `reconnect_allocator_api_key`'s shape almost exactly) is the tighter match to this table's established UPDATE posture. The admin-client-direct alternative is simpler to wire and equally safe; either is defensible.

3. **Should the update route be gated to `exchange === 'mt5'` only?**
   - What we know: CONTEXT.md's Goal and the ROADMAP entry both frame this phase entirely around MT5 ("show the MT5 account number," "correct a wrong password" in an MT5-specific context). D-03's wording is venue-agnostic in principle.
   - What's unclear: whether a ccxt/OKX-passphrase-shaped generalization is in scope now or a deliberate non-goal.
   - Recommendation (see Assumption A2): gate to MT5 only for this phase, per CLAUDE.md Rule 2 (minimum code, nothing speculative) and the phase's explicit framing; record a ccxt-secret-rotation idea in Deferred Ideas if the planner wants to preserve it for a future phase, mirroring how D-01 already deferred non-MT5 venues for the display column.

4. **Where does the "update password" affordance surface, relative to the existing "Reconnect" button?**
   - What we know: `AllocatorExchangeManager.tsx` already has a `Reconnect` button (`[VERIFIED: src/components/exchanges/AllocatorExchangeManager.tsx:704,829-893]`) for disconnected keys, which calls `reconnect_allocator_api_key` and assumes the credential is *already correct* — it does not re-validate. The new "update password" affordance is functionally distinct (the credential is *wrong* and needs correction) and should not be conflated with Reconnect.
   - What's unclear: whether it should appear only on keys in an error/disconnected state, or as a general always-available action on every key row/card (both components).
   - Recommendation: surface it as a distinct action available on every MT5 key card/row (not gated to error state) — a founder may want to rotate a password proactively (e.g., after a broker-mandated reset) even when the current credential still works. This is a UI/UX call for the planner, not something this research can settle from repo evidence alone.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---|---|---|
| V2 Authentication | Indirect | Not re-authenticating the founder for this action — relies on the existing session (`withAuth`), consistent with every other `keys/**` mutation route |
| V3 Session Management | Yes | `withAuth` (session + profile-approval + CSRF via `assertSameOrigin`) — reuse, do not hand-roll |
| V4 Access Control | Yes | Ownership check (`user_id` scoping) at BOTH the read pre-check (user-scoped client, Pattern 3) AND the write (explicit `.eq("user_id", ...)` filter even under a service-role client, or `auth.uid()` check inside a `SECURITY DEFINER` RPC body — never rely on RLS alone since `api_keys` UPDATE has no grant for RLS to even apply to) |
| V5 Input Validation | Yes | `new_secret` non-blank/length-bounded server-side (mirror the `api_secret.length < 8` ccxt check pattern from `create-with-key`, though MT5 investor passwords may be shorter — `create-with-key`'s own comment notes MT5 skips the 8-char floor: `(isMt5 ? api_key.trim().length === 0 : api_key.length < 8)`, so the update route's `new_secret` gate should mirror MT5's own non-blank-only rule, not the ccxt 8-char floor) |
| V6 Cryptography | Yes | Never hand-roll — reuse `encryption.py`'s `encrypt_credentials`/`decrypt_credentials` exclusively (Don't Hand-Roll table) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Plaintext credential leak into logs/Sentry | Information Disclosure | `scrubSeamError()` + explicit `secrets: [...]` arrays at every `captureToSentry`/`console.error` call touching this route — the established pattern in every existing `keys/**` route (SEAMCORE-06) |
| Cross-tenant credential overwrite (wrong `user_id`) | Tampering / Elevation of Privilege | Ownership filter on BOTH the read and the write, `user_id`-LEADING in any new index if one is ever added (per the existing `api_keys_user_exchange_venue_account_uniq` precedent's own stated rationale for leading with `user_id`) |
| Silent accept of a still-wrong password (D-04's whole reason for existing) | Repudiation (the user believes a fix occurred that did not) | Validate-before-persist, atomic; never persist on a validation the Python seam did not structurally confirm `read_only: true` |
| Duplicate-account collision on backfill write (Pitfall 1) | Tampering (silent wrong-row attribution) | Catch `23505` on `api_keys_user_exchange_venue_account_uniq` explicitly and answer a classified, honest error rather than a generic 500 |
| A caller probing an unowned key id (ownership check timing/response shape) | Information Disclosure | One honest 404 for "wrong owner, unknown id" — never distinguish (the `strategies/[id]/name` route's own stated rationale, directly applicable here) |
