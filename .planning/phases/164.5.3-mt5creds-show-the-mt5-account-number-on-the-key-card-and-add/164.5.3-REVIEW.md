# Phase 164.5.3 (MT5CREDS): Code Review Report

**Reviewed:** 2026-09-20
**Depth:** deep (cross-file: call chains, deploy-target boundaries, error-code channels, census/roster integrity)
**Files Reviewed:** 28 source files (+6 census/roster test files)
**Status:** issues_found

## Summary

The pieces are all present and individually well built. The seam plumbing, the
Python endpoint's fail-closed ordering, the three-way column sync and every
hand-typed census were done carefully and correctly. What the phase did NOT
achieve is the goal stated for it end to end: **a founder who corrects a wrong
MT5 password gets a row whose ciphertext is right and whose status fields still
say the key is broken** — and on one status value the key is permanently
excluded from the automated fan-out afterwards. That is CR-01 and it is the
central finding.

Two further blockers sit either side of it: a merge-time deploy race that takes
down the key list for **every** allocator (not just MT5), and a rate-limit
response shape that renders the "we cannot tell you whether your last action
took effect" envelope for a throttle the route itself imposed.

Judged against the five questions asked:

- **Goal end-to-end — NOT MET.** The seam is CR-01 (`sync_status`), amplified by
  WR-02 (a venue-identity collision discards the whole correction).
- **Identifier honesty — CLEAN.** No UI copy, label, aria-label or comment in
  the changed surface claims broker verification. `src/lib/types.ts`'s `ApiKey`
  field comment states the residual explicitly ("what the server passed, never
  what the venue confirmed"); the card renders the neutral `MT5 account {id}`.
  The one arguable phrase is in a code comment, not user-visible (IN-02).
- **DESIGN.md — the surfaced conflict was honoured, not re-averaged.** No
  formatter module was extracted for a two-line helper; both cards use the
  in-file `.font-metric` + em-dash idiom; the identifier is not comma-grouped
  and its non-separation is pinned by an assertion. One minor deviation (IN-03).
- **Scope deviations — all four justified.** Audit taxonomy (TS+Python together,
  forced by the parity test), seam registries (forced by a new `SeamBudgetKey`,
  and the `RouteBudgetKey` type fence genuinely refused the repo until both
  halves moved), dialog-envelope roster (forced by a fourth envelope-building
  dialog), wizard error tables (forced by a genuinely new 409 emitter). None is
  scope creep.
- **Census integrity — CLEAN, and this was the risk area.** Every count moved in
  both the assertion AND the restating title/docblock: 14→15 across four seam
  files, FOUR→FIVE + 15th→16th in the retry registry, 3→4 / 3→5 / 19→28 in the
  dialog law, 11→12 in the wizard law, 92→93 twice in the copy-table scans. The
  **deliberate mismatch was preserved**: `rosterFloor` stayed at `4` with a
  re-argued reason rather than tracking the membership — exactly the flattening
  the brief warned about, and it did not happen. Nothing widened a ceiling,
  lowered a floor, or added an unsanctioned exemption (the Python
  `NO_LIMITER_QUARANTINE` entry is the roster's own documented mechanism, with a
  reason a reader can check).
- **Test quality — no vacuous test found.** The Python suite proves the
  not-called properties rather than status codes alone; the dialog suite asserts
  real rendered copy; the card suites drive a real click through to a real
  `fetch` URL. The weakest items are the `source pins` describe (string
  presence over the route file), which is supplementary rather than load-bearing.
  The genuine test gap is that nothing pins the rate-limit deny **body**
  (CR-03) and nothing pins post-rotation `sync_status` (CR-01) — absence of
  coverage, not vacuity.

## Critical Issues

### CR-01: A successful rotation leaves `sync_status` untouched — the card still says "Key revoked" and the fan-out still skips the key

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` — the PERSIST ARM's
`admin.from("api_keys").update({...})` payload
**Issue:**

The UPDATE clears `sync_error` and `disconnected_at` and nothing else on the
status side. `sync_status` is left at whatever the failed sync wrote.

Trace the exact scenario the phase exists to serve:

1. The founder's MT5 password goes wrong. The allocator worker's failure arm
   (`analytics-service/services/allocator_positions.py::_map_exception_to_sync_status`)
   writes `sync_status` — `'revoked'` for an authentication/permission error,
   `'error'` otherwise — alongside `sync_error`.
2. The founder opens `UpdateMt5SecretDialog`, enters the correct password, the
   broker probe succeeds, and the route persists fresh ciphertext with
   `sync_error: null, disconnected_at: null`.
3. The row now reads `sync_status='revoked'`, `sync_error=NULL`.

Two consequences, both measured at HEAD:

- **The UI lies in the opposite direction D-05 worried about.**
  `src/components/exchanges/AllocatorSyncStatus.tsx` renders `'revoked'` as a
  red pill labelled `Key revoked` with `REVOKED_HELPER` — copy that tells the
  founder to *re-add a read-only key from the exchange*, i.e. to do the
  delete-and-re-add this phase was built to make unnecessary. For `'error'` the
  pill reads `Sync failed` and its helper is `syncError ?? ""` — which this
  route just set to NULL, so the founder gets a red failure pill with **no**
  explanation at all. Either way the founder cannot tell the correction worked.
- **On `'revoked'` the key is permanently out of the automated fan-out.** The
  live ledger-refresh enqueuer
  (`supabase/migrations/20260917120000_ledger_fanout_admit_private.sql`, the
  eligible-key predicate) carries `AND ak.sync_status IS DISTINCT FROM 'revoked'`,
  and the allocator polling enqueuer
  (`enqueue_poll_allocator_positions_for_all_keys`) carries the same exclusion.
  Nothing in the rotate path clears it and nothing else will, because the only
  writer that sets `sync_status` back to a healthy value is the worker — which
  is never dispatched for this key. The credential is correct and the key never
  syncs again.

CONTEXT.md's own D-07 named `reconnect_allocator_api_key` as *"the closest
structural match to D-05's clear-on-success requirement."* That RPC
(`supabase/migrations/20260422101911_api_keys_disconnected_at.sql`) sets **three**
fields — `disconnected_at = NULL, sync_error = NULL, sync_status = 'idle'` —
with a header comment saying precisely why: *"so the next tick picks the key up
fresh."* The route copied two of the three.

**Fix:** add the third field to the same statement, so the clear stays atomic
with the validated ciphertext write (D-05's own requirement):

```ts
      sync_error: null,
      disconnected_at: null,
      // D-05 + the `reconnect_allocator_api_key` precedent: a validated
      // credential must re-enter the fan-out. `'revoked'` is an explicit
      // exclusion in both enqueuers, and the pill renders `Key revoked` with
      // "re-add a read-only key" copy until this moves.
      sync_status: "idle",
```

and pin it: extend the existing happy-path payload assertion in
`src/app/api/keys/[id]/rotate-secret/route.test.ts` (the
`issues the admin UPDATE with the exact ciphertext + status-clear payload`
case) to include `sync_status: "idle"` — it is a `toEqual`, so the pin is free.

### CR-02: The GRANT and the projection that depends on it ship in one merge — every allocator's key list hard-errors until a human approves the PROD apply

**File:** `supabase/migrations/20260920120000_api_keys_venue_account_id_grant.sql`
(header) together with `src/lib/constants.ts` → `API_KEY_USER_COLUMNS_ARR`
**Issue:**

`venue_account_id` was added to `API_KEY_USER_COLUMNS_ARR`, which is the literal
projection string every user-scoped `api_keys` read uses —
`src/lib/queries.ts::getUserApiKeys`, `::getStrategylessActiveKeys`,
`ApiKeyManager::loadKeys`, `AllocatorExchangeManager`'s client refetch. Until
the GRANT is live on PROD, PostgREST answers `42501 permission denied for
column` for all of them.

`getUserApiKeys` does not degrade — it deliberately **throws** so the page error
boundary fires (its own comment records why: an earlier silent `[]` rendered
"connect your first exchange" to an allocator who had keys). So during the
window every allocations page and exchanges page is a hard error, for **every**
allocator, MT5 or not.

The window is not hypothetical and not short. Per CLAUDE.md, merging
`supabase/migrations/**` runs `apply-test` on shared TEST first and then PROD's
`apply` behind the **`Production` environment's human reviewer gate** — while
Vercel builds and promotes off the same merge with nothing ordering the two.

This repo already knows this hazard on this exact table. The header of
`supabase/migrations/20260812083206_api_keys_venue_account_id.sql` — the
migration that created this very column — opens with:

> `⛔⛔ DEPLOY ORDER — READ BEFORE MERGING. THIS MIGRATION MUST BE LIVE ON PROD
> BEFORE THE VERCEL DEPLOYMENT THAT PASSES p_venue_account_id.`
> `Merging to main fires the Supabase auto-apply AND the Vercel build, with NO
> ordering between them.`

and names the remedy: apply first, confirm green, only then promote. The new
migration's header discusses readability, the SEC-005 allowlist and the D-01′
override at length, and says **nothing** about deploy order. Neither do any of
the five SUMMARYs (grepped: zero hits for `42501`, `deploy order`, or the
ordering discussion).

**Fix:** two parts, both cheap.

1. Add the ordering warning to the migration header, in the same words the
   sibling uses, so the fact travels with the artifact:

```sql
-- ⛔⛔ DEPLOY ORDER — READ BEFORE MERGING. THIS MIGRATION MUST BE LIVE ON PROD
-- BEFORE THE VERCEL DEPLOYMENT THAT ADDS venue_account_id TO
-- API_KEY_USER_COLUMNS_ARR. Same hazard 20260812083206:7-19 documents, same
-- remedy. If the deployment wins the race, every user-scoped api_keys SELECT
-- answers 42501 and getUserApiKeys THROWS — the allocations and exchanges
-- pages hard-error for EVERY allocator until the apply lands.
```

2. Take the sibling's remedy at ship time: get the PROD apply approved and green
   **before** the Vercel production promotion, or split the merge (migration PR
   first, applied and confirmed; TS/component PR second). Record whichever is
   chosen in the ship notes — the ordering cannot be enforced from inside either
   file, which is exactly why the precedent writes it down.

### CR-03: The rate-limit refusal carries no `code`, so the dialog renders the UNKNOWN envelope — "we cannot tell you whether your last action took effect", with a Retry — for our own cap

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` — the
`rateLimitDenyJson(rl, { headers: NO_STORE_HEADERS })` call
**Issue:**

`rateLimitDenyJson` with no `throttledBody`/`misconfiguredBody` override emits
its bare fallback: `{ error: "Too many requests" }` at 429, or
`{ error: "Rate limiter unavailable" }` at 503 on the fail-closed path
(`src/lib/ratelimit.ts`). Neither body carries a `code`.

`UpdateMt5SecretDialog.handleSubmit` routes every non-ok response through
`recogniseDashboardDialogCode(ROUTE, body?.code)`. With `code` undefined that
answers `UNKNOWN`, whose copy is:

> *"We could not classify this failure, so we cannot tell you what happened or
> whether your last action took effect."* — actions `["clear_and_retry", …]`,
> i.e. a Retry button.

Both halves are false and the second is harmful: we know exactly what happened,
we know nothing was submitted, and inviting an immediate retry re-trips the same
bucket.

This is a named, previously-paid-for defect in this codebase. The identical arm
in `src/app/api/strategies/create-with-key/route.ts` carries a long comment
ending: *"Omitting `RATE_LIMITED` … would leave it failing ConnectKeyStep's
membership check and falling through to `UNKNOWN` — whose copy IS recoverable —
so the reader would get 'Try the last action again.' with a Retry for our own
cap."* It supplies `throttledBody` and `misconfiguredBody` for that reason.

It also slipped past the new coverage law by construction, not by luck:
`src/lib/dialog-envelope.invariant.test.ts` derives a route's emitted codes with
a `code:`-first **object-literal** predicate, and this body never rides a
`NextResponse.json` literal. The law cannot see it, so its silence is not
evidence.

**Fix:** supply both bodies and roster the codes (`SEAM_MISCONFIGURED` is
already on the rotate roster; `RATE_LIMITED` needs adding):

```ts
  const rl = await checkLimit(userActionLimiter, `keys-rotate-secret:${user.id}`);
  if (!rl.success) {
    return rateLimitDenyJson(rl, {
      headers: NO_STORE_HEADERS,
      throttledBody: { code: "RATE_LIMITED", error: "Too many requests" },
      misconfiguredBody: {
        code: "SEAM_MISCONFIGURED",
        error: "Rate limiter unavailable",
      },
    });
  }
```

then add `"RATE_LIMITED"` to the `"keys/[id]/rotate-secret"` Set in
`DASHBOARD_DIALOG_ROUTE_CODES` (`src/lib/wizardErrors.ts`) and move the
`checked` count in the dialog law's non-vacuity assertion 28 → 29 with the
reason, per that file's own instruction. Add a test asserting the 429 body's
`code`: the existing 429 case in `route.test.ts` asserts status and
`Retry-After` only, which is why nothing red.

## Warnings

### WR-01: The seam's machine code and upstream status are discarded, so every non-credential Python failure collapses to UNKNOWN 500 with a retry invitation

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` — the `if (!res.ok)`
block inside the `try`
**Issue:** the route throws a bare
`new Error(seamHumanMessage(errBody) ?? \`Upstream ${res.status}\`)`. No `cause`,
no `seamCode`, no status. `classifyKeyValidationError` reads `error.seamCode` /
`error.seamTransportCode` **before** its substring cascade — both are undefined
here, so every failure is decided by sniffing the human sentence.

Replayed against the sentences `analytics-service/routers/internal.py::rotate_key_secret`
and its callees actually produce:

| Python arm | sentence | cascade verdict |
|---|---|---|
| `RATE_LIMITED` (per-key bucket, 429) | "Too many secret-rotation attempts for this key…" | no branch matches → `UNKNOWN`, 500 |
| `KEK_UNAVAILABLE` (500) | "Credential encryption is not configured. This needs an operator, not a retry." | → `UNKNOWN`, 500 |
| `KEY_UNDECRYPTABLE` (500) | "This stored key could not be decrypted. It must be reconnected." | → `UNKNOWN`, 500 |
| `MT5_GATEWAY_UNCONFIGURED` (500) | "The MetaTrader gateway is not configured…" | → `UNKNOWN`, 500 |

`KEY_UNDECRYPTABLE` is the costly one: the Python side knows the actionable
remedy ("it must be reconnected") and the founder is shown "Something went
wrong… Try the last action again" instead, which can never succeed. This is the
DOGFOOD-3 class `classifyKeyValidationError`'s own docblock says it exists to
keep traffic out of.

The sibling seam route already solves this:
`src/app/api/keys/[id]/permissions/route.ts` builds its throw with
`buildSeamFailureCause(res.status, seamErrorCode(err), parseRetryAfterSeconds(res.headers))`.

**Fix:** carry the same evidence. Read `seamErrorCode(errBody)` and attach it so
the classifier's machine-code branch can fire (either via
`buildSeamFailureCause`, matching the sibling, or by assigning `seamCode` as an
own property on the constructed Error, matching what
`classifyKeyValidationError` actually reads). Then roster whatever wizard codes
that admits on `"keys/[id]/rotate-secret"` and move the dialog law's `checked`
count in the same commit.

### WR-02: A venue-identity 23505 on the UPDATE discards the entire correction — the founder is told to use a key they cannot use, with no way to fix this one

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` — the `updateErr.code === "23505"`
branch, together with the `venue_account_id` backfill spread above it
**Issue:** the 409 arm is correctly discriminated, but it aborts the *whole*
statement. The broker probe already succeeded and fresh ciphertext already
exists; the route throws it away and persists nothing — including the
`sync_error` clear.

Two reachable paths, both without any forged input:

1. **Two legacy MT5 rows for one account.** Both have `venue_account_id = NULL`
   today (the column was only ever written by the wizard RPC). Rotate key A →
   backfilled with login *L*, key A live. Rotate key B → the backfill writes *L*
   again, the partial UNIQUE `(user_id, exchange, venue_account_id) WHERE
   venue_account_id IS NOT NULL AND disconnected_at IS NULL` fires → 409. Key B
   can now **never** be password-corrected; the only remaining remedy is Delete
   + Add Key, which destroys the row and its sync history — the exact defect
   this phase removes.
2. **A disconnected duplicate.** The unconditional `disconnected_at: null`
   (WR-03) pulls a previously-excluded row into the partial index, so the same
   409 fires even with no backfill at all.

The copy makes it worse rather than better: `KEY_VENUE_ALREADY_CONNECTED` says
*"Use the key you already have connected for this account instead"* and
*"email security@… before disconnecting anything"* — advice that does not
address "the key I am trying to repair is the one that is broken."

**Fix:** make the collision non-fatal to the correction. On a 23505 naming
`VENUE_IDENTITY_CONSTRAINT`, re-issue the UPDATE **without** the
`venue_account_id` key (and, if the row was disconnected, without the
`disconnected_at` clear), so the password fix and the `sync_error` clear still
land; answer 409 only if the retry also fails. Alternatively gate the backfill
on a pre-check against the caller's other live rows. Pin both arms with a test —
the current suite only asserts that the 409 is *distinct from* the 500, never
that the correction survived.

### WR-03: `disconnected_at: null` is unconditional — a deliberately disconnected key is silently reconnected, and the dialog copy does not say so

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` (UPDATE payload) and
`src/components/exchanges/AllocatorExchangeManager.tsx` (the Disconnected-section
"Update password" button)
**Issue:** CONTEXT.md D-05 scopes the clear to *"lift a **soft**
`disconnected_at`"* — i.e. the auth-failure state. The implementation lifts
every `disconnected_at`, including one a founder set on purpose via the
Disconnect affordance. Since `AllocatorExchangeManager` renders "Update
password" inside the Disconnected section, a founder correcting a password on a
key they deliberately parked silently puts it back into the worker rotation
(`disconnected_at IS NULL` is an eligibility predicate in both enqueuers).

The dialog's copy — *"Enter the new MT5 investor password. We re-validate it
against your broker before saving — nothing changes if it doesn't work."* —
promises only a credential change.

**Fix:** decide and record, don't leave it implicit. Either (a) keep the
reconnect and say so in the dialog copy when the host card knows the row is
disconnected (one extra sentence, and an assertion pinning it), or (b) clear
`disconnected_at` only when the row was disconnected by the failure path rather
than by the user. (a) is the simpler honest answer given the button's placement,
and it composes with the CR-01 fix in the same statement.

### WR-04: The backfilled identifier is the raw decrypted login, not trimmed — every other writer normalises

**File:** `analytics-service/routers/internal.py::rotate_key_secret` — the
`return {**encrypted, "venue_account_id": login}` line, consumed by
`src/app/api/keys/[id]/rotate-secret/route.ts`'s backfill spread
**Issue:** `login` here is `decrypt_credentials(...)`'s first element, i.e.
`payload["api_key"]` verbatim. `_validate_mt5_key` normalises internally (via
`parse_mt5_credentials`) but the raw value is what is returned and stored.

Every other writer of this column normalises:
`src/app/api/strategies/create-with-key/route.ts` uses `api_key.trim()`,
`src/app/api/keys/validate-and-encrypt/route.ts`'s new derivation uses
`api_key.trim()` (and its comment calls the bare `.trim()` deliberate), and the
wizard RPC applies `NULLIF(btrim(p_venue_account_id), '')`.

A legacy row whose stored login carries surrounding whitespace therefore
backfills an untrimmed value, which (a) renders on the card with a stray space
inside a `.font-metric` span and (b) does **not** collide with its trimmed twin
in the partial UNIQUE — silently defeating the dedup for that pair.

**Fix:** normalise at the one place that produces it, so no caller has to
remember:

```python
    return {**encrypted, "venue_account_id": login.strip()}
```

and add a case to `analytics-service/tests/test_mt5_rotate_secret_internal.py`
asserting a padded synthetic login comes back stripped.

### IN-02: A code comment describes the identifier as broker-confirmed

**File:** `src/lib/analytics-schemas.ts` — the `RotateSecretResponseSchema`
docblock ("the login the seam just re-confirmed")
**Issue:** the phrase is defensible on this one path (the probe did log in with

copy, so the obligation is not breached — but it is the sentence a future reader
will quote.
**Fix:** reword to the vocabulary `src/lib/types.ts` already uses — "the login
this key is stored against", not "re-confirmed".

### IN-03: The label text sits inside the `.font-metric` span

**File:** `src/components/exchanges/AllocatorExchangeManager.tsx` and
`src/components/strategy/ApiKeyManager.tsx` — the `MT5 account {…}` paragraphs
**Issue:** DESIGN.md reserves the Geist Mono voice for figures and for
**uppercase, letter-tracked** micro-labels. Here a sentence-case label
("MT5 account") renders in the figures voice because the whole `<p>` carries
`font-metric`. Small, and it does keep the two cards consistent with each other.
**Fix:** if tightened, wrap only the value: `MT5 account <span className="font-metric">{…}</span>`.
The existing assertions read `identifier.toHaveClass("font-metric")` off the
paragraph, so they would need to target the span.

### IN-04: The Railway deploy is the second half of the two-target window

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts` (the seam call) vs
`analytics-service/routers/internal.py`
**Issue:** CONTEXT.md D-04 flagged two deploy targets. If Vercel promotes before

`seamHumanMessage` → "Not Found" → `classifyKeyValidationError` → `UNKNOWN`, 500.
Self-healing within minutes and strictly less severe than CR-02, but the founder
who tries the new button first sees the un-classifiable envelope.
**Fix:** nothing in code; note it in the ship checklist beside CR-02's ordering
step (verify the Railway `commitHash` and `/health` before exercising the new
affordance).
