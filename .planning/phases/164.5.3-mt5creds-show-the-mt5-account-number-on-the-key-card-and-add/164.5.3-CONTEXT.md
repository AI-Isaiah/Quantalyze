# Phase 164.5.3 — MT5CREDS: Context

**Phase:** 164.5.3 MT5CREDS — show the MT5 account number on the key card and add a credential-update path
**Discussed:** 2026-09-20 · branch `feat/164.5.3-mt5creds` from `main` @ `76542eee`
**Mode:** autonomous — grey areas decided from repo evidence and recorded here, per the founder's standing delegation. No `checkpoint:decision` was emitted for ordinary design calls.

---

## Goal

A founder (and a first-time client) can tell **which MT5 account** a key card belongs to, and can **correct a wrong password without deleting the key** — preserving the row, its id, and its sync history.

---

## Premises, re-measured at HEAD (not inherited)

| # | Claim | Verdict |
|---|---|---|
| 1 | No update path exists | ✅ **CONFIRMED.** Every key-touching route under `src/app/api/**` exports only `POST` or `GET` — `keys/validate-and-encrypt`, `keys/sync`, `keys/[id]/permissions`, `strategies/create-with-key`, `strategies/composite/add-key`, `debug-key-flow`. **Zero `PATCH`/`PUT`.** A wrong password is fixable only by Delete + Add Key. |
| 2 | The card cannot identify the account | ✅ **CONFIRMED.** `API_KEY_USER_COLUMNS_ARR` (`src/lib/constants.ts`) does not expose any account identifier, so the card falls back to `label` — sourced from the OPTIONAL nickname field. Several MT5 accounts render indistinguishably. |
| 3 | The exposure idiom is established | ✅ **CONFIRMED and it is the fourth instance.** Migration 027 (`20260410225608`, SEC-005) REVOKEs `SELECT ON api_keys FROM anon, authenticated` at table level, then GRANTs an allowlist back. Migrations **066** (`sync_error`), **068** (`last_429_at`) and **075** (`disconnected_at`) each added exactly ONE column to the GRANT *and* to the ARR, each with an inline reason comment. |

### ⭐ The measurement that reshaped the design

⛔ **There is no plaintext login column to expose.** `api_key_encrypted` is, per migration 027's own rationale block, a **"Fernet ciphertext blob of the credential JSON"**. `api_secret_encrypted` and `passphrase_encrypted` are **legacy and currently NULL**. The MT5 slot mapping documented in `validate-and-encrypt` — login → `api_key`, investor password → `api_secret`, broker server → `passphrase` — describes the *request payload*, which is then sealed into that single blob alongside `dek_encrypted` / `nonce`.

**Consequence:** the account identifier cannot be surfaced by reading an existing column, and decrypting to populate one is exactly what the locked design forbids. A **new display column, written at the moment the plaintext is legitimately in hand server-side**, is the only route that neither decrypts nor relaxes a REVOKE. This is not a preference — it follows from the storage shape.

## Locked decisions

### D-01 — A GENERAL display column, populated only by MT5 for now
**Decision:** add one nullable text column holding the venue's non-secret account identifier, named generically (not `mt5_login`). Only the MT5 path populates it initially.
**Why:** the repo's own precedent settles this. All three predecessor columns are generally named and populated only where applicable — `last_429_at` is stamped solely on ccxt 429s and is NULL for venues that never rate-limit that way. A venue-specific name would force a rename migration the first time a second venue has an identifier worth showing, and an applied migration is never edited.
**Refused:** `mt5_login`. ⛔ Also refused: populating it for other venues in this phase — that is speculative work with no measured need.

### D-02 — No backfill migration. The column arrives NULL and the update path is itself the backfill.
**Decision:** the migration adds the column and extends the GRANT. **Nothing reads data.** Existing rows stay NULL until their next *successful* credential write — either a fresh create or the new update path this phase adds.
**Why:** ⛔ A data-reading `RAISE EXCEPTION` in a migration is forbidden (`[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`): shared TEST holds PROD's catalogue and never its data, so such a migration can pass PROD and REFUSE TEST, and a refused TEST apply BLOCKS the PROD apply. Beyond that, a backfill would have to decrypt — the one thing the locked design rules out.
⭐ **The pleasing consequence:** the act of fixing a wrong password is also the act that makes the card identifiable. The two halves of this phase feed each other rather than sitting side by side.
**Deferred:** an out-of-band service-role backfill for keys whose password is already correct. It needs credentials, so it is founder-only; see Deferred Ideas.

### D-03 — The update path accepts the PASSWORD ONLY
**Decision:** the credential-update route changes the secret and nothing else. It does not accept a new login, and it does not accept a new broker server.
**Why:** the login *is* the identity the display column advertises, and the broker server qualifies it. Allowing either to change would silently re-point a row — and its entire sync history — at a different account, while the card kept showing the old one. That is a worse version of the defect this phase exists to remove. Changing account is what Delete + Add Key legitimately means.

### D-04 — Re-validate against the broker BEFORE persisting. Always.
**Decision:** the update path validates the new credential against the live broker and persists only on success. A failed validation persists nothing and mutates nothing.
**Why:** `keys/validate-and-encrypt` already establishes validate-then-encrypt as this codebase's shape, and a silent accept of a still-wrong password would reproduce precisely the defect being fixed — the user would believe they had corrected it. ⛔ This is a data-integrity and user-facing path, so its gates BLOCK.

### D-05 — Clear the failure state only on a successful validation, never on submission
**Decision:** on a validated, persisted update, clear the auth-failure state (`sync_error`, and lift a soft `disconnected_at`). On a failed validation, leave every status field exactly as it was.
**Why:** clearing an error because someone *attempted* a fix asserts something untrue about the account's state. The status fields are read by the exchange-status pill, so a premature clear renders a healthy pill over a still-broken key. D-04 makes success a measured fact rather than an assumption, which is what earns the right to clear.

### D-06 — UI follows DESIGN.md, with one deliberate, recorded deviation
**Decision:**
- The key card is a **card** primitive per DESIGN.md § Component Patterns — white surface, 1px `#E2E8F0`, 8px radius, subtle shadow. ⛔ Not a data panel; do not conflate.
- The account identifier renders in **Geist Mono with `tabular-nums` via `.font-metric`**, per the Numbers Contract's Typeface row.
- ⭐ **DEVIATION, deliberate:** the Numbers Contract's *Integers* row prescribes thousands separators. ⛔ **Not applied here.** An MT5 login is an **identifier, not a quantity** — rendering it `1,234,567` would be wrong and unrecognisable to the person matching it against their broker terminal. The contract's own framing is that "numbers are the product"; an account number is a name that happens to be numeric. Recorded here because the contract binds by default and a silent departure would read as drift.
- **Absent value renders `—`**, per the Numbers Contract's Null rule: *"em-dash. Never `0`, never blank, never a fabricated value."* ⭐ This is not a degradation workaround — it is the product-wide contract, and it is honest about absence, which is exactly right for a key whose identifier is not yet known (D-02).
- Update failures render through **`ErrorEnvelope`** (`src/components/error/ErrorEnvelope.tsx`), sourcing copy via `buildEnvelope()`, per DESIGN.md § Error Envelope. ⛔ No bespoke error UI.

## Consequences this phase carries

- ⚠️ **It ships a migration** ⇒ ⛔ three reviewers before any apply (`migration-reviewer`, `rls-policy-auditor`, `silent-failure-hunter`), then merge → `apply-test` on shared TEST → the PROD `apply` behind the **`Production` human reviewer gate**. ⭐ That gate is a REAL STOP the founder must approve; it is planned for, never routed around.
- ⚠️ **User-facing and credential-adjacent** ⇒ anti-vacuity BLOCKS; review findings here BLOCK rather than being fix-or-drop.
- ⛔ **Never widen the REVOKE on the encrypted columns.** The new column is additive and narrow; `api_key_encrypted`, `api_secret_encrypted`, `passphrase_encrypted`, `dek_encrypted` and `nonce` stay service-role only.
- ⚠️ The GRANT allowlist and `API_KEY_USER_COLUMNS_ARR` **must stay in sync** — migration 027 says so explicitly and the three precedent migrations each moved both together.
- ⚠️ Next.js here carries breaking changes versus training data — read `node_modules/next/dist/docs/` before writing route or component code.
