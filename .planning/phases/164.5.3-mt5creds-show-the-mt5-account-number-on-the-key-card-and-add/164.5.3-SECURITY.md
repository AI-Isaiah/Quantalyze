# Phase 164.5.3 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

**What this phase did, in security terms.** Two things, and both matter here: it **widened a
confidentiality boundary** (an existing column, `venue_account_id`, became readable by
`authenticated` and is now rendered on the key card), and it **added a route that decrypts,
re-validates and re-encrypts a live credential**. Everything below is scoped to those two changes.

⛔ **The premise a fresh reader gets wrong.** `164.5.3-CONTEXT.md`'s `# ⛔ AMENDMENT` SUPERSEDES
decisions D-01/D-02 in the body above it. The column was NOT added by this phase — it already
existed (migration `20260812083206`, Phase 154 / WIZCONT-02), was populated by MT5 only, and was
simply never EXPOSED. This phase REUSES and EXPOSES it under **D-01-PRIME**, a founder-approved
override. A threat model written against the un-amended body would be wrong.

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| `authenticated` (owning user) → `api_keys` SELECT | The allowlist GRANT this phase extends. RLS still scopes every row to the owning user; unchanged by this migration. | A non-secret venue account identifier |
| Browser → `PATCH /api/keys/[id]/rotate-secret` | Authenticated, CSRF-checked, profile-approval-gated. | A newly-typed password, for the life of one request |
| Next.js route → the Python internal seam | VPC-internal, gated by the shared internal-token secret; never browser-reachable. | The new password, plus the caller's user id for owner scoping |
| Python seam → the live MT5 gateway | The same probe every other credential-validation path already uses; no new external surface. | Login, broker server and the new password |
| Route → `api_keys` UPDATE (admin client) | ⛔ RLS does NOT apply to a service-role client, so the explicit ownership filter is the ONLY tenant boundary on this write. | Re-encrypted ciphertext and status fields |
| Migration → TEST → PROD | The standing migrate pipeline; PROD sits behind a human reviewer gate. | DDL only |

## ⛔ T-164.5.3-16 — the one OPEN threat, recorded as open

**The risk.** The GRANT must be live on PROD **before** the frontend promotion carrying the
column-projection change lands. Ship them the other way round and a deployed frontend requests a
column it is not yet permitted to read, and the key card fails for every user until the migration
catches up.

**Why it is not closed.** Nothing in the code enforces it, and nothing can: the ordering spans two
independent pipelines — the database migration behind a human reviewer gate, and the frontend
build-and-promote. The migration's own header documents the required order, but a header is prose,
not a control.

**Why it does not block.** It is `medium`, below the `high` block threshold, so `threats_open`
remains 0 by the gate's own definition. ⛔ That is a statement about the gate, **not** a claim that
the risk is handled — which is why `threats_open_below_threshold: 1` is recorded above and this
section exists rather than a quiet row in a table.

**Who owns it and when.** The founder, at ship time. It is item 3 of `164.5.3-UAT.md`: either the
migration is applied and green on PROD first, or the merge splits into two PRs. ⚠️ This is
time-boxed to the ship itself, not to a later QA pass.
