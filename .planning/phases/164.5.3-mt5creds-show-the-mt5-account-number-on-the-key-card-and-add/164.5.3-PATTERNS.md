## ⭐⭐ CRITICAL PRE-PLANNING FINDING — read before anything else

**A column matching D-01's description already exists: `api_keys.venue_account_id`**
(`supabase/migrations/20260812083206_api_keys_venue_account_id.sql`, Phase 154 / WIZCONT-02).
It is nullable text, holds "the venue's non-secret account identifier" (the MT5 broker login,
`mt5_probe`-asserted), is populated today only by `create_wizard_strategy`'s wizard path, and is
generically named — i.e. it satisfies D-01's surface description almost exactly. **CONTEXT.md's
premise measurement never mentions it** (grepped the full file — zero hits), so this was a miss
by the upstream research, not a deliberate rejection.

**Why it is NOT simply reusable as this phase's display column, stated from the migration's own
text:**
- Its migration explicitly forbids exactly what D-06 requires: *"⛔ Never echo this value to the
  browser (UI-SPEC): non-secret is not the same as publish."* There is no GRANT for it in
  `API_KEY_USER_COLUMNS_ARR` / the allowlist, by design — migration 027's REVOKE governs it and
  nothing extends the GRANT.
- It carries a **named, unfixed trust residual (CR-01)**: `create_wizard_strategy` is `SECURITY
  DEFINER` and stamps `venue_account_id` from a caller-supplied RPC parameter **with no
  validation** — "any browser session can POST .../rpc/create_wizard_strategy directly with a
  `p_venue_account_id` of its choosing." The column's only real protection is a BEFORE INSERT
  scrub trigger that closes the *direct table INSERT* path, not the RPC path. The migration's own
  words: *"Treat the value as 'what the server passed', not 'what the venue confirmed'."*
- It is **load-bearing for a UNIQUE dedup index** (`api_keys_user_exchange_venue_account_uniq`,
  partial on `venue_account_id IS NOT NULL AND disconnected_at IS NULL`) that exists to stop
  duplicate wizard drafts. Extending its GRANT or its writers couples a display concern to that
  dedup fence's carefully-scoped predicate (see the migration's "Why the UNIQUE is scoped to LIVE
  keys" section) — a mistake here risks the WIZCONT-02 guarantee, not just the display feature.
- It is populated only by the wizard path today; `keys/validate-and-encrypt` (the non-wizard
  create path) and the composite-key RPC do **not** stamp it.

**This is a decision for the planner, not something I resolve here.** Two live options, both
consistent with D-01–D-06:
1. **Treat `venue_account_id` as the display column.** Extend its GRANT (068-style), add it to
   `API_KEY_USER_COLUMNS_ARR` and `ApiKey` (types.ts), and make D-02's update path populate it —
   but this means the update path is now also feeding the WIZCONT-02 dedup fence, and the CR-01
   residual (unvalidated value) becomes user-visible for the first time. That widens this migration
   's blast radius well past "additive and narrow."
2. **Add a genuinely new, distinct column** (as D-01's wording implies), keeping
   `venue_account_id` untouched and dedup-only. Cleaner isolation, matches CONTEXT.md's own
   locked language, but ships a *second* MT5-login-shaped column on the same table — name the two
   apart clearly in the migration header so a future reader does not conflate them.
Flag this prominently to the planner; do not silently pick one.

## Pattern Assignments

### New migration — display column + GRANT extension

**Analogs, and where they DIVERGE (surfaced per house rule — do not blend):**

Three migrations move a column into the `authenticated` GRANT allowlist, but they are **not one
template** — they diverge sharply in shape:

| Migration (self-declared #) | File | Shape |
|---|---|---|
| 066 | `20260420073003_allocator_holdings.sql` | `sync_error` GRANT is STEP 5 of a ~1000-line, many-feature migration (cron orchestration, `compute_jobs`, triggers). Its self-verify DO block checks the grant as one line among ~15 unrelated assertions. |
| **068** | `20260420103151_api_keys_last_429_at_grant.sql` | **Standalone, ~45 lines.** One `GRANT SELECT (col) ... TO authenticated`, a self-verifying `DO $$` block that checks exactly two things (grant present for `authenticated`, absent for `anon`), and an explicit ROLLBACK note in the header. |
| 075 | `20260422101911_api_keys_disconnected_at.sql` | `disconnected_at` GRANT is STEP 1 of a larger migration (also adds an index, two RPCs, worker-dispatch filter changes). Self-verify DO block covers the column, RPCs, index and grants together. |

**Pick 068 as the template.** It is the ONLY one of the three that is *purely* additive
column+GRANT — which is exactly D-02's shape ("the migration adds the column and extends the
GRANT. Nothing reads data."). 066 and 075 are bundled migrations solving a different, larger
problem each; their GRANT step is a sub-clause, not their reason to exist. Using their size as the
template would smuggle in unrelated scope. **Flag 066 and 075 for what they are — precedent that
the *convention* (GRANT-extend + self-verify + ARR comment) is well-established, not templates for
this migration's *size*.**

**Copy from 068 (full file read, `supabase/migrations/20260420103151_api_keys_last_429_at_grant.sql`):**
- Header banner format: `-- ===...===` rule, `-- Migration NNN: <one-line purpose>`, issue/phase
  tag, a paragraph naming which prior migration's allowlist is being extended and citing the
  sibling precedent migration by number, a `ROLLBACK:` line stating the exact reverse GRANT/ARR
  edit and why it's safe.
- Body: single `GRANT SELECT (<col>) ON api_keys TO authenticated;` — no `public.` prefix needed
  (068 omits it; 075 includes `public.` — both apply, `public.` is the current convention per the
  newer file).
- Self-verify: `DO $$ BEGIN IF NOT has_column_privilege('authenticated', 'api_keys', '<col>',
  'SELECT') THEN RAISE EXCEPTION ...; IF has_column_privilege('anon', ...) THEN RAISE EXCEPTION
  ...; RAISE NOTICE ...; END $$;` — the anti-leak check (anon must NOT gain the grant) is the
  load-bearing half; migration 027's REVOKE is what this is re-verifying didn't regress.

**Cross-reference for `venue_account_id`-shaped concerns (idempotency, self-verify posture, CHECK
constraints, comment density) if the planner's new column needs a CHECK or non-blank guard:**
`supabase/migrations/20260812083206_api_keys_venue_account_id.sql` is the most recent, most
heavily-verified `api_keys` migration in the repo (ABORTing pre-flight census, `DROP` + `CREATE`
banner for signature changes, post-verify block asserting body content not just presence). If the
new column needs any constraint beyond nullable-text, this file's idiom (not 068's, which has
none) is the one to copy — but note its size is proportionate to what it does (a UNIQUE index +
2 triggers + an RPC signature change), which D-02's "nothing reads data, nothing else changes"
scope should NOT need.

### New credential-update route

**Primary analog (skeleton, ownership, error-code shape, modern params):**
`src/app/api/strategies/[id]/name/route.ts` (full file read, 241 lines).

Copy:
- **Modern dynamic-segment convention:** `{ params }: { params: Promise<{ id: string }> }`, then
  `const { id } = await params;` — this is the CURRENT idiom. (Contrast:
  `keys/[id]/permissions/route.ts` parses `new URL(req.url).pathname.split("/")` instead, with an
  explicit comment *"Next 16 prefers searching the URL over a `params` arg in this old route
  helper; we keep this compatible..."* — **that is the OLDER, superseded shape for the SAME
  concern (id extraction on a dynamic route). Use the `name` route's `params: Promise<...>`
  convention for any new route; do not copy the URL-parsing form** — it is explicitly marked as a
  compatibility shim in its own comment, not the house style to propagate.**
- CSRF: `const csrfError = assertSameOrigin(req); if (csrfError) return csrfError;` first line.
- Auth: `createClient()` → `supabase.auth.getUser()` → 401 with a `code` + `error` pair on no user.
- Ownership + state gate in ONE query chain: `.update({...}).eq("id", id).eq("user_id",
  user.id).in("status", [...]).select("id")` then branch on `updatedRows.length === 0` → 404 with
  ONE honest error for "wrong owner, unknown id, or gated state" (never distinguish — avoids
  leaking row existence). **D-03's "password only, never login/server" maps directly onto this
  shape**: the `.update()` payload must contain only the re-sealed blob field(s), analogous to how
  this route's `.update({ name })` touches exactly one column.
- Error-envelope shape: every JSON error body is `{ code: "<SCREAMING_SNAKE>", error: "<human
  string>" }`, `code` written FIRST in the object literal (their own comment: *"the coverage laws
  derive their populations with a `code:`-first predicate, so an arm written `{ error, code }` is
  invisible to them"* — replicate the field order).
- `updateErr` (transport/DB failure) is a DISTINCT arm from `!updatedRows.length` (0 rows matched)
  — labelled `DASHBOARD_WRITE_INDETERMINATE` vs `DASHBOARD_ROW_STALE` respectively. **D-04's
  "failed validation persists nothing" and "a failed validation leaves every status field exactly
  as it was" (D-05) map onto this same indeterminate-vs-refused distinction** — the new route
  needs an equivalent third arm for "broker validation itself failed" (400/502, no DB write
  attempted at all), which is BEFORE this route's update step, not a variant of it.
- Rate limit is checked AFTER validation, before the write (`checkLimit` call, comment: *"so a
  rejected name does not burn one of the caller's own tokens"*) — same ordering should apply here:
  validate shape/ownership first, THEN check the rate limiter, THEN call the broker.
- `logAuditEvent(supabase, { action: "...", entity_type: "...", entity_id: id, metadata: {...} })`
  on success — fire-and-forget, not awaited/blocking the response. D-05's "clear sync_error /
  disconnected_at only on validated success" is the write payload analog of this route's
  single-column update; consider auditing the credential-update event the same way.

**Secondary analog (external validate-before-persist, this repo's OWN precedent for D-04):**
`src/app/api/keys/validate-and-encrypt/route.ts` (957 lines — grepped only, not fully read; import
block and control-flow markers at lines 1-37, 213-535).

Copy:
- `withAuth(handler)` wrapper is this route's auth style (vs. hand-rolled `auth.getUser()` in the
  `name` route) — **these are TWO DIFFERENT auth idioms live in the repo simultaneously.**
  `withAuth` additionally gates on profile-approval and centralizes the CSRF check; the `name`
  route's hand-rolled form is leaner but duplicates both checks per-route. Given the credential
  route is user-facing + data-integrity (D-04, CONSEQUENCES section: "review findings here BLOCK"),
  prefer `withAuth` — it is the more defended, more centrally-audited idiom, and `keys/[id]/...`
  is exactly the route family it already governs (`permissions/route.ts` also uses it). Flag `name`
  route's hand-rolled auth as the older/leaner sibling, not the one to propagate onto a new
  credentials-adjacent route.
- `getCorrelationId()` (`@/lib/correlation-id`) generated once, threaded into the outbound
  `resilientFetch` call to the analytics-service seam (`"X-Correlation-Id": correlationId`) AND
  into the client-facing error envelope on failure — this IS the mechanism D-06's "update failures
  render through `ErrorEnvelope`, sourcing copy via `buildEnvelope()`" needs: `buildEnvelope(code,
  correlationId, context)` takes exactly this correlation id.
- `CircuitOpenError` / `SeamBodyReadError` from `@/lib/seam-errors`, `seamErrorCode` from
  `@/lib/seam-discriminator`, `scrubSeamError` from `@/lib/seam-redaction` — the seam-call error
  taxonomy this route already applies when calling the Python analytics-service to validate
  credentials against a broker. The new update route's "re-validate against the broker" step
  (D-04) is the SAME kind of call (MT5 credential validation via analytics-service) and should
  reuse this exact taxonomy rather than inventing a new one.
- `userActionLimiter` / `checkLimit` / `rateLimitDenyJson` from `@/lib/ratelimit` — same rate-limit
  helpers as the `name` route, confirming this is the house convention across both create and
  mutate paths.

**Error-code vocabulary precedent:** `src/lib/wizardErrors.ts` already carries
`KEY_MT5_MASTER_PASSWORD` (`WizardErrorCode` union, ~line 109; copy entry ~line 1611) — "the login
worked but [wrong credential type] was given" — the closest existing MT5-specific validation
failure code. The new update route's broker-revalidation failure should either reuse this code
(if the failure mode is identical) or add a sibling entry in the same file following its shape
(`{ title, cause, fix: [...], actions: [...] }`), not invent an ad-hoc string.

### Update-failure UI (D-06's `ErrorEnvelope` requirement)

**Analog (client-side pairing for the `name` route, i.e. the closest existing "PATCH a single
field, render failure via ErrorEnvelope" round trip):** `src/components/strategy/RenameStrategyDialog.tsx`.

Copy:
```typescript
import { ErrorEnvelope } from "@/components/error/ErrorEnvelope";
import { buildEnvelope, type ErrorEnvelope as ErrorEnvelopeShape } from "@/lib/envelope";

const [envelope, setEnvelope] = useState<ErrorEnvelopeShape | null>(null);
...
try {
  const res = await fetch(`/api/.../${id}`, { method: "PATCH", ... });
  if (!res.ok) {
    const body = await res.json().catch(() => null);
    setEnvelope(buildEnvelope(body?.code ?? "UNKNOWN", correlationId, { ... }));
    return;
  }
  ...
} catch {
  setEnvelope(buildEnvelope("UNKNOWN", correlationId));
}
```
render: `{envelope && <ErrorEnvelope envelope={envelope} />}`.

**Underlying pieces, already read:**
- `buildEnvelope(code, correlation_id, context?)` (`src/lib/envelope.ts:75-91`) — maps a
  `WizardErrorCode` through `formatKeyError()` (from `src/lib/wizardErrors.ts`) into the
  `{ ok, code, human_message, cause, debug_context, correlation_id, recoverable,
  retry_after_seconds }` shape. **The `code` passed in must be a valid `WizardErrorCode`** — this
  is why the new route's failure vocabulary should reuse/extend `wizardErrors.ts` (see
  `KEY_MT5_MASTER_PASSWORD` above) rather than inventing a bare string; `buildEnvelope` falls
  through to an `UNKNOWN` entry for anything it doesn't recognise, so an ad-hoc code silently
  degrades to a generic envelope.
- `ErrorEnvelope` component (`src/components/error/ErrorEnvelope.tsx:1-40+`) — canonical
  surface-agnostic renderer per DESIGN-02; all buttons must be `type="button"` (documented
  Pitfall 9, relevant if the update form is inside another `<form>`).
