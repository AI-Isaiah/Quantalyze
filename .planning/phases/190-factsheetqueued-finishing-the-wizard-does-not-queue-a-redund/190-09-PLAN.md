<objective>
Keep the flags a success wrote next to the numbers that success stored, for the whole re-run window, including the minutes between the derive hop's flag prestamp and the compute hop's success write. The checker found that plan 03's evidence rule, which needs a success-written `cumulative_method` marker, read false after `_prestamp_dq_flags`. A single-key broker re-run (the founder's own case) would then hide its factsheet from the prestamp until the success write. That breaks D-02 ("allocators keep seeing the last computed numbers") and SC-3 for exactly the case the phase exists for.

Purpose: plan 03 keeps its consistency check: shown numbers never sit beside flags a different run wrote (SC-6). The flags that go with the numbers must therefore exist somewhere through the derive hop. This plan carries them inside the prestamp the derive already writes, as a snapshot bound to `computed_at`. Plan 03 reads the snapshot.

Output: one constant, one pure helper and one guarded read in `run_derive_broker_dailies_job`, a new pytest file, and a runner pin. No migration, no TypeScript, no change to what the compute hop reads.

The contract, stated identically in plan 03 (the TypeScript reader):
- Key: `data_quality_flags.last_success_snapshot`. Its value is a JSON object `{"computed_at": <the row's computed_at string exactly as read>, "flags": <the row's data_quality_flags object as read, without any last_success_snapshot key>}`.
- Writer: only the derive hop's prestamp, and on every strategy-mode prestamp: the snapshot object, or JSON null when there is none (the pre-read failed, or the row's flags carried neither the marker nor a well-formed snapshot). The success writers rebuild or merge the flags and write a top-level `cumulative_method`. The reader then prefers the live flags, so a snapshot is never read after a success.
- Reader rule (plan 03): use the live flags when they carry a top-level string `cumulative_method`. Otherwise use the snapshot's flags only when the snapshot is a well-formed non-null object and its `computed_at` is the same instant as the row's `computed_at`. Otherwise use the live flags. D-04 (founder 2026-11-03): a terminal-success row whose live flags lack the marker and carry the key, with no snapshot bound, is withheld as not_computed. The key, not the missing marker, is the evidence that a prestamp replaced the success flags, because a legacy row computed before the marker existed lacks the marker at rest and carries no key.
- Why the binding is sound: the two writers of `strategy_analytics.computed_at` are the two terminal-success writers (`_mark_complete` in `run_csv_strategy_analytics` and the composite stitch's persist, both `"computed_at": "now"`, plan 01 verdict SNAPSHOT). The hold trigger keeps `computed_at` through computing and failed. So a snapshot whose `computed_at` still equals the row's was taken after the last success that stored the row's numbers. Any later success moves `computed_at` or writes a top-level marker, and the snapshot is then never used.

Design choices (recorded here and in the SUMMARY; planner defaults the founder can still flip, apart from the null-valued key, which D-04's detection needs):
- No migration. RESEARCH recommends none. The prestamp already replaces `data_quality_flags` wholesale, and the success rebuild drops unknown keys, so a key nested there lives exactly from one derive to the next success, which is the lifetime the snapshot needs. A sibling column would outlive the window and would need a migration that auto-applies to PROD on merge, plus a deploy-window guard.
- Rejected: moving the prestamp into a staging column the compute hop reads. That changes what the compute hop reads. The API service and the backfill worker both claim jobs and deploy independently, so a chain whose derive ran on new code and whose compute ran on old code would rebuild its flags from the previous derive's guard and marks keys. `marks_covered_from` drives the dense reindex, so that could move a published number.
- Rejected: a snapshot column written by the success writers. It needs a migration plus a backfill of every existing row, or each strategy's first post-deploy re-run would still hide.
- Version skew fails closed except in one recorded case. A derive on code from before this plan writes no key. A pending or computing row in that window withholds (fail closed). A terminal-success row in that window is not detected by D-04, so until that chain's success it still shows the new derive's flags beside the last success's figures. Plan 08 records this deploy-skew limit. A TypeScript reader from before plan 03 ignores the key.
- Known limits carried to plan 08: the snapshot carries flags only. `metrics_json_by_basis`, the MTM, smoothed and cash_settlement series rows and `series_completeness` are still written by the derive hop. Plan 05 makes the MTM and smoothed toggles read the new derive's by-basis, series and `mtm_gated_reason` together. The day basis follows the new derive's frozen conventions, which differ from the last success's only when the day-basis setting changed in that run.
</objective>
