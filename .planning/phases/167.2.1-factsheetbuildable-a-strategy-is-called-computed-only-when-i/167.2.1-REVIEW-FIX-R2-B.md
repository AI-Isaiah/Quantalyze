### WR-02 / SFH-R2 N-4: a transient admin read error cached a `null` on the public factsheet for the TTL

**Files modified:** `src/app/factsheet/[id]/v2/page.tsx`,
`src/app/factsheet/[id]/v2/page.public-cache-key.test.tsx`,
`src/app/factsheet/[id]/v2/page.owner-compute-state.test.tsx`,
`src/__tests__/phase-148-owner-lane-cache-isolation.test.ts`
**Commit:** `d7cd45e56`
**Status:** fixed: requires human verification (this changes what gets cached)

**Applied fix:**
- `buildFactsheetPayloadCached`: the `unstable_cache` callback now calls
  `fetchAndBuildPayloadWithReason(id, withPublishedOnly)`. On `reason === "read_error"` it throws a
  module-private `FactsheetReadError`. Every other reason is a fact about the stored row, so it is
  still cached as `null`.
- The page catches only `FactsheetReadError`. The public lane then renders the existing
  placeholder, KCS10's one sentence ("The detailed factsheet for this strategy is not available
  yet."), and nothing is cached. It does not return a 500.
  - The public lane has no separate "unreadable" state. KCS10 is documented as true in every
    state, and an outage is one of those states.
  - The `payload pending` warn now carries `publicReadFailed`.
  - Any other throw still goes to the error boundary.
  - No second Sentry capture is added. The resolve stage has already captured the error once, with
    its code, and the test asserts exactly one capture.
- **Re-verified in the bundled Next (16.2.11),**
  `node_modules/next/dist/server/web/spec-extension/unstable-cache.js`, function `unstable_cache`:
  - **Cache miss** (both the work-store branch and the no-store branch): the code awaits
    `workUnitAsyncStorage.run(innerCacheStore, cb, ...args)` *before* it calls `cacheNewResult`.
    So a throw propagates and nothing is stored.
  - **Stale entry:** the background `revalidationPromise` has a `.catch` that logs and
    `return cachedResponse`, and it does not call `cacheNewResult`. The last good entry survives,
    and the next request retries.
  - **Residual:** during that stale window, the request that triggers the revalidation is served
    the stale value. That is Next's rule and was already true.
- **Accepted residual, recorded in a code comment:** a composite whose `csv_daily_returns` read
  failed still arrives as `composite_unbuildable`, because `readCompositeFactsheet` folds the error
  into an empty series. So it is still cached as `null`. This is accepted under D-07 and owned by
  Phase 169 plan 04.
- **The phase-148 pin was moved on purpose.**
  - It now requires `fetchAndBuildPayloadWithReason(id, withPublishedOnly)`, and it refuses the
    `fetchAndBuildPayload(id,` text.
  - A new pin requires `"read_error"` and `throw new FactsheetReadError` in the callback.
  - Reverting to the old call makes both of those pins fail. This was measured; see below.
  - The literal-predicate rule, the single-`unstable_cache` rule and the no-visibility-parameter
    rule are unchanged.
  - `fetchAndBuildPayloadWithReason` is declared in the canonical builder module, so rule 4b
    (declarers and importers) needs no allowlist change.
- **`PUBLIC-PENDING` was updated deliberately.** It asserted that the public lane never calls
  `fetchAndBuildPayloadWithReason`, and the cache fill now does. It now allows exactly one call and
  pins that call's predicate to `withPublishedOnly` **by identity**. That keeps the real property:
  the public lane never runs the owner build.

**New test:** `READ-ERROR-NOT-CACHED` in `page.public-cache-key.test.tsx`. Two requests under the
same `computed_at`: the first has an admin read error (code `57014`), the second reads cleanly. The
test asserts:
- the first request renders the placeholder sentence and does not throw;
- there is exactly one capture, with tags `stage factsheet-resolve`, `reason read_error` and
  `code 57014`;
- the second request builds, `adminReads === 2`.

The cache double now documents that a throw skips the store, which mirrors Next's miss path.

### WR-03: the owner page said "could not be built from its results" beside "we could not check"

**Files modified:** `src/lib/status-surface-copy.ts`, `src/lib/status-surface-copy.test.ts`,
`src/app/factsheet/[id]/v2/page.tsx`, `src/app/factsheet/[id]/v2/page.owner-compute-state.test.tsx`
**Commit:** `7e184c79c`
**Status:** fixed

**Applied fix:**
- **New copy row `KCS09-FINISHED-UNREADABLE`**, tone muted:
  *"The last computation finished. We could not read its results to build the factsheet."*
  - It is declarative, sentence case and in the active voice ("We could not read"), per DESIGN.md
    § Voice / microcopy.
  - It says only what is known: the jobs finished, and the read failed.
- **Remedy:** the existing read-again line (`KCS09-UNREADABLE`, "Reload this page to try again.").
  It is never "Contact support … to have it checked", because an outage is not a data fault.
- **Copy API:** `ownerStateLine` and `ownerRemedy` take an optional
  `OwnerBuildFacts = { buildUnreadable: boolean }`.
  - `stateLineKeyOf` maps `finished` to `finished_build_unreadable` only when `buildUnreadable` is
    true.
  - Only the finished state changes, because it is the only line that claims a build outcome.
    Every other state line is about the jobs alone and stays true.
  - Totality is kept: the new key is in `STATE_LINES` and `REMEDY_RULES`, both of which are
    `satisfies Record<StateLineKey, …>`.
- **Page:** `FactsheetV2Page` passes `{ buildUnreadable: ownerBuildability?.unreadable === true }`
  to both calls. `ownerBuildabilityOf` marks both `read_error` and `not_visible` as unreadable.
- I chose option (a) over (b), omitting the line. The page renders its computation-status section
  only when both a line and a remedy exist. Otherwise it falls back to KCS10, the *public*
  sentence, which is the wrong voice on the owner lane.

**Tests:**
- `S7-OWNER-BUILD-READ-ERROR` now asserts:
  - the KCS09-FINISHED text is absent, and so is the contact-check remedy;
  - the state line is the new text, with class `text-text-secondary`;
  - the remedy is "Reload this page to try again.".
- `S7-OWNER-BUILD-NOT-VISIBLE` asserts the same, except for the contact-check absence.
- The existing table case `KCS09-FINISHED`, where the build is readable and not computed, still
  renders the finished line. That is the control.
- New copy tests:
  - the text, tone and id of the new line;
  - the read-again remedy for every shape;
  - a readable build keeps KCS09-FINISHED;
  - `queued`, `failed permanent`, `never_started` and `unreadable` are unchanged when the build is
    unreadable.
