## Warnings

### WR-01: The probe path still sends one Sentry event per failed or unbuildable row per page load. The aggregation covers only throws, and those are not how saturation arrives.

**File:** `src/lib/factsheet/fetch-and-build-payload.ts`: `resolveFactsheetInputs` (the `if (error)`
capture), `compositeUnbuildable` and `singleKeyUnbuildable`. Also `src/app/(dashboard)/strategies/page.tsx`
(`StrategiesPage`: the `probeThrows` aggregate and its `probe_failures` tag).

**Issue.** This overlaps SFH-R2 N-1 on `read_error`. It adds two facts.

1. The scenario WR-01 was filed for, pool saturation, reaches the stage as a supabase-js
   `{ error }` and not as a throw. It is captured once per failed row with
   `caller: "probe"`, at error level. The page aggregate only ever sees a real throw: a missing
   service key, or a code bug. So the one event per page load and the `probe_failures` count
   miss exactly the failures they were built for. The tag name also suggests it counts every
   failed check, and it counts only throws.
2. The stage also captures two **durable data states** on every probe:
   - `composite_unbuildable`, at level warning;
   - `malformed_series`, with no `level`, so an error.

   `/strategies` is the dashboard's landing page and is unpaginated. An owner with k such rows
   sends k events on every navigation, for as long as the data stays that way. That is the
   N-events-per-load pattern WR-01 set out to remove, now with no failure behind it at all.

**Fix. This answers open question (1): yes.**
- Capture in the stage only when `caller === "build"`.
- For `"probe"`, return the facts instead: widen the not-buildable arm to
  `{ buildable: false; reason; code?: string; gate?: string }`.
- `StrategiesPage` then emits **one** event per page load, with a count per reason and the
  distinct codes as tags, for example
  `{ read_error: "3", composite_unbuildable: "1", codes: "57014" }`.

The owner lane and the public cache fill are `"build"` callers. So H-1's property, that a
"contact support" note has an event behind it, still holds whenever the factsheet itself is
opened. The `/strategies` aggregate carries the same fact once per load. Rename `probe_failures`,
or count every failure kind in it. Pin it with a `/strategies` test: 6 rows answering
`read_error` and 2 `composite_unbuildable` rows give exactly one capture carrying the counts.
Neuter the fix, observe RED, restore.

### WR-02: A transient admin read error still caches a `null` for the full TTL under the current `computed_at`. Fixer B's other residual does not exist.

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`buildFactsheetPayloadCached`, the
`unstable_cache` callback `fetchAndBuildPayload(id, withPublishedOnly)`).

**Issue.** This overlaps SFH-R2 N-4 on the symptom. What it adds is the corrected residual set and
a measured fix shape.

- **The residual that does not exist.** Fixer B recorded (a): "a recompute entering `computing`"
  keeps the same `computed_at`. That is not so. In `sync_strategy_analytics_status` (the latest
  definition, migration `20260906120000`), branch (a) is the `v_nonterminal_count > 0` arm. Its
  `ON CONFLICT DO UPDATE` sets `computed_at = now()` on **every** bridge call, including the
  transition into `computing`. Branch (c) stamps it again at the end. So the key moves when the
  job starts and again when it finishes. The protected branch (b-prime) writes no status and no
  `computed_at`, so it changes nothing the builder reads.
- **The residual that does exist.** A `read_error` is one PostgREST blip. It makes the callback
  return `null`, and `unstable_cache` stores that `null` under the current `computed_at` for
  3600 s.
  - During that hour a published strategy's public link serves the "still computing"
    placeholder.
  - Meanwhile `/strategies` probes fresh, gets `buildable: true`, and shows **no note**.

  That is the exact contradiction round-1 WR-02 was filed for.
- **The same shape that cannot be told apart.** A `csv_daily_returns` outage on a composite folds
  into `composite_unbuildable` (D-07). Its `null` is cached the same way, and nothing in the stage
  can distinguish it. Record that, and do not claim the fix below covers it.
- **Next's staleness rule.** In `unstable-cache.js`, a stale entry is returned once more while it
  is revalidated in the background. So "drains on the TTL" really means "drains on the first
  request after the TTL, which still gets the stale value".

**Fix. The shape is measured in `node_modules/next/dist/server/web/spec-extension/unstable-cache.js`.**
On a cache miss, a callback that throws propagates without reaching `cacheNewResult`. On a stale
revalidation, a throw returns the last good value. So:

```ts
return unstable_cache(
  async () => {
    const built = await fetchAndBuildPayloadWithReason(id, withPublishedOnly);
    // A failed read is an outage, not an answer: never let it outlive its request.
    if (built.reason === "read_error") throw new FactsheetReadError();
    return built.payload;
  },
  ["factsheet-v2-payload-v6", id, computedAt],
  { revalidate: 3600, tags: ["factsheet-v2", `factsheet-v2:${id}`] },
)();
```

Then catch `FactsheetReadError` in the page and render the same placeholder, uncached. The stage
has already captured the error once. This changes the callback text that
`src/__tests__/phase-148-owner-lane-cache-isolation.test.ts` pins as
`fetchAndBuildPayload(id, withPublishedOnly)`. Update that pin so it still requires the
`withPublishedOnly` literal and no parameter, and add the new export to its allowlist. Add a
`page.public-cache-key.test.tsx` case, `READ-ERROR-NOT-CACHED`: a read error, then a clean read,
under the same `computed_at`, must build twice. Neuter, observe RED, restore.

This answers open question (2). Drop residual (a). Fix residual (b) as above. Record the
composite-outage variant as accepted under D-07.

### WR-03: On the owner page, a failed owner build renders "the factsheet could not be built from its results" above "We could not check what a private link shows". This is CR-01's shape, introduced by the H-2 fix.

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`FactsheetV2Page`, the owner `!payload` branch:
`ownerLine = ownerStatus && ownerStateLine(ownerStatus.state)` together with the `shareNote`
ternary on `ownerBuildability?.unreadable`). The copy is `KCS09-FINISHED` in
`src/lib/status-surface-copy.ts`.

**Issue.** The state line comes from compute **jobs**. The note now comes from the owner **build**.
When the build's admin read fails (`read_error`), or finds no row (`not_visible`), the jobs are
usually all done, so the state is `finished`. The page then renders:

- the state line (KCS09-FINISHED): *"The last computation finished, but the factsheet could not
  be built from its results."*
- the note (KCS12-PROBE-UNREADABLE): *"We could not check what a private link to this strategy
  shows right now. Reload this page to check again."*

The first line is **false**: nothing was built from the results, because the read failed. The
second line correctly says the page does not know. Side by side, they contradict each other.
`ownerRemedy` for `finished` then sends the owner toward a data remedy for an outage.

Before H-2 the note was also wrong, so the pair was consistently wrong. H-2 fixed the note and
not the line. `S7-OWNER-BUILD-READ-ERROR` seeds exactly this state
(`chainJob("compute_analytics_from_csv", "done")`) but asserts only the last element (the note),
so the state line is untested.

This is a user-facing, bounded (one request), transient condition. It is on the page the owner
uses to decide whether to share, and D-02's rule is that the note must be true in every arm it is
selected for. The same rule applies to the line beside it.

**Fix.** When `ownerBuildability?.unreadable`, do not render a state line that claims a build
outcome. Two options:
- (a) Replace `ownerLine` with a line that says what is known: *"The last computation finished.
  We could not read its results just now. Reload this page to check again."* Give it its own
  KCS id, and suppress `ownerRemedyLine`.
- (b) Omit the state line, and let the note carry the page.

Then extend `S7-OWNER-BUILD-READ-ERROR` and `S7-OWNER-BUILD-NOT-VISIBLE` to assert that the
panel does **not** contain the KCS09-FINISHED text. Neuter, observe RED, restore.

## Info

### IN-01: The comments give the wrong reason `computed_at` moves

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`buildFactsheetPayloadCached`) and
`src/lib/factsheet/fetch-and-build-payload.ts` (the "CACHE KEY REALITY" block on
`fetchAndBuildPayload`, and the MTM-01 comment in `buildFromResolved`).

**Issue.** Both comments say that the finalizer stamps `computed_at = now()` on every
**successful** run, and that a status change within one run drains on the TTL. As WR-02 shows,
branch (a) stamps it on every bridge call, including the start of a job. The guarantee is
stronger than the comments say. A future reader who trusts the weaker claim may "fix" a residual
that does not exist, for example by adding the status to the key.

**Fix.** Say "the status bridge stamps `computed_at = now()` on every job transition it
resolves (branches (a) and (c)); the protected branch (b-prime) writes neither status nor
`computed_at`".

### IN-02: The H-1 composite and malformed captures cannot be tied to a strategy

**File:** `src/lib/factsheet/fetch-and-build-payload.ts` (`compositeUnbuildable`,
`singleKeyUnbuildable`).

**Issue.** The tags are `{ stage, caller, gate }` and carry no id, which is correct under this
repo's tags-only rule. But the note these reasons select says "Contact support … to have them
checked", and from the event alone support cannot tell which strategy it is. The only link is the
timestamp: the `resolve(<caller>)` console line beside it carries `id`, and it is in the Vercel
logs, not in Sentry. H-1 wanted "contact support" to be answerable. Today it is answerable only
through a manual join between the two.

**Fix.** Write that join in `compositeUnbuildable`'s docstring: Sentry event time, then the
`resolve(<caller>)` log line with the id. Or decide explicitly whether a strategy id is
acceptable as a Sentry tag for a **published** row. No code change is required.

### IN-04: Open question (3). The client-side `captureToSentry` no-op is a class. Book it; do not fix it in this phase.

**File:** `src/components/strategy/ApiKeyManager.tsx` (`readKeyCompositeMemberships`) and every
other `"use client"` file that calls `captureToSentry`. A count taken at this SHA found 16 files.
Regenerate the count rather than trusting it.

**Recommendation.**
- Do not add a client `Sentry.init` inside 167.2.1. It is a security decision:
  `src/instrumentation.ts` warns that a browser channel needs `scrubSentryEvent` before it opens.
  It would span 16 files, and it is observability, not data integrity. Under the repo's review
  policy, that makes it a booked item, not a phase.
- Fixer C's docstring now states the real coverage: the route's 5xx are captured server-side with
  their code, and a 429 or 503 is warned server-side. That is enough for this phase.

  - a client `Sentry.init` whose `beforeSend` is `scrubSentryEvent`;
  - a tags-only, rate-limited server beacon route.
- Until one of those exists, new client code should not add `captureToSentry` calls on the belief
  that they report.
