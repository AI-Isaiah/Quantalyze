# Phase 167.2.1: FACTSHEETBUILDABLE - Research

**Researched:** 2026-09-25
**Domain:** Next.js 16 server pages + Supabase (RLS vs service-role reads), factsheet payload builder, key-card delete flow
**Confidence:** HIGH for the code facts (every anchor read this session). MEDIUM for the cost numbers (one local micro-benchmark). LOW for how many PROD rows are affected (not measured; no remote DB access in this session, by instruction).

## Summary

**The main finding: WR-02's blocking premise is false, and this phase needs no migration for it.**
167.2's review recorded WR-02 as UNFIXABLE-IN-PHASE because "the series sit behind deny-all
RLS" and "no owner-readable scalar records payload buildable". The baseline schema says
otherwise. Every input whose absence makes `fetchAndBuildPayload` return `null` can be read by
the owner:
- `strategies`
- `strategy_analytics.computation_status`, `daily_returns`, `returns_series`, `data_quality_flags`
  and `metrics_json_by_basis`, through policy `analytics_read`
- `csv_daily_returns`, through policy `csv_daily_returns_owner_select`

The only deny-all table on the builder's path is `strategy_analytics_series`, which holds the
MTM and smoothed series. Its readers degrade to "no bundle" and never make the builder return
null. So buildability can be **decided at read time, on the server, by the builder's own code**.
Nothing needs to be stored.

**Primary recommendation, WR-02.** Split `fetchAndBuildPayload` into two stages:
1. A resolve stage that returns either the build inputs or a typed `notBuildable` reason.
2. The build itself.

Export a probe, `probeFactsheetBuildable(id, visibility)`, that runs stage 1 and the builder's
own point-count predicate. Move the predicate out of `buildFactsheetPayload` into one exported
function, and have both stages call it. `/strategies` then probes only its computed rows, and it
routes each unbuildable row through the **existing** `readRecipientArm → recipientShareNote`
path. The share page runs the same path when its payload is null.

The list, the share page and the owner factsheet then decide from one code path. Use no stored
flag: a flag written by the Python job would be a second implementation of TypeScript gates,
which is the drift class this repo keeps paying for.

**Primary recommendation, R2-L4(b).** Move the Delete-confirm membership read server-side. Add a
GET route, `src/app/api/keys/[id]/memberships`, wrapped in `withAuth`. It proves ownership with
an explicit `user_id` equality and reads `strategy_keys ⋈ strategies` on the service-role client.
An RLS regression then cannot turn the read into an error-free `[]`. This also needs no
migration. A SECURITY DEFINER RPC is the fallback if the founder wants the guard at the database
layer. It is specified below, and it would carry the three-reviewer rule and auto-apply to PROD.

### Pattern 1: one resolve stage, two consumers (WR-02)

**What:** Pull stages G0 to G3 of `fetchAndBuildPayload` into a module-private
`resolveFactsheetInputs(admin, id, visibility)`. It returns
`{ ok: true, strategy, analytics, dqf, isComposite, dailyReturns, compositeBuildOpts? }` or
`{ ok: false, reason }`. `fetchAndBuildPayload` becomes resolve → (single-key basis opts) → build.
Its bytes and its null behaviour do not change. Export:

```ts
// src/lib/factsheet/build-payload.ts: the G4 predicate, exported and used by buildFactsheetPayload itself
export const MIN_FACTSHEET_SERIES_POINTS = 2;
export function hasBuildableSeries(rows: DailyReturn[]): boolean {
  return normalizeDailyReturns(rows).length >= MIN_FACTSHEET_SERIES_POINTS; // the existing private normalize
}

// src/lib/factsheet/fetch-and-build-payload.ts
export type NotBuildableReason =
  | "not_visible" | "read_error" | "not_computed" | "composite_unreadable" | "no_series" | "too_few_points";
export type FactsheetBuildability = { buildable: true } | { buildable: false; reason: NotBuildableReason };
export async function probeFactsheetBuildable(
  id: string,
  visibility: StrategyVisibility,          // REQUIRED, as for the builder
): Promise<FactsheetBuildability> { /* resolveFactsheetInputs + hasBuildableSeries; no basis reads, no compute */ }
```

These names are proposals [ASSUMED]; the planner fixes them. The `DailyReturn` type and
`normalizeDailyReturns` exist [VERIFIED: build-payload.ts:1, :162].

**Why not simply call `fetchAndBuildPayload` per row?** It is exact, but it pays the full
compute. Measured locally this session: `buildFactsheetPayload` took **13.7 ms/op on a 365-point
series and 47.2 ms/op on 1500 points**, CPU only, on the local machine. That runs serially on one
Node thread per request, and it adds the MTM series reads. The probe skips both. It is the right
answer only if the refactor is refused.

**Why not a stored flag?** A column written by the Python analytics job would re-implement G2 to
G4 (the three `daily_returns` shapes, the equity-curve fallback, dedup, the composite headline
check) in a second language, and the two would drift. A generated column cannot express the
normalization. It would also need a migration and the three-reviewer gate, and it could not be
backfilled (the house rule forbids fabricating provenance), so every existing row would read
"unknown". Reject it.

**Which client:** the probe keeps the builder's own `createAdminClient()` and the owner predicate
`(q) => withPublishedOrOwner(q, user.id)`, exactly as the owner lane calls the builder
(`v2/page.tsx:413`). Using the same client and the same code gives parity by construction. It
also avoids a trap: on the RLS client, a regressed policy would make the list claim "not
available" for a buildable row. The page's list query already restricts to
`.eq("user_id", user.id)`, so no foreign id reaches the probe.

### Pattern 2: the list joins the share page's own path

In `strategies/page.tsx`, keep the cheap status filter first: rows the embed calls uncomputed
behave exactly as today. For the computed rows, run the probe with `Promise.all`. A row counts as
"without a buildable factsheet" when it is uncomputed OR `probe.buildable === false`. Such a row
goes through the unchanged `readRecipientArm → recipientShareNote(mode, arm)`, the SAME
derivation the share page uses when its payload is null. A probe that **throws** maps to arm
`unreadable` (`KCS12-UNREADABLE`, the "placeholder page" sentence). It is logged and
captured with tags only, matching the page's `compute-state` capture. It never counts as
"buildable".

A published row keeps `PUBLIC_URL_NOTE` whatever the arm (167.2 IN-04: no RPC).

**Copy:** reuse the locked strings verbatim. A computed but unbuildable row whose chain job is
`done` derives `finished`, which maps to `not_available`. That renders KCS12-MINT-B, the same
line the owner factsheet already shows for that row (167.2 REVIEW WR-02: "The owner factsheet lane
handles this row correctly (`KCS09-FINISHED` plus `KCS12-MINT-B`)"). One weakness: the tail "The
numbers appear there once a computation succeeds" is imprecise for a row whose computation DID
succeed. That is an open copy question (see Open Questions), not a blocker.

### Pattern 3: server-side membership read (R2-L4(b))

Add a new `GET src/app/api/keys/[id]/memberships/route.ts`, wrapped in `withAuth`, following the
sibling `api/keys/[id]/permissions/route.ts`:
1. `withAuth`, then `checkLimit(userActionLimiter, …)`, the id taken from the path, `NO_STORE_HEADERS`.
2. `createAdminClient()`, then `api_keys.select("id").eq("id", keyId).eq("user_id", user.id).maybeSingle()`. The ownership check is an explicit equality, **not** RLS. No row gives 404, with no existence oracle.
3. On admin, `strategy_keys.select("strategy_id, strategies ( name, status )").eq("api_key_id", keyId)`. `strategy_keys.owner_id` is forced equal to the key owner and the strategy owner by `enforce_strategy_keys_owner_coherence` [VERIFIED: baseline.sql, function body read], so every returned name is the caller's own.
4. Answer `{ memberships: [{ name, status }] }`. A read error gives 500 and a capture.

In `ApiKeyManager.readKeyCompositeMemberships`, replace the browser `strategy_keys` read with
`fetch` to this route. Keep the 15 s bound (`BASELINE_READ_BOUND_MS`) and the existing
`"unreadable"` arm. Treat any non-2xx, non-JSON, or missing/non-array `memberships` as
`"unreadable"`, which gives KCS-DELETE-UNCHECKED. That arm already warns and is already
captured (`stage: "delete-membership-read"`). No copy changes. The route performs no mutation, so
`audit-coverage.test.ts` does not require `logAuditEvent`. It is not under `api/admin`, so the
admin-route manifest is untouched. It is not a page, so the route-contract manifest is untouched.

**Residual (record it, do not fix it):** a membership added between the read and the Delete
(TOCTOU) still cascades unwarned. The published-composite trigger
`api_keys_published_composite_delete_guard` still refuses for PUBLISHED composites. It raises
`foreign_key_violation` [VERIFIED: baseline.sql:12954, function body read]. Closing the window
would need a delete RPC that compares an acknowledged membership count, which is a migration.
The founder decided the flow warns and does not block, so closing it is out of scope unless the
founder asks.

### Migration fallback (only if the founder wants SC5 at the DB layer)

`get_api_key_composite_memberships(p_api_key_id uuid) RETURNS TABLE(name text, status text)`,
`LANGUAGE sql` or plpgsql, `SECURITY DEFINER`, `SET search_path = public, pg_catalog`. It raises
`42501` when `(SELECT user_id FROM api_keys WHERE id = p) IS DISTINCT FROM auth.uid()`, following
the house precedent `delete_allocator_api_key` [VERIFIED: baseline.sql, body read]. It uses
`REVOKE ALL … FROM PUBLIC` and `GRANT EXECUTE … TO authenticated`. It creates only a function and
reads no data at apply time, so it **applies cleanly on an empty TEST DB**. Costs:
- the three reviewers;
- a `supabase/tests/test_*.sql` gate, which moves the SQL-corpus censuses. GREP them, do not count them (memory: supabase/tests censuses);
- a timestamp later than 167.1.2's planned `20260925120000_api_keys_account_identity.sql`.

### Anti-Patterns to Avoid
- **A second copy of the gates in the page.** Do not re-implement G1 to G4 inline in `strategies/page.tsx`. That repeats the discovery-detail duplication one more time.
- **Letting the probe diverge from the builder.** The builder must CALL the resolve stage and `hasBuildableSeries`, not merely sit beside them.
- **Folding a probe error into "buildable".** Error is not absence: an error yields `unreadable`.
- **Probing uncomputed rows.** They already get a note, and probing them wastes the heavy select.
- **Reading the membership through RLS "and also" the route.** One source. The route replaces the browser read.

## Common Pitfalls

### Pitfall 1: the builder's own guard tests
**What goes wrong:** the refactor reddens `src/__tests__/phase-148-owner-lane-cache-isolation.test.ts`. That test pins `fetch-and-build-payload.ts` as the ONE declaring file and walks the builder's transitive closure for cache reach (`CLOSURE_FLOOR = 30`, a lower bound).

|---------|--------|---------------------|
