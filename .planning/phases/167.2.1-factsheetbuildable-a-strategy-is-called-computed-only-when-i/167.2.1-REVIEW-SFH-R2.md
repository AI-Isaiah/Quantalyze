## MEDIUM

### N-1 — The WR-01 "one event per page load" covers only probe THROWS, but saturation arrives as a returned `read_error`, which the resolve stage captures once per row

**Location:** the `StrategiesPage` `probeThrows` aggregate, `resolveFactsheetInputs` G0 (`captureToSentry(... "admin strategy read failed" ...)`), `compositeUnbuildable` and `singleKeyUnbuildable`.

**Scenario.** The comment on `probeThrows` justifies the aggregate with "a saturated pool makes every row throw". supabase-js does not throw on a PostgREST error, a statement timeout or a fetch failure. It returns them in `{ error }`, and `createAdminClient` sets no `throwOnError`. So pooler exhaustion on a list of 30 computed rows reaches G0 as 30 `read_error`s, and G0 captures **30 events** (`stage: factsheet-resolve`, `caller: probe`) on every load. A failed composite `csv_daily_returns` read does the same through `compositeUnbuildable` (`gate: empty_series`), and so does every durable malformed row through `singleKeyUnbuildable` at error level, on every list load. The only thing the aggregate batches is the rare case, such as `createAdminClient` throwing on a missing key. The common failure produces the per-row flood the fix set out to remove. The counts are also wrong: the event count measures rows times page loads, not the size of the outage.

**Fix.** Keep the stage's capture for `caller: "build"`. For `caller: "probe"`, carry the code out in the reason (`{ reason: "read_error", code }`) and do not capture in the stage. Then have the page fold `read_error` codes, composite refusals and malformed rows into its post-fan-out aggregate: one event per `(stage, code)` per load, with the count as a tag. Alternatively, pass a collector into `probeFactsheetBuildable`. Pin the fix with a test in which 5 rows answer `read_error` and `captureToSentry` is called at most once for that stage.

### N-2 — The aggregate keeps only the FIRST throw, so a second, different cause never reaches Sentry

**Location:** `StrategiesPage`, `if (probeThrows.length > 0) { const first = probeThrows[0]; captureToSentry(first ...) }`.

**Scenario.** `probeThrows` is filled in completion order. Row 3 throws a transient `fetch failed`. Row 11 throws a `TypeError` from a code regression in the resolve stage, such as a new column read on a null. Sentry receives one event with the transient's stack and `probe_failures: "2"`. The regression's type, message and stack are only in a Vercel `console.error` line, which does not alert. Whichever cause completes first hides the other, and completion order changes from load to load, so the issue even flips identity between loads.

**Fix.** Bucket the throws by `${err.name}:${err.message.slice(0, 80)}`. Capture one event per distinct bucket, capped at about 3 per load, each tagged with its own count and with `probe_failure_kinds` set to the number of buckets.

### N-3 — No probe has a time bound, and the limiter turns one slow read into a page-wide stall that is never captured

**Location:** `concurrencyLimiter` / `runProbe` in `StrategiesPage`, and `createAdminClient`, which has no fetch timeout.

**Scenario.** The limiter itself is correct. A rejected task releases its slot in the `finally`, and a synchronous throw from `task()` is inside the `try`. It also has no deadline. Four probes stuck on a pooler wait, or on a large composite csv read, hold all four slots, and every other computed row queues behind them. Even when nothing hangs, the list's latency is now about ceil(N/4) sequential heavy reads on the dashboard landing page. If the platform function timeout fires first, the request dies with a 504. The post-fan-out `captureToSentry` never runs, and the queued rows never log. That is a failure with no Sentry event and no per-row line. Before the limiter a hung probe also hung `Promise.all`, so the stall is not new. The limiter widens the window, and the aggregate moved the only capture to after the point a timeout kills.

**Fix.** Bound each task inside `runProbe`: race it against a timer that rejects with a named `ProbeTimeoutError`, about 5 s, which lands in `probeThrows` and renders `probeUnreadableShareNote`. Thread an `AbortSignal` into the query (`.abortSignal(signal)` on the PostgREST builder) so the abandoned read stops. Keep the slot until the aborted read settles, so the concurrency cap stays true.

### N-4 — A transient read failure caches a null payload on the PUBLIC factsheet for up to an hour, while `/strategies` probes fresh and shows no note

**Location:** `buildFactsheetPayloadCached` in `src/app/factsheet/[id]/v2/page.tsx` (`async () => fetchAndBuildPayload(id, withPublishedOnly)` under keyParts `[..., id, computedAt]`).

**Scenario.** WR-02's comment names this disagreement as the reason for the key change: the list says "no note" while the public lane serves a cached placeholder. The new key closes it **across** analytics runs only. Within one run, a single admin-read blip, or a failed composite `csv_daily_returns` read that becomes an empty series, makes `fetchAndBuildPayload` return `null`. `unstable_cache` stores that `null` unconditionally, as the same comment says, under a key that does not move until the next job transition. For up to 3600 s every anonymous reader gets the placeholder. The owner's `/strategies` probe is uncached and succeeds a second later, so it renders **no note**, which states that the public link works. The miss is captured once, on the cache-fill request, and the hour of placeholders after it is silent. The resolve stage now knows the difference between an outage (`read_error`) and a data fact, and the cached callback throws that knowledge away.

**Fix.** Inside the cached callback, call `fetchAndBuildPayloadWithReason`, and throw a named `TransientBuildError` when `reason === "read_error"`. A rejected `unstable_cache` callback is not stored; confirm this against the bundled Next's `unstable_cache` docs under `node_modules/next/dist/docs/`, per `AGENTS.md`. The page catches that error and renders the placeholder uncached. The composite read failure cannot be separated from a real empty series until `readCompositeFactsheet` returns its error (D-07). Record that residual under Phase 169 plan 04, next to the N-6 residual.

## LOW

### N-5 — `malformed_series` fires when `daily_returns` is short but valid and `returns_series` is long, and the event's name misleads triage

**Location:** `singleKeyUnbuildable` (`Math.max(storedEntryCount(dailyRaw), storedEntryCount(returnsSeriesRaw) - 1)`) against `resolveDailyReturnSeries`, which returns the `daily_returns` series whenever it is non-empty and never falls back.

**Scenario.** A row with 1 valid `daily_returns` entry and a 500-point `returns_series` resolves to 1 point. `storedReturns` is 499, so the answer is `malformed_series` and an error event reads "stored single-key series is malformed". Nothing is malformed. The builder's column precedence shadowed the long series. The owner copy ("we cannot build … contact support") is honest here. The Sentry event sends the engineer looking for corrupt entries that do not exist.

**Fix.** Tag which column was counted and which one the resolver used, e.g. `source: "daily_returns" | "returns_series"` and `shadowed: true` when `daily_returns` was non-empty but short while `returns_series` held enough. Add an `extra` count per column.

### N-6 — A composite read outage and a genuinely empty composite are the same event

**Location:** `readCompositeFactsheet` (`sparseErr` is only console-logged, and its `code` is not even logged there) → `compositeUnbuildable(caller, "empty_series")`.

**Scenario.** H-1's event exists now, but a `csv_daily_returns` timeout, a `42501`, and a composite that really has no rows all produce `gate: empty_series`, level warning, with no code. Support can see that something refused but cannot tell whether to re-stitch or to page the DB. G0's `error.code || "none"` has the same weakness for a network-level failure: supabase-js gives it an empty code, so every fetch failure groups under `none`.

**Fix.** Route this to Phase 169 plan 04, which already edits `composite-read-path.ts`. Return `{ error: { code } }` from `readCompositeFactsheet` and tag it as `gate: read_error`, `code`. Until then, add `errorCode: sparseErr.code` to the existing `console.error`, which costs one line. For G0, tag a coarse class when the code is empty, e.g. `code: "fetch"` when the message starts with `TypeError`/`fetch failed`.

### N-7 — `unbuildableNoteKindOf`'s `never` arm throws outside the per-row `try`, so one unknown reason takes down the whole list

**Location:** `unbuildableNoteKindOf` `default` arm; its caller in `StrategiesPage` (`const kind = unbuildableNoteKindOf(probe.reason)`), which runs after the probe's `try`/`catch`.

**Scenario.** It is reachable only through a type lie, such as an `as` cast or a widened reason deserialized from elsewhere. If it happens, `Promise.all` rejects and the owner gets the error boundary for the entire `/strategies` page, not one row's "could not check". The `probeThrows` aggregate is also skipped, because it runs after the `await`. The compile-time half is the real value. The runtime half is loud, which is correct, but its blast radius is the page.

**Fix.** Optional. Keep the throw, and move the `unbuildableNoteKindOf` call inside a per-row `try` that routes the error into `probeThrows` and renders `probeUnreadableShareNote(mode)`. That confines the failure to one row and keeps it captured.

## Done well

- The `concurrencyLimiter` slot hand-off is correct. `release` hands the slot to the next waiter without decrementing, so a caller arriving in between cannot overshoot `limit`. A rejecting task releases its slot in the `finally`.
- `resolveAndBuild` has no payload-less success. `buildFromResolved` is declared `Promise<FactsheetPayload>`, `BuildableSeries` can only be produced by the type guard, and there is no `as BuildableSeries` cast anywhere in `src/lib/factsheet`. Each null has a reason, and each reason maps to its note.
- The owner lane now takes its share-note reason from its own build (WR-03). That removes a second resolve, a second composite read, and the SFH M-5 race, where round 1 only proposed detecting it.
- `errorCodeTag` keeps "no error object" apart from "an error with no code". The coherence tripwire counts mismatches and dangling embeds separately and sends nothing identifying.
