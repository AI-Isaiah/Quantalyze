<objective>
Give the eight validate-key 400 arms whose codes the TypeScript roster already knows the flat `{detail, code, recoverable}` body (CONN-05, part 1).

CONTEXT ruling, verbatim: "Every validate-key 400 gets the flat `{detail, code, recoverable}` shape. Codes: `AUTH_FAILED` (bad credentials on any venue, incl. sFOX 401/empty token and MT5 bad password), `MT5_WRONG_SERVER`, `MT5_MASTER_PASSWORD`, plus new `VENUE_DISABLED` (sFOX/MT5 go-dark gates) and `INVALID_REQUEST` (`create_exchange` `ValueError`). Permanent arms are `recoverable:false`. Every `detail` string stays byte-identical (the TS classifier matches on detail text). One test per venue reads `code`."

Purpose: today a ccxt credential failure carries a machine code while an sFOX 401 or an MT5 bad password answers a bare `{detail}`, so a consumer branching on `body.code` behaves differently per venue for one condition (TODOS review M-07). This plan converts the eight arms whose codes (`AUTH_FAILED`, `MT5_WRONG_SERVER`, `MT5_MASTER_PASSWORD`) are already in `EXPECTED_EMITTED_CODES`, so the vocabulary invariant does not move. Plan 05 converts the three arms that introduce new codes, together with their roster entries, in one task.

Output: eight converted raise sites, a new wire-test file, a new committed contract fixture, and a new zero-mock TS parity test.

TODOS this plan closes jointly with plans 05 and 08 (deleted at ship, not here): the "One route, two body shapes for one condition" bullet (review M-07) of "v1.16 Phase-140.1.2 review — findings routed onward".
</objective>
