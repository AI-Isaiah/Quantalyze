How the permanence ruling is implemented, and why (recorded, not silent): adding the two MT5 codes to `_ROUTE_TERMINAL_ERROR_CODES` would change nothing observable, because the 424 pre-gate runs first and sends every code outside `PERMANENT_VALIDATION_ERROR_CODES` to the retryable 424 arm before `_envelope_error` is reached (RESEARCH Pattern 7, permanence note). The plumbing that exists is the explicit `recoverable` parameter plus `ValidationResult.permanent`, which MT5 sets for exactly these two codes. The route honours a stated True only, RESEARCH's minimal "`and val.permanent is not True`" on the pre-gate: the CONTEXT ruling feeds the MT5 permanent codes into the recoverable derivation and moves nothing else, so a stated False leaves every rejection on its HEAD verdict (a credential or scope 403 is never turned into a retryable 424 by an adapter's say-so on this arm). `services/ingestion/long_fetch.py` keeps honouring both directions; the asymmetry is deliberate, and `services/ingestion/adapter.py`'s comment, which warns that a True-only consumer "would make this docstring a lie", is amended in the same task to name this consumer and the decision. The same stated-True pass goes on the one other adapter-fed `_envelope_error` call, `_run_validate_only`'s invalid return, because the ruling names that function's recoverable derivation and the arm already carries an `Mt5SessionAbandoned` catch for MT5 traffic. Live behaviour is unchanged today: MT5 is admitted to onboard and resync only and `_is_long_fetch` routes both to the worker, and the only onboard caller that sends `step: "validate"` (`_unifiedValidateAndEncryptHandler` in `src/app/api/keys/validate-and-encrypt/route.ts`) is dormant with zero callers, while csv-validate sends source csv.
