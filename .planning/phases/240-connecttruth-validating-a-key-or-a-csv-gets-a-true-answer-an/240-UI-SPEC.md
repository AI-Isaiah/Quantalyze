# Phase 240 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This phase places **no new element, token, component or sentence on any rendered
surface.** It is a correctness phase behind three existing surfaces, and this contract fixes what
each of them must look like after the change. Mostly that is "the same as today, for a truer
reason".

1. **CSV upload wizard (CONN-06).** A file whose numeric date column holds a month-name cell
   (`12 Mar 2024`) stops being rejected. The visible change is that the wizard **advances to the
   preview step** instead of showing the `coerce_dtype` row error, and the preview's `Date range`
   row is correct.
2. **Key-connect error envelope (CONN-05).** Every validate-key 400 gains a wire `code`, and every
   `detail` stays byte-identical. The rendered verdict, copy and Retry control are unchanged for
   every arm (§2).
3. **The request-limit envelope (RLIM-01, RLIM-02).** Its copy is unchanged. What changes is who
   gets it: a signed-in CSV user inside the edge limit never sees it because of the upstream
   bucket, and one anonymous IP can no longer cause it for another.

**Sources:** `240-CONTEXT.md` (founder rulings for all four requirements, 2026-11-24), ROADMAP
`### Phase 240`, REQUIREMENTS CONN-05/CONN-06/RLIM-01/RLIM-02, `DESIGN.md` (Error Envelope, Voice,
Numbers Contract, Color gates), and TODOS `[170.1-CSV-ODD-SPELLING-REJECTED]`. Every code anchor
was re-measured at HEAD `431475550` (VERSION `0.133.67.1`) on 2026-11-24. Anchors are cited by
symbol, not by line.

## Global rules (apply to every section)

- **G1. No new rendered sentence.** Every string a user can see after this phase is already in
  `WIZARD_ERROR_COPY`, `CSV_RULE_LABELS` or a route's existing body. The one new string is the
  `date_format_normalized` flag message (§1.3), which lives in the validator envelope and reaches no
  rendered surface (HEAD table, row 1).
- **G2. Detail strings stay byte-identical (CONN-05).** The TS classifier
  (`classifyKeyValidationError` cascade) matches on `detail` text. A `code` is **added** to each
  400 body. Nothing in `detail` is reworded, re-cased or re-punctuated.
- **G3. No Retry control changes.** The wizard derives `recoverable` from `actions`, never from the
  wire. Setting the wire `recoverable: false` on the permanent arms adds and removes no button.
- **G4. No number in any limit copy.** No rendered limit sentence names a count or a window. The
  RLIM tier numbers are therefore CONTEXT's discretion and can move without a copy change. The one
  rendered figure is the existing `Try again in {N}s.` line, which comes from the server's own
  `Retry-After` and is printed only when that header arrived.
- **G5. No new tokens, sizes, weights or colours.** Every host keeps its existing classes (the
  Typography and Color tables below).
- **G6. No new `"rule":` literal in `csv_validator.py`.** Two TS tests classify the producer's
  rule literals by hand: `CsvValidationEnvelope.producer-parity.test.tsx` (`INFO_FLAG_RULES`) and
  `seam-venue-vocabulary.invariant.test.ts` (`CSV_RULE_FAMILY_EXEMPTIONS`). CONN-06 reuses
  `date_format_normalized`.

## 1. CONN-06: a month-name cell in a numeric date column is read

### 1.1 Observable before and after

| | Before (HEAD) | After |
|---|---|---|
| Upload a `daily_returns` / `daily_nav` / `trades` file whose `date` column is `DD/MM/YYYY` (or `MM/DD/YYYY`, or ISO) with one cell written `12 Mar 2024` | `CsvValidationEnvelope` shows a row error under the `coerce_dtype` label `A value is not a valid date or number`, and the wizard stays on the upload step | The wizard **advances to `CsvPreviewStep`** with no error panel |
| `Date range` row on the preview | not reached | `formatDay(date_range[0]) – formatDay(date_range[1])`, computed from the parsed dates. **This includes the case where the month-name cell is the first or the last data row**, so the range is never shortened by one row. |
| Sample-row cells in the preview table (first three and last three rows only) | not reached | If the month-name row is among them, its date cell renders **in the same form as every other date cell in that preview**. Today an accepted, normalized column is returned parsed, and `formatPreviewCell` renders the date column. The month-name cell must not be the one cell left as raw text in a column of normalized dates. |
| `Rows detected` | not reached | Counts the month-name row (no row dropped) |

### 1.2 What stays rejected, unchanged

These keep today's loud row error with today's label. A month name removes day/month ambiguity
only when the rest of the cell is unambiguous too.

- A month-name cell whose year is not four digits (`12 Mar 24`). The century and the day/year
  order would both be guesses. (Assumption A2.)
- A month name that is not English, full or three-letter (`12 Mär 2024`, `12 Mrz 2024`).
- A month-name cell that carries an unreadable zone, or is longer than `MAX_DATE_CELL_CHARS`. The
  existing D-14 and T-170.1-51 rules apply first, unchanged.
- A month-name cell that lands out of order. The existing order check reports it at its row, as it
  does for any other date.

Spellings that must be accepted: `12 Mar 2024`, `12-Mar-2024`, `12 March 2024`, and
`"Mar 12, 2024"` **as a quoted CSV field** (day before or after the month name, abbreviated or full,
case-insensitive). Unquoted, `Mar 12, 2024` splits at its comma, and the file fails earlier, as
today, with `Could not parse CSV: a data row has more fields than the header row.` That parse
error is unchanged and correct. The planner may accept more spellings that are equally unambiguous,
but no fewer.

### 1.3 The flag message (validator envelope only)

The rule literal stays `date_format_normalized` (G6). The message must be **true for the file it
describes**. It is built from two sentences:

| Sentence | Present when | Text |
|---|---|---|
| D (day-first) | today's day-first branch fires, exactly as now | `Detected day-first (DD/MM/YYYY) dates and normalized them to YYYY-MM-DD.` (**byte-identical to today**) |
| M (month name), N = 1 | at least one month-name cell was read in a column that also holds numeric dates, and D is absent | `Read 1 date written with a month name (such as 12 Mar 2024) and normalized it to YYYY-MM-DD.` |
| M, N > 1, D absent | as above | `Read {N} dates written with a month name (such as 12 Mar 2024) and normalized them to YYYY-MM-DD.` |
| M after D, N = 1 | both apply | `Also read 1 date written with a month name (such as 12 Mar 2024).` |
| M after D, N > 1 | both apply | `Also read {N} dates written with a month name (such as 12 Mar 2024).` |

- D and M join with one space, D first. A file with no month-name cell produces **today's flag,
  byte for byte, or no flag where today has none**. A column written entirely with month names
  (no numeric date cell) is out of CONN-06's scope. Its behaviour and flag stay exactly as today,
  whatever that is: this contract did not measure it, and the planner pins it as-is with a test.
- `{N}` is an integer with thousands separators (DESIGN.md Numbers Contract), for example
  `f"{n:,}"`.
- `12 Mar 2024` is a **fixed example, never a cell from the file.** The module rule that no message
  carries a cell holds.
- `detected_format` and any count field are the planner's to shape. The message is the contract.

## 2. CONN-05: the validate-key `code` field changes no rendered verdict

The wire body becomes flat `{detail, code, recoverable}` on every validate-key 400. In the wizard,
the verdict comes from `VENUE_WIRE_CODE_TO_VERDICT` first and the `detail` cascade second. The
required rendered outcome per arm:

| Python arm | Wire `code` | `detail` | Rendered verdict at HEAD | Rendered verdict after | Copy change |
|---|---|---|---|---|---|
| Bad credentials on any venue, sFOX 401 or empty token, MT5 bad password | `AUTH_FAILED` | `AUTH_FAILED_DETAIL` (unchanged) | `KEY_AUTH_FAILED` | `KEY_AUTH_FAILED` (now through the existing table row) | none |
| MT5 wrong server | `MT5_WRONG_SERVER` | `MT5_WRONG_SERVER_DETAIL` (unchanged) | `KEY_MT5_WRONG_SERVER` (cascade "broker server") | `KEY_MT5_WRONG_SERVER` | none |
| MT5 master password | `MT5_MASTER_PASSWORD` | `MT5_MASTER_PASSWORD_DETAIL` (unchanged) | `KEY_MT5_MASTER_PASSWORD` (cascade "master password") | `KEY_MT5_MASTER_PASSWORD` | none |
| sFOX or MT5 go-dark gate (`sfox_enabled_server()` / `mt5_enabled_server()` false) | `VENUE_DISABLED` (new) | `SFOX_DISABLED_DETAIL` / `MT5_DISABLED_DETAIL` (unchanged) | `UNKNOWN` (no cascade branch matches) | `UNKNOWN`, **unchanged** (ruling R1) | none |
| `create_exchange` `ValueError` | `INVALID_REQUEST` (new) | `Unsupported exchange: {name}` (unchanged) | `UNKNOWN` | `UNKNOWN`, **unchanged** (ruling R2) | none |

**Ruling R1: `VENUE_DISABLED` gets an exemption, not a verdict row.** The only existing candidate,
`KEY_VENUE_NOT_ENABLED`, says "Your credentials were not sent anywhere and nothing was stored." That
is false on the Python arm, because the credentials reached our analytics service before its gate
refused them. A verdict row would render a false clause, and that alone decides the ruling. Record
the reason in `VENUE_WIRE_CODES_WITHOUT_VERDICT` (over 80 characters, measured, as that roster
requires).

Reachability, measured at HEAD: three of the four validate-key callers gate the venue in TS first
and answer `KEY_VENUE_NOT_ENABLED` before any call (`validate-and-encrypt`, `create-with-key` and
`composite/add-key` each reference `isSfoxEnabledServer` / `isMt5EnabledServer`). The fourth,
`src/app/api/keys/[id]/rotate-secret/route.ts`, is MT5-only (`keyRow.exchange !== "mt5"` refuses
every other venue) and has **no** `isMt5EnabledServer` gate (`grep -c` returns 0). So if MT5 is ever
switched off, rotating a stored MT5 key reaches the Python arm and renders `UNKNOWN` for a closed
venue. That is true today and stays true after the phase, because this contract changes no verdict.
It is a pre-existing gap outside CONN-05, recorded here for the planner (Assumption A3).

**Ruling R2: `INVALID_REQUEST` gets an exemption, not a verdict row.** Its only emitter is
`create_exchange`'s `Unsupported exchange` `ValueError`, reached only after the TS routes have
already accepted the venue against their own closed set. `KEY_UNSUPPORTED_VENUE` would tell the
user to "Pick one of the exchanges shown on this step", but they did. The cause is a TS/Python venue
set mismatch, which is ours. This matches the existing `UNSUPPORTED_EXCHANGE` exemption's
reasoning.

**Why the rulings are needed at all.** `seam-venue-vocabulary.invariant.test.ts` derives its
population from the real Python emitters (`deriveEmitterSites`) and compares it with a hand-typed
roster and a count pin. Two new emitted codes turn it red until each has a disposition. A verdict
row that renders a false clause would be worse than the honest `UNKNOWN`. If the founder prefers
new wizard codes with true copy for either arm, that is new copy and a new booking (Assumption A3).

## 3. RLIM-01 / RLIM-02: who sees the request-limit envelope

| Surface | Refusal | What renders (unchanged) | Contract change |
|---|---|---|---|
| CSV upload step (`csv-validate`), edge limiter | `CSV_RATE_LIMIT` 429 + `Retry-After` | `CsvUploadStep` leaves `CSV_RATE_LIMIT` out of `KNOWN_CSV_VALIDATE_CODES`, so it maps to `RATE_LIMITED`. That renders `ErrorEnvelope` with `You have reached our request limit.`, its cause and fix, and `Try again in {N}s.` | none |
| CSV upload step, upstream `/process-key` | Python `RATE_LIMITED` 429 + `Retry-After` | the same `RATE_LIMITED` envelope | **Must not occur** for a signed-in user inside the edge limit (RLIM-02). The copy stays as the answer for any remaining upstream refusal. |
| CSV submit step (`csv-finalize`), its own limiter after the split | `CSV_RATE_LIMIT` 429 | `CsvSubmitStep` also leaves `CSV_RATE_LIMIT` out of its roster, so the same `RATE_LIMITED` envelope renders | Only the limiter instance changes |
| Anonymous teaser (`verify-strategy`) | edge `publicIpLimiter` (body `{error: "Too many requests"}`), or Python `RATE_LIMITED` 429 from the per-IP or aggregate anonymous bucket | **No page renders the teaser** (`[192-ORPHANED-LANDING-VERIFY]`). Direct callers get the bodies as today. | One IP's traffic no longer refuses another IP. `publicIpLimiter` is not retuned (CONTEXT Specifics). |
| Simulator | Python `RATE_LIMITED` 429 | as today | none (HEAD table, row 2) |

**Wire body rules.**
- The Python 429 body keeps its shape (`ok`, `code: "RATE_LIMITED"`, `human_message`, `detail`,
  `correlation_id`, `recoverable: true`, `retry_after_seconds`) and the `Retry-After` header.
- **No 429 body, header or log line carries the raw client IP, the IP hash or the bucket key.**
  `detail` stays `Rate limit exceeded: {limit string}`.
- Both CSV routes' throttled bodies say `Too many requests. Wait a minute and try again.` That is
  true only while each limiter's window is 60 s. The split csv-finalize limiter **keeps a `"60 s"`
  window**, and if a window ever changes, the sentence changes in the same commit. Neither wizard
  step renders this sentence today. It is wire copy for direct callers.
- The aggregate anonymous ceiling refuses through the same `RATE_LIMITED` body. The copy ("We cap
  how often this action can run and this attempt went over the cap") is true for an aggregate cap
  too, so no second variant is minted.

## Assumptions (no human was available; each is a default, not a user answer)

- **A1. No info-flag rendering in this phase.** CONTEXT rules the flag "through the existing
  date-normalization info flag" and does not ask for a visible chip. The flag has never reached the
  browser (HEAD table, row 1). Plumbing `info_flags` through `csv_adapter`, `process_key` and the
  route into a wizard chip would be a new seam field and new visual design. That is outside this
  proportionate phase, and if wanted it is a separate booking. The `validate_csv` comment "so the
  wizard can surface a chip" describes intent that was never built.
- **A2. Two-digit years stay rejected.** CONTEXT's ruling rests on "a month name carries no
  day/month ambiguity". `12 Mar 24` still has day/year ambiguity and a century guess, so accepting
  it would break the premise the ruling gives.
- **A3. No new wizard code for `VENUE_DISABLED` / `INVALID_REQUEST`.** R1 and R2 keep `UNKNOWN`
  because no existing entry is wholly true on those arms, and the brief excludes new copy. If the
  founder wants dedicated codes, that is new copy for a later phase. The ungated
  `rotate-secret` route (§2, R1 reachability) is a pre-existing gap. Adding an
  `isMt5EnabledServer` gate there is a one-route change outside CONN-05's requirement text. The
  planner may take it or book it, but must not silently skip the decision.
- **A4. The simulator re-key is already shipped** (HEAD table, row 2). The planner verifies it, and
  this contract asks for nothing there.
