## Task 2: each note lines up with its strategy name (D-06)

The wide describe reads the draft's note at scrollLeft 0 and at max (`readMystrNote`): block inside the region (left = region left within 1 px, right <= region right + 1); at V1080 the first element's left = region left + 16 within 1 px; at V1100/V1280 the first element's left = the Strategy name link's first text node left (a Range) within 1 px. The note's first text node (a Range) is additionally asserted to sit exactly the first element's own computed `padding-left` inside it.

Harness readings: V1080 first element 325 = region 309 + 16; V1100 and V1280 first element 381 = name text 381 at scroll 0 and 380.7/380.8 at max (fractional scrollLeft, inside 1 px); first text node 389 (8 px = the amber block's `px-2`).

**Decision flagged (UI-SPEC wording vs. the D-08 markup).** The plan and UI-SPEC say the note's "first text line" starts at the name text's left edge. The review-feedback block is `rounded px-2 py-1 … bg-warning/5`, so its first GLYPH is 8 px right of the block's box, always (measured: 389 vs 381). Taken literally on the glyph, the relation can never hold for a draft's note. I asserted the block's box at the name's left (the amber fill lines up with the name; plan 07 made the same reading for the phone case and logged the glyph) and asserted the glyph is exactly the block's own padding further in, so it cannot drift by anything else. If the intent is the GLYPH aligned with the name text, the fix is outside this plan's files (a `-ml-2` on that `<p>` in the page's note builder shifts both phone and wide relations by 8 px) and is the founder's call; no CSS was changed here.

**CSS fix:** none needed. The note block's `@3xl:pl-[calc(var(--pin-strategy-left)+1rem)]` aligns correctly in the harness at both pinned widths (RESEARCH A1, `w-[100cqw]`, held at V1280 in plan 07's harness and again here).

**Neuter (harness, byte backup/restore, `cmp` clean):**

| Neuter | Result |
|---|---|
| indent replaced by `@3xl:pl-4` | alignment RED at V1100 and V1280 (the first element lands 56 px left of the name text, `V1100@0 first vs name` fails; the scratch assertion mirrors the spec's) |
| indent replaced by the fixed `@3xl:pl-18` | **GREEN**, as the plan predicted when the rank width is 56 px: `calc(var(--pin-strategy-left)+1rem)` = 56 + 16 = 72 = `pl-18` here (no star column, `--pin-strategy-left` falls back to the rank width). The e2e alignment case does NOT guard the variable form on this page; plan 02's unit test (`expected [ '@3xl:pl-18' ] to deeply equal [ Array(1) ]`) is the guard, as the plan allowed. |
