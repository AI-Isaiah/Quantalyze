## Warnings

### WR-01: The default Created sort leaves gaps in the `#n` rank column, the defect STALE-01 exists to prevent (MEDIUM, confidence 9)

**File:** `src/components/strategy/StrategyTable.tsx:817-821` (partition skipped under `created_at`), `:1169` (`rank = page * PAGE_SIZE + i + 1`), `:1298` (`hasComputedAnalytics ? \`#${rank}\` : "—"`)

**Issue:** The STALE-01 comment in this file states the invariant directly. Ranked rows "may only be numbered while they occupy an unbroken prefix of the list. Interleave one unranked row and either it steals an ordinal or, if skipped, leaves a hole in the sequence."

D-09 removes the partition under `created_at`, so unranked rows now interleave. The rank is still the paged index, and an unranked row prints `—`. So the sequence has a gap wherever an unranked row sits.

**Failure scenario:** This is the page's default view (`initialSort={{ key: "created_at", dir: "desc" }}`). A manager creates a strategy, and it has no analytics yet. That is the case D-09 was built for.
- The top row reads `—`. The next row reads `#2` and the one after `#3`. No row says `#1`.
- A draft in the middle of the list gives `#1, —, #3`.

The manager-rows test fixture already renders exactly this: Newest `—`, Middle `#2`, Oldest `#3`. No test asserts the ordinals of the ranked rows, so it goes unnoticed.

A second point: under a date sort, `#1` reads as a performance rank ("3rd best here", per the rank-cell comment) when it really means "newest computed strategy". That conflicts with the reason the rank cell is suppressed for unranked rows.

**Fix:** Number only the ranked rows, counted over the full sorted list so the numbering continues across pages. For example, inside the `filtered` memo, after the sort:

```ts
// ordinal among RANKED rows in the active order, contiguous across pages
const ordinals = new Map<string, number>();
let n = 0;
for (const s of result) if (isRankedRow(s)) ordinals.set(s.id, ++n);
return { rows: result, ordinals };
```

The cell then renders `hasComputedAnalytics ? \`#${ordinals.get(s.id)}\` : "—"`. This leaves the default mounts unchanged, because under every metric key the ranked rows already form the prefix and the ordinals equal `page * PAGE_SIZE + i + 1`. The default-mounts fixture confirms that.

The alternative is a founder decision: render `—` in the rank column for every row whenever the active key is not a performance metric (`created_at`, and arguably `name`). Add a manager-rows assertion that the ranked rows read `#1, #2` under the Created sort.

### WR-02: On `/strategies` the filter bar's "Sort by" control shows Sharpe while the table is sorted by Created, and it cannot switch the table to Sharpe (MEDIUM, confidence 8)

**File:** `src/components/strategy/StrategyTable.tsx:507-508` (`sortKey`/`sortDir` seeded `sharpe`/`desc`), `:546-551` (`initialSort` seeds only `tableSortKey`/`tableSortDir`), `:926-929` (`sortKey={sortKey}` / `sortDir={sortDir}` passed to `StrategyFilters`); `src/components/strategy/StrategyFilters.tsx:350-371` (the select, rendered on every mount)

**Issue:** UI-SPEC keeps the filter bar on `/strategies`. `initialSort` seeds the table sort only. The visible `<select aria-label="Sort by">` is controlled by `sortKey === "sharpe"` and its direction select by `desc`, so on first load the page shows "Sort by: Sharpe, Descending" while the rows are newest first. The prop doc describes this as "this mount starts that way". Two concrete faults follow:

1. **Choosing Sharpe does nothing.** The select's value is already `sharpe`, so picking Sharpe fires no `change` event. `handleSortKeyChange` never runs, and the table stays on Created. The only way to get a Sharpe sort from the menu is to pick another key first and then come back.
2. **The direction control flips the wrong key.** `handleSortDirChange` sets `tableSortDir` while `tableSortKey` stays `created_at`. Picking "Ascending" therefore puts the oldest strategy first, under a label that still reads "Sharpe Ascending".

A screen-reader user hears "Sort by Sharpe" for a list that is not sorted by Sharpe.

**Fix:** Bring the two controls into line for this mount. In order of preference:
- (a) Seed `sortKey`/`sortDir` from `initialSort` when its key is a `SortKey`. For `created_at`, give `StrategyFilters` a "Created" option. The cleanest version is an optional extra-options prop that only the manager mount passes, so Discovery's select is byte-identical.
- (b) Hide the Sort controls when `initialSort` is set. A `showSort` prop on `StrategyFilters`, like `showViewToggle`, would do it. The column headers already sort and the Created header is a button.

Add a page-level test asserting that the select's value matches the active table sort on first render.

### WR-03: The owner-scope pin can't catch removal of `.eq("user_id", user.id)` from the list read (MEDIUM, confidence 9)

**File:** `src/app/(dashboard)/strategies/page.table.test.tsx:607`, `:213` (`eq: () => builder`); `src/__tests__/phase-149-my-strategies-parity.test.ts` pin 10 (`expect(stripComments(readSource(consumers[1]))).toContain('.eq("user_id", user.id)')`); `src/app/(dashboard)/strategies/page.tsx:393` and `:431`

**Issue:** The brief names the owner-scoped query as the safety condition for the second `owner-all-statuses` consumer: pin 10's own comment says "the prop does not narrow anything", and the threat is T-170.7-05. Both pins check it with a substring match on the whole page source. But `page.tsx` holds that exact substring twice:
- `:393` is the list read.
- `:431` is the wizard-draft lookup.

The runtime mock records `select` columns only. Its `eq` is `() => builder`, so no filter is ever recorded.

**Failure scenario:** A later edit drops `.eq("user_id", user.id)` from the list read at `:393`, for example while refactoring the select. Both the source pin and parity pin 10 stay green, because `:431` still carries the string. The runtime test stays green too, because it never sees the filter.

In production the list then returns whatever RLS lets an authenticated user read, which includes every other manager's published strategies. Each one would get a row with an Edit link, a Share control and `StrategyActions`, and `owner-all-statuses` would stop filtering anything.

**Fix:** Make the runtime mock record filters per select and assert them on the list read:

```ts
const builder = {
  select: (cols: string) => { current = { table, cols, eqs: [] }; state.selects.push(current); return builder; },
  eq: (col: string, val: unknown) => { current.eqs.push([col, val]); return builder; },
  ...
};
// in the test:
expect(list!.eqs).toContainEqual(["user_id", MOCK_USER_ID]);
```

Alternatively, tighten the source pin to the chained expression on the list read. For example, a regex requiring `.select(\`*, strategy_analytics (${CATEGORY_RANKING_ANALYTICS_COLUMNS})\`)` followed directly by `.eq("user_id", user.id)`. Then point parity pin 10 at the same anchored form. Either way, confirm the pin goes RED with `:393` removed and `:431` left in place.

### WR-04: Nothing pins the cross-page half of D-11, so counting the ordinals per page passes every test (MEDIUM, confidence 7)

**File:** `src/components/strategy/StrategyTable.tsx:855-863` (`rankOrdinals` loops over `filtered`); `src/components/strategy/StrategyTable.manager-rows.test.tsx:847-876` (D-11 describe, 3 rows)

**Issue:** D-11 and the memo's own comment both say the numbering continues across pages ("page 2's first ranked row follows page 1's last").
- Before this round, the page offset was written into the expression: `page * PAGE_SIZE + i + 1`.
- Now it holds only because the loop iterates `filtered` and not `paged`.
- Every D-11 test and every default-mount fixture uses fewer than `PAGE_SIZE` (20) rows.

Changing `for (const s of filtered)` to `for (const s of paged)` leaves all 938 tests green. That one-word change is the natural "only number what is visible" refactor.

**Scenario:** A later edit scopes the memo to `paged`. Page 2 of /discovery, /browse and /strategies would then restart at `#1` instead of `#21`, and nothing would fail.

**Fix:** Add two tests:
- A Discovery-shaped test (no `managerRows`): 21 or more ranked rows, click `Next`, and assert the first row reads `#21`.
- A manager Created test with one unranked row on page 1: click `Next`, and assert page 2's first ranked row reads `#20`, continuing from page 1's last ranked ordinal.
