### MEDIUM-2: a `conventions` echo that is present but not an object is still treated as "no row" without any log

**Commit:** `883fdd720`
**Status:** fixed: requires human verification. This is a state-handling change: one more input class now counts as a failure.

**Files modified:**
- `src/lib/factsheet/composite-read-path.ts`
- `src/lib/factsheet/composite-read-path.conventions.test.ts`
- `src/lib/factsheet/fetch-and-build-payload.single-key-conventions.test.ts`

**Applied fix.** `readCashConventions` now handles a successful read in three ways:

| `conventions` value | Answer | Signal |
|---|---|---|
| `undefined` or `null` (no row, no key, or a null echo) | `{ conventions: null, failed: false }`. This is an older run, a fact. | none, as before |
| a plain object | `{ conventions, failed: false }` | none, as before |
| a string, a number, a boolean or an array | `{ conventions: null, failed: true, code: "malformed", message: "conventions is a string" }` (or `a number`, `an array`, ...) | `console.error` naming the strategy, then the existing HIGH-1 path |

The `failed: true` answer rides the path fixer A built, without changes. The resolve stage captures it once, for a build only, with `reason: "conventions_read_error"` and `code: "malformed"`. It sets `conventionsDegraded`, and the cached callback in `v2/page.tsx` refuses to store the build.

**`fetch-and-build-payload.ts` is unchanged.** Its capture already forwards `code` as a tag, so `"malformed"` needs no new tag value there. I kept the review's first option (ride the existing path) over the second (a separate `reason: "conventions_malformed"` capture), as the brief asked. A Sentry query can split the two cases on `code: malformed`.
