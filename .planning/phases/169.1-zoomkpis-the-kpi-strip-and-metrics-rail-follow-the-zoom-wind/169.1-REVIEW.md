### MD-01: Every brush pointer-move re-runs the whole series bundle synchronously, measured at 37 / 146 / 298 ms per window

**Files:**
- `src/app/factsheet/[id]/v2/basis-context.tsx:633-648` (`useWindowedView`)
- `src/app/factsheet/[id]/v2/basis-context.tsx:590-613` (`windowView` calls `deriveSeriesBundle`)
- `src/app/factsheet/[id]/v2/MasterBrush.tsx:156-195` (`onPointerMove` → `setXRange` on every move)

**Issue:** `MasterBrush.onPointerMove` calls `setXRange` on every pointer move during a pan or handle drag. Each new range gives `useWindowedView` a new cache key (`basis:leverage:startIdx:endIdx`), so `windowView` re-runs the FULL `deriveSeriesBundle` on the slice.

That bundle computes far more than the D-27 follow-list reads:
- 2000 block-bootstrap resamples;
- three rolling arrays, plus a rolling beta per comparator;
- correlations and the correlation matrix;
- style drift, stress windows, the monthly and daily heatmaps, and Calmar by Year.

`windowView` then discards everything except nine fields.

I measured it with a throwaway vitest bench (Node, dev laptop, `benchmarkPrices: { unavailable: true }`, so no BTC alignment cost), averaged over 5 runs:

| record length | ms per derive |
|---|---|
| 365 obs | 37.0 |
| 1500 obs | 145.9 |
| 3000 obs | 298.1 |

Real cost is higher: a live payload adds the BTC and SPX alignment and comparator blocks, and a phone CPU is several times slower.

`useDeferredValue` only lowers the render's priority. The `useMemo` body is one synchronous call, and React cannot yield inside it. Once the deferred pass starts, the main thread blocks for the whole derive, and the next pointer moves queue behind it. A drag on a 4-year record therefore runs at roughly 5-7 frames per second on desktop and worse on mobile. That is the per-frame interaction D-27 builds on.

The single-entry cache (T-169-45) dedupes across consumers within one window, but not across the stream of windows a drag produces.

**Fix:** Pick one or combine them.
- (a) Derive only what the follow-list reads. Add a window-scoped builder in `build-payload.ts` that shares `deriveSeriesBundle`'s argument object and calls `compute()`, `worstDrawdowns`, `quantileSummary`, `bootstrapCI` and the comparator blocks' summary and joint. Skip the rolling arrays, correlations, style drift, stress windows and heatmaps, which the window never reads (D-25 still holds: same shared functions, same arguments).
- (b) Keep the bootstrap off the drag path. Commit the window's bootstrap on pointer-up, or derive it in a second deferred pass, so the strip and the rail track the drag and the CI settles after.
- (c) Commit the range to the strip and the rail on pointer-up only. The charts keep following the live `xRange`.

Pin the result with a timing-free test that counts `bootstrapCI` calls across a simulated multi-move drag.

### MD-02: On an active-day-basis composite with interior gaps, rolling volatility and rolling Sortino run over the present days, not the engine's zero-filled series

**Files:**
- `src/lib/factsheet/build-payload.ts:450-456`
- `analytics-service/services/metrics.py:2648-2659`

**Issue:** D-39 says that under `"active"` the rolling vol and Sortino "stay on all returns (`stratRet`), as the engine's do". That premise is true for a single-key strategy and false for a composite.

The engine computes `rolling_volatility_*` from `returns` (`metrics.py:2657-2659`, and the Sortino components alongside at `:2648-2654`). For a composite, `returns` is `gap_fill_daily_returns(stitched)`: zero-filled on every calendar day, under every day basis. The `day_basis` switch only moves `stat_returns` and `_rolling_basis` (`:2033`).

The code does this:

```ts
strategyRollingVol: activeBasis
  ? rollingVol(stratRet, rollWindow.window, periodsPerYear)          // present days
  : onBasis(rollingVol(basis.returns, ...)),
```

On a composite whose config is `metrics_basis: "active_day"`, the active branch therefore rolls over the present days, not the zero-filled series. `metricsBasisSeries`'s active branch ignores density by design. On any composite with interior gaps, both rolling charts and the Rolling Metrics table (Now / Min / Max / Avg) then disagree with the engine at full history. That is the D-39 defect class, left open on one arm.

The tests pin the active case only on a GAPLESS non-composite fixture (`build-payload.rolling-basis.test.ts:159-162`), so they cannot see this.

**Fix:** Feed vol and Sortino the density-only series under every day basis. The day basis then moves only the rolling Sharpe, as in the engine:

```ts
const dense = metricsBasisSeries(stratRet, dates, { calendarDense }); // ignores dayBasis
const onDense = (rolled: Array<number | null>) => dense.positions.map((p) => (p === null ? null : rolled[p]));
strategyRollingVol: onDense(rollingVol(dense.returns, rollWindow.window, periodsPerYear)),
strategyRollingSortino: onDense(rollingSortino(dense.returns, rollWindow.window, periodsPerYear)),
```

`dense` is `stratRet` itself with identity positions when `calendarDense` is false, so non-composites stay byte-identical. Add a red-first case: an active-basis gapped composite, where the rolling vol and Sortino at the last date equal the functions over the hand-built zero-fill twin and differ from their present-days values.

### MD-03: An active-basis window with fewer than two non-zero days shows a fabricated "0.0%" annualized volatility, beside a "—" Sharpe and Sortino

**Files:**
- `src/lib/factsheet/compute.ts:63-83` (`basisReturns` / `dispersion` / `annVol`)
- `src/lib/portfolio-math-utils.ts:64-81` (`mean([])` = 0, `stdDev` = 0 for n < 2)

**Issue:** Under `dayBasis: "active"`, `basisReturns` holds only the non-zero days. When a window holds 0 or 1 of them, `dispersion(basisReturns, 0)` returns `sd = 0`, because `stdDev` returns 0 for an empty or one-element population. So `annVol = 0 * √P = 0`, which the KPI strip and the rail render as "0.0%". Sharpe beside it is null ("—", via `sharpe()`'s `xs.length < 2` guard) and Sortino is NaN ("—").

The engine gives `None` for the same input. `stat_returns.std()` of an empty or one-row pandas Series is NaN, so `qs.stats.volatility` comes back NaN, which `_safe_float` turns into None (`metrics.py:1911-1915`).

It is reachable: the zoom clamp allows a 5-observation window, and active-day-basis strategies are exactly the sparse traders with runs of zero-return days. Zooming onto an idle stretch shows a measured-looking 0.0% volatility where no volatility exists. That breaks the DESIGN.md Numbers Contract and founder decision D7 (absence renders "—", never 0), and the strip contradicts itself (vol 0.0%, Sharpe "—").

The same `basisSd` feeds the per-basis MTM and smoothed bundles, so a full-history MTM bundle of an active single-key strategy with fewer than two non-zero MTM days hits it too.

**Fix:** Withhold the basis statistics when the basis series cannot carry a deviation. That is the engine's rule, and it changes nothing on the calendar basis, where `basisN = n >= 2` on every rendered path:

```ts
const annVol = basisN >= 2 ? basisSd * Math.sqrt(periodsPerYear) : NaN;
```

Add a window case: an active-basis payload, a 5-day slice of all-zero returns. Assert that Ann. Vol renders "—" on the strip and the rail, and assert the one-active-day variant.
