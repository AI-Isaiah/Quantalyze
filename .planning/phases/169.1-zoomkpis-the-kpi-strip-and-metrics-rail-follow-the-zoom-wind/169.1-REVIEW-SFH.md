# Phase 169.1 ZOOMKPIS: silent-failure review, round 1

Only CRITICAL, HIGH and MEDIUM findings are listed. Each was checked against the source at
`ac9b514e8`. Where a finding says "measured", the number came from running the shipped `compute()`
with `npx tsx`.

## Paths checked that are sound

- **`metricsBasisSeries` throw (calendar-dense, dates not strictly increasing).** It is reachable
  only through `compute()` / `deriveSeriesBundle` with `calendarDense = dataQuality.composite`.
  `readCsvDailyReturns` orders by date and throws `CompositeSeriesReadError("page_order")` on a
  non-increasing date, so the server build never hands it a bad axis. The client window re-derive
  slices that same server axis, so it cannot either. If it ever did throw, the throw propagates
  (`resolveAndBuild` has no catch, and `onRequestError` captures it), so nothing would be swallowed.
  `chart-configs.ts`'s `bridgeAt` call passes no `calendarDense`, so it cannot throw.
- **Discovery detail page on `fetchAndBuildPayloadWithReason`.** `read_error` gets its own sentence,
  and the resolve stage captures it once. A build throw is not caught anywhere, so it stays loud. The
  dropped discovery-only projection is not read by anything left.
- **Window withholds.** Below 2 points, and with no `periodsPerYear`, every follow-list field is
  replaced by NaN or emptied. Nothing keeps a full-history figure under a "Selected range" eyebrow,
  and the no-annualization case has its own reason line.
- **Cache key.** It moved v10 to v11, and it is the only payload `unstable_cache`. Stale entries
  without `cumulativeMethod` / `dayBasis` cannot be served.
- **`maybeSingle()` on the conventions read.** `strategy_analytics_series` has
  `PRIMARY KEY (strategy_id, kind)`, so a multi-row PGRST116 cannot happen.

## HIGH-1: a failed conventions read builds on the config tier, the public cache stores that build, and Sentry never hears of it

**Location:** `src/lib/factsheet/composite-read-path.ts`, `readCashConventions` (both the `if (error)`
arm and the `catch`). Callers: `src/lib/factsheet/fetch-and-build-payload.ts`, `resolveFactsheetInputs`
(the single-key arm, `const cashConventions = caller === "build" ? await readCashConventions(...)`),
and `readCompositeFactsheet`'s `Promise.all`. The cache is `src/app/factsheet/[id]/v2/page.tsx`
(`["factsheet-v2-payload-v11", id, computedAt]`, `revalidate: 3600`).

**What happens.** On a PostgREST error or a thrown chain, `readCashConventions` logs `console.error`
and returns `null`. `resolveMetricsConventions` then resolves the method and day basis from the live
`returns_denominator_config`. The build goes on and returns a normal payload. Three things go wrong:

1. **The figures are confident and can be wrong.** D-30 / D-83 read the frozen echo first because
   the live config "can be edited after publish without a recompute". On an outage, the fallback is
   exactly the tier the echo exists to override. When the config was edited after the run, the curve
   is drawn on the wrong method, along with the monthly grid, Calmar-by-year, stress windows, the
   bootstrap Max DD, the day basis of the rolling Sharpe and every window KPI. The strip still shows
   the persisted headline, so the headline and the curve disagree. That is the drift HARD-03 and
   D-83 close. `returnsConventionOverride` flips as well, so `leverageEligibleFor` can offer the
   leverage what-if (a geometric re-derive) on a strategy whose stored headline is `simple` or
   active-day.
2. **The public cache stores it.** Every sibling series read (csv, MTM, smoothed, the stored cash
   series) throws `CompositeSeriesReadError`, which becomes `read_error`. The cached callback throws
   on that, so an outage is never stored. This read is the one exception. A single blip is served
   to every anonymous viewer for up to the 1 h revalidate window, and it keeps being served while
   revalidation hits the same outage.
3. **No Sentry signal.** `src/instrumentation.ts` calls `Sentry.init` with no console integration
   (`resilient-fetch.test.ts` documents this), so `console.error` reaches only Vercel logs.
   `seriesReadError` calls `captureToSentry` for its sibling reads. This one does not, so an
   outage that changed published figures leaves no event.

The degrade itself was decided ("a blip must not blank a factsheet", CONTEXT D-30 and its
2026-09-30 note). Neither the caching nor the missing capture was. The fix below keeps the
decided degrade.

**Hidden errors:** a PostgREST timeout (`57014`), connection reset or `socket hang up`, an RLS or
permission regression on `strategy_analytics_series`, a renamed JSON path (`payload->conventions`),
and an admin client that answers `from()` with `undefined` (`composite-read-path.conventions.test.ts`
"does not answer the conventions query at all" pins that this one builds silently).

**User impact:** for up to an hour, every public viewer sees a curve, buckets and window figures on a
method or day basis different from the one the headline beside them used, and nobody is alerted. It
needs both an outage and a config edited after the run, which is a narrow combination. But when it
happens it cannot be seen at all, and the cache makes it last.

**Recommendation:** keep the build, but mark the result as degraded, capture it, and keep it out of
the public cache:

```ts
// readCashConventions: return a discriminated result instead of null
return { conventions: null, failed: true as const, code: error.code ?? null };
// resolveFactsheetInputs (build only): on failed
captureToSentry(new Error(`factsheet resolve: cash_settlement conventions read failed (${code})`), {
  tags: { stage: "factsheet-resolve", caller, reason: "conventions_read_error", strategy_id: id },
});
// and carry a `conventionsDegraded: true` on the build result so the cached
// callback in v2/page.tsx throws (or skips storing) exactly as it does for read_error,
// while the uncached discovery lane still renders the degraded build.
```

Change the two `console.error`-only tests in `composite-read-path.conventions.test.ts` and
`fetch-and-build-payload.single-key-conventions.test.ts` so they assert the capture, and add a test
that the cached wrapper does not store a degraded build.

## MEDIUM-1: an active-day-basis window with 0 or 1 active day shows Ann. Vol "0.0%" as a measured figure

**Location:** `src/lib/factsheet/compute.ts`, `compute()`, at
`const annVol = basisSd * Math.sqrt(periodsPerYear)` over `metricsBasisSeries(...).returns`. It
surfaces through `windowView` (`basis-context.tsx`) on the KPI strip (`FactsheetView.tsx`
`{ label: "Ann. Vol", value: pct(m.ann_vol, 1) }`) and the rail.

**What happens.** Under `dayBasis: "active"` the basis series drops every zero-return day.
`dispersion()` takes `mean` and `stdDev` from `portfolio-math-utils`, which return **0** for an
empty array, and population `stdDev` returns 0 for one element. So a window that covers a flat
stretch reports zero volatility. Measured at `ac9b514e8`:

```
compute([0,0,0,0,0], dates, 0, 365, { dayBasis: "active" })     → ann_vol 0, sharpe NaN, sortino NaN
compute([0,0.01,0,0,0], dates, 0, 365, { dayBasis: "active" })  → ann_vol 0, sharpe NaN
```

The engine gives no number here. On `day_basis="active"`, `stat_returns` is the nonzero days, and
pandas `std()` (ddof=1) of zero or one points is NaN. That makes `qs.stats.volatility` NaN, which
is stored as `None` and shown as "—". The TypeScript window shows "0.0%" beside a "—" Sharpe and
Sortino. "0.0%" says the range was measured and was riskless, when it was not measured.

`windowView` withholds only when the CALENDAR slice has fewer than 2 points. On the basis series
the count can still be 0 or 1. Active-day basis exists for sparse traders, so a range over an idle
stretch is the ordinary case for these strategies, not a corner case. The "Only N observations"
caveat counts calendar days (`wv.strategyMetrics.n`), so it says nothing about this either.

**Hidden errors:** an empty basis series, read as a measured zero.

**Recommendation:** in `compute()`, make `annVol` NaN when `basisN < 2` (or when `basisSd` is NaN,
to mirror the engine's ddof=1 NaN). Optionally have `windowView` withhold when the basis count is
below 2. Add a `compute.conventions.test.ts` case for an all-zero and a single-active-day active-basis
series that asserts `ann_vol` is not finite.

## MEDIUM-2: on a chain-broken row, a selected range compounds across the TWR break and the coverage caveat is hidden

**Location:** `src/app/factsheet/[id]/v2/FactsheetView.tsx`
(`const coverageCaveat = leverageApplied || selected ? null : ...`) and `MetricsColumn.tsx`
(`const coverageCaveat = selected ? null : storedCaveat;`). The window derive is
`basis-context.tsx`, `windowView`.

**What happens.** For a `twrChainBroken` row, Python compounds the stored headline only over the
record after its last interior break (`nav_twr._last_interior_break_suffix`). The page states this
in the caveat. While a range is selected, the caveat is removed, and `windowView` re-derives Cum.
Return, CAGR, Max DD and Calmar by compounding the slice straight across the break, with no note.
CONTEXT justifies the removal with "It follows the same rule the leverage arm already uses". That
premise does not hold: `leverageEligibleFor` returns false for `twrChainBroken === true`, so the
leverage arm never computes anything on a chain-broken row. The window arm does compute on these
rows, so it is the only client re-derive that compounds through a break the engine deliberately
leaves out.

**Hidden errors:** a break-spanning compounded return, shown under "Selected range" as a clean figure.

**User impact:** if a viewer drags the range across the break, they get a Cum. Return and CAGR that
the engine's own rule refuses to compute, with nothing on the page saying the range spans a break.
A range entirely after `headlineCoversFrom` is fine.

**Recommendation:** when `dataQuality.twrChainBroken === true` and the scope's `start` is before
`headlineCoversFrom` (or `headlineCoversFrom` is `null`), keep a caveat that names the break, such
as "This range spans a break in the return chain; its compounded figures cross it", or withhold the
compounded fields for such a window. Pin both cases (a range before the break and a range after it)
in `FactsheetView.window-kpis.test.tsx`. Correct the CONTEXT line that cites the leverage arm as
precedent.
