### HIGH-1: a failed conventions read builds on the config tier, the public cache stores that build, and Sentry never hears of it

**Commit:** `e347ec94e`
**Status:** fixed: requires human verification. This is a state-handling change: the fallback path is now marked and kept out of the cache.

**Files modified:**
- `src/lib/factsheet/composite-read-path.ts`
- `src/lib/factsheet/fetch-and-build-payload.ts`
- `src/app/factsheet/[id]/v2/page.tsx`
- `src/lib/factsheet/composite-read-path.conventions.test.ts`
- `src/lib/factsheet/fetch-and-build-payload.single-key-conventions.test.ts`
- `src/app/factsheet/[id]/v2/page.composite-read-error.test.tsx`
- `src/app/(dashboard)/discovery/[slug]/[strategyId]/page.pending-fallback.test.tsx`. This file is outside the brief's file list. See "Decisions" below.

**Applied fix.** The degrade decided in D-30 ("a blip must not blank a factsheet") is unchanged. What changed:

1. **`readCashConventions` reports a failure.** It returns a discriminated `CashConventionsRead`. A failure carries its PostgREST code and message. A thrown chain carries the code `"threw"`, and this includes an admin client whose `from()` returns `undefined`, the case the review named. It still never throws, and it still logs `console.error`. `readCompositeFactsheet` passes the failure up as `conventionsReadFailure`, next to `buildOpts` and not inside it. That keeps it out of the payload and out of `BuildFactsheetOpts`, which topic B owns.
2. **The resolve stage captures it once, and only for a build.** The capture uses the same tag set as `seriesReadError`: `stage: "factsheet-resolve"`, `caller`, `reason: "conventions_read_error"`, `code`, `strategy_id`, `read: "cash_settlement"`, plus `extra.errorMessage`. It fires at the stage's **success exit**, not at the read. If a build fails later in the stage on a sibling series read, it sends only its own `read_error` event, for a payload that never ships. The existing `MTM-READ-ERROR-NOT-CACHED` test fails both reads and asserts exactly one capture, and it still passes. A probe never captures (167.2.1-REVIEW-R2 WR-01), and the composite probe still reads the echo (D-83 (a) scope).
3. **The degraded build is kept out of the public cache.** `FactsheetBuildResult`'s success arm gains an optional `conventionsDegraded: true`. It is set only when the read failed, so a clean result is byte-for-byte the same as before. The cached callback in `v2/page.tsx` throws a module-private `FactsheetDegradedBuildError` that **carries the payload**, and the page renders that payload uncached. So D-30 still holds: the public viewer sees the factsheet, not the placeholder. I checked this against the bundled Next `unstable_cache` (`node_modules/next/dist/server/web/spec-extension/unstable-cache.js`):
   - On a cache miss, the callback is awaited before `cacheNewResult`, so the throw propagates as the same instance and nothing is stored.
   - On a stale entry, the background revalidation's `.catch` returns the cached value, so the last good entry survives.
   - No cache-key bump is needed, because the stored shape did not change.
   - The owner lane, the share page and the discovery lane were already uncached. They render the degraded build, and the resolve stage captures it.

## Decisions

- **I edited a test outside the brief's file list:** `src/app/(dashboard)/discovery/[slug]/[strategyId]/page.pending-fallback.test.tsx`, in one test, *"a `simple` returns_denominator_config draws the arithmetic curve and withholds the leverage what-if"*.
  - **Why it broke:** that file's default admin double throws on every table except `strategies`. So the conventions read had been failing silently all along. With this fix the failure is captured, and the test's `captureToSentry not called` assertion fails.
  - **What I changed:** in that one test, the double now answers the conventions read as an empty, successful read (no echo row, which is a fact and not an outage). The test's assertions are unchanged: arithmetic curve, `returnsConventionOverride`, no capture.
  - **Why I edited it rather than handing it back:** it is test-only, it is disjoint from the files topics B and C own, and leaving it would have committed a red suite.
  - **Please confirm** that this out-of-list edit is acceptable.
- **The capture is at the resolve stage, not in the reader.** The reader has no `caller`. A capture in the reader would fire on every /strategies probe of a composite (WR-01), and it would double-count when a sibling read also fails. The review's sketch had the capture in the resolve stage too.
- **The public lane renders the degraded payload rather than the placeholder.** The review sketch said "throws (or skips storing) exactly as it does for read_error". Taken literally, that would render the placeholder and blank the factsheet, which contradicts D-30. Carrying the payload on the error keeps D-30 and still keeps the build out of the cache.
- **No new Sentry event when a stale entry revalidates.** The resolve stage captures, so the background revalidation captures once per attempt. Next logs and swallows the error, and the stale good entry keeps being served. That matches how `read_error` already behaves.
