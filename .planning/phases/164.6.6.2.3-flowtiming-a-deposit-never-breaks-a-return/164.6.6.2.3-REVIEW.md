# Phase 164.6.6.2.3: Code Review Report (round 1)

**Reviewed:** 2026-10-12T20:25:59Z, at `d5f151362` (plans 01-07, 09-12), plus the plan 08 dry-run harness read in the p08 worktree at `2123b6d6e`.

## Summary

The core change holds up on the paths it was built for:

- The per-cohort split uses `bisect_right`, so a flow and an open on the same instant count the flow first (D-09).
- Overnight positions land in cohort 0 (D-04).
- A `DayTiming` that does not reproduce the day's NAV change fails loud.
- The flow clause is gone from `_guard_denominator`. The negative, dust and pnl-dominated guards still fire, both on the day-level path and per cohort.
- The retired key is carried, never emitted. It is popped on a composite recompute.
- The TS reader shrink is type-safe, and the stale-cache "undefined" case is covered.
- The MT5 USD writer basis satisfies the compose's writer-mode preconditions (W = the NAV days, gap-fill rows are exactly 0.0, the terminal sits on max(W)).
- The transforms threshold reads `USD_FLOORS.dust_nav` on both branches.

What I found are three classes of problem:

1. **A caller left on the old return convention.** `scripts/mt5_soak.py` forward-rolls `NAV_{t-1}(1+r_t)+F_t` over `combine_mt5_deal_ledger`'s returns. A cohort return breaks that identity, so the fidelity gate now false-fails a correct reconstruction.
2. **The money math against the founder's words.**
   - **(a)** The cohort base leaves out P&L realized earlier the same day, so cohorts that overlap compound. The result jumps when a flow appears: a $0 or $1 flow record moves a 20% day to 21%. The Fraction oracle uses the same formula, so no test can catch it.
   - **(b)** The inception tolerance is $1, but the Deribit §5 gate accepts up to $5 of dust per currency (and a total residue up to max($1, 1e-4 x NAV)). A Deribit key with the recorded PROD dust shape (about $1.06) therefore still warns on day 0, so D-01 is not delivered for it.
   - **(c)** On a timed day that re-funds an emptied account, the empty cohort 0 is still judged. That drops and warns a day whose every position sat on real capital.
3. **The plan 08 harness verdict is degenerate.** "Confirmed day-0" is reported for every unguarded MT5 row, and "confirmed flow-only" is unreachable. This feeds the D-13 founder checkpoint.

Oracle independence. `_exact_cohort_return` (test_nav_twr) and `_timed_oracle` (test_mt5_deal_reconstruction) use exact Fraction arithmetic and pick the cohort by a different mechanism (a count, not a bisect). But both restate the same `prod(1 + P_k/B_k)` with `B_k = prev + sum of earlier flows`. They are independent of the implementation, not of the formula. Only one test pins a convention-free invariant: "flow after every open equals the end-of-day formula". The two invariants that would have exposed finding WR-02 are missing: a zero-amount flow is a no-op, and the return is continuous as F goes to 0.

## Warnings (MEDIUM)

### WR-01: `mt5_soak` fidelity gate false-fails on every timed deposit-then-trade day (silent caller change)

**Confidence:** 7/10
**File:** `analytics-service/scripts/mt5_soak.py:155-175` (`_forward_terminal_nav`), `:301-312` (`recon_ok`); cause at `analytics-service/services/broker_dailies.py:883-895` (`timing=timing, full_history=True`)

**Issue:** The soak runner reconciles by rolling `combine_mt5_deal_ledger`'s returns FORWARD with the end-of-day identity `NAV_t = NAV_{t-1}*(1+r_t) + F_t`. It then compares the result to the balance under `max($1, 1e-6*|balance|)`. Since plan 05, a timed flow day's `r_t` is a cohort return, and that identity no longer holds for it. Plans 05 and 06 moved the allocator compose to the writer basis for exactly this reason (the 0.1099 vs 0.1 case). The soak is a second consumer of the same identity and was not moved. Its tests stay green only because their fixtures carry no timed day.

**Failure scenario (reproduced at HEAD):**
- The ledger: deposit 10,000 at 08:00 on 10-16, then deposit 100,000 at 09:00 on 10-17. A position opens at 10:00 and closes at 15:00 for +1,100. Next day, a position makes +500. Balance 111,600.
- `combine_mt5_deal_ledger` returns r(10-17) = 0.01 (correct under D-03).
- `_forward_terminal_nav` rebuilds 110,595.50 against the balance of 111,600. The residual is about -1,004.5 on a $112 tolerance, so `recon_ok=False`, `parity_ok=False`, exit 1.
- The reconstruction is correct and the gate reports a breach. Any operator soak run on a real account that deposits and then trades the same day goes red.

**Fix:** Reconcile on levels instead of on returns. Roll `reconstruct_mt5_nav_levels(...)`, or the `mt5_day_pnl` identity `NAV_t = NAV_{t-1} + P_t + F_t` (the writer basis, which has no return factor), and keep the same tolerance. If the returns must stay in the check, apply the forward roll only to days absent from the fold's `timing`, and assert the timed days through the level identity. Add a soak test with the MM-2x timed shape at USD scale that fails on today's code.

### WR-02: Cohort bases leave out intraday realized P&L, so overlapping cohorts compound and the return jumps with a zero or tiny flow

**Confidence:** 6/10
**File:** `analytics-service/services/nav_twr.py:509-536` (`_judged_cohorts`: `bases.append(bases[-1] + amount)`) and `:539-566` (`growth *= 1.0 + pnl / base`); same formula in `tests/test_nav_twr.py:1861` (`_exact_cohort_return`) and the MT5 `_timed_oracle`

**Issue:** `B_k = B_{k-1} + F_k` leaves out the P&L the account had already realized before the open. The day return is then `prod(1 + P_k/B_k) - 1`. When cohort 0 and cohort k both carry P&L, the product adds a cross term `P_0*P_k/(B_0*B_k)` that the account never earned.
- The result jumps as F goes to 0. A day with a flow record of $0 (an MT5 BALANCE deal with `profit` 0 or None: `_fold_mt5_deals` keeps it in `flow_deals_by_day`, so the day still gets a `DayTiming`) or of $1 returns a different number than the same day with no flow.
- A true time-weighted split values the account at the flow instant, so the next base is `B_0 + P_0 + F`. That gives exactly the no-flow answer as F goes to 0.
- This also departs from D-02's literal words, "the Capital that was in the Account When the Trade opened": a position closed before the open has its P&L in the account at that time. D-03's paraphrase ("start-of-day NAV plus the flows timestamped before the open") drops it.
- That is a conflict between two founder statements. Under Rule 7 it should be surfaced, not averaged.

**Failure scenario (reproduced at HEAD):**
- prev 10,000. Position A opens at 09:00 and makes +1,000. A flow F arrives at 10:00. Position B opens at 11:00 and makes +1,000.
- No flow: the day is 20.0%. F = 0 as a timed record: 21.0%. F = +$1: 20.999%.
- The stored return, Sharpe and CAGR now depend on whether a zero or negligible balance deal sits between two opens.
- For the same shape at -10% / -10%, the stored day is -19% instead of -20%.
- On ordinary 1% days the error is about 1e-4 per day. It compounds over a track record and it is invisible to every test, because both oracles encode the same formula.

**Fix:**
1. Decide the base definition with the founder, D-02 literal or D-03 paraphrase. Record the choice in CONTEXT and in the ROADMAP.
2. If D-02 literal: take `B_k` as `prev` plus every flow AND every cash effect whose instant is at or before the open, which the fold already resolves. That needs the closing-deal instants, not only the opens.
3. Whatever the decision, drop zero-amount flows before the split (`if amount != 0.0` in `_mt5_flow_day_timing`, or in `_judged_cohorts`). A zero flow can then never change a return.
4. Add two invariant tests that are not restatements of the formula:
   - (a) a timed day with a zero-amount flow equals the plain formula;
   - (b) `lim F->0` of the timed return equals the no-flow return to 1e-9.

### WR-03: Deribit day 0 keeps `dust_nav_guard` on a residue the §5 inception gate already accepted (D-01 not delivered)

**Confidence:** 7/10
**File:** `analytics-service/services/nav_twr.py:679-681` (`abs(prev) <= floors.residual_abs_tol`, which is $1.00 for USD); `analytics-service/services/native_nav.py:725-731` (passes `full_history=ledger.full_history` and no `floors`); gate tolerance at `native_nav.py:180, 201, 215, 887-889, 918`

**Issue:**
- `chain_linked_twr` treats day 0 as the inception only when the supplied `prev0_usd` is within `residual_abs_tol` = $1.
- `prev0_usd` is the sum of the rolled pre-history residues (`_prev0_usd`). Before that, the §5 gate (`_assert_inception_reconciled`) has already passed a per-currency residue as dust:
  - up to `INCEPTION_DUST_CAP_USD` = $5 (within 1e-4 of throughput);
  - plus a non-dust total up to `max($1, 1e-4 x |NAV|)`. That is $100 on a $1M book.
- So any accepted Deribit ledger whose day-0 residue falls between $1 and $5 (or up to the relative tolerance) keeps `dust_nav_guard` and `complete_with_warnings` (`negative_nav_guard` if the residue is negative).
- The repo records a PROD shape of about $1.06 (`test_inception_dust_relative_to_throughput_passes`, the PR-1 note at `native_nav.py:203-210`).
- The plan 07 premise ("zero within tolerance on a full-history ledger by the section-5 gate") is therefore false. D-01 says "whatever the noise's sign" and does not limit it to $1 of noise.

**Failure scenario (reproduced at HEAD):** `chain_linked_twr(nav, pnl, flows=[10000, 0, 0], prev0=1.06, full_history=True)` returns `{'dust_nav_guard': True, 'flow_timing_day_level': True}`, with day 0 NaN. The status stays `complete_with_warnings`, as if the phase had not shipped for that key. The day-level annotation also counts day 0 as a "flow at end of day" day.

**Fix:** Make the predicate agree with the gate that certified the ledger. Two options:
- Have `reconstruct_native_nav_and_twr` pass an explicit inception verdict, `inception_base_ok=True` when the §5 gate passed (it raises otherwise).
- Or use the gate's own tolerance, `max(INCEPTION_ABS_TOL_USD, INCEPTION_REL_TOL * |anchor_nav|)` plus the per-currency dust cap, rather than `floors.residual_abs_tol`.

Then add a test at `prev0=1.06` (the PROD shape) and at `prev0=-1.06` that asserts no dust or negative flag. The plan 08 dry run should report Deribit day-0 verdicts separately (see WR-05). Today the harness lumps a day-0 dust guard into "still dropped".

### WR-04: A timed re-funding day of an emptied account is dropped and warns, although every position on it opened on real capital

**Confidence:** 5/10 (this is not a regression: the day-level path dropped the same day before; it is a D-02/D-05 gap the timing data could close)
**File:** `analytics-service/services/nav_twr.py:527-536` (cohort 0 judged unless `inception`) and `:557-561` (`_guard_denominator(base)` on every judged cohort)

**Issue:** On a timed day, cohort 0 is always judged, except on day 0 of a full-history account. When the start-of-day NAV is about 0 (the account was withdrawn to zero earlier) and cohort 0 holds no P&L, cohort 0 measures nothing. Yet its base still trips `negative_nav_guard` or `dust_nav_guard`, and the whole day becomes NaN with a warning. D-02 says a position is measured on the capital at its open, and D-05 says a flow never drops a day. Every position that day opened after the re-deposit.

**Failure scenario (reproduced at HEAD):**
- Full-history MT5 ledger. Deposit 5,000 on day 0; +50 on day 1; withdraw 5,050 on day 2 (NAV 0).
- On day 3: re-deposit 5,000 at instant 1000, then a position opens at 2000 and makes +50.
- Day 3 is NaN with `negative_nav_guard`. It should be 50/5,000 = 1%.
- The row goes to `complete_with_warnings` and picks up an interior `twr_chain_broken`. Under FACTSHEETTRUTH D-01 the headline then compounds only the suffix after day 3, so the factsheet's headline drops the account's whole earlier history.

**Fix:** Apply the inception rule's exemption to any cohort 0 that holds no P&L (`if k == 0 and pnl == 0.0: continue`) when at least one later cohort is judged. A cohort with no positions has no return to guard. Keep the guard when cohort 0 carries P&L (D-06 on a real broken base). Pin it with the scenario above, and with a twin where cohort 0 has P&L on the zero base and must still be guarded.

### WR-05: Dry-run harness verdict is degenerate: "confirmed day-0" for every unguarded MT5 row, "confirmed flow-only" unreachable

**Confidence:** 5/10
**File:** `quantalyze-164.6.6.2.3-p08/analytics-service/scripts/flowtiming_dry_run.py:473-521` (`_classify_row`, `leading = first stored return - after.first_index_day`; `if leading > 0: "confirmed day-0"`)
