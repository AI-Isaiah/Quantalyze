# Phase 164.6.6.3.4: STATUSBRIDGE - Context

**Gathered:** 2026-10-07
**Status:** Ready for planning

<domain>
## Phase Boundary

A strategy's analytics status (`strategy_analytics.computation_status`, written by `sync_strategy_analytics_status`)
reads `failed` only for a live analytics failure. A failed `process_key_long` is superseded by a later
successful follow-on chain, and side kinds that produce no analytics never pin the status. A genuine
analytics failure is still never masked. One migration re-basing the latest
`sync_strategy_analytics_status` body (`supabase/migrations/20261003120000_sync_status_bridge_residues.sql`),
plus a PROD status re-sync after it applies. No new UI.
</domain>

<decisions>
## Implementation Decisions

### Carried from the ROADMAP (founder 2026-10-06)
- **D-01 (i):** A failed `process_key_long` is superseded by a later successful follow-on chain for the
  same strategy (`derive_broker_dailies` + `compute_analytics_from_csv`), because that chain re-reads the
  full history.
- **D-02 (ii):** Side kinds that produce no analytics never enter the analytics live-failure set. Their
  failures surface on the key or job surface instead.
- **D-03:** Rejected for now: rotate-secret enqueues a resync.
- **D-04:** The per-kind rule stays for every other kind: a later `done` of a DIFFERENT kind never masks
  a real analytics failure.

### Founder decisions (2026-10-07, AskUserQuestion)
- **D-05 (side kinds):** An explicit, named list of side kinds is excluded (`sync_funding`,
  `poll_positions`, and any other kind research proves produces no analytics, each with evidence). Any
  kind NOT on the list, including future kinds, still counts toward `failed`. Unknown resolves loud.
- **D-06 (supersession):** A failed `process_key_long` is cleared only when BOTH `derive_broker_dailies`
  and `compute_analytics_from_csv` for the same strategy finished `done` strictly after the failure
  (`created_at` later). A later compute alone does not clear it.
- **D-07 (surface):** No new UI in this phase. Research confirms that a side-kind failure stays visible
  on an existing surface (key card, job surface, Sentry). Only if one would become fully invisible does
  the planner add the smallest key-card note for it.
- **D-08 (backfill):** After the migration applies on PROD, re-run `sync_strategy_analytics_status`
  through the function itself (no hand UPDATEs), with a before/after table of statuses recorded in the
  phase. Marker query first.
  ⛔ **AMENDED 2026-10-07 (founder, AskUserQuestion, after research):** NOT every strategy. Only the
  `failed` rows that have compute jobs (3 at research time: Eclipse plus two genuine failures that stay
  `failed`), one call each. Reason: branch (c) stamps `computed_at = now()` unconditionally, so a
  blanket re-run would make 22 healthy rows (12 with compute dates older than two days) read as freshly
  computed. The original "every strategy" wording above is superseded.

- **D-09 (founder 2026-10-07, AskUserQuestion after review round 1, "Fix before merge"):** when the ONLY failures this call sees are excluded side kinds (D-05) and nothing else moved the row to branch (c), the bridge must NOT stamp `computed_at = now()` and must NOT clear a `computation_error` it did not write. A failing nightly side job (e.g. a `sync_funding` timeout) must never make stale analytics look freshly updated. A gate arm that goes RED with the fix removed pins it. Source: SFH M1 (confidence 6) + migration-reviewer note 2.
