## Summary

The only executable change is two conjuncts in the `live_failures` CTE of `sync_strategy_analytics_status`. I diffed everything from the `-- the bridge, re-based` banner to the end of the old file against the new file. There are exactly three hunks:

- six new `DECLARE` variables in the verify block;
- the new anchors (xv) to (xviii), plus the replaced final NOTICE.

The `REVOKE` and `GRANT` are byte-equal, and there is no `COMMENT ON FUNCTION`. The rollback's restore block (banner through `GRANT`) is byte-identical to 20261003120000 (`diff` printed nothing). I reproduced the VAC-04 `--diff-bodies` row, and `schema:functions:check` is current.

The SQL semantics hold:
- **NULL kind.** `compute_jobs.kind` is `NOT NULL` (baseline `:1376`, and FK to `compute_job_kinds`), so `f.kind NOT IN (...)` is two-valued and cannot silently drop a row. The four literals are non-NULL, so the NULL-element trap of `NOT IN` does not apply.
- **Empty list.** An empty `NOT IN ()` is a syntax error in Postgres, and anchor (xv) refuses a NULL or different literal set through `COALESCE(..., FALSE)`.
- **Supersession key.** It is matched on `strategy_id` and strict `created_at > f.created_at`, per failure, with both EXISTS required. That is exactly D-06. Key-mode derives (`strategy_id IS NULL`) cannot match, which is the safe direction.
- **Interactions.** `process_key_long` is outside the marker kind list, so `is_protected`, `has_live_successor` and `v_protect_hold` are unaffected. While the chain is in flight the pkl failure stays in `v_unprotected_job_ids`, so branch (a) still clears a writer stamp naming it.
- **Read order.** The monotonicity argument for the read order still holds: a chain job turning `done` between the two reads leaves the non-terminal count at least 1, so branch (a) runs.

I swept the rest of the corpus. No other gate seeds a failed side-kind job and asserts `failed`. Only `test_sync_status_preserves_warnings.sql` Part 4 did, and that is the executor's deviation 1. `test_sync_status_supersede_failed_per_kind.sql` uses `poll_positions` only as a later DONE sibling, which is unaffected. The census values reconcile: the `ci.yml` sum comment is 269, and 591 / 700 / 87 / 60 match across all five pin files. origin/main has not moved past 239106dc5.

I found no CRITICAL, HIGH or MEDIUM defects. The LOW findings are drift in documentation and guards: in-body comments that now contradict the code, an anchor whose stated purpose it cannot serve, and gaps in the drift test and the gate that a static anchor covers only partly.

### IN-02 [LOW, confidence 8]: Anchor (xviii) cannot catch the failure it says it exists for

**File:** `supabase/migrations/20261009120000_sync_status_analytics_scope.sql` (anchor (xviii), the `v_pkl_sites` block near the foot)

**Issue:** The comment says "A second site is how the exemption gets copied onto another kind by a copy edit." A copy edit changes the literal in the copy (`f.kind = 'sync_trades'`), so the count of `'process_key_long'` stays 1 and (xviii) passes. (xvii) also passes, because its regex needs one match and does not count matches. In practice (xviii) only catches edits that add a second `'process_key_long'` literal, such as the `OR TRUE` neuter plan 02 used.

**Failure scenario:** A copy of the D-06 clause for `sync_trades` applies cleanly on TEST and PROD. Only the behavioural gate arm G2 (failed `sync_trades`, then a done chain, stays `failed`) goes red, and only if that gate runs against the re-based body.

**Fix:** Count the supersession clauses rather than the literal. For example, require exactly one match of `NOT\s*\(\s*f\.kind\s*=\s*'[a-z_]+'\s+AND\s+EXISTS` and require its literal to be `process_key_long`. Or reword the comment to say what (xviii) actually guards.

### IN-03 [LOW, confidence 6]: Drift test has two blind spots: `stitch_composite` on the side list, and a silent fall-back to a stale coherence CHECK

**File:** `src/__tests__/status-bridge-side-kinds-drift.test.ts:67-68, 132-163, 173, 190-201`

**Issue:**
1. The disjointness test checks side ∩ `FACTSHEET_CHAIN_KINDS` only. `stitch_composite` counts toward `failed` but is not in `FACTSHEET_CHAIN_KINDS`. If it is added to the side list, `classified` still contains it, `phantom` is empty and `both` is empty, so all three tests pass. That is the unsafe direction the header names: "a kind quietly added to the side list would silently stop pinning failed". Only SQL anchors (xv) and (xvi) catch it, at apply time.
2. `COHERENCE_ADD_RE` accepts only `ALTER TABLE [public.]compute_jobs ADD CONSTRAINT ...`. If a later migration re-adds the constraint as `ALTER TABLE ONLY ...`, with quoted identifiers, or through `EXECUTE format(...)`, the scan skips it and silently returns the older `20260717233529` CHECK. A newly admitted strategy-carrying kind is then never seen, which defeats the "forcing function".

**Fix:**
- Assert `side ∩ {stitch_composite, ...counting kinds outside the chain list}` is empty, or simply that `side` is disjoint from `classified \ side`.
- For the scan, either widen the regex (`ALTER\s+TABLE\s+(?:ONLY\s+)?(?:IF\s+EXISTS\s+)?(?:"?public"?\.)?"?compute_jobs"?`), or assert that no migration newer than the one found mentions `compute_jobs_kind_target_coherence` outside a comment.
