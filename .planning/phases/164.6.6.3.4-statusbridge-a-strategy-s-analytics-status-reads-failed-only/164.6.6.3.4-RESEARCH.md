## Summary

The change is small and local. In `supabase/migrations/20261003120000_sync_status_bridge_residues.sql` the whole decision
lives in one CTE (`live_failures`, lines 504-653): its `FROM compute_jobs f WHERE ...` clause (lines 642-653) selects every
`failed_final` job with no later `done` of the SAME kind. D-05 adds one conjunct there (`f.kind NOT IN (<four side kinds>)`)

throwaway pg-lane: the whole carried self-verify block (marker-list identity, membership count 8, hold CASE count 4, kind-list

The four side kinds are `sync_funding`, `poll_positions`, `reconcile_strategy`, `compute_intro_snapshot`. Their handlers write

### The two conjuncts (prototyped, GREEN)

```sql
     FROM compute_jobs f
     WHERE f.strategy_id = p_strategy_id
       AND f.status = 'failed_final'
       -- D-05: closed list of side kinds. NOT IN, so an unknown or future kind still counts.
       AND f.kind NOT IN ('sync_funding', 'poll_positions', 'reconcile_strategy', 'compute_intro_snapshot')

       -- chain finishing done strictly later. No marker test: a ledger-refresh chain counts.
       AND NOT (
         f.kind = 'process_key_long'
         AND EXISTS (SELECT 1 FROM compute_jobs c1
                      WHERE c1.strategy_id = f.strategy_id AND c1.kind = 'derive_broker_dailies'
                        AND c1.status = 'done' AND c1.created_at > f.created_at)
         AND EXISTS (SELECT 1 FROM compute_jobs c2
                      WHERE c2.strategy_id = f.strategy_id AND c2.kind = 'compute_analytics_from_csv'
                        AND c2.status = 'done' AND c2.created_at > f.created_at)
       )
       AND NOT EXISTS ( ... existing same-kind supersession, unchanged ... )
```

### The RED-UNDER idiom (from `test_sync_status_bridge_residues.sql`)

- `-- RED-UNDER-SETUP: {"apply":[ ...ordered file list... ]}` once per file: fixtures first, then migrations in apply order.
- Per arm, a `-- RED-UNDER:` prose line and a `-- RED-UNDER-M: {"arm":"<ID>","apply":[{"kind":"edit","file":"<migration>","find":"<exact text>","replace":"<text>","occurrences":N}, ...]}` twin that edits the LAST-DEFINING migration.
- **Layered twins.** Every twin that neuters a statement also stands down its companion verify anchor (`"find":"IF NOT v_x_anchored THEN","replace":"IF FALSE AND NOT v_x_anchored THEN"`) and re-baselines any COUNT anchor it moves (`IF v_membership_sites <> 8` -> `<> 7`). Without the companion edit the lane apply RAISES inside the migration and the runner scores a defect instead of the intended `TEST FAILED (arm)`.
- Identities carry a digit (`W1`, not `W`): `sectionOfIdentity` collapses a `-SUFFIX` into its parent only after a digit.
- Arm body: `INSERT INTO auth.users`, `profiles`, `api_keys`, `strategies`, `strategy_analytics`, `compute_jobs` (explicit `created_at` to force generation order), then the REAL `mark_compute_job_failed` / `mark_compute_job_done`, then read `strategy_analytics` back. Whole file inside `BEGIN; ... ROLLBACK;`, completion sentinel `RAISE NOTICE 'ALL N ARMS EXECUTED (...)'`.
- SETUP vacuity guards ("the fixture reached the branch this arm is about") are named `<ID>-SETUP` and are deliberately not twinned.

## Q7. Pitfalls

### Pitfall 1: re-basing on a stale body
**What goes wrong:** copying `20260906120000` or an older snapshot silently drops the BRIDGERESIDUE arms (membership sites, hold CASEs, in-bridge lock, `service_role` grant).
**How to avoid:** copy `20261003120000` byte-for-byte; the carried verify block is the proof (membership sites = 8, hold CASEs = 4, lock placement, `service_role` EXECUTE). Do not re-issue `COMMENT ON FUNCTION` (the A1 anchor at 1244-1250 keys on `20260826120000` surviving `CREATE OR REPLACE`).
**Warning signs:** the migration applies but `test_sync_status_bridge_residues.sql` goes RED on the local stack.

### Pitfall 2: ACL and SECDEF regressions
Preserve `LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_catalog`, `SET LOCAL search_path` / `SET LOCAL lock_timeout = '3s'` at the top, `REVOKE ALL ... FROM PUBLIC, anon, authenticated` and the explicit `GRANT EXECUTE ... TO service_role` (a bare cluster without Supabase default privileges has none; the lane proves it). The carried arms at 1255-1284 and (xiv) at 1810-1815 assert these.

### Pitfall 3: a data-reading DO block refusing on TEST
TEST's `public` is a schema-only copy: every table is empty. The migration's DO block must not count jobs or rows (`[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`). All new anchors read only `pg_get_functiondef`. The backfill is a separate manual step.

### Pitfall 4: the comment-bearing H1 anchor
Any `last_error` in a function-body comment raises on apply. Put every explanation in the file header (`pg_get_functiondef` does not return it).

### Pitfall 5: kind-list regexes
`kind NOT IN` is invisible to `\mkind\s+IN\s*\(` (verify (ix)) and to the Python/TS drift readers, which is why it applied green. `NOT (kind IN (...))` is not invisible. Never fold the side list into the marker list.

### Pitfall 6: branch (c) is a published-success transition for a side-only failure
After the change a strategy whose only live-looking failure is a side kind falls through to branch (c): `complete` (or `complete_with_warnings` if warned), `computation_error` cleared, `computed_at = now()`. This is the same transition a successful `sync_funding` already produces today (114 done rows on PROD). Eclipse's nightly failing `sync_funding` will re-stamp `computed_at` each night. This is the booked stated limit (migration header lines 133-144, Phase 166.5 COMPUTEDATSTAMP), not new, but it is why the D-08 scope question matters.

### Pitfall 7: in-flight side jobs still count in branch (a)
Branch (a) counts EVERY non-terminal job (lines 421-431), side kinds included, so a running `sync_funding` still moves a plain `complete` row to `computing` today. D-05 scopes the FAILURE set only; the read order and hold logic stay. Left for the founder as awareness (Open Questions Q-B).

### Pitfall 8: twins that break the lane apply
A twin that removes the `NOT IN` line must also stand down the (xv)/(xvi) anchors, and one that removes the D-06 clause must stand down (xvii)/(xviii); otherwise the apply RAISES inside the migration before the gate runs.

### Pitfall 9: timestamp and version collisions
The newest migration on `origin/main` is `20261007120000_api_keys_account_currency.sql`; the new file must sort after it. Other worktrees (164.6.6.3.x) may also ship migrations: re-pick the timestamp and the VERSION digit from `origin/main` right before the single CI run.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| A second bridge or a TS-side status derivation | new status logic | the one SECDEF bridge | every terminal mark already routes through it under the per-strategy lock |
| Bulk status repair | `UPDATE strategy_analytics SET computation_status = ...` | `SELECT sync_strategy_analytics_status(id)` | D-08; hand UPDATEs bypass provenance and the lock |
| A helper function holding the side list | `IMMUTABLE` list function | inline `NOT IN` | one reader; a helper needs ACL, comment and verify arms |
| New mutation-lane kind registration inside a gate | `INSERT INTO compute_job_kinds` in the gate body | a pg-lane fixture | gate bodies run inside `BEGIN/ROLLBACK`; fixtures are the documented seam |

**Key insight:** the existing structure already separates "which failures exist" (the CTE) from "what to do about them" (the branches). Filtering at the CTE keeps every downstream invariant (ordering, provenance, hold, partition) correct by construction instead of re-proving each.
