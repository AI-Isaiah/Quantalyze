**Files (research Q5 procedure, narrowed by the D-08 amendment).**
The CLI returns only the LAST statement's rows, so each guard file is a `DO` block that RAISEs, followed by
one final `SELECT` of a fixed OK string.
- `00-marker.sql`: a `DO` block that reads `shobj_description(oid, 'pg_database')` for `current_database()` into a variable and RAISEs EXCEPTION (a single literal, never including the marker text) when it is NULL, when it does not match `prod` case-insensitively, or when it matches `test` as a whole word (`(^|[^[:alnum:]_])test([^[:alnum:]_]|$)`, case-insensitive); then `SELECT 'marker OK' AS which_database_check;`.
- `05-live.sql`: a `DO` block that RAISEs EXCEPTION unless `position('compute_intro_snapshot' IN pg_get_functiondef('public.sync_strategy_analytics_status(uuid)'::regprocedure)) > 0` AND a `supabase_migrations.schema_migrations` row with the new migration's version exists; then `SELECT 'live OK' AS live_body_check;`.
- `10-before.sql`: status counts by value over `strategy_analytics`; the target list (`computation_status = 'failed'` AND `EXISTS` a `compute_jobs` row for the strategy) with, per target, an ordinal, the pre-image columns, the count of in-flight jobs (status IN (`pending`, `running`, `done_pending_children`, `failed_retry`), named explicitly as the bridge's read 1 does, never a NOT IN), and the read-only PREDICTION in the bridge's own read order: (1) any in-flight job -> branch (a): `complete_with_warnings` when `computation_warned` is TRUE or the current status is `complete_with_warnings`, otherwise `computing`; else (2) the count of `failed_final` jobs that are not a side kind, not a `process_key_long` superseded by a later done derive AND a later done compute, and not superseded by a later done of the same kind -> `failed` if > 0; else (3) `complete_with_warnings` if `computation_warned`, otherwise `complete`.
- `20-resync-<n>.sql`: `SELECT public.sync_strategy_analytics_status('<id>'::uuid);`, one file per target.
- `30-after.sql`: the same reads as `10-before.sql` for the same targets.
- `40-check.sql`: a read-only `DO` block over the targets re-synced so far (Task 1: the one target; Task 2: every target). For each, it re-derives in-flight at check time FIRST, with the same inclusive status list: a target with an in-flight job gets `RAISE NOTICE` naming its ordinal and its current status (recorded, never an exception). Otherwise it RAISEs EXCEPTION naming the ordinal when the status differs from its prediction.
