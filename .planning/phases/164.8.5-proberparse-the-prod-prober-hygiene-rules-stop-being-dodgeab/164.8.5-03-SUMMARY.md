# Phase 164.8.5 Plan 03: The hygiene lexer and the derived-length header rules — Summary

The cron-drift hygiene rules now read a real lexer instead of raw text: `codeSpans()` re-enters a
top-level `DO $body$` block as CODE, the header rules length-test the value a command can DERIVE
rather than the first literal they happen to see, an unbalanced header region is refused out loud
instead of silently widened, and every measured bypass shape that returned zero violations before
this phase now fires a named rule. **`HEADER_LITERAL_MIN` and `HEADERS_LITERAL_MAX` did not move
(D4) — the measurement fed to them did.** All 14 committed PROD commands stay clean.

## Deviations from Plan

### 1. [Rule 1 - Bug] The criterion-4 apostrophe pair STRADDLES the threshold, so the plan's own fixtures would have DISAGREED

- **Found during:** Task 1, measuring the prototype before writing the rules.
- **Issue:** the plan prescribes `$q$FAKE-don't-0123456789-0123456789$q$` vs the same without the
  apostrophe. **MEASURED: 32 and 31 characters.** `HEADERS_LITERAL_MAX` is 32, so the first fires
  `long-literal-in-headers` and the second is clean — and Task 2's `<verify>` asserts they are
  **equal**. The pair would have failed for a reason that has nothing to do with the lexer: the
  apostrophe adds one character and the threshold sits exactly between them.
- **Fix:** both spellings padded by four characters (`…-0123`), giving 37 and 36 — both comfortably
  over the threshold, both `["long-literal-in-headers"]`, and the criterion now isolates the LEXER
  from the threshold, which is what it was for. The scenario additionally refuses a pair that agrees
  on EMPTY.
- **Files modified:** `hygiene-bypass.json`, and Task 2's verify string. **Commit:** `c904c3cc`.

### 2. [Rule 1 - Bug] The plan's `pg-password` raw arm SUBSUMES its masked arm — a control that cannot fail

- **Found during:** Task 1, checking each new arm was individually neuterable.
- **Issue:** the plan says to test `/password\s*:=/i` on `masked` **and keep `/password\s*:?=/i` on
  raw**. With the colon OPTIONAL, the raw arm also matches `v_password :=` — and everything matching
  on masked matches on raw at the same index, because the mask only ever blanks. **MEASURED:**
  `/password\s*:?=/i.test("… v_password := 'FAKEpw' …")` → `true`. The masked arm could therefore
  never be the reason a command was flagged. Its `<done>` line ("removing the masked `:=` arm drops
  `pg-password`") could not have held.
- **Fix:** the raw arm is the EXISTING `/password\s*=/i` (no optional colon), which does **not**
  match the assignment form — measured `false`. The three arms are now provably disjoint and rows 6
  and 7 of the matrix each redden alone.
- **Files modified:** `scripts/prod-prober/arms/cron-drift.mjs`. **Commit:** `545db484`.

## Live-behaviour note the next reader needs

Two NEW ways for the hourly prober to go red:

1. **A command whose header argument list does not balance is now `measure-fail`**, and the run exits
   1 with no drift verdict for that row. This is new: the old code silently widened the region to the
   end of the text and kept judging. A truncated reading of a long `DO` block would now be refused
   rather than quietly cleared.
2. **The header rules see far more spellings.** Anything that DERIVES 16+ characters under
   `X-Service-Key` / `Authorization` / `apikey`, or 32+ under any header name, now fires — including
   `||`-splits, `concat`/`format`/`chr`/`decode`/`quote_literal`, and `$q$…$q$` / `E''` / `U&''`
   literals. The false-positive direction is guarded by the committed-manifest budget and by the
   green fixtures, but a NEW cron job that assembles a long non-credential header value from parts
   would be a new red. The remedy is in the rule id.
