## The findings

### CR-01 — `normalizeCommand` collapsed newlines into `--` comments — **CLOSED (code), NOT CLOSED (the committed oracle)**

`ws-collapse-v1` was `.replace(/\s+/g, " ")`. A newline is not whitespace in SQL; it is what
TERMINATES a `--` comment. `captureManifest` STORES `normalizeCommand(command)`, so the fold was
baked into the oracle at capture time.

Fixed: `ws-collapse-v2` normalises `\r\n`/`\r` to `\n`, then collapses HORIZONTAL whitespace
per line and trims each line. Line breaks survive. `NORMALIZATION` bumped. The
`hygieneViolations` docstring's claim that "normalization does not change any of these
judgements" is corrected — it was measurably false.

**⚠️ THE COMMITTED MANIFEST NOW READS AS INVALID AGAINST ITSELF. Measured, not predicted:**

```
compareManifest(cron-manifest.json, its own rows as PROD):
  manifest-invalid :: the cron manifest declares normalization "ws-collapse-v1";
                      this arm computes ws-collapse-v2.
```

Two further measurements that bound what that means:

- `shas that no longer bind under ws-collapse-v2: 0 of 14`. Every committed `command_sha256`
  still equals `sha256(normalizeCommand(command))`, because every stored command is already
  single-line. So this is a VERSION refusal, not a hash break. The (1a) sha-binding check passes.
- The refusal is the honest state and is the loud signal that forces the re-capture. **I did not
  re-capture — that needs a PROD read and is the founder's call.** Until then the live hourly arm
  will report one `manifest-invalid` and no drift comparison. Section (0)'s PROD-side credential
  scan is above every `return` in `compareManifest` and is unaffected.

**The 14/14 positive-control gate could NOT be met, and here is why.** The brief expected
`13/14 → 14/14` after CR-01. It stays 13/14, and the reviewer's finding contains one wrong
inference about WHERE the fold happened:

```
PROBE (token 39 chars): 13/14 caught
  BLIND: retention_compute_jobs_orphaned_running -> []
```

- Section (0) scans PROD's **raw** `cron.job.command` straight from `parseCronJobRows`, newlines
  intact. It was never blind. The blindness is on the MANIFEST side, because the manifest's
  `command` field is the text that was already normalized at capture.
- `retention_compute_jobs_orphaned_running` as committed is 1791 characters with **0 newlines**,
  opening with `-- CANARY_162_V1_PROSE_ONLY`. Measured: `commands whose OUTER span masks to ALL
  WHITESPACE: 1`. As a SQL program that text is entirely a comment — a no-op. The arm reading
  nothing in it is a TRUE reading of a damaged artifact, not a rule defect.
- No change to `normalizeCommand` can put those newlines back. Only a re-capture can.

What I CAN measure, and did (the restored text is CONSTRUCTED by me and labelled as such — it is
not a claim about PROD):

```
v1 artifact as committed      -> []
same program, line break back -> ["long-token-anywhere"]
their normalized shas differ  -> true
```

So the class is closed at the mechanism: under v2 the fold cannot happen again, and the working
program no longer hashes identically to its no-op twin. The committed artifact remains 13/14
until re-captured. **Recommendation to the founder: re-capture the oracle** (`--capture-manifest`
against PROD, review by hand, commit). That single action takes the probe to 14/14 and clears the
`manifest-invalid`.

**Anti-vacuity.** New self-test scenario "CR-01: capture STORES the line breaks…" over a new
fixture `prod-multiline-comment.json`, asserting the stored command keeps its break, still lexes
to executable code, still catches a spliced token — with the v1-folded twin measured inline as the
negative (`0` executable characters, `no rule fired`) and the two shas asserted different.
`prod-ok-shuffled-crlf.json` lost its literal CRLF bytes: it proved "not drift" by RE-WRAPPING a
command, which under v2 IS drift; CRLF and lone-CR equivalence moved to a direct assertion on
`normalizeCommand`, which names the function under test.

Neuter (`normalizeCommand` reverted to v1), declared and matched exactly —
`others=[] missing=[]`:
1. `and RE-WRAPPING is drift: the same bytes with and without one line break normalise DIFFERENTLY…`
2. `the STORED command still carries its line break — under v1 it did not… (stored 1 line(s))`

### CR-03 / F1 — `DO '…'` was a total blind spot — **CLOSED**

Reproduced:

```
DO $$  => ["long-token-anywhere"]
DO '…' => []
spans: 2 1
```

`codeSpans` iterated `dollarRegions` only; `literalsIn` skipped every `DO`-prefixed literal
INCLUDING single-quoted ones, on the premise that `codeSpans` re-enters them. For `DO '…'` nobody
did — skipped as code AND skipped as data. `codeSpans` now walks the span with the same
primitives every other walk uses (`skipQuotedIdent` + `literalAt`) and recurses on the
`''`-unescaped content. `DO_PREFIX` gained `(?:[EU]&?)?` so `DO E'…'` / `DO U&'…'` are covered
and the ONE predicate stays honest for BOTH readers.

After: both spellings report `["long-token-anywhere"]`, `spans: 2 2`.

**Recorded, not fixed:** the single-quoted recursion runs on the unescaped content (the program
PostgreSQL actually runs), so a child span's `base` is an approximation — every `''` shortens the
body by one character. Nothing reads `base` today; the docstring now says so.

**Anti-vacuity.** Bypass row `(k) bypass_do_single_quoted_job`, derived MECHANICALLY from the `(h)`
row so the two cannot drift, carrying `expect_same_verdict_as: bypass_var_key_job`.

Neuter (the `DO_PREFIX` test at the single-quoted call site alone), `others=[] missing=[]`:
1. `every MEASURED bypass shape now fires at least one rule ((k) DO '…' — the SINGLE-QUOTED procedural body…)`

Commit `4ee7d8af`.

### F3 — a throw in `compareManifest` discarded every defect already collected — **CLOSED**

Both hygiene loops (section 0 PROD-side, section 2 manifest-side) now judge each row through a
`judgeRow` wrapper: a throw becomes a `measure-fail` naming `prod:<job>` / `manifest:<job>` and the
loop CONTINUES.

pointing the wrong way — it ran on three CLEAN rows and asserted the ABSENCE of
`cron-secret-in-command`. It now runs on `prod-leaky-plus-match.json` (the flagship beside a
LEAKING non-flagship row) and asserts the credential line is STILL THERE, with a PRECONDITION that
the fixture really leaks when the snapshot is present, plus an assertion that defects collected
AFTER the refused row survive.

⚠️ **A residual worth naming:** `hygieneViolations` builds its list and only then calls
`reachesVaultRead`, so if the row that throws is itself leaking, ITS OWN findings are still lost

resolves callables for. Scoping the refusal to the row is a strict improvement over losing all
rows; making a single row report both a credential AND a refusal would need a new rule id, a red
fixture and an `UNJUDGEABLE_RULE_IDS` edit, which is a larger change than this finding asked for.

**Anti-vacuity.** Two neuters, one per call site, `others=[] missing=[]` each:
1. section (0) unwrapped → `exactly one measure-fail, SCOPED TO THE ROW that could not be judged (got measure-fail:null)`

The `measure-fail:null` in (1) is the mechanism itself: the arm-level throw with no subject.
