## Accomplishments

- **Criterion 2, both directions at once.** `text.includes("vault.decrypted_secrets")` got D2 wrong in BOTH directions simultaneously: it accepted a command naming the table in a `--` comment or a string, and it rejected `SELECT public.match_engine_cron_tick();` — the command Phase 164.5.1 will schedule PROD onto, which carries no Vault reference at all. The rule now asks reachability: the `FROM`/`JOIN vault.decrypted_secrets` shape on some code span's MASKED text, or a call (also collected on masked text, so a "call" inside a comment is not one) to an unqualified/`public.` function whose COMMITTED body reaches one, transitively.
- **Fail closed, in three distinguishable ways.** An unknown callable → the rule FIRES and NAMES it (a function name, never a value). A missing snapshot DIRECTORY → throws, which `runProber` maps to `measure-fail` — absence of the instrument is not absence of the finding. Resolvable-but-not-a-reader → fires with nothing named.
- **The 164.5.1 collision is measured every run, not argued in a plan.** One scenario resolves the real command against the real `supabase/schema/functions/` snapshot, with a control arm proving the green is a real resolution rather than a rule that accepts everything.
- **`long-token-anywhere` catches (h) and (i).** Both are what a normal developer writes, with no obfuscation: in (h) the header value is a plpgsql variable, so every header-anchored rule has nothing to measure; in (i) the header NAME lives inside a bigger literal, so the anchor never matches. Every other rule in the arm looks at a header region; in both shapes the key is elsewhere.
- **The Q2 partition became an invariant.** `export const TOKEN_MIN = HEADERS_LITERAL_MAX;` — one source of truth by source line — plus a wiring pin asserting equality under a title that states the argument. `HEADERS_LITERAL_MAX` keeps its value (D4); it is merely exported.

The cause: at the OUTER span a top-level `DO $$ … $$` is one dollar-quoted literal, and
`headerRegions` finds NOTHING there because the whole body is blank in the outer mask. So without

partition would have held only for non-`DO` commands, which are the MINORITY shape (4 of the 14 real
commands are `DO` blocks). The answer was to ship `header_region_only_in_do`, a second `expect_not`

## Decisions Made

1. **The absent-directory check is at the TOP of `reachesVaultRead`, not inside `resolveCallable`.**
   The plan specified the throw inside the resolver, which is only REACHED by a command that needs
   resolution. Measured consequence of that placement: a deleted snapshot reads CLEAN for
   `DO $$ … FROM vault.decrypted_secrets … $$` (it satisfies the shape directly and never resolves
   anything), and the missing-snapshot scenario over `prod-ok.json` would have found no defect at
   all. Hoisting it makes a missing instrument loud for every judgement of that job.
2. **`literalsIn` skips `DO` bodies**, using `codeSpans`' own `DO_PREFIX` predicate byte-identically.
   Otherwise every CODE token in a procedural body is length-tested as data, and (per the matrix
   above) the header-region exclusion silently stops applying inside `DO` blocks.
3. **Equality, not `>=`, for the `TOKEN_MIN` pin.** `>=` is what the partition needs; equality is
   what the derivation says. A divergence in either direction should be somebody's deliberate act.
4. **The count-free pin is anchored to the ASSERTION form.** A bare `red.data.length === \d+`
   predicate matched wave 3's dated lineage COMMENT recording the defect it fixed. History must stay
   readable; what criterion 9 forbids is a hand-typed count that JUDGES something.
