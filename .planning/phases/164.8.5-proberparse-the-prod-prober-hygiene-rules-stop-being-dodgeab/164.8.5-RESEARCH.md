## Summary

Every question below was answered by running code against this HEAD, and two of the answers overturn the plan as CONTEXT.md sketches it:

1. **`masked` alone breaks the arm on four of the fourteen real PROD commands.** `scanSql` treats a top-level `DO $body$ … $body$` as one dollar-quoted STRING and blanks its entire content. The real `match_engine_cron` command, the hygiene GREEN fixture for it, and three other live jobs are `DO` blocks. A `vault-absent` rule written as "executable read shape on `masked`" therefore fires on the very shape it exists to endorse. `[MEASURED]`: `real jobid1 naive: false`, `green match_engine_cron naive: false`. The fix is small and I prototyped it — treat a dollar region whose masked prefix ends in `DO [LANGUAGE x]` as CODE and re-scan it recursively (`codeSpans`) — but it must be the FIRST thing the hygiene plan builds, and every rule in Q2 is written against `codeSpans`, not against `masked`.
2. **"A long literal ANYWHERE ≥ 32" fires on 5 of 14 real commands, at every threshold up to 64.** `[MEASURED]`: 6 literals ≥ 32 chars, all `RAISE` message text or one URL, lengths 73–156. The narrowing that measures to ZERO false positives on the real corpus while still catching bypasses (h) and (i) is: split literal contents on whitespace, flag a token ≥ 32 chars that contains at least one digit and is not a bare URL. Q4 has the token census.

The rest confirms the plan: importing `scanSql` is free of cost or rule violation (Q1); the derived-length sum must skip `(SELECT …)` subselects or it fires on the green `'Bearer ' || (SELECT …)` shape (Q3 — the naive sum reads 28, the refined one 7); the Vault-reading callable set is exactly one function in a 120-file hermetic snapshot with zero transitive edges today (Q5); the four `DETECT_RE` spellings are `E'`, `$tag$`, `U&'` and `/*c*/` before the paren, and the review's proposed regex leaves the corpus at 12→12 with zero per-file diffs (Q6).

## Q2 — What `masked` gives each rule, and where it stops

### The finding that changes the design: `DO $tag$ … $tag$` is masked as ONE STRING

`scanSql` records every top-level dollar quote as a `dollarRegion` and blanks its content in `masked` `[VERIFIED: sql-body-normalize.mjs:177-196]`. It has no concept of `DO`. So for a cron command that is a `DO` block, `masked` is `DO $body$` + spaces + `$body$` — every rule that reads `masked` sees nothing.

`[MEASURED]` on the committed oracle and the committed green fixture:

```
real jobid1      naive: false  withDo: true
green match_engine_cron            naive: false  withDo: true
green fixture_bearer_concat_job    naive: true   withDo: true
green fixture_apikey_var_job       naive: false  withDo: true
red vault-absent naive: false  withDo: false
comment-only : false  literal-only: false  dollar-literal-only: false  tick-call: false
DO nested literal: false
```
(`naive` = `/\b(FROM|JOIN)\s+vault\.decrypted_secrets\b/i` on `scanSql(cmd).masked`; `withDo` = same test over `codeSpans(cmd)`.)

Four of the 14 real commands are `DO` blocks `[MEASURED]`: `audit_log_hot_to_cold` (`DO $body$`), `match_engine_cron` (`DO $body$`), `reconcile_dropped_enqueue_sweep` (`DO $sweep$`), `retention_notification_dispatches` (`DO $body$`). Today's raw-text rules only work on them BECAUSE they are dollar-blind — which is also why bypass (a) works.

**The recursion, prototyped and measured (put this in `cron-drift.mjs`, not the normalizer):**

```js
// Source: prototype run this session against scanSql; DO_PREFIX tested on all 14 real commands
import { scanSql } from "../../sql-body-normalize.mjs";
const DO_PREFIX = /\bDO\s+(?:LANGUAGE\s+[A-Za-z_]+\s+)?$/i;
const MAX_DOLLAR_DEPTH = 4;
/** Every span of EXECUTABLE text: the outer command, plus each DO body, recursively. */
export function codeSpans(sql, base = 0, depth = 0, out = []) {
  if (depth > MAX_DOLLAR_DEPTH) throw new Error(`dollar-quote nesting deeper than ${MAX_DOLLAR_DEPTH}`);
  const { masked, dollarRegions } = scanSql(sql);
  out.push({ base, sql, masked, dollarRegions });
  for (const r of dollarRegions) {
    if (DO_PREFIX.test(masked.slice(0, r.start))) {
      codeSpans(sql.slice(r.contentStart, r.contentEnd), base + r.contentStart, depth + 1, out);
    }
  }
  return out;
}
```
Nested tags are handled by construction: `DO $a$ x := $b$inner$b$; $a$` recurses into the `$a$` body, whose own `scanSql` sees `$b$…$b$` as a literal (measured `false` for a Vault string inside it). The depth cap is the give-up point — make it throw, and let `run()`'s existing throw→`measure-fail` mapping (`run.mjs:429-441`) carry it, since no real command nests two deep.

`[ASSUMED]` A1: `DO LANGUAGE plpgsql $$…$$` and `DO $$…$$ LANGUAGE plpgsql` are both valid; the prefix regex handles the first, and the second needs no handling (suffix irrelevant). Not exercised by any real command (all four use bare `DO $tag$`).

## Q3 — Length-testing a DERIVED value

**Smallest honest implementation (prototyped, measured):** walk the VALUE expression on `masked` from just after `'Name',` to the next depth-0 `,` or `)`; sum the lengths of literal contents that are DIRECT operands — at depth 0, or inside parentheses whose callee is on a short allowlist of string builders; count each `chr(` as 1; never descend into `(SELECT` or into a non-allowlisted function.

```js
// Source: session prototype; results below
const BUILDERS = /(?:concat|concat_ws|format|chr|decode|encode|convert_from|quote_literal|lower|upper|replace|reverse|translate|btrim|trim|substr|substring|left|right|repeat|lpad|rpad|regexp_replace|split_part|to_hex)\s*$/i;
```
- literal length = content read off `sql` between the quote delimiters `masked` marks, with `''` collapsed (over-counts `U&'\0073…'` escapes 6:1 and `E'\x..'` 4:1 — conservative, the right direction).
- `decode('…','base64')` — do not bother with ×3/4: the base64 literal is at least as long as its payload; summing it raw is conservative.

That is D4's forbidden outcome. The subselect skip is what makes it 7. Write the fixture for this exact shape as a GREEN control in the derived-length scenario, not just in `hygiene-green.json`.

**Where it must give up, and what it does then:**

1. **Unbalanced parentheses in a header region.** Today `headerRegions` silently uses `text.length` as the close when `matchingParen` returns −1 `[VERIFIED: cron-drift.mjs:279,:287]` — a silent WIDENING, not a failure. Replace with a violation under a new rule id `header-unparseable`.

## Q4 — "Long literal ANYWHERE": false-positive surface on the 14 real commands

**Ran it. The rule as stated is unacceptable; a token-level narrowing measures to zero.**

```

```
(`D` column = contains a digit: NONE of them does.)

Rule `long-token-anywhere` (id proposal): a whitespace-delimited token inside any literal (in any code span, excluding `DO` bodies which are code) with **length ≥ 32 AND at least one digit AND not matching a bare URL** `^https?:\/\/[A-Za-z0-9.-]+(?::\d+)?(?:\/[A-Za-z0-9._~\/-]*)?$` (a URL carrying `?`, `#` or `user:pw@` is NOT exempt).
- Real corpus: **0 FP** (the two 32/34-char tokens have no digit; the URL is bare).
- Bypass (h) `k := 'sk_live_…'` → token ≥ 32 → fires (measured 32 with a digit-free synthetic; **write the fixtures with digits**, e.g. `FAKE0123456789…`, because the digit test is part of the rule).
- Bypass (i) JSON `'{"X-Service-Key":"…"}'` → the whole JSON is one token (52) → fires; a JSON with spaces still yields the key as a ≥ 32 token.
- `hygiene-red` rows: `jwt-shape` row also trips it (64) and `long-literal-in-headers` (37) — so those two red rows would fire TWO rules and break the one-rule isolation assertion. Either exempt tokens already claimed by `jwt-shape` (`eyJ` prefix) and let `long-literal-in-headers` subsume (it is the same test scoped to a header region — consider MERGING: `long-literal-in-headers` becomes "long-token-anywhere fired inside a header region" with the higher 32 threshold already shared), or shorten those two rows' payloads below 32 chars. Recommend the merge: one rule, one threshold, header-region scope becomes the DETAIL not a separate id. ⚠️ Removing a rule id changes `HYGIENE_RULE_IDS` and the red fixture set; that is allowed (the scenario asserts set equality, not a count).

**Deviation from CONTEXT to record:** CONTEXT says the Vault-read shape is the rule's only exemption. Measured, the real corpus needs the token+digit+bare-URL narrowing regardless of Vault (none of the five FP jobs reads Vault). The Vault exemption is still correct to keep for the `match_engine_cron` job's own URL literal if 164.5.1 ever inlines a query-string URL — but it is not what makes the rule usable. `[ASSUMED]` A2: real analytics keys and JWTs contain digits (every credential shape this repo has recorded — `sk_live_`-style, `eyJ…` JWTs, hex — does; a pure-alphabetic 32+ key would evade). **Resolution algorithm (recommend, prototyped):**
1. On each code span's `masked`, collect calls `(?:\b(schema)\.)?\b(name)\s*\(` — masked text so a call inside a comment or literal is not a call.
2. Drop schema-qualified `vault.`, `net.`, `cron.`, `pg_catalog.` names and known builtins by the simple rule "resolve only names that have a snapshot file"; strip `public.`.

If none matches, recurse into the calls found in that body (visited set, depth cap 5). Overloads: one file per name; test every def in it; any reader counts.
4. **Unknown name / missing file / missing directory → NOT a Vault reader → `vault-absent` fires**, with a sentence naming the unresolved callable. Fail closed. That is the direction that cannot silently un-block or re-block 164.5.1: 164.5.1's command resolves today (measured), and if someone deletes the Vault read from the tick and regenerates the snapshot, the rule starts firing — correct.
5. Inject the resolver: `hygieneViolations(jobname, command, { resolveCallable = defaultFsResolver } = {})`. The self-test tri-state scenario (accept tick-call / reject comment-only / reject literal-only / reject unresolvable name) then runs against a fixture snapshot under `fixtures/cron-drift/functions/`, not the real one — otherwise a 164.8.6 edit to the tick could flip a 164.8.5 scenario. Keep ONE additional scenario that resolves against the REAL snapshot with the REAL 164.5.1 command string, so the collision with `[164.7-VAULT-ABSENT-RULE]` is measured every run.

**Recursion problem?** Trivial today (0 edges). The bounded DFS costs nothing and is what stops a future `SELECT public.hourly_tick()` → `match_engine_cron_tick()` wrapper from re-opening the collision.
