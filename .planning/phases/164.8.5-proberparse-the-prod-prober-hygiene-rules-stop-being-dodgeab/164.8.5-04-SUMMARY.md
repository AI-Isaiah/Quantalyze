## ⭐ THE ADJUDICATION — the question the brief asked, answered from measurement

**The question.** Plan 04's `must_haves` demand `others=[]` ("no row disables more than one
control; a row whose RED could be attributed to two controls is split before it is run"). Wave 3
declined that standard for its lexer neuters and substituted **pairwise-distinct failure
fingerprints at message granularity**, arguing that a lexer is read by every rule, so one control
legitimately reddens several scenarios, and that forcing `others=[]` would mean weakening scenarios
until they stopped noticing things.

**The verdict, in one line: wave 3's argument is SOUND but its substitute is INCOMPLETE, and the
`must_haves` wording is what is actually wrong.** Neither criterion subsumes the other. Both are
required, plus a third thing that is not an output criterion at all.

### Finding 1 — `others=[]` would NOT have caught wave 3's own Deviation 6. MEASURED.

Wave 3's Deviation 6 found the two `pg-password` arms producing byte-identical failure output. I
reconstructed the pre-Deviation-6 tree by reverting that single edit (`missed.push(\`${row.rule}
(${row.jobname})\`)` → `missed.push(row.rule)`) and re-ran matrix rows 8 and 9. Harness:
`scratchpad/mirror.mjs`, restored with `cp` + `cmp`.

```
ROW 8: exit=1 observers=["hygiene RED: every rule fires on its own fixture row, …"]
   RED  every red row fires the rule it names (pg-password)
ROW 9: exit=1 observers=["hygiene RED: every rule fires on its own fixture row, …"]
   RED  every red row fires the rule it names (pg-password)

  row 8  others=[] missing=[]  => PASSES
  row 9  others=[] missing=[]  => PASSES
  fingerprints IDENTICAL       : true => fingerprint criterion CATCHES it
```

Two genuinely different controls. **`others=[]` passes both.** It operates on the SET OF FAILING
OBSERVERS, and both rows fail exactly one observer — the same one. It is blind to the fact that the
evidence is the same sentence, because it never looks at the sentence.

This is not an isolated pair. My own matrix, at its clean end state, records **four** pairs of rows
with byte-identical observer sets while every row has `others=[]`:

```
  declared-set exact match (others=[] AND missing=[]): 12/12
  MESSAGE-granularity fingerprint clashes: 0 []
  OBSERVER-SET-granularity clashes (what others=[] can see): 4 [[1,2],[3,5],[7,11],[8,9]]
```

**A third of the rows are pairwise indistinguishable at the granularity `others=[]` works at.** So
wave 3 did not merely substitute a different criterion — it substituted one that catches a class
`others=[]` structurally cannot see, and it earned its keep by finding a real defect on the first
run. That much of wave 3's judgement is vindicated.

### Finding 2 — fingerprint-distinctness does NOT catch a silently-lost observer. MEASURED.

The brief asked me to construct a case where fingerprints miss what `others=[]` catches. Here it
is, run rather than argued (`scratchpad/counterexample.mjs`, byte backups, `cmp`-restored):

Take row 3 (the per-depth-0-argument derived sum on `long-literal-in-headers`). It has two live
observers: scenario 38 (bypass row (j)) and scenario 48 (red row `fixture_nonanchored_split_job`).
Delete that one red row — the kind of thing a fixture edit does by accident.

```
step 1 — dropped fixture_nonanchored_split_job: 22 rows -> 21
step 2 — self-test WITHOUT that red row: exit=0 failures=0
   ✅ GREEN — the red fixture silently lost a row and the whole self-test still passes.

step 3 — row 3 neutered on the DEGRADED corpus: exit=1
   RED [hygiene BYPASS: every enumerated shape fires at least one NAMED rule, …]
       every MEASURED bypass shape now fires at least one rule ((j) ||-split value under a
       header name outside the three anchored ones)

  row is RED                                        : true
  wave 3 — fingerprint distinct from every other row: true  => PASSES
  declared-set — missing=["hygiene RED: every rule fires on its own fixture row, …"] others=[]
                                                    => FAILS (names the lost observer)
```

The row is still RED. Its fingerprint is still unlike every other row's. **Wave 3's criterion passes
it.** And yet the red fixture — the artefact every future reader will treat as "this rule is
covered" — has stopped watching this control, and nothing said so. Only a **declared** expectation
can catch this, because fingerprints are compared row-to-row and never against a belief about which
observer watches which control.

This is the direction that matters most for a phase whose whole subject is controls that cannot
fail: it is exactly how coverage rots without a red run.

### The standard this phase should hold, and why it is three things

| # | property | what it catches | what it CANNOT catch |
|---|---|---|---|
| 1 | **one control per EDIT** — single replacement, anchor unique, file must change (exit 2 otherwise) | a batch neuter, i.e. D3's forbidden shape | nothing about the output |
| 2 | **DECLARED expected failing set, matched exactly (`others=[]` AND `missing=[]`)** | a lost or wrong observer (Finding 2) | two controls with identical evidence (Finding 1) |
| 3 | **pairwise-distinct fingerprints at MESSAGE granularity** | two controls whose failures are indistinguishable (Finding 1) | a lost observer (Finding 2) |

⛔ **Property 1 is the one that actually prevents a batch neuter, and it is a HARNESS INVARIANT, not
an output criterion.** Both 2 and 3 only detect a batch neuter's symptoms. The reverted repair that
started this phase disabled two comparisons in ONE edit; property 1 is what makes that impossible,
and neither wave 3's criterion nor plan 04's `must_haves` is the thing doing that work.

⛔ **`others=[]` is attainable here and wave 3 was wrong that it would cost scenario strength — but
only once "expected" is a DECLARED SET rather than a singleton.** My matrix hits **12/12** exact
declared-set matches with no scenario weakened, no fixture trimmed and no assertion removed. Rows 1
and 2 legitimately redden three observers each; declaring all three is not a weakening, it is
writing down what a shared lexer dependency actually implies. Wave 3 read `others=[]` as
"exactly ONE observer" — waves 1 and 2's singleton spelling — and correctly concluded that was
unattainable. The right response was to generalise the expectation, not to drop it.

**So: plan 04's `must_haves` wording should be AMENDED, not quietly ignored.** Its first clause
("no row disables more than one control") is property 1 and is right. Its second ("a row whose RED
could be attributed to two controls is split before it is run") is wrong for a shared dependency and
should read: *a row DECLARES the observers it expects to redden, and the run must match that set
exactly; two rows may share observers but must not share a fingerprint.* Recording it here rather
than editing the plan mid-wave.
