## Critical Issues

### CR-01: `normalizeCommand` collapses newlines into `--` comments — it blinds the manifest-side hygiene scan on a real committed row, and makes the published oracle a no-op that hashes clean

**File:** `scripts/prod-prober/arms/cron-drift.mjs:201-206` (definition); consumed at
`scripts/prod-prober/run.mjs:3333` (capture stores the normalized text), `cron-drift.mjs:1362`
(section (2) hygiene reads it), `cron-drift.mjs:1462-1463` (sha comparison), `cron-drift.mjs:1495-1496`
(the printed diff).

**Issue.** `normalizeCommand` does `.replace(/\s+/g, " ")`, which collapses **newlines**. A `--`
line comment is terminated by a newline; after the collapse it runs to end-of-text. Three consequences,
all measured at HEAD:

1. **The committed oracle carries a 100 %-masked row.** `captureManifest` stores
   `normalizeCommand(r.command)`. Measured over `scripts/prod-prober/cron-manifest.json`: 0 of 14
   commands retain a newline, and `retention_compute_jobs_orphaned_running` (1791 chars, leading
   `-- CANARY_162_V1_PROSE_ONLY …` prose block) masks to **100 % spaces**. Injecting a real inline
   credential into that row's `DO $sweep$` body yields `[]`; the same text with its newlines restored
   yields `[x-service-key-literal, long-literal-in-headers]`. Section (2) — the scan whose stated
   purpose is that "a PROD command that matches the manifest byte for byte and still carries an
   inline key is STILL a defect" — cannot fail for that row.
2. **The `hygieneViolations` docstring's claim is false.** `cron-drift.mjs:758-760` states
   *"normalization does not change any of these judgements"*. Measured: it changes them from two
   violations to zero.
3. **⛔ The drift detector conflates a working command with a no-op, and the remedy instructs the
   operator to install the no-op.** Measured:
   `"-- housekeeping\nDO $s$ … $s$;"` and `"-- housekeeping DO $s$ … $s$;"` normalize to the same
   string and therefore to sha `5deac64b2c2ef319` **both**. The first runs; the second is one comment
   line and does nothing. `REMEDIES["cron-drift"]` says *"re-schedule PROD from the manifest"* — doing
   that with the published single-line text for `retention_compute_jobs_orphaned_running` silently
   stops the orphaned-`compute_jobs` reaper, and `compareManifest` reports **no drift**, because the
   shas agree.

**Failure scenario (concrete).** Operator sees a `cron-drift` defect on
`retention_compute_jobs_orphaned_running`, follows the printed remedy, `cron.schedule`s the manifest's
`command` verbatim. The job is now `-- CANARY… DO $sweep$ … $sweep$;` on one line = a comment.
`compute_jobs` rows stuck in `running` are never reaped. The next hourly prober run computes
`sha256(normalizeCommand(prodCommand))`, gets the identical digest, and prints
`0 differing`.

**Fix.** Make the normalization newline-preserving and bump the version so every committed sha is
re-derived rather than silently reinterpreted — the `NORMALIZATION` constant exists for exactly this:

```js
export const NORMALIZATION = "ws-collapse-v2"; // bumped: v1 collapsed newlines into `--` comments

/** CRLF → LF, trim, every run of HORIZONTAL whitespace → one space. Newlines are
 *  PRESERVED, because a `--` comment is terminated by one: collapsing them makes a
 *  working command and a no-op hash identically (measured 2026-09-11). */
export function normalizeCommand(text) {
  return String(text ?? "")
    .replace(/\r\n/g, "\n")
    .trim()
    .replace(/[^\S\n]+/g, " ")
    .replace(/\n{2,}/g, "\n");
}
```

Then re-capture `cron-manifest.json` (the shas all move, by design), and add an anti-vacuity arm to
the false-positive-budget scenario (see WR-04) so a future 100 %-masked row cannot pass as clean.

### CR-02: `parseCronJobRows` accepts a record with MORE than seven fields and silently truncates the command — the mirror image of the `<7` defect this phase fixed

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1079-1091`

**Issue.** The guard is `if (f.length < 7)`. A `cron.job.command` containing a **field** separator
(``) — legal via `E'\x1f'` or a pasted control byte, exactly the hazard
`CRON_JOB_SEPARATORS`' own corrected docstring at :173-178 admits for `` — splits the record
into 8+ fields. That passes the guard, `command: f[6]` keeps only the text **up to** the separator,
and `malformed` stays empty, so neither `run()` (`:1591`) nor `captureManifest`
(`run.mjs:3299`) raises anything.

**Failure scenario — CONFIRMED by execution.** A row whose real command is
`SELECT 1;<US>SELECT net.http_post(… 'X-Service-Key','FAKE-abcdef0123456789abcdef0123456789'…)`:

```
malformed: []
rows: 1
command captured: "SELECT 1;"
hygiene on PARSED row:  [ '[vault-absent]' ]
hygiene on TRUE command:[ '[x-service-key-literal]', '[long-literal-in-headers]', '[vault-absent]' ]
```

The credential is invisible to every rule, and because `captureManifest` hashes the **same truncated
text**, an oracle captured through this path agrees with PROD forever — no drift, no hygiene finding,
no measure-fail. The docstring at `:1054-1062` says *"A ROW THE PARSER COULD NOT READ IS NOT A ROW
THAT IS NOT THERE"*; that principle is implemented in one direction only.

**Fix.** The field count is exact, not a minimum:

```js
    // Seven columns are SELECTed. Fewer means a record separator split one row into
    // two; MORE means a FIELD separator split one command — and `f[6]` would then be
    // a TRUNCATED command that every hygiene rule would judge as if it were whole.
    if (f.length !== 7) {
      malformed.push({ index, fields: f.length });
      continue;
    }
```

Both callers already refuse on a non-empty `malformed`, so no other change is needed. Add a red
fixture with an 8-field record beside `prod-malformed-record.json` so the new arm is individually
falsifiable (D3).

### CR-03: the single-quoted `DO '…'` procedural body is never re-entered — a complete hygiene bypass, the 10th member of the family this phase exists to close

**File:** `scripts/prod-prober/arms/cron-drift.mjs:335-349` (`codeSpans`), `:420-438` (`literalsIn`),
`:308` (`DO_PREFIX`)

**Issue.** `codeSpans` recurses only over `scanSql`'s `dollarRegions`, so only `DO $tag$ … $tag$` is
re-entered as code. PostgreSQL's `DO` takes **a string literal** — dollar-quoting is merely
*recommended* — so `DO 'BEGIN … END'` is a valid cron command. `scanSql` blanks that literal's
contents; `literalsIn` then skips it as well (the `DO_PREFIX` test at `:431` fires on the single
quote too), so the body is invisible to `long-token-anywhere`, to all three header-anchored rules, to
`long-literal-in-headers`, to `header-unparseable`, and to `vault-absent`'s masked shape and callee
resolution.

**Failure scenario — CONFIRMED by execution** (`hygieneViolations("audit_log_hot_to_cold", …)`):

```
DO $$ ... $$        -> [ 'x-service-key-literal', 'long-literal-in-headers' ]
DO '...'            -> []          ← spans = 1, never re-entered
DO '...' LANGUAGE   -> []
```

Both commands post the identical 37-character `X-Service-Key` credential. The dollar-quoted spelling
is caught; the single-quoted spelling trips **nothing** — not even `long-token-anywhere`, whose whole
purpose per `:846-856` is to catch the key when it is "somewhere else entirely".

**Fix.** Re-enter a single-quoted `DO` body the same way, undoubling its quotes, and give it its own
red fixture row so the arm is individually neuterable:

```js
  // A `DO` body may be ANY string literal — PostgreSQL only *recommends* dollar
  // quoting. `DO 'BEGIN … END'` is code, not data, exactly as `DO $$…$$` is.
  for (const lit of singleQuotedLiteralsIn({ masked, sql, dollarRegions })) {
    if (!DO_PREFIX.test(masked.slice(0, lit.start))) continue;
    // content already has `''` undoubled by literalAt; offsets into the original
    // are approximate for a body carrying doubled quotes, so report at `base`.
    codeSpans(lit.content, base + lit.start + 1, depth + 1, out);
  }
```

and mirror the same predicate in `literalsIn` so the body is not double-counted as one giant literal.

### CR-04: `BARE_URL_RE` exempts a credential carried in a URL **path** segment — the most common webhook-token shape

**File:** `scripts/prod-prober/arms/cron-drift.mjs:298` (pattern), consumed at `:892`

**Issue.** The pattern's path class is `(?:\/[A-Za-z0-9._~/-]*)?`, which matches an arbitrarily long
opaque token. The docstring at `:291-297` reasons carefully that `?`, `#` and `user:pw@` are absent
"so a 'URL' carrying a token in its query string … is NOT exempt" — it never considers the path, and
`https://hooks.slack.com/services/T00/B00/<token>`-style secrets are precisely path-borne.

**Failure scenario — CONFIRMED by execution:**

```
BARE_URL_RE.test("https://hooks.x.invalid/ingest/FAKE-abcdef0123456789abcdef0123456789") -> true
  cron command with the token in the URL PATH  -> []
  cron command with the token in the QUERY     -> [ 'long-token-anywhere' ]
```

A production cron command posting to a path-token webhook reports **zero** hygiene violations, and
`captureManifest` will happily commit it into the public oracle.

**Fix.** Exempt the *shape* the corpus actually needs — a URL whose path segments are all short —
rather than any path whatever. The committed 79-character analytics URL's longest segment is
`cron-recompute`; `TOKEN_MIN` is the existing yardstick for "long enough to be a credential":

```js
/** A bare URL, WITH NO OPAQUE SEGMENT. A path segment of TOKEN_MIN+ characters is a
 *  credential wearing a path's clothing — measured: hooks.x/ingest/<37-char key> was
 *  exempt under the old pattern. `?`, `#` and `user:pw@` stay absent, as before. */
export const BARE_URL_RE = /^https?:\/\/[A-Za-z0-9.-]+(?::\d+)?(?:\/[A-Za-z0-9._~-]*)*$/;
export const isBareUrl = (t) =>
  BARE_URL_RE.test(t) && t.split("/").slice(3).every((seg) => seg.length < TOKEN_MIN);
```

Re-run the false-positive-budget scenario against the committed manifest to confirm the 79-character
URL still passes (it does under the segment test), and add the path-token shape as a red row in
`hygiene-bypass.json` with `expect_any_of: ["long-token-anywhere"]`.

### WR-05: `DETECT_RE` misses a comment placed **after** the opening paren, and both the docstring and the test title claim a completeness they do not measure
