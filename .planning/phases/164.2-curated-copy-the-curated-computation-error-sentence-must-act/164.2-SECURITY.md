## The HIGH threat — T-164.2-13, SECURITY DEFINER bridge

`sync_strategy_analytics_status` is `CREATE OR REPLACE`d by a migration that
**auto-applies to PRODUCTION on merge to main**. Verified on four counts:

1. **REVOKE grantee set is byte-identical** to the definition it re-bases on —
   new `:1064` `REVOKE ALL ON FUNCTION sync_strategy_analytics_status FROM PUBLIC, anon, authenticated;`
   vs prior `20260826120000:909`.
2. **`search_path` pinned** — `:396` `SET search_path = public, pg_catalog`.
3. **Zero `GRANT` statements in the whole 1716-line file** (`grep -nE '^\s*GRANT\b'` → no match).
4. **The new trigger function is SECURITY INVOKER**, pinned path, REVOKEd
   (`:1108-1111`, `:1146`), assigns only the two marker columns to NULL.

Function-body diff vs the prior definition shows only the six declared provenance
deltas plus an `id DESC` tiebreak — **no guard, scope or ownership predicate removed.**

**Anti-vacuity — three lane mutants, each bit its own arm:**

| Mutation | Observed |
|---|---|
| REVOKE → `GRANT EXECUTE … TO authenticated` | `ERROR: P0001: Criterion 2 re-base failed: role authenticated can EXECUTE sync_strategy_analytics_status` |
| trigger fn → `SECURITY DEFINER` | `ERROR: P0001: … strategy_analytics_drop_stale_error_provenance is SECURITY DEFINER` |
| `SET search_path` deleted | `ERROR: P0001: … lost its pinned search_path in the re-base` |

Pristine tree ⇒ exit 0. ⭐ These assertions run at **apply time**, so a weakened ACL
**aborts the production deploy** rather than shipping silently.

## Open non-blocking

**F-164.2-A — the two success/reset writers are outside the PGRST204 degrade.**
Severity: low-medium (below `block_on: high`, so it does not gate the ship).
Surfaced by measurement outside the declared register; it narrows T-164.2-17's claim.

`analytics_runner.py:1929-1930` and `job_worker.py:7918-7919` send the two marker
keys as explicit `None` in a **success** payload via a bare
`supabase.table("strategy_analytics").upsert(...)`, with no `upsert_or_drop_provenance`
wrapper. The nine *failure* stamp sites all carry it. So the migration header's claim
that "the Python half carries its own minimal-key fallback" is **true for failures only**.

Consequence in a worker-ahead window: PostgREST answers `PGRST204` naming
`computation_error_source` on the SUCCESS write, the CSV catch-all runs
`_mark_unrecoverable`, and the row lands `computation_status='failed'` with
"CSV analytics computation failed." **over a computation that succeeded** — burning a
retry attempt against `max_attempts 3`.

Window realism, measured: `supabase-migrate.yml` fires on `push: branches:[main]`
(paths `supabase/migrations/**`) and normally lands minutes before the Railway deploy,
which waits on main CI. BUT the apply is one transaction under `SET lock_timeout='5s'`;
a lock wait aborts it, the workflow goes red, **nothing gates Railway on that**, and the
worker runs ahead until a manual `workflow_dispatch` re-run.

⚠️ Precedent: the pre-existing `"computing_started_at": None` key in the same payloads
already carries this identical exposure — the design has accepted it once. That is why
this is non-blocking, not why it is acceptable.

**Disposition: FIXED in this phase before merge** (route both reset writers through
`upsert_or_drop_provenance`). See the audit trail entry below.

## Observations (none blocking)

1. **`164.2-02-SUMMARY.md` has no `## Threat Flags` section** — the only one of ten
   missing it. T-164.2-03 and T-164.2-04 were verified independently, so this is a
   disclosure-hygiene gap, not a coverage gap.
2. **Lock surface not named by T-164.2-14's accept.** The migration runs two
   `ALTER TABLE … ADD CONSTRAINT … CHECK` **without `NOT VALID`** (`:316-318`, `:348-350`)
   plus a `CREATE TRIGGER` (`:1149`). Each takes `ACCESS EXCLUSIVE` on
   `public.strategy_analytics` and the two CHECKs perform a validating scan at apply.
   Both columns are all-NULL and the table is one row per strategy, so exposure is brief —
   but it is availability surface the accept does not name. **The register should say so;
   the migration should not change.**
3. **T-164.2-15 pin timing.** The plan says floors are pinned "in the same commit" as the
   measured run. On this branch the gate file landed in `19d9de8f` and the floor raise in
   `39cc7ae4` — same phase, different commits. No ship risk (both precede merge).
4. **Pre-existing, explicitly outside the T-164.2-09 delta:**
   `validate-and-encrypt/route.ts:858` still forwards `error: err.message` verbatim on the
   4xx-forward arm. That is the F5a contract this phase deliberately left byte-unchanged,
   and it is the channel a bare upstream 401's message rides to the browser. Noted for the
   register, not a phase regression.
