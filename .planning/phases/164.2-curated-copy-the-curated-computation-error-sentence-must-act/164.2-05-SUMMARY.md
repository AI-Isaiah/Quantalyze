## ⭐ The finding the plan warned about, and what it changed

The plan said the roster row *"is a coupling guard, not a copy guard — omitting it does NOT render UNKNOWN"* and told me to check per route rather than copy a neighbour's sentence. Checking changed three comments and one assertion:

| Roster | Recogniser at the call site | What the row buys | Proven by |
|---|---|---|---|
| `KNOWN_ADD_KEY_CODES` | `recogniseSeamErrorCode(seamErrorCode(data))` **first**, then membership | **COUPLING.** The wire table self-maps `RATE_LIMITED`, so the hop answers and the row cannot change what renders. | Neuter 1: invariant + both oracles red, `MultiKeyConnectStep.test.tsx` stays **GREEN** |
| `KNOWN_SET_MEMBERS_CODES` | **no translate step at all** — `data.code && KNOWN_SET_MEMBERS_CODES.has(...)` → `"UNKNOWN"` | ⭐ **COPY.** Omit it and a real throttle renders the generic card. | Neuter 1b: the rendered envelope reads `data-error-code="UNKNOWN"` |
| `KNOWN_VALIDATE_AND_ENCRYPT_CODES` | none — no consumer reads the `code` field | **VOCABULARY only** ("typed, and has copy"). | Neuter 2: only the invariant reds |

And a second correction the plan did not anticipate: **`KEY_RATE_LIMIT` does not "stay because the classifier returns it" on all three.** That is true only on `add-key`. On `KNOWN_SET_MEMBERS_CODES` the code is now reachable from **no emitter at all**, and on `KNOWN_VALIDATE_AND_ENCRYPT_CODES` it was **never listed** even while the route emitted it — a pre-existing hole, invisible because the 4th `ROUTES` row's scanner cannot see a code that rides `rateLimitDenyJson`. Both facts are written at the rosters and hand-typed per route in the invariant (`keepsKeyRateLimit`), so a future author cannot copy one route's answer onto another.

## Decisions Made

1. **One commit for both tasks** — see the note under Task Commits.
2. **The map is NOT exported from `route.ts`.** The plan offered "export it and import it from the invariant test — exporting is fine, it is a constant". A Next.js `route.ts` has a constrained export surface (handlers plus the route-config keys), and adding a data export to it risks a build-time route-type error for a test's convenience. The invariant SOURCE-SCANS it instead, with its own self-test — the idiom that file already uses for the union, the rosters and the alias table.
3. **400 is deliberately absent from the map.** A bare 400 from the validator is a verdict about the USER's key whose sentence we did not receive, and `VALIDATION_FAILED`'s copy ("The fault is in our software, not in your key or your data") would be false for it. Written into the map's docblock so the next author does not "complete" the table.
4. **`rosterFloor` stays 4 while the roster went 6 → 7.** Its docblock states its job — catch a roster that parsed as `[]`, 1 or 2 — and says explicitly that it must not re-pin the roster's size. A floor that tracks membership becomes a second, weaker size pin.
5. **`KEY_RATE_LIMIT` is kept on `KNOWN_SET_MEMBERS_CODES` despite being unreachable.** Removing it is a rendering change (deploy skew would move a stale sentence to the UNKNOWN card) that this plan did not measure, and the plan's own `<fails_when>` names its removal as a failure. Annotated unreachable-by-design at the roster and hand-typed in the invariant, with the removal recorded as owed below.
6. **`set-members` keeps its older bare-`NextResponse.json` deny shape** (the plan says so, Rule 3 agrees). Its one live consequence — being the only one of the four visible to `emitterRe` at 429 — is now an assertion rather than a fact nobody wrote down.
