## Summary

Reviewed in the priority order the brief set: the ten Python provenance writers and their integration with the `BEFORE UPDATE` trigger and the conditional bridge; the four rewired API routes and the two minted codes; the cross-file roster/copy integration; the anti-vacuity of the new and inverted tests; then the rest of the diff. The migration itself was not re-litigated — only how the TypeScript and Python surfaces meet it.

**What holds up, measured rather than taken from the SUMMARIES:**

- All ten stamped literals derive both markers from ONE expression (`provenance_source(X)` beside `"computation_error_job_id": X`, with X byte-identical at every site — `job.get("id")` at P1–P5, `job_id` at P6–P10). A half-stamp is not expressible; the pairing CHECK cannot fire from application code. Verified by reading every site, not the census.
- `upsert_or_drop_provenance` cannot swallow a real error: non-23514 `APIError` re-raises untouched (which keeps P10's `PGRST204` arm reachable), a 23514 on a marker-free payload re-raises, and the single re-issue's own exception propagates. Every `_write_*` closure references its payload dict by name at call time, so the popped dict is what gets re-sent.
- No writer trips the trigger unintentionally. The runner's four failure arms (`_mark_failed`, `_mark_truncated`, `_mark_config_failed`, `_mark_unrecoverable`) are mutually exclusive (`except HTTPException: raise` guards the catch-all; the truncated/config arms re-raise typed exceptions). The derive and composite D-15 `_upsert_error_only` arms return before their `_upsert` siblings. The documented blind spot — same job id, different sentence — is the ONLY mechanism, and it is reachable in exactly one sequence (IN-01).
- There are no `.update()` writers of `computation_error` on `strategy_analytics` in `analytics-service/` — every writer is an `upsert(<literal>)`, so the AST census's scan surface is the whole class.
- Routes: no route under `src/app/api` emits the `"KEY_RATE_LIMIT"` literal; every 429 body is `RATE_LIMITED`; status codes match the copy's `actions` (`PRESELECT_REQUEST_INVALID` 400 with no recoverable action; `DRAFT_SESSION_COLLISION` 409 with no Retry; `RATE_LIMITED` 429 with `clear_and_retry` + `Retry-After`). The post-23505 read is tenant-scoped, source-pinned, selects `api_key_id` alone, never reaches the wire, and a dark read falls to the weaker claim. The `??` chain reads `err.seamCode` first.
- Cross-file: both minted codes are union members with copy, rostered on `ConnectKeyStep`, in `EXPECTED_409_CODES` / `EXPECTED_SPLIT_CODES`, and rendered by the 82-row sweep on their real surface. No surface gained a code it cannot render; no surface lost a code it still emits.
- Security: no new endpoint, no key id on the wire, breadcrumb data goes through `scrubRecord`, `sentry-capture.ts` still has exactly one import. Clean.
- Anti-vacuity: the seven mechanisms the SUMMARIES record as fixed are fixed. Looked specifically for survivors — an assertion satisfiable by any value, a neuter proving one arm of many, a law holding by coincidence, an arm made unfalsifiable by a fix elsewhere. Found one residual (IN-04): the routing of nine of ten sites through the retry helper is not pinned by any test.

**What does not hold up:** one stamp is inert and its SUMMARY claim is false (WR-01); the deploy-window mitigation covers one of ten sites where a two-line extension of the helper would cover all ten (WR-02); the helper's 23514 arm attributes any CHECK on the table to the markers (WR-03).

### WR-01: P1's provenance stamp is inert — `mark_compute_job_done` runs branch (c) one RPC later and erases the sentence, the status and the markers

**File:** `analytics-service/services/job_worker.py:2098-2149` (the `_mark_analytics_failed` payload at 2098, its comment at 2110-2117, the `DispatchOutcome.DONE` return at 2147); `analytics-service/main_worker.py:929-934`
**Issue:** `run_sync_trades_job` writes `computation_status = 'failed'` plus the curated "Analytics enqueue failed during sync…" sentence, now stamped `(writer, <sync_trades job id>)`, and then returns `DispatchOutcome.DONE` because the trades persisted. `main_worker.py:929` maps DONE to the `mark_compute_job_done` RPC, which ends in `PERFORM sync_strategy_analytics_status`. With the sync job done and no analytics job enqueued (that is the failure being recorded), every job for the strategy is terminal-done, `live_failures` is empty, and branch (c) writes `computation_status = 'complete'`, `computation_error = NULL`, both markers NULL, `computed_at = now()`. The provenance is cleared by (c)'s own unconditional clear; the markers never reach a write branch that consults them.

Failure scenario: wizard onboarding, `enqueue_compute_job` fails after a successful trade sync → the user's row reads `complete` with no analytics and no sentence, `computed_at` fresh. The comment at :2110-2117 ("this sentence tells the user the sync SUCCEEDED and only the analytics enqueue failed … losing it misattributes the failure — the class this phase exists to close") and plan 08's SUMMARY ("Every Python strategy_analytics failure literal … carries [markers]" as criterion 2 closed) both claim a protection that does not exist on this path. The erasure is pre-existing (it is exactly the class the 161.1 F1 comment at `job_worker.py:5082-5100` names and fixes for the derive path by returning FAILED instead of DONE), so this is not a regression — but this phase added code and prose asserting the opposite, and the census now reports P1 as a stamped, protected writer.

**Fix:** Apply the F1 remedy already used at `:5082`: on the enqueue-failure path return `DispatchResult(outcome=DispatchOutcome.FAILED, error_message=..., error_kind="permanent")` so the bridge takes branch (b) with `v_latest_job_id = <this job>`, the markers match, and the P1 sentence survives — which is the only way the stamp written at :2098 can ever be read. If the founder wants sync_trades to stay DONE (the trades did persist), then the honest alternative is to delete the stamp and the comment at :2110-2117, reclassify P1 out of `EXPECTED_STAMPED_SITES` (10 → 9), and book the branch-(c) erasure as its own item. Either way, correct plan 08's SUMMARY "eleven writers" table so P1 is not listed as protected.

### WR-02: Nine of ten stamped writers have no `PGRST204` fallback for the deploy window, and the helper that would close it is one arm away

**File:** `analytics-service/services/strategy_analytics_provenance.py:101-155`; `analytics-service/services/analytics_runner.py:2185-2252` (the only site with a fallback)
**Issue:** The migration must reach PROD before a worker sends `computation_error_source` / `computation_error_job_id`, or PostgREST answers `PGRST204` and writes nothing. Plan 08 dispositioned this as T-164.2-17 "mitigate" and states the in-code mitigation "covers ONE arm only" — P10's `_mark_unrecoverable`. At P1–P9 a `PGRST204` propagates to the enclosing `except Exception → logger.warning` and the failure record is lost: the row stays at whatever `_mark_computing` or the bridge left it (`'computing'`) until the 16-hour reaper, and the wizard poller spins. The phase's safety argument is pipeline ordering (migrations auto-apply on merge; Railway deploys after main CI), which is plausible but not a property of the tree, and the phase adds TWO new columns to the very payload that records a failure.

`upsert_or_drop_provenance` already implements exactly the right degrade (drop both markers, re-issue once, log ERROR) and already sits at all ten sites. `PGRST204`'s message names the column (`Could not find the 'computation_error_source' column of 'strategy_analytics' in the schema cache`), so the helper can recognise the marker case without touching P10's arm: at P10 the re-issue still carries `computing_started_at`, and if that column is also unknown the second `PGRST204` propagates to the existing arm exactly as today.

**Fix:**
```python
_PGRST_SCHEMA_CACHE_MISS: Final[str] = "PGRST204"
_MARKER_COLUMNS = (PROVENANCE_SOURCE_KEY, PROVENANCE_JOB_ID_KEY)

def _refuses_a_marker(exc: APIError) -> bool:
    code = getattr(exc, "code", None)
    if code == _PG_CHECK_VIOLATION:
        return True
    if code == _PGRST_SCHEMA_CACHE_MISS:
        msg = str(exc.message or "")
        return any(col in msg for col in _MARKER_COLUMNS)
    return False

# in upsert_or_drop_provenance:
    except APIError as exc:
        if not _refuses_a_marker(exc):
            raise
        if all(k not in payload for k in _MARKER_COLUMNS):
            raise
        ...pop both, log ERROR naming exc.code, write() once...
```
Add a runtime case beside `test_marker_23514_still_records_the_failure` that injects `{"code": "PGRST204", "message": "Could not find the 'computation_error_source' column …"}` at a NON-P10 site (e.g. `_mark_failed` via the insufficient-history path) and asserts the failure record lands; and keep the existing P10 PGRST204 test proving the `computing_started_at` arm is still reached. Then T-164.2-17 is mitigated at all ten sites rather than one.

### WR-03: The 23514 arm blames the provenance markers for any CHECK violation on the table

**File:** `analytics-service/services/strategy_analytics_provenance.py:135-155`
**Issue:** The arm matches on SQLSTATE `23514` alone. `strategy_analytics` carries other CHECK constraints today and will gain more; any of them firing on a marker-bearing payload takes this branch: the markers are popped, an ERROR is logged saying "the database REFUSED the computation_error markers … (TODOS PROV-WRITER-23514)", and the write is re-issued once — which fails with the same 23514 and propagates (correct, nothing swallowed). The cost is one wasted round trip on the failure path and, more importantly, a misleading operator signal: the helper's own comment says the ERROR line "is the only place that bug becomes visible", and it now fires with the wrong diagnosis for every other constraint on the table. A future author reading logs will chase the marker pair while the real constraint (a status CHECK, say) is the one refusing.

**Fix:** Narrow the match to the two constraints this helper owns — their names appear in `exc.message` (`… violates check constraint "strategy_analytics_computation_error_source_check"` / `…_markers_together_check`):
```python
_MARKER_CONSTRAINT_FRAGMENT: Final[str] = "strategy_analytics_computation_error_"

if getattr(exc, "code", None) != _PG_CHECK_VIOLATION:
    raise
if _MARKER_CONSTRAINT_FRAGMENT not in str(exc.message or ""):
    raise  # a different CHECK on this table — not ours to strip provenance for
```
and add a negative-control test: a 23514 whose message names a different constraint on a marker-bearing payload must propagate with the payload untouched and NO error log. (`test_helper_reraises_a_23514_on_a_payload_with_no_markers` covers the marker-free half only.)
