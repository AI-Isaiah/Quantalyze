## Deploy notes

⛔ **ONE-DIRECTIONAL DEPLOY ORDER.** The migration `20260906120000_computation_error_provenance.sql` must be on PROD **before** any worker sends the two new keys. PostgREST answers a schema-cache miss on an unknown column with `PGRST204` and writes NOTHING, so a worker that runs ahead of the DDL fails its own failure-write.

What makes this safe in practice, and what does not:

- **Merging `supabase/migrations/**` to main AUTO-APPLIES to PROD**, and Railway deploys the analytics service only after main CI goes green — so on a single merge the DDL lands first and the worker second. That ordering is a property of the pipeline, not of this code.
- **The reverse order is safe by design**: with the migration applied and no writer stamping yet, every row has NULL markers and the bridge behaves exactly as it did before. That is why plan 06 shipped first.
- **The in-code mitigation covers ONE arm only.** P11's minimal-key re-issue catches `PGRST204` at `analytics_runner._mark_unrecoverable`, the catch-all exit. The other nine stamped writers have no such fallback: in the window they would raise, and their existing `except Exception → logger.warning` callers would swallow it, leaving the row where it was. That is T-164.2-17, dispositioned `mitigate`, and it is the reason the deploy order is stated as a constraint rather than a preference.
- **`upsert_or_drop_provenance` does NOT cover this window** and must not be mistaken for cover: it matches `23514` only. `PGRST204` propagates untouched — deliberately, because at P10 the enclosing handler owns it.
- **Plan 10 carries the post-merge PROD check.** Nothing in this plan was applied to PROD or to shared TEST; no database was touched at all (the whole suite runs against mocks).

## Decisions Made

1. **The two markers are derived from one expression, not typed independently.** See Deviations #1. This is the root-cause fix for a 23514 that would have fired on three of four callers.
2. **The census checks a shape, not a constant.** Rule A demands `provenance_source(<X>)` with `<X>` byte-identical (`ast.dump`) to the job-id value. Strictly stronger than the plan's `Constant('writer')`: it rejects statically what the constraint would otherwise reject at runtime, on the failure path.
3. **The retry helper takes the write as a callable.** A helper that performed the upsert would have hidden ten payloads from both AST censuses — the failure `_guard_failure_payload_inplace`'s docblock already records (its exempt count fell 1 → 0 and the gate went red). Four payloads did have to be bound to locals so the retry can pop keys out of them; that moved `EXPECTED_KEPT_VIA_N1` 7 → 11 and moved NOTHING kept → skipped.
4. **The P11 exempt key set is imported from the JOB-01 census, not re-typed.** Two hand-typed copies could drift into exempting different payloads — the D-10 lesson, applied again.
5. **`upsert_or_drop_provenance` re-raises a 23514 on a payload with no markers**, rather than swallowing it: that is a different constraint, and re-issuing an identical payload would be a no-op dressed as a recovery.
