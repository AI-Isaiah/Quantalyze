## Summary

This phase has two halves that share one thesis and nothing else. Half (a) is a schema + plpgsql + Python change: `strategy_analytics.computation_error` gains a provenance marker, `sync_strategy_analytics_status` becomes conditional on it, and every Python writer stamps it. Half (b) is six independent TSX/TS copy corrections (wizard refusals, the KeyPermissionBadge prefix, two freshness bucketers, the HONEST-08 sync-arm proof, the anonymous factsheet placeholder), each of which must ship with a test that has been observed RED with its subject neutered.

The measured state at HEAD differs from the briefing in five places the planner must not inherit: **(1)** the latest bridge definition is `20260826120000_computation_error_curated_copy.sql:336`, NOT `20260826140000` (that file only widens `compute_jobs_error_kind_check` and redefines `get_user_compute_jobs` — it never touches the bridge) `[VERIFIED: grep over supabase/migrations; 20260826140000:31-142 read]`; **(2)** `routers/portfolio.py:722-734` writes `portfolio_analytics.computation_error`, a different table with NO bridge (`20260826120000:240-241` says so in as many words), so it is not a writer criterion 1 can reach and stamping it is a no-op for the defect; **(3)** there are FOUR TypeScript writers of `strategy_analytics.computation_error` that CONTEXT does not list (`finalize-wizard/route.ts:2294`, `:2367`, `csv-finalize/route.ts:1928`, `keys/sync/route.ts:552`) and one further SQL writer, the stuck-computing reaper's cron command (`20260803130000:151`); **(4)** `RATE_LIMITED` already carries the honest our-limiter copy ("the cap is ours, not your exchange's", `wizardErrors.ts:3326-3335`), so the `KEY_RATE_LIMIT` source split does not need a new code — it needs the two `userActionLimiter` arms of `create-with-key` to emit the existing member and the roster to admit it; **(5)** an existing `SyncBadge` test (`SyncBadge.staler-of-two.test.tsx:62`) already renders the sync arm binding over a fresh series — HONEST-08-RESIDUAL's missing half is the `FreshnessChip` twin and the live observation, not a from-scratch test.

The single largest risk is not any of the fixes; it is the mutation-runner and SQL-gate coupling around the bridge. A migration that re-bases `sync_strategy_analytics_status` sits under three gate files whose `RED-UNDER-SETUP` apply lists end at `20260826120000`, an arm (`0a`) that mutates the OLD migration's `COMMENT ON FUNCTION`, two applied-ness gates that regex the function comment for `20260825150000` and `20260826120000`, a `pg_get_functiondef` self-verify that forbids the identifier `last_error` in the body, `FILES_FLOOR = 44` / `ARMS_FLOOR = 361` / `WAIVED_CEILING = 0`, and `scripts/dump-sql-functions.ts --check`. Each of these will go red for a specific, predictable reason listed under Pitfalls; a plan that does not name them will discover them in CI.

**Primary recommendation:** Two waves. Wave 1 (half b, six file-disjoint plans, all pure TS/TSX, parallel-safe) lands first because it is independent and the neuter-and-observe evidence is cheap to produce. Wave 2 (half a) is one migration + one Python plan + one SQL-gate plan, sequential, behind the three-reviewer gate, with the new gate file written on the pg-lane (`scripts/pg-lane/run.sh`) driving `mark_compute_job_failed` — the same substrate `test_sync_status_marked_refresh_protected.sql` already uses to perform a real transition.
