`strategy_analytics_computation_error_source_check CHECK (computation_error_source
IN ('writer'))`, and `computation_error_job_id UUID`. Both nullable, no default, no
FK. NULL on either means BRIDGE-OR-LEGACY provenance, which reproduces today's
behaviour exactly for the ~103 legacy PROD rows — that is what makes "no backfill" a
decision rather than an omission. Each carries a `COMMENT ON COLUMN` stating the NULL
semantic, who writes it, who reads it, and that the bridge nulls it on every
overwrite.

**The bridge.** `CREATE OR REPLACE` re-based on `20260826120000:336-905`. The body
was extracted with `sed -n '336,905p'` and edited only at the six delta points, so
everything else is byte-identical (verified: `diff` shows 11 hunks, and every `<`
line belongs to one of the six deltas):

1. `f.id` projected in the `live_failures` CTE.
2. `v_latest_job_id UUID` / `v_protected_job_id UUID` in DECLARE, filled by two more
   `(array_agg(id ORDER BY created_at DESC) FILTER (…))[1]` terms on the SAME
   aggregate, same FILTERs, same ordering as the two existing kind picks.
3. Branch (b)'s `DO UPDATE` arm becomes
   `CASE WHEN …computation_error_source = 'writer' AND …computation_error_job_id =
   v_latest_job_id THEN …computation_error ELSE EXCLUDED.computation_error END`,
   with the two markers carried on the same predicate (`ELSE NULL`). Its VALUES arm

4. Branch (b-prime)'s SET becomes the same CASE keyed on `v_protected_job_id`, with

5. Branches (a) and (c) null BOTH markers unconditionally, alongside the sentence
   they already blanked (CONTEXT correction 2 — a marker standing over a NULLed
   sentence would make the next generic write look curated).
6. Nothing else. `COMMENT ON FUNCTION` is NOT reissued; `computation_error_copy` is
   NOT redefined.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] Every anchor from `20260826120000`'s self-verify carried forward, not just the six the plan enumerated

- **Found during:** Task 1, while reading `20260826120000:1231-1233` ("Retained
  anchors from the definitions this re-bases on. Dropping any of these silently
  reverts a closed defect") and its delta note at `:237-240` ("Every CR-01 / JOB-01 /
  F-3 / PUB-02 / SI-02 anchor in the self-verify block is carried forward").
- **Issue:** The plan's self-verify spec named ~10 assertions. The file's own stated
  convention is that a re-base carries ALL of them, because a re-base is exactly the
  event that drops one silently.
- **Fix:** The new self-verify carries forward the CR-01 protection predicate, the
  health conjunct and its negative twin, the kind scope and all three kind literals,
  branch (a)'s hold, `has_live_successor` and its three scoping anchors, the
  marker-list spelling count, both position-ordering anchors, branch (b-prime)'s
  guarded-statement anchor, JOB-01's two, F-3/PUB-02's two, SI-02's count-of-3, and
  HONEST-01's H1 (the banned identifier), H2 (branch (b)'s VALUES) and H4 (the copy
  function's totality, which branch (b-prime)'s ELSE arm still depends on).
- **Not carried:** H3, H5, H5b and H6 — those pin `computation_error_copy`, an object
  this migration explicitly does not redefine and which is defined in exactly one
  migration (`grep -ln "FUNCTION computation_error_copy" supabase/migrations/*.sql` →
  one file). H4 IS carried, because b-prime's ELSE arm assigns its value
  unconditionally and a NULL return would blank the column over a live failure.
- **Commit:** `f1eafd76`

### 2. [Rule 1 — bug] The `IS NOT DISTINCT FROM` ban was placed where it could never fire, and was moved

- **Found during:** Task 1, designing the neuter for that arm.
- **Issue:** As first written, the ban sat AFTER the six positive CASE anchors. Every
  one of those spells `computation_error_job_id\s*=\s*v_…_job_id`, so an edit to
  `IS NOT DISTINCT FROM` breaks a positive anchor first and the ban is never reached.
  That is the file's own named vacuity class: "an assertion that contributes nothing
  while READING as independent coverage."
- **Fix:** Moved to `(P2a-neg)`, immediately after the aggregate anchors and above
  every positive CASE anchor, with the reasoning recorded in place. Arm 7 above is the
  measurement that it now fires and names the actual regression.
- **Commit:** `f1eafd76`

### 3. [Rule 3 — blocking] Branch (b-prime)'s positive anchor and BOTH its negative anchors had to be re-anchored

- **Found during:** Task 1.
- **Issue:** `20260826120000:1187-1190` asserts
  `SET computation_error = computation_error_copy(v_protected_kind)` as a bare
  assignment, and `:1224-1230` are two negative anchors keyed on that same prefix.
  Under this migration that prefix no longer exists: the positive one would have been
  RED on every apply, and the two negative ones would have been **silently dead**.
  That file's comment at `:1213-1223` predicted this exact edit and asked the next
  author to come back — this is that author doing so.
- **Fix:** All three re-keyed on `SET computation_error = CASE`, which occurs only in
  branch (b-prime) (branches (a) and (c) open their SET lists with
  `computation_status`). The negative pair keeps its `(?!WHERE\s+strategy_id)` bound
  rather than a `;` bound, for the measured reason recorded there. Arms 11, 14 and 15
  are the proof that all three bite.
- **Commit:** `f1eafd76`
