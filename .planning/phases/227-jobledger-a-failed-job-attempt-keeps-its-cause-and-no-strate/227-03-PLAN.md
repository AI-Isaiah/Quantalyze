<objective>
HEAL-02, database half: a token-fenced lease renewal. The worker claims up to five jobs at once and runs
them one after another, so a waiting job's `claimed_at` ages through its batch-mates' runtime and the
watchdog resets it while it still sits in the worker's list, after which it runs twice (RESEARCH Pattern 2,
traced). This plan adds `renew_compute_job_claims`, which moves `claimed_at` to now() only for rows still
running under the caller's own token. Plan 08 calls it from the worker before each dispatch and from the
heartbeat.

Purpose: HEAL-02 design is Claude's Discretion (CONTEXT, "research first"). RESEARCH Option A is taken.
Option B (a started_at column) does not close it, Option C (batch size 1) cuts throughput fivefold and
leaves other kinds open, and Option D (raise the threshold) is forbidden by the phase boundary.
Output: one migration, its rollback, one gate, one snapshot.
</objective>

## Decisions this plan records

- **DEC-03-A Fence on the token, not the worker id.** A row renews only when `status = 'running'` and its
  `claim_token` equals the caller's. The watchdog NULLs the token in the same UPDATE that resets the row,
  so a reset row can never be renewed by its old worker.
- **DEC-03-B No SKIP LOCKED in the renew.** A row being reset right now is locked by the watchdog; the
  renew waits for that one row, then sees the NULL token and renews nothing. SKIP LOCKED would let a renew
  report success-by-omission for a row it never looked at. The renew touches at most five rows.
- **DEC-03-C Returns the renewed ids.** The worker reads membership of the returned set to decide whether
  it still owns a row (plan 08's pre-dispatch fence).
