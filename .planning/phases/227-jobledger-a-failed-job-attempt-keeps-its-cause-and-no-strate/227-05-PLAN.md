## Decisions this plan records

- **DEC-05-A Registration lives in a runbook (resolves a conflict with RESEARCH).** RESEARCH recommended
  a new pg_cron job in a migration. Under the Phase 164.7 rule, restated as D-02 in derivecron-go-live.md
  and D-10 in outagealert-migration-schedules-nothing.test.ts, a migration never schedules. Registration is
  a marker-guarded live step after merge. So the migration ships the callable, and
  docs/runbooks/jobledger-go-live.md registers it. Until that step runs, the sweep does not fire on PROD,
  and the runbook says so in those words.
- **DEC-05-B Grace anchor = first observation by the sweep.** No finalize-time column exists, and RESEARCH A5
  found no usable anchor. `strategies.created_at` is wrong: a draft created days ago and finalized now would
  be caught in the seconds between finalize and its `after()` enqueue. The sweep stamps `first_seen_at` the
  first time a strategy matches, and re-enqueues only after `first_seen_at < now() - interval '90 minutes'`.
  So the grace is always longer than 1 hour. Rejected: adding a `finalized_at` column plus a re-base of
  `finalize_wizard_strategy`. That is a wider change to a hot RPC, for a guarantee the observation already gives.
- **DEC-05-C "Never synced and no job ever" reads DATA absence plus job absence.** The candidate conjuncts are:
  - status = 'private' only (DEC-05-G);
  - api_key_id present, with the key `is_active` and `disconnected_at IS NULL`;
  - no compute_jobs row with `strategy_id = s.id` or `api_key_id = s.api_key_id`. This covers the manager
    arm's `process_key_long` and the wizard's preview chain;
  - no trades row, no csv_daily_returns row and no strategy_keys row for the strategy;
  - no strategy_analytics row in a status other than 'pending'.

  Job absence alone is not enough, because done rows are pruned at 30 days and `/cron-sync` keeps strategies
  current without job rows. `api_keys.last_sync_at` is not a signal, because the finalize `after()` touches it
  even when the enqueue fails.
- **DEC-05-D The enqueue is a direct INSERT**, mirroring the first hop's own row: kind `sync_trades`,
  exchange NULL, metadata `{"source":"first-hop-sweep","detected_at":now()}`, ON CONFLICT DO NOTHING. It
  matches the reconcile sweep's precedent. `enqueue_compute_job`'s strategy path runs `_assert_owner`, which
  has no caller identity under the scheduler.
- **DEC-05-E Named state, no new enum value.** It is `computation_status = 'failed'` plus the sentence in the
  truths, with NULL provenance markers. Every existing reader already renders 'failed' with
  computation_error (SyncProgress, useStrategySyncPoller, ApiKeyManager, strategyGate, the admin review
  route). A new status value would touch every CHECK and reader for no gain. "Retry also fails" means every
  job of the strategy is failed_final and the analytics row is absent or 'pending'. A retry that ran and was
  marked failed already has the bridge's own failed row, and that row is kept.
- **DEC-05-G Only `private` strategies.** The finalize route sets `pending_review` for the manager flow and `private` for a contribution (`terminalStatus` in src/app/api/strategies/finalize-wizard/route.ts). Only the single-key contribution takes `runLegacyFinalize`, whose `after()` enqueues `sync_trades`. A single-key manager strategy goes through the unified arm, which "enqueues no sync_trades" (the route comment above the contribution branch). Its first hop is `process_key_long` through `postProcessKey`, and a failed dispatch is answered at submit time with SUBMITTED_ANALYTICS_NOT_QUEUED. Re-enqueueing `sync_trades` for it would be the wrong job: deribit, sfox and mt5 keys are ledger-backed and route through `process_key_long` to `derive_broker_dailies`, so a fill-based sync would fail and write a misleading failed state. HEAL-01 names the first `sync_trades` enqueue, so the sweep admits `private` only. A composite is excluded by `api_key_id IS NULL`.
- **DEC-05-F Hourly at minute 55.** The manifest's hourly slots 0, 15, 20, 25, 30, 35, 40, 45 and 50 are
  taken (`20 * * * *` is prod_prober_cadence_check). The runbook re-reads occupancy at run time.
- **RESEARCH census (a):** PROD has 0 keyed strategies with no compute_jobs row today, so the sweep catches
  nobody on today's data. The gate fabricates the dropped case.
