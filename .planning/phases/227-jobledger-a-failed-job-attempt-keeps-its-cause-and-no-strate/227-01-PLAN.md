<objective>
MT5D-01, first slice: a failed compute-job attempt keeps its cause. This plan creates the append-only
ledger `public.compute_job_attempt_failures`, makes `mark_compute_job_failed` write one `error` row in the
same transaction that flips the job to failed, and adds `record_compute_job_attempt_error` for the two
paths where the worker holds the real error but the mark could not land (55P03, 55006).

Purpose: the founder ruling for MT5D-01 (CONTEXT, 2026-11-23): "New append-only table, one row per failed
attempt: job id, attempt number, cause class, error text. Written before the M-1137 last_error clear on
re-claim, which stays and stays pinned. Survives job-row pruning, because 230 MT5NIGHTLY reads real nights
of these records." Reversibility one-way, already ruled by the founder, so no checkpoint.
Output: one migration, its rollback, one new SQL lane gate, two regenerated function snapshots.

## Decisions this plan records (planner, within CONTEXT "Claude's Discretion")

- **DEC-01-A Cause vocabulary.** `cause_class` CHECK admits exactly four values: `error` (a real failure,
  written here), `watchdog_reset` and `stall_reclaim` (written by plan 02 in `reset_stalled_compute_jobs`
  and `reclaim_stuck_compute_jobs`), and `orphan_reaped` (written by plan 07 through a narrow trigger on the orphan terminalizer's running-to-failed_final transition, because the terminalizer's cron body cannot be re-registered by a migration under the Phase 164.7 runbook rule).
  The founder named three ("a real error vs a stall reset vs a watchdog reset"); the code has four
  attempt-ending paths, and MT5D-01 says "every failed attempt", so all four are recorded (RESEARCH Open
  Question 2 decided IN).
- **DEC-01-B Write point.** The record is written at the failure source, in the failing transaction, so it
  commits before any later claim can run. The claim pair in `20260927120000` is NOT re-issued; its M-1137
  clear stays exactly as pinned, and this migration's self-verify re-reads that pin from the catalog
  (carried forward) because MT5D-01's correctness depends on the clear being the only place a cause is
  erased.
- **DEC-01-C Attempt identity.** `UNIQUE (job_id, claim_token, cause_class)`, not `(job_id, attempts)`:
  `reclaim_stuck_compute_jobs` decrements `attempts`, so a count can repeat, while every claim mints a fresh
  `claim_token`. The third column lets one attempt carry both a reset row and the worker's real-error row
  (RESEARCH Open Question 3), which is the honest record when both happened. A NULL token (legacy rows)
  never deduplicates, so no record is ever dropped for it.
- **DEC-01-D Lifecycle.** No foreign key to `compute_jobs` (the 30/90-day retention prunes must not delete
  the records 230 reads; precedent `strategy_analytics.computation_error_job_id`). `strategy_id` and
  `api_key_id` carry `ON DELETE CASCADE` to `strategies` and `api_keys`, mirroring `compute_jobs`' own owner
  cascades, so error text that can name a broker account is deleted with its owner. No `allocator_id`
  column: a `REFERENCES auth.users` on it would enrol the table in the GDPR export manifest
  (`scripts/check-gdpr-export-coverage.ts`), and allocator-side jobs are already covered by `api_key_id`.
  No retention cron in this phase; the table comment states that.
- **DEC-01-E Phase 230 columns.** `kind`, `exchange`, `api_key_id` and `job_created_at` are copied from the
  job row because 230 reads MT5 `derive_broker_dailies` nights, and those jobs can be keyed by `api_key_id`
  with a NULL `strategy_id` (TODOS `[175-NIGHTLY-MT5-DERIVE-CHECK]`).
- **DEC-01-F RLS shape.** RLS enabled with NO policy (the `mt5_server_clock_readings` shape), `ENABLE`
  without `FORCE` so the SECURITY DEFINER owner writes are not RLS-subject. Grant `SELECT` only, to
  `service_role`. Do not copy `compute_job_dedup_events`' FK or its deny-all policy (PATTERNS Rule 7 note).
