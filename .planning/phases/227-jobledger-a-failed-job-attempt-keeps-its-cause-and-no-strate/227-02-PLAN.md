## Decisions this plan records

- **DEC-02-A Which function.** Both. `reset_stalled_compute_jobs` is the live path (worker `watchdog_tick`);
  `reclaim_stuck_compute_jobs` gets the same treatment so it cannot become a second silent path if
  someone wires it up. Fixing only reclaim would close nothing in production.
- **DEC-02-B One bridge call per distinct (strategy_id, kind).** The trigger job id passed is the lowest
  reset job id in that group. Per kind, not per strategy, so a strategy with a reset side-kind job AND a
  reset main-kind job still bounces: the bridge's own `v_side_kinds` early return decides each call, and
  the reset never respells that list (PATTERNS: do not respell it elsewhere). Calls run in the order
  hashtext(strategy_id::text), strategy_id, kind, which is the order every other bridge caller locks in.
- **DEC-02-C Lock order.** Row locks (the reset's SKIP LOCKED selection) are taken first, then the bridge
  advisory lock, the same order as `mark_compute_job_failed`. A reset row is `running`, while the fan-in
  cascade locks only `done_pending_children` rows, so no cycle was found (RESEARCH Pattern 3). There is no
  lock_timeout on this path; plan 10's lane run measures the reset's duration with 500 rows (RESEARCH
  pitfall 6).
- **DEC-02-D The bridge's comment.** `sync_strategy_analytics_status`'s body comment lists
  `reset_stalled_compute_jobs` among the NON-caller writers. The bridge is NOT re-issued to fix a comment;
  this migration's header records the correction.
- **DEC-02-E Reclaim keeps its token.** Reclaim does not NULL `claim_token` today. Changing that is out of
  scope. Its ledger row carries the token it held.
