## Warnings

### WR-01: The CRITERION 2 scenario is one twelve-link `&&` chain — a red in (a) suppresses the public-log control in (g)

**File:** `scripts/prod-prober/run.mjs:4059-4107`

**Issue:** The whole scenario is a single expression:

```js
      pass =
        expect(
          row6.kind === "mt5-not-authorized" && row6.subject === "-6",
          `(a) the -6 fixture's ROW is mt5-not-authorized on subject -6 …`,
        ) &&
        expect( … ) &&   // (b) … (f2)
        expect(
          offenders.length === 0,
          `(g) THE PUBLIC-LOG CONTROL: no mt5 remedy carries a six-or-more-digit run …`,
        ) && …
```

`expect()` returns `false` on failure (`run.mjs:553-560`), so `&&` short-circuits and **none of the
later assertions execute**. Concretely: if branch (6b) is ever renamed or reordered, `(a)` goes red
and `(b)`–`(g-calibration)` never run — including `(g)`, the only gate in the repo standing between
an MT5 account number and a world-readable Actions log. The run still exits 1, so this is not a
silent pass, but a single unrelated regression blinds the disclosure control and credits one RED to
twelve controls.

This is not a style preference: plan 03 classified the identical shape as **"Rule 2 — Missing
Critical"** and fixed it thirty lines earlier in the same file (`run.mjs:3948-3955`: *"⛔ FOUR
SEPARATE `expect` CALLS … so a failure in the first does not silently prevent the other three from
running"*), and plan 04 restated it again (`prod-prober-wiring.test.ts:2534-2535`). The phase
shipped with its own rule violated in the one scenario that carries the disclosure gate.

**Fix:** Split the chain the way plan 03 already did, at minimum for the independent legs:

```js
      pass = expect(row6.kind === "mt5-not-authorized" && row6.subject === "-6", `(a) …`) && pass;
      pass = expect(row6.remedy.includes("VNC console") && …, `(b) …`) && pass;
      // …
      pass = expect(offenders.length === 0, `(g) …`) && pass;
      pass = expect(digitMutant !== row6.remedy && hasAccountShapedRun(digitMutant), `(g-calibration) …`) && pass;
```

The `if (row6 === null || …)` guard above already handles the only case where a later leg could
throw, so nothing depends on the short-circuit.

### WR-02: The `-6` defect row states two facts it never measured, and fires without checking that `initialize()` actually failed

**File:** `scripts/prod-prober/arms/mt5.mjs:320-333`

**Issue:**

```js
  if (code === -6) {
    return {
      kind: "mt5-not-authorized",
      subject: "-6",
      detail:
        "MT5 initialize() failed with -6: the rpyc bridge ANSWERED, … " +
        "That is why terminal_info() came back null and neither connected nor trade_allowed could be read. …",
```

The branch keys on `code === -6` alone. Two claims in the operator-facing `detail` are asserted
rather than read:

1. **"initialize() failed"** — `probe.initialize` is never consulted. Branch (6b) sits *above*
   branch (7) (`if (probe.initialize === true)`), so a transcript with `initialize: true`,
   `terminal_info: null` and a stale `last_error` of `-6` is reported as `mt5-not-authorized` with a
   detail that says initialize failed when it returned `true`.
2. **"terminal_info() came back null"** — `probe.terminal_info` is never consulted either. A `-6`
   arriving alongside a non-null `terminal_info` produces a row that contradicts its own transcript.

Neither is likely in production today (a successful `initialize()` leaves `last_error()` at
`(1, 'Success')`), which is why this is a Warning and not a Blocker. But this arm's whole doctrine
is that nothing unmeasured may be claimed — the same docblock states `connected`/`trade_allowed` are
*"printed and NEVER JUDGED"* and `mt5.mjs:124-127` refuses `bool(d.get(...))` specifically because
*"an absence produced a positive reading"*. A defect row that narrates a state it did not read is
the same defect class this phase removed, one level down. Branches (5) and (6) share the flaw; the
fix below is compatible with tightening them in the same shape later.

**Fix:** Guard the branch and derive the second clause:

```js
  if (code === -6 && probe.initialize !== true) {
    return {
      kind: "mt5-not-authorized",
      subject: "-6",
      detail:
        "MT5 initialize() failed with -6: the rpyc bridge ANSWERED, so the terminal is up and the IPC " +
        "transport is not implicated — but NO ACCOUNT IS AUTHORIZED on it. " +
        (terminalInfoPresent
          ? "terminal_info() did come back, so read connected/trade_allowed against the Journal. "
          : "That is why terminal_info() came back null and neither connected nor trade_allowed could be read. ") +
        "One state, one cause — not a code to look up.",
```

An `initialize: true` + `-6` transcript then falls to branch (7), whose detail (`"initialize ok but
terminal_info() returned null (last_error -6)"`) is true of that state. Add one fixture for it so
the new guard is not itself untested.

**Issue:** Verified independently, and plan 02's self-record is accurate. Both lists sit at the tail

and on any earlier failure `&&` short-circuits before it. The same holds at `:3798`. Under this
repo's own standard (*"a test that CANNOT FAIL is worse than none"*) these are two assertions that

in the summary, which CI never re-runs.

not defensible for *the new name*, which had a live alternative available in the same file.

it widens by itself and can actually fail:

```js

          "a transport failure is NOT reported as any statement about the terminal …",
        ) &&
```

`VERDICT_KINDS` is already defined at `run.mjs:589-591`. Alternatively move the absence assertion
*above* the `d.kind === …` pin so it is evaluated against an unconstrained result.

### IN-04: `autoIssueStep` slices to EOF, and `kindsMentioned` substring-matches English words

**File:** `src/__tests__/prod-prober-wiring.test.ts:2233-2241`

**Issue:** `autoIssueStep` is `text.slice(anchorIndex(text, AUTO_ISSUE_ANCHOR))` — unbounded. It is
correct today only because `- name: Open or update the prod-prober issue` happens to be the last step
(`prod-prober.yml:371`, file is 441 lines). Any step appended after it silently widens the subject
of an assertion documented as "the auto-issue step's slice". The file already has
`sliceBetweenAnchors` for exactly this. Separately, `kindsMentioned` uses `text.includes(k)` over a
roster containing `floor` and `absurdity` — ordinary English words — so innocuous future prose in
that step would red a test whose message reads *"selection has stopped being kind-independent"*.

**Fix:** Bound the slice (`sliceBetweenAnchors(text, AUTO_ISSUE_ANCHOR, "\n      - name: ")` with a
fallback to EOF for the last-step case), and match kinds on a word-ish boundary,
e.g. `new RegExp(`["'\`\\s-]${k}\\b`).test(text)`.
