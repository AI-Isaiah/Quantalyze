## 3. Remedy text conventions (house style, extracted)

Source: `arms/mt5.mjs:133-144` (five remedies), `arms/cron-obs.mjs:139`,
`arms/pyapi06.mjs:72-95`. The governing docblock is `mt5.mjs:124-132`:
> ⛔ ONE REMEDY PER KIND, AND THE TWO IPC REMEDIES SAY OPPOSITE THINGS.

**What a good remedy in this repo DOES:**
1. **Opens with the STATE, in caps for the discriminator** — "The rpyc bridge is NOT ATTACHED
   (-10004):", "The bridge IS ATTACHED but the terminal is NOT ANSWERING (-10005)."
2. **Names the exact action with the exact tool** — `` `railway redeploy` on the mt5-gateway
   service``, "Open the gateway's VNC console and clear the MODAL LOGIN DIALOG",
   "re-point the Vault secret analytics_service_key" (`cron-obs.mjs:139`).
3. **Names what to check, IN ORDER** — `mt5-ssh-transport` (`mt5.mjs:138-139`):
   "Check, in order: the RAILWAY_API_TOKEN's scope …, then the project / environment / service
   variables, then the gateway container's own state."
4. **Says what does NOT work, with ⛔ and a reason** — "⛔ a redeploy does NOT fix this, because
   the Wine prefix and the dialog live on the persistent volume and come straight back."
5. **Names the confirming observation** — "a SECOND consecutive hourly hit is the confirmation";
   "confirm the NEXT net._http_response row for this job is 2xx".
6. **Distinguishes the instrument from the subject** where they could be confused —
   `mt5-probe-timeout` (`mt5.mjs:140-141`): "this is our instrument's timeout, NOT the terminal's
   -10005 IPC timeout, and it says nothing about the terminal."
7. **≥ 40 chars and unique** — machine-enforced at `run.mjs:1104-1113`. In practice 200-400 chars.
8. **Never prints a value.** `pyapi06.mjs:40` — "⛔ NEVER PRINTS A VALUE." Remedies land in a
   PUBLIC Actions log; `CREDENTIAL_REMEDIES` (`run.mjs:197-200`) says "Names only".

**What a good remedy NEVER does:** send the reader to a lookup table, tell them to "investigate"
or "check the logs" without naming which log and which minute, restate the kind name, or share a
string with another kind.

**The one being REPLACED — `mt5-terminal-error`, `mt5.mjs:142-143`:**
> "The terminal answered with a NON-IPC failure code, so the bridge is fine and the fault is
> inside MT5 itself. Read the reported code against the MT5 error table and the gateway container
> log for the same minute; neither IPC remedy applies here."

⚠️ It is violating rule 2 only in its second sentence. Its FIRST sentence is the catch-all's
correct meaning and criterion 4 requires the bucket survive — so the pattern to follow is
**narrow the catch-all's second sentence, add a new remedy**, not delete the entry. (⚠️ Whether
"read against the MT5 error table" survives in the narrowed catch-all is the planner's call
under criterion 2's ⛔, which is scoped to the `-6` kind.)

**Source material for the new remedy's specifics (all tracked, all dated):**
- `docs/runbooks/mt5-go-live.md:174-177` — the two-field verification criterion verbatim:
  "`terminal_info()` must report **`connected: true` AND `trade_allowed: true`**. Both, not
  either — a detached terminal is a documented SIBLING cause of the same refusal."
- `mt5.mjs:8-13` — why a login re-clears `[Experts] Enabled` (the 2026-08-13 incident).
- CONTEXT `<specifics>` — the Journal line `'34043761': authorization on VantageMarkets-Live 14

## 4. Anti-vacuity / falsifier harnesses (criterion 6)

⛔ **The repo has TWO distinct falsifier idioms, and only one of them is on-disk.** Pick
deliberately; do not blend.

### (a) IN-PROCESS TEXT MUTANT — the dominant idiom in `prod-prober-wiring.test.ts`

35 `it("CALIBRATION: …")` tests. Shape: read the real source/fixture into a string, mutate the
COPY, assert the predicate flips, and assert the mutant actually differs from the original.
Nothing is written to disk, so nothing can be destroyed.

Canonical example — `prod-prober-wiring.test.ts:804-810`:
```typescript
it("CALIBRATION: a kind with no by-name assertion is reported UNCOVERED", () => {
  const selfTestBody = RUNNER_TEXT.slice(anchorIndex(RUNNER_TEXT, "export async function selfTest()"));
  const mutant = selfTestBody.split('kind === "mt5-probe-timeout"').join('kind === "mt5-probe-elapsed"');
  expect(mutant, "the rename must actually change the text").not.toBe(selfTestBody);
  const exercised = new Set([...mutant.matchAll(/kind === "([a-z0-9-]+)"/g)].map((m) => m[1]));
  expect(DEFECT_KINDS.filter((k: string) => !exercised.has(k))).toEqual(["mt5-probe-timeout"]);
});
```
Two supporting primitives, both mandatory:
- `anchorIndex(text, anchor)` — `prod-prober-wiring.test.ts:98-111`. **Throws by name** on a
  missing anchor rather than letting `slice(-1)` degenerate into a vacuous pass. Use it for any
  narrowing slice.
- The "mutant must differ" guard — `expect(mutant).not.toBe(original)`, and its data analog
  `withoutField()` at `:1856-1866`, which **throws** when the key it deletes was not there.

### (b) DATA MUTANT DRIVEN THROUGH THE REAL FUNCTION — the closest analog for a CLASSIFIER

`prod-prober-wiring.test.ts:1846-1897` (`[164.8.5-02] compareManifest totality`). Deep-copies a
committed fixture, removes exactly one field, drives the real exported function, asserts the
defect fires and names both the job and the field. Its header comment (`:1840-1844`) states the
rule the phase's criterion 6 is echoing:
> ⭐ FOUR SEPARATE `it()`s ON PURPOSE … the neuter matrix darkens each alone with the other two
> left live. A single test covering all three would credit one RED to three controls.

⭐ **This is the shape `-6` should copy**, because `classifyProbe` is a PURE exported function
(`mt5.mjs:160`) — the falsifier can import it and drive `6.txt`'s PROBE payload with the code
changed, or drive the real `-6` payload and assert `kind === "mt5-not-authorized"` while a
mutated-code payload falls through to `mt5-terminal-error`. That is a neuter-equivalent with
**zero on-disk writes**.

### (c) ON-DISK NEUTER → OBSERVE RED → RESTORE FROM BYTES

The only production instance is the SQL mutation runner (`scripts/mutation-runner/run.mjs`,
`neuterArm`), and even its own unit test (`src/__tests__/mutation-runner-neuter.test.ts:69-80`)
drives `neuterArm` on in-memory strings, never on disk. The on-disk neuter in this repo is a
**manual, recorded procedure**, evidenced by the measured records left in comments —
`prod-prober-wiring.test.ts:1899-1912`:
```
// MEASURED 2026-09-11, each `!…judged ||` arm dropped ALONE:
//     (B) prod side only     -> SELF-TEST PASSED: 73/73   (GREEN)
//     (C) manifest side only -> SELF-TEST PASSED: 73/73   (GREEN) + vitest GREEN
//     (B+C) both             -> SELF-TEST FAILED
```
**The house pattern is therefore: perform the neuter by hand, run
`node scripts/prod-prober/run.mjs --self-test`, record the exact observed output and date in a
comment beside the control, restore from a byte backup.** CONTEXT's discretion note and the
global memory both fence it: ⛔ never `git checkout --` in the harness; re-take the byte backup
after every edit.
