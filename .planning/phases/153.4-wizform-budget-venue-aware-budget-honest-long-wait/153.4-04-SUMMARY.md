## Accomplishments

- **The card is reachable.** 153.4-03 built `ValidateWaitCard` and mounted it nowhere. It now renders above the submit row on the single-key connect step, 300 ms after submit, torn down on every outcome — success, failure, cancel and deadline alike. The step owns the clock (a 1 s tick, never faster), the controller and the gate; the card stays pure, exactly as 153.4-05 needs it to be for N member panels.
- **⭐ The unpaid gate is PAID, in the commit that created the obligation.** `buildEnvelope` now receives `surface: "connect"` **and** `budgetSeconds` from the same commit that first emits `SEAM_DEADLINE_EXCEEDED`. Without the surface, 153.1-04's absence-suppresses rule silently withholds *"Your key details are still on this page."* — from the one user who most needs it, after a two-minute wait. It has its own `it`, so it cannot be dropped quietly.
- **`Stop waiting` costs nothing, and that is asserted at the level where it could be a lie.** The test reads the `AbortSignal` the fetch actually received: the card unmounting, the sentence rendering and the fields surviving are all local state, and every one of them would look identical while the credential-carrying POST ran on. Deleting `signal: controller.signal` reds it by name.
- **A cancel and a deadline are told apart before anything classifies them.** Both arrive as the same `AbortError`. The catch branches on a recorded reason FIRST: a user cancel sets a neutral line, logs nothing and fires no `wizard_error`; the deadline emits the code and fires exactly one event carrying it. Both directions asserted, in separate cases, so the funnel and the screen cannot disagree — and an operator cannot read a user's choice as MT5 failing.
- **The browser gives up LAST.** The deadline fires at `validateBudgetMsFor(venue) + WAIT_ABORT_GRACE_MS` (135 000 ms on the serialized arm), never at the budget itself — aborting there could cut off a verdict already on the wire and re-create the silent UNKNOWN this phase exists to end. The advertised figure stays the budget: the grace is the client's margin over the promise, not an extension of it.
- **The wait's venue is frozen at submit.** The exchange cards stay clickable while a validate is in flight. Reading live `exchange` would let a mid-flight card click re-time the client deadline and put a budget nobody granted into the card's promise and the envelope's `budgetSeconds` (T-153.4-12). Every duration this step states describes the request actually on the wire.
- **D-17 closes at this surface, as a side effect that is not incidental.** This is the FIRST of the fourteen `buildEnvelope` call sites to pass `venue`. An MT5 user hitting `KEY_NETWORK_TIMEOUT` no longer reads *"switch to a different exchange"* — a remedy that presupposes another venue exists when their broker account IS the venue. Byte-neutral for every ccxt venue, where the predicate already answers `true`. Asserted in both halves.
- **Full suite green:** 772 files / **11 587 passed / 287 skipped / 0 failed**; `npx tsc --noEmit` clean; `npm run lint` 0 errors.

## Deviations from Plan

### Acceptance criteria reconciled rather than silently satisfied

**1. `grep -c $'…' ConnectKeyStep.tsx` returns 1, not the 0 the criterion demands — and it returned 1 at HEAD too.**

The pre-existing occurrence is line 31, inside 140.5-03's `Retry-After` docblock, which quotes a malformed HTTP date (`Number("Wed, 21 Oct…")`) to explain why the raw-parse ESLint rule exists. The criterion was unsatisfiable as written without deleting an unrelated comment that this plan has no business touching.

What was done instead: my own first draft added a SECOND occurrence (a `<Button ref=…>` shorthand in a new comment); it was rewritten to spell the error out (`TS2322: "Property 'ref' does not exist"`), so the count is 1 before and 1 after — **this plan added none.** The property the grep proxies for is D-21: no U+2026 in RENDERED copy. That is now asserted rather than grepped — the busy-label case walks the card through three rungs and asserts its `textContent` contains no `…`, which a comment can never satisfy. This is the fourth time in this phase a bare substring grep has collided with prose (153.4-01, -02, -03 deviations); the resolution is the house one each time.

**2. The test file's own oracle-independence guard collided with itself TWICE, and the second collision is worth recording.**

The plan asks for an assertion "that the same test file does not compute `120` itself". Written as `source.includes("wizard/validate-budget")`, the guard matched **the assertion's own line** — the substring is in the expression that looks for it. Rewritten as an IMPORT-EDGE scan over comment-stripped source (the house form: `seam-ssr-exposure.pin.test.ts`, and `validate-budget.test.ts` for this very module), it then matched **its own positive self-test fixture**, because `importSpecifiers('import { x } from "@/lib/wizard/validate-budget";')` contains a real, edge-shaped `from "…"`.

The fix keeps both halves: the fixture is ASSEMBLED from an interpolated quote (`` `import { x } from ${q}…${q};` ``), which is edge-shaped to the extractor and invisible to the whole-file scan. The guard therefore has a working positive self-test, a negative one (a plain string mention must NOT match), a vacuity floor (it must find `@testing-library/react` and `./ConnectKeyStep`), and it can still fail on a real import. A substring grep would have had none of those.

### Deliberate divergences from the plan's action text

**3. `setSubmitting(false)` is NOT unconditional in the `finally`.** The plan says "always clear `waitStartedAt`, the card gate and `setSubmitting(false)` in a path that runs on every outcome". The first two ARE unconditional — a card outliving its request is the indefinite spinner in a new costume. The third is guarded by a `succeeded` flag, because the success arm has always left the button disabled while the parent advances the step; re-enabling it re-opens a double-submit window on a key that has already been stored. The `finally` still calls it for every non-success outcome, so it is a backstop for an arm that forgets, not a removal. Written out at the call site.

**4. Focus moves in an EFFECT, and the ref is on the submit ROW.** The plan says `handleStopWaiting` should "move focus to the submit button (add a ref to it)". Two facts prevent the literal form, both measured:
- At the instant of the click the submit button is still `disabled` (the abort resolves a tick later). `focus()` on a disabled control is a no-op, so the literal implementation would drop focus to `<body>` — the opposite of the affordance. An effect keyed on `cancelled && !submitting` fires once the button is enabled.
- `<Button ref={…}>` does not compile: `ButtonProps extends ButtonHTMLAttributes`, which carries no `ref` (`TS2322`, observed). Adding one is right and is a one-line change, but this phase's UI-SPEC ⛔ forbids editing `Button.tsx` and `AllocateDialog.test.tsx` carves that component out BY IDENTITY. The row holds the ref; the effect queries `button[type="submit"]` inside it. Logged in TODOS.md beside the existing focus-ring item, which lands in the same file.

**5. `venue` is passed alongside `surface`, which the plan's action text does not mention.** This sub-phase's UI-SPEC carries a ⛔ requiring BOTH at the `buildEnvelope` call sites it owns, and the omission is user-facing: an MT5 user reads *"switch to a different exchange"* for a venue that is their own broker account (D-17, the class 153.1-03 built the filter for). Byte-neutral for every ccxt venue. Asserted in both halves (the truthful replacement renders; the unwinnable one does not).

### Out of scope, logged not fixed

**6. `e2e/api-key-flow.spec.ts` has two failures, MEASURED as pre-existing.** Both are `request`-fixture POSTs to `/api/keys/validate-and-encrypt` that expect 401 and receive 403. Proven rather than assumed, against a local dev server:

No file this plan touches is involved — the failing cases never render a wizard step. The remedy is an `Origin` header on those requests, **not** relaxing a CSRF guard the spec predates. Logged in TODOS.md.
