<objective>
C27, the handler half, owned by this phase by founder ruling 3 (2026-11-24, "Yes, 223 fixes it"):
the daily Bybit `sync_funding` walk runs past its 180-second budget and, because rows are upserted
only after the whole walk, has never filled `funding_fees`. After this plan the handler walks one
7-day window at a time, oldest first, through plan 03's end bound, and stores each window (sorted
ascending, in 500-row slices, stopping at the first failing slice) before reading the next. A timeout
still fails the job, and each attempt keeps what it stored, so the next attempt resumes from the
stored cursor.

Purpose: SC-5. The cursor is the table itself, so persistence order is the whole correctness story.
Output: the windowed Bybit arm and `_store_funding_window` in `job_worker.py`, the C27 pins, and five
PROOF-01 records in the SUMMARY.
</objective>

## Decisions this plan applies (quoted from CONTEXT)

- Ruling 3, C27, the Bybit `sync_funding` walk over budget: "Yes, 223 fixes it". The walk must fit
  its budget, or be restructured so it fills the table, without hiding a timeout.
- [C27] (Decided autonomously): "run_sync_funding_job walks the Bybit range one 7-day window at a
  time (fetch_funding_bybit gains an optional end bound), reading both categories per window and
  upserting after each window, oldest first, so the max-timestamp cursor only advances over ranges
  already stored and the next attempt resumes there". No schema, no migration.
- [C27]: "No self-deadline. The handler timeout stays the only stop, so a walk still over budget
  fails as Handler exceeded timeout and is retried; each attempt keeps what it stored".
- [C27]: "linear then inverse inside the same window, before that window's upsert".
- [PROOF-01]: "a C27 test that a cancelled walk keeps the windows it finished; each goes RED on a
  neutered copy and GREEN after cp/cmp restore".
- RESEARCH refinement adopted (the hazard the locked design does not name): sort each window
  ascending, upsert it in `FUNDING_UPSERT_BATCH_SIZE` slices, stop the walk at the first failing slice.
  Reason: a cancel between batches, or a failed batch followed by a good one, would otherwise leave a
  newer row stored ahead of an older unstored one, and the 2-day overlap cannot reach back across a
  7-day window.

## Facts measured for this plan (HEAD f9d6d770e, 2026-11-24)

- `run_sync_funding_job` reads the cursor (`_load_funding_cursor`, newest `funding_fees.timestamp`),
  derives `since_ms` with `_funding_since_from_cursor` (None for an empty table), lazily imports the
  fetchers, fetches inside `try`/`except ccxt.RateLimitExceeded`/`finally: aclose_exchange`, and only
  AFTER the `finally` calls `upsert_funding_rows` once. The H-1115 branch logs each error and returns
  FAILED transient with `sync_funding: {n} upsert batch(es) failed: {errors[:3]}`.
- The handler reads the upsert result with `result.get("errors")`. A bare `AsyncMock` returns a
  `MagicMock`, which reads as truthy errors, so every upsert mock in this plan returns or produces
  the dict `{"inserted": n, "skipped": 0, "errors": []}` (or a non-empty `errors` list on purpose).
- `TIMEOUT_PER_KIND["sync_funding"]` is `3 * 60`; `dispatch` reads `TIMEOUT_PER_KIND` at call time and
  `classify_exception` maps the budget's timeout to transient `Handler exceeded timeout: ...`.
- `FundingFeeRow["timestamp"]` is a `datetime`; `upsert_funding_rows` continues past a failed batch
  by design (pinned by `TestUpsertFundingRowsErrors::test_partial_batch_failure_records_error_continues`,
  shared with `scripts/backfill_funding.py`), so it is called per slice and never edited.
- Three existing tests break by construction and are updated deliberately in Task 1, intent kept:
  `TestRunSyncFundingJob::test_happy_path_calls_upsert_with_rows` (Bybit, bare MagicMock cursor gives
  53 windows; rows lack `timestamp`), and both `TestRunSyncFundingJobCursorWiring` call-site tests
  (`assert_awaited_once()` and `args[2] is None` no longer hold).
- The C27 census pin calls `fetch_funding_bybit(exchange, "s", None)` directly and asserts
  `TIMEOUT_PER_KIND["sync_funding"] == 180`; it stays green unedited.
