## The questions in the brief, answered

1. `chain_ceiling_hit` / `*_complete` reading complete when a group failed: no. Every failure path that is not a ceiling sets `any_failed` and leaves `chain_ceiling_hit` field-absent. A group's values are merged only after the group returns, so a failed group leaves its `*_complete` key at field-absent. The in-group swallows (a refused 7-day page, a refused or garbled sweep filter) return `complete=False` explicitly. One False beside a failed state remains: the `diverged` branch sets `chain_diagnostic=failed` and step `analysis`, and if all five groups then run it writes `chain_ceiling_hit=False`. Plan Task 1 step 9 treats a `chain_diagnostic` other than `run` as `sc1: not-measured` and stops before Task 2, so no decision reads that False.
2. Remaining-budget deadline going negative or zero: it does not skip groups as complete. `max(0.0, left_s)` gives `budget_s=0.0`; `min(300, 0.0)` makes the deadline now; `asyncio.wait_for(run(), 0.0)` cancels the not-yet-started group and raises `TimeoutError`, which lands in the generic `except` as `Timeout` at step `close`, with `chain_calls=0`, `chain_ceiling_hit` absent and every group key absent. `budget_s=None` is tested with `is None`, not truthiness, so 0.0 is not mistaken for "no budget". The `max(0.0, ...)` in the caller is redundant (mutation M9 passes), harmless. The record cannot tell "no budget left" from "close hung for 300 s", but `chain_calls=0` does (INFO).
3. `chain_recent_refused` / `chain_sweep_refused` reading 0 when not measured: not when the group did not run (default is field-absent) and not on a group failure. They do print a measured 0 beside a read that was cut before it reached every page or filter (R3-04).
4. The unfiltered newest page being miscounted: three LOW edges (R3-03).

## New findings

### R3-01 LOW (data-integrity of the recorded cause) - the stopper also overwrites the `diverged` analysis marker
`scripts/okx_chain_record.py:489-496` (the `diverged` branch pre-sets step `analysis`, class `other`) and `:573`; docstring `:452-453`.

Evidence: the stopper branch assigns step and class unconditionally. The docstring and the code comment say it replaces "a recorded malformed one", but it replaces whatever is recorded, including the `analysis`/`other` pair that marks a refold which held beside a chain_break refusal. Test `test_a_venue_fault_after_a_diverged_refold_is_the_recorded_failure` pins this on purpose. After such a run the record says `chain_diagnostic=failed chain_failed_step=recent class=NetworkError`, and plan Task 1 step 9's `sc1: not-measured (... step=<..> class=<..>)` line prints only those two, so the founder is not told the refold diverged unless he reads `chain_arm` in the `chain-reading:` line. The symmetric loss for a malformed group followed by a stopper is real as well (the malformed step and class are gone; its keys read absent), but the decision there is second-run either way.

Hidden errors: a refold/oracle disagreement (the SFH-179-05 signal) masked by a later transport fault.

Impact: needs two independent faults in one run; the outcome is second-run regardless. LOW. To close it, keep `analysis` when `chain_arm == "diverged"`, or add `chain_arm` to the step 9 not-measured line.

### R3-02 LOW (residual of SFH-R2-04) - the refusal count does not say what was refused, and plan Task 2 does not read it
`services/okx_bills_chain.py:664-665, 696-712, 765`; `scripts/okx_chain_record.py:524, 547`; `179-03-PLAN.md:159-162`.

Evidence: `Sweep.refused` counts the unfiltered newest-page failure (`rejected += 1` at `:712`) in the same counter as refused type filters and refused instType filters, while the field comment says "Filters the venue refused". `chain_sweep_refused=1` with 25 filters probed is ambiguous between a refused `EVENTS` instType (irrelevant to D-02), a refused type filter (the D-02 evidence) and a failed unfiltered page. No exception class is carried. The plan's cut-short rule still says "a second run can complete it" for `chain_sweep_complete` / `chain_recent_complete` not True, and does not mention the new keys, so a refusal that repeats on every run keeps recommending second-run. The keys will appear in the `chain-reading:` line automatically (it lists every CHAIN_KEYS key), so the information reaches the founder; the plan text just does not tell the executor to use it.

Impact: wasted approved Railway runs, no wrong verdict. Cheapest closure is a plan sentence: "`chain_recent_refused` or `chain_sweep_refused` above 0: the venue's refusal repeats on every run; name it in the caveat and do not offer second-run as completing that search." Splitting the count (type / instType / unfiltered) is optional.

### R3-03 LOW (data-integrity, hidden-kinds row) - the unfiltered newest page can still miscount in three narrow ways
`services/okx_bills_chain.py:698-712, 737-742`.

1. Order. The unfiltered page is read first and the roughly 25 to 31 filtered probes after it. A bill stamped before the walk that the archive ingests between the unfiltered read and its filter's probe is above the walk's largest `billId`, absent from `served_now` and present in the filtered reply: counted hidden. Reading the unfiltered page last would make the check one-directional (it could only suppress). The window is tens of seconds, and the walk began minutes earlier.
2. Coverage. `served_now` is the newest 100 rows. If the unfiltered page is full and the late bill is older than its oldest row (a very active account in the 10-20 minutes between walk and sweep), the bill is not suppressed and is counted hidden. Nothing in the record says the unfiltered page was full, so `chain_sweep_complete=True` with `chain_types_hidden>0` (plan row 6) cannot be told from a lag artefact. A short unfiltered page is a complete suppression set; a full one is not. a4 has 1282 trades in total, so the exposure is small.
3. Failure path. If the unfiltered read fails, `rejected` goes to 1 and the sweep is not complete, so row 6 cannot fire: sound. If it hits the call ceiling, `sweep_hidden` returns `Sweep(0, 0, 0, 0, 0, {}, False, True)` and `_sweep` writes those zeros (`chain_types_probed=0`, `chain_hidden_kinds="none"`) beside `chain_ceiling_hit=True`. Any other group that hits the ceiling before measuring leaves its keys field-absent (the `CallCeilingReached` raised out of `read_bill_types` propagates to the loop). Raising `CallCeilingReached` here instead of returning zeros keeps the "not measured is absent" rule the SFH-179-04 fix established; the plan's ceiling rule already blocks any decision on it.

Impact: each is a route to an over-counted hidden type, all low probability; none flips `complete`.

### R3-04 LOW - a refused count from a cut read prints as a measured 0
`scripts/okx_chain_record.py:524, 547`; `services/okx_bills_chain.py:523-536, 765`.

`chain_recent_refused` and `chain_sweep_refused` are written unconditionally, unlike the sibling counts that go through `_lower_bound`. A 7-day read cut by the call ceiling before page 1, or a sweep cut by the ceiling after three filters, prints `refused=0` for pages or filters never attempted. Zero from a cut read proves nothing about the unprobed remainder (the SFH-179-04 principle). Both reads also set `ceiling_hit`, which the plan reads first, so no decision moves.

### R3-05 LOW (test cannot fail on the mechanism it exists for) - the probe test does not pin the elapsed-time term
`tests/test_allocator_history_probe.py::test_a_chain_diagnostic_never_outlasts_what_is_left_of_the_outer_bound`; code `scripts/allocator_history_probe.py:1045, 1113`.

Evidence: the test sets the outer bound to 0.5 s, below the 30 s margin, so `left_s` is negative whatever the elapsed term is. Mutation: replace `asyncio.get_running_loop().time() - started` with `0.0` and the test still passes (1 passed). So the stamp at the top of `_measure_anchor`, which is the point of the fix, is untested at the probe level; dropping the margin or ignoring `budget_s` is caught (M3, M8). The `_hangs` patch on `read_below_stop` in that test is dead (the run stops at `close` before it). The record-level test `test_the_callers_remaining_budget_shortens_the_chain_deadline` covers `budget_s` but not how the probe computes it. A test that sets the bound to, say, 32 s and fakes the loop clock past 2 s before the chain, then asserts the Timeout lands, would pin the stamp. Cheap fix: extract `left_s` into a small pure helper and test it.

### R3-06 LOW (residual of SFH-R2-05) - a deadline or network fault mid-sweep still discards every probe already measured
`services/okx_bills_chain.py:670-770`; `scripts/okx_chain_record.py:557-573`.

`asyncio.wait_for` cancellation drops the `Sweep` locals, so a Timeout in the sweep (the longest group: up to about 31 filters plus the new unfiltered page; the budget is now the smaller of 300 s and the outer remainder) leaves all sweep keys absent and `chain_failed_step=sweep class=Timeout`. Loud and correct (second-run), but the D-02 evidence from the probes that did finish is lost. Not fixed by design; recorded for the Task 2 caveat text.
