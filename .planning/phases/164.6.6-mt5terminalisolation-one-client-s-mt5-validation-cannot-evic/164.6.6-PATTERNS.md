## Pattern Assignments

### `analytics-service/services/mt5_session_episodes.py` (service, event-driven) — criterion 3

**Analog:** `analytics-service/routers/cron.py` symbol `_escalate_prober_cadence_gap`, with
`analytics-service/routers/internal.py` symbol `_alert_kek_unavailable` as the earlier, structurally
identical precedent. ⚠️ **`services/audit.py` is NOT the analog** — it calls `sentry_sdk.capture_exception`,
a different idiom with no rate-limit/window state; RESEARCH.md's own correction flags this and it was
re-verified this session (`services/audit.py` does not define the windowed-`capture_message` shape).

**The insertion point already exists** — the `blind = (...)` computation followed by
`logger.log(logging.WARNING if blind else logging.INFO, ...)` inside `record_mt5_session_reading`.
That `logger.log` call is exactly what the ROADMAP's criterion 3 measurement refers to: it flips
INFO→WARNING and computes `blind=True`, and nothing outside the module reads it. A rate-limited
Sentry escalation belongs directly beside it, gated on `blind`.

**Core pattern to clone** (shape only — quote the STRUCTURE, not any literal that could carry an
account or a broker string):
```python
# Source shape: routers/cron.py::_escalate_prober_cadence_gap
# (equally present, same shape, in routers/internal.py::_alert_kek_unavailable)
_SOME_ALERT_WINDOW_S = 3600.0            # window is a MODULE constant, float seconds
_last_alert_at: dict[str, float] = {}    # keyed by the alarm's OWN identity, never shared

def _escalate_<name>(...) -> None:
    # 1. Log UNCONDITIONALLY, before any window check — the RATE of these lines
    #    is itself operator evidence, independent of whether Sentry fires.
    logger.error("<structured message, no credential, no account, no free-text last_error()>")

    # 2. Rate-limit the ESCALATION ONLY, keyed by the alarm identity (never a
    #    single shared timestamp — a second alarm source must not silently
    #    suppress a first one's paging).
    now = time.monotonic()
    last_at = _last_alert_at.get(key)
    if last_at is not None and (now - last_at) < _SOME_ALERT_WINDOW_S:
        return
    _last_alert_at[key] = now

    # 3. Bare try/except: pass around the Sentry call ONLY — a transport
    #    failure must never mask or crash the path being reported on.
    try:
        sentry_sdk.set_tag("<tag_name>", key)
        sentry_sdk.capture_message("<scrubbed message>", level="error")
    except Exception:
        pass
```

**Test-only reset helper convention** (both analogs ship one):
```python
def _reset_prober_cadence_alert() -> None:
    """Test-only helper to clear the escalation window between cases."""
    _last_prober_cadence_alert_at.clear()
```
A fourth clone needs the same `_reset_<name>_alert()` helper so
`test_mt5_session_episodes.py` can clear the window between cases exactly as
`test_prober_cadence_alert.py` does.

**Security/error-handling constraint carried from the analog, and load-bearing here specifically
because criterion 2's whole subject is client account numbers and broker names:** neither the log
line nor the Sentry message may carry a credential, header value, account number, broker server
name, host or port — `_escalate_prober_cadence_gap`'s own docstring states this explicitly for its
own alarm, and `mt5_session_episodes.py`'s own module docstring independently states the identical
constraint for every row it already writes ("WHAT MAY NEVER REACH A ROW … no login, no password, no
broker server, no gateway host, no port, no terminal key, and NO free-text detail from
`last_error()`"). The new Sentry call must obey the SAME list — only `kind` / `code` / the
`consecutive_not_measured` / `escalation_threshold` counters already computed at that site are
safe to echo.

**Also respect the existing decided-kinds exemption** — `_DECIDED_BLIND_KINDS` already keeps a
deliberately-disabled feature (e.g. algo trading turned off on purpose) from ESCALATING the log
level; the new Sentry call must sit downstream of the same `blind` boolean rather than re-deriving
its own condition, or it re-introduces an alarm on a state an operator chose.

### C2 disclosure test — "no enumeration" assertion (test, assert-absence)

**Analog:** two symbols inside `analytics-service/tests/test_mt5_session_episodes.py` —
`test_the_module_global_scanner_BITES` and `test_no_credential_host_or_port_reaches_ANY_field_of_ANY_row`.
Together they are this repo's own established shape for "prove a thing is absent, and prove the
absence-check itself is not vacuous."

**Core pattern — the self-test-that-the-scanner-bites idiom** (structure only):
```python
def test_the_module_global_scanner_BITES() -> None:
    """⛔ THE CALIBRATION. A scanner that returned the empty set would make the
    assertion above pass over ANY amount of [the thing being forbidden]."""
    source = inspect.getsource(<module>)
    anchor = "<a real source line the forbidden pattern would introduce>"
    assert anchor in source, (
        f"the mutation anchor {anchor!r} is gone — the mutant would not apply "
        "and this calibration would pass VACUOUSLY"
    )
    mutated = source.replace(...)
    # ... assert the scanner DOES flag the mutated (bad) source ...
```
Pair this with an assert-absence test structured like the credential-scan test: assert on the
COUNT or the KEY SET of whatever a would-be violation would touch (e.g. "no field name outside an
allowlisted set reached a row/log record"), never on the forbidden VALUE itself — per D-05, the
test must not itself capture and assert on an account list, because a captured-and-compared list is
the disclosure the criterion exists to prevent. Model the fixture-level anti-vacuity guard too
(`assert len(sink.rows) == N, "...the scan below would otherwise pass over an empty table"`) so the
new test cannot pass by observing nothing.

**Where this test physically lands is the planner's call**, not fixed by this document — candidates
are `test_mt5_session_episodes.py` (if the check rides beside the criterion-3 escalation code) or
`test_mt5_concurrency.py` (if it instead asserts something about the lease/D-10 remedy). Either
host file already carries this exact idiom.

**Analog:** the file's own `mt5_terminal_lease` async context manager, specifically its `finally`

**The load-bearing ordering to extend, never reorder** (structure, quoted from the function's own
in-code comment, which is itself the pattern to preserve):
```python
    yield
    finally:
        # ORDER IS LOAD-BEARING (WIZFORM-ABANDON / D-36).
        #  1. BUMP BEFORE RELEASE.
        #  2. Un-stamp SECOND, so the stamp is live for the whole hold.
        #  3. Release LAST.
        bump_mt5_terminal_epoch(terminal_key)
        end_mt5_lease_occupancy(token)
        lock.release()
```
Any restore-on-release call added here needs its position relative to these three existing steps
reasoned about explicitly in the plan (before the bump? between bump and un-stamp? after release?)
— the comment's own "ORDER IS LOAD-BEARING" warning applies to any addition, not only the three
existing lines. The docstring on the same function also states the two acquisition-arm invariant
("a timed-out acquisition releases NOTHING … it BUMPS NOTHING and STAMPS NOTHING") — a restore call
must not run on that arm either, since it never held the terminal.

**Exactly ONE registry, never a second** — the module's own header comment
("A SECOND `dict[str, asyncio.Lock]` terminal registry anywhere in the tree SERIALIZES NOTHING")
applies to any option-3 remedy too: a restore mechanism must hang off THIS lease, not stand up a
parallel bookkeeping structure.

## Shared Patterns

### Rate-limited Sentry escalation (criterion 3)
**Source:** `analytics-service/routers/cron.py` (`_escalate_prober_cadence_gap`),
`analytics-service/routers/internal.py` (`_alert_kek_unavailable`)
**Apply to:** `analytics-service/services/mt5_session_episodes.py` (the new escalation call) and its
test file.
**Shape:** log unconditionally at `error`, rate-limit the Sentry `capture_message` call to at most
once per window keyed by the alarm's own identity (never a single shared timestamp), wrap the
capture in a bare `try/except: pass` so a Sentry transport failure can never mask the path being
reported on. Never let the message carry a credential, account number, broker server name, host,
port or free-text `last_error()` detail.

### Lease `finally`-block ordering discipline (criterion 1, if D-10 picks option 3)
**Source:** `analytics-service/services/mt5_concurrency.py` (`mt5_terminal_lease`)
**Apply to:** any restore-on-release addition.
**Rule:** bump the terminal epoch BEFORE release; un-stamp occupancy SECOND; release the lock LAST.
A timed-out acquisition bumps and stamps NOTHING, because it never held the terminal. This ordering
is documented in-code as load-bearing (WIZFORM-ABANDON / D-36) and pinned by
`test_mt5_concurrency.py` — do not reorder it to fit a restore call; reason explicitly about where
the restore sits relative to these three steps.

### Assert-absence + self-test-that-the-scanner-bites (criterion 2, disclosure)
**Source:** `analytics-service/tests/test_mt5_session_episodes.py`
(`test_the_module_global_scanner_BITES`, `test_no_credential_host_or_port_reaches_ANY_field_of_ANY_row`)
**Apply to:** the C2 "no enumeration" test, and any other assert-absence test this phase needs.
**Rule:** a test that asserts a forbidden thing is absent must ALSO prove its own scanner/assertion
can detect the forbidden thing if present (mutate the source or the input and observe the assertion
flip) — this repo's own answer to "a test that cannot fail is worse than none," applied to
absence-checks specifically. The check itself must report a COUNT or a KEY SET, never capture and
compare against the forbidden VALUE (an account list) — a captured-and-compared list is itself the
disclosure D-05 forbids.

### Credential-free, non-identifying detector (D-03/D-05 boundary — preserve, do not extend)
**Source:** `analytics-service/services/mt5_client.py` (`Mt5Client.assert_session_authorized`)
**Applies to:** any D-10-costing or eviction-detection work this phase's plan proposes.
**Rule, preserved not created:** the detector distinguishes "some account is authorized" from `-6`
(no account authorized) from IPC faults (`-10003`/`-10004`/`-10005`) WITHOUT ever identifying WHICH
account — by design, per its own docstring ("a detector that carried a credential could not be used
to DECIDE whether to send one"). Any new detection code this phase adds must preserve this
non-identifying property; extending it to name an account would collide with D-05.

### Read-only, non-enumerating diagnostic convention (D-05 boundary — preserve, do not extend)
**Source:** `scripts/mt5-diag.sh`
**Applies to:** any diagnostic or costing script this phase's plan proposes for D-10.
**Rule, preserved not created:** the script calls `initialize()` + `terminal_info()` and never
`login()`; it reports booleans (`trade_allowed`, `connected`, etc.) and never a registered-account
list. Its own header names the reason a probe that logs in would re-break the exact thing it
measures (an armed `[Experts] Account=1` re-clears `Enabled` on every account change) — the same
reasoning D-11 applies to costing D-10 option 3's re-login-on-restore.
