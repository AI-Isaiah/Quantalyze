⛔ **START FROM D-01: THE MUTEX IS NOT MISSING, AND NOTHING IN THIS PLAN ADDS A LOCK.**
`analytics-service/services/mt5_concurrency.py` is already the single-source per-terminal lock
registry (`_MT5_TERMINAL_LOCKS`, `_mt5_terminal_lock_for`, `mt5_terminal_lease`), and
`analytics-service/routers/exchange.py` already takes it on the interactive validate path. The
2026-09-21 eviction happened WITH the lease correctly held. A second `dict[str, asyncio.Lock]`
registry anywhere in the tree hands out two perfectly functional lock objects per key and
serializes NOTHING (`MT5CONC-02`), so a plan that "strengthens the lock" makes things worse.

`mt5_terminal_lease` is backed by `asyncio.Lock` objects in that one module-level registry. It
is correct today for exactly one reason: `analytics-service` runs as ONE process with ONE event
loop. Add a second worker or a second replica and the lease silently serializes NOTHING while
every existing test still passes — the two-registries failure mode the module's own docstring
already forbids, arriving through deployment instead of through code.

⛔ **D-04 SAYS THIS IS "NOWHERE STATED". MEASURED AT HEAD, THAT IS TOO STRONG, AND THIS PLAN
CORRECTS IT RATHER THAN RESTATING IT.** It is stated twice:

1. `analytics-service/services/mt5_concurrency.py`, the MT5CONC-02 header, section headed
   `SCOPE — a DOCUMENTED gap, not silently assumed`: an `asyncio.Lock` is single-event-loop;
   the honest remaining gap is REPLICAS; two replicas own two registries and serialize nothing
   against each other; a scale-up is a correctness change, not a capacity knob.
2. `docs/runbooks/mt5-go-live.md` § Step 1: `⛔ INVARIANT — SINGLE REPLICA, BOTH SERVICES
   (153.3 / D-33)`, naming both services, the mechanism, the symptom, and the remedy a raise
   would require first (a durable cross-process serializer).

⭐ **WHAT IS GENUINELY MISSING IS TWO THINGS, AND THE RUNBOOK ITSELF NAMES THE FIRST ONE**
