## The structural gates this module already carries — ⛔ MEASURED 2026-09-22, read before editing

Four gates in `analytics-service/tests/test_mt5_session_episodes.py` constrain where the new
code may sit. They were re-read from source this session; none of them is optional and none of
them may be widened to fit the escalation.

1. **`test_the_recorder_satisfies_the_SHARED_never_raises_predicate`** — `_heal_guard_defects`
   (imported from `analytics-service/tests/test_mt5_relogin.py`, never copied) parses
   `record_mt5_session_reading`'s own source and requires: exactly ONE top-level statement
   outside the docstring and it must be the `try`; exactly one handler catching bare
   `Exception`; that handler's body exactly one nested `try` whose handler list is exactly
   `['BaseException']`; no `finally:` and no `else:` on either. ⇒ **The escalation call goes
   INSIDE the existing `try` body, beside the `logger.log(...)`. A `global` declaration or an
   import at the function's top level is a second top-level statement and reds this gate** —
   which is exactly why `_count_blind_reading` and `_stamp_reading_and_measure_gap` are already
   separate functions. The new escalation helper is a MODULE-LEVEL `def`, which the predicate
   never sees.
2. **`test_the_module_holds_NO_EPISODE_STATE_AT_ALL_by_construction`** — the set of module-level
   names any function REBINDS (via `ast.Global`) must EQUAL `_DECLARED_MUTABLE_MODULE_GLOBALS`,
   today `{_LAST_MEASURED_READING_MONOTONIC, _CONSECUTIVE_NOT_MEASURED_READINGS}`. A scalar
   window global rebound with `global` makes this gate FIRE, and the gate's own failure message
   says how to satisfy it: add the name WITH the reason it cannot be episode state.
   ⛔ Do not dodge it with a `dict` mutated in place — a dict needs no `global` statement, so
   the scanner would never see it and the gate would go quiet over new module state. The scalar
   is chosen precisely because it keeps this gate doing its job.
3. **`test_this_module_never_catches_OSError`** — no handler in the module may name `OSError`
   or `TimeoutError` (`asyncio.TimeoutError is TimeoutError` and its MRO runs through
   `OSError`, so such a handler silently eats a budget expiry). `except Exception` is correct.
4. **`test_no_except_BaseException_in_this_module_ever_wraps_an_await`** — an `except
   BaseException` may not guard an `await`. The escalation helper is synchronous and awaits
   nothing, so it is unaffected; do not make it `async`.

## Why a SCALAR window and not a keyed dict — the identity model, stated rather than assumed

The `assumption-delta` detector FIRED on this phase (`gsd query assumption-delta scan 164.6.6`
-> `detected: true`, `kind: pluralization`). It is firing correctly: this phase is a
singular-to-plural seam.

MEASURED: `record_mt5_session_reading` takes `kind`, `code`, `source` and `poll_interval_s` and
**no terminal identity at all**; `_CONSECUTIVE_NOT_MEASURED_READINGS` is a scalar `int` and
`_LAST_MEASURED_READING_MONOTONIC` a scalar `float | None`. This module is SINGULAR by
construction. ⇒ The window is a scalar `float | None`, mirroring
`analytics-service/routers/internal.py`'s `_last_kek_alert_at`, not
`analytics-service/routers/cron.py`'s `_last_prober_cadence_alert_at: dict[str, float]` — that
one is keyed because its alarm genuinely has a `cron_name` axis and this one has no axis to key
by. Inventing a key would fabricate an identity the module does not have.

⚠️ **This is a real cost of D-10 options 1 and 2 and it is carried into the decision dossier
(plan 04), not swallowed here.** Ephemeral or pooled terminals make the terminal plural, and
this module — counter, stamp and alarm alike — would then be measuring an aggregate of N
terminals as if it were one.

## The failure mode this plan ACCEPTS, stated rather than discovered later

`164.6.6-RESEARCH.md` Open Question 2 asks the planner to say explicitly which of two failure
modes is being accepted, and this section is that answer.

**ACCEPTED: a redeploy during a dark window resets the blind-run count, and can therefore delay
an escalation past its intended threshold.** The counter, the previous-reading stamp and the new
alarm window are all in-process and reset on deploy. The bound is how often `analytics-service`
redeploys, which is measurable from Railway deploy history. ⭐ The module's own comment above
`_CONSECUTIVE_NOT_MEASURED_READINGS` already accepts exactly this trade in exactly these words —
a redeploy can restart a blind run's count, the cost is a late escalation on a mechanism that
also writes nothing while blind, and paying it is cheaper than a second durable write path. This
plan inherits that acceptance rather than re-opening it.

**DECLINED: the PROD `pg_cron` alternative** (a `prod_prober_cadence_check()`-shaped function
watching `public.cron_runs` for staleness). It is declined BY ELIMINATION, not by preference:
`mt5_session_episodes.py` writes rows on state TRANSITIONS only, so a long, healthy, unbroken
authorized period produces NO new rows and reads identically to a genuinely dark terminal under
a gap-since-last-row check. No sound redesign of those semantics was found, and the in-process
counter — which updates on EVERY tick regardless of transitions — is the only signal that
actually distinguishes the two. It is also strictly cheaper: no migration, no founder-gated live
`cron.schedule` session, no three-reviewer migration gate. ⛔ Do not "upgrade" this plan to the
pg_cron shape without first solving the per-transition semantics; a naive copy would alarm on
healthy sessions.
