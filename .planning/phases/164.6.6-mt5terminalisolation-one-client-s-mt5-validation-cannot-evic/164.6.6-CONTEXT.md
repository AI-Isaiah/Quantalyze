# Phase 164.6.6: MT5TERMINALISOLATION - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

One client's MT5 key validation cannot evict, disturb or expose another client's
broker session on the shared terminal — and a shared-terminal outage reaches a human
without one clicking a button.

⛔ **SAME INCIDENT AS 164.6.5, DIFFERENT DEFECT, and this is the fence most likely to
be lost.** 164.6.5 makes validation stop BREAKING the terminal — availability. THIS
phase makes the terminal stop being a SHARED MUTABLE RESOURCE — architecture.
`164.6.5-CONTEXT.md` states the same fence from its side: *"THIS PHASE DOES NOT FIX
THE EVICTION — that is Phase 164.6.6. The outage was the symptom; the shared mutable
terminal is the defect."*

⛔ **THE NORMAL PATH IS THE DEFECT HERE, NOT THE FAILURE PATH.** The 1h39m outage
belongs to 164.6.5 and must not overshadow this: the eviction measured 2026-09-21 was
a **clean, successful, one-second handover** — `04:08:06 disconnected` →
`04:08:07 authorized`. **A validate that SUCCEEDS still silently destroys another
client's session.** The evicted account was serving a live session with 11 open
positions and got no error, no signal and no record against it.

</domain>

<decisions>
## Implementation Decisions

### A. The eviction — what is actually missing (⛔ it is not a lock)

- **D-01: ⛔⛔ THE MUTEX IS NOT MISSING. DO NOT PLAN "ADD A LOCK".** MEASURED at
  `956f663f`: `analytics-service/services/mt5_concurrency.py` is a single-source
  per-terminal lock registry (`_MT5_TERMINAL_LOCKS`, `_mt5_terminal_lock_for`,
  `mt5_terminal_lease`), and the INTERACTIVE VALIDATE PATH ALREADY TAKES IT —
  `analytics-service/routers/exchange.py` opens
  `async with mt5_terminal_lease(terminal_key, wait_s=_MT5_LEASE_WAIT_S)` around the
  connect-and-probe region. The module's docstring is explicit that a second registry
  anywhere serializes nothing (`MT5CONC-02`), so a planner who adds one makes things
  worse, not better. ⇒ The eviction happened **with the lease correctly held**.
  — **Reversibility:** reversible — a finding, not code.

- **D-02: WHAT IS MISSING IS RESTORATION, NOT EXCLUSION — and the design says so in
  its own words.** The lease guarantees no two callers occupy the IPC region at once.
  It guarantees NOTHING about which account the terminal is left logged into when the
  body exits. `routers/exchange.py` records the intent verbatim: *"What is capped here
  is CONCURRENCY, and nothing else … one terminal cycles through hundreds of accounts
  across a day (D-29, REVISED 2026-08-08)."* ⇒ This phase's subject is the terminal's
  **RESTING STATE BETWEEN LEASES**, which nothing currently owns.
  — **Reversibility:** reversible.

- **D-03: ⛔ THE EVICTED PARTY NEVER HELD A LEASE, AND THAT IS THE STRUCTURAL GAP.**
  The lease already fences abandoned work INSIDE the process: `mt5_terminal_lease`
  bumps `bump_mt5_terminal_epoch` on **every** exit path (normal, raising, cancelled)
  before releasing, and stamps occupancy via `begin_mt5_lease_occupancy` /
  `end_mt5_lease_occupancy`, so a zombie thread is distinguishable from a live caller
  (WIZFORM-ABANDON / D-36). But a broker session that is merely **authorized** —
  `<account A>` with its 11 open positions — is terminal-side state held by no Python
  caller. It took no lease, so no epoch bump reaches it and no fence can notice it
  died. ⛔ **Adding another epoch bump does not close this.** Either the authorized
  session becomes a modelled occupant, or eviction is made harmless by restore.
  — **Reversibility:** reversible as a finding; the remedy it forces is D-10.

- **D-04: ⚠️ THE LEASE IS PROCESS-LOCAL, THIS IS LOAD-BEARING, AND IT IS NOWHERE
  STATED.** MEASURED: the registry holds `asyncio.Lock` objects, and
  `analytics-service/Dockerfile` starts `uvicorn main:app` with **no `--workers`
  flag**, so exactly one event loop exists and the lock is real. Add `--workers 2`,
  a second replica, or any out-of-process caller and the lease **silently serializes
  nothing while every existing test still passes** — the two-registries failure mode
  the module already warns about, arriving through deployment rather than through
  code. ⛔ This phase states the assumption explicitly and makes it observable; it
  must not be discovered by whichever phase later scales the service.
  — **Reversibility:** reversible to record. The scaling fix it implies is not, which
  is why recording it here is the cheap half.

### B. Disclosure — the accumulating account list (criterion 2)

- **D-05: ⛔⛔ THE DELIVERABLE IS PREVENTION OR ASSERTION — NEVER AN INVENTORY.** A
  natural-looking task here is "enumerate the Navigator tree and check it is short".
  ⛔ **Forbidden.** This repository is PUBLIC, `.planning/` is TRACKED and CI logs are
  world-readable, so a check that lists registered accounts **publishes exactly the
  client account numbers and broker server names criterion 2 exists to protect** —
  the proof-of-absence-publishes-the-thing class this repo already has a dated case
  of. MEASURED: `scripts/mt5-diag.sh` is the only in-repo gateway diagnostic, is
  fenced READ-ONLY, **never calls `login()`**, and **does not enumerate accounts
  today**. ⭐ That is a property to PRESERVE, not a gap to fill. Any check reports
  COUNTS and VERDICTS only.
  — **Reversibility:** one-way — a published client account list cannot be
  unpublished, and this repo's history is public.

- **D-06: CRITERION 2 IS DOWNSTREAM OF CRITERION 4 AND MUST SAY WHICH ANSWER IT
  INHERITS.** Accumulation is a consequence of the ownership model, not an independent
  bug: per-validation isolation prevents it structurally (an ephemeral terminal
  registers nothing that outlives it), while serialize-and-restore does not and needs
  its own purge or assertion. ⛔ Do not plan criterion 2 as a standalone item — a plan
  that does will either duplicate D-10's remedy or contradict it.
  — **Reversibility:** reversible.

### C. Salience — making an outage reach a human (criterion 3)

- **D-07: DETECTION IS BUILT AND IT WORKED. THE GAP IS THE SINK.** ⛔ Do not plan
  another detector. MEASURED: the durable episode record exists and is written by
  `analytics-service/services/mt5_session_episodes.py`
  (`MT5_SESSION_EPISODE_CRON_NAME`, `blind_run_escalation_threshold`,
  `_count_blind_reading`, `_clear_blind_run`) — Phase 164.6.4 built it — and a sweep
  for consumers finds **none outside that module**. The prober filed on the P1 issue
  within 80 seconds. ⇒ The deliverable is a path from a signal that already exists to
  a human who is not already looking.
  — **Reversibility:** reversible.

- **D-08: ⛔ DO NOT RAISE SALIENCE BY MAKING THE PROBER EXIT NON-ZERO.** The exit-0
  behaviour for status-class defects is DELIBERATE and documented: it exists so
  Railway's wait-for-CI does not skip the deploy. Flipping it couples an MT5 status
  defect to deploy gating and buys an outage-shaped outage. Whatever carries salience
  must **not** ride the prober's exit code.
  — **Reversibility:** costly — the deploy gate is a cross-system contract with the
  Railway wait-for-CI behaviour, not a local flag.

- **D-09: THE DEDUP-BY-LABEL BEHAVIOUR IS THE DEFECT, NOT THE FILING.** The issue
  dedups by label, so a fresh P1 lands under a title still carrying a defect date from
  2026-09-10 and reads as stale while the Actions view reads green. ⛔ Cross-link
  `MT5-WEDGE-OBS-01`; do NOT reopen it.
  — **Reversibility:** reversible.

### D. The ownership model — ⛔ THE ONE OPEN DECISION (criterion 4)

- **D-10: ⛔ DELIBERATELY LEFT OPEN. This is the ROADMAP's own criterion 4 and it says
  the choice must not be taken silently.** Three candidates:
  1. **Per-validation ephemeral terminal** — structurally prevents both the eviction
     (D-03) and the accumulation (D-05/D-06). ⛔ Costs the most: we do not build the
     terminal image today (see the constraint below), and an ephemeral terminal has no
     persistent Wine prefix, which is the exact property `164.6.5` D-07 rates one-way
     because it is what makes unattended auto-login work.
  2. **Pooled terminals** — bounds the blast radius without one-per-validation cost;
     inherits the same image-ownership problem N times over, and needs a placement
     rule nothing in the repo has today.
  3. **Serialize-and-restore on the one terminal** — cheapest in infrastructure, and
     ⛔ see D-11 before calling it cheap.
  ⛔ Whichever is chosen MUST satisfy D-02, D-03 and D-05, and MUST be recorded with
  the reason it beat the other two. The planner closes this behind a
  `checkpoint:decision`; ⛔ an agent must not close it by default.
  — **Reversibility:** one-way — options 1 and 2 make this repo the builder and
  operator of a container image it only consumes today, and unwinding that means
  re-pointing the deploy and re-establishing an upstream pin the broker's terminal
  self-update already makes unreliable.

- **D-11: ⛔ SERIALIZE-AND-RESTORE IS NOT THE CHEAP OPTION, AND MUST NOT BE PICKED AS
  ONE.** Restoring the prior occupant means a re-login on lease release — and a login
  **IS an account change**, which is precisely the operation 164.6.5 is investigating
  for wedging the terminal, and precisely the operation `scripts/mt5-diag.sh`'s own
  header warns re-clears `Enabled` while `[Experts] Account=1` is armed. ⇒ Option 3
  roughly **DOUBLES the rate of the known-dangerous operation**. Cost it as that, not
  as a lock change.
  — **Reversibility:** reversible as a costing note.

- **D-12: ⭐⭐ D-10 AND `164.6.5`'s D-05 ARE COUPLED AND MUST NOT BE DECIDED
  INDEPENDENTLY.** `164.6.5-CONTEXT.md` D-05 chooses a SUPERVISION remedy and its
  option 1 is *"wrap the image"* — our own thin Dockerfile over the third-party base.
  If 164.6.5 wraps, this phase's options 1 and 2 get materially cheaper, because the
  image-ownership cost is already paid. If 164.6.5 picks external supervision or a
  container restart policy, they get more expensive and option 3 gains ground. ⛔ A
  planner that reads only this file will mis-cost D-10. ⚠️ The dependency also runs
  the other way in TIME: 164.6.5 ships first by ROADMAP order, so its D-05 is likely
  to be resolved before this one — read its answer, do not re-derive it.
  — **Reversibility:** reversible as a note; it changes the inputs to a one-way call.

## Existing Code Insights

### Reusable Assets
- **`mt5_terminal_lease` is the right seam and it already exists** — every job kind
  and the interactive validate already contend on it. A restore-on-release remedy
  (D-10 option 3) has an obvious home in its `finally`, beside the epoch bump.
- **The epoch/occupancy fence** (`bump_mt5_terminal_epoch`, `begin/end_mt5_lease_occupancy`)
  is a working precedent for "tell a stale holder it is stale" — the shape D-03 needs,
  applied to a party that currently takes no lease.
- **The episode record** already gives criterion 3 a durable, production-proven write
  path. Only the reader is missing.

### Established Patterns
- **Exactly ONE terminal-lock registry** — a second one serializes nothing and every
  test still passes (`MT5CONC-02`). Any new keying must be byte-identical to
  `Mt5Client.terminal_key` (`f"{host}:{port}"`).
- **Bound the acquisition for interactive callers, leave batch unbounded** — the
  `wait_s=None` vs float split already encodes who may refuse to queue.
- **Bump before release, un-stamp second, release last** — the lease's documented
  ordering is load-bearing; ⛔ do not reorder it.
- **Status-class defects exit 0** in the prober, deliberately (D-08).

### Integration Points
- `routers/exchange.py` validate → `mt5_terminal_lease` → terminal IPC region.
- `mt5_session_monitor` 10-minute tick → `mt5_session_episodes` durable record → ⛔
  **no consumer** (D-07 is exactly this edge).
- ⛔ **The container image is NOT an integration point in this repo today**
  (`164.6.5` D-04). Whether it becomes one is D-10.
