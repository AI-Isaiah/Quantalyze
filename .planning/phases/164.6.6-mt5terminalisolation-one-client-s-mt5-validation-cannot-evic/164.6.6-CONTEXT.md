## Implementation Decisions

### A. What counts as an eviction, and the isolation model (ROADMAP criteria 1 and 3)

- **D-01: SCOPE = VALIDATION SWITCHES ONLY.** "Eviction" in criterion 1 means a switch of the job
  terminal caused by a key validation (a switch to an account that is not yet onboarded). Normal job
  switches between onboarded keys STAY, because the shipped read model logs the one terminal into
  each key's account per call and the MT5 API has no logout (RESEARCH Summary). Each of those
  switches is RECORDED against the holder it displaced (the handover record, plan 01), which answers
  criterion 1's "no error, no signal and no record against it" for the switches that remain.
  Beat: "every switch" (one pinned terminal per account, about $20.06 per account per month, a much
  larger phase). The founder did not name the 2026-09-21 displaced account; RESEARCH found no
  Quantalyze path that relies on the terminal staying on an account between leases.
  — **Reversibility:** reversible — widening to "every switch" later is a new phase that builds on
  the second-`terminal_key` routing this phase ships.

- **D-02: OPTION (b)+(f) — a SEPARATE VALIDATION-ONLY GATEWAY, WIPED AFTER EVERY USE, PLUS RECORDING
  ON THE JOBS TERMINAL.** A second gateway service (same image, its own volume, private networking
  only) serves only the two validate sites (`routers/exchange.py::_validate_mt5_key_probe`,
  `services/ingestion/mt5.py::Mt5Adapter.validate`), as a second key in the ONE lease registry
  (`services/mt5_concurrency.py::mt5_terminal_lease`), never a second registry. The job terminal's
  switches are recorded (f). ⚠️ The "wiped after every use" half is delivered by Phase 164.6.6.1
  MT5SCRUB, not here (see the split above).
  **Rejected: serialize-and-restore (c)**, because there is no home-account concept to restore to,
  the displaced account is still gone for the whole lease hold, every restore doubles the
  cross-account switches against the open `MT5-SWITCH-WEDGE-CAUSE-01` mechanism, and it does nothing
  for criterion 2. Also beaten: (a) ephemeral container per validation (cold start is minutes against
  a 75 s deadline; collapses into (b) once warm), (d) a second in-container instance (re-opens
  `tests/test_mt5_shutdown_roster.py::PERMITTED_SHUTDOWN_SITES`, most unknowns), (e) a managed
  provider (a third party custodies customer broker credentials).
  — **Reversibility:** one-way in practice — a second Railway service and routing onboarding through
  it commit infrastructure; removing the service and the routing returns to today, but only after
  the founder tears the service down.

- **D-07: H3 IS HIGH AND IS FIXED IN 164.6.6.** Founder's words: "authentication or network isolation
  on the rpyc channel, and reject master passwords before any login, each with a failing-first test."
  Two parts, both in scope here:
  1. **The rpyc channel** (T-134-03: unauthenticated, arbitrary remote code) gets authentication OR
     network isolation, on BOTH gateways, with a test that fails first.
  2. **Master passwords are rejected BEFORE any login.** Today `services/mt5_probe.py::run_probe`
     logs in with the typed password and `classify_trade_capability` rejects a master (trading)
     password only afterwards, so for that window a trade-capable session sits on a shared terminal.
     The fix must stop a master password reaching `login()` at all, with a test that fails first.
  ⚠️ **Feasibility flag for the planner, not a softening.** The MT5 Python API reveals trade
  capability only through a logged-in session (`account_info()` after `login()`). If no mechanism
  can tell a master password from an investor one before any login, the planner reports that back
  to the founder as a finding; it does not quietly narrow the decision (for example to "reject as
  early as possible after login").
  — **Reversibility:** reversible for the code; any channel-auth change on the gateway side is a
  founder infrastructure step.

### D-07 part 2 — feasibility finding and founder answer (2026-10-03)

⭐ **Amends D-07 part 2; the D-07 bullet above is unchanged and kept as lineage.** Source: plan 02
Task 2, founder AskUserQuestion on 2026-10-03.

**The finding (planner, read-only code reading, 2026-09-27).** Every signal that separates a master
(trading) password from an investor (read-only) one belongs to a logged-in session:
`classify_trade_capability` reads `account_info()["trade_allowed"]`, the `order_check` probe's
retcode and `terminal_info()["trade_allowed"]`, and all three exist only after `client.login(...)`
succeeds. Before a login the service holds only what the user typed (`parse_mt5_credentials`: a
login number, a password string, a broker server name), and the two password kinds have no format
difference. The MT5 Python API (via `mt5linux`) has no "check this password without logging in"
call, and `initialize(login, password, server)` is itself a login. So "reject master passwords
before any login" cannot be met with the tools this product has.

**The founder's answer, verbatim:** "Park after login (Rec.)", option id `park-after-login`.
What the founder was shown before answering: the park skips, with an alert, on timeouts and on a
hung or switched terminal; it costs one extra login per validation; and its premise (the house
account logged in on BOTH terminals at once) is NOT yet measured, because the job terminal is on a
client account today and will not be switched without the founder's say-so, while MT5 normally
allows one account on several terminals. The full option text, including every exit where no park
can run and the park-ceiling residual, is plan 02 Task 2's `park-after-login` option.

**What it means for plan 06.** Plan 06 implements the park: every validation that reached its
login attempt ends, inside the same lease and before the client is released, with the validation
terminal logged back into the house account. It is containment AFTER login, not rejection before
it. No park is sent while the probe thread may still be on the wire, so none runs on the wizard's
stage ceiling (the common hung-terminal exit), its end-to-end deadline, the worker's probe ceiling,
a fenced probe (`Mt5SessionAbandoned`), a mid-probe switch (`Mt5AccountMismatchError`), or with less
deadline left than the park needs (`_MT5_PARK_MIN_BUDGET_S`); each of those skips with an alert
naming the cause. Unset house credentials skip the park with an ERROR and an alert, never silently.

⚠️ **The park premise is NOT MEASURED, and the founder accepted it with that caveat.** Re-measured
2026-10-03 by the orchestrator from the analytics service over the private network, with
`initialize()` only (no login, nothing changed): the validation terminal reads authorized as the
house account, `connected` true, `trade_allowed` true, `tradeapi_disabled` false; the job terminal
reads `connected` true and `trade_allowed` true but is NOT authorized as the house account (it is on
a client account). "The house account logged in on both terminals at the same time" has therefore
never been observed. It is recorded as an accepted, unmeasured premise, never as passed. Plan 06's
tests must not rely on it. **Open live-check item (for verification, `human_needed`):** after
deploy, observe a park while the job terminal is on the house account, and confirm both terminals
stay authorized as the house account and the job terminal is not logged out by the park.

— **Reversibility:** reversible. The park is code in this repo; switching to
`accept-isolation-residual` later removes it, and nothing it does commits infrastructure or deletes
data.

H3-MASTER-PASSWORD-MODE: park-after-login

**Park alert level (founder, AskUserQuestion 2026-10-03, during plan 06: "Warn on glitch, page else
(Rec.)").** Plan 06 found that the plan's "a park that cannot run logs ERROR and alerts" collides
with D-15 ("a bridge blip never pages"): a validation that ends on a bridge blip then parks over the

so it measures the blip path, not the unset-credentials path.
