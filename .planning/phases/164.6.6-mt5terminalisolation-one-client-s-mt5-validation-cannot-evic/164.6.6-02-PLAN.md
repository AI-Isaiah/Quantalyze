  <context>
**The finding (planner, 2026-09-27, read-only code reading).** Everything that separates a master
(trading) password from an investor (read-only) one is a property of a LOGGED-IN session:
- `classify_trade_capability` reads `account_info()["trade_allowed"]`, the `order_check` probe's
  retcode and `terminal_info()["trade_allowed"]`. All three exist only after `client.login(...)`
  has succeeded; `run_probe` calls `client.login` first for exactly that reason.
- Before a login, the service holds only what the user typed: a login number, a password string and
  a broker server name (`parse_mt5_credentials`). The two password kinds have no format difference.
- The MT5 Python API (via `mt5linux`) offers no "check this password without logging in" call, and
  `initialize(login, password, server)` is itself a login.
- The broker-side tools that know a password's kind (the MT5 Manager API) belong to the broker, not
  to this product.
So "before any login" is not reachable with the tools this product has. Per CONTEXT D-07 this goes
to the founder as a finding, not as a quiet narrowing.

**What already bounds the exposure after this phase, whichever option you pick:** plan 04 moves
every validation to the validation-only terminal (D-02), so a master password no longer reaches the
terminal that serves live jobs; plan 05 part 1 makes the analytics service refuse to dial a gateway
over anything but the private network (D-07 part 1). What remains is a trade-capable session on the
VALIDATION terminal from the moment `login()` succeeds until the next login there, plus the saved
password on its disk (the disk half is Phase 164.6.6.1's scrub, D-03).

**Recommendation (not a decision): `park-after-login`.** It ends the trade-capable session inside the
same lease, seconds after it began, on every path where the probe thread has come back, including a
probe that raised after login (where the verdict is never known). ⚠️ Its known limit, stated so the
choice is made on the true shape: when the wizard's end-to-end deadline fires while the probe is
still blocked on the gateway, that thread still owns the connection and cannot be cancelled; a
second login on the same client would put two callers on one MT5 pipe (the wedge class 164.6.5
exists to avoid). So on that path NO park runs: an alert fires with a named cause and the session
lasts until the next login on the validation terminal. Its cost is one extra login on the
validation terminal per validation, which is a switch on a terminal that serves no live job. It
relies on plan 03's S-01 reading: the validation terminal can be logged into the house account while
the job terminal is too. If S-01 was not `authorized`, `park-after-login` is not available and the
choice is between the other two.
  </context>
