## The eviction mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| Add a mutex around the validate path | The intuitive reading of "one client evicts another" — no serialization exists | |
| Restoration, not exclusion — the lease is held and the terminal is simply left switched | Serialization exists and worked; nothing owns the resting state between leases | ✓ |
| Treat it as a 164.6.5 wedge symptom | Fold into the availability phase | |

**Resolved:** option 2.
**Notes:** Decided by measurement, and it reverses the obvious reading.
`services/mt5_concurrency.py` already holds a single-source per-terminal lock registry,
and `routers/exchange.py` ALREADY takes `mt5_terminal_lease` around the validate
region. The eviction happened **with the lease correctly held**, so "add a lock" would
have been a no-op at best and a second-registry regression at worst — the module's own
docstring warns that a second registry serializes nothing while all tests still pass.
The design note in `routers/exchange.py` states the accepted behaviour verbatim: the
terminal *"cycles through hundreds of accounts across a day"*. Became D-01, D-02.

A second finding fell out of the same read: the evicted party **never held a lease at
all**, so the existing epoch fence structurally cannot reach it. Became D-03.

A third, unlooked-for: the lease is `asyncio.Lock`-backed and the shipped
`analytics-service/Dockerfile` runs `uvicorn` with **no `--workers`**, so the lock is
real only because exactly one process exists. Became D-04.

## Disclosure — the accumulating account list

| Option | Description | Selected |
|--------|-------------|----------|
| Build an inventory check that enumerates registered accounts | Prove the list is short | |
| Prevention or assertion only — counts and verdicts, never a listing | Never let the list reach a log | ✓ |
| Defer entirely to the ownership decision | Say nothing until criterion 4 is answered | |

**Resolved:** option 2, with option 3 folded in as a dependency note.
**Notes:** Option 1 is the trap, and it is an attractive one: a check that proves the
account list is bounded would **publish the client account numbers and broker server
names** the criterion exists to protect, into a public repo with world-readable CI
logs. This repo has a dated case of a proof-of-absence publishing its own subject.
MEASURED that `scripts/mt5-diag.sh` is READ-ONLY, never calls `login()`, and does not
enumerate accounts today — a property to preserve rather than a gap to fill. Became
D-05. The dependency on the ownership choice became D-06.

## Salience — an outage reaching a human

| Option | Description | Selected |
|--------|-------------|----------|
| Add a detector | Build new monitoring for the wedge | |
| Give the existing signal a reader | Detection already works; nothing consumes the record | ✓ |
| Make the prober exit non-zero | Let the red CI check carry the alarm | |

**Resolved:** option 2. Option 3 was actively ruled OUT, not merely passed over.
**Notes:** Detection and filing both worked during the incident — the prober filed on
the P1 issue within 80 seconds. MEASURED that the durable episode record written by
`services/mt5_session_episodes.py` has **no consumer outside its own module**, so the
deliverable is a sink, not a detector (D-07). Option 3 was rejected on a documented
design rationale: status-class defects exit 0 deliberately so Railway's wait-for-CI
does not skip the deploy, and flipping that couples an MT5 status defect to deploy
gating (D-08). The specific defect is the label-dedup putting a fresh P1 under a stale
title (D-09).

## The ownership model

| Option | Description | Selected |
|--------|-------------|----------|
| Per-validation ephemeral terminal | Structurally prevents eviction and accumulation | |
| Pooled terminals | Bounds blast radius; needs a placement rule | |
| Serialize-and-restore on the one terminal | Cheapest infrastructure | |
| ⛔ LEFT OPEN for the planner behind a `checkpoint:decision` | Founder decision; inputs incomplete | ✓ |

**Resolved:** deliberately NOT resolved.
**Notes:** The ROADMAP names this a founder decision that must not be taken silently,
and it is rated one-way — options 1 and 2 make this repo the builder and operator of a
container image it only consumes today. Two costing findings were recorded so the
choice is made on real numbers rather than intuition:

- **Option 3 is not the cheap one.** Restoring the prior occupant means a re-login per
  lease release, and a login IS an account change — the exact operation 164.6.5 is
  investigating for wedging the terminal. It roughly DOUBLES the rate of the
  known-dangerous operation (D-11).
- **This decision is COUPLED to `164.6.5`'s D-05** and must not be taken independently.
  If 164.6.5 picks "wrap the image", options 1 and 2 get materially cheaper because the
  image-ownership cost is already paid; if it picks external supervision, they get more
  expensive (D-12).

Became D-10, with D-11 and D-12 as its inputs.
