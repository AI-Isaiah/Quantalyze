Each one below either sits on a misconfiguration path that is latent today (the configured hosts are private, and both validation variables are set and read back present) or narrows a residual the phase already documents. None defeats one of the phase's truths on the configured system.

- **WR-03 (W-1 residual):** the worker park's ceiling is `_MT5_PROBE_TIMEOUT_S` (35 s), but a park makes two round-trips, `initialize` and then `login`, each bounded at 30 s. **The comment in `services/ingestion/mt5.py`, saying the ceiling "already has the inner-rpyc-bound-fires-first ordering", is false for a two-round-trip park.** A ceiling that fires mid-park can let an abandoned house login land on the next validation's session. The wizard has the same issue: one 60 s stage against 2 × 55 s.
- **WR-05:** nothing refuses a validation pair that equals or aliases the job pair. That misconfiguration silently restores the eviction, and an alias spelling also splits the lease key. N-01 remains the infrastructure check.
- **M-3:** a non-private validation host pages with "unset or malformed". The true cause is logged once at WARNING.
- **M-4:** the park's Sentry throttle is keyed by cause only, unlike the sibling D-05 alert, which is keyed per site. One site's capture silences the other's for an hour.
- **M-5:** the glitch class is a negative definition, the classifier's catch-all. A persistent park failure therefore never escalates. This finding compounds the gap above. On its own, the escalation would need a founder sign-off.
- **M-6:** the park's outer `except Exception` logs ERROR and sends no capture, and a `CancelledError` mid-park bypasses every park alert. **Why this is a known limit and not a gap against "every other failure still pages":** that handler is a catch-all for exceptions the block is written never to raise, because `report_park_skipped` and `park_on_house_account` both never raise. It still emits an ERROR line, so it is never silent. Cancellation requires a redeploy or a 30-minute dispatcher budget. WR-04, by contrast, is the designed, tested, common path deciding its alert level against the decision's condition.

### Gaps Summary

There is one gap, and it is narrow. It concerns the alert level of a failed park, not whether the park runs.

The founder's 2026-10-03 answer allowed WARNING only for a park that fails "for the same bridge-glitch reason **the validation hit**". The code and its test apply the WARNING to any glitch-class park failure, including one after a clean validation that may just have detected a master password. That is exactly the case where a trade-capable session stays on the validation terminal. Because the glitch class is the classifier's catch-all (M-5), that case pages no one, however often it repeats.

**Fix (small):**
- Carry a `validation_hit_glitch` flag from each site's transient-upstream arm into `park_on_house_account`.
- Downgrade only when both the validation and the park glitched.
- Split the test so the clean-validation case fails first.
