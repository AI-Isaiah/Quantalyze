## User Constraints (from CONTEXT.md)

### Locked Decisions

**A. The eviction — what is actually missing (it is not a lock)**
- **D-01:** The mutex is NOT missing. `analytics-service/services/mt5_concurrency.py` is the single per-terminal lock registry (`_MT5_TERMINAL_LOCKS`, `_mt5_terminal_lock_for`, `mt5_terminal_lease`), and `analytics-service/routers/exchange.py` already takes it on the interactive validate path. The eviction happened WITH the lease correctly held. Do not plan "add a lock."
- **D-02:** What is missing is RESTORATION, not exclusion. The lease guarantees no two callers occupy the IPC region at once; it guarantees nothing about which account the terminal is left logged into when the body exits. Subject: the terminal's resting state between leases.
- **D-03:** The evicted party never held a lease — that is the structural gap. A broker session that is merely authorized is terminal-side state held by no Python caller; no epoch bump reaches it. Either the authorized session becomes a modelled occupant, or eviction is made harmless by restore. Adding another epoch bump does not close this.
- **D-04:** The lease is process-local (this is load-bearing and nowhere else stated). The registry holds `asyncio.Lock` objects; `analytics-service/Dockerfile` starts `uvicorn main:app` with no `--workers` flag, so exactly one event loop exists. `--workers 2`, a second replica, or an out-of-process caller silently serializes nothing while every test still passes. This phase must state the assumption explicitly and make it observable.

**B. Disclosure — the accumulating account list (criterion 2)**
- **D-05: THE DELIVERABLE IS PREVENTION OR ASSERTION — NEVER AN INVENTORY.** Enumerating the Navigator tree "to check it is short" is forbidden — the repo is public, `.planning/` is tracked, and such a check would publish client account numbers and broker server names. `scripts/mt5-diag.sh` is read-only, never calls `login()`, and does not enumerate accounts today — preserve that property. Any check reports COUNTS and VERDICTS only.
- **D-06:** Criterion 2 is downstream of criterion 4 and must say which answer it inherits. Per-validation isolation prevents accumulation structurally; serialize-and-restore does not and needs its own purge or assertion. Do not plan criterion 2 as a standalone item.

**C. Salience — making an outage reach a human (criterion 3)**
- **D-07: DETECTION IS BUILT AND IT WORKED. THE GAP IS THE SINK.** Do not plan another detector. The durable episode record is written by `analytics-service/services/mt5_session_episodes.py`; a sweep for consumers finds none outside that module. The prober filed on the P1 issue within 80 seconds. The deliverable is a path from a signal that already exists to a human who is not already looking.
- **D-08:** Do NOT raise salience by making the prober exit non-zero. Exit-0 for status-class defects is deliberate (so Railway's wait-for-CI does not skip the deploy). Whatever carries salience must not ride the prober's exit code.
- **D-09:** The dedup-by-label behaviour is the defect, not the filing. Cross-link `MT5-WEDGE-OBS-01`; do NOT reopen it.

**D. The ownership model — the one open decision (criterion 4)**
- **D-10: DELIBERATELY LEFT OPEN.** Three candidates: (1) per-validation ephemeral terminal, (2) pooled terminals, (3) serialize-and-restore on the one terminal. Whichever is chosen MUST satisfy D-02, D-03 and D-05, and MUST be recorded with the reason it beat the other two, behind a `checkpoint:decision`. An agent must not close it by default.
- **D-11:** Serialize-and-restore is NOT the cheap option and must not be picked as one. Restoring the prior occupant means a re-login on lease release — and a login IS an account change, precisely the operation 164.6.5 is investigating for wedging the terminal. Option 3 roughly doubles the rate of the known-dangerous operation. Cost it as that.

If 164.6.5 picks external supervision or a restart policy, they get more expensive and option 3 gains ground. 164.6.5 ships first by ROADMAP order — read its answer, do not re-derive it.

### Pattern 1: The rate-limited Sentry escalation clone (criterion 3, primary recommendation)

**What:** A small, reusable shape already used three times in this exact service: log unconditionally at `error` level (the RATE is itself operator evidence), then escalate to Sentry at most once per window, wrapped in a bare `try/except: pass` so a Sentry transport failure can never mask the path being reported on.

**When to use:** Any time an in-process signal needs to reach a human without a new detector, a new migration, or a new PROD live-op session — exactly criterion 3's shape (D-07: "the gap is the sink").

**Example (the THIRD existing instance of this exact pattern in this service — the one to clone for a fourth):**
```python
# Source: analytics-service/routers/cron.py — _escalate_prober_cadence_gap
# [VERIFIED: analytics-service/routers/cron.py:2239-2282]
_PROBER_CADENCE_ALERT_WINDOW_S = 3600.0
_last_prober_cadence_alert_at: dict[str, float] = {}

def _escalate_prober_cadence_gap(alert: ProberCadenceAlert) -> None:
    logger.error(
        "prober_cadence_alert: cron_name=%s gap_minutes=%s ceiling=%s "
        "detected_at=%s — prod-prober contact exceeded the measured cadence "
        "ceiling",
        alert.cron_name, gap_display, alert.ceiling, detected_display,
    )
    now = time.monotonic()
    last_at = _last_prober_cadence_alert_at.get(alert.cron_name)
    if last_at is not None and (now - last_at) < _PROBER_CADENCE_ALERT_WINDOW_S:
        return
    _last_prober_cadence_alert_at[alert.cron_name] = now
    try:
        sentry_sdk.set_tag("prober_cadence_alert", alert.cron_name)
        sentry_sdk.capture_message(
            f"prod-prober cadence alarm: {alert.cron_name} last contact "
            f"{gap_display} min ago (ceiling {alert.ceiling}, detected "
            f"{detected_display})",
            level="error",
        )
    except Exception:
        pass  # never mask the path this is reporting on
```
The earlier instances of the same shape are `routers/internal.py:_alert_kek_unavailable` and `routers/cron.py:_escalate_prober_cadence_gap` — both re-verified BY SYMBOL by the orchestrator 2026-09-22 and both present.

### Pattern 2: The PROD pg_cron cadence-check pattern (criterion 3, heavier alternative)

**What:** A `SECURITY DEFINER` plpgsql function, registered via a founder-gated live `cron.schedule(...)` session (never inside a migration, per this repo's settled convention), that reads a staleness signal from `public.cron_runs` and, on a stale verdict, posts to the analytics service over `net.http_post`, landing on the same `/api/prober-cadence-alert` → Sentry terminus as Pattern 1.

**When to use:** When the signal to watch genuinely needs to live outside the `analytics-service` process's own liveness (e.g., "is `analytics-service` itself still ticking at all" — which an in-process check structurally cannot answer about itself). This is NOT that case for criterion 3: the blind-run counter already lives inside `analytics-service`, which is the same process that would run the escalation, so Pattern 1 is strictly cheaper for this specific signal.

**Example (the live, working instance — `[VERIFIED: supabase/migrations/20260918120000_prod_prober_cadence.sql:50-149]`, quoted in Sources):**

⚠️ **Do not copy this pattern's gap-since-last-row semantics onto `mt5_session_episode` unmodified.** `prod_prober_cadence_check` works because the prober writes a fresh row EVERY hourly tick regardless of outcome, so "no fresh row" cleanly means "the prober stopped." `mt5_session_episodes.py` writes rows only on state TRANSITIONS, never per tick (`[VERIFIED: analytics-service/services/mt5_session_episodes.py — module docstring, quoted below]`: "one row per session-state TRANSITION"), so a long, healthy, unbroken AUTHORIZED period produces NO new rows and would look identical to staleness under a naive copy of this gap check. This is documented as Open Question 2, not resolved here — it is exactly why Pattern 1 (reading the in-process counter, which DOES update every tick regardless of transition) is the better host for this specific signal.

### Anti-Patterns to Avoid
- **A second `dict[str, asyncio.Lock]` terminal registry:** explicitly forbidden by `mt5_concurrency.py`'s own docstring (`MT5CONC-02`) — it hands out functioning `Lock` objects that serialize nothing because two registries mean two different `Lock` instances per key.
- **Flipping the prober's exit code to raise salience:** forbidden by D-08 — it couples an MT5 status defect to Railway's deploy-skip-on-red-CI behavior, a cross-system contract this phase must not touch.
- **An inventory-shaped fix for criterion 2:** forbidden by D-05 — a check that lists registered accounts to "prove the list is short" publishes exactly the client account numbers and broker server names the criterion protects.
- **Treating `latest_cron_success()` as an automated alert:** it is not. Its own migration comment, corrected 2026-09-18, states it "has NO programmatic caller anywhere in this tree ... its one reader is a human running `docs/demos/pre-flight-checklist.md` by hand" (`[VERIFIED: supabase/migrations/20260918120000_prod_prober_cadence.sql:257-263]`). A planner reaching for it as criterion 3's remedy would be reusing a documented dead end.

The work here is almost entirely "wire an existing signal to an existing reader," not "build."

## Common Pitfalls

### Pitfall 1: Mistaking "the lease is held" for "the terminal is safe"
**What goes wrong:** A planner reads the incident as a lock bug and proposes strengthening or duplicating the lease.
**Why it happens:** The natural mental model for "two users stepped on each other" is a missing/broken mutex. This incident's actual shape — a clean, successful, one-second handover that still destroyed a live session — is counter-intuitive precisely because the lock worked perfectly.
**How to avoid:** Re-read D-01/D-02/D-03 before writing any task. The lease already correctly serializes ACCESS; the defect is about STATE that outlives the lease's own holder.
**Warning signs:** Any task description containing "add a lock," "widen the lease," or "make the lease cover more."

### Pitfall 2: Costing D-10 option 3 as "cheap" because it needs no new infrastructure
**What goes wrong:** Serialize-and-restore looks like the free option because it needs no Dockerfile, no image ownership, no pooling logic.
**Why it happens:** Its cost is HIDDEN in a different axis — operation frequency on a known-dangerous verb, not infrastructure surface.
**How to avoid:** D-11 names the actual cost: restoring the prior occupant means a re-login on every lease release, and a login IS an account change — the exact operation `164.6.5` is investigating for wedging the terminal, and the exact operation `scripts/mt5-diag.sh`'s own header warns re-clears `Enabled` while `[Experts] Account=1` is armed (`[VERIFIED: scripts/mt5-diag.sh:9-13]`, quoted below). Whether the checkbox is currently armed was separately measured by `164.6.5` D-15/164.6.4-UAT: `[Experts] Account=1`-style re-clear is GATED by "Disable algorithmic trading when the account has been changed," which was found UNCHECKED on 2026-09-16 (`[CITED: 164.6.5-CONTEXT.md D-15, quoting 164.6.4-UAT]` — this research did not itself re-read the terminal's live settings, per the no-VNC/no-login constraint, so this is carried forward as CITED, not independently re-verified this session). Cost option 3 as "roughly doubles the rate of the known-dangerous operation," per D-11's own framing, not as infrastructure-free.

Full text of the mt5-diag.sh warning, quoted verbatim `[VERIFIED: scripts/mt5-diag.sh:9-13]`:
```
# ⛔ READ-ONLY, and deliberately so: it calls initialize() + terminal_info() and
# NEVER login(). A login() is an "account change"; while
# `[Experts] Account=1` is armed, MT5 re-clears `Enabled` on every account
# change, so a probe that logged in would itself re-break the thing it is
# measuring.
```

### Pitfall 3: Copying `prod_prober_cadence_check()`'s gap-since-last-row logic onto `mt5_session_episode` unmodified
**What goes wrong:** A naive "reuse the pattern" instinct writes a PROD pg_cron function that reads `MAX(completed_at) WHERE cron_name = 'mt5_session_episode'` and alarms on staleness, exactly mirroring the prober's own check.
**Why it happens:** The prober's version is the freshest, most recently proven precedent in the repo, and copying a working pattern feels safe.
**How to avoid:** `mt5_session_episodes.py` writes rows on TRANSITIONS only (`[VERIFIED: analytics-service/services/mt5_session_episodes.py:1-5]`, module docstring: "every `authorized ↔ dark` transition... written as ONE ROW PER TRANSITION"). A long, healthy, unbroken authorized session produces zero new rows for however long it lasts, which a gap-since-last-row check reads identically to a genuinely dark terminal nobody is watching. This is the load-bearing reason Pattern 1 (the in-process counter, which increments on every `not_measured` TICK regardless of transitions) is the better host for this specific alarm — see Open Question 2 for what remains unresolved even there.

### Pitfall 4: Treating `assert_session_authorized()` as if it can answer "whose account"
**What goes wrong:** A planner reaches for `Mt5Client.assert_session_authorized()` (the credential-free detector already shipped in 164.6.2) as a way to detect an eviction "before it happens," and extends it to identify or log which account is currently authorized.
**Why it happens:** It is the closest existing thing to a terminal-side "who's home" signal, and research question 3 explicitly asked whether one exists.
**How to avoid:** By design (`[VERIFIED: analytics-service/services/mt5_client.py:1266-1320]`, `assert_session_authorized` docstring, quoted below) it is DELIBERATELY credential-free and answers only a binary "is *any* account authorized, and if not, which fault code" — never *which* account. Extending it to identify the account would require either a credential (defeating its whole design purpose, per its own docstring: "A detector that carried a credential could not be used to DECIDE whether to send one") or an account-list read, which collides directly with D-05's disclosure fence. It is a real, cheap, already-proven precedent for "detect a state change without a login" (useful groundwork for D-10 option 3's restore-on-release path, or for a lighter-weight "session existed but nobody in our process owns it" check), but it structurally cannot answer "whose."

Quoted verbatim `[VERIFIED: analytics-service/services/mt5_client.py:1266-1320]`:
```python
def assert_session_authorized(self) -> None:
    """Assert that the terminal currently HAS an authorized broker account —
    the CREDENTIAL-FREE detector (criterion 1(a), RESEARCH question FOUR).
    ...
      * ``-6`` — no account is authorized. ... this is the ONE fault this
        phase heals — by re-running ``initialize()`` in its CREDENTIALED form
      * ``-10003`` / ``-10004`` / ``-10005`` — IPC faults. ...
    ⛔ NO credential is passed, and none may ever be added. A detector that
    carried a credential could not be used to DECIDE whether to send one —
    it would already have sent it ...
    """
```

## Open Questions

1. **Does an authorized-but-leaseless session leave ANY terminal-side signal that could make eviction detectable, even if not preventable, before D-10 ships?**
   - What we know: `Mt5Client.assert_session_authorized()` (credential-free) can already distinguish "some account is authorized" from "-6, no account authorized" from IPC faults (`-10003`/`-10004`/`-10005`) — `[VERIFIED: analytics-service/services/mt5_client.py:1266-1320]`. It cannot identify WHICH account, by design.
   - What's unclear: Whether comparing "who WE last logged in as" (something `routers/exchange.py`'s trace already knows, in-process, for the duration of ITS OWN lease) against a later `assert_session_authorized()` reading FROM A DIFFERENT CALLER's tick could construct a "someone else is now authorized where we left client X authorized" inference — without ever reading or logging an account number, only a boolean "state changed since my own release" per terminal generation (the existing epoch counter may already carry enough information for this).
   - **Falsifiable test for the planner:** Read `mt5_client.py`'s epoch/occupancy mechanism (`bump_mt5_terminal_epoch`, `begin_mt5_lease_occupancy`) end to end and determine whether the epoch value at the time client A's lease released could be compared, at a later tick, against the CURRENT epoch to produce a true/false "somebody else has held the terminal since I left" signal with zero new credential and zero account-identifying data. If this is possible without adding a data field, it is a real, cheap building block for D-10 option 3 (or even as a standalone pre-C4 mitigation); if the epoch is bumped by every legitimate handover too (including a client's own retry), the signal is too noisy to be useful and this question is answered NO.

2. **Can a durable, per-tick (not per-transition) staleness signal be added to `mt5_session_episodes.py`'s sink cheaply enough to make Pattern 2 (the PROD pg_cron alternative) viable, or does Pattern 1 (in-process) strictly dominate for this specific alarm?**
   - What we know: The in-process blind-run counter (`_CONSECUTIVE_NOT_MEASURED_READINGS`) already updates every tick and is the thing that actually flips INFO→WARNING. It is NOT durable (module-global, reset on redeploy, per the module's own comment about a redeploy restarting a blind run's count).
   - What's unclear: Whether the non-durability of the in-process counter (Pattern 1) is an acceptable trade against the semantic mismatch of copying Pattern 2's gap-since-last-row check onto a per-transition table.
   - **Falsifiable test for the planner:** State explicitly, in the plan, which of the two failure modes is being accepted: Pattern 1 accepts "a redeploy during a dark window resets the blind counter and could delay escalation past the intended threshold" (bounded by how often `analytics-service` redeploys, which is measurable from Railway deploy history); Pattern 2 (if attempted) would need to accept or solve "a long healthy authorized period looks identical to staleness" (Pitfall 3) — if no sound redesign is found for Pattern 2's semantics, Pattern 1 is the only sound choice and this question closes in Pattern 1's favor by elimination, not by preference.

The planner must choose it"). `164.6.5` is planned but not fully executed (parked behind founder gates, per D-13 of THIS phase's own CONTEXT.md).
