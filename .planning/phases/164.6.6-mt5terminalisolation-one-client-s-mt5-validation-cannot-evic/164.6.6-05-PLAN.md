Purpose, part 1 (the channel). The rpyc bridge is an unauthenticated arbitrary-remote-code channel
(T-134-03; `deploy/mt5-gateway/railway-gateway.md` HARD CONSTRAINT), and after plan 04 there are two
of them. D-07 asks for "authentication OR network isolation". The planner's choice (CONTEXT
`### Claude's Discretion`, the H3 channel mechanism) is network isolation, because it is the only
branch this repo can deliver:
- Authentication: `mt5linux` 0.1.9 builds its connection with `rpyc.classic.connect(host, port)`
  inside `MetaTrader5.__init__` (see `services/mt5_client.py::_default_connect`'s docstring), and the
  server side is `python.exe /tmp/mt5linux/server.py --host 0.0.0.0 -p 8001`, written by the package
  inside the prebuilt `gmag11/metatrader5_vnc` image (runbook "The live spike that proved the
  mechanism"). An rpyc authenticator or SSL requires that server to be started with it, which means
  owning or patching the image, which 164.6.5 rejected (runbook "Why Option 2 beat the other two").
  A TLS sidecar needs a second process in the same container: the same image change.
- Network isolation: Railway private networking already carries the channel. What was missing is a
  CHECK: nothing stopped the analytics service dialling a public host (a Railway public domain, a TCP
  proxy, an IP). This plan adds that check at the one real transport factory, and the founder's N-01
  reading (plan 03) covers the gateway side.

Purpose, part 2 (master passwords). Plan 02 recorded that "reject before any login" is not reachable
with the MT5 API (every trade-capability signal is post-login), and the founder's answer as
`H3-MASTER-PASSWORD-MODE`. Task 3 implements that answer and nothing wider.

and both endpoint readers, a single-transport AST pin, a runbook posture note, and (mode
`park-after-login`) `park_on_house_account` called from both validate sites.

reader → site → refusal → D-05 alert) and proves the transport factory itself refuses.

`requirements:` id `164.6.6-CH3` is this phase's id for the H3 work.
