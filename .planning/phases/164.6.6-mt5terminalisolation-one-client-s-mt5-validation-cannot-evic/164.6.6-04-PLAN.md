<objective>
Route both validate sites to the validation terminal (D-02 = option (b)), so an onboarding
validation can no longer switch the terminal that serves live jobs. This is the part of criterion 1
that D-01 scopes in: validation switches.

Purpose: the lease registry is already keyed by `terminal_key`, so a second terminal is a second
key with its own lock, epoch and occupancy stamp (RESEARCH "What 137 and 164.6.5 already give each
option"). The code change is small; the gates that prove it are the work.

Output: a shared validation-endpoint reader, both validate sites routed through it with their own
misconfiguration dispositions, the D-05 alert on both refusal paths, a routing pin, and the founder
setting the two env vars before the change deploys.

D-05 (founder, 2026-09-27): "refuse the validation with a clear error and an alert; never fall back
to the jobs terminal". The alert mechanism is the planner's choice (CONTEXT `### Claude's
Discretion`): the repo's existing paging shape, reused, never a new vendor. Measured at planning:
`routers/internal.py::_alert_kek_unavailable` and `routers/cron.py::_escalate_prober_cadence_gap`
both log at ERROR on every occurrence, then `sentry_sdk.set_tag` + `sentry_sdk.capture_message(...,
level="error")` at most once per window, inside `try/except: pass`; `routers/cron.py` records that
`SENTRY_DSN` is set on the analytics service (founder-measured 2026-09-18, presence only) and
carries the caveat that delivery depends on it staying set.

Criterion 2 is met only IN PART by this phase (see must_haves): this plan is what stops un-onboarded
accounts reaching the job terminal; wiping is Phase 164.6.6.1's.

Spec-less probe fallback skipped: phase has no requirement IDs to probe (visible skip). The
`requirements:` IDs above are RESEARCH's proposed IDs.

Scope justification (plan-check revision 1 warning: 11 files against a warning line of 10, estimate
80,000 of 100,000, confidence low). Kept as ONE plan on purpose, not split:
- Only three files carry new production logic: `services/mt5_relogin.py`, `routers/exchange.py`
  and `services/ingestion/mt5.py`. `src/lib/wizardErrors.ts` is a comment-only edit. The other
  seven are test files, and four of them (`test_status_contract_exchange_internal.py`,
  `test_validate_key_venue_transient.py`, `test_mt5_validate_parity.py`,
  `test_mt5_internal_probe.py`) only get existing gateway-env fixtures re-cut onto the validation
  pair. Those edits are mechanical.
- The re-cuts cannot move to another plan. Once Task 1 routes the wizard to the validation pair,
  every validate-path fixture that sets only the job pair goes red. So each re-cut belongs in the
  same commit as the routing change it follows.
- Splitting buys no parallelism. Task 2 calls the D-05 alert helper that Task 1 writes in
  `services/mt5_relogin.py`, and Task 2's verify command runs Task 1's test files. A second plan
  would therefore sit one wave later, and plans 05, 06 and 08 all depend on this one, so each would
  move back one wave for no safety gain.
- The 0.80 ratio is measured against a zero-sample, low-confidence estimate.
- Executor mitigation: each task commits atomically, so the Task 1 tracer is durable before Task 2
  starts. If context runs short after Task 1, stop at that commit and hand back naming Task 2,
  rather than compressing it.
</objective>
