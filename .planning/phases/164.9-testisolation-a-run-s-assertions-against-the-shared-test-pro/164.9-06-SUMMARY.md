## Accomplishments

### Task 1 — two keys, two units, and zero exclusion removed

`scripts/shared-test-db-keys.sh` is the ONE place the new constant is written. It exports `SHARED_TEST_SCHEMA_APPLY_INFLIGHT_KEY`, an acquire emitter using `pg_try_advisory_lock` (an announcement must never block the apply it announces), and a **read-only** probe that queries `pg_locks` for the decomposed identifiers — ⛔ never a try-and-release, which would ACQUIRE the key whenever it is free, the exact opposite of a read. Its `--self-test` derives its own check count and proves the constant is a single live line, that it differs from the mutual-exclusion key, that it sits in the positive 32-bit range the probe's `objid` comparison assumes, and that the probe's generated SQL contains none of eleven data-modifying or lock-acquiring verbs.

The mutual-exclusion key is **untouched**. Not one of its call sites was rewritten; its occurrence counts are pinned and unmoved at 27 in `ci.yml` and 7 in `supabase-migrate.yml`. The file's header records that asymmetry as a decision rather than leaving a reader to wonder which key was forgotten, and records why giving the writer its OWN lock would have been the wrong fix (it would make the writer stop excluding the readers — the one collision Phase 164.8 Area 4 recorded as CORRUPTING a reading).

The `supabase-migrate.yml` edit carries an in-file statement, as CONTEXT Area 3 requires, that **it is a planned isolation fix**: it adds an announcement and removes no gate, relaxes no condition and clears no red. It is not the act `CLAUDE.md` forbids by name.

### Task 2 — ordering by a checked fact, not a won race

`sql-tests`, `python` and `e2e-seeded` each gained `Wait for the TEST schema apply to conclude (merge pushes only)` **immediately before** their `Acquire shared-test-db mutex` step (verified by step INDEX, not by line proximity). The step's `if:` conjoins each job's own existing gating with `github.event_name == 'push'`, explicitly rather than inherited.

Each poll makes two reads: the in-flight flag (the only signal that sees `test-restore-from-baseline.yml`, which produces no Actions run on the commit) and the Actions API for the `apply-test` **job** on this exact head commit. Three outcomes, one line each: `apply-concluded` (proceed; an unsuccessful finish says so and still proceeds, because reddening here would duplicate an existing red check under the wrong job's name), `no-apply-run` (nothing to order against), `wait-exhausted` (RED, naming which condition was still true, pointing at the runbook). No message interpolates raw API output, a DSN, a host or a username.

An **appearance grace** distinct from the wait budget keeps the common case cheap: `supabase-migrate.yml` only triggers on a push touching `supabase/migrations/**`, so on most merges no run will ever appear and the step must not pay the congested case's budget.

Job-level `permissions:` on all three jobs grants `actions: read` and **restates** `contents: read`, because a job block replaces the workflow block rather than merging with it. Zero `needs:` edges were added.

Docs: runbook section 7 (dated, with the prior six sections kept as lineage, plus a pointer in the header so a reader of section 1 is not stranded) gives the two keys and their units, states the second is a flag nobody blocks on, tabulates the three outcomes against what an operator does about each, and carries a corrected **file-level** census of the mutual-exclusion key that is wider than section 1's three jobs. `CONTRIBUTING.md` names both keys beside each other. `mutex-probe.yml`'s header now states which key it exercises and that a green run is **no evidence** about the flag; its triggers are unchanged.

### Task 3 — a retry that recovers, exhausts, and refuses to launder a defect

The bounded retry sits **on top of** the three named measurement failures. After the budget an unreadable read still reaches its `MEASURE_FAIL` and still exits non-zero — that is what keeps it distinguishable from a clean read, and no silent fallback was restored.

Only a **failed invocation** is retried. A read that succeeded and returned no row, or a non-number, is a failure about the ANSWER and is still reached on the FIRST attempt; an arm asserts exactly that by reading the attempt count out of the message text. Each retry prints one line, on **fd 9** — every call site either captures the seam's stderr into a file it withholds or discards it, so a retry notice on stderr would be invisible on precisely the path this exists for, and on the `ledger_rows` path would also inflate the withheld-line count the failure reports.

The arm ratchet moved 11 → 13 in the same commit as the arms, with its dated MEASURED line and its `prints N/N` sentence moved beside it. The green-path tally moved THREE → FOUR, regenerated with the grep its own comment prescribes rather than restated.

## Falsification — observed RED, restored from `cmp`-verified byte backups

Both directions were driven. Each restore came from a `cp` byte backup verified with `cmp`, and the backup was **re-taken between directions** so a stale backup could not make `cmp` pass on a corrupt restore.

**Direction 1 — the retry neutered so it never re-invokes the seam** (`if [ "$attempt" -ge "$LEDGER_QUERY_ATTEMPT_BUDGET" ]` → `-ge 1`). The edit was confirmed applied by grep before the run. Exit 1, verbatim:

```
  FAIL retry recovers a transient ledger read (GREEN) (exit 1, expected 0)
       | MEASURE_FAIL: the gate exited 1 on a read that failed transiently and then SUCCEEDED within the budget. A recoverable transport fault must not red this gate.
  FAIL retry EXHAUSTS loudly, and answer-level failures are not retried RED (exit 0, expected 1)
       | MEASURE_FAIL: the exhaustion message did not name the attempt count against the budget.
SELF-TEST FAIL: 11/13 arms behaved as declared.
```

Restored: `RESTORE-A-VERIFIED`, and the neutered line confirmed back to `-ge "$LEDGER_QUERY_ATTEMPT_BUDGET"`.

**Direction 2 — the budget neutered so the retry never exhausts** (`LEDGER_QUERY_ATTEMPT_BUDGET=3` → `200`, against a shim that fails 98 times). Exit 1, verbatim:

```
  FAIL retry EXHAUSTS loudly, and answer-level failures are not retried RED (exit 0, expected 1)
       | MEASURE_FAIL: a ledger read that failed every attempt exited 0, not 1. An unreadable input must still fail LOUDLY after the budget — that is what keeps it distinguishable from a clean one.
SELF-TEST FAIL: 12/13 arms behaved as declared.
```

Restored: `RESTORE-B-VERIFIED`, and `LEDGER_QUERY_ATTEMPT_BUDGET=3` confirmed back.

⚠️ **The second neuter was BOUNDED rather than literally infinite, and the reason is recorded rather than glossed.** The plan's words were "neuter the budget so the retry never terminates". An unbounded loop would have been run as a grandchild process that `timeout` on the parent would not reap, leaving a spinning orphan on the machine. Setting the budget to 200 against a shim that fails 98 times is the same measurement — the retry does not terminate within the horizon the arm assumes, the arm reds with a named message, and the run finishes.

## Deviations from Plan

### 1. [Rule 3 — Blocking issue] The flag is held by a SECOND session, not inside the mutual-exclusion session

- **Found during:** Task 1.
- **Issue:** The plan said to take the flag "inside its already-held mutual-exclusion session so the flag's lifetime is exactly the apply's… it introduces no second connection". That session is the backgrounded `start_holder` psql inside the `Acquire shared-test-db mutex` step — and `src/__tests__/supabase-migrate-test-first.test.ts` pins that step's **suffix byte-identical across ci.yml, supabase-migrate.yml and test-restore-from-baseline.yml**, with `start_holder` inside the pinned region. Adding a `-c` there would either break that gate or, if re-synced across all three, put the flag on the **READER** jobs too — which destroys the flag's meaning entirely.
- **Fix:** A separate short announcement step opening one long-lived session, carrying the same libpq keepalives and the same two session GUCs as the mutex holder. Its lifetime spans the apply and its post-verification.
- **Files:** `.github/workflows/supabase-migrate.yml`, `.github/workflows/test-restore-from-baseline.yml`. **Commit:** `a78ddad3`.

### 2. [Rule 3 — Blocking issue] The announce steps carry no `exit 0`, no `::warning::` and no `2>/dev/null`

- **Found during:** Task 1, caught by the existing no-softening gates going RED.
- **Issue:** Both jobs carry a nine-token no-softening scan, an every-`run:`-turns-`-e`-on rule, and (in the restore) an EXACT site allowlist for `2>/dev/null`. My first draft used all three. ⛔ The gates were NOT widened — no allowlist entry was added and no exemption taken.
- **Fix:** Restructured to `set -euo pipefail`, a single `case` over an `outcome` variable with no early exits, `: > "${log}"` before any `grep` so no stderr suppression is needed, and plain named log lines (`schema-apply-in-flight: NOT-ANNOUNCED`) instead of `::warning::`. The last is also the honest shape: nothing the step can observe is a failure, and an in-file comment says so and forbids "improving" it back.
- **Commit:** `a78ddad3`.

### 3. [Rule 3 — Blocking issue] No release step for the flag

- **Found during:** Task 1. A `Release the schema-apply-in-flight flag (best effort)` step was written and then **removed**, because every form of it needed a softening token in a job that forbids them. Job teardown releases the session and the announcement's own `client_connection_check_interval` reaps an orphaned backend in ~30s — the same steal path the mutex itself relies on. The in-file comments state this so nobody adds one back.
- **Commit:** `a78ddad3`.

### 4. [Rule 3 — Blocking issue] The restore's announcement is placed AFTER its activity gate

- **Found during:** Task 1, by reading the activity gate rather than by a failing test — it cannot fail locally.
- **Issue:** That gate counts non-idle client backends and excludes exactly ONE `application_name`, the mutex holder's. The announcement opens a second long-lived session running `pg_sleep`, which reads `active`. Announcing before the gate would make the gate count our own announcement and **refuse the restore it is guarding**.
- **Fix:** Placed after the gate, with the reasoning in-file so it is not "tidied" back. **Commit:** `a78ddad3`.

### 5. [Rule 3 — Blocking issue] The wait logic is a new shared script, not triplicated YAML

- **Found during:** Task 2. `scripts/wait-for-test-schema-apply.sh` is not in the plan's `files_modified`.
- **Rationale:** The mutex acquire IS triplicated byte-for-byte in `ci.yml` — and it has a gate pinning that identity. A third ~80-line triplication with no such gate is exactly the one-site drift that step's own comment warns about, and a script can carry a `--self-test` that YAML cannot. The three outcome names are LIVE in the script and named per-site in each job's step comment.
- **Commit:** `884ea490`.

### 6. [Rule 1 — Consequential test update] Two stderr-count pins are now DERIVED, not restated

- **Found during:** Task 3. Because the retry discards **no** attempt's stderr channel, a read that fails every attempt captures one stub stderr line per attempt, so `1 line(s) of stderr captured` became `3`. Rather than swapping one literal for another (a stale pin waiting to happen — the `[164.7-CITATION-DRIFT-01]` class), the four assertions now derive the count from `ledgerGateAttemptBudget(LEDGER_GATE_SRC)`, which itself only matches the FIXED, non-overridable assignment form.
- **Commit:** `a92e34b0`.

### 7. [Rule 3 — Blocking issue] `drift-check-scripts.test.ts` gets an explicit 60s test timeout

- **Found during:** Task 3. MEASURED: `--self-test` took **4.93s at the commit before these arms** against vitest's 5000ms default — a 70ms margin, i.e. a red that depended on scheduling luck. The two new arms took it to 5.97s and turned that into a reproducible timeout, and starved the neighbouring VAC-04 legs in the same worker.
- **Fix:** `vi.setConfig({ testTimeout: 60_000 })` with the measurement recorded in-file. ⛔ No assertion was weakened and no floor moved; a timeout is not a gate on behaviour, and an under-sized one only manufactures false reds that get "fixed" by deleting coverage. It stays bounded at 60s so a genuine hang still fails.
- **Commit:** `a92e34b0`.

### 8. [Rule 3 — Blocking issue] The retry's backoff is env-overridable; the BUDGET is not

- **Found during:** Task 3. Harnesses need the retry's logic without its wall clock. The asymmetry is deliberate: overriding the BUDGET to 1 would disable the retry from a workflow `env:` with nothing in the run saying so. A new static leg pins the SHIPPED backoff default, because every harness overrides it and nothing else in the repo would ever observe a wrong one.
- **Commit:** `a92e34b0`.
