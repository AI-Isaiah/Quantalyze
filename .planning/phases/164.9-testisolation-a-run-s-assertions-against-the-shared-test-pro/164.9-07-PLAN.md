<objective>
Two restore-workflow items routed here from Phase 164.8. ⚠️ CONTEXT Area 6 is explicit that they are
topically about the RESTORE, not about per-run isolation — they live in this phase because it is the
hardening deferrals' home and depends on 164.8's restore. ⛔ They must not dilute
`FANOUT-GLOBAL-01`, which remains this phase's reason to exist.

**The extension guard** asserts strict equality on a WHOLE-DATABASE extension count while its own
message reasons about the public schema. It therefore fired on a legitimate GAIN — an extension the
dump correctly created in a different schema — and phrased that gain as a loss. And it runs after
the transaction commits, so in restore mode it can only mislabel an outcome, never prevent one.

**The replay's value blindness** is the same family as the rest of this phase: a green reading that
is not measuring what it claims. A migration seeds a row, a later migration updates it, the restore
replays only the insert, and the row comes back PRESENT, at the RIGHT COUNT, in the WRONG STATE.
Both existing legs count rows, so neither can see it.

Purpose: make both guards measure what their messages say they measure, and prove each direction
rather than believing it.

Output: a schema-scoped, two-directional extension guard; a third gate leg pinning expected column
VALUES beside the emptiness and shortfall legs; and five new self-test arms with the ratchet moved
in the same commit.
</objective>
