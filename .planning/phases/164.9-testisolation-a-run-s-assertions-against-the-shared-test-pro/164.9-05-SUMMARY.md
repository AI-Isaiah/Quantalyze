## Decisions Made

- **Budget = 3 attempts, backoff base = 0.5s.** Justified in a dated module comment against the
  measured evidence (ROADMAP criterion 11's run needed exactly 3 attempts to reach green). Not a
  round number picked without evidence.
- **Classifier boundary drawn at the exact two measured signatures plus the obvious siblings:**
  `httpx.TransportError` (any subclass — `ConnectError`, `ReadTimeout`, `ConnectTimeout`,
  `RemoteProtocolError`, etc.) is always transient; `postgrest.exceptions.APIError` and
  `httpx.HTTPStatusError` are transient only when their status/code casts to {502, 503, 504};
  everything else — including a Postgres SQLSTATE-shaped `APIError.code` and `AssertionError` —
  is NOT transient. `int(exc.code)` handles both the int-status and SQLSTATE-string
  representations of `APIError.code` uniformly without extra type branching.
- **Retry log line does not repeat the module name.** The original draft's log line
  (`"live_db_transport: retry attempt %d/%d after %s"`) contained the literal string
  `live_db_transport`, which made the helper's own source match the Task 2 verify script's
  "which module imports the helper" substring scan (`grep -l 'live_db_transport' tests/*.py`,
  which does not exclude `tests/live_db_transport.py` itself). That made the plan's own verify
  command compare 4 factories against 5 "wrapped" modules and fail. Fixed by dropping the
  redundant module-name prefix from the log text (the logger's own `%(name)s` already carries
  module identity) — the line still names the attempt number, budget, and exception type, so
  T-164.9-05-05's distinguishability requirement is unaffected.

## Issues Encountered

- A pre-existing, order/timing-dependent flaky failure in
  `tests/test_mt5_session_monitor.py::test_CRITERION_2_a_dark_reading_drives_the_heal_with_no_human_and_no_restart`
  surfaced on the first full-suite run and passed both standalone and on a second full-suite
  re-run. Unrelated to this plan's files; not fixed (out of scope per Rule 3's scope boundary).
- **Interaction with a pre-existing local retry, disclosed but not modified.**
  `test_compute_jobs_fencing.py` already has its own hand-rolled outer retry,
  `_rpc_retry_timeout(fn, attempts=2)`, wrapping several `admin.rpc(...).execute()` call sites. It
  catches only when `"timed out" in str(exc).lower()` and otherwise re-raises, using that as a
  signal to `pytest.skip()` after its own 2 attempts (treating a persistent timeout as an
  infrastructure limit rather than a fence failure). Now that `admin` returns the wrapped proxy,
  the INNER `retry_transport()` retries first (up to 3 attempts with backoff); if it exhausts, it
  raises `TransportRetryExhausted`, whose message reads `"...last exception type: ReadTimeout"` —
  which does **not** contain the substring `"timed out"`. So a persistent `httpx.ReadTimeout` that
  outlives the inner retry's budget now propagates immediately through the outer
  `_rpc_retry_timeout` rather than getting that helper's own additional 2-attempt retry-and-skip
  grace. This is a genuine, previously-unobserved interaction between the two retry layers. It was
  **not fixed**: the plan's Task 2 acceptance criterion requires `git diff` on this file to show
  changes ONLY in the import block and the factory's return expression, and `_rpc_retry_timeout`
  is neither — editing it would violate that criterion. The interaction cannot be exercised here
  either way (the DATABASE SAFETY constraint forbids driving a live-DB test against shared TEST
  from this environment), so it is disclosed rather than "fixed" quietly. If it matters in
  practice, `[164.9-SHARED-TEST-TRANSPORT-FLAKE]`'s owning phase or a follow-up should decide
  whether `_rpc_retry_timeout`'s string match should widen to catch `TransportRetryExhausted` too,
  or whether the inner retry's budget alone is now sufficient and the outer helper should be
  retired.
