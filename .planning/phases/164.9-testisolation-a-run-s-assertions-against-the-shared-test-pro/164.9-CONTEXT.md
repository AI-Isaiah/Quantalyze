<domain>
## Phase Boundary

Close `FANOUT-GLOBAL-01`: replace GLOBAL assertions against the shared TEST project with
PER-RUN isolation, so a CI run asserts about the rows IT created and nothing else.

The family this phase treats is one defect wearing several faces: **a green reading that is not
measuring what it claims.** Every routed item below is an instance of it — a global count that
includes other people's rows, a gate that goes green on assertions its own harness declared
untrustworthy, a restored row present in the wrong state, a test class that cannot go red
because nothing runs it.

⛔ **OUT OF SCOPE, stated so it cannot drift in:** raising Playwright workers above 1. Per-run
isolation is the PRECONDITION for parallelism, not a bid for it — `e2e-seeded` sits behind
`sql-mutation`, so parallelism buys 1–2 minutes of wall clock. Isolation is worth doing for
ASSERTION RELIABILITY; the parallelism is a consequence, never an objective.

⛔ Also out of scope: the coupling whereby a red check-suite on `main`'s head makes Railway skip
the analytics deploy. It is real and it is why criteria 11–13 are worth fixing rather than
tolerating, but it has its own phase.

</domain>

## Implementation Decisions

### Area 1 — What "per-run isolation" means, and what counts as closing `FANOUT-GLOBAL-01`

- **Isolation means a run-scoped discriminator carried on the rows a run creates, and every
  assertion filtered by it.** The global form ("no stuck jobs exist", "the table is empty") is
  REPLACED, not narrowed. A narrowed global assertion is still global.
- **The calibration is non-negotiable and is what makes the criterion real:** seed a FOREIGN row
  (one this run did not create), then show the new assertion stays GREEN where the old one would
  have gone RED. Without that, "isolated" is an unproven claim about a passing test.
- ⛔ **Every assertion this phase adds or changes is proven able to fail** — neutered, observed
  RED, restored from a **`cp` byte backup** verified with `cmp`. ⛔ Never `git checkout --` /
  `git restore` / `git stash`: they restore to HEAD and silently destroy concurrent uncommitted
  work. ⚠️ Re-take the backup after every edit; a stale backup makes `cmp` pass on a corrupt
  restore.
- ⚠️ **Assert about YOUR OWN rows — this is the phase's subject matter, so getting it wrong
  inside the fix is the obvious failure.** A global assertion written while building the
  isolation is the defect reproducing itself.

### Area 4 — The credentialed test class: MEASURED, and the answer changes the shape

⭐ **Criterion 13 demanded this be established FIRST rather than assumed. It is now measured, and
the claim the entry deliberately declined to make turns out to be TRUE — with a stated reason
that rules out the obvious fix.**

- **CI's vitest shards deliberately run WITHOUT TEST credentials.** The `frontend-test` job
  carries an explicit in-file prohibition: *do not add* `NEXT_PUBLIC_SUPABASE_URL` /
  `SUPABASE_SERVICE_ROLE_KEY` *to this job*, because doing so **"would un-skip ~284 live-DB tests
  (`src/lib/test-helpers/live-db.ts`), shifting the coverage denominator and invalidating the
  ratchet baseline (which was measured with those tests skipped)."** `frontend-build` sets a
  placeholder URL rather than a real one.
- **`HAS_LIVE_DB` in `src/lib/test-helpers/live-db.ts` gates on exactly those two variables** —
  the same two the shard comment forbids. So the skip is not incidental; the gate and the
  prohibition are the same decision seen from two files.
- ⛔ **CONSEQUENCE, and it is the load-bearing one: the class cannot be un-skipped by adding
  credentials to the shards.** That is the obvious fix and it would break the coverage ratchet,
  which is a blocking CI gate. Criterion 13's deliverable therefore needs a **SEPARATE LANE**.
- ⭐ **The repo already has the precedent and it is documented as such:** `frontend-seam-redis`
  sets env JOB-WIDE and its own comment calls itself *"the exact INVERSE of the frontend-test
  warning"* — safe only because it runs one narrow test selection and nothing else, with
  *"never widen this job's test selection"* written beside it. That is the shape to copy:
  a narrow lane, job-wide env, an explicit non-widening fence.
- ⛔ **CORRECTED 2026-09-21, AFTER RESEARCH — the paragraph here leaned toward a local stack and
  the evidence REFUTES that lean. Recorded rather than silently swapped, because the reasoning is
  the useful part.** The lean said a local stack would close the criterion and be better aligned
  with isolation, "but only if it can host the schema — do not assume it can; measure it." It was
  measured, and it cannot:
  - The `PGRST203` overload ambiguity is in **`supabase/schema/baseline.sql` ITSELF** — two live
    definitions of `claim_compute_jobs_with_priority`, a 2-arg and a 5-arg. A local stack builds
    from that same baseline, so it reproduces the ambiguity rather than fixing it.
  - `supabase/config.toml` sets `schemas = ["public", "graphql_public"]`, so `cron` is outside
    PostgREST **everywhere** — local stack included. The `Invalid schema: cron` failure is not a
    shared-TEST condition.
  - The `key_hash` failure is a **stale test fixture**, not drift: `key_hash` appears **0** times
    in `baseline.sql` and **0** times across `supabase/migrations/`, while `api_key_encrypted`
    appears 19 times. That column has never existed.
- ⭐ **CONSEQUENCE — the task is a different shape than "pick a lane."** At least three of the
  five recorded failure classes are baseline/fixture defects that follow the tests to ANY host.
  Criterion 13 therefore needs **schema and fixture repair alongside the lane decision**, and a
  plan that only stands up a lane will still be red. ⛔ Do not close it by choosing a host.
- ⚠️ **Still unmeasured, and it must not be rounded up:** only 3 of the 38 failures were traced.
  The remaining per-file census is owed before anyone claims the class is understood.
- ⛔ **NOT closed by deleting the tests, by skipping them permanently, or by arguing CI's green
  is sufficient.** CI's green is precisely the thing measured to be uninformative here.
- ⚠️ The recorded failure signatures are shared-TEST schema DRIFT, not logic — two live overloads
  of one claim function so PostgREST cannot choose, a table absent from the schema cache, a
  missing column, an invalid schema reference, and a permission denial. Fix the drift; do not
  rewrite the tests to match a drifted schema.

### Area 5 — Transport flake and the dead mutex holder

- **`[164.9-SHARED-TEST-TRANSPORT-FLAKE]` is planned WITH criterion 4, not as a separate
  ratchet.** Criterion 4 asked for flakiness to be MEASURED before a remedy was prescribed; it
  now is (three attempts of one run at one commit, two different failure signatures on different
  tests, then green on identical code). Non-deterministic victims across attempts is the proof
  that this is TRANSPORT, not logic.
- ⛔ **The remedy is NEVER a bare re-run** — a re-run is what made it green and it taught nothing.
  Deliverable: a bounded retry at the transport boundary that keeps a transient fault
  DISTINGUISHABLE from a clean run, or per-run isolation. ⛔ **The retry must be observed to
  EXHAUST** (neuter → RED → restore from a byte backup), never assumed.
- ⚠️ **It is NOT the wedged-pool mechanism and must not be triaged as it** — a live probe returned
  three sub-second 200s and the backends were all idle, so the recorded `pg_terminate_backend`
  remedy was correctly NOT fired at infrastructure shared with other people's CI.
- **`[164.9-MUTEX-HOLDER-DIED-UNSERIALIZED]`: the dead-holder condition must produce a NON-ZERO
  verdict** (or the run's DB assertions re-run under a live holder), proven by killing the holder
  mid-job on the throwaway lane and observing RED. Today the only signal is advisory prose in a
  log nobody re-reads, and the job's verdict is unaffected — so a run can go GREEN on assertions
  its own harness has just declared untrustworthy. ⛔ NOT closed by deleting, softening or
  re-wording the warning.
