### CR-01: The live-DB execution ledger's SHRINK-ONLY rule is prose only — a two-line edit turns a real regression green

**File:** `scripts/live-db-execution-ledger.mjs` (`evaluate`, the `isNew` branch) ·
`scripts/live-db-execution-ledger.txt` (`# ENTRY_COUNT`) ·
`src/__tests__/live-db-execution-ledger.contract.test.ts`

**Issue:** The gate compares the failing set against the ledger for **set equality**. Nothing —
in the gate, in the contract test, or anywhere else in the repository — prevents the ledger from
GROWING. The file's header says an entry "is added only with the founder decision the ledger
header states", the gate prints `⛔ This is NOT closed by adding a line`, and the contract test
deliberately declines to pin any tally ("restating it here would make a correct shrink red"). That
reasoning rules out pinning the *exact* count; it does not rule out a CEILING, and no ceiling
exists. `blocker`-tier because `frontend-live-db-lane` is wired BLOCKING into the `frontend`
aggregator's strict arm, so this is the only thing standing between a new live-DB regression and a
green board.

**Reproduced during this review**, on temp copies only (no tracked file mutated):

```
# a synthetic artifact reproducing all 18 ledger arms PLUS one brand-new regression
$ node scripts/live-db-execution-ledger.mjs --artifact $S/art.json
[live-db-ledger] executed: 396 test(s) (377 passed, 19 failed), 81 skipped, 477 collected, across 49 file(s)
[live-db-ledger] NEW: 1 failing arm(s) the ledger does not carry.
    src/__tests__/audit-log-rls.test.ts
      arm:       Migration 049 > A BRAND NEW REGRESSION
[live-db-ledger] FAILED.

# the evasion: append one TAB line, change 18 -> 19
$ node scripts/live-db-execution-ledger.mjs --artifact $S/art.json --ledger $S/led.txt
[live-db-ledger] ledger: 19 entr(y/ies)
[live-db-ledger] OK — the failing set is EXACTLY the ledger (19). Every corpus file executed;
                 no arm outside the ledger failed; no ledger entry has gone stale.
EXIT=0
```

The contract test also stays green against the mutated ledger: it asserts only that `ENTRY_COUNT`
agrees with the list, that fields are well-formed, and that no specimen leaked. The whole
"NEW is never closed by adding a line" rule is therefore a sentence, not a control — which is
exactly the `[164.7-CITATION-DRIFT-01]`/"prose beside a constant" class this repo already records
four times over, and the repo already knows the mechanical answer (`WAIVED_CEILING` in
`scripts/mutation-runner/run.mjs` is enforced, not narrated).

**Fix:** add a dated ceiling constant beside the entry list and gate on it, mirroring
`WAIVED_CEILING`. A genuine shrink lowers the ceiling in the same commit as the deletion (visible
in the diff); a genuine addition raises it, which is precisely the founder decision the header
describes, and it becomes a reviewable line instead of an invisible one.

```js

 * ENTRY CEILING — dated 2026-09-21, seeded by the founder decision in the ledger header.
 * ⛔ The ledger ONLY SHRINKS. Lowering this in the commit that deletes a line is the ratchet
 *    act. RAISING it is the founder decision, and it must be a visible diff.
 */
export const ENTRY_CEILING = 18;

// in evaluate(), beside the declaredCount checks:
if (ledger.entries.length > context.entryCeiling) {
  problems.push(
    `LEDGER GREW: ${ledger.entries.length} entr(y/ies) against a ceiling of ${context.entryCeiling}. ` +
      "A NEW failing arm is FIXED, not ledgered. Raising the ceiling is the founder decision the header states.",
  );
}
```

Add a self-test leg (red: 19 entries vs ceiling 18 → `LEDGER GREW`; green: 18 vs 18) and a
stale-low leg in `live-db-execution-ledger.contract.test.ts`
(`expect(ENTRY_CEILING).toBe(readEntries().length)` fails loudly when the ceiling is left above a
shrunken list) — the two-floors-two-layers shape `src/__tests__/mutation-runner-floors.test.ts`
already uses.

### CR-02: `live-db-execution-ledger.mjs` has no entry-point guard — importing it spawns the lane and kills the process

**File:** `scripts/live-db-execution-ledger.mjs`, final statement `process.exit(main(process.argv));`

**Issue:** The module `export`s `DESTINATION`, `classifySignature`, `routeKind`, `parseLedger`,
`measuredRecords` and `evaluate`, and then unconditionally executes its CLI at module scope. Any
consumer that imports it — a future test, a tool, a dead-code reporter walking `scripts/` —
triggers the full `runLane()` path (`spawnSync("npm", ["run", "test:live-db"])`) and then
terminates the host process via `process.exit`. **Measured during this review:** a plain
`import { evaluate } from ".../live-db-execution-ledger.mjs"` booted the live-DB lane, hit the
globalSetup refusal, printed the gate's whole verdict, and exited. So every export on this module
is unusable by construction, and the import is destructive.

This is not a style point: **all three of its siblings from the same plan carry a guard.**
`scripts/live-db-lane-corpus.mjs` guards with `resolve(process.argv[1]) === resolve(fileURLToPath(import.meta.url))`;
`scripts/lint-migration-data-dependence.mjs` carries an elaborate three-way guard whose own
comment records the MEASURED incident it exists to prevent; `scripts/live-db-fixture-drift-census.mjs`
guards too. This file is the one that does not, and it is the one with the largest side effect.

**Fix:** adopt the sibling idiom verbatim.

```js
// ⛔ Guarded, like every sibling in this plan: this module EXPORTS its verdict
//    functions, and an unguarded `process.exit(main(...))` at module scope makes
//    an import spawn the whole lane and then kill the importer. MEASURED.
if (
  process.argv[1] &&
  resolve(process.argv[1]) === resolve(fileURLToPath(import.meta.url))
) {
  process.exit(main(process.argv));
}
```

Prefer `lint-migration-data-dependence.mjs`'s three-way form (exit 2 on a basename match that does
not resolve) so a misinvocation cannot fall off the end and read as a clean run — the same reason
that file gives.

### WR-02: an ABSENT marker is reported as a positive, measured claim

**File:** `scripts/mutex-dead-holder-verdict.sh` (`verdict()`, the else branch)

**Issue:** `verdict()` prints *"this run's DB assertions were serialized as designed"* whenever the
marker file does not exist. That is an inference from an absence, not a measurement, and this repo
states the rule against it in this very phase (`vitest.livedb.globalsetup.ts`: *"A failure to ASK
is also a refusal. 'Could not measure' is not 'measured safe'"*). Three ways to reach the
affirmative line without any serialization having been verified: (a) the release step's
`if [ ! -f "${pidfile}" ]` early-`exit 0` path (fork PR / acquire skipped) writes no marker;
(b) the release step is edited or fails before the write (WR-01); (c) the CLIENT psql survives
while the server BACKEND died — the detection is `kill "${holder}"` against the client pid only,
even though the release step already runs a `pg_locks` census on the exact key and backend pid
three lines below.

**Fix:** make the green line report what it actually measured, and use the census that is already
there. Minimum: change the wording to `no dead-holder marker present at <path>` and drop the
"were serialized as designed" claim. Better: have the release step write a *positive* witness
(`: > "${RUNNER_TEMP}/shared-test-db-mutex-holder-alive"`) on the successful-`kill` path, and have
the verdict refuse when NEITHER file exists — so "the release step never ran" is distinguishable
from "the holder was alive". Best: gate the green on the existing `pg_locks` reading
(`objid = 61616158 AND pid = <backend>` still granted) rather than on client-process liveness.

### WR-03: the ordering wait's `apply-concluded` branch ignores the in-flight flag entirely

**File:** `scripts/wait-for-test-schema-apply.sh` (`wait_for_apply`, the
`case "${apply}" in concluded-ok|concluded-bad)` arm)

**Issue:** The header states the flag *"is the only signal that sees `test-restore-from-baseline.yml`,
which produces no Actions run on this commit"*. The decision table honours that only in the
`absent` arm. Whenever the Actions read returns `concluded-ok`/`concluded-bad`, the outcome is set
from the API alone and `flag` is never consulted — so on a merge push that touched migrations
while a restore is dispatched concurrently, the reader proceeds and prints *"This job's DB work is
ordered behind it"* while a `DROP SCHEMA public CASCADE` is in flight. The self-test's own
calibration arm covers only `held` + `absent` (`"absent apply but flag HELD is NOT no-apply-run"`),
so the gap is unmeasured. The mutual-exclusion key still prevents overlap, which is why this is a
warning and not a blocker — but the log line asserts an ordering fact that is false in that case,
and the file's stated contract is broader than its code.

**Fix:** make a held flag beat every apply state, not just `absent`, and add the missing
calibration arm:

```sh
case "${apply}" in
  concluded-ok|concluded-bad)
    # ⛔ A HELD FLAG BEATS A CONCLUDED APPLY. The restore produces no Actions run
    #    on this commit, so the API's "concluded" says nothing about it.
    if [ "${flag}" != "held" ]; then outcome="apply-concluded"; fi
    ;;
```

```sh
arm "concluded apply but flag HELD is NOT apply-concluded" 1 "wait-outcome: wait-exhausted" held concluded-ok
```

### WR-04: the wait's two reads are combined across an unbounded interval, and neither real probe body is ever exercised

**File:** `scripts/wait-for-test-schema-apply.sh` (`probe_inflight_flag`, `probe_apply_state`,
`wait_for_apply`)

**Issue:** Two separate problems in the same seam.

1. `flag="$(probe_inflight_flag)"` is taken, then `apply="$(probe_apply_state)"` runs
   1 + N `gh api` round trips (up to 20 runs × a jobs call each, with no timeout), and only then is
   the `no-apply-run` decision made from the now-stale `flag`. A restore can announce in that
   window and the reader still concludes "nothing to order against". The mutex bounds the damage;
   the decision is still made on data the script itself has invalidated. Re-read the flag
   immediately before committing to `no-apply-run`.
2. `--self-test` replaces BOTH probes wholesale through `TEST_INFLIGHT_PROBE_CMD` /
   `TEST_APPLY_STATE_CMD`, so the psql invocation, the `:6543/` → `:5432/` DSN rewrite, the
   `tr -d '[:space:]'` normalisation and every `jq` filter in `probe_apply_state` are covered by
   nothing. A regression in any of them degrades to `unknown`/`unreadable`, which can never
   produce `no-apply-run` — so it burns the full 900 s budget and reddens `sql-tests`, `python`
   and `e2e-seeded` on every merge push, including commits that changed no migration at all.

**Fix:** re-probe the flag at the decision point; and add self-test legs that feed
`probe_apply_state`'s and `probe_inflight_flag`'s **parsers** canned inputs (a captured runs JSON,
a captured jobs JSON, a `" 0 \r\n"` psql answer) rather than replacing the whole function — split
the parse out of the fetch so the parse is drivable.

### WR-05: the data-dependence linter's taint does not propagate through variable-to-variable assignment

**File:** `scripts/lint-migration-data-dependence.mjs` (`variableAssignments`, the
`v := <expression>` matcher; `classifySource`, the `inForce` resolution)

**Issue:** The flow-sensitive design is correct and well argued, but taint is recorded ONLY from an
assignment whose right-hand side contains a `SELECT` over an application relation. Any assignment
without a `SELECT` records `relation: null`, and `inForce` then treats it as CLEARING the taint.
So both of these evade R1 completely:

```sql
SELECT count(*) INTO v_n FROM public.strategies;   -- tainted
v_total := v_n;                                    -- relation null -> untainted
IF v_total = 0 THEN RAISE EXCEPTION '...'; END IF; -- NOT refused
```

```sql
SELECT count(*) INTO v_n FROM public.strategies;
v_n := v_n + 0;                                    -- clears its own taint
IF v_n = 0 THEN RAISE EXCEPTION '...'; END IF;     -- NOT refused
```

The second is contrived; the first (`v_remaining := v_total - v_used;`) is ordinary code. The
file's own stated priority is that false negatives matter more than false positives here, and a
missed data-dependent migration blocks a production deploy at apply time.

**Fix:** propagate taint through the RHS. When an assignment's expression mentions an
already-tainted local and reads no relation of its own, inherit the in-force relation of the
mentioned variable instead of recording `null`:

```js
for (const m of body.matchAll(/\b([A-Za-z_][A-Za-z0-9_]*)\s*:=([^;]*)/g)) {
  const rels = /\bSELECT\b/i.test(m[2]) ? appRelationsIn(m[2], locals) : [];
  let relation = rels[0] ?? null;
  if (relation === null) {
    // INHERIT: `v_total := v_n` where v_n is tainted is still a data-derived value.
    const at = m.index + m[0].length;
    for (const prior of out) {
      if (prior.at < at && prior.relation &&
          new RegExp(`\\b${prior.name}\\b`, "i").test(m[2])) relation = prior.relation;
    }
  }
  out.push({ name: m[1].toLowerCase(), at: m.index + m[0].length, relation });
}
```

(`out` must be kept sorted, or resolved in a second pass.) Ship it with a red fixture
`r1-taint-through-assignment.red.sql` and a green twin whose intermediate is catalogue-derived.

### WR-06: three raise-on-data shapes are invisible to the linter, and all three occur in this corpus today

**File:** `scripts/lint-migration-data-dependence.mjs` (`raiseSites`,
`RAISE_LEVELS_THAT_ARE_NOT_EXCEPTIONS`, `classifySource`)

**Issue:** `raiseSites` only recognises an explicit `RAISE` whose next word is not one of five
non-exception levels, and `classifySource` only refuses when the ENCLOSING `IF`/`ELSIF` condition
is data-derived. Three PL/pgSQL shapes raise on data with neither property:

1. **`SELECT ... INTO STRICT v FROM <app relation>`** — raises `P0002 no_data_found` on an empty
   TEST with no `RAISE` statement anywhere. This is the canonical data-dependent apply refusal and
   the linter parses `INTO STRICT` for taint purposes while never treating it as a raise site.
2. **`IF NOT FOUND THEN RAISE EXCEPTION ...`** — `FOUND` is an implicit variable, so it is not in
   `names`, and the condition text carries no `SELECT`, so neither R1 nor R2 fires. Data-dependent
   by construction: it reads the result of the immediately preceding statement.
3. **`ASSERT <data-derived condition>`** — raises `assert_failure`; `ASSERT` is not scanned at all.

Measured over the real corpus (driving the linter's own `anonymousBlocks` so function bodies are
correctly excluded): **1 anonymous block uses `INTO STRICT`, 2 use `NOT FOUND` alongside
`RAISE EXCEPTION`, 0 use `ASSERT`.** All three current occurrences read the CATALOGUE, so there is
no live escape today — but the shapes are established house style in `DO` blocks here, which makes
the gap a live-fire risk rather than a hypothetical.

**Fix:** treat all three as raise sites.
- `INTO STRICT`: in `variableAssignments`, when the `STRICT` keyword is present and the read
  resolved to an application relation, emit a synthetic raise site at that offset with the
  relation attached — no enclosing condition needed.
- `NOT FOUND`: seed `names` with the implicit `found`, and taint it at every `SELECT ... INTO` /
  `FOR ... LOOP` site the way a declared local is tainted, so `IF NOT FOUND THEN RAISE` resolves
  through the existing R1 path.
- `ASSERT`: add it to the raise-site scan beside `RAISE` (its condition is the text up to the
  first top-level comma).

Each needs a red and a green fixture and a bump of `REFUSALS_FLOOR` if a new refusal id is added.
State the residual gaps in the "KNOWN LIMITATIONS" block either way — today that block names only
the dynamic-`EXECUTE` gap.

### WR-07: `DO LANGUAGE plpgsql $$ ... $$` is not recognised as an anonymous block

**File:** `scripts/lint-migration-data-dependence.mjs` (`anonymousBlocks`)

**Issue:** The block test is `lastWord !== "DO"` against the last identifier before the dollar
body. PostgreSQL accepts `DO LANGUAGE plpgsql $$ ... $$` (the `LANGUAGE` clause may precede the
code), where the last word is `plpgsql`. Such a block executes at apply time and is skipped
entirely — a silent unscanned migration, which the file elsewhere calls out as never a pass.

**Fix:** accept `DO` anywhere in the preceding clause rather than only as the immediately
preceding word:

```js
const tail = (words || []).slice(-4).map((w) => w.toUpperCase());
if (!(tail.at(-1) === "DO" || (tail.includes("DO") && tail.includes("LANGUAGE")))) continue;
```

Add a `do-language-clause.red.sql` fixture so the shape is proven covered.

### WR-08: the bounded transport retry replays NON-IDEMPOTENT writes

**File:** `analytics-service/tests/live_db_transport.py` (`retry_transport`,
`_RetryingClientProxy.__getattr__`, `wrap_live_db_client`)

**Issue:** `.execute()` is wrapped unconditionally — the proxy cannot tell a `select` chain from an
`insert`/`update`/`delete`/`rpc` chain, and the module never mentions idempotency. A `504 Gateway
Timeout` is classified TRANSIENT and retried, but a 504 is precisely the signal that says the
server may have COMMITTED and the gateway gave up waiting. So against shared TEST a retried
`insert` can (a) double-insert, or (b) hit the unique index and raise `APIError` code `23505`,
which `is_transient_transport_fault` correctly classifies NOT transient and propagates — i.e. the
retry manufactures a hard, misleading test failure out of a transient fault it was added to
absorb. That is the same "a green/red reading that is not measuring what it claims" family this
phase exists to remove.

**Fix:** either restrict the retry to read paths, or make the write path explicit and opted-in.
The cheapest honest version is to record the verb on the chain and refuse to retry a mutating one:

```python
_MUTATING = frozenset({"insert", "upsert", "update", "delete", "rpc"})

# in __getattr__, when wrapping a chained builder:
if name in _MUTATING:
    return _passthrough(attr)   # chain onward with retries DISABLED
```

and state in the header why: a 504 on a mutating call is ambiguous about commit, so replaying it
trades a transient red for a silent double-write. If a retry on writes is genuinely wanted, it
needs an idempotency key, and that is a different design.

### WR-09: the retry proxy breaks on dunder access and on attribute assignment

**File:** `analytics-service/tests/live_db_transport.py` (`_RetryingClientProxy`, `_wrap`)

**Issue:** `__getattr__` is bypassed by Python's special-method lookup, so `len(proxy)`,
`proxy[0]`, `iter(proxy)`, `bool(proxy)`, `repr(proxy)` and `isinstance(proxy, PostgrestClient)`
all go to the proxy rather than the target. `__slots__` is declared with no `__setattr__`
override, so any call site that assigns an attribute on a wrapped object
(`client.postgrest.session = ...`, the exact shape `test_compute_jobs_fencing.py`'s `admin`
fixture is documented as performing) raises `AttributeError` instead of reaching the target.
`_wrap` also proxies every non-scalar — a returned `list`, `dict` or `datetime` becomes a proxy —
so anything that is not reached through `.execute()` can surface as a proxy in a test assertion.

**Fix:** narrow the proxy to the seam it needs. Add `__setattr__` delegating to the target, and
either forward the handful of dunders the builders use or drop the general proxy in favour of
wrapping the terminal `.execute` at the point the fixture builds the chain. Add a unit test that
sets an attribute through the proxy and one that indexes a returned collection.

discriminator column."* What shipped is a **margin measurement** (how much budget headroom the
existing seeding discipline has against one competitor), not per-run isolation.

ROADMAP criterion 2 asks for the opposite: *"A global assertion … is replaced, not narrowed — and
a calibration proves it by seeding a foreign row and showing the assertion stays GREEN where the
old one would have gone red."* `164.9-CONTEXT.md` Area 1 restates it: *"A narrowed global
assertion is still global."* No arm here exercises the OLD assertion to show it would have gone
red; the old form was not replaced.

The disclosure is honest and in-code, which is why this is a warning and not a blocker — but the
criterion should be reconciled before a verifier reads it as closed. Two acceptable outcomes: book
the discriminator column as a named routed deferral with a destination phase (the disclaimer
already names the missing artefact), or amend criterion 2 in the ROADMAP with the dated reason,
per the phase's own "where narrowing IS the honest answer, it is dated and reasoned in-code" rule.
⛔ Do not close it by editing the criterion silently.

### WR-11: the ledger gate can read a STALE execution artifact

**File:** `scripts/live-db-execution-ledger.mjs` (`readArtifact`, `runLane`, `main`)

**Issue:** `.live-db-lane-execution.json` is never deleted before a run and carries no run
identity, no timestamp and no head SHA. `runLane()` accepts lane exit status 0 or 1 and then reads
whatever is on disk. If a run exits 1 without the reporter's `onTestRunEnd` firing, the gate
adjudicates the PREVIOUS run's artifact — and `artifact.reason` will read `"failed"`, satisfying
the completeness check. The `--artifact <file>` path has no freshness binding either. CI is
protected only incidentally (fresh checkout per job), so this bites a developer and any future
re-use of the flag.

**Fix:** `rm -f` the artifact before `runLane()` and refuse when it is absent afterwards; and have
the reporter stamp `generatedAt` plus `process.pid` / `GITHUB_RUN_ID`, with `evaluate` refusing an
artifact older than the invocation's own start time.

### WR-12: the corpus is self-derived, so `CORPUS MISMATCH` cannot see a file being removed from the lane

**File:** `scripts/live-db-lane-corpus.mjs` (`liveDbLaneCorpus`) ·
`scripts/live-db-fixture-drift-census.mjs` (`walkCorpus`, `LIVE_DB_GATE_SYMBOL`) ·
`scripts/live-db-execution-ledger.mjs` (`evaluate`, the `counts.files !== context.corpusSize` arm)

**Issue:** Both the lane's vitest `include` list and the gate's `corpusSize` come from the SAME
walk (`text.includes("HAS_LIVE_DB")`). Deleting or renaming that reference in a failing spec drops
the file from both sides simultaneously, so the guard whose message reads *"The lane's selection
must never be narrowed"* compares 48 against 48 and passes. Combined with CR-01 this is a second
route to "the failing set equals the ledger" that involves no fix. The damage is bounded — but
only loosely — by `CORPUS_FLOOR = 40` in `src/__tests__/live-db-fixture-drift.test.ts` against a
corpus measured at 49 today, i.e. roughly nine files of silent headroom.

**Fix:** pin the lane corpus with its own ratchet in the same shape (`LANE_CORPUS_FLOOR`, dated,
read by symbol, raised when the corpus grows durably) and assert it from the contract test, so a
shrink needs a visible diff rather than passing under nine files of slack.
