<objective>
Criteria 3 and 4 share one root — two jobs contending for one advisory key with nothing ordering
them — and CONTEXT Area 3 locks them as ONE unit of work, because splitting them creates the
sequential-ratchet-patched-in-one-place hazard this repo has already paid for once. The bash half of
criterion 11 rides with them for the same reason: it is a retry around a read on the same key, on
the same shared database.

⭐ **THE IDENTITY-MODEL QUESTION, ANSWERED HERE BECAUSE THE FIX TURNS ONE KEY INTO SEVERAL.**
What unit does the key protect today? Measured 2026-09-21: it is taken across five workflows and
named in three scripts and the runbook, and it is used as one mutual-exclusion token for everything
that touches shared TEST. The tempting reading of "distinct keys" — give the writer its own — would
make the writer STOP excluding the readers, and Phase 164.8 Area 4 recorded that a schema apply
racing a running gate is the one collision that corrupts a reading rather than merely delaying it.
That reading removes the exclusion the repo most needs, which is the widening this phase forbids.

So the answer is TWO KEYS PROTECTING TWO DIFFERENT UNITS, and the existing name stays correct for
the first:
- **the mutual-exclusion key (unchanged, `61616158`)** — unit: *the shared TEST database*. Every
  current taker keeps taking it, unchanged, literal for literal. Zero exclusion is removed and zero
  regression risk is taken on the working mechanism.
- **the schema-apply-in-flight flag (NEW)** — unit: *"a schema apply against this project is in
  flight"*. ⛔ It is NOT a lock between peers: nothing blocks on it. It is held by the two schema
  WRITERS for the duration of their apply and READ, non-blockingly, by the readers. Calling it a
  lock would be the naming error this question exists to catch; it is named as a flag and the
  runbook says so.

**ORDERING — the mechanism chosen, and the two that were ruled out.** A mutex guarantees no two
holders overlap; it never guarantees which goes first. Ordering therefore needs its own primitive,
and RESEARCH named three candidates without selecting one:
- ⛔ *Pull the TEST apply into a reusable workflow called from the CI workflow* — RULED OUT by a
  LOCKED prior decision. Phase 164.8 Area 1 requires the production apply job to depend on the TEST
  apply **inside the same workflow**: "one place decides what reaches production; two workflows
  cannot order themselves". Moving the TEST apply out breaks that gate.
- ⛔ *Trigger the CI DB jobs on the migrate workflow's completion* — RULED OUT by blast radius. The
  migrate workflow runs only on push to the default branch and on dispatch, so the DB jobs would
  stop firing on pull requests entirely and the PR-time gate would vanish.
- ✅ *A bounded cross-workflow wait, polling the Actions API for the apply's conclusion on the same
  head commit*, modelled on the acquire loop this repo already runs. **ACCEPTED TRADEOFF, stated
  plainly:** it adds a step with its own timeout and its own failure mode, it needs the workflow
  read permission at job scope, and it lengthens a merge push by however long the apply takes. That
  is the price of ordering two workflows that cannot order themselves, and it is smaller than the
  price of either alternative.

⚠️ **`.github/workflows/supabase-migrate.yml` IS edited by this plan, and CONTEXT Area 3 requires
this plan to state which of two acts that is. IT IS A PLANNED ISOLATION FIX.** It adds the
in-flight flag to the TEST apply. It removes no gate, relaxes no condition and clears no red. It is
not a workflow edit made under deploy pressure to get a deploy out; the standing prohibition in
`CLAUDE.md` names that act and this plan does not perform it.
</objective>
