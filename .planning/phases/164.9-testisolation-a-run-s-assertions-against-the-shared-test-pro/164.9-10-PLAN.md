<objective>
ROADMAP criterion 6: shared TEST's scheduled tick demonstrably no longer reaches production compute,
shown by reading the LIVE row rather than the migration that set it.

The hazard is real and pre-existing: the destination row is seeded with the production analytics
host, and that row feeds a network-tick function. So a tick on TEST can post to the production
service. ⚠️ It is routed here rather than fixed at its origin because the restore replays that seed
FAITHFULLY by an explicit founder decision — omitting it would leave TEST missing a setting its own
ledger claims applied — and because "which service does a TEST tick talk to" is the same question as
"whose rows is a TEST run asserting about".

⭐ The remedy chosen, with its reasoning: point TEST's row at the loopback discard literal that the
row's own allow-list constraint ALREADY permits. It needs no new infrastructure, it is legal under
the existing constraint without touching it, and an outbound attempt lands on a closed local port
and is refused harmlessly. The alternative — standing up a TEST-scoped service — would make the
asynchronous-tick trap load-bearing and require service-side observability this phase has no way to
build. ⛔ Neither remedy weakens the allow-list; the remedy changes which allowed value the row
holds.

⚠️ **THE LOOP, recorded rather than discovered later.** The replay reseeds the production host, so a
future restore re-arms this hazard. That is not a defect in the remedy; it is why the durable
deliverable is the MEASUREMENT. The gate catches it and says so. ⛔ It is NOT resolved by editing
the allowlist, and this plan books the residual with a named destination instead of pretending the
loop is closed.

Output: a marker-branched measurement arm in the existing gate, a TEST-only remediation that refuses
to run anywhere else, a runbook, and a booked residual.
</objective>
