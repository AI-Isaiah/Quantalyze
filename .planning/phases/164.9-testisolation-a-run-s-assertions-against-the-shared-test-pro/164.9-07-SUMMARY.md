# Phase 164.9 Plan 07: Two-directional extension guard and a value-pinning reference-data leg Summary

**Schema-scoped, two-directional `pg_extension` census with an extracted, database-free-testable `check_extension_guard()`, plus a third reference-data gate leg (`v_wrong_state`) pinning `public.profiles.manager_status` against its post-migration value — five new self-test arms, ratchet moved 27 → 32.**

## Performance

- **Duration:** ~75 min
- **Tasks:** 3 completed
- **Files modified:** 4

## Accomplishments

- Re-scoped the extension census from a whole-database `count(*)` to a public-schema NAME SET (one census line per extension), keeping the `extensions` key name stable per the plan's instruction, and extracted the comparison into `check_extension_guard()` — a pure function of two census files, the same testable shape `census_rollback_view` (arm 25) already established — so it can be exercised without a database.
- Made the guard fail independently in the LOSS direction and the GAIN direction, each with its own message, forbidding the naive `-ge` one-sided fix CONTEXT Area 6 names.
- Added a third reference-data gate leg (`v_wrong_state`), a sibling of the existing emptiness (`v_empty`) and shortfall (`v_short`) legs inside the same collect-first-raise-once PL/pgSQL block, pinning `public.profiles.manager_status` for the teaser sentinel row against its POST-migration value `'verified'` — the value `20260521150000_universal_signup_approval_gate.sql:28-31` sets and the INSERT-only replay never re-applies.
- Added five new self-test arms (28-32) and moved `EXPECTED_ARMS` 27 → 32, with the dated MEASURED line and the printed tally sentence moved beside it.
- Extended `baseline-fixture.sql`'s `fx_keep` table with a `status` column (not a new table — `tables=2` stays unaffected for arms 9/12/18) and its allowlisted replay to give the new arms a real fixture-side discriminator.

## Decisions Made

**1. The historical-migration search verdict (Task 1's first required measurement).** Searched `supabase/migrations/` and `supabase/schema/baseline.sql` for any extension creation targeting the public schema, explicitly or by relying on the default search path. `supabase/schema/baseline.sql` declares every extension with an explicit non-public schema (`pg_catalog`, `extensions`, or `vault`). One migration, `supabase/migrations/20260513094906_enable_pg_cron.sql:17`, runs `CREATE EXTENSION IF NOT EXISTS pg_cron;` with **no explicit schema clause at all** — relying on whatever the default search path resolved to when it ran. Per the plan's own literal rule ("If ANY historical migration did create an extension in public... implement the set comparison"), this migration's schema-ambiguous statement is treated as a hit, and the guard was implemented as a **NAME-SET comparison**, not a scoped count — the conservative, more rigorous choice, and one that additionally catches a same-count swap a scoped count could not. (Separately, that migration's own SQL is never replayed during a restore — the ledger seed for every migration file is a provenance sentence, not the applied statement — so it does not itself move the census; the ambiguity is why a count was not trusted, not evidence that this specific statement executes.)

**2. Loss-direction RED, quoted verbatim** (constructed pre/post census files, via the extracted `check_extension_guard()`, no database):
```
::error::EVIDENCE: post-census extensions=<none>, pre-census had pgcrypto. LOST from public: pgcrypto. An extension that lived in public was CASCADE-dropped and the dump did not put it back.
```

**3. Gain-direction RED, quoted verbatim** (same technique, pre/post swapped) — a DIFFERENT message, as required:
```
::error::EVIDENCE: post-census extensions=pgcrypto, pre-census had <none>. GAINED in public: pgcrypto. An extension now lives in public that did not before the restore — a DIFFERENT fault from something lost, and the dump did not intend to put anything there.
```

**4. Wrong-state RED, quoted verbatim** (arm 31, the real `--run --mode restore` dispatch against the throwaway lane — captured by a temporary, reverted debug print in `run_arm`'s "ok" branch, since the self-test only surfaces a FAILING arm's own captured output):
```
::error::restore-test-from-baseline: restore aborted at psql:.../restore.sql:416: ERROR:  restore aborted: reference row(s) came back in the WRONG STATE after the replay — public.fx_keep.status for id=2 disagrees after the replay (actual 6 char(s), expected 8 char(s)). The replay reproduces INSERT effects only; a later migration that UPDATEd this row was never re-applied, so the row is present at the right count but not the value a real restore should carry ([164.8.1-REPLAY-INSERT-ONLY-SCOPE]). Not closable by editing the allowlist — an UPDATE is not a literal INSERT (C2) — see the allowlist's own SCOPE BOUNDARY block; the transaction was rolled back, the database is unchanged.
```
("6 char(s)" = `newbie`, "8 char(s)" = `verified` — the row's actual and expected values' SHAPES only, never the values themselves, per the task's own instruction; confirmed the message text carries neither literal word, and arm 31 asserts that negatively.)

**5. The correct-state GREEN** (arm 32, default seam values — `public.fx_keep` id=1, whose allowlisted INSERT sets `status='verified'` explicitly) restores cleanly: `restore: tables=2 policies=1 functions=2 ledger_rows=3 survivors=3/3 filtered=1 mode=restore`, with no wrong-state fault — proving the leg discriminates rather than always firing.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The value-pinning leg needed a fixture analog to be testable without breaking ~10 pre-existing arms' pinned counts**
- **Found during:** Task 2
- **Issue:** The plan bounds the leg to `public.profiles`, which does not exist on the throwaway self-test lane. Hardcoding the check against `public.profiles` unconditionally would abort every restore-mode arm on an undefined relation. A new fixture TABLE would change `EXP_TABLES` and break arms 9/12/18's exact `tables=2` pin.
- **Fix:** Added the check as four environment seams (`REFDATA_WRONGSTATE_TABLE/ID/COL/EXPECTED`), matching the established `REFDATA_KIND_REGISTRY/COL/CHECK` pattern exactly, and pointed the self-test at a new `status` COLUMN on the existing `fx_keep` table (not a new table) plus an explicit value in one row of its existing allowlisted INSERT.
- **Files modified:** scripts/restore-test-from-baseline.sh, scripts/restore-test-from-baseline-fixtures/baseline-fixture.sql, scripts/restore-test-from-baseline-fixtures/migrations/20260103000000_fixture_c.sql
- **Verification:** Full self-test (32/32) confirms arms 9/12/18/22/23/24 (all of which touch `fx_keep`) are unaffected.
- **Committed in:** `1232d372`

**2. [Rule 3 - Blocking] Adding four new env seams raised `envSeams(SRC)`'s count past the vitest `SEAM_FLOOR=16` ratchet, and each new seam had to be documented in the `--help` ENV SEAMS block or the WR-04 test reds**
- **Found during:** Task 2
- **Issue:** `src/__tests__/restore-test-from-baseline.test.ts`'s `IN-05/WR-04` test requires every derived env seam to be named in the script's own `--help` header.
- **Fix:** Added a full `REFDATA_WRONGSTATE_*` entry to the `--help` ENV SEAMS block, matching the header/continuation-line format the per-seam calibration loop parses. Left `SEAM_FLOOR` itself unmoved (see Decisions #6) since it is a floor, not an exact count.
- **Files modified:** scripts/restore-test-from-baseline.sh
- **Verification:** `npx vitest run src/__tests__/restore-test-from-baseline.test.ts` — 43/43 passed, including the per-seam calibration loop over the new names.
- **Committed in:** `1232d372`

### Sequencing note (not a deviation, but worth surfacing per the dispatch instruction to flag plan issues rather than work around them quietly)

The plan assigns Tasks 1 and 2 their own `<verify>` blocks that each independently run `bash scripts/restore-test-from-baseline.sh --self-test` and require exit 0, while Task 3 alone is charged with raising `EXPECTED_ARMS`. Taken literally in strict task-commit isolation, Task 1's commit (which adds arms 28-30 but does not touch the ratchet) would report "an arm was ADDED without raising the ratchet" and fail its own self-test — the ratchet and the arms that require it cannot be separated across commits without one of them being self-test-red in isolation. Resolved by committing Tasks 1+2's arms together with the full ratchet raise (27→32) in one commit (`1232d372`, satisfying Task 3's own instruction to raise the ratchet "in the SAME commit as the arms"), and committing Task 3's remaining, genuinely separable contribution — sweeping the vitest file's own pinned literals and dispositioning every other count site — as its own commit (`a2f7907f`). All three tasks' `<verify>` blocks and `<acceptance_criteria>` were run and passed against the final, cumulative state; none was skipped.
