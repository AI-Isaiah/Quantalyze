<objective>
The dead-holder condition already DETECTS correctly and already fires. What is missing is the
consequence: the detection is a GitHub log annotation, and by the release step's own documented
design a log annotation does not change exit status. So a run concludes GREEN on DB assertions its
own harness has just declared untrustworthy — `FANOUT-GLOBAL-01` in its purest form.

Purpose: ROADMAP criterion 12. This plan is the phase's TRACER — the thinnest path through every
layer this phase modifies: a shared-TEST harness condition, a marker, a committed shell verdict,
a workflow step that runs it, and a falsification on a disposable local cluster that observes RED.

Output: a verdict script with its own self-test, a disposable-cluster drill that kills a real
holder, five paired verdict steps, and a source-shape gate that keeps the pairing true.

⚠️ **This plan edits `.github/workflows/supabase-migrate.yml`, and CONTEXT Area 3 requires that any
plan touching it state in writing which of two acts it is doing. IT IS A PLANNED ISOLATION FIX.**
It is NOT a workflow edit made to clear a red so a deploy can go out — the standing prohibition in
`CLAUDE.md` forbids that and this plan does not do it. The edit ADDS a failure mode to
`apply-test` (a dead holder now reddens it); it removes none. The consequence is deliberate and
follows from Phase 164.8's locked Area 1 decision that a failed TEST apply blocks the PROD apply:
an apply that ran unserialized against shared TEST is exactly an apply whose result must not gate
production.
</objective>
