## What was fixed, per class, per commit

### F2 — the post-mig-117 claim-token fence (13 failures → 0) — `e2f0c581`

`mark_compute_job_done` / `mark_compute_job_failed` require a non-NULL
`p_claim_token` that MATCHES the row's own `claim_token`. Production mints it in
`claim_compute_jobs[_with_priority]`; these fixtures seeded a `running` row by direct
INSERT, so the row carried `claimed_at`/`claimed_by` but no token — a state no real
claim can produce — and every arm answered `22023` at the entry fence before reaching
the behaviour under test.

Repaired at the call site: the fixture mints the token a claim would have written,
stores it on the seeded row and threads it through. In
`claim-failed-retry-dedupe-migrations` the token is instead READ OFF the claimed row
(`claim_compute_jobs_with_priority` RETURNS SETOF compute_jobs), which is the
production path exactly; that arm now also pins that a claim mints a token at all.

⚠️ **Two GREEN arms in this file set were VACUOUS and are fixed here too**, though
neither was in the red set:

| arm | why it could not fail |
|---|---|
| residual "concurrent mark_failed + reclaim_stuck leaves the row in a consistent state" | the token-less `mark_failed` always raised 22023, so only the watchdog branch could ever win. **No race was exercised.** |
| residual "child with un-done sibling-parent does NOT advance" | nothing advanced because the `mark_done` call never ran. The assertion held for the wrong reason. |

Both still pass after the repair, now for the right reason.

### F4 — the two one-offs (2 of 3 closed) — `cc867e42`

**`PGRST205`, reproduced by execution.** g10b's P13 read
`.from("information_schema.columns")`, which PostgREST resolves as a relation
literally named `public."information_schema.columns"` and answers
`PGRST205 Could not find the table … in the schema cache` on EVERY host —
`supabase/config.toml` exposes only `public` and `graphql_public`. Same
unexposed-schema class as plan 08's `cron` repair.

⭐ **This is the argument for the lane existing, stated as plainly as it can be.**
`PGRST205` is the one ROADMAP failure signature plan 03 recorded as **NOT
reproducible from tracked text**. A static reader cannot see it: nothing in the source
is wrong to look at, and the defect only exists relative to a running PostgREST's
schema cache. Running the corpus reproduced it on the first try — and it was NOT in
the file plan 08's census predicted (`request-allocator-holdings-sync-queued`), which
is a second reason re-derivation mattered.

⛔ The repair is not to widen `[api].schemas`. `public.compute_jobs` IS on the REST
surface, so the column's presence is asked directly of the relation.

**FALSIFIED, not assumed.** The probe was neutered to select
`reclaim_count_NEUTERED`, the neuter was asserted to APPLY (exactly one occurrence
replaced — a neuter that does not apply reads as green), and the arm went RED:

```
FAIL … P13: get_user_compute_jobs returns last_error=null (redacted) …
  "message": "column compute_jobs.reclaim_count_NEUTERED does not exist"
  Tests  1 failed | 18 skipped (19)
```

Restored from a `cmp`-verified byte backup; `grep -ac` for the neuter returns 0. ⛔ No
`git checkout --`, no `git restore`, no `git stash` was used anywhere in this round.

**The protocol-relative URL.** `BASE_URL` is NOT an unset variable in a vitest run:
Vite/vitest inject `process.env.BASE_URL` themselves (it mirrors Vite's `base`,
default `"/"`), and jsdom sets it to `"/"` for the same reason. `??` only falls back
on null/undefined, so the fallback never fired and the fetch target was the literal
`//api/match/decisions/holding`, which Node rejects with `ERR_INVALID_URL` before any
request leaves the process. The sibling `scenario-commit-rls` already carries this
exact defence and names the same cause; this file is brought into line with it rather
than inventing a second idiom.

## ⛔ The three left RED, with their causes derived

None of these is closable by a fixture. Each is recorded rather than papered over.

### 1. g10b P12 — a REAL production defect the retired kind was masking

`enqueue_compute_job` routes all three of its modes to the **ten-arg**
`_enqueue_compute_job_internal`, whose INSERT omits `status` entirely, so the row
takes the column DEFAULT `'pending'`. Only the older **seven-arg** overload still
carries migration 109's `v_initial_status := 'done_pending_children'` branch for a row
with parents, and nothing reaches it.

**Consequence: a job enqueued through the public wrapper WITH `parent_job_ids` never
enters the fan-in state**, so `mark_compute_job_done`'s fan-in advance can never see
it. The P12 invariant is silently absent in production.

⭐ Invisible to a static census by construction — it is a missing column in an INSERT
inside one of two same-named overloads — and it was masked, until now, by an error
raised earlier in the same call. Closing it needs a migration against a production
catalogue, which this milestone's gate work is ordered ahead of by decision. The
derivation is written at the assertion so the next reader does not re-derive it.

### 2. `match-decisions-xor-rls` — an assertion about a RETIRED unique index

⛔ **Plan 08's SUMMARY classified this as F3 (`match_decisions.decided_by`). That is
wrong** — the fixture already supplies `decided_by`. The measured failure is
`expect(boErrS2).not.toBeNull()`: a second `bridge_outcomes` row for the same
(allocator, strategy) was expected to collide with 23505 and did not.

The cause is in the catalogue's own words. `bridge_outcomes_unique_per_strategy_holding`
(migration 072) was **REPLACED** by `bridge_outcomes_allocator_match_decision_unique`
in migration 081 — "Natural per-decision key now that voluntary kinds … exist. Every
bridge_outcome FKs to one match_decision; one outcome per decision is the invariant".
Two different match_decisions legitimately get two outcomes now. The old index does
not exist in the baseline at all.

Repairing it means deciding what the arm should assert under the CURRENT invariant.
That is an intent question about a uniqueness contract, not fixture drift, and
rewriting the assertion is the one move this round was told not to make.

### 3. `request-allocator-holdings-sync-queued` — an UNREACHABLE branch

⛔ **Plan 08's SUMMARY attributed the `PGRST205` to this file. That is wrong too** —
its measured failure is `expected undefined to be true`.

`request_allocator_holdings_sync` returns `{already_inflight, next_attempt_at}` only
from an `EXCEPTION WHEN unique_violation` handler around `enqueue_compute_job`. But
`_enqueue_compute_job_internal` does an optimistic look-up FIRST and **RETURNS the
existing in-flight id** rather than raising, so the handler never fires and the RPC
answers `{ok, job_id}`. The arm's own title calls this "the previously-unreachable
Queued shape"; it is still unreachable.

Closing it needs a change to the RPC (a migration) or a decision that the Queued shape
is retired. Neither is a fixture fix.

## ⚠️ The one judgement call, stated so a reviewer can reverse it in one line

`match-decisions-holding-endpoint-rls` needs a running Next app server; the lane boots
a database only. After repairing the URL defect it would have failed with a connection
error instead of `ERR_INVALID_URL` — redder, not righter.

It now carries `HAS_BASE_URL` alongside `HAS_LIVE_DB`, matching
`scenario-commit-rls.test.ts` verbatim in shape.

**Why this is a missing precondition and not a bought green:** this file's own header
has documented that gate since it was written — *"Gate: requires
NEXT_PUBLIC_SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY + BASE_URL. Skips gracefully when
those are absent"* — and never implemented it. The arm runs whenever a server URL is
supplied (`BASE_URL=http://localhost:3000 npm run test:live-db` against a running
`next dev`). **Deleting the `HAS_BASE_URL` conjunct is the one-line change that makes
it unconditional again.** If a reviewer disagrees with the call, that is the line.

This is the only skip-count movement in the round: 80 → 81.
