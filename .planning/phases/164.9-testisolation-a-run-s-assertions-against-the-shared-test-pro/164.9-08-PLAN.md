<objective>
ROADMAP criterion 13's deliverable: the live-DB class runs somewhere it can go RED, or its drift is
fixed with a gate proven to bite. Plan 03 measured the class statically and handed this plan a named
backlog with destinations; this plan repairs it and stands the lane up.

⭐ **THE HOST DECISION, which CONTEXT reserved to Claude's discretion AFTER the measurement, and the
reasoning for it.** The lane targets the LOCAL STACK, not shared TEST:
1. This phase's whole thesis is that an assertion against a project this repo does not own is
   unreliable by construction. Standing a NEW lane up against shared TEST would ADD a global
   assertion surface at the moment the phase is removing them.
2. The local stack is per-run isolated by construction — a fresh database per run — which is the
   property criterion 2 spends a whole plan proving for the gates that cannot have it.
3. It consumes NO secret and NO repo variable, so it runs identically on a fork PR. That is what
   lets the aggregator judge it with its STRICT arm and no tolerance, the same reasoning the
   existing narrow seam lane records for itself.
4. It is already proven working in CI for another gate, so the question is not whether the shape
   boots.
5. RESEARCH measured that at least three of the five failure classes reproduce on ANY host — they
   are baseline- and fixture-level. Those are fixed here, not avoided by a host choice.

⛔ **THE COST, stated rather than discovered later:** a local-stack lane cannot catch drift that
exists only on shared TEST. That loss is acceptable because repo-versus-TEST ledger and body drift
already has its own gate, and repo-versus-production body drift has another. It is NOT acceptable
silently, so it is recorded here and in the lane's own header.

Output: the fixture and call-site repairs the census named, a dynamically derived lane corpus, a
lane config that never touches coverage, and a blocking CI job.
</objective>
