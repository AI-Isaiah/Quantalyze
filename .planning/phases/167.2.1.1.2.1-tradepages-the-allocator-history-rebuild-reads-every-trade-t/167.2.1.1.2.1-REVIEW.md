## Summary

The Bybit 7-day windowing, the cursor handling, the 729-day start, the midnight guard, the refusal-token count and the probe's read-only wrapper all hold up when traced. One new path silently under-reads. The OKX dedupe keys on the bare ccxt `id`. For OKX that is `tradeId`, which is numbered per instrument, so two different fills can share it. Three further MEDIUMs:

- A truncated read is still persisted after its WARNING.
- The generic walk now drops a legitimately new last page. This is latent today.
- The newly unblocked 729-day Bybit window reaches a transfer read whose behaviour past 365 days has not been measured.

Verification run: `pytest` on the six touched or new test files gives 269 passed. CI mypy line: `Success: no issues found in 121 source files`. Two of the findings were reproduced with the phase's own fakes (scratch script `<scratchpad>`, read-only, no network).

Checked and found sound:

- **Bybit request shape.** `since` maps to `startTime` and `until` to `endTime` through `handle_until_option`. `cursor` passes through. The windows are `[w, w+7d-1ms]` and tile with no gap or overlap. `nextPageCursor` is found on any row's `info`.
- **Midnight guard.** It uses a strict `<`. Within one UTC day, a start 729 days back is never refused. A start crossing midnight raises `BadRequest`. On the forced path that becomes `account_key_read_failed`, and on the unforced path it becomes `permanent`. `FORCED_REBUILD_REFUSAL_REASONS` still has 15 entries.
- **Probe is read-only.** `ReadOnlySupabase` exposes only `table().select`. The one write reachable inside `_fetch_and_price_window` (`_cache_coingecko_prices` upsert) raises `AttributeError` inside its own `try`. The probe makes no preflight, stamp, persist or audit call. Its stdout goes only through the validated emitter.
- **WARNING contents.** They carry only counts, constant inst types, the DB venue label, key and allocator ids (already logged by the existing loop), and closed-vocabulary tokens. No venue text appears.
- **OKX same-millisecond group at `since_ms`, split at a page edge.** The executor noted this. It needs fills at exactly 00:00:00.000 UTC of the window-start day and is negligible. Not reported.

## Critical Issues

### CR-01 (HIGH, BLOCKER): OKX id-dedupe drops real fills, because ccxt's OKX `id` is a per-instrument `tradeId` and not a unique fill key

**File:** `analytics-service/services/equity_reconstruction.py:592-605` (`_extend_unseen`), called at `:798` (OKX pass) and `:672` (Bybit). Same key in the probe: `analytics-service/scripts/allocator_history_probe.py:332, 360-367`.

**Issue:** `_extend_unseen` drops any row whose `row["id"]` is already in `seen`. The OKX `seen` set covers one whole instrument-type pass. For example, the `swap` pass holds every perpetual: BTC-USDT-SWAP, ETH-USDT-SWAP, and so on. ccxt 4.5.85 `okx.parse_trade` sets `id = safe_string(trade, 'tradeId')`. OKX numbers `tradeId` per instrument. It is not unique across instruments. The repo's own `trades_dedup_fill` index makes the same assumption, but that is a separate path. The collision risk is highest on FUTURES and OPTION, because every dated contract or strike starts its own sequence. So a fill on one instrument whose `tradeId` equals a fill on another instrument in the same pass is silently discarded. No WARNING fires, because `added > 0` for the page and the walk carries on.

Before this phase there was no dedupe, so this is a new silent under-read that the phase introduced. The probe's `trades_read` counts distinct `id` across every call and every inst type of a member, so it collapses the same rows. It cannot detect the loss, and the D-03 measurement inherits the blind spot.

**Reproduced:** the book holds 5 BTC-USDT-SWAP and 5 ETH-USDT-SWAP fills that share tradeIds `00000..00004`. Read through the real-ccxt OKX stub (`real_ccxt_client("okx", …)`) and `_fetch_trades_with_pagination`, the result was `book 10 read 5 ['BTC-USDT-SWAP']`. Every ETH fill was gone. In the replay this appears as wrong positions and quantities for every day after the missing fills. The forced rebuild then persists that curve (data integrity).

**Test gap:** every fixture gives globally unique ids (`trade_rows` `id_prefix`), so no test can catch this.

**Fix:** dedupe on a key that identifies the fill. The same fill re-read on an overlapping page has the same symbol and id, so a finer key still absorbs real repeats:
```python
def _extend_unseen(trades, seen, page):
    added = 0
    for row in page:
        row_id = row.get("id")
        if row_id is not None:
            key = (row.get("symbol"), row_id)
            if key in seen:
                continue
            seen.add(key)
        trades.append(row)
        added += 1
    return added
```
Apply the same `(symbol, id)` key in the probe's `_describe_call` / `trades_read`. Add a test where two instruments in one OKX pass share a `tradeId` and both fills must reach the replay. Bybit `execId` is globally unique, so the change is harmless there.

## Warnings

### WR-01 (MEDIUM, data integrity): a read cut off by a ceiling or a full-page stop is still persisted as complete

**File:** `analytics-service/services/equity_reconstruction.py:675-693` (Bybit window stop / ceiling), `:803-818` (OKX pass stop / ceiling), `:865-880` (generic walk).

**Issue:** each loud stop logs one WARNING and then returns the partial list as if it were the whole book. `_fetch_and_price_window` builds rows from it, and the forced rebuild replaces the window and audits `reconstruct_complete`. Nothing in the telemetry or the audit marks the read as truncated. The plan 01 threat model names this exact boundary ("a truncated read becomes a wrong curve once a forced rebuild persists it"), but the mitigation stops at a log line. Two concrete cases:

- **OKX.** One order sweeping more than 100 resting orders produces more than 100 fills with the same `ts`. Under an inclusive `end`, the fills at `oldest` and `oldest+1` together over 100 do the same. Either way the pass stops with "did not advance", and every older fill of that instrument type in the 89-day window is dropped, not just the rest of the group.
- **Bybit.** More than 10,000 fills in one 7-day window (about 1,430 a day, plausible for a grid or market-making bot) are cut at `_BYBIT_WINDOW_PAGE_CEILING`. The rest of that week is dropped, and the read continues with the next window.

The D-04 rebuild runbook (plan 06 Task 1 step 4) gates only on the probe's `okx_passes_ended_full`. The probe has no Bybit equivalent, and the rebuild run itself is not gated on these WARNINGs.

**Fix:** have each truncating stop return a flag, for example `(trades, truncated: bool)`, and carry it into `telemetry`. On the forced path (`require_anchor=True`), refuse with an existing token rather than persist. `account_key_read_failed` through the gather converter keeps the 15-token set. At minimum, add a Bybit `windows_ended_full` count to the probe and make plan 06's gate read it.

### WR-02 (MEDIUM, latent, data integrity): the generic walk drops a legitimately new last page whose rows all sit at `cursor_ms`

**File:** `analytics-service/services/equity_reconstruction.py:852-864`

**Issue:** after the first page, `cursor_ms = prev_max + 1`, and the venue answers rows `>= cursor_ms`. A page whose rows all carry `timestamp == cursor_ms` is new data, for example a final fill exactly 1 ms after the previous page's newest. But `max_ts <= cursor_ms` treats it as non-advancing, and since `cursor_ms != since_ms` it is dropped without being appended. A short page also skips the WARNING. The base appended before the check, so this is a regression.

**Reproduced:** 3 rows, then a 4th at `prev_max + 1`, with a page cap of 3. Result: `generic book 4 read 3`.

A second case on the same walk, not new but still silent under D-02: a full page cut inside a same-millisecond group advances to `max_ts + 1`, so the rest of the group is skipped and no WARNING fires, because `max_ts > cursor_ms`.

Latent today. The only venue on this walk is Binance, which raises `ArgumentsRequired` first (TODOS `167.2.1.1.2.1-BINANCE-TRADES-NEED-SYMBOL`). It goes live as soon as that entry is fixed.

**Fix:** treat only `max_ts < cursor_ms` as non-advancing. Better: advance to `cursor_ms = max_ts` (not `+1`) and add rows through `_extend_unseen` (with CR-01's key), stopping when a page adds nothing. That handles both cases. Add a test with a last page at exactly `prev_max + 1` and one with a group split at the page edge.

### WR-03 (MEDIUM, data integrity, conditional): the 729-day Bybit window now reaches a transfer read whose behaviour past 365 days is unmeasured, and an empty answer would be persisted silently

**File:** `analytics-service/services/equity_reconstruction.py:2324-2325` (`_account_rebuild_window` Bybit arm), `:5010-5014` (unforced start). The transfers are read at `:3410-3420` from `transfers_since_ms = start_ms`.

**Issue:** before this phase, a Bybit account's 730-day crawl died on the trade read (retCode 10001), so it never wrote. D-01 moves the start inside the trade limit, so the crawl now goes on to `fetch_ccxt_transfers` from 729 days back. The repo itself treats Bybit deposit history as 365 days deep (`services/nav_twr.py:123` `BYBIT_DEPOSIT_TERMINUS_DAYS = 365`, flagged low-confidence). RESEARCH Open Question 1 left "fails or returns empty" unresolved. The plan 06 runbook only catches the "fails" branch, as a probe failure class. If Bybit answers windows older than a year with an empty list, deposits and withdrawals from days -729 to -365 are missing from the replay. The forced rebuild then persists a curve whose older year is wrong, and the probe's records (which carry no transfer counts) would not show why.

**Fix:** before any D-04 Bybit rebuild, measure it. Add per-member deposit and withdrawal counts for the windows older than 365 days to the probe, or run one read-only check. Until that is measured, either clamp the Bybit transfer read to the documented retention and mark the replay `pre_terminus`, as the OKX terminus path does at `:3410-3414`, or refuse the forced rebuild for Bybit accounts whose window predates the transfer retention.
