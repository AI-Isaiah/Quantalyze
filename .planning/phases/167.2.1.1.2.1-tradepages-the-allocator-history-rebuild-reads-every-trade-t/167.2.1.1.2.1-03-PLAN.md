<objective>
Keep every Bybit request inside Bybit's two-year trade-history limit (D-01) and refuse, never clamp, a crawl that
crosses that limit at midnight (RESEARCH Q3 and Pitfall 4).

D-01 verbatim from CONTEXT: "Founder 2026-10-23, AskUserQuestion: 'Shorten the window (Recommended)'. An account holding
a Bybit key starts its window at the first whole UTC day Bybit still serves (729 days instead of 730). Older stored days
stay as they are (ACCTREBUILD D-01) and the seam date is recorded (ACCTREBUILD D-03). No new refusal token."

Why the midnight refusal is code and not only a handoff rule (Claude's discretion, recorded here): `end_date` is fixed
when the job starts and the trade read runs later, so a job that starts at 23:50 UTC reads at a start 730 days old.
Bybit would reject it (RESEARCH A4 says how Bybit measures two years is assumed), so the guard refuses before sending,
measured against the wall clock the read itself uses. It raises `ccxt.BadRequest` with static text, the class Bybit's
retCode 10001 arrives as (ccxt maps 10001 to BadRequest), so both paths dispose it exactly as they already dispose the
venue's own rejection: forced, the gather converter refuses `account_key_read_failed`; unforced, the generic arm fails
it permanent. No new token (D-01), no new exception class, no clamp (a clamp would start the trades after the curve
starts, RESEARCH Anti-Patterns).

Purpose: SC-1 ("never earlier than its two-year limit") and SC-2 (a2's refusal was this limit; the re-run in plan 06
needs it gone).
Output: the window rule at both sites, the guard, the pins.
</objective>
