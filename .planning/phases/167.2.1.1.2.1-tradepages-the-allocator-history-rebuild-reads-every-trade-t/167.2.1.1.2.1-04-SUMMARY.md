# Phase 167.2.1.1.2.1 Plan 04: CRAWL-DIAGNOSTICS WARNINGs and the TODOS edits Summary

**A member of a forced account rebuild that comes back refused, or as an MT5 failure result, is now named in one WARNING carrying static fields only (allocator, member key, venue, and the refusal token or the outcome, error kind and MT5 arm name); a code fault is no longer called a venue fault; and the ledger closes `[167.2.1.1.2-ACCOUNT-CRAWL-DIAGNOSTICS]` with its history kept and books the three follow-ups this phase found but does not fix.**

## What changed

- `services/equity_reconstruction.py`, `_crawl_whole_account` gather loop: the `ForcedRebuildRefusedError` branch logs `account crawl refused allocator= key= venue= reason=` before the re-raise (the loop raises on the first refused member in key order, so one line per refused job). The `DispatchResult` branch logs `account crawl failed allocator= key= venue= outcome= error_kind= arm=` before the return, `arm` being the `_MT5_BACKFILL_MESSAGES` key whose fixed text equals the result's message, else `unmapped`.
- `_AccountCrawlRetryableError.__init__`: for `error_kind == "unknown"` the text is "whole-account rebuild crawl hit an unclassified fault (<class>); nothing was written"; every other kind keeps "retryable venue fault". Docstring updated in one sentence.
- `tests/test_reconstruct_whole_account.py`: four tests, ten cases (below).
- `TODOS.md`: the diagnostics heading gains `, CLOSED 2026-10-23` inside its parenthesis (the only changed line of the old text) and a `**CLOSED 2026-10-23 (Phase 167.2.1.1.2.1 TRADEPAGES plan 04).**` paragraph; a new section `## Phase 167.2.1.1.2.1 (TRADEPAGES) — routed items (logged 2026-10-23)` at the end of the file holds `167.2.1.1.2.1-STRATEGY-BYBIT-7DAY`, `167.2.1.1.2.1-BINANCE-TRADES-NEED-SYMBOL` and `167.2.1.1.2.1-BYBIT-TRADES-LINEAR-ONLY`.

## The Binance finding (re-read at HEAD, not taken from RESEARCH or the plan)

What a symbol-less Binance trade read ends as:

- `_fetch_trades_with_pagination` sends every venue except OKX and Bybit to `_fetch_trades_paginated_one_pass`, which calls `fetch_my_trades(None, ...)`. It catches only `ccxt.NotSupported`.
- ccxt's Binance `fetch_my_trades` (read in the installed 4.5.85; `requirements.txt` pins 4.5.88) raises `ArgumentsRequired` when the symbol is absent and the market type is neither stock nor option. It does so before any request.
- `classify_exception(ccxt.ArgumentsRequired(...))` was executed: it returns `unknown` (a `ccxt.ExchangeError`, in neither the transient nor the permanent tuple).
- **Forced path:** `_crawl_account_key` lets it escape (only `RateLimitExceeded` is caught); the gather loop logs the class, `classify_exception` gives `unknown`, so the job ends FAILED with error kind `unknown` via `_AccountCrawlRetryableError` ("unclassified fault (ArgumentsRequired)" after this plan; "retryable venue fault" before), retried, nothing written.
- **Unforced path:** the handler's generic `except Exception` arm: FAILED, error kind `unknown`, the scrubbed ccxt text as the message, a `reconstruct_failed` audit, retried.
- **So RESEARCH Q1 was wrong:** the failure is NOT `account_key_read_failed` and not permanent, on either path. It is a deterministic `unknown` failure that retries to the queue's attempt cap and never yields a trade. Booked as `167.2.1.1.2.1-BINANCE-TRADES-NEED-SYMBOL` with this disposition. No Binance key existed at the 2026-10-22 census (taken from the ACCTREBUILD plan 09 SUMMARY and the existing `167.2.1.1-BINANCE-FUTURES-WALLET-UNREAD` entry; not re-measured, no PROD access).
- Also confirmed for the third entry: with no symbol and no type, installed ccxt's `get_bybit_type` returns `linear`, and the rebuild passes no category.
