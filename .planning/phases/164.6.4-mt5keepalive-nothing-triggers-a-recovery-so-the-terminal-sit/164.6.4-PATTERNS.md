## 1. The new background loop — COPY THE SKELETON FROM `dispatch_loop`, THE BODY FROM `heal_mt5_terminal_session`

**Analog A (loop skeleton): `main_worker.dispatch_loop` / `watchdog_loop`.**
The canonical periodic-cancellable idiom, used identically by all three worker loops:

```python
async def dispatch_loop(worker_id: str, interval: float = 30.0) -> None:
    while not SHUTDOWN.is_set():
        try:
            await dispatch_tick(worker_id)
        except Exception as exc:  # noqa: BLE001
            logger.error("dispatch_loop tick failed: %s", exc, exc_info=True)
        # Wait for interval OR shutdown, whichever comes first
        try:
            await asyncio.wait_for(SHUTDOWN.wait(), timeout=interval)
            break  # SHUTDOWN was set
        except asyncio.TimeoutError:
            pass  # interval elapsed, loop again
    logger.info("dispatch_loop exiting (shutdown)")
```

**COPY:** the `while not SHUTDOWN.is_set()` gate; the per-tick `try/except Exception`;
the `wait_for(SHUTDOWN.wait(), timeout=interval)` sleep (it is BOTH the cadence and the
cancellation point — never `asyncio.sleep`); the exit log line.
⭐ `except Exception` deliberately does NOT catch `CancelledError`, and
`main.lifespan._crash_handler` early-returns on `task.cancelled()` — so cancellation
propagates and shutdown stays clean. Preserve that.

**AVOID from this analog:** its guard is only per-tick. The `while` header, the `wait_for`
block and the exit `logger.info` all sit OUTSIDE any handler — good enough for a loop whose
tick is the only risky part, NOT good enough for the AST predicate in §2, which demands the
whole body inside one top-level `try`. A `logger.error(... exc_info=True)` argument
evaluation is also unguarded here (IN-06 class).

**AVOID from `daily_enqueue_loop`:** the startup tick before the loop (an extra unguarded
statement) and the `_daily_enqueue_already_ran_today()` dedup — no analogue here.

**AVOID from `_bridge_healthz` (defined inline in `main.lifespan`):** it is a closure in
`lifespan`, so it is invisible to `inspect.getsource` by symbol and awkward to AST-gate. The
new loop must be a MODULE-LEVEL coroutine in `services/`, like the heal.

**Analog B (the body, the guard, the lease, the knobs): `services.mt5_relogin.heal_mt5_terminal_session`.**
Copy its exact shape — `try:` as the single top-level statement, kill switch read FIRST
before anything is constructed, bounded lease, `wait_for(to_thread(...))`, then the
outer `except Exception` whose handler body is itself ONE nested `try/except BaseException`
with an argument-free fallback log:

```python
    except Exception as exc:  # noqa: BLE001 — see the docstring; this is the control
        try:
            logger.warning(
                "mt5 boot heal did not complete — ... (exc_class=%s scrubbed=%s)",
                type(exc).__name__,
                _describe_exception_for_log(exc, credentials),
            )
        except BaseException:  # noqa: BLE001 — see the comment; this is the control
            logger.warning(
                "mt5 boot heal did not complete, and the failure could not be "
                "described — continuing without it"
            )
```

Also copy: `credentials: tuple[...] | None = None` bound BEFORE the first statement that can
raise (so the handler never hits an unbound local); the nested
`except Mt5TerminalBusyError` → INFO skip; the nested `except asyncio.TimeoutError` → ERROR
"ABANDONED at the budget, a round-trip is still in flight" arm. ⛔ Those nested handlers sit
INSIDE the one top-level `except`, never beside it — the AST gate allows exactly one
top-level handler.

⚠️ **The composition problem the plan must solve explicitly:** the heal's never-raise shape
is written for a ONE-SHOT coroutine (`return` on every early exit). A LOOP must not `return`
on a transient miss — it must `continue`. The safest shape, and the one that keeps the AST
predicate reusable unchanged, is **two symbols**: a never-raising one-shot
`probe_mt5_session_once()` shaped exactly like the heal, and a thin
`mt5_session_monitor_loop()` whose body is also entirely inside one top-level guard and whose
`while` lives inside it. Decide and name this in the plan; the AST gate's "exactly ONE
top-level statement and it is the `try`" rule is what forces it.

## 3. Tuning knobs read per call — `_env_float` IS the pattern, use it unchanged

**Analog:** `services.mt5_relogin._env_float` + `_relogin_budget_s` / `_relogin_lease_wait_s`.

```python
def _relogin_lease_wait_s() -> float:
    """The bound on ACQUIRING the terminal — deliberately short (D-29)."""
    return _env_float(
        _MT5_RELOGIN_LEASE_WAIT_ENV,
        _MT5_RELOGIN_LEASE_WAIT_DEFAULT_S,
        floor=_MT5_RELOGIN_LEASE_WAIT_FLOOR_S,
        ceiling=_MT5_RELOGIN_LEASE_WAIT_CEILING_S,
    )
```

Properties to preserve for the **DETECTION POLL CADENCE** knob: read PER CALL (never a
module-load constant); absent/blank/non-numeric/zero/negative/`nan`/`inf` all fall back to
the default; `math.isfinite` tested FIRST (a naive `floor <= v <= ceiling` ACCEPTS `nan`);
`effective_ceiling = max(ceiling, default)` and `effective_floor = min(floor, default)` so a
window can never be empty from either end; the VALUE is never logged, only the NAME and the
fault class (T-164.6.2-12); `_log_configuration_fault_once` for throttling.

⛔ **Scope fence for the plan (criterion 1, D-3):** the only knob in scope is the
**DETECTION POLL CADENCE**. The **KEEPALIVE INTERVAL** is forbidden here. Name the constants
so the two can never be conflated by a later reader — e.g. `MT5_SESSION_POLL_S`, and do NOT
introduce any symbol containing `KEEPALIVE_INTERVAL`.
⚠️ A cadence floor must be derived (as the budget's is) so a poll cannot be configured to
fire faster than its own lease wait + round-trip, which would starve the lease.

## 7. Durable verdict recording (D-3 / `[MT5-VERDICT-SINK-01]`)

**What this codebase already has, in ascending durability:**

   **⛔ NEVER raises** (`except Exception` → one warning). Better, but still a log; same
   retention risk.
3. ⭐ **A service-role table — the right analog for "readable AFTER the fact".**

**Table analog: `reconciliation_reports`** (`supabase/migrations/20260416125429_reconciliation.sql`)
— one row per (subject, date), a CHECKed `status` enum, a count, a JSONB detail column,
`UNIQUE` on the natural key so the writer can upsert idempotently on a re-run, RLS ENABLED
with NO public policies (service-role only), and a self-verifying `DO` block. The migration
header states what it does and what it deliberately does NOT do. Copy all of that shape.

**Writer analog: `services/job_worker.py`'s `_upsert_report`:**

```python
    def _upsert_report() -> None:

            {

                "report_date": report.report_date,
```

`services.db.db_execute` is the required seam — it runs the synchronous Supabase call on the
bounded `_DB_EXECUTOR` so the event loop is never blocked.

**Shape the plan should use for an episode record** (CONTEXT `<specifics>`: `authorized_at`,
`went_dark_at`, how it was resolved): one row per episode, natural key = (terminal_key,
went_dark_at), upserted so a repeated poll inside one dark window updates rather than
duplicates, and a `resolved_at` + `resolution` column written when the next authorized
reading lands. That makes `n` computable by a single query rather than by re-deriving from
logs — which is exactly the D-3 requirement.

⛔ **Three hazards to design against, all measured in this repo:**
- A DB write inside the never-raising loop is a NEW raise source. It must sit inside the
  top-level guard, and a sink failure must NOT change the detection verdict — copy
  `emit_mt5_stage_event`'s posture ("instrumentation must not change what a caller observes",
  T-153.3-24).
- Adding a migration makes the PR apply to shared TEST FIRST, and a data-reading `DO` block
  that `RAISE EXCEPTION`s on an unexpected count can apply to PROD and REFUSE on TEST
  (`[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`). Keep the self-verifying block structural.
- If the migration seeds any reference row (e.g. a `compute_job_kinds` entry), it must go
  through the Phase 164.8.1 refdata allowlist or a TEST restore will lose it.

**If the plan chooses NOT to add a table,** the fallback with precedent is
`emit_mt5_stage_event` with a dedicated `stage` + `outcome` — but then the plan must state
how the record is read after the fact, because "readable while it scrolls past" is the named
failure this criterion exists to prevent.

## Shared Patterns (apply to every new file)

### Never-raise posture
**Source:** `services/mt5_relogin.heal_mt5_terminal_session` + `mt5_client.emit_mt5_stage_event`.
**Apply to:** the loop, the probe, the sink writer. One top-level `except Exception`; the
handler body itself guarded by `except BaseException` with an ARGUMENT-FREE fallback line.

### Kill switch first
**Source:** `services/closed_sets.mt5_enabled_server` + the heal's call site.
**Apply to:** the loop entry — read per call, before any construction, fail-closed, log at
INFO naming the ENV VAR.

### Per-call validated env knobs
**Source:** `services/mt5_relogin._env_float`.
**Apply to:** the detection cadence and any new bound. Floor AND ceiling, both clamped
against the default; `math.isfinite` first; value never logged.

### Never log a secret; names only
**Source:** T-164.6.2-12 as enforced throughout `mt5_relogin.py`, plus
`mt5_client._redact_credential_values`.
**Apply to:** every log line and every raise on the new path.

### Off-loop blocking work
**Source:** `asyncio.wait_for(asyncio.to_thread(_heal_blocking, ...), timeout=budget_s)` with
the client CONSTRUCTED INSIDE the thread body (rpyc's connect carries no timeout of its own),
and `services.db.db_execute` for Supabase calls.
**Apply to:** the probe and the sink write. ⛔ Never join the abandoned thread after a
`wait_for` expiry — that holds the lease for the length of the hang (WEDGE-01 / D-25).

## Things the CONTEXT decisions appear to have mis-assumed

1. **D-4's "fix the shared site by value".** `_raise_last` has no credentials and the client
   stores none; its other callers have no values to redact by. The achievable form is a
   parameterised `_raise_last`, not an unconditional one. (§6)
2. **D-2's "a fifth `main.lifespan` task".** `lifespan` already creates FIVE tasks
   (`dispatch_loop`, `watchdog_loop`, `daily_enqueue_loop`, `healthz_bridge`, `mt5_boot_heal`)
   — the new one is the **sixth**, and `_LIFESPAN_CREATE_TASK_COUNT_AT_164_6_2 = 5` must be
   re-cut to 6. Both CONTEXT and the roadmap phrase it as "fifth"; the count pin is the
   measurement.
3. **CONTEXT's `<code_context>` mentions `redact.py` / `pii-scrub.ts` alongside the fix.**
   Those are key-name denylists and cannot catch a bare value — they are not the lever for
   criterion 5. (§6)
4. **The lease roster is SIX, not five** — `_PRODUCTION_LEASE_SITES` was already re-cut by
   164.6.2 to include the boot heal; the new poll makes it SEVEN.
