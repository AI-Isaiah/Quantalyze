# Phase 164.6.4 MT5KEEPALIVE: Code Review Report

**Reviewed:** 2026-09-15T17:53:36Z
**Depth:** standard

## Summary

Production code read in full: the two new modules (`services/mt5_session_episodes.py`,
`services/mt5_session_monitor.py`), the `_raise_last` parameterisation in
`services/mt5_client.py`, the `HealOutcome`/`source` rework in `services/mt5_relogin.py`,
and the sixth `lifespan` entry in `main.py`. Tests were read only where a gate's ability
to fail was in question.

The four named hazard classes came back as follows. **Credential disclosure: clean, and
I looked hard.** **Never-raises / loop survival: clean structurally, with one gate hole
(WR-05).** **Terminal contention: clean.** **Dataset honesty: three defects (WR-01, WR-03,
WR-04).** Detail under *Critical Issues*.

The six Warnings cluster in one place: the recorder and the loop are correct about
*what they write* and wrong about *what they infer and what they fail to say*. WR-01 is
the sharpest — the compare-and-set that the module's own docstring calls "load-bearing
and not defensive programming" has its result thrown away, so a caller that LOST the race
still stamps `started_at_is_lower_bound: false`. WR-03 is the phase's own stated defect
class (a blind instrument indistinguishable from a healthy one) reappearing on the three
configuration paths that return before any reading is recorded.

## Critical Issues

**None found.** Each of the four hazard classes was checked against the code rather than
against the prose, and the reasoning that earns the "clean" verdict is recorded here so a
later reader can attack it rather than inherit it.

**1. Credential disclosure — clean.**
`_raise_last`'s three `raise Mt5ClientError(...)` points all route through
`_redact_with_optional_credentials`, which delegates to `_redact_credential_values` —
so the shape scrub is not lost on the credential-bearing arm (`_redact_credential_values`
opens with `scrub_freeform_string(str(text))` before the by-value pass). The code is parsed
out of `err[0]` before the text is rewritten, so `-6` survives. `login()` and
`initialize_with_credentials()` both pass the triple; the five credential-free callers pass
nothing, which is correct — there is no value to redact by. The `None` arm is
`scrub_freeform_string` only, i.e. exactly today's behaviour, so nothing regressed.

Every field written to a row was traced to its producer: `metadata.opening_kind` /
`closing_kind` are module `Final[str]` constants; `opening_code` / `closing_code` are the
terminal's integer code; `error` is `f"{opening_kind}:code={opening_code}"` or the literal
`superseded`; `attribution_limit` is a fixed string; `opened_by` / `closed_by` are the two
`HEAL_SOURCE_*` constants. `HealOutcome.verdict` — the one field that carries
terminal-supplied free text — is read by the two `logger` calls in `mt5_relogin` and by
nothing in `mt5_session_episodes`. **No credential, account number, gateway host, port,
terminal key or free-text detail can reach a row.** Every log line added by this phase
carries only `type(exc).__name__`, an env var NAME, a kind constant, an int code or a count.

**2. Never-raises — clean structurally.**
`run_mt5_session_monitor_tick`, `mt5_session_monitor_loop`, `record_mt5_session_reading`
and `record_mt5_heal_outcome` each have a body that is exactly one `Try`, no
`finally:`/`else:` on the guard, a single bare `except Exception`, and a handler body that
is one nested `try` with an argument-free `except BaseException`. No statement sits outside
the guard. The loop's only `break` is the one `SHUTDOWN` earns (in the `try` body, not a
handler). The handler-order trap is handled correctly: `except asyncio.TimeoutError: pass`
is FIRST and the broad arm below it does not `break`. `except BaseException` wraps no
`await` anywhere, so shutdown cancellation still propagates and `_crash_handler`'s
`task.cancelled()` early return holds. See WR-05 for the one escape route the gate cannot see.

**3. Terminal contention — clean.**
`run_mt5_session_monitor_tick` delegates to `heal_mt5_terminal_session` and takes no lease,
constructs no `Mt5Client` and holds no raw lock. `_PRODUCTION_LEASE_SITES` is unchanged at
six and is pinned with `==` rather than `>=`, with a synthetic calibration that splices a
lease into the monitor's own text and asserts the scanner reports it. The bounded acquire
(`wait_s=_relogin_lease_wait_s()`) is inherited, so a busy terminal is a SKIP and never a
queue. The DB writes happen strictly OUTSIDE the `async with mt5_terminal_lease(...)` block
— verified by structure, not by comment.

**4. Dataset honesty — three defects, all Warning-tier.** See WR-01, WR-03, WR-04.
The parts that hold: rows are written per TRANSITION (the `live_state == reading.state`
early return is the mechanism); the open episode is re-read from the DB on every
observation, so there is no in-process episode state a redeploy can truncate;
`not_measured` closes nothing and writes nothing; `code == 0` is recorded `unattributed`
and never guessed into a state; `code is None` (busy skip, budget abandon) falls through to
`not_measured` correctly because `None == 0` is `False`.

## Warnings

### WR-01: `_close_row` discards the compare-and-set result, so a caller that LOST the race still claims a measured transition

**File:** `analytics-service/services/mt5_session_episodes.py` — symbols `_close_row`,
`record_mt5_session_reading`

**Issue:** `_close_row` ends with a bare `await db_execute(_update)` and is typed `-> None`.
The UPDATE carries `.eq("status", "running")` — the compare-and-set whose docstring says it
"is LOAD-BEARING AND IT IS NOT DEFENSIVE PROGRAMMING" — but nothing reads how many rows it
matched. A zero-row UPDATE is indistinguishable from a winning one at the call site.

`record_mt5_session_reading` then sets `continued_a_measured_run = True` unconditionally
after the measured-close branch, and passes `started_at_is_lower_bound=not
continued_a_measured_run` into `_open_row`. Under the exact scenario the module is designed
to tolerate — a Railway deploy overlap, two containers having read the same row as live —
container B's close no-ops against A's already-closed row, and B nonetheless stamps
`started_at_is_lower_bound: false` on the row it opens, i.e. asserts "the previous state's
run was just closed as MEASURED" about an UPDATE that touched nothing. The CAS protects the
ROW; it does not protect the caller's INFERENCE, and the docstring's argument
("READING THE ROW FIRST AND BRANCHING IN PYTHON DOES NOT FIX IT") stops one line short of
the place where the same interleave is still being read as a measurement.

The secondary cost is on the same path: B's `_open_row` then closes A's freshly-inserted
episode as `superseded`, so each race produces a zero-duration junk row and fires the
"an open row was still standing … This is an ANOMALY" WARNING.

**Fix:** make the close report whether it bit, and gate the inference on it.

```python
async def _close_row(...) -> bool:
    ...
    response = await db_execute(_update)
    # A zero-row UPDATE means the CAS lost: another writer closed this row first.
    return bool(rows(response))
```

```python
            else:
                continued_a_measured_run = await _close_row(
                    live,
                    state=live_state,
                    closing_kind=reading.kind,
                    closing_code=reading.code,
                    source=source,
                    measured=True,
                )
                if not continued_a_measured_run:
                    logger.warning(
                        "mt5 session episode: the measured close lost its "
                        "compare-and-set — another writer closed this run "
                        "first. The run opened next carries "
                        "started_at_is_lower_bound: true, because THIS process "
                        "measured no transition it can bound."
                    )
```

⚠️ PostgREST returns the updated rows only when `Prefer: return=representation` is in
effect; supabase-py's `.update()` sets it by default, but confirm against the pinned
client version rather than this sentence, and fail CLOSED (`continued_a_measured_run =
False`) if the response shape cannot be read.

### WR-02: the monitor's first tick runs concurrently with the boot heal on every deploy, and nothing sequences them

**File:** `analytics-service/main.py` — the `tasks` list in `lifespan`;
`analytics-service/services/mt5_session_monitor.py` — symbol `mt5_session_monitor_loop`

**Issue:** `mt5_session_monitor_loop` ticks FIRST and sleeps second
(`while not SHUTDOWN.is_set(): await run_mt5_session_monitor_tick(); <wait>`). `lifespan`
creates `mt5_boot_heal` and `mt5_session_monitor` back to back, so on **every deploy** two
tasks drive `heal_mt5_terminal_session` against the ONE shared terminal at the same instant.
Three consequences, none of them named in the module docstrings, the plans or the summaries:

1. Whichever task loses the bounded acquire records a `busy_skip` → `not_measured`,
   so the blind-run counter starts at 1 on every boot and the monitor's first REAL
   reading is delayed by a full poll interval.
2. If the winner finishes inside `_relogin_lease_wait_s()` (2.0 s default — an
   already-authorized probe is one round trip), the loser then acquires and probes the
   terminal a SECOND time at boot, for no information.
3. The two `record_*` calls run after their respective lease releases and can interleave at
   their `await` points, so both can read zero open rows and both insert. `_open_row`'s
   invariant-restoring loop then supersedes one — meaning the "an open row was still
   standing when a new run was opened … This is an ANOMALY, not a normal path" WARNING fires
   on an ordinary boot. An alarm that fires on the normal path stops being an alarm, which
   is this milestone's own defect class.

The two-writer rationale in `_read_open_rows` names only "Railway OVERLAPS CONTAINERS ON
DEPLOY". The single-process, same-event-loop case is unaddressed and is guaranteed rather
than occasional.

**Fix:** make the loop wait before its first tick, so the boot heal owns the boot window and
the monitor owns everything after it. This is a one-statement reorder, and it keeps the
"flipping the kill switch takes effect without a redeploy" property intact.

```python
        while not SHUTDOWN.is_set():
            # ⛔ WAIT FIRST. `main.lifespan` starts `mt5_boot_heal` in the same
            # gather; ticking immediately means two tasks drive the heal against
            # ONE terminal at boot, and the loser's busy_skip is a blind reading
            # on every deploy. The boot heal owns the boot window.
            try:
                await asyncio.wait_for(
                    SHUTDOWN.wait(), timeout=session_poll_interval_s()
                )
                break
            except asyncio.TimeoutError:
                pass
            except Exception as exc:  # noqa: BLE001 — the control; it CONTINUES
                ...
            try:
                await run_mt5_session_monitor_tick()
            except Exception as exc:  # noqa: BLE001 — the control; it CONTINUES
                ...
```

⚠️ P-inner asserts the `while` body is statements that are each a `try`; the reorder
preserves that. `_LOOP_SURVIVAL_MUTANTS` and `_LOOP_GUARD_MUTANTS` anchor on comment text
that moves with the blocks, and `_splice` asserts anchor uniqueness — re-run the calibration
and expect it to stay green rather than assuming it.

### WR-03: the blind-instrument escalation cannot fire on the three configuration paths, which are exactly the paths that go silent forever

**File:** `analytics-service/services/mt5_relogin.py` — symbol
`heal_mt5_terminal_session`; `analytics-service/services/mt5_session_monitor.py` — symbol
`run_mt5_session_monitor_tick`; `analytics-service/services/mt5_session_episodes.py` —
symbols `_count_blind_reading`, `blind_run_escalation_threshold`

**Issue:** `_CONSECUTIVE_NOT_MEASURED_READINGS` is only ever incremented inside
`record_mt5_session_reading`. Four paths return BEFORE any reading is recorded:

* the monitor tick's own kill-switch arm (`_log_configuration_fault_once`, once per process);
* `heal_mt5_terminal_session`'s credentials-absent / credentials-invalid arms
  (`_log_configuration_fault_once`, once per process);
* its gateway-absent / port-not-numeric arms (same throttle).

On any of these, the loop ticks forever, records NOTHING, increments nothing, and — because
the throttle is per process per reason — emits exactly ONE line for the life of the
container. After that line scrolls past, a monitor that has measured nothing for days is
byte-identical in the logs to a monitor that has found the session healthy every tick. That
is the module's own stated defect class ("a quiet instrument and a healthy one emit the same
thing", `mt5_session_episodes` section (d)) reproduced on the paths where it is most likely:
a Railway variable that was never set, or a kill switch someone flipped and forgot.

The escalation the phase built covers only `busy_skip`, `budget_abandoned`, `ipc_fault` and
the `code=0` sentinel — the cases where the mechanism at least reached the terminal.

**Fix:** record the configuration refusals as readings too, so the same counter and the same
escalation cover them. They are honestly `not_measured`; the point is that they are
*counted*.

```python
        if not mt5_enabled_server():
            _log_configuration_fault_once(...)
            # ⛔ COUNTED, not merely logged-once. A throttled line is invisible
            # after the first tick, and an uncounted refusal cannot reach the
            # blind-run escalation — which is the control for exactly this.
            await record_mt5_session_reading(
                KIND_DISABLED, None, source=source, poll_interval_s=poll_interval_s
            )
            return
```

with a new `KIND_DISABLED` / `KIND_NOT_CONFIGURED` pair in `mt5_session_episodes`,
both classifying to `not_measured` in `classify_reading` (they fall through by default).
⛔ Do not reuse `KIND_BUSY_SKIP` — the class in a row and the class in a log line are pinned
to each other on purpose.

### WR-04: "a DARK run's duration is the EXPOSURE this phase exists to collapse" is false on the mechanism's primary path

**File:** `analytics-service/services/mt5_session_episodes.py` — module docstring and
symbol `record_mt5_heal_outcome`

**Issue:** `record_mt5_heal_outcome` reports the FIRST probe's reading and then the FINAL
re-probe's, within one tick. On the path the monitor exists for — find `-6`, heal it — that
is `no_authorized_account/-6` → `dark` followed by `healed` → `authorized`, both inside the
same tick. The dark run is therefore OPENED and CLOSED seconds apart, and its
`completed_at - started_at` measures **the heal**, not the dark window. The actual exposure
is bounded by `since_previous_reading_s` on that row (up to one poll interval), which is a
different field entirely.

The module docstring states the opposite as a flat contract: "an AUTHORIZED run's duration
is the session LIFETIME … and a DARK run's duration is the EXPOSURE this phase exists to
collapse." The authorized half is true. The dark half is true only for an episode the
monitor failed to heal across multiple ticks — i.e. the exception, not the rule. A successor
phase that reads the sentence and computes `SUM(completed_at - started_at) WHERE state =
'dark'` will conclude the exposure is seconds when it is up to a poll interval, and the
whole point of D-3 is that the successor's arithmetic is done against these rows.

**Fix:** correct the sentence and name the field that actually carries the quantity. No code
change is required — the data is already there.

```
  an AUTHORIZED run's duration is the session LIFETIME (the number a successor
  chooses the keepalive interval from). ⛔ A DARK run's DURATION is NOT the
  exposure: on the heal-succeeds path the dark run is opened and closed inside
  ONE tick, so its duration measures the HEAL. The exposure is bounded by the
  dark row's own `since_previous_reading_s` — the gap to the previous MEASURED
  reading — and is unbounded only where `started_at_is_lower_bound` is true.
```

### WR-05: P-inner's escape scan checks `break`/`raise` but not `return`/`continue`, so two real escape routes leave the gate green

**File:** `analytics-service/tests/test_mt5_session_monitor.py` — symbol
`_loop_survival_defects`

**Issue:** the rule reads
`if isinstance(node, (ast.Break, ast.Raise))` and its own defect message claims to catch
"a handler that ends the loop". Two statements end or corrupt the loop and are not in that
tuple:

* `return` in a per-tick handler — ends `mt5_session_monitor_loop` for the life of the
  process, exactly the silent death the predicate is named for, with P-outer never entered
  so nothing logs;
* `continue` in the interval-wait handler — skips the wait and produces the hot loop the
  handler-order comment is written against.

This is not a style nit: the predicate is the ONLY control for the property, the module is
the only thing it polices, and a future edit taking either shape ships green. The gate's
stated contract ("a handler that `break`s or re-`raise`s ENDS THE LOOP") is narrower than
the hazard it claims.

**Fix:** widen the node set and add the two calibrating mutants, so the widening is a gate
rather than a claim.

```python
                    if isinstance(
                        node, (ast.Break, ast.Raise, ast.Return, ast.Continue)
                    )
```

and in `_LOOP_SURVIVAL_MUTANTS`, beside `per-tick-handler-BREAKS`:

```python
    "per-tick-handler-RETURNS": (<same anchor>, "...\n                    return\n..."),
    "sleep-handler-CONTINUES": (<unique sleep-arm anchor>, "...\n                    continue\n..."),
```

⚠️ `_splice` asserts anchor uniqueness; the sleep arm's anchor must be taken from its own
`logger.error` text, which differs from the tick arm's ("the interval wait failed" vs
"a tick escaped its own guard").

### WR-06: the tick carries no overall deadline, so the detection cadence is unbounded and unlogged — and the cadence FLOOR's derivation asserts the opposite

**File:** `analytics-service/services/mt5_session_monitor.py` — the
`_MT5_SESSION_POLL_INTERVAL_FLOOR_S` derivation comment and symbol
`run_mt5_session_monitor_tick`

**Issue:** the floor comment derives itself from a stated property: "A tick must never still
be running when the next one starts … Taking the heal's own ceiling makes that structural:
the slowest tick the heal permits itself still finishes inside one interval."

The heal's budget bounds only the `asyncio.to_thread(_heal_blocking, …)` call. A tick also
pays: the bounded lease acquire (`_relogin_lease_wait_s()`), and then the recorder's
Supabase round trips — which are UNBOUNDED at the tick level and carry postgrest-py's
`DEFAULT_POSTGREST_CLIENT_TIMEOUT = 120` seconds each. `record_mt5_heal_outcome` issues up
to two readings, each up to one SELECT + N closes + one INSERT. A degraded Supabase can
therefore stretch a single tick well past the 600 s default cadence, and nothing logs it —
the loop simply ticks less often than its own configured interval while every line it emits
still reads normal.

Overlap itself is impossible (the loop is sequential — `await tick` then wait), so the
floor's conclusion happens to hold for a reason the comment does not give. The actionable
half is the invisible cadence stretch.

**Fix:** bound the tick and say so when the bound bites. The guard already contains the
`await`, so this adds no escape route.

```python
        await asyncio.wait_for(
            heal_mt5_terminal_session(
                source=HEAL_SOURCE_SESSION_MONITOR,
                poll_interval_s=interval,
            ),
            # The whole tick, not merely the heal's own thread budget: the
            # recorder's Supabase calls carry postgrest's 120 s default and there
            # are up to six of them, so an unbounded tick silently stretches the
            # cadence past the configured interval.
            timeout=interval,
        )
```

⚠️ `asyncio.TimeoutError` from this `wait_for` lands in the tick's existing
`except Exception` arm, which logs `exc_class` and continues — correct, but the message
("the tick did not complete") should be made to distinguish a budget bite from a fault, or
an operator cannot tell a slow sink from a broken gateway. ⛔ Do NOT add an
`except OSError` arm to distinguish it: `asyncio.TimeoutError is TimeoutError` and its MRO
runs through `OSError`.

### IN-01: `_close_row`'s `state` argument is dead on every superseded close

**File:** `analytics-service/services/mt5_session_episodes.py` — symbol `_close_row`, and
its three superseded call sites in `_open_row` and `record_mt5_session_reading`

**Issue:** `state` is read exactly once, in `if measured and state == STATE_AUTHORIZED`.
Every superseded close passes `measured=False`, so `state` is never read on those paths —
yet all three sites compute `state=stale_state or STATE_DARK`, fabricating a default that
nothing consumes. A reader will reasonably infer that a superseded close records the row as
dark. It does not: `_close_row` preserves the previous `metadata` and never overwrites
`metadata["state"]`.

**Fix:** make `state` optional (`str | None`) and pass `state=stale_state` at the superseded
sites, so the `or STATE_DARK` fabrication disappears and the `None` case is visible in the
signature.

### IN-02: a superseded close of an unparseable row writes the literal `"None:code=None"` into `error`

**File:** `analytics-service/services/mt5_session_episodes.py` — symbol `_close_row`

**Issue:** when `row["metadata"]` is not a dict, `metadata` starts as `{}`, so
`metadata.get("opening_kind")` and `metadata.get("opening_code")` are both `None`. That
branch is only reached when `measured` is true, and an unparseable row always takes the
`measured=False` arm — so the string is not reachable today. It becomes reachable the moment
someone widens `_recognised_open_state`, and `"None:code=None"` in a durable column is worse
than an empty one.

**Fix:** `error = f"{opening_kind or 'unknown'}:code={opening_code if opening_code is not None else 'unknown'}"`,
or assert the precondition the branch relies on.

### IN-03: `session_poll_interval_s()` is read twice per iteration, so the interval recorded in a row can differ from the one actually slept

**File:** `analytics-service/services/mt5_session_monitor.py` — symbols
`run_mt5_session_monitor_tick`, `mt5_session_monitor_loop`

**Issue:** the tick reads it to hand to the heal (whence it rides into
`metadata.poll_interval_s` and into `blind_run_escalation_threshold`), and the loop reads it
again for the wait. Reading per call is deliberate and correct (CR-02), but the two reads
straddle the tick, so an operator retune between them puts one number in the row and a
different one on the wire. It also means the escalation threshold and the actual blind span
can disagree for one tick.

**Fix:** read once per iteration at the top of the `while` body, inside the per-tick guard,
and pass the same value to both. ⚠️ Keep the read INSIDE a guard — a module-scope or
loop-header read is the CR-02 shape that took uvicorn down.

### IN-04: the outermost fallback `logger.error` in the loop is itself unguarded

**File:** `analytics-service/services/mt5_session_monitor.py` — symbol
`mt5_session_monitor_loop`, the final `except BaseException` body

**Issue:** if that argument-free `logger.error` raises, the exception escapes
`mt5_session_monitor_loop` and reaches `_crash_handler` → `SHUTDOWN.set()`. Practically

`heal_mt5_terminal_session` already carries and that the shared predicate MANDATES. Recorded
for completeness, not as a regression: closing it would require changing the predicate for
three symbols at once.

**Fix:** none recommended. If it is ever worth closing, close it at the predicate, never at
one call site.
