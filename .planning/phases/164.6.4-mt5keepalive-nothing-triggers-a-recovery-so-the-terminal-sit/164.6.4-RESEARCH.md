## Summary

Every load-bearing mechanism this phase needs already exists in the tree and was read this session. `heal_mt5_terminal_session` is a complete, lease-correct, never-raising, credential-free **detector followed by a conditional heal** whose verdict vocabulary (`already_authorized` / `healed` / `not_healed:{reason}:code={n}`) is exactly the episode vocabulary D-3 asks for. What is missing is three things and only three: **(a)** something that calls it on a cadence without being able to take the worker down, **(b)** somewhere durable for the verdict to land, and **(c)** the `_raise_last` by-value fix, which criterion 5 correctly makes a precondition rather than a nicety because the loop multiplies how often that path fires.

Three findings change the shape of the plan and none of them is visible from the CONTEXT alone. **First, the AST never-raises predicate cannot be reused verbatim** — it requires the function body be *exactly one* `Try`, which for a loop produces a guard whose handler **ends the loop** on the first tick error, i.e. a keepalive that dies silently and leaves the worker green. A loop needs *two* properties (an outer guard the task can never escape, and an inner per-tick guard the loop can never be killed by) and a predicate that asserts both. **Second, `except BaseException` — the IN-06 fallback shape the heal uses — must never wrap an `await` in a loop**: measured on this repo's own venv (Python 3.12.13), `asyncio.CancelledError` is **not** an `Exception` subclass, so `except Exception` correctly lets shutdown cancellation through while `except BaseException` would swallow it and hang `lifespan`'s 10 s shutdown gather. **Third, the detector cannot tell whose account is authorized**: the allocator/derive paths call `Mt5Client.login(...)` with *per-customer* credentials on the same shared terminal and `close()` deliberately never calls `shutdown()`, so after any per-account job the terminal is authorized **as that customer**. `assert_session_authorized()` answers "some account is authorized", never "the house session is alive" — which is a correctness note for the *trigger* (still right: `-6` means nobody is authorized) but a **validity hazard for D-3's lifetime data**, and it is the single biggest threat to the n>1 measurement this phase exists to start collecting.

A fourth finding is procedural and should reach the founder before planning finishes: **ROADMAP criterion 1 and CONTEXT D-3 read in opposite directions.** Criterion 1's literal text is a deliverable (*"The interval **is chosen** against MORE THAN ONE measured session lifetime"*); D-3 is an explicit refusal to choose it here. A verifier reading criterion 1 literally will mark this phase incomplete no matter how well it ships. See §Contradictions.

**Primary recommendation:** ship a new `services/mt5_keepalive.py` whose loop is a *pure scheduler* — it calls the existing `heal_mt5_terminal_session()` unchanged in behaviour (which already probes credential-free, heals only `-6`, re-probes, holds exactly one bounded lease and cannot raise) — and move the durable **episode record into `services/mt5_relogin.py`, beside the verdict that produces it**, writing one row per *transition* into `public.cron_runs` under a distinct `cron_name` (no migration, table already service-role-writable and GDPR-classed). ## 1. An asyncio loop in `main.lifespan` that CANNOT take down the worker

### 1.1 The hazard, verified at source

`main.lifespan` builds a `tasks` list and attaches `_crash_handler` as a done-callback to every member. `_crash_handler` reads, verbatim from `analytics-service/main.py`:

```python
def _crash_handler(task: asyncio.Task) -> None:
    if task.cancelled():
        return
    exc = task.exception()
    if exc is not None:
        logger.error(
            "Worker task %s crashed: %s", task.get_name(), exc, exc_info=exc
        )
        SHUTDOWN.set()
```
[VERIFIED: analytics-service/main.py, `lifespan` → `_crash_handler`, read this session]

⭐ Two consequences the planner must hold at once:

1. **A raise sets `SHUTDOWN`**, which stops `dispatch_loop`, `watchdog_loop` and `daily_enqueue_loop` — while uvicorn keeps answering `/health`. That is the silent analytics outage D-2 is written against.
2. **`task.cancelled()` returns early.** So cancellation at shutdown is *already safe*, provided the loop lets `CancelledError` propagate. It does so for free: [VERIFIED, measured this session on `analytics-service/.venv/bin/python`, Python **3.12.13**] `issubclass(asyncio.CancelledError, Exception)` is **False**. An `except Exception` guard therefore cannot swallow cancellation. ⛔ An `except BaseException` guard **can**, which matters below.

### 1.2 How the heal achieves never-raising today, and what the gate actually checks

`heal_mt5_terminal_session`'s **entire body is one top-level `try` with exactly one `except Exception` handler**, whose handler body is itself exactly one nested `try` with an `except BaseException` fallback that takes **no arguments to evaluate**. The nesting exists because `logger.warning`'s arguments (`type(exc).__name__`, `_describe_exception_for_log(exc, credentials)`) are evaluated *before* `logging` is entered and `logging` only swallows formatting errors during emit, not argument evaluation (the module's own IN-06 note).

The AST predicate `_heal_guard_defects` in `tests/test_mt5_relogin.py` asserts, and I read each branch:

- the function's non-docstring body is **exactly one statement** and it **must be the `try`**;
- exactly **one** handler, catching bare `Exception` (a narrowed handler is a named defect);
- the handler body is **exactly one** nested `Try` whose handler list is exactly `["BaseException"]`, with no `finally:`/`else:`;
- the outer guard has **no `finalbody` and no `orelse`** (WR-04 — both sit *outside* the handler, so a raise there reaches `_crash_handler`);
- `mt5_enabled_server` appears inside the guard (the kill switch is covered).

It is calibrated: `_HEAL_GUARD_MUTANTS` splices five escape routes (`finally-outside-the-handler`, `else-outside-the-handler`, `narrowed-handler`, `fallback-narrower-than-the-failure`, `handler-body-grew-an-unguarded-statement`) into a **copy** of the shipped source and asserts the predicate names a defect for each, and that each mutant **parses** (a first draft produced a `SyntaxError` mutant and "passed" without reaching the assertion).
[VERIFIED: analytics-service/tests/test_mt5_relogin.py — `_heal_guard_defects`, `_HEAL_GUARD_MUTANTS`, `test_the_heal_body_sits_entirely_inside_one_top_level_except_exception`, `test_the_never_raises_predicate_REDS_on_every_escape_route`; and RUN this session: both that structural test and the criterion-5 asymmetry test pass — `2 passed in 1.89s`]

### 1.3 ⛔ THE PREDICATE CANNOT BE REUSED VERBATIM FOR A LOOP — and copying it is worse than not gating

**"Body is exactly one `Try`"** forces the loop *inside* the guard. The guard's handler then runs **once**, after which the `try` is over and **the loop is gone**. A single transient DB error on tick 3 would silently end the keepalive for the life of the process, with a WARNING that looks exactly like the heal's transient wording and a worker that stays green. That is the *same defect class* this phase exists to remove (nothing notices), arriving inside the fix.

⭐ A loop needs **two** properties, and the planner should gate both:

| Property | Shape | What it protects |
|---|---|---|
| **P-outer** — the task can never escape | whole body inside one `try` / `except Exception`, handler body itself guarded (IN-06), no `finally:`/`else:` | `_crash_handler` → `SHUTDOWN.set()` |
| **P-inner** — the loop can never be killed by one tick | every statement of the `while` body inside a `try` whose handler catches bare `Exception` and **continues** | a keepalive that dies quietly on tick 3 |

The three shipped loops already carry P-inner and nothing else, and the shape is uniform: `dispatch_loop`, `watchdog_loop` and `daily_enqueue_loop` each wrap their `*_tick()` in `except Exception as exc: logger.error(...)` and then sleep via `await asyncio.wait_for(SHUTDOWN.wait(), timeout=interval)` / `break` on set / `except asyncio.TimeoutError: pass` on elapse. `_bridge_healthz` in `main.py` uses the identical sleep idiom.
[VERIFIED: analytics-service/main_worker.py `dispatch_loop`/`watchdog_loop`/`daily_enqueue_loop`; analytics-service/main.py `_bridge_healthz`]

⛔ **They do NOT carry P-outer** — an exception raised by `SHUTDOWN.wait()` or by `logger.error`'s own argument evaluation escapes them to `_crash_handler`. For the three shipped loops that is arguably correct (a dispatch loop that cannot sleep *should* take the worker down). For the keepalive it is not: a **best-effort** MT5 instrument must never be able to stop job processing. So the new loop is **stricter than its neighbours**, deliberately, and that asymmetry should be written at the site in this repo's voice rather than discovered later.

### 1.4 Cancellation, shutdown and the two traps

- `lifespan`'s `finally` sets `SHUTDOWN`, gathers with `timeout=10.0`, and only then `t.cancel()`s. ⛔ **A loop that sleeps with a bare `await asyncio.sleep(interval)` will not exit within 10 s** at any sane cadence and will be force-cancelled every deploy. Use the `wait_for(SHUTDOWN.wait(), timeout=…)` idiom — it is the house pattern and it exits immediately.
- ⛔ **Never put `except BaseException` around an `await`.** IN-06's fallback is correct *only* because it wraps an argument-free `logger.warning`. Around an `await` it would swallow `CancelledError` (measured: not an `Exception` subclass) and the 10 s gather would hang until the force-cancel, then hang again.
- ⚠️ [VERIFIED, measured this session] `asyncio.TimeoutError is TimeoutError` (builtin) on 3.12.13, and `TimeoutError.__mro__` is `TimeoutError → OSError → Exception → BaseException`. So **`except OSError` swallows the budget timeout.** If any tick handler catches `OSError` for socket errors it will silently eat the `wait_for` expiry that the heal logs at ERROR as its most important outcome.

### 1.5 The lifespan wiring, and the pin that will red

`tasks` currently holds five `create_task` calls: `dispatch_loop`, `watchdog_loop`, `daily_enqueue_loop`, `healthz_bridge`, `mt5_boot_heal`. The new loop becomes the **sixth** and must be in the same list so it inherits `_crash_handler` (it is a *containment* contract, not a crash contract — the loop's own P-outer guard is what makes the callback inert).

⛔ **A gate will red by construction and must be re-cut deliberately:**

```python
_LIFESPAN_CREATE_TASK_COUNT_AT_164_6_2 = 5
...
assert len(tasks) == _LIFESPAN_CREATE_TASK_COUNT_AT_164_6_2, (...)
```
[VERIFIED: analytics-service/tests/test_mt5_relogin.py, `_LIFESPAN_CREATE_TASK_COUNT_AT_164_6_2` and `test_CRITERION_1_lifespan_starts_the_heal_exactly_once_as_a_task`]

It is `==`, it is the *anti-vacuity leg* of the criterion-1 pin (measured independently of the heal's name so a silently-stopped predicate cannot take both halves down together), and its own message says *"Re-cut it deliberately."* Re-cut to 6; do not weaken to `>=`. Its mutant-calibration sibling asserts the count falls by **exactly one** on the excised mutant, so that arithmetic still holds.

## 2. Detection semantics — what a credential-less check can and cannot tell you

### 2.1 What `assert_session_authorized()` actually does

It calls **`self._mt5.initialize(timeout=self._ipc_timeouts_ms["initialize"])`** under a `_timed("session_authorized", …)` bracket, converts any transport raise into a shape-scrubbed `Mt5ClientError(0, …)`, and on a falsy return calls `self._raise_last()`. It passes **no credential and none may ever be added** — its own docstring: *"A detector that carried a credential could not be used to DECIDE whether to send one — it would already have sent it."*
[VERIFIED: analytics-service/services/mt5_client.py, `Mt5Client.assert_session_authorized`]

`_raise_last` then takes a **second** round-trip (`last_error()`), and that is where the code comes from:

| Observed | Meaning | Remedy class |
|---|---|---|
| returns `None` (no raise) | *Some* account is authorized; the bridge answered | none — record `authorized` |
| `Mt5ClientError.code == -6` | ⛔ The bridge **ANSWERED** and **NO ACCOUNT IS AUTHORIZED**. `terminal_info()` is null in this state, so `connected` and `trade_allowed` **cannot be read at all** | ⭐ THE one fault this phase's heal owns |
| `code == -10004` | Bridge **not attached** | redeploy the gateway |
| `code == -10005` | Bridge attached, terminal **not answering** — the modal-login-dialog wedge | ⛔ a redeploy does NOT fix it; VNC console |
| `code == 0` | ⚠️ A **sentinel for THREE distinct faults**: an unknown `last_error`, a malformed `last_error` shape, or a transport raise converted by `_raise_last`'s own except arm | unattributable — the verdict's detail text is the only discriminator |
| any other code | non-IPC terminal fault | read against the MT5 error table |

⚠️ **IN-02, and it is load-bearing for this phase:** `-6` is *only ever observable through `last_error()`*. If that second round-trip is the broken one, the fault is classified `code=0` and healed **not at all**. Fail-closed is right (a credential is never sent on a guess) — but it means **the one fault the keepalive exists to catch is undetectable whenever the second round-trip is the broken one**, and the episode record must say `unattributed`, never `authorized` and never `dark`.
[VERIFIED: analytics-service/services/mt5_client.py `_raise_last`; analytics-service/services/mt5_relogin.py `_heal_blocking` docstring, IN-02 paragraph]

### 2.2 ⛔ Reuse the prober's vocabulary — it is already the repo's

`mt5-not-authorized` (`-6`) · `mt5-no-ipc` (`-10004`) · `mt5-ipc-timeout` (`-10005`) · `mt5-terminal-error` (non-IPC code, or `initialize` ok while `terminal_info()` is not an object) · `mt5-ssh-transport` (no PROBE line — *the prober's own transport*) · `mt5-probe-timeout` (*the prober's own 120 s budget*) · `measure-fail` (the CLI was absent) · plus the OK reading, whose `info` line is `initialize=true last_error=<n> connected=<b> trade_allowed=<b>` with **the two booleans RECORDED AND NEVER JUDGED**.

### 2.4 Detection latency: what can be MEASURED (criterion 2) and the DETECTION cadence

⛔ True detection latency (time from *lapse* to *notice*) is **unknowable** — nothing observes the lapse. What is measurable, and what criterion 2 should be read as demanding, is a **bound**, and it comes free from two stamps the episode record already has:

```
detection_latency ≤ went_dark_at − last_authorized_reading_at   (≤ one poll interval)
```

Plus a genuinely independent cross-check: the **hourly prod-prober** reads the same terminal from inside the container over a different transport. Two instruments disagreeing is itself a measurement. ⚠️ Mining the prober's archives is rejected by D-3 (they are polluted by self-test fixtures that print `mt5-not-authorized` by name, and a scheduled run carries no `NARROWED DIAGNOSTIC dispatch of arm mt5:` execution anchor) — but *comparing a future prober run against a future episode row*, both forward-dated, is not mining history and is the honest way to close criterion 2's "MEASURED".

**The DETECTION cadence — `MT5_SESSION_POLL_INTERVAL_S` — derived from instrument bounds and ZERO lifetime observations:**

| Input | Value | Source |
|---|---|---|
| rpyc request bound (worker chain) | `MT5_REQUEST_TIMEOUT_S`, default **30 s** | [VERIFIED: services/mt5_client.py, `MT5_REQUEST_TIMEOUT_S = float(os.getenv("MT5_REQUEST_TIMEOUT_S", "30"))`] |
| MT5 IPC ceiling for `initialize` | `MT5_INITIALIZE_TIMEOUT_MS`, default **20000** | [VERIFIED: services/mt5_client.py, `MT5_INITIALIZE_TIMEOUT_MS = int(os.getenv("MT5_INITIALIZE_TIMEOUT_MS", "20000"))`] |
| Round-trips a *detect-only* tick makes | **2** (`initialize`, then `last_error` via `_raise_last`) | rows 2–3 of the heal's own five-trip table |
| Round-trips a *detect-then-heal* tick makes | **5** — already derived and gated | `_MT5_RELOGIN_ROUND_TRIPS: Final[int] = 5`, budget `5 × 30 + 10 = 160 s`, ceiling **300 s**, floor `MT5_REQUEST_TIMEOUT_S` |
| Existing independent instrument's cadence | **hourly** | prod-prober schedule |

⭐ **The derivation, stated so a reader can check it rather than trust it:**
- **Floor** — a tick must never still be running when the next one starts, so the cadence floor is the worst-case tick, i.e. the existing heal budget (**160 s** at defaults, **300 s** at the declared ceiling). Below that the loop would overlap itself against a shared terminal.
- **Ceiling** — at or above **3600 s** the loop measures nothing the hourly prober does not already measure, so it adds contention without adding information.
- **Duty cycle** — worst-case share of wall-clock the keepalive can hold the terminal is `tick_budget / cadence`. At the heal's 160 s budget, a **600 s** cadence bounds it at ~27% *in the pathological case where every tick both times out and heals*, and at roughly one round-trip (single-digit seconds) in the overwhelmingly common `already_authorized` case. A 900 s cadence bounds the pathological case at ~18%.
- Against the measured exposure (**≥2 h 34 m confirmed dark**, inside a ≈8 h 05 m bracket), any cadence in the 10–15 minute band collapses exposure by one-and-a-half orders of magnitude, and the difference *between* 600 s and 900 s is immaterial to that.

⛔ **This number is the DETECTION cadence and is NOT the keepalive interval.** It is derived from timeouts and from the prober's cadence; **no session-lifetime observation enters the arithmetic**, which is exactly why choosing it does not violate criterion 1 or D-06. Ship it through `_env_float`-style validation with a floor and a ceiling, in the house idiom, so an operator typo cannot produce a tick that overlaps itself.

### 2.5 ⛔ `services/mt5_probe.py` is NOT reusable

It is *"the ONE MT5 login+read+probe body"*, consumed by the two validate paths, and it logs in with **per-user** credentials. Using it here would violate D-1, P-3 and criterion 3 in one call. [VERIFIED: analytics-service/services/mt5_probe.py module docstring]

## 3. The lease, and criterion 4

### 3.1 What the lease guarantees, and what it does not

`mt5_terminal_lease(terminal_key, *, wait_s=None)` — `wait_s=None` acquires **unbounded** (the batch behaviour, used by all three job sites); a float bounds the acquire and raises `Mt5TerminalBusyError` at the bound. A timed-out acquisition **releases nothing, bumps nothing and stamps nothing** (the raise sits above the `try`). On every exit path the `finally` runs, in this order and the order is load-bearing: **bump the epoch → un-stamp occupancy → release the lock**.
[VERIFIED: analytics-service/services/mt5_concurrency.py, `mt5_terminal_lease`]

⭐ **It genuinely serializes.** A keepalive tick holding the lease cannot interleave with a job's terminal-IPC region, because both go through the one registry (`_mt5_terminal_lock_for`, keyed by `mt5_terminal_key(host, port)` — ⛔ never a second hand-spelled `f"{host}:{port}"`).

⚠️ **It does not bound the other direction.** IN-04, stated at the site: the heal refuses to queue behind real work, but **real work DOES queue behind the heal** — `run_derive_broker_dailies_job`, `_fetch_mt5_account_balance` and `_fetch_mt5_account_rows` all acquire with `wait_s=None`. So a keepalive tick can make a job wait for up to the tick's budget, now **on a cadence, forever** rather than once at boot. That is criterion 4's real content, and the mitigation is the cadence derivation in §2.4 plus keeping the detect-only path at 2 round-trips.

### 3.2 ⭐ D-08's hazard does NOT transfer — verified, and worth stating so the planner does not over-apply it

D-08 struck "heal on session open" because `job_worker._make_mt5_session` builds in **PREFLIGHT**, outside and before the lease, and *"a touch there would stamp the generation early"*. The natural worry is that a periodic lease release now lands inside somebody's preflight-to-lease window and fences a legitimate derive read.

It does not, for two independently verified reasons:

1. **The epoch binds on FIRST TOUCH, not at construction.** `_assert_live` sets `self._epoch = current` on the first call and returns; a preflight-built client has `_epoch is None` until the job's own `login()` *inside* its lease. [VERIFIED: analytics-service/services/mt5_client.py, `Mt5Client._assert_live` — *"First touch — it happens under the lease that owns this session."*] `_make_mt5_session` only constructs (`Mt5Session(client=Mt5Client(host, int(port_raw)), …)`) and touches nothing. [VERIFIED: analytics-service/services/job_worker.py, `_make_mt5_session`]
2. **The construction fence is a ContextVar, and preflight carries no token.** `_MT5_LEASE_OCCUPANCY` defaults to `None` and is set only by `begin_mt5_lease_occupancy` inside the lease; the module comment states the exemption as *"the honest encoding of 'this construction is not happening under anyone's lease'"*. [VERIFIED: analytics-service/services/mt5_client.py, `_MT5_LEASE_OCCUPANCY` / `begin_mt5_lease_occupancy`]

⛔ The constraint that *does* transfer: **one `Mt5Client` per lease acquisition.** The tick must build its client **inside** its own lease (and inside the `to_thread` body, so the unbounded `rpyc.classic.connect` is covered by the caller's `wait_for`) and `close()` it before releasing — exactly as `_heal_blocking` does. ⚠️ `close()` is safe to call per tick: since D-35 it **never calls `mt5.shutdown()`** and touches only our own rpyc socket. [VERIFIED: analytics-service/services/mt5_client.py, `Mt5Client.close`]

### 3.3 ⛔ The busy-skip doctrine must NOT be copied verbatim

`mt5_relogin` skips on `Mt5TerminalBusyError` with the reasoning *"a busy terminal is a terminal somebody is already successfully using, which is itself evidence that the session is fine and there is nothing here to heal."*

⛔ **That inference is false for a keepalive.** It is cheap and defensible for a once-per-boot heal. For a loop it is a standing claim about session state that the tick **did not measure** — and a terminal held by a *failing* job is precisely the case where it is most wrong. The repo's own doctrine, stated three times in the prober arm and once in WR-01's re-probe fix, is *nothing unmeasured may be claimed*.

⭐ **Correct behaviour:** still skip (never queue ahead of real work), log at INFO, and record the tick as **`not_measured`** — never as `authorized`, never as a transition. The next tick answers. ⚠️ And add a guard the boot heal did not need: **N consecutive busy skips is itself a signal** (the loop has been blind for N × cadence); it should escalate the log level rather than stay INFO forever.

### 3.4 Criterion 4's test: the harness already exists, teeth included

`tests/test_mt5_derive_branch.py` has exactly the shape criterion 4 demands — `_run_two_concurrent_mt5(neuter_lock: bool)` drives two MT5 flows through an `_OrderedMt5Transport` that appends `(tag, "enter"/"exit")` to a shared `order` list, then asserts the second flow's `enter` index is **after** the first's `exit`; and immediately re-runs with `neuter_lock=True` (a **fresh `Lock` per call**, which serializes nothing) asserting the interleave **does** happen, so the positive assertion cannot be vacuous.
[VERIFIED: analytics-service/tests/test_mt5_derive_branch.py, `_run_two_concurrent_mt5` and its two assertions]

⭐ Copy that shape: run the keepalive tick concurrently with a simulated job holding the lease; assert no keepalive touch falls inside the job's `[enter, exit]` window; then neuter the lease and assert it **does** — the test fails if the tick can steal the terminal, which is criterion 4's literal requirement. ⚠️ **Patch `services.mt5_concurrency._mt5_terminal_lock_for`, not the re-export on `job_worker`** — that indirection is a documented silent no-op since the lease refactor.

### 3.5 The lease roster will red — re-cut it to SEVEN

`_PRODUCTION_LEASE_SITES` is a hand-typed `frozenset` asserted with `==` and keyed on `(file, enclosing function)`; it currently holds six entries (`allocator_positions._fetch_mt5_account_rows`, `ingestion/mt5.validate`, `job_worker._fetch_mt5_account_balance`, `job_worker.run_derive_broker_dailies_job`, `routers/exchange._validate_mt5_key_probe`, `mt5_relogin.heal_mt5_terminal_session`). A sibling assertion requires all enclosing functions be **distinct** (at most one lease per function ⇒ no function can carry a client from one acquisition into the next). The walk now includes `main.py` and `main_worker.py`, so a lease taken there is visible too.
[VERIFIED: analytics-service/tests/test_mt5_concurrency.py, `_PRODUCTION_LEASE_SITES`, `test_no_production_function_holds_two_terminal_leases`, `test_the_lease_walk_can_SEE_the_top_level_entrypoints`]

⛔ Before re-cutting, answer the question the roster exists for, in the plan: *does the new site touch an `Mt5Client` that was ALREADY touched under a different lease?* If the tick delegates to `heal_mt5_terminal_session` (which builds and closes its own client inside its own single lease), the answer is **no** and no new site appears at all — §6's recommended shape adds **zero** lease sites and leaves this roster untouched. ⭐ That is a real argument for the delegating design.

## 4. Durable episode recording (D-3)

### 4.1 What must be recorded, and why in-process state is not enough

Per D-3 and `<specifics>`: each `authorized → dark` episode needs `authorized_at`, `went_dark_at`, and **how it resolved**.

⛔ **The open episode must survive an analytics redeploy.** Railway deploys the analytics service on every green main CI, so a process-memory `authorized_since` is reset several times a day and every recorded lifetime would be biased short — which would corrupt the *exact* number this phase exists to let a successor choose. **The sink must therefore also be the state**: on boot, read the open episode back and continue it. ⚠️ This is a requirement the CONTEXT does not state and the planner must not miss.

## 5. Criterion 5 — the `_raise_last` by-value redaction (D-4)

### 5.1 The defect, precisely

`_raise_last` builds its detail from the **terminal's own `last_error()` text** and raises `Mt5ClientError(code, text)`. `Mt5ClientError.__init__` applies `scrub_freeform_string` — which is **shape**-based (`password=<value>` key/value shapes) and is a **measured NO-OP on the `mt5linux` kwargs-repr shape**, because its `SENSITIVE_KEY_VALUE` pattern needs `key` immediately followed by `[:=]` and the repr puts a closing quote between them. A broker that echoes the submitted account or server back into `last_error()` therefore discloses it. `mt5linux` 0.1.9 f-string-interpolates arguments into remotely-eval'd source (T-134-01), so this reaches a PUBLIC log.
[VERIFIED: analytics-service/services/mt5_client.py — `_raise_last`, `Mt5ClientError.__init__`, `_redact_credential_values` docstring]

### 5.2 `_raise_last` has EIGHT call sites, not two — and that reshapes D-4

⚠️ **CONTEXT D-4 says `_raise_last` is reached by `login()` and `initialize_with_credentials()`. Measured this session, it is reached by both of those plus six more:** `assert_session_authorized`, `account_info`, `terminal_info`, `history_deals_get`, `order_check`, and `login`'s two arms. [VERIFIED: `grep -n "_raise_last" analytics-service/services/mt5_client.py` — call sites in `login` (×2), `assert_session_authorized`, `initialize_with_credentials`, `account_info`, `terminal_info`, `history_deals_get`, `order_check`]

⛔ **Consequence: "so every caller benefits" cannot be literally true**, and the plan should say so rather than inherit an overpromise. Five of the eight callers have **no credential in scope**; there is no value for them to redact by. This is not a weakening — it is the identical argument `_describe_exception_for_log`'s own docstring already makes for its `None` arm: *"a placeholder login of `0` would replace every `0` in the message with the marker, mangling the very text an operator needs."* The honest statement is **every credential-carrying caller benefits, at one site, by construction**.

### 5.3 The shape of the fix, and the gate it must not dodge by accident

The by-value redactor is already correct and already escape-aware: `_credential_renderings(literal)` returns the raw literal plus the escaped bodies of `repr()`, `ascii()` and `json.dumps()`, ordered **longest-first**; `_redact_credential_values(text, login, password, server)` shape-scrubs and then runs **ONE GLOBAL longest-first pass across all three literals** (a per-literal loop strands a password that contains the login). [VERIFIED: analytics-service/services/mt5_client.py, `_credential_renderings` / `_redact_credential_values`]

⛔ **The parameter NAME you give `_raise_last` decides which gates fire.** `_credentialed_client_methods` classifies every `Mt5Client` method from source:
- positional params **exactly** `(login, password, server)` with no kw-only ⇒ **DRIVABLE** (the redaction driver calls it positionally and makes its credential-carrying transport call raise);
- otherwise, if `password` appears in positional-or-kw-only ⇒ **RESIDUAL**, and `test_CREDENTIAL_REDACTION_no_password_carrying_method_escapes_the_driver` asserts RESIDUAL is **empty**, with the message *"⛔ EXTEND THE DRIVER to cover the new signature shape. Weakening the derivation so it no longer sees them is the WRONG fix."*
[VERIFIED: analytics-service/tests/test_mt5_client_contract.py, `_credentialed_client_methods`]

⭐ Measured this session by importing the test module and printing the derivations:

```
DRIVABLE ['initialize_with_credentials', 'login'] floor 2
ESCAPE_AWARE ['initialize_with_credentials', 'login'] floor 2
RESIDUAL {}
```

So: a signature of `_raise_last(self, login, password, server)` makes it DRIVABLE and the driver will try to make its *credential-carrying transport call* raise — it has none, so the driver breaks. A signature naming `password` any other way makes it RESIDUAL and reds the empty-residual gate. **A `credentials: tuple[int, str, str] | None = None` parameter is neither** — and that is not a dodge, because the gate's class is *"methods that hand a credential to a transport call"* and `_raise_last` hands credentials to **nothing**; it only formats. ⛔ Write that argument at the site; do not let it be discovered as an accident.

## 6. Recommended shape (prescriptive)

⭐ **The tick delegates; the recorder lives beside the verdict; the loop only schedules.**

```
services/mt5_keepalive.py   (NEW)
    mt5_session_keepalive_loop()      # P-outer guard, P-inner guard, SHUTDOWN-aware sleep
        └── awaits services.mt5_relogin.heal_mt5_terminal_session()   # unchanged in behaviour

services/mt5_relogin.py     (EXTENDED, inside its existing single top-level guard)
    heal_mt5_terminal_session()  ->  None      # ⛔ return type UNCHANGED (see below)
        └── records the episode transition beside the verdict it already computes

main.py  lifespan
    tasks = [... , create_task(mt5_session_keepalive_loop(), name="mt5_session_keepalive")]
```

**Why delegate rather than re-implement the tick:**
- `heal_mt5_terminal_session` already does, in order: kill switch → credentials → gateway endpoint → **bounded** lease by key → `to_thread` under a budget → credential-free probe → branch on code → heal only `-6` → **re-probe** → classified verdict. Re-implementing any of that creates a second detector and a second lease site.
- It adds **zero** entries to `_PRODUCTION_LEASE_SITES` (§3.5) and zero new `Mt5Client` lifetimes to reason about.
- Its verdict tokens are already the episode vocabulary.

**Why the episode write goes in `mt5_relogin`, not in the loop:**
- `heal_mt5_terminal_session` returns `None` on every path and two behavioural tests assert exactly that (`assert await mt5_relogin.heal_mt5_terminal_session() is None`). Changing the return type to hand the verdict to the loop **reds those** and weakens a stated contract (*"the return value is NOT an oracle for success"*). ⛔ Don't. The module that **knows** the verdict is the module that should **record** it.
- The write sits inside the existing top-level guard, so it inherits never-raising for free and the AST predicate (which counts *statements in the body of the `try`*, not their number) stays satisfied. ⚠️ Re-run `test_the_heal_body_sits_entirely_inside_one_top_level_except_exception` after the edit regardless — it is cheap and it is the gate.

⛔ **D-08's docstring must be AMENDED, deliberately and in this repo's voice.** It currently says *"STARTUP ONLY. The heal is called from `main.lifespan` and NOWHERE ELSE."* This phase is chartered to change that. The amendment must record **why the original hazard does not transfer** (§3.2: lazy epoch bind + ContextVar occupancy, both verified) — exactly as D-07 was amended rather than quietly contradicted. A reader who finds the sentence false and the reason unwritten has found drift.

⚠️ **One refinement D-1 implies and the boot heal does not do:** the heal returns early when the credential triple is absent, *before* it probes. A **detector** needs no credentials. If the planner wants the episode record to keep accruing on a deployment with `MT5_LOGIN` unset, the detect step must run first and the credential read must gate only the heal. That is a genuine design choice, it is small, and it should be made on purpose rather than inherited.

## Common Pitfalls

### Pitfall 1 — The never-raises gate, copied verbatim, produces a loop that dies on tick 3
**What goes wrong:** body-is-exactly-one-`Try` puts the `while` inside the guard; the first tick exception exits the loop permanently. **Warning signs:** one WARNING at startup-plus-N, then silence forever, worker green. **Avoid:** two guards, two predicate properties (§1.3).

### Pitfall 2 — `except BaseException` around an `await` swallows shutdown
**Root cause:** `CancelledError` is a `BaseException`, not an `Exception` (measured, 3.12.13). **Avoid:** confine `BaseException` to argument-free logging, exactly as IN-06 does.

### Pitfall 3 — `except OSError` eats the budget timeout
`asyncio.TimeoutError is TimeoutError` and builtin `TimeoutError` subclasses `OSError` (measured). A socket-error handler silently absorbs the most important outcome the heal emits.

### Pitfall 4 — Recording a busy skip as "authorized"
A busy terminal is not evidence of a healthy session. Record `not_measured`; never close an episode on it (§3.3).

### Pitfall 5 — ⛔ "Authorized" does not mean the HOUSE session
`_fetch_mt5_account_rows` runs `session.client.login(session.login, session.investor_password, session.server)` per customer on the same shared terminal, and `close()` never calls `shutdown()`, so the terminal stays authorized **as that customer** afterwards. `assert_session_authorized()` cannot tell the two apart. The *trigger* stays correct (`-6` = nobody authorized), but an episode's `authorized_at` may be a customer login. [VERIFIED: analytics-service/services/allocator_positions.py, `_mt5_read` inside the `mt5_terminal_lease` block; analytics-service/services/mt5_client.py, `Mt5Client.close`] ⚠️ The founder's own wave-5 record already half-notices this: *"If the terminal authorizes but per-account work then refuses, an account mismatch between the env credential and the stored key is the first thing to check — and it is a founder-side check."* ⛔ Do **not** "fix" it by reading `account_info()` — that is an extra read (P-4) and it would put the account number into a log on a PUBLIC repo. **Record the limit in the episode row** (`reading_attributes_account: false`) so the successor computing lifetimes knows what it has, and note the contamination rate is bounded by the per-account job cadence (`daily_enqueue_loop(interval=86400.0)`).

### Pitfall 6 — In-process episode state, reset by every deploy
Railway deploys analytics on every green main CI. Read the open episode back at boot (§4.1).

### Pitfall 7 — Per-tick DB writes into a shared, gated table
Write transitions only (§4.4).

### Pitfall 8 — Silent hand-edit of the two hand-typed counts
`_LIFESPAN_CREATE_TASK_COUNT_AT_164_6_2` (5 → 6) and, only if a second lease site is introduced, `_PRODUCTION_LEASE_SITES` (6 → 7). Both are `==` anti-vacuity legs; re-cut with the reasoning recorded, never weaken to `>=`.

### Pitfall 9 — `[164.6.2-KILLSWITCH-COMMENT-DRIFT]` is NOT this phase's to fix
Three comment blocks claim `"TRUE "` reads the switch OFF while `mt5_enabled_server()` is `(os.getenv("MT5_ENABLED") or "").strip().lower() == "true"` — so `"TRUE "` reads **ON**. [VERIFIED: analytics-service/services/closed_sets.py, `mt5_enabled_server`] Routed to Phase 164.6. ⛔ Correct the COMMENTS there, never the code, and not here.

### The loop's two guards (P-outer + P-inner)

```python
async def mt5_session_keepalive_loop() -> None:
    # P-outer: the whole body inside ONE try/except Exception, handler body itself
    # guarded (IN-06), no finally:/else:. ⛔ This loop is STRICTER than dispatch_loop
    # on purpose: a best-effort MT5 instrument must never reach _crash_handler.
    try:
        while not SHUTDOWN.is_set():
            # P-inner: one bad tick must never end the loop.
            try:
                await heal_mt5_terminal_session()   # returns None on every path
            except Exception as exc:                # noqa: BLE001 — the per-tick control
                logger.error("mt5 keepalive tick failed: %s", exc, exc_info=True)

            # The house sleep idiom (main_worker.dispatch_loop / main._bridge_healthz).
            try:
                await asyncio.wait_for(SHUTDOWN.wait(), timeout=_poll_interval_s())
                break
            except asyncio.TimeoutError:
                pass
    except Exception as exc:  # noqa: BLE001 — see the docstring; this is the control
        try:
            logger.warning(
                "mt5 keepalive loop exited — continuing without it (exc_class=%s)",
                type(exc).__name__,
            )
        except BaseException:  # noqa: BLE001 — argument-free fallback, NEVER around an await
            logger.warning("mt5 keepalive loop exited and could not be described")
```

⚠️ Note `heal_mt5_terminal_session()` cannot raise, so the P-inner handler is defence in depth — which is the point: the property must be **structural**, not inherited from a callee's discipline. That is the same argument `_describe_exception_for_log`'s docstring makes about `scrub_freeform_string`.
