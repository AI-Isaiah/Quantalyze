<domain>
## Phase Boundary

Nothing TRIGGERS a recovery of the MT5 terminal's broker session, so the terminal sits
dark for hours while recovery itself takes minutes.

⭐ **The sizing input is the DARK WINDOW, not the recovery.** MEASURED in Phase 164.6.2
wave 5 (`164.6.2-MEASUREMENT-WAVE5.md`, and sharpened by that phase's re-verification):
the terminal read `-6` at `2026-09-15T08:12:37Z` and was still dark at the `10:46:35Z`
gateway restart — **≥2h34m confirmed dark with nothing in the system able to act**,
inside a looser ≈8h05m bracket. Recovery after the restart took `00:03:43` (itself an
UPPER BOUND; the true value may be ≈23 s). ⛔ Do not size against the recovery number.

⚠️ **The 164.6.2 boot heal is NOT this mechanism and does not cover this case.** It was
deployed, armed and idle through the entire dark window: it fires once, at analytics
startup, which has no correlation with the terminal losing its session. RESEARCH
assumption A3 (a broker-side block) remains untested — the heal has never been exercised
against a real `-6`, and its only production verdict is an `already_authorized` no-op.

⛔ NOT in scope: re-litigating 164.6.2 criterion 1's worker-side shape (a founder decision
taken on a measurement), and changing what the gateway READS.
</domain>

<decisions>
## Implementation Decisions

### D-1 — Detection is a PERIODIC CREDENTIAL-LESS PROBE
A loop performs the cheap read-only authorization check; an unauthorized reading (`-6`,
or a `terminal_info()` that cannot be read) is what triggers a heal. ⛔ **The mechanism
never logs in merely to look.**
**Why:** it reuses the credential-free detector 164.6.2 already built and proved, and it
cannot re-clear the Expert-Advisors options — which matters because question THREE (D-09)
is **UNSETTLED** with `R1: true` and `r2 pending`, so the account-change hazard is neither
confirmed nor refuted and must be treated as LIVE.
**Rejected:** healing unconditionally on a cadence — it calls the CREDENTIALED verb on a
schedule even when nothing is wrong, multiplying both the D-09 hazard and the `_raise_last`
exposure. **Rejected:** reacting only to the job path's own `-6` — nothing notices while the
system is IDLE, which is exactly the measured dark window, so it fails criterion 2.

### D-2 — The touch runs as a FIFTH `main.lifespan` TASK, STRUCTURALLY INCAPABLE OF RAISING
A new named task beside `dispatch_loop`, `watchdog_loop`, `daily_enqueue_loop`,
`_bridge_healthz` and `mt5_boot_heal`.
⛔ **`_crash_handler` calls `SHUTDOWN.set()` on ANY background-task exception** — a loop that
raises stops dispatch, watchdog and enqueue **behind a green `/health`**. `heal_mt5_terminal_session`
was built never to raise for exactly this reason and is AST-asserted so; this loop must
carry the same property, and a keepalive is a LOOP, so the hazard is permanent rather than
one-shot.
**Rejected:** folding into `watchdog_loop` — couples MT5 session health to the job watchdog's
cadence and failure modes, and makes it hard to kill-switch independently.
**Rejected:** a Railway cron / scheduled job — a new deploy surface on a phase forbidden to
change what the gateway reads, and pg_net/cron is ASYNC so a green cron run is not a 200
(this repo hid 7 days of 401s behind one).

### D-3 — SHIP DETECTION FIRST, HARVEST LIFETIMES; the interval is a LATER decision
⛔ **This phase does NOT choose the keepalive interval** (criterion 1, and D-06 in 164.6.2).
Wave 5 produced exactly ONE observation of each quantity; an interval set from n=1 is the
guess D-06 exists to prevent.
The mechanism that DETECTS is also the mechanism that MEASURES: each
`authorized → dark` episode is recorded with its stamps, so **n grows on its own, in
production**. What ships now is a DETECTION cadence (cheap, read-only). The KEEPALIVE
interval is chosen in a follow-up against n>1.
**Rejected:** mining history first — MEASURED this session, scheduled prober archives are
polluted by self-test fixtures and read authorized-looking in BOTH directions (the `08:12Z`
run needed a special execution anchor to read at all), and the dark window stays open
meanwhile. **Rejected:** picking a conservative interval now — that is precisely what
criterion 1 forbids; it was offered explicitly so its refusal is recorded rather than silent.

### D-4 — Fix `_raise_last` ITSELF, BY VALUE (criterion 5)
`_raise_last` is SHARED: `Mt5Client.login()` reaches it and so does
`initialize_with_credentials()`, the verb this phase drives. Redact the credential values at
the shared site using the by-value redactor 164.6.2 already built
(`_redact_credential_values` / `_credential_renderings`), so every caller benefits.
**Why:** fixing only `login()`'s falsy arm leaves the shared function unscrubbed for
`initialize_with_credentials`, which is the verb the new loop calls — so it would not close
the exposure this criterion exists for.
⚠️ `test_CREDENTIAL_REDACTION_the_falsy_arm_asymmetry_is_measured_not_assumed` pins the
current asymmetry in BOTH directions and **will red when this closes** — that is expected,
and updating it is part of the work, not a surprise.
</decisions>

<specifics>
## Specific Ideas

- The detection cadence and the keepalive interval are **two different numbers**. Only the
  first is chosen here, and it is a cheap read-only poll rather than a session-preserving
  touch. Name them distinctly in the plan so a later reader cannot conflate them.
- Every episode record needs `authorized_at`, `went_dark_at` and how it was resolved, so the
  follow-up can compute lifetimes without re-deriving them from logs.
- ⚠️ A verdict that can only be seen while it scrolls past is this repo's known failure shape
  (`[MT5-VERDICT-SINK-01]`, Phase 164.9 criterion 12). Whatever this phase records must land
  somewhere readable AFTER the fact.
</specifics>
