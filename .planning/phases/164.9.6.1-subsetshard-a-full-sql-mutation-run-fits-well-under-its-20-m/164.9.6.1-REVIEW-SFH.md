# 164.9.6.1 silent-failure review

One HIGH and two MEDIUM findings. Nothing in the diff lets a lane failure, a skipped file or an
unreadable log turn into a passing run or a narrowed scope.

- SFH-03 (HIGH): a lane that overflows its output buffer can hang the whole pool until the job's
  20-minute cancel, with nothing named.
- SFH-01 and SFH-02 (MEDIUM): failures that are reported, but under the wrong name, so a reader is
  pointed at the wrong cause.

## SFH-03: HIGH. An output overflow in one lane can hang the pool until the 20-minute cancel, with no lane named

**Where:** `scripts/mutation-runner/run.mjs`: `spawnAsync`. The overflow branch calls
`child.kill("SIGKILL")`, but the promise settles only on `close`.

**Mechanism, measured 2026-10-03 (scratchpad, macOS, node).** I ran `bash -c 'yes; :'` with
maxBuffer set to 1 MiB, once through each spawn path:

- `spawnSync`: returned in **10 ms** with `error ENOBUFS`, `signal SIGTERM`.
- The same collect/overflow/SIGKILL/settle-on-`close` logic as `spawnAsync`: **still unsettled when
  the 10 s watchdog fired**.

`close` waits until every holder of the child's stdout and stderr pipes has exited. SIGKILL reaches
only `bash`. The foreground `psql` inherited the pipes, and the `data` handler keeps draining them
after it stops collecting, so `psql` never blocks and never gets SIGPIPE. `spawnSync` closes its own
pipe ends on overflow, so its grandchild dies of SIGPIPE, and SIGTERM also lets `run.sh`'s trap run.
On this point the change is a regression, not a hang that already existed.

**Failure scenario.** A mutation turns a gate loop into a RAISE NOTICE storm that does not end, the
realistic way to pass 128 MiB. That lane's promise never settles. The worker never claims another
file, and `Promise.allSettled` waits forever. The job is cancelled at `timeout-minutes: 20`:

- no `lane-unrunnable` row and no `arms:` / `lane-invocations:` summary are printed;
- the stuck file's sink and every later file's sink are never flushed.

A cancelled `sql-mutation` is exactly what forces FULL on the next push (D-02 refuses it), which is
the cascade this phase exists to break. If the storm does end, the lane settles, but with
the orphan described in SFH-01.

**Hidden errors:** any overflowing lane whose `psql` keeps writing. The instrument fault turns into
an unnamed wall-time cancel.

**Recommendation.**
- Best: spawn with `detached: true` and, on overflow, send SIGTERM to the process group
  (`process.kill(-child.pid, "SIGTERM")`). That kills `psql`, so bash's deferred TERM trap fires
  and tears the cluster down. Follow it with a SIGKILL to the group after a grace period. The
  `pg_ctl` postmaster has its own session and is not reached by the group signal, so SFH-01's
  exit-2 classification is still needed.
- Minimum: on overflow, `child.stdout.destroy(); child.stderr.destroy();` so the grandchild gets
  SIGPIPE, and settle on `exit` rather than `close` once overflow is set.
- Either way, add a self-test row: a stub lane command that floods without end must settle as
  `lane-unrunnable` ENOBUFS within a bound.

**Confidence: 8/10.** Measured against the same logic. The trigger, more than 128 MiB from one
lane, is rare.

## SFH-01: MEDIUM. An orphaned lane cluster now blocks its worker's fixed port, and every later lane on that worker is reported as a corpus defect

**Where:** `scripts/mutation-runner/run.mjs`: `spawnAsync` (the `ENOBUFS` branch),
`allocateLanePorts`, the `worker`/`runFile` pool in `runCorpus`. Also the baseline, arm and restore
verdicts, which read a non-zero `status` with no `measureFail` as a gate result.

**What changed.** Before this phase, each lane got a fresh port from `run.sh`'s `alloc_port` just
before it bound. `spawnSync`'s `maxBuffer` overflow killed the child with the default
`killSignal`, SIGTERM. `run.sh` turns SIGTERM into `exit 143`, and its EXIT trap stops the cluster.
Now two things are different:

1. `spawnAsync` uses `child.kill("SIGKILL")` when output goes past 128 MiB. Bash cannot trap
   SIGKILL, so `cleanup()` never runs. The postmaster started by `pg_ctl` runs in its own session
   and keeps running, still bound to the lane's port.
2. Each worker keeps one port, `ports[k]`, for the whole run and reuses it for every lane it runs.

**Failure scenario.** One arm lane on worker k produces too much output. For example, a mutation
turns a gate loop into a RAISE NOTICE storm. That arm is correctly reported as `lane-unrunnable`
MEASURE_FAIL. But its postmaster is left running on `ports[k]`. Every later lane worker k runs then
fails `run.sh`'s bind-test collision guard and exits 2 ("something is already listening on
127.0.0.1:P"). `laneSpawnFailure` only classifies errors, signals and a missing status, so exit 2
counts as a normal gate exit:

- a baseline lane becomes a `baseline` defect: "pristine corpus did not go GREEN (exit 2); first
  failure: none";
- an arm lane is counted in `armsExecuted`, has no attributable raise, and is reported as a corpus
  defect for that arm, not as `lane-unrunnable`;
- a restore lane becomes a `restore` defect.

So one instrument fault shows up as a run of corpus defects across about a quarter of the remaining
files. `bitingArms` drops, so a FULL run can also fail its floor. The run still exits 1, so nothing
is silently passed. But the defect table names the gate files, not the lane, which is the
corpus-defect-named-for-an-instrument-failure shape that `laneSpawnFailure`'s own header says was
fixed on 2026-09-02. `run.sh`'s own cleanup also has paths that leave a postmaster running ("no
postmaster.pid ... it is ORPHANED"). Before this phase those were harmless, because the next lane
got a new port. Now the same port is reused, so they cascade too.

**Hidden errors:** ENOBUFS overrun; an orphaned postmaster from `pg_ctl stop` failing; any
non-lane process that takes `ports[k]` between two lanes. All three surface as corpus defects.

**Recommendation (either part is enough; both is best):**
- Kill with SIGTERM, as `spawnSync` did, so `run.sh`'s trap still tears the cluster down. If you
  need a hard stop, add a SIGKILL after a grace timeout.
- Treat `run.sh`'s documented exit 2 (port collision, refused) as an instrument failure, never a
  gate verdict. Something like:

```js
// in runLane, after laneSpawnFailure(proc):
const collided = proc.status === 2 && /^ERROR: (something is already listening|a PostgreSQL server) on 127\.0\.0\.1:/m.test(proc.stderr);
const measureFail = laneSpawnFailure(proc) ?? (collided ? `lane could not run: port ${port} collision (run.sh exit 2)` : null);
```

  Optionally, have a worker take a fresh port after any lane that ended in MEASURE_FAIL.

**Confidence: 7/10** for the mechanism (SIGKILL skips the trap, the port is fixed per worker, and
exit 2 is unclassified). The trigger itself is rare.

## SFH-02: MEDIUM. The tolerant proof assumes the `frontend` aggregator is red because of the drift, but the aggregator's skip-based failures are invisible to it

**Where:** `scripts/classify-changed-paths.mjs`: `toleratedDriftVerdict`. Also its use of
`PREDECESSOR_OK_CONCLUSIONS = {success, skipped, neutral}` and the reason
"`frontend` aggregator red with it".

**What changed.** The strict proof required `frontend` to conclude `success`. That carried the
aggregator's whole skip policy: on a trusted event, a `skipped` `e2e-seeded`, `test-db-drift` or
default-arm row fails the aggregator. The tolerant proof only requires `frontend` to be `failure`
in `sql-gate-lint`'s suite, and every other run to be in `PREDECESSOR_OK_CONCLUSIONS`. `skipped` is
in that set. A job the aggregator itself treats as a failure (the "#1 silent-green" `e2e-seeded`
skip on a push) therefore passes the run-level checks. The proof then puts the aggregator's red down
to the drift without reading the aggregator's log.

**Failure scenario.** A migration merge leaves P red with tolerated `content-drift — DRIFT` rows.
On the same push, `E2E_TEST_DB_CONFIGURED` is lost, so `e2e-seeded` and `test-db-drift` both
conclude `skipped`, and `frontend` prints `::error::e2e-seeded result=skipped on a TRUSTED event`.
On the next push, `predecessorVerdict(..., { tolerateBaselineDrift: true })` returns `ok: true,
tolerated: true`, and `scope-reason:` reads "predecessor ... red only with tolerated baseline drift:
f/1 (... frontend aggregator red with it)". The second cause of P's red, a lost go-live badge gate,
is not mentioned in the line that says why the run narrowed.

**Scope of harm, stated precisely.** The narrowing decision itself stays safe:

- `sql-mutation` and `sql-gate-lint` share the same `needs: [changed-paths]` and the same
  `docs_only != 'true'` condition, so `sql-mutation` cannot be `skipped` while `sql-gate-lint` ran
  and failed;
- `sql-mutation`'s own non-OK conclusion is still refused by name.

The defect is the accuracy of the reason, and D-05's premise that tolerance rests on positive
evidence. The evidence that `frontend` is red only because of the drift is assumed, not read.

**Hidden errors:** any aggregator failure caused by a `skipped` row: `e2e-seeded` or
`test-db-drift` skipped on a trusted event, or a future default-arm job that gains an `if:`.

**Recommendation.** Make "red with it" positive evidence. Either:

- also read the `frontend` job log (same `fetchJobLog` seam, so no new permission is needed) and
  require its `name: result` echo rows to be `success` everywhere except `sql-gate-lint: failure`
  and the event's documented skip-by-design rows (`plan-anchor-verify` on a push), with exactly one
  `::error::One or more frontend-* jobs did not succeed.` line; or
- require every run in `sql-gate-lint`'s suite, other than `sql-gate-lint` and `frontend`, to be
  `success` exactly, with a named allowlist for skip-by-design rows. Treat any other `skipped` as
  untolerated: "check 'e2e-seeded' concluded skipped, which the aggregator fails on a push".

**Confidence: 5/10.** The mechanism is certain. Impact is limited to a misleading reason, not a
wrong narrowing.

## Checked and found clean (no finding)

- **Pool error handling (`worker`, `Promise.allSettled`, `firstError`).** A file that throws sets
  `stop`, the other workers finish their current file, cleanup runs only after all workers have
  settled, and the first error is rethrown. `process.exit(await main())` turns the rejection into a
  non-zero exit with a stack trace. Nothing is swallowed. Output from finished files after the
  failed index is not printed, but the run fails anyway.
- **Lost files and tally agreement.** The claim `next++` is synchronous. Every early `continue` in
  the old loop became a `return` from `runFile`, whose sink is still stored and flushed, so its
  `parse`/`baseline` defects are kept. `laneTally` and `laneArmGateTally` are still incremented only
  inside `runLane`, and the `armsExecuted` updates are commutative. Defects and per-file tallies are
  written by index and flushed in corpus order. I found no shared-state read inside `runFile`, such
  as the outer `defects` or a direct `console.*` call, that would bypass the sink.
- **`spawnAsync` itself.** It settles once. ENOENT settles on `error` because no pid was assigned.
  A post-spawn `error` still waits for `close`, so it does not settle twice or leave the promise
  pending. ENOBUFS keeps its error code and reaches `laneSpawnFailure` (the SIGKILL concern is
  SFH-01).
- **`parseBaselineDriftLog` and `toleratedDriftVerdict`.** Every refusal reads as FULL with a
  reason. Tolerance requires exactly one exit line, under the drift step's exact header; every
  `##[error]` line must be a tolerated row inside that step, or the single FAILED line; there must
  be at least one row, a well-formed `name/nargs` token, and exactly one `findings N` line inside
  the step with N equal to the row count. That catches truncation, unknown findings, `allowlist-*`,
  `SNAPSHOT_ONLY`, `UNCOMPARABLE`, `MEASURE_FAIL`, a `--self-test` exit and a second exiting step.
  A throwing, timed-out or over-`maxBuffer` `gh api` call reads as FULL. Run-level refusals,
  including a cancelled `sql-mutation`, return before the log is read. `classifyPushRange` stays
  strict, and the contract test pins that.
- **The ci.yml and nightly `lane-concurrency:` assert step.** The grep exit status is checked
  (`rc <= 1`). A missing line, more than one line, a non-numeric value and N < 1 each
  MEASURE_FAIL with a named message. The two copies are byte-equal, as the parity test requires.
- **Below the reporting bar, noted only:** the drift step is not the last step of `sql-gate-lint`.
  Later steps, such as the data-dependence gate and the reference-data allowlist audit, do not run
  on a drift-red P, so "red only with tolerated drift" cannot speak for them. They run again in full
  on the next push and play no part in the `sql-mutation` subset decision, so this does not reach
  MEDIUM.
