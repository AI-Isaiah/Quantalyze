## Warnings

### WR-R2-01 (MEDIUM, confidence 8): `killLaneGroup` throws an uncaught `EPERM` on macOS when the lane's group holds only a zombie, and the runner crashes

**File:** `scripts/mutation-runner/run.mjs`. The function is `killLaneGroup` (`:1716`), and it has three callers:
- the overflow branch in `spawnAsync`'s `collect` (`:1689`);
- the escalation timer (`:1690`);
- the forwarding loop in `forwardSignalsToLaneGroups` (`:1739`).

**Issue:** `killLaneGroup` catches `process.kill(-pid, sig)` failures and rethrows anything that is not `ESRCH`. Darwin returns `EPERM`, not `ESRCH`, for `kill(-pgid)` when the group's only member is a zombie. That is a lane whose leader has exited but that libuv has not yet reaped.

Measured on this macOS box:
- with a plain fork, `setsid` and `_exit`, and no reap, `kill(-pgid)` gave `EPERM` and `kill(pid)` gave ok;
- after the reap, `kill(-pgid)` gave `ESRCH`.

The same probe in a Linux container (`node:22-slim`) returned ok before the reap and `ESRCH` after it, so ubuntu CI does not hit this.

**Reproduced through the shipped `spawnAsync`, first iteration:**

```js
spawnAsync("head", ["-c", "3000000", "/dev/zero"], { env: process.env, maxBuffer: 3000000 - 10, graceMs: 50 })
// -> uncaughtException: EPERM kill EPERM
```

The lane writes its last bytes and exits. Node reads the final chunk, the chunk crosses `maxBuffer`, and the overflow branch signals a group whose leader is already a zombie. The throw comes out of a stream `data` handler, so nothing in `runCorpus` can catch it.

**Failure scenario:** a developer runs `node scripts/mutation-runner/run.mjs` on macOS. Either a lane's output crosses `maxBuffer` in the bytes read after its `bash` exited, or the developer presses Ctrl-C while one lane is between exit and reap. What happens next:
- The runner dies with a stack trace and exit 1, before the summary block. No `arms:` or `lane-invocations:` line is printed, and no lane is named.
- In the forwarding loop, the throw on one group aborts the `for` loop. Groups after it in `liveLaneGroups` never receive the signal, and the re-raise `process.kill(process.pid, sig)` is never reached. Ctrl-C then exits 1 instead of 130.
- The lanes that were skipped are detached, so the terminal's SIGINT never reached them either. Each one finishes or dies of SIGPIPE on its next write before `run.sh`'s trap stops its cluster. Nothing leaks permanently, but the runner no longer controls the teardown.
- The escalation timer has the same exposure. It fires if a TERM-trapped teardown ends in the moment just before the timer, and the result is an uncaught exception from a timer callback.

**Likelihood is low and limited to macOS.** With real `run.sh` lanes, the last gate output is printed about 100 ms or more before `bash` exits, because `pg_ctl stop` and `rm -rf` run in between. The overflow window therefore needs the event loop to stall. The Ctrl-C window lasts as long as one lane's exit-to-reap gap. It stays MEDIUM rather than LOW for four reasons:
- the defect is in code this round added;
- it is deterministic in the stub shape;
- it turns a named MEASURE_FAIL into an unnamed crash;
- macOS is where the runner is run by hand.

**Fix:** treat `EPERM` from a group kill as "the group is gone or unsignallable", and isolate each pid in the forwarding loop so one failure cannot skip the rest or the re-raise:

```js
function killLaneGroup(pid, signal) {
  if (pid === undefined) return;
  try {
    process.kill(-pid, signal);
  } catch (e) {
    // ESRCH: group gone. EPERM: Darwin's answer for a group whose only member
    // is an unreaped zombie (measured 2026-10-03; Linux returns success).
    if (e.code !== "ESRCH" && e.code !== "EPERM") throw e;
  }
}
// forwardSignalsToLaneGroups:
for (const pid of liveLaneGroups) {
  try { killLaneGroup(pid, sig); } catch { /* keep forwarding; the re-raise must run */ }
}
process.kill(process.pid, sig);
```

A deterministic regression row on macOS is the `head -c N /dev/zero` call above with `maxBuffer = N - 10`. It must settle as `lane could not run: ENOBUFS`, with no uncaught exception. On Linux the row passes before and after the fix, which is expected because the defect is Darwin-only.
