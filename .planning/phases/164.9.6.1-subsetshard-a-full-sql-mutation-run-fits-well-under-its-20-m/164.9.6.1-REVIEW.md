I found no CRITICAL or HIGH issues. There are two MEDIUM findings: one latent gap in the tolerant predecessor proof, and one isolation regression in the lane pool.

**What I traced and found sound** (these are not findings):
- **`runCorpus` drain.** The file pool runs `Promise.allSettled` over every worker before the `finally` calls `rmSync(scratchRoot)`. The first error is rethrown after that, so a rejection cannot delete a sibling's workdir. vitest Test E covers this.
- **Output and defect order.** Each file writes to its own sink. `flush` advances only over a contiguous completed prefix, so log lines and defects come out in corpus order. `perFileTallies[index]` and `waivers` are written before the file's first `await`.
- **Tally independence.** `laneTally` and `laneArmGateTally` are still incremented only in `runLane`, and `armsExecuted` only in the verdict loop. All accumulators are commutative sums on one thread.
- **`spawnAsync`.** It settles exactly once. ENOENT (no pid) resolves on `error`, and every other outcome resolves on `close`. ENOBUFS and ENOENT keep the `laneSpawnFailure` / `invoked` parity with `spawnSync`.
- **Ports.** `allocateLanePorts` holds all listeners at once, so it always returns distinct ports. The probe borrows `ports[0]` and is awaited before the pool starts.
- **Exit codes.** A runner throw becomes a top-level rejection, which exits 1, as before.
- **`parseBaselineDriftLog` fails closed.** It requires positive evidence on every axis:
  - exactly one exit line;
  - the last step header equals the drift step's;
  - every `##[error]` line in the whole log is a tolerated row, the FAILED line or the exit line;
  - the rows sit inside the drift step and carry an `FN_TOKEN_RE` token;
  - exactly one in-step `findings N`, with N equal to the row count.

  I found no log shape that reads as tolerated other than a real drift-only one. `printable` and `oneLineReason` keep refusal text single-line ASCII, and `sql_gate_reason` reaches shell only through `env:`, so there is no script injection.
- **D-04.** `classifyPushRange` calls `predecessorVerdict` with two arguments, and the contract test pins that. `derivePush` is the only opt-in caller.
- **Workflow parity.** The `lane-concurrency:` assert block in `sql-mutation-nightly.yml` is byte-identical to the one in `ci.yml`.
- **Every new gate can fail.** vitest drives the assert block RED for an absent line, a doubled line and N = 0. The concurrency self-test's in-flight row fails on a serial pool.

## Warnings

### WR-01: The tolerant predecessor proof never requires positive evidence that `sql-mutation` ran and succeeded

**File:** `scripts/classify-changed-paths.mjs:toleratedDriftVerdict` (reached from `predecessorVerdict` with `tolerateBaselineDrift: true`, called by `scripts/sql-gate-subset.mjs:derivePush`)

**Confidence:** 5/10. The gap is demonstrated in-process. It is latent against today's `ci.yml`.

**Issue:** In the strict path, `frontend` concluding `success` is what proves each `skipped` row was legitimate: the aggregator's loop rejects a `skipped` `sql-mutation` unless the push was docs-only. The tolerant path accepts `frontend = failure` and assumes the failure comes from the `sql-gate-lint` red. It only examines runs whose conclusion is outside `PREDECESSOR_OK_CONCLUSIONS`, and `skipped` is inside that set. Nothing in the tolerant path ever checks the `sql-mutation` run.

Measured with a scratch harness that imports `predecessorVerdict` and `syntheticDriftLog`. The input was the 26b041ce2 body: `sql-gate-lint` failure, `python` success and `frontend` failure, all in suite 7. Every one of these returns `{ ok: true, tolerated: true }`:
- `sql-mutation` concluded `success`;
- `sql-mutation` concluded `skipped`;
- the `sql-mutation` run is absent entirely.

The next push then narrows to a SUBSET. That is only sound if the predecessor's own mutation run actually proved the corpus. D-05 says "Tolerance must rest on POSITIVE evidence", and here no positive evidence covers the one job whose verdict the narrowing inherits.

**Why it is latent today:** `sql-mutation` and `sql-gate-lint` carry the same `if: needs.changed-paths.outputs.docs_only != 'true'`, so a `skipped` `sql-mutation` cannot appear beside a red `sql-gate-lint` right now. Any of these future edits would make the proof narrow over a predecessor that never mutated anything, with no test going red:
- giving `sql-mutation` its own skip route;
- renaming the job;
- splitting it into matrix shards, whose check-run names change.

Plan 02 accepts T-10 ("the `frontend` aggregator's own log is not read"). This is the concrete way that acceptance bites, so it is reported here rather than left inside T-10.

**Fix:** Require the positive fact directly, after the aggregator check:
```js
const mutation = runs.find((r) => r.name === "sql-mutation" && r.check_suite.id === lintSuite);
if (!mutation || mutation.conclusion !== "success") {
  return { ok: false, why: `check 'sql-mutation' ${mutation ? `concluded ${mutation.conclusion}` : "is absent"} in ${TOLERATED_DRIFT_CHECK}'s suite ${lintSuite}, so the predecessor's mutation verdict is unproven` };
}
```
Add `skipped` and absent refusal rows to the self-test, and add a contract pin that the `sql-mutation` job key exists. That pin should sit beside the existing `TOLERATED_DRIFT_CHECK` pin, so a rename goes red in the contract test rather than silently.

### WR-02: Each worker reuses one fixed port for its whole share of the corpus, so one bad port poisons every later lane on that worker and is misreported as corpus defects

**File:** `scripts/mutation-runner/run.mjs`. Symbols: `runCorpus` (`worker` passes `ports[k]` to every `runFile`), `allocateLanePorts`, and `spawnAsync` (ENOBUFS path).

**Confidence:** 4/10. This is unmeasured: no CI run has shown it, and the scenarios below are low-frequency.

**Issue:** Before this phase, every lane ran without `PORT`, so `scripts/pg-lane/run.sh` called `alloc_port` and got a fresh port per lane. A port problem could affect one lane at most. Now `allocateLanePorts` opens and closes N listeners once, and worker k sends every lane of every file it claims to `ports[k]`, for the whole run (minutes, and on the order of 150 lanes per worker on a FULL run). The port is not held between lanes, and each lane leaves it unbound during teardown, the collision probe, initdb and `pg_ctl start`.

If anything holds `ports[k]` when the next lane starts, `run.sh`'s collision guard exits **2** (or `pg_ctl` fails and the lane exits 1). That is an integer status, so `laneSpawnFailure` returns null and the runner records:
- a `baseline` defect ("pristine corpus did not go GREEN"), or
- an arm-level `wrong-first-failure`, which `no identity` explains.

Those are corpus defects attributed to an instrument fault. This is the misattribution class `laneSpawnFailure`'s own doc comment exists to prevent. It now repeats for every remaining file on that worker, instead of hitting one lane. Concrete ways the port gets held:
1. **This phase's ENOBUFS path uses `SIGKILL`.** `spawnSync`'s maxBuffer kill used its default `killSignal`, SIGTERM. `run.sh` turns SIGTERM into its EXIT-trap cleanup (`trap 'exit 143' TERM`) and stops the cluster. SIGKILL bypasses the trap, so the daemonized postmaster survives, still bound to `ports[k]`. `rmSync(scratchRoot)` later deletes its data dir out from under it.
2. **A failed `pg_ctl stop`.** `run.sh` already warns about this "ORPHANED on port" case. Before this phase it cost nothing beyond the leak. Now it poisons the worker.
3. **Ephemeral-range reuse.** `listen(0)` draws from the same `ip_local_port_range` that sibling lanes' psql clients use for their outbound source ports. Linux's parity split (bind(0) prefers odd ports, connect() prefers even) makes this very unlikely on the ubuntu runner. macOS developer boxes have no such split.

**Fix (any one closes the cascade; the first two are cheap):**
- In `spawnAsync`, kill with `SIGTERM` on overflow, matching `spawnSync`'s default, so `run.sh`'s trap still stops the cluster. Escalate to SIGKILL only after a grace period.
- Classify a lane that died before running SQL as `lane-unrunnable`, not as a corpus verdict. For example, have `runLane` treat `run.sh`'s collision exit (2) as `measureFail: "lane could not run: port collision"`. Or check the output for `run.sh`'s `ERROR: … Refusing.` marker before judging status.
- Allocate a fresh port per lane rather than per worker. Keep the in-flight set distinct by allocating inside `runFile` immediately before each `laneRunner` call, and exclude ports held by siblings. Optionally allocate below `ip_local_port_range`'s low bound so client source ports can never land on a lane port.
