## Fixed Issues

### SFH-03: An output overflow in one lane can hang the pool until the 20-minute cancel, with no lane named

**Status:** fixed: requires human verification
**Files modified:** `scripts/mutation-runner/run.mjs`, `src/__tests__/mutation-runner-floors.test.ts`
**Commit:** `9c04f3481`

**What changed (`spawnAsync`):**
- Lanes are spawned with `detached: true`, so each lane is its own process group.
- On overflow, the runner sends SIGTERM to the whole group (`process.kill(-pid, "SIGTERM")`, ESRCH tolerated). `psql` dies, so bash's deferred `trap 'exit 143' TERM` fires and `run.sh`'s EXIT trap stops the cluster. That is the behaviour `spawnSync`'s default `killSignal` gave before this phase.
- The pipes keep being drained and discarded until bash exits. `run.sh`'s cleanup writes WARNING lines to stderr, and a closed read end would SIGPIPE bash partway through its teardown.
- A group that ignores SIGTERM gets SIGKILL after `graceMs`. The production default is 5000 ms, and the timer is unref'd and cleared on settle.
- An overflowed lane settles on `exit`, then destroys both pipes, so a straggler still holding them gets SIGPIPE instead of blocking the run. A normal lane still settles on `close`, so no trailing output is lost.
- The result shape is unchanged: `error.code === "ENOBUFS"`, with `status` and `signal` null. `laneSpawnFailure` therefore still returns `lane could not run: ENOBUFS`, and `runLane`'s `invoked = !proc.error` rule is untouched.
- **Side effect handled:** `detached` takes lanes out of the runner's terminal process group, so a Ctrl-C or a job-cancel signal sent to the runner would no longer reach them. `forwardSignalsToLaneGroups` is installed once, on the first spawn. It passes SIGINT, SIGTERM and SIGHUP to every live lane group, then re-raises the signal on the runner, so the runner still dies of it.
  - Measured locally: SIGINT sent to a node process holding a `sleep 30` lane made the lane's INT trap fire, node exited 130, and no process was left behind.
- `spawnAsync` is now exported, for the test rows only. `runLane` is still its only production caller.

**Rows added:**
- `SELF-TEST (lane lifecycle) 1/2`: bash runs with TERM and EXIT traps and a foreground `yes` grandchild that floods without end (`; :` stops bash from exec-ing into it, which is the same shape as `psql`). The row asserts three things:
  - the lane settles within a 15 s watchdog;
  - it is classified as `lane could not run: ENOBUFS`;
  - the EXIT trap ran.
- `SELF-TEST (lane lifecycle) 2/2`: the same lane, but the whole group ignores SIGTERM. It must be SIGKILLed after a 500 ms grace and still settle as ENOBUFS.
- Three vitest rows mirror these: the trap-running flood, the TERM-deaf flood, and a normal lane that must still settle on `close` with its full output and its own exit status.
- Each flood row kills its flooder by a unique token in a `finally`, so a RED run leaves nothing behind. Checked with `pgrep` after every neuter run: nothing remained.

**Neuter evidence:** restored each time from a byte backup with `cp`, confirmed with `cmp`, and never with `git checkout`.
1. Neutered to the pre-fix logic (`child.kill("SIGKILL")`, settle on `close` only, not detached):
   - self-test: `SELF-TEST FAIL: the flooding lane settled (after 15000 ms; null = still running at the 15 s watchdog)` and `SELF-TEST FAIL: the TERM-deaf lane settled (after 15000 ms; null = still running at the 15 s watchdog)`, then `=== SELF-TEST FAILED ===`, rc=1;
   - vitest: both flood rows fail at their 10 s watchdog (`still running at the 10 s watchdog: the overflow kill did not end the lane`).
2. Neutered to SIGKILL sent to the group (untrappable) while still settling on `exit`: the vitest row fails with `the EXIT trap did not run: the lane was not stopped with a trappable signal`. This shows the trap-ran assertion catches a SIGKILL-based fix on its own.
3. Restored: lane lifecycle 1/2 settled in 7 ms and 2/2 in 506 ms, and the full self-test passed (rc=0).

### SFH-01: An orphaned lane cluster now blocks its worker's fixed port, and every later lane on that worker is reported as a corpus defect

### WR-02: Each worker reuses one fixed port for its whole share of the corpus, so one bad port poisons every later lane on that worker and is misreported as corpus defects

**Status:** fixed: requires human verification (one fix for both findings)
**Files modified:** `scripts/mutation-runner/run.mjs`, `src/__tests__/mutation-runner-floors.test.ts`
**Commit:** `d86984b40`

**What changed:**
- **Part 1, the SIGTERM teardown:** this is the SFH-03 commit above. An overflowing lane no longer bypasses `run.sh`'s trap, so the orphan path that SIGKILL created no longer exists.
- **Part 2, the classification:** a new pure exported function, `lanePortCollision(proc)`, returns `lane could not run: port 127.0.0.1:<P> was already taken (run.sh's collision guard refused, exit 2)`. It does so only when **both** of the following hold:
  - the exit status is 2;
  - `run.sh`'s own line-anchored `ERROR: something is already listening on 127.0.0.1:<P>` line is present (or the `pg_isready` fallback spelling `ERROR: a PostgreSQL server on 127.0.0.1:<P>`), along with its `This lane would DROP SCHEMA public CASCADE on it. Refusing.` line.

  Exit status 2 alone is not enough, because `psql` exits 2 on a lost connection, which is a real lane outcome. `runLane` now classifies with `laneSpawnFailure(proc) ?? lanePortCollision(proc)`. The refused lane did start a process, so it stays `invoked` and both tallies count it, the same way a signalled lane is counted. The baseline, arm and restore verdicts already route any `measureFail` to `lane-unrunnable`.

**Rows added:**
- `SELF-TEST (port collision) 1/1`: a real `runLane` call through `runCorpus`'s real verdict loop. The lane's port is already held by a `createServer().listen()`, standing in for an orphaned postmaster. The probe leg keeps its own port. The row asserts three things:
  - exit code 1;
  - a `lane-unrunnable` defect naming that port;
  - no `baseline`, `wrong-first-failure` or `restore` defect.
- Three vitest rows:
  - the classifier, in both `port_occupied` spellings;
  - the negatives: a lost psql connection at exit 2, the text at exit 3 or 0, the text inside a `psql:` diagnostic, and the ERROR line without the refusal line;
  - the wiring line in `runLane`, plus a check that `run.sh` still prints the exact lines the classifier matches, followed by `exit 2`. This catches drift between the two files.

**Neuter evidence:** restored from a byte backup with `cp`, confirmed with `cmp`.
1. Wiring neutered (`runLane` back to `laneSpawnFailure(proc)` alone):
   - self-test: `SELF-TEST FAIL: a lane-unrunnable defect names port 63638 as already taken (got ["baseline: pristine corpus did not go GREEN (exit 2); first failure: none"])`, then `=== SELF-TEST FAILED ===`, rc=1. This is exactly the misattribution the reviewers described;
   - vitest: the wiring row fails.
2. Classifier neutered (`lanePortCollision` returns null): the vitest positive row fails.
3. Restored: the self-test row prints `lane-unrunnable: MEASURE_FAIL: lane could not run: port 127.0.0.1:63045 was already taken (run.sh's collision guard refused, exit 2) — the runner could not execute the baseline lane, ...`, and the full self-test passes (rc=0).

## Known limits (recorded, not fixed)

- **The per-worker port can still cascade, but it is now named correctly.** If something holds `ports[k]` (a `pg_ctl stop` that failed, or an unrelated listener), every later lane on worker k is now a `lane-unrunnable` MEASURE_FAIL naming the port, not a corpus defect. The run still exits 1, and the defect table points at the instrument. WR-02's third option, a fresh port per lane (or a fresh port after any MEASURE_FAIL lane), was **not** taken. It is a scheduling change beyond the brief, and the misnaming is closed without it.
- **Signal forwarding covers SIGINT, SIGTERM and SIGHUP only.** A SIGKILL sent to the runner itself cannot be forwarded. That was already true before this phase: a SIGKILLed node never signalled its children. Such lanes end by SIGPIPE when they next write, and `run.sh`'s trap then runs.
- **The SIGKILL escalation can still skip `run.sh`'s trap.** It fires only for a lane group that ignores SIGTERM. `run.sh` traps TERM and does not ignore it, so this path guarantees that the run settles, not that the cluster is torn down.
