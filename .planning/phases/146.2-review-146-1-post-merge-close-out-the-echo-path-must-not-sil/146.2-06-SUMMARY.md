## Accomplishments

### R7 — the route-side date fence (Task 1, `4850cd18`)

The fold refuses a pre-1900 row itself: GUARD 9,
`20260819151000_csv_finalize_fold_guard1_null_safe.sql:369` —
`OR (elem->>'date')::DATE < DATE '1900-01-01'` — with SQLSTATE 22023. On this route a
fold 22023 is a CLASS 1 rolled-back failure answered **500 CSV_FINALIZE_FAIL**, whose
copy tells the user the submission is *safe to try again*. It is not. The same file
fails identically forever, so the user was being invited into a retry loop that cannot
terminate.

`parseDailyReturnsSeries` already mirrored GUARD 9's other two conjuncts — the
`|daily_return| <= 10` magnitude bound mirrors `BETWEEN -10 AND 10`, and the future-date
arm mirrors `> now()::date`. Only the lower bound was missing. It is now a
`MIN_DAILY_RETURN_DATE` constant holding the fold's literal **copied verbatim**, with the
obligation to move both in one commit stated at the constant and at the fence.

**Magnitude parity re-confirmed, not changed** (the plan asked for a check, not an edit):
the route rejects `Math.abs(r.daily_return) > 10`, accepting `[-10, 10]`; the fold's
`BETWEEN -10 AND 10` accepts `[-10, 10]`. Equal.

The comparison is lexicographic, which is sound for the regex- and calendar-validated
fixed-width `YYYY-MM-DD` form — the same property the resolve arm's min/max scan and its
`ORDER BY date` reads already rely on, cited in the comment.

### Absorbed item 5 — the two undriven fail-closed arms (Task 2, `8c881aa3`)

`resolveExistingStrategyOrRefuse` funnels every unusable read into one `failClosed()`
helper (503 `CSV_PERSIST_FAIL` + a capture tagged `finalize-resolve-read-fail`). Two of
its call sites had **no test at all**, so the step tag was unpinned:

- **A** — the strategies re-fetch resolves with an error object. supabase-js resolves on
  a read failure rather than throwing, so an unchecked binding reads as "no row": a
  failed read rendered as a measurement.
- **B** — the re-fetch resolves `data: null` with no error.
- **B'** — added beyond the plan: a row whose `id` is not a UUID. `!isUuid(existingRow.id)`
  is the second half of the same predicate and a `data: null`-only case leaves it unpinned.

⭐ **The arms are separated by forensic payload, not by status or tag.** Both funnel into
the same helper, so on status + tag alone, deleting `if (refetchErr) return failClosed(…)`
would let case A fall through to the null arm and the case would still pass — pinning
nothing. Each case therefore asserts what the capture CARRIES: arm A the driver's error
(SQLSTATE `57014`, which is how ops tells a statement timeout from an RLS hide), arm B a
synthetic Error naming the condition. Neuter N4 below is the proof.

### Absorbed item 4 — the echo discrimination, restored and BOUNDED

The c14 resolve-echo case seeds `status: 'private'` and asserts the echoed body reports
`'private'`. With 146.2-01's `?? "pending_review"` fallback gone, replacing the echoed
value with any hardcoded literal — the old fallback constant first among them — reds this
case. That is "echoed, not fabricated", carried by this case alone again (neuter N5).

**What it still cannot prove is now written into the test rather than implied.** A2
refuses every echo whose committed status differs from the request's, so on any surviving
echo path the two are provably equal: **no test here can separate `existingRow.status`
from `args.terminalStatus`**, because the code guarantees they hold the same value. That
substitution is discriminated by the refusal cases in
`csv-finalize-cross-submission-merge.test.ts`, and the comment says so. The plan's phrasing
("the discrimination is provable again") was narrowed to what is actually true — see
Deviations.

**Fixtures now DECLARE `category_id` / `asset_class`.** Since 146.2-01 those columns drive
a tri-state where absent, `null` and a string each mean something different, so an omitted
field silently selected the absent branch. The one case that keeps them absent (B', whose
predicate sits above the tri-state) says so and says why.

### Absorbed item 1 — the audit event (Task 3, `1fc9abdb`)

**Decided IN SCOPE by the plan, and implemented — not deferred.** The fold commits a
user-visible strategy, its verification row and its whole daily-returns series in one
transaction. It is the creation of a track record on a product whose entire value is that
the record is trustworthy, and it was the only such write with no forensic row at all.
`create-with-key` skips `create_wizard_strategy` on the grounds that "the user-visible
creation is audited at finalize time"; that rationale cannot be reused here, because this
IS finalize.

- **`@audit-skip` deleted.** It was an honest placeholder, but a pragma is an *exemption*:
  while it sat there the audit-coverage law waved the mutation through. With it gone the
  law now REQUIRES the emission (neuter N6 shows the law naming `route.ts:694`).
- **The taxonomy extension is a FOUR-step, not the documented three.**
  `analytics-service/services/audit.py` carries a mirrored `Literal` that
  `TestAuditTaxonomySyncWithTypeScript::test_action_literal_matches_ts_union` pins
  byte-for-byte. Verified by removing the Python entry and observing the parity test red
  (`Extra items in the right set: 'strategy.csv_finalize'`). This is recorded as a
  deviation because the plan's `files_modified` did not list that file.
- **Emission on the FRESH branch only.** A 23505 resolve echo means a PRIOR request
  created the row and this one rolled back entirely; emitting there writes a second
  creation record for one creation, which on an append-only log is not a duplicate but a
  false fact.
- **`logAuditEventAsUser` + admin client**, matching the preferences route's C-2 call
  shape: the emit settles inside `after()` after the response flushes, and
  `log_audit_event` derives its actor from `auth.uid()`, so a short-TTL JWT expiring in
  that window yields a 200 with no audit row. The service-role path is JWT-immune.
- **Behavioural cases added, because the law is a static grep.** It proves a call is
  WRITTEN within its window and nothing else — it would stay green if the call sat on an
  unreachable branch, fired on every echo, or named the wrong entity. Three cases now
  drive it: fresh emits exactly one correctly-anchored event; an echo emits nothing; a
  failed fold emits nothing.
- **No DB migration needed:** `audit_log.action` is free-form `TEXT` with no CHECK
  constraint (verified at HEAD).

⚠️ The comment above the fold call now states the constraint that made the placement
non-obvious: **the emission must stay within 60 lines below the RPC**, because that is the
law's own coverage window. Moving it to the enqueue epilogue would silently
un-instrument the mutation while every test stayed green.
