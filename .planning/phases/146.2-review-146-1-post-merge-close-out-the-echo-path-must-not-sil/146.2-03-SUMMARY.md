# Phase 146.2 Plan 03: R4 — The Re-mint Persists the New Id Summary

**The RT-3 re-mint wrote the envelope before it swapped the session id, so it persisted the RETIRED id next to the CLEARED burn; the mint now happens into a local that feeds both the setter and a single save, so a reload in that window can never resume a spent id with the fence disarmed.**

## Accomplishments

- **R4 closed.** At `WizardClient.tsx:595` the burn-clear `saveWizardState({ wizardSessionId, …, failedCsvSubmitSig: null })` captured the OLD closure value and `setWizardSessionId(newWizardSessionId())` ran after it, with no follow-up save. The persisted pair therefore de-synced: burn cleared, id spent. A reload in that window restored a session id the server had already seen with nothing left to retire it, so the corrected resubmit took the server's equality refusal (409) and the user was stuck. The name autosave cannot repair it — it is gated on step `csv_upload` and the re-mint fires past that step.
- **Fixed to the file's own house rule.** The burn site 25 lines below already states it: *"The ref and the envelope are set from one expression so they cannot disagree."* The re-mint now does the same — `const nextWizardSessionId = newWizardSessionId()` feeds both `saveWizardState` and `setWizardSessionId`. One call, no second save, no flush choreography: `saveWizardState` serializes by CALL order (documented at `src/lib/wizard/localStorage.ts:283-296`), so a single call cannot be interleaved.
- **The regression pins the CALL SITE, not the helper.** It drives the real component through failed-submit → unmount (reload) → hydrate → corrected upload, then reads what a reload at that instant would resume from — the actual signed envelope in the storage double. Only `newWizardSessionId` is spied.

## Decisions Made

- **Mint into a local, not a second save.** The alternative — leave the write first and add a follow-up `saveWizardState` with the new id — would have made correctness depend on two queued writes both landing, and would have contradicted the file's stated house rule. One expression, two consumers, one call.
- **Telemetry keeps the RETIRED id.** `trackForQuantsEventClient("wizard_csv_session_reminted", { wizard_session_id: wizardSessionId })` still reads the old binding. The comment at that site says this is deliberate (an operator correlates the re-mint with the earlier `wizard_error` on the session the failed submit spent). Preserved verbatim; the fix is careful to introduce `nextWizardSessionId` rather than reassign anything the telemetry reads.
- **Instance-only.** `newWizardSessionId()` has five call sites. `:203` is the mount initializer; `:853` and `:900` both run immediately after `clearWizardState()` (no envelope survives to disagree with); `:1140` is the API-branch restart, also post-clear. Only the CSV re-mint writes an envelope in the same commit as a swap. Sites left untouched, confirmed by the hunk list (all four hunks in `:589-615`).
- **Waited on the cleared burn, not on a timer.** The case blocks on "the re-mint's write has landed" using the same signal the pre-existing clear case uses, then asserts the id synchronously. That yields a precise `expected 'mint-1' to be 'mint-3'` failure instead of an uninformative `waitFor` timeout.
