<domain>
## Phase Boundary

Every Python blend reads daily returns, never the stored wealth curve as if it were returns.

`strategy_analytics.returns_series` holds the strategy's cumulative curve (`services/metrics.py`: `(1 + r).cumprod()` on the geometric method, `1 + Σr` on the simple method), written at the end of `compute_all_metrics`. Measured on PROD 2026-10-07 across 32 rows: first value about 1.0, last values averaging about 209k. These Python sites read it through `_records_to_series` and weight it as daily returns:
- `routers/portfolio.py`: `_compute_portfolio_analytics` (also run by `routers/cron.py` and `services/job_worker.py`), `portfolio_optimizer`, `portfolio_bridge`
- `routers/simulator.py`: `portfolio_simulator`
- `routers/match.py`: `_load_candidate_universe`, `_load_allocator_context`, `_score_one_allocator`
- `services/native_to_usd.py` (`UsdSeriesConverter`), the 164.6.6.2 BTC twin, which is fed the same curve

The TypeScript side already converts through `resolveDailyReturnSeries` / `equityCurveToDailyReturns` (`src/lib/factsheet/resolve-series.ts`), but always by ratio.

In scope: one shared Python boundary that turns a stored row into daily returns; every site above reading through it; the TypeScript resolver honouring the same method rule; `_compute_portfolio_analytics`'s missing-column read; fixtures that can tell a curve from returns; a PROD before/after measurement.

Out of scope: the USD view of a BTC account (Phase 164.6.6.2.1 BTCUSDVIEW); changing how `returns_series` is written; the 164.6.6.2 review MEDIUMs not named here.
</domain>

<decisions>
## Implementation Decisions (founder, 2026-10-07)

- **D-01 Honor the stored cumulative method, in both runtimes.** A compounded (geometric) curve converts by ratio, `r_k = w_k / w_{k-1} - 1`; a simple (sum-based) curve converts by difference, `r_k = w_k - w_{k-1}`. The method is read from what the row already stores (research to name the field). The TypeScript resolver gets the same rule, so Python and TypeScript read the same series from the same row. Day 0 is dropped (it has no prior value). A non-finite or non-positive level on the ratio path makes the dependent day absent, never 0.
- **D-02 `daily_returns` first.** Where the row has a non-empty `daily_returns` column (CSV strategies), Python reads that and derives from `returns_series` only when it is empty, the same order as the TypeScript `resolveDailyReturnSeries`.
- **D-03 Rollout: measure, ship, let the crons recompute.** Record before/after outputs for a sample on PROD in the phase (marker query first, read-only), ship, and let the next scheduled runs replace stored outputs. No manual backfill.
- **D-04 Fix `_compute_portfolio_analytics` here.** It selects `equity_curve` and `total_aum`, which do not exist on `strategy_analytics`, so it cannot complete on PROD today. Research first measures how it fails on PROD (logs, job rows). Rebuild its inputs from the corrected daily returns and drop or re-source the missing columns from real ones.

- **D-05 Stamp the method on the row (founder, after research).** The single-key analytics run writes `cumulative_method` into the row's `data_quality_flags` (`analytics_runner.py`, plus the `DataQualityFlags` TypedDict), as composites already do. No migration. Readers default to geometric when the key is absent, which is exact for every PROD row today (research: all 32 curves geometric, no simple row). This adds a key to the flags; it does not change how `returns_series` is written.
- **D-06 Include the two correlation matchers.** `verify_strategy` matching (`routers/portfolio.py`) and `services/strategy_matching.py` read through the same shared boundary.
- **D-07 Portfolio total AUM = sum of `portfolio_strategies.allocated_amount`,** null unless every strategy in the portfolio has one (a 0 counts).

### Claude's Discretion
- The shape of the shared boundary (one function in a services module that every router imports, versus a fix inside each `_records_to_series` copy) — the planner picks, preferring one implementation over three copies.
- The shared oracle: whether to extend `tests/fixtures/native_to_usd_oracle.json` or add a sibling fixture for the curve-to-returns step, read by both runtimes.
</decisions>
