## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01 Honor the stored cumulative method, in both runtimes.** A compounded (geometric) curve converts by ratio, `r_k = w_k / w_{k-1} - 1`; a simple (sum-based) curve converts by difference, `r_k = w_k - w_{k-1}`. The method is read from what the row already stores (research to name the field). The TypeScript resolver gets the same rule, so Python and TypeScript read the same series from the same row. Day 0 is dropped (it has no prior value). A non-finite or non-positive level on the ratio path makes the dependent day absent, never 0.
- **D-02 `daily_returns` first.** Where the row has a non-empty `daily_returns` column (CSV strategies), Python reads that and derives from `returns_series` only when it is empty, the same order as the TypeScript `resolveDailyReturnSeries`.
- **D-03 Rollout: measure, ship, let the crons recompute.** Record before/after outputs for a sample on PROD in the phase (marker query first, read-only), ship, and let the next scheduled runs replace stored outputs. No manual backfill.
- **D-04 Fix `_compute_portfolio_analytics` here.** It selects `equity_curve` and `total_aum`, which do not exist on `strategy_analytics`, so it cannot complete on PROD today. Research first measures how it fails on PROD (logs, job rows). Rebuild its inputs from the corrected daily returns and drop or re-source the missing columns from real ones.

## Summary

`strategy_analytics.returns_series` is the cumulative curve, not returns: geometric `(1 + returns_for_chart).cumprod()` at `analytics-service/services/metrics.py:1829`, simple `1.0 + _cumsum` at `:1762`, persisted at `:2048-2063` as `[{date, value}]` capped to the trailing 5000 points (`services/transforms.py:395`, no downsampling, so consecutive points are consecutive days). Measured on PROD this session (32 rows with a non-empty curve): first value 0.979 to 1.021, median last value 1.369, mean last value 209,472 (one outlier at 2.34M), 0 non-positive levels, lengths 25 to 1112. Every Python reader weights those levels as returns.

The method that built each curve is already stored, but in three places of unequal reach. **`data_quality_flags.cumulative_method`** is written only by the composite stitch (`services/job_worker.py:9223`); the single-key/CSV runner rebuilds `data_quality_flags` as `{"csv_source": True}` (`services/analytics_runner.py:1907`) and does not write it. The **frozen `strategy_analytics_series` row `kind='cash_settlement'`** carries `payload.conventions.cumulative_method` (`services/basis_series.py:268,358`), persisted from the same `derive_basis_series` result that produced `returns_series` (`analytics_runner.py:2104-2105`). The **live `strategies.returns_denominator_config`** can drift after the run. On PROD all 32 curves are geometric: 22 rows have a `cash_settlement` conventions row (all `geometric`/`calendar`), 3 composites carry the dqf key (all `geometric`), 10 rows carry neither (8 `failed` rows holding a stale curve, 2 legacy `complete` rows), and 0 of 45 strategies have a `returns_denominator_config`.

**Primary recommendation:** add one pure module `analytics-service/services/wealth_returns.py` (pandas only, no router imports) holding the single `records_to_series`, the method parser and `daily_returns_from_row(row, name=)` (D-02 order, method from `row["data_quality_flags"]`); make all eight Python read sites call it; give the TS resolver an optional `method` argument defaulting to geometric; share one hand-computed oracle `analytics-service/tests/fixtures/wealth_to_returns_oracle.json` read by pytest and vitest. Resolve the method from the row alone by also stamping `cumulative_method` into the single-key `data_quality_flags` (Open Question 1, needs a founder yes).

### Pattern 1: one pure services module, routers import it
**What:** `routers/simulator.py:181-186` keeps its own `_records_to_series` "so the simulator router doesn't cross-import from another router"; `services/strategy_matching.py:50-62` keeps its own to avoid a circular import once `process_key` imports it. A services module importing only pandas/numpy/logging satisfies both. `services/native_to_usd.py` is the precedent (pure, injected I/O; routers and services already import it).
**When:** every read of `returns_series`. Replace all four copies (portfolio `:429`, match `:252`, simulator `:181`, strategy_matching `:50`) with the one tolerant version: skip malformed records with one warning, `sort_index`, dedupe `keep="last"` (the simulator's G15-006 behaviour, a superset of the other three; the portfolio and match copies do not dedupe).

### Pattern 2: call at the row, convert after
Every site already builds `_records_to_series(row.get("returns_series"), name=sid)` from a row that also carries `data_quality_flags` (except the two matching sites), then calls `UsdSeriesConverter.convert`. Swap only the first call; the converter order is unchanged (boundary, then USD conversion, then the weighted sum). The converter drops its input's first point again (`native_to_usd.py:107-110` loops `k >= 1`; TS `native-to-usd.ts` loops `k = 1`), so a BTC leg loses its first two stored days, in both runtimes. That is parity, not a defect to fix here (see Pitfall 7).

### Anti-Patterns to Avoid
- **Fix inside each copy:** four divergent copies is how the simulator got sort+dedupe and the others did not.
- **Reading the live config as tier 1:** `returns_denominator_config` can be edited after the run; the stored method must win (TS `resolveMetricsConventions`, `composite-read-path.ts:930-976`, already orders dqf, then frozen conventions, then config).
- **A third vocabulary:** the worker strings are `"geometric"` / `"simple"`; the `simple` to `arithmetic` map lives only in the factsheet read basis (`composite-read-path.ts:975`). The new helper takes the raw worker string.

## Common Pitfalls

### Pitfall 1: stale `failed` rows keep a curve
**What goes wrong:** 10 of 32 PROD curves belong to `failed` rows; Python blends read them (no status gate), so before/after samples mix dead runs. **Avoid:** do not widen scope to add a status gate; filter the replay sample to `complete*` rows (22) and say so. **Sign:** a replay count of 32 not 22.

### Pitfall 2: simple-method row read as geometric
**What goes wrong:** the single-key runner writes no dqf method, so a dqf-only reader defaults to geometric on a `1 + sum(r)` curve (ratio of sums, a wrong return). **Avoid:** Open Question 1 option A; the oracle's `same curve, both methods differ` case. **Sign:** 0 such rows on PROD today, so it is silent until the first allocated-capital strategy.

### Pitfall 3: day 0 is lost, not recovered
First stored level is `1 + r_0` (PROD first values 0.979-1.021). D-01 drops day 0; it is consistent with the legacy day-0 exclusion and with TS. Do not "recover" `r_0 = w_0 - 1`.

### Pitfall 4: filter-then-pair bridges a bad level
Current TS drops non-positive levels then pairs survivors, emitting a multi-day ratio. D-01 wants the dependent day absent. **Avoid:** adjacency is in the STORED order; day k is emitted only if both `w_{k-1}` and `w_k` are valid. Oracle case `nonpositive_level_mid_series` (levels 1.0, 1.1, 0, 1.2, 1.32 geometric: day 1 = 0.1, days 2 and 3 absent, day 4 = 0.1) is RED on today's TS.

### Pitfall 5: non-positive is legal on the simple path
A `1 + sum(r)` curve can be at or below 0 after a large cumulative loss; differences stay valid. Only the ratio path drops on non-positive. Non-finite drops the dependent day on both.

### Pitfall 6: the writer stamp breaks two exact-equality tests
`tests/test_csv_analytics_runner.py:144` and `:394` assert `data_quality_flags == {"csv_source": True}`. If option A is taken they change, and `DataQualityFlags` (`analytics_runner.py:103`) needs the key. The composite and TS readers already treat the key as tier 1, so the write is additive. No migration, no DDL.

### Pitfall 7: a BTC leg loses its first two stored days
The boundary drops day 0; the converter drops its input's first point again. TS does the same. Keep it (parity); put one oracle case that pins the combined behaviour so a later "fix" in one runtime cannot drift.

### Pitfall 8: dedupe and sort are behaviour changes for portfolio/match paths
The portfolio and match copies never sorted or deduped. Moving to the simulator's behaviour is correct for a diff (an unsorted curve gives garbage ratios) and benign for unique-date input; the duplicate-date oracle case is OPTIONAL because TS `normalizeDailyReturns` does not dedupe (keep it out of the shared oracle unless TS gains the same rule).

### Pitfall 9: mocks that accept any column
Make `_make_supabase_for_compute` (and the other table routers) reject a select naming a column absent from `strategy_analytics` (parse `supabase/schema/baseline.sql`, the precedent being `src/__tests__/strategy-analytics-match-columns-schema-sync.test.ts`). Neuter by re-adding `equity_curve`: must go RED.

## Code Examples

### Boundary (illustrative contract; the executor writes it)
```python
# analytics-service/services/wealth_returns.py -- pure: pandas, numpy, logging only
def curve_to_daily_returns(levels, method):
    s = levels.sort_index()
    s = s[~s.index.duplicated(keep="last")]
    v = pd.to_numeric(s, errors="coerce")
    prev = v.shift(1)
    if method == CURVE_SIMPLE:
        ok = np.isfinite(v) & np.isfinite(prev)
        out = (v - prev)[ok]
    else:
        ok = np.isfinite(v) & np.isfinite(prev) & (v > 0) & (prev > 0)
        out = (v / prev - 1.0)[ok]
    out = out.iloc[1:] if len(out) and out.index[0] == v.index[0] else out   # day 0 never emits
    return out.rename(levels.name) if len(out) else None
```
Source: derived from the CR-01 fix sketch (`164.6.6.2-REVIEW.md` CR-01 "Fix") extended with the method switch and the adjacency rule from D-01. The first row of `prev` is NaN so day 0 already fails `ok`; the explicit guard is belt and braces.
