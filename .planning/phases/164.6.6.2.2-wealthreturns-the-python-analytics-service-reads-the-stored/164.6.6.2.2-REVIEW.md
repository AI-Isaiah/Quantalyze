## Summary

The core of the phase is correct. I checked these points and found no defect in them:

- **Boundary math (`services/wealth_returns.py`).** Geometric reads `w_k/w_{k-1}-1` and simple reads `w_k-w_{k-1}`, with no sign error. Day 0 is dropped and pairs are formed by stored adjacency, so a bad level makes both of its dependent days absent and nothing is bridged. A non-positive level is unusable only on geometric. "Nothing usable" returns `None`, never an empty Series, and every router's `is not None` path is unchanged.
- **Method default.** An absent stamp, null, or non-mapping flags read geometric silently. An unknown string warns once and reads geometric. All PROD curves are geometric, so this is exact.
- **Writer side.** `cumulative_method` is stamped in `run_csv_strategy_analytics` (`analytics_runner.py:1926`) from the same variable handed to `derive_basis_series`. The composite path already stamps it (`job_worker.py:9223`). The other `derive_basis_series` callers (MTM, smoothed, cash basis, process_key teaser) write the sibling basis tables, not `strategy_analytics.returns_series`.
- **Every Python reader is migrated.** portfolio compute, optimizer (in-portfolio and candidates), bridge (in-portfolio and candidates), verify_strategy, simulator, match universe and allocator book, and strategy_matching all go through the boundary. Each of their selects names `daily_returns` and `data_quality_flags`. No code in `routers/` or `services/` still parses `returns_series` itself.
- **Removed functions.** `usd_equity_from_converted_returns` and the four `_records_to_series` copies have zero remaining callers in the repo.
- **total_aum (D-07).** It is the sum of `allocated_amount`, filled before the analytics loop, using `is not None` so a 0 counts. It is None unless every strategy reports. Tests cover a missing analytics row and a strategy with no usable returns.
- **TWR scaffold.** `equity_from_daily_returns` + `total_return_from_equity` equals `prod(1+r)-1`. The portfolio TWR and BTC TWR now include the first blended day, consistent with each other.
- **TS twin.** Every `resolveDailyReturnSeries` caller passes `curveMethodFromFlags(...)`. The `allocator-portfolio-payload` re-export passes all three arguments. The raw flags never cross the RSC boundary.
- **Tests.** The Python phase suites pass (497 passed), and so do the TS phase suites (135 passed). The oracle uses hand-computed literals and is read by both runtimes. The runner-to-boundary end-to-end test inverts the real runner's curve, and it is proven able to tell the two methods apart.

The defects are in what sits around the boundary:

1. **(HIGH)** The blends this phase makes produce real numbers still annualize risk on √252 for crypto books.
2. **(MEDIUM)** The native->USD converter misprices the gaps that the boundary's ABSENT rule creates.
3. **(MEDIUM)** The tests cannot fail if a router stops honouring the method.
4. **(MEDIUM)** The census allowlist is count-only.
5. **(MEDIUM)** One TS component still correlates curve levels as returns.

### WR-01 [HIGH, confidence 8]: Blend risk is annualized on √252 regardless of asset class. Crypto portfolios now get plausible-looking, under-stated Sharpe and vol.

**Files:**
- `analytics-service/routers/portfolio.py:1056`: `sharpe_vol_status_from_backbone(portfolio_returns_series)` uses the default `periods_per_year=DEFAULT_PERIODS_PER_YEAR = 252` (`services/metrics.py:39`, `:2734`).
- `analytics-service/services/portfolio_optimizer.py:294`: `_compute_sharpe` hardcodes `np.sqrt(252)`. It is imported by `bridge_scoring.py:17` and `simulator_scoring.py:32`, which return `current.sharpe` / `proposed.sharpe` / `sharpe_delta` to the UI.

**Issue:** The diff does not touch these lines, so the defect is pre-existing. The phase makes it live and user-facing:
- **D-04** makes `_compute_portfolio_analytics` complete on PROD for the first time. Before, it selected two phantom columns.
- **D-01** turns its input from levels (Sharpe 30.68, vol 16.31 in MEASUREMENT.md) into real daily returns (Sharpe 2.32, vol 0.13).

The old numbers were obviously garbage. The new ones look credible but use the wrong clock. The project rule is: risk is annualized by frequency, crypto 365, traditional 252, and a blend uses 365 if any leg is crypto. Every PROD strategy in the replay sample is a crypto account on a calendar series.

**Failure scenario:** A crypto-only portfolio with daily mean 0.00121 and sd s. The displayed vol is `s·√252` against a correct `s·√365`, and the displayed Sharpe is `mean/s·√252` against `mean/s·√365`. Both are under-stated by a factor of `√(252/365) = 0.831`, a 17% understatement, and the dashboard persists them as the portfolio's headline. The simulator's `current.sharpe` / `proposed.sharpe` and the optimizer and bridge Sharpe figures carry the same bias.

**Fix:** Thread the clock from the strategies' `asset_class`. `periods_per_year_for_asset_class` already exists in `services/metrics.py`.
```python
# routers/portfolio.py, after strategy rows are known (select strategies(id, name, asset_class))
classes = {(row.get("strategies") or {}).get("asset_class") for row in portfolio_strategies}
ppy = 365 if any(c != "traditional" for c in classes) else 252   # any crypto/unknown leg -> 365
vol, sharpe, sharpe_status = sharpe_vol_status_from_backbone(portfolio_returns_series, periods_per_year=ppy)
```
Give `_compute_sharpe(returns, rf=0.0, periods_per_year=252)` a parameter, and pass the same blend clock from the optimizer, bridge and simulator callers. Add a test that pins a crypto book at √365. If the founder prefers to defer this, book it as a TODOS entry instead of leaving it implicit.

### WR-02 [MEDIUM, confidence 8]: The native->USD converter turns a boundary ABSENT day into a mispriced multi-day USD return (Python and TS twins).

**Files:** `analytics-service/services/native_to_usd.py:112-132`, interacting with `analytics-service/services/wealth_returns.py:173-188`. The TS twin pairs the same way: `src/lib/factsheet/native-to-usd.ts:57-62`, fed by `resolve-series.ts:84-95`.

**Issue:** The boundary drops a day whose level pair is unusable, so the output series has a date gap. The converter prices `r_k` against `P(d_k)/P(d_{k-1})`, where `d_{k-1}` is the previous date present in the series. That assumes `r_k` covers `[d_{k-1}, d_k]`. After an ABSENT day, `r_k` is a one-day native return, but the price leg spans the whole gap. This is the bridging the boundary docstring promises never happens, re-introduced one step downstream.

**Failure scenario (reproduced at HEAD):**
- Curve: `1.0, 1.1, null, 1.2, 1.32` on 03-02..03-06, `native_unit=BTC`.
- BTC closes: `100, 100, 200, 400, 400`.
- The boundary yields `{03-03: 0.10, 03-06: 0.10}`.
- The converter emits `03-06: 3.40` (+340%), because it computes `(1.1)*(400/100)-1`.
- The true USD return for 03-06 is `(1.1)*(400/400)-1 = 0.10`.

That +340% day is weighted into every blend that holds the leg. Today's writer never stores a null or non-positive geometric level (`metrics.py` fills NaN with 0, clips, and calls `_drop_nonfinite`), and PROD has no native-unit rows. So this is latent, but it is reachable from any legacy or hand-edited row and from the first BTC account that hits it. The oracle has no native case with a gap.

**Fix:** Keep the ABSENT position visible to the converter rather than deleting it. Add an internal variant that returns the series with NaN at absent days. The converter already skips a non-finite `r`, and its next pair then starts at the NaN day's date, so it prices exactly one interval. Drop NaN after conversion.
```python
def curve_to_daily_returns(levels, method, *, keep_absent: bool = False):
    ...
    out = out.where(mask)            # NaN where the pair is unusable
    if not keep_absent:
        out = out[np.isfinite(out)]
```
Native-unit callers convert the `keep_absent=True` series and then `dropna()`. Add the oracle case above (native + mid-series null) to `wealth_to_returns_oracle.json` so both runtimes are pinned.

### WR-03 [MEDIUM, confidence 8]: No test can fail if a router drops `data_quality_flags` from its select or otherwise stops honouring the curve method.

**Files:** `analytics-service/tests/test_wealth_returns_census.py:305-332`. The router suites (`test_portfolio_compute_integration.py`, `test_simulator_router.py`, `test_match_router.py`, `test_portfolio_router_logic.py`, `test_correlation_residue_sites.py`) contain no simple-curve row; `grep cumulative_method` finds no hit in them.

**Issue:** The method is read from `row["data_quality_flags"]`. If a select omits that column, `curve_method_from_flags(None)` reads geometric silently, by design, and every simple curve on that path is read by ratio. The census check requires `daily_returns` in each select (`:330`) but not `data_quality_flags`. Every router fixture is geometric, so the default and the stamped value coincide. That makes the per-router wiring of D-05 untested. The only simple-method proof is the boundary-level end-to-end test, which never goes through a router select.

**Failure scenario:** A future edit trims the optimizer select back to `"strategy_id, returns_series, daily_returns"`. Every test stays green. A strategy with `returns_denominator_config.cumulative_method='simple'` is then read by ratio in the optimizer. On a curve like `1.0 -> 0.5 -> -0.1` that makes days absent and changes values (oracle `nonpositive_level_is_legal_on_simple`).

**Fix:**
```python
# census, inside the per-select loop
cols = {c.strip() for c in str(s.value).split(",")}
if "data_quality_flags" not in cols:
    problems.append(f"{rel}:{s.lineno}: select names returns_series without data_quality_flags (method unreadable)")
```
Also add one parametrized simple-curve row (`curve_from_returns(..., method="simple")` plus the stamp) to each router suite, with a hand-computed expectation that differs from the geometric reading.

### WR-04 [MEDIUM, confidence 7]: The census allowlist is count-only. A raw curve parse can replace an allowlisted reference and keep the census green.

**File:** `analytics-service/tests/test_wealth_returns_census.py:163-194, 280-289`

**Issue:** `ALLOWED_RETURNS_SERIES_REFS` pins a COUNT per file and a free-text reason. `_code_references` counts every string constant and identifier alike: select lists, log messages, dict keys and `.get(...)` loads. In `routers/portfolio.py` (count 12), four of the twelve are log-message strings, and one (`row.get("returns_series")` at `:2589`) is already a value read.

**Failure scenario:** Someone deletes the word `returns_series` from one log message, for example `portfolio_optimizer: %d/%d portfolio strategies missing returns_series`. In the same commit they add `pd.Series({r["date"]: r["value"] for r in row["returns_series"]})` in a new helper. The count stays 12, the census passes, and CR-01 is back. The "no second parser" check only matches the names `_records_to_series` / `records_to_series`, so it does not catch an inline comprehension either.

**Fix:** Classify each hit instead of counting. A string constant is allowed only as an argument of a `.select(...)` call or a logger call. A load of the column (a `Subscript` / `.get` on a row, or a `Name`) is allowed only at enumerated `(file, enclosing function)` sites, today just `verify_strategy`'s trim. Anything else fails, naming the line. Keep the count only as a secondary tripwire.

### WR-05 [MEDIUM, confidence 8]: TS residual: `CompareCorrelationMatrix` still correlates stored curve LEVELS as daily returns (outside the 42-file scope, inside the phase's intent).

**File:** `src/components/strategy/CompareCorrelationMatrix.tsx:24-31`. The comment says "Extract trailing daily returns". The code takes `item.analytics.returns_series` values verbatim.

Then add a TS census twin of the Python one: a vitest scan that fails on a `returns_series` value read outside `resolve-series.ts` and an explicit allowlist (chart-as-curve consumers such as `CompareEquityOverlay` and `buildWealthPoints`).

### IN-01 [LOW, confidence 6]: A mixed-timezone date in a stored series raises instead of being skipped, which 500s a whole blend or cron.

**File:** `analytics-service/services/wealth_returns.py:130-132`

**Issue:** `pd.to_datetime(..., format="ISO8601", errors="coerce")` still raises `ValueError: Mixed timezones detected` (pandas 3.0.3, reproduced) when a series mixes `2026-03-02` and `2026-03-03T00:00:00+00:00`, or two different offsets. The docstring promises that malformed records are skipped and that None is returned "instead of a 500". In `_load_candidate_universe` a single such row aborts the recompute for every allocator, which is the M-0604 class the deleted copies were hardened against. An all-tz-aware series would also produce a tz-aware index that cannot join the naive indexes in the blends.

**Fix:** Parse with `utc=True` and then `.tz_localize(None)`, or catch `ValueError` around the parse and fall back to a per-record parse that skips the offenders with the existing single warning.

### IN-02 [LOW, confidence 5]: The Python and TS twins diverge on an overflowing derived return.

**Files:** `analytics-service/services/wealth_returns.py:184` against `src/lib/factsheet/resolve-series.ts:89-93`

**Issue:** Python drops a non-finite output (`out[np.isfinite(out)]`). TS pushes it. A positive subnormal predecessor (`prev=5e-324, curr=1`) gives `Infinity` in TS and an absent day in Python. Simple `1e308 - (-1e308)` behaves the same way. The module docstring lists the known parity gaps, but this one is not listed and the oracle does not cover it.

**Fix:** In TS, push only `Number.isFinite(v)` results, and add a 21st oracle case.

### IN-03 [LOW, confidence 7]: A comment over-claims that the per-strategy and portfolio TWRs cover "the same days (1..n)".

**File:** `analytics-service/routers/portfolio.py:835-839` (also `:884-890`)

**Issue:** Each strategy TWR is `prod(1+r)` over that strategy's own span. The portfolio TWR is over the union of all dates with `fillna(0)`. For strategies with different inception dates, `compute_attribution` compares returns over different windows. That is pre-existing semantics, but the new comment asserts the opposite and will mislead the next reader. The tests only use identical date sets.

**Fix:** Reword it to "each TWR covers its own series' days 1..n; the portfolio TWR covers the union". Optionally, book attribution-window alignment as a deferral.

### IN-04 [LOW, confidence 5]: The geometric writer bridges NaN days as 0.0, so the boundary's ABSENT-never-0 guarantee does not hold for chain-break days.

**File:** `analytics-service/services/metrics.py:1739, 1829` (writer, out of scope by CONTEXT), read by `wealth_returns.py:161-188`

**Issue:** `cumulative = (1 + returns.fillna(0).clip(...)).cumprod()` carries the level across an interior NaN chain break. The boundary then derives an exact `0.0` return for that day, which is indistinguishable from a real flat day, and the blends weight it as one. The module docstring's ABSENT rule only covers levels that are stored as bad.

**Fix:** Document the limit in the `wealth_returns` docstring. If it matters, have the writer stamp interior-gap spans (as `gap_spans` already exists on composites), and have the boundary mask those dates.

### IN-05 [LOW, confidence 6]: The census scans `routers/` and `services/` only, though the shared scan list also covers `scripts/` and the entrypoints.

**File:** `analytics-service/tests/test_wealth_returns_census.py:232-240`

**Issue:** `_py_scan_files()` returns `main.py`, `main_worker.py` and `scripts/**`, and `_surface_files` then filters them out. Nothing in those paths reads `returns_series` today (verified by grep), but a backfill or report script added there would be invisible to the census.

**Fix:** Drop the `startswith(("routers/", "services/"))` filter, keeping only the boundary exclusion.

### IN-06 [INFO]: `missing_equity_sids` is now a producer-less list that is kept for shape.

**File:** `analytics-service/routers/portfolio.py:782-788`

**Issue:** This is intentional and documented. It still leaves `partial_data` / narrative wiring that can never fire from this cause. Consider removing it in a later shape-change phase.

### IN-07 [INFO]: `curveMethodFromFlags` warns on every call.

**File:** `src/lib/factsheet/resolve-series.ts:25-27`

**Issue:** Per-row loops (`queries.ts` dashboards, the scenario-share legs) will log once per row per render for a bad stamp. Python has the same per-call behaviour. Consider deduping by strategy id if a malformed stamp ever appears.

### IN-08 [INFO]: Inside Python, numeric-string values are accepted on the list shape but rejected on the dict shapes.

**File:** `analytics-service/services/wealth_returns.py:133` against `:202-207`

**Issue:** `records_to_series` coerces `"0.01"` through `pd.to_numeric`, but `_normalize_daily_returns`' `_finite` rejects strings for the flat and nested dict shapes. This is harmless today, since `daily_returns` is NULL on all 44 PROD rows and has no writer. Pick one rule.

### R2-01 [HIGH, confidence 8]: The optimizer and bridge rank candidates on different clocks inside one list, so for a book with no crypto leg a crypto candidate gets a ~20% Sharpe bonus from its label alone.

**Files:**
- `analytics-service/services/portfolio_optimizer.py:87-88, :129, :161`
- `analytics-service/services/bridge_scoring.py:140-141, :153, :197`

**Issue:** `blend_ppy = blend_clock(asset_classes, [*port_cols, cid])` is chosen per candidate. Both sides of each delta share it, so a single delta is internally consistent. The aligned window is the intersection (`.dropna()`), which for a weekday-sparse traditional book (user-CSV rows are never gap-filled, `analytics_runner.py:1363-1368`) is the book's weekday cadence for every candidate. ### R2-02 [MEDIUM, confidence 7]: A book's "current" Sharpe changes with the candidate it is compared against, and disagrees with the portfolio's own headline.

**Issue:** The brief asks whether a traditional book showing its "current" Sharpe on 365 because the candidate is crypto is acceptable. My answer is no, for two reasons.

1. **The rule's own terms.** The founder rule is "a BLEND uses 365 if any leg is crypto". The current book is not blended with the candidate, and it has no crypto leg. Option (a) also resolves R2-01, so I recommend it. Whichever is chosen, pin `current.sharpe` equal to the headline clock for the same book in `test_blend_annualization_clock.py`.
