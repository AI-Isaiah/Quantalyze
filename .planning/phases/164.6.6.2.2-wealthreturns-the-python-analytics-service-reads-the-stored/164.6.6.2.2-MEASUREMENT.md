Reading the table:

- The OLD column is absurd by construction: a level near 1.0 weighted as a daily return is a +100% day,

- Day counts differ by one (1254 vs 1253, overlap 857 vs 856): day 0 has no stored predecessor and is
  not recovered (D-01).
- Rankings change, not just magnitudes: the top optimizer candidate moves from C3 to C1, and the
  replacement scores for C1 and C3 reorder their fit labels.

```sql
WITH latest AS (
  SELECT DISTINCT ON (mb.allocator_id, mb.mode)
         mb.id AS batch_id, mb.allocator_id, mb.mode, mb.computed_at,
         mb.candidate_count, mb.excluded_count
    FROM match_batches mb
   ORDER BY mb.allocator_id, mb.mode, mb.computed_at DESC
), alloc AS (
  SELECT allocator_id, dense_rank() OVER (ORDER BY allocator_id) AS a_ord
    FROM (SELECT DISTINCT allocator_id FROM latest WHERE mode = 'personalized') x

SELECT 'A' || a.a_ord || '-K' || row_number() OVER (PARTITION BY l.allocator_id ORDER BY mc.strategy_id) AS pair_label,
```

### Finding that changes the post-deploy expectation (fail loud)

The plan and RESEARCH expected the personalized `portfolio_fit` values to change after deploy. On
today's PROD data they will not: every one of the 8 ranked personalized rows already reads
`portfolio_fit = 0`, and the three personalized allocators have portfolios with **no strategies**, so
there is no book for `_load_allocator_context` to read through the boundary. The stored zeros are
"no book", not "levels read as returns". The same reasoning applies to `portfolio_analytics` (no
portfolio can be recomputed) and to the holdings pseudo-strategy path (untouched by this phase).
Consequence: the post-deploy comparison below is expected to show **unchanged** personalized
`portfolio_fit` and unchanged screening rows. That is a pass for "no regression", not evidence that
the boundary fixed a stored match score. The before/after evidence of the fix on real rows is the
replay table above. The plan's backstop truth ("personalized `portfolio_fit` values differ from the
recorded pre-deploy values") cannot be met on current PROD data and should be restated or retired by
the verifier.

### Batch retention finding

`match_batches` rows are not pruned by age. `_retention_sweep` in `routers/match.py` keeps the
newest **7** batches per allocator (`keep=7`) and deletes the older ones; it runs after a
personalized recompute and in the cron sweep. The other deleters are the per-user sanitize routine
and the admin and service `DELETE` policies. Consequence for this measurement: the pre-deploy
batch of each allocator survives until seven newer batches exist for that allocator, so the
snapshot above is still readable in the database for several recomputes, and it is recorded here
regardless. Also measured: the latest personalized batches are dated 10:00, 13:00 and 14:00 UTC
while screening batches run to 19:00 UTC, so personalized recompute is not an every-hour write.
