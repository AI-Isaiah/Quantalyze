### CR-01 is correct for what ScenarioComposer renders

- **What the page renders.** `ScenarioComposer.tsx:5936` renders `${formatDay(start)} – ${formatDay(end)}`. A code-point check shows the separator is `0x20 0x2013 0x20`. `formatDay` (`utils.ts:162`) returns `Mon` + U+00A0 + `D,` + U+00A0 + `YYYY`, with `MONTH_ABBR` as three-letter `Sep` and so on (`utils.ts:131-134`). So each date carries two U+00A0, not one, and the spec comment's "a U+00A0" undercounts. That is harmless.
- **The spec's regex.** The literal around the dash at `composer-axe.spec.ts:274` is also `0x20 0x2013 0x20`.
- **How Playwright matches a RegExp.** In Playwright 1.64.1, `ExpectedTextMatcher.matches` (`playwright-core/lib/coreBundle.js`) normalizes the actual text only `if (!this._regex)`. So a RegExp is tested against the raw `textContent`, U+00A0 included, with no anchoring. JS `\s` matches U+00A0.
- **The pin passes and can fail.** A node check of the new regex:
  - It matches `Sep 9, 2024 – Oct 30, 2026` (built with U+00A0).
  - It rejects `All history`, the arrow form, the hyphen form, and the `— – —` null-date fallback.
  - The old regex rejects the new text.
- **No other stale pins.** No other e2e spec pins the arrow, or a date with ASCII spaces in a regex or exact string.
- **Not executed in a live lane** (as the fix report says). Its first real run is CI `e2e-seeded`. The reading above is from the matcher source, not a run.

### IN-01: The booked "axis moves at the front" case, plus two behaviours of the derived fallback

**File:** `src/app/factsheet/[id]/v2/factsheet-context.tsx:224`
**Issue:** The founder decision is still open. The range is held as indices, not dates. The derived fallback (rather than clearing state) adds two visible behaviours in the composer, where the axis changes without a reset:
- **Front trim.** "Include, which shortens the window" trims the start.
  - An end-anchored period pick such as 12M `[447, 699]` on 700 points now falls back to full history, because 699 is greater than 599.
  - A mid-history zoom that still fits keeps its indices, so it now names different dates. This is the same index-versus-date class as front growth.
- **Resurrection.** The masked `userRange` stays in state. If the axis later grows back past its end, the old selection reappears without a user action. It cannot reproduce the one-day symptom, because `setXRange` already guaranteed a width of at least `MIN_VISIBLE_SAMPLES`. On a different axis, though, it can name different dates.

**Fix:** None now. Fold these into the founder decision. Anchoring the user range to dates (start and end ISO) instead of indices would settle front growth, front trim and resurrection together.

### IN-02: The three-term axis bound is written twice, and the inner copy shadows the outer one

**File:** `src/app/factsheet/[id]/v2/factsheet-context.tsx:218-223` and `:245-256`
**Issue:**
- The render-scope `maxIdx` (new) and the `maxIdx` inside `setXRange` must stay identical. If a fourth basis term is ever added to `setXRange` only, a valid user range in the new tail is silently dropped back to full history.
- The inner `const maxIdx` also shadows the outer one.

**Fix:** Compute `maxIdx` once (a plain const or `useMemo`) and have `setXRange` read it, with `maxIdx` in its deps in place of the three payload terms.
