### 2. Trigger feasibility against THIS codebase's landmines

#### 2a. The trigger-on-SECDEF-helper REVOKE production-breaker — FOUND, and it does NOT apply

`[VERIFIED: migration source read]` The incident is
`supabase/migrations/20260516170000_match_decisions_visibility_check_secdef_fix.sql:3-11`,
quoted verbatim:

> `_match_decisions_visibility_check` trigger fires as the caller's role and
> `PERFORM`s `_assert_strategy_visible_to_allocator` which mig 20260516160700
> REVOKEd from service_role. Every direct service_role INSERT into
> match_decisions … would fail with `42501 permission denied for function
> _assert_strategy_visible_to_allocator`. **PRODUCTION-BREAKING.**

The remediation is at `:114` — `GRANT EXECUTE … TO service_role, authenticated`.
A retro-audit oracle was later added to keep it granted
(`20260517013000_revoke_probe_oracle_assert_strategy_visible_to_allocator.sql:118-126`).

**Root cause, precisely:** the *trigger function itself* is invoked by the
trigger machinery, which does **not** re-check EXECUTE at fire time (the ACL is
checked once, at `CREATE TRIGGER`). What IS re-checked at fire time is any
**function the trigger body calls**. `[CITED: PostgreSQL docs — CREATE TRIGGER,
"the user must … have EXECUTE privilege on the trigger function"]`

**Therefore the mitigation is structural, not a GRANT ritual: keep the stamp
trigger's body 100% self-contained.** The body proposed in §Architecture
Patterns reads only `NEW`, `OLD`, `TG_OP` and calls exactly one function —
`now()` — which is `pg_catalog` and PUBLIC-executable. **No helper. No
`PERFORM`. No SECDEF dependency.** With that constraint the 20260516170000
class is structurally unreachable, and this must be stated as an explicit
invariant in the migration header + pinned by a self-verify `DO` block that
greps the function body for a `PERFORM`/helper call.

**The template to copy is already in-repo:**
`supabase/migrations/20260716131000_guard_strategies_publish_transition.sql` —
a `BEFORE INSERT OR UPDATE … FOR EACH ROW` trigger on a money-adjacent table
(`strategies`), SECURITY INVOKER, `SET search_path = public, pg_catalog`
(`:44`), `REVOKE ALL … FROM PUBLIC, anon, authenticated` (`:74`),
`DROP TRIGGER IF EXISTS` before `CREATE TRIGGER` (`:76-80`),
`SET LOCAL lock_timeout = '3s'` (`:35`), `COMMENT ON TRIGGER` (`:82`), and a
self-verifying `DO` block that fails the migration at apply time if the guard
did not land (`:86+`). **Do not invent a new shape.**

#### 2c. `BYPASSRLS` / service-role writes — triggers still fire, and RLS makes the blast radius tiny

`[VERIFIED: supabase/migrations/20260405061912_rls_policies.sql:6,36-44]`

```
ALTER TABLE strategy_analytics ENABLE ROW LEVEL SECURITY;
CREATE POLICY analytics_insert_deny ON strategy_analytics FOR INSERT WITH CHECK (false);
CREATE POLICY analytics_update_deny ON strategy_analytics FOR UPDATE USING (false);
```

Consequences, all load-bearing for D-17:

1. **`authenticated` and `anon` cannot write this table AT ALL.** So the
   `current_user = 'authenticated'` idiom that
   `guard_strategies_publish_transition` uses to scope its RAISE is **not
   applicable here**. The stamp trigger must apply to every writer,
   unconditionally.
2. **The complete write surface is exactly three roles/paths:** (i) `service_role`
   via PostgREST — the Python worker and the Next.js admin clients
   (`createAdminClient`); (ii) the SECDEF bridge `sync_strategy_analytics_status`
   (`REVOKE ALL … FROM PUBLIC, anon, authenticated`,
   `20260412094454_sync_strategy_analytics_status.sql:168`), running as the
   function owner; (iii) the pg_cron reaper body, running as the cron job owner.
3. **`BYPASSRLS` does not bypass triggers.** BYPASSRLS suppresses row-security
   *policies* only; row-level triggers fire on every INSERT/UPDATE regardless of
   the writer's role. `[CITED: PostgreSQL docs — "Row Security Policies" /
   `BYPASSRLS`]` So the trigger genuinely covers all three paths — which is
   exactly what makes it strictly stronger than any per-writer fix.

#### 2d. Can the trigger fail LOUD? — **No, and this is the honest cost**

Analysed against the three bridge writes:

| Bridge branch | Write | What a RAISE-on-violation trigger would do |
|---|---|---|
| (a) non-terminal → computing (`mig:312-341`) | `INSERT … ON CONFLICT DO UPDATE` whose Arm 3 already keeps the stamp | Passes. |
| (b) failed_final → `failed`, stamp NULL | terminal exit | Passes. |
| (c) all-done → `complete`/`complete_with_warnings`, stamp NULL | terminal exit | Passes. |
| `_mark_computing` (`analytics_runner.py:1228-1241`) | unconditional `now()` on an already-computing row | **RAISES → 500 → `classify_exception` → job retries → retries also raise → 3 attempts burn → `failed_retry` → the strategy is stranded with NO factsheet.** Strictly worse than the ~10 h clock inflation it was fixing. |

So a raising trigger is only safe **after** the Python writer is corrected — at
which point the trigger is a belt to the Python braces, not a replacement for
them. A **coercing** trigger (silently `NEW.computing_started_at :=
OLD.computing_started_at`) is safe on day one against every existing writer.

**State this plainly to the founder, because it is a real trade:** a coercing
trigger replaces an *invisible clock bug* with an *invisible payload-ignored
behaviour* — `_mark_computing` will still read as if it advances the stamp
while the DB silently discards the value. That is a comprehension hazard, not a
correctness one, and it is mitigated by three things the plan must include:

1. Correct the false comment at `analytics_runner.py:1236-1237` (mandatory, and
   independently required by D-01's `missing:` clause).
2. Pin the trigger body in a SQL gate that reddens if the coercion arm is deleted.
3. `COMMENT ON TRIGGER` naming the coercion explicitly, so `\d strategy_analytics`
   discloses it.

**Recommended posture:** coerce, do not raise. Revisit RAISE only if a later
phase wants a hard contract; it would then be a one-line change with all writers
already compliant.

#### 2e. `INSERT … ON CONFLICT DO UPDATE` trigger firing order — the gotcha, and why it is benign here

`[CITED: PostgreSQL docs — INSERT, "ON CONFLICT DO UPDATE"]` On an upsert that
conflicts, **`BEFORE INSERT` row triggers fire first** (against the proposed
row), the insert is then abandoned, and **`BEFORE UPDATE` row triggers fire**
for the `DO UPDATE`, with `OLD` bound to the existing row. Both the bridge
(`mig:312`) and every Python writer use `.upsert(..., on_conflict="strategy_id")`,
so both paths execute.

This is benign **only because the proposed trigger body has zero side effects** —
it mutates `NEW` and returns. The abandoned `BEFORE INSERT` `NEW` is discarded.
A trigger that logged, wrote an audit row, or `PERFORM`ed anything would
double-fire. **Constraint for the planner: the trigger body must remain
side-effect-free.** Pin it.

### 5. Recommendation, cost, and the losing argument stated fairly

#### Recommendation: **Option A (trigger), with three named preconditions**

1. **D-12 first** (already locked as the phase's first commit) — the branch is
   red on the snapshot gate *right now*, and Option A adds a second function
   that the same gate tracks. Fixing D-12 first proves the ritual works before
   it is relied on again.
2. **Correct `analytics_runner.py:1236-1237`'s false comment in the same wave as
   the trigger.** Non-negotiable. The trigger makes the comment *more*
   misleading, not less — it will describe a write the DB silently discards.
   D-01's `missing:` clause requires this independently.
3. **Plan D-11's companion cron arm SEPARATELY.** It is not subsumed.

#### The strongest argument for Option B, stated fairly

*"Pass B — a deep, independent reviewer that traced every state transition
across four runtimes and filed zero blockers — proposed the two-statement split
and did not propose a trigger. The trigger is DDL on a money table, in a phase
whose entire premise is that the previous phase over-reached. `_mark_computing`
is provably the only Python writer and provably reachable from exactly one
handler; a five-line change to it closes the confirmed defect with a blast
radius of one function. The trigger's coercion is silent, which is the failure
class this repo has been burned by repeatedly. Every additional trigger is
another object to re-base, snapshot, and reason about at 3am. Ship the small
fix; book the trigger as tech debt."*

**That argument is genuinely strong and it loses on exactly two facts, both
verified above:**

- **The two-statement split creates a real `(computing, NULL)` window** — the
  precise state this phase has already classified as its worst residual failure
  mode (D-11). Trading a bounded, conservative ~10 h clock inflation for an
  unbounded permanent spinner, however narrow the window, is the wrong
  direction on the founder's own stopping rule (user-facing / data-integrity).
- **The invariant is a property of the TABLE, not of a writer.** RLS
  (`20260405061912:43-44`) already establishes that `strategy_analytics` writes
  come from three privileged paths, only one of which is `_mark_computing`.
  D-04 exists *because* a fourth path is one refactor away and no static gate

## D-11 — companion cron arm

### The blind spot, re-verified

`[VERIFIED: migration source read]` `mig:509-511`:

```sql
WHERE s.computation_status = 'computing'
  AND s.computing_started_at IS NOT NULL
  AND s.computing_started_at < now() - interval '16 hours'
```

Pass C executed the real body against Postgres 16 with a NULL-stamp `computing`
row present: **"neither reaped nor mutated, and produced no signal"**
(`142-VERIFICATION.md:36,171`). The migration's claim at `:103-107` that the
static CI gate is the detection mechanism is a category error.

### Design decisions the planner must make — with evidence

#### (a) Same `$cron$` body, or a second `cron.schedule` entry?

**Recommendation: a SECOND statement in the SAME `$cron$` body, placed BEFORE
the existing reap statement.**

- pg_cron accepts a multi-statement command string; the whole body runs in one transaction per tick. `[ASSUMED — standard pg_cron behaviour; not exercised in this repo today]`
- Same-body keeps **one** `cron.job` row, so the existing drift gate
  (`TestReaperThresholdDriftGate`, which does `SELECT command INTO v_command FROM cron.job` — `supabase/tests/…:346,449,471`) keeps seeing the whole mechanism in one string. A second `cron.schedule` entry would be **invisible to that gate**, re-creating a coverage hole in the very phase that exists to close coverage holes.
- Placing the clock-start **before** the reap means a row stamped this tick is
  not reaped in the same tick — it gets a full threshold. Correct and
  non-destructive.
- ⚠️ **The SQL gate's `EXECUTE v_command` oracle then runs BOTH statements.** The
  three existing `EXECUTE v_command` call sites and their assertions must be
  re-checked: **arm D** at `supabase/tests/…:333-336` currently asserts a
  NULL-stamp row is left *unmutated*. **That assertion inverts under the
  companion arm** — the row will now be stamped. The plan MUST update arm D, or
  the gate goes red for the right change. This is a concrete, easy-to-miss task.

#### (b) `now()`, or a conservative floor from `compute_jobs.created_at`?

**Recommendation: `now()`.** Reasoning, stated honestly:

- *Against `now()`*: it grants a fresh 16 h to a row that may already have been
  stale for hours. Worst case the user waits 16 h + up to 15 min *from
  detection* rather than from stranding. **The concern is real and CONTEXT.md is
  right to raise it.**
- *For `now()`*: the alternative anchor is `compute_jobs.created_at` — but the
  arm's own predicate requires `NOT EXISTS (active compute_jobs)`, and the
  orphaned-running purge (`20260720120000`, 4 h window) **DELETEs** the job rows.
  So on the exact rows this arm targets, **`compute_jobs` frequently has no row
  at all to anchor to.** Any fallback would be `computed_at`, which the migration
  header (`:79-88`) proves is wrong in *both* directions — the same argument that
  justified adding `computing_started_at` in the first place.
- A "conservative floor" that silently degrades to a wrong anchor is worse than
  an honest, slightly-late `now()`. The clock-start is **detection latency**, and
  the migration already has a heading ("CADENCE HONESTY", `:32-36`) whose whole
  point is to state such latencies rather than hide them. **Extend that block
  with the companion arm's own bound.**
- **Also fix the CADENCE HONESTY block's `~16h15m` claim** while editing it —
  D-01's `missing:` clause offers this as the *alternative* to fixing the writer.
  Under Option A the writer IS fixed, so `~16h15m` becomes true again for the
  main arm. **Say so explicitly in the migration comment**, and add the
  companion arm's separate worst case (`stranding → detection ≤15 min → +16 h →
  ≤15 min`, i.e. up to ~32.5 h for a NULL-stamp row) rather than leaving one
  number to cover two mechanisms.

#### (c) The arm body

Pass B's proposal (`142-REVIEW.md:223-231`) is correct as written. Reuse the
**byte-identical** non-terminal status list from the reap arm (`mig:519-521`) —
`('pending','running','done_pending_children','failed_retry')` — since Pass C
verified the byte-identity property is what makes the `NOT EXISTS` conjunct
trustworthy (`142-VERIFICATION.md:144`). Add a `LIMIT` + `FOR UPDATE SKIP
LOCKED` mirroring the reap arm's bound (`mig:522-524`) so the companion arm
cannot hold locks unboundedly either.

### Pattern 1 — the stamp trigger (Option A)

**What:** relocate the "stamp only on transition in, never advance, always clear
on exit" invariant from three uncoordinated writers into one table-level trigger.

**When to use:** an invariant over a column whose write surface is >1 privileged
path and where the payload is a literal that cannot express a condition.

**Body — copy the SHAPE from `20260716131000`, not the predicate:**

```sql
-- SECURITY INVOKER (default). SELF-CONTAINED BY CONSTRUCTION: reads only
-- NEW/OLD/TG_OP and calls only now() (pg_catalog, PUBLIC-executable). It must
-- NEVER PERFORM a helper — see 20260516170000, where a trigger PERFORMing a
-- SECDEF helper that had been REVOKEd from service_role was PRODUCTION-BREAKING.
-- INSERT/UPDATE only: extending to DELETE would import the
-- quantalyze.sanitize_in_progress exemption obligation (20260710160000:67).
CREATE OR REPLACE FUNCTION public.strategy_analytics_stamp_computing_started()
RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = public, pg_catalog
AS $$
BEGIN
  IF NEW.computation_status = 'computing' THEN
    IF TG_OP = 'UPDATE'
       AND OLD.computation_status = 'computing'
       AND OLD.computing_started_at IS NOT NULL THEN
      -- Arm 3 equivalent: already computing — NEVER advance. Coerce silently;
      -- a RAISE here would kill the live _mark_computing writer (see D-17 §2d).
      NEW.computing_started_at := OLD.computing_started_at;
    ELSIF NEW.computing_started_at IS NULL THEN
      -- Genuine transition in (fresh INSERT, or from any non-computing status,
      -- or the deliberate one-shot backfill leaving it NULL). Close the
      -- NULL-stamp hole at the source.
      NEW.computing_started_at := now();
    END IF;
    -- else: caller supplied an explicit non-NULL stamp on a transition in
    -- (the STEP 2 backfill anchor). Respect it.
  ELSE
    -- Every exit from 'computing' clears the reaper key, unconditionally.
    NEW.computing_started_at := NULL;
  END IF;
  RETURN NEW;
END;
$$;

REVOKE ALL ON FUNCTION public.strategy_analytics_stamp_computing_started()
  FROM PUBLIC, anon, authenticated;

DROP TRIGGER IF EXISTS strategy_analytics_stamp_computing_started_trigger
  ON public.strategy_analytics;
CREATE TRIGGER strategy_analytics_stamp_computing_started_trigger
  BEFORE INSERT OR UPDATE ON public.strategy_analytics
  FOR EACH ROW
  EXECUTE FUNCTION public.strategy_analytics_stamp_computing_started();
```

⚠️ **The exact predicate above is a design sketch derived from the bridge's
three arms (`mig:328-341`); it has NOT been executed.** The planner must have it
proven by the G1 gate, not accepted on this document's word — that is precisely
the failure mode this phase exists to close.

## Common Pitfalls

### P1 — the frozen transaction clock
**What goes wrong:** an "advance" assertion silently cannot fail.
**Why:** `now()` is transaction-constant.
**Avoid:** pre-set a fixed sentinel (`supabase/tests/…:547-556`).
**Warning sign:** identical microseconds in the observed values.

### P2 — trigger PERFORMs a SECDEF helper
**What goes wrong:** 42501 on every service_role write. PRODUCTION-BREAKING.
**Why:** the ACL on a function *called by* the trigger body is checked at fire time.
**Avoid:** self-contained body; pin it with a self-verify `DO` block.
**Warning sign:** any `PERFORM` / helper call in the trigger body.

### P3 — `ON CONFLICT DO UPDATE` fires BOTH BEFORE INSERT and BEFORE UPDATE
**What goes wrong:** any side effect in the trigger body double-fires.
**Avoid:** side-effect-free body (mutate `NEW`, return).

### P4 — `EXECUTE v_command` in the SQL gate now runs the companion arm too
**What goes wrong:** the existing **arm D** assertion (`supabase/tests/…:333-336`,
"NULL-stamp row left unmutated") **inverts** and the gate reddens on a correct change.
**Avoid:** update arm D in the SAME commit as the companion arm.

### P5 — running pytest from the repo root
**What goes wrong:** VCR `cassette_library_dir` misses ⇒ **LIVE broker calls** and two bogus failures.
**Avoid:** `cd analytics-service && pytest …`, always. `[CITED: CLAUDE.md / project memory]`

### P6 — shipping `analytics-service` without `mypy --strict`
**What goes wrong:** the GSD milestone path runs pytest only; type errors stay latent until PR CI.
**Avoid:** `cd analytics-service && mypy --strict --follow-imports=silent services/ routers/ models/` before ship. Fix via `cast()`, never `# type: ignore`.

### P7 — "no SKIPPED rows remain" ≠ "all rows observed"
**What goes wrong:** the exact conflation that produced the WRONG "11 Observed / 0 SKIPPED" report (`STATE.md:223-227`).
**Avoid:** count `✅ Observed` explicitly; `⬜ pending` is not `SKIPPED`.

### P8 — trusting a ledger's Mutation coordinates
**What goes wrong:** SC-5b and SC-5c in `142-VALIDATION.md` name lines that do not exist any more.
**Avoid:** grep every file:line in a ledger row before transcribing it.
