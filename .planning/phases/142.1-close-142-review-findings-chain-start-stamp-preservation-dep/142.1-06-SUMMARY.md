# Phase 142.1 Plan 06: D-01's comment + the D-02/R2 PGRST204 fallback — Summary

Two closures on the same money path. **D-01** is prose: `_mark_computing`'s comment
asserted that every invocation of that writer is a real transition into `computing`,
which was false before plan 142.1-05 and is *more* misleading after it — the trigger
now silently overrides the value on the dominant path. **D-02/R2** is the amplifier:
`_mark_unrecoverable` is the catch-all exit writer, and during a deploy window its
payload names a column PostgREST's schema cache does not know yet. PostgREST rejects
it and writes nothing, so an already-failed job cannot even stamp `failed` — the row
stays `computing` forever and the owner-side UI spins. The fallback drops the unknown
key and re-issues; a degraded stamp beats a permanent spinner.

## What Was Built

### Task 1 — D-01: the comment says what the database does

The false clause is gone. The replacement splits the behaviour by how the job was
reached, because the value's *effect* differs by path even though the write is
unconditional:

| Path | What happens to the payload value |
|---|---|
| 4-hop chain (`process_key_long` → `sync_trades` → `derive_broker_dailies` → `compute_analytics_from_csv`) | the row has been `computing` since hop 1, so the upsert takes its `ON CONFLICT` path — an UPDATE — and `strategy_analytics_stamp_computing_started_trigger` (migration `20260803120000`) silently coerces it back to the hop-1 chain-start stamp |
| CSV-first (`csv-finalize/route.ts:822-826` enqueues `compute_analytics_from_csv` as the strategy's FIRST job) | this stamp IS the real transition in and lands as written — the UPDATE-only trigger (D-18) does not fire on the INSERT path at all, and on a real transition-in UPDATE its arm (c) respects an explicit stamp |

The comment names the trigger by object name and the migration by prefix, so
`\d strategy_analytics` and the source agree. It closes with an instruction not to
make the write conditional on the strength of the first row alone — on the second
path there is no other writer. The client-side-UTC-ISO half of the old comment is
kept verbatim (a PostgREST payload is a literal and cannot express SQL `now()`).

The payload dict is **byte-identical**: filtering `git diff` to non-comment changed
lines returned nothing.

### Task 2 — D-02/R2: the fallback, its tests, and the census exemption

**The arm** (`analytics_runner.py`). The existing terminal upsert is wrapped in
`try` / `except APIError`. Anything whose `.code` is not `PGRST204` **re-raises
unchanged** — swallowing every `APIError` would hide a serialization failure or a
permission denial behind a silently degraded payload. On `PGRST204` it logs a warning
naming the deploy-window cause and re-issues a **second explicit dict literal**: the
same keys minus `computing_started_at`, same `on_conflict="strategy_id"`, same
read-modify-written `prior_flags`. The literal shape is C-12: even with D-07 softened,
a literal keeps the census resolvable and the counts stable.

The code is matched by `.code`, not by a message substring — `services/audit.py:279-299`
already establishes why (server messages localize; the code does not). The literal
lives in one module-level constant beside the logger, mirroring audit.py's
`_SQLSTATE_PERMISSION_DENIED`.

**The tests** (`tests/test_pgrst204_recovery_fallback.py`, 291 lines, written first).
Side effects route by the dispatched callable's `__name__` (PATTERNS S-8), and
`db_execute` is **not** patched away for `_mark_unrecoverable` — the real callable
runs against the supabase mock, because the behaviour under test is that it issues a
second upsert.

The injection is schema-faithful rather than positional: the mock rejects any write
issued from inside `_mark_unrecoverable` whose payload **names the unknown column**,
which is what PostgREST does. A fallback that kept the key would be rejected
identically instead of sliding past a "first call only" counter. It is scoped to that
one writer because R2 is deliberately bounded — `_mark_computing`'s own exposure to
the same window is the "never started" case, not the "cannot stamp failed" case, and
is out of this plan's scope.

1. **Fallback works** — two terminal writes; the first carries the stamp key, the
   second does not; `computation_warned` is `False` on the fallback too (SI-02);
   `strategy_id`, `computation_error` and the read-modify-written flags all carry
   forward; `on_conflict` is unchanged (a lost conflict target would INSERT a
   duplicate instead of updating the row).
2. **Narrowness** — a `40001` `APIError` is observed leaving `_mark_unrecoverable`
   as the *same object*, exactly one terminal write is attempted, and the caller's
   PR #273 warning still fires.
3. **Negative control** — no injection ⇒ exactly one terminal write, still clearing
   the stamp to `None`, nothing raised.

⚠️ Tests 2 and 3 are green on **both** sides of the fix, by construction — they pin
what the fallback must not disturb. Test 1 is the RED. That is stated in the module
docstring so a reader does not mistake their green for coverage of the new arm.

**The census exemption** (`test_computing_started_at_stamp.py`). The fallback is a
terminal payload with no stamp key, which the exit-clear rule flags. It is carved out
by **shape** — the exact 5-key set `{strategy_id, computation_status,
computation_warned, computation_error, data_quality_flags}` with a `"failed"` literal,
in `analytics_runner.py` — and pinned at `EXPECTED_STAMP_OMISSION_EXEMPT = 1`.

Shape rather than file+function is the load-bearing choice. `_mark_unrecoverable`
holds **two** payloads; a function-name match would have exempted the compliant one
as well. With a key-set match, stripping the stamp from the compliant sibling collapses
its signature onto the carve-out, the count goes to 2, and the gate reddens. Both
directions were observed live (below).

Counts re-derived from a live scan, not assumed: `kept 13` (was 12), `runner 7`
(was 6), `worker 6`, `n1 2`, `n2 1`, `skipped 0`.

## Deviations from Plan

### 1. [Reported, not forced] `EXPECTED_SKIPPED_UNRESOLVED` stays 0 — the inherited obligation's premise did not hold

- **The obligation:** plan 142.1-04's hand-off says the counter "WILL move
  `EXPECTED_SKIPPED_UNRESOLVED` from 0 to 1, and that counter must be bumped in the
  same commit, with the site named."
- **Why it did not:** that forecast is explicitly conditional on the fallback being
  built with `dict(...)` / `{**base, …}` — a shape the AST census cannot resolve. This
  plan's own C-12 constraint forbids exactly that and requires a second explicit dict
  literal, and a literal **is** resolvable. So the fallback is COUNTED among the kept
  sites rather than skipped. The two instructions are not in conflict; the hand-off
  described the branch this plan did not take.
- **Evidence** — live scan of the shipped tree, not an assumption:
  ```
  kept 13 / runner 7 / worker 6 / n1 2 / n2 1
  SKIPPED 0 []
  ```
  The same scan on the pre-task tree read `kept 12 / runner 6 / skip 0`.
- **Action:** did **not** force the literal to 1 — that would have made the counter
  assert a skip that does not exist, i.e. a permanently red gate or a lie. Instead the
  census docstring now records the forecast, why it did not land, and that the number
  was re-measured rather than assumed, so the next reader does not conclude the D-07
  coupling is dead. The counters that DID move (`13`, `7`) were bumped in the same
  commit as the change that caused them (`9c34d316`), which is the substance of the
  obligation.

### 2. [Judgment] The exemption is matched by payload SHAPE, not by file + function

The plan's action text says "add a pinned, counted exemption (e.g. a
`PGRST204_FALLBACK_EXEMPT` literal count == 1 …)" without fixing the matching rule.
The obvious implementation — exempt `_mark_unrecoverable` in `analytics_runner.py` —
is wrong here, and quietly so: that function holds **two** terminal payloads, and a
function-scoped carve-out covers both. Deleting `computing_started_at` from the
compliant one would then pass a green gate.

Matching the exact 5-key signature instead gives anti-vacuity in both directions, and
both were driven live rather than argued (see Falsifiability). The `2 == 1` RED above
is the probe the function-scoped version fails.

### 3. [Judgment] The error injection is schema-faithful, not positional

The plan's behaviour spec says the mock raises "on the FIRST call only". Implemented as
"raise for any write from inside `_mark_unrecoverable` whose payload names the unknown
column" — a strict superset. Under first-call-only, a broken fallback that re-sent the
identical payload would **succeed** on call two and be caught only by the key-absence
assertion; under the schema-faithful rule it is rejected the way PostgREST would reject
it. Both assertions are present; the harness just cannot pass for the wrong reason.
The reasoning, and the deliberate scoping to `_mark_unrecoverable` only, is written into
the module docstring.

in the same deploy window a job can fail to *enter* `computing` at all. That is a
different failure (a job that never starts, visible as a job-level error) rather than a
permanent spinner, and it was explicitly out of this plan's scope — but it is not
closed, and the fallback's own test docstring says so rather than implying the window
is fully handled.
