# Phase 142.1 Plan 03: Close D-05 (isolation by construction) + D-02/R1 — Summary

Deleted the three cross-tenant neutralizing `UPDATE`s from the reaper SQL gate and
replaced isolation-by-mutation with isolation-by-construction (century-old seeds +
identity-scoped assertions), added a one-rule grep gate that keeps the pattern from
growing back, serialized `sql-tests` into the existing `shared-test-db` group, and
made `supabase-migrate` fail loud instead of reporting green having applied nothing.

## What Was Built

### Task 1 — D-05 / D-18 Part 3: the neutralizers are GONE, not narrowed

Three statements of this shape were **deleted** (Part 2 pre-oracle, Part 3
pre-tick-1, Part 3 pre-tick-2):

```sql
UPDATE public.strategy_analytics
   SET computing_started_at = NULL
 WHERE computation_status = 'computing'
   AND strategy_id <> ALL (v_seeded);
```

They wrote across **every other tenant's rows** on the shared TEST project. Iteration
1's proposal to re-target them at `now()` is WITHDRAWN per D-18: under plan 142.1-05's
UPDATE-only trigger, arm (a) reverts `NEW := OLD` on an already-`computing` row, so the
stale-stamp half would be a silent no-op while the grep gate reported green — the exact
silent-narrowing class this phase exists to kill.

**Isolation is now by construction.** Part 2 arm A and Part 3's 26 staggered loop seeds
moved from `interval '100 days'` to `interval '100 years'`. The deployed reap arm is
`ORDER BY computing_started_at ASC … LIMIT 25`, so a century-old seed outranks any
plausible foreign row for the budget — the seeds win by sorting, not by mutating.

**Part 3 arm E is reseated IDENTITY-scoped.** The old proof was a global shape
("exactly 25 of 26 seeded rows are failed, exactly 1 is computing"). It is now:

- `v_youngest := v_seeded[1]` (the `i=1`, least-old seed)
- tick 1 → `count(… = ANY (v_seeded) AND <> v_youngest AND status='failed') = 25`
  **and** `v_youngest` is still `'computing'`
- tick 2 → `v_youngest` is `'failed'` **and** the seeded failed count is 26

Naming *which* rows must move is strictly stronger than counting *how many* did: the
youngest-seed assertion is what reddens if the `LIMIT` disappears, and it needs no
reference to any row this block does not own.

**Header rewritten.** The section formerly titled "why the neutralization UPDATE exists"
is now "isolation by construction", quotes the deleted statement so a future reader knows
what was removed and why, and states the residual assumption honestly. The `lock_timeout`
rationale no longer describes a statement that does not exist: the 5 s bound now covers
the **EXECUTEd deployed body's own** `FOR UPDATE SKIP LOCKED` reap, which can briefly
lock up to 25 foreign candidate rows inside the rolled-back transaction.

**New `analytics-service/tests/test_sql_gate_scoped_updates.py`** — pure stdlib, one rule,
no special cases. Every statement matching `UPDATE\s+(?:public\.)?strategy_analytics`
(the optional-schema alternation is mandatory — `test_metrics_by_basis_write.sql:68,71,74,83`
prove the unqualified form is live and correctly scoped today) must carry
`strategy_id = <plpgsql identifier>` or `strategy_id = ANY (<identifier>)`. There is
**no accepted `<> ALL (…)` form and no staleness-conjunct branch** — the shape no longer
exists in the tree, so the gate has nothing to special-case. Comments are stripped first
(S-1), with a dedicated test proving it, because the reaper's own header quotes the
deleted pattern verbatim.

### Task 2 — D-05: `sql-tests` joins `shared-test-db`

`ci.yml`'s `sql-tests` job gained the **existing** group verbatim
(`group: shared-test-db`, `cancel-in-progress: false`) — the same one `python`
(`:1096`) and `e2e-seeded` (`:1462`) already carry. A job-private name would serialize
this job only against itself and leave the cross-job races against the same physical
project wide open.

**A5 confirmed as a non-issue:** `sql-tests` has **no `needs:`** at all, so the
group cannot deadlock against a job it waits on. (`e2e-seeded` carries both the group
and `needs: frontend-typecheck`, which is the harder case and already ships.)

### Task 3 — D-02/R1: `supabase-migrate` fails loud

The `Check secrets are configured` step no longer takes a silent
`configured=false` + `::notice::` branch on a push. It now emits one `::error::` per
missing name plus a summary line and `exit 1`, gated on `github.event_name == 'push'`
(bound through `env: IS_PUSH`, never interpolated into the shell). The tolerant path
survives **only** below that gate, for `workflow_dispatch`.

No column-capability probe was built — correction C-2 explicitly rejected that as
re-importing D-07's static-resolution problem.

### D-02/R1's live half — ⚠️ REVIEWER-OBSERVABLE ONLY

**The workflow actually reddening with secrets unset is NOT observable per-commit.** It
requires a push to `main` touching `supabase/migrations/**` on a repo with the secrets
removed. Per `142.1-VALIDATION.md`'s Manual-Only table, the standing observable is the
vitest YAML-shape assertion **plus reviewer inspection of the yml diff**.

To narrow that gap I extracted the step's shell body verbatim and drove all three arms
locally (this is evidence about the SCRIPT, not about GitHub's dispatch of it):

| Arm | `IS_PUSH` | secrets | result |
|-----|-----------|---------|--------|
| push, all three unset | `true` | none | 4 × `::error::`, **exit 1** |
| dispatch, one unset | `false` | 2 of 3 | `::notice::`, exit 0, `configured=false` |
| push, fully configured | `true` | all 3 | `configured=true`, exit 0 |

This also caught a real hazard in passing: `set -euo pipefail` combined with the
`[ -z "$X" ] && MISSING=…` idiom would have exited the step on the first *present*
secret. The shipped code uses explicit `if … fi` blocks instead.

- **Commit:** n/a (pre-execution)

**2. [Rule 1 - Bug in my own edit] My ci.yml comment broke the plan's own acceptance grep**
- **Found during:** Task 2 verification
- **Issue:** I named the forbidden group `shared-test-supabase-sql` inside the ⛔ warning
  comment. The acceptance criterion is
  `grep -c 'shared-test-supabase-sql' .github/workflows/ci.yml` → 0, and it returned **1**.
  A literal grep cannot tell a comment from a value.
- **Fix:** Reworded the warning to point at `142-REVIEW.md:286-291` without the literal
  token. The substance (a private group name is the wrong fix, and why) is unchanged, and
  the vitest pin enforces the positive property far more strongly than the grep did.
- **Files modified:** `.github/workflows/ci.yml`
- **Commit:** `cbe6324e`

**3. [Rule 1 - Bug in my own edit] Residual-assumption line was capitalized past its own criterion**
- **Found during:** final acceptance sweep
- **Issue:** I wrote the header line as "NO FOREIGN ROW … OLDER than the seed epoch". The
  criterion greps case-sensitively for `older than the seed epoch` → **0 hits**. The
  statement was present; the criterion could not see it.
- **Fix:** Lowercased that clause. Prose only — no seed, assertion or message changed.
- **Files modified:** `supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql`
- **Commit:** `178bde21`

**4. [Rule 2 - Missing critical] `set -euo pipefail` added to the migrate check step**
- **Found during:** Task 3
- **Issue:** The step's `run:` block had no shell strictness. Rewriting it into a
  multi-branch script with an `exit 1` path makes an unset variable or a silently-failing
  command materially more dangerous than it was in the two-line original.
- **Fix:** Added `set -euo pipefail`, and deliberately used explicit `if … fi` blocks
  rather than the shorter `[ -z "$X" ] && MISSING=…` idiom, which under `set -e` exits the
  step whenever the test is false. Proven on all three arms locally (table above).
- **Files modified:** `.github/workflows/supabase-migrate.yml`
- **Commit:** `b6054336`
