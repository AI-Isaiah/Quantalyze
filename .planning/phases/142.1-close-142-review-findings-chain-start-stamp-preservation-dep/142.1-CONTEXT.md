### ⚠️ Architecture decision that gates D-01 / D-04 / D-07 / D-11

- **D-17 — ⭐ SETTLED 2026-08-02 (orchestrator, on RESEARCH.md evidence):
  Option A — a `BEFORE INSERT OR UPDATE` trigger on `strategy_analytics`
  becomes the single enforcement point for the stamp invariant.**

  The invariant moves out of per-writer code. Payload shape and call-site
  language become irrelevant, which is what D-01, D-04 and D-07 are each a
  symptom of.

  **Why Option A won, on evidence:**
  - The feared landmine **does not apply**. The production-breaker is
    `20260516170000_match_decisions_visibility_check_secdef_fix.sql:3-11` — a
    trigger that `PERFORM`ed a SECDEF helper REVOKEd from `service_role`. The ACL
    is re-checked at fire time only for *functions the trigger body calls*, never
    for the trigger function itself. A **self-contained body** (`NEW` / `OLD` /
    `TG_OP` / `now()` only, zero helper calls) makes the class structurally
    unreachable. Copy the template at
    `20260716131000_guard_strategies_publish_transition.sql` verbatim.
  - `sanitize_user` never touches `strategy_analytics` (grep: zero hits), and the
    trigger is INSERT/UPDATE-only, so the `sanitize_in_progress` exemption is
    **not** needed.
  - RLS (`20260405061912:43-44`) denies all `authenticated`/`anon` writes;
    `BYPASSRLS` bypasses policies, never triggers. The service-role worker is
    covered.
  - **Option B has a real correctness hole, not just an ergonomic one.**
    `.is_("computing_started_at","null")` does work (verified against the
    installed postgrest; 11 existing call sites in-repo), but `db_execute` has no
    transaction wrapper — the two statements are two round-trips, leaving a real
    `(computing, NULL)` window. That is the exact state D-11 documents as
    invisible to every mechanism the phase ships. Option B would manufacture more
    of the rows D-11 exists to rescue.

  **Locked constraints on the implementation:**
  - **The trigger MUST coerce silently, not `RAISE`.** Raising would kill the
    live `_mark_computing` call → 3 retries → a stranded strategy. This is the
    honest cost of Option A: it trades an invisible clock bug for invisible
    payload-ignored behaviour. It is accepted **only because** the new SQL gate
    Part 6 (below) makes the coercion observable.
  - The trigger predicate sketched in RESEARCH.md § Architecture Patterns (A4) is
    a **sketch**. It must be proven by a new SQL gate Part 6, not accepted on the
    research document's word.
  - **Forward-only delta migration.** `20260802120000` is NOT on `origin/main`
    (PROD unaffected) but IS applied to TEST as version `20260802111053`. Do
    **not** amend it — add a new migration with a timestamp strictly later than

### Clear the founder stopping rule on their own (user-facing / data-integrity)

- **D-01** — `analytics_runner.py:1238`. `_mark_computing` re-stamps
  `computing_started_at` on a row that is ALREADY `computing`, so the reap clock
  restarts at the LAST chain hop instead of chain start. Worst-case stranded
  spinner **≈25.8 h (≈28 h with retries)** against the migration header's
  advertised `~16h15m` — under a heading titled "CADENCE HONESTY".
  `TestReaperThresholdInvariant`'s premise no longer matches the code. Note the
  shape: the migration's Arm 3 and the SQL gate's Part 4 sentinel correctly
  forbid a *bridge* call from advancing the stamp — verified live on TEST — but
  the Python writer sets the column DIRECTLY, outside that boundary. The
  cross-language census passed because it checks that writers stamp, not that
  they stamp ONLY on transition. Direction is conservative (later, never
  earlier), so it cannot mis-reap a healthy chain; the cost is user-visible
  spinner duration ≈1.75× the advertised bound. Either fix the writer **or**
  correct the migration's `~16h15m` claim and `TestReaperThresholdInvariant`'s
  docstring — and ship a gate that CAN fail on a Python re-advance (the current
  Python gate provably cannot).
