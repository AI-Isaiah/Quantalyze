## SFH-01 (HIGH, introduced by this phase): a chain-broken row's stored CAGR bypasses the card's 0.95-year gate

**Location:** `src/lib/factsheet/og-metrics.ts:98-105` (the gate and the `stored?.cagr` swap), and
`src/app/api/og/factsheet/[id]/route.tsx:73` (the embed projects no `data_quality_flags`).

**What is wrong.** The card's display rule is "CAGR only past 0.95 calendar years". The gate measures
the span of the EMBEDDED series (`resolveDailyReturnSeries` over `returns_series`). The stored `cagr`
covers a different window. `analytics-service/services/metrics.py:1854-1861` annualizes CAGR over
`_last_interior_break_suffix(returns)`, the stretch after the last chain break, with
`365 / _elapsed_days`. `returns_series` (`metrics.py:2047-2051`) is the full-span `fillna(0)` wealth
curve. On a `twr_chain_broken` row the gate therefore passes on the full record, while the value it
lets through is annualized over the suffix alone. That suffix can be days long.
`MIN_ANNUALIZATION_DAYS` (`metrics.py:64-75`) only sets the `insufficient_window` annotation and
leaves the value as computed. Its own comment gives the example of "a 3-day suffix ... annualizes a
+3% move to +3,960%".

**Failure scenario.** A broker strategy has 2 years of history and a chain break 10 days before its
last day, with +2% over those 10 days. The stored `cagr` is about 1.02^36.5 - 1, roughly +106%. The
card sees 2 calendar years with `cum > 0`, so the gate passes, and the card renders "+106.0%" in green.
The factsheet shows the same number, but beside `headlineCoverageCaveat`
(`src/app/factsheet/[id]/v2/MetricsColumn.tsx:41-53`), which says the figure covers only the record
after the break. The card carries no such text. Before this phase the card computed CAGR over the
full span, so its gate and its value described the same window. The response then sits in CDN cache
for `s-maxage=86400` plus 7 days of SWR, and in Slack, LinkedIn and X unfurl caches beyond that.
This is the case the card's own docblock warns about: "annualizing a sub-year track ships nonsense
on social cards".

**Hidden condition.** The gate passes silently. Nothing logs and nothing on the image marks the
figure as covering only a suffix.

**Fix.** Keep the stored value, and make the gate describe the same window the value does. Add
`data_quality_flags` to the embed. Pass `twr_chain_broken` and `insufficient_window` through
`OgPersistedScalars`. When the stored CAGR is the one shown and either flag is `true`, render CAGR as
NaN ("—"). The card has no room for the factsheet's caveat, so hiding the figure is its way of
applying the same honesty. A stricter version would run the 0.95-year gate over the suffix span, but
the card cannot rebuild that span. The flag is the value the writer stamped, so read the flag.

```ts
// og-metrics.ts, CAGR arm
if (years >= 0.95) {
  if (stored?.cagr !== undefined) {
    const suffixOnly = stored.twr_chain_broken === true || stored.insufficient_window === true;
    cagr = suffixOnly ? NaN : storedFigure(stored.cagr);
  } else {
    cagr = Math.pow(cum, 1 / years) - 1;
  }
}
```

Add a unit test where the series spans ≥1 calendar year, the flags set `twr_chain_broken: true`, and
`cagr: 1.06`. Assert CAGR comes back NaN. Neuter the flag check and watch the test go RED.

## SFH-02 (HIGH, pre-existing, in the touched function; separable): a failed strategy read renders a generic card and caches it for a day

**Location:** `src/app/api/og/factsheet/[id]/route.tsx:77-83` (`data = res.data ?? null`, with
`res.error` never read), `:153-155` (compute catch), `:205-208` (unconditional long cache header).

**What is wrong.** supabase-js/PostgREST never throws on a query error. It returns `{ data: null,
error }`. The `try/catch` at `:78-83` therefore never fires on a real read failure: a statement
timeout, pool exhaustion, a 5xx, or a column error from the select this phase widened. `res.error` is
dropped with no log. The route then renders `name = "Strategy"` with three em-dashes, and `:205`
stamps it `public, max-age=3600, s-maxage=86400, stale-while-revalidate=604800`. The compute catch at
`:153` has the same shape. It logs to console, but the dash card it produces still gets the 24h+7d
header. The STALE-01 comment at `:121-127` names exactly this hazard ("one render of a dead figure is
served from CDN for a day ... unfurl caches keep their own copy").

**Failure scenario.** A share goes out during a brief PostgREST incident. The first unfurl fetches
the card, the read fails, and nothing is logged. A card reading "Strategy — — —" under the
"verified" badge is cached at the edge for a day and copied into LinkedIn's unfurl cache, which does
not refetch. The published strategy's own share preview carries no name, and nobody has an error
to find.

**Why it is in this report.** Not introduced here. This phase added three columns to the failing
statement's projection, which widens the set of errors that land on this path (for example, a
column rename or drop in a later migration). It is the "cached card freezing a failure" case the
brief asked about.

**Fix.** Check `res.error` and send it to Sentry with the strategy id. On any failure path (read
error, or compute catch), send a short cache header (`no-store`, or `max-age=60, s-maxage=60`) so the
next unfurl retries rather than freezing the failure. The not-found case (`data === null`,
`error === null`: unpublished or missing) is legitimate and may keep the long TTL.

```ts
const res = await withPublishedOnly(/* ... */).maybeSingle();
if (res.error) {
  readFailed = true;
  console.error("[og:factsheet] strategy read failed", id, res.error);
  captureToSentry(res.error, { tags: { stage: "og-factsheet-read", strategy_id: id } });
}
data = res.data ?? null;
// ...
response.headers.set(
  "Cache-Control",
  readFailed || computeFailed
    ? "public, max-age=60, s-maxage=60"
    : "public, max-age=3600, s-maxage=86400, stale-while-revalidate=604800",
);
```

Under the review-findings policy this is pre-existing and separable, so book it rather than fold it
into this phase if the orchestrator prefers. It is user-facing, so it qualifies for a phase.

## Checked and cleared (no finding at MEDIUM+)

- **Stored NULL/NaN coerced to 0.** No. `storedFigure` maps anything that is not a finite number to
  NaN, and `fmtNum`/`fmtPct` render NaN as "—". A present `null` hides the figure and never falls to
  the recomputation (`og-metrics.ts:79-82, 93, 104`).
- **A failed or stale run read as a number.** No. The route gates on `isComputedAnalytics`
  (`route.tsx:137`), and `computeOgHeadline` independently re-gates the stored scalars on
  `isRankableAnalyticsRow`, the same predicate (`og-metrics.ts:55-58`). A failed run's leftover
  scalars are never read.
- **Silent fall to a recomputation that disagrees with the lists.** Reachable only when a key is
  ABSENT from the embed (`undefined`), meaning projection drift. The route always passes all three
  keys, and `route.test.tsx` O1d pins the select to carry `sharpe`, `cagr` and `max_drawdown`, so
  drift fails CI before it ships. The fallback itself does not log. The factsheet twin
  (`persistedCashHeadline`, `composite-read-path.ts:894-906`) sends the same condition to Sentry as
  `missing_keys`. That asymmetry is noted here but is not reachable from this route today.
- **Composite: card vs factsheet.** They agree. `run_stitch_composite_job` builds the top-level
  headline by spreading the SAME `cash_metrics_json` object it writes into
  `metrics_json_by_basis.cash_settlement`, in one upsert
  (`analytics-service/services/job_worker.py:8854-8929`, "headline == by-basis by construction"). A
  failed restitch keeps the old scalars but stamps `failed`, and both surfaces gate that out. The
  composite series is 0-gap-filled into one chain (`gap_fill_daily_returns`), so SFH-01's suffix
  divergence does not apply to composites.
- **Max drawdown sign.** The stored `max_drawdown` is quantstats-convention negative, the same sign
  the old in-route computation produced. `fmtPct` output does not change.
