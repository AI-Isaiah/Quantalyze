- `og-metrics.ts:78-83` reads the flags with `=== true`. The two other readers of these flags,

- The column is `jsonb` (`baseline.sql:11947`). The Python writers store real booleans: the

  unaffected, and so are Sharpe and max drawdown.

  that hides CAGR on every row.
- Composites: SFH-02's cleared list said the suffix divergence cannot happen on a composite. That
  is not quite right. The composite scalar input keeps an in-index member-guard NaN as a chain
  break (`job_worker.py:8165-8172`, `nan_dates`). `twr_chain_broken` reaches the composite's flags
  through `member_warn_flags`, because it is a member of `NAV_TWR_GUARD_KEYS`

### SFH-02: failed read cached for a day. CLOSED

- **Every failure branch is `no-store`.** `failed` is set on all three: the `res.error` arm
  (`:118-121`), a thrown read (`:123-127`), and a thrown compute (`:199-201`). `:254` is the only
  place that sets `Cache-Control`.
- **Not-found and healthy keep the long cache.** `failed` starts `false` and nothing else sets
  it. F2 (no row, no error) and F3 (healthy) pin this.
- **Sentry does not block the response.** `captureToSentry` runs inside `after()` (`:38-43`). It
  returns a promise that always resolves (`sentry-capture.ts:205-231`), so a failed Sentry import
  cannot surface as an unhandled rejection. Outside a request scope, `after()` throws, and the
  surrounding `try` catches it (`:45`). The route still cannot 500.
- **Nothing leaks.** The response is a PNG, so the error reaches only the server log and Sentry,
  never the client. Sentry gets the PostgREST error object and the strategy id, scrubbed by
  `scrubCaptureInput`.
- **Test isolation holds.** F2's `not.toHaveBeenCalled()` does not inherit F1's capture:
  `route.test.tsx:252` calls `vi.clearAllMocks()`, and `beforeEach` resets the throttle.

## Warnings

### MR2-01 (MEDIUM, introduced by fix 7b03563d2): a malformed id is reported as a read failure, sent to Sentry at error level, and served `no-store`

**File:** `src/app/api/og/factsheet/[id]/route.tsx:69`, `:111`, `:118-121`

**Issue:** `id` comes straight from the public URL segment and reaches `.eq("id", id)` with no
check. `strategies.id` is `uuid` (`baseline.sql:11505`). For a non-UUID segment, for example
`/api/og/factsheet/abc` from a crawler or a truncated share link, PostgREST returns
`{ data: null, error: { code: "22P02", ... } }`. Before this fix, `res.error` was ignored, so the
request rendered the generic card as not-found, with the long cache. The new arm now:

1. logs it with `console.error` as `[og:factsheet] read failed`, and
2. sends it to Sentry at level `error` under `stage: "read"`, and
3. sends the card `no-store`.

That is a caller-input not-found classified as a database failure. The Sentry throttle key is
per stage, not per cause (`og-factsheet:read`, one capture per 60 s per instance,
`sentry-capture.ts:339-352`). So steady junk-id traffic uses up the one capture slot per window,
and during a real incident (a statement timeout, pool exhaustion) the capture that gets through
can be a 22P02. The operator then reads "a bot" where there is an outage. That is the SFH-02
failure mode the fix was meant to close. The no-store also stops the CDN from absorbing repeat
hits on the same junk URL.

The repo already handles this case elsewhere: `api/strategies/[id]/ownership/route.ts:70-72`
checks the id is a UUID "BEFORE it reaches `.eq()`", because a non-UUID "lands as a Postgres 22P02
cast" (H-0341). No test covers a malformed id. F1 uses `57014`.

**Fix:** Treat a non-UUID id as not-found before the read, so it keeps the long cache and does
not reach Sentry. `isUuid` already exists in `src/lib/utils.ts:81`.

```ts
import { isUuid } from "@/lib/utils";
// ...
const { id } = await ctx.params;
// A malformed id is a not-found, never a read failure: without this, PostgREST
// answers 22P02 and the SFH-02 arm reports it to Sentry and sends it no-store.
if (isUuid(id)) {
  try { /* existing read */ } catch (err) { /* existing */ }
}
```

Add a route case: `ctx("not-a-uuid")` should produce the long cache, no `captureToSentry` call,
and no `.from("strategies")` read. To show the test can fail, drop the guard, give the mock a
22P02 error for a non-UUID id, and check the case goes RED.
