# Phase 174 MARKPAUSE - Silent-failure hunt (SFH)

**Scope:** `git diff 2941b367a..HEAD -- . ':!.planning'` on branch `feat/174-markpause`.
**Focus:** the never-raise refusal recorder/clearer in `analytics-service/services/job_worker.py`, the CASE cooldown in migration `20261030120000`, and whether the tests can fail.
**Floor:** MEDIUM and above. Nothing below is LOW.

## Verdict

3 MEDIUM, 0 HIGH, 0 CRITICAL.

- F1 is user-facing: a one-day transient refusal now freezes a published series for a week and loses six mark days for good.
- F2 is a record that can lie, and the runbook says it cannot.
- F3 is a never-raise contract that half its tests do not exercise.

The weekly window cannot freeze a paused strategy forever (see "Checked and sound").

## F1 - MEDIUM (user-facing, data integrity): the weekly window keys on the flag, so one transient refusal costs a week of marks

**Where:** `supabase/migrations/20261030120000_ledger_fanout_marks_paused_weekly.sql:520-521`, mirrored in `supabase/schema/functions/enqueue_ledger_refresh_for_strategies.sql:369-370`. The flag is stamped at `analytics-service/services/job_worker.py:7718`.

**Mechanism:**
- `marks_trailing_since` is stamped whenever the last applied mark is older than the day the derive labels (`_last_applied < _label_day`).
- A single refused read is enough. The closed refusal set includes read-failure tokens: `balance_error`, `upnl_unreadable`, `positions_unreadable`, `option_value_unreadable`.
- The new `CASE` treats that flag as a persistent pause. It gives no way to tell a one-day blip from a real pause.

**Failure scenario:**
1. Day D, 00:10Z. The venue returns a transient `balance_error`. The mark for D-1 is refused and not stored.
2. The derive finishes. The series is cut at the last mark (Pitfall 7). `marks_trailing_since = D-1` is published.
3. Before this phase, the next fan-out tick 20 hours later re-derived, stored the D mark, and cleared the flag. The series ran through D.
4. Now the strategy is held for 7 days.
5. A mark is a current read labelled yesterday and is write-once per closed day. It cannot be back-filled. The marks for D through D+5 are never taken, and `mark_gap_days` grows permanently.
6. The public factsheet shows "marks stopped on D-1" for the whole week.

This is exactly the user-visible degradation the flag was built to announce. D-01 chose "re-admit weekly" for a persistent pause, and the SQL applies it to every flagged strategy.

**Silent part:** nothing logs or records the difference between blip and pause. The new refusal row carries `first_seen_day`, but the cooldown never reads it.

**Recommendation (minimal):**
- Make the window depend on how long the pause has lasted. The flag's own value is the first trailing day, so no new column is needed.
- Use the 7-day window only when `(sa.data_quality_flags->>'marks_trailing_since')` is at least N days old, for example 3. Keep 20 hours otherwise.
- Guard the cast. A malformed value must fall to 20 hours, not raise inside the lock-holding fan-out.
- Sketch:

```sql
WHEN EXISTS (SELECT 1 FROM public.strategy_analytics sa
              WHERE sa.strategy_id = lrs.strategy_id
                AND sa.data_quality_flags ? 'marks_trailing_since'
                AND (sa.data_quality_flags->>'marks_trailing_since') ~ '^\d{4}-\d{2}-\d{2}$'
                AND (sa.data_quality_flags->>'marks_trailing_since')::date <= CURRENT_DATE - 3)
THEN INTERVAL '7 days'
```

- Add matched P arms for a 1-day-old flag (stays daily) and an old flag (weekly).
- If the founder wants D-01 exactly as decided, record this cost in the CONTEXT and the migration header. Neither says a transient refusal now costs a week.

## F2 - MEDIUM: a refusal row can outlive the pause, and the runbook says a present row means "paused NOW"

**Where:**
- Recorder and clearer: `job_worker.py:3612-3692`.
- Call sites: `job_worker.py:7165`, `7232`, `7254`.
- The claim: `docs/runbooks/navmtm-chain-move-go-live.md:287` ("so a row that is present means the key is paused NOW").

**Stale-row paths, none of which delete the row:**
1. **A failed clear is swallowed.** `_clear_nav_mark_refusal` catches `Exception` and logs a WARNING with the exception class only. The mark is stored, the row stays, and nothing retries the delete. The next healthy derive's clear is a retry, but only if that derive happens and succeeds.
2. **Derives that never reach the clear.** A key that is disconnected, revoked or deleted, or that moves to a venue outside the uniform/marked sets, or whose `_mark_read_at is None` (`job_worker.py:7172-7174`, returns `None, None`), never calls the clear. `allocator_equity_derived.kind` is text with no FK. Compose's orphan sweep (`job_worker.py:14970`) only walks `key_inputs:` rows. These rows live forever.
3. **A permanently failed derive.** In key mode a `NavReconstructionError` after the record fails the job. The record write precedes it, and the derive's own test was loosened to allow it (`tests/test_derive_broker_dailies_dualmode.py`, the `others` filter).

**Consequences:**
- **The readout reports a dead pause as live.** The runbook readout (the `## Mark refusals (Phase 174)` SQL) counts these rows as refused keys now.
- **A wrong `first_seen_day`.** Refusal on D (row written), the clear fails on D+3, a new refusal on D+30. `_record_nav_mark_refusal` read-before-writes and carries `first_seen_day = D`, so the owner-only record says the key has been paused 30 days when it paused one day ago.

**Visibility of the failure itself:**
- Both warnings (`job_worker.py:3665-3669`, `3689-3692`) carry only the exception class: no key id, no job id, no day.
- A systematic failure, for example a policy or permission change on `allocator_equity_derived`, yields one unattributable WARNING per derive, no Sentry event, and no metric.
- This record is now the only place the token and first-seen day live. The log line `nav mark refused (token=... api_key=...)` just before it does carry the key, so adjacency helps. The clear failure has no such neighbour except the INFO "nav mark stored" line.
- This matches the `_persist_refused_key_capture` precedent, so it is a convention match rather than a regression. It is still the right place to decide that "never raises" should not mean "never visible".

**Recommendation:**
- Include `api_key` (the id is already logged elsewhere) in both warnings. Use `logger.error` or the repo's Sentry-reporting path for a delete or upsert failure, still without raising.
- The readout must not claim "now". Keep `last_seen_day` in the claim ("last refused on <day>; a row older than the last derive is stale"), or have the recorder-less paths clear.
- Say in the runbook that a row can be stale for deleted or disconnected keys.

## F3 - MEDIUM (test cannot fail): the never-raise contract of `_clear_nav_mark_refusal` is untested

**Where:** `analytics-service/tests/test_nav_marks_refusal_record.py:64` and `:121-124`. The hook `fail_refusal_delete` is defined and wired into the fake, but no test ever sets it (`grep fail_refusal_delete` hits only those lines).

**What goes unguarded:**
- `test_a_failed_record_write_does_not_change_the_derive` covers the upsert only.
- Remove the `try/except` from `_clear_nav_mark_refusal`, or narrow it to a specific exception, and every test stays green.
- In production a delete failure on the post-mark path would then raise out of `_write_nav_mark_for_this_derive` after `write_nav_mark` has committed. The derive fails and retries for a bookkeeping row, which is the L3 violation this phase's docstring forbids.

**Also unexercised:**
- The select-before-write failing (same `try`, a separate network call).
- A malformed existing `payload` (non-dict, or `first_seen_day` not a string), where the `isinstance` guards silently reset `first_seen` to today.

**Recommendation:**
- Add a test that sets `fail_refusal_delete` on the `test_a_stored_mark_clears_the_record` scenario. Assert that the outcome is DONE, the mark is stored, exactly one WARNING contains "not cleared" and the class name, and the stale row remains.
- Add one for a malformed `payload`, asserting the chosen behaviour.
- Neuter-test both (remove the `try`), see RED, then restore from a byte backup.

## Checked and sound (no finding)

- **Frozen forever?** No. The `CASE` only lengthens the attempt window and is keyed on `compute_jobs.created_at`, never on success. A strategy with no attempt in 7 days is admitted again. Arm P3 (8-day attempt, paused) measures this behaviourally. `compute_jobs` retention (30/90 days) exceeds 7.
- **Flag shapes:** a NULL `data_quality_flags` or a missing key falls to the 20-hour branch (fail toward the old cadence). The unpaused arm P2 pins that the weekly window does not leak.
- **Per-venue cap and LIMIT:** a longer window removes paused strategies from candidate selection for longer, which only frees slots for healthy ones. It cannot starve healthy candidates.
- **Verify block:** needle 12 asserts both the flag key and the 7-day interval, with disjointness reasoning against the arms' mutations. The migration-time assert is real, not a NOTICE.
- **`except Exception` in the recorder and clearer:** `CancelledError` is a `BaseException`, so cancellation and timeouts still propagate. `RuntimeError` from pool saturation is swallowed, which is the intended behaviour here.
- **Public leak:** `test_no_refusal_token_reaches_public_flags` is parametrised over the whole `MARK_REFUSAL_TOKENS` set and fails if a token reaches a `strategy_analytics` upsert. Key mode keeps its existing private `key_inputs.nav_mark_refusal`.
- **Clear on found-stored and stored paths:** both are pinned (`test_a_mark_found_already_stored_clears_the_record`, `test_a_stored_mark_clears_the_record`).

## Notes below the floor (not findings, not to be fixed)

- Arms P1 (2-day) and P3 (8-day) pin the window only to the interval (2, 8) days. A 7 to 3 or 7 to 5 drift would stay green.
- The runbook readout test is a text/regex pin. It cannot catch a SQL error in the readout.
- A token outside the closed set is dropped with a generic warning that names no token. The preceding `nav mark refused (token=...)` line carries it.
