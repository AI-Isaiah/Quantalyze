## What the three defects actually were

**C-08 (CRITICAL).** The pre-check ran at the old `:721`, **before** `strategy_id` was read at `:768`. There was nothing to scope by at that point, so the fix could not be "add a filter" — the block had to **move** below the `strategy_id is None` branch first. That single move also un-shadowed the csv-finalize branch, which is C-20.

**C-19.** The duplicate path returned a hardcoded `queued: False` ~170 lines above the enqueue it never reached. The draft INSERT and the enqueue are two independent PostgREST round trips with no client-side transaction, so a crash between them — or a plain double-submit — left the session answering "duplicate, not queued" on **every** retry, forever, with no state from which it could recover.

**C-21.** `/api/keys/sync` sends no `wizard_session_id`, so a fresh uuid4 was minted and the pre-check missed *by luck*. The `WIZARD_DUPLICATE` branch at `keys/sync/route.ts:438` was dead code that nonetheless documented a reachable state.

## The ownership gate, and why `user_id`-absent fails closed

`.eq("strategy_id", …)` is necessary and **not sufficient**: `context.strategy_id` is entirely caller-supplied, so a caller who supplies a foreign id just gets a read that is *consistently* foreign. The second layer looks `strategies` up on `id` AND `user_id` before the first SV read and answers 403 `STRATEGY_NOT_OWNED` on a miss.

The plan did not specify the `user_id is None` case. **Decision: 403 (fail closed.)** A row cannot be owned by nobody, so treating absence as a skip would make the whole gate opt-out by omission — an attacker would simply drop the field. Blast radius was measured before deciding, not assumed: every non-teaser caller that sends a `strategy_id` already forwards `user_id` —

| Caller | flow_type | sends `strategy_id`? | sends `user_id`? |
|---|---|---|---|
| `keys/sync/route.ts:413-417` | resync | yes | **yes** |
| `strategies/finalize-wizard/route.ts:1301-1310` | onboard | yes | **yes** |
| `keys/validate-and-encrypt/route.ts:203-210` | onboard | no (`step=validate`) | yes |
| `strategies/csv-finalize/route.ts:1177-1183` | csv | no (finalize branch) | yes |
| `verify-strategy/route.ts:180-187` | teaser | anchor-injected | — (exempt) |

There is no `internal_report` caller in `src/`. So the refusal reaches only a misconfigured caller — precisely the state the pre-existing I-SEC2 warning already flags without acting on.

Teaser is exempt: it has no tenant, and its `strategy_id` is force-overwritten with `TEASER_ANCHOR_STRATEGY_ID` before this point, so nothing caller-supplied survives to check.

The lookup is deliberately **not** wrapped in `try/except`. Answering 403 to a database outage blames the caller for our fault; the exception propagates exactly as the draft INSERT's does.

## The reply contract (PYAPI-09)

`queued` is redefined from *"this call reached the enqueue statement"* — unobservable to the caller and false by construction on this path — to:

> **a non-terminal `compute_job` exists for this verification at the moment of reply**

and `_resume_duplicate_job` makes that **true** rather than asserting it. `job_state` splits the three cases the old blanket `queued:false` collapsed:

| Case | Before | After |
|---|---|---|
| synchronous flow, work done inline | `queued:false` | `queued:false, job_state:"not_applicable"` |
| duplicate, job live | `queued:false` (lie) | `queued:true, job_state:"running"` |
| duplicate, wedged (no job, SV still `draft`) | `queued:false` (wedge as success) | `queued:true, job_state:"enqueued"` |
| duplicate, session already finished | `queued:false` | `queued:false, job_state:"not_applicable"`, **no re-enqueue** |

Re-enqueue is gated on the SV row still being `draft`. The RPC dedupes only over non-terminal **job** statuses, so without that gate a stray replay of a completed session would mint a fresh job on every refresh and silently re-sync it.

`job_state` is derived from a read-back of the job the RPC returned, not from a control-flow guess. That read is **label-only** — the RPC returning an id already establishes that a non-terminal job exists, so a failure there cannot make `queued` wrong, only cost precision between two true labels. It therefore degrades to `"enqueued"` with a WARN. The **enqueue RPC's** own exception is not swallowed: reporting `queued` for an enqueue that raised would recreate the exact lie being removed.

## Deviations from Plan

### 1. [Decision the plan left open] `user_id`-absent ⇒ 403, not skip

- **Found during:** Task 1, writing the ownership gate.
- **Issue:** The plan says "assert ownership … on miss return 403" but does not say what a *missing* `context.user_id` is. `.eq("user_id", None)` is not a valid filter, so it had to be decided explicitly.
- **Resolution:** fail closed (403), with the caller inventory above taken **before** deciding rather than assumed. Documented in the helper's docstring so the reasoning is not re-litigated.

### 2. [Rule 3 — required by the change] `_build_supabase_mock` had to route by table name

- **Found during:** Task 1, after the first full-file run.
- **Issue:** The shared mock collapsed every table onto one object and its `.eq()` returned a fresh auto-mock on the **second** call. With two `.eq()`s now on both SV reads, `one()` narrowed the result to `None` and every idempotent-hit test silently fell through to the insert path — passing while asserting nothing. Separately, the new `strategies` and `compute_jobs` reads would have consumed the strategy_verifications `side_effect` queue and desynchronised the pre-check/race sequence.
- **Fix:** `.eq()` self-chains; `.table()` routes `strategies` and `compute_jobs` to their own mocks. `fake.table.return_value` is deliberately left pointing at the strategy_verifications mock so the existing `fake.table.return_value.insert.call_args_list` assertions keep working untouched.
- **Files modified:** `analytics-service/tests/test_process_key.py`.

### 3. [Tooling substitution — not a code deviation] Management API instead of `psql`/MCP

- **Found during:** Task 3.
- **Issue:** No `mcp__supabase__*` tool was exposed to this agent, `psql` is not installed, and the Supabase CLI is linked to **PROD** — so neither the plan's `psql` command nor `supabase db query --linked` was usable as written.
