<decision_a04>
## A-04 RESOLVED BY THE PLANNER — `wrong_server` at backfill time is TRANSIENT

A-04 left this open and recorded the researcher's recommendation (permanent, validate-shaped) as a
recommendation, NOT a decision. It is settled here the other way, on measured evidence.

**The researcher's argument** was that backfill has no prior successful read to fall back on, so it
is architecturally closer to validate than to derive.

**Why it does not hold.** It mistakes *no prior READ* for *no prior PROOF*. Measured at HEAD: the
job is enqueued by `request_allocator_holdings_sync(p_api_key_id)`, which takes an EXISTING
`api_keys` row, and `_allocator_key_preflight` refuses a row that is not `is_active`. An MT5
`api_keys` row only exists because `routers/exchange.py`'s `validate_key` MT5 arm accepted the login
and the server at connect. The server WAS proven correct — by validate, not by a deal read.

**Three further measurements, all pointing the same way.**
1. The sibling derive branch already chose transient for exactly this, and its shipped comment names
   the failure mode of the other choice: the `[ASSUMED]` token set folds network/bridge errors into
   `wrong_server`, so *"a routine gateway redeploy or connection reset mid-derive would otherwise
   PERMANENTLY fail a valid strategy and falsely blame the user's credentials with no retry"*.
   Plan 01 narrows those tokens but does not eliminate the hazard — the classifier is still deciding
   from broker-supplied text.
2. The founder's own preference ordering is recorded in this phase's ROADMAP entry: *"A silent retry
   is recoverable; a wrong user-blame stamp sends someone down the wrong path."*
3. CONTEXT.md's D-01 bullet is binding and unambiguous: *"An MT5 fetch failure routes through the
   SAME classifier, so the backfill path cannot stamp permanent-and-blamed either."* Choosing
   permanent for `wrong_server` would re-create, on a NEW code path, the precise defect this phase's
   other half removes.

**The cost is asymmetric and terminating.** Transient exhausts the DB backoff to `failed_final` — a
verdict, just later. Permanent strands a working account immediately with a credential-blaming
message, on a job that runs ONCE per key.

**DECISION: only `auth` is permanent. `wrong_server` and every unrecognised signal are transient.**
</decision_a04>

<planner_findings>
## MEASURED AT HEAD BY THE PLANNER — read before writing code

**1. The branch replaces the FETCH, not the job.** `run_reconstruct_allocator_history_job` is
preflight → deribit refusal → per-key idempotency → `_fetch_and_price_window` inside an
`asyncio.wait_for` → depth resolution → sibling check → `replace_equity_snapshots` (sole key) or
`persist_equity_snapshots` (multi key) → audit. ⭐ Only the fetch step is venue-specific. Produce the
same `(rows, hit_terminus, telemetry)` triple and EVERYTHING downstream is inherited, including the
atomic sole-key replace whose docblock records the SIGKILL-between-DELETE-and-INSERT window it
closes. ⛔ Do not duplicate any of that half.

**2. The row contract, measured from the ccxt row builder and both persist functions.**
`{"asof": <ISO day str>, "value_usd": round(total, 2), "breakdown": <dict|None>, "source": <str>,
"pre_terminus_balance_unknown": <bool>}`.
- `source` is CHECK-constrained to `'exchange_primary' | 'coingecko_fallback' | 'mixed'`.
  MT5's deal ledger IS the venue's own primary record ⇒ `'exchange_primary'`.
- `breakdown` is nullable JSONB. MT5 is single-currency with no per-symbol decomposition ⇒ NULL is
  the honest value. ⛔ Do not fabricate a single-key breakdown; verify no reader breaks on NULL.
- `history_depth_months_for_venue("mt5")` returns `None` — `VENUE_HISTORY_DEPTH_MONTHS` has no mt5
  key. That is correct (a full-history deal fetch has no retention cap) and needs no edit.
- `pre_terminus_balance_unknown` is `False` and `hit_terminus` is `False`: `history_deals_get` is a
  FULL-HISTORY fetch with no retention terminus, which is why `combine_mt5_deal_ledger` can stamp
  `series_completeness = "ledger_complete"` at all.

**3. ⛔ `BACKFILL_CAP_DAYS` IS 730 AND THE MT5 LEDGER IS FULL HISTORY.** The persist docstring sizes
its single atomic upsert on that assumption — *"730 rows × ~150B is ≈110KB — well within PostgREST
payload limits"*. An unclipped multi-year MT5 ledger blows through it. The MT5 rows MUST be clipped
to the same `[start_date, end_date]` window the ccxt path uses.

**4. The level index is SPARSE and must be made dense by FORWARD-FILL, never zero-fill.** Plan 05's
sibling returns levels on the pnl ∪ flow index. The repo already states the semantics for exactly
this, in `services/native_nav.py`'s `_reindex_ffill`: *"a balance is constant between ledger events
BY DEFINITION — this is NOT a price fill; marks are never filled."* That holds exactly here because
the reconstruction is REALIZED-basis. ⛔ A zero-fill would write $0 equity days. ⛔ And days BEFORE
the first ledger day inside the window get NO ROW — `_reindex_ffill` uses 0.0 for "it did not exist
yet", which is right for a per-currency bucket and WRONG for a persisted `value_usd` that a dashboard
reads as a real balance.

**5. The kill-switch is NOT inherited (A-03).** `equity_reconstruction.py` imports neither
`mt5_enabled_server` nor `MT5_DISABLED_DETAIL` today. It DOES already have a
`from services.closed_sets import (...)` block — add both names there, matching how `job_worker.py`
single-sources them from the same module.

**6. ⚠️ What the kill-switch does and does not stop — do not overstate it.** `_allocator_key_preflight`
has ALREADY decrypted the credentials and built the session by the time control reaches the branch.
The gate stops every terminal READ; it does not stop the transport connect. `job_worker.py`'s own
151-review WR-08 comment records this correction verbatim after an earlier version overstated it.
Write the same honest scope.

**7. The test harness already exists — extend it in place.** `tests/test_equity_reconstruction.py`
carries `_FakeTable` / `_FakeUpsertResult` / `_FakeSelectResult`, a `_fake_preflight` returning a
ready `_ExchangeContext`, the `get_supabase` and `log_audit_event` patches, and the `_FakeDatetime`
pattern for pinning "now". ⛔ Add the MT5 cases to THAT file. A separate file would need to import
the harness from a test module; lifting it into a shared helper is a refactor that is not in this
phase's scope.
</planner_findings>
