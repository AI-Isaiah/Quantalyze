# Phase 164.5.4 Plan 04: The ONE MT5 deal-ledger read — Summary

The `history_deals_get` fetch+adapt half of the MT5 derive branch is now
`services/mt5_read.py::read_mt5_deal_ledger`, a leaf module the full-backfill job can
call without a cycle and without a second hand-written login sequence — extracted with
zero behaviour change, zero test-file edits, and both MT5CONC-02 login brackets pinned
at the helper for the first time.

## What Was Built

**The defect this closes before it happens.** CONTEXT.md's defect (1) needs the MT5 deal
read from a SECOND call site (`equity_reconstruction.py`, plan 06). The read lived as a
closure inside `run_derive_broker_dailies_job`, so the second caller's only options were
to import a nested closure (impossible) or write its own. The repo already shows what
the second option produces: the login bracket alone existed in THREE hand-written copies.

**The move, in one commit (`63a68cc4`).**

- `services/mt5_read.py` (NEW, 138 lines) holds the whole read: `login` → `account_info`
  → PRE bracket → `history_deals_get(0, now + margin)` → an assertion-only `account_info`
  re-read wrapped so an `Mt5ClientError` there becomes `_Mt5PostReadVerificationError` →
  POST bracket → return `(pre_info, deals)`. Every load-bearing comment travelled with
  it verbatim — the MT5CONC-02 bracket rationale, the IN-01 re-signal rationale, and the
  `None` → typed-raise / `()` → honest-empty distinction — because a summary of those is
  not the thing that makes the read safe.
- The two WR-02 margin constants and their `assert` moved WITH the read, and
  `job_worker` re-imports them. This was forced, not stylistic: the constants lived in
  `job_worker`, so a helper importing them from there while `job_worker` imported the
  helper is a cycle. The re-import keeps `jw._MT5_DEAL_FETCH_MARGIN_S` resolving for the
  existing derive regression that reads them through the module alias.
- Both brackets call the shared `mt5_probe.assert_expected_login`. The local
  `_assert_expected_login` closure is gone in the same commit — a fourth copy was the
  alternative.
- The lease, the `asyncio.wait_for` bound and all five `except` arms stayed exactly where
  and as they were. The call became
  `asyncio.to_thread(read_mt5_deal_ledger, _mt5_session, now=_mt5_now)`.

**The pins (`4c6c26b9`).** `tests/test_mt5_read.py` (NEW, 264 lines, 7 cases — one per
`<behavior>` row) exercises the helper directly with the derive suite's own
`_FakeMt5Transport`, imported rather than re-implemented. The bracket cases are the ones
that matter: they are the structural guarantee that `api_verified` is never stamped on
another account's numbers, and until now they were only exercised THROUGH a job. Nothing
in the file asserts a disposition, touches the lease or names the `wait_for` bound.

## What Plan 06 Inherits — and what it does NOT

- ⭐ **It inherits the brackets by construction.** Calling `read_mt5_deal_ledger` gets the
  PRE and POST assertions, the WR-02 margin and the IN-01 type separation with no
  re-derivation. The tests in `test_mt5_read.py` are what keep that true for it.
- ⛔ **It does NOT inherit the kill-switch (A-03).** `equity_reconstruction.py` does not
  import `mt5_enabled_server()` today, and this helper deliberately does not call it —
  the gate is a POLICY decision about whether to touch the terminal at all, and it sits
  in the derive branch ahead of the read, exactly where its sibling must place its own.
  Nothing about calling this helper takes that gate for you.
- ⛔ **It does NOT inherit a bound, a lease or a disposition.** The helper is blocking and
  unbounded by design; plan 06 must supply its own `asyncio.to_thread` + `wait_for` and
  its own `mt5_terminal_lease`, and must decide for itself what each of the five
  exceptions means on the backfill path (A-04's `wrong_server` question is still open and
  is plan 06's to settle on evidence).
