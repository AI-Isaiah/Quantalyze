- **`negative_nav` refusal** — `nav.min()` cannot silently be NaN here: `reconstruct_nav`'s inputs
  (`daily_pnl`, `terminal_nav`, `flows_by_day`) are all routed through `nav_twr._coerce_float`,
  which explicitly rejects non-finite values with `NavReconstructionError` before any `nav` array
  is built (`services/nav_twr.py:260-263`) — that exception is already caught one frame up and
  mapped to `_fail("nav_structural", "permanent")`. So by the time `nav.min()` runs, every element
  is a real finite float; `len(nav)` guards the empty case. `"permanent"` matches every sibling
  structural-failure arm in this same function (`non_finite`, `deal_unclassifiable`,
  `nav_structural` are all `"permanent"` too) — not a new/inconsistent choice. The new message was
  independently verified against `test_no_mt5_backfill_message_is_classifier_matchable`, which
  iterates `_MT5_BACKFILL_MESSAGES.items()` with no hardcoded count, so the twelfth member is
  automatically covered — no census to bump.

  populated for every non-empty `nav` this line can see (`_build_nav_meta` unconditionally sets
  `computation_status_hint` to `"complete"` or `"complete_with_warnings"`), so the guarded
  `logger.warning` cannot fire on every successful run — it fires exactly when
  `computation_status_hint != "complete"`, which is exactly when a guard flag is set, which is
  exactly when `_guards_fired` is non-empty; the two conditions are not independent, so there's no
  double-fire or always-fire failure mode. `sorted(k for k, v in meta.items() if v is True)` is an
  identity check (`is True`), so the non-bool `series_completeness: "ledger_complete"` string
  value is correctly excluded rather than accidentally matched by truthiness.
- **Anti-vacuity arithmetic** — independently re-derived the backward roll for
  `test_mt5_backfill_negative_reconstructed_nav_is_refused`: `nav[d7]=1000` (terminal anchor),
  `nav[d8] = nav[d7] - pnl[d7] - flow[d7] = 1000 - 0 - 0 = 1000`,

  every other refusal path in this job also yields `FAILED`/`permanent`.
- **Swallowed-`TypeError` sweep** — grepped every reference to `_mt5_bounded_restart` in the tree.
  The two `job_worker.py` call sites (`:4203`, `:4303`) still call it with a single positional arg

## Warnings

### WR-01: `log_prefix="refresh_allocator_positions"` is not this job's name — it should be `"poll_allocator_positions"`

**File:** `analytics-service/services/allocator_positions.py:691` and `:730`
**Issue:** SF-M1's stated purpose (`services/mt5_concurrency.py:154-158`) is that a failed restart
previously "named the wrong job during incident triage," and the fix is to have each call site pass
its real job name. The two new call sites inside `_fetch_mt5_account_rows` pass
`log_prefix="refresh_allocator_positions"` — but that string does not exist anywhere else in this
codebase. The job this function actually serves is registered in the dispatcher as
`kind == "poll_allocator_positions"` (`services/job_worker.py:9517-9518`), its handler is
`run_poll_allocator_positions_job`, and **every other `logger.warning` call inside this exact
function** (there are ~10, e.g. `services/allocator_positions.py:687`, `:712`, `:725`, `:738`,
`:774`, `:784`, `:792`, `:813`, `:819`, `:867`) uses the prefix `"poll_allocator_positions:"`. The
two new restart-failure log lines are therefore the only lines in this function that will name the
job wrong — during exactly the incident-triage scenario (a wedged MT5 terminal restart failing)
that SF-M1 was written to fix. This is not caught by any test: the five doubles that stand in for
`_mt5_bounded_restart` across `tests/test_allocator_positions_non_ccxt.py` and
`tests/test_equity_reconstruction.py` all accept `log_prefix` as a keyword-with-default but none of
them assert or capture the value actually passed by production code, so a wrong-but-well-formed
string sails through green.
**Fix:**
```python
# services/allocator_positions.py:691 and :730
await _mt5_bounded_restart(session.client, log_prefix="poll_allocator_positions")
```
Optionally, add an assertion in one of the two existing spy-based tests
(`test_mt5_read_timeout_restarts_and_raises_transient` or
`test_mt5_login_mismatch_never_emits_a_wrong_account_row`) that captures and checks the `log_prefix`
value the production call site actually passes, so a future rename of this job or a copy-paste of
this call site into another module can't silently drift again.

## WR-01 (R2) — FIXED + GATED. The finding was a defect in ROUND 1's OWN FIX.

**Measured:** `log_prefix="refresh_allocator_positions"` named a job kind that exists **NOWHERE** in
the tree. The real dispatcher kind is `poll_allocator_positions` — the string `job_worker`'s dispatch
branch matches on, and the one the ~10 sibling `logger.warning` calls in that same function already
use. So round 1's fix, whose sole purpose is naming the job correctly during a wedged-terminal
triage, **shipped a fresh misattribution** — the exact defect it was written to remove.

⚠️ The other two prefixes were checked rather than assumed, and are CORRECT:
`reconstruct_allocator_history` and `derive_broker_dailies` are both real dispatcher kinds.

⭐ **WHY NO TEST CAUGHT IT, and this is the transferable lesson.** Every double in the file accepts
`log_prefix` as a keyword **WITH A DEFAULT**, so not one of them ever observed the value production
actually passes. The parameter was gated for EXISTENCE and never for VALUE — a gate that cannot fail
on the thing that went wrong. An invented string constant is invisible to a type checker, to a
linter, and to a green suite.

**The gate now pins the VALUE**, in the test that actually restarts
(`test_mt5_read_timeout_restarts_and_raises_transient`), and it was CALIBRATED against the exact
mistake: reintroduce `refresh_allocator_positions` → RED; restore → GREEN; byte backup `cmp`-identical.

⚠️ **The first placement of that assertion was WRONG and failed honestly** — it went into the
abandoned-session test, which never restarts, so it captured an empty list. Moved to the timeout
test. Recorded because a gate placed on a path that never executes is the vacuity this repo keeps
booking.
