**Researched:** 2026-09-20
**Domain:** MT5 broker-integration reconstruction (Python analytics-service) + the
Python/TypeScript error-classification seam (Next.js wizard)
**Confidence:** HIGH for defects (1) and (2) (all claims verified by reading the source this
session); MEDIUM for defect (3)'s permissions-route half (a genuine architecture gap found this

## Summary

All three defects were re-verified by reading the live source, not by trusting the ROADMAP prose.
Defects (1) and (2) match CONTEXT.md's account exactly. Defect (3) is **more asymmetric than
CONTEXT.md's decision text implies**: the two routes it names ("rotate-secret and permissions")
do not share a mechanism today, so "mint one `WizardErrorCode`" closes rotate-secret for free but
does **not by itself** close permissions — that route has its own private, non-`WizardErrorCode`
vocabulary and its client component renders an unconditional Retry ("Re-check") button regardless
of the error code. This is the single most important finding of this research and is expanded in
Architecture Patterns / Pattern 3 below.

**Primary recommendation:** (1) add a `venue == "mt5"` branch to
`run_reconstruct_allocator_history_job` that gates on `mt5_enabled_server()`, fetches via a shared
helper extracted from `job_worker.py`'s existing `_mt5_read` closure, calls
`combine_mt5_deal_ledger` directly, and — because that combiner returns *returns*, not *levels* —
reconstructs the `value_usd`-per-day rows the persist layer expects by walking the anchor
backward with `services.nav_twr.reconstruct_nav` (imported directly; see Open Questions #1 for why
this is new territory, not a copy of an existing pattern). (2) Replace the two bare-word token
tuples in `mt5_validation.py` with anchored phrases chosen so no known transient/ambiguous MT5
message over-matches, keep the fail-closed default (unrecognised → `"transient"`), and add the
precedence test CONTEXT.md specifies. (3) Mint one `WizardErrorCode` (e.g. `KEY_UNRECOVERABLE`)
with `actions: []` for the rotate-secret route (which already calls `classifyKeyValidationError`
+ `buildEnvelope` and gets the no-Retry behaviour automatically once the copy table omits
`clear_and_retry`/`try_another_key`), **and separately** patch
`src/components/connect/KeyPermissionBadge.tsx` to suppress its always-rendered "Re-check" button
when the permissions route's private `code` is `KEY_UNDECRYPTABLE` — that route deliberately does
not call `classifyKeyValidationError` (measured reason below) so the new code cannot reach it by
osmosis.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Defect (2) — the classifier's failure posture**
- Keep the three-member `Literal` on `classify_mt5_login_error`; add a REFUSAL rule. The three
  classes collapse to TWO real dispositions (`auth`/`wrong_server` → HTTP 400 permanent
  user-blamed; `transient` → propagate, HTTP 424, no blame). Production call sites, by symbol:
  `routers/exchange.py` (`validate_key` MT5 arm), `services/ingestion/mt5.py` (the
  `Mt5ClientError` handler), `services/job_worker.py` (the MT5 derive branch).
- Replace the bare single-word tokens with ANCHORED PHRASES. `_AUTH_TOKENS` currently holds both
  `invalid` and `account`, so the observed rejection matches twice over and can never reach the
  `transient` default. Broad single words are the root cause; adding more tokens makes
  over-matching worse.
- An unrecognised or ambiguous message must NEVER produce a user-attributed permanent stamp. It
  degrades to `transient`, which the caller propagates untouched.
- Fail-CLOSED ordering gets an EXECUTABLE pin, not a comment. A test feeds a message matching BOTH
  tables and asserts `wrong_server` wins. The existing code-gate on the IPC transport codes stays
  ahead of all text matching and keeps its own arm.
- The refusal rule ships WITHOUT the live spike. It is independently correct and is what removes
  the wrong-blame stamp.

**The live spike hand-off**
- No agent may drive it. The founder enters credentials; no agent ever enters, reads, decrypts,
  logs or echoes one. The phase designs the hand-off rather than planning a task nothing can
  execute.
- Captured: `(code, text)` pairs from login rejections ONLY. Never an account identifier, never a
  broker server name, never a password.
- Transport: a fixture table keyed by SYNTHETIC accounts. The repo is PUBLIC and `.planning/` is
  TRACKED, so identifying values are replaced BEFORE anything is written — verdicts, never
  specimens, and never the pattern searched for.
- Partial sets LAND. Each measured pair retires one `[ASSUMED]` marker independently; there is no
  all-or-nothing gate.
- Nothing in this phase blocks on it. The spike is an additive follow-up.

**Defect (1) — the missing MT5 backfill branch**
- Call `combine_mt5_deal_ledger` directly. It is a PURE function —
  `(deals, account_equity, account_balance, *, server_utc_offset_s) -> (returns, meta)` — with no
  session and no IO, and `equity_reconstruction.py` already imports from `services.job_worker`, so
  the added dependency introduces no cycle. NO parallel implementation.
- Extract the `history_deals_get` FETCH+ADAPT half into ONE shared helper that both the backfill
  job and its sibling call. The combiner is already shared; the fetch is the part that would
  otherwise drift apart again.
- Add an explicit `venue == "mt5"` branch BEFORE the generic ccxt crawl, mirroring the existing
  `venue == "deribit"` guard, so the `AttributeError` is unreachable by construction. NOT by
  widening the `except` to catch `AttributeError` — that hides the class instead of closing it.
- An MT5 fetch failure routes through the SAME classifier, so the backfill path cannot stamp
  permanent-and-blamed either.

**Defect (3) — `KEY_UNDECRYPTABLE` at the language seam**
- Mint a real `WizardErrorCode` whose copy states the actual remedy.
  - NOT a `VENUE_WIRE_CODE_TO_VERDICT` row: it forces an honest verdict member and there is not
    one. `KEY_PROBE_FAILED` is recoverable and renders the same useless Retry; `SEAM_MISCONFIGURED`
    is wrong because an operator cannot fix a corrupted per-row ciphertext.
  - NOT a per-route pre-classifier arm: it duplicates the fix once per route.
- Copy says: reconnect this key. Python already raises the code with `retryable=False` and the real
  remedy; TypeScript carries that remedy rather than re-deriving it.
- NO Retry control. Offering a retry for a ciphertext that will never decrypt IS the defect.
- Closed on BOTH routes — rotate-secret and permissions. Closing one leaves the other on the
  useless envelope.
- Bounded cost, established by GREP rather than by counting: `EXPECTED_TABLE_SIZE` appears as
  exactly TWO hand-typed declarations, both in `src/lib/wizardErrors.test.ts`, both `93`, guarded
  by a meta-gate asserting exactly two declarations that agree. Minting moves both to `94` and the
  meta-gate proves they did not diverge. The count must also move in any test TITLE restating it.
  `grep` is SILENTLY BLIND to that file (deliberate NUL byte) — always `grep -a`.

### Pattern 1: The three MT5 production callers of `classify_mt5_login_error` all follow the
identical dispatch shape

**What:** every call site does `kind = classify_mt5_login_error(exc)` then branches
`if kind == "auth": <permanent, stamp> elif kind == "wrong_server": <permanent, stamp> else:
<transient, no stamp>`.

**When to use:** the derive-branch backfill job (defect 1) must adopt this SAME three-way branch,
not invent a fourth. CONTEXT.md's decision already settles this; the branch shape is additionally
verified here at all three call sites.

**Example (the DERIVE sibling this phase mirrors most closely — `job_worker.py:4362-4406`):**
```python
# Source: analytics-service/services/job_worker.py:4362-4406 (read this session)
except Mt5ClientError as exc:
    _kind = classify_mt5_login_error(exc)
    _scrubbed = str(scrub_freeform_string(str(exc)))
    if _kind == "auth":
        await _stamp_strategy_analytics_failed(
            "MT5 login was rejected (bad credentials).", detail=_scrubbed,
        )
        return DispatchResult(outcome=DispatchOutcome.FAILED,
                               error_message="derive_broker_dailies: mt5 login rejected — " + _scrubbed,
                               error_kind="permanent")
    # wrong_server AND transient both take this arm at DERIVE time — the key
    # already validated at connect, so wrong_server is treated as retriable here
    # (narrower permanence rule than at validate time).
    return DispatchResult(outcome=DispatchOutcome.FAILED,
                           error_message="derive_broker_dailies: mt5 read transient error — retrying",
                           error_kind="transient")
```
The backfill job (defect 1) is closer in *shape* to `routers/exchange.py`'s validate-time three-way
split (auth → 400, wrong_server → 400, transient → 424) than to the derive branch's two-way
collapse, because — like validate — the backfill job's own outer exception handling
(`ccxt.RateLimitExceeded` / `asyncio.TimeoutError` / generic `Exception` at
`equity_reconstruction.py:2145-2219`) already has its own `error_kind` classification via
`classify_exception`. CONTEXT.md's instruction — "An MT5 fetch failure routes through the SAME
classifier, so the backfill path cannot stamp permanent-and-blamed either" — means only that
`classify_mt5_login_error` must decide auth-vs-not; it does not mandate reusing the derive
branch's two-way collapse. **Decision needed at planning time:** does `wrong_server` at backfill
time behave like validate (permanent — the server truly doesn't exist) or like derive (transient —
the key already worked once, so treat network blips leniently)? The backfill job runs once, at
first key connect, with no prior successful read to fall back on — this is architecturally closer
to *validate* than to *derive*. Recommend mirroring `routers/exchange.py`'s three-way split
(`auth`/`wrong_server` → `permanent`, `transient` → `transient`), not `job_worker.py`'s two-way
collapse.

# Source: analytics-service/services/job_worker.py:4114-4119 (read this session) — MIRROR this,

if not mt5_enabled_server():

### Pattern 3: The `WizardErrorCode` → `envelope.ts` no-Retry precedent already exists three times

**What:** `WIZARD_ERROR_COPY` entries with `actions` that omit BOTH `clear_and_retry` and
`try_another_key` (the two members of `RECOVERABLE_ACTIONS` in `src/lib/envelope.ts:54`)
automatically yield `recoverable: false` via `envelope.ts:88`
(`recoverable: copy.actions.some((a) => RECOVERABLE_ACTIONS.has(a))`), which is what suppresses
the Retry control downstream.
**Verified precedents (all read this session, `src/lib/wizardErrors.ts`):**
- `DRAFT_STATE_INVALID` (~line 2863) — `actions: [...]` without either recoverable action; comment
  explicitly states "Their absence derives `recoverable: false` and suppresses the Retry control".
- `COMPOSITE_UNSUPPORTED_UNIFIED` (~line 3396) — `actions: ["request_call", "expand_log"]`, same
  comment verbatim.
- `ALLOCATION_NOT_ALLOCATABLE` (~line 3745) — same pattern, same comment.
- `MT5_VALIDATE_INVARIANT_VIOLATION` (`VENUE_WIRE_CODE_TO_VERDICT`, line ~4510-4513) — the CLOSEST
  precedent of all: a code minted by the *previous* phase (164.5.3) specifically for a
  rotate-secret hardening path, mapped to `SEAM_INTERNAL_FAULT`. Its docblock (lines 4493-4509)
  records the exact reasoning CONTEXT.md's rejected options mirror: "NOT `SEAM_MISCONFIGURED`
  (operator-fixable setting)... NOT `KEY_PROBE_FAILED` (recoverable, renders the same useless
  Retry)". **Cite this docblock directly when writing the new code's own docblock** — it is the
  most recent, most similar precedent in the file and states the same reasoning CONTEXT.md already
  decided for defect (3).
**When to use:** minting `KEY_UNDECRYPTABLE`'s replacement code, give it `actions: []` (or
`actions: ["request_call"]` if a support-escape-hatch action is wanted — check whether
`request_call` exists as a member of `WizardErrorAction` and is NOT in `RECOVERABLE_ACTIONS`;
confirmed by the `DRAFT_STATE_INVALID`/`COMPOSITE_UNSUPPORTED_UNIFIED` precedents above that
`request_call` is safe to include without re-enabling Retry).

### Anti-Patterns to Avoid
- **Widening `except ccxt.NotSupported` to catch `AttributeError` in the generic ccxt crawl** —
  CONTEXT.md explicitly forbids this; it hides the defect class instead of closing it. The fix is
  an explicit `venue == "mt5"` branch that never reaches the ccxt crawl at all.
- **Assuming the permissions route's `KEY_UNDECRYPTABLE` gap is a missing-classification problem**
  — it is not. `routers/internal.py`'s `get_key_permissions` already raises the code with the
  right detail; `permissions/route.ts` already has a dedicated arm (line ~599) with correct copy.
  The residual defect is purely in `KeyPermissionBadge.tsx`'s unconditional "Re-check" button. A
  plan that only touches `wizardErrors.ts` will not close this route's half of defect (3).
- **Wiring `KeyPermissionBadge.tsx` onto `classifyKeyValidationError`** to "share the fix" — the
  permissions route's own docblock (lines 622-632) explains it deliberately does NOT use that
  classifier: 5 of its 6 real fault messages would resolve to `UNKNOWN`/500 because it classifies
  a PROXY-INFRASTRUCTURE vocabulary (`PROBE_*`), not key-validation faults. Route the client-side
  fix through the route's own `code` field, not through the shared classifier.
- **Adding tokens to `_WRONG_SERVER_TOKENS`/`_AUTH_TOKENS` as the primary fix** — CONTEXT.md is
  explicit: "adding more tokens makes over-matching worse". The tables must be REPLACED with
  narrower anchored phrases, not extended.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| MT5 deal ledger → daily returns | A bespoke per-day PnL loop | `combine_mt5_deal_ledger` (`services/broker_dailies.py:545`) | Already handles deal classification, UTC-day bucketing, cashflow separation, and the DQ-01 guard set; CONTEXT.md forbids a parallel implementation |
| Returns → NAV level reconstruction | A hand-rolled compounding loop | `services.nav_twr.reconstruct_nav` (imported directly, same fail-loud coercion `combine_mt5_deal_ledger` itself uses internally) | `reconstruct_nav_and_twr` already builds this level series internally (`nav_twr.py:363-381`) but does not return it — re-deriving it from the SAME daily_pnl/flows/terminal-anchor inputs via the exported `reconstruct_nav` function reuses the honest core rather than reinventing the backward-roll arithmetic |
| MT5 login-failure classification | A second token table at a new call site | `classify_mt5_login_error` (`services/mt5_validation.py:300`) | Single-seam guarantee — 3 existing call sites already share it; a 4th independent implementation is exactly the drift this module's own docstring exists to prevent |
| MT5 fetch (login → account_info → history_deals_get) | A second copy of the read sequence in `equity_reconstruction.py` | Extract `job_worker.py`'s `_mt5_read` closure (lines 4158-4192) into a shared helper | CONTEXT.md explicitly requires this extraction; the account-mismatch bracket (MT5CONC-02) and the terminal-lease acquisition around it are non-trivial safety logic that must not be re-derived |

**Key insight:** every piece of MT5-specific logic this phase touches already has ONE canonical
implementation somewhere in the codebase (`combine_mt5_deal_ledger`, `classify_mt5_login_error`,
`_mt5_read`). The work is almost entirely *wiring* — reaching those implementations from a new
call site — not authoring new MT5 domain logic. The one genuinely new piece of domain logic is the
returns→value_usd conversion for the backfill job (Open Question #1), because no existing venue
combiner in this codebase has needed to do that conversion before.

## Common Pitfalls

### Pitfall 1: Treating `combine_mt5_deal_ledger`'s output as ready to persist
**What goes wrong:** `run_reconstruct_allocator_history_job` persists via
`replace_equity_snapshots`/`persist_equity_snapshots`, both of which expect
`rows: list[dict]` with a `value_usd` field per day (`equity_reconstruction.py:1287-1360`).
`combine_mt5_deal_ledger` returns `(returns: pd.Series, meta: NavTWRMeta)` — a *return* series, not
absolute equity levels. A naive persist of `returns` as `value_usd` would silently write daily
percentage changes as dollar balances.
**Why it happens:** the sibling derive branch (`job_worker.py`) also calls
`combine_mt5_deal_ledger` and never needs to invert back to levels, because it persists to
`strategy_analytics` (a returns-shaped table), not `allocator_equity_snapshots` (a levels-shaped
table). The two persistence targets look similar but are not.
**How to avoid:** reconstruct the level series from the same `account_equity` anchor
`combine_mt5_deal_ledger` itself anchors to, using `nav_twr.reconstruct_nav` (or equivalent) on the
SAME `daily_pnl`/`flows`/`terminal_nav` triple. See Open Questions #1 for the exact shape decision
this requires at planning time.
**Warning signs:** a persisted `allocator_equity_snapshots` row for an MT5 allocator with
`value_usd` in the range `[-1, 1]` instead of a real dollar balance.

### Pitfall 2: Assuming sFOX is a working precedent for "native combiner → equity_snapshot rows"
**What goes wrong:** `equity_reconstruction.py`'s only explicit venue branch inside
`run_reconstruct_allocator_history_job` is `venue == "deribit"`, and that branch REFUSES (permanent
"not supported") rather than reconstructing. **Measured this session:** grepping the whole file for
"sfox" returns only one comment (`:87`, a timeout-bound justification) — there is NO working
`venue == "sfox"` branch in this function either. `SfoxClient` (`services/sfox_client.py:96`) does
not implement any of the six ccxt methods the generic crawl needs, exactly like `Mt5Session`. This
means there is no existing pattern in THIS function for "a native (non-ccxt) combiner feeding
`allocator_equity_snapshots` rows" to copy from — the planner is not missing a hidden precedent;
none exists yet.
**Why it happens:** deribit and (apparently) sfox allocators never reach the full-backfill job with
real data today — either they are excluded upstream at enqueue time, or they silently hit the same
`AttributeError` class this phase is fixing for MT5 (unconfirmed — out of this session's budget to
trace the enqueue path). Do not assume sfox's absence here means sfox "already works" some other
way.
**How to avoid:** treat the returns→value_usd conversion as new code, design it directly against
`replace_equity_snapshots`'s row contract (`asof`, `value_usd`, `breakdown`, `source`,
`pre_terminus_balance_unknown`), and cite this research's Open Question #1 rather than a
non-existent "sfox already does this" precedent.
**Warning signs:** a plan task that says "mirror the sfox branch" — there isn't one to mirror,
inside this specific function.

### Pitfall 3: Fixing defect (3) on `wizardErrors.ts` alone and believing both routes are closed
**What goes wrong:** the natural read of CONTEXT.md ("mint a `WizardErrorCode`... closed on BOTH
routes") is that one code addition in `wizardErrors.ts` suffices for both. It suffices for
rotate-secret (already wired to `classifyKeyValidationError`) but not for permissions, whose client
component ignores the code entirely for the Retry-affordance decision. See Architecture Patterns /
Pattern 3 and Architecture Patterns diagram section for the full trace.
**Why it happens:** the two routes were built at different times under different constraints
(permissions predates the shared classifier's key-validation scope; the classifier's own docblock
records that routing permissions through it would degrade 5 of 6 real faults to `UNKNOWN`).
**How to avoid:** plan an explicit second task for `KeyPermissionBadge.tsx` — gate the "Re-check"

### Pitfall 5: MT5's real `last_error()` text is not documented anywhere authoritative
**What goes wrong:** assuming a web search or training-data recollection of MT5 error strings is
reliable enough to hard-code as the anchored phrases.
**Why it happens:** MetaTrader5's Python wrapper deliberately fails silently and returns raw
`(code, text)` tuples from `last_error()`; **no official MQL5 documentation page enumerates the
exact text strings** — confirmed by a web search this session returning only community forum posts
and no authoritative string table. This is exactly why CONTEXT.md defers exact-token validation to
the live spike and instead directs this phase toward the STRUCTURAL refusal rule.
**How to avoid:** choose anchored phrases from the STRINGS ALREADY PRESENT in this repo's own test
corpus (real observed/constructed values: `"No IPC connection"`, `"IPC timeout"`,
`"Invalid account"`, `"connection reset during account re-read"`,
`"Terminal: AutoTrading disabled by the client terminal"`) rather than inventing new ones from
memory, and mark every phrase `[ASSUMED]` pending the live spike per CONTEXT.md's own posture.
**Warning signs:** a plan or PLAN.md that cites an MQL5 docs URL as the SOURCE of a specific error
string — no such page was found this session.
