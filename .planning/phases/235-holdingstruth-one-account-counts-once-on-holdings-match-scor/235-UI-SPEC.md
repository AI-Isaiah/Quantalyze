# Phase 235 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This phase adds **one sentence** to the product, and it adds it in **two places**. It
adds no component, no token, no glyph and no dependency.

1. **HOLD-04: the unpriced-check note.** When the dashboard's `native_unpriced:` marker read fails,
   the rows are kept. A muted one-sentence note under the figures says those rows may include an
   account's positions from an earlier day. It is a new `degrade-warnings.ts` entry, rendered
   through `DegradeLine` on the Overview (under the glance) and on the Holdings tab (in Positions).
2. **HOLD-05: no new copy.** `MissingDataMessage` keeps every sentence it prints today. What changes
   is **when** the existing shared-account fallback prints: under the R3-01 rule, it stays unless
   every attributed key is in a printed line (§3).
3. **HOLD-01 and HOLD-02 have no rendered surface of their own.** HOLD-01 turns a would-be double
   count into a thrown read. On `/allocations` that throw reaches the route's existing
   `allocations/error.tsx` boundary ("Something went wrong" / "Try again"), unchanged. This was
   traced at HEAD: `fetchHoldings` is called by `getNetExposureSeries` and `getAllocationSeries`,
   and `derivePhase07Fields` by `getMyAllocationDashboard`. All three are awaited in `page.tsx`'s
   one `Promise.all` with no `try`. There is no `try`/`catch` inside `getMyAllocationDashboard`
   around the derive call, and the page comment requires the throw to reach `error.tsx`. HOLD-02
   changes a request-time match score and prints nothing new.

**Sources:** `235-CONTEXT.md` (decisions, and Claude's Discretion for the HOLD-04 wording and
placement), ROADMAP `### Phase 235`, REQUIREMENTS HOLD-01/02/04/05, TODOS
`170.4-DASHBOARD-MARKER-READ-SILENT` and `198-SHARED-ACCOUNT-FALLBACK-UNNAMED`, and `DESIGN.md`
(Voice, Color gates, Typography, Spacing). Every code anchor was re-measured at HEAD `f11d58ea6`
(VERSION `0.133.93.1`) on 2026-11-26. Anchors are cited by symbol, not by line.

**No founder channel in this run.** The orchestrator said not to ask questions. Every choice below
that CONTEXT did not lock is recorded as **Claude's discretion (CD-n)**, and the founder can

## 1. HOLD-04: the unpriced-check note

### 1.1 Registry entry (new, `src/lib/degrade-warnings.ts`)

Add it next to the other `allocation.*` read failures, after `allocation.alerts-unverified`.

| Field | Value |
|---|---|
| `id` | `allocation.holdings-unpriced-check-failed` |
| `surface` | `my-allocation` |
| `class` | `read_failure`. The payload is a bare boolean with no key and no day, so `degrade` would fail the judge. |
| `scope` | `none` |
| `action` | `A-RELOAD` (an existing vocabulary id; the vocabulary stays closed) |
| `shippedAction` | not set |
| `text` | `(): DegradeSegment[] => [ "<sentence 1.2> ", { action: "A-RELOAD" } ]` |

The comment above the entry must say the origin: Phase 235 HOLD-04 (CONTEXT; TODOS
`170.4-DASHBOARD-MARKER-READ-SILENT`). It must also say why the entry is `read_failure`: the
marker read failed, the payload names no account, and the rows are kept on purpose.

### 1.2 Copy (CD-1, Claude's discretion; founder may override)

Rendered plain text, verbatim. It is one string literal plus the action segment:

> We could not check whether each account's newest day could be priced in USD, so the holdings shown may include an account's positions from an earlier day. Reload this page to try again.

- First segment, exactly: `We could not check whether each account's newest day could be priced in USD, so the holdings shown may include an account's positions from an earlier day. ` (it ends with one space).
- Second segment: `{ action: "A-RELOAD" }`. `DegradeLine` renders it as `Reload this page to try again.` with no link, because the `A-RELOAD` link is `none`.
- The apostrophe is ASCII U+0027, as in `allocation.book.history-read-failed`'s "allocation's".

Why these words:
- **Voice.** "We could not check …, so … may …" is the shape of the shipped
  `strategies.placeholder-keys-unreadable` sentence. It is active, declarative and sentence-case
  (DESIGN.md Voice).
- **"priced in USD"** is the vocabulary of the sibling entries (`allocation.unpriced-dated`,
  `-whole`, `-history`). CONTEXT's working phrase "priced-checked" is **not** used.
- **"the holdings shown"** means what the rows feed and nothing more: Allocation equity, Positions
  and Exposure. The Glance group and the tab are both titled "Holdings". It deliberately avoids
  **"the total"**, which the derived-total notes own (see the HEAD table, row 4).
- **"may include an account's positions from an earlier day"** is exactly what a failed marker read
  can do. A key whose newest poll was declared unpriced keeps counting its older rows (the TS
  reader's `{day: unpricedAsof, hasRows: false}` rule does not fire). The sentence claims no more
  than that. It names no account, because the payload carries none.
- **No date.** The read failed, so there is no day to state, and none is invented (DESIGN.md
  "dated document": the note states its own limit rather than a guessed date).

### 1.3 Mount points (CD-2, Claude's discretion; founder may override)

Both mounts render the **same entry** with the **same condition**:

```
render when  payload.<flag> === true  &&  (payload.holdingsSummary ?? []).length > 0
```

- `<flag>` is the boolean CONTEXT puts on the payload. The suggested name is
  `holdingsUnpricedCheckFailed?: boolean`: optional, so legacy fixtures compile, as
  `departedHistoryUnavailable` is. The planner owns the final name.
- With no rows there is nothing the failed check could have left in, so the sentence would be false
  and it does not render. The Sentry event still fires. The capture does not depend on rows.

**Mount A: Overview** (`AllocationDashboardV2.tsx`).
- **Position:** directly **after `<MissingDataMessage lines={missingLines} />`** and **before**
  the `DepartedHistoryNote` line.
- **Why not directly under the glance:** `GlancePanel`'s `noteBelow` sr-only pointer ("See the note
  below.") refers to the missing-data message that sits directly under it (198-14 SFH-01). Putting
  this note between them would break that pointer.
- **Gate:** **not** `!isRebuilding`. The glance's Holdings group prints in both history states.
- **Spacing: `mt-3 mb-3`, one more class than the siblings, and deliberately so.** This is the
  only Overview note that renders while the history rebuilds, and a rebuilding book always has at
  least one `MissingDataMessage` line. That section is `mt-4` with no bottom margin, and its lines
  are the same `text-sm text-text-secondary`. With no top margin, the note would sit flush under the
  last "What is missing" line and read as one more item of that list. `mt-3` gives a 12px gap.
  When the missing-data section is absent, the note's `mt-3` collapses with `GlancePanel`'s `mb-3`
  (sibling block margins collapse in this plain `div` flow), so the gap stays 12px and does not
  double.
- **Markup**, the sibling notes' classes plus `mt-3`:

```tsx
<p
  role="status"
  data-testid="dashboard-holdings-unpriced-check-note"
  className="mt-3 mb-3 px-1 text-sm text-text-secondary"
>
  <DegradeLine
    id="allocation.holdings-unpriced-check-failed"
    segments={degradeSegments("allocation.holdings-unpriced-check-failed", undefined)}
  />
</p>
```

**Mount B: Holdings tab, Positions section** (`HoldingsTabPanel.tsx`).
- **Position:** the first child after the Positions header row. That row is the
  `div.flex … gap-x-4` holding `h3#holdings-positions-heading` and the
  `positions-book-equity` span. The note comes **before** the `positions-unreported-caption`.
- **Why there:** it qualifies the `Allocation equity … · read …` figure on that header. It also
  qualifies everything below it on the tab (spot table, derivative table, Exposure). The
  Strategies section above reads no holdings rows, so the note does not go at the top of the tab.
- **Markup:** the section's `gap-4` grid spaces it, so it gets no margin of its own:

```tsx
<p
  role="status"
  data-testid="positions-holdings-unpriced-check-note"
  className="text-sm text-text-secondary [overflow-wrap:anywhere]"
>
  <DegradeLine
    id="allocation.holdings-unpriced-check-failed"
    segments={degradeSegments("allocation.holdings-unpriced-check-failed", undefined)}
  />
</p>
```

Each id is written as a **literal at its render site**, so the scan test attributes it (the
`MissingDataMessage` / `UnpricedAccountNote` convention). Do not build a shared wrapper component:
two inline `<p>` blocks are the established pattern, and this phase adds no component.

**Not mounted: Scenario tab** (recorded, not silent, ⚠ in §5). The Scenario composer seeds its
draft weights from `holdingsSummary`, but it prints no holdings dollar figure. Its live strip reads
`liveBaselineMetrics` (`liveBookFigures`), not the rows. CONTEXT scopes the note to "wherever the
Holdings / live total reads the affected rows". The scenario **commit** path already reports the
same condition to Sentry, and its persisted figure is governed separately (`auditEvidence: false`).
If the founder wants the note on Scenario too, it is the same entry and the same `<p>`, and only a
third ledger move.

### 1.4 Visual treatment (CD-3)

- **Muted, not amber.** DESIGN.md gives two readings of amber, and the choice rests on precedent,
  not on either reading. The Color "Approach" line reserves warning for "transient recoverable
  states that the system will handle on its own". The normative Semantic-color gate is wider:
  "Amber = system- or user-recoverable disclosure". A failed read cleared by a reload is
  user-recoverable, so the gate would **allow** amber. The deciding fact is the shipped page:
  every read failure already on `/allocations` is neutral. That is `allocation.alerts-unverified`
  (muted caption), `allocation.holdings-strategies-read-failed` (neutral bordered box) and
  `allocation.book.history-read-failed` (muted line). The figure notes this one sits beside
  (`UnpricedAccountNote`, `FailingKeyExitNote`, `DepartedHistoryNote`) are muted too. Amber on
  `/allocations` is held by `StalenessBanner`, a book-wide condition. One sentence about one
  failed check stays in the register of its neighbours (Rule 11, conformance).
- **`text-sm text-text-secondary` (14px, #4A5568), not the `text-xs text-text-muted` captions** of
  the Positions section. This note says the figure above may be off, which is stronger than the
  read-day and price-gap captions. It takes the weight of the Overview figure notes on both tabs,
  so one sentence looks the same wherever it appears.
- **No box, no border, no icon, no glyph, no colored stripe** (DESIGN.md AI-slop ban:
  colored-left-border cards, decorative glyphs).
- **Visible at every width.** Do **not** copy `AlertBanner`'s `hidden md:block`. The note must show
  at 390px. It wraps (`[overflow-wrap:anywhere]` on Mount B; on Mount A the `px-1` stack
  already wraps prose).
- **No interaction.** The action sentence links nowhere (`A-RELOAD`), and nothing is dismissible.
  The condition is re-read on every render (page load, and the Overview's poll), so a dismiss could
  hide a statement that is still true.
- **Live behaviour on the Overview.** The Overview's `router.refresh()` poll rebuilds the payload,
  so the note appears on the first poll after the read starts failing and disappears on the first
  poll after it succeeds again. No transition or animation is added: it mounts and unmounts like
  its sibling notes. The Holdings tab does not poll. There, the note reflects the last page load or
  tab switch.

### 1.5 Accessibility

- `role="status"` on the `<p>`, as on every sibling note in the Overview stack. It is in the SSR
  payload at first render. On the Overview, a poll can mount it mid-session, and the implicit
  polite live region of `role="status"` then announces the sentence once. That is the intended
  behaviour for a non-blocking state change (DESIGN.md A11y minimums: `role="status"` on
  non-blocking state changes), and it matches the sibling notes, which mount the same way. There is
  no `aria-live` override and no `role="alert"`: the read failing does not block anything.
- 14px #4A5568 on #F8F9FA / #FFFFFF is above 4.5:1 (the DESIGN.md text-secondary token).
- No focusable element is added.

## 3. HOLD-05: every failing shared-account key covered (superseded in part by S1 resolution: every key is NAMED, one new undated line)

**Copy: unchanged.** No sentence is added, removed or reworded. The two entries involved stay
byte-for-byte as shipped:
- `allocation.key-gap.shared-account-failing`: `{labels}: {coverage}. Fix or reconnect one of these keys on the Exchanges page.`
- `allocation.book.shared-account-no-working-key`: `The equity chart and the ratios built from it are hidden for your whole history. The keys that read one of your exchange accounts are all failing to sync, so that account's history stops. Fix or reconnect one of them on the Exchanges page.`

**What changes is when the fallback prints.** `missingDataLines` applies the R3-01 rule to
`shared_account_failing` as it does to `not_syncing`. The fallback stays unless every attributed
key (the new producer field, every key of each all-failing group) appears in a printed gap line.

**How the producer shapes this, traced by reading `key-data-gaps.ts` at HEAD (not executed).**
- `accountGroups` keeps only groups of **two or more** keys on one known account.
- In the `shared_account_no_working_key` arm, `keyDataGaps` pushes each all-failing group as **one**
  gap carrying the whole group's ids, with the tail starting after the group's **latest** last day
  (`push(group, "shared_account_failing", 2, { lastDay: latest, … })`).
- A group whose latest day already reaches yesterday has an empty tail, and `push` emits **nothing**
  for it.

So the uncovered case is **two all-failing accounts**. Account 1 has a gap and prints its line.
Account 2's latest day reaches yesterday, so it has no gap. Today `causesPrinted` counts 1 named
gap out of 1 and suppresses the fallback, so account 2's keys go unmentioned.

**Expected render for the uncovered case** (rebuilding, reason `shared_account_no_working_key`;
account 1 = keys A1, A2 with a gap; account 2 = keys B1, B2 reaching yesterday):
1. Account 1's line: `{A1 label} and {A2 label}: no data for {range}. Fix or reconnect one of these keys on the Exchanges page.`
2. The fallback, because B1 and B2 are attributed and in no printed line. It is the book line
   quoted above, sorted last, as book lines are.

**Prohibitions** (each a test assertion):
- P1. A key whose history reaches yesterday is **never** printed with null coverage. "no complete
  history yet" is false for it, and `keyDataGaps`' empty-tail rule exists to prevent exactly that.
- P2. Such a key is **never** merged into another account's dated line. Attributed ids travel
  beside the gaps, and a gap's `apiKeyIds` is unchanged.
- P3. A raw key id never prints. Labels still resolve only through `apiKeyLabelById(apiKeys)`
  (T-198-17).
- P4. When every attributed key is in a printed line, the fallback stays suppressed. There is no
  duplicate book line, so the shipped no-double-message behaviour holds.
  ⛔ CORRECTED 2026-11-26 (review round 1 WR-01, verified fixed in round 2): when any shared-account group is named only by the undated line, the book-level fallback line also prints (`everyGroupNamed && !anyUndated` in `missingDataLines`). The fallback is dropped only when every group is named by a printed dated gap. Every failing key is still named by label (SC-4). The text before this note is kept as lineage.

**Surfaced, not resolved here** (the planner and verifier should read these):
- **S1. RESOLVED 2026-11-26 (orchestrator, after the UI check).** ROADMAP SC-4 and REQUIREMENTS HOLD-05 say every failing key is "**named**", and they govern over CONTEXT's earlier "named, or the fallback prints" (CONTEXT now carries a dated correction). So the contract is: every attributed `shared_account_failing` key appears BY LABEL. A key no dated gap line names gets a labelled line that states no day, from ONE new registry entry (working id `allocation.key-gap.shared-account-failing-undated`, final id at planning), whose copy is the shipped shared-account-failing sentence without its coverage clause, in DESIGN.md Voice. P1 is read as "named", not "named or covered by the fallback". The unnamed book line stays only for a key the owner's list cannot label. This adds one more new copy element (Claude's discretion, no founder channel; founder may override at review).
- **S2. Ambiguity, as a known limit.** When the fallback prints next to a named shared-account line,
  "one of your exchange accounts" can be read as the account just named. The sentence is true either
  way. It is recorded here and is not fixed by this phase.
- **S3. The TODOS / CONTEXT test fixture cannot go RED as worded.** Both say "two keys, both
  shared-account failing, one with a gap and one with data through yesterday". Two keys can be
  **one** shared account only (`accountGroups` needs two or more per account). That account's
  latest day is yesterday, so `keyDataGaps` emits no gap, and the fallback **already prints at
  HEAD**. That fixture passes before the fix and cannot satisfy PROOF-01. The fixture that goes RED
  on pre-fix code is the **two-account** case above (four keys, or more). This departs from
  CONTEXT's literal wording and keeps its intent ("both must be covered"). The planner should
  record the departure, and may keep the two-key case as an extra GREEN-only regression.
- The fallback renders only while the history is rebuilding. That is consistent: the
  `shared_account_failing` cause is produced only under the `shared_account_no_working_key` rebuild
  reason, so a ready book never has an attributed key to cover.
