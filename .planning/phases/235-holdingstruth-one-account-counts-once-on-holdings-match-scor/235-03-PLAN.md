<objective>
HOLD-04, the server half: when the dashboard's `native_unpriced:` marker read fails, `getMyAllocationDashboard` says so in its payload and reports it to Sentry. Today it drops `fetchLatestHoldingsPerKey`'s `markerReadError` (only the scenario commit route reads it), so an account whose newest day could not be checked counts its earlier-day rows silently.

This plan adds the boolean `holdingsUnpricedCheckFailed` to both payload literals and a throttled warning capture. It also adds a marker-only failure injection to the test harness, because the existing injection fails the whole `allocator_equity_derived` table and would take the equity-curve read down with it. Plan 04 renders the note from this flag.

Purpose: the "a Sentry event fires" half of SC-3, and the data the "page shows a note" half needs.
Output: the payload field, the capture, the harness key, the arms, and the PROOF-01 transcripts in the SUMMARY.
</objective>

Planner decisions (Claude's discretion, no founder channel; recorded, reversible, founder may override at review):
1. Tags (RESEARCH open question 2; two conventions surfaced per CLAUDE.md Rule 7, not blended silently). Every capture inside `getMyAllocationDashboard` uses `op` + `reason`, while the commit route uses `area` + `gate`. This capture carries all three: `op: "getMyAllocationDashboard"`, `reason: "holdings_marker_read_failed"` (file conformance, Rule 11, and existing Sentry filters on `op`) and `area: "my-allocation-dashboard"` (CONTEXT's area tag). The `area` value is undotted, so the degrade-warning scan can never read it as a registry id (UI-SPEC T8).
2. Throttle (RESEARCH open question 3, UI-SPEC T8). Reuse the existing 6 h per-instance window by extending `shouldCaptureDerivedRowRejection`'s union with `"holdings_marker_read_failed"`. The Overview's 30 s `router.refresh()` poll would otherwise send about 120 events an hour per open tab, the volume R3-WR-04 already fixed for derived rows. The console line and the flag stay on every load. Server-side throttling is not the client-side suppression UI-SPEC T8 forbids.
3. The flag is a const computed once after the `assertOk` block and set explicitly in both literals (Pitfall 3). It is optional on the type (`holdingsUnpricedCheckFailed?: boolean`, like `departedHistoryUnavailable`) so legacy fixtures compile, but the server always sets it.

## Flagged assumption (edge probe: HOLD-04 unclassified, status unresolved)

The spec-less edge probe could not classify HOLD-04. Planner assumption, flagged and not auto-resolved:
- (a) ONE failed key is enough to set the flag for the whole payload, because the reader reports the first failed key's message and the payload names no account.
- (b) Several failed keys give one flag and, within the window, one capture.
- (c) A book with no keys reads no marker, so the flag is false.
- (d) A book with keys but zero holdings rows can still set the flag and the capture. The capture does not depend on rows; plan 04's note does not render without rows.
Verifier: confirm (a) to (d) against the code rather than treating them as proven edges. Arms H1 to H3 and S1 to S4 pin the single-key case only.
