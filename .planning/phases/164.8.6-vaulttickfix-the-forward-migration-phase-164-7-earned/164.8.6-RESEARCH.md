## Summary

This phase is one SQL wave and one JavaScript wave that share nothing but a phase number. The SQL wave ships forward migration(s) that (a) re-run `20260907120000`'s check 6 with needles bound to statement shapes instead of tokens, (b) make `match_engine_cron_tick()`'s Vault read single-row-safe and whitespace-safe, and (c) assert the whole EXECUTE grantee set of all three SECURITY DEFINER functions. Every one of those fixes is a NEW migration; no applied file is edited for a fix. The JS wave hoists the manifest-side hygiene loop above `compareManifest`'s early returns and replaces five hygiene exemptions with a whole-token measure.

Three findings change how the planner must lay this out. **First**, criterion 5 is answered: the Supabase CLI plans by VERSION, never by content, so a comment-only edit to an applied migration changes nothing in the plan — but `supabase-migrate.yml:848-851` turns "zero migrations applied on a push event" into `exit 1`, so a comment-only edit merged ALONE goes red and blocks the PROD apply, while the same edit merged BESIDE a real new migration passes. **Second**, the mutation-runner couples every `edit`-kind gate arm to the file it edits: appending a new `CREATE OR REPLACE` migration to a gate's apply list makes every existing arm that byte-edits the OLD migration's body non-biting (the later definition overwrites the mutation), so 6 arms in the vault-tick gate (and 26 in the two fan-out gates, if the fan-out bodies change) must be re-pointed, and the migration's own verification needles must be DISJOINT from the strings those arms mutate, or the mutation aborts the apply and the arm needs a waiver — with `WAIVED_CEILING = 0`. **Third**, the ROADMAP's "one forward migration" collides with the apply-list topology: the vault-tick gate's lane does not carry the ledger stack and the fan-out gates' lanes do not carry the vault stand-in, so a single file touching both function families cannot apply on either lane. Two files, one PR.

**Primary recommendation:** Ship TWO forward migrations in ONE PR — `..._vault_tick_hardening.sql` (criteria 1-4 for `match_engine_cron_tick`, appended to the vault-tick gate's apply list) and `..._ledger_fanout_grantee_set_and_dormancy_instrument.sql` (criterion 4 for the two fan-outs + the dormancy instrument, appended to both fan-out gates' apply lists) — with verification needles chosen from the set `{FROM vault.decrypted_secrets, FROM public.system_settings, FROM public.system_flags, v_enabled IS DISTINCT FROM TRUE, v_cnt > 1}` and gate `find` strings kept disjoint from them; fold the `20260907130000` comment fix into the same PR; run the full-corpus lane with `export PGBIN=/opt/homebrew/opt/postgresql@16/bin` and separate `ARMS_FLOOR` both ways before pinning; run the three reviewers before `gh pr create`.

### Pattern 1: variable-bound statement-shape needle over a comment-stripped body (the sibling idiom)

**What:** bind each needle to a `TEXT` variable holding the statement SHAPE, strip `--` comments with `regexp_replace(def, '--[^\n]*', '', 'g')`, sanity-check the stripped length, then `position(needle IN def) = 0 → RAISE`.
**When to use:** any apply-time assertion that a function body still carries a specific READ or GUARD. Lint rule `R2-functiondef-comment-strip` mandates the strip for the gate corpus (`scripts/lint-sql-gates.mjs:135-147`); the migration matches it.
**Source (verbatim, `20260907130000_ledger_refresh_switch_to_system_flags.sql:766-775`):**
```sql
  -- The two positive needles, held in variables so the loop states each one once.
  v_flag_needle TEXT := 'FROM public.system_flags';
  -- ⚠️ BOUND TO THE GUARDED VARIABLE, not floating. `IS DISTINCT FROM TRUE`
  -- alone asserts only that the token appears SOMEWHERE in the stripped body —
  -- it is satisfied by a null-safe comparison of any other variable, in any
  -- other statement, while the activation guard itself has been rewritten to
  -- `NOT v_enabled`. Naming the variable is what makes check 5 an assertion
  -- about the flag. Measured before tightening: `v_enabled IS DISTINCT FROM
  -- TRUE` occurs exactly ONCE per body (and nowhere else in this file), so the
  -- widened needle costs nothing today and refuses the drift tomorrow.
  v_null_needle TEXT := 'v_enabled IS DISTINCT FROM TRUE';
```
and the assertion half (`:896-903`):
```sql
    v_def := regexp_replace(v_def_raw, '--[^\n]*', '', 'g');

    IF v_def IS NULL OR length(v_def) < 500 THEN
      RAISE EXCEPTION 'Migration 20260907130000: the comment-stripped definition of public.% is % character(s) — the strip is broken, so checks (4)-(6) below would pass over nothing', v_fn, COALESCE(length(v_def), 0);
    END IF;

    -- 4. the guard READS THE TABLE.
    IF position(v_flag_needle IN v_def) = 0 THEN
      RAISE EXCEPTION 'Migration 20260907130000: public.% does not read the activation flag from the settings table (looked for "%") — the fail-closed switch is gone and this function would fan out unconditionally', v_fn, v_flag_needle;
    END IF;
```

### Anti-Patterns to Avoid
- **Editing an applied migration for a FIX.** Locked out by CONTEXT.md; also the CLI would never re-run it (§Q1).
- **`RAISE EXCEPTION` inside an `EXCEPTION WHEN` handler** to translate `STRICT`'s `NO_DATA_FOUND`/`TOO_MANY_ROWS` — `20260907130000:244-245` names that as "the shape lint rule R1 flags in the gate corpus; keeping it clean at the source is what stops a gate copying the bad shape". Use the explicit count form (§Q3).
- **Re-running check 5 (seed-row read) or `20260907130000` check 7 (flag-row read) in the new migration.** Both read DATA; shared TEST's `public` tables are empty (§Q5).
- **Calling any of the three functions at apply time.** `20260907130000:743-747` and `20260907120000:398` forbid it; `match_engine_cron_tick()` fires a real `net.http_post`.
- **Pasting a `prod-body-ack` hash off the CI log.** It must be EARNED by reproducing PROD's hash from origin/main's snapshot (`20260907130000:6-46` shows the full derivation).
- **A `skip` or `RAISE NOTICE` branch in a gate for "TEST cannot do X".** The file's own header forbids it (`test_analytics…:55-56`); guard with a named `TEST FAILED (X-SETUP)` instead (`:229-238` pattern).

## Research Questions — answered with evidence

### Q1. Criterion 5 — does a comment-only edit to an applied migration change what `supabase-migrate`'s plan job plans?

**Answer: NO for the plan; YES for the workflow's verdict when the edit is merged alone.** Three independent readings agree:

1. **The CLI plans by version, not content.** `findPendingMigrations` reconciles the 14-digit version parsed from each local filename against the remote history table's version list: `if (remote === local) { i++; j++; }`; `--include-all` only adds local versions absent from the remote table (`includeAllPending`). File content is never hashed. `[CITED: Context7 /supabase/cli — apps/cli/src/command-internal/migration-pending.ts, db-push-core.ts]`; `supabase db push --help` states `--include-all  Include all migrations not found on remote history table.` `[VERIFIED: shell, CLI 2.84.2]`. So an edited-but-recorded version is not pending; the dry-run bullet list is EMPTY.
2. **The workflow turns an empty applied set on a `push` event into a red check.** Verbatim, `.github/workflows/supabase-migrate.yml:848-851`:
   ```
   if [ "${IS_PUSH}" = "true" ] && [ "${applied_n}" -eq 0 ]; then
     echo "::error::the TEST push applied ZERO migrations on a push-to-main run. … If the change was genuinely a no-op (a comment edit inside an already-applied migration file), re-run via 'gh workflow run supabase-migrate.yml --ref main', where an empty set is tolerated."
     exit 1
   ```
   `[VERIFIED: .github/workflows/supabase-migrate.yml:848-851]`. `apply-test` RED → PROD `apply` is skipped (`:1074` `if: … needs.apply-test.result == 'success'`) and `apply-test-verdict` (`:982`) names the failure. The same file's own comment at `:822-823` records the empty case as "hard-fail on a `push` event, tolerated on `workflow_dispatch`", proven by run `34354619770` printing `planned 0 migration version(s); push reported 0.` `[VERIFIED: :817-823]`.
3. **The drift gates are comment-blind by construction.** VAC-04: "Both sides are comment-stripped and whitespace-normalized" (`scripts/prod-body-drift-check.sh:19-22`); VAC-08 uses "the SAME implementation VAC-04 uses (D-05: the comment trap is fixed once, not twice)" (`scripts/test-ledger-drift-check.sh:85-87`). `[VERIFIED]`. ### Q3. The Vault read now, and the single-row-safe form in this repo's style

**Now (`20260907120000:321-326`, identical in the snapshot `supabase/schema/functions/match_engine_cron_tick.sql:29-34`):**

```sql
  -- ONE read; count and value from the same scan. count = 0 leaves v_key NULL and the

   WHERE name = 'analytics_service_key';
  IF v_cnt > 1 THEN
    RAISE EXCEPTION 'analytics_service_key is not unique in vault (% rows) — refusing to pick one';
  END IF;

```

## Common Pitfalls

### Pitfall 1: The later `CREATE OR REPLACE` silently un-bites every body-editing arm
**What goes wrong:** appending the new migration to a gate's apply list without re-pointing V1/U1/C1/C2/C3 (tick) or the 26 fan-out arms → `no-red` defects → `sql-mutation` exit 1.
**How to avoid:** re-point every `edit` whose `find` is function-body text to the new file; re-measure `occurrences`; leave R3 (table REVOKE) on `20260907120000`.
**Warning signs:** `no-red` rows naming those arms in the runner report.

### Pitfall 2: A verification needle that a gate arm mutates
**What goes wrong:** the mutation trips the migration's own `DO` block at apply → lane aborts before the gate → no attributable `TEST FAILED` → needs a waiver → `WAIVED_CEILING exceeded: 1 waived arm(s) > ceiling 0`.
**How to avoid:** needles ∈ {`FROM vault.decrypted_secrets`, `FROM public.system_settings`, `IF v_cnt > 1 THEN`, `FROM public.system_flags`, `v_enabled IS DISTINCT FROM TRUE`}; gate `find`s ∈ {`IF v_key IS NULL OR btrim(v_key) = '' THEN`, `IF v_url IS NULL OR v_url = '' THEN`, `WHERE s.key = 'analytics_service_url'`, `IF v_url !~ c_url_allowed THEN`, the C3 message suffix}. Assert disjointness in the plan and paste both lists into the migration header.

### Pitfall 3: A data read in the verification block
**What goes wrong:** applies on PROD, refuses on empty TEST, blocks the PROD apply (§Q5).
**How to avoid:** catalogue reads only; never re-run `120000:534` or `130000:926`.

### Pitfall 4: Comment-only edit merged on its own
**What goes wrong:** `supabase-migrate.yml:848-851` fires; `apply-test` RED; verdict job red.
**How to avoid:** bundle with the new migrations (§Q1). For 164.5.1: annotate beside.

### Pitfall 5: The pasted `prod-body-ack`
**What goes wrong:** an ack "transcribed off a log" satisfies the grep and proves nothing (`20260907130000:42-46`).
**How to avoid:** `node scripts/sql-body-normalize.mjs --diff-bodies <origin/main snapshot> <HEAD snapshot>` must reproduce the hash VAC-04 reports for PROD; expected today: the three hashes in §Q4.

### Pitfall 6: Lane boots the wrong keg
**What goes wrong:** `pg_ctl` on PATH is 18.6 (`/opt/homebrew/bin`), pg_cron lives only in the @16 keg; the lane fails "named diagnosis" or `lane-probe: pg_cron ABSENT`.
**How to avoid:** `export PGBIN=/opt/homebrew/opt/postgresql@16/bin` in the shell that runs the runner (the check script refuses a one-shot prefix — quoted in §Environment).

### Pitfall 7: Pre-merge red on shared TEST is expected, not a defect
**What goes wrong:** V2 (whitespace) and the whole-set arm are RED on TEST until the merge applies the migrations; a reviewer reads it as a broken PR. Then on the merge push `sql-tests` may race `apply-test` (advisory key `61616158`, `[164.8-PUSH-RACE-VAC08]`).
**How to avoid:** say so in the PR body with the CLAUDE.md coupling (b) citation; re-run `sql-tests` after `apply-test` lands; never edit `supabase-migrate.yml`.

### Pitfall 8: `STRICT` swaps V1's by-name message for `P0002`
See §Q3. Use the count form.

### Pitfall 9: Forgetting `npm run schema:functions`
**What goes wrong:** `schema:functions:check` reports `stale: supabase/schema/functions/match_engine_cron_tick` (`dump-sql-functions.ts:506`) and the `frontend` aggregator goes red; VAC-04 then compares the OLD snapshot to PROD and reports no drift — a false green for the ack.
**How to avoid:** regenerate, commit, then run VAC-04 locally against origin/main's snapshot.

### Pitfall 10: Treating the JS items with migration discipline (or vice-versa)
The three reviewers, TEST-before-PROD and the marker query apply to `supabase/**` only; `cron-drift.mjs` needs vitest + fixtures + the prober's own self-test. Separate wave, separate commit(s), same PR or a second PR — the CONTEXT allows either; a second PR keeps the migration diff reviewable.

## Code Examples

### Whole grantee set = `{owner}` (catalogue-only, lane-falsifiable)
```sql
-- Source: idiom from supabase/migrations/20260515205431_sec_def_public_execute_guard.sql:86-90
FOREACH v_fn IN ARRAY ARRAY['match_engine_cron_tick'] LOOP   -- ledger file: the two fan-outs
  SELECT pg_get_userbyid(p.proowner),
         string_agg(CASE WHEN a.grantee = 0 THEN 'PUBLIC' ELSE pg_get_userbyid(a.grantee) END, ',' ORDER BY 1)
    INTO v_owner, v_grantees
    FROM pg_proc p
    JOIN pg_namespace n ON n.oid = p.pronamespace
    CROSS JOIN LATERAL aclexplode(COALESCE(p.proacl, acldefault('f', p.proowner))) a
   WHERE n.nspname = 'public' AND p.proname = v_fn AND p.pronargs = 0
     AND a.privilege_type = 'EXECUTE'
   GROUP BY p.proowner;
  IF v_grantees IS NULL THEN
    RAISE EXCEPTION 'Migration <ts>: could not read the EXECUTE grantee set of public.% — the function is missing or has no aclitem at all', v_fn;
  END IF;
  IF v_grantees IS DISTINCT FROM v_owner THEN
    RAISE EXCEPTION 'Migration <ts>: EXECUTE on public.% is held by [%], expected exactly the owner [%]. service_role''s grant survived Phase 164.7 precisely because only anon/authenticated were probed; a SECURITY DEFINER function that posts the analytics service key must be callable by the scheduler alone', v_fn, v_grantees, v_owner;
  END IF;
END LOOP;
```
