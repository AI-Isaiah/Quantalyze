## What was built

- `services/native_to_usd.py`: `convert_native_returns_to_usd(series, unit, btc_closes)`. `unit is None` returns the SAME object; a unit with `btc_closes is None` returns an empty float series; otherwise day 0 is dropped and each later day is emitted only when every calendar day in the interval holds a usable close. Plus `parse_native_unit` (the TypeScript `^[A-Z]{2,10}$` rule, via `fullmatch` so a trailing newline is refused), `native_units_by_id` (reads `data_quality_flags.native_unit` off the SAME analytics row that carries `returns_series`), `UsdSeriesConverter` and `usd_equity_from_converted_returns`.
- `services/benchmark.get_btc_closes()`: every stored BTC `close_price` row, keyset-paged newest first (strictly decreasing across pages, the TypeScript `readBenchmarkPrices` rule), no bundled fixture, no completed-day trimming. A read error is `None` plus a WARNING (a non-DB error is ERROR plus a Sentry capture, the module's convention); an empty table or no usable close is `None`. `BTC_CLOSES_SOURCE = "benchmark_prices only"` is asserted equal to the fixture's `closes_source`.
- Converted sites, by function name:
  - `routers/portfolio.py::_compute_portfolio_analytics` (the select gains `data_quality_flags`; the converted dict feeds the weighted `portfolio_returns_series`, the correlation / rolling correlation / covariance risk decomposition, the equity curve, Sharpe, period returns and the attribution; per-strategy TWR rebuilt from converted returns)
  - `routers/portfolio.py::portfolio_optimizer` (portfolio series and published candidates, one closes read)
  - `routers/portfolio.py::portfolio_bridge` (portfolio series incl. the incumbent, and candidates; an unconvertible incumbent takes the existing `incumbent_no_data` path)
  - `routers/simulator.py::portfolio_simulator` (constituents and the candidate; an unconvertible candidate takes the existing 400 "Candidate has no returns history")
  - `routers/match.py::_score_one_allocator` (book, candidates, and the `compute_holding_flags` call that weights the same book), fed by `_load_allocator_context` and `_load_candidate_universe`, which now select `data_quality_flags` and carry `native_units`

### Plan-vs-reality choices (documented, not bugs)

1. **Scope beyond the three named sites in `routers/portfolio.py`.** The plan says to convert "every other site in `routers/portfolio.py` that puts a strategy series into a weighted sum". That is `portfolio_optimizer` and `portfolio_bridge` (listed above), and each got its own test and neuter proof, which the plan did not name.
2. **Per-strategy TWR for attribution.** The plan's truth says attribution never blends raw BTC returns, but the stored `equity_curve` of a native account is in the native unit and feeds `strategy_twrs`. It is rebuilt from the converted returns (`usd_equity_from_converted_returns`), with its own test and neuter.
3. **The portfolio tests live in `test_portfolio_router_logic.py`, as declared, but borrow the supabase mock builder `_make_supabase_for_compute` from `test_portfolio_compute_integration.py`** (imported, not copied; that file is not in `files_modified` and is unchanged). Its tests still pass.
4. **The plan names `AsyncMock`-style closes injection as "fetched once per request".** For `match.py` a "request" is a cron run, so the converter is memoised on the `universe` dict (`universe["_usd_converter"]`); the closes are read once per universe, not once per allocator.
5. **Branch name.** The orchestrator prescribed `wt/164.6.6.2-p13`, which is outside the executor's default `agent-*` allow-list; HEAD was never on a protected branch, so commits proceeded under the orchestrator's instruction.

## Observations recorded, NOT fixed (out of this plan's scope)

- `routers/portfolio.py::verify_strategy` correlates the verified exchange series against every published strategy's `returns_series` with `dispersing_corrwith`. That is a correlation match, not a weighted sum, so it was left as is; a native-unit candidate's raw BTC returns are correlated there. Worth a decision whether the match should use converted returns.
- `_compute_portfolio_analytics` sums `strategy_analytics.total_aum` across strategies for the portfolio `total_aum`. If a native-unit account's `total_aum` is in its native unit, that sum mixes units. This plan converts return series only; the unit of `total_aum` is plan 03's / the ingestion side's question.
- `data_quality_flags.native_unit` is WRITTEN by plan 03 (running concurrently). Until it lands on a row, every converter call here is a no-op and every site behaves exactly as before.
- Interpretation of `returns_series` at each site: all converted sites treat it as DAILY RETURNS (a `{date, value}` list of per-day returns); none treats it as a wealth index, so the converter was fed the existing series unchanged. Nothing looked wrong.
- The TypeScript fixture case `dropped_close_is_never_bridged` needs no separate handling in Python: `get_btc_closes()` omits a dropped date, and the "every calendar day has a usable close" rule refuses to bridge it. The Python test asserts the fixture's invariant that a `dropped` date is never in `closes`.
