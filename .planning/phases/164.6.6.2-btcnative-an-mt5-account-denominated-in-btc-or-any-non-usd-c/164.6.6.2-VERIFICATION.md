## CR-01 and D-23, stated plainly

D-23 is **not met in substance and I am not calling it met.**

- **What is true.** The Python twin exists (`services/native_to_usd.py`), is pinned to the same hand-computed 0.21 oracle as the TypeScript function, and both runtimes pass it (28 vitest, 43 pytest). The arithmetic and the pairing rule match on return-shaped input. Every Python blend seam the founder named calls it.
- **What is false.** Every one of those seams hands the twin `strategy_analytics.returns_series`, which `services/metrics.py` stores as `(1 + r).cumprod()` (a wealth index, first value near 1.0). The TypeScript side first converts that curve to daily returns (`resolveDailyReturnSeries`) and then converts to USD. The Python side converts the levels directly. For a BTC leg whose wealth index reads 1.30 on a day BTC rose 1%, the Python twin emits (1 + 1.30) x 1.01 - 1 = +132% for that one day. So the two runtimes disagree on every native leg, which is precisely the property D-23's "one function per runtime with one shared oracle" was meant to guarantee. The shared oracle cannot see it because every Python router test builds `returns_series` from return-shaped literals, and the oracle's input is returns by construction.
- **Pre-existing and wider than this phase.** The same misreading already mis-weights USD legs in the simulator, match, optimizer and bridge (PROD measured 2026-10-07 across 32 rows: first value about 1.0, last values averaging about 209k). This phase did not introduce it; it built a conversion on top of it and its plan-13 SUMMARY recorded "Nothing looked wrong". On PROD today `_compute_portfolio_analytics` cannot complete at all (it selects two columns that do not exist), so that seam has never run on real data.
- **Routing.** Founder 2026-10-07 routed the fix to Phase 164.6.6.2.2. That phase is in the ROADMAP at HEAD with a goal that names this defect, so the item is deferred, not a gap. It does not change this phase's status (Step 9b), but the founder should explicitly accept that BTCNATIVE ships with the Python D-23 half known-wrong on real data (listed under `human_verification`).
- **Blast radius to keep in mind.** The factsheet, share card, tear sheet, scenario composer, shared scenario page, allocator dashboard and portfolio page all use the TypeScript seams and are not affected. Only the analytics-service blends (simulator before/after, match personalization, optimizer, bridge, portfolio analytics) are. A BTC leg's own metrics (the thing MM-2x's client is waiting on) are not affected either.
