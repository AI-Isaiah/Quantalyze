## Summary

The TypeScript side of the conversion holds up. `convertNativeReturnsToUsd` is applied exactly once on
every TS seam I traced:

- **Dashboard query:** converts server-side. The composer then takes a book leg's `daily_returns` as delivered.
- **Returns route:** emits `daily_returns_usd`. The composer blends that series for a lazy native leg and
  never blends the raw series.
- **Share resolver:** converts per leg, reading the RPC's raw series.
- **Portfolio page:** converts a BTC constituent's resolved daily series before the cumulative product.

All of them read one DB-only `readBtcCloses` window, and `benchmark_prices` has a `USING (true)` SELECT
policy, so every client used can read it. On my reading, the arithmetic and the pairing rule of the Python
twin match `alignCoveredReturns` with the 7-day calendar. Dropped, non-positive and missing closes are all
treated as unpriced, and day 0 is dropped.

The disclosure reads are also clean. The OG route, `generateMetadata`, the tear sheet, the returns route,
the share page and the portfolio page each keep only `parseReturnsUnit(...)`. `strategy_analytics` has no
column-level revokes, so the published-only reads can reach `data_quality_flags`. The tear sheet logs when
its read fails.

The defects are on the Python side and in persisted state:

- **CR-01 (the main one).** The Python D-23 seams convert `strategy_analytics.returns_series`. That column
  holds the cumprod wealth index, not daily returns. So the Python twin does not compute what the TS twin
  computes for the same strategy, and the shared oracle cannot catch it because every Python router test
  feeds return-shaped values.
- **WR-01.** The new `api_keys.account_currency` column can be written by an authenticated client INSERT.
  The column COMMENT says it cannot, and D-03 treats the stored value as the authority.
- **WR-02.** A native account's pre-phase `value_usd` backfill rows survive, because the new skip returns
  an empty window that the atomic replace refuses to apply.
- **WR-03.** The simulator and match routers throw away the list of unconvertible series.

Pre-existing context. This is not a finding against this phase, but it bounds what CR-01 means in
practice. `_compute_portfolio_analytics` selects `equity_curve, total_aum` from `strategy_analytics`
(`routers/portfolio.py:779-781`). Neither column exists on that table: the column list in
`supabase/schema/baseline.sql` has neither. So that function cannot complete against PROD, and the
D-23 seam the phase added there, including `usd_equity_from_converted_returns`, has never run on real

## Critical Issues

### CR-01: The Python twin converts a wealth index as if it were daily returns, so D-23's USD blend is not what the TS twin computes [HIGH, confidence 7]

**Files:** `analytics-service/routers/simulator.py:402,428-437`, `analytics-service/routers/match.py:1122-1139`,
`analytics-service/routers/portfolio.py:805,844-868,1812-1834,2108-2128`,
`analytics-service/services/native_to_usd.py:90-134,223-239`

**Issue:** Every D-23 seam builds its input as `_records_to_series(row["returns_series"])` and passes it to
`UsdSeriesConverter.convert`. The analytics writer stores `returns_series` as the cumulative wealth curve,
not as daily returns:

- **Geometric:** `services/metrics.py:1829` computes `cumulative = (1 + returns_for_chart).cumprod()`.
- **Arithmetic:** `:1762` computes `cumulative = 1.0 + _cumsum`.
- **Persist:** `:2048-2051` writes `returns_series = [{date, value: cumulative}]`. The same fact is recorded
  in `src/lib/factsheet/resolve-series.ts` and in the TODOS Phase-147 audit.

The TS twin first differences that curve (`resolveDailyReturnSeries`, then `equityCurveToDailyReturns`) and
converts the result. The Python twin converts the levels directly.

Failure scenario: take a BTC strategy whose wealth index reads 1.30 on day k, with BTC up 1% that day. The
Python twin emits a "USD return" of (1 + 1.30) x 1.01 - 1 = 1.323, which is +132% for one day, and
weights it in:

- the simulator's before/after blend;
- the match engine's personalized portfolio series and the candidate scoring;
- the optimizer and bridge.

The TS dashboard, composer and share card blend roughly 0.01 for the same leg and the same day. So the two
runtimes disagree on every native leg, which is the exact property D-23's "one shared oracle" was meant to
guarantee. On the portfolio path, `usd_equity_from_converted_returns` then compounds these values into
`prod(1 + ~1.x)`, an attribution TWR on the order of 2^n.

The root is older than this phase. Every Python router reads `returns_series` as returns, so USD legs are
already mis-weighted. But this phase built a conversion on top of that reading and recorded in plan 13's
SUMMARY that "none treats it as a wealth index ... Nothing looked wrong." The tests cannot see the problem:
`tests/test_portfolio_router_logic.py` (`_recs`), `test_simulator_router.py` and `test_match_router.py`
build `returns_series` from daily-return literals, which is not the shape PROD stores.

**Fix:** Convert levels to returns once, at the shared boundary, before any blend or conversion. Use a
Python twin of `equityCurveToDailyReturns`: strictly positive, finite levels, sorted, `curr/prev - 1`.
Feed that to `UsdSeriesConverter` and to the weighted sums. Then rebuild the router fixtures from a wealth
curve, so a test goes red if anything weights a level:

```python
def wealth_to_daily_returns(levels: pd.Series | None) -> pd.Series | None:
    if levels is None:
        return None
    s = pd.to_numeric(levels, errors="coerce").sort_index()
    s = s[np.isfinite(s) & (s > 0)]
    if len(s) < 2:
        return None
    return (s / s.shift(1) - 1.0).iloc[1:].rename(levels.name)

# at each seam:
s = wealth_to_daily_returns(_records_to_series(row.get("returns_series"), name=sid))
```

Because this also changes the USD legs, it is a founder-visible behaviour change to the Python blends.
Route it as such, not as a silent fix inside this phase. The scope decision is out of the reviewer's
hands, but the phase's D-23 claim cannot be marked delivered while the twin is fed levels.

## Warnings

### WR-01: `api_keys.account_currency` and `account_balance_native` can be written by an authenticated client INSERT, and D-03 trusts the stored value [MEDIUM, confidence 6]

**Files:** `supabase/migrations/20261007120000_api_keys_account_currency.sql:52-54,77-94,120-131`;
`analytics-service/services/job_worker.py:5434-5453`

**Issue:** The migration verifies that anon and authenticated cannot SELECT the new columns. It does not
check write privilege. `authenticated` keeps table-level INSERT on `api_keys`, and that is deliberate:
`20260810120000_lock_api_keys_exchange_column.sql:187` RAISEs if INSERT is lost, because the browser
performs the key INSERT itself. A table-level INSERT grant covers columns added later. So any signed-in
user can create their own key row with `account_currency = 'EUR'` (the CHECK accepts any
`^[A-Z]{2,10}$`) and an arbitrary `account_balance_native`.

The column COMMENT says "Written only by the analytics worker's derive (service role); no client INSERT
or UPDATE path exists". That is false. The D-03 guard reads that column as the authority: `ctx.key_row`
comes from `select("*")`, and the derive refuses whenever the live currency differs from the stored one.

Failure scenario: a user, or a buggy future connect flow that spreads a payload into the insert, inserts
an MT5 key carrying a seeded `account_currency` that does not match the account. Every derive then ends
`transient` with "the MT5 account currency differs from the one stored", and nothing ever writes a
series. With UPDATE revoked, the row can never be corrected from the client. The blast radius is the
user's own key, the same shape as the documented `exchange` residual. But the worker's guard is built on
a value it believes only it can write.

**Fix:** Close the write path on the two worker-owned columns. Column-level REVOKE cannot subtract from a
table grant, so use the venue-lock pattern this table already uses, a BEFORE INSERT trigger that forces
them to NULL for non-service callers:

```sql
CREATE OR REPLACE FUNCTION public.api_keys_worker_owned_columns_null_on_client_insert()
RETURNS trigger LANGUAGE plpgsql SECURITY INVOKER SET search_path = '' AS $$
BEGIN
  IF current_user IN ('anon', 'authenticated') THEN
    NEW.account_currency := NULL;
    NEW.account_balance_native := NULL;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER api_keys_worker_owned_columns BEFORE INSERT ON public.api_keys
  FOR EACH ROW EXECUTE FUNCTION public.api_keys_worker_owned_columns_null_on_client_insert();
```

Also correct the COMMENT, and add a post-verify arm for the trigger. Alternatively, make D-03 ignore a
stored value the worker did not write, for example by pairing it with a worker-only timestamp.

### WR-02: The backfill's native-unit skip leaves earlier BTC-as-dollars `value_usd` rows in place [MEDIUM, confidence 5]

**Files:** `analytics-service/services/equity_reconstruction.py:3247-3289` (new skip) and
`:3630-3645,3700-3703` (empty-window disposition)

**Issue:** The skip returns `([], False, telemetry)` for a native, unsupported or malformed currency. The
shared persist half treats empty `rows` as `reconstruct_no_data`. On the sole-key path, the atomic replace
refuses an empty replace when history exists (`EmptyReplaceRefusedError` → `purge_refused`), so nothing
is deleted.

`_mt5_fetch_window` already backfilled MT5 allocator keys before this phase, and it assumed USD. A
BTC-denominated MT5 allocator key backfilled before deploy therefore keeps rows whose `value_usd` is the
BTC balance, for example 0.11 stored as $0.11. These rows stay on `allocator_equity_snapshots`, and every
later backfill keeps them, because the skip runs before any row is built. D-13 says a non-USD key is
"skipped honestly" with a named reason, but the stale curve is still there beside the new note. This is
a unit-mixing defect in a USD field: focus area 2, "value_usd backfill rows".

Failure scenario: an allocator connected a BTC MT5 key before this deploy. Their legacy equity chart keeps
a flat near-$0 line for that key indefinitely, and nothing tells them it is a BTC balance.

**Fix:** For the native, unsupported and malformed arms, purge the key's existing
`allocator_equity_snapshots` explicitly. That is an honest replace-with-nothing, scoped to the one key, so
it is not the "empty replace" the guard exists to refuse. Or return a distinct disposition that the
persist half turns into that purge. First, measure on PROD whether any MT5 key with a non-USD
`account_currency` has snapshot rows. If none do, record that reading and downgrade this finding.

### WR-03: The simulator and match routers discard the unconvertible-series list, so a BTC leg that could not be priced vanishes without any sign in the response [MEDIUM, confidence 5]

**Files:** `analytics-service/routers/simulator.py:415,433-437`; `analytics-service/routers/match.py:1134-1139`

**Issue:** `UsdSeriesConverter.convert` returns `(map, dropped)`. `portfolio.py` (all three seams) adds
`dropped` to its missing-returns telemetry. `simulator.py` and `match.py` bind it to `_`, and the only
trace is the converter's WARNING log.

In the simulator, a BTC constituent with no priced interval is removed from `portfolio_returns` while its
entry in `weights` stays. The before/after comparison is then computed on a book that silently lacks that
leg. The candidate arm also turns "no BTC price source" into "Candidate has no returns history", a
different and wrong cause. In match, a BTC holding drops out of the personalized portfolio series that
scores every candidate, and nothing persisted says so.

Failure scenario: `benchmark_prices` cannot be read, or holds no close covering the strategy window. A
user simulating "add X" to a book containing MM-2x gets a confident before/after that excludes MM-2x,
with no partial-data signal. This is focus area 5: a silent fallback that changes the numbers shown.

**Fix:** Carry `dropped` into the same channel the portfolio router uses. For example, return a
`missing_returns_strategy_ids` or `unpriced_native_ids` field in the simulator response and name the
cause in the candidate error. In match, add the ids to the run's telemetry or audit row. Neither router
should continue as if the leg had no history.
