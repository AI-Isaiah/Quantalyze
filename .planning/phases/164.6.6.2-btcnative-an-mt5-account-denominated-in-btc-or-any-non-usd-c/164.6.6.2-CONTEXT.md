# Phase 164.6.6.2: BTCNATIVE — an MT5 account denominated in BTC reports its returns in its own unit - Context

**Gathered:** 2026-10-07
**Status:** Ready for planning

<domain>
## Phase Boundary

An MT5 account whose deposit currency is BTC reports its NAV, returns and drawdown in BTC, and the
factsheet says so. Today the MT5 path assumes a USD-family account, so a BTC-sized balance is read as
dollars. It falls under `nav_twr.py` `DUST_NAV_FLOOR` (1000, a USD floor) and every daily return
becomes a dust break.

**Measured on PROD 2026-10-07 (marker query first, read-only):** MM-2x
(`source = wizard`, one `mt5` key created 2026-10-03) has `strategy_analytics.computation_status =
complete_with_warnings`, `cumulative_return = 0.0`, `max_drawdown = 0.0` and `data_quality_flags =
{csv_source: true, dust_nav_guard: true, insufficient_window: true}`, computed 2026-10-06 18:25 UTC.
`csv_source` is stamped by the CSV analytics run (`analytics_runner.py`, `job_worker.py` pre-stamp)
that every `csv_daily_returns` series goes through, MT5's included; it is not a CSV upload. A client is waiting on MM-2x.

**In scope:** BTC (native unit) only. The founder's 2026-10-06 order: "BTC only first, USD later".
The USD view of a native-unit account is a separate follow-up phase (D-15).

**Out of scope:** the USD view; Deribit and every non-MT5 venue; non-USD currencies other than BTC
(they are refused by name, D-06).

</domain>

<decisions>
## Implementation Decisions

All 16 answers below were the recommended ones, accepted by the founder 2026-10-07 (AskUserQuestion,
four areas, "Accept all" on each).

### Capturing the account's currency
- **D-01:** The currency comes from `account_info().currency` on every derive and backfill read.
  `Mt5Client.account_info()` already returns it, so no new RPC is needed. It is parsed with the
  existing validator in `allocator_positions.py` `_fetch_mt5_account_rows`: blank means a transient
  error, a non-code means refuse, otherwise an uppercase code.
- **D-02:** It is stored in a new nullable text column `api_keys.account_currency`, written by
  derive. The factsheet reads the unit from the strategy's key.
- **D-03:** A currency change between reads (the broker re-denominates) fails loud. Log ERROR, end in
  a transient failure, keep the existing series, and never mix units in one series.
- **D-04:** "USD" means the `USD_FAMILY` set the code already uses (`external_flows.py`: USD, USDC,
  USDT, EURR, DAI). Behaviour for those is unchanged. Every other currency is "native".

### The dust floor and the other USD-sized thresholds
- **D-05:** The dust floor is per currency, in native units: BTC 0.01 (about the $1000 USD floor at
  today's prices). The USD family stays at 1000.
- **D-06:** A non-USD currency with no floor defined (EUR, ETH, and so on) is refused. Its metrics
  stay null and a named data-quality flag says the unit isn't supported yet. Never guess.
- **D-07:** The other USD-sized thresholds on the MT5 path use the same per-currency table, so a
  broken key holding 5 BTC still fails loud. These are the material-equity fail-loud ($100,
  `_DERIBIT_EMPTY_LEDGER_FLOOR_USD`), the history-settle materiality (`mt5_read.py`
  `material_equity_floor_usd`) and the uPnL materiality (`nav_twr.py`, `job_worker.py`).
- **D-08:** A native-unit series is flagged with `data_quality_flags.native_unit: "BTC"`. The
  factsheet reads it, and it is not a warning.

### What the factsheet shows for a BTC strategy
- **D-09:** The unit is shown as a "Returns in BTC" chip beside the strategy name, and as "in BTC" on
  the equity chart and on the return KPI labels.
- **D-10:** For a BTC-unit strategy, the BTC benchmark overlay and the alpha, beta and correlation
  against BTC are hidden. The comparisons show null with the reason "returns are in BTC". A
  BTC-in-BTC benchmark is a flat line, and USD against BTC mixes units.
- **D-11:** AUM and equity figures are shown in BTC (for example "2.41 BTC"), never with a `$` sign.
- **D-12:** The share card and the scenario numbers use the same unit label as the factsheet.

### The USD-only surfaces a BTC key would feed today
- **D-13:** A non-USD key is skipped honestly, with a named reason, in the allocator equity
  snapshots (`allocator_equity_snapshots.value_usd`) and on the allocator dashboard. This matches
  what the positions panel already does (`MT5_NON_USD_NOTE`). The USD-view follow-up fills it in.
- **D-14:** `api_keys.account_balance_usdt` stays null for a non-USD key, and the native balance is
  kept beside it. BTC is never written into a USD field. This also covers `ExternalFlow.usd_signed`
  and the `allocator_equity_derived` key_inputs `anchor_usd` / `flows`.
- **D-15:** The USD view (native NAV × the BTC benchmark price) is booked now as its own follow-up
  phase, Phase 164.6.6.2.1 BTCUSDVIEW (booked 2026-10-07).
- **D-16:** After deploy, MM-2x is fixed by re-running derive and analytics through the product's
  own paths, then reading the factsheet live on PROD.

### Answers to the UI-spec questions (founder, 2026-10-07, AskUserQuestion)
- **D-17 (E-1):** Only the BTC benchmark comparisons are hidden, exactly as D-10 says. The other
  USD-priced comparisons (SPX, the ETH/S&P/Gold/IEF correlations, the allocator blends, the peer
  percentile) stay visible as they are today. The founder chose this over the recommended "hide
  every USD comparison".
- **D-18 (E-2):** A BTC strategy DOES enter a scenario blend, converted to USD first. Founder's
  words: "blends but is calculate in USD. So BTC times BTC USD price = value and then you blend it."
  Its BTC value is multiplied by that day's BTC/USD price (the `benchmark_prices` BTC daily close the
  composer already reads), and the resulting USD series is what gets blended. A day without a BTC
  price is not invented: that day stays null for the BTC strategy, the same way the composer
  already treats a missing day. This is the scenario composer's USD conversion only. The
  persisted USD view (allocator snapshots, `account_balance_usdt`) stays in 164.6.6.2.1.
- **D-19 (E-3):** The "in BTC" chip on the strategy list surfaces (Discovery, `StrategyTable`) is
  booked into Phase 164.6.6.2.1 BTCUSDVIEW, not this phase.

### Answers to the research questions (founder, 2026-10-07, AskUserQuestion)
- **D-20 (supersedes D-05):** The BTC dust floor is **0.001 BTC** (about $100), not 0.01. Research
  measured MM-2x at just over 0.01 BTC on PROD, so with the D-05 floor its backward-rolled history
  would be dust-guarded again and the phase's own acceptance (D-16) would fail. Real dust is still
  guarded, and the USD-family floor stays 1000. D-05's line above is kept as lineage.
- **D-21 (deviation from D-11, founder override):** For a BTC strategy the AUM shows **`—`**. The
  factsheet AUM is the manager's declared `strategies.aum`, a USD figure, so labelling it BTC would
  be false, and the only BTC figure is the account's LIVE balance (`account_balance_native`), which
  the public factsheet has never disclosed. The capacity span and utilization bar are not drawn,
  and the tear sheet's Minimum Allocation shows `—` (UI-SPEC A12, B5). Recorded in the ROADMAP too.
- **D-22 (extends D-18):** The BTC × daily-BTC/USD-close conversion is ONE pure function, called
  everywhere a BTC strategy is blended with USD ones: the scenario composer, the shared-scenario
  resolver (`share-resolve.ts`), the portfolio page and the allocator dashboard queries. No surface
  blends raw BTC returns with USD returns.

- **D-23 (extends D-22, founder 2026-10-07, AskUserQuestion):** The planner found three more blends,
  in the analytics service: `routers/portfolio.py` `_compute_portfolio_analytics` (the portfolio
  page's portfolio-level TWR, Sharpe, attribution, risk and equity curve), `routers/simulator.py`
  (the add-a-candidate before/after blend) and `services/match_engine.py` (the personalized
  `portfolio_returns_series`). They convert too, through a Python twin of the conversion pinned to
  the same 0.21 oracle and a fixture shared with the TypeScript function. So it is one function per
  runtime with one shared oracle, the founder's reading of D-22's "ONE pure function".

- **D-24 (supersedes D-20's value, founder 2026-10-08, AskUserQuestion at plan 12 Task 3 Pitfall 1):** "it should measure more. at least to 0.0000001". The BTC `dust_nav` floor drops from 0.001 to **1e-7 BTC**, so the opening stretch of an account like MM-2x is measured, not guarded. Measured before the change: MM-2x read `dust_nav_guard` with 355 unguarded days (2025-10-18 onward) and every guarded day before that. `material_equity` and `residual_abs_tol` were orchestrator-scaled from D-20 (Claude's Discretion below) and are NOT founder values; whether they must move with the floor is measured in the gap-closure plan, never assumed. D-20's line above is kept as lineage.

- **D-25 (founder 2026-10-08, AskUserQuestion after the plan 14 review WR-01 / SFH M1):** with the floor at 1e-7, a day measured on a tiny base (e.g. after a near-total withdrawal while a winning position is open: +500%) is kept exact AND flagged: a visible "measured on a very small balance" warning whenever a measured day's starting balance is below the unit's `material_equity` (BTC 1e-4). The flag is informational: it never breaks the chain and never drops the day.
- **D-26 (founder 2026-10-08):** the supported phone widths are 360 px (small Android), 375 px (iPhone mini) and 390 px (iPhone 12/13/14) and up. 320 px is not a target; the UI-SPEC's 320 px backstops are superseded by 360 px.

### Claude's Discretion
- **Recorded 2026-10-07 after the plan check (orchestrator decisions, NOT founder decisions; an earlier
  planner draft attributed them to the founder, which was wrong):**
  - The BTC row's other two values are scaled from D-20 by the same ratio (0.001 / 1000 = 1e-6):
    `material_equity` 0.0001 BTC and `residual_abs_tol` 1e-6 BTC.
  - Key-mode treats an unsupported currency like a native one (anchor null, reason `native_unit`,
    no combine), following D-13's honest skip.
  - The tear sheet reads the unit through the OG route's existing published-only read;
    `PUBLIC_ANALYTICS_COLUMNS` is not widened.
  - `nativeAmount` is not built here (nothing calls it under D-21); it moves to 164.6.6.2.1 with
    its first caller.
  - **The positions poll keeps its existing USD test (`ccy != "USD"`) for valuation**, per D-04
    ("behaviour for those is unchanged"). The shared classifier is used there only for the blank,
    malformed and native decisions. USDT, USDC, EURR and DAI MT5 accounts stay skipped by the poll,
    as today; valuing EURR at a $1.00 mark would invent data.
  - Correlation-only consumers (`strategy_matching.find_matched_strategy`,
    `bridge_scoring.find_replacement_candidates`) and the unlabelled own-capital MTD
    (`getOwnCapitalStrategies`) are not blends. They are booked into 164.6.6.2.1 as known limits,
    not fixed here.
  - **Where the D-18/D-22 conversion runs (revision round 1):** server-side only, never in the
    browser. The returns route sends a converted `daily_returns_usd` field and the composer blends
    it; `ScenarioComposer.tsx` carries no conversion code. Every seam (dashboard query, portfolio
    page, returns route, share resolver, Python twin) reads the same DB-only `benchmark_prices`
    window, because the Python image cannot read the bundled `btc-daily.json`. This supersedes the
    UI-SPEC's "client composer" contract note; the founder's D-18 rule (BTC × that day's BTC/USD
    close, a missing day stays null) is unchanged.
- D-06 mechanics (research Open Question 3): the factsheet is built only for terminal-success
  statuses, so an unsupported currency ends as a failed analytics row with curated copy naming the
  unit, rather than a success row with null metrics.
- The key-mode anchor reason for a funded native key is a distinct `native_unit` token, never
  `"dust"`, and it is not added to `_NO_CAPITAL_ANCHOR_REASONS` (research Open Question 4).
- Deploy shape (research Open Question 6): a single PR, with the worker's write tolerant of the
  column not existing yet (`PGRST204`).
- The residual tolerance in `reconcile_flow_residual` (an absolute `max(1.00, …)`, missed by D-07)
  is per unit, from the same floor table.
- The shape of the per-currency floor table (a module constant next to `DUST_NAV_FLOOR`, or a small
  mapping in `external_flows.py`), as long as there is ONE table that every threshold in D-07 reads.
- How the unit reaches `chain_linked_twr` / `_guard_denominator`, for example a parameterised floor.
  The TWR arithmetic does not depend on the unit and must not be duplicated.

<code_context>
## Existing Code Insights

### Reusable Assets
- `Mt5Client.account_info()` (`analytics-service/services/mt5_client.py`) returns the whole MT5
  AccountInfo, `currency` included. `read_mt5_deal_ledger` (`services/mt5_read.py`) returns the PRE
  read as the economic anchor.
- The currency parse and validate block in `services/allocator_positions.py`
  (`_CURRENCY_CODE_RE`, `_fetch_mt5_account_rows`, `MT5_NON_USD_NOTE`).
- `nav_twr.reconstruct_nav_and_twr` / `chain_linked_twr`. The arithmetic does not depend on the
  unit; only `_guard_denominator`'s `DUST_NAV_FLOOR` and the materiality checks are USD-sized.
- `external_flows.USD_FAMILY` and `ExternalFlow.currency` / `.quantity`.
- `native_nav.py` (`classify_currency`, `MarkBranch`). ⚠️ `reconstruct_native_nav_and_twr` always
  marks to USD before TWR, so it IS the deferred USD view, not this phase's path.
- The `benchmark_prices` BTC daily closes (for the deferred USD view only).

### Established Patterns
- MT5 is in `_NATIVE_RETURNS_VENUES` (`job_worker.py`). "Native" there means the venue builds its
  own returns, not a native unit; do not conflate the two.
- Guard flags travel `NavTWRMeta` → the `data_quality_flags` pre-stamp in `job_worker.py` →
  `analytics_runner.py` → `strategy_analytics.data_quality_flags`.
- Never invent data: an uncomputable metric is null.

### Integration Points
- Derive: `job_worker.py` `run_derive_broker_dailies_job` reads `_mt5_info["equity"]` /
  `["balance"]`, and `broker_dailies.combine_mt5_deal_ledger` calls `reconstruct_nav_and_twr`.
- Backfill: `equity_reconstruction.py` reads `info["equity"]` / `["balance"]`, then
  `reconstruct_mt5_nav_levels` and `_mt5_rows_from_levels` (`value_usd`).
- Sync balance arm: `job_worker.py` `_fetch_mt5_account_balance` writes `account_balance_usdt`.
- Material-equity and dust uses: `job_worker.py` (anchor `dust` reason, the material-equity
  fail-loud, the wedge check), `mt5_read.py` (settle materiality), `nav_twr.py` (uPnL materiality).
- Factsheet: `src/lib/factsheet/fetch-and-build-payload.ts` (the `strategy_analytics` select and the
  `FactsheetPayload` type), `src/app/factsheet/[id]/v2/FactsheetView.tsx` (chip line,
  `formatUsdCompact` for AUM), the charts and the BTC benchmark comparators (`SignaturePanels.tsx`,
  `ComparatorPicker.tsx`, `EquityCurve.tsx`, `DrawdownChart.tsx`).
- Tests that pin the USD dust behaviour on MT5 (for example `tests/test_mt5_deal_reconstruction.py`)
  will need their premises re-read, not just their numbers.
- The `broker_dailies.py` docstring and `job_worker.py` comments state "MT5 is USD-family" as an
  invariant; correct them where this phase changes it.
