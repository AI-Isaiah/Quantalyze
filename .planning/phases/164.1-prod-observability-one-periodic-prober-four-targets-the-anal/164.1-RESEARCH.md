## Summary

The phase is one Node script (`scripts/prod-prober/run.mjs`) with four injectable seams — an HTTP fetcher, a SQL runner, an SSH runner and an env reader — driven hourly by a new workflow and by a `--self-test` mode that stubs each seam with a fault fixture and asserts the run exits 1 naming that arm. Every idiom the script needs already exists in this repo: the aggregate-then-exit defect table, the pinned `ARMS_FLOOR`, the `expect()` self-test helper and the vitest pin that reads `selfTest()`'s source for `kind === "…"` all live in `scripts/mutation-runner/run.mjs:4600-5225` and `src/__tests__/mutation-runner-floors.test.ts:596-720`; the hard-fail-on-absent-credential step lives in `.github/workflows/migration-drift-check.yml:91-108`; the dedup'd auto-issue lives in `analytics-deploy-verify.yml:158-215`.

Three findings change the plan's shape. **(1) Credentials:** only the two Supabase arms can run on secrets that exist today (`SUPABASE_ACCESS_TOKEN` + `SUPABASE_DB_PASSWORD` + `vars.SUPABASE_PROJECT_REF`, via `supabase link` and the session pooler the CLI writes to `supabase/.temp/pooler-url`). The PYAPI-06 arm needs a NEW `ANALYTICS_SERVICE_KEY` secret and the MT5 arm needs a NEW `RAILWAY_API_TOKEN` (workspace/account, not a project token) plus a NEW registered `RAILWAY_SSH_PRIVATE_KEY` — because `railway ssh` 4.x is native-SSH only and refuses project tokens. The workflow will be RED until the founder adds three secrets; that is the design, not a bug. **(2) CRON-OBS-01 correlation** is by TIME, not URL: `net._http_response` has no url column and `net.http_request_queue` rows are deleted on completion, so the arm joins each `cron.job_run_details` row of jobid 1 to response rows created inside its 60 s timeout; rows live only `pg_net.ttl` = 6 h by default, so the hourly cadence sees each tick roughly six times before it is pruned, and an arm that finds ZERO responses for a `succeeded` run must fail, not pass. **(3) PYAPI-06 blast radius** is concentrated in one file: eleven `describe` blocks in `src/lib/analytics-client.test.ts` set `INTERNAL_API_TOKEN` but not `ANALYTICS_SERVICE_KEY` and drive the real seam through a stubbed fetch — a throw on the absent key reddens all of them until each `beforeEach` sets the key. Route tests are unaffected (all mock the client wholesale). On the Python side three test files pin the absent-header body to `{"detail": "Unauthorized"}` and must move with the new code.

One conflict must be surfaced rather than averaged (Rule 7): the locked decision says "exit non-zero (red workflow run), reusing the auto-issue pattern in `analytics-deploy-verify.yml`", but that file's own header (`:17-25`) records that a red check on main HEAD made Railway SKIP the deploy on 2026-06-21 — a red hourly prober would block the deploy of the very fix it is asking for. See Pitfall 1 for the recommended resolution (script exit 1 is the contract and is self-tested; the workflow layer must be designed so Railway's wait-for-CI cannot read it as the commit's check-suite failing).

**Primary recommendation:** Build `scripts/prod-prober/run.mjs` as a port of `mutation-runner/run.mjs`'s skeleton (seams → arms → defects → floors → summary → exit), prove each arm with a `--self-test` scenario before the live run in the same job, read PROD through `supabase link` + psql session pooler with `PGPASSWORD`, and reach MT5 with `railway ssh --service mt5-gateway -- python3 -c …` exactly as `scripts/mt5-diag.sh:45` already does.

## Finding 2 — CRON-OBS-01 mechanics

**Shape of `net._http_response`** `[CITED: github.com/supabase/pg_net README]`: `id bigint`, `status_code integer`, `content_type text`, `headers jsonb`, `content text`, `timed_out boolean`, `error_msg text`, `created timestamptz default now()`. There is NO url, method or request-body column. `net.http_request_queue` holds `url`/`headers`/`body` only until the worker executes the request, then the row is deleted `[CITED: supabase.com/docs/guides/database/extensions/pg_net]`. So a completed response cannot be joined back to a URL.

**Retention.** `pg_net.ttl` defaults to `6 hours`; the worker deletes older rows lazily "while its processing requests", and changing it needs `ALTER SYSTEM` (superuser — on Supabase, contact support) `[CITED: pg_net README; Supabase pg_net docs]`. Consequence: with jobid 1 hourly, at most ~6 response rows exist at any time, and an hourly prober sees each tick before it is pruned. A daily prober would be blind to 18 of 24 ticks. Do NOT assume the TTL: the arm should `SELECT current_setting('pg_net.ttl', true)` and print it `[ASSUMED: readable by `postgres`; verify on first live run]`.

**Correlation to a job.** Only ONE job in the repo issues `net.http_post`: `match_engine_cron` (`20260408113029_cron_heartbeat.sql:166` and `20260408215026_schedule_match_cron_hourly.sql:69`; no other migration calls `net.http_get`/`http_post`/`supabase_functions.http_request` `[VERIFIED: grep over supabase/migrations]`). PROD jobid 1 IS `match_engine_cron` `[VERIFIED: TODOS.md:1735-1746, measured 2026-09-01]`. Therefore every `_http_response` row is attributable to jobid 1 **as long as CRON-DRIFT-01 holds** (an extra job that posts would break the attribution — which is why the two arms ship together). Join by time window:

- for each `cron.job_run_details` row with `jobid = 1` and `start_time > now() - interval '3 hours'`: expect ≥1 `_http_response` row with `created BETWEEN start_time AND start_time + interval '90 seconds'` (60 000 ms request timeout `[VERIFIED: 20260408215026:75]` + slack);
- a run with ZERO matching responses inside the TTL window is a DEFECT ("enqueued, never answered") — this is the vacuity hole an `WHERE status_code >= 400` query would sail through;
- any matched row with `status_code NOT BETWEEN 200 AND 299`, or `timed_out`, or `error_msg IS NOT NULL` is a DEFECT that prints `id`, `status_code`, `created` and the first 200 chars of `content` (the 401 body is `{"detail":"Unauthorized"}`, the 200 body `{"status":"ok","processed":N,…}` `[VERIFIED: TODOS.md:1737,1744]`); never print `headers` (may echo the request context).
- `cron.job_run_details` is NOT cleaned automatically `[CITED: Supabase cron quickstart]`; bound the scan by `start_time`, never full-table.

`cron.job_run_details.status = 'succeeded'` remains meaningless for this job (standing rule, `TODOS.md:1776-1777`); the arm must never treat it as a pass signal.

## Finding 3 — CRON-DRIFT-01 oracle

**What the migrations say, and why they cannot be the oracle.** Both scheduling migrations build the command on `current_setting('app.analytics_service_url'/'app.analytics_service_key', true)` and SKIP scheduling when those GUCs are unset (`20260408113029:145-150`, `20260408215026:49-54`). Setting them needs `ALTER DATABASE … SET` on a placeholder GUC → 42501 on Supabase `[VERIFIED: TODOS.md:1753-1757]`. So on PROD those DO blocks either skipped (writing a `cron_runs` error sentinel) or the job was later hand-scheduled — which is what happened: jobid 1 carried a hardcoded URL and an INLINE key until 2026-09-01, then was re-scheduled onto "a `DO` block that reads `vault.decrypted_secrets`" `[VERIFIED: TODOS.md:1740-1750]`. Nothing in the repo records that command text (`grep decrypted_secrets` hits only `TODOS.md:1743` `[VERIFIED]`).

**What is achievable.** Vault exposes `vault.decrypted_secrets` (`id, name, description, secret, decrypted_secret, key_id, nonce, created_at, updated_at`) and `vault.create_secret(value, name, description)`; whoever can SELECT the view reads plaintext, so grants are the control `[CITED: supabase.com/docs/guides/database/vault]`. The secret already exists on PROD as `analytics_service_key`, described "X-Service-Key for match_engine_cron (cron.job jobid 1)" `[VERIFIED: TODOS.md:1740-1742]`. The achievable command shape (the ONE that can run under the `postgres` role) is therefore:

```sql
-- shape only — the committed manifest holds the EXACT text captured from PROD
DO $$
DECLARE k text; u text;
BEGIN
  SELECT decrypted_secret INTO k FROM vault.decrypted_secrets WHERE name = 'analytics_service_key';
  u := '<analytics base url>';   -- or a second vault secret
  PERFORM net.http_post(
    url := u || '/api/match/cron-recompute',
    headers := jsonb_build_object('Content-Type','application/json','X-Service-Key', k),
    body := '{}'::jsonb, timeout_milliseconds := 60000);
END $$;
```
`[ASSUMED shape — the live jobid-1 command has not been read this session; the manifest capture (Wave 0) replaces this with the real text]`.

**What the manifest is.** A committed file (recommend `scripts/prod-prober/cron-manifest.json`) captured FROM PROD by a `--capture-manifest` mode, containing for every row of `cron.job`: `jobid`, `jobname`, `schedule`, `active`, `database`, `username`, `command_sha256`, and the normalized `command` text ONLY when it contains no secret (an assertion, see below) plus `captured_at` and the `shobj_description` project marker. Comparison = set equality on `jobname`, then per-job equality of `schedule`, `active`, `command_sha256`. `cron.job` columns: `jobid, schedule, command, nodename, nodeport, database, username` `[CITED: pg_cron README]`, plus `jobname` and `active` on pg_cron ≥1.4 as used by every migration here (`WHERE jobname = …`, `20260408215026:57`) `[VERIFIED: in-repo usage]`.

**Secret hygiene assertions the arm itself makes on jobid 1's command text** (these are what make the oracle "achievable" rather than merely "whatever PROD has"):
- MUST contain `vault.decrypted_secrets` (or `vault.` at minimum);
- MUST NOT contain `'X-Service-Key', '` followed by a literal (the pre-2026-09-01 inline-key shape);
- MUST NOT contain `current_setting('app.` (the unrunnable GUC shape).

### Pattern 1: Injectable seams, single verdict loop
**What:** `runProber` receives `{fetchImpl, sqlRunner, sshRunner, env}`; arms never touch `process.env`/`fetch`/`spawnSync` directly. **When:** always — it is what makes `--self-test` a real run of the real verdict loop rather than a unit test of helpers (the `mutation-runner` 164.3.1-10 lesson, `run.mjs:3722-3728`).

### Pattern 2: Hard-fail credential step in the workflow AND in the script
**What:** `migration-drift-check.yml:91-108` idiom — list every missing secret in one `::error`, `exit 1`, no `if:` that could make the step not run. **Why both:** the workflow step catches a mis-wired `env:` block; the script's own gate catches a local run and is what the self-test proves.

### Pattern 3: Red must isolate one kind
**What:** `lint-sql-gates.mjs:1329-1340` — a red fixture must fire its rule and NOTHING else. **Why here:** criterion 3 (-10004 ≠ -10005) is exactly this property.

- **Reading `cron.job_run_details.status`** as evidence — standing rule `TODOS.md:1776`.
- **Deriving the cron oracle from migrations** — locked out; the GUC design never ran on Supabase.
- **`login()` in the MT5 probe** — re-breaks `[Experts] Enabled` (`mt5-diag.sh:9-15`).
- **A module-load assertion for `ANALYTICS_SERVICE_KEY`** — rejected in CONTEXT; breaks build/import paths.
- **Dedenting the Sentry capture out of `if provided:`** — `main.py:826-832` and `test_service_key_log_companion.py:127-146` both forbid it.

## Common Pitfalls

### Pitfall 1: A red hourly run on main HEAD can BLOCK the Railway deploy that fixes it
**What goes wrong:** `analytics-deploy-verify.yml:17-25` records (2026-06-21) that a failed check on the main-HEAD commit made Railway's wait-for-CI treat the check-suite as red and SKIP the analytics deploy; `phase-19-stability.yml` avoids it only because it rarely fails. A PYAPI-06 outage would then red every hourly run on HEAD, and the merge carrying the fix inherits a red suite… until the next commit. **Why it conflicts:** the locked decision wants exit non-zero AND cites that very file as precedent. **How to handle (recommendation, planner decides):** keep exit 1 as the SCRIPT contract (self-tested, mode-identical locally), and in the WORKFLOW confirm by measurement whether Railway's "wait for CI" counts scheduled-run check-runs on that SHA (Wave 0: dispatch a deliberately failing run against a throwaway commit and read Railway's deploy `skippedReason`). If it does, the workflow surfaces failure through the dedup'd issue + `::error` and a job-summary while keeping the check green (the documented `analytics-deploy-verify` posture), and the RED signal is the issue, not the check. If it does not, exit non-zero as decided. Do not average the two: pick one after measuring, and record the reading in the workflow header. `[VERIFIED: analytics-deploy-verify.yml:17-25; memory: Railway waits on main CI and SKIPS if red]`

### Pitfall 2: `net._http_response` rows vanish after ~6 h
Hourly probing is what makes the TTL survivable; a run that finds zero responses for a `succeeded` jobid-1 run must fail as `cron-no-observation`, never pass as "no non-2xx rows". Print `pg_net.ttl` each run.

### Pitfall 3: Reddening `analytics-client.test.ts`
Eleven describe blocks (§F5) run the real seam with no key. Add the key to each `beforeEach` in the SAME commit as the throw, or the suite goes red for an unrelated-looking reason. Set env BEFORE the dynamic import (`:883-889`).

### Pitfall 4: `railway ssh` refuses project tokens, and prompts when no registered key is found
Use `RAILWAY_API_TOKEN` (workspace/account) and pass `-i ~/.ssh/id_ed25519`; feed `< /dev/null` so PTY autodetect stays off; wrap in `timeout 120`. A prompt in CI must FAIL fast, not hang until `timeout-minutes`.

### Pitfall 5: Secrets in `cron.job.command` reaching a public log
The pre-2026-09-01 jobid 1 carried an inline key. The drift arm must hygiene-assert BEFORE printing any command text, and print sha256 only when the assertion fails. `--capture-manifest` must refuse to write a command that fails the assertion.

### Pitfall 6: Unpinned Railway CLI in CI
`bash <(curl -fsSL cli.new)` installs latest; the ssh code path just changed (native-only). ### Pitfall 7: The guarded GET has a real cost and a real limiter
`/api/match/eval` computes hit-rate metrics and is limited 30/min per tenant/platform (`match.py:1855-1861`). Three calls per hour is trivial, but `lookback_days=1` keeps it cheap; do not loop on retries.

### Pitfall 8: `psql` exit status vs empty output
`psql -At` prints nothing for zero rows AND for a permissions error if `ON_ERROR_STOP` is off. Always `-v ON_ERROR_STOP=1`, check the exit status, and treat non-zero as `MEASURE_FAIL` for that arm (a distinct kind), never as zero rows.

### Pitfall 9: `[ci skip]`-class tokens and `-pr` branch deletion guard
Memory: a `[ci skip]` anywhere in a commit body suppresses checks; the `/gsd-pr-branch` deletion guard is mandatory. Standard ship hygiene, restated because this phase adds a workflow whose first green run must be SHA-bound.

### Known Threat Patterns
| Pattern | STRIDE | Mitigation |
|---|---|---|
| Secret echoed into a public Actions log (`cron.job.command`, `_http_response.headers`, env values) | Information disclosure | Hygiene assertions before print; never print headers; name secrets, never values (`main.py:196-220` rule) |
| Prober's own key mismatch reads as a PROD outage | Repudiation | The three-request control distinguishes "our key wrong" (keyed 401 + wrong-key 401 + absent 401+code) from "server accepts anything" |
| Over-scoped Railway account token in repo secret | Elevation | Prefer workspace token; SSH key is CI-only and revocable via `railway ssh keys` |
| `railway ssh` exec = arbitrary code inside the gateway | Tampering | The command is a committed constant (base64 of a fixed block); no run-time interpolation of inputs |
