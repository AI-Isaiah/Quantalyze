### Additional Finding (Human Verification, Not a Roadmap Truth)

**The declared hourly cadence is not delivered by the platform, and this verifier's own broader measurement is worse than the orchestrator's flagged figure.**

`.github/workflows/prod-prober.yml:65` declares `cron: "0 * * * *"`. The comment immediately above states the cadence's purpose in absolute terms: *"A 6-hourly cadence would leave a 6h blind window on the exact defect that ran 401 for seven days behind a green cron history."*

Independently re-measured via `gh run list --workflow=prod-prober.yml`:
- **Orchestrator's window** (15 most recent `event == "schedule"` runs, 54.8 h span): median gap 3.96 h, max gap 5.81 h. Confirmed exactly by this verifier's own re-run of the same query.
- **This verifier's wider sample** (75 scheduled runs, 273.4 h span — expected 274 hourly ticks): **75 actual runs delivered (27%)**, median gap 3.28 h, **max gap 7.13 h** — which *exceeds* the 6-hour window the workflow's own comment names as the threshold this cadence exists to avoid.

This is a GitHub Actions platform behavior (scheduled workflows are best-effort and are throttled/dropped under platform load), not a defect in this phase's code — the prober's detection logic is correct and does exit non-zero whenever it runs (see Truth 1). No line of this phase's code controls GitHub's scheduler. But the phase's own stated rationale for choosing hourly over 6-hourly is measurably not what is being delivered, and the actual worst-case gap observed already meets-or-exceeds the exact blind window the design rejected as unacceptable. This is a detection-latency property of a production control (data-integrity/user-facing class per this repo's own scoping rule), so it is reported here as a human-verification item rather than silently accepted or inflated into a criterion-1 failure — criterion 1's literal text (non-zero exit per arm, no skip) is met regardless of cadence.
