<decisions>
## Implementation Decisions

### Prober substrate, cadence and failure surface
- Runs as a **GitHub Actions scheduled workflow** driving one script under
  `scripts/prod-prober/`. Rationale: `.github/workflows/analytics-deploy-verify.yml` is the
  existing prod-probe precedent on this repo and the credentials already exist as repo secrets.
  Rejected: a Railway sidecar (new deploy surface) and a pg_cron job (structurally blind to the
  MT5 and HTTP arms).
- **Hourly** (`0 * * * *`). PROD jobid 1 is hourly, so a 401 is caught within one tick; matches
  `phase-19-stability.yml`. A 6-hourly cadence would leave a 6h blind window on the exact defect
  that ran 401 for 7 days.
- A failing arm makes the **job exit non-zero** (red workflow run), reusing the auto-issue
  pattern already in `analytics-deploy-verify.yml`.
- **ALL four arms run every time**, each printing its own line; the run aggregates and exits 1 at
  the END. A first-failure exit is precisely the OPS-08-F8 defect and must not be reproduced.

### Anti-vacuity — every arm PROVEN to bite
- A **`--self-test` mode** injects each arm's fault against fixtures and asserts the non-zero exit
  NAMING that arm. This follows `scripts/mutation-runner/run.mjs`'s SELF-TEST discipline, which
  this project already trusts.
- **An absent credential is a HARD FAILURE, never a SKIP.** Success criterion 1 states a SKIP on
  an absent credential fails the criterion. The run prints WHICH credential is absent.
- **Read-only against PROD**: `net._http_response`, `cron.job`, one authenticated GET to the
  analytics service, one MT5 `terminal_info()`. No writes. No MT5 `login()` — `scripts/mt5-diag.sh`
  records that a login re-breaks the very thing it measures.
- A pinned **`ARMS_FLOOR` of 4**, so an arm silently disappearing fails the run rather than
  shrinking the corpus quietly.

### PYAPI-06 — both halves
- **TS half**: `analytics-client.ts` throws `SeamConfigError` BEFORE the fetch when `SERVICE_KEY`
  is absent. The file already carries the ME-01 config-fault class that routes a caller/deploy
  fault distinctly from a dead upstream. Rejected: a module-load assertion, which breaks local dev
  and any build step importing the module without the secret.
- **Python half**: an absent `X-Service-Key` is REJECTED with a machine code distinct from a wrong
  key (`SERVICE_KEY_ABSENT` vs today's mismatch path). The HTTP status stays 401 — moving absent to
  400 would change the public contract for unauthenticated callers.
- The `if provided:` guard on the Sentry capture **stays**. Its docblock records that dedenting it
  one level fires on every unauthenticated internet prober and buries the real signal.
- Each half gets a test that FAILS when its guard is deleted: neuter → observe RED → restore.

### CRON-DRIFT-01 and MT5 oracles
- The cron-drift oracle is a **COMMITTED manifest of the ACHIEVABLE Vault-backed `cron.job`
  command**, NOT derived from migrations. `20260408215026`'s GUC design returns 42501 on Supabase
  and could never have run here; deriving from migrations would encode an unrunnable design as the
  oracle.
- **ALL rows in PROD `cron.job` are in scope.** An unexpected EXTRA job is drift too.
- The comparison result is RECORDED so the next reader knows which side moved (criterion 4).
- The MT5 arm round-trips via **`initialize()` + `terminal_info()`, never `login()`**.
- **-10004 and -10005 are TWO distinct arms with two distinct remedies**: -10004 = bridge not
  attached (redeploy); -10005 = bridge attached, terminal not answering — look at the VNC screen
  for a modal login dialog, which survives redeploys via the persistent volume. Reporting them as
  one failure does not meet criterion 3.

### Workflow placement and the deploy-skip hazard (founder decision 2026-09-05)
- The prober ships as its OWN workflow file, `prod-prober.yml`, **outside** the `frontend`
  aggregate and outside the main CI run whose verdict Railway consults.
- ⛔ **Reason, and it is not stylistic.** Railway waits on main CI and SKIPS the analytics deploy
  when it is red. A four-arm production prober is EXPECTED to go red sometimes; that is its job.
  If a wedged MT5 terminal also blocked every analytics deploy, one outage would become two.
- ⚠️ The precedent named in the substrate decision above, `analytics-deploy-verify.yml`, records
  this exact hazard in its own header (a red check on main HEAD made Railway skip the deploy,
  2026-06-21). RESEARCH raises it as Pitfall 1 and treats it as an OPEN QUESTION, not a settled
  fact — so the plan MEASURES it once on a real dispatch before the posture is fixed.
- The SCRIPT contract is unchanged and not in question: aggregate all four arms, exit non-zero on
  any defect. Only the workflow-layer wiring depends on that measurement.

### Credential sequencing (founder decision 2026-09-05)
- ⛔ **Planning is BLOCKED until three GitHub Actions secrets exist.** The founder chose to create
  them BEFORE the planner runs, rather than land the prober red and fill them in after.
- The two Supabase arms (CRON-OBS-01, CRON-DRIFT-01) need nothing new. `SUPABASE_ACCESS_TOKEN`,
  `SUPABASE_DB_PASSWORD` and `vars.SUPABASE_PROJECT_REF` already exist, and `supabase link` yields
  a session-pooler DSN (port 5432, IPv4) with the password passed as `PGPASSWORD`, never in the DSN.
- Missing, with the arm each one unblocks:
  - `ANALYTICS_SERVICE_KEY` → PYAPI-06. It is the Railway analytics service's own `SERVICE_KEY`.
    ⚠️ Copy Railway → GitHub, never the reverse, and watch for a TRAILING NEWLINE on paste — the
    backlog records that a trailing newline alone reproduced the original outage.
  - `RAILWAY_API_TOKEN` → MT5. Must be WORKSPACE- or ACCOUNT-scoped; `railway ssh` REFUSES a
    project-scoped token.
  - `RAILWAY_SSH_PRIVATE_KEY` → MT5. An ed25519 key generated for CI, whose public half is
    registered with Railway under that same token.
- `vars.RAILWAY_PROJECT_ID` (and the environment/service names) can be repo VARIABLES, not secrets.
- ✅ **RESOLVED 2026-09-05, all of it, and one RESEARCH claim is CORRECTED by measurement.**
  - `ANALYTICS_SERVICE_KEY` — SET. Copied Railway `SERVICE_KEY` → GitHub through a trimming pipe.
    Measured: raw 41 chars, trimmed 41. No trailing whitespace existed this time; the hazard is
    real but did not bite here.
  - `RAILWAY_API_TOKEN` — SET (account/workspace scope).
  - `RAILWAY_SSH_PRIVATE_KEY` — ⛔ **NOT NEEDED. RETIRED.** RESEARCH Finding 4 states the MT5 arm
    needs "an SSH private key whose public half is registered with Railway". MEASURED against the
    installed CLI (railway 4.36.1): `--native` is an OPT-IN flag whose own help reads "Use native
    SSH client (requires SSH key setup)", so the DEFAULT transport requires no key. Ran
    `railway ssh --project dedf7fc5… --service mt5-gateway --environment production -- echo ok`
    with no key configured: printed `ok`, exit 0. Do not generate or register a CI SSH key.
  - Repo VARIABLES set (not secrets): `RAILWAY_PROJECT_ID` =
    `dedf7fc5-b3f8-450f-b16c-6734722f5b52`, `RAILWAY_MT5_SERVICE` = `mt5-gateway`,
    `RAILWAY_ENVIRONMENT` = `production`. `SUPABASE_PROJECT_REF` already existed.
- ⚠️ **What is still UNMEASURED, and Wave 0 owns it:** that a workspace-scoped token authenticates
  `railway ssh` from a GitHub-hosted runner, non-interactively. The `echo ok` above used the
  developer's OWN logged-in CLI session, not the token. That is a different auth path and only a
  real dispatch settles it. The credential-arm map must therefore treat the MT5 arm's auth as
  unproven until one dispatch says otherwise.
- ⚠️ This decision does not change the anti-silent-skip rule. Once built, an absent credential must
  still raise `credential-absent` NAMING the secret and exit non-zero. Waiting for the secrets is a
  sequencing choice, not permission for the prober to tolerate their absence.
