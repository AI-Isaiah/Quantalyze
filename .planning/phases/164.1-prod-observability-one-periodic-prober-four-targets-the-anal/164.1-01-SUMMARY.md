# Phase 164.1 Plan 01: Prod-prober tracer (PYAPI-06 arm) Summary

**A production prober skeleton — injectable seams, an arm registry, a named-defect table, a pinned `ARMS_FLOOR = 4` and a single exit code decided at the end — proven end to end on one arm by a 13-scenario `--self-test` that drives the real verdict loop, plus a live no-credential run that exits 1 naming both absent credentials and the floor.**

## Performance

- **Duration:** ~30 min
- **Tasks:** 2 of 2
- **Files created:** 9 (3 modules, 6 fixtures)
- **Commits:** 2

## Accomplishments

1. **`scripts/prod-prober/seams.mjs`** — `createSeams({fetchImpl, sqlRunner, sshRunner, clock})` plus `realFetch`. Every seam call increments a module-level tally (total and per-arm) BEFORE delegating, which is what gives the runner a second, independent count of its own work. `sql` and `ssh` throw `seam <name> not wired` until plans 03/04 wire them. Nothing in the file reads the process environment and nothing in it prints.

2. **`scripts/prod-prober/run.mjs`** — the CLI contract header (verbatim for plan 05's workflow), the exit-code table (0/1/2/3), the `WHAT DEFECT CLASS THIS EXISTS FOR` block naming all four measured outages, and the verdict loop: credential gate → arm runs (each wrapped, a throw becomes `measure-fail`) → floors → absurdity cross-check → one report → one exit code. Exports `ARMS_FLOOR = 4`, `SELF_TEST_SCENARIOS = 13`, `DEFECT_KINDS` (all 20), `ARMS`, `runProber`, `absurdityViolations`, `selfTest`, `setSeamsFactoryForTests`, `main`, `MANIFEST_PATH`.

3. **`scripts/prod-prober/arms/pyapi06.mjs`** — the first arm. Four GETs: our key (expect 200), no header (expect 401 + `SERVICE_KEY_ABSENT`), a deliberately wrong key (expect 401), and `/health` (expect `SERVICE_KEY` absent from `config_degraded_secrets`). The three-request control is what separates "our key is refused" from "the server accepts anything" — two faults with opposite remedies that a single authenticated GET would conflate.

4. **Six fixtures** — one green plus one red per pyapi06 kind, all obviously fake, no key material.

5. **The table-driven isolation harness** — `ARM_FIXTURE_TABLE` drives scenarios 1-6; a missing fixture is a `SELF-TEST FAIL`, each red must fire exactly one defect of its own kind on its own arm carrying its own remedy, and an ABSENCE calibration asserts nothing of the other 19 kinds fired. `KIND_ASSERTIONS` makes a by-name assertion per kind MANDATORY — a red fixture naming a kind with no entry fails the run.

## Deviations from Plan

### 1. [Rule 3 - Blocker] `KIND_ASSERTIONS` had to move INSIDE `selfTest()`

- **Found during:** Task 2, running the task's own `<verify>` command.
- **Issue:** The plan's Task-2 verify slices `run.mjs` from `indexOf("function selfTest()")` to end of file and requires every relevant kind to appear there as a literal `kind === "<k>"`. With `KIND_ASSERTIONS` declared at module level (the natural place, next to `ARM_FIXTURE_TABLE`), two kinds appeared by name only in that map and the verify failed: `uncovered: [ 'pyapi06-absent-uncoded', 'pyapi06-wrong-key-accepted' ]`.
- **Fix:** Moved the map and its docblock inside `selfTest()`. The docblock now states why it must stay there.
- **Files modified:** `scripts/prod-prober/run.mjs`
- **Verification:** the verify command now prints `coverage ok: 9` and exits 0.
- **Commit:** `950f1f28`

### 2. [Rule 3 - Blocker] `runProber` / `selfTest` / `main` are async; the CLI uses top-level await

- **Found during:** Task 1, writing the arm.
- **Issue:** The plan sketches `process.exit(main(process.argv.slice(2)))`, but four real HTTP requests cannot be issued synchronously, so `main` must return a Promise.
- **Fix:** The CLI guard is `let code = 3; try { code = await main(...) } catch { ... } process.exit(code)` — top-level await, legal in an ESM module on Node 22, and still exactly ONE `process.exit` on the `endsWith`-guarded line as the acceptance criterion requires. A crash before the report yields 3 (environment error) rather than an unhandled rejection.
- **Files modified:** `scripts/prod-prober/run.mjs`
- **Verification:** `grep -c 'process.exit'` → `1`; all four invocation modes return their documented codes.
- **Commit:** `012078cf`

### 3. [Rule 2 - Missing critical] Floors are not enforced in a narrowed `--arm` run

- **Found during:** Task 1, scenario 13.
- **Issue:** The plan requires `main(["--arm","pyapi06"])` to return 2 when green, but with `ARMS_FLOOR = 4` and one registered arm an unconditional floor check makes every narrowed run exit 1, so the "narrowed green = 2" contract could never hold.
- **Fix:** Floors are skipped in narrowed mode and the run prints `⚠️ NARROWED DIAGNOSTIC RUN (--arm): arm floors NOT enforced.` — the same posture as `scripts/mutation-runner/run.mjs:4313-4317`, and safe because that mode never exits 0 anyway. The absurdity cross-check still applies in EVERY mode, narrowed included.
- **Files modified:** `scripts/prod-prober/run.mjs`
- **Verification:** scenario 13 returns 2; scenario 9 proves the floor still fires on a full run.
- **Commit:** `012078cf`

### 4. [Rule 1 - Correctness] Scenario headers are auto-numbered

- **Found during:** Task 2, refactoring scenarios 2-6 into the table loop.
- **Issue:** With scenarios generated by a loop, hardcoded `k/13` numbers would silently disagree with what ran as soon as plans 03/04 add table entries.
- **Fix:** `scenario(title)` numbers off the same counter the completeness assertion reads. `SELF_TEST_SCENARIOS` remains the pinned constant and is still asserted against the printed count, so adding a scenario without bumping it fails the run.
- **Files modified:** `scripts/prod-prober/run.mjs`
- **Verification:** `ok — the counted scenario set is complete: 13 header(s) printed, SELF_TEST_SCENARIOS is 13`; `grep -c '^=== SELF-TEST'` still `14`.
- **Commit:** `950f1f28`
