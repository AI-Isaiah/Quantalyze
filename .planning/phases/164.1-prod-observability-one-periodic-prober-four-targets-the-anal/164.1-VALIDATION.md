## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | vitest (TS) · pytest (Python, from `analytics-service/`) · a `--self-test` mode on the prober itself |
| **Config file** | `vitest.config.ts` · `analytics-service/pytest.ini` · prober fixtures under `scripts/prod-prober/fixtures/` (Wave 0) |
| **Quick run command** | `node scripts/prod-prober/run.mjs --self-test` |
| **Full suite command** | `npx vitest run` then, from `analytics-service/`, `python3 -m pytest` then `mypy --strict` |
| **Estimated runtime** | self-test seconds; full vitest ~239 s ALONE on the box |

⛔ **The full suite must not share the box.** Measured: the same code went 1 → 9 → 55 red under
contention, 54 of them timeouts, 239 s clean versus 685 s contended. Serialize vitest, then pytest,
then mypy. A red full-suite run taken under contention is not evidence of a regression.

⚠️ **pytest runs from `analytics-service/` and with `python3`, never from the repo root.** A
repo-root run misses the VCR cassettes and issues LIVE broker calls.

---

## Sampling Rate

- **After every task commit:** `node scripts/prod-prober/run.mjs --self-test` plus the one vitest or
  pytest file the task touched.
- **After every plan wave:** full vitest alone on the box, then pytest from `analytics-service/`,
  then `mypy --strict` there.
- **Before `/gsd-verify-work`:** full suite green, and one SHA-bound `workflow_dispatch` of the new
  prober workflow on the finished tree, read arm by arm.
- **Max feedback latency:** under 30 s for the per-task loop.
