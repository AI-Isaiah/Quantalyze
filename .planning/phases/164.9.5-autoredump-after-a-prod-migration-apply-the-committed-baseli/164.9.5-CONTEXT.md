**Status:** Ready for planning

<domain>
## Phase Boundary

After `supabase-migrate.yml`'s PROD `apply` job succeeds on `main`, the committed baseline is
re-dumped and PROPOSED as a pull request automatically, so `main` never sits red on
`baseline-content-drift` waiting for a founder-run dump.

The automation reproduces the manual procedure in `supabase/schema/BASELINE.md`
`## Regenerating`. The worked example of the output is PR #864 (v0.93.0.2, merge `35d1d412f`),
whose footprint is exactly six files: `supabase/schema/baseline.sql`,
`supabase/schema/baseline-carried-migrations.txt`, `supabase/schema/BASELINE.md`, `VERSION`,
`package.json`, `CHANGELOG.md`.

Requirement: TODOS `[164.9.5-MANUAL-BASELINE-REDUMP]` (owned here).

**In the boundary:** the dump, marker regeneration from the applied merge's tree, the five-class
secret scan plus gitleaks, `scripts/local-stack/run.sh --check-currency`,
`baseline-content-drift`, mechanical BASELINE.md provenance, VERSION/package.json/CHANGELOG, the
bot PR, a route to a SHA-bound CI run on that PR, wiring tests, docs, and a pre-merge security
review.

**Out of the boundary:** auto-merge of anything; any change to `ci.yml`'s `secret-scan` job scope
(owned by `.planning/WINDOWS.md` entry 61); any change to the `apply` / `apply-test` jobs'
behaviour; any change to the shared-TEST restore path; any new long-lived credential; any
migration.

</domain>

<decisions>
## Implementation Decisions

### A. Where the automation lives and when it fires

- **D-01:** The re-dump is a NEW JOB inside `.github/workflows/supabase-migrate.yml`
  (working name `redump`), with `needs: [apply]` and an `if:` that requires
  `needs.apply.result == 'success'` AND `github.ref == 'refs/heads/main'`. It is NOT a separate
  `workflow_run` workflow.
  Evidence: (i) on the push run `github.sha` IS the merge commit whose PROD apply preceded the
  dump, which is exactly the `MERGE` that `BASELINE.md` `## Regenerating` requires the marker to be
  taken from; (ii) the file's `concurrency:` group (`supabase-migrate-${{ github.ref }}`,
  `cancel-in-progress: false`) already serialises apply runs, so a second merge's apply cannot
  interleave between this merge's apply and its dump; (iii) a `workflow_run` trigger fires on
  WORKFLOW conclusion, which is `success` when `apply` was SKIPPED, so it cannot bind to "the
  apply job succeeded" without extra API plumbing. **Reversibility:** reversible (delete the job).
- **D-02:** The ref guard mirrors the `dispatch-ref-guard` / `apply-test` pattern: the job runs
  only on `refs/heads/main`, on `push` and on a `workflow_dispatch` against `main`. A dispatch
  from any other ref never reaches it (the job's own `if:` plus `needs: [apply]`, whose chain is
  already ref-guarded). The wiring test pins the `if:` expression by symbol.

### B. Credentials (security-sensitive)

- **D-03:** The dump uses EXACTLY the credential set the `apply` job already uses:
  `secrets.SUPABASE_ACCESS_TOKEN`, `secrets.SUPABASE_DB_PASSWORD`, `vars.SUPABASE_PROJECT_REF`,
  passed through `env:` only, never inline `${{ }}` in a `run:` body. No new secret is added.
  Measured 2026-09-26 (names only, no values): both secrets are REPOSITORY secrets, and the
  `Production` environment has no protection rules and no deployment-branch policy. The job
  still declares `environment: Production`, matching `apply`, so the PROD credential is only ever
  read under that environment's audit trail. ⚠️ That buys an audit trail, NOT a stop: the
  reviewer gate was removed 2026-09-23 (CLAUDE.md), and nothing in this phase re-adds one.
- **D-04:** No DSN, password, token or project ref is ever printed. The dump is taken with
  `supabase link --project-ref "$SUPABASE_PROJECT_REF"` then `supabase db dump --linked -f
  supabase/schema/baseline.sql`, the same CLI pin as `apply` (`supabase/setup-cli`, `version:
  2.98.2`). No agent, planner or executor enters or reads a credential; every local verification
  runs against FIXTURE dumps only.
- **D-05:** Least-privilege `permissions:`. The workflow-level default stays `contents: read`.
  Only the `redump` job is uplifted, to `contents: write` (push the bot branch) and
  `pull-requests: write` (open/edit the PR). No `actions: write` (see D-12). `actions/checkout`
  keeps `persist-credentials: false`, the file's convention; the push authenticates explicitly
  and scoped to the push step. Analog: `.github/workflows/cassette-refresh.yml` (job-level
  `contents: write` + `pull-requests: write`, workflow-level `contents: read`).

### C. The gates the bot runs BEFORE it may push (refuse on any failure)

- **D-06:** Five-class secret scan, exactly the `BASELINE.md` pattern (DSN, Supabase host, project
  ref, `\connect`, `ALTER DATABASE`, JWT), with `grep -a` mandatory. ⛔ **A hit must NEVER print the
  matched line** - this is a PUBLIC Actions log, and `BASELINE.md`'s own command is `-anE`, which
  would publish the secret it found. The bot prints the COUNT and line NUMBERS only. grep exit 1 is
  clean, exit 0 is REFUSE, exit >= 2 is MEASURE_FAIL and also REFUSE.
- **D-07:** gitleaks over the dump with the pinned version `8.30.1` (the value `ci.yml`'s
  `secret-scan` pins as `GITLEAKS_VERSION`) and an EXPLICIT `-c .gitleaks.toml` / `--config
  .gitleaks.toml` (CLAUDE.md: gitleaks auto-loads config from cwd, so omitting it tests nothing;
  8.24.3 silently drops `[[allowlists]]`). Any finding refuses. gitleaks is run in a mode that does
  not echo the secret value to the log (redaction).
- **D-08:** Integrity checks from the #864 provenance table: no NUL bytes, exactly one
  `SET client_encoding`, no local home path / username. Any failure refuses.
- **D-09:** The marker `supabase/schema/baseline-carried-migrations.txt` is regenerated in the SAME
  commit from `git ls-tree --name-only "$MERGE" supabase/migrations/` with `MERGE = github.sha` of
  the applying run (never the working tree), with the header comments preserved and the
  `baseline-sha256:` line recomputed. Then `bash scripts/local-stack/run.sh --check-currency` must
  report `marker-sha=match defects=0`, and `node scripts/baseline-content-drift-check.mjs` must
  report `findings 0`. Either failing refuses.
- **D-10:** Idempotency: if the new dump's sha256 equals the committed one AND the regenerated
  marker is byte-identical, the job exits 0 with a `::notice::` and opens no PR. This is also the
  expected outcome of the post-merge verification dispatch (D-18).

### D. The pull request

- **D-11:** ONE fixed bot branch, force-pushed (working name `automation/baseline-redump`), with
  ONE open PR reused across applies (`gh pr create` when none is open, `gh pr edit` when one is).
  Rationale: when applies chain, only the newest dump is meaningful, and a fixed branch supersedes
  older dumps by construction instead of leaving a queue of stale PRs a human must close.
  **Reversibility:** reversible. ⚠️ Founder-visible choice, recorded here; per-merge branches were
  considered and rejected for the stale-queue reason.
- **D-12:** CI on the bot PR. A PR opened with `GITHUB_TOKEN` does not fire `pull_request`
  workflows. `workflow_dispatch` is the documented exception, BUT a dispatched `ci.yml` is not a
  usable verdict here: measured 2026-09-26, `ci.yml`'s `secret-scan` job runs
  `gitleaks-action` at `fetch-depth: 0`, which on a dispatch walks the FULL history and is red on
  the 37 pre-existing fixture literals (CLAUDE.md "CI gate integrity" section 2, WINDOWS.md entry
  61), and `version-gate` is `if: github.event_name == 'pull_request'`, so it would skip. Therefore:
  **no dispatch, no new credential.** The PR body instructs the human reviewer to CLOSE and REOPEN
  the PR (a human-actor `pull_request` `reopened` event fires the full PR gate set), and carries
  the SHA-bound check-count command from CLAUDE.md (`gh api
  "repos/<owner>/<repo>/actions/runs?head_sha=<sha>"`). The researcher must confirm that a
  human reopen of a `GITHUB_TOKEN`-authored PR fires `pull_request` workflows.
  ⚠️ **FOUNDER DECISION (not taken):** a GitHub App installation token or fine-grained PAT would
  let the bot's PR fire CI directly. That adds a long-lived credential, so it is out of scope
  unless the founder asks for it.
- **D-13:** The PR NEVER auto-merges. No `gh pr merge`, no `--auto`, no auto-merge label, no
  approval by the bot. The wiring test asserts the absence.
- **D-14:** The bot's commit message and PR body are composed from a fixed template and are
  checked against the six CI skip tokens from CLAUDE.md before commit and before `gh pr create` /
  `gh pr edit`; any hit refuses. The template itself names none of them, not even to deny them.
  The commit and body carry no credential-shaped literal (the push-to-main gitleaks scan sees the
  squash commit's CHANGELOG diff).

### E. What the bot writes (mechanical only)

- **D-15:** `VERSION` and `package.json` get a 4th-digit bump computed from the current `main`
  value, written as byte-equal 4-digit strings by direct edit (never `npm version`, which rewrites
  the lockfile), which `src/__tests__/critical-regressions.test.ts` asserts.
- **D-16:** `CHANGELOG.md` gets one entry `## [X.Y.Z.B] - YYYY-MM-DD` in this repo's vocabulary
  (`### Changed`, `### Notes`), shaped like #864's, carrying only MEASURED values: the applying run
  id, the merge sha (short), old/new sha256 prefixes, shape counts (tables / policies / function
  statements / data statements), the migrations newly carried (from the marker diff), and the
  verbatim `baseline-currency:` and `baseline-content-drift:` summary lines. `BASELINE.md` gets
  the capture-table update (`Taken`, `Supabase CLI`, `sha256`, `Shape`) plus a dated
  `### Regenerated YYYY-MM-DD` section listing the same measured values. ⛔ The bot does NOT
  write #864's "what it adds" column: that is a human judgment (Rule 5, "if code can answer, code
  answers" - and code cannot answer it). The PR body invites the reviewer to add it.
- **D-17:** The bot `git add`s EXACTLY the six paths of D-15/D-16 plus the dump and marker, by
  explicit path. `supabase link` writes `supabase/.temp/*` into the runner checkout; that must
  never be staged. The wiring test or the script asserts the staged set equals the six paths.

### F. Structure, testing and verification

- **D-18:** Repo house style: the logic lives in a repo script (the gates of section C and the
  writers of section E), runnable offline against a FIXTURE dump, with a `--self-test` that proves
  each refusal can fire (red fixture) and the happy path passes (green fixture). The workflow step
  stays thin and calls the script. A vitest wiring test pins the job's `needs:`, `if:`,
  `permissions:`, `environment:`, CLI pin, gitleaks pin + explicit config, absence of auto-merge,
  and absence of inline `${{ }}` in `run:` bodies. The existing pins on `supabase-migrate.yml`
  (`src/__tests__/supabase-migrate-test-first.test.ts` among them) are updated in the same plan
  that adds the job, so no existing test goes red.
  Post-merge verification (human-verification item, not run by any plan):
  `gh workflow run supabase-migrate.yml --ref main` applies zero migrations (tolerated on a
  dispatch) and exercises `redump` end to end; it should no-op per D-10.
- **D-19:** Docs: `BASELINE.md` `## Regenerating` gains a paragraph stating the procedure is now
  automated by the `redump` job, what it refuses on, and that the manual procedure remains the
  fallback. TODOS `[164.9.5-MANUAL-BASELINE-REDUMP]` is closed with the phase's evidence. The
  phase's own ship writes its CHANGELOG entry and VERSION bump per CLAUDE.md "CHANGELOG discipline".
- **D-20:** Security review BEFORE merge is a planned step: `/gsd-secure-phase` (threat model
  verification) plus a GitHub Actions workflow-injection review of the new job (untrusted-input
  interpolation, `permissions:`, credential persistence, token exposure, log leakage). If a static
  auditor such as `zizmor` or `actionlint` is used, it is run ad hoc (not added as a repo
  dependency) unless the research shows one is already present.

### G. Amendments from research (2026-09-26, evidence in 164.9.5-RESEARCH.md F1, F2, F9, F10)

- **D-21 (amends D-01 and D-05):** the automation is TWO jobs in `supabase-migrate.yml`, not one.
  `redump-dump`: `needs: [apply]`, `if: needs.apply.result == 'success' && github.ref ==
  'refs/heads/main'`, `environment: Production`, `permissions: {contents: read, packages: read}`,
  ghcr login (the `migration-drift-check.yml` template), setup-cli 2.98.2, dump into
  `$RUNNER_TEMP`, every gate of section C, then a `retention-days: 1` artifact holding only the
  gated dump, the marker and a measured-values JSON, uploaded only after every gate passes.
  `redump-pr`: `needs: [redump-dump]`, runs only when `redump-dump` succeeded, reported a change
  and the ref is `main`; `permissions: {contents: write, pull-requests: write}`; no Supabase
  secret, no setup-cli. It composes current `main` + the two files, re-runs the offline gates,
  writes VERSION / package.json / CHANGELOG / BASELINE.md, runs the skip-token guard, pushes and
  creates or edits the PR.
  Evidence: `src/__tests__/contracts/ghcr-login-before-image-pull.contract.test.ts` requires any
  job running `supabase db dump` to hold the workflow permissions plus `packages: read` and
  "nothing more", so a single job with a write token fails that contract. Two jobs are STRICTER
  than D-05: the PROD credential and the write token never share a job. `redump-dump` is added to
  that test's `PULLING_JOBS` roster. Everything else in D-01/D-02 stands (same file, `needs:`
  chain from `apply`, ref-guarded, no `workflow_run`). **Reversibility:** reversible.
- **D-22:** both new jobs sit BEFORE `apply:` in file order (between
  `prod-credential-divergence-verdict:` and `apply:`), because `critical-regressions.test.ts`'s
  WR-05 calibration arm goes red when any job follows `apply:`. Run order comes from `needs:`.
  Job keys are bare lines. Both checkouts keep `persist-credentials: false`, every `uses:` is
  SHA-pinned, and no second top-level `permissions:` block is added. The header "Flow:" comment
  and the "No GitHub API writes" comment in the same file are corrected in the same edit.
- **D-23 (amends D-12):** GitHub changed on 2026-06-11: a PR created or updated by `GITHUB_TOKEN`
  now gets `pull_request` runs in an APPROVAL-REQUIRED state. The PR body therefore instructs
  the reviewer to click **Approve workflows to run**, then to read each head-SHA run's
  CONCLUSION (not only count runs), and states that branch protection is off so the PR could be
  merged with zero completed checks. Close-and-reopen stays only as a fallback. No dispatch, no
  new credential: D-12's conclusion is unchanged.
- **D-24:** before any force-push of `automation/baseline-redump`, `redump-pr` lists the remote
  branch's commits not in `main`; if any author is not `github-actions[bot]`, it refuses loudly
  and names the PR. Human edits on the bot branch are never discarded silently.
- **D-25:** the push refspec is hard-coded to `HEAD:refs/heads/automation/baseline-redump`, and a
  wiring-test assertion proves no `git push` in the file names another ref. With branch
  protection off, `contents: write` could reach `main`; that residual is an ACCEPTED RISK recorded
  in the threat model until a ruleset exists (founder-visible, not a stop).
- **D-26:** gitleaks is installed from the pinned `8.30.1` release tarball verified against a
  sha256 hard-coded in the workflow, run as `gitleaks dir` with explicit `--config
  .gitleaks.toml`, `--redact` and `--ignore-gitleaks-allow`, and ONLY after the script has
  asserted the target exists and is non-empty (measured trap: a missing or empty target exits 0).
  The wiring test asserts the pinned version equals `ci.yml`'s `GITLEAKS_VERSION`.
- **D-27:** the shape counts come from greps over the dump (the `restore-test-from-baseline.sh`
  precedent); the script refuses on zero tables or on any data statement. Migration basenames are
  validated against `^[0-9]{14}_[a-z0-9_]+\.sql$` before they are written anywhere.
- **D-28 (amends D-20):** the workflow-injection review runs `actionlint` (already available
  locally) ad hoc; `zizmor` is optional and sits behind a `checkpoint:human-verify` because the
  package-legitimacy check rated it SUS. Neither becomes a repo dependency.
- **D-29 (execution precondition):** this worktree's base predates merge `35d1d412f` (PR #864),
  so the offline gates read red here (DRIFT 5). Execution must start from a base that contains
  `35d1d412f` (bring in current `main` first). Only `supabase/schema/*` differs.
