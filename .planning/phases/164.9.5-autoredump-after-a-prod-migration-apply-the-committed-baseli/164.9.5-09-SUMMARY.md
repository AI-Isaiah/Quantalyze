## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] The run-body scan keeps shell-comment lines inside a `run:` block**
- **Found during:** Task 1
- **Issue:** The plan says the run-body scan "operates on liveLines only". Inside a `run: |` block, a `#` line is a shell comment, and GitHub still substitutes `${{ }}` expressions in it. Filtering those lines out would leave an injection path open.
- **Fix:** `runBodies()` finds each body by structure and scans every body line. YAML comments outside a body never enter the scan.
- **Verification:** calibration "an expression seeded into a SHELL comment inside the gate body (still substituted)" flips the predicate.
- **Committed in:** `ac57193f5`

**2. [Rule 2 - Missing critical] Two credential pins stricter than the plan's letter**
- **Found during:** Task 1
- **Issue:** "Every secret line is an env: child" would accept a job-level `env:`, which exposes the PROD credential to every action step. The plan's text also did not bound the job token in `redump-pr`.
- **Fix:** The parent `env:` must be step-level, and `vars.` reads count too. In `redump-pr`, `github.token` must appear on exactly one live line: the push step's `GH_TOKEN`. Plan 04's SUMMARY states that property.
- **Verification:** the calibrations "hoisted to a job-level env:" and "the job token exposed to the compose step too" each flip the predicate.
- **Committed in:** `ac57193f5`

**3. [Trivial] Static import instead of the plan's dynamic `import()`**
- This follows the house precedent in `check-banned-packages.test.ts`. The `invokedDirectly()` guard holds in both forms.
