  - A network failure is a curl exit other than 0, so it is `MEASURE_FAIL`.

## MEDIUM

### R2-01 (MEDIUM, caused by the fix pass: D-31): the "ahead" skip is green and relies on a later run that may never happen

**Location:** `gateDump`, the `mainJudged.verdict === "ahead"` branch; `judgeMainListing`.

D-31 turns "main already has a later migration" into a `::notice::` plus `changed=false`, and
the run goes green. That is correct only if the later merge's own workflow run reaches its
`redump-dump`. Two cases end with no such run, and the baseline then stays stale, with a green
notice as the only trace:
- **The later migration merge produces no workflow run.** The concrete route in this repo is the
  skip trailer riding into a squash body. CLAUDE.md records it as measured, with zero runs for the
  merge SHA.
- **The later run's `apply` fails or is skipped**, and the fix lands through a commit that does
  not touch `supabase/migrations/**`, so nothing re-triggers.

Nothing else turns a stale baseline red. `check-baseline-staleness.mjs` is a co-edit rule (the
recorded sha equals the file sha), not an age check. The lane replays migrations newer than the
dump, so a stale baseline has no correctness consequence there. The shared-TEST restore path
refuses a dump older than the migrations, which is loud. The notice text does name the remedy
(`gh workflow run supabase-migrate.yml --ref main`).

**Why MEDIUM, not HIGH:**
- It needs a separate upstream failure.
- The stale state is safe under the lane's replay.
- The founder chose green-with-notice over red in D-31, to protect the Railway deploy.

**Recorded limit.** If it is ever tightened, the proportionate step is a staleness age check that
compares the marker against the migration tree on `main`. Another option is a scheduled dispatch.
Re-reddening this path would reverse D-31.

**Recorded limit.** A cheap closure would add policy and grant counts to `countShapes`, and refuse

### R2-03 (MEDIUM, caused by the fix pass: WR-03): the password pattern misses common spellings and could false-positive on a function body

**Location:** `SECRET_SCAN_PATTERN` (the WR-03 alternation), the byte-equal grep in BASELINE.md
`## Regenerating`, and `.gitleaks.toml` rule `baseline-dump-password` (the same regex).

**False negatives.** Each of these was checked against `(^|[^_A-Za-z])password( ?= ?[^ ,)]| [^ -&(-~])`,
where `[^ -&(-~]` admits only the single quote among printable ASCII:
- the upper-case `PASSWORD '…'`, because both the JS regex and the gitleaks RE2 rule are
  case-sensitive;
- `password := '…'`, a plpgsql assignment in a function body;
- `"password": "…"`, inside a jsonb default or a `COMMENT ON` literal;
- `password  = …`, with two spaces;
- `password E'…'`, an escape-string literal.

None of these existed before WR-03, so this is a narrower-than-hoped new check, not a regression.

**False positive.** Any `password = <expr>` in a dumped function body matches the first
alternative, for example `WHERE password = crypt(…)` or `IF password = ''`. A migration that ships
one would make every later redump refuse at the scan, turning each migration merge on `main` red,
until someone runs a hand re-dump. That is loud, not silent. Measured at HEAD: 0 such lines in the
dump or in `supabase/migrations/`.

**Recorded limit.** If it is widened, add a case-insensitive flag and the `:=` / `":"` forms to
the gitleaks rule only. The JS pattern is pinned byte-equal to the portable ERE in the doc.
Measure false positives over the committed dump before shipping.
