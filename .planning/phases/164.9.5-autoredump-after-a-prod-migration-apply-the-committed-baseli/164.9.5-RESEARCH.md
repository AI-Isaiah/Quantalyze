### Locked Decisions

#### A. Where the automation lives and when it fires

- **D-01:** The re-dump is a NEW JOB inside `.github/workflows/supabase-migrate.yml`
  (working name `redump`), with `needs: [apply]` and an `if:` that requires
  `needs.apply.result == 'success'` AND `github.ref == 'refs/heads/main'`. It is NOT a separate
  `workflow_run` workflow.
  Evidence: (i) on the push run `github.sha` IS the merge commit whose PROD apply preceded the
  dump, which is exactly the `MERGE` that `BASELINE.md` `## Regenerating` requires the marker to be
  taken from; (ii) the file's `concurrency:` group (`supabase-migrate-${{ github.ref }}`,
  `cancel-in-progress: false`) already serialises apply runs, so a second merge's apply cannot
  interleave between this merge's apply and its dump; (iii) a `workflow_run` trigger fires on
  WORKFLOW conclusion, which is `success` when `apply` was SKIPPED, so it cannot bind to "the
  apply job succeeded" without extra API plumbing. **Reversibility:** reversible (delete the job).
- **D-02:** The ref guard mirrors the `dispatch-ref-guard` / `apply-test` pattern: the job runs
  only on `refs/heads/main`, on `push` and on a `workflow_dispatch` against `main`. A dispatch
  from any other ref never reaches it (the job's own `if:` plus `needs: [apply]`, whose chain is
  already ref-guarded). The wiring test pins the `if:` expression by symbol.

#### B. Credentials (security-sensitive)

- **D-03:** The dump uses EXACTLY the credential set the `apply` job already uses:
  `secrets.SUPABASE_ACCESS_TOKEN`, `secrets.SUPABASE_DB_PASSWORD`, `vars.SUPABASE_PROJECT_REF`,
  passed through `env:` only, never inline `${{ }}` in a `run:` body. No new secret is added.
  Measured 2026-09-26 (names only, no values): both secrets are REPOSITORY secrets, and the

- **D-05:** Least-privilege `permissions:`. The workflow-level default stays `contents: read`.

## Summary

The automation is buildable exactly as CONTEXT describes, with three evidence-backed corrections the planner must carry, because each one makes a locked decision unworkable as literally written.

1. **One job cannot hold both the PROD dump and the write token.** `src/__tests__/contracts/ghcr-login-before-image-pull.contract.test.ts` requires every job that runs `supabase db dump` to be in its pinned `PULLING_JOBS` roster, to log in to ghcr.io first, and to declare job permissions equal to the workflow's plus `packages: read`, "nothing more". D-05 puts `contents: write` and `pull-requests: write` on that same job. Both cannot hold. The recommended resolution is two jobs: a dump job that holds the PROD credentials and a read-only token, and a PR job that holds the write token and no PROD credentials. This is stricter than D-05, and it deviates from D-01's singular "a NEW JOB".
2. **D-12's premise changed on 2026-06-11.** GitHub now creates `pull_request` runs for a GITHUB_TOKEN-created or updated PR, in an **approval-required** state. A write-access user starts them with an **Approve workflows to run** button in the merge box. D-12's conclusion still holds: no dispatch, no new credential, and a human action before CI runs. Only the instruction changes, from close-and-reopen to approve. Close-and-reopen stays as an `[ASSUMED]` fallback.
3. **Appending the job after `apply:` breaks `critical-regressions.test.ts`.** Its WR-05 calibration arm (`it("CALIBRATION (WR-05): applyJobBlock THROWS …")`, line 1224) seeds an unrecognised key at end-of-file and expects a throw. Any real job placed after `apply:` makes the bound match that job instead, so the throw never fires and the test goes red. Put the new jobs before `apply:` in file order. Execution order comes from `needs:`, not from text order.

The CLI format-skew worry in `BASELINE.md` is mostly settled at the source level. `pkg/migration/scripts/dump_schema.sh` is byte-identical between CLI v2.84.2 and v2.98.2. When the CLI is linked it runs `pg_dump` inside the remote project's own `supabase/postgres` image; VAC-04 run `36229959793` pulled `17.6.1.104`. The per-run `\restrict` key lines from newer `pg_dump` are commented out and then deleted by the default `/^--/d` filter, so they never reach the file. Byte-identity of the first automated dump against the founder's 2.84.2 capture is still `[ASSUMED]`, and the D-18 dispatch is the test that settles it.

**Primary recommendation:** Build `scripts/baseline-redump.mjs` (name at the planner's discretion). It holds pure `judge*`/`compose*` functions and a `--self-test`. Wire it into two new jobs in `supabase-migrate.yml`, placed before `apply:`:

- **`redump-dump`:** `environment: Production`, `permissions: {contents: read, packages: read}`, ghcr login, dump, all scan and integrity gates, marker. It uploads a 1-day artifact only after every gate passes.
- **`redump-pr`:** `permissions: {contents: write, pull-requests: write}`, no setup-cli, no PROD secrets. It rebases the files onto current `main`, re-runs the offline gates, writes VERSION, CHANGELOG and BASELINE.md, checks the skip tokens, pushes the fixed branch, and creates or edits the PR.

Because the new jobs read only `GITHUB_SHA`, `GITHUB_RUN_ID`, `GITHUB_REPOSITORY` and `GITHUB_REF` from the runner's env, and put secrets only in `env:`, both tools should report nothing on them.
- **Security-review plan:** run `actionlint .github/workflows/supabase-migrate.yml` and a version-pinned `uvx zizmor==1.30.1 --offline .github/workflows/supabase-migrate.yml` ad hoc, and paste the output into the plan's SUMMARY. Put the zizmor run behind a `checkpoint:human-verify` (SUS verdict). Do not add either tool as a repo dependency (D-20).

### F13. Reusable offline fixtures (Q11)

- `scripts/restore-test-from-baseline-fixtures/baseline-fixture.sql` (181 lines) is baseline-SHAPED, but it begins with `--` comment lines, which a real CLI dump never contains (`/^--/d`). It is fine for shape-count arms and wrong for "looks like a real dump" arms.
- The committed `supabase/schema/baseline.sql` is the best GREEN fixture: read-only, real bytes, and it passes every gate on `main`. `check-baseline-currency.mjs` and `baseline-content-drift-check.mjs` already use the house `--self-test` style, driving pure `judge()` functions over synthetic in-memory inputs.
- **Recommendation:** build RED fixtures at runtime by mutating a copy of the committed dump in a temp dir: append a NUL byte, a second `SET client_encoding`, a `\connect` line, a DSN-shaped line, a `/home/x/` path, and a JWT-shaped value assembled from fragments at runtime. Also cover a `gitleaks:allow` line, a data `INSERT INTO` line, an empty file and a missing file. ⛔ Never commit a JWT- or DSN-shaped literal: `ci.yml`'s `secret-scan` would flag it in the push-to-main range scan (CLAUDE.md gitleaks rule).

### Pattern 1: script modes the workflow calls (thin steps)

- `node scripts/baseline-redump.mjs --self-test`: must run first in each job, following the `ci.yml` precedent that a self-test precedes the real run.
- `node scripts/baseline-redump.mjs --gate-dump <dump> --merge-tree HEAD --base-ref origin/main --out <dir>`: scans, runs integrity, counts shapes, writes the marker, compares with the base, and writes `changed=` to `$GITHUB_OUTPUT`.
- `node scripts/baseline-redump.mjs --compose --in <artifact-dir> --run-id "$GITHUB_RUN_ID" --merge "$GITHUB_SHA"`: runs the offline gates via child processes, runs the writers, asserts the staged set, and composes the message and body into files.

Each mode's refusal prints `::error::` with counts and line numbers only and exits 1. `MEASURE_FAIL` (a tool could not decide) also exits 1. There is no `exit 0` on a failure path.

### Anti-Patterns to Avoid

- `grep -anE … baseline.sql` in a public log. It prints the secret it found.
- A `gitleaks dir` run whose result is trusted without a preceding exists/non-empty assertion (exit 0 on a missing file, F4).
- `${{ … }}` inside any `run:` body. Use the runner env (`GITHUB_SHA`, `GITHUB_RUN_ID`, `GITHUB_REPOSITORY`, `GITHUB_REF`) or step `env:`.
- `git add -A` / `git add .`. Stage the six paths explicitly and assert with `git diff --cached --name-only`.
- A second full-64-hex `| sha256 |` row in `BASELINE.md` (IN-03 ambiguity, F2).
- Uploading the dump as an artifact before the scans pass.

## Common Pitfalls

1. **Single-job design fails the ghcr contract.** RED on "nothing more" permissions and on the roster. Warning sign: the plan puts `contents: write` on the job that runs `supabase db dump`.
2. **Job appended after `apply:`.** `critical-regressions.test.ts:1224` goes RED. Place the jobs before `apply:`.
3. **gitleaks false-clean on a missing or empty file** (measured exit 0). Assert the file first.
4. **The dump truncates its target** (`O_TRUNC`). Dump to `$RUNNER_TEMP` and copy only after the gates pass.
5. **Gates run on a stale checkout.** This worktree is behind `main` and shows DRIFT 5 with findings 2. Rebase before executing. In the workflow, the PR job must judge the composed tree on current `main`.
6. **`--check-currency` without `supabase/config.toml`.** It errors in any sparse or partial checkout, so use a full checkout.
7. **The project ref appears in the env echo.** Pre-existing and a `vars` value, but the bot's own prints must never add it. Never paste it into docs.
8. **A human edit lost to force-push** (D-16 column). Refuse on foreign commits on the bot branch.
9. **"Checks present" ≠ "checks passed"** on a bot PR. Approval-required runs exist before approval. Read `.conclusion`.
10. **A red redump on a merge commit may skip the Railway analytics deploy.** Railway's "Wait for CI" skips a `main` commit whose check suite failed (project memory, 2026-05-25). Only in the body-drift case is the merge commit already red on `ci.yml`'s `sql-gate-lint`. When the apply leaves no body drift, `main` is green and a redump refusal is new red. `[ASSUMED]`: Railway counts the `supabase-migrate.yml` suite. See Open Question 2.
11. **Skip tokens quoted by the executor in its own commit messages or this phase's CHANGELOG.** Use prose.
12. **The D-18 verification dispatch also runs `apply-test`**, which takes the shared-TEST mutex (up to a 3600 s queue) and applies zero migrations to TEST. That is expected and slow; the human-verification item should say so.

## Code Examples

### Count-and-lines secret scan (never the line), node

```javascript
// Source: pattern verbatim from supabase/schema/BASELINE.md `## Regenerating`, first code block (wiring test asserts equality)
export const SECRET_SCAN_RE = /postgres(ql)?:\/\/|@[a-z0-9.-]+\.supabase\.(co|com)|[a-z]{20}\.supabase|\\connect|ALTER DATABASE|eyJ[A-Za-z0-9_-]{10,}/;
export function judgeSecretScan(text) {
  const lines = [];
  text.split("\n").forEach((l, i) => { if (SECRET_SCAN_RE.test(l)) lines.push(i + 1); });
  return lines; // caller prints `secret-scan: ${lines.length} hit(s) at line(s) ${lines.join(",")}`, never the text
}
```
