## Summary

This review covers the `redump-dump` and `redump-pr` jobs in `supabase-migrate.yml`, all of
`scripts/baseline-redump.mjs` (the modes, judges, writers, the bot-branch check, the PR create/edit
path and the self-test), the wiring test and the three widened test pins.

**What holds, checked rather than assumed:**
- **Credential split.** The PROD credential stays in step-level `env:` inside `redump-dump`. The
  write token appears only in the push step of `redump-pr`.
- **Permissions.** `redump-dump` has `contents: read, packages: read`. `redump-pr` has
  `contents: write, pull-requests: write`. The workflow default is still `contents: read`.
- **Injection.** No `${{ }}` appears in any `run:` body. `LEASE` and `GH_TOKEN` arrive through
  `env:`, and the lease is a hex sha the script emits itself.
- **Ordering.** `needs: [apply]` combined with `needs.apply.result == 'success'` and the implicit
  `success()` means a failed or skipped apply never reaches either job. Neither job can change
  the apply.
- **Lease.** An empty lease means the branch must not exist, and a tip lease is re-verified
  against the fetched tip.
- **gitleaks.** It runs with an explicit `--config`, `--redact` and `--ignore-gitleaks-allow`, and
  the binary is sha256-pinned. The script refuses a missing or empty target before the scan.
- **Refusals.** Every refusal throws and ends in `::error::` with exit 1. A schema-1 check of
  `measured.json` and a compose-side re-scan back this up.
- **Staged set.** Staging uses the six explicit paths only.
- **Marker.** The marker is taken from the merge tree and bound to the dump's sha256.
- **Tests.** The wiring test's calibrations mutate the workflow and assert red.

Measured locally: the four test files ran green (231 tests), and
`node scripts/baseline-redump.mjs --self-test` passed (198 assertions).

**The two HIGH findings are about what the code does on GitHub, not what its fixtures show.**
- The repository does not allow the workflow token to create a pull request, so the first real
  changed run fails at `gh pr create` (CR-01).
- The documented review path is: add a human commit, then squash-merge. That path leaves the bot
  branch in a state that every later run refuses (CR-02).

Both turn every later migration merge's run red on `main`, and per CONTEXT assumption A7 a red run
here holds the Railway deploy.

## Critical Issues

### CR-01: HIGH — the repository does not let the workflow token create a pull request, so every changed re-dump goes red at `gh pr create`

**File:** `.github/workflows/supabase-migrate.yml` (job `redump-pr`, step `Push the bot branch and open or edit its PR`); `scripts/baseline-redump.mjs` (`openOrEditPr`, `buildPrArgv`)

**Issue:** A read-only query of the repository's Actions workflow permissions returns
`{"default_workflow_permissions":"read","can_approve_pull_request_reviews":false}`. That field is
the API form of **"Allow GitHub Actions to create and approve pull requests"**. While it is off, a
`GITHUB_TOKEN` cannot create a pull request. `gh pr create` fails with "GitHub Actions is not
permitted to create or approve pull requests", whatever the job's `pull-requests: write` says.

No pull request authored by `app/github-actions` exists in the repository (checked read-only), so
nothing shows the setting has ever been on. `cassette-refresh.yml` depends on the same capability
through `peter-evans/create-pull-request` with the default token, and it has no bot PR on record
either. A grep of the phase directory for the setting finds nothing: it is neither a recorded
precondition nor a human-verification item.

This is what happens on the first migration merge whose dump changed:
1. `git push` succeeds. The bot branch is now public.
2. `--open-or-edit-pr` runs `gh pr list` (allowed), then `gh pr create` (refused), and throws
   `MEASURE_FAIL: gh pr create exit 1`.
3. `redump-pr` goes red, so the Supabase Migrate run on the `main` merge commit goes red. Per
   assumption A7, that holds the Railway deploy.
4. Every later changed run repeats this. The branch holds only bot commits, so
   `--check-bot-branch` passes, the push succeeds, and create fails again.

D-18's planned post-merge proof (`gh workflow run supabase-migrate.yml --ref main`) takes the D-10
**no-op** path. It never reaches `gh pr create`, so it cannot catch this. The failure first shows
on a real migration merge.

**Fix:** This is a founder setting, not code. Pick one route and record it as a precondition:
- Turn on *Settings → Actions → General → Workflow permissions → "Allow GitHub Actions to create
  and approve pull requests"*. ⚠️ The same box also lets ANY workflow holding
  `pull-requests: write` **approve** PRs. With branch protection off, an approval gates nothing
  today, but record the widened surface in the threat model.
- Or reopen D-12's rejected route: a GitHub App installation token or a fine-grained PAT used for
  the `gh` call only.

Either way:
- Add the setting to the phase's human-verification items and to the `AUTOMATED 2026-09-26`
  paragraph in `BASELINE.md`.
- Make the first proof a run that takes the **changed** path, not only the no-op dispatch.
- Have `openOrEditPr` recognise this refusal and name the setting, because a bare
  `gh pr create exit 1` points the reader nowhere:
```js
// realGh already returns stderr on failure; pass it through to the judge
if (r.status !== 0 && /not permitted to create or approve pull requests/i.test(r.stderr ?? "")) {
  throw new Error("gh pr create refused: the repository setting 'Allow GitHub Actions to create and approve pull requests' is off; the bot branch was pushed but no PR exists");
}
```

### CR-02: HIGH — after a squash merge, the human commit the PR body asks for blocks every later run on the bot branch

**File:** `scripts/baseline-redump.mjs` (`checkBotBranch`, `judgeForeignCommits`, `composePrBody`)

**Issue:** `composePrBody` tells the reviewer to "Add the 'what it adds' column … **as a commit on
this branch**". Read-only settings show that the repository allows squash and rebase merges and
has `delete_branch_on_merge: false`. The repo practice is to squash (CLAUDE.md "CI gate
integrity" §1).

After the reviewer squash-merges (or rebase-merges) the bot PR:
- The bot branch still exists.
- Neither of its commits is an ancestor of `main`.
- `git log origin/main..origin/automation/baseline-redump` still lists the human commit.

On the next PROD apply whose dump changed, `judgeForeignCommits` finds the foreign author, and
`checkBotBranch` throws. It throws again on every apply after that, and nothing clears it.

The refusal text also points the wrong way. The merged PR's `refs/pull/<n>/head` stays frozen at
the tip, so `findPullRefsForSha` returns `[n]`. The message then says "It sits on pull request(s)
#n … **Merge or close that pull request**", which the human has already done. Nothing says the
actual remedy, which is to delete the bot branch.

A PR closed without merging, with a human commit on it, wedges the same way. The result is a
permanent red `redump-pr` on every migration merge. Per A7 that holds the Railway deploy, until
someone works out that the branch has to be deleted by hand.

**Fix:** Refuse only while the human commit is on an **open** PR. Once every PR pointing at the tip
is closed or merged, the work has been accepted or abandoned by a human, so the bot may replace it.
- Look up open PRs anonymously. The repository is public, so
  `GET /repos/{o}/{r}/pulls?head={o}:automation/baseline-redump&state=open` needs no token, which
  keeps the check step token-free. The other option is to reuse `openOrEditPr`'s `gh pr list`
  in the push step, before the push.
- If foreign commits exist and no open PR has the branch as head, print a `::notice::` naming the
  closed PR numbers and emit the tip as the lease. Refuse only when the head of an open PR carries
  the foreign commit.
- Fix the refusal text: for a merged or closed PR, name "delete the branch" as the remedy.
- As a complement, not a substitute (the closed-unmerged case still wedges), consider
  `delete_branch_on_merge: true`.
- Add a self-test arm: foreign commit, tip equal to a closed PR's head, no open PR → pass with a
  notice.

## Warnings

### WR-01: MEDIUM — composing onto CURRENT `main` gives a false red when two migration PRs merge close together

**File:** `scripts/baseline-redump.mjs` (`compose`, `judgeDriftLine`); `.github/workflows/supabase-migrate.yml` (`redump-pr` checkout `ref: main`)

**Issue:** Suppose merge M1 applies to PROD and `redump-dump` takes the M1 dump. Meanwhile M2, which
changes a function, has merged and its run is queued behind this one by the `concurrency:` group.
`redump-pr` checks out `main` (now M2) and runs `baseline-content-drift-check.mjs` against M2's
migration chain. That script does not read the carried-migrations marker (grep for
`carried`/`marker` finds only unrelated prose), so it reports M2's function as drift, and
`judgeDriftLine` refuses. The code predicts this itself ("Likely cause: main holds a migration
that has not applied to PROD yet; the queued apply run will produce the right dump").

The refusal is a red `redump-pr` on M1's merge commit. It is not a notice. That red is a false
alarm, but a human still has to triage it, and per A7 it can skip M1's deploy.

**Fix:** Before composing, compare the merge's and `origin/main`'s `supabase/migrations/` trees. If
`main` carries a migration the merge does not, stop with a `::notice::` ("a later apply is queued;
it will re-dump") and emit `committed=false`, instead of a red. The other option is to compose onto
the merge commit and let CI's version gate catch any version collision.

### WR-02: MEDIUM — re-running an old run's `redump-dump` pairs today's PROD with that run's stale marker

**File:** `scripts/baseline-redump.mjs` (`gateDump`); `.github/workflows/supabase-migrate.yml` (`redump-dump`)

**Issue:** "Re-run failed jobs" on an older Supabase Migrate run re-runs `redump-dump` with that
run's original `github.sha`. A transient ghcr throttle is a natural trigger. `gateDump` only
checks `HEAD == --merge`, and that holds. The re-run then dumps **current** PROD, which already
carries later merges' migrations, and writes the marker from the **old** merge tree.

The composed PR has three problems:
- The marker under-claims what the dump carries. The local-stack lane then replays those
  migrations on top of a dump that already contains them: silently when they are idempotent,
  fatally when they are not.
- The provenance says "after the PROD apply of merge <old>".
- The drift gate on `main` passes, because PROD and `main` agree.

The concurrency argument in D-01(ii) holds only for attempt 1.

**Fix:** In `redump-dump`, refuse when `GITHUB_RUN_ATTEMPT` is not `1`. Pass it through `env:` and
check it in the script, not in a `${{ }}` in `run:`. Point the message at the remedy the PR body
already names, `gh workflow run supabase-migrate.yml --ref main`, which gets a fresh `github.sha`.
Add a wiring-test arm for it.

### WR-03: MEDIUM — neither gate catches a Supabase `sb_secret_` key, and the dump is public as soon as the push lands

**File:** `scripts/baseline-redump.mjs` (`SECRET_SCAN_PATTERN`, `gitleaksArgv`); `supabase/schema/BASELINE.md` (`## Regenerating` grep)

**Issue:**
- **Why the gates are the only stop.** The bot branch is pushed to a public repository before any
  human reads the PR, so the two scans are the only thing between the dump and the public.
- **Neither scan matches the key.** Supabase's current secret-key format is `sb_secret_<random>`,
  which is not a JWT. The five-class pattern has no class for it.
- **Probe result.** Measured locally: gitleaks 8.30.1 with this repo's `.gitleaks.toml` and the
  exact flags `gitleaksArgv` uses returned exit 0, no finding, over a fixture holding a random
  `sb_secret_`-shaped value in a `COMMENT ON` literal.
- **The same class.** Keyword-form connection strings (`host=… password=…`) carry a credential in
  `CREATE USER MAPPING … OPTIONS (password …)` or `CREATE SUBSCRIPTION … CONNECTION`. Neither
  `postgres(ql)?://` nor any other class matches them. The committed dump carries neither
  statement today (measured: 0 hits), so this is a latent gap.

**Fix:** Add classes such as `sb_secret_[A-Za-z0-9_-]{16,}` and `password\s*[= ]\s*'`, or refuse any
`USER MAPPING`/`SUBSCRIPTION` statement outright.
⚠️ `SECRET_SCAN_PATTERN` and the `grep -anE` argument in `BASELINE.md` must move in the same
commit. The self-test and the wiring test both pin them as byte-equal.
Also add a self-test arm that plants a runtime-assembled `sb_secret_` value and asserts the
refusal.

### WR-04: LOW — the concurrency group is now held up to ~35 minutes longer, which widens the existing pending-run cancellation window

**File:** `.github/workflows/supabase-migrate.yml` (`concurrency:`; `redump-dump` `timeout-minutes: 20`, `redump-pr` `timeout-minutes: 15`)

**Issue:** `cancel-in-progress: false` keeps only ONE pending run per group. If a third migration
merge arrives while one run is in progress and one is pending, the pending run is **cancelled**.
The newest run's `--include-all` still applies its migrations, but the cancelled run leaves a
cancelled check on its merge commit. This existed before the phase. The redump jobs now keep the
group busy for up to 35 more minutes after `apply` finishes, which widens the window.

**Fix:** Record it as a known limit in the file's header comment and in the threat model, or
lower the redump timeouts toward the measured runtime once a real run exists.

## Info

### IN-01: The ghcr token stays in `~/.docker/config.json` for the rest of `redump-dump`

**File:** `.github/workflows/supabase-migrate.yml` (`redump-dump`, step `Log in to ghcr.io before the CLI pulls its images`)

**Issue:** `docker login` writes the job token (`contents: read`, `packages: read`) to the runner's
docker config. The dump and gate steps can still read it. The token is read-only and ends with the
job.
**Fix:** Optionally add a `docker logout ghcr.io` step with `if: always()` after the dump step.

### IN-02: `setup-node` in the write-token job gets the write token through its default `token:` input

**File:** `.github/workflows/supabase-migrate.yml` (`redump-pr`, `actions/setup-node` step)

**Issue:** `setup-node` defaults `token:` to `github.token`, which here is `contents: write`. It
uses the token only to fetch Node manifests, and the action is SHA-pinned first-party code. It is
still one more consumer of the write token than D-05's "the push step only" describes.
**Fix:** Set `token: ''` on that step, or record the exception beside D-05.

### IN-03: `botPrStatus` turns a failed lookup into a warning on the no-op path (by design)

**File:** `scripts/baseline-redump.mjs` (`botPrStatus`)

**Issue:** A failed `ls-remote` on the D-10 no-op path produces a `::warning::` and a green
job, deliberately (RESEARCH A7). This is recorded so a later reader does not "fix" it into a red:
the dump gates already passed before this lookup runs.
**Fix:** None. Keep it as is.
