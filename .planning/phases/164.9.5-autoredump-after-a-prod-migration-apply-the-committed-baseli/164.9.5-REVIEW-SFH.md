## HIGH

### SFH-01 (HIGH): re-running a failed `redump-dump` after a later migration merge writes a marker that disagrees with its dump, and no gate catches it

**Location:** `.github/workflows/supabase-migrate.yml` job `redump-dump` (checkout at the default
ref, then `Gate the dump` passing `--merge "${GITHUB_SHA}"`); `scripts/baseline-redump.mjs`
`gateDump` (the `head !== merge` check and `git ls-tree --name-only merge supabase/migrations/`).

**What happens.** D-01 relies on the file's `concurrency:` group to guarantee that no second
merge's apply lands between this merge's apply and its dump. That holds for a run's first attempt.
It does not hold for **Re-run failed jobs** on an older run.

Take run A for merge M1. Its `redump-dump` goes red on something transient: a ghcr throttle, a
network error during `supabase db dump`, or a runner fault. Merge M2 then adds a migration, and
run B applies it to PROD. A human then re-runs A's failed jobs. `apply` is not re-run, so its
`success` result carries over. `github.sha` is still M1, so the checkout is M1 and
`head === merge` passes. The dump, though, is taken from PROD **now**, and PROD already carries
M2. The marker lists M1's tree only. The result is a marker that says M2 is not carried, next to
a dump that carries it.

**Why no gate catches it:**
- `compose` runs `--check-currency`. It flags a marker naming a migration the checkout lacks. It
  cannot flag the reverse. Here M2 is in main's checkout and absent from the marker, so it simply
  enters the replay set.
- `baseline-content-drift-check.mjs` compares the dump's function bodies against the full
  migration chain in the checkout, not against the marker. By its own header it compares
  functions only.
- The PR body names run A's id and M1's short sha. Neither tells a reviewer that PROD had moved
  on since.

**Hidden consequence.** Once the PR merges, the local-stack lane (`sql-tests`,
`frontend-local-stack`, `frontend-live-db-lane`) replays M2 on top of a dump that already
contains it.
- If M2 is non-idempotent (`CREATE TABLE`, `CREATE POLICY`), the replay is FATAL. That shows up
  only on the bot PR's CI, and only after a human approves those runs.
- If M2 is idempotent (`CREATE OR REPLACE`, `IF NOT EXISTS`), the double apply is silent.
- If M2 seeds data, its INSERTs run a second time.

This is the "carried-migrations marker written against the wrong sha" class. The marker is bound
to M1's tree, while the dump reflects M2's database.

**Recommendation (fail loud, no new credential).** Refuse in `redump-dump` unless the merge's
migration set equals current main's migration set. Two ways to do it:

1. Fetch `refs/heads/main` anonymously, the same token-free `anonGit` idiom `checkBotBranch`
   uses. Then refuse when `git ls-tree --name-only <merge> supabase/migrations/` differs from the
   same listing at `FETCH_HEAD`. Name the fix in the error: "dispatch a fresh run on main".
2. The coarser alternative: refuse whenever `GITHUB_RUN_ATTEMPT != 1`.

Option 1 is precise. It still allows a legitimate re-run when no migration has landed since.

```js
// gateDump, after the head === merge check
const mainTip = anonFetchMainTip(repoRoot, remote);            // anonymous, MEASURE_FAIL on error
const at = (ref) => git(repoRoot, ["ls-tree", "--name-only", ref, MIGRATIONS_REL]);
if (at(merge) !== at(mainTip)) {
  throw new Error("main carries migrations this merge does not; PROD may already hold them, so the " +
    "marker would disagree with the dump. Dispatch supabase-migrate.yml on main instead of re-running this run");
}
```

Add a self-test arm in which main's migration listing gains one entry, and prove the arm refuses.

## MEDIUM (recorded limits, no fix round of their own)

### SFH-02 (MEDIUM): re-running `redump-pr` can propose an OLDER dump over a newer committed one

**Location:** `scripts/baseline-redump.mjs` `compose`, the "Second D-10 check" and the
`newlyCarried` computation.

`compose` checks out current main and refuses only when the pair is byte-identical. Suppose a later
run's bot PR has already merged a newer baseline. A re-run of an older run's `redump-pr` can still
run within the one-day artifact window. It then overwrites main's newer baseline and marker with
the older ones, bumps VERSION, and opens a PR.

The marker and dump stay mutually consistent, so the currency and drift gates stay green and
nothing refuses. The PR still regresses the baseline. `compose` never checks that `measured.merge`
is an ancestor of HEAD or that the new marker's basenames are a superset of main's committed
marker.

Remedy: refuse when `oldBasenames` is not a subset of `newBasenames`, printing the count only. The
SFH-01 guard also closes the most likely route in.

### SFH-03 (MEDIUM): no completeness or shape-regression floor, and extensions or schemas are not measured

**Location:** `countShapes`, `judgeShapeCounts`, `gateDump`.

The only shape refusals are zero tables and any data statement. The CLI's dump carries no
`dump complete` footer: the committed file ends in blank lines after
`ALTER DEFAULT PRIVILEGES`. A dump truncated mid-stream but exiting 0 is therefore measured by
nothing that `redump-dump` runs. The same is true of a dump that loses `CREATE EXTENSION` lines.
The committed dump has 6, including `pg_cron` and `pg_net`, and a Supabase CLI pin change could
alter the dump's schema exclusions.

In `compose`, the drift gate sees function bodies only. It is blind to extensions, grants, policies
and tables. The remaining defence is a human reading the shape delta in the PR body, and that delta
does not count extensions.

Remedy: add `extensions` (`^CREATE EXTENSION`) and `schemas` (`^CREATE SCHEMA`) to `countShapes`.
Refuse when any count falls below the committed dump's count unless a migration in the marker diff
drops that object class. At minimum, print both counts in the PR body.

### SFH-04 (MEDIUM): the marker is derived from the git tree, never from PROD's ledger

**Location:** `gateDump` (`ls-tree` at the merge).

D-09 chose the tree deliberately, and on a first attempt it is correct, because `apply` in the same
run just pushed `--include-all` and post-verified. Two things break the assumption that the tree
equals what PROD applied, and nothing between the dump and the marker measures either:
- the re-run window in SFH-01;
- the developer CLI, which is linked to PROD (CLAUDE.md), acting out of band.

Recorded as a limit. The SFH-01 guard covers the in-workflow case.

## Checked and found sound

- **Grey-versus-red chain.** `redump-dump` carries no status function in its `if:`, so an
  implicit `success()` is ANDed in. Its ancestors are `apply` → `plan` and `apply-test`, and `apply`
  itself runs only after both succeed. So when `apply` succeeds, `redump-dump` runs. It cannot skip.
  A failed or skipped `apply` skips it, which is correct: `apply-test-verdict` already reports the
  failed or skipped apply as red.
- **Dump fails.** `set -euo pipefail` on `supabase link` and `supabase db dump` makes a failure red.
- **Empty or missing dump.** `assertScanTarget` refuses before gitleaks is spawned (the false
  clean was measured), and `gateDump` refuses a 0-byte read again.
- **gitleaks.** Only exit 0 with `[]` counts as clean. Exit 0 with findings refuses. A null exit
  (a signal), an exit of 2 or more, or an unreadable report is MEASURE_FAIL. The binary's
  version is probed and the tarball is sha256-pinned. `--config .gitleaks.toml` is explicit, and
  the allowlist paths cannot match the `$RUNNER_TEMP` target.
- **Upload.** It sits behind the default `success()` and `changed == 'true'`, with
  `if-no-files-found: error` and no `always()`.
- **Bot branch exists.** An empty lease means the branch must not exist, and a tip lease binds the
  judged sha. A foreign commit refuses and names the PR. A branch that moved between ls-remote and
  fetch is MEASURE_FAIL.
- **`gh`.** A failure of `gh pr list`, `pr create` or `pr edit` is MEASURE_FAIL, and so is a
  `create` that prints no URL. Two or more open bot PRs refuse. A missing GH_TOKEN or repository
  slug refuses before any `gh` call.
- **Refusal exits.** Every mode throws, and `main` maps a throw to `::error::` and exit 1. An
  unknown argument exits 1.
- **`continue-on-error` and `|| true`.** Neither appears in either new job.
- **Mutex.** Neither job touches shared TEST or advisory key `61616158`, so there is no acquire
  or release path that could leak.
- **Writers and staging.** Each writer refuses on a regex that matches nothing. The staged set is
  judged equal to the six paths. The skip-token judge runs before the commit and again before `gh`.
