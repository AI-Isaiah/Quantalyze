# Phase 153.6 Plan 02: Cluster C — the deadline and the oracle that could not see it Summary

The browser's connect-route abort was sized against the CLOSED-breaker column; it now covers the
FAILING column on **both** venue arms (190 500 / 100 500), and the oracle guarding it was replaced
with one quantified over every breaker state, so the wrong column cannot be selected again.

## What was built

**The defect.** `connectAbortDeadlineMsFor` returned `validate + encrypt + grace` and was justified
against `~158 500 ms` — the CLOSED cell of the create-with-key / composite-add-key serialized row in
`seam-budgets.invariant.test.ts`'s branch table. A healthy seam never keeps a browser waiting long
enough to reach a client deadline; the state a route is actually in when that deadline fires is the
FAILING one, which charges three breaker-store commands per seam call where the closed state charges
one. The governing figures are therefore **175 500 / 85 500**, and the deadline was short by the
identical **10 500 ms** (`failing_store − grace = 25 500 − 15 000`) on **both** arms — the shortfall
does not depend on the validate budget, which is precisely why a serialized-only fix would have been
this phase committing its own headline mistake.

**The fix.** A new client-safe hand-typed twin `BREAKER_STORE_WORST_CASE_FAILING_MS = 25_500`
(2 seam legs × 3 failing-state store commands × 4 250 ms), added to `connectAbortDeadlineMsFor`'s
**arm-agnostic** body — one edit, both arms:

| | serialized | default |
|---|---|---|
| route worst case, failing | 175 500 | 85 500 |
| deadline before | 165 000 ❌ | 75 000 ❌ |
| deadline after | **190 500** ✅ | **100 500** ✅ |
| margin | exactly `WAIT_ABORT_GRACE_MS` | exactly `WAIT_ABORT_GRACE_MS` |

Both remain far under the routes' 300 000 ms `maxDuration`.

**The oracle.** `seam-budgets.invariant.test.ts` gained *"the browser is the last party to give up"*
— for each of the two browser-aborted connect routes and each venue arm, the client deadline must
exceed the MAX over `BREAKER_STATES` of that branch's `worstCaseMs`, computed with the file's own
`branchWorstCases`. It carries three fences the pin it replaces did not have: hand-typed anti-vacuity
floors (2 routes, 2 arms), a states-covered floor, and a **structural arg-max pin** — the governing
state must *be* `"failing"`, at the hand-computed 175 500 / 85 500.

**The pin.** A fourth twin in `seam-constants.pin.test.ts` beside the existing trio, both halves
hand-typed per that file's own doctrine: the client constant equals the server-side derivation built
from `BREAKER_STORE_TIMEOUT_MS` / `_RETRIES` / `_BACKOFF_MS`, **and** equals a bare `25_500` typed in
the pin file.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 — Blocking] The hand-typed deadline composites in the two step suites**
- **Found during:** Task 2
- **Issue:** `ConnectKeyStep.test.tsx` and `MultiKeyConnectStep.test.tsx` each build their own
  `SERIALIZED_DEADLINE_MS = SERIALIZED_BUDGET_MS + ENCRYPT_BUDGET_MS + ABORT_GRACE_MS`. The plan's
  file list named only the three prose sites, but these composites are the same premise and 6 tests
  failed on them.
- **Fix:** Added a hand-typed `BREAKER_STORE_FAILING_MS = 25_500` to each with the derivation and the
  failing-vs-closed rationale written out, in the files' existing hand-typed-constant idiom.
- **Files:** both step test suites · **Commit:** `d3807e42`

**2. [Rule 1 — Bug, latent] `MultiKeyConnectStep` enforces its deadline on a 1 000 ms tick**
- **Found during:** Task 2
- **Issue:** That step has no per-panel `setTimeout` — it checks every panel from one 1 000 ms
  interval. `165 000` happened to be a whole number of ticks, so nobody had to notice; `190 500` is
  not, and the deadline is acted on at the first tick at or after it (**191 000**). Three tests that
  advanced to `deadline + 1` stopped seeing the abort.
- **Fix:** No production change — the rounding is **UP**, which is the safe direction (the browser
  still gives up last, by up to one tick more). Recorded as a hand-typed
  `SERIALIZED_DEADLINE_TICK_MS = 191_000` with the property written down, rather than absorbed into
  a `+ 1` that would hide it again.
- **Files:** `MultiKeyConnectStep.test.tsx` · **Commit:** `d3807e42`

**3. [Rule 2 — Prose that would become a wrong figure] `158_500` scrubbed from comments too**
- **Found during:** Task 1
- **Issue:** My first draft of both new comments quoted the refuted literal as `158_500`, which left
  it greppable in the very files that exist to stop wrong figures — the exact trap
  `seam-budgets.invariant.test.ts:152-158` records ("naming the DEFECT instead of reprinting it
  keeps the record and empties the scanner").
- **Fix:** Re-cut to the spaced prose form. `grep -rn "158_500\|158500" src/` → **0 hits**.
