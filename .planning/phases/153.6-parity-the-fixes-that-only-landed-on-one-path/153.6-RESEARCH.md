## Summary

Four of the five clusters are already fully traced in source; the research found no ambiguity about
*what is broken*, only about *which remedy shape is cheapest*. Three corrections to the CONTEXT's own
statements are recorded below and are load-bearing for planning.

**Cluster D is smaller than it looks, and the CONTEXT under-describes the ground truth in a way that
makes the fix much cheaper.** `/api/keys/validate-and-encrypt` persists **nothing** — it returns
ciphertext to the browser and that is all (`route.ts:326`). But the wizard — the only surface that
can connect an MT5 key — does **not** use a client INSERT at all: it POSTs
`/api/strategies/create-with-key`, which calls the **SECURITY DEFINER** RPC `create_wizard_strategy`
with `p_exchange: exchangeNormalized`, and *that RPC performs the `api_keys` INSERT server-side*
(`supabase/migrations/20260602190000_f6_wizard_session_idempotency.sql:130-138`). The composite twin
`add_wizard_composite_key` is structurally identical
(`20260710180000_wizard_composite.sql:125-137`). So a server-attested venue already exists inside a
privileged writer; it simply is not stored anywhere the probe gate reads. The recommended remedy is a
single nullable `api_keys.attested_venue` column written only by those two RPCs, plus a `BEFORE
INSERT` trigger that NULLs any client-supplied value — **no new grant or revoke** (D-02 satisfied
structurally), **no extra round trip** for the probe gate (it already does the admin `select` at
`route.ts:1162-1166`), and **no seam call** (which matters: `finalize-wizard`'s composite branch has
only 22 500 ms of headroom against the 300 000 ms ceiling, so a per-member decrypt round trip is
arithmetically impossible — see §Q3(c)).

**Cluster A's three twins are all in one function body each, and the extraction target already
exists in outline.** `services/mt5_validation.py` is the established "one seam both paths call", and
it imports only `services.mt5_client` — so a sibling `services/mt5_probe.py` importing both is a
clean third module with no cycle (D-07 satisfied). ⚠️ **A2 and B1 must be fixed in the same edit**:
adding the router's broad `except Exception` to the worker's `_read_terminal` would import B1 onto
the worker path. The correct single implementation catches `Mt5SessionAbandoned` and re-raises it
**before** the broad arm.

**Cluster C's arithmetic is exact, and the defect is bigger than the finding says: BOTH venue arms
are short by exactly 10 500 ms**, because the shortfall is `failing_store − grace = 25 500 − 15 000`,
a per-route quantity independent of which validate budget the branch spends. And the wrong-column
oracle is **not** in `seam-budgets.invariant.test.ts` — it is
`src/lib/wizard/validate-budget.test.ts:226`. Editing the file CONTEXT names would leave the real
guard untouched.

**Primary recommendation:** five plans, one per cluster, with D and A/B parallelisable. Land the
`services/mt5_probe.py` extraction (A+B1) before the parity guard, land the `_timed` sink fix (B3)
before or with it, and treat the cluster-D migration as the single highest-risk artefact of the
phase — it AUTO-APPLIES to PROD on merge and it carries a data backfill.

#### Q3. Candidate homes for a server-held venue record

**(a) A new column on `api_keys`, written only by the two SECURITY DEFINER RPCs, with a `BEFORE
INSERT` trigger that NULLs any client-supplied value. — RECOMMENDED.**

| Property | Answer |
|---|---|
| Migration needed? | Yes: `ALTER TABLE api_keys ADD COLUMN attested_venue text` + `CREATE OR REPLACE` of both RPCs + one `BEFORE INSERT` trigger + backfill. ⚠️ Auto-applies to PROD (§Q16). |
| Extra round trip for the probe? | **No.** The single-key arm already runs an admin `select("exchange")` at `:1164`; it becomes `select("exchange, attested_venue")`. The composite embed becomes `api_keys ( exchange, attested_venue )` with one field added to `compositeMemberRowsSchema` (`:159-164`). |
| Grant/revoke needed? | **No** — D-02 satisfied structurally. Migration 027 already column-allowlists `SELECT` (`20260410225608:20-40`), so a new column is simply *not granted* to `authenticated`, which is the correct posture: the client never needs to read it. Table-level `INSERT` is untouched, so a client *can* supply the column — the trigger is what makes that irrelevant. |
| Forgery resistance | The trigger is `SECURITY INVOKER` (so `current_user` is the real caller) and does `IF current_user NOT IN ('postgres','service_role','supabase_admin') THEN NEW.attested_venue := NULL; END IF;`. Inside a `SECURITY DEFINER` RPC `current_user` is the function owner → the RPC's value survives. A direct `authenticated` INSERT (including DELETE-then-re-INSERT) always lands `NULL` → `venueSupportsScopeProbe(null) === true` → **probed**. |
| ⚠️ SECURITY DEFINER trap | The migration header at `20260810120000:70-74` warns DEFINER made `prevent_profile_role_change` a no-op. That trap applies to a function that *checks a privilege*; this one *checks a privilege too*, so it must stay INVOKER — same as `prevent_api_key_venue_change` (`:114-116`). State this in the plan or a reviewer will "fix" it the wrong way. |
| Backfill | See §Q4. |

**(b) A new table (e.g. `api_key_venue_attestations`, keyed by `sha256(api_key_encrypted)`), written
by the mint route with the service-role client.**

| Property | Answer |
|---|---|
| Migration needed? | Yes (one new table), but **no DDL on `api_keys`** — genuinely lower blast radius on the security-critical table. |
| Extra round trip? | **Yes, one per key** — the probe must read `api_key_encrypted` (admin can; `authenticated` cannot, per migration 027's allowlist), hash it, and query the attestation table. On the composite branch that is up to 10 extra Supabase reads. Not a seam call, so `SEAM_ROUTE_BUDGETS`/SC-4b are unaffected — but it is real latency on the tightest route in the table. |
| Legacy rows | No attestation → probe. Same backfill problem as (a), plus a second one: rows minted-but-never-inserted accumulate and need retention. |
| Verdict | Viable fallback if the planner judges `api_keys` DDL too risky. Materially more moving parts. |

**(c) Binding the venue INTO the encrypted payload. — REJECTED, on arithmetic.**

`encrypt_credentials` builds `json.dumps({"api_key", "api_secret", "passphrase"})` under a Fernet DEK
(`encryption.py:73-80`); adding `"venue"` is trivial and `payload.get("venue")` degrades gracefully
for legacy rows. Fernet is authenticated (HMAC-SHA256), so the binding would be *cryptographic* —
strictly the strongest option. **But the probe gate is a Next.js route and has no KEK.** Reading the
venue requires a new analytics-service endpoint, i.e. a new seam leg on `finalize-wizard`. That
route's composite branch already sits at **277 500 ms failing against a 300 000 ms ceiling — 22 500
ms of headroom** (`seam-budgets.invariant.test.ts:120, :131-135`). A per-member decrypt leg at even
5 000 ms × 10 calls adds 50 000 ms of request budget plus `3 × 4 250 × 10 = 127 500` ms of store term
in the failing state. It breaches by a wide margin and SC-4b would red. A single batched call could
be made to fit, but it is a new seam surface for a value option (a) obtains for free. [VERIFIED:
source arithmetic]

**(d) Considered and not recommended: an HMAC'd venue token minted by the route and stored in a
client-writable column.** No new table, but needs a new server secret, a rotation story, and
verification code in the Next layer — more surface than (a) for the same guarantee.

#### Q4. The backfill question — what should the probe do for a pre-phase key?

**Recommendation: fail-toward-probing is the correct DEFAULT for the mechanism, and a one-time,
count-pinned backfill from `exchange` is the correct treatment for the enumerable legacy set. Do
both.** Reasoning:

1. **Pure fail-toward-probing (no backfill) would break PROD MT5 today.** All three live PROD MT5
   keys pre-date this phase [CITED: MEMORY.md — *"all 3 PROD MT5 keys sit at `sync_status='error'`"*].
   With `attested_venue` NULL they would be probed, and an MT5 ccxt permissions probe is the
   PERMANENT failure that 153.2-04 exists to prevent (`route.ts:740-747` states this in the code).
   Any re-finalize of an MT5 draft would then answer `KEY_SCOPE_CHECK_UNAVAILABLE` with no remedy.
   That is a self-inflicted regression on the milestone's own headline venue.
2. **A backfill is not "trusting the column forever" — it is a bounded, dated snapshot.** After the
   migration the column stops being the authority for every row created afterwards, and the residual
   is exactly "rows that existed on 2026-08-11 and had already been forged". `UPDATE` on the column
   has been revoked since 2026-08-10 (`20260810120000:104`), so a forgery would have required a
   DELETE + re-INSERT in that window — an event with a detectable footprint (`api_keys.created_at`
   later than the strategy that references it).
3. **Make the backfill count-pinned rather than blind.** Two `DO $$` self-verify blocks in the same
   migration, in the style the file already uses (`20260810120000:163-201`):
   - assert the number of rows backfilled to a probe-exempt venue equals a hand-typed literal (today
     expected `3` — ⚠️ **must be re-measured against PROD before merge**, OQ-1);
   - assert zero rows remain with `attested_venue IS NULL AND created_at >= <migration ts>`.
   A count that does not match aborts the migration. This converts "we trusted a column" into "we
   trusted N specific rows and wrote N down".
4. **Do not carve an exemption into the read path.** The probe gate must read `attested_venue` and
   nothing else; "if attested is null, fall back to `exchange`" is the hole that never closes, and it
   would make the whole phase a no-op for every existing row.

#### Q5. Is `exchange` genuinely the SOLE authority for skipping the probe?

**Confirmed, with one qualification.** [VERIFIED: source]

The skip is `if (!venueSupportsScopeProbe(venue)) return { ok: true };` (`route.ts:767-769`). There is
no second condition inside the helper. `venueSupportsScopeProbe` is
`venueCapabilities(venue)?.scopeProbeSupported ?? true` (`closed-sets.ts:196-200`), and the only row
with `scopeProbeSupported: false` is `mt5` (`closed-sets.ts:146`). `venueCapabilities` uses
`Object.hasOwn` (`:179-181`), so prototype keys cannot forge a row.

**The qualification:** reaching the helper at all is gated. The single-key arm runs only
`if (apiKeyId)` (`:1230`); the composite loop `continue`s on a member with no `api_key_id`
(`:1511-1513`). Those are absence-of-key conditions, not venue conditions — they do not weaken D-01,
but a plan that says "one gate" should say "one gate, behind an api_key_id presence check".

**Falsifiable oracles that already exist and must be re-pointed at the attested venue:** the two
CLASS SWEEPS at `finalize-wizard/route.test.ts:3712-3745` (single-key) and `:3747-3771` (composite)
drive `STATE.adminApiKeysExchange` / the embed's `exchange`. After D-01 they must drive
`attested_venue`, and a **new** case must assert that a row with `exchange='mt5'` and
`attested_venue='binance'` is **PROBED** — that single test is the whole cluster-D deliverable in
oracle form, and it is falsified by reverting the gate's read back to `exchange`.

### Cluster A — the shared module

#### Q6. Side-by-side diff-in-prose of the three missing twins

**A1 — the terminal short-circuit.**

*Router (`routers/exchange.py:663-706`, inside `_probe`):* after `terminal = _read_terminal()` at
`:670`, it asks the seam itself —
`if classify_trade_capability(info, {}, terminal) == "undetermined":` (`:698`) — and on a match runs
the POST bracket `_assert_expected_login(connected.account_info())` (`:702`) and returns
`info, {}, terminal` (`:703`) **without calling `order_check`**. The 27-line rationale at `:671-697`
records the incident: under MetaQuotes' default-ON *"Disable automatic trading through the external
Python API"* the `order_check` is refused, its `Mt5ClientError` leaves by the classify door, and
`_WRONG_SERVER_TOKENS` carries `"terminal"` — so an operator-side checkbox surfaced as a 400 telling
the user their broker server is wrong.

*Worker (`services/ingestion/mt5.py:247-259`, inside `_probe`):* identical up to
`terminal = _read_terminal()` at `:256`, then **unconditionally**
`probe = client.order_check(mt5_probe_request())` at `:257`, POST bracket at `:258`, return at
`:259`. **No short-circuit.** The exact documented incident is reachable on this path.

⚠️ The consequences differ by path and both are bad: on the router the incident is a 400; on the
worker the `Mt5ClientError` reaches `except Mt5ClientError as e` (`ingestion/mt5.py:307`),
`classify_mt5_login_error` returns `wrong_server`, and `_wrong_server()` (`:116-126`) returns
`ValidationResult(error_code="MT5_WRONG_SERVER", permanent=True)` — a **permanent, user-blaming**
verdict for an operator-side setting.

**A2 — the broad `except` around netref materialization.**

*Router (`:641-661`):* `try: return connected.terminal_info()` / `except Mt5ClientError as
terminal_err:` (logs `terminal_err.code`, returns `None`) / `except Exception as terminal_exc:` which
logs **`type(terminal_exc).__name__` only** and returns `None`. The comment at `:619-640` explains
the hole precisely: `_guarded_read` converts a *raise*, but the netref is materialized **after** that
wrapper returns, so a mid-materialization drop is a raw transport exception, is not an
`Mt5ClientError`, and escaped to an unhandled bodyless 500 (= SERVICE-PERMANENT under R-1).

*Worker (`:230-245`):* `except Mt5ClientError as terminal_err:` **only**. A materialization failure
escapes `_read_terminal` → escapes `_probe` → is caught by
`except Mt5ClientError as e` (`:307`)? **No** — it is not an `Mt5ClientError`, so it escapes

### Anti-patterns to avoid

- **Adding the router's broad `except Exception` to the worker's `_read_terminal`.** That imports B1
  onto the worker path. The single shared implementation must catch `Mt5SessionAbandoned` first.
- **Unifying the two lease-wait bounds or the two timeout chains.** Both divergences are deliberate
  and documented at the sites (`ingestion/mt5.py:73-90`, `:180-190`).
- **Fixing cluster C's number without the oracle.** D-10/D-11 explicitly make this half a job.
- **Fixing only the serialized arm of cluster C.** Both arms are short by the same 10 500 ms.
- **Deleting a pin to make a change pass.** `EXPECTED_TABLE_SIZE` has a meta-test that counts its own
  declarations; deletion is loud, and re-cutting is the documented remedy.
- **Falling back to `exchange` when `attested_venue` is null.** The hole that never closes.
- **`SECURITY DEFINER` on the new INSERT trigger.** It checks a privilege; DEFINER makes that check a
  no-op — the trap `20260810120000:70-74` records.

## Common Pitfalls

### P1 — Editing `seam-budgets.invariant.test.ts` for cluster C and shipping green
**What goes wrong:** the wrong-column literal is in `validate-budget.test.ts:226`, not there.
**How to avoid:** grep for `158_500` before and after; the count must go from 1 to 0.
**Warning sign:** the plan's diff touches only `.invariant.test.ts` and the suite stays green.

### P2 — The backfill breaks PROD MT5
**What goes wrong:** ship `attested_venue` with no backfill; the three live MT5 keys start being
probed and every MT5 finalize answers a permanent `KEY_SCOPE_CHECK_UNAVAILABLE`.
**How to avoid:** §Q4's count-pinned backfill, with the count re-measured against PROD first (OQ-1).
**Warning sign:** the migration has no `UPDATE … SET attested_venue` statement.

### P3 — Re-basing a SECURITY DEFINER function off a stale body
**What goes wrong:** `CREATE OR REPLACE create_wizard_strategy` from the 2026-04 definition silently
reverts F6's advisory-lock idempotency fence, re-opening double-submit duplicate drafts.
**How to avoid:** grep ALL migrations, re-base on the LATEST (`20260602190000`) [CITED: MEMORY.md].
**Warning sign:** the new function body has no `pg_advisory_xact_lock`.

### P4 — Re-stamping the `exchange` column comment and disarming the SQL test
**What goes wrong:** D-04's prose correction rewrites `COMMENT ON COLUMN api_keys.exchange` without
the `20260810120000` substring; `test_api_keys_exchange_not_user_writable.sql`'s gate goes false and
assertions 2 and 3 **SKIP** silently instead of failing.
**How to avoid:** preserve the substring; add a positive assertion that the gate evaluated true.

### P5 — The `KNOWN_FINALIZE_CODES` omission
**What goes wrong:** a new wizard code that is not added to `SubmitStep.tsx:316` falls to `UNKNOWN`.
For cluster E specifically this is insidious: `UNKNOWN`'s copy IS recoverable, so the Retry button
appears and the change looks like it worked while the honest copy never renders.
**How to avoid:** add the member in the same commit the route starts emitting the code; assert the
rendered title, not just the presence of a Retry control.

### P6 — Fixing a fence and re-introducing a leak
**What goes wrong:** restructuring `restart()` to move check 2 outside `_timed` breaks the three
interacting cleanup invariants at `mt5_client.py:1276-1295` (stale socket, fresh WR-01 socket,
`_closed` latch). 153.5 warns these are exactly where a fix creates two new leaks.
**How to avoid:** fix B3 at `_timed`, changing nothing inside `restart()`.

### P7 — Testing the helper instead of the wiring
**What goes wrong:** `mt5_probe.run_probe` is tested and passes while `ingestion/mt5.py` still holds
its own copy.
**How to avoid:** neuter the shared module and prove BOTH paths red [CITED: MEMORY.md — *"testing a
fix's helper ≠ testing the call site INVOKES it"*]. This is also what the ast roster is for.

    try:
        return client.terminal_info()

        # Absorbing it here would tell an operator the gateway failed to
        # materialize a netref, which never happened, and would let the probe

        raise
