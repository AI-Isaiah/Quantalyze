## What changed, per finding

### M2-01 (conf 9) — the pin was structurally un-recuttable

The MIG-01 fix made `v_sig` an equality target against one hand-typed date. That is fine while
PROD's probe-exempt rows share a creation day and impossible the moment they do not: the abort
requires **all** `c_pin_mt5` rows to carry the signature, so for any single date `v_sig < v_mt5`
and no choice of literals passes — while the block's own rule forbids softening the comparison.

Reviewer's option (a): `c_pin_dates CONSTANT DATE[]`, `v_sig` counted with
`(created_at AT TIME ZONE 'UTC')::date = ANY (c_pin_dates)`, one `v_dates` declaration rendering
the set into all three messages. The re-cut instruction now names exactly which literals move
(`c_pin_mt5` **and** `c_pin_dates`, together), why `c_pin_total` never needs re-cutting, and
restates the no-softening rule.

**The two-sided discriminator survives untouched** — `v_sig >= 1` is still the first test, so a
PROD apply cannot fall into the lenient branch, and a signature-free TEST/CI database still takes
it (re-measured, ledger `M2-01-twosided`).

### M2-02 (conf 9) — the guard that could not fail ⭐

Post-verify (d) read `col_description` on `api_keys.exchange` and asserted the `20260810120000`
marker survived *this migration's* re-stamp — but the re-stamp ran 129 lines later. (d) was
reading the comment `20260810120000` had written. The regression it names could not fail it.

Section 8 (both `COMMENT ON COLUMN` statements) now runs **before** the `DO $verify$` block,
renumbered 7 / 8. Everything was already inside the file's single transaction, so nothing else
moved. (d)'s own comment, the header's item list, and a ⛔ at the top of the new section 7 all
record that the order is the guard.

**Proven both ways with the same one-line mutation** (`'level by migration 20260810120000 and'` →
`'level by an earlier migration and'`):

| | Result |
|---|---|
| **Before the move** | `COMMIT` — and (d) printed `post-verify OK: … 20260810120000 marker preserved …` while `col_description(…) LIKE '%20260810120000%'` on the applied comment read **`f`** |
| **After the move** | `ERROR: Migration 20260811210000 failed: the api_keys.exchange comment no longer names 20260810120000 — the SQL test gate that arms assertions 2 and 3 would silently start SKIPPING. Rolling back.` |

⭐ The mutation was already caught downstream by SQL-test assertion 5a, which is precisely how a
guard that cannot fail survives review: the surface looks defended, so nobody checks whether the
inner guard is doing any of the defending.

### M2-03 (conf 8) — two claims that outlived the code

1. The header said the census pin means *"we trusted 29 specific rows and wrote the number down"*.
   MIG-01 demoted the total to a NOTICE; the pin now aborts on the **probe-exempt** population
   only. Rewritten to state what is enforced, why a non-exempt row cannot weaken the backfill's
   argument, and why the total is reported rather than enforced.
2. The permanent column comment said rows *"predating this migration"* were backfilled on
   2026-08-11. The cutoff is `2026-08-11T00:00Z`; the apply is 2026-08-12 or later. Now reads
   *"Rows created before 2026-08-11T00:00Z"*, matching the GUC, and states that a row in the gap
   lands NULL and is PROBED.

Claim 2 was falsified empirically rather than argued: a `deribit` row created `2026-08-11T12:00Z`
comes through the apply with `attested_venue` NULL (`UPDATE 29` of 30 rows). Nothing in the
migration would have reddened — the failing artifact was prose, which is why the ledger row says
so explicitly.

### M2-04 (conf 8) — the precondition, moved to where a venue author will trip over it

The CHECK makes the probe-skip bypass **self-defeating, not impossible**, and only while every
probe-exempt venue is unsyncable. That precondition lived only in `153.6-07-SUMMARY.md`, and
`src/lib/closed-sets.ts` already carries an OPEN QUESTION about giving sFOX the same opt-out.
A dev adding `scopeProbeSupported: false` to a syncable venue would make the forgery **free**
without ever reading a phase summary.

Now stated twice: a ⛔⛔ block in section 1b, and mirrored in the permanent `COMMENT ON COLUMN`
(so it is readable from `\d+ api_keys` with no repo access). Both name remedy (a) — service-role
writer plus withdrawing `authenticated` EXECUTE — as the thing that must land first, and both say
plainly that no constraint on these two columns can substitute for it.

D-02 discipline held: the comment says "withdrawing", never `GRANT`/`REVOKE`.

## Could anything NOT be fully closed?

**All five findings are closed.** Two carry residuals worth stating plainly rather than burying:

1. **M2-04 ships no guard, and the ledger records it as SKIPPED, not caught.** It is a
   documentation-placement fix; there is no mutation that reddens prose. The hazard it warns
   about — a *syncable* venue joining `scopeProbeSupported: false` — **is** mechanically
   falsifiable, but the test that would do it does not exist. The nearest existing oracle
   (`closed-sets.sfox-flag.test.ts`, ledger row `D-OQ3`) fires when a probe-exempt venue reaches a
   client-facing picker, not when one becomes syncable. A guard binding "probe-exempt ⇒
   unsyncable" is the honest follow-up and is **not** claimed as shipped here.

2. **M2-05 restores a false claim into an applied migration's header, and that is the trade.**
   Reverting `20260810120000` puts back the original "self-defeating forgery" residual, whose
   argument rests on a claim Phase 153.6 refuted. The correction is now in `20260811210000` — the
   newer migration on the same column, which names the older one throughout — and in `TODOS.md`.
   A reader who opens `20260810120000` alone and stops there still sees the refuted text. The
   alternative was to keep editing an applied migration, which is the invariant the finding
   exists to protect; between "an applied file records what ran, verbatim" and "no header
   anywhere is stale", the first is the one a later reader cannot recover if we break it.

Beyond the five findings, the phase's own standing residual is unchanged and still accurate as
written in `153.6-07-SUMMARY.md` §"Residual Risk": the RPC door remains open by decision, the
bypass is self-defeating rather than impossible, and only remedy (a) closes it.
