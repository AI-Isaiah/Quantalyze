## Area 1 — Cluster D: the venue lock is bypassable

**Framing given:** an owner can DELETE their `api_keys` row and re-INSERT it with a different
`exchange`, because `authenticated` keeps table-level INSERT and DELETE and the browser already holds
the server-minted ciphertext. That column is the sole authority for skipping `finalize-wizard`'s
scope-broadening probe. Live on PROD.

**Options presented:**

| # | Option | Completeness | Core trade-off |
|---|---|---|---|
| A | **Server-held venue is the authority** | 9/10 | Attacks the trust model; no REVOKE, no UI change; leaves the column writable but harmless |
| B | Revoke DELETE + SECURITY DEFINER delete RPC | 6/10 | Closes one half; runs into the line-181 warning; column still the probe's authority |
| C | INSERT trigger vs a server-held mint record | 8/10 | Validates the claim, but puts a trigger on the hottest write path |
| D | Full server-side key writes | 10/10 on the hole | Widest blast radius — regresses the path 153.4 just stabilised |

**Selected: A — Server-held venue is the authority.** (Recommended option.)

**Notes:** the user took the root-cause option over three cheaper write-path patches. Recorded in
CONTEXT as D-01..D-05, with D-02 explicitly forbidding a new REVOKE and D-03 accepting that the
column stays user-writable. Two consequences were folded in that the question did not itself raise:
the migration header states the opposite of the truth and must be corrected (D-04), and the existing
SQL test proves DELETE survives but never tests the round trip (D-05).
