## Keyword design (why a resolver and not a precomputed switch)
The switch date depends on the bills census, which only this walk produces, and a second full OKX walk can cost up to `DAILY_PNL_READ_DEADLINE_S` (RESEARCH "fetch_daily_pnl design": one read, booking in a post-step). So the keyword CONTEXT names carries the plan-01 `UnitSwitchResolver`: an async callable the fetch awaits once, after the walk, with the census. The derive builds it (plan 06); it reads the holdings evidence only when coin bills exist. Rated costly in CONTEXT; recorded here.

## Side channel shape created here
`UnitSwitchRead` frozen slots dataclass in exchange.py: `switch: UnitSwitch | None`, `refusal: str | None` (the closed token the resolver returned: a UNIT_SWITCH_REFUSALS member, or the derive's `holdings_read_failed` from plan 06), `census: dict[str, tuple[str, int]]`, `stable_by_day: dict[str, float]`, `coin_by_day: dict[str, float]` (native coin amounts per UTC day, days on or after `switch.last_usd_day`). Stored in a ContextVar `_LAST_UNIT_SWITCH_READ` reset to None at fetch_daily_pnl entry beside `_LAST_DQ_FLAGS.set({})`, drained by `get_and_clear_last_unit_switch_read()`. Set only when a resolver was passed and the census was non-empty.
