# Phase 170.6.1.1: ANONKEYID - Context

**Gathered:** 2026-10-13. The founder chose "Own phase, now" for the anon `api_key_id` exposure that DISCOVERYPHONE's planner measured on PROD.
**Status:** Ready for planning

<domain>
## Phase Boundary

Two grant changes on `public.strategies`, nothing else:
- `anon` must not be able to read `api_key_id`.
- `anon` must hold no INSERT, UPDATE or DELETE grant.

Every public page must keep working afterwards. This phase does not change policies, columns or the published gate.
</domain>

<decisions>
## Implementation Decisions
- **D-01 (founder, 2026-10-13):** This is its own phase, run now, beside the others. It does not depend on 170.6.1. DISCOVERYPHONE's venue function never returns a key id, and DISCOVERYPHONE plan 03 books the TODOS item `[170.6.1-ANON-STRATEGIES-API-KEY-ID]`. This phase closes that item. If this phase ships first, it books and closes the item itself, so whichever phase lands second must not re-book it.
- **D-02:** **Census first, revoke second.** A column-level revoke makes any anon query that names `api_key_id`, or selects `*`, fail with 42501. Before the migration, list every reader that queries `strategies` with the anon key or as a signed-out visitor:
  - pages under `src/app/` for /browse, /discovery, factsheets, OG routes and share links;
  - `src/lib/queries.ts`;
  - edge functions;
  - SECDEF functions, which are not affected.

  Each reader must be shown to keep working: either narrow its projection to an explicit column list without `api_key_id`, or prove it runs as service role or authenticated. The narrowing ships BEFORE, or in the same PR as, the revoke. A reader that breaks after deploy is a P1 outage.
- **D-03:** The grant shape is the planner's call, from the repo's own precedent. Grep `sec-005` and the `api_keys` column-grant pattern. The two shapes are:
  - revoke table-level SELECT from anon, then grant column-level SELECT on every other column;
  - a column-level REVOKE alone, if Postgres honours it against a table-level grant. It does not: a table-level SELECT covers all columns, so the table grant must be replaced by column grants.

  Write the decision into the plan with the evidence.
- **D-04:** anon's INSERT, UPDATE and DELETE on `strategies` are revoked at both table and column level. First confirm that no anon write path exists in code.
- **D-05:** The migration carries a catalogue-only verify, using `has_column_privilege` / `has_table_privilege` for anon on `api_key_id` and on the write privileges, plus a rollback and a SQL gate with RED-UNDER arms. It moves every census a new gate file moves. Pick the stamp against the PROD ledger tip at execution, marker query first. These stamps are held in flight: 20261013120000 (NAVBREACH), 20261014120000 and 20261014120100 (RECONMARKER), 20261015120000 (OUTAGEALERT), and 20261016120000, provisionally, for DISCOVERYPHONE.
- **D-06:** After the PROD apply, a live anon probe proves zero readable `api_key_id` values: `BEGIN READ ONLY; SET LOCAL ROLE anon; … ROLLBACK`, with the marker query first. An anonymous browser pass then covers /browse, /discovery, one factsheet, its OG image and a share link.
- **D-07:** migration-reviewer and rls-policy-auditor must both be clean before merge.

- **O-1 (orchestrator, 2026-10-14):** **Two merges, not one.** The plan-checker's W1 found a deploy-ordering window: on the push to main, `supabase-migrate.yml` applies a migration to TEST and then PROD while Vercel builds the same commit in parallel. A single PR carrying both the narrowing and the revoke can therefore leave PROD holding the revoked anon grants while the old `select("*")` readers are still the live deploy, which means 42501 on `/browse`, `/strategy/[id]`, the tearsheet and `/`, the P1 outage D-02 names. The window is closed by re-sequencing, not accepted:
  - **PR-A (no migration):** narrow the four anon readers to `STRATEGY_PUBLIC_COLUMNS`, move the Verified badge guards to `trust_tier`, the `Strategy.api_key_id` type change, the static census pin, and the live probe's reader arms. Safe on its own, because narrowing a select works under the current grants.
  - **PR-B (the migration alone):** opened only after PR-A's Vercel production deployment is READY on the PR-A merge SHA. It carries the revoke and the column grants, the SQL gate, the census moves, the rollback, the live probe's refusal and write arms, and the post-apply PROD probe.
  - Each PR has its own release commit: a VERSION bump and a CHANGELOG entry, the version re-picked from origin/main at ship time.
  - This resolves the "Claude's Discretion" item below: the narrowing ships AHEAD of the revoke, in its own PR, which D-02 allows ("BEFORE, or in the same PR as").
  - It also answers the checker's W6 (sizing): the work is split so no plan is above roughly 100k estimated tokens. Plans 01-04 are PR-A; plans 05-08 are PR-B.

### Claude's Discretion
- Whether the reader narrowing goes in the same PR as the revoke (preferred, if the census is small) or ahead of it. **Resolved by O-1: ahead of it, in PR-A.**
</decisions>
