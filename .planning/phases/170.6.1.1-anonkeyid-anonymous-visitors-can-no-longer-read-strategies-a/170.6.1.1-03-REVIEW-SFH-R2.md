## Findings

### R2-1 - MEDIUM (confidence 6) - The tearsheet PDF route turns the new throw into a cached 200 PDF of an error page
`src/app/api/factsheet/[id]/tearsheet.pdf/route.ts:183-228` against `src/app/factsheet/[id]/tearsheet/page.tsx:285`.
The route's pre-check reads `strategies` with `createAdminClient()` (line 183), so it still passes after the PR-B revoke. It then drives puppeteer to the anonymous tearsheet page, which now throws from `getFactsheetDetail` on a 42501 and returns a 500 error render. `page.goto` is never checked for `response.status()` / `ok()`, so `page.pdf()` prints the error page and the route answers 200 `application/pdf` with `Cache-Control: public, s-maxage=300`. The old `return null` produced a "Strategy not found" page that was equally printed, so this is inherited. The fix changes the render, not the route's blindness.
Scenario: PR-B ships with a missed column grant. The PDF download "works", delivers a document reading as an error, and the CDN holds it for 5 minutes. The route's own `catch` and Sentry capture never fire, because nothing throws in the route. The only signal is the page-side capture.
Fix: after `goto`, `if (!resp || resp.status() >= 400)` throw into the existing catch, which already captures and returns 500.

### R2-2 - MEDIUM (confidence 6) - Landing stats capture fires 3 events per page view with no throttle, on the most-visited anonymous page
`src/app/(marketing)/page.tsx` (`reported` helper in `getSocialProofStats`).
Under a column-grant outage, which the doc comment calls an expected failure class, every landing hit makes up to three unconditional `captureToSentry` calls. `shouldCaptureNow` in `src/lib/sentry-capture.ts` exists for exactly this, per the WR-06 note: per-request capture sites burn quota and drop other alerts during the incident. The `console.error` should stay unconditional. The remote capture should be throttled, keyed on `stat` plus code.
Related visibility limit, acknowledged in REVIEW-FIX: `null` and `0` render the same dash, so a visitor and a reviewer of the rendered page cannot tell an outage from a genuine zero. The only signal is Sentry. If the throttle is added, make sure the first event per window is still sent.

### R2-3 - MEDIUM (confidence 4) - `failAnonRead` fires the capture and throws without holding the promise
`src/lib/queries.ts` (`failAnonRead`, new in abafdb13c).
`captureToSentry` returns its import chain precisely so a serverless finish does not reap it. The repo's own precedent in `queries.ts` (`scheduleDerivedRowCapture`, SFH-R2-05) holds it with `after()` plus a `queueMicrotask` fallback. `failAnonRead` discards it and throws immediately, so the tagged `{op, code}` event can be lost on a cold finish.
Mitigation, and why confidence is low: the thrown error also reaches `onRequestError` in `src/instrumentation.ts`, which captures with `routePath` tags and the message (which contains the PostgREST message but not the `code` tag). So an alert most likely still lands, and the loss is the `code` and `op` tags. The same applies to the landing helper.
Fix: reuse `scheduleDerivedRowCapture(captureToSentry(...))` or equivalent in `failAnonRead` and the landing page.

Verdict: 3 findings (MEDIUM and above)
