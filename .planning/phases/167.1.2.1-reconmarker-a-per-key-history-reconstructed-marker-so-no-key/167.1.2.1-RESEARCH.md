## Summary

"Reconstructed" is inferred today from three different shapes of evidence, none durable and none per key: (a) `compute_jobs` rows with `status='done'` (Python `_api_key_already_reconstructed`; reaped after 30 days by `retention_compute_jobs_done`), (b) `compute_jobs` rows in `('done','pending','running','done_pending_children')` (the RPC gate `v_prior_reconstruct`, which omits `failed_retry`), and (c) allocator-wide `allocator_equity_snapshots` row existence (the fan-out's zero-snapshot bootstrap and the Python refresh hold). Replacing all of them with two columns on `public.api_keys` is straightforward: `api_keys` is a service-role-written table where `authenticated` and `anon` hold NO `UPDATE` and NO `INSERT` privilege and only a per-column `SELECT` allowlist, so new columns are un-writable and un-readable by clients by default (no leak, no policy change needed). No view or trigger exposes `api_keys` columns.

The real complexity is not the columns. It is (1) the SQL gate corpus: the fan-out gate `supabase/tests/test_refresh_fanout_zero_snapshot_bootstrap.sql` (32 `RED-UNDER-M` arms) is hard-wired to migration `20260928140000`'s text AND encodes the semantics this phase deletes (arm N5, "a book with snapshots is never sent a bootstrap reconstruct", is the exact inverse of SC-2/SC-4); (2) D-07 reverses the 2026-04 stale-curve fix and inverts three existing pytest arms; (3) the PR-split must be ordered so no Python code writes a column PROD does not have yet; and (4) the D-05 backfill only recovers keys with a `done` job from the last 30 days, so on PROD every older key is "owed" and will be re-reconstructed by the daily fan-out (a sole-key reconstruct DELETEs and re-INSERTs the allocator's snapshot rows). That last item is the highest-impact finding and is raised as Open Question 1.

**Primary recommendation:** Two columns + CHECK on `api_keys`, no client grant in PR 1 unless the reader (PR 2) needs it; PR 1 = migration M1 (columns, backfill, RPC re-base adding `failed_retry` to the reconstruct gate and the marker as an extra skip) + Python D-07 (no new-column access, safe at any deploy order); PR 2 = migration M2 (re-run backfill, fan-out re-base with an owed-key arm that increments `history_reconstruct_attempts` at enqueue and stops at 5, per-run cap kept) + Python (marker set on completion AND on the already-reconstructed short-circuit, `_api_key_already_reconstructed` reads the marker, refresh hold reads the marker, Sentry event at the cap) + the reader. Write the new SQL gate and rewrite the old fan-out gate against the new migration file, and move every census file in the same PR.

### Pattern 1: Sentry EVENT vs breadcrumb (the codebase's convention)
**What:** An event is an explicit `sentry_sdk.capture_message`/`capture_exception` inside a throwaway scope, tagged with the job, one static message per condition so Sentry groups them, and no key id, allocator id or USD figure. A `logger.warning` is only a breadcrumb: `sentry_init.py` keeps the default `LoggingIntegration` whose event level is ERROR (stated in the comment at `equity_reconstruction.py:4092-4096`).
**Example (verbatim, `analytics-service/services/equity_reconstruction.py:4099-4107`):**
```python
with sentry_sdk.new_scope() as scope:
    scope.set_tag("compute_job_id", str(job.get("id")))
    scope.set_tag("refresh_outcome", "book_emptied")
    sentry_sdk.capture_message(
        "refresh_allocator_equity_daily: book_emptied, every counted "
        "account is proven empty and today's legacy snapshot was "
        "written as $0",
        level="warning",
    )
```
Second precedent: `job_worker.py:3002-3009` `_capture_read_failure` (`capture_exception` with a `compute_job_id` tag) and `job_worker.py:12424-12433` (`derive_refusal` tag). There is no shared "capture an event" helper; the idiom is the inline `new_scope()` block. [VERIFIED: equity_reconstruction.py:4099-4107, job_worker.py:3002-3009, job_worker.py:12424-12433]

### Q4. D-06 fan-out, dedupe, claim path, replace scope, cap and Sentry

**Enqueue and dedupe.** `enqueue_compute_job` → `_enqueue_compute_job_internal` (current 10-param body, `supabase/schema/functions/_enqueue_compute_job_internal.sql`): optimistic look-up of `compute_jobs WHERE api_key_id = p_api_key_id AND kind = p_kind AND status IN ('pending', 'running', 'done_pending_children')`, then `INSERT ... ON CONFLICT DO NOTHING`, then a re-read; if the winner already left in-flight it raises `serialization_failure` ("enqueue race lost"). The dedupe arbiter is the partial unique index (baseline.sql:13852):
```
CREATE UNIQUE INDEX "compute_jobs_one_inflight_reconstruct_per_api_key" ON "public"."compute_jobs" USING "btree" ("api_key_id", "kind") WHERE (("api_key_id" IS NOT NULL) AND ("kind" = 'reconstruct_allocator_history'::"text") AND ("status" = ANY (ARRAY['pending'::"text", 'running'::"text", 'done_pending_children'::"text"])));
```
`failed_retry` is NOT in that predicate, so an enqueue while a job sits in `failed_retry` inserts a second `pending` row. `idempotency_key` (CHECK `compute_jobs_idempotency_key_safe`, regex `^[A-Za-z0-9_:.-]+$`, length ≤ 128) is a label, not a constraint. Consequently the owed arm's own `NOT EXISTS` must list `failed_retry` as in-flight (the current body already does).

**Claim path** (`supabase/schema/functions/claim_compute_jobs_with_priority.sql`): partitions by `(kind, api_key_id)` and keeps `rn_k = 1`; a `failed_retry` row is held back while a `pending` row of the same `(kind, api_key_id)` exists. So a fan-out enqueue that coexists with a `failed_retry` job runs the new job first, and the old `failed_retry` row may then be claimed again afterwards (a second crawl). This is why SC-5 matters and why the owed arm must treat `failed_retry` as in flight.

**Does a reconstruct replace the allocator's snapshots?** Yes, in exactly one case. `run_reconstruct_allocator_history_job` calls `replace_equity_snapshots` (:3708) only when `not sibling_check.has_siblings` (:3699); otherwise `persist_equity_snapshots` (ON CONFLICT DO NOTHING, first writer wins, :3716). `replace_allocator_equity_snapshots` (verbatim body fragment): `PERFORM pg_advisory_xact_lock(hashtext('alloc:' || p_allocator_id::text)); DELETE FROM public.allocator_equity_snapshots WHERE allocator_id = p_allocator_id;` then `INSERT ... ON CONFLICT (allocator_id, asof) DO NOTHING`. ## Common Pitfalls

### Pitfall 1: The fan-out gate is hard-wired to the migration it replaces
**What goes wrong:** M2 re-bases the function; `sql-tests` (all migrations applied) runs the old gate against the new body and goes red on N5/N4d/F/B/C/S/MX, while `sql-mutation` (explicit apply list) stays green on the old file, hiding it until the full corpus runs.
**Why it happens:** `RED-UNDER-SETUP` names `20260928140000...sql` and each `RED-UNDER-M` edit's `find` text lives in that file.
**How to avoid:** rewrite or retire the gate in the same PR as M2; append M2 to the apply list and repoint every `edit`; run `node scripts/mutation-runner/run.mjs` once and move all census files from that run.
**Warning signs:** `sql-tests` red on arm N5; mutation runner "annotation that does not bite".

### Pitfall 2: Python writes a column PROD does not have yet
**What goes wrong:** `UPDATE api_keys SET history_reconstructed_at` 400s until M1 applies.
**How to avoid:** marker writer in PR 2 (Q6), heal on the short-circuit.

### Pitfall 3: Counting attempts where only some failures pass
**What goes wrong:** a handler-side or dispatch-hook counter never sees a preflight exception, a reaped job or an orphan-terminalized job; the key retries forever and the cap never fires.
**How to avoid:** increment at enqueue in the fan-out transaction (Q1/Q4).

### Pitfall 4: D-05 turns every key older than 30 days into a mass reconstruct
See Q3 and Open Question 1.

### Pitfall 5: A new reason in the TS union silently hides a ready curve
**What goes wrong:** Route A gates `equityHistoryState`; a legacy-store backfill failure then blanks a trustworthy v2 history.
**How to avoid:** Route B (non-gating note) unless the founder says otherwise.

### Pitfall 6: Deribit and strategy-linked keys reported as "could not be rebuilt"
They are never enqueued, never counted, never marked. The reader predicate must include the attempts condition or the same qualifying filter.

### Pitfall 7: D-07 inverts three passing tests silently
Delete-and-forget would also delete the only guard on the OLD fix. Invert with the D-07 reason, so the trade-off stays readable.

## Open Questions (RESOLVED)

All five were resolved on 2026-10-13 after this research was written: OQ1 by founder decision D-12, OQ2-OQ5 by orchestrator decisions D-13 to D-16 (`167.1.2.1-CONTEXT.md`, "Decisions after research"). The original text is kept below as lineage; each question names its resolving decision.

1. **Mass re-reconstruct of keys older than 30 days (founder / plan-phase).** RESOLVED by **D-12**: the backfill also reads audit-log success events, and a counts-only PROD census goes to the founder before PR 2 merges (plan 08).
   - What we know: D-05 backfills only keys with a retained `done` job (≤ 30 days). Everything else starts owed and the PR-2 fan-out reconstructs it, up to the per-run cap (25 keys/run today). A sole-key reconstruct DELETEs and re-INSERTs the allocator's snapshot rows.
   - What's unclear: how many PROD keys that is, and whether replacing live-written rows with replay-derived rows for them is acceptable.
   - Recommendation: keep the 25-key per-run cap on the owed arm; run the read-only count (owed = qualifying, marker NULL after backfill; counts only, marker query first) BEFORE merging PR 2 as well as after (D-11 specifies after; an earlier count is the same read-only query and de-risks the merge); ask the founder whether to also union durable `audit_log` evidence (`action IN ('allocator.equity.reconstruct_complete','allocator.equity.reconstruct_partial_unsupported','allocator.equity.reconstruct_no_data','allocator.equity.reconstruct_unexpected_noop')`, `entity_id` = api_key id) into the backfill. That would shrink the owed set; it widens D-05 so it needs an explicit yes.
2. **Does SC-5 also cover the poll prefetch list?** RESOLVED by **D-13**: `failed_retry` goes into the reconstruct gate only; the poll prefetch list and `c_pre_re` are unchanged.
   - What we know: ROADMAP SC-5 says "status list includes `failed_retry`, as the cron's does"; D-08 says "status lists". The RPC has two lists: the reconstruct gate (:207) and the poll prefetch (:178). The `failed_retry` omission matters for the reconstruct gate (double crawl, Q4).
   - What's unclear: adding `failed_retry` to the poll prefetch changes "Sync now" during a poll backoff (30 s to 1 h) from "enqueue a fresh poll that supersedes the retry" to `{already_inflight, next_attempt_at}`, i.e. the owner cannot force a sync until the retry fires. That is a user-visible behaviour change and the copy-check arm `c_pre_re` pins the list literally.
   - Recommendation: add `failed_retry` to the reconstruct gate only; leave the poll prefetch alone unless the founder says otherwise.
3. **Where does D-09's "history could not be rebuilt" surface, and does it gate?** (Q8) Recommendation Route B; confirm in plan-phase. RESOLVED by **D-14**: Route B, a non-gating note mirroring `departedHistoryUnavailable`, excluding Deribit and strategy-linked keys (plan 06).
4. **`reconstruct_unexpected_noop` and the marker (A3).** RESOLVED by **D-15**: no marker on that outcome; the key stays owed (plans 01 and 05). Recommendation: do not set the marker for a sole-key DONE that wrote 0 rows from a non-empty payload; it is an anomaly the existing audit already flags.
5. **Should reconnect (`reconnect_allocator_api_key`) or a successful re-sign-in reset `history_reconstruct_attempts`?** RESOLVED by **D-16**: out of scope (not required by SC-1..7); recorded as a named residual in plan 09's CHANGELOG entry. A capped key whose owner fixes the credential would otherwise stay capped. Recommendation: reset to 0 in the same UPDATE that `reconnect_allocator_api_key` already performs (re-base on its latest definition first); not required by SC-1..7, so book it explicitly if deferred.
