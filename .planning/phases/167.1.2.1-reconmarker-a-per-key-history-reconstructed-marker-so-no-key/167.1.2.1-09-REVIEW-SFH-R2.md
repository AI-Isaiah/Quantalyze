## Findings (MEDIUM and above)

### R2-1 - MEDIUM (confidence 7): the F3 fix can cap a key with no job ever run, and that route has no Sentry event
- Location: `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql:355-362` (book handler counting `v_boot_key`); event source `analytics-service/services/job_worker.py` `_capture_history_reconstruct_capped` / `report_orphaned_capped_reconstructs`.
- Scenario: the book handler now burns one attempt for ANY exception that escapes the per-key handler, which catches only `serialization_failure` and `unique_violation`. A `deadlock_detected` or `lock_not_available` on the attempts UPDATE, a statement timeout, or an error raised while the cursor advances (blames the last cleanly enqueued key, an innocent one, as the comment's residual (iii) admits) counts as a failed try. Five such days cap the key although no reconstruct job existed, so the key is never enqueued again and its history stays unrebuilt.
- Why it is silent: both Sentry routes for D-09 start from a compute job (`dispatch` terminal, or an `orphaned` job). A key capped by the book handler has neither. The only traces are `bootstrap_book_skipped` rows (one per day) and the daily `history_reconstruct_capped` cron_runs row, and the round-1 F1 point stands for those: nothing in the non-planning tree reads `cron_runs` for `equity_refresh_fanout`. The Overview note still shows, but the operator-facing "loud at five" claim is untrue for this route. Round 1 F1 was closed for the orphan route only.
- Hidden errors: transient lock/deadlock/timeout errors in a book; an innocent key blamed by cursor-advance errors.
- Recommendation: either narrow the count to errors that are not transient (re-raise-and-skip `deadlock_detected`, `lock_not_available`, `query_canceled` without counting), or give the capped-by-failure route a Sentry source (a prober or worker check on `cron_runs` `history_reconstruct_capped` rows in the last 25h), or book that read as a routed deferral with a gate.

### R2-2 - MEDIUM (confidence 6): the orphan sweep marks a job reported before the event is evaluated, so a transient read failure loses the capped event for that job for good
- Location: `analytics-service/services/job_worker.py` `report_orphaned_capped_reconstructs`, the loop that does `_orphan_cap_reported.add(job_id)` before `await _capture_history_reconstruct_capped(...)`, with `_orphan_cap_reported.intersection_update(listed)` afterwards.
- Scenario: `_capture_history_reconstruct_capped` catches its own key-read failure, sends a generic `capture_exception` (no capped message) and RETURNS normally. The sweep cannot tell that apart from "evaluated, not capped", the id stays in `_orphan_cap_reported`, and every later tick skips it until it leaves the 3-hour window. If that orphaned job was the fifth attempt, the "key capped and unmarked" event never fires. What reaches Sentry is a bare exception with the compute-job tag, not the grouped capped issue the operator watches. The outer `except` in the sweep (a raise from the hook) only logs a warning and ALSO leaves the id marked, so even a raising hook loses the event.
- Hidden errors: transient PostgREST/network failure on the `api_keys` read for exactly the job that matters.
- Recommendation: add the id to `_orphan_cap_reported` only after the check returns a verdict (make the hook return a bool or raise on read failure), and discard the id on the `except` path so the next tick retries inside the window. The docstring already says a duplicate is chosen over a lost event; the code does the opposite for a read failure.
- Minor, same code: `limit(100)` plus `intersection_update(listed)` means ids past the first 100 are neither examined nor remembered; below MEDIUM.
