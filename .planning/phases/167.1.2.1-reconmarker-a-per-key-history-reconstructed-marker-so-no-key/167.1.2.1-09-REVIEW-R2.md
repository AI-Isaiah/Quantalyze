## Warnings

### WR-01: The Overview note's predicate is a third copy of the fan-out's capped-key predicate, and nothing pins it to the SQL

**Severity:** MEDIUM · **Confidence:** 6/10
**File:** `src/lib/queries.ts:4572-4582`. The SQL side is `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql`, the `ck` count. Compare `analytics-service/tests/test_fanout_owed_predicate_twins.py`.

**Issue:** Round 1 asked whether the copies of the predicate could drift. The fix answered that for Python only: `test_fanout_owed_predicate_twins.py` reads the newest migration's `rk` conjuncts and fails on any term it does not know. The TS note re-spells the same predicate as hand-typed literals:

- `["revoked", "sign_in_failed", "error"]`
- `"deribit"`
- `is_active`
- `disconnected_at`
- the link set

The only thing tying it to the SQL is the comment "Keep this in lockstep with the SQL predicate in migration 20261018120000 (aliases ck, cks, cksk, ckks)". Grepping `src/__tests__` and `src/lib/*.test.ts` for `20261018120000` finds only the mutation-annotation parser test. `history-reconstruct-cap-twins.test.ts` pins the cap value and nothing else.

**Scenario:** A later migration adds a qualifying term to the fan-out, for example a new non-retryable `sync_status`. It updates `rk`, `bq` and `ck`, and the Python twin test goes red until Python follows. The TS predicate does not follow and no test notices. A capped key in the new state is no longer counted by the fan-out's `history_reconstruct_capped` row, but the Overview still shows "The history of at least one connected account could not be rebuilt after repeated attempts". That is the round-1 WR-02 false note, re-entered through drift. The reverse drift, where a term is removed in SQL, hides a key that really is capped. The comment's own wording, "keep in lockstep", is the mechanism this repo records as insufficient.

**Fix:** Add a vitest twin of the Python test. It should:

1. read the newest migration defining `enqueue_refresh_allocator_equity_for_all`;
2. classify every conjunct of the `ck` count;
3. assert that the sync_status literal set equals a constant the TS predicate imports, rather than an inline array;
4. drive `derivePhase07Fields` once per term, with attempts at the cap and one attribute varied.

Better still, export one `NON_RETRYABLE_SYNC_STATUSES` constant from `src/lib/constants.ts` and have both the predicate and the test use it.

### WR-02: The note still says "could not be rebuilt" while the fifth attempt is in flight (the unaddressed half of SFH F4)

**Severity:** MEDIUM · **Confidence:** 5/10
**File:** `src/lib/queries.ts:4572-4582`. The increment is at `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql`, inner block, at enqueue time. The copy is at `src/app/(dashboard)/allocations/AllocationDashboardV2.tsx:443`.

**Issue:** The fan-out increments `history_reconstruct_attempts` when it enqueues (D-17), not when a job ends. Two consequences:

- The moment the 05:00 run enqueues a key's fifth attempt, that key reads `attempts = 5` with the marker NULL, and the new predicate raises the note.
- The job can then sit `pending`, `running`, or in `failed_retry` backoff for up to `max_attempts` (3) job-level retries. That window lasts hours, not minutes.

Round 1's F4 named this case ("the note can appear a day before the attempt has failed … exclude keys with an in-flight reconstruct if the column is available"). The fix commit (`166e1fe41`) addresses only the qualifying-column half. Nothing in the diff, its tests or its comments decides the in-flight half, either by fixing it or by recording it as accepted.

**Scenario:** A key fails attempts 1-4 because the exchange is rate-limiting. On day 5 the fan-out enqueues attempt 5, and it lands in `failed_retry` behind a backoff. For the rest of the morning the allocator reads "could not be rebuilt after repeated attempts". At 11:00 the retry succeeds, the marker is stamped and the note disappears. For those hours the dashboard reported a terminal failure that never happened. The Python side treats this exact state as "waited on" (`_RECONSTRUCT_IN_FLIGHT_STATUSES`), so the two surfaces disagree about the same key at the same moment.

**Fix:** Exclude keys with a reconstruct in flight. The dashboard already batches owner-scoped reads; add one more:

```ts
// compute_jobs: kind = 'reconstruct_allocator_history',
// status in ('pending','running','done_pending_children','failed_retry'),
// api_key_id in owner's key ids
```

Pass the resulting id set into `derivePhase07Fields`, excluding it as the link set is excluded and failing closed (`null`, so no note) on a read error. Then add a test with attempts at 5 and one job in each in-flight status. Alternatively, if it is accepted as a known limit, record that decision in CONTEXT and the field's JSDoc so it is no longer silent.

## Checked and not raised (below MEDIUM or by design)

- **F3 under a systemic enqueue failure.** A multi-day systemic failure now advances the newest key of every book toward a cap that is never reset (D-16). The cap was already exposed in the same way through worker-side failed_final jobs during an outage of five days or more, so this is not a new class. `_enqueue_compute_job_internal` has no routine backpressure raise; its only raises are structural, plus the lost-race `serialization_failure` that the per-key handler catches. One edge: `deadlock_detected` (40P01) is not caught per key, so it now burns an attempt. That is LOW.
- **F3 when the count is refused by the same cause.** If the error that failed the book was a trigger on `api_keys` UPDATE, the handler's own UPDATE fails the same way. It falls to a WARNING and counts nothing. This is narrow, and the skipped-book row is still written.
- **Orphan sweep `.limit(100)` with no ORDER BY.** Combined with `intersection_update`, more than 100 orphaned reconstruct jobs inside 3 h would churn the reported set and re-report jobs. That needs a mass worker-death event, so it is LOW.
- **Python twin pins only `rk`.** `bq` is a separate copy (arm O4 already needs both edited). Drift between `bq` and `rk` is a pre-existing SQL-internal risk, so it is LOW.
- **TS `deriveStrategyLinkedKeyIds` treats a NULL `status` as live, while SQL `<>` treats it as not linked.** This only matters if `strategies.status` can be NULL. It predates this diff, so it is LOW.
