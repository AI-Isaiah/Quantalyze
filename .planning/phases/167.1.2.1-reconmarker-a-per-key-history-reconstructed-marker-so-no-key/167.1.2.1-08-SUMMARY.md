## How the census ran

- Marker query ran first and alone, from the main checkout (Supabase CLI linked to PROD). Its
  answer names production. The raw marker text is not pasted here.
- The census file begins with the same marker query, then `BEGIN READ ONLY;` and
  `SET TRANSACTION READ ONLY;`, then one `SELECT` made of CTEs. The transaction was read-only
  (confirmed on the wire with `current_setting('transaction_read_only')` = `on` before the run);
  it was never committed, and no statement writes.
- The census output carries its own check (`marker_names_prod = true`), evaluated in the same
  statement.
- Predicates were copied from the committed migrations, not rewritten:
  - Qualifying filters, in-flight list and cap: the `rk` per-key query of M2
    (`20261018120000_refresh_fanout_owed_key_reconstruct.sql`): active, not revoked, sync_status
    not `sign_in_failed`/`error`, not disconnected, not Deribit, not linked to one of its owner's
    non-archived strategies (`strategies.api_key_id` or `strategy_keys`); owed = marker NULL,
    `history_reconstruct_attempts < 5`, no `reconstruct_allocator_history` job in `pending`,
    `running`, `done_pending_children` or `failed_retry`.
  - Evidence rule: the `newest_outcome` / `done_job` / `evidence` CTEs of
    `public.backfill_api_keys_history_reconstructed_at()` in M1
    (`20261014120000_api_keys_history_reconstruct_marker.sql`), including the owner match, the
    four outcome actions, `days_written`, the 2026-04-24 03:12:38+00 bound, the echo and
    transient-failure exclusions and the `reconstruct_unexpected_noop` rule, evaluated as a
    SELECT. The function itself was never called.
  - `owed_after_rerun` = `owed_now` keys for which that evidence yields no marker.
  - Sole-key book = an owner with exactly one `api_keys` row of any state, which is the worker's
    own sibling test (`_allocator_has_other_api_keys`: any surviving row of the same owner).
  - `drain_runs` = ceil(`owed_books` / 25), the `v_bootstrap_cap` of M2.

## In plain words

PR 2's fan-out will retry 3 keys in total, in 3 different books, and all of them fit in a single
daily run (the per-run cap is 25 books), so the drain takes 1 day. All 3 books already have
snapshot rows, which is exactly SC-2's population (a book with snapshots whose key was never
reconstructed, never retried before). None of the 3 books is a sole-key book (the one
single-key owner on PROD is not among them), so the sole-key replace path in
`replace_allocator_equity_snapshots` is not taken for any of them: the reconstruct writes with
first-writer-wins semantics and no recorded row is replaced by a replay. No key is at the
attempt cap today (as expected before PR 2). The D-12 audit-log evidence did its job: of 4
qualifying keys, 1 is already marked and the 3 owed ones have no retained success evidence.

## Surprises

- The population is far smaller than D-12 feared. D-12 expected "almost every PROD key older
  than a month" to be owed without audit-log evidence; on PROD only 4 keys qualify at all, because
  most keys are strategy-linked, Deribit, disconnected or inactive (the fan-out never touches
  those).
- The 127 reconstruct audit rows yield only 4 markers table-wide; the likely reason is the evidence
  rule (WR-01, WR-02, B1, SFH-2, the owner match) plus many audit rows belonging to keys that
  are no longer in `api_keys` or share a key (not measured here), so a reader expecting "one
  marker per audit row" will be surprised.
- Re-run rule: if plan 09's review round changes M2's owed predicate, qualifying filters,
  `v_reconstruct_attempt_cap`, `v_bootstrap_cap` or the backfill evidence rule, re-run this
  census and restate the counts to the founder.
