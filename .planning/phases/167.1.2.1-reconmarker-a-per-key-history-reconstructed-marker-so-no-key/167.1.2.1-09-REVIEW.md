# Phase 167.1.2.1 plan 09: Code Review Report (PR 2)

**Reviewed:** 2026-10-14
**Depth:** deep (worker writer and hold traced against the M2 fan-out, the PR 1 backfill, `_allocator_has_other_api_keys`, `_enqueue_compute_job_internal` and the dashboard reader)

## Summary

These parts are sound:

- **Fan-out rewrite.** M2 is re-based exactly on `20260928140000`: the rollback function body diffs byte-equal to it, comments stripped. The fan-out takes one attempt per enqueue inside the inner block, and the owed predicate excludes in-flight jobs. As a result, neither a lost race nor a rolled-back book burns an attempt, and no attempt is counted twice. `_enqueue_compute_job_internal` dedupes only on in-flight status, never on the reused `reconstruct-alloc-<key>-initial` label, so a retried key really does get a new job.
- **Cap twins.** The SQL, Python and TypeScript copies are pinned equal by reading the newest declaring migration, plus a hand-typed founder value.
- **Rollback.** It restores the previous function, its grants and its comment.

There are three findings:

1. The new marker writer stamps a key as reconstructed on two outcomes that this phase's own PR 1 backfill classifies as transient failures, not completions.
2. The Python refresh hold can freeze a zero-snapshot book permanently. The case is one the docstring calls a bounded residual, but it is not bounded.
3. The Overview note reads every key the owner has ever had. It shows "a connected account could not be rebuilt" for disconnected, revoked or later strategy-linked keys, and nothing ever clears it.

## Critical Issues

### CR-01: The marker is stamped on outcomes the backfill rules are NOT a completed reconstruct (sibling or snapshot lookup failed)

**Severity:** HIGH · **Confidence:** 8/10
**File:** `analytics-service/services/equity_reconstruction.py:3963` (the stamp gate), with `:3788-3790`, `:1489-1507` and `:3909`. Contradicts `supabase/migrations/20261014120000_api_keys_history_reconstruct_marker.sql:266-277`.

**Issue:** The stamp gate is `if audit_kind != "allocator.equity.reconstruct_unexpected_noop"`, and D-15 is the only exclusion it makes. Two other outcomes reach the gate and get stamped:

- **Sibling lookup failed.** `_allocator_has_other_api_keys` raises, and the fail-safe returns `has_siblings=True, lookup_failed=True` (`:1489`, `:1506`). The worker then takes the multi-key `ON CONFLICT DO NOTHING` path. Because `has_siblings` is True, the `unexpected_noop` branch at `:3909` cannot fire, so even `count == 0` with rows in hand is classified `reconstruct_complete`. The marker is stamped.
- **Snapshot lookup failed.** `EmptyReplaceRefusedError` with `lookup_failed=True` falls through as `reconstruct_no_data` carrying `snapshot_lookup_failed=true`. The marker is stamped. The comment at `:3956-3958` says this is intentional.

The PR 1 backfill (SFH-2, `20261014120000:266-277`) calls exactly these two rows "TRANSIENT FAILURES, not outcomes … Neither says the key's history was rebuilt; the next run of the worker may". It removes them from the evidence before it picks the newest event. So the same phase holds two definitions of "reconstructed": the backfill withholds the marker on these rows, and the live writer grants it on them.

**Scenario (data integrity):** A sole-key book already has stale or orphan snapshot rows, which is the case the sole-key replace exists for (see the `/investigate 2026-04-22` comment). The owed key's reconstruct runs, and the `api_keys` sibling count hits a transient PostgREST error. The worker falls back to DO NOTHING: every reconstructed row collides with an existing row and is dropped (`days_written: 0`). The audit says `reconstruct_complete` with `sibling_check_failed: true`, and the marker is stamped. From then on:

- the fan-out never enqueues the key again;
- `request_allocator_holdings_sync` treats it as reconstructed (O-2: the marker is authoritative);
- the Overview note never fires;
- the hold releases.

The stale curve becomes permanent. Nothing that reads the marker shows that the key's history was never rebuilt. Before this phase, the 30-day retention of `done` jobs at least bounded the false "done". The marker has no expiry.

The writer tests do not cover the case. `test_reconstruct_marker_writer.py` has no case with `lookup_failed`, `sibling_check_failed` or `snapshot_lookup_failed`.

**Fix:** Apply the backfill's rule in the writer, so one rule decides what counts as completion. Leave both transient outcomes owed, so the next fan-out retries them under the cap.

```python
transient_outcome = sibling_check.lookup_failed or purge_snapshot_lookup_failed
if audit_kind != "allocator.equity.reconstruct_unexpected_noop" and not transient_outcome:
    await _mark_api_key_history_reconstructed(...)
```

Add a pytest for each of the two cases that asserts the marker stays NULL and the job still ends DONE. Each test must be RED on the current gate. Better still, factor the "is this a completion" predicate into one helper that a test pins against the backfill's exclusion list.

## Warnings

### WR-01: The refresh hold never lifts for a key linked to a strategy after an attempt, so a zero-snapshot book is frozen indefinitely

**Severity:** MEDIUM · **Confidence:** 6/10
**File:** `analytics-service/services/equity_reconstruction.py:1810-1826` (`_fanout_would_still_retry`) and `:1858-1860` (the "Residual" docstring). Interacts with `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql:255-256` and its refresh arm.

**Issue:** `_fanout_would_still_retry` re-applies the fan-out's cheap qualifying columns, but not the strategy-link filter. It uses `attempts >= 1` as a stand-in for "the fan-out qualifies this key". The docstring accepts the gap as "a key linked to a strategy AFTER an attempt keeps holding until it caps or is marked". That bound does not hold:

- The SQL bootstrap excludes strategy-linked keys (`NOT EXISTS … strategies … status <> 'archived'`). It never enqueues the key again, so the key's attempts never reach 5.
- The SQL refresh arm's owed-key subquery also excludes linked keys. It therefore keeps enqueuing the refresh for the book's unlinked keys every day.
- Each day, the Python hold counts the linked key as owed and holds the refresh.

**Scenario:** An allocator book has zero snapshots. It has key A, which is marked, and key L, which is unlinked. The 05:00 fan-out enqueues L's reconstruct (attempt 1), and it ends `failed_final`. The user then links L to one of their strategies. From the next day:

- the fan-out never retries L;
- A's daily refresh is held, with an audit row of `reason: reconstruct_owed` every day;
- the book never gets its first legacy snapshot.

This lasts until someone manually syncs L successfully or archives the strategy. It is exactly the "hold that blocks refresh forever" class that the cap was meant to prevent. The Overview note does not fire either, because L's attempts are below 5.

**Fix:** Make the hold's key set agree with the SQL owed predicate. Either:

- re-apply the strategy-link check in `_sel_keys`, using the `strategies` and `strategy_keys` reads that `deriveStrategyLinkedKeyIds` mirrors; or, preferably,
- drop the Python reimplementation and call one SQL helper (`api_key_owes_reconstruct(id)`, or a book-level count) that both the fan-out and the worker use, so the predicate exists once.

Add a pytest in which L has `attempts=1`, no in-flight job, and an active strategy link. Assert that the refresh writes.

### WR-02: The Overview note shows "a connected account could not be rebuilt" for disconnected, revoked or later-linked keys, and nothing ever clears it

**Severity:** MEDIUM · **Confidence:** 7/10
**File:** `src/lib/queries.ts:4543-4547`. The copy is at `src/app/(dashboard)/allocations/AllocationDashboardV2.tsx:217` and `:443`. The tests are at `src/lib/queries.test.ts:2490-2502`.

**Issue:** `historyReconstructFailed` is `apiKeys.some(marker == null && attempts >= cap)`. Here `apiKeys` is `getUserApiKeys(userId)`: every key row the owner has, including disconnected, inactive, revoked and strategy-linked ones. Nothing ever resets `history_reconstruct_attempts`; D-16 puts the reset out of scope, and grepping the tree finds no reset. Nothing sets the marker on a key the fan-out has abandoned either. So:

- **Disconnected or revoked key (likely).** Its reconstruct capped, and the user then disconnected it or its credential was revoked. The project's policy is to disconnect, never delete. The book still shows, permanently: "The history of at least one connected account could not be rebuilt after repeated attempts." The account is no longer connected, the fan-out no longer counts it (its capped `cron_runs` count filters on qualifying keys), and the user can take no action that clears the line.
- **Key linked to a strategy after capping.** D-14 says strategy-linked keys are excluded from the note, but this key keeps raising it.

This is a false state on a user-facing dashboard, and the SQL capped-count and the reader disagree about which keys are capped.

The tests that claim to cover the exclusions cannot fail on them:

- "a Deribit key at marker NULL and zero attempts" differs from the capped control in two attributes (exchange AND attempts), despite the "exactly one attribute" comment. It passes on attempts alone, so it duplicates the 4-attempt test.
- The "strategy-linked" case is only `attempts: 0` with no link data at all.

Neither test would go red if the reader started flagging Deribit or linked keys.

**Fix:** Restrict the predicate to keys the fan-out still qualifies. The cheap columns are already in the projection:

```ts
const historyReconstructFailed = apiKeys.some(
  (k) =>
    k.history_reconstructed_at == null &&
    (k.history_reconstruct_attempts ?? 0) >= HISTORY_RECONSTRUCT_ATTEMPT_CAP &&
    k.is_active && k.disconnected_at == null &&
    !["revoked", "sign_in_failed", "error"].includes(k.sync_status ?? "") &&
    k.exchange.toLowerCase() !== "deribit" &&
    !strategyLinkedKeyIds.has(k.id),
);
```

Then rewrite the exclusion tests so each one holds `attempts: 5` and varies a single attribute:

- `exchange: "deribit"`;
- `disconnected_at` set;
- `sync_status: "revoked"`;
- a real strategy link.

Each must be RED on the current predicate.
