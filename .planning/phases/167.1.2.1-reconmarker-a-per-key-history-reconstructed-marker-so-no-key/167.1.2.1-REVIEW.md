## Warnings

### WR-01: The D-12 backfill revives reconstruct evidence that the 2026-04-24 heal migrations deliberately invalidated

**Severity:** WARNING (MEDIUM) · **Confidence:** 5/10
**File:** `supabase/migrations/20261014120000_api_keys_history_reconstruct_marker.sql:186-216` (`newest_outcome`). The same text is in `supabase/schema/functions/backfill_api_keys_history_reconstructed_at.sql`.

**Issue:** Two migrations, `20260424012820_equity_contract_size_healing.sql:70-72` and `20260424031238_equity_defensive_heal.sql:68-70`, did the same three things:
- deleted every `allocator_equity_snapshots` row;
- deleted every `done` `reconstruct_allocator_history` job, explicitly to un-mark every key ("MUST also be reset ... would otherwise ... leave allocators permanently pinned to the broken series");
- re-enqueued reconstructs, but for connected keys only.

They did not touch `audit_log`, and its rows stay hot for 2 years. `newest_outcome` filters on the success actions and `unexpected_noop` only, so `reconstruct_failed` is not in the set. Two kinds of key therefore get marked from a pre-heal `reconstruct_complete` that described a series the heal deleted:
- a key whose post-heal reconstruct ended in `reconstruct_failed`;
- a key that was disconnected at heal time, got no re-enqueue, and was reconnected later.

Under PR 2, such a key is never reconstructed, and D-16 means a reconnect never clears the marker. The population is small (the heal header says 3 allocators and single-digit keys). Each affected book, though, shows a hole with no "history could not be rebuilt" note. This violates the brief's "never mark a key that has no real reconstruct evidence".

**Fix:** Bound the audit evidence below by the last heal. Take the apply time from PROD's ledger, because the filename time is only approximate:
```sql
       AND a.created_at IS NOT NULL
       AND a.created_at >= TIMESTAMPTZ '2026-04-24 03:12:38+00'  -- 20260424031238 heal: earlier outcomes describe a deleted series
```
Add a matched-pair arm: the same `reconstruct_complete` row dated before the bound leaves the key NULL, with a `RED-UNDER` that drops the bound. Alternatively, have plan 08's census count the keys whose newest success outcome predates 2026-04-24 before PR 2 merges.

### WR-02: Pre-D-18 own-key forgeries are accepted without even a shape check, although every genuine success row carries `days_written`

**Severity:** WARNING (MEDIUM) · **Confidence:** 5/10
**File:** `supabase/migrations/20261014120000_api_keys_history_reconstruct_marker.sql:204-214`

**Issue:** D-18 closes the forging path from now on. Rows written through `log_audit_event` before it applies are still read as evidence, and so is the re-run in PR 2's migration. A forged row's metadata is whatever the caller sent, `{}` in the gate's own fixtures. Every genuine outcome row from the worker is built from `audit_metadata` (`equity_reconstruction.py:3802-3839`). That always includes `days_written`, `venue` and `atomic_replace`, on the MT5 path too, because it falls through to the shared persist. Only the echo lacks it, and the echo is already excluded. So a naive forgery is cheaply distinguishable, but the backfill does not check.

**Fix:** Pick one.
- (a) Require the worker's shape on success rows, for example `AND a.metadata ? 'days_written'`. Update the B2 / B4 / B5 fixtures to carry it, and add a `{}`-metadata twin that stays NULL. First confirm on PROD (read-only, marker query first) that no genuine pre-H-1168 success row lacks the key, or the bound under-marks keys and PR 2 re-reconstructs them, which is D-12's concern.
- (b) Keep the SQL and add to plan 08's census a count of success rows without `days_written`, brought to the founder with the D-12 numbers.

### WR-03: The backfill function body permanently records "founder decision pending" for a gap this same PR closes

**Severity:** WARNING (MEDIUM) · **Confidence:** 7/10
**Files:**

**Issue:** The comment at lines 194-202 sits inside a `LANGUAGE sql` body. It is therefore stored in `pg_proc.prosrc`, and `pg_get_functiondef` on PROD will always read "It cannot close a user forging a row about their OWN key ... (founder decision pending, see the plan 01 SUMMARY)". The header at :57-60 says "Closing that needs a founder decision". D-18 was decided and is shipped in `20261014120100` within this PR. Once applied, the migration is immutable. Correcting the catalogue text later would take a `CREATE OR REPLACE`, a snapshot regeneration and a new VAC-04 ack. Today it is a free edit. A future reader of the live definition gets the wrong security posture.

**Fix:** Before merge, reword both comments. For example: "own-key forgery through public.log_audit_event is refused from 20261014120100 (D-18); rows written before that are not cleaned". Regenerate the snapshot with `npm run schema:functions` and re-run the gate. None of the B-arm needles touches these lines.
