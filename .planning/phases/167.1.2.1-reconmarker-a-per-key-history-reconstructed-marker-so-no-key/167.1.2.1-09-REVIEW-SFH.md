# 167.1.2.1 plan 09 - Silent-failure review (PR 2, RECONMARKER)

Scope: `git diff 5f978b4f..HEAD -- . ':!.planning'` (fan-out migration 20261018120000, worker marker stamp and cap event, reader, dashboard note). Read-only review.

## What was checked and is sound
- Marker stamp (`equity_reconstruction.py` `_mark_api_key_history_reconstructed`, called at :3963): raises on an UPDATE exception and on zero matched rows; the caller turns that into a FAILED transient job plus a `reconstruct_failed` audit. No swallow. The D-15 no-op is deliberately left unmarked.
- `_capture_history_reconstruct_capped` (`job_worker.py:13571`): a failed key read is logged and captured to Sentry, never swallowed; the dispatch wrapper (:13777) only guards the best-effort hook.
- Reader (`queries.ts:4543`): `getUserApiKeys` throws on a query error (queries.ts ~5200 comment), so a read error does not degrade to "no failure". The absent-column default (`?? 0`) is the quiet side by design.
- Attempt increment sits in the same inner block as the enqueue, so a rolled-back enqueue burns no attempt.

## Findings (MEDIUM and above)

### F1 - MEDIUM (confidence 8): a capped key reaches nobody on the watchdog-reaped / orphan-terminalized route, and the only durable trace is a row nobody reads
- Location: `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql:345-348` (`history_reconstruct_capped` cron_runs row); `analytics-service/services/job_worker.py:13571-13600` docstring ("Not covered ... watchdog-reaped and orphan-terminalized").
- Scenario: the fifth reconstruct job for a key is reaped by the watchdog or orphan-terminalized (the routes D-17 itself says never return through `dispatch`). The Sentry event never fires. The key sits at attempts=5, marker NULL, never enqueued again. The only operator-facing trace is the daily `cron_runs` error row, and `grep` of the non-planning, non-migration, non-test tree finds no reader of `equity_refresh_fanout` or `history_reconstruct_capped` anywhere (no prober, no alert, no admin view). The allocator sees a muted dashboard note; the operator learns nothing.
- Hidden errors: any reaped fifth attempt; any capped key whose last job never passes `dispatch`.
- Recommendation: either have the fan-out's capped branch be the Sentry source for keys whose last job is not terminal-through-dispatch (e.g. a prober check on `cron_runs` rows with error `history_reconstruct_capped` in the last 25h), or book the prober read explicitly as a routed deferral with a gate. As shipped, "stops loudly at five" is only true for the dispatch route.

### F2 - MEDIUM (confidence 7): a failure of the capped-key count or its trace row is a WARNING only, with no cron_runs fallback
- Location: migration `:350-351` (`EXCEPTION WHEN OTHERS ... RAISE WARNING`).
- Scenario: the count query or the INSERT into `cron_runs` raises (a `cron_runs` check constraint or ACL change, a plan error on the correlated `NOT EXISTS`). The handler logs a Postgres WARNING that nobody tails and proceeds. The very signal that exists to make a capped key loud is then lost every day, silently, while the refresh loop keeps going. The sibling bootstrap handlers (:283-300, :305-325) at least try to write a `cron_runs` row (the loop-level one with its own nested guard); this block does not.
- Hidden errors: undefined_column / insufficient_privilege / check_violation on `cron_runs`; any error in the `v_capped` select.
- Recommendation: mirror the loop-level pattern: on failure, attempt a `cron_runs` row with cause `history_reconstruct_capped_trace_failed` and SQLSTATE in a nested guarded block, and keep the WARNING as the last resort.

### F3 - MEDIUM (confidence 6): a book whose bootstrap block keeps failing never burns an attempt, so it never caps and never raises the cap event
- Location: migration `:273` (increment inside the inner block) with `:283-300` (book-level `WHEN OTHERS` rollback + `bootstrap_book_skipped` row).
- Scenario: a non-unique/serialization error raised for one book (a trigger on `api_keys` UPDATE, an `enqueue_compute_job` guard, a lock timeout) rolls back the book's enqueues and their attempt increments every day. Attempts stay 0 for that book's keys, so the cap (D-09) is unreachable, the Sentry event never fires, the Overview note never shows, and Python `_fanout_would_still_retry` (needs `attempts >= 1`) does not hold the refresh either. The only trace is the `bootstrap_book_skipped` cron_runs row, which nothing reads (see F1). The key is permanently "owed and invisible".
- Recommendation: count the failed try outside the rolled-back sub-transaction (increment after the handler, in the handler, for the keys the book was attempting), or at minimum make the unread `bootstrap_book_skipped` row alertable and book that read.

### F4 - MEDIUM (confidence 6): the reader and note flag keys the fan-out will never retry or that the user cannot act on
- Location: `src/lib/queries.ts:4543-4548`; note text `AllocationDashboardV2.tsx` `HistoryReconstructFailedNote`.
- Scenario: `historyReconstructFailed` is `apiKeys.some(marker NULL && attempts >= 5)` with no `is_active` / `disconnected_at` / `sync_status` / strategy-link filter, and attempts are never reset (D-16). A key that capped, then was disconnected, revoked, or linked to a strategy, keeps the "could not be rebuilt after repeated attempts" note for ever, and a reconnected key is also never retried (the fan-out skips it at the cap), so the note is permanent with no path to clear it. Conversely, `getUserApiKeys` returns the pair even for the fifth attempt still in flight, so the note can appear a day before the attempt has failed (also acknowledged in the plan 04 summary). The line says "connected account", which is false for a disconnected key.
- Hidden errors: not an error-swallow, but a status line that stops meaning what it says; it will train users to ignore it.
- Recommendation: filter the reader with the same cheap columns the fan-out uses (`is_active`, `disconnected_at`, not revoked/sign_in_failed/error) or reset attempts on reconnect; exclude keys with an in-flight reconstruct if the column is available.
