## Summary

This phase is a two-line-of-substance Python change wrapped in a large amount of already-completed
verification work by its two sibling phases. `ALLOWED_STRATEGY_STATUSES` in
`analytics-service/routers/cron.py` — one module-level `set` literal, one reader — currently admits
`{draft, pending_review, published}` and must admit `private`. Every fact this phase needs to
reason about the change (the blast radius, the ordering hazard, the reason a naive "mirror the SQL
fan-out's set" is wrong) was already measured and recorded in CONTEXT.md, TODOS.md and the
ROADMAP by phases 164.5.1.1, 164.5.1.2 and 164.5.1.4. This RESEARCH.md's job was to re-verify those
claims against the code at the current HEAD (`60b8ed1b`) rather than re-derive them, and one claim
needed sharpening: 164.5.1.4's migration has been re-confirmed, via a live `gh run view` against
GitHub Actions rather than a dated document, to still be sitting at the `apply-test` (shared TEST)
step with its PROD `apply` job in `waiting` state behind the `Production` environment's human
reviewer gate. That is the load-bearing fact governing when this phase's own change may be merged
and deployed.

The single highest-value question the brief posed — whether the ledger-refresh migration's checks
8/9 ("never mirror `ALLOWED_STRATEGY_STATUSES`") bind this phase's own change — resolves cleanly on
direct inspection of that migration's DO block: those checks assert facts about the LEDGER
function's OWN executable text (`supabase/migrations/20260917120000_ledger_fanout_admit_private.sql`),
never about `cron.py`, and their stated reason (`draft` has no factsheet to refresh; `archived` is
not a refresh candidate) is a LEDGER-domain reason that says nothing about whether trade-sync
should admit `private`. They forbid the ledger fan-out from copying `draft` OUT of
`ALLOWED_STRATEGY_STATUSES`; they say nothing about `ALLOWED_STRATEGY_STATUSES` admitting `private`.
The two sets will remain genuinely different after this phase (trade-sync keeps `draft`, which the
ledger fan-out deliberately excludes) and that divergence is intentional on both sides, not a defect
to reconcile.

No SQL, no external package, and no new production dependency is needed. `sync_trades` (the RPC the
widened constant's readers call) carries no lifecycle-status gate of its own — it is a bare
`p_strategy_id`/`p_trades` upsert-style function — so admitting `private` in Python is sufficient by
itself; there is no SQL-side blocker to discover or widen. `enqueue_compute_job` likewise carries no
status conjunct. The change is Python-only and ships through the ordinary CI path.

**Primary recommendation:** Add `"private"` to `ALLOWED_STRATEGY_STATUSES` (one-line diff), prove it
behaviourally by extending `TestStrategyLifecycleFilter`'s existing consequence-gate idiom (not a
membership assertion on the constant), add a behavioural regression proving the widening does not
reopen `SYNC-CURSOR-PER-KEY-STRANDS-STRATEGY-01` on a mixed-success key, and gate the whole change
behind a mechanical assertion that the SYNCCURSOR marker machinery is present in the same file —
sequenced so the PR cannot merge (or, more precisely, cannot be treated as safe to deploy) until
164.5.1.4's migration has actually applied to PROD, which as of this research is NOT yet true.

### Pattern 1: Consequence-gate widening (this repo's established, non-vacuous idiom)

**What:** Prove a lifecycle-set widening by driving the actual reader end-to-end and asserting on
the resulting side effect (which strategy IDs reached the RPC), never by asserting membership in the
constant directly.
**When to use:** Any change to `ALLOWED_STRATEGY_STATUSES`.
**Example — the existing template to extend** (verbatim, `[VERIFIED: analytics-service/tests/test_cron_router.py:637-705]`):
```python
mixed_strategies = [
    {"id": "s-pub", "status": "published"},
    {"id": "s-draft", "status": "draft"},
    {"id": "s-review", "status": "pending_review"},
    {"id": "s-archived", "status": "archived"},
    {"id": "s-suspended", "status": "suspended"},
    {"id": "s-deleted", "status": "deleted"},
]
...
rpc_strategy_ids = sorted(
    call.args[1]["p_strategy_id"]
    for call in mock_supabase.rpc.call_args_list
    if call.args and call.args[0] == "sync_trades"
)
assert rpc_strategy_ids == ["s-draft", "s-pub", "s-review"]
```
Post-widening, adding `{"id": "s-private", "status": "private"}` to `mixed_strategies` and asserting
`rpc_strategy_ids == ["s-draft", "s-private", "s-pub", "s-review"]` is the minimal, direct extension.
Run this assertion BEFORE the `cron.py` edit (observe RED: `s-private` absent) and AFTER (observe
GREEN) — that RED/GREEN pair IS the calibration success criterion 3 asks for.

**What:** Every lifecycle-set widening in this codebase documents, at the point of change, the

constant cannot silently widen past the decision.
**When to use:** The `cron.py` edit itself; put the exclusion reasoning in the same comment block
`ALLOWED_STRATEGY_STATUSES` already carries.
**Example — the precedent, read directly from the migration** (`[VERIFIED: supabase/migrations/20260917120000_ledger_fanout_admit_private.sql:794-799]`):

The exclusion message at `[VERIFIED: supabase/migrations/20260917120000_ledger_fanout_admit_private.sql:983]`

### Pattern 3: Ordering gate — no existing analog; design guidance

No gate in this repo currently asserts a cross-phase landing-order invariant this way (confirmed
against `test_ledger_refresh_gates.py`'s exact-set-over-migrations idiom, which is a structural
cousin but guards SQL migration presence, not a Python symbol's existence conditioned on another
Python symbol — see `PATTERNS.md`'s "No Analog Found" table, same conclusion reached
independently here). Two candidate shapes, both usable, with a recommendation:

1. **Structural/import-time assertion** — `assert hasattr(cron_mod, "_STRATEGY_SYNC_CURSOR_TABLE")`
   and/or `assert "_strategy_resume_point" in dir(cron_mod)` guarded by
   `if "private" in cron_mod.ALLOWED_STRATEGY_STATUSES`. Cheap, but by itself is close to the
   "AST predicate over a symbol name" shape this repo's own anti-vacuity rule treats with
   suspicion (a name can exist and still not be *used* on the path that matters).
2. **Behavioural composition proof (recommended)** — a `TestPrivateAdmissionComposesWithSyncCursor`-
   shaped test: seed a key with TWO strategies, one already-admitted (e.g. `published`) and one
   newly-admitted `private`, make the `private` strategy's `sync_trades` RPC raise while the
   `published` one succeeds, and assert the KEY cursor advances (a sibling succeeded — unchanged
   pre-phase behaviour) while the FAILED `private` strategy's entry in `strategy_cursors_held`
   is present (i.e. its per-strategy marker did NOT advance, per 164.5.1.4's own contract). This
   is calibrated by construction: if 164.5.1.4's marker machinery were ever reverted while `private`
   stayed admitted, this exact test would fail because `strategy_cursors_held` would be empty or
   absent and the failed strategy's window would be silently lost — which is precisely
   `SYNC-CURSOR-PER-KEY-STRANDS-STRATEGY-01` reopening. This satisfies the anti-vacuity bar (it is
   both user-facing and data-integrity) far more strongly than a structural check, and needs no new
   test infrastructure — it composes `TestStrategyLifecycleFilter`'s hand-built `keys_data` shape
   with the existing `strategy_cursors_held` envelope field 164.5.1.4 already shipped.
   Recommend pairing (2) with a lightweight (1) as a cheap first-line trip-wire, not a substitute.

### Anti-Patterns to Avoid
- **Asserting `"private" in ALLOWED_STRATEGY_STATUSES` directly:** vacuous — nothing else reads that
  membership; the assertion restates the line it is meant to test. `PATTERNS.md` documents that this
  exact mistake was already made and fixed once at this call site (the discarded "local-replay"
  test `TestStrategyLifecycleFilter`'s docstring references).
- **Using `_make_key_row` for a status-varying test:** it only accepts a flat `strategy_ids: list[str]`
  and cannot express per-strategy status — hand-build the `keys_data` dict the way
  `TestStrategyLifecycleFilter` already does.
- **Reaching for the SQL migration's DO-block/needle idiom for this Python constant:** heavier
  machinery solving a problem a plain importable Python test already solves more simply and more
  strongly (see Pattern 1/3 and `PATTERNS.md`'s "Contradiction Surfaced").
- **Treating the migration's check 8/9 refusal as if it also constrains `cron.py`:** it does not —
  see Summary. Do not add a code comment implying the ledger migration "blocks" or "permits" this
  change; it does neither.

## Common Pitfalls

### Pitfall 1: Mistaking the ledger migration's refusal for a constraint on this phase
**What goes wrong:** A plan or a code comment states that the ledger fan-out migration's checks 8/9
"block" or "govern" whether `cron.py` may admit `private`.
**Why it happens:** Both changes look identical at a glance (same lifecycle value, same kind of
set-widening, same repo, three weeks apart) and the migration's own header explicitly warns against
"a tidy that mirrors `ALLOWED_STRATEGY_STATUSES`" — easy to over-read as bidirectional.
**How to avoid:** State explicitly, in the phase's own artifacts, that checks 8/9 assert facts about
the LEDGER function's executable text only (verified by reading the DO block directly — see
Architecture Patterns Pattern 2) and that the two constants are expected to diverge (`draft` stays
in trade-sync's set, stays out of the ledger's).
**Warning signs:** Any sentence of the form "since the ledger migration excludes X, trade-sync
should also exclude X" (or the converse) without an independent, trade-sync-specific reason.

### Pitfall 2: Shipping/deploying before 164.5.1.4's PROD apply actually lands
**What goes wrong:** The `cron.py` PR merges and Railway deploys it (CI-green auto-deploy) while
`strategy_sync_cursors` still does not exist on PROD, because the migration's `apply` job is still
sitting behind the `Production` human reviewer gate.
**Why it happens:** The code-level dependency (the marker mechanism existing in `cron.py`) IS
already satisfied at HEAD — it is easy to mistake "the code is there" for "the fix is live," which
is exactly the trap 164.5.1.4's own TODOS entry (`SYNC-CURSOR-PER-KEY-STRANDS-STRATEGY-01`) warns
about: *"the migration has not applied to any database... the code is inert on arrival
deliberately; it is not a fix in production until the table is there."*
**How to avoid:** RE-MEASURE the live deployment state immediately before this phase's own change
is merged, not just at planning time. **Freshly re-confirmed this session** (`[VERIFIED: gh run
view 35478916418]`, GitHub Actions, the Supabase Migrate run for commit `60b8ed1b`): the
`apply-test` job (shared TEST) is `completed`/`success`; the `plan` job (the PROD apply gate) is
`status: waiting`, `conclusion: ""` — i.e. as of this research, 164.5.1.4's migration has **NOT**

### Pitfall 3: Multiplicity assumption on the "5 of 5" measurement
**What goes wrong:** Assuming the five keyed `private` strategies map 1:1 to five distinct API keys
each carrying exactly one strategy, and sizing "new RPC load" or "new recompute load" as exactly
five additional calls of each kind per tick.
**Why it happens:** 164.5.1.2's PROD measurement establishes "5 of 5 [private, keyed strategies]
sit on a key with no in-set sibling" — this proves the keys are DISTINCT from any currently-eligible
key, but does not by itself prove each of those keys backs exactly one strategy (a key could
plausibly back more than one `private` strategy).
**How to avoid:** `[ASSUMED]` — flagged in the Assumptions Log below. If the plan wants an exact
"N additional `sync_trades` calls per tick" figure for its blast-radius documentation, that needs
its own targeted PROD read (a `checkpoint:human-action`, per this repo's PROD-access rules) rather
than being inferred from the 5-of-5 figure alone. The correctness of the fix does not depend on the
exact multiplicity; only the precision of a blast-radius claim does.
**Warning signs:** A plan or migration-header-style comment stating "exactly 5 additional
`sync_trades` RPC calls per tick" as measured fact rather than as a bound.

### Pitfall 4: Treating the recompute-enqueue stranding path as this phase's to fix
**What goes wrong:** Because admitting `private` is what newly exposes the "a failed
`enqueue_compute_job` is never re-driven" path on these five keys, a plan scope-creeps into fixing
that path here.
**Why it happens:** The path becomes newly *reachable* by this phase's own change, so it is easy to
conflate "newly exposed" with "this phase's defect."
**How to avoid:** CONTEXT.md's Deferred Ideas section is explicit: this belongs with 164.5.1.4's
cursor work. This phase's obligation is only to NAME it (in a code comment at the point where
`recompute_strategy_ids` is built, and/or in the TODOS entry this phase touches), not to remediate
it.
**Warning signs:** A plan task titled anything like "fix recompute-enqueue retry" inside this
phase's scope.
