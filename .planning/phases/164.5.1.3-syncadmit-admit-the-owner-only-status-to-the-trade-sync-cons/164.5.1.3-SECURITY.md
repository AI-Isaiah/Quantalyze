# Phase 164.5.1.3 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

**Register origin:** authored at plan time. `164.5.1.3-01-PLAN.md` carries a parseable
`<threat_model>` block with three rows, so this audit VERIFIES declared mitigations
rather than scanning for new threats. `threats_open: 0` with `asvs_level: 1` and a
plan-time register meets the workflow's own short-circuit rule (L1 grep-depth
sufficient), so no separate auditor pass was spawned; each mitigation below was
confirmed directly against the implementation at the sha in the frontmatter.

**What this phase changed, in security terms:** one Python set literal gained one
member. `ALLOWED_STRATEGY_STATUSES` now admits the owner-only status alongside the
three it already carried. No new attack surface, no new secret, no new external
caller, no auth or session-boundary change, no SQL, no migration.

⭐ **The load-bearing finding, traced independently by two reviewers:** the widening
creates **no new code path**. Everything a newly-admitted strategy now reaches —
the `/cron-sync` fan-out, `sync_trades`, the per-strategy resume marker, the marker
write, `enqueue_compute_job`, `derive_broker_dailies`, `strategy_analytics`, the
portfolio recompute cascade and the status-bucket accounting — is **status-agnostic**:
none of it branches on a strategy's lifecycle status. Two statuses that are already
non-public (`draft`, `pending_review`) have been exercising that identical pipeline
all along. Admitting a third therefore routes more traffic through an already-hardened
path rather than opening an unguarded one, and opens no new class of exposure.

⚠️ Corollary worth keeping: `ALLOWED_STRATEGY_STATUSES` is the **only** lifecycle gate
in the entire pipeline. Both RPCs it feeds were checked and contain no status gate of
their own. That concentration is what makes the guard comment on the constant a
security control rather than documentation.

### Audit note on T-164.5.1.3-03 — the ordering threat, and why it is closed rather than accepted

⚠️ **This threat was live for most of the phase and is recorded that way on purpose.** Two
readings exist and the second supersedes the first; the gap between them is the control
working, not noise.

- **At execution time:** run `35478916418` (headSha `60b8ed1b`) had `apply-test`
  `success` (shared TEST) while the PROD-apply gate job `plan` sat `waiting` on the
  `Production` environment's human reviewer. No `apply` job existed yet, being gated
  behind `plan`. The phase completed execution under that constraint and **did not
  merge or deploy**.
- **After the founder approved the `Production` gate:** the same run is `success`
  overall, with `apply-test`, `plan`, `apply-test-verdict`, **`apply`** and
  `prod-credential-divergence-verdict` all `success` (`dispatch-ref-guard` skipped, as
  designed). `strategy_sync_cursors` therefore exists on PROD, the fail-open paths
  resolve against a real table, and the ordering hazard is structurally gone.

⭐ It is `closed`, not an accepted risk: nothing was tolerated. The unsafe window was
held open until the dependency landed, then measured shut.
