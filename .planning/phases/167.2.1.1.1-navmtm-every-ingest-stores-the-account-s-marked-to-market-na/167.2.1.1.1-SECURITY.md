## Focus-area findings (the five items the caller named)

1. **Marks table: owner-only read, service-role insert-only write - CLOSED.**
   `supabase/migrations/20261029120000_api_key_nav_marks.sql`:
   `REVOKE ALL ... FROM PUBLIC, anon, authenticated, service_role` (L220), then `GRANT SELECT ... TO authenticated`
   (L221) and `GRANT SELECT, INSERT ... TO service_role` (L222). UPDATE, DELETE and TRUNCATE are therefore withheld from
   every role, which is the right control because `service_role` has BYPASSRLS and a policy cannot gate it. `FORCE ROW
   LEVEL SECURITY` (L206); the only policy is `api_key_nav_marks_owner_select ... TO authenticated USING (allocator_id =
   auth.uid())` (L208-211); no anon policy, no authenticated write policy. First-writer key `UNIQUE (api_key_id,
   mark_day)` (L103). Both foreign keys `ON DELETE CASCADE` (L89-90). The only migration in the phase touching the table
   is this one (checked by diff and by grep over `supabase/migrations`), so no later grant widens it.
   Code side: the only writer is `write_nav_mark` (`analytics-service/services/nav_marks.py:435`), which calls
   `upsert(..., on_conflict="api_key_id,mark_day", ignore_duplicates=True)` (L450), i.e. `ON CONFLICT DO NOTHING`, which
   needs INSERT alone. A grep of `analytics-service`, `src` and `scripts` found no `.update(` / `.delete(` / merge-duplicates
   against the table; every consumer goes through `read_stored_mark` / `read_key_marks` (select only). A loopback-guarded
   live PostgREST probe (`tests/test_nav_marks_writer_live.py`) exists for the PostgREST translation.
   SQL gate `supabase/tests/test_api_key_nav_marks.sql` has 11 arms, each with a `RED-UNDER-M` mutation (owner read arm 1
   mutates the policy to `USING (true)`; arms 3 and 4 mutate the service_role grant to add UPDATE and DELETE; arm 11
   removes FORCE RLS).

2. **No refusal token, id or amount reaches a public factsheet field beyond the decided flags - CLOSED.**
   The only values the derive writes into the PUBLISHED `strategy_analytics.data_quality_flags` are in the prestamp block
   of `job_worker.py` (about L8691-8702): `marks_since`, `marks_covered_from`, `mark_gap_days`, `marks_trailing_since`,
   all ISO dates or lists of ISO dates, none a member of `NAV_TWR_GUARD_KEYS`. The runner validates them before they
   move the reindex boundary or are re-published (`analytics_runner.py:1380` `_NAVMTM_DAY_RE`, `:1394`
   `_is_iso_calendar_day`, `:1405` `_read_navmtm_flags`; `fullmatch` plus `date.fromisoformat`, malformed dropped with a
   reason-only warning). The runner never reads the marks table (no import of `nav_marks` anywhere outside `job_worker`).
   `nav_mark` (a NAV and open-profit echo) and `nav_mark_refusal` (the mark-write refusal token, for example
   `borrow_present`) go only into the `key_inputs:<id>` payload of `allocator_equity_derived`, which is FORCE-RLS,
   owner-SELECT, no anon policy (migration 20260717233529). The apply-refusal path
   (`job_worker.py` about L7576-7600) puts a fixed user sentence in `computation_error` and a token-only detail in
   the log and `compute_jobs.error_message`, through the existing HONEST-01 detail/message split in
   `_stamp_strategy_analytics_failed`. The TS side reads only `marks_since` and `marks_trailing_since`
   (`fetch-and-build-payload.ts`, `src/lib/nav-marks-start.ts`, one reader, `isIsoCalendarDate` exact-calendar check) and
   renders them as text (no `dangerouslySetInnerHTML` or other sink in the UI diff). Note, informational only: the
   fourth published key `marks_covered_from` is a validated date, registered by plan 08 (T-28), and carries no id,
   amount or token. `mark_gap_days` is an unbounded list of validated dates; that is a size matter, not a disclosure.

3. **`key_inputs` read in `src/lib/queries.ts` uses the user-session client with the owner filter - CLOSED.**
   `readMarksStart` (L4176) selects from `allocator_equity_derived` with `.eq("allocator_id", userId)` (L4188) and
   `.in("kind", key_inputs:<id>...)`. It is called with `supabase` (`createClient()`, the user-session client, L5247),
   never the `admin` client that is also in scope in `getMyAllocationDashboard`, and only after the function's
   `authUser.id !== userId` fail-closed gate (L5269). It fails closed (null) on a read error and on the
   `departed_history_unavailable` case, logs `error.message` only, and the result is a date. The factsheet path
   (T-34) takes the published flag and never touches the marks table.

4. **Venue reads never log secrets or venue text - CLOSED.** Every added log line in the diff of
   `equity_reconstruction.py`, `job_worker.py`, `deribit_ingest.py`, `deribit_txn.py` and `ccxt_flows.py` was reviewed.
   Venue exceptions are logged by `type(exc).__name__` only, with the in-code reason "ccxt error text can carry a
   request signature" (Bybit UTA read, OKX option read, Binance options read, the once-per-day Bybit/Binance read, the
   OKX wrapper). Other lines carry tokens, counts, venue name, the internal key id, and mark day. The Deribit twin logs
   the exception class (`nav_twin_error` is `type(exc).__name__`). The MT5 SFH-3 F1 warning logs two integer counts.
   Informational (not a finding): `parsed_code` in the Binance options log is the `\d+` capture from the venue's
   response text, so it is a digit run of venue-controlled length; it is not a secret and is the only part of the text
   that is ever read.

5. **Binance -2015 handling matches D-20 (as restated by D-22) - CLOSED, with one declared and accepted measurement
   limit.** `_BINANCE_OPTIONS_NO_ACCESS_CODES = {"-2015"}` (`equity_reconstruction.py:4154`); the code is parsed from
   the error text by a regex (L4158), never decided by exception class (ccxt maps both -2015 and -2014 to
   `AuthenticationError`). `_binance_options_call` (L4167) returns `no_access` only for a raised read whose parsed code
   is in that set, and `unreadable` for every other raise. `_read_binance_options_exposure` (L4225) reads
   `marginAccount` and `position` independently: any non-zero balance or open position -> `option_value_unverified`
   (a known holding beats an unreadable sibling), any unreadable read or garbled shape -> `option_value_unreadable`,
   no-access counts as zero. It is called only after `_fetch_current_equity` succeeded and `partial` is empty (L4402), so
   an L4 refusal is returned as it stands and no options read is made (D-22's precondition). Both tokens are members of
   `MARK_REFUSAL_TOKENS` (`nav_marks.py:102`). Residual, by design and recorded in the code (I2): `-2015` is a
   placeholder until the first post-deploy run measures what a key without options permission really receives; a
   different observed code fails closed (a refusal, not an omitted option holding), and D-22 sends it to the founder.
   Note for the post-deploy reading: Binance documents -2015 as "invalid API-key, IP, or permissions", so the reading
   should confirm it is returned for options-permission absence and not for a revoked key on a key whose main read passed.
