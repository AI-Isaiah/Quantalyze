# Phase 167.2.1.1.1 NAVMTM - Context

**Gathered:** 2026-10-26
**Status:** Ready for planning

<domain>
## Phase Boundary

From the day this phase deploys, every daily ingest stores each key's marked-to-market NAV (equity including unrealized profit) and the unrealized amount itself. The derived compose curve (the one drawn on screen) and the strategy return series use those real marks from that day on, instead of realized-basis values. Earlier days stay as stored. The day storage starts is recorded and shown. One mark-price rule across all paths, agreement with the legacy snapshot curve, and the last-bar spike belong to MARKSOURCE 167.2.1.1.1.1.

</domain>

<decisions>
## Implementation Decisions

### Carried, not re-asked
- L1, ACCTREBUILD D-01 "Keep them as they are (Recommended)": days before storage starts keep their realized-basis values. Nothing is backfilled or recomputed.
- L2, ACCTREBUILD D-03 "Allow the step, mark the date (Recommended)": where marked days meet realized-basis days the curve may step. The step stays, the boundary date is stored, and no values are invented. Reuse the `snapshot_rebuild_boundary` pattern (`src/lib/snapshot-rebuild-boundary.ts`).
- L3, ACCTREBUILD D-02 "Refuse that account (Recommended)": a rebuild or re-derive never silently replaces or drops a stored mark. If it cannot reproduce one, it refuses with a named reason and writes nothing.
- L4, UPNLVENUES D-01: Bybit and Binance marked equity is wallet balance plus position open profit, read the way the reconstruct anchor reads it, never the derive's `walletBalance`-only figure.
- L5, ROADMAP scope fence: the single price rule, legacy-curve agreement and the last-bar spike are MARKSOURCE's.

### D-01 Storage (G1)
Founder 2026-10-26: "New append-only table (Recommended)". One row per key per day holding NAV, open profit, mark time, venue and owner. The migration needs migration-reviewer and rls-policy-auditor clean before merge, because PROD applies automatically after TEST.

### D-02 Writer and cadence (G2)
Founder 2026-10-26: "Derive, daily for every key (Recommended)". The mark comes from the equity read the derive already makes, with no extra venue calls. Every active key gets a daily derive or mark whether it traded or not. Today a strategy derive is queued only after new trades (`analytics-service/routers/cron.py`).

### D-03 Mark day: move the daily chain to just after midnight UTC (G3)
Founder 2026-10-26, who asked "Why not move all captures to midnight?" and then chose "Move the chain to ~00:10Z (Recommended)". The daily chain keeps its order (trade sync, then derive, which writes the mark, then compute) and moves to just after 00:00 UTC, so every mark sits on the UTC day boundary and labels the day that just closed. The planner must:
- confirm that funding and fills paid at 00:00Z have arrived before the read;
- move every job that depends on the old 04:30Z/05:30Z times, re-measuring the live cron set;
- store the exact mark time.

### D-04 The step day's return (G4)
Founder 2026-10-26: "Book it as that day's return (Recommended)". On the first marked day, the open profit at the boundary is booked as that day's return, once per key, so cumulative return keeps matching the change in NAV. This adds one outlier day per key to the published metrics.

### D-05 A day with no mark after storage starts (G5)
Founder 2026-10-26, asked again: "No row; next mark covers it". This replaces the first answer, "Realized P&L, catch up next mark (Recommended)". Invent nothing. A day with no mark gets no marked value and no return of its own. The next stored mark's return covers the whole gap, and the gap days are named.

### D-06 Can a stored mark change (G6)
Founder 2026-10-26: "Write-once (Recommended)". The first writer of a day wins. Rebuilds read marks and never replace them. Key deletion follows the existing key-delete cascade.

### D-07 Units for non-USD accounts (G7)
Founder 2026-10-26: "Native + USD + price day (Recommended)". Store the native amount and unit, the USD figure, and the close day used to price it. The pricing rule itself stays with MARKSOURCE.

### D-08 Showing the start of real marks (G8)
Founder 2026-10-26: "Small note on charts (Recommended)". A small marker or note on the factsheet and on My Allocation wherever the start date falls inside the drawn range. This needs a UI-SPEC and a DESIGN.md check.

### D-09 Backfill from existing position history (G9)
Founder 2026-10-26: "No, start at deploy (Recommended)". Marks start when this phase ships. `allocator_holdings` and `position_snapshots` are not used to invent earlier marks.

### D-10 Bybit and Binance positions read (research OQ-1)
Founder 2026-10-26: "Accept one call per key (Recommended)". D-02's "no extra venue calls" holds for OKX, Deribit, MT5 and sFOX. Bybit and Binance get one positions read per key per day, because their marked equity (L4) needs it.

### D-11 A late retry still writes the day's mark (research OQ-3)
Founder 2026-10-26: "Any time that day". A run that writes the mark later the same UTC day, for example a retry at 05:00Z, still writes it. `marked_at` records the real time.

### D-12 The public start date lives in the strategy's analytics (research OQ-5)
Founder 2026-10-26: "Store it in the strategy's analytics (Recommended)". The compute writes the marks-start date into the strategy's analytics data, which published factsheets already read (like `headline_since`). The owner-only marks table is not exposed.

### D-13 The day-roll SQL gate becomes a minimum offset (research OQ-7)
Founder 2026-10-26: "Minimum offset after midnight (Recommended)". `supabase/tests/test_derive_allocator_keys_fanout.sql` assertion 6 (hours 1-22) is replaced by a rule that the chain runs at least a few minutes after 00:00Z. This is a consequence of D-03.

### D-14 Allocated-capital strategies use marks too
Founder 2026-10-26: "Apply marks to them too". The planner had proposed keeping their allocated-capital series and naming them `marks_not_applied`; the founder chose otherwise. From the first mark, an allocated-capital strategy's returns follow its key's marked NAV, like every other strategy. This changes how those strategies' performance is measured.

### D-15 A return that spans a gap is one observation
Founder 2026-10-26: "Yes, one observation (Recommended)". After marks start, a return covering several unmarked days (D-05) counts as a single observation in volatility, Sharpe and drawdown. Nothing is spread over the gap days. The post-deploy readout reports how often this happens.

### D-16 Bybit and Binance marked equity: accept the extra reads (amends D-10's call count)
Founder 2026-10-26: "Accept the extra reads (Recommended)". Reading Bybit and Binance marked equity exactly as the reconstruct anchor does (L4) costs one positions read, one balance read and one price read per held non-stable asset, per key per day. The founder accepts that. This amends D-10's count of "one positions read per key per day"; D-02's "no extra venue calls" still holds for OKX, Deribit, MT5 and sFOX.

### D-17 Bybit marks come from Bybit's own account total (amends L4 for Bybit)
Founder 2026-10-26, AskUserQuestion: "Use Bybit's account total (Recommended)". Research (2026-10-26, Bybit V5 docs and ccxt 4.5.85/4.5.88 source) found that `fetch_positions()` on Bybit reads only `category=linear, settleCoin=USDT`, so an account also holding USDC-settled or inverse positions was refused every day. On a Unified Trading Account 2.0 the wallet-balance read the derive already makes (`accountType=UNIFIED`) carries `totalWalletBalance`, `totalPerpUPL`, `totalMarginBalance` and `totalEquity` across USDT, USDC and inverse perpetuals and futures and options. The Bybit mark takes NAV and open profit from those totals with no position walk. It refuses by name when the venue does not itself report UTA 2.0 (`unifiedMarginStatus` 5 or 6, never ccxt's default when the field is missing), when the account is in isolated margin, when any coin carries a non-zero borrow, when a field is missing or not finite, or when Bybit's `totalWalletBalance` disagrees with our own independently priced wallet (`wallet_total_usd`) beyond the anchor's tolerance. The existing `totalPerpUPL` cross-check is retired on this path, because it would compare Bybit's figure with itself. Binance is unchanged (L4 as written). This replaces how L4 reads Bybit open profit; L4 still governs Binance.

### D-18 A Bybit NAV includes open option value
Founder 2026-10-26, AskUserQuestion: "Yes, include option value". The Bybit NAV is `totalEquity` (wallet plus perpetual and futures open profit plus option value). The stored open profit is `totalEquity - totalWalletBalance`, so the D-04 step books option value with the rest of the open profit.
Founder amendments 2026-10-26: "D 18 should be true for OKX as well", then "And binance and deribit". An OKX NAV also includes open option value. Whether OKX's `totalEq` (the figure the OKX mark reads today) already carries option market value, or a separate field (for example per-currency `optVal`) has to be added, is verified from OKX's v5 docs before the plan is written, and the stored open profit carries option value the same way as Bybit's.
The same holds for Binance and Deribit: each venue's NAV includes open option value. For each of OKX, Binance (options sit in a separate European Options account) and Deribit (collapsed equity per currency), the plan first verifies from the venue's own docs whether the equity figure the mark reads already carries option market value, adds the missing read where it does not, and refuses by name (never omits silently) when an account's option value cannot be read.

### D-19 OKX accounts holding options: refuse until measured
Founder 2026-10-26, AskUserQuestion: "Refuse until measured (Recommended)". While an OKX account holds an open option, its daily mark is refused with `option_value_unverified`. Once SSH works, a live comparison on an account that holds an option measures whether `totalEq` already includes option value. If it does, the refusal is lifted in a later change. Plan 11's dry run (or plan 14) records that measurement whenever such an account exists.

### D-20 Binance options: refuse holders, no access counts as zero
Founder 2026-10-26, AskUserQuestion: "Refuse holders; no-access counts as zero (Recommended)". A key that holds options is refused with `option_value_unverified`. A key without options permission counts as zero option value, but only on the specific Binance "no options account / no permission" error code. That code is measured first (in plan 11's dry run); until it has been measured, the plan pins it by test from the docs or ccxt. Any other read error still refuses with `option_value_unreadable`.

### D-21 Deribit stored open profit is NAV minus wallet
Founder 2026-10-26, AskUserQuestion: "Align: NAV minus wallet (Recommended)". From now on Deribit's stored open profit is NAV minus wallet, like Bybit and OKX. The D-04 step must still book the boundary open profit correctly under this definition.

Orchestrator note 2026-10-26: the question that produced D-21 said "as on Bybit and OKX", but OKX stores its account-level `upl` (plan 06), not NAV minus wallet. For an OKX account holding no open option the two coincide (per-currency `eq` is cash balance plus `upl`), and D-19 refuses every account that holds one, so OKX needs no change now. When D-19's refusal is lifted after the live measurement, the OKX open-profit definition is re-checked against NAV minus wallet in that same change, so open profit keeps one meaning on every venue.

### D-22 The venue dry run moves to right after deploy
Founder 2026-10-26, AskUserQuestion: "Move it to right after deploy (Recommended)". Plan 11's dry run moves from before the merge to right after deploy. The same read-only checks run on the deployed worker over `railway ssh`, as a stdin script, before the first nightly marks; or they read the first night's results. This is safe because every uncertain case refuses that day's mark and writes nothing (D-05). The Binance no-options-access code is measured on that first run, and any key that misbehaves goes to the founder. The access path is named: `railway ssh` into the worker, where the KEK that decrypts the keys lives and whose egress IP the venues see. This restates D-20's "measured first" as "measured on the first post-deploy run"; plan 19's zero-on-no-access rule applies only after the main Binance read on the same key has succeeded.

### D-23 A flow is placed by its own time against the mark read (review round 2)
Founder 2026-10-26, AskUserQuestion: "Use the deposit's exact time (Recommended)". A deposit or withdrawal dated the day after a mark can land before that mark's read (the read runs at about 00:10Z). Round 1 handled it by skipping such mark days (review round-1 WR-02); round 2 showed that skip drops almost every Deribit mark (its composed flows carry a 0.0 entry on every NAV day) and can book a first-mark deposit twice (+2% published as -32%). The skip is removed. Each flow keeps the instant its raw venue row carries (Deribit transaction log, ccxt transfers, MT5 deals, sFOX rows), and a flow made before a mark's `marked_at` is counted in that mark's day; one made after it is counted in the next day. This supersedes the round-1 WR-02 rule.

### D-24 A realized tail after the last mark reverses that mark's open profit (review round 2)
Founder 2026-10-26, AskUserQuestion: "Reverse the open profit (Recommended)". When a closed composite member (round-1 WR-03) or a closed allocated mandate (plan 16 W2) keeps its realized rows after its last applied mark, the first tail row books the reverse of that mark's D-04 open-profit step, `r1' = (1 + r1) * (M_last - U_last) / M_last - 1`, so the tail is purely realized. A position closed in the tail nets correctly; one still open at the window end loses its unrealized profit, the convention before this phase.
