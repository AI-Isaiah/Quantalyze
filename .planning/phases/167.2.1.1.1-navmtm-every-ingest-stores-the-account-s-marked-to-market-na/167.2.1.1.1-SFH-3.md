## Findings

### F1. MEDIUM (data-integrity, not directly user-visible): an MT5 deal with an untrustworthy instant silently falls back to day placement, with no log and no flag
`job_worker.py` ~6725-6735 (`if _deal_ms is not None:`), consumed by `nav_marks_apply.py` rule 10 (`fi.day == read_day and at_ms <= read_s`).

Judgment on the fixer's claim ("keeps its own day"): that is the pre-phase behaviour, so it is not a regression against main, but round 1 deliberately refused this exact case (it skipped the mark). Now a deal dated `d+1` whose `time_msc` disagrees with `time` (or is fractional or non-numeric) stays in `d+1`. If it really landed before the mark's read, the wallet holds it, the mark's return books it as profit on `d`, and `d+1` books it again as a loss. Nothing records that it happened: no warning, no counter, no `meta` key. The same applies to any instants list shorter than its day aggregate; nothing cross-checks them (the sums are only checked in tests).

Hidden errors: broker deals with `time_msc` in a different second than `time`, boolean or fractional `time_msc`, DST-shifted server clocks (Pitfall 3 noted in `mt5_deals.py`).

Minimal fix: count the `None` instants and emit one `logger.warning` with the count and the number that fall on a day that is some mark's read day (counts only, no amounts). Optionally stamp a present-only note. Do not default the instant.

### F2. MEDIUM (user-facing: a composite or key derive fails): `_tail_without_open_profit` divides by the last mark's NAV with no guard
`job_worker.py` `_tail_without_open_profit` (`(nav - open_pnl) / nav`), called at the single-key tail (~7620), `_apply_member_marks` (~9850) and `_allocated_member_marks` (~9968).

Scenario: a member whose window has closed, whose last stored mark is an emptied account (NAV 0.0, or non-positive), and which has realized tail rows after that mark. The tail is non-empty, `nav == 0.0` raises `ZeroDivisionError`, which is not a `MarkApplyRefusal` or `NavReconstructionError`, so it escapes both handlers and the stitch or derive job fails as an unclassified error and retries. A tiny positive NAV instead produces an unbounded first-row return that is stored as real history.

Hidden errors: NAV 0, negative NAV, non-finite NAV, NAV at or below the dust floor.

Minimal fix: at the top of the helper, `if not (math.isfinite(nav) and nav > 0): return tail` (keep the tail verbatim, as before the phase), and log once. Same guard covers all three call sites.

### F3. LOW: `datetime.fromisoformat(mark.marked_at)` is unguarded and timezone-naive tolerant
`job_worker.py` `_marks_in_series_unit` (~525), `_apply_member_marks` (~9815), `_allocated_member_marks` (~9936).

A naive `marked_at` would be read by `.timestamp()` in the process's local zone, shifting every read-day placement by hours with no signal; a malformed value raises a bare `ValueError` outside `MarkApplyRefusal`'s token set (fail-loud but unclassified). Supabase returns an offset-bearing string today, so this is hardening. Fix: parse once in one helper, require `tzinfo`, and map a failure to `MarkApplyRefusal("mark_input_nonfinite")` or a sibling token.

### F4. LOW: `assert` used as a production guard in the new code
`job_worker.py` `assert _marks_in is not None` (~7620) and `assert marked.terminal is not None` (~9829, ~9945). Under `python -O` these vanish and the next line fails with an unrelated `TypeError`. `apply_marks` with a non-empty list always sets `terminal`, so this is theoretical.

### F5. LOW (user-facing wording): the My Allocation note takes the earliest trailing day across keys
`queries.ts` `readMarksStart`: if key A paused on Jan 5 and key B is current, the portfolio chart says "Marks paused from Jan 5" under a curve that still moves because of B. The text overstates for the whole curve. Acceptable if UI-SPEC intends it; otherwise name the scope ("for one account").
