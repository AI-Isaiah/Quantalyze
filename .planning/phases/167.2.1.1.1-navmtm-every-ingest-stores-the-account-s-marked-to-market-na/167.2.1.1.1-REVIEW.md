# Phase 167.2.1.1.1 NAVMTM: Code Review Report

**Reviewed:** 2026-10-26T19:49:33Z
**Depth:** deep (cross-module: writer, apply, strategy/key/composite seams, series runner, stitch, factsheet TS recompute, cron chain)
**Files Reviewed:** 78 (`git diff 59bc8eecf..HEAD -- . ':!.planning'`)

## Summary

The storage half is sound: the migration (write-once by grant, owner-coherence trigger, label CHECK,
owner-only RLS, cascade erasure, catalogue-only verify), the writer (`write_nav_mark` re-selects the
stored row, Pitfall 1), the per-venue NAV / open-profit reads (OKX `totalEq`/`upl` plus the D-19
option refusal, Bybit UTA totals per D-17/D-18, Binance L4 plus the D-20 options check, Deribit
NAV minus wallet per D-21, MT5 equity minus balance, sFOX open 0), and refusal-writes-nothing on the
mark write all hold as specified. No security defect was found.

The money-math defects sit in how the stored marks are APPLIED. `apply_marks` re-derives the first
mark's base, `L_real(S-1)`, on every derive from that derive's live realized terminal rolled back
through every realized day since `S`, and it re-applies the whole immutable mark history every time.
Three consequences:

1. The D-04 step `r_S` is not booked once. It is re-stamped every day and absorbs every change in
   the realized terminal that the realized P&L and flows do not explain (CR-01, reproduced).
2. Any refusal that history contains becomes permanent. An emptied-then-refunded account, or a
   guard-NaN realized day after `S` on a ccxt or sFOX key, fails every later derive, on purpose and
   forever, because marks and flows never change (CR-02, reproduced).
3. A refusal streak that does not end (a persistent account state such as `borrow_present`,
   `wallet_basis_mismatch` or `option_value_unverified`) silently freezes the published series at
   the last stored mark. Nothing flags it (CR-03).

**Executor item (browser recompute of composite covered days): CONFIRMED, and it is user-visible**
in two places. See WR-01.

Reproduction scripts (read-only, they import the module under review): `<scratchpad>/drill/base_drift.py`
and `<scratchpad>/drill/empty_refund.py`, run with `analytics-service/.venv/bin/python -I`.

## Critical Issues (HIGH)

### CR-01: The first marked day's return is re-computed every derive and absorbs every unexplained change in the realized terminal since `S` [HIGH, user-facing, data-integrity]

**File:** `analytics-service/services/nav_marks_apply.py:292-316` (the `base0` roll), fed by
`analytics-service/services/job_worker.py:7491-7502` (ccxt, MT5 and sFOX terminal
`(returns.index[-1], equity - open_unrealized_usd)`), `:7446-7464` (Deribit), `:7411-7440`
(allocated twin), `:7370-7395` (key mode), and the composite seams `:9681-9714` and `:9777-9784`.

**Issue:** `S` (the first stored mark) is fixed, but `E` (the last realized day) moves forward by
one day on every derive. `base0` is therefore `T_t - Σ_{d∈[S,t]}(P_d + F_d)`, where `T_t` is the
live realized level read on derive `t`. Between two derives `base0` moves by
`(T_{t+1} - T_t) - P_{t+1} - F_{t+1}`, the part of the wallet change the realized series does not
explain. Sources include residuals the realized series does not carry, and on OKX every non-USD
balance inside `totalEq - upl`, revalued at the live price with no realized P&L. The stored mark
`M_S` never changes, so the persisted `r_S = (M_S - base0 - F_S)/base0` is rewritten every day. The
cumulative return from inception becomes `Π_pre(1+r) · M_t / base0(t)`, so a gain that raises both
`M_t` and `base0` is cancelled out of the published track record.

Reproduced with the module itself (`<scratchpad>/drill/base_drift.py`). The stored marks and the
realized rows on and before 11-05 are identical across the two runs, and only the derive day moved:

```
derive A  r_S(11-04) = 0.05
derive B  r_S(11-04) = 0.029412 (same stored mark, same realized rows)
cum A through 11-05: 0.060222  cum B through 11-06: 0.060124
```

NAV rose 105,500 → 107,600 (+2.0%) between the two derives, but the published cumulative return
fell, because the $2,000 the realized P&L does not explain moved into `base0`. Realistic scale: an
OKX account that is 50% BTC by balance, where BTC rises 50% in six months, sees `base0` rise about
25%. `r_S` then swings from a small step to a large negative day, inflating max drawdown, and the
cumulative return is understated by a factor of about 1.25. No test runs two consecutive derives
and asserts `r_S` stays fixed. `test_first_mark_base_equals_the_compose_roll_of_the_realized_series`
checks one call only. The D-04 wording "booked as that day's return, once per key" is not what ships.

**Fix (minimal):** compute `base0` only from quantities that are final once day `S` is past, and
never from a later terminal. The stored first mark already carries its own wallet
(`nav_usd - open_pnl_usd`, the same basis as the realized terminal on every venue: OKX `totalEq-upl`,
Bybit `totalWalletBalance`, Deribit balance, MT5 balance, sFOX nav). Roll back one day from it:

```python
# apply_marks: base for the first mark from the first mark's own wallet, not the live terminal
w_S = first_mark.nav - first_mark.open_pnl          # pass open_pnl through AppliedMark
r_real_S = realized_return_on(S)                     # or day_pnl[S] under roll_basis="day_pnl"
base0 = (w_S - flows.get(S, 0.0)) / (1.0 + r_real_S)  # or w_S - P_S - F_S
```

The alternative is to persist `base0` once, at the first derive that applies `S`, and read it back
afterwards. Either way the terminal is no longer needed after `S`, which also removes most of CR-02.
Add a regression test that runs `apply_marks` for derive `t` and `t+1` with an unexplained terminal
move and asserts `r_S` is byte-identical.

### CR-02: Any refusal inside the immutable history wedges the strategy, key or composite permanently [HIGH, user-facing, data-integrity]

**File:** `analytics-service/services/nav_marks_apply.py:322-327` (`mark_base_nonpositive`),
`:217-223` (`mark_base_unrollable` on a NaN day with no `day_pnl`), `:297-299` (no terminal);
consumed at `analytics-service/services/job_worker.py:7512-7537` (strategy and key mode, FAILED
`error_kind="permanent"`, user-visible `_stamp_strategy_analytics_failed`) and `:9681-9714` /
`_refuse_member_marks` (the whole composite).

**Issue:** every derive re-applies ALL stored marks against ALL flows. Marks are write-once and
flows are history, so a refusal that comes from history refuses every later derive with no path to
recovery. L3 ("refuse that derive by name") becomes "this strategy never updates again".
Three reachable triggers:

- **(a) Emptied and refunded account.** The owner withdraws everything on day `p+1`, so that day's
  mark is refused `dust`/`nonpositive` and the day becomes a gap. The owner deposits later, so the
  next mark's base is `M_p + F_{p+1} ≤ 0` and the apply raises `mark_base_nonpositive`. Reproduced
  (`<scratchpad>/drill/empty_refund.py`):
  `refused: mark_base_nonpositive` and, two marks later, `still refused: mark_base_nonpositive`.
  Moving funds out and back in is ordinary user behaviour.
- **(b) A guard-NaN realized day on or after `S`** (dust base, `pnl_dominated_guard`, an
  inception-like deposit-only day) on a ccxt or sFOX series. The strategy-mode ccxt and sFOX
  branches pass no `day_pnl` (`job_worker.py:7473-7479`), so `_roll_back_by_returns` raises
  `mark_base_unrollable`, and does so on every later derive, because `[S, E]` only grows. The drill
  prints `NaN realized day after S -> mark_base_unrollable`.
- **(c) One bad live read.** A dust, non-finite or `balance_error` equity read gives
  `_apply_terminal = None` (`:7491-7502`) and FAILED permanent for that day. Plan 07 recorded this as
  "worth a founder look". It flips a published strategy to `failed` for a transient read error.

Each trigger stamps the user-visible failed copy (strategy mode). In key mode it leaves
`key_inputs` frozen on the last good row, so My Allocation degrades. A composite member takes the
whole composite down (`_refuse_member_marks`). The realized TWR path handles the same events as a
chain break (NaN plus `twr_chain_broken`). The marks path has no equivalent.

**Fix (minimal):** (1) the CR-01 fix removes (b) and (c), because nothing after `S` is rolled.
(2) In the mark loop, treat a non-positive base, or one below `DUST_NAV_FLOOR`, as a chain break and
not a refusal. Emit no return for that mark day and pin `level_prev = nav`, exactly like rule 4's
"no base, no return row". Name the day in a list such as `mark_break_days` that the runner maps to
the existing chain-break flag:

```python
if not (math.isfinite(base) and base > DUST_NAV_FLOOR):
    breaks.append(md)            # surfaced like twr_chain_broken, never a refusal
else:
    rows.append((md, day_result / base)); ...
level_prev = nav; prev_day = md
```

This also covers the missing small-base guard. Today a gap-day withdrawal that leaves a base of $50
(above 0, below the $100 dust floor) publishes a return of several hundred percent, where the
realized path would NaN-guard it.

### CR-03: A refusal streak that never ends silently freezes the published series at the last stored mark [HIGH, user-facing]

**File:** `analytics-service/services/nav_marks_apply.py:337-359` (output ends at `last_mark`;
`mark_gap_days` only covers `(S, last_mark)`); `analytics-service/services/job_worker.py:7090`
(a refused write) together with `:7505-7514` (the apply still runs on the older marks).

**Issue:** once a key has one stored mark, every realized row after the latest stored mark is
dropped (Pitfall 7). D-05 assumes "the next stored mark's return covers the whole gap". Several
refusal tokens are persistent account states, not daily noise: `borrow_present` (Bybit UTA
auto-borrow), `wallet_basis_mismatch` (a Bybit/Binance account starts holding USDC or BTC),
`account_mode_unsupported`, `isolated_margin_unsupported`, `uta_wallet_mismatch`, and
`option_value_unverified` (any OKX or Binance account that opens an option after its first mark,
refused "until measured" by D-19/D-20). Scenario: a Bybit strategy is marked on 11-04, and from
11-05 it carries a USDT borrow. Every derive from then on publishes a series ending 11-04 with
status `complete`. `mark_gap_days` is empty because there is no later mark, nothing reaches
`data_quality_flags`, and the factsheet shows a stale track record with no warning. Strategy mode
does not persist the refusal token at all (Plan 19 limit: "strategy-mode logs the refusal token").
For Deribit and sFOX strategies the frozen `last_return_date` also makes
`ledger_refresh_staleness.is_stale` true after 4 days, and the hourly `ledger_refresh_fanout` then
re-crawls the full history every hour to no effect. D-05's "the gap days are named" is unmet for a
trailing gap.

**Fix (minimal):** stamp the trailing gap. When the last stored mark is older than the label day of
this derive (`mark_day_for(_mark_read_at)`), add `marks_trailing_since: <last_mark+1>` and the
refusal token to the prestamp flags. Make that a warning key (a `NAV_TWR_GUARD_KEYS` member, so
`computation_warned` is set) once it exceeds a small bound such as 3 days, so the factsheet says the
figures stop on that day. Persist `nav_mark_refusal` in strategy mode as key mode already does. A
fallback to realized rows after N refused days is a founder decision and should be routed, not
improvised.

## Warnings (MEDIUM)

### WR-01: Executor item, CONFIRMED. The browser recompute counts a composite's covered days as flat 0.0 observations, against D-15 [MEDIUM, user-facing]

**File:** `src/app/factsheet/[id]/v2/basis-context.tsx:270` (`calendarDense: view.dataQuality?.composite === true`),
`src/lib/factsheet/compute.ts:423-447` (zero-fill at `:441`, `while (returns.length < offset) returns.push(0);`),
`src/lib/factsheet/compute.ts:141` (ann_vol, Sharpe, Sortino, arithmetic CAGR over that series),
`src/lib/factsheet/build-payload.ts:414-417,480-482` (rolling vol/Sortino on `dense`, rolling Sharpe on `basis`).
The server excludes the same days: `job_worker.py:10804-10842`
(`_scalar_input_without_covered_days`) and `basis_series.py` (`covered_days` dropped from the scalar
input and from `gap_spans`).

**Issue:** after NAVMTM, an absent day inside a composite's span is one of two things. Either it is a
real inter-member hole (a persisted gap span, server 0.0-fills it) or it is a covered day (inside the
next mark's single return, which the server drops: D-15, one observation). `metricsBasisSeries` with
`calendarDense` cannot tell them apart, because the payload carries no covered-day list. It
zero-fills both. Where it is visible:

- **Selected-range KPIs.** `windowView` (`basis-context.tsx:643-650`) re-derives the strip and the
  rail through `deriveSeriesBundle(slice, rederiveArgs(view))`. For a composite, ann_vol, Sharpe,
  Sortino and the arithmetic CAGR/Calmar of any window containing a covered day are computed with
  extra 0.0 observations. This is visible as soon as a user zooms. At full history the seven
  headline KPIs are the persisted overlay (`basis-metrics.ts:18-26`), so those are correct. A range
  of one day less than full history therefore shows a different Sharpe for a reason that is not in
  the data.
- **Rolling volatility, Sortino and Sharpe charts**, at full history too, from `build-payload.ts:480-482`.

The leverage arm is not affected, because composites are leverage-ineligible.

Concrete case: a composite's current OKX member is refused for five days (an option is held) and then
marked +4% over the six days. The server counts one +4% observation. The browser counts five zeros
plus +4% in the window figures and rolling charts, so the vol is lower per observation, the Sharpe
is diluted, and the rolling vol dips across the gap. Plans 09 and 17 recorded this as a known
limit. It is a D-15 violation on a published surface, not a cosmetic one. It appears only when a
composite has covered days, and D-15's own readout says it should be rare. Each occurrence still
lands on the factsheet.

**Fix (minimal):** the persisted composite `gap_spans` already exclude covered days (`coverage_mask`
and `derive_basis_series`), and the payload carries them as `missingSegments`. In the `calendarDense`
branch of `metricsBasisSeries`, zero-fill only the absent days that fall inside a `missingSegments`
span and skip every other absent day. `rederiveArgs` and the `deriveSeriesBundle` callers already
pass `missingSegments`, so they need only thread it into `compute()`/`metricsBasisSeries`. This
reproduces the server's scalar input exactly. Pin it with a fixture that has one gap span and one
covered day.

### WR-02: A flow dated the read day that lands before the mark read is booked as profit on `d` and as a loss on `d+1` [MEDIUM, user-facing, data-integrity]

**File:** `analytics-service/services/nav_marks_apply.py:328` (`day_result = nav - base - flows.get(md, 0.0)`),
`:357-359` (`mark_flow_read_days` only names it).

**Issue:** mark `d` is read on UTC day `d+1`, between about 00:10 and 00:40Z on the moved chain and up
to 24 hours later under a D-11 retry. A deposit `F` at 00:05Z on `d+1` is inside `M_d` but dated
`d+1`. Then `r_d = (M_d - base - F_d)/base` counts `+F/base` as profit, and
`r_{d+1} = (M_{d+1} - M_d - F)/M_d` counts `-F/M_d` as a loss. Example: base 100k and a 50k deposit
at 00:05Z publish +50% on `d` and about -33% on `d+1`. Cumulative return roughly survives, but vol,
Sharpe, Sortino, worst days and max drawdown carry two fabricated outliers. Rule 10 names the day
and leaves the arithmetic as it is. The day-granular flows cannot be placed by instant, but the
mark itself can be dropped.

**Fix (minimal):** in `apply_marks`, treat a mark day listed in `mark_flow_read_days` as unmarked
(a gap) unless it is the last mark. The next mark's single return then spans both days with
`F_d+1` in its numerator and `F_d` in its base. That is correct whichever side of the read the
deposit fell. Keep listing the day so the readout still counts it.

### WR-03: A composite member's realized days between its last in-window mark and `window_end` are dropped and published as a 0.0 hole [MEDIUM, data-integrity]

**File:** `analytics-service/services/job_worker.py:9681-9714` (`_apply_member_marks`:
`relevant = mark_day < window_end`) with the stitch at `:10695` and `:10836`.

**Issue:** Pitfall 7 drops every realized row on or after a member's first mark. For a member whose
window has CLOSED, the days between its last relevant mark and `window_end - 1` are covered by no
later mark (marks `>= window_end` are excluded on purpose), and the realized rows are gone. Scenario:
member A's window is `[2026-01-01, 2026-11-20)`, and its marks for 11-17..11-19 are refused (option
held, a read failure, `borrow_present`). A's output ends 11-16, 11-17..11-19 become a
`coverage_mask` gap span, and `gap_fill_daily_returns` 0.0-fills them. A's real P&L for those three
days leaves the composite's cumulative return permanently. Before NAVMTM those days carried A's
realized returns. The allocated member has the W2 tail rule for exactly this case (`:9806-9819`),
and the non-allocated member does not.

**Fix (minimal):** mirror W2 in `_apply_member_marks`. When `window_end` is set and
`window_end <= mark_day_for(_utc_now())` (closed), append the member's own pre-apply rows dated in
`(marked.terminal[0], window_end)` to `marked.returns`.

**Fix:** fold it into the WR-03 change. Treat the first in-window mark whose previous mark lies before
`window_start - 1` as having no base (rule 4).

### IN-06: My Allocation names a marks-start date even when that key's key-mode apply refused [LOW]

**File:** `src/lib/queries.ts` (`readMarksStart`, earliest `mark_day` of included keys).
**Issue:** a key whose key-mode derive refuses (CR-02) keeps a realized-basis `key_inputs` row, yet
its marks still set the note "Recorded equity from …".
**Fix:** read the start from `key_inputs.payload.marks_since` (written only when the apply succeeded)
instead of the raw marks table.

### IN-07: `covered_day_count: 0` is echoed when a composite member had marks but no covered days [INFO]

**File:** `analytics-service/services/job_worker.py:10840` (`covered_days=_covered if member_marked else None`).
**Issue:** an empty tuple is not `None`, so `conventions.covered_day_count = 0` is added and the
payload is no longer byte-identical. This is harmless.
**Fix:** `covered_days=_covered or None`.

- Plans 09 and 17 "the browser recompute still zero-fills a composite's covered days": confirmed
  and user-visible (WR-01).
- Plan 09 "a realized row after a member's last mark is dropped": for a closed window this is data
