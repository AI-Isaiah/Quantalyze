# Phase 167.2.1.1.1 Plan 19: Option value in the OKX and Binance marks Summary

An OKX or Binance mark is now stored only when the account holds no open option value (or, on Binance, the key has no options access), and is otherwise refused by name: `option_value_unverified` for a holding, `option_value_unreadable` for a read or shape that cannot be trusted. Deribit is plan 20's.

## What was built

**OKX (D-19).** `read_okx_option_exposure(exchange)` awaits `exchange.privateGetAccountPositions({"instType": "OPTION"})` (`GET /api/v5/account/positions?instType=OPTION`) and returns `None` (no row with a non-zero `pos`; a row at exactly zero is flat), `"option_value_unverified"` (at least one non-zero `pos`) or `"option_value_unreadable"` (raise, body not a dict, `data` not a list, a row that is not a dict or whose `pos` is not a finite number). A holding wins over a garbled sibling row. `job_worker._read_okx_option_refusal_once_per_day` runs inside the ccxt venue `try`, right after `_mark_read_at` is stamped and before `finally: aclose_exchange` (B1): it reads the stored mark for (key, closed day) first and returns `None` without any venue call when one exists (W1), otherwise awaits the reader under `_BROKER_CRAWL_TIMEOUT_S` (a timeout or stray exception is `option_value_unreadable`, never a failed derive). The token goes to `build_mark_read(refusal=...)` in `_write_nav_mark_for_this_derive`; with a stored row the writer is still called and returns the stored row, so it stays the authority.

**Binance (D-20, D-22).** After the L4 read has succeeded (an L4 refusal is returned as it stands and no options read is made), `_read_binance_options_exposure` makes both `eapiPrivateGetMarginAccount()` (`GET /eapi/v1/marginAccount`) and `eapiPrivateGetPosition()` (`GET /eapi/v1/position`), each judged on its own:

- margin rows (`asset[]`) need a finite `marginBalance` and `equity`; either non-zero is a holding;
- position rows need a finite `quantity` or `markValue`; either non-zero is a holding (a row at zero for both is flat);
- a read that raises with a parsed numeric code in `_BINANCE_OPTIONS_NO_ACCESS_CODES` (`frozenset({"-2015"})`) counts as zero; any other raise (including `-2014`, same ccxt class) or a garbled shape is unreadable;
- a holding anywhere is `option_value_unverified` and wins over an unreadable sibling.

### The parsed-code log line (stable; plan 11's dry run greps it)

One line per refused or unreadable options read, from logger `quantalyze.analytics.equity_reconstruction`:

```
binance options read: endpoint=<marginAccount|position> outcome=<no_access|unreadable> parsed_code=<code|none> exc_class=<exception class|none>
```

`parsed_code` is the signed integer from the error text (for example `-2015`), or `none` when there is none; `exc_class` is `none` when the problem was a reply shape rather than a raise. `outcome=no_access` is logged at INFO, `outcome=unreadable` at WARNING. Venue text is never logged. The OKX reader logs `okx option exposure: ...` lines (class name, counts and tokens only). To decide whether -2015 was observed: grep for `binance options read:` and look for `outcome=no_access parsed_code=-2015`; any `outcome=unreadable` line with a different `parsed_code` on a key the founder knows has no options access means the pinned code is wrong.

## For plan 11: the call sequences the post-deploy dry run runs

Per key per UTC day, and only when the closed day's mark is not already stored:

- **OKX derive:** existing equity read (`totalEq`) -> stored-mark DB read -> `GET /api/v5/account/positions?instType=OPTION` (one) -> close. Was: equity read only.
- **Binance derive:** existing stored-mark read -> L4 read (`fetch_balance`, `fetch_positions`, one `fetch_ticker` per held non-stable asset) -> `GET /eapi/v1/marginAccount` (one) -> `GET /eapi/v1/position` (one). When the L4 read refuses, the two options reads are not made. When the mark is stored, none of these calls is made.

Call counts amend D-02 for OKX (one option read) and D-16 for Binance (two options reads).

## Known limits

- **I2, what is not proven:** `-2015` is a placeholder until plan 11's first post-deploy run measures the code a key without options permission receives. The tests pin only what ccxt states (4.5.85: `exceptions['exact']['-2015']` and `['-2014']` are both `AuthenticationError`), so the class cannot tell options no-access from a bad key; the reader goes by the parsed numeric code, and nothing here can prove Binance returns -2015 for options access. A different observed code stops plan 11 and goes to the founder.
- Binance response shapes (`asset[].marginBalance`/`equity`, position `quantity`/`markValue`) are from the documentation by field name only; no live call was made. A real reply that differs would read as `option_value_unreadable` (refused by name), not as zero.
- Both Binance options reads are always made, so a key with no options access logs two `no_access` lines per day and a wallet-basis mismatch is still judged after the two reads were spent.
- OKX judges "open" by a non-zero `pos` only; it does not read `optVal`. Until the post-deploy measurement lifts D-19, every OKX account with an open option is refused.
- The OKX option read shares the derive's per-crawl bound; the refusal reaches `key_inputs.nav_mark_refusal` in key-mode only (strategy-mode logs the refusal token, as before).
- `job_worker.py` edits are confined to the helper, the `_okx_option_refusal` local, the `elif venue == "okx"` call and the `refusal=` argument; plan 20 follows on the same file.
