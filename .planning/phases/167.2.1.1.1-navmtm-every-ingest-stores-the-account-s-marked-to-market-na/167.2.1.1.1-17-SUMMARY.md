# Phase 167.2.1.1.1 Plan 17: NAVMTM allocated-capital composites follow marked NAV Summary

**The Deribit member of a composite with a returns_denominator_config now keeps its allocated history up to its first in-window mark, books the D-04 step over the NAV twin's level of its own crawl, follows its key's marked NAV by the day-P&L roll from then on, keeps a closed mandate's tail, and refuses the whole composite by name (`mark_allocated_nav_unreconciled`, nothing written but the failed stamp) only when it has a mark it cannot apply.**

## What was built

All in `run_stitch_composite_job` (`analytics-service/services/job_worker.py`), plus one module-level exception (`_MemberNavUnreconciled`). `git diff -w` of the plan on that file is 163 insertions and 6 deletions.

- **The selector now sets a seq.** In `_reconstruct_all`, `_member_returns_are_allocated` (plan 09) sets `_member_allocated_mark_seq` on the cash pass only (the mark_to_market and smoothed passes are not marked, as in plans 07, 09, 16). Plan 09's skip comment is replaced by one naming D-14, plan 16 and Bug B.
- **The twin request (before the crawl).** `_reconstruct_deribit` takes `allocated_mark_seq`. For that member it reads the key's stored marks (`_allocated_member_marks`: inside the composite's mandate window by plan 16's `_marks_in_mandate_window`, and before the member's closed window end by plan 09's rule), and sets `_member_wants_nav_twin` true only when that list is non-empty or `_mandate_window_contains(mark_day_for(_utc_now()), config)`. `nav_twin=_member_wants_nav_twin` is passed on the cash-basis `build_deribit_native_ledger` call ONLY on this path, so every other member makes the call it always made.
- **The apply (before the clip).** `_apply_allocated_member_marks` runs the three helpers (`native_ledger_realized_terminal`, `_day_pnl`, `_composed_flows`) on `report.nav_twin_ledger` off the loop (`asyncio.to_thread`, WEDGE-01), then `apply_marks(..., roll_basis="day_pnl")` on the member's UNCLIPPED allocated series, records the result in `member_marked[seq]` (so the covered days, `marks_since` and gap flags of plan 09 follow), and returns it; `clip_to_window` cuts afterwards as before.
- **W2 tail.** With a `mandate_end` after the last applied mark day and before the day this run's marks label, the member's own allocated rows in (last applied mark day, `mandate_end`] are appended verbatim. While the window is open nothing is appended.
- **W1 / L3.** No in-window mark: nothing is applied and one `nav_twin_unbuildable (seq=<n> error=<class>)` warning is logged when a twin was asked for and is absent. An in-window mark and a missing twin, or a `NavReconstructionError` from a helper (section 5 included), raises `_MemberNavUnreconciled` (token `mark_allocated_nav_unreconciled`, plan 16's constant). `_reconstruct_all`'s Deribit arm catches it together with `MarkApplyRefusal`, ahead of every degrade arm, and `_refuse_member_marks` returns plan 09's whole-composite refusal: `run_stitch_composite_job: nav marks refused (seq=<n>, mark_allocated_nav_unreconciled)`, FAILED permanent, nothing persisted but the failed stamp, the member not reported degraded, no amount in any text.
- **The simple-sum rule (D-14).** The composite already measures by its configured `cumulative_method`; `test_simple_sum_rule_for_the_composite` pins that the headline cumulative return is the sum of every persisted row (member 1, the allocated pre-mark rows and the marked rows) and not the compounded figure.

## Deviations from Plan

**1. [Rule 3 - Blocking] Two existing tests edited for the new twin keyword.** `test_stitch_composite_job.py`: the `_build` stand-ins of `test_smoothed_composite_structural_failure_degrades` and `test_smoothed_composite_budget_overrun_degrades` (both use a composite with a config and an open mandate) now accept `nav_twin: bool = False` (4 changed lines, no assertion changed), because the cash pass now asks the allocated member for the twin. Same call plan 16 made for `test_mtm_single_key.py`. The plan's acceptance line names only the new module; this is why it does not hold literally.

**2. [Rule 1] Plan 09's hand-off test replaced.** `test_configured_composite_deribit_member_is_left_for_plan_17` asserted the very behavior this plan removes (an unmarked allocated member). It is now `test_configured_composite_deribit_member_is_no_longer_left_alone`: with a stored in-window mark and the harness' stub ledger (no twin) the composite refuses by name, writing only the failed stamp. The real behavior is pinned in the new module.

**3. The Task 2 refusal and W1 code landed in Task 1's GREEN commit, and `red2.log` is run against the plan-base file.** An allocated member that applied marks but could not refuse would raise an unhandled error that is retried forever, so W1, the section-5 path and the named refusal went in with the first seam (as plans 07, 09 and 16 did). Task 2's tests therefore pass on their first run at HEAD; their ability to fail is shown by `red2.log` and the drills. Task 2 has no code commit of its own.

**4. The mark filter intersects two windows.** The plan names the mandate window; the member's own closed window end (plan 09's rule, Deviation 2 there) is kept as well, so a mark that can change nothing the member's window shows cannot refuse the composite. Pinned by `test_allocated_member_mark_outside_its_window_cannot_refuse_the_composite` and drill D-WE.

**5. A new exception class, not `MarkApplyRefusal`.** `MarkApplyRefusal` rejects any token outside `apply_marks`' closed set, so `mark_allocated_nav_unreconciled` could not be raised through it. `_MemberNavUnreconciled` carries the token and is caught beside `MarkApplyRefusal` in the Deribit arm of `_reconstruct_all`.

**6. The log line reads `nav_twin_unbuildable (seq=<n> error=<class>)`**, the token form the behavior spec names and plan 16 used, not the spaced `nav twin unbuildable` of the action sketch.

**7. Branch.** Committed on `feat/167.2.1.1.1-p17` as the orchestrator assigned (the plan text names `feat/167.2.1.1.1-navmtm`); it is not in the `agent-*` namespace the pre-commit allow-list expects, it is not protected, and no `<sequential_execution>` block was given (same call as plans 03, 06, 07, 09, 13, 16).

## Known limits (recorded, not fixed)

- **The twin is requested for every allocated Deribit member of an open-mandate composite, marks or not.** The plan's rule (the window holds the day the run's marks label) was written for the single-strategy derive, which writes that day's mark itself; the composite stitch writes none, so for a composite this request is an extra in-memory build (no venue call) for a member that may have nothing to apply. It is harmless, as the W1 (a) path shows, and is as the plan states.
- **A member whose twin cannot be built refuses the WHOLE composite on every stitch from its first in-window mark** until the twin can be built (named, nothing written, T-167.2.1.1.1-59/-62 as in plan 16's T-48). Plans 11 and 14 read the risk and the outcome.
- **The mark_to_market and smoothed composite bases keep their realized (allocated) basis**, as in plans 07, 09 and 16.
- **Conservative over-refusal** from plan 16 applies unchanged (a missing price on a currency's last balance day refuses even when the currency is liquidated that day).
- **The browser recompute still zero-fills a composite's covered days** (plan 09's recorded limit, unchanged).
