## Summary

The replay emits only literal top-level `INSERT … VALUES` statements (criteria C1-C4). Phase 164.9 plan 07 then added a value-pinning leg (`v_wrong_state`) that pins the teaser sentinel profile's `manager_status` to `verified`. The UPDATE that produces `verified` (`20260521150000_universal_signup_approval_gate.sql`) is never replayed. So the first real preflight, run `36003106273`, aborted on that leg. I re-read that run's log this session (read-only `gh run view`). It printed `refdata: 23 statement(s) replayed into 8 table(s)` and then `restore aborted: reference row(s) came back in the WRONG STATE after the replay — public.profiles.manager_status for id=00000000-0000-0000-0000-000000000000 disagrees after the replay`. Conclusion `failure`, head `71697364`.

The fix is small and well bounded. Measured at HEAD, the migration corpus has exactly 8 top-level UPDATEs on a `public` table the replay fills: 5 on `profiles` and 3 on `strategies`. None touches the five FK/CHECK-bearing reference tables. 6 of the 8 are literal: no `FROM`, `SELECT`, `USING`, `RETURNING` or `WITH`, and no function calls. The other 2 are non-literal joins (`… FROM user_app_roles`, `… FROM (SELECT … unnest …)`). A throwaway classifier run over the real corpus shows that exactly one of the six literal UPDATEs changes a replayed row: `20260521150000` line 28, which sets the sentinel's `manager_status` to `verified`. The other five match no replayed row. One of those five (`20260429063138`) comes before the sentinel's INSERT in filename order. That makes it the natural falsifier for criterion 2: emit order must be migration-filename order, not allowlist-line order.

**Primary recommendation:** Keep ONE allowlist file. Add a new C5 statement class, keyed exactly like C1-C4 as (file, table, pinned count), with the count spelled `update:<n>` in field 3. Add a `decline:<n>` spelling so every top-level UPDATE/DELETE on a replayed table is accounted for by name, never skipped in silence. Emit INSERT and UPDATE blocks merged and sorted by (migration basename, byte offset). Give UPDATEs their own trailers (`-- refdata-update:` / `-- refdata-update-expect:`) so the existing INSERT count gates and census lines stay byte-identical. Leave the `v_wrong_state` predicate, its four seams and its `verified` default untouched. It is the phase's acceptance oracle, and it goes green on its own once the UPDATE replays.

## Q1 — How the extractor classifies today, and every pinned count

**Classification path** [VERIFIED: `scripts/extract-reference-inserts.mjs`, read this session]:
- `prepareFile(src)` builds `maskSql` + `statements()` spans (from `scripts/lint-sql-gates.mjs`). Each span carries `inBody` (the `dollarBodyRanges()` scan), `hasTag` and `terminated`.
- `matchTable(src, prep, qualified)` matches `headRe` (`^INSERT INTO [schema.]table`, quoted spellings too). It then sorts each span into `ok` / `body` / `rejected`. `rejected` covers: CTE-prefixed INSERTs, unterminated statements, a `$`-tag, and a `literalCheck()` failure (SELECT/FROM, no VALUES, an ON CONFLICT action other than DO NOTHING, a non-literal token in the VALUES tuple; allowed are `NULL TRUE FALSE DEFAULT`, `::casts`, `now()`, `gen_random_uuid()`).
- `parseAllowlist` requires exactly 4 TAB fields: `BASENAME_RE`, `QUALIFIED_RE`, a count matching `/^[1-9][0-9]*$/`, and a `# consumer`. It gates C3 through `schemaAllowed(qualified)`, which returns `qualified.startsWith("public.") || qualified === "auth.users"`.
- **The ONE refusal path** is `refuse()`, exit 1. Three modes: emit (default), `--audit`, `--self-test`.
- ⚠️ **Emit order is allowlist-line order.** `modeEmit` iterates `entries` and pushes blocks per entry. Measured this session: today's output happens to already be in (file, line) order, because the allowlist is written in filename order. Sorting explicitly is therefore a no-op for today's INSERT output (see Pattern 4).

**Refuse, never replay:**
- any non-`public` target. `auth.users` is the INSERT-only C3 exception and must NOT carry over to C5 ("never `auth.*`").
- non-literal shapes: FROM/USING joins, subqueries, CTE-prefixed `WITH … UPDATE`, RETURNING, function calls other than `now()`. `current_setting`, `auth.uid()`, `net.http_*` and `pg_notify` are all caught by the call ban.
- `$`-tags (the redaction grep), and unterminated statements.

**How the extractor fails loud on an unclassifiable one.** For every top-level UPDATE/DELETE/TRUNCATE/MERGE whose head names a table that has an INSERT entry, `--audit` requires the (file, table) pair to carry EITHER an `update:<n>` line (literal, replayed) OR a `decline:<n>` line (non-literal, with a `# reason`), and the count must match. Anything else is a named `refuse()`:
- literal + unlisted → "add an `update:` line";
- non-literal + unlisted → "classify by hand: decline it with a reason; this extractor does not replay joins";
- DELETE/TRUNCATE/MERGE → "C5 replays UPDATE only";
- `update:` line on a non-literal statement → the literal-check reason;
- `decline:` line on a literal statement → "a literal UPDATE is replayed, not declined". Otherwise a decline could hide a replayable effect.

This is the INSERT side's `audit-unlisted` rule, with limitation 2 (silent skip of an unlisted non-literal) deliberately NOT carried over.

## Q3 — Interleaving with the INSERTs, inside the same transaction

**Where the statement list is built** [VERIFIED: `scripts/restore-test-from-baseline.sh`, `build_transaction`, read this session]:
1. `build_transaction` runs `node "$REFDATA_EXTRACTOR" --allowlist … --migrations …` a second time, into `$RESTORE_OUT_DIR/refdata.sql`.
2. It writes the `TXN_REFDATA_HEAD` heredoc: the `$rlsguard$` DO block (the role must be `rolbypassrls OR rolsuper`), then `SET LOCAL search_path = public, pg_catalog;`.
3. `cat "$RESTORE_OUT_DIR/refdata.sql" >> "$out"`: **the replay is the extractor's output, verbatim.**
4. `TXN_REFDATA_TAIL` (`SET LOCAL search_path = pg_catalog;`), then the `TXN_REFDATA_GATE` DO block (EMPTY / SHORT / `v_wrong_state` / kind-registry), then the ledger.

It all sits inside one `BEGIN; … COMMIT|ROLLBACK` stream fed to one psql session. **So interleaving is entirely the extractor's emit order.** No bash change is needed for criterion 2, and an UPDATE emitted into `refdata.sql` is inside the same transaction automatically. The local-stack lane runs the same generator in `load_reference_data` (`psql -f` of the extractor output after the baseline load). It inherits the same order.

**Order rule:** sort every emitted block by (migration basename, byte offset of the statement's first token in that file). Basename order is filename-timestamp order, which is the ledger's and PROD's chronological order. Within one file, byte offset is authored order. Do NOT sort by allowlist line order; that is the bug the falsifiers catch.

## Architecture Patterns

### System Architecture Diagram

```
supabase/migrations/*.sql ──┐
                            ├─► extract-reference-inserts.mjs ──(prepareFile: maskSql+statements+dollarBodyRanges)
allowlist.txt (C1-C4 + C5) ─┘        │
                                     ├─ INSERT entries ─► matchTable ─► ok | body | REFUSE
                                     ├─ update: entries ─► matchUpdate (C5 literal check) ─► ok | REFUSE
                                     ├─ decline: entries ─► must be non-literal ─► counted, never emitted
                                     ▼
                     merge + sort by (basename, offset)  ──► refdata.sql
                     trailers: -- refdata: / -- refdata-expect: (INSERT only)
                               -- refdata-update: / -- refdata-update-expect: (C5)
                                     │
      ┌──────────────────────────────┼─────────────────────────────────┐
      ▼                              ▼                                 ▼
restore build_transaction      local-stack load_reference_data     --audit (CI: sql-gate-lint,
BEGIN; dump; survivors;        psql -f (loopback lane)             restore workflow pre-steps)

TXN_REFDATA_GATE (EMPTY/SHORT from refdata-expect;
  v_wrong_state UNCHANGED; kind registry)
ledger seed; COMMIT|ROLLBACK
```

### Pattern 1: C5 lives in the SAME allowlist and the SAME classifier module
**What:** extend `parseAllowlist` with an entry `kind` (`insert` | `update` | `decline`), and add `matchUpdate(src, prep, qualified)` beside `matchTable`, sharing `prepareFile`, `refuse()` and the head-regex helpers (`quotedId`).
**Why:** `filterRefdataAllowlist` keys on field 1, so the lane gets C5 for free. The restore's two extractor invocations need no new flag. The file is not scanned by a second parser.
**Rejected alternative:** a second allowlist file. That needs a second `REFDATA_ALLOWLIST_IN/OUT` pair in `check-baseline-currency.mjs` (its R-arms), a second seam in `run.sh`, and a second argument in both restore call sites. More surface for no gain.

### Pattern 2: the C5 literal check (over the MASKED statement)
Refuse `\b(FROM|USING|SELECT|RETURNING|WITH)\b`, any `$`, and any `identifier(` except `IN (` and `now(`. Require `^UPDATE [ONLY] <target> [[AS] alias] SET`. Column identifiers in SET/WHERE are allowed; that is the one real difference from C2's VALUES-tuple rule. The prototype over the real corpus is in the Q2 table.

### Pattern 3: decline, never skip
A `decline:<n>` line is an accounted-for non-replay with a written reason. It is emitted as nothing, counted in the C5 census, and refused if the statement turns out literal. It stays a human call, the way C4 does.

### Pattern 4: emit order = (basename, offset)
Collect `{file, first, sql, trailer}` for every ok span of every entry, sort, then push. Sorting today's INSERT set is a no-op (measured). That is the byte-identity invariant.

### Pattern 5: separate trailers
`-- refdata-update: <file>:<line> <table>` after each UPDATE block, plus `-- refdata-update-expect: <table>=<n>`. The restore's awks match `^-- refdata-expect: ` and `^-- refdata: ` exactly, so they cannot pick these up. Optionally add a second restore `note` with the UPDATE count, so the TEST log records that C5 ran. That is evidence for criterion 4.

### Pattern 6: prove the fix through the UNCHANGED oracle
New arms 33/34 point the existing `REFDATA_WRONGSTATE_*` seams at fixture row 3. No new gate leg, and nothing about the leg changes.

### Anti-Patterns to Avoid
- **Counting UPDATEs into `refdata-expect`.** It breaks the SHORT floor's soundness argument ("each allowlisted statement inserts at least one row").
- **Re-using `auth.users`' C3 exception for C5.** `auth.users` survives the DROP, so an UPDATE there would mutate shared TEST's live row.
- **Emitting in allowlist-line order.** `20260429063138` then silently depends on who sorted the file.
- **Replaying a joined UPDATE because "it's a no-op on an empty table".** True today, unprovable in general. Decline it with a reason instead.

## Common Pitfalls

### Pitfall 1: "fixing" the wrong-state leg instead of the replay
Do not touch the `v_wrong_state` SELECT, `REFDATA_WRONGSTATE_TABLE/ID/COL/EXPECTED` (defaults `public.profiles`, `00000000-0000-0000-0000-000000000000`, `manager_status`, `verified`, verbatim from the script's seam block) or arms 31/32. ⚠️ The RAISE's explanatory prose ("The replay reproduces INSERT effects only … an UPDATE is not a literal INSERT (C2)") becomes stale once C5 lands. Updating PROSE is not relaxing the check, but it is inside the unquoted `TXN_REFDATA_GATE` heredoc. So: no backticks (refusal 9, `refuse_backticks_in_txn_heredocs`), and arm 31 greps only `WRONG STATE after the replay` and `public.fx_keep.status for id=2`. Keep both substrings. See Open Question 1.

### Pitfall 2: UPDATEs leaking into the count floor
`refuse_bad_refdata_allowlist` builds `REFDATA_EXPECT` from `-- refdata-expect:` trailers. The gate asserts `count(*) >= expected`. An UPDATE counted there inflates `expected` and makes `profiles` read SHORT (1 row vs 4 statements), which aborts every restore.

### Pitfall 3: triggers on the UPDATE path
`profiles_lock_privileged_cols` (`prevent_profile_privileged_change`) fires `BEFORE … UPDATE OF … manager_status …`. It returns early only when `current_user IN ('postgres', 'service_role', 'supabase_admin')` [VERIFIED: `supabase/schema/baseline.sql` function body, read this session]. Any other connecting role gets `42501`. The self-test lane is initdb's superuser `postgres`. That shared TEST's session-mode connection runs as `postgres` is [ASSUMED]; the existing `$rlsguard$` checks only `rolbypassrls OR rolsuper`, not the role NAME. The preflight measures this safely, because a 42501 aborts and rolls back. `profiles_reject_sentinel` passes any non-`authenticated`/`anon` user. The strategies triggers (`guard_wizard_draft_updates`, `guard_strategies_publish_transition`) fire only per matching row, and no strategies UPDATE matches a replayed row today.

### Pitfall 4: the W3 masthead recipe silently changes meaning
`grep -vE '^[[:space:]]*(#|$)' … | cut -f1 | sort -u | wc -l` counts C5 lines' files too: 19 → 25, because none of the 4 replay files or the 2 decline files is among today's 19 (checked against the allowlist's field 1). Rewrite the recipe class-aware (e.g. filter field 3 `^[0-9]+$` first), keep the old paragraph as dated lineage, and update the entries/files/tables/statements sentence.

### Pitfall 5: `refdata-allowlist.test.ts` measures every entry as an INSERT
"every pinned count agrees…" and "CALIBRATION" call `measure()` → `matchTable`. A `update:3` line fails `^[1-9][0-9]*$` in today's parser and makes the live-allowlist tests red. Branch on `kind`, and give C5 its own calibration (±1 on an `update:` count must be caught).

### Pitfall 6: the lane's filtered allowlist and a membership check in emit mode
`check-baseline-currency.mjs --replay-set` drops allowlist lines naming migrations newer than the dump. An `update:` line whose file is carried while every INSERT for its table is in a replayed file would fail an emit-time "table must be INSERT-filled" check and FATAL the lane boot for everyone. That only happens for an UPDATE older than its table's seed (like `20260429063138`), with a dump older than the seed. It is latent today (`replay=0`). **Enforce membership in `--audit` (full allowlist, CI), and only `public.*` in emit.**

### Pitfall 7: CTE-prefixed UPDATE evading the head regex
`WITH x AS (…) UPDATE t …` does not start with UPDATE. Refuse it by name (mirror `cteHeadRe`), never skip it.

### Pitfall 8: closing the TODOS entry by rewriting its evidence
`[164.8.1-REPLAY-INSERT-ONLY-SCOPE]` says "⛔ Not closable by editing the allowlist … would break C2". C5 is a new criterion, not a C2 relaxation. Close the entry with a DATED note saying so, and keep the original text as lineage (the repo's "CORRECTED … kept as lineage" idiom). Do the same for the allowlist's `SCOPE BOUNDARY` block, which lists "five" UPDATEs. The census now reads 8 (the entry's own list names 7 lines across 5 files).

### Pitfall 9: fixture edits ripple into the restore arms
Put the new fixture UPDATE in `20260103000000_fixture_c.sql`. A new fixture migration file would change the seeded-ledger count every ledger arm pins. Re-run all 34 arms; arm 22's row counts and arm 24's "2-over-3 shape" must be unaffected (an UPDATE adds no row).

### Pitfall 10: a post-commit red on the committing run
See Q6 step 6. A `mode=restore` run can COMMIT and still conclude `failure` on the post-commit extension guard. Record the conclusion as it is. Criterion 4 wants GREEN, so a post-commit red is a new finding to surface, not something to re-dispatch around.

## Code Examples

### C5 literal check (sketch; the executor adapts it to the module's style)
```js
// Source: pattern of literalCheck() in scripts/extract-reference-inserts.mjs, adapted for UPDATE
export function updateLiteralCheck(masked) {
  if (/\b(FROM|USING|SELECT|RETURNING|WITH)\b/i.test(masked))
    return "carries FROM/USING/SELECT/RETURNING/WITH — a joined or sub-selected UPDATE is not a literal C5 update; decline it with a reason (C5)";
  if (masked.includes("$")) return "carries a dollar-quoted body (C5)";
  const call = /([A-Za-z_][A-Za-z0-9_]*)[\t\n ]*\(/g;
  for (let m; (m = call.exec(masked)); )
    if (!/^(IN|now)$/i.test(m[1])) return `calls \`${m[1]}()\` — only literals, column references, IN lists and now() are replayable (C5)`;
  return null;
}
```

### Emit merge + sort
```js
// Source: modeEmit() in scripts/extract-reference-inserts.mjs — replace per-entry push with collect-then-sort
blocks.push({ file: e.file, first: s.first, text: `${s.sql}\n-- refdata-update: ${e.file}:${s.line} ${e.qualified}` });

blocks.sort((a, b) => (a.file < b.file ? -1 : a.file > b.file ? 1 : a.first - b.first));
```
