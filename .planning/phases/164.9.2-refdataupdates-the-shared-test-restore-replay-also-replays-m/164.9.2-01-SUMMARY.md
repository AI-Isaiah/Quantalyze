## Deviations from Plan

**1. [Rule 1 - Bug] `AND (`, `OR (` and `NOT (` were read as function calls**
- **Found during:** Task 2, a regex sanity probe.
- **Issue:** the plan's call ban ("any `identifier(` except `IN (` and `now(`") refuses `WHERE a = 1 AND (b = 2 OR c = 3)` as a call to `AND(`. That statement is literal. The rule would have forced it into a `decline:` line, so a decline would hide a replayable effect, the thing C5's decline-on-literal refusal exists to prevent.
- **Fix:** `updateLiteralCheck` also admits the boolean keywords AND, OR and NOT before a parenthesis. They are reserved words in PostgreSQL and never calls. `current_setting(`, `pg_notify (` and the rest are still refused (probed). No corpus statement changes classification: the census is unchanged.
- **Files:** scripts/extract-reference-inserts.mjs. **Commit:** `337f8e0ea`.

**2. [Rule 2 - Correctness] An allowlist of C5 lines only is refused**
- The extractor's empty-allowlist refusal now also fires when every line is a C5 line. This mirrors CONTEXT W6 for the restore side: such a file replays nothing the count floor can measure. **Commit:** `9d5fc8ef7`.

**3. Emit's second stderr line.** The plan asked for "a separate stderr line" for the update count. It reads `extract-reference-inserts: emitted <u> C5 update statement(s) over <t> table(s) from <n> update: line(s); <d> decline: line(s) emit nothing.` The existing INSERT line is byte-stable. No consumer parses stderr, checked by grep of the restore script and `scripts/local-stack/run.sh`.

**4. Audit output layout.** The indented C5 detail lines (`C5 lines:` plus a per-table `replayed / declined` row) print ABOVE the `audit OK:` line. The C5 census line follows `audit OK:` directly, so "after it exactly one line" holds literally. The INSERT census rows and the `audit OK:` line itself are unchanged.
