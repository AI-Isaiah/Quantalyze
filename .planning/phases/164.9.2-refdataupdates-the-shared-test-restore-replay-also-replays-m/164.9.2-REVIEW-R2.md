## Critical Issues

### CR-01: the WR-03 fix admits `set(…)` as a grammar construct, but `SET` is an unreserved keyword, so `set(…)` anywhere in the statement is a real function call replayed on shared TEST

**File:** `scripts/extract-reference-inserts.mjs`, `C5_ALLOWED_CALLS` (the `"SET"` member) as used by
`updateLiteralCheck` (the `if (callNext) { if (C5_ALLOWED_CALLS.has(up)) continue; …` branch). The member was introduced by commit `e0da7509e`.

**Issue:** `SET` was added so that the multi-column head `SET (a, b) = (…)` is admitted. The check is
position-blind, though, so `set(` is admitted at ANY token position. `SET` is an unreserved keyword in
PostgreSQL, not a reserved one, so it is a legal function name. `ROW`, `COALESCE`, `NULLIF`,
`GREATEST` and `LEAST` are column-name keywords and can never name a function, so they are safe. Every
other member is either reserved or `NOW`. Measured with `matchUpdate` against `public.profiles`, both
of these are `LITERAL`:

```
UPDATE public.profiles SET x = set(1) WHERE id = 1;
UPDATE public.profiles SET x = 1 WHERE id = 1 AND set(2) IS NOT NULL;
```

An end-to-end `--audit` over a scratch fixture with an `update:1` line for
`UPDATE fx_ref SET label = set('x') WHERE id = 1;` prints `audit C5 OK: 1 update statement(s) …
replayed`. MEASURED on a pg-lane cluster: after `CREATE FUNCTION public.set(text) … INSERT INTO
public.side_effects …`, both statements above ran the function (`side_effects=2`) under
`search_path = public, pg_catalog`, which is the replay's own bracket.

**Failure scenario:** this is the CR-01 shape from round 1 again, now spelled without quotes. A
migration defines any function named `set`, and a later literal-looking UPDATE of a replayed table
calls it. The audit classifies that UPDATE as literal and advises adding the `update:` line. The next
`mode=restore` then runs the function inside the transaction that COMMITs on shared TEST. This is
latent: there are 0 corpus instances, and `supabase/schema/baseline.sql` defines no `public.set`
(measured). It is still a hole in the allowlist whose whole purpose, per its own header, is to make an
admitted call impossible to smuggle.

**Fix:** admit `SET (` only in head position, never as a general call:

```js
// the SET token of `UPDATE [ONLY] t [[AS] a] SET (…)` — the first word SET at
// paren depth 0 — is the multi-column head; any other `set(` is a call
if (up === "SET" && callNext) {
  if (!seenHeadSet && depth === 0) { seenHeadSet = true; continue; }
  return `makes the non-literal call \`${t.v}(\` — …`;
}
```

Track `depth` over `(`/`)` tokens. Then remove `"SET"` from `C5_ALLOWED_CALLS`. Add a
`c5-update-set-call` red leg (`SET label = set('x')`) whose green twin keeps
`SET (label, n) = ('v', 1)`. Raise `SELF_TEST_KINDS_FLOOR` to the measured count, and add the id to
`REQUIRED_KINDS`.

## Warnings

### WR-01: a DO body now launders what a top-level statement cannot do. A DO-body DELETE/TRUNCATE/MERGE/COPY is declinable, and so is a literal DO-body UPDATE of a replayed row, which makes "a decline can never hide a replayable effect" false

**File:** `scripts/extract-reference-inserts.mjs`: `c5Verdict` (the `nonLit` array, which folds
`m.doWrites` in with `nonLiteral: true`), `matchDoBodyWrites` (heads UPDATE, DELETE, TRUNCATE,
MERGE, upsert and COPY), and the self-test kind `c5-audit-do-body-write`.
`scripts/restore-test-refdata-allowlist.txt`: the C5 criterion block's "so a decline can never hide a
replayable effect".

**Issue:** there are two asymmetries, both introduced by `436da37a9`.

1. At top level, a DELETE, TRUNCATE, MERGE or `COPY … FROM` of a replayed table is a HARD refusal
   (`matchOtherDml`: "no allowlist line can account for it"). CONTEXT's deferred section rests on
   that ("`--audit` refuses one if it appears"). The same statement wrapped in
   `DO $$ BEGIN … END $$;` becomes a `doWrites` hit and is cleared by a `decline:1` line with any
   reason text.
2. `c5-decline-literal` protects the top-level invariant: a literal UPDATE under a `decline:` line is
   refused. A DO-body write is never literal-checked, though. The green leg of `c5-audit-do-body-write`
   pins the exact pattern the invariant exists to forbid: `UPDATE fx_ref SET label = 'v' WHERE id = 1`
   runs inside a DO body on the row the fixture's INSERT seeded (id 1), and a `decline:1` line makes it
   green. A restore then commits id 1 as `'seed'` while PROD holds `'v'`, and the census reads
   `1 declined … 0 unaccounted`.

The four real declines are sound (see Summary). Now, though, the ONLY thing between a DO-body backfill
of a replayed row and a silently wrong restore is a reviewer's prose. The refusal's second remedy
("or move the write to a top-level literal UPDATE") is not available for an applied migration.

**Fix:**
- Point the self-test fixture's DO-body write at a row the replay did not write (id 2, say), so the
  green leg no longer pins a hidden replayable effect.
- Correct the allowlist sentence, with a date. It should say that a decline over a DO-body write is a
  REVIEW judgement that the write reaches no replayed row, and that no mechanism checks it.
- Either hard-refuse DO-body DELETE/TRUNCATE/MERGE/COPY to match their top-level twins, or give
  DO-body writes their own line kind (e.g. `do-decline:`). The census can then report them apart from
  the D-02 non-literal declines, and the refusal text can stop offering an impossible remedy. The b5b
  probe-row DELETEs need a way through, so the second option is the one that keeps today's corpus
  green.

### WR-02: a top-level upsert on a replayed table is refused with no way to account for it, while the identical upsert inside a DO body is declinable

**File:** `scripts/extract-reference-inserts.mjs`: `modeAudit` (the INSERT loop's unlisted branch,
`for (const r of m.rejected.filter((x) => x.upsert))`), and `c5Verdict` (whose `nonLit` does not
include upsert rejections).

**Issue:** measured on a scratch fixture. `INSERT INTO fx_ref (id, label) SELECT id, 'x' FROM other
ON CONFLICT (id) DO UPDATE SET label = EXCLUDED.label;` sits in a file with a `decline:1` line for
`public.fx_ref`, and it produces TWO refusals. The first is the upsert refusal. The second is
`the C5 line pins decline:1 … but 0 were measured`. No allowlist line of any kind can clear it: an
INSERT line refuses the rejected statement, and `decline:` does not count it. The refusal text says
"classify it by hand at review", but there is nowhere to record that classification. Meanwhile
`matchDoBodyWrites` lists `INSERT … ON CONFLICT DO UPDATE` among the DO-body writes a `decline:` line
DOES clear.

**Failure scenario:** a future migration backfills profiles the idiomatic way
(`INSERT … SELECT … FROM auth.users ON CONFLICT (id) DO UPDATE`). `sql-gate-lint` goes red, and the
only way out is editing the extractor. That is the pressure that produces a relaxed classifier.

**Fix:** in the C5 loop, fold the pair's top-level upsert rejections into `nonLit` (as
`{ line, nonLiteral: true, reason: "…ON CONFLICT DO UPDATE…" }`) so that a `decline:` line accounts
for them the way it accounts for the DO-body twin. Drop the separate unlisted-branch refusal, or keep
it only for pairs with no C5 line. If a hard refusal is intended, record that in CONTEXT beside
DELETE/TRUNCATE/MERGE, and make the DO-body path consistent with it.

### WR-03: the reason given for refusing `lower()` applies equally to the admitted `now()`. Under the replay's `search_path = public, pg_catalog`, a `public.now()` shadows `pg_catalog.now()`

**File:** `scripts/extract-reference-inserts.mjs`, the `C5_ALLOWED_CALLS` doc comment ("lower() /
upper() are deliberately NOT here … a `public.lower` would win"). `scripts/restore-test-from-baseline.sh`,
`build_transaction`, `SET LOCAL search_path = public, pg_catalog;` ahead of the `refdata.sql` cat.

**Issue:** `now` is not a keyword. It resolves on the search_path exactly as `lower` does. MEASURED on a
pg-lane cluster: with `public.now()` defined to insert a row, `UPDATE fx_ref SET seen = now()` inside
`SET LOCAL search_path = public, pg_catalog` ran the public function (`now_shadow_side_effects=1`).
The migration itself ran in PROD under the default path, where `pg_catalog` is searched implicitly
FIRST, so the replay can resolve a name differently from the run it reproduces. The same holds for
C2's `now()` / `gen_random_uuid()` and for every operator spelling C5 admits. This is latent:
`baseline.sql` defines no `public.now` and no `CREATE OPERATOR` (measured). The fix round reasoned
about exactly this lookup and stopped halfway.

**Fix:** change the replay bracket to `SET LOCAL search_path = pg_catalog, public;`. That is PROD's
effective order: tables still resolve to `public`, and built-ins can no longer be shadowed. Move the
arm that greps for the bracket line (arm 23's search_path leg) in the same commit. If the bracket must
stay as it is, correct the `C5_ALLOWED_CALLS` comment so it states that `now()` carries the same
exposure.

### WR-04: the WR-03 fix blanks `IS [NOT] DISTINCT FROM` to spaces, so `col IS DISTINCT FROM (…)` now reads as the call `col(`. A literal UPDATE is refused under a false reason, and the audit tells the reviewer the classifier is wrong

**File:** `scripts/extract-reference-inserts.mjs`: `C5_BLANKED_PHRASES` and its use at the top of
`updateLiteralCheck` (`text.replace(re, (p) => " ".repeat(p.length))`).

**Issue:** after the phrase is blanked, the column before it and the `(` after it are adjacent tokens.
Measured: `UPDATE fx_ref SET label = 'v' WHERE label IS DISTINCT FROM ('v');` is refused as
`makes the non-literal call \`label(\``. With no C5 line, the audit then prints the new WR-03 text:
"if this statement is literal, the classifier is wrong: fix the classifier". This does not make
anything unsafe, since it fails closed. It is, however, the over-refusal class WR-03 set out to close,
with a message naming a call the statement does not make. The same happens for `IS NOT DISTINCT FROM`
before any parenthesised operand, such as `(1)` or a row value `(1, 2)`.

**Fix:** replace the phrase with a length-preserving OPERATOR token rather than spaces, so the walk
sees `col = (…)`:

```js
text = text.replace(re, (p) => "=".padEnd(p.length, " "));
```

Add `WHERE label IS DISTINCT FROM ('v')` to the `c5-update-nonliteral` green leg.

## Info

### IN-01: `audit C5 FAILED: 0 unaccounted` is printed for failures that are not C5 at all, and C5 membership refusals are not tallied

**File:** `scripts/extract-reference-inserts.mjs`, `modeAudit` (the `if (bad) { io.err.push(\`… audit C5 FAILED: ${c5Unaccounted} …\`) }` block, and the membership loop over `pairs.values()`, which sets `bad` without `c5Unaccounted++`)

**Issue:** measured on scratch fixtures. An INSERT pin drift prints `audit C5 FAILED: 0 unaccounted
C5 refusal(s)`. So does a `decline:` line naming a table no INSERT entry fills, which is a C5
refusal. Anyone triaging a red `sql-gate-lint` reads that C5 failed and counted zero, which is
misleading on both counts.
**Fix:** tally the membership refusals, and print the `audit C5 FAILED:` line only when
`c5Unaccounted > 0`. Otherwise print a neutral `audit FAILED:` line.

### IN-02: the `C5 scope:` NOT-traced list is incomplete. A plain INSERT inside a DO body is traced by neither class

**File:** `scripts/extract-reference-inserts.mjs`, `modeAudit` (the `C5 scope:` census line);
`scripts/restore-test-refdata-allowlist.txt`, limitation 2's WR-02 correction.

**Issue:** measured on a scratch fixture. `DO $$ BEGIN INSERT INTO fx_ref … ; END $$;` passes
`--audit` with `0 unaccounted` and no mention anywhere. The INSERT class looks at top level only, and
C5 lists only the upsert form. The scope line names "a function called at top level, and dynamic
SQL" as the untraced shapes, so a reader takes everything else as covered. `CALL` of a procedure is
also untraced, and it is only loosely covered by "a function".
**Fix:** add "a plain INSERT inside a DO body, and CALL" to the NOT-traced clause, on the census line
and in the allowlist.

### IN-03: two of the new decline reasons argue their case wrongly, although both conclusions hold

**File:** `scripts/restore-test-refdata-allowlist.txt`, the `decline:1` lines for
`20260407164606_perfect_match.sql` and `20260713120000_cleanup_abandoned_wizard_drafts.sql`

**Issue:**
- perfect_match: "the teaser sentinel, which is not an admin, so it reaches no row". The DO body
  selects by `auth.users` email against an app setting, not by current admin status, and "not an
  admin" is circular for an UPDATE that sets `is_admin`. The real reason is ordering: `20260407164606`
  runs before `20260515095804` inserts the sentinel, so the UPDATE cannot reach it.
- cleanup_abandoned_wizard_drafts: "its success sentinel (:182)". Line 182 is a comment. The sentinel
  is the block's `RAISE EXCEPTION 'SELFVERIFY_OK' USING ERRCODE = 'ZZ999'` and its
  `WHEN SQLSTATE 'ZZ999'` handler.

**Fix:** restate the first as an ordering argument. Cite the second by symbol (`SELFVERIFY_OK` /
`ZZ999`), not by line.

### IN-04: the `matchUpdate` comment claims nine DO-body writes on `auth.users`; the measurement is eight

**File:** `scripts/extract-reference-inserts.mjs`, `matchUpdate` (the "(Measured 2026-09-25: the nine
DO-body writes on auth.users …)" comment)

**Issue:** `matchDoBodyWrites(prepareFile(src), "auth.users")` over the whole corpus returns 8 hits
across 7 files. All 8 are DELETEs keyed by a probe variable, so the conclusion holds and only the
count is wrong. REVIEW-FIX.md repeats the same "9".

### IN-05: `DEFAULT` and `::` casts are admitted, but both can run catalogue code the statement text does not show

**File:** `scripts/extract-reference-inserts.mjs`: `C5_ADMITTED_RESERVED` (`DEFAULT`) and
`skipC5CastType`

**Issue:** `SET col = DEFAULT` evaluates the column's default expression in the RESTORE session. That
is the same "replays the restore's value, not PROD's" concern that led the fix to refuse the niladic
session functions. A default of `auth.uid()` or `current_setting(…)` would replay a session-dependent
value. `col::sometype` can also invoke a `CREATE CAST … WITH FUNCTION`. Neither applies today: the
non-constant defaults on `profiles` and `strategies` are `now()` and `gen_random_uuid()`, and
`baseline.sql` has no `CREATE CAST` (both measured). C2 admits both as well.
**Fix:** add one sentence to the C5 criterion block, beside the IN-03 trigger sentence: an `update:`
line whose statement uses DEFAULT or casts to a non-built-in type is a review decision.
