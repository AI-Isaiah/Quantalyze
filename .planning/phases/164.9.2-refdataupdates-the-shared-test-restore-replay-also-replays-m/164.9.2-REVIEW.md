## Summary

Scope: the C5 class in `scripts/extract-reference-inserts.mjs` (`parseAllowlist`, `updateLiteralCheck`,
`matchUpdate`, `matchOtherDml`, `c5Verdict`, `modeEmit`, `modeAudit`, the 20 `c5-*` self-test kinds), the
restore script's C5 note, `REFDATA_ENTRY_N` and the RAISE correction, the 6 C5 allowlist lines, both
workflows' census steps, and the four vitest files.

Measured at HEAD `838312df3`. No database was touched; every probe imported the extractor's exported
functions and ran them over in-memory strings:

- `--self-test` prints `39 kinds, red+green each.` and exits 0. `--audit` prints the `audit OK:` and
  `audit C5 OK: 6 … replayed; 2 declined …; 0 unaccounted.` lines and exits 0.
- **Ordering is sound.** `modeEmit` sorts every block on (basename, `first`). All 274 migration basenames
  have a 14-digit prefix, so plain string order is the order the migrations ran. The emitted INSERT half
  is byte-stable, and `-- refdata-expect:` stays INSERT-only.
- **The restore transaction is sound.** `refdata.sql` is appended with `cat`, not through an unquoted
  heredoc, so a `$` or backtick in a replayed literal is not expanded. The replayed UPDATEs run under the
  `public, pg_catalog` search_path bracket, inside the same transaction as the INSERTs and ahead of the
  unchanged gate. The only triggers on `public.profiles` and `public.strategies` are BEFORE guards gated on
  `current_user` (`reject_sentinel_writes`, `prevent_profile_privileged_change`, …), and they admit
  `postgres`. No AFTER trigger fires a side effect. D-01 holds: only the RAISE's explanatory clause and
  comments changed.
- **`auth.*` cannot reach replay through an allowlist line.** `parseAllowlist` refuses every non-public C5
  line. `modeAudit` iterates `tables`, which includes `auth.users`, so a top-level UPDATE there is refused
  (verified via `c5-audit-auth-update` and `c5-audit-auth-nonliteral-update`).
- **Bounded captures.** Every capture in both census steps, and in the data-dependence step, now carries
  `|| <name>=$?` and an rc>1 branch. The wiring harness executes both copies under `bash -e`, with an
  `unbind` calibration for each.

The core defect is in `updateLiteralCheck`, the C5 literal classifier. Its call ban can be bypassed by a
quoted identifier. The same text the audit reads as "literal, add an `update:` line" can therefore carry
a side-effecting function call, and that call would run inside a COMMITting transaction on shared TEST.
The INSERT side's `literalCheck` is not affected. Beyond that, the audit's `0 unaccounted` claim has
three silent blind spots, over-broad refusals push literal UPDATEs into `decline:`, and one restore arm
carries a false sentence about what it falsifies.

## Critical Issues

### CR-01: `updateLiteralCheck` admits a quoted-identifier function call, so a side-effecting UPDATE classifies as literal and gets replayed on shared TEST

**File:** `scripts/extract-reference-inserts.mjs`, `updateLiteralCheck`, the `call` regex `/([A-Za-z_][A-Za-z0-9_]*)[\t\n ]*\(/g`
**Issue:** `maskSql` deliberately keeps quoted identifiers ("Quoted identifiers are CODE, not data"). The
call ban only matches an identifier followed directly by whitespace or `(`. In `"pg_notify"(`, the
character before `(` is `"`, so the regex never matches and the call passes. Measured with the exported
`prepareFile` + `matchUpdate` against `public.profiles` (each shows `ok 1, rejected []`):

```
UPDATE public.profiles SET x = "pg_notify"('c','p') WHERE id = 1;
UPDATE public.profiles SET x = "net"."http_post"('u') WHERE id = 1;
UPDATE public.profiles SET x = 'a' WHERE id = 1 AND ("pg_sleep"(1) IS NOT NULL);
```

**Failure scenario:** a future migration adds a top-level UPDATE of a replayed table with a
quoted-name call, such as `"net"."http_post"(…)` or a quoted SECURITY DEFINER helper. `--audit` classifies
it as literal and refuses with *"NO C5 allowlist line; add an update: line for this top-level literal
UPDATE"*. That message tells the reviewer to add exactly the line that replays it. The next `mode=restore`
then runs the call inside the transaction that COMMITs on shared TEST. The pg_net request fires on
commit, and it cannot be rolled back. This breaks C5's stated invariant ("no call but `now()`") and the
phase focus ("could a non-literal … slip into replay"). The equivalent INSERT-side check,
`literalCheck`, is not affected: it rejects every bare token in the tuple, quoted or not. It is latent
(0 corpus instances today, measured), but it is a hole in the gate that stands between a migration and
a write to a shared database.
**Fix:** make the call ban quote-aware, and give the shape its own self-test leg:
```js
// a call is <ident>( or "<ident>"( — optionally schema-qualified either way
const call = /"?([A-Za-z_][A-Za-z0-9_$]*)"?[\t\n ]*\(/g;
```
Also refuse any `"` immediately followed by `(`, and any `U&"` identifier, in the masked span. That is
belt and braces: the quoted spelling has no legitimate use in a literal C5 UPDATE. Add a
`c5-update-quoted-call` red leg (`SET a = "pg_notify"('c','p')`) and a green twin, raise
`SELF_TEST_KINDS_FLOOR` to the measured count, and add the id to `REQUIRED_KINDS`.

## Warnings

### WR-01: `updateLiteralCheck` also admits `IN (TABLE other)` and the SQL-standard niladic session functions

**File:** `scripts/extract-reference-inserts.mjs`, `updateLiteralCheck` (`notCalls` admits `IN`, and the banned-word list is `FROM|USING|SELECT|RETURNING|WITH`)
**Issue:** measured as `ok 1`:
- `UPDATE public.profiles SET x = 1 WHERE id IN (TABLE other_ids);`. `TABLE t` is a sub-query spelled
  without SELECT or FROM, and `IN (` is exempt from the call ban. The UPDATE's effect then depends on
  another table's contents, which is the "reads existing rows" concern C5 exists to exclude.
- `UPDATE public.profiles SET x = current_user WHERE id = 1;`. `current_user`, `session_user`, `user`,
  `current_role`, `current_schema` and `current_catalog` take no parentheses. They are read as "column
  references" and replay a session-dependent value. The restore's role is only an assumption (D-A1).

**Failure scenario:** a migration of either shape reaches `update:` through the same audit instruction
as CR-01. The restore then replays a value PROD never held.
**Fix:** add `TABLE` and `VALUES` to the banned-word regex, as whole words in the masked text. Refuse the
niladic set by name:
`/\b(current_user|session_user|current_role|current_schema|current_catalog|user|system_user)\b/i`.
Add a red leg for each.

### WR-02: the audit prints `0 unaccounted` over three shapes it never sees

**File:** `scripts/extract-reference-inserts.mjs`, `modeAudit` (the C5 loop and the INSERT loop's `if (m.ok.length === 0) continue; // limitation 2`), `updateHeadRe` / `matchOtherDml` / `headRe` (`[\t\n ]` separators)
**Issue:** the allowlist header (C5 block) and the census line claim that EVERY top-level mutation of a
replayed table is accounted for. Three shapes pass in silence:
1. **A literal upsert in an unlisted file.** `INSERT … VALUES … ON CONFLICT (id) DO UPDATE SET …` into a
   replayed table is rejected by `literalCheck` (not DO NOTHING). The pair has no INSERT line, so the
   audit takes the `m.ok.length === 0 → continue` branch. It is an UPDATE effect on a replayed row, and
   neither the INSERT class nor C5 names it. Measured 0 corpus instances today.
2. **A `DO $$ … UPDATE public.profiles … $$;` block run at migration time.** It lands in `m.body` and is
   dropped. Today all 30 body UPDATEs on replayed tables sit inside `CREATE FUNCTION` bodies (measured),
   so none runs at migration time. The classifier cannot tell the two apart.
3. **A head separated by `\r` or `\f`.** `UPDATE\r\npublic.profiles SET …` and `DELETE\r\nFROM fx_ref;`
   measured `ok 0, rejected 0`, and `matchOtherDml` returned `[]`. The statement vanishes from both C5
   and the DML refusal. There are no CRs in the corpus today, and the INSERT side's `headRe` shares the
   blind spot.

**Failure scenario:** a future migration of shape 1 or 2 changes a replayed row in PROD. The restore
does not reproduce it, the census still reads `0 unaccounted`, and the wrong-state leg checks one
column of one row, so it will not notice.
**Fix:**
- (1) In `modeAudit`, refuse by name any `rejected` INSERT hit on a replayed table whose reason is the
  ON CONFLICT action, even when the pair is unlisted.
- (2) Distinguish `DO` bodies from `CREATE FUNCTION` bodies in `dollarBodyRanges` (the text before the
  tag). Refuse a top-level `DO` whose body writes a replayed table, or require a `decline:` line for it.
- (3) Use `\s` (or `[\t\n\r\f ]`) in every head regex, on both sides, and add a CRLF red leg.

If any of these is judged out of scope, make the census line or the allowlist header say so, rather
than "0 unaccounted".

### WR-03: the literal-check over-refusals push replayable UPDATEs into `decline:`, which is the effect D-02 forbids

**File:** `scripts/extract-reference-inserts.mjs`, `updateLiteralCheck` (`\bFROM\b`, and every `identifier(` except IN/AND/OR/NOT/now), `c5Verdict` (the `classify by hand: decline it with a reason` branch)
**Issue:** these statements are refused as non-literal (measured), and every one is literal:
- `WHERE status IS DISTINCT FROM 'x'`: the `FROM` token.
- `WHERE id = ANY('{1}')`: the `ANY(` call.
- `SET (a, b) = (1, 2)`: read as a call to `SET(`.
- `ROW(…)`, `coalesce(b, 1)` and `lower(b)`: read as calls.

For an unlisted one, `c5Verdict` tells the reviewer to *"decline it with a reason"*. A `decline:` line
is then accepted, because `c5-decline-literal` only fires when `updateLiteralCheck` itself says literal.
**Failure scenario:** a replayable reference UPDATE (the `IS DISTINCT FROM` idempotence idiom is common
in this repo's migrations) is declined on the tool's own advice. The restore omits it, and nothing
checks that column. This is the "replayable one declined" path the review brief asked about. It is not
silent, because a human writes the line, but the tool sends the human the wrong way.
**Fix:** strip `IS [NOT] DISTINCT FROM` before the word test. Admit `ANY`/`ALL` over a literal array,
the multi-column `SET (…) =` head, and a small allow-set of pure immutable functions (`lower`, `upper`,
`coalesce`, `nullif`), each with a green leg. In the unlisted non-literal branch, change the message so
it no longer recommends a decline outright: "declines are for joins and sub-selects only; if this is
literal, the classifier is wrong — fix it, do not decline".

### WR-04: arm 33 and its fixtures state a falsifier they do not have: "only a (basename, offset) sort" orders the UPDATE after its INSERT

**File:** `scripts/restore-test-from-baseline.sh`, `arm_c5_update_green` header comment; `scripts/restore-test-from-baseline-fixtures/migrations/20260103000000_fixture_c.sql` (the 164.9.2 C5 comment above the UPDATE); `scripts/restore-test-from-baseline-fixtures/refdata-allowlist.txt` (the `update:1` line's field 4)
**Issue:** each of the three says the `update:1` line sits above the INSERT line, "so only the
extractor's (basename, offset) sort replays it after its INSERT". Plan 03's own SUMMARY (Deviation 1)
measured this as false. `modeEmit` pushes every INSERT block before every C5 block, so with the sort
line deleted the fixture still emits INSERT, INSERT, UPDATE, and arm 33 stays green (`34/34`). Arm 33
catches only emission in allowlist-line order. Sort removal is caught by the extractor's own
`c5-update-count-drift.green` ORDER leg and not by the restore self-test. This repo treats a false
sentence inside a gate as a defect (D-01's own rationale). The next reader will believe the restore
self-test pins the sort, and could delete the ORDER leg as redundant.
**Fix:** correct all three sentences, with a date, to what was measured: "arm 33 goes RED if blocks are
emitted in allowlist-line order; sort removal alone is caught by the extractor self-test's
`c5-update-count-drift.green` ORDER leg, not here". Keep the old wording as lineage.

## Info

### IN-01: the workflows' `0 unaccounted` regex term cannot fail against the real extractor

**File:** `.github/workflows/ci.yml` and `.github/workflows/test-restore-from-baseline.yml`, the audit census step's `c5_line` grep; `scripts/extract-reference-inserts.mjs` `modeAudit` (the literal `0 unaccounted.` in the census template)
**Issue:** the extractor refuses before it would ever print a non-zero count, and the census template
hardcodes `0`. So the `0 unaccounted\.$` term, and the wiring arm feeding `1 unaccounted`, test a line
the real tool cannot emit. It does no harm, but its evidential weight is nil, and WR-02 shows the "0"
itself is not guaranteed.
**Fix:** either compute the count and print it, or record in the step comment that the term is a format
pin and not a measurement.

### IN-02: an `update:` pair with a stray non-literal UPDATE refuses with the bare classifier reason

**File:** `scripts/extract-reference-inserts.mjs`, `c5Verdict`, the non-literal branch (`upd ? r.reason : …`)
**Issue:** when the pair has an `update:` line but no `decline:` line, the refusal is just the
classifier text ("carries the token FROM …"). It does not tell the reviewer that a `decline:` line for
the same pair is legal and required.
**Fix:** append "— add a decline: line for this (file, table) with the reason, beside the update: line".

### IN-03: C5's safety premise covers the statement text, not the target table's triggers

**File:** `scripts/restore-test-refdata-allowlist.txt`, the C5 criterion block ("such an UPDATE can reach only rows the replay itself wrote")
**Issue:** today this is true: the triggers on `public.profiles` and `public.strategies` are BEFORE guards
gated on `current_user` (measured in `supabase/schema/baseline.sql`). A future `update:` line on a
public table carrying an AFTER trigger that writes outside `public` (vault, cron, pg_net) would mutate
surviving shared-TEST state, and the criterion text says that cannot happen. The INSERT class has the
same premise.
**Fix:** add one sentence to the criterion: "an `update:` line on a table with an AFTER/INSTEAD OF
trigger, or a trigger function that writes outside public, is a review decision". Optionally add an
audit cross-check against the baseline's `CREATE TRIGGER … ON <table>` lines.

### IN-04: the TRUNCATE, MERGE and CTE-prefixed DELETE/MERGE heads in `matchOtherDml` have no self-test leg

**File:** `scripts/extract-reference-inserts.mjs`, `matchOtherDml`; `SELF_TEST_KINDS` entry `c5-audit-unlisted-delete`
**Issue:** only the DELETE head has a red leg (the plan 02 SUMMARY records this). I probed the other
three by hand, and each fires on its shape: `TRUNCATE TABLE a, fx_ref CASCADE`, `MERGE INTO fx_ref …`,
and `WITH d AS (DELETE FROM fx_ref RETURNING 1) SELECT 1`. A regression in any of them would still leave
the self-test green.
**Fix:** add `c5-audit-unlisted-truncate` / `-merge` / `-cte-delete` red+green kinds, and move both
ratchet layers from the measured run.
