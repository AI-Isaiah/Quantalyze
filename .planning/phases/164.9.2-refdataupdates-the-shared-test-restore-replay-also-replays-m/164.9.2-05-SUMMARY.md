### 2. [Process - disclosed] The lane's docker project collided with another worktree's lane, twice
- **What happened:** A lane from another worktree (164.6.7) was running at start (`supabase_*_quantalyze`, up from about 07:53 local), so this plan polled every 60 s. It cleared at 08:26.
  - The first `up` failed in the CLI's own `Initialising schema…` step (`error running container: exit 1`). The other worktree was starting its own `up` at the same moment.
  - The second `up` printed `supabase start is already running.` It **attached to the other worktree's freshly started stack** and loaded the baseline and reference data into it. That stack was then torn down by its owner seconds later, and a psql read against it was refused.
  - Nothing remote was touched; everything stayed on loopback. But this plan's writes likely broke the other worktree's lane run, and **its owner should re-run it.**
- **Root cause:** both worktrees derive the same docker `project_id` (`quantalyze`) from the tracked `supabase/config.toml`. `run.sh` has no cross-worktree lock, and `supabase start` treats an already-running stack of the same project as success.
- **What was done:** the idle check was tightened (no `supabase_*` container, including stopped ones, and no `local-stack/run.sh` process, held for 60 s). The recorded rehearsal also ran boot, reads, corpus and teardown in ONE process, so no teardown by anyone else could interleave. Its log shows no `already running` line: this plan started that stack itself.
- **Not fixed here (out of scope):** a lane lock or a per-worktree `project_id`. It is a lane-infrastructure change in `scripts/local-stack/run.sh`, which this plan does not own. It is recorded for the orchestrator to route.
