## Summary

Both residues reproduce on today's body, and both close in SQL alone. The Python ends are unchanged since 164.5.2's research: every honour write and every loud write still stamps `computation_error_source`/`computation_error_job_id` for its own job. D-05b holds, and `job_worker.py` needs no edit.

**D-04 as written (branch (b) only, keyed on `v_latest_job_id`) is NOT sufficient. D-05a's trigger fired, and the measurement overturns D-04's letter.** Measured on the pg-lane, three corners, prototype P1 = D-04 + D-05 exactly as locked:
1. **Later-created sibling failure (A4).** It does not self-heal. The row ends `failed` with `warned=t`, then shows `complete_with_warnings` on the next in-flight sibling.
2. **Sibling in flight when X is marked.** This corner is new, and it is the common one. Branch (a) fires at X's own mark and writes `complete_with_warnings` there and then. It also blanks the provenance, so branch (b) can never clear `warned` later.
3. **All-terminal-at-mark.** This is the only corner P1 closes.

Prototype P2 closes all three. It adds a membership aggregate (`array_agg(id) FILTER (WHERE NOT is_protected)`), and uses "the row's writer job is among the unprotected live failures" in branch (b)'s warned CASE and in three new branch-(a) arms. P2's end states match the Python LOUD path row-for-row on every scenario. SI-02 and the protected (unretracted) honour path are untouched.

One residual stays open in P2 and **cannot be closed in SQL alone**. If a sibling's bridge call lands between the Python honour write and X's own mark, it blanks the provenance first. That is **FOUNDER-OWNED** (see Open Questions).

**D-06: take the in-bridge lock.** Measured facts:
- Exactly two SQL callers exist, one strategy each.
- The DEFERRED Python call is a single-statement PostgREST transaction holding nothing.
- No claim RPC is touched, so there is **no sequencing blocker with Phase 164.9.3 CLAIMPAIR**.
- The lock converts a direct bridge call's wait from `transactionid` to `advisory` (namespace OID, objsubid 2).

It has one hard consequence, measured. If the new migration joins `test_mark_rpc_bridge_advisory_lock.sql`'s apply list, that gate's L1/L2 twins stop biting (`lockgate-L1twin-p3 rc=0`), which is a runner exit-1 defect. Keep that gate pinned, and prove the bridge lock in its own LANE-ONLY gate.

**Primary recommendation:** Ship ONE migration `20260927140000_sync_status_bridge_residues.sql` (164.5.2 house style). It is the 20260906 body plus the P3 delta below. The 20260906 `DO $verify$` is carried forward unchanged (measured to pass on P3), and the new anchors are added on comment-stripped text. Prove it with a new both-lanes residue gate and a new LANE-ONLY bridge-lock gate. Re-point the curated gate's seven twins. Move the drift test to a scan.

## Common Pitfalls

1. **The in-flight corner hides in the "all terminal" test shape.** A gate that marks X with nothing else in flight never reaches branch (a). W3–W5 exist for this. Seed a pending sibling.
2. **Lane kind FK.** `sync_trades` / `poll_positions` raise 23503 on the pg-lane (measured). Use registered kinds.
3. **`created_at` ties.** A later-created sibling needs an explicit timestamp offset.
4. **Twin layering.** Every body edit also neutralises its anchor in the same apply, or the apply aborts and the arm scores NO-IDENTITY.
5. **Shadowed L1/L2** if the lock gate's setup gains the new migration.
6. **Census pins in five files plus ci.yml.** `lint-sql-gates.test.ts`'s `scanned N file` is the historically missed one.
7. **Expected red** (`baseline-content-drift`, VAC-08) is not a regression. Do not allowlist it.

```sql
           computation_warned = CASE WHEN strategy_analytics.computation_error_source = 'writer' AND strategy_analytics.computation_error_job_id = ANY (v_unprotected_job_ids) THEN FALSE ELSE strategy_analytics.computation_warned END,
           …
           computing_started_at = CASE
             WHEN strategy_analytics.computation_error_source = 'writer' AND strategy_analytics.computation_error_job_id = ANY (v_unprotected_job_ids)
             THEN CASE WHEN strategy_analytics.computation_status IS DISTINCT FROM 'computing' THEN now() ELSE strategy_analytics.computing_started_at END
             WHEN strategy_analytics.computation_status = 'complete_with_warnings'
                  OR strategy_analytics.computation_warned
             THEN NULL
             WHEN v_refresh_keep AND strategy_analytics.computation_status = 'complete'
             THEN NULL
             WHEN strategy_analytics.computation_status IS DISTINCT FROM 'computing'
             THEN now()
             ELSE strategy_analytics.computing_started_at
           END,
-- branch (b) ON CONFLICT SET, after the two marker CASEs
           computation_warned = CASE WHEN strategy_analytics.computation_error_source = 'writer' AND strategy_analytics.computation_error_job_id = ANY (v_unprotected_job_ids) THEN FALSE ELSE strategy_analytics.computation_warned END,
```
All `ON CONFLICT … SET` expressions read the OLD row, so every predicate sees the provenance the writer left, even where the same statement NULLs it. The provenance trigger does not fire on these writes (the sentence is unchanged in (b); both markers change in (a)).
