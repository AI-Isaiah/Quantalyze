## Warnings

### WR-01: The stated hold guarantee is false through branch (c), and the booked limit names only the opposite direction

**File:** `CHANGELOG.md:48`, `supabase/migrations/20261003120000_sync_status_bridge_residues.sql:94-127` (header "A KEPT ROW HOLDS ITS DATE"), `supabase/migrations/20261003120000_sync_status_bridge_residues.sql:1028` (branch (c) `computed_at = now()`), `TODOS.md:1552-1570`

**Issue:** The CHANGELOG says the hold means "the FreshnessChip and the PDF vintage never show a
date fresher than the last real compute". The migration header and the hold-CASE comment say the
columns are held "because nothing was computed". The mechanism holds only in branch (a).

Branch (c) still writes `computed_at = now()` unconditionally. On a `complete_with_warnings` row
it keeps the status (`WHEN computation_status = 'complete_with_warnings' OR computation_warned
THEN 'complete_with_warnings'`).

So suppose an unrelated strategy-scoped job finishes `done` with nothing else in flight. Examples
are the cron `sync_trades` poller the body's own CR-01 comment names, or a `process_key_long`.
That job's mark takes branch (c) and re-stamps `computed_at` on the warned cohort's published row,
although nothing was recomputed.

The code matches the founder decision literally, since that decision is scoped to branch (a)'s
keep arms. But the ledgers state a guarantee the code does not deliver. The booked
`[164.5.2.1-COMPUTED-AT-RUNNER-STAMP]` covers only the LAG direction (a real recompute held stale).
It omits this FRESH-WITHOUT-COMPUTE direction. The same runner-side stamp that fixes the lag would
fix this, provided the bridge stops stamping in (c).

K2 seeds a pending job and makes a direct call, so no arm exercises the (c) path.

**Fix:** Do not change the code in this phase; branch (c) is outside the founder's decision.
Correct the claims and widen the booked limit:
- In `CHANGELOG.md:48`, replace "never show a date fresher than the last real compute" with
  "no longer advance on a row branch (a) keeps; branch (c) still stamps `now()` when the last
  in-flight job of ANY kind finishes".
- In the migration header's STATED LIMIT paragraph, add the second direction in one sentence:
  branch (c) re-stamps `computed_at` on a `complete_with_warnings` row when an unrelated job is
  the last to finish.
- In `TODOS.md` `[164.5.2.1-COMPUTED-AT-RUNNER-STAMP]`, add the same direction under **What
  happens**. Extend **Closed when** so that the bridge no longer stamps `computed_at` in branch (c)
  once the runner owns the stamp. Also add a test that fails on an unrelated job's (c) re-stamp.

### WR-02: Residue-gate arms W5 and R5 are vacuous on the `sql-tests` lane, because the stamp trigger rescues the mutated code there

**File:** `supabase/tests/test_sync_status_bridge_residues.sql:158` (`RED-UNDER-SETUP`, no `20260803120000`), `:503` (W5 twin), `:927-980` (R5 and its twin)

**Issue:** The gate runs on both lanes (D-08). The `RED-UNDER-SETUP` apply list omits
`20260803120000`, so the pg-lane has no `strategy_analytics_stamp_computing_started` trigger. The
`sql-tests` local stack does have it: `supabase/schema/baseline.sql:14093`, `BEFORE UPDATE ... FOR
EACH ROW`. That trigger stamps `now()` on any UPDATE that leaves a `computing` row unstamped
(arm b), and clears the stamp on every non-`computing` row (arm d).

On `sql-tests`, then:
- **W5:** delete the membership arm of the stamp CASE. Control falls to the warned arm (`THEN
  NULL`). The trigger re-stamps the `computing` row, and W5 stays GREEN.
- **R5:** delete the keep arm of the stamp CASE. The row resolves `complete`, so the trigger clears
  the stamp, and R5 stays GREEN.

Both twins bite only on the pg-lane. In production the bridge's two new stamp arms are
defense-in-depth behind the trigger. A future regression in them would be caught only by
`sql-mutation`, never by the lane that runs the real schema. The gate header does not say so.

**Fix:** Pick one of these.
- (a) Add `supabase/migrations/20260803120000_<stamp-trigger>.sql` to the residue gate's
  `RED-UNDER-SETUP`. The pg-lane then matches production. Re-measure: both twins should stop
  biting, which proves the arms redundant. Then either drop the two stamp-arm twins, re-baselining
  the floors by measurement, or re-target W5/R5 at the trigger.
- (b) Keep the arms and add a header note naming the asymmetry: "W5/R5 measure the bridge's own
  stamp CASE. On `sql-tests` the 20260803120000 trigger produces the same end state, so these two
  arms can only go RED on the pg-lane."

## Info

### IN-01: The lock-order header rests on a false premise (the conclusion survives)

**File:** `supabase/migrations/20261003120000_sync_status_bridge_residues.sql:144-146`

**Issue:** "no transaction holds that row (or a job row) while waiting on the advisory lock" is
false. Three lines earlier the same header records that the mark path takes "the job row (and,
for done, the fan-in children), then the advisory lock". So a mark DOES wait on the advisory lock
while it holds job rows.

There is still no cycle. The reason is the converse: no holder of the advisory lock ever waits on
a job row. The bridge only `SELECT`s `compute_jobs`, and the DEFERRED path holds nothing else.

**Fix:** Reword the premise: "no transaction that holds the advisory lock then waits on a job row
(the bridge only reads compute_jobs), and nothing holds the strategy_analytics row while waiting on
the advisory lock, so there is no cycle."

### IN-02: The mark RPCs' own lock lines are now redundant

**File:** `supabase/schema/functions/mark_compute_job_done.sql:103`, `supabase/schema/functions/mark_compute_job_failed.sql:100`

**Issue:** Each RPC takes the lock immediately before `PERFORM sync_strategy_analytics_status(...)`.
The bridge's first statement after its NULL guard is the same lock. The serialization point is
therefore identical, and the RPC lines add nothing. This is also why the 164.5.2 gate's L1/L2
twins stop biting with this migration applied (recorded in `test_mark_rpc_bridge_advisory_lock.sql:98-106`).

It is not a defect. It is a single source of truth that is now duplicated, and the next re-base
of either RPC may "simplify" one copy without knowing which one is load-bearing.

**Fix:** Pick one of these.
- Name the redundancy in the migration header's LOCK ORDER paragraph. Book the removal of the RPC
  lines for whichever phase next re-bases the mark RPCs.
- Or keep both deliberately, and say so (belt-and-braces against a future bridge re-base that
  drops its lock).
