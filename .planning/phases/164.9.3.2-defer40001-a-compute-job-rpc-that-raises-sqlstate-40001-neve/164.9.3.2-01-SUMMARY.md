## Enqueue race-loss raise (`_enqueue_compute_job_internal`)

### A2: a deterministic non-converging shape. REFUTED (measured)

The plan expected A2's psql proof to raise SQLSTATE 40001. It does not. The shape cannot get past the function's entry guard or the table's CHECKs. Measured in psql inside `BEGIN; ... ROLLBACK;` with `VERBOSITY verbose`:
- A row carrying both a strategy id and an api key id with kind `poll_allocator_positions`: `ERROR: 23514 ... violates check constraint "compute_jobs_kind_target_coherence"`.
- The same row with kind `poll_positions`, whose coherence arm does not name `api_key_id`: `ERROR: 23514 ... violates check constraint "compute_jobs_target_xor"`.
- The A2 call on the 10-param overload (`p_strategy_id` and `p_api_key_id` both set), with kinds `poll_allocator_positions` and `poll_positions`: both raise `ERROR: 22023: _enqueue_compute_job_internal: exactly one of p_strategy_id, p_portfolio_id, p_allocator_id, p_api_key_id must be non-null`. That is the guard `IF v_target_count <> 1 THEN`, which runs before the look-up, the INSERT and the race-loss RAISE.

Through PostgREST:
- `_enqueue_compute_job_internal` (10-param, both ids): A2 internal http=400 real=0.002928, body `code=22023`.
- `enqueue_compute_job` (both ids): A2 wrapper http=400 real=0.002546, body `code=22023`.

Why no reachable shape exists: every in-flight partial unique index is keyed on one target column plus `kind`, over the same three statuses (`pending`, `running`, `done_pending_children`). That holds for `compute_jobs_one_inflight_per_kind_strategy`, `_portfolio`, `_allocator` and `_api_key`, and for `compute_jobs_one_inflight_reconstruct_per_api_key` and `compute_jobs_one_inflight_refresh_equity_per_api_key`. The target-typed re-read after `ON CONFLICT DO NOTHING` uses the same target column, the same `kind` and the same status set. The strategy index additionally excludes `compute_intro_snapshot`, which only removes conflicts. So the INSERT can conflict only with a row the re-read also finds, unless that row leaves the in-flight statuses in between.

Which PostgREST-callable wrappers can forward both ids (decided by body text):
- `enqueue_compute_job`: NO. Its three branches each require exactly one target (`IF p_strategy_id IS NOT NULL AND p_allocator_id IS NULL AND p_api_key_id IS NULL`, and the allocator and api-key analogues). Otherwise it raises `enqueue_compute_job: exactly one of p_strategy_id, p_allocator_id, p_api_key_id must be non-null` (22023, measured above). The api-key branch forwards `NULL, NULL, ..., NULL, p_api_key_id`.
- `enqueue_compute_portfolio_job`: NO. It forwards `_enqueue_compute_job_internal(NULL, p_portfolio_id, 'compute_portfolio', ...)`, the 7-param overload, which has no api key parameter at all.
- `request_allocator_holdings_sync`: NO. It calls `enqueue_compute_job(p_strategy_id := NULL, ..., p_api_key_id := p_api_key_id)`.
- `update_allocator_mandates`: NO. It calls `enqueue_compute_job(p_strategy_id := NULL, p_kind := 'rescore_allocator', ...)`.
- The cron fan-outs: NO. They all go through `enqueue_compute_job` with one target. `enqueue_poll_allocator_positions_for_all_keys`, `enqueue_derive_broker_dailies_for_allocator_keys` and `enqueue_refresh_allocator_equity_for_all` pass `p_strategy_id := NULL` with an api key. `enqueue_ledger_refresh_for_strategies` and `enqueue_ledger_composite_refresh` pass a strategy id only, and they catch `serialization_failure` themselves.

### A1: convergence. The conflict-wait path converges (measured). The race-loss raise itself was NOT inducible (unmeasured, with reason)

The plan's A1 probe (start the A2 call, then move the competitor out of in-flight after 3 s) cannot run as written: A2 answers `400` in 3 ms, so there is no call left running. With a committed competitor, the optimistic look-up returns the competitor's id and never reaches the RAISE. A1 was therefore measured on the shape that actually reaches the conflict path:
- **A1-i, conflict wait.** A psql session INSERTs an in-flight `poll_positions` row for strategy S and holds the transaction open 5 s. One second in, PostgREST calls `_enqueue_compute_job_internal(S, poll_positions)`, and the call blocks on the conflict. Result: A1 conflict-wait http=200 real=4.009691, returning the competitor's id (match 1/1). It converged when the competitor committed.
- **A1-ii, race-window attempts (5 tries).** The competitor INSERTs in-flight, holds 3 s, COMMITs, then immediately runs `UPDATE ... status='done'` in a separate statement. All 5 tries returned `http=200` in about 2.0 s with the competitor's id (try 1: A1-ii http=200 real=2.007010). The db log counted 0 `enqueue race lost` lines on every try. The re-read beat the competitor's flip each time.

Verdict:
- The enqueue paths reachable through PostgREST converge in every shape measured.
- The race-loss RAISE needs the competitor to leave the in-flight statuses inside the window between the INSERT's conflict check and the re-read. Five attempts never hit that window, and its width is unmeasured. It could not be induced deterministically, so its PostgREST behaviour is UNMEASURED.
- Reasoned, not measured: if it fires, the PostgREST retry re-runs the whole call. By then the competitor is terminal, so the optimistic look-up finds nothing and the INSERT succeeds. This is the research's A1, and nothing measured here contradicts it.
