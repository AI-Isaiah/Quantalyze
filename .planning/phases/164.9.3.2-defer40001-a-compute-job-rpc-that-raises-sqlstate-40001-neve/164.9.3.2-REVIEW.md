## Warnings

### WR-01: "Deploy window safe in both directions" is false for the worker-first order, and four sites state it

**Files:**
- `analytics-service/main_worker.py:384-387`
- `analytics-service/services/job_worker.py:929-932`
- `analytics-service/tests/test_compute_jobs_fencing.py:184-187`, and the premise of the test at `:212-214`
- `CHANGELOG.md:14`

**Issue:** Each site says the message-literal fallback makes a preempted mark or defer classify "whichever of the migration apply and the worker deploy lands first". The CHANGELOG calls this covering "the deploy window in both directions". Only one direction holds:

- **SQL first, old worker:** the body raises 55006 and PostgREST answers once. The old classifier misses on the code (it checks `"40001"`) but matches the literal. This order is safe.
- **Worker first, old SQL:** the body still raises 40001. PostgREST 14 re-runs the call without bound, so no response, and no literal, ever reaches the new classifier. The call hangs exactly as it does today, until the client timeout. The literal branch never runs.

So the worker-first order is no regression, but it is not covered. The migration header says this correctly at lines 22-24: "a new worker meeting an old body sees exactly the old behaviour". The Python comments, the test docstring and the CHANGELOG contradict it. Prose like this is what an operator reads when deciding whether deploy order matters during a PROD auto-apply, so it should not overstate the guarantee. The unit test at `:212` is still a valid test of the classifier. Only its premise ("the literal fallback must classify it" in the deploy window) describes a response PostgREST 14 never delivers.

**Fix:** State the asymmetry at every site, for example:
```python
# The literal branch (b) covers ONE deploy order: migration first, old worker.
# A 55006 is answered once, and an old classifier matches it by the literal.
# The reverse order (new worker, old body) is NOT covered: the body still
# raises 40001, PostgREST 14 retries it without bound, and nothing reaches
# this classifier. That is the pre-fix behaviour, unchanged, until the
# migration applies.
```
Apply the same correction to `CHANGELOG.md:14`. Keep the test at `test_compute_jobs_fencing.py:212`, but reword its docstring: it covers a non-PostgREST transport, or a PostgREST >= 16 that answers a 40001 once.

## Info

### IN-01: Both classifiers treat a bare SQLSTATE 55006 as a fence preemption, with no literal required

**Files:** `analytics-service/main_worker.py:400-405`, `analytics-service/services/job_worker.py:936-937`
**Issue:**
- `code == "55006"` alone returns True. 55006 is a generic class (`object_in_use`) that Postgres itself raises, for example "is being used by active queries".
- None of these raises is reachable from the three RPCs or from `sync_strategy_analytics_status` today. The repo's other 55006 raisers are in `create_wizard_strategy_for_key`, `api_keys_account_identity` and `working_holder_rule_d18`, and none are on these paths.
- A future 55006 on a mark path would be swallowed silently as `LATE_MARK_IGNORED`. The job would then sit `running` until the watchdog reclaims it.
- This is narrower than the pre-phase rule, which accepted a bare 40001. The tests `test_apierror_with_code_55006_detected_without_literal` and `test_defer_lost_ownership_code_55006_alone_classifies` pin it as intended.

**Fix (optional hardening):** Classify on the literal alone: `return _PREEMPTED_MESSAGE_LITERAL in str(exc)`. Once the literal is required, the code check adds nothing, and transports that drop `.code` already rely on the literal. Alternatively, keep code-alone and record the reachability assumption next to the check.
