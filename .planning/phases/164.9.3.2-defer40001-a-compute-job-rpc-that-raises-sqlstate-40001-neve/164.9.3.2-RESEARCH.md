## Summary

PostgREST 14.x runs every request inside `hasql-transaction`'s retrying transaction. That transaction loops without bound when the server returns SQLSTATE `40001` (and `40P01`). Four RAISE sites in three compute-job RPCs raise `ERRCODE = 'serialization_failure'` on a condition that NEVER changes on retry: a claim-token mismatch. Through PostgREST, each of those calls busy-loops instead of failing. The 164.9.4 measurement saw ~27k re-runs in ~9 s on v14.5 and ~29k on v14.7, and on v14.7 the loop outlived the client disconnect. Upstream fixed this in PostgREST **16.0** (2026-08-07, #3673). No 14.x release carries the fix (14.18, 2026-09-10, does not).

The fix is a surgical errcode swap in the latest bodies of `defer_compute_job`, `mark_compute_job_done` (2 raises) and `mark_compute_job_failed`. The message text stays byte-identical, because both Python classifiers fall back to the literal `preempted by watchdog reclaim`, and that fallback is what makes the deploy window safe in both directions. The recommended code is `55006` (`object_in_use`). It already has repo precedent: `20260925120000` translates an enqueue 40001 into `55006` "so no raw 40001 reaches the client". No SQL function calls these three RPCs or catches their 40001, so the errcode change breaks no internal caller.

The enqueue race-loss raise in `_enqueue_compute_job_internal` (both overloads) also raises 40001, and it is reachable through PostgREST (`enqueue_compute_job`, `request_allocator_holdings_sync` and others). It is a DIFFERENT topic. The condition usually converges on retry. Three SQL functions catch it with `WHEN serialization_failure`, and the OPS-08-TS TypeScript retry branches on it. Changing it cascades into ~4 large re-based functions plus the TS helper. **Recommendation: this phase ships the fence family only. It measures and books the enqueue path to a sibling phase, following the 164.5.2 → 164.5.2.1 split precedent.** The OPS-08-TS retry-once is effectively unreachable while PROD runs PostgREST 14, because PostgREST absorbs the 40001 before TS ever sees it.

**Primary recommendation:** Ship one migration, `20261001120000_compute_job_fence_errcode_55006.sql`, re-based on `20260529170000` (defer) and `20260926120000` (mark_done/mark_failed). It swaps `ERRCODE = 'serialization_failure'` → `'55006'` at the 4 fence raises and keeps every message literal. Prove it with three layers: (1) a pg-lane SQL gate with `RED-UNDER-M` arms, one per raise site; (2) live-DB vitest arms through the lane's PostgREST, bounded by `.abortSignal`, in CI via `frontend-live-db-lane`; (3) the Python fencing tests run locally on the lane. Switch the Python classifiers from `"40001"` to `"55006"` and keep the literal fallback.

### Pattern 1: Errcode swap, message byte-identical
**What:** In each re-based body, change only `USING ERRCODE = 'serialization_failure'` → `USING ERRCODE = '55006'` at the 4 fence raises. Update each `COMMENT ON FUNCTION`: all three say "raises serialization_failure" today (baseline.sql:3279, 6851, 6951). Restate `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated;` exactly as the latest migration did. `CREATE OR REPLACE` preserves the ACL, and the restatement keeps the file self-evidently safe. Keep `SECURITY DEFINER` and `SET search_path = public, pg_catalog`. Keep `SET LOCAL search_path = public, pg_catalog;` and `SET LOCAL lock_timeout = '3s';` at the file head (20260926120000:144-145 precedent).
**Why 55006 over alternatives:**

| Code | PostgREST HTTP (v14 table) | For | Against |
|---|---|---|---|
| **`55006` object_in_use (recommended)** | 500 (`55*`) | Repo precedent (20260925120000, TS `create-with-key/route.ts:678` branches on it). Standard class, unique among these RPCs' raise sites. "Another holder has the job" is the true meaning. | 500 rather than 4xx. That is irrelevant to the worker, which branches on the code. |
| `P0001` (plain RAISE) | 400 | Supabase's first suggested fix | Not distinct. Classifiers would have to use the message only. |
| `PT409` | 409 | Semantically "conflict" | PostgREST-specific. The JSON `code` value for PT codes is unverified [ASSUMED]. Non-PostgREST callers (psql, SQL tests) see an odd class. |
| `55P03` lock_not_available | 500 | "contention" | Misleading. `55P03` is a real `lock_timeout` signal that other gates read as flake (critical-regressions.test.ts mentions 55P03 flakes). |
| custom `QZxxx` | 400 ("other") | Unique | No repo precedent. Invents a namespace. |

### Anti-Patterns to Avoid
- **Widening `_rpc_retry_timeout`'s skip match to Kong's 504 text, or raising Kong's timeout.** Forbidden by ROADMAP. Both hide the loop.
- **Rewording the fence messages.** The literal `preempted by watchdog reclaim` is load-bearing for the deploy window (Pitfall 1).
- **Changing `no_data_found` or `invalid_parameter_value` raises in the same functions.** Out of scope. They do not loop.
- **Probing inside the EXCEPTION handler in the SQL gate** (lint rule `R1-exception-handler-probe`). Capture `SQLSTATE`/`SQLERRM` into variables in the handler and assert AFTER the block.
- **Regex over a raw `pg_get_functiondef`** in the migration verify or the gate (`R2-functiondef-comment-strip`). Strip comments first: `regexp_replace(..., '--[^\n]*', '', 'g')`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Retry-safe signalling from an RPC | A client-side "detect hang, cancel, retry" layer | A non-40001/40P01 errcode | PostgREST 14 owns the retry. No client code can stop a server-side loop, and on v14.7 it outlives disconnect. |
| Latest-body extraction | Manual sed of migrations | `supabase/schema/functions/<fn>.sql` + `npm run schema:functions` | G23-187 shipped a stale-body revert. The snapshot is the canonical current body. |
| prod-body ack hash | Hashing the snapshot file | `sql-body-normalize.mjs --diff-bodies` `live` column | VAC-04 greps for that exact hash (20260926120000:95-121 precedent) |
| Invocation counting through PostgREST | Log scraping | Bounded client timeout (`.abortSignal`, `curl --max-time`) as the discriminator; lane-only side-effect sequence for the measurement probe | "Returns once within N s with code X" is binary and RED on today's code |

**Key insight:** the loop lives in the gateway, not the function. A function-level test through psql cannot see it, and a client-level test cannot bound it. Proof therefore needs both a psql-level errcode gate (safe to mutate) and a PostgREST-level single-return test.

## Common Pitfalls

### Pitfall 1: The deploy window between migration apply and Railway deploy
**What goes wrong:** the migration applies to PROD on merge (after TEST), and Railway deploys analytics-service when `main` CI is green. The two land minutes apart, in either order.
**How to avoid:** keep `preempted by watchdog reclaim` byte-identical in all 4 raises. Old worker + new function: `.code` is `55006`, not `40001`, so the literal fallback matches. New worker + old function: PostgREST loops exactly as today, which is no regression. Add a SQL gate arm asserting `SQLERRM` contains the literal for each of the 4 paths, with a RED-UNDER-M that mutates the literal.
**Warning signs:** a reviewer suggests "curated copy" for these messages. These messages are operator-facing and never reach a user.

### Pitfall 2: The migration's own verify block aborts the mutation lane
**What goes wrong:** the migration's DO block asserts "no `serialization_failure` in the comment-stripped body". A RED-UNDER-M that flips an ERRCODE back to `'serialization_failure'` trips that DO block, the apply aborts, and no arm executes. GRAMMAR.md Rule 2 documents exactly this failure ("mutating it trips the migration's own verification block … aborts the apply").
**How to avoid:** each RED-UNDER-M carries TWO edit steps: flip the ERRCODE, AND neuter the matching verify `IF` (→ `IF FALSE THEN`). `test_csv_finalize_double_submit.sql` arm `Part 1c` is the precedent.

### Pitfall 3: Four identical `USING ERRCODE = '55006'` needles
**What goes wrong:** `occurrences` must be MEASURED per needle, and the bare ERRCODE line appears 4 times, so `occurrence-mismatch` fires (MEASURE_FAIL).
**How to avoid:** make each needle include the unique preceding message line (e.g. `(late mark on already-done row,`). Measure each count with a count of the exact multi-line string before writing the annotation.

### Pitfall 4: A RED observation through PostgREST poisons the lane
**What goes wrong:** on v14.7 the loop keeps running after the client aborts, and "stopped only when that container was restarted" (164.9.4-MEASUREMENT). Every later measurement on that lane is contaminated: CPU, one pool slot, and the row stays locked in a loop.
**How to avoid:** after every RED observation through PostgREST, run `bash scripts/local-stack/run.sh down` then `up` before the next measurement. Bound every probe with `timeout` / `curl --max-time` / `.abortSignal(AbortSignal.timeout(ms))`. Bound all loops with `timeout` (memory: orphaned CPU loops).

### Pitfall 5: `python` CI on this PR still hits shared TEST
**What goes wrong:** until 164.9.4 lands, the `python` job reads shared TEST, which carries the OLD bodies until apply-on-merge. `test_defer_compute_job_token_fence` will therefore still loop there and skip, or fail if Kong answers first. The PR's `python` result says nothing about the fix.
**How to avoid:** prove SC-2 LOCALLY on the lane with the 164.9.4 recipe and paste the output into the SUMMARY. Leave `_rpc_retry_timeout` unchanged on this PR. The CI-enforced PostgREST proof pre-merge is the live-DB vitest arm (`frontend-live-db-lane` runs on the lane with this PR's migration replayed). The planner must record this ordering decision explicitly.

### The retry source (why 40001 and 40P01)
hasql-transaction `src/library/Hasql/Transaction/Private/Sessions.hs` at HEAD (fetched via `gh api`):
```haskell
inRetryingTransaction level mode retryOnError session =
  fix $ \retry -> do
    attemptRes <- tryTransaction level mode retryOnError session
    case attemptRes of
      Just a -> return a
      Nothing -> retry
...
    onServerError (ServerError code _ _ _ _) =
      case code of
        "40001" -> retryOrThrow
        "40P01" -> retryOrThrow
        _ -> throwError error
```
This is HEAD, which carries the `retryOnError` flag PostgREST 16 uses to disable retries. PostgREST 14.x's behaviour rests on [CITED: PostgREST CHANGELOG 16.0 "Fix automatic transaction retries on `40001 (serialization_failure)` errors … #3673"], [CITED: Supabase troubleshooting page: "This bug is present in PostgREST 14 and is fixed in PostgREST 16"] and [CITED: 164.9.4-MEASUREMENT.md, run `36304648008`].
