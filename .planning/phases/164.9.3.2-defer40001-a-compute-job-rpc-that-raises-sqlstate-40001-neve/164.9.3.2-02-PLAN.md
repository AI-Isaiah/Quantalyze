<objective>
Ship the fix in SQL: one migration that re-bases `defer_compute_job`, `mark_compute_job_done` and
`mark_compute_job_failed` on their latest definitions and changes only the errcode of their four fence
raises from SQLSTATE 40001 to `55006`, plus a both-lanes SQL gate that is observed RED without the
migration and GREEN with it, with a mutation twin per arm.

Purpose: PostgREST 14 re-runs a call that raises SQLSTATE 40001 without bound (164.9.4 measurement,
hasql-transaction source, PostgREST 16.0 changelog). A claim-token mismatch never changes on retry, so
each of these four raises loops through PostgREST instead of failing once. `55006` is answered once.

**Lanes: `pg-lane`** (`scripts/pg-lane/run.sh` via the gate's own setup list, and
`node scripts/mutation-runner/run.mjs --file`) **and `local-stack`** (the `[BLOCKING]` replay proof).

**Planner decisions recorded here (`164.9.3.2-CONTEXT.md`, added 2026-10-01, puts every implementation choice at Claude's discretion and leaves ENQ-SCOPE open as plan 01's founder checkpoint; these fill that discretion):**
- **PD-01 errcode `55006` (object_in_use), spelled as the literal `'55006'`.** Research's comparison table:
  repo precedent (`20260925120000_api_keys_account_identity.sql` translates an enqueue 40001 into `55006`
  "so no raw 40001 reaches the client"), not retried by PostgREST, unique among these RPCs' raise sites.
  Rejected: `P0001` (not distinct), `PT409` (PostgREST-only), `55P03` (a real lock_timeout signal other
  gates read as flake), a custom class (no precedent).
- **PD-02 re-issue each `COMMENT ON FUNCTION`.** All three deployed comments state the old errcode, so
  leaving them makes them false. Each is re-based on its latest COMMENT statement (defer:
  `20260529170000`; mark_done: `20260603120000`; mark_failed: `20260529180000`, re-grepped at execution)
  with only the errcode wording changed. Implemented by plan 05 (split out of this plan for context
  budget), on the migration this plan commits.
- **PD-03 update the one defer body comment** that says the branch mirrors mark_done's
  serialization_failure branch, so it names the preempted branch and SQLSTATE 55006. Comment-only; the
  verify strips comments.
- **PD-04 the rule sentence** "never raise 40001 or 40P01 from a PostgREST-callable function on
  PostgREST < 16" goes in the migration header (research Pitfall 8). A lint rule for it is not in scope.

Output: the migration (bodies, REVOKEs, self-verify), the gate and the three regenerated snapshots.
Plan 05 completes the migration (COMMENTs, prod-body-acks) and runs the full `[BLOCKING]` schema proof.
</objective>

observation and never a pass.

**Feedback latency (Nyquist).** The fast pre-check, run after every edit to the migration or the gate and
before any lane, is `node scripts/lint-sql-gates.mjs` (static, seconds; catches R1/R2 shape errors). The
pg-lane LANE CMD (about a minute: a throwaway cluster plus the setup list) and `run.mjs --file` (one lane
per twin, minutes) have no faster stand-in: an errcode arm is proven only when a real Postgres raises the
real SQLSTATE from the re-based body, and a twin is proven biting only when that lane goes RED on it. The
PostgREST loop itself is invisible to psql at any speed; plan 03 owns that observation.
