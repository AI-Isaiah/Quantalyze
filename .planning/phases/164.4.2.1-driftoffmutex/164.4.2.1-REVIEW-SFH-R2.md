## HIGH

### SFH-R2-01: the fail-closed pin still passes when the VAC-08 step is disabled

**Where:** the `it` "test-db-drift runs the ordering wait BEFORE VAC-08 …" in `critical-regressions.test.ts`, specifically the `vac08Step` assertions.

**Issue.** Round 1 pinned the WAIT step's `if:` exactly. The comment gives the reason: "a changed condition can DISABLE the wait while the step stays in place and in order". The VAC-08 step got no equivalent pin. Its `vac08Step` checks cover `continue-on-error`, `set -euo pipefail`, the bare invocation, `commandsAfter` and `PGCONNECT_TIMEOUT`. None of them looks at a step-level `if:`.

This was established by reading the code, not by a run. An `if:` line sits at 8-space indent. `commandsAfter` only keeps lines at 10 or more spaces, and every other check is a positive match that an added line cannot break. So adding `        if: false`, or `if: github.event_name == 'push'`, to the VAC-08 step leaves every assertion green.

**Hidden failure.** A skipped step leaves the job at `success`. The `frontend` aggregator's `test-db-drift` arm only inspects the JOB result, so it reads success. VAC-08 then stops running on every PR, or on every event, with a green board. This is the "gate quietly absent" failure that the aggregator's skip arm was built to catch at job level. It is invisible at step level.

**Fix.** In the same `it`, assert that the VAC-08 step has no step-level condition. Slice the step first (see SFH-R2-07):

```ts
expect(
  /^ {8}if:/m.test(vac08StepOnly),
  "ci.yml test-db-drift's VAC-08 step carries a step-level `if:` — a skipped step leaves the job `success`, so the aggregator reads a gate that never ran as green (SC-2)",
).toBe(false);
```

Neuter it by adding `if: false` to VAC-08, observe RED, then restore.

### SFH-R2-02: the aggregator's red-`test-db-drift` message still blames a mutex acquire timeout

**Where:** `ci.yml`, the `frontend` job's result loop, the `elif [ "$name" = "test-db-drift" ]` arm, non-skip `::error::` branch.

**Issue.** When `test-db-drift` is red on a trusted event, this is the line a reader sees first. It still reads: *"If this is a mutex acquire timeout, see docs/runbooks/shared-test-db-mutex.md sections 2-3: queue depth and a wedged holder are different faults."* Since this phase, `test-db-drift` has no acquire step, so neither cause it names can produce the red. Round 1 (IN-06) corrected the same sentence in `analytics-deploy-verify.yml` to "A red `test-db-drift` is its ordering wait (`wait-outcome: wait-exhausted`) or VAC-08 itself, never the lock (runbook 7.3)". The aggregator copy was missed. The repo now holds two texts that contradict each other, and the one that fires in CI is the wrong one.

**User impact.** Whoever triages the red is sent to hunt for queue depth and wedged holders in `pg_locks`. The real causes are never named:
- a wait-exhausted ordering wait;
- a PR-run overlap with `apply-test` or a restore, which round 1's `test-ledger-drift-check.sh` messages now call out;
- real drift.

**Fix.** Replace the trailing sentence with the IN-06 wording. It should name `wait-outcome: wait-exhausted`, VAC-08 itself, and the PR-run writer overlap, and point at runbook 7.3 and section 0. It should drop "mutex acquire timeout" and "sections 2-3". Sweep ci.yml for any other `test-db-drift` text that still names an acquire: `grep -n 'test-db-drift' .github/workflows/ci.yml`, then read each hit outside comments. This closes the whole IN-06 class, not just one instance.

## MEDIUM

### SFH-R2-03: `SCRIPT_TAKES_KEY` matches variable names, not the act of taking a lock

**Where:** the `SCRIPT_TAKES_KEY` constant, and `JOB_TAKES_KEY` for the `_shared` gap.

**Issue.** Inside a followed script, a take counts only when it matches one of three spellings: `MUTEX_KEY=`, `PGAPPNAME=ci-shared-test-db-mutex`, or an advisory-lock call whose argument is the literal key or `MUTEX_KEY`. It matches `test-only-normalize-analytics-url.sh` only because of its `MUTEX_KEY=` assignment. The actual take there is `pg_try_advisory_xact_lock(c_key)` in PL/pgSQL, which the regex does not see. The round-1 claim "every spelling of TAKING the key the repo uses now counts" holds for the repo's current scripts. It does not hold for the next script someone writes.

**Measured misses** (each returned `[]`, meaning not a holder):
- **C:** a script with `LOCK=61616158` followed by `SELECT pg_advisory_lock(${LOCK});`.
- **D:** a script with `pg_advisory_lock_shared(${SHARED_KEY})`. `_lock_shared(` never matches `_lock\(` in either regex.
- **J:** the same `_shared` call written directly in the job's YAML, with a psql variable argument.

A natural refactor walks straight into C: moving the mutex key into `scripts/shared-test-db-keys.sh` beside `SHARED_TEST_SCHEMA_APPLY_INFLIGHT_KEY`, where its self-test already holds it as `local mutex_key=61616158`. `\bMUTEX_KEY=` does not match `SHARED_TEST_DB_MUTEX_KEY=`, because there is no word boundary after `_`.

**Fix.** Make the script rule fail closed. In a followed script, count ANY `pg_(try_)?advisory(_xact)?_lock(_shared)?\(` call as a take, with two exceptions:
- the argument is a numeric literal other than the key;
- the argument is exactly `${SHARED_TEST_SCHEMA_APPLY_INFLIGHT_KEY}`, the one known non-mutex take.

Then `test-db-drift`'s real scripts still read as non-holders. `shared-test-db-keys.sh` try-locks only the in-flight key, and `test-ledger-drift-check.sh` calls no lock. `c_key`, `$LOCK` and `_shared` would all count. Add `(?:_shared)?` to `JOB_TAKES_KEY` as well. Add calibration cases for C, D and J.

### SFH-R2-04: `scriptsRunBy` misses several ordinary ways a job runs a script

**Where:** `scriptsRunBy`.

**Issue.** The walk seeds from `scripts/[\w./-]+\.sh` tokens in the job body. From there it follows only whole-line `.`/`source` directives, and the source regex is anchored with `\s*$`. Measured misses, each returned `[]` while the script it reaches does take the key:

| probe | form | why it is missed |
|---|---|---|
| E | `. "${SCRIPT_DIR}/inner.sh" \|\| exit 1` | the `$` anchor rejects a trailing `\|\| exit 1` or `# comment` |
| F | a followed script that runs `bash "${SCRIPT_DIR}/restore-test-from-baseline.sh"` | only `.`/`source` is followed, never an executed child |
| G | `node scripts/x.mjs` (or python, or tsx) | only `.sh` seeds the walk |
| H | `cd scripts && bash restore-test-from-baseline.sh` | the token has no `scripts/` prefix |

Today no repo script executes a key-taking child. `grep` for `bash|sh|exec` of a `.sh` from `scripts/*.sh` finds only self-test temp files and `pg-lane/run.sh --print-pgbin`. So these are latent gaps, not live ones. But this detector is the only thing the D-02 negative rests on, and every miss here resolves to "no holder".

**Fix.**
- Follow every `[\w./-]+\.(sh|mjs|js|ts|py)` token on a followed script's non-comment lines. Resolve it against both the script's directory and the repo root.
- Drop the `\s*$` anchor on the source regex.
- Where a job line runs `bash`, `sh` or `source` on a token that cannot be resolved to a repo file, THROW with the unresolved form named. Do not skip it. An unfollowable invocation should be a loud detector gap, not a silent non-holder.

### SFH-R2-05: the private-lane exemption can be bypassed with a `..` path, and it covers whole directories

**Where:** `PRIVATE_LANE_SCRIPT` and its use in `measureHolders`.

**Issue.** The exemption is a prefix test on the path as it was written, before any normalisation. `read()` goes through `join`, which does normalise. So `bash scripts/pg-lane/../restore-test-from-baseline.sh --mode preflight` is exempt, and the real key-taking restore script goes uninspected.
- probe L: that path returned `[]`;
- probe M: the same script by its plain path returned `['probe']`.

Separately, the exemption covers every file under `scripts/pg-lane/` and `scripts/local-stack/`. Its only justification is that `local-stack/run.sh` refuses a non-local DSN. A new sibling script in either directory that connects to `TEST_SUPABASE_DB_URL` would be exempt with no evidence behind it. Probe I did exactly this and returned `[]`.

**Fix.**
- Apply `posix.normalize(path)` before the prefix test, and before adding the path to `seen`.
- Narrow the exemption to named files: `scripts/pg-lane/mutex-dead-holder-lane.sh`, plus any other file proven to boot a private cluster. The calibration already re-proves each named file with its `SCRIPT_TAKES_KEY.test(readText(...))` expect.
- Add probe L to the calibration as a must-see case.

### SFH-R2-06: a job whose key line has a trailing comment is never measured

**Where:** `measureHolders`, the job enumeration `/^ {2}([a-z0-9-]+):\s*$/gm`. This regex predates round 1, but it is now the only holder census.

**Issue.** A job key written as `  probe:  # holder`, or any key with an uppercase letter or an underscore, is never enumerated. Probe A did this with a literal `Acquire shared-test-db mutex` step and `pg_advisory_lock(61616158)` in the body, and returned `[]`. The holder-set pin then reports a set without that job. For `test-db-drift` itself, this is backstopped: `jobSlice`'s `findOrFail` throws on the same key-line shape, which is loud. A NEW holder added with such a key line would be invisible.

**Fix.** Enumerate with `/^ {2}([A-Za-z0-9_-]+):\s*(?:#.*)?$/gm`. Apply the same tolerance to the per-job body regex and to `jobSlice`. Add probe A to the calibration.

## LOW

### SFH-R2-07: `vac08Step` runs to the end of the job, not the end of the step

**Where:** `const vac08Step = body.slice(vac08)`.

**Issue.** VAC-08's `continue-on-error`, `PGCONNECT_TIMEOUT` and `commandsAfter` checks all read every step after VAC-08 as well. Two consequences:
- If `PGCONNECT_TIMEOUT` moves to a later step and VAC-08 loses it, the pin passes. That is a silent pass.
- Adding any later step with a `run: |` body fails the pin with "runs a command AFTER scripts/test-ledger-drift-check.sh". That is a loud red, but it blames the wrong step.

**Fix.** Bound the slice the same way `waitStep` is bounded, at the next `\n {6}- `.

### SFH-R2-08: a sourced helper is resolved by basename only

**Where:** `scriptsRunBy`, the source regex's `([\w.-]+\.sh)` capture, joined to `posix.dirname(path)`.

**Issue.** The directory part of the sourced path is thrown away. `. "${SCRIPT_DIR}/../lib/k.sh"` from `scripts/a.sh` resolves to `scripts/k.sh`. If no such file exists, the read throws ENOENT: loud, but for the wrong reason. If a file with the same name exists in the sourcing script's directory, the walk silently inspects the wrong file.

**Fix.** Capture the whole path, substitute `${SCRIPT_DIR}`/`$(dirname …)` with the script's directory, then normalise. Throw on any path that still contains a variable.

### SFH-R2-09: a new failure message states an unmeasured cause as fact

**Where:** `check()` in `scripts/test-ledger-drift-check.sh`, the ledger-presence `fail` message.

**Issue.** The message says: *"A restore's TRUNCATE of the ledger holds this query past its statement timeout on every attempt."* Whether that is true depends on how long the restore holds the lock between TRUNCATE and COMMIT, compared with `LEDGER_QUERY_ATTEMPT_BUDGET` (3) times a 30 s `statement_timeout` plus backoff. Nothing measured that duration. Stated as fact, it can wrongly convince a reader that a concurrent restore explains a red.

**Fix.** Change "holds" to "can hold". The condition and the asserted substring are unaffected.

## INFO

### SFH-R2-10: a missing psql would show up as a 900 s wait timeout, not as a missing binary

`test-db-drift`'s ordering wait now depends only on the `Install psql client` step. No pin requires that step to come before the wait step. `wait-for-test-schema-apply.sh` has no `command -v psql` guard, so without psql its probe returns `unknown`. That is correctly treated as not clear, but the step then exhausts its `WAIT_BUDGET_SECONDS` and reports an in-flight-flag problem instead of "psql is not on PATH". VAC-08 has that guard (`command -v psql … || fail "psql is not on PATH."`). The job still fails, so this is only a diagnostics issue. A one-line `command -v psql` check at the top of the wait's `main` would make the fault name itself.
