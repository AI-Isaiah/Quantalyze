## Which runs count

- **Admissible:** a `push` run of `ci.yml` on `main` that CONCLUDED, whose head SHA has THIS
  phase's merge commit as an ancestor. Paste, per run:
  `git merge-base --is-ancestor <164.4.2.1 merge sha> <run head sha> && echo AFTER-CONFIRMED`.
- **Bind each run to its SHA and COUNT that SHA's workflow runs** (an empty or short list is a
  finding, not a pass):
  `gh api "repos/AI-Isaiah/Quantalyze/actions/runs?head_sha=<sha>" -q '.workflow_runs | length'`.
- **Not admissible:** a `pull_request` run, a `workflow_dispatch` run, any run on the phase branch,
  or a re-attempt (`run_attempt` > 1) standing in for a first attempt.
- **Degenerate** = 164.4.2's rule: `python`'s acquire-wait NOT near its 0m05s floor means the run
  sat in a cross-run pile-up. **Plus a recorded "overlapped a sibling run?" column**: yes if the
  run's `run_started_at` falls inside another admissible run's `run_started_at` → `updated_at` span,
  or vice versa. This column exists because 164.4.2's Runs 2 and 4 passed the old rule while
  overlapping a sibling. The column is recorded for every run; the degenerate classification itself
  stays 164.4.2's rule, so the two phases are graded on the same criterion.
- **MIGRATION STRATUM.** A run whose SHA has a `supabase-migrate.yml` run (Step 4) is its own
  stratum: its ordering wait inherits `apply-test`'s own queue (research Pitfall 4), which no
  164.4.2 AFTER run measured. It is recorded in `### Migration-stratum runs` below and reported
  separately, never averaged in.
- ⛔ **A migration-stratum run does NOT count toward "the first 5 non-degenerate".** The five graded
  runs are all non-migration pushes. Stratum runs are recorded in their own table beside them, in
  addition to the five.
- **How many:** the first 5 admissible, non-degenerate, non-migration-stratum runs are graded, in
  order of `run_started_at`. EVERY degenerate run met on the way is recorded in full and marked,
  never dropped, and is compared against the full spread (16m18s–62m20s), not the non-degenerate
  band.

## Verdict rule

Decided here, before any `ci.yml` change, and not moved after the AFTER is read. Each clause is
graded per run and then over the five graded runs.

- **(a) The critical path falls back.** Two readings, both computed on every graded run:
  - **GRADED (D-01, the Goal reading):** a non-degenerate, non-migration run-total **inside or
    below 16m18s–18m50s**, i.e. ≤ 18m50s. PASS at five runs = every graded run ≤ 18m50s. A run
    above 18m50s is a FAIL on this clause and is said so, not re-described.
  - **RECORDED, NOT GRADED (the strict 164.4.2 reading):** run-total **below 16m18s**. Its result
    is written beside the Goal reading on every run and **booked as evidence for Phase 164.9
    TESTISOLATION**. It is never this phase's pass/fail (D-01).
- **(b) Regression guard — this phase must not undo 164.4.2's one passing clause.** `sql-tests`
  job-total below **8m31s** on every graded run.
- **(c) The remaining holders do not absorb the freed time — made non-vacuous (D-06).**
  - `test-db-drift`'s acquire-wait is **0 by construction**: the step no longer exists. It is
    written as 0 and is NEVER evidence and never counted as a win.
  - The graded term is `python` + `e2e-seeded` acquire-wait. PASS = below **12m05s** AND not above
    those two jobs' own BEFORE sum **5m35s–7m00s** by more than their measured BEFORE spread.
  - **Fixed numbers, written before any code:** spread = 7m00s − 5m35s = **1m25s**; ceiling =
    7m00s + 1m25s = **8m25s**. So clause (c) **PASS per run = combined ≤ 8m25s** (which is also
    below 12m05s). Both inputs were re-read from the 164.4.2 `### Verdict rule` and `## BEFORE
    table` on 2026-09-25 (see `## BEFORE`); they agree with the values this phase's plan carried,
    so nothing was recomputed.
- **(d) A faster wall clock alone confirms nothing.** Clause (a) passing while (c) fails is recorded
  as luck in runner availability or queue depth, NOT as a confirmation (164.4.2's clause (d)).
- **SC-1 structural reading.** On every admissible run the `test-db-drift` job's step list shows no
  `Acquire shared-test-db mutex` step at all. A run that shows one means the merged `ci.yml` is not
  the one this phase shipped; stop and find out why before grading anything.

**A win for this phase** = SC-1's structural reading holds, (a)-Goal PASS, (b) PASS and (c) PASS
on the five graded runs. The strict (a) result is reported either way and does not enter it.
