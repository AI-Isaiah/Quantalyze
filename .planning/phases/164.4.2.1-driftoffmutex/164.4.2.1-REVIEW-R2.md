## Warnings

### WR-01: The "fail-closed" ordering pin does not pin VAC-08's own `if:`. `if: false` on that step leaves the job green with VAC-08 never run

**File:** `src/__tests__/critical-regressions.test.ts` (the `it` named "test-db-drift runs the ordering wait BEFORE VAC-08 …")
**Issue:**
- The round-1 fix pins the WAIT step's `if:` exactly. For the VAC-08 step it pins
  `continue-on-error`, `set -euo pipefail`, the bare invocation and "nothing after".
- It never asserts that the VAC-08 step carries NO `if:`. An `if: false`, or an
  `if: github.event_name == 'push'` that silently drops PR coverage, passes every
  assertion in the `it`.
- A skipped step reports success, so `test-db-drift` concludes `success`. The `frontend`
  aggregator's `test-db-drift` arm accepts that.
- I grepped `src/__tests__` for any other pin on this step's `if:` and found none. This
  is exactly the case the fix's own comment describes: "a gate whose failure cannot fail
  the job is not a gate". A skipped gate is the degenerate form of that.
- A smaller cousin: a `trap 'exit 0' EXIT` placed before either invocation also masks
  the exit status. `commandsAfter` does not see it because it only looks after the
  invocation.

**Fix:**
```ts
expect(
  /^ {8}if:/m.test(vac08Step),
  "ci.yml test-db-drift's VAC-08 step carries an `if:` — a condition can SKIP the gate, and a skipped step is a green job (SC-2)",
).toBe(false);
expect(
  /^\s*trap\b[^\n]*\bexit\s+0\b/m.test(waitStep) || /^\s*trap\b[^\n]*\bexit\s+0\b/m.test(vac08Step),
  "a trap that exits 0 masks the invocation's exit status (SC-2)",
).toBe(false);
```
Neuter each (add `if: false` / the trap), observe RED, restore with cp+cmp.

### WR-02: `vac08Step` runs to the END OF THE JOB, so any later step false-reds the pin with a misleading message

**File:** `src/__tests__/critical-regressions.test.ts`, `const vac08Step = body.slice(vac08);` and the `commandsAfter(vac08Step, …)` / `^ {8}continue-on-error:` assertions on it
**Issue:**
- `waitStep` is correctly bounded at the next `\n {6}- `. `vac08Step` is not bounded.
- VAC-08 is the job's last step today, so the pin is green. If anyone adds an ordinary
  step after it, the pin goes red. Examples: an `if: always()` summary, or an
  `upload-artifact` whose `with:` values sit at 10 spaces.
- `commandsAfter` counts every non-comment line at 10+ spaces after the invocation, so
  the new step's `run:` body or `with:` keys fail the pin with "VAC-08 step runs a
  command AFTER scripts/test-ledger-drift-check.sh". That is false.
- A `continue-on-error:` on that LATER step would likewise fail the pin as "VAC-08 step
  carries continue-on-error".
- The message sends the next editor to the wrong step. The reflexive "fix" is then to
  loosen the assertion.

**Fix:** Slice `vac08Step` the same way as `waitStep`:
```ts
const afterVac08 = body.slice(vac08);
const nextAfterVac08 = afterVac08.slice(1).search(/\n {6}- /);
const vac08Step = nextAfterVac08 === -1 ? afterVac08 : afterVac08.slice(0, nextAfterVac08 + 1);
```
Then prove it: add a trailing `- name: x\n        run: echo x` step and observe that the pin stays GREEN.

### WR-03: `measureHolders`' script-side rule is narrower than its comment claims. Several spellings of a real take read as a non-holder

**File:** `src/__tests__/critical-regressions.test.ts` (`SCRIPT_TAKES_KEY`, `scriptsRunBy`, and the comment "Every spelling of TAKING the key the repo uses now counts")
**Issue:** I measured each spelling below by running the shipped regexes in node.
- **`SCRIPT_TAKES_KEY` returns FALSE for scripts that do take the key:**
  - `local key=61616158` followed by `pg_advisory_lock(${key})`. This is the natural
    spelling if the `python`/`e2e-seeded` acquire is ever extracted into a script.
  - `SHARED_TEST_DB_MUTEX_KEY=61616158`. `\bMUTEX_KEY=` has no word boundary after `_`.
  - `pg_advisory_lock(61616158::bigint)`.
  - `pg_advisory_lock (61616158)`, with a space before the parenthesis.
  - `PG_ADVISORY_LOCK(61616158)`. SQL is case-insensitive.
  - `pg_advisory_lock_shared(61616158)`. A shared-mode lock still conflicts with the
    exclusive holders.
- **`JOB_TAKES_KEY` misses the same `_shared` / uppercase / space-before-paren forms on
  a variable key.** Its literal-key arm still catches the literal forms.
- **`scriptsRunBy` follows only `.`/`source` lines that END with the path.** It misses:
  - `. "${SCRIPT_DIR}/k.sh" || exit 1` (not followed)
  - `. ./k.sh # comment` (not followed)
  - `source "$(dirname "$0")/k.sh"` (not followed)
  - scripts a followed script EXECUTES rather than sources (`bash "$DIR/restore-….sh"`)
  - non-`.sh` entry points (`node scripts/x.mjs`)
  - a bare `bash restore-….sh` under `working-directory: scripts`

A job that re-acquires the key through any of these reads as a non-holder. The holder-set
pin and the D-02 negative then both stay green, which is the SFH-02 false-green class the
fix set out to close. No current `ci.yml` job uses one of these spellings, so this is a
pin gap rather than a live defect. The comment's "every spelling" is not true.

**Fix:** Either widen the script rule to "the literal key appears on a NON-comment line
together with any advisory-lock verb (case-insensitive, `\s*\(`, optional `_shared`)",
and follow executed `scripts/…` paths as well as sourced ones. Or, more simply, rewrite
the comment to name exactly the spellings the detector sees and add those three
`scriptsRunBy` misses to the calibration `it` as documented non-coverage. Do not keep
prose that claims completeness.

### IN-03: `scriptsRunBy` resolves paths in ways that can crash the pin or read the wrong file

**File:** `src/__tests__/critical-regressions.test.ts` (`scriptsRunBy`)
**Issue:**
- `scripts\/[\w./-]+\.sh` matches `scripts/…` as a SUBSTRING. A job that runs
  `analytics-service/scripts/x.sh`, or a bare `scripts/x.sh` under the `python` job's
  `working-directory: analytics-service`, is read as repo-root `scripts/x.sh`.
- A sourced path keeps only its basename and is re-rooted at the sourcing script's
  directory. `. "${SCRIPT_DIR}/../lib/k.sh"` therefore resolves to `scripts/k.sh`.
- A job line that merely echoes a deleted script path makes `readFileSync` throw ENOENT.
  The result is a stack trace, not a named assertion.
- All of these fail loudly or over-count today. None hides a holder.

**Fix:** Resolve `../` properly with `posix.normalize(posix.join(dir, captured))`, where
`captured` is the whole path, not the basename. Wrap `read` so a missing file fails with
a message that names the job and the path.

### IN-05: The 90m-TTL paragraph says connects are bounded, so a black-holed host "fails in seconds". A mid-session network loss is still unbounded

**File:** `.github/workflows/ci.yml` (`test-db-drift`, "WHAT 90m NOW BOUNDS" and the VAC-08 step's `PGCONNECT_TIMEOUT` comment)
**Issue:**
- `PGCONNECT_TIMEOUT` bounds the connect only.
- `statement_timeout` is enforced by the server. If the network drops after connect, the
  client blocks on a read until TCP keepalive fires, and the default idle time is far
  beyond 90m. The TTL is then the only bound.
- The wait probe and the mutex census pair `PGCONNECT_TIMEOUT=15` with a wall-clock
  `timeout 20`. VAC-08 has no equivalent.
- The paragraph is the stated basis for any future TTL decision (D-04), so it should not
  overstate the bound.

**Fix:** Qualify the claim ("an unreachable host at CONNECT fails in seconds; a
mid-session loss is bounded only by the TTL"), or wrap each psql in the script with a
wall-clock `timeout`, as the wait probe does. libpq keepalives are connection-string
parameters with no environment variable, so they cannot be set from the step's `env:`.
The prose qualification is the smallest fix.

### IN-06: The new VAC-08 ledger-presence failure message states a speculative mechanism as fact

**File:** `scripts/test-ledger-drift-check.sh` (`check()`, the `ledger presence query failed` `fail`)
**Issue:**
- The message says "A restore's TRUNCATE of the ledger holds this query past its
  statement timeout on every attempt".
- The restore's `TRUNCATE supabase_migrations.schema_migrations` sits near the end of
  its transaction. The lock is held only for the re-seed tail before COMMIT.
- The likelier overlap outcome is a short wait followed by a read of the post-restore
  state. Exhausting three 30s attempts plus backoff requires that tail to outlast the
  whole budget.
- As a triage hint this is harmless, but it is worded as certain.

**Fix:** Change it to "can hold this query past its statement timeout on every attempt
if the restore's post-TRUNCATE tail outlasts the retry budget".

### IN-07: The SFH-04 correction in `test-restore-from-baseline.yml` says an overlap "can only red VAC-08". SFH-05's correction says it can also PASS

**File:** `.github/workflows/test-restore-from-baseline.yml` (THE ACTIVITY GATE comment, `⛔ CORRECTED 2026-09-25 … SFH-04`)
**Issue:**
- The comment reads "an overlap can only red VAC-08 (a read of a state that really
