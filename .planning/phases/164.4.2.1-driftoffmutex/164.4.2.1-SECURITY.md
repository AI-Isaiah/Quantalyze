## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |
|---------|------------|-----------|-------------|------|
| AR-164.4.2.1-01 | T-164.4.2.1-07 | With the key gone, a TEST writer (apply-test, or a dispatched restore) can overlap VAC-08. That happens on any `pull_request` run, which has no ordering wait, and in the seconds-wide window after the wait on a merge push. Every migration file and the restore are each one transaction, so under MVCC VAC-08 reads only committed state. An overlap therefore ends one of two ways: (a) a loud RED (statement timeout → MEASURE_FAIL, or a transient frontier/ceiling breach), or (b) a correct verdict on a state that really committed. It never gives a GREEN on a state that never committed. The false-red messages now name this cause (`test-ledger-drift-check.sh` query-failure and `FRONTIER_EXEMPT_CEILING` texts, and the aggregator's `test-db-drift` arm). The plan's D-03 revisits only if a red is observed. ## Advisories (non-blocking)

1. **T-03 rests on one assumption the research marks ASSUMED (A1):** that `supabase db push` commits each migration's ledger row in the same transaction as the file. Neither ordering yields a false GREEN. If the row commits after the file, the newest file reads as above the frontier and is exempted, within the ceiling. If the row commits before the file, the function-body half reds. So the threat stays closed either way. The assumption is recorded, not measured.
2. **Holder detector limit:** what a node/python/TS entry point imports or spawns is not walked. A future writer that takes the key only inside an imported module would read as a non-holder. The limit is stated in the detector's own header comment. No such file exists today.
3. **PR-run VAC-08 is unordered against TEST writers.** This is new since the phase, and it is the accepted risk above. It can only red loudly or read committed state.
