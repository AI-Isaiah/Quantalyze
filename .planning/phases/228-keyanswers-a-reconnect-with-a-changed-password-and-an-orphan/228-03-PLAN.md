<objective>
A reconnect with a rotated or mistyped MT5 password gets a named answer that matches what `api_keys` holds afterwards, and KEY_ORPHANED names the key for every role.

Purpose: CONN-02 under the founder ruling of 2026-11-26, "Validate and update in place" (228-CONTEXT.md `### CONN-02: rotated or mistyped MT5 password`, ROADMAP `### Phase 228` founder ruling line), and CONN-04's SC-2 role test (CONTEXT `### CONN-04: orphaned key copy`).

Output: the rotate leg in `src/app/api/strategies/create-with-key/route.ts`, with route tests that pin every arm, and the emitter census moved.

Recorded decisions (the plan's final set, as CONTEXT asks the planner to record):
- **Rotating arms (final set):** pre-validation fence verdicts `connected`, `orphaned`, `held` and the other-session `draft`, ONLY when the resolver picked the caller's own WORKING holder (`liveKeyId = picked.id`, after `isWorkingHolder`) AND `picked.venue_server !== null && picked.venue_server === venueServer` (the exact tier, CONTEXT server-rule amendment). The `held` from a failing holder with a composite dependent never rotates (CONTEXT amendment). `failing_holder` keeps its 225-07 path. The post-validation resolve and the 23505 race arm keep their refusals (CONTEXT amendment "Only at the pre-validation fence"). The same-session draft never reaches the fence: F6 answers it first.
- **The key id** travels as an explicit `rotate?: { keyId: string }` member set only on the working-holder exact-tier path in `resolveByVenueIdentity`, never inferred from a verdict kind, and never serialised.
- **One probe:** the rotate seam alone (CONTEXT `### Decided autonomously`). Probe-then-compare, so `unchanged` truthfully means "and it signs in" (Plan 01).
- **Catch placement:** the fence records the rotate-bearing verdict in a `let` declared beside `failingHolderId`, and the rotate leg runs as the FIRST statement inside the existing `try`, before `validateKey`. A seam throw therefore reaches the existing `catch` (`classifyKeyValidationError`, `keyRouteFailureHeaders`, scrubbed with this request's secrets). There is no second catch and no re-indent.
- **Wire shape:** the existing refusal code and body, plus `key_secret: { outcome: "updated" | "unchanged"; name?: string }` from Plan 02's `keySecretField`. There is no new wizard code (RESEARCH Q7). The answer stays HTTP 409 (RESEARCH A8, a CHANGELOG `### Notes` item).
- **Rate limit:** no second token; the request already spent `strategies-create-with-key:<uid>`. Brute force is bounded by that 5 per 60 s plus the seam's 10 per 60 s per key.
- **Authz (CONTEXT `### Review scope`):** owner only, with rotate-secret's checks. `withAuth` supplies CSRF, the session and the approval gate. The key id comes from the owner-filtered resolver read. A user-scoped (RLS) re-read of that key filtered on `id` + `user_id` + `exchange = 'mt5'` + live proves ownership again. The seam receives `user_id` from the session. The UPDATE is filtered on `id` + `user_id` + `exchange = 'mt5'` inside `persistRotatedMt5Secret`.
- **Master password:** the seam raises before re-encrypting, and the route reaches `persistRotatedMt5Secret` only after a parsed seam success, so a refusal writes nothing (UI-SPEC O3).
- **Concurrent sync (known limit):** the poll writers are out of scope (Phase 225-21 owns them; CONTEXT Deferred). A sync already running with the old password can mark the key failed after the rotate; the next sync clears it. Stated here, and for the ship's CHANGELOG `### Notes`.
- **Inherited from rotate-secret, unchanged:** the UPDATE resets `history_inclusion` to null when the key is live afterwards, as every rotate-secret success does. A working holder is live before and after, so this clears only a departure-scoped choice.
</objective>
