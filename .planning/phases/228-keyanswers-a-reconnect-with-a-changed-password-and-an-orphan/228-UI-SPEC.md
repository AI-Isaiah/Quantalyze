# Phase 228 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This phase touches three existing surfaces on the strategy wizard's connect step. It adds
**one new rendered element**, the outcome notice. It adds no component, token or colour.

1. **The outcome notice (CONN-02, new).** An MT5 reconnect on a same-account arm now validates the
   typed password and, if the password is new, rotates it into the stored key. That is an outcome,
   not a failure. It renders as a plain notice in `ConnectKeyStep`, directly above the unchanged
   `ErrorEnvelope`, which still carries the arm's refusal (§1).
2. **The F6 dedup strip (CONN-02).** The fallback sentence in `WizardClient.tsx`
   (`data-testid="wizard-dedup-notice"`) stops claiming that the credentials just entered "are already
   connected" (§2).
3. **`KEY_ORPHANED`'s Disconnect bullet (CONN-04).** It names the key when the holder is known, and
   otherwise falls back to today's sentence byte for byte (§3).

**Sources:** `228-CONTEXT.md`, which holds the founder's CONN-02 ruling of 2026-11-26 ("Validate and
update in place", locked), plus ROADMAP `### Phase 228`, REQUIREMENTS CONN-02 / CONN-04, and
`DESIGN.md` (Error Envelope, Voice, Semantic-colour gates, A11y minimums). Every anchor was
re-measured in this worktree at HEAD `966b6863d` (VERSION `0.133.93.1`) on 2026-11-26. Anchors are
cited by symbol, and line numbers are given only as `~` hints.

## Global rules (apply to every section)

- **G1. No identifier in any rendered string or accessible text (T-154-06-C).** No login, broker
  server, key id or venue account id appears in the notice, the strip, the bullet, a `data-*`
  attribute or the LiveRegion. The only names rendered are the caller's own key nickname, strategy
  name or draft name, read from the caller's own rows.
- **G2. Names render as React text, trimmed.** A blank or whitespace-only name counts as "not
  told" and selects the unnamed sentence. Never print empty quotes, `undefined` or a placeholder.
  This is the rule `formatKeyError`'s holder arms already follow.
- **G3. Every sentence must be true on every arm that can reach it.** This is the repo's
  copy-honesty rule. §5 audits each surviving sentence against the post-write state.
- **G4. One builder per string (TWIN-8).** Each notice sentence and the named Disconnect bullet is
  built in exactly one place. The planner picks the module, under the censuses
  (`KNOWN_CREATE_WITH_KEY_CODES`, the invariant scanner and the roster tests).
- **G5. Voice.** Declarative, sentence case, active voice, no exclamation, no adjective where a fact
  exists (DESIGN.md §Voice). The founder's sentence is used verbatim as the notice's first clause.

## 1. CONN-02: the outcome notice

### 1.1 Render decision (Claude's discretion, with reasons)

The notice is **a plain notice element beside the envelope, not a variant of the envelope.**

- **An `ErrorEnvelope` tone variant is out.** DESIGN.md §Error Envelope fixes the shell as
  `role="alert"` + `border-negative/30 bg-negative/5`. A variant would amend a founder-owned contract,
  and there is no one to approve that.
- **Prepending the sentence into the envelope's `cause` is also out.** It would put a verified,
  successful write inside a red alert. That breaks the semantic-colour gate ("Red = permanent /
  negative only"), and on a skim it reads as "nothing happened".
- **The refusal stays an `ErrorEnvelope`.** The arm still refuses to mint a strategy, still names
  what holds the account, and still carries a `code` and a correlation id for Diagnostics. That is
  what `buildEnvelope` is for.
- **No new component.** No `strategy_id` is minted, so `ConnectKeyStep` stays mounted and the notice
  lives there. It reuses the existing strip class recipe (the session-expired and dedup strips in
  `WizardClient.tsx`, and the success panel in `ScenarioCommitDrawer.tsx`).

### 1.2 The signal the notice reads

The notice renders from **two values taken off the same create-with-key response** as the error
code. The wire shape (a new code, or the existing code plus a marker) is the planner's call per
CONTEXT.

| Value | Meaning | Absent / malformed |
|---|---|---|
| outcome | `updated`: the seam validated the new password and the stored key was rewritten. `unchanged`: the seam reported that the typed password equals the stored one, and nothing was written. | No notice renders. The envelope renders exactly as today. |
| key nickname | The `label` of the **key whose password was checked**, from the caller's own `api_keys` row, trimmed. | The unnamed sentence (§1.3). |

The client shape-checks the nickname as a non-blank string, as `parseAccountHolder` does for
`holder`. It is never used as an `href`.

### 1.3 Copy (verbatim)

| Outcome | Nickname known | Notice text |
|---|---|---|
| `updated` | yes | `We updated the password on your key "{nickname}". No new key or strategy was created.` |
| `updated` | no | `We updated the password on your stored key for this account. No new key or strategy was created.` |
| `unchanged` | yes | `Your key "{nickname}" already uses this password and it signs in, so we changed nothing.` |
| `unchanged` | no | `Your stored key for this account already uses this password and it signs in, so we changed nothing.` |

- **Quotes.** Straight double quotes, as in the founder's sentence and in `formatKeyError`'s
  cause-line holder arms (`your key "X"`).
- **Why the second sentence exists (`updated`).** Two of the refusals that render below the notice
  end with `Your new key was not saved.` (`VENUE_DRAFT_IN_PROGRESS`, `KEY_VENUE_ALREADY_CONNECTED`).
  "No new key or strategy was created" frames "new key" as a new row, so the notice and the envelope
  agree. It is true on all four arms: none mints a `strategy_id` or inserts an `api_keys` row.
- **"and it signs in" (`unchanged`)** is true only if the seam's broker probe ran before the compare
  reported `unchanged`. CONTEXT's decision is that the answer "says the stored password already
  works", so the contract assumes probe-then-compare. **If the planner puts the compare before the
  probe**, drop the clause and use `Your key "{nickname}" already uses this password, so we changed
  nothing.` (unnamed: `Your stored key for this account already uses this password, so we changed
  nothing.`). Record the choice in the plan.
- **No claim beyond these.** The notice does not say "syncing resumes", "your strategy is fixed" or
  anything about when the next sync runs. A sync that started with the old password can still mark
  the key failed afterwards (CONTEXT: deferred, recorded as a limit). So "the key now syncs" would
  not be true on every arm.

### 1.4 Visual contract

Both outcomes share one recipe and differ only in tone. **One `<p>` element:**

| Outcome | Classes | Tone ruling (DESIGN.md semantic-colour gates) |
|---|---|---|
| `updated` | `rounded-md border border-positive/30 bg-positive/5 px-3 py-2 text-body text-text-primary break-words` | **Positive.** The tone is earned: the broker accepted the new password and we wrote it. Success is carried by the border and the tint, not by the text colour. |
| `unchanged` | `rounded-md border border-border bg-page px-3 py-2 text-body text-text-primary break-words` | **Neutral.** Nothing was written, so the steady state is muted. This is the dedup strip's border and fill. |

- **Placement.** In the credential render of `ConnectKeyStep` only: the immediate previous sibling of
  `{errorEnvelope && <WizardErrorEnvelope … />}` (~:1892), inside the form (`space-y-5`). The form's
  existing 20px rhythm separates it from the envelope, and **no wrapper is added**. DOM order is
  notice, then envelope, so reading order is outcome, then refusal.
- **Not in the preselect render.** The same-account arms are reached only through the credential
  submit (`handleSubmit`), and the reuse arm never rotates.
- **No other client can reach the rotate arms.** Measured with
  `grep -rn "/api/strategies/create-with-key" src e2e | grep -v '\.test\.'`: the only browser
  caller is `ConnectKeyStep`. Its credential submit (`wizardFetch("/api/strategies/create-with-key"`,
  ~:1146) carries a password. Its reuse submit (~:1386) carries only the session token and a key id,
  so it cannot rotate. `MultiKeyConnectStep` posts to `/api/strategies/composite/add-key`, a different
  route that this phase does not change. `e2e/for-quants-onboarding.spec.ts` only stubs the route. So
  the credential render of `ConnectKeyStep` is the one place the notice renders.
- **No icon, no glyph, no left stripe, no button, no link.** The envelope below already carries the
  holder link and the remedies.
- **Hooks.** `data-testid="wizard-key-outcome-notice"` and `data-outcome="updated" | "unchanged"`.
  No identifier in either (G1).

### 1.5 Lifecycle and announcement

- **Set from the same response as `errorCode`, every time.** The notice is self-clearing in the way
  the dedup strip already is: a response without the signal takes it down.
- **Cleared** at the start of every submit (where `errorCode` is cleared today) and in the envelope's
  `onRetry` (today `() => setErrorCode(null)`). The notice describes that response and must not
  outlive its refusal.
- **Announcement.** A `role="status"` region that mounts together with its text, beside a
  `role="alert"`, is often missed (`LiveRegion`'s docblock). So the visible `<p>` carries **no
  role**. A `<LiveRegion message={noticeText} />` (polite) stays **mounted for the whole credential
  render**, with `message` null when there is no notice and the notice's exact sentence when there
  is one. The envelope's own `role="alert"` is unchanged. A screen reader hears the refusal, then the
  outcome, because a polite announcement queues behind an assertive one. Sighted users read the
  outcome first. Both channels carry the same words.

## 2. CONN-02: the F6 session-fence strip

Only the **fallback** branch changes. The markup, the gate (`dedupedExisting && step ===
"sync_preview"`), the test id and the two other branches stay byte-identical.

| Branch | Today | After |
|---|---|---|
| `dedupedKeptDraft` | `We kept the strategy this setup already created, on its original key. To connect different credentials, delete this draft first.` | **Unchanged.** True on both reaching arms. |
| `dedupedHeldOnly` | `We continued with a strategy that already exists for these credentials or this setup instead of creating a duplicate. To connect different credentials, delete that draft first.` | **Unchanged.** Its "or" hedge keeps it true, and it is out of this phase's scope. |
| fallback | `These credentials are already connected. We continued with your existing strategy instead of creating a duplicate.` | `We continued with the strategy this setup already created, on the key it was first connected with. The details you just entered did not change that key. To connect different credentials, delete this draft first.` |

Why each clause holds on both reaching arms (the F6 fence ~:1504 and the post-validation same-session
arm ~:1764):

- **"this setup already created"**: both arms match on `wizard_session_id`.
- **"on the key it was first connected with"**: both return the draft's own `api_key_id`.
- **"did not change that key"**: the F6 arm returns before `validateKey`. The post-validation arm
  returns before `encryptKey` and before the RPC. Neither writes. The sentence describes this
  submission's effect, so it stays true for a double submit whose credentials the first request
  already stored.
- **"checked" and "not saved" are deliberately absent** (HEAD re-measurement row 3, A2). "checked"
  is false on the post-validation arm. "not saved" is false for a resend of credentials the first
  request stored.

The same-session `draft` is **not** in CONTEXT's rotate set. So a changed MT5 password submitted on
the same session lands here, and "did not change that key" is what tells the user the new password
was not applied. Visual is
unchanged: `mb-4 rounded-md border border-border bg-page px-3 py-2 text-caption text-text-secondary`,
neutral, no role.

### 4.1 The 9-state matrix (DESIGN.md §9-State Matrix), for the outcome notice

| State | Notice behaviour |
|---|---|
| loading | Not rendered. The existing wait UI owns this state (§4). |
| empty | Not rendered (no signal). The unnamed sentence covers an absent nickname. |
| error | Not rendered on a seam refusal or any validation error (§4). |
| partial | An outcome without a nickname renders the unnamed sentence (§1.3). |
| success | Rendered: `updated` positive, `unchanged` neutral (§1.4). |
| retry-in-flight | Cleared at submit, so a resubmit never shows the previous response's notice. |
| stale | Cannot occur. The notice is set and cleared from one response and is not persisted (it is never written to the wizard's localStorage). |
| optimistic | Never. The notice renders only from a server response. |
| offline | Not rendered. A request that never completes takes today's hop-failure envelope, and the notice was cleared at submit. |

## 5. Copy audit: every surviving sentence after a write

### 5.1 What renders on each arm (`updated`, nickname `K`)

Exchange display for MT5 is `MT5` (`EXCHANGE_DISPLAY.mt5`). `S` is a strategy name, `D` a draft name,
and `{date}` comes from `formatDay`. The preselect-only bullet of `VENUE_ALREADY_CONNECTED` is
filtered out on this surface (`REQUIRES_PRESELECT_SURFACE`).

| Arm | Notice | Envelope (title / cause; fix and link unchanged) | Ruling |
|---|---|---|---|
| `connected`: `VENUE_ALREADY_CONNECTED` | `We updated the password on your key "K". No new key or strategy was created.` | `This account is already connected to one of your strategies.` / `It is connected to "S". The account behind these details already backs a strategy of yours, … Nothing new was created and the existing strategy was left exactly as it was.` | **True.** The strategies row is not written. The key, not the strategy, changed, and the notice says so. |
| other-session `draft`: `VENUE_DRAFT_IN_PROGRESS` | same | `This exchange account is already in one of your unfinished drafts.` / `Your unfinished MT5 draft "D" already uses this account. … Your new key was not saved.` | **True.** No new key row. The notice's second sentence reconciles "new key" with the password update. |
| `orphaned`: `KEY_ORPHANED` | same | `This key is already stored, but no strategy uses it.` / `You already stored this account as your key "K", added {date}. … Entering this account's credentials again is refused until the saved key is disconnected.` Plus the named bullet (§3). | **True.** The connect is still refused, and a further submit gets `unchanged` plus the same refusal. The named Disconnect bullet is still true for MT5, though it is no longer the only route to a new password. It stays as CONTEXT specifies. |
| `held`: `KEY_VENUE_ALREADY_CONNECTED` | same | `This exchange account is already connected on your account.` / `Your key "K", added {date}, already connects this account.` (or `Your strategy "S" already uses this account.`) `… Your new key was not saved.` | **True**, on the same ground as `draft`. |

For `unchanged`, the same envelopes render, and every sentence holds a fortiori because nothing was
written.

### 5.2 Table copy stays byte-identical

No `WIZARD_ERROR_COPY` title, cause or existing bullet is edited by CONN-02. The only table-adjacent
change is §3's named bullet, built in `formatKeyError`'s existing `KEY_ORPHANED` holder arm (the
per-code interpolation shape, not a new filter).

### 5.3 Copy-honesty obligations for the planner (the copy is true only if these hold)

- **O1. `KEY_MT5_WRONG_SERVER` on the seam path.** Its cause says "the broker server name **you
  entered**". The seam validates against the **stored** login and server. That is the same string
  only on the exact-server fence match. On the null-server legacy fallback, or wherever the typed
  server differs, either the seam must not be reached, or the code it returns must not assert "you
  entered". Pin it with a test on the rotate arm.
- **O2. `SEAM_DEADLINE_EXCEEDED` on the rotate arm.** Its cause ends `Nothing was saved — your key was
  not stored`. The code is raised **in the browser** when `connectAbortDeadlineMsFor(venue)` fires.
  It is sized to give up after the route's validate budget. On this arm the route makes the rotate
  seam call and then the owner-scoped UPDATE. If that path can outlast the browser deadline, the
  route can write after the browser has said "Nothing was saved". The planner either keeps the
  rotate path inside the budget the deadline is derived from, or changes what the deadline answer
  claims on this arm. A test pins whichever is chosen.
- **O3. `KEY_MT5_MASTER_PASSWORD`'s "we refused it and stored nothing"** must hold on the rotate arm.
  The seam raises before re-encrypting, and the Next side must not UPDATE on any seam refusal.
- **O4. The cancelled line** ("the check may still be finishing on our side, and connecting again
  picks up that key rather than storing a second one") stays true. A rotate that finishes after
  `Stop waiting` writes no second key, and a resubmit then gets `unchanged`.

## Assumptions (no human was available; each is Claude's discretion, not a user answer)

- **A1. Notice beside the envelope, not an envelope variant** (§1.1). Cheap to undo: one element in
  one step.
- **A2. The F6 fallback replaces CONTEXT's "not checked or saved" with "did not change that key".**
  The post-validation same-session arm reaches the same branch after `validateKey` ran, so "not
  checked" would be false there. Its callers (a reload, second tab or double submit) usually resend
  credentials the first request already stored, so "not saved" would be false for them. "The details
  you just entered did not change that key" is true on both arms and still tells a user with a
  changed password that it was not applied. This narrows CONTEXT's wording to what every reaching arm
  supports, and adds nothing (Rule 7: surfaced, not blended).

  it with the refusal's `Your new key was not saved.`. Cheap to undo.

  per CONTEXT's "the stored password already works". The other variant is specified for the other
  order.
- **A5. The `KEY_ORPHANED` Disconnect bullet keeps "new credentials"** as CONTEXT specifies, although
  for MT5 an in-place password update now exists. The sentence stays true, and it is no longer the
  only route.
