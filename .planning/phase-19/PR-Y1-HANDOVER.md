## Why this PR exists

The `.github/workflows/supabase-migrate.yml` workflow is structurally broken for this repo. It runs `supabase db push` on every push to `main` that touches `supabase/migrations/**`, but our migration files use sequential numbering (`001_initial_schema.sql`, ..., `132_teaser_anchor_strategy.sql`) while Supabase's tooling expects timestamp-prefixed names (`<14-digit-ts>_name.sql`).

The remote `supabase_migrations.schema_migrations` table currently has a hybrid history:

| Version pattern | Range | Origin |
|---|---|---|
| `NNN` (3-digit sequential) | 001-091 | Applied via Supabase Studio or earlier `apply_migration` calls before timestamp convention took over |
| `YYYYMMDDHHMMSS` (14-digit timestamp) | 32 entries from `20260424012820` to `20260515095804` | Auto-generated by Supabase CLI or by MCP `apply_migration` (which writes a timestamp); names like `093_strategy_verifications`, etc. (match local 092-131 by name, not version) |

`supabase db push` sees this and exits with `"Remote migration versions not found in local migrations directory"` because 32 timestamped versions in the remote aren't matched by `supabase/migrations/<ts>_*.sql` files locally.

Supabase's recommended fix is `supabase migration repair --status reverted <32 timestamped ids>`. But that would mark them as "needs to be reverted then re-applied" — and **the schema changes those migrations represent are already applied to the live DB**. Re-running 092-131 would 23505 / fail / corrupt schema.

The actual fix: **align local file naming with the remote convention** by renaming all 132 local migration files to timestamp-prefixed names, then aligning the `schema_migrations.version` for the 91 sequential entries to synthesized timestamps that match the renamed files.

Eventually the supabase-migrate workflow will fail in even more confusing ways.

### `schema_migrations` table — DB-side reconciliation

For versions `001`-`091` in the remote, the version string is sequential. After renaming local files to timestamps, the schema_migrations.version for those 91 rows must be updated to match the new local timestamps. **This is a UPDATE on a Supabase-managed table** and is the riskiest step. Sequence:

1. Determine the synthesized timestamp for each of the 91 sequential entries. Could:
   - (a) Use the original file's git first-commit timestamp via `git log --diff-filter=A --follow --format=%aI -- supabase/migrations/NNN_*.sql | tail -1`
   - (b) Synthesize sequential timestamps starting from 20260101000000 incrementing by 1 second per entry. Less authentic but trivially safe.
   - Option (b) recommended: less work, ordering is preserved, no risk of weird timestamps.
2. Run `UPDATE supabase_migrations.schema_migrations SET version = '<new_ts>' WHERE version = 'NNN'` for each of the 91 rows.
3. Verify with `SELECT version, name FROM supabase_migrations.schema_migrations ORDER BY version`.

### Naming convention going forward

Adopt the standard Supabase CLI naming: `<14-digit-utc-timestamp>_snake_case_name.sql`. New migrations would be created via `supabase migration new <name>` (which auto-generates the timestamp) OR by writing the file directly.

## Risk flags

- **Editing `schema_migrations` is high-blast-radius.** Test on `qmnijlgmdhviwzwfyzlc` first. Have a rollback SQL ready that restores the previous version values.
- **Supabase CLI version matters.** Old versions may behave differently around the `repair` and `db push` flows.
- **The rename might break tools we don't grep for.** Migration-related grep patterns might be embedded in third-party tools or vendor scripts not searched.
- **PR-Y1 touches 200+ files.** Code review burden is high. Split commits aggressively: (A) file renames only, (B) test updates, (C) doc updates, (D) schema_migrations UPDATE recorded as a follow-up SQL migration `133_align_migration_history.sql`.
