## Critical / High

### 1. A `429` throttle on the allocator's weight optimizer now renders as a permanent refusal that tells the allocator to change their strategy selection

**File:** `src/app/(dashboard)/allocations/components/WeightOptimizerSection.tsx:163`
(copy at `:112-115`)
**Severity:** High — allocator money surface, new false claim, reachable on a
common path.
**Confidence:** High.

```ts
// WeightOptimizerSection.tsx:163
setFailure(res.status >= 400 && res.status < 500 ? "refused" : "unavailable");
```

```ts
// WeightOptimizerSection.tsx:112-115
refused: {
  heading: "The optimizer refused this request",
  body: "The optimizer answered but would not run this request. Change the objective or the selected strategies and run it again.",
},
```

The panel POSTs `/api/scenario/optimize` (`:155`). That route's **own** limiter
fires before anything else:

```ts
// src/app/api/scenario/optimize/route.ts:145-150
const rl = await checkLimit(userActionLimiter, `scenario-optimize:${user.id}`);
…
{ error: "Too many optimize requests. Try again shortly." },
{ status: 429, headers: NO_STORE_HEADERS },
```

`userActionLimiter = makeLimiter(5, "60 s")` (`src/lib/ratelimit.ts:95`).

**Concrete failure:** an allocator iterating in Scenario Composer runs the
optimizer a 6th time inside 60 s. The route answers `429`. `res.status` is in
`[400,500)`, so `failure = "refused"` and the panel says *"The optimizer answered
but would not run this request. Change the objective or the selected strategies
and run it again."* The allocator changes the **selected strategies** — an input
to a money decision — and re-runs; it 429s again; the same sentence repeats. The
one true fact (they are throttled and the remedy is to wait ~60 s) is never
shown.

This is worse than what it replaced. The pre-diff copy was *"The optimizer is
unavailable right now. Try again shortly"* — vague, but its remedy ("try again
shortly") was correct for a 429. The new copy is a specific lie plus active
mis-steering, which is the exact class the phase's own docblock at `:83-100`
argues against ("*a 4xx means the optimizer ANSWERED and refused … the identical
request will be refused identically every time*" — untrue of a 429).

Note the phase itself flagged this endpoint's throttle as sharp: `scenario/optimize/route.ts:154-157`
says */api/optimize-weights is 20/minute … two allocators running Scenario
Composer could 429 each other.*

**Why it slipped:** `WeightOptimizerSection.test.tsx` pins only `400` (`:183-196`)
and `503` (`:172`). No case exercises `429`.

**Fix:** split the throttle out of the 4xx arm before the refusal arm — e.g. a
fourth `OptimizerFailure` member `"throttled"` gated on `res.status === 429`,
whose copy names waiting as the remedy (and, if `SEAMUX-06`'s
`parseRetryAfterSeconds` is wired here, the advertised wait). Consider also that
`401`/`403` land in `"refused"` and are equally mis-advised.

### 2. The scrubber was applied to the Sentry sink and not to its `console` twin, in the same commit, on two routes this diff just gave credentials to — and the SEAMCORE-06 guard is structurally unable to see either

**Files:**
- `src/app/api/verify-strategy/route.ts:384`, `:423-426`, `:440`
- `src/app/api/keys/sync/route.ts:220`, `:265`, `:290`, `:382`, `:439`, `:454`
- Guard roster: `src/lib/seam-log-coverage.test.ts:55-65` (`SEAM_FILES`) and its
  completeness assertion at `:283-303`.

**Severity:** High (a `SUPABASE_SERVICE_ROLE_KEY` in a Vercel log is full
RLS-bypass DB access).
**Confidence:** High on the mechanism; the leak premise is the project's own
stated threat model, quoted below.

`verify-strategy/route.ts` gained three `captureToSentry(..., { secrets: perRequestSecrets })`
calls in this diff. Each is followed **immediately** by a `console.error` that
passes the same value **raw**:

```ts
// verify-strategy/route.ts:379-384
captureToSentry(configErr, { …, secrets: perRequestSecrets });
console.error("[verify-strategy] createAdminClient config error:", configErr);

// :419-426
captureToSentry(persistError, { …, secrets: perRequestSecrets });
console.error("[verify-strategy] CT-3 public_token persist failed:", persistError);

// :436-440
captureToSentry(err, { …, secrets: perRequestSecrets });
console.error("[verify-strategy] CT-3 public_token persist threw:", err);
```

The last two stand over `admin.from("strategy_verifications").update(...)` — an
outgoing request whose headers carry `SUPABASE_SERVICE_ROLE_KEY`. That is exactly
the case `seam-redaction.ts:72-74` cites as its reason for putting that variable
on the env list:

> `SUPABASE_SERVICE_ROLE_KEY` — the admin client's key; **a Supabase transport
> error can inline it, and several seam sites log Supabase errors.**

So by the diff's own model, the Sentry copy of the failure is scrubbed and the
Vercel-log copy of the same failure is not.

`keys/sync/route.ts` has the same shape at `:265` (`console.warn(..., assetClassErr)`
directly above `captureToSentry(assetClassErr, …)`), plus five more unscrubbed
error-shaped bindings (`:220 err`, `:290 rpcError`, `:382 sessionErr`,
`:439 readErr`, `:454 stampErr`).

**Why the guard cannot catch it.** `seam-log-coverage.test.ts` scans a
**hand-typed** 8-file roster and justifies excluding the other seven routes with:

> `SEAM_ROUTE_BUDGETS`: that table lists fifteen ROUTES, **of which only five
> carry credential-bearing error logs** (`:37-40`)

That sentence stopped being true **inside this diff**. Commit `5d48eb81`
(*"forward X-User-Access-Token on both remaining flows (TS-15)"*) put a live
end-user Supabase JWT in scope on `keys/sync` (`:375-386`) and `verify-strategy`
(`:216-224`) — the very credential the guard's own `FAILURE_REASON` string names:

> *"and — on the CSV finalize flow — `X-User-Access-Token`, which is a LIVE
> end-user Supabase JWT"*

The HI-02 completeness assertion (`:283-303`) can't close the gap either: its
membership test is `CREDENTIAL_BEARING_CALLS = ["validateKey(", "encryptKey("]`.
Neither of the two routes calls those, so neither is reported.

**Scanner result (my re-run of the guard's own logic over all 15 seam routes):**
10 of 15 routes have unscrubbed `console.*` error arguments — `bridge:194`,
`simulator:219`, `portfolio-optimizer:126,236`, `scenario/optimize:198,245`,
`admin/match/eval:185,217,245`, `admin/match/recompute:136,172,201`,
`keys/sync` (6 sites), `verify-strategy` (3 sites), `csv-finalize` (8 sites).
Most of those hold no credential; **`verify-strategy` and `keys/sync` do**, and
both were edited by this diff.

**Fix (either, not both):**
1. Add `src/app/api/verify-strategy/route.ts` and `src/app/api/keys/sync/route.ts`
   to `SEAM_FILES` and wrap the eight sites in `scrubSeamError(...)`; **or**
2. Widen the HI-02 membership probe beyond `validateKey(`/`encryptKey(` so a
   route that acquires a session token (`auth.getSession()`) or constructs an
   admin client is pulled onto the roster automatically. The current probe
   enumerates one credential source; the class is "holds a credential".

Also worth noting for whoever takes it: the guard permits `scrubSeamError(err)`
with **no** second argument, so passing a scrubber satisfies it while a
**per-request** secret still ships. That is the same env-vs-per-request asymmetry
HI-03 fixed inside `seam-redaction.ts` but did not fix in the guard.

### 3. Accessibility regression — three `role="alert"` announcements deleted from `PortfolioOptimizer`, replacement surface has none

**File:** `src/components/portfolio/PortfolioOptimizer.tsx:267-297`
**Severity:** Important — explicit DESIGN.md rule, allocator surface.
**Confidence:** High.

`git diff 4b59fb31^ HEAD -- 'src/**/*.tsx' | grep '^[-+].*role="alert"\|^[-+].*aria-live'`
returns **three deletions and zero additions**, all in this file:

```
-            <p className="mt-2 text-caption text-negative" role="alert">   (empty state)
-            <p className="mt-2 text-caption text-negative" role="alert">   (no-candidates state)
-        <p className="mt-3 text-caption text-negative" role="alert">       (results state)
```

`error` is now routed to the "Failed" card at `:267-297`, which renders a plain
`<div>` + two `<p>`s with **no** `role="alert"` and no `aria-live`. There is no
ancestor live region: `OptimizerPanel.tsx` (the only mount site, via
`next/dynamic`) contains no `aria-live` / `role="alert"` / `role="status"`.

**Concrete failure:** a screen-reader user on `/allocations` presses "Run
Optimizer". `/api/portfolio-optimizer` returns 503 with the breaker sentence. The
card silently swaps to the failure state; nothing is announced. Pre-diff the same
failure inserted a `role="alert"` paragraph and was announced. The user is left
with no signal that the run failed.

This contradicts two normative DESIGN.md clauses:
- §Error Envelope, line 317: *"Shell: `role="alert"` + …"*
- §9-State-Matrix A11y minimums (DESIGN-05), line 369: *"ARIA live regions:
  `role="alert"` on blocking errors"*

**Fix:** put `role="alert"` on the failure card's wrapper `div` at `:284`. (The
pre-existing `computationStatus === "failed"` server-rendered path also lacked it,
but that state ships on first paint where an alert is not required; the new
client-driven path is a state *change* and is.)

## Lower impact (reported for completeness, not blocking)

### 4. `seam-redaction.ts`'s plain-object fallback dumps the whole object, defeating the whitelist the docblock claims

**File:** `src/lib/seam-redaction.ts:174-182` vs `:416-427`
**Severity:** Low–Medium. **Confidence:** High that the code contradicts the
comment; low that a credential-bearing shape reaches it in practice.

`PLAIN_OBJECT_DIAGNOSTIC_KEYS` is introduced with:

> *"Nothing else is read. A whitelist rather than a dump is the TRAP-1-safe
> direction: an arbitrary object on this seam can carry a request body, and a
> request body on the key-connect path carries raw exchange credentials."* (`:171-173`)

But when **none** of the seven whitelisted keys is present, `describeThrown`
falls through to:

```ts
const serialised = JSON.stringify(err);       // :420
… serialised.slice(0, MAX_SERIALISED_OBJECT_CHARS)   // 500 chars
```

i.e. it dumps up to 500 characters of the arbitrary object — including exactly the
`{ api_key, api_secret, passphrase }` shape the comment says the whitelist
excludes. `scrubSeamString` still runs over the result, so the leak is bounded to
call sites that do **not** pass `extraSecrets`. The two key-connect routes do pass
them; `resilient-fetch.ts:1489` (body-read arm), and most `finalize-wizard` sites
do not.

Not a demonstrated leak — I could not construct a real throw of that shape on the
seam — but the guarantee the comment states is not the guarantee the code
provides, and the whole file is written to be read as a security contract.

  `verdict.status_code`), the range guard in `VenueTransientHTTPException`
  already admitted the whole 4xx band, and `seamBreakerVerdict` classifies 424 as

  routes take their status from `classifyKeyValidationError`, which discards the
