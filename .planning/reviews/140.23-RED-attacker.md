## A1 — HIGH — the csv-validate raw-message echo is a **rendered** leak, and the redaction leaf is applied to Sentry but skipped on both first-party sinks

**Status: CONFIRMED (MEASURED source chain). Extends the known body-only finding.**

The brief established that `csv-validate/route.ts:274` returns the raw caught
`err.message` in the HTTP body and that a probe saw `INTERNAL_API_TOKEN` in it.
What had not been traced is where that string **goes next**, and it does not stop
at the body.

Chain, every hop read at source:

| # | file:line | what happens |
|---|---|---|
| 1 | `src/app/api/strategies/csv-validate/route.ts:262` | `const message = err instanceof Error ? err.message : "CSV validation failed"` |
| 2 | `src/app/api/strategies/csv-validate/route.ts:273` | `console.error("[strategies/csv-validate] unified path threw:", message)` — **raw**, no scrub |
| 3 | `src/app/api/strategies/csv-validate/route.ts:274` | `csvErrorEnvelope("CSV_UPSTREAM_FAIL", message, {}, 502)` → `human_message` on the wire |
| 4 | `src/app/(dashboard)/strategies/new/wizard/steps/CsvUploadStep.tsx:278-279` | `human_message: data.human_message ?? WIZARD_ERROR_COPY.CSV_VALIDATION_FAILED.title` — **taken verbatim**, no guard |
| 5 | `src/app/(dashboard)/strategies/new/wizard/steps/CsvUploadStep.tsx:492-497` | passed into `<CsvValidationEnvelope>` |
| 6 | `.../steps/CsvValidationEnvelope.tsx:69` | rendered as the panel **title** (`errors.length === 0`, because `debug_context` is `{}` on this arm) |
| 7 | `.../steps/CsvValidationEnvelope.tsx:56` → `:70` | `causeText = envelope.human_message` → rendered **again** as the subtitle |

So the platform token does not merely sit in a JSON body a curious user could
open devtools for — it is **painted into the wizard's error panel twice**, in the
one flow whose whole job is "the upload failed, screenshot this and send it to
support." That is the realistic exfiltration path: a user pastes the error into a
support ticket, a Slack channel, or a public forum.

**The redaction leaf that would stop this is already in the repo and is already
imported by the sibling routes.** Measured coverage across the changed route
files (`scrubSeamError`/`scrubSeamString` count vs `captureToSentry` count):

```
scrub=4  capture=3   src/app/api/keys/[id]/permissions/route.ts
scrub=4  capture=2   src/app/api/keys/sync/route.ts
scrub=2  capture=3   src/app/api/keys/validate-and-encrypt/route.ts
scrub=6  capture=6   src/app/api/strategies/create-with-key/route.ts
scrub=13 capture=11  src/app/api/strategies/finalize-wizard/route.ts
scrub=0  capture=4   src/app/api/strategies/csv-validate/route.ts   ← 
```

`captureToSentry` scrubs at its own chokepoint — verified at
`src/lib/sentry-capture.ts:59-77`, which rebuilds the `Error` with
`scrubSeamString(err.message)`, `scrubSeamString(err.name)` and
`scrubSeamString(err.stack)`. So the shape of the defect is precise and slightly
perverse:

> **The third-party sink (Sentry) is scrubbed. The two first-party sinks — the
> Vercel log line and the HTTP response body the user's browser renders — are
> not.**

`csv-validate/route.ts` is the only changed seam route that calls
`captureToSentry` without ever importing `seam-redaction`.

The route's own header comment (`csv-validate/route.ts:13-18`) asserts
"PER-REQUEST SECRETS AT THIS ROUTE: none. The one credential the outgoing request
carries is `INTERNAL_API_TOKEN`, which is already on `seam-redaction.ts`'s
env-name list". Both halves are true and the conclusion still does not hold — being
*on the list* only helps at a site that *calls the leaf*, and lines 273/274 do not.

**What the attacker gains:** the platform's `INTERNAL_API_TOKEN`. Per
`tenant-claim.ts:31-34`, that token is full `/process-key` auth **and** the HMAC
key for `X-Tenant-Claim`, so holding it means calling the analytics seam directly
as any tenant and minting claims for arbitrary tenant buckets.

**Difficulty:** low for the observation, but gated on producing a *throw* rather
than a classified envelope. `postProcessKey` classifies nearly everything into
`!result.ok` (`csv-validate/route.ts:259`), so line 274 is the residue: a
transport failure or a header-construction `TypeError`. An ordinary user cannot
summon that on demand; they collect it opportunistically during a Railway blip
and it lands in their support screenshot. Treat as **HIGH severity, opportunistic
trigger** — the payoff is the platform credential, so a low trigger rate does not
buy much.

**Fix shape (one line, in-tree idiom):** `scrubSeamError(err)` at both 273 and
274, matching what `keys/sync/route.ts:141` and
`keys/[id]/permissions/route.ts:578` already do.

## A2 — MEDIUM — `safeHumanMessage` was installed on the anonymous surface; the authenticated surfaces render the same field verbatim, and the threat the guard cites originates on the authenticated one

**Status: CONFIRMED (MEASURED). Novel.**

`140.3-12 / TS-17` added a disclosure guard for upstream-supplied prose:
`src/components/landing/VerificationForm.tsx:41-66` — `DISCLOSURE_SHAPES`
(URL / scheme / hostname / `localhost` / IPv4 / bare HTTP status /
`traceback|file "|line \d+|exception|stack`) plus a 200-char cap, exposed as the
exported `safeHumanMessage`.

Its own docblock (`VerificationForm.tsx:25-40`) states why it is needed:

> `process-key-client.ts` forwards a non-2xx upstream body VERBATIM
> (`NextResponse.json(body, {status: res.status})`) … `services/ingestion/okx.py`
> passes `result.get("error")` (raw exchange text) and **`csv_adapter.py` passes
> `str(exc)`**. So the string CAN carry an exception body, and it reaches an
> unauthenticated browser.

Both halves verified independently:

- The verbatim forward is real: `src/lib/process-key-client.ts:646` —
  `response: NextResponse.json(body, { status: res.status })`.
- The `str(exc)` sources are real: `analytics-service/services/ingestion/csv_adapter.py:123`
  and `:136` — `human_message=str(exc)`. `analytics-service/services/ingestion/okx.py:55`
  — `human_message=result.get("error")`.

**The guard is applied at exactly one call site**, the anonymous landing form
(`VerificationForm.tsx:106-107`). Every authenticated consumer of the same field
takes it raw:

- `CsvUploadStep.tsx:278-279` — `data.human_message ?? …`
- `CsvSubmitStep.tsx:193-194` — `data.human_message ?? …`
- `src/components/strategy/ApiKeyManager.tsx:87-88` — `return fields.human_message`

The asymmetry is backwards relative to the docblock's own evidence: the cited
`csv_adapter.py` `str(exc)` source is on the **CSV flow**, which is authenticated
and never touches `VerificationForm`. The anonymous teaser reaches key-validation
prose, not the CSV adapter. So the guard sits on the surface where the named
threat does not originate, and is absent from the surface where it does.

**Honest exploitability.** The two `csv_adapter` arms actually reachable today
are `CsvTooLargeError` (our own sentence) and a `ValueError` for an unknown
`fmt` — both curated, neither juicy. So **this finding's direct payload is low**.
Its value is that it leaves the CSV wizard's render slot ungated as a *class*,
which is what A1 then walks through with the platform token. Rank it as the
structural half of A1, not as an independent extraction.

**Caveat worth stating plainly:** `safeHumanMessage` is a *disclosure-shape*
denylist, not a secret redactor. A bare undici header-error message carrying
`INTERNAL_API_TOKEN` need not match any of the seven shapes and may sit under
200 chars — so **applying `safeHumanMessage` at CsvUploadStep would NOT reliably
stop A1.** The correct fix for A1 remains `scrubSeamError` server-side (A1's fix
shape); `safeHumanMessage` at the authenticated consumers is defence in depth on
top, not a substitute.

## A3 — MEDIUM — global-breaker denial of service, already documented and accepted; the authenticated arithmetic is cheaper than the note implies

**Status: CONFIRMED reachable, but PRE-EXISTING and EXPLICITLY ACCEPTED in-code.
Recorded for completeness, not claimed as a discovery.**

`src/lib/resilient-fetch.ts:473-508` (the `process-key-sync` budget row) already
states the exposure, names it ME-04, and defers the fix to Phase 141. It is also
noted at `.planning/reviews/140.23-SPEC-silent-failure.md:1016`. I am not
re-raising it as new; I am adding the attacker's arithmetic.

Measured constants:
- `BREAKER_FAILURE_THRESHOLD = 5`, window `30s`, `BREAKER_COOLDOWN_S = 30`
  (`resilient-fetch.ts:146,188`).
- The `process-key-sync` row declares `dependencies: []`, so failures key on
  `GLOBAL_BREAKER_KEY = "breaker:railway"` (`seam-discriminator.ts:67`), which
  `breakerKeysFor` appends to **every** call site's check — all fifteen routes.
- `csvValidateLimiter = makeLimiter(20, "60 s")` (`ratelimit.ts:204`).

So an ordinary authenticated user has a 20-per-minute allowance against a budget
whose failures land on the widest key in the system, and needs 5 failures in 30
seconds. Firing 5 concurrent 10 MB uploads that each exhaust the 60 s
`process-key-sync` deadline records 5 transport verdicts (`seamBreakerVerdict`
returns `TRANSPORT`, `counts: true`, global key, `seam-discriminator.ts:376-386`)
within one instant, opening the circuit for every tenant for 30 s. The 20/min
allowance sustains the loop.

**What genuinely defends here, and is worth crediting:** `500` does **not**
count. `seam-discriminator.ts:437-444` classifies `500` as `service-permanent`,
`counts: false`, with the stated rationale that a deterministic fault can only be
cleared by an operator so counting it guarantees a self-sustaining outage. That
closes the much cheaper "post a payload that crashes Python five times" variant
outright. Likewise a user-influenced breaker key is closed: `serviceDependencyOf`
(`seam-discriminator.ts:167-190`) membership-checks against a frozen closed set
and discards anything else with a warning.

The residual is the deadline path only, and it requires the user to actually make
the upstream slow — **INFERRED**, since I did not execute a 10 MB upload against
the live Python service.

## Lanes hunted and REFUTED — these are clean

Recorded with evidence so the next pass does not re-walk them.

**R1 — 404-vs-403 ownership oracle at `keys/[id]/permissions`. REFUTED.**
The route looks like a textbook oracle: `keys/[id]/permissions/route.ts:383`
answers `404 "Key not found"` and `:386` answers `403 "Forbidden"`, and the
select at `:373-377` carries **no** `.eq("user_id", user.id)`. But the read goes
through the user-scoped client (`createClient()`, `:372`) and
`supabase/migrations/20260405061912_rls_policies.sql:22` is
`CREATE POLICY api_keys_owner ON api_keys FOR ALL USING (user_id = auth.uid())`
with no admin OR-clause. A foreign row is therefore invisible, `keyRow` is null,
and control reaches the 404. **The 403 branch is unreachable defence in depth for
an ordinary user.** Worth a note only: `keyId` is not UUID-shape-checked, so a
malformed segment produces a PostgREST cast error → `keyErr` → `500 "Lookup
failed"`, distinguishable from the 404. That distinguishes UUID-validity, which
the attacker already knows. No ownership signal.

**R2 — attacker-influenced breaker key (cross-tenant DoS / shard-to-never-trip).
REFUTED.** `seam-discriminator.ts:167-190` admits only the frozen
`SERVICE_DEPENDENCIES` set and logs+discards anything else; the venue name read
(`seamDependencyName`, `:255-270`) is display-only, slug-bounded
(`/^[a-z0-9][a-z0-9._-]{0,39}$/`), and explicitly excluded from the key path.
`seamBreakerVerdict` never calls `seamCorrelationId`.

**R3 — attacker-controlled `correlation_id` into DOM / clipboard / logs.
REFUTED as an attack.** `CORRELATION_ID_SHAPE = /^[A-Za-z0-9._:-]{1,128}$/`
(`seam-discriminator.ts:104`) excludes CR/LF/NUL, so no log-record splitting and
no markup. React escapes the DOM render (`ErrorEnvelope.tsx:209`). The value is
the attacker's own echoed header, so the clipboard path
(`ErrorEnvelope.tsx:44-59`, which does *not* scrub `correlation_id`) is
self-referential — there is no victim.

**R4 — anonymous teaser leaking upstream internals. REFUTED.**
`verify-strategy/route.ts:452-478` builds an explicit allowlist
(`verification_id`, `public_token`, `expires_at`) rather than spreading the
upstream body, and passes `metrics_snapshot` through `sanitizeMetricsSnapshot`.
The rationale comments name the two prior red-team findings this closed.

**R5 — cross-tenant rate-limit burn at `keys/sync`. REFUTED.** The per-strategy
bucket is `keys-sync:${user.id}:${strategy_id}` (`keys/sync/route.ts:125`) — the
user id is in the key, so a foreign `strategy_id` exhausts only the attacker's own
throwaway bucket. The `keysSyncUserLimiter` ceiling (`:117`) re-caps aggregate
volume so varying the uuid does not bypass.

**R6 — the new `code` tokens re-opening the `keys/sync` existence hole.
REFUTED.** The `.single()` → `.maybeSingle()` split (`keys/sync/route.ts:159-190`)
pulls out only the transport error (`DRAFT_LOOKUP_FAILED`, 500); not-found and
not-owned still both reach the same `GATE_DRAFT_GONE` 404 with a byte-identical
body. The select retains `.eq("user_id", user.id)`, so a foreign id cannot reach
the 500 arm.

**R7 — `debug-key-flow` returning `human_message: String(err)`
(`debug-key-flow/route.ts:295`). REFUTED for the ordinary-user lens.**
Gated at `:71` by `isAdminUser(supabase, user)`.

**R8 — the new unusable-response message reaching a browser. REFUTED.**
`unusableSeamResponseMessage` (`analytics-client.ts:196-204`) echoes only a
lower-cased, 64-char-capped media type, and is thrown with
`UNUSABLE_RESPONSE_STATUS = 502` (`:180`). The one route that forwards an upstream
message to the client does so only for `400 <= status < 500`
(`keys/validate-and-encrypt/route.ts:319-324`), so 502 falls past it into the
static `"Key validation failed."` arm.

**R9 — `mintTenantClaim(payload, secret)` transposition. REFUTED at the two
dangerous sites.** The hazard was real (two adjacent `string`s, the second being
a user-chosen passphrase). It is closed by type: the `validateKey` / `encryptKey`
wrappers take a `TenantIdentity` one-field object (`tenant-claim.ts:88-95`), which
cannot be confused with a credential, so a transposition is a compile error.
The two mint sites pass server-derived values —
`process-key-client.ts:339` (`args.userId`, threaded from each route's `withAuth`
session) and `analytics-client.ts:321` (`options.tenantId`). *Scope note: I
spot-checked the mint sites and the two credential-adjacent wrappers; I did not
exhaustively re-derive `tenantId` for all nine analytics-client wrappers.*

**R10 — the Sentry chokepoint being decorative. REFUTED, it genuinely scrubs.**
`sentry-capture.ts:59-77` rebuilds the `Error` with scrubbed `name`/`message`/
`stack` and folds the `cause` chain in scrubbed rather than re-attaching it
(`:65-68`) — the re-attachment would have been the obvious way to reintroduce the
unscrubbed string. `tags` and `extra` go through `scrubRecord`/`scrubValue`
(`:92-116`).

**R11 — the 400 → 424 remap widening what gets forwarded to browsers. REFUTED,
no widening.** `analytics-service/routers/exchange.py` moved seven
`VenueTransientHTTPException` sites from 400 to 424. Both are inside the
`400 <= status < 500` forward band at
`keys/validate-and-encrypt/route.ts:319-324`, and both are breaker-inert
(`seam-discriminator.ts:398-415`). The forwarded strings remain the curated
`RATE_LIMITED_DETAIL` / `NETWORK_ERROR_DETAIL` module constants.

## Residual I could not close

The non-JSON 4xx arm at `analytics-client.ts:473-483` puts the **raw upstream
response text** into `AnalyticsUpstreamError.message`, which
`keys/validate-and-encrypt/route.ts:324` then forwards verbatim to the browser
for any 4xx. For this to leak anything the analytics service would have to answer
a 4xx with a non-JSON body — a platform edge page (Railway "Application not
found", a proxy 403) rather than the app. I could not demonstrate that shape is
producible on demand by an ordinary user, so I am **not** claiming it; the payload
would in any case be hosting-provider branding, not a credential. Recorded only so
the next pass knows it was looked at and left open.
