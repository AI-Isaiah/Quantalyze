## CRITICAL

### C-1 · The per-request-secret leak class is closed on the Sentry sink and left open on the `console` sink — including inside the core itself

**Severity: Critical · Confidence: 95 (the asymmetry) / 75 (that a credential
actually reaches the line in production)**

Every `captureToSentry(...)` added in this diff that sits in a
credential-bearing scope names its per-request values in `secrets`. The
`console.*` twin standing beside it, in the same commit, frequently does not.
The scrubber is only as good as its second argument, and
`seam-log-coverage.test.ts:213-232` (`bareReferences`) asserts only that a
caught identifier is *wrapped* — never that the second argument is populated —
so `scrubSeamError(err)` and `scrubSeamError(err, [api_key, api_secret,
passphrase])` are indistinguishable to the guard. This is the exact
"assertions written against ENV-derived secrets pass while PER-REQUEST secrets
leak" shape the phase was built to end.

**a) `src/lib/resilient-fetch.ts:1489` — the core's body-read arm. Highest blast
radius; every seam call on every route.**

```ts
: `[resilient-fetch] ${budgetKey}: response body read failed: ${scrubSeamError(err)}`,
```

Its sibling transport arm at `:1797` was fixed by TS-15 and reads
`scrubSeamError(err, credentialHeaderValues(requestInit))`. The body-read arm is
the unfixed member of the same class and *structurally cannot* be fixed in
place: `instrumentBody(res, budgetKey, timeoutMs, recordOnce)`
(`resilient-fetch.ts:1445-1450`) never receives `requestInit`, so
`credentialHeaderValues` is unreachable from it.

Concrete scenario: `strategies/csv-finalize` POSTs `/process-key` with
`X-User-Access-Token: <live end-user Supabase JWT>` (`process-key-client.ts:413-415`).
Railway returns headers and then the body stalls or the connection resets. The
read rejects with a non-`SyntaxError`, and only the five names in
`SEAM_SECRET_ENV_NAMES` are removed — the JWT is not one of them. The docblock
at `resilient-fetch.ts:1369-1394` states the fix as a *class* fix ("any
credential-bearing header the core is ASKED TO SEND is scrubbed … whichever
caller supplied it"); at `:1489` that sentence is not true.

**b) `src/lib/process-key-client.ts:542` — names the JWT, not the request body's
credentials.**

```ts
scrubSeamError(message, [args.userAccessToken]),
```

`args.context` is credential-bearing on the teaser path:
`verify-strategy/route.ts:183-191` builds `teaserContext = { email, exchange,
api_key, api_secret, passphrase }` and it is `JSON.stringify`'d into the
outgoing body at `process-key-client.ts:417-421`. An anonymous landing-page
verification with a live OKX key that hits a transport throw whose message
inlines the request init loses all three. The *same route's* Sentry sites name
all three (`perRequestSecrets`, `verify-strategy/route.ts:248-252`) — the console
sink is the straggler. The `SeamConfigError` arm at `:478` has the same gap.

**c) `src/app/api/strategies/create-with-key/route.ts:409` and
`src/app/api/strategies/composite/add-key/route.ts:386` — the same object,
scrubbed two ways in one file.**

```ts
console.error("… RPC error:", scrubSeamError(error), error.code);              // no secrets
captureToSentry(error, { …, secrets: [api_key, apiSecretNormalized, passphraseOrNull] });  // :440 / :417
```

Both files' *outer* catch (`create-with-key:543`, `add-key:485`) gets it right,
so this is an intra-file inconsistency, not a missing convention. Same class,
lower value: `create-with-key:261` (`existingDraftErr`) and `:504`
(`assetClassErr`).

**d) `src/app/api/verify-strategy/route.ts:384`, `:423`, `:440` — raw caught
values reach `console.error` with **no scrubber at all**, while
`perRequestSecrets` is in scope and each paired capture two lines above uses it.**

```ts
captureToSentry(configErr, { …, secrets: perRequestSecrets });   // :375-380
console.error("[verify-strategy] createAdminClient config error:", configErr);  // :384
```

The comment added directly above the capture says *"a Supabase client
constructor error can inline the key it was handed"* — and the line below it
logs that error verbatim. `SUPABASE_SERVICE_ROLE_KEY` **is** on
`SEAM_SECRET_ENV_NAMES`, so a one-word change (`scrubSeamError(configErr)`)
would cover it; the same applies at `:423` (`persistError`) and `:440` (a thrown
supabase-js transport error, the shape that inlines outgoing headers). This file
is not in `SEAM_FILES`, so the coverage guard never looks at it.

**e) `src/lib/analytics-client.ts:530` — the zod-issue render on the raw-credential
path.**

```ts
scrubSeamString(JSON.stringify(result.error.issues)),
```

The comment three lines above names the exact threat ("a `received` field on a
credential-shaped input") and then scrubs with the env list only. `parseResponse`
has no credential parameter, but `validateKey` (`:570-588`) and `encryptKey`
(`:591-608`) both POST `api_key`/`api_secret`/`passphrase` and then call it. If
`/api/validate-key` drifts so a field typed as an enum receives a
credential-shaped value, zod's `invalid_enum_value` issue carries
`received: "<the value>"` into the Vercel log. (The *thrown* twin is safe —
`validate-and-encrypt:343`, `create-with-key:583`, `add-key:514` all catch it
with `secrets` populated.)

**Suggested fix order:** (a) then (d) — (a) is the core and affects every seam
call; (d) is one word each. Then extend `bareReferences` to require a non-empty
second argument whenever the enclosing function holds a per-request credential;
without that mechanism this class re-opens at the next call site.

**Checked and clean:** all 22 `extra:` payloads (flat scalars, booleans, key-*name*
arrays; no raw body, headers object or parsed credential object anywhere).
`sentry-capture.ts`'s `MAX_EXTRA_DEPTH = 4` is not reachable — `scrubRecord`
enters at depth 0 and the deepest real payload is two levels.

### C-2 · The 400→424 remap puts **permanent caller faults** on the wire as "the caller's exchange is at fault" — a shape `service_error()` itself refuses to construct

**Severity: Critical · Confidence: 90 · Files:**
`analytics-service/routers/exchange.py:619-624`,
`analytics-service/routers/portfolio.py:2354-2359`

140.3-06 / TS-32 remapped all seven `VenueTransientHTTPException` sites from 400
to 424. Both raise sites are **verdict-agnostic** — they fire for *every*
`error_code` `validate_key_permissions` produces, not only venue failures.
`analytics-service/services/exchange.py:1015-1023` lists five of those as
permanent caller faults:

```python
PERMANENT_VALIDATION_ERROR_CODES = {AUTH_FAILED, PERMISSION_DENIED, TRADE_SCOPE, WITHDRAW_SCOPE, MISSING_SCOPE}
```

Live wire output through the real `main.app` handler stack (mocked producer,
real route):

```
WIRE AUTH_FAILED    -> 424 {'detail': 'Authentication failed. Check your API key and secret.', 'code': 'AUTH_FAILED',    'recoverable': False}
WIRE TRADE_SCOPE    -> 424 {'detail': 'This key has trading permissions enabled...',           'code': 'TRADE_SCOPE',    'recoverable': False}
WIRE WITHDRAW_SCOPE -> 424 {'detail': 'This key can withdraw funds...',                        'code': 'WITHDRAW_SCOPE', 'recoverable': False}
```

The same contract module refuses that exact pair on the nested shape — run
against `services/error_contract.py:180-195`:

```
NESTED {'dependency': None}                          -> REFUSED: a 424 must name the venue that failed in `dependency`
NESTED {'dependency': 'binance', 'retryable': False} -> REFUSED: a 424 is recoverable — the venue may come back
```

So `424 + recoverable:false` is **unconstructable** via `service_error()` and is
now the committed, test-pinned wire shape at the highest-traffic 424 emitter —
`analytics-service/tests/fixtures/validate_key_venue_transient_contract.json:135-143`
(`ccxt_auth_failed_permanent_control`) pins `"status": 424, "recoverable": false`.

Three written rules broken, all in `analytics-service/docs/STATUS_CONTRACT.md`:

- §1 table (line 36) — CALLER'S EXCHANGE requires `retryable: true`, "renders as **recoverable**".
- §6 O-1 (line 346) — "`424` is recoverable… It must **NOT** be collapsed into 'caller error, not recoverable'".
- §5 warning box (lines 310-316) — "It does **not** license attributing an arm to
  the venue merely because a venue name is in scope… **The test is whether we
  actually spoke to the venue on that path**". A key with trading scope enabled
  is a verdict reached *after* a successful venue conversation; the venue
  answered correctly.

Note the irony against §5 point 2 (line 323): the stated reason not to use 400 is
that overloading it "destroys the distinction between *'fix your input'* and
*'wait for your venue'*". The remap performs the identical overload in the other
direction — 424 now carries both.

`VenueTransientHTTPException.__init__` (`services/error_contract.py:410-460`) has
only a `400 <= s < 500` range guard and no 424 arm, so nothing catches this. Its
own docstring (line 419) still calls the class "a CALLER-class 4xx by
construction", which is no longer the class it emits.

**Concrete downstream failure.** `src/lib/seam-discriminator.ts:416-423` returns
`attributability: "caller-exchange"` for a user who typo'd their API secret, and
the first consumer written to that contract *already ships in this same diff*:
`src/components/admin/match/venueOutageCopy.ts:71-73` — *"An exchange isn't
responding right now. The fault is at the venue, not in the analytics service.
Retry in a moment."* — wired to `res.status === 424` at
`AllocatorMatchQueue.tsx:269` and `MatchEvalDashboard.tsx:75`.

**Precisely scoped:** this is **not** user-visible on key-connect today.
`classifyKeyValidationError` (`src/lib/wizardErrors.ts:1372`) branches on
`body.code` before status, so `AUTH_FAILED → KEY_AUTH_FAILED/400` and
`TRADE_SCOPE → KEY_HAS_TRADING_PERMS/400` (line 1500) still render correctly. The
defect is on the wire and in every status-driven consumer. Before the remap these
arms were `400 + recoverable:false` — a valid CALLER row. The remap created the
contradiction.

Narrowest fix preserving the plan's intent: keep 424 only when `error_code ∉
PERMANENT_VALIDATION_ERROR_CODES` (the same predicate already computing
`recoverable` on the very next line), 400 otherwise — and add a 424 ⇒
`recoverable` guard to `VenueTransientHTTPException.__init__` so the pair cannot
be reconstructed.
