## 1. Invariants documented in prose but not in the type

### A1 — `RouteResponseError` (`src/lib/route-response-error.ts:37-43`)

The class's stated contract is a *security* predicate:

> Throw `RouteResponseError` when the message was built from a route response —
> its JSON `error`/`code` fields, or its HTTP status/statusText, **both of which
> are ours and carry no upstream detail**.

The type carries none of that. It is `class RouteResponseError extends Error {
constructor(message: string) }` — any string, from anywhere, becomes blessed copy.
"Grep `RouteResponseError` to enumerate every member of this class" (`:43`) is the
enforcement mechanism, in writing.

**The counterexample landed in the same diff.** `src/app/api/admin/match/eval/route.ts:224-227`
and `src/app/api/admin/match/recompute/route.ts:179-182` both now return

```ts
{ error: err.message, dependency: err.dependency }
```

where `err.message` is `AnalyticsUpstreamError.message`, constructed at
`src/lib/analytics-client.ts:465` from the **upstream's** `detail` string. So the
premise "the route's `error` field carries no upstream detail" became false at
commit `7323c388`, one plan after `2d1bf074` wrote it down. The routes are right to
forward it (a 4xx `detail` is operator-curated); the *class* is what is now lying.

Reachability today: the three consumers hit `/api/bridge`,
`/api/portfolio-optimizer` and `/api/keys/[id]/permissions`, all of which answer
with static bodies, so this is **latent, not live**. But the recipe the class
documents is precisely what `src/components/portfolio/ReplacementPanel.tsx:67`
does — `throw new RouteResponseError(body.error ?? \`HTTP ${res.status}\`)` — and
copying that four lines into an admin panel against `/api/admin/match/eval` renders
upstream text as reviewed copy with nothing red.

Fix that fits the codebase: make the constructor private-by-convention and expose
one factory that *takes the evidence*, e.g.
`routeResponseError(body: { error?: string; code?: string }, res: Response)`.
Then a message that did not come from those fields is unconstructible, and the
grep becomes unnecessary. ~15 lines, three call sites.

### A3 — `SeamBreakerVerdict` (`src/lib/seam-discriminator.ts:125-134`)

```ts
/** The verdict. `breakerKey` is non-null exactly when `counts` is true. */
export interface SeamBreakerVerdict {
  readonly counts: boolean;
  readonly breakerKey: string | null;
  …
}
```

The iff is in the comment. The type is a product of a boolean and a nullable, so
three of four combinations are representable and two of those are wrong. Both
consumers pay for it by re-deriving the invariant by hand:

- `src/lib/resilient-fetch.ts:1803` — `if (transportVerdict.counts && transportVerdict.breakerKey !== null)`
- `src/lib/resilient-fetch.ts:1827` — `if (verdict.counts && verdict.breakerKey !== null)`

The failure direction is the bad one. A future arm that returns
`{counts: true, breakerKey: null}` does not throw and does not log — it silently
**skips the record**, so the breaker never trips during a real outage. That is the
exact outcome the module's own comments say twice they will not accept ("would
silently disarm the breaker", `:381` and `:376`). Nothing in the suite would go
red: the recording call simply does not happen.

A discriminated union removes the second conjunct at both sites and makes the drift
a compile error:

```ts
export type SeamBreakerVerdict =
  | { readonly attributability: …; readonly counts: false; readonly breakerKey: null; readonly dependency: null }
  | { readonly attributability: …; readonly counts: true;  readonly breakerKey: string; readonly dependency: string | null };
```

Four return sites in the leaf, two call sites in the core. Low cost, and it does not
touch the leaf's purity.

Secondary, same interface: `dependency: string | null` is typed `string` even though
`serviceDependencyOf` (`:171-189`) membership-checks it against the frozen closed
set before returning it. The union already exists — `SeamServiceDependency`,
`src/lib/resilient-fetch.ts:124` — and `breakerKeyFor(dependency: SeamServiceDependency)`
(`:136`) cannot consume the verdict's field without a cast. The leaf cannot import
the union (purity, correctly), but it can declare its own identical one; that is
already the duplication discipline `seam-constants.pin.test.ts` enforces, and it
would let `SERVICE_DEPENDENCIES` stop being `readonly string[]` (`:75`), which
today narrows to nothing on `.includes()`.

### C4 — `SEAM_ROUTE_BUDGETS.branch` (`src/lib/resilient-fetch.ts:571`)

`branch?: string`, with a 20-line comment above the finalize-wizard row saying
"TWO EXCLUSIVE BRANCHES, and the row must not be read as their sum". The only
consumer that honours it is the test (`seam-budgets.invariant.test.ts:403-416`).
A future consumer that sums `budgets[].calls` over-counts finalize-wizard by 11
seam calls, i.e. computes a headroom figure that is wrong in the unsafe direction.
Expressible cheaply as `budgets: Leg[] | { branches: Record<string, Leg[]> }`,
or by requiring `branch` and typing it as a per-route literal union.

## 2. Widening that lost an invariant

### A4 — `mintTenantClaim` (`src/lib/tenant-claim.ts:118`)

`TenantIdentity` (`:88`) was introduced *in this diff*, with this rationale:

> two adjacent `string`s where a transposition compiles cleanly and mints the claim
> over a USER-CHOSEN SECRET: a credential in an outbound header … That is threat
> T-140.2-09-02 with the compiler unable to help.

The mint function itself, 30 lines below, is exactly that shape:
`mintTenantClaim(payload: string, secret: string)`. And it is the site where the
transposition actually costs something. `mintTenantClaim(internalToken, args.userId)`
compiles, passes all three guards (non-empty; no `.` — a hex token has none;
non-empty secret), and puts **`INTERNAL_API_TOKEN` on the wire as the
`X-Tenant-Claim` payload**, verbatim, while collapsing every caller onto one
limiter bucket — the pre-140.1 defect the whole mechanism exists to remove, plus a
platform credential in an outbound header.

Both producers are correct today (`process-key-client.ts:339`,
`analytics-client.ts:321-324`) and nothing type-level holds them there. The fix is
the one this file already chose one screen earlier: take `TenantIdentity`, or a
single `{ payload, secret }` object. Two call sites.

Note the object *is* used correctly at the outer wrappers — `validateKey` /
`encryptKey` take `tenant: TenantIdentity` and pass `tenantId: tenant.userId` into
a named field (`analytics-client.ts:585,606`). The invariant survives the wrapper
boundary and dies at the primitive.

### B4 — the wait, typed twice, two different ways

`ErrorEnvelope.retry_after_seconds?: number` (`src/lib/envelope.ts:51`) and
`WizardErrorContext.retryAfterSeconds?: number` (`src/lib/wizardErrors.ts:1177`).
Both docblocks argue at length about *absence* (absence means "no wait was
advertised", never zero — correct and well done) and say nothing about the domain.
The domain is positive integer seconds; the type is `number`.

`CircuitOpenError`, in the same diff, enforces exactly that on exactly this quantity
(`src/lib/seam-errors.ts:75`) with the stated reason "the value is forwarded onto
the wire". The envelope field is forwarded onto the wire *and* rendered into user
copy. `parseRetryAfterSeconds` (`src/lib/retry/retry-after.ts:44-47`) admits any
finite positive number, so an edge/WAF `Retry-After: 3.5` — a shape the permissions
route explicitly anticipates ("a 429 from that layer", `keys/[id]/permissions/route.ts:279-289`)
— reaches `ErrorEnvelope.tsx:128` and renders "Try again in 3.5s". Severity is low;
the point is that one phase made two different decisions about one quantity, and the
looser one is the one that reaches a human.

### `ErrorEnvelope.code: string` (`src/lib/envelope.ts:27`)

`buildEnvelope` takes `WizardErrorCode` (`:76`) but the field it writes is `string`,
so any hand-built envelope literal can put anything there. That widening is what
makes A5 possible. See below.

## 3. `AnalyticsUpstreamError` at *two* extensions — is it a bag?

**No, and I would keep the additive shape.** All four fields answer one question
("what did the upstream say"), all are `readonly`, every field has exactly one
producer (`analytics-client.ts:465`), and the one field with a wire consequence
(`status`) is validated at construction with a `RangeError` (`:118-122`). Sibling
error types would be worse: the consumers branch on `err.status` ranges, and
splitting on `seamCode` presence would force every catch ladder to grow an arm.

The smell is not the field count. It is the **parameter list**:

```ts
constructor(
  message: string,
  status: number,
  seamCode: string | null = null,
  dependency: string | null = null,
)
```

Two trailing defaulted `string | null`s, positionally adjacent, semantically
unrelated, and mutually assignable. `new AnalyticsUpstreamError(msg, status, venue, code)`
compiles and produces an error whose machine code is a venue name — which
`classifyKeyValidationError` would then look up in `VENUE_WIRE_CODE_TO_VERDICT`
and miss, falling silently to the substring cascade. A third extension makes it
three adjacent nullable strings and the transposition space grows quadratically.
That is the same argument `TenantIdentity` made, in this diff, and it should be
applied here **before** the next field: keep `(message, status)` positional and
take the rest as one named options object.

**And there is a next field, already argued for and not applied.** The justification
for carrying `dependency` on the class (`analytics-client.ts:87-93`) is:

> It has to be carried HERE because this is where the body dies: the route handlers
> downstream see only the thrown error, so a `dependency` not read at this line is
> unreachable to every consumer.

That is word-for-word true of `correlation_id`. `seamCorrelationId` exists
(`seam-discriminator.ts:321`) and is called at exactly one place — `SubmitStep.tsx`,
on a **raw response body**, on the wizard path where no `AnalyticsUpstreamError` is
in play. Every route that catches `AnalyticsUpstreamError` has already lost the
upstream correlation id at line 465, so the diagnostic 140.1-04 "relocated rather
than deleted" is still deleted on those paths. Flagging it as the predictable third
extension, not asking for it now.

## 4. Boundaries where two vocabularies meet without a total mapping

### A2 — `RATE_LIMITED` means two different things and the classifier does not ask which (LIVE)

`src/lib/wizardErrors.ts:1320-1327` states the collision plainly:

> `RATE_LIMITED` IS IN TWO WIRE VOCABULARIES WITH TWO MEANINGS … Telling them apart
> needs the upstream STATUS (400 vs 429), which this function still discards — that
> is TS-32 / TS-34's, deliberately not smuggled in here.

So it is a recorded residual. What has not been stated is that it is **live and
mis-attributing right now**, and that the type is why it looks deferrable.

`classifyKeyValidationError` (`:1372`) reads `error.seamCode` (`:1422`) and never
`error.status`, which is right there on the same object. The app-global limiter
emits a flat `{code: "RATE_LIMITED"}` at 429 (`analytics-service/main.py`, per
`STATUS_CONTRACT.md` §2.1); `seamErrorCode` reads flat top-level codes
(`seam-discriminator.ts:206-210`); `analytics-client.ts:465` puts it on the error.
So **our own limiter refusing a key-connect request renders KEY_RATE_LIMIT**:

> "The exchange rate-limited this request. … This is a transient, exchange-side
> throttle and not a problem with your key." (`wizardErrors.ts:464-474`)

That is the "blames a venue for our own limit" outcome the same file names as the
reason the two tables must stay separate. Reachable from `create-with-key` and
`composite/add-key` — the two key-connect routes, i.e. the money surface. The
sibling route already fixed the identical problem the right way by gating on
`seamFailure.status === 429` (`keys/[id]/permissions/route.ts:470`), so the remedy
is in-repo and one branch long.

The type-design contribution: both tables are keyed `string`
(`ReadonlyMap<string, …>`, `:1337` and `:1551`). If the two wire vocabularies were
two *types* — `VenueContractCode` and `AppGlobalCode` — `"RATE_LIMITED"` appearing
in both would be a visible declaration-site collision rather than a paragraph, and
a lookup that takes only a code without a status would not type-check.

### A5 — `CSV_INVALID_FORMAT`: the calibration example, second instance, and this one has no test

`src/app/api/strategies/csv-validate/route.ts:67` declares
`csvErrorEnvelope(code: string, …)` and emits `"CSV_INVALID_FORMAT"` at `:119`,
`:124`, `:141`, `:156`; `src/app/api/strategies/csv-finalize/route.ts:127,141`
emits it too, and *types it as a literal there*. **`CSV_INVALID_FORMAT` is not a
member of `WizardErrorCode`.** The union has `CSV_INVALID_EXTENSION`,
`CSV_PARSE_FAILED`, `CSV_SCHEMA_VIOLATION`, `CSV_VALIDATION_FAILED` — not this one.

Same shape as `COMPOSITE_UNSUPPORTED_UNIFIED`, different branch, and with two
differences that make it worse:

1. **Nothing pins it.** `COMPOSITE_UNSUPPORTED_UNIFIED` at least has a recorded
   negative pin (`SubmitStep.test.tsx:540`, added at `39ea3b20` this phase).
   `CSV_INVALID_FORMAT` has none; I could not find a test on either side that
   observes the code crossing the boundary.
2. **The copy and the code can disagree.** `CsvUploadStep.tsx:277-281` builds
   `{ code: data.code ?? "CSV_VALIDATION_FAILED", human_message: data.human_message
   ?? WIZARD_ERROR_COPY.CSV_VALIDATION_FAILED.title }` — two independent `??`
   fallbacks over one envelope. A route that sends a code and no message (or the
   reverse) produces an envelope whose `code` says `CSV_INVALID_FORMAT` and whose
   sentence is `CSV_VALIDATION_FAILED`'s. The type permits it because both fields
   are `string` and independently optional.

The funnel consequence is stated by `WizardErrorCode`'s own comment
(`wizardErrors.ts:276`): "Code IDs are STABLE — renaming breaks PostHog
`wizard_error { code }` events". That declares the funnel's vocabulary to *be*
`WizardErrorCode`. `CsvUploadStep.tsx:289` posts `code: errEnvelope.code` — a
`string` — into that funnel. So the funnel's domain is already wider than the
declaration says, silently, on the CSV branch.

### B3 — the wire vocabulary is untyped on both sides

Python: `service_error(status_code, code: str, …)` (`error_contract.py:274`) and
`VenueTransientHTTPException(code: str)` (`:410`), guarded only for non-emptiness
(`:444-450`). TypeScript: `seamErrorCode` → `string | null`, and every consuming
table keyed `string`. No enumeration exists anywhere.

Consequences, all silent:
- a code minted in Python that no TS table knows → `UNKNOWN` (by design) —
  **indistinguishable from a typo**;
- a code deleted in Python → a dead row in a TS map, nothing red;
- the two maps' domains overlap (A2) with no way to see it.

The `validate-key-venue-transient-parity` fixture pins the six venue codes
cross-language, which is the right instrument and covers one of the two
vocabularies. The app-global set (`VALIDATION_FAILED`, `RATE_LIMITED`) and the
Next-authored set (`CIRCUIT_OPEN`, `UPSTREAM_TIMEOUT`, `UPSTREAM_NETWORK_ERROR`,
`SEAM_MISCONFIGURED`, `COMPOSITE_UNSUPPORTED_UNIFIED`, `draft_state_invalid`,
`CSV_INVALID_FORMAT`, `PROBE_RATE_LIMITED`, `PROBE_FAILED`,
`PROBE_BACKEND_UNAVAILABLE`) have no equivalent. Note the casing is not even
consistent — `draft_state_invalid` is snake_case among SCREAMING_SNAKE peers,
which is itself evidence the set was never enumerated.

Recommendation, cheap and in-repo style: one exported `type SeamWireCode = …` union
in `seam-discriminator.ts` (it stays a leaf — a type costs no bundle bytes), type
the route envelope bodies' `code` with it, and let `recogniseSeamErrorCode` become
`(c: SeamWireCode) => WizardErrorCode`, i.e. a **total** function. Adding a wire code
then forces a decision about its render code at the declaration.

## 5. Guards enforced by test where the type could carry it

### C1 — `KNOWN_FINALIZE_CODES` is misdeclared, and that is *why* `COMPOSITE_UNSUPPORTED_UNIFIED` is a `TS2769`

`src/app/(dashboard)/strategies/new/wizard/steps/SubmitStep.tsx:148`:

```ts
const KNOWN_FINALIZE_CODES: ReadonlySet<WizardErrorCode> = new Set<WizardErrorCode>([…]);
```

The declared element type is the **render** vocabulary. The set's actual job, stated
in the comment two lines above it and again at `:200-209`, is to answer "did
`finalize-wizard` emit this?" — a question about the **wire** vocabulary. The type
is wrong about what the set *is*. That is the whole of the `TS2769`: admitting a
real wire code to a set typed by render codes cannot type-check, and it never
should — the compiler is correct and the declaration is not. Framing it as
"COMPOSITE_UNSUPPORTED_UNIFIED needs to become a WizardErrorCode" accepts the wrong
premise and would mint a render code for a condition with no copy.

Three further consequences visible at HEAD:

- The set is **declared inside the submit callback**, so it is rebuilt on every
  submit and is invisible to any test that does not drive the component.
- Nothing binds it to the route. It has gone stale twice in this phase alone, and
  both fixes carry a comment admitting it: `"COMPOSITE_TOO_MANY_MEMBERS"` (`:163-171`)
  and `"SEAM_MISCONFIGURED"` (`:180-191`), each saying it is "admitted HERE IN THE
  SAME COMMIT that the route started emitting it … without this line … the whole
  obligation ships invisible while every route-side test is green." Two instances of
  one class, each closed by hand, is the shape this programme exists to stop.
- `candidate as WizardErrorCode` at `:210` is a cast used to *ask the question the
  set is supposed to answer* — the standard smell of a `Set<T>.has()` whose element
  type does not match its domain.

Shape that carries it: `finalize-wizard/route.ts` exports its own emitted-code
tuple as a `const` assertion; `SubmitStep` imports it and derives the set. Then a
route arm emitting an unlisted code is a type error, the set cannot go stale, and
`COMPOSITE_UNSUPPORTED_UNIFIED` is admitted to the *wire* set (where it belongs)
while `recogniseSeamErrorCode` remains the one place it resolves to `UNKNOWN`
— by an explicit table row rather than by falling off the end.

Same class, second site: `ConnectKeyStep.tsx:190` describes itself as carrying a
copy of this shape.

### C2 — `EXPECTED_TABLE_SIZE = 55`, twice

`src/lib/wizardErrors.test.ts:1348` and `:1491`. Two hand-typed literals for one
fact, in one file.

The guard's stated purpose (`:1339-1347`) is two properties: (a) the table did not
shrink to vacuity, (b) the reasoning was re-run over new entries. Property (a) is
**already carried by the type**: `WIZARD_ERROR_COPY: Record<WizardErrorCode, WizardErrorCopy>`
(`wizardErrors.ts:280`) is exhaustive, so an entry cannot be deleted without deleting
the union member, and the export cannot be replaced by `{}` — `npx tsc --noEmit` is
the falsifier and it is exit 0 at HEAD. Property (b) is a human process and a size
literal cannot express it; what the literal actually does is force a diff-time
prompt, which is legitimate but is one property, not two.

I would **not** delete it — the prompting effect is real and the comment about not
deriving it from `Object.keys` is correct. I would (i) declare it once and share it
between the two suites, and (ii) say in the comment that shrink-to-vacuity is
covered by the `Record<>` annotation, so a future reader does not think the literal
is load-bearing for a property it is not.

### C3 — `EXPECTED_EXPORTS` set-equality

`seam-discriminator.purity.test.ts:104` (5 members), `seam-copy.purity.test.ts:79`
(1), `seam-errors.purity.test.ts:77` (2). **Keep these.** "Nothing else is exported
from this module" is not expressible in TypeScript, the set-equality-not-count
reasoning is right (a rename passes a count), and the failure message names the
decision to record. This is the best guard in the diff.

One observation, not a request: the purity assertions themselves are regexes over
source text (`/^\s*import\s/m`, `/\brequire\s*\(/`, `/process\.env/`,
`seam-discriminator.purity.test.ts:123-160`). They are defeated by `await import(…)`,
by `globalThis.process`, and by any string concatenation — none of which is an
adversary here, but the repo already ships custom ESLint machinery
(`eslint-local-rules/rules/no-raw-analytics-fetch.mjs`, extended in this diff), so a
structural `no-restricted-imports` override scoped to the three leaf paths would
guard the same property against the module graph rather than the bytes. The
export-set assertion should stay either way — ESLint cannot see it.

## 6. Per-type ratings

### `src/lib/seam-discriminator.ts` — the leaf

- **Encapsulation 9/10.** `nestedDetail` and `serviceDependencyOf` are private and
  the rationale for keeping them private is recorded (`:283-296`); the
  frozen `SERVICE_DEPENDENCIES` cannot be mutated by a consumer; the export set is
  pinned. The one deduction: `SERVICE_DEPENDENCIES` is typed `readonly string[]`
  rather than a union, so the closed set is closed at runtime and open at compile
  time.
- **Invariant expression 6/10.** The two central invariants — "a breaker key comes
  only from the closed set" and "`breakerKey` is non-null iff `counts`" — are
  enforced by code and stated in prose respectively. The first is genuinely well
  built (the key is constructed from a module-private prefix plus a
  membership-checked value, never interpolated from the wire). The second is the
  A3 gap.
- **Usefulness 10/10.** This is the right decomposition: status-line-first
  classification, body only as refinement, and the `424`/`429` split is load-bearing
  for real money paths. `seamDependencyName` vs `serviceDependencyOf` — same wire
  field, two disjoint admissible sets, opposite directions, both membership-checked
  — is exactly the kind of distinction that prevents a lie at a render.
- **Enforcement 8/10.** Total by construction (every arm returns; `null` rather than
  throw, because it runs inside catch blocks). `CORRELATION_ID_SHAPE` and the venue
  slug regex are anchored at both ends and bounded. Deduction for A3 and for the
  fact that a caller can pass a non-integer `status` and get `TRANSPORT` silently —
  correct behaviour, but it means the function's `number | null` parameter accepts
  values the docstring says cannot occur.

### `AnalyticsUpstreamError` (`src/lib/analytics-client.ts:65`)

- **Encapsulation 7/10.** All fields `readonly`; one producer. But the class is
  read *structurally* by design at `wizardErrors.ts:1422`
  (`(error as { seamCode?: unknown })?.seamCode`) to survive wholesale mocks — a
  defensible trade, explicitly reasoned, that nonetheless means the field is part
  of a public duck-type contract that no type expresses.
- **Invariant expression 5/10.** See §3: two adjacent defaulted `string | null`
  parameters make a transposition undetectable, and `null` carries two different
  meanings across the two fields ("the body carried none" vs "a venue failed and
  the wire did not say which"), both documented, neither typed.
- **Usefulness 9/10.** The additive choice is right. `dependency` in particular
  earns its place: it is the last line at which the body exists, and the
  alternative (sniffing it out of `message` later) is the defect class C-6 caught.
- **Enforcement 6/10.** `status` is validated with a `RangeError` and the reason is
  recorded. `seamCode` and `dependency` are validated *upstream* by the leaf's
  extractors and not at all here, so a direct construction (a test helper, a future
  caller) can put anything in either.

### `src/lib/seam-copy.ts`

- **Encapsulation 10/10.** One export, purity-guarded, alias-not-second-export is
  the correct call and the reasoning at `:57-63` is exactly right — a second export
  would create a second thing that can drift.
- **Invariant expression 4/10.** "This string is reviewed, publishable copy" is the
  invariant, and the type is `string`. Contrast `RouteResponseError`, introduced in
  the same phase to express nearly the same predicate as a *class*. Two mechanisms
  for one property, neither aware of the other.
- **Usefulness 9/10.** It closed a real production↔production drift gap
  (ten independent declarations, none exported). The "do not point the twelve test
  literals at this module" note (`:40-48`) is correct oracle discipline and worth
  preserving verbatim.
- **Enforcement 8/10.** `seam-copy.pin.test.ts` asserts repo-wide single
