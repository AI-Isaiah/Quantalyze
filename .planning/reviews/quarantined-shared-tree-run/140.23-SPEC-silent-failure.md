## F1 — HIGH. The seam's one observability chokepoint is the fire-and-forget pattern two prior reviews already removed from this repo

**Location:** `src/lib/sentry-capture.ts:144-158`

```ts
void import("@sentry/nextjs")
  .then((Sentry) => {
    try { Sentry.captureException(payload, { tags, extra, level: ... }); }
    catch { /* Swallow — caller already logged via console.error / warn. */ }
  })
  .catch(() => { /* Sentry import failed — swallow. */ });
```

`captureToSentry` returns `void`. Nothing awaits the dynamic import, the capture,
or the transport. Three empty `catch` blocks (`:152`, `:156`, `:159`) guarantee no
trace is left when any of them fires.

**This repo has already ruled on this exact pattern, twice, and written it down:**

`src/lib/preferences.ts:266-270`

> `F-02 (specialist-review 2026-05-26): the prior `void import(...)` pattern
> detaches the Sentry promise before captureException resolves. On a Vercel
> cold-finish the lambda can be reaped before Sentry flushes — same failure mode
> fixed in audit.ts NEW-C10-03. Await the import chain so the `waitUntil` window
> stays open until the capture settles, then throw.`

`src/lib/audit.ts:963`

> `NEW-C10-03: await so the `waitUntil` window stays open until capture settles.`

Corroborating evidence, run:

```
$ grep -rn "Sentry.flush\|withSentryConfig" next.config.ts src/ instrumentation.ts
(no matches)
```

So there is no `flush()` anywhere in the repo, and `next.config.ts` does not wrap
with `withSentryConfig` — meaning the Sentry Next SDK's automatic route-handler
wrapping (which is what normally calls `flush()` through `vercelWaitUntil`) is not
installed. `Sentry.init` is called manually.

**Concrete scenario.** `/api/admin/match/recompute` catches an unclassified
upstream error, calls `captureToSentry(err, …)` at `route.ts:198`, then
immediately `return NextResponse.json(…, {status: 500})` at `:202`. On Fluid
Compute the instance can freeze the moment the response is written. The dynamic
`import("@sentry/nextjs")` may not even have resolved. The event is dropped and
nothing anywhere records that it was.

**Why this is a 140.2/140.3 finding and not merely pre-existing.** The `void
import` predates the diff, but this phase made `captureToSentry` *the* seam
observability chokepoint and routed **nine more routes** through it
(`00aeddbc` + `b22a2047`, SEAMUX-08). It multiplied the blast radius of a defect
class the codebase had already closed elsewhere, while the file's own docblock
(`:29-34`) argues the chokepoint exists because "the caller will remember" is not
an acceptable control.

**NEW ASPECT of the known "Sentry ingestion never verified end-to-end" item:**
this is a *mechanism* for why ingestion may be failing, independent of the breaker
short-circuit confound. Note also the trap it creates for that verification: every
`catch` here is empty, so "no event arrived" is not distinguishable from "no
capture was attempted" — the absence-shaped evidence problem, applied to the
instrument you would use to measure it.

**Recommendation.** Make `captureToSentry` return the promise, `await` it (or
`after(...)` it) at call sites that return immediately afterwards, and add
`Sentry.flush(2000)` — matching `audit.ts` / `preferences.ts`. At minimum, replace
the three empty catches with a `console.warn` so a dropped capture is observable.

## F2 — HIGH. A probe that did not run renders as a confident scope verdict about a money-bearing key

**Locations:**
- `src/components/connect/KeyPermissionBadge.tsx:250-253` (the pills)
- `src/components/connect/KeyPermissionBadge.tsx:255-261` ("Detected … from the exchange")

140.3-07 / SEAMUX-09 closed the sibling case in this very file — its own comment
at `:87-96` states the harm exactly:

> "Without this, 'Re-check' during an outage left the previous Read/Trade/Withdraw
> verdict rendered beside the error — **a stale SECURITY claim about a
> money-bearing key, read as a current fact about its scope**."

The `probe_error: true` case is the *same class* and was left open. When the
upstream answers 200 with `probe_error: true`, the component takes the `perms &&`
branch and renders:

1. the correct summary sentence ("Could not contact the exchange to verify
   scopes…") — good; then
2. **three definitive pills** built from scope booleans that describe nothing; then
3. `Detected <relative time> from the exchange.` — a provenance claim about an
   exchange that was never reached.

**Concrete scenario A (ccxt keys — Binance, Bybit, Deribit, OKX).**
`analytics-service/services/key_permissions.py:60-65`:

```py
_FAIL_CLOSED: PermissionDict = {
    "read": True, "trade": True, "withdraw": True, "probe_error": True,
}
```

A Binance API blip during a re-check ⇒ the badge renders **`Trade ✓` and
`Withdraw ✓` in `text-negative` (red)**, which by the component's own docblock
(`:51-56`) means "wrong scope, key should be re-keyed". A user with a perfectly
read-only key is told, in red, that it holds trade and withdraw permission.

**Concrete scenario B (sFOX).** `analytics-service/routers/internal.py:415-421`
and `:427-432` return `read/trade/withdraw = False` with `probe_error: True` ⇒
the badge renders `Read ✗` in red, and the summary logic's "wrong-scope" fallback
copy for that shape is "⚠ No read permission detected on this key. The key may
have been revoked or scoped wrong." — except the summary is suppressed by the
probe-error branch, so the user gets the correct sentence *and* three pills that
say the key is dead.

Note the two fail-closed shapes are **opposites** (`True,True,True` vs
`False,False,False`) and the badge renders both as verdicts.

The `detected_at` timestamp is present on all six emitter arms (verified at
`routers/internal.py:368, 384, 406, 420, 432, 517`), so
`KeyPermissionsPayloadSchema` parses cleanly and the misleading render is reached
— the schema work in 140.3-03 does not block it.

**The gate is fine.** `finalize-wizard/route.ts:521` checks `probe_error` before
the scope gate at `:533`, so publish correctly fails closed. This is a *render*
defect, not a gate defect — but it is a false security claim shown to the owner
of a live exchange credential, and the plausible user response is to revoke and
re-key a credential that was never the problem.

**Recommendation.** Suppress the pills and the `detected_at` line when
`perms.probe_error` is true, or render them in an explicit unknown state. Do not
fix this by changing `_FAIL_CLOSED` — the gate depends on it.

## F4 — MEDIUM-HIGH. A failed dependency peek is indistinguishable from "no dependency named", and keys the GLOBAL breaker

**Location:** `src/lib/resilient-fetch.ts:1567-1579`

```ts
async function readDependencyBody(res: Response): Promise<unknown> {
  if (res.status !== 503) return undefined;
  if (typeof res.clone !== "function") return undefined;
  try { return await res.clone().json(); }
  catch {
    // … Deliberately NOT logged …
    return undefined;
  }
}
```

The clone shares the request's `AbortSignal.timeout` — the file says so itself at
`:1555-1558`: *"The read is bounded by the same `AbortSignal.timeout` deadline as
the request, because the clone shares the underlying stream."*

**Concrete scenario.** The MT5 gateway is down. `POST /api/validate-key` runs on
the 30 s `validate-key` budget (the slow live-exchange probe). Railway answers
`503 {"detail":{"dependency":"mt5-gateway", …}}` at t≈29.8 s. The clone read
aborts on the shared deadline ⇒ `undefined` ⇒ `seamBreakerVerdict(503, undefined)`
⇒ `serviceDependencyOf` returns `null` (`seam-discriminator.ts:171-189`) ⇒
`breakerKey = "breaker:railway"`, the residual global key. Five of those and
`breakerKeysFor` (`resilient-fetch.ts:804-806`) appends the global key to every
call site, so `/api/bridge`, `/api/simulator`, `/api/portfolio-optimizer`,
`/api/scenario/optimize`, `csv-finalize` and the anonymous landing-page teaser are
all short-circuited for the cooldown — by an MT5 outage none of them can touch.

That is verbatim the A-01 harm ("one MT5 gateway restart denying every Deribit
user, the optimizer and CSV finalize") that `BREAKER_KEY`'s own docblock at
`resilient-fetch.ts:87-96` claims was fixed by per-dependency keying.

**The absence-shaped half.** The `seam.breaker.open` event at
`resilient-fetch.ts:922` prints `breakerKey: "breaker:railway"` and is
**byte-identical** to a genuine transport-caused global trip. Nothing anywhere
distinguishes "the wire named no dependency" from "we failed to read the one it
named". Contrast `seam-discriminator.ts:181-187`, which emits a loud `console.warn`
for the adjacent case (a dependency outside the closed set) for exactly this reason.

The docblock defends the shrug on the grounds that the peek "can only ever make
the key MORE specific; it can never decide whether to record". True — but it does
decide **which cohort is denied**, which is the entire purpose of per-dependency
keying.

Secondary: `await readDependencyBody(res)` at `:1826` blocks on the tee before the
caller ever receives the response, so on a degraded upstream it consumes the
remaining budget and *then* returns `undefined`.

**Recommendation.** One `console.warn` in that catch naming the budget key and
"dependency unreadable — keying global". Two lines, and it converts a silent
A-01 regression into a measurable one.

## F5 — MEDIUM-HIGH. Our own rate limiter is rendered to the user as the exchange throttling them

**Location:** `src/lib/wizardErrors.ts:1343`

```ts
["RATE_LIMITED", { code: "KEY_RATE_LIMIT", status: 503 }],
```

The docblock two paragraphs above (`:1320-1327`) names the hazard precisely:

> "`RATE_LIMITED` IS IN TWO WIRE VOCABULARIES WITH TWO MEANINGS … Merging the two
> tables would force one answer onto both producers and **blame a venue for our
> own limit**, or the reverse. Telling them apart needs the upstream STATUS
> (400 vs 429), which this function still discards."

The two tables were kept separate — but `VENUE_WIRE_CODE_TO_VERDICT` is consulted
on the `seamCode` alone, regardless of status, so the merge happens anyway.

**Concrete, fully-traced scenario.**

1. `/api/validate-key` is slowapi-rate-limited — `analytics-service/routers/exchange.py:468-472`:
   `@router.post("/validate-key")` immediately followed by `@limiter.limit(...)`.
2. The app-global 429 handler emits `{detail: "<scalar>", code: "RATE_LIMITED"}` —
   `analytics-service/main.py:445-448`: *"The replacement carries BOTH a scalar
   `detail` string AND `code:"RATE_LIMITED"`"*.
3. `analytics-client.ts:465-470` builds
   `AnalyticsUpstreamError(msg, 429, seamErrorCode(body) === "RATE_LIMITED", null)`.
4. `create-with-key/route.ts:558` → `classifyKeyValidationError(err)` →
   `wizardErrors.ts:1424-1431` → `VENUE_WIRE_CODE_TO_VERDICT.get("RATE_LIMITED")`
   → `{code: "KEY_RATE_LIMIT", status: 503}`.
5. `wizardErrors.ts:464-474` renders:
   > **"The exchange rate-limited this request."**
   > "The exchange asked us to slow down. This is a transient, **exchange-side**
   > throttle and not a problem with your key."

The truthful member exists two hundred lines away and says the opposite —
`wizardErrors.ts:1073-1082`: *"You have reached **our** request limit … the cap is
ours, not your exchange's."*

**Why it belongs to this phase.** The pre-140.3-05 cascade reached the same wrong
answer by accident (`lower.includes("rate")`). 140.3-05 replaced the accident with
an explicit, hand-typed table entry — the lie is now deterministic and enshrined,
and the discriminating fact (`err.status` — 429 for our limiter, 424/400 for the
venue) is *already on the object being classified*. SEAMUX-04's stated obligation
is "our outage is never reported as the user's, and the user's venue is never
reported as ours" (`venueOutageCopy.ts:54-56`); this is the second half of that
sentence, unmet.

**Recommendation.** Read `(error as {status?: number}).status` alongside
`seamCode` — same `typeof` idiom, same mock-survival property — and route
`429 + RATE_LIMITED` to the `RATE_LIMITED` wizard member.

## F7 — MEDIUM (latent). The Sentry scrub's depth cap returns the value UNSCRUBBED

**Location:** `src/lib/sentry-capture.ts:95`

```ts
function scrubValue(value, secrets, depth) {
  if (depth > MAX_EXTRA_DEPTH) return value;   // MAX_EXTRA_DEPTH = 4 (:50)
```

Every other cap in this diff *replaces* the over-limit value — `seam-redaction.ts:358`
returns `"…"`, `:423` returns `…[truncated]`. This one passes the original through.

`@sentry/nextjs`: a secret passed as `secrets: [secret]` at depth 5 was dispatched

today**, so this is latent, not a live leak. It is still a hole in the one control
whose docblock (`:29-34`) argues it exists because callers cannot be trusted to
remember, and the fix is `return "[depth-capped]"`.

## F9 — MEDIUM. The Sentry scrub drops every custom own property from the error

**Location:** `src/lib/sentry-capture.ts:70-77`


so the same payload is diagnosable through the log path and blanked through the

**Recommendation.** Copy the original's own enumerable properties onto `rebuilt`,
scrubbed through `scrubValue`.

## Suggested order of attack

1. **P1 + P2 are one fix** — the collapse sites need the verdict→class mapping the
   single-condition arms already have (venue codes → 424; credential/scope codes →
   400/403; our-infra codes → 503 `dependency="mt5-gateway"`). Routing
   `VenueTransientHTTPException` through `_validate` is what would have caught both
   mechanically.
2. **F1** — `captureToSentry` flush/await. Until this is fixed, no absence of a
   Sentry event proves anything, including for the other findings here.
3. **F2** — suppress the pills + `detected_at` when `probe_error` is true. Small,
   and it is a false red security claim about a live credential.
4. **F3** — branch on `SeamConfigError` / `TenantClaimError` in the analytics-client
   consumer routes. One class, currently fixed at one of two clients.
5. **F4** and **F6** — two one-to-two-line changes that turn silent seam behaviour
   into measurable seam behaviour.
6. **F5** — read `err.status` beside `seamCode`; stop blaming a venue for our limiter.
7. **F8** — thread `retryAfterSeconds` into `buildEnvelope` at the three wizard
   surfaces that drop it.
8. The rest (F7, F9–F14, P3–P8) as capacity allows; F7/F12/F13 are latent-by-measurement
   and should be fixed for invariant integrity rather than for a live incident.
