## Answer to the question that matters most

**Mostly they describe illegal states rather than forbid them — but the diff contains one genuinely excellent counter-example that shows the authors know how.**

`ProbeParseMiss` (`src/app/api/strategies/finalize-wizard/route.ts:142`) is the counter-example and it should be the template for the rest. `fetchLivePermissions` returns `LivePermissions | ProbeParseMiss`; the miss sentinel carries `probe_error: true` as a *literal* and carries **no scope fields at all**. The gate at `:521` (`if (livePerms.probe_error)`) therefore narrows `ProbeParseMiss` out of the union before `:533` reads `livePerms.trade`. A parse miss cannot present a scope verdict — not by discipline, by construction, and it survives reordering of the gates. That is the standard. Very little else in the diff meets it.

The dominant pattern elsewhere is: the invariant is discovered, argued at length in a docblock, enforced at *one* reader, and then dropped at the carrier that transports it. The register below is ordered by whether a wrong state is constructible today.

# Register

## F1 — `probe_error` is optional, and absence is read as the UNSAFE answer (publish gate)

`src/lib/analytics-schemas.ts:363-368`

```ts
export const LivePermissionsSchema = z.object({
  read: z.boolean(),
  trade: z.boolean(),
  withdraw: z.boolean(),
  probe_error: z.boolean().optional(),
});
```

The publish gate consumes it at `src/app/api/strategies/finalize-wizard/route.ts:521` (`if (livePerms.probe_error)`) and then at `:533` rejects only on `livePerms.trade === true || livePerms.withdraw === true`.

**The wrong state that is constructible.** The Python fail-closed transient arm returns `{read: False, trade: False, withdraw: False, probe_error: True}` (`analytics-service/routers/internal.py:415-421`; the empty-credential arm at `:363-369` is the same shape). Remove the single `probe_error` key from that dict and the body still parses cleanly — `optional()` accepts its absence — `undefined` is falsy at `:521`, `trade`/`withdraw` are both `false` at `:533`, and the gate returns `{ ok: true }`. A key whose live exchange scopes were **never successfully probed** is published as read-only-verified. The failure is silent on both sides.

**Why this is a type defect and not a Python bug.** The same file, sixteen lines below, requires `detected_at` on exactly the opposite reasoning:

> `detected_at` is REQUIRED because every one of the emitter's six return arms sets it (verified at source in `routers/internal.py` …). A body without it is contract drift
> — `src/lib/analytics-schemas.ts:381-385`

`probe_error` has identical provenance (all six arms set it; `analytics-service/tests/test_sfox_internal_probe.py:99,122,140,180,196` assert it on each) and a strictly worse consequence when absent — `detected_at` missing renders a broken timestamp, `probe_error` missing publishes an unverified key. The weaker field got the weaker treatment.

**Calibration, honestly.** No producer omits it today, so this is not live. It is one Python edit — or one new probe arm — from silent, and "an optional field every real producer sets" is precisely the widening this review was asked to find. It is ranked first because the blast radius is the publish gate on live exchange keys.

**Fix (cheap, one line).** `probe_error: z.boolean()`. A producer that drops it then fails `safeParse` at `route.ts:215`, returns `PROBE_PARSE_MISS`, and lands on the fail-closed arm — the doctrine the file already states. `.default(true)` is the same safety with looser coupling. Either makes the unsafe reading unrepresentable.

## F2 — The wire vocabulary and the render vocabulary are disjoint sets with no total mapping

This is the second live example in the brief, enumerated.

### F2a — Codes emitted by the route `SubmitStep` posts to, that cannot render

`src/app/(dashboard)/strategies/new/wizard/steps/SubmitStep.tsx:208-213` translates via `recogniseSeamErrorCode` then membership-checks `KNOWN_FINALIZE_CODES`. Two codes emitted by `finalize-wizard/route.ts` itself pass through both and land on `UNKNOWN`:

| Wire code | Emission | Why it can never match |
|---|---|---|
| `COMPOSITE_UNSUPPORTED_UNIFIED` | `finalize-wizard/route.ts:1551`, HTTP 409 | Absent from `SEAM_CODE_TO_WIZARD_CODE` (`wizardErrors.ts:1550-1567`) and from `KNOWN_FINALIZE_CODES` |
| `draft_state_invalid` | `finalize-wizard/route.ts:1190`, HTTP 409 | **lowercase** — structurally incapable of matching either table's SCREAMING_SNAKE keys |

Both are acknowledged in prose at `wizardErrors.ts:1541` as out of scope and ledgered, so the *facts* are known. What is not stated is the type-level consequence: **`data.code` at `SubmitStep.tsx:208` is typed `string`, so nothing at the emitting route can be told it has minted an unrenderable code.** A `code:` literal added to any `NextResponse.json` on that route type-checks, ships, and renders as "something went wrong" with `wizard_error {code:"UNKNOWN"}` in the funnel. The 409 `draft_state_invalid` case is worse than UNKNOWN-as-fallback: the user is told to retry a draft that is in a genuinely unfinalizable state.

### F2b — `ValidationEnvelope.code: string` — a `string` where a union exists, with **no membership check at all**

`src/app/(dashboard)/strategies/new/wizard/steps/CsvSubmitStep.tsx:38-44`, populated at `:191`:

```ts
interface ValidationEnvelope { code: string; … }
…
code: data.code ?? "CSV_SUBMIT_FAILED",
```

Unlike `SubmitStep`, this path has **no `KNOWN_*` set and no translation** — the wire value is stored verbatim and rendered into `data-error-code` (`ErrorEnvelope.tsx:138`) and shipped to PostHog. The upstream vocabulary feeding it is **not closed**: `analytics-service/services/ingestion/csv_adapter.py:172` mints codes as `error_code=first_rule.upper()`, i.e. any new pandera rule name in `analytics-service/services/csv_validator.py` becomes a new wire code with no code change anywhere. `CSV_TOO_LARGE` (csv_adapter.py:122) vs the union's `CSV_FILE_TOO_LARGE`, and `CSV_FINALIZE_FAILED` (`routers/process_key.py:1084`) vs the route's `CSV_FINALIZE_FAIL` (`csv-finalize/route.ts:1139`) are already-shipped near-misses of exactly the kind `wizardErrors.ts:1541` calls "a two-string near-miss".

This directly contradicts the module docstring's claim that raw backend strings never reach the UI.

### F2c — Scale, and where the boundary is actually held

Six wire codes have a translation (`SEAM_CODE_TO_WIZARD_CODE`, `wizardErrors.ts:1550-1567`); a further six have a *server-side-only* one (`VENUE_WIRE_CODE_TO_VERDICT`, `:1342-1357`). Against those twelve there are on the order of **fifty** distinct wire codes emitted across `src/app/api/**` and `analytics-service/`, e.g. `PERMISSION_DENIED`, `TRADE_SCOPE`, `WITHDRAW_SCOPE`, `MISSING_SCOPE`, `UNSUPPORTED_EXCHANGE`, `VALIDATION_UNEXPECTED` (`analytics-service/services/exchange.py:1135,1260,1257,1101,1219,1214`), the `PROBE_*` family (`keys/[id]/permissions/route.ts:492-537`), `DRAFT_LOOKUP_FAILED` / `SYNC_KICKOFF_FAILED` (`keys/sync/route.ts:167,300`), and every nested `service_error` code, whose `code` is not even at the top level of the body so `data.code` is `undefined` for the whole family.

Two artefacts worth flagging as symptoms:
- **`SEAM_DEGRADED`** is named in prose at `wizardErrors.ts:1521,1564` and asserted against in `src/lib/analytics-client.test.ts:1732` — but **no producer emits it** anywhere in `src/` or `analytics-service/`.
- **`CSV_DUPLICATE_SESSION`** is branched on at `CsvSubmitStep.tsx:219` with **no producer anywhere in the repo**.

Both are the signature of a vocabulary maintained by hand on two sides with nothing joining them.

**Fix that fits the codebase.** Do not try to unify the vocabularies — the `RATE_LIMITED`-means-two-things note at `wizardErrors.ts:1321-1328` is right that they must stay separate. Instead give the **wire** vocabulary a type: a `WireErrorCode` union in a dependency-free leaf, and require route handlers to emit `code: WireErrorCode`. `SEAM_CODE_TO_WIZARD_CODE` then becomes `ReadonlyMap<WireErrorCode, WizardErrorCode>`, and a wire code with no translation is a *compile* error at the table, not an `UNKNOWN` render. That is a real, bounded refactor and it converts F2a and F2b into type errors. `SubmitStep.tsx:210`'s `candidate as WizardErrorCode` cast disappears with it.

## F3 — `AnalyticsUpstreamError`: additive extension has outgrown its shape

`src/lib/analytics-client.ts:65-125`. Extended **twice** in this range: `seamCode` (140.3-01 / TS-05, `:78`) and `dependency` (140.3-11 / TS-18, `:100`). The constructor is now:

```ts
constructor(
  message: string,
  status: number,
  seamCode: string | null = null,
  dependency: string | null = null,
)
```

**Is additive extension still right at that count?** The *homing* decision is right and should be kept — the docblock at `:82-87` ("the seam has one error vocabulary and adding to it is not this plan's to do") is correct, and a sibling error type would fragment the `instanceof` ladder in every route catch arm. What has outgrown its shape is the **positional constructor**, not the class.

**The wrong state that is constructible.** Parameters 3 and 4 are adjacent, identically typed `string | null`, both defaulted. This compiles with no error:

```ts
new AnalyticsUpstreamError(msg, 424, "binance", "EXCHANGE_UNAVAILABLE")
```

The venue slug becomes `seamCode` (no entry in `SEAM_CODE_TO_WIZARD_CODE` → `UNKNOWN` at every consumer) and the machine code becomes `dependency`, which `140.3-11` renders to an admin as **the name of the third party that failed**. That is precisely the attribution lie TS-18 exists to make impossible, reachable by transposing two arguments at the one line — `analytics-client.ts:465-470` — where both are supplied.

**Second-order: the invariant is validated at the reader and dropped at the carrier.** `seamDependencyName` (`seam-discriminator.ts:269-281`) tests the value against `^[a-z0-9][a-z0-9._-]{0,39}$` and rejects members of the closed service set — then hands the result to a constructor that accepts any string. The constructor already demonstrates it knows how to fail loud: `:116-120` throws `RangeError` on a malformed `status` because "the value is forwarded onto the wire". `dependency` is forwarded to a human as an attribution, which is the same argument, and it gets no guard.

**Fix.** Collapse positions 3–4 into one options object — `new AnalyticsUpstreamError(message, status, { seamCode, dependency })` — which is four call sites (`analytics-client.ts:422,465,481,494`) and kills the transposition class permanently rather than one instance of it. If that is too much churn, at minimum apply the slug regex in the constructor and throw, matching the `status` guard directly above.

## F4 — `SeamBreakerVerdict`: the correlation invariant is in the doc comment, not the type

`src/lib/seam-discriminator.ts:125-134`

```ts
/** The verdict. `breakerKey` is non-null exactly when `counts` is true. */
export interface SeamBreakerVerdict {
  readonly counts: boolean;
  readonly breakerKey: string | null;
  …
}
```

The biconditional is real, load-bearing and true of every arm — and it is a sentence. All three consumers pay for its absence by re-deriving it:

- `src/lib/resilient-fetch.ts:1507` — `if (bodyVerdict.counts && bodyVerdict.breakerKey !== null)`
- `src/lib/resilient-fetch.ts:1803` — same
- `src/lib/resilient-fetch.ts:1827` — same

**The wrong state.** A future arm that returns `counts: true, breakerKey: null` type-checks. All three guards then evaluate false, **nothing is recorded, and no error is raised** — a breaker that silently never trips during a real Railway outage. This is the fail-open direction, and it is invisible: the `&& !== null` reads as defensive hygiene, so nothing at any of the three sites signals that a case was dropped.

**Fix.** A two-member discriminated union:

```ts
export type SeamBreakerVerdict =
  | { readonly counts: true;  readonly breakerKey: string; readonly attributability: SeamAttributability; readonly dependency: string | null }
  | { readonly counts: false; readonly breakerKey: null;   readonly attributability: SeamAttributability; readonly dependency: null };
```

`if (verdict.counts) await recordOnce(verdict.breakerKey)` then type-checks with no null test, the three redundant guards delete, and the fail-open arm becomes unconstructible. This is the same shape as `ProbeParseMiss` — the pattern the diff already got right once.

## F5 — `mintTenantClaim(payload, secret)`: adjacent same-typed strings, and one of them is the platform secret

`src/lib/tenant-claim.ts:118`

```ts
export function mintTenantClaim(payload: string, secret: string): string
```

This is the sharpest instance of the transposition category in the diff, and what makes it notable is that **the fix for this exact threat is declared eight lines above it and then not applied here.** `TenantIdentity` (`:88-95`) exists solely for this reason:

> two adjacent `string`s where a transposition compiles cleanly and mints the claim over a USER-CHOSEN SECRET … That is threat T-140.2-09-02 with the compiler unable to help. A one-field object cannot be confused with a credential
> — `src/lib/tenant-claim.ts:74-79`

The principle was applied at the wrapper boundary and stopped one layer short of the mint, which is the only place a secret is actually a parameter.

**The wrong state.** `mintTenantClaim(process.env.INTERNAL_API_TOKEN ?? "", options.tenantId)` compiles. All three guards pass — the token is non-empty (GUARD 1, `:125`), is dot-free so GUARD 2 (`:138`) does not fire, and the userId is a non-empty secret for GUARD 3 (`:152`). The function returns `<INTERNAL_API_TOKEN>.<exp>.<mac-keyed-by-userId>`, and both call sites put that value straight into an outbound `X-Tenant-Claim` header — `analytics-client.ts:321` (nine routes) and `process-key-client.ts:339`. The platform secret leaves the perimeter in plaintext, in a header, to a service that logs headers.

**Currently enforced only by test — category 5.** `src/lib/process-key-client.test.ts:376,381` asserts `payload === "user-42"` and `expect(claim).not.toContain("internal-test-token")`; `src/lib/analytics-client.test.ts:1050` destructures and checks the payload for the other site. Those are good tests and they would catch this today. They are also the wrong layer: they guard two known call sites, and every future caller is unguarded until someone remembers to write a third.

**Fix.** The type already exists — take it. `mintTenantClaim(identity: TenantIdentity | "public", secret: InternalApiToken)`, where `InternalApiToken` is a branded string (`type InternalApiToken = string & { readonly __brand: unique symbol }`) minted by one reader of `process.env.INTERNAL_API_TOKEN`. Transposition then fails to compile at every call site that exists and every one that does not yet. The literal `"public"` teaser payload (`verify-strategy/route.ts:192`) is accommodated by the union member and stays explicit.

## F6 — Guards enforced by test where the type could carry them

Three named in the brief, with distinct verdicts:

**`EXPECTED_TABLE_SIZE = 55`** — `src/lib/wizardErrors.test.ts:1348` and `:1491`, two literals in one file. **Largely redundant with the type.** `WIZARD_ERROR_COPY: Record<WizardErrorCode, WizardErrorCopy>` (`wizardErrors.ts:~300`) already makes a union member without copy a compile error, which is the failure the count is nominally guarding. What the count adds is detection of *deliberate* union growth — i.e. it fires on intended changes, which is why it needs editing in the same commit each time. Two copies of the same magic number in one file is a self-inconsistency waiting to happen. Recommend collapsing to one `const` and treating it as a changelog tripwire, not a safety guard; the `Record` is the safety guard.

**`EXPECTED_EXPORTS`** — `src/lib/seam-discriminator.purity.test.ts:104-110`, five members, set-equality. **Keep as-is.** This one genuinely cannot be a type: it guards *export surface growth* of a leaf whose whole value is that it stays small, and TypeScript has no way to say "this module exports exactly these five names". The five-member surface with a private `nestedDetail` is well-judged — `seamCorrelationId` was added on the recorded mechanism (`seam-discriminator.ts:288-296`), and the rejections of a generic `seamDetailField(body, name)` getter and of exporting `nestedDetail` are both correct. Best-designed unit in the diff after `ProbeParseMiss`.

**`KNOWN_FINALIZE_CODES`** — `SubmitStep.tsx:148`. **Weakest of the three, and it is not really a guard.** It is a `const` declared *inside a component's async event handler*, so it is reconstructed on every submit, is unreachable from any test (`SubmitStep.test.tsx` only mentions it in comments), and nothing binds it to what `finalize-wizard/route.ts` emits. F2a is the direct consequence: two codes on that very route are outside the set and nobody found out. Hoist it to module scope at minimum; the real fix is F2c's `WireErrorCode` union, which makes the set derivable rather than hand-maintained.

## F7 — `retry_after_seconds`: prose invariant, `number` type — but the renderer holds it

`src/lib/envelope.ts:51` and `src/lib/wizardErrors.ts:1176`. The docblocks are emphatic — absence means "no wait was advertised", never zero; "no clamp, no default, no unit change" (`envelope.ts:67-70`); TRAP-3 says a surface must never name a duration it did not receive. The type is `number | undefined`, which admits `0`, negatives, fractions and `NaN`.

**Calibrated honestly: this is "could be tighter", not a live bug.** Both producers guard — `CircuitOpenError.retryAfterS` throws `RangeError` on anything not a non-negative integer (`seam-errors.ts:75-79`), and the renderer requires `waitSeconds > 0` before displaying (`src/components/error/ErrorEnvelope.tsx:129-130`), so `0` and `NaN` are already unrenderable. Reported only because the guard lives in three places that each had to rediscover it, and a branded `Seconds` type (or simply documenting that `ErrorEnvelope.tsx:130` is the enforcement point) would consolidate it. Low priority.

## F8 — `RouteResponseError` is a marker with no evidence (note, not a defect)

`src/lib/route-response-error.ts:45-50`. The discrimination is the right idea and the rationale at `:27-33` — why "replace every caught message with a stable sentence" would have deleted the breaker surface — is a genuinely sharp piece of reasoning. But the class carries no proof of its own claim: `new RouteResponseError(caughtTypeError.message)` compiles and launders an undici transport string, complete with internal URL, into the "reviewed copy, safe to render" class. The invariant is "the message came from a route response" and the type says only "someone said so".

All four current sites are honest — `ReplacementPanel.tsx:67`, `KeyPermissionBadge.tsx:114,121`, `PortfolioOptimizer.tsx:225` — all constructing from `body.error`, `res.status`, `res.statusText` or `err.code`. Cheap hardening if it is ever touched: make the constructor private and expose `RouteResponseError.fromResponse(res, body)`, so the only way to obtain one is from a `Response`. Not worth a dedicated change now.

# Recommended order of work

1. **F1** — `probe_error: z.boolean()`. One line, closes a publish-gate fail-open. Do this first regardless of what else happens.
2. **F3** — collapse `AnalyticsUpstreamError` positions 3–4 into an options object (4 call sites), or at minimum guard `dependency` in the constructor.
3. **F4** — `SeamBreakerVerdict` as a discriminated union; deletes three redundant null-tests and one silent fail-open.
4. **F5** — brand the token, take `TenantIdentity` at the mint. Small, and it retires a class rather than an instance.
5. **F2c** — the `WireErrorCode` union. Largest of the five, and the only one that converts F2a and F2b from "a test might notice" into "it does not compile". Worth planning properly rather than squeezing in.

F6 (`KNOWN_FINALIZE_CODES` hoist), F7 and F8 are cleanups to fold into whichever plan next touches those files.
