### RG-1 — `PortfolioOptimizer`'s error is now announced to nobody, and the announcement was the ONLY channel left

**Severity: HIGH (a11y, normative DESIGN.md violation) · SILENT · introduced by `88ba5900` (140.3-07)**

`git diff 4b59fb31^ HEAD | grep 'role="alert"'` → **three deletions, zero additions**, all in
`src/components/portfolio/PortfolioOptimizer.tsx`.

| | before (`4b59fb31^`) | after (`a77d607e`) |
|---|---|---|
| live regions in the file | **3** | **0** |
| where the error rendered | inline `<p className="mt-2 text-caption text-negative" role="alert">` inside the empty state (`:316`), the no-candidates state (`:336`) and under the ranking list | inside the failed Card at `src/components/portfolio/PortfolioOptimizer.tsx:283-289`, as a plain `<p className="mt-0.5 text-caption text-text-secondary">` |

DESIGN.md is normative and names this twice:
- `DESIGN.md:317` — "Shell: `role="alert"` + …" (Error Envelope visual contract)
- `DESIGN.md:369` — "ARIA live regions: `role="alert"` on blocking errors"

**Why this is worse than the register's framing.** `140.23-SPEC-review.md §3` records the deletion.
What it does not say is that the announcement was the *only* remaining channel. Trace the click:

1. User presses **Run Optimizer** (`:316`).
2. `runOptimizer` sets `loading = true`. The very next branch is
   `if (loading || computationStatus === "computing") return <shimmer>` (`:258`) — the button the
   user was standing on **unmounts on click**, and focus falls to `document.body`. *This is
   pre-existing; it is not the regression.*
3. Before: the request fails, `loading` clears, the component returns to the empty-state branch and
   **inserts a fresh `role="alert"` node** → a screen reader announces the failure even though focus
   is on `<body>`.
4. After: the request fails and the component returns the **failed Card**, which has no live region
   and receives no focus. A screen-reader user gets **silence** — no announcement, no focus move, no
   change they can perceive without re-reading the page.

So the deletion did not degrade a redundant channel; it removed the sole one, on a surface whose
focus was already gone by construction.

**Reasoned or incidental?** The removal is *argued* — the two inline sites carry a comment saying a
second error surface that cannot render is how a reviewer loses track. That reasoning is sound about
*duplication*. It is silent about `role`: no comment, no SUMMARY line, and no plan requirement
mentions that the replacement surface must carry the attribute the deleted nodes carried.

**Would any gate have caught it?** No. `grep -rln 'role="alert"' tests/ src/__tests__/ e2e/` returns
exactly one file (`e2e/onboarding-banner-smoke.spec.ts`), unrelated. axe cannot flag the *absence* of
a live region. `PortfolioOptimizer.test.tsx` — which this diff grew by 276 lines — contains zero
matches for `alert`, `aria` or `focus`. The 140.3-07 test additions pinned the discard-the-stale-
ranking behaviour and nothing about how the replacement is perceived.

**Fix:** `role="alert"` on the failed Card's wrapper at `PortfolioOptimizer.tsx:283`.

### RG-2 — `WeightOptimizerSection`: a 401 and a 429 now both tell the allocator to change their strategy selection

**Severity: HIGH · reasoned-but-wrong (the docblock argues the case it gets wrong) · `20fd9619` (140.3-08)**

`src/app/(dashboard)/allocations/components/WeightOptimizerSection.tsx:163`:

```ts
setFailure(res.status >= 400 && res.status < 500 ? "refused" : "unavailable");
```

`FAILURE_COPY.refused` (`:166-169`):
> **The optimizer refused this request** — "The optimizer answered but would not run this request.
> **Change the objective or the selected strategies** and run it again."

The replaced copy was `"The optimizer is unavailable right now. Try again shortly."`

`src/app/api/scenario/optimize/route.ts` 4xx arms, read at source:

| line | status | reality | new copy is |
|---|---|---|---|
| `:69-72` | **401** `{error:"Unauthorized"}` | the session expired | **false** — changing the objective cannot restore a session |
| `:85-135` | 400 ×6 | genuine request-shape refusals | correct |
| `:147-150` | **429** `{error:"Too many optimize requests. Try again shortly."}` | our own `userActionLimiter` | **false** — and note the route's own body literally says *"Try again shortly"*, the sentence this change deleted |

`140.23-SPEC-review.md §1` has the 429. **The 401 is new here**, and it is the worse of the two: an
allocator whose session lapsed is told their *portfolio selection* is the problem, with no hint to
re-authenticate. The route also attaches **no `Retry-After`** on `:147-150`, so nothing downstream
can recover the wait either.

The docblock at `:83-101` explicitly reasons *"a 4xx means the optimizer ANSWERED and refused"* and
*"the identical request will be refused identically every time"*. Both statements are false for the
429 (it succeeds after the window) and for the 401 (it succeeds after re-auth). This is a case where
the fix's own justification is the thing that is wrong.

**Fix:** exclude 401/403/408/429 from the `refused` bucket — they belong in `unavailable`, which the
docblock already names as the conservative default.

### RG-3 — `AllocatorMatchQueue`: a failed recompute went from a blocking, announced `alert()` to a silent inline card

**Severity: MEDIUM (admin surface) · SILENT on the a11y half · `20fd9619` (140.3-08)**

`src/components/admin/AllocatorMatchQueue.tsx:288-294`:

```diff
-      alert(`Recompute failed: ${err instanceof Error ? err.message : "Unknown error"}`);
+      setError(err instanceof Error ? err.message : "Recompute failed");
```

The *routing* change is right and argued (an `alert()` is dismissed while the stale queue stays on
screen). Three consequences are not argued anywhere:

1. **Notification channel deleted.** A native `alert()` is modal: it steals focus and is announced by
   every AT. The replacement is `src/components/admin/AllocatorMatchQueue.tsx:403-412` — a `Card`
   with `<p className="text-small text-negative">` and **no `role="alert"`**. File-wide live-region
   count is **0, before and after**, so the component never had one to fall back on. Net: the surface
   went from *always announced* to *never announced*.
2. **The trigger is a keyboard shortcut.** Recompute is bound to `r` (the diff's own new
   `recomputeIdRef` comment calls it *"a repeatable keyboard shortcut pointed at a service that,
   during an outage, is exactly what an anxious founder leans on"*). A keyboard-driven action whose
   only failure signal is a silent DOM swap several hundred pixels away is the worst combination of
   the two.
3. **Focus is dropped.** `if (error || !data) return <Card>` replaces the *entire* queue subtree, so
   whatever row/button had focus is unmounted. Previously the queue stayed mounted behind the alert.

The `recomputeIdRef` in-flight guard added in the same hunk (`:180-188`, `:229-230`) is a genuine
improvement and is not in dispute.

**Fix:** `role="alert"` on the error Card at `:405`; optionally move focus to it.

### RG-4 — `/api/keys/sync` silently changed the resumed-wedge duplicate from `202 + status:"syncing"` to `200 + status:<whatever the old row holds>`

**Severity: MEDIUM (wire contract) · SILENT — the comment reasons about `queued` only · `8aee95c9` (140.3-02)**

`src/app/api/keys/sync/route.ts:577`:

```diff
-    if (upstream.queued === false && upstream.code === "WIZARD_DUPLICATE") {
+    if (upstream.code === "WIZARD_DUPLICATE") {
```

Removing the `queued === false` conjunct is correct and well argued (`process_key.py::_resume_
duplicate_job` produces `queued:true` + `WIZARD_DUPLICATE`, and the old conjunct skipped the branch
on exactly that case). But re-pointing the branch also **moves that case between two different
response envelopes**, and the 40-line comment block at `:551-574` discusses only the `queued` field:

| resumed wedge (`queued:true, code:WIZARD_DUPLICATE`) | before | after |
|---|---|---|
| HTTP status | **202** (`:598`) | **200** (`:597`) |
| `status` field | hardcoded `"syncing"` | `upstream.status` — e.g. `"validated"`, whatever the pre-existing verification row holds |
| `idempotent` | absent | `true` |
| `composite` | `false` | `false` |

**Blast radius today: low, but only by luck.** I traced both consumers:
- `SyncPreviewStep.tsx:639-644` reads only `composite` off a 2xx kickoff and branches on `!res.ok` —
  200 and 202 are indistinguishable to it.
- `ApiKeyManager.tsx` gates on `isSyncEnqueued(body)` → `ok === true`, which both envelopes stamp.

So nothing breaks *today*. What broke is the **contract**: a documented `202 Accepted` for a case
that is still an accepted, enqueued job now answers `200 OK` with a *terminal-looking* `status`, and
no SUMMARY, comment or test names the change. The next consumer that (reasonably) branches on 202 or
on `status === "syncing"` inherits the defect. Cf. `140.23-SPEC-silent-failure.md M4`, which flags a
*different* keys/sync 200 (the drift fallback) — this is not that one.

**Fix:** either keep 202 for `queued === true`, or state the status change in the route docblock and
pin both branches.

guard fires. The over-reach is latent, not live. It becomes live the moment a fifth `setIsComposite`
call site appears — worth a negative pin, not a fix.

## 4. WHAT THIS DIFF DID **NOT** BREAK — stated plainly

prose that outran the code, and fixes whose stated justification is wrong about its own subject

request will be refused identically every time"* about a rate limiter).
