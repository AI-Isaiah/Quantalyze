**Wave 0** writes RED tests + migration 064 SQL (NOT yet applied). **Wave 1** starts with a BLOCKING decision checkpoint (`5-01-W1-01`, reordered per Voice-C2) for the underperformer source; migration 064 apply (`5-01-W1-02`) runs AFTER the decision so a "defer" choice never triggers a live-DB rollback. Wave 1 then wires admin route + admin UI + read-side (`computeOutcomeKPIs`, `deriveOutcomeStatusPill`, `getMyAllocationDashboard` fan-out with `.limit(200)` cap, curves endpoint). **Wave 2** ships the **single-file** `OutcomesWidget.tsx` (Voice-D1 consolidation — inline KpiStrip / TimelineTable / TimelineRow / ExpandedPanel / Sparkline sub-components; separate registry / barrel / default-layout edits stay as single-task entries because they touch distinct files). **Wave 3** ships follow-up NOT NULL migration 065, runs visual typography review (Voice-D9), and phase gate (npm test + typecheck + lint + security greps). **Source of underperformer identity on admin side:** Wave 1 starts with a BLOCKING `checkpoint:decision` task. The `SendIntroPanel` component does NOT currently carry an `underperformer_strategy_id` in state (verified 2026-04-19: grep for `underperformer` across `src/components/admin/` returns zero matches; `CandidateRow` has no such field). No silent inventions. **Voice-C2 ordering:** this decision now runs BEFORE migration apply so a "defer" answer never leaves the live DB in an unwound state.

**Zero new npm dependencies** (Recharts 3.8.1 already pinned).

**Purpose:** close the Bridge feedback loop for allocators visually — they see the realized outcome of every Bridge recommendation they acted on, reconciled 1:1 with the feedback-engine math from Phase 4. The column placement on `match_decisions` also pays dividends for Phase 4 feedback-engine attribution (index on `(allocator_id, original_strategy_id)` supports future queries like "how did strategy X perform as a replacement for Y across all allocators").

### Critical Notes

**CRITICAL — column placement on `match_decisions`, NOT `bridge_outcomes`.** The previous planning pass placed `original_strategy_id` on `bridge_outcomes`. That was architecturally wrong: the underperformer identity is known at intro-SEND time (admin side, via `send_intro_with_decision`), not at outcome-RECORD time (allocator side). Putting it on `bridge_outcomes` would force the allocator UI to discover the underperformer at record time, which it cannot. Correct placement: `match_decisions.original_strategy_id UUID NULL` (initially; tightened to NOT NULL in follow-up migration 065 per Voice-C3). Phase 5 read-path hops `bridge_outcomes.match_decision_id -> match_decisions.original_strategy_id -> strategies(id, name)` via a single nested Supabase select.

**CRITICAL — NO fallback of `originalStrategyId = strategyId`.** The previous pass proposed "v1 default uses the held row's own strategy id" — REJECTED. That collapses Original == Replacement and makes the two-series sparkline one line drawn on top of itself. STRICTLY rejected. If the admin flow has no persisted underperformer source, the executor MUST surface the BLOCKING checkpoint (Task 5-01-W1-01 — reordered per Voice-C2) for user decision rather than invent a tautological default.

**CRITICAL — NO allocator-side plumbing changes.** The previous pass added prop threads through `BridgeOutcomeBanner` / `AllocatedForm` / `RejectedForm` / `PositionsTable::BannerSubRow`. Those changes are REMOVED. The allocator does not need to know the underperformer at outcome-record time — Phase 5 resolves it server-side via the `match_decision_id` FK on every `bridge_outcomes` row.

**CRITICAL (Voice-C2 reorder) — decision checkpoint BEFORE migration apply.** Migration 064 destructively ALTERs a live DB and DROPs the old 5-arg `send_intro_with_decision` RPC. If the user picks Option C ("defer Phase 5") at the underperformer-source checkpoint, the plan MUST NOT leave a live migration to roll back. Therefore the order is: `5-01-W1-01` (decision) → `5-01-W1-02` (apply, only if W1-01 resolves to Option A or B). Option C at W1-01 halts execution before any DDL hits the DB.

**CRITICAL (Voice-C3) — migration 064 ships NULL-allowed; 065 tightens to NOT NULL.** The previous pass shipped migration 064 as `NOT NULL` banking on an empty-table precondition. Voice-C3 flagged this as fragile (branch DBs, race between apply + admin-UI deploy). Revised shape: migration 064 adds the column as `NULL` with `ON DELETE RESTRICT`; follow-up migration 065 (Wave 3, applied after admin UI has shipped values) executes `ALTER COLUMN original_strategy_id SET NOT NULL` guarded by a `DO block` that verifies `SELECT count(*) FROM match_decisions WHERE original_strategy_id IS NULL = 0`, else RAISE EXCEPTION. The `SELECT count(*) FROM match_decisions` pre-apply empty-table check is REMOVED; presence of the `ON DELETE RESTRICT` clause is verified via `information_schema.referential_constraints` instead (per Voice-D3).

**CRITICAL (Voice-D3) — FK is ON DELETE RESTRICT, not CASCADE.** Previous pass used `ON DELETE CASCADE` on the new FK. Voice-D3 flagged this as inconsistent with migration 059 A6 precedent (which uses SET NULL for `bridge_outcomes.match_decision_id` to preserve outcome history).
