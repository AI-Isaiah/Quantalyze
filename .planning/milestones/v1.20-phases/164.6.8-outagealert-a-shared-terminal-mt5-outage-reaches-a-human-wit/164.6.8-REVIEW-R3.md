## 1. Round-2 findings: verdict

| Finding | Verdict | Evidence |
|---|---|---|
| WR-R2-01 (recovered closed with no channel) | **Mechanically fixed, but not effective in production.** See WR-R3-01. | Every recovered caller now closes only on `await_delivery(...) is True`. The cancel and no-channel paths leave the source unmarked. The test with no Sentry id and an email 502 would fail without the fix. But "delivered" counts a Sentry event id, and the only Sentry rule that notifies anyone filters on `ops_alert_event = outage`. |
| WR-R2-02 (failed close never retried; close needs a count) | **Fixed.** | `_close_rows` reads `count=CountMethod.exact` and falls back to rows, the same idiom as `mt5_session_episodes._close_row`. A False close unmarks the source, so the next healthy reading re-reads and re-closes. The window then makes the duplicate notice return the holder's done future instead of re-sending. `test_a_close_whose_update_matched_nothing_reports_failure` and `test_a_won_close_is_counted_even_when_the_transport_returns_no_rows` both bite. |

**The fixer's declared deviation** keeps a row left by an earlier process and replaces only rows this process knows are stale. **I accept it.** The residual is narrow. It needs all of the following, in order:
1. Process P1's close failed, or its notice reached no channel.
2. P1 was redeployed before its next healthy reading.
3. P2's first readings open a NEW incident before any healthy reading.

Only then does the new incident inherit the old row. The opposite choice would cut short the `since` of the far more common case, a redeploy in the middle of an outage. Below the floor; not reported.

**Checked and sound:**
- **No double-send through the shared outcome.** A suppressed recovered returns the holder's future, so a re-read-and-close inside the hour sends nothing.
- **The fabricated `True` branch cannot fire in practice.** `page` returns a fresh `True` when the page is suppressed and `held is None`. That branch is unreachable outside test resets: `_last_alert_at[k]` and `_delivery_by_key[k]` are set together on admission and popped together by `_release_window`, and `_drop_window_entries` removes the suppressing entry.
- **The outcome future always settles.** It is set in `_settle_window`'s `finally`, in the unschedulable-email branch, in the no-task branch and in the outer `except`.
- **`await_delivery` is bounded and shielded.** It cannot hang a tick, and a cancelled waiter does not cancel the page's settlement.
- **No deadlock.** No await happens under `_LOCK`, and the `finally` in `_send_recovered` takes the lock only around set operations.

## 2. Findings

### WR-R3-01: A RECOVERED notice counts as "delivered" on a Sentry event id, but no Sentry rule notifies anyone about a recovered event. In production the record is closed even when the founder email fails, which is WR-R2-01 again.

**Severity:** MEDIUM. **Confidence:** 8/10.
**Files:**
- `analytics-service/services/ops_alert.py:357-358`, in `_settle_window`: `outcome = email_ok or sentry_ok`.
- `analytics-service/services/ops_alert.py:519`: `delivered.set_result(sentry_ok)`.
- `analytics-service/services/ops_alert.py:491-494`: `sentry_ok = event_id is not None`.
- `analytics-service/services/mt5_outage_alert.py:376-387`, `analytics-service/services/mt5_validation_liveness.py:430-438`: these callers trust that outcome.
- `analytics-service/tests/test_ops_alert.py`, `test_a_sentry_event_alone_reports_delivered_even_when_the_email_fails`: pins the rule.

**Issue:** `164.6.8-01-SUMMARY.md` (Task 3) records the Sentry rules that exist:
- The only per-event rule created for this phase is "Ops alert: outage (164.6.8)", with filter `ops_alert_event equals outage`.
- The pre-existing "high priority issues" rule fires on a NEW high-priority issue or a regression. A recovered capture is sent at `level="warning"` with a fixed fingerprint per `(source, cause, "recovered")`. That makes it at best a medium-priority issue, and from its second occurrence on, an existing issue.
- `LoggingIntegration` does not turn the WARNING recovered log line into an event.

So for `event="recovered"`, a Sentry event id proves the event was queued to Sentry. It does not prove a human was told. With `SENTRY_DSN` set (production), `capture_message` returns an id on effectively every call, so `sentry_ok` is True and `email_ok` never matters.

**Failure scenario (production, DSN set):**
1. The jobs terminal is paged OUTAGE, and the founder gets the email plus the Sentry rule email.
2. It recovers. `_send_recovered` → `page(... "recovered")`. Sentry returns an event id. The founder-email POST answers 502 (a Resend blip) or 401 (a `SERVICE_KEY` rotation on one side).
3. `_settle_window` computes `outcome = False or True = True`. The window is not released, and `await_delivery` returns True.
4. `close_open_page` closes the record. The source is marked checked.
5. Nobody is told the terminal recovered, and nothing will re-send the notice. The founder's last message stays OUTAGE. This is the exact end-state WR-R2-01 named. The new tests do not catch it, because each no-channel test sets `capture_message.return_value = None`, which is the configuration production does not have.

The same counting releases no window for a recovered in that case. So the SFH-F2 retry does not happen for recovered either.

**Fix:** For a recovered notice, count only a channel that reaches a human. The smallest code fix scopes the Sentry credit to events a notifying rule covers:

```python
# ops_alert.py, page(): only an OUTAGE capture is covered by a notifying Sentry rule
# ("Ops alert: outage (164.6.8)", filter ops_alert_event=outage).
sentry_counts = sentry_ok and event_n == "outage"
...
functools.partial(_settle_window, key, now, sentry_counts, delivered)
...
delivered.set_result(sentry_counts)   # both non-callback branches
```

Add a test: recovered, `capture_message` returns an id, email 502. Assert that `await_delivery` is False, the record stays open, and the next authorized reading re-sends. The alternative is a founder action to widen the Sentry rule filter to `recovered` too. If that is chosen, record it in the 01 SUMMARY, because the code's correctness then rests on a live setting that no file in the repo holds.

### WR-R3-02: An in-process re-send tells the founder "the analytics service restarted" when it did not

**Severity:** MEDIUM. **Confidence:** 7/10.
**Files:**
- `analytics-service/services/mt5_outage_alert.py:296-308`: `_restart_recovered_detail` returns "...after the analytics service restarted while a page was open".
- `analytics-service/services/mt5_outage_alert.py:311-345`: `_durable_recovery_request` always uses that text.
- `analytics-service/services/mt5_outage_alert.py:385-393`: the round-3 fix now routes in-process re-sends through it.

**Issue:** Before round 3, `_durable_recovery_request` was reached only on the first healthy reading of a fresh process, so the sentence was true. The round-3 fix reuses that path as the retry mechanism: `_DURABLE_CHECKED.discard(source)` after a no-channel recovered or a failed close. Every re-send in the same process therefore carries the restart claim. The debt-source re-send goes through the same function with the label `terminal=jobs relaunch debt`, so it says the same thing.

**Failure scenario:**
1. A jobs recovered notice reaches no channel (email 502 with no Sentry credit, which after WR-R3-01's fix is the normal production case).
2. Ten minutes later the next healthy reading re-sends it.
3. The founder's only RECOVERED email says the analytics service restarted while a page was open.

No restart happened. On an incident channel, a founder who reads "the service restarted" goes looking at Railway deploys or crash loops for an event that never occurred. The same happens to any re-send after a close that kept failing for more than the window. Nothing tests the detail text of the re-send, so this ships unnoticed.

**Fix:** Pass the reason into the detail. For example, give `_durable_recovery_request` a `reason` argument, or compute it from whether this process has already read the record once: "after the analytics service restarted while a page was open" on the first read of the process, and "re-sent: the earlier recovered notice reached no channel" (or "the open-page record could not be closed") on a retry. Add a test on `mt5_outage_pages[-1].detail` in `test_a_recovered_notice_that_reached_no_channel_keeps_the_record_and_is_sent_again`.

### WR-R3-03: The recovered path now awaits the email, but the tick bounds still assume it does not. The cancel path also skips the stale mark, so a same-process new incident can still inherit the old row.

**Severity:** MEDIUM. **Confidence:** 5/10.
**Files:**
- `analytics-service/services/mt5_validation_liveness.py:120-125`: the `PROBE_TICK_BOUND_S` comment reads "a little room for the tracker's page (a Sentry capture and a scheduled POST, neither awaited to completion)". That is now false.
- `analytics-service/services/mt5_validation_liveness.py:241-242`: `READ_TICK_BOUND_S = _READ_TIMEOUT_S + 5.0` (10 s), described as "the read plus the page".
- `analytics-service/services/ops_alert.py:99`: `_DELIVERY_WAIT_S = 15 s`.
- `analytics-service/services/mt5_outage_alert.py:371-393` and `analytics-service/services/mt5_validation_liveness.py:428-439`: on cancellation the `finally` unmarks the source but never calls `mark_open_page_stale`.

**Issue:**
- **The scrub reader overruns its own bound by design.** Its restart or in-process recovery now does a 5 s row read, then a 5 s open-page read, then `page`, then an `await_delivery` of up to 15 s (the httpx 10 s timeout applies per phase, so the POST itself can exceed 10 s), then a 5 s close. That is up to 30 s inside a 10 s `wait_for`.
- **The validation probe has the same problem.** It has 5 s of slack after the lease and probe.
- **Any Sentry-credited page still waits for the email.** `delivered` is resolved only in the email task's done-callback, even when the Sentry credit already decided the outcome.
- **A cancellation leaves the row unmarked.** In the cancel path the row stays open, but `_STALE_SOURCES` is not marked. Both the no-channel branch and `close_open_page`'s failure branch do mark it.

**Failure scenario:**
1. The newest scrub row turns `scrubbed`. The recovered page is admitted, and the founder email takes about 9 s (a Vercel cold start plus Resend).
2. The 10 s `READ_TICK_BOUND_S` cancels the reader inside `await_delivery` or `close_open_page`, logging "the scrub-row reader did not complete inside its bound". `restart_checked` becomes False. The row stays `running` and is NOT marked stale.
3. Before the next tick can re-close it, the next scrub writes a new `relaunch_unverified` row. `record_open_page` finds an open row that is not stale and keeps it, so the new incident inherits the old incident's cause and `since`.
4. If the process then restarts before the new incident ends, the restart RECOVERED names the old cause and a `since` that spans both incidents. That is the WR-R2-02 end-state, reached through the cancel path the fix did not cover.

Without step 3, the design converges: the next tick returns the held future and closes. So the cost is an extra WARNING per recovery and a close that is delayed by one cadence.

**Fix:**
- Resolve the outcome as soon as it is known. In `page`, when the page counts as delivered through Sentry (after WR-R3-01, only for outage), `delivered.set_result(True)` immediately and let `_settle_window` skip a done future. A recovered then waits only on the email.
- Size the bounds for the new work, and correct both comments. For example: `READ_TICK_BOUND_S = 2 * _READ_TIMEOUT_S + ops_alert._DELIVERY_WAIT_S + _OPEN_PAGE_TIMEOUT_S`, and the same term for `PROBE_TICK_BOUND_S`.
- In both `finally` blocks, mark the source stale whenever the record was not closed and a recovery was attempted:

```python
finally:
    if not closed:
        ops_alert_open.mark_open_page_stale(source)
    with _LOCK:
        ...
```
