# Phase 164.6.8 Plan 02: ops_staleness_check reader Summary

**One SECURITY DEFINER function pages through the existing `/api/prober-cadence-alert` route when the `cron_sync` heartbeat is stale, absent or twice in error, or when the backfill queue stalls; a 14-arm SQL gate with a biting twin per arm and a parity test pin it.**

## What shipped

- `public.ops_staleness_check() RETURNS BIGINT`, SECURITY DEFINER, `search_path = public, pg_catalog`, EXECUTE revoked from PUBLIC, anon, authenticated and service_role. The migration schedules nothing and its only DO block reads the catalogue (no data-reading RAISE, safe on data-less TEST).
- cron_sync arm (D-11), first match wins: `never_ran`, `heartbeat_stale` (newest closed row older than 2 days), `two_consecutive_errors` (both of the two newest closed rows `error`).
- backfill arm (D-10): `backfill_queue_stalled` (an eligible `pending`/`failed_retry` job past `next_attempt_at` by the ceiling and no claim within it) and `backfill_running_stuck` (a `running` job claimed longer ago than ceiling plus one watchdog tick).
- One observer row per call in `public.cron_runs` (`ops_staleness_check`, status `error` or `ok`, causes and minutes in metadata), written before any outbound call. A refused call rolls it back.
- Post body per stale arm: `cron_name` (`cron_sync` or `backfill`), `gap_minutes` (null when never), `ceiling`, `detected_at`, `cause`. Returns the number of posts queued.
- No recovered notice for these two sources (D-06 is MT5-specific). Recorded so the absence is not read as an omission.
