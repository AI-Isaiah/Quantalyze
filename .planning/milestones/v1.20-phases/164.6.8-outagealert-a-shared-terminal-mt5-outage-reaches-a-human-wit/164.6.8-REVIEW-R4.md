## 2. Round-3 findings: verdict

| Finding | Verdict |
|---|---|
| WR-R3-01 (recovered credited to Sentry) | **Fixed.** `sentry_counts = sentry_ok and event_n == "outage"` (`ops_alert.py:513`). A recovered notice is delivered only on a 2xx from the founder email, and a 502 now releases the window, so the next healthy reading re-sends. The production-shaped test (an event id plus an email 502) bites. |
| WR-R3-02 (re-send claims a restart) | **Fixed.** `_RESEND_REASON` is written in `_finish_recovered`'s `finally` and popped on a closed record, or when the durable read finds nothing. A source with no entry is a previous process's row, and only that case says "restarted". |
| WR-R3-03 (bounds, cancel path skips stale mark) | **Fixed.** Both `finally` blocks mark the source stale whenever the record was not closed, a cancellation included. `READ_TICK_BOUND_S` is now 5 + 5 + 15 + 5 = 30 s. The email POST has a total 10 s deadline, so the real worst case is about 25 s. |
| R3-SFH-01 (healthy reading held behind the email) | **Fixed.** An outage that Sentry took resolves at once. A recovered notice's wait and close run in a held task, so `record_mt5_session_reading` writes the healthy row without waiting. |

**Checked and sound:**

- **Task lifetime.** `_RECOVERY_TASKS` holds a strong reference, and a done-callback discards it. `_finish_recovered` catches `Exception`, so no task dies with an error nobody retrieves. A `CancelledError` (shutdown, or the reset) runs the `finally`, which marks the source stale, unmarks it and records `_REASON_UNDELIVERED`. The row stays open, so the next process re-sends it with the restart text, which is then true. Nothing in `main.py` drains or cancels the set. The loop's own teardown cancels it, and a lost in-memory mark is moot once the process ends.
- **Races between a held task and a new outage or recovery for the same source.** `close_open_page` closes by SOURCE, not by row id, so a held task that outlived its incident would close a NEW incident's row. I checked whether that can be reached:
  - The held task is bounded at about 20 s: `await_delivery` waits at most 15 s, and the POST now settles inside 10 s, then the close takes up to 5 s.
  - Readings for a tracker source arrive once per monitor tick. That cadence is at least `_MT5_SESSION_POLL_INTERVAL_FLOOR_S`, minutes apart, and an outage pages only after `ceil(3600 / interval)` consecutive non-authorized readings.
  - The debt page fires on a busy tick, which is a later tick than the settle.
  - The boot heal runs once, while the monitor waits out its first interval.
  - The heal's two readings in one tick are ordered first, then final.

  So no new incident can record a row while a finish task is still alive. A second recovered while the first is pending gets the holder's future back from the window, so no second email goes out. Both tasks then close, and the second close finds no row, which counts as True.
- **`_RESEND_REASON` lifecycle.** The entry is set only on a failed finish and cleared by a closed record or by a durable read that finds no row. A new incident in between replaces the stale row, and that incident's own recovery goes through the run, which does not read the reason. So a reason never ends up on the wrong incident's notice.
- **`asyncio.wait_for` on the POST.** Cancelling `_post()` unwinds the `async with httpx.AsyncClient`. The `TimeoutError` is caught by the `except Exception` and logged with its class only. `_DELIVERY_WAIT_S` (15 s) is now strictly above the POST's total bound (10 s).
- **Tick bounds.** For the probe: a validation reading awaits one durable read or one write. A retried close inside the hour also awaits an inline close, about 10 s against 5 s of slack. That can be reached only when the probe used its whole lease and thread caps AND the sink is slow. The `finally` then marks the row stale and the next tick converges. Below the floor.
- **The early `set_result(True)` for an outage** cannot be overwritten. `_settle_window` and every other branch check `delivered.done()` first.

## 3. Findings

### WR-R4-01: An OUTAGE is still credited to Sentry when the Sentry rule's 60-minute action interval suppresses the notification. A relapse inside the hour, with a founder-email failure, leaves the founder's last message saying RECOVERED for up to an hour while the terminal is down.

**Severity:** MEDIUM. **Confidence:** 6/10.
**Files:**
- `analytics-service/services/ops_alert.py:508-518`: `sentry_counts = sentry_ok and event_n == "outage"` and the early `delivered.set_result(True)`. The new comment says an outage capture "is covered by a Sentry alert rule that notifies a person".
- `analytics-service/services/ops_alert.py:372-374` (`_settle_window`): `outcome = email_ok or sentry_counts`. On True it returns without releasing the window.
- `analytics-service/services/ops_alert.py:321-322` (`_admit_through_window`): a recovery drops every outage entry of the source, so a relapse is re-admitted at once.
- The rule as recorded in `164.6.8-01-SUMMARY.md`, Task 3: "Ops alert: outage (164.6.8)", "Triggers: first seen, regression, or every event", **"Action interval: 60 minutes"**. Sentry applies an issue alert's action interval per ISSUE. The capture's fingerprint is `["ops_alert", source, cause, "outage"]`, so every outage of one source with the same cause is the same issue.

**Issue:** fixD narrowed the Sentry credit to the event a notifying rule covers. That rule notifies at most once per 60 minutes per issue. A capture inside that interval returns an event id, so `sentry_counts` is True, but nobody is told. The window logic deliberately lets a relapse page at once after a recovery (SFH-F1 / WR-02: "the founder's last message says RECOVERED while the system is down"). In that relapse case, Sentry is exactly the channel that does not deliver.

**Failure scenario (production, DSN set):**
1. 10:00. The jobs terminal pages OUTAGE with cause `ipc_fault`. Sentry notifies the founder, and the email is sent.
2. 10:20. It recovers, and the RECOVERED email arrives. That is the founder's newest message.
3. 10:40. It relapses with the same cause. The window admits the page, because the recovery dropped the outage entry. `capture_message` returns an id, which lands on the same issue, last notified at 10:00, so the rule's action interval suppresses the notification. The founder-email POST fails (a 502 blip or a 10 s timeout).
4. `sentry_counts=True`, so `delivered` resolves True and `_settle_window` keeps the window. The repeat outage readings every tick are suppressed until about 11:40.
5. For about an hour the founder's inbox ends on RECOVERED while the terminal is down. Nothing logs at ERROR that the page reached nobody. `_post_founder_email` logs its own failure, but the "no channel delivered" ERROR is skipped because the outcome counted as True.

This needs a relapse with the same cause inside 60 minutes of the last notification, plus an email failure on that one POST. A flapping terminal makes the first condition common. The code's correctness rests on a live Sentry setting, and that setting contradicts the comment the code carries.

**Fix:** credit Sentry for an outage only when its rule would actually notify: no notified capture of the same fingerprint within the rule's action interval. For example:

```python
# ops_alert.py
_SENTRY_RULE_ACTION_INTERVAL_S: Final = 3600.0  # "Ops alert: outage (164.6.8)", 01-SUMMARY Task 3
_last_sentry_credit_at: dict[tuple[str, str, str], float] = {}

# in page(), replacing line 513
last = _last_sentry_credit_at.get(key)
sentry_counts = (
    sentry_ok
    and event_n == "outage"
    and (last is None or now - last >= _SENTRY_RULE_ACTION_INTERVAL_S)
)
if sentry_counts:
    _last_sentry_credit_at[key] = now
    delivered.set_result(True)
```

Then an email failure on a relapse releases the window, and the next reading retries the email. Add a test: an outage paged and credited, then a recovery, then the same-cause outage 20 minutes later with an event id and an email 502. Assert that `await_delivery` is False and the next reading POSTs again. The alternative is to record in the 01 SUMMARY that a relapse inside the hour depends on the email alone, and to drop "covered by a Sentry alert rule that notifies a person" from the comment at `:508`.
