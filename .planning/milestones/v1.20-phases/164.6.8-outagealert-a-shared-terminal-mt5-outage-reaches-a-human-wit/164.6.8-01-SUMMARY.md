## Deviations from Plan

**1. [Rule 1 - Bug] Recovered events log at WARNING, not ERROR**
- **Found during:** Task 1 design.
- **Issue:** The plan says "every call logs ERROR". Sentry's default `LoggingIntegration` turns an ERROR log into a Sentry event, so a *recovery* notice would itself raise an error event while telling the founder to stop worrying. The plan already sends the recovered capture at `warning` level.
- **Fix:** `logger.log(ERROR if outage else WARNING, ...)`. Every outage call still logs ERROR; the window and POST are unchanged. Plan 04 (which sends `recovered`) should not count an ERROR for it.
- **Files:** `analytics-service/services/ops_alert.py`.

**2. [Rule 2 - Missing critical functionality] Stable Sentry fingerprint**
- **Issue:** The capture message embeds since/detail, which vary per call, so each hourly page would mint a NEW issue and a frequency rule ("seen more than N times in M minutes") would never see a recurrence. D-02 requires frequency delivery.
- **Fix:** `scope.fingerprint = ["ops_alert", source, cause, event]`; tested by `test_the_capture_is_grouped_by_key_not_by_its_varying_text`.

**3. [Rule 2 - Missing critical functionality] Scrub order**
- **Issue:** The plan lists the digit pass before the by-value MT5 replacement. With that order `Broker-Demo12345` becomes `Broker-Demo<digits>`, the by-value match then misses it, and the server-name prefix leaks.
- **Fix:** by-value replacement first. Tested by `test_scrub_alert_detail_redacts_the_server_by_value_before_the_digit_pass`.

**4. [Rule 3 - Blocking] `vercel-cron-limits.test.ts` fails on any new `api/cron/*` handler**
- **Issue:** The H-1155 census requires every `src/app/api/cron/<dir>/route.ts` to be scheduled in `vercel.json`. `ops-alert` is a POST-only service-key endpoint (under `/api/cron/` only so the session proxy bypasses it); Vercel Cron sends GET with `CRON_SECRET`, so a schedule could only 401.
- **Fix:** an explicit `UNSCHEDULED_CRON_DIR_HANDLERS = ["ops-alert"]` exclusion in the disk walk, plus a test that the entry is never scheduled. The "nine production crons" pin is unchanged. File is outside the plan's `files_modified`.
- **Commit:** 81f692b47.

**5. [Plan-addition] `extra_tags` kwarg on `page()`**
- The plan says to keep the `prober_cadence_alert` tag. An unscoped `set_tag` would label every later event (the WR-03 defect the plan itself cites), so `page` takes an optional `extra_tags` applied inside the capture's own scope. Backward compatible.

**6. [Process] Branch name outside the `agent-*` allow-list**
- The pre-commit assertion's worktree allow-list expects `agent-*` branches. This worktree's branch is `wt/164.6.8-p01`, assigned by the orchestrator; the protected-branch check passed and the branch allow-list was not applied.

## Task 3: RESOLVED 2026-10-13 (founder checkpoint, D-02)

Founder approved "Create it, 60 min". The orchestrator created the rule through the Sentry tool and read it back. No Sentry org, project, rule or detector ids are recorded here.

**Existing rules before this change** (one Sentry project, `quantalyze`, three issue rules):
- "Send a notification for high priority issues". Triggers: new high-priority issue, existing issue escalates to high priority, or regression. Action interval 0. On its own it does not re-notify a sustained outage, because one issue keeps the same fingerprint.
- "MT5 terminal wedge persists (164.6.5)". Fires on every event, filtered to messages containing "mt5 session heal: ipc_fault". Interval 60.
- A pull-request notification rule, unrelated.
- Verdict: no existing frequency or per-event rule matched `ops_alert_event = outage`.

**Created:** "Ops alert: outage (164.6.8)".
- Triggers: first seen, regression, or every event.
- Filter: tag `ops_alert_event` equals `outage`.
- Action: email to issue owners, falling back to active members, the same target as the existing rules.
- **Action interval: 60 minutes.**
- Status: active.

**Cadence:** a sustained outage emails at most once every 60 minutes, matching the helper's hourly capture window.

**Still open:** delivery to the founder's inbox is not yet proven; plan 09's drill proves it. D-03 is unchanged: whether the alarm watches its own delivery (`PROBER-ALERT-DELIVERY-UNVERIFIED-01`) is neither closed nor narrowed here.
