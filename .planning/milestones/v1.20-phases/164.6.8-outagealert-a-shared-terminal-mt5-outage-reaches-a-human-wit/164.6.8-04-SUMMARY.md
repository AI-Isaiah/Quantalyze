# Phase 164.6.8 Plan 04: OUTAGEALERT jobs-terminal outage tracker Summary

A separate per-role outage run now pages the founder (Sentry capture plus email, through `ops_alert.page`) when the jobs terminal reads anything other than a measured `authorized` for `blind_run_escalation_threshold(poll_interval_s)` consecutive readings, sends exactly one recovered notice on the first measured authorized reading, and carries the scrubbed pre-recycle wedge evidence.

## What was built

- `services/mt5_outage_alert.py` (new). Per-role state (`count`, `since`, `last_cause`, `paged`, `evidence`, `file_versions`) under a `threading.Lock`, because the heal stashes from a worker thread and the tracker reads on the event loop.
  - `note_outage_reading(role, reading_state, kind, code, *, poll_interval_s)`: increments on every non-authorized reading, pages when `count >= threshold` and `kind not in _DECIDED_BLIND_KINDS`, on every qualifying reading, and lets the helper's hourly window per `(source, cause, event)` bound captures and emails (D-05). A measured authorized reading sends one `recovered_from_<cause>` notice only if the run paged, then pops the run (stash included).
  - `note_wedge_evidence(role, fragment)`: first fragment of a run wins. `note_recycle_file_versions(role, value)`: its own field, latest wins. Opening a run keeps a stash that already exists (the heal thread stashes before the reading reaches the loop).
  - All three are one `try` with the IN-06 handler shape and never raise.
- `record_mt5_session_reading`: one function-local import and one `await note_outage_reading(ROLE_JOBS, ...)` right after `classify_reading`, inside the existing single `try`, before the not_measured branch. Its not_measured line is now ERROR (was WARNING) when `blind` (D-04); message text unchanged. `_reset_session_episode_state_for_tests` also resets the tracker (function-local import).
- `mt5_relogin._escalate_ipc_fault`: stashes the pre-recycle fragment right after `_capture_wedge_evidence` and the recycle's `file_versions` right after `verdict = result.verdict`, both through `_stash_for_outage_alert`, a wrapper that cannot raise.
- Counting semantics (stated in the module docstring): the threshold counts READINGS, and `record_mt5_heal_outcome` records two readings on a tick where the heal ran, so a persisting fault the heal acts on reaches the threshold in fewer ticks than one per reading. That is the existing threshold's meaning, not a new number.

## Deviations from Plan

**1. [Rule 3 - Blocking] `tests/conftest.py` modified (outside `files_modified`)**
- **Issue:** many existing tests drive `record_mt5_session_reading` far past the threshold. Unpatched, each would now call the real `ops_alert.page` (a Sentry capture and a scheduled founder-email POST).
- **Fix:** an autouse fixture, `mt5_outage_pages`, swaps `mt5_outage_alert.ops_alert` for a recording stub and yields the list of pages, in the style of the existing handover and scrub refusal fixtures. A test wanting the real channel puts `ops_alert` back (`real_channel` in the new file does).
- **Commit:** ad439b2c4.

**2. [Rule 1 - Bug] The IPC code was eaten by the page scrub**
- **Issue:** `scrub_alert_detail` replaces every run of five or more digits, and `-10003` .. `-10005` are exactly five digits, so a detail saying `code=-10005` reached the founder as `code=-<digits>` and lost the one field the wedge calibration needs.
- **Fix:** the code is formatted with thousands separators (`code=-10,005`). It is an `int` the classifier produced, never an account number. Pinned by `test_the_ipc_fault_code_survives_the_digit_scrub_in_the_page`. For the same reason `since` is rendered at second precision in the detail (microseconds are a six-digit run); the `since` argument to `page` stays a full datetime.

**3. [Rule 3 - Blocking] Test load flaked two existing monitor tests**
- **Found during:** Task 2 verification. `test_mt5_session_monitor.py::test_CRITERION_2_a_dark_reading_drives_the_heal...` and `..._CRITERION_3_an_already_authorized_terminal_...` failed intermittently (3 of 8 runs) when run beside the new file under `-n 4`. Their log shows `the tick did not complete inside its own 0.0s cadence`: they run the monitor at a test cadence of effectively zero, a timing race that starves under CPU load. Measured: 12/12 clean on the plan's base commit and 10/10 clean on this branch without the new file (both over the episodes, monitor and handover test files under `-n 4`), so the cause was the new file's load, specifically 24 interpreters spawned at once by the import-order test.
- **Fix:** the import-order test now runs its 24 interpreters two at a time. After that, 10 consecutive runs of the four-file verification set under `-n 4` were green. The monitor tests' own race is pre-existing and was not touched (out of scope); it is worth a TODOS entry if it ever flakes in CI.

## Behaviours worth the next reader's attention

- The hook's function-local import sits inside the recorder's single `try`, as the plan decided. If that import ever failed, the recorder's own handler would swallow it and skip the episode write too. The tracker itself never raises, so only an import-time failure could do that, and the import-order test pins that it cannot.
- Every blind reading at or after the threshold now logs the episode line at ERROR, so each poll adds a Sentry event through `LoggingIntegration` on top of the helper's hourly capture. That is D-04 as written ("the blind-run log line is ERROR"). The new "Ops alert: outage" rule filters on the `ops_alert_event` tag and is not triggered by it.
- The cause is the reading's own kind, and D-05's window is per `(source, cause, event)`. A sustained outage whose readings alternate between two kinds (for example `ipc_fault` and `busy_skip`) therefore pages once an hour per kind, not once an hour in total. The run itself, its `since` and the single recovered notice are unaffected.
- A comment at `mt5_session_episodes.py` line ~733 still says "a blind-run WARNING"; it is history about the 164.6.5 alarm design and was left alone.
- State is in-process, as the blind-run counter is: a redeploy forgets the run and delays a page by at most one threshold (T-164.6.8-20, accepted).
