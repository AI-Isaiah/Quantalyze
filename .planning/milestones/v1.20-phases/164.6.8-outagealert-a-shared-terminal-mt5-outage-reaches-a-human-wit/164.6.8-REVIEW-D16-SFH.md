# 164.6.8 D-16 silent-failure review

## SFH-D16-01 (MEDIUM, confidence 4): an event id proves the envelope was queued, not sent, and it now closes a one-shot record

- File: analytics-service/services/ops_alert.py, `page` (`sentry_ok = event_id is not None`, `sentry_counts = sentry_ok`).
- Verified in sentry_sdk 2.71.0 `client.py` `capture_event`: `return_value = event_id` is set right after `self.transport.capture_envelope(envelope)`. The id comes back once the envelope is queued. A 429 rate limit, a full queue or a network failure is dropped later, in the transport thread, with no signal to `page`.
- Checked and fine: a `before_send` that returns None, a sampled-out event and an unset DSN (no `init`, so the NonRecordingClient) all return None, so they are not credited. `init(dsn="")` is not used.
- Scenario: a recovery is credited on a queued id, `close_open_page` closes the durable row, and the transport drops the event during a Sentry quota or rate-limit episode. Before D-16 the email still gated a recovered notice. Now nobody gets it, and the one-shot record that would have re-sent it is gone, with no ERROR anywhere. The outage path had the same exposure before this change, but it has no one-shot record.
- This follows D-16's literal wording ("event id not None"), so it is a residual risk and not a deviation.
- Fix (optional): after a credited recovered capture, call `sentry_sdk.flush(timeout=...)` off-thread. Or log at WARNING that the notice is credited on queue only. Or have the caller pair the close with an email 2xx once Resend is configured.

## Checked and clean

- Email failure after a Sentry credit stays loud. `_post_founder_email` logs ERROR itself for every failure path (unresolved URL, missing SERVICE_KEY, non-2xx, exception). `_settle_window` returns early on a credit, so only the "no channel delivered" summary is skipped, which is correct since a channel did deliver.
- "At most once per window": the email is scheduled only for admitted pages, so a failing email logs once per window.
- The email task's exception is observed. `_settle_window` always calls `task.exception()` or checks `task.cancelled()`, and `_post_founder_email` catches Exception.
- A failed capture (None or raise) leaves `sentry_ok` False, so the window is released and the next reading retries.
- A durable record cannot close without `await_delivery` True. The callers (`mt5_outage_alert._close_after_recovered`, `mt5_validation_liveness`) close only on True, and mark the record stale otherwise.
