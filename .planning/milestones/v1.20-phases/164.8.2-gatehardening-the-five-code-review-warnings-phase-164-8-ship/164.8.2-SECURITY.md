### What rounds 2–3 changed, checked adversarially

| Question asked of the new code | Answer, measured |
|---|---|
| Can a verdict file be written where the scan did NOT clear? | **No.** `backup-scan.ok` is the statement AFTER both the identity floor and the `hits` check `exit 1`; `credential-scan.ok` is the last statement of `refuse_credential_in_published_sql`, after the hits `fail` and the `scanned == 4` floor, and its own write is `|| fail`-checked |
| Can one verdict file stand in for the other? | **No** by filename — the script writes only `credential-scan.ok`, the backup step only `backup-scan.ok`, and a wiring arm pins each writer's sentence to its own gate. ⚠️ The two gates grep for the SAME substring, so the FILENAME is the only discriminator (see `[164.8.2-VERDICT-SENTENCE-SHARED]` below) |
| Can a stale verdict survive a re-run? | **No.** `runs-on: ubuntu-latest`; a re-run gets a fresh `RUNNER_TEMP`. Within a job nothing rewrites `ledger.csv`, `schema-before.sql` or the four `.sql` files after their scan |
| What if `outdir` / `RESTORE_OUT_DIR` is empty or unset? | **Fail-closed both ways.** In the workflow `outdir` is a literal `${RUNNER_TEMP}/test-backup` under `set -u`. In the script an empty `RESTORE_OUT_DIR` becomes an OWNED `mktemp -d`, so the four `.sql` files and the verdict never appear in the staged directory and nothing is staged. `cleanup_out_dir` removes only `OWNED_OUT_DIR`, never the workflow's directory |
| Is anything reaching the artifact UNGATED? | **One file: `README.txt`** — and it is a `<<'BACKUP_README'` **quoted** heredoc, so it carries no run-time interpolation at all. Every other staged name is behind `backup_ok`, `scan_ok` or `REDACT_OUTCOME = success`. Traced all four `if: always()` steps: the mutex release writes nothing into the backup directory, the redaction step only DELETES, staging is enumerated, and the upload's `path:` is the staging directory alone. There is exactly one `upload-artifact` in the file |
| Does a flagged file fail to reach the artifact even when `rm -f` fails? | **Yes, twice over.** `withhold()` reports by name, counts a second hit and never aborts; the `[ -e ]` post-check catches an `rm -f` that exited 0 without removing. And because the run then exits before writing `backup-scan.ok`, the staging step denies BOTH backup files regardless. A wiring arm asserts the unwithholdable case does not leave the run green |
| Did the marker-step fix reach both copies? | **Yes** — byte-identical, both rc-bounded (`-gt 1` ⇒ MEASURE_FAIL, exit 1) and both `grep -aEiq`. The PROD refusal now fails CLOSED |
