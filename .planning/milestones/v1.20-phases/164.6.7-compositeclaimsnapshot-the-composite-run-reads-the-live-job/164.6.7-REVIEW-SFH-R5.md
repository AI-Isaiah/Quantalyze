## MEDIUM

### SFH-R5-01 — A stamp call cut off by the handler's wall-clock timeout still loses the curated cause (the class SFH-R4-01 closed, through the cancellation exit)

**Where:** `_stamp_io` (`except Exception` only); `dispatch`
(`asyncio.wait_for(handler(job), timeout=timeout)`); the `classify_exception`
`asyncio.TimeoutError` arm.

**Failure scenario:** the handler's per-kind deadline fires while a stamp call
is still waiting: a `db_read_with_retry` 504 sequence, a slow upsert, or a
saturated `_DB_EXECUTOR` queue. `wait_for` cancels the handler. The resulting
`CancelledError` is a `BaseException`, so it passes straight through
`_stamp_io`'s `except Exception`. No ERROR line is written, there is no capture,
and no `StampIOUnavailable` is raised. `dispatch` then sees `TimeoutError` and
files `transient` with `last_error = "Handler exceeded timeout: "`. The curated
cause is recorded nowhere. The only earlier line that carries it is the
closure's `detail` WARNING, which is gated on `detail` and not at ERROR. If the
retries run out, the bridge writes generic copy. That is the exact end state
SFH-R4-01 was meant to rule out.

**Measured** in the clean HEAD export with a throwaway probe. The run was an
unmarked `stitch_composite` with no members (cause `Composite strategy has no
member keys.`). `db_read_with_retry` was patched to await a sleep longer than a
0.3 s `TIMEOUT_PER_KIND["stitch_composite"]`. Result: `error_kind='transient'`,
`error_message='Handler exceeded timeout: '`, 0 ERROR lines carrying the cause,
0 WARNING lines carrying it.

**Why MEDIUM and not HIGH:** the disposition (`transient`) is the correct one.
Only the cause is lost, and only when a stamp call straddles the deadline.
It is not structural either. The composite has no tail reserve for its stamp
I/O: only the smoothed third pass is sliced
(`_MTM_SECOND_PASS_BUDGET_FRACTION` of the remaining time since
`_stitch_start`), and every member-level `_stamp_failed` runs after unsliced
member crawls. So a slow member fan-out can put a stamp at the deadline. A 504
retry sequence can then outlast it, because each attempt waits out the gateway
window. The derive path reserves `_DERIVE_POST_CRAWL_RESERVE_S`, which makes it
less exposed.

**Secondary effect:** the cancelled executor thread keeps running, so a
cancelled loud write can still land after the job was filed `transient`. The
upsert is idempotent and the retry re-decides, so this is harmless. It does
mean `last_error` and `strategy_analytics` can briefly disagree.

**Recommendation:** add a cancellation arm to `_stamp_io` that logs the cause
and never swallows the cancel:

```python
    except asyncio.CancelledError:
        logger.error(
            "%s: %s for strategy %s on compute_job %s was CANCELLED (handler "
            "deadline or shutdown). No terminal stamp is confirmed for: %s.",
            site, op, strategy_id, job_id, cause,
        )
        raise
```

Pin it with a test shaped like the probe above: the stamp call hangs past a
tiny per-kind timeout, and the test asserts exactly one ERROR line carrying
the cause.

### SFH-R5-02 — `test_stamp_io_exhaustive.py` discovery is blind to any closure call made off the closure's thread

**Where:** `_in_a_stamp_closure`, `_Recorder.on_execute`, `_RecordingClient`.

**Failure scenario:** discovery counts a call only when the closure's frame is
on the stack of the thread that runs `.execute()`. The harness patches
`services.job_worker.db_execute` and `services.db.db_execute` inline, so those
two paths are seen. A call issued through `asyncio.to_thread(...)`,
`loop.run_in_executor(...)` or a task started with `asyncio.create_task(...)`
runs where the closure frame is absent. The recorder answers "not in a
closure", and the call is never recorded, never failed and never
parametrised. It gets no RED case, just silence. The stitch path already uses
`asyncio.to_thread` (WEDGE-01), so this is a plausible future edit rather than
a contrived one. Two more routes are blind in the same way. First, a call on
a client attribute that `_RecordingClient.__getattr__` forwards unwrapped
(`.schema(...).table(...)`, `.postgrest`, `.storage`): only `.table()` and
`.rpc()` are wrapped. Second, a call on a client the helper obtained before the
closure ran, other than `ctx.supabase` or the patched
`services.job_worker.get_supabase`, such as another module's own
`services.db.get_supabase()`. In the fake environment that second route
usually fails the clean run loudly, but the harness does not guarantee it.

**Measured** in the clean HEAD export. I added one unwrapped
`await asyncio.to_thread(lambda: supabase.table("strategy_analytics")...execute())`
before the composite status read. All 55 cases in the file still passed, and
the collected case count did not change: the call was never discovered. The
same read written as `await db_execute(...)` turned 8 cases RED.

**Why MEDIUM:** HEAD has no live defect of this shape. The hand-read in the
verdict above finds no such call. The weakness is that the gate's own claim
("A call added to either closure later is picked up by discovery … without
editing this file") is false for a whole category of calls, and it fails
GREEN.

**Recommendation:** pair the dynamic discovery with the repo's house idiom, a
static source-region scan. Bound each closure by indentation, as
`tests/test_ledger_refresh_publish_guard.py` already does, and assert that
every `db_execute(`, `db_read_with_retry(`, `to_thread(`, `run_in_executor(`,
`create_task(`, `.execute(` and `get_supabase(` in the region appears either
inside a `_stamp_io(` argument or inside `_heal_delete_basis_series`. The
frame walk catches a call that the scan's regex misses, and the scan catches a
call that runs off the frame. Add a neuter note for each. Also narrow the
docstring's "picked up by discovery" claim to what the frame walk can see.

## LOW

### SFH-R5-03 — `_heal_delete_basis_series` failure: the permanent disposition is safe, but the WARNING hides code defects and uses the unscrubbed form

**Where:** `_heal_delete_basis_series` (`except Exception as _heal_exc` →
`logger.warning(... %s, _heal_exc)`); pinned by
`test_a_failing_post_stamp_call_keeps_the_landed_stamp`, which asserts
`capture_exception.call_count == 0`.

**Is leaving it permanent with a WARNING safe? The disposition, yes.** The loud
stamp has landed with the cause in `computation_error`, so no cause is lost. A
`transient` raise would re-run the whole crawl for a job whose stamp already
landed, and the heal is defence in depth. The row is `failed`, so
`src/lib/strategyGate.ts` returns `ANALYTICS_FAILED` and a stale series row is
not rendered. **The observability is the weak part:**

- A `_READ_PROGRAMMING_ERRORS` member is swallowed at WARNING. Example: a
  `persist_basis_series` signature drift raises `TypeError` on every failed
  loud stamp, forever. That contradicts the round-4 policy stated above
  `_READ_PROGRAMMING_ERRORS` ("EVERY site that classifies a failed read or
  write handles them the same way: log at ERROR, one tagged capture, then
  re-raise"). The heal is the one database site left out, and the policy
  sentence does not name that exception.
- A persistent infrastructure failure of the heal is equally invisible: a
  permission denial on `strategy_analytics_series`, for instance. There is no
  capture, and the worker loop logs failed jobs at WARNING, so no Sentry event
  ever records that stale series rows are piling up.
- `_heal_exc` is interpolated raw. Every newer line uses
  `_read_failure_text(exc)`, which is scrubbed and bounded (I-R4-4's stated
  rule).

**Recommendation:** keep the permanent disposition and the absence of a raise
for infrastructure errors. Log the failure at ERROR with
`_read_failure_text(_heal_exc)` and make one `_capture_read_failure` call, so
that a heal that never succeeds reaches Sentry. For a `_READ_PROGRAMMING_ERRORS`
member, either do the same and say explicitly that a re-raise is avoided on
purpose (the stamp has landed), or amend the policy sentence to name the heal
as the exception. Moving `test_a_failing_post_stamp_call_keeps_the_landed_stamp`'s
`capture_exception.call_count == 0` and ERROR-count assertions is part of the
fix. The runbook's alert-volume row "single-key series heal fails … +0" moves
with it.

### SFH-R5-04 — Nothing pins that the curated cause survives `classify_exception`'s 500-character cut

**Where:** `StampIOUnavailable` text built in `_stamp_io`;
`classify_exception` (`str(exc)[:500]`).

**Failure scenario:** today the worst case is about 420 characters, about 80
under the cut (see the verdict). The exhaustive test uses the two SHORTEST
causes, 38 and 66 characters. A new curated `message` of about 270 characters
or more, or an f-string site whose interpolation grows (the
`len(members)`/`_max_members` sentence, the `venue!r` sentence), would have its
tail cut off in `last_error` with no test going RED. The stamp-site sentences
have been growing: the longest is 187 and was added for the annualization
refusal.

**Recommendation:** add a static test that collects every literal first
argument to `_stamp_failed` / `_stamp_strategy_analytics_failed` and every
`stamp_detail=` value, as the AST walk in this review did. It should assert
that the worst-case prefix (the longest `site`, the longest `_STAMP_OP_*`, a
120-character failure plus a class name, and the joining words) plus the
scrubbed message fits in 500. f-string sites can be bounded by their literal
part plus a stated allowance.

### SFH-R5-05 — `dict(existing_row.get("data_quality_flags") or {})` sits outside `_stamp_io` in the composite `_stamp_failed` (pre-existing, M-2)

**Where:** the composite `_stamp_failed`, immediately after the wrapped
status read.

**Failure scenario:** `data_quality_flags` is `jsonb`. A non-object value is
unlikely but storable, such as a non-empty array of scalars or a string. Then
`dict(...)` raises `ValueError` or `TypeError` after the read succeeded and
before any write. For `ValueError`, a stamp raised inside the F-5 MTM `try` is
caught by that arm's `except ValueError`, which calls `_stamp_failed` again
under the chain-break cause. That is the misattribution IN-04 closed for
`MarkerStateNotLoggable`. The second call fails the same way and propagates.
For `TypeError`, the job is filed `unknown`. In both cases no ERROR line
carries the cause and `last_error` names only the `dict()` failure.

**Recommendation:** guard the shape (`existing_flags = dict(raw) if
isinstance(raw, dict) else {}`, plus a WARNING naming the coercion) rather than
wrapping a non-I/O step in `_stamp_io`. Low priority: this is pre-existing and
needs a malformed row.

## INFO

### SFH-R5-06 — A programming error in a stamp call leaves `last_error` without the cause (documented trade-off, confirmed)

`_stamp_io` re-raises a `_READ_PROGRAMMING_ERRORS` member unchanged, so
`classify_exception` files `unknown` with the exception's own text, and the
curated cause lives only on `_stamp_io`'s ERROR line. This is the stated
decision (the block above `_READ_PROGRAMMING_ERRORS`), and
`test_a_programming_error_in_a_stamp_call_is_unknown_and_captured` pins the
ERROR line and the capture. One caveat worth a sentence in that block:
`KeyError`/`TypeError`/`IndexError` can also come out of a client library
parsing an unexpected gateway body. Such an infrastructure answer is then
labelled a programming error. The retry budget and the user sentence are the
same, so only the label moves.

### SFH-R5-07 — The WR-01 exposure is unchanged by round 4, not widened

A `StampIOUnavailable` on the D-15 protected path (a failed marker re-read or
error-only write) files the job `transient`. The bridge's `failed_retry`
transition rewrites a plain `complete` row to `computing`, so the retry's entry
snapshot no longer protects it, and a second failure takes the LOUD path. Before
round 4 the same failed calls also ended the attempt and were retried: the
marker read and composite status read already raised a transient, and the
unwrapped error-only write's raw exception was classified on its own. So round 4
did not widen the exposure. It remains the documented WR-01 caveat above
`MarkerLiveState`.

### SFH-R5-08 — `_refresh_marker_live_state` and the entry publish-state read: programming-error re-raise verified

At both sites a `_READ_PROGRAMMING_ERRORS` member is logged at ERROR with
`_read_failure_text`, captured once with the job tag, and re-raised unchanged.
Everything else becomes `READ_ERROR` plus text (chain edge and tail mirror) or
`RefreshMarkerRereadUnavailable` (entry read). The entry read also closes the
exchange before either raise. At the tail mirror a re-raise re-runs the derive
after the hop-2 enqueue, and the comment records that the enqueue dedup serves
the in-flight hop 2. Nothing is swallowed and no finding is raised.
