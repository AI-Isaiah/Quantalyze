# 164.6.7 — Silent-failure review, round 1

Cited by symbol, not by line. Nothing here was run against any remote database; the only
execution was the three affected pytest files from `analytics-service/` with the repo venv:
`118 passed`.

## Verdict

The fail-safe direction holds. Every way the live re-read can fail answers "not marked": no
id, no row, a non-dict row or metadata, a different source, and a raised exception. Every one
of those takes the LOUD stamp. None of them ends up protected. I checked the one library shape
that could have bitten: postgrest 2.31 `maybe_single().execute()` returns `None` for zero rows
instead of raising, and `_refresh_marker_still_on_row` reads it through
`getattr(res, "data", None)`, so that case is handled. The tests pin the three RED cases and
one GREEN control. The fake serves the live row only for the seeded id, so a re-read of the
wrong row turns the control RED instead of passing quietly. The probe's `_judge` needs a
trusted control before it accepts any retracted reading.

What remains is **operator visibility**, not suppression. Every failed re-read now turns a
background refresh into an un-publish of a live factsheet. The only record of that is a
WARNING, and some of those warnings name the wrong cause. The probe also has two places where
it can pass or abort for a reason other than the one it prints.

## HIGH

### SFH-01 — A failed re-read un-publishes a live factsheet, and the only record is a WARNING that never reaches Sentry

**Location:** the `except Exception` arm of `_refresh_marker_still_on_row`, and the new
`logger.warning` at the composite honour site in `_stamp_failed` (`run_stitch_composite_job`).

**Issue.** The loud path is loud for the account holder: `computation_status='failed'`, and
`strategyGate` renders ANALYTICS_FAILED. It is quiet for operators. `sentry_init.py` calls
`sentry_sdk.init` without a `LoggingIntegration(event_level=...)`, so the default event level of
ERROR applies. Both warnings on this path become breadcrumbs, never events. The phase built this
arm for a transient infra fault during a background refresh: a PostgREST gateway timeout, an
httpx connect error, a 5xx. That fault now un-publishes a funded composite's live factsheet, and
nobody is paged. Before this phase, the same fault could not affect the decision at all.

**Hidden errors.** `postgrest.exceptions.APIError` (gateway timeout, 5xx, a 406 when more than
one row matches), `httpx.TransportError`, and `RuntimeError` from a shut-down executor. The
broad catch also absorbs programming errors (`AttributeError`, `TypeError`), for example after
a supabase-py API change. Those would switch off composite protection for EVERY marked refresh,
and each occurrence would show up only as one warning line. The control test
(`test_marker_still_on_the_live_row_stays_error_only`) catches that only in the test fake, not
against the real client.

**User impact.** A live composite factsheet goes dark after one network blip. The logs say
"could not re-read" at WARNING, and nothing alerts.

**Recommendation.** Keep the fail-safe direction. Make the downgrade observable:

```python
    except Exception as exc:  # noqa: BLE001
        logger.error(
            "ledger-refresh: could not re-read the refresh marker on compute_job %s "
            "(%s: %s) — treating the marker as RETRACTED; a marked refresh will take "
            "the LOUD terminal path and un-publish a live factsheet.",
            job_id, type(exc).__name__, exc,
        )
        return False
```

Or call `sentry_sdk.capture_exception` there with the job id in `extra`. If the design can
afford it, the stronger alternative is to classify a transient re-read failure as a transient
job failure and let the job retry, rather than resolving it into a destructive stamp. That is
a decision for the phase owner, not a drive-by change. Surface it, don't average it.

### SFH-02 — The composite site's warning claims "RETRACTED … a user-initiated request was served" whenever the helper returns False, whatever the real cause

**Location:** the new `logger.warning("stitch_composite: the refresh marker on compute_job %s
has been RETRACTED since the claim …")` inside `_stamp_failed`.

**Issue.** `_refresh_marker_still_on_row` returns a bare `bool`. The site cannot tell a real
retraction from these other causes:
- `job_id` is falsy (logged as `compute_job None has been RETRACTED`),
- `maybe_single` found no row (the helper logs nothing, so this warning is the ONLY record, and it is false),
- the live metadata is not a dict, or its `source` is some other marker,
- the read raised (the helper's own warning is followed by this one, which asserts a user-initiated request that never happened).

Four different root causes produce one log line that confidently names the wrong one. Six
months from now, whoever reads it will go looking for a user's resync that doesn't exist.
Three single-key sites already use the same shape (the `derive_broker_dailies` stamp closure
and the chain-edge forward), so this phase copied an existing defect. It is a class, not a
point fix (Rule 11: surfacing, not forking).

**Recommendation.** Have the helper return the reason, and log it at each of the four sites:

```python
async def _refresh_marker_live_state(supabase, job_id, expected) -> tuple[bool, str]:
    # ("still_marked" | "retracted" | "no_job_id" | "no_row" | "other_source" | "read_failed")
```

Say "RETRACTED … user-initiated" only for `retracted`, which means the live metadata carries
`refresh_marker_retracted == expected`, the TypeScript helper's write shape. Log `no_row` and
`no_job_id` at ERROR, because a claimed job whose row has vanished is an invariant breach.

## MEDIUM

### SFH-03 — Probe: `python_branch=error_only` is read from an UNCHANGED status, so a handler that stamped nothing reads as "protected"

**Location:** `_run_arm` in `probe_composite_claimtime.py`, where
`status_after_run == _SEEDED_STATUS → python_branch = "error_only"`.

**Issue.** The error-only branch writes `computation_error` and leaves `computation_status`
alone. That is also what `strategy_analytics` looks like when the handler wrote nothing: an
earlier permanent return, a stamp that raised inside `db_execute` but was absorbed higher up,
or a write that PostgREST accepted and applied to zero rows. The control arm's
`python_branch == "error_only"` requirement in `_judge` is met without `_stamp_failed` ever
running. `error_kind == "permanent"` does not close this gap, because every early exit in the
handler returns permanent.

**Recommendation.** `_seed` leaves `computation_error` NULL. Read it in `_read_analytics`, and
require it to be non-NULL after the run before classifying either branch. Raise `ProbeError`
if it is still NULL. That one check separates "the handler chose error-only" from "the handler
did nothing".

### SFH-04 — Probe: the DB loopback guard checks the URI netloc, which libpq's `host` / `hostaddr` query parameters override

**Location:** `_read_stack_env` (`urlparse(values[key]).hostname`), then
`psycopg.connect(env["DB_URL"], ...)` in `_main_async`.

**Issue.** libpq lets query parameters override the netloc. With
`postgresql://127.0.0.1:54322/postgres?hostaddr=<remote>`, the guard sees `127.0.0.1` and the
connection goes to `<remote>`. The source is `supabase status -o env`, which is trusted
output, so this is defence in depth. But this checkout's CLI is linked to PRODUCTION, and the
docstring claims both URLs "must name a loopback host before … any client exists". The guard
does not quite deliver that claim. There is also no check after connecting.

**Recommendation.** Parse with `psycopg.conninfo.conninfo_to_dict(values["DB_URL"])` and
require every `host` and `hostaddr` entry to be loopback. After connecting, also assert
`conn.info.host` (or `SELECT inet_server_addr()`) is loopback, or NULL for a Unix socket,
before `_assert_bridge_definition` runs.

### SFH-05 — Probe: `_cleanup` in `finally` can replace the arm's real failure with a cleanup error

**Location:** the `try/finally` in `_run_arm` → `_cleanup`.

**Issue.** Suppose an arm raises `ProbeError("the claim did not return the arm's own job")`
and `_cleanup` then raises too, say an FK violation from a row the handler or
`mark_compute_job_failed` wrote that references the strategy. Python raises the cleanup
exception and keeps the original only as `__context__`. `main` prints
`HARM-PROBE error: ForeignKeyViolation`, and the fail-loud message that names the real problem
is lost. A half-cleaned lane can also leave a claimed `stitch_composite` row behind. The next
run's 1000-row claim then picks it up (see SFH-07).

**Recommendation.** Wrap `_cleanup` in its own `try`. If an arm exception is already in
flight, log the cleanup failure to the handler log and re-raise the ORIGINAL. Otherwise raise
the cleanup failure as a named `ProbeError("cleanup failed for an arm")`.

### SFH-06 — Probe: running without `--expect` prints `result=ok` and exits 0 having asserted nothing

**Location:** `_judge`, `if expect is None: return "ok", 0`.

**Issue.** This is print-only mode by design. Plan 01's tracer greps the verdict lines
itself. But the summary line `HARM-PROBE summary: expect=none … result=ok` reads as a pass. A
future runbook step or a copied command that leaves out `--expect` gets a green, vacuous run.

**Recommendation.** Return `"unasserted", 0` so the summary line says `result=unasserted`.
Nothing in the tree greps for `expect=none … result=ok`, so the rename is safe.

## LOW

### SFH-07 — Probe: the 1000-row claim can take foreign `stitch_composite` rows and leave them claimed; the count is printed but never judged

`_run_arm` and `_drive_next_bridge` claim with `p_batch_size: 1000`. `foreign_rows_claimed` is
reported, but `_judge` never requires it to be 0, and the foreign rows are never released. On
a private lane the most likely source of foreign rows is an earlier aborted probe run
(SFH-05), which is exactly the case where the new run's readings deserve less trust. Have
`--expect` modes fail when `foreign_rows_claimed != 0`, or claim with `p_batch_size: 1` after
asserting the kind queue is empty.

### SFH-08 — Probe: a post-fix "loud" retracted arm is not tied to the retraction

`_judge(post-fix)` accepts `python_branch == "loud"` on the retracted arms without checking
WHY. An arm whose re-read failed on the lane (SFH-01's broad catch) is also loud. The control
arm catches a SYSTEMATIC read failure. A read failure specific to one arm would still pass.
After the run, scan `--handler-log` for the helper's `could not re-read the refresh marker`
line, and fail the post-fix judgement if it appears.

### SFH-09 — Probe: nothing enforces that `--handler-log` sits outside the repo

The handler log carries job and strategy ids, and the repo is public. The only protection is
the `--help` text ("kept outside the repo"). Refuse a path that resolves under `_REPO_ROOT`.

## INFO (no action required; recorded so they are not re-raised)

- **I-1, the residual TOCTOU window between the re-read and the stamp.** A retraction can land
  after `_refresh_marker_still_on_row` and before the upsert or `mark_compute_job_failed`. The
  run then keeps error-only while the bridge reads the job as unprotected, and
  `computation_warned` is left un-cleared. That reproduces the pre-fix shape in a window of
  milliseconds. It is already booked, with an owner, as `[164.6.7-COMPOSITE-REREAD-RESIDUE]` in
  `TODOS.md` and in the runbook, so it is acknowledged, not silent.
- **I-2, two spellings of the marker at one site.** `_honour_marker` compares against the
  inline literal `"ledger-refresh-composite"`, while the re-read passes
  `LEDGER_REFRESH_COMPOSITE_SOURCE`. If they drift, every re-read answers False and protection
  switches off. That is fail-safe, but see SFH-01. `test_marker_still_on_the_live_row_stays_error_only`
  goes RED on that drift, so a gate exists. The inline literal is a documented contract with
  the migration.
- **I-3, test-fake fidelity.** `_FakeQuery.execute` answers a missing `compute_jobs` row with
  `SimpleNamespace(data=None)`. Real postgrest 2.31 `maybe_single` returns `None` itself. The
  helper's `getattr(res, "data", None)` treats both the same, so the tests stay valid, but a
  future helper that reads `res.data` directly would pass in the fake and raise
  `AttributeError` in production, where the broad catch would absorb it (SFH-01). Consider
  having the fake return `None` so it matches the real library.

## Done well

- `_refresh_marker_still_on_row`'s fail-safe is complete, and its block comment states it as a rule.
- `_run` seeds the live row equal to the snapshot by default, so tests 1–8 kept their meaning.
- The fake serves the live row only on `("id", live_job_id)`, which makes "re-read the wrong row" observable.
- The probe keeps ids, DSNs and keys out of the verdict stream, reports only the exception TYPE on an abort, and checks the lane's bridge definition before it trusts its own copy of the predicate.
- `_drive_next_bridge` catches only `InsufficientPrivilege`, and it reports which method it used.
