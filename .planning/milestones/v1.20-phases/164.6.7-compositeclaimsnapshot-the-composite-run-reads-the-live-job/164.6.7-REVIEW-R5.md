### (a) Every database call in both closures is wrapped, on every path

I read `_stamp_strategy_analytics_failed` and the composite `_stamp_failed` in full at HEAD.

**Composite `_stamp_failed`** has four database calls, and all four go through `_stamp_io`:
- the status read: `db_read_with_retry(_read_existing_failed_row)`, `_STAMP_OP_STATUS_READ`;
- the marker re-read: `_read_refresh_marker_state`, `_STAMP_OP_MARKER_READ`;
- the D-15 error-only write: `db_execute(_upsert_error_only)`, `_STAMP_OP_ERROR_ONLY_WRITE`;
- the loud write: `db_execute(_upsert)`, `_STAMP_OP_LOUD_WRITE`.

**Single-key `_stamp_strategy_analytics_failed`** makes no status read. `existing_status` is the
entry snapshot `_refresh_publish_status`. Its three database calls all go through `_stamp_io`:
the marker re-read, the D-15 error-only write and the loud write.

Nothing else in either closure does I/O. `provenance_source` is pure. `scrub_freeform_string` is
pure. `_log_marker_not_confirmed` only logs, or raises `MarkerStateNotLoggable`.

**The one unwrapped call is deliberate: `_heal_delete_basis_series`.** It runs only after the
loud stamp has landed with the cause in `computation_error`, so its failure loses no cause. A
TRANSIENT raise there would retry a job whose terminal stamp already landed. It keeps its
pre-existing WARNING and the job stays `permanent`. `test_a_failing_post_stamp_call_keeps_the_landed_stamp`
pins this disposition, and `test_the_post_stamp_set_is_the_heal_and_only_on_the_single_key_loud_path`
pins where post-stamp calls exist. I confirm the decision. It is not a finding.

### (b) The exceptions are caught where they must be, and none is swallowed

**`_stamp_io` on a failure.** For an ordinary failure it does three things:
- logs ONE ERROR carrying site, operation, `_read_failure_text` and `cause`;
- makes ONE `_capture_read_failure`, tagged `compute_job_id`;
- raises `StampIOUnavailable ... from exc`.

A `_READ_PROGRAMMING_ERRORS` member gets the same ERROR and capture, then a bare `raise`.
`asyncio.CancelledError` is a `BaseException`, so the `except Exception` does not catch it, and
the cancellation semantics are unchanged.

**AST walk over every transitive stamp caller.** The walk covered `_stamp_failed`,
`_stamp_strategy_analytics_failed` and the helpers that reach them: `_dispose_broker_nav_error`
and `_reconstruct_all`. The only `try` handlers enclosing any call are these:
- `ccxt.RateLimitExceeded`;
- the deribit crawl's `asyncio.TimeoutError` / ledger-error tuple / `LedgerValuationError` / `NavReconstructionError`;
- the composite MTM `try`'s `CompositeOverlapError` / `ValueError` (F-5);
- the smoothed pass's `asyncio.TimeoutError` / `_PERMANENT_LEDGER_ERRORS`.

None of these catches `HandlerIOUnavailable`, `StampIOUnavailable` or `MarkerStateNotLoggable`.
None of those three subclasses `ValueError` or `TimeoutError`.

**`dispatch` and `classify_exception`.** `dispatch` catches `Exception` and calls
`classify_exception`. The only arm ahead of `isinstance(exc, HandlerIOUnavailable)` is
`asyncio.TimeoutError`, so `StampIOUnavailable` files `transient` with `str(exc)[:500]`. The raise
text puts `_read_failure_text` (capped at 120 characters) BEFORE `scrubbed`, so the 500-character
cut cannot drop the cause.

**Side effect of the new types, and it is an improvement.** On Python 3.12, `asyncio.TimeoutError`
is the builtin `TimeoutError`. Before round 4, a stamp write inside the crawl `try` or the
smoothed-pass `wait_for` could raise a builtin `TimeoutError`. The crawl's or the smoothed pass's
timeout arm would then catch it and misread it as a crawl timeout or a smoothed-pass degrade.
Now it arrives as `StampIOUnavailable` and is not intercepted.

**Issue:** Discovery records the calls made on the 8 `_SCENARIOS` paths only. Neuter N4 put an
unwrapped read on the composite `OTHER_SOURCE` branch, and all 84 tests in the exhaustive file and
the composite file passed. Several branches have no scenario:

A call added only on one of those branches escapes. Today no call exists on those branches, so

**Fix:** Add a deterministic static complement. Over the two closure regions, use the

#### IN-02 [LOW]: at the tail mirror, a programming error now fails a job whose work already landed

**File:** `analytics-service/services/job_worker.py`, `_refresh_marker_live_state` (the
`_READ_PROGRAMMING_ERRORS` branch) as reached from the tail mirror in
`run_derive_broker_dailies_job` via `_refresh_marker_still_on_row`.

**Issue:** Before round 4, a `_READ_PROGRAMMING_ERRORS` member in the tail-mirror read answered
`READ_ERROR`: ERROR, a capture, and the job DONE. Now it propagates after the hop-2 enqueue and
every hop-1 write, and the job is filed `unknown`. A programming error is deterministic, for
example a renamed client method. So until the code is fixed, every marked single-key refresh will:
- re-crawl its venue up to `max_attempts` times;
- re-write the hop-1 rows each time;
- ride the enqueue dedup;
- send the derive job through `failed_retry`, and in the end `failed_final`, with the bridge's
  `sync_strategy_analytics_status` running while hop 2 is in flight.

The tail mirror's own comment says "nothing it could do would change hop 2". The SFH-R4-02 split
turns a code defect in that log-only read into a job failure. This was deliberate: SFH-R4-02 asked
for it, and `test_at_the_tail_mirror_it_is_unknown_after_the_one_enqueue` pins it. So it is LOW
and not MEDIUM. Separately, the docstring of `_refresh_marker_still_on_row` does not say that it
can now raise.

**Fix:** Either keep the tail mirror log-only for programming errors too, with ERROR + capture and
then `READ_ERROR`, because the capture already carries the "needs a human" signal and the label
buys nothing after the enqueue. Or keep the split and record the re-crawl cost in the tail mirror
comment and in the runbook row. In both cases, add "raises a `_READ_PROGRAMMING_ERRORS` member
unchanged" to the docstring of `_refresh_marker_still_on_row`.

#### IN-03 [LOW]: the probe's vacuity guard now checks a line the composite stamp path does not emit

**File:** `analytics-service/scripts/probe_composite_claimtime.py`,
`_assert_reread_fragment_in_source` / `_count_reread_failures`, against `_stamp_io` and
`_STAMP_OP_MARKER_READ` in `analytics-service/services/job_worker.py`.

**Issue:** The guard checks that the literal `"could not re-read the refresh marker"` appears in
the source. At HEAD, only the ERROR line of `_refresh_marker_live_state` satisfies it, and that
line belongs to the chain edge and the tail mirror. The probe drives the composite stamp, which
since round 4 emits the fragment only through composition: `"%s: could not %s ..."` with
`op=_STAMP_OP_MARKER_READ`. Suppose `_stamp_io`'s format is reworded so that the two parts are no
longer contiguous, for example `"could not complete: %s"`. Then the source guard still passes, the
composite handler log carries no fragment, and the post-fix scan passes vacuously. That is exactly
what the guard exists to prevent. The unit pins assert `"could not"` and `"re-read the refresh
marker"` separately in the rendered line, not as one contiguous string. No test binds the
rendered stamp line to `probe._REREAD_FAILURE_FRAGMENT`: the only test use of the constant builds
a synthetic log line.

**Fix:** Add one test that drives a failing composite marker re-read, renders the `_stamp_io`
ERROR line, and asserts that `probe._REREAD_FAILURE_FRAGMENT` is a substring of it. Optionally,
make the probe's source guard also require `_STAMP_OP_MARKER_READ = "re-read the refresh marker"`
and the `"could not %s"` format.

#### IN-04 [INFO]: a runbook table row names an unreachable path, "loud write after `PRESENT`"

**File:** `docs/runbooks/ledger-refresh-go-live.md`, the round-4 alert-volume table, row "any
`_stamp_io` call fails (… loud write after `PRESENT` / `RETRACTED` / `OTHER_SOURCE` / an unmarked
stamp)".

**Issue:** `PRESENT` always takes the D-15 error-only write and returns. Neither closure can reach
a loud write after `PRESENT`. The count on the row is right. The path list is not.

**Fix:** Drop `PRESENT` from that list. The error-only write is already named separately on the
same row.

#### IN-05 [INFO]: the runbook's provenance-degrade note understates when it adds an ERROR

**File:** `docs/runbooks/ledger-refresh-go-live.md`, the round-4 "One pre-existing addition" note;
`upsert_or_drop_provenance`.

**Issue:** The note says the provenance ERROR adds 1 "to a failed-write row" when the re-issue
also fails. But `upsert_or_drop_provenance` logs its ERROR BEFORE the re-issue, so the ERROR also
fires when the re-issue SUCCEEDS. In the deploy window (a `PGRST204`) or on a marker 23514, the
row "D-15 protects → 0" reads 1, and every landed-stamp row gains 1. This is pre-existing
behaviour. Only the note is new.

**Fix:** Reword the note to say "adds 1 to any row whose write meets a marker refusal, whether or
not the re-issue lands. The worst case is still 4 per attempt when the re-issue also fails."

#### IN-06 [INFO]: the heal WARNING still interpolates the raw exception

**File:** `analytics-service/services/job_worker.py`, `_heal_delete_basis_series`, its `except
Exception as _heal_exc` WARNING.

**Issue:** This is the class that I-R4-4 fixed at two other lines in this region: raw
`%s` of the exception, not `_read_failure_text`. The line is byte-unchanged in this range and
is pre-existing. It is the one remaining raw-exception log in the stamp closure's call graph.

**Fix:** Use `_read_failure_text(_heal_exc)` for consistency. It is optional.
