## Summary

This round reviewed the round-1 fix commits `1b298d48e`, `2b7ec95ba`, `62525b2a6`, `d3904ab17`,
`bb83647d1` and `57d9fc8d3`. I found **no regression**:

- The `MarkerLiveState` refactor keeps the fail-safe direction at all four sites.
- `classify_exception` maps `RefreshMarkerRereadUnavailable` to transient. No earlier arm
  intercepts it: only `asyncio.TimeoutError` comes before it, and the class subclasses
  `Exception` directly.
- I ran my own AST walk over all 36 call sites of `_stamp_failed`,
  `_stamp_strategy_analytics_failed` and `_dispose_broker_nav_error`. None of them sits in a `try`
  body that catches `Exception`, `BaseException` or everything. The composite `_reconstruct_all`
  smoothed pass catches only `asyncio.TimeoutError` and `_PERMANENT_LEDGER_ERRORS`. This confirms
  the fixer's trace.
- The phase's four touched test files pass: `179 passed`, run from `analytics-service/` with the
  main checkout's `.venv` and the env scrubbed.

Three findings are **incomplete closures of round-1 intent**, not regressions. All three are in the
user-facing class ("un-publishing a funded strategy because a read failed") that the orchestrator
already ruled fix-not-defer on 2026-09-26. **WR-01** matters most: for a plain-`complete` row, the
transient retry cannot keep the protection it was added to keep.

### Answers to the orchestrator's questions

- **Can a transient retry loop forever?** No.
  - The claim RPC increments `attempts` (`claim_compute_jobs_with_priority`,
    `20260719073701_claim_kind_filter.sql`, `attempts = attempts + 1`).
  - `mark_compute_job_failed` (`20260528183100_mark_compute_job_strict_claim_token.sql`) moves the
    job to `failed_final` once `attempts >= max_attempts`. The default is 3
    (`20260411144407_compute_jobs_queue.sql`). The backoff between attempts is 30 s, then 2 min.
  - Across refresh cadences, the fan-out's `created_at` attempt cooldown bounds the total per day.
  - A read error that is deterministic, for example a malformed job id giving `22P02`, burns
    exactly 3 attempts.
- **What does the job look like after the last retry?**
  - The row is `failed_final`, `last_error_kind='transient'`.
  - `last_error` holds the re-read sentence, which says "retrying the job" even on the final
    attempt. The original failure is not in it (WR-03).
  - Python wrote nothing to `strategy_analytics`. The SQL bridge decides from the live marker and
    the live publish health.
  - Marker still present and row still healthy: branch (b-prime) keeps the row published. It
    overwrites `computation_error` with `computation_error_copy('transient')`.
  - Marker actually retracted: branch (b) takes the loud path, which is the correct answer.
  - ⚠️ A plain-`complete` row is no longer healthy by then. Branch (a) moved it to `computing`
    after attempt 1, so the final outcome is loud whatever the marker says (WR-01).
- **Does any definitive answer now retry?** No.
  - `NO_ID` returns before any read.
  - For zero rows, postgrest 2.31's `SyncMaybeSingleRequestBuilder.execute` returns `None` itself
    (I checked the installed source). `getattr(None, "data", None)` then yields `NO_ROW`.
  - `RETRACTED` and `OTHER_SOURCE` are decided from a row that was read.
  - Only an exception that escapes `db_read_with_retry` yields `READ_ERROR`.
- **Does any read error still un-publish?** Yes, at one site: the chain-edge forward (WR-02). The
  tail mirror only logs. Separately, WR-01 is a retry that un-publishes after a read error without
  a second read failure.
- **Is the Sentry capture per failure bounded?** Yes, but each failure is reported three times
  (IN-01).
  - At most one re-read fails per attempt. A stamp-site `READ_ERROR` raises and ends the attempt.
    A chain-edge `READ_ERROR` sets `_refresh_source_out = None`, which skips the tail mirror.
  - Each failed read produces 3 events, so at most 3 per attempt and 9 per job.

### Recommendation on the open decision (chain-edge `READ_ERROR`)

**Raise `RefreshMarkerRereadUnavailable` at the chain edge. Do not forward "no marker".** The
reasons are detailed under WR-02. In short:

1. The failures are correlated, not independent. A read that still fails after
   `db_read_with_retry` means the database is unhealthy, and hop 2 depends on that database.
   The marker is dropped exactly when hop 2 is most likely to fail.
2. Re-crawling on a transient is already accepted in this worker. `run_stitch_composite_job`
   returns transient after two complete crawls when the smoothed pass's degraded set diverges
   (the message reads "retry to re-crawl both"), and `dispatch`'s timeout path retries whole
   derives.
3. The outcome on exhaustion is fail-safe. The marker stays on hop 1's row, so the bridge's
   branch (b-prime) keeps the factsheet stale-but-live. Dropping the marker creates a hop-2 job
   the bridge can never protect.

Forwarding the marker on `READ_ERROR` is ruled out: if the marker had in fact been retracted, that
would suppress a failure somebody is watching. A new "unconfirmed" metadata state that hop 2
re-reads would be a new cross-hop contract. Hop 2 has no re-read today, and it would meet the same
`READ_ERROR` question one hop later. The raise is effective only together with WR-01's fix. Until
then it protects `complete_with_warnings` rows only.

## Warnings

### WR-01: the transient retry cannot preserve a plain-`complete` publish state, so D-09's "the retry re-reads the row" is true only for the `complete_with_warnings` cohort

**Classification:** WARNING. Not a regression: before round 1 the same row was un-published at
attempt 1. The effect is user-facing, the class ruled fix-not-defer.
**File:** `analytics-service/services/job_worker.py`: the `READ_ERROR` arms of `_stamp_failed` in
`run_stitch_composite_job` and of `_stamp_strategy_analytics_failed` in
`run_derive_broker_dailies_job`; `_read_entry_publish_state`; `_read_existing_failed_row`.
`docs/runbooks/ledger-refresh-go-live.md`, item 2's D-09 notes.

**Issue:** Trace, cited by symbol:
1. Attempt 1: the re-read raises. The stamp site writes nothing and raises, and `dispatch`
   classifies the result as transient.
2. `mark_compute_job_failed` (latest definition, `20260528183100`) sets `failed_retry` and then
   runs `PERFORM sync_strategy_analytics_status`.
3. In the bridge (`20260906120000_computation_error_provenance.sql`), `v_nonterminal_count`
   counts `'failed_retry'`. `v_protect_hold` requires a protected `failed_final`, and none exists,
   so branch (a) fires. Its CASE keeps `complete_with_warnings` (or a warned row), and it
   **rewrites a plain `complete` to `computing`**. The code states this itself, above the entry
   snapshot: "Branch (a) preserves 'complete_with_warnings'; it does NOT preserve plain
   'complete'."
4. Attempt 2 then reads a status that is no longer terminal-success:
   - Single-key: `_read_entry_publish_state` runs again at handler entry and reads `computing`.
     `_refresh_publish_status` is not in `STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES`.
   - Composite: `_read_existing_failed_row` reads the live `computation_status`, which is
     `computing`, so `_honour_marker` is False.
5. The marker re-read never runs, and the destructive stamp fires if the underlying failure
   recurs. That failure is the reason a stamp was needed in the first place, so it usually recurs
   (a revoked key, an incomplete ledger).
6. If the retry budget runs out instead, the bridge sees `computing`. `computing` is not
   `v_publish_healthy`, so branch (b) un-publishes.

For a plain-`complete` row, then, the D-09 retry helps only when the ORIGINAL failure clears on
retry. The `complete_with_warnings` rows are fully covered. The runbook's item-2 note and both
`READ_ERROR` code comments present the retry as re-deciding from the row, and they do not state
this limit. Plain `complete` is what a clean recompute leaves, according to the bridge migration
header quoted in the F1 comment, and `STRATEGY_ANALYTICS_TERMINAL_SUCCESS_STATUSES` protects it
deliberately. How many live rows are plain `complete` today is stated only in dated comments; I
did not measure it.

**Fix:** The root closure is the one the entry-snapshot comment already names: the publish state
must live somewhere the bridge cannot overwrite. Minimum viable version:
```python
# at the READ_ERROR arm, before raising, persist the pre-refresh snapshot onto the job row once,
# so attempt N>1 reads it instead of the bridge-rewritten column:
#   compute_jobs.metadata || {"publish_status": <attempt-1 snapshot>, "publish_warned": ...}
# and at handler entry prefer metadata["publish_status"] when attempts > 1.
```
The fuller fix mints `publish_status` into the job metadata at fan-out time, as that comment
proposes, which also closes the F2 residual. If neither fits this phase, amend runbook item 2 and
both comments to state the limit ("covers `complete_with_warnings`; a plain-`complete` row loses
the protection on retry"), and route it under the deferral rule.

### WR-02: the chain-edge forward still un-publishes on a read error, and no test pins what it does (the open decision; recommendation: raise)

**Classification:** WARNING. User-facing (a funded factsheet can go dark). It needs a second
failure, but that failure is correlated with the first.
**File:** `analytics-service/services/job_worker.py`, `run_derive_broker_dailies_job`, the REUSE-01
FORWARD DIRECTION block (`_live_state_out`) just before `_enqueue_csv_analytics`.

**Issue:** On `READ_ERROR`, `_refresh_source_out` is set to `None`. Hop 2 is then enqueued with no
`source` and no `publish_status`. Every hop-2 failure path is loud, and the site's own consequence
string says so ("hop 2 fails LOUDLY"). Those paths include hop 2 burning its own transient retries
to `failed_final`, after which the bridge's branch (b) sees an unmarked job.

The "two consecutive failures" framing understates this. `READ_ERROR` is reported only after
`db_read_with_retry`, which already retried gateway timeouts, has given up. That is a
database-health signal, and hop 2 is claimed on the next ticks against the same database.

The fixer's cost objection (a re-run re-crawls the venue and re-persists dailies) is weaker than
stated:
- The worker already takes that cost on transients after a crawl. `run_stitch_composite_job`
  returns transient ("… retry to re-crawl both") after two full fan-outs.
- The hop-1 writes before the chain edge are upserts: the dailies and `_prestamp_dq_flags`. The
  prestamp payload carries no `computation_status`.
- If every retry fails, `metrics_json_by_basis` is left newer than `metrics_json`. That state
  already arises today whenever hop 2 fails, so it is not new.

No test exercises this arm. `TestChainEdgeDoesNotForwardARetractedMarker` covers only the
retracted case and the live-marker control. `TestSingleKeySitesNameTheRealCause` covers `NO_ROW`.
Whichever way the decision lands, it is unpinned.

**Fix:**
```python
if _live_state_out is MarkerLiveState.READ_ERROR:
    _log_marker_not_confirmed(
        _live_state_out, site="derive_broker_dailies", job_id=job.get("id"),
        strategy_id=strategy_id,
        consequence=("Enqueueing NO chain edge; failing the job TRANSIENT so it "
                     "retries with the marker still on the row"),
    )
    raise RefreshMarkerRereadUnavailable(
        "derive_broker_dailies: the live re-read of the refresh marker failed at "
        "the chain edge; no follow-on was enqueued"
    )
if _live_state_out is not MarkerLiveState.PRESENT:
    ...  # unchanged loud drop for definitive answers
```
The raise must go BEFORE `_enqueue_csv_analytics`, so a retry never enqueues twice. Add a
`dispatch`-driven test asserting three things: `transient`, zero `enqueue_compute_job` calls, and
the marker still on the claimed row. Note that it protects only `complete_with_warnings` rows until
WR-01 is fixed: on retry, a plain-`complete` row's entry snapshot is `computing`, so no
`publish_status` rides the edge. If the orchestrator keeps the drop instead, pin it with a test
and record the correlation argument above as the accepted risk, not "two independent failures".

### WR-03: the `READ_ERROR` raise discards the failure it was stamping, both in the operator's `last_error` and in the account holder's copy on exhaustion

**Classification:** WARNING (it loses the diagnosis; it becomes user-facing once retries run out).
**File:** `analytics-service/services/job_worker.py`: the `RefreshMarkerRereadUnavailable` raises
in `_stamp_failed` (composite) and `_stamp_strategy_analytics_failed` (single-key).

**Issue:** Both closures receive `message`, the curated sentence (for example the scope-auth or
ledger-incomplete copy), and optionally `detail`. On `READ_ERROR` they raise a fixed string, and
`dispatch` → `classify_exception` records `str(exc)` as the job's `last_error`. The result:
- `compute_jobs.last_error`, which the curated-copy migration calls the operator-only home of "the
  raw diagnosis", records only that a read failed, and adds "retrying the job" even on the final
  attempt.
- The curated `message` is never logged on this path. `detail` survives only as the WARNING line,
  and only for callers that passed one.
- The raise happens inside `except` arms such as the `NavReconstructionError` disposer, so Python
  chains the original as `__context__`. Nothing reads it: `classify_exception` uses `str(exc)`,
  and no capture sees the outer exception.
- On exhaustion, branch (b-prime) finds no writer provenance for this job, so it writes
  `computation_error_copy('transient')`: "Analytics could not complete after several automatic
  retries. Retry the sync, or contact support…". For an underlying PERMANENT cause such as a
  revoked key, that is the wrong advice. The copy for `'permanent'` exists to say that retrying
  will not help.

**Fix:** Carry the curated sentence (it is already scrubbed and safe for `last_error`) and drop
the unknowable "retrying":
```python
raise RefreshMarkerRereadUnavailable(
    "stitch_composite: the live re-read of the refresh marker failed, so no "
    f"terminal stamp was written for: {scrubbed}"
)
```
Also log `message` in the `READ_ERROR` consequence. Consider whether exhaustion should end
`permanent` when the underlying failure was permanent. That would be a separate decision, since
it changes the retry disposition.

## Info

### IN-01: each failed re-read produces three Sentry events, and a test docstring's rationale is stale

**Classification:** WARNING, info tier (noise, bounded; no behaviour change).
**File:** `analytics-service/services/job_worker.py`, `_refresh_marker_still_on_row` (`logger.error`
then `sentry_sdk.capture_exception`) and `_log_marker_not_confirmed`'s `READ_ERROR` arm
(`logger.error`); `analytics-service/tests/test_ledger_refresh_composite_nondestructive.py`,
`TestTransientReReadFailureRetries`.

**Issue:** `init_sentry` passes `integrations=[StarletteIntegration(), FastApiIntegration()]`
without disabling the default integrations. The default `LoggingIntegration` turns every
`ERROR`-level record into an event, so one failed read yields:
- the helper's ERROR line,
- the explicit capture,
- the call site's ERROR line.

The test asserts `capture_exception.call_count == 1`, which is true of the mock. Its message
justifies the capture with "A WARNING is a breadcrumb, not an event". That was true of the old
WARNING line, and the line is now ERROR, so the capture only duplicates. It is bounded at 9 events
per job.

**Fix:** Keep the capture (it carries the traceback) and use `logger.warning` for the helper's
text line, or drop the call site's second ERROR. Update the docstring.

### IN-02: the D-09 block comment claims the 504 retries widen the read-to-stamp window; they do not

**Classification:** WARNING, info tier (misleading comment).
**File:** `analytics-service/services/job_worker.py`, the block comment above `MarkerLiveState`
("The cost is a slightly longer window between this read and the stamp").

**Issue:** `db_read_with_retry` sleeps between attempts BEFORE the read that answers. The window
that matters for `[164.6.7-COMPOSITE-REREAD-RESIDUE]` runs from the answering read to the bridge,
and it is not lengthened. What does lengthen is the handler's total wall time.

**Fix:** Reword: "the cost is up to ~3-4 s more wall time on a gateway-timeout path; the
read-to-stamp window is unchanged."

### IN-03: the tail mirror's `NO_ID` / `NO_ROW` message calls the follow-on a "claimed job"

**Classification:** WARNING, info tier (misleading log text).
**File:** `analytics-service/services/job_worker.py`, `_log_marker_not_confirmed`'s final arm, as
reached from the REUSE-01 MIRROR DIRECTION block with `_tail_job_id`.

**Issue:** The message reads "A claimed job with no id or no live row is an invariant breach". At
the tail site the job was just ENQUEUED, not claimed, and `_tail_job_id` is the RPC's return
value. The sentence sends an operator looking at the wrong invariant.

**Fix:** Pass a `subject` ("claimed job" or "enqueued follow-on") into `_log_marker_not_confirmed`,
or let the tail site word its own `NO_ID`/`NO_ROW` sentence.

### IN-04: the probe's `foreign_rows_claimed` reading is always 0, so `_judge`'s foreign check is dead, and foreign rows it claims are left `running`

**Classification:** WARNING, info tier (dead guard, lane-only side effect).
**File:** `analytics-service/scripts/probe_composite_claimtime.py`, `_claim_own` and `_judge`.

**Issue:** `_claim_own` raises `ProbeError` when `foreign` is non-zero, before it returns
`(own[0], foreign)`. The returned count is therefore always 0, and `_judge`'s first check
(`int(r["foreign_rows_claimed"]) != 0`) can never fire. The probe's own error text says the
foreign rows are "left running under the probe's worker id". On the private lane they would sit
until the stalled-job reaper, and `_cleanup` does not touch them because it deletes by the arm's
own `strategy_id`. The `_assert_no_foreign_claimable` pre-check makes this unlikely, but that
check is a check-then-act.

**Fix:** Either drop the returned count and the `_judge` check (the raise is the guard), or return
the count and have the caller release the foreign rows (`status='pending'` by id) before failing.
The first is simpler.
