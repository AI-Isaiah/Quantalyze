## HIGH

### SFH-R3-01 — Composite `_stamp_failed`: when the flags/status read fails, the handler's curated cause is recorded nowhere (SFH-R2-01, one read earlier)

**Location:** `run_stitch_composite_job` → `_stamp_failed`. The problem is the order of two
statements: the `if detail:` WARNING at the top of the closure, then
`existing_row = await db_read_with_retry(_read_existing_failed_row)`. Both come before the
round-2 cause line (the `logger.error("stitch_composite: terminal failure for strategy %s on
marked compute_job %s — …")` inside `if _honour_marker:`).

**Scenario.** A composite handler reaches a permanent failure and calls
`_stamp_failed(message)` with no `detail`. The zero-member stamp is one example. The closure's
first I/O is `_read_existing_failed_row`. Suppose it fails: a 504 three times in a row, or on
the first attempt a 42501, a PostgREST 4xx, a transport error, or an `AttributeError` after an
SDK change. Then:
- the read's exception leaves the closure before any line names `message`, because the only
  earlier log is gated `if detail:`;
- `classify_exception` maps the read error (a postgrest `APIError` or anything else unmatched)
  to `unknown` and writes the READ's text to `compute_jobs.last_error`;
- `unknown` retries. Every attempt repeats the stitch fan-out, and a failure that is really
  permanent is spent as a retryable one;
- on exhaustion the bridge writes the generic `computation_error_copy` sentence in place of the
  curated `message` that HONEST-01 exists to show.

**Checked against round 2's SFH-R2-01 criteria, one by one:**

| R2-01 criterion | R3-01 |
|---|---|
| The cause is replaced in `last_error` by the read's text | yes |
| A no-detail stamp's cause is logged nowhere | yes: the only pre-read log is `if detail:` |
| A detail-bearing stamp logs it only at WARNING (a breadcrumb) | yes |
| A permanent failure is reported as retryable | yes (`unknown` retries) |
| Generic copy replaces the curated sentence on exhaustion | yes |
| A persistent non-gateway read error (the programming-error class) triggers it on attempt 1 | yes |

It is broader than R2-01 in one respect: it fires on EVERY composite terminal stamp, marked or
not. A user-initiated stitch, the case this closure was written for, is included. It is
narrower in one respect: since `f7db9543c` a single 504 no longer triggers it. The outcome
is the same, so the rating is the same. The label is **pre-existing, missed by round 2**, not
introduced by this phase.

**Hidden errors.** The handler's own cause (member-set errors, structural ledger errors, the
insufficient-data stamps) whenever the database misbehaves on the stamp's first read.

**Single-key counterpart checked, and clean.** `_stamp_strategy_analytics_failed` makes no read
before its cause line. `existing_status` is the entry snapshot `_refresh_publish_status`, so the
first I/O on the marked path is the marker re-read, and the cause line already precedes it.

**Fix.** Apply R2-01's fix step 1 at the top of the closure, before the first read. Log the
scrubbed `message` whether or not a detail exists (ERROR, or WARNING if the orchestrator wants
the Sentry volume held; see SFH-R3-03), with `detail` appended when present. Then either:
- (a) wrap `_read_existing_failed_row` so that an exhausted or failed read re-raises with the
  cause attached, for example as a typed exception whose text ends `…for: {scrubbed}`; or
- (b) accept `last_error` naming the read, now that the cause line guarantees one durable record.

(a) matches what R2-01 did at the re-read. Pin it by extending `TestStampReadRetriesAGateway504`,
or with a sibling case that exhausts the budget: assert the cause sentence was logged and, under
(a), that it appears in `result.error_message`. Neuter: move the log back under `if detail:` and
confirm the test goes RED.

## LOW

### SFH-R3-02 — `last_error` at the entry-read and chain-edge raises omits the underlying read failure

**Location:** the `except Exception as _entry_exc` arm around `_read_entry_publish_state` in
`run_derive_broker_dailies_job`, and the chain-edge `READ_ERROR` raise before
`_enqueue_csv_analytics`.

`classify_exception` records `str(exc)[:500]`, and `str()` of `RefreshMarkerRereadUnavailable`
does not include `__cause__`. So `last_error` says that the read failed, never why. The type and
text do reach the ERROR line and `capture_exception` (the entry arm logs
`type(_entry_exc).__name__`, and the helper logs the chain-edge read's), so the cause is not lost.
It is missing only from the surface operators read first. The entry arm's `except Exception`
also re-labels a programming error (an `AttributeError`, a 42501) as TRANSIENT. That is
consistent with how the helper maps every read failure to `READ_ERROR`, and it is cheap here
because nothing has been crawled, but it means such a bug retries to `failed_final` before anyone
sees it. **Fix:** append the scrubbed `type(exc).__name__: text` to both raise messages. At the
chain edge that requires the helper to hand back the exception, or a short reason, alongside
`READ_ERROR`.

### SFH-R3-03 — The runbook's Sentry-volume bound was already stale when it landed; the cause line also makes every honoured D-15 suppression an event

**Location:** `docs/runbooks/ledger-refresh-go-live.md`, composite precondition item 2, the
"Alert volume, a known property" bullet. The emitters are the round-2 cause lines in both stamp
closures.

The bullet counts 3 events per failed stamp-site re-read and at most 9 per job. At HEAD there are
4 per attempt: the cause line (`777c7e0bb`), the helper's ERROR, the helper's
`capture_exception`, and the site's `_log_marker_not_confirmed` ERROR. That makes the bound
**12**. The chain edge stays at 3, and the entry read at 2. The bullet's own condition ("if the
deployed commit adds an ERROR line on this path, re-count the bound") was met by `777c7e0bb`,
which the bullet's commit `905ac27fe` already followed. Separately, the cause line fires
whenever protection would be granted, before the re-read. So every honoured D-15 suppression, a
background refresh failing on a live row, is now one Sentry event, and the bullet does not
count that. This is not a silent failure. It is an operator document that understates what will
page. **Fix:** re-count in the bullet. Say that a suppressed marked failure is one event by
design, or downgrade the cause line to WARNING when the re-read succeeds, which requires logging
it after the read.

### SFH-R3-04 — The chain edge's exhausted-retry end state is a mixed-generation row, and the comment calls the writes "upserts" without saying so

**Location:** the D-09-at-the-chain-edge comment and raise in `run_derive_broker_dailies_job`.

By the time the chain edge raises, hop 1 has already persisted the following:
- `_prestamp_dq_flags`, which replaces `data_quality_flags` wholesale and writes
  `series_completeness` and `metrics_json_by_basis`;
- the MTM series persist or heal.

If every retry hits the same read failure, hop 2 never runs. Branch (b-prime) keeps the row
published, so the factsheet shows hop-1 flags, verdict and by-basis values next to the previous
hop 2's headline `metrics_json`. That is the same class as a protected hop-2 failure, which D-15
already accepts, so it is not new harm. But the comment's justification ("the writes above are
upserts") speaks only to the retry, not to the terminal state. **Fix:** one sentence in the
comment and in runbook item 2 naming the end state.
