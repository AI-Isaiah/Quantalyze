**2. Can the live probe pass vacuously? No.**
- **Arm (a) needs a real grant refusal.** It requires a non-null error, code `42501`, and the text `permission denied for table strategies`. A network error has no `42501` code. A schema-cache error comes back as `PGRST*` or `42703`. Losing schema USAGE says "schema public", not the table. Each of these fails the arm.
- **Arm (a) does not depend on a row existing.** The permission check runs when the query is planned, so it fires whether or not a published row is there.
- **The write arms (n), (o) and (p) cannot be passed by RLS.** They fail on a call that comes back with no error, which is the shape of an RLS-filtered UPDATE or DELETE. They also fail on a `row-level security` message.
- **Arm (q) is an independent admin re-read.** It checks that the seeded row is unchanged.
- **A missing anon key is not a silent skip.** It is caught by the `advertises the live-DB skip reason` assertion (`HAS_LIVE_DB` ⇒ `HAS_ANON_PROBE`).

## Warnings

### WR-01: `HIDDEN_COLUMN_EXEMPTIONS` records "anon must NOT see this" but nothing enforces it, so an exempted column that gets granted to anon passes green

**Severity:** MEDIUM · **Confidence:** 7/10

**Files:**
- `supabase/tests/test_strategies_anon_grants.sql:83-86` (the declaration)
- `supabase/tests/test_strategies_anon_grants.sql:118-137` (GRANT 3)
- `supabase/tests/test_strategies_anon_grants.sql:31-37` (header contract)
- `supabase/migrations/20261022120000_strategies_anon_api_key_id_revoke.sql:54-61, 137-143`
- `supabase/migrations/down/20261022120000-rollback.sql:14-15, 28-32`

**Issue:**
- **What the list promises.** The header (lines 34-37) and the migration header (lines 58-61) both say that adding a column to `HIDDEN_COLUMN_EXEMPTIONS` "records 'anon must NOT see this' as a decision instead of an accident".
- **What the gate actually does with it.** It only ever uses the list to *remove* columns from GRANT 3's sweep (lines 121 and 129). No arm checks that an exempted column is in fact *not* readable by anon.
- **Which columns really get the denial check.** GRANT 1 and GRANT 4 assert denial for `api_key_id` alone, because the name is hardcoded. So the only hidden column the gate truly enforces is `api_key_id`. A column the list declares hidden gets no denial check at all.

**Concrete failure scenario:**
1. A later migration adds `strategies.internal_notes`. GRANT 3 goes RED, as designed. The author takes remedy (2) and adds `'internal_notes' -- reason: staff-only` to the list. The gate goes green.
2. Some time later, anon is handed that column. The likeliest way is the procedure this PR documents:
   - Someone runs `down/20261022120000-rollback.sql`. Its own header says "re-apply the migration afterwards" (lines 14-15 and 28-32).
   - Re-applying the migration re-derives the grant from `pg_attribute` as "every column except `api_key_id`" (migration lines 137-143). That grants `internal_notes` to anon.

   Two other routes end the same way: a copy of this migration's catalogue-derived grant pattern, or a stray `GRANT SELECT (internal_notes) ... TO anon`.
3. The gate stays **green**:
   - GRANT 3 skips the column because it is exempt.
   - GRANT 1 and GRANT 4 only look at `api_key_id`.
   - No other arm reads exempted columns.

   The column the list exists to protect is now readable by every visitor holding the publishable key. RLS never restricts columns, which is the premise of this phase, so nothing else stops it.

There is a second problem with the same root. The migration's derivation (`a.attname <> 'api_key_id'`) and its self-check (lines 155-161, "anon lost SELECT on … column(s)") do not know about the exemption list. A re-apply after the first exemption exists would therefore actively grant the hidden column, and its self-check would require it. The migration and the gate's list contradict each other as soon as the list stops being empty.

**Fix:** turn the exemption into an enforced denial, and give it a biting twin.

```sql
-- ===== ARM GRANT 5 — every HIDDEN_COLUMN_EXEMPTIONS entry is a real, anon-denied column
SELECT string_agg(e.col, ', ' ORDER BY e.col) INTO v_bad_exempt
  FROM unnest(v_hidden_column_exemptions) AS e(col)
 WHERE NOT EXISTS (SELECT 1 FROM pg_attribute a
                    WHERE a.attrelid = v_rel AND a.attname = e.col
                      AND a.attnum > 0 AND NOT a.attisdropped)          -- stale entry
    OR has_column_privilege('anon', v_rel, e.col, 'SELECT');           -- exempt but readable
-- RED-UNDER / RED-UNDER-M: needs a non-empty list on the lane, e.g. an `edit` step that
-- adds a fixture column (such as 'name') to the array, so the arm bites on today's grants.
IF v_bad_exempt IS NOT NULL THEN
  RAISE EXCEPTION 'TEST FAILED (GRANT 5): HIDDEN_COLUMN_EXEMPTIONS column(s) % are readable by anon or do not exist ...', v_bad_exempt;
END IF;
```

Also do one of the following, so that re-applying the migration cannot undo an exemption:
- Make the migration's header and the rollback's "re-apply the migration afterwards" note say that a re-apply must exclude every column on the exemption list.
- Or, simpler: since SQL cannot share the list, state in the gate header that the first non-empty entry *must* come with this arm. Do not leave it as prose.

Adding the arm moves the census (+1 arm, `ARMS_FLOOR` 723→724) in the same commit.
