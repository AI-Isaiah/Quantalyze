## Warnings

### WR-01: The three narrowed readers turn a column-grant failure into a silent "not found" or empty list, with no Sentry signal. That is the exact failure mode PR-B creates.

**Severity:** MEDIUM · **Confidence:** 7/10
**File:** `src/lib/queries.ts:423-426` (`getStrategiesByCategory`), `src/lib/queries.ts:1281`
(`getPublicStrategyDetail`), `src/lib/queries.ts:1336` (`getFactsheetDetail`)

**Issue:** This PR couples these three public readers to a hand-maintained column list. Its own
docblock (`src/lib/constants.ts`, the `STRATEGY_PUBLIC_COLUMNS_ARR` comment) says that once PR-B
lands, "a column added to `strategies` is NOT anon-readable until a migration grants it". A
PostgREST 42501 on these selects is therefore now an expected class of failure. How each reader
handles an error:

- `getStrategiesByCategory` logs `console.error` and returns `[]`, with no `captureToSentry`.
  Its siblings in the same file, `getPopulatedCategorySlugs` and `getOwnRowPercentiles`, capture
  their errors.
- `getPublicStrategyDetail` and `getFactsheetDetail` do `if (error || !strategy) return null;`.
  They log nothing and capture nothing, so an error cannot be told apart from a genuine miss.

**Concrete failure scenario:** after PR-B, a later phase adds a column to `strategies` and to
`STRATEGY_PUBLIC_COLUMNS_ARR`, because a public page needs it. The phase forgets the anon column
grant, or the grant lands in a later PR than the Vercel deploy, which is the same ordering window
O-1 exists to close. Every anonymous visitor then gets:

- `/browse/<slug>`: an empty category, rendered as a normal page.
- `/browse/<slug>/<id>` and `/strategy/<id>`: the not-found state, which
  `src/app/strategy/[id]/page.tsx` also uses for `generateMetadata`, so share unfurls degrade
  too.
- `/factsheet/<id>/tearsheet`: not found.

None of these raises a Sentry event, and the tearsheet and detail paths do not even log. The
outage D-02 calls P1 would surface only when a person notices. D-06's anonymous browser pass
covers the PR-B deploy itself, but nothing covers any later column change.

**Fix:** report the error branch separately from the empty or missing branch, and do it in all
three readers. That is the NEW-C03-05/06 idiom this file already uses:

```ts
// getStrategiesByCategory
if (error) {
  console.error("[queries.getStrategiesByCategory] supabase error:", error.message ?? error);
  captureToSentry(error, { tags: { op: "getStrategiesByCategory", code: error.code ?? "none" }, level: "error" });
  return [];
}

// getPublicStrategyDetail / getFactsheetDetail
if (error) {
  // PGRST116 (no row) is the legitimate not-found; anything else (42501 after the
  // ANONKEYID column grants) is an outage that must not read as a 404.
  if (error.code !== "PGRST116") {
    console.error("[queries.getPublicStrategyDetail] supabase error:", error.message ?? error);
    captureToSentry(error, { tags: { op: "getPublicStrategyDetail", code: error.code ?? "none" }, level: "error" });
  }
  return null;
}
if (!strategy) return null;
```

PR-B could alternatively carry this fix, but it has to land no later than the revoke. Fixing it
in PR-A is cheaper and touches only these three functions.

## Considered and dismissed (below threshold, not counted)

  (`src/app/api/admin/strategy-review/route.ts:278`, `review_note: null` on publish), so a
  published row carries none. The other columns in the list (`user_id`, `fingerprint`,
  `wizard_session_id`, `public_contact_email`) were already anon-readable under the table grant,
  so they are not a regression from this PR.
- `ANON_ROUTE_EXEMPTIONS` is keyed per file with an exact hit count. A swap that moves
  `readTradeFacts` from `createAdminClient()` to the session client would keep the count at 1 and
  pass. The live probe does not run `readTradeFacts`. This is low likelihood. A per-select anchor
  such as "the exempt select is preceded by `createAdminClient()`" would close it.
- With `api_key_id?:` optional on `Strategy`, an owner reader narrowed by mistake to
  `STRATEGY_PUBLIC_COLUMNS` would quietly read `undefined` (for example `hasApiKey={!!s.api_key_id}`
  on `/strategies`) and the type checker would not notice. This is speculative, and no such
  narrowing exists today.
- The `/browse` table/grid badge now shows for an `api_verified` composite strategy, or for one
  whose key was deleted (`strategies_api_key_id_fkey ON DELETE SET NULL`). The public factsheet
  already behaves this way, so the two surfaces now agree. PROD count today: 0.
