# Phase 167.2.1 Plan 02: Server-side Key Membership Read Summary

**The key card's Delete confirm now gets a key's composite memberships from `GET /api/keys/[id]/memberships`. The route checks ownership with an explicit `api_keys.user_id` equality, then reads `strategy_keys` joined to `strategies` on the service role. The browser no longer reads `strategy_keys` through RLS. Every failed or malformed answer shows KCS-DELETE-UNCHECKED instead of an empty list.**

## Performance

- **Duration:** about 17 min
- **Tasks:** 2 of 2
- **Files:** 2 created, 5 modified

## Accomplishments

- New route `src/app/api/keys/[id]/memberships/route.ts`. It checks, in order:
  1. `withAuth`
  2. `isUuid` (400)
  3. `checkLimit(userActionLimiter, key-memberships:<user>)`, answering with the limiter's deny
  4. the admin `api_keys` read with `.eq("id").eq("user_id", user.id)`. A read error gives 500 with a tags-only capture (`stage: ownership`). An absent key and a foreign key get the same 404.
  5. the admin `strategy_keys` read. An error or a non-array answer gives 500 with a capture (`stage: memberships`). Otherwise it answers 200 `{ memberships: [{ name, status }] }`, and a one-element embed array is unwrapped.
  Every answer carries `NO_STORE_HEADERS`, and the route writes nothing.
- `readKeyCompositeMemberships`: only its body and doc comment changed. It races the fetch and its `.json()` against `BASELINE_READ_BOUND_MS`, then:
  - answers `"unreadable"` for `!res.ok`, a JSON parse throw, a missing or non-array `memberships`, a non-object element, a rejected fetch, or the bound;
  - maps a non-string field to null and never drops an element.
  The existing console.error and the tags-only capture (`stage: delete-membership-read`) are kept. The unused `SupabaseClient` import was removed.
- KCS copy is unchanged. The three oracle literals are byte-identical to the merge-base (the plan's check printed nothing).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `ApiKeyManager.poll.test.tsx` DELETE-MEMBERSHIP-BOUND moved to the route fetch**
- **Found during:** Task 1
- **Issue:** This case held the old browser `strategy_keys` read open through `mockState.membershipResult`, and its `fetch` answered every URL with a 202 body. Once the card read the route instead, the read failed straight away, so the "held for 14 s" assertion went red.
- **Fix:** The case's `fetch` now never settles for `/api/keys/<id>/memberships`. The dead `membershipResult` field, its reset and the `strategy_keys` mock arm were removed, with a lineage comment. The oracle is unchanged. The file is not in plan 01's file set.
- **Commit:** `087bbd3c1`

**2. [Rule 3 - Blocking] `src/lib/api/limiter-ordering.test.ts` classification**
- **Found during:** Task 2, when running the route-scanning tests
- **Issue:** The B15 completeness check fails on any limiter route that has no classification. The plan checked only the audit, route-contract and admin-manifest gates.
- **Fix:** The route is classified `NO_INPUT`: a GET with no body, whose `[id]` is checked with isUuid before `checkLimit`. Its comment matches the share, returns and sync-progress siblings. This is the gate's own "conscious classification" step. It is not an exemption, and removing the entry turns the check red.
- **Commit:** `ad00e9ba5`

**3. [Rule 2 - Security] Defence-in-depth redaction of a foreign strategy's name**
- **Found during:** Task 1
- **Issue:** The service-role read trusts the `enforce_strategy_keys_owner_coherence` trigger for the claim that every embedded strategy is the caller's. That trigger fires only on `strategy_keys` writes, and a later admin-side change to `strategies.user_id` would not re-check it.
- **Fix:** The embed also selects `user_id`. A row whose strategy is not the caller's is still listed, so the warning still fires, but with a null name and status. Pinned by FOREIGN-STRATEGY-REDACTED. The response still carries only `name` and `status`.
- **Commit:** `087bbd3c1`

**4. [Constraint adjustment] The node_modules symlink was not removed before each commit**
- The symlink is shared with plan 01, which runs at the same time in this checkout. Removing it would have broken plan 01's vitest runs mid-flight.
- `.gitignore` `/node_modules` covers the symlink, `git status --short` never listed it, and every commit used `git commit -- <explicit paths>`. So it could not be staged either way.

**5. [Plan shape] The untyped `SupabaseClient` cast was not added**
- `createAdminClient()` already returns the untyped client (see its NOTE in `src/lib/supabase/admin.ts`), so the plan's cast would do nothing.
