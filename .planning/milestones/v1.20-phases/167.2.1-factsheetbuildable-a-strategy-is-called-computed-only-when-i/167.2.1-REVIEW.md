Answers to the brief's key questions:

1. **Can the probe and the builder disagree?** Not in the code as it stands. `buildFactsheetPayload`
   has two null exits: `if (!dailyReturns.length) return null` and the `hasBuildableSeries` gate.
   `resolveFactsheetInputs` G3 and G4 ask both of them about the same `dailyReturns` array that
   `fetchAndBuildPayload` passes on unchanged. The basis reads (`readSingleKeyBasisOpts`) and
   `buildOpts` do not change the series. So nothing can currently return null outside the resolve
   stage. The guard against a *future* null exit is weaker than its docstring claims, though
   (WR-04).
2. **Memberships route: existence oracles or cross-tenant reads?** None found. `isUuid` runs before
   the limiter and before any client. The `api_keys.user_id = user.id` equality runs before the
   `strategy_keys` read. An absent key and a foreign key get byte-identical 404s. A foreign-owned
   strategy embed has its name and status nulled. `route.test.ts` neuters the owner equality and
   expects the result to change. The caller, the strategy edit page, is itself owner-gated
   (`.eq("user_id", user.id)`), so no admin or impersonation path hits the new 404. The only
   residual items are SFH M-4 and L-3.
3. **Does any probe error path claim "buildable"?** No. `probeFactsheetBuildable` returns
   `{ buildable: true }` only when `resolveFactsheetInputs` returns `ok: true`. Both callers map a
   throw, `read_error` and `not_visible` to "unreadable". The one "buildable-looking" outcome that
   is not a real build is IN-03: a builder *throw* at the recipient's request is outside the
   probe's domain, and the docstring says so.
4. **Is the copy true and DESIGN.md-compliant?** Not always. CR-01 shows a reachable page that
   states two contradicting facts, and WR-02 shows a "Right now" claim that the cached public lane
   can falsify. IN-02 covers a DESIGN.md voice deviation.
5. **Performance.** Yes, N extra reads per load, and they are heavy (WR-01).

## Critical Issues

### CR-01: The owner factsheet says "Its last computation succeeded" beside "none is on record", a state every unbuildable draft reaches 30 days after its last compute

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`FactsheetV2Page`, the owner `!payload` branch:
`ownerLine` from `ownerStateLine(ownerStatus.state)` and `shareNote` from
`recipientShareNoteFor("mint-token", recipientArm(ownerStatus.state), ownerBuildability?.kind)`).
The copy is `MINT_UNBUILDABLE_NOTES` in `src/lib/status-surface-copy.ts`.

**Issue.** On the owner placeholder, the state line comes from compute *jobs*
(`readOwnerPendingStatus` → `deriveComputeState`). The new share note comes from the *analytics
row* through the probe. `recipientShareNoteFor` picks an UNBUILDABLE line whenever
`arm === "not_available"`. That arm covers `finished`, `never_started`, `failed` and `stalled`.
Every UNBUILDABLE line opens its reason with "Its last computation succeeded". Two of those arms
make that sentence contradict the line directly above it on the same page:

- **`never_started`.** It is reachable by construction. The `retention_compute_jobs_done` cron
  (`supabase/migrations/20260417110539_retention_crons.sql`) deletes `done` jobs older than 30
  days. A draft whose analytics are `complete` and whose last compute was more than 30 days ago
  therefore reads `never_started` (`deriveComputeState`: no chain job and `readExhaustive`). The
  page then renders KCS09-NEVER, *"No computation is running for this strategy, and none is on
  record."*, and directly below it the share note *"… Its last computation succeeded with fewer
  than 2 days of returns …"*. Project memory records that ledger venues never re-compute, so
  "more than 30 days since the last compute" is the normal state for such a strategy, not an edge
  case.
- **`failed` / `stalled`.** The latest job is `failed_final` (kept for 90 days) or a stalled
  stitch, while `strategy_analytics.computation_status` still reads `complete` from an earlier
  run, for example a fetch-phase failure that never reached the analytics writer. The page then
  renders *"The last computation stopped on a problem that retrying alone will not resolve."*
  and *"Its last computation succeeded, but its results cannot be built …"*.

Only the `finished` arm pairs coherently: KCS09-FINISHED already says the factsheet "could not be
built from its results". This is a user-facing contradiction on the page the owner uses to decide
whether to share. D-02's own rule is that the note must be true in every arm it is selected for.
`/strategies` shows only the note and no state line, so it is not self-contradictory there. Its
"last computation" wording still refers to a different computation than the owner page's line
for the `failed` / `stalled` case.

**Fix.** State the reason from what the probe actually measured, the stored results, and not from
"the last computation", which the job read owns:

```ts
const MINT_UNBUILDABLE_NOTES = {
  too_short:
    "Right now, a private link to this strategy shows that its factsheet is not available. Its stored results hold fewer than 2 days of returns, and a factsheet needs at least 2.",
  cannot_build:
    "Right now, a private link to this strategy shows that its factsheet is not available. We cannot build a factsheet from its stored results. Contact support@quantalyze.com to have this composite checked.",
} as const satisfies Record<UnbuildableNoteKind, string>;
```

Apply the same change to `PUBLIC_UNBUILDABLE_NOTES`. Then add a
`page.owner-compute-state.test.tsx` case for `never_started` + `too_few_points` and one for
`failed` + `composite_unbuildable`. Each should assert that the rendered page does not hold both
the state line's "none is on record" / "stopped" claim and a "last computation succeeded" claim.
Neuter the copy back, observe RED, then restore.

## Warnings

### WR-01: `/strategies` now issues one uncached, unbounded, heavy service-role read per computed row, plus a composite read of up to 20,000 rows each

**File:** `src/app/(dashboard)/strategies/page.tsx` (`StrategiesPage`, the `shareNotes`
`Promise.all` over `strategies ?? []`) → `probeFactsheetBuildable` → `resolveFactsheetInputs` →
`readCompositeFactsheet` (`src/lib/factsheet/composite-read-path.ts`).

**Issue.** Before this phase a computed row did no reads. Now every computed row does the following:
1. calls `createAdminClient()`;
2. selects the strategy row with the `strategy_analytics` embed, including `daily_returns`,
   `returns_series` and `metrics_json_by_basis`. These are the largest JSON columns in the
   schema, and they are fetched only for a yes/no answer;
3. for a composite, reads `csv_daily_returns` `.limit(20000)`;
4. in Node, runs `resolveDailyReturnSeries` plus a sort-and-dedupe (`hasBuildableSeries`) over the
   full series.

The list query has no pagination, and the fan-out is a bare `Promise.all`, so a manager with 40
computed strategies fires 40 heavy reads at once on every dashboard navigation. `/strategies` is
the dashboard's landing list. This is more than a latency concern. Pooler exhaustion turns into
`read_error`, and then into a false "unreadable" note on every row. Each row also calls
`captureToSentry` separately, so one saturation event produces N Sentry errors per page load.
This matters more than usual because SFH H-2 already shows that the "unreadable" note is wrong
for published rows.

**Fix.** The parity invariant has to hold, so the probe must keep running the resolve stage. The
cost can still be bounded:
- Cap the concurrency, for example a small local limiter of 4 in-flight probes.
- Coalesce the probe's Sentry captures to one event per page load, carrying a count tag
  (`probe_failures: n`).
- Record the cost, and book a writer-side follow-up: persist a `factsheet_buildable` verdict at
  the analytics write, or expose a column-light "resolve only" read. As long as `/strategies` has
  no pagination, the page cost grows linearly with the number of computed strategies.
If the phase keeps the current shape, write the accepted per-row cost in the `shareNotes`
comment. Today the comment says "probed, uncached" and nothing about cost.

### WR-02: The public-URL note is decided by a fresh probe, but the public recipient reads a 1-hour, id-keyed cache that also caches `null`

**File:** `src/app/(dashboard)/strategies/page.tsx` (`shareNotes`, the `probe.buildable` →
`[s.id, null]` arm and the `PUBLIC_UNBUILDABLE_NOTES` arm), versus
`buildFactsheetPayloadCached` in `src/app/factsheet/[id]/v2/page.tsx`.

**Issue.** For a published row, the note claims *"Right now, this strategy's factsheet link
shows …"*, or it is absent because the factsheet is buildable. The recipient of that link is
served through `unstable_cache` with an id-only key and `revalidate` 3600. The page's own comment
says `unstable_cache` stores a `null` unconditionally, and the only `revalidateTag("factsheet-v2:<id>")`
call in `src/` is in the admin `strategy-review` route. Two false "right now" states follow:
- A published strategy whose placeholder `null` was cached before its first successful compute
  keeps serving the placeholder for up to an hour. Meanwhile the probe says buildable, and
  `/strategies` shows no note, which reads as "the link shows your factsheet".
- A recompute that leaves the series unbuildable shows the PUBLIC-UNBUILDABLE note, while the
  link still serves the previous, cached, built payload.
The phase exists to make this note true. The cache staleness is pre-existing (the phase-148
TODOS item), but this phase is the first to make a precise present-tense claim that depends on
it.

**Fix.** Either `revalidateTag(\`factsheet-v2:${id}\`)` wherever analytics complete (the
compute-completion path), or soften the public lines so they do not assert the present state of
a cached page. For example, "The factsheet link cannot show numbers for this strategy: …" makes
a claim about the data, not about the page. Book the choice against the phase-148 cache item.

### WR-03: The owner lane throws away the builder's reason and re-runs the whole resolve (including the composite read) to recover it, which also creates the race SFH M-5 then has to handle

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`FactsheetV2Page`: `fetchAndBuildPayload(id, …)`,
then `readOwnerBuildability(id, ownerUid!)` → `probeFactsheetBuildable`) and
`src/lib/factsheet/fetch-and-build-payload.ts` (`fetchAndBuildPayload`: `if (!resolved.ok) return null`).

**Issue.** On the owner null path the same request runs `resolveFactsheetInputs` twice. That is
two heavy strategy reads and, for a composite, two `csv_daily_returns` reads of up to 20,000
rows. The second run exists only to recover a `reason` the first run computed and discarded.
The two runs are not atomic, so the answers can differ. `readOwnerBuildability` must then handle
`buildable: true` on a null payload, and `not_computed` after the builder refused. SFH M-5
proposes adding telemetry to that race arm. That treats the symptom. It is also the arm SFH
calls the one runtime detector of a D-09 break. With a single resolve, the invariant would hold
by construction and would not need a detector.

**Fix.** Add a module-private `resolveAndBuild(id, visibility)` that returns
`{ payload } | { payload: null; reason }`. `fetchAndBuildPayload` becomes a thin wrapper that
returns `.payload`, which keeps the one-declaration pin in
`phase-148-owner-lane-cache-isolation.test.ts`. Export a sibling, for example
`fetchAndBuildPayloadWithReason`, for the owner lane only. The owner lane then gets its reason
from the build it already ran, `readOwnerBuildability` loses its race arm, and the second
composite read disappears.

### WR-04: NO-NULL-AFTER-RESOLVE can only fail for a fixture that reaches the new null exit, so the docstring's "a rebase that adds a null exit breaks it" is overstated

**File:** `src/lib/factsheet/fetch-and-build-payload.test.ts` ("NO-NULL-AFTER-RESOLVE: every
fixture the probe calls buildable builds a payload"), together with the `probeFactsheetBuildable`
docstring ("A rebase that adds a null exit to `fetchAndBuildPayload` OUTSIDE the resolve stage
breaks it").

**Issue.** The test loops over `PARITY` and asserts `fetchAndBuildPayload !== null` for every
buildable fixture. Suppose a new null exit is added on a branch no fixture reaches: an
options/MTM `buildOpts` arm (every fixture has `metrics_json_by_basis: null` or a cash-only
headline), an `asset_class` branch, or a composite `gap_spans` path. The test stays green, and
the probe then says "buildable" while the builder answers null. On `/strategies` that shows as
**no note**, which is exactly the WR-02 class that 167.2-REVIEW raised. SFH M-5 names Phase 169
plans 04 and 05 as the edits that will touch `build-payload.ts`, so this is the regression the
guard exists for, and the guard does not cover it. The live-DB spec has the same limit: three
rows.

**Fix.** Make the invariant structural instead of sampled. Either:
(a) Type-level: have `hasBuildableSeries` narrow to a branded `BuildableSeries` type, and give
`buildFactsheetPayload` an overload `(strategy, BuildableSeries, opts) => FactsheetPayload`
(non-null). `fetchAndBuildPayload` then returns `Promise<FactsheetPayload>` after the resolve,
and a new `return null` stops compiling. Or
(b) A source-scan test: assert that the body of `fetchAndBuildPayload` after the
`resolveFactsheetInputs` call contains no `return null`, and that `buildFactsheetPayload` has
exactly the two known null returns. Neuter it, observe RED, then restore.
In either case, correct the docstring so it names what actually fails.

## Info

### IN-01: A delete race on `/strategies` is captured as an error and rendered as "unreadable"

**File:** `src/app/(dashboard)/strategies/page.tsx` (`shareNotes`, the
`probe.reason === "read_error" || probe.reason === "not_visible"` arm).
**Issue.** The row id comes from the owner's own RLS-filtered list moments earlier, and the probe
uses the owner predicate. So on this page `not_visible` means the row was deleted between the two
reads. It is not an outage. It is logged with `console.error` and captured as an error in the same
event group as a real `read_error`, which inflates the outage signal SFH M-2 wants to sharpen.
**Fix.** Split the arm. Keep `read_error` captured. Log `not_visible` at `console.warn` with no
capture, and either omit the note or render the unreadable line without a capture.

### IN-02: The new copy uses the passive voice DESIGN.md bans, and hardcodes the support address beside the `SUPPORT_EMAIL` constant

**File:** `src/lib/status-surface-copy.ts` (`MINT_UNBUILDABLE_NOTES.cannot_build`,
`PUBLIC_UNBUILDABLE_NOTES.cannot_build`).
**Issue.** "its results cannot be built into a factsheet" is passive. DESIGN.md § Voice /
microcopy requires "Active voice. 'We validate every row' — not 'every row is validated.'" Both
lines also spell `support@quantalyze.com` literally, while every other support line in the same
module interpolates `SUPPORT_EMAIL`, so a future address change would miss these two lines.
**Fix.** "We cannot build a factsheet from its stored results. Contact ${SUPPORT_EMAIL} …" (see
CR-01). The `status-surface-copy.test.ts` pins stay byte-exact.

### IN-03: "Buildable" means "no null exit", not "renders". A builder throw at the recipient still shows no note

**File:** `src/app/(dashboard)/strategies/page.tsx` (`if (probe.buildable) return [s.id, null]`).
**Issue.** The probe's documented domain excludes throws in `readSingleKeyBasisOpts` and
`buildFactsheetPayload`, for example `compute` on a pathological series. For such a row the list
shows no note, and the recipient gets the error boundary. This is documented in the probe's
docstring, but the `shareNotes` comment says the list and share page "decide from the builder's
own code", which reads as a full guarantee.
**Fix.** Add one sentence to the `shareNotes` comment that names the throw case as out of the
note's domain. No code change.

### IN-04: The owner lane awaits two independent reads one after the other

**File:** `src/app/factsheet/[id]/v2/page.tsx` (`ownerStatus = await readOwnerPendingStatus(...)`,
then `ownerBuildability = await readOwnerBuildability(...)`).
**Issue.** Neither read depends on the other, so the placeholder's latency is their sum.
Superseded if WR-03 is taken.
**Fix.** `Promise.all([...])`, or drop the second read per WR-03.
