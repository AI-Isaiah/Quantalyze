# 167.2.1 — Silent-failure review, round 1

Scope: `src/lib/factsheet/fetch-and-build-payload.ts` (`resolveFactsheetInputs`,
`probeFactsheetBuildable`, `fetchAndBuildPayload`), `src/lib/factsheet/build-payload.ts`
(`hasBuildableSeries`), `src/app/api/keys/[id]/memberships/route.ts` (`GET`),
`src/components/strategy/ApiKeyManager.tsx` (`readKeyCompositeMemberships`),
`src/lib/status-surface-copy.ts` (`unbuildableNoteKindOf`, `recipientShareNoteFor`),
`src/app/(dashboard)/strategies/page.tsx` (`StrategiesPage` `shareNotes`, `armOf`,
`uncomputedNote`), `src/app/factsheet/[id]/v2/page.tsx` (`readOwnerBuildability`).
All citations are by symbol.

## Premise measured before reading the handlers

`console.error` and `console.warn` do **not** reach Sentry in this repo. `register()` in
`src/instrumentation.ts` calls `Sentry.init` with `dsn`, `tracesSampleRate`, `environment`,
`beforeSend` and `beforeSendTransaction` and **no `integrations`**, so there is no
`captureConsoleIntegration`. The same file states that Sentry is server-only: there is no client
`Sentry.init`. Two consequences run through the findings below:

- A server-side failure that is only `console.*`-logged is invisible to Sentry.
- `captureToSentry` called from a `"use client"` component is a no-op in the browser.

## HIGH

### H-1 — A composite `csv_daily_returns` read outage renders "cannot be built, contact support", with nothing in Sentry

**Location:** `resolveFactsheetInputs` (the `if (!composite) return notBuildable("composite_unbuildable")`
arm and the G3 and G4 arms when `isComposite`). It is consumed by the `StrategiesPage` `shareNotes`
fall-through to `unbuildableNoteKindOf` and by `readOwnerBuildability`'s last `return`.

**Issue.** `readCompositeFactsheet` folds a `sparseErr` into an empty series and logs it with
`console.error`. Its comment says "Log at ERROR (→ Sentry)", which is false by the premise above.
The empty series then fails G3, and the probe answers `composite_unbuildable`. Both callers treat
that reason as a data fact: they pick `MINT_UNBUILDABLE_NOTES.cannot_build` or
`PUBLIC_UNBUILDABLE_NOTES.cannot_build` and capture **nothing**. Only the `read_error` and
`not_visible` arms and the `catch` call `captureToSentry`.

D-07 accepted the *reason-code* conflation, because splitting it would edit
`composite-read-path.ts`. It did not accept an uncaptured outage. The copy sends the owner to
support "to have this composite checked", and support has no event to look up. A transient
database blip on a composite's read turns into a durable-sounding defect claim on every
`/strategies` load until the read recovers, and no telemetry anywhere records that it happened.

**Hidden errors:** PostgREST timeouts, statement cancellation, pooler exhaustion, and a
permission regression on `csv_daily_returns` for the service role. All of them render as "cannot
be built".

**Recommendation.** This needs no edit to `composite-read-path.ts`, so D-07's reason stands. In
both callers, capture the `composite_unbuildable` arm at level `warning`, with tags only, e.g.
`stage: "factsheet-probe-composite"`. The event is not proof of an outage. It is what makes
"contact support" answerable. Correct the false "(→ Sentry)" comment in `readCompositeFactsheet`
when Phase 169 plan 04 edits that file, and route that correction there.

```ts
// StrategiesPage shareNotes, before unbuildableNoteKindOf(probe.reason)
if (probe.reason === "composite_unbuildable") {
  captureToSentry(new Error("factsheet probe answered composite_unbuildable"), {
    level: "warning",
    tags: { route: "strategies/page", stage: "factsheet-probe-composite" },
  });
}
```

### H-2 — On a PUBLISHED computed row, a probe failure renders a confident and likely false "not available yet"

**Location:** `StrategiesPage` `shareNotes`, in the `catch` arm and in the
`read_error` / `not_visible` arm. Both return `recipientShareNote(mode, "unreadable")`.

**Issue.** For `mode === "public-url"`, `recipientShareNote` ignores the arm (IN-04) and returns
`PUBLIC_URL_NOTE`: *"Right now, this strategy's factsheet link shows that the factsheet is not
available yet. The numbers appear there once a computation succeeds."* The "unreadable" intent of
D-05 is therefore discarded for every published row. Before this phase, a computed published row
got **no** note. Now a thrown probe or a `read_error` shows the owner a definitive statement,
while the public factsheet very likely renders fine, because it is a different request with the
same data. The tail "once a computation succeeds" is also false: the row is computed, since that
is the only way to reach the probe. D-05 is satisfied in the letter ("never read as buildable")
and missed in its purpose, because the failure is read as "not available" instead of "could not
check". The error is logged and captured, but the *user-facing* result is a wrong claim, not an
uncertainty.

**Hidden errors:** every probe throw (for example `createAdminClient` without a service key) and
every admin read error, on published rows only.

**Recommendation.** Add a public-url unreadable line, e.g. *"We could not check what this
strategy's factsheet link shows right now. Reload to check again."* Select it when
`mode === "public-url"` and the probe failed. Do not route it through `recipientShareNote`, which
by design cannot express this case. Pin it with a test that asserts the published + `read_error`
row does **not** render `PUBLIC_URL_NOTE`. The mint-token KCS12-UNREADABLE line has the same false
"once a computation succeeds" tail for a computed row, which is a milder instance of the same
issue. Reword it or add a computed-row variant.

## MEDIUM

### M-1 — Log lines cannot tell the probe from the build

**Location:** every `console.warn` inside `resolveFactsheetInputs`. They are prefixed
`"[factsheet] fetchAndBuildPayload — …"`, including "admin probe returned no strategy",
"analytics row is not a terminal success; withholding the payload" and "return series has fewer
than the minimum …; withholding the payload".

**Issue.** The lines moved into the shared stage verbatim, so a `probeFactsheetBuildable` call logs
as if a factsheet build ran. `/strategies` now emits one builder-labelled "withholding the payload"
warning per computed-but-unbuildable row **per list load**, with no factsheet request anywhere in
the trace. The owner lane of `FactsheetV2Page` emits the **same line twice** for one request
(builder, then `readOwnerBuildability`), and the two copies cannot be told apart. Anyone triaging
by `requestPath` in Vercel logs will chase a factsheet render that never happened. This matches
the memory rule "an effect never identifies the writer".

**Recommendation.** Give `resolveFactsheetInputs` a `caller: "build" | "probe"` argument and put it
in every log payload, and in the prefix, e.g. `[factsheet] resolve(probe) — …`. The two public
functions pass their own label.

### M-2 — `read_error` loses its code on the way to Sentry, and the builder path still captures nothing

**Location:** `resolveFactsheetInputs` G0 (`notBuildable(error ? "read_error" : "not_visible")`),
`fetchAndBuildPayload` (`if (!resolved.ok) return null`), and the `read_error` arms of
`StrategiesPage` and `readOwnerBuildability`.

**Issue.**
(a) G0 logs `errorMessage` and `errorCode` with `console.warn`, which is not forwarded. The probe
callers then capture `new Error("factsheet probe answered read_error")` with no code. The Sentry
event cannot tell a timeout from `42501` from a pooler refusal.
(b) This is pre-existing and now cheap to fix. On the builder path, a G0 `read_error` returns
`null`, and the public factsheet renders the "still computing" placeholder with **no Sentry event
at all**. The refactor now hands `fetchAndBuildPayload` a typed `reason` and then discards it.

**Recommendation.** Carry `{ reason: "read_error", code?: string }` out of the stage, and tag the
code (a PostgREST or SQLSTATE code is not identifying). In `fetchAndBuildPayload`, capture on
`resolved.reason === "read_error"` before returning `null`. `not_visible` and `not_computed` stay
silent, because they are legitimate.

### M-3 — `too_few_points` also covers a malformed or corrupt series, and tells the owner a false data fact

**Location:** `resolveFactsheetInputs` G3 (`dailyReturns.length === 0`) and G4
(`!hasBuildableSeries`) on the single-key arm, where the input is `resolveDailyReturnSeries` and
through it `normalizeDailyReturns` (`src/lib/portfolio-math-utils.ts`) and
`equityCurveToDailyReturns`.

**Issue.** D-07 calls the single-key cases "data facts, no read involved". But
`normalizeDailyReturns` (the `portfolio-math-utils` one that `resolveDailyReturnSeries` calls)
silently drops rows whose value is not a finite number (a numeric string included) and rows whose
date is not a string, and `equityCurveToDailyReturns` drops every step whose previous value is `<= 0`. A
row holding 500 corrupt entries, or a `returns_series` of the wrong shape, reaches G3 or G4 as
empty or short. The owner then reads *"Its last computation succeeded with fewer than 2 days of
returns"*, which is false. The only trace is a `console.warn` carrying `dailyType` and `isArray`.
That is a writer-side defect in the analytics job, rendered as a benign fact and never captured.

**Recommendation.** In G3 and G4, compare the raw entry count with the normalized count. When the
raw column had at least `MIN_FACTSHEET_SERIES_POINTS` entries but normalization left fewer, answer
a distinct reason. Map it to the composite-style "cannot be built, contact support" line, and
capture it. A short series that really is short keeps `too_few_points`.

### M-4 — The membership route's defence-in-depth tripwire fires silently

**Location:** `GET` in `src/app/api/keys/[id]/memberships/route.ts`, in the `rows.map` branch
`if (!strategy || strategy.user_id !== user.id) return { name: null, status: null }`.

**Issue.** The header calls this "defence in depth": `enforce_strategy_keys_owner_coherence` should
make a foreign-owned strategy impossible. When that branch runs, the trigger has regressed, or the
embed is dangling. Either one is a data-integrity event. The route lists the row, which is correct
because the warning still fires, but it logs nothing and captures nothing. A tripwire nobody hears
is not defence in depth.

**Recommendation.** Count the mismatches and the null embeds. If either count is non-zero,
`console.error` the counts (no ids) and `captureToSentry(new Error("key memberships: strategy
owner mismatch or dangling embed"), { tags: { route: ROUTE_TAG, stage: "coherence" } })`.

### M-5 — On the owner null-payload path, `buildable: true` is the D-09 invariant breaking, and it is swallowed

**Location:** `readOwnerBuildability`: `if (probe.buildable) return { unreadable: false, kind: null }`.

**Issue.** The docstring says that on this path `buildable: true` "can only be a race". The other
explanation is that someone added a null exit outside the resolve stage.
`buildFactsheetPayload` still has two of its own (`if (!dailyReturns.length) return null` and the
`hasBuildableSeries` gate), and Phase 169 plans 04 and 05 edit `build-payload.ts` (D-09). That is
exactly the regression `NO-NULL-AFTER-RESOLVE` guards against in tests. This branch is the one
**runtime** detector of it, and it returns the arm note with no log.

**Recommendation.** Log with `console.warn` and capture at level `warning`, with tags
`stage: "factsheet-probe-parity"`. A race is rare, so the event stays quiet unless the invariant
actually breaks. Do the same, at `console.warn` only, for the `not_computed` race arm in
`StrategiesPage`, so the race rate is measurable.

### M-6 — The client-side "unreadable" causes of the membership read never reach Sentry

**Location:** `readKeyCompositeMemberships`, in its trailing `captureToSentry(new Error("composite
membership read before a delete failed"), …)` call.

**Issue.** `ApiKeyManager` is `"use client"`, and Sentry is server-only, so this capture is a
browser no-op. The docstring's "logged, and captured with tags only" is true only for the route's
own 500s, which `GET` captures server-side. The other failures the card maps to "could not check"
reach only the user's browser console: the bound firing, HTTP 401, 404 and 429, a non-JSON body
and a malformed `memberships`. The user-facing behaviour is correct, since the confirm warns. The
observability claim is not. This is pre-existing across every `captureToSentry` in this component,
so it is a class and not a point defect.

**Recommendation.** Correct the docstring now, so it says the capture is server-side for 5xx only.
Book the class-wide question (a client Sentry init must adopt `scrubSentryEvent`, per
`instrumentation.ts`) rather than fixing one call site. Optionally, `console.warn` the 429 path in
the route, where it is observable.

## LOW

### L-1 — `unbuildableNoteKindOf` is not exhaustive

`default: return null` turns any future `NotBuildableReason` into "no kind". In `StrategiesPage`
such a reason falls through to `recipientShareNoteFor(mode, arm, null)`, which gives the
uncomputed copy for a computed row, or `PUBLIC_URL_NOTE` for a published row, without a signal.
List every reason explicitly and end with `const _exhaustive: never = reason`, so the compiler
flags the next one.

### L-2 — The membership fetch is not aborted when the bound wins

`readKeyCompositeMemberships` races the `read` IIFE against `bound` but passes no
`AbortController` signal to `fetch`. After a timeout the request and body read keep running and
the answer is discarded. Correctness is unaffected (`Promise.race` attaches a handler, so a late
rejection is not unhandled), but the request is wasted. Abort in the `finally`.

### L-3 — The route's Sentry events drop the error code

The `ownership` and `memberships` captures in `GET` create a fixed-message `Error` and log
`keyErr.message` / `membersErr.message` only to the console. Add `code: keyErr.code` (and the same
for `membersErr`) as a tag. It is not identifying, and it separates a timeout from a
permission regression.

## Done well

- `probeFactsheetBuildable` is always wrapped in `try`/`catch` by both callers, and a throw never
  reads as buildable (D-05).
- `GET` separates "read failed" (500, captured) from "no rows", returns the same 404 for an absent
  key and a foreign key, and never answers a policy-filtered `[]`. This closes 167.2 R2-L4 (b) at
  its root.
- `readKeyCompositeMemberships` bounds the body read together with the request, and it rejects a
  missing array and a non-object element instead of coercing them to `[]`.
- `hasBuildableSeries` is one predicate shared by the builder's gate and G4, so the probe and the
  builder cannot disagree on point counts.
