## Findings

### 1. ⭐ THE MIXED FILES' SHADOW IS PRIVILEGE-SHAPED, and it decides every twin

These seven gates make PRIVILEGE claims: *the owner can still read / delete its own row*, *the
client cannot INSERT*, *authenticated holds no EXECUTE*. The obvious mutation for each is to move
the privilege — and it does not work, MEASURED on the lane: a missing table privilege aborts psql
with `permission denied for table api_keys`, text that carries no `TEST FAILED (…)` at all, so the
runner scores **NO-IDENTITY**, not RED. Three of these arms even wrap that case in their OWN
non-idiom raise (`OUTAGE (1)`, `OUTAGE (6)`), which would claim the failure first anyway.

The falsifier that works is the **ROW filter**. RLS returns zero rows instead of raising, so the
same user-visible breakage — "the owner cannot reach its own row" — arrives at the arm as a value
mismatch it can name. Five of the fifteen twins turn on that distinction (`1` and `4` in both
api_keys files, and `1` in the profiles file), and each says so in its prose so the next reader
does not re-derive the dead end.

### 2. ⭐ A migration that REFUSES TO APPLY on an unidentified database — and why the fix is a data seed

`20260823120000_revoke_api_keys_insert.sql`'s pre-flight census (`:139-151`) will not guess which
database it is on: it takes the PROD branch only on `exchange='mt5'` rows created on three pinned
2026-08 dates, the non-PROD branch only on `api_keys` rows labelled `e2e-%`, and **ABORTS**
otherwise with `22000 … unidentified database`. On a virgin lane both signatures are absent, which
is exactly what that guard is for.

Dropping the migration was not an option: `5c scrub half` exists ONLY inside `IF v_insert_revoked`,
so without it that whole section is unreachable and un-twinnable. Stand-in
`25-fixture-api-keys-e2e-census-seed.sql` therefore seeds one `e2e-`labelled row — the same
signature the repo's e2e helper leaves on TEST/CI, which that migration's own comment measures at
3,530 of 3,544 rows there against 0 on PROD. It selects the migration's non-PROD BRANCH and nothing
else: the REVOKE, the column-comment marker and every structural post-verify run identically on
both branches, and it cannot select the PROD branch.

### 4. ⭐ ONE ARM CAME BACK NO-RED, AND THE APPLY LIST WAS THE DEFECT
