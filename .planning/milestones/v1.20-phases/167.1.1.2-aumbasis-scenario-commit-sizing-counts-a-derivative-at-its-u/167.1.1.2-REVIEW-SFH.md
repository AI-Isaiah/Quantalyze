## MEDIUM

### M-1: a book whose only included holdings are NULL-P&L derivatives writes no snapshot and is audited as "no holdings today"

- Evidence: `analytics-service/services/equity_reconstruction.py:4519` (`if not breakdown and not book_emptied:`),
  fed by the NULL-skip loop whose count and symbols are recorded at 4496-4503.
- Why it is a defect now: before this phase the writers stored 0.0, so such a book got a snapshot
  with a 0-valued `:PERP` key. With NULL stored (D-05), the loop skips every derivative and
  `breakdown` stays empty. The job then takes the "nothing to write" branch, and the
  `allocator.equity.refresh_complete` audit carries `reason: "no_holdings_today"`. That is false:
  holdings exist and their P&L is unreported. The `__pnl_missing__` record the phase adds
  (4582-4588) is created only AFTER this gate, so the stored curve carries no disclosure. The
  disclosure lives only in the separate `perp_upnl_missing` event.
- User and data impact: the allocator's legacy equity curve silently stalls on its last positive
  day. This is the same shape SFH-R2-02 already fixed for the emptied-book case, and the comment
  at 4510-4518 describes it. Anyone reading `refresh_complete` alone is told the book is empty.
  The RESEARCH Pitfall 3 choice to write no snapshot is sound (a fabricated $0 day is worse). The
  defect is only the reason label and the missing link between the two audit events.
- Hidden errors: any stuck poller or venue that stops reporting P&L (for example an OKX CCXT
  `unrealizedPnl: None`) for every derivative of an allocator with no spot rows.
- Recommendation: when the gate fires and `perp_upnl_missing_total > 0`, emit `reason:
  "derivative_pnl_unreported"` (or add `pnl_missing_count` to the existing payload) instead of
  `no_holdings_today`. Keep writing no row. Add one test for the all-NULL book that asserts the
  reason string is not `no_holdings_today`.

## Below the reporting bar (recorded, no action requested)

1. LOW: `aum_left_out_refs` is `.sort().slice(0, 50)` (`src/app/api/allocator/scenario/commit/route.ts:1203`)
   and `aum_left_out_count` counts ROWS (1201). A reader cannot tell a complete list from a capped
   one when the count is above 50, because rows can exceed distinct refs. The count itself is never
   truncated, so the disclosure survives. The Python `__pnl_missing__` record has the same
   count-versus-capped-symbols shape (50 cap).
2. LOW: `aum_left_out_count` is measured over the whole book, while the composer narrows to
   contributing keys. The route comment calls it "the figure the composer shows"; on a partial book
   the two can differ. This is the residual the route already records for the AUM itself.
3. LOW: `server_aum_not_positive` (route.ts:1145) is also what a book gets when ALL counted rows
   are left out (AUM 0 because unmeasurable, not because non-positive). This is per D-01 and
   D-03, and `aum_left_out_count == countedRowCount` disambiguates. A single sentinel was the
   founder's choice.
4. LOW: `reported_pnl` (`positions.py:30`) and `holding_equity_contribution` (Python) treat a
   non-finite P&L as 0.0 without marking it missing, while the TS route and composer count it as
   left out via `holdingEquityIsReported`. The totals agree (0 added); only the disclosure differs.
   The case is not reachable from JSON or NUMERIC transport in practice.
