## Warnings

### WR-01: MEDIUM (confidence 6). A push that changes only the dead-holder drill's inputs takes `none` and skips the drill

**File:** `scripts/sql-gate-subset.mjs:149` (`PUSH_MACHINERY_PREFIXES`), with the drill's inputs at
`scripts/pg-lane/mutex-dead-holder-lane.sh:45-46` and the gated step at `.github/workflows/ci.yml:2602`.

**Issue:** The `sql-mutation` job runs more than the mutation corpus. Its "Dead-holder drill" step
runs `scripts/pg-lane/mutex-dead-holder-lane.sh`, and that script executes two files that are outside
every machinery list:
- `scripts/mutex-dead-holder-verdict.sh`;
- the release-step body it extracts from `.github/workflows/supabase-migrate.yml`.

Neither path is in `MACHINERY_PREFIXES`, so neither is in `PUSH_MACHINERY_PREFIXES`.

Take a squash push that edits only one of those files, for example a change to the mutex release step
in `supabase-migrate.yml`. It changes no gate, no migration and no listed machinery, so `judgePush`
returns `none`. The scope step then writes `skip_lane=true`, and the drill (`if:
steps.scope.outputs.skip_lane != 'true'`) does not run on `main`.

Before this phase, every push to `main` ran the drill. On a pull request it still runs, because the
lane is never skipped there. On `main` it now runs only in the nightly, up to about 24 hours later.
D-09 accepted the nightly as the backstop for **mutation inputs**. The drill guards the shared-TEST
and PROD migration mutex, which is a different gate. Its inputs changing is exactly the case where it
needs to run.

**Fix:** Name the drill's inputs as push machinery, so such a push runs FULL. Then add a self-test row
showing that a push changing only `scripts/mutex-dead-holder-verdict.sh` is FULL:

```js
// scripts/sql-gate-subset.mjs: inputs of a lane step other than the corpus (the dead-holder drill)
export const LANE_STEP_INPUTS = ["scripts/mutex-dead-holder-verdict.sh", ".github/workflows/supabase-migrate.yml"];
export const PUSH_MACHINERY_PREFIXES = [
  ...MACHINERY_PREFIXES.filter((p) => p !== MIGRATIONS_DIR_PREFIX && p !== CI_WORKFLOW && p !== FLOORS_FILE),
  ...LANE_STEP_INPUTS,
];
```

The alternative is to move the drill ahead of the scope step's skip. It needs only PostgreSQL
binaries and runs in seconds.

### WR-02: MEDIUM (confidence 6). `migrationLoaders` silently drops setup entries it does not recognise, so a changed lane input can yield `none`, or a SUBSET that leaves out its loader gate

**File:** `scripts/sql-gate-subset.mjs:203-218`. The silent drop is the `continue` at `:213`.

**Issue:** The parser (`validateSetup` in `scripts/mutation-runner/parse.mjs`) accepts any
repo-relative `apply` path without `..`, and the lane applies every entry. `migrationLoaders` keeps
an entry only when it starts byte-for-byte with `supabase/migrations/`, and drops every other entry
without a word. Two cases are lost:

- **A setup input outside both directories,** for example `supabase/seed.sql` or
  `supabase/schema/*.sql`. A push changing it is not machinery, not a gate and not a migration, so
  `judgePush` returns `none`, the lane is skipped, and the gate that applies it is never mutated
  against the change.
- **A migration spelled in a form the parser accepts,** for example `./supabase/migrations/x.sql`.
  That gate is missing from `loaders.get("supabase/migrations/x.sql")`. A push changing `x.sql`
  becomes a SUBSET without that gate, or FULL-by-"loaded by no gate" if no other gate loads it.

Today's corpus contains neither case: every entry I measured is under `supabase/migrations/` or
`scripts/pg-lane/`. So this is latent. It still breaks the module's own "any doubt is FULL" rule,
and the next annotation that hits either case narrows a push silently. This corroborates SFH-01 in
`164.9.6-REVIEW-SFH.md`.

**Fix:** Fail toward FULL. Normalise each entry with `path.posix.normalize`. Throw, naming the gate
and the entry, when the entry is under neither `MIGRATIONS_DIR_PREFIX` nor a `PUSH_MACHINERY_PREFIXES`
directory. `derivePush` already turns that throw into FULL. Map the normalised spelling:

```js
for (const raw of parsed.setup?.apply ?? []) {
  const applied = posix.normalize(String(raw));
  if (PUSH_MACHINERY_PREFIXES.some((m) => applied.startsWith(m))) continue; // machinery forces FULL anyway
  if (!applied.startsWith(MIGRATIONS_DIR_PREFIX)) {
    throw new Error(`${rel}: RED-UNDER-SETUP applies ${JSON.stringify(raw)}, a lane input this derivation cannot map`);
  }
  ...
}
```

### WR-03: MEDIUM (confidence 6). A red SUBSET push to `main` is masked by the next `none` or SUBSET push, so `main` HEAD reads green with a known red unresolved

**File:** `scripts/sql-gate-subset.mjs:278-360` (`judgePush`) and `:825` (`derivePush`).

**Issue:** The push path judges only the pushed range. It never asks whether CI on `before`
concluded green. Before this phase, every push to `main` ran FULL, so a red `sql-mutation` came back
on the next push and stayed red until someone fixed it. Now it can disappear:

1. Push A changes gate G1. It takes SUBSET [G1], and `sql-mutation` goes red (an arm stopped biting).
2. Push B changes only `src/…` or `README.md`. It takes `none`, so `sql-mutation` is green and the
   `frontend` aggregator is green.
3. `main` HEAD now carries A's defect with a green board. Railway deploys B.

The same happens when B is SUBSET [G2]. It also happens when A ran no CI at all, for example because
the skip-trailer class suppressed it.

`classifyPushRange` handles exactly this shape for its docs-only short path through
`predecessorVerdict`, the subject of 164.9.4 review rounds 2 to 4. RESEARCH Pitfall 4 removed that
check from the subset path, to avoid a `gh api` call. Its justification covers only whether the
**PR** run was green ("that trust is D-03's own rationale"). It does not cover a red that **main**
had already measured. D-09 accepted the nightly as the backstop for **coverage**. It did not accept
a measured red turning green on the next push. The nightly would red HEAD again within about 24 hours,
but only if it runs (see SFH-03).

**Fix:** On a push to `main`, take `none` or SUBSET only when `before` is proven green. Reuse
`predecessorVerdict` from `classify-changed-paths.mjs`, the same proof the docs short path uses. If
it is not proven, return FULL with the reason. This costs the derivation step `checks: read` and
`GH_TOKEN`, which `changed-paths` already grants to the `classify` step. A narrower alternative is to
check only the `sql-mutation` check run on `before`, and treat FULL as owed when it is missing, red or
pending.
