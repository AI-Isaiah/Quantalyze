# Phase 170.2 Plan 04: /compare overlay (SC-3) Summary

The /compare equity overlay now draws each strategy's stored equity levels over the span its headline cumulative return covers, so the last point equals the table's Cumulative Return cell (+14.54% for the measured example) instead of the old compounding of levels, which read about 1e37 percent.

## What changed

- **Overlay maths.** `returns_series` stores LEVELS on a base of 1.0. The overlay read them as daily returns and compounded them. A clean row now plots `(level - 1) * 100`. A chain-broken row (alias exactly `"true"`) plots only days on or after its covered-from date, rebased on `openingLevel` (the stored level on the last stored day before that date): `(level / openingLevel - 1) * 100` for geometric, `(level - openingLevel) * 100` when `curveMethodFromFlags` says `simple`. A non-finite level is dropped, never plotted as 0. If no stored day precedes the covered-from date the whole series is plotted as a clean row with no note.
- **Tooltip** goes through `formatPercent(Number(value) / 100)`, so it prints the same string as the CompareTable cell (`+14.54%`).
- **Notes under the legend** (`<div className="mb-3 grid gap-1">`, `<p className="text-caption text-text-secondary">`, in legend order, nothing rendered when empty): `Measured since {date} ({name})`, `{name}: no return series yet.`, `{name}: the span of its cumulative return cannot be dated, so no curve is drawn.`, and the new `{name}: its measured span could not be loaded, so no curve is drawn.` A row with no line gets no swatch. When no row draws, the existing empty copy renders first, then the notes (C-7).
- **Read path.** `COMPARE_ANALYTICS_COLUMNS` gained `twr_chain_broken:data_quality_flags->>twr_chain_broken` (scalar alias only, the blob stays out); `StrategyAnalytics.twr_chain_broken?: string | null`; `readHeadlineCoversFrom` is now exported (body unchanged, doc comment names the compare page as second caller).
- **Compare page** reads the covered-from date with the service-role client only for rows the `withPublishedOnly` read returned whose alias is exactly `"true"`, in parallel, and passes only `headlineCoversFrom` and `headlineCoversFromStatus` to the overlay (not to the table or the correlation matrix). The series payload never leaves the reader.

## Decisions and additions the UI checker should see

- **New copy, not in the UI-SPEC copywriting table:** `{name}: its measured span could not be loaded, so no curve is drawn.` for a failed covered-from read. Same element, class and voice as the C-5 notes. It is a distinct state because the reader's contract says an outage is never rendered as "the span cannot be named".
- **Failed read degrades one chart.** The plan left this to discretion: one chart must not hide the comparison table, so the page does not throw to `compare/error.tsx`. The error message is logged through `console.error` (`[compare/page] covered-from read failed:`), never the error object. The reader's own message carries only the read name and PostgREST code, and a test pins that the database message is not logged.
- **Formatter copied, not imported.** `isoToMonthDay` lives in `MetricsColumn.tsx`, a client module that would pull the factsheet metrics rail into the /compare bundle for a four-line function, so `formatSpanDate` in the overlay copies its `Mon D, YYYY` UTC contract with a comment naming the source.
- **Two edge cases the spec does not name**, both treated as "span cannot be located" (no line, the C-5(c) note): a covered-from date after the last stored day (no point to draw), and a geometric opening level that is not positive (cannot be divided by).

## Known limits (recorded, not fixed)

- `-0.00%` for a value in (-0.00005, 0) is accepted per UI-SPEC C-4 (the table prints the same string).
- The overlay trusts `returns_series` to carry one point per date. Duplicate dates in a stored series would collapse to the last one in the merge map, as before.
- `readHeadlineCoversFrom` selects the full `cash_settlement` payload server-side to derive one date. At most four rows are read per page view and only for chain-broken rows (7 on PROD at research time), so a narrower JSON-path select was not added.
