## The bounds, with D-09's CORRECTED derivation

**Per-tick LIMIT 4. Per-venue rank cap 2. Attempt cooldown 20 hours.**

1. One refreshed strategy costs **up to 1500 s of worker time, not 900 s**:
   `derive_broker_dailies` (900 s) auto-chains to `compute_analytics_from_csv` (600 s) on the
   same sequentially-dispatching worker (`job_worker.py:488-504`, `:526`).
2. **The binding constraint is the 20-hour ATTEMPT cooldown, not the LIMIT.** The fan-out only
   enqueues; the worker drains asynchronously, so a tick that outruns the drain rate is not by
   itself a runaway. The cooldown plus the in-flight conjunct cap the outstanding backlog at the
   COHORT SIZE whatever the tick rate — 5 strategies ⇒ ~7500 s of queued work against 86 400 s
   of worker day.
3. The LIMIT is a **burst / smoothing cap only**, and must stay strictly greater than the cap or
   arm G1 stops discriminating one from the other.

The retracted `n × 900 s < 3600 s ⇒ n = 4` arithmetic appears nowhere in the shipped file; the
header says explicitly that it is wrong on both the cost and the model.

**A7's measurement, recorded as evidence and NOT as a reason to retune:** the real chain ran in
44 s (derive 35 s + auto-chained analytics) against the 1500 s ceiling — about 34× conservative.
The derivation stands as a ceiling, not an estimate.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 — Missing critical functionality] The in-flight conjunct did not cover `failed_retry`**
- **Found during:** Task 2, while choosing arm F's fixture status.
- **Issue:** The plan specifies "a `compute_jobs` row for this strategy in a non-terminal status",
  and the repo's canonical non-terminal set is `('pending','running','done_pending_children')` —
  what the RPC's dedupe (`20260716090000:259-261`) and
  `compute_jobs_one_inflight_per_kind_strategy` both use. But `CLAIMABLE_STATUSES = ("pending",
  "failed_retry")` (`job_worker.py:200`): a `failed_retry` row is scheduled to be claimed again.
  Neither the RPC nor the index would have stopped a second derive landing beside one, and two
  concurrent derives for one strategy is exactly what the venue that serialises on a single
  shared terminal registry cannot absorb.
- **Fix:** the conjunct includes `failed_retry`, with a comment stating that this set is
  deliberately WIDER than the RPC's and why.
- **Committed in:** `917c51ec`

**2. [Rule 1 — Bug, in my own task-2 output] The gate wrote rows it did not seed**
- **Found during:** the full-suite sanity run, via
  `analytics-service/tests/test_sql_gate_scoped_updates.py`.
- **Issue:** arms G1/G2 assert GLOBAL counts, so the first draft "quarantined" pre-existing
  candidates with `UPDATE public.strategies SET status='draft' WHERE id IN (SELECT … FROM
  ledger_refresh_staleness WHERE is_stale)`. On the ONE SHARED test project that is the D-05
  hazard on a neighbouring table: it writes across a concurrent PR's live fixture mid-run, and
  the surrounding ROLLBACK hides that from the WRITER, not from a concurrent READER. The existing
  D-05 gate only scans `strategy_analytics`, so nothing would have caught it.
- **Fix:** read-only isolation instead. (a) A fail-loud foreign-candidate PRECONDITION — a
  concurrent PR's fixtures are uncommitted and therefore invisible, so a non-zero count means the
  project carries committed stale live ledger strategies, which is a standing property a human
  should see rather than something this file should paper over. (b) Century-old seeds so the
  fixtures outrank any plausible foreign row — the reaper gate's own isolation-by-construction
  idiom. (c) `g2_v1` staggered a further century back so the cap's neutering reddens G2
  deterministically instead of by tie-break.
- **Verification:** all four SQL neuterings re-run against the REWORKED fixtures (the table above
  records those runs, not the pre-rework ones); the `4/0` claim measured directly.
- **Committed in:** `153de456`

### Non-fix changes, both about not tripping a gate with prose

**Every venue name was moved out of the function body.** Plan 05 gate 2 asserts the FUNCTION

plan's task 1 asks for D-01 "in full" as a comment on the composite conjunct, and D-01's text
names MT5; so does the per-venue cap's rationale. Writing either inside the body would have made
gate 2 red on prose. The full narrative lives in the file HEADER (outside the body) and the

`binance`, `okx`, `bybit`, `deribit`, `sfox`, `mt5`; the whole file contains 0 occurrences of
either pg_cron registration verb. This is the same lesson plan 01 recorded.

**Arm G2's claim was narrowed to what it actually proves.** The plan's wording is "the global
LIMIT is what stops it at 4". With two venues and a cap of 2, four is ALSO the ceiling the cap
alone imposes, so G2 does not by itself pin the LIMIT integer. It pins the 2/2 spread and the
LIMIT's LOWER edge; plan 05 gate 5 pins the upper edge. Making the LIMIT bind dynamically would
need a third venue in the tick, and the only third ledger venue is sfox, which CONTEXT forbids
any arm here from asserting produces work. The file says all of this rather than overclaiming —
a stated reason that is falsifiable-and-false is the failure D-16 is about.
