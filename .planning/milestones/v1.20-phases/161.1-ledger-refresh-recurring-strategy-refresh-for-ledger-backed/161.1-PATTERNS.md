### ⚠️ ONE DISAGREEMENT WITH THE ROADMAP SENTENCE — planner must absorb this

The prompt says `process_key_long` "is enqueued in exactly one place — strategy
creation (`api/strategies/finalize-wizard`)". **At HEAD that is wrong in both the
count and the location.**

- The Next route does **not** enqueue. Its own test says so:
  `src/app/api/strategies/finalize-wizard/route.test.ts:1630` — *"backbone, which
  enqueues process_key_long worker-side (NOT from this route)"*.
- The enqueue lives in the **Python** `routers/process_key.py`, at **two** sites:
  - `:1517` — the fresh long-fetch dispatch (`_is_long_fetch(body)` → `onboard`/`resync`)
  - `:765` — `_resume_duplicate_job`, the idempotent re-enqueue on a duplicate submit
- Next reaches it via `postProcessKey` (`src/lib/process-key-client.ts`), an
  internal-token HTTP call (`:477` `Authorization: Bearer ${internalToken}`).

**Consequence for the plan:** the new enqueuer's chain is *not* `finalize-wizard`.
It is either (a) a direct `enqueue_compute_job` RPC call that reproduces
`process_key.py:1517`'s metadata contract, or (b) an HTTP `postProcessKey` with
`flow_type: "resync"`. The two options have very different prerequisites — see the
next section, which is the single most load-bearing finding in this document.

## ⛔ BLOCKING PRECONDITION: `process_key_long` is NOT idempotently re-runnable

Before any file assignment, the planner must confront three gates inside
`run_process_key_long_job` (`analytics-service/services/ingestion/long_fetch.py:66-200`).
A naive recurring `enqueue_compute_job(p_kind='process_key_long')` **fails or no-ops
on all three**.

**Gate 1 — the drain check** (`long_fetch.py:94-106`):
```python
flag_at_claim = metadata.get("unified_backbone_at_claim")
...
if flag_at_claim != "true":
    log.info("process_key_long.drain_skip", flag_at_claim=flag_at_claim)
    return DispatchResult(outcome=DispatchOutcome.FAILED, error_kind="permanent")
```
This key is **not** set by the enqueuer — it is stamped by the *claim* RPC from a
live flag argument (`supabase/migrations/20260603120000_...:304-313`, preserved on
watchdog re-claim by `COALESCE`). So the enqueuer does not control it, but the
planner must confirm the prod worker passes `p_unified_backbone_active=true`, or
every new job dies `failed_final`.

**Gate 2 — mandatory metadata** (`long_fetch.py:108-113`): `verification_id` and
`source` are required; absence is a permanent failure. `flow_type` and `source`
must additionally satisfy the closed enums (`long_fetch.py:118-133`).

**Gate 3 — the advanced-status short-circuit** (`long_fetch.py:155-200`) — ⭐ **this
is the one that silently defeats the whole phase:**
```python
advanced_statuses = {"validated", "metrics_captured", "encrypted",
                     "report_queued", "published"}
if existing_data and existing_data.get("status") in advanced_statuses:
    log.info("process_key_long.advanced_status_skip", status=...)
    return DispatchResult(outcome=DispatchOutcome.DONE)
```
An onboarded strategy's verification row is `published`. Re-enqueuing
`process_key_long` **against that same `verification_id` returns DONE without
refreshing anything** — a green job, a fresh `compute_jobs` row, and a
`strategy_analytics.computed_at` that never moves. That is the current bug wearing
a success badge, and it would pass any check keyed on job status.

**Therefore a refresh requires a NEW `strategy_verifications` row**, exactly as the
existing user-triggered resync does. The authoritative minting path is
`process_key.py:1403-1445` (resync draft-dedup, then draft INSERT). Two viable
shapes, both with real analogs — the planner picks one and states why:

| Option | Analog to copy | What it buys | What it costs |
|---|---|---|---|
| **A — HTTP resync** (recommended): cron calls `postProcessKey({flow_type:"resync"})` per strategy | `src/app/api/keys/sync/route.ts:566-580` (`unifiedKeysSyncHandler`) | Reuses the verification mint, the resync draft-dedup (`process_key.py:1403`), the enum validation, the rate-limit, and the whole tested contract. Zero new SQL. | Fan-out is N HTTP calls from a Vercel function; needs bounding (see §MT5 concurrency) |
| **B — SQL fan-out RPC** | `enqueue_refresh_allocator_equity_for_all` (`supabase/migrations/20260420213754_allocator_equity_snapshots.sql:314-361`) | Advisory-locked, per-row idempotent, runs in-DB | Would have to mint `strategy_verifications` rows **in SQL**, duplicating the Python state machine. ### 4. The DORMANT ship pattern (prompt question 3)

There are **three distinct dormancy mechanisms** in this repo. They are not
interchangeable, and the phase needs a specific combination.

**(a) Fail-closed env flag — the `SFOX_ENABLED` / `MT5_ENABLED` pattern.**
Canonical helper, `analytics-service/services/closed_sets.py:93-109`:

Properties that make this the pattern rather than an ad-hoc `if`: read **per-call**

### 5. Staleness / observability keyed on `computed_at` (prompt question 5)

⛔ **Finding: no existing check keys a *refresh decision* on `strategy_analytics.computed_at`.**
Every `computed_at` consumer at HEAD is either a writer or a *stuck-row reaper*.
Success criterion 3 therefore has **no exact analog** — it is genuinely new logic,
and the planner should build it from the reaper's predicate shape rather than
expect a drop-in.

**Closest analog — the reaper predicate** (`supabase/migrations/20260516122247_portfolio_analytics_stuck_row_reaper.sql:19,50`):
```sql
--   * computation_status='computing' AND computed_at < threshold
     AND computed_at < (now() - p_stale_threshold);
```
Sibling for `strategy_analytics` specifically:
`supabase/migrations/20260802120000_strategy_analytics_stuck_computing_reaper.sql`.

⚠️ **A trap that document records** (`20260802120000_...:82`):
> *The SQL bridge re-stamps `computed_at = now()` on EVERY job transition*

Confirmed at `:342` and `:398` (`computed_at = now()` inside the status bridge), and
in the older bridges (`20260412094454_...:121,149,161`; `20260707120000_...:121,145,162`;
`20260708120000_...:119,147,167`). **So `computed_at` advances on a job transition,
not only on a successful recompute.** Combined with the Gate-3 short-circuit above,
a `process_key_long` that returns `DONE` without recomputing would still move
`computed_at` — reproducing the `last_sync_at` lie one column over.

⭐ **This is the highest-value thing for the planner to pin.** A staleness check on
`computed_at` alone is *not* sufficient to prove a refresh happened. The check should
corroborate with a value that only a real recompute can move — e.g. the latest
`strategy_analytics_series` date (`supabase/migrations/20260428120919_strategy_analytics_series.sql:75`),
which `supabase/tests/test_strategy_analytics_series_completeness.sql` already
exercises. That is the "economic invariant, not self-referential oracle" discipline.

Related existing recency comparison worth reading for query shape:
`src/app/api/admin/match/allocators/route.test.ts:229,291` (48h staleness with a
`computed_at` recency tiebreak).

### 6. MT5 concurrency — the fan-out bound (prompt question 6)

**Source of truth:** `analytics-service/services/mt5_concurrency.py`. Read its module
docstring (`:1-36`) before planning any fan-out; it is unusually prescriptive.

**The serialization invariant** (`mt5_concurrency.py:13-18`):
```
⚠️ A SECOND dict[str, asyncio.Lock] terminal registry anywhere in the tree
SERIALIZES NOTHING (MT5CONC-02 / 151-RESEARCH Pitfall 2). ... There must be
exactly ONE registry — this one. Import it; NEVER re-declare a terminal-lock
dict elsewhere.
```
Every mt5-touching kind contends on the same registry: `derive_broker_dailies`,
`sync_trades`'s balance arm, and the holdings fetch (`:6-11`).

**How existing callers bound themselves** — the pattern to copy is the *lease with an
explicit wait bound*, `routers/exchange.py:805`:
```python
async with mt5_terminal_lease(terminal_key, wait_s=_MT5_LEASE_WAIT_S):
```
Constants: `_MT5_LEASE_WAIT_S = 20.0s` (`mt5_concurrency.py:112`, env `MT5_LEASE_WAIT_S`) —
the *interactive* bound, chosen because "a human validating a key must not wait
forever" (`:297`). `_MT5_DERIVE_READ_TIMEOUT_S` (`:73-77`) is derived from
`MT5_REQUEST_TIMEOUT_S + 10s` rather than re-hardcoded, so a retuned rpyc bound
carries through — copy that derived-constant convention for any new timeout.

⚠️ **The v1.11 wedge shape, restated concretely for this phase.** MT5 keys serialize
on ONE terminal. N mt5 strategies fanned out at a fixed hour execute strictly
sequentially on the single prod worker, each up to the derive handler's ceiling —
`TIMEOUT_PER_KIND["derive_broker_dailies"] = 15 min` with a 30-min watchdog
(`main_worker.py`, `WATCHDOG_PER_KIND_OVERRIDES`), and `process_key_long` at
**30 min handler / 40 min watchdog** (`services/job_worker.py:500`,
`main_worker.py:306`). Worst case wall-clock ≈ N × 30 min on the interactive worker.
`flipretry-derived-equity-go-live.md:9` records what that did: 24 keys fanned onto
one sequential worker, event loop blocked on an `await`, `LAST_TICK_AT` froze,
healthz stale 12 minutes, the 90s auto-restart never fired.

**Mitigations with existing analogs:**
- **Stagger, don't burst.** `enqueue_compute_job` accepts `p_run_at`
  (`src/lib/database.types.ts:3652-3663`; 10-param internal overload at
  `supabase/migrations/20260716090000_...:181-189`). Spacing `p_run_at` per row is
  the least-invasive bound and needs no new machinery.
- **Route off the interactive worker.** `WORKER_CLAIM_ROLE` +
  `_claim_kind_args` (`main_worker.py:238-247`) already split `interactive` vs
  `backfill` claim scopes via `p_kind_exclude` / `p_kind_include`; pinned by
  `supabase/tests/test_claim_kind_filter.sql` and `test_staff_role_both_backfill.sql`.
- **Cap the batch.** No existing cron caps its fan-out — all four iterate the full
  population. A cap would be new; if added, it must be *deterministic* (e.g. oldest
  `computed_at` first) so a capped run does not starve the same tail forever.

**The SQL fan-out pattern in full** (`20260420213754_allocator_equity_snapshots.sql:314-361`)
— copy verbatim if Option B is chosen; the lock-release-on-error arm is the part
authors most often drop:
```sql
CREATE OR REPLACE FUNCTION enqueue_refresh_allocator_equity_for_all()
RETURNS VOID LANGUAGE plpgsql SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
DECLARE v_key RECORD; v_today TEXT := to_char(now() AT TIME ZONE 'UTC','YYYY-MM-DD');
BEGIN
  IF NOT pg_try_advisory_lock(hashtext('daily_equity_refresh')) THEN
    RAISE NOTICE '...another run holds the lock; skipping'; RETURN;
  END IF;
  BEGIN
    FOR v_key IN SELECT ak.id AS api_key_id, ak.user_id FROM api_keys ak
                 WHERE ak.is_active = TRUE AND EXISTS (...)
    LOOP
      BEGIN
        PERFORM enqueue_compute_job(
          p_strategy_id     := NULL,
          p_kind            := 'refresh_allocator_equity_daily',
          p_idempotency_key := 'daily-equity-' || v_key.api_key_id::text || '-' || v_today,
          p_api_key_id      := v_key.api_key_id);
      EXCEPTION WHEN unique_violation THEN NULL; -- already inflight; benign
      END;
    END LOOP;
  EXCEPTION WHEN OTHERS THEN
    PERFORM pg_advisory_unlock(hashtext('daily_equity_refresh')); RAISE;
  END;
  PERFORM pg_advisory_unlock(hashtext('daily_equity_refresh'));
END; $$;

REVOKE ALL ON FUNCTION enqueue_refresh_allocator_equity_for_all() FROM PUBLIC, anon, authenticated;
```

**Shared dedup primitive.** All of them lean on `enqueue_compute_job`, whose dedup
is on `(target, kind)` over **non-terminal** statuses, returning the existing id
rather than inserting — stated at `analytics-service/routers/process_key.py:744-748`
and pinned by `supabase/tests/test_enqueue_compute_job_dedupe_non_terminal.sql`.
Signature: `src/lib/database.types.ts:3652-3663`
(`p_strategy_id` required; `p_kind`; optional `p_allocator_id`, `p_api_key_id`,
`p_exchange`, `p_idempotency_key`, `p_metadata`, `p_parent_job_ids`, `p_run_at`).

⚠️ **Dedup does not equal freshness.** A strategy with a stuck non-terminal job is
skipped every tick, forever, silently. `supabase/tests/test_reconcile_dropped_enqueue_sweep.sql`
+ `supabase/migrations/20260816140000_reconcile_dropped_enqueue_sweep.sql` are the
existing treatment of that class — read them before relying on dedup alone.

### 8. pg_cron scheduling pattern (only if Option B)

**Analog:** `20260420213754_allocator_equity_snapshots.sql:369-392` — idempotent
`unschedule`-then-`schedule`, guarded on the extension so local dev is a NOTICE:
```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pg_cron') THEN
    IF EXISTS (SELECT 1 FROM cron.job WHERE jobname = 'refresh-allocator-equity') THEN
      PERFORM cron.unschedule('refresh-allocator-equity');
    END IF;
    PERFORM cron.schedule('refresh-allocator-equity', '0 5 * * *',
      $cron$SELECT enqueue_refresh_allocator_equity_for_all();$cron$);
  ELSE
    RAISE NOTICE 'pg_cron extension not present — skipping schedule (local dev)';
  END IF;
END$$;
```

05:30 derive-allocator-key-dailies (unscheduled), per the map at
`20260817120000_retention_orphaned_running_terminalize.sql:94`.
