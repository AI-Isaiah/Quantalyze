# 164.4.2.1 DRIFTOFFMUTEX — silent-failure review, round 1

Scope: `test-db-drift` in `.github/workflows/ci.yml` lost its `Acquire shared-test-db mutex`,
`Release shared-test-db mutex (best effort)` and `Verdict — shared-test-db mutex holder died
mid-job` steps. Also in scope: `measureHolders` and the new ordering `it` in
`src/__tests__/critical-regressions.test.ts`, the Test 2 floor in
`src/__tests__/mutex-dead-holder-verdict.test.ts`, and the comment edits in
`scripts/wait-for-test-schema-apply.sh`, the runbook and `CLAUDE.md`.

No database command was run. Every conclusion below comes from reading source.

## Headline: no reachable FALSE PASS was found

I tried to find a way for VAC-08 to pass on a half-applied or dropped TEST schema without
the key. I could not find one. The reasoning, so the next reviewer can attack it:

1. **Restore is atomic.** `restore-test-from-baseline.sh` assembles one `BEGIN; … COMMIT;`
   transaction. The `DROP SCHEMA public CASCADE`, the ledger `TRUNCATE` and the re-seed
   `INSERT`s all sit inside it, and `--mode restore` differs from preflight only in its
   terminator. A reader sees either the pre-restore state or the post-restore state.
2. **An apply only adds ledger rows.** So the frontier tip `check()` computes can only rise
   during an apply. It never falls. Any prefix of a `db push` that VAC-08 sees is a state it
   could already see before this change, by running just before `apply-test` took the key.
3. **Body drift fails toward red.** If a migration still in flight changes a
   `BODY_CHECK_FUNCTIONS` body, the checkout's snapshot and TEST disagree, and the result is
   `DRIFT`, which is loud.

⚠️ **UNMEASURED premise.** This assumes `supabase db push` commits each migration and its
ledger row together. If it does not, the extra intermediate states still produce only a
`DRIFT` red or a pass that matches the post-apply state. I checked this by reasoning through
the cases, not by running anything.

## HIGH

### SFH-01 — On `pull_request` events, `test-db-drift` now has NO ordering control, and none of the new prose says so

- **Location:** `ci.yml` job `test-db-drift`. The step
  `Wait for the TEST schema apply to conclude (merge pushes only)` has an `if:` ending
  `&& github.event_name == 'push'`. The new ordering `it` in `critical-regressions.test.ts`
  pins that exact `if:` string. The job-level `if:` admits same-repo PRs.
- **Issue:** Before this change, a PR run of VAC-08 was kept out of every concurrent
  key-holding writer by the mutex. Those writers are a `main` push's `apply-test` and a
  dispatched `test-restore-from-baseline.yml` restore. The wait never covered PR events, so
  on a PR the mutex was the ONLY thing between VAC-08 and those writers. Now nothing is.
  The new comment on `test-db-drift`, the runbook section 0 bullet ("For this job the wait
  is the only ordering control against `apply-test`") and the `CLAUDE.md` correction
  ("The wait is now its only ordering control") are all written from the merge-push point
  of view. None of them says that on PR events there is no control at all.
- **What now happens on a PR, and every outcome is loud:**
  - **VAC-08 overlaps a restore's `TRUNCATE`.** The `missing` query blocks on the
    AccessExclusive lock. Its `statement_timeout = '30s'` fires on all three
    `run_ledger_query` attempts, which takes about 96 s. Then `fail` prints
    *"the ledger presence query failed (exited N; … stderr … WITHHELD)"*. That message names
    no possible cause, and before this change a concurrent writer could never cause it on a
    PR. An operator will go looking for a connection or credential fault that does not
    exist.
  - **VAC-08 overlaps an `apply-test` of several migrations.** More than
    `FRONTIER_EXEMPT_CEILING` (3) migrations sit above the tip, so the gate reports *"a
    stalled apply … apply-test has stopped applying to TEST"*. That is a wrong diagnosis for
    an apply that is simply still running.
- **Hidden errors:** none silent. The defect is misattribution: a timing red now reads as an
  infrastructure fault or a stalled pipeline.
- **Recommendation:**
  - Say it where the decision is recorded: in the `test-db-drift` comment, runbook section 0
    and the `CLAUDE.md` correction, state that on `pull_request` events VAC-08 runs with no
    ordering control and why that is accepted (outcomes are loud-only, per the headline).
  - Make the two reds name the new cause. In `check()`, the ledger-presence `fail` and the
    `FRONTIER_EXEMPT_CEILING` breach message should add one clause, e.g. *"…or a TEST writer
    (a restore or another commit's apply-test) was running; this job holds no key since
    Phase 164.4.2.1 — re-run once `supabase-migrate.yml` / `test-restore-from-baseline.yml`
    are idle."*
  - Do NOT widen the wait's `if:` to PR events. It keys on `GITHUB_SHA`'s own
    `supabase-migrate.yml` run, which never exists on a PR. Every PR run would then sit out
    the appearance grace for nothing.

## MEDIUM

### SFH-02 — `measureHolders` misses any holder that does not spell the literal step name or the literal key number, and the D-02 negative pin shares that blind spot

- **Location:** `critical-regressions.test.ts`, `measureHolders`. Its predicate is
  `/- name: Acquire shared-test-db mutex|61616158/`.
- **Issue:** The repo already holds this key through spellings the regex cannot see:
  - `scripts/test-only-normalize-analytics-url.sh` and `scripts/restore-test-from-baseline.sh`
    each set `MUTEX_KEY=61616158` and take or check the lock inside the script.
  - `scripts/shared-test-db-keys.sh` is the established pattern for a key constant that
    lives in a helper.

  So each of these would acquire the key and be counted as a non-holder:
  - a ci.yml job that runs `bash scripts/<something>.sh` which takes the key;
  - a job that uses a composite action;
  - a job that uses an `env:`-sourced key;
  - a renamed step (`Acquire shared TEST mutex`).

  Because the new `it("test-db-drift holds and names no shared-test-db key …")` reuses the
  same detector, `test-db-drift` could quietly re-acquire by any of those routes and pass
  both the DB_JOBS equality and the negative. That silently brings back the 20m31s queue this
  phase removed, and nothing would go red.
- **Hidden errors:** a re-acquired key in `test-db-drift`; a new holder job that
  `DB_JOBS`-scoped pins never inspect (keepalives, ccci, the guarded reap, the verdict
  pairing).
- **Recommendation:** Widen the predicate to the ways the key is actually taken:
  `pg_advisory(_xact)?_lock`, `pg_try_advisory(_xact)?_lock`, a reference to any
  `scripts/*.sh` whose text contains `61616158`, and `PGAPPNAME=ci-shared-test-db-mutex`.
  For the script case, resolve each `bash scripts/X.sh` inside the job and grep X for the
  key. Neuter → RED → restore: add `bash scripts/test-only-normalize-analytics-url.sh` to a
  scratch copy of `test-db-drift` and confirm the negative fails.

### SFH-03 — The ordering pin proves the wait is present and first, but not that its failure can stop the job

- **Location:** the new `it("test-db-drift runs the ordering wait BEFORE VAC-08 …")`. It
  checks the `if:` (exact), the invocation (by substring
  `bash "${GITHUB_WORKSPACE}/scripts/wait-for-test-schema-apply.sh"`) and the order.
- **Issue:** The wait's only fail-closed outcome is `wait-outcome: wait-exhausted`, which
  returns 1. Its own comment makes it "the ONLY ordering control on VAC-08". Three one-line
  edits leave every assertion in that `it` green while turning the control into a no-op on
  exactly the event it exists for:
  - `continue-on-error: true` on the step;
  - `|| true` after the invocation (the substring match still passes);
  - dropping `set -euo pipefail` and adding a later command.

  `continue-on-error` in particular is pinned against elsewhere in this repo
  (`mutation-runner-floors.test.ts`, `supabase-migrate-test-first.test.ts`), but not here.
- **Hidden errors:** an exhausted wait (flag `held`, apply `running`, or either one
  `unknown`/`unreadable`) is turned into a green step, and VAC-08 then reads TEST during the
  apply of this very commit.
- **Recommendation:** On `waitStep`, assert
  `not.toMatch(/^\s*continue-on-error:/m)`, assert that the invocation line is the last
  command and has no `||`, and assert `set -euo pipefail`. Do the same for the VAC-08 step,
  whose `bash scripts/test-ledger-drift-check.sh` is pinned by an anchored regex but whose
  `continue-on-error` is not. Neuter each one and observe RED.

### SFH-04 — Two safety comments that the phase did not touch now state a premise that is false

- **Location:** `test-restore-from-baseline.yml`, the `THE ACTIVITY GATE` comment above
  `Activity gate — is shared TEST measurably quiet?`: *"any run that would collide is either
  already visible to this query or is still blocked on the mutex we are holding. There is no
  window."* Also `restore-test-from-baseline.sh`'s `RESTORE_REQUIRE_MUTEX` refusal: *"The
  mutex is the only thing keeping other people's CI out during DROP SCHEMA public CASCADE."*
- **Issue:** `test-db-drift` is now a CI session on shared TEST that the mutex does not keep
  out. It can start after the activity gate has measured "quiet", with no window closed
  against it. The restore's safety does not depend on this, because VAC-08 only reads. But
  the founder condition these comments encode ("only if TEST is measurably quiet") is now
  met with a known exception that the gate's own text denies. The next person to reason
  from "There is no window" will be reasoning from a false premise.
- **Recommendation:** Add a dated correction next to each one. Say that since Phase
  164.4.2.1 `test-db-drift` (VAC-08, read-only) is not kept out by the mutex, and that this
  is accepted because a read can only go loudly red against a restore (SFH-01), never write
  to TEST. Cite by symbol, not line.

## LOW

### SFH-05 — The new wait-script correction overstates how an overlap resolves

- **Location:** `wait-for-test-schema-apply.sh`, the `⛔ CORRECTED 2026-09-25` note inside
  `wait_for_apply`.
- **Issue:** It says *"an overlap makes them fail loudly, never pass falsely. A restore's
  lock blocks them until COMMIT or their statement timeout."* Two problems:
  - The restore takes AccessExclusive on the ledger only at its `TRUNCATE`, near the END of
    its transaction. For the whole `DROP SCHEMA public CASCADE` and replay before that point,
    VAC-08's reads go through against the pre-restore committed state and can PASS.
  - An overlap with an apply can also PASS through the frontier exemption.

  Neither is a false pass: each describes a state that really existed. But "fail loudly" is
  not the only outcome, and the sentence will mislead someone trying to explain a green
  VAC-08 that ran during a restore.
- **Recommendation:** Rephrase along these lines: *"an overlap either reads a committed
  state that really existed (pass or fail on its merits) or fails loudly; it cannot pass on
  a state that never committed."*

### SFH-06 — On a merge push there is a small TOCTOU window between the wait's exit and VAC-08's first read

- **Location:** `test-db-drift`. `setup-node` runs between the wait step and the VAC-08
  step.
- **Issue:** Before this change, the key closed this window against any later writer. Now a
  later push's `apply-test` or a dispatched restore can start inside it. The outcomes are
  only the loud reds described in SFH-01. This is recorded as a known window, not a defect.
- **Recommendation:** No code change. Mention it in the same place as SFH-01's
  documentation.
