### The key question: can VAC-08 now read TEST mid-apply or mid-restore, and go green on a half-built schema?

**Can it overlap a writer? Yes.**
- **PR runs.** There is now no control at all. The wait's `if:` ends `github.event_name == 'push'`, so it never runs on a PR, and the key is gone. Before this phase, a PR-run VAC-08 held 61616158. `apply-test` and the restore also take 61616158, so VAC-08 could not overlap either one.
- **Merge pushes.** There is a window of a few seconds. The wait reads "flag clear" at one instant, then `actions/setup-node` runs, then VAC-08. A restore dispatch or a later commit's `apply-test` can start inside that window.
- **Dispatch runs.** Not reachable. The job-level `if:` needs `github.event_name == 'push'` or a same-repo `pull_request`, so the job is skipped on `workflow_dispatch`.

**Can the overlap go falsely green? I found no path.** Three things make the reads fail closed:
1. **The restore is one transaction.** `restore-test-from-baseline.sh` builds a single `BEGIN; … COMMIT;` stream and feeds it to one psql session, which contains both `DROP SCHEMA public CASCADE` and `TRUNCATE supabase_migrations.schema_migrations`. Each VAC-08 read sees either the committed pre-restore state or the committed post-restore state, never the half-built schema in between.
2. **The TRUNCATE blocks ledger reads.** Its ACCESS EXCLUSIVE lock holds the `missing` and `ledger_rows` queries until COMMIT or until their 30 s `statement_timeout`. Retries are `LEDGER_QUERY_ATTEMPT_BUDGET=3`, so failure comes after about 96 s, and it is MEASURE_FAIL red.
3. **Other commits' rows cannot widen the frontier exemption.** The frontier tip is computed only from the checkout's own `repo_names` that are present in the ledger (the `frontier_tip` loop). Rows written by a later commit's migration are not in the checkout, so they cannot raise the tip. They surface only as the advisory `extra` line.

On merge pushes, the same-commit apply is covered by the Actions-API read in `probe_apply_state`. So the answer to "worse, green on a half-built schema" is **no**.

What the overlap does add is new *loud* false reds on PR runs, which the phase's docs say cannot newly happen. That is WR-01.

**Is the wait sufficient ordering?**
- **Merge pushes: yes, for the same commit.** The only gap is the seconds-wide TOCTOU window described above. That window is narrower than the one before the change: back then the wait was followed by up to 3600 s of queueing for the key, and a later apply could take the key first.
- **PR runs:** there is no ordering at all (WR-01).
- **Dispatch:** the job is skipped.

## Warnings

### WR-01: PR-run VAC-08 now has NO ordering control against `apply-test` or a restore, and the docs claim this adds no new red

**File:** `.github/workflows/ci.yml` (`test-db-drift` job; its `Wait for the TEST schema apply to conclude (merge pushes only)` step `if:`), `docs/runbooks/shared-test-db-mutex.md` (section 0, "The choice, and its reason"), `scripts/wait-for-test-schema-apply.sh` (`wait_for_apply`, the new ⛔ CORRECTED 2026-09-25 comment)

**Issue:** The runbook justifies Option A with: *"The worst case is a rare red that fails loudly. That red can already happen today, whichever job gets the lock first. The key bought it nothing."* That is true for merge pushes. It is false for PR runs.

Before this phase, the key was the only thing keeping a PR-run VAC-08 out of a concurrent restore or `apply-test`, because the wait never runs on `pull_request`. Three reds can now happen on a PR that could not happen before:
- A restore's TRUNCATE holds the ledger reads past `LEDGER_QUERY_ATTEMPT_BUDGET` × 30 s, which ends in MEASURE_FAIL.
- The `extra` query silently degrades to its `::warning::` branch.
- `pg_get_functiondef` races the restore's COMMIT, or a later apply's function replace, and fails `run_body_fetch`, which gives "could not read TEST's definition".

None of these is a false green (see Summary), and restores are rare manual dispatches. But the phase's own justification text is factually wrong, and an engineer triaging a PR-run VAC-08 red during a restore will be told this "can already happen today". The CLAUDE.md addition ("the wait is now its only ordering control") also does not say that on PRs there is no control at all.

**Fix:** Correct the claim rather than add a control, since reds are loud and the key's cost is measured. In the runbook's section 0 bullet and in the `wait_for_apply` ⛔ comment, add:

```text
On a pull_request run the wait does not run (its `if:` is merge-push only), so
VAC-08 has NO ordering against apply-test or a dispatched restore. An overlap
can red a PR (ledger lock wait past the retry budget, or a body-fetch race on
the restore's COMMIT) that the key used to prevent. It cannot turn a real
drift green: the restore is one transaction, and the frontier tip is computed
from the checkout's own migrations. Re-run the PR check after the restore.
```

Mirror one sentence into the CLAUDE.md 2026-09-25 correction.
