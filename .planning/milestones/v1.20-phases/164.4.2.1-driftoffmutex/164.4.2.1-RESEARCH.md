## Summary

`test-db-drift` holds the shared-TEST mutual-exclusion key `61616158` for 2–5 s of read-only VAC-08
SELECTs and waited up to 20m31s to get it (`164.4.2-MEASUREMENT.md` `## AFTER`, Runs 2–4). The job
already carries a SEPARATE ordering primitive — the `Wait for the TEST schema apply to conclude
(merge pushes only)` step (`scripts/wait-for-test-schema-apply.sh`) — which runs BEFORE the acquire
and refuses to proceed until (i) the `apply-test` job for THIS commit has concluded (or none exists
after a 90 s grace) AND (ii) the schema-apply-in-flight FLAG (advisory key `61616146`, held by both
schema writers, `apply-test` and the restore) is clear. SC-2's "reads shared TEST after apply-test's
schema apply" is therefore delivered by the wait step, not by the key. [VERIFIED: scripts/wait-for-test-schema-apply.sh:241-270, scripts/shared-test-db-keys.sh:56]

What the key adds for a READ-ONLY gate is only mutual exclusion against a schema writer that starts
AFTER the wait concluded (a later commit's `apply-test`, or a dispatched restore). Those writers are
transactional (the restore is one `BEGIN … COMMIT` stream; each migration file is its own
transaction), so a reader never observes a half-written file; and every interleaving that remains
produces a LOUD red (a statement timeout behind an `ACCESS EXCLUSIVE` lock, or a body newer than the
checkout's snapshot) — none produces a false GREEN, because a concurrent writer can only make TEST
*actually* match the repo, never merely look like it. The same false-red interleaving exists TODAY
with the key, because lock order between `test-db-drift` and a later `apply-test` is arbitrary.
`python` and `e2e-seeded` write rows, never the ledger or function bodies (grep below). So the key
buys VAC-08 nothing it relies on.

**Primary recommendation:** Option A — delete `test-db-drift`'s three mutex steps (`Acquire
shared-test-db mutex`, `Release shared-test-db mutex (best effort)`, `Verdict — shared-test-db mutex
holder died mid-job`) and change NOTHING else about the job: keep `needs: [python, changed-paths]`,
the `if:`, `timeout-minutes: 90`, `permissions:`, the ordering-wait step, `setup-node` and the VAC-08
step byte-identical. In the SAME commit, move the two tests that pin the holder set
(`critical-regressions.test.ts` `DB_JOBS`, `mutex-dead-holder-verdict.test.ts` Test 2 floor 5 → 4)
by measurement, and add a pin that `test-db-drift` holds NO key and still carries the ordering wait
before VAC-08.

⚠️ **Predicted outcome, stated before the change so it cannot be graded on its narrative:** the fix
removes the 20-minute tail (Runs 2 and 4 → e2e-seeded-bound, ~17–18 min) and passes clause (c) on
non-overlapping runs, but clause (a) AS WRITTEN ("run-total must land BELOW 16m18s") is predicted to
FAIL, because on non-degenerate runs `e2e-seeded` (waiting on `python`, untouched here) is the
critical path at ~18m. The ROADMAP Goal ("no slower than before", "falls back inside its BEFORE
band") and SC-3 ("meet clause (a)") disagree. That must be resolved before plan lock — Q1.

### Interleavings once the key is gone (exhaustive)

| Concurrent event during VAC-08's ~5 s | What VAC-08 sees | Verdict effect | Same with the key today? |
|---|---|---|---|
| Same-commit `apply-test` not yet concluded | cannot happen — the wait step blocks until `apply-concluded` / `no-apply-run` with flag `clear` | — | same (wait is before the acquire) |

| The same, mid-transaction | nothing — MVCC; uncommitted DDL is invisible [CITED: supabase.com/docs/guides/deployment/database-migrations — a change "which can't run in the same transaction" gets its own file ⇒ one file = one transaction] [ASSUMED that the ledger INSERT shares that transaction — A1] | — | — |
| A dispatched restore (`DROP SCHEMA public CASCADE` + TRUNCATE ledger, one `BEGIN … COMMIT`) | reads block on `ACCESS EXCLUSIVE` until COMMIT or hit `statement_timeout = '30s'` → `run_ledger_query` retries then MEASURE_FAIL | **RED** (loud) or a correct read of post-restore TEST | with the key the restore would have waited or VAC-08 would have — green; the gain is avoiding a rare loud red |
| `python` / `e2e-seeded` writing rows | nothing VAC-08 reads | none | — |

**No interleaving yields a false GREEN**: a green requires every repo migration present and every
trio body equal to the committed snapshot; a concurrent writer can only make that TRUE, never make a
true drift look absent. The residual cost is a rare, loud, self-explaining red on a restore dispatch
or a back-to-back migration merge — the same class that already exists under arbitrary lock order.

### Pattern: a read-only gate orders itself by FACT, not by lock
The repo already separates the two units ("TWO KEYS, TWO DIFFERENT UNITS", scripts/shared-test-db-keys.sh:7-37):
the mutual-exclusion key for writers, and the in-flight flag that readers READ without blocking.
VAC-08 is a reader of schema state; it belongs on the flag side only.

### Anti-Patterns to Avoid
- **A private key for `test-db-drift`** — explicitly banned in the job's own ⛔ block ("Do NOT give this job its own private lock key"); it would also re-create a holder the DB_JOBS pin must track.
- **`pg_try_advisory_lock` / `pg_advisory_lock_shared` on the FLAG key from the reader** — banned: "IT MUST NEVER TRY TO TAKE THE LOCK TO FIND OUT" (shared-test-db-keys.sh:73-78); a reader holding the flag makes every other reader see "held".
- **Deleting the ordering wait "since the key is gone"** — it is now the ONLY ordering control (SC-2).
- **Leaving `61616158` in a comment inside `test-db-drift`** — keeps it a "holder" by the pin's regex.
- **Reading clause (c)'s `test-db-drift` acquire-wait of 0 as evidence** — zero BY CONSTRUCTION, the exact vacuity 164.4.2 struck from its own refutation text.

### Pitfall 1: the holder-set pin reads comments
**What goes wrong:** `critical-regressions` stays RED after the steps are deleted.
**Why:** holder detection is `/- name: Acquire shared-test-db mutex|61616158/` over the whole job body including comments.
**How to avoid:** rewrite in-job comments to name "the shared-test-db key" without the literal, or accept and delete; verify `awk` span count of `61616158` in `test-db-drift` = 0.

### Pitfall 2: the anti-vacuity floor
**What goes wrong:** `mutex-dead-holder-verdict.test.ts` Test 2 (`>= 5`) fails at 4.
**How to avoid:** lower to 4 in the SAME commit with a dated reason naming this phase; never delete the floor.

### Pitfall 3: clause (a) is predicted to fail
**What goes wrong:** the phase ships, and SC-3 reads FAIL on clause (a) even though the regression is gone.
**Why:** measured this session (`gh api …/runs/<id>/jobs`): `e2e-seeded` ends within 6–11 s of `test-db-drift` on Run 1 (`00:53:07` vs `00:53:18`) and on `35968690547` (`07:34:27` vs `07:34:33`) — on non-degenerate runs `e2e-seeded` is the critical path (~17–18 min) and this phase does not touch it. Run 4 shows the win (`e2e-seeded` ended `05:09:25`, `test-db-drift` `05:24:41` → ~15 min saved → ~17m25s run-total); Run 2 shows no win (`e2e-seeded` itself waited 19m25s behind an overlapping sibling run and ended at `02:05:14`).
**How to avoid:** resolve Q1 before plan lock; state the prediction in the new MEASUREMENT file before code.

### Pitfall 4: a migration-touching merge push is a different stratum
**What goes wrong:** the ordering wait inherits `apply-test`'s own queue behind `python`/`e2e-seeded`; the 900 s budget can exhaust → `wait-exhausted` RED.
**Why:** pre-existing (the wait already preceded the acquire), but the five 164.4.2 AFTER runs carried NO `supabase-migrate.yml` run (their "runs counted for the SHA" lists none), so it has never been measured.
**How to avoid:** record, per AFTER run, whether a `supabase-migrate.yml` run exists for the SHA; report migration pushes as their own stratum; do NOT raise `WAIT_BUDGET_SECONDS` in this phase (SC-4 spirit; the script forbids setting it in a workflow).

### Pitfall 5: node_modules absent at the phase root
**What goes wrong:** `vitest` from the main checkout's `node_modules/.bin` fails to load `vitest.config.ts` here (observed this session: a `requireStack` error from `vite`).
**How to avoid:** executor runs tests in a worktree/checkout with installed deps (`npm ci`), or verifies with `node --version` + an actual `vitest run` before trusting a result.
