## New findings

### N1. MEDIUM, user-facing: `marks_trailing_since` is write-only. Nothing reads it, key mode never stamps it, the composite never carries it
`job_worker.py:7503-7518` (computed), `8564-8571` (stamped), `8266` (key mode returns before the prestamp), `11428-11440` (composite flag merge, no trailing); reader grep: no hit for `marks_trailing_since` anywhere under `src/`.

Scenario: a strategy's account enters a state no mark can be taken in (borrow, options holder, dust, non-USDT asset). Marks end on day X; every realized row after X is dropped (Pitfall 7). The CR-03 fix stamps `marks_trailing_since` in strategy `data_quality_flags`, but `fetch-and-build-payload.ts` only parses `marks_since`. The published factsheet therefore still silently ends at X, which is exactly what CR-03 said must not happen; the new test proves only that the Python flag exists. For an allocator key (key mode), the computed value is discarded at the early return, so My Allocation's curve stops with no note. A composite re-stitch never merges or pops it.

Minimal fix: (a) add `marks_trailing_since` to the factsheet `dqf` type and render one dated note beside the `marks_since` marker (reuse `parseMarksStart`); (b) write it into the key-mode `_key_inputs_payload` beside `marks_since` and have `readMarksStart`'s sibling surface it; (c) pop/merge it in the composite flag block. If (a) is out of scope, book it as a user-facing gap and do not describe CR-03 as closed.

### N2. MEDIUM, user-facing (data-integrity): a composite member whose window is still OPEN loses its P&L after its last applied mark, silently
`job_worker.py:9693-9712` (`_apply_member_marks`): the WR-03 tail rule keeps realized rows only when `window_end <= mark_day_for(now)`. For an open window the rows after the member's last mark are dropped and the stitch zero-fills them, assuming "the next mark covers it".

Scenario: a ccxt member's key becomes structurally refused after day X (nightly, never clears). Window open, so no tail kept, no next mark ever comes. Composite shows the member flat from X+1 on; its real P&L for those days is lost and no flag says so (composite merges `mark_gap_days` only up to each member's last mark, and has no trailing flag per N1).

Minimal fix: when a member's `marked.terminal` day is before `min(window_end, mark_day_for(now))`, add the member's trailing start to a composite `marks_trailing_since` (earliest across members). Optionally keep the realized tail for days older than N (for example 2) days past the last mark.

### N3. LOW: a LAST mark that gets no return row is not reported as trailing
`nav_marks_apply.py` loop plus `job_worker.py:7516-7518`. Trailing uses `terminal` (the last STORED mark day), not the last emitted row. If the last mark's base is unusable (non-finite or at or below `dust_floor`), it emits no row while `terminal` equals the label day, so no trailing flag; `mark_gap_days` is strictly between S and the last mark, so it omits that day too. Realistic only when the previous level is dust and no flow arrived. Fix: stamp trailing from `max(emitted)` rather than `terminal`, and include the last mark in the gap list when it has no row.

### N4. LOW: the flow-read skip rule can discard most marks without any signal beyond a day list
`nav_marks_apply.py` (`if md != last_mark and md + 1 in flows: skipped`). An account with a flow dated every day (a recurring sweep) skips every mark except the last. The one last mark then replaces all realized rows from S on with ONE return, and `marks_since` is still stamped, so the factsheet shows "Recorded equity begins" over what is effectively one observation. Pnl is preserved; resolution (volatility, Sharpe, drawdown) is not. Fix: log one warning with skipped/total when skipped is more than half, or do not stamp `marks_since` when fewer than 2 marks were used.

### N5. LOW: `mark_gap_days` can grow without bound
A permanently negative or dust level makes every later mark base-unusable, so the list gains a day each night and is stored and re-parsed every derive. Cap the stored list (for example the latest 400) with a count.

### N6. LOW: `mark_input_nonfinite` / `mark_days_not_ascending` still end as permanent FAILED with "needs nothing from you"
`job_worker.py` seam (about 7515-7540). Input is history, so it repeats forever, which is the intended class, but the copy tells the user nothing and a non-finite stored flow is a data-corruption signal worth a Sentry capture. Fix: `logger.error` with key id and token (confirm the existing line is error level).

### N7. LOW: `readMarksStart` selects whole `key_inputs` payloads
`queries.ts:4173-4177` pulls each key's full payload (returns arrays) to read one date. Not a silent failure; a payload past the row cap would surface as the existing error path. Fix later with a `payload->marks_since` projection.
