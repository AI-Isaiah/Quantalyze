## Decisions for the founder (plan rule 10)

A mark is read on the UTC day after its label, so a flow dated the read day (mark day + 1) may be inside the read. Flows carry days only, so the code cannot place it by instant. `apply_marks` names the mark day in `mark_flow_read_days` and leaves the arithmetic unchanged (that flow is held out when it is also after the last mark, and enters the next derive's base otherwise). This is the planner's recorded decision, implemented as written; it belongs in the phase summary the founder reads.

## Deviations from Plan

### Auto-fixed Issues

None.

### Judgment calls inside the plan's interface (no rule triggered)

1. **Refusal-token mapping for malformed inputs, not fixed by the plan's closed set.** A mark day that is not a canonical `YYYY-MM-DD` string is `mark_days_not_ascending` (it cannot be ordered). A flow or day-P&L key that is not a canonical ISO day is `mark_input_nonfinite` (an input the rule cannot read). A realized-terminal day that is not a canonical ISO day is `mark_terminal_day_mismatch`. A boolean or non-numeric amount is `mark_input_nonfinite`. A malformed `returns` index (not ISO strings or a `DatetimeIndex`, or a repeated day) raises a plain `ValueError`, because it is a programming error and not an input refusal.
2. **Terminal checks.** With `roll_basis="returns"`, a non-None `realized_terminal` that is not the input's last index day is `mark_terminal_day_mismatch` even when no base is needed; an empty input with a non-None terminal is therefore a mismatch (plan: "an empty input takes `realized_terminal` None"). A missing terminal is `mark_base_unrollable` only when an input day precedes S. With `roll_basis="day_pnl"`, `day_pnl` and the terminal-day check apply only when a base is needed.
3. **Task 1 intermediate state.** To keep Task 1 to its listed rules, the `E >= S` branch raised `mark_base_unrollable` as a fail-closed placeholder until Task 2, which is what made the roll tests go RED in Task 2.
4. **Tests added beyond the plan's list:** `test_a_datetime_index_input_keeps_its_index_type` (the derive builds a `DatetimeIndex`, the compose reads ISO strings), `test_the_token_set_is_closed`, `test_compose_roll_property_over_random_marks_and_flows` (300 seeded histories, oracle is `replay_key_equity`), `test_first_mark_base_equals_the_compose_roll_of_the_realized_series` (200 seeded histories with `E >= S`, oracle is `replay_key_equity` on the realized series), `test_a_caller_supplied_scalar_input_is_used_verbatim`, and extra refusal cases (zero first base, a mark of zero as the next base, no terminal, NaN terminal, infinite flow). Drill D-G is also extra.
5. **Branch name.** The plan text names `feat/167.2.1.1.1-navmtm`; the orchestrator assigned this worktree on `feat/167.2.1.1.1-p03`, so I committed there. That branch is not in the `agent-*` namespace that the executor's pre-commit allow-list expects for isolated worktrees. It is not a protected branch, and the orchestrator's dispatch named it explicitly, so I treated it as an orchestrator-assigned branch and proceeded.

## Known limits (recorded, not fixed)

- `covered_days` that lie outside `[first row, last row]` of the sparse series are accepted and still counted in `covered_day_count`, though they cannot affect `gap_spans`. The plan did not ask for a range check.
- On a series with covered days, `compute_all_metrics` receives a scalar input that is not gap-free (by design, D-15). It ran without error on every test input, including the unpatched calls in the new test file. Plan 14's post-deploy readout is where the effect on real strategies is measured.
- Flows are day-granular, so a deposit inside a gap is weighted as present for the whole gap (research OQ-8(b)); the days are named by `mark_gap_days`.
