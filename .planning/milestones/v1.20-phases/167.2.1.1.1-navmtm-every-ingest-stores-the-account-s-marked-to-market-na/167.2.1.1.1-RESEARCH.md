## Summary

The mark has one natural writer and one natural reader seam, both inside the daily derive. All five venue branches of `run_derive_broker_dailies_job` converge on the same four local variables, `equity, balance_error, open_unrealized_usd, upnl_unreadable`, before `_run_key_mode_compose_epilogue()` persists `key_inputs`. That convergence point is the minimal place to write a mark with no extra venue read for OKX, Deribit, MT5 and sFOX. Bybit and Binance are the exception: today's derive read is the realized-basis USDT wallet with a hard-coded `0.0` wedge, so L4 forces one extra venue read there (`fetch_positions()`), which contradicts the literal "no extra venue calls" in D-02 (Open Question OQ-1).

The return series cannot use marks by a small edit to one combiner: five call sites build returns (`reconstruct_nav_and_twr` twice in `services/transforms.py`, MT5 and the NAV-levels sibling in `services/broker_dailies.py`, the native Deribit core, and sFOX via `chain_linked_twr`). The recommended design therefore applies marks once, as a pure function at the derive's persist seam (the "MT5-12 verdict seam", the code comment calls it the fail-loud chokepoint every keyed venue passes through). It pins the level on every marked day to the stored NAV, emits no row and no level for an unmarked day after the start (D-05, revised 2026-10-26), and gives the next marked day one return that spans the whole gap; D-04's step day falls out of the same rule as the first such span. The compose job then needs no new input: if the derive stores a marked terminal and marked writer-basis fields, the compose's backward roll reproduces the marked levels by construction, and any inconsistency is caught by the existing `KEY_INPUTS_MISMATCH` (blocking) degrade.

Two findings change the plan beyond what CONTEXT anticipated. (1) The key-mode derive already runs daily for every eligible key (`derive-allocator-key-dailies`, 05:30Z, all active, non-revoked, non-disconnected keys), so D-02's gap is only the strategy-mode derive, which `cron_sync` queues for `stored > 0` strategies only. (2) Moving the chain to hour 0 collides with an existing SQL gate that fails any `derive-allocator-key-dailies` schedule outside hours 1-22, and with native-BTC pricing: `latest_completed_close_day` needs the previous UTC day's BTC close, which the Vercel `refresh-benchmark` cron writes at 00:30Z, after a 00:10Z derive would read.

**Primary recommendation:** New table `api_key_nav_marks` (surrogate `id`, `UNIQUE (api_key_id, mark_day)`, owner FK, grants-based append-only, no trigger beyond the house owner-coherence one), written first-writer-wins by the derive at the persist seam, consumed by one pure `apply_marks` function in a new `services/nav_marks.py`, with the chain moved by a runbook live operation plus a committed manifest update, and the benchmark refresh moved ahead of it.

## 1. The marks table (D-01, D-06, D-07)

### Shape (recommendation)

```sql
-- SKETCH, not a verified definition. Names are the recommendation; types follow reviewer invariant 7.
CREATE TABLE public.api_key_nav_marks (
  id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  api_key_id       UUID        NOT NULL REFERENCES public.api_keys(id) ON DELETE CASCADE,
  allocator_id     UUID        NOT NULL REFERENCES auth.users(id)      ON DELETE CASCADE,
  mark_day         DATE        NOT NULL,   -- the UTC day this mark closes (D-03)
  marked_at        TIMESTAMPTZ NOT NULL,   -- exact instant of the equity read
  venue            TEXT        NOT NULL,   -- CHECK against the closed venue set
  nav_native       NUMERIC,                -- D-07: native amount incl. open profit
  open_pnl_native  NUMERIC,
  native_unit      TEXT,                   -- 'USD' for venue-USD reads, 'BTC' for a BTC MT5 account
  nav_usd          NUMERIC     NOT NULL,
  open_pnl_usd     NUMERIC     NOT NULL,
  price_day        DATE,                   -- D-07: close day used to price native to USD; NULL when native is USD
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT api_key_nav_marks_key_day UNIQUE (api_key_id, mark_day)
);
```

- **Key choice.** `UNIQUE (api_key_id, mark_day)` is the write-once key. A surrogate `id` PK (as `csv_daily_returns` has since `20260624120000`) keeps the GDPR export's `getOrderColumn` fallback to `id` valid; a composite natural key with no `id` would need an `ORDER_COLUMN_OVERRIDES` entry, and `mark_day` is not unique across one user's keys, so it could not be that override [VERIFIED: `src/lib/gdpr-export-manifest.ts` `ORDER_COLUMN_OVERRIDES` docblock, "Each chosen column is `NOT NULL` ... ORDER BY is total and deterministic"].
- **Column types.** Reviewer invariant 7: "durations and PnL-derived columns MUST be NUMERIC, not INTEGER or DOUBLE PRECISION" [VERIFIED: `.claude/agents/migration-reviewer.md` invariant 7]. `csv_daily_returns.daily_return` is DOUBLE PRECISION for the series; the marks are dollars and stay NUMERIC. NUMERIC admits `'NaN'`: add `CHECK (nav_usd <> 'NaN'::numeric AND open_pnl_usd <> 'NaN'::numeric)` (the worker already refuses non-finite amounts before JSONB, so this is the DB-side twin).
- **Day vs time coherence.** A CHECK `mark_day = (marked_at AT TIME ZONE 'UTC')::date - 1` makes the label a function of the read instant (D-03 "labels the day that just closed"). It is only correct if the writer's eligibility window (OQ-3) keeps every accepted read on the day after its label.
- **Native fields (D-07).** Single-currency reads store `native_unit` and `nav_native`. Deribit is multi-currency (per-currency native ledger collapsed at marks), so one native number/unit does not exist: OQ-4.
- **Owner column.** `allocator_id` NOT NULL REFERENCES `auth.users` (= `api_keys.user_id`, sourced from the preflight, never a job payload) mirrors `csv_daily_returns` and `allocator_equity_derived`; the GDPR hook triggers on exactly this shape: "`user_id UUID` ... or `(user_id|allocator_id) UUID NOT NULL`" [VERIFIED: `scripts/check-gdpr-export-coverage.ts` regex, `allocator_id)\s+UUID\s+NOT\s+NULL`].

### RLS, grants, append-only, cascade

- **RLS (house pattern).** `ENABLE` + `FORCE ROW LEVEL SECURITY`; owner `SELECT` for `authenticated` with `USING (allocator_id = auth.uid())`; a `service_role` `FOR ALL` policy documenting intent; no anon policy [VERIFIED: `supabase/migrations/20260717233529_allocator_equity_derived_surface.sql` STEP 2: `CREATE POLICY allocator_equity_derived_owner_select ON allocator_equity_derived FOR SELECT TO authenticated USING (allocator_id = auth.uid());`]. Per-key owner gate precedent: `csv_daily_returns_allocator_owner_select ... USING (allocator_id = auth.uid())` [VERIFIED: `20260624120000_csv_daily_returns_per_key_axis.sql`].
- **BYPASSRLS caveat.** `service_role` skips RLS even with FORCE, so policies cannot make the table append-only for the worker [VERIFIED: `.claude/agents/rls-policy-auditor.md` "BYPASSRLS"]. D-06 therefore needs a grant-level control. House precedent: `REVOKE UPDATE, DELETE ON audit_log FROM authenticated, service_role;` [VERIFIED: `supabase/migrations/20260416201929_audit_log_hardening.sql:92`]. Recommend `GRANT SELECT, INSERT` to `service_role`, `REVOKE UPDATE, DELETE, TRUNCATE` from `authenticated, service_role, anon, PUBLIC`.
- **First-writer-wins.** The service-role write is `upsert(..., on_conflict="api_key_id,mark_day", ignore_duplicates=True)`, i.e. `ON CONFLICT DO NOTHING` (precedent: `persist_equity_snapshots` uses `on_conflict="allocator_id,asof", ignore_duplicates=True`) [CITED: ACCTREBUILD RESEARCH Q1, which read `equity_reconstruction.py:1370-1377`]. `DO NOTHING` needs only INSERT. After the insert the writer must **re-select the stored row** and use it, not its own read (Pitfall 1).
- **Key delete.** `ON DELETE CASCADE` from `api_keys` is what D-06 calls "the existing key-delete cascade" (same as `csv_daily_returns.api_key_id`). A trigger-based append-only guard would block cascades and needs a `quantalyze.sanitize_in_progress = 'on'` exemption (reference: `20260710160000_api_keys_published_composite_delete_guard.sql`); the grants route avoids it.
  - `[ASSUMED]` RI cascade deletes run with the table owner's privileges, so the `service_role` REVOKE does not block them. The SQL test must delete an `api_keys` row (and call the sanitize path) and read the marks gone; do not rely on this sentence.
- **Owner coherence.** `csv_daily_returns` guards `allocator_id = api_keys.user_id` with a BEFORE INSERT/UPDATE trigger function (`enforce_csv_daily_returns_owner_coherence`). Copying it adds one function, which costs bookkeeping (below). Skipping it leaves coherence to the worker (which sources `allocator_id` from `ctx.key_row["user_id"]`). Recommend copying it: a mismatched owner would let one user read another's NAV, and the trigger is the cheap DB-side proof.

### 4.2 Are funding and fills paid at 00:00Z available by about 00:10Z?

Funding rows are stamped on the cadence boundary.
- **Which day owns a payment stamped exactly 00:00:00Z?** The derive buckets by UTC date and `_bucket_8h` uses windows `[00:00, 08:00)`, so a 00:00:00Z payment belongs to the **new** day D+1. A 00:10Z equity read already contains it. So the mark labelled D includes up to ~10 minutes of D+1 settlement. This is not a data-arrival problem; it is a label skew with a bound. Under the revised D-05 it has no arithmetic consequence: after the start no realized P&L is used, every return is the observed difference between two stored marks, so nothing is counted twice. It only means the label D is "the read taken just after D closed", which is exactly what `marked_at` records.
- **Arrival latency by venue is unmeasured.** Whether Bybit, OKX and Binance expose a 00:00Z funding row to the read APIs within ten minutes is `[ASSUMED]` (A3): the repo comments say settlements land on hour boundaries but not how long the ledger endpoints lag. Deribit funding is not a separate row (continuous accrual inside the transaction log) [ASSUMED: A3]. MT5 is not on this clock: deals are bucketed by `deal_utc_day(time, server_utc_offset_s)`, where the server offset is itself `[ASSUMED A2]` in the source comment. The equity read itself is a live balance, so the mark does not wait for ledger rows. Recommendation: measure arrival with one orchestrator reading after the first 00:10Z run (newest funding row timestamp per venue at read time, counts and ages only). The post-start return series does not depend on ledger rows at all (revised D-05), so lag cannot corrupt a stored value or a marked return; it matters only for the pre-start realized-basis history and for the strategy's trade-sync freshness.
- A mark is an observation, not a ledger sum: it is correct at `marked_at` whatever the ledger has caught up on. That is why the mark time is stored (D-03 third bullet) and why the eligibility window (OQ-3) is a property of `marked_at`.

### 4.3 Which day is the derive's last return day?

Not a fixed day. The returns index is the union of days with realized P&L, funding or flows, gap-filled between first and last (`gap_fill_daily_returns`: "Reindex to EVERY calendar day in `[first, last]`"), so the last return day is the last day with any event, not "today". At 00:10Z on D+1 a perp book with a 00:00Z funding payment has a row for D+1 (10 minutes old, funding only); a quiet book ends days earlier. The live anchor is placed on that last day (`terminal_nav = anchor_nav - open_unrealized_usd`, "MTM-at-endpoint"). Therefore: **the mark's day is derived from `marked_at`, never from the series' last day**, and a series' last return day may be one day after its latest mark. After the start (S) the revised D-05 drops such a trailing realized row: post-start the series ends at the latest mark day.

## 5. How marks are consumed

### 5.1 The rule (pure function)

`apply_marks(returns_realized, flows, realized_terminal, marks) -> (returns_marked, levels_marked, flags)`, in a new `services/nav_marks.py`, USD only, no I/O:

1. Rebuild the realized levels `L_real(d)` for days before the start by the same backward roll the compose uses (`equity_{t-1} = (equity_t - F_t)/(1 + r_t)` from `realized_terminal`), so the function needs only quantities available at the seam.
2. `S` = earliest `mark_day`. For `d < S`: level and return = today's realized-basis values, untouched (L1). Realized rows dated `>= S` are dropped; after `S` the series holds marked days only.
3. For a marked day `d >= S`: level = `nav_usd(d)` (**pin**; SC-2 "uses the stored marked NAV for every day it exists", SC-3 exact reproduction).
4. For an unmarked day `d > S` (**D-05, as revised 2026-10-26**): no level, no return, no row. Nothing is carried and no realized P&L is read. The day is named (below).
5. Return on a marked day `d`, with `p` the previous marked day (or, for `S`, the last pre-start day) and `G` the set of days strictly between `p` and `d`:
   `r(d) = (M_d - (L_p + sum_{g in G} F_g) - F_d) / (L_p + sum_{g in G} F_g)`.
   One return, stamped on `d`, covers the whole gap. Flows dated inside the gap enter the **base**, flows dated `d` stay in the numerator. That placement is forced, not chosen: the compose treats a flow on a no-return day as an `r = 0` equity day (HIGH-1 flow-day union), so its stored levels step by `F_g` on the gap day, and the next return's base must be the stepped level for the compose roll to reproduce `M_d` exactly. It weights a mid-gap deposit as if present from the first gap day (OQ-8). For a gap of zero days this is the audited chain-link definition [VERIFIED: `chain_linked_twr` docstring `r_t = (NAV_t - NAV_{t-1} - F_t) / NAV_{t-1}`].
6. Index: realized days before `S`, then exactly the mark days. A quiet key's series therefore reaches its latest mark.
7. Flags (counts and ISO days only): `mark_gap_days` (the unmarked days between `S` and the latest mark, sorted) and `marks_start`. These two are the "named" gap (D-05) and the start (D-08/L2) in one place.

Properties that fall out, each a test:
- **D-04.** `r(S) = (M_S - L_real(S-1) - F_S) / L_real(S-1)`; when `nav_usd - open_pnl_usd == L_real(S)` this equals `(P_S + U_S)/L_real(S-1)`, the realized return plus the boundary open profit, booked once on `S` [Pitfall 6].
- **D-05.** A day with no row yields no row. The next mark's return equals the observed change over the gap (flows adjusted as in step 5). Nothing in the output is computed from a day that has no mark.
- **Cumulative identity (independent oracle).** With zero flows, `prod(1 + r) - 1 == M_T / L_real(S-1) - 1` over any span that starts at `S-1`; the oracle is computed from the stored marks in the test, never from the code under test.
- Nothing before `S` changes: byte-identical to today's series for those days (D-09 / no backfill proof).
- **Consumers of a sparse series.** Rows stay sparse (gap days absent). `derive_basis_series` has `densify_policy` of `"sparse"`, `"broker_nan"` or `"zero_fill"` ("`sparse` -> rows verbatim"; `broker_nan` turns every in-span absence into a guard NaN; the default re-densifies with 0.0) [VERIFIED: `services/basis_series.py` module docstring]. Default 0.0 fill would add zero-return days to the scalars; `broker_nan` would mark the chain broken. Neither matches "no return of its own"; the plan must pick `"sparse"` or accept and name the distortion (OQ-8).

### 5.2 Why the compose needs no new input (and the coherence requirement)

The compose rolls each key backward from its stored terminal over its stored returns. If the derive stores (i) marked returns, (ii) the marked terminal (`anchor_usd` is already the live equity, which on the last mark day equals the mark) and (iii) a `realized_terminal` / writer-basis payload that describes the **marked** basis, the roll reproduces the marked levels exactly (the chain `r(d)` is the inverse of the roll). Fields that must change together, otherwise the compose detects a mismatch and degrades blocking (`KEY_INPUTS_MISMATCH`, `writer_basis_mismatch`):
- ccxt venues: `_ccxt_terminal_usd = float(equity) - float(open_unrealized_usd)` (stored as `realized_terminal_*` when the wedge is non-zero) must become the marked terminal once marks cover the last day.
- MT5 and Deribit writer basis: `writer_basis_payload(_basis_day_pnl, _composed_flows_usd)` carries `NAV_t - NAV_{t-1} - F_t` per day; marked days change that P&L, and the compose's writer-basis mode requires "every return day is in W or carries a stored return of exactly 0.0" and `realized_terminal` on `max(W)`.
- `dropped_day_pnl`, `native_*`, `segment_terminals` are untouched pre-`S`.
- **Gap days in the compose.** A gap day has no return row. With no flow it falls under the existing benign flag `_MISSING_RETURN_INSIDE_COVERAGE` ("a key-day inside the key's own coverage with no return row AND no flow ... The key's level is carried with r = 0, as before; the flag says it happened"), so the allocator curve draws the previous mark flat across the gap [VERIFIED: `services/allocator_equity_compose.py` module constants]. That is a drawn carry of a stored value, not a new value, but the chart must not present those days as observed (UI-SPEC, Section 6). In writer-basis mode the post-start day set W holds marked days only; the "every return day is in W" rule still holds because gap days are not return days.

This is the highest-risk part of the phase and the reason the pure function should be tested against `replay_key_equity` directly (Section 7, T-PY-3).

## Common Pitfalls

### Pitfall 1: Using your own read instead of the stored mark
**What goes wrong:** two derives (key-mode fan-out and strategy-mode from `cron_sync`) read equity seconds apart; the loser's insert is ignored but its in-memory read feeds its series, so the stored mark and the persisted returns disagree by the move between reads.
**How to avoid:** after `DO NOTHING`, reselect and use only the stored row. Test: two derives, different reads, both series use the first value.

### Pitfall 2: Late retry labels a drifted read as the closed day
**What goes wrong:** a transient failure retries the derive at 05:00Z; a mark labelled D now holds five hours of D+1.
**How to avoid:** a mark is accepted only inside the eligibility window after 00:00Z (OQ-3); outside it no mark is written and the day becomes a gap day (D-05). First writer in-window wins.

### Pitfall 3: Native BTC keys unpriced at 00:10Z
**What goes wrong:** the previous day's close is not stored yet (Vercel `refresh-benchmark` is at 00:30Z today), so BTC-priced MT5 keys write no mark every day.
**How to avoid:** move the benchmark refresh ahead of the chain; test that a missing close yields the `native_unpriced` refusal, not a mark priced at an older close.

### Pitfall 4: Marks without the coherent key_inputs fields
**What goes wrong:** marked returns with a realized `realized_terminal` or writer-basis payload make the compose roll land on the wrong levels or degrade blocking, so the allocator curve flips to the legacy fallback.
**How to avoid:** change returns, terminal and writer-basis fields in one commit with one test that composes the result (T-PY-3).

### Pitfall 5: A quiet strategy's series never reaches its mark
**What goes wrong:** `gap_fill_daily_returns` stops at the last activity day.
**How to avoid:** after `S` the series index is the mark days; D-02 change 1 also enqueues the derive.

### Pitfall 6: The step is more than open profit
**What goes wrong:** D-04 books `nav_usd - L_real(S)` as the step. That equals `open_pnl_usd` only when `nav_usd - open_pnl_usd == L_real(S)`. OKX (`totalEq - upl`) and MT5 (`equity - balance`) satisfy it by construction; Deribit's realized terminal is rolled from the native balance "at the mark of the last ledger day" (CR-01 comment: `U` = open uPnL plus any coin mark move since the last ledger day); Bybit/Binance satisfy it only with the USDT-wallet basis (Section 2.1).
**How to avoid:** the identity is a per-venue test; on Deribit the step also contains the coin mark move since the last ledger day (real MTM profit) and the plan states it.

### Pitfall 7: Realized rows leaking past the start
**What goes wrong:** the realized path still emits a row for a day `>= S` that has no mark (for example the 10-minute D+1 row a 00:00Z funding payment creates). Persisted, it would be a return of its own for an unmarked day, which D-05 forbids, and it would double count what the next mark's span covers.
**How to avoid:** `apply_marks` drops every realized row dated `>= S`; the delete-absent reconcile (`csv_daily_returns` upsert, then delete absent days) then removes stale rows. Test: a derive whose realized series has a row on an unmarked post-start day persists none.

### Pitfall 8: Reading position history to "fill" earlier days
D-09. `allocator_holdings` and `position_snapshots` must not be read by the mark writer; a spy test proves no call.

### Pitfall 9: Copying the newest migration's wrapper
`BEGIN`/`COMMIT` and `search_path = public, pg_temp` appear in the ACCTREBUILD file but violate reviewer invariants 14 and 3 as written; follow the invariants (Section 1).

```python
# SKETCH. Pattern source: persist_equity_snapshots uses on_conflict + ignore_duplicates.
def _write_nav_mark(supabase, row):  # row: dict with api_key_id, mark_day, marked_at, nav_usd, ...
    supabase.table("api_key_nav_marks").upsert(
        row, on_conflict="api_key_id,mark_day", ignore_duplicates=True

        .eq("api_key_id", row["api_key_id"])

        .single()
        .execute()
        .data
    )
    return stored  # the authority; never `row`
```

### Pin rule core (pure)
```python
# SKETCH of apply_marks' loop; levels are USD floats, days are ISO strings.
# D-05 (revised): unmarked post-start days produce nothing.
prev_level, gap_flows = last_pre_start_level, 0.0   # L_real(S-1)
out = {}
for d in ascending_days_from_start:            # every day >= S that has a mark OR a flow
    if d not in marks:                         # no mark: no row, no level, no return
        gap_flows += flow.get(d, 0.0)          # flow sits in the next base (compose convention)
        gap_days.append(d) if is_inside_marked_span(d) else None
        continue
    base = prev_level + gap_flows
    out[d] = (marks[d].nav_usd - base - flow.get(d, 0.0)) / base   # one return spans the gap
    prev_level, gap_flows = marks[d].nav_usd, 0.0
```
