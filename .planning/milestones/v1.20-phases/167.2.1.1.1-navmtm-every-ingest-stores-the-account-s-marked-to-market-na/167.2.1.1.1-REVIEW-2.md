# Phase 167.2.1.1.1 NAVMTM: Code Review Report, round 2

## Summary

The round-1 refusal class is gone. CR-02 and SFH F1 are fixed: the apply no longer needs a live
terminal, and an unusable base is a gap, never a permanent FAILED. WR-01, F2 and IN-06 are fixed.
The fixed suites pass at HEAD (136 Python tests in the seven NAVMTM files, 193 vitest tests in the
three TS files).

Two fixes create new money-math defects, and both are reproduced with the module under review:

1. **WR-02's read-day skip tests whether the day is a KEY in the flows dict, not whether a flow
   landed on it.** Every Deribit path feeds a dense flows dict, with `0.0` on every NAV day
   (`native_composed_flows` through `_iso_day_amounts`). So every Deribit mark except the last is
   skipped, and the whole marked era collapses into one return that is re-stamped every day (CR-01).
2. **CR-01's first-mark base reads the first mark's wallet, and that wallet can hold a flow dated
   `S+1` that landed before the read.** WR-02 then skips `S` but keeps that base, so the next
   return books the flow a second time. The result is a permanent fabricated loss or gain of
   about `F/base` (CR-02, reproduced: -32% where the truth is +2%).

The tests did not catch either one. Every apply test uses a sparse flows dict, and several
derive-level fixtures were moved off the read day so that the new rule would not touch them
(IN-04).

Reproduction scripts (read-only, run with `analytics-service/.venv/bin/python -I <script> "$PWD"`
from `analytics-service/`): `/tmp/navmtm-r2/deribit_dense.py`, `/tmp/navmtm-r2/dense_flows.py`,
`/tmp/navmtm-r2/first_mark_read_day_flow.py`, `/tmp/navmtm-r2/cr02_cr01.py`.

## Critical Issues (HIGH)

### CR-01: The WR-02 skip fires on zero-valued flow days, so every Deribit mark but the last is dropped and the marked era is one return [HIGH, user-facing, data-integrity, introduced by the WR-02 fix]

**File:** `analytics-service/services/nav_marks_apply.py:281` (`md + timedelta(days=1) in flows`) and
`:319-321` (`mark_flow_read_days`, same test). The flows come from
`analytics-service/services/job_worker.py:602-606` (`_iso_day_amounts` keeps every entry, zeros
included) applied to `native_ledger_composed_flows`. That function returns the flows "on every NAV
day (zero where no flow landed)" (`native_nav.py:773-788`, built over the union calendar at
`:500-551`). Affected call sites, all of them Deribit:
- strategy mode, `job_worker.py:7440-7444`
- allocated twin, `:7431`
- key-mode writer basis, `:7387` (`_composed_flows_usd` from `:5129`)
- composite Deribit member, `:9911`
- composite allocated member, `:9775`

**Issue:** a Deribit NAV day exists for every day with ledger P&L or a flow. Daily settlement,
funding and trades make that nearly every day for an account with positions, so the dict has a key
for `d+1` on nearly every mark day `d`. Every mark that is not the last is skipped. The output is
the realized rows before `S`, then ONE row on the last mark that spans `S..last`, with every day in
`mark_gap_days`. Every derive moves that row to the new last mark, so:
- the published series holds a single marked observation, whatever the age of the marks;
- vol, Sharpe, Sortino and drawdown for the marked era are computed from one point (D-15 turns
  into "the whole era is one observation");
- the key-mode `writer_day_pnl` is `0.0` on every gap day, so the My Allocation curve is flat from
  `S` and jumps on the last day, and the jump moves every night;
- `mark_flow_read_days`, a public `data_quality_flags` list, grows by one entry per day for ever.

Reproduced end to end, with the real helper feeding the apply as the strategy branch does
(`/tmp/navmtm-r2/deribit_dense.py`). There is no flow at all, and there are six daily marks:

```
flows dict (every NAV day, zeros kept): {'2026-11-01': 0.0, ..., '2026-11-09': 0.0}
rows from 11-03: [('2026-11-08', 0.003599)]
mark_gap_days: ('2026-11-04', '2026-11-05', '2026-11-06', '2026-11-07')
```

The same marks with an empty flows dict give six rows (`/tmp/navmtm-r2/dense_flows.py`). Every
apply-level and derive-level test passes a sparse dict or a mocked `composed_flows` list, so
nothing exercised the real shape.

**Fix (minimal):** test for a flow, not for a key, in both places:

```python
def _read_day_flow(md: date) -> bool:
    return flows.get(md + timedelta(days=1), 0.0) != 0.0

if md != last_mark and _read_day_flow(md):      # :281
...
mark_flow_read_days=tuple(d.isoformat() for d in mark_days if _read_day_flow(d)),  # :320
```

Do not drop zeros in `_iso_day_amounts`. The writer-basis `writer_day_pnl` and the compose read
the same dict. Add an apply test that feeds `native_ledger_composed_flows` output (the repro above
is a ready fixture) and asserts one row per mark day.

**Follow-up to route, not improvise:** Deribit `usdc_reward` is an external flow
(`deribit_txn.py:742-743`). An account that holds USDC and is paid that reward daily would still
have a nonzero flow on most days, and would still lose most of its marks after the minimal fix.
The flows are day-aggregated here, but the raw rows (Deribit transaction log, ccxt transfers, MT5
deals, sFOX rows) all carry instants. Two options need a founder decision: compare the flow
instant with `marked_at`, or skip only when the flow is material against the base. The reward
cadence is UNMEASURED.

### CR-02: A flow dated `S+1` that lands before the first mark's read sits inside the first mark's wallet, so the base carries it and the next return books it again, permanently [HIGH, user-facing, data-integrity, introduced by the CR-01 fix together with WR-02]

**File:** `analytics-service/services/nav_marks_apply.py:259-273` (`wallet = navs[0] - open_pnls[0]`,
`base0 = (wallet - flow_s) / factor`) together with `:280-283` (the skip). A skipped first mark
leaves `level_prev = base0` and `prev_day = S-1`, so the next mark's base is
`base0 + F_S + F_{S+1}`.

**Issue:** mark `S` is read on `S+1`. Under D-11 that can be hours later, and before the operator's
Step B chain move the marks are read at 04:30-05:30Z. A deposit `F` dated `S+1` that lands before
the read is inside `w_S`, so `base0` is overstated by about `F`. WR-02 then skips `S` (it is no
longer the last mark), keeps `base0`, and adds `F_{S+1}` to the next mark's base or numerator a
second time. The next return books about `-F/base`. Marks are immutable, so this repeats on every
derive and can never heal. Before the CR-01 fix, the base was rolled back from the realized
terminal through the flows, so this case was correct.

Reproduced (`/tmp/navmtm-r2/first_mark_read_day_flow.py`): realized level 100,000, open profit 2,000
at `S`, no P&L after, a 50,000 deposit dated `S+1`:

```
deposit AFTER the read:  rows={'2026-11-05': 0.02,  '2026-11-06': 0.0} cum=0.020000
deposit BEFORE the read: rows={'2026-11-05': -0.32, '2026-11-06': 0.0} cum=-0.320000
```

The truth in both cases is one +2% step. A withdrawal before the read publishes a fabricated gain
of the same size. Exposure is one read window per key, and every key's first mark falls on the
night after deploy, while marks may still be read on the old 04:30Z/05:30Z chain.

**Fix (minimal):** anchor the base on the first mark that is used. Before computing `start`, drop
the leading marks that the read-day rule would skip, that is marks with a nonzero flow on their
read day that are not the last mark. Treat the first remaining mark as `S` for `pre`, `base0`,
`marks_since` and `covered_from`. Its wallet has no read-day flow, so it is a clean `L_real(S)`.
The realized rows before it stay as they are (L1). If the first mark is later found to be
ambiguous, the start moves forward by a day, once. Add the test above (flow before the read vs
after the read, same published series).

## Warnings (MEDIUM)

### WR-01: The last-mark exemption publishes a read-day flow as that day's profit or loss, and keeps it for ever when no later mark comes [MEDIUM, user-facing]

**File:** `analytics-service/services/nav_marks_apply.py:281` (`md != last_mark`), docstring rule 10
`:56-64`. The case is permanent for a closed composite window: `job_worker.py:9676-9681` excludes
marks `>= window_end`, so the member's last relevant mark is last for ever.

**Issue:** when the newest mark `d` has a flow dated `d+1` that landed before its read, the apply
publishes `r_d = (M_d - base - F_d)/base`. That return includes `+F/base`, and `F_{d+1}` is held
out. The next derive skips `d` and repairs it. Until then the factsheet, its persisted metrics and
the My Allocation curve carry a fabricated day of unbounded size: a deposit equal to the base
publishes +100%. The day is never repaired in three cases:
- the next marks are refused for a while (a refusal streak, then a trailing series);
- the strategy winds down with partial withdrawals;
- it is a closed composite member whose last in-window mark is `d`.

The derive already knows about the flow, because the flow is in its own dict (`held_out_flow_days`).

**Fix (minimal):** treat a last mark with a nonzero read-day flow like any other ambiguous mark.
It gets no row, the terminal is the last used mark, and flows after that mark are held out. The
series trails by one day, and `marks_trailing_since` already names that. For a closed composite
window, the WR-03 realized tail then covers `d`.

### WR-02: The WR-03 realized tail books the last mark's open profit a second time when the position closes in the tail [MEDIUM, data-integrity; the W2 allocated tail has the same shape]

**File:** `analytics-service/services/job_worker.py:9692-9708` (`_apply_member_marks` tail) and
`:9800-9812` / `:7524-7545` (the W2 allocated tail it mirrors).

**Issue:** the tail rows are realized-basis returns appended after a marked level. The last mark
`M_last = w_last + U_last` has already booked the open profit `U_last`. If the position is closed
during the tail, the realized P&L there contains `U_last` again. Example: member A's last
in-window mark is 11-16 with a +5k open perp (wallet 100k). Marks for 11-17..11-19 are refused,
and the perp is closed flat on 11-18. The tail publishes +5% on 11-18 that the account never
earned. The composite's cumulative return keeps it for ever, because the window is closed. Before
the fix, 0.0-filling those days happened to be exact in this scenario and lost P&L in others.
Neither rule is right in general, because no mark exists at `window_end`.

**Fix:** this is a basis choice for the founder. Route it, as round 1 said for any realized
fallback. If a minimal mechanical fix is wanted now, make the tail purely realized-basis by booking
the reverse of the D-04 step on its first row, `r1' = (1 + r1) * (M_last - U_last) / M_last - 1`.
That needs the last mark's `open_pnl` from `marked`. With that change, a position closed in the
tail nets to zero, and a position still open at `window_end` loses `U_last` (the pre-NAVMTM
convention). Apply the same change to the W2 tail.

### WR-03: A trailing marked series still triggers the hourly ledger re-crawl (carried from round-1 CR-03, not addressed) [MEDIUM, not user-facing]

**File:** `supabase/migrations/20260825120000_ledger_refresh_staleness_view.sql:49-55,249`
(`is_stale` is `last_return_date` older than 4 days), and the fan-out selects on it
(`20260907130000_ledger_refresh_switch_to_system_flags.sql:293,540`).

**Issue:** for a Deribit or sFOX strategy whose marks stop (a refusal streak, or the CR-01 shape
after its fix if the last mark is skipped), `last_return_date` freezes at the last mark. After 4
days the hourly fan-out re-crawls the full ledger every hour. The derive succeeds and changes
nothing, so no failure backoff engages. This wastes venue calls and adds rate-limit pressure
indefinitely.

**Fix:** book it. A minimal option is to exclude from `is_stale` any strategy whose
`data_quality_flags` carries `marks_trailing_since` (the derive is current; the series is not), or
to compare against the latest `compute_jobs` success instead of the series end. This is SQL, so it
needs migration-reviewer and rls-policy-auditor.

### WR-04: SFH F3 judged. The fixer was right not to write refusal tokens into `data_quality_flags`, and the finding stands [MEDIUM, not user-facing; book, no fixer round]

**File:** `analytics-service/services/job_worker.py` (the strategy-mode refusal only reaches
`logger.warning`); D-12 makes `data_quality_flags` the published factsheet surface.

**Judgment:** writing `borrow_present`, `option_value_unverified`, `isolated_margin_unsupported` and
similar tokens into the strategy's public flags would disclose account positioning to every
factsheet viewer. Declining to do that is correct. The gap is operational, not user-facing: a key
refused every day from its first mark never gets marks. It then keeps a current realized-basis
series with no `marks_since`, so nothing published is wrong or stale, but nobody learns which
accounts are permanently excluded. Book it with an owner-only or admin-only sink. Options: the
`compute_jobs` result for the derive, a nullable token plus first-seen day on the owner-only
`api_keys` row, or the post-deploy readout counting tokens over N nights. Do not use the public
flags.

## Info

### IN-01: CR-01 residual. `r_S` still moves between derives, because the realized input is re-rolled from the live anchor [LOW, data-integrity]

**File:** `analytics-service/services/nav_marks_apply.py:265-269`; the ccxt strategy branch passes
no `day_pnl` (`job_worker.py:7458-7462`).

**Issue:** `base0 = (w_S - F_S)/(1 + r_S)` with `r_S = P_S / L(S-1)`. The realized builder
recomputes `L(S-1)` from each derive's live anchor, so an unexplained wallet move after `S` still
moves `r_S`. `/tmp/navmtm-r2/cr02_cr01.py`: `P_S = 1000`, anchor-implied `L(S-1)` 100k vs 125k
gives a marked `r_S` of 0.060500 vs 0.058400. This is second order and far smaller than round-1
CR-01. The unit test holds `r_S` fixed, so it cannot see this.

**Fix:** where `day_pnl` holds `S`, use `base0 = w_S - P_S - F_S` on both roll bases. That form is
exact and anchor-free, and for MT5 it also avoids the DayTiming-cohort return convention. Pass the
combine's own per-day P&L for ccxt.

### IN-02: A first mark with no row loses the D-04 step silently [LOW]

**File:** `analytics-service/services/nav_marks_apply.py:316-318` (`_days_between(start, last_mark)`
excludes `S`).

**Issue:** when `S` has no usable base (a NaN `r_S` without day P&L, a dust `base0`, or a skipped
`S` followed by an unusable base), the open profit at the boundary and day `S`'s P&L are never
booked. `S` is in `covered_days` but not in `mark_gap_days`, so no flag names it.

**Fix:** list `S` in `mark_gap_days` when it is not emitted.

### IN-03: CR-03's user-facing half is covered by the existing freshness surface. The new flag is not rendered, and composites and key mode do not stamp it [LOW]

**File:** `src/app/factsheet/[id]/v2/FactsheetView.tsx:1497-1558` (`resolveSeriesEnd`, series arm),
`src/lib/freshness.ts:123-124` (`SERIES_FRESH_DAYS = 3`, `SERIES_STALE_DAYS = 7`). `grep` finds no
reader of `marks_trailing_since` or `mark_gap_days` under `src/`.

**Judgment (task 3b): not a MEDIUM+ user-facing gap on the factsheet.** The chip and
`SeriesRecencyLine` derive the series end from the published dates. When the series end is older
than the job, the chip names the series end date, and it turns stale after 3 days. A frozen marked
series therefore already says where the figures stop. Two things are missing:
- the reason, which is correct to withhold (see WR-04);
- days 1 to 3, which match normal one-day lag tolerance.

The composite stitch and the key-mode epilogue do not stamp `marks_trailing_since`. The composite
inherits the same chip. The My Allocation freshness surface was not checked.

**Fix:** none required now. If the flag is meant to be read, render it as the cause line under the
existing series-recency sentence.

### IN-04: Derive-level fixtures were moved off the read day, and no test feeds real composed flows [INFO, test reliability]

**File:** `analytics-service/tests/test_nav_marks_compose_roundtrip.py` (`SFOX_MARKS`, `MT5_MARKS`,
`OKX` flows moved), `tests/test_nav_marks_derive_apply.py` (`CCXT_MARKS`/`CCXT_FLOWS` moved
03-08→03-09 and 03-07→03-08), `tests/test_nav_marks_apply.py` (flows moved in four tests).

**Issue:** these edits keep the old assertions green by keeping a flow off every mark's read day.
After them, no derive-level test has a flow on a read day other than the targeted WR-02 tests, and
every Deribit test mocks `composed_flows` as a sparse list. That is how CR-01 and CR-02 shipped green.

**Fix:** with the CR-01 and CR-02 fixes, add one derive-level Deribit test on a real
`NativeLedger` with daily P&L, and one first-mark read-day-flow test per roll basis.
