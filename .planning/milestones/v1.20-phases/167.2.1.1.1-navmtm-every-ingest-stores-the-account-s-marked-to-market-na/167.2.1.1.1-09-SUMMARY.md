# Phase 167.2.1.1.1 Plan 09: NAVMTM composite strategies use their members' marks Summary

**A composite now stitches member series that already carry each member key's stored marks (applied on the member's cash series before it is clipped to its window), counts the days a mark's return covers as neither gaps nor flat days, names where the marks begin, and refuses as a whole by name, persisting nothing, when a member's marks cannot be applied.**

## What was built

In `run_stitch_composite_job` (`analytics-service/services/job_worker.py`), all confined to the member fan-out, the cash-pass call, the coverage/scalar/derive lines and the flag merge:

- **The member seam.** `_apply_member_marks(ctx, seq, returns, build_inputs)` reads the member key's marks (`read_key_marks` through `db_execute`), keeps those dated before the member's window end, and, when any remain, calls `apply_marks` with the member builder's own inputs and records the `MarkedSeries` in `member_marked[seq]`. `build_inputs` is a callable that runs only when there is a mark to apply (a member without marks makes no new call and is byte-identical). `_reconstruct_ccxt_member` and `_reconstruct_deribit` each gained an optional `mark_seq` and call the seam at their end, before returning to `_reconstruct_all`, which clips afterwards.
- **Per-venue inputs (no second venue read).** ccxt: flows summed per `utc_day_iso` from the member's `external_flows`; realized terminal `(returns.index[-1], equity - open_unrealized_usd)` only when the anchor was trustworthy (plan 07's rule), else none and the apply refuses by name. Deribit: `native_ledger_realized_terminal`, `_day_pnl` and `_composed_flows` on the member's own ledger (Pitfall 6 as in plan 07: the first marked step also holds the coin's mark move since the last ledger day).
- **Cash pass only.** `_reconstruct_all(..., apply_member_marks=True)` on the cash call; the mark_to_market and smoothed passes leave it False.
- **The returns-basis selector (D-14, BLOCKER 1).** `_member_returns_are_allocated = venue == "deribit" and denominator_config is not None`, defined per member in `_reconstruct_all`. `_member_mark_seq` is None for such a member, with a comment naming plan 17 and D-14, so it is never read as an exclusion. Every ccxt member, configured composite or not, takes the roll.
- **Coverage and scalars (D-05, D-15).** `_composite_mark_summary(member_marked, _window_by_seq)` reads each member's `covered_days`, `mark_gap_days`, `mark_flow_read_days` and mark days INSIDE that member's half-open window. `coverage_mask(..., covered_days=...)` (`services/stitch_composite.py`, additive, default None byte-identical) removes covered days from `gap_days` only. The cash scalar input is `gap_fill_daily_returns(stitched)` minus the covered days (`_scalar_input_without_covered_days`), and `derive_basis_series` receives `covered_days` (None when no member applied a mark, so the conventions echo is absent).
- **Flags (D-12).** `marks_since` (the earliest in-window mark day of any member), `mark_gap_days` and `mark_flow_read_days` (unions), present-only; each is popped when the stitch lacks it, beside the `headline_since` pop. None is a `NAV_TWR_GUARD_KEYS` member, so none promotes `computation_status` (a test pins `complete`).
- **L3.** `except MarkApplyRefusal` in both member arms, ahead of the degrade and bare-`Exception` arms, returns `_refuse_member_marks`: a fixed user sentence through `_stamp_failed` (token-only detail) and `FAILED permanent` with `run_stitch_composite_job: nav marks refused (seq=<n>, <token>)`. Every persist sits below the fan-out, so nothing but the failed stamp is written, and the member is not appended to `degraded_members`.

## Deviations from Plan

**1. Task 2's code landed in Task 1's commit.** The Deribit member arm, the selector, the three flag pops and the `MarkApplyRefusal` handling all live in the one member seam and the one flag-merge block Task 1 had to write (an unhandled `MarkApplyRefusal` would be classified `unknown` and retried forever, and the flag block could not carry the marks without its pops). So there is no `feat` commit for Task 2, and the Task 2 tests pass at HEAD on their first run. Their ability to fail is shown twice: `red2.log` runs the module against the PLAN_BASE `job_worker.py` and `stitch_composite.py` (12 failed, 3 passed; the 3 are the "unchanged" pins), and the drills above. Same call plans 07 and 16 made.

**2. [Rule 2 - Missing critical functionality] Marks dated on or after a member's closed window end are not applied.** Not in the plan text. Such a mark can change nothing the window shows (the apply emits rows only on mark days from the first mark on, so every output row it adds is dated at or after the window end and is clipped away), yet applying it could refuse the whole composite (a nonpositive base, an untrustworthy terminal) for a member whose window closed long ago. Pinned by `test_marks_dated_after_a_closed_window_are_not_applied` and drill D-MW. A member with no relevant mark makes no new call.

**3. D-C1 bites on a dedicated test, not the tracer.** The plan said to choose a fixture where a clip-first order is RED if the tracer's window does not cut the base day. It does not (the tracer's window opens before the realized history), so `test_marks_apply_before_the_window_clip` uses a window that opens on the first mark day. The tracer test stays green under D-C1; the dedicated test is the one that goes RED.

**4. The refusal stamps a failed row.** The plan says the refusal writes "no csv row, no headline and no flags". Every other permanent return in this job stamps a terminal `failed` row so the wizard poller reaches a gate, and plan 07's strategy-mode refusal does the same, so this one calls `_stamp_failed` with a fixed sentence and a token-only detail. The stamp merges the composite markers over the existing flags (the M-2 read-modify-write); it carries no marks field, no headline and no series. `wrote_anything_but_a_failed_stamp` in the test asserts exactly that.

**5. The DQ-02 flow-coverage terminus is held off in the new tests.** It reads the wall clock against the venue's deposit retention and, with a flow in the fixture, truncated the member to nothing (a degrade, `insufficient_history`). The harness patches `services.nav_twr.flow_coverage_terminus_day` to return None so the module does not depend on today's date. The terminus is not what this plan pins.

**6. Branch.** Committed on `feat/167.2.1.1.1-p09` as the orchestrator assigned (the plan text names `feat/167.2.1.1.1-navmtm`); it is not in the `agent-*` namespace the pre-commit allow-list expects, it is not protected, and no `<sequential_execution>` block was given (same call as plans 03, 06, 07, 13, 16).

## Known limits (recorded, not fixed)

- **The browser recompute still zero-fills a composite's covered days.** `src/app/factsheet/[id]/v2/basis-context.tsx` sets `calendarDense` for a composite, and `metricsBasisSeries` in `src/lib/factsheet/compute.ts` then zero-fills every absent calendar day before ann_vol, sharpe and sortino. A covered day (e.g. 03-08 in the tests) would be counted as a flat 0.0 observation there, while the server headline (this plan) drops it (D-15). TypeScript is outside this plan's files; the owner of the factsheet read path should decide whether the stored `covered_day_count` / `marks_since` / `mark_gap_days` are enough to exclude the days there. Worth booking.
- **The mark_to_market and smoothed composite bases keep their realized basis**, so a mixed composite's smoothed series carries an unmarked ccxt leg while its cash series carries a marked one. By decision, as in plan 07.
- **The allocated Deribit member of a configured composite is not marked yet.** It is plan 17 (wave 8, same PR) and the selector `_member_returns_are_allocated` is where it hangs; until then such a composite has ccxt members marked and its Deribit member as today.
- **A stored mark dated before a member's window start still shapes the chain.** The return stamped on the first in-window mark day may span days before the window (one observation of the composite, D-15). Not a defect; stated so a reader of `mark_gap_days` is not surprised.
- **A realized row after a member's last mark is dropped** (Pitfall 7 as in plan 07), so a current member's series ends on its latest mark until the next mark lands.
- **Flows are day-granular** (plan 03, OQ-8); `mark_flow_read_days` names the mark days where a flow dated the next day may be inside the read.
