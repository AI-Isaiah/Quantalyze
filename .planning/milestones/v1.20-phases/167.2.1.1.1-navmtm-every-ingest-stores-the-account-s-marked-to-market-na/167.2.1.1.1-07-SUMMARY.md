# Phase 167.2.1.1.1 Plan 07: NAVMTM strategy-mode derive applies the stored marks Summary

**A strategy's derive now reads its key's stored marked NAVs and persists `apply_marks`' output instead of the realized series, from the first mark day on, for every NAV-path venue, configured or not; it stamps where marks begin and which days they skipped, and refuses by name, writing nothing, when it cannot reproduce a mark.**

## What was built

`run_derive_broker_dailies_job` (`analytics-service/services/job_worker.py`), one seam placed after the DQ-02 terminus and the R2-WR-02 realized terminal and textually above `_run_key_mode_compose_epilogue`'s definition, the `<2` short-circuit, the MT5-12 verdict seam and every csv write:

- `_returns_are_allocated = venue == "deribit" and denominator_config is not None`, defined once beside the seam with a comment that it mirrors the selector `combine_native_ledger` uses and that every other strategy returns NAV changes. The roll runs when `not is_key_mode and not _returns_are_allocated`. For an allocated strategy it does nothing here and a comment names plan 16 and D-14, so the branch is not an exclusion.
- It reads `read_key_marks` through `db_execute`; with none stored nothing else runs (byte-identical path). Otherwise it builds `AppliedMark`s in the series' own unit (`_marks_in_series_unit`: `nav_usd` for a USD series, `nav_native` only from a mark stored in the same native unit for a BTC series, else `mark_unit_mismatch`), builds the builder's own inputs per venue, calls `apply_marks`, replaces `returns` with its output and logs `nav marks applied (marks=%d since=%s gaps=%d mode=strategy id=%s)`, counts and dates only.
- The prestamp gains `marks_since`, `marks_covered_from`, and when non-empty `mark_gap_days` and `mark_flow_read_days`, present-only with a comment in the existing annotation voice. The cash_settlement `derive_basis_series` call passes `covered_days` when marks applied (`None` otherwise, byte-invisible).
- The existing span reconcile does the Pitfall 7 deletion unchanged (the span is the output's `[min, max]`); no second delete was added.

## Per venue: what feeds `apply_marks` in strategy mode

All are computed at the seam from data the derive already holds. No venue call.

| Venue | Realized terminal (day = last return day) | Flows by day | Day P&L |
|---|---|---|---|
| OKX | `equity - open_unrealized_usd` (the real wedge) | `external_flows` summed per `utc_day_iso` | none |
| Bybit, Binance | same expression; the wedge is 0.0, so the USDT wallet figure | same | none |
| MT5 USD | same expression; `open_unrealized_usd = equity - balance`, so the BALANCE | `_mt5_flow_by_day` (account unit) | `mt5_day_pnl(deals, offset)` |
| MT5 BTC | same, in BTC; dust test uses the unit's own floor (1e-7 BTC), not the USD one | `_mt5_flow_by_day` in BTC | `mt5_day_pnl` in BTC |
| Deribit (NAV path) | `native_ledger_realized_terminal(native_ledger, indexable)`; its own day | `native_ledger_composed_flows` | `native_ledger_day_pnl` |
| sFOX | same expression; no wedge, so the last observed `usd_value` | `_flows_series` | none |

Deribit's three calls were key-mode-only; strategy mode now makes them only when stored marks exist (a derive without marks makes no new call). The terminal is `None` when the anchor was untrustworthy (balance error, missing, dust, non-finite wedge) and the apply then refuses by name.

**Deribit caveat (Pitfall 6).** Its realized terminal is the native balance at the mark of the LAST LEDGER DAY, while a mark is today's collapsed equity, so the first marked day's step also contains the coin's mark move since that ledger day. That is real marked-to-market profit and it is booked as the day's return, not an error. `run_deribit` in the test module says so beside the scenario.

## Known limits (recorded, not fixed)

- **A realized row dated after the LAST mark survives.** The span reconcile deletes only inside `[min, max]` of the output, which ends at the last mark day. Measured in a scratch test: with one mark on 03-06 and a stale row on 03-07, the 03-07 row stays. In steady state no derive writes such a row. It can exist once, on the deploy day, when an earlier realized derive wrote today's partial row; the next day's derive covers that day with a mark row and replaces it. For up to a day the series the runner loads can carry that one realized-basis row. The plan said not to add a second delete, so none was added; a delete bounded to `date > last mark day` in marks mode would close it.
- **A derive whose own equity read was unusable refuses, it does not retry.** Measured: dust equity with a stored mark gives FAILED permanent `mark_base_unrollable`, because there is no realized terminal to roll from. Before this plan the same read published a heuristic series. This follows the plan's L3 (refuse by name, write nothing); a transient balance read error is treated the same as a permanent one, and the next sync's derive supersedes the failed row. Worth a founder look.
- Key mode is untouched (plan 12). An allocated-capital Deribit strategy is untouched (plan 16) and is stamped with no marks fields. The Deribit mark-to-market second pass (`mtm_returns`) keeps its realized basis.
- Flows are day-granular, so a deposit inside a gap is weighted as present for the whole gap (plan 03, OQ-8). The gap days are named by `mark_gap_days`.
