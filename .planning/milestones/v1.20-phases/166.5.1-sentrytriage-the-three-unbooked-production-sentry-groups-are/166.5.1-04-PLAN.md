<objective>
Move the four pure reads Sentry named onto the read-retry helper, as D-02a decides. Then record the
SC-2 classification for all six ReadTimeout groups and hand SC-4 to the orchestrator.

**The decision, quoted from 166.5.1-CONTEXT.md (D-02a, founder 2026-10-21):** "move the four pure
reads Sentry named onto the helper. Top in-app frames read from Sentry 2026-10-21:
- 2E `services/job_worker.py` `report_orphaned_capped_reconstructs` → its `_sel` read (via
  `db_execute`);
- 2F `routers/match.py` `_should_skip_allocator` → the latest `match_batches` read
  (`.eq("allocator_id", …).order("computed_at", desc=True).limit(1)`);
- 2D `routers/match.py` `_load_allocator_context` → the `allocator_preferences` `.maybe_single()` read;
- 2G `services/allocator_positions.py` `read_native_unpriced_days` → its marker read (called from
  `match._load_holding_portfolio_context`).
No retry is added to any other write."

Purpose: SC-2 for QUANTALYZE-2D, 2E, 2F and 2G, and SC-4's handoff.
Output: four retried reads with RED-first tests, a synchronous twin of the helper, a six-row
classification table, and the D-04 readout steps.

**Granularity: the failing read only, never the whole function (planner's choice).** 2D and 2G sit
inside synchronous functions that run in a worker thread:
- `_load_allocator_context` is called through `asyncio.to_thread` from `_score_one_allocator`, at the
  `ctx = await asyncio.to_thread(_load_allocator_context, allocator_id)` line in routers/match.py, and
  from the rescore handler in services/job_worker.py (the same call shape). It issues a dozen or more
  reads, and through `_load_holding_portfolio_context` it reaches the 2G read.
- `read_native_unpriced_days` is also called by the daily refresh in services/equity_reconstruction.py,
  through `db_execute`.

Wrapping a whole call would re-run every read on a retry and add a retry to reads Sentry did not
name. The async `db_read_with_retry` cannot be awaited inside a function running in a worker thread.
So Task 1 adds a synchronous twin, `db_read_with_retry_sync`: same predicate, same constants,
`time.sleep` backoff. Both 2D and 2G wrap only their own single select with it. Every caller of the
two functions, including job_worker's and equity_reconstruction's, gets the retry with no call-site
change.

**Worst case (measured in plan 03).** The client's read timeout is 120 s per attempt, so one retried
read can now take about 6 minutes (3 x 120 s plus about 4 s of backoff), where it took 120 s before.
- For 2E, `watchdog_loop` runs this read right after `watchdog_tick`'s retried reset, so one watchdog
  iteration can take up to about 12 minutes before its sleep.
- For 2D, 2F and 2G, the cron request (or the rescore job) holds that long on one allocator.
This is a recorded consequence of D-02a, not a new decision.
</objective>
