<objective>
The storage half of D-02: the tables that let a Bybit trade read keep what it has read between claims, so a book of any
size eventually completes. Nothing writes to them until plan 07 deploys.

D-02 verbatim from CONTEXT: "Founder 2026-10-27, AskUserQuestion: 'Resumable across runs' (chosen over the recommended
single time budget with stall-splitting). The read position and what has been read are kept between runs so a book of
any size eventually completes; each run reads within the existing crawl bound and defers (`defer_compute_job`) instead of
refusing. Nothing is written to the allocator's history until the read is complete (ACCTREBUILD D-02). Persisted trade
data needs a migration with owner/service-role RLS and an expiry, migration-reviewer and rls-policy-auditor clean before
merge (PROD auto-applies after TEST), and a catalogue-only verify block."

Decisions recorded by this plan (Claude's discretion inside D-02; each gets one header line in the migration):
- TR-1 What is persisted: raw compact trades of each COMPLETE 7-day window (RESEARCH section 1), positional arrays
  `[timestamp_ms, symbol, side, amount, price, cost, fee_cost]` in read order, chunked at 5,000 trades per row so no
  single request carries more than about 300 KB (RESEARCH Pitfall 7 / A4: the gateway body limit is unmeasured, so the
  design never depends on it). A chunk count makes a half-written window detectable.
- TR-2 Service-role only (orchestrator decision 3, above).
- TR-3 Expiry: an `expires_at` column on both tables (7 days, written by the worker) plus the worker's purges: at claim
  start, on a successful rebuild (plan 07) and an hourly sweep from the worker's watchdog loop (plan 08), which is what
  removes an idle key's expired rows. No database-scheduled job (no pg_cron).
- TR-4 Venue-agnostic names (`allocator_trade_read*`, `window_*_ms`, a `venue` column with a CHECK to widen), so Phase 173
  can adopt the store for OKX without a redesign; only 'bybit' is admitted now.
- TR-5 `read_version` on both tables: a stored window is reused only by the same read version (plan 04).
- TR-6 `last_job_id` (no foreign key; an opaque marker) lets a NEW job start with a fresh stalled-claims count while
  reusing the stored windows, which is what makes the stall refusal "a reason a later run can clear" (plan 04).
- TR-7 The rollback renames the tables aside and keeps the rows (founder rule: keep data unless told otherwise). The rows
  are transient, so a plain removal would also be defensible; it is not chosen without the founder.

Purpose: SC-1 (the resumable half). Output: the migration, its manual rollback, the 8-arm SQL gate.
