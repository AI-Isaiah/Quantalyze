<objective>
Fix D-04 and D-05 here, as the founder decided on 2026-10-07. A failed `stitch_composite` must stop
re-stamping `strategy_analytics.computed_at`, and so must a job start: the column moves only on a
successful write (D-05). Python never writes that column on a failure; the SQL
status bridge does, in branch (b) (`computed_at = now()`), called from `mark_compute_job_failed`.
PROD shows the signature (the row's `computed_at` equals the failed job's `updated_at`). The fix is
a narrow table trigger, following the repo's two `strategy_analytics` BEFORE UPDATE coercion
triggers, so the bridge function STATUSBRIDGE is editing stays untouched and the 31 RED-UNDER-M
twins that edit the bridge's migration stay valid.

Purpose: analytics freshness is read from `computed_at` (CLAUDE.md). A failed run that stamps it
makes a stale row look current on the FreshnessChip and the PDF vintage.
Plan 06 adds `computation_status` to the factsheet cache key in the same PR. Without it, the
widened hold would let the cache serve a complete payload for a computing or failed row.
Output: migration, rollback, annotated gate seen RED per arm, a reader re-verification with
evidence, a Python guard, censuses and floors moved by measurement.
</objective>
