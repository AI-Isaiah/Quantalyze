# Phase 166.3.1 Plan 06: NAVBREACH, the factsheet cache key gains computation_status Summary

The public factsheet `unstable_cache` key is now `["factsheet-v2-payload-v12", id, computed_at, computation_status]`, read from the same signature probe as `computed_at`, so a status change under a held `computed_at` can no longer be served an entry built for the old status.

(`commits: 4` was measured at write time, before this SUMMARY's own commit.)

## What changed

- `page.tsx`: both signature probes (Lane A, Lane B owner probe) select `strategy_analytics ( computed_at, computation_status )`. `computationStatus = signAnalytics?.computation_status ?? "none"` sits beside `computedAt`; `buildFactsheetPayloadCached(id, computedAt, computationStatus)` carries it as the fourth keyPart. The WR-02 comment block now says the key moves on every status change and on every successful compute, and that since D-05 `computed_at` alone no longer moves at job start or on failure (cites the plan 02 trigger). Viewer-independence corollary kept.
- `unstable_cache` reference (bundled Next, `node_modules/next/dist/docs/.../unstable_cache.md` and `next/dist/server/web/spec-extension/unstable-cache.js`): the key is `${cb.toString()}-${keyParts.join(',')}` plus `JSON.stringify(args)`. `join` renders `undefined` as an empty string, so the sentinel `"none"` is chosen by the caller. The cache API and options are untouched.
- Tests, censuses and comments as listed in the files above.

## Open item for the orchestrator (not a plan failure)

The analytics runner's own terminal write (`analytics_runner.py` `_mark_complete` / `_mark_computing`) names no `computed_at`. After plan 02's trigger, the sequence for a recompute is `complete(t0)` -> `computing(t0, held)` -> runner writes `complete` or `complete_with_warnings` (still t0) -> bridge branch (c) at `mark_compute_job_done` stamps t1. During the gap between the runner's write and the bridge's stamp, the row reads `complete` at the OLD `computed_at`, so the factsheet key and the PDF ETag equal the pre-recompute ones; a cached pre-recompute payload can be served for that gap (seconds, longer when sibling jobs keep branch (a) in flight, but then the status reads `computing` and the new keyPart withholds). Before D-05 the job-start stamp had already moved the key off t0, so this window is new with D-05. It is exactly plan 02's booked residue (iii) ("166.5's runner stamp must land on the success write"); adding the status to the PDF ETag would not close it (complete to complete is the same status). Recommend 166.5 COMPUTEDATSTAMP carry it with this evidence.

Also noticed, out of this plan's files: `src/lib/queries.ts:464,588` and the `StrategyTable.*.test.tsx` / `queries.stale-analytics-detail.test.ts` comments still say the bridge re-stamps `computed_at = now()` on the `computing` and `failed` branches. They are false once plan 02's trigger lands; plan 02 or 07 owns the staleness-reader re-verification.
