## Design decisions (technical; recorded so the checker and the founder can see them)

- **T-KL1-UNIT: the days ride the unit (`StrategyForBuilder.undefined_return_days`), not `ScenarioState`; this differs from the first sketch (an optional per-key set in `ScenarioState`) on purpose.** `ScenarioState` is rebuilt from parts at five places on the live-book paths (`mergeAddedIntoPerKeySet`, `computeMetricsForDraft`'s `projectionState`, the composer's `projectionState`, the solver's `sleeveStateAt`, the SSR baseline's own state), and a state field not forwarded at one of them would silently read the day as 0 again on that panel, the exact disagreement D-07 removes. `strategies` passes through every one of those sites unchanged. And `ScenarioState` holds the allocator's choices (selection, weights, start dates, leverage, window), while which days a key has no return is a fact about the key's series, so it belongs with `daily_returns`. The two per-key builders are the only places that set it.
- **T-KL1-AXIS: a named day is not on the unit's axis.** Building the date axis without each unit's named days means every axis day has at least one unit with a return on it, so a named day can never leave an axis day whose weight sum it emptied and which the existing `activeWeightSum > 0 ? ... : 0` guard would write as 0. (A day whose only defined units carry weight 0 behaves as today; this plan does not touch weights.) That mirrors the compose ("a day where no key is defined is absent from `returns`"). A stale row on a named day is treated as named.
- **T-KL1-CORR: one correlation day set for every pair (the axis days no unit names), chosen over per-pair deletion on purpose.** The diversification panel (DR, ENB, PCR) builds ONE covariance matrix from aligned series and one sigma per constituent, and its consistency pin requires the rho rebuilt from that matrix to equal the engine's `correlation_matrix` to 3 dp. With per-pair day sets the two could not agree and the matrix could lose positive semi-definiteness. The cost: on a named day every pair loses that day, not only the named key's pairs. Only named days are affected. This plan sets the engine's day set; plan 10 aligns the diversification panel on the same set.
- **T-KL1-SCOPE: every per-key unit carries its days, the live book and saved drafts with per-key members alike.** A saved draft that blends the same keys at other weights must read the same series the live-book column beside it reads, or the compare panel shows two semantics of one key on one screen. The Risk tab is not a `computeScenario` reader: `book-risk-input.ts` uses the stored book for `compositeReturns`, and `CorrelationMatrix.alignedPair` and `RiskDecomposition`'s covariance align on dates both series report, so a left-out day is already skipped there. The public share page (`share-resolve.ts`) and `computeCompositeCurve` build no per-key units. None of them changes.
- **KL-4 (carried limit):** see the must_haves. A failed read or malformed list leaves that key on today's arithmetic, and the existing warning and Sentry capture name the failure.
- **KL-5 (carried limit, recorded, not changed):** strategy legs (a composer-added strategy, a shared scenario's published series in `share-resolve.ts`) carry no `undefined_return_days`, so the engine still 0-fills a day their stored series lacks, as it does today for any absent day. D-07 covers the per-key units of the allocator's own book; a strategy's stored series is not a per-key unit and has no `key_inputs` row to read the days from. See the must_haves.
