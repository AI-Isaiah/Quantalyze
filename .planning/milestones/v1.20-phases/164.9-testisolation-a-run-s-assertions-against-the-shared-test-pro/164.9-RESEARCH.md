## Summary

This phase has almost no "learn a new technology" surface — it is entirely a set of targeted
fixes to this repo's own CI workflows (`ci.yml`, `supabase-migrate.yml`), two bash scripts
(`scripts/test-ledger-drift-check.sh`, `scripts/restore-test-from-baseline.sh`), and the
`supabase/tests/*.sql` gate corpus. The research therefore consisted of reading those files
directly rather than consulting external documentation.

The single most consequential finding: **most of `supabase/tests/*.sql` (≈71 of 75 files) is
already isolated by construction** — each gate wraps its writes in a per-part `BEGIN…ROLLBACK`
and scopes every assertion to `gen_random_uuid()`-generated fixture ids in its own `WHERE`
clause, so a foreign row cannot touch it. **The true global-assertion offenders are a small,
named set**: `test_strategy_analytics_stuck_computing_reaper.sql`, `test_prod_prober_cadence.sql`,
`test_retention_orphaned_running.sql`, `test_reconcile_dropped_enqueue_sweep.sql` (all four
`EXECUTE` the real deployed cron body's `ORDER BY … LIMIT` sweep by design — the file's own
"oracle discipline" forbids re-implementing the predicate), plus VAC-08's ledger-row-count read,
the e2e-seeded fixed-id demo dataset, the extension-count restore guard, and the
`system_settings.analytics_service_url` row. **None of these need a new schema column.** The
cron-body sweeps already use a staleness-seeding discipline to dominate their `ORDER BY`/`LIMIT`
budget; what is missing is the CALIBRATION criterion 2 demands (prove it survives a foreign
row), not a new discriminator mechanism.

Second finding, with direct evidence: **the credentialed-test lane question is measurably
harder than "local-stack vs. shared TEST."** I confirmed by reading `supabase/schema/baseline.sql`
directly that at least two of the five reported failure signatures are **not TEST-only drift** —
they are present in the baseline every lane (including local-stack) would boot from: the
`claim_compute_jobs_with_priority` 2-arg/5-arg overload ambiguity exists in baseline.sql itself
(`:1534`/`:1625`), and `config.toml`'s `[api] schemas = ["public", "graphql_public"]` excludes
`cron` from every PostgREST-fronted lane, local-stack included. A third failure (`key_hash` on
`api_keys`) is not TEST drift at all — it is a stale test fixture referencing a column that has
never existed in this schema's history (real column: `api_key_encrypted`). Moving the lane to
local-stack does not make these three pass; it only removes the fourth-and-fifth class (genuine
shared-TEST ledger/permission drift) from the picture. This materially changes the shape of
criterion 13's work: part of it is "pick a lane," but part of it is "fix or retire specific
broken fixtures," and conflating the two would waste a plan wave.

Third finding: the advisory-key race (Q3) cannot be fixed by workflow-internal ordering alone.
`sql-tests`/`python`/`e2e-seeded` live in `ci.yml`; `apply-test` lives in `supabase-migrate.yml`.
These are separate workflow files triggered independently by the same push event — GitHub Actions
has no native `needs:` edge across workflow files. "Distinct keys plus explicit ordering" (locked)
therefore requires either a cross-workflow polling wait (same shape as the existing mutex-wait
loop, but polling the OTHER workflow's run conclusion via the GitHub API) or restructuring
`apply-test` into a reusable/called workflow so `ci.yml`'s DB jobs can `needs:` it directly. Both
are real options; neither is free. This is flagged loudly for the planner rather than decided here.

**Primary recommendation:** treat this phase as four largely-independent repair kits sharing one
root cause (global assertions on a project this repo does not exclusively own), not as one
mechanism. Do not build a single "discriminator library" — the four kits (SQL-gate calibration,
advisory-key restructuring, credentialed-test lane + fixture repair, restore-workflow gate
hardening) have different shapes and different blast radii, and the locked ordering (backlog
entries first, criteria 3+4 as one unit) already reflects that.

## Key Findings by Research Question

### Q1 — The concrete per-run discriminator, and where it is threaded

`[VERIFIED: supabase/tests/*.sql, read this session]` **Most of the 75-file corpus needs no new
discriminator.** A representative sample (`test_api_key_delete_atomicity.sql`,
`test_capital_ownership_allocation_guard.sql`, `test_cleanup_orphaned_api_keys_sweep.sql`, and
~40 others) scopes every `count(*)` assertion with a `WHERE id = <locally generated uuid>` or
`WHERE user_id = <locally created test user>` clause, and wraps writes in a per-part
`BEGIN;`/`ROLLBACK;` (documented explicitly in
`test_strategy_analytics_stuck_computing_reaper.sql:59-68`, quoted below). A foreign row cannot
appear in a `WHERE id = <this run's own generated uuid>` filter. **No schema change is needed for
this majority.**

`[VERIFIED: .github/workflows/ci.yml:2790-2803]` The `sql-tests` job's own header comment names
the genuine exception directly:
> "`test_strategy_analytics_stuck_computing_reaper.sql` `EXECUTE`s the REAL deployed cron body —
> a GLOBAL `ORDER BY computing_started_at ASC LIMIT 25` over strategy_analytics that cannot be
> scoped to a caller."

`[VERIFIED: supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql:30-42]` The file's
own "ORACLE DISCIPLINE" section states why the predicate can never be parameterized by a run id
without a production migration:
> "The behavioral parts read the REAL deployed body out of cron.job.command and `EXECUTE
> v_command` it. They NEVER re-type the predicate. A gate that re-implements the predicate passes
> when the DEPLOYED predicate is wrong."

Grepping the corpus for the same shape (`ORDER BY … LIMIT` combined with `FOR UPDATE SKIP LOCKED`)
found exactly **four** files carrying it: `[VERIFIED: grep over supabase/tests/*.sql, this
session]` `test_strategy_analytics_stuck_computing_reaper.sql`, `test_prod_prober_cadence.sql`,
`test_retention_orphaned_running.sql`, `test_reconcile_dropped_enqueue_sweep.sql`. Of these,
`test_prod_prober_cadence.sql` is a false positive for this concern — it asserts about the cron
*schedule itself* (a global singleton, not multi-tenant data), so per-run isolation is a category
error there; it stays global by design.

For the remaining three (reaper, retention-orphaned-running, reconcile-dropped-enqueue-sweep),
the existing mitigation is already a **seeding discipline**, not a discriminator column: seed this
run's rows with an extreme `computing_started_at`/equivalent timestamp so they sort first (or
last) in the deployed `ORDER BY … LIMIT N` and dominate the budget regardless of foreign
candidates. `[VERIFIED: supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql:509,
692]` comments confirm this is the intended mechanism ("the deployed `ORDER BY
computing_started_at ASC LIMIT 25` budget" / "the 25 OLDEST seeds are exactly the ones a
[foreign row could crowd out]"). **What is missing is proof, not mechanism**: nothing in the repo
today seeds a competing foreign row and shows the assertion survives. That proof is exactly
criterion 2's calibration and is the concrete, bounded task for these three files.

`[VERIFIED: scripts/seed-demo-data.ts:746-751]` The e2e-seeded demo fixture set uses **fixed,
deterministic** ids and emails (`demo-cold@example.com`, `ALLOCATOR_COLD`, etc.) — quoted
verbatim: `{ id: ALLOCATOR_COLD, email: "demo-cold@example.com" }`. This is a shared, idempotent,
cross-run fixture set by design, not per-run data — "isolation" in the criterion-2 sense does not
apply to it; the live concern is the separate "which rows may a run assume exist" CONTRACT
question (see Open Questions — `[164.8-TEST-DATA-RESEEDED]`'s inclusion in this phase's scope is
ambiguous and flagged there).

`[VERIFIED: src/__tests__/claim-dedupe-done-pending-children-guard.test.ts:304 and 46 similar
files]` The TS/vitest live-DB layer already has an informal per-test discriminator: emails/ids
suffixed with `Date.now()` (e.g. `` `c39-dpc-guard-${ts}@test.sec` ``), via
`createTestUser`/`cleanupLiveDbRow` in `src/lib/test-helpers/live-db.ts`. This is timestamp-unique,
not collision-proof against parallel same-millisecond runs, but it is the existing convention and
a real signal that the vitest layer already leans toward per-run scoping without a schema change.

**Verdict for Q1: no migration is needed for the discriminator mechanism itself.** The work is
(a) proving the existing seeding discipline in the four cron-body-sweep files survives a foreign
row, (b) VAC-08's ledger read is not a "whose rows" problem at all — it's an ordering problem,
folded into Q3, and (c) the e2e fixed-fixture set is a separate contract question, not this
criterion's discriminator work.

### Q3 — The advisory-key fix (7 + 27 sites, distinct-keys-plus-ordering)

`[VERIFIED: grep -c "61616158" .github/workflows/ci.yml → 27; .github/workflows/supabase-migrate.yml → 7, this session]`
Both counts match the ROADMAP's re-measured figures, correcting CLAUDE.md's stale "26" for
`ci.yml`. Grouped by job (each job repeats the same acquire/wait/timeout/reap template):

| Workflow | Job | Occurrences | What it protects |
|---|---|---|---|
| `ci.yml` | `sql-tests` | 10 (comments + acquire/wait/census/timeout/reap) | Reads `supabase/tests/*.sql` incl. VAC-08's ledger reconciliation |
| `ci.yml` | `python` | 9 | pytest live-DB integration suite |
| `ci.yml` | `e2e-seeded` | 8 | Playwright specs against the fixed demo fixture set |
| `supabase-migrate.yml` | `apply-test` | 7 | `supabase db push --include-all` — the ONLY one of the four that WRITES the schema |

`[VERIFIED: .github/workflows/ci.yml:2790-2870, comment block]` This job's own comments already
document that the ONLY correctness requirement the mutex provides is mutual exclusion — never
ORDER: *"When `sql-tests` wins, it measures a TEST the merge has not yet applied to; when it
loses, it queues."* The mutex conflates two distinct needs today: (a) prevent concurrent writers
from corrupting each other's reads (genuinely needs a shared lock across all four), and (b)
guarantee `apply-test` finishes before `sql-tests`/`python`/`e2e-seeded` read the post-merge state
(needs *ordering*, which a shared lock cannot provide — whichever job happens to acquire first
wins, and that's arbitrary).

**Grouping by what each job protects, for the "distinct keys" half of the locked fix shape:**
- `apply-test` is the sole WRITER (DDL/schema mutation) — it should hold its OWN key, exclusive
  against everything else that touches TEST's schema.
- `sql-tests`, `python`, `e2e-seeded` are readers/temp-writers that must still serialize against
  each other AND against `apply-test`, but do not need to serialize against each other for the
  SAME reason `apply-test` needs isolation (they don't mutate schema). Whether they can be
  further split from each other is a separate, smaller question the planner should treat as
  optional (the current single shared key across the three has not caused a documented defect
  beyond the ones already booked here).

**For the "explicit ordering" half — three real options, with genuine tradeoffs (none pre-selected here):**
1. **Cross-workflow polling wait** (same pattern the existing mutex-acquire loop already uses,
   `.github/workflows/ci.yml:3036-3072`, but polling the GitHub Actions REST API for
   `apply-test`'s conclusion on the same `head_sha` instead of polling `pg_advisory_lock`). Keeps
   the two workflow files separate; adds a bounded wait step with its own timeout and failure
   mode, mirroring the existing "queue depth vs. wedged holder" ambiguity the runbook already
   documents for the DB mutex.
2. **`workflow_run` trigger** — restructure so `ci.yml`'s DB-touching jobs (or a new workflow)
   fire only `on: workflow_run: { workflows: ["Supabase Migrate"], types: [completed] }`. Cleaner
   semantically but changes when `ci.yml`'s other (non-DB) jobs run relative to the DB ones,
   which today share one `push` trigger — this is a bigger restructure with wider blast radius.
3. **Pull `apply-test` into a `workflow_call` reusable workflow** invoked as a job FROM `ci.yml`
   itself, giving native `needs:` ordering with no lock-based coordination at all for the ordering
   half (the exclusivity half would still need its own key, now trivially satisfied by same-run
   `needs:`). This is the architecturally cleanest option but the largest structural change —
   `supabase-migrate.yml`'s PROD job (the security-reviewed, environment-gated, human-approved
   half) would need to stay untouched while only `apply-test` moves.

I did not choose among these — the locked decision says "distinct keys plus explicit ordering,"
not which ordering mechanism, and CONTEXT explicitly reserves the "concrete discriminator
mechanism... and where it is threaded" to Claude's Discretion at plan time. `[ASSUMED: none of the
three is obviously ruled out by anything I found; each is a genuine, workable GitHub Actions
pattern]` — flagging this as the single largest architectural decision this phase's plan must
make explicitly, with its own written rationale (CONTEXT requires: "any plan touching
[supabase-migrate.yml] states in writing which of the two it is doing" — the same discipline
should extend to naming which ordering mechanism was chosen and why).

### Q5 — The dead-holder verdict

`[VERIFIED: .github/workflows/ci.yml:3855-3885 and the two duplicate blocks at 4429-4458,
5479-5508]` The release step is explicitly designed to NEVER fail the job, by its own comment:
> "Annotation only: this step is `if: always()` and must never redden a job whose real work
> passed, and `echo ::error::` does not change the exit status. Job teardown remains the
> guaranteed release path."

`echo "::error::mutex holder pid ${holder} died BEFORE this release step…"` (line 3884) is a
GitHub Actions log annotation only — it colors the log line red in the UI but does not set the
step's (or job's) exit code. This is the exact, precisely-located root cause of
`[164.9-MUTEX-HOLDER-DIED-UNSERIALIZED]`: the detection already exists and already fires
correctly; only the CONSEQUENCE is missing.

**The fix cannot simply make this step exit 1**, because the step's own stated purpose (best-effort
release, must never fail a job whose real work passed) is a real, separate design constraint —
release itself being flaky (e.g., a transient network hiccup on the release attempt) must not
fail a job. The dead-holder condition is a DIFFERENT signal (retroactive doubt about the job's
OWN earlier assertions, not a release-step incidental failure) and deserves its own gate. Pattern:
write a marker (e.g. a file in `${RUNNER_TEMP}`) when the dead-holder branch is taken, and add a
NEW subsequent step (also `if: always()`, so it always evaluates) whose ONLY job is to check that
marker and `exit 1` if present — separating "best-effort cleanup, never fails" from "verdict about
this run's trustworthiness, fails on purpose." This keeps the existing best-effort release
behavior completely intact while making the dead-holder condition a real, job-reddening verdict.

**Falsification path, honoring the DATABASE SAFETY constraint:** the mutex acquire/release SQL
(`pg_advisory_lock`/`pg_terminate_backend` on a session key) is generic Postgres behavior, not
dependent on being the actual hosted shared-TEST project. `scripts/pg-lane/run.sh` (the disposable
throwaway cluster, already the designated home for this kind of calibration per CONTEXT.md) can
host the SAME acquire/release script logic against a local, disposable Postgres instance — kill
the "holder" process mid-job on the pg-lane, observe the new verdict step correctly exit 1, then
restore the holder and observe GREEN. This satisfies "proven by killing the holder mid-job on the
throwaway lane and observing RED" without ever touching shared TEST or requiring any of the
forbidden database commands against a real project.

## Common Pitfalls

### Pitfall 1: Treating "shared-TEST schema drift" as the sole cause of the credentialed-test failures
**What goes wrong:** Assuming all 38 failing files/280→94-skip-delta tests will pass once pointed
at a fresher/more-isolated TEST (or at local-stack).
**Why it happens:** The ROADMAP criterion's own wording ("failure signatures are shared-TEST
schema DRIFT, not logic") primes the reader toward an environment-only diagnosis.
**How to avoid:** This research directly falsified that framing for 2 of 5 named signatures
(overload ambiguity exists in baseline.sql itself; `cron` schema is unexposed by `config.toml`
everywhere) and for 1 more it's not drift at all (stale `key_hash` fixture). Budget explicit time
for fixture/baseline-level repair, separate from the lane decision.
**Warning signs:** A plan wave that closes criterion 13 purely by adding a new CI job with no
fixture-file diffs.

### Pitfall 2: Believing the shared-TEST mutex provides ordering
**What goes wrong:** Assuming that because `apply-test` and `sql-tests`/`python`/`e2e-seeded` all
take the same advisory lock, they are safely sequenced.
**Why it happens:** "Serialized" and "ordered" sound like the same property; they are not — a
mutex guarantees no two holders overlap, never which one goes first.
**How to avoid:** Treat exclusivity (needs a shared/distinct lock) and ordering (needs a `needs:`
edge, a `workflow_run` trigger, or a poll) as two separate mechanisms to design, per Q3.
**Warning signs:** A plan that "fixes" this criterion by adjusting lock keys alone, with no
new ordering primitive.

### Pitfall 3: Making the dead-holder detection redden the ALWAYS() release step directly
**What goes wrong:** `exit 1` added inline to the existing `if: always()` release step, which then
fails on ANY release hiccup (not just the dead-holder case), regressing the step's own documented
"must never redden a job whose real work passed" invariant for unrelated transient release
failures.
**Why it happens:** The dead-holder branch and the release step are the SAME step today, so the
naive fix touches the wrong granularity.
**How to avoid:** Separate the detection (existing, correct, in the release step) from the
verdict (new, in a dedicated subsequent `if: always()` step that only checks a marker).
**Warning signs:** A single-step diff to the "Release shared-test-db mutex" step that adds `exit 1`
somewhere inside it.

### Pitfall 4: Assuming the extension-guard fix is "just flip `=` to `>=`"
**What goes wrong:** Changing `[ "$post_ext" = "$pre_ext" ]` to `[ "$post_ext" -ge "$pre_ext" ]`
silences the false positive on a legitimate gain but reopens blindness to a genuine loss masked
by an unrelated, coincidental gain elsewhere in the database (count-based comparison cannot tell
WHICH extensions changed, only whether the total changed) — this is precisely the "naive fix
reintroduces the same one-sidedness pointing the other way" CONTEXT warns against.
**Why it happens:** It is the smallest possible diff that clears the immediate false positive.
**How to avoid:** Scope the count to `public` first (removing nearly all legitimate churn from the
picture, since this repo's own extensions never live there), then keep the comparison strict.
**Warning signs:** A one-line diff (`=` → `-ge`) with no accompanying schema-scoping change.
