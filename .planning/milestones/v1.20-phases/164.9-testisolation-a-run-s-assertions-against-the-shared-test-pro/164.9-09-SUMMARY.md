# Phase 164.9 Plan 09: The data-dependent migration refusal Summary

A hermetic author-time refusal that stops a migration whose anonymous block raises on rows the
TEST database does not have from merging at all — plus the dated, shrink-only census of the 83
such guards the corpus already carries, each routed to a booked destination, with no migration
edited.

## What the phase criterion asked for, and what it got

ROADMAP criterion 5 asked that `[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]` get a **MECHANISM, not a
pragma**. The failure is structural: the TEST restore is schema-only, so TEST mirrors production's
CATALOGUE and never its DATA; a migration in this repository's house style — an anonymous block
that reads a populated table and `RAISE EXCEPTION`s on an unexpected count — applies cleanly to
production and REFUSES on TEST; and because a failed TEST apply gates the production apply, that
refusal withholds a production deploy.

Phase 164.8 had already designed the escape hatch, specified it with a three-arm proof, and
deliberately not built it, because a hatch is something a person must remember to claim under
exactly the deploy pressure that makes people claim things. This plan built the other answer: a
refusal that fires on the pull request, cannot be forgotten and cannot be claimed.

## Accomplishments

- **`scripts/lint-migration-data-dependence.mjs`** — node-builtins-only, no database, no
  container, no secret, no network. Two numbered refusals, each with a red and a green fixture;
  `--self-test` runs before any corpus scan; a census line is printed on every run.
- **The refused property is a CONJUNCTION**, and both halves are proven load-bearing by a fixture
  rather than asserted: an anonymous block whose body BOTH reads an application relation AND
  raises under a condition derived from that read. Either half alone is allowed.
- **Lexing is borrowed, not re-invented** — `maskSql` from `lint-sql-gates.mjs` and
  `dollarBodyRanges` from `extract-reference-inserts.mjs`. A third lexer would be a second place
  the classification can drift (decision D-05).
- **`scripts/lint-migration-data-dependence-baseline.txt`** — the census, GENERATED from the
  classifier (no line typed by hand), dated, shrink-only, with a tool-verified `ENTRY_COUNT` and a
  destination on every entry.
- **Three additive steps in `sql-gate-lint`**, the job the `frontend` aggregator gates with no
  tolerance: bare self-test first, bare corpus scan second, a stdout-capturing assertion third.
- **`src/__tests__/lint-migration-data-dependence.test.ts`** — 17 tests pinning what the workflow
  cannot pin itself.
- **`[164.9-DATA-DEPENDENT-GUARD-CENSUS]` booked in `TODOS.md`** with an owner, the inherited
  trigger and the forbidden closures.


**272 migrations, 345 anonymous blocks, 83 refusals across 63 files.** Not zero — the class exists
as a large pre-existing backlog, not merely as a hazard. Two refusal rules split it
**R1 (variable-conditioned) / R2 (inline-subquery-conditioned)**.

⭐ **The census found the specimen the backlog entry names by file**, which is the calibration that

**Destination for every entry:** `[164.9-DATA-DEPENDENT-GUARD-CENSUS]`. Per-file destinations are

⚠️ **THE CENSUS IS NOT A TRIAGE, and the ledger header says so.** The scan refuses a SHAPE. Some

then raising only if the round-trip failed. A static scan cannot tell those from a genuine
precondition without executing them. The per-entry decision is what the destination owns.

⛔ **NO migration was edited.** `git diff --name-only -- supabase/migrations/` is empty, asserted

## Deviations from Plan

### 1. [Rule 1 - Bug] Flow-insensitive taint condemned a catalogue guard (commit `e0b4b402`)

- **Found during:** Task 3, by the contract test being written in the same task — which is exactly
  what the second layer is for.
- **Issue:** `taintedVariables()` built a flow-INSENSITIVE map keeping the first tainted
  assignment per name. A block reusing one scratch variable — `SELECT ... INTO v_n FROM pg_class`
  for a catalogue assertion, then `SELECT ... INTO v_n FROM public.t` later for a `RAISE NOTICE` —
  had the later data read reach BACKWARDS and condemn the earlier catalogue guard. That is a false
  positive on a migration doing exactly what the linter's own header prescribes, and a false
  positive here BLOCKS A DEPLOY.
- **Fix:** `variableAssignments()` records EVERY assignment, tainted or not, with its offset;
  `raiseSites()` carries each condition's start offset; each condition resolves against the
  assignment IN FORCE where it is evaluated. Recording the UNTAINTED assignments is the
  load-bearing half — an overwrite clears a taint exactly as it clears a value.
- **Consequence, recorded because it moved UPWARDS:** the census went **79 -> 83** over the SAME
  63 files. Position-resolution is more precise in both directions, so conditions previously
  attributed to whatever relation a variable read FIRST are now attributed to the one actually in
  force, separating keys that had been collapsing. The ledger was REGENERATED from the classifier,
  never hand-patched, and `TODOS.md`'s figures moved with it.
- **Limitation now stated in code:** this is position-ordered, not control-flow-ordered. Inside a
  `LOOP` an assignment textually after a condition does reach it on the next iteration. The edge
  biases toward ALLOWING, never toward refusing — the right direction for a gate whose false
  positive withholds a deploy.
- **Files:** `scripts/lint-migration-data-dependence.mjs`,
  `scripts/lint-migration-data-dependence-baseline.txt`, `TODOS.md`
- **Commit:** `e0b4b402`

### 2. [Rule 2 - Missing critical] `TODOS.md` was outside the plan's `files_modified`, and an acceptance criterion required it

- **Found during:** Task 2.
- **Issue:** the criterion is *"every destination has a matching booked id in `TODOS.md`"*, and no
  id existed for repairing the existing offenders. `[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]` is
  what this plan CLOSES (the mechanism); its candidate shapes are about the hatch, not about 63
  applied migrations. Pointing 83 entries at nothing is precisely the `FANOUT-GLOBAL-01` failure
  mode `CLAUDE.md` names — a planner sent looking for a spec nobody wrote.
- **Fix:** booked `[164.9-DATA-DEPENDENT-GUARD-CENSUS]` with owner, the inherited trigger
  (`apply-test` RED on a data-block `RAISE` while PROD's `plan` dry-run is CLEAN), the interim
  remedy and the forbidden closures. This follows the phase's own precedent: plan 08 booked
  `[164.9-LIVEDB-LANE-EXECUTION-CENSUS]` from an executor in the same way.
- **Verification:** the contract test asserts every bracketed destination id in the ledger appears
  in `TODOS.md`, so the routing cannot silently rot.
- **Commits:** `3a34a539`, `e0b4b402`

### 3. [Rule 3 - Blocking] The softening-token prohibition tripped its own acceptance scan

- **Found during:** Task 3.

- **Fix:** the in-region comment names the CLASS ("no trailing-truth command after a pipeline, and
  no bare zero-status `exit`") and points at its twin above, which sits outside the scanned region
  and spells them out. Re-measured: `soft=0`.
- **Files:** `.github/workflows/ci.yml`
- **Commit:** `bd82ef38`
