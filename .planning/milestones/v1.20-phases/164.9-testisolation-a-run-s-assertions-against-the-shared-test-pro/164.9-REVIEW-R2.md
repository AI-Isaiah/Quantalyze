### CR-01: The dead-holder drill that item 8 rewrote is invoked by NOTHING — the fourth recurrence of the class this same fix round closed for a sibling

**File:** `scripts/pg-lane/mutex-dead-holder-lane.sh` (whole file); `.github/workflows/ci.yml` (no call site)
**Introduced by:** `6691b3a4` (fix round)

Commit `6691b3a4` replaced a self-contained drill with one that EXTRACTS the
`Release shared-test-db mutex (best effort)` step's `run:` body out of `ci.yml` at run time by
exact indentation (`awk` on a 6-space `- name:`, an 8-space `run: |`, a 10-space body) and
`eval`s it, then derives the pidfile and the marker path by `grep`+`eval` over that extracted
text. I ran it: it works today, end to end, on a real throwaway cluster.

**But nothing in CI or `package.json` runs it.** Measured:

```
grep -ra "mutex-dead-holder-lane" .github package.json
  → no matches
```

The only references are `docs/runbooks/shared-test-db-mutex.md` (which names it merely as a file
that mentions the advisory key) and the phase's own SUMMARY prose. That is verbatim the defect
the SAME fix round wrote up four commits earlier, in `ci.yml`'s new self-test step, in its own
words: *"`wait-for-test-schema-apply.sh --self-test` was invoked by NOTHING. Every reference to it
in this repo was PROSE … Six written claims, zero executions"* and *"A gate whose control only
runs when the gate runs cannot catch a commit that defangs it."*

Why it is worse here than for a static gate: the new drill is now COUPLED to `ci.yml`'s exact
YAML indentation and step name. A reformat, a rename, or moving the release step to a different
indent level silently breaks the extraction — and the drill's own `fail` messages, the ones that
would say so, are never executed by anything. The file's header asserts *"a ci.yml that stops
writing a marker makes this drill FAIL LOUD instead of passing"*; that sentence is only true for
a developer who happens to run it by hand.

**Fix:** wire it exactly like the sibling fix, in a job that already provisions PostgreSQL server
binaries and is in the `frontend` aggregator's `needs` (`sql-mutation` already runs
`scripts/pg-lane/run.sh`):

```yaml
      - name: Dead-holder drill - the release step's OWN body, on a disposable cluster
        run: bash scripts/pg-lane/mutex-dead-holder-lane.sh
```

If the intent is genuinely developer-only, say so IN THE FILE and delete the "fail loud" claim,
because an uninvoked drill cannot fail loud at anyone.

### CR-02: The retry's idempotency narrowing re-opens a `pytest.skip` on the exact failure ROADMAP criterion 11 measured — a shared-TEST transport fault can now report GREEN

**Files:** `analytics-service/tests/live_db_transport.py` (`_NON_IDEMPOTENT_BUILDER_METHODS`);
`analytics-service/tests/test_compute_jobs_fencing.py` (`_rpc_retry_timeout`)
**Introduced by:** `0ced56bb`, documented by `d99e9bc1`

The narrowing itself is CORRECT engineering — replaying a write whose 504 may name an already-
committed transaction is worse than not replaying it, and `rpc` is fail-closed because the
wrapper cannot read a function body. I am not asking for it to be reverted.

What it does is restore a live `pytest.skip` path on the RPC surface, and the RPC surface is
precisely the one criterion 11 was written from. ROADMAP criterion 11's evidence names run
`34763669052`: *"`python` RED on `tests/test_compute_jobs_fencing.py` with
`postgrest.exceptions.APIError … 504 Gateway Timeout`"*. `_rpc_retry_timeout` wraps every
`admin.rpc(...).execute()` call site in that file and ends:

```python
    pytest.skip(
        f"defer_compute_job live-DB RPC timed out {attempts}x under shared "
        ...
```

Before the narrowing, the inner `retry_transport` absorbed the timeout and, on exhaustion, raised
`TransportRetryExhausted` — whose message does NOT contain `"timed out"`, so the outer helper
re-raised and the job went RED. After the narrowing the inner retry never runs for an `rpc`
chain, the raw exception propagates, and I verified the string match fires:

```
str(httpx.ReadTimeout('The read operation timed out'))  → 'timed out' in it: True
```

So a sustained shared-TEST RPC timeout is now a SKIP and a green `python` job. That is the
"a skip is a green that measures nothing" condition the phase's charter, `frontend-live-db-lane`'s
own header and `csv-finalize-rpc.test.ts`'s tombstone all exist to end — re-created inside the
phase that exists to end it.

The disclosure is real but it is in the WRONG places and one place it should be is still false:

- disclosed: the `_rpc_retry_timeout` docstring and `wrap_live_db_client`'s docstring;
- **not** disclosed: ROADMAP criterion 11 itself, which still reads as delivered;
- **contradicted**: `164.9-05-SUMMARY.md` still says the inner retry *"retries first (up to 3
  attempts with backoff)"* for these call sites (see WR-07);
- **unowned**: the named follow-up — *"an explicit allowlist of read-only RPC names"* — exists
  ONLY as a sentence in a Python docstring. Measured: zero hits for it in `TODOS.md` and in
  `.planning/ROADMAP.md`. This repo's rule is that a deferral names a phase; this one names a
  docstring.

**Fix (any one of these closes it; the first is smallest):**

```python
# In test_compute_jobs_fencing.py — stop skipping; the phase's whole point is that this reds.
    raise AssertionError(
        f"defer_compute_job live-DB RPC timed out {attempts}x. Since Phase 164.9 the transport "
        "retry deliberately does NOT replay an RPC (idempotency boundary), so this is a "
        "sustained shared-TEST transport fault and it reds rather than skips."
    ) from last
```

or ship the read-only-RPC allowlist now (`claim_*`/`mark_*` stay excluded, `defer_compute_job`
is decided explicitly), **and** book the residue as a real `TODOS.md` entry with an owner and a
phase, **and** amend ROADMAP criterion 11 so it does not read as fully delivered.

### WR-01: `ENTRY_CEILING` is defeated by editing two numbers in one commit, and the contract test turns it into a mirrored pin rather than a ceiling

**Files:** `scripts/live-db-execution-ledger.mjs` (`ENTRY_CEILING`);
`src/__tests__/live-db-execution-ledger.contract.test.ts` (the `RATCHET STALE` arm)

I reproduced round-1's evasion and confirmed it is now caught (`LEDGER GREW`, exit 1). But the
question asked was whether the fix survives a two-number edit, and it does not. The contract
test's staleness arm is:

```ts
    expect(ENTRY_CEILING, `RATCHET STALE: …`).toBe(entries);
```

`toBe`, not `toBeGreaterThanOrEqual`. So `ENTRY_CEILING` is FORCED to equal the entry count
exactly. A growth commit is therefore: append one TAB line, `# ENTRY_COUNT = 18` → `19`,
`ENTRY_CEILING = 18` → `19`. All three gates stay green; the gate's own message
("Raising the ceiling to clear this message is the defect") is prose again. One number harder
than before, not a different kind of control.

Two secondary consequences worth naming:

- The contract test's header states it *"deliberately does NOT pin the per-kind tally (9/6/3),
  nor an exact total"* — and then arm 5 pins the exact total through `ENTRY_CEILING`. The file
  contradicts itself.
- `ENTRY_CEILING` is now a restated copy of a number that lives in a tracked file two directories
  away, which is the "prose beside a constant" class `CLAUDE.md` records four times over, in the
  constant introduced to answer that class.

**Fix:** stop restating the count. Derive the ceiling from the ledger and gate on the DIRECTION
instead — e.g. keep a dated `ENTRY_CEILING_AT` (the commit sha the ceiling was set at) and have
the contract test assert `entries <= ENTRY_CEILING` plus *"the ceiling was not raised in this
commit"* via `git log -S` on the constant, so a raise is visible as its own reviewable act
rather than a digit inside a fix. At minimum, relax the arm to
`toBeGreaterThanOrEqual`/`toBeLessThanOrEqual(entries + 0)` and record in the message that the
ceiling and the count moving together in one commit is the known residual.

### WR-05: A new test cannot fail for the half of the claim its own name makes

**File:** `analytics-service/tests/test_live_db_transport.py`
(`test_a_mutating_method_taints_only_the_rest_of_its_own_chain`)

The name and docstring promise *"the same wrapped client still retries a READ issued after a write
chain — otherwise one insert would silently disable the retry for the whole fixture."* The body
then builds a **second** `_FakeBuilder` and a **second** proxy for the read:

```python
    read_client = _FakeBuilder(log, fail_times=1)
    read_proxy = wrap_live_db_client(read_client, attempts=3, …)
    assert read_proxy.table("compute_jobs").select("*").execute() == …
    assert read_client._execute_calls == 2  # the read DID retry
```

`wrap_live_db_client` always passes `retry_safe=True`, so a fresh proxy is retry-safe no matter
how the taint is stored. If the taint were implemented as sticky per-root-proxy state — the exact
defect the "only" in the test's name rules out — this assertion would still pass. (The first half
of the test, the `pytest.raises` on the insert chain, IS load-bearing; it is also already covered
by the parametrised test immediately above.) The production behaviour is correct; the test
does not prove it.

**Fix:** drive the read through the SAME proxy:

```python
    assert proxy.table("compute_jobs").select("*").execute() == {"data": [{"id": 1}]}
```

with a fake whose `_execute_calls` is reset, so the arm reds if the taint ever becomes sticky.

### WR-06: The ordering wait now has no successful termination while the in-flight flag reads `unknown` — a transient probe failure burns 900 s and reds three blocking jobs

**File:** `scripts/wait-for-test-schema-apply.sh` (`wait_for_apply`)
**Introduced by:** `43b0a6ff`

After the fix, BOTH terminating arms require `flag = "clear"`:

```sh
      concluded-ok|concluded-bad)
        if [ "${flag}" = "clear" ]; then outcome="apply-concluded"; fi
        ;;
      absent)
        if [ "${waited}" -ge "${APPEAR_GRACE_SECONDS}" ] && [ "${flag}" = "clear" ]; then
```

`probe_inflight_flag` answers `unknown` whenever `TEST_SUPABASE_DB_URL` is empty OR the bounded
`psql` (`PGCONNECT_TIMEOUT=15 timeout 20`) fails — and `classify_inflight_answer` maps any
non-numeric output to `unknown`, correctly. The consequence is that there is now NO path to a
zero exit while the flag is unmeasurable: the loop runs the full `WAIT_BUDGET_SECONDS` (default
900) and then `wait-exhausted` returns 1, in `sql-tests`, `python` and `e2e-seeded` — three jobs
the `frontend`/CI aggregators gate on, on every merge push.

The fail-closed DIRECTION is right (an unreadable probe cannot rule out a `DROP SCHEMA`), and the
`absent` arm already had this property before the fix, so this is a widening rather than a new
class. What is missing is a bounded degradation: 900 s of wall clock is spent BEFORE the red, and
the red is identical whether the flag was held or simply unaskable.

**Fix:** distinguish "could not measure" from "waited out a real holder" and fail FAST on the
former — e.g. after N consecutive `unknown` reads with an `absent`/`concluded` apply state,
break out immediately with a distinct outcome (`flag-unmeasurable`) that still returns 1 but
names itself and does not burn the budget. The exhaustion message already carries the
distinction in prose; make it a control.
