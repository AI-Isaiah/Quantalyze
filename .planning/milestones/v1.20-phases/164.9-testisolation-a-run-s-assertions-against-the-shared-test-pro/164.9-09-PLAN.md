<objective>
ROADMAP criterion 5: a data-reading migration that applies to production and refuses on a
data-empty TEST must not block a production deploy — and it must get a MECHANISM, not a pragma.

The failure is structural. The TEST restore is schema-only, so TEST mirrors production's CATALOGUE
and never its DATA. A migration written in this repository's house style — an anonymous block that
reads a populated table and raises on an unexpected count — therefore applies cleanly to production
and REFUSES on TEST. And because the TEST apply gates the production apply, that refusal withholds
a production deploy.

⭐ **Why a refusal at author time rather than an escape hatch at apply time.** Phase 164.8 already
designed the escape-hatch shape — a header pragma parsed by one consumer — specified it with a
three-arm proof, and then deliberately did NOT build it, because it had zero consumers. An escape
hatch is something a person must remember to claim, under exactly the deploy pressure that makes
people claim things. A refusal that fires on the pull request cannot be forgotten and cannot be
claimed. ⛔ It is also not a widening: the shape it refuses is one this repository's own database
rules already forbid ("self-verify must be CATALOGUE-ONLY"), written down but never enforced.

Output: a hermetic linter with red and green fixtures per refusal, a dated shrink-only census of the
existing corpus, and a fifth sibling step in the lint job that asserts the census line it prints.
</objective>
