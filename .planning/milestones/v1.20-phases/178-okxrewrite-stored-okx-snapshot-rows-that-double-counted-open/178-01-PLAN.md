<objective>
Fix the defect the founder named in D-05 at its root: a forced whole-account rebuild refuses the WHOLE allocator `account_key_not_working` when any ONE exchange account of it has no working key. After this plan the rebuild skips that exchange account and counts it, the allocator's other exchange accounts are rebuilt, and only an allocator with no working exchange account at all still refuses the token. The count is carried to the completion audit and to the read-only probe so the operator plans can compare it with a measurement.

D-05 verbatim (founder 2026-10-28): "If a bybit Ley is Revoked, then that is only relevant for that Key. It is Not relevant for OKX and its keys, neither for other bybit keys". CONTEXT D-05: "178 fixes it at the root, in every place where one non-working key refuses or blocks an account (rebuild key selection, the probe's selection, any similar gate), as an autonomous code plan ahead of the operator plans, with a test that goes RED on the current whole-account refusal."

Root-cause audit (RESEARCH Finding 1a, re-measured at planning): the token has ONE raise site in production code, `_select_account_crawl_keys` in `analytics-service/services/equity_reconstruction.py`; the forced crawl (`_crawl_whole_account`) and the probe (`_probe_account`) both call it, so fixing it fixes both. `identity_pending_venues` counts only working keys and `choose_job_key` already picks a working OKX key when the Bybit key is dead, so neither blocks on a dead key.

Widened at plan revision (2026-10-28): the token grep is not the whole audit. In the same loop the two `account_key_venue_unsupported` raises run BEFORE the working check and read every member's venue, so a revoked or disconnected key on a venue outside `_ACCOUNT_REBUILD_VENUES` (sfox, an unknown venue), or a dead member of a cross-venue marker group, refuses the whole allocator just the same. The daily refresh leaves such an account out too (`_fetch_latest_holdings_per_eligible_key`: a group with no eligible key is skipped), so this plan fixes those sites as well, each with a test RED on HEAD. A WORKING sfox or unknown-venue account still refuses `account_key_venue_unsupported`, unchanged. The executor runs the widened audit (every raise statement in the selection, every key-status predicate on the forced path and in the probe, every other refusal raise of the module, and the job-key preflight) and records each disposition.

What a skipped dead key contributes inside the window (CONTEXT D-05's open question, answered by RESEARCH Finding 1c and ruled by the founder in D-06): both stored-row writers count a key up to the day it stops and $0 after it, so skipping matches the stored rows only on days after the key stopped. The account whose dead key overlaps the window is NOT rebuilt (D-06); that guard is plan 02's P7 census and the operator plans (Claude's discretion C1, CONTEXT), not code here. P7 also counts a dead member on another venue than its group's working keys, since the crawl of that group does not read it. This plan writes nothing to any database.

Purpose: the four OKX-holding accounts the 2026-10-28 deployed probe refused at selection become readable, so plan 03 can measure them (D-01) and plan 04 can rebuild the ones the founder rules on.
Output: the selection change with its audit and probe plumbing, inverted and new tests, a RED proof in the SUMMARY. VERSION, package.json and CHANGELOG are written by the orchestrator at ship (plans 01, 02 and 05 ship as one PR), not by this plan.
