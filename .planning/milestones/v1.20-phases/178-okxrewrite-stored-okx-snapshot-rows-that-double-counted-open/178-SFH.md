## Checked and sound (so the next reader does not re-derive it)

- SQL grouping and state classification versus Python: `working` matches `working_holder_predicate`
  (`is_active` is NOT NULL, same three not-working statuses, NULL status counts as working); marker kinds
  match `SHARED_ACCOUNT_KINDS`; the recursive `reach` closure equals `account_groups`' connected
  components; `zero` before `dead` before `refused` equals the Python order; `dead_exchange_accounts`
  counts groups, not keys, as the audit does.
- Window prediction (90 with a crawled OKX group, else 730) matches `_account_rebuild_window`
  (`BYBIT_TRADE_TERMINUS_DAYS` and `BACKFILL_CAP_DAYS` are both 730).
- Carry-window date math: the daily refresh counts a group on day D only from holdings with
  `asof` in `[D-7, D]`, so `[first_asof - 1, last_asof + 7]` is a sound superset (the -1 is slack, not an
  off-by-one). `date - integer` arithmetic is date-typed.
- A missing `account_non_working_accounts_excluded` in the completion audit is not read as 0: the audit
  form yields NULL and B'5 rule 6 STOPs on it. A pre-fix probe or worker fails loudly on the 2-vs-3 tuple
  unpack rather than silently.
- Python tests for the selection and the dead-account rebuild assert concrete values and would go RED on
  the old whole-account refusal.

## M1 - MEDIUM, data-integrity: P7's decision and the dead-account count are read before the write, and the only re-check is after it

Where: `docs/runbooks/marksource-okx-history-correction.md` P7 (line 488), B'3a (557), B'5 rule 5 (820);
`analytics-service/services/equity_reconstruction.py:6863-6865`.

Evidence: P7 reads key state once, in pre-flight. The job reads key state again when it starts, and
`_select_account_crawl_keys` treats `sync_status` `error` and `sign_in_failed` as dead (a state a healthy
key can be in for a poll or two). B'3a only re-checks in-flight jobs, not P7. The persist-time guard
compares the SET OF KEY IDS only (`!= account.account_key_ids`), not any key's state, so a key that
flips to `error`/`revoked` between P7 and the job's key read is silently skipped by the rebuild. The only
check that sees it is B'5 rule 5 (audit count versus P7's `dead_exchange_accounts`), which runs after the
atomic window replace has committed. The Rollback section states there is no rollback and that the B'2
before-file is evidence, not a restore source, and B'6 deletes it.

Silent path: P7 reads `dead_keys = 0`, outcome `rebuild`. The key then reads `error` at job start, the
rebuild drops that exchange account from every in-window day it was counted on (understating a stored
window by a whole account), and the job ends DONE. The mismatch STOP in rule 5 fires only afterwards,
with the rows already replaced.

Hidden errors this hides: transient `error`/`sign_in_failed` flips; a key disconnected or revoked in the
minutes between P7 and the worker's key read; a dead key revived between P7 and the read (rebuild runs,
dead count differs, again post-hoc).

Recommendation (minimal): require P7 to be re-run, and its row compared field by field with the first
reading, immediately before B'3b (add it to B'3a's expected line); STOP on any change in
`dead_exchange_accounts`, `dead_keys` or `p7_outcome` for a chosen label. A code-side alternative is to
carry P7's expected dead-account count in the enqueue metadata and refuse before the persist on a
mismatch, but the runbook re-run is enough given the three one-off accounts.

## M2 - MEDIUM, data-integrity: the crosswalk's label-total check has no STOP, and its fingerprint cannot tell similar accounts apart

Where: `docs/runbooks/marksource-okx-history-correction.md:266-282` (crosswalk prose), P4 (line ~469).

Evidence: the proof that a probe record belongs to a census label is "the statement" plus "the
fingerprint". The fingerprint is six small counts (for example one OKX member, zero everything else,
window 90), so two accounts routinely share it; the statement is then the only discriminator. The
statement's labels shift whenever an owner gains or regains an ACTIVE okx/bybit key with an early
`created_at` between the probe run and the crosswalk run (an owner whose old key is re-activated slots
into the middle). The guard against that is the sentence "check that `probe_accounts_total` equals the
probe summary's `accounts`", which carries no "Abort if" or STOP wording, unlike P1 to P7. A total that
is equal after one key joined and another left also passes it. The probe orders ties by arbitrary
Postgres row order while the SQL orders by `user_id`, a second unflagged way for two same-time owners to
swap.

Silent path: a target is written on another account's ordering reading (D-02 intends each target's OWN
reading), and the runbook reads that as "proven twice".

Recommendation: state it as an abort ("Abort if `probe_accounts_total` differs from the summary's
`accounts`, or if the probe and the crosswalk ran on different UTC days"), and require an ok record's
fingerprint to be unique among the census rows before it is accepted (else STOP and re-run the probe).
