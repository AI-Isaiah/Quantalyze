## Summary

The reference-data chain (allowlist → extractor → in-transaction replay → in-transaction gate → census) is well built and unusually well instrumented. I could not find a path by which a dollar-body fixture INSERT becomes replayable, could not find a SQL-injection seam, and every measured number in the allowlist masthead and in the workflow assertions reproduced exactly when I re-ran the printed recipes.

The defects I found cluster in three places:

1. **One new, unnoticed regression in the safety instrument itself.** This phase added *externally mutable row counts* to the census that `--mode preflight` compares **byte-for-byte** as its proof of rollback. On shared TEST that comparison can now fail for reasons that have nothing to do with the transaction — and its diagnosis is `Treat this database as modified.` That is CR-01.
2. **A cluster of comment-truth defects around the count floor.** The floor's stated soundness argument ("each of those statements inserts at least one row") is false for this corpus, and the comment's own worked example does not fire the gate it is cited to justify. Measured: `public.compute_job_kinds` is 15 statements / 16 rows.
3. **Discipline claims that are not applied uniformly** — three env-var seams reach SQL string literals without `sql_lit` two lines after the file declares they are `sql_lit`-quoted at every such site; the extractor's stated falsification of `insideBody()` is measurably wrong.

## Critical Issues

### CR-01: `--mode preflight`'s byte-for-byte rollback proof now compares row counts that other sessions can change on shared TEST

**File:** `scripts/restore-test-from-baseline.sh:463-466` (the new census rows) and `scripts/restore-test-from-baseline.sh:1379-1381` (the comparison)

**Motivating lines, verbatim:**

```
464:    printf "SELECT 'refdata:%s=' || CASE\n         WHEN to_regclass('%s') IS NULL THEN 'absent'\n         ELSE (xpath('/row/c/text()',\n                query_to_xml('SELECT count(*)::text AS c FROM %s', false, true, '')))[1]::text\n       END;\n" \
```

```
1379:    if ! cmp -s "$RESTORE_OUT_DIR/pre-census.txt" "$RESTORE_OUT_DIR/post-census.txt"; then
1381:      fail "post-census != pre-census. The transaction was supposed to ROLL BACK and the database is NOT byte-for-byte unchanged. Treat this database as modified."
```

**Issue:** Before this phase the census held only counts that no concurrent session mutates in normal operation (`tables=`, `functions=`, `policies=`, `extensions=`, `ledger_rows=`, survivor keys). This phase added eight `refdata:<schema.table>=<row count>` lines to that same file, and the preflight proves its rollback by `cmp`-ing the whole file pre and post.

Those eight values are **not** stable on shared TEST:

- `auth.users` is the C3 exception this phase added. It lives **outside `public`**, so `DROP SCHEMA public CASCADE` never takes a lock on it — a concurrent signup on shared TEST commits freely during the entire transaction and changes the count between the two censuses.
- `public.profiles`, `public.strategies` are written by e2e/pgTAP traffic against TEST.
- `public.feature_flags` and `public.system_flags` are described by this phase's own documentation as runtime-mutable: `restore-test-refdata-allowlist.txt:108-110` — *"`feature_flags` and `system_flags` are RUNTIME-MUTABLE operational switches"* — and `:122` — *"That this silently changes shared TEST under another team's CI run is the SHARED-TEST hazard"*. The authors knew the values move; the connection to the byte-identity comparison was not made.

The advisory mutex (`61616158`) does not close this: it is voluntary and only this repo's workflows take it, while `CLAUDE.md` states plainly that *"TEST is SHARED with other people's CI"* and that *"a global assertion there is NOT reliable … Assert about YOUR OWN rows."* These eight rows are exactly a global assertion.

Consequence: a preflight whose transaction rolled back **perfectly** can now abort with `Treat this database as modified.` — the loudest, most alarming message this script has, on the one instrument the founder-executed destructive restore is gated on. The failure direction is safe, but the diagnosis is wrong, it is non-deterministic on the only database it is meant to run against, and a preflight that cries wolf is a preflight an operator learns to re-run past.

**Fix:** keep the counts in the census (they are the right place for the reading) but exclude them from the byte-identity comparison, so the rollback proof stays over the schema-shape rows only. Concretely, compare filtered copies:

```bash
  if [ "$mode" = "preflight" ]; then
    # The rollback proof is over the SCHEMA-SHAPE rows only. `refdata:` rows are
    # ROW COUNTS of tables other sessions write on SHARED TEST (auth.users is not
    # even locked by the DROP), so including them makes a correct rollback
    # reportable as "the database is NOT byte-for-byte unchanged".
    grep -av '^refdata:' "$RESTORE_OUT_DIR/pre-census.txt"  > "$RESTORE_OUT_DIR/pre-census.shape"
    grep -av '^refdata:' "$RESTORE_OUT_DIR/post-census.txt" > "$RESTORE_OUT_DIR/post-census.shape"
    if ! cmp -s "$RESTORE_OUT_DIR/pre-census.shape" "$RESTORE_OUT_DIR/post-census.shape"; then
      diff "$RESTORE_OUT_DIR/pre-census.shape" "$RESTORE_OUT_DIR/post-census.shape" >&2 || true
      fail "post-census != pre-census. ..."
    fi
    # The refdata readings are still PRINTED and still compared, but with a
    # diagnosis that names concurrency rather than a failed rollback.
    diff <(grep -a '^refdata:' "$RESTORE_OUT_DIR/pre-census.txt") \
         <(grep -a '^refdata:' "$RESTORE_OUT_DIR/post-census.txt") >&2 \
      || note "refdata census moved across the transaction — on SHARED TEST that is concurrent traffic, not a failed rollback (auth.users is outside public and is never locked by the DROP)."
```

⚠️ Arm 8 (`arm_g_preflight`) asserts the byte-for-byte equality on the lane, where nothing is concurrent, so it will stay green either way — the fix needs its own note beside the filter rather than a new arm.

### WR-05: `literalCheck` stops at `ON CONFLICT` and never inspects the conflict action — a future `DO UPDATE` would be replayed into `auth.users`, whose rows SURVIVE the restore

**File:** `scripts/extract-reference-inserts.mjs:308-309`

**Motivating lines, verbatim:**

```
308:  const stop = /\bON\s+CONFLICT\b|\bRETURNING\b/i.exec(region);
309:  if (stop) region = region.slice(0, stop.index);
```

**Issue:** C2 is enforced only over the VALUES tuple. Everything after `ON CONFLICT` is unexamined, so `ON CONFLICT (id) DO UPDATE SET role = 'admin'` classifies as replayable reference data. Against a table the DROP emptied that is a no-op (no conflicts). Against **`auth.users`** — the single C3 exception this phase introduced, documented at `restore-test-refdata-allowlist.txt:68-76` precisely because *"That row … SURVIVES the restore"* — a `DO UPDATE` arm would silently **mutate a pre-existing row on shared TEST**, inside a transaction that then commits.

Measured at HEAD: all 22 `ON CONFLICT` clauses in the emitted SQL are `DO NOTHING` (1 × `flag_key`, 3 × `id`, 3 × `key`, 15 × `name`), so this is latent, not live. It is also not in the header's "KNOWN LIMITATIONS" list at `:33-54`, which is where the file's other two blind spots are honestly stated.

**Fix:** refuse anything but `DO NOTHING` — the allowlist's own C4 idiom is idempotent seeds:

```js
  const conflict = /\bON\s+CONFLICT\b([\s\S]*)$/i.exec(maskedStatement);
  if (conflict && !/\bDO\s+NOTHING\b/i.test(conflict[1])) {
    return "the ON CONFLICT action is not DO NOTHING — a DO UPDATE arm MUTATES a pre-existing row, and `auth.users` (the one C3 exception) SURVIVES the restore, so its rows are other people's on shared TEST (C2)";
  }
```

and add a `c2-on-conflict-do-update` self-test kind, raising `SELF_TEST_KINDS_FLOOR` and `REQUIRED_KINDS` in the same commit.

### WR-06: the head regex is blind to quoted identifiers and to CTE-prefixed INSERTs, so `--audit` silently skips them — and the limitations list does not say so

**File:** `scripts/extract-reference-inserts.mjs:359-366`

**Motivating lines, verbatim:**

```
361:    ? new RegExp(`^INSERT[\\t\\n ]+INTO[\\t\\n ]+(?:public[\\t\\n ]*\\.[\\t\\n ]*)?${table}\\b`, "i")
```

**Issue:** two shapes evade the classifier entirely:

- `INSERT INTO "public"."compute_job_kinds" …` — `maskSql` deliberately does **not** blank quoted identifiers (`lint-sql-gates.mjs:411`, *"Quoted identifiers are CODE, not data — skipped over, never blanked"*), so the masked text still carries the `"` and `^INSERT\s+INTO\s+(?:public\s*\.\s*)?compute_job_kinds\b` does not match. `supabase/schema/baseline.sql` is written entirely in this style, so it is the house style one directory over.
- `WITH x AS (…) INSERT INTO compute_job_kinds …` — the `^INSERT` anchor fails.

In both cases the statement is **silently skipped**, not flagged: in `modeAudit` the `m.ok.length === 0 && m.rejected.length === 0` branch at `:626` `continue`s. That is the one behaviour the audit exists to prevent (`ci.yml:1084-1086`: *"this step reddens when a new migration adds a top-level literal INSERT into an allowlisted table with no allowlist line"*).

Measured: zero migrations use quoted-identifier INSERTs today (`grep -rlE 'INSERT[[:space:]]+INTO[[:space:]]+"' supabase/migrations/` → no hits), so this is latent. But it is a *silent* blind spot in a gate whose whole value is that it is not silent, and it is absent from the honest limitations list at `:33-54` that names the other two.

**Fix:** accept the quoted spelling in `headRe` and refuse the CTE form loudly rather than skipping it:

```js
function headRe(schema, table) {
  const q = (id) => `"?${id}"?`;             // the baseline.sql spelling
  const pfx = schema === "public" ? `(?:${q("public")}[\\t\\n ]*\\.[\\t\\n ]*)?` : `${q(schema)}[\\t\\n ]*\\.[\\t\\n ]*`;
```

### WR-10: `process.exit()` immediately after `process.stdout.write` can truncate a refusal on a pipe

**File:** `scripts/extract-reference-inserts.mjs:917-922`, `:968`

**Motivating lines, verbatim:**

```
919:  if (io.out.length) process.stdout.write(`${io.out.join("\n")}\n`);
920:  if (io.err.length) process.stderr.write(`${io.err.join("\n")}\n`);
968:    process.exit(main(process.argv.slice(2)));
```

**Issue:** writes to a pipe are asynchronous in Node; `process.exit()` on the next tick can drop buffered bytes. The paths that matter most are safe — the restore script redirects to files (`> "$RESTORE_OUT_DIR/refdata.sql" 2> "$RESTORE_OUT_DIR/refdata.err"`, `:1061-1062`) and both CI assertion steps redirect to `$REFDATA_*_LOG`, and file writes are synchronous. The exposed paths are the two bare `run: node scripts/extract-reference-inserts.mjs --self-test|--audit` steps, whose stdout is the Actions log pipe, and `spawnSync` in `runLeg`. Output there is well under a pipe buffer today, so this is low-likelihood — I am reporting it because the failure shape (exit 1 with no reason printed) is precisely the "could not measure is never a pass" mode the file is built around.

**Fix:** `process.exitCode = main(process.argv.slice(2));` and let the event loop drain, or keep `process.exit` but flush explicitly.
