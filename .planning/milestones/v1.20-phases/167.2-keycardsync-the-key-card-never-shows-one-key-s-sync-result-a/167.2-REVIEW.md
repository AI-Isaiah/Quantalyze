## Critical Issues

### CR-01: After a give-up, `Use & Sync` on another key inherits the still-running job of the previous key and shows its result as the new key's

**File:** `src/components/strategy/ApiKeyManager.tsx` — the `no_result` arm of `handleSyncStatusChange`, the `unconfirmed` arms of `handleSyncTrades`, the `disabled={!!syncingKeyId || loading}` on Resync / Use & Sync; `src/components/strategy/SyncProgress.tsx` — the KCS-02 evidence gate and `jobQueueSaysChainSettled`
**Issue:** `no_result` (KCS-22) and `unconfirmed` (KCS-03) both call `endAttempt`, which clears
`syncingKeyId`. The copy says it outright: *"The sync may still be running"*. Every key's
`Use & Sync` becomes clickable again at once. The evidence the next attempt relies on is scoped to
the STRATEGY, never to the key:
- evidence (a) is a `computing` analytics row;
- evidence (b) is a moved `computed_at`;
- KCS-18 asks whether any factsheet-chain job is in flight.

The enqueue behind `/api/keys/sync` dedupes on (target, kind) over
`pending/running/done_pending_children` and returns the EXISTING job id. See
`_enqueue_compute_job_internal` as described in `analytics-service/services/job_worker.py`
(REUSE-01), and `process_key.py`'s `process_key_long` enqueue.

Concrete scenario (RESEARCH P2 says a crawl longer than 120 s is common):
1. Key K1 is resynced. At 120 s the panel shows "No result yet", while K1's `process_key_long` is
   still `running`.
2. The owner clicks `Use & Sync` on key K2. `handleLinkKey` relinks the strategy to K2.
3. The baseline is read, and the enqueue returns `ok: true`, served by K1's deduped job.
4. The poll reads `computing` (set by bridge branch (a)), so `sawComputingRef` is set.
5. K1's chain finishes, and `jobQueueSaysChainSettled` sees nothing in flight.
6. The panel, whose subject and `lastAttemptedKeyId` are K2, renders "Up to date". It also uses
   K2's `last_sync_at`.

K2 was never fetched, and the strategy is now linked to K2. That is exactly "one key's sync result
shown as another key's", the defect named in the phase title.
**Fix:** Refuse to start an attempt on a key other than the last attempted one while a chain job
is live. In `handleSyncTrades`, before registering the attempt (or before the link), read
`/api/strategies/[id]/sync-progress` once when `lastAttemptedKeyIdRef.current !== keyId`. If
`isFactsheetJobInFlight(jobStatus)` is true, or the read is degraded or failed (fail closed), do
not start. Show key-scoped authored copy instead, for example "Wait for the running sync to finish
before syncing another key" (a new UI-SPEC row, pinned). A lighter alternative is to keep link
controls on other keys disabled after `no_result`/`unconfirmed` until a reload. Either way, add a
test that fails without the guard: no_result on K1, then `Use & Sync` on K2 while the job route
says `running`, expecting no link update and no enqueue.

### CR-02: `KCS23-COMPOSITE` tells the owner the composite reads from keys it does not use (orchestrator item 2)

**File:** `src/components/strategy/key-card-copy.ts` — `COMPOSITE_CARD_NOTE`; `src/components/strategy/ApiKeyManager.tsx` — `loadKeys` (`from("api_keys").select(API_KEY_USER_COLUMNS).order(...)`, no strategy filter) and the `keyShape === "composite"` render
**Issue:** On a composite card the note says *"This composite strategy reads from every key
below"*. But `loadKeys` lists EVERY `api_keys` row the owner can read, which RLS limits to the
owner and nothing else. Scenario: an owner has five keys and a two-key composite. The card claims
all five feed it. Each non-member key's "Sign-in failed" pill now sits under a sentence saying the
composite reads from that key. That implies the composite is affected, which is the opposite of
the owner-facing honesty this phase exists for. The `/strategies` list, in the same phase, already
computes the true member set (`feedingKeyIdsByStrategy`), so the two surfaces disagree about the
same strategy. The string shipped verbatim because the UI-SPEC locked it, and `deferred-items.md`
records it. But a locked string that is false is still a false user-facing claim. It is shipped by
this diff, and the repo policy says user-facing defects block.
**Fix:** Prefer filtering over re-wording. With the strategy id and `keyShape === "composite"`,
read the member ids on the RLS-scoped client, which `strategy_keys_owner` permits with no
migration:
```ts
const { data: members } = await (supabase as unknown as SupabaseClient)
  .from("strategy_keys").select("api_key_id").eq("strategy_id", strategyId);
```
Then render only those keys. Fail closed: if the member read fails, render no note and log. If
the owner must still see non-member keys, render them in a separate, labelled group. Otherwise
re-word the note in the UI-SPEC and its pin so it is true of the list as rendered. Either way, add
a test with one member key plus one non-member key that fails on the current copy.

### WR-03: A failure written by another job between the baseline read and the enqueue is shown as this attempt's "Sync failed" (orchestrator item 4)

**File:** `src/components/strategy/SyncProgress.tsx` — the `if (next === "error") { onStatusChange?.(next, { computationError }); return; }` short-circuit after the evidence gate; `src/components/strategy/ApiKeyManager.tsx` — `readEvidenceBaseline` is called BEFORE `enqueueExchange`
**Issue:** The window is not microseconds. The baseline is read before the `fetch`, and the enqueue
exchange can legitimately take up to `ENQUEUE_BOUND_MS` (180 s; 36 s and 126 s are pinned as
normal). Scenario:
1. A recurring or other-tab chain job reaches `failed_final` during that enqueue.
2. `sync_strategy_analytics_status` writes `failed` with a fresh `computed_at`, because this
   attempt's job does not exist yet, so the in-flight count is 0.
3. This attempt's job is then enqueued as `pending`, but no mark RPC runs until its handler
   finishes, so the row stays `failed`.
4. The first poll sees `failed` with a moved `computed_at`. Evidence (b) passes, and the `error`
   arm forwards WITHOUT the KCS-18 job-state read.

The card then says "Sync failed" with another job's `computation_error` and offers Retry, while
its own job is queued. A Retry during a `failed_retry` backoff inserts a second job (F-3). Success
is safe, because KCS-18 sees the pending job. Failure is not.
**Fix:** Apply the job-state check to `error` too, with the opposite polarity. Forward an evidenced
`failed` only when `jobQueueSaysChainSettled` is true, meaning no chain job is in flight. While
this attempt's job is pending, the failure cannot be its own. Keep failing closed: an unreadable
job state holds the terminal and the poll continues to the cap (`no_result`). Add a test that fails
without the check: a moved `computed_at` plus `failed`, with the job route answering `pending`, and
expect no forward.

### WR-04: A link update that answers after `LINK_UPDATE_BOUND_MS` can re-link the strategy behind a newer attempt (orchestrator item 5)

**File:** `src/components/strategy/ApiKeyManager.tsx` — the `linkOutcome === "timed_out"` branch of `handleSyncTrades` (`await linked`), and `handleLinkKey` (unconditional `router.refresh()`)
**Issue:** Plan 05's late-answer handling is sound for STATE. `endAttempt` and the `attemptRef`
checks stop every write, nothing but the closure is retained, and a late setState after unmount is
a React no-op. It does not cover the late DATABASE write. The request is not aborted, by design.
Scenario:
1. `Use & Sync` on K1 hangs, and at 15 s the card shows "Sync not started".
2. The Resync / Use & Sync buttons are re-enabled immediately.
3. The owner clicks `Use & Sync` on K2. The K2 link lands, and the K2 enqueue goes out.
4. The stalled K1 `update({ api_key_id: K1 })` then reaches PostgREST, and the strategy is linked
   to K1 again.
5. K2's job syncs whatever `strategies.api_key_id` the handler reads, while the panel's subject is
   K2.

The KCS03-LINK copy says "Reload this page to check which key is linked before you sync again",
but nothing enforces that. The late `handleLinkKey` also fires its own `router.refresh()`
regardless of liveness.
**Fix:** Verify the link from the server before the enqueue. Widen the baseline read to
`select("computed_at, strategies!inner(api_key_id)")`, or do a separate bounded read of
`strategies.api_key_id`. If it is not `attempt.keyId`, end the attempt as `unconfirmed` or
`link_bound` without enqueueing. Separately, move `router.refresh()` out of `handleLinkKey` into
the live-attempt path, so a late link cannot refresh the page.

### WR-05: `Delete` on a composite card silently removes the key from an unpublished composite, which the new note says this card cannot do

**File:** `src/components/strategy/ApiKeyManager.tsx` — `handleDeleteKey` (not gated on `keyShape`) and the Delete modal copy; `supabase/schema/baseline.sql` — `strategy_keys_api_key_id_fkey ... ON DELETE CASCADE`, `enforce_api_keys_published_composite_integrity` (guards `status = 'published'` only)
**Issue:** KCS-23 treats changing a composite's membership from this card as a data-integrity
defect, and the new note says *"Keys are not linked or synced from this card: contact support … to
change which keys it uses"*. Yet `Delete` on a member key of a DRAFT or pending-review composite
cascades its `strategy_keys` row away. Consequences:
- The next stitch computes over fewer members.
- Deleting the last member drops the member count to 0, so the strategy stops being a composite
  and becomes "unlinked" (`resolveStrategyShape`).
- The modal promises *"Trade data already imported will not be affected"*.

The phase's measured trigger was exactly an unpublished composite. This is pre-existing, and the
published case is guarded by the trigger. But this phase authored copy that makes the gap an
explicit false statement.
**Fix:** On `keyShape === "composite"`, for member keys (this needs CR-02's member read), either
disable `Delete` with the same support pointer, or show a composite-specific confirm that states
the consequence ("Deleting this key also removes it from this composite strategy"). That confirm
needs a new UI-SPEC row and pin. Add a test that fails if a member key's Delete fires with no
composite-specific confirm.

### WR-06: KCS-22's "no Retry while a job may be live" is defeated by Resync, which re-enables immediately

**File:** `src/components/strategy/ApiKeyManager.tsx` — the `no_result` and `unconfirmed` arms (`endAttempt` clears `syncingKeyId`, so `Resync` is enabled); `ApiKeyManager.test.tsx` WR-02 pins "Resync … usable again"
**Issue:** KCS-22 removes Retry on `no_result` because *"a re-POST during `failed_retry` inserts a
second job (F-3)"*. `Resync` on the same key is the same re-POST, and it is clickable the moment
the panel says "No result yet". Scenario: the job goes to `failed_retry` at minute 3, and the owner

behaviour.
**Fix:** Share CR-01's pre-registration job-state read. Refuse a new attempt while `jobStatus` is

`no_result`/`unconfirmed` until the job route reports nothing in flight. Update the WR-02 pin with
a reason that says why.

## Info

### IN-01: The `eslint-disable` on `loadKeys` is safe today but is a latent stale-closure trap (orchestrator item 6)

**File:** `src/components/strategy/ApiKeyManager.tsx` — `loadKeys` (`useCallback(..., [currentKeyId])` with `// eslint-disable-next-line react-hooks/exhaustive-deps`), `retireWithheldSuccess`
**Issue:** `loadKeys` captures the `retireWithheldSuccess` of the render in which `currentKeyId`
last changed. Today that is harmless:
- The call passes an explicit argument, so the default `panelSubjectUntrusted`, the only
  render-scoped value, is never read.
- The body touches only the stable `setSyncStatus`.
- The subject comes from `lastAttemptedKeyIdRef`.

So the risk is not live. It becomes live the moment anyone adds a render-scoped read to
`retireWithheldSuccess`, for example `keys` or `syncingKeyId`, and the disable hides the lint that
would catch it.
**Fix:** Extract the core into a stable callback and depend on it honestly:
```ts
const retireSuccessIf = useCallback((untrusted: boolean) => {
  if (untrusted) setSyncStatus((p) => (isComputedAnalytics(p) ? "idle" : p));
}, []);
```
Call `retireSuccessIf(...)` from `loadKeys`, with `[currentKeyId, retireSuccessIf]` deps and no
disable. Keep `retireWithheldSuccess()` as a thin wrapper that reads `panelSubjectUntrusted`.

### IN-02: An unmount during a live attempt leaves `attemptRef` set, so its continuations still read the network and call `router.refresh()`

**File:** `src/components/strategy/ApiKeyManager.tsx` — no unmount cleanup for `attemptRef`
**Issue:** If the owner navigates away mid-attempt, the handler's continuations still run: the
baseline read, the enqueue, `loadKeys`, and `router.refresh()`, which then refreshes whatever route
is current. They run because `attemptRef.current === attempt` still holds. The state writes are
React no-ops. This is pre-existing, and plan 05 made it no worse.
**Fix:** `useEffect(() => () => { attemptRef.current = null; }, [])`, so every liveness guard drops
the continuation.

### IN-03: A stale `stitch_composite` row wins job selection forever on a composite already converted to single-key

**File:** `src/lib/compute-state.ts` — `selectFactsheetJob` (stitch-PREFERRING)
**Issue:** KCS-23 exists because `Use & Sync` could turn a composite into a single-key strategy. A
strategy converted that way before this phase still has its old stitch rows, which are retained
for 30 or 90 days. Selection prefers the latest stitch over any newer chain row. So the owner page
states the old stitch's state: "composite … stopped reporting progress", or a red permanent
failure. KCS-18's success gate also reads the old `done` stitch as "settled" while the
single-key chain runs, which reopens the warned-row mid-chain early success. How often this
happens depends on the data, and it is bounded by retention.
**Fix:** Prefer the stitch only when it is at least as new as the newest chain row, or when the
strategy currently has `strategy_keys` members. Alternatively, measure on PROD, owner-scoped and
read-only, whether any strategy has `api_key_id` set together with a stitch row, before deciding.

### IN-04: `/strategies` makes an RPC per published uncomputed row whose answer is discarded

**File:** `src/app/(dashboard)/strategies/page.tsx` — `shareNotes` (`recipientShareNote("public-url", …)` ignores the arm)
**Issue:** For `public-url` mode the note is always `PUBLIC_URL_NOTE`, but `readRecipientArm`
still runs a 100-row RPC for the row. The 09 SUMMARY accepts this for "a single code path", but it
is dead work, and a failure in it logs an error about a value nobody reads.
**Fix:** Skip `readRecipientArm` when `isPublishedStatus(s.status)` is true.
