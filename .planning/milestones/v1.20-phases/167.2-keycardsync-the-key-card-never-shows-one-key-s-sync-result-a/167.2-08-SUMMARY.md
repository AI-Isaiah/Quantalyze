# Phase 167.2 Plan 08: The share page's two neutral arms over a bounded compute_jobs read Summary

**A share link whose factsheet is not built now reads the matched strategy's compute jobs and says "being prepared" only while a job will still do work. A failed, stalled, finished-without-payload, never-started or unreadable compute says "This factsheet isn't available yet … Check with the person who shared this link before trying again." It no longer says "try again in a few minutes". The read is bounded by the matched strategy id alone and projects five fields.**

## Accomplishments

- **KCS-11:** the `!payload` branch, after its existing `console.warn` breadcrumb, calls `readShareComputeState(match.strategy_id)`. That function runs `.from("compute_jobs").select("status, kind, created_at, claimed_at, member_progress_at:metadata->>member_progress_at").eq("strategy_id", strategyId).order("created_at", { ascending: false }).limit(COMPUTE_STATE_READ_LIMIT)` on the admin client. It reshapes each row into `ComputeJobRow` (`metadata: { member_progress_at }`) so `isStitchStalled` applies unchanged, then calls `deriveComputeState` with `readExhaustive: rows.length < COMPUTE_STATE_READ_LIMIT` and `nowMs: Date.now()`.
- **Fail closed:** a PostgREST `{ error }`, a non-array answer and a throw each log `[factsheet-share/page] compute-state read failed` with `{ message }` only, and derive `unreadable`. The page maps anything that is not `in_progress` to `not_available`, and `EmptyStateCard` receives `SHARE_CARD_COPY[arm].heading` / `.body`.
- **SECURITY BOUNDARY header:** "Two reads" is now three. Read (3) is documented with its bound, its five fields, the fields it never selects, and the fact that it runs only when the payload is pending. Every existing paragraph is kept.
- **Tests:** the admin mock gains a `compute_jobs` arm that records the select string, every `eq` pair, the order and the limit. The `token page read an arbitrary table` throw is kept for every other table. The existing pending pin now queues a running `process_key_long` row and keeps its `isn&#x27;t ready yet` anchor as arm (a).

## Decisions Made

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] A non-array compute_jobs answer with no error is unreadable**
- **Found during:** Task 1
- **Issue:** The plan named `{ error }` and a throw. A `{ data: null, error: null }` answer would otherwise read as zero rows, an exhaustive window and `never_started`, which is a state claim with no evidence behind it. It lands on arm (b) either way, but the log would be silent.
- **Fix:** treated as a read failure. It is logged by message and derives `unreadable`. This matches plan 07's owner read.
- **Files modified:** `src/app/factsheet-share/[token]/page.tsx`
- **Committed in:** `baac7438c`
