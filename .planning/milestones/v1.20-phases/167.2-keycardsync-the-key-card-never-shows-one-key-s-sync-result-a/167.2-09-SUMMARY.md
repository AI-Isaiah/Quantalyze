# Phase 167.2 Plan 09: The /strategies key pill over every feeding key, and the recipient note beside each uncomputed row's share control Summary

**A /strategies row fed by a revoked or sign-in-failed key, whether that key is the row's `api_key_id` or any `strategy_keys` member of a composite, now carries the key card's own `AllocatorSyncStatus` pill and remedy line, one line per distinct status. A row with no computed factsheet also says, beside its share control, what a recipient of that link sees right now. A healthy, computed row renders nothing new.**

## Accomplishments

- **KCS-06 (S4):** `page.tsx` reads `strategy_keys` (`strategy_id, api_key_id, seq`, `.in("strategy_id", strategyIds)`) through the type-only `SupabaseClient` cast the composite members route uses. It then reads `api_keys` with the allowlisted projection `id, exchange, sync_status, sync_error, last_sync_at` for the union of `api_key_id` and every member's key. The module-level `untrustedKeyLines` keeps the keys where `isUntrustedKeySyncStatus` holds and groups them by status in first-seen order over `[api_key_id, ...members by seq]`. Each line renders `untrustedKeyCaption` and mounts `AllocatorSyncStatus` with the first key's `sync_error`, `last_sync_at` and `exchange`, exactly as the key card does.
- **KCS-12 (S5):** the strategies select embeds `strategy_analytics ( computation_status )`, normalised by `computationStatusOf` from an object or a one-element array. Every row failing `isComputedAnalytics` calls `readRecipientArm`, which runs `get_user_compute_jobs` with `{ p_strategy_id, p_limit: COMPUTE_STATE_READ_LIMIT }` under `Promise.all` and derives through `deriveComputeState` and `recipientArm`. The note is `recipientShareNote(shareAffordanceMode(isPublishedStatus(status)), arm)`. It renders after any S4 lines as `<p className="text-xs text-text-muted">`.
- **Fail loud, never guess:** an `api_keys` error logs `[strategies/page] api_keys read failed` and renders no mark. A `strategy_keys` error logs `[strategies/page] strategy_keys read failed`, and the row is judged on `api_key_id` alone. An RPC error, a non-array answer or a throw logs `[strategies/page] compute-state read failed` with `{ id, code, message }` and renders `KCS12-UNREADABLE`.
- **Unchanged:** `ShareableLink`'s props and position, the row's name link to `/strategies/{id}/edit`, and every existing element above the band. No number is rendered and no claim about the strategy's numbers is made.

## Decisions Made

See `key-decisions` in the frontmatter. The predicate decision in full: "has a computed factsheet" is `isComputedAnalytics(computation_status)`. It is the first gate `fetchAndBuildPayload` applies (STALE-01), so every row the list calls uncomputed is one the builder refuses, and the note never fires on a row whose factsheet builds for that reason. The opposite direction is not fully decidable from this page. That gap is the residual below.

## Verification residual (user-facing, routed by the orchestrator)

**A computed row whose series cannot build reads as "has a factsheet" on the list and shows no note, while its recipient sees the pending page.** This is the KCS-12 known limit, recorded and not fixed.

- **When it happens:** after normalisation the series has fewer than two dated points, the series is empty, or a composite has a read-path data defect.
- **Why this page cannot close it:** the builder decides it from the full `daily_returns` / `returns_series` jsonb. For a composite it also reads `strategy_analytics_series` and `csv_daily_returns` on the ADMIN client, and `strategy_analytics_series` is deny-all under RLS. The owner's request client cannot evaluate that, and no scalar column records the outcome. Checking it here would mean pulling whole series into a list render, or an admin read on a list page. The plan ruled both out (D-04: owner-scoped reads only, no factsheet path).
- **Destination:** this phase's verification residual. The orchestrator routes it to a named phase at verification. This plan did not edit ROADMAP.md or TODOS.md for it.
