## Part 2 — new findings introduced by the fix round

### R2-H1 (HIGH) — M-7's history cross-check locks an ordinary unlinked strategy out of Add Key and Use & Sync, deterministically and silently

- **Where:** `src/lib/strategy-shape.ts`, `compositeHistoryOf` (`return read.readExhaustive ? "none" : "unreadable"`) and `resolveStrategyShape` (`if ((input.compositeHistory ?? "none") !== "none") return "unknown"`). Consumers: `src/app/(dashboard)/strategies/[id]/edit/page.tsx`, `EditStrategyPage` (the `members.keyIds.length === 0 && !strategy.api_key_id` arm), and `src/app/factsheet/[id]/v2/page.tsx`, `readOwnerPendingStatus`.
- **Mechanism:** `readOwnerComputeJobs` re-asks at the 1000-row cap ONLY when the first window is full AND holds no chain row (`isWindowFullWithoutFactsheetJob`). When the first 100 rows include any chain row, there is no re-ask, `readExhaustive` is `false` and `windowFull` is `false`. `compositeHistoryOf` then finds no stitch in those rows and answers `"unreadable"`, so `resolveStrategyShape` answers `"unknown"`.
- **Scenario:** an owner deletes the key linked to an active single-key strategy (for example while rotating it). `strategies.api_key_id` is `ON DELETE SET NULL` (initial schema), so the strategy becomes unlinked with zero members. `handleDeleteKey` calls `router.refresh()`, and the edit page re-renders server-side. The strategy has ≥100 `compute_jobs` rows in retention: daily recurring kinds plus the chain rows of past syncs (RESEARCH P11 is the reason the window is 100 at all). The card flips to `keyShape === "unknown"`. **Add Key, Resync and Use & Sync all disappear.** The card says `SHAPE_UNKNOWN_CARD_NOTE` ("…Reload this page to try again"), but a reload reproduces the same state on every render until retention trims the rows below 100. The owner cannot re-link any key to the strategy from its own card. The owner factsheet derives the same `"unknown"` shape, so its remedy changes too.
- **Why it is silent:** this path is a *successful* read. `EditStrategyPage` logs only `jobs && !jobs.ok` or a throw, and `captureToSentry` is called only on the member-read failure arm (H-2). A non-exhaustive history, a `"seen"` history and a failed history read all produce `"unknown"` with **no capture**, and the non-exhaustive case produces **no log at all**. So the H-2 defect ("failing closed silently") comes back through M-7's door.
- **Tests:** `edit/page.test.tsx` has `M7-STITCH-HISTORY` and `M7-NO-HISTORY`, both with one-row doubles. No test feeds a 100-row, non-exhaustive, stitch-free history, so the lockout is untested in both directions.
- **Fix:**
  1. Make "no stitch" provable instead of inferring it from exhaustiveness. When the read is not exhaustive and no stitch is in it, re-ask once at `COMPUTE_STATE_READ_LIMIT_MAX`, as M-5 does. Only a read that is still non-exhaustive at the cap should be `"unreadable"`. Better still is a kind-scoped question: the RPC has no kind filter, so either add one in a later phase or accept the 1000-row re-ask here.
  2. Capture every path that produces `"unknown"` on the edit page, not only the member-read failure: `captureToSentry(new Error("composite history <seen|unreadable>"), { tags: { route: "strategies/edit/page", stage: "composite-history" } })`. Also log the non-exhaustive case.
  3. Add a test: zero members, no `api_key_id`, a 100-row history with chain rows and no stitch, must give `"single"` (after the re-ask) and must never give `"unknown"`.
  4. For the deterministic `"seen"` case (a former composite that is now unlinked), "Reload this page to try again" is a false remedy. Decide whether it should name support, as `COMPOSITE_CARD_NOTE` does.

### R2-M1 (MEDIUM) — A late transport-level failure of the enqueue now shows a definitive "Sync failed" for a request whose server-side outcome is unknown

- **Where:** `src/components/strategy/ApiKeyManager.tsx`, `handleSyncTrades`, the M-1 late-answer block (`catch (lateErr) { … if (stillShown()) { setSyncStatus("error"); setSyncError(message) } }`), together with `syncFailureMessage` (a non-JSON body returns `SYNC_UNAVAILABLE_COPY`).
- **Scenario:** `/api/keys/sync` has `maxDuration = 300` and `ENQUEUE_BOUND_MS` is 180 s, so a late answer can only arrive between 180 s and 300 s. The likeliest late answers in that window are not route verdicts:
  - the platform's `FUNCTION_INVOCATION_TIMEOUT` 504 at 300 s, with a non-JSON body, which becomes *"We couldn't start the sync. Your key is saved — retry in a moment…"*;
  - a rejected `fetch` (the laptop slept, the network dropped), which becomes `TypeError: Failed to fetch`.

  In both cases the upstream enqueue may already have committed, because the route was waiting on the analytics service when it was killed. Before M-1, the panel kept KCS03-ENQUEUE's honest *"it may still be running"*. Now it overwrites that with "Sync failed" plus a claim that the sync did not start. The Retry it offers is then refused by the CR-01 gate (`chain_in_flight`), so the owner sees "Sync failed", clicks Retry, and is told "a sync for this strategy is still running". The two panels contradict each other, and the only record is a generic `late-enqueue-answer` warning that does not distinguish a route verdict from a transport failure.
- **Fix:** apply a late rejection only when it is a *route verdict*: a response the route itself produced, with a JSON `error` / `human_message` body. `enqueueExchange` could throw a tagged error class for `!res.ok` with a JSON body. Keep the `unconfirmed` / `enqueue_bound` panel for a thrown `fetch`, a non-JSON 5xx, or a 504. Add the error class to the `late-enqueue-answer` capture as a tag (`kind: "verdict" | "transport"`).

### R2-M2 (MEDIUM) — M-7's history-read failures on the edit page reach the console only, and the non-exhaustive case not even there

This is the observability half of R2-H1. I list it separately because it stands even if the lockout is fixed by the re-ask.

- **Where:** `EditStrategyPage`, the `readOwnerComputeJobs` try/catch (`console.error("… composite history read threw" / "… failed")`).
- **Scenario:** the job RPC errors or throws on the edit page of an unlinked strategy. The card loses every link control (`"unknown"`), exactly as in H-2, but unlike H-2's member-read arm nothing reaches Sentry. The owner factsheet captures its own failed job read, so the two surfaces again disagree on observability, which is M-6's original complaint.
- **Fix:** `captureToSentry(err-or-new Error(jobs.message), { tags: { route: "strategies/edit/page", stage: "composite-history" } })` in both arms, with tags only (the id stays in the log), as H-2 does.

### R2-L1 (LOW) — The pre-attempt gate turns a deterministic DEGRADED answer into a permanent refusal that says "Try again in a moment"

- **Where:** `readChainJobState` (`degraded` → `unreadable`) → `handleSyncTrades` gate → `PANEL_STOP_COPY.chain_unreadable`.
- **Scenario:** two of the route's three new DEGRADED cases are deterministic. One is `compute-jobs-window-full`, a window still full at 1000 rows with no chain row. The other is `compute-jobs-bad-status`, a status outside `COMPUTE_JOB_STATUSES`, which would appear if a future migration adds a status value before this list learns it. For such a strategy EVERY Resync, Use & Sync, post-add sync and Retry is refused with *"we could not check whether a sync … is still running. Try again in a moment."* Retrying can never help. It is captured, once per click (`pre-attempt-job-state` on the card, and `compute-jobs-*` from the route), so it is not silent in production. To the owner, though, it is an undiagnosable dead end.
- **Fix:** carry the route's degrade `stage` in the DEGRADED body (for example `degradedReason`, a non-sensitive closed string), and choose copy that does not promise a retry for the deterministic reasons. Alternatively, keep `COMPUTE_JOB_STATUSES` pinned by a test against the `compute_jobs_status_check` constraint, so the bad-status case cannot appear silently from a migration.

### R2-L2 (LOW) — The M-3 give-up attributes any `failed_final` chain to this attempt, including a previous run's when nothing new was enqueued

- **Where:** `SyncProgress` `onError` (`read.kind === "settled" && read.jobStatus === "failed_final"` → `onStatusChange("error", { computationError: null })`). Source of the case: `/api/keys/sync` returns `ok: true` for `code: "WIZARD_DUPLICATE"` with `queued: upstream.queued === true`, which can be `false`, and `isSyncEnqueued` checks only `ok === true`.
- **Scenario:** a duplicate submission answers `ok: true, queued: false`. The card enters `computing` with no new job. The newest chain row is the previous run's `failed_final`. At the cap the give-up reports "Sync failed" (no detail) for an attempt that enqueued nothing. Before M-3 this was `no_result`. KCS-02's rule is that a terminal is forwarded only with per-attempt evidence, and this path forwards one with none. This is rare (it needs `queued: false` plus a failed previous chain), and a Retry is honest afterwards because the gate reads `settled`.
- **Fix:** forward `failed_final` from the give-up only when the selected job is provably this attempt's. For example, have the projection carry the job's `created_at`, and require it to be later than the attempt's start as recorded by the server clock via the enqueue response. Otherwise keep `no_result`. Separately (and pre-existing), treat `queued: false` as "nothing enqueued" in `isSyncEnqueued`.

### R2-L3 (LOW) — A give-up with no clean read at all is not captured

- **Where:** `useStrategySyncPoller` (`onErrorRef.current(sawCleanRead ? "cap" : "unreadable")`), consumed by `SyncProgress` `onError`.
- **Scenario:** the session expires mid-poll. All 40 reads error, each logged to the console, and the panel shows `PANEL_STOP_COPY.unreadable`. The copy is now honest (M-3). Nothing reaches Sentry, though, although "the panel could not read `strategy_analytics` for a whole attempt" is exactly the operational signal M-6 asked to surface.
- **Fix:** in `SyncProgress` `onError`, when `reason === "unreadable"`, `captureToSentry(new Error("the sync panel could not read the analytics row for a whole attempt"), { level: "warning", tags: { component: "SyncProgress", stage: "poll-unreadable" } })`.

### R2-L4 (LOW) — WR-05's Delete refusal: the membership read failure is console-only, and an RLS-filtered zero lets the cascade through

- **Where:** `ApiKeyManager.tsx`, `handleDeleteKey` (the `strategy_keys` `.eq("api_key_id", keyId)` read).
- **Scenario (a):** the read errors. The Delete is correctly refused with `DELETE_FAILED_COPY`, but only `console.error` records it. Every other read added this round is captured.
- **Scenario (b):** this is the M-7 class again. RLS on SELECT filters instead of erroring, so a regressed `strategy_keys_owner` returns `[]` with no error, and the Delete proceeds and cascades the key out of a draft composite, which is the outcome WR-05 exists to prevent. The database's publish guard still protects a published composite.
- **Fix:** (a) capture with `tags: { component: "ApiKeyManager", stage: "delete-membership-read" }`. (b) Moving the guard server-side (the delete RPC refusing a key with memberships) is the real fix. It needs a migration, so route it with WR-02 rather than doing it in this phase.

## What is done well this round

- The whole class of "could not tell" answers on the sync-progress route now fails in one direction, and I checked every consumer: nothing reads DEGRADED as settled or as failed.
- `readChainJobState` never throws and is bounded at 15 s. Its `in_flight` / `settled` / `unreadable` split is used identically by the gate, the terminal gate and the give-up.
- Every liveness guard added this round (`attemptRef.current !== attempt`, `stillShown`, the `computingTokenRef` token, and the IN-02 unmount cleanup) is checked after each await. I found no continuation that writes panel state for an ended attempt.
- Every Sentry capture I read passes tags only, and `captureToSentry` scrubs the message.
