## Summary

This phase adds a disclosure and changes no money math. The number an allocator sees as their holdings-derived "headline AUM" is `liveHoldingsSum` in `ScenarioComposer.tsx`. It is computed by one `useMemo` that walks `scenario.draft.toggleByScopeRef`, keeps enabled `holding:` refs, resolves each through `holdingByRef`, and drops holdings whose key is outside `contributingApiKeyIds` whenever that set is non-empty (`narrowToModelledBook`). It then sums `holdingEquityContributionLocal(h)`. Everything the marker needs is already on the client: `payload.apiKeys[].sync_status` (tenant-scoped by `getUserApiKeys`, `.eq("user_id", userId)`), `holdingsSummary[].api_key_id`, and `contributingApiKeyIds`. No SSR, SQL or Python change is required `[VERIFIED: codebase read]`.

The cleanest way to satisfy D-04's single-pass rule and D-15 pin 5 (the test double) is a **pure helper module** under `src/app/(dashboard)/allocations/lib/`. It classifies every enabled holding in one loop into three buckets: *summed*, *summed and untrusted*, and *excluded by the key-set narrowing and untrusted*. The composer's `liveHoldingsSum` becomes `summary.total`, and the helper's own unit test can `vi.mock("@/lib/closed-sets")` without disturbing the 15,367-line composer test file. The same pass yields D-06 option (b)'s `$Y` for free, so the D-06 task only adds a render branch.

The re-enumeration **refutes D-01's claim that the list is complete**. D-01's composer-field and override-note findings are confirmed. So are its non-sites: `KpiStrip` has no AUM cell, `liveBaselineMetrics.aum` is unrendered, `deriveMandateGates` has only a test caller, and the Overview's AUM reads `portfolio_analytics.total_aum`, which the Python service sums from strategy AUMs. **But the Holdings tab renders two more holdings-derived dollar totals that include untrusted-key holdings:**
1. `OpenPositionsTable`'s footer, "Total unrealized P&L (equity contribution)". It sums every derivative row, and struck-through untrusted rows are included.
2. The `ExposureByClass` Gross/Net/Long/Short KPI cells. These are read straight from `allocator_holdings` with no `api_key_id` projected.

Neither of them is "AUM", and D-01 did not list either one. Under D-01's own rule ("a missed site is a plan gap, not a footnote"), the planner must put a scope call on each one (see Open Questions 1 and 2) rather than absorb them silently.

**Primary recommendation:** Extract a pure `summarizeLiveHoldings` helper (plus `holdingEquityContributionLocal`, moved beside it) into `allocations/lib/live-holdings-summary.ts`. Point `liveHoldingsSum` at `summary.total` without changing its value. Render one muted marker whose copy is built from `formatUsd` and `UNTRUSTED_KEY_SET_NOUN`, gated on the live total actually being displayed. Put D-06 (b) behind its own `checkpoint:decision` task that only adds a render branch over `summary.excludedUntrusted`.

### P2. How `liveHoldingsSum` is computed (verbatim anatomy)

From `ScenarioComposer.tsx`, symbol `liveHoldingsSum` `[VERIFIED: read this session]`:

```ts
const liveHoldingsSum = useMemo(() => {
  const contributing = new Set(payload.contributingApiKeyIds ?? []);
  const narrowToModelledBook = contributing.size > 0;
  let sum = 0;
  for (const [scopeRef, on] of Object.entries(scenario.draft.toggleByScopeRef)) {
    if (!on) continue;
    if (!scopeRef.startsWith("holding:")) continue;
    const h = holdingByRef.get(scopeRef);
    if (!h) continue;
    if (narrowToModelledBook && !contributing.has(h.api_key_id)) continue;
    sum += holdingEquityContributionLocal(h);
  }
  return sum;
}, [scenario.draft.toggleByScopeRef, holdingByRef, payload.contributingApiKeyIds]);
```

- `holdingByRef` is a `Map` built from the **mode-gated** `holdingsSummary`, which is `[]` in blank mode. It is keyed by `buildHoldingRef({ venue, symbol, holding_type })`, not by key. The SSR (`derivePhase07Fields`, `holdingsMap` keyed by `holdingScopeKey`) already collapses to one row per venue:symbol:type triple, and each row carries exactly one `api_key_id`, the latest-`asof` writer's. So **each holding maps to exactly one key**, and the untrusted join is per holding, never ambiguous.
- `holdingEquityContributionLocal`: for a derivative it returns `unrealized_pnl_usd ?? 0` (non-finite gives 0); for spot it returns `value_usd` (non-finite gives 0). It is a module-private function, not exported, and is also used by the `equityByApiKeyId` memo. Its docblock explains why it is duplicated from the `server-only` SSR `holdingEquityContribution`.

### P3. Which untrusted statuses can reach the summed set (D-05, verified)

`src/lib/queries.ts` `[VERIFIED: read this session]`:

```ts

  return (
    key.is_active && key.sync_status !== "revoked" && key.disconnected_at == null
  );
}
...
const eligibleKeyIds = apiKeys.filter(isPerKeyDailiesEligibleKey).map((k) => k.id);
...

const bookEntryGateSatisfied = contributingApiKeyIds.length > 0;
```

- `revoked` never reaches `contributingApiKeyIds`. In book mode (`usePerKeySources = entryMode === "book" && bookEntryGateSatisfied`) `contributing.size > 0`, so a revoked key's holdings are **skipped** by `liveHoldingsSum`. The only way a revoked holding enters the sum is the `contributing.size === 0` degrade branch. Its comment calls that branch unreachable in production, but the payload-read path can hit it. Writing the marker against the whole predicate covers that branch automatically (D-05).
- `sign_in_failed`: an active, non-disconnected, non-strategy-linked key with a non-empty per-key series **is contributing**, so its holdings **are summed**. This is the live case the marker exists for.
- `sign_in_failed` without a series (allocator-eligible, not contributing) is excluded from the sum. It is counted in the existing `scenario-aum-modelled-note` "Models N of M keys" disclosure as one of the M−N.
- Soft-disconnected keys (`disconnected_at != null`) are excluded from eligibility whatever their status. If their status is not untrusted, neither `$X` nor `$Y` sees them. That is correct: disconnecting is a deliberate user act, not a trust failure. It is out of scope, but a planner should know it.

### P4. D-06 option (b): precisely what `$Y` sums

**Definition (for the checkpoint-gated task):**

> `$Y` = Σ `holdingEquityContributionLocal(h)` over every `h` reached by the **same** loop as `liveHoldingsSum` (enabled `holding:` ref, resolved in `holdingByRef`) such that `narrowToModelledBook && !contributing.has(h.api_key_id)` (i.e. dropped by the key-set narrowing) **and** `isUntrustedKeySyncStatus(statusByKeyId.get(h.api_key_id))`.
> The render condition is "at least one such holding exists", not `$Y > 0` (the same reasoning as D-07).

Payload fields used: `scenario.draft.toggleByScopeRef`, `holdingsSummary` (via `holdingByRef`), `payload.contributingApiKeyIds`, `payload.apiKeys[].{id, sync_status}`. **No new field.**

**Refinement the founder or planner must settle inside the D-06 checkpoint (manager-side keys):** the narrowing also drops **manager-side** keys (strategy-linked, and not `own_capital`). Those are excluded because of their *role*, not their trust. If such a key is untrusted, an unrefined `$Y` would say "excludes $Y from keys needing attention" about money that would be excluded even with a healthy key.
- It **can** be removed for `sign_in_failed` manager keys. A manager-side key is identifiable from the payload as `eligibleApiKeyIds \ allocatorEligibleApiKeyIds`.
- It **cannot** be removed for `revoked` manager keys. A revoked key is in *neither* set (`isPerKeyDailiesEligibleKey` drops it before the role split), so the payload cannot tell a revoked allocator key from a revoked manager key. Separating them would need a new SSR field (reopening D-10/D-11).
- **Recommendation:** define `$Y` as above, minus known manager-side keys (`eligibleApiKeyIds \ allocatorEligibleApiKeyIds`), and **record** that a revoked manager-side key's holdings are counted in `$Y`. That is an over-disclosure, not a hidden amount, and it errs toward "nothing silently disappears". `[ASSUMED]`: it is the founder's call whether that residual is acceptable. It goes in the checkpoint's option text.

### Pattern 1: Single-pass classifier (D-04)
**What:** one loop, three accumulators. The total and its untrusted subset cannot drift because they come from the same `continue` chain.
**When:** always. Never a second loop that re-implements the filters.
**Why a pure module over extending the memo:** it can be unit-tested with a `closed-sets` test double (D-15.5) without mocking in the 15k-line composer file. It is also the natural place for D-06's `excludedUntrusted`. Moving `holdingEquityContributionLocal` there as well gives the composer's two memos (`equityByApiKeyId`, `liveHoldingsSum`) one shared definition instead of adding a fourth copy. This is the one deliberate move in the phase; update its docblock to say where it now lives.

### Pattern 2: Disclosure beside the figure (Phase 151 F2 precedent)
`scenario-aum-modelled-note` exists because "a headline money figure may not change meaning silently". The new marker is a sibling `<span data-testid="scenario-aum-untrusted-note">` in the same `mt-3 flex flex-wrap items-center gap-3` row. `[ASSUMED]`: the testid name is not fixed anywhere; the planner or UI-SPEC names it.

### Anti-Patterns to Avoid
- **A second loop for `$X`.** It violates D-04, and the two sums will drift the first time someone edits a filter.
- **`sync_status === "sign_in_failed"` (or `!== "revoked"`) anywhere new.** This is the defect 167 D-16 removed.
- **Subtracting `$X` from anything.** That is the rejected alternative (D-03).
- **Rendering on `amount > 0`.** A ≤ 0 derivative contribution would then hide the disclosure (D-07).
- **Rendering the marker when the live total is not on screen.** Examples: the field is blank because `liveHoldingsSum <= 0`, or the manual value equals the live sum so no override note shows. The marker would then qualify a number the reader cannot see (see Pitfall 2).
- **Importing `UNTRUSTED_KEY_SET_NOUN` into the *test oracle*.** Production derives from the constant (D-02). The test types the literal, following the file's own "oracle independence" rule.

## Common Pitfalls

### Pitfall 1: The marker drifts from the total
**What goes wrong:** `$X` counts a holding the total does not (or the reverse).
**Why:** two loops, or a filter added to one of them.
**Avoid:** one helper returning both. The unit test asserts `untrusted.amount` equals Σ over an independently hand-listed subset, *and* that `total` equals the pre-phase figure.
**Warning sign:** any `for (const [scopeRef` loop in the composer diff other than the one being replaced.

### Pitfall 2: D-07 and D-08 interact at the edges
**What goes wrong:** the marker renders beside an empty field ("Required to size and commit.") or beside a manual value that happens to equal the live sum. In both cases the live total is on screen nowhere.
**Why:** D-07 gates on the holding set; D-08 gates on *where the live total is displayed*. The field shows the live total only when `sanitizedManualAum === undefined && liveHoldingsSum > 0`. The override note shows it only when `sanitizedManualAum !== undefined && liveHoldingsSum > 0 && sanitizedManualAum !== liveHoldingsSum`.
**Avoid:** render condition = `entryMode === "book" && summary.untrusted.count > 0 && (fieldShowsLive || overrideNoteShowsLive)`, with both booleans computed once and reused by the existing JSX so the conditions cannot fork. Flag the `total <= 0` derivatives-book edge to the UI-SPEC. There the untrusted contribution exists but no live total is displayed, and the reader sees only "Required to size and commit." Recommendation: no marker, because it would qualify an absent number. `[ASSUMED]`, so confirm in the UI-SPEC.
**Warning sign:** a test that renders the marker with an empty `scenario-aum-input`.

### Pitfall 3: `aumInputText` is not the committed value
**What goes wrong:** the placement is keyed to the text the user is typing.
**Why:** `aumInputText` changes per keystroke. `sanitizedManualAum` changes only on commit (blur or Enter).
**Avoid:** key placement on `sanitizedManualAum` (committed state), like the existing override note.

### Pitfall 4: The fixture is vacuous for pin 5
**What goes wrong:** the test-double test passes whether or not the helper calls the shared predicate.
**Avoid:** the fixture needs a holding whose status is *trusted by the real predicate* (e.g. `"error"`, a member of `TRUSTED_OR_NEUTRAL_KEY_SYNC_STATUSES`) and which the widened double marks untrusted. Assert the marker is absent under the real module and present (with the right amount) under the double. The mock pattern is `vi.mock("@/lib/closed-sets", async (importOriginal) => ({ ...(await importOriginal<typeof import("@/lib/closed-sets")>()), isUntrustedKeySyncStatus: (s) => s === "revoked" || s === "sign_in_failed" || s === "error" }))`. The mock factory is hoisted, so use `vi.hoisted` for a toggle or put the widened case in its own file. `[CITED: vitest docs, vi.mock hoisting]`, `[ASSUMED]` that the exact factory shape typechecks. Verify with `npx tsc --noEmit`.

### Pitfall 5: A revoked key in the unreachable degrade branch
**What goes wrong:** with `contributingApiKeyIds: []`, book mode sums the *whole* book, revoked keys included.
**Avoid:** the helper tests the predicate on every summed holding, so the marker covers it. Pin it in the unit test (D-05: "a future change to eligibility cannot silently put a `revoked` contribution in the total unflagged").

### Pitfall 6: A NUL byte or the skip token in a commit
Repo traps (CLAUDE.md, memory). Not specific to this phase, but the CHANGELOG plan writes prose. Never write a skip token, and never quote a credential-shaped literal.

## Code Examples

### The helper (skeleton — the values quoted are from files read this session)
```ts
// src/app/(dashboard)/allocations/lib/live-holdings-summary.ts  (NEW)
import { isUntrustedKeySyncStatus } from "@/lib/closed-sets";
import type { MyAllocationDashboardPayload } from "@/lib/queries"; // type-only: no server-only runtime import

type Holding = MyAllocationDashboardPayload["holdingsSummary"][number];

/** Moved verbatim from ScenarioComposer.tsx (body unchanged). */
export function holdingEquityContributionLocal(h: Holding): number {
  if (h.holding_type === "derivative") {
    const pnl = h.unrealized_pnl_usd ?? 0;
    return Number.isFinite(pnl) ? pnl : 0;
  }
  return Number.isFinite(h.value_usd) ? h.value_usd : 0;
}

export interface LiveHoldingsSummary {
  total: number;                                    // === pre-phase liveHoldingsSum (D-03)
  untrusted: { amount: number; count: number };     // $X — subset of total (D-04)
  excludedUntrusted: { amount: number; count: number }; // $Y — D-06 (b) only
}

export function summarizeLiveHoldings(args: {
  toggleByScopeRef: Record<string, boolean>;
  holdingByRef: ReadonlyMap<string, Holding>;
  contributingApiKeyIds: readonly string[];
  statusByKeyId: ReadonlyMap<string, string | null>;
}): LiveHoldingsSummary {
  const contributing = new Set(args.contributingApiKeyIds);
  const narrowToModelledBook = contributing.size > 0;
  const out: LiveHoldingsSummary = {
    total: 0,
    untrusted: { amount: 0, count: 0 },
    excludedUntrusted: { amount: 0, count: 0 },
  };
  for (const [scopeRef, on] of Object.entries(args.toggleByScopeRef)) {
    if (!on) continue;
    if (!scopeRef.startsWith("holding:")) continue;
    const h = args.holdingByRef.get(scopeRef);
    if (!h) continue;
    const eq = holdingEquityContributionLocal(h);
    const untrusted = isUntrustedKeySyncStatus(args.statusByKeyId.get(h.api_key_id));
    if (narrowToModelledBook && !contributing.has(h.api_key_id)) {
      if (untrusted) { out.excludedUntrusted.amount += eq; out.excludedUntrusted.count += 1; }
      continue;
    }
    out.total += eq;
    if (untrusted) { out.untrusted.amount += eq; out.untrusted.count += 1; }
  }
  return out;
}
```
Notes:
- `import type { MyAllocationDashboardPayload } from "@/lib/queries"` is the established client-safe form. `ScenarioComposer.tsx` and the sibling `allocations/lib/mandate-gates.ts` both use exactly this import `[VERIFIED: grep this session]`.
- D-06's manager-side refinement (P4) would add an `excludeKeyIds` argument to the excluded bucket only. Add it inside the D-06 task, not before.
- The accumulation order must match the old loop (the same `Object.entries` walk), so `total` is bit-identical and not merely equal within a float tolerance.
