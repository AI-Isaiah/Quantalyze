## T-164.4.1-SC — supply chain, verified in depth

This is the only genuinely new external-code path the phase introduces, so it was
audited beyond a grep.

**macOS — `scripts/pg-lane/install-pg-cron-macos.sh` (READ, syntax MEASURED):**

- The tag is pinned (`PG_CRON_TAG="v1.6.7"`, `:60`) and the URL is built from it
  over HTTPS to github.com (`:62`). No branch, no `master`, no floating ref.
- The digest is a constant (`PG_CRON_SHA256`, `:61`) compared against a locally
  computed `shasum -a 256` at `:217-228` — **before** `tar xzf` at `:230` and
  before `make` at `:254`. A redirected or tampered archive therefore fails closed
  with nothing unpacked and nothing built. The refusal text explicitly forbids
  re-pinning the constant to the new digest without establishing provenance,
  which is the correct instruction for this failure.
- The digest's provenance is documented as two independent sources agreeing (a
  local computation plus Homebrew core's `Formula/p/pg_cron.rb`), which is what
  makes it a pin rather than a transcription of whatever the network served.
- The build tree is `mktemp -d` **outside** the repo with an EXIT trap `rm -rf`
  (`:209-211`), explicitly so it cannot land in the runner's dirty-checkout
  assertion.
- No `sudo`. No `eval`. No backticks in code. MEASURED: `bash -n` is clean on both
  scripts, and a scan for `eval` and command substitution in code (as opposed to
  comments) returns nothing in either.
- Uninstall removes an explicitly enumerated set of 10 paths (`:164-173`, `:269`)
  and nothing computed by glob.

**ubuntu — the `Provision pg_cron` step in `.github/workflows/ci.yml` (READ):**

- The package name is `postgresql-${major}-cron`, and `major` is read from the
  resolved binaries' own `pg_config` and then **hard-refused unless it equals
  16**. The install line is therefore not steerable to an arbitrary package name
  past that gate.
- `apt-cache policy` and the `dpkg -s` Version line are printed, so which source
  won (measured: noble/universe, 1.6.2-1) is a fact in the log rather than an
  assumption. The step ends with `ls -l` on the `.so` and the `.control` under
  `set -euo pipefail`, so a missing artifact fails the step before any lane runs.
- Actions are pinned to full commit SHAs (`actions/checkout@9c091bb...`,
  `actions/setup-node@48b55a0...`), not to tags.

**Trigger and privilege exposure (READ):**

- The workflow runs on `push: [main]`, `pull_request: [main]` and
  `workflow_dispatch`. It does **not** use `pull_request_target`, so a fork PR
  gets no repository secrets.
- Workflow-level `permissions: contents: read`; the `sql-mutation` job declares no
  `permissions:` uplift and references no `secrets.*`.
- The step introduces `sudo apt-get`. On a GitHub-hosted runner the runner user
  already has passwordless sudo, and this job already executes repo-controlled
  code (`run.mjs`, `run.sh`) from the branch under test, so the step **does not
  widen** the privilege a PR already has. Blast radius is one ephemeral runner
  with a read-only token and no secrets. Recorded as accepted risk AR-04.

## Database blast radius (CONTEXT D-05)

The critical invariant — a lane is a throwaway cluster and never a Supabase
database — was verified three ways:

1. **MEASURED.** The commit-range diff over `scripts/`, `.github/`, `supabase/`
   and `src/` adds no `--db-url`, no `--project-ref`, no `supabase.co`, no
   `postgres://` or `postgresql://`, no `SUPABASE_DB_URL`, no `db push` and no
   `db reset`.
2. **READ.** `scripts/pg-lane/run.sh` has one connection primitive, `psqlq()` at
   `:200`, hardcoded to `-h 127.0.0.1 -p "$PORT" -U postgres -d postgres`. There
   is no host or DSN parameter anywhere in the CLI surface. The cluster is created
   by `initdb` at `:343` and started with `listen_addresses=127.0.0.1` and `-k ''`.
3. **MEASURED.** Every caller passes a scratch workdir: `run.mjs` uses
   `mkdtempSync(join(tmpdir(), "mutation-runner-"))` (`:3794`) and derives every
   slot beneath it; the self-test, `--tracer-proof` and the macOS installer's
   `prove_via_lane` all use `mktemp -d`.

The hostile-input surface of the new `--print-pgbin` verb was exercised rather
than reasoned about:

```
$ PGBIN='/tmp/x; touch /tmp/PWNED_PGBIN' bash scripts/pg-lane/run.sh --print-pgbin
ERROR: PGBIN=/tmp/x; touch /tmp/PWNED_PGBIN has no executable pg_ctl
exit=1
```

No injection artifact was created; the value is quoted at every use, the verb
boots nothing, and it exits 1 rather than printing an empty line CI would read as
an answer (CI's own MEASURE_FAIL covers the empty case).

## Mutation-runner file safety

**MITIGATED, MEASURED.** The runner never edits a tracked file:

- `materialize()` (`scripts/mutation-runner/run.mjs:3697-3708`) copies the corpus
  from `REPO_ROOT` into a `slot-N/src/<rel>` path under the scratch root. Every
  subsequent `writeFileSync` (`:3994`, `:4024`, `:4031`) targets a path from that
  map or a slot-local `post-apply.sql`. There is therefore no restore step that
  can fail to run and leave a mutated tracked file behind — the tracked file was
  never mutated. The `restore` leg is a pristine-corpus lane re-run, not a file
  rollback.
- Escape is refused at parse time: `parse.mjs:79-83` rejects absolute paths,
  Windows drive letters and any `..` segment, in both `apply` steps and
  `RED-UNDER-SETUP` apply lists.
- Subprocesses are spawned with argv arrays and no shell (`spawnSync` at `:3124`
  and `:2258`), so an annotation-supplied path cannot become shell text.
- A working-tree snapshot is taken before (`:3787`) and after (`:4231`), and any
  delta raises a hard `dirty-checkout` defect; an unreadable status is itself a
  MEASURE_FAIL, so an absent measurement cannot read as a pass.
- The scratch root is removed in a `finally` (`:4224-4225`).

MEASURED: three narrowed corpus runs (3, 28 and 37 arms, each with a baseline and
a restore leg) left the porcelain status empty and produced no defects.

Minor, non-blocking observation: the `finally` covers throws and normal exits but
not SIGKILL. Two abandoned `mutation-runner-*` scratch roots from earlier sessions
were found under the system temp dir. They hold copies of tracked repo SQL only —
no credential — and live outside the repo. Noted, not a finding.

## Open findings (outside the declared register)

### F-164.4.1-A — BLOCKER (high) · Tampering / Destruction

**`scripts/pg-lane/run.sh` deletes a `pgd/` tree it did not create, while its own
comment states it cannot.**

The comment at `scripts/pg-lane/run.sh:129-130` reads:

> CREATED is set only AFTER this run makes its own data dir, so cleanup can never
> remove a cluster this run did not create.

That is false. At `:341-343` the sequence is:

```bash
mkdir -p "$PGD"
CREATED=1
initdb -D "$PGD/data" -U postgres --auth=trust -E UTF8 >/dev/null
```

`mkdir -p` succeeds silently on an **existing** directory, so `CREATED=1` is set
whether or not this run made anything. When `initdb` then refuses because the
directory is not empty, `set -e` fires, the EXIT trap runs, the `[ -d "$PGD/data" ]`
test at `:137` is true — of the pre-existing data — and `rm -rf "$PGD"` at `:162`
destroys it.

**MEASURED.** A scratch workdir outside the repo was seeded with a
`pgd/data/<sentinel file>` and the lane was pointed at it. Output:

```
initdb: error: directory ".../pgd/data" exists but is not empty
WARNING: pg_ctl stop FAILED for the lane cluster on 127.0.0.1:62111 at .../pgd/data.
WARNING: no postmaster.pid under .../pgd/data, so there is no pid to SIGKILL; removing .../pgd.
LANE_EXIT=1
```

The sentinel was gone afterwards. The whole `pgd/` tree was removed.

- **Reach:** local filesystem only. It cannot touch TEST or PROD — that separate
  invariant holds (see "Database blast radius").
- **Why high, not low:** this is irreversible destruction of data the run did not
  create, and the guarding comment claims a broader property than the check
  performs. That is the same defect class the repo already treats as serious in
  this exact file (IN-07: a refusal message that claims a broader check than it
  performs), and the sibling harm — a lane destroying a neighbour's cluster — is
  documented at `:271-276` as having actually cost a reviewer a session. The
  severity is the claim, not just the odds.
- **Why it is in scope:** the code is pre-existing and untouched by this phase's
  diff, but it is precisely the code T-164.4.1-01's mitigation plan cites (the
  lane "still initdb's under `--workdir` ... EXIT trap") as its evidence. A cited
  control that carries a false safety claim cannot be recorded as verified.
- **Not exercised by any shipped caller:** `run.mjs`, the self-test,
  `--tracer-proof` and the macOS installer all pass fresh `mktemp`/`mkdtemp`
  directories, so CI is not affected today. The exposure is an operator naming a
  `--workdir` at a path that already holds a `pgd/`.

**Suggested fix (refuse rather than delete):**

```bash
[ ! -e "$PGD" ] || fail "--workdir already contains $PGD. This lane would DELETE it on exit. Pick an empty workdir."
mkdir -p "$PGD"
CREATED=1
```

### F-164.4.1-B — OPEN, non-blocking (low) · Tampering

**`--workdir` is not constrained to a scratch location and may resolve inside the
repository.**

`scripts/pg-lane/run.sh:267-269` does `mkdir -p "$workdir"`, canonicalises it and
derives `PGD="$workdir/pgd"`. Nothing checks that the result is outside the
checkout.

**MEASURED.** A run with a repo-relative `--workdir` completed normally, booting a
cluster under the repository, and left the directory in the checkout afterwards.
(The cleanup removes `$PGD` and correctly does not remove a caller-supplied
workdir — that is only auto-removed in `legacy_run`.)

Impact is hygiene, not destruction: a crash mid-run would leave a Postgres data
dir inside the checkout where the secret-scan and planning-hygiene gates run, and
a porcelain status does not report an empty directory. It cannot delete anything
beyond `$PGD`. Below the `high` blocking threshold, so it is **not** counted in
`threats_open`. One guard closes this and F-164.4.1-A together.
