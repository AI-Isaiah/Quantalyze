## 1. The `RED-UNDER` annotation idiom — canonical exemplars

### 1a. Canonical SIMPLE file: `supabase/tests/test_metrics_by_basis_write.sql`

Annotated by plan 164.4-10 (7th file move). Two twinned sections out of six arms — the
shape where **not every arm is a section**, which four of this phase's five files share.

**Header block** (`test_metrics_by_basis_write.sql:31-44`) — the boilerplate paragraph every
annotated file carries verbatim, followed by file-specific ⚠️ notes:

```sql
-- ⭐ MACHINE-EXECUTABLE TWINS (phase 164.4, REDUNDER-BACKFILL). Each prose
-- RED-UNDER below carries an adjacent `RED-UNDER-M` object that
-- scripts/mutation-runner executes on every push: it mutates COPIES on a
-- throwaway pg-lane cluster, requires the FIRST `TEST FAILED (…)` to name that
-- arm, and restores GREEN. Schema: scripts/mutation-runner/GRAMMAR.md.
-- ⚠️ THE TWO CHECKS ARE LAST-DEFINED IN DIFFERENT MIGRATIONS, and each twin
--    targets whichever LAST defines the constraint it mutates. …
--    Only arms 4 and 6 are twinned: arms 1, 2, 3 and
--    5 are positive-path writes that raise nothing, so they are not sections.
```

⭐ Copy that last sentence's SHAPE: when a file's arms are not uniformly sections, the header
says **which** are twinned and **why the rest are not**. That is what makes a partial
annotation reviewable rather than a gap.

**APPLY LIST** (`test_metrics_by_basis_write.sql:45`) — one line, one JSON object, at
line-start, comment-prefixed, ordered as the lane applies it (fixtures before migrations,
migrations in the order a real apply would run them):

```sql
-- RED-UNDER-SETUP: {"apply":["scripts/pg-lane/fixtures/01-fixture-core.sql","scripts/pg-lane/fixtures/15-fixture-auth-role.sql","scripts/pg-lane/fixtures/02-fixture-sanitize-tables.sql","scripts/pg-lane/fixtures/03-fixture-compute-jobs.sql","scripts/pg-lane/fixtures/07-fixture-supabase-default-privileges.sql","supabase/migrations/20260411144407_compute_jobs_queue.sql","scripts/pg-lane/fixtures/04-fixture-compute-jobs-targets.sql","supabase/migrations/20260710120000_strategy_keys.sql","supabase/migrations/20260710130000_stitch_composite_kind.sql","supabase/migrations/20260717233529_allocator_equity_derived_surface.sql"]}
```

Grammar: exactly ONE `RED-UNDER-SETUP` line per file
(`scripts/mutation-runner/parse.mjs:416`), validated by `validateSetup`
(`parse.mjs:365-381`), schema in `scripts/mutation-runner/GRAMMAR.md:448` ("`RED-UNDER-SETUP`
— the in-file apply list").

**Prose + structured twin pair** (`test_metrics_by_basis_write.sql:97-109`), immediately
above the assertion they falsify:

```sql
  -- RED-UNDER: widen the strategy_analytics_metrics_by_basis_shape CHECK in
  --            migration 20260710120000 to admit jsonb_typeof 'null' as well
  --            as 'object'. That is exactly the loosening the header calls the
  --            carry-forward hazard: … The migration's own self-verify only checks
  --            that the COLUMN exists and is nullable (:207-213) — it never
  --            probes the CHECK's rejection behaviour — so the widened
  --            constraint applies perfectly clean. That is precisely why this
  --            arm has to exist: a shape CHECK that stops rejecting is not a
  --            shape CHECK, and nothing upstream of this file would notice.
  -- RED-UNDER-M: {"arm":"Arm 4","apply":[{"kind":"edit","file":"supabase/migrations/20260710120000_strategy_keys.sql","find":"  CHECK (metrics_json_by_basis IS NULL OR jsonb_typeof(metrics_json_by_basis) = 'object');","replace":"  CHECK (metrics_json_by_basis IS NULL OR jsonb_typeof(metrics_json_by_basis) IN ('object', 'null'));","occurrences":1}]}
```

The `"arm"` value must be the **section**, i.e. the identity inside `TEST FAILED (…)` with
its sub-letter stripped (`sectionOfIdentity`, pinned at
`src/__tests__/mutation-runner-floors.test.ts:1660-1677`). Here `"Arm 4"` matches
`RAISE EXCEPTION 'TEST FAILED (Arm 4): …'` at `test_metrics_by_basis_write.sql:118` and
`:121` — **two identities, one section, one twin**. That is the arm-unit rule.

⛔ **Three refusals the parser enforces on the twin** (copy these constraints, do not
rediscover them):
- `occurrences` is REQUIRED on every byte-edit and a mismatch is MEASURE_FAIL, not "arm did
  not redden" (`parse.mjs:25-37`).
- A `replace`/`text` may not inject a `TEST FAILED (` literal, directly or by SQL `||`
  concatenation (`parse.mjs:107`, `:128`, `refuseSelfSatisfying` at `:130-141`).
- A twin may not target a pg-lane **stand-in fixture** (`parse.mjs:217-233`, GRAMMAR rule 4
  at `GRAMMAR.md:361`). Mutate the real migration.

Step kinds and allowed keys: `parse.mjs:62-68` — `edit` / `insert-after` / `sql`.

## 2. The exception idiom that makes a raw SQLSTATE report an arm name

**Source:** `supabase/tests/test_resync_retry_single_job.sql:208-247` (plan 164.4-09;
resolved `[REDUNDER-WAIVER-01]`'s sibling without spending a waiver).

**The rationale comment** (`:208-214`) — copy this verbatim in shape:

```sql
  -- The INSERT is wrapped in the SAME `BEGIN ... EXCEPTION WHEN unique_violation`
  -- idiom assertion (c) below already uses, for the MIRROR-IMAGE reason. (c)
  -- needs the handler because the collision it describes is the PASS; (b) needs
  -- it because the collision is the FAILURE -- and an UNHANDLED 23505 here
  -- aborts psql with a raw driver error before this arm can name itself, so the
  -- one production change this assertion exists to refuse would be
  -- indistinguishable from any other crash. Phase 164.4 measured exactly that.
```

**The wrap** (`:235-247`):

```sql
  BEGIN
    INSERT INTO strategy_verifications
      (strategy_id, wizard_session_id, status, trust_tier, flow_type, source)
    VALUES
      (strat_r, session_1, 'draft', 'api_verified', 'resync', 'binance'),
      (strat_r, session_2, 'draft', 'api_verified', 'resync', 'binance');
  EXCEPTION
    WHEN unique_violation THEN
      RESET ROLE;
      RAISE EXCEPTION
        'TEST FAILED (b): two draft strategy_verifications rows for strategy % with DISTINCT wizard_session_ids (%, %) collided on a unique violation, but distinct sessions must insert cleanly. …',
        strat_r, session_1, session_2;
  END;
```

Three load-bearing details: (1) the handler is a **nested `BEGIN … EXCEPTION`** = an implicit
savepoint, so the outer block survives; (2) `RESET ROLE;` precedes the raise (the arm may be
running under `SET ROLE authenticated`); (3) the message re-states the ECONOMIC reason, not
just the symptom.

⚠️ For this phase the analogous raw SQLSTATE is `0A000` / `feature_not_supported` raised by
`supabase/migrations/20260826140000_compute_jobs_error_kind_orphaned.sql:206-209` when
`pg_extension` has no pg_cron. If pg_cron is present on the lane that raise never fires; if
the preload silently fails, it aborts the APPLY (before any gate text runs), which the runner
scores `baseline` — a distinct defect kind, correctly loud. No wrap is needed there. The
wrap idiom is needed wherever a NEW twin can make a gate hit a driver-level error inside the
gate's own `DO` block.

The `CHECK`-constraint sibling of the same idiom (trap + `GET STACKED DIAGNOSTICS
CONSTRAINT_NAME`, so the WRONG constraint also fails the test) is at
`supabase/tests/test_metrics_by_basis_write.sql:110-122`.

## 4. Threading a lane-startup option through `run.sh`

**Source:** `scripts/pg-lane/run.sh:250-262`. The cluster is started exactly ONCE per lane, so
server settings belong on the `pg_ctl -o` string — no `postgresql.conf` edit, no restart:

```bash
  mkdir -p "$PGD"
  CREATED=1
  initdb -D "$PGD/data" -U postgres --auth=trust -E UTF8 >/dev/null
  # -k '' => TCP only. A unix socket under a scratch path blows the 103-byte limit.
  # -w waits for startup; the harness's `sleep 2` here was a measured race.
  pg_ctl -D "$PGD/data" -o "-p $PORT -c listen_addresses=127.0.0.1 -k ''" \
         -l "$PGD/pg.log" -w start >/dev/null
```

The existing `-o` string is itself the precedent for adding a `-c <setting>=<value>`: it
already carries three (`-p`, `-c listen_addresses`, `-k`), each with a one-line comment
stating the measured reason. Follow that — one comment per new setting, naming what it costs.

**Binary resolution — do NOT re-hardcode.** `resolve_pgbin()` at `run.sh:67-77` is the
four-step chain (`pg_ctl` on PATH → `pg_config --bindir` → `/usr/lib/postgresql/*/bin` →
`/opt/homebrew/opt/postgresql@*/bin`). ⚠️ An extension `.so` must match the server MAJOR that
this chain picks. `ci.yml:933-955` already prints the resolution as a **non-fatal probe** so a
lane failure gets a named diagnosis; that step is the analog for any new "did the extension
land next to the right binary" probe.

⛔ **Two pins constrain any new SQL you add inside `run.sh`**
(`src/__tests__/mutation-runner-floors.test.ts:1627-1642`):
- `psqlq()` must remain exactly one line matching `^\s*psqlq\(\)\s*\{` and must keep
  `-v VERBOSITY=verbose` and `-v ON_ERROR_STOP=1` (`run.sh:176`);
- `expect(bare).toEqual([])` — **zero** lines matching `^\s*psql\s`. A `CREATE EXTENSION
  pg_cron;` issued as a bare `psql -c` reddens vitest. Route it through `psqlq -q -c "…"`,
  the way the role bootstrap does at `run.sh:264`.

Related: `alloc_port()` at `run.sh:87-99` and the bind-based collision guard at `:230-243`
are untouched by this work but are what make parallel lanes safe.

## 5. `run.sh --self-test` arms — the neuter → observe RED → restore convention

**Sources:** `run.sh:559-572` (arm 4, failure path) and `run.sh:574-587` (arm 5, success
path). They are a matched PAIR, and the pairing is the pattern: an arm that only proves the
happy case proves nothing.

```bash
  echo "=== SELF-TEST 4/5: failure-path cleanup ==="
  wd=$(mktemp -d)
  gate="$wd/failing-gate.sql"
  printf "DO \$\$ BEGIN RAISE EXCEPTION 'TEST FAILED (SELF-TEST): deliberate'; END \$\$;\n" >"$gate"
  port=$(alloc_port)
  set +e
  PORT="$port" bash "$0" --workdir "$wd" \
    --apply "$FIXTURES/01-fixture-core.sql" --gate "$gate" >"$wd/out" 2>&1
  rc=$?
  set -e
  [ "$rc" -ne 0 ] || st_fail "the deliberately-failing gate exited 0"
  no_orphan "$port" "$wd/pgd" "failure-path"
  rm -rf "$wd"
  echo "  ok  failing gate exited $rc and cleaned up"
```

Copy: nested lane spawned as `bash "$0" --workdir … --apply … --gate …` with its own
`alloc_port`; `set +e` / capture `rc` / `set -e` (never a pipe — `$?` would be the last
command's); a NEGATIVE assertion via `st_fail` (`run.sh:394`); `no_orphan` teardown check
(`run.sh:397-406`); a `  ok  …` line naming what was proven.

**A new arm proving the pg_cron preload took effect** should be the arm-4/arm-5 pair applied
to the preload: a gate whose SQL asserts the extension really loaded (RED if it did not), and
the control that the same lane is otherwise green. The nearest existing "did the lane really
do X" gate text is `scripts/mutation-runner/fixtures/lane-probe/pg-cron-probe.sql:27-33`.

⛔ **The arm-count bookkeeping is manual and spelled in EIGHT places.** Adding a 6th arm means
editing all of: `run.sh:455` (`5/5` inside a comment), `:465` (`1/5`), `:506` (`2/5`),
`:555` (`3/5`), `:559` (`4/5`), `:574` (`5/5`), `:589` (comment), `:593`

**The `run.mjs` sibling** (for a runner-side arm rather than a lane-side one) is

### The classifier

`scripts/mutation-runner/parse.mjs:1043-1049` `gateNeedsPgCron` — two projections of the SAME

```js
export function gateNeedsPgCron(text) {
  for (const stmt of tokenizeStatements(text)) {
    if (!PG_CRON_CATALOG_RE.test(stmt.executableText)) continue;
    if (stmt.commentMaskedText.toLowerCase().includes(PG_CRON_EXTENSION)) return true;
  }
  return false;
}
```

Literals spelled ONCE at `parse.mjs:1002-1003`. `classifyGateIdiom` at `:1086-1099` — order
matters: `inert` → `unreachable` → (`lane-blocked` | `pending`), asserted at

## 7. The CI MEASURE_FAIL convention (`sql-mutation`, `.github/workflows/ci.yml:804-1405`)

**The three-arm block** — `ci.yml:1223-1244` is the exemplar to copy for any new stdout
assertion. Every assertion distinguishes "could not measure" from "measured, no problem"
(`ci.yml:1114-1117`):

```yaml
          lane_blocked_line=$(grep -a -m1 -E '^lane-blocked: [0-9]+ file\(s\) ' "$RUNNER_LOG" || true)
          if [ -z "$lane_blocked_line" ]; then
            echo "::error::MEASURE_FAIL: the run printed NO 'lane-blocked: N file(s) …' line, so which gate files this run DEFERRED, and why, is unknown. …"
            exit 1
          fi
          echo "$lane_blocked_line"
          lane_blocked_claimed=$(echo "$lane_blocked_line" | sed -E 's|^lane-blocked: ([0-9]+) file\(s\) .*|\1|')
          case "$lane_blocked_claimed" in ''|*[!0-9]*)
            echo "::error::MEASURE_FAIL: could not read the deferred-file count out of '$lane_blocked_line'."; exit 1;; esac
          lane_blocked_named=$(echo "$lane_blocked_line" | grep -a -o -E '[A-Za-z0-9_]+\.sql' | wc -l | tr -d '[:space:]' || true)
          case "$lane_blocked_named" in ''|*[!0-9]*)
            echo "::error::MEASURE_FAIL: could not count the file names on '$lane_blocked_line'."; exit 1;; esac
          if [ "$lane_blocked_claimed" -ne "$lane_blocked_named" ]; then
            echo "::error::MEASURE_FAIL: the run CLAIMS $lane_blocked_claimed deferred file(s) but NAMES $lane_blocked_named. …"
            exit 1
          fi
```

Five conventions in that block, all transferable:
1. `grep -a` always (NUL-blindness, `ci.yml:972-976`), `-m1`, anchored `^`, `|| true`.
2. Empty-string check BEFORE any numeric comparison — an empty var satisfies `-eq 0`.
3. Unreadable extraction is its own MEASURE_FAIL (`case … in ''|*[!0-9]*)`).
4. Claimed count must equal names printed beside it.
5. ⭐ `|| true` on the `grep -o | wc -l` pipeline, explicitly because under `set -euo
   pipefail` an EMPTY set makes `grep -o` exit 1 and would abort the step with **no
   `::error::` at all** — comment at `ci.yml:1232-1237` names `lane-blocked: 0 file(s)` as
   the exact state "this phase's successor reaches". That is this phase. The guard is
   already correct; do not remove it.

**ONE judge per question** (`ci.yml:1255-1263`): the `lane-probe:` assertion deliberately does
NOT judge AVAILABLE, because the runner already exits 1 via `lane-blocked-stale`. CI's job is
to notice the probe went MISSING. The `(absent|AVAILABLE)` alternation at `ci.yml:1264` is
what makes the third form (`UNREADABLE`) fail here too.

**No literal counts in `ci.yml`** — `ci.yml:1220-1222`: "the runner derives the set and both
sides come from the run output, so the day the four are annotated this block needs no edit."
Honour that: the count changes need no `ci.yml` edit.
