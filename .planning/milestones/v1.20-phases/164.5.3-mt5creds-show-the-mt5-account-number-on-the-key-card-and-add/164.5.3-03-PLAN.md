<objective>
Per D-04 (founder decision, 2026-09-20): add a new Python internal endpoint,
`POST /internal/keys/{key_id}/rotate-secret`, that decrypts the stored MT5 credential, re-validates the
CALLER-SUPPLIED new investor password against the live broker using the exact login and broker server
already on file, and — only on a structural success — re-encrypts and returns fresh ciphertext. Mirrors
`/internal/keys/{key_id}/permissions`'s posture exactly: plaintext never leaves this service. Next.js
(the phase's other Wave-1 plan) calls this; it must never decrypt or see the broker server itself.

⛔ This is the ONLY place in the phase that touches a live credential in plaintext. ⛔ No agent enters,
reads, logs, or echoes a real credential at any point — the test fixture's "new password" is a synthetic
placeholder string, never anything credential-shaped.

Purpose: D-03 fixes the update route's contract to "password only" — the login and broker server the
credential is checked against must come from THIS SERVICE's own decrypt of the stored row, never from
the browser or from Next.js. No existing endpoint offers "revalidate this stored key with one new field"
— `/validate-key` and `/encrypt-key` both require the full plaintext triple from the caller.

Output: one new router handler (decrypt + validate + re-encrypt, reusing every existing primitive —
`decrypt_credentials`, `encrypt_credentials`, `_validate_mt5_key`, `get_supabase`,
`_verify_internal_token` — and building nothing new except the chokepoint that wires them together) and
its test file.
</objective>

      dek_encrypted, nonce, kek_version, venue_account_id: login}` — HTTP 200.
    - A missing/wrong `X-Internal-Token` returns 403 before any Supabase read (`_verify_internal_token`
      reused verbatim, same as `get_key_permissions`).
    - An unknown `key_id` returns 404 before any decrypt is attempted.
    - An `api_keys` row whose `exchange` is not `"mt5"` returns 422 before any decrypt is attempted
      (this endpoint is MT5-only, per the phase's explicit scope — see 164.5.3-04-PLAN.md's route,
