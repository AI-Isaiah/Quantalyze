<objective>
Wire the phase's second capability — "correct a wrong password without deleting the key" — into both
founder-visible key cards, via a single new shared dialog component so the fetch/error-envelope logic
exists in exactly one place rather than being duplicated across two card files.

Per RESEARCH.md's Open Question 4 (resolved here): the affordance is a DISTINCT action, available on
EVERY MT5 key row regardless of connection state — not gated to an error/disconnected state, and never
conflated with the existing Reconnect button (which clears `disconnected_at` and assumes the stored
credential is already correct; it does not re-validate anything). A founder may want to rotate a
password proactively (e.g. after a broker-mandated reset) even when the current credential still works.

⛔ The dialog collects ONLY the new password (D-03) — never a login, never a broker server field, even
as an optional/advanced toggle. ⛔ Update failures render through `ErrorEnvelope`, sourcing copy via
`buildEnvelope()` — no bespoke inline error string (D-06).

Purpose: this is the user-facing half of the phase's second goal. Without it, Plan 04's route exists but
no founder can reach it.

Output: one new shared dialog component, its test, and the wiring into both card components — this
plan's own file overlap with Plan 01's already-edited card files is why it is Wave 2, not Wave 1.
</objective>
