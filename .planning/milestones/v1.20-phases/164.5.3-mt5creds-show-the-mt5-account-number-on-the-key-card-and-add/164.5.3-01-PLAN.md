<objective>
Publish `api_keys.venue_account_id` (Phase 154 / WIZCONT-02's existing, currently-unexposed column) to
the owning user, per the founder's locked decision D-01-PRIME: **reuse the existing column, do not add
a new one**. Extend its GRANT (068-shaped migration), thread it through the three-way sync
(`API_KEY_USER_COLUMNS_ARR` -> `ApiKey` interface), and render it on BOTH founder-visible key cards
(`ApiKeyManager.tsx`, `AllocatorExchangeManager.tsx`) per D-06's typography contract.

This is the phase's tracer: the thinnest path that makes the identifier real to a founder end-to-end —
DB column already exists (Phase 154) -> GRANT makes it readable -> config makes it selectable -> a card
renders it — for the wizard-created MT5 keys that already carry a value. It does NOT yet close the
NULL-population gap for keys created via "Add Key" (validate-and-encrypt) or correct wrong passwords —
those are separate plans in this wave/the next, per RESEARCH.md's finding that D-01-PRIME/D-02-PRIME's
"add a column" language is satisfied by "extend the GRANT on the column that already exists."

⛔ Do NOT add a new column. ⛔ Do NOT backfill existing NULL rows (no data-reading migration — see
Non-Negotiable). ⛔ Never widen the REVOKE on the encrypted columns (`api_key_encrypted`,
`api_secret_encrypted`, `passphrase_encrypted`, `dek_encrypted`, `nonce`) — this migration is additive
and narrow, touching only `venue_account_id`.

Purpose: a founder (and a first-time client) currently cannot tell which MT5 account a key card belongs
to — every MT5 key falls back to the optional nickname field, and several accounts render
indistinguishably. This plan makes that identifiable for every key the wizard has ever created.

Output: one migration, two TS config edits, two component edits, extended tests, and the pg-lane
fixture the migration's own self-verify needs to be checked locally before it ever reaches TEST/PROD.
</objective>
