# Phase 164.8: TESTPREPROD — Context

**Gathered:** 2026-09-08
**Status:** Ready for planning
**Mode:** Smart discuss (autonomous), 4 areas / 16 questions, all accepted as recommended

<domain>
## Phase Boundary

The shared TEST project stops being a stale bystander and becomes the stage every
migration crosses BEFORE production. Two halves: (1) bring TEST current; (2) apply on
merge to TEST FIRST, then PROD, so a migration that cannot apply is caught against a
real Postgres instead of against customers.

⛔ **NOT in this phase:** per-run isolation on TEST, Playwright worker parallelism,
`FANOUT-GLOBAL-01`, and any change to WHICH gates exist or what they assert.

</domain>

<decisions>
## Implementation Decisions

### Area 1 — Apply pipeline: when, and what a failure blocks
- **The TEST apply runs on merge to `main`**, as a job that must succeed BEFORE the PROD
  apply job. Not on PR (a PR head is not the merge result) and not nightly (too late to
  gate anything).
- **A failed TEST apply BLOCKS the PROD apply.** Warn-only was considered and rejected:
  it makes the phase decorative, and "caught against a real Postgres instead of against
  customers" is the entire goal.
- **Same workflow** (`supabase-migrate.yml`), a new job the PROD job `needs:`. One place
  decides what reaches production; two workflows cannot order themselves.
- **A new GitHub Environment `Test`** carrying its own project ref and password,
  mirroring how the PROD job is already pinned by `environment: Production`
  (`supabase-migrate.yml:118`).

### Area 2 — Bringing TEST current
- **Forward-only from a declared cut date.** ⚠️ This is a DELIBERATE SCOPE CUT, accepted
  knowingly: it does NOT bring TEST current in the sense of matching PROD. It declares
  the accumulated past out of scope and starts the discipline from the cut. Justified by
  measurement — 69 of 262 migrations do not replay from empty (`BASELINE.md`), and a full
  replay is precisely what hits `42883` on `20260908120000`.
- **The 31 baselined-absent migrations are NOT bulk-applied.** The list shrinks by
  founder decision, one at a time, as it already has once
  (`20260823120000_revoke_api_keys_insert`, 32 → 31). A bulk apply is 31 unreviewed
  schema changes on a database other people's CI uses.
- **The catch-up is a one-shot `workflow_dispatch`, founder-approved, never automatic** —
  it writes to a SHARED database.
- **A failure mid-catch-up STOPS and reports the failing migration by name.** Continuing
  past a failure leaves TEST in a state nobody can describe.

### ⛔ SUPERSEDING DECISION 2026-09-08 — Area 2 Q1 IS REVERSED: RESTORE TEST FROM A PROD DUMP

**Founder decision, taken AGAINST my stated recommendation and with my objections visible at
the time.** I recommended a bounded repo-owned applier and labelled this option "I would do
this EVENTUALLY, not here". The founder chose it anyway. Recorded plainly so nobody later
reads this as a planner's drift. My objection was blast-radius-and-timing; the founder's
choice is goal-weighted, and on that axis it is the better call — forward-only would have
shipped a pipeline that never delivered the motivation the ROADMAP quotes in the founder's
own words, *"the only thing that fixes e2e running against a stale schema."*

**WHAT FORCED THE REVERSAL — measured 2026-09-08 against TEST, read-only, marker verified:**

| Reading | Value |
|---|---|
| TEST ledger rows | 243 |
| Repo migration files | 266 |
| **Ledger rows whose `version` matches NO repo file** | **40** |
| Repo files with no ledger row, by exact `version` | **63** (VAC-08 reports 32) |

⭐ **The 63-vs-32 gap is the whole diagnosis.** VAC-08 joins on FOUR naming conventions and
sees a migration as present when the ledger's `name` matches; `supabase db push` compares
`version` ONLY. Roughly 40 TEST rows were written with the APPLY timestamp instead of the
FILENAME timestamp — e.g. `version=20260828061901` carrying
`name=20260827120000_sanitize_user_revoke_strategy_shares`. Those 40 are `ErrMissingLocal`
hard errors raised BEFORE `--include-all` is consulted
(`pkg/migration/apply.go:21-54`, `up.go:42-52`, CLI v2.98.2 as pinned by CI). So the
forward-only Area 2 Q1 answer was **not implementable by the CLI at all**, and clearing the
blockers would then have applied 63 migrations, not the 31 already rejected.

**THE DECISION:** rebuild TEST's schema from the production dump, seed its ledger to match
PROD's, then apply-on-merge natively from a ledger the CLI understands.

**CONSEQUENT CHANGES — planning must treat these as decided:**
- **Area 2 Q1 (forward-only from a cut date): DEAD.** No cut date, no `TEST_APPLY_CUT`
  constant, no bespoke applier. Do not plan them.
- **Area 2 Q2 (do not bulk-apply the 31): MOOT.** A restore makes TEST match PROD, so the
  absent set collapses rather than being applied one by one.
- **The 40 bad ledger rows: MOOT.** They are replaced, not repaired.
- ⚠️ **`scripts/vac08-ledger-baseline.txt` becomes STALE BY CONSTRUCTION.** Its 31 entries all
  mean "absent from TEST"; after the restore they are present. Its own header says a listed
  name that turns up PRESENT is a **HARD FAILURE — delete the line**, and that the file
  MUST ONLY SHRINK. So the restore should empty it, legitimately, and that emptying is a
  DELIVERABLE of this phase — not a side effect to discover. ⛔ It must be emptied BESIDE AN
  AIM, per this repo's convention for a deliberately empty set, never as a bare empty file.
- ⚠️ **OPEN — does Area 3's pragma survive?** If TEST's ledger is seeded from PROD's, then
  `20260908120000` is already marked applied and VAC-08 goes green without any pragma; and if
  TEST mirrors PROD thereafter, a DROP that is valid for PROD is valid for TEST. The pragma
  may be unnecessary for THIS migration while still being the right general mechanism, or it
  may be dead scope. ⛔ PLANNING MUST SETTLE THIS EXPLICITLY rather than building it by
  inertia — a mechanism nobody needs is exactly the vacuity this milestone removes.

**SAFETY THE PLAN MUST CARRY — non-negotiable, this is a DESTRUCTIVE act on a SHARED database:**
1. Verify the identity marker (`shobj_description(oid,'pg_database')`) immediately before any
   write, and ABORT on a NULL or non-TEST marker. Never infer from `current_database()`.
2. Hold the shared-TEST advisory mutex for the WHOLE restore, not per statement.
3. Back up TEST's current ledger AND schema to an artifact before dropping anything, so the
   act is reversible.
4. ⛔ Founder-executed or founder-approved AT THE MOMENT OF EXECUTION — a `checkpoint:decision`,
   never an unattended job. TEST is shared with other people's CI and we cannot see their runs.

   ⚠️ **SUPERSEDED 2026-09-08 by founder decision — CONDITIONAL DELEGATION.** Asked directly who
   should decide at the moment of execution, the founder chose: *"Delegate, but only if TEST is
   measurably quiet."* The restore may now be dispatched by the executor WITHOUT a founder reply,
   **if and only if an ACTIVITY GATE passes**. The gate turns "we cannot see their runs" from an
   assumption into a measurement. It is NOT a blanket delegation:

   a. **Mutex FIRST, then probe** — acquire the shared-TEST advisory lock (key `61616158`) BEFORE
      probing. Probing first and locking second measures a window that has already closed; holding
      the lock first stops every cooperating job from STARTING its DB work, so the probe then
      describes a state the gate controls rather than one it merely observed.
   b. **`idle in transaction` COUNTS AS ACTIVE.** The naive `state <> 'idle'` predicate reads an
      idle-in-transaction session as quiet while it holds locks. Both `idle in transaction` and
      `idle in transaction (aborted)` are ACTIVE for this gate.
   c. **Any non-zero count ABORTS and returns to the founder**, naming each session by
      `application_name`, `state` and `state_change` — never a bare count.
   d. The gate is a SNAPSHOT under a held lock, not a proof. It cannot see a job that connects
      after it passes, and it cannot see work scheduled but not yet started. The founder accepted
      that explicitly; the option they chose said so in its own text.

   ⛔ Task 1 of Plan 04 is UNCHANGED and still `checkpoint:human-action`: the wave 1-3 PR must be
   merged to `main` by the founder before anything is dispatchable at all (`workflow_dispatch`
   resolves only on the default branch). This amendment delegates the RESTORE decision, not the
   merge.
5. Source of truth is `supabase/schema/baseline.sql` at the sha recorded in `BASELINE.md`
   (`27826b76…`, regenerated and secret-scanned 2026-09-08), NOT a fresh unreviewed dump.

### Area 3 — The unappliable-migration disposition (`[164.5-TEST-VAC08-DROP-UNAPPLIABLE]`)
- **The migration AUTHOR declares it; the gate does not infer it.** Inference means
  probing TEST for the object and staying silent when it is absent — which is
  indistinguishable from the genuine missing-apply the gate must still catch.
- **Shape: a dated header pragma** in the migration (e.g. `-- TEST-NOT-APPLICABLE: <reason>`),
  parsed by ONE piece of code that both consumers read. Conforms to the `RED-UNDER` and
  `APP-GUC-LINEAGE` idioms this repo already has.
- **One declaration exempts BOTH the TEST apply and VAC-08's drift verdict.** Two
  independent switches drift, and the apply pipeline would then abort on exactly the
  migrations VAC-08 had been told to forgive.
- **Anti-vacuity is a THREE-arm proof, not a pair:**
  1. RED — a genuinely unapplied migration with NO pragma still fails.
  2. GREEN — the pragma'd migration passes.
  3. RED — a pragma whose stated reason is FALSE (the object DOES exist on TEST) fails.
  ⛔ Arm 3 is what stops the pragma becoming a mute button. A disposition proven only in
  direction (2) is worse than the red it replaces.

### Area 4 — Shared-TEST blast radius
- **No new isolation mechanism in this phase**, stated explicitly rather than left
  implicit. The ROADMAP already fences it.
- **`FANOUT-GLOBAL-01` stays deferred**, named in the phase as a known limit on any
  assertion made against TEST.
- **The apply step TAKES the existing shared-TEST advisory mutex** — the same one
  `ci.yml`, `analytics-deploy-verify.yml`, `main-ci-cancelled-watcher.yml` and
  `mutex-probe.yml` use. An apply racing a running `sql-tests` is the one collision that
  corrupts a reading rather than merely delaying it.
- **A foreign conflicting change surfaces as a LOUD apply failure.** We cannot lock a
  database we do not own, and a defence that cannot be tested is worse than a clear error.

### ⚠️ ACCEPTED CONSEQUENCE — a coupling neither answer shows alone
Area 1 Q2 (a TEST apply failure BLOCKS the PROD apply) and Area 4 Q3 (the apply takes the
SHARED mutex) combine into: **a hung or slow mutex holder, owned by someone else's CI, now
sits between a merge and the production deploy.** Today nothing blocks a PROD deploy on
TEST at all, so this is a NEW coupling to a resource this project does not control. It was
surfaced at decision time and accepted. ⛔ Planning must not discover this and quietly
soften Area 1 Q2 to resolve it. If it proves intolerable, the escape hatches identified —
a timeout on mutex acquire that proceeds with a loud warning, applying without the mutex,
or blocking PROD only on apply FAILURE rather than apply UNAVAILABILITY — are founder
decisions, not planner ones.
