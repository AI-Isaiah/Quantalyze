## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 3 — Blocking] `supabase/setup-cli` installed unconditionally instead of inside the restore-only post-verify.**
The plan's step 12 said "setup-cli pinned 2.98.2, then `supabase db push …`" under `if: inputs.mode == 'restore'`, but step 10's backup runs `supabase db dump` in BOTH modes. Following the step list literally would have left the backup with no tool and every preflight red at the backup. The `uses:` is hoisted to run unconditionally with a comment saying why. *Commit `1ea0a4b3`.*

**2. [Rule 3 — Blocking] The artifact UPLOAD moved to the end of the job; the backup step that WRITES the files did not move.**
The plan asked the upload to be `if: always()` "so an aborted script still leaves the backup" AND for the script's `RESTORE_OUT_DIR` census to be in the artifact. Both cannot hold if the upload runs immediately after the backup step — the census does not exist yet. Placing the upload last with `if: always()` satisfies both, and the pinned ordering (`backup < script < post-verify`) is untouched. *Commit `1ea0a4b3`.*

**3. [Rule 2 — Missing critical functionality] A redaction step was ADDED before the upload.**
Threat T-164.8-10's mitigation asserts "the DSN is never written to the artifact". psql's and the Supabase CLI's connect/auth failures print `connection to server at "<host>" (<ip>) …`, `FATAL: password authentication failed for user "<user>"` and libpq's `host=…`/`user=…` forms — which land in `ledger.err`, `dump.log` and `transaction.out`, files bound for a world-readable artifact on a PUBLIC repo. The new step applies ci.yml's own WR-08 redactions (plus the key=value shapes) to `*.err`, `*.log`, `*.out` **only** — never to `ledger.csv` or the two `.sql` files, where a substitution would corrupt the bytes the reversal recipe replays. The same redaction is applied inline in the marker step and the CLI post-verify before anything is printed. *Commit `1ea0a4b3`.*

**4. [Rule 1 — Bug] The backup step's ledger row count was derived from `wc -l` on the CSV.**
The `statements` column carries multi-line SQL, so a CSV line count is not a row count — the log would have printed a number that reads true and is not. Replaced by a `SELECT count(*)` asked of the database, with the failure path being a red (a backup whose completeness cannot be reported is not a reported backup). *Commit `1ea0a4b3`.*

**5. [Rule 1 — Bug, in this plan's own test] `stepBody()` returned `""` for the LAST step in the file.**
The extractor's lookahead needs a following step / job header, and the upload step is last. Every assertion over it would have passed vacuously. Caught because the first run FAILED loudly on `expected '' not to be ''` — the pin asserts non-emptiness first, by design. Fixed with an end-of-file sentinel and a comment recording the measurement. *Commit `f2c12086`.*

### Plan-internal inconsistencies resolved, with the reasoning

**6. Task 3's `<automated>` verify expects `grep -c '… --ref main -f mode=' == 2`. The tree has 3, and that is CORRECT.**
Task 1 requires the `dispatch-guard` job to print the correct dispatch (`… -f mode=preflight`), and Task 3 requires two recipe lines in the header (`mode=preflight`, `mode=restore -f confirm=…`). Three lines is the only tree that satisfies both tasks. The count assertion's INTENT — both recipes present — is preserved and **strengthened** in `test-restore-workflow-wiring.test.ts`, which asserts that the HEADER specifically carries both commands and that the GUARD BLOCK specifically carries the preflight one; a total count cannot tell those apart. Deleting the guard's line to satisfy the literal would have removed the one message an operator reads at the exact moment they mis-dispatched. Measured: header 2, guard 1.

**7. Task 1 step 4 asks for one step that both calls `gh` and reads "from a prior `id:` step's outputs".** Implemented as the two steps that sentence describes — `Read PROD's newest migration apply` (`id: prod-apply`) and `Assert PROD's ledger equals the repo file set` — which is also what makes Task 2's stub execution possible in the shape it specifies (the three readings injected through the env the assert step reads). No `${{ }}` appears in any `run:` body anywhere in the file.

**8. The softening-token scan excludes the ACQUIRE step, not only the RELEASE step.**
Forced, not chosen: the plan requires the acquire suffix to be byte-identical to ci.yml's, and ci.yml's suffix legitimately contains `exit 0` (the successful acquire), `|| true` (the bounded census) and `::warning` (the retried session fault). Scanning it would put two plan requirements in direct contradiction. The excluded region is not unpinned — it is governed by an exact byte-identity assertion, and our own divergent prefix by a dedicated "contains no zero-status exit, does contain `exit 1`" pin, which is stronger than a token scan over the same bytes. The test says all of this in a comment at the exclusion site.
