### WR-01: `refuse_backticks_in_txn_heredocs` cannot fire on three unquoted-heredoc shapes its own comment says it covers

**File:** `scripts/restore-test-from-baseline.sh:615-659` (guard), `:2858-2875` (arm 26 leg (d))

**Issue:** The guard's comment at `:617-623` says "⛔ **MATCH EVERY UNQUOTED HEREDOC**, not just
the `TXN_*` ones", and arm 26 leg (d) declares "THE FOUR EVASIONS" closed. I drove the shipped
function against fixtures and it accepted a **live** backtick in three more shapes. This is
exactly the failure the comment names — "a guard named for a general property while testing a
narrow one is how the next reader concludes they are covered."

**Mutation and observation.** I sourced the shipped script with its final `main "$@"` line removed
and called the real function against three fixtures:

```
=== ev1 ===  exit=0     cat >> "$out" <<TXN_EV >/dev/null   … `RAISE` …   TXN_EV
=== ev2 ===  exit=0     cat >> "$out" <<TXN_EV2 / "    TXN_EV2" (indented) / … `RAISE` … / TXN_EV2
=== ev3 ===  exit=0     cat >> "$out" <<TXN_EV3 | cat        … `RAISE` …   TXN_EV3
```

All three returned 0 = accepted. I then proved bash really substitutes in those bodies:

```
$ bash proof1.sh; cat proof1.out
  -- prose carrying a live PWNED backtick
$ bash proof2.sh; cat proof2.out
    TXN_EV2
  -- prose carrying a live PWNED2 backtick
```

Root causes, both in the awk at `:631-654`:
1. The `[ \t]*$` anchor at the end of the opener regex means a delimiter followed by **any**
   redirect or pipe (`<<EOF >file`, `<<EOF | cmd`, `<<EOF 2>&1`) is never recognised as an opener,
   so the whole body is unscanned. The comment at `:628-630` keeps the anchor deliberately, but
   only reasons about the self-test's own `printf` line — not about `<<EOF >file`.
2. The terminator comparison at `:643-644` strips leading whitespace from **every** line, so an
   indented line equal to the delimiter ends `inside` state. bash does **not** treat that as a
   terminator for a non-`<<-` heredoc, so the guard leaves the body early and everything after is
   unscanned.

**Failure scenario:** someone adds `cat >> "$out" <<TXN_NEW >/dev/null` (a plausible shape when
splitting the transaction assembly) with an SQL `-- comment mentioning \`RAISE\`` inside. The
guard passes, arm 26 leg (c) passes, and bash command-substitutes that span while assembling the
`DROP SCHEMA public CASCADE` transaction — the precise class the guard exists for. No live
instance exists in the file today (I independently scanned for openers whose delimiter is not at
EOL: zero real hits, only comments and `printf` strings), which is why this is WARNING and not
BLOCKER.

**Fix:** recognise the opener anywhere on the line, then find the delimiter token, rather than
anchoring on `$`; and compare the terminator on the raw line for plain `<<`, stripping only tabs
for `<<-`. Add the three fixtures above to arm 26 leg (d):

```awk
!inside {
  # scan every `<<` on the line, not just one anchored at EOL
  rest = $0
  while (match(rest, /<<-?[ \t]*("[A-Za-z_][A-Za-z0-9_]*"|'[A-Za-z_][A-Za-z0-9_]*'|[A-Za-z_][A-Za-z0-9_]*)/)) {
    tok = substr(rest, RSTART, RLENGTH); rest = substr(rest, RSTART + RLENGTH)
    sub(/^<<(-?)[ \t]*/, "", tok)
    if (tok ~ /^["']/) continue
    term = tok; dash = ($0 ~ /<<-/); inside = 1; break
  }
  next
}
{ line = $0; if (dash) sub(/^\t+/, "", line) }   # plain `<<` => NO stripping
inside && line == term { inside = 0; next }
```

### WR-02: the VAC-08 apply-on-merge frontier exemption has no ceiling, so one failed TEST apply silently disables the ledger-presence ratchet indefinitely

**File:** `scripts/test-ledger-drift-check.sh:425-476` (the exemption), `:515` (the summary line)

**Issue:** `frontier_tip` is the greatest authoring timestamp among repo migrations **measured
present** in the TEST ledger; every measured-missing migration with `ts > tip` is removed from
`new_file` before `new_count` decides the gate. Nothing bounds how many entries that removes and
nothing bounds how long they stay removed. The only compensating readings are a `::notice::` and
an echoed `ledger frontier: tip=…` line — neither of which fails anything — plus the absurdity
floor, which needs the match rate to fall **below 50 %** before it fires.

**Failure scenario (concrete, and it is the phase's own open case):**
1. `20260910000000_x` merges. `apply-test` fails — e.g. the data-dependent RAISE booked as
   `[164.8-DATA-DEPENDENT-MIGRATION-ESCAPE]`, whose stated interim remedy is to revert the merge.
   The merge is on `main` regardless; branch protection is deferred, so nothing blocks it.
2. `sql-tests` on the next PR: tip is still `20260909…`, so `_x` is `> tip` → exempted →
   `0 NEW drift` → green.
3. Every subsequent migration is also `> tip` and also exempted. The window widens without limit,
   and VAC-08's ledger-presence half reports green while TEST is arbitrarily far behind the repo.

The comment at `:453-459` acknowledges the direction ("the exempt window widens by the same
amount … A narrow, quiet lag is NOT caught here") and books it as `[164.8-PUSH-RACE-VAC08]`, but
"narrow" is not enforced anywhere — the gap between "narrow" and the 50 % floor is unbounded, and
this repo's own idiom for tolerated exceptions is a hard ceiling (`WAIVED_CEILING = 0` in
`scripts/mutation-runner/run.mjs`, held through two founder decisions).

**Fix:** give the exemption the ceiling every other tolerance in this repo has, so the window is a
ratchet rather than a hole:

```bash
# The exemption covers the apply-on-merge WINDOW, which is at most the migrations
# added since the last merge. More than that is a stalled apply, not a timing artefact.
FRONTIER_EXEMPT_CEILING="${FRONTIER_EXEMPT_CEILING:-3}"
if [ "$exempt_count" -gt "$FRONTIER_EXEMPT_CEILING" ]; then
  echo "::error::${GATE}: ${exempt_count} migration(s) above the ledger frontier (tip ${frontier_tip}), ceiling ${FRONTIER_EXEMPT_CEILING}. That is not an apply-on-merge window — supabase-migrate.yml's apply-test has stopped applying to TEST. Fix the apply; do NOT raise the ceiling."
  bad=1
fi
```

and add a red self-test arm driving `exempt_count > ceiling` so the ceiling itself is armed.

### WR-05: the world-readable backup artifact carries seven script-written files that are neither secret-scanned nor redacted, and the step comment claims otherwise

**File:** `.github/workflows/test-restore-from-baseline.yml:1407-1411` (the scope claim),

**Issue:** `RESTORE_OUT_DIR` is pointed at the same directory as the backup

`census.sql`, `pre-census.txt`, `post-census.txt`, `survivors.keys`, `survivors.sql`,
`restore.sql`, `refdata.sql` — plus `census.err`, `marker.err`, `refdata.err`, `transaction.out`.

* `scan_for_secrets` runs in the **backup** step, i.e. **before** the script produces any of those
  files, and it scans exactly two: `ledger.csv` and `schema-before.sql` (`:1124-1125`).
* The redaction step's globs are `*.err`, `*.log`, `*.out` only (`:1424`, `:1439`), and
  `test-restore-workflow-wiring.test.ts:626-634` pins them at exactly two loops so they "must never
  widen".
* So the seven files above reach a world-readable artifact having passed through **neither**
  control.

The step's own scope comment at `:1407-1411` states the opposite: *"ledger.csv and the two .sql
files are left byte-exact by design, and are secret-SCANNED at the point they are written."* There
are not two `.sql` files in that directory — there are four (`schema-before.sql`, `census.sql`,
`survivors.sql`, `restore.sql`, plus `refdata.sql`), and only one of them is scanned.

**Failure scenario:** `pre-census.txt` emits column 4 of every survivor row as full DDL —
`pg_get_triggerdef(...)` and a reconstructed `CREATE POLICY … USING (<qual>)` read off **live
shared TEST**, plus `nonpostgres_rel=`/`nonpostgres_fn=` lines naming objects and their owning

redaction step "is NOT" the closure for it. On the real TEST those policy expressions name tables,
columns and role predicates that are not otherwise public. Nothing has been proven to leak a
credential, which is why this is WARNING rather than BLOCKER — but the control's declared scope
and its real scope differ, and a reader trusting the comment will not look.

**Fix:** move the scan to cover the whole artifact directory immediately before the upload, or run
it a second time after the script:

```yaml

        if: always()
        run: |
          set -euo pipefail
          outdir="${RUNNER_TEMP}/test-backup"
          [ -d "${outdir}" ] || { echo "no artifact directory"; exit 0; }
          re='postgres(ql)?://|@[a-z0-9.-]+\.supabase\.(co|com)|[a-z]{20}\.supabase|\\connect|eyJ[A-Za-z0-9_-]{10,}'
          bad=0
          for f in "${outdir}"/*; do
            [ -f "${f}" ] || continue
            case "${f}" in *ledger.csv) continue ;; esac   # ALTER DATABASE carve-out, already scanned
            rc=0; n="$(grep -acE "${re}" "${f}")" || rc=$?
            [ "${rc}" -le 1 ] || { rm -f "${f}"; echo "::error::unreadable: $(basename "${f}") — withheld"; bad=1; continue; }
            [ "${n}" = "0" ] || { rm -f "${f}"; echo "::error::secret shape in $(basename "${f}") — WITHHELD from the public artifact"; bad=1; }
          done
          [ "${bad}" -eq 0 ]
```

and correct the `⚠️ SCOPE:` paragraph at `:1407-1411` to name the files it actually covers.
