# Phase 164.6.6.1 MT5SCRUB: silent-failure review (SFH)

Scope: `git diff origin/main...HEAD`, analytics-service sources only. Base read: CONTEXT.md, `mt5_terminal_scrub.py` in full, the scrub verb and its remote literal in `mt5_client.py`, `mt5_relogin.py` (scrub, relaunch, debt, boot, entry), both validate sites, `main.py`, `mt5_session_episodes.py`. Report is MEDIUM and above only.

Worst severity: HIGH (2 findings).

## SFH-01 HIGH (confidence 8): the validation scrub reports `scrubbed`, clears the owed mark and stays silent while client deal caches or a profile `accounts.dat` survive

- Where: `services/mt5_terminal_scrub.py:409-422` (`_delete_landed`), `:425-438` (`_classify`), `:478-480` (mark cleared); verdict fields produced at `services/mt5_client.py` `_REMOTE_TERMINAL_SCRUB_SRC` (`trades_errors`, `profile_errors`, `profile_accounts_found`).
- Defect: `_delete_landed` looks at `refused` and `accounts_errors` only. The validation path passes `delete_trades=1` (`_VALIDATION_SCRUB_DELETE_TRADES`), and the remote literal records every failed `rmtree` / `os.remove` / `listdir` of `Bases/<server>/trades/<account>` in `trades_errors`. Nothing reads that list. `profile_accounts_found > 0` (the S-07 tripwire for an `accounts.dat` under the per-user profile directory, which the literal never deletes) and `profile_errors` are likewise unread.
- Failure scenario: a client validates, the scrub kills the terminal, deletes `Config/accounts.dat`, but `shutil.rmtree` on the client's account-named cache directory raises (Wine file lock, `PermissionError`, `OSError`). `refused == 0`, `accounts_errors == []`, the house relaunch verifies, so `_classify` returns `scrubbed`. `clear_mt5_scrub_owed` runs, only an INFO line is logged, no alert fires, and the next validation is not refused. The client's account number stays on the disk under a directory name the house goal says must not persist. The row's closed metadata key set (`_SCRUB_ROW_METADATA_KEYS`) has no `trades_errors` or `profile_errors` count, so even the audit trail cannot show it later. The same happens when `os.listdir(Bases)` fails (`trades_errors` only).
- Fix: treat a non-empty or unparseable `trades_errors` (when `delete_trades == 1`) and a non-zero or non-int `profile_accounts_found` as `errored` in `_delete_landed` (kind `failed`, mark kept, ERROR alert), and add `trades_errors` and `profile_errors` counts to the row's key set.

## SFH-02 HIGH (confidence 8): the jobs-terminal scrub path ignores `accounts_errors` entirely, so a failed `accounts.dat` delete is logged at INFO as a healthy recycle

- Where: `services/mt5_relogin.py:1544-1574` (`_classify_scrub_relaunch`), `:1913-1958` (level ladder), `:1876-1898` (detail line). `grep accounts_errors services/mt5_relogin.py` returns no hit.
- Defect: the classifier decides on `_recycle_landed` (matched / terminated counts), then the relaunch and post-relaunch status. A verdict with `refused == 0` and `accounts_errors == ["PermissionError"]` is `KIND_IPC_FAULT_RECYCLED` (verified house session), level `logging.INFO`. `accounts_errors` is not even printed in the `detail` line (only `accounts_deleted`, `accounts_missing`, `trades_deleted`, `profile_accounts_found`), so an operator reading the log cannot see the failure. `profile_accounts_found` is printed but never raises the level.
- Failure scenario: the delete of the saved `accounts.dat` fails after the kill. The credentialed relaunch verifies, so `clear_mt5_relaunch_debt` runs (`:1528-1529`). The stale saved copy, which is the L7 Login-dialog wedge source this phase exists to remove, stays on the jobs terminal with an INFO line and no debt. The validation path (`_delete_landed`) does treat this as `failed`, so the two paths now disagree about the same verdict.
- Fix: in `_classify_scrub_relaunch` (or the level ladder) raise to ERROR when `accounts_errors` is non-empty or not a list, include its count in `detail`, and use the same predicate as the validation path (share one function rather than two).

## SFH-03 MEDIUM (confidence 5): jobs path, `matched == 0` leaves `accounts.dat` in place and the outcome is a WARNING with the debt cleared

- Where: `services/mt5_relogin.py:1915-1930` and `:1951-1958`.
- Defect: when the scrub finds no `terminal64.exe` the literal refuses (`refused=1`) and deletes nothing. If the credentialed relaunch then authorizes and verifies, the kind is `recycle_not_landed`, level WARNING ("either no terminal was running and the relaunch launched one, or the process name did not match; the first live run decides"). The ERROR escalation at `:1957` applies only when `_recycle_landed(verdict)` is true, which it is not here. The debt is cleared because `post_status` is verified. A renamed image or a Wine process-name change then turns every escalation into a silent no-op scrub at WARNING while the stale saved account remains. The validation path alerts at ERROR for the same verdict (`refused` leads to `SCRUB_KIND_REFUSED`).
- Fix: log `refused != 0` at ERROR regardless of `_recycle_landed`, or at least on the second consecutive occurrence.

## SFH-04 MEDIUM (confidence 5): a builtin `TimeoutError` raised inside the scrub thread is labelled `abandoned`

- Where: `services/mt5_terminal_scrub.py:475-476`.
- Defect: `except TimeoutError` cannot tell `asyncio.wait_for`'s timeout from a `TimeoutError` / `socket.timeout` raised by `Mt5Client(host, port)` (`rpyc.classic.connect`) inside the thread. In Python 3.11+ both are the same class. A connect timeout is a clean failure where nothing crossed, but it is recorded and alerted as `abandoned` ("thread may still be running; lease release fences it"), the wrong operator diagnosis, and the row `kind` is wrong. The alert still fires and the mark is kept, so no state is lost.
- Fix: have `_scrub_validation_terminal_blocking` wrap the thread's own raises (or catch around `to_thread` with a flag set by the thread on exit, as the probe event does) so `abandoned` means the bound fired.

## SFH-05 MEDIUM (confidence 4): the abandoned scrub thread can still clear the relaunch debt after the lease is released

- Where: `services/mt5_relogin.py:1528-1529` (`clear_mt5_relaunch_debt`, no epoch check), reached from the thread orphaned by `services/mt5_terminal_scrub.py:465-476`.
- Defect: after `wait_for` fires, the lease exits and the fence refuses the zombie's next client crossing, which is the intended containment. A crossing already in flight when the lease released (`_read_post_relaunch_state`'s `session_snapshot`) can still return `verified`, and the registry write that follows is not fenced. By then a later validation may hold the terminal and have logged a client in, so the debt is cleared on a terminal that is not on the house account. The scrub-owed mark is safe (cleared on the event loop, only after a non-timeout return). The window is narrow (the budget is built so crossings fit before the bound), so this is low confidence.
- Fix: guard the clear with the same epoch check `_note_terminal_holder` uses, or return the verdict and clear on the event loop only when the scrub was not abandoned.

## SFH-06 MEDIUM (confidence 4): a stuck pending scrub is invisible, because refusals while it is pending are WARNING-only and the scrub's own alert only fires on completion

- Where: `services/mt5_terminal_scrub.py:343-351` (pending branch of `report_scrub_owed_refusal`) and `:537-539` (`wait_s=None`).
- Defect: while `key in _PENDING_SCRUB_KEYS`, every refused validation logs one WARNING with no capture, as CONTEXT specifies for the queued case. The task acquires the lease unbounded. If the lease is held by something that never releases it (a leaked holder, a hung validation), the scrub never runs, never alerts, and the pending key never clears, so every wizard validation is refused at WARNING indefinitely with no ERROR and no Sentry event. The CONTEXT carve-out assumes the pending scrub finishes.
- Fix: stamp the pending entry with its schedule time and, past a bound (for example `_SCRUB_PROBE_WAIT_S + _VALIDATION_SCRUB_BUDGET_S` plus margin), report the refusal through `_alert_scrub_failed` instead of the WARNING branch.

## Checked and clean

- No credential, account number, host, port or terminal key reaches a log line, alert, exception text, row or Sentry call in the new code: alerts and rows use closed cause/kind/site sets and `type(exc).__name__`; the house triple only reaches `initialize_with_credentials`; the scrub verb takes an int flag only.
- The owed and debt marks are cleared only on `scrubbed` (validation) or a verified house snapshot (debt). `refused`, `failed`, `relaunch_unverified`, `abandoned` and the skip kinds keep them.
- Never-raises wrappers (`scrub_validation_terminal`, `schedule_validation_terminal_scrub`, `mark_validation_terminal_owed_at_boot`, `run_owed_validation_scrub_in_lease`, `record_mt5_terminal_scrub`, `_alert_scrub_failed`) do not swallow silently: each logs at ERROR or WARNING with the exception class, and every non-scrubbed kind alerts at ERROR.
- Not reported (documented, LOW): row `status` is `"ok"` for every kind; no reader exists yet (deferred to Phase 164.6.8), so a future `latest_cron_success("mt5_terminal_scrub")` would count a failed scrub as success.
