## Summary

The four areas the brief asked about were traced end to end against source, and mostly hold.

- **Concurrency (check 1): holds EXCEPT when the scrub's own connect or verb is slow (WR-05).** The W-1 gate is the probe thread's own
  `threading.Event` (set in the thread's `finally`), registered on every schedule, waited for under a
  bound, and the scrub is skipped (mark kept, `probe_in_flight` alert) when it is still unset. The
  pending key is released inside the lease body, in a `finally`, with a `released` guard on the outer
  path. The owed gate sits after lease acquisition and before any client construction at both validate
  sites. Because both the wizard and the worker also check `mt5_relaunch_debt`, a zombie scrub verb
  that lands after another scrub succeeded still leaves a gate that refuses. The caveat: the fence is a
  per-METHOD entry check (`_assert_live` is the first statement of each client method), not a
  per-crossing one. `scrub_terminal_account_data` makes three crossings behind one fence and
  `Mt5Client.login` makes two or three, so "at most one crossing" is really "at most one client method".
  The design leans on the W-1 event (not the fence) for the probe thread, and on the owed/debt gates for
  a zombie scrub. Both hold for the cases they were built for. They do not cover a scrub thread that is
  slow BEFORE its verb, because the gates are read at lease entry and the racing holder is already past
  them, and the validation scrub has no pre-verb budget gate (WR-05).
- **Credential residue (check 2): holds.** Every new log line, alert, row and exception carries class
  names, codes, counts or closed literals. `house` is a call argument, never module state. The
  `ScrubRelaunchResult` fields are structured only. `sentry_init.py` sets `include_local_variables=False`,
  so a captured frame does not expose the tuple. `_try` and `_relaunch_as_house` return codes only.
  **Terminal command line:** the credential crosses as `initialize(login=..., password=..., server=...)`
  keyword arguments over the rpyc channel, never as argv. CONTEXT S-11(c) measured the terminal that a
  credentialed rpyc call launched: one `terminal64.exe`, `/portable` present, no argument beyond it. That
  is the only launch shape measured (a launch performed by a credentialed call, not by a bare one), and
  it is the shape the code uses, so the surface is covered by measurement, not by construction.
- **Jobs-terminal escalation (check 3): holds on the three named properties, with one liveness gap
  (WR-02).** No bare `initialize` follows a scrub (`_relaunch_as_house` and `_settle_relaunch_debt` are
  credentialed only, and `session_snapshot` is a read). The debt is cleared in exactly three places, each
  gated on `post_status == verified`. The round-trip count is unchanged (2+1+3+2 = 8), so the derived
  budget stays at 250 s under the 300 s ceiling.
- **Remote literal (check 4): holds.** The delete block is inside `if refused == 0`, which requires a
  non-failed walk, `matched >= 1`, every match terminated, and every match exited. It names only
  `Config/accounts.dat` and, when `delete_trades == 1`, children of `Bases/<x>/trades`. The profile
  directory is only counted.

The defects are in what the scrub does NOT treat as a failure, and in a starvation path that the
debt design depends on.

## Warnings (MEDIUM)

### WR-01 (MEDIUM, confidence 8): the validation scrub reports `scrubbed` and clears the owed mark when the deal-cache delete failed

**File:** `analytics-service/services/mt5_terminal_scrub.py:409-438` (`_delete_landed`, `_classify`);
literal at `analytics-service/services/mt5_client.py:1856-1896`; row keys at
`analytics-service/services/mt5_terminal_scrub.py:237-252`

**Issue:** The validation scrub is the only caller that passes `delete_trades=1`. The remote literal
records every failed cache delete in `trades_errors` and still returns `refused == 0`. `_delete_landed`
inspects only `refused` and `accounts_errors`. So an `OSError` or `PermissionError` on a cache entry (a
read-only attribute or ACL, or a partial `shutil.rmtree` that leaves a child behind; the processes have
all exited by this point, so an open handle is not the trigger) yields `kind == scrubbed`, `clear_mt5_scrub_owed(key)` runs, no alert fires, and the
row carries only `trades_deleted` (the error list is not a metadata key). The only trace is the verb's
own WARNING line.

Verified by driving the real classifier with a verdict of `refused=0`, `accounts_errors=[]`,
`trades_errors=['PermissionError']`, `profile_accounts_found=2` and a verified relaunch. The result is
`scrubbed`. The module docstring promises "Only a scrub that DELETED ... clears the mark", and success
criterion 1 includes the client's deal history. No test covers `trades_errors`
(`test_TERMINAL_SCRUB_a_delete_that_reported_ERRORS_is_failed_never_scrubbed` covers `accounts_errors`
only). `profile_accounts_found > 0` (the tripwire the literal's own comment calls "the tripwire if that
ever changes") is likewise recorded and never acted on.

**Fix:**
```python
def _delete_landed(verdict):
    ...
    errors = verdict.get("accounts_errors")
    trades_errors = verdict.get("trades_errors")
    errored = (
        not (isinstance(errors, list) and len(errors) == 0)
        or not (isinstance(trades_errors, list) and len(trades_errors) == 0)
    )
    return refused, errored
```
Add `trades_errors` (a count) and `profile_accounts_found` to the row, treat a non-zero
`profile_accounts_found` as `failed` (or at least alert), and add a test that a non-empty
`trades_errors` keeps the mark.

### WR-02 (MEDIUM, confidence 6): an outstanding jobs-terminal relaunch debt is invisible, and the heal that pays it can be starved by job traffic

**File:** `analytics-service/services/mt5_relogin.py:2680-2710` (the `Mt5TerminalBusyError` arm of
`heal_mt5_terminal_session`); `_relogin_lease_wait_s` default 2.0 s at `mt5_relogin.py:620`;
`_heal_blocking` debt branch at `mt5_relogin.py:2317`

**Issue:** D-10 pays the debt only inside `_heal_blocking`, which runs only after the heal wins the
lease. The heal's acquisition is bounded at 2 s (`_MT5_RELOGIN_LEASE_WAIT_DEFAULT_S`), while the three
job sites acquire with `wait_s=None` and nothing in the job path consults `mt5_relaunch_debt` (it is read
only in `routers/exchange.py`, `ingestion/mt5.py` and `mt5_relogin.py`). Against a scrubbed, unverified
jobs terminal, each job's `Mt5Client.login()` opens with a credential-less `initialize()`, which S-03(b)
and S-10 measured at 25-30 s before it fails. The jobs therefore hold the lease for most of every tick,
and each tick's bounded acquire expires. The busy arm then logs at INFO that "a busy terminal is a
terminal somebody is already successfully using, which is itself evidence the session is fine" and
records `busy_skip`. With a debt outstanding that sentence is false, and there is no ERROR on that path
(`_log_relaunch_debt_outstanding` fires only from `_settle_relaunch_debt`). That is a path that leaves
the jobs terminal logged out for as long as the backlog drains, reported as healthy. CONTEXT D-11
accepts a slow launch that the NEXT tick pays. It does not accept a tick that cannot run.

**Fix:** In the busy arm, read `mt5_relaunch_debt(mt5_terminal_key(host, port))`. When set, log at ERROR
(debt outstanding and the heal could not get the lease) instead of the "session is fine" INFO. Consider
also raising the heal's lease wait to one rpyc crossing while a debt is owed, which the existing
`_MT5_RELOGIN_LEASE_WAIT_CEILING_S` permits. A longer-term option is a debt check in the job sites'
`login()` that fails fast instead of waiting 25-30 s on an account-less terminal.

### WR-03 (MEDIUM, confidence 6): a jobs-terminal scrub whose `accounts.dat` delete errored is classified `recycled` at INFO

**File:** `analytics-service/services/mt5_relogin.py:1544-1573` (`_classify_scrub_relaunch`) and
`:1913-1914` (the level ladder)

**Issue:** `accounts_errors` is not read anywhere in `mt5_relogin.py` (zero occurrences). The literal
returns `refused == 0` with `accounts_deleted=0`, `accounts_missing=0` and `accounts_errors=[...]` when
`os.remove` raises. `_classify_scrub_relaunch` consults `_recycle_landed` (process counts) and the
relaunch result only. A scrub whose delete failed but whose credentialed relaunch verified therefore
returns `ipc_fault_recycled`, logs at INFO ("scrub landed"), and ends the run. Criterion 4's whole
rationale is that the stale saved house login must be gone. The `detail` line prints
`accounts_deleted=0 accounts_missing=0` but not the errors, and the sink is INFO. The validation side
already refuses this shape (`_classify` returns `failed`), so the two scrub consumers disagree on what a
clean delete is. A credentialed login with the correct password would usually overwrite the stale entry,
which is why this is MEDIUM and not HIGH.

**Fix:** Share one predicate between both consumers (move `_delete_landed`'s logic next to
`ScrubRelaunchResult`). In `_escalate_ipc_fault`, treat `accounts_errors != []` like `refused != 0`: add
`accounts_dat_kept=delete_errored` to the detail and set the level to ERROR.

### WR-04 (MEDIUM, confidence 3): nothing stops the validation endpoint from equalling the job endpoint, and then every validation scrub deletes the jobs terminal's deal caches

**File:** `analytics-service/services/mt5_relogin.py:954-1014` (`read_env_validation_gateway_endpoint`);
consumers `mt5_terminal_scrub.py:140` (`_VALIDATION_SCRUB_DELETE_TRADES = 1`) and
`mt5_terminal_scrub.py:619-672`

**Issue:** `read_env_validation_gateway_endpoint` checks presence, integer port and private host. It
never compares against `MT5_GATEWAY_HOST` / `MT5_GATEWAY_PORT`. Before this phase an equal pair merely
lost the isolation 164.6.6 built. Now it is destructive. The validation scrub kills the shared terminal
after every validation and passes `delete_trades=1`, which deletes the per-account deal caches of the
terminal that serves live jobs. The job path deliberately passes 0 until 164.6.6.3 fixes Finding C (a
fresh cache hands back a partial deal history, a silent wrong-metric risk). Nothing in the code prevents the pair from being equal. Confidence is
low (3) because it needs an operator misconfiguration. I searched for a guard or a decision that
allows equality in 164.6.6's CONTEXT and RESEARCH, `tests/test_mt5_concurrency.py` (its routing pin
checks which reader each site calls, not the values) and `docs/runbooks/mt5-go-live.md`. None exists,
and the runbook's rollback is "unset `MT5_VALIDATION_GATEWAY_HOST`" (which refuses), not "point it at
the job gateway". So the finding rests on the new destructiveness alone, not on a likely rollback.

**Fix:** In `read_env_validation_gateway_endpoint`, compare `mt5_terminal_key(host, port)` with the job
pair's key (via `read_env_gateway_endpoint`) and return `None` with a named log-once fault when they are
equal, so both validate sites take their existing D-05 refusal. Add the matching boot-time refusal in
`mark_validation_terminal_owed_at_boot`.

### WR-05 (MEDIUM, confidence 5): the validation scrub has no pre-verb budget gate, and a slow scrub thread can run its kill and delete under the next lease holder

**File:** `analytics-service/services/mt5_terminal_scrub.py:376-406` (`_scrub_validation_terminal_blocking`)
and `:457-480` (`_scrub_decide`); `analytics-service/services/mt5_relogin.py:1480-1530`
(`scrub_and_relaunch_as_house`, the unconditional verb call at ~1505 and the relaunch-only gate at ~1517)

**Issue:** The jobs path refuses to start a scrub unless `_affordable(deadline,
SCRUB_RELAUNCH_RESERVE_CROSSINGS)` holds (`mt5_relogin.py:1762`). That gate is the W-2 control ("no scrub
path may delete the saved login unless a relaunch fits the budget"). The validation path has none.
`_scrub_validation_terminal_blocking` builds the client inside the thread and calls
`scrub_and_relaunch_as_house`, which calls the verb unconditionally and gates only the RELAUNCH on
`_affordable(deadline, 2)`. The deadline is computed on the loop thread before the thread starts, and
`rpyc.classic.connect` has no timeout of its own (the module docstring says so; the budget carries only a
10 s slack for it). Two traces:

1. Connect takes about 120 s. The verb then runs, kills the terminal and deletes `accounts.dat` in about
   2 s. About 38 s remain, under the 60 s a relaunch needs, so the relaunch is skipped. That is the W-2
   shape: a delete with no affordable relaunch. On the validation terminal the kept mark and debt contain
   the damage (the next validation is refused, pays the scrub), so it is not a silent outage.
2. Connect over about 70 s plus a slow verb. The verb's remote call is three crossings behind ONE
   `_assert_live`, so it can straddle the `wait_for` bound and the lease release (which happens only after
   the alert and the up-to-5 s row insert). The kill and delete then land under the NEXT holder. Under the
   worker's inline scrub nothing waits for a scrub thread: `_UNFINISHED_PROBES` registers probe events
   only. The zombie's kill can land after the inline scrub already verified and cleared both the mark and
   the debt, leaving a dead terminal with no `accounts.dat`, no mark and no debt, until a failed
   validation self-heals it. The owed and debt gates do not cover this, because they are read at lease
   entry and the racing holder is already past them.

Both need a slow `connect`, which is the gateway-unhealthy case, so confidence is moderate.

**Fix:** Add the same pre-verb gate the jobs path has: in `scrub_and_relaunch_as_house` (or at the top of
`_scrub_validation_terminal_blocking`), return a `skipped_budget` result without calling the verb unless
`_affordable(deadline, SCRUB_RELAUNCH_RESERVE_CROSSINGS)`. Register the scrub thread's own done-event in
`_UNFINISHED_PROBES` (set in the thread's `finally`) so a later scrub or inline scrub waits for it, the
same way it waits for a probe thread.

### 2. The design choice: a fired profile tripwire is `failed` on the validation path

**Ruling: `failed` (fail closed) is the correct classification. It is not a finding. ERROR-alert-but-`scrubbed` is the wrong alternative.**

Reasoning, against the phase goal ("the validation terminal is wiped of every validated account") and the house rule (no path leaves a client account saved without an alert):

- The tripwire fires only when S-07's measured layout has stopped holding (CONTEXT S-02, S-07 and RESEARCH line 298 measured the install directory as the only data directory under both launch modes). That measurement says the tripwire is unlikely to fire. It does not say a firing is benign: in the world where it fires, the terminal may be keeping its data in the profile directory, where the literal never deletes.
- `scrubbed` would clear the owed mark and write a `kind = scrubbed` audit row asserting the goal met while the scrub knows it was not. The next validation would then save another client's login into the same unreachable place, with only an hourly-windowed capture as the signal. An alert alone satisfies the letter of the house rule and not the goal.
- Report-only for this count is exactly the state SFH-01 (HIGH, confidence 8) flagged. Plan 01's "reported only and gates nothing" line is about `profile_errors`, which stays that way. Reversing the fix would reopen a HIGH.
- The "repeated kill per validation" cost is smaller than framed. Every validation already ends in a kill, delete and house relaunch; that is the design's normal cost. The marginal cost of the tripwire is that validations are refused instead of served. It lands on the validation terminal only (not the job terminal, unless WR-04's equal-endpoint misconfiguration is present). Each kill ends in a house relaunch, so the cost is liveness and noise, not data. On the worker's inline path the refusal is a transient `Mt5ClientError` (`services/ingestion/mt5.py:255-262`), so the retries are bounded by `compute_jobs.max_attempts` (schema default 3, `20260411144407_compute_jobs_queue.sql:122`; not verified for the validation job kind). On the wizard path, `schedule_validation_terminal_scrub` dedupes on `_PENDING_SCRUB_KEYS` (`mt5_terminal_scrub.py:601`), so a burst of refused attempts schedules one scrub, and a new one runs only when the user tries again after it finished.

What is NOT designed, and is rated below.

### RR2-01 (MEDIUM, confidence 4): a tripwire `failed` has no distinct cause and no operator path, so a condition that can never self-clear is reported as one that will

**File:** `analytics-service/services/mt5_terminal_scrub.py:225-232` (`_KIND_CAUSES`), `:310-317` (`_alert_scrub_failed` text), `:324-327` (the per-cause capture window), `:432-441` (`_classify`)

**Issue:** The fix routes a fired tripwire to `SCRUB_KIND_FAILED`, which maps to cause `failed`. That cause is shared with every transient failure (a raised verb, a locked cache entry). Two consequences:

1. The Sentry capture is windowed per cause (`_SCRUB_ALERT_WINDOW_S = 3600`). A tripwire capture can be suppressed by an unrelated `failed` capture in the previous hour, and the reverse.
2. The ERROR text tells the operator "the next validation owes the scrub (Phase 164.6.6.1 D-08)". For every other `failed` that is true, because the next scrub retries. For the tripwire it is false: the literal never deletes the profile copy, so no later scrub can clear it.
