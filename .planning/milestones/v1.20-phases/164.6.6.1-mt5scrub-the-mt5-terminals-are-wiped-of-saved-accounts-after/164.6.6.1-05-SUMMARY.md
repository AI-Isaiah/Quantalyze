# Phase 164.6.6.1 Plan 05: validation-terminal post-verdict scrub Summary

**`services/mt5_terminal_scrub.py`: after a validation's verdict, a supervised background task takes the validation terminal's lease for `house`. It waits out any validation probe thread still in flight, deletes `accounts.dat` and the per-account `trades` caches, and relaunches the terminal with the house credentials. Only a clean delete followed by a house-verified relaunch clears the "scrub owed" mark. Every attempt writes one closed `cron_runs` row, and every exit that does not end `scrubbed` alerts.**

## What was built

- **`schedule_validation_terminal_scrub(host, port, *, site, probe_thread_done)`.** Synchronous, and it never raises. In order, it:
  1. sets the scrub-owed mark;
  2. registers the probe thread's own event;
  3. spawns at most one task per terminal, held in `_SCRUB_TASKS` (the `_audit_tasks` strong-reference shape).

  It is not added to `main.lifespan`'s task list. A missing event loop logs ERROR and leaves the mark set.
- **`scrub_validation_terminal`** is the task. It takes `async with mt5_terminal_lease(key, wait_s=None, holder=HOLDER_HOUSE, site=SITE_TERMINAL_SCRUB)` and then runs `_scrub_under_lease`. If the lease itself raises, it still alerts and writes a `failed` row. The pending key is released inside the lease body, while the lock is still held (fix commit e94dbba1b). If the lease's acquisition raised, an inner `finally` releases it instead. Both sit inside the single outer `except Exception` guard, so the shared never-raises predicate holds.
- **`_scrub_under_lease`** (the lease is already held) runs, in order:
  1. the W-1 wait, bounded by `_SCRUB_PROBE_WAIT_S`, over every registered event, re-reading the registry after each wait;
  2. the house triple;
  3. `asyncio.wait_for(asyncio.to_thread(_scrub_validation_terminal_blocking, ...), timeout=_VALIDATION_SCRUB_BUDGET_S)`. The client is built inside the thread, and the call uses `delete_trades=1`;
  4. classification into a kind;
  5. the mark cleared on `scrubbed` only;
  6. an alert on every other kind;
  7. one row.

  Any `Exception` inside becomes `failed` and still gets its alert and its row. This covers client construction, `Mt5SessionAbandoned` and anything unexpected.
- **`_scrub_validation_terminal_blocking`** calls plan 03's `scrub_and_relaunch_as_house`. On a verified relaunch it re-stamps the holder as `house` through `_note_terminal_holder` (PATTERNS (d2)). Without that, the worker's inline path would leave the terminal recorded as `validation`.
- **`run_owed_validation_scrub_in_lease`** is the worker's inline path, run under the worker's own validation lease. It returns True only for `scrubbed` and never raises.
- **`report_scrub_owed_refusal(*, site, key)`** is for plan 06. If a scrub is already queued for the key, it logs one WARNING (cause `owed_validation_refused`) with no capture. If nothing is queued, it logs ERROR and makes the windowed capture.
- **Kinds:**
  - `scrubbed`
  - `refused`
  - `relaunch_unverified`
  - `failed`
  - `abandoned`
  - `skipped_probe_in_flight`
  - `skipped_no_house_credentials`

  Alert causes form a closed set: each kind's cause, plus `owed_validation_refused`, plus `unrecognised_cause`. A caller string is never interpolated, and the site is normalized through `_SITES`.
- **Row:** `cron_name = 'mt5_terminal_scrub'`, inserted closed (`status 'ok'`, `started_at == completed_at`). No migration is needed (`cron_name` has no CHECK). The metadata key set is closed:
  - `schema_version`, `kind`
  - `terminal_role`: always `"validation"`, never the key
  - `site`
  - `refused`, `accounts_deleted`, `accounts_missing`, `accounts_errors`, `trades_deleted`, `profile_accounts_found`
  - `relaunch_status`
  - `records_account_number: false`
- **Budget:** `_VALIDATION_SCRUB_BUDGET_S` = `SCRUB_RELAUNCH_RESERVE_CROSSINGS` (5) × `MT5_REQUEST_TIMEOUT_S` (30) + 10 s connect slack = 160 s at the defaults, on the worker chain. `_SCRUB_PROBE_WAIT_S` = `MT5_VALIDATE_REQUEST_TIMEOUT_S` + 5 = 60 s, the wizard's stage bound. It is imported from `services.mt5_client`, as `routers/exchange.py` does, so the service does not import FastAPI.
- **Flagged default, kept:** Journal `logs`, `mail` and `subscriptions` are not deleted (CONTEXT "Still OPEN"). Plan 07 records this as residue.

**6. [Rule 1 - Bug] A schedule could be dropped while a finished scrub still read as pending**
- **Found during:** final review, after the first version of this SUMMARY.
- **Issue:** the pending key was released only after the whole lease exited. The lease releases the lock first and then awaits its handover row, bounded at 5 s; that row is written on almost every scrub because the holder moves from validation to house. A validation that took the terminal in that gap scheduled its scrub, was deduped onto the finished task, and left the mark set with no scrub coming. The next validation would then page `owed_validation_refused` for an internal race.
- **Fix:** the key is released inside the lease body, while the lock is still held. A raise before the body ran releases it in the outer `finally` instead, guarded by a local `released` flag so it never drops a key a newer task has since taken. The never-raises predicate's shape is unchanged.
- **Gate:** `test_TERMINAL_SCRUB_a_validation_in_the_gap_after_the_lock_release_still_gets_its_scrub`, confirmed by neuter 3.

## Notes for plan 06 and the reviewer

- **Call `schedule_validation_terminal_scrub` while the validation's own lease is still held.** The probe event must be registered before the scrub can acquire the terminal. The W-1 wait re-reads the registry, so a registration that arrives during the wait is also covered. A registration that arrives after the scrub has crossed is not.
- **The boot hook is plan 06's, and must be named `mark_validation_terminal_owed_at_boot`** (plan 01's note). This module does not provide it. Until it ships, a restart forgets an owed scrub, as `mt5_client`'s registry comment says.
- **On the worker's inline path, False from `run_owed_validation_scrub_in_lease` must mean "do not probe in this lease": refuse or re-queue, then release.** After `abandoned`, the scrub thread may still be running under the worker's own lease, and the fence engages only when that lease releases. After `skipped_probe_in_flight`, a probe thread is still in flight on the terminal. Probing in the same lease in either case would race a live thread.
- The abandoned path relies on the lease's epoch bump to fence the still-running thread. The scrub verb's own fence check runs only at its first statement, so a thread already mid-crossing finishes that crossing. This is the same limit the heal has.
- Observation, not a defect of this plan: `Mt5Client`'s `mt5.stage` structlog events print `terminal_key` to stdout. That field is on the client's closed allow-list (153.3 D-32), and the scrub reuses the client unchanged. This plan's own rows, its log records and its alerts carry no key, as the hygiene gates check.
