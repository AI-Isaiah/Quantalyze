## MEDIUM-01 (new): the predecessor gate no longer requires any CI verdict to exist

**Location:** `scripts/classify-changed-paths.mjs:407` (`predecessorVerdict`), specifically the
`runs.length === 0` check at `:421`ff, which is the only presence requirement left. The round-2
predicate asked `?check_name=frontend` and refused when it was absent. Round 3 widened the read to
every Actions check run and dropped that requirement. iter5's LOW-04 fix (b) read "every check run
… non-red, **plus `frontend` present**", and only the first half was implemented.

**Measured.** For `before = a…a` with one `github-actions` check run named `changed-paths`,
concluded `success`, the result is `{ ok: true }`. The same holds for `secret-scan` = success plus
`check-version-bump` = skipped. No row in the self-test feeds a body without `frontend`. All three
"proven" rows carry one, so the table cannot see this.

**Failure scenario.** "Every Actions check run the API returns is non-red" means "CI validated
`before`" only if two things are true: every `ci.yml` job on `before` already has a check run, and
the run has started. Neither is measured, and I am not claiming GitHub's timing either way. Here
are the shapes where they do not hold:

1. **The `ci.yml` run on `before` is queued or not yet created, while a faster push workflow has
   finished.** `contracts.yml` (3 jobs) runs on every push to `main`. If its runs are the only Actions
   check runs on `before` when B's `changed-paths` asks, B takes the short path over A's
   unvalidated code.
2. **The gap between `ci.yml` stages.** Jobs blocked on `needs:` (`test-db-drift` behind
   `python`, and the `frontend` aggregator behind everything) are commonly understood to get their
   check run only when they are queued. Suppose the last running job has completed and its
   dependants are not yet queued. Then every returned run is `completed`, and the predicate says
   ok over a commit whose `test-db-drift` or `frontend` may still go red.
3. **`ci.yml` produces no check runs on `before` at all, while other push workflows go green.**
   For example, the run fails to start.

In every shape, B writes `docs_only=true`. B's suite is a short green run, Railway gates on B's
check runs, so it deploys A's code. That is the SFH-04 class this gate exists to close. Round 2's
`frontend` requirement doubled as a "CI on `before` finished" sentinel, because the aggregator is
the last job created.

**Why MEDIUM and not HIGH:** shape 2's window is the scheduler's job-creation latency, typically
seconds. Shapes 1 and 3 need an unusual queueing or start failure. The defect itself is certain,
because the probe above returns `ok: true`. Whether it is reachable depends on GitHub's
check-run creation semantics, which nothing in the repo measures. Confidence: 10/10 that the
predicate admits it, about 7/10 that it is reachable in production.

**Fix:** keep the every-Actions-check rule, and also require at least one Actions run named
`frontend` that is `completed` with `success`. Its conclusion is already covered by the loop.
Presence is the missing half.

```js
const runs = all.filter((r) => r?.app?.slug === PREDECESSOR_APP_SLUG);
if (runs.length === 0) return { ok: false, why: "absent: no GitHub Actions check run on that commit" };
if (!runs.some((r) => r.name === "frontend")) {
  return { ok: false, why: "absent: no `frontend` check run on that commit, so CI on it has not finished" };
}
```

Add an `unproven` row, `checkRuns(done("changed-paths", "success"), done("contracts", "success"))`
expecting `"absent"`, and add its FAIL line to neuter leg 5's assertions. The three `proven` rows
already carry `frontend` and stay green.

## LOW-07 (new): the "no cross-suite dedupe" property is a claim about inputs the API may never return

**Location:** the `predecessorVerdict` doc comment above `PREDECESSOR_APP_SLUG`. The `changed-paths`
`classify` step comment in `ci.yml` says "(all workflows and events; no cross-suite dedupe)". The
self-test row is at `:846` ("an older RED run in another suite beside a newer GREEN run").

**Failure scenario:** the classifier asks GitHub for `filter=latest`. If `latest` collapses
same-named check runs across check suites, an older red `e2e` in the push suite never reaches the
classifier. A newer green `e2e` from a `workflow_dispatch` re-run of `ci.yml` on the same SHA would
replace it. The classifier then says ok. The self-test row feeds both runs by hand, so it proves
the classifier's arithmetic, not what it can see. The same applies to `total_count`: if GitHub
counts superseded runs in it, every commit with a re-run is refused forever. That direction is
safe, but the short path then dies with only a printed reason.

**Why LOW:** Railway probably reads the same `latest` view, so the classifier and the gate it
mirrors agree on whatever GitHub does. Neither `total_count` direction produces a false docs-only
path.

**Fix (pick one, record which):** measure `filter=latest` against `filter=all` on a SHA that has a
dispatch re-run, and write the result into the comment. Or switch to `filter=all` and dedupe
explicitly by `(check_suite.id, name)`, keeping the latest per pair, which makes the stated
property true by construction.

## LOW-08 (new): the whole-tree derivation has three blind spots that pass while finding nothing

**Location:** `src/__tests__/contracts/ci-docs-path-filter.contract.test.ts`, the `closure()` and
`derive()` functions (`:1039` for the literal regex, `:1047` for `if (!existsSync(abs)) continue`).

**Failure scenarios.** Each of these is a reader the derivation cannot see, so the "the list cannot
lag the tests" arm stays green:

1. **Template literals and f-strings.** The quote class is `["']`. A future
   `` readFileSync(`.planning/${x}/FOO.md`) `` or Python `f".planning/{x}"` is invisible.
   I measured zero such reads today.
2. **Split-segment spawns.** A spawned script is followed only through a single quoted
   `scripts/….(mjs|ts|…)` literal. Ten test files spawn through `join(…, "scripts", "x.mjs")`-style
   segments (for example `local-stack-lane-wiring.test.ts` and `drift-check-scripts.test.ts`). Those
   scripts are not walked unless something else imports them. Today none of the scripts reached
   only that way reads a named planning file. The only script readers are the three NOT_SCANNED
   walkers, and `verify-phase18-artifacts.ts`, which nothing invokes.
3. **Absent-file literals are dropped silently.** A test that pins a planning file's ABSENCE, the
   way the 164.3-07 pins assert the `-SUMMARY.md` stays absent, names a file that does not exist.
   The derivation skips it, and only the one hand-listed SUMMARY is accounted for. A new
   absence-pin would be invisible, and a docs-only push that creates that file would end the pin
   with no full run.

**Fix:** widen the literal regex to accept backticks and Python f-prefixes. Treat any
`${…}`/`{…}` segment as a hard red ("a computed planning path cannot be derived; list it by hand
and pin it here"). Resolve adjacent `"scripts", "x.mjs"` segments the same way `.planning` segments
already are. Collect absent-file literals and require each to be either on the list (like the
SUMMARY) or in an explicit `FIXTURE_COLLISIONS`-style set.

## LOW-09 (new): a NOT_SCANNED reason claims coverage that does not exist

**Location:** `ci-docs-path-filter.contract.test.ts:957` (`NOT_SCANNED`), on two entries.

- `src/__tests__/check-planning-hygiene.test.ts`, whose reason is "the always-on frontend-lint runs
  the same hygiene script". The test's `it("the tracked tree carries no ENCODED form of this
  machine's identity")` builds base64 and hex forms itself, over every tracked file.
  `scripts/check-planning-hygiene.ts` only *documents* that an encoding is not a redaction. It does
  not scan encoded forms. So a docs-only push that commits an encoded identity under `.planning/`
  skips the only check that would catch it. In practice the CI-side scan sees only the runner's
  identity, which makes it close to moot on CI, but the reason is still false.
- `scripts/verify-plan-anchors.mjs`, whose reason is "plan-anchor-verify runs it unfiltered".
  `plan-anchor-verify` is `if: github.event_name == 'pull_request'`, so on a docs-only merge push
  the `--pending` scan runs nowhere. This is the accepted `[CI-DOCSPATH-01]` PR-side trade that the
  classifier's header already records ("on every PR"). The new reason string drops the "on every
  PR" and reads as push coverage.

**Fix:** reword both reasons to what is true. For the hygiene test, either move the encoded-form
scan into the script, or say the exclusion accepts losing it on a docs-only push.

## LOW-10 (new): IN-02's "ONE name for every reader and writer" stops at `run.sh`'s edge

**Location:** `scripts/local-stack/run.sh:96` (`ENV_FILE="${LANE_ENV_FILE:-…}"`) and its comment
"ONE name for every reader and writer". The other readers are:

- `scripts/local-stack/sql-corpus-report.mjs:58`, with `ENV_FILE` hard-coded to the default.
- `scripts/local-stack/capability-probe.mjs:322`, which reads a third variable, `STACK_ENV_FILE`.

**Failure scenario:** suppose a developer exports `LANE_ENV_FILE`, the case IN-02 exists for.
`up` writes the override, and the two readers then read the default path. If no file is there,
both fail loudly (the report exits 2, "is the lane up?"). That is safe, but confusing, since `up`
just succeeded. If a stale default `.stack-env` is left from an earlier run, they read the stale
stack's ports instead. `down` under the override never deletes that stale file, so a mode-600
copy of the service-role key stays at the default path for good. Separately, a non-default path
inside the repo is not covered by `.gitignore` (which lists only the default). The `mv` also
overwrites whatever file the override names, with no existence check.

**Why LOW:** CI sets no divergent value, every value is loopback-only by `assert_local`, and every
reader that misses fails loudly. Nothing in the repo pins the override line either, so reverting it
would also pass silently.

**Fix:** make the two readers honour `LANE_ENV_FILE`, with `STACK_ENV_FILE` kept as an alias or
retired. Alternatively, narrow the comment to "every reader and writer inside `run.sh`". Consider
having `up` refuse an override inside the repo that `git check-ignore` does not ignore.
