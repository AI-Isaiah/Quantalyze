# Phase 164.9.4 Plan 02: CSP connect-src derives the configured Supabase origin (D-14) Summary

`next.config.ts` now appends the origin of `NEXT_PUBLIC_SUPABASE_URL` and its `ws:`/`wss:` twin to the global CSP `connect-src`, but only when no existing source already allows it. A loopback lane build can reach the lane. A production or placeholder build emits today's header byte for byte. An env value that could inject a CSP token is refused. A 12-case contract test pins all of it, and it was observed RED under all three planned neuters.

## Next.js docs reading (AGENTS.md obligation)

I read `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/headers.md` before the edit. It says `headers` is an async function that returns an array of objects with `source` and `headers` properties, where `headers` is an array of `{ key, value }`. It also says headers are checked before the filesystem. **It does not say when `headers()` runs**, whether at build time or per request. The design does not depend on the answer: `withConfiguredSupabaseOrigin` reads the env when `headers()` is called, and plan 08 exports the lane URL to both `npm run build` and `next start`.

I found one more thing in `node_modules/next/dist/shared/lib/router/utils/prepare-destination.js` `compileNonPath`. Next escapes every `:` in a header value before compiling it. Only a `:<paramKey>` token gets substituted, and the only param key of the `/(.*)` source is `0`. So the `:54421` port in a derived source is emitted literally and is not treated as a route parameter.
