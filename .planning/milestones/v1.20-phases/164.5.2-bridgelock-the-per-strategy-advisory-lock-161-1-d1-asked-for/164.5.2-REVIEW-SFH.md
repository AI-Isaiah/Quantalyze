## Hunt checklist: each item checked and found clean

- **A lock on a NULL strategy id.** The lock is the first statement inside the existing
  `IF v_strategy_id IS NOT NULL` guard in both RPCs, so a strategy-less job takes no lock by
  decision rather than by the STRICT no-op on NULL. The migration's `DO $verify$` enforces this
  placement with one statement-shaped regex (`c_lock_re`) over the comment-stripped body, and a
  NULL body raises instead of passing through.
- **Transaction scope versus session scope.** The lock is `pg_advisory_xact_lock`, so it is
  released at commit or rollback. It cannot leak past the RPC's transaction, and it is not
  released early. Python reaches both RPCs only through PostgREST `supabase.rpc(...)`, one
  transaction per call (`main_worker` `_mark_done` / `_mark_failed` /
  `_mark_failed_fallback`), so the lock is held for milliseconds after the bridge.
- **Exception paths are unchanged.** Every RAISE path (NULL token, bad kind, not found,
  preempted, unexpected status) and the idempotent-retry early RETURN in `mark_compute_job_done`
  exit before the guard. They are byte-identical to the previous bodies, so the SQLSTATE and
  message a caller sees did not change.
- **A mark that could now block forever.** The same-strategy wait is not new. The research
  measurement recorded in the gate header (RESEARCH Q3) shows that without the lock, B already
  waited for A's commit, on the `transactionid` ShareLock of A's `strategy_analytics` write. The
  lock moves that wait earlier, to before B's bridge reads. It does not add a new unbounded
  wait. The lock is taken last in each RPC, after the job and fan-in child row locks, so a
  holder can wait only on the `strategy_analytics` row or the strategies key-share, as the
  header's deadlock argument says. The `FOR SHARE` diamond is still owned by D-12 and is not
  made worse.
- **Snapshot correctness after the wait.** The lock and the bridge are separate PL/pgSQL
  statements in VOLATILE functions at READ COMMITTED. B's `PERFORM sync_strategy_analytics_status`
  therefore takes a fresh snapshot after A commits, and the second bridge run sees both
  terminal states. This is the property 161.1-D1 asked for.
- **A gate that passes without dblink or without a second backend.** The gate opens with
  `CREATE EXTENSION IF NOT EXISTS dblink`, so an absent extension fails and names itself. Each
  arm's SETUP checks refuse on a missing seed, on backend b seeing fewer than 2 running jobs,
  on b never waiting (L1–L3), on b neither finishing nor waiting (L4), and on the two marks not
  both completing. An error inside b surfaces through `dblink_get_result`, which fails on error
  by default. The lane boots with `--auth=trust` and `listen_addresses=127.0.0.1`
  (`scripts/pg-lane/run.sh`), so the loopback connection string is deterministic on every box.
- **A CI probe that skips.** The new step in the `sql-mutation` job has no `if:` and no
  `continue-on-error`. It runs under `set -euo pipefail`. An unresolved `--print-pgbin` and a
  missing `dblink.so` or `dblink.control` each exit 1 with a named `::error::`. The `|| true`
  on `--print-pgbin` is followed by an explicit empty-value refusal, so it does not skip.
- **LANE-ONLY registration.** The file is registered in `LANE_ONLY_SITES` in
  `ci-anti-skip-gate.contract.test.ts` with the same object, fixture and job as its
  `-- LANE-ONLY:` header, so the `sql-tests` exclusion is declared rather than silent.

## LOW findings (recorded limits, no fix round)

### LOW-1: no gate arm pins the failure RPC's lock namespace or two-integer form

- **Location:** `supabase/tests/test_mark_rpc_bridge_advisory_lock.sql`, arms L2 and L3.
- **Issue:** L2's predicate is `locktype = 'advisory'` only. L3 checks `classid` and
  `objsubid = 2`, but it drives `mark_compute_job_done` only. Suppose the lock in
  `mark_compute_job_failed` alone were rewritten to the single-key `hashtext(v_strategy_id::text)`
  that `sync_trades` takes. L2 would still see an advisory wait (objsubid 1), L3 would be
  untouched, and no arm would go red. This is reasoned from the predicates and was not run as
  an extra twin.
- **Why only LOW:** the migration's own `DO $verify$` applies the same exact-form `c_lock_re`
  anchor to BOTH bodies (`v_failed_lock_anchored`), so that mutation aborts the apply. That is
  the gate's documented layering, so the mutation is still caught. It is just not caught by the
  concurrency gate.
- **If ever tightened:** add a failed/failed twin of L3's `classid = v_ns AND objsubid = 2`
  predicate. That needs a separate seed strategy and one more arm (a census move).

### LOW-2: the gate runs on a narrower schema than PROD

- **Location:** the gate's `RED-UNDER-SETUP` apply list.
- **Issue:** the lane leaves out `20260603120000` (on purpose) and every later compute_jobs
  migration (for example the 164.9.1 fan-in / FOR SHARE work). On PROD, a trigger or path
  missing from the lane could make B wait on some other lock before it reaches the advisory
  lock. The gate cannot see that.
- **Why only LOW:** it limits what the gate observes, not what production does. The lock
  statement and its placement are the same on the lane and on PROD (the body is the full
  re-base), and the snapshot-drift / VAC-04 pairing binds the PROD body.

### LOW-3: the namespace-distinctness check omits the CI mutex key space

- **Location:** migration `DO $verify$` arm (0).
- **Issue:** the check compares `hashtext('mark_compute_job_bridge')` only against
  `hashtext('admin_role_mutate')`. The CI mutex `pg_advisory_lock(0, 61616158)` in the
  workflows is also a two-integer key, with classid 0. The header's claim "the only other
  namespace in any migration" is literally true, because the mutex lives in workflows and not in
  migrations. Still, the check does not cover every two-integer key on TEST.
- **Why only LOW:** a collision needs `hashtext('mark_compute_job_bridge') = 0` AND one
  strategy's `hashtext` equal to `61616158`, and it would only affect TEST, while CI holds the
  mutex. This is negligible and recorded for completeness.

### LOW-4: an unbounded wait surfaces as a generic timeout, not as a named error

- **Location:** both RPCs' `PERFORM pg_advisory_xact_lock(...)`.
- **Issue:** the wait has no local `lock_timeout`. If a same-strategy holder ever stalled, the
  waiting mark would end in the role's `statement_timeout` (57014). The worker's `_safe_mark`
  would then report that as a plain mark failure, not a lock-specific one.
- **Why only LOW:** this is not a new failure class. The same wait existed before the lock, on
  the `strategy_analytics` row. Every holder is a single-statement PostgREST RPC transaction,
  and no SQL caller wraps a mark in a longer transaction.
