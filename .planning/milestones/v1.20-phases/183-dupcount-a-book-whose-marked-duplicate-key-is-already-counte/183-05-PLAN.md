With the remedy gone, the note moves to `text-text-muted`, the tone of the row's own "Balance shown on ..." caption.

Collision verdict — can this note show for a REAL double count? NO; the note is reachable only in the counted-once case, so the whole note changes and no branch keeps a disconnect remedy. Evidence, read at the plan's base:
1. `accountShareNote` returns a sentence only when `account_share_kind` is `duplicate` with a holder id, `isWorkingHolder(key)` holds, and the holder is in the caller's `keysById` with `isWorkingHolder(holder)`. Both callers build `keysById` from the signed-in owner's own `api_keys` rows (ApiKeyManager: every key its read returns; AllocatorExchangeManager: its `keys`), the same set the derive loads (`derive_allocator_equity` reads `api_keys` with `.eq("user_id", allocator_id)`).
2. Working implies eligible: `working_holder_predicate` (twin of `isWorkingHolder`) needs `is_active` true, `disconnected_at` null and a sync status outside revoked, sign_in_failed and error; `eligible_key_predicate` needs `is_active`, a status other than revoked and `disconnected_at` null. Its own docstring says "Every working key is eligible". So both keys of a pair the note names are in `eligible_ids`.
3. `account_groups` unions a key into its holder's group whenever its kind is in `SHARED_ACCOUNT_KINDS` (duplicate is) and the holder is among the owner's keys and is not the key itself (the database also forbids a self-marker: CHECK `api_keys_account_share_not_self`). The group loop takes the group's eligible members (two or more here), keeps exactly one (`kept`, working first), puts every other member in `excluded_shared`, and sets `duplicate_counted_once`. So the pair is counted once, always, and the stored curve carries the flag `duplicate_shared_account_counted_once`.
4. `account_identity_collision` needs two COUNTED keys on one account. The note's pair contributes one counted key, and two live keys cannot carry the same venue id (partial unique index `api_keys_user_exchange_venue_account_uniq`, `WHERE venue_account_id IS NOT NULL AND disconnected_at IS NULL`). A collision on such a book therefore needs a departed key's included history (`departed_end_by_key`) overlapping the counted key. That key is disconnected, so it never carries this note (the allocator card renders the note on active rows only, and the function returns null for a key that does not work), and the double count lies between the counted key and that departed history, not between the two live keys the note names. That case is the Overview's rebuilding panel `duplicate_account` line, which D-03 leaves as is.
5. "A marked key whose holder is not working" shows no note today (the holder check) and the derive counts that account once through the working marked key (the holder-drop half of the group loop). Unchanged.
6. The reader agrees: plan 183-02 deleted the reader's key-list duplicate helper from `src/lib/queries.ts` (`grep -ac isWorkingHolder src/lib/queries.ts` prints 0 at HEAD), so the key list never holds a book back over a marked duplicate, and the panel line is reached only through a stored collision or a pre-Phase-183 refusal token. Holdings and the allocator row's balance also count one account once (`keyAccountOf` / `accountIdentityTokens` in `src/lib/latest-holdings-per-key.ts`; the row's balance bearer, D-74).

Evidence, read at the plan's base:
(a) "That account" is counted in the OWNER's book, and every owner with a key gets one, managers included. The nightly fan-out `enqueue_derive_broker_dailies_for_allocator_keys` (current snapshot `supabase/schema/functions/enqueue_derive_broker_dailies_for_allocator_keys.sql`) enqueues a key-mode `derive_broker_dailies` for EVERY eligible `api_keys` row. Its filter is only `is_active`, not revoked and not disconnected, with no role and no strategy condition; its COMMENT calls it "the role-agnostic eligible_key_predicate". `_allocator_key_preflight` loads the key by id and refuses only a missing or inactive key. Every key-mode derive then runs `_run_key_mode_compose_epilogue`, which enqueues `derive_allocator_equity` for `allocator_id = ctx.key_row["user_id"]`, the key's owner. That compose loads all of the owner's keys by `user_id` and counts the pair once (collision verdict points 2 and 3). A strategy-linked key is therefore in its owner's book like any other (the founder rule: a strategy-linked key can also be in an allocator book, never "manager-only by design"). Holdings group by account the same way (`keyAccountOf`).
(b) No strategy sums the pair. A single-key strategy reads one key. For a composite holding both keys, the stamper marks the pair `composite_member` when their declared windows are disjoint (`_share_kind` in `analytics-service/services/account_identity.py`), and that kind shows no note. When the windows overlap, the pair is marked `duplicate`, but `run_stitch_composite_job` calls `assert_windows_disjoint(windows)` and fails permanently on the `CompositeOverlapError`, so it never composes the account twice. Two strategies that each hold one key of the pair are two track records of one account, each shown on its own, not a sum. The one cross-strategy AUM total in the product, the marketing page's `strategies.aum` sum, reads the manager-entered AUM field from the wizard's metadata step, not key balances.
