## Critical Issues

### CR-01: A trading loss that takes a key below 1% of its peak refuses the whole allocator book (a regression against `main`)

**File:** `analytics-service/services/allocator_equity_derive.py:1141-1151` (the Pitfall 5 stretch-start check). The classification is at `:1116-1127`.
**Confidence:** 9/10

**Issue:** The Pitfall 5 hardening accepts only two explanations for the first day of a stretch: a withdrawal (`fbd < 0`) or a stored **dropped-day** P&L. It treats a day with an ordinary stored return as "a data fault". But a stored return IS the writer's explanation of that day. `nav_twr` drops a loss day only when the loss is P&L-dominated (`PNL_DOM_RATIO = 10.0`, so 10 times the prior NAV, which a loss cannot reach unless leveraged past -1000%) or when the prior NAV is under the dust floor. So an ordinary loss day that crosses the 1% band always has a return row, and it always refuses.

Before PR-2 the level was positive, so `bad == 0` and the key composed. The compose job turns this `NavReconstructionError` into a permanent structural refusal of the allocator's **entire** book.

**Reproduced** with `replay_key_equity` from `origin/main` and from this branch on one input:

- The shape: peak $500k, a withdrawal of $490k (level $10k, 2% of the peak, not emptied), then a -60% return day that leaves $4k (0.8%).
  - `main`: `composed []`.
  - Branch: `NavReconstructionError: ... an emptied stretch begins on day 8 of 16 with no withdrawal and no stored day P&L`.
- A pure drawdown with no withdrawal at all (100k, then -50% a day for eight days) gives the same split: `main` composes `{'opening_flows_reconciled': 1}` with no reasons, and the branch refuses.

**Why it matters:** "Withdraw most of it, keep a small stake trading, lose it" and "liquidated to dust" are ordinary crypto accounts. They are not data faults, and one of them blocks every allocator book that holds the key. The PROD reading in plan 09 cleared only the options-holding account's two stretches, which both begin on withdrawals. Nothing measured the other connected keys, or the MT5 and ccxt keys this classifier also runs on now, for a loss-driven crossing.

**Tests pin the defect:** `tests/test_allocator_equity_emptied_stretch.py:311-330` (`_no_flow_collapse`, a stored -99.5% return day) and `:348` (`test_a_data_fault_after_a_restart_peak_also_refuses`) assert the refusal. They encode a stored return as a data fault.

**Fix:** treat a day that carries a stored return as explained, and refuse only the old class: a level that is not positive and that nothing in the ledger explains.

```python
for t in range(n):
    if emptied[t] and (t == 0 or not emptied[t - 1]):
        day = days[t]
        explained = (
            fbd.get(day, 0.0) < 0.0          # a withdrawal
            or day in pnl_by_day             # a stored dropped-day P&L
            or (day in r and equity[t] > 0.0)  # the writer's own stored return took it there
        )
        if not explained:
            raise NavReconstructionError(...)
```

Then rewrite `_no_flow_collapse` as a case that composes (emptied, zero capital), and add a RED-first test with the partial-withdrawal-then-loss shape above.

### CR-02: A materially negative reconstructed level is now silently zeroed and the book reads trustworthy (it used to refuse)

**File:** `analytics-service/services/allocator_equity_derive.py:1126-1131` (`elif peak is not None and e < EMPTIED_FRACTION * peak: emptied[t] = True`, then `bad` excludes emptied days). The zeroing is at `:1157-1160`.
**Confidence:** 7/10

**Issue:** Every level below `0.01 * peak` counts as emptied, including a level of -5% or -50% of the peak, and an emptied day is exempt from the `non-positive reconstructed equity` refusal. Pitfall 5 checks only the first day of a stretch. So a stretch that starts on a real withdrawal absorbs any later negative level of any size, and the series is then set to exactly 0.0, which hides it.

A negative level is not an "emptied" account. It is the backward roll saying that a flow it was given never happened: a duplicated or mis-dated deposit row pushes every earlier level down by its amount. That is the class the old refusal existed for (`"a flow dominates prior capital (refusing ...)"`).

**Reproduced** (`main` against the branch, same input, `history_reaches_inception=False`, as for an MT5 or ccxt key):

- The input: a $10M account, a full withdrawal on day 10, a phantom +$500k deposit row on day 12, and a terminal of $1.
- `main`: `NavReconstructionError: non-positive reconstructed equity on 1 of 19 day(s)`.
- Branch: composes with **zero degrade reasons**. The flags are `emptied_stretch_days: 9`, `emptied_stretch: True` and `emptied_last_day_anchor_in_band: 1`. Day 9's level is $9,590,362 where the truth is about $10,090,362: every pre-stretch level is understated by the phantom $500k, and the book is trustworthy.
- On a Deribit key (`history_reaches_inception=True`) the shifted opening run would at least trip `INCEPTION_UNRECONCILED`. Every other venue gets no signal.

**Fix:** only near-zero levels count as emptied. A level below a small negative band still refuses as before. Reusing the existing relative band keeps the plan's -1e-6 float-noise case (`tests/test_allocator_equity_emptied_stretch.py:192`) green:

```python
_EMPTIED_NEGATIVE_BAND = _INCEPTION_ZERO_START_BAND  # 1e-4 of the prior peak
...
elif peak is not None and e < EMPTIED_FRACTION * peak:
    if e < -_EMPTIED_NEGATIVE_BAND * peak:
        materially_negative += 1   # falls through to the existing refusal
    else:
        emptied[t] = True
```

Add a RED-first test with the phantom-deposit shape above. It must refuse on the branch exactly as it does on `main`.

## Warnings

### WR-01: Writer-basis mode checks the calendar but never the values, so levels and book returns can come from two different derives and still read trustworthy

**File:** `analytics-service/services/allocator_equity_derive.py:1037-1049` (`writer_mode` gate; `r_roll = {}`). The consumer is `allocator_equity_compose.py:654` (`portfolio_returns` reads the stored returns, weighted by the replayed levels).
**Confidence:** 5/10

**Issue:** Before D-06 the levels were rolled through the stored returns, so the levels and the book returns agreed by construction. In writer mode the levels come only from `W` and the writer flows (`r_roll = {}`), while the book's daily returns still come from `csv_daily_returns`. The gate checks only day membership: every non-zero return day is in `W`, and the terminal is on `max(W)`.

A `key_inputs` row and a returns set from two derives with the same last NAV day pass that gate. That happens with a same-day re-derive after a ledger correction, a retried key, or a manual enqueue. The R2-WR-01 lagging check cannot see it either, because it compares only last days. Such a pair composes on the old `W` and the new returns, with no `KEY_INPUTS_MISMATCH`.

A cheap, exact cross-check exists: the writer chains `r_t = P_t / NAV_{t-1}` off the same levels.

**Fix:** in the `writer_mode` predicate, require for every return day `d` with a defined prior writer level `L > 0` that `abs(r[d] * L - w_pnl[d]) <= _SELF_CHECK_ABS + _SELF_CHECK_REL * abs(L)`. Compute `L` from a first backward pass. A miss makes the row fall back with `writer_basis_mismatch` and `KEY_INPUTS_MISMATCH`, the existing path. Add a test with a single-day return perturbation on an otherwise matching row.

### WR-02: The $5 inception cap now gates every section 5 caller, and the PROD clearance covered only the key-mode cash arm

Record it in the Wave 5 hand-off as `composite-cap-verdict:`, so that a flip to `failed` is expected rather than discovered. Do not loosen the cap.

### WR-03: The emptied rule can hide real live capital indefinitely, with no degrade reason

**File:** `analytics-service/services/allocator_equity_derive.py:1116-1130` (D-07 `ends_stretch` band) and `:1176-1185` (last-day `anchor_in_band` keeps 0.0).
**Confidence:** 5/10 (decision-scoped: the arithmetic follows D-01/D-07; the concern is the combination)

**Issue:** An emptied day never lifts the peak, and under D-07 only a deposit that reaches 1% of the old peak restarts it. An account with one large transient (say $10M in and out) followed by real trading at $50k is therefore emptied on every later day. The last-day rule then keeps the level at 0.0 while the live anchor is $50k. The book shows $0 for that key, permanently, and its returns carry no weight.

- The only signal is the benign `emptied_stretch` token. `emptied_last_day_anchor_in_band` is an int, so `_bool_flag_tokens` drops it from the payload.
- The last-day handling was the plan's own design (plan 04), not a founder decision.
- D-01's words were "the book continues normally on re-deposit".

**Fix:** surface it rather than change the band. When `anchor_in_band` holds the live anchor at 0.0 above some absolute floor (for example `_DERIBIT_EMPTY_LEDGER_FLOOR_USD`), emit a boolean flag token (`emptied_last_day_live_capital_hidden: True`) so the dashboard and the readers can see it. Put the "peak never decays" consequence of D-07 to the founder as a one-line question. Do not settle it in code.

### R2-WR-01 (MEDIUM, confidence 7): a materially negative live anchor on an emptied last day composes as 0.0 with no degrade reason, where `main` refuses

**File:** `analytics-service/services/allocator_equity_derive.py:1215-1222`. The `anchor_in_band` test is `float(anchor) < EMPTIED_FRACTION * peak_at_last_day`, and it has no lower bound. Line 1223 then skips the `not (anchor > 0)` refusal at :1227.

### R2-WR-02 (MEDIUM, confidence 7; decision-scoped): D-08's floor tests the post-deposit level, so a cents deposit on a residual of 100 USD or more ends the stretch, and the same residual with no deposit stays 0.0 forever

**File:** `analytics-service/services/allocator_equity_derive.py:1143-1149` (`e >= EMPTIED_RESTART_FLOOR_USD`). The last-day check at `:1218` applies no floor.

**Scenario (reproduced, both on this branch):** peak 1.01M, then a withdrawal of 1.007M leaves about 3,000 USD of real, trading capital (0.3% of the peak, so emptied).

A and B then both compose the 3k as live, a cents flow decides nothing, and the PROD stretches (all under 100 USD by the fixer's measurement) are unchanged. Re-measure the 755/2 reading under it. The alternative keeps D-08 literal but requires the deposit itself to cross the floor (`e - fbd[day] < FLOOR <= e`); that hides A permanently. Add the A/B pair as a test whichever is chosen.
