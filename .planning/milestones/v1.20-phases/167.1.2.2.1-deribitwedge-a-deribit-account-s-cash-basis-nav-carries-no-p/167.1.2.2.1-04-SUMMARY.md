# Phase 167.1.2.2.1 Plan 04: Emptied stretch composes as zero capital Summary

**An account that withdrew everything, sat at zero and re-deposited now replays to exact `0.0` levels on its empty days instead of refusing the allocator's whole book, and a level that a data fault drives below the band with no withdrawal and no stored day P&L still refuses loudly.**

`PLAN_BASE` is `f64e97894e3722a9822b83a0763ace7b1c19bfa5`. `commits: 5` is measured with `git rev-list --count`. Nothing is shipped; the code goes in PR-2.

## What was built

`analytics-service/services/allocator_equity_derive.py`, `replay_key_equity`:

- `EMPTIED_FRACTION = 0.01` beside `_INCEPTION_ZERO_START_BAND`, commented as the founder's number (D-01, 2026-10-09, relative, not to be loosened without a founder decision).
- Between the backward loop and the refusal, a chronological pass over the RAW writer-basis levels builds `emptied`. A day is emptied iff a prior peak exists and its level is below `EMPTIED_FRACTION * peak`. The peak is the maximum of EARLIER non-emptied positive levels (D-02); an emptied day never lifts it. D-04: when the previous day was emptied and a deposit lands today, today is not emptied and the peak restarts at today's level.
- The refusal counts only non-emptied non-positive days; its text is byte-identical. A non-positive level with no prior peak is not emptied and still refuses.
- Pitfall 5 hardening: the first day of every stretch must carry a withdrawal (`fbd < 0`) or a stored dropped-day P&L, else `NavReconstructionError("... an emptied stretch begins on day {t} of {n} with no withdrawal and no stored day P&L — refusing to read a data fault as zero capital")`. Day index and count only.
- Pitfall 6: `_assert_forward_agreement` runs on the raw series, then the series is copied and emptied positions are set to exactly `0.0`. `implied_start` and `level_first_return` keep reading the raw list.
- Flags, present only when a stretch exists: `emptied_stretch_days` (count), `emptied_stretches` (maximal runs), `emptied_stretch` (True). A key with no stretch keeps exactly the flag dict it had.
- Last day: when the last day is emptied and `float(anchor) < EMPTIED_FRACTION * peak_at_last_day`, the level stays `0.0`, `emptied_last_day_anchor_in_band = 1`, and the non-positive-anchor refusal is skipped. Otherwise today's step runs (the anchor wins) and `emptied_last_day_live_anchor = 1`. A non-emptied last day is byte-identical to before.

Downstream needs no code (RESEARCH 3.3, confirmed by the compose-level tests): `portfolio_returns` weights by the previous day's level, so a 0.0 level weighs 0, and a day on which every key is empty is omitted and counted through the existing benign skip. No TypeScript change.

`analytics-service/tests/test_allocator_equity_emptied_stretch.py` (25 tests): the Fraction forward oracle (the 1% restated as `Fraction(1, 100)`), the PATTERNS section C key at stretch levels 0.0, -1e-6 and +1e-6, the 0.99% / 1.01% boundary, D-02 (a huge later deposit does not reclassify the past), D-04 (a 0.5% re-deposit ends the stretch, 2% daily returns carried), Pitfall 5 (two cases and a control), the last-day anchor cases, the compose-level payload through restated `extractTrustworthyDerivedSeries` checks, the W5 overlap case, and the leak scan.

## Design notes the reader should know

- `emptied_stretch_days` counts days classified emptied. On the live-anchor-wins last day (`emptied_last_day_live_anchor`) that day is counted but carries the anchor level, not 0.0; the flag is what says so.
- The hardening applies to the first day of EVERY stretch. Plan 06 Task 1 replays the stored PROD inputs (RESEARCH 3.2: 755 emptied days, 2 stretches) through this rule, which has not been run against them here. If either PROD stretch begins on a day with neither a withdrawal nor a stored day P&L, it will now refuse; that is the intended behaviour but plan 06 should read it.
- Known semantic caveat (RESEARCH 3.4, recorded, not fixed): the factsheet CAGR annualizes over the calendar span, so a book empty for long stretches reads a diluted CAGR. Plan 07 records it in the CHANGELOG notes.
