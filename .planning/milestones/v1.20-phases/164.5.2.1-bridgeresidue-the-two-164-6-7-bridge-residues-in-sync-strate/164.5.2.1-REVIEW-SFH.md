## LOW

### L-1 — Carried 20260906120000 anchors still match on comment-bearing `v_fn`
**Where:** `supabase/migrations/20261003120000_sync_status_bridge_residues.sql`, the carried part of `DO $verify$` (about `:1179-1595`). Examples: the P2b/P2c CASE anchors, `f\.kind\s+IN`, `\)\s*AS\s+has_live_successor`, and the `position('INTO v_publish_healthy' …)` order test.
**Failure scenario:** a future edit deletes or rewrites an anchored statement but leaves the identical text in a `--` comment inside the function body. The carried anchor still matches, the migration applies green, and the shipped body no longer has the property the anchor names. The new anchors (`:1597` on) avoid this by running on `v_body`, which has comments stripped. The carried ones do not.
**Measured today:** no comment in the shipped body satisfies any carried anchor. I grepped the snapshot's comment lines for the anchored phrases, and the only hits are two backticked mentions of `has_live_successor`, which the `\)\s*AS` prefix rejects. So this is latent, not live.
**Fix:** in a later re-base, point the carried anchors at `v_body`. This file could do it now at no behavioural cost, but every RED-UNDER-M twin that edits an anchor's `find` string would need re-checking, so it is reasonable to defer.

### L-2 — B2 pins the lock namespace and form but not its strategy-scoped second key
**Where:** `supabase/tests/test_sync_status_bridge_lock.sql:330-334`. It checks `classid = v_ns AND objsubid = 2` and never checks `objid`.
**Failure scenario:** the bridge's second key is changed to a constant, which turns the lock into a global bridge lock. B1, B1-DIRECT and B2 all stay green, because b still waits on a two-integer advisory lock in the right namespace. Correctness is unaffected (it serialises more, not less), but every strategy's bridge call would queue behind every other strategy's mark. That is a throughput fault the gate cannot see. The verify-block regex (`:1708`) does pin `hashtext(p_strategy_id::text)` textually, so the residual exposure is only an edit that also changes that anchor.
**Fix:** add `AND objid = (hashtext(s::text)::bigint & 4294967295)::oid` to B2's predicate, so the behavioural gate proves the per-strategy key as well.

### L-3 — Hold-CASE count anchor does not pin which value each THEN writes
**Where:** `…bridge_residues.sql:1699-1703` (`v_hold_cases`).
**Failure scenario:** the regex accepts any of `EXCLUDED.computation_error | NULL | now()` in the membership THEN, with `ELSE \2` required to match it. A mutation that rewrites both arms of `computed_at` to `NULL` still gives 4 matches. The result is that every row going `computing` gets `computed_at = NULL`, which the FreshnessChip and PDF vintage read as "never computed". I found no K or W arm that asserts `computed_at` is non-NULL after a transition into `computing`.
**Fix:** either bind the value per column in the anchor (4 separate regexes), or add one assertion to W1/R1: `computed_at IS NOT NULL` after the transition.

### L-4 — Two setup guards are NULL-transparent
**Where:** `supabase/tests/test_sync_status_bridge_residues.sql:377` (`… OR NOT (v_y_at > v_x_at)`), `:402` (`IF NOT (v_done_at > v_y_at)`), `:1038` (`… OR v_later <> 0`).
**Failure scenario:** if either timestamp read came back NULL (a row not found by the `SELECT … INTO`), `NOT (NULL > x)` is NULL and the guard does not raise, so the arm continues on a setup it never proved. Today `created_at` is NOT NULL with a default and `v_later` is a `count(*)`, so this cannot happen. It is the vacuity shape the file otherwise avoids everywhere.
**Fix:** write them as `(v_y_at > v_x_at) IS NOT TRUE` and `v_later IS DISTINCT FROM 0`.

### L-5 — Re-pointed R1 failure message still says branch (a)'s clears are "unconditional"
**Where:** `supabase/tests/test_sync_status_curated_sentence_survives.sql`, the R1 `RAISE EXCEPTION` text at `:626`, which reads "branch (a)'s own unconditional clears are the only thing standing here." The header prose at `:150` has the same wording ("the branch's OWN unconditional clears").
**Failure scenario:** the twin and the header note were updated (the clears are now the ELSE arms of the hold CASEs), but the message was not. An engineer debugging an R1 failure will look for an unconditional `computation_error_source = NULL` in branch (a) that no longer exists. That costs debugging time without hiding anything.
**Fix:** change it to "branch (a)'s hold-CASE ELSE arms (the clear a non-kept re-entry reaches)".

### L-6 — The LOCK ORDER header states a false invariant, though the no-cycle conclusion holds
**Where:** `…bridge_residues.sql:144-146`: "no transaction holds that row (or a job row) while waiting on the advisory lock".
**Failure scenario:** the lines just above it (`:139-141`) say the mark path holds its job row, and for `done` the fan-in children (which can belong to *other* strategies), *then* waits on the advisory lock. The real reason there is no cycle is a different invariant: **no transaction holding the advisory lock ever waits on a compute_jobs row lock**. The bridge only reads compute_jobs and then writes strategy_analytics. I checked the caller census: only the two mark RPCs (in `supabase/schema/functions/`) and the Python DEFERRED RPC call the bridge, and none writes strategy_analytics or job rows of the same strategy after taking the lock. So the conclusion holds today. The risk is the next maintainer: someone who adds a compute_jobs UPDATE inside the bridge, or after the lock in a mark RPC, will read "no transaction holds a job row while waiting" and believe it is safe. It would then produce 40P01 deadlocks. On the DEFERRED side those are swallowed (I-1).
**Fix:** restate the invariant as "the advisory lock holder never waits on a compute_jobs row lock; the bridge only reads compute_jobs", and name it as the property any future edit inside the lock must preserve.

Swapping one column's value for another's also drops it to 3. A duplicate CASE cannot make up for a missing one, because Postgres rejects two assignments to the same column in one `DO UPDATE SET`.
