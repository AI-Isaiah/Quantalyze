### 2. The RLS'd table + policies

**Analog: the `system_flags` policy set, `20260407164606_perfect_match.sql` section "8. RLS"** (lines 236, 283-291):
```sql
ALTER TABLE system_flags ENABLE ROW LEVEL SECURITY;
…
-- system_flags: scoped public-read for the kill switch only; admin and service role write
CREATE POLICY system_flags_match_engine_public_read ON system_flags FOR SELECT
  USING (key = 'match_engine_enabled');
CREATE POLICY system_flags_admin_all ON system_flags FOR ALL
  USING (EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND is_admin = true))
  WITH CHECK (EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND is_admin = true));
CREATE POLICY system_flags_service_all ON system_flags FOR ALL
  USING (auth.role() = 'service_role')
  WITH CHECK (auth.role() = 'service_role');
```
Roles in play: none pinned by `TO` (every policy applies to all roles, including `anon`);
admin = `profiles.is_admin`; service = `auth.role() = 'service_role'`. The public-read
policy is scoped to ONE key by predicate — for `system_settings` there is no anon reader,
so do NOT copy that policy; the SECDEF fan-out reads as its owner and bypasses RLS
(CONTEXT "The guard read cannot hit an RLS trap"; the fanout verify check 2b pins the
owner's exemption).

**Newer table-creation hygiene to layer on top — `20260621120000_scenarios_table_and_rls.sql`** (lines 48-70) and `20260827120000_strategy_shares_generation_model.sql` (the `strategy_shares_owner` policy, ~line 267-274):
```sql
-- `TO authenticated` scopes the policy to the role the request-scoped client
-- actually connects as. Without it the policy applies to ALL roles incl. anon; …
CREATE POLICY scenarios_owner ON scenarios
  FOR ALL
  TO authenticated
  USING (allocator_id = auth.uid())
  WITH CHECK (allocator_id = auth.uid());

-- Defense-in-depth: REVOKE all default grants from anon. … a fresh table inherits
-- Supabase's default `GRANT ALL ON TABLE scenarios TO anon, authenticated`
```
Copy both habits: pin the admin policy `TO authenticated`, and REVOKE the bootstrap
default grants from `anon` on the new table (and consider the same for the ledger key on
`system_flags` — its public-read policy is key-scoped, so `anon` cannot read the new row,
but the table-level grant still exists).

⚠️ pg-lane consequence (`scripts/pg-lane/fixtures/07-fixture-supabase-default-privileges.sql`
header): "On a vanilla cluster anon never had the grant, so that REVOKE is a no-op and the
arm passes for a reason unrelated to the migration — a vacuous PASS inside the vacuity
detector." Any gate arm asserting the anon REVOKE must list fixture 07 BEFORE the
migration in its apply list.

**CONFLICT 1 — admin predicate: `profiles.is_admin` vs `current_user_has_app_role(ARRAY['admin'])`.**
Eight migrations (Apr-Jun 2026, e.g. `20260501055202_strategy_verifications.sql`
`strategy_verifications_admin_select`) use the helper; `system_flags` and the majority use
`profiles.is_admin`. Pick **`profiles.is_admin`**: (a) `src/lib/admin.ts` header (C-0144 /
C-0150) states "admin = (profiles.is_admin = TRUE)" is the DB-side source of truth and
`user_app_roles` is secondary; (b) it matches the sibling table byte-for-byte; (c) the
helper carries a trap — `20260715120000_grant_anon_execute_current_user_has_app_role.sql`
records that a `{public}`-scoped policy calling it 42501s for anon unless anon has EXECUTE
(memory: "SECDEF in {public} RLS policy needs anon EXECUTE"). Flag the helper idiom as the
other; do not blend (no policy that checks both).

**pg-lane substrate for these policies** (needed by any gate that applies the migration):
`auth.uid()` comes from `01-fixture-core.sql`; `auth.role()` from
`15-fixture-auth-role.sql` ("policies of the `*_service_all` family spell their predicate
`auth.role() = 'service_role'`, so the function must exist for the CREATE POLICY to parse at
all"); `profiles.is_admin` from `12-fixture-profiles-is-admin.sql` ("DEFAULT false on
purpose"). `20260407164606_perfect_match.sql` itself CANNOT go in an apply list (it reads
`auth.users`, FKs `strategies`, creates four unrelated tables); the precedent is fixture
12's header: "Additive stand-in … that migration is not in any apply list (it seeds a dozen
unrelated subsystems and would pull the whole chain in)". So `system_flags` on the lane
needs a NEW additive fixture (`NN-fixture-system-flags.sql`) mirroring the CREATE TABLE +
three policies — and it must not SHADOW a later migration's object (lint rules
`R5-fixture-shadows-migration-table` / `R7-fixture-shadows-policy` in
`scripts/lint-sql-gates.mjs`): the new migration must only `INSERT … ON CONFLICT` into
`system_flags`, never `CREATE TABLE IF NOT EXISTS` it again, or R5 fires.
