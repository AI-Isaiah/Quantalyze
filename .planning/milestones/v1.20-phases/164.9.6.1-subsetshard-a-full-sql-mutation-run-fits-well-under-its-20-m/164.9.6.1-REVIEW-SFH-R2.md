# 164.9.6.1 silent-failure re-review (round 2)

**Verdict: both fixes hold. One MEDIUM, no HIGH or CRITICAL.**

- **SFH-03 is closed.** An overflowing lane now gets a SIGTERM sent to its whole process group, then
  a SIGKILL after the grace period. The promise settles on bash's `exit`. Two self-test rows and two
  vitest rows cover the trappable case and the case that ignores SIGTERM, each bounded by a watchdog.
- **SFH-01 / WR-02 is closed.** The collision is recognised only when `run.sh`'s exit 2 and its own
  two anchored lines are both present. It becomes `lane-unrunnable`, which is a defect, so the run
  exits 1.

Nothing in the diff lets a lane settle as a pass or a skip when it should fail. Nothing lets a
`lane-unrunnable` row end in exit 0.

The remaining MEDIUM is about how far one failure spreads and whether its cause gets named. The
new classification correctly tells you the port was taken. It cannot tell you which lane left a
postmaster on it, because the runner throws away the teardown WARNINGs from `run.sh` that would
say so.

## SFH-R2-01: MEDIUM. A lane whose teardown leaks its cluster is judged normally and its WARNING is discarded, so one leak poisons most of the remaining corpus as port-taken rows that name no cause

**Where:**
- `scripts/mutation-runner/run.mjs`:
  - `runLane`: `measureFail = laneSpawnFailure(proc) ?? lanePortCollision(proc)`. Only the exit
    status and `measureFail` reach the verdict loop.
  - the `worker` / `runFile` pool in `runCorpus`, where worker k keeps `ports[k]` for the whole run.
  - the early `return` after a baseline `lane-unrunnable`.
- `scripts/pg-lane/run.sh`: `cleanup()`, the `WARNING: pg_ctl stop FAILED ...` and `... ORPHANED ...`
  lines.

**Mechanism.** These points were read from the code, not run against a real leak.

1. `run.sh`'s `cleanup()` keeps the lane's own exit status when `pg_ctl stop` fails. It prints its
   WARNING lines to stderr and then exits with the gate's status. A lane whose teardown left a
   postmaster behind can therefore finish with status 0, or with a correctly attributed RED.
2. `runLane` puts stderr into `output`, but the verdict loop reads `output` only for identity
   attribution and the baseline's first-failure needle. A grep for `pg_ctl stop FAILED`, `ORPHANED`
   or `WARNING:` in `run.mjs` finds nothing. The leak is not a defect and is not logged. The arm,
   baseline or restore that leaked is reported as healthy.
3. The next lane on worker k hits `run.sh`'s collision guard. Since d86984b40 it is correctly
   `lane-unrunnable`. But a baseline `lane-unrunnable` makes `runFile` return straight away, so each
   later file on worker k costs one lane that fails in milliseconds.
4. The other workers are busy with real lanes that take seconds each. The poisoned worker keeps
   claiming files with `next++` far faster than they do, so it takes most of the rest of the queue.
   The probe borrows `ports[0]` before the pool starts, so a leak in the probe poisons worker 0 from
   its first file.

**Failure scenario.** In CI, `pg_ctl stop -m immediate -w` fails for one arm lane on worker 2. The
cause could be a slow shutdown under load or a stale pid file. That arm is reported
`RED (identity ok)` and counted as biting. Every later file on worker 2 then produces:

```
lane-unrunnable  <gate>  MEASURE_FAIL: lane could not run: port 127.0.0.1:NNNNN was already taken
(run.sh's collision guard refused, exit 2) ...
```

On a corpus of about 70 files with 4 workers, that can be dozens of rows. The run exits 1, so
nothing is green that should not be. But:

- **None of the rows names the leaking lane, or says that `pg_ctl stop` failed.** The WARNING that
  says so existed only in a discarded string. The JSDoc for `lanePortCollision` itself lists "a
  `pg_ctl stop` that failed" as a cause, and the runner has no way to show which lane that was.
- **The blast radius is not 1/N of the corpus.** It is most of what was left in the queue when the
  leak happened. Those files reach no verdict on this push. A cancelled or red `sql-mutation` is
  also what forces FULL scope on the next push, which is the cascade this phase exists to break.
- **When the leaking lane is worker k's last lane,** no collision follows. The leak is then fully
  silent: an orphaned postmaster on a developer box, and a run that reports nothing about it.

**Hidden errors:** every teardown failure in `run.sh`'s `cleanup()`:

- `pg_ctl stop` failing;
- a `postmaster.pid` with no numeric pid;
- a `kill -9` that fails;
- a missing pid file while a postmaster may still hold the port.

**Recommendation.** Two small changes. Neither touches the classification d86984b40 got right.

1. Make a teardown failure visible on the lane that caused it. In `runLane`, match `run.sh`'s
   teardown lines, anchored at the start of the line as `lanePortCollision` does, and return them,
   for example as `teardownWarning`. The verdict loop should then either raise its own defect (a new
   `lane-teardown` kind in `DEFECT_KINDS`, MEASURE_FAIL, not counted against biting), or at minimum
   log them into the file's sink beside the leg's exit line. Either way the run's output must name
   the leg and gate whose cluster leaked.
2. Bound the spread. After a `lanePortCollision` result, worker k should stop claiming files. Each
   file it would have claimed then goes to a healthy worker, which costs time but no coverage. The
   alternative is to re-allocate worker k's port once through `allocateLanePorts(1)` and retry the
   lane, recording that it did so. Either way a single leak costs one file's measurement, not most
   of the queue.

```js
// runLane, beside measureFail
const teardownWarning =
  (proc.stderr ?? "").match(/^WARNING: (?:pg_ctl stop FAILED|.*ORPHANED|could not SIGKILL pid).*$/gm) ?? [];
return { status: proc.status, output, seconds, measureFail, invoked, teardownWarning };

// worker loop: a refused lane retires its worker instead of draining the queue
if (sink.portRefused) return; // the remaining files go to healthy workers
```

**Confidence: 7/10.** The discard and the queue-claiming behaviour are certain from the code. How
often `pg_ctl stop -m immediate` fails on an ubuntu runner has not been measured, so this rates
likelihood, not mechanism.

## Checked and found clean (no finding)

- **Kill and escalation paths in `spawnAsync`.**
  - `killLaneGroup` swallows only `ESRCH`, the group already being gone, which is correct.
  - Any other errno, such as `EPERM`, is rethrown from a `data` handler or a timer. That is an
    uncaught exception with a stack trace, so it fails loudly, not silently.
  - `settle` is idempotent. It clears the escalation timer and removes the pid from
    `liveLaneGroups` on every path.
  - On overflow, `error` is set before the kill, so the result is always `status: null`,
    `signal: null`, `error.code: "ENOBUFS"`. `laneSpawnFailure` turns that into a
    `lane-unrunnable` MEASURE_FAIL, and `invoked: false` keeps the lane out of both tallies, exactly
    as before. An overflowed lane cannot read as status 0.
  - The drain keeps reading after overflow, so bash's teardown WARNINGs cannot SIGPIPE it, and both
    pipes are destroyed only after `exit`.
  - The normal path still settles on `close`; the vitest row checking status 3 with whole stdout
    and stderr pins this.
- **Timers and listeners keeping the process alive.**
  - The escalation timer is `unref`'d and cleared in `settle`. While it matters, the live child
    handle keeps the event loop running, so the SIGKILL still fires.
  - Measured 2026-10-03 (node, macOS): a process with the three `process.once` signal listeners and
    nothing else exits 0 at once. Node signal handles are unref'd, so the listeners cannot hold the
    runner open.
  - With an interval running, a SIGTERM to that process ended it with status 143. The `once`
    listener is removed before the re-raise, so the runner still dies of the signal, with the same
    exit status as before.
- **Signal forwarding under `nohup`.** I checked whether adding a SIGHUP listener overrides an
  inherited ignore. It does not change anything: a node process with no listener, started under
  `trap '' HUP`, also died on HUP, because Node resets dispositions at startup. This is not a
  regression.
- **Can `lane-unrunnable` hide a corpus defect?** Every `lane-unrunnable` is pushed to `defects`,
  and `exitCode` is `defects.length > 0 ? 1 : ...`, so the run can only get louder. A
  false-positive match would need psql to exit 2, which happens only on a lost connection; psql
  exits 3 under ON_ERROR_STOP. It would also need both of `run.sh`'s exact lines at the start of a
  line. psql prefixes its diagnostics (`psql:file:N:`, or `ERROR:` followed by two spaces), and
  vitest pins both refusals. Even such a mislabel would still exit 1. For an arm, the collision
  lane is `invoked`, so it counts as executed and unjudged, and not as biting. Both tallies agree.
- **Pass or skip where it should fail.** No path in the diff turns a non-zero status, a signal or a
  spawn failure into status 0 or into a skipped leg. The probe leg has no LANE-PROBE marker on a
  collision, so it still raises `lane-unrunnable`.

## Below the reporting bar (noted only, not findings)

- **The signal-forward path does not drain.** The listener re-raises immediately, so the runner's
  pipe ends close while lanes are still tearing down. If `pg_ctl stop` also fails, `cleanup()`'s
  first WARNING `echo` can SIGPIPE bash before its `kill -9` of the postmaster runs. It needs a
  Ctrl-C or a job cancel together with a failed stop. The next run takes fresh ports with
  `listen(0)`, so it is not poisoned.
- **The exit-before-overflow race.** If bash exits, then late buffered data pushes the count past
  `maxBuffer`, the `exit` handler has already run with `overflowed === false`. Settlement then
  waits for `close`, which the escalation SIGKILL still guarantees. It is bounded by `graceMs`.
- **Collisions that bypass the guard** (TOCTOU between the guard and `pg_ctl start`, or no `node`
  on run.sh's PATH with a non-PostgreSQL squatter) still exit 1 through `fail` and read as a
  `baseline` corpus defect. This behaviour predates the diff, and the guard catches the orphaned
  postmaster case the fix targets.
