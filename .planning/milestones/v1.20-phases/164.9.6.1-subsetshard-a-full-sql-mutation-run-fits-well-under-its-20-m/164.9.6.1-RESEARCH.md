## Summary

The serial cost is easy to measure. On main run 37130225515 (b2c59c720, attempt 2, a FULL run), the mutate step ran from 15:01:02 to 15:13:53, about 12.85 min. It drove **691 lanes in series**: 1 probe, 58 baseline, 574 arm and 58 restore lanes, printed as `lane-invocations: 574 … plus 58 baseline / 58 restore leg(s)` and `per-arm lane time: mean 1.1s over 574 arm run(s)`. The cancelled run 37128872396 (9c1dc3137) ran the same corpus for 18 min before the job was killed and printed nothing. The mutate step redirects to `$RUNNER_LOG` and `cat`s it only at the end. Runner-to-runner variance is therefore about 40%, and the margin matters.

Every lane is one `spawnSync("bash", [scripts/pg-lane/run.sh …])` inside `runLane`. Each lane owns a fresh `initdb` cluster under its own `slot-N/lane/pgd` directory, listens on TCP only (`-k ''`, so no socket file), and takes a port that `alloc_port` gets from the OS. The only shared mutable state is three things: the module-level `laneTally` / `laneArmGateTally` counters, the `runCorpus` accumulators, and the port namespace.

**Recommended design:** make `runLane` an async `spawn`, and make `runCorpus` async with a **file-level worker pool**. Up to N gate files run at once. Inside a file the order is unchanged: baseline, then arms, then restore. Each file's log lines and defects are buffered and flushed in corpus order. I measured this design locally by running four `--file` processes at once: 45.2 s serial against 15.4 s concurrent (**2.94x**), with identical verdicts, tallies and zero defects.

The cost is churn in pins, not risk. Four vitest source anchors on `"export function runCorpus({"` and the synchronous call sites must change. They are enumerated below.

The predecessor half has three real traps:

1. The `changed-paths` job token lacks `actions: read`, which the job-logs endpoint needs. A contract test pins the permissions at exactly two entries.
2. The runner image's `gh` 2.101 refuses to print a job log unless `--allow-escape-sequences` is passed. I measured the refusal locally on gh 2.100.
3. "No other errors" is not proof enough. The tolerated reading must be POSITIVE: DRIFT rows, the FAILED line, a findings count equal to the DRIFT row count, and the drift step as the step that failed.

**Primary recommendation:** async file-level pool, capped at `min(4, os.availableParallelism())`, with a distinct `PORT` per worker. Add a separate, opt-in tolerant predecessor proof that only `sql-gate-subset.mjs` calls and that reads the `sql-gate-lint` job log via `gh api --allow-escape-sequences`. Add `actions: read` to `changed-paths`.

### Pattern 1: Async file-level pool inside `runCorpus`
**What:** The per-file body of `for (const name of targets) { … }` (in `runCorpus`, after the probe) becomes a nested `async function runFile(name, sink)`. In it every `laneRunner(...)` becomes `await laneRunner(...)`, and every `log`/`addDefect` goes to a per-file `sink`. N workers pull file indices in order:

```js
// Sketch only — names illustrative except those quoted from run.mjs.
const results = new Array(targets.length);
let next = 0, flushed = 0;
const flush = () => {
  while (flushed < targets.length && results[flushed]) {
    for (const line of results[flushed].lines) log(line);
    for (const d of results[flushed].defects) defects.push(d);
    flushed += 1;
  }
};
const worker = async (k) => {
  while (next < targets.length) {
    const i = next++;                       // synchronous claim: no two workers take one file
    results[i] = await runFile(targets[i], { port: ports[k] });
    flush();
  }
};
await Promise.all(Array.from({ length: Math.min(concurrency, targets.length) }, (_, k) => worker(k)));
```

- `armsExecuted += 1`, `armsUnjudged`, `armsAnnotated`, `armsWaived` and `timings.push` stay in `runCorpus`'s scope. The nested function sits textually inside `runCorpus`, so the source pins that look for `armsExecuted += 1` in the `runCorpus` body still find it. JS is single-threaded, and these are commutative sums, so the totals are identical.
- `perFileTallies` must be ordered. Pre-allocate it by index, or push it in the ordered flush. Never push it from a worker in completion order.
- `laneTally[leg] += 1` stays inside `runLane`, now on the child's `close` when it started (`!error`). This keeps the SP-C05 independence.
- `nextSlot()` is synchronous (`slot++`), so slots stay unique.
- **Await the probe lane before the pool starts.** Its result gates the `lane-blocked-stale` defect.
- **The concurrency default lives inside `runCorpus`'s parameter list** (`concurrency = defaultLaneConcurrency()`), and the CLI never passes it. `main`'s call text then changes only by gaining `await`. The pin at `mutation-runner-floors.test.ts` ("the CLI can never hand a subset run a lowered floor: main's runCorpus call passes no floor, ceiling or lane runner") matches `runCorpus\(\{[^}]*\}\)` and expects exactly `runCorpus({ scopeDir, onlyFile, onlyArm, subsetFiles, scopeReason })`. That still holds if `main` becomes `return (await runCorpus({ scopeDir, onlyFile, onlyArm, subsetFiles, scopeReason })).exitCode;`.
- Self-tests and vitest pass `concurrency: 1` or `concurrency: 4` explicitly where they need to.
- **`lane-concurrency:` line.** Print it once, before any lane and after `log(reasonLine);`. That keeps the source pin, which requires the next `log(` after `log(scopeLine);` to be `log(reasonLine);`. Suggested text: `lane-concurrency: <N>   (gate files in flight at once — min(cap 4, availableParallelism <A>); lanes within a file run in order)`. This is a new line: no existing regex in ci.yml (`^scope: `, `^scope-reason: `, `^coverage: files `, `^unreachable: `, `^lane-blocked: `, `^lane-probe: `, `^arms: `, `^biting: `, `^lane-invocations: `, `^  file …`, `^ARMS_FLOOR …`) can match it.

**Why file-level and not arm-level:** an arm lane may only start after its file's baseline is GREEN. `runCorpus` does `continue; // arms cannot be judged against a red baseline`. If arm lanes were spawned speculatively, `laneTally.arm` would count lanes that the verdict loop never adds to `armsExecuted`, and `absurdity` would fire. The file pool keeps the existing per-file control flow byte-for-byte.

**Makespan:** the largest file is `test_strategy_shares_rls.sql` at 45 arms, so 47 lanes, or about 52 s. The whole job is about 691 × 1.1 s / 4 ≈ 190 s of lane time. The tail is bounded by one file.
- Optional: dispatch files longest-first by annotated count, which still flushes in corpus order. It is a small gain, and not required.

### Pattern 2: Async lane spawn that keeps the `spawnSync` result shape
**What:** `runLane` returns the same `{ status, output, seconds, measureFail, invoked }`. A small `spawnAsync` builds `{ status, signal, error, stdout, stderr }`, so `laneSpawnFailure(proc)` (exported and pinned) is reused unchanged.
- Resolve once, on `close`. Set `error` on the `error` event (ENOENT).
- **Emulate `maxBuffer: 128 * 1024 * 1024`.** Count bytes, and on overflow kill the child and set `error = { code: "ENOBUFS" }`. `laneSpawnFailure` documents ENOBUFS as one of its classified cases, and async `spawn` has no `maxBuffer` of its own.
- Keep `output = stderr + "\n" + stdout`. The current order puts stderr first, because psql streams RAISE output there. Do not interleave the two streams by arrival time, because attribution reads stderr-first order.
- Pass `env: { ...process.env, PORT: String(port) }` (Pattern 3).

### Pattern 3: One port per worker, handed out by the runner
**What:** before the pool starts, allocate N **distinct** ports in-process (`net.createServer().listen(0, "127.0.0.1")`, read the port, close; repeat until there are N distinct values). Worker k passes `PORT=<ports[k]>` to every lane it runs. Its lanes are sequential, so the port is reused only after the previous lane's `pg_ctl stop -m immediate -w` returned.
- `run.sh` already honours `PORT`: `if [ -z "${PORT:-}" ]; then PORT=$(alloc_port) || exit 1; fi` [VERIFIED: scripts/pg-lane/run.sh:288]. It still runs its bind-test collision guard, which exits 2 per its header: `# Exit codes: 0 pass · 2 port collision (refused) · 130 SIGINT · 143 SIGTERM ·` [VERIFIED: scripts/pg-lane/run.sh:44].
- A side benefit: an exported `PORT` in a developer's shell would otherwise be inherited by every concurrent lane, and they would all collide. The explicit per-worker env overrides it.

### Pattern 4: Opt-in tolerant predecessor proof (D-02)
**What:** leave `predecessorVerdict(sha, fetchPredecessor)` strict for the docs-only classifier (`classifyPushRange` calls it before taking its short path). Add a tolerant variant: either an exported function, or an options argument such as `predecessorVerdict(sha, fetch, { tolerateBaselineDrift: true, fetchJobLog })`. **Only** `sql-gate-subset.mjs` `derivePush` passes it. See Open Question 1.

**Algorithm.** It must route around all three early returns, which today are `bad`, `redSuite` and the `frontendOk` requirement (a):
1. Run the same shape checks, foreign-SHA check, `(check_suite.id, name)` dedupe and pending check as today.
2. `bad` = every deduped GitHub Actions run whose `conclusion` ∉ `PREDECESSOR_OK_CONCLUSIONS`. Tolerance is considered only if:
   - every `bad` run's name ∈ {`sql-gate-lint`, `frontend`};
   - a `sql-gate-lint` run is among them, with conclusion exactly `failure`. `cancelled` or `timed_out` mean the log is incomplete;
   - all of them sit in ONE check suite.
3. `redSuite`: every non-OK GitHub Actions suite must be exactly that suite. Any other red suite, for example a red `supabase-migrate` workflow, stays RED.
4. Read the deduped (latest-attempt) `sql-gate-lint` run's job log. **The check-run `id` equals the job id.** Measured: check run `111213703410` `sql-gate-lint` is job `111213703410` (`…/actions/runs/37126803714/job/111213703410`).
5. Parse the log (rules below). On success, return `{ ok: true, tolerated: true, why: "red only with tolerated baseline drift: <fn/nargs list>" }`. `judgePush` then composes `…; predecessor <sha12> red only with tolerated baseline drift: sync_strategy_analytics_status/1`.
6. Requirement (a) is relaxed ONLY on this path, and only into a POSITIVE condition. A deduped `frontend` run must EXIST, be `completed` with conclusion exactly `failure`, and sit in the same suite as `sql-gate-lint`. Without this, a predecessor whose only run is a red `sql-gate-lint` would narrow even though its aggregator never ran, which is the "CI has not finished" case requirement (a) exists to refuse. On the strict path `frontend` must still be `success`.

**Production log reader:**
```js

  encoding: "utf8", stdio: ["ignore", "pipe", "pipe"], timeout: 60_000, maxBuffer: 16 * 1024 * 1024,
});
```

- The runner image has gh 2.101.0, and the guard is in gh ≥2.97 [CITED: web search on cli/cli releases, see Sources], so CI will refuse without the flag.

These come from the source of truth: `report()` prints `` console.error(`::error::MEASURE_FAIL — ${mf.reason}`); `` and `` console.error(`::error file=${f.file},line=${f.line}::${f.kind} — ${f.message}`); `` [VERIFIED: scripts/baseline-content-drift-check.mjs:691-694]. `describeRow` builds `` `${r.status} ${r.name}/${r.nargs} ` + `snapshot=${r.snapshotHash ?? "(absent)"} chain=${r.candidateHash ?? "(absent)"}` `` plus an optional `` ` differing-lines=${r.hunks}` `` [VERIFIED: scripts/baseline-content-drift-check.mjs:446-451].

**Parse rules.** All must hold, otherwise RED with a named reason:
1. Strip the BOM and the `^\S+Z ` timestamp prefix.
2. Find the LAST `##[group]Run ` header before `##[error]Process completed with exit code 1.`. It must be exactly `##[group]Run node scripts/baseline-content-drift-check.mjs`, not the `--self-test` step and not any later step. This is positive proof that the drift step is the one that failed.
   - Why it matters: if the drift `--self-test` fails, it prints `SELF-TEST FAIL: …` to stderr with NO annotation [VERIFIED: scripts/baseline-content-drift-check.mjs:936]. The log then holds only the exit line, and a "no other errors" rule would wrongly accept it.
3. Every `##[error]` line in the whole log must be one of exactly three kinds:
   - `content-drift — DRIFT <name>/<nargs> …` rows. At least one is required.
   - The single `baseline-content-drift FAILED.` line.
   - The single `Process completed with exit code 1.` line.
4. These make the result RED:
   - any `allowlist-hash-moved` / `allowlist-stale` / `allowlist-malformed` finding;
   - `MEASURE_FAIL`;
   - `content-drift — SNAPSHOT_MISSING` or `SNAPSHOT_ONLY` (Open Question 2);
   - any other `##[error]`.
5. `baseline-content-drift: findings <N>` must be present, and N must equal the DRIFT row count. This catches truncation and any finding the regex missed.
6. The function list goes into `why`. Keep only `[\w.]+/\d+` tokens: the text reaches `$GITHUB_OUTPUT` and the `scope-reason:` line, where `oneLineReason` already sanitises it.

### Anti-Patterns to Avoid
- **Printing lane results in completion order.** This breaks determinism and every ordered pin. Buffer per file and flush in corpus order.
- **Incrementing `laneTally` anywhere but `runLane`, or `armsExecuted` anywhere but `runCorpus`.** The source pins fail, and the two tallies stop being independent.
- **Speculative arm lanes before the baseline verdict.** This trips `absurdity`, as covered under Pattern 1.
- **Relying on `run.sh`'s `alloc_port` under concurrency.** See Pitfall 1.
- **Reading "no other `##[error]`" as proof.** Require the positive reading in Pattern 4.
- **Changing `predecessorVerdict`'s strict behaviour for the docs-only path without a decision** (Open Question 1).
- **Adding a CLI `--concurrency` flag that ci.yml passes.** It breaks the nightly FULL-tail byte-equality (`FULL_TAIL_FIRST_LINE` in the parity test) and the `main` call pin. If a flag is wanted for local debugging, the CI line must not use it.

## Common Pitfalls

### Pitfall 1: Port TOCTOU becomes a flake source under concurrency
**What goes wrong:**
- `alloc_port` binds port 0 in a throwaway `node` and closes it.
- `run.sh` then runs `initdb` (about 0.35 s, measured locally) before `pg_ctl … -o "-p $PORT …" start` binds the port.
- A sibling lane's `alloc_port` inside that window can get the same port. That lane then exits 2 (guard) or 1 (`pg_ctl could not start`).
- Both are integer statuses, so `laneSpawnFailure` returns `null`. An arm reads as `wrong-first-failure` and a baseline as `baseline`: a corpus defect named for an instrument flake.

**Why:** the lanes are separate processes and cannot see each other's chosen ports.

**How to avoid:** Pattern 3.

**Warning signs:**
- `wrong-first-failure` with `NO-IDENTITY` on an arm that was green on the previous run;
- `pg_ctl could not start the lane cluster on 127.0.0.1:<port>` in a lane's output.

**Rough size [ASSUMED: Linux random bind(0) model]:** about 700 lanes, each window seeing about 1 sibling allocation, over about 14k candidate ports ⇒ about 5% of runs.

### Pitfall 2: Source pins anchored on the synchronous signature
**What goes wrong:** `export async function runCorpus({` no longer contains the anchor `"export function runCorpus({"`. Every test that slices the function body then fails with "anchor not found".

**Where (enumerate and update them all in one task):** `src/__tests__/mutation-runner-floors.test.ts`:
- `fnBody("export function runCorpus({")` (WR-02 per-file wiring test);
- `fnBody("export function runCorpus(")` (twice: the tally independence pins);
- `anchorIndex(code, "export function runCorpus({")` (the SOURCE PIN on `log(scopeLine);` → `log(reasonLine);`);
- the end anchor `"\n}\n"` used to cut the body. Nested functions must stay indented so their closing brace is not `\n}\n`.

`anchorIndex(src, "function selfTest()")` still matches `async function selfTest()`. Also update:
- the synchronous `runCorpus(...)` calls in vitest (`it("FIRES through runCorpus's real verdict loop…")`, the dead/killed lane rows, the print-contract test, the SUBSET fixture helper, and the floors rows) → `await`;
- the 28 calls inside `selfTest()`;
- `main` and `process.exit(main(...))` → `process.exit(await main(...))`.

**Warning sign:** "anchor not found" or `expected undefined` on `.exitCode` (a Promise).

### Pitfall 3: Self-test numbering census
**What goes wrong:** adding "SELF-TEST 18/18" renumbers every `N/17` header. `src/__tests__/gate-family-meta.test.ts` uses the needles `"SELF-TEST 9/17: [R4-C01] …"`, `"SELF-TEST 11/17: [R4-C02] …"` and `"SELF-TEST 12/17: the nested-EXECUTE DO forgery"`, and a ci.yml comment says "17/17".

**How to avoid:** add a separate family, as the precedent `=== SELF-TEST (subset) N/7 …` already does. For example: `=== SELF-TEST (concurrency) 1/2: the selftest corpus at concurrency 1 and 4 prints identical normalised output and tallies ===`.

### Pitfall 4: Token scope for the job-logs endpoint
**What goes wrong:**
- `changed-paths` declares `permissions:` with only `contents: read` and `checks: read` (ci.yml, `changed-paths:` job; `checks: read` sits right after `contents: read`).
- A job-level block sets every unlisted scope to none.
- `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs` is listed under the **Actions** permission with access **read** [CITED: docs.github.com permissions-required-for-fine-grained-personal-access-tokens].
- Without `actions: read` the read fails, and the proof fails SAFE, to FULL. The tolerance would then never engage, silently.

**How to avoid:**
- Add `actions: read`.
- Update `ci-docs-path-filter.contract.test.ts` (`it("\`changed-paths\` declares exactly \`contents: read\` + \`checks: read\`…")`). It asserts `expect(perms.sort()).toEqual(["checks: read", "contents: read"])`, and its comment says "nothing needs `actions: read`".

**Verify on CI:** the first PR run cannot exercise a push predecessor. The proof comes on the first push to main after merge whose predecessor is drift-red, or from a manual read of the job log with the job's token. "It works without `actions: read`" is [ASSUMED] and should not be relied on.

### Pitfall 5: The fake-gh harness pins exactly two calls
**What goes wrong:** the `sql-gate-subset.mjs` self-test row "WR-03 END TO END…" pins `red.ghArgv` to exactly the check-runs and check-suites calls. A tolerated scenario makes a third call (the logs endpoint), and the offline fake `gh` must answer it. `runMainOnPush` in `classify-changed-paths.mjs` writes that fake.

**How to avoid:**
- Extend the fake `gh` with a logs response mode.
- Pin the third argv, including `--allow-escape-sequences` and `repos/self-test/repo/actions/jobs/<id>/logs`.
- Bump `EXPECTED_ASSERTIONS` (currently `92`, `scripts/sql-gate-subset.mjs` `export const EXPECTED_ASSERTIONS = 92;`). The self-test refuses a count mismatch.

### Pitfall 6: Contention raises the per-lane time
**What goes wrong:**
- Locally, `per-arm lane time` went from 0.9-1.1 s serial to 1.2-1.4 s at 4-way.
- Nothing parses that line. Only ci.yml comments quote historical values.
- Wall-clock gain is less than 4x: 2.94x measured on 10 cores.
- On a 4-vCPU runner the cores are the limit. Expect 2-3x [ASSUMED]. That still meets "about half" (12.85 min → about 4.5-6.5 min).

**How to avoid:** quote the first FULL main push's mutate-step timestamps as the success measurement (CONTEXT `<specifics>`). Do not tune the cap above 4 without a measurement.

### Pitfall 8: A rejecting worker reaches `finally` while sibling lanes still run
**What goes wrong:**
- Today a throw in the per-file loop propagates synchronously, and `rmSync(scratchRoot, …)` in `finally` runs with nothing in flight.
- With `Promise.all`, the first rejection jumps to `finally` while the other workers' lanes are still running inside `slot-N/lane`. Their workdirs are deleted mid-lane, and their `pgd` clusters are left to the lane's own EXIT trap.

**How to avoid:** drain every worker before cleanup. Use `Promise.allSettled`, or a stop flag plus a completion barrier, then rethrow the first rejection. Only after that does `finally` remove the scratch root.

### Pitfall 9: Overlapping `runCorpus` calls in one process corrupt each other's tallies
**What goes wrong:** `laneTally` and `laneArmGateTally` are module-level, and `runCorpus` reads them as snapshot deltas (`const laneTallyBefore = { ...laneTally };`). Two `runCorpus` calls that overlap in time each count the other's lanes, and `absurdity` fires.

**How to avoid:** every serial-versus-parallel comparison, in `SELF-TEST (concurrency)` and in vitest, runs the two calls ONE AFTER THE OTHER (`await a; await b;`), never under `Promise.all`. Concurrency lives INSIDE one `runCorpus` call only.

### Pitfall 7: The cancelled run prints nothing
**What it is:** the mutate step does `node … > "$RUNNER_LOG" 2>&1; status=$?; cat "$RUNNER_LOG"`. A job killed at the timeout loses the whole runner log: run 37128872396's mutate step printed nothing between 14:15:54 and `##[error]The operation was canceled.` at 14:33:56. The "printed BEFORE any lane so a run killed mid-corpus still says what it was covering" comment on the `scope:` line does not hold in CI.

**Scope:** not in scope (D-03: no time guard). Do not "fix" it with a `tee`: that changes the byte-equal mutate block in both workflows. Note it only.

## Open Questions

1. **Which callers get the tolerance?**
   - What we know: D-02 names `predecessorVerdict`. That function serves BOTH `classifyPushRange` (the docs-only short path, which skips heavy CI) and `sql-gate-subset.mjs` `derivePush`. 164.9.6 D-13 calls the push proof "the same proof the docs-only short path uses".
   - What's unclear: whether a docs-only push on top of a drift-red main should skip CI. If it does, `sql-gate-lint` would not run on the new HEAD and main would read green while the drift is still unresolved.
   - Recommendation: make it **opt-in for `sql-gate-subset` only**. The docs-only path stays strict, and a self-test row pins it. Confirm with the founder, and record the choice in CONTEXT (D-02 addendum).
2. **`SNAPSHOT_MISSING` rows.**
   - What we know: a migration that ADDS a function produces `content-drift — SNAPSHOT_MISSING <fn>/<n>` until the post-apply re-dump. The drift script's own lineage records this as the normal post-migration state ("Same shape as the 164.1.1 move above: both are SNAPSHOT_MISSING findings").
   - What's unclear: D-02 as written ("only `content-drift — DRIFT <fn>` rows") keeps those predecessors RED, so they still force FULL.
   - Recommendation: implement D-02 literally (DRIFT only) and ask the founder whether `SNAPSHOT_MISSING` and `SNAPSHOT_ONLY` belong in the tolerated class. Do not widen it silently.
3. **Can `frontend` be red for its own reasons?**
   - What we know: the aggregator prints a `<job>: <result>` row block, measured in job 111216556719: `sql-gate-lint: failure`, `plan-anchor-verify: skipped`, `… tolerated for this row only.` It can fail on a non-tolerated `skipped` row, and a `skipped` check run counts as OK in `PREDECESSOR_OK_CONCLUSIONS`.
   - Recommendation: optionally read the `frontend` log too (same reader) and require `sql-gate-lint: failure` to be its only non-`success` row apart from rows with a printed tolerance line. That is one more API call. The planner decides. If it is skipped, record the residual in the plan.
4. **Should ci.yml assert the `lane-concurrency:` line?**
   - Fail-loud house style says yes (MEASURE_FAIL on absence, value ≥1). It requires a byte-equal edit to the nightly's assert copy, and the parity test enforces that.
   - Recommendation: assert presence only, in both workflows.
