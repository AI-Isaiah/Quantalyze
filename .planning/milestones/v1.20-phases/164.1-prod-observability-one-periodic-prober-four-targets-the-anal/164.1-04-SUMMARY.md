`mt5-no-ipc`:

> The rpyc bridge is NOT ATTACHED (-10004): the gateway is down or mid-redeploy, so the terminal was never reached. Run `railway redeploy` on the mt5-gateway service, wait for the container to report healthy, then re-run this prober. This is the code a redeploy DOES fix.

> The bridge IS ATTACHED but the terminal is NOT ANSWERING (-10005). ## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 2 - Missing critical functionality] `MT5_PROBE_PY` emits `terminal_info` in both branches**
- **Found during:** Task 1
- **Issue:** The plan (following `mt5-diag.sh`) sets `terminal_info: null` only in the null branch, so the HEALTHY reading is the ABSENCE of a key. `classifyProbe`'s OK test would then be satisfiable by a truncated or malformed PROBE line.
- **Fix:** the else branch also sets `out["terminal_info"] = "present"`. What the probe CALLS is unchanged. Documented at the constant.
- **Files:** `scripts/prod-prober/arms/mt5.mjs`, `fixtures/mt5/ok.txt`
- **Commit:** `459f5146`

**2. [Rule 3 - Blocking] A per-entry fixture `load` hook**
- **Found during:** Task 2
- **Issue:** `ARM_FIXTURE_TABLE`'s loop calls `loadFixture`, which JSON-parses. The mt5 fixtures are raw text.
- **Fix:** `loadFixtureText` plus an optional per-entry `load` defaulting to `loadFixture` — the same shape plan 03 used for `kinds` and `makeSeams`.
- **Commit:** `c66099c7`

**3. [Scope, recorded not fixed] The mt5 table entry declares FOUR kinds, not five**
- `mt5-probe-timeout` is a property of the SPAWN; no stdout transcript can produce it, and the acceptance criteria pin the fixture count at 6. It has its own counted scenario (46/50), its own by-name `KIND_ASSERTIONS` entry, and the code says why at the site.

**4. [Extra coverage] The exit-255-WITH-a-PROBE-line positive control**
- The plan's criterion "the two IPC kind literals appear in DIFFERENT scenarios" could not be met by splitting scenario 47/50, which needs both rows by nature. Rather than weaken it, a positive control was ADDED to scenario 45/50: a CLI that exited 255 while the terminal answered `-10004` must still be reported as `-10004` with the REDEPLOY remedy. Without that leg, 45/50 would also pass an arm that treated any non-zero exit as transport and never read stdout. Measured after: `kind === "mt5-no-ipc"` appears in scenarios {45, 47}, `kind === "mt5-ipc-timeout"` in {47, 49} — each has a scenario the other lacks.

No architectural changes were needed; no Rule 4 decision arose.

## Known limits (filed to `.planning/WINDOWS.md`)

The mt5 arm MUST declare `RAILWAY_PROJECT_ID` / `RAILWAY_MT5_SERVICE` / `RAILWAY_ENVIRONMENT` (D-06, and they are 3 of the 10 slots), but their LIVE values are `mt5-gateway` and `production` — short, common strings. **Measured at this plan** against the real-shaped env:

Fail-SAFE (it over-redacts, never under-redacts) but it degrades the `mt5-ssh-transport` diagnostic, which is precisely the row an operator reads when the transport is broken. **Not fixed here:** the scrubber is plan 01's, and classifying names as secret-vs-identifier is a change to a security control, outside this plan's task scope — the same call plan 03 made for entry 36.

The Railway workspace token is long and high-entropy, so no realistic value of it can appear as a substring of unrelated text. The mt5-shaped hazard is the one above, and it is the identifiers rather than the token.
