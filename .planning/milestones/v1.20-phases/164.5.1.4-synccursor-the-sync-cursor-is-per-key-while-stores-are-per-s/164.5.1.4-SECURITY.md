## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| `anon` / `authenticated` browser client → `public.strategy_sync_cursors` | PostgREST exposes every table in `public`. The marker is a NEW TABLE rather than a column on `strategies` precisely because `strategies_read` is a PUBLIC-read policy — a column there would publish internal sync state for every published strategy. | Internal sync watermark (per-strategy resume timestamp) |
| `service_role` → `strategy_sync_cursors` | The sole writer. `BYPASSRLS` is a ROW-level exemption and confers NO object-level privilege, so the table needs an explicit GRANT or the whole phase is inert in production. | Read + upsert of marker rows |
| repo migration file → shared TEST → PROD | A migration asserting over DATA can pass PROD and REFUSE shared TEST (TEST holds PROD's catalogue, never its data), and a refused TEST apply BLOCKS the PROD apply. | DDL + self-verify assertions |
| this checkout's Supabase CLI → PRODUCTION | The CLI here is linked to prod and `current_database()` proves nothing. No apply happens from this phase; the only cluster touched is the disposable `scripts/pg-lane` cluster. | None — no DB command was run from this checkout |
| venue trade history → per-key `fetch_all_trades` window → per-strategy stores | A window chosen too late loses real trades permanently; too early costs an idempotent re-fetch. Every decision here is biased toward the second. | Trade records |
| in-process `per_strategy_stored` / `recompute_enqueue_errors` → durable `strategy_sync_cursors` | The only point where per-strategy outcome becomes durable. A write placed before the enqueue loop reads a half-filled input. | Per-strategy sync outcome |
| phase verdict → Phase 164.5.1.3 SYNCADMIT's plan | SYNCADMIT is queued behind this and blocked on it. An overstated verdict propagates into the next phase's assumptions. | Claims about production state |

## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |
|---------|------------|-----------|-------------|------|
| R-01 | T-164.5.1.4-16 | A persistently-held strategy pins the key's fetch window, so healthy siblings re-fetch a growing range every tick. Precedented: the `held` terminal status already documents and accepts the same growth at key level, and the re-fetch is idempotent — the cost is efficiency, not correctness. Accepted with a NAMED SIGNAL rather than silently: the held set appears in the `cron_sync` response envelope and one warning per key states the consequence. | Phase 164.5.1.4 plan 03, autonomous-mode delegation | 2026-09-19 |
| R-02 | T-164.5.1.4-17 | The held-strategy warning names strategy ids. Those ids are already logged by name throughout this function's existing error paths; the destination is the internal log sink, not the public repo. No new class of value is exposed, and the severity is below the `high` block threshold. | Phase 164.5.1.4 plan 03, autonomous-mode delegation | 2026-09-19 |
| R-03 | T-164.5.1.4-23 | **Recorded here because it did not exist at plan time and must not be inherited silently.** `MAX_MARKER_LOOKBACK_MS` (30 days) bounds how far back a held marker can pin the key's fetch window. Without it an unclearable hold grows the window every tick until it exceeds `KEY_SYNC_TIMEOUT` and wedges EVERY strategy on the key. The bound was chosen over the wedge — but the truncation is per-KEY and it is a LOSS, not a deferral: trades older than the cap will be fetched by no tick. Three controls make it visible and keep it narrow: (a) round 2 established that the clamp applies ONLY to a marker-derived floor, never to the key-cursor fallback, so the migration's "inert on arrival" property is intact and the clamp cannot fire on a strategy that never held; (b) the loss reaches the response envelope as `strategy_cursor_window_clamped`, not only the log — it was log-only until round 2 and that was the phase's one remaining silent permanent-loss path; (c) the warning states that a hold this old needs a human. | Phase 164.5.1.4 round-2 review (WR-04 / BL-01 / NEW-1), orchestrator | 2026-09-19 |
