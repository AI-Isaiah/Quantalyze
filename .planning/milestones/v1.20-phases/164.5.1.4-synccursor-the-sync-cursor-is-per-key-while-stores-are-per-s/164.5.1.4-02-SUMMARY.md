## What shipped

### The two helpers, and why there is exactly one resolver

`_strategy_resume_point(strategy_id, strategy_cursors, key_cursor)` implements the membership rule
and nothing else: `strategy_id in strategy_cursors` returns the mapped value **verbatim, including
when it is null**; otherwise the key's own cursor. Its docstring carries the trace of why a `.get()`
is wrong — under a `.get()`-shaped design the failed strategy is given no row, the key cursor
advances anyway (correctly, a sibling succeeded), the next tick falls back to that advanced cursor,
and the strategy is stranded exactly as before while every "a row was written" assertion stays green.

Both the read floor and the hold-write call this one function. Neither re-implements it. That is the
whole reason it exists as a named helper rather than as two inline `in` checks.

`_resume_floor_ms(strategy_ids, strategy_cursors, key_cursor)` is the N-way floor: with no eligible
strategies it parses the key cursor (today's behaviour on an empty fan-out); otherwise it takes the
minimum across resolved resume points, and **any** null or unparseable value collapses the whole
window to a full-history fetch. One `fetch_all_trades` call serves the whole key, so the window must
cover the slowest linked strategy — over-fetching costs an idempotent re-store, under-fetching loses
data permanently, and every decision here is biased toward the first.

It calls the module-global `parse_since_ms` **by name**, which is what keeps the existing
`patch.object(cron_mod, "parse_since_ms", ...)` tests intercepting it.

### The write, and why its placement is a constraint

The marker upsert is the **last** write in `_sync_single_key`, after both the storage loop and the
recompute-enqueue loop, because it reads `recompute_enqueue_errors` — which only exists after the
second loop. A comment above the condition states this in the file, so a later reader cannot move the
block up without reading why it cannot.

The condition is:

```
strategy_advances = (not trades) or (per_strategy_stored.get(sid, 0) > 0
                                     and sid not in recompute_enqueue_errors)
```

A naive `stored > 0` mirror closes the trade-stranding criterion and looks correct while leaving the
recompute-stranding criterion wide open: a strategy whose trades stored but whose
`derive_broker_dailies` job never got queued would advance past the very window whose recompute never
fired. That is the Phase-18 shape the enqueue loop's own pre-existing comment already describes.

Every strategy in the fan-out produces a row. A held strategy's value is `_strategy_resume_point(...)`
resolved against the **pre-tick** key cursor, captured into a local at the top of the function before
the `api_keys` UPDATE overwrites the stored one.

### The read, and the production source of the mapping

`cron_sync` collects the union of eligible strategy ids across all keys, walks
`strategy_sync_cursors` in `_CRON_IN_LIST_PAGE_SIZE` chunks using this file's established `in_`
idiom, and attaches to each key row the sub-mapping restricted to its own strategies. Membership is
preserved at both steps: a strategy with no row is **absent**, never present-with-a-null.

The whole lookup is fail-open. On failure every key gets an empty mapping — which *is* the absent-row
semantics, so the tick degrades to today's key-cursor-only behaviour rather than to a wrong window —
and the error is recorded in the response body (`strategy_cursor_lookup_error`) beside the existing
recompute `lookup_error` rather than raised. The marker write degrades the same way
(`strategy_cursor_write_error` in the per-key envelope): markers stay behind, the next tick
over-fetches, and over-fetching is idempotent because `sync_trades` deletes payload-window-scoped
before re-inserting.

⚠️ **This is also what makes the change inert on the tick the migration lands.** No rows exist, every
mapping is empty, every strategy falls back to the key cursor, and the fetch window is byte-for-byte
what it is today.

### 2. [Design decision the plan delegated] The control test asserts marker existence before asserting the window advanced

The plan's task-1 `<done>` requires **both** new tests to be RED against unmodified `cron.py`. As
first drafted, the control's load-bearing assertion (`tick 2's since_ms > t0_ms`) would have **passed**
against unmodified code — the key cursor advances on full success, so the unmodified read produces a
window past T0 for the right-looking wrong reason.

Fixed by having the control derive tick 2's inputs from tick 1's captured upsert payload and assert
that derivation is non-empty first (`set(cursors) == {"strat-A", "strat-B"}`). That is not a fudge to
manufacture a RED: it is the same two-tick contract the consequence test asserts, and it is what makes
the control a real second observation of the loop rather than a single-tick assertion wearing a
control's name. MEASURED: it failed on that assertion against unmodified code
(`both strategies must get a marker row; captured: {}`), and passes after the fix.
