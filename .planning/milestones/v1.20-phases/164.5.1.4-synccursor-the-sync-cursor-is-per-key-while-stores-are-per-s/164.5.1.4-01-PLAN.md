defect (the resume cursor is per-KEY while stores are per-STRATEGY, so one succeeding sibling
advances the shared cursor past every failing sibling's window), name the phase, and carry an

state); it does not harmonise the two sync-cursor disciplines — the marker is written with the plain
direct-write style `cron.py` already uses for `api_keys`, not the fenced `advance_sync_cursor` RPC
style `job_worker.py` uses, and harmonising them is deliberately out of scope per CONTEXT Area 2;
and it registers no scheduled job. That last item exists because a reviewer unfamiliar with the
deliberate split will reasonably ask why this write is not fenced — answer it in the file, not in
the review thread.

**Transaction.** `BEGIN;` then `SET lock_timeout = '3s';`, matching this repo's new-table convention.

**Table.** `CREATE TABLE IF NOT EXISTS strategy_sync_cursors` with exactly three columns:
`strategy_id UUID PRIMARY KEY REFERENCES strategies(id) ON DELETE CASCADE`; `last_sync_at
TIMESTAMPTZ` (nullable); `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. No `api_key_id` column —
`strategies.api_key_id` is `ON DELETE SET NULL` and mutable, so keying on it would strand the old row
when a strategy is re-pointed. No surrogate `id` — `PRIMARY KEY (strategy_id)` already indexes the
exact column the read path filters on and is the conflict target the writer upserts against, so a
secondary index would be dead weight. No `updated_at` trigger: this table has exactly one writer
(the cron upsert), which sets the column in its own payload; installing a trigger for a
single-writer table buys nothing and adds a second thing to keep correct.

⭐ **Name the column `last_sync_at`, matching `api_keys.last_sync_at` byte-for-byte**, and not the
`last_synced_trade_at` RESEARCH proposed. The value stored is wall-clock at sync time, exactly like
the key column it falls back to — not the maximum trade timestamp in the payload. A name containing
"trade" invites a future reader to derive it from the payload, which would silently diverge from the
one column it mirrors.

**Comments.** `COMMENT ON TABLE` naming it as internal cron resume state with no user-facing
consumer. `COMMENT ON COLUMN strategy_sync_cursors.last_sync_at` must state the three-state
semantics precisely, because the read path depends on it and a `.get()`-shaped reading of it is
wrong: a row that is ABSENT means "no per-strategy information — fall back to `api_keys.last_sync_at`",
which is what makes this migration inert the moment it lands; a row that is PRESENT with a NULL
value means "this strategy must re-fetch from the start of history"; a row present with a timestamp
means "resume from here". Absent and present-with-NULL are DIFFERENT states and the consumer must
distinguish them by key membership.

**RLS.** Enable row level security, then a single policy `strategy_sync_cursors_deny_all` `FOR ALL`
with `USING (false)` and `WITH CHECK (false)`, preceded by `DROP POLICY IF EXISTS` so the file is
re-runnable, plus a `COMMENT ON POLICY` in the shape `compute_jobs_deny_all` uses.

⭐ **This is Option B from PATTERNS.md and it is taken on evidence, not by default.** Two shipped
precedents exist. `allocator_holdings_service_all` writes an explicit `auth.role() = 'service_role'`
arm — but that table HAS an owner-facing SELECT tier, so its service-role arm is one of three, and
the intent it documents is "service_role in addition to owners". `compute_jobs_deny_all` has no
owner tier at all, which is exactly this table's posture: the sole writer is the analytics service's
service-role client, and no browser, anon or authenticated consumer exists or is planned. Both forms
work only because service_role bypasses RLS by default (ADR-0003, quoted in the `allocator_holdings`
comment); `USING (false)` is the strictly narrower WRITTEN grant of the two, since the `auth.role()`
form would also admit any non-bypassing connection presenting that role claim. Narrower wins for a
table with zero user-facing consumers. Do NOT add a `REVOKE` for `anon`/`authenticated` on top: the
policy is then no longer the live control, and an assertion that a non-service caller is denied would
start passing for the GRANT reason rather than the POLICY reason — the vacuity trap both existing
`*_rls.sql` gates independently warn about.

**Self-verify.** Close with a `DO $$ ... $$` block whose every assertion reads ONLY catalogs —
`information_schema` and `pg_catalog`. Assert, each with its own `RAISE EXCEPTION` naming the phase
and what failed: the table exists in schema `public`; its primary key column set is exactly
`{strategy_id}`; a foreign key from `strategy_id` to `strategies` exists whose delete action is
CASCADE; row level security is enabled on the relation; and a policy named
`strategy_sync_cursors_deny_all` exists on it. ⛔ No assertion anywhere may read the contents of a
pre-existing row, count rows against a production condition, or insert a throwaway row. The
dummy-row functional probe the `advance_sync_cursor` migration uses is REJECTED here and the reason
belongs in a comment beside the block: satisfying this table's foreign key needs a real `strategies`
row, which needs a `profiles` row, which needs an `auth.users` row — three production inserts whose
triggers and constraints the disposable lane cannot model, which is a materially larger risk than
the probe buys over a catalog assertion.

⚠️ One judgement call to settle by MEASUREMENT on the lane, not by guessing: if you also want to
assert the policy's qualifier is the false constant, first check on the lane how
`pg_get_expr(polqual, polrelid)` actually renders it. Include the assertion only if the rendering is
confirmed; if it renders as anything you did not predict, OMIT the assertion. A migration that
raises because a catalog rendered text differently than expected blocks the PROD apply, and this
table's qualifier cannot drift without the policy statement itself being edited, which the named-policy
assertion already catches.
