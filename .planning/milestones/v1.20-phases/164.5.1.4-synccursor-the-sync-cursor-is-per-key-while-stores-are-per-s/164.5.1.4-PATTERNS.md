## Pattern Assignments

### `supabase/migrations/<ts>_strategy_sync_cursors.sql` (migration, new table)

**Two analogs are needed together — no single existing migration matches both the RLS shape and
the header/self-verify conventions this table needs.**

#### RLS shape — TWO real precedents exist, pick on evidence, not by default

**Option A — explicit `auth.role() = 'service_role'` policy** (what RESEARCH recommends,
mirroring `allocator_holdings`'s "belt-and-suspenders" 3-tier pattern's service-role arm).

Read from `supabase/migrations/20260420073003_allocator_holdings.sql`, section "STEP 9: 3-tier
RLS on allocator_holdings":

```sql
-- Explicit service_role FOR ALL policy (belt-and-suspenders; service_role
-- also bypasses RLS by default per ADR-0003, but an explicit policy
-- documents intent and survives any future RLS-hardening that might flip
-- the bypass).
DROP POLICY IF EXISTS allocator_holdings_service_all ON allocator_holdings;
CREATE POLICY allocator_holdings_service_all ON allocator_holdings FOR ALL
  USING (auth.role() = 'service_role')
  WITH CHECK (auth.role() = 'service_role');

-- NOTE: No INSERT/UPDATE/DELETE policy for authenticated — worker is sole
-- producer via service_role. Phase 08 revoke/delete operates via
-- SECURITY DEFINER RPC, not direct DML.
```

⚠️ That file's full RLS block is 3-tier (owner SELECT + admin SELECT + this service-role arm).
CONTEXT/RESEARCH deliberately want ONLY the service-role tier for `strategy_sync_cursors` — do not
copy the owner/admin SELECT policies, only this one block.

**Option B — narrower `USING (false)` deny-all, no `auth.role()` check at all** — a genuine,
already-shipped precedent for an internal-operational, non-user-facing table, MORE PRECISELY
analogous to `strategy_sync_cursors` than `allocator_holdings` (which has real owner-facing
SELECT). Read from `supabase/migrations/20260411144407_compute_jobs_queue.sql`, "STEP 5: RLS —
service-role only":

```sql
-- compute_jobs is operational infrastructure, not user-facing data. Direct
-- reads from the user-scoped supabase client are denied. Admin helpers use
-- the service-role client which bypasses RLS by default. User-scoped reads
-- (e.g. for the wizard SyncPreviewStep showing the user their own jobs)
-- go through get_user_compute_jobs() SECURITY DEFINER which filters by
-- strategy ownership.
ALTER TABLE compute_jobs ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS compute_jobs_deny_all ON compute_jobs;
CREATE POLICY compute_jobs_deny_all ON compute_jobs
  FOR ALL
  USING (false)
  WITH CHECK (false);

COMMENT ON POLICY compute_jobs_deny_all ON compute_jobs IS
  'Service-role-only. Non-service callers get zero rows. User-scoped reads go through get_user_compute_jobs() SECURITY DEFINER. See migration 032.';
```

**Why both are shown rather than picking one:** `USING (false)` works ONLY because service_role
bypasses RLS entirely by default (ADR-0003, named explicitly in the `allocator_holdings` comment
above) — a deny-all policy is invisible to service_role and total for everyone else, which is
exactly `strategy_sync_cursors`'s desired posture (cron writes via service-role client only, no
browser/anon/authenticated consumer exists or is planned). `auth.role() = 'service_role'`
(Option A) is *more explicit* about intent but functionally redundant with the RLS bypass it
documents. `strategy_sync_cursors` has NO owner-select tier at all (unlike `allocator_holdings`),
so `compute_jobs`'s deny-all is the closer structural match; `allocator_holdings`'s service-role
arm is the closer *intent-documentation* precedent. Planner's call — RESEARCH already leans
Option A; this file surfaces Option B as the evidence-based narrower alternative it asked for.

#### Table/index/FK shape — no direct precedent (RESEARCH confirmed: no per-strategy-PK table
exists anywhere in the schema). Nearest FK-cascade convention, read from
`supabase/migrations/20260405061911_initial_schema.sql` (`strategy_analytics` table def):

```sql
-- strategy_analytics (precomputed, cached)
CREATE TABLE strategy_analytics (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  strategy_id UUID NOT NULL UNIQUE REFERENCES strategies ON DELETE CASCADE,
  computed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ...
);
```

This is the closest EXISTING per-strategy-singleton table (surrogate `id` PK + `strategy_id UNIQUE
... ON DELETE CASCADE`, functionally one row per strategy) — same shape RESEARCH's proposal
collapses to `strategy_id UUID PRIMARY KEY REFERENCES strategies(id) ON DELETE CASCADE` (using
`strategy_id` itself as PK instead of a surrogate + UNIQUE). Either form satisfies "one row per
strategy, cascades on delete"; using `strategy_id` as the PK directly (RESEARCH's proposal) is
simpler and matches the read path's `WHERE strategy_id IN (...)` query without needing a separate
unique index — no precedent contradicts it, `strategy_analytics` just predates the
`upsert(..., on_conflict="strategy_id")` convention that makes the simpler shape natural now (see
`job_worker.py` excerpt below, which already upserts INTO `strategy_analytics` on that exact
conflict target).

**`updated_at` convention — no trigger needed for THIS table** (unlike `compute_jobs`, which has a
`compute_jobs_set_updated_at` BEFORE UPDATE trigger because rows mutate via many code paths).
`strategy_sync_cursors` has exactly one writer (the `cron.py` upsert), which can set `updated_at`
explicitly in the payload alongside `last_synced_trade_at` — simpler than installing a trigger for
a single-writer table. Flag this trade-off in the plan rather than silently defaulting to a
trigger.

And `parse_since_ms`'s own contract, read from `analytics-service/services/exchange.py`:

```python
def parse_since_ms(
    last_sync_at: str | None,
    preferred: str | None = None,
) -> int | None:
    """...When `preferred` is provided and non-null, it is used in place of
    `last_sync_at`..."""
    value = preferred if preferred is not None else last_sync_at
    if not value:
        return None
    try:
        dt = datetime.fromisoformat(value.replace("Z", "+00:00"))
        return int(dt.timestamp() * 1000)
    except Exception as exc:
        logger.warning(
            "parse_since_ms: failed to parse %r — caller will refetch from start: %s",
            value, exc,
        )
        return None
```

⚠️ `parse_since_ms` is single-value `preferred`-vs-`last_sync_at`, not multi-strategy-aware. The
cron read path needs a FLOOR across N strategies' markers before calling `parse_since_ms` once (or
calling it once per candidate and taking `min()` of the parsed ints) — `job_worker.py`'s call is
the closest existing COMPOSITION pattern for "prefer a narrower cursor, fall back to the wider
one," not a drop-in for the multi-strategy floor itself. RESEARCH's proposed snippet (in
164.5.1.4-RESEARCH.md, "Read path" section) is the untested design that extends this idiom to N
markers — treat it as a starting point, not verified code.

## Shared Patterns

### Fail-open reads for optional/degradable lookups
**Source:** `analytics-service/routers/cron.py` (recompute-lookup try/except, quoted above)
**Apply to:** the new per-strategy-marker read inside `cron_sync`, before the per-key fan-out. A
Supabase blip fetching markers must degrade to "every strategy's marker is absent" (NULL/fallback
