# Phase 164.5.1.4 SYNCCURSOR — gate calibration record

**What this file is.** One section per anti-vacuity calibration performed in this phase. Each
section records a neuter that was APPLIED to shipped code, the RED that was OBSERVED (not asserted),
the proof that the restore was byte-identical, and the re-run that confirmed GREEN returned.

**Why it exists.** These are DATA-INTEGRITY gates, so anti-vacuity BLOCKS here (CONTEXT Area 5): a
gate that cannot fail is worse than none. The method is not negotiable — neuter, observe RED,
restore, prove byte-identity, record the observed text.

⛔ **Verdicts and observed test output only.** No credential, connection string, project ref, key,
absolute path, username or full identifier appears in this file. The repository is public and
`.planning/` is tracked.

⛔ **No `git checkout --`, `git restore` or `git stash` was used in any harness below.** They restore
to HEAD and silently destroy uncommitted work. Every restore is from a `cp` byte backup taken into
the session scratch directory and re-taken after each edit.

## Section 1 — the two-tick consequence gate (plan 02)

**Gate:** `analytics-service/tests/test_cron_router.py::TestSyncCursorPerStrategyResume`
**Subject under test:** the per-STRATEGY resume path in `analytics-service/routers/cron.py`
**Property pinned:** on a two-strategy key where one `sync_trades` RPC raises, the NEXT tick still
asks the venue for the failed strategy's window — measured at the `since_ms` keyword that reaches
`fetch_all_trades`, not at the marker row write.

### The neuter, and why this target rather than the alternatives

**Applied:** the window expression inside `_sync_single_key` was replaced with its pre-phase form —
the plain parse of the key row's own `last_sync_at`, ignoring the marker mapping entirely. In other
words, the marker READ was removed and the marker WRITE was left fully intact.

| candidate target | rejected because |
|---|---|
| the body of `_strategy_resume_point` | it would neuter the read AND the hold-write together, so a gate that only pinned the row write would also go red — the gate could pass the calibration while still being vacuous |
| the marker upsert (the WRITE) | reddens for the trivial reason that no row exists; proves nothing about whether anything READS the marker |
| **the window expression (the READ)** — chosen | the table still receives correct rows every tick and nothing consumes them. This is the sharpest available neuter: it reproduces exactly the failure mode CONTEXT Area 5 names — "a test that merely asserts the new column is written would pass against a marker nothing reads". If the gate survived this, it would be pinning the row and not the consequence. |

**Proof the neuter APPLIED** (a neuter that does not apply reads as GREEN, and one applied to the
wrong occurrence reds loudly while measuring nothing):

```
cmp <backup> routers/cron.py
  -> "... differ: char 24155, line 494"   cmp_exit=1
```

and the working diff showed exactly the intended three-line-to-one-line replacement at the
`fetch_all_trades` call site, with no other hunk.

⭐ **Read what the failure line says, because it is the whole point.** The test did NOT fail on a
missing marker row — every row-existence assertion in the test passed under the neuter, since the
write was untouched. It failed on the ONE assertion that measures what the venue is actually asked
for: `1789842747126` is the ADVANCED key cursor, `1768435200000` is the millisecond parse of T0, the
resume point the failed strategy was held at. That is the stranding defect reproduced live, with the
marker table being written correctly the entire time.

**The control behaved correctly under the neuter, and that is expected, not a miss.**
`test_full_success_lets_the_fetch_window_advance` stayed GREEN: with no failure holding anything
back, the key cursor and the markers agree, so removing the read cannot change the window. A control
whose job is to prove the pinned window is a CONSEQUENCE of the failure has nothing to detect when
there is no failure. The consequence test is the arm this neuter targets, and it bit.

## Section 2 — the recompute-enqueue conjunct (plan 03)

**Gate:** `analytics-service/tests/test_cron_router.py::TestSyncCursorPerStrategyResume::test_failed_recompute_enqueue_holds_that_strategys_marker`
**Subject under test:** the SECOND conjunct of the per-strategy advance condition in
`analytics-service/routers/cron.py` — `sid not in recompute_enqueue_errors`.
**Property pinned:** a strategy whose trades STORED FINE but whose `derive_broker_dailies` enqueue
RAISED keeps its resume point, so the next tick re-fetches that window and re-attempts the enqueue.

### Why this needed its own section rather than riding on section 1

The advance condition is `(not trades) or (stored > 0 AND sid not in recompute_enqueue_errors)`.
Section 1's gate only ever injects a STORAGE failure, which drives the FIRST conjunct to False all
by itself — so that gate passes unchanged against an implementation carrying the storage conjunct
alone. That narrower implementation is not a strawman: it is the verbatim per-strategy mirror of the
key-level `should_advance_cursor` formula, which is the shape a reader reaches for by default, and
RESEARCH's Pitfall 1 predicts exactly this. The recompute conjunct therefore needed an injection
point of its own on which the storage conjunct is TRUE.

### The neuter

**Applied:** the `and sid not in recompute_enqueue_errors` conjunct was deleted from the advance
condition in `_sync_single_key`, reducing it to that verbatim per-strategy mirror. The storage
conjunct, the marker read, the marker write and their placement were all left intact.

**Proof the neuter APPLIED:**

```
cmp <backup> routers/cron.py
  -> "... differ: char 39834, line 760"   cmp_exit=1
```

and `git diff` showed exactly ONE hunk — a four-line condition collapsed to one line — with no
other change anywhere in the file.

### ⭐ The gates are INDEPENDENT — recorded, because a tidy green board would have hidden the opposite

**Plan 02's two tests STAYED GREEN under this neuter** (the `2 passed` above is exactly them), and
plan 02's neuter left this one untouched in the other direction. That asymmetry is the finding, and
it is structural rather than lucky: plan 02's injection sets `per_strategy_stored["strat-B"] = 0`,
so the FIRST conjunct is already False and deleting the second cannot change its outcome. Had both
gates reddened on the same neuter they would have been covering the same thing and one of them would
have been redundant — which is precisely the claim "criterion 4 has its own coverage" is supposed to
carry, and it would have been false.

### A SECOND observation, because the first RED landed on a row assertion

⚠️ Read where the failure above landed: on `cursors["strat-B"] == self.T0`, a MARKER-ROW assertion,
which short-circuits the test before the fetch-window arm is ever reached. Section 1's discipline is
that this file's gates pin the CONSEQUENCE and not the row, so leaving it there would have recorded
less than it appears to. A second, separately-restored observation was therefore taken with the two
row-level assertions temporarily disabled and the same `cron.py` neuter still applied:

`1768435200000` is the millisecond parse of T0; the larger number is the advanced key cursor. So the
consequence arm bites on this axis too, independently of the row assertions — the gate is not
satisfiable by an implementation that writes the right row and then reads the wrong window.
