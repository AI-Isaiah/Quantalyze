## HIGH

### SFH-H-01: an unavailable BTC read renders as BTC +0.00% / 0.00% DD in every stress window, on every factsheet

- **Location:** `src/lib/factsheet/build-payload.ts:450`
  (`computeStressWindows(dates, stratRet, nullAsZero(btcAl), "BTC", markets)`), rendered by
  `src/app/factsheet/[id]/v2/StressWindowsPanel.tsx:121-126` (`pctSigned(w.benchReturn)`,
  `pct(w.benchMaxDD)`). The browser leverage re-derive (`basis-context.tsx`, via
  `deriveSeriesBundle`) takes the same path.
- **Failure scenario:** `readFactsheetBenchmark` answers `{ unavailable: true }` (PostgREST
  error, probe error, page-cap overflow, or any throw). `alignComparators` gives
  `al.btc = null`, `btcAl = unavailableAlignment(n)` (all null), and `nullAsZero` turns that
  into all zeros. `computeStressWindows` then compounds `1 + 0` over every window. Each
  evaluated window (FTX, SVB, COVID, Luna...) prints **BTC +0.00%** and **BTC DD 0.00%**.
  The same factsheet's comparator block says "BTC prices unavailable". Before this phase
  BTC could never be unavailable, so this is a regression: a failed read now shows up as a
  flat BTC through every crash. The same thing happens more mildly at a dropped close
  inside a window (two intervals entered as 0), which loses a real move.
- **Why this is not the known D-65 limit:** D-65's decision text (CONTEXT) and its
  ROADMAP routing to 169.4 (ROADMAP.md:4196) name only the **api arm's** allocator
  portfolios and event signatures (`SignaturePanels`, `CrossSignaturePanels`,
  `BatchDPanels`). `deriveSeriesBundle` builds stress windows for **every** ingest source,
  csv and composite included. The executor extended D-65 to them as a Rule-2 deviation
  (169.5-01-SUMMARY:203). The CHANGELOG known limits mention that extension, but no ROADMAP
  entry names `computeStressWindows` or `StressWindowsPanel`, so no phase owns the fix. The
  unavailable case also differs from D-65's interior-null case: the whole BTC column is
  made up, not just one day.
- **Hidden errors:** every cause of the unavailable form (PostgREST 5xx, RLS/permission
  error, the 50-page cap, the non-descending page guard, a code bug caught by the broad
  catch in SFH-M-01) comes out as a plausible "BTC was flat" row.
- **Suggested fix (smallest honest one):** when `al.btc === null`, give stress windows a
  bench leg they can mark as absent. For example, pass `btcAl.returns` as
  `Array<number | null>` and have `computeStressWindows` set `benchReturn` / `benchMaxDD`
  to `null` for a window that holds any null bench day (the panel renders "—"). Or skip
  the bench columns when the whole leg is null. If the fix is deferred, add
  `computeStressWindows` / `StressWindowsPanel` to the 169.4 ALLOCTRUTH routing entry (or to
  169.1-07, which already owns stress-window method), so the limit has a named owner.

## MEDIUM

### SFH-M-01: the catch in `readFactsheetBenchmark` covers computation code, and its log drops the message and all context

- **Location:** `src/lib/factsheet/fetch-and-build-payload.ts:745-776` (`try` ... `catch (err)`),
  `:778-786` (`benchmarkReadFailed`).
- **Failure scenario:** the `try` wraps more than the two awaits. It also covers
  `mergeWithFixture`, the trims, and `alignCoveredReturns` (inside `anyCovered`). A
  TypeError or RangeError in that pure code (a regression in `align.ts`, say, or an
  unexpected row shape) is caught, turned into "BTC prices unavailable" on every factsheet,
  and logged as
  `"[factsheet] benchmark_prices read failed; BTC comparator unavailable" { code: "TypeError" }`.
  For any non-PostgREST error only `err.name` is kept, so these all log the same
  `{ code: "Error" }`: the 50-page-cap error, the "not strictly older" page guard and the
  "no data and no error" guard. The line carries no strategy id and no `from` / `to`. A
  code bug is reported as a database outage, the message that would tell the causes apart
  is thrown away, and D-54 already rules out a Sentry event. This log line is the only
  trace.
- **Suggested fix:** narrow the `try` to the two awaits (`readBenchmarkPrices` and the
  probe), and let a throw from the pure merge / align code propagate as a build error, or
  rethrow anything that is not a PostgREST error. Log
  `{ id, from, to, code, message: err instanceof Error ? err.message : String(err) }`.
  Both call sites have the strategy id to pass in.

### SFH-M-02: the two data-driven "unavailable" exits log nothing

- **Location:** `src/lib/factsheet/fetch-and-build-payload.ts:766`
  (`if (prices.length === 0) return BENCHMARK_UNAVAILABLE;`) and `:771`
  (`if (!anyCovered) return BENCHMARK_UNAVAILABLE;`).
- **Failure scenario:** the BTC refresh cron stalls for weeks. Every strategy whose window
  lies entirely after the last stored close now gets the unavailable form. The page shows
  the same "BTC prices unavailable" caption as a read outage, and the factsheet path emits
  no log line. Only the failed-read arm logs. Nobody operating the factsheet can tell
  "the DB is stale", "the DB is empty in this window" and "the read failed" apart, and the
  first two produce no output at all.
- **Suggested fix:** one `console.warn` on both arms, with a stable message and
  `{ id, from, to, firstStored, readCount: read.prices.length, readThrough: read.through }`.
  This only asks for a log. The behaviour on these arms is decided (D-09 / D-54) and stays.

### SFH-M-03: the executor's open question: inferring BTC's calendar from the bounded window pairs a real gap on short windows (measured)

- **Location:** `src/lib/factsheet/align.ts:115-116` (calendar built from the `prices`
  handed in) and `:156` (`paired[k] = count === expected`).
- **Measured** (tsx, against this branch's `alignCoveredReturns`): a weekday strategy
  `[2025-01-02 Thu, 01-03 Fri, 01-06 Mon, 01-07 Tue]` with BTC missing Saturday 2025-01-04:
  - window 2025-01-01..01-07, which holds only that one Saturday: `paired = [true,true,true,true]`
  - same gap, window starting 2024-12-27, which holds another Saturday: `paired = [true,true,false,true]`
- **Failure scenario:** when a weekday has no close anywhere in the bounded window, that
  weekday drops out of the "calendar". `expected` shrinks to match the missing day, so the
  engine's `count == expected` (166.4 WR-01) passes for exactly the interval it exists to
  unpair. A missing BTC day becomes a calendar feature, and the bridged Fri-to-Sun move is
  paired into alpha, beta, IR, the correlations and rolling beta, with no signal. The server
  and the browser re-derive agree, because both use the same bounded prices, so no parity
  test can catch it. Exposure: windows under about two weeks (`MIN_FACTSHEET_SERIES_POINTS`
  is 2), or a systematic gap such as a feed that skipped every Sunday. The four fixture
  comparators are unaffected: `alignComparators` passes their full series.
- **Suggested fix:** make the calendar an explicit input and stop inferring it. For
  example, `alignCoveredReturns(prices, dropped, dates, calendar)`, with all seven weekdays
  for BTC and ETH and Monday to Friday for SPX, GLD and IEF. The read rule and the bound
  stay as they are. Pin it with the short-window case above.

### SFH-M-04: the correlation strip drops the BTC row without a trace when BTC is unavailable

- **Location:** `src/app/factsheet/[id]/v2/DistributionPanels.tsx:347`
  (`view.correlations.filter(r => Number.isFinite(r.rho))`), fed by `pairedCorr`
  (`build-payload.ts`, which returns NaN with fewer than two paired intervals).
- **Failure scenario:** the BTC read fails, or BTC has fewer than two paired intervals (a
  short or stale window). `rho` for BTC is NaN and the "Cross-Asset Correlation" strip
  quietly shows four rows instead of five, with no "—" and no note. The correlation matrix
  in the same view shows "—" for the same cell. The picker's "BTC prices unavailable"
  caption appears only when BTC is the active comparator, so with SPX or none selected
  nothing on the page says why BTC left the strip. The filter predates this phase, but
  before the phase BTC always had a finite rho.
- **Suggested fix:** keep non-finite rows and render them as "—" with no bar, the way the
  matrix does, or add a one-line "BTC: prices unavailable" footnote under the strip.

### SFH-M-05: a partly covered BTC renders truncated figures beside the strategy's full-span figures in the same row (disclosure is not next to the numbers)

- **Location:** `src/lib/factsheet/comparator-block.ts:83` (`pastThrough` nulls only
  MTD/YTD/3M/6M/1Y) and `:116` onward (`cum_ret`, `cagr`, `ann_vol`, `sharpe`, `max_dd`,
  `longest_dd` over the covered dates). Rendered at `MetricsColumn.tsx` Main Metrics / Max
  Drawdown rows. The same shape shows in the EoY current-year cell,
  `MetricsColumn.tsx:690` and `DistributionPanels.tsx:53`.
- **Failure scenario:** BTC is stored through March 31, and the strategy runs through
  September. Main Metrics prints the strategy's Jan-Sep Cumulative Return and CAGR next to
  BTC's Jan-Mar figures under a single "vs BTC" header. The EoY table's current-year BTC
  cell prints the Jan-Mar compound as that year's BTC return, while two panels up the
  **Year-to-date** BTC cell is "—" (`pastThrough`). One page shows the same quantity as a
  number in one panel and as unavailable in another. D-54 decides that a comparator is
  measured only over its covered days, so this finding does not dispute that rule. It
  reports that the only disclosure is the picker caption ("BTC prices through Mar 31"),
  which sits apart from the rows that are affected.
- **Suggested fix (keeps D-54):** make EoY agree with `pastThrough`. A year whose last
  strategy date is after `through` gets a null BTC cell, or a dated one ("to Mar 31"). Add
  the through-date marker to the bench column header of Main Metrics / Max Drawdown when
  `through < lastDate` (for example "BTC to Mar 31").

### SFH-M-06: regime shading paints a bull or bear band past the comparator's last close

- **Location:** `src/app/factsheet/[id]/v2/TimeSeriesChart.tsx:139`
  (`segs.push({ start: curStart, end: cmp.rollingSharpe.length - 1, bull: curBull })`).
- **Failure scenario:** with the regimes toggle on and BTC stored only through a date
  before the strategy's end (stale DB), `rollingSharpe` is null after `through`, as this
  phase intends. The loop skips the trailing nulls, but the final segment is still closed
  at `length - 1`. The chart therefore shades the whole uncovered tail as the last BTC
  regime (for example "bull") for dates that have no BTC price. The comparator line stops
  at `through`, yet the band under it runs on. The same bridging happens across any long
  interior null run. This became user-visible in this phase: before it, forward-filled
  zeros kept the series non-null.
- **Suggested fix:** close a segment at the last non-null index (track `lastNonNull` and
  push `end: lastNonNull`), and treat a null as the end of a segment, not something to skip
  over.

### SFH-M-07: the coverage caption reads the cash comparator and cash dates, not the active basis view

- **Location:** `src/app/factsheet/[id]/v2/ComparatorPicker.tsx:44-50`
  (`payload.comparators[comparator].through`, `payload.dates[payload.dates.length - 1]`).
- **Failure scenario:** D-64(4) Amendment A records that nothing clamps the MTM or
  smoothed series to the cash range, and widens the BTC read for that reason. Take an MTM
  series that ends after the cash series, with BTC `through` equal to the cash last date.
  The cash check `through < lastDate` is false, so no caption shows. Under the MTM basis,
  though, the view's comparator has `pastThrough` true, so its MTD/YTD/3M/6M/1Y read "—" and
  its chart lines stop short. Nothing explains why. The caption was added to explain
  exactly that em-dash.
- **Suggested fix:** compute the caption from `useBasisSeriesView(payload)`, using
  `view.comparators[comparator].through` and `view.dates` at the end, the same view the
  numbers come from.
