## Arm R3: each way it could pass silently, checked

- **Trigger not armed or WHEN mis-scoped.** `enq40001_gate_bi_k` fires only when `NEW.api_key_id = k_r3 AND NEW.kind = 'poll_allocator_positions' AND NEW.status <> 'done'`. If the WHEN excluded the RPC's row, `shots_k` would stay uncalled. The `is_called` read would then give 0 and `v_shots <> 1` fails. If the competitor were never flipped, `flips_k = 0` fails. The re-read would also return the competitor's id, so no 40001 would be raised and the SQLSTATE check fails first.
- **Sequence state leaking from R1/R2.** R3 uses fresh sequences, `shots_k` and `flips_k`, created after R2's assertions.
  - R1's row trigger `enq40001_gate_bi` keys on `NEW.strategy_id = s_r1`, which is NULL for every R3 row, so it never fires.
  - R1's statement trigger `enq40001_gate_ai` does fire on R3's INSERTs. Its UPDATE only touches in-flight competitors with `strategy_id = s_r1`, and R1's competitor is already done, so it changes no rows and cannot advance `flips`. R3 does not read `flips` anyway.
  - In the other direction, R3's triggers are created after R1 and R2 have run.
- **The branch is the real one.** The wrapper's api_key branch (`supabase/migrations/20260515210300_scoring_weight_overrides_high_hardening.sql:322-327`) calls the 10-param `_enqueue_compute_job_internal`. That function's `ELSE` arms are the code the twin mutates: the look-up at `supabase/migrations/20260924230827_fanin_initial_status_10param.sql:338-343` and the re-read at `:398-403`. The arbiter index is `compute_jobs_one_inflight_per_kind_api_key` (`supabase/migrations/20260420073003_allocator_holdings.sql:288-291`), which is on the apply list. Without that index the RPC's INSERT would succeed, step 1 would see `v_state IS NULL`, and R3 would fail loudly.
- **An EXCEPTION handler swallowing the wrong code.** Both R3 blocks only capture `SQLSTATE` and `SQLERRM`. Step 1 requires `40001` and a message starting with `enqueue race lost`, so a 40001 raised anywhere else fails the prefix check. Step 2 fails on any non-NULL state. A 42501, or a 23514 from the kind/target coherence check, is reported by name.
- **A zero-row seed.** The api_keys seed (`:279-281`) is a plain INSERT, so a constraint failure aborts the DO block loudly. The done-winner seed is guarded, as above.
- **A weak equality check under the twin.** After step 1, `k_r3` has two done rows: the flipped competitor and `v_done_k`. Under the twin, the `LIMIT 1` look-up could return the competitor, and then `v_new_id = v_done_k` would not fire. The arm still goes red, because the competitor's status is `done`, which fails `v_status IS DISTINCT FROM 'pending'`, and the in-flight count is 0. Commit 7cbf8f389 records the measured result:
  - first failure: `the api_key re-run returned the finished winner's id`
  - `arms: 3/3/0`
  - `biting: 3`
- **Cleanup hiding a failure.** Every R3 object lives inside the file's transaction and dies with `ROLLBACK`: the sequences, functions, triggers and the api_keys row. No cleanup step runs that could mask an assertion.
