## Decision recorded by this plan

- **PD-O, adapted (marker rule).** When the forced account branch ran and `_reconstruct_outcome_completes_the_key`
  allows the stamp, `_mark_api_key_history_reconstructed` is called for every id `_account_marker_key_ids` returns, in id
  order, inside the existing marker try (its except arm handles any failure). `_account_marker_key_ids(account_keys)`
  returns the sorted ids of the persist-time key re-read (the set the replace was checked against) whose `is_active` is
  True and whose lower-cased stripped exchange is not in `_ACCOUNT_ZERO_CONTRIBUTION_VENUES`. Inactive keys are not
  touched (no reconstruct can run for them: the preflight fails an inactive key permanently). Deribit keys are not
  touched (their history is counted as $0, not rebuilt). An active key whose exchange account was rebuilt through
  another member IS stamped: its account's history is now the rebuilt one.

Facts measured at worktree HEAD 61a13db4c (cite by symbol, never by line):
- The marker ladder stamps only the job's key, through `_mark_api_key_history_reconstructed(supabase, api_key_id)`,
  when `_reconstruct_outcome_completes_the_key` allows it; it RAISES when the UPDATE raises or touches no row, and the
  ladder fails the job transient.
- An unmarked key is what the daily fan-out treats as owed; its unforced reconstruct on a multi-key allocator persists
  first-writer-wins, which fills any day the rebuilt book lacks with that key's value alone.
- `identity_pending_venues` counts venues holding TWO or more eligible, working keys whose account is unknown; one
  unstamped key alone is not pending.
