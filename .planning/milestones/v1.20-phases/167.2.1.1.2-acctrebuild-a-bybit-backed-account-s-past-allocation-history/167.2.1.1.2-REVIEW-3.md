## Warnings

### WR-01 (MEDIUM, operational and diagnostic, introduced by the round-2 WR-03 fix): a permanent MT5 member failure no longer records which account failed or why

**Files:**
- `analytics-service/services/equity_reconstruction.py:4618-4619`: the gather loop returns the member's `DispatchResult` without logging.
- `:4776-4780`: the handler replaces that result with `_forced_refusal_result(allocator_id, api_key_id, venue, "account_key_read_failed")`.
- The `_fail` arms that write no log of their own: `kill_switch` `:4052`, `auth` `:4235`, `account_snapshot` `:4295`, `non_finite` `:4299` and `negative_nav` `:4337`.

**Issue:** Before the fix, a failed MT5 member left a `reconstruct_failed` on its own key. That audit carried the arm's kind and, for `auth` and `account_snapshot`, the scrubbed broker detail. With `emit_audit=False`, that audit is gone. Its replacement on the job's key carries only the generic refusal text. The member's `DispatchResult.error_message` names the arm (it is the static `_MT5_BACKFILL_MESSAGES[key]`), and the handler drops it on the permanent path. For the five arms above, nothing names the member key or the cause.

I measured this with a scratch test, now removed, on a Bybit job key with an MT5 sibling and the kill switch off:

```
AUDIT reconstruct_started  entity=...0001 {'venue': 'bybit', 'forced_rebuild': True, ...}
AUDIT reconstruct_failed   entity=...0001 {'error_kind': 'permanent', 'sanitized_message': 'forced rebuild refused (account_key_read_failed): ...'}
log lines naming the MT5 member key, "mt5" or "kill": []
only WARNING: "... forced rebuild refused allocator=... key=...0001 venue=bybit reason=account_key_read_failed"
```

The one WARNING says `venue=bybit` for a failure that happened on an MT5 account.

Why this matters here:
- Census accounts (1) and (2) hold 5 and 2 MT5 keys. When B'5 records "recorded, not recomputed (account_key_read_failed)" for either, nothing says which MT5 account failed or why.
- `auth` is the one MT5 arm the code calls user-attributable (an investor password changed). It is now indistinguishable from the kill switch, from a non-finite snapshot, and from a ccxt sibling that failed to open.
- The ccxt siblings still get a WARNING that names their key id and exception class (`:4621-4626`), so only the MT5 members lost this trail.

The round-2 fix brief asked for the audit to move to the job's key. It did not say that the identifying detail must move with it. That gap was round 2's.

This is not user-facing and not data integrity: nothing is written and the disposition is correct. It degrades triage of the SC-3 handoff.

**Fix (minimal, one log line, no new abstraction):** in `_crawl_whole_account`, log before handing the member's result on. `error_message` is the static `_MT5_BACKFILL_MESSAGES` text, so it is safe to log.

```python
            if isinstance(outcome, DispatchResult):
                if outcome.outcome == DispatchOutcome.FAILED:
                    logger.warning(
                        "reconstruct_allocator_history account crawl failed "
                        "allocator=%s key=%s venue=%s error_kind=%s reason=%s",
                        allocator_id, key.get("id"), _key_venue(key),
                        outcome.error_kind, outcome.error_message,
                    )
                return outcome
```

Optionally, extend `_fail` so that when `emit_audit` is False and `detail` is set, it logs the already-scrubbed detail with `api_key_id`. This restores the `auth` / `account_snapshot` broker detail that used to sit in the member's audit. Add one assertion to `test_two_failing_mt5_accounts_leave_one_failure_audit_on_the_job_key`: a WARNING record names `API_KEY_ID_1` with `venue=mt5` and the kill-switch message. In that test the job's own key is the failing MT5 member. A mixed bybit + MT5 case would assert `API_KEY_ID_2`.
