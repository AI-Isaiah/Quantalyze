Measured by the planner at HEAD 0da7c814e (cite by symbol, never by line); these answer the orchestrator's questions 3
and 4.

**Q3, anchors compose.**
- Every ccxt exchange account is crawled with require_anchor=True. Its curve therefore either ends at its venue equity
  including open uPnL, or raises ForcedRebuildRefusedError with a plan 05 token.
- The crawls are gathered with return_exceptions=True. In key order, the first refusal is raised as-is, and any other
  non-result becomes account_key_read_failed.
- Only when every exchange account returned rows are they summed.
- Every raise happens inside the handler's crawl try, BEFORE the persist half and the marker writer, so a refusal writes
  nothing.

**Q4, no migration.**
- The sole-key replace is the SECURITY DEFINER RPC `replace_allocator_equity_snapshots(p_allocator_id, p_rows,
  p_depth_months)` (latest body: migration 20260602183000). In one transaction under
  `pg_advisory_xact_lock(hashtext('alloc:' || p_allocator_id))` it DELETEs every row of the allocator and INSERTs the
  payload ON CONFLICT DO NOTHING; there is no sibling guard in SQL.
- It takes any row set, so the summed rows go through the Python wrapper `replace_equity_snapshots` unchanged. No
  function, grant or schema changes; nothing under supabase/ is edited, so the migration-reviewer and rls-policy-auditor
  passes do not apply.
- Residual (accepted, T-167.2.1.1-26): a key added in the one round-trip between the key-set re-read and the RPC is not
  seen. This is the same known limit `_allocator_has_other_api_keys` documents for the sole-key replace.

**Budget.**
- `TIMEOUT_PER_KIND['reconstruct_allocator_history']` is 30 minutes (watchdog 35), and one crawl is bounded by
  `_RECONSTRUCT_CRAWL_TIMEOUT_S` (1500 s). Sequential crawls could therefore pass the handler budget.
- The crawls run concurrently under ONE `_RECONSTRUCT_CRAWL_TIMEOUT_S` bound. The existing TimeoutError arm classifies
  an overrun as transient, exactly as for one key.

**Circuit breaker.**
- `_allocator_key_preflight` runs `_check_circuit_breaker(supabase, job, key_row)`. On a cooldown that calls
  `defer_compute_job` with `job["id"]` and `job.get("claim_token")`.
- Called for a sibling with this job's dict, only `api_key_id` replaced, a sibling's cooldown defers THIS job, which is
  the wanted outcome.
- The handler must then return that DEFERRED unchanged (main_worker marks nothing on DEFERRED).

Planner decisions:

**PD-M (one replace).** The persist half re-reads the key list right before the replace, and refuses
account_keys_changed when the id set differs from the crawled account's. Then it calls `replace_equity_snapshots` with
the summed rows, sets `used_atomic_replace = True`, and sets `sibling_check = SiblingCheckResult(has_siblings=False)`,
so the existing audit-kind ladder applies (`reconstruct_unexpected_noop` on a 0-row insert from a non-empty payload).
Plan 09 adds the stored-days check in front of this replace.

**PD-N (concurrency, deferral, one converter).**
- Sessions are built first, in key order, stopping at the first non-context. A DEFERRED is returned unchanged; any other
  outcome, or a raise, is account_key_read_failed.
- Then the crawls are gathered. `_crawl_account_key` stamps `_stamp_429` on ITS key for a `ccxt.RateLimitExceeded` and
  re-raises the original exception.
- The gather loop of `_crawl_whole_account` is the ONLY converter of non-refusal exceptions: one scrubbed WARNING with the
  allocator, key, venue and exception class, then account_key_read_failed from None.
- Sessions built here are closed in a finally; the job key's own session stays with the handler's finally.

**PD-W (no empty rebuild).** If `_sum_account_rows` returns no row, `_crawl_whole_account` raises account_sum_empty: an
account rebuild never reaches `reconstruct_no_data` and its marker stamp having rebuilt nothing.
