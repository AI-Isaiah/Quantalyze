Recording rules:
- Labels: a1..a5 for the accounts (the users owning an active Bybit key), ordered by their earliest active Bybit key's
  `created_at`; k-labels for keys inside an account if needed.
- Counts, booleans, day counts and 3-significant-figure ratios only. No amount, key id, account number, PROD id or home
  path in tracked text.
- Amount- and id-bearing readings stay in the session scratchpad and are deleted after.

**Part 0' — preconditions.**
1. The phase is merged, main's CI is green, and the migration applied: a read-only catalogue query (after B'0's marker
   query) shows `public.replace_allocator_equity_snapshots_window` exists, `has_function_privilege('service_role', ...,
   'EXECUTE')` is true and the same for `anon` and `authenticated` is false.
2. The analytics worker runs a SHA containing plans 01-08:
   `railway ssh "cd /app && python -c 'import scripts.bybit_upnl_probe as p, services.equity_reconstruction as e; print(e.RECONSTRUCT_FORCE_REBUILD_KEY, p.EXIT_OK, len(e.FORCED_REBUILD_REFUSAL_REASONS), callable(e._crawl_whole_account))'"`
   prints `force_rebuild 0 15 True`.
3. The clock is not within 30 minutes of 00:00 UTC (a job crossing midnight mid-crawl refuses
   `anchor_skipped_okx_terminus`).

**Part B' — rebuild every account (product RPC only; no hand INSERT, UPDATE or DELETE).**
- Reversibility: one-way for stored rows inside each account's window. Settled by UPNLVENUES D-04/D-05 and this phase's
  D-01..D-03 (founder, 2026-10-22), so there is no new checkpoint.
- What plans 01-08 guarantee: a forced job either writes, in one window replace, the per-day sum of every exchange
  account's anchored curve (each counted once, a Deribit one as $0, over the days they all share), keeps every older
  row byte-identical and records the boundary, or writes nothing and fails with a named token.

B'0. Marker query first, in every SQL file run through `supabase db query --linked -f <scratch file>`:
`SELECT shobj_description(oid, 'pg_database') AS which_database FROM pg_database WHERE datname = current_database();`
It must name PRODUCTION. NULL means re-set the marker; never proceed on a guess. No leading `--` comment line.

B'1. Census and prediction (read-only, counts only), per a-label:
- api_keys rows by exchange, split working or not (working: is_active, disconnected_at NULL, sync_status NULL or not in
  revoked / sign_in_failed / error), and stamped (venue_account_id set), marked (account_share_kind set) or neither;
- the TOTAL count of that user's api_keys rows (any status);
- predicted window: 90 if any non-refused exchange account is on okx, else 730; and the count of the user's
  `allocator_equity_snapshots` rows dated before the predicted window start (they are KEPT, D-01, so a boundary row is
  expected iff that count is above 0).
- Predict the outcome by the code's rules: a key on sfox or another venue outside bybit / binance / mt5 / okx / deribit
  -> account_key_venue_unsupported; deribit counts as $0; an exchange account with no working key ->
  account_key_not_working; two or more unstamped, unmarked working keys on one of bybit / binance / okx ->
  account_identity_pending; otherwise "rebuildable unless a venue-read refusal or history_days_unreproduced" (that
  token depends on the replay and cannot be predicted from the database).
Record the prediction per a-label. If every account is predicted to refuse, still run B'2-B'5 (each refusal writes
nothing and is the deployed proof), then ask the founder under [167.2.1.1.2-ACCOUNT-REBUILD-BLOCKERS].

B'2. Before (read-only, scratchpad only): `allocator_equity_snapshots (allocator_id, asof, value_usd,
history_depth_months, reconstructed_at)` and `allocator_equity_derived (allocator_id, kind, computed_at,
md5(payload::text))` for the 5 accounts.

B'3a. In-flight pre-check (read-only), targets selected inside the SQL: `now() AS t0`, and the count of `compute_jobs`
rows of kind `reconstruct_allocator_history` for EVERY api_keys row of the 5 accounts with status in ('pending',
'running', 'done_pending_children', 'failed_retry'). Keep t0 in the scratchpad. If the count is above 0, poll until 0,
then re-run B'3a for a fresh t0.

B'3b. Enqueue, targets selected inside the SQL, printing only counts. Re-read the latest `enqueue_compute_job`
definition first. ONE forced reconstruct per account, on its earliest-created active Bybit key
(`DISTINCT ON (user_id) ... ORDER BY user_id, created_at, id`):
`public.enqueue_compute_job(p_strategy_id := NULL, p_kind := 'reconstruct_allocator_history', p_api_key_id := <that key>, p_metadata := jsonb_build_object('force_rebuild', true))`.
- Never a second forced job for the same account: two would race the same replace.
- A returned id is not proof of a new job. A `serialization_failure` means a lost race: re-run B'3a, then B'3b.
- The flag literal is `force_rebuild`, pinned by `test_force_rebuild_key_spelling_is_the_handoff_literal`.

B'3c. New-job proof (read-only, right after B'3b). Per a-label: does a `reconstruct_allocator_history` row exist for its

B'5. After. Per a-label, read the chosen key's audit trail inside the SQL (`audit_log`, `entity_type = 'api_key'`,

- TERMINAL AUDIT = after it, the first `reconstruct_failed` whose `metadata ->> 'sanitized_message'` starts with
  `forced rebuild refused (` if one exists, else the first of `reconstruct_complete`, `reconstruct_failed`,
  `reconstruct_no_data`, `reconstruct_partial_unsupported` or `reconstruct_unexpected_noop`. (An MT5 member's own

(ii) A `reconstruct_complete` with `reason = already_reconstructed_for_api_key` after t0: STOP and ask the founder (the
