## Warnings

### WR-01: A failed venue RPC quietly puts the SC-2 defect back on every row, as a confident label (MEDIUM, confidence 7)

**File:** `src/lib/queries.ts:1325-1360` (reader), `src/lib/queries.ts:478-492` (merge),
`src/components/strategy/SyncBadge.tsx:249-251` (label fallback)

**Issue:** On any RPC error or throw, `readPublishedTradeVenues` returns an empty map. Every row
then has no `tradeVenues`, so `exchangeLabel` falls back to `supported_exchanges[0]`. That
fallback is exactly what the page showed before this phase.

Scenario: anon EXECUTE on `get_published_trade_venues` is revoked by a later grant sweep. The
ANONKEYID work has just tightened anon grants, so this is a realistic class. After that:
- the row PROD measured as listed Bybit with its key on OKX reads "Bybit" again;
- the tooltip reads "Trades last fetched from the exchange";
- no mismatch cue shows.

The page carries no marker of the failure. The only signal is a Sentry event, and nothing in
the UI tells the reader the label is a fallback.

This also differs from the contract it says it copies. `readPublicVerificationSignals`
degrades in the CAUTIOUS direction: a failed read HIDES the trust badge and never shows a
claim. This reader degrades to a POSITIVE claim (an exchange name) that the phase has already
shown can be wrong. It also diverges from the ANONKEYID contract (`failAnonRead`,
`queries.ts:405-418`), where an anon read error must not render as a normal state. A failed
venue read renders exactly as the normal "this strategy has no key" state.

Fail-soft is defensible for a display-only label. Throwing to the error boundary would
over-correct. But the soft state should be the absence of a venue claim, not the old wrong one.

**Fix:** carry the failure to the badge, and have the badge drop the venue label (and the
"from the exchange" wording) instead of guessing. For example:

```ts
// queries.ts: the reader returns null on failure, distinct from an empty Map
async function readPublishedTradeVenues(ids): Promise<Map<string, string[]> | null> { ... return null; }
// merge: tag every row when venues === null
return shaped.map((row) => venues === null
  ? { ...row, tradeVenuesUnavailable: true }
  : /* existing */);
// SyncBadge: when tradeVenuesUnavailable, exchangeLabel = null (no listed fallback)
```

Then pin it with a test: an RPC error means `span.font-medium` is absent, not "Bybit".

### WR-02: Venues from closed `strategy_keys` windows are treated as current, so a rotated key can raise a false mismatch and a false "fetched from" (MEDIUM, confidence 5)

**File:** `src/lib/queries.ts:1340-1350` (it consumes every row unfiltered).
`src/components/strategy/SyncBadge.tsx:259-267` (mismatch cue) and `:325` (fresh tooltip).
The source is `supabase/migrations/20261019120000_get_published_trade_venues.sql`, whose
second UNION arm joins `strategy_keys` with no `window_end` predicate.

**Issue:** The function returns the exchange of EVERY `strategy_keys` member, including members
whose half-open window has closed (`window_end` is not null and is in the past). The reader and
the badge treat the resulting set as "where trades come from now".

Scenario: a strategy listed as `okx` moves from a Binance key (window closed 2026-06-01) to an
OKX key (open window). The badge then:
- labels the row "Binance, OKX";
- builds `venueOutsideListing` as true because `binance` is not in `[okx]`;
- renders the tooltip "Trades last fetched from Binance, OKX 2h ago. … Listed as OKX; trades
  come from Binance, OKX."

The listing is correct, but the cue says it disagrees with the venue. The tooltip also says
the latest fetch came from a key that has not been fetched since June.

The stale sentence has the same problem ("No trades fetched from Binance, OKX in more than N
days"). For multi-venue strategies, the joined label also cannot say which venue the single
`trades_fetched_at` stamp belongs to.

The analytics service does model these windows (`account_identity.py:274-308` reads
`window_start, window_end, seq`), so closed windows are real data and not hypothetical.

**Fix:** decide which set the label claims. If it claims "current trade source", restrict the
`strategy_keys` arm to open windows in a follow-up migration (PR-A's function, with a rollback
and a RED-UNDER arm for a closed-window member):

```sql
JOIN public.strategy_keys sk ON sk.strategy_id = s.id
 AND (sk.window_end IS NULL OR sk.window_end > current_date)
```

If the historical union is what was intended, the tooltip must not tie it to the latest fetch.
Say "Trades come from …" without "last fetched from …", and limit the mismatch cue to the
active venue. Either way, add a badge test where a listed `okx` with venues `[binance, okx]` (one
retired) produces no false mismatch.
