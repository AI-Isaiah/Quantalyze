# 170.6.1 plan 05 (PR-B) - silent-failure review

Scope: `git diff 8ddd9a8c..fec89198b -- . ':!.planning'` (queries.ts reader, SyncBadge, StrategyTable, StrategyGrid, their tests).
Method: read the full diff and the new tests, read `get_published_trade_venues` (migration 20261019120000), the `failAnonRead` sibling contract, and the two callers (browse and discovery pages; neither caches the result, so a failed read is not pinned for a revalidate window).

What holds up, for the record: the RPC `error` branch logs to the console first, then pages Sentry at `error` with `op: readPublishedTradeVenues`, and the test pins log, tag, level and the error identity. The `catch` clears the map, so a throw part-way through the fold cannot leave half-populated labels. `tradeVenues` never reaches `resolveTradeFetch`, so a bad or empty array cannot move a state. An empty or all-blank venue array falls back to the listed exchange, not to a blank or to "the exchange" as a confident name. The reader uses the request client, no service role.

## Findings

### SFH-1 (MEDIUM, confidence 6) - a malformed 200 response is dropped with no log and no capture
`src/lib/queries.ts` in `readPublishedTradeVenues`: `(Array.isArray(data) ? data : [])`, and the per-row `if (!row.strategy_id || !venue) continue;`.

Scenario: the RPC succeeds (`error` null) but the payload is not the expected row list: a later migration changes the return to `jsonb` or `SETOF` a different shape, PostgREST returns an object, or `exchange` is renamed so every row's `exchange` is undefined. Every row is skipped silently, the map is empty, and Discovery shows the listed (wrong) exchange again on every row, which is exactly the defect this phase fixes. Nothing reaches the console or Sentry, because both alarms hang off `error` or a throw. The fail-soft comment promises "loud", but only two of the three failure classes are.

Test gap: all four cases in `queries.trade-venues.test.ts` use a well-formed array or a populated `error`. No case feeds a non-array `data`, a row with a null or missing `exchange`, or a thrown `createClient`/`rpc`, so the `catch` branch and the silent-drop branches are unexercised. Deleting either would stay green.

Fix: when `data` is non-null and not an array, or when ids were requested and a row fails the shape check, `console.error` and `captureToSentry` once (count dropped rows) and add a test per branch. Zero rows for a non-empty id list is legitimate (CSV and demo strategies), so do not alarm on that alone.

### SFH-2 (MEDIUM, confidence 5) - on RPC failure the fallback is indistinguishable from the bug being fixed, and departs from the sibling anon-read contract
`src/lib/queries.ts` `readPublishedTradeVenues` error branch, plus `getStrategiesByCategory` tail (`tradeVenues && tradeVenues.length > 0 ? {...row, tradeVenues} : row`).

Scenario: anon EXECUTE is revoked, the function is renamed, or the TEST/PROD ledger drifts so the function is absent (the exact class `failAnonRead` was written for: its docblock says an expected failure after the anon grant revoke must be loud and must not read as a normal state). The page renders every row with the listed exchange as a plain confident label and no cue. A reader looking at a "Bybit" row whose key is on OKX sees the same wrong claim the phase set out to remove. Sentry is paged, so operators learn of it, but the viewer does not, and the label cannot be told apart from a genuine "no key" row (D-05 keeps the listed exchange for those too).

This is a recorded choice (T-170.6.1-17, mirrors `readPublicVerificationSignals`), so I rate it on the user-facing consequence only: it is acceptable if the founder accepts a stale-but-wrong label during an outage. If not, either throw via `failAnonRead` (consistent with the other two anonymous readers in this file) or mark the failure on the result (for example a boolean the badge turns into no venue label rather than the listed one). Worth a one-line decision note either way.
