# Phase 167.1.2.2.2 Plan 01: cron_sync_tick Summary

**`public.cron_sync_tick()` ships as a reviewed, gate-pinned migration that posts `{}` to `/api/cron-sync` with the Vault key (timeout 180000 ms) and schedules nothing.**

## What was built

- Migration `supabase/migrations/20261010010000_cron_sync_tick.sql` (`{TS_TICK}` = `20261010010000`): a copy of the re-based `match_engine_cron_tick` house shape. It takes 0 args, is SECURITY DEFINER, and pins `search_path = public, pg_catalog`. The Vault key is read in one count and max scan that refuses a duplicate or blank key. The URL comes from `system_settings` and is re-tested against the allow-list without being echoed. EXECUTE is held by the owner alone (REVOKE ALL from PUBLIC, anon, authenticated and service_role; no GRANT). The `DO $verify$` block is catalogue-only: it never calls the tick, never names `vault.*` or `net.*` as objects, and counts no rows. The needles are concatenated: vault read, settings read, cardinality guard and `'/api/' || 'cron-sync'`. The file contains no pg_cron schedule or unschedule token (`grep -aciE 'cron\.(un)?schedule'` prints 0).
- Gate `supabase/tests/test_cron_sync_tick.sql`: LANE-ONLY over the fixture 34 pg_net stand-in, with a `RED-UNDER-SETUP` list ending in the new migration. Every refusal arm also asserts zero new `net._lane_posts` rows.
- Generated snapshot `supabase/schema/functions/cron_sync_tick.sql` from `npm run schema:functions`.
