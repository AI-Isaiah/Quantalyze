### Summary

The core resume-window change is sound. The high-water reader filters `is_fill = false` on a
NOT NULL column. The day floor is applied to every window. The held-absent rule keeps a
156-day high-water from being turned into a 30-day-clamped marker. The stamp follows
`strategy_advances`, not the key cursor. The selector filter is applied in the query and
before any venue call. The factsheet key went to v16 and carries `trades_fetched_at` plus a
provenance fingerprint taken from the same signature probe. `readTradeFacts` is published-only
with an `exchange`-only embed. All six `SyncBadge` mounts pass `tradeFetchVenue={null}`, so no
mount derives the venue from `supported_exchanges`. Every list projection that feeds a badge
carries `trades_fetched_at` (category ranking, `/strategies`, `getMyStrategies` via `*`, the
portfolio embed, the recommendations status select). The three gate fixes in the last three
commits are honest: the seam pin moves by one with a dated argument, `anchorIndex` closes a
real vacuous-pass path, and the fingerprint helper moves out of the page without touching the
guard.

Four defects are real. One is in the derive path: the combiner fix drops real funding days
inside the venue's reach. Three are in the tick. A Deribit strategy key would be stamped
"fetched" with no fetch. A truncated venue page is treated as a complete window, and this
phase is what makes truncation reachable. The heartbeat calls a tick "ok" when every fetching
key failed transiently.

### HIGH

#### HI-01: The combiner fix drops real funding P&L that is inside the venue's reach (confidence 7)

**File:** `analytics-service/services/broker_dailies.py:278-289` (caller `services/job_worker.py`, the `derive_broker_dailies` ccxt branch)

**Issue:** The fix uses "the first day that has a realized record" as a stand-in for "how far
back the realized fetch reaches", and they are not the same thing. In the only caller, both
streams are fetched over the same window (`fetch_all_trades(..., since_ms=None)` and
`fetch_funding_<venue>(..., None)`). So funding dated before the first realized record is
usually NOT beyond the realized reach. It is just a span where the account held a position and
closed nothing. Those days really happened: the return is funding only, and no zero-fill is
involved. The new filter deletes them from the series.

Plan 07's pin, `test_funding_inside_the_realized_reach_and_funding_only_accounts_are_untouched`,
only covers funding dated after the first realized day, so the case that matters has no test.
The rule is also discontinuous. A funding-only account keeps all its funding days
(`if realized_pnl_records and funding_records`), but one realized close late in its history
erases every funding day before that close.

**Failure scenario:** A perp account opens a long on day 1, pays funding three times a day, and
closes for the first time on day 40. Before this change the derived series covered days 1..N,
with days 1-39 carrying the funding cost. Now it starts on day 40. 39 days of real funding
cost are gone from the track record, and cumulative return and Sharpe are overstated for a
public strategy. The docstring's claim that "the retained days' returns are unchanged" is true
and beside the point: the lost days ARE the error. A separately recorded deposit on day 1 is
still unioned into the index by `_union_flow_days` with pnl 0.0, which brings back the flat
stretch the fix was meant to remove, just from a different input.

**Fix:** Bound by the realized fetch's real reach, not by the first record. One option is to
pass the realized fetcher's effective lower bound into the combiner and drop only funding dated
before it:

```python
def combine_realized_and_funding(realized, funding_rows, account_balance, ...,
                                 realized_reach_start: str | None = None):
    funding_records = funding_rows_to_daily_pnl_records(funding_rows)
    if realized_reach_start is not None:
        funding_records = [r for r in funding_records
                           if (_funding_iso_day(r["timestamp"]) or "") >= realized_reach_start]
```

`job_worker` would pass the venue's realized retention floor (OKX bills reach, Bybit's 365
days, or `None` for Binance, which reaches inception). Add a red-first test with funding
dated before the first realized day but inside the reach: it must stay. The pin that exists
today is green on the buggy behaviour.

### MEDIUM

#### ME-01: A strategy key on a venue with no `fetch_daily_pnl` branch (Deribit) is stamped "Trades fetched" every day with no fetch (confidence 8)

**File:** `analytics-service/routers/cron.py:1350` and `:1616-1622`; `analytics-service/services/exchange.py` `fetch_daily_pnl` (the `okx` / `binance` / `bybit` chain has no `else`, so control falls through to `return daily_pnl` at `:2029`)

**Issue:** `deribit` is in `EXCHANGE_CLASSES`, so a strategy key on it skips the `deferred`
early return and reaches `fetch_all_trades`. That call returns `[]` with no
`daily_pnl_fetch_error` flag. `strategy_advances` is then `(not trades) and not
fetch_degraded`, which is True, so the strategy advances. Its marker moves to now and
`trades_fetched_at` is stamped with the tick instant. On the TS side a non-null stamp counts
"whatever the venue says" (`resolveTradeFetch`), so every viewer, anonymous ones included,
sees a green "Trades fetched 5h ago". No trade was ever read.

D-13's comment names the exact mechanism ("Deribit has no `fetch_daily_pnl` branch, so it would
return nothing and stamp `last_sync_at`") but excludes only allocator-only Deribit keys. A
Deribit key backing an eligible strategy stays in the tick. The PROD census has none today, so
the bug is dormant. It goes live with the first Deribit strategy that a manager publishes, and
the wizard supports Deribit. The `freshness.trade-fetch-venues.test.ts` pin ties the TS venue
list to the Python branches, but nothing ties the STAMP to that list.

**Failure scenario:** A manager publishes a Deribit strategy. From the next 04:30 tick onward,
its factsheet, tear sheet and list badge say "Last trades fetched less than a day ago" forever.
That is the exact false-liveness claim SC-4 and D-07 exist to remove.

**Fix:** Make an unsupported venue fail closed at the source, so it can never read as idle:

```python
# exchange.fetch_daily_pnl, after the bybit branch
        else:
            _record_dq_flag("daily_pnl_fetch_error", True)
            logger.warning("fetch_daily_pnl: no daily-PnL branch for %s", exchange.id)
```

Alternatively, route a key whose exchange is not in the daily-PnL venue set to the `deferred`
return in `_sync_single_key`. Add a test with a Deribit key backing a published strategy that
asserts no stamp and no marker advance.

#### ME-02: A truncated venue page is treated as a complete window, and this phase is what makes truncation reachable (confidence 6)

**File:** `analytics-service/routers/cron.py:1023-1024`; `analytics-service/services/exchange.py:1490` (`daily_pnl_truncated_okx`), `:1836` (`daily_pnl_truncated_bybit`), and the OKX archive loop (`range(100)` with no cap flag at all)

**Issue:** `fetch_degraded` reads only `daily_pnl_fetch_error`. The truncation flags are drained
by `get_and_clear_last_dq_flags()` and then thrown away. They are not consulted and not put in
the response. Before this phase the window was the key cursor, roughly one day, so the page
caps could not be reached. TRADESYNC deliberately makes windows unclamped: 157 days for
ordinal 1, and full reach on a failed high-water read. OKX pages newest-first through `after`,
so hitting the cap truncates the OLDEST days of the window, which are exactly the gap days this
phase exists to recover.

**Failure scenario:** An active OKX account's 157-day window hits `OKX_BILLS_PAGE_CAP` on one
inst type, or the silent 100-page archive limit. The payload still has rows, so
`per_strategy_stored > 0`, the strategy advances, its marker moves to now and the stamp says
"fetched". The un-fetched oldest span is never requested again, because the next tick resumes
from the marker. Step B2's `gap-measure` then names that span as an unrecovered gap, even
though the bills endpoint still serves it. The result is a false public statement and a
permanent hole, from a tick that looks green.

**Fix:** Treat any `daily_pnl_truncated_*` flag as degraded for the advance and the stamp. Add
a cap flag to the OKX archive loop. Put the drained flag names in the per-key result:

```python
fetch_degraded = bool(fetch_dq_flags.get("daily_pnl_fetch_error")) or any(
    k.startswith("daily_pnl_truncated") and v for k, v in fetch_dq_flags.items()
)
```

With the held-absent rule, a truncated first tick then writes no marker and re-drives the same
window, which is the intended behaviour. Add a test where a truncation flag is set and assert
no stamp and no marker.

#### ME-03: The heartbeat records `status: ok` when every fetching key failed transiently or partially (confidence 8)

**File:** `analytics-service/routers/cron.py:1823-1842` (`_CRON_SYNC_HEARTBEAT_METADATA_KEYS`, `_CRON_SYNC_ERROR_COUNTERS`)

**Issue:** The error counters are `failed`, `timed_out` and `revoked`. The metadata set leaves out
`transient`, `partial` and `deferred`. The route's own `_NON_OK_STATUSES` treats
`transient_failure` and `partial` as unhealthy, and its summary comment warns that "every key
hit a transient validation failure" must not read as idle. The heartbeat repeats that exact
misreading, and it is the row the booked staleness alarm is designed to read. Because
`transient` is not even in the metadata, a later alarm cannot recover the count from the row.
No test in `TestCronSyncHeartbeat` covers a transient or partial run.

**Failure scenario:** OKX validation times out (`transient_failure`) for all three OKX keys, and
the Bybit key ends `partial`, every day for a week. Each day `cron_runs` gets
`status = ok, error = NULL` with metadata `{synced: 0, failed: 0, ...}`. Meanwhile
`trades_fetched_at` ages past D-05 and the public badges turn red. The operator signal says
healthy while the user-facing signal says stale.

**Fix:** Add `transient` and `partial` to both tuples, and add a heartbeat test for each one:

```python
_CRON_SYNC_HEARTBEAT_METADATA_KEYS = frozenset({..., "transient", "partial", "deferred"})
_CRON_SYNC_ERROR_COUNTERS = ("failed", "timed_out", "revoked", "transient", "partial")
```

### LOW

#### LO-01: A failed high-water read sends the WHOLE key to full history, and the "idempotent over-fetch" will likely time out every tick (confidence 6)

**File:** `analytics-service/routers/cron.py:501-549` and `_resume_floor_ms` (a `None` resume point anywhere returns `None` for the key)

**Issue:** A read error maps one strategy to `None`. `_resume_floor_ms` then returns `None`
(full history) for every strategy on that key, and for OKX that triggers the full archive
crawl across four inst types. The docstring calls this "bounded by `KEY_SYNC_TIMEOUT`". In
practice it means a 60 s timeout, then no marker and no stamp, then the same again the next
day for as long as the read keeps failing. That is a silent stall, not an over-fetch. The
error does reach the response and makes the heartbeat `error`, which limits the damage.

**Fix:** On a failed read, hold the strategy for this tick (treat it as "do not advance", with
no full-history window), or fall back to a bounded window such as `MAX_MARKER_LOOKBACK_MS`.
Keep the recorded error.

#### LO-02: `TradeFetchLine`'s `useState(() => Date.now())` does not pin "now" across SSR and hydration (confidence 5)

**File:** `src/app/factsheet/[id]/v2/FactsheetView.tsx:1599`

**Issue:** The comment claims the line "cannot flicker between server and client". A
`useState` initializer runs separately on the server render and again during client
hydration. The two clocks differ, and near a whole-day boundary or the 48 h verdict boundary,
the text ("less than a day" / "1 day", "Last trades" / "Stale: last trades") and the class

re-renders that subtree on the client. `FreshnessChip` has the same pattern, so this is not
new, but the comment is wrong.

**Fix:** Correct the comment. If it matters, pass the server's request time down in the payload
props and use it as the single "now".

#### LO-04: An allocator-protected revoked key that backs a strategy makes every heartbeat `error` forever (confidence 5)

**File:** `analytics-service/routers/cron.py` (selector comment beside `skipped_no_strategy`; `_CRON_SYNC_ERROR_COUNTERS`)

**Issue:** The selector comment excludes revoked allocator-only keys because "any alarm on

**Fix:** Count protected-revoked keys apart from `revoked` (or record them as `held`), so a

### MEDIUM

#### R2-ME-01: The Binance futures-income fallback is a degraded fetch that the new degradation reader does not see. It gets stored, advanced and stamped (confidence 8)

**Files:** `analytics-service/routers/cron.py:487-512` (`_fetch_degradation`) and `analytics-service/services/exchange.py:1693-1731` (the Binance `except` arm)

**Issue:** If `fapiPrivate_get_income` raises for any reason (a network blip, a 5xx, a permission or schema change), the Binance branch does three things:

- it records only `daily_pnl_binance_income_fallback`;
- it calls `fetch_my_trades("BTC/USDT", ...)`;
- it returns those spot fills, shaped as daily-P&L rows.

`daily_pnl_fetch_error` is never set. `_fetch_degradation` reads only that flag and the `daily_pnl_truncated_*` prefix, so the tick treats this window as complete. SFH-H1's own docstring defines `reasons` as "the flags that mean the window was not read in full". A BTC-only spot window replacing all futures income is exactly that, and it is missing from the set.

**Failure scenarios.** Both apply to a Binance key backing a published strategy.

- **(a) BTC trades exist.** `sync_trades` runs its payload-window DELETE over `[min, max]` of the fill timestamps. That removes the strategy's real `is_fill = false` daily rows in that span and inserts BTC spot fills in their place (`price` = BTC price, `quantity` = amount). The marker advances, `trades_fetched_at` is stamped, and a recompute is queued on the corrupted rows.
- **(b) No BTC trades.** `trades == []` reads as an idle success, so every marker advances and the strategy is stamped "fetched" with nothing read. That is SFH-H1 itself, reached by a different path.

This is dormant today: the 08e60e854 booking records no Binance strategy key on PROD. It goes live with the first one, and the same booking already names that moment as the trigger for the Binance income work.

**Fix:** Treat the fallback as degraded where the rest of the fix lives, and pin it with a cron test that sets the flag and asserts no store, no marker and no stamp:

```python
# routers/cron.py
_FETCH_DEGRADED_FLAGS = ("daily_pnl_fetch_error", "daily_pnl_binance_income_fallback")
...
reasons.extend(f for f in _FETCH_DEGRADED_FLAGS if flags.get(f))
```

Or fold the item into `[167.1.2.2.2-BINANCE-INCOME-PAGINATION]` with an explicit "cron must not store the fallback" done-criterion. The `job_worker` `sync_trades` path stores the same fallback, but that predates this phase and is out of scope.

### LOW

#### R2-LO-01: A truncation that recurs every tick wedges the whole key, including fresh sibling strategies and the strategy's own recent days. One comment claims the cost is "one tick" (confidence 7)

**Files:** `analytics-service/routers/cron.py:1120-1129` and `TODOS.md` `[167.1.2.2.2-OKX-PERSISTENT-TRUNCATION]`

**Issue:** The window is the earliest resume point across the key's strategies, and a high-water floor is unclamped. If that window truncates on every tick, nothing is stored for ANY strategy on the key, and the window grows by a day each tick. So:

- a sibling strategy with a one-day-old high-water also stops receiving data and goes stale;
- the slow strategy stops receiving even its newest days. Before this fix those newest days still landed, with a silent hole behind them.

The booking describes this only as "reports `error` daily". It does not mention sibling starvation or the series freezing. Its owner, OKXHISTORY, is scoped in the ROADMAP as rebuilding from the quarterly archive, not as chunking the walk.
