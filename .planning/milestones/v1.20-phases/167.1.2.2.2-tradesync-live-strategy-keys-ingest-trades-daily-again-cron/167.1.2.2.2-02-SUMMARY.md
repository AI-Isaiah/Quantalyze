# Phase 167.1.2.2.2 Plan 02: trade-fetch and provenance columns Summary

**`strategy_analytics` gains `trades_fetched_at timestamptz` and `series_provenance jsonb` (object-only CHECK), both nullable with no default or backfill, behind a seven-arm gate whose every arm was observed RED under its own twin, and reviewed CLEAN by all three reviewers.**

## What was built

- Migration `supabase/migrations/20261010000000_strategy_analytics_trade_fetch_provenance.sql`: `BEGIN; SET LOCAL lock_timeout = '3s';`, both `ADD COLUMN IF NOT EXISTS`, the guarded CHECK `strategy_analytics_series_provenance_is_object`, a `COMMENT ON COLUMN` for each, and a catalogue-only `DO $verify$` block. The block reads back presence, exact type, nullability and default-absence (because `ADD COLUMN IF NOT EXISTS` no-ops on a pre-existing column of any type), the CHECK by name, and that `analytics_read`, `analytics_insert_deny` and `analytics_update_deny` are still present. It counts no rows and schedules nothing (`cron.(un)schedule` appears 0 times), so it passes on TEST's empty database. No RLS or grant is written.
- Rollback `supabase/migrations/down/20261010000000-rollback.sql`: a catalogue precondition that refuses when either column is absent, then `DROP CONSTRAINT IF EXISTS`, `DROP COLUMN IF EXISTS` for both, and a catalogue verify. The header says to roll the readers back first and that the ledger row is left in place.
- `src/lib/database.types.ts`: `series_provenance: Json | null` and `trades_fetched_at: string | null` in Row, optional in Insert and Update, in alphabetical position. `npx tsc --noEmit` exits 0.
- Gate `supabase/tests/test_strategy_analytics_trade_fetch_provenance.sql`. The header states that arm 5 measures the lane stand-in (which has no trigger), and that the two real BEFORE UPDATE triggers are exercised by the same arm when `sql-tests` runs the file against the baseline.

## Deviations from Plan

None of these change a plan truth.

**1. [Rule 1 - Bug] `SET LOCAL lock_timeout`, not `SET lock_timeout`**
- **Issue:** inside an explicit BEGIN, a session-level `SET` survives COMMIT and leaks into later migrations of the same `db push` (documented in `20260803150000`). The plan text said `SET lock_timeout = '3s'`.
- **Fix:** `SET LOCAL`, same 3s bound, in the migration and the rollback.
- **Commit:** b50a4a526

**2. [Rule 3 - Blocking] Gate apply list includes the real RLS migration**
- **Issue:** the verify block names three RLS policies the pg-lane stand-in does not carry, so the migration would abort on the lane.
- **Fix:** apply list is fixtures 01, 07, 02, 03, 10, then `20260405061912_rls_policies.sql`, then the new migration (the prefix `test_strategies_private_owner_isolation.sql` uses). 07 precedes 03 so anon holds the default grants arm 6 measures.
- **Commit:** bf28c8b6b

**3. Arm 4 twin is `CHECK (true)`** rather than removing the clause, so the constraint name survives and no verify term needs layering. A mutant that drops the constraint outright was not run.
