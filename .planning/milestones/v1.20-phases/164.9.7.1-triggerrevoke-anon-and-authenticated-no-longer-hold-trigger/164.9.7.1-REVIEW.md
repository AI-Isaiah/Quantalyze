## Summary

The migration is safe to auto-apply on TEST and then on PROD. I found no BLOCKER. Here is what I checked and what the checks rest on:

- **PG16 parse safety.** In the PG16 grammar `MAINTAIN` is a bare `ColId` in the privilege list. So the static `REVOKE MAINTAIN` and `ALTER DEFAULT PRIVILEGES ... REVOKE MAINTAIN` inside `IF v_maint` pass PL/pgSQL's compile-time raw parse. `unrecognized privilege type` is raised only at execution, and that branch never runs on 16. `has_table_privilege(..., 'MAINTAIN')` is reached only through `v_verbs`, which holds `MAINTAIN` only on 17. The full mutation run applied the file on the PG16 pg-lane 61 times (baseline legs, `No defects`), which confirms this in practice.
- **PG17 correctness.** The migration is the same shape as 20261009130000, which already applied on TEST and PROD. `ON ALL TABLES` covers relkinds r, p, v, m and f, which matches the sweep's set. The has_table_privilege sweep catches a grantor mismatch, a PUBLIC grant and an inherited grant, and it raises inside the same DO block, so a failure aborts atomically and leaves nothing half-applied.
- **TEST apply risk.** The pre-merge TEST read (PROD-READINGS) shows 0 relations not owned by postgres, 0 TRIGGER/MAINTAIN ACL entries with a grantor other than postgres, and 0 PUBLIC grantee entries. None of the self-check's raise sites is expected to fire on TEST. The migration reads no data, so the empty-TEST escape cannot apply.
- **Rollback fidelity.** I rebuilt each of the four per-verb, per-role lists independently from `supabase/schema/baseline.sql` and diffed them against the rollback. All four match exactly: TRIGGER 56 / 59, MAINTAIN 57 / 61. `cron_runs` and `system_settings` are correctly left out of the TRIGGER lists. The count check is a strict set-equality proof, because every listed GRANT must succeed and any extra holder pushes the count over.
- **Gate twins.** Each of the five VERB twins is a `sql` step on TRIGGER. The recorded full run shows `biting 11/11` for this file. The MAINTAIN half has no twin by founder decision D-07, and that decision has compensating controls (the self-check, the manual PG17 RED and the vitest pin).

The two findings below are both in the gate's positive controls. Neither affects the migration or the PROD apply.

## Warnings

### WR-01: The gate's positive controls require client-role DML on `cron_runs`, a privilege that is itself leftover over-grant, so a future least-privilege fix would turn the gate red with a misleading message

**File:** `supabase/tests/test_truncate_revoke_anon_authenticated.sql:179-183` (VERB 1-SETUP) and `:311-323` (VERB 4)
**Issue:** VERB 1-SETUP fails unless `authenticated` holds DELETE on `public.cron_runs`. VERB 4 fails unless `authenticated` holds INSERT, UPDATE and DELETE on it. VERB 4's message says *"every RLS-scoped write the client roles make is a verb this check names"*. But `cron_runs` has no client write path:
- its policies are `cron_runs_admin_read` (SELECT only) and `cron_runs_service_role` (`auth.role() = 'service_role'`), at baseline.sql:15171-15177;
- `GRANT SELECT,INSERT,DELETE,MAINTAIN,UPDATE ... TO "anon"|"authenticated"` (baseline.sql:16969-16970) is the platform's default-ACL residue, the same class of over-grant this phase exists to remove.

So the gate now treats keeping that residue as an invariant. A later hardening migration that correctly revokes INSERT, UPDATE or DELETE on `cron_runs` from the client roles would turn `sql-tests` red. The failure would read as "the revoke went too far", or for VERB 1-SETUP as "fixture 07 is missing from the apply list". Either message steers the next engineer toward re-granting a privilege that should not exist. TODOS already keeps exactly that kind of follow-up open: REFERENCES and DELETE on `api_keys`, and the 2026-10-30 platform withdrawal. TRUNC4-DEFAULT-WITHDRAWAL-01 records the same trap for TRUNC 4, but it does not cover VERB 4 or VERB 1-SETUP.

**Fix:** Point the "the revoke removed exactly two verbs" control at a privilege the client roles legitimately need, and point the anti-vacuity setup at something the migration does not own. For example:
```sql
-- VERB 1-SETUP: anti-vacuity without depending on client DML residue
IF NOT (SELECT bool_and(has_table_privilege('service_role', 'public.cron_runs'::regclass, vb.verb))
          FROM unnest(v_verbs) AS vb(verb))
   OR NOT has_table_privilege('authenticated', 'public.cron_runs'::regclass, 'SELECT') THEN ...
-- VERB 4: assert the verbs on a table where an RLS policy actually grants the client role writes
-- (e.g. a table with an authenticated INSERT/UPDATE policy), keeping the twin a single REVOKE on it.
```
If you keep `cron_runs`, at least book VERB 4 and VERB 1-SETUP next to TRUNC4-DEFAULT-WITHDRAWAL-01, and change both messages to say that a deliberate revoke of client DML on `cron_runs` must re-point the control and must not re-grant.

### WR-02: VERB 5 accepts any 42501, so on the local-stack lane it can pass for a reason other than the missing TRIGGER privilege

**File:** `supabase/tests/test_truncate_revoke_anon_authenticated.sql:329-354`
**Issue:** VERB 5 is meant to be the behavioural proof that the migration closed `CREATE TRIGGER` for `authenticated`. Its header says this proof is non-vacuous only on the local-stack lane, because on the pg-lane `profiles` never held TRIGGER. The assertion checks SQLSTATE `42501` and nothing else. `CREATE TRIGGER` also returns 42501 for at least two other causes:
- no EXECUTE on `suppress_redundant_updates_trigger()`;
- no USAGE on the schema.

TRUNC 6 matches the message (`'%permission denied for table cron_runs%'`) precisely to rule these out. VERB 5 drops that check, citing `lc_messages`. The arm's twin runs only on the PG16 pg-lane, where it proves the function and schema path is open there. It proves nothing about the PG17 local-stack image, where the real proof has to happen, and the plan 02 V4 round trip never reached VERB 5 (VERB 1 failed first). This is not live today: Supabase grants the client roles USAGE on public, and pg_catalog functions are EXECUTE-to-PUBLIC. But the one lane that matters is the one place the arm cannot tell the difference.

**Fix:** Add a locale-independent check that the refusal names the target table. A translated message still carries the relation name, and an EXECUTE refusal names the function instead:
```sql
-- in the handler (record only, lint R1):
v_msg := SQLERRM;
-- after RESET ROLE:
IF v_state IS DISTINCT FROM 'denied' OR v_sqlstate IS DISTINCT FROM '42501'
   OR v_msg NOT LIKE '%profiles%' OR v_trg_cnt <> 0 THEN
```
Also clear `v_msg := NULL` before the block, as TRUNC 6 does.
