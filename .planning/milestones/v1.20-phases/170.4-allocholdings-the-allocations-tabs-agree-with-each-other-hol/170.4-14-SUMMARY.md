# Phase 170.4 Plan 14: The over-time series count one exchange account once per day

NetExposureChart and AllocationOverTime now count two keys that read one exchange account once per (day, holding_type) by plan 11's `oneKeyPerAccountDay`, applied per `asof`; keys on different accounts still sum, every day of history keeps its point, and a failed identity read rejects the series. Closes T-170.4-33, the item plan 09 left open.

## What changed

- `src/lib/latest-holdings-per-key.ts`: `KEY_IDENTITY_COLUMNS` and `KeyIdentityRow` exported; the inline `accountIdentityTokens` block in `fetchLatestHoldingsPerKey` extracted, with the same field coercions, the same five null placeholders and the same `key:<id>` fallback, into the exported pure `keyAccountOf(keys)`. The reader now calls it.
- `src/lib/portfolio-exposure.ts` `fetchHoldings`: reads the owner's `api_keys` (identity columns, `.eq("user_id", userId)`, `.limit(HOLDINGS_ROW_CAP)`, user client) before paging; throws the PostgREST error, and throws a named Error at the cap. Selects the eight columns (six plus `api_key_id, updated_at`). After all pages, groups by `asof`, calls `oneKeyPerAccountDay(dayRows, accountOf)` once per group and concatenates in ascending `asof` order. `HoldingsUpdatedAtError` propagates. Both series' sum, gap and empty logic is untouched (D-03). Module docblock rewritten where false (one row per key since plan 09; eight columns plus the identity read; a D-11 paragraph); the current-snapshot paragraph was not touched.
- `src/lib/portfolio-exposure.test.ts`: `@/lib/supabase/server` mock is table-aware (`allocator_holdings`, `api_keys` via a new hoisted `keysResolver`, any other table throws); `HoldingRow`/`row()` carry `api_key_id` (K1) and `updated_at`; a D-11 describe with hand-typed figures; the T-98-08 pin tightened.
