## Critical Issues

### CR-01: `match.py` groups keys by the marker alone, so the scorer counts one exchange account twice (D-08/D-10 runtime divergence)

**File:** `analytics-service/routers/match.py:669-701` (with `analytics-service/services/allocator_equity_derive.py:280-321`)
**Confidence:** 7/10

**Issue:** The scorer builds its accounts with `account_groups(key_rows)`. That function unions keys ONLY through an `account_share_kind` marker. Every TypeScript reader in this PR and the commit RPC use a different identity:
- the dashboard (`fetchLatestHoldingsPerKey` → `accountIdentityTokens`, `src/lib/departed-history.ts:120-169`);
- the commit AUM (the same reader);
- `commit_scenario_batch`'s `contributing` CTE (`account_edges`, migration 20260929120000).

Those three also treat two keys with the same non-blank `(lower(exchange), venue_account_id)` as one account, marker or not. Python already has that identity as `account_identity_tokens` (`analytics-service/services/job_worker.py:11857`), and `match.py` does not use it.

**How the two keys arise.** `api_keys_user_exchange_venue_account_uniq` only covers live keys (`WHERE venue_account_id IS NOT NULL AND disconnected_at IS NULL`, migration 20260812083206). So when an owner disconnects key A and connects a new key B for the same login, B takes the freed slot. B gets the same `venue_account_id` and no marker. A's rows stay, because a soft disconnect keeps the `api_keys` row.

**Scenario.** A last polled on day D1 and B polls on D2:
- TypeScript (Holdings, Exposure, commit AUM) and the commit RPC see one account whose newest day is D2, so only B's rows count.
- `match.py` puts A and B in different groups. It counts A's D1 rows AND B's D2 rows, so `portfolio_aum` and `portfolio_weights` include the account twice. For a symbol both keys hold, `holdings_map` sums the two `value_usd` values.

**Before this PR**, the `(venue, symbol, holding_type)` collapse kept one row per symbol, so this double count is a regression introduced here.

**Why the tests miss it.** Every case in `tests/test_match_portfolio_aum_per_key.py:139-206` links its keys with a `duplicate` marker. No test has a shared `venue_account_id` without a marker. `one_key_per_account_day_cases.json` replays only the within-account tie-break, never the grouping.

**Fix:** Group with the same identity the TypeScript side uses. Move `account_identity_tokens` into `services/allocator_equity_derive.py`, since `job_worker` already imports from that module, so the move adds no import cycle. Then use it in `match.py`:
```python
from services.allocator_equity_derive import account_identity_tokens, one_key_per_account_day

tokens = account_identity_tokens(key_rows)          # same rule as accountIdentityTokens
group_of = {k: t for k, t in tokens.items() if t is not None}

def _account(holding: Row) -> str:
    key_id = str(holding["api_key_id"])
    return group_of.get(key_id, f"key:{key_id}")
```
Add a red-first case to `test_match_portfolio_aum_per_key.py`: a disconnected key and a live key with the same `(exchange, venue_account_id)`, no marker, and different newest days. The expected AUM is the live key's rows only. Also add the grouping input to the shared JSON case table, so both runtimes replay the account identity and not just the tie-break.

## Warnings

### WR-01: under today's index, a later spot-only poll erases another key's derivative rows from persisted figures

**Files:**
- `src/lib/holdings-account-day.ts:113-158`
- `analytics-service/services/allocator_equity_derive.py:387-417`
- applied at `analytics-service/services/equity_reconstruction.py:2059-2064`
- applied at `src/app/api/allocator/scenario/commit/route.ts:862-870`

**Confidence:** 6/10

**Issue:** The tie-break picks ONE key per account-day for ALL of that day's rows. It compares only `updated_at`. Today's index has no `api_key_id` (the migration that adds it is PR 2), so on one day an account's rows can be split across keys:
- key X's complete poll at t1 writes spot and derivative rows;
- key Y's later poll at t2 is partial (`complete_with_warnings`, positions unread), writes only the spot rows, and takes them over.

Y wins, so X's derivative rows stop counting. Before this PR they counted, because the old readers summed every row of the day, and the rows were different symbols, so nothing was double counted. Docblock case (b) records this loss and calls it disclosed. The disclosure is `partialPositionReads`, which only the dashboard shows. The paths that PERSIST a figure get none:
- The daily equity refresh (`_fetch_latest_holdings_per_eligible_key`) writes `allocator_equity_snapshots` without the derivative uPnL, and nothing records that it was dropped.
- The commit route runs with `auditEvidence: false`, so `partialReads` is always `[]`. It persists an understated `size_at_decision_usd` with `_size_source: "server_aum"`.
- The scorer's `portfolio_aum` drops the positions with no log.

If a duplicate key reads the account with narrower permissions and polls after its sibling, this happens every day. The rule is a planner tie-break ("Claude's Discretion", plan-checker round 5), not a founder decision.

**Fix:** Pick the winner per `(account, holding_type)`, not per account:
```ts
// key the instants map by `${account}\u0000${r.holding_type}`, and filter on the same pair
```
Then a spot-only later poll can win the spot class without erasing the derivative class another key of the same account read on that day. No account is counted twice: each class still comes from exactly one key. Make the same change in `one_key_per_account_day`. Add a red-first case (b) to `one_key_per_account_day_cases.json` that expects the derivative rows to survive. If the founder prefers to keep the per-account rule, the persisted paths must at least say so. The refresh should log a warning and the commit should set a `_size_source` sentinel whenever a winner's day omits a holding type another key of that account wrote on that day.

### WR-02: the client fingerprint row set does not equal the RPC's `contributing` set when a key is native-unpriced, and nothing books the fix

**Files:**
- `src/lib/queries.ts:4587-4600` (`holdingsFingerprintRows`)
- `src/lib/latest-holdings-per-key.ts:380-396`
- `supabase/migrations/20260929120000_commit_scenario_batch_fingerprint_reader_set.sql:376-395`

**Confidence:** 8/10

**Issue:** The brief and the docblocks say `holdingsFingerprintRows` IS the RPC's `contributing` row set. They differ on one arm. The TypeScript reader treats a newer `native_unpriced:<key>` marker as a reading day with no rows. That drops the key, and it can also move the account's newest day so that sibling keys drop too. The CTE has no native-unpriced arm (no later migration redefines `commit_scenario_batch`), so it keeps those rows. For an allocator with a BTC-denominated MT5 account on an unpriced day, the client fingerprint lacks tokens that the server recompute carries. Every book-mode commit is then refused as `portfolio_fingerprint_stale` until the next priced poll, and a refresh does not clear it. `170.4-07-SUMMARY.md:96` acknowledges this. It appears in no `TODOS.md` entry (no `portfolio_fingerprint_stale` hit there), and none of the PR 2 plans (09, 10, 13) mention it. A planned PR 2 migration is the obvious carrier, but none of them is scheduled to fix this.

**Fix:** Add the native-unpriced arm to the `contributing` CTE in the PR 2 migration: a `key_day` of `(marker_day, has_rows=false)` when the service-written marker's day is after `latest_day`. Pin it with a new case in `test_commit_scenario_batch_fingerprint_precondition.sql`. Or book it as a dated `TODOS.md` entry with an owner, so the docblock's "equals the contributing CTE" claim has a recorded exception.

### WR-03: the scorer's holdings read is unbounded and unchecked, and the new account-newest-day rule depends on it being complete

**File:** `analytics-service/routers/match.py:605-613`
**Confidence:** 5/10

**Issue:** The scorer reads `allocator_holdings` with no `.limit` and no cap check. It covers every day the allocator has ever held, ordered by `asof DESC`. PostgREST's `max_rows` is 1000 on this project (`src/lib/latest-holdings-per-key.ts:55-63`), and a capped read returns a partial list with no error. Under the new rule, each account's newest day is taken from whatever rows came back. Suppose an allocator has several keys and a long history. Then any account whose last poll is older than the newest ~1000 rows either disappears from `portfolio_aum` or is counted from a partial set of rows on its newest day. The TypeScript twin avoids this by reading per key with `HOLDINGS_ROW_CAP` and failing loud. The unbounded read predates this PR, but D-08 now depends on it being complete.

**Fix:** Read the same way as `fetchLatestHoldingsPerKey`: per key, the latest `asof` with `.limit(1)`, then that day's rows. Or at minimum add a `.limit(1000)` and raise when `len(rows) >= 1000`, so a truncated book fails the request instead of scoring a partial AUM.

### The brief's specific checks

- **TS and Python stay identical.** Both use the same slot, the same maximum instant per key within a type, and the same tie-break on the smaller lowercase id. The TS slot is `account\u0000type`. The Python function receives one account's rows, so its slot is `(type, key)`, which is the same partition.
