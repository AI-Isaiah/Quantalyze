  <action>
Add a module-scope guard to `src/test-setup.ts`, placed immediately after the import block and BEFORE
any other module-scope statement — before the global installation, before the module mock, before the
share-token fixture assignment and before the inherited-environment capture. The reason is the whole
point of the guard: nothing else in the bootstrap should get to run on an environment that was
inherited by accident.

Import `HAS_LIVE_DB` from the live-DB helper module. ⭐ Import the exported value; do NOT recompute
the boolean from `process.env` in the bootstrap. One definition, referenced — the same rule this
phase applies to the redaction expressions, applied to the credential predicate.

The condition is exactly two terms: the credentials are present, AND the sentinel environment
variable is not set to its declared value. ⛔ There is NO `CI` escape hatch, and its absence is a
measured decision, not an oversight — no CI job that runs vitest carries both variables, so an escape
hatch would be inert today and an unearned exemption tomorrow. Record that reasoning in the comment,
with the date and the way to regenerate it.

Name the sentinel `VITEST_LIVE_DB_INTENDED` and require the literal value `1`. A dotenv file could
plausibly define two commonly-present Supabase variables by accident; it will not also define this
one. This is intent, not provenance — and the distinction matters, because a repo-side guard
CANNOT distinguish "auto-loaded from a dotenv file" from "genuinely exported by the operator":
`process.env` carries no provenance metadata. Say so in the comment, so the next reader does not try
to build provenance detection.

Write the remedy message as a named constant and make it actionable: it must name the two variables
BY NAME, state that both were found set, state that this turns skipped live-DB suites into real
writes against a SHARED test database other people's CI uses, and give both exits — set the sentinel
if this was intended, or unset the two variables if they were inherited from a dotenv file a wrapper
auto-loaded. ⛔ THE MESSAGE MUST NEVER PRINT EITHER VALUE, not truncated, not hashed, not a length.
Key names only. A guard that prints a credential to prove a credential leaked is this phase's own
worst failure mode.

Throw rather than warn. The locked decision says fail loud, and a warning in a suite of hundreds of
files is not loud. A setup-file throw fails every test file that loads it, which is unmissable.

Add an explanatory comment block in the file's existing voice recording: what the leak was, why the
fix lives here rather than in the wrapper (the wrapper has no repo-local copy and its own upgrade
overwrites it — the same non-durability class this repo already records for its global workflow
files), and why the skip gates are deliberately untouched.
