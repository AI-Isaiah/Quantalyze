### Known limit recorded, not a defect

- **jsdom accessible name:** `dom-accessibility-api` trims each child's text, so jsdom computes `contact form(opens in a new tab)` where a browser concatenates `contact form (opens in a new tab)`. Tests assert `textContent` exactly and the name by a space-tolerant regex. A real-browser axe/Playwright reading of the name has NOT been taken here.
- **No e2e run:** `e2e/` specs were not executed in this worktree.
- **Fixture ids:** unit fixtures use ids such as `strat-1` (7 characters) which `/contact`'s `CONTACT_ID_RE` (8 to 64) would drop; the href builder does not validate, so this plan's tests are unaffected. The real-id case is the first Issue below.

## Issues Encountered

- **Possible id-fence mismatch (not changed here, belongs to plan 03/05):** the correlation id the wizard mints for a page load is shaped `wizard:<uuid>` (`src/lib/wizard/wizard-correlation.ts:87` returns `` `wizard:${crypto.randomUUID()}` ``; seen in the encoded href `ref=wizard%3A1035616c-...` in the rehydration test). `parseContactPrefill` drops any value outside `[A-Za-z0-9_-]{8,64}`, so a `wizard:`-prefixed `ref` would be dropped silently on the form and only the `draft=` part would prefill. Server-minted envelope ids (`cid-...`, UUIDs) pass. Measured: `/^[A-Za-z0-9_-]{8,64}$/.test("wizard:<uuid>")` is `false`. Recommend allowing `:` in `CONTACT_ID_RE` (and the matching `wizard_session_id` charset note) or minting wizard ids without a colon. Not fixed here: `src/lib/contact.ts` is plan 03's file and is outside this plan's `files_modified`.
- A pre-existing `gc.log` warning on the shared worktree git dir appeared on commit; harmless, not touched.
