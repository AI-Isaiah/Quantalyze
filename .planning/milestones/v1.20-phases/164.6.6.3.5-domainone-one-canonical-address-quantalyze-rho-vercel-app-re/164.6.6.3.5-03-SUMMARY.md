**1. [Rule 3 - Blocking] The gate carries four arms, not three.**
- **Found during:** Task 3 (`mutation-annotation-parser.test.ts`, "every SECTION an annotated file raises for also carries a twin")
- **Issue:** the behavioural section 4 raises `TEST FAILED (4a..4e)` and had no twin; the plan's acceptance line `grep -c 'RED-UNDER-M' ... prints 3` conflicts with that repo invariant.
- **Fix:** added arm 4b (a competing TOTAL unique index under another name, which sections 1-3 cannot see because they read only the named index). The literal acceptance count is therefore 4, and `ARMS_FLOOR` is 578 rather than 577.
- **Commit:** `e356fa33e`

**2. [Rule 3 - Blocking] Census files outside this plan's `files_modified` moved.** The new gate file moves the corpus counts these pin, so they were updated in Task 3 (each edit carries a dated CURRENCY comment): `src/__tests__/mutation-runner-floors.test.ts` (GREEN_LOG/SUBSET_LOG fixtures and ~30 derived literals, new per-file row, lane-time line), `src/__tests__/mutation-annotation-parser.test.ts` (armsSeen 574 to 578, filesTotal 85 to 86 twice, filesAnnotated 58 to 59, by-name list), `src/__tests__/lint-sql-gates.test.ts` (scanned 85 to 86), `src/__tests__/gate-family-meta.test.ts` (the two registered threshold keys `FILES_FLOOR=59`, `ARMS_FLOOR=578`, each with its measurement recorded). `stepsSeen` (668) did not move: the four twins are single `sql` steps.

**3. [Rule 2 - Missing critical] 200-character reference cap in `parseContactPrefill`.** Three valid 64-character ids compose to 209 characters, which `for_quants_leads_reference_len_check` would reject as a 500 at the route. A later part that would overflow is dropped whole (a clipped id points at nothing); the individual `ref`/`draft`/`strategy` fields still report what the page read. Pinned by a test. This also adds the exported `CONTACT_REFERENCE_MAX`.

**4. [Decision] `contactHref` uses `encodeURIComponent`, not `URLSearchParams`.** The plan's action text names `URLSearchParams`, the UI-SPEC contract names `encodeURIComponent`. For the fenced id charset they are byte-identical; they differ only for a space (`%20` vs `+`). The UI-SPEC wording was taken as the binding one. If plan 04+ prefers `+`, it is a one-line change with one test.
