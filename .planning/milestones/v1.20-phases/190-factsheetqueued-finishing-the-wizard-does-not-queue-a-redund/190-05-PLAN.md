<objective>
Make every inner gate of the factsheet build follow plan 03's single admission decision, and move the public cache key so no pre-deploy withheld entry outlives the deploy.

Purpose: with only plan 03, an admitted single-key row builds its headline by recomputing the series in TypeScript (the stored-headline gate still refuses a non-terminal row), and an options strategy's MTM and smoothed toggles render disabled with copy that says the basis is unavailable, which is false during a re-run. RESEARCH Pattern 2 says to pass the resolve stage's one decision down and to leave no gate on the raw status. `unstable_cache` stores unconditionally, so a v19 entry keyed on a computing status can hold the withheld null for up to an hour after the deploy.

Output: one exported readability predicate in headline-basis.ts, an option threaded through readSingleKeyBasisOpts, parity tests on the build and the probe, and cache key v20 with every pin moved.

Design note (Pitfall 3, RESEARCH A1, checked in plan 01; revised at plan-check 2026-11-03). In the single-key derive-to-success window, plan 09's snapshot gives plan 03 the last success's flags, so the cash headline, the curve and every note stay one generation. The derive hop also writes `metrics_json_by_basis`, the MTM, smoothed and cash_settlement series rows, and the live `mtm_gated_reason`, all from one derive. This plan therefore pairs the MTM and smoothed gates with that live generation, so neither basis mixes runs. Two narrow windows remain, recorded as known limits in the SUMMARY. (1) The day basis follows the new derive's frozen cash conventions. It differs from the last success's only when the day-basis setting changed in that run. (2) The composite stitch rewrites `csv_daily_returns` and its basis series seconds before its atomic headline write, the documented D5 HONEST BOUNDARY in `analytics-service/services/job_worker.py`. This phase widens the visibility of that window from complete_with_warnings rows to every re-run.

D-04 (founder 2026-11-03, locked) needs no new code here. Plan 03 withholds a terminal-success row whose derive prestamp left no bound snapshot in the shared resolve stage, before `readSingleKeyBasisOpts` runs. So `basisDqf`, which uses `effectiveDataQualityFlags`, only ever sees a row whose effective flags are proven to be a success's. Task 1 pins that the probe answers the same as the build for that row.
</objective>
