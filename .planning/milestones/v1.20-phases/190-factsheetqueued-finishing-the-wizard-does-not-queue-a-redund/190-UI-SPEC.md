## Interaction and Placement Contract

### The line

| Property | Value |
|----------|-------|
| Element | `<p>` |
| Classes | `mt-1 text-caption text-text-muted` (byte-identical to `SeriesRecencyLine`, `FactsheetView.tsx:1628`) |
| Copy | `Updating with the latest data. These figures are from the last completed computation.` (see Copywriting Contract) |
| `data-testid` | `factsheet-analytics-updating` |
| ARIA | none: no `role`, no `aria-live`, no `aria-label` (see Accessibility) |
| Print | **No** print-hiding class. It prints like its siblings (see Surfaces) |
| Render condition | `payload.analyticsUpdating === true`, and nothing else. Never derived from lane, viewer, cookies or client state |
| Data source | `payload.analyticsUpdating`, read from the same local `payload` that `FactsheetHeader` already resolves to the NATIVE payload (`unitView?.nativePayload ?? payloadProp`, D-19 rule 4). It is row state, so it is identical in the USD view |

### Position (exact DOM order inside the header's right-column wrapper `<div>`)

```
<div>                                   ← existing wrapper, FactsheetView.tsx:1304
  <FreshnessChip … />                   ← unchanged
  <SeriesRecencyLine … />               ← unchanged; still chip.nextElementSibling
  <p data-testid="factsheet-analytics-updating">…</p>   ← NEW, only when analyticsUpdating
  <TradeFetchLine … />                  ← unchanged
  <UnrecoveredGapLines … />             ← unchanged
  <ReconstructedRangeLines … />         ← unchanged
</div>
```

**This deliberately differs from RESEARCH Pattern 3** ("before `SeriesRecencyLine`"). The line goes
**after** `SeriesRecencyLine` for two reasons:
1. `FactsheetView.recency-line.test.tsx` F-1 pins `expect(chip.nextElementSibling).toBe(line)`. The
   wrapper exists so the chip's date line and the track-record line stay a pair (D-162-2, comment at
   `FactsheetView.tsx:1286-1302`). Inserting between them would break that pairing whenever the flag
   is true.
2. Both date statements (when the job last succeeded, and how far the record runs) read first. The
   updating line then qualifies them: "these figures are from the last completed computation".

When `SeriesRecencyLine` renders nothing (empty or unparseable series), the line sits directly after
the chip. That is acceptable, because the order above still holds.

### Layout behaviour

- Inherits the wrapper's alignment: right-aligned at `sm` and up, left-aligned below `sm` (the parent
  is `text-left sm:text-right`). No new alignment class.
- Wraps naturally. No `max-w`, no `truncate`, no `whitespace-nowrap`. This matches the sibling
  sentences (`UnrecoveredGapLines`, `TradeFetchLine`), which also carry no cap.
- No animation, spinner, pulse, dot or icon (DESIGN.md Motion: "No decorative animation";
  `animate-pulse` is reserved for skeletons).
- No link, button or CTA. The viewer has no action that speeds up a recompute.
- No polling or auto-refresh. The line stays until the next page load. This phase adds no
  client-side refresh.

### Accessibility

- **No `role="status"` and no `aria-live`.** DESIGN.md's A11y minimum puts `role="status"` +
  `aria-live="polite"` on non-blocking state **changes**. This line is server-rendered, present at
  load, and never toggles client-side. The repo precedent is `OwnerUnpublishedNotice`
  (`FactsheetView.tsx:905-907`): "NOT `aria-live` (server-rendered, present at load)". A live
  region on static load-time text would announce on every page load, which is noise.
- **Not `role="alert"`.** Nothing went wrong.
- Contrast: `text-text-muted` #64748B is 4.76:1 on `#FFFFFF` and 4.51:1 on page `#F8F9FA` (measured by the UI checker; DESIGN.md:181 states 4.85),
  which passes WCAG 2 AA for 12-13px text. It is the same pair the sibling lines already pass under
  the axe matrix.
- Read order equals DOM order equals visual order. No `sr-only` duplicate.

### Surfaces

| Surface | Carries the line? | Why |
|---------|-------------------|-----|

A builder that never admits a recompute row sets `false`, and nothing renders. |

Because the line carries no print-hiding class, a PDF generated mid-recompute states that its figures predate a running computation. That is the honest print. ## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #F8F9FA (`--color-page`) | Page background behind the factsheet shell (existing) |
| Secondary (30%) | #FFFFFF (`--color-surface`) | Data panels and surfaces (existing) |
| Accent (10%) | #1B6B5A (`--color-accent`) | **Not used by this phase** |
| Destructive | #DC2626 (`--color-negative`) | **Not used by this phase.** There are no destructive actions |
| Updating line text | #64748B (`text-text-muted`) | The one colour this phase applies |

Accent reserved for (existing, unchanged): the `api_verified` trust-tier fill, primary buttons,
the active nav item, focus rings and borders, and the chart strategy line. The updating line must
**never** take accent.

Semantic gate ruling (DESIGN.md "Semantic-color gates"):
- **Muted**, because a recompute over a stored result is a steady state with nothing to flag. The
  KCS09 queued and running lines are `tone: "muted"` (`status-surface-copy.ts:70-104`) for the same
  reason.
- **Not amber.** Amber means a recoverable disclosure: a retry, or an exclusion a one-click action
  reverses. A normal recompute is neither, and the viewer has no action.
- **Not red.** Nothing failed. A failed re-run stays on today's `failed` path (D-02), which withholds
  the factsheet as it does today.
- **Not positive/green.** The line claims no success.

The FreshnessChip's own tone (fresh/stale/old, from `computed_at` and the series end) is unchanged.
During a recompute it can read `stale` or `old` beside the updating line. That is correct: the
figures are as old as the chip says.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Updating line (NEW, id `FQ190-UPDATING`) | `Updating with the latest data. These figures are from the last completed computation.` |
| Primary CTA | none. This phase adds no action |
| Empty state heading | unchanged (SC-4). A strategy with no stored analytics keeps today's placeholder |
| Empty state body | unchanged (SC-4). The owner lane keeps `KCS09-QUEUED` "A computation for this strategy is queued and has not started yet." or the matching `KCS09-RUN-*` line, verbatim from `status-surface-copy.ts` |
| Error state | unchanged. A `failed` row is still withheld and shows the existing `KCS09-FAIL-*` lines (RESEARCH V1/V2). The updating line never renders on a failed row |
| Destructive confirmation | none. This phase has no destructive actions |

**Character rules for the new string** (`status-surface-copy.ts` house convention):
- ASCII only, ending in a full stop U+002E. **No trailing ellipsis U+2026.** In this codebase the
  ellipsis marks in-flight button labels that resolve on the same screen within seconds
  (`"Copying…"`, `"Creating link…"`, `FactsheetView.tsx:2279`). This line is static,
  server-rendered and persists until reload. Every KCS-09 status line ends in a full stop.
- Sentence case, two declarative sentences, no exclamation (DESIGN.md Voice).
- No date, time, duration or percentage. The chip already carries the date. A time promise
  ("about 15 minutes") is not measured per run and would break SC-6.
- No strategy name, no venue, no internal vocabulary (`computing`, `pending`, `job`, `queue`).

**Why this wording and not D-03's example "Updating with new data…"** (D-03 offered it as "e.g.";
CONTEXT puts wording under Claude's Discretion "with a DESIGN.md check"):
1. "new data" claims the inputs changed. A re-run can recompute unchanged inputs (a user resync
   with no new fills, an `asset_class` correction, a composite member edit). "the latest data" is
   true in every case: the run reads whatever is current. This is a never-invent-data rule (SC-6)
   applied to copy.
2. The second sentence states the limit the reader needs: the numbers on screen predate the run.
   This follows DESIGN.md "copy that states its own limits".
3. The ellipsis is dropped for the reason in the character rules above.

**Single source.** The string is an exported constant `ANALYTICS_UPDATING_LINE` in
`src/lib/status-surface-copy.ts` (directive-free, already imported by factsheet pages and
client-safe). It is pinned character for character in `src/lib/status-surface-copy.test.ts`, as
that module's header requires. `FactsheetView.tsx` and, if widened, the tear sheet both import it.
Never inline a second copy.

## Open Questions for Founder

The agent brief forbids asking mid-run, so each default below was taken and is recorded for review.

1. **Wording.** Chosen: "Updating with the latest data. These figures are from the last completed
   computation." D-03's example was "Updating with new data…". It was changed because "new" claims
   the inputs changed, which a re-run does not guarantee, and because the house style keeps the
   trailing ellipsis for in-flight button labels. If you want the D-03 wording verbatim, it is a
   one-constant change plus its pin.
2. **shadcn initialization.** The gate default was **not** to initialize. The project's
   hand-authored design system and DESIGN.md drift gates already govern every token this line uses.
3. **Surfaces beyond the factsheet.** The line appears on every factsheet lane (public, owner,
   share link, discovery detail) and, automatically, in the page PDF if its gate is widened. It does
   **not** appear on the OG card or on list rows. If the planner extends D-02 to lists or the OG card
   (RESEARCH Open Question 1), those surfaces would show the last computed numbers with no updating
   marker. That is the default here, because D-03 placed the line on the factsheet only.
4. **No reload hint.** The line stays until the viewer reloads. It does not say "reload to see the
   new figures", because D-03 asked for one quiet line and the factsheet does not poll.
