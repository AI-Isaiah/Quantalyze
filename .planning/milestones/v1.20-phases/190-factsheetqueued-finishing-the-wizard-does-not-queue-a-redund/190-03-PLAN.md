D-04 (founder 2026-11-03, locked; Task 3). A row can keep a terminal-success status while the derive hop's prestamp replaces its flags. The status bridge holds `complete_with_warnings` (and a row carrying `computation_warned`) through the non-terminal branch, and holds `complete` through a ledger refresh (`v_refresh_keep`), until the compute hop's `_mark_computing`. A protected refresh that fails or aborts restores the terminal status and keeps the prestamp flags (`_guard_failure_payload_inplace`, `_upsert_restore`). G1 admits such a row as a terminal success. With a bound snapshot the build reads the snapshot's flags. Without one, today's code would draw the last success's figures under the new derive's flags. D-04 makes the factsheet fall back to today's queued state in that case. Detection is positive, not inferred from a missing marker. The live flags lack the marker and carry the `last_success_snapshot` key, and no snapshot is bound. Plan 09 writes that key on every strategy-mode prestamp, as null when it has no snapshot. A legacy row computed before the marker existed lacks the marker at rest too, but it carries no key. Keying on the missing marker alone would hide every such factsheet at rest, the defect class this phase fixes.

Founder decisions D-04 to D-06 (2026-11-03, CONTEXT.md) are locked and applied: D-04 in Task 3; D-05 keeps this plan's reach to every factsheet lane through the resolve stage; D-06 is plan 04's copy. The remaining Open Questions keep their defaults, recorded here:
- OQ-4 default: a failed-then-retried row shows its pre-failure numbers with the updating flag only when all three evidence checks pass. Under this plan's rule, a failure arm that wrote csv_source-only flags drops both the marker and any snapshot, so its retry stays withheld. A failure arm that carried the prior flags forward keeps the snapshot plan 09 wrote, so its retry is admitted with the flags of the success whose numbers are stored (plan 01's A2 verdict lists which arm does which).
- Evidence definition, a deliberate deviation from RESEARCH Pattern 2 (stored series plus finite headline): this plan adds a third check, success-written flags carrying `cumulative_method`. Reason, found while planning and checked in plan 01: the derive hop (`run_derive_broker_dailies_job`, `_prestamp_dq_flags`) REPLACES data_quality_flags and metrics_json_by_basis minutes before the compute hop's success write. A payload built in that window from the live flags would draw the old numbers under a different run's flags (native unit, curve method, chain-broken dating).
- The success-written flags therefore survive the derive hop (plan-check revision, 2026-11-03). Plan 09 makes the derive hop carry them inside its prestamp as `data_quality_flags.last_success_snapshot = {computed_at, flags}`. This plan reads them through `effectiveDataQualityFlags`. The third check, and every flag the build reads, use the effective flags, so the factsheet holds for the whole window with figures and flags from one success. The snapshot is used only when its computed_at is the same instant as the row's computed_at. Only the two terminal-success writers stamp computed_at (plan 01 verdict SNAPSHOT), so a stale, racing or version-skewed snapshot fails closed to withheld, never to mixed: a pending or computing row by check (c), a terminal-success row by D-04. The contract is stated identically in plan 09.
- OQ-2 default: ranking (percentiles, `get_verified_cohort_rank`) stays on terminal success during a re-run; no migration.
- CONTEXT Claude's Discretion, "what stored analytics means": the three evidence checks above. The displayed freshness stays `strategy_analytics.computed_at` (the FreshnessChip), never `last_sync_at`.
