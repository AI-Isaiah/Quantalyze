## The arms (ids are final; arms 1 and 2 use a post-apply `sql` twin, arms 3-10 an `edit` of the migration with a measured `occurrences`)

Keys: S = `source` (a ledger-refresh marker), C = `correlation_id`, P = `member_progress`,
U = `unified_backbone_at_claim`, K = `read_refusal_kept_figures`, R = `refresh_marker_retracted`.
Arms 3 and 5 seed only S, C and P (never K or U), so the twins of arms 9 and 10 make those arms the
FIRST failure. Inside the gate's single transaction `now()` is frozen, so `updated_at` cannot show a
write: assert "unchanged" with the row's `ctid` and metadata before and after.

- 1: marker function is SECURITY DEFINER, `search_path=public, pg_catalog`, service_role EXECUTE,
  anon, authenticated and PUBLIC none. Twin: a post-apply `sql` step,
  `{"arm":"1","apply":[{"kind":"sql","stmt":"GRANT EXECUTE ON FUNCTION public.mark_compute_job_kept_figures(uuid) TO authenticated"}]}`.
  This runs after the migration's own catalogue verify, which an `edit` widening the GRANT would
  trip during the apply. Precedent: the `TV-anon-exec` and `TV-auth-exec` twins in
  `supabase/tests/test_get_published_trade_venues.sql`. Plan 191-02's static test keeps
  edit-the-GRANT, because it reads text and applies nothing.
- 2: the same for the retraction function. Twin: a post-apply `sql` step,
  `{"arm":"2","apply":[{"kind":"sql","stmt":"GRANT EXECUTE ON FUNCTION public.retract_ledger_refresh_marker(uuid, text) TO authenticated"}]}`.
- 3: the marker keeps S, C and P with their values, sets K to JSON true, returns true. Twin: the
  marker's SET assigns only the K object (drops the left operand of the merge).
- 4: the marker on NULL, JSON null, array and scalar metadata leaves exactly `{"read_refusal_kept_figures": true}`
  and returns true; on an unknown id it returns false and writes nothing. Twin: the `jsonb_typeof`
  guard replaced by bare `metadata`.
- 5: the retraction of EACH marker returns `retracted` with the marker; S is gone, R holds the old
  marker, C holds the new id, P is kept; a NULL correlation id writes JSON null. Twin: the FIRST
  marker list (`nth` 1, the WHERE clause) narrowed to `('ledger-refresh')`.
- 6: not a marker (another source, NULL metadata, array metadata, an object without `source`)
  returns `no_marker`; metadata and `ctid` unchanged. Twin: the WHERE clause's marker predicate
  deleted.
- 7: a `done` row with a marker returns `done` with that marker and is unchanged; a `done` row
  without one returns `done` with a null marker; `pending`, `running`, `done_pending_children`,
  `failed_retry` and `failed_final` rows with a marker are retracted. Twin: `AND status <> 'done'`
  deleted.
- 8: a random uuid and a NULL id return `no_row`. Twin: the `no_row` outcome literal replaced with
  `no_marker`.
- 9: SC-3, two writers: on rows seeded S, C, P, marker then retraction and retraction then marker
  end with EQUAL metadata holding K true, R, the new C and P, and no S. Twin: the retraction also
  deletes K (`- 'read_refusal_kept_figures'` after `- 'source'`).
- 10: SC-3, three writers: all six orders of {marker, retraction, claim-style write} end with EQUAL
  metadata holding K, U, R, the new C and P, and no S. The claim-style write is a plain UPDATE using
  the merge expression copied from `supabase/schema/functions/claim_compute_jobs_with_priority.sql`
  (the `unified_backbone_at_claim` arm). Twin: the marker also deletes U.
- 11: control, untwinned: read metadata into a variable, run the real retraction, then write the
  stale copy plus K back as the old writers did; require that R is LOST and S is back, and raise
  when it is not (the harness would be blind). It carries no prose RED-UNDER: parity counts prose
  against twins (GRAMMAR "The parity gate"), and no migration edit can make this arm the first
  failure.
If a measured first failure forces a different twin, prefer a narrower mutation; use `neuter` only
for a structurally shadowed arm; never a waiver. Record any change and why in the SUMMARY.
