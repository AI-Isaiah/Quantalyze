### WR-01: A missing benchmark RETURN inside a multi-day interval is compounded as if it were 0

**Status:** fixed: requires human verification (a pairing-rule change, adapted from the review's suggestion)
**Files modified:** `analytics-service/services/metrics.py`, `analytics-service/tests/test_benchalign.py`
**Commits:** d1d1fc077 (the fix and its test), 288cc5019 (follow-up: the D-02 cross-citation)
**Applied fix:** `_interval_matched_benchmark` now pairs interval k only when every date of the
benchmark's OWN calendar inside (t_{k-1}, t_k] carries a return (`count == expected`). The
calendar is the set of weekdays the benchmark ever carries: seven for BTC, five for a business-day
series. `expected[k]` is a vectorised running count of those weekdays over the calendar days from
t_0 to t_last.

**Why the review's patch was not applied as written.** The suggested `count == span_days` (every
calendar day in the interval) breaks SC4. The golden fixture pair (`golden_returns`,
`benchmark_returns`) and the `tests/test_metrics_parity.py` pairs are both on `pd.bdate_range`, so
every Monday interval has span 3 and count 1, and the literal patch would have unpaired every
Monday of those pairs and moved `test_benchalign_dense_parity_bit_identical[golden]` and the parity
suite. The review's note that it "should" keep SC4 holds only for 7-day benchmarks. Inside one
interval, returns alone cannot tell a business-day Friday-to-Monday step from BTC with its weekend
rows dropped. The only signal is which weekdays the benchmark carries elsewhere in the series, so
the adapted rule reads that.

Behaviour, checked case by case: a business-day pair still pairs its Mondays (expected 1, count 1).
D-04 is unchanged (a daily strategy's Monday against a business-day benchmark is still unpaired by
the endpoint rule). The review's probe, a Saturday dropped from contiguous BTC, now unpairs the
Monday (expected 3, count 2). The production NaN-close shape, where Saturday and Sunday are both
dropped, also unpairs it (expected 3, count 1). A benchmark that only ever has weekday dates is
treated as business-day by construction, so a BTC window without any weekend date would be read
as weekday-only. For production BTC series longer than a week that cannot happen.

**Docstring:** the telescoping sentence is corrected. It holds only when every date of the
benchmark's own calendar inside the interval carries a return. A new INTERIOR GAPS paragraph says a
missing PRICE row would telescope but a missing RETURN row drops a move, and that the helper cannot
tell them apart, so it treats both as a gap.

**Test added:** `test_benchalign_gap_missing_row_inside_a_weekday_interval_unpairs_it`. A weekday
strategy against a contiguous 7-day benchmark with one Saturday return row dropped. It asserts that
exactly that Monday is unpaired and that every other paired value equals the price-ratio oracle on
the UNGAPPED benchmark (rtol 1e-12). It was RED on the pre-fix code (the Monday was paired) and is
GREEN after.

**D-02 cross-citation (follow-up commit 288cc5019).** The helper docstring and the module docstring
of `tests/test_benchalign.py` said the Python pairing and the Phase 169.5 BENCHCOMPARE TypeScript
twin (`src/lib/factsheet/align.ts`) differ at index 0 only. That is no longer true. Both now name
the second difference: for k >= 1 the Python helper also unpairs an interval missing a date of the
benchmark's own calendar inside it, and the TypeScript twin has no such rule. **Open for 169.5
BENCHCOMPARE:** decide whether to adopt the interior-gap rule, so the two stay aligned.

**CHANGELOG (not touched here, per the fixer brief).** The amended REVIEW.md WR-01 text says this
fix deliberately stops the telescoping across a BTC price gap for SPARSE strategies: a sparse
interval that spans a stale-fallback or fresh-fetch price gap is now unpaired. The current release
entry describes stale-fallback behaviour for dense series only. The ship step's re-fold needs a
line for the sparse case. The review leaves one question open and this fix does not answer it:
whether `fetch_btc_daily_prices` can emit a NaN close.

### WR-02: r_squared and correlation/beta read different rows when the strategy carries ±inf

**Status:** fixed
**Files modified:** `analytics-service/services/metrics.py`, `analytics-service/tests/test_benchalign.py`
**Commit:** a4cbd5969
**Applied fix:** `_benchmark_pair` now maps the strategy's ±inf to NaN once, so every
benchmark-relative metric (fan-out scalars, rolling, r_squared) drops the same rows. The two
per-call `.replace([np.inf, -np.inf], np.nan)` in `_r_squared` and `_r_squared_pair_varies` are
removed. The docstrings of `_benchmark_pair` and of `_r_squared` (NaN CONVENTION) now name where
the mapping happens. `test_benchalign_one_pairing_r_squared_is_correlation_squared` gains
`dense_daily_with_pos_inf_day` and `dense_daily_with_neg_inf_day`. Both were RED on the pre-fix
code (`correlation is None`) and are GREEN after.

One consequence to know: in `_rolling_greeks` the former inf row now reaches that function's
existing frame `fillna(0)` as NaN. Before, it entered the window as inf. No pre-existing test
covers that path.
