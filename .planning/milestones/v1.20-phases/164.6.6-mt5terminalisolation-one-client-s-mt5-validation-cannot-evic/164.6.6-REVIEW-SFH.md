# Phase 164.6.6: silent-failure review

**Verdict: no CRITICAL or HIGH findings. There are 7 MEDIUM findings.** The core
invariants hold:

- A validation is never silently routed to the job terminal. Both validate sites
  read only `read_env_validation_gateway_endpoint`, and a `None` refuses the
  validation and alerts.
- The handover recorder cannot replace a lease body's exception.
- Every gated park skip is reported.

What remains is alert precision rather than total silence. The findings cover four
areas: alerts that name the wrong cause, a throttle keyed too coarsely, classes of
park failure that never page, and server misconfigurations that the worker
classifies as retryable `unknown`.

All line numbers are at the reviewed HEAD. Paths are relative to the repo root.

---

## M-1: `Mt5GatewayHostNotPrivate` is classified `unknown`, so it is retried as if it could clear (brief item confirmed, with a correction)

- **Location:**
  - `analytics-service/services/job_worker.py:879`, the catch-all at the end of `classify_exception`.
  - The raise is at `analytics-service/services/mt5_client.py:1034`, in `_default_connect`.
  - It is reached from `job_worker._make_mt5_session`, which reads `MT5_GATEWAY_HOST` raw and does not go through `read_env_gateway_endpoint`.
- **Severity:** MEDIUM. The fault is latent: plan 04 measured the PROD job host as a private-network name.
- **Confidence:** 9 that the gap exists. I checked that no `except ValueError` between `_make_exchange_client` and the dispatcher remaps it. `_allocator_key_preflight`'s `except Exception as build_exc` re-raises.
- **Correction to the brief:** it is not retried forever. Each job is retried up to `max_attempts` (default 3) and then goes to `failed_final`. It recurs only because the scheduler re-enqueues every derive, balance and holdings job for every MT5 key.
- **Scenario:** an operator sets `MT5_GATEWAY_HOST` to a public host, for example while debugging over a temporary TCP proxy like the one N-01 removed.
  - Every MT5 job raises `Mt5GatewayHostNotPrivate` while it builds the client.
  - `classify_exception` returns `("unknown", <fixed refusal text>)`, and each job burns 3 attempts on a fault that no retry can clear.
  - This is the A3 class, the bare `RuntimeError` that was retried, which the `Mt5GatewayMisconfigured` arm exists to remove.
  - The heal and the session monitor take a different path. See M-2.
- **Recommendation:** add an arm above the catch-all, next to the `Mt5GatewayMisconfigured` arm:
  ```python
  if isinstance(exc, Mt5GatewayHostNotPrivate):
      return ("permanent", str(exc))  # fixed text: names no host or port
  ```
  The message is already fixed and free of host details, so `str(exc)` is safe.

## M-2: the worker's D-05 refusal is a bare `RuntimeError`, which also lands in `unknown`

- **Location:** `analytics-service/services/ingestion/mt5.py:189`, the `raise RuntimeError("MT5 gateway not configured: MT5_VALIDATION_GATEWAY_HOST / ...")`.
- **Severity:** MEDIUM. **Confidence:** 8.
- **Why this is more reachable than M-1:** this phase adds a newly required env pair. Any environment that runs the worker without `MT5_VALIDATION_GATEWAY_HOST` and `MT5_VALIDATION_GATEWAY_PORT` hits this path. So does an environment where the host is set but not private (see M-3).
- **Scenario:** a `process_key_long` MT5 onboarding job runs on an environment missing the pair.
  - `long_fetch.py:370` calls `adapter.validate`, which raises the `RuntimeError`.
  - `classify_exception` returns `unknown`, and the job is retried up to 3 times.
  - Each attempt fires `alert_mt5_validation_gateway_unconfigured`. That alert is throttled hourly, so the paging is fine.
  - The user's onboarding sits through the retries and ends with a raw text that is not curated.
- **Recommendation:** raise `Mt5GatewayMisconfigured` with a curated detail, or a dedicated typed error that `classify_exception` maps to `permanent`. This is the pattern A3 established for this exact adapter. The same pre-existing bare `RuntimeError` in `job_worker._make_mt5_session` (`job_worker.py:1166`) belongs in the same fix.

## M-3: a validation gateway host that is not private pages as "unset or malformed", and the true cause is logged once per process

- **Location:**
  - `analytics-service/services/mt5_relogin.py:921`, the `mt5_validation_gateway_host_not_private` arm.
  - That arm goes through `_log_configuration_fault_once` at WARNING, once per process.
  - The alert text is at `mt5_relogin.py:965` and in the `capture_message` that follows. Both sites call `alert_mt5_validation_gateway_unconfigured`.
- **Severity:** MEDIUM. **Confidence:** 8.
- **Scenario:** N-01 records that the validation gateway briefly carried a public domain during stand-up.
  - An operator pastes that domain into `MT5_VALIDATION_GATEWAY_HOST`.
  - Every wizard and worker validation is refused, which is correct.
  - Every refusal logs ERROR and pages: "MT5_VALIDATION_GATEWAY_HOST / MT5_VALIDATION_GATEWAY_PORT is unset or malformed."
  - The operator opens Railway and sees both variables visibly set, with a numeric port.
  - The only line naming the real cause ("not a private-network host (T-134-03)") was emitted once at WARNING, possibly hours earlier, and never again until a process restart.
  - The page sends the operator in the wrong direction.
- **Recommendation:** make the reader return a reason with its `None`, or expose the last refusal reason, and put the closed reason in the alert:
  - `absent`
  - `port_not_numeric`
  - `host_not_private`

  Variable names only, never values. At minimum, change the alert copy to "unset, malformed, or not a private-network host".
- **Related job-pair gap:** the same not-private arm on the job pair (`mt5_relogin.py:858`, `read_env_gateway_endpoint`) logs one WARNING per process with no capture. After that, the heal and the session monitor skip on every tick with nothing more said. The job side does get some signal from the failing jobs (M-1), but the heal skip itself is silent after the first line.

## M-4: the park's Sentry throttle is keyed by cause only, so one site's capture suppresses the other's for an hour

- **Location:** `analytics-service/services/mt5_probe.py:546`, `_park_last_alert_at[cause] = now`, in `_alert_park_failed`.
- **Severity:** MEDIUM. **Confidence:** 8.
- **Scenario:**
  - A worker `process_key_long` validation's park fails with `login_refused`, for example because the house password was rotated at the broker. That capture is sent.
  - For the next 3600 s, every wizard park that fails with `login_refused` logs ERROR but sends no capture.
  - Sentry shows one event tagged `site=validate_worker`. An operator triaging from Sentry concludes the wizard is unaffected.
  - Meanwhile every interactive master-password validation is leaving its session on the validation terminal.
- **Contradiction:** this phase's own D-05 alert, `_last_mt5_validation_alert_at` in `mt5_relogin.py`, is keyed per site specifically "so the worker's alert can never silence the wizard's inside one window", which is the WR-02 shape. The park alert does not follow its sibling.
- **Recommendation:** key the throttle on `(cause, site)`. `site` is already one of two closed literals.

## M-5: park failures whose cause is unrecognised are downgraded to WARNING, and a persistent park failure never escalates

- **Location:**
  - `analytics-service/services/mt5_probe.py:557`, `_is_park_bridge_glitch`.
  - `mt5_probe.py:634`, where its result is used.
- **Severity:** MEDIUM. **Confidence:** 6.
- **Why it matters:** `_is_park_bridge_glitch` is a negative definition. It means `classify_mt5_login_error == "transient"`, which is the classifier's catch-all for any text it does not recognise, minus two carve-outs. These house-login failures all reach the glitch arm, which logs WARNING and sends no capture:
  - `Mt5Client.login` returned falsy and `_raise_last` could not read `last_error()`: the round-trip died, or the answer was missing or malformed. This arrives as a plain `Mt5ClientError`, not as `Mt5LoginRefusedError`.
  - A falsy login answered with code `1` (RES_S_OK) or with `-10000` to `-10003`: this is `Mt5LoginRefusedError`, but `is_mt5_login_refusal` excludes those codes and `is_ipc_transport_fault` covers only `-10004` and `-10005`.
  - A transport raise wrapped as `Mt5ClientError(0, <scrubbed text>)`, whatever the text.
- **This follows the founder's decision as written.** It is the same chain the validate site uses at WARNING. The gap is that nothing distinguishes a one-off blip from a park that fails the same way on every validation.
- **Scenario:**
  - The validation terminal starts answering the house login falsy with an `last_error()` it cannot read.
  - Every validation, including master-password ones, then ends with a WARNING, and the master session stays on the validation terminal.
  - It stays there indefinitely, with no page, because each occurrence on its own looks like a blip.
  - The validate site has the same blind spot for user keys. For the park it matters more, because the credential is always the same house account, so repetition is itself the signal.
- **Recommendation:** honour both D-15 and "page else":
  - Count consecutive glitch-class park failures per site.
  - Escalate through `_alert_park_failed("bridge_glitch_persistent", ...)` after N consecutive failures, or after any failure M minutes since the last successful park.
  - Reset the count on a successful park.
  - Add the new cause to `_PARK_ALERT_CAUSES`.
  - This needs a founder sign-off, because it refines the 2026-10-03 decision.

## M-6: the park's outer `except Exception` handler is the one park failure path that never pages, and a cancellation during the park bypasses every alert

- **Location:**
  - `analytics-service/routers/exchange.py:1240`.
  - `analytics-service/services/ingestion/mt5.py:507`.
  - At both, `except Exception as park_exc:` with `logger.error(...)` only.
- **Severity:** MEDIUM. **Confidence:** 4. The paths are reachable but unlikely.
- **Scenario (a), an exception escapes the park block:**
  - `report_park_skipped` and `park_on_house_account` are written never to raise.
  - Anything else in that block can still raise and reach this handler, for example:
    - `asyncio.to_thread` raising `RuntimeError` after the default executor shuts down during a graceful stop;
    - an unexpected error from `read_env_mt5_credentials()`, which runs on the loop as an argument expression.
  - When that happens, the park did not run and the handler logs one ERROR with no Sentry capture.
  - That breaks the founder rule that every park skip or failure other than the glitch pages.
- **Scenario (b), a cancellation lands during the park's await:**
  - Examples are a Railway redeploy cancelling an in-flight worker task, or the dispatcher's per-kind `wait_for`. The latter has a 30-minute budget for `process_key_long`, so it needs an extremely long lease wait.
  - `CancelledError` is neither `TimeoutError` nor `Exception`, so neither `report_park_skipped("ceiling")` nor this handler runs.
  - The `finally` then releases or closes the client while the park thread may still be on the wire, which is the W-1 class the gate exists to prevent.
  - No park alert of any kind fires.
- **Recommendation:**
  - In the outer handler, also call `report_park_skipped("unrecognised_cause", site=...)`. It is already a closed member and never raises.
  - For cancellation, add an `except asyncio.CancelledError:` arm around the park await that reports a park skip and re-raises.

## M-7: a login that fails may still displace the previous holder, and it is never recorded or named in the attribution limit

- **Location:**
  - `analytics-service/services/mt5_client.py:2145`.
  - `_note_terminal_holder` is reached only after a successful login.
  - The docstring says "A raising or falsy login never reaches it, so it never changes the record."
  - `HANDOVER_ATTRIBUTION_LIMIT` is in `analytics-service/services/mt5_handover.py`.
- **Severity:** MEDIUM. **Confidence:** 5. It depends on terminal behaviour that is unmeasured: whether a refused `login()` logs the previous account out.
- **Scenario:**
  - Job key A holds the job terminal.
  - A derive for key B, whose stored investor password has gone stale, calls `login()`, and the terminal answers falsy.
  - If the MT5 terminal drops A's session when it attempts B's login, which is the usual GUI behaviour on a failed account switch, A has been evicted.
  - No handover row is written, and the registry still says A.
  - The next lease for A sees `before == after == A` and records nothing either. The eviction left no trace.
- **What is wrong today:** the row's own `attribution_limit` sentence lists what the record cannot see (the VNC console, a relaunch, other processes, abandoned sessions) but not this case. So a reader of the record would trust its silence.
- **Recommendation:**
  - Either stamp `HOLDER_UNKNOWN` through the one door in the falsy-login arm, so that the next diff records "unknown to the next holder";
  - or add "a login that failed (the previous session may have been dropped)" to `HANDOVER_ATTRIBUTION_LIMIT`.
  - The first gives a visible signal. The second makes the silence an honest gap rather than one nobody stated.
