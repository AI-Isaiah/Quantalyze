## Summary

**The single most important finding: the account handover is the NORMAL PATH OF EVERY MT5 JOB, not a validation defect.** The shipped read model is "log in per call, read, leave". Seven production sites take the terminal lease, and every per-customer one logs the ONE shared terminal into that key's account with `Mt5Client.login`. The MT5 Python API has no logout function, and `Mt5Client.close()` never calls `shutdown()`. So the terminal always sits on whichever account the last caller used, and the next caller of any kind evicts it. The shipped code says this in its own words: *"MT5 binds one account per terminal AT A TIME — a serialization constraint, not a capacity one — so ONE terminal cycles through hundreds of accounts across a day."* [VERIFIED: `services/mt5_concurrency.py::_MT5_LEASE_WAIT_S` comment block]. Phase 137's context spoke of a "logout-between-accounts" loop, but the API has no logout. The only teardown ever shipped was `mt5.shutdown()`, which per EVIDENCE §A6 (quoted in the `Mt5Client` module docstring) *"does not log the account out"*, and 153.3 D-35 removed it from `close()`. Nobody should go looking for a deleted logout. **The planner cannot scope criterion 1 until the founder says which switches count as "eviction":** only validations (switches to un-onboarded accounts), or every switch.

**Criterion 2 is larger than "account numbers in the Navigator".** MetaTrader's own settings page says the terminal can *"save account details (number, main and investor passwords) on the hard disk"* [CITED: metatrader5.com Platform Settings]. The repo's own live spike recorded that a bare relaunch came back logged in, read-only, to whichever account the last service call had used, so that client's password was persisted in the terminal's account database [VERIFIED: `deploy/mt5-gateway/railway-gateway.md` "Caveats"]. A validate logs in BEFORE it can tell a master password from an investor one (the master rejection happens after `login()` succeeds). So the terminal's on-disk store may hold saved passwords for every account ever validated, **including master (trading) passwords that the product rejected**. Beside it sit per-account deal caches under `Bases`, Journal logs naming account and server, and `servers.dat`. The first half is measured; the "every account, including master" half is `[ASSUMED]` and must be confirmed live by the founder.

**Criterion 3 options differ mainly on how many account switches remain and where credentials land.** Serialize-and-restore (option c) is the cheapest code, but there is no "home account" concept in the code to restore to. Every restore is a second cross-account switch per operation, which doubles exposure to the still-unexplained switch wedge (`MT5-SWITCH-WEDGE-CAUSE-01`). It also does nothing for criterion 2. Isolating validation onto a separate terminal that is scrubbed after each use (option b or d) is the only family that addresses C1-for-validations and C2 together. Neither option can be proven feasible without a founder-run live spike.

**Primary recommendation (NOT A DECISION — founder one-way door):** isolate validation from the job terminal on a dedicated validation terminal, and scrub its account store, deal cache and logs after every validation (option b, "pool of one plus scrub"). Record every job-terminal handover as an attributable event (no migration). Scrub the job terminal on each recycle. A founder spike must gate it first. Reject serialize-and-restore as the primary mechanism.

## Where the switch happens, and why nothing records it against A

**The switch:** `services/mt5_client.py::Mt5Client.login` first calls a bare `self._mt5.initialize(timeout=...)` (attach) and then `self._mt5.login(login, password=password, server=server, timeout=...)`. The second call is the account change. For the 2026-09-21 clean handover the Journal read `'<account A>': disconnected` at 04:08:06, then `'<account B>': authorized` at 04:08:07 (ROADMAP criterion 1).

**Why no record exists against A, four independent reasons, each read this session:**

1. **No prior-holder state.** Every job builds a fresh `Mt5Client` (`Mt5Client.terminal_key` docstring: "every job builds a fresh client via `_make_mt5_session`"). Nothing in-process remembers which account the terminal was on.
2. **The login bracket checks only the incoming account.** `services/mt5_probe.py::assert_expected_login` and the local `_assert_expected_login` closures assert `account_info()['login'] == expected` for the CALLER's key, before and after the read. They protect B's data from being stamped on the wrong account. They say nothing about who was displaced.
3. **The stage instrument carries no account by design.** `services/mt5_client.py::emit_mt5_stage_event` builds `fields` from `"stage"`, `"duration_ms"`, `"ok"` and optional `terminal_key` / `error_class` / `outcome`, a closed allow-list ("⛔ The event's field set is a CLOSED ALLOW-LIST", module docstring).
4. **The session-episode sink refuses attribution on purpose.** `services/mt5_session_episodes.py::ATTRIBUTION_LIMIT` reads, verbatim: *"This reading cannot attribute the authorized session to any particular account: the detector is credential-free, other paths log in per customer on the same shared terminal, and close() never calls shutdown()."* Its rows carry `"reading_attributes_account": False`.

**Consequences for any "record against A" design:**
- It can only be keyed by `api_key_id`, never by account number (public repo and log hygiene).
- It can see only handovers **this process** made. A VNC login, a relaunch auto-login, or a heal to the house account are invisible to it unless recorded at their own sites.
- The cheapest correct source is **prior-holder tracking at the lease**: remember, per `terminal_key`, the `api_key_id` (or `"house"`) whose login last succeeded. An extra pre-login `account_info()` read would put the displaced account number in memory and cost a round trip on every job.

### What does A actually lose? (open, founder-owned)

`[ASSUMED]` MT5 positions and orders are held on the broker's trade server. A terminal leaving an account does not close them, and an investor-password session cannot trade in the first place. Under the shipped read model **no Quantalyze path depends on the terminal staying on A between leases**: every reader logs in again under its own lease and brackets the account. So the economic harm to A from a switch is, as far as the code shows, nil. The harms that ARE evidenced:

- **(H1) No record, no attribution.** Nothing says A was displaced, by whom, or when (above).
- **(H2) Every switch is exposure to the unexplained switch wedge.** Cause B of `-10005` is triggered by an account switch and its mechanism is open (`MT5-SWITCH-WEDGE-CAUSE-01`). One wedge took MT5 down for everyone for 1h39m (ROADMAP 164.6.5). The fewer cross-account switches, the less exposure.
- **(H3) The "disturb" window: a master-password validate puts a TRADE-CAPABLE session on the shared terminal.** *"Allow algorithmic trading"* is CHECKED (it has to be, or branch 5 of `classify_trade_capability` refuses every key as `undetermined`). The account-change disable option is pinned UNTICKED (U6). `run_probe` logs in with the typed password before the verdict can reject a master one. For that window the shared terminal holds a live trading session on a client account, reachable over an **unauthenticated arbitrary-remote-code** rpyc channel (T-134-03, `deploy/mt5-gateway/railway-gateway.md` hard constraint). This is a finding for the planner and founder. Fixing the probe order is NOT proposed here; that would be a scope expansion.
- **(H4) Credential and data persistence** (next section).

⚠️ **Open question the founder must answer before criterion 1 is scoped:** who was account A? Was it the house account (the `MT5_LOGIN` heal target) or a client? Does anything, such as a human watching the Trade tab or an EA, rely on the terminal staying on it? Was the 04:08 switch a validation, as the ROADMAP says, or a scheduled batch job? `daily_enqueue_loop` runs once at startup (unless `_daily_enqueue_already_ran_today` finds a same-UTC-day run), then every `interval` seconds, default one day, from that point. There is no fixed hour, so 04:08 cannot be attributed from code alone [VERIFIED: `main_worker.py::daily_enqueue_loop` body read this session]. The loop seeds `poll_positions` jobs, which can reach the MT5 holdings read.

## Common Pitfalls

### Pitfall 1: Scoping criterion 1 as "validation-only" without saying so
**What goes wrong:** the plan isolates validation, and the job terminal keeps switching accounts dozens of times a day. A verifier then reads criterion 1 literally and finds evictions still happening.
**How to avoid:** get the founder's answer on the scope question first, and write it into the criterion text.

### Pitfall 2: A scrub that deletes the saved house login
**What goes wrong:** the next unattended recycle relaunches to `-6`, and MT5 goes dark until the monitor's next tick heals it (600 s default).
**How to avoid:** the scrub's relaunch must be `initialize_with_credentials` with the house triple, inside the same lease.

### Pitfall 3: Scrubbing only one data directory
**What goes wrong:** the portable install dir and the per-user dir each hold an account store, and a container restart flips between them.
**How to avoid:** the verb enumerates both. The offline test pins both paths as literals in the committed constant.

### Pitfall 4: A second lock registry
**What goes wrong:** `mt5_concurrency` warns that a second `dict[str, asyncio.Lock]` serializes nothing.
**How to avoid:** a validation terminal is a second KEY in the one registry, never a second registry. `_PRODUCTION_LEASE_SITES` stays authoritative, and moving a site re-cuts it deliberately.

### Pitfall 5: Interpolating anything into a new remote-source constant
**What goes wrong:** mt5linux evals source remotely. An interpolated path or credential is both an injection and a disclosure risk.
**How to avoid:** copy the `TERMINAL_RECYCLE` test shape in `tests/test_mt5_client_contract.py`: an AST string literal with no brace, a no-argument signature (or int-only arguments), abandoned-session refusal, and a scrubbed traceback.

### Pitfall 6: Logging the displaced account
**What goes wrong:** a handover record that names the displaced account number leaks it into Railway logs or Actions logs, which are public.
**How to avoid:** key by `api_key_id` and never widen `emit_mt5_stage_event`'s allow-list.

### Pitfall 7: More switches means more wedge exposure
**What goes wrong:** any design that adds switches (restore, scheduled scrub-relaunch) multiplies exposure to Cause B, which is still unexplained.
**How to avoid:** count switches per design in the plan, and prefer designs that reduce them.

### Pitfall 8: Assuming the recycle's terminate works live
**What goes wrong:** `recycle_terminal_process` over the channel has never run live (WINDOWS entry 68). A scrub built on it inherits that.
**How to avoid:** the founder's first live scrub run doubles as that measurement.
