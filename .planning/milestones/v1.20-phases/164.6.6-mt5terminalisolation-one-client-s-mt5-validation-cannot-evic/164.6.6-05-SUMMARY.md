# Phase 164.6.6 Plan 05: H3 part 1, the dial-side private-host check

**The analytics service now refuses to dial an MT5 gateway at any host that is not a private-network name.** `services/mt5_client.py::is_private_gateway_host` is checked at the top of `_default_connect`, the only production transport factory, before `mt5linux` is imported. Both endpoint readers in `services/mt5_relogin.py` apply the same check, so a public validation host is reported as a server misconfiguration (500 `MT5_GATEWAY_UNCONFIGURED`, or the worker's `RuntimeError`, plus the D-05 alert) and never as a 503 that votes on the gateway breaker.

## What was built

- **`is_private_gateway_host(host)`.** It is pure: no DNS lookup and no socket. It returns True only for:
  - an IP literal (IPv6 optionally in brackets) inside `_PRIVATE_GATEWAY_NETWORKS`: 127/8, ::1, 10/8, 172.16/12, 192.168/16, 100.64/10 (the Tailscale fallback) and fc00::/7;
  - a name whose last label is in `_PRIVATE_GATEWAY_TLDS` (`internal`, `test`, `localhost`), case-insensitive, with one trailing dot ignored;
  - a single-label name.

  IP literals are judged first, so a public IPv6 (which has no dot) cannot pass as a single-label name. The stdlib's private-address flag is not used: `grep -cE '\.is_private([^_]|$)' services/mt5_client.py` prints 0.
- **`Mt5GatewayHostNotPrivate(ValueError)`.** Its message is fixed and names the refusal and T-134-03, never the host or the port. It is deliberately not an `Mt5ClientError`, because the credential classify arms match on that class.
- **The readers.** `read_env_gateway_endpoint` and `read_env_validation_gateway_endpoint` return `None` for a non-private host. Each logs once under its own new reason (`mt5_gateway_host_not_private` and `mt5_validation_gateway_host_not_private`), naming the env var NAME and "not a private-network host (T-134-03)", never the value.
- **Single-transport pin.** `test_only_default_connect_builds_an_mt5_transport` walks `tests.test_mt5_concurrency._production_python_files()` plus `scripts/*.py`, 116 files. It asserts four things:
  - `mt5linux` is imported only inside `services/mt5_client.py::_default_connect`, and exactly once there.
  - No production file imports `rpyc`.
  - Nothing calls `rpyc.classic.connect`, `rpyc.connect` or `rpyc.ssl_connect`.
  - Neither package is imported dynamically by a string literal.

  `test_the_single_transport_pin_reports_each_violation` calibrates the checker on eight in-memory violations, plus the sanctioned form.
- **Runbook.** `deploy/mt5-gateway/railway-gateway.md` has a new section, `## T-134-03 (Phase 164.6.6, D-07 part 1) — private-host check on the dialling side`. It covers what is checked, the allowlist in words, why authentication was not taken, what the code does not prove (the gateway side is N-01 and L-H3), and the boundary and residual.

## How a refusal surfaces on the job path (code reading, nothing run live)

`job_worker._make_mt5_session` reads `MT5_GATEWAY_HOST` raw and builds `Mt5Client(host, int(port_raw))`. `Mt5Client.__init__` calls the stored factory, so for a public host `_default_connect` raises `Mt5GatewayHostNotPrivate` during construction. From there:

- **Preflight.** The exception is raised inside the preflight (`_key_preflight` / `_allocator_key_preflight`), which re-raises it unchanged. On the allocator poll, `account_identity.escalate_session_build_failure` first logs ERROR with the exception CLASS name only.
- **Classification.** The dispatcher turns it into a FAILED result. `job_worker.classify_exception` has no arm for it. It is not `Mt5GatewayMisconfigured`, not an HTTPException and not ccxt, so it falls through to `("unknown", <fixed message>)`.
- **No credential verdict.** It is not an `Mt5ClientError` or an `Mt5ValidationError`, so no credential classify arm can match it. I grepped the poll, stamp and derive paths for `except ValueError` and `isinstance(..., ValueError)` arms. Every hit wraps a payload `float()`/`int()` parse or a timestamp parse, never the client construction. The fixed message carries no host or port, and it matches none of the anchored `_AUTH_PHRASES` / `_WRONG_SERVER_PHRASES` (it contains no "password", "account" or "trade server" phrase). **The user's key is never blamed.**
- **Finding (not fixed here; `job_worker.py` is off-limits to this plan):** `unknown` RETRIES, so a public job host is retried as though it might clear, when it is a permanent misconfiguration. That is the same class the `Mt5GatewayMisconfigured` arm was built to remove. It is reachable only if someone sets a public `MT5_GATEWAY_HOST`, which plan 04 measured is not the case today (the job host is `.railway.internal`). The heal and the session monitor do not reach this path: they read through `read_env_gateway_endpoint`, which now skips with the log-once line. A follow-up that maps `Mt5GatewayHostNotPrivate` to `permanent` in `classify_exception` would close it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Resolver numeric IPv4 forms and public IPv6 literals**
- **Found during:** Task 1
- **Issue:** The plan's rule "single-label name (no dot) is private" would admit 8.8.8.8 written as a single decimal number and `0x8080808`. The C resolver accepts both as 8.8.8.8 (I checked with `socket.inet_aton` in the venv). It would also admit an unbracketed public IPv6 such as `2001:4860:4860::8888`, which has no dot. All three would dial a public address and break the must-have "any public IP literal is refused".
- **Fix:** `_private_ip_literal` judges IP literals first. It uses `ipaddress` and falls back to `socket.inet_aton` (which parses only, with no network access) for the numeric forms. These hosts are now in both the refusal test and the table.
- **Files modified:** `analytics-service/services/mt5_client.py`, `analytics-service/tests/test_mt5_client_contract.py`
- **Commit:** 0ae304321

**2. [Rule 2] Single-transport pin is wider than the plan's minimum**
- **Found during:** Task 2
- **Issue:** The plan asked for (a) `mt5linux` imported only in `_default_connect` and (b) no rpyc connect call. An aliased import such as `from rpyc import classic as c; c.connect(...)` would slip past a call-name match.
- **Fix:** The pin also bans any `rpyc` import in production (there are none today), string-literal dynamic imports of either package, and an `mt5linux` import nested inside a function within `_default_connect`. It asserts exactly one sanctioned import, so a truncated walk cannot pass. It also sets a floor of 100 files (116 measured).
- **Commit:** 015281073
