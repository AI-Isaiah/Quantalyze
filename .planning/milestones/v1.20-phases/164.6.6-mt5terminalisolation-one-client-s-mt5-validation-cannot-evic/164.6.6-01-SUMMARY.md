# Phase 164.6.6 Plan 01: MT5 terminal handover record Summary

When the service logs the shared MT5 terminal into a different holder than the one it last logged in, `mt5_terminal_lease` now writes one closed `cron_runs` row (`cron_name = 'mt5_terminal_handover'`). The row names the displaced holder and the incoming holder, each an `api_key_id` or a closed literal. A stamp from a session whose lease has already been released is refused by the epoch guard. All seven production lease sites pass a holder and a site, and an AST roster test pins that.

## How it works

- **Registry and stamp.** `services/mt5_client.py` holds `_MT5_TERMINAL_HOLDERS`, keyed by `terminal_key`. `_note_terminal_holder` is the only function that writes it. It runs only after `Mt5Client.login` or `Mt5Client.initialize_with_credentials` succeeds. `Mt5Client.recycle_terminal_process` calls it with `HOLDER_UNKNOWN`. The holder comes from the `_MT5_LEASE_HOLDER` ContextVar, which `asyncio.to_thread` carries into the login thread.
- **Epoch guard.** If the context's occupancy is not exactly `(terminal_key, current epoch)`, nothing is stamped. One WARNING is logged, carrying the stage and the two epoch integers.
- **Lease.** `mt5_terminal_lease` takes keyword-only `holder` and `site`. It reads `before` on acquisition. The busy raise stays above the `try`. In the `finally`, the original order is kept: bump the epoch, un-stamp, release. Only after `lock.release()` does it read `after`, with no `await` in between. If `after` differs from `before`, it awaits `record_mt5_terminal_handover`. It is awaited directly rather than spawned as a background task.
- **Recorder.** `services/mt5_handover.py` builds the payload inside the outer `try` and inserts one closed point-event row, bounded by `_HANDOVER_RECORD_TIMEOUT_S` (5 s). The metadata has exactly these keys: `schema_version`, `previous_holder`, `incoming_holder`, `site`, `records_account_number`, `attribution_limit`. Its shape is one `except Exception` with a nested `except BaseException` fallback. No migration was needed: `cron_runs.cron_name` has no CHECK constraint.

With the fixture neutered it went RED (`DID NOT RAISE RuntimeError`): the real client would have been built. I restored the file from a byte backup and confirmed it with `cmp`.
- **Commit:** fc501c041

## Known limits (written into every row as `HANDOVER_ATTRIBUTION_LIMIT`)

The record sees only logins this process makes through the lease. It does not see:
- logins made at the VNC console;
- the account a relaunched terminal auto-logs into (recorded as `unknown`);
- logins by other processes or replicas;
- a login that an abandoned session completes after its lease was released. The epoch guard refuses to stamp it and it appears only as a WARNING.

A stamp that a zombie recycle makes after its lease was released is refused the same way, so the registry can briefly lag behind a terminal that really was recycled.
