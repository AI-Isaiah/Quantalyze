## Warnings

### WR-01: `Mt5GatewayHostNotPrivate` on the job path is classified `unknown`, and the session path refuses the same host only with a log-once WARNING (KNOWN ITEM, confirmed and restated)

**File:** `analytics-service/services/job_worker.py:1162-1173` (`_make_mt5_session`), `analytics-service/services/job_worker.py:879` (the `classify_exception` fall-through), `analytics-service/services/mt5_client.py:1033-1034`, `analytics-service/services/mt5_relogin.py:852-863` and `:626`

**Confidence:** 8/10

**Issue:**
- **Classification.** `_make_mt5_session` reads `MT5_GATEWAY_HOST` raw, with no strip and no private check, and
  constructs `Mt5Client(host, int(port_raw))`.
  - The constructor dials, so `_default_connect` raises `Mt5GatewayHostNotPrivate`, which is a `ValueError`.
  - `classify_exception` has no arm for it, so it falls to `("unknown", str(exc))`.
- **Correction to the brief: it is NOT retried forever.** An `unknown` failure reaches `failed_final` once
  `attempts >= max_attempts` (default 3, DB-side; see the comment at `job_worker.py`, around line 11725).
- **What actually happens.** Every MT5 job on every cron tick burns its full retry budget against a fault that
  cannot clear.
  - It then ends with the "automatic retries exhausted" user copy, which comes from the curated-copy function in
    migration `20260826120000`.
  - That copy is false: no retry can fix this. The correct copy says the failure will not resolve by retrying.
- **The second half, on the session path.** For the same public host, `read_env_gateway_endpoint` returns `None`
  and logs through `_log_configuration_fault_once`, which is `logger.warning` and fires once per process.
  - So the boot heal and the session monitor go dark with a single WARNING, no ERROR and no Sentry capture.
  - The validation pair, under D-05, gets ERROR plus Sentry for the same misconfiguration.
  - The job pair is the more important of the two terminals, and it is the quieter one.

**Failure scenario:**
1. An operator swaps `MT5_GATEWAY_HOST` to the gateway's public TCP-proxy host while debugging connectivity.
2. Every `sync_trades`, `derive_broker_dailies`, holdings and backfill job for every MT5 key fails three times per
   enqueue.
3. Users are told the retries were exhausted.
4. Heal stops with one WARNING line, and nobody is paged.

Latent today: the configured host is private.

**Fix:**
```python
# job_worker.classify_exception, beside the Mt5GatewayMisconfigured arm:
if isinstance(exc, Mt5GatewayHostNotPrivate):
    return ("permanent", str(exc))  # fixed message, names no host/port
```
- Make `_make_mt5_session` read through `read_env_gateway_endpoint()`. A `None` should raise
  `Mt5GatewayMisconfigured` (or a dedicated permanent type), so there is one reader and one strip.
- Raise the session-path refusal for a non-private host to ERROR with the D-05 alert shape.

### WR-02: The D-05 worker refusal is a bare `RuntimeError`, which is the A3 anti-pattern `Mt5GatewayMisconfigured` was created to remove

**File:** `analytics-service/services/ingestion/mt5.py:183-194`

**Confidence:** 7/10

**Issue:**
- With `MT5_VALIDATION_GATEWAY_*` unset, malformed or non-private, `Mt5Adapter.validate` fires the D-05 alert and
  raises `RuntimeError`.
- `classify_exception` has no arm for `RuntimeError`, so it returns `unknown`. The job retries up to
  `max_attempts`, and each attempt re-runs the adapter and fires the D-05 ERROR line again.
- The arm comment at `job_worker.py`, around lines 762-770, describes this exact case: a bare RuntimeError "fell
  through to the catch-all … and `unknown` RETRIES … for a fault that can never clear".
- `mt5_probe.py`'s module docstring names the same fix (A3).
- The sync validate-only arm in `routers/process_key.py`, around line 1056, catches only `Mt5SessionAbandoned`.
  `main.py` registers no generic `Exception` handler, so on that path the refusal is an unstructured 500 instead
  of the `MT5_GATEWAY_UNCONFIGURED` contract D-05 names. That path is currently dormant: the wizard uses
  `/validate-key`.
- The trigger is realistic. D-05 itself says every validation is refused until the founder sets the new pair, so
  the first deploy with the pair unset hits this on every queued MT5 validation.

**Failure scenario:**
1. The routing change deploys before the founder sets `MT5_VALIDATION_GATEWAY_HOST`.
2. Each queued MT5 key validation fails as `unknown`, retries twice more, and ends `failed_final` with "automatic
   retries exhausted" copy instead of a permanent operator-fault verdict.

**Fix:** Raise `Mt5GatewayMisconfigured` with a curated detail added to the `curated_gateway_detail` allow-list
(for example "the MT5 validation gateway is not configured; this needs an operator"). It then lands in the
existing permanent arm. Keep the D-05 alert call before the raise.

### WR-03: The worker park's ceiling is shorter than the two bounded round-trips a park makes, but the comment says the inner bound fires first (W-1 residual)

**File:** `analytics-service/services/ingestion/mt5.py:480-506` (the comment at 480-482, the ceiling at 503, the `ceiling` arm at 506), with `services/mt5_client.py` `Mt5Client.login` (around lines 2085-2115)

**Confidence:** 6/10

**Issue:**
- `Mt5Client.login` makes two separate rpyc round-trips: `initialize(...)`, then `login(...)`.
- On the worker client each is bounded by `MT5_REQUEST_TIMEOUT_S` (30 s), so a park can legitimately take up to
  about 60 s.
- The park's ceiling is `_MT5_PROBE_TIMEOUT_S` (35 s).
- The comment claims the ceiling "already has the inner-rpyc-bound-fires-first ordering". For a single round-trip
  that is true; for the park it is not.
- When the ceiling fires with the park's second round-trip on the wire:
  1. `client.close()` runs concurrently on the same rpyc connection.
  2. The lease then releases.
  3. The next validation can log the terminal in while the abandoned house `login` is still in flight.
- The epoch guard keeps the holder record honest. It does not stop the in-flight RPC from switching the terminal.
- The wizard site documents the equivalent residual (`routers/exchange.py:164-170`); the worker site documents
  the opposite.
- The probe has the same multi-round-trip property under the same ceiling. The park adds nothing new in kind, but
  it adds an occurrence after every validation.

**Failure scenario:**
1. A slow broker or Wine `initialize` takes 25 s and the house `login` takes 15 s.
2. The ceiling fires at 35 s and the alert reads `ceiling`.
3. The lease releases, and the next queued validation logs in the user's account.
4. The abandoned house login lands after it.
5. The next probe's POST bracket sees the house account, raises `Mt5AccountMismatchError`, and fails a valid key
   as a transient error.
6. The house login also overwrites that user's session mid-probe.

**Fix:**
- Size the worker park ceiling as `2 * MT5_REQUEST_TIMEOUT_S + margin`, derived rather than hand-set. The worker
  has no client budget, so this costs nothing user-facing.
- Or correct the comment and state the residual exactly as the wizard site does.
- Apply the same derivation at the wizard (`_MT5_PARK_MIN_BUDGET_S` is one stage, 60 s, against 2 × 55 s), or keep
  that residual documented.

### WR-04: A park glitch is downgraded to WARNING even when the validation itself was clean, which is broader than the founder's decision

**File:** `analytics-service/services/mt5_probe.py:557-573` (`_is_park_bridge_glitch`), `:634-635` (the arm in `park_on_house_account`)

**Confidence:** 5/10

**Issue:**
- **What the founder was shown (CONTEXT, "Park alert level"):** "A park that fails for the **same** bridge-glitch
  reason **the validation hit** logs a WARNING only… Every other skip or failure still pages."
- **What the implementation does:** it downgrades any park failure in the glitch class, whether or not the
  validation hit a glitch.
  - The park receives no information about how the validation ended.
  - A validation that completed cleanly (for example, it detected a master password and returned the refusal) and
    is followed by a glitch-class park failure produces only a WARNING, with no Sentry capture.
- **Why it matters:**
  - In that case the trade-capable session stays on the validation terminal, which is the exact exposure D-07
    part 2 exists to contain.
  - A recurring glitch-class failure of the house login never pages anyone, however often it repeats.
  - The SUMMARY records the broader reading ("a park that fails on a bridge glitch logs WARNING"). That wording is
    not the text the founder answered.

**Failure scenario:**
1. A user submits their master password.
2. The probe classifies it, and the wizard rejects it.
3. The park's house `login` returns a transient-class code because the house server is intermittently slow.
4. A WARNING is logged and nothing is captured.
5. The master-password session sits on the validation terminal until the next validation. This repeats for every
   validation that day, and no one is paged.

**Fix:**
- Pass the validation's own outcome into the park, for example `validation_hit_glitch: bool` set by the
  transient-upstream arm.
- Downgrade to WARNING only when both the validation and the park hit the glitch class.
- Or put the broader reading back to the founder as an explicit decision.

### WR-05: Nothing refuses a validation endpoint that is the job terminal, so a misconfiguration silently restores the eviction

**File:** `analytics-service/services/mt5_relogin.py:868-928` (`read_env_validation_gateway_endpoint`)

**Confidence:** 5/10

**Issue:**
- D-05's premise is "never fall back to the jobs terminal". The code enforces this by name only: it never reads
  the job pair.
- If `MT5_VALIDATION_GATEWAY_HOST/PORT` is set to the same host and port as `MT5_GATEWAY_HOST/PORT`, every
  validation leases and logs into the job terminal again. Copying the job pair is a plausible way to clear D-05's
  refusal quickly.
- The park then also logs the house account into the job terminal after every validation.
- If the pair is a different spelling of the same terminal (another hostname, or a trailing-dot or case variant),
  `mt5_terminal_key` yields two different keys. The validation and job leases then do not even serialize with each
  other: the MT5CONC-02 / Pitfall 2 class, with two callers on one terminal.
- No alert fires in either case.

**Failure scenario:**
1. The founder, under time pressure after D-05 starts refusing, sets the validation pair to the job pair's values.
2. Onboarding logins switch the live job terminal again with no signal.
3. If the pair is spelled differently, they also race the derive job on the same terminal.

**Fix:**
- In `read_env_validation_gateway_endpoint`, compare the normalized `(host.lower().rstrip("."), port)` against
  `read_env_gateway_endpoint()`.
- On equality, return `None` with its own log-once reason, so D-05's refuse-and-alert path fires.
- State in the docstring that an alias of the same terminal cannot be fully detected from the name, and that N-01
  remains the infrastructure check.
