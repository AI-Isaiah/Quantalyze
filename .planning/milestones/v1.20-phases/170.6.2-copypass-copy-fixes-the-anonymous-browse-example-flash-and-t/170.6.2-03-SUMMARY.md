# Phase 170.6.2 Plan 03: Compute Jobs Kind filter lists every present kind Summary

The admin Compute Jobs Kind select now lists "All kinds" plus every registered kind that has at least one job (for example `derive_allocator_equity`), read through a gated `?facets=kinds` branch of the existing route; the hardcoded three-kind list is gone.

## What changed

- **Route** (`route.ts`): after the unchanged same-origin guard and `isAdminUser` gate, `facets=kinds` creates the same service-role client, reads `compute_job_kinds` (`select("name")`), and probes `compute_jobs_admin` once per registered name (`select("id").eq("kind", name).limit(1)`, in parallel). It returns `{ kinds }` sorted ascending with no-store headers. Any registry or probe error is a generic 500 `Failed to fetch compute job kinds` with the raw error logged server-side. The page path is byte-identical; no migration; nothing under `supabase/` changed.
- **Component** (`ComputeJobsTable.tsx`): `KIND_OPTIONS` removed (`grep -ac KIND_OPTIONS` prints 0). `ALL_KINDS_OPTION` stays. `fetchKinds` validates the body is `{ kinds: string[] }`. Options are `All kinds` plus the union of fetched kinds and the current `kindFilter`, de-duplicated and sorted, so the selected kind never drops. A failed, rejected or malformed read KEEPS the previous good list, logs its cause with `console.error`, and shows `Could not load the job kinds.` (with ` (HTTP <status>)` when the failure had a status; `data-testid="compute-jobs-kinds-error"`, `role="status"`); a later good read clears it. *(Superseded 2026-10-13, review SFH-1: this line first said a failure "clears the list". It no longer does. A request-sequence ref also drops any response that is not from the latest facet read, so an older response landing late cannot overwrite a newer one.)*
