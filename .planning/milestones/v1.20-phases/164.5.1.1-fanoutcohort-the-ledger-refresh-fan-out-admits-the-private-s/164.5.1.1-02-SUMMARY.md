## Decisions Made

1. **A third COULD-NOT-MEASURE guard, beyond the two the plan named.** See deviation 1.
2. **The arm reads its own comment-stripped body rather than borrowing arm 0's `v_body`.** Arm 0
   reads the same function and strips it the same way, so the value would have been identical — but
   an arm that borrows another arm's variable inherits that arm's silence when the READ is the thing
   that broke, and arm Q's COULD-NOT-MEASURE diagnostics have to be raised by arm Q.
3. **The search is scoped to the EXTRACTED conjunct list, never the whole body.** A status name
   occurs in that body for unrelated reasons — the in-flight guard's `cj2.status IN (…)` set is four
   JOB statuses — so a whole-body search would pass for the wrong reason and could never fail.
4. **Chronological placement for the apply-list entry** rather than "immediately after the core
   fixture". Both are correct (the migration only `ALTER`s), and chronological is the property the
   rest of the list already has.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] A third unmeasurable state would have passed silently**

- **Found during:** Task 1
- **Issue:** The plan prescribed two COULD-NOT-MEASURE raises — a NULL constraint definition, and a
  lifecycle conjunct the arm cannot locate. A third unmeasurable state exists and neither covers it:
  a constraint definition that is present and non-NULL but from which the extraction parses ZERO
  quoted literals. The loop would then run zero times, assert nothing, and the arm would pass. That
  is precisely the "an empty scan and a clean scan are identical to every numeric test" failure the
  plan's own prohibition names, reached through a door the two prescribed guards leave open. It is
  not hypothetical: it is the shape the arm would take if `strategies.status` were ever migrated to
  an enum-backed domain, which is the very thing RESEARCH.md wrongly assumed it already was.
- **Fix:** A `v_checked` counter incremented for every non-excluded status the loop asserts, and a
  third raise when it is still 0 at the end — with its own distinct message naming the constraint
  definition it could not parse. The acceptance criterion asked for two distinct messages; three is
  a strict superset of that.
- **Files modified:** `supabase/tests/test_ledger_refresh_fanout.sql`
- **Verification:** the arm is RED under its own twin with all three guards in place (RUN 2,
  `first failure: Q`), and GREEN restored (RUNs 1 and 3) — so the added guard does not make the arm
  unfalsifiable in either direction. `lint-sql-gates` 0 findings; full corpus 394/394, no defects.
- **Committed in:** `b9169d02`
