## Summary

This phase widens exactly one SQL predicate — `s.status IN ('published','pending_review')` inside
`enqueue_ledger_refresh_for_strategies()` — to admit `private`. The function's candidate CTE,
its GRANT/REVOKE footer, and its apply-time verification block all live in
`supabase/migrations/20260911130000_ledger_fanout_grantees_and_dormancy.sql`, confirmed to be the
**latest** definition in the migration chain (no later migration touches the function name).
The companion function `enqueue_ledger_composite_refresh()` in the **same file** carries no status
conjunct at all — it excludes on `is_composite = TRUE` only — so "one site" in CONTEXT.md's
decision is a measured fact about production code, not a simplification.

Two things the CONTEXT.md decisions do **not** mention, found while reading the gate corpus
directly, change the shape of the plan: (1) **two test files**, not the production function alone,
hard-code the same `('published','pending_review')` literal as a *foreign-candidate precondition*
guard (`test_ledger_refresh_fanout.sql:425` and `test_ledger_refresh_composite_arm.sql:434`) — both
need the literal widened to `private` or they silently stop detecting a foreign private candidate
polluting the global per-tick/per-venue arms (G1, G2); and (2) `ALLOWED_STRATEGY_STATUSES`
(`cron.py:148`, unchanged in this phase per the Decisions) gates the **daily trade-sync cron**
(`POST /cron-sync`), not the ledger-refresh fan-out — meaning a `private` strategy admitted to the
refresh fan-out may be refreshed against trade data that a separate, unrelated cron job has never
been syncing, a distinct risk from anything CONTEXT.md's "blast radius" paragraph names.

The migration house style for this exact function is unusually heavy (documented, in-repo,
apply-time `DO $verify$` blocks with `RAISE EXCEPTION` on any missing invariant, `aclexplode`-based
GRANT re-derivation, and a VAC-04 body-hash acknowledgement) — and the immediately preceding
migration (`20260911130000`) is itself the best and most current precedent to imitate, since it
CREATE-OR-REPLACEd this exact function five days ago.

**Primary recommendation:** one forward migration, `CREATE OR REPLACE FUNCTION
public.enqueue_ledger_refresh_for_strategies()` re-based on the CURRENT committed snapshot
(`supabase/schema/functions/enqueue_ledger_refresh_for_strategies.sql`, which is `20260911130000`'s
body verbatim), changing only the status literal; carry the VAC-04 body-hash ack, the apply-time
verification block, and the REVOKE-ALL/no-GRANT footer forward unmodified in shape. Extend, do not
duplicate, `test_ledger_refresh_fanout.sql` with a new `private`-admits arm and widen its own
foreign-candidate precondition in the same edit. Add the cohort-agreement arm as a new, separate
gate proving `ledger_refresh_staleness ∖ {statuses the fan-out admits}` is empty for every status
currently in `strategies_status_check`.

## The house style for a forward migration re-defining a SECURITY DEFINER function

`[VERIFIED: supabase/migrations/20260911130000_ledger_fanout_grantees_and_dormancy.sql]` — read in
full (1755 lines). This file **is itself the immediate precedent** for the migration this phase
writes, since it is the last thing to touch this exact function. Its shape, to imitate:

1. **Naming/timestamp:** `YYYYMMDDHHMMSS_snake_case_description.sql` under `supabase/migrations/`.
   No enforced increment size observed (`120000`, `130000`, `140000` seen), but same-day files are
   spaced by whole hours-worth of the six-digit suffix.
2. **Header comment block** states: the phase/plan/ROADMAP-criterion that authorizes the change, the
   OPS warning that merging auto-applies to shared TEST then PROD, and an explicit "FORWARD
   MIGRATION, NOT AN EDIT" statement naming which prior migration is being re-based rather than
   rewritten.
3. **VAC-04 acknowledgement block** (`[VERIFIED: 20260911130000:44-101]`): before the `CREATE OR
   REPLACE`, the header documents having run
   `node scripts/sql-body-normalize.mjs --diff-bodies supabase/schema/functions/<fn>.sql <origin/main's copy>`
   and records two `prod-body-ack: <sha256>` comment lines — one per function body being replaced —
   where the hash is the `live` column of `--diff-bodies` (PROD's *current* body), **never** the
   `--hash` of the snapshot file (the header explicitly warns this distinction is load-bearing: a
   whole-file digest would read as an ack to a human and be invisible to the gate). This ack is what
   the VAC-04 CI job (repo-vs-PROD function-body diff, run in `migration-drift-check.yml` on
   migration PRs) reads.
4. **`CREATE OR REPLACE FUNCTION ... SECURITY DEFINER SET search_path = public, pg_catalog`** — the
   body is re-based on the **committed snapshot** under `supabase/schema/functions/<fn>.sql` (not on
   the migration file that first created it), with every edit enumerated in a "RE-BASE DISCIPLINE"
   comment block naming exactly what changed line-by-line.
5. **REVOKE ALL, re-issued explicitly**, even though `CREATE OR REPLACE FUNCTION` in PostgreSQL
   preserves existing grants on the same OID — this repo's own header explains why: a prior migration
   (`20260907130000`) revoked three of four roles and left `service_role` holding EXECUTE because its
   own check only probed two roles; `20260911130000` re-issues the REVOKE against the full set
   (`PUBLIC, anon, authenticated, service_role`) as a correction. **For this phase's migration, no
   grant/revoke change is needed** — only the status literal changes, and the existing REVOKE ALL /
   no-GRANT-follows shape (owner-only EXECUTE) is unaffected by a `CREATE OR REPLACE` that keeps the
   same signature — but the REVOKE statement should still be re-issued in the new migration, matching
   this repo's established idiom of never relying on CREATE OR REPLACE's grant-preservation silently.
6. **Apply-time verification block**, `DO $verify$ ... END $verify$;` immediately before `COMMIT;`
   (`[VERIFIED: 20260911130000:1349-1748]`, verification statements spanning many `IF ... THEN RAISE
   EXCEPTION` checks). This block uses `pg_get_functiondef(...)` and `position(needle IN v_def)` to
   assert specific fragments of the new body are present/absent, and `aclexplode(COALESCE(p.proacl,
   acldefault(...)))` to assert the EXECUTE grantee set is *exactly* the function owner. **This
   verification reads catalogue metadata only (`pg_proc`, `pg_class.relacl`) — never application
   table rows** — which is the property that keeps it safe on shared TEST (see §"Shared-TEST escape
   hatch" below).
7. **`COMMIT;`** at the very end, inside a `BEGIN; ... COMMIT;` wrapper spanning the whole file.

  SELECT count(*) INTO v_foreign
    FROM public.ledger_refresh_staleness lrs
    JOIN public.strategies s ON s.id = lrs.strategy_id
   WHERE lrs.is_stale
     AND s.status IN ('published', 'pending_review');

## Shared-TEST escape hatch — what this means for this migration

`[CITED: CLAUDE.md, "Currency 2026-09-09 — what shared TEST IS now" section]` TEST's `public` schema
is a schema-only restore of PROD's catalogue (`0 data statements`), so `strategies`, `api_keys`, and
`compute_jobs` on shared TEST hold **no** pre-existing rows beyond whatever CI itself has written
since the restore — certainly no committed `private`-status strategy exists there by default.

**What this means concretely for this phase's migration:** the migration's own apply-time
verification block (the `DO $verify$ ... END $verify$;` pattern, confirmed above to read only
`pg_proc`/`pg_class` catalogue metadata via `pg_get_functiondef` and `aclexplode`) is **safe** — it
asserts things about the function's own text and privilege set, never about row counts or specific
data in `strategies`/`api_keys`. **The trap this phase must avoid:** do not add any verification
statement to the migration itself that counts or inspects `strategies` rows (e.g., "assert N
strategies with status='private' now qualify") — any such check would read `0` on shared TEST (no
private strategies exist there) and could either false-fail (if written to expect `>0`) or silently
pass vacuously (if written to expect `>=0`), neither of which the project's own escape-hatch entry
considers safe. **The shape that avoids the trap:** keep the migration's own in-transaction
verification scoped to catalogue metadata only (as the current house style already does), and put
all data-dependent proof — the "a private strategy IS selected" assertion — in the **gate file**
(`test_ledger_refresh_fanout.sql`, which builds its own fixtures and runs against a throwaway pg-lane,
not shared TEST) rather than in the migration's apply-time block. This is exactly the separation the
existing `20260911130000` migration already follows (its verify block never touches
`strategies`/`api_keys` row data), so no departure from house style is required — only continued
discipline.

## Common Pitfalls

### Pitfall 1: Editing only the production function's literal
**What goes wrong:** The migration widens `enqueue_ledger_refresh_for_strategies()` but the two
foreign-candidate-precondition literals in the gate files (`test_ledger_refresh_fanout.sql:425`,
`test_ledger_refresh_composite_arm.sql:434`) are left at `('published', 'pending_review')`.
**Why it happens:** CONTEXT.md's "one site" framing refers to production code, and is correct about
production code — but the gate corpus independently duplicates the same literal for an unrelated
purpose (precondition guarding, not candidate selection).
**How to avoid:** Grep both test files for the literal string before considering the edit complete;
widen both preconditions in the same PR.
**Warning signs:** Arms G1/G2 (the global per-tick/per-venue bound arms) producing counts that don't
match a fresh derivation if a foreign private strategy is ever committed on shared TEST.

### Pitfall 2: Pointing new RED-UNDER-M twins at the wrong migration file
**What goes wrong:** A new edit-kind twin targets `20260911130000...sql` instead of this phase's new
migration file; since the new file's `CREATE OR REPLACE` runs *after* `20260911130000`'s in the gate's
apply list, the twin mutates a body that gets overwritten before any assertion runs, and the arm
reports `no-red`.
**Why it happens:** copy-pasting an existing twin's `file` field without updating it.
**How to avoid:** Follow the file's own documented rule (quoted above): every edit-kind twin must name
the LAST migration in the apply list that defines the function, which after this phase is the new
migration file, not `20260911130000`.
**Warning signs:** `no-red` in the mutation runner's own output for the new arm.

### Pitfall 3: Writing the cohort-agreement arm against `enum_range` when status is a CHECK constraint
**What goes wrong:** `SELECT unnest(enum_range(NULL::strategies_status_enum))` fails to compile /
returns nothing if `strategies.status` is `TEXT` with a `CHECK` constraint rather than a native
`ENUM` type.
**Why it happens:** The name `strategies_status_check` (Postgres's default naming for a `CHECK`
constraint) was not independently re-verified this session as a type vs. constraint distinction.
**How to avoid:** `SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname =
'strategies_status_check'` first, and derive the literal list from its text if it is a `CHECK`, or
confirm the type name if it is an `ENUM`, before committing the arm's SQL shape to a plan.
**Warning signs:** A `type "strategies_status_enum" does not exist` error at gate-apply time.
