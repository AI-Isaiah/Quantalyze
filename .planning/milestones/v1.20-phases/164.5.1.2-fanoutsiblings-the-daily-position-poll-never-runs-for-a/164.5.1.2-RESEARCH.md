## §1. The PROD read — design it exactly, because the plan pastes it verbatim

### What it answers

Per D-01: does a `private`-status strategy share an `api_key_id` with a sibling strategy whose
status IS in `ALLOWED_STRATEGY_STATUSES` (`{draft, pending_review, published}`)? This determines
whether the KEY behind a `private` strategy is synced at all today, which sets the scope of harm
the constant's gap causes and whether D-03's cursor-lie is currently live on any real key.

### Schema facts this read depends on, verified this session

- `strategies.api_key_id` is the FK: `JOIN api_keys ak ON ak.id = s.api_key_id`
  `[VERIFIED: supabase/schema/functions/enqueue_poll_positions_for_all_strategies.sql:42]`
  (canonical current body, replayed from migrations — this file states at its own header
  `-- source migration: 20260412094449_compute_jobs_admin_and_defer.sql`, and a repo-wide grep for
  `CREATE OR REPLACE FUNCTION enqueue_poll_positions_for_all_strategies` returns exactly that one
  migration — no later migration redefines this function).
- The status domain is five values, not four:
  `CHECK (status IN ('draft', 'pending_review', 'published', 'archived', 'private'))`
  `[VERIFIED: supabase/migrations/20260716130000_strategies_status_private.sql:59-61]`
  — added by CONTRIB-02 (Phase 110), 2026-07-16.
- `ALLOWED_STRATEGY_STATUSES = {"draft", "pending_review", "published"}` and its sole reader,
  `and e.get("status") in ALLOWED_STRATEGY_STATUSES`
  `[VERIFIED: analytics-service/routers/cron.py:150,660]`.

### The read itself

**Statement 1 — the marker, run FIRST, unconditionally.** A NULL answer stops the session; do not
proceed on a guess.

```sql
SELECT shobj_description(oid, 'pg_database') AS which_database
  FROM pg_database WHERE datname = current_database();
```

**Statement 2 — counts and shapes only, never key material, never a strategy id, never a host.**

```sql
WITH private_with_key AS (
  SELECT s.id, s.api_key_id
  FROM strategies s
  WHERE s.status = 'private' AND s.api_key_id IS NOT NULL
),
sibling_check AS (
  SELECT
    p.id AS private_id,
    EXISTS (
      SELECT 1 FROM strategies sib
      WHERE sib.api_key_id = p.api_key_id
        AND sib.id <> p.id
        AND sib.status IN ('draft', 'pending_review', 'published')
    ) AS has_in_set_sibling
  FROM private_with_key p
)
SELECT
  count(*)                                            AS private_strategies_with_key,
  count(*) FILTER (WHERE has_in_set_sibling)          AS with_in_set_sibling,
  count(*) FILTER (WHERE NOT has_in_set_sibling)       AS without_in_set_sibling
FROM sibling_check;
```

**Statement 3 — the strategies without a key at all (structurally can never be synced by ANY
widening of this constant, so they should not count against the constant's harm).**

```sql
SELECT
  count(*) FILTER (WHERE api_key_id IS NULL)     AS private_no_key,
  count(*) FILTER (WHERE api_key_id IS NOT NULL) AS private_with_key
FROM strategies WHERE status = 'private';
```

### What each possible answer implies — written BEFORE the read, so it cannot be rationalised after

- **If `without_in_set_sibling = 0`** (every `private` strategy with a key shares that key with an
  in-set sibling): the constant's gap does NOT currently starve any key entirely — every such key
  is already being synced (because the sibling's id is in `strategy_ids`), so D-03's cursor-lie
  path (`strategy_ids` empty due to the filter) is **not live today for any of these keys**. The
  `private` strategy's OWN `trades` rows still never populate (its own id is still excluded from
  `strategy_ids` — this is unaffected by sibling status, per D-01's structural point). **Verdict
  lean:** the constant's harm is narrower than the TODOS entry's framing suggested; widening it
  would only newly sync the `private` strategy's OWN rows, not "unstarve" any currently-dark key.
  Any widening decision should be evaluated on that narrower basis, not on "the key is never
  synced" (which would be false).
- **If `without_in_set_sibling > 0`** (at least one `private` strategy's key has NO in-set
  sibling): for those specific strategies, the key is genuinely never synced by any path today, and
  D-03's cursor-lie is live and reachable RIGHT NOW every time that key's owner triggers (or would
  trigger) a sync tick with the venue returning trades. **Verdict lean:** the constant's stated
  harm is real and current for at least this subset; this raises (without settling) the case for
  widening `ALLOWED_STRATEGY_STATUSES`, and per Success Criterion 3 any such widening must state
  what it does to the cursor-advance path.
- **If `private_with_key = 0`** (no `private` strategy has a key at all): the entire
  `ALLOWED_STRATEGY_STATUSES` question is moot for the current `private` cohort — nothing to sync
  regardless of the constant. (Unlikely: PROD's 2026-09-17 measurement already shows `private:
  strategies=6 … ever_synced=2`, which requires at least 2 of the 6 to have had a working key at
  some point — though note that count could also be explained by these 2 having been synced BEFORE
  their status transitioned to `private`, which the sibling read does not distinguish from a
  currently-shared-key explanation. If the founder wants that distinguished, `ever_synced` would
  need a timestamp comparison against the status-transition time, which is a SEPARATE read not
  designed here — do not conflate the two.)

### How to record the reading

Model the PROD session file byte-for-byte on `164.5.1.1-04-PLAN.md` Task 3's idiom (already proven
in this repo): a `checkpoint:human-action` task, `<action>` states there is no CLI path from this

ready-made pattern to re-use, adapted to this phase's file name.

## §2. The `last_sync_at` cursor advance — traced to the statement level

### The exact mechanism

```
        synced_count = sum(per_strategy_stored.values())
        any_trades_to_store = bool(trades) and bool(strategy_ids)
        should_advance_cursor = (not any_trades_to_store) or synced_count > 0
```
`[VERIFIED: analytics-service/routers/cron.py:421-423]`

```
        update_data: dict[str, Any] = {}
        if should_advance_cursor:
            update_data["last_sync_at"] = datetime.now(timezone.utc).isoformat()
```
`[VERIFIED: analytics-service/routers/cron.py:425-427]`

`strategy_ids` here is `key_row.get("strategy_ids")`
`[VERIFIED: analytics-service/routers/cron.py:168]` — `strategy_ids: list[str] = list(key_row.get("strategy_ids") or [])` — which was built exactly once, upstream in the `cron_sync` handler, by filtering the PostgREST-embedded `strategies` rows through `ALLOWED_STRATEGY_STATUSES` (§ quote already given above, `cron.py:650-660`).

### Reachability — bounded to the two clauses of `any_trades_to_store`, both read verbatim above

`any_trades_to_store = bool(trades) and bool(strategy_ids)`. This is False, and the cursor
therefore advances unconditionally (`not any_trades_to_store` is True regardless of
`synced_count`), whenever **either** conjunct is falsy:

1. **`bool(trades)` is False** — the venue genuinely returned no trades in the window. This is the
   INTENDED "idle tick, nothing to store" case the code comment documents (`# … OR when there were
   no trades to store at all (idle tick)`, `[VERIFIED: analytics-service/routers/cron.py:409-411]`
   quoting the comment's own words). **Not a defect.**
2. **`bool(strategy_ids)` is False** — no strategy on this key is currently eligible. Two distinct
   causes converge here, and CONTEXT.md's framing ("via the status filter") only names the first:
   - **(2a) every linked strategy failed the `ALLOWED_STRATEGY_STATUSES` filter** — the case this
     phase's TODOS entry names (an owner-only/`private` key with no in-set sibling, or an
     all-archived key).
   - **(2b) the key has literally zero linked strategies at all** — a structural case independent
     of any lifecycle status: `strategy_ids` is built by flattening the PostgREST `strategies`
     embed (`[VERIFIED: analytics-service/routers/cron.py:637-645]`, the loop building `entries`
     from `strategy_rel`), and an `api_keys` row whose embed returns nothing produces `entries=[]`
     → `strategy_ids=[]` by the same code path, with no status ever evaluated. Whether this case
     occurs in PROD (an orphan key with zero strategies) is not established by this research and
     is a code-reachable path, not a measured one — `[ASSUMED]` that it is rare/structural rather
     than a live class; flag for the founder if the plan wants it distinguished in the PROD read.

**When trades ARE non-empty and `strategy_ids` is empty (case 2), the defect is genuine and
distinct from the idle-tick case:** the venue held real trades in the sync window, and they are
permanently skipped — the cursor moves past them and the next tick's `since_ms` starts after them,
so they are never refetched. This is the `last_sync_at` LIES class on a path distinct from the
already-fixed C-0198 case (§ below).

**What C-0198 already fixed, and why it does NOT cover this path.** `TestC0198CursorOnlyAdvancesWhenStored` (`analytics-service/tests/test_cron_router.py:2465-2542`) pins the case where `strategy_ids` is NON-empty but every `sync_trades` RPC call fails (`synced_count == 0`) — there, `any_trades_to_store` is True (both conjuncts hold) and `should_advance_cursor` correctly becomes False via the `synced_count > 0` disjunct, so the cursor correctly holds. **This is the opposite branch from the defect in case 2**, where `any_trades_to_store` is False from the START because `strategy_ids` itself is empty — `synced_count > 0` is never even consulted. `[VERIFIED: analytics-service/tests/test_cron_router.py:552-620,2477-2542]` — grepped and read; no existing test in this file constructs `strategy_ids=[]` with non-empty `fetch_all_trades`.

### A ready-made, calibratable oracle for this defect (Wave-0 gap, see Validation Architecture below)

`_make_key_row(strategy_ids=[])` `[VERIFIED: analytics-service/tests/test_cron_router.py:91-109]`
already supports constructing exactly this fixture. A new test in the same file, in the same class
(`TestC0198CursorOnlyAdvancesWhenStored`) or a sibling class, calling `_sync_single_key` directly
with `strategy_ids=[]` and `fetch_all_trades` mocked to return non-empty trades, then asserting on
`api_keys` UPDATE payloads (same assertion shape as the two existing C-0198 tests) is directly
buildable from patterns already in the file. This clears the anti-vacuity bar (data-integrity,
per the standing repo rule) because it pins real cursor-write behavior, not a comment or an AST

## §4. What would make the poll-positions refusal (D-02) falsifiable later

**The precedent, in detail.** `164.5.1.1-04-PLAN.md` Task 3's automated verify step
(`[VERIFIED: .planning/phases/164.5.1.1-fanoutcohort-the-ledger-refresh-fan-out-admits-the-private-s/164.5.1.1-04-PLAN.md:433-434]`) is a **polarity-aware negation grep** over a named, closed list of
produced artifacts (never `*-PLAN.md`, `-CONTEXT.md`, `-RESEARCH.md`, `-PATTERNS.md` or
`-VALIDATION.md` — those carry the mandated negations and would make the check unable to ever
return 0). It scans for a regex matching "composite … fixed/resolved/refreshed/addressed by this
phase" with no negation word on the same line, and fails loud on any hit, printing the offending
line. It was calibrated BOTH directions (2026-09-17): the real negations give 0, two constructed
positive claims give 2, exit 1. This is the exact idiom to reuse for D-02: a check scanning this
phase's own SUMMARY/TODOS/ROADMAP/PROD-SESSION artifacts for an unnegated claim that the
poll-positions predicate was "widened," "fixed," or "completed" here, which would catch a future
editor who "finishes" the widening without re-measuring the second conjunct.

**But per this repo's own anti-vacuity threshold** (MEMORY: *"a vacuous gate over an AST
predicate/log wording/comment/unread counter is FIX-OR-DROP, never a blocker … money-math oracles
pin ECONOMICS not the impl's own formula"*), a comment-polarity grep over planning prose is NOT
itself a data-integrity or user-facing gate — it guards against mis-STATEMENT, not against a real
regression in behavior. It is a reasonable low-cost addition (mirrors 164.5.1.1's own precedent
exactly) but should not be treated as satisfying the anti-vacuity bar on its own.

**The behavior-pinning alternative, and it is currently ABSENT from the gate corpus.** Searched
`supabase/tests/*.sql` for any file exercising `enqueue_poll_positions_for_all_strategies` — the
only three files matching the substring `poll_positions` are `test_retention_orphaned_running.sql`,
`test_sync_status_supersede_failed_per_kind.sql`, `test_sync_status_preserves_warnings.sql`, none of
which test this function's candidate-selection `WHERE` clause. **No SQL gate today pins that a
`published` strategy passing both conjuncts IS selected, or that a `private` strategy (passing

Postgres function against real rows, not a wording grep), so it clears the anti-vacuity bar. If

## §5. Blast radius if `ALLOWED_STRATEGY_STATUSES` is ever widened to admit `private`

Traced mechanically, not to recommend the widening (CONTEXT.md's D-01 explicitly defers that
decision to the PROD read in §1):

1. **`/cron-sync`'s `strategy_ids` gains the `private` strategy's own id** for any key where it
   appears `[VERIFIED: analytics-service/routers/cron.py:650-660]` (the filter is the only gate).
2. **That id now receives its own `sync_trades` RPC call** in the per-strategy loop
   `[VERIFIED: analytics-service/routers/cron.py:359-407]` — trades land in `trades` for the
   `private` strategy's own row for the first time.
3. **If `stored > 0` for that id, it enters `recompute_strategy_ids`**
   `[VERIFIED: analytics-service/routers/cron.py:473-475]`, `sid for sid, stored in
   per_strategy_stored.items() if stored > 0` — and an `enqueue_compute_job('derive_broker_dailies',
   …)` follow-on fires for it (same mechanism the comment block at `cron.py:441-472` documents).
   Per D-04, that job does NOT read `trades` itself — it re-crawls the venue independently
   (`job_worker.py:2624`) — so this step mainly means the `private` strategy starts appearing in
   the daily recompute cascade going forward, not that this one sync populates its dailies.
4. **The poll-positions second conjunct (`EXISTS sync_trades in 30 days`) becomes satisfiable for
   `private` strategies for the first time** — but **the poll-positions FIRST conjunct
   (`s.status IN ('published', 'pending_review')`) is UNCHANGED by this widening**
   `[VERIFIED: supabase/schema/functions/enqueue_poll_positions_for_all_strategies.sql:44]` and
   D-02 refuses to widen it. **So this widening alone does NOT cause `private` strategies to start
   being polled** — both conjuncts would need to be widened together for that, and D-02 has
   already refused the poll-side half. This is a useful, previously-unstated finding: satisfying
   the constant does not chain into satisfying the poll predicate.
5. **The guard's own stated harm** — *"syncing into an archived or deleted strategy can overwrite
   its submission snapshot and flip its approval-gate verdict between Submit and Approve"*
   `[VERIFIED: analytics-service/routers/cron.py:146-149]` — names `archived` and `deleted` (not
   `published`/`draft`/`pending_review`/`private`). The approval-gate mechanism this refers to is
   `checkStrategyGate` in the admin strategy-review route, which is consulted only for strategies
   in the admin review queue, filtered `[VERIFIED: src/app/(dashboard)/admin/page.tsx:40]`
   `.eq("status", "pending_review")`. A `private` strategy never enters that queue — its status is
   terminal and reached outside the publish-review flow (CONTRIB-02's own migration comment states
   the wizard "must finalize to an owner-only status that is NEVER a publish candidate,"
   `[VERIFIED: supabase/migrations/20260716130000_strategies_status_private.sql:6-9]`). **So the
   specific harm the constant's comment warns about does not appear to apply to `private`** — this
   is a code-grounded inference, not a measurement, and is `[ASSUMED]` in the sense that no test or
   PROD reading directly confirms "a `private` strategy's approval-gate verdict is unaffected by
   new trades," because `private` strategies have no approval-gate verdict to flip. Flag this
   explicitly to the founder if criterion 3 of the phase's success criteria is read strictly — the
   comment's literal harm does not transfer, but the constant's ONE declaration / ONE reader shape
   means any change to it is a change to the shared guard, and the guard's original two excluded
   statuses (`archived`, and the fifth value not in the CHECK constraint at all — `deleted`, which
   does not appear as a live status value per the CHECK read in §1) still apply unchanged.

## Common Pitfalls

### Pitfall 1: Reading the sibling-key answer as settling the poll-positions verdict too
**What goes wrong:** treating a favorable §1 answer ("most private strategies DO have an in-set
sibling") as if it weakens D-02's already-closed refusal.
**Why it happens:** D-01 and D-02 both touch "siblings" and it is easy to conflate them.
**How to avoid:** D-02 is closed on its own PROD evidence (the five `pending_review` strategies
that already pass the poll predicate and still get zero) — that evidence does not depend on §1 at
all, per D-01's structural argument (`cj.strategy_id = s.id` keys on the strategy's OWN id, not a
sibling's). §1 only scopes the `ALLOWED_STRATEGY_STATUSES` verdict and the D-03 cursor question.
**Warning signs:** a plan task that reads "if §1 shows most keys are shared, we don't need to widen
poll-positions" — that framing was already refused independent of §1.

### Pitfall 2: Fixing D-03 in a way that silently also relies on §1's answer
**What goes wrong:** deferring the cursor-advance fix "until we know whether keys are shared."
**Why it happens:** superficially both concern "empty `strategy_ids`."
**How to avoid:** CONTEXT.md D-03 explicitly separates this — "not silently folded into the
constant's verdict … the advance is wrong even if the constant is left exactly as it is." The fix
(or the decision to book it with an owner) does not need §1's answer; §2's trace shows the defect
is live via BOTH sub-causes (2a and 2b), and 2a is live TODAY regardless of what §1 finds, because
the six `private` strategies exist today and at least the ones without an in-set sibling are
already hitting it on every tick.

### Pitfall 3: Routing an `ALLOWED_STRATEGY_STATUSES` widening through the SQL apply pipeline
**What goes wrong:** applying Success Criterion 4's "three reviewers, `apply-test`, PROD apply
behind human reviewer" ceremony to a widening of `ALLOWED_STRATEGY_STATUSES`, which is a plain
Python constant, deployed by Railway on merge, not a Supabase migration.
**Why it happens:** the adjacent, better-known widening in `164.5.1.1` WAS a SQL migration, and
this phase inherits that phase's vocabulary closely.
**How to avoid:** criterion 4 says "Any SQL change follows this apply path" — a Python-only
constant change is not a SQL change. If the plan pairs it with a NEW SQL gate (§4's option), THAT
gate addition, if it touches `supabase/migrations/**`, DOES need the apply path; the constant edit
itself does not.
**Warning signs:** a plan task requesting `migration-reviewer`/`rls-policy-auditor` review for a
one-line `cron.py` diff with no accompanying SQL file.
