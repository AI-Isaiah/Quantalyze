## Summary

The phase's entire production change is one line in `_sync_single_key`
(`analytics-service/routers/cron.py`): `should_advance_cursor` dropped the `bool(strategy_ids)`
conjunct and now reads `(not trades) or synced_count > 0`, plus the single "held last_sync_at
unchanged" `logger.warning` was split into two branches on `if not strategy_ids:`. This is a
genuine, narrowly-targeted data-integrity fix for a real production defect (real trades fetched,
zero currently-eligible strategy on the key, cursor advanced anyway, trades lost on the next
tick).

**Boundary trace (the four questions):**

1. **Correctness of `(not trades) or synced_count > 0`.** Traced every path: `trades=[]`/falsy →
   advances (correct idle-tick). `trades` non-empty, `strategy_ids=[]` → `per_strategy_stored`
   stays `{}` (the RPC loop is gated on `if trades and strategy_ids:` and never runs) →
   `synced_count=0` → does **not** advance (the fix, correct). `trades` non-empty, all
   per-strategy RPCs raise → `synced_count=0` → does not advance (unchanged from pre-existing
   C-0198, correct). `trades` non-empty, at least one strategy stores → `synced_count>0` →
   advances. Each per-RPC call is individually `try/except`-wrapped inside the loop, so a
   mid-loop exception never escapes to skip the cursor-gate logic entirely. `fetch_all_trades` is
   typed `list[dict[str, Any]]` (never `None`); an exception raised while fetching trades or
   validating the key is caught by the function's outer `except Exception`, which returns before
   any `update_data` is built — the cursor is left untouched on that path, consistent with
   "unknown state → don't advance."
   - **(a) Does any path still advance over trades never stored?** Yes, but it is *unchanged*
     pre-existing behavior, not introduced by this diff: when `strategy_ids` has ≥2 entries and
     only some RPCs succeed, `synced_count > 0` advances the *single per-key* cursor even though
     the failed strategy's own trades were never stored for it. This formula and this tradeoff
     both predate this phase (C-0198) and are explicitly documented in the surrounding comments;
     the diff under review does not touch this behavior. Not a new finding.
   - **(b) Does any path now fail to advance forever?** Yes, by design, and it is not
     hypothetical: `ALLOWED_STRATEGY_STATUSES = {"draft", "pending_review", "published"}` means
     any key whose only linked strategies are `private` gets `strategy_ids=[]` on *every* tick
     until `FANOUT-COHORT-SYNC-CONSTANT-01`'s widening (routed to Phase 164.5.1.3) ships —
     TODOS.md's own measurement puts this at 5 live production keys today. Each tick refetches
     and discards the same window. This is correct (nothing is lost — there is nothing eligible
     to store), and the resource cost of repeated refetching is a performance concern, out of
     this review's scope. See WR-01 for the one consequence of this that *is* in scope.
2. **Warning split is behavior-neutral.** Confirmed via `git diff main...ed1b7d92`: both branches
   sit inside the same `if not should_advance_cursor:` guard, call `logger.warning` with the same
   two format args (`key_id`, `len(trades)`), and neither branch returns, mutates
   `should_advance_cursor`, nor swallows anything. No control-flow change beyond which string is
   logged.
3. **No silent failure introduced.** `per_strategy_stored`/`synced_count` trace to the per-RPC
   `try/except` (failure → `per_strategy_stored[sid]=0` + `strategy_errors[sid]=...`, logged via
   `logger.exception`) and to the `rpc_result.data` shape-drift branch (non-int response →
   logged at `logger.error` and falls back to `len(trades)`, loudly, not silently). Neither path
   is touched by this diff.
4. **The new test bites.** `test_D03_empty_strategy_ids_with_trades_does_not_advance_cursor`
   (`TestC0198CursorOnlyAdvancesWhenStored`, third member of the class) uses
   `key_row(strategy_ids=[])` with `fetch_all_trades` returning two trades. Against the *old*
   expression — `any_trades_to_store = bool(trades) and bool(strategy_ids)` = `True and False` =
   `False`, so `should_advance_cursor = (not False) or ... = True` — the test's assertion that no
   `api_keys` update carries `last_sync_at` would fail (a payload containing `last_sync_at` would
   be present). Against the *new* expression, `should_advance_cursor = (not trades) or
   synced_count > 0 = False or False = False`, satisfying the assertion. The test genuinely
   distinguishes old from new; it is not vacuous. This is corroborated by the commit pair cited
   in TODOS.md — `d1157059` ("test(164.5.1.2-02): RED — D-03 cursor lies when strategy_ids is
   empty") and `ca432660` ("fix(164.5.1.2-02): D-03 — cursor no longer lies when no strategy is
   eligible") — both present in repo history with subjects matching the claimed RED/GREEN
   sequence.

## Warnings

### WR-01: The fixed "held cursor" case reports `status: "ok"`, indistinguishable from a genuinely idle tick

**File:** `analytics-service/routers/cron.py` (`_sync_single_key`'s status classification —
`any_stored = any(n > 0 for n in per_strategy_stored.values())` / `if strategy_errors and
any_stored: … elif strategy_errors: … else: status = "ok"` — and the per-key summary log line
`level = logging.INFO if r["status"] == "ok" else logging.WARNING`)

**Issue:** The new `strategy_ids=[]`-with-real-trades path this phase fixes (cursor correctly
held, `per_strategy_stored={}`, `strategy_errors={}`) falls into the `else: status = "ok"` branch
— the same bucket as a genuinely empty tick with zero trades fetched. Two consequences:
- The aggregate `cron_sync complete: %d synced, %d partial, %d failed, ...` summary counts this
  key under `synced`, alongside truly healthy keys.
- The per-key observability log line (`cron_sync key_id=... status=ok`) is emitted at `INFO`, not
  `WARNING`, even though real trades were fetched and zero were stored on this key.

The only WARNING-level signal for this condition is the `logger.warning("cron_sync: key %s held
last_sync_at unchanged...")` emitted earlier inside `_sync_single_key` — a single line per tick,
easy to lose in volume, and not reflected in any of the aggregate counters a dashboard or alert
would realistically watch. This is not hypothetical: per TODOS.md's own current measurement, 5
live production keys hit exactly this path on every 15-minute tick today (their only linked
strategies are `private`, filtered out by `ALLOWED_STRATEGY_STATUSES`), and will continue to
until `FANOUT-COHORT-SYNC-CONSTANT-01`'s widening (Phase 164.5.1.3) ships. This is a genuine
improvement over the prior behavior (data is no longer silently lost), but the stuck-retry state
itself is now invisible to any status-count-based monitoring for as long as those keys stay
`private`.

**Fix:** Distinguish the two `status="ok"` causes, either by adding a narrow `SyncStatus` bucket
(e.g. `"no_eligible_strategy"`) for the `trades and not strategy_ids` case, or — cheaper — by
having the per-key summary log line's level check also catch `not should_advance_cursor` (which
would require threading that boolean, or an equivalent derived condition, into the result dict)
so this case logs at `WARNING` in the observability loop rather than `INFO`. Either avoids
inventing a new top-level counter while making the stuck condition visible to whatever currently
watches non-`ok` counts or `WARNING`-level cron log lines.
