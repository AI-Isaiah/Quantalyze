### The retry: can it return a partial book without raising? No.

`equity_reconstruction.py:838-853`. The retry fires only when the page is full, the walk did not advance, `end_ms != oldest_seen`, and the page holds a fill newer than `oldest_seen`. It then asks once more with `until = oldest_seen`.

**Exclusive end reading: the retry never fires.** After a normal step `end = o+1`, so the page holds only fills with `ts <= o`. A stall means either nothing was added (every fill on the page is already held, so `ts >= o`) or the oldest fill is still `o`. Either way every fill on the page is at `o`, so `max <= oldest_seen` and the code raises. After a retry under exclusive reading (`end = o`), the page holds only fills with `ts < o`. None of those are held, so "nothing added" cannot happen. The step that could skip the rest of a same-ms group under an exclusive end is therefore unreachable.

**Inclusive end reading: the retry fires exactly when the fills at `o+1` crowd the page.** The invariant is that every fill newer than the current end bound has already been read. It holds because the page that first reached `o` ranked every fill at `o+1` above its last row. Asking for fills up to `o`, inclusive, then misses nothing at `o`. If the retried page is entirely at `o`:
- `end_ms == oldest_seen` and the code raises. That is the documented single-ms limit, and it is loud.
- Otherwise the walk resumes the normal `oldest + 1` step.

Each retry strictly lowers the end bound or raises, so the pass terminates within the ceiling.

**OKX ignoring `end` altogether.** The second page repeats the first, the retry fires, the third page repeats again, `end_ms == oldest_seen`, and the code raises.

**Randomized check**, 3,000 books per distribution, alternating the end reading, with dense ties, multi-instrument shared ids and the 100-row cap:
- Every one-millisecond group below 100: all 3,000 read whole, with 0 partials and 0 raises.
- Groups of 100 or more allowed: 2,779 raised and 221 read whole, with 0 partials.

**Residual premise, not new:** the walk assumes OKX ranks fills strictly newest-first by `ts`. The plan 06 `okx-order:` gate measures that before any OKX rebuild.

## Warnings

### WR-07 (MEDIUM, data integrity, conditional): the `bybit-transfers:` gate pools deposits and withdrawals, so one kind can pass the gate for the other

**File:** `analytics-service/scripts/allocator_history_probe.py:403-415` (`transfers_older_than` counts `(kind, id)` pairs from both kinds into one number) and `:732-735`. Plan 06 Task 1 step 5 (`.planning/.../167.2.1.1.2.1-06-PLAN.md:133-136`) passes an account when the pooled count is above 0.

**Issue:** Bybit serves deposits and withdrawals from two separate endpoints (`/v5/asset/deposit/query-record`, `/v5/asset/withdraw/query-record`). The repo has measured the history depth of neither. `services/nav_twr.py:123` holds a single, low-confidence 365-day constant. The gate is meant to stop a rebuild that would persist the older year without its transfers. A pooled count above 0 proves only that one of the two endpoints served something older than 365 days.

**Scenario:** a Bybit account has a deposit 500 days ago and a withdrawal 400 days ago. Bybit serves deposits for two years and withdrawals for one year, and the withdrawal endpoint returns an empty list rather than an error. The probe prints `transfers_older_365d: 1`, the gate writes `bybit-transfers: ok`, and the forced rebuild persists a 729-day curve with that withdrawal missing from the replay. Nothing logs it.

This is conditional on the two endpoints' depth differing, which is unmeasured either way. The gate was written to close exactly that unknown.

**Fix (minimal):** record the count per kind in the probe, either as `deposits_older_365d` and `withdrawals_older_365d` or as a split of the existing field. Then have the plan 06 gate read `ok` only when each kind is above 0 for the account. An account where either kind reads 0 is named in `unmeasured (...)` and takes the same founder STOP. An alternative is one read-only measurement per endpoint on a known-old account before Task 2, recorded in the SUMMARY.
