## N1 (malformed `marks_trailing_since` took the 7-day window) - RESOLVED

### The change

`supabase/migrations/20261030120000_ledger_fanout_marks_paused_weekly.sql:535` (mirrored byte for byte at `supabase/schema/functions/enqueue_ledger_refresh_for_strategies.sql:376`) adds, ahead of the text compare inside the paused `EXISTS`:

`AND (sa.data_quality_flags ->> 'marks_trailing_since') ~ '^\d{4}-\d{2}-\d{2}$'`

`~` on text cannot raise, and a NULL left side makes the conjunct NULL, so the `EXISTS` is false and the cooldown stays 20 hours. The never-raise half of D-04 is intact.

## Notes below the floor (not findings, not to be fixed)

1. **The regex's strictness is pinned only at the empty string.** Arm P5 seeds `''`; no arm seeds `'2026'`, `'2026-10'` or `'0'`. Two further mutants of the migration kept the whole gate green (`ALL 31 ARMS EXECUTED`): dropping the `$` anchor (`'^\d{4}-\d{2}-\d{2}'`), and loosening the pattern to `'^\d'`. The second one brings back three of N1's five original values (`'0'`, `'2026'`, `'2026-10'` go weekly again). It needs a deliberate edit of a one-line regex, and the only way in is an out-of-band write, so I rate it below the floor. If you want it closed cheaply, give P5 a second value such as `'2026-10'` (it sorts below the cutoff and fails the shape), which kills the `'^\d'` mutant; the `$`-anchor mutant would additionally need a value like `'2026-01-01x'`. I did not run those two extra seeds as arms.
2. **Calendar-impossible but shape-valid old dates still take the weekly window.** `'2025-13-45'`, `'2026-02-30'` and `'0000-00-00'` match the regex and sort below the cutoff. `'2026-13-45'` is 20h only because month 13 sorts above `'2026-10-xx'`, an accident of the current date. Calendar validation without a raise path would need a month and day range in the regex. The writers already emit only real dates (`job_worker.py` writes `date.isoformat()`; `analytics_runner._read_navmtm_flags` drops anything that is not a real `YYYY-MM-DD`), so this needs the same out-of-band write as N1 and a value that looks exactly like a date. Recording it, not asking for a fix.
3. **Wording.** The migration header (`:31`), the in-function comment (`:523`), the runbook (`docs/runbooks/ledger-refresh-go-live.md:684`) and D-04 say "a malformed value keeps the 20 hours". After this fix that is true for anything that is not shaped like `YYYY-MM-DD`, and not for the Note 2 values. Reading "malformed" as "not date-shaped" makes the claim exactly true.
4. **`\d` in the function body** depends on `standard_conforming_strings = on` when the plpgsql statement is parsed. That is the Supabase default and the setting of every session this repo uses, and arms P1 and P5 would catch an off session in the lane. Not a finding.
