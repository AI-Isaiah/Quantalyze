## Summary

`strategy_analytics.computed_at` has exactly one writer today: the status bridge `sync_strategy_analytics_status` (latest body: `supabase/migrations/20261009120000_sync_status_analytics_scope.sql`). No Python, TypeScript or other SQL path writes it. [VERIFIED: grep of `analytics-service`, `src` and `supabase/schema/functions/*.sql` this session; the two Python `"computed_at":` hits at `job_worker.py:6268` and `:12230` target `allocator_equity_derived`, read at `:6262-6270` and `:12226-12232`.] The bridge stamps `now()` in branch (a) ON CONFLICT (`:961-968`), branch (b) (`:1024`) and branch (c) (`:1150`), and a first-ever row takes the column default (`"computed_at" timestamp with time zone DEFAULT "now"() NOT NULL`, `supabase/schema/baseline.sql:12157`). PROD today shows the damage: of 43 `strategy_analytics` rows, 7 carry a date from the last 24 h and 6 of those had no runner finish in that window; 5 rows carry a date equal to a later side-job finish.

There are exactly **two real recompute finishes**: the CSV runner's `_mark_complete` upsert (`analytics_runner.py:2069-2131`, the single success return at `:2191`) and the composite `headline_payload` upsert (`job_worker.py:9454-9529`, written at `:9625`). Everything else that touches the row (entry `computing` write, restore, the failure writers, the derive pre-stamp, the sibling-flag write, the TS pre-enqueue placeholders, the reaper, `set_wizard_composite_members`) is not a finish and must not stamp.

**Primary recommendation:** stamp with the database clock by adding the literal `"computed_at": "now"` to those two success payloads. Postgres reads the special input `now` as the transaction start time; PostgREST passes the JSON string through the column's input function. Measured this session on real PostgREST v14.10 over Postgres 17.6.1.113: an upsert carrying `"computed_at":"now"` moved a 30-day-old date to the DB clock on the conflict path and stamped a fresh row on the insert path, and an upsert that omitted the key left the old date alone. No migration, no new column, no new function, no deploy-window hazard. In the same migration, re-base the bridge (same signature, `CREATE OR REPLACE`, ACL and COMMENT preserved) with all three `computed_at` writes removed, the D-09 release clause **deleted** (it would fire after every normal compute once the runner stamps earlier than the job's `updated_at`), and the (a-hold) early return widened to a side-kind trigger of any outcome. A scratch spike of that body passed every existing SQL gate arm except the four stamp-expecting assertions (scope D10, D12, D15; marked-refresh I3).

### Pattern 1: DB-clock stamp as a payload literal

**What:** the success payload names `computed_at` with the string `"now"`; the database evaluates it.
**When to use:** only at the two terminal-success writes (status `complete` / `complete_with_warnings`).
**Example (measured):**
```sql
-- Source: executed this session on PG 16 (local) and via PostgREST v14.10 on PG 17.6.1.113.
-- PostgREST-shaped statement; the second row shows json_to_recordset, the other shape PostgREST uses.
INSERT INTO sa (strategy_id, computed_at, status)
SELECT * FROM json_to_recordset('[{"strategy_id":"...","computed_at":"now","status":"complete"}]'::json)
         AS _(strategy_id uuid, computed_at timestamptz, status text)
ON CONFLICT (strategy_id) DO UPDATE SET computed_at = EXCLUDED.computed_at, status = EXCLUDED.status;
-- result: computed_at = transaction_timestamp()  (eq_txn_start = t, lag to clock_timestamp 1.2 s after pg_sleep)
```
```
# PostgREST v14.10, table with NOT NULL DEFAULT now() column, row seeded 30 days old:
POST /sa?on_conflict=strategy_id  Prefer: resolution=merge-duplicates
  {"strategy_id":"1111...","computation_status":"complete","computed_at":"now"}
  -> computed_at 2026-10-09T07:44:34.917476+00:00   (DB now() read 07:44:34.99), sharpe 1.0 preserved
fresh row, same body            -> computed_at 2026-10-09T07:44:34.929014+00:00
omit computed_at on conflict    -> computed_at unchanged (…34.917476), status computing
"computed_at":"nowish"          -> 22007 invalid input syntax for type timestamp with time zone
```

### Pattern 2: Table-level invariants already on this table

`strategy_analytics_stamp_computing_started_trigger` and `strategy_analytics_drop_stale_error_provenance_trigger` are BEFORE UPDATE row triggers that neither read nor write `computed_at` [VERIFIED: `supabase/schema/baseline.sql:9577-9651`, trigger DDL `:14318-14330`; PROD carries exactly 2 triggers on the table, PROD read this session]. They are the precedent for table-level invariants (and for the 166.3.1 hold trigger discussed below), and they prove a stamp literal in a payload is not disturbed by them.

### Anti-Patterns to Avoid

- **Stamping from Python `datetime.now()`** (D-02), or from a value read back from the job row.
- **Stamping on `_mark_computing`, the restore, the failure writers, the pre-stamp or the sibling-flag write.** None is a finish. A `computed_at` stamped while the row is `computing` would also be silently discarded by 166.3.1's hold trigger if that lands.
- **Keeping the D-09 release clause.** See Q4: with an earlier runner stamp, `d.updated_at > sa.computed_at` is TRUE after every normal compute, so the release would fire every time and defeat the hold.
- **Re-issuing `COMMENT ON FUNCTION sync_strategy_analytics_status`.** Its text is the applied-ness key for arms 0a/0b of `test_sync_status_marked_refresh_protected.sql` and assumption A1 in the old verify block (`20261009120000...sql:1579-1597`); `CREATE OR REPLACE` with an unchanged signature preserves it. (164.5.2.1 D-03 made the same call.)
- **Dropping NOT NULL / the default on `computed_at`.** It would touch every reader's type (`database.types.ts`, 30+ files read the column). Not requested by any decision.

**Why not "unmeasured"**: the whole recommendation rests on `now` surviving PostgREST, so it was measured rather than argued (outputs in Pattern 1). The local-stack lane already pins the same images, so a live-DB probe test is cheap (see Validation Architecture).

**Interaction with the bridge's transaction and advisory lock.** The runner's write is a standalone PostgREST transaction that takes no bridge lock; the bridge is called afterwards from `mark_compute_job_done`/`failed`. With the bridge no longer reading or writing the date, there is no ordering to protect and the lock's concerns no longer include `computed_at`. `IN-R4-02` (two transaction-start clocks compared across transactions) existed only inside the release clause; with that clause deleted there is no cross-transaction clock comparison left in the bridge. **IN-R4-02 is moot** (confirmed, record it).

**Interaction with 166.3.1's hold trigger** (unmerged, see Q3a): its `BEFORE UPDATE` trigger restores `OLD.computed_at` when `NEW.computation_status IN ('failed','computing')`. A runner stamp rides a write whose status is `complete`/`complete_with_warnings`, so it is not held. ## Common Pitfalls

### Pitfall 1: The release clause stays and quietly un-holds everything
**What goes wrong:** `d.updated_at > sa.computed_at` fires after every normal compute because the runner stamps earlier than the mark RPC's `updated_at`, so a later side failure releases the hold.
**How to avoid:** delete it and its anchor; replace the arm per D-06's second sentence. Spike confirmed nothing else needs it.
**Warning signs:** an arm "side failure after a normal compute holds" going RED on a runner-shaped fixture.

### Pitfall 2: 166.3.1 lands second (or never)
**What goes wrong:** a fast failure shows no completion evidence in the key-card panel (~120 s wait) and the factsheet cache serves a cached `complete` payload to a `failed` row for up to 3600 s; 166.3.1's C1 arm contradicts this phase; migration ordering breaks.
**How to avoid:** Wave 0 dependency probe (Q3a); order 166.3.1 first.

### Pitfall 3: A stamp on the wrong write
**What goes wrong:** `computed_at: "now"` copied into `_mark_computing`, a failure payload or the pre-stamp makes a failure look fresh again, or is discarded by 166.3.1's trigger.
**How to avoid:** an AST census asserting that any `strategy_analytics` payload naming `computed_at` carries the literal `"now"` AND a terminal-success status; negative cases for every failure writer in Q1.

### Pitfall 4: `.neq("status","done")` turns a legitimate no-op into an error (TS)
**What goes wrong:** `retractInheritedRefreshMarker` treats a zero-row update as "marker NOT retracted" and throws, so a user resync that deduped onto a refresh that just finished logs an error and Sentry noise.
**How to avoid:** read `status` first and return `{ retracted: false }` for `done` (Q5).

### Pitfall 5: Gates pass on the wrong bridge
**What goes wrong:** an inverted arm ("date held") passes in `sql-tests` (new bridge) and fails in the mutation lane (old bridge in its apply list), or the reverse.
**How to avoid:** append the new migration LAST to every gate whose arms changed; re-point twins; run `node scripts/mutation-runner/run.mjs` FULL on the lane and set floors by measurement; layer the verify-anchor stand-down on every bridge twin.

### Pitfall 6: Mixed-vintage payload cached under the new key
**What goes wrong:** the stamp now lands at `_mark_complete` / `headline_payload`, BEFORE the sibling-series RPC (`upsert_strategy_analytics_series_batch`, `analytics_runner.py:2154-2162`; composite siblings after `:9625`). Previously the bridge stamped after everything. A factsheet request landing in that window builds from new scalars plus not-yet-rewritten sibling series and caches under the NEW key for up to 3600 s (`revalidate: 3600`, `v2/page.tsx:231`).
**Severity:** low (one RPC wide). `[ASSUMED]` whether the cached build reads the rolling/drawdown sibling kinds; the persisted cash/MTM series are written BEFORE the scalar flip (D5 ordering) so those are safe.
**How to avoid:** D-01 locks "same write", so keep it and record the window as a known limit; if the planner finds a cached reader of the sibling kinds, the escape is a second tiny `{strategy_id, computed_at:"now"}` upsert after the siblings, not a reordering of the D5 series-before-scalar discipline. Decide at planning time, not execution.

### Pitfall 7: Deploy skew degrades silently
**What goes wrong:** migration applies first (bridge stops stamping) and Railway deploys later (or the reverse): in the gap a real recompute may leave the date unmoved or doubly stamped. Both directions are harmless to correctness but Wave 5 run inside the gap would look broken.
**How to avoid:** Wave 5 precondition checks (Q6); no deploy-window shim needed because no new column is named in a payload.

### Pitfall 8: Prose and comments that now lie
Stale prose to correct (planner decides how much): the migration header "the bridge is the only writer of strategy_analytics.computed_at" (`20261009120000...sql:77-80`, but that file is applied and immutable; the NEW file's header carries the correction), `analytics_status.py:36-45` docstring, `test_job_worker.py:887-889`, `queries.ts:473-476,597`, `v2/page.tsx:127-129`, `fetch-and-build-payload.ts:535-540,660-664`, the `computing_started_at` column COMMENT (says the bridge re-stamps), and the 166.3.1 trigger COMMENT ("Residue owned by Phase 166.5").
