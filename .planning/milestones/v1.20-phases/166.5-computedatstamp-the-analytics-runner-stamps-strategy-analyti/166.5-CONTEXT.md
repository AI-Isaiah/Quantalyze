# Phase 166.5: COMPUTEDATSTAMP - Context

**Gathered:** 2026-10-08
**Status:** Ready for planning

<domain>
## Phase Boundary

`strategy_analytics.computed_at` means "when these metrics were really computed". Today nothing in Python writes it; the status bridge `sync_strategy_analytics_status` (latest definition in `supabase/migrations/20261009120000_sync_status_analytics_scope.sql`) is its only writer, and it stamps `now()` on several branches that are not a real recompute: a SUCCESSFUL side-kind job with a sibling in flight takes branch (a)'s `ELSE now()` (and blanks the sentence and markers), branch (b) stamps `now()` on a failure, and branch (c) stamps `now()` when every job is done even if only side jobs ran since the last compute. This phase makes the analytics runner the only writer, at the moment it writes metrics, so the freshness chip, the factsheet cache key, the tearsheet badge and the PDF ETag never move without a real recompute. Scope is `strategy_analytics` only; `portfolio_analytics.computed_at` (the portfolio PDF vintage) is not touched.

</domain>

<decisions>
## Implementation Decisions

### Who stamps (founder, AskUserQuestion 2026-10-08)
- **D-01:** The analytics runner is the ONLY writer of `strategy_analytics.computed_at`. It stamps it in the same write that stores the metrics: the CSV path's `_mark_complete` (`analytics-service/services/analytics_runner.py`) and the composite path's `headline_payload` (`analytics-service/services/job_worker.py`), and any other path the research finds that writes metrics.
- **D-02:** The stamp uses the DATABASE clock, not the Python clock, because the bridge's D-09 release compares `compute_jobs.updated_at` (DB clock) against `computed_at`. The mechanism is the planner's choice (a DB-side default or trigger keyed on the runner's metrics write, or an RPC), but a Python `datetime.now()` is not acceptable.
- **D-03:** The bridge stops writing `computed_at` on EVERY branch: (a), (a)'s membership arm, (b) and (c). It keeps every status, sentence and marker behaviour it has today, except that the "sentence blanked by a side job's ELSE branch" in review item (a) must no longer blank a sentence when no real recompute happened. The migration re-bases on the latest definition (`20261009120000`) and its header's "the bridge is the only writer" sentence is corrected.

### On failure (founder, AskUserQuestion 2026-10-08)
- **D-04:** A failed recompute leaves `computed_at` at the last good compute. The failure shows through `computation_status` and its sentence, never by moving the date. This retires the 164.5.2.1 "hold the date" special case and the 164.6.6.3.4 D-09 hold as date mechanisms (nothing else writes the date any more); their status and sentence rules stay.

### Existing rows (founder, AskUserQuestion 2026-10-08)
- **D-05:** Rows already carrying a too-new date get a FORCED recompute of every strategy after this phase deploys, so all dates become true. It runs inside the Wave 5 consolidated PROD recompute (the goal's "166.5" entry there), not as a separate fan-out, so no row is recomputed twice. This phase delivers the code and names the recompute set; Wave 5 runs it.

### STATUSBRIDGE round-4 leftovers (founder, AskUserQuestion 2026-10-08: "Yes, both")
- **D-06 (WR-R4-01):** a SQL gate arm pins the EQUAL boundary of the D-09 release (a counting `done` whose `updated_at` equals `computed_at`), shown RED under `>=`. If D-03/D-04 make the D-09 release clause obsolete, the planner removes the clause and replaces the arm with one that pins "a side-only finish never moves `computed_at`" instead, and records why.
- **D-07 (IN-R4-01):** both marker retractions (`analytics-service/services/ingestion/long_fetch.py` and `src/lib/ledger-refresh-marker.ts`) update a compute job only when it is not `done` (status guard), with a test each that fails without the guard.
- **IN-R4-03** (42883 on the Python call after a rollback of the 2-arg bridge) stays recorded only, not fixed. **IN-R4-02** (cross-transaction clocks) is moot once D-02 holds; the planner confirms that and records it.

### Founder decision after research (AskUserQuestion, 2026-10-09)
- **D-08 (status heal):** a successful side-kind job never moves a `failed` row to `complete`; only a real recompute (a runner finish) can. Today branch (c) heals a `failed`+sentence row when a side job is the last in flight. Fixed in this phase, in the same bridge edit, with a gate arm that is RED on today's code.

### Orchestrator resolutions at planning (2026-10-09)
