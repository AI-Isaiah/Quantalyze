### SFH-1 (long_fetch.py retraction logging): CLOSED

The update keeps the D-07 `.neq("status","done")` filter. postgrest-py 2.31.0's `update()` defaults to `returning=ReturnMethod.representation` (`.venv/.../postgrest/_sync/request_builder.py:418`), so a non-empty `.data` list means a row matched. A not-done job that still carries the marker after a zero-row update cannot come from the filter (the filter matches every non-done status), so the error arm only fires for a vanished row. Error level is proportionate.
- Test double: the `_queue_supabase` change (update returns `[{"id": job_id}]` on match and `[]` on a missing row) matches representation semantics. The vanished-row test's double returns `MagicMock(data=None)` where the real client returns `None`. Production code handles both, so this costs nothing.

Two things go wrong:
1. **Donut slice tooltip** (`page.tsx:222` feeds `computedAt` to `SyncBadge`). If the badge renders at all (it returns null when neither the series end nor a trade fetch binds, `SyncBadge.tsx:252`), the tooltip ends "Analytics last computed 3h ago" (`SyncBadge.tsx:254-258`) for a strategy nothing has computed. The metric values are not misstated: a never-computed row has no figures. The breakdown table for the same row shows no date, because it gates on `isRankableAnalyticsRow` (`StrategyBreakdownTable.tsx:126-128`). So the two surfaces disagree, the very oracle `buildCompositionRows`'s own doc comment cites.
2. **`staleConstituents`** (`page.tsx:660`). `computeFreshness(insert-time)` is not `stale` for the first 48 h after the insert, so the amber "Stale constituent data" warning omits that constituent. After 48 h the unmoving date makes it fire.

**Why it is below MEDIUM:**
- **Not a regression of this phase.** Before 166.5 the bridge stamped `now()` on every hop, including failure (b) and (c). The same rows then carried an even fresher false date. 166.5 strictly narrows it, and R-06 removed one of the ways such a row was created (a side job inserting a first `complete` row).
- **Recorded decision.** CONTEXT R-04: "first-ever rows keep the column `DEFAULT now()` (NOT NULL); recorded as a known limit."
- **Small population, bounded window.** The breakdown table's own comment says constituents are "OTHER managers' published strategies", and a published strategy almost always has a real compute. The false freshness lasts at most 48 h per row and never inflates a figure.

A PROD count (read-only, marker first) would settle it: rows of `strategy_analytics` that are portfolio constituents with `computation_status NOT IN ('complete','complete_with_warnings')` and `cagr`, `sharpe`, `max_drawdown`, `daily_returns` all NULL. If that count is non-zero, re-rate.

## The proposed root migration: right direction, not ready as written

`ALTER ... computed_at DROP DEFAULT, DROP NOT NULL`, a one-off `UPDATE ... SET computed_at = NULL` for never-completed rows, and `StrategyAnalytics.computed_at: string | null`.

**Right direction.** NULL is the honest encoding of "never computed", and most readers already degrade correctly on it:
- `computeFreshness(null)` returns `stale` (`freshness.ts:79`).
- `|| null` collapses at `page.tsx:222` and `StrategyBreakdownTable.tsx:149`.
- The bridge INSERT arms already omit the column (`20261023120000_...sql:787`, `:890`, `:1029`), so they need no edit.

**Risks, in order of severity:**
1. **The backfill is silently undone by the hold trigger.** `strategy_analytics_hold_computed_at_until_success()` does `IF NEW.computation_status IN ('failed', 'computing') THEN NEW.computed_at := OLD.computed_at;` (`20261013120000_strategy_analytics_hold_computed_at_until_success.sql:107-108`, BEFORE UPDATE, `:138-141`). The proposed UPDATE targets rows whose status is not success, mostly `computing`/`failed`, so for exactly those rows the trigger restores the old date and the UPDATE reports success while changing nothing. It sticks only for `pending`. The migration needs one of:
   - a trigger-aware path (`ALTER TABLE ... DISABLE TRIGGER strategy_analytics_hold_computed_at_until_success_trigger` around the UPDATE, inside the transaction);
   - a guard in the trigger that lets an explicit NULL through. This also means updating that migration's verify anchors at `:185-189`, which regex-match the body, and the SQL gate that pins the trigger;
   - in all cases, a post-UPDATE `DO` block that asserts the count of remaining never-completed non-NULL rows is 0, so a no-op fails loud.
2. **It reverses CONTEXT R-04.** That makes it a founder decision and its own phase, not a review-round change. Booking it is correct; doing it inside 166.5 is not.
3. **The rollback cannot restore `NOT NULL` without fabricating dates.** Once NULLs exist, `SET NOT NULL` fails unless the rollback first writes a value into them, which reintroduces the false "computed now" date the change exists to remove. The rollback must name the value it writes and why.
4. **NULL semantics at readers that never saw one:**
   - Any `ORDER BY computed_at DESC` over `strategy_analytics` puts NULLs FIRST by default in Postgres and PostgREST. None found in `src/lib/queries.ts`: the `.order("computed_at")` sites at `:2757`, `:5220`, `:6050` are on `portfolio_analytics`/`match_batches`. Re-check SQL functions, though, e.g. `get_allocator_recommendations` returning `sa.computed_at AS analytics_computed_at`.
   - Any `x > sa.computed_at` comparison silently evaluates false. The bridge's D-09 clause that did this is deleted by R-03, but the `ledger_refresh_staleness` view projects the column.
   - The factsheet cache key and the PDF ETag must treat NULL as a distinct, non-colliding value.
   - Every other `INSERT INTO strategy_analytics` site (5 in the baseline, including the wizard RPCs and `finalize_csv_strategy_with_returns`) will start producing NULL. That is intended, but each consumer of those rows needs the typecheck sweep the fixer named.
5. **Gate and snapshot churn.** It touches the baseline snapshot, the carried-migration marker, VAC-04 and baseline-content-drift, and the hold trigger's own verify anchors. It needs migration-reviewer and rls-policy-auditor clean before merge, since PROD auto-applies with no human stop.
