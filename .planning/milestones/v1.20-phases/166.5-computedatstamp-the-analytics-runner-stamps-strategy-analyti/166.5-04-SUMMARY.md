# Phase 166.5 Plan 04: marker retractions leave a finished job alone Summary

Both marker retractions (Python reuse-collision helper, TS inherited-marker helper) now update a `compute_jobs` row only while its `status` is not `done`, so the `compute_jobs_set_updated_at` trigger can no longer bump a finished job's `updated_at`; each half has a test that goes RED without it.

## What shipped

- `analytics-service/services/ingestion/long_fetch.py`: the retraction update chain is `.update(...).eq("id", job_id).neq("status", "done").execute()`.
- `analytics-service/tests/test_ledger_refresh_reuse_collision.py`: the `_queue_supabase` update chain gains `_neq` and models PostgREST's zero-row update (a row failing any recorded `neq` is neither captured nor mutated). New `TestRetractionHelper.test_done_job_with_marker_is_not_rewritten` and the control `test_running_job_with_marker_is_still_retracted`.
- `src/lib/ledger-refresh-marker.ts`: `.select("metadata, status")`; `done` early return directly after the null-row check; `.neq("status", "done")` on the UPDATE; on a zero-row UPDATE one `select("status")` re-read by id (`done` returns `{ retracted: false }`, a re-read error throws with `cause`, anything else throws the existing `matched no row`). The doc comment's "Error contract" names the `done` outcome and the re-read.
- `src/lib/ledger-refresh-marker.test.ts`: `fakeAdmin` gains `updateNeq`, `readSelect`, `readCalls` and a `reread` result. Five new cases in `[161.1-D13] retractInheritedRefreshMarker` (the four planned, plus the re-read error path, which is a branch this plan adds).
