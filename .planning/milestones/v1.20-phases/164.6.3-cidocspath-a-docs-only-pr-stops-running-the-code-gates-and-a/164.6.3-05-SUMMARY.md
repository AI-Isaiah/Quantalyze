# Phase 164.6.3 Plan 05: The MW02 Oracle Repair Summary

The executed-tolerance oracle now measures the aggregator that exists at HEAD instead of the one
that existed before wave 1 — and proves, on every invocation, that it catches a mutation the
pre-repair machinery passed.

## The defect, and why it mattered

Wave 1 hoisted `docs_only=` and `ALWAYS_ON=` above the `for r in \` anchor that
`extractResultLoopBlock` slices from. The executed script therefore MENTIONED both names and
DEFINED neither; bash expanded them to the empty string; the uniform docs-only arm was dead in the
simulation; eleven rows gained skip-tolerance; and the oracle whose entire subject is *"which rows
may skip"* printed the pre-change answer and passed green.

⭐ The milestone's named defect class — a control that cannot fire — inside the phase whose subject
is controls that silently stop firing. Wave 3 adds the docs-only conjunct to fifteen more job keys,
so the oracle was repaired BEFORE the filter was widened.

## What was built

**The two-layer repair.** `extractResultLoopScript` slices from the step's own whole-line `fail=0`
through `done`, so the prologue is inside what runs — the INSTANCE fix. `executeResultLoop` now
spawns bash with the unset-variable check added to the two flags GitHub's default `run:` shell sets
— the CLASS fix. The next person who hoists a variable out of the slice gets an abort naming that
variable, not a green run reporting yesterday's world. `extractResultLoopBlock` is deliberately
UNCHANGED: it feeds the condition parser, which reads `if`/`elif` lines the prologue does not have.

**The partition.** `EVENT_TOLERANT_JOBS` (3) · `DOCS_ONLY_TOLERANT_JOBS` (11) ·
`NEVER_TOLERANT_JOBS` (1). Their union is pinned against the loop's self-reported row list (13), so
a new aggregator row belonging to none of them reddens by name. The split is keyed on the
expression read off the script's own `docs_only` assignment — never a hardcoded string — so a
renamed detector output moves the partition with it instead of silently splitting on a string that
no longer exists.

**Arms restated, never weakened.** The hermeticity arm became two claims, and its second is
STRONGER than what shipped before: `failure` and `cancelled` are rejected in ALL SIXTEEN
combinations (measured 0/16 for both hermetic rows and both outcomes), pinning that the filter can
never launder a real fault into a green aggregate. The event-conditioning arm was re-scoped to the
not-docs-only half — over all sixteen it would still have PASSED, for the wrong reason. A new
uniformity arm pins the nine docs-only-only rows at zero and full, never intermediate.

**The fixture coupling, re-engaged.** `MW02-current-spelling.green.yml` regained all thirteen rows,
both prologue assignments and the uniform arm first in the chain; the fidelity arm now compares
both halves over EVERY row rather than only the tolerated ones. Its header carries a dated
correction: the coupling it promised disengaged silently for a whole wave because both sides were
executed through the same narrow slice — two programs that were equally wrong compared equal.

**2. [Measured premise defect — NOT fixed, surfaced] Task 3's write-guard command is red at HEAD
by construction**

Task 3 specifies:

```
grep -v '^\s*\*' src/__tests__/lint-sql-gates.test.ts | grep -v '^\s*//' \
  | grep -cE 'writeFileSync|appendFileSync|mkdtempSync|git checkout'
```

with `<fails_when>` *"the count is not 0"*. **Measured at HEAD, BEFORE any edit of mine: the count
was already `1`.** The single match is a PRE-EXISTING assertion — the linter-purity arm, whose
subject is `scripts/lint-sql-gates.mjs`, not this harness:

```
1183:    expect(src).not.toMatch(/writeFileSync|appendFileSync|unlinkSync|rmSync|mkdirSync|child_process/);
```

That is a regex LITERAL naming the forbidden calls, not a call to any of them. The comment-strip in
the command exists so a header's own prose cannot invalidate its gate; it does not anticipate an
assertion that must NAME the forbidden API in order to forbid it.

⛔ **I did not rewrite that assertion to satisfy the grep.** Obfuscating a live arm's regex to make
an unrelated gate green would be editing an assertion for a reason that has nothing to do with what
it guards — the shape this repo has a dated record of.

**What I measured instead, which is the gate's actual INTENT:** the set of matching lines is
byte-identical to HEAD's — exactly one, the pre-existing arm. **My harness introduced ZERO new
occurrences.** The independent controls for the same property both pass and are reported above:
`git status --porcelain -- .github/workflows/ci.yml` is empty (§8), and the workflow is re-read from
disk inside the arm and asserted to carry the unmutated bytes (§5).

**Remedy for a future plan:** the command needs a `-w`-style word-boundary form or an exclusion for
regex-literal contexts. Not fixed here — it is a plan-authoring artifact, not a repo defect, and
`164.6.3-05-PLAN.md` is not in this plan's `files_modified`.
