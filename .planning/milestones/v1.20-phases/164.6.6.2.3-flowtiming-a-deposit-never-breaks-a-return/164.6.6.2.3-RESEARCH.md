## Summary

The defect is two arithmetic conventions in one pure module. `_guard_denominator` refuses a day when `|flow| >= 1.0 x prev_nav` (`flow_dominated_guard`) and, on day 0 of a full-history ledger, labels the exact-zero pre-inception base by the sign of float noise (`negative_nav_guard` / `dust_nav_guard`). `chain_linked_twr` then divides by the start-of-day NAV with the day's flow in the numerator, so a deposit that funded the day's positions inflates the day's return (a 1.0 BTC deposit on a 0.1 BTC base, later 1% on the 1.1 BTC that traded, reads +11% with the end-of-day formula; computed in this session). Nothing in the codebase today carries an hour-and-minute for a flow or a position open past the first fold: every producer buckets to a UTC day string (`ExternalFlow(utc_day_iso, ...)`).

**What the data allows (D-10).** Only **MT5** has both halves in the data the worker already fetches: every `history_deals_get` row carries `time`/`time_msc`, `type`, `entry`, `position_id` (official TradeDeal field list), the deal list sits in memory at derive time, and the realized-basis MT5 NAV is exactly the running balance, so a sub-period split at flow instants needs no mark-to-market. Deribit and the ccxt venues carry flow timestamps but no position-open time on the series path; sFOX carries flow timestamps and a sampled end-of-day NAV with no positions; Binance and sFOX have no keys on PROD. Recommendation: **intraday timing for MT5 only; every other venue takes D-07** (named per strategy as an info note). Deribit is the one judgement call (raw log has `open buy`/`open sell` sides and ms timestamps) and is listed as Open Question 2.

**PROD census (2026-10-11, marker verified).** 11 of 43 `strategy_analytics` rows carry a retired-or-day-0 guard: dust 8, negative 7, flow_dominated 10, pnl_dominated 0. All 9 MT5 strategy rows carry at least one; the other 2 are a stitched composite and its failed twin; 0 of 5 Bybit/OKX rows. The CONTEXT's "12 of 24" is now "11 of 23" `csv_source` rows. The day-0 cause is confirmed at the **per-key series level** (8 of 8 MT5 keys and 9 of 9 Deribit keys have their first stored return 1 or 2 days after their first flow, and every interior missing day - 6 MT5, 79 Deribit - sits on a flow day); it cannot be proven row by row from stored data because strategy-mode derives store neither flows nor the deal ledger. The dry run (D-13) is the only row-by-row proof.

**Two findings that change the plan's shape.**
1. **The allocator compose is NOT inert to the new return convention for MT5 keys (contradicts the D-14 premise).** `replay_key_equity` rolls levels backward with `equity_{t-1} = (equity_t - F_t - P_t)/(1 + r_t)`. That identity holds only for the end-of-day return. All 8 PROD MT5 `key_inputs` rows lack the writer-basis fields (`composed_day_pnl`, `composed_flows`); only Deribit has them (8 of 9). With a cohort return the legacy inversion mis-states the prior level by about 9-10% on a MM-2x-shaped flow day (computed: 0.1099 against a true 0.1). The fix is derive-side (also store the writer basis for MT5 keys), not a compose code change; see Pitfall 1 / Open Question 1. The founder should be told before the plan locks D-14.
2. **D-05 plus D-07 means non-MT5 flow days now emit end-of-day-convention returns that can be inflated** (the +11% against a true +1% shape above) where they used to be NaN with a warning. `pnl_dominated_guard` (10x) is the only remaining backstop. This is the founder's accepted outcome, but the dry run must size it per venue before the plan ships (Open Question 3).

**Primary recommendation:** put the sub-period arithmetic in a new pure helper inside `nav_twr.py` called from `chain_linked_twr` for days that carry a `DayTiming` record (additive keyword, default `None`, byte-identical when absent); build `DayTiming` in the MT5 fold (`_fold_mt5_deals`, the single deal pass) from `time_msc`, `type`, `entry`, `position_id`; delete the flow clause from `_guard_denominator` and the key from `NAV_TWR_GUARD_KEYS`; add `flow_timing_day_level` as an annotation (outside the guard keys, like `small_base_measured`); add the MT5 writer-basis to the key_inputs payload so the compose levels stay exact.

### Pattern 1: Cohort sub-period return (the arithmetic for D-02/D-03/D-04/D-09)
**What:** For a UTC day with start-of-day NAV `prev`, flows `f_1..f_m` at instants `tau_1 <= ... <= tau_m`, define bases `B_0 = prev`, `B_k = prev + f_1 + ... + f_k`. A trading cash effect with open instant `o` belongs to cohort `k = bisect_right([tau_i], o)` (a deal at exactly `tau_i` lands AFTER flow i: flow first, D-09). An overnight position (`o` before the day) belongs to cohort 0 (D-04). `P_k` is the cohort's summed cash effect. The day's return is `prod_k (1 + P_k / B_k) - 1`, skipping any cohort `k > 0` with `P_k == 0` (no position was opened on that capital, so no return and no guard).
**When to use:** only for a day with a `DayTiming` record. A day without one uses the existing end-of-day formula.
**Properties (all verified by hand in this session, to be proven by the Fraction oracle):**
- No flows: one cohort, `P_0/prev`: byte-identical to today.
- A flow after every open: all P in cohort 0, `r = P/prev` = today's `(cur - prev - F)/prev` (since `cur = prev + P + F`).
- Deposit before any open: `r = P/(prev + F)` (today's formula would give `P/prev`).
- `sum_k P_k` equals the day's P&L, so the day-end NAV levels are unchanged: only `r_t` moves.
**Example (illustrative; arithmetic verified in this session):**
```python
# prev=0.1, deposit 1.0 before the day's trading, P=+0.011 realized that day
# today's end-of-day formula:  (1.111 - 0.1 - 1.0) / 0.1 = 0.11    (+11%)
# cohort formula (D-02):        0.011 / (0.1 + 1.0)       = 0.01    (+1%)
# legacy compose inversion with the cohort r:  (1.111 - 1.0) / 1.01 = 0.1099  (true prev 0.1)
```

### Pattern 2: Day-0 inception (D-01 / D-12)
**What:** At `t == 0` with `prev0 is None`, when the caller declares the account full-history, the day's own flow is positive, and `abs(prev) <= floors.residual_abs_tol`, the pre-inception base is zero by construction. Float residue of either sign is not evidence. With a `DayTiming` for day 0, run the cohort formula with cohort 0 expected empty (`P_0 == 0`); a non-zero `P_0` on a zero base is a real anomaly and keeps the negative/dust guard. Without timestamps the day is NaN with no flag (the inception day).
**Why the tolerance:** `UnitFloors.residual_abs_tol` is the module's existing "zero within the unit's reconciliation tolerance" constant (USD 1.00, BTC 1e-6) and is what the debug note recommended. Scope the rule to `t == 0`; interior near-zero bases keep the guards (D-06).

### Pattern 3: Carrying an annotation (the `small_base_measured` precedent)
`flow_timing_day_level` must be added in the same six places `small_base_measured` already occupies: `NavTWRMeta` + `NAV_TWR_ANNOTATION_KEYS` + the `_build_nav_meta` carry (nav_twr), the `_prestamp_flags` block (job_worker), `DataQualityFlags` + the `existing_flags` carry (analytics_runner), `singleKeyDataQuality` (composite-read-path.ts), `BuildFactsheetOpts["dataQuality"]` (types.ts), the caveat paragraph (FactsheetView.tsx). Deliberately NOT in `NAV_TWR_GUARD_KEYS` (no status promotion).

### Anti-Patterns to Avoid
- **Inventing a time:** a flow or open without a resolvable instant takes the whole day to the day-level rule. Never default a missing time to midnight or noon.
- **A second deal pass:** `_fold_mt5_deals` is the one classification fold with three consumers. Extend it; do not re-run `classify_deal` elsewhere.
- **Calling `reconstruct_nav_and_twr` without `timing` in `reconstruct_mt5_nav_levels`:** that function takes its `meta` from a second `reconstruct_nav_and_twr` call "so the DQ-01 guard flags ... are identical facts about ONE reconstruction". Pass the same `timing` or the levels path and the returns path disagree about flags.
- **Substitution patterns in `nav_twr.py`:** `tests/test_nav_twr.py::test_no_forbidden_denominator_guards` greps non-comment lines for `\.replace\(0`, `\.clip\(`, `np\.clip\(`, `max\([^)]*floor`, `np\.maximum\(`, `\.fillna\([1-9]`. A helper written with `max(x, floor)` or `np.maximum` fails that gate.
- **Raw magnitudes in flags/logs/errors** (T-73-02): the new annotation is a bool only, any count is an int, never a NAV or flow amount.

## Common Pitfalls

### Pitfall 1: The allocator compose inverts the return with the end-of-day identity (contradicts D-14 for MT5)
**What goes wrong:** `replay_key_equity` (legacy branch) computes `equity[t-1] = (equity[t] - F_t - P_t) / (1 + r_t)`. With the cohort return the pair `(r_t, F_t)` no longer satisfies it. Worked example (this session): `prev 0.1`, deposit `1.0`, `P = +0.011`: cohort `r = 0.01`, inversion gives `0.1099` against the true `0.1`; a two-cohort day gives `0.1088` against `0.1`. The forward self-check `_assert_forward_agreement` checks the same identity against the same rolled levels, so it will not flag it; the error is silent and compounds into every earlier level and the D-06 book-return weights.
**Why it happens:** the compose was built when `r_t` was always `(NAV_t - NAV_{t-1} - F_t)/NAV_{t-1}`.
**How to avoid:** give MT5 keys the writer basis Deribit already has: also persist `composed_day_pnl` and `composed_flows` in the MT5 `key_inputs` payload (the values are `mt5_day_pnl` and the event-time flows, both already computed in the same derive). `replay_key_equity`'s writer mode uses `equity[t-1] = equity[t] - F_t - P_t` with no return factor, so the return convention stops mattering. It engages only when every return day is in W (or carries a stored 0.0), every writer flow day is in W, and `realized_terminal` is on `max(W)`; check those conditions on MT5. This is a derive-side payload change, not a compose code change; the founder should confirm it sits inside "no separate compose change".
**Warning signs:** a compose test with one timed flow day whose rolled prior level differs from the writer's NAV; `writer_basis_mismatch` flag set on an MT5 key.

### Pitfall 2: Deleting the flow clause makes non-timed flow days emit inflated returns
**What goes wrong:** `(cur - prev - F)/prev` with a deposit that funded the day's trading divides the day's P&L by a base that excludes the deposit: +11% where the position-relative truth is +1% (example above). Previously the day was NaN plus a warning.
**Why it happens:** D-05 removes the guard, D-07 keeps the end-of-day rule where no time exists.
**How to avoid:** do not add a substitute guard (D-05 is locked). Size it: the dry run reports, per non-MT5 strategy and key, the flow days that newly gain a return and the largest `|r|`. `pnl_dominated_guard` (10x the base) still fires on the extreme cases. Raise the number at plan review (Open Question 3).

### Pitfall 3: Server-time offset and DST
**What goes wrong:** `MT5_SERVER_UTC_OFFSET_S` is one fixed env integer (`10800`, EEST), so the day bucket is off by an hour after the Oct/Mar DST transitions [CITED: TODOS.md "Server-UTC offset now SET (2026-07-25)"]. Flows and deals share the broker clock, so their RELATIVE order (all that D-03/D-09 need) is exact; only which UTC day a deal near midnight lands on is affected.
**How to avoid:** apply the same integer to the instant helper; never add a second offset. Record the DST limit as a Note, not a defect of this phase.

### Pitfall 4: Dropping the retired key makes a CSV-only recompute lose the stored flag
**What goes wrong:** `analytics_runner` rebuilds `data_quality_flags` wholesale and re-adds only keys in `NAV_TWR_GUARD_KEYS` from `existing_flags`. If `flow_dominated_guard` leaves the tuple, any CSV-only re-run before the Wave 5 derive silently drops the stored flag while the day is still absent from `csv_daily_returns`. D-14 says stored rows keep their flags.
**How to avoid:** keep a carry-only `NAV_TWR_LEGACY_GUARD_KEYS = ("flow_dominated_guard",)` (never emitted, never in the TypedDict the core returns) read by `analytics_runner`'s carry and `job_worker` composite drop-stale loop; or accept the drop and say so. A test must pin whichever is chosen. TS readers must ignore the key regardless (D-14).

### Pitfall 5: Interior `prev` near zero is not inception
**What goes wrong:** relaxing day-0 handling globally would hide a real emptied-account day. **How to avoid:** the inception rule is `t == 0` only, requires `prev0 is None`, `flow_0 > 0`, `full_history`, and `abs(prev) <= floors.residual_abs_tol`; every other near-zero base keeps `negative_nav_guard`/`dust_nav_guard` (D-06).

### Pitfall 6: Position id and entry semantics
**What goes wrong:** commission/fee-only deals (types 7..11) carry no `position_id` (`0`), scale-ins have several `IN` deals, reversals are `DEAL_ENTRY_INOUT`, and a `DEAL_ENTRY_OUT_BY` closes against an opposite position. **How to avoid:** a deal with no resolvable open (missing `entry`, missing `position_id`, a position whose `IN` deal is absent from the ledger on a non-overnight day) makes that whole day day-level (D-07), flagged `flow_timing_day_level`; an account-level fee deal (no position) is assigned by its own instant. Pin each case with a fixture.

### Pitfall 7: Tests that pin the retired flag move
See the census below. A test that asserts `flow_dominated_guard is True` becomes a test that the day is measured; the replacement must still be able to fail (neuter the cohort split and see RED).

### Cohort helper skeleton (shape only; the planner owns the final form)
```python
class DayTiming(NamedTuple):
    """One UTC day, pure data built by a venue fold. Instants are UTC epoch milliseconds."""
    flows: tuple[tuple[int, float], ...]               # ascending by instant
    pnl: tuple[tuple[int | None, float], ...]          # (open instant | None = opened before the day, cash)

def _timed_day_return(prev: float, timing: DayTiming, floors: UnitFloors) -> tuple[float, str | None]:
    instants = [t for t, _ in timing.flows]
    bases = [prev]
    for _, amount in timing.flows:
        bases.append(bases[-1] + amount)
    cohort_pnl = [0.0] * len(bases)
    for open_ms, cash in timing.pnl:
        k = 0 if open_ms is None else bisect_right(instants, open_ms)   # flow first on a tie (D-09)
        cohort_pnl[k] += cash
    growth = 1.0
    for k, (base, pnl) in enumerate(zip(bases, cohort_pnl)):
        if k > 0 and pnl == 0.0:
            continue                                   # nothing opened on this capital
        key = _guard_negative_dust(base, floors.dust_nav)
        if key is not None:
            return float("nan"), key
        if abs(pnl) >= PNL_DOM_RATIO * base:
            return float("nan"), "pnl_dominated_guard"
        growth *= 1.0 + pnl / base
    return growth - 1.0, None
```
The sketch uses no clamp, floor, `np.maximum`, `.clip(` or `.fillna(` so it clears the substitution source-scan.
