### What I traced and found sound

**First-pass lock order.** `mark_compute_job_failed` takes F `FOR UPDATE` in its first SELECT. It then reads the closure and locks it with ONE helper call. Every closure row is a strict descendant of F, so it has a greater longest-chain depth than F. `parent_job_ids` is fixed at insert, so the depth key is stable across transactions. The cascade's first pass is therefore globally ascending.
- `mark_compute_job_done` ascends: its own row, then its children.
- The enqueue ascends: the helper `FOR SHARE`, then a fresh-snapshot status read.
- An ascending acquirer cannot form a cycle with another ascending acquirer.

**The enqueue's in-flight unique insert.** It cannot close a cycle with the cascade. Its optimistic lookup reads the committed in-flight version of any row the cascade has updated, and returns that id instead of inserting. So it never waits on the cascade's xid while holding a parent share lock.

**The FL4 and FL5 arms are real races.**
- AFTER ROW stall triggers fire at the end of the level-1 statement, so the twin reproduces the per-level hold-and-wait (D held, B wanted).
- FL4's twin (`JOIN clo ON FALSE`) pushes B into a second pass.
- FL5's twin (`= ARRAY[clo.id]`) drops the multi-parent rows.
- Both arms assert `40P01` absence and the final states. Their SETUP guards fail loud when the interleaving was not set up.

**Termination.**
- The recursive CTE uses `UNION`. PostgreSQL appends to the working table only the rows not already in the result, so a cycle or a self-reference (`parent_job_ids @> ARRAY[self]`) ends.
- The inner level loop exits when a level fails nothing. Each UPDATE moves rows out of `done_pending_children`, so it is finite.
- The outer loop exits when a pass fails nothing. Every pass that continues has moved at least one row to a terminal state.
- No closure row can be released by a concurrent `mark_compute_job_done`: level-1 rows have a `failed_final` parent, and deeper rows have a `done_pending_children` parent. So "closure non-empty, nothing failed" happens only when another cascade already failed those rows. That cascade also owns their late-born children through its own second pass.

**The WR-01 existence test** (`bridge_outcomes_sync_holding_ref`). I checked visibility and concurrency case by case:
- **The `ON DELETE SET NULL` cascade.** The RI action runs as a later command of the deleting transaction. The trigger's SELECT therefore runs under a new command id, and the deleted decision is invisible to it. Result: `former = OLD.match_decision_id`. OD1 and OD2 agree.
- **A concurrent decision delete (T2) and owner detach (T1) on the same outcome:**
  - T2 commits first: T1 re-evaluates under EvalPlanQual and sees `OLD.match_decision_id IS NULL`, so it keeps `former = D`. Correct.
  - T1 commits first: T1 saw D still present, so it stored `former = NULL`. T2's RI UPDATE then re-checks the row, finds it no longer references D, and skips it. The result is a born-NULL row, which is the right reading of a voluntary detach.
  - T2 has deleted D but not committed when T1's trigger runs: T1 still sees D and stores NULL. T2's RI waits on T1's row lock, then skips the row. Same result.
- **No interleaving records a former id while the decision still exists.**
- **RLS does not apply.** The function is `SECURITY DEFINER`, and the owner bypasses RLS on `match_decisions`, so a decision the caller cannot see still counts as existing.
- **No app path is affected.** No application path writes `match_decision_id = NULL` (grep over `src/`, `analytics-service/`). So the new 23505 on a voluntary detach that has a born-NULL sibling reaches no user flow.

**Re-base.** No migration after `20261009120000` redefines `mark_compute_job_failed`, `mark_compute_job_done`, the enqueue, or the sync trigger. That includes `20261023120000` from #1050, which only self-verifies the old literal and runs before this file in filename order.

## Warnings

### WR-01 (MEDIUM, WARNING): the cascade's second pass still locks out of order, and the header's reason it cannot deadlock is false

**File:**
- `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql`, the outer `LOOP` of the cascade. The second `PERFORM public._fan_in_lock_rows(v_kids, TRUE)` runs while the first pass's rows are still held.
- The claim is in the header paragraph at `:79-85`: "they are new rows that only their creator knows". It is repeated in the body comment: "the only transactions that can know them are the ones that created them".

**Issue:** pass 2 locks a row X born during pass 1's lock wait. Pass 2 runs while the cascade still holds every pass-1 row, including rows DEEPER than X. That is exactly the hold-deep, wait-shallow order that CR-01 removed from pass 1.

The disclosed justification does not hold. Once X's enqueue commits, X is visible to every transaction:
- to another cascade's closure read;
- to any enqueue that names it as a parent.

So other transactions can know X.

**Failure scenario 1: two cascades.**
- Graph:
  - F1 and F2 are running.
  - A has parents [F1], depth 1.
  - The chain C2..C4 hangs below A.
  - D has parents [C4, F2], depth 5.
- Run:
  1. Cascade 1 (F1 ends `failed_final`) reads its closure {A, C2, C3, C4, D}. It waits on A, because an enqueue E1 holds A `FOR SHARE`.
  2. E1 commits X, with parents [A, F2] and depth 2.
  3. Cascade 1 locks A..D, fails them, and starts pass 2 for X. It holds D at depth 5.
  4. Meanwhile cascade 2 (F2 ends `failed_final`) has read the closure {X, D}. It locks X first (depth 2) and then waits on D.
  5. Cascade 1 waits on X while holding D. Cascade 2 waits on D while holding X.
- Result: SQLSTATE 40P01.

**Failure scenario 2: an enqueue.** The second actor is an enqueue E2 naming [X, D], which starts after E1 commits. E2 share-locks X, then waits on D. Cascade 1 holds D and wants X `FOR UPDATE`. Result: 40P01.

**Impact:**
- PostgreSQL detects the deadlock and aborts one transaction.
- An aborted `mark_compute_job_failed` leaves its job `running` until the watchdog reclaims it. No row is corrupted.
- The surviving cascade does not fail the rows the aborted one owned. Only the reclaim and rerun reach them.
- **Latent today.** D-04's census says PROD holds no parented rows, and no caller passes parents. But the header states "no 40P01" as a rule ("every path ascends the same key, so none exists"), and the stated exception is mis-argued. The next phase that adds a parent-passing caller would inherit a false safety claim.

**Fix:** pick one of these.

(a) **Make pass 2 truly ascending.** Do the read, lock and re-read inside a subtransaction. If the closure grew during the wait, roll back to the savepoint (which releases those row locks) and retry with the larger set. One ascending call then covers everything.

```sql
LOOP
  BEGIN
    -- read closure into v_kids (as now)
    PERFORM public._fan_in_lock_rows(v_kids, TRUE);
    -- re-read the closure; if it holds ids not in v_kids, raise a private
    -- SQLSTATE so this block's subtransaction rolls back and drops the locks
    ...
  EXCEPTION WHEN SQLSTATE 'P0F1' THEN
    CONTINUE;  -- retry with the grown closure
  END;
  -- level-by-level UPDATEs over the locked v_kids (as now)
  EXIT;
END LOOP;
```

(b) **Keep the second pass, but tell the truth about it.** Replace "only their creator knows / PROD holds none" at `:79-85` and in the body comment with the two scenarios above. Say plainly that a 40P01 is possible there and is answered by deadlock detection plus the watchdog reclaim. Book it in TODOS against the first caller that passes parents.

### WR-02 (MEDIUM, WARNING): the second pass, which keeps late-born children from stranding, has no gate that can fail

**File:**
- `supabase/migrations/20261024120000_fan_in_graph_and_decision_cascade.sql`, the outer `LOOP` and `EXIT WHEN NOT v_progress;`.
- The gates `supabase/tests/test_fan_in_lock_order_race.sql` (FL1 to FL5) and `supabase/tests/test_fan_in_failure_cascade.sql` (FC1 to FC8).

**Issue:** the outer loop exists for one case (the fixer's own comment). An enqueue E holds a closure row A `FOR SHARE`, the cascade waits on A, and E commits a child X as `done_pending_children`. X has to commit before A fails, because the cascade's `FOR UPDATE` on A waits for E. Without pass 2, X keeps a `failed_final` parent and can never be released, which is the stranding D-01 exists to end.

No arm reaches this case:
- FL3, FL4: the enqueue is refused 22023, so no child is ever born.
- FL5: no enqueue.
- FC5's twin: it edits `EXIT WHEN NOT v_progress;` only together with the level-loop exit. It does so to defeat the masking between the two loops, not to test pass 2.

The mutation `EXIT WHEN NOT v_progress;` → `EXIT;` on its own still runs the whole pre-existing closure in pass 1. By reading, every one of the 13 arms stays green under it. **I did not execute it.**

So the code that keeps a late-born child from stranding (user-facing: its strategy reads `computing` forever) ships unverified. `ARMS_FLOOR` 743 does not count it.

**Fix:** add an FL6 arm with the existing dblink and stall machinery:
1. F is running, and A is a waiting child of F.
2. Backend e enqueues X with parents [A]. An AFTER INSERT stall trigger bound to X's strategy parks e after its INSERT, while it still holds A `FOR SHARE`.
3. Backend m marks F permanent and is seen waiting (not granted) on a row lock.
4. Release the stall. e commits, then m finishes.
5. Assert: no SQLSTATE on either side, X reads `failed_final`, and X's `last_error` names A in its first 60 characters.

Twin: `EXIT WHEN NOT v_progress;` → `EXIT;`. No anchor reads that line, so no stand-down is needed.
