# Phase 164.6.6.2 Plan 14: the BTC dust floor drops to 1e-7 Summary

**A BTC-denominated MT5 account is now measured down to a base of 1e-7 BTC instead of 0.001 BTC (founder decision D-24), with `material_equity` and `residual_abs_tol` left in place after every consumer of the three floors was read.**

Plan number: `164.6.6.2-13` already exists (the merged Python conversion twin), so this gap closure is 14.

## Decision quoted and followed

CONTEXT D-24: "it should measure more. at least to 0.0000001". The BTC `dust_nav` floor drops from 0.001 to **1e-7 BTC**. "`material_equity` and `residual_abs_tol` were orchestrator-scaled from D-20 (Claude's Discretion below) and are NOT founder values; whether they must move with the floor is measured in the gap-closure plan, never assumed."

## Consumers of the three BTC floor values (all read)

| Value | Consumer | What it does with it |
|---|---|---|
| `dust_nav` | `nav_twr.chain_linked_twr` -> `_guard_denominator` | `0 < prev < dust_nav` is `dust_nav_guard` (NaN day). The only place the floor decides a return. |
| `dust_nav` | `nav_twr.reconstruct_nav_and_twr` | the terminal uPnL-wedge materiality test is evaluated only when `anchor > dust_nav` |
| `dust_nav` | `job_worker` (belt-and-braces wedge flag) | same test on `_mt5_equity > floors.dust_nav` |
| `material_equity` | `mt5_read` history settle wait | `abs(equity) > material_equity` decides whether a zero-deal count may settle |
| `material_equity` | `job_worker` material-equity refusal | `abs(equity) > material_equity` and fewer than two usable days is a permanent failure |
| `residual_abs_tol` | `nav_twr.reconcile_flow_residual` | the band is `max(residual_abs_tol, 1e-6 * |terminal|)`, a roll-vs-sum self-check; raises on a dropped flow |

Also read: the broker_dailies pass-through (`floors=` keyword), the sFOX, Deribit and ccxt callers (USD row, untouched), and the tests that pin the row. There is no TypeScript or SQL mirror of any of the three (`grep -a` over `src`, `scripts`, `supabase`, tests and docs).

**Invariants between the three:** none in code. No consumer compares one floor with another, and no test asserts `dust_nav >= material_equity` or any ordering. The one cross-value pin was `test_account_unit.py`'s "material and residual equal the USD row times dust_nav / 1000", which encodes the orchestrator's scaling rule, not a requirement of the logic; it is replaced by literals (see Deviations). **Nothing forced `material_equity` or `residual_abs_tol` to move, so the stop-and-report condition did not trigger.**

Observation, not a coupling: the row is now `dust_nav` 1e-7 < `residual_abs_tol` 1e-6 < `material_equity` 1e-4, the reverse of the USD row, where dust (1000) is above material (100) is above residual (1.00). It is deliberate and the row's comment says so.

## Founder follow-up: MM-2x's actual shape (2026-10-08, from his MT5 screenshots)

1. **Exact oracle.** `test_mm2x_shape_every_small_balance_day_is_measured_and_exact` builds the ledger in `Fraction`: deposit 0.1 (2025-10-16), deposit 1.0, five trading days, a near-total withdrawal (derived so the ledger closes exactly to 0.00961461), then ten small-balance trading days with P&L from 2e-5 to 5e-4. Expected return per day is `pnl / prior NAV` in `Fraction`. Every day after the second ledger day is measured (never `dust_nav_guard` NaN) and matches to 1e-12. Two lower-balance variants of the same shape (terminal 5e-4 and 3e-6 BTC, trades scaled) are measured too; those are the ones the old floor guarded.
2. **Pre-inception.** The reconstruction's index starts on the first ledger day (deposits and trades are unioned into it, `gap_fill_daily_returns` reindexes only `[first, last]`), so no row exists for any earlier calendar day. Day 0's base is `NAV_0 - pnl_0 - F_0`, the opening capital, which is zero in theory and only float noise (about 1e-17) or an incomplete ledger leaves a residue R there. Measured sweep of R in {0, 5e-8, 1e-7, 3e-5, 5e-4, 0.02, 0.2}: day 0 is NaN for every R up to the deposit (negative or dust guard for float noise; `flow_dominated_guard` once R >= 1e-7 because the 0.1 deposit is at least the base, `FLOW_DOM_RATIO` 1.0), and for R = 0.2 (larger than the deposit) it is exactly 0.0, a deposit-only day with no P&L. **The code does not emit a residue-return at 1e-7**, so the stop condition did not trigger. The range the old floor hid as dust (3e-5, 5e-4) is stopped by the flow guard instead. `test_no_return_is_emitted_before_the_first_deposit` pins it for all seven residues.
3. **Floors against MM-2x's scale** (balance 9.6e-3, smallest trade 2e-5): `material_equity` 1e-4 is an account-level equity test (the balance is 96 times it) that never looks at a single trade, so it cannot drop a day. `residual_abs_tol` 1e-6 is a whole-series roll self-check on float residuals of about 1e-16; it drops no day, and a dropped 2e-5 flow is 20 times the band so it still raises (`test_reconcile_residual_tolerance_catches_the_smallest_mm2x_trade`). Neither distorts a real MM-2x day. Neither changed.

### Design decisions

| Question | Decision | Why |
|---|---|---|
| Where is it detected | `nav_twr.chain_linked_twr`, after the day passes every guard and `returns[t]` is set: `prev < floors.material_equity` | A guarded day is not a measured day; the day keeps its return (no `continue`). |
| Does it make the status `complete_with_warnings` | **No.** It is NOT a `NAV_TWR_GUARD_KEYS` member. `_build_nav_meta` warns on any key outside `NAV_TWR_ANNOTATION_KEYS`, so the old `bool(flags)` behaviour is exactly preserved for every existing key | Matches `native_unit` and `insufficient_window`. Promoting would mark every BTC account with one tiny-base day as warned and withhold it in founder-lp strict mode, for a caveat the page already prints. The founder said informational. |
| Chain break | **No.** Not `twr_chain_broken`; the day is not NaN, so `cumulative_twr_segmented` sees no interior break | pinned by tests that the cumulative is the exact product |
| What is persisted | the bool `small_base_measured` only. The day count and the smallest prior NAV live in the in-process meta (logs, tests) | the smallest prior NAV is an account-size magnitude (T-73-02) |
| Path to `data_quality_flags` | `nav_twr._build_nav_meta` (own present-only carry) -> `job_worker` derive pre-stamp (outside the guard loop, like `native_unit`) -> `analytics_runner` wholesale rebuild (outside both `_warned` loops) | an unbridged pre-stamp is wiped by the rebuild |
| USD | **Exactly unchanged, by construction.** `dust_nav` 1000 is above `material_equity` 100, so a USD prior NAV under 100 is dust-guarded before the check runs; the flag cannot fire for USD, ccxt, sFOX, Deribit or native-NAV paths (all use the default USD row). No existing test needed a change for USD. | `test_small_base_is_unreachable_for_the_usd_row` |
| TS closed set | None exists. `grep -a` over `src`, `supabase`, `scripts` and `docs` finds no TS or SQL mirror of the guard keys (the only mirror is the Python `NAV_TWR_GUARD_KEYS == {...}` pin, which is unchanged because the flag is not in it). `singleKeyDataQuality` is the ONE owner that lifts persisted flags to `dataQuality`. | `test_small_base_is_an_annotation_not_a_guard_key` pins the non-membership |
