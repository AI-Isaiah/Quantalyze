# Phase 166.2 COMPUTEONCE: silent-failure review, round 4 (confirmation)

Scope: the round-3 fix pass, `ceb73b631..HEAD` outside `.planning/`, at HEAD `cd2349d42`. Cited by
symbol only. The brief asks three things: (a) are SFH-R3 HIGH-1 (`calmarByYear`) and HIGH-2
(Profit Factor) closed, (b) did the pass add a new HIGH or CRITICAL silent failure, and (c) how to
rate three `: 0` fallbacks outside the fixer's files.

**Measured, not argued.**
- One temporary tsx probe ran against the worktree's `src/` from the session scratchpad. It was
  deleted afterwards and never committed.
- The probe series were all synthetic: a constant daily yield (+0.02% for 400 days), an all-zero
  series, an all-positive dispersing series, the same series with one small loss every 100 days, an
  all-negative dispersing series, and a two-year series whose 2023 stub (20 days) is all gains.
- Vitest ran over `src/lib/factsheet`, `src/app/factsheet/[id]/v2`, `src/app/api/og` and the
  scenario payload widget directory: **84 files, 1,099 tests, all pass** at HEAD.

## Verdict in one paragraph

(a) Both round-3 HIGHs are **closed** at HEAD. I measured each on the real function, and each has a
render test that fails under the old `: 0` arm. (b) The pass added **no new HIGH or CRITICAL**. I
traced every production reader of the five `compute` fields and of the per-year Calmar. Each one goes
through a formatter that tests `Number.isFinite` (and therefore also handles the JSON `null`), or
through a comparison that is false for NaN and null. No reader sorts, ranks or exports these values.
The one arithmetic reader, the MetricsColumn common-sense ratio, cannot receive a NaN or a null
Profit Factor, because a negative 5th percentile implies a losing day (LOW-1). (c) None of the three
fallbacks is HIGH. The variance-contribution percentage is MEDIUM: it is pre-existing, separable
and on an authenticated widget, but it has a real silent path (MEDIUM-1). The `computeWinRate`
empty-input result has no production caller (LOW-2). The partner-ROI intros-per-manager row never
renders its 0 (not a finding).

## (b) New silent failures introduced by the fix pass: none at HIGH or CRITICAL

I checked every production reader of `profit_factor`, `avg_win`, `avg_loss`, `skew`, `kurt` and
per-year `calmar` (grep across `src`, tests excluded):

- **MetricsColumn** (Main Metrics, Returns, Max Drawdown and Extended Metrics). `num`, `pct` and
  `signed` all test `v == null || !Number.isFinite(v)` and return "—". `ratioStr` tests
  `Number.isFinite` on both arguments. The `accent={m.kurt > 6}` prop is false for both NaN and
  null.
- **Common-sense ratio in MetricsColumn** (`tailRatio * m.profit_factor`). This is the one
  arithmetic reader. It is safe by an invariant, not by a guard (see LOW-1).
- **The common-sense ratio inside `compute`.** The new comment's claim is true: `tailRatio` is
  non-null only when `p5 < 0`, which needs a losing day, and then `lossSum < 0`, so the Profit
  Factor is finite. In the probe, `common_sense_ratio` was null on every no-loss series.
- **Style drift** (`StyleDriftPanel` Skew and Kurtosis rows). `fmt` and `fmtDelta` test
  `Number.isFinite` on each operand, which also covers a JSON `null`.
- **Comparator column.** `buildComparatorBlock` copies `profit_factor` from the benchmark's own
  `compute`. It is rendered by `num(b?.profit_factor)`. Nothing else reads it.
- **Basis and leverage views.** `overlayBasisScalars` overlays only the seven `BASIS_KPI_MAP`
  headline scalars, and none of the five changed fields is among them. Under MTM or leverage, the
  changed fields come from `deriveSeriesBundle` over the same series as the quantiles, so the
  invariant behind LOW-1 holds on every basis.
- **Scenario body.** `emptyComputeSummary` already carried NaN for `avg_win`, `avg_loss` and
  `profit_factor` (D-26). The live scenario body calls the same `compute` and `calmarByYear` and
  renders through the same `FactsheetBody`.
- **Not readers:**
  - The OG route (`api/og/factsheet/[id]`) and the PDF route reference none of these fields.
  - `computePeerPercentile` ranks only Sharpe, Sortino and max DD.
  - `TradeAndPositionPanel`'s Profit Factor, Payoff and Expectancy read the trade-metrics row,
    not `compute`.
  - `allocator.ts` imports `compute` but only `void`s it.
  - No CSV exporter serialises `strategyMetrics` or `calmarByYear`.
- **Avg Win becoming NaN.** No production code divides by `avg_win` or `avg_loss` except
  `ratioStr`, which is guarded. No payoff or Kelly figure is derived from them anywhere in `src`.
  The probe shows Avg Win is NaN only on a series with no winning day (all zeros, all negative).
  On a constant positive yield it stays a real +0.02%.
- **Bootstrap caption at `n_valid === 0`.** The `used === 0` arm replaces the "from 0 of …"
  caption with "no resample has a {label}". The partial-survival arm is unchanged. The IN3-01 test
  fails under the old string, and its control pins the partial case.
- **Comment-only edits.** The four test files that named `factsheet-v2-payload-v6` now say `vN`.

## (c) The three `: 0` fallbacks outside the fixer's files

### MEDIUM-1 (pre-existing, separable): the variance-contribution percentage reads 0% for every strategy, with no cue, when the widget cannot measure risk

- **Location.** `computeRiskDecomposition` in `src/lib/portfolio-stats.ts` returns
  `percentage: portfolioVarianceIsReal ? (c / totalVariance) * 100 : 0`. It is rendered by
  `RiskDecomposition` (allocations → risk widget) as a bar chart of "Risk Contribution".
- **Paths that reach 0.**
  1. The book has no dispersion, such as constant yields (Phase 166.1 D-17 chose this on purpose).
  2. `buildCovMatrix` in `RiskDecomposition.tsx` finds **fewer than 2 dates common to every
     strategy**. It then returns an all-zero matrix, so every bar reads 0%. This is the real
     silent failure. "These strategies do not overlap" is shown as "every strategy contributes
     zero risk". Nothing is logged and no empty-state message appears. The existing empty state
     ("No strategy data for risk decomposition") fires only when there are no strategies at all.
  3. A NaN total also reads 0, for example when a NaN return in a strategy's daily series passes
     through the `dateMap`.
- **Why MEDIUM, not HIGH.**
  - The surface is an authenticated allocator widget, not the public factsheet.
  - The bars summing to 0% rather than 100% is a visible tell.
  - Path 1 is a recorded decision (166.1 D-17 / D-07).
  - Under D7's letter, a share of zero variance does not exist and would read "—". This widget,
    however, predates and sits outside this phase's surface.
- **D9 class.** Pre-existing and separable. The fix pass did not touch `portfolio-stats.ts` or the
  widget.
- **Recommendation.**
  - Have `computeRiskDecomposition` return `percentage: NaN` (or `null`) when
    `!portfolioVarianceIsReal`.
  - Have `RiskDecomposition` render an explicit empty state ("not enough overlapping days to
    split risk" or "no measurable portfolio variance") instead of a chart of zero bars.
  - Make `buildCovMatrix`'s `len < 2` case distinguishable from a real zero-variance book.

### LOW-2 (pre-existing): `computeWinRate` returns `{ winRate: 0, profitFactor: 0 }` on empty input

- No production caller exists: a grep of `src` outside tests finds only the definition. The fallback
  therefore cannot reach a page today.
- Its docstring already separates `null` ("infinitely good") from `0` ("no trades, or no wins").
  The empty-input 0 would be a D7 residue if a caller were ever added.
- D9: pre-existing. Record it, or delete the dead function.

### Not a finding: partner-ROI intros per manager per month

- `introsPerManagerPerMonth = managers > 0 ? introsPerMonth / managers : 0` in
  `admin/partner-roi/page.tsx`.
- Its only render site is wrapped in `{managers > 0 && introsPerMonth > 0 && (…)}`, so the 0 arm is
  never displayed.
- It is also an admin-only revenue simulator's input arithmetic, not a measured statistic.

### LOW-1 (latent; safe today): the MetricsColumn common-sense ratio relies on an invariant, not a guard

- `commonSenseRatio = tailRatio != null ? tailRatio * m.profit_factor : null`, in the Extended
  Metrics panel.
- After the JSON cache a NaN Profit Factor becomes `null`, and `x * null` is `0`, which `num` would
  print as "0.00". The TypeScript type (`number`) does not flag this.
- It cannot happen today. `tailRatio` is non-null only when the interpolated `q.p05 < 0`, which
  requires a negative daily return. That makes `lossSum < 0`, so the Profit Factor is finite.
  `q` and `m` come from the same series on every basis (cash payload, the MTM bundle, the levered
  `deriveSeriesBundle`).
- The fix pass added a comment stating this invariant for `compute`'s own floor-index tail ratio,
  but not for this second site.
- A one-token hardening would make it robust to a future change in either producer:
  `Number.isFinite(m.profit_factor)` in the condition.
