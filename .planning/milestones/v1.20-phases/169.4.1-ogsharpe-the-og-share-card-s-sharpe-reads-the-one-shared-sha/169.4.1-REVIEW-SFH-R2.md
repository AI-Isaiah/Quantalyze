## SFH-01: CLOSED

The embed select now projects `data_quality_flags` (`route.tsx:109`), and the route forwards it
(`route.tsx:196`). `computeOgHeadline` reads `twr_chain_broken === true || insufficient_window === true`
(`og-metrics.ts:78-83`). When either is set it hides the stored CAGR (`og-metrics.ts:129-130`). The
flag read matches the writer:

- `twr_chain_broken` is raised by `nav_twr.cumulative_twr_segmented` exactly when an interior break
  shortens the suffix (`nav_twr.py:555-559`), which is the same boundary `metrics.py:1854`
  annualizes over. It is a `NAV_TWR_GUARD_KEYS` member. The derive pre-stamps it, and the CSV hop
  carries it into the SAME `_mark_complete` upsert that writes `cagr`
  (`analytics_runner.py:1885-1893`, `:2022`). Flag and value are written together.
- `insufficient_window` is computed beside `cagr` at the CAGR site (`metrics.py:1871-1874`) and
  lifted into the same payload (`analytics_runner.py:1931-1932`).
- Fail direction: flags `null`, absent, `{}`, or a non-boolean `"true"` all show the stored CAGR.
  That is correct and not fail-open. A row without the flag has a full-span suffix, and pre-DQ-03
  rows annualized over the full span (`metrics.py:1852-1853`, "byte-identical" on a clean series).
  The route test `O1e` (`route.test.tsx:365`) and the two `it.each` tables in `og-metrics.test.ts`
  (`:234-251`: the hide cases, plus negative controls including the truthy non-boolean) pin both
  directions.

## Checked and cleared (no finding at MEDIUM+)

- **Leading-NaN suffix (DQ-02 flow-coverage terminus).** `apply_flow_coverage_terminus`
  (`nav_twr.py:690-720`) sets the pre-terminus days to NaN and stamps `flow_coverage_incomplete`, not
  `twr_chain_broken` (leading NaNs are not an interior break, `nav_twr.py:537-540`).
  `returns_for_chart = returns.fillna(0)` (`metrics.py:1743`), so `returns_series` covers the whole
  record. The card's 0.95-year gate therefore measures the full span, while the stored CAGR is
  annualized over the post-terminus suffix. This is the same window mismatch as SFH-01, and the card
  does not read `flow_coverage_incomplete`. Cleared for two reasons:
  (a) `insufficient_window` still hides any suffix under `MIN_ANNUALIZATION_DAYS = 90`
  (`metrics.py:74`). The writer treats 90 days as its own threshold for annualizing, and the
  retention windows are OKX 90 days and Bybit 365 days (`nav_twr.py:110-111`). An OKX suffix lands at
  89 or 90 days depending on whether the last PnL day is the compute day. At 90 days it is shown,
  which is at the writer's floor, not below it.
  (b) `headlineCoverageCaveat` (`MetricsColumn.tsx:41-53`) gates on `twrChainBroken` only, so the
  factsheet shows the same figure with no caveat. SC4 parity holds.
  If the card's 0.95-year rule is meant to bind the stored value's own window, the one-line extension
  is to add `flow_coverage_incomplete === true` to `storedCagrCoversSuffixOnly`. That is a
  display-policy choice, not a silent failure.
- **Flag and value written at different times.** `_prestamp_dq_flags` (`job_worker.py:6514-6518`)
  replaces the flags wholesale BEFORE the CSV hop rewrites `cagr`. While both hops run, a
  `complete_with_warnings` row stays rankable, because the status bridge preserves that status. For
  that window the row carries new flags beside the old `cagr`. The card fails open only if a
  previously chain-broken row re-derives as clean, which leaves the old suffix CAGR shown for the
  seconds between the two hops. That is transient and rare, the factsheet and lists show the same
  value in that window, and the ordering is a pre-existing writer property this phase does not touch.
- **Failure-path payload drops the flags.** `_guard_failure_payload_inplace`
  (`analytics_runner.py:1456-1461`) pops `data_quality_flags` on a protected refresh failure. It also
  leaves the old `cagr` in place, so the old flags and the old value stay a matched pair.
- **Throttle granularity.** `shouldCaptureNow("og-factsheet:<stage>")` is keyed per stage over a
  60-second window (`sentry-capture.ts:339`). N strategies failing in one minute produce one Sentry
  event. The per-call `console.error` keeps the id, so detail is lower but the failure is not silent.
- **Comment-only `catch {}` in `reportOgFailure`.** It guards only the scheduling of `after`. The
  primary log fires before the `try`. Not a swallow of the route's error.
- **Non-terminal row renders dashes under the long TTL.** This is STALE-01's designed answer
  ("analytics aren't ready"), not a failure path. It predates the fix and the fix leaves it unchanged.
