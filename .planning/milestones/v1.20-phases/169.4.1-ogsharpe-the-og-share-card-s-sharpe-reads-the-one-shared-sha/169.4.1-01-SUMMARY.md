## Deviations from Plan

1. **The plan describes the 166.2 side cases incorrectly (no code impact).** The plan and D-43 say both side cases, "CAGR hidden (NaN) for a dense sub-year series" and "single / duplicate / unsorted dates never produce Infinity", expect a NaN Sharpe on a constant series. At HEAD, 166.2's review round 1 (IN-03) had already changed the first one to a dispersing `alternating(300)` fixture that asserts a FINITE Sharpe. The operative rule, do not edit either case, was followed: neither was touched.
2. **TDD commit split.** The RED tests were committed first (`3cebcaaf3`, failing at that commit by design), then the implementation (`d0ec8d07d`).
3. **Executor protocol checks.** The worktree allow-list (`agent-*` branch namespace) would reject `feat/169.4.1-ogsharpe`, but that is the branch the orchestrator assigned, and it is not protected, so the commits were made there. The `node_modules` symlink is gitignored and was never staged; it was left in place, as the orchestrator's brief says, which replaces the plan's "remove before every commit" step.
4. **Route comment left as-is.** The STALE-01 comment in `route.tsx` still says the card "recomputes … IN-ROUTE". That is now true only for the fallback, and the new comment directly above the call explains the persisted arm. It was left alone to keep the change surgical.

## Notes for the orchestrator

- **Behaviour change on PROD cards.** A computed row whose stored `sharpe`/`cagr`/`max_drawdown` is NULL now shows "—" for that figure where it used to show a recomputed number. This is intended (a stored null hides, as on the lists), but a card may now show fewer figures than before for such rows.
- **Composites.** The card reads the top-level stored scalars, the same ones the lists rank on. For composites the factsheet headline overlays `metrics_json_by_basis.cash_settlement` instead. Whether those two agree for a composite is outside this plan and was not measured. Plan 169.4.1-02's browser re-check uses a single-key strategy.
- **Caching.** The OG response is cached `s-maxage=86400, stale-while-revalidate=604800`, and unfurl caches keep their own copies. Plan 02's post-deploy comparison should fetch the card fresh, with a cache-busting query, before comparing.
- No migration, no DB command, no push, and STATE.md / ROADMAP.md were not edited.
