# Phase 164.6 Plan 01: OPS-08-TS single 40001 retry Summary

**A lost enqueue race (SQLSTATE 40001) is now retried exactly once, immediately, at csv-finalize's analytics enqueue and at the allocator holdings sync RPC, through one stateless factory-taking helper in `src/lib/supabase/`. Each site's existing failure path runs unchanged once the retry is used up.**

## Accomplishments

- `retryOnceOnSerializationFailure(call, onRetry)` is the only export of a pure module with no imports and no timer. It returns after one call for any code other than `40001`. On a `40001` it calls `onRetry(first)` and then the factory once more, and returns that second result whatever it is.
- csv-finalize `enqueueCsvAnalyticsAfter` wraps `admin.rpc("enqueue_compute_job", …)`. The retried attempt is logged with `console.warn`, using the existing `logPrefix` and `correlation_id` framing, and is never sent to Sentry. Everything from `if (enqueueErr)` down is byte-identical. The `@audit-skip:` pragma sits within the 8-line window, and `audit-coverage.test.ts` passes.
- holdings sync `POST` wraps `supabase.rpc("request_allocator_holdings_sync", …)` on the unchanged user-scoped client. `createAdminClient` appears 0 times, the same as the base. The 403, 500 and audit branches are unchanged. The header JSDoc gains step 5, which explains why re-issuing the whole RPC is safe.
- D-08 prose: the `ENQUEUE_LOST_RACE_USER_COPY` JSDoc now says the route retries a 40001 once and that the copy is written only after that retry is used up. The `WR-07` comment above `let enqueueLostRace` is now marked as pre-164.6 history. A join across comment lines finds `nothing in this repo retries a 40001` 1 time at base and 0 times after. The user-copy literal matches `HEAD` byte for byte. Applied migration 20260826150000 was not touched.

## Decisions Made

- The helper returns the second result, not a synthesized error. The call sites' existing error branches therefore handle an exhausted retry without any new code (D-04).
- The retry `console.warn` includes `first.error?.message`. This is the same operator text the existing failure warn already logs, so it adds no disclosure beyond T-164.6-04's accepted scope.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Queued `mockResolvedValueOnce` results leaked across test cases**
- **Found during:** Task 3 (first csv-finalize neuter)
- **Issue:** Both `beforeEach` blocks used `vi.clearAllMocks()` and then `mockResolvedValue(...)`. That clear keeps queued once-results. Under the neuter, the curated-copy case consumed one of its two queued 40001s, and the leftover poisoned the next case. The first neuter run therefore failed 4 cases, both CONTROLs among them, and the holdings run failed the unrelated audit case. That hid which case the neuter actually broke.
- **Fix:** `adminRpcMock.mockReset()` and `mockRpc.mockReset()` are now called before the default `mockResolvedValue` in the respective `beforeEach`, with a dated comment. Both neuters were re-run: only the targeted retry cases fail, and every CONTROL stays green.
- **Files modified:** `src/app/api/strategies/csv-finalize/route.test.ts`, `src/app/api/allocator/holdings/sync/route.test.ts`. The holdings test file is not in Task 3's `<files>`, but it is in the plan's `files_modified`.
- **Verification:** the neuter table above. Every route file was restored `cmp`-clean before the test edit, and the test files were backed up again after the edit.
- **Committed in:** `c1ce981b8`
