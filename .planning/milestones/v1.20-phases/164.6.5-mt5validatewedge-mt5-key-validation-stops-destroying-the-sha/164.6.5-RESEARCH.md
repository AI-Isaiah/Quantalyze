# Phase 164.6.5: MT5VALIDATEWEDGE - Research

**Researched:** 2026-09-22
**Domain:** Third-party Docker image supervision (s6-overlay), IPC liveness probing (rpyc), incident-driven error-copy correction, telemetry correlation IDs
**Confidence:** MEDIUM — the codebase evidence is HIGH confidence (read directly, this session); the D-05 supervision options rest partly on external documentation for a third-party image, tagged accordingly

## Summary

This phase closes a live production incident: an MT5 key validation tore down the
shared terminal's broker session and the terminal did not recover for 1h39m because
nothing supervises `terminal64.exe`. CONTEXT.md's fifteen decisions (D-01…D-15) are
locked; this research exists to give the planner the evidence needed to choose the
open one — **D-05, the supervision remedy** — and to ground the other fourteen in
verified code, not restated prose.

The single most important finding this research adds beyond CONTEXT.md: **the RPyC
channel the analytics-service already holds to the gateway is not a narrow API — it
is `rpyc.classic.connect`, an arbitrary-remote-code channel, by the codebase's own
documented threat model** (`deploy/mt5-gateway/railway-gateway.md:9-13`, cited as
Phase-134 finding T-134-03). That channel is already reachable from
`Mt5Client.__init__` on every validate and every heal tick. This means **Option 2
(external supervision) does not need a new restart mechanism to be invented** — the
same channel the session monitor already dials can, in principle, execute a
process-level kill-and-relaunch of the wedged Wine process from outside the
container, without touching the persistent volume. This is a genuine third path
distinct from "wrap the image" (Option 1) and "Railway container restart policy"
(Option 3), and it satisfies D-07 (same container, same volume) more directly than
either — but it is also the most architecturally uncomfortable, because it turns a
documented security liability into a load-bearing recovery mechanism. The planner
must weigh this explicitly, not discover it mid-implementation.

The second major finding: **the upstream image's `start.sh` backgrounds
`terminal64.exe` with a bare `&` and never restarts it — confirmed by reading the
actual upstream script, not inferred from the vendor README** [CITED:
github.com/gmag11/MetaTrader5-Docker]. There is no s6-rc.d service for the terminal
today. The base image (`ghcr.io/linuxserver/baseimage-kasmvnc`) IS s6-overlay v3
based and linuxserver.io's own documentation describes a supported "docker-mods"
pattern for adding s6-rc.d services on top of a base image [CITED:
docs.linuxserver.io/general/container-customization] — so Option 1 (wrap the image,
add a supervised service) is architecturally standard for this image family, but it
requires the wrapper to either replace or race against the vendor's own `start.sh`
(a maintenance surface that moves under a `:2.3` tag pin — see D-03a below).

The third finding, which surfaces a genuine gap the planner must resolve rather than
paper over: **D-15's "assertion that fails loudly if the algo-trading-disable
setting ever flips" cannot be built by reading the setting directly.** The setting
(`[Experts] Account=1` / `Profile=1` in `Config/terminal.ini`) is written to disk
only on a clean terminal exit — `scripts/mt5-diag.sh`'s own comment forbids reading
it live for exactly this reason — and it is not exposed as a `terminal_info()`
field. The only live-observable signal is the *consequence*: `trade_allowed`
flipping to `false` immediately after a validate. That field already exists in the
prober's probe body but is currently informational-only by explicit design
(`scripts/prod-prober/arms/mt5.mjs`'s own header: *"`connected` and `trade_allowed`
are printed and NEVER JUDGED"*). D-15 wants this promoted to judged, in a context
the existing arm deliberately does not judge it in. See Open Questions.

**Primary recommendation:** research supports Option 1 (wrap the image with an
added s6-rc.d longrun service for the terminal) as the most defensible D-05 choice —
it is the only option that adds supervision without repurposing a documented
security liability (Option 2's RPyC-exec path) or leaving the liveness-probe fence
unmet by construction (Option 3 has no HTTP surface to healthcheck against without
first doing Option 1's work anyway). But the planner should read the D-05 costing
table below before deciding — this is Claude's-discretion evidence, not a locked
decision, and CONTEXT.md is explicit that the choice and its reasoning are the
planner's to record.

### Pattern 1: Structured heal outcomes, never string-parsed

**What:** `HealOutcome` (a dataclass in `mt5_session_episodes.py`) carries
`verdict`, `first_kind`, `first_code`, `final_kind`, `final_code` as typed fields.
`_heal_blocking` in `mt5_relogin.py` returns one of these on every branch.
**When to use:** Any new escalation (D-08) that acts on `not_healed:ipc_fault` must
read `outcome.final_kind == KIND_IPC_FAULT` (or the verdict string via
`startswith(_VERDICT_NOT_HEALED_PREFIX)`), never regex/substring the verdict text
composed by `_not_healed()`.
**Example:**
```python
# Source: analytics-service/services/mt5_relogin.py:566-596 (read this session)
def _not_healed(
    reason: str, err: Mt5ClientError, login: int, password: str, server: str
) -> str:
    detail = _redact_credential_values(str(err), login, password, server)
    return f"{_VERDICT_NOT_HEALED_PREFIX}{reason}:{detail}"
```
The escalation trigger for D-08 should branch on the *structured* `HealOutcome`
fields the caller already has (`outcome.final_kind`), not re-derive from the string
— the whole point of `HealOutcome` (per its own docstring, "STRUCTURED OUTCOME
INSTEAD OF STRING PARSING") is to avoid exactly that class of drift.

### Pattern 2: Committed, non-interpolated probe bodies (prod-prober security pattern)

**What:** `scripts/prod-prober/arms/mt5.mjs` executes a COMMITTED Python constant
(`MT5_PROBE_PY`) over `railway ssh`, base64-encoded, with **zero runtime
interpolation** — enforced by a self-test that decodes the argv and diffs it against
the source constant (T-164.1-16).
**When to use:** Any change to the probe body for D-09/D-10/D-11 must preserve this
property — add fields to the committed constant, never build the probe string from
variables at run time.
**Example:**
```javascript
// Source: scripts/prod-prober/arms/mt5.mjs:129-141 (read this session)
export const MT5_PROBE_PY = [
  "import json",
  "from mt5linux import MetaTrader5",
  'mt5 = MetaTrader5(host="127.0.0.1", port=8001)',
  'out = {"initialize": bool(mt5.initialize()), "last_error": mt5.last_error()}',
  "ti = mt5.terminal_info()",
  "if ti is None:",
  '    out["terminal_info"] = None',
  "else:",
  "    d = ti._asdict()",
  '    out["terminal_info"] = {"connected": d.get("connected"), "trade_allowed": d.get("trade_allowed")}',
  'print("PROBE " + json.dumps(out))',
].join("\n");
```

### Pattern 3: One remedy per kind, remedies must differ (self-test enforced)

**What:** `REMEDIES` in `arms/mt5.mjs` is a flat object; the arm's own self-test
(exercised via `src/__tests__/prod-prober-wiring.test.ts`) asserts every kind has a
remedy of at least 40 chars and no two remedies are byte-identical.
**When to use:** D-09's split of the two `-10005` causes must mint a genuinely
distinct `kind` string (not overload the existing `mt5-ipc-timeout` string with a
longer remedy) if the two causes are to be reported distinguishably — see Open
Questions for why the current probe transcript may not be able to tell them apart
mechanically.

### Anti-Patterns to Avoid

- **Reading `Config/terminal.ini` for live state:** `scripts/mt5-diag.sh`'s own
  comment states MT5 only rewrites that file on a clean exit, so it can report a
  stale value while the running terminal disagrees. This is called out three times
  independently in the codebase (`mt5-diag.sh`, `mt5_validation.py:230`,
  `arms/mt5.mjs`'s header) — do not "improve" any check by reading the file instead
  of the live IPC oracle.
- **Judging `trade_allowed` inside the existing informational branch of
  `classifyProbe`:** that branch is explicitly documented as "printed and NEVER
  JUDGED" and the arm's own comment names WHY (a probe that logs in would itself
  re-trip the landmine). A D-15 assertion needs its own context (post-validate), not
  a change to this branch's judgment.
- **Sending a credential to decide whether to send a credential:**
  `assert_session_authorized()`'s docstring is explicit that the detector is
  credential-free by design, precisely so it can be used to DECIDE whether to heal.
  Any new liveness probe for D-06 must follow the same shape.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| IPC liveness detection | A new probe method on `Mt5Client` | `assert_session_authorized()` — already exists, already credential-free, already the shipped detector `mt5_relogin.py` and the boot heal both use | Building a second detector duplicates the exact class of drift `mt5_relogin.py`'s own comments warn about ("a second detector, a second lease acquisition, a second budget and a second verdict vocabulary") |
| Structured heal outcomes | A second `HealOutcome`-shaped record for the escalation | Extend `mt5_session_episodes.py`'s existing `KIND_*` vocabulary with a new kind for "escalated to supervision", read off the existing `HealOutcome` | The recorder, the severity ladder (`_VERDICT_NOT_HEALED_PREFIX`), and the downstream consumers already key off this one vocabulary; a parallel one fragments the audit trail D-08 exists to complete |
| Process supervision inside a Docker image | A custom supervisor loop hand-rolled in a shell script | s6-overlay's own `longrun` service type (the base image already ships s6-overlay v3) | The base image's own init system already solves "restart on exit, log to a supervised pipe, dependency ordering" — a hand-rolled `while true; do ...; done` bash loop re-implements a subset of s6 worse and without its logging/dependency guarantees |
| Wizard error taxonomy | A hand-rolled if/else chain for the new arm | Follow the `KEY_SCOPE_CHECK_UNREADABLE` precedent exactly (a sibling `NextResponse.json({code, error}, {status, headers: NO_STORE_HEADERS})` block, positioned by specificity before the generic tail) | This route already has an established, self-testing convention for "known-specific-cause siblings beside a generic transport code" — reproducing its shape is what keeps `SubmitStep`'s `KNOWN_FINALIZE_CODES` membership check meaningful |

**Key insight:** almost everything this phase needs already exists in the codebase
in a form built for exactly this class of problem (credential-free detectors,
structured heal outcomes, one-remedy-per-kind prober arms, sibling error codes). The
work is connecting existing pieces (D-08's "escalate", D-09/D-12's "split"), not
building new primitives — except for D-05, which is genuinely new construction
because nothing in the repo today supervises anything inside the third-party image.

## Common Pitfalls

### Pitfall 1: Option 3 (Railway healthcheck) has no HTTP surface to check against

**What goes wrong:** A planner reaches for Railway's `healthcheckPath` setting
(already used by `analytics-service/railway.toml:7-8`) as the cheap D-05 remedy for
the gateway too.
**Why it happens:** It is the cheapest-looking option and the pattern already exists
elsewhere in the repo.
**How to avoid:** The gmag11 image exposes only noVNC (`:3000`) and the RPyC bridge
(`:8001`, explicitly forbidden from public exposure per the HARD CONSTRAINT in
`railway-gateway.md:9-13`) — there is no HTTP endpoint to healthcheck, and per D-06
the check must exercise the IPC bridge, not merely "is the container up". Building
an HTTP healthcheck endpoint that itself calls `terminal_info()` requires modifying
the image — i.e., doing Option 1's work anyway. Option 3 alone cannot satisfy D-06.
**Warning signs:** A plan task that sets a Railway healthcheck setting without also
adding *something* inside the container that answers on that path.

### Pitfall 2: `-10005` may be mechanically indistinguishable from a single probe reading

**What goes wrong:** D-09 asks for two remedies for the two causes of `-10005`
(modal dialog vs. the account-switch/self-update wedge). A planner may assume the
committed probe body can be extended to tell them apart in one reading.
**Why it happens:** The probe already returns `last_error` as `[code, message]` —
it looks like there should be more signal available.
**How to avoid:** Both causes are documented as producing the IDENTICAL
`-10005 IPC timeout` from `initialize()`. The probe is read-only by hard constraint
(D-15's own landmine reasoning: a `login()` call is itself an account change).
Distinguishing the two causes mechanically, in a single stateless reading, may not
be possible — the planner should decide whether D-09 is satisfied by (a) broadening
the `mt5-ipc-timeout` remedy text to name BOTH possible causes and stop asserting a
redeploy never helps, or (b) correlating with EXTERNAL state (e.g., "did a validate
run in the last N minutes" from the session monitor's own episode log) to pick a
remedy. See Open Questions — this is not resolved by this research and should not be
silently resolved by the planner either.
**Warning signs:** A plan task that adds a new `kind` string to `classifyProbe`
without a stated mechanism for how the classifier tells the two `-10005` causes
apart from the committed probe's output alone.

### Pitfall 3: The upstream image's `start.sh` is not append-only — a D-05 Option 1 wrapper can silently stop matching it

**What goes wrong:** A Dockerfile that `FROM gmag11/metatrader5_vnc:2.3` and adds an
s6-rc.d service assumes `start.sh`'s launch sequence (mono install check → MT5
install check → `wine terminal64.exe &` → Python/mt5linux setup →
`python3 -m mt5linux ... &`) is stable across the `:2.3` tag being re-pushed.
**Why it happens:** `railway-gateway.md:26-28` already documents that the `:2.3` tag
"can be silently re-pushed" and recommends pinning the digest — but digest-pinning
freezes the base image, and D-03a already establishes the MT5 terminal binary
self-updates independently of the image regardless.
**How to avoid:** Any Option 1 implementation should supervise the PROCESS
(`wine ... terminal64.exe`) rather than re-implementing or forking the whole
`start.sh` sequence, so a future upstream `start.sh` change is less likely to
silently diverge from the wrapper's assumptions. Document the exact upstream commit
or image digest the wrapper was built against.
**Warning signs:** A wrapper Dockerfile that copies and edits `start.sh` in place
rather than adding a service that watches for `terminal64.exe`'s exit independently.

### Pitfall 4: A restart that looks safe on paper still needs D-07's proof re-run

**What goes wrong:** Any D-05 implementation is trusted to preserve the auto-login
because "the volume is untouched", without re-observing the actual 2.0s
`started → authorized` sequence the incident measured.
**Why it happens:** D-07's own text already proves this happened once, so it is
tempting to treat it as a property of the volume alone.
**How to avoid:** The 2.0s recovery was measured for a SPECIFIC restart mechanism
(a process kill-and-relaunch under the same container). A DIFFERENT restart
mechanism (e.g., a full container/service redeploy, or a Wine-level crash the
supervisor catches differently) is not proven to hit the same path — re-verify
empirically once D-05 ships, against a real or deliberately induced wedge (this
maps directly onto D-11's own "calibrate against a real wedge" requirement).
**Warning signs:** A plan that treats D-07 as closed by citing the incident's
historical recovery rather than re-observing it against the NEW mechanism.

## Code Examples

### Existing credential-free detector (the shape any new liveness check should copy)

```python
# Source: analytics-service/services/mt5_client.py:1266-1320 (read this session)
def assert_session_authorized(self) -> None:
    """... a bare initialize() is the one probe that distinguishes
    the faults whose remedies are OPPOSITE.
      * -6 -- no account is authorized. ... healed by re-running initialize()
        in its CREDENTIALED form.
      * -10003/-10004/-10005 -- IPC faults. ... Re-sending a credential
        heals NOTHING there.
    """
    self._assert_live("session_authorized")
    try:
        inited = self._timed(
            "session_authorized",
            lambda: self._mt5.initialize(timeout=self._ipc_timeouts_ms["initialize"]),
        )
    except Mt5ClientError:
        raise
    except Exception as exc:  # noqa: BLE001
        raise Mt5ClientError(0, scrub_freeform_string(str(exc))) from None
    if not inited:
        self._raise_last()
```

## Open Questions

1. **Can the two causes of `-10005` be mechanically distinguished at all, and if not, what does D-09 mean by "split"?**
   - What we know: both causes produce the identical `initialize()` failure code
     `-10005`. The committed probe body is read-only and currently projects only
     `initialize`, `last_error`, `connected`, `trade_allowed`.
   - What's unclear: whether some other read-only MT5 API call (e.g., checking for
     an open dialog window, or a terminal build/uptime field) could disambiguate the
     two causes, or whether disambiguation must come from external correlation
     (recent validate timestamp from the session monitor's own episode log).
   - Recommendation: the planner should decide explicitly between (a) broadening the
     `mt5-ipc-timeout` remedy text to describe both possible causes without falsely
     asserting "a redeploy does NOT fix this" in the one case where it might, or
     (b) building a correlation-based split using the session monitor's existing
     episode records. **This should be a stated planning decision, not something the
     execute phase discovers.**

2. **Is Option 2 (RPyC-exec-based external restart) an acceptable architecture, given it turns a documented security liability into a load-bearing recovery path?**
   - What we know: the channel already grants arbitrary code execution and is
     already dialed from the analytics-service on every validate and heal tick — no
     NEW exposure is created by using it for this purpose.
   - What's unclear: whether the project's threat model (T-134-03) intends for this
     channel's blast radius to ever be treated as "ours to use programmatically" for
     anything beyond the narrow, structurally-limited `Mt5Client` surface (which
     deliberately exposes no trade methods and no `__getattr__` passthrough).
     Option 2 as sketched would need a NEW code path that sends an arbitrary shell
     command over that same connection — a different posture than `Mt5Client`'s
     careful method whitelist.
   - Recommendation: if the planner selects Option 2, it should be implemented
     through as narrow a surface as `Mt5Client` uses today (a single, committed,
     non-interpolated restart command — following Pattern 2's non-interpolation
     discipline — rather than a general "run arbitrary code" helper), and the
     security posture should be called out explicitly for `/gsd-secure-phase`.

3. **D-15's assertion: what does "fails loudly" mean operationally, and where does it live?**
   - What we know: the proxy signal (`trade_allowed` post-validate) already exists
     in the prober's probe output but is deliberately unjudged there.
   - What's unclear: whether the check belongs in the prober arm (extending
     `classifyProbe` with new, TIME-SCOPED logic — "was there a validate in the last
     N minutes AND is `trade_allowed` now false") or in the analytics-service's own
     validate path (checking `trade_allowed` immediately after its own `login()`
     call, before returning to the caller) — the latter is more precisely scoped to
     "immediately after MY account change" and does not need the prober's hourly
     cadence, but adds a fourth MT5 round-trip to every validate.
   - Recommendation: the planner should weigh this cost against the pin's stated
     one-way severity (D-15's own "ticking the box silently disables algo trading
     ... failure would be silent rather than loud") and decide where the check
     lives, explicitly.
