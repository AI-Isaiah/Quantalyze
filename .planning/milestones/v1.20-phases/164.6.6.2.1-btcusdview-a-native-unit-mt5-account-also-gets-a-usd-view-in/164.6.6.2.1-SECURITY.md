## Service-only marker rows (`allocator_equity_derived`, kind `native_unpriced:<api_key_id>`)

Write side: CLOSED.
- RLS is ENABLEd and FORCEd (migration `20260717233529`). The only policies are `allocator_equity_derived_owner_select` (FOR SELECT TO authenticated, `allocator_id = auth.uid()`) and `allocator_equity_derived_service_all` (FOR ALL, `auth.role() = 'service_role'`). No later migration touches policies on the table. An authenticated owner has no INSERT, UPDATE or DELETE policy, so table-level default grants do not matter.
- `supabase/tests/test_allocator_equity_derived_rls.sql` already asserts authenticated write denial.
- The only writer in the new code is `persist_native_unpriced_marker` (service client, upsert on `allocator_id,kind`); the payload is `{native_unpriced: true, asof: <poll date>}`.

Read side: CLOSED, no reader trusts owner-writable data.
- Readers of the marker: `read_native_unpriced_days` (Python, used by the daily refresh, `routers/match.py`, equity reconstruction) and `fetchNativeUnpricedDays` / the per-key inline read in `fetchLatestHoldingsPerKey` (TS, used by scenario commit, `getLatestExposureSnapshot`, latest holdings). Each requires `native_unpriced === true` and a strict ISO `asof`.
- The audit-log dependency of the first version is fully gone from the new code. A scan of the added non-test lines of the diff for `audit_log` and `log_audit_event` finds only comments explaining why not. `NativeUnpricedNote` is a typed `str` subclass so the handler decides from the type, not the wording.
- Residual note (not a gap): a failed marker read fails OPEN in the request-time readers (rows kept as before, logged, captured), and CLOSED in the daily refresh (raises, because its snapshot is first-writer-wins). That is a documented accuracy-versus-availability choice; the integrity direction in the one persisting reader is the safe one.

## Pre-existing audit_log-trusting readers (predate the phase, not part of this diff)

Informational. The owner can forge `audit_log` rows through `log_audit_event` (SECURITY DEFINER, GRANTed to authenticated, any action), so these readers trust owner-writable evidence. The effect is bounded to the forging owner's own data (their own holdings carry or drop), but they are not service-only:
- `src/lib/latest-holdings-per-key.ts` `fetchLatestHoldingsPerKey`: `pollRes` and `newestPollRes` read `audit_log` for `cleanPollDay` and `partialPollDay` (3 `audit_log` references on `origin/main`, blame 2026-09-30).
- `analytics-service/services/equity_reconstruction.py` (poll-outcome proof query, `supabase.table("audit_log")`, blame 2026-09-29): the "clean empty poll" proof that stops an empty MT5-style account being carried.
Other `audit_log` reads (`flag-monitor` cron, `/api/me/audit-log/export`, GDPR export) are display or export paths, not integrity decisions.
Suggested follow-up, outside this phase: route the "clean poll" and "partial poll" evidence through a service-written row, the way the marker now does.
