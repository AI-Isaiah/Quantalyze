# Phase 164.6.6.2.1 Plan 06: Own-capital MTD in USD Summary

`getOwnCapitalStrategies` now reduces a native-unit (BTC) strategy's series after converting it at the stored daily BTC close, so the Holdings table's unallocated MTD matches the positioned half instead of showing an unlabelled BTC figure.

`PLAN_BASE=7ed456ff67e989bac10f393db015cd380ddea6c3`

## What changed

- `src/lib/queries.ts :: getOwnCapitalStrategies`
  - `parseReturnsUnit(data_quality_flags.native_unit)` is read per row BEFORE the flags are stripped (the `_dqf` strip is unchanged, so the raw blob still never leaves the function).
  - `readBtcCloses(supabase)` is called once, and only when some row is native (a USD-only list makes zero reads). A null result logs a `console.error` in the same pattern as `getMyAllocationDashboard`.
  - Native row: `computeMtd(convertNativeReturnsToUsd(resolveDailyReturnSeries(..., true), unit, btcCloses))`, with absent days kept as NaN placeholders as the dashboard does (WR-02). An empty converted series gives `mtd = null`. USD rows keep today's exact call.
- `src/lib/queries.own-capital-strategies.test.ts`: four new cases with a mocked `readBtcCloses` (idiom from `queries.my-allocation.test.ts`).

## RED and GREEN

RED, before the implementation (3 failed, 7 passed):

- BTC row: `expected 0.10000000000000009 to be close to 0.21` (0.10 received, 0.21 expected).
- Null closes: `expected 0.10000000000000009 to be null`.
- Mixed book: `readBtcCloses` called 0 times, expected 1.

GREEN: 10 of 10 in the file. The 0.21 oracle is hand-computed in a comment (1.1 x 66000/60000 - 1 = 0.21 for the first day, a flat second day, so 1.21 x 1.00 - 1), and the BTC MTD would be 0.10.

Neuter proof: byte-copied `queries.ts`, replaced the native branch's converted series with the raw resolved series, and the BTC case, the mixed-book case and the null-closes case all went RED (3 failed). Restored with `cp`, `cmp` confirmed identical.

Note on the plan's `vi.setSystemTime` suggestion: not needed. `computeMtd` takes its month from the series' last date, not the clock, so the fixture dates (2026-07-31, 08-01, 08-02) are deterministic without a fake clock.
