## Critical Issues

### CR-01: The settle loop's last comparison runs over a sub-interval sliver, so a history that is still downloading is accepted as settled

**File:** `analytics-service/services/mt5_read.py:157-170` (and `:263`, where the settled record is written)

**Issue:** Each iteration sleeps `min(_MT5_HISTORY_POLL_S, max(0.0, deadline - _clock()))`
and then compares the new count with the previous one. When an iteration ends just before
the deadline, the next sleep shrinks to the remainder. That can be milliseconds. The final
`count == previous` check then compares two reads taken almost back to back, and any growing
history looks "stable" across such a gap. So the function returns `(deals, True)` at the
moment it should raise `Mt5HistoryUnsettledError`. It hands back a partial ledger as
complete, and `read_mt5_deal_ledger` then calls `note_mt5_history_settled`, so later reads
skip the wait.

This is exactly the outcome D-06/D-15 forbid. In the derive, a partial ledger either gets
the permanent "material equity but <2 usable daily-return days" stamp (the Item 0 UAT defect
coming back) or publishes a plausible but truncated daily series.

The tests never exercise it. The autouse fake clock makes reads cost 0 s, so every iteration
lands exactly on a 2 s boundary and the final interval is always the full 2 s.

**Reproduced** (scratch script calling the real `services.mt5_read._settle_deal_history`):

- Each read costs 0.3 s. The history keeps growing by 100 deals every second, so every
  full-interval comparison sees a change.
- The 13th iteration ends at t=29.9. The loop sleeps 0.1 s and reads at t=30.0-30.3.
- Result: `SETTLED True 3100 at t=30.3`. It should have raised.

**Fix:** Never compare across a shortened interval. Make expiry the decision taken *before*
a sleep that cannot be a full interval:

```python
deadline = _clock() + _MT5_HISTORY_WAIT_S
previous = len(first)
while True:
    if _clock() + _MT5_HISTORY_POLL_S > deadline:
        raise Mt5HistoryUnsettledError(previous, material)
    _sleep(_MT5_HISTORY_POLL_S)
    deals = session.client.history_deals_get(
        0, int(now.timestamp()) + _MT5_DEAL_FETCH_MARGIN_S
    )
    count = len(deals)
    if count == previous and (count > 0 or not material):
        return deals, True
    previous = count
```

Add a failing-first test whose fake `history_deals_get` advances the fake clock by a
non-divisor of the poll interval (e.g. 0.3 s) while the count keeps changing on every full
interval. It must raise, not settle.

## Warnings

### WR-01: "The helper's deadline fires before the outer bound" is not guaranteed, and its pin test is a tautology

**File:** `analytics-service/services/job_worker.py:4997-4998`, `analytics-service/services/equity_reconstruction.py:3085-3086`, `analytics-service/tests/test_mt5_concurrency.py:273`

**Issue:** The fresh outer bound is `_MT5_DERIVE_READ_TIMEOUT_S + _MT5_HISTORY_WAIT_S`
(40 + 30 s). Before this phase, the 40 s covered login, PRE `account_info`, one
`history_deals_get` and POST `account_info`. The settle loop adds 30 s of polling plus one
more `history_deals_get`. That read starts just before the deadline (see CR-01) and can run
up to the 30 s rpyc request timeout. Nothing budgets it.

On a fresh account whose first and last reads are slow, a terminal that is still
downloading can hit the outer `asyncio.TimeoutError`. That arm calls `_mt5_bounded_restart`
and kills the download that D-05 says the wait must never trip.

Comments at both call sites assert the opposite ("this arm is reached, the timeout arm above
is not"). The test meant to prove it ends with
`assert _MT5_DERIVE_READ_TIMEOUT_S + wait_s > wait_s`. That holds for any positive read
timeout, so it can never fail (CLAUDE.md Rule 9).

**Fix:** Budget the trailing read explicitly. Either:

- check the deadline before issuing a read (the CR-01 restructure does this, so no read
  starts after `deadline - poll`), or
- derive the outer bound as `_MT5_DERIVE_READ_TIMEOUT_S + _MT5_HISTORY_WAIT_S +
  _MT5_REQUEST_TIMEOUT_S`.

Then replace the tautology with a test that drives the real `read_mt5_deal_ledger` under a
fake clock with slow reads and asserts `Mt5HistoryUnsettledError` (not `TimeoutError`) at the
derived bound.

### WR-02: Stability is one equal pair of reads 2 s apart, so a fresh login that returns a stale on-disk cache settles on it immediately

**File:** `analytics-service/services/mt5_read.py:144-170`

**Issue:** "Settled" means two consecutive equal non-zero counts. A login counts as "fresh"
after a process restart (the registry is empty), after another key used the terminal, or
after a scrub whose trades delete errored (`trades_kept=delete_errored`, which is now only
logged). In all of these, the account's old `trades` cache may still be on disk:

1. MT5 serves that cache immediately as the first read, with count N.
2. MT5 syncs the delta from the server in the background.
3. If the delta lands later than one poll interval, the second read also returns N, so the
   loop returns `settled=True`.
4. The settled record is written, and the derive publishes a history that is missing its
   most recent deals.

The same holds for a fresh download that arrives in chunks with a pause longer than 2 s.

D-04 left the cadence to discretion, and RESEARCH A1 names it as tunable. But in this
configuration, "settled" cannot tell a stale cache apart from a complete history. That is
the kind of partial publication this wait exists to prevent.

**Fix:** Require K ≥ 2 consecutive unchanged intervals (three equal reads) before settling,
or a longer stability window (e.g. ≥ 6 s). Pin it with a test whose fake history holds
steady for one interval and then grows.

### WR-03: An unscoped `sentry_sdk.set_tag` leaks `mt5_server_unknown` onto every later event in the worker process

**File:** `analytics-service/services/mt5_probe.py:683`

**Issue:** `_capture_server_unknown_once` calls `sentry_sdk.set_tag(tag, value)` on the
current scope before `capture_message`. On the HTTP path, Sentry's per-request isolation
scope contains it. On the worker path (`SITE_VALIDATE_WORKER`, `Mt5Adapter.validate`) there
is no per-request scope, so after one unlisted-server refusal every later Sentry event the
worker sends carries `mt5_server_unknown=unlisted` (or `known_servers_unconfigured`). That
mislabels unrelated failures in the founder's alert triage.

The repo's own precedent scopes tags correctly: `job_worker.py:2894`, `:11320` and
`equity_reconstruction.py:3948` use `with sentry_sdk.new_scope() as scope:`. The copied
`_alert_park_failed` pattern at `mt5_probe.py:555` has the same leak.

**Fix:**

```python
with sentry_sdk.new_scope() as scope:
    scope.set_tag(tag, value)
    sentry_sdk.capture_message(message, level="error")
```

### IN-01: The rotate-secret pre-check reports itself as the wizard site

**File:** `analytics-service/routers/exchange.py:562`

**Issue:** `_validate_mt5_key_probe` always passes `site=SITE_VALIDATE_WIZARD`. A rotate-secret
refusal (`routers/internal.py:740`) is therefore logged and captured as a wizard validate,
which misdirects the founder about where the unlisted server was submitted.

**Fix:** Thread a `site` argument through `_validate_mt5_key` / `_validate_mt5_key_probe`,
or accept the label and document it.

### IN-02: Case-folded matching can admit a server spelling the terminal may not resolve

**File:** `analytics-service/services/mt5_probe.py:634-637`, `:718`

**Issue:** The match uses `strip().casefold()`, but `login()` gets the raw user string.
RESEARCH A3 records the terminal's case handling as unmeasured. If MT5 is case-sensitive, a
listed server typed in different case passes the pre-check and falls back into the 45.6 s
hang and `SIGN_IN_FAILED`, which is the Item 9 symptom.

**Fix:** Pass the canonical listed spelling to `login()` when the match was case-insensitive,
or match exactly until A3 is measured.

### IN-03: The copy says "we have been notified" even when no capture was sent

**File:** `analytics-service/services/closed_sets.py:115-118`; `src/lib/wizardErrors.ts` (`KEY_MT5_SERVER_UNKNOWN.fix[1]`)

**Issue:** `_capture_server_unknown_once` skips the capture inside the 1 h dedupe window, when
the 256-key table is full, or when Sentry raises. The ERROR line is always written, so
"notified" is true in a loose sense only.

**Fix:** Soften the wording ("this has been logged for our team"), or leave it as it is with
the caveat recorded.

### IN-04: A long_fetch comment is now false

**File:** `analytics-service/services/ingestion/long_fetch.py:503` (an immediate caller of `Mt5Adapter.validate`)

**Issue:** The comment says "No adapter states False at HEAD". `_server_unknown()` now states
`permanent=False`, so this branch does run in production. A queued validate with an unlisted
server is retried as transient until `max_attempts`, and each attempt re-logs an ERROR and
re-transitions the verification to `draft`. That behaviour is intended under D-09, but the
comment hides it.

**Fix:** Update the comment to name the MT5 `MT5_SERVER_UNKNOWN` arm as the first adapter
that states `False`.
