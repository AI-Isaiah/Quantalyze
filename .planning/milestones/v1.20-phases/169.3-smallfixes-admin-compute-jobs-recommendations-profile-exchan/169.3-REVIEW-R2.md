## Warnings

### WR-01 [MEDIUM]: Fix A opened `NoBatchState` to unset and unknown mandates, and it says "Your mandate is set"

**File:** `src/app/(dashboard)/recommendations/page.tsx:366-382` (branch), `:437-448` (`NoBatchState` copy), `:333-335` (header)
**Issue:** Before the fix round, `NoBatchState` was reachable only when `mandateSet` was true
(`f8c24a46e`: `!mandateSet ? <NoMandateState/> : … <NoBatchState/>`), so its body text,
"Your mandate is set. The match engine recomputes…", was always true. Fix A made two changes:
- D-73 (WR-01) withholds only when no engine-read preference is saved;
- CR-01 added an `unknown` state that never withholds.

The copy was not updated for either change. Two new paths now reach the `!batch` arm:

1. **D-73 case, `mandateState === "unset"`.** An allocator with only a drawdown tolerance (`DRAWDOWN_ONLY`)
   and no batch yet gets the header "Strategies matched to your mandate, updated daily. **No mandate is
   set yet.**" with a card saying "**Your mandate is set.**" underneath. The page makes two contradictory
   statements about the same fact, which is the class of defect round 1 flagged in WR-03.
2. **CR-01 case, `mandateState === "unknown"`.** The page shows "We couldn't load your mandate" and then
   "Your mandate is set." It asserts a fact it has just said it could not read. The allocator may have
   no mandate at all.

The same widening applies to `NoCandidatesState` ("none of the current strategies matched your
mandate"). That arm is weaker: for a drawdown-only allocator, "relax your filters" is true advice.

No test catches this. `page.mandate-gate.test.tsx` has no EP* or ER* case with an empty batch. MG3 is
the only `NoBatchState` case, and it uses a set mandate. That is why the 213 passing tests stayed green.
**Fix:** Pass `mandateState` into `NoBatchState` and word the sentence for each branch, for example
"Your mandate is set." only when `mandateState === "set"`, and otherwise "The match engine recomputes
recommendations once a day…" with no mandate claim. The alternative is to drop the sentence entirely.
Add RED-first tests:
- `DRAWDOWN_ONLY` prefs, batch-meta RPC `[]`, recs RPC `[]`: assert that `queryByText(/Your mandate is set/)` is null and that "No mandate is set yet" renders.
- The same with the prefs read returning `{ data: null, error }`: assert that `/Your mandate is set/` is null and the unknown notice renders.

### WR-02 [MEDIUM]: Fix C can put the account's balance on a never-synced row and hide the real one ("zero times")

**File:** `src/components/exchanges/AllocatorExchangeManager.tsx` `balanceBearers` (the `rank` tuple),
together with the render site (`showBalance` / `balanceElsewhere`)
**Issue:** The bearer is chosen by (working, unmarked, lowest id) and never looks at whether the row
holds a balance. A newly connected key starts with `is_active = true`, `sync_status = 'idle'` and
`account_balance_usdt = NULL` (`baseline.sql`, `api_keys` defaults). `routers/exchange.py:1351-1357`
stamps its `venue_account_id` at connect, before the first sync writes the balance
(`exchange.py:1533`, `cron.py:1067`). The account-share marker comes later: fix B's report names this
the "stamper-lag window". During that window the new key and the existing key are **both unmarked and
both working**, on the same `(exchange, venue_account_id)`, so `accountIdentityTokens` unions them. The
tie then goes to the lower UUID, which is a coin flip. When the new key wins:
- the new row reads `Balance —` (`formatUsd(null)`);
- the old row, which holds the real, current balance, shows no balance and reads "Balance shown on <new key>".

So the account's balance is shown **zero times**, and the row that has the number points to a row that
does not. Before this phase both rows showed a balance, so the fix round introduced this regression.
Round 2 was asked to confirm that no live account shows its balance zero times, and this case breaks
that. The window lasts until the first sync of the new key (or the marker lands). It recurs on every
same-account re-connect, which is the key-rotation flow D-74's union is designed for. The same happens
whenever the winning working key simply has a NULL balance, for example after an exchange where
`fetch_usdt_balance` returned `None`.

No test covers it. Every D-74 liveness case gives all rows a non-null balance.
**Fix:** Add a "has a balance" leg to the rank, after "working" and before "unmarked":
```ts
const rank = (k: ExchangeConnection): [number, number, number, string] => [
  isWorkingHolder(k) ? 0 : 1,
  k.account_balance_usdt === null || k.account_balance_usdt === undefined ? 1 : 0,
  isMarked(k) ? 1 : 0,
  k.id,
];
```
Extend `before` to the new leg. Add a liveness case: two unmarked working keys on one venue id, the
lower id with `account_balance_usdt: null` and the higher id with `5000`. Assert exactly one
`Balance $5,000`, on the higher-id row, and assert that no `Balance —` renders. This is a
presentational tie-break inside D-74's founder-approved order. It does not reverse D-74, but the
orchestrator should note it next to D-74.
