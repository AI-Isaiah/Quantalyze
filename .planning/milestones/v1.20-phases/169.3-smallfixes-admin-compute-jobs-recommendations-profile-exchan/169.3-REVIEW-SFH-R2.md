## R2-SFH-01 [MEDIUM] `NoBatchState` says "Your mandate is set" in two states the round-1 fixes created, where that is unknown or contradicted

**Location:** `src/app/(dashboard)/recommendations/page.tsx:365-379` (the render branch), `:437-449` (`NoBatchState`)

**What happens.** `NoBatchState` hard-codes the sentence "Your mandate is set. The match engine recomputes recommendations once a day…". Before round 1, it could only render when `deriveMandateIsSet` was true, so the sentence was always true. Round 1 opened two new ways to reach it:

1. **The read failed (fix A, CR-01).** `mandateState === "unknown"` sets `withholdList` to false. With no batch row and no RPC error, the page renders `MandateUnknownNotice`, "We couldn't load your mandate", and directly under it `NoBatchState`, "Your mandate is set". The failure is logged, but the page also states the opposite of what the log records. The notice says the mandate could not be read, and the next card says it is set. For an allocator who in fact has no mandate, the notice and the log still say the read failed, yet the card tells them it is set. This is the same class as SFH-01: an error path that renders a confident state.
2. **Only a non-gating field is saved (fix A, WR-01 / D-73).** An allocator whose only saved preference is, say, `max_drawdown_tolerance` gets `mandateState === "unset"` and `withholdList === false`. Before the next daily run there is no batch. The header then reads "No mandate is set yet." and the card below it reads "Your mandate is set." This case is reachable: MandateForm autosaves each field on its own, so a new allocator whose first saved field is a drawdown tolerance lands here until the 01:00 UTC run.

No test covers either combination. The `NoBatchState` assertion at `page.mandate-gate.test.tsx:258` runs with a mandate that is set.

**Hidden condition:** the `unknown` and D-73 `unset`-with-an-engine-field arms, which fall through to the no-batch arm.

**User impact:** two contradictory statements on one screen. In the `unknown` case, the card asserts a fact the page has just said it could not load.

**Fix.** Do not assert the mandate in `NoBatchState`, or make the sentence depend on `mandateState`. For example, pass `mandateState`, and render "Your mandate is set." only when it is `"set"`. Otherwise keep only "The match engine recomputes recommendations once a day. Your first batch will appear here after the next run." Add two cases:
- the preferences read errors, there is no batch and there is no RPC error: assert that "Your mandate is set" is absent;
- the row holds a drawdown tolerance only and there is no batch: assert that "Your mandate is set" is absent.

Both cases fail at HEAD.

## R2-SFH-02 [MEDIUM] The D-74 bearer is picked without checking that it has a balance, so an account's only recorded balance can be hidden behind "Balance —"

**Location:** `src/components/exchanges/AllocatorExchangeManager.tsx:237-241` (`rank` in `balanceBearers`), `:1317` (`showBalance`), `:1340` (`formatUsd(key.account_balance_usdt)`), and the "Balance shown on …" line after it

**What happens.** `rank` orders the live keys in a group by three things: working first, then unmarked before marked, then lowest id. It never looks at `account_balance_usdt`. The bearer's row prints `formatUsd(null)`, which is `"—"`. Every other row in the group prints no balance, and instead prints "Balance shown on <bearer>". If the bearer's balance is null and a sibling's is not, the only balance on record is hidden. The page gives no sign of it: one row shows "Balance —", and the row that holds the number points at that row.

**Concrete scenario, reachable today.**
- Holder B of an account is disconnected.
- Key C, marked `duplicate` against B, is still live and working, with a balance of $5,000.
- The allocator reconnects the account as a fresh key A. `create-with-key` stamps `venue_account_id` at creation. `sync_status` defaults to `'idle'`, which counts as working. `account_balance_usdt` is null until A's first sync writes it.
- `accountIdentityTokens` unions A with B by venue, and C with B by marker, so A, B and C form one group.
- A and C are both working. A is unmarked, so A wins.
- Result: A reads "Balance —", and C reads "Balance shown on A".

Before D-74, C kept its own balance, because the share note is null when the holder is departed. The window lasts until A's first sync succeeds. If A's first sync ends in `error` or `sign_in_failed`, C wins again. The window is still open whenever a working, unmarked key has never written a balance. The same happens with any working holder whose balance fetch returned null (`COALESCE(p_account_balance, account_balance_usdt)` keeps the null), while a marked sibling holds one.

**Why it is MEDIUM, not HIGH:** it is a display defect on `/profile`. It is usually transient (it lasts until the next sync), and no stored data is wrong. It is still the "grouping silently drops a balance" failure that D-74 was meant to rule out. The D-74 tests do not catch it, because every one of their fixtures gives every key a balance.

**Fix.** Add a balance-presence term to `rank`, after "working" and before "unmarked": `[isWorkingHolder(k) ? 0 : 1, k.account_balance_usdt == null ? 1 : 0, isMarked(k) ? 1 : 0, k.id]`. With this order, a working key that has a number beats a working key that has none, and a failing key's stale number still never beats a working key (D-74's freshness proxy holds). Add a liveness case:
- working unmarked A with `account_balance_usdt: null`, and working C marked against A (or against a departed holder that A shares a venue with) with `$5,000`;
- assert that `$5,000` renders exactly once, and that no row reads "Balance —" while another row names it.

That case fails at HEAD.
