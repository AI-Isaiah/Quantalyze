### WR-02 / SFH-04: one account's balance rendered twice when either key of a duplicate pair was failing

**Files modified:** `src/components/exchanges/AllocatorExchangeManager.tsx`, `src/components/exchanges/AllocatorExchangeManager.liveness.test.tsx`
**Commit:** `dac3e76df`
**Status:** fixed. This is a logic change, so it needs human verification.

**Applied fix.** `showBalance` no longer combines two different "is this key working" tests. A new pure helper, `balanceBearingKeyIds(activeKeys)`, groups each holder with every active key marked `duplicate` against it (following the pointers transitively; a cycle resolves to its lowest id). It then picks **exactly one** row per group from the group's `isLiveKey` keys, in this order:

1. a working key (`isWorkingHolder`, the D-18 rule the share note uses) before a live-but-failing one,
2. the holder before a marked key,
3. the lowest id.

`showBalance = balanceBearers.has(key.id)`. A key that reads through a working holder never shows a balance, whatever its own state. The row that shows the note is never picked: the note needs both keys working, and then the holder wins. Working stands in for "freshest read", because nothing on the row dates the stored balance (`last_sync_at` is the trades cursor). The code comment says so and does not claim "newest reading". `account-share-note.ts` is unchanged.

**The one-rule choice, and why it is not the review's snippet.** The reviewer's snippet still shows the balance twice when both keys fail (holder `error`, marked key `error`). The group rule picks one row in every combination.

**Decision: this fix does not group by `accountIdentityTokens`.** The brief preferred the D-16(a) identity grouping. That identity also merges `composite_member` pairs and two unmarked keys that share `(exchange, venue_account_id)`. Plan 03 recorded a key decision (`169.3-03-SUMMARY.md`): "A live composite_member key keeps its balance: accountShareNote says nothing for it and the plan forbids new share wording". Grouping by identity would reverse that decision and leave a working row blank with nothing on it to say why. A fixer cannot record that reversal in `169.3-CONTEXT.md`, which is outside this group's files. So the fix is scoped to `duplicate` markers, which is what both findings describe.

**Recorded residual, for the orchestrator:** an account read by a `composite_member` pair, or by two unmarked keys on the same venue account id (the stamper-lag window), still shows its balance on both rows. Hiding one of them needs wording that plan 03 forbids. This needs a decision, not a fixer edit.

**Tests (6 new cases in `AllocatorExchangeManager.liveness.test.tsx`):**
- holder `error` + working marked key: shown once, on the marked key
- holder `sign_in_failed` + working marked key: shown once, on the marked key
- marked key `error`, working holder: shown once, on the holder
- marked key `sign_in_failed`, working holder: shown once, on the holder
- both `error`: shown once, on the holder
- failing holder + two working marked keys: shown once, on the lowest id

A seventh new case pins unchanged behaviour: a lone key in `error` keeps its balance. Every case asserts `getAllByText(/Balance \$5,000/)` has length 1 and names the row that carries the balance.

**Neuter, recorded:** I restored `const showBalance = shareNote === null && isLiveKey(key);`. The result was `Tests 6 failed | 10 passed (16)`, with `expected [ <p …(1)></p>, <p …(1)></p> ] to have a length of 1 but got 2` (and `got 3` for the two-marked-keys case). After restoring the fix: `16 passed`. The same 6 cases were also RED at HEAD before any edit.

**Second neuter (the working-first leg is load-bearing):** I swapped the rank so holder-first beats working-first. The result was `Tests 3 failed | 16 passed (19)`: holder `error` + working marked key, holder `sign_in_failed` + working marked key, and failing holder + two working marked keys. The fix was restored afterwards.

### WR-03 / SFH-03: "0 connected · Active Allocation auto-synced" when every key is revoked

**Files modified:** `src/components/exchanges/AllocatorExchangeManager.tsx`, `src/components/exchanges/AllocatorExchangeManager.liveness.test.tsx`
**Commit:** `70811bcb2`
**Status:** fixed

**Applied fix.**
- `liveKeys = activeKeys.filter(isLiveKey)` now drives `connectedCount` and `anySyncing`.
- When `connectedCount === 0` the header reads just `0 connected`, with no "auto-synced", "first sync in progress" or "no open positions yet" suffix. Nothing reads the account, and `allocator_holdings` outlives its keys, so any suffix would describe a frozen book as live. `0 connected` is the copy plan 03 accepted above a revoked row. It is neutral and makes no claim about syncing.

**Why the empty-state gate was not moved.** The "No exchanges connected yet." line and the dashed upload panel stay keyed to `activeKeys.length`, the rendered list. Plan 03 recorded this as a key decision ("the empty state stays keyed to the rendered list"). The existing tests also pin that a revoked row keeps its place, its pill and its Disconnect control. Keying the panel to live keys would make the revoked row disappear without a trace. The brief's "base the empty-state check on live keys" is met by the header text: with no live key, the header no longer asserts any sync or holdings state.

**Existing assertion changed on purpose:** the lone-revoked-key case (`hasHoldings={false}`) used to expect `"0 connected · no open positions yet"`. It now expects `"0 connected"`, because "no open positions yet" is also a claim about the book that no live key backs.

**Tests (3 new cases, 1 revised):**
- lone revoked key with `hasHoldings={true}` → `0 connected`, and no "auto-synced"
- lone inactive key in `syncing` with `hasHoldings={false}` → `0 connected`
- live key + inactive key in `syncing` with `hasHoldings={false}` → `1 connected · no open positions yet`. This is the only case that proves `anySyncing` ignores keys that are not live.

**Neuter, recorded:** I restored the old subtitle (no `connectedCount === 0` branch) and `anySyncing = activeKeys.some(...)`. The result was `Tests 4 failed | 15 passed (19)`:
- `Received: "0 connected · no open positions yet"`
- `Received: "0 connected · Active Allocation auto-synced"`
- `Received: "0 connected · first sync in progress"`
- `Received: "1 connected · first sync in progress"`

After restoring the fix: `19 passed`.
