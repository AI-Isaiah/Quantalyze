# Phase 169.3: Code Review Report

**Reviewed:** 2026-09-30T14:17:58Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

Scope: `git diff origin/main HEAD -- src analytics-service` (origin/main `f1ca32b56`, branch
`feat/169.3`). Plan 169.3-01 shipped separately in #868 and is out of scope. Founder rule applied:
only CRITICAL, HIGH and MEDIUM are reported. `critical:` counts the one HIGH finding, and `warning:`
counts the three MEDIUM ones.

## Summary

The match-engine change (plan 02, D-05) is sound. `authored_set` reaches both the strict pass and the
relaxation pass. `allocator_id` is a `str` on every caller: `str(req.allocator_id)` at
`routers/match.py:1689`, a DB row in the cron and the job worker. `manager_id` is the `strategies.user_id`
string, so the `==` comparison cannot fail silently because the types differ. `exclusion_provenance`
has no CHECK constraint, and the admin queue renders the string as it is. The four Python tests fail
if `authored_set` is removed from either pass. No finding.

Two casts were checked and are safe today. `(preferences ?? null) as AllocatorOwnPreferences | null`
works because `deriveMandateIsSet` reads exactly the two projected columns. `as unknown as Array<...>`
covers the postgrest-js negative-index parse. The first cast would only hide a field if D-03's
widening ever happened, which is below the reporting floor.

The defects are in how this phase's pieces fit together. Plan 02 now **withholds** the whole list
when `mandateSet` is false. That gives two older weak points a much bigger effect: the preferences read
ignores its error (CR-01), and the mandate predicate is narrow (WR-01). On /profile, plan 03's balance
rule uses `isLiveKey` and the share note uses `isWorkingHolder`, and the two disagree on
`sign_in_failed` and `error` keys. Because of that, one account's balance can still render twice
(WR-02). The new live-only count also produces "0 connected · Active Allocation auto-synced" (WR-03).

## Critical Issues

### CR-01 [HIGH]: A failed preferences read shows "No mandate is set yet" and hides every recommendation

**File:** `src/app/(dashboard)/recommendations/page.tsx:77-89`
**Issue:** `const { data: preferences } = await supabase.from("allocator_preferences")...maybeSingle()`
never reads `error`. When the read fails (transient PostgREST or network error, RLS or JWT trouble,
statement timeout), `preferences` is `null`, `deriveMandateIsSet(null)` returns `false`, and the page:
- states as fact, in the header, "No mandate is set yet." to an allocator who has one;
- since plan 02, **withholds** the whole scored list and shows `NoMandateState` ("Set your mandate…")
  in its place.

The error is not logged either, so nothing records that the page lied. Before this phase the same error
added a wrong CTA next to a list that still rendered. Now it removes the list. The same function already
handles errors correctly about 20 lines earlier: the attestation read checks `error`, logs it with the
`[recommendations]` prefix, and fails closed. Plan 04's SUMMARY records this read as an open item and
turns down `getOwnPreferences` because it throws. That reasoning argues for handling the error here, not
for ignoring it.

Failure scenario: an allocator with `max_weight = 0.2` loads /recommendations during a brief Supabase
blip. The page says they have no mandate and tells them to set one. They open /preferences, see their
mandate saved, and have no explanation.
**Fix:**
```tsx
const { data: preferences, error: preferencesError } = await supabase
  .from("allocator_preferences")
  .select("max_weight, preferred_strategy_types")
  .eq("user_id", user.id)
  .maybeSingle();
if (preferencesError) {
  console.error("[recommendations] allocator_preferences read failed:", preferencesError.message);
}
const mandateSet = preferencesError
  ? null // unknown: neither "set" nor "not set"
  : deriveMandateIsSet((preferences ?? null) as AllocatorOwnPreferences | null);
```
When `mandateSet === null`, render a neutral degraded state and header ("We couldn't load your mandate.
Reload to see your recommendations."). Do not render `NoMandateState`, and do not render the
"No mandate is set yet" description. A "no row" result and a "read failed" result must not produce the
same answer. Add a test in `page.mandate-gate.test.tsx` where the preferences mock returns
`{ data: null, error: {...} }`, and assert that neither "Set your mandate" nor "No mandate is set yet"
renders.

## Warnings

### WR-01 [MEDIUM]: An allocator whose engine-consumed mandate lies outside the two gated fields now sees no recommendations

**File:** `src/app/(dashboard)/recommendations/page.tsx:86-88` (predicate) with `:284-299` (withhold branch)
**Issue:** `deriveMandateIsSet` returns `true` only for `max_weight` or a non-empty
`preferred_strategy_types`. `MandateForm` autosaves each field separately (`save("excluded_exchanges")`
at `MandateForm.tsx:132`, `save("max_drawdown_tolerance")` at `:178`, and so on). The self-edit
allowlist (`closed-sets.ts:663-674`) also includes `excluded_exchanges`, `max_drawdown_tolerance`,
`correlation_ceiling`, `liquidity_preference`, `style_exclusions` and `target_ticket_size_usd`, and the
engine reads all of them. An allocator who set only a drawdown tolerance and excluded one exchange has
a real mandate, and their batch was scored with it. The page now tells them "No mandate is set yet",
withholds the list, and asks them to set one.

The 169.3-02 SUMMARY ("Withhold, and its interim cost", line 168) says plan 04's switch to
`deriveMandateIsSet` "closes the gap" for "an allocator who filled in engine-consumed preferences but
left the free-text archetype empty". It only partly closes it: the gap is still open for every
engine-consumed field other than those two. D-03 decided not to widen the predicate and gave this
reason: "widening changes /allocations behaviour, which no SC asks for". That decision came before plan
02 turned the same predicate into the gate for the whole list. So the list-hiding consequence is a new
fact that D-03 did not weigh. The copy lie is also new, because on /allocations the same predicate only
decides a CTA.
**Fix:** A founder or orchestrator decision is needed, and this review does not choose. Either
(a) record in CONTEXT, next to D-03, that allocators whose mandate lives only in the other
engine-consumed fields lose /recommendations until they set `max_weight` or a strategy type, and correct
the 02-SUMMARY sentence that says the gap closes; or (b) gate the **withhold** (not
`deriveMandateIsSet` / /allocations) on "any `SELF_EDITABLE_PREFERENCE_FIELDS` value other than
`mandate_archetype` is non-null or non-empty". That keeps D-03 intact for /allocations and stops hiding
a list the engine scored against a saved mandate.

### WR-02 [MEDIUM]: One exchange account's balance still renders twice when either key of a duplicate pair is failing

**File:** `src/components/exchanges/AllocatorExchangeManager.tsx:1244`
**Issue:** `showBalance = shareNote === null && isLiveKey(key)`. The two predicates it combines disagree:
- `isLiveKey` (`departed-history.ts:86-92`) excludes only `revoked`, inactive and disconnected keys.
- `accountShareNote` returns `null` unless **both** the marked key and its holder pass `isWorkingHolder`
  (`account-share-note.ts:73-80, 100, 102`), which also excludes `sign_in_failed` and `error`.

Scenario A: key B is marked `duplicate` of working holder A, and B's last sync is `error`. B's note is
`null` because B is not working (`:100`). `isLiveKey(B)` is true, so B shows its balance. A is unmarked
and live, so A shows its balance as well. The same account's balance appears twice, and B's is a stale
read from a failing key that D-18 says "counts for nothing".
Scenario B: holder A is `sign_in_failed` and marked B is working. B's note is `null` (`:102`), so B
shows its balance. `isLiveKey(A)` is true, so A shows its stale balance too. Again, twice.

Plan 03's stated property is "the balance is the ACCOUNT's, so it renders once". Both scenarios break
it. The liveness tests do not catch this. They only cover a *revoked* holder, where `isLiveKey` and
`isWorkingHolder` happen to agree. `sign_in_failed` and `error` are ordinary states (bad credentials,
exchange 5xx), not rare edge cases.
**Fix:** Decide suppression by the account, not by the note text. A key whose marker points at a
working holder never shows a balance, whatever its own state:
```tsx
const holder = key.account_shared_with_api_key_id
  ? keysById.get(key.account_shared_with_api_key_id)
  : undefined;
const readsThroughWorkingHolder =
  key.account_share_kind === "duplicate" && holder !== undefined && isWorkingHolder(holder);
const heldForAWorkingDuplicate = activeKeys.some(
  (k) => k.account_shared_with_api_key_id === key.id &&
         k.account_share_kind === "duplicate" && isWorkingHolder(k) && !isWorkingHolder(key),
);
const showBalance = isLiveKey(key) && !readsThroughWorkingHolder && !heldForAWorkingDuplicate;
```
The better option is to group by `accountIdentityTokens`, the one-account identity that 167.1.2 D-16(a)
already uses for Open Positions, and show the balance only on the working key that holds the newest
reading of that account. Add liveness cases for a marked key in `error` and a holder in
`sign_in_failed`.

### WR-03 [MEDIUM]: The subtitle reads "0 connected · Active Allocation auto-synced" when every key is revoked

**File:** `src/components/exchanges/AllocatorExchangeManager.tsx:1181, 1192-1199, 1210-1212`
**Issue:** The empty-state gate still uses `activeKeys.length`, but the count is now
`activeKeys.filter(isLiveKey).length`. When every non-disconnected key is revoked or inactive, the card
takes the `connectedSubtitle` branch with `connectedCount === 0`. `hasHoldings` comes from an
unscoped `allocator_holdings` head count (`profile/page.tsx:74-89`, whose own comment says holdings
outlive their keys). Revoking a key does not purge its holdings, so `hasHoldings === true` is the
normal case here. The card then states "0 connected · Active Allocation auto-synced". Nothing is
connected and nothing is syncing, so that is two contradictory claims on one line. Before this phase it
read "1 connected · Active Allocation auto-synced", which was wrong differently. The new count removed
the false number and exposed the false suffix. The 03-SUMMARY accepts "0 connected" above the revoked
row, but not this suffix.
**Fix:** Make the suffix conditional on at least one live key:
```tsx
const connectedSubtitle =
  connectedCount === 0
    ? "0 connected"
    : hasHoldings === true
      ? `${connectedCount} connected · Active Allocation auto-synced`
      : ...
```
Also add a liveness case with one revoked key and `hasHoldings: true`, asserting that "auto-synced"
does not render. `anySyncing` has the same gap: it should use live keys only, so that
"0 connected · first sync in progress" cannot render either.
