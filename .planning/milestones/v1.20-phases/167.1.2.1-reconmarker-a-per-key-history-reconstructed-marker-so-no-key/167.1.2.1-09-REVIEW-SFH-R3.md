## Findings

### F1 - MEDIUM (confidence 6/10): a persistent transient-class SQLSTATE is never counted, never capped, and has no alert

Location: `supabase/migrations/20261018120000_refresh_fanout_owed_key_reconstruct.sql`, per-book handler `IF v_boot_key IS NOT NULL AND v_boot_in_enqueue AND SQLSTATE NOT LIKE '40%' AND SQLSTATE NOT LIKE '53%' AND SQLSTATE <> '55P03'` (diff hunk at about `@@ -350,11 +392,19`).

Scenario: a key whose own enqueue fails every day with a class 40, class 53 or 55P03 error is excluded from the attempt count by design. Examples are a trigger or `enqueue_compute_job` path that raises `40001` deterministically, a table kept locked by a stuck session or prepared transaction (55P03 under `lock_timeout`), or a persistently full disk or connection pool (53xxx). The key then stays owed with attempts below 5. It is retried and fails again every day forever, and it never reaches the cap. The capped-key count and the worker-side `capped` Sentry event, which are the only loud signals for a key that cannot be rebuilt, are never reached. The D-09 guarantee ("never given up silently") is replaced by "never given up and never reported".

Residual trace: one `bootstrap_book_skipped` row in `public.cron_runs` and a `RAISE WARNING` per day. Grep finds no consumer (no worker, CI or Sentry check) that alerts on repeated `bootstrap_book_skipped` rows for the same key. The user sees the equity history stuck in the not-yet-built state with no "could not be rebuilt" note, because the note requires attempts >= 5.

Hidden errors: deterministic `40001`/`40P01` from a custom trigger, a persistent advisory or row lock holder, and persistent resource exhaustion on one key's data.

Recommendation: keep the exclusion (it fixes R2-1) but bound it with a second counter, or a distinct `cron_runs.error` (`bootstrap_book_skipped_transient`) that carries the key id. Add a check that raises when the same key appears N days running (for example 3). The alternative is to count a transient class error after K consecutive days. Today a persistent transient failure is invisible in every user-facing and Sentry surface.

Note: the migration's own residual list records a related case (iii), a non-transient error with a transient-looking SQLSTATE that is counted. It does not record this inverse case, where a persistently transient-class error is never counted and never alerted.
