Each twin's `occurrences` is MEASURED against the migration by the builder (not typed) and every one is 1. Interference walk and matched pairs are in the gate's header. Design notes that differ from a naive reading of the plan:

- **O3 needs a sibling.** With only the in-flight key in the book, removing `'pending'` from `rkj` alone is inert (`bqj` still excludes the book). The second call therefore adds a new owed sibling to the same book, so `bq` takes the book and the mutated `rkj` re-selects the pending key; the enqueue helper returns the existing row and only the attempt count moves. The sibling is also the positive control (1 job, 1 attempt).
- **O6t clears the in-transaction rows it reads.** It deletes capped-key rows with `completed_at = now()` (this transaction's own time) before O6's call, so a foreign capped key on a shared database cannot satisfy it; it then asserts exactly one row, a count of at least 1, and no `api_key_id`/`owner_id` key and no key or owner uuid anywhere in the metadata.
- **O10's strategy-linked half** has no mutation of its own in this gate (one arm, one mutation); it is covered by plan 07's repointed M-arms and was neutered by hand here, see below.
