## Forgery review of the D-12 evidence (coordinator request)

1. **Who can write `audit_log`, and with what.** Direct INSERT: the table-level GRANT gives `anon` and `authenticated` INSERT, but RLS policy `audit_log_service_insert` (`WITH CHECK auth.role() = 'service_role'`) is the only INSERT policy, so a direct INSERT is refused. MEASURED on the local stack as `authenticated`: `new row violates row-level security policy for table "audit_log"`. **RPC path: `public.log_audit_event(p_action, p_entity_type, p_entity_id, p_metadata)` is SECURITY DEFINER, `GRANT EXECUTE ... TO authenticated`, and accepts ANY action, entity_type and entity_id** (`user_id := auth.uid()`; no allow-list, no ownership check, no trigger on audit_log INSERT). MEASURED on the local stack: an `authenticated` session called it with `allocator.equity.reconstruct_complete` / `api_key` / an arbitrary uuid and got a row id back. `log_audit_event_service` is service_role only. So forgery IS possible, and the entity_id can name another user's key (the uuid must be known).
2. **Constrained at the source.** Two layers.
   - Cross-tenant: M1's `newest_outcome` JOINs `api_keys` and requires `a.user_id = ak.user_id` (the worker writes `user_id` = the key's owner; a forger's row carries their own `auth.uid()`). Arm B8, RED-first.
   - Own key, **closed by the founder's D-18 decision ("Deny worker-only actions")**: see the next section.
3. Item 3 (pin a service-role-only precondition) does not apply, since forgery through the RPC was possible; D-18 closes the RPC instead.
