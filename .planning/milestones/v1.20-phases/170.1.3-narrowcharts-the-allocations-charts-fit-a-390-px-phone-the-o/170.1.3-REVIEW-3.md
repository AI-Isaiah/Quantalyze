## Summary

Fix round 2 replaced Recharts' DOM-measured tick pick on the three rolling charts with an
arithmetic list (`fitXTickValues`, passed as `ticks` with `interval={0}` by `RollingXAxis`).
The arithmetic is right: the spacing bound holds for every series length, not only the 60 to 400
day sweep. The fixture no longer depends on fonts, and the forced-font control shows that the check
can fail. Both round-2 findings are closed.

The fix adds one crash. `RollingXAxis` reads `dates[0]` without checking it, and a real producer
sends an empty series. It also changes the desktop tick set of every rolling chart in the product.
That contradicts D-04 and SC-3 as written, and no decision is recorded for it.

### The five questions

1. **Is `fitXTickValues` correct at the edges?** Yes. Let `W = plotRight - plotLeft` and
   `m = max(1, floor(W / pitch))`.
   - **`n <= m`:** the list is returned whole, and the spacing `W/(n-1) >= W/(m-1) > W/m >= pitch`.
   - **Thinned:** `k = ceil(n/m) >= n/m`, so the drawn spacing `k*W/(n-1) > W/m >= pitch`.
   - **`n = 1`:** the one point is centred by the point scale.
   - **`m = 1`:** only the newest label is kept.
   - **The newest label is always kept**, because the walk starts at `n-1`.
   - **The right edge:** the pitch includes `overshoot`, so the clamped newest label clears its
     neighbour by the 8 px gap exactly.
   - **The left edge:** the first label is never cut, but only because `plotLeft` is 65 (YAxis
     width 60 plus margin 5), which is more than half a label (18). The function does not model a
     left clamp, so its doc comment's general claim is wider than its arithmetic. That is LOW and
     not raised.

   The one edge that is wrong is the oldest label. It is never anchored (MD-01).
2. **Does the sweep assert what the browser draws?** It asserts a model of it. `drawnBoxes`
   rebuilds the point scale and `EdgeFitXTick`'s clamp inside the test, and it uses the same
   `estLabelWidth` that chose the ticks. So it proves the arithmetic is self-consistent, not
   that Recharts places ticks there.
   - I closed that gap separately. A probe rendered a real sized `LineChart` with `RollingXAxis`
     in jsdom, outside the repo and deleted afterwards. It drew 5, 13 and 13 ticks for 5, 61 and
     400 points at 858 px, which matches the model.
   - The real-glyph check is still the 1280 fixture plus the V390/V640 overlap gate.
   - The 8 px gap covers the largest proportional fallback measured (DM Sans "MM-DD", up to
     37.47 px).

   Not a finding.
3. **Is the undefined path safe on first render?** The undefined branch is safe: it passes every
   date, and the probe shows the final DOM is thinned once layout resolves. The **defined** branch
   is not safe. When the plot area is known and `dates` is empty, it throws (HI-01).
   - The unit tests cannot see this. All three chart tests mock `useChartWidth` and `usePlotArea`
     to `undefined`, so the defined branch never runs in a unit test.
4. **Is anything else in the desktop comparison still Recharts-measured and font-dependent?**
   Nothing that matters.
   - The other Recharts chart in the comparison is `ReturnHistogram` (composer #16). It uses
     `interval={3}`, a fixed stride with no measurement.
   - The YAxes keep Recharts' default `preserveEnd`, which measures label HEIGHT. With 5 or 6
     ticks over about 200 px the margin is tens of px, so a font change cannot flip a pick.
   - The forced serif and mono runs both pass, which agrees.
   - Every other svg in the fixture is TimeSeriesChart or a hand-built svg using arithmetic
     positions.
5. **Is `fitXTickValues` a needless duplicate of `thinXTicks`?** Partly. The 5-line keep-every-k
   loop is identical in both (`EquityChart.tsx:79-83`). The stated reasons for not reusing
   `thinXTicks` are true, though: it returns the list unchanged at 400 px and wider, and it uses
   a fixed pitch. A shared core would be tidier, but that is LOW and not raised.

## High

### HI-01: `RollingXAxis` throws on an empty series and takes down the strategy page's Rolling Sharpe view [user-facing]

**File:** `src/components/charts/EdgeFitXTick.tsx:100-110`. The trigger is
`src/components/strategy-v2/HeadlineMetricsPanel.tsx:350-354`.

**Issue:** `estLabelWidth(label(dates[0]), …)` runs as soon as `useChartWidth()` and
`usePlotArea()` are defined. With `dates = []`, `label(undefined)` is `undefined.slice(5)`, a
TypeError.

- **Reproduced.** A sized `LineChart` in jsdom with `<RollingXAxis dates={[]} />` threw
  `TypeError: Cannot read properties of undefined (reading 'slice')`.
- **Before this round** the XAxis rendered an empty axis for the same input.
- **A real producer sends it.**
  - `metrics.py` `_rolling_sharpe` returns `[]` when `len(returns) < window`
    (`analytics-service/services/metrics.py:3225-3226`). A strategy with fewer than 30 return days
    therefore persists `{sharpe_30d: [], sharpe_90d: [], sharpe_365d: []}`. A window whose every
    point `_finalize_rolling` drops as NaN does the same.
  - `HeadlineMetricsPanel` gates only on `Object.keys(rolling_metrics).length > 0`, which is 3, so
    it mounts `RollingMetrics`.
  - `RollingMetrics` returns `null` only when there are no keys. Here `merged` is `[]` and the
    chart renders.
  - The throw then unwinds to `src/app/strategy/[id]/error.tsx`. A new strategy's page goes to
    the error screen when its owner clicks "Rolling Sharpe".
- `RollingSortinoChart` and `RollingVolatilityChart` guard `data.length === 0`, so they are not
  hit today. But `RollingXAxis` is exported for reuse and carries no guard of its own.
- **Why tests missed it:** every unit test mocks both hooks to `undefined`, so the branch that
  throws is never run.

**Fix:** guard in the component, where the bad input lands:
```tsx
const ticks =
  dates.length > 0 && chartWidth !== undefined && plot !== undefined
    ? fitXTickValues(dates, estLabelWidth("MM-DD", CHART_TICK_STYLE.fontSize), plot.x, plot.x + plot.width, chartWidth)
    : dates;
```
Add a unit test that renders a real, sized `LineChart` (unmocked `recharts`) with `RollingXAxis` and
`dates={[]}`, and a second that mounts `RollingMetrics` with
`{ sharpe_30d: [], sharpe_90d: [], sharpe_365d: [] }`. Each must go RED on `66b371d88`.

## Medium

### MD-01: The oldest date is never labelled; on a phone the first third of the rolling chart carries no date [user-facing]

**File:** `src/lib/chart-ticks.ts:157-164` (`fitXTickValues`)

**Issue:** The walk keeps every k-th value counted back from the newest, so the oldest point is
kept only when `(n-1) % k === 0`. Before the phase, `interval="preserveStartEnd"` always labelled
the start. The round-2 review's suggested fix also said "keeping the first and last ticks", and
that part was dropped.

Measured with the shipped function on the 275-point composer series:

| svg width | drawn labels | series start | unlabelled lead-in |
|---|---|---|---|
| 1280 desktop (858) | 01-28 first | 01-18 | 10 days |
| V390 (260) | 04-18, 07-19, 10-19 | 01-18 | the first 33 % of the plot |

For a short V390 series (MEASUREMENT: 07-21, 09-04, 10-19), the reader cannot tell where the
rolling series begins. On these charts that point matters, because it is where the window first
fills.

**Fix:** anchor both ends and space the interior evenly. With `m` as now and `m >= 2`, keep
indices `Math.round(j * (n-1) / (m'-1))` for `j = 0..m'-1`. Choose `m'` so that the worst-case
rounded gap still clears the pitch:
`m' = 1 + floor((n-1) / ceil((n-1) * pitch / W))`.
The newest label remains at index `n-1`, and the oldest at 0 sits at `plotLeft`, clear of the left
edge. Extend the sweep to assert `boxes[0].i === 0` as well as the newest. This also brings the
desktop set closer to the pre-phase shape, which helps HI-02.
