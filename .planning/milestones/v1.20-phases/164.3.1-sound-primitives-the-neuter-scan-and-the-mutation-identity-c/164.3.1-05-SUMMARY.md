# Phase 164.3.1 Plan 05: Primitive B — arm identity by source location Summary

**The mutation runner's arm identity moves from an in-query nonce (a secret the gate's own SQL could read back through `current_query()`) to the raise's SOURCE LOCATION — psql's gate-file prefix, a CONTEXT chain of exactly one `inline_code_block … at RAISE` frame, and a tokenizer-resolved line — closing [R4-C02] with a recorded demonstration, its passing control, and a neuter proving the chain rule load-bearing.**

## Accomplishments

- **The nonce is DELETED, not deprecated.** `makeIdentityNonce`, `stampIdentities`, `stampedIdentity`, `firstFailureArm` and `unstampedIdentities` are gone from the module surface, and the lane no longer rewrites the gate copy at all. [R4-C02] killed the nonce not by defeating its logic but by pointing out that it was a **secret transmitted to the attacker** — the stamped text rides in the query text of the statement the gate is running, and PostgreSQL hands query text to server-side code. Keeping it alongside the replacement would have left that channel live.

- **The three-legged rule, all three legs measured, all three proven load-bearing.** (a) the `psql:` prefix names this lane's gate scratch file at the failing statement's last line; (b) the CONTEXT chain is **exactly one** `PL/pgSQL function inline_code_block line N at RAISE` frame, bounded by verbose's `LOCATION:` sentinel; (c) `stmtStartLine + N − 1` resolves to the arm's raise line through plan 01's tokenizer spans.

- **Leg (b) is the correction RESEARCH forced, and it is not theoretical.** Measured on this checkout: a trigger running `EXECUTE 'DO $d$' || repeat(E'\n', 4) || 'BEGIN RAISE …'` produced `inline_code_block line 5 at RAISE` — **the genuine arm's exact resolved line**, under the gate file's own prefix. Legs (a) and (c) both PASS for that forgery. Only the chain's length refuses it, and neutering the length check flips it to a false `RED (identity ok)` with `biting` rising 1 → 2.

- **SC-3 discharged by demonstration with its control in the same run** (`164.3.1-05-ATTRIBUTION.md`): `CTRL 1 → RED (identity ok)`, `FORGE 1 → SYNTHESISED` (the R4-C02 `current_query()` trigger), `FORGE 2 → SYNTHESISED` (RESEARCH's recipe), `FORGE 3 → SYNTHESISED` (the echo-free variant), `biting: 1`, exit 1. Neither forgery spells `TEST FAILED (` — both use the POSIX class `TEST FA[I]LED`, which rule 3a is blind to by construction, so what refuses them is provably the attribution rather than the spelling rule.

- **All three former nonce read sites covered, defect kinds unchanged.** Synthesis is checked FIRST and over **all** output — a `RAISE NOTICE` carrying the identity without aborting the lane (measured: exit 0, severity NOTICE, no chain) is still caught, which was the nonce design's strongest property.

- **SC-7: the verdicts print what they saw AND what they wanted.** A `SYNTHESISED`/`NO-IDENTITY` detail now names the identity text, why it was not attributable, the offending block verbatim, and the expected `file:line (statement A-B, so psql prefix :B and CONTEXT line N)`.

- **The unobserved-host residual is restated, not absorbed.** An unreadable psql grammar — a changed format, or a localized `FEHLER:`/`KONTEXT:` build — is a named `MEASURE_FAIL`, never "no attributable arm" and never a pass. WINDOWS.md 28 is quoted at the site.

## Decisions Made

See `key-decisions` in the frontmatter. The load-bearing one is the assumption-delta:

> **Primary representation of arm identity: in-query nonce → SOURCE LOCATION. Decision: PROMOTE.**
> The raise's source location becomes the ONLY identity channel; the nonce is deleted, not deprecated. ## Deviations from Plan

### 1. [Rule 3 — Blocking] Scratch demonstration fixtures live INSIDE the checkout, not outside it

- **Found during:** Task 2
- **Issue:** The plan directed the scratch gate fixtures to a directory outside the checkout. `runCorpus` computes `gateRel = relative(REPO_ROOT, gate)` and `materialize` then computes `join(slotDir, "src", gateRel)`. For a path outside the repo that relative path is `../`-laden, so the "copy" escapes the scratch slot and is no longer isolated from the original — the runner would have mutated the fixture in place and the restore leg would have compared against mutated bytes.
- **Fix:** The fixture lived at `scripts/mutation-runner/fixtures/scratch-05/`, created **before** `runCorpus` took its `treeBefore` snapshot. The plan's stated reason for "outside" was the dirty-checkout gate — but that gate diffs before-vs-after rather than requiring a clean tree, so a pre-existing untracked file does not trip it. This is the same shape `--self-test` already uses with `SELFTEST_DIR`. Confirmed: zero `dirty-checkout` defects across five demonstration runs.
- **Files modified:** none in the final tree — the fixture was deleted after recording; its text is quoted in full in `164.3.1-05-ATTRIBUTION.md` §3 so plan 11 can promote it.
- **Verification:** `git status --porcelain` after deletion showed only the intended artifact.
- **Committed in:** `a40fe717` (recorded in the artifact and the commit message)

### 2. [Rule 2 — Missing critical] A fourth demonstration arm (FORGE 3) added, because the planned proof was vacuous

- **Found during:** Task 2
- **Issue:** The plan's chain-length neuter was to be driven against RESEARCH's forgery recipe. Run as specified, **the neuter did not flip it.** RESEARCH's recipe spells the identity inside the `EXECUTE`d DO string; psql prints that string back as a `SQL statement "…"` frame of the CONTEXT chain, so the identity is sighted a second time in a **field** rather than a message — which is unattributable independently of chain length. The recipe is double-guarded, and a proof run against it would have "passed" while proving nothing about leg (b): a vacuity of exactly the kind this phase exists to close.
- **Fix:** Added `FORGE 3`, the same forgery with its echo removed — the trigger stashes the identity in a GUC and the forged DO reads it back with `current_setting()`, so the forged statement text names no identity anywhere and the chain rule stands alone. Its HEAD diagnostic carries a single sighting (no `+N further` suffix), confirming the second control is gone.
- **Files modified:** the scratch fixture (deleted after recording); the finding is written into `run.mjs`'s residual list and `164.3.1-05-ATTRIBUTION.md` §5, and flagged as a carry-forward for plan 11.
- **Verification:** with `FORGE 3`, the neuter flips it to `RED (identity ok)` and `biting` 1 → 2; restore returns it to `SYNTHESISED` and `biting` to 1.
- **Committed in:** `a40fe717`, with the residual comment in `a7169196`

### 3. [Process] Task 1 was measurement-first, not test-first, and the RED was obtained by neuter afterwards

The order actually followed was: measure six real psql shapes on a throwaway cluster → implement → verify the parser against real lane output → write the pins from the **verbatim measured bytes**.

Recorded verbatim in `164.3.1-05-ATTRIBUTION.md` §7.
- **Verification:** leg (a) → the non-gate-file pin RED; leg (b) → the forgery pin RED; leg (c) → the line-mismatch pin RED; restore → 71/71.
- **Committed in:** `f79eadcb`

## Issues Encountered

1. **The demonstration fixture's trigger fired on the wrong statement.** The first run had `FORGE 2` scoring `NO-IDENTITY` with *no* `TEST FAILED` in the output at all. Cause: an `AFTER INSERT` trigger fires on the **first** matching INSERT in the file, which belonged to the arm above; `current_query()` then held the wrong block, the substring returned NULL, and `EXECUTE NULL` aborted the lane before the forgery could aim. Fixed by guarding each forgery on its own row id (`IF NEW.id <> 90N THEN RETURN NULL`). Worth recording for plan 11: **a forgery fixture that aborts early looks exactly like a forgery that was refused**, and only the `SIGHTINGS: none` half of the SC-7 diagnostic distinguished them.

2. **The chain-length neuter initially proved nothing** — see deviation 2. This is the more important of the two: the first neuter run *looked* like a failure of the harness and was in fact a finding about the fixture's guard structure.
