## The Key Measurement — psql source-location attribution (Primitive B)

Run on a private throwaway `initdb` cluster (PostgreSQL 16.13, the same PGBIN pg-lane resolves on this machine). Neither shared TEST nor PROD was touched.

### Case 1 — a gate DO-block raise (the shape of all 104 corpus raises)

Gate file: `DO $$` at file line 3, `RAISE EXCEPTION 'TEST FAILED (X 1): demo arm'` at file line 7, `END $$;` at file line 9. Command: `psql -v ON_ERROR_STOP=1 [-v VERBOSITY=verbose] -f gate1.sql`.

```
# DEFAULT verbosity
psql:…/gate1.sql:9: ERROR:  TEST FAILED (X 1): demo arm
CONTEXT:  PL/pgSQL function inline_code_block line 5 at RAISE

# VERBOSITY=verbose
psql:…/gate1.sql:9: ERROR:  P0001: TEST FAILED (X 1): demo arm
CONTEXT:  PL/pgSQL function inline_code_block line 5 at RAISE
LOCATION:  exec_stmt_raise, pl_exec.c:3911
```

### Case 2 — a raise from a trigger installed by a `sql` step (the R4-C02 forgery path)

Trigger `forge_fn()` raising the identical message; gate file just `INSERT INTO t VALUES (1);` at line 2.

```
psql:…/gate2.sql:2: ERROR:  P0001: TEST FAILED (X 1): demo arm
CONTEXT:  PL/pgSQL function forge_fn() line 3 at RAISE
LOCATION:  exec_stmt_raise, pl_exec.c:3911
```

### Case 3 — the trigger fired from INSIDE a gate DO block (real-corpus DML shape)

```
psql:…/gate3.sql:5: ERROR:  P0001: TEST FAILED (X 1): demo arm
CONTEXT:  PL/pgSQL function forge_fn() line 2 at RAISE
SQL statement "INSERT INTO t VALUES (1)"
PL/pgSQL function inline_code_block line 3 at SQL statement
LOCATION:  exec_stmt_raise, pl_exec.c:3911
```

The innermost frame is still the trigger; `inline_code_block` appears only deeper in the chain, and only `at SQL statement`, never `at RAISE`.

### Case 4 — multi-statement gate file, raise in the second DO block

```
psql:…/gate5.sql:6: ERROR:  P0001: TEST FAILED (Y 2): from second block
CONTEXT:  PL/pgSQL function inline_code_block line 4 at RAISE
```

`psql:<file>:<N>` gives the LAST line of the failing statement (`:6` = the `END $$;`); `CONTEXT` gives the raise's line RELATIVE to the DO body (line 1 = the remainder of the `DO $$` line). **Resolution formula, verified twice:** `raise_file_line = DO_statement_start_line + context_line − 1` (3+5−1=7 ✓; 2+4−1=5 ✓). The runner therefore needs each DO statement's start line — which is exactly what the Primitive A tokenizer emits. **The two primitives share the tokenizer; A is a hard prerequisite of B.**

### ⚠️ Adversarial finding — the innermost frame ALONE is forgeable; the CHAIN is not

A trigger that runs `EXECUTE 'DO $d$ BEGIN … RAISE EXCEPTION ''TEST FAILED (X 1): …''; END $d$'` (with padding newlines to hit any target line number) produces:

```
psql:…/gate.sql:5: ERROR:  P0001: TEST FAILED (X 1): forged with padded line
CONTEXT:  PL/pgSQL function inline_code_block line 4 at RAISE
SQL statement "DO $d$ BEGIN … END $d$"
PL/pgSQL function forge_fn() line 3 at EXECUTE
SQL statement "INSERT INTO t VALUES (1)"
PL/pgSQL function inline_code_block line 3 at SQL statement
LOCATION:  exec_stmt_raise, pl_exec.c:3911
```

The innermost frame reads `inline_code_block line 4 at RAISE` — name AND line are attacker-controlled — under the gate file's own `psql:` prefix. What the attacker CANNOT remove is the rest of the chain. **The attribution rule must therefore be: the error's CONTEXT chain consists of EXACTLY ONE frame, `PL/pgSQL function inline_code_block line N at RAISE`, with N resolving through the tokenizer's statement span to the arm's recorded raise line, under the gate scratch file's `psql:` prefix.** Anything else — extra frames, a named function, `at EXECUTE`, a non-gate file prefix — scores NO-IDENTITY. All 104 corpus raises are single-frame (every `TEST FAILED` raise sits directly in a DO body; the file's only `CREATE FUNCTION` text is inside the NONCE 4c annotation's `sql` step, and that trigger raises nothing), so the passing control holds corpus-wide. This constraint must ALSO be written into GRAMMAR.md as a 164.4 authoring rule: an arm whose raise is nested inside `EXECUTE` or a helper function will be refused as NO-IDENTITY — by design, loudly.

### Two further parse facts the planner needs

1. **`CONTEXT` appears at DEFAULT verbosity.** What `VERBOSITY=verbose` adds is the inline SQLSTATE (`P0001`) and a `LOCATION:` line naming the SERVER'S C source (`exec_stmt_raise, pl_exec.c:3911`) — identical for genuine and forged raises, useless for attribution. Use verbose anyway (locked decision): the `P0001` token lets the parser assert the error IS a `RAISE EXCEPTION`, and `LOCATION:` is a convenient end-of-block sentinel. The load-bearing fields are the `psql:` prefix and the CONTEXT chain.
2. **`RAISE NOTICE` can forge output without aborting the lane.** Under verbose, NOTICE blocks also carry `LOCATION:` lines (measured, Case 4's first block). A trigger could emit `TEST FAILED (X 1)` as a NOTICE — the lane still fails later or even passes. The current nonce detector scans ALL output (`unstampedIdentities`, `run.mjs:534-538`); its replacement must preserve that property: every `TEST FAILED (` occurrence anywhere in lane output must be attributable, or the arm scores the synthesised-identity defect (checked BEFORE the red/no-red verdicts, preserving the order at `run.mjs:964-1012`).
3. **Where verbosity gets set:** the lane's psql wrapper is `scripts/pg-lane/run.sh:140` (`psqlq() { psql -h 127.0.0.1 -p "$PORT" -U postgres -d postgres -v ON_ERROR_STOP=1 "$@"; }`) and the gate exec is `:232` (`psqlq -f "$gate"` — the only non `-q` invocation). Adding `-v VERBOSITY=verbose` there (or only on the gate leg) is a one-line change; the runner reads combined stderr+stdout (`run.mjs:725-727`) and knows the gate scratch path (`gateAbs`) for prefix matching. Lane exit 3 = psql script error under ON_ERROR_STOP (observed on all 30 RED arms).

## Architecture Patterns

### Pattern 1 — the statement tokenizer (Primitive A)

**What:** a character-level scanner over the whole file carrying five states across lines — normal, `'…'` (with `''` escape), `"…"` (identifier quoting), `$tag$…$tag$` (tag-matched, per the existing single-line regex `\$([A-Za-z_]\w*)?\$` at `run.mjs:300`), `/* … */` (⚠️ decide and document nesting: PostgreSQL block comments NEST; the current line-local regex does not handle that — a tokenizer that un-nests is strictly more correct, and either choice must ship with a fixture), and `-- …` (to end-of-line). Emits statements as `{ startLine, endLine, text, executableText }`; `;` terminates only in normal state.
**Consumers:** `executableText` (per-line masking becomes a projection of tokenizer state), `isBranchHead` (now asked of a STATEMENT, closing both unanchored arms: `EXCEPTION WHEN OTHERS THEN v_raised := true; END;` decomposes so the trailing statements are visible; `SET ROLE postgres; IF NOT ok THEN` decomposes into `SET ROLE postgres;` + an open `IF … THEN`), `neuterArm`'s forward scan and `statementEndLine` (both currently track ONLY `'` — `run.mjs:399-427` and `:609-627`, the measured P4/P5 defects), and **Primitive B's line resolution** (DO-statement start lines).
**Calibration inputs that must be in the fixture set:** the seven P1 lines verbatim; P3's compound-head shape; P4's odd-parity comment; P5's cross-line parity shape; R3-C01's six embeddings (already generated as `BRANCH_HEAD_WORDS × 7 embeddings` in `mutation-runner-neuter.test.ts` — extend, don't replace); the three multi-line shapes from R3 residual #1 (a `$q$…$q$` body whose interior line reads exactly `BEGIN`, one reading `DECLARE junk int;`, a multi-line literal ending in `THEN`) — these currently REFUSE loudly and must now CLASSIFY correctly.
**Non-regression gate:** R3-C01's measurement discipline — run the new predicate against the real gate file's 104 identities / 103 backward scans and record agreements/refusals before shipping. Criterion 6 (re-derive ARMS_FLOOR/biting) is this measurement's output.

### Pattern 2 — source-location attribution (Primitive B)

Covered in The Key Measurement. Summary of the verdict rewrite: per arm, the runner records `{ gateScratchPath, armRaiseFileLine }` (from the tokenizer + the needle search it already does); lane runs verbose; the parser walks output blocks; verdicts become — `SYNTHESISED` (any `TEST FAILED (` in output not attributable: wrong file prefix, chain ≠ single `inline_code_block … at RAISE` frame, or line mismatch — including NOTICE-carried text), `NO-RED` (exit 0), `NO-IDENTITY` (error present, no attributable arm), `WRONG-ARM` (attributable but different arm), `RED (identity ok)`. The neuter-missed check (`run.mjs:1016-1025`, currently `stampedIdentity`-based) becomes: a neutered arm's identity appearing ANYWHERE in output is the defect (loud direction — forging it only makes CI fail).
**The R4-C02 demonstration (criterion 3):** re-create the `current_query()` trigger annotation, observe NO-IDENTITY/SYNTHESISED; in the same run a genuine arm scores RED. Add the nested-`EXECUTE DO` forgery from this research as a SECOND corpus entry — it is the strongest known attack on the chosen design and it is what the single-frame rule exists to refuse.

## Common Pitfalls

### Pitfall 1 — asserting only the innermost CONTEXT frame
**What goes wrong:** the nested `EXECUTE 'DO …'` forgery (measured above) spoofs frame name AND line. **Avoid:** single-frame-chain assertion + gate-file `psql:` prefix + tokenizer-resolved line. **Warning sign:** any attribution test suite without the nested-DO forgery as a red fixture.

### Pitfall 2 — tokenizer refuses shapes the corpus legally uses
The R3-C01 measurement discipline exists for this: 104 identities / 103 backward scans / 0 disagreements was the shipping bar last time. Re-run it under the new tokenizer; every refusal must be enumerated and either fixed or recorded with the arm that proves it loud. Criterion 6's "record any movement" is this output.

### Pitfall 3 — the A/B/C fixture for [AUDCOV-01] agreeing by construction
The shipped SP-I01 arms were all single-line — that IS the [AUDCOV-01] finding. Case B (the no-`/*` control) is the calibration control; the fixtures must be multi-line real-shape bytes, and the fix must keep case C green while making A find its site and B still pass (criterion 5's exact wording).

### Pitfall 4 — nonce removal breaking invariants it silently carried
`stampIdentities` load-bears in three places today: `firstFailureArm` (arm identity), `unstampedIdentities` (synthesis detection over ALL output incl. NOTICEs), and the neuter-missed check (`:1016-1025`). The attribution redesign must cover all three reads, not just the first. Also `parse.mjs`'s rules 3a/3b (`refuseSelfSatisfying:129-141`, `refuseRetargetingFailureLiteral:165-173`, `identityRewriteDetail`) stay — they are parse/apply-time refusals independent of the runtime identity, and GRAMMAR.md's standing instruction ("read this before adding a fourth regex") governs edits there.

### Pitfall 5 — verbose output breaking existing parses
Verbose adds `P0001:` after `ERROR:` and `LOCATION:` lines after every ERROR **and NOTICE** (measured). Any existing regex over lane output (`firstFailureArm`'s successor, the self-test scenario expectations, `vac06-mechanism-arms.test.ts`'s re-derived regexes) must be checked against the new shape. The self-test fixtures (`fixtures/selftest/*.sql`, 8 scenarios) will exercise this — run `--self-test` early in the work, not at the end.

### Pitfall 6 — testing the helper, not the wiring
The pg-lane verbose flag, the runner's parse, and the CI job are three layers; a green unit test on the parse proves nothing about `psqlq`'s flag (project memory: "Test the wiring, not just the helper"). The runner's own `--self-test` against real clusters is the wiring proof; extend its scenarios rather than adding vitest-only coverage.

### Pitfall 7 — concurrent-agent noise during execution
`[MUT-I03]` (out of scope to FIX): other agents' edits redden the runner's dirty-checkout gate. Execution plans should serialize runner-invoking tasks (memory: full vitest must not share the box; same applies to 30-lane runner runs at ~1.8s/arm ≈ 2 min each).
