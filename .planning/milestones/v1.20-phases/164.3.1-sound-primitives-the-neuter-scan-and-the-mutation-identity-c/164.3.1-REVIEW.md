## Critical Issues

### CR-01: `END LOOP` is a branch head — the neuter refusal walk terminates on it and the failure-branch invariant anchors on it

**File:** `scripts/mutation-runner/parse.mjs:494` (`LOOP_OPENERS` contains `"END"`), consumed at `parse.mjs:779-783`, `scripts/mutation-runner/run.mjs:594-609` (`neuterArm` backward walk) and `run.mjs:1223-1233` (`failureBranches`)
**Issue:** `LOOP_OPENERS = new Set(["FOR","FOREACH","WHILE","LOOP","END"])` — with `END` in the set, a segment whose first word is `END` and whose next word is `LOOP` is emitted with `head: true` (probe output: `1|H| |"END LOOP"`), while `END IF;` and `END CASE;` are emitted as ordinary terminated statements. Two consumers rely on `head` meaning "the head of the enclosing branch", and both are wrong at a loop close:

1. **`neuterArm` accepts a leaking neuter (silent).** The WR-07 walk (`run.mjs:594-609`) stops at the first `isBranchHead` sibling. For
   ```sql
   IF x THEN
     SET ROLE postgres;
     FOR r IN SELECT 1 LOOP NULL; END LOOP;
     RAISE EXCEPTION 'TEST FAILED (A): boom';
   END IF;
   ```
   the walk hits `END LOOP`, breaks, and returns `found: true` with `SET ROLE postgres;` left executing (reproduced; the same text with `END IF;` in place of the loop is refused: `"unrecognised statement before its RAISE (line 4: END IF;)"`). A bare `LOOP … END LOOP;` leaks identically. This is exactly the measured RESET-ROLE class the file's own header calls "loud HERE only by luck", reached through a keyword-set entry rather than a regex.
2. **`identityRewriteDetail` is blind to guard negation behind a loop (silent).** `failureBranches` walks back to the nearest head, which is now `END LOOP`, so the branch text is `END LOOP;\n RAISE …` and excludes the `IF NOT ok THEN` guard. Reproduced: `identityRewriteDetail(gate, gate.replace("IF NOT ok THEN","IF TRUE THEN"))` returns `null` when a loop sits between the guard and the raise, and returns the MEASURE_FAIL detail without the loop. That is the R3-C02 secondary defect (GRAMMAR § 3b: "the guard is part of the branch") reopened for every such arm.

Neither oracle covers this: the neuter cross-product (`mutation-runner-neuter.test.ts:255-263`) and the tokenizer pin (`sql-statement-tokenizer.test.ts:197-205`) both spell `LOOP` only as its *opener* (`FOR r IN SELECT 1 LOOP`) and never assert that a loop *closer* is not a head. Corpus exposure today: `grep -a -A1 'END LOOP;'` finds no raise directly after a loop close in `supabase/tests`, so the 30-arm baseline and the 103/103 re-measurement could not have observed it — "a measurement over one file's shapes is not a measurement over the class", as `run.mjs:384` says.
**Fix:** Remove `END` from `LOOP_OPENERS` so `END LOOP;` tokenizes exactly like `END IF;` — a terminated non-head statement that the neuter walk refuses loudly and `failureBranches` walks through to the real head. Then pin the closer in both oracles.
```js
// parse.mjs:494
const LOOP_OPENERS = new Set(["FOR", "FOREACH", "WHILE", "LOOP"]);
```
```ts
// sql-statement-tokenizer.test.ts — new arm beside "every keyword … produces a head"
it("a loop CLOSER is not a head — END LOOP; tokenizes like END IF;", () => {
  for (const closer of ["END LOOP;", "END IF;", "END CASE;"]) {
    const s = tokenize(closer);
    expect(s.map((x) => [x.head, x.terminated, x.text])).toEqual([[false, true, closer]]);
  }
});
// mutation-runner-neuter.test.ts — add to UNCLASSIFIABLE-style coverage
it("SET ROLE above a closed loop is refused, not accepted past END LOOP", () => {
  const text = ["  IF NOT raised THEN", "    SET ROLE postgres;",
    "    FOR r IN SELECT 1 LOOP NULL; END LOOP;",
    "    RAISE EXCEPTION 'TEST FAILED (ARM L): x';", "  END IF;"].join("\n");
  const r = neuterArm(text, "ARM L");
  expect(r.found).toBe(false);
  expect(r.reason).toContain("unrecognised statement before its RAISE");
});
```
Also add a guard-negation arm through a loop to the `R2-W04 / GRAMMAR rule 3b` block in `mutation-annotation-parser.test.ts`, and re-run the corpus + `--self-test` to confirm 30/30/0 and 12/12 are unchanged (they should be: no corpus raise follows a loop close).

## Warnings

### WR-01: The tokenizer does not model `E'…'` backslash escapes; the normalizer does — two definitions of "what is code"

**File:** `scripts/mutation-runner/parse.mjs:657-679` vs `scripts/sql-body-normalize.mjs:126-154`
**Issue:** `scanRegion` treats every `'` literal as standard-conforming (`''` is the only escape). `scanSql` in the normalizer honours `\` escapes when the literal is `E'…'`. For `RAISE EXCEPTION E'it\'s TEST FAILED (B)';` the tokenizer closes the literal at `\'`, then the trailing `s TEST FAILED (B)'` opens a new literal that runs to the next apostrophe or EOF. Reproduced: the raise statement is emitted `terminated: false` and its text swallows `SET ROLE postgres;` and `END $$;`; `failureBranches` returns that whole span as the branch, so `identityRewriteDetail` reports an identity-rewrite for an edit to the *unrelated* `SET ROLE` line, and `neuterArm` refuses with "could not find the end of the RAISE statement". Both are the loud direction, but (a) `gateAttributionRecords` line spans for everything after the mis-tokenized literal are wrong, and (b) the phase's own thesis ([VAC04-C1]) is that two readers with different blind spots compose into a silent hole — `stripSqlComments`/`normalizeSql` and `maskNonCode` now disagree on the same bytes. Corpus today: no `E'…\'` in `supabase/tests` (grep `-a`), so this is latent.
**Fix:** Mirror the normalizer's rule in `scanRegion`: when the `'` is immediately preceded by `E`/`e` that is not itself preceded by an identifier character, honour `\x` escapes inside the literal; blank the interior the same way. Add a tokenizer fixture (`RAISE EXCEPTION E'it\'s x'; SELECT 1;` → two statements, both terminated) and a normalizer/tokenizer agreement arm over the corpus (`maskNonCode(text)` non-blank offsets ⊆ `scanSql(text).masked` non-blank offsets, or at least equal statement counts on every `supabase/tests/*.sql`).

### WR-02: `--parse-only` measures each `apply` step against the pristine file; the real run applies steps sequentially — mode identity is not held for layered annotations

**File:** `scripts/mutation-runner/run.mjs:2015-2053` (`parseOnlyCorpus`) vs `run.mjs:1633-1659` (`runCorpus`)
**Issue:** In `runCorpus`, `before = readFileSync(target)` is re-read after each step is written, so step N sees the output of step N−1. In `parseOnlyCorpus`, `before = readFileSync(join(REPO_ROOT, step.file))` is the repo file every time, and `applyFileStep`/`identityRewriteDetail` run against that. A layered annotation (GRAMMAR "Shape 3", the documented pattern for 164.4) whose second step's needle count changes after the first — step 1 inserts text that contains step 2's needle, or step 2 targets text step 1 produced — gets `occurrence-mismatch` in one mode and not the other. The header (`run.mjs:26`) makes mode identity a stated contract, GRAMMAR § 3b says the identity-rewrite check runs "in both the full run and `--parse-only`", and the mutation-annotation-parser test's "REAL CORPUS" arm (`mutation-annotation-parser.test.ts:574-600`) already threads a per-file buffer forward — so the test and the runner's static mode disagree on what "the file before this step" means. Today's 49 steps are pairwise independent (SHAPE 1, SHAPE 5), so no current annotation diverges.
**Fix:** Thread the text forward in `parseOnlyCorpus` exactly as the test does:
```js
const buffers = new Map(); // per annotation
for (const ann of parsed.structured) {
  buffers.clear();
  for (const step of ann.apply) {
    if (step.kind === "sql") continue;
    // … existing bad-file-ref / existsSync checks …
    if (!buffers.has(step.file)) buffers.set(step.file, readFileSync(target, "utf8"));
    const before = buffers.get(step.file);
    const actual = countOccurrences(before, step.kind === "edit" ? step.find : step.anchor);
    if (actual !== step.occurrences) { addDefect(…); continue; }
    const applied = applyFileStep(before, step);
    if (applied.ok) {
      const rewrite = identityRewriteDetail(before, applied.text, step.file);
      if (rewrite !== null) addDefect("identity-rewrite", …);
      buffers.set(step.file, applied.text);
    }
  }
}
```
Add a selftest fixture with a two-step annotation where step 2 only matches after step 1, and assert `--parse-only` and `runCorpus` agree on it.

### WR-03: The MW02 result-loop parser recognises a tolerance only as an `if`/`elif` containing `$result = skipped`; the pin claims "ANY spelling"

**File:** `src/__tests__/lint-sql-gates.test.ts:395-461` (`extractResultLoopConditions`), asserted at `:604-618` and `:620-656`
**Issue:** The walk only reads lines matching `/^(\s*)(?:el)?if\s+(.+?)\s*;\s*then\s*$/` and classifies a tolerance when the normalized condition matches `/\$result\s*=\s*skipped/`. A per-job tolerance spelled as `case "$result" in success|skipped) : ;; *) fail=1 ;; esac`, as a negated guard `if [[ $result != success && $is_fork_pr != true ]]; then fail=1; fi`, or as `[ "$result" = success ] || [ "$is_fork_pr" = true ] || fail=1` is a real, effective skip tolerance the parser cannot see. `parsed.tolerance.get("sql-mutation")` then stays `undefined` and the `tolerance === null` arm passes on a workflow that has grown one — the [MUT-W02] shape, one spelling-set wider than the `[[`/`==` case the fixture pair closes. The test titles ("in ANY spelling") and the D-12 comment over-claim what is measured.
**Fix:** Either replace the spelling parser with an execution oracle — extract the real loop block (already done), run it under `bash` with `needs.<job>.result` substituted to `skipped` for each hermetic job and every guard variable forced to both values, and assert `fail=1` — or keep the parser but (a) also walk `case` labels and any condition mentioning `skipped`/`success` in either polarity, and (b) retitle the arms to state the spellings actually covered. The execution form is the one that cannot be re-spelled around, which is this phase's own lesson (GRAMMAR § 3: "any rule stated over a spelling can be re-spelled around").

### WR-04: Two grep exit-code sites in `prod-body-drift-check.sh` still use the bare idiom the same file fixes at `:689-704` ([VAC04-C3])

**File:** `scripts/prod-body-drift-check.sh:548-555` and `:667`
**Issue:**
- `:549` `SNAPSHOT_BODY_COUNT="$(find "$SNAPSHOT_DIR" … -print | grep -ac '[^[:space:]]')"` under `pipefail`: a `find` that fails mid-walk (permission, I/O) exits **1**, which `[ "$_snap_rc" -le 1 ]` accepts as "counted, no rows". The comment beside it claims ">= 2 = could not read", which is true of `grep` only. A failed `find` yields a low count, the floor goes INERT with a `::warning::` instead of a MEASURE_FAIL, and the "every function is new — pass" shape the floor exists to catch is unguarded on that run. Bounded today by the `-d` check at `:154`, but the discipline is broken on the one line that decides whether the absurdity floor is armed.
- `:667` `if [ ! -s "$live" ] || ! grep -aqE '[^[:space:]]' "$live"; then` — a grep exit ≥ 2 on `$live` is read as "empty body" and routed to the index lookup. When the name is in the index this fails closed (extraction failure); when it is not, the run takes the measured-absent pass for a body it never read. Same shape as [VAC04-C3], one branch earlier.
**Fix:**
```bash

set +e
find "$SNAPSHOT_DIR" -maxdepth 1 -type f -name '*.sql' -print > "$TMP/snapshot-bodies.txt"
_find_rc=$?
set -e
[ "$_find_rc" -eq 0 ] || fail "MEASURE_FAIL: could not enumerate ${SNAPSHOT_DIR} (find exited ${_find_rc}) …"
set +e; SNAPSHOT_BODY_COUNT="$(grep -ac '[^[:space:]]' "$TMP/snapshot-bodies.txt")"; _snap_rc=$?; set -e
[ "$_snap_rc" -le 1 ] || fail "MEASURE_FAIL: could not count … (grep exited ${_snap_rc})"

# :667 — capture the status and branch three ways, as :689 does
set +e; grep -aqE '[^[:space:]]' "$live"; _live_rc=$?; set -e
[ "$_live_rc" -le 1 ] || fail "MEASURE_FAIL: could not read the fetched body for '${fname}' (grep exited ${_live_rc}) …"
if [ ! -s "$live" ] || [ "$_live_rc" -eq 1 ]; then
```
Add a PATH-shim `grep` arm in `drift-check-scripts.test.ts` keyed on `*.live.sql` (the SP-M01 idiom already used for `prod-names.txt`) proving the `:667` site MEASURE_FAILs.
