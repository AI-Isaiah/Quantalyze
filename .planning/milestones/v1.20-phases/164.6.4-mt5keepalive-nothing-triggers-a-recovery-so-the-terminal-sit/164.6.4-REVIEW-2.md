### WR-08: the cadence FLOOR is derived from the heal's budget CEILING alone and omits the bounded lease acquire, so at the floor the new outer deadline pre-empts the heal's own abandoned-thread arm

**File:** `analytics-service/services/mt5_session_monitor.py` — the
`_MT5_SESSION_POLL_INTERVAL_FLOOR_S` derivation comment and symbol
`run_mt5_session_monitor_tick`; `analytics-service/services/mt5_relogin.py` — symbol
`heal_mt5_terminal_session`, its `except asyncio.TimeoutError` arm

**Issue:** `_MT5_SESSION_POLL_INTERVAL_FLOOR_S = _MT5_RELOGIN_BUDGET_CEILING_S` = 300.0. A
heal's worst-case wall time is NOT the budget: it is `_relogin_lease_wait_s()` (ceiling
`MT5_REQUEST_TIMEOUT_S`, default 2.0 s) PLUS `_relogin_budget_s()` (ceiling 300.0). With
`MT5_RELOGIN_BUDGET_S=300` and `MT5_SESSION_POLL_INTERVAL_S=300` — both values inside their
own declared, validated windows — the tick's `timeout=interval` is 300 s while the heal's
worst case is ~302 s. The outer deadline fires FIRST.

That matters because of what it pre-empts. The heal's `except asyncio.TimeoutError` arm is
the one place that says, at ERROR and above every verdict, "a round-trip is still in flight
against the shared terminal on a thread that was NOT cancelled" — and it records
`KIND_BUDGET_ABANDONED`. Under an outer pre-emption neither runs: the cancellation
propagates past that handler (a `CancelledError` is not a `TimeoutError`), and the operator
gets the monitor's generic "did not complete inside its own 300.0s cadence" instead, with no
row and no mention of the abandoned credentialed call. The heal's own docstring calls that
outcome "the one outcome here that leaves the SYSTEM in a state nobody measured"; the fix
round made it reachable without its own sentence. ⚠️ The D-36 fence still protects
correctness — this is an observability defect, not a safety one.

The SAME omission weakens WR-02's rationale: the comment claims "waiting first lets the boot
heal own the boot window uncontested," which holds only while `interval > lease_wait +
budget`. At the floor with the budget at its ceiling it does not, and the boot-time
collision WR-02 removed comes back as a busy skip. The claim is configuration-dependent and
is written as though it were structural.

**Fix:** derive the floor from what a tick can actually cost, and say which quantities it
sums.

```python
# FLOOR = the heal's DECLARED BUDGET CEILING **plus its bounded lease acquire**.
# ⛔ The budget bounds only the `to_thread` body; the acquire happens before it,
# so a floor equal to the budget ceiling alone lets the tick's own `wait_for`
# pre-empt the heal's abandoned-thread ERROR arm and its `budget_abandoned`
# reading — the one outcome that leaves the system in a state nobody measured.
_MT5_SESSION_POLL_INTERVAL_FLOOR_S: Final[float] = (
    _MT5_RELOGIN_BUDGET_CEILING_S + _MT5_RELOGIN_LEASE_WAIT_CEILING_S
)
```

and correct WR-02's comment to state the condition it depends on rather than asserting
"uncontested" flatly.

### WR-09: WR-02 traded the boot collision for a window in which the monitor leaves ZERO evidence it exists — the HIGH-1 defect class, reproduced in the sibling module

**File:** `analytics-service/services/mt5_session_monitor.py` — symbol
`mt5_session_monitor_loop`; `analytics-service/main.py` — the `tasks` list in `lifespan`

**Issue:** the loop now emits nothing at all before its first tick. Its first statement is a
guarded import, then the `while`, then the wait. `main.lifespan` logs only `"Worker starting
as %s"` and names no task. So for one full poll interval after every deploy — 600 s by
default — a running, healthy monitor and a monitor that does not exist are BYTE-IDENTICAL in
the logs. If the process does not survive that interval (two deploys inside ten minutes;
a crash loop under `restartPolicyType ON_FAILURE x3`; any other background task raising and
`_crash_handler` calling `SHUTDOWN.set()`), the monitor ticks ZERO times for the life of the
process and leaves no line saying so.

That is precisely the ambiguity `heal_mt5_terminal_session`'s HIGH-1 fix removed for its
sibling, in this module's own words: "zero log lines was simultaneously consistent with FIVE
hypotheses: MT5 disabled, the `create_task` entry reverted, the import failing, the process
killed before the task was scheduled, or `LOG_LEVEL` raised above INFO." Before `332d6620`
the monitor could not be in that state — it ticked at once, and a tick always logs. The
reorder re-opened it, and the module that carries the fix for it is the module the loop
imports.

The second cost is the one the launch brief asked about, and it is real but smaller:
detection is now delayed one full interval after every deploy, and the boot heal does NOT
reliably cover that window — the heal's own `Mt5TerminalBusyError` arm calls the boot race
"the ordinary one IN-04 describes: `dispatch_loop` claims a `derive_broker_dailies` job
within a second or two of boot," so a busy-skipped boot heal plus a waiting monitor means
nothing measures the session for up to one interval. Against a ≥2h34m measured exposure a
bounded 600 s is an acceptable trade; the UNBOUNDED, unlogged case above is not.

**Fix:** make the wait visible, and it costs one line inside the existing guard.

```python
        from main_worker import SHUTDOWN

        # ⛔ WR-09 — SAY THAT WE ARE WAITING. Without this the loop's first
        # interval is indistinguishable from the task never having been created
        # (the HIGH-1 five-hypotheses shape), and a process that does not outlive
        # one interval leaves no evidence the monitor ran at all.
        logger.info(
            "mt5 session monitor: started — the boot heal owns the boot window; "
            "the first detection tick runs in %.0fs.",
            session_poll_interval_s(),
        )
        while not SHUTDOWN.is_set():
```

⚠️ This adds a statement to the OUTER guard's body, which is allowed (P-outer requires the
function body to be one `Try`; P-inner requires the guard body to hold exactly one `while`,
which it still would — the predicate counts `While` nodes, not statements). ⛔ Do NOT put it
inside the `while` body: every statement there must itself be a `try`.

⭐ Optionally also bound the FIRST wait by the boot heal's own worst case rather than the
full cadence (`min(interval, _relogin_lease_wait_s() + _relogin_budget_s())`), which keeps
the collision closed while cutting the post-deploy blind window from 600 s to ~162 s.

### WR-10: `KIND_DISABLED` escalates a deliberate operator decision to a WARNING on every tick, forever — contradicting the comment two lines above it

**File:** `analytics-service/services/mt5_session_monitor.py` — the kill-switch arm of
`run_mt5_session_monitor_tick`; `analytics-service/services/mt5_session_episodes.py` —
symbol `record_mt5_session_reading`, the `blind` branch

**Issue:** `blind = threshold is not None and consecutive >= threshold`, and once the run
passes the threshold it stays past it — the log level is WARNING on EVERY subsequent tick,
with no second throttle. At the default cadence the threshold is
`ceil(3600/600) = 6`, so a service with `MT5_ENABLED` deliberately unset emits a WARNING
every ten minutes, forever, after the first hour.

The code two lines above the new call says the opposite of what the new call does: "a
disabled switch is an operator DECISION rather than a misconfiguration," which is exactly
why `_log_configuration_fault_once` throttled it in the first place. And round 1's own WR-02
supplies the standard this violates: "an alarm that fires on the normal path stops being an
alarm, which is this milestone's own defect class." A deliberately-disabled MT5 is a normal
path.

WR-03's substance survives — the refusal must be COUNTED, and it now is. The defect is the
LEVEL, not the count.

**Fix:** keep the counter, and decide the level from whether the blindness is a decision or
a fault.

```python
#: ⛔ WR-10 — kinds whose blindness is an operator DECISION. They still extend the
#: run (so a later genuine fault's escalation is not reset by them) but they never
#: raise the LEVEL: an alarm that fires on a deliberately-disabled service is an
#: alarm operators learn to ignore.
_DECIDED_BLIND_KINDS: Final[frozenset[str]] = frozenset({KIND_DISABLED})
...
            blind = (
                threshold is not None
                and consecutive >= threshold
                and reading.kind not in _DECIDED_BLIND_KINDS
            )
```

⚠️ ⛔ Do NOT extend this to `KIND_NOT_CONFIGURED`. A Railway variable that was never set is
a MISCONFIGURATION and is precisely the case WR-03 was raised for.

### WR-12: WR-01's compare-and-set verdict is read off a response SHAPE that nothing pins — and this repo already flips write paths to `returning='minimal'` for performance

**File:** `analytics-service/services/mt5_session_episodes.py` — symbol `_close_row`, its
`return bool(rows(response))`

**Issue:** round 1's fix note said "confirm against the pinned client version rather than
this sentence." I confirmed it: `postgrest==2.31.0`'s `SyncRequestBuilder.update` defaults
`returning=ReturnMethod.representation`, so a winning UPDATE returns its rows today and
`bool(rows(response))` is correct. The problem is what happens when that stops being true.

`rows(response)` is EMPTY in two indistinguishable situations: the CAS lost, and the
response simply does not echo rows. The failure is silent and total in the second case —
every measured close would report `False`, every row would carry
`started_at_is_lower_bound: true`, a WARNING claiming a lost race would fire on every
ordinary transition, and the bounded-vs-unbounded distinction that `_open_row`'s docstring
calls "the difference between a bounded and an unbounded error on every duration a successor
computes from these rows" would be gone from the whole dataset. **The suite would stay
green**: `tests/test_mt5_session_monitor._FakeQuery.execute` models representation by
construction (`return _FakeResponse([dict(r) for r in matched])`), so no gate is watching
this property.

This is not hypothetical in this repo. `services/equity_reconstruction.py` deliberately
passes `returning="minimal"` on its write paths and carries a test asserting it, with the
stated rationale of not shipping row representations back over the wire. A performance pass
over `cron_runs` writes taking the same decision would invert WR-01's inference without a
single red test.

**Fix:** read the count, which survives `returning='minimal'`, and fail closed on an
unreadable response.

```python
    def _update() -> Any:
        return (
            supabase.table("cron_runs")
            # ⛔ WR-12 — `count="exact"` is the CAS's own answer and it survives a
            # future `returning="minimal"`. `rows(response)` would silently read
            # EVERY winning close as a LOST one, with the whole suite green.
            .update(payload, count="exact")
            .eq("id", row.get("id"))
            .eq("status", "running")
            .execute()
        )

    response = await db_execute(_update)
    matched = getattr(response, "count", None)
    if matched is None:
        matched = len(rows(response))
    return bool(matched)
```

⚠️ If the count route is rejected, the minimum is a contract test that pins
`inspect.signature(SyncRequestBuilder.update).parameters["returning"].default` —
so a dependency bump that changes the default reds HERE rather than silently in production.

            for statement in (*handler.body,):

### IN-08: the WR-02 gate asserts on wall-clock against a 0.2 s cadence, which is a flake mechanism under parallel pytest

**File:** `analytics-service/tests/test_mt5_session_monitor.py` — symbol
`test_the_first_ITERATION_waits_BEFORE_ticking_so_the_boot_heal_owns_the_window`

**Issue:** `await asyncio.sleep(cadence_s * 0.25)` then `assert tick_offsets == []`. The
assertion is only safe while that 0.05 s sleep completes in under 0.2 s of wall time. Under
`-n auto` on a loaded box a starved event loop can overshoot, the loop's own 0.2 s wait
elapses, the first tick lands, and the gate REDS on a correct implementation. (The second
assertion, `tick_offsets[0] >= cadence_s * 0.5`, is safe in the other direction — load can
only make it larger.) The run is green here, and this is recorded as a flake shape rather
than a present failure: a gate that reds on healthy code is one somebody eventually
xfails, and this is the only control for the WR-02 property.

**Fix:** drive the clock rather than the wall — patch `monitor.session_poll_interval_s` to
return a large value and assert the tick has not fired after a real short sleep (the
ordering claim does not need a real cadence), or assert against
`asyncio.get_running_loop().time()` deltas with a margin derived from the cadence rather
than a fixed fraction of it.

### IN-09: IN-03's skip was the right call, but the stated blocker is avoidable — the tick can RETURN the interval it used

**File:** `analytics-service/services/mt5_session_monitor.py` — symbols
`run_mt5_session_monitor_tick`, `mt5_session_monitor_loop`

**Issue:** the launch brief invited an opinion. The decision to defer is defensible on
blast-radius grounds and it is recorded rather than silent, which is the part that matters.
But the reason given — that closing it "requires changing `run_mt5_session_monitor_tick`'s
public no-argument call signature" across six monkeypatch sites and a mutant anchor — is
true only of the shape the round-1 fix suggested. A returning shape costs none of that:

```python
async def run_mt5_session_monitor_tick() -> float | None:
    ...  # returns `interval`, or None on the kill-switch / fault paths
```

```python
            try:
                slept_from = await run_mt5_session_monitor_tick()
```

The call stays zero-argument, every existing double keeps working (an `async def` double
returning `None` simply makes the loop fall back to its own read), and
`_LOOP_GUARD_MUTANTS`'s anchor — the literal `"await run_mt5_session_monitor_tick()"` —
remains a substring of the new line, so the mutant still applies. ⚠️ Recorded so the
follow-up phase that picks IN-03 up does not re-derive the blocker from the fix report and
conclude the change is wider than it is. No action owed in this phase.
