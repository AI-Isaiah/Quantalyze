`test_no_credential_host_or_port_reaches_ANY_field_of_ANY_row`

`46190411` added three keys a production row can now carry — `last_confirmed_at`,

* `test_every_honesty_field_is_present_on_a_written_row_by_NAME` — `set(meta) == _OPEN_ROW_METADATA_KEYS`, driven on a FRESH open row;

**MEASURED rather than argued.** Injecting a credential-shaped free-text key through the confirm

### WR-14: WR-10's exemption makes a kill-switch MISCONFIGURATION permanently unescalatable — and three sibling sites still assert the opposite

**File:** `analytics-service/services/mt5_session_episodes.py` — symbols `_DECIDED_BLIND_KINDS`,
`KIND_DISABLED` (its comment block), `record_mt5_session_reading` (the `blind` computation);
`analytics-service/services/mt5_session_monitor.py` — the kill-switch arm of
`run_mt5_session_monitor_tick`; `analytics-service/tests/test_mt5_session_monitor.py` — symbol
`test_the_disabled_kill_switch_reading_is_COUNTED_not_merely_logged`

**Issue — two halves, one root.**

**(a) The exemption is narrow in KIND-space but not in FAULT-space.**
`services/closed_sets.py::mt5_enabled_server` is
`(os.getenv("MT5_ENABLED") or "").strip().lower() == "true"`. So `MT5_ENABLED=1`, `on`, `yes` or
`enabled` — an operator who INTENDED to switch detection on and typed a plausible truthy value —

exempt from `blind_run_escalation_threshold`. The remaining evidence is (i) one
`_log_configuration_fault_once` line for the life of the process and (ii) an INFO line per tick

DECISION from FAULT — at this call site it cannot, because the reader collapses both into the

**(b) Three sibling sites were left asserting the pre-WR-10 property.** Each is now false:

* `mt5_session_episodes.KIND_DISABLED`'s own comment: *"Recording these as `not_measured`

### WR-15: `_confirm_row`'s `status='running'` scope — the ONE thing preventing a confirm from stamping an already-settled episode — is pinned by nothing

**File:** `analytics-service/services/mt5_session_episodes.py` — symbol `_confirm_row`;
`analytics-service/tests/test_mt5_session_episodes.py` — symbol `_OrderedCronRuns.after_select`

**Issue:** the confirm UPDATE carries `.eq("status", "running")`, and its own comment names the
property: *"a row closed between the caller's read and this write is left untouched rather than
having a confirmation stamped onto its already-closed metadata."* That is the correct behaviour
and it is the property the launch brief asked about ("can a confirm-write resurrect or extend an
episode a superseded close already settled?"). The answer is no — **by a code shape nothing
gates.**

**MEASURED:** deleting the `.eq("status", "running")` line from `_confirm_row` and running
`tests/test_mt5_session_episodes.py tests/test_mt5_relogin.py tests/test_mt5_session_monitor.py
tests/test_mt5_concurrency.py` gives **356 passed**. The suite is completely blind to it.

The harness that can reach this interleave already exists — `_OrderedCronRuns.after_select`
lands another container's write between our read and our write, and its own docstring says *"a
harness that cannot tell them apart is one that certifies the bug."* It is used at exactly two
sites, both on the CLOSE path (`_container_a_closes_it_genuinely`,
`_container_a_closes_it_first`). The confirm path — the one this round added — has no such
driver.

Without the scope, a confirmation would be stamped onto a row another writer had already closed:
`last_confirmed_at` LATER than `completed_at` on a settled episode, which is precisely the
"resurrect/extend" shape, and which a successor computing lifetimes has no way to detect.

**Fix:** one test, reusing the existing hook.

```python
async def test_WR_15_a_confirm_that_LOST_its_race_leaves_the_SETTLED_row_untouched(
    sink: _OrderedCronRuns,
) -> None:
    """⛔ A confirm is scoped to `status='running'` so it cannot stamp a
    confirmation onto an episode another writer already settled — a
    `last_confirmed_at` LATER than `completed_at` is the resurrect shape."""
    seeded = _seed_open_row(sink, mt5_session_episodes.STATE_AUTHORIZED, id="live")

    def _container_a_closes_it_between_our_read_and_our_confirm() -> None:
        seeded["status"] = "ok"
        seeded["completed_at"] = "2026-09-15T02:00:00+00:00"

    sink.after_select = _container_a_closes_it_between_our_read_and_our_confirm

    await _observe(_AUTHORIZED_READING)

    meta = sink.metadata(seeded)
    assert "last_confirmed_at" not in meta, (
        "a confirm stamped a settled episode — its `last_confirmed_at` would "
        "post-date its own `completed_at`"
    )
    assert "confirmations" not in meta
    assert seeded["completed_at"] == "2026-09-15T02:00:00+00:00"
```

Calibrate it by deleting the `.eq("status", "running")` line and confirming it reds.

### WR-16: WR-12 gated the CAS oracle's READ but not its REQUEST — dropping `count=CountMethod.exact` leaves both WR-12 tests green

**File:** `analytics-service/services/mt5_session_episodes.py` — symbol `_close_row`, its
`_update()` closure; `analytics-service/tests/test_mt5_session_episodes.py` — symbol
`_MinimalReturningCronRuns`

**Issue:** the fix is two halves and only one is gated.

* **The read half IS calibrated.** Reverting to `return bool(rows(response))` REDS
  `test_WR_12_a_WON_compare_and_set_is_read_from_COUNT_not_inferred_from_rows` with its own
  message ("a WON compare-and-set against a minimal-returning transport read as LOST"). Measured.
* **The request half is not.** MEASURED: replacing `.update(payload, count=CountMethod.exact)`
  with `.update(payload)` and running `-k WR_12` gives **2 passed**.

The cause is in the fake. `test_mt5_relogin._FakeQuery.execute` is careful — it sets
`response.count = len(hits)` only `if self._count_requested == "exact"`, which is exactly right.
But `_MinimalReturningCronRuns._execute` then overwrites it unconditionally:

```python
            if query._op == "update":
                response.count = len(response.data)
                response.data = []
```

so the minimal-returning transport VOLUNTEERS a count the request never asked for. Against real
postgrest, `count` is only populated when `Prefer: count=exact` was sent — so an edit that drops
the kwarg (a reviewer "simplifying" a call, a merge conflict resolution) reinstates the whole
WR-12 defect: under a future `returning='minimal'`, `response.count` is `None`, the fallback
reads `len(rows(response)) == 0`, **every winning close reports LOST**, every row carries
`started_at_is_lower_bound: true`, and the "lost its compare-and-set" WARNING fires on every
ordinary transition — with the suite green. That is the exact failure WR-12 was raised to
prevent, one kwarg away, and no gate between.

**Fix:** make the minimal transport honour the request, exactly as the base fake does.

```python
        def _execute() -> Any:
            response = original()
            if query._op == "update":
                # ⛔ WR-16 — HONOUR THE REQUEST. Real postgrest sets `.count`
                # ONLY when `Prefer: count=exact` was sent. A fake that
                # volunteers it makes the `count=` kwarg untestable, and
                # dropping that kwarg is exactly how WR-12 comes back.
                assert getattr(response, "count", None) is not None, (
                    "the UPDATE did not request `count=exact`, so a real "
                    "minimal-returning transport would answer `None` and "
                    "every WON compare-and-set would read as LOST"
                )
                response.data = []
            return response
```

⚠️ The base fake compares against the literal `"exact"`; `CountMethod` is a `str` Enum on
postgrest 2.31.0 (`isinstance(CountMethod.exact, str)` is `True`), so that comparison holds
today — but a future postgrest turning it into a plain `Enum` would silently stop setting
`.count` in the fake. Comparing against `CountMethod.exact` by symbol rather than the string
literal costs nothing and removes that dependency.

### IN-10: a close in another container ERASES the confirmations written by this one

**File:** `analytics-service/services/mt5_session_episodes.py` — symbols `_confirm_row`,
`_close_row`

**Issue:** both functions do a read-modify-write of the whole `metadata` object from the snapshot
their caller read at `_read_open_rows()` time. Same-process this is fine (each tick re-reads, so
`confirmations` accumulates correctly — the CONFIRMS test drives 1 → 2 and proves it). Under the
Railway deploy overlap the module is designed for, container A confirms and container B — whose
snapshot predates that confirm — then closes the row, writing back a `metadata` with no
`last_confirmed_*` keys at all. Both UPDATEs are `status='running'`-scoped, so both apply, and
the liveness evidence for that episode is silently gone at exactly the moment the module's
two-writer reasoning is in force.

**Fix:** none required for correctness (the count is advisory, and the durable STATE is

### IN-12: the WR-08 floor's "BY CONSTRUCTION" is a claim about a SUM; the two deadlines are ordered, and at the exact floor the outer one still wins

**File:** `analytics-service/services/mt5_session_monitor.py` — the
`_MT5_SESSION_POLL_INTERVAL_FLOOR_S` derivation comment and the WR-02/WR-08 comment inside
`mt5_session_monitor_loop`

**Issue:** the comment asserts *"`interval >= floor >= actual_lease_wait + actual_budget` holds
for every value each knob's own window admits."* The arithmetic is right (≤ 30 + ≤ 300 ≤ 330),
but the two timers do not start together: the tick's `asyncio.wait_for(..., timeout=interval)`
begins at t₀, and the heal's bounded acquire begins at t₀+ε (after `mt5_enabled_server()`, the
credential read, the endpoint read and the INFO line). At the exact configuration
`MT5_SESSION_POLL_INTERVAL_S=330`, `MT5_RELOGIN_LEASE_WAIT_S=30`, `MT5_RELOGIN_BUDGET_S=300` —
each individually legal — a heal that consumes both bounds in full expires at t₀+ε+330 while the
outer deadline expires at t₀+330. The outer one still pre-empts the heal's own
`budget_abandoned` arm, which is the precise outcome WR-08 set out to make impossible.

**Fix:** either make the floor a strict cushion above the sum, or state the condition honestly.

```python
#: ⚠️ A CUSHION, not an exact equality: the tick's own deadline starts BEFORE
#: the heal's acquire does, so a floor exactly equal to the sum still lets the
#: outer bound win by the width of the preamble.
_MT5_SESSION_POLL_INTERVAL_FLOOR_S: Final[float] = (
    _MT5_RELOGIN_BUDGET_CEILING_S + 2 * _MT5_RELOGIN_LEASE_WAIT_CEILING_S
)
```

⚠️ Recorded as a boundary-only defect: it requires all three knobs set simultaneously to their
own extremes, and the shipped defaults (600 / 2 / ~35) leave ~560 s of headroom. The wording is
what overstates, not the number.

### IN-13: two shipped test docstrings state a reason that is false — the deadline arm makes no DB call

**File:** `analytics-service/tests/test_mt5_session_monitor.py` — symbol
