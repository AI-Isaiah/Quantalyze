## Skipped Issues

### IN-03: `session_poll_interval_s()` is read twice per iteration, so the interval recorded in a row can differ from the one actually slept

**File:** `analytics-service/services/mt5_session_monitor.py:` `run_mt5_session_monitor_tick`, `mt5_session_monitor_loop`
**Reason:** the review's exact suggested fix ("read once per iteration at the top of the
`while` body, inside the per-tick guard, and pass the same value to both") requires changing
`run_mt5_session_monitor_tick`'s public no-argument call signature so the loop can thread a
single reading into both the tick and its own wait. That signature is currently relied on,
as a zero-argument callable, by **6 monkeypatch call sites** across
`test_A_TICK_THAT_RAISES_DOES_NOT_END_THE_LOOP`,
`test_A_RAISING_TICK_NEVER_REACHES_THE_CRASH_HANDLER`,
`test_the_first_ITERATION_waits_BEFORE_ticking_...`,
`test_the_kill_switch_OFF_skips_the_tick_and_NEVER_ends_the_loop`,
`test_a_tick_that_fails_MID_FLIGHT_...`, and
`test_a_tick_that_fails_EVERY_time_...` — plus `_LOOP_GUARD_MUTANTS`'s own
`"the-guard-no-longer-demonstrably-covers-the-tick-call"` mutant, whose anchor is the literal
text `"await run_mt5_session_monitor_tick()"` (zero-arg). Threading a parameter through would
require touching all of these plus the mutant anchor, for an **Info**-severity finding whose
real-world cost is a one-tick disagreement between the row's recorded `poll_interval_s` and the
loop's next sleep duration — negligible next to the blast radius. WR-06 (already fixed in this
pass, commit `62bb0a24`) independently narrows the exposure window: the tick's own heal call is
now bounded to `interval` seconds, so the maximum straddle between the tick's read and the
loop's subsequent read is now itself bounded by the configured cadence rather than unbounded.
Left as a documented, lower-priority follow-up rather than forcing a wide signature change
under this fix pass; a future phase touching this loop's call shape for another reason should
pick this up at the same time.
