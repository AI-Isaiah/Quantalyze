## LOW (new)

### N-1 `services/ccxt_flow_fetch.py:116-120`: the empty-raw-page early return is the one exit with no log, and it also swallows the only fingerprint of shape drift

Evidence. Scenarios C and D above. `if not raw_rows: return True` is correct for the sticky-cursor case (F-1), but it exits before `nxt` is read and before anything is logged, whatever the answer held. An answer whose rows moved to a key `add_pagination_cursor_to_result` does not read (`list`, `rows`, `data`, `dataList` only) arrives as "zero rows plus a non-empty `result.nextPageCursor`". A genuinely empty last page carries `""`. Before round 2 that shape was loud (the walk continued on the cursor and raised `TransferPageStalled` when it repeated); now it ends the window clean. This is the same family as round-2 L-1 (a malformed answer reads as an empty window), which stays open and is not re-raised here; what is new is that the F-1 fix removed the incidental tripwire that used to catch part of it.

Hidden errors: a Bybit answer-shape change on the deposit or withdraw record endpoint (renamed rows key) reads as "this window has no transfers" for every Bybit allocator, with no trace. Today that needs a venue change that ccxt would also have to follow, which is why this is LOW and not MEDIUM.

User impact: flows silently missing from the flow-aware TWR base and from composite NAV marks, nothing in the logs to find it by.

Minimal fix. Count-only line on the one branch that can be told apart from a clean end:

```python
if not raw_rows:
    if _bybit_next_cursor(response) is not None:
        logger.warning(
            "Bybit transfer page held no rows but carried a cursor "
            "(kind=%s window_start_ms=%d)", kind, window_start,
        )
    return True
```

Test: scripted answer `{"result": {"rows": [], "nextPageCursor": "c1"}}` logs once and returns `[]`; the F-1 test still passes (it would log once on its second page, which is accurate).

### N-2 `services/ccxt_flow_fetch.py:126-137`: the drop warning cannot tell its three causes apart, and one of them (the 50-row slice) still loses credited rows with a log line only

Evidence. `parse_transactions` drops (a) rows stamped 0 or None (an uncredited or failed deposit, the common benign case), (b) rows older than `window_start` (the `since` filter), and (c) everything past 50 after the ascending sort (scenario B: 60 raw rows, the 10 newest are discarded, the walk then continues on the cursor, and nothing is re-read). The log reports `raw_rows=60 parsed_rows=50`, the same shape as ten uncredited deposits. Two consequences. First, a deposit that will never be credited (a rejected one stays stamped 0 forever) is inside its 30-day window on every derive for a month, one WARNING per derive per page, indefinitely, which trains the operator to ignore the line that would also announce (c). Second, (c) is a data loss, not a benign drop, and the round-2 disposition declined the raise. That disposition stands (the endpoint is asked for `limit=50` and Bybit honours it; the round-2 fix report records it as not fixed), so this is a note on observability only.

Hidden errors: a venue that ignores `limit` (or a future ccxt that raises the cap) sends more than 50 rows; the newest ones are cut and counted only as a generic drop.

User impact: low; the line exists and carries the numbers. The cost is diagnosability, not a hidden failure.

Minimal fix. Add the one number that separates (c) from the rest: `over_limit=max(0, len(raw_rows) - _BYBIT_TRANSFER_PAGE_LIMIT)` in the same line, so `over_limit > 0` is greppable and unambiguous. No new raise, no new abstraction. Test: 60 raw rows logs `over_limit=10`; a 3-row page with one stamp-0 row logs `over_limit=0`.

## Things checked and found sound (no finding)

- Ordering inside the loop: `raw_rows` first, empty-page return, parse, drop log, `nxt`, row append and dedup, `nxt is None` return, then the seen-cursor raise. The seen-cursor and ceiling raises remain reachable and cannot fire on a natural end. The page's rows are appended before the seen-cursor raise, but the raise discards `all_rows` with the exception, so no partial list escapes.
- `add_pagination_cursor_to_result` mutates raw row 0 in place (writes `nextPageCursor`). It runs before `parse_transactions` and before `_bybit_next_cursor(response)`, and the cursor read comes from `response["result"]`, which the mutation does not touch. The ordering change in round 2 therefore does not change which cursor is read.
- Only `ccxt.NotSupported` is caught, around `load_markets` and the endpoint call. `add_pagination_cursor_to_result`, `parse_transactions` and the new log call sit outside the `try`, so a non-dict raw row (`first['nextPageCursor'] = ...` on a non-dict), a parse error or a malformed stamp propagates rather than being swallowed.
- The drop log passes `%d` for `window_start`; an int in every caller, and a `logging` format error would print to stderr rather than raise into the job.
- The non-Bybit branch of `fetch_ccxt_transfers` is unchanged by round 2 (its 1000-page ceiling still logs a WARNING and continues, pre-existing and out of this phase's scope, Binance and OKX read exactly as before).
