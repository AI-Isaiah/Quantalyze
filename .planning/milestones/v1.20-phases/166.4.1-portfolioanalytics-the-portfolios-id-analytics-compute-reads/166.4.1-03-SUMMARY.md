## Deviations from Plan

**1. [Rule 3 - blocking, scope call for the orchestrator] A latent page-crash defect, fixed at the adapter.**
- **Found during:** Task 2, first Playwright run (5 of 5 failed: the page showed its "Something went wrong" error boundary; the dev log named `PortfolioEquityCurve.useEffect`: `Invalid date string=2026-06-11T00:00:00, expected format=yyyy-mm-dd`).
- **Issue:** `_series_to_curve` in the Python router serializes a DatetimeIndex with `Timestamp.isoformat()`, so a computed `portfolio_equity_curve` (and `rolling_correlation`) stores `2026-06-11T00:00:00`. lightweight-charts accepts only `yyyy-mm-dd`. Any portfolio computed by the real Python service therefore crashed `/portfolios/[id]` into its error boundary. It is PRE-EXISTING (the DatetimeIndex and `isoformat()` predate WEALTHRETURNS; the page never met such a row because the compute selected phantom columns until #973, and PROD's 6 rows are seeder rows with date-only strings). It is not caused by Plans 01 or 02. It blocks SC-5 outright, so it was fixed rather than hidden.
- **Fix:** `parseTimeSeriesPoint` in `src/lib/portfolio-analytics-adapter.ts` keeps the `yyyy-mm-dd` of a stored timestamp, covering every time series the adapter reads and any already-stored row. Failing-first test `normalizes a stored timestamp to its calendar date on every time series` was seen RED (`1 failed | 21 passed`) before the fix, then GREEN. The Python writer's stored shape is unchanged, so no Plan 01 test moved.
- **Files:** `src/lib/portfolio-analytics-adapter.ts`, `src/lib/portfolio-analytics-adapter.test.ts`. **Commits:** 4c8c80cd3 (test), 3c315792f (fix).
- **For the orchestrator:** this is production code in a plan whose text says "adds no production code". The two commits are self-contained; drop them if you would rather fix the writer (`_series_to_curve`, which `verify_strategy` also uses) and re-run the spec. CHANGELOG (Plan 04) should name it.
