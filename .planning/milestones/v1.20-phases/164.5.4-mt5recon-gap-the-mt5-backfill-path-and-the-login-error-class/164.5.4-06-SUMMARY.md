# Phase 164.5.4 Plan 06: the MT5 backfill branch, wired end to end Summary

**An MT5 allocator's first key connect now produces a real reconstructed dollar equity
curve instead of `failed (unknown)`: `run_reconstruct_allocator_history_job` has an
explicit `venue == "mt5"` branch that makes the generic ccxt crawl unreachable by
construction, takes its own go-dark gate, answers eleven failure shapes with a recorded
disposition, persists nothing on any of them, and can stamp permanent-and-blamed on
nothing but a genuine auth signal.**

## The defect, and why the fix is a branch rather than a guard

`Mt5Session` carries **none** of the six ccxt methods `_fetch_and_price_window` reaches
for — a measured 0/6. An MT5 allocator therefore fell into the generic crawl and died on
`exchange.fetch_my_trades(...)` with `'Mt5Session' object has no attribute
'fetch_my_trades'`. That is an `AttributeError`, invisible to the `except
ccxt.NotSupported` arms around it, so it surfaced as an unclassified `failed (unknown)` —
measured in PROD on 2026-09-16.

Widening an `except` would have hidden the class and left the other five methods waiting
for the next caller. The branch closes it: `_fetch_and_price_window` is now unreachable
for mt5, and `test_mt5_backfill_never_reaches_the_ccxt_crawl` proves that by replacing it
with a landmine and requiring the job to still reach `DONE`.

⭐ **The unreachability assertion is on REACHABILITY, not absence, and that distinction is
the whole point.** A real `Mt5Session` has no `fetch_my_trades` — asserting its absence
would be asserting the bug. So the test's session is given booby-trapped versions of all
six methods that raise if touched; if the branch is deleted, the crawl now *finds* the
attribute, calls it, and the failure names exactly which method it reached.

## A-04, settled — and the reasoning lives in the arm

The plan's `<decision_a04>` was binding and was followed without re-litigation: **only
`auth` is permanent; `wrong_server` and every unrecognised signal are transient.** The
three measurements are written into the `except Mt5ClientError` arm's own comment, not
only here, because a future reader will otherwise find the researcher's contrary
recommendation in `164.5.4-RESEARCH.md` and "fix" this back:

1. **Validate already proved the server.** The job runs only against an existing,
   `is_active` `api_keys` row, which exists only because `validate_key`'s MT5 arm accepted
   the login AND the server at connect. "No prior READ" is not "no prior PROOF".
2. **The sibling derive branch chose the same**, and its shipped comment names the failure
   mode of the other choice: the token set can fold network/bridge faults into
   `wrong_server`, so a routine gateway redeploy would permanently fail a valid account.
3. **CONTEXT.md's D-01 is binding**: this path "cannot stamp permanent-and-blamed either".

The cost is asymmetric and terminating: transient exhausts the DB backoff to
`failed_final` — a verdict, just later — while permanent strands a working account
immediately, on a job that runs ONCE per key.

## The message table, and why it is a table

⛔ **No arm concatenates broker-supplied text into `error_message`.** Every message this
branch can write into `compute_jobs.error_message` is a fixed member of
`_MT5_BACKFILL_MESSAGES`; the scrubbed broker detail goes to the audit event's
`sanitized_message` and to the warning log, neither of which is ever re-classified.

That is a deliberate divergence from the derive branch's `"... — " + scrubbed` shape, and
it is what makes the plan's acceptance criterion *satisfiable*: "every constructible
`error_message` classifies `transient`" is only provable over a BOUNDED set.
`test_no_mt5_backfill_message_is_classifier_matchable` runs the **shipped** classifier over
all eleven members — never a grep — so a future `[ASSUMED]` table edit that would make one
of these sentences read as a credential accusation reds there rather than in PROD.

## The row contract

- **Window clip** to the same `[start_date, end_date]` the ccxt path computes from
  `BACKFILL_CAP_DAYS`. `persist_equity_snapshots` does ONE atomic upsert sized on that
  window in its own docstring, and `history_deals_get` is a full-history fetch. Proven with
  a ledger ~900 days long: the row count is `BACKFILL_CAP_DAYS + 1`, bounded by the window
  and not by the ledger.
- **Densify-then-clip, in that order.** A ledger that STARTED before the window must still
  contribute its carried balance on `start_date`; clipping first would drop the last
  pre-window event and lose the level entirely.
- **Forward-fill** across interior quiet days, citing `native_nav._reindex_ffill`'s own
  statement of the semantics — a realized balance is constant between ledger events, and
  this is not a price fill. ⛔ Never `gap_fill_daily_returns`.
- ⛔ **No row before the first ledger day.** This is the half of `_reindex_ffill` that does
  NOT transfer: `0.0` for "it did not exist yet" is right for a per-currency bucket and is
  read by the dashboard as a **real balance of zero**. The distinction is written as a
  comment on the row builder so the next reader does not "align with `_reindex_ffill`" and
  reintroduce it.
- **Flags:** `source` `'exchange_primary'` (the deal ledger IS the venue's primary record,
  and the column is CHECK-constrained to three values), `breakdown` NULL,
  `pre_terminus_balance_unknown` False, `hit_terminus` False so `history_depth_months`
  stays NULL for mt5 and the terminus warning is never logged.
- **A never-traded (deposit-only) ledger** yields an empty level series, which routes to
  the job's EXISTING no-data disposition — `reconstruct_no_data`, `DONE`, zero rows — never
  a flat curve fabricated out of pure capital flows.

### ⭐ The NULL-`breakdown` reader verdict — VERIFIED, not assumed

The plan demanded a verdict naming the readers inspected. All four were read; **NULL is
safe in every one**, and in each case it is safe by an explicit guard rather than by luck:

| reader | handling of a NULL breakdown | verdict |
|---|---|---|

⭐ And it is the only honest value: MT5 is single-currency with no per-symbol
decomposition, so a fabricated single-key breakdown would invent a decomposition that does
not exist. A per-symbol series for an MT5 account correctly comes back as "not available"
rather than as a wrong one.

## Honest limits, named rather than smuggled

- **The omitted anchor keys are honest at the telemetry seam and flattened downstream.**
  `_mt5_telemetry` deliberately omits `anchor_partial_ticker_symbols`,
  `anchor_offset_implausible`, `anchor_replay_unreliable` and `anchor_offset_skipped_usd`,
  because MT5 attempts no anchor step. The SHARED audit emit reads all four through
  `.get(..., default)`, so the emitted metadata carries the defaults anyway and an operator
  cannot distinguish "no anchor attempted" from "anchor attempted and clean". Fixing that
  would mean changing the ccxt path's own emit, which is outside this plan's files. It is
  an observability nuance with no data-integrity or user-facing consequence, so under the
  standing rule it is fix-or-drop rather than a deferral that names a phase — recorded here
  so the residual is visible, not filed as work.
