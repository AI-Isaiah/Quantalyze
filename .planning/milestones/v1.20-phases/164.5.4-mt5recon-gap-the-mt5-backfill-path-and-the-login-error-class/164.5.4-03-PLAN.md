<planner_findings>
## MEASURED AT HEAD BY THE PLANNER — read before writing code

**1. The component's state and the code's fate.** `KeyPermissionBadge` holds exactly three pieces of
state: `perms`, `loading`, `error` (plus a `mountedRef`). Inside `load`'s non-ok branch it reads
`err.code`, sends it to `console.error` as its OWN argument and to `addSentryBreadcrumb` as
`message`, and then throws a `RouteResponseError` carrying ONLY the human sentence. The code is
never retained. The header button's `disabled` is gated on `loading` alone.
⇒ The fix needs ONE new piece of state, set where the code is already read, and one term added to the
`disabled` expression. That is the whole change.

**2. ⛔ Do NOT wire this component onto `classifyKeyValidationError` "to share the fix".** The
permissions route's own docblock records that routed through that classifier, FIVE of its SIX real
thrown messages fall to `UNKNOWN`/500, because every fault reachable there is a PROXY-INFRASTRUCTURE
fault and that function classifies KEY faults. The route's own `code` field is already correct and is
what the component must read.

**3. The component must HARDCODE the literal.** `src/lib/probe-vocabulary.invariant.test.ts`'s
`ROSTER` is TEST-ONLY — measured: zero non-test references to `retryClearsIt`. There is no shared
production constant to import, and the permissions route itself hardcodes the same literal. Match the
route.

**4. ⭐ `KEY_UNDECRYPTABLE` is the ONLY `retryClearsIt: false` member of that six-member ROSTER**
(`CIRCUIT_OPEN`, `PROBE_RATE_LIMITED`, `KEY_UNDECRYPTABLE`, `PROBE_BACKEND_UNAVAILABLE`,
`PROBE_TIMEOUT`, `PROBE_FAILED`). That matters twice over:
  - gating on it introduces ZERO behavioural change for any other code today, so the gate is narrow
    by construction rather than by care;
  - the file ALREADY carries a `!e.retryClearsIt` filter with its own non-vacuity guard ("no roster
    entry is marked `retryClearsIt: false`, so the retry-framing assertion below would iterate an
    empty..."), so binding the component to that filter inherits a working non-vacuity floor instead
    of inventing one.

**5. `KeyPermissionBadge.test.tsx` already has the harness.** Its `ROUTE_REFUSALS` table already
carries `KEY_UNDECRYPTABLE` with its status and prose, alongside `CIRCUIT_OPEN`,
`PROBE_RATE_LIMITED` and siblings, driven by a `mockRefusal` helper. EXTEND that table and its
describe block; do not build a parallel harness.

**6. `disabled`, not removal — and the reason is a test property, not taste.** Keeping the control
rendered with `data-testid="key-permission-recheck"` and asserting its `disabled` attribute is a
stronger, less brittle gate than asserting absence, and the route's own reconnect sentence renders
directly beside it and explains why it cannot be used. An absent control with no explanation is
worse for the founder than a disabled one beside a sentence that says retrying will not help.
</planner_findings>
