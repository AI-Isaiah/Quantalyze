## SC-8 deploy note

Same text as `167.1.2.1.1-DEPLOY-NOTE.md`.

**Avoid 03:30-06:45 UTC for the Railway deploy.** The chain is the poll at 04:00 (`poll-allocator-positions`), the refresh fan-out at 05:00 (`refresh-allocator-equity`) and the per-key derive at 05:30 (`derive-allocator-key-dailies`), verified in `scripts/prod-prober/cron-manifest.json`. Composes were observed finishing by about 06:30 UTC; the 06:45 end is a margin over that reading (RESEARCH assumption A3), and 03:30 is the 04:00 poll with half an hour of lead. Railway deploys only after main's CI is green, so merge with CI's duration in mind: the deploy, not the merge, must land outside the window. At landing, read the Railway deployment's creation time and record that it is outside 03:30-06:45 UTC.

**The window is not widened.** R3-WR-02's emptiness proof (`_polled_empty_since`) accepts a proof only from a `sync_completed` event whose metadata carries `final_status` and `asof`. Every `sync_completed` event has carried both since Phase 167.1.2 PR C2, so every current event has the new shape. This phase changes neither the event, nor the proof, nor any dependence on poll-event timing for a proof: its new "polled" evidence needs only that an event EXISTS, in any shape. D-02's cap shortens the worst case of the same class: an account without proof now holds after 7 days instead of being carried indefinitely.

**A held day is a permanent gap by design.** `allocator_equity_snapshots` is first-writer-wins on `(allocator_id, asof)` with one refresh job per key per day, so a held day is never back-filled: a permanent gap. Its readers are the dashboard snapshot counts, the GDPR export and a non-gating script. The Overview curve reads `allocator_equity_derived`, not the snapshots table.

**After landing.** The derivecron runbook's `v2_rows_fresh` counter now also counts refusal rows (plan 01 writes a refusal row where it used to delete the curve row), because that counter never filtered on trust: a refusal row is version 2 with a fresh `computed_at`. A fresh count is therefore not proof of a successful compose; filter on `is_trustworthy` for that (the runbook's `fresh` count in `d06` already does).
