## Summary

The writer side of `allocator_equity_derived` has exactly **one** application reader of the `kind='equity_curve'` row: `getMyAllocationDashboard` / `derivePhase07Fields` in `src/lib/queries.ts`. No Python code, no SQL function and no RPC reads it (the match scorer imports `account_identity_tokens` and `one_key_per_account_day` from the derive module but reads neither the derived table nor `allocator_equity_snapshots` at HEAD; the CONTEXT line saying `match.py` reads the snapshots is stale). The reader's gate is two independent guards: `trustworthyDerivedCurve` needs `is_trustworthy === true` and a non-empty well-formed curve, and every other field the producer stamps from the payload is gated on `equityHistoryState === "ready"`. That makes the recommended storage shape safe: **keep the refusal in the same `(allocator_id, 'equity_curve')` row** as a version-2 payload with `is_trustworthy:false`, `curve:[]`, `returns:[]` and `degrade_reasons:[<token>]`. One atomic upsert replaces a stale trustworthy curve and records the reason; a separate `kind` would need a second read in the dashboard `Promise.all` and a non-atomic delete-plus-insert. The reader already routes an untrustworthy v2 row through `untrustworthyRebuildReason(payload)`, so D-04 is a mapping extension of one pure function plus widening the `MissingSeriesReason` type with two existing members; no new reason, no new copy, no change to the `REBUILD_REASON_CLASS` table.

The five writer-side checks are small and local. SC-2, SC-3 and SC-6 add three blocking `DegradeReason` members that travel through `compose_allocator_equity(degrade_reasons=...)` exactly as `SHARED_ACCOUNT_NO_WORKING_KEY` and `SHARED_ACCOUNT_HISTORY_TRUNCATED` do today. SC-4, SC-5 and SC-6 (refresh half) are one hold mechanism placed right after `_fetch_latest_holdings_per_eligible_key` and before the breakdown loop. **The load-bearing finding for SC-4 is the definition of "never polled":** it must be "no `allocator.holdings.sync_completed` audit event for any member key", NOT "no `allocator_holdings` row". On PROD today 5 of 23 eligible keys (all Deribit) have no holdings rows but have a successful empty poll on record; a row-based predicate would freeze one allocator's snapshots permanently. Today none of the D-01, D-02, D-03 (SC-6) predicates fires on PROD (0 never-polled working accounts by the event definition, 0 carries over 7 days, 0 failing keys, 0 unstamped working ccxt keys), so the blast radius of landing is zero by measurement.

SC-9 is **not reproducible**: today every one of the 8 connected MT5 keys, the BTC-unit one included, replays clean on its stored writer basis (implied start at most 1.3e-14 of the first return day's level against the 1e-4 band), book 1 reads trustworthy since the 2026-10-14 derive, and no PROD `equity_curve` row carries `inception_unreconciled`. The 0.15% was measured on rows written before the 164.6.6.2.3 (FLOWTIMING) recompute; those rows are overwritten, so the exact old inputs cannot be re-observed. Verdict: a writer-side cause that is already fixed upstream, plus a stale premise in the ROADMAP; no writer change for SC-9 and no band change. The orchestrator informs the founder (D-05 asks that the measurement go back when the data is right).

**Primary recommendation:** persist a same-row refusal payload (one helper, one closed token enum, one cross-runtime JSON fixture), extend `untrustworthyRebuildReason` and `MissingSeriesReason` to map every token to an existing line, add three blocking tokens, add one refresh hold with the poll-event "polled" predicate and a single new audit action `allocator.equity.refresh_held` (reason in metadata), write `departed_history_unavailable_keys` into `payload["inputs"]`, and close SC-9 by a recorded re-measurement with no writer change.

### Finding 2 - SC-2 / D-03: one failing key whose series ends early

- **Why it is silent today:** `run_derive_allocator_equity_job` skips every group with fewer than two eligible members (`if len(members) < 2: continue`) before `no_working_groups` is counted. In `portfolio_returns` (`allocator_equity_compose.py`) a non-rotated key whose series ended "keeps its last level with `r = 0` (stale-mark carry)"; the benign `STALE_MARK_CARRY` is the only trace.
- **Predicate (computed in the derive, in memory):** after the group loop and after the no-capital exit rule has run (so exiting keys are excluded), for each group with exactly one eligible member `m` in `counted_ids` and `not working_holder_predicate(m)`: flag when `last_return_day[m] < book_last`, where `book_last = max(last_return_day[k] for k in counted_ids if k in last_return_day)`. `last_return_day` already exists (built from `csv_rows` before the loop). Exclude any key in `departed_end_by_key` (no-capital exits and the BTC `priced_through` exit leave the book by design). Groups of two or more eligible members keep today's unconditional `no_working_groups`.
- **Account id known:** the derive need not test it. A failing ccxt key with an unknown id is caught earlier by the reader (`pending.some(failingToSync)` -> `key_not_syncing`, before the series is read), so a superset flag from the derive is harmless; parity is by reader precedence.
- **New member:** `DegradeReason.FAILING_KEY_SERIES_ENDED = "failing_key_series_ended"`, added to `_BLOCKING_REASONS`, passed in the `degrade_reasons=[...]` list next to `SHARED_ACCOUNT_NO_WORKING_KEY`.
- **Reader mapping:** `key_not_syncing` is NOT usable: it is a key-list reason, only reachable for `identityStillPending` keys, and its line says "so we cannot confirm which exchange account it reads", which is false for a key whose account id is known. `derivation_rejected` is true but non-actionable. The true, actionable, existing line is `shared_account_no_working_key`: "The keys that read one of your exchange accounts are all failing to sync, so that account's history stops. Fix or reconnect one of them on the Exchanges page." (class `needs_action`). Map the token there in `untrustworthyRebuildReason`.
- **Parity table (R2-WR-01):** `shared_account_resolution.json` gives every key the same three return days, so no cell has a series that ends early and no existing cell changes. Add a SMALL second fixture (see Validation Architecture) rather than a third axis on the 72-cell table.

### Finding 3 - SC-3 / D-03: flows disagree on an owned day

- **Mechanism today:** `stitch_shared_account(links)` takes, for each day, flows only from the member that owns it ("the first member keeps its flows dated before its first day"; for `index > 0`, `flow_day < own_first` is dropped; for a non-last member `flow_day >= next_first` is dropped). A newer key's flow on an older member's owned day is silently dropped.
- **Flows carried:** `ExternalFlow(utc_day_iso, usd_signed, currency="USD", quantity=None)`, deposits positive, no transaction id. The derive builds `source_flows[k]` (older members) and `flows_by_key[kept]` (counted member) from each `key_inputs` row's `flows` list, run through `validate_flow_shape`.
- **Honest computation:** a new pure helper next to `stitch_shared_account` that shares ONE ownership function with it (so the stitch and the check cannot drift): owned(i) = `[own_first_i, next_first_i)`, with member 0 also owning every earlier day. For each owned day `d` of member `i`, compare `S_i(d)` (the per-day sum of member `i`'s flows) with `S_j(d)` for every later member `j` that LISTS the day. Disagreement is: some later member lists day `d` (non-empty) and `abs(S_i(d) - S_j(d))` exceeds a tolerance, including `S_i(d) = 0` (the "newer key lists a deposit the owning key does not" case). A later member that lists nothing on `d` is NOT disagreement (its crawl may simply not reach back; absence is silence, not evidence). Return the count of disagreeing days (counts only in logs).
- **Tolerance:** `math.isclose(a, b, rel_tol=1e-9, abs_tol=0.01)` (USD). `[ASSUMED]` (A1): two keys of one account price the same transfer through the same code path, so equal inputs give byte-equal floats; the abs floor only absorbs cent rounding. A boundary pair of tests (exactly at, just over) pins it.
- **Reaction:** when `S` disagreement > 0 for a stitched account, count it like `truncated_accounts` (refuse that stitch, keep the counted member alone) AND raise `DegradeReason.SHARED_ACCOUNT_FLOWS_DISAGREE = "shared_account_flows_disagree"` (blocking). Reader line: `shared_account_history_truncated` ("we cannot join its history from before the change to the new key's, so your history is not shown", class `held_back`), which is true for it. Agreement keeps today's stitch and the benign `shared_account_history_stitched` flag.
- **Blast radius on PROD today:** 13 marked keys, 1 of them eligible, 0 same-account eligible pairs: the check cannot fire now.

### Finding 4 - SC-4 / SC-5 / D-01 / D-02: the hold

**Where it lands in `run_refresh_allocator_equity_daily_job`:** right after `latest = await _fetch_latest_holdings_per_eligible_key(...)` and the carry-age warning, BEFORE the breakdown loop. **Fields to add to `_LatestHoldings`** (all counts): `never_polled_working_accounts` (hold), `never_polled_failing_accounts` (left out, D-01), `polled_no_rows_accounts` (informational), `over_age_accounts`, `oldest_over_age_days`, `identity_pending_venues` (SC-6). **The "never polled" predicate (critical).** `_fetch_latest_holdings_per_eligible_key` today treats "no `allocator_holdings` row for the group" as never polled (`if not asofs: never_polled += len(eligible); continue`). A ccxt poll with an empty result persists NO rows (`persist_allocator_holdings` writes nothing for an empty list), Deribit rows are skipped from the total anyway, and sFOX/unsupported venues return no rows with a warning. PROD today (23 eligible keys, 2026-10-16): 18 have holdings dated today; **5 (all Deribit) have no rows at all, every one of them with a successful `sync_completed` event, and all 5 with an empty-poll event** (1 of the 5 is not linked to a strategy). > group is "never polled" iff it has no `allocator_holdings` row for any member key AND no `allocator.holdings.sync_completed` audit event (`entity_type='api_key'`, `user_id = allocator_id`, `entity_id` in the group's key ids) for any member key.

`_POLL_COMPLETED_ACTION = "allocator.holdings.sync_completed"` already exists, and `run_poll_allocator_positions_job` emits the event on every successful persist, including `complete_with_warnings` and `row_count: 0`. Read it only for groups with no rows (one `limit(1)` query per such group; the same owner filter as `_polled_empty_since`). A group with an event and no rows is `polled_no_rows` (counted, no hold, no carry). Deribit-only groups never hold (the refresh excludes Deribit rows from the total). A failed read RAISES, like every read in this function (a swallowed read would fall through to the write the hold exists to prevent).

**D-01 split:** among never-polled groups, hold iff some eligible member is WORKING (`working_holder_predicate`); a group whose eligible members are all failing is left out of the total and counted in `never_polled_failing_accounts` plus a Sentry event.

### Anti-Patterns to Avoid
- **Row-absence as "never polled"** (freezes allocators whose accounts hold nothing; see Finding 4).
- **Persisting the compose payload for an empty trustworthy compose** (reads as `malformed`, error-level Sentry).
- **A refusal row without `version: 2`** (reads `not_version_2` -> the false `awaiting_derivation` line).
- **Writing a refusal row on a transient path** (`lagging_inputs`, raised transient errors): the stale row is deliberately kept.
- **Putting a count in the payload `flags` list** (only `True` booleans become tokens; use `payload["inputs"]`).
- **Editing `account_groups` / `accountIdentityTokens` for SC-6** (not needed; would trigger the four-way coupling).
- **A second place that decides stitch ownership** (the disagreement check must call the stitch's own ownership function).

## Common Pitfalls

### Pitfall 1: the hold freezes a book that merely holds nothing
**What goes wrong:** D-01 keyed on "no holdings row" holds the daily write for ever for an allocator whose working account polls empty (PROD: 5 of 23 eligible keys, all Deribit).
**How to avoid:** "never polled" = no rows AND no `sync_completed` event (Finding 4); test with a working key that has an event and no rows (must NOT hold) and one with neither (must hold).
**Warning signs:** `never_polled_working_accounts > 0` on a book whose keys all have poll events.

### Pitfall 2: a refusal row reads as the wrong line
**What goes wrong:** `version` other than 2 -> `awaiting_derivation`; `is_trustworthy:true` with `curve:[]` -> `malformed` + error Sentry.
**How to avoid:** one `refusal_payload()` helper and the cross-runtime fixture (Python asserts the payload equals the fixture, TS asserts the reader outcome from the same fixture).

### Pitfall 3: tests that pin the old behaviour fail (this is the RED set, not breakage)
Every delete assertion in `tests/test_derive_allocator_equity_job.py` (`fake.deletes` / `_curve_deletes` around the F2, M3, F1b, B2, structural-refusal, duplicate/collision, read-cap and `test_no_capital_exit_refusal_without_a_candidate_still_deletes_the_row` tests), `tests/test_holder_matrix_parity.py` (the `refuse` branch asserts `_curve_upserts(fake) == []` and one delete), and the helper `_is_equity_curve_upsert` (used to assert "no curve upserted"; it must now tell a trustworthy curve from a refusal row). Tests that must STAY: the transient-preserves-the-row test, the no-delete assertions in `tests/test_allocator_equity_departed.py` and the compose-refusal-reverts-candidates test.

### Pitfall 4: held first day of a zero-snapshot book
A book with zero snapshots whose first day is held stays zero-snapshot; the fan-out's owed-key arm (marker-based since 167.1.2.1) does not re-bootstrap on snapshot count, so no reconstruct loop results. Cover with one test.

### Pitfall 5: N refresh jobs, N Sentry events
One refresh job per eligible key; elect a leader (smallest eligible key id) for the Sentry event, keep the audit per job.

### Pitfall 6: SC-2 flapping on a transient `error`
`sync_status = 'error'` can be transient; a key that errors for a day and recovers makes the book read "rebuilding" for that derive and ready again at the next. D-03 gives no grace; do not add one silently. Test the recovery (status back to working -> token gone).

### Pitfall 7: exits are not failures
A no-capital exit (`departed_end_by_key`) and the BTC `priced_through` exit end a key's series on purpose; exclude them from SC-2 or a correct exit reads as a failing key.

### Pitfall 8: SC-3 absence is not disagreement
A newer key that lists nothing on an owned day is silent, not disagreeing. Flag only when the newer member LISTS the day.

### Pitfall 9: runbook counters
`v2_rows_fresh` (derivecron runbook) counts refusal rows; say so in the SUMMARY so a future reading is not mistaken for a successful compose.
