### The two weight notions

The two notions are kept apart consistently:

- **Scoring weights:** strategies plus priced holdings, normalised to 1 over the series passed to the engine.
- **AUM share:** contribution over the D-16 AUM. It feeds the persisted `weight` and the max-weight test.

`compute_holding_flags`'s correlation-ceiling test uses the scoring weights for the rest-of-book blend and renormalises them over `rest_ids`. That is correct for a return blend. The two notions only meet in the engine's ticket sizing (`add_weight = ticket / portfolio_aum`). Per D-21, that ratio uses the D-16 AUM, so the 0.5 clamp on a tiny positive AUM is consistent with the founder's ruling. The AUM <= 0 branch is not covered by that ruling (WR-01).

## Critical Issues (HIGH)

### CR-01: The holding return series are string-indexed and production candidates are DatetimeIndex-indexed, so the portfolio-fit axis is null for every holdings book. The phase's tests miss this because they hand the engine string-indexed candidates.

**File:**
- `analytics-service/routers/match.py:978-983`: the series is built with `index=[day for day, _ in marks.returns]`, plain `"YYYY-MM-DD"` strings in a `pandas.Index`.
- Candidate side: `routers/match.py:558-560`. `daily_returns_from_row` reaches `services/wealth_returns.py:91` `records_to_series`, which documents "a DatetimeIndex float Series".
- Join: `services/match_engine.py:668` (`pd.DataFrame(...).dropna()`) and `services/window_alignment.py` `align_current_and_proposed`, which uses `pd.concat(..., axis=1).dropna()`.

**Issue:** `align_current_and_proposed` intersects the book's index with the candidate's index. A string `'2026-06-15'` never equals `Timestamp('2026-06-15')`, so in production a holdings-only book has zero overlap with every candidate. `_compute_portfolio_fit_components` then returns `sharpe_lift`, `dd_improvement`, `corr_reduction` and `corr_with_portfolio` as None. Those components carry 40% of the personalized score. The phase's purpose was per-holding returns from marks that feed the matcher, and in production those returns reach no candidate comparison.

Measured at HEAD with the phase's own `_context` helper (BTC book, 119 returns from marks) and the real `_compute_portfolio_fit_components`, `add_weight` 0.10:

| candidate series | sharpe_lift | dd_improvement | corr_with_portfolio |
|---|---|---|---|
| string index (shape of `_candidate_returns()` in `test_match_book_join_overlap.py:132`) | -0.0408 | 0.0052 | 0.8628 |
| the same values through `records_to_series` (shape of `_load_candidate_universe`) | None | None | None |

Two more consequences follow from the same mismatch:

- **Mixed books.** A book with strategy allocations (DatetimeIndex, `match.py:1197`) and holdings (string index) has an empty `.dropna()` join. For that book:
  - the portfolio-fit axis is null;
  - every correlation-ceiling test in `compute_holding_flags` (`rest_df.empty`) is skipped silently;
  - the new D-22 `book_join_marker` persists `book_join_too_short, shared_days: 0`. That names an overlap problem, but the calendars can overlap fully; the cause is the index type. This is a false cause in a persisted row.
- **Holdings-only books.** The marker never fires, because the holdings share string days with each other. The fit axis is still null for every candidate, which is the silent null D-22 was meant to name.

This mismatch predates the phase: the deleted `reconstruct_symbol_returns` also indexed by asof strings, and the universe became DatetimeIndex-indexed in 164.6.6.2.2. But this phase rebuilt the series construction, and its stated goal, its D-20 rationale ("a thin series could null the portfolio-fit axis") and its D-22 marker all depend on the join working. Every phase test that asserts a computing fit axis uses the string-indexed `_candidate_returns()`:

- `test_match_book_join_overlap.py:132`, `_assert_the_fit_axis_computes`;
- `test_match_scoring_weights.py`, the non-vacuity `sharpe_lift != 0.0` check;
- `test_match_book_join_marker.py`.

So none of them can see this, and the round-1 measurement of CR-01 used the same shape.

**Fix:**
1. Build the holding series on the same index type as the universe, in `_load_holding_portfolio_context`:
   ```python
   portfolio_returns[pseudo_id] = pd.Series(
       [ret for _, ret in marks.returns],
       index=pd.DatetimeIndex([day for day, _ in marks.returns]),
       dtype=float,
       name=pseudo_id,
   )
   ```
   Then check the readers that may assume string days. `book_join_marker` and `compute_holding_flags` work with either type. `holding_marks.py` keeps strings internally, which is fine.
2. Fail loud at the join. In `_score_one_allocator`, before `score_candidates`, assert that every book series and candidate series has a `DatetimeIndex`. A mixed or string index raises a named error. It must never silently empty the join.
3. Re-base the tests on the production shape:
   - `_candidate_returns()` builds through `records_to_series`, as `_load_candidate_universe` does;
   - add one end-to-end test that runs `_score_one_allocator` with a `FakeDb`-backed `_load_candidate_universe`, a holdings book, and a mixed strategies-plus-holdings book, and asserts that `score_breakdown.raw.sharpe_lift` is a float in both;
   - neuter the index fix and confirm the test goes RED.

## Warnings (MEDIUM)

### WR-01: When the AUM is zero or negative and a ticket is set, the engine sizes the candidate at a fixed 0.10. The persisted score and `mandate_fit_raw.max_weight` are then computed from that made-up share, and they run opposite to the tiny-positive-AUM case.

**File:**
- `analytics-service/routers/match.py:1290` (`"portfolio_aum": combined_aum if combined_aum > 0 else None`);
- `services/match_engine.py:997-1007` (`add_weight = 0.10  # Default for cold-start or unknown AUM`), consumed at `:526-535` (mandate max_weight dimension) and `:718-721` (the proposed book);
- the WARNING text at `routers/match.py:1268-1274`.

**Issue:** Before D-16, `portfolio_aum` was None only for a book with no value: cold start, where a 0.10 default is a reasonable stand-in. Now it is None whenever derivative losses exceed the spot and strategy value, with a real book and a real `target_ticket_size_usd`. In that case `ticket / AUM` is undefined (the ticket exceeds the equity). Instead of naming that, the engine substitutes 0.10, and that number reaches persisted, user-facing outputs:

- `match_candidates.score`;
- `score_breakdown.mandate_fit_raw.max_weight`;
- `score_breakdown.raw.sharpe_lift` and `dd_improvement`, which are modelled at a 10% ticket.

The result also runs opposite to D-21's tiny-positive case. Measured on the real `score_candidates` with max_weight 0.1 and a ticket of 50,000:

| matcher AUM | add_weight | mandate_fit_raw.max_weight | score |
|---|---|---|---|
| +$100 (D-21, accepted) | 0.5 (clamp) | 0.0 | 45.23 |
| <= 0 (passed as None) | 0.10 (default) | 1.0 | 47.63 |

A book whose equity has just gone negative scores better on the mandate's max-weight dimension than one with $100 of equity left, so moving from +$1 to -$1 of AUM flips the dimension from fully penalised to fully satisfied. Nothing in the batch records that the sizing fell back. The `aum_not_positive` WARNING says "scoring weights are unaffected". That is true, but it leaves out that the ticket sizing is affected. The fixer's report calls this "known, pre-existing and untouched". The fallback itself predates the phase, but D-16 is what makes this path reachable with real money. `test_match_scoring_weights.py:104-107` passes `portfolio_aum=None` on purpose, so no test covers it.

**Fix:** This needs a founder ruling, because D-21 covers the max-weight denominator and not the ticket sizing. Book it as Q-C, with these options:

- **(a) Recommended, monotone with D-21.** With a positive ticket and an AUM <= 0, size at the engine's ceiling. A ticket larger than the equity is the limit of `ticket / AUM` as AUM goes to 0 from above, so this gives the same 0.5 clamp the tiny-positive path already uses. Pass the AUM sign through, for example `portfolio_aum` as a signed float with the engine branching on `<= 0`. Do not use None, which means "unknown".
- **(b) Never invent.** Leave the max_weight mandate dimension out and mark it unavailable, as the AUM share already is.

Whichever is chosen:

- record it on the batch, for example a `ticket_sizing: "aum_not_positive"` field on the D-22 book entry or in `effective_thresholds`;
- correct the WARNING so it names the sizing fallback;
- add a test: spot 1,000, perp P&L -1,500, `target_ticket_size_usd` 50,000, `max_weight` 0.1, asserting the chosen behaviour on `score_breakdown.mandate_fit_raw.max_weight`.
