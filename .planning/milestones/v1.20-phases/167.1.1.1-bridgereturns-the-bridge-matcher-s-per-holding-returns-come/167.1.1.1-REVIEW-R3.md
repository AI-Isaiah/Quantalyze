## Critical Issues (HIGH)

### CR-01: When no series joins the book, the D-23 entry records 0.5 sizing on the batch, but the engine sized the candidate at 0.10

**Classification:** data-integrity (a false fact persisted in `match_batches.holding_flags`) and user-facing (`match_candidates.score` and `score_breakdown.raw.mandate_fit_raw.max_weight` use the sizing D-23 forbids). The code diverges from D-23.

**File:**
- `analytics-service/routers/match.py:1340-1342`: `aum_not_positive` is true for any book that has holding rows, priced or not.
- `analytics-service/routers/match.py:1680-1700` (`add_weight_fallback_entry`) and `:1806-1813`: the sentinel AUM is chosen and the entry is built before scoring, and neither checks the engine's mode.
- `analytics-service/routers/match.py:1876`: the entry is appended whatever mode the engine ran in.
- `analytics-service/services/match_engine.py:885`: `mode = "personalized" if portfolio_strategies else "screening"`.
- `analytics-service/services/match_engine.py:997-1007`: the ticket / AUM sizing applies only when `mode == "personalized"`. Otherwise `add_weight = 0.10`.
- `analytics-service/services/match_engine.py:1135-1137`: that 0.10 still feeds `_compute_mandate_fit_score` in screening mode.
- The WARNING at `routers/match.py:1350-1356` also says, without condition, "a ticket is sized at the 0.5 add-weight ceiling".

**Issue:** `ctx["portfolio_strategies"]` holds only the book's strategies and its **priced** spot holdings. Withheld spot (stablecoins as `fixed_price`, `account_balance`, `no_price`, `too_few_priced_days`, `too_few_adjacent_returns`) and every derivative stay out of it (D-01, D-09, D-19). A book with no strategy and no priced spot holding therefore runs in **screening** mode. Its AUM can still be <= 0. For example: a stablecoin balance plus perp losses larger than that balance, or a thin BTC series plus perp losses. Stablecoins are the dominant spot class on PROD (CONTEXT, D-01 evidence), so this shape is realistic. For such a book:

- the engine ignores `portfolio_aum` and sizes `add_weight` at the fixed 0.10. D-23 says that must never happen.
- `_score_one_allocator` still appends `{"kind":"book","holding_ref":null,"add_weight_fallback":"aum_not_positive_ceiling_0_5","add_weight":0.5,"flagged":false}`, so the batch records a sizing that did not take place.
- the WARNING says the same false thing.

This is the false-cause class the phase exists to remove, introduced by the round-2 fix itself. The D-23 test (`tests/test_match_aum_not_positive_sizing.py`) uses only a book with a priced BTC holding of 119 returns (`_book`), which is personalized mode, so it cannot see this.

**Evidence (measured at HEAD, scratch test outside the repo, real `_load_allocator_context`, `_score_one_allocator` and `score_candidates`):** the book is BTC 1,000 with only 10 adjacent marked days (so it is withheld as too thin) plus a perp with P&L -1,500. The fixtures are the phase's own (`_rows`, `_perp_row`, `_db`, `_universe`), and the preferences are `max_weight` 0.1 and ticket 50,000.

```
ctx["portfolio_strategies"] == []        ctx["aum_not_positive"] is True
batch["mode"] == "screening"
book entry: {'kind': 'book', 'holding_ref': None, 'add_weight_fallback': 'aum_not_positive_ceiling_0_5', 'add_weight': 0.5, 'flagged': False}
candidate: score 80.75, mandate_fit_raw.max_weight == 1.0   # add_weight 0.10 <= 0.1, so the max-weight dimension is fully satisfied
```

At the 0.5 sizing the entry claims, `mandate_fit_raw.max_weight` would be 0.0, as in the personalized-mode test. So the persisted row contradicts the persisted score.

**Fix:** Decide the substitution and the record from the mode the engine actually runs in, and pin both modes.

1. Make the record honest. Build the entry from `result["mode"]` after `score_candidates` returns, and append it only when `result["mode"] == "personalized"`. The sentinel then actually set `add_weight` to 0.5 only in that mode. For example:
   ```python
   if add_weight_fallback is not None and result["mode"] != "personalized":
       add_weight_fallback = None  # the engine sized at its screening default; nothing was substituted
   ```
   Move the WARNING inside `add_weight_fallback_entry`, or condition it the same way, and remove the unconditional "a ticket is sized at the 0.5 ceiling" clause from the `aum_not_positive` WARNING at `routers/match.py:1350-1356`.
2. D-23 says the candidate is "never sized at the engine's fixed 0.10 default". In screening mode the router cannot honour that without an engine change (an explicit `add_weight` override, or letting a non-None `portfolio_aum` drive sizing in screening mode). Taking the honest-record half of step 1 alone leaves the code diverging from D-23 for these books. Route that choice to the founder, as Q-D, rather than settling it silently. Option (a): extend the ceiling to screening mode through the engine. Option (b): accept 0.10 in screening mode and record it by name, for example `add_weight_fallback: "aum_not_positive_screening_default_0_10"`.
3. Add a test beside `test_match_aum_not_positive_sizing.py` for a book with no priced spot holding and no strategy (stablecoin or thin series, plus perp losses, AUM <= 0). Assert that the persisted entry's `add_weight` equals the add-weight the score was computed with (0.5 gives `mandate_fit_raw.max_weight` 0.0, 0.10 gives 1.0 at `max_weight` 0.1). Neuter the mode check and confirm the test goes RED.

## Considered, not reported (below MEDIUM or not a defect)

- **Index guard against stored data.** `records_to_series` does not normalise tz itself. All stored series dates are written as `YYYY-MM-DD` (`services/metrics.py:2135-2140`), and the USD converter rebuilds a naive index. No healthy production series is tz-aware, so the guard does not turn a working book into a failure.
- **Strategy-only books with unknown AUM** keep the 0.10 default. Their AUM is unknown, not non-positive, so D-23 does not reach them, and the fixer's scope note already records this.
- **NaN AUM.** A non-finite `combined_aum` would fail both `<= 0` and `> 0`, so it would reach the engine as None with no entry. That needs a `numeric` NaN in `value_usd` or `allocated_amount`, which no writer produces. LOW.
