## Case table: each persisted entry checked against the engine's sizing

The engine's sizing (`match_engine.py`, the `add_weight` block) works like this. In personalized
mode with an AUM above zero and a ticket above zero, `add_weight = clamp(ticket / aum, 0.01, 0.5)`.
Every other case gets `add_weight = 0.10`. Mode is `"personalized"` exactly when
`portfolio_strategies` is non-empty. The engine reads the ticket through `merge_with_defaults`,
which is the same function `_engine_ticket_is_positive` calls.

Things I checked:

- **Same ticket reading on both sides.** The substitution and the entry both decide through
  `_engine_ticket_is_positive`. Neither the engine nor the router mutates `ctx["preferences"]`
  between the two calls: the engine copies via `merge_with_defaults`, and relaxation builds
  `active_prefs` as a separate dict. A ticket that is a bool, NaN or missing resolves the same way
  in both places.
- **The engine's early return** when nothing is eligible still carries `mode` and
  `candidates: []`, so the candidates gate covers it.
- **D-24 reachability.** `aum_not_positive` is true whenever the book has any holdings row and
  the combined AUM is <= 0. So `portfolio_aum is None and not aum_not_positive` in personalized
  mode can only be a strategies-only book whose positive allocated amounts sum to zero. The
  allocation API (`portfolio-strategies/allocation/route.ts`) rejects a non-positive amount,
  which makes the WARNING text "no allocated amount on any strategy" accurate.
- **WARNINGs fire only with their entry.** Every WARNING sits in `add_weight_fallback_entry`,
  just before the `return` of the entry it names. The format string has three `%s` for three
  arguments, and the detail strings contain no stray `%`. The context-time `aum_not_positive`
  WARNING no longer claims a sizing.
- **The `holding_flags` reader** (`src/lib/queries.ts`, `rawFlags.filter(f => f.flagged &&
  f.top_candidate_strategy_id)`) drops all three book entries (`flagged: false`, no candidate).
  The new D-24 entries on strategies-only batches cannot reach the UI.
- **Tests run:** `tests/test_match_aum_not_positive_sizing.py` 14 passed. `pytest -k match`
  over `tests/`: 948 passed, 6 skipped. Both ran from `analytics-service/` with its `.venv`. The
  fixer's neuter table in REVIEW-FIX-R3 covers the mode gate, the candidates gate, each entry and
  the D-24 substitution, and each neuter went RED.

## Below threshold (LOW, recorded, not booked, no fix requested)

- The oracle cannot tell 0.10 from a smaller default. With `max_weight` 0.1, `_sized_score`
  returns 1.0 for any `add_weight` <= 0.1. The D-24/D-25 score-agreement assertions therefore
  prove "at or under the cap", not "0.10". If the engine's literal default drifted below 0.10,
  `_ADD_WEIGHT_DEFAULT` would go stale without going RED. The exact-shape entry assertions still
  pin the entry itself. A `max_weight` such as 0.08 (0.10 gives 0.75) would make the check exact.
- Stale comments. The comment above `_ADD_WEIGHT_CEILING` (`routers/match.py`, D-23 block) and
  the one on the context's `aum_not_positive` key still describe ceiling sizing without the D-25
  "personalized only" qualifier.
- The D-23 entry claims 0.5. That only holds for tickets at or above 5e-7 USD, since a smaller
  ticket divided by 1e-6 clamps below 0.5. No real preference is that small.
