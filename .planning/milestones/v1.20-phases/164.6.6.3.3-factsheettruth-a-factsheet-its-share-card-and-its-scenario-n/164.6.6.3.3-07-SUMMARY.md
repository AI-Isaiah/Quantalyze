## Deviations from Plan

**1. [Rule 3 - Blocking] WARNING, not ERROR, in the two terminal-stamp closures.** The plan and its must_have say "log record at ERROR". My first implementation logged ERROR once the stamp landed. The full suite then showed 9 RED cases in `tests/test_stamp_io_exhaustive.py` (a file outside this plan's `files_modified`): it pins `log.error.call_count == 0` on a clean landed stamp and "exactly one ERROR line" per failing-I/O case, the 164.6.7 round 3/4 decision recorded in the closure's own comment ("The CAUSE is logged at ERROR exactly where it is at risk, and nowhere else"). Two conventions conflicted (Rule 7). I kept the earlier, tested one: ERROR stays reserved for a stamp that needs a person, and the missing record is added at WARNING, the closure's own level for the cause when a detail is given. The owner sentence needs a findable log record, and it now has one. **For the orchestrator/founder:** if ERROR is wanted on every terminal stamp, that is a policy change to the 164.6.7 contract and `test_stamp_io_exhaustive.py`'s expected counts must move with it; it was not done here. Commits 2ccd4a3bd (first, ERROR) then 61297c071 (corrected).

**2. [Process] Pre-commit allow-list.** The `agent-*` branch-namespace assertion was not applied because the orchestrator designated branch `wt/164.6.6.3.3-p07`. The protected-default-branch check passes.

No other deviation. Plan 01's D-13 code in `run_stitch_composite_job` is untouched (the only `job_worker.py` hunks are the two logging `else:` branches inside the stamp closures). No status value, bridge rule or `computation_error_source` semantics changed. New messages reuse the path's own scrubbed text and a row count; no secret, account number or row payload was added.
