# Phase 164.9.8: APTHANG - Context

**Gathered:** 2026-10-07
**Status:** Ready for research and planning
**Source:** founder AskUserQuestion 2026-10-07 ("Book a CI phase, ship first") plus orchestrator measurement

## Phase Boundary

Every apt invocation in `.github/workflows/` fails over or fails fast when a package mirror stalls, instead
of blocking the job until its job-level timeout. In scope: the apt calls, their step time limits, and skipping
installs the runner image already satisfies. Out of scope: anything else in the jobs these steps sit in.

## Implementation Decisions

- **D-01 (founder 2026-10-07):** Fix it properly now, as its own phase, and ship it FIRST in the merge queue,
  ahead of the Wave 1 phases. Re-running failed jobs is the stopgap only.
- **D-02:** Short network timeouts and retries on every apt call (e.g. `Acquire::http::Timeout`,
  `Acquire::https::Timeout`, `Acquire::Retries`), defined once and reused, not 31 hand-copied option strings
  if the workflow structure allows a shared form. A guard test fails when a new apt call lacks them.
- **D-03:** Every install step gets its own `timeout-minutes`, so a hang ends the step with a named failure.
- **D-04:** Measure on a real runner whether the image already ships the tool (psql first, and whatever
  "Provision pg_cron" installs). Skip the install only where the measurement proves it present and at a version
  the step's consumer accepts; record the measurement.
- **D-05:** Never raise `sql-mutation`'s 20-minute ceiling (CLAUDE.md). Keep the `sql-mutation` ↔
  `sql-mutation-nightly` copied-step byte parity (`src/__tests__/sql-mutation-nightly-parity.test.ts`) green by
  copying any changed `run:` block; note the parity test does not compare `with:`/`env:`, so copy those by hand.
- **D-06:** Never write a skip-CI token anywhere, and never re-trigger main via `workflow_dispatch` as proof
  (CLAUDE.md "CI gate integrity").

- **D-02 CORRECTED 2026-10-07 (orchestrator, after research; intent unchanged):** the runner image already sets `Acquire::Retries 1` and 15 s http/https timeouts (`/etc/apt/apt.conf.d/zz-retries`), and every failing log shows the azure fail-over working (~30 s); the hangs are a post-fallback trickle that apt's inactivity timers never end. So the shared form is a wrapper script (`scripts/ci-apt.sh`) that keeps the explicit Acquire options AND bounds each network phase by wall clock (`timeout` on `update` and `install --download-only`, bounded retries, forensics on failure), skips an install whose tool is already on PATH (D-04), and is called from inside the existing `run:` blocks (no new step, no local composite action: both break the sql-mutation parity and scope-step pins). The guard test (D-02) enforces the wrapper, not bare `-o` flags. Original D-02 kept as lineage above.

- **DEVIATIONS from D-03, recorded 2026-10-07 (planner revision, after the plan check; CLAUDE.md deviation policy, mirrored in the ROADMAP 164.9.8 block):**
  1. **The two `Acquire shared-test-db mutex` steps carry NO step `timeout-minutes`.** They are apt-reaching only through a dead branch (`if ! command -v psql`). The step itself waits for the shared-TEST advisory lock by design, measured at up to 1977 s (about 33 min). A short step limit would kill a legitimate lock wait. Their apt is bounded by the wrapper's own 400 s budget. The guard test names this as its single exemption.
  2. **Playwright's internal apt (`playwright install --with-deps`) is bounded only by the runner image defaults plus a 10-minute step cap.** The wrapper cannot reach inside Playwright. Basis: 6 cache-miss installs in 600 ci.yml runs, slowest 308 s (a 32.1 MB apt fetch trickling at 112 kB/s). The nightly demo-pdf step has never run: 181/181 runs skipped it because the canary is disabled. Accepted risk: a trickle below about 55 kB/s on that set ends the step by name at 10 minutes.
- **Measured caps (planner revision 2026-10-07, refines the D-02 correction; intent unchanged):** per-phase wall-clock caps are update 150 s and fetch 120 s, inside one total retry budget (400 s by default, 360 s for pg_cron). Both caps are above the slowest measured successful phase: 37.7 s update, 69.2 s fetch with azure failover, about 115 s computed for an index trickle at the slowest working throughput. Step limits are derived from the budget: 8 for psql, 7 for pg_cron (sql-mutation worst case 1075 s of 1200 s), 10 for Playwright. Basis: RESEARCH "Planning addendum".
