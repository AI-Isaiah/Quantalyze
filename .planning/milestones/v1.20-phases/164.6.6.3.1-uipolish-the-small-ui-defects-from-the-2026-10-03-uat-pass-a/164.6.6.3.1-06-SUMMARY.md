## Two observations (recorded, not booked)

1. **A background tab defers the read entirely.** In the first, uncontrolled attempts the tab was a background tab (`document.visibilityState: hidden`). The page's client code, key reads included, did not start until the tab was brought to the foreground: the first fetch ran at 18.5 s, exactly when a screenshot activated the tab. The reads then took 375 ms (REST) and 644 ms (permissions). One earlier attempt was also stalled by the orchestrator's own blocking script and is discarded. A user who opens the edit page in a background tab (cmd-click) and switches to it later would see "Loading..." or the empty state until they look. That is a plausible explanation for the UAT's "~20 s", but it is INFERRED, not reproduced as the founder experienced it.
2. **The empty-state flash is live on PROD.** On every cold load the first frame showed "No API keys connected. Add a read-only exchange key..." before the keys arrived, about 1 s later. PROD does not yet carry this phase's plan 02 (the key card's loading state), which removes that flash. So this corroborates plan 02's target on the live site; plan 02's fix is not yet deployed.
