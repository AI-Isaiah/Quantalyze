## Summary

The D-17 code does what CONTEXT D-17 asks. The strip cannot change a digit or merge two real bills, and the
shape cannot carry a character of the id into `last_error`, the log or `info.bal_chain`. The tests can fail
on every behaviour the brief names. I re-ran the seven OKX test files on a scratch extract of `489379b92`
(code, `docs/` and `scripts/` from `git archive`, never the worktree) and got `747 passed`, which matches
the SUMMARY.

**Answers to the brief's focus questions:**

- **Can the strip alter digits? No.** `_strip_bill_id` (`okx_archive_files.py:257-265`) loops over
  `str.strip()` then `str.strip("'\"")` until the value stops changing. Both calls remove characters from
  the two ends only. `str.strip()` removes only characters where `isspace()` is true, and no ASCII digit is
  whitespace. The loop ends because each pass either shrinks the string or returns it. An inner separator
  is kept, so an id with an inner space stays non-digit and stops (`test_the_inside_of_a_bill_id_is_never_touched`,
  neuter N7).
- **Can the strip merge two distinct bills? Not two real ones.** Two raw ids map to one stripped id only
  when they differ by edge whitespace or quotes alone. An OKX billId is an integer, so two different bills
  never differ that way. When the same bill appears twice with different wraps, the strip treats it the
  right way. Identical content is dropped as one duplicate. Different content still stops
  `duplicate_bill_conflict` (`test_the_same_bill_wrapped_two_ways_in_one_file_is_one_bill`,
  `test_a_wrapped_bill_id_with_different_content_is_still_a_conflict`). If an exporter had first lost
  precision through a float, distinct ids could collide after the strip. That case fails closed: the
  conflict check stops on different content, and the chain breaks on the lost ordering.
- **Dedup and conflict are consistent across every reader.** The strip runs once, at `:297`, before the
  `ts` check, the missing check, the within-file de-duplication and every downstream reader.
  `tuple(row.values())` (`:301`) keeps header order, since `_check_header` rules out a duplicate column
  name, and holds the stripped id. The within-file tuple, `aggregate_archive`'s cross-file `unique`,
  `verify_bal_chain`'s `seen` and run `unique`, `_stop_census`, `_bill_order_key` and `_balance_vs_nav` all
  key on the same stripped `ArchiveRow.bill_id`. Nothing else in the job reads a billId (grep of
  `bill_id`/`billId` in `okx_archive_job.py`). No bill id is persisted, and the fingerprint does not depend
  on the wrap. `TestBillIdExportWrap` pins `fingerprint`, `census`, `reconcile`, `excluded`, `d03`,
  `strategies`, `info` and every per-quarter reading to be equal to the bare file's, for four wraps and for
  a wrapped Q2+Q3 pair.
- **Value safety holds.** The shape alphabet is closed. `_bill_id_shape` (`okx_archive_classify.py:166-189`)
  maps characters to `9`, `A`, `TAB`/`SP`/`DQ`/`SQ` or `unicodedata.category`. I ran a probe over every code
  point except surrogates (`chr(cp) + "1"`) and **0 of 1,112,064 shapes fall outside `NONDIGIT_SHAPE_RE`**,
  so no character makes a shape the job then withholds as `unreadable`. A cell of 131,072 identical letters,
  the csv field limit, still matches the `{n}` bound. No module in `analytics-service` raises
  `csv.field_size_limit`. If one ever does, a longer run fails the grammar and reads `unreadable`, which is
  the safe direction. Two gates check the value before it is echoed: the job checks the shape with
  `fullmatch` (`_shape_or_unreadable`, `okx_archive_job.py:1319-1325`), and the length with `_count_token`
  in both `last_error` and `info`. Neither check can raise. `scrub_freeform_string` returns the full stop
  text byte-equal (probed), so the log line matches `last_error`. `ArchiveParseError.__str__` contains the
  detail, but every detail value is a shape, a count or a day. The e2e test's forbidden list (`1.23E+17`,
  `1.23`, `E+17`, every `LINK_SECRETS` entry) is checked over `error_message`, the result JSON and the
  captured log in both modes.
- **Grammar and regex.** `_SHAPE_RUN` lists all 30 Unicode general categories plus the six fixed symbols.
  The count group `\{(?:[2-9]|[1-9][0-9]{1,5})\}` accepts exactly 2..999999 and refuses `{1}`, `{0}` and a
  leading zero. `{0,7}` more runs plus an optional `-MORE` matches `_SHAPE_MAX_RUNS = 8`. The alternation
  branches are prefix-distinct and the repeat is bounded, so the regex cannot backtrack catastrophically. A
  `match`-for-`fullmatch` slip in the job would turn red on the `two-letters` and `not-a-category` poison
  cases.
- **First-offender ordering is correct.** `first_shape` / `first_len` are set once, on the first row where
  `row_nondigit` holds. That row is found in the order `files` is passed (`_ingest_all` builds `files` and
  `tags` from `quarters[]` in input order, `okx_archive_job.py:1495-1500`), then file row order, skipping
  a bill already seen in an earlier file. A blank-ccy bill that stops first does not take the slot
  (`test_the_stop_names_the_first_non_digit_id_in_row_order` puts one first). Reversing the file order
  names the other id (`test_the_first_non_digit_id_is_taken_in_the_order_the_files_are_passed`). The shape
  is taken after the strip (`test_the_shape_is_taken_after_the_strip`).
- **Can the tests fail? Yes.** The N1–N19 table in the SUMMARY covers the strip (none, whitespace only,
  quotes only, single pass, wrap-only kept, raw dedup tuple, inside stripped), the shape (echo, no merge,
  no cap, last instead of first), and every job-side gate. I looked for mutants outside that list.
  "Shape of the first STOPPING row, whatever its cause" is caught: the row-order test's first stopping row
  is a blank-ccy bill with an all-digit id. "Strip on one side only" is caught by `space-padded` and `double-quote`. "Run the
  `seen` skip after the tally" is equivalent, because the earlier file already took the slot. I found no
  surviving mutant that changes a reading the founder acts on.
- **Runbook: accurate.** The token order (`first_day`, `last_day`, `first_nondigit_shape`,
  `first_nondigit_len`, `rows_by_quarter`) matches `_unchainable_tokens`. A wrap-only id does map to
  `duplicate_bill_conflict` with `parse=missing_bill_id` (`_PARSE_STOP_CLASS`). `quarters[]` order then
  row order matches the code. The category examples are correct for Python 3.12 (`.` Po, `+`/`=` Sm, `-`
  Pd, U+00A0 Zs), and so is the worked example `9-Po-9{2}-A-Sm-9{2}` for scientific notation. `none`
  versus `unreadable` matches the code.

## Below the threshold (not findings, recorded so they are not re-derived)

1. **A wrapped billId over 4,300 ASCII digits now reaches `int()` and raises a bare `ValueError`.** This is
   in `_bill_order_key` (`okx_archive_classify.py:192-194`) and `_balance_vs_nav`
   (`okx_archive_job.py:2019`). Probed on the scratch extract: `"'" + "1" * 5000` through
   `parse_archive_csv` and `verify_bal_chain` raises `Exceeds the limit (4300 digits) for integer string
   conversion: value has 5000 digits`, with no `stop_class`. Before D-17 that wrapped id stopped cleanly as
   `nondigit_bill_id`. The same crash already existed at `0f94c4bf3` for an UNWRAPPED 5,000-digit id, so
   D-17 widens a pre-existing path, the same pattern as P20 WR-02. The message carries a digit count, not
   the id. Real OKX ids are about 18 digits, and the file comes from the allow-listed archive host. A
   minimal fix, if it is ever wanted: compare digit ids without `int()`, as
   `(not digits, len(bill_id), bill_id)` after `lstrip("0")`. Another option is to stop a billId longer
   than a small cap such as 32 as non-digit.
2. **The module contract lines still say `last_error` holds "dates and counts only".** See
   `okx_archive_job.py:43` and `:296`, and the runbook at `:56`. `last_error` now also carries the
   closed-grammar shape, and before this plan it already carried the `parse=`/`cause=` labels. The
   runbook at `:492` already says "closed-vocabulary classes". This is wording drift only. The gates are
   the code, not this sentence.
3. **The strip is broader than CONTEXT D-17's wording.** `str.strip()` also removes U+00A0, U+3000,
   U+2000–U+200A, U+0085 and the C0 separators U+001C–U+001F. That cannot change a digit or the inside of
   an id. It does mean the runbook's `Zs` example can only come from an INTERIOR no-break space.
4. **A cell that alternates whitespace and quotes takes about n/4 passes of `_strip_bill_id`.** Each pass
   copies the string, so the cost is quadratic up to the 131,072-character field limit. That is
   performance and out of v1 scope. A single `re.sub(r"^[\s'\"]+|[\s'\"]+$", "", raw)` would remove it.
