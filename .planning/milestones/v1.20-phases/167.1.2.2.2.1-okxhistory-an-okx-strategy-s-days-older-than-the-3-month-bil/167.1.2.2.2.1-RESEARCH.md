## Summary

The work list on PROD, re-measured read-only today (marker named PRODUCTION): four non-archived OKX strategies; ordinals 1, 2, 4 share one venue account, ordinal 3 is on a disconnected key. Ordinal 1 (pending_review) names a 70-day gap 2026-05-24..08-01, ordinal 2 (published) an 87-day gap 2026-05-07..08-01. Both carry `headline_since` = 2026-08-02 and `insufficient_window`, i.e. their headline today is a suffix after the gap. Ordinal 2's carried legacy rows are dense (73 rows for 73 days); ordinal 1's are sparse (26 rows over 90 days), so after the rebuild ordinal 1's headline will start at the last interior break inside its legacy region, about 2026-05-24, not 2026-02-23, while ordinal 2's can reach back to 2026-02-23. That is a published-number change and belongs in front of the founder before apply.

The design that fits this repo with the least new surface: **one new api_key-scoped `compute_jobs` kind whose handler is stateless against OKX's own request state** (the venue stores the apply time `ts` and the `finished/ongoing/failed` state; the handler re-derives its step on every claim and never stores a download link), waiting with `defer_compute_job` (hard cap 3600 s per defer, attempts are not consumed). The handler runs in three operator-selected modes: `preflight` (account config and bill-type census only), `calibrate` (full read-only: apply, wait, ingest, reconcile, report, write nothing) and `apply` (re-ingest, re-reconcile, then one atomic database write). The rebuilt days are computed by running the SAME `combine_realized_and_funding` core over live data plus archive days prepended, so live-day returns are unchanged by construction (asserted), and they are persisted as ordinary `csv_daily_returns` rows strictly older than the live derive's span start, where the derive's write path provably does not reach (`job_worker.py:7382-7383`, delete bounded at `:7412`). Atomicity of rows plus provenance needs one small SQL function; that is the only part with a real surface cost (Section 8).

Three findings change the plan's shape. (1) The archive CSV, per OKX's current docs, carries `subType` and no `type` column, while the live aggregator keys funding on `type == "8"`; classification must go through `subType` and `GET /account/subtypes`, and the documentation no longer lists the types at all (it points at that endpoint). (2) The live aggregator only fetches `instType` in SWAP, FUTURES, SPOT, MARGIN; OKX's bills endpoints also accept OPTION and EVENTS, and the archive file contains every row, so "to the cent" reconciliation must filter the archive identically and report the excluded classes separately. (3) ccxt's rate table prices the apply POST at cost 72000; measured here, the first POST is free but the next call on the same exchange instance blocks about 7,920 s, so the apply must be the last call on its instance.

**Primary recommendation:** build `okx_archive_rebuild` as an api_key-scoped, stateless, three-mode job; pin the reconciliation tolerance as a constant of 0.01 with no parameter; calibrate on the real Q3 overlap (it expires around 2026-12-30 as the live 90-day reach slides) before any write; and make the PROD write one RPC that inserts rows with DO NOTHING, narrows `unrecovered_gaps`, appends `reconstructed_ranges`, and refuses outside a recorded gap.

### Pattern 1: A stateless handler against the venue's own state machine
**What:** On every claim the handler derives its step from OKX (`result`/`state`/`ts`), never from process memory or a stored link. Waiting is `defer_compute_job`, which returns the row to `pending`, sets `next_attempt_at`, decrements `attempts` (so waiting never burns a retry) and is claim-token fenced.
**When to use:** any wait longer than the handler timeout.
**Example:** `DispatchOutcome.DEFERRED` means "the handler already called `defer_compute_job`; `main_worker` must not call `mark_*`" [VERIFIED: `job_worker.py:629-636`, quote: `DEFERRED = "deferred"`]. The existing deferral call shape is in `_check_circuit_breaker` (`job_worker.py` around `supabase.rpc("defer_compute_job", {"p_job_id": ..., "p_defer_seconds": ..., "p_reason": ..., "p_claim_token": job.get("claim_token")})`).
⛔ `defer_compute_job` rejects more than one hour: [VERIFIED: `supabase/migrations/20261001120000_compute_job_fence_errcode_55006.sql:150`, quote: `IF p_defer_seconds > 3600 THEN`]. A 2 h wait is therefore at least two defers; the give-up bound must come from OKX's `ts` (first request time), not from a counter the defer RPC does not keep.

### Pattern 2: Derive the rebuilt days with the live core, then slice
**What:** Build the same inputs the derive builds, prepend archive-derived daily records for days strictly before the live span start, call `combine_realized_and_funding` once, and keep only covered-and-in-gap days. The NAV roll is backward from the terminal anchor (`nav[t - 1] = nav[t] - pnl[t] - flows[t]`, [VERIFIED: `nav_twr.py:457`]), so prepending earlier days cannot change any later day's NAV, and therefore cannot change a live day's return. Assert it.
**Why not a separate formula:** D-07 says the method is identical; a second implementation is the divergence the founder ruled out.

### Pattern 3: Covered-quiet is not uncovered
A day inside a verified quarter file with no bill is genuinely flat (the live path also zero-fills quiet days via `gap_fill_daily_returns`, [VERIFIED: `broker_dailies.py:321`, quote: `returns = gap_fill_daily_returns(returns)`]). A day in a quarter that was NOT ingested is unknown and stays absent. The code must inject an explicit zero-P&L record for each covered quiet day, because `combine_*` only indexes days that have a record or a flow, and the gap fill only spans first-to-last record.

### Anti-Patterns to Avoid
- **Storing `fileHref`:** expires after 5.5 h per OKX; the lost-link bug.
- **Classifying by description substring:** subType 110/111 are "Liquidation transfer in/out" [CITED: okx.com/docs-v5/en, bills `px` table]; the word "transfer" does not make them external capital flows.
- **Summing the archive without the live instType filter:** reconciles to nothing the live path ever produced (Section 4).
- **One strategy-scoped job for the wait:** flips a published strategy to `computing` for hours.
- **Enqueueing a second job of the same kind from inside the first:** blocked by `compute_jobs_one_inflight_per_kind_api_key` ([VERIFIED: `baseline.sql:14372`, quote: `CREATE UNIQUE INDEX "compute_jobs_one_inflight_per_kind_api_key" ... ("api_key_id", "kind") WHERE (("api_key_id" IS NOT NULL) AND ("status" = ANY (ARRAY['pending'::"text", 'running'::"text", 'done_pending_children'::"text"])))`]). One job carries all requested quarters.
- **Widening the tolerance, adding an env override, or a function parameter for it:** D-10 forbids it; pin a constant and test that no parameter exists.

## Findings by research question

### 1. Currency (founder instruction): what is measured, what is not, how to handle it

- **The defect is real in code.** [VERIFIED: `analytics-service/services/exchange.py:1614`, quote: `pnl_val = _pnl_raw + _fee_raw`] and the surrounding loop never reads `ccy`; the daily record's currency label is a hard-coded constant [VERIFIED: `exchange.py:1647`, quote: `"fee_currency": "USDT",`]. Funding is also ccy-blind: amount is the bill's `pnl` [VERIFIED: `funding_fetch.py:565`, quote: `amount_raw=item.get("pnl"),`] and `currency=item.get("ccy", "USDT")` is stored but never used by `funding_rows_to_daily_pnl_records`.
- **Stored-data reading (PROD, read-only, 2026-10-15, counts only).** Across the three in-scope strategies: the OKX-format raw fills (instType present) number 406, all `SWAP`, all `feeCcy` USDT; the OKX type-8 funding rows number 568, all `ccy` USDT, all `SWAP` instruments; every stored `fee_currency` is USDT (but that column is written from a constant, so it proves nothing). Ordinal 4 additionally holds thousands of rows in a non-OKX symbol format (`XXXUSDT`, no `instType`, funding `type` SETTLEMENT); those are not OKX bills and are not evidence about the OKX ledger. **Conclusion: every OKX-format row stored is SWAP / USDT. That covers fills and funding only. It says nothing about SPOT, MARGIN, FUTURES or OPTION bills, transfers, interest or rebates, none of which is stored anywhere.** Whether the in-scope account's archive rows are all USDT is therefore **UNMEASURED**; the measure is the preflight/calibrate census (Section 12).
- **Docs raise two concrete risks** [CITED: okx.com/docs-v5/en, Get account configuration]: `feeType` "0: fee is charged in the currency you receive from the trade" (a spot buy pays its fee in the base coin) and `settleCcy` / `settleCcyList` (USD-margined contracts can settle in `USD`, `USDC`, `USDG`). `USDG` is in neither `USD_FAMILY` (`external_flows.py:42`, quote: `USD_FAMILY: frozenset[str] = frozenset({"USD", "USDC", "USDT", "EURR", "DAI"})`) nor `STABLECOINS` (`closed_sets.py:237-239`, quote: `{"USDT", "USDC", "DAI", "BUSD", "TUSD", "FDUSD", "USD"}`).
- **Required handling (a plan task, not a footnote):** the archive aggregator reads `ccy` on every row it counts. ### 2. How rebuilt days are produced and persisted (no clobber, no zero-fill, included in compute)

**What the live derive writes and where it stops.** The derive builds `returns` for its own dense span, upserts non-NaN days on `strategy_id,date` ([VERIFIED: `job_worker.py:7334`, quote: `_conflict = "strategy_id,date"`]), then deletes only calendar days inside that span that the payload did not carry ([VERIFIED: `job_worker.py:7382-7383`, quotes: `_span_start = returns.index.min().date().isoformat()` and `_span_end = returns.index.max().date().isoformat()`; delete bounded at `:7412`, quote: `.gte("date", span_start)`]). The block comment states rows older than `index.min()` "are never named by the delete -> PRESERVED". The span's start is the first day of the union of realized days, funding days and flow days; ordinals 1 and 2's first live row is 2026-08-02 [VERIFIED: PROD, `csv` min of the derived block, `trades` daily rows 2026-08-02].

**Therefore:** rebuilt rows dated before the live span start are untouched by every future derive. This is the same survival mechanism the D-08 carried legacy rows rely on (they were written directly into `csv_daily_returns` by the runbook, and the derive has not removed them: the three legacy ranges are still present today).

**Two live-reach facts to design around.**
1. The 3-month `bills-archive` reach slides forward daily (`should_fetch_archive = since_ms is None or since_ms < three_months_ago_ms`, [VERIFIED: `exchange.py:1508`]); the span start can only move later or be pulled earlier by a new flow/bill day. A deposit dated inside the quiet stretch inside the 90-day flow window would pull the span start earlier and the derive would then write 0.0 rows over rebuilt days in `[new start, 2026-08-01]` (the derive's days win, D-12). Harmless to correctness, but `reconstructed_ranges` would over-claim those days. Guard: the apply RPC records exactly the days it inserted; the readback form compares `reconstructed_ranges` to `csv` rows after the next derive; test T-CLOBBER-1 pins the derive-wins behaviour.
2. `apply_flow_coverage_terminus` NaNs returns before the DQ-02 floor when the window extends past the 90-day deposit retention with evidence (`nav_twr.py:1166-1196`). The rebuild job must NOT apply it to archive-backed days, because archive transfer bills supply flows back to 2021. Say so in code and test that the rebuilt range keeps its returns.

**Producing the days (recommended, Pattern 2).** Inputs per account: live `realized`, `funding`, `flows`, `equity`, `upl` fetched with the same functions the derive uses (`fetch_all_trades(since_ms=None)`, `fetch_funding_okx`, `fetch_ccxt_transfers` + `ccxt_rows_to_dated_flows`, `fetch_account_equity_and_upnl_usd`). Refuse (permanent) when `balance_error`, `equity is None` or dust: a heuristic base is not acceptable for a rebuild. Archive days = realized and funding records for days `< live_first_day`, plus one zero-P&L record per covered quiet day, plus archive flows for days below the live flow-coverage start. Call `combine_realized_and_funding(realized_union, funding_union, account_balance=equity, external_flows=flows_union, open_unrealized_usd=upl, full_history=False)`. Then assert (T-IDENT-1): for every day `>= live_first_day`, the union's return equals the live-only call's return (tolerance 1e-9; the live-only first day may legitimately differ if the live core guards its day 0, record rather than fail on that single day). Keep only `covered ∩ gap` days with finite returns; guard-NaN days stay absent, exactly as the live series treats them.

**NAV anchoring across the gap.** The roll is anchored on today's equity less the open-uPnL wedge and runs backward through live days, then through archive days; the NAV at the end of 2026-08-01 is whatever the live roll produces for that date. Rebuilt returns are frozen at the apply-time anchor, so they drift from the derive's later anchors by the same mechanism every reconstructed day does ("reconstruction error accrues into the distant past", `broker_dailies.py` docstring). Record that as an accepted limit in the runbook, not a surprise. An independent reading is available for free: the archive's `bal` (account balance after each bill, per ccy) at the end of 2026-08-01 vs the rolled NAV (realized basis). Report it in calibration; gate on it only if it matches in the Q3 overlap.

**What happens to the existing `unrecovered_gaps` entry (D-05).** A pure function `subtract_ranges(gaps, covered)` narrows each stored gap by the days actually inserted: full cover removes the entry, partial cover narrows it (possibly splitting in two). `covered` = verified quarter range ∩ gap, minus any day that already had a row at write time (D-12), minus days the core refused. The RPC applies the arithmetic result with a compare-and-set on the stored `unrecovered_gaps` value the job read. Example for SC-4: Q3 ingested, Q2 not -> only the 2026-07-01.. part inserted; the Q2 part stays in `unrecovered_gaps`, named, with no row and no 0.0 in it (T-GAP-1).

**Inclusion in compute (D-07).** `run_csv_strategy_analytics` loads all `csv_daily_returns` rows, dense-reindexes a broker-sourced series so in-span absent dates become NaN (`analytics_runner.py` around `dense_index = pd.date_range(...)`; `returns = returns.reindex(dense_index)`), and the segmenter takes the suffix after the last interior NaN. With rebuilt rows present the interior break closes and `headline_since` moves. Nothing in the Python service reads or writes `series_provenance` (grep over `analytics-service` finds none outside docs), so the runner cannot clobber the new key.

## Common Pitfalls

### Pitfall 1: the next call after the apply POST hangs for two hours
**What goes wrong:** ccxt's throttler charges 72000 tokens for the POST; the next call on that instance blocks about 7,920 s, past the handler timeout, and the job fails with a misleading timeout.
**Why:** `okx.py:606` rate-table cost.
**How to avoid:** apply last on its instance, or disable the limiter for that call and pace by hand; test with a fake exchange that records call order.
**Warning signs:** `asyncio.TimeoutError` right after a successful apply.

### Pitfall 2: reconciling against the wrong thing
**What goes wrong:** summing the whole archive (OPTION, EVENTS, blank-instType, funding, transfers) against `fetch_daily_pnl` produces cents-to-dollars of "difference" that is really classification.
**How to avoid:** the legs in Section 4 with the live filter; the excluded-class reading separate; funding as its own leg.

### Pitfall 3: classifying by `type` when the file has `subType`
**How to avoid:** subType-keyed table, the map from `/account/subtypes`, header pin, cross-check if `type` exists.

### Pitfall 4: a rebuild that zero-fills uncovered days
**What goes wrong:** union index spans first to last record, so a missing Q2 file turns into 0.0 returns for Q2 days.
**How to avoid:** explicit covered-quiet records only inside verified quarter ranges; test T-GAP-1 (Q3 only, gap spans Q2/Q3) asserts no row and no 0.0 in the Q2 part and that the named gap remains.

### Pitfall 5: attributing live-day changes to history
**What goes wrong:** prepending days must not alter live returns; a guard difference at the first live day can.
**How to avoid:** identity assertion T-IDENT-1 on every run, abort on any non-first-day difference.

### Pitfall 6: provenance and rows out of step
**How to avoid:** the atomic RPC; test that a containment violation rolls back the row insert (T-RPC-1).

### Pitfall 7: the strategy-scoped job flips a published strategy to `computing`
**How to avoid:** api_key scope; a test that the enqueue uses `p_api_key_id` and `p_strategy_id = NULL`.

### Pitfall 8: the first real file is the first time anything is learned
**How to avoid:** `preflight` and `calibrate` write nothing; the apply refuses without an approved fingerprint; every parse assertion is permanent-fail with a class name, never data.

### Pitfall 9: the Q3 overlap quietly disappearing
**What goes wrong:** after about 2026-12-30 the live reach no longer overlaps Q3, so calibration (D-10) cannot be taken at all.
**How to avoid:** schedule calibration before then; record the date in the runbook header.

### Pitfall 10: handler-side metadata writes
**What goes wrong:** a read-modify-write of `compute_jobs.metadata` races the claim RPC (documented residual). **How to avoid:** metadata is input only.

from decimal import Decimal
TOLERANCE_USD = Decimal("0.01")          # D-10: never a parameter, never configuration

def day_misses(archive: dict[str, Decimal], live: dict[str, Decimal]) -> list[tuple[str, Decimal, Decimal]]:
    return [(d, archive.get(d, Decimal(0)), live.get(d, Decimal(0)))
            for d in sorted(set(archive) | set(live))

## Security Domain

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (no new user auth) | — |
| V3 Session Management | no | — |
| V4 Access Control | yes | RPC `REVOKE ... FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role`; target strategies re-checked against the key's account; disconnected/revoked keys refused |
| V5 Input Validation | yes | Header pin, Decimal parsing, quarter-range assertion, closed classification table, `ExternalFlow` validation |
| V6 Cryptography | no new | KEK/DEK decrypt stays in `services.encryption`; never hand-roll |
| V7 Error Handling and Logging | yes | counts-only logs, `scrub_freeform_string`, no URL query or amounts in logs or `last_error` |
| V9 Communications | yes | https-only fetch, exact host allow-list, no auth headers on the download |
| V12 Files and Resources | yes | stream caps, no extraction to disk, single-member archive, no member-name paths |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SSRF via the `fileHref` of a third-party response | Tampering / Information disclosure | exact host allow-list, https, private-range refusal, redirects off or re-validated |
| Zip/gzip bomb | Denial of service | running byte and row caps, ratio cap, single member |
| Wrong-account file | Spoofing / Tampering | `uid` == `venue_account_id` for key and all targets |
| Poisoned or truncated file | Tampering | range assertion, `bal` continuity reading, live-overlap reconciliation, approved-fingerprint handshake at apply |
| Bearer URL leakage | Information disclosure | never log or persist the URL; log scheme+host only |
| Account-size leak in tracked text | Information disclosure | ordinals, counts and dates only; no amounts in RESEARCH/PLAN/SUMMARY/runbook output |
| Circuit-breaker abuse | Denial of service | no `_stamp_429` from this job |
| Replay / double apply | Tampering | DO NOTHING inserts, compare-and-set provenance, idempotent re-run |
