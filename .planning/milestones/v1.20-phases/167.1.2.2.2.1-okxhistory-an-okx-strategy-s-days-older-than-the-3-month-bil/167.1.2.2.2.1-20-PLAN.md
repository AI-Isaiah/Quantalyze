<objective>
Make the `unchainable_row` stop say what stopped it, and skip the blank-currency bills that cannot move a balance. When `verify_bal_chain` meets bills it cannot chain, the stop carries the cause split (`blank_ccy`, `nondigit_bill_id`), the count per quarter file and the first and last UTC day of those bills, in `last_error` and in `info.bal_chain`. A bill with a blank `ccy` and zero balance effect is left out of the chain and counted. Every other bill the chain cannot place still stops, now with those details.

Without the split, a re-run would be blind again.

**"Zero balance effect", settled from the code (HEAD `bb83337db`).** `parse_archive_csv` gives each `ArchiveRow` four money fields, `pnl`, `fee`, `bal_chg` (`balChg`) and `bal`, each an exact finite `Decimal` (a blank cell already stops `unparseable_amount`). `posBalChg` and `posBal` are header columns only and never reach the row. `verify_bal_chain` chains per ccy, in billId order, on `row.bal == prior.bal + row.bal_chg`. So `bal_chg` is the bill's effect on its currency's balance, and `bal` is the balance after it.
- The definition: `row.bal_chg == 0 and row.pnl == 0 and row.fee == 0`.
- Why `bal_chg == 0` is what makes the skip safe. A blank-ccy bill fits no currency's chain. If its `balChg` is 0, then whatever currency it really belongs to has the same balance before and after it, so the two neighbouring bills of that currency still satisfy `next.bal == prev.bal + next.bal_chg` without it. Skipping it can neither hide a break nor make one. If a balance really moved through it anyway (a `bal` jump with `balChg` 0), the next bill of that currency breaks the chain whether or not it is skipped. A blank-ccy bill with a nonzero `balChg` moved a balance the chain cannot attribute, so it stops.
- Why `pnl == 0 and fee == 0` as well. It makes "zero effect" mean one thing in this code: `aggregate_archive`'s `nonzero` is `row.pnl != 0 or row.fee != 0 or row.bal_chg != 0` (it drives `unknown_zero_effect`), and `_stop_census` repeats it. A bill with money on it that the chain does not see is what D-16 says still stops, so the definition fails closed.
- Why not `bal`. It is state, not effect. A zero-change bill on a funded account carries a nonzero `bal`, so requiring `bal == 0` would stop every such bill.
- Why not `posBalChg` / `posBal`. They are position balances, not the currency balance the chain proves. The parser does not read them, and adding them would widen this plan beyond D-16.

**What the skip touches, settled from the code.** In `_census_of`, `aggregate_archive` runs BEFORE `verify_bal_chain`, over every row, and this plan does not change it.
- A blank `ccy` is outside `ARCHIVE_USD_FAMILY`, so a blank-ccy bill is never summed into the realized, funding, flow or non-external leg, and never enters `summed_ccys`. The `MIN_CHAINED_PAIRS` floor therefore never applies to it.
- A blank-ccy bill with a nonzero effect already stops `non_usd_ccy` as `(blank)` (pinned by `test_currency_blank_ccy_with_a_nonzero_effect_is_a_stop`), or `unknown_subtype_nonzero` for an unclassified subType. That leaves one exception: a realized or non-external subType whose instType is outside `LIVE_REALIZED_INST_TYPES` (OPTION, EVENTS, a blank instType). There it is counted in `excluded_non_usd_rows` and goes on to the chain.
- So calibrate run 3's stopping bills were one of three kinds: zero-effect blank-ccy bills (now skipped), blank-ccy bills with money in an excluded instType class (still stop, `blank_ccy`), or non-digit billIds (still stop, `nondigit_bill_id`). The re-run tells them apart.
- Subtype classification is keyed on `sub_type`, not `ccy`, so the skip does not change it. The bill still counts in `census` (`rows`, `by_ccy` `(blank)`, `by_inst_type`, `by_sub_type`, `by_bucket`) and, for an unclassified subType, in `unknown_zero_effect`. The fingerprint hashes `census`, so it still binds the count.
- `longest_billless_run` reads `file.rows` directly, so the bill still marks its day as billed. It is a real line in the file, and this plan leaves that reading alone.
- `_balance_vs_nav` reads USD-family rows only. `_stop_census` and `_fingerprint` are not changed.
- Identical duplicate bills cannot sit in two files. Each `ts` lies inside its own file's half-open UTC+8 range, and a billId with different content stops `duplicate_bill_conflict` in the aggregate first. So per-file counts summed over files equal the de-duplicated count, and on a clean calibrate `census.by_ccy` `(blank)` equals `blank_ccy_skipped` (every blank-ccy bill on a clean run is a skipped one).

**Design fixed here (planner's decision under D-16, so the executor does not re-derive it).**
- Cause attribution. For each row, `blank` is `not row.ccy`, `nondigit` is `not row.bill_id.isdigit()`, and `zero_effect` is the definition above.
  - A row stops when `nondigit or (blank and not zero_effect)`.
  - A row is skipped when `blank and zero_effect and not nondigit`.
  - `blank_ccy` counts `blank and not zero_effect`, and `nondigit_bill_id` counts `nondigit`. One bill can carry both causes; `rows` counts each stopping bill once.
- The tally is per file, in the order `files` is passed, which is `quarters[]` order in the job. Each entry is `{ts_min_day, ts_max_day, rows, blank_ccy, nondigit_bill_id, first_day, last_day}`, where `first_day` / `last_day` are the earliest and latest `row.day` of the file's stopping bills, or None for a file with none.
- The `unchainable_row` detail is `{reason, rows, blank_ccy, nondigit_bill_id, first_day, last_day, files, blank_ccy_skipped}`. The totals are sums over files, and `first_day` / `last_day` are the min / max over files. The keys `reason` and `rows` keep their current meaning.
- The skip sits INSIDE the existing chaining loop, as its first statement: a row whose `ccy` is blank is passed over before `ccys.setdefault`. By then it can only be a skipped row, because stopping rows raised before the runs were built. The per-run `unique` de-duplication and its `duplicate_bill_conflict` check still see every row. No `""` ccy entry is ever created, and `previous` is never set from a skipped row.
- `blank_ccy_skipped` (an int, 0 when there is none) is added to every `verify_bal_chain` outcome after the tally: the `unchainable_row` detail, the `bal_chain_break` / `too_few_pairs` detail, and the success reading `{ccys, total_pairs, blank_ccy_skipped}`.
- The `last_error` tokens follow plan 17's `_quarter_range_tokens` style. After `cause=unchainable_row`, one space, then `rows=<n> blank_ccy=<n> nondigit_bill_id=<n> first_day=<day> last_day=<day> rows_by_quarter=<tag>:<n>[,<tag>:<n>]`, in that order, single spaces.
  - Counts must be a non-negative int that is not a bool (`_count_token`). Days must pass `_iso_day`. Anything else, and any missing key, renders the literal `unreadable` and never raises.
  - `rows_by_quarter` pairs each tag with that file's `rows`. It is `unreadable` as a whole when `files` is not a list of mappings exactly as long as the tag list; a single entry's bad count renders `<tag>:unreadable`.
  - `blank_ccy_skipped` is NOT a token. It lives in `info.bal_chain`, so the token text is final after Task 1.
- `_census_of` gains a third parameter, `tags: list[str]`. `_ingest_all` passes `[_quarter_tag(entry["year"], entry["quarter"]) for entry in quarters]`, and `_ingest_all` is its only caller. The tags come from the validated job input, never from a file. The tokens are appended only when the sanitised reason is `unchainable_row`, so the `bal_chain_break` and `too_few_pairs` texts stay byte-equal.
- `_bal_chain_info` copies these top-level detail keys when present: `rows`, `blank_ccy`, `nondigit_bill_id`, `first_day`, `last_day`, and (from Task 2) `blank_ccy_skipped`. Each `files[]` entry keeps `ts_min_day` / `ts_max_day` and copies the same per-file keys when present. A `bal_chain_break` entry carries only the two ts keys, so its reading is unchanged except for `blank_ccy_skipped`. These values are computed by the job's own code (counts, and days from `_ms_to_day` on an integer `ts`), never file text. They pass through as they are, as `ts_min_day` already does.
- The success `info.bal_chain` is `{**_safe_bal_chain(chain), "blank_ccy_skipped": chain["blank_ccy_skipped"], "floor": MIN_CHAINED_PAIRS}`.
