## Warnings

### WR-01: The completeness floor stops on currencies whose money never enters the rebuild. One coin-margined option bill is a permanent `archive_incomplete`

**File:** `analytics-service/services/okx_archive_classify.py:208-209` (`carries_money`) and `:220-223` (`starved`)

**Issue:**
- `carries_money` adds a currency when any of its rows has a nonzero `pnl`, `fee` or `balChg`. It does not check the bucket, the instType or whether the currency is in the USD family.
- `aggregate_archive` deliberately lets two kinds of row through without summing them:
  - non-USD REALIZED rows outside `LIVE_REALIZED_INST_TYPES`;
  - non-USD NON_EXTERNAL rows outside that set.

  It counts both in `excluded_non_usd_rows`.
- The commonest real case is a BTC- or ETH-margined OPTION bill: `BTC-USD-...-C` options settle in the coin.
- Such a currency typically has one or two bills in two quarters. It falls under `MIN_CHAINED_PAIRS` and stops the whole job as `archive_incomplete cause=too_few_pairs`. That is a permanent class, nothing is written, and only a code change gets past it.
- Measured with the probe in the Summary: `q3_like.csv` plus one BTC OPTION bill gives an aggregate that passes, then `STOP archive_incomplete too_few_pairs ['BTC']`.
- The binding direction (fix-findings-r2 item 2) scoped the floor to "a ccy carrying nonzero **realized/funding/flow effect**", meaning effect on the legs the rebuild sums. The implementation is wider than that.
- The fixture history points at the same risk. `q3_like.csv`'s USDC currency had one money bill, and it had to be padded with two zero-effect rows to pass. Any real currency touched once or twice in six months (dust, a single USDC trade, one coin option) hits the same stop.
- This is fail-closed, so no wrong figure is published. But a false permanent stop on the first real calibrate needs a reviewed code change before the overlap closes on 2026-12-14. That is the same schedule risk round 2 booked for RESEARCH A7.

**Fix:** Key the floor to the currencies whose money the rebuild actually sums. Leave the break gate on every currency: a break anywhere still means a truncated file.

```python
# okx_archive_classify.py, aggregate_archive: record which ccys reached a summed leg
summed_ccys: set[str] = set()
...
# wherever realized/funding/flows/non_external is incremented for a USD-family row:
summed_ccys.add(row.ccy)
...
return ArchiveAggregate(..., summed_ccys=frozenset(summed_ccys))

# verify_bal_chain(files, summed_ccys): floor only those
starved = sorted(c for c in summed_ccys if ccys.get(c, {}).get("pairs_checked", 0) < MIN_CHAINED_PAIRS)
```

Add a RED-first test: a lone BTC OPTION bill with P&L must pass the floor and still appear in `bal_chain.ccys`. A lone USDC realized bill must still stop.

### WR-02: `flow_totals_overlap` now starts 7 days before the seam, where the live side is empty by construction. A seam double-count reads as agreement, and the runbook explains a disagreement wrongly

**File:**
- `analytics-service/services/okx_archive_job.py:1950-1955` (`first = seam - margin`; `archive_total`, `live_total` over `[first, last_covered]`)
- `docs/runbooks/okxhistory-go-live.md:675-676`

**Issue:**
- `live.flows` comes from `fetch_ccxt_transfers(..., flow_since_ms=floor)`, where `floor = flow_retention_floor(...)` is the seam at midnight. `rebuild_union` also filters `flows_live` to the seam and later. So no live flow exists before the seam.
- `flow_totals_overlap.archive` still includes the archive transfers of `[seam-7, seam)`, while `.live` cannot. The reading therefore equals `archive_before_seam_used` plus the post-seam comparison. It mixes two different questions, with two consequences:
  - **The double-count reads as clean.** In `test_a_withdrawal_counted_by_both_sources_across_the_seam_shows_both_sides`, the archive has -200 on 07-30 (pre-seam, used) and the live side has -200 on 07-31 (used). `flow_totals_overlap` is `{archive: "-200", live: "-200"}`, which agrees, for exactly the movement counted twice.
  - **An ordinary movement reads as dirty.** A deposit plus its transfer on seam-3 puts +X on the archive side only, and the runbook (`:675-676`) tells the founder "a disagreement there is an internal transfer the live endpoints do not list". That explanation is wrong for this window.
- Under fix-findings-r2 item 3, the reading was to be "aligned with the actual flow seam". A window that opens before the seam is not comparable across the two sources. The comparable window opens AT the seam.

**Fix:** Open the totals at the seam, so they compare only days both sources can carry. `flow_seam` already covers the pre-seam side.

```python
archive_total = sum((v for d, v in aggregate.flows_by_day.items() if seam <= d <= last_covered), Decimal(0))
live_total = sum((v for d, v in live_flows if seam <= d <= last_covered), Decimal(0))
```

Then change runbook `:675-676` to "from the seam to the end of the archive (days both sources can carry)". Re-pin `TestFlowSeamReading`'s `flow_totals_overlap` expectation, and add an assertion that the withdrawal double-count does not read as agreement (or, with `flow_seam` as the only seam reading, that the runbook names `flow_seam` as the double-count detector).

## Info

### IN-01: Runbook Step 3 item 2's `total_pairs` identity and "the P&L currency's" range are approximations

**File:** `docs/runbooks/okxhistory-go-live.md:637-639`, `:644-646`

- "`total_pairs` equals the sum of `quarters[].row_count` less one per currency" holds only when all requested quarters form one adjacent run. Each run restarts every currency's chain (`_adjacent_runs`, `verify_bal_chain`), so the true identity subtracts one per currency per run.
- The head/tail rule names "the P&L currency's `first_day`". When USDT and USDC both carry P&L, each currency's chain proves only its own span, so a USDC bill missing before USDC's `first_day` is unprovable even inside USDT's span.

Say "per currency that carries P&L" and "one per currency per adjacent run".

### IN-02: `flow_seam`'s "both nonzero" no-go fires on ordinary activity, and its window can outrun the archive late in the overlap period

**File:** `docs/runbooks/okxhistory-go-live.md:673-674`; `analytics-service/services/okx_archive_job.py:1956-1962`

- "`archive_before_seam_used` and `live_from_seam_used` both nonzero" is true for any account with one normal deposit in the week before the seam and another in the week after. This conservative rule will produce human no-gos with no defect behind them.
- `after_last = seam + 6` is not clamped to `max(covered_days)`. For a run date after about 12-23 with Q3 as the last quarter, the archive-discarded side misses days that the live side counts, so `diff` becomes nonzero falsely.
- Both are readings only, so the effect is noise.

Clamp `after_last` to `last_covered`, and phrase the no-go as "a `diff` that the founder cannot match to one movement".
