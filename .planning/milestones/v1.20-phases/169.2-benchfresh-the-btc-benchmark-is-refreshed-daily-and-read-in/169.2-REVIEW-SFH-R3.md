## 2. What the fix round introduced: the hunt

### Except-arm order in `get_benchmark_returns`

Callers other than the refresh are unchanged:

- `BenchmarkCacheWriteError` is raised only when `require_persist` is true.
- The new re-raise arm therefore catches nothing on the default path.
- The order is correct: the specific arm comes before `except Exception`, inside the fresh-fetch
  `try`.
- A cache HIT returns before the write arm, so the flag does not affect it.

No finding.

### `wait_for` and cancellation

This check found nothing:

- **Nothing catches a cancellation.** Python is 3.12 (`.python-version`, Dockerfile). The
  fetch path (`services/benchmark.py`) and `services/db.py` `db_execute` contain no
  `except BaseException` and no bare `except:`. Every arm is `except Exception` or
  `_CACHE_READ_ERRORS` (`APIError`, `httpx.HTTPError`, `OSError`), and none of those matches
  `CancelledError`.
- **Only the deadline reaches the handler's arm.** `asyncio.wait_for` raises the builtin
  `TimeoutError`. Every failure inside `_benchmark_refresh_once` is already turned into an
  `HTTPException`, so the handler's `except TimeoutError` can only see the deadline.
- **A write can still land after the 500.** The docstring says so. The next run's read-back
  reflects it, and the thread count is bounded by `_DB_EXECUTOR`.

The one gap is diagnostic and is recorded as LW-R3-02.

### `after()` callbacks

`captureToSentry` is total: it returns a promise that always resolves, and both of its arms
swallow errors. The callbacks passed to `after` therefore cannot reject. `shouldCaptureNow` runs
synchronously before `after` is scheduled. The route is a Route Handler, so `after` always has a
request scope. No finding.

### `shouldCaptureNow` masking a different error

Both dropped-closes and read-error have their own key, so neither can mask the other. Within the
read-error arm, one key covers several different causes. See LW-R3-01.

### The one-day rule and a result that looks healthy

See MD-R3-01.

### MEDIUM

#### MD-R3-01: a missing-row gap is dropped with no console line and no capture, and a gap-riddled table answers a normal-looking cacheable `200 []`

- **Location:**
  - `src/lib/factsheet/benchmark-source.ts` `pricesToDailyReturns`: the `if (gap !== DAY_MS) continue;` line.
  - `src/app/api/benchmark/btc/route.ts` `GET`: the call to `pricesToDailyReturns(prices)` and the
    `NextResponse.json(series, { status: 200, headers: { "Cache-Control": CACHE_CONTROL } })` that follows it.
- **Origin:** introduced by the fix round (fdbcc561d). Before it, a missing row was bridged, which
  was wrong but visible as a number. It is now skipped, which is right, but nothing records it.
- **Issue: the two kinds of hole are treated unequally.**
  - A dropped close logs a `console.warn` and a throttled capture.
  - A missing row goes through the same `continue` and leaves no trace at all: no count, no
    console line, no capture.
- **The Python side does not catch it either.** Suppose the upstream series itself has a hole,
  for example the CoinGecko irregular `interval=daily` fallback that round-2 WR-02 named as a
  source of gaps.
  - The write then succeeds, so `require_persist` does not fire.
  - `_stored_through` reads yesterday, so the cron is green.
  - Every analytics compute logs a cache miss at info level only, and then refetches.
  - The TypeScript route then drops the return silently.
  - This is the reader-side half of the same class as LW-R2-01: every layer looks healthy, and
    the data has a hole.
- **The degenerate case.** If `prices.length >= 2` and no two stored closes are consecutive (a
  sparse table), the route answers `200 []`:
  - The response is the same as a truly empty table and carries the public cache header
    (`s-maxage=3600` hard, then background revalidation under stale-while-revalidate).
  - The server leaves no trace at all.
  - The consumers render the neutral "unavailable" state (`ScenarioBenchmarkSection` via
    `benchmarkAvailable`), so the user is not shown a wrong number. The operator is simply never
    told.
- **Trigger, stated honestly.** The column is `DATE` (migration `20260405093623_indexes_and_benchmark.sql`),
  so the `Date.parse` NaN path, which would skip every pair, is not realistic. The realistic
  trigger is sparse or holed rows.
- **Why this is not a BLOCK.** No wrong value reaches a consumer. The scenario code inner-joins by
  date (`innerJoinByDate`), so a skipped day drops out of TE, IR and beta instead of being
  zero-filled. What the gap removes is the ability to see the problem.
- **Hidden errors:**
  - a persistent upstream hole in `benchmark_prices`;
  - a partial write from an earlier failed run;
  - a sparse table that thins or empties the served series with every monitor green.
- **Fix: add a signal and leave the status and cache unchanged.** Changing either would be a second
  behaviour change that needs its own human check.
  - Have `pricesToDailyReturns` also report how many pairs it skipped for a gap, for example by
    returning `{ points, gaps }` or by exporting a sibling counter. Alternatively, the route can
    compute `prices.length - 1 - series.length` minus the non-finite skips.
  - When `gaps > 0`, the route should `console.warn` on every request.
  - It should also send one throttled capture, `shouldCaptureNow("benchmark-btc:gaps")` inside
    `after`, with the fixed message `"benchmark_prices has calendar gaps"` and
    `extra: { gaps, priceCount: prices.length, returnCount: series.length }`.
  - Use `level: "error"` when `prices.length >= 2 && series.length === 0` and `"warning"`
    otherwise.

  Whether a fully-gapped `[]` should stay publicly cacheable is a decision for the fixer or a human.
  This review does not require it.
- **Tests:**
  - A missing middle row gives one capture across two GETs and two console lines.
  - A table with no two consecutive dates gives a capture at `error` level and still answers
    `200 []`.
  - Neuter check: make the gap count zero and watch both tests go red.

### LOW

#### LW-R3-01: one read-error throttle key covers every cause of a failed read

- **Location:** `src/app/api/benchmark/btc/route.ts` `GET`, `shouldCaptureNow("benchmark-btc:read-error")`.
- **The causes that share the key:**
  - a transient PostgREST error;
  - the reader's own errors that mean the data is wrong (`not strictly older than`,
    `exceeded N pages`, `no data and no error`).
- **Issue:** the first failure in a 60 s window, on each instance, uses up the capture. A
  different cause inside the same window reaches the console only. A persistent cause is captured
  again in the next window, so the loss is bounded. That is why this is LOW.
- **Fix:** key by kind, for example `benchmark-btc:read-error:${code ?? "reader"}`. `code` is the
  PostgREST error code when present. The reader's own `Error`s map to one or more fixed kinds.

#### LW-R3-02: the deadline capture is a bare `TimeoutError` with no stage

- **Location:** `analytics-service/routers/cron.py` `benchmark_refresh`, the `except TimeoutError` arm.
- **Issue:** the event does not say which phase used up the 80 s: the upstream fetch (up to 20
  Binance pages, then CoinGecko), the upsert, or the table read-back. It also does not say whether
  the write may have landed after the 500. Debugging a recurring deadline then means guessing.
  Nothing is hidden, only unlabelled.
- **Fix:** keep a `stage` variable that `_benchmark_refresh_once` updates (`fetch`, then
  `read-back`). One way is a small mutable holder passed in; another is `sentry_sdk.set_tag` just
  before each await. Put it in the log line and on the capture's scope.

#### LW-R3-03: `test_too_few_rows_refetch_with_failed_upsert_answers_500` asserts only the status

- **Location:** `analytics-service/tests/test_benchmark_refresh.py`.
- **Issue:** the test proves that the refresh fails, not why. Any other 500 on this path would
  keep it green, for example a fixture change that makes the read-back fail. Fix-A's neuter 1 did
  turn it red, so it can fail today. It is just not tied to its cause.
- **Fix:** add `assert "BenchmarkCacheWriteError" in resp.text`, as the gap test does.

#### LW-R3-04: nothing tests that the capture throttle lets a capture through again after 60 s

- **Location:** the capture tests in `src/app/api/benchmark/btc/route.test.ts`, and the absence of
  any test of `shouldCaptureNow`'s expiry. A grep finds it only in route, `ratelimit` and
  `resilient-fetch` tests, and none of them advances the clock past the window.
- **Issue:** the new tests assert "once per window" by making two calls inside one window. A
  regression of `shouldCaptureNow` into a one-time, per-process latch would still pass them. It
  would also silence this route's only remote signal for the life of the instance. It is a shared
  library, so the risk is not specific to 169.2, but this phase now depends on it.
- **Fix:** add a unit test that calls `shouldCaptureNow(k, 0)`, then `(k, 59_999)` (false), then
  `(k, 60_000)` (true). The route's capture tests can also advance with `vi.setSystemTime` and
  assert a second capture.

### Noted, not raised

- **`through` in the all-corrupt case.** The new test "an all-corrupt DB still cuts the fixture"
  pins `through` to a fixture date (`2024-01-02`) even though the DB holds rows. The JSDoc calls it
  "the last REAL price date". For the planned Phase 169 / 169.4 consumers this is a mismatch between
  contract and comment. It is not a silent failure in this phase, because `dropped` travels with
  the result. Worth a sentence in the JSDoc so a factsheet does not show a fixture date as the DB's
  freshness.
- **The midnight test (IN-02).** `test_today_is_read_once_before_the_fetch` mocks

  the handler's `lt(today)` check is lenient enough that no wrong verdict follows. No finding.

## Done well

- **The re-raise arm is ordered correctly and pinned by a test.** Fix-A measured the exact trap
  the review snippet would have hit: the lost write coming back through the stale fallback as a
  500 for the wrong reason. The narrow exception class is the root fix, not a workaround.
- **The capture assertions in the Python tests are strict.** Each test patches `capture_exception`
  on the shared `sentry_sdk` module, which both `routers/cron.py` and `services/benchmark.py`
  call. So `assert_called_once` would also catch a stray second capture from the fetcher.
- **The throttled route tests use the real `shouldCaptureNow`.** They observe the route's actual
  capture volume, not a mock's.
- **The deadline is pinned to the TypeScript seam budget by symbol.** It is read from
  `src/lib/resilient-fetch.ts`, never restated as a number, so lowering the TypeScript budget turns
  a Python test red.
