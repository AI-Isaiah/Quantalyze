## Fixed Issues

### WR-03 / MD-04: offset paging repeated a boundary row under a concurrent upsert

**Fix:** `readBenchmarkPrices` now pages by a keyset cursor. Each page after the first adds
`.lt("date", <oldest date read so far>)` with `.order("date", desc).limit(BENCHMARK_PAGE_SIZE)`. It
still stops on an EMPTY page, still returns an error at `BENCHMARK_MAX_PAGES`, and now also checks
that the accumulated dates strictly decrease. A repeated or out-of-order row (a server that ignored
the cursor) returns `{ ok: false }` instead of a series with a duplicated day. The module docstring's
claim that "pages can neither skip nor repeat a row" is corrected.
**Tests:** new "a NEW newest day upserted between two pages neither repeats nor skips a stored day".
The fake client answers both `.range()` and `.lt()+.limit()`, so the old reader can run against it.
New "a server that ignores the cursor is an error at the first repeated day". The ceiling test now
uses an endless-table fake. The "advances by rows received" test asserts the `lt` cursors instead
of the offsets.
**Bite proof:** I re-edited the reader back to offset `.range()` with the monotonic check disabled.
The insert test went RED with `expected 1500 to be 1501`: 1501 dates, 1500 of them unique, so one
boundary day was duplicated. The cursor-ignoring test and the two limit/cursor assertions also went
RED. I restored the reader by reverse edit and confirmed it with `cmp` against a byte copy taken
before the neuter.

### WR-04 / MD-03 (+ IN-02 / LW-02): a dropped bad close was bridged into a multi-day return labelled as one day — fixed: requires human verification

**Which layer owns what:** the READER owns validity. It still leaves a non-numeric, non-finite or
non-positive close out of `prices`, and it now reports that close's date on a new
`BenchmarkReadResult.dropped: string[]` field (ascending). The field is additive. The ROUTE owns the
hole. It skips any return whose two closes straddle a dropped date, which restores the pre-169.2
semantics: a bad close at D gives no return at D and no return at the next stored day.
The route's `Number(...)` re-coercion and its four-way positivity guard were unreachable (IN-02 /
LW-02) and are deleted, with a comment that names the reader as the enforcer. `Number.isFinite(value)`
stays, because a float overflow on an extreme ratio can still reach it. When a close is dropped, the
route now logs a `console.warn` and sends `captureToSentry` at level `warning`, tag
`stage: dropped-closes`, with `extra.dropped`, so a corrupt row no longer disappears without a trace.
**Test restored:** the "non-positive CURRENT close" case in `route.test.ts` expects
`[{ date: "2024-01-04", value: 0.1 }]` again (the pre-phase expectation), and it also pins the
capture. The reader test pins `dropped: ["2024-01-02","2024-01-03","2024-01-04"]`.
**Bite proof:** disabling the gap skip turned the route test RED (it received the bridged
`2024-01-03` point). Disabling the capture turned it RED. Disabling `dropped.push` turned the reader
test RED. Each change was restored by reverse edit and checked with `cmp`.
**Stated limit:** a day with NO stored row at all is still bridged, as it was before 169.2. SFH
MD-03's stronger option (skip any return whose dates are not consecutive calendar days) was not taken,
because it would change behaviour that predates this phase. **For a human:** confirm that restoring the
pre-phase semantics is the intended choice, as opposed to the calendar-consecutive rule.
**For later consumers:** Phase 169 plan 169-02 and plan 169-03, and Phase 169.4 plan 169.4-02, will
read `prices`. The docblock tells any consumer that derives returns to honour `dropped` in the same way.

### MD-05: a read error was served as a CDN-cached `200 []`

**Callers read first:** `ScenarioComposer`'s mount fetch (`if (!r.ok)` → warn with the status,
degrade to `[]`) and the scenario-share page's `fetchBtcDaily` (`if (!res.ok) return []`). Both
already treat any non-2xx as the neutral "unavailable" state. A non-2xx is therefore safe with both
callers, and it is also more observable, because the Composer logs the status.
**Fix:** the `!read.ok` arm now answers **503** with `Cache-Control: no-store` and the static body
`{ error: "Benchmark temporarily unavailable" }`. It still logs and captures. A genuinely empty series
(0 or 1 stored closes) stays `200 []` with the public cache. The "Honesty on failure" docblock is updated.
**Tests:** "answers a read error with 503 + no-store ... AND captures the error" replaces the old
`200 []` + `public` pin. New "returns 200 [] (cacheable) for an EMPTY table".
**Bite proof:** I re-edited the arm back to `emptyResponse()`. Two tests went RED with
`expected 200 to be 503`. Restored and checked with `cmp`.

**Bite proof:** I re-edited the reader back to `data ?? []`. The reader test went RED. Restored and
