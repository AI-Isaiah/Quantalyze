## Fixed Issues

### WR-03: the route bridged a MISSING day into a multi-day return. Fixed, requires human verification

**Root fix, not a CONTEXT note.** The review offered a choice: apply the general rule, or record bridging
as a deliberate decision. I applied the rule. `benchmark-source.ts` now exports ONE helper,
`pricesToDailyReturns(prices)`. It uses pct-change as `benchmark.py` `prices_to_returns` does, and it
emits a return only when the two closes are exactly one UTC day apart (`Date.parse` difference ===
86 400 000). It also keeps the `Number.isFinite` overflow guard. A missing row, a dropped corrupt
close and a fixture/DB seam all leave a gap, and none of them is bridged. This matches the Python
side's rule (`_cache_miss_reason`: any calendar gap is a defect).
**Simplified:** the route's `dropped` two-pointer walk is deleted, and the route calls the helper.
`BenchmarkReturnPoint` moved into `benchmark-source.ts`, and the route re-exports it as a type.
**Kept:** the `BenchmarkReadResult.dropped` field. It still has two consumers: the route's
`dropped-closes` capture and `mergeWithFixture`'s cut. The JSDoc and the module docblock now name
`pricesToDailyReturns` as the one rule for returns.
**Tests:** route "never bridges a MISSING day" (2024-01-03 absent, so the output is `[01-02, 01-05]`
and there is no point at 01-04). Helper tests cover consecutive days across a leap day, the
missing-row gap and the overflow case. The restored dropped-close case ("non-positive CURRENT close")
still expects only `2024-01-04`.
**RED proof:** I made the gap check never fire (`gap !== DAY_MS && false`). Four tests went red:
the route's missing-day and dropped-close cases, the helper's gap case, and the merge test's
no-bridge assertion. Restored by reverse edit and checked with `cmp` against a copy taken before
the neuter.
**For a human:** this is a behaviour change from the pre-169.2 route, which bridged missing days.
The Scenario composer and the scenario-share page will now see no return at the day after any gap
in `benchmark_prices`. That is the intended root fix, but please confirm it.

### WR-01: unthrottled Sentry capture on a public, cache-bustable route

**Fix:** in `GET`, both capture arms keep their console line on every request, and only the remote
capture is gated by `shouldCaptureNow`. The keys are `benchmark-btc:read-error` and
`benchmark-btc:dropped-closes`: one capture per arm, per instance, per 60 s window, as
`resilient-fetch.ts` and `ratelimit.ts` do. The `dropped-closes` message is now the fixed string
`"benchmark_prices holds unusable BTC closes"`, so a changing count no longer splits grouping. The
count and the newest dropped dates go in `extra: { count, dropped: read.dropped.slice(-DROPPED_EXTRA_CAP) }`,
with `DROPPED_EXTRA_CAP = 20`. The read-error capture also gained `stage: "read"`.
**Test harness:** the test's `@/lib/sentry-capture` mock now spreads `importActual` and replaces only
`captureToSentry`, so the real throttle runs. `__resetCaptureThrottleForTests()` runs in `beforeEach`.
**Tests:** "captures a persisting corrupt row ONCE per window" (two GETs give one capture, the stable
message, and two console lines). "captures a persisting READ ERROR once per window" (two 503s, one
capture, two console lines). "caps the dropped dates ... at the NEWEST 20" (30 corrupt rows give
`{count: 30, dropped: <newest 20>}`).
**RED proofs:** each change below was restored by reverse edit and checked with `cmp`.
- `|| true` on both gates: the two once-per-window tests went red.
- A count in the message: the corrupt-row test went red.
- `slice(-CAP * 0)`: the cap test went red.

### IN-03: the route's captures were fire-and-forget

**Fix:** both captures are scheduled with `after(() => captureToSentry(...))` from `next/server`. I read
`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md` first: `after` is valid in
Route Handlers and runs after the response for up to the route's max duration. I used the bare-`after`
form of `intro/route.ts`. The `try { after } catch { queueMicrotask }` fallback belongs in lib code
that can run outside a request scope, and a route handler always runs inside one.
**Tests:** `next/server` is mocked with an `afterSpy` that runs the callback. Both once-per-window
tests assert `afterSpy` was called once.
**RED proof:** I replaced `after(` with an immediate call `((f) => f())(`, and both tests went red.
Restored and checked with `cmp`.

### MD-R2-01 (ride-along MEDIUM): `mergeWithFixture` erased the dropped-dates contract

**Fix:** the signature is now `mergeWithFixture(db: { prices; dropped }, fixture)`, returning
`{ prices, through, dropped }`. The fixture is cut strictly before the first STORED date, which is the
earlier of `db.prices[0].date` and `db.dropped[0]`. A dropped oldest row therefore stays a hole and is
not filled by the fixture. An all-corrupt DB (no valid prices, some dropped rows) also cuts the fixture.
`through` is the last date of the merged series. Planned consumers should derive returns through
`pricesToDailyReturns`, which the module docblock names. The function still has no production caller,
so the only callers updated were the four existing tests.
**Tests:** "a DROPPED oldest stored row is not filled by the fixture" (also asserts that
`pricesToDailyReturns` does not bridge the hole) and "an all-corrupt DB still cuts the fixture at its
first stored date".
**RED proof:** I reverted the cut to `[db.prices[0]?.date]` only, and both tests went red. Restored and
checked with `cmp`.

### LW-R2-02 (ride-along LOW): the cron's misconfigured-limiter 503 reached no Sentry

**In scope:** the fix sits entirely inside `src/app/api/cron/refresh-benchmark/route.ts`. No sibling
cron has a limiter. The capture copies the shape of this route's own failure arm and of
`flag-monitor`: an awaited `captureToSentry`.
**Fix:** in `handle`, when `isRateLimitMisconfigured(rl)` is true, the route logs a static
`console.error` and then awaits
`captureToSentry(new Error("refresh-benchmark: limiter unavailable, refresh skipped"), { tags: { route: "cron.refresh-benchmark", stage: "limiter" }, level: "error" })`
before `rateLimitDenyJson`. The 429 arm, where the limiter is working, is still not captured. The cron
runs once a day, so no throttle is needed.
**Tests:** the existing 503 case now asserts exactly one route capture with those options. The existing
429 case still asserts zero captures.
**RED proof:** I made the guard never fire (`&& false`), and the 503 case went red for both the GET and
POST handlers. Restored and checked with `cmp`.

## Not changed

- `ScenarioComposer.tsx`: no edit. The route's contract (`[{date, value}]`, a no-store 503 on a read
  error) is unchanged, and the comment above the BENCH-01 mount fetch is still accurate. The one visible
  effect is that there is no point at the day after a gap. The composer does not describe that.
- The fixture/DB seam, stated so a later round does not reopen it: when the fixture's last date and
  the DB's first stored date are consecutive UTC days, `pricesToDailyReturns` emits one return at the
  seam, computed from a fixture close and a DB close. That follows from the D-09 merge design and is
  correct under the one-day rule. When the two are not consecutive, as with a dropped first stored
  row, the seam is a gap and no return is emitted.
