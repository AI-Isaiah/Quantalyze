## Fixed Issues

### CR-01: The refresh endpoint answered 200 when the cache write failed (fixed: requires human verification)

**Files modified:** `analytics-service/routers/cron.py`, `analytics-service/tests/test_benchmark_refresh.py`
**Applied fix:** After `get_benchmark_returns("BTC")` returns a non-empty series that is not stale,
`benchmark_refresh` now calls `_stored_through("BTC", today=...)`. That call reads the newest stored
BTC `date` from `benchmark_prices` (`select("date").eq("symbol").lt("date", today).order(desc).limit(1)`
through `db_execute`). The handler answers 500 unless that date is at least yesterday (UTC). The 200
body's `through` is now that stored date, not the last index of the in-memory series.

The field names `{symbol, through, stale, points}` are unchanged. `points` is still `len(series)`.

`.lt("date", today)` mirrors the fetcher's completed-days rule (`services.benchmark._completed_days_only`),
so a partial-day row for today cannot count as fresh.

A failure of the verification read itself (for example `get_supabase()` "not configured", a
PostgREST error or a transport error) is also a 500. Its log line and detail carry the exception
type only, and the exception is sent to Sentry. The status stays 500 on every arm and never 503 (W2).

The fetcher was left as it is. `get_benchmark_returns` has other lenient callers (`job_worker`,
`analytics_runner`, `portfolio`, `process_key`), and re-reading the table is the control that
checks the effect directly.

**Neuter → RED → restore evidence.** The new tests were written first and run against the
unchanged handler:
`7 failed, 7 passed, 1 warning in 3.96s`. The CR-01 case is
`test_failed_upsert_through_the_real_fetcher_answers_500`, which runs the REAL `get_benchmark_returns`
with only `fetch_btc_daily_prices` patched and the upsert raising. Against the old handler it failed with:

```
E       AssertionError: {"symbol":"BTC","through":"2026-09-26","stale":false,"points":5}
E       assert 200 == 500
```

In other words, the old handler reported a refresh through yesterday while the table stayed 3 days
old. With the fix applied: `14 passed, 1 warning in 3.21s`. The positive control
`test_successful_upsert_through_the_real_fetcher_answers_200` passes on both handlers. It proves the
fake table and the real fetcher path produce a 200 once the write actually lands.

Other new tests for this finding:
- `test_through_is_reported_from_the_table_not_the_series`: the series ends yesterday but the table
  ends 3 days earlier, so the answer is 500 and names the stored day.
- `test_empty_table_answers_500`
- `test_table_read_failure_answers_500_type_only_and_captured`

### WR-01: A fetch ending before yesterday answered 200 (fixed: requires human verification)

**Files modified:** `analytics-service/routers/cron.py`, `analytics-service/tests/test_benchmark_refresh.py`
**Applied fix:** The CR-01 table check (`stored >= yesterday` UTC) closes this finding as well. A
lagging upstream is written, but the stored newest day is older than yesterday, so the handler
answers 500 and the detail names that date.

New tests:
- `test_fetch_ending_before_yesterday_answers_500` (real fetcher). The upstream ends the day before
  yesterday, and the test asserts the rows DID land (`table.newest()`), which proves this is a
  freshness failure and not a write failure. It was RED against the old handler, which answered
  200 with `through` equal to that date.
- `test_a_row_for_today_does_not_count_as_fresh` pins the `.lt("date", today)` filter.

**Known limit:** `today` is read after the fetch returns. If a refresh ran across UTC midnight,
yesterday could advance past the data the fetcher had just written, and the result would be a
false 500. The cron runs at 00:10 UTC, ten minutes after midnight, so this cannot happen at the
current schedule. The failure mode is also safe: it pages instead of hiding staleness.

### IN-04 / SFH MD-02: The failure path discarded everything except the exception type (fixed)

**Files modified:** `analytics-service/routers/cron.py`, `analytics-service/tests/test_benchmark_refresh.py`
**Applied fix:** `sentry_sdk.capture_exception(exc)` is now called before each `raise HTTPException(...) from None`,
in both the fetcher-exception arm and the new table-read arm. This matches the capture the delegated
module already makes on its cache-read arm (`services.benchmark.get_benchmark_returns`, the
non-DB-error `except`). The stack reaches Sentry through `sentry_init`'s redacting `before_send`.

The log line and the response `detail` stay type-only. `exc_info=True` was deliberately NOT added
to the log line, because it would put the upstream message into plain logs.

The "not current" arm uses `logger.error`, which becomes a Sentry event under the default
`LoggingIntegration`. `sentry_init` passes an explicit `integrations=[...]` list, but it does not
disable the default integrations. That line now also names the stored date, the needed date and
the fetched series' last day.

Tests: `test_exception_answers_exactly_500_logged_by_type_only` now asserts
`capture_exception` was called once with the raised exception. It was RED against the old
handler: `Expected 'mock' to be called once. Called 0 times.` The table-read test asserts the same
capture. Both tests keep the canary assertions, which require that the secret-bearing message
appears neither in the body nor in the logs.

## Skipped Issues

### SFH LW-01: `.limit(days + 1)` against a `max_rows` of 1000

**File:** `analytics-service/services/benchmark.py` (`get_benchmark_returns`, the cache read)
**Reason:** Skipped because it is not clearly a bug. The measurement is real:
`supabase/config.toml` sets `max_rows = 1000`, so with `days=1000` the `+1` row is capped away
and the comment's stated purpose does not hold under that config. The consequence is still benign:

- The only affected case is a stored row dated today, and the current writer never writes one,
  because `_completed_days_only` drops it.
- A legacy row of that kind costs at most one day of cache misses. Each miss refetches correct
  data, and the next day's upsert overwrites that date with the real close.
- No wrong data is served in either case.

PROD's `max_rows` was not measured. The function is pre-existing, has several callers, and the 17 test
files in the gate below reference it, so changing it here carries regression risk out of proportion to
the finding.

If someone picks it up, the clean fix is to add `.lt("date", today)` to the cache read and use
`.limit(days)`. That makes the `+1` and its comment redundant, and the read is then correct at any
`max_rows` of `days` or more.

**Original issue:** A requested 1001 rows come back as 1000 under `max_rows = 1000`, so a legacy
row for today would make every cache read that day a miss.
