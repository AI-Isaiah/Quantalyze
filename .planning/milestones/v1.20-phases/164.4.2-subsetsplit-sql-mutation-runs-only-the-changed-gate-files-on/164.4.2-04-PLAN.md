  <behavior>
    - demand for a class is 0 and supply absent -> that class is SATISFIED (nothing asked for it)
    - demand for a class is >0 and supply present -> SATISFIED
    - demand for a class is >0 and supply absent -> UNSATISFIED, and the class is named
    - supply for any class unreadable (probe query failed / returned nothing) -> MEASURE_FAIL, exit non-zero; unknown is not absent and it is not present
    - the corpus glob matches zero files -> MEASURE_FAIL, exit non-zero; an empty corpus is never a clean probe
    - the verdict line always names every class with both numbers, on the satisfied path too
  </behavior>
  <action>
Write the probe with the repo's library+CLI shape: `export const CLASSES` (each class carries
its own demand detector and its own supply query), a PURE `export function judge({demand,
supply})` returning named findings, `export const EXPECTED_ASSERTIONS` pinned and checked, an
`invokedDirectly()` realpath guard, `main(argv)` returning an exit code, and `--self-test`
driving `judge()` over the arms in `<behavior>`.

The five classes, each with its demand detector over `supabase/tests/test_*.sql` and its supply
query, derived from the census in RESEARCH R2:
  * `pg_net` — demanded by files mentioning the extension or an `net.http_` call; supplied when
    `pg_extension` carries it.
  * `vault` — demanded by files referencing the `vault.` schema; supplied when the vault
    extension is installed. ⚠️ Do NOT conflate this with the commented-out `[db.vault]` block in
    `supabase/config.toml` — that governs a secret-key override, not whether the extension
    exists.
  * `auth-functions` — demanded by files calling `auth.uid()` / `auth.jwt()`; supplied when
    those functions resolve in the catalogue.
  * `platform-roles` — demanded by files naming `anon` / `authenticated` / `service_role` or
    switching role; supplied by the count of those roles present.
  * `pg_cron` — demanded by files referencing the `cron.` schema; supplied when the extension
    is installed.

Demand is COUNTED per class (how many corpus files ask) and printed. ⛔ It is not pinned, not
floored and not compared against a stored number — this plan adds no census.

Supply comes from ONE `psql` invocation against the lane's DSN, read from `.stack-env` as
described in `<context>`, with the results parsed per class. Refuse a DSN that is not a local
loopback address before connecting, matching the lane's own local-only refusal. Pass the DSN as
an argv element to `execFileSync`, never through a shell string.

Print exactly one always-on verdict line, shaped so a CI step can assert on it:
`stack-probe: <class>=<demand>/<present|absent> … verdict <SUFFICIENT|INSUFFICIENT>`

absent-supply branch so an unsatisfied class returns no finding, run `--self-test`, OBSERVE

after every edit. ⛔ Never `git checkout --`, `git restore` or `git stash`.
