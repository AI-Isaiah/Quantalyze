# Phase 164.9.7 Plan 01: TRUNCATEREVOKE migration and gate Summary

**anon and authenticated lose TRUNCATE on every public relation and on tables postgres creates later, the apply refuses itself from the catalogue if that is not true, and a six-arm SQL gate that fails without the migration proves it.**

## What was built

- `supabase/migrations/20261009130000_revoke_truncate_anon_authenticated.sql`: one `DO $verify$` block. It counts `service_role` TRUNCATE holders (r,p,v,m,f), runs `REVOKE TRUNCATE ON ALL TABLES IN SCHEMA public FROM anon, authenticated`, runs `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE TRUNCATE ON TABLES FROM anon, authenticated`, then raises `migration 20261009130000 failed: ...` on a surviving holder, on a surviving postgres default-ACL grant, or on a moved service_role holder count. It reads `pg_class`, `pg_default_acl`, `aclexplode` and `has_table_privilege` only; no row of any public table is read, so the schema-only shared TEST behaves like PROD.
- `supabase/tests/test_truncate_revoke_anon_authenticated.sql`: annotated gate, arms TRUNC 1 to TRUNC 6, with a `TRUNC 1-SETUP` anti-vacuity check (the sweep must see a relation on which a client role holds SELECT). Apply list is the `test_cron_runs_rls.sql` list (fixtures 01, 07, 12, 15, cron_heartbeat) with the new migration appended last.
