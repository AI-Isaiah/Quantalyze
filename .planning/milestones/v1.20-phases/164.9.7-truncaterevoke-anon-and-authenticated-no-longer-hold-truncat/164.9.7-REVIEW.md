## Medium Issues

### MD-01: The PG 17 MAINTAIN privilege is the same RLS-exempt class, and it is held, unbooked, and left out of the TODOS "still open" list

**Severity:** MEDIUM · **Confidence:** 6/10
**File:** `TODOS.md:7161`. Source of the measurement: `164.9.7-RESEARCH.md:67` (`arwdDxtm`; `m` = MAINTAIN).

**Issue:** The phase's premise, stated in the migration header lines 6–14 and in TODOS, is that row security never evaluates some verbs, so the grant layer is the only control there. On PostgreSQL 17 that is equally true of MAINTAIN. PROD's default ACL hands MAINTAIN to anon and authenticated (`anon=arwdDxtm/postgres`). So the same roles hold it on the same tables.

MAINTAIN lets a client-role session run:

- `LOCK TABLE … IN ACCESS EXCLUSIVE MODE`, held for as long as its transaction stays open
- `VACUUM FULL`
- `CLUSTER`
- `REINDEX`
- `REFRESH MATERIALIZED VIEW`

Every one of these takes an ACCESS EXCLUSIVE lock, which blocks every other reader and writer on the table. That is not data loss. It is a full-table outage reachable by exactly the "SQL-capable path running as anon" this phase defends against.

The new TODOS annotation says, as if exhaustively: "Still open and still owned by this entry: REFERENCES and TRIGGER on both roles, and DELETE on anon." MAINTAIN appears nowhere in TODOS. The only `MAINTAIN` hit, `TODOS.md:7191`, is the word MAINTAINABILITY. It does not appear in CONTEXT or in the ROADMAP residual either. The existing entry is also scoped to `api_keys`, while the residue it names (REFERENCES, TRIGGER and MAINTAIN) sits on every default-granted public table.

**Failure scenario:** The phase ships, and the ledger now reads as if the only open RLS-exempt verbs were REFERENCES and TRIGGER on `api_keys`. A later reader concludes that the class is closed. A client-role SQL path then opens a transaction, takes `LOCK TABLE public.strategies IN ACCESS EXCLUSIVE MODE`, and stalls every read and write on the table until the session is killed. RLS never sees it.

**Fix:** Do not widen this migration, because that is outside D-01. Book the class in TODOS instead, with an owner and a trigger, and correct the annotation's list. For example:
```
- Still open and still owned by this entry: `REFERENCES`, `TRIGGER` and (PG 17) `MAINTAIN` on both
  roles across every default-granted `public` table (not only `api_keys`), and `DELETE` on `anon`.
  MAINTAIN is RLS-exempt like TRUNCATE (LOCK TABLE ACCESS EXCLUSIVE / VACUUM FULL / CLUSTER /
  REINDEX); the class fix mirrors 20261009130000 (ON ALL TABLES + FOR ROLE postgres default + sweep).
```

### LOW-01: TRUNC 1-SETUP does not prove what its message says. Fixture 01 already grants client-role SELECT, so the check passes without fixture 07

**Severity:** LOW · **Confidence:** 8/10
**File:** `supabase/tests/test_truncate_revoke_anon_authenticated.sql:88-99` (claim at `:14-18`, `:32-38`)

**Issue:** The setup check requires at least one public relation on which anon or authenticated holds SELECT. Its error text says the purpose is to catch fixture 07 or the cron_runs migration going missing from the apply list.

But `scripts/pg-lane/fixtures/01-fixture-core.sql:47` runs `GRANT SELECT ON strategies, profiles TO authenticated`. So the check is satisfied by fixture 01 alone. With fixture 07 removed from `RED-UNDER-SETUP`:

- `cron_runs` inherits no default.
- The migration's REVOKE does nothing.
- TRUNC 1 passes for the reason the header at `:35-38` says it must not.

The hole is closed only indirectly. TRUNC 3 (service_role TRUNCATE on the probe table) and TRUNC 4 (client SELECT on the probe table) would go RED, because without fixture 07 a new table gets no default grants at all.

**Failure scenario:** A future edit trims fixture 07 from the setup list. The reason a reader gets is TRUNC 3 or TRUNC 4, phrased as "the default-privilege change removed the verb from service_role". That points at the migration, not the missing fixture. TRUNC 1-SETUP, the guard written for exactly this case, stays green.

**Fix:** Pin the setup check to the default-granted object:
```sql
IF NOT (has_table_privilege('authenticated', 'public.cron_runs'::regclass, 'DELETE')
        AND has_table_privilege('service_role', 'public.cron_runs'::regclass, 'TRUNCATE')) THEN
  RAISE EXCEPTION 'TEST FAILED (TRUNC 1-SETUP): public.cron_runs does not carry the bootstrap default grants ...';

```

### LOW-04: PROD-READINGS decodes the ACL letter wrongly. `t` is TRIGGER and `D` is TRUNCATE

**Severity:** LOW · **Confidence:** 10/10
**File:** `.planning/phases/164.9.7-…/164.9.7-PROD-READINGS.md:29` (a phase artifact, outside the 9-file scope, but plan 04 reads it)

**Issue:** "The `t` in each entry's privilege string is TRUNCATE". PostgreSQL's ACL letters are `a`=INSERT, `r`=SELECT, `w`=UPDATE, `d`=DELETE, `D`=TRUNCATE, `x`=REFERENCES, `t`=TRIGGER and `m`=MAINTAIN. RESEARCH line 67 has this right.

After the apply, PROD's postgres default row will read `anon=arwdxtm/postgres`. That still contains `t`.

**Failure scenario:** Plan 04's verifier, or the founder at the residual checkpoint, follows this file's own key. They read the AFTER default ACL, see `t` still present, and conclude that the default-privilege revoke failed. The reverse error is also possible: they treat a surviving `D` as harmless.

**Fix:** Change it to "The `D` in each entry's privilege string is TRUNCATE (`t` is TRIGGER)". Better still, record the AFTER default-ACL reading through `aclexplode(...).privilege_type = 'TRUNCATE'` rather than by eye.

### LOW-05: The rollback's count self-check is self-referential, so a holder created after the merge base is silently not restored

**Severity:** LOW · **Confidence:** 5/10
**File:** `supabase/migrations/down/20261009130000-rollback.sql:192-210`

**Issue:** The expected counts (56 and 59) are this file's own line counts. A count match therefore proves only that the listed GRANTs landed and that nothing else holds TRUNCATE. It cannot detect a relation that held TRUNCATE immediately before the migration but is missing from the list.

The list was derived from the merge-base dump. Suppose a migration that creates a public table merges between this branch's base and its merge, or with a lower timestamp merged after it. That table would inherit TRUNCATE from the still-unrevoked default, lose it to this migration, and stay without it after the rollback. The rollback's DO block would still pass.

**Failure scenario:** The rollback is not "exact prior set" for that table, and nothing says so. The direction is safe (it under-grants), which is why this is LOW. But the header's "restores the EXACT holder set" becomes untrue without anyone being told.

**Fix:** At merge time, re-check that `supabase/migrations/` has gained no public `CREATE TABLE` since `239106dc5` (`git diff 239106dc5..<merge> --name-only -- supabase/migrations`). Alternatively, qualify the header claim: "exact as of the dump at `<sha>`; a table created by a migration merged after that is not restored".
