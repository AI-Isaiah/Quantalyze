## Notes carried forward (not threats)

- **Recorded residual, pre-existing — ⚠️ CORRECTED 2026-09-07, it is WORSE than first written.**
  This bullet previously said the incoming-`null` arm "presents as a silent resume rather than a
  dead end". That UNDERSTATES the consequence. Traced end to end and verified by command at
  HEAD, both legs:
  1. `src/app/(dashboard)/strategies/new/wizard/page.tsx:101` catches a `readLatestWizardDraft`
     fault and degrades `initialDraft` to `null` — its own comment says *"Degrade to \"no
     draft\""*. That route passes **no `preselectKey` at all** (`:141-145` renders
     `<WizardClient initialDraft initialDraftKind />` only), so
     `initialDraft?.api_key_id ?? preselectKey?.id ?? null` resolves to `null` and
     `sessionKeyMatches` returns `true` — key A's `wizardSessionId` is restored.
     ⚠️ And a read FAULT is not the only way in: `draftIsOnThisBranch` (`:108-110`) nulls
     `initialDraft` whenever the stored draft belongs to the OTHER branch
     (`draftMatchesSource(kind, source)` false) — normal operation, no fault required.
  2. `src/app/api/strategies/create-with-key/route.ts:1096-1104` then hits its F6 idempotency
     fence, which keys ONLY on `(user_id, wizard_session_id)`:
     `if (existingDraft?.id && existingDraft.api_key_id) { return { ok, strategy_id:
     existingDraft.id, api_key_id: existingDraft.api_key_id } }` — returning the existing draft
     **without ever comparing the submitted key**, and **without setting a `deduped` flag** the
     client could notice.
  So on the manager route `/strategies/new/wizard`, with an abandoned key-A payload in
  localStorage, a user who connects **key B** can be handed back **key A's strategy and key A's
  `api_key_id`**, silently. Say that plainly rather than "a silent resume".
  What is equally true and mitigating: this is **PRE-EXISTING** — before this phase the same
  path restored key A's token unconditionally, so 164.2.1 did not introduce it and did not
  widen it (see the monotonicity argument in T-164.2.1-01: incoming `null` is byte-for-byte
  pre-PR behaviour). It is **outside criterion 1 as written**, which is about a preselect for
  key B; here there is no preselect at all. And it follows from **founder-locked decision
  D-01**. `threats_open` is therefore NOT raised and this is not a new finding against the
  work — it is a correction of the record. Booked in root `TODOS.md` as
  `[164.2.1-INCOMING-NULL-CONFLATION]`, tagged FOUNDER CALL because resolving it changes D-01.
