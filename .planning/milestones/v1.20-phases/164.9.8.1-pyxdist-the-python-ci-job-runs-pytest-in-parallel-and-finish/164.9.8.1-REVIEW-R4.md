What holds, checked against the code rather than the commit messages:

1. The sweep removed the last bound on every subprocess child, and the suite has no hang diagnostics. A hang is now an unnamed 90-minute cancellation, or an endless hang locally.

3. The session-monitor deadline test no longer proves that the deadline is the cadence.

## Warnings

### WR-01: MEDIUM. A hung test is now undiagnosable: no subprocess bound, no `faulthandler_timeout`, no `pytest-timeout`, and an un-verbose xdist run

**File:** `analytics-service/tests/test_feedback_engine.py:1715`, `test_qstats_gate.py:156`, `test_limiter_stub_restore.py:161`, `test_limiter_route_coverage.py:242`, `test_mt5_outage_alert.py:1275`, `test_structlog_frozen_proxy.py:171`, `test_xdist_group_is_real.py:51` and `:96`. Interacts with `analytics-service/pytest.ini` (no `faulthandler_timeout`), `requirements-dev.txt` (no `pytest-timeout`) and `.github/workflows/ci.yml:5622` (`pytest -n auto --dist loadgroup ...`, no `-v`, under the job's `timeout-minutes: 90`).

**Issue:** Each of these `subprocess.run` calls now waits without limit, and each uses `capture_output=True`. The comment on every call says "a child that genuinely hangs is stopped by the CI job timeout". That is true, but the stop carries no information:

- `faulthandler_timeout` is not set, so pytest never dumps the stuck stack.
- `pytest-timeout` is not installed.
- The run is `-n auto` without `-v`, so the log shows no per-test progress lines.
- The child's own output sits in a pipe that dies with the process.

Failure scenario: one child pytest session deadlocks or blocks on I/O. For example, `test_xdist_group_is_real.py:51` runs a nested `-n 2` session, and the children at `test_limiter_stub_restore.py:161` and `test_qstats_gate.py:156` run full pytest sessions with conftest and the live-DB lane env inherited. The xdist worker that owns the test blocks, every other worker finishes, and the controller waits. 90 minutes later GitHub cancels the step. The log ends in a row of dots with no test id, no traceback and no child output.

Before the sweep, the same hang produced a `TimeoutExpired` that named the test after 120-300 s. Locally (`make test`, or `pytest` from analytics-service/) there is no outer bound at all, so the session hangs forever.

The sweep also applied two conflicting patterns:

- In-process waits got 10 s deadmen (`test_mt5_concurrency.py:541, 623, 628`).
- Subprocess waits got no deadman, on the stated reason that "any clock bound is a bet on CPU speed".

A deadman sized far above the measured worst case (50-130 s) is not a bet on CPU speed, and the sweep's own in-process changes rely on exactly that argument.

D-14 asked that bounds "that would fail under CPU starvation are fixed the same way" as the lazy-import test. It did not ask that hang detection be removed.

**Fix:** Pick one of these. Neither makes a verdict depend on the clock.

```ini
# analytics-service/pytest.ini, diagnostic only: it dumps every thread's stack
# (naming the stuck test) and never fails or skips anything
faulthandler_timeout = 900
```

Or give each child a deadman that is an order of magnitude above the measured worst case, and fail with the test named:

```python
try:
    proc = subprocess.run([...], capture_output=True, text=True, timeout=1800)  # DEADMAN: ~14x the 130 s worst case
except subprocess.TimeoutExpired as exc:
    pytest.fail(f"child hung past the 1800 s deadman; partial stdout={exc.stdout!r} stderr={exc.stderr!r}")
```

The first option has one more benefit. It also covers in-process hangs such as WR-02, which no subprocess bound can reach.

### WR-02: MEDIUM. The lease-expiry deadman rests on a false premise; the regression it guards against is an infinite hang

**File:** `analytics-service/tests/test_mt5_concurrency.py:396-409`, against `services/mt5_concurrency.py:357-419`

**Issue:** The new comment says: "A wait that ignored `wait_s=0.05` would fall back to the module default (20 s), so any bound strictly inside that default tells the two apart." That is not what the lease does. `mt5_terminal_lease(..., wait_s=None)` means acquire **with no bound** (`services/mt5_concurrency.py:374-376`, `if wait_s is None:` at `:419`). `_MT5_LEASE_WAIT_S` is a value that callers pass in, not a fallback inside the lease.

The test holds the lock with `await lock.acquire()` (`:396`) and never releases it before `async with mt5_terminal_lease("h:1", wait_s=0.05)` (`:400`).

Failure scenario: a regression drops or mis-threads `wait_s`. For example, a refactor forwards `wait_s=None`, or the bounded branch is skipped. The acquisition then waits forever on a lock that nothing will release. The `elapsed < _MT5_LEASE_WAIT_S / 2` assertion (`:407`) is never reached, and with WR-01 the hang is unnamed.

So the regression this test exists for, "the bounded wait did not fire at its bound", shows up as a 90-minute anonymous CI cancellation, not as its own message. The comment also tells the next reader that the case is already covered.

A second, smaller point: the bar is now read from `MT5_LEASE_WAIT_S` in the environment (`services/mt5_concurrency.py:183`). If an operator or CI env ever sets it below 0.1, `/ 2` falls below the 0.05 bound under test and the test goes RED falsely.

**Fix:** Make the acquisition itself carry a deadman. Then a missed bound fails with the test's own message instead of hanging. Also fix the comment.

```python
started = time.monotonic()
async def _attempt() -> None:
    async with mt5_concurrency.mt5_terminal_lease("h:1", wait_s=0.05):
        pytest.fail("the body must never run when the terminal was never acquired")
try:
    with pytest.raises(mt5_concurrency.Mt5TerminalBusyError):
        # DEADMAN: wait_s=None means UNBOUNDED, so an ignored bound hangs on the held lock forever.
        await asyncio.wait_for(_attempt(), timeout=10.0)
except asyncio.TimeoutError:
    pytest.fail("the bounded wait never fired: the lease waited on the held lock as if wait_s were None")
```

(`asyncio.TimeoutError` is not a `Mt5TerminalBusyError`, so it escapes `pytest.raises` and reaches the `except`.) Also give the bar a literal, for example `elapsed < 5.0`, instead of a value that the environment can change.

### WR-03: MEDIUM. The session-monitor deadline test no longer proves that the deadline IS the cadence

**File:** `analytics-service/tests/test_mt5_session_monitor.py:679-706`. The same weakening, in smaller form, is at `:743-752`.

**Issue:** The test's contract, from its own docstring: "A tick whose heal call outlives the configured cadence must be cut off AT the cadence" (cadence = 0.05 s). The new assertion is `cut_short and elapsed < park_s / 2`, which is 50 s. It only proves that something cancelled the heal within 50 s.

The old `elapsed < 2.0` caught any deadline of 2 s or more. The new form catches only deadlines of 50 s or more, or no cancellation at all.

Failure scenario: the tick's `asyncio.wait_for(..., timeout=interval)` (`services/mt5_session_monitor.py:296-301`) regresses to a deadline between 2 and 50 s. Examples are a hard-coded 30 s, the relogin budget (`MT5_RELOGIN_BUDGET_S`), or `interval` scaled by a mis-ported factor. The heal is still cancelled, so `cut_short` is True, elapsed is about 30 s (under 50), and every later assertion still holds: the distinct message, no `exc_class=`, and the counter at 1. The test is green on exactly the "silent cadence stretch" WR-06 exists to stop. It merely runs 30 s slower.

The sibling test at `:743-752` has the same flaw on a smaller scale. A loop that polls `SHUTDOWN` on a 2-4 s timer instead of waiting on the event passed `< 1.0` as RED and now passes `< 5.0` as GREEN.

**Fix:** Take the verdict from the value that decides the behaviour, not from the clock. Record the timeout the tick passes, and keep the cancellation record:

```python
seen_timeouts: list[float | None] = []
real_wait_for = asyncio.wait_for
async def _spy_wait_for(aw, timeout=None):
    seen_timeouts.append(timeout)
    return await real_wait_for(aw, timeout)
monkeypatch.setattr(monitor.asyncio, "wait_for", _spy_wait_for)  # or a namespace stand-in like _BackoffSleepSpy
...
assert cut_short and seen_timeouts and seen_timeouts[0] == cadence_s, (
    f"the heal was not cut off AT the cadence: wait_for timeout(s)={seen_timeouts}, cancelled={cut_short}"
)
```

Keep `elapsed < park_s / 2` only as a deadman. For the SHUTDOWN test, the structural form is that the loop awaits `SHUTDOWN.wait()` (the `:481-482` call). A `wait_for` spy can assert that the awaited timeout is `session_poll_interval_s()` and not a short poll.
