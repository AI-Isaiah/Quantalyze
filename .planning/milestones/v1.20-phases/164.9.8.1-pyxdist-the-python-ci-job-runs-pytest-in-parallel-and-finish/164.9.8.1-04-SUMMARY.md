| `tests/test_feedback_engine.py::test_lazy_import_not_triggered_at_module_load@shared_test_db` | gw1 | `subprocess.TimeoutExpired: ... timed out after 15 seconds` (the child was killed, return code -9) |

### Root cause (measured; this one is not caused by any change in plans 01-03 or the review fixes)

The test starts a clean interpreter with `subprocess.run([sys.executable, "-c", script], timeout=15)`. The script does `import routers.match` and exits 1 if `services.feedback_engine` got imported. The assertion is structural (does module import pull the module in), yet the test also carries a 15 s wall-clock bound on a cold interpreter running a heavy import chain. That is the same class of defect as the stopwatch races fixed in review rounds 1 and 2: a real-time bound whose purpose is a hang guard, but which is small enough to lose to CPU starvation.

Measurements, taken on the same box after the failure, still loaded by other sessions (load average 50 to 63, no lane work of mine running):

| Cold `import routers.match` in a clean interpreter | Wall |
|---|---|
| plain, 3 runs | 8.76 s, 11.59 s, 9.24 s |
| with the pytest-cov child-process environment variables set, 2 runs | 7.60 s, 7.27 s (I could not confirm that the child coverage hook engaged; no data file appeared, so treat this row as plain) |

So at a load of 50 to 63 the import already costs 7 to 12 s, which is half to four-fifths of the bound. The RED run began at a load average of 20 and ended near 59 (1-minute reading right after it), with 10 xdist workers, the lane's containers and other sessions' pytest runs on the same 10 cores; 15 s was exceeded. This is the only subprocess test with a bound that small: the other subprocess bounds in `analytics-service/tests` are 60 s (`test_compute_jobs_fencing.py`), 120 s (`test_mt5_outage_alert.py`), 180 s (`test_limiter_route_coverage.py`) and 300 s (`test_qstats_gate.py`, `test_limiter_stub_restore.py`, `test_xdist_group_is_real.py`). The 15 s bound dates from the commit that introduced the test (2026-04-19, `f89115cf3`). It is a latent flake that serial CI runs on a quiet 4-vCPU runner have not hit; 10 workers on a shared 10-core box make it reachable.

It is NOT a `routers.*` eviction, not a lane write from an ungrouped module, not the limiter-identity flake and not the fence flake. The test's pass or fail does not depend on the live database; it carries the group suffix only because the file mentions a sentinel string.

### Recommended fix (a new plan or an orchestrator decision under D-04; not done here)

The bound is not the property under test (the assertion is on the child's exit code), so the right shape is to make the bound a deadman, not a race: raise it to the 300 s the sibling subprocess tests use, or drop the real-time dependence entirely with a static check (parse `routers/match.py` with `ast` and assert that no module-level import reaches `services.feedback_engine`). D-04 forbids widening a bound that is itself the property; whether this counts is the orchestrator's and founder's call, and I have not made the change.
