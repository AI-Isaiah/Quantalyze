### The oracles, in assertion order

1. **`data-error-code`** on the rendered envelope equals the expected code. This is
   criterion 3's literal subject and it runs FIRST, because vitest aborts a case at its

## Deviations from Plan

### [Rule 2 — missing critical functionality] The plan's DOM assertion is not satisfiable on one surface, so a second channel was added rather than the row exempted

The plan specifies `expect(screen.getByText(WIZARD_ERROR_COPY[expectedCode].title))`.
MEASURED: `KNOWN_CSV_FINALIZE_CODES` is a `ReadonlySet<string>`, and four of its five
members (`CSV_FINALIZE_FAIL`, `CSV_INVALID_FORMAT`, `CSV_PERSIST_FAIL`,
`CSV_SESSION_REUSED`) have **no `WIZARD_ERROR_COPY` entry at all** — deliberately; that
roster's docblock says the codes travel *"on the wire in its OWN vocabulary"*, and
`CsvSubmitStep` branch 1 renders the route's curated per-arm sentence instead (the route's
`CSV_PERSIST_FAIL` sentence declines to claim *"Nothing was saved"*, which the generic entry
asserts).

Rather than exempt those rows from the headline oracle, the row carries a `titleChannel`
discriminator and the `wire-prose` rows assert that the SERVER's sentence reached the reader —
beside the same `data-error-code` and UNKNOWN-absence checks every other row makes. The
exemption is then **sized and named**: a dedicated case pins the branch-1 roster to exactly
those five codes and pins which four lack union copy, so a fifth member or a newly-copied
code reds instead of inheriting a quietly widened exemption.

### [Rule 3 — blocking] The plan's grep gate was tripped by the file's own prohibition prose

Writing "no `describe.skip` / `it.skip`" verbatim in the header made
`grep -c 'describe.skip\|it.skip'` print **2** while nothing was skipped — the file failed
the gate plan 10 will run on it. Reworded to spell the forms apart, using the idiom the repo
already carries at `wizardErrors.ts`'s `formatKeyError` (*"Spelled in prose, not in the
literal form the plan's grep gate counts"*). **Now prints 0.**

### [Rule 1 — bug in the plan's typing] `expectedCode` is `string`, not `WizardErrorCode`

Same measurement as above: casting the four non-union CSV codes to `WizardErrorCode` would
make the type assert something false and let `WIZARD_ERROR_COPY[code]` typecheck while
returning `undefined` at runtime. The cast is applied only where the value really is a union
member, at the copy lookups.

## Surfaces not rendered

⛔ **`keys/validate-and-encrypt` — the fifth locked surface — is NOT rendered, and the
blocker is a product fact, not a jsdom one.**

**The blocker, re-measured at HEAD 2026-09-06 by reading all three files:** the route has
exactly three consumers, and **none of them reads the response's `code` field.**

| Consumer | What it reads | Line evidence |
|---|---|---|
| `src/components/strategy/ApiKeyManager.tsx` | `err.error` | `throw new Error(err.error \|\| "Key validation failed")` |
| `src/components/strategy/StrategyForm.tsx` | `err.error` | `throw new Error(err.error \|\| "Key validation failed")` |
| `src/components/exchanges/AllocatorExchangeManager.tsx` | `result.error` | `setFormError(result.error ?? "Validation failed")` |

There is therefore **no code → `WIZARD_ERROR_COPY` render path on that surface at all**. A
render row could only be satisfied by feeding the expected title in as the wire prose and
reading it back out — a tautology, and precisely the proof-by-adjacent-signal that let
WIZFORM-02 be believed closed in Phase 153.

This is not a new discovery so much as the first time it has blocked something:
`KNOWN_VALIDATE_AND_ENCRYPT_CODES`' own docblock already states it (*"treat 'rostered' as
'typed and has copy', never as 'the user will see it'"*, measured 2026-08-24) and 164.2-05
re-measured it (*"VOCABULARY-only (validate-and-encrypt) … none of that route's three
consumers reads the code field"*). What is new is that criterion 3 asks for a RENDER, and
that roster has nothing to render.

**The exclusion is asserted, not narrated.** Two cases in the file:

- one walks the three consumers, confirms each still POSTs to the route, and asserts none
  reads `code` — with a failure message that says the red is **good news** and instructs the
  reader to add the surface to `SURFACES` with a real harness;
- one pins the consumer census at **3**, so a fourth poster cannot appear unmeasured.

⚠️ **Consequence for plan 10, stated because the plan states it:** *"plan 10's close is
conditioned on that section being ABSENT."* This section is present, so **WIZFORM-02 does not
close on this plan**, and the `GATED ON WIZFORM-02 CLOSING` marker in TODOS.md must not come
down on the strength of it. The remaining work is named debt that already exists — wire the
three consumers onto the code channel the way 161-10 wired the three dashboard dialogs — and
the day that lands, the assertion above reds and tells the next author to add the fifth
surface here.

⚠️ **The PROD row is still proven, on a different surface.** The 2026-08-25 reproduction is a
bare upstream 401; 164.2-05 closed it AT THE ROUTE (`UPSTREAM_STATUS_TO_SEAM_CODE`:
401/403 → `SEAM_MISCONFIGURED`). What a *wizard step* now receives for that failure is
`SEAM_MISCONFIGURED`, and the named row proves `connect-key` renders it as itself. The half
that is not proven is that the three dashboard consumers show it — because they cannot.
