- **Found during:** Task 2.

- **Commit:** `40f130ea`.

### `[Rule 1 — flake]` Date-granularity control fixtures moved from +2 days to +3

- **Found during:** Task 2, before writing.
- **Issue:** a `YYYY-MM-DD` value is read at UTC midnight, so "N days ahead" is
  really "between N−1 and N days ahead" depending on the hour the suite runs. A
  `+2`-day DATE fixture is only **1.0000…** days ahead at 23:59:59 UTC, landing
  on the one-day allowance boundary — a ~millisecond flake window per day, and a
  control that can flake is a control readers learn to ignore.
- **Fix:** `+3` for every date-granularity control (chip C-14, the badge's table
  control, the joint matrix's far-future row), with the reasoning in a comment at
  each site. The TIGHT bound is carried by the badge's instant-precision 25 h
  arm instead, so nothing was traded away.
- **Commit:** `40f130ea`.

### `[Deliberate no-op, measured]` `SyncBadge.tsx` was NOT modified

The plan's Task 1 action asked to find "wherever the SERIES sentence is chosen by
a `CLOCK_SKEW_TOLERANCE_MINUTES` comparison" and move it to the day allowance.

break the sync arm (`computedAt` +1 h would read "just now"). The file is
untouched, and `staler-of-two:206` ("the dot and the sentence never describe one
date two ways") plus the new `WR-06-UTC BOUND (upper)` arm are what keep that
conclusion honest rather than assumed.
