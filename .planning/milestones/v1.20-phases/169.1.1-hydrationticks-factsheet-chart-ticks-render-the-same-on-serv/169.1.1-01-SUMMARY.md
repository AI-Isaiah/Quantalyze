# Phase 169.1.1 Plan 01: Engine-independent chart ticks, tracer through TimeSeriesChart Summary

**A shared tick helper (`src/lib/chart-ticks.ts`) computes the power of ten as `Number("1e"+exp)` with the exponent from `toExponential()` and snaps near-anchor ticks to the anchor. The factsheet daily-returns chart now renders byte-identical y-axis markup under Node's and Chromium's power of ten, and its zero tick reads `+0.0%` on the baseline style. A server-render test that was red on the old code proves it.**

## Accomplishments

- `src/lib/chart-ticks.ts` is pure and calls no transcendental Math function. Its doc comment records three things: why the native power and log10 are not used, the one-ulp-below-a-power-of-ten edge (RESEARCH Finding 4), and the founder decision of 2026-10-02.
- `TimeSeriesChart.tsx` changes:
  - `niceLinearTicks` delegates to `niceStepValues(lo, hi, 5, 12, anchor)`. Its `hi <= lo` early return is byte-unchanged.
  - The log branch's candidate power of ten is now `pow10(d)`. The decade and exp lines are untouched.
  - `makeYTicks` takes `config.baseline`, and the `yTicks` memo depends on it.
  - `isBaseline` is now `Math.abs(t.value - config.baseline) <= yTickTol`. The `y-${value}` key and every stroke and font value are unchanged.
- SC-3 component test: it was red on the old code and is green after the fix.
- The node-env helper matrix includes a control arm. That arm runs the pre-fix algorithm and asserts that the Node and Chromium regimes give different arrays, so the suite can still fail after the old code is gone.

## Decisions Made

- I followed the founder's minimal construction exactly. I did not use index times step.
- `decimalExponent` checks for non-finite input and zero explicitly. Parsing `Infinity.toExponential()` gives `Infinity`, and the RESEARCH sketch's `|| 0` does not catch that. The plan pins 0.
- `niceStepValues` returns `[]` on non-finite bounds. The old loop would have produced a degenerate array there. Domains are finite in practice.
- Anchor-1 domain: on the plan's example `[0.9993, 1.0007]`, the anchor-0 call already yields exactly `1` at par, so "snaps to exactly 1" could not fail. I measured `[0.9989991, 1.0003027]` instead. There the anchor-0 tick at par is `0.9999999999999999` and the snap makes it `1`. The test now also asserts that the anchor-0 value is not 1.
