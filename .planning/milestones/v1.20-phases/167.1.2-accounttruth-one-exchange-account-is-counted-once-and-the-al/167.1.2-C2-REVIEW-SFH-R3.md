### SFH-R3-01 — high — one empty poll zeroes the account, and now the whole book, permanently

**Location:** `analytics-service/services/equity_reconstruction.py:2064-2130` (`_polled_empty_since`),
`:3650-3654` (`book_emptied`), `:3729-3737` (the WARNING). The proof's input comes from
`analytics-service/services/allocator_positions.py:566-600`.

**What the proof actually proves.** `row_count` is `len(holdings)` (`persist_allocator_holdings`,
`allocator_positions.py:1503-1537`). The poll builds holdings from spot `balance["total"]`
(`:570`, qty > 0 only) plus open derivative positions. A `complete` poll with 0 rows therefore
means "nothing this poll reads", and in each of the following cases the account still holds
money:

- **The documented parse-empty class, in the same module** (`:572-590`). A funded Bybit UTA
  account whose CCXT `total` "can be empty/zero". The fix there was a fallback. When that fallback
  misses (shape drift, a venue without one), `non_zero` is empty, `_fetch_spot_rows` returns `[]`
  with **no warning** (`:599-600`), the poll ends `complete` with 0 rows, and the account is
  "proven empty".
- **Deribit, by design** (`:566`). Spot is skipped before any network call, so a Deribit account
  with no open positions always polls `complete` with 0 rows. On its own this is low: the legacy
  series never held Deribit collateral. It is the structural example: zero rows plus `complete`
  cannot tell an empty account from an account the poll cannot see.
- **A flat derivatives account** whose margin sits in a wallet the spot read does not cover.

**What round 2 changed.**
- Round 1 already zeroed such an account inside a partial book.
- Round 2 (R2-CR-01) made the proof **non-expiring**. It now lives on `audit_log` (2 years hot),
  where round 1's rested on `compute_jobs` (30 days).
- Round 2 (SFH-R2-02) now **writes the whole-book case as an explicit $0 row**. First-writer-wins
  (`ON CONFLICT DO NOTHING`) makes that day's $0 permanent, even if the next poll that day reads
  the money again.

**Measured** (bybit key with 200,000 USDT two days ago, yesterday's snapshot at 200,000, and one
clean, empty poll event yesterday):

```
TRANSIENT today [0.0] reason book_emptied levels ['INFO', 'WARNING']
DERIBIT   today [(0.0, {})] reason book_emptied emptied 1 levels ['INFO', 'WARNING']
```

**Why the signal is not enough.** The WARNING says "every counted account … is proven empty",
which is false in each case above. It is also only a WARNING. This same fix round established
(the SFH-07 remainder) that `sentry_init.py` keeps the default `LoggingIntegration`, so a WARNING
reaches Sentry as a breadcrumb only, and answered the derive refusal with `capture_message`. The
`book_emptied` zero-write did not get the same treatment. Within one fix round, the derive's
refusal pages and the refresh's $0 write does not.

**Who sees the $0 today.** The GDPR export (raw rows) and any future reader of the legacy store.
`reconstruct_symbol_returns`, `extract_symbol_value_at` and the compare adapter skip zeros, and
/compare is held at "rebuilding" (D-13), so no dashboard number moves today. I rate this HIGH as
a permanent false row in a persisted equity store, stated with a proof claim it does not have. If
the orchestrator applies the round-2 yardstick strictly (a wrong number **on screen**), it is
MEDIUM. The fix is small either way.

**Recommended fix, in order.**
1. **Corroborate before zeroing.** Each ccxt key's per-key derive already persists an
   independent live-equity read: `key_inputs:<api_key_id>` has `anchor_usd` and
   `anchor_null_reason`, from `fetch_account_equity_and_upnl_usd` (`job_worker.py:5570-5625`).
   Admit the proof only when that read also says there is no material capital: `anchor_null_reason`
   is `dust` or `nonpositive`, or `anchor_usd <= DUST_NAV_FLOOR`, at an `anchor_asof` on or after
   the proving event. A clean, empty poll beside a material anchor is a contradiction, not a proof.
   In that case keep the D-07 carry and count it (for example `empty_poll_contradicted`).
2. **Capture the $0 write.** Call `sentry_sdk.capture_message` for `book_emptied`, at level
   `warning`, with a static message and counts only, exactly as `job_worker.py`'s refusal capture
   does.
3. **Add `deribit` to the venues that cannot prove emptiness**, beside `NON_CCXT_VENUES` in
   `_polled_empty_since`. Its zero-row poll proves "no open positions".
4. Optional: require the **newest** in-window event of the group to be the clean, empty one. At
   present an older clean read still proves after a newer `complete_with_warnings`.

Pin 1 with a test: a clean, empty event plus a material `anchor_usd` writes no $0 and carries.

### SFH-R3-02 — medium — the stitch drops a flow that only the counted key lists

**Location:** `analytics-service/services/allocator_equity_derive.py:357`
(`if index > 0 and flow_day < own_first: continue`).

**Failure scenario.** Every flow of the counted (last) member dated before its own first return
day is dropped. The rule assumes the older member's list holds every transfer on the days it owns.
It does not hold when the older key's flow crawl missed a transfer that the newer key's crawl
lists. Two ways that can happen:
- the older key's last successful derive ran before a late-booked transfer appeared on the venue;
- the two crawls have different depths.

The deposit then vanishes from both lists. The replay reads it as a return, and the curve stays
`is_trustworthy: true` under the benign `shared_account_history_stitched` flag.

**Measured** (pure call: H returns for May with no flows; M returns from June 1, listing a
May 15 deposit of 1000):

```
stitched days 34 flows []
```

**Test gap.** `test_a_stitched_account_takes_each_days_flows_from_the_key_that_owns_the_day`
lists the May deposit in **both** keys' flows. No test has a flow present only in the counted
key's list on a day the older key owns. How often the precondition occurs in production is
**unmeasured**. The consequence is a silent wrong number in a "ready" book.

**Recommended fix.** Before accepting a stitch, check each flow the counted key lists before
`kept_first` against a same-day flow in the owning member's list. If one has no counterpart,
refuse the join (`stitch_shared_account` returns `None`), so the account falls to the BLOCKING
`shared_account_history_truncated`. Do not merge the two lists: the same transfer priced at two
crawl times can differ, and a merge would double it. Add the test above.

### SFH-R3-03 — medium — an account left out under `identity_unknown_not_carried` has only a counter

**Location:** `analytics-service/services/equity_reconstruction.py:1977-1980`, audited at
`:3672`/`:3754` and logged in the INFO line at `:3757`.

**Failure scenario.**
- The rule applies to a group with no working key, no `venue_account_id` on any key, and a venue
  that stamps ids.
- Such an account is left out of the day's row whenever it has no rows today. That is the
  orchestrator's recorded trade-off, and main's today-only read behaved the same way.
- First-writer-wins then makes the short total permanent for that day.
- The fixer's report says "the audit counts it, so the drop is not silent". That is the same claim
  round 1 made for the benign flags, and SFH-R2-06 already ruled that audit metadata plus INFO is
  not a signal: nothing reads it, and INFO pages nobody.

**Measured** (a working okx key with 1000 today, plus a failing, never-stamped bybit key with
50,000 yesterday):

```
IDUNK today [1000.0] iu 1 warnings>=WARNING []
```

**What the user sees.** My Allocation holds the curve under `key_not_syncing` and names the key
(`identityStillPending` and `failingToSync`, `queries.ts:3834-3855`), so the dashboard is not
silent. The persisted legacy row is short by the account, and no log line above INFO says so.

**Recommended fix.** Log at WARNING when `identity_unknown_not_carried > 0`, with counts only.
Better, capture it once per refresh, as SFH-R3-01 recommends for `book_emptied`. Fold in the open
SFH-R2-06 half: WARNING on a partial `emptied_accounts > 0`, and on `never_polled_keys > 0` when
the book already has snapshots.

### SFH-R3-04 — medium (user-facing) — the two new blocking states say "did not pass its checks"

**Location:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:69-70`;
`derivedPayloadRejection` in `src/lib/queries.ts` collapses every writer verdict into
`untrustworthy`.

**Failure scenario.**
- `shared_account_no_working_key` and `shared_account_history_truncated` now make the v2 row
  untrustworthy, so the reader shows `derivation_rejected`: "The latest rebuild of your history
  did not pass its checks, so it is not shown."
- The unlock for both is "fix the failing key on the Exchanges page". The line names neither the
  cause nor that action.
- Fixer A handed this off as a copy call. Fixer B's report predates fixer A's (13:10 vs 13:25) and
  records only that the state reaches `derivation_rejected`. Nobody took it.
- The same line also shows during the ordinary new-key backfill: a counted key with `key_inputs`
  and no returns is `DROPPED_KEY`. There it tells the owner that something failed when it will
  heal on its own. Fixer B recorded this.
- **Inconsistency.** A SINGLE failing key with a known id flat-carries inside a **"ready"** book,
  which is the pre-existing residual. Two failing keys on one account now hide the whole history.
  The owner sees opposite outcomes for the same kind of problem (a dead account's frozen capital).

**Recommended fix.** Have the reader read the payload's `degrade_reasons` tokens, which are
already persisted, when `is_trustworthy` is false:
- map `shared_account_no_working_key` and `shared_account_history_truncated` to a line that
  mirrors `key_not_syncing` ("An account's keys are not syncing … Check them on the Exchanges
  page.");
- map a lone `dropped_key` to a backfill wait;
- keep "did not pass its checks" for everything else.

Pin each mapping with a render test. Record the single-key inconsistency as a founder call, or
route it to a phase. It is user-facing.

### SFH-R3-05 — low — a silent skip in the stitch loop, unreachable today

**Location:** `analytics-service/services/job_worker.py:10671-10672`.

```python
if kept_series is None:
    continue  # the kept key's returns vanished between the two reads
```

**Verified unreachable.**
- `first_return_day` and `returns_by_key` are built from the **same single** `csv_daily_returns`
  read (`csv_rows`, `:10374`). There is no second read, so the comment is false.
- A kept key with a `first_return_day` has at least one row with a non-null key and date, so it is
  in `_grouped`.
- The kept key is in `counted_ids`: it is eligible and never in `excluded_shared`, since each key
  belongs to exactly one group.

If a future edit made the branch reachable, the sources would stay excluded and unstitched
**without** incrementing `truncated_accounts`, so the history would be dropped with no reason
raised: the exact SFH-R2-03 shape. **Fix:** count it as truncated (`truncated_accounts += 1`), or
`assert`, and correct the comment.

### SFH-R3-06 — low — `flow_drop` can be masked, so cut flows can be stitched

**Location:** the gate at `job_worker.py:10632`; the epilogue's reason chain at `:5602-5611`.

The epilogue stamps one `anchor_null_reason`, and `flow_drop` is the **last** `elif`. A key whose
flows were cut as non-finite **and** whose balance read failed (or was non-finite, non-positive
or dust) is stamped `balance_error` (or the matching earlier token). The stitch gate refuses only
`!= "flow_drop"`, so it admits those cut flows for the days the older key owns, and they
mis-level those days in a trustworthy stitched curve. This needs non-finite flows, which the code
calls corruption, so it is rare. **Fix:** persist `skipped_nonfinite_flows` in the `key_inputs`
payload, independent of the anchor reason, and gate the stitch on it.
