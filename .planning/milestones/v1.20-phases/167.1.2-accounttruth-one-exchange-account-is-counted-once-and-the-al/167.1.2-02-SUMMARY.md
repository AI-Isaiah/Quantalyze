# Phase 167.1.2 Plan 02: capture the venue account id at connect Summary

OKX, Bybit, Binance and Deribit keys now carry their exchange account id from validation to
`api_keys.venue_account_id`. The id is read from responses the validator already fetches: OKX
`account/config` `data[0].uid`, Bybit `query-api` `result.userID`, the Binance spot balance `info.uid`,
and the Deribit `fetch_balance({"extended": True})` `info.id`. Both connect routes (Add Key and the
wizard) stamp it. The existing venue-identity unique index and its existing 23505 mappings then refuse
a second live key on the same account. No new index, request or permission was added, and the id never
appears in a response body or log line.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] A ccxt uid would have been logged on the 23505 path**
- **Found during:** Task 1
- **Issue:** The persist arm scrubbed only `[api_key, api_secret, passphrase]` from the collision log and
  from the generic-failure log and Sentry capture. Postgres' DETAIL echoes `venue_account_id`. For MT5 that
  value equals `api_key`, but for a ccxt key it is the venue uid, which would have reached the logs
  (threat T-167.1.2-11).
- **Fix:** Added `venueAccountId` to both scrub lists. Test (b) carries the uid in the DETAIL and asserts
  the console line does not contain it. The neuter was observed RED.
- **Files modified:** src/app/api/keys/validate-and-encrypt/route.ts and its test
- **Commit:** c8e1c6cea

**2. [Rule 3 - Blocking] Two ccxt success-shape pins outside the plan's file list**
- **Found during:** Task 1
- **Issue:** `test_ccxt_exchange_still_uses_create_exchange_path` in test_sfox_validate.py and in
  test_mt5_validate.py pinned the ccxt return as exactly `{"valid", "read_only"}`. The plan changes that
  shape on purpose.
- **Fix:** Both tests now expect `"venue_account_id": None`, with a comment explaining why.
- **Commit:** c8e1c6cea

**3. [Rule 3 - Blocking] The Deribit scope suite's exchange double did not accept `params`**
- **Found during:** Task 2 (GREEN)
- **Issue:** `_FakeDeribit.fetch_balance(self)` took no arguments, while ccxt's real `fetch_balance(params={})`
  does. Once the validator passed `{"extended": True}`, two DRB-03 tests hit a TypeError.
- **Fix:** The double now takes `params=None`, matching the real signature. No assertion changed.
- **Files modified:** analytics-service/tests/test_deribit_scope_validation.py
- **Commit:** f1bea2a13

**4. [Scope] Extra tests beyond the plan's list**
- test_key_permissions.py gained okx and bybit detector cases. These are the wiring oracles for
  `account_id`.
- create-with-key gained a case asserting the RPC error log is scrubbed of the uid.

**Total deviations:** 3 auto-fixed (1 security, 2 blocking), plus additive tests. **Impact:** no scope
change. The security fix is the plan's own threat-register mitigation, applied at a sink the plan did not
name.

## Known residuals (not fixed, stated)

- `src/app/api/keys/[id]/rotate-secret/route.ts` still answers the old "You already have a connected key
  for this account." for its own 23505. That route is MT5-only (secret rotation), so the sentence is true
  there. It is out of scope and D-10 keeps MT5 behaviour unchanged.
- A ccxt id is only known after validation, so the wizard has no pre-validate fence for it. A colliding
  ccxt key spends one encrypt round-trip before the RPC's index refuses it, and the race arm then answers.
  The plan marked the pre-RPC `resolveByVenueIdentity` call optional. It was not added.
- The zod bound `.max(128)` means a venue returning an id longer than 128 characters fails the whole
  validate parse. No venue documents ids that long.
- The CR-01 provenance residual carries over: the stored id is "what the server read from this
  credential", not "what the venue attested".
