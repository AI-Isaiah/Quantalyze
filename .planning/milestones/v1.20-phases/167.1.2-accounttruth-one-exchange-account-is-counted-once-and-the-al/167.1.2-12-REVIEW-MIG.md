## Findings

### MIG-01 (LOW): the idempotency-key claim in the header and the COMMENT is not what deduplicates, and the `unique_violation` handler cannot fire

**Evidence.** The header (edit (3)) says the reconstruct is enqueued "with the idempotency key `reconstruct-alloc-<key>-initial`, the one `request_allocator_holdings_sync` uses, so the cron path and the user path name one job; a unique_violation is swallowed as the RPC does". The `COMMENT ON FUNCTION` repeats the idempotency-key framing. Two facts in the schema disagree:

1. `compute_jobs.idempotency_key` is not enforced by the database. Its own column COMMENT in `supabase/schema/baseline.sql` says "NOT enforced at the DB level at all", and no unique index names the column. What deduplicates the cron path against the user path is the partial unique index `compute_jobs_one_inflight_reconstruct_per_api_key` (and `compute_jobs_one_inflight_per_kind_api_key`), and only while a row is `pending`, `running` or `done_pending_children`. After that, the dedupe is this migration's own any-status `NOT EXISTS` on `compute_jobs`, plus the worker's `_api_key_already_reconstructed`. The shared key string is a correlation label; it does not make two enqueues one job.
2. The latest `_enqueue_compute_job_internal` (the api-key-scoped branch that `enqueue_compute_job` routes to) pre-checks for an in-flight row and then inserts with `ON CONFLICT DO NOTHING`, so it never raises `unique_violation`. The `EXCEPTION WHEN unique_violation THEN NULL` block around each `enqueue_compute_job` call is unreachable.

This shape is inherited verbatim from 075's refresh loop, so it is pre-existing and not introduced here. Behaviour is correct: test arm Z2 asserts the key string, and the any-status gate prevents a second reconstruct. The risk is only that a future editor relies on the idempotency key for dedupe.

**Fix.** Before merge (the file is not yet applied, so editing it is allowed), reword the header's edit (3) and the `COMMENT ON FUNCTION` to say the key string matches the RPC's for correlation, and that dedupe comes from `compute_jobs_one_inflight_reconstruct_per_api_key` while in flight plus the any-status `NOT EXISTS` gate. Optionally say the `unique_violation` handler is kept for parity with 075 and is unreachable today. No code change is required.

### MIG-02 (INFO): a lost enqueue race raises `serialization_failure`, which aborts the whole daily run

**Evidence.** When `_enqueue_compute_job_internal`'s `ON CONFLICT DO NOTHING` inserts nothing and the re-select finds no in-flight row (the winner already went terminal), it raises `serialization_failure` (40001). The per-call handler catches only `unique_violation`, so the outer `EXCEPTION WHEN OTHERS` unlocks the advisory lock and re-raises. The whole call rolls back, both the bootstrap and the refresh, for every tenant that day. This is pre-existing in 075's refresh loop; the new bootstrap loop adds a second call site. Hitting it needs a concurrent enqueue for the same key whose job then finishes within the gap between the conflicting insert and the re-select, and the only other reconstruct enqueuer is a user-initiated sync, so the probability is negligible.

**Fix.** Optional. Catch `serialization_failure` beside `unique_violation` in both per-call handlers so one lost race skips one key and not the day. Not required for this merge.

### MIG-03 (INFO): the refresh population on snapshot-bearing books now drops revoked keys

**Evidence.** Edit (1) adds `ak.sync_status IS DISTINCT FROM 'revoked'` to the refresh loop, so a revoked key on a book that already has snapshots no longer gets a `refresh_allocator_equity_daily` job. That is a behaviour change for the existing population, not only for zero-snapshot books. It is intended: D-17 in `167.1.2-CONTEXT.md` says "The existing population (books that already have snapshots) is unchanged apart from dropping revoked keys", test arm R pins the exclusion and arm E pins the unchanged remainder, and the canonical eligible predicate used by sibling fan-outs (for example `enqueue_derive_broker_dailies_for_allocator_keys`, per its COMMENT) already carries this conjunct.

**Fix.** None. Recorded so it reads as reviewed and not missed.

### MIG-04 (INFO): the any-status reconstruct lookup has no full index on `compute_jobs (api_key_id, kind)`

**Evidence.** The four `NOT EXISTS (SELECT 1 FROM compute_jobs … WHERE api_key_id = … AND kind = 'reconstruct_allocator_history')` probes match rows in ANY status. The only indexes on `compute_jobs` that lead with `api_key_id` are partial on the in-flight statuses (`compute_jobs_one_inflight_per_kind_api_key`, `compute_jobs_one_inflight_reconstruct_per_api_key`, `compute_jobs_one_inflight_refresh_equity_per_api_key`), so a `done` or `failed_final` row is found by a scan. `compute_jobs` is bounded by the `retention_compute_jobs_done` (30 days) and `retention_compute_jobs_failed` (90 days) crons, and `api_keys` is small, so this is a once-a-day planner cost well below the 30-minute handler budget.

**Fix.** None now. If `compute_jobs` grows by orders of magnitude, add a plain `(api_key_id, kind)` index in its own migration (CONCURRENTLY, split per invariant 5).
