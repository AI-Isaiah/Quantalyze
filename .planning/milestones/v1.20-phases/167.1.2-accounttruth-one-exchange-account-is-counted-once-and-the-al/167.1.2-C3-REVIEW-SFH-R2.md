## (2) New findings

### SFH-C3R2-01: MEDIUM. The paginated returns read can skip another key's row when a dailies write lands between pages, and the compose keeps the curve trustworthy

**Location.**
- `analytics-service/services/job_worker.py:10388-10398` (the read).
- `services/db.py` `paginated_select`, the `for page in range(hard_cap_pages)`
  loop: one `.range(start, end).execute()` per page, each a separate request with
  no shared snapshot.
- The writer: `job_worker.py:5975-6005`, `_reconcile_span_delete` and then chunked
  upserts, which are separate statements.

**The issue.** The total order stops duplicates and skips only while the table
stays still. Offset pagination across separate PostgREST requests does not
guarantee that. Two things combine to make this likely:

- The key-mode `derive_broker_dailies` job deletes a key's `[span_start,
  span_end]` rows and upserts them back, in several statements.
- It runs per key on the same daily cron fan-out as the compose for the same
  allocator. The two jobs use different inflight indexes, per-api_key and
  per-allocator, so nothing serialises them.

**Failing scenario.**
1. The allocator has keys K1 < K2 < K3 in `api_key_id` order, with 2804 rows. The
   compose reads page 1, rows 0-999, which end inside K2's series.
2. K1's dailies job now runs `_reconcile_span_delete` over its last 30 days.
   Every row after them shifts left by 30.
3. The compose reads page 2, rows 1000-1999. That page now starts 30 rows later
   in K2's series, so K2 loses 30 consecutive days at the page boundary and no
   error is raised. K1's rows are unaffected.
4. In `portfolio_returns`, each missing K2 day is a key-day inside coverage with no
   level. It is carried with `r = 0` and counted as
   `missing_return_inside_coverage`. `allocator_equity_compose.py:62-65` says this
   is "Reported, not blocking", so `is_trustworthy` stays true.
5. The upserted `equity_curve` shows a flat 30-day stretch where K2 really moved.

If the page is read after K1's upsert instead, the rows shift right and a row is
DUPLICATED. That case is harmless: `day_map` is a dict and the values are
identical.

**Why it does not heal quickly.** K1's epilogue then enqueues
`derive_allocator_equity`. The compose is still `running`, and
`compute_jobs_one_inflight_per_kind_allocator` covers `pending`, `running` and
`done_pending_children` (`baseline.sql:13290`). So the idempotent enqueue returns
the running job's id, and no fresh compose is queued. The wrong curve stays until
the next dailies write for any of the allocator's keys, which is usually the next
daily cron.

**How it compares with before the fix.** A single unpaginated read had a
mid-write window too, and SFH-R3-07 dropped about 1800 arbitrary rows on every
run. This fix is a large net improvement, and the finding is a residual.
- The new part: the damage lands on a key that was NOT being written, K2 in the
  scenario above.
- The mitigating part: the race needs an allocator with more than 1000 rows and a
  write during the few requests between pages.

**Hidden error.** A concurrent-write skip becomes a trustworthy curve that has a
silent flat segment.

**Recommendation (any one closes it).**
- Read per key: loop `paginated_select(... .eq("api_key_id", k), order_by=(("date", False), ("id", False)))`
  over the ids in `key_rows` from `_load_keys`, which are known before the read,
  stitch-source candidates included. Do not loop over `counted_ids`: that set is
  derived FROM this read, through `first_return_day` and the stitch.
  A shift then needs a write to the SAME key during its own read. That is the
  pre-existing mid-write window of that key's own dailies job, not new
  cross-key damage.
- Or ask for `count="exact"` on the first page and compare it with `len(rows)`
  after the drain. On a mismatch, raise a transient error so the job retries on a
  settled table.
- Or treat a `missing_return_inside_coverage` count greater than 0 on a key whose
  stored rows are dense as blocking. That is a larger behaviour change; I do not
  prefer it.

**Class note.** `analytics_runner.py:1638` uses the same helper with the same
offset semantics. That is a strategy-scoped series with a single writer per
strategy, so the cross-key version of this race does not apply there.

### SFH-C3R2-02: INFO. The warm-up count and its threshold are consistent for every state the HEAD writer can produce

**Location:** `AllocationDashboardV2.tsx:236-259` (the JSDoc known-limit) and
`:271-278` (the copy and the count).

**What I checked.** The builder's condition is on returns
(`dailyReturns.length < 2`), while the note counts curve days. The two could
disagree whenever a trustworthy curve holds fewer than `days - 1` returns. I tried
the one path that could produce that, a disjoint rotation seam: on the handoff day
no key has a level on both `t-1` and `t`, so `portfolio_returns` skips that day
as the benign `skipped_nonpositive_denominator`.

**Why the HEAD writer does not reach it.** The key-mode dailies job refuses a key
with fewer than 2 interpretable days (`job_worker.py:5701`,
`int(returns.notna().sum()) < 2`), so it writes no rows for such a key. That gives
three consequences:
- Every key that reaches the compose has at least 2 level days, so each key
  contributes at least one return by itself.
- Two disjoint keys give a curve of at least 4 days and at least 2 returns, since
  the seam skips exactly one day. The builder accepts that, and the panels render.
- One key gives `days - 1` returns. So the only state that is ready while the
  builder returns null is a 2-day curve with 1 return. There the note reads "…at
  least three days… 2 days of blended equity history so far". That is
  consistent.

Fix A's statement that "nobody has shown this state can be reached" stands.

**The residual is Fix C's unmeasured one.** A `csv_daily_returns` key row written
before the `< 2` gate existed could still produce a single-row key. Keep it routed
with IN-05. No change is owed in C3.

### SFH-C3R2-03: LOW. `shared_account_history_truncated` is classed `rebuilding`, so the Scenario says "being rebuilt" for a hold the Overview says nothing heals in this release

**Location:** `EquityHistoryRebuilding.tsx:73` (the class entry). Compare

**Issue.** The class comment at `:52-62` says "the generic 'being rebuilt' copy is

day until a code change. The owner is told a process is running when nothing is.
No action is available either way, so waiting costs the owner nothing. That is why

**Ownership.** My round-1 recommendation listed three passive reasons and never
classed this eighth member. The fixer classed it without guidance. This is my gap,
not the fixer's.

**Recommendation.** Add a fourth class, `held`, with Scenario copy such as "Your
book's own history is on hold, so the comparison with your current book is not
shown. The Overview says why." The alternative is to keep `rebuilding` and
correct the class comment so it no longer claims the copy is true for every
member. Either way, the test's literal class table must follow.

### SFH-C3R2-X1: HIGH (CRITICAL if a PROD count confirms it). The dashboard's per-key `csv_daily_returns` read silently drops the newest rows past 1000

**Location.**
- `src/lib/queries.ts:4433-4448`:
  `.from("csv_daily_returns").select("api_key_id, date, daily_return").eq("allocator_id", userId).gte("date", <730 days ago>).order("date", { ascending: true }).limit(20000)`.
- `:4686`: `assertOk` catches errors only, not truncation.
- `:4877-4883`: feeds `buildPerKeyReturnsByApiKeyId`. Nothing in between
  paginates.

**Issue.** This is SFH-R3-07's twin on the display side.
- PostgREST applies its max-rows cap whatever limit the client asks for; the
  `paginated_select` docstring in `services/db.py` states that behaviour.
- The PROD evidence is the measurement Fix C cited: an unbounded select returned
  exactly 1000 rows from a 7351-row table. On the hosted project the cap is an API
  setting. `supabase/config.toml:18` (`max_rows = 1000`) configures the LOCAL
  stack only, so editing that file fixes nothing in PROD.
- The comment above the read claims that `.limit(20000)` is a "SAFETY CEILING"
  that does not truncate "for any realistic key count". That claim is false under
  the cap.
- Because the read sorts by date ascending across all keys, the rows it loses
  are the most recent ones.

**Consumers.** The truncated series reaches:
- the Phase 36 per-key live baseline (the curve shape and KPIs, per the comment
  at `:4864-4876`);
- `ScenarioComposer.tsx:2912`;
- `scenario-adapter.ts:146`;
- `scenario-compare.ts:188`;
- the Scenario's `bookEntryGateSatisfied`.

**Failing scenario.**
1. The 2804-row allocator (orchestrator's PROD reading, 2026-09-29) has, say,
   1600 rows inside the 730-day window.
2. The read returns the oldest 1000 of them.
3. Each key's series ends months before today.
4. The Scenario's per-key blend and the live baseline are computed on a stale
   window and shown as current.
5. A key whose rows all fall after the cutoff has no series. The book-entry gate
   then treats it as having no data yet and forces blank mode.

No error is raised and no log line is written.

**Why it is not a C3 finding.** It is untouched by this diff. Fix D's census said
explicitly that TypeScript-side and other `csv_daily_returns` access was not
checked, and round 1 scoped itself to the C3 files.

**Recommendation for the orchestrator.**
- **Measure first.** Count this allocator's rows inside the 730-day window on PROD
  (read-only). Over 1000 confirms live truncation.
- **Fix.** Page with `.range()` under a total order `(date, api_key_id, id)`, or
  read per key. Then assert that the page count reached a short page.
- **Route.** Book it as data-integrity and user-facing, in a phase and not only in
  TODOS.
