# 167.1.2 C4 — silent-failure review (plans 09 and 15)

Every finding was verified at the HEAD above by reading the file, not the diff hunk. Line numbers
are HEAD line numbers. Nothing was measured on a database; each scenario is traced through code.

## HIGH

### SFH-C4-01 — Open Positions still shows a closed position across a key rotation (plan 15, D-16)

- **Location:** `src/lib/queries.ts:4183-4189` (collapse keyed by `holdingScopeKey`, no `api_key_id`),
  `src/lib/latest-holdings-per-key.ts` (key set includes departed keys, by D-16),
  `src/app/(dashboard)/allocations/HoldingsTabPanel.tsx:226-249` (row status from `sync_status` only).
- **Scenario:** the owner rotates a key on one Binance account. Old key D is disconnected on
  2026-09-01 (its last poll, 2026-08-31, holds BTC-PERP). New key N on the same account polls daily.
  On 2026-09-10 the account closes BTC-PERP. `latestHoldingsPerKey` keeps N's rows at 2026-09-29
  (no BTC-PERP) and D's rows at 2026-08-31 (BTC-PERP). The triple-key collapse has one candidate for
  `binance:BTC-PERP:derivative`, D's row, and keeps it. `openPositionRows` renders it with
  D's own `sync_status` (`disconnect_allocator_api_key` sets only `disconnected_at`, so it stays
  `complete`; the client stamps `idle` optimistically). Neither value carries a chip, and the row
  carries no `asof`. The same applies to every position closed between D's last poll and N's
  first poll: it renders forever.
- **Hidden path:** D-16's success criterion ("a position a key closed before its latest poll leaves
  holdingsSummary") holds within ONE key. Across keys that read one account, a departed key's last
  poll outlives the live key's close. Before D-16 the same symbol showed N's own stale row; after it,
  D's older row. The defect changed source, it did not go away, and rotation is exactly the departed
  case plan 09 exists for.
- **User impact:** a closed perp shows as open, with a stale mark and uPnL, on the page the owner
  reads positions from. The summary partitions route D's dollars to `excludedNotConnected`, so the
  table and the disclosure disagree on the same page.
- **Recommendation:** decide per row, not per triple. Either drop a departed key's rows when a live
  key reads the same account (`accountIdentityTokens` is now in TS and is the account rule plans 09
  and the derive share), or collapse by `(api_key_id, triple)` and label departed-key rows with
  their key's state and `asof`. Add a test with a departed and a live key on one account where the
  live key closed a symbol the departed key held.

### SFH-C4-02 — A key that closes its LAST position keeps showing it forever (plan 15, D-16; Deribit in particular)

- **Location:** `analytics-service/services/allocator_positions.py:566-567` (Deribit spot returns
  `[]` before any call), `:1518-1519` (`persist_allocator_holdings` writes nothing for an empty
  list), `src/lib/latest-holdings-per-key.ts:111-119` (latest `asof` is the newest row that exists).
- **Scenario:** a Deribit key holds options that all expire on 2026-09-26. Deribit spot is deferred,
  so the 2026-09-27 poll returns zero rows and persists nothing. The key's latest `asof` stays
  2026-09-26, and `fetchLatestHoldingsPerKey` returns the expired options as the key's current
  positions on every later day. The same holds for any account whose poll returns no rows at all
  (an emptied account on any venue).
- **Hidden path:** the per-key rule reads "the key's rows at its own latest asof", and a poll that
  measured "nothing" writes no asof. MT5 already met this exact class and fixed it by emitting a
  floored `$0` row (`allocator_positions.py:1054-1060`: "emitting nothing froze the last POSITIVE
  equity in place forever"). The ccxt and Deribit paths were not given the same treatment, and
  D-16 docblock says "a quiet key ... still shows its last poll, never flat", which is true only
  when "quiet" means "did not poll".
- **User impact:** expired or closed Deribit positions stay in Open Positions indefinitely with no
  date or warning. Not a regression (the pre-D-16 collapse did the same), but it is the defect
  item 8 names and SC-8 claims closed.
- **Recommendation:** record that a poll succeeded with zero rows (a per-key poll marker, or a
  sentinel row as MT5 does), and make the per-key read treat a newer empty poll as "no positions".
  `_fetch_derivative_rows` (`allocator_positions.py:650-680`) returns `[]` for zero positions with
  no placeholder, confirmed at HEAD. `api_keys.last_sync_at` is NOT a usable substitute marker: the
  poll's success arm writes it (`job_worker.py:9426`), but it is also the trades cursor advanced by
  sync (`job_worker.py:2040`). Until a real marker exists, do not claim SC-8 for a key whose poll
  can return nothing; say so in the PR text.

### SFH-C4-03 — Update password on a DISCONNECTED MT5 key silently erases the owner's history choice (plan 09)

- **Location:** `src/app/api/keys/[id]/rotate-secret/route.ts:498` (`history_inclusion: null`
  written unconditionally), `:232` (the pre-read selects no `disconnected_at`),
  `src/components/exchanges/AllocatorExchangeManager.tsx:1423-1430` (the disconnected MT5 card
  offers "Update password").
- **Scenario:** the owner disconnects MT5 key K (known account) and switches its history OFF
  (`exclude`), because it was a test account. Later, on the same Disconnected card, the owner clicks
  "Update password" to prepare a reconnect. The route writes `sync_status = 'idle'` and
  `history_inclusion = NULL`, and by design (WR-03) it does not touch `disconnected_at`, so K is
  still departed. The default rule now applies: K is included again. The next compose puts the test
  account's history back into the book. The card flips from "you excluded it" to "History included
  until …" on the next load, with no notice. The mirror case (an unknown-account key the owner
  included) silently drops out.
- **Hidden path:** the reset was added because this route is how a REVOKED key returns to live, and
  the column COMMENT binds "every path that returns a departed key to live". A disconnected key
  does not return to live here, so the reset is outside that contract. The new test
  (`route.test.ts` "resets history_inclusion to NULL") pins the unconditional write and would pass
  with the bug.
- **User impact:** an explicit data decision the owner made is discarded without a word, and the
  book's contents change on the next recompose.
- **Recommendation:** add `disconnected_at` (and `is_active`) to the pre-read at `:232` and write
  `history_inclusion: null` only when the update actually makes the key live (not disconnected,
  active). Add the disconnected-MT5 arm to the route test, asserting the payload does NOT carry
  `history_inclusion`.

### SFH-C4-04 — "Ready" book silently missing a departed account's history (`departed_history_unavailable` is benign and unread)

- **Location:** `analytics-service/services/job_worker.py:11236-11255` (the key is removed from the
  compose, WARNING log only), `:11310` (benign token), `src/lib/queries.ts:3641-3664` and
  `extractTrustworthyDerivedSeries` (the reader reads `is_trustworthy`, `curve`, `returns`,
  `version`; no reader in `src/` reads `flags`; `grep -rn departed_history_unavailable src` finds
  only a comment in `departed-history.ts`).
- **Scenario:** every key that departed before C4 deploys lost its `key_inputs` row to the old
  orphan cleanup on its allocator's next compose (plan 09 SUMMARY, Known limits, first bullet). On
  the first C4 compose each such key that the D-09 rule includes lands in `departed_unavailable`,
  is dropped, and the curve is written `is_trustworthy = true`. My Allocation renders "ready" and
  computes KPIs over a curve that lacks those accounts' past. The only disclosure is the key card on
  the profile page, which the owner has no reason to open.
- **Hidden path:** a WARNING is a Sentry breadcrumb, not an event (the file says so itself at the
  SFH-07 comment at `:10986-10995`), so no operator signal either. D-22 accepted this state "until C4",
  and C4 now makes it permanent for every pre-C4 departure, while the phase's own words say "C4
  restores it".
- **User impact:** the headline curve, return and drawdown describe a smaller book than the one the
  owner ran, and nothing on the page says so.
- **Recommendation:** do NOT make it blocking (the comment at `:11227-11232` is right: that would
  hold the book untrustworthy forever). Instead, one of: (a) the reader surfaces the payload flag as
  a disclosure line on My Allocation ("History of N disconnected account(s) is not in this curve");
  or (b) the founder re-decides D-22 knowingly, with plan 08's census giving the count. Either way,
  capture it once at Sentry `warning` level (counts only), as the identity refusal does.

## MEDIUM

### SFH-C4-05 — The switch reads ON while the card says the history is not available

- **Location:** `src/components/exchanges/AllocatorExchangeManager.tsx:580, 600`,
  `src/lib/departed-history.ts:242-245`.
- **Scenario:** a departed key on a known, distinct account with no anchor (SFH-C4-04's population).
  `decision.included` is true, so `aria-checked` is `true` and the switch renders in the accent
  colour, while the line beside it says "History not available". For an unknown-account key the
  card says "Include it if it was a different account"; the owner includes it, the RPC succeeds, the
  status line promises "recomputed with this change within a few minutes", and nothing changes.
- **Recommendation:** derive the switch state and the recompute notice from
  `decision.included && anchored`; when not anchored, disable the switch and do not invite an
  include that cannot take effect.

### SFH-C4-06 — "Not available" names the wrong cause for a null last anchor

- **Location:** `analytics-service/services/job_worker.py:11141-11156` (only `anchor_usd` is read;
  `anchor_null_reason` is ignored), `src/lib/departed-history.ts:244`,
  `AllocatorExchangeManager.tsx` `anchorOf`.
- **Scenario:** a key's last epilogue before it departed wrote `anchor_usd = null` with
  `anchor_null_reason = 'balance_error'` (or `nonpositive`, `flow_drop`). While live, that null
  anchor degraded the book (DROPPED_KEY, untrustworthy). After it departs, the same row makes it
  `departed_unavailable`, a BENIGN omission, and the card says "the balance it is measured from was
  deleted before departed history was kept", which is false: the row exists and names its reason.
- **Recommendation:** read `anchor_null_reason` in both places. Say "the last balance read failed"
  for a real-capital reason, and keep the "deleted" sentence for a missing row only. Count the two
  apart in the WARNING.

### SFH-C4-07 — A successor that ends earlier drops the predecessor's tail with no flag

- **Location:** `analytics-service/services/job_worker.py:10581-` (`departed_history_inclusion`,
  successor bound), `src/lib/departed-history.ts:215`; no fixture row covers it
  (`departed_history_inclusion.json` cases 01-17).
- **Scenario:** departed keys A (returns 2026-01-01 to 2026-03-01) and B (2026-02-01 to
  2026-02-15) on one known account, no live key on it. A is bounded to 2026-01-31, B runs to
  2026-02-15, and 2026-02-16 to 2026-03-01, real data on A, counts nowhere. The account's capital
  leaves the book on 2026-02-16 through B's exit seam, booked as an outflow.
- **Hidden path:** D-09 case (2) assumes the successor carries the account "from then on". Both
  languages implement that faithfully; the spec has the hole. No reason token distinguishes it.
- **Recommendation:** give the predecessor back the days after the successor's end (bound it by
  the successor's window, not only its first day), or flag the lost interval. Add the fixture row
  to both languages.

### SFH-C4-08 — Open Positions shows a quiet or departed key's rows with no age

- **Location:** `src/lib/latest-holdings-per-key.ts` (no date window, by D-16),
  `HoldingsTabPanel.tsx:226-249` (`OpenPositionRow` carries no `asof`; only `revoked` and
  `sign_in_failed` get a chip).
- **Scenario:** a key failing with `error` for three weeks, or disconnected months ago, shows its
  last poll as current positions. D-16 chose "never flat" on purpose, which is defensible, but the
  row then needs to say how old it is.
- **Recommendation:** carry `asof` into the row and show it when it is older than the newest poll,
  or label rows whose key is disconnected or failing.

- **SFH-C4-11 — `_utc_day` raises on a malformed `disconnected_at` outside the corrupt-input
  disposal.** `job_worker.py:10497` is reached from `:10921`, before any `_permanent_corrupt_input`
  try, so a bad value would retry as `unknown`. The TS twin returns null and falls back to the last
  returns day: the two languages diverge on the same input. Postgres always returns a valid
  timestamptz, so this is defence in depth.
- **SFH-C4-12 — the card's returns days are cached for the life of the page.** `returnsDays` is
  never invalidated after `router.refresh()`, so a departed key bounded by a new live key with no
  returns yet keeps saying "not included" after that key derives, until a full reload.

## INFO

- An owner's `include` on an unknown-account key can double count one account. That is D-09 case
  (3), founder-confirmed 2026-09-25; the card sentence carries the burden and says so.
- The Open Positions vs exposure-panel disagreement is routed as R-15-3. Plan 15 requires the PR C4
  description to carry its sentence; check it is there when the PR opens.
- A live key on the same account with no returns yet bounds a departed key to zero days, under
  "a key you still have connected reads the same exchange account over these days". Transient: the
  book is rebuilding in that window anyway (the live key is missing or anchored-without-returns).
- A departed key whose last day is the book's last day gets no exit seam, so its level is in the
  book's last point. Correct as of that day; it exits on the next union day.

## Done well

- The include/exclude RPC's refusals are mapped by SQLSTATE, never by message, the optimistic
  switch rolls back on every error, and 55006's DETAIL and HINT are shown as given.
- The per-key holdings read cap-checks the key-id read too (`latest-holdings-per-key.ts:99`) and
  every read carries an explicit `.limit`, so truncation fails loud through `assertOk` whatever
  `max_rows` is.
- Rebase seam with C3 confirmed: `_load_allocator_daily_returns` iterates every `key_rows` id, so
  departed keys' returns are read and feed both the rule's first/last days and the compose.
  `queries.ts` holds no drain-by-id conflict with the new per-key read.
- The orphan cleanup is narrowed to hard-deleted keys, so the switch stays reversible.
- The exit is a curve seam plus a ledger outflow and leaves both sums of `portfolio_returns`; it is
  never a return and never a carried level (`allocator_equity_compose.py:164, 239`).
- The marker-link identity (plan 09 Deviation 1) closes the departed-holder double count the plan
  as written would have opened, and the B4 gate now runs on the identity token.
- The Delete confirm's warning appears exactly when the hard-delete path is chosen.
