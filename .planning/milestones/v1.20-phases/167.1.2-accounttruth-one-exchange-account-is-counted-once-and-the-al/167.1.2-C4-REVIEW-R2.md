### WR-R2-02 (MEDIUM): an unanchored covering key zeroes the key it covers, so the account's days count nowhere

**Files:**
- `analytics-service/services/job_worker.py:10967-10980` (the rule decides)
- `job_worker.py:11293-11301` (`departed_unavailable` is dropped afterwards)
- `src/lib/departed-history.ts:385-386` (the covered key's sentence)

**Issue:**
- `departed_history_inclusion` runs with no knowledge of anchors. Only after it has
  chosen the account's carrier does the derive remove every included departed key whose
  anchor is `None`: `del departed_end_by_key[k]`, plus its returns and flows.
- Under the pre-fix rule, a key with no anchor could only lose its own days, plus the
  predecessor tail that IN-01 records.
- The covered rule adds a new shape. Take A (2026-01-01 to 2026-03-01) and B
  (2026-02-01 to 2026-02-15) on one known account, with no live key on it:
  1. The rule makes A the carrier and B `same_account_as_earlier_key`, with zero days.
  2. A has no anchor. Examples: a pre-C4 departure whose `key_inputs` row the old orphan
     cleanup deleted (SFH-C4-04's population), or a `balance_error` last read. A lands
     in `departed_unavailable` and is removed.
  3. B is anchored, but it is never considered again.
- Result:
  - The account's whole history is out of the book on a `ready` curve.
  - Pre-fix, B's 2026-02-01 to 2026-02-15 would have counted.
  - B's card says "History not included: an earlier key read the same exchange account
    over all of these days." That is false: the earlier key's history is not in the
    book either.
  - The switch is disabled, because 'include' never lifts a known-account bound, so the
    owner cannot recover it.
  - The only disclosure is the generic dashboard line.
- The new invariant test `test_no_day_of_a_known_account_is_dropped` cannot see this. It
  runs the pure rule. The job-level `_fixture_supabase` gives every key a `key_inputs`
  row with an anchor, so no test composes an unanchored covering key.

**Fix:**
- Decide availability before the rule. The `key_inputs` rows are already loaded.
- Treat a departed key whose row is missing or has a null anchor as not counted in the
  rule, the way `'exclude'` is. It then neither covers nor bounds, and the chain
  re-forms around the keys that can be levelled.
- The TS twin already fetches each departed key's anchor state (`anchorById`). Pass it
  into `departedHistoryInclusion` (for example as an `anchored?: boolean` input field,
  defaulting to true) so both twins decide the same way.
- Add fixture rows for an unanchored covering key and an unanchored successor, which
  also closes IN-01. Add a job-level arm where one key has no `key_inputs` anchor.

### WR-R2-03 (MEDIUM): WR-01's disclosure line clears on the next failed poll while the partial rows stay

**Files:**
- `src/app/(dashboard)/allocations/HoldingsTabPanel.tsx` `partialPositionReadNotes`
  (filter `k.sync_status === "complete_with_warnings"`)
- `analytics-service/services/job_worker.py:9223`, `:9283`

**Issue:**
- The line reads the key's CURRENT `sync_status`. A poll that fails writes a different
  status and no rows:
  - `rate_limited` (`:9223`)
  - `error`, or a classified status (`:9283`)
  - `syncing` while a poll runs
- The key's latest `asof` stays on the partial day, so its derivative positions stay
  missing from Open Positions, and the line is gone.
- The table's chips cover only `revoked` and `sign_in_failed`. So one transient 429 on
  the day after a partial poll brings back exactly the silent disappearance WR-01
  reported.
- The docblock says the line "clears when a sync reads the positions again". It also
  clears when a sync reads nothing at all.

**Fix:**
- Bind the line to the poll that wrote the rows, not to the key's status.
  `fetchLatestHoldingsPerKey` already reads the key's `sync_completed` events. Also
  read the key's newest event with no `final_status` filter.
- Mark the key partial when that event's `metadata.asof` equals the key's latest `asof`
  and its `final_status` is `complete_with_warnings`.
- Carry the flag out with the rows, for example as a per-key set on the payload. Render
  the line from that flag.
- Add an arm: a partial poll, then a `rate_limited` poll. The line must stay.

### IN-R2-05 (LOW): the SFH-C4-02 evidence can be absent in two cases, and the closed rows then come back

**File:** `src/lib/latest-holdings-per-key.ts:210-219`

**Issue:**
- (a) The reader reads `audit_log` only. The hot-to-cold cron moves rows older than 2
  years to `audit_log_cold` (baseline.sql:11106). A departed key whose last clean poll

  predates C4.

  docblock's "the key contributes nothing".

**Fix:** Record both limits in the docblock. For (a), also read `audit_log_cold` (it has
its own owner-read policy), or accept and date the limit.
