## Warnings

### WR-01: Both consumers fail OPEN on any value other than `"rebuilding"`; the fail-closed default only covers a missing field

**File:** `src/app/(dashboard)/allocations/AllocationDashboardV2.tsx` (`isRebuilding`), `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx` (`isOwnBookRebuilding`)
**Issue:** Both gates test `equityHistoryState === "rebuilding"`. A destructuring default only
applies when the value is `undefined`. So `null`, `""` or any state added later reads as "ready" in
both consumers. Examples are a `"partial"` state that plan 11 might add, or a producer that
serializes a missing value as `null`. In either case the Overview builds the factsheet (every KPI)
from whatever `equityDailyPoints` holds, and the composer computes the own-book delta. T-167.1.2-01
claims the fail-closed default holds in both consumers, but the code does not deliver it. Today the
producer always emits `"rebuilding"` and `[]`, so nothing wrong reaches a user yet. That is the only
reason this is not a blocker. The composer suite never tests the missing-field default at all:
`makePayload` always sets the field.
**Fix:** Gate on the only value that may show the curve, in both files:
```ts
const isRebuilding = equityHistoryState !== "ready";          // AllocationDashboardV2
const isOwnBookRebuilding = equityHistoryState !== "ready";   // ScenarioComposer
```
Add two test cases:
- In `AllocationDashboardV2.rebuilding.test.tsx`, render with an unrecognised value (cast through
  `never`) and assert the rebuilding panel shows.
- In the composer suite, delete `equityHistoryState` from the payload and assert that
  `scenario-ownbook-rebuilding` renders and the chart receives `equityDailyPoints: []`.

### WR-02: A pre-existing composer test has lost the premise it pins

**File:** `src/app/(dashboard)/allocations/components/ScenarioComposer.test.tsx` (the `assembled folded surface — own-book degenerate blend (0 constituents)` case, assertion `expect(props.scenarioOwnBookDelta ?? null).toBeNull()`)
**Issue:** The test's comment says the own-book delta is absent "because the default book equity
(2 points) gives <2 derivable returns". That was the only test that pinned the second guard in
`scenarioOwnBookDelta` (`if (bookReturns.length < 2) return undefined;`). The default `makePayload`
now sets `equityHistoryState: "rebuilding"`, so `baselineEquityDailyPoints` is `[]` and the FIRST
guard returns undefined before the second one is reached. If someone deleted the second guard, the
2-point book would produce a delta built from one return, and no test would catch it. The new
"ready" regression test uses a 3-point curve (2 returns), so it passes the guard and does not cover
this case either. Under the project's rule that every test must be able to fail, this is a test
made vacuous by this diff.
**Fix:** Pass `equityHistoryState: "ready"` in that test's `makePayload` call and add a comment
naming D-02 (the same move made for the blank-mode case). Or add a dedicated case: "ready" plus a
2-point curve, asserting `scenarioOwnBookDelta` is undefined. Confirm it goes RED with the guard
removed.

### WR-03: The panel copy makes claims that are false for many of the allocators who see it

**File:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx` (body paragraph)
**Issue:** The panel renders for every allocator who has holdings, and also when
`holdingsEmpty && hasSyncing` (a first connect). Three parts of the copy are wrong for some of them:
1. **Single-key allocators.** "The earlier chart added up snapshots from several keys. It could
   count one exchange account twice" cannot be true with one key.
2. **Allocators who never saw a chart.** "The earlier chart" did not exist for a first connect, for
   a first-day book, or for an allocator who had fewer than 2 points and only ever saw the warm-up
   copy.
3. **Stale books.** "Holdings and AUM on this page are current" renders beside the
   `StalenessBanner`, which fires when every key's last sync is over 24 hours old. That banner says
   "Analytics may be stale. Last successful sync was 3d ago". The page then contradicts itself about
   the very numbers it asks the reader to trust.

The house rule is "no invented data" and honest absence. A reason stated as fact to a reader it does
not apply to is the same class of defect D-02 exists to remove.
**Fix:** Keep the copy static and conditional:
- Word the cause as possible, not certain. For example: "The earlier chart combined snapshots across
  your keys and could count one exchange account twice or read a day with no sync as zero, so its
  curve and ratios were not reliable."
- Drop "current", or render the AUM sentence only when `!allKeysStale`. Passing a boolean prop is
  enough. For example: `{!stale && <> Holdings and AUM on this page are current.</>}`.

Pin the stale case in the rebuilding test with `allKeysStale: true`.

### WR-04: The panel heading skips from `<h1>` to `<h3>` (axe `heading-order`, best-practice tag this repo gates on)

**File:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx` (`<h3>`)
**Issue:** The Overview's only heading above the panel is the page `<h1>` "My Allocation" in
`AllocationsTabs`. `InsightStrip`, `AlertBanner` and both banners render no heading. The
`FactsheetBody` headings this panel replaces are not mounted. So the heading tree becomes h1 → h3.
`e2e/helpers/axe.ts` `buildAxe` runs the `best-practice` tag, which includes `heading-order`. No axe
spec loads a seeded-book Overview today: `axe-app-wide` seeds a no-book allocator and lands on
EmptyState. So CI will not catch this. It will surface the first time any axe run reaches a real
book. EmptyState, the sibling on the same surface, uses `<h2>`.
**Fix:** Use `<h2>` and keep the 16px semibold styling. The DESIGN.md H3 size is a visual token, not
a heading level. Optionally use the fluid `text-h3` tier instead of `text-base`, per the DESIGN.md
type spine.

### WR-05: `/compare` still renders a per-holding Sharpe, return, max drawdown and vol built from the same defective snapshot store

**File:** `src/app/(dashboard)/compare/lib/holding-compare-adapter.ts` (`fetchHoldingCompareItem` → `reconstructAndAnalyze`)
**Issue:** The brief asks for any surface still showing a wrong Sharpe or return. This one does.
`fetchHoldingCompareItem` reads `allocator_equity_snapshots.breakdown` and computes cumulative
return, Sharpe, max drawdown and vol from the per-symbol $ values.

- **Two keys on one account (D-01's defect).** The breakdown sums the symbol's value from both keys
  on days both polled, and from one key on days only one polled. That produces the same ±100% and
  −50% swings, inside a per-symbol series.
- **A key that did not poll (D-07).** Its symbols are dropped from that day's breakdown. The
  adapter's zero and absent filter removes those days rather than forward-filling, so the next
  return spans two days.

CONTEXT D-07 records that the compare adapter is not touched by this phase, and plan 10 repairs the
writer. From PR A's merge until PR C lands, `/compare` keeps showing these numbers while My
Allocation says the same data is unreliable. Plan 01's scope does not cover this surface, so it is
not a defect of this diff. It is a data-integrity gap D-02's premise ("a wrong number the allocator
can act on is worse than an honest absence") applies to, and nothing records it.
**Fix:** Decide explicitly, and record the decision in CONTEXT.md and the ROADMAP. Either:
- extend D-02's gate to `fetchHoldingCompareItem`, returning null (the existing "not available" path)
  until plan 10 or 11 lands; or
- record the decision to leave it showing, with the reason and the owning plan.

Do not leave the gap unrecorded.
