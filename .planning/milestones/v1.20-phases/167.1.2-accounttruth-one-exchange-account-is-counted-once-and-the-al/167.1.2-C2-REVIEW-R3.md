## Answers to the six directed points

1. **The audit event as the proof.**
   - The event is written on the success path of the only holdings persist site (`job_worker.py:9281` persists, `:9356` emits). It goes through `log_audit_event_service`, which stores `p_metadata` unchanged.
   - `scrub_pii` does not touch `row_count` or `final_status`.
   - `service_role` has SELECT on `audit_log`, and `idx_audit_log_entity` serves the read.
   - An event dropped for a transient reason means no proof, so the account is carried. That is the safe direction.
   - **Retention:** hot `audit_log` keeps 2 years (`audit_log_hot_to_cold`). A proof expires only if a key goes 2 years without a successful poll, which is negligible.
   - **Joinability is where it breaks.** The proof keys on the event's `created_at`, but the rows the poll writes are dated by `today_str`, which is taken before the fetch (`job_worker.py:9073`). See R3-WR-01.
   - **Deploy day:** the fixer's "≤1 day" is conditional. See R3-WR-02.
2. **Stitching.**
   - The index is ISO strings, asserted on each link.
   - Each earlier member owns `[own_first, next_first)` and the kept member owns `[kept_first, …]`. There is no double day, and a gap refuses the stitch.
   - Flows are passed through unchanged (`ExternalFlow`, deposits positive), so the sign convention is kept.
   - The kept key's flows dated before its first day are dropped, and so are the source's flows on or after `next_first`. The fixer's same-deposit test pins this.
   - `shared_account_history_truncated` fires for each of the three cases it claims.
   - Residual edge cases are in IN-01 and IN-02.
3. **The parity table.** The 72 cells check out. Both sides run the real function, and a neuter on either side fails. Limit: the TS side builds the producer's input through its own `readerInputs` mapping (IN-03).
4. **Reader/writer agreement.**
   - I found no cell that shows "ready" while the derive double-counts a marked pair, or while a stitch is truncated.
   - Two gaps remain. A single failing key, or a pair with one inactive member and one failing member, still reads ready over a flat carry (IN-04). A departed older key's history is still dropped (plan 09's domain, not in C2).
   - The copy for the two new blocking states is not actionable (R3-WR-03).
5. **`after()`.**
   - `getMyAllocationDashboard` is called only by `allocations/page.tsx` (a Server Component). It is re-rendered by `AllocationsTabs`' `router.refresh()`. Both paths are in a request scope.
   - Every `"use client"` importer of `@/lib/queries` imports types only.
   - The capture promise is created once, before scheduling. `after` and `queueMicrotask` only hold that promise, so the fallback cannot report twice.
6. **`equityHistoryNotSyncingKeyIds`.**
   - The ids are the owner's own `api_keys.id` values, and the same payload already carries them in `apiKeys`.
   - The masked tail is `••••` plus the last 4 characters of the row UUID, not of any credential (`dataSourceLabel`).

## Warnings

### R3-WR-01: One poll that runs across UTC midnight vetoes the emptiness proof for up to 200 later polls, so a proven-empty account is carried at its stale balance (the R2-CR-01 class, narrower trigger)

**File:** `analytics-service/services/equity_reconstruction.py:2110` (`.gte("created_at", next_day)`) and `:2125` (`if row_count > 0: return False`); `analytics-service/services/job_worker.py:9073` (`today_str` taken before the fetch) and `:9356` (the event is emitted after persist)

**Issue.**
- **How the veto arises.** A poll's rows are dated `today_str`, fixed at handler start. Its `sync_completed` event is created after the fetch, the persist and `_update_ok`. A poll that starts before 00:00 UTC and emits after it writes rows dated D and an event created on D+1.
- **Why it persists.** Suppose that was the account's last poll with holdings, so its latest `asof` stays at D. The proof window then starts at D+1 and contains that event with `row_count > 0`, which vetoes every later clean, empty event. The veto lasts until 200 newer events of the group push it out of `_POLL_OUTCOME_READ_LIMIT`, about 200 days at one poll a day.
- **The result.** Each of those days persists the stale carried balance, first writer wins, into the store that match.py, compare and the GDPR export read. After that the series flips to $0.
- **Measured** with the refresh fixture: key 2's last rows are at TODAY−3, a `row_count=1` event is created at 00:00:04 on TODAY−2, and clean empty events follow on TODAY−2 and TODAY−1:

```
STRADDLE persisted 1500.0  emptied_accounts 0      # 1000.0 is correct
```

**Why WARNING and not BLOCKER.** The 04:00 cron never straddles midnight, so only a manual sync near 00:00 UTC does. The account must also empty before its next poll that writes rows. The consequence has the same persisted-wrong-figure shape as R2-CR-01, so the orchestrator may raise it.

**Fix.** Bind the event to the day its rows carry, not to the time it was created:

```python
# job_worker.py, sync_completed metadata
"final_status": final_status,
"asof": today_str,
```

```python
# _polled_empty_since: keep created_at only as an index prefilter
poll_asof = metadata.get("asof")
if isinstance(poll_asof, str):
    if poll_asof <= latest_asof:
        continue            # this poll's rows (or emptiness) are not after latest
# (legacy events without asof: keep today's created_at rule)
if row_count > 0: return False
```

Add the straddle arm above as a test.

### R3-WR-02: Deploy day is safe only if the deploy lands outside about 03:30–05:00 UTC. Otherwise the refresh writes one permanent stale row per empty account, where main writes $0

**File:** `analytics-service/services/equity_reconstruction.py:2064-2130`. Schedules: `poll-allocator-positions` `0 4 * * *` (`supabase/migrations/20260420073003_allocator_holdings.sql:692`) and `refresh-allocator-equity` `0 5 * * *` (`20260420213754_allocator_equity_snapshots.sql:379-383`)

**Issue.** The fixer measured deploy day against round 1, but round 1 never shipped. The correct baseline is `origin/main`.
- **On main:** the refresh reads today's rows only, so a connected ccxt account that is empty contributes $0.
- **With C2:** that account is carried at its last positive balance unless it is proven empty. The proof (`final_status` in the event) exists only once a poll has run the new code.
- **Case A.** The Railway deploy lands after the 04:00 polls ran on the old code, but before the 05:00 refresh. The 05:00 refresh then runs the new code over events that have no `final_status`. It writes one stale row for each empty account, first writer wins, permanent.
- **Case B.** An empty account whose key has no successful poll after deploy (it fails, or the first poll hits a 429) has no event in the new shape. It is carried at its stale balance until one exists.
  - For a key that was already failing at deploy, that means indefinitely.
  - On main, the same account contributed $0.

Case B's population is small: a key stamped after C1, then emptied, then failing, all before C2 deploys.

**Fix.**
- Record a landing gate for the orchestrator: merge so that Railway's post-CI deploy lands outside roughly 03:30–05:00 UTC.
- Alternatively, accept an event in the old shape as proof when `row_count == 0` and `holding_type_counts` are both 0, and the key's CURRENT status is `complete`. That is round 1's rule, used only for events without `final_status`, and it expires on its own.
- Either way, correct "≤1 day" in the fix report, which is conditional.

### R3-WR-03: The two new blocking states show a line that names no way forward, one of them never heals, and the handoff that should have fixed the copy was dropped

**File:** `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:69-70`; `src/lib/queries.ts` (`derivePhase07Fields`, where untrustworthy maps to `derivation_rejected`); `analytics-service/services/job_worker.py:10666-10690`

**Issue.** Both `shared_account_no_working_key` and `shared_account_history_truncated` now make the payload untrustworthy. The reader then shows "The latest rebuild of your history did not pass its checks, so it is not shown."
- **Gap case, `truncated`: the state never heals.** A new key whose history does not reach back to the old key's last day will never cover the gap. The book is hidden for good.
- **The only remedy is invisible.** The user's move would be to disconnect the old key. The copy does not say so, and that path then silently drops the old history, because plan 09's departed-key history is not in C2.
- **`no_working_key` lasts until the user fixes a key.** The line does not say which key, or that a key is the cause.
- **This breaks DESIGN.md Voice** ("the reader learns exactly what unlocks it"). It is the SFH-05 pattern again: a line that a permanent state never makes true.
- **The handoff was dropped.** Fixer A's report hands "name the unlock" for these two states to fixer B or the orchestrator ("Handoff to fixer B"). Fixer B's report does not mention it.

**Fix.** The read site already has `payload.degrade_reasons`. Map the two tokens to their own reason lines before the generic `derivation_rejected`:
- `shared_account_no_working_key`: "An exchange account's keys are not syncing, so its history stops. Check them on the Exchanges page."
- `shared_account_history_truncated`: an honest line that the two keys' histories cannot be joined, with the Exchanges page link.

Pin both lines with a render test. The founder approves the wording.

### R3-WR-04: The `derived_row_rejected` capture fires on every 30-second poll of an open Overview tab, now for two long-lived user states

**File:** `src/lib/queries.ts:4410-4425` (the capture), `src/app/(dashboard)/allocations/AllocationsTabs.tsx:209,485-494` (`PERFORMANCE_POLL_INTERVAL_MS = 30_000`, `router.refresh()`)

**Issue.**
- **The real rate.** Fixer B sized the volume as "once per dashboard load". But `router.refresh()` re-runs `getMyAllocationDashboard` every 30 s while Overview is visible. That is about 120 Sentry events per hour per open tab.
- **It now covers long-lived states.** Round 2 made two such states untrustworthy: no working key, and a gap that never heals. The ordinary new-key `DROPPED_KEY` backfill also still fires it.
- **The effect.** The `derived_row_rejected` issue stays active permanently, and the events spend Sentry quota. That defeats the alert this capture was added for, which is SFH-05.

**Fix.** The writer knows the verdict at compose time. Capture an untrustworthy compose once per compose in the derive, the way fixer A captures the refusal path. Keep the reader capture for `malformed` only, which is a writer bug. At minimum, key the reader capture on `(allocator, computed_at)` so that one row reports once.

**Issue.** Probe: sources A and B both start 2026-05-01. A comes first by id and owns `[05-01, 05-01)`, which is empty. ### IN-02: The stitch refuses too readily with three members, and it relies on dense series

**File:** `analytics-service/services/allocator_equity_derive.py:341-345`
**Issue.**
- The gap check compares each source only with the next member's first day. Take A covering 05-01..06-10, B covering 05-15..05-20, and kept from 06-01. B's early end refuses the stitch, even though A alone covers the range honestly. The result is BLOCKING truncation.
- An interior hole in a source is accepted: the probe with `["05-01","05-31"]` returned a stitch. That is correct only because per-key dailies are gap-filled (`gap_fill_daily_returns`).
**Fix.** Choose the owner per day from the members whose series covers that day. Otherwise, record the dense-series assumption as the precondition it is.
