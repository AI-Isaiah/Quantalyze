## Fixed

### SFH-R2-01: every book-mode scenario commit returns a 409 that no refresh can clear

**Commits:** `9f9b6f221` (fix and gate), `b6230c047` (the test file header now names the migration tests 10 to 14 need)
**Files:**
- `supabase/migrations/20260929120000_commit_scenario_batch_fingerprint_reader_set.sql` (new)
- `supabase/migrations/down/20260929120000-rollback.sql` (new)
- `supabase/tests/test_commit_scenario_batch_fingerprint_precondition.sql` (tests 10 to 14 added)

**Root cause, confirmed at HEAD.** The latest definition of `commit_scenario_batch` is
`20260601120000` (no later migration replaces it; `baseline.sql` carries the same body).
Its step (3b) takes the newest row per `(venue, symbol, holding_type)` over every date. The
client fingerprints `holdingsSummary`. Since D-16 that comes from `fetchLatestHoldingsPerKey`,
which reads each key at its own latest asof, keeps one reading per exchange account
(SFH-C4-01), and drops a key whose newer clean poll read nothing (SFH-C4-02). A closed
position keeps its last row, so it stayed in the server set and dropped out of the client's.
Reproduced on the local lane: test 10 (BTC-PERP last seen two days ago, ETH today,
fingerprint `ETHUSDT:binance:spot`) returned `portfolio_fingerprint_stale` on the old body.

**What changed.** Step (3b) now computes the reader's set, step for step:
1. the owner's keys, departed ones included;
2. for each key, its latest asof, and its newest `allocator.holdings.sync_completed` event
   with `final_status = 'complete'` (by `created_at DESC`, NULLs first as PostgREST orders).
   The event counts only when `row_count` is a non-negative whole number and `asof` is a
   `YYYY-MM-DD` string. That is `cleanPollDay`. If the event's day is strictly after the
   key's rows, the key reads as that day with no rows;
3. keys grouped by the D-09 account identity: the same non-blank `venue_account_id` on one
   exchange, or a `duplicate` / `composite_member` marker. The grouping is transitive and
   uses a recursive CTE. Only keys on the account's newest reading day that have rows
   contribute;
4. those keys' rows at that day, one token per triple.

Days are compared as text under `COLLATE "C"` and are never cast to `date`, so a malformed
audit `asof` cannot raise inside the RPC. The comparison of the two sets is unchanged
(`COLLATE "C"` sort on both sides). Everything else in the body is the `20260601120000` text
verbatim: the `auth.uid()` guard, the idempotency reservation, the 50-diff cap, the per-diff
ownership probes, the published-strategy gates, the inserts and the audit emission. Every
read is scoped to `p_allocator_id`, which step (1) has already proved equals `auth.uid()`.
The fix touches no owner or tenant check.

**The fingerprint still detects a real change, and now detects more of them.** Test 9 (a new
symbol) is still refused. New test 11 refuses a draft listing a position that closed since
it was built. The old set only ever grew, so it missed that case.

**Why server-side (the choice asked for).**
- **Client-side is not available.** The client would need the all-dates read that D-16
  removed, and even then that rule cannot see a close.
- **A route-side recompute was rejected.** The route would reuse the TypeScript reader,
  which avoids a twin. But the check would then run before the RPC's idempotency step. A
  network retry of a batch that is already committed would get a 409 after any poll,
  where today it gets the cached result. The check would also move out of the transaction.
  In addition, the route's `null ⇒ skip` contract is pinned by T_R20, T_R24 and the CR-01
  test.
- **The cost is a third twin.** The rule now exists in TypeScript
  (`latest-holdings-per-key.ts` + `accountIdentityTokens`), in this SQL, and as the grain
  rule in plan 10's Python. The SQL comment says so. Tests 10 to 14 are the gate against
  drift. One concrete drift point: the SQL hardcodes `IN ('duplicate', 'composite_member')`.
  TypeScript derives the same set from `MARKER_KIND_IS_SHARED`, which has a compile-time
  forcing function. Today the `api_keys_account_share_kind_valid` CHECK pins the same two
  kinds, so adding a kind already needs a migration. That migration must also edit step (3b).

**Migration hygiene.**
- Same 5-arg signature, so `CREATE OR REPLACE` with no DROP. Measured on the lane after
  apply: `proacl = {postgres=X, authenticated=X, service_role=X}`, `prosecdef = t`,
  `search_path=public, pg_catalog`. That matches the baseline's grants.
- The `REVOKE … FROM PUBLIC, anon` / `GRANT EXECUTE … TO authenticated` pair is re-issued.
  `_assert_no_public_execute` is re-asserted.
- The DO block reads only the catalog: overload count, arity, body text and the index. It
  reads no data, so it applies the same way on empty TEST. It keeps every body probe from
  `20260601120000` and adds three for the new rule (clean-poll event, account marker,
  per-key asof join).
- No CONCURRENTLY. Timestamp `20260929120000` is after `20260928140000`.
- `database.types.ts` is unchanged, because the signature is unchanged.

## Needs routing

   in parallel. If that change alters which rows contribute, `20260929120000` step (3b) must
   change with it in the same PR, or SFH-R2-01 comes back. Please diff topic C's reader
   change against the step (3b) comment before merge. `accountIdentityTokens` (topic B's
   file, `departed-history.ts`) has the same coupling.
2. **Pre-existing, same function, not changed here.** The per-diff ownership probes
   (`voluntary_remove`, `voluntary_modify`, `bridge_recommended`) still accept a triple
   whose newest row over all dates has `value_usd > 0`. So a direct RPC caller can name a
   position that closed on an earlier day, or one an account's newer reading superseded.
   The fingerprint now refuses that case only when the caller sends a fingerprint, and
   NULL skips it. This is not cross-tenant: it only reads the caller's own rows. It is
   data-integrity for that caller's own outcomes.
3. **Pre-existing, route.** The audit recompute of `size_at_decision_usd` in
   `src/app/api/allocator/scenario/commit/route.ts` (the NEW-C18-04 block) also collapses
   over all dates. A closed triple therefore still gets a server size. This is the same
   class as item 2.
4. **Known, negligible divergences, recorded:**
   - JS `trim()` strips Unicode whitespace; SQL `btrim` strips spaces only. The
     `api_keys_venue_account_id_nonblank` CHECK and server-derived values make this moot
     in practice.
   - The reader's 1000-row cap fails the page loudly and has no counterpart in SQL.
   - Ties on `created_at` in the poll read are unordered on both sides.
5. **PR text:** because the fix ships with the reader, the reviewer's "book-mode commits are
   refused" caveat is not needed. The PR should name the new migration: merging it
   auto-applies it to TEST and then to PROD. It still needs migration-reviewer,
   rls-policy-auditor and silent-failure-hunter before merge.

   the new file (measured), and the next bot re-dump will carry it.
