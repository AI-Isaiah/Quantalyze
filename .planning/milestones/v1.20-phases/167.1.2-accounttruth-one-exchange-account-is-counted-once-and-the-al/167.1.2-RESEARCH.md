## Summary

Most of the machinery this phase needs already exists. What is missing is how it is wired together. **Account identity**: the fence is already in place. `api_keys_user_exchange_venue_account_uniq` is a partial UNIQUE on `(user_id, exchange, venue_account_id) WHERE venue_account_id IS NOT NULL AND disconnected_at IS NULL`. The persist arm of `validate-and-encrypt` already turns its 23505 into `KEY_VENUE_ALREADY_CONNECTED` (409). The wizard route already resolves a 23505 through `resolveByVenueIdentity`. None of this fires for ccxt venues, because nothing puts a ccxt account id into `venue_account_id`. The permission probes the validator already runs for OKX and Bybit fetch responses that carry the account uid (`account/config` → `data[0].uid`; `user/query-api` → `result.userID`), and the code throws that uid away. Binance's spot `fetch_balance` response carries `uid`. Deribit's `get_account_summaries` returns `id` when asked with `extended=true`. **No new unique index is needed.** The work is: capture the id, stamp it at every connect path, backfill existing keys, and mark existing duplicates.

**Equity history**: Phase 115.1 already built the right derivation. `compose_allocator_equity` replays each key's $-equity backward from a live venue anchor using that key's flow-adjusted daily returns and external flows. It sums the keys, carrying the last known level forward so a missing day never reads as $0, adds 0 before a key opens, and handles rotation seams. Three defects keep it from being "the rebuilt series" on this book. (1) Two keys on one account are two eligible keys, so the compose sums the same account twice. (2) The payload persists only a $-level curve. The dashboard turns that curve back into returns with `equityCurveToDailyReturns`, so a deposit, or a key joining the sum, reads as a return even on the derived path. (3) Any gap in derivation (a missing key, `DROPPED_KEY`, an empty compose) degrades to the legacy `allocator_equity_snapshots` curve. That curve is the first-writer-wins patchwork the founder saw. The fix: persist a flow-neutral portfolio return series next to the $-curve, read KPIs from it, gate readiness on account identity, and never render the legacy store on My Allocation again.

**Primary recommendation:** Ship the hide first as a pure TS producer gate: one `equityHistoryState` on the payload, the curve withheld on the server, and one honest rebuilding panel. Then add identity capture. Do it by extracting ids from responses the validator already fetches, stamping them through the existing columns and index, and backfilling from the daily poll job with a disclosed duplicate marker. Then extend the 115.1 compose to emit `returns`, and retire the legacy fallback. Fix the scenario zero-mass and silent-drop defects, and the three small fixes, as independent plans.

### Pattern 4: Named cleanup for existing duplicates (SC-1c), with nothing silently deleted

1. **Backfill in the worker, inside the daily poll.** `run_poll_allocator_positions_job` already runs for **every live key, role-agnostic** (`enqueue_poll_allocator_positions_for_all_keys` selects `is_active = true AND sync_status IS DISTINCT FROM 'revoked' AND disconnected_at IS NULL`) [VERIFIED: supabase/schema/baseline.sql function body], and its preflight already holds the decrypted ccxt session with `key_row` loaded via `select("*")` [VERIFIED: job_worker.py `_allocator_key_preflight`]. Add a step that runs only for ccxt venues where `venue_account_id IS NULL`: `read_venue_account_id(exchange)` → `UPDATE api_keys SET venue_account_id = :id WHERE id = :key AND venue_account_id IS NULL`. The step is wrapped so **any failure never fails the poll**; it is logged and retried at the next poll. This avoids a new compute kind, which would change `compute_jobs_kind_check`, the enqueue functions and the pg_cron wiring.
2. **On 23505** (a live sibling already holds this identity): do **not** disconnect and do **not** delete. Write `api_keys.account_duplicate_of_api_key_id = <holder id>` (new nullable column; see (f)) and emit an audit event. A name like `api_key.account_duplicate_detected` is [ASSUMED]; check the audit action closed set before minting one.
3. **Surface:** the key card (`AllocatorExchangeManager.tsx`, `ApiKeyManager.tsx`) renders "This key reads the same exchange account as <holder label>. Disconnect one of them." next to the **existing** Disconnect (`disconnect_allocator_api_key`, soft) and Delete (`delete_allocator_api_key`) controls. That is the named path.
4. **Self-heal:** once the holder is disconnected, the duplicate's next poll stamps successfully, because the index excludes disconnected rows, and clears the marker. If the user disconnects the duplicate instead, the holder is untouched.
5. **Readiness:** while any eligible key carries the marker, `equityHistoryState` stays `rebuilding` (Pattern 5).

**Lighter alternative** (considered, not recommended): no column. A census run after the merge lists duplicates and the founder disconnects them by hand. That is honest for a book with one user, but it gives no named path in the product for anyone else, and SC-1 says "a named cleanup path".

### Pattern 5: The rebuilt series (SC-3), extending the 115.1 derivation rather than replacing it

**What already exists** [VERIFIED: allocator_equity_derive.py, allocator_equity_compose.py, job_worker.py `run_derive_allocator_equity_job`, read this session]:
- Per key: `replay_key_equity(returns, flows, anchor)` rolls backward from the live venue anchor with `equity_{t-1} = (equity_t − F_t)/(1 + r_t)`. It unions flow days into the index, refuses non-finite values, refuses non-positive equity, and runs a forward self-check. So **deposits and withdrawals are already levels, not returns, per key**.
- Allocator: `allocator_equity_curve` sums over the **union** of windows. A key contributes **0 before its window opens**. A still-held key whose window ended is **carried forward** (LOCF, `STALE_MARK_CARRY`, benign) and never read as $0. A rotated-out key contributes 0 after its last day.
- Inputs come only from the DB: `csv_daily_returns` per `api_key_id` (from `derive_broker_dailies` key mode, cron `derive-allocator-key-dailies` 05:30 UTC), and `key_inputs:<api_key_id>` rows carrying `flows` and `anchor_usd` plus `anchor_null_reason`. It **never reads or writes `allocator_equity_snapshots`**. The legacy patchwork is structurally outside it, which answers the "duplicate-writer date" test by construction.
- Eligible set: `eligible_key_predicate`, i.e. `is_active AND sync_status IS DISTINCT FROM 'revoked' AND disconnected_at IS NULL`.

**Why it is not "trustworthy" or not used on this book (code-derived; PROD not measured):**
1. `run_derive_allocator_equity_job` **deletes** the `equity_curve` row, so the dashboard shows legacy, if any eligible key has neither returns nor `key_inputs` (`missing_ids`), if the compose is empty, or if the compose raises. `compose_allocator_equity` marks the curve **untrustworthy** (`DROPPED_KEY`) if any key has returns without an anchor, or an anchor without returns. The frontend `extractTrustworthyDerivedCurve` then returns `null`, which means legacy [VERIFIED: queries.ts `extractTrustworthyDerivedCurve`, `derivePhase07Fields`]. The code comment says the legacy fallback "is load-bearing until the founder-gated per-key backfill runs". That figure is a dated claim; re-measure it with the census.
2. **Two keys on one account are two eligible keys.** Each derives a full-account return series and a full-account anchor, and `allocator_equity_curve` **sums** them. That is a double count flagged **trustworthy**. So the derived curve must not render until identity is resolved.
3. **KPIs re-derive returns from $-levels.** The payload carries `curve[{date, equity_usd}]` and the Dietz/MWR scalars, not the blend returns it computes and discards. `AllocationDashboardV2` passes the $-curve to `equityCurveToDailyReturns`, which computes plain `curr / prev − 1` [VERIFIED: src/lib/factsheet/resolve-series.ts]. On the $-curve that turns every deposit and every key joining the sum into a return. **The derived path would repeat the Sharpe-vs-cumulative contradiction.**

**Design (prescriptive):**
- **Account = live key**, enforced by SC-1. After the refusal and cleanup, each account has exactly one live key, so the per-key series **is** the per-account series. A key rotation on one account (disconnect A, connect B) gives B's derive the account's full venue history, and A drops out of the eligible set. Pre-terminus history on OKX (3-month bills horizon) is honestly truncated (`WINDOW_TRUNCATED`, benign).
- **Keys leaving (revoked or disconnected):** they leave the eligible set, so their **whole** history leaves the curve. There is no cliff; the curve becomes "the history of the accounts connected now". [ASSUMED] This scope needs founder confirmation (Open Question 3). The alternative, keeping a departed key's history up to its last day as a seam, reintroduces the rotation-seam ledger for non-rotations and is much larger.
- **Keys joining:** in the $-curve a join is a level step. In the **returns** it must be flow-neutral. Emit `returns` in the payload as the **capital-weighted portfolio TWR**:
  `r_t = Σ_k E_{k,t−1} · r_{k,t} / Σ_k E_{k,t−1}` over keys present on both `t−1` and `t`, where `E` is the replayed per-key equity and `r_k` the key's own return (0 on carried days).
  This is exactly the return of the summed book net of all flows and joins. Because `E_{k,t} = E_{k,t−1}(1+r_{k,t}) + F_{k,t}`, it equals `(ΣE_t − ΣF_t − joins_t)/ΣE_{t−1} − 1`. Pin that identity as a test. ⚠️ This departs from Phase 115 D1, whose blend uses **static current-equity weights**. [ASSUMED] preference for dynamic weights, to confirm in discuss (Open Question 4). If the founder keeps D1, persist the segment-wise blend the compose already computes instead. Either way, **KPIs read `payload.returns`, never `equityCurveToDailyReturns(curve)`**.
- **Carry-forward:** a key whose derive stalled keeps its last `key_inputs` anchor and its window ends early. LOCF carries its level, and its return on carried days is 0. Never $0.
- **Identity gate in the compose (defence in depth):** `run_derive_allocator_equity_job` also loads `venue_account_id`, `exchange` and `account_duplicate_of_api_key_id` for eligible keys. If any eligible key is marked duplicate, or two eligible keys share `(exchange, venue_account_id)`, delete the `equity_curve` row and return DONE with a logged reason. That is the same degrade path the job already uses for `missing_ids`.
- **`equityHistoryState = "ready"`** iff: a derived row exists, `is_trustworthy === true`, the payload carries a well-formed `returns` (payload version bump), every eligible ccxt key has a non-NULL `venue_account_id`, and none carries the duplicate marker. Otherwise `"rebuilding"`. **The legacy snapshot fallback is removed from My Allocation** (`equitySnapshotsToDailyPoints(...)` branch deleted from `derivePhase07Fields`). The legacy store keeps its other readers (Pitfall 6).
- **Payload versioning:** add `payload.version: 2`. The TS extractor requires version 2 and a well-formed `returns`. A version 1 row (existing PROD rows) reads as `rebuilding` until recomputed. That is honest.

### Anti-Patterns to Avoid
- **Adding `api_key_id` to `holdingScopeKey` or the holdings index in this phase.** That is 167.1.1's job, and before SC-1 it would triple-count a shared account (the 167.1.1 correction note).
- **A second unique index** on `(user_id, venue, venue_account_id)`. One already exists as `api_keys_user_exchange_venue_account_uniq`. A duplicate index would make `pgConstraintName` ambiguous.
- **Auto-disconnecting a duplicate in the worker.** The founder's criterion says nothing is silently deleted, and a soft disconnect is still a silent state change of the user's key.
- **Reading returns off any $-curve** (`equityCurveToDailyReturns` on the derived curve), and **reading 115.1's Dietz/MWR scalars as a headline**. The compose itself warns they "can be numerically ABSURD" on short windows.
- **Hand-dispatching gsd agents / hand-editing STATE via handlers**: see CLAUDE.md orchestration rules.

## Common Pitfalls

### Pitfall 1: The deploy race on a new column read by the key list
**What goes wrong:** `API_KEY_USER_COLUMNS` is the SELECT allowlist projection for key lists. If it gains `account_duplicate_of_api_key_id` in the same merge as the migration, Vercel can deploy before PROD applies the migration. Every key-list read then answers 42703/42501, and the Exchanges page breaks.
**How to avoid:** Put the migration (column plus `GRANT SELECT (col) TO authenticated`) in its own **earlier** PR, or have the TS read tolerate the column's absence for one deploy. The repo's own precedent is the DEPLOY ORDER banner in migration 20260812083206.

### Pitfall 2: Blank or whitespace identities collapse two accounts
**What goes wrong:** `''` is non-NULL, so the partial index governs it. The migration notes this "inverts into wrong-account attribution".
**How to avoid:** The extractor returns `None` for blank. `str()` the integers. Do not lowercase (uids are numeric or opaque).

### Pitfall 3: `ValidateKeyResponseSchema` is `.passthrough()` under a lint exception that says it is "never spread into a write"
**What goes wrong:** once `venue_account_id` from that response is written into `api_keys`, the sanctioned-exception comment is false.
**How to avoid:** Name `venue_account_id: z.string().trim().min(1).max(128).nullable().optional()` explicitly in the schema and read that field, never a spread. Update the exception comment.

### Pitfall 4: The identity step must never fail the poll
**What goes wrong:** a new venue call inside `run_poll_allocator_positions_job` that raises would flip `sync_status` and blame the user's key.
**How to avoid:** Wrap it, classify the error, log it without the id value, never touch `sync_status` from this step, and retry next poll. Test that an identity-read exception leaves the poll outcome and `sync_status` unchanged.

### Pitfall 5: Reconnect now collides for ccxt
**What goes wrong:** `reconnect_allocator_api_key` sets `disconnected_at = NULL`, and the index then refuses with a raw 23505. That was previously MT5-only.
**How to avoid:** Map it to a named refusal (RPC or client), and test it.

### Pitfall 6: The legacy store has other readers
**What goes wrong:** deleting or "fixing" `allocator_equity_snapshots` breaks R1 (match.py per-symbol breakdown), R2 (compare adapter), R5 (GDPR export) and R6 (SQL enqueue/cron), per the `allocator_equity_derive.py` header.
**How to avoid:** Only stop **rendering** it on My Allocation. The refresh job's "today-only sum" defect stays for those readers. See Open Question 5.

### Pitfall 7: The TEST database is empty, so data-reading migration blocks refuse
**How to avoid:** Any census inside a migration must tolerate zero rows. The PROD census is a separate read-only script, not a migration `DO` block.

### Pitfall 8: The derived compose can be trustworthy and wrong
**What goes wrong:** with two keys on one account, the compose is trustworthy and double-counts.
**How to avoid:** Apply the identity gate in **both** Python (delete the row) and TS (`equityHistoryState`). Test: two eligible keys with the same `(exchange, venue_account_id)` → no `equity_curve` row.

### Pitfall 9: Composite members
**What goes wrong:** composite strategies stitch several keys over disjoint windows. Two live members on one account would be flagged duplicate by the stamper.
**How to avoid:** Resolve Open Question 2 before the stamper plan. Until then, skip keys that are members of a multi-key composite (`strategy_keys`), or flag them only.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Evading the fence by supplying a forged id | Tampering | The id comes from the venue via our server only; the client cannot write the column (INSERT/UPDATE revoked; scrub trigger). The residual CR-01 provenance note carries over. |
| Cross-tenant identity leak via the unique index | Information disclosure | Index is `user_id`-leading (C-08); refusal copy names no id and no other key |
| Uid readable by the owner's browser | Information disclosure (bounded) | `authenticated` already has column SELECT (164.5.3 D-01-PRIME), RLS owner-scoped; display stays MT5-only (`key.exchange === "mt5"`) |
| Duplicate marker pointing at another tenant's key | Tampering | Written only by service_role in the worker; the FK target must share `user_id` (assert in the migration, e.g. a CHECK via trigger or the stamper's own same-user lookup) |
