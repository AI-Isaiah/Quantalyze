# Phase 167.1.2 Plan 15: Open Positions keeps each key's own latest poll

**Open Positions now shows each key's positions as of that key's own latest `asof`, read through a bounded per-key query that returns a named error at the 1000-row cap instead of a partial list. A position closed before the key's latest poll no longer shows.**

## Performance

- **Duration:** 12 min (2026-09-29T18:00:52Z to 18:13Z)
- **Tasks:** 3/3
- **Files:** 2 created, 4 modified

## Accomplishments

- `src/lib/latest-holdings-per-key.ts` (new):
  - `latestHoldingsPerKey` is the pure filter: "that key's rows at its own latest asof; ordering is not trusted for correctness". It finds each key's maximum with one scan and keeps the matching rows with a second, so input order does not matter.
  - `fetchLatestHoldingsPerKey` is the bounded read, in three steps: the owner's key ids, then each key's latest `asof` (in parallel), then that key's rows at it.
  - `HOLDINGS_ROW_CAP = 1000`.
- `derivePhase07Fields` applies `latestHoldingsPerKey` just before the `holdingsMap` loop. `holdingScopeKey` and the collapse loop are unchanged (D-08).
- In `getMyAllocationDashboard`'s `Promise.all`, the `allocator_holdings` slot now calls `fetchLatestHoldingsPerKey` with the same column list. The result keeps the name `phase07HoldingsRes`, and the same `assertOk(phase07HoldingsRes, "allocator_holdings")` checks it.
- The key set is unchanged: every key the allocator owns, departed ones included. Two things in the schema guarantee this, and the docblock cites both by symbol. First, `allocator_holdings.api_key_id` is a foreign key that refuses to delete a key while it still has holdings (a delete aborts with 23503 unless the holdings are cascaded), and `enforce_allocator_holdings_owner_coherence` pins each row to one of the owner's keys. Second, a departed key is only soft-disconnected (`disconnect_allocator_api_key`), so its `api_keys` row stays.
