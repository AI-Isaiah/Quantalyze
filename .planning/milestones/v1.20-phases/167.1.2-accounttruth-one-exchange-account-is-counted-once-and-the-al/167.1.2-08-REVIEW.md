## Warnings

### WR-01: The stamp-gate bucket reads a stale marker as resolved, so the gate can show 0 while keys are still unchecked

**File:** `scripts/accounttruth-census.mjs:136-144` (SQL_A, both `live_keys_unstamped_unmarked` arms)

**Issue:** The bucket excludes any key with `holder_id IS NOT NULL`. A marker is never cleared when
its HOLDER departs (D-18, stated in the script's own (b) comment). Take a key that was marked
against a holder that has since disconnected. It is no longer blocked by the index, and it is not
stamped until its own next successful poll. If that poll keeps failing (`error`,
`sign_in_failed`), or the key is not polled at all, it stays unstamped, outside the duplicate
check, and invisible to this bucket. The runbook's step-3 "Done" line reads only this bucket being
0, so that gate can pass with unresolved keys left behind. The vitest section (5) checks the arms
only by substring (`holder_id IS NULL`), so it cannot catch this semantic gap.

**Fix:** Count a key as resolved only if its marker points at a holder that still holds the
index slot. Use `disconnected_at IS NULL`, the predicate of the partial unique index, not `eligible`.
A holder that is revoked but still connected keeps blocking the stamp, and an `eligible`
predicate would make its sibling unresolvable for good:
```sql
SELECT e.exchange || '.live_keys_unstamped_unmarked', count(k.id)
  FROM exchanges e
  LEFT JOIN keys k ON k.exchange = e.exchange AND k.eligible AND NOT k.venue_known
       AND NOT EXISTS (SELECT 1 FROM keys h
                        WHERE h.id = k.holder_id AND h.user_id = k.user_id
                          AND h.disconnected_at IS NULL)
 GROUP BY e.exchange
```
Make the same change to the `all.` arm. Add a fixture or a SQL-semantics test that would fail on a
marker whose holder has departed. One option is a bucket such as `live_keys_marked_holder_gone`,
so the gap is printed rather than folded in.

## Info

### IN-01: The MT5 stamp skips the 128-character cap, and Python `strip()` is not exactly JS `trim()`

**File:** `analytics-service/services/account_identity.py:510-518`, `analytics-service/services/mt5_validation.py:221`

**Issue:** `_mt5_account_id` returns the session value as it is. The ccxt path goes through
`_normalise`, which enforces `MAX_VENUE_ACCOUNT_ID_LENGTH` (the zod `.max(128)` twin).
`int()` accepts digit strings far longer than 128, so an absurd login would be stamped where
connect's schema refuses it. Separately, the docstring says the helper "matches the connect routes'
`api_key.trim()`", but the two whitespace sets differ. Python strips `\x1c`-`\x1f` and `\x85`,
which `int()` also tolerates. JS trims `﻿`. A connect-stored login carrying one of those
would not collide with a poll-stamped one. Both cases are edge inputs.

**Fix:** Apply the same length cap in `_mt5_account_id`, treating an over-cap value as `no_id`. Make
the docstring say "equivalent for ASCII whitespace" rather than claiming byte equality.

### IN-02: The read-only and RLS read-backs run in different sessions from the counts

**File:** `scripts/accounttruth-census.mjs:566-583, 652-675`

**Issue:** `realSqlRunner` spawns one psql per statement. The `transaction_read_only` and
`row_security` read-back proves the PROBE's session honoured PGOPTIONS. It assumes, rather than
proves, that each later session did too. That holds when the pooler treats startup options
deterministically, which is likely, and every statement is a SELECT anyway. Still, the comment
"a pooler that silently dropped PGOPTIONS fails loud here" claims more than one session can show.

**Fix:** Either run the probe and the sections in ONE psql session, with the statements on stdin
under `-v ON_ERROR_STOP=1`, or prefix each section's output with its own
`current_setting('transaction_read_only')` column and refuse a row where it is not `on`.

### IN-03: Rough CLI edges

**File:** `scripts/accounttruth-census.mjs:719-748`

**Issue:** `--fixture` passes the file to `JSON.parse(readFileSync(...))` without a try/catch, so a
missing or invalid file ends in an uncaught stack trace, not a clean exit 1 or 2. `--print-sql`
silently ignores any other argument passed with it. The header also says the printed text is
"byte-identical to what live mode sends", but the printed form appends `;`.

**Fix:** Wrap the fixture read in a try/catch with an exit-2 usage error, reject extra arguments in
print mode, and soften the "byte-identical" wording to "identical apart from the terminating `;`".

### IN-04: An MT5 stamp needs no venue call but still gives up when the poll budget is spent

**File:** `analytics-service/services/job_worker.py:9549-9560`, `analytics-service/services/account_identity.py:658-661`

**Issue:** MT5 polls hold the shared terminal and can use most of the handler timeout. When the
remaining budget is 0 or less, the stamp returns `skipped_no_budget`, even though the MT5 branch
makes only DB calls. MT5 keys now escalate too, so a slow-polling unstamped MT5 key would log
ERROR every day for a check that needed no terminal time. Whether real MT5 polls exhaust the budget
has not been measured.

**Fix:** Watch for `skipped_no_budget` on `venue mt5` after deploy. If it appears, give the MT5 branch
a small fixed DB-only budget that does not depend on the terminal time used.

### IN-05: TODOS A-3 does not yet say that the poll now stamps legacy MT5 keys

**File:** `analytics-service/services/account_identity.py:466-474` (MT5 branch of `_stamp`), with
`analytics-service/services/mt5_validation.py:202-221`

**Issue:** The identity is the bare login. TODOS A-3 records that a login is unique only within a
broker server. Before this change, A-3 could bite only at connect or rotate, where the user gets a
refusal. The poll now also stamps pre-column MT5 keys. If two of one owner's keys were on different
brokers with the same login number, the second would be marked `duplicate` and grouped with the
first by `allocator_equity_derive.account_groups`. That is not silent: the key card shows the
duplicate note and an audit event fires. But no refusal happens at connect time.

The exposed set is closed. New MT5 keys are stamped at connect (`validate-and-encrypt/route.ts:771-774`
writes `api_key.trim()`). The composite RPC cannot create an MT5 key: migration 20260812083206
says MT5 cannot be a composite member. So only keys connected before 2026-08-12 are affected. The
runbook measured those as 2 PROD keys, on one broker account, for which a `duplicate` marker is the
correct result. Uniqueness is not weakened. Per-owner scope is by design, and cross-owner keys on
one account are expected and out of the index's reach.

**Fix:** Amend TODOS A-3 in the same PR with one sentence: the poll stamp (167.1.2, Option B)
now also covers pre-column MT5 keys, and a cross-server login clash would show up as a `duplicate`
marker rather than a connect refusal. If a later change opens another path that creates a NULL MT5
key, A-3 should be re-scored then.

### IN-R2-07 / IN-02 / SFH L-1: accepted

Each census statement runs read-only through its own session settings. `realSqlRunner` builds every psql invocation
through `psqlInvocation`, and that function sets `PGOPTIONS: PGOPTIONS_READ_ONLY`
(`-c default_transaction_read_only=on -c row_security=off -c statement_timeout=...`) on every call, not only on the probe.
So no statement is sent without the read-only startup options. What stays a sample is the READ-BACK.
`READ_ONLY_PROBE_SQL` proves only that its own session received the options. The comment "a pooler that silently dropped
