## SFH-R2-01: the fixer's "residual" is SFH-01's main path, unchanged. N4 now pins it (HIGH, data integrity)

**Evidence.**

- Round 1's loss sequence was: the bootstrap enqueues a reconstruct, the refresh is enqueued in the
  same run, the refresh writes today's row, the reconstruct later ends `failed_final`, and the book
  now has snapshots, so it is never bootstrapped again. In round 1 the `bkj` test counted a
  `pending` row as bootstrapped. It still does: `pending` is in the new in-flight-or-done list. So on
  the day a book is first bootstrapped, the refresh is enqueued in the same call, exactly as before
  the fix.
- `run_refresh_allocator_equity_daily_job` does not check for an in-flight reconstruct. It persists
  a row whenever the latest holdings produce a non-empty breakdown, and it returns
  `no_holdings_today` only when they do not. The refresh job is fast and the reconstruct crawl runs
  up to 30 minutes with up to `max_attempts` retries, so in practice the refresh's row lands first.
- The status filter therefore closes SFH-01 in only two cases:
  - (a) a zero-snapshot book with **no holdings**, where the refresh writes nothing and the failed
    key is retried the next day;
  - (b) a `failed_final` row that already exists when this migration first applies.

  The measured PROD case in the migration header, a key connected 2026-09-24, is a key that polls,
  so it has holdings. It falls in the unclosed path.
- **Arm N4 now pins the residual, the same way round-1 N4 pinned the defect.** It asserts that a
  zero-snapshot book whose reconstruct failed gets 1 retry **and 1 refresh in the same call**. That
  refresh is the enqueue that closes the gate if the retry also fails.
- **A second path, not mentioned in the fix report or the header.** A reconstruct writes snapshot
  rows itself: the sole-key path through `replace_allocator_equity_snapshots`, the multi-key path
  through `persist_equity_snapshots`. On a two-key zero-snapshot book, suppose key A's reconstruct
  ends `done` and writes rows, and key B's ends `failed_final`. The book then has snapshots, and B is
  never re-bootstrapped. Round 1 named this case and asked for a sibling arm. No arm was added, and
  no refresh-timing change can close it.
- **The header overstates the recovery path.** It says "the key's next sync through
  request_allocator_holdings_sync recovers it". That RPC runs only from a user-initiated Exchanges-page
  sync. Per D-17 (b) it also returns `{already_inflight}` before its reconstruct gate whenever a poll
  is in flight. Those are exactly the two conditions this migration exists to work around. Nothing
  tells the user, or an operator, that a sync is needed. The only trace is an
  `allocator.equity.reconstruct_failed` audit event, and the `failed_final` row itself is reaped
  after 90 days.

**Can it be closed without contradicting D-17?** Only part of it.

- **The single-key path (the main one): yes.** D-17's revision-1 text says "the refresh waits
  until every qualifying key has a reconstruct job **in any status**". The SFH-01 fix already
  narrowed that literal: `failed_final` no longer counts. D-17 states its two load-bearing halves
  as "the refresh is still enqueued, and the reconstruct is still capped". Both still hold if a
  **zero-snapshot** book's bootstrapped test (`bkj` only) counts `done` and nothing else. The refresh
  is then enqueued on the first run after every reconstruct is `done`.
  - The cost to the curve is nil when the reconstruct succeeds: its window ends today UTC
    (`end_date` in `run_reconstruct_allocator_history_job`), so it writes the rows the early refresh
    would have written.
  - What this changes is plan-level arms, not D-17: Z1, B, C, N3c and N4 assert a same-run refresh
    and would need rewriting.
  - One real policy choice remains, a **bounded give-up**. With `done`-only, a key whose reconstruct
    can never succeed keeps its book at zero forever. For example, a `failed_final` count at or
    above N within the 90-day retention could count the key as bootstrapped. The give-up should
    write a durable trace (see SFH-R2-02). Picking N is the orchestrator's or the founder's call.
  - An equivalent fix outside these four files: `run_refresh_allocator_equity_daily_job` skips
    writing for a zero-snapshot allocator while any of its keys has a reconstruct in flight.
- **The sibling path: no, not in this function.** Closing it needs a key-level gate on a book that
  already HAS snapshots. D-17 (c) scopes the arm to zero-snapshot books because "reconstructed" is
  not durable in `compute_jobs` (done rows are reaped after 30 days). This is the same shape as the
  unrouted R-12-1: a key on a book with snapshots that has no backfill. The root cause is the same
  too: no durable per-key "history reconstructed" fact.

**Fix.**

1. Take the `bkj`-`done`-only change with a bounded give-up, or the equivalent refresh-side skip, and
   rewrite N4 to assert no same-run refresh while the retry is in flight.
2. Route the sibling path together with R-12-1 (round-1 SFH-05), through `/gsd-phase --edit`, to one
   phase that adds a durable per-key reconstruct marker.
3. Until both are done, the header's "RESIDUAL, recorded (T-167.1.2-58)" should say what it is: the
   primary path for any book with holdings. It should not say it is recovered by the next sync.

## SFH-R2-02: the SFH-02 swallow turns a loud cron failure into a Postgres-log line that nothing reads (MEDIUM)

**Evidence.**

- Before the fix, an error in the bootstrap loop failed the pg_cron run, which is at least visible
  in `cron.job_run_details`.
- Now the bootstrap sub-block's `WHEN OTHERS` emits `RAISE WARNING` and the call returns normally.
  pg_cron records the run as succeeded, and the WARNING exists only in the Postgres server log.
- `scripts/prod-prober/arms/cron-obs.mjs` does not watch this job. Round-1 SFH-03 (no run summary,
  cron unwatched) was deferred.
- Round 1's SFH-02 fix asked for "RAISE WARNING **and record a failure (see SFH-03)**". Only the
  first half was done.
- Consequence: an error that recurs every day disables the whole bootstrap arm, with no signal. Examples
  are a column renamed under one of the anti-joins, a new CHECK or trigger on `compute_jobs`, or
  a statement-level failure. Every zero-snapshot book then stays at zero. That is the defect this
  migration was written to fix, and it comes back silently.

**Fix.** In the sub-block's handler, after the savepoint rollback, write one durable row with the
SQLSTATE and SQLERRM through the existing SQL-side audit sink (`audit_log` already takes inserts
from SQL functions in this repo). That row survives, because the outer transaction still commits
the refresh loop. Add an arm that asserts the row exists after X2's forced failure. This is a small
subset of SFH-03 and does not need the prober work.

## SFH-R2-03: one poisoned key rolls back EVERY book's bootstrap, every day (MEDIUM)

**Evidence.**

- The per-key handler catches only `unique_violation` and `serialization_failure`. Any other error
  on one key's enqueue reaches the sub-block's `WHEN OTHERS`, which discards the reconstructs of
  every book taken in that run, including books processed before the bad key.
- If the error is deterministic for that key, it recurs on every run. Examples: a trigger or
  constraint that refuses its row, or a data condition in the helper. Then no zero-snapshot book is
  ever bootstrapped, and per SFH-R2-02 nothing records it.
- X2 exercises exactly this shape, with a P0001 on one key, and asserts it as the intended outcome.
  The arm is right to prove that the refresh survives. But its fixture is also a demonstration that
  one key blocks every other book.

**Fix.** Give the per-key block its own `WHEN OTHERS` as well. It logs the key id and SQLSTATE,
writes the durable row from SFH-R2-02, skips the rest of that key's book, and continues with the
next book. Skipping is safe by the same construction the header already relies on: a book whose key
has no in-flight-or-done row is not bootstrapped, so its refresh stays withheld. Keep the sub-block
for errors that come from the book-selection query itself. Add an arm with X2's fixture that asserts
the other book's key still gets its reconstruct.

## SFH-R2-04: two terms the fix relies on are unpinned by any arm (LOW)

**Evidence.**

- **`failed_retry` in the in-flight list.** No arm seeds a `failed_retry` row; the only statuses
  seeded are `failed_final` (N4, F) and `done` (N4d). Removing `'failed_retry'` from `bqj`/`rkj`
  leaves every arm green. Yet the fix report calls this term load-bearing: without it the cron
  enqueues a second 30-minute reconstruct while one is scheduled for retry. Neither the enqueue
  helper's pre-check nor the partial unique index covers `failed_retry`. Both list only `pending`,
  `running` and `done_pending_children`, so nothing else would stop the duplicate.
- **The two-key sibling arm** (one key `done`, one `failed_final`) that round 1 asked for was not
  added. Whatever SFH-R2-01 decides, that case needs an arm stating the chosen behaviour.

**Fix.** Add an arm that seeds a `failed_retry` reconstruct on a zero-snapshot book and asserts 0 new
reconstructs, with a RED-UNDER-M that drops `'failed_retry'` from `bqj` and `rkj`. Add the sibling
arm once SFH-R2-01's decision is made.

## SFH-R2-05: a reconstruct that always fails on a no-holdings book retries every day, with no back-off (LOW)

**Evidence.**

- Round 1 offered a re-enqueue back-off as one of two bounds, and neither bound was added.
- The failure mode covers a zero-snapshot book whose key refuses reconstruction for a
  non-credential reason, so its `sync_status` stays qualifying. The reconstruct failure path does
  not write `sync_status`; only the poll path can move a key to `sign_in_failed`/`error`. Such a key
  is re-enqueued every day. Each enqueue carries its own `max_attempts`, and each attempt can take
  up to 30 minutes of crawl.
- The books are ordered newest-first under a cap of 25. So 25 or more such books that are newer
  than a legitimate book would starve it, and nothing records the starvation.
- Today the population is small, which is why this is rated LOW.

**Fix.** Skip a key whose latest reconstruct row is `failed_final` and newer than N days. Or fold
it into SFH-R2-01's bounded give-up, which needs the same count.

## SFH-R2-06: minor items (INFO)

- **The WARNINGs leak nothing.** The per-key messages carry the api_key UUID and the SQLSTATE. The
  sub-block message carries the SQLSTATE and SQLERRM. SQLERRM is the primary message only:
  constraint and unique-violation row values go to DETAIL, which is not interpolated. No credential
  column is read by either loop.
- **`v_bootstrap_enqueued` counts skipped keys.** It is incremented after a WARNING-skipped
  enqueue and after a helper call that returned an existing in-flight id. This is conservative:
  it can only stop the cap early. No action needed.
- **`query_canceled` is not caught by `WHEN OTHERS`.** The fix report says this, and it is correct.
- **The rollback is unchanged.** Round-1 SFH-08's note still applies: restoring 075 re-admits
  revoked keys to the refresh, and the rollback header does not say so.
- **The plan's threat register is stale.** `167.1.2-12-PLAN.md` still carries the old
  T-167.1.2-42 and T-167.1.2-58 text, as the fixer flagged. Per SFH-R2-01, T-167.1.2-58's "no first
  snapshot row closes the gate before every qualifying key's reconstruct is enqueued" is still not
  what prevents stranding: an enqueued reconstruct can still fail after the gate closes.
