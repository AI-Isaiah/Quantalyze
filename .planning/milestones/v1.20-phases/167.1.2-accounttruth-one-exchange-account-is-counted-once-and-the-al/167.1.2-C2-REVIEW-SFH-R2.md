### SFH-R2-01 — medium — a poll landing between the two reads is read as an emptied account

**Location:** `analytics-service/services/equity_reconstruction.py:1936-1958` (per group: the
`_sel_latest_asof` read, then `_polled_empty_since`), and `:1993-2027`.

**Failure scenario.** For each group, the refresh makes two separate round trips:
1. It reads the latest `asof` (for example yesterday).
2. It asks whether a `done` poll was claimed after that day.

Suppose a member's poll persists today's rows and is marked `done` between those two reads. Then
read 1 missed today's rows and read 2 finds the poll. The group is counted as **emptied**: it
contributes $0, and the row is persisted under `ON CONFLICT (allocator_id, asof) DO NOTHING`. The
account's real balance is gone from that day's row for good. The audit says `emptied_accounts: 1`,
which reads like a correct outcome.

**Measured.** I wrapped `_polled_empty_since` so that it seeds today's row and a done job before
calling the real function, which is exactly the interleaving above. Key 1 has 1000 USDT today.
Key 2 had 500 BTC yesterday and 510 today, landing mid-refresh. Result:

```
RACE today [(1000.0, {'USDT': 1000.0})] emptied 1      # expected 1510
```

**Likelihood.** The window is one `db_execute` round trip. The poll's persist-to-done span is
longer, because it includes the audit, the first-sync RPC and the identity stamp. So the race
needs the refresh coroutine to stall between its two awaits, for example under a saturated
thread pool while the daily fan-out runs polls and refreshes together. It is rare, but the
result is a permanent wrong row.

**Recommendation.** When the proof comes back true, re-read the group's latest `asof`. If it has
moved past the value used for the proof, read the new day's rows instead of zeroing the account.
This costs one extra query, and only on the emptied path. Add a test with exactly the interleaving
above.

```python
if latest < today_iso and await _polled_empty_since(supabase, eligible, latest):
    recheck = [str(r["asof"]) for r in (getattr(await db_execute(_sel_latest_asof), "data", None) or []) if r.get("asof")]
    if not recheck or max(recheck) == latest:
        emptied += 1
        continue
    latest = max(recheck)  # a poll landed between the reads: count what it wrote
```

### SFH-R2-02 — medium — a fully emptied book writes no row, so the old balance stays "latest"

**Location:** `analytics-service/services/equity_reconstruction.py:3539-3560` (`if not
breakdown:` leads to the `no_holdings_today` INFO line and audit, then DONE with no row).

**Failure scenario.** CR-04's claim is that an emptied account contributes $0. When the emptied
accounts are the **whole** book, `breakdown` is empty, the job takes the `no_holdings_today`
branch, and it persists nothing. The newest `allocator_equity_snapshots` row is then the last
positive day. Every reader of the legacy store sees that balance as current: match.py's
breakdown, the compare adapter, the GDPR export and the SQL cron's "latest" reads. The code now
holds positive proof that the book is empty (`emptied_accounts: 1` in that same audit) and still
takes a branch that means "nothing to say today", logged at INFO.

**Measured.** One okx key, rows three days ago, a done poll claimed today, and yesterday's
snapshot at 500:

```
ALLEMPTY rows [('2026-09-19', 500.0)]  meta {'reason': 'no_holdings_today', ..., 'emptied_accounts': 1, ...}
```

The same happened before plan 10 on main, so this is parity for the "no rows" path. But CR-04 is
what makes this state reachable with proof. The fix report's "contributes $0" does not hold when
the empty account is the whole book.

**Recommendation.** Tell "no rows because nothing polled" apart from "no rows because every
counted account is proven empty":
- when `emptied_accounts > 0` and every counted account was emptied, persist a `$0` row with an
  empty `breakdown`, checking first that the terminus clamp and the reconstruct readers accept a
  zero row. If that is a founder call, at least use a distinct audit reason (`book_emptied`) and
  log at WARNING;
- add a test for this case.

### SFH-R2-03 — high — working-first drops the older failing key's history under a benign flag

**Location:** `analytics-service/services/job_worker.py:10372-10390` (`pool = working or members`,
`kept = min(pool, …first_return_day…)`), and the benign tokens at `:10631-10640`.

**Failure scenario (a key rotation, the realistic D-18 case).** Old key H holds the account, with
returns from May. H's credential is rotated out, so H is `sign_in_failed`, still active and
connected. New key M (`duplicate` or `composite_member`) is working, with returns from June. The
pool is the working members only, so M is kept and H is excluded. The curve is recomputed in full,
so the book's whole history now **starts at M's first day**. H's earlier returns leave the curve,
Sharpe, CAGR and drawdown. The payload carries only the benign `duplicate_shared_account_counted_once`
or `composite_shared_account_counted_once` flag, so it stays `is_trustworthy: true`. The reader
shows **"ready"**, with no signal that history was dropped.

For a composite this changes what the book showed yesterday. While both keys were working, H was
kept (its returns start first), and the curve went back to May. The day H starts failing, the
displayed history shrinks to June, silently.

**Measured** (H: 34 days from 2026-05-01, `sign_in_failed`; M: 3 days from 2026-06-01, working):

```
KIND duplicate        first 2026-06-01 n 3 trust True flags ['duplicate_shared_account_counted_once', 'sole_key'] reasons []
KIND composite_member first 2026-06-01 n 3 trust True flags ['composite_shared_account_counted_once', 'sole_key'] reasons []
```

Fixer A recorded this as the WR-01 residual ("a design call, not taken here"). What makes it a
silent failure and not only a design gap is the benign flag: the truncation is neither blocking
nor visible.

**Hidden errors:** a new key whose per-key dailies do not reach back as far as the old key's, for
example because the venue's history depth has rolled forward since the old key's backfill. Also a
new key with `key_inputs` but no returns yet. That one is kept anyway (it is the only working
member), so the whole book becomes `DROPPED_KEY` untrustworthy and reads `derivation_rejected`
while the old key's full history sits unused.

**Recommendation.** One of the following, in order of preference:
1. Stitch the account. Use the dropped member's returns for the days before the kept member's
   first return day, and the kept member's returns from its first day on (D-09 case (2) ordering).
   One account is still one series, so nothing is double-counted.
2. If stitching is deferred, stop calling it benign. When a dropped member's first return day is
   earlier than the kept member's, add a flag that the reader turns into a visible note, or a
   blocking reason such as `shared_account_history_truncated`.

Add a derive test: failing older holder plus working newer member, asserting that the curve starts
at the older start (option 1) or is not silently trustworthy (option 2).

### SFH-R2-04 — medium — "no working key" is counted once and then goes unseen

**Location:** `analytics-service/services/job_worker.py:10453-10465` (WARNING) and `:10636` (the
benign `shared_account_no_working_key` token); `equity_reconstruction.py:1978`
(`no_working_accounts`, audit and INFO only).

**Failure scenario.** Both keys of one shared account fail (`error` / `sign_in_failed`). The derive
counts the account once, which is correct. But the account's series stopped on the day the keys
began failing, and after that it is **flat-carried at r = 0** while the book's other accounts keep
moving. What each layer does with that:
- The payload flag is benign, so the curve stays trustworthy.
- The reader reads no flag.
- `countsAsDuplicate` is false, because the holder is not working.
- `identityStillPending` is false, because the holder's id is known.

So the book is **"ready"**. Its displayed return is diluted by a dead account's frozen capital,
and nothing on screen says so. The only signals are a WARNING (a breadcrumb in Sentry, not an
event, so it pages nobody), a flag nobody reads, and an audit field.

**Measured** (a failing pair at 100k, plus a healthy okx key O at 50k earning 2%/day for three
more days):

```
NOWORK last {'date': '2026-06-06', 'equity_usd': 150000.0} trust True
       flags ['degraded', 'duplicate_shared_account_counted_once', 'shared_account_no_working_key', ...]
       returns tail [{'r': 0.0064}, {'r': 0.0065}, {'r': 0.0066}]        # O's own days were +2%
```

A single failing key with a known identity already behaves this way, before C2. What C2 adds is a
new flag that claims to make the shared-account case "not silent" when it is.

**Recommendation.**
- Surface it where the owner looks. The reader already has every key's `sync_status`. When an
  eligible account group, or a single eligible key, has no working member, show a note or reason
  such as "One account's keys are not syncing; its history stops on <date>. Check it on the
  Exchanges page." This mirrors `key_not_syncing`, which today covers only identity-pending keys.
- Alternatively, have the reader treat the flag as a caption.
- At minimum, do not describe the flag as making the state loud.
- Pin whichever is chosen with a readiness or render test.

### SFH-R2-05 — low — the new Sentry captures are fire-and-forget in a server read

**Location:** `src/lib/queries.ts:4315` (`derived_row_read_failed`) and `:4334`
(`derived_row_rejected`).

`captureToSentry` returns the import chain **so that a server caller can hold the request open
until the capture settles**. Its own doc block says a discarded chain "can be reaped before Sentry
flushes and the alert is lost silently", and that server call sites should schedule it with
`after()` (as in `resilient-fetch.ts`). Both new calls drop the promise. The `console.error`
before each one survives, so the event is not lost from Vercel logs. But the Sentry event, which
is the new alerting half of SFH-05 and SFH-06, is best-effort.

Separately, as fixer B recorded: a book holding a permanent version-1 row (ledger venues that
never re-derive) sends a `not_version_2` Sentry warning **on every dashboard render**. Sentry
groups them by message, so the volume ends up in one issue, but that issue will always read as
active.

Also, `derivation_rejected` with its Sentry warning fires on every render during the ordinary
new-key backfill. A counted key with `key_inputs` but no returns yet makes the compose
`DROPPED_KEY`, so the row is written untrustworthy. The reader cannot tell that transient state
from a permanent rejection, so the `derived_row_rejected` issue will stay active in normal
operation. It will also say "did not pass its checks" for something that heals on its own.

**Recommendation.** Schedule both with `after(captureToSentry(...))` from `next/server`.
`queries.ts` is server-only: it imports `@/lib/supabase/server` and `@/lib/supabase/admin`. Every
`"use client"` importer of `@/lib/queries` (`HoldingsTabPanel.tsx`, `AllocationsTabs.tsx`,
`EquityHistoryRebuilding.tsx`) uses `import type` only, which is erased, so the bundle constraint
in the helper does not apply. Or schedule it from the page that calls `getMyAllocationDashboard`. Consider
capturing `not_version_2` once per allocator per day (for example keyed by `computed_at`), or
leave it and record the expected steady-state volume in the Sentry issue.

### SFH-R2-06 — low — the new refresh counters are written, and nothing reads or alerts on them

**Location:** `equity_reconstruction.py:1945-1951` (`never_polled`), `:1978` (`no_working`), and
the INFO log line at `:3629-3639`.

`never_polled_keys`, `no_working_accounts` and `emptied_accounts` go only into `refresh_complete`
audit metadata and an INFO line. `git grep` finds no reader of any of the three outside the
writer. `never_polled_keys > 0` on a book that already has snapshots is the SFH-08 case (a day
written without an account, then a next-day step equal to its whole balance), and it logs nothing
above INFO. `emptied_accounts` is where SFH-R2-01's false $0 would show, and it looks the same as
a correct zero.

**Recommendation.**
- Log at WARNING when `never_polled_keys > 0` and the book already has snapshots.
- Log at WARNING when `emptied_accounts > 0`. A book emptying out is rare, so the line is cheap
  and makes SFH-R2-01 findable.
- Leave `no_working_accounts` at INFO for the refresh, since SFH-R2-04 carries the user-facing
  half.

## What is done well

- `account_groups` is deterministic: members are sorted by id and groups by their first member.
  An unresolvable marker or a self-pointer becomes a group of one, so a bad marker can never merge
  or remove an account.
- The refresh's group read closes CR-03 cleanly: one account is read once, across every member's
  rows, departed members included.
- Every CR-04 no-proof case falls back to the carry, never to $0: no done job, a claim on the
  rows' own day, `complete_with_warnings`, `error`, MT5, sFOX and a running poll. A failed proof
  read raises into FAILED.
- Fixer B's rejection paths are pure at the decision (`derivePhase07Fields`,
  `equityHistoryReadiness`), log at the read site only, and never log a curve value.
- SFH-11(b) drops the leg. It does not compute a Sharpe on fewer observations.
