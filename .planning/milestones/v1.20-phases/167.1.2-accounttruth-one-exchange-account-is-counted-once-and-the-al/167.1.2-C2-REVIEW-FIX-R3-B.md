### R3-WR-04: the `derived_row_rejected` capture fired on every 30-second poll

**Files modified:** `src/lib/queries.ts`, `src/lib/queries.my-allocation.test.ts`

**Commit:** `1476a6a65`

**Applied fix:**
- **The window.** `DERIVED_ROW_CAPTURE_WINDOW_MS = 6 h` is exported so the test can use it. A module-level `Map<string, number>` is keyed `${allocatorId}:${rejection}`. `shouldCaptureDerivedRowRejection` returns true, and records the time, only when the pair has no entry or its last report is at least one window old.
- **Only the capture is gated.** The `derived_row_rejected` capture is gated. The `console.error` line above it runs on every load. `derived_row_read_failed` is unchanged, because it was not in scope.
- **`// ponytail:` comment** (the ceiling):
  - the window is per server instance and in memory, and it resets on a cold start;
  - each warm instance keeps its own window, so the real bound is one event per (allocator, rejection) per 6 h **per instance**, not per deployment;
  - entries are never evicted, and the map holds at most one entry per allocator per rejection token.
- **Bound.** Before: about 120 events per hour per open Overview tab. After: at most 1 per 6 h per (allocator, rejection) per warm instance.
- **Why 6 h.** The writer recomposes daily (05:30 UTC). With a 6 h window, a lasting state still reports a few times a day per instance, so the Sentry issue stays visible without staying permanently active.
- **Test hook.** `__resetDerivedRowCaptureThrottleForTests()` follows the repo convention in `sentry-capture.ts` (`__resetCaptureThrottleForTests`). The D-02 describe's `beforeEach` now calls it. Every test there reads as `user-1`, so without the reset the second capture-asserting test in the file would have been throttled.

**Tests (new, `queries.my-allocation.test.ts`):**
- `Date.now` is stubbed and restored in a `finally`.
- Three polls inside the window give 1 capture and 3 log lines.
- A malformed row for the same allocator is captured, because it has its own window.
- At `t0 + window`, the still-untrustworthy row is captured again: 2 captures and 5 log lines in total.

**RED → GREEN, and proof the test can fail:**
- RED 1: the suite failed before the implementation, because the reset export did not exist. That alone is weak evidence, so I also ran two neuters after the implementation.
- Neuter 1: the window check made to always return true, i.e. capture on every load. The new test failed with `expected 3 to be 1`.
- Neuter 2: the rejection dropped from the key. The new test failed with `expected +0 to be 1` on the malformed arm.
- After each neuter, the source was restored with Edit and confirmed byte-identical to a backup taken before the neuters (`cmp`). Then 185/185 passed across `queries.test.ts` and `queries.my-allocation.test.ts`.
- A side effect of neuter 1: SFH-05's positive-control test also failed, because my test's spies were not restored after its first assertion threw. The new test now restores its spies in a `finally`, so a failure there cannot spill into the next test.

**Status:** fixed
