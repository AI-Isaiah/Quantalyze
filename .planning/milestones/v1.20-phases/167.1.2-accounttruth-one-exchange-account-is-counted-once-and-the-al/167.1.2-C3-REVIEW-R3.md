**WR-01 (R2) detail.** `_load_allocator_daily_returns` is at `job_worker.py:10389-10473`. `_load_returns` calls it at `:10596`.
- **The query shape.** It reads one key per loop: `eq(allocator_id)` + `eq(api_key_id)`, then `gt(date, cursor)`, `order(date)` and `limit`.
- **Why the order is total.** `(api_key_id, date)` is unique (`baseline.sql:13358`), so with the key fixed by `eq`, the date cursor is a total order.
- **Stop and cap.** It stops on an EMPTY page, not a short one. The cap check comes after the empty check, so a read landing exactly on the cap is read whole. Past the cap it raises `PaginatedSelectTruncated` with the byte-same hint, and the unchanged `except` arm disposes of it as permanent.
- **Key set.** `key_rows` comes from `_load_keys` (`:10532-10547`, `api_keys` by `user_id`). Every consumer (`first_return_day` `:10630-10637` through `.get(row["id"])`, and `_grouped` `:10811-10815`) admits only ids in `key_rows`. So restricting the read to those ids drops nothing a consumer used.
- **Cap semantics.** The `pages` counter is now a total across keys rather than per query. The ceiling is the same 1M rows, so this is not a finding.

**SFH-C3R2-X1 detail.**
- **Dashboard.** `queries.ts:4448-4470` drains through `drainById`:
  - keyset on `id`, which is the PK and alone a total order;
  - `eq(allocator_id)`, `not(api_key_id is null)` and `gte(date, windowStart)`;
  - natural key `api_key_id|date`.
- **Failure paths are errors, not partial reads.** A page error, a null page, a non-integer id, a non-monotone id, and the 100-page ceiling all return `{ data: null, error }` (`drain-by-id.ts:103-133`). `assertOk` at `queries.ts:4710` then throws.
- **Consumer order.** `buildPerKeyReturnsByApiKeyId` (`queries.ts:3612-3627`) only groups by key and appends in row order. The drain's `(api_key_id, date)` sort, whose uuid and ISO-date parts are both fixed-width so a lexicographic compare is correct, gives it per-key date order.
- **Wizard composite read.** It is fixed the same way (`SyncPreviewStep.tsx:1454-1467`), with the `id` column stripped before the snapshot (`:1550-1552`).

## Regression checks (the brief's invariants)

**1. Writer upsert-then-delete keeps the exact end state.**
- **Refused days end absent.**
  - Derive: the absent list is the span's calendar minus the payload dates. Payload dates are `ts.date().isoformat()` (`job_worker.py:5963`, `:5975`), and the span bounds use the same `.date().isoformat()` (`:6027-6028`), so the set difference compares like with like.
  - `csv_daily_returns.date` is `DATE` (`baseline.sql:11551`), so every stored in-span row is one of those calendar days.
  - Strategy mode with an all-NaN payload: the complement is the whole span, which gives the same end state as the old ranged delete.
- **Out-of-span behaviour differs by writer. Each is unchanged from before, and the two must not be conflated.**
  - **Derive:** every delete carries `gte(span_start)` / `lte(span_end)` AND an `in_` list drawn only from inside the span (`:6056-6062`). It cannot touch a row before `span_start`, so retention-windowed history is preserved exactly as before.
  - **Composite:** the `lt(first_day)` / `gt(last_day)` deletes (`:8600-8611`) deliberately remove out-of-payload rows. That is F5(a) full-series ownership, and it matches the old whole-series delete. "Out-of-span untouched" is true of the derive only.
- **The scope filter is identical.**
  - Derive: `eq(api_key_id)` in key mode, `eq(strategy_id)` in strategy mode (`:6065-6068`). This is the same branch as before.
  - Composite: every statement carries `eq(strategy_id)`.
  - Fix H neuter N4 (scope dropped) turned 6 tests RED.
- **The UPDATE arm is safe.**
  - Payload columns are `api_key_id, allocator_id, strategy_id=None, date, daily_return` in key mode and `strategy_id, date, daily_return` otherwise.
  - The only table columns left unset on UPDATE are `created_at` and `updated_at`.
  - The owner-coherence trigger fires on UPDATE (`baseline.sql:13874`) and checks the same `allocator_id == api_keys.user_id` it checked on INSERT.
  - The one `created_at` reader, the reconcile sweep, excludes any strategy with a live or finished `compute_jobs` row, and composites through `strategy_keys`. Fix H's assessment holds against `cron-manifest.json:105`.
- **Batching is bounded.**
  - `_RECONCILE_DELETE_IN_BATCH = 200` (`:3136`).
  - Both loops slice `[i : i+200]`, and an empty complement sends no delete.
  - The composite `min()`/`max()` over the payload is safe: the F2 guard (`:8033-8042`) returns before the persist when fewer than 2 days are present.
  - `test_h1_derive_batches_a_long_refused_span_into_bounded_in_lists` asserts each batch size is between 1 and 200, and that the batches sum to the refused count.

**2. Keyset reads are total and cannot skip or duplicate.**
- Both Python readers fix the outer key with `eq` and cursor on `date > last`. The index backing each is unique (`:13358`, `:13362`).
- A row present for the whole read is reached, because no page start depends on row counts before it.
- A row is never read twice, because the cursor strictly increases.
- A server cap below the page size only adds requests. Fix E N2 and fix H N6 turned the short-page stop RED.

- Error arms: page error `:109-118`, `data == null` `:119-121`, non-safe-integer id `:126-128`, non-monotone id `:129-133`, and the page ceiling `:103-107`.
