### WR-R2-03 / SFH-R2-02: the positions-unread line cleared on the next failed poll

**Before:** the line read the key's current `sync_status === "complete_with_warnings"`.
A later poll that failed (`rate_limited`, `error`, a classified status) or was still
`syncing` wrote no rows. The key's partial rows stayed, and the line went.

**Now:** the line follows the poll that wrote the rows on screen.
- `fetchLatestHoldingsPerKey` step 2 makes a third read per key: the key's newest
  `allocator.holdings.sync_completed` event of any outcome. It uses the same `user_id`,
  `action`, `entity_type` and `entity_id` scoping as the clean-poll read, with no
  `final_status` filter.
  - The clean-poll read stays as it was. SFH-C4-02 needs the newest clean event, and one
    unfiltered read cannot do both jobs.
- A new helper, `partialPollDay(metadata)`, returns the event's `asof` when
  `final_status` is `complete_with_warnings` and `asof` is an ISO day. Otherwise it
  returns null.
- A key goes into `partialReads` (as `{ api_key_id, asof }`) only when both hold:
  - it contributes rows, so it is in `toRead` after the SFH-C4-01 account grouping;
  - that event's day equals the day of the rows returned.
- **Why the flag survives a failed poll:** a failed poll emits `sync_failed` or
  `persist_failed`, never `sync_completed`, and a running poll emits nothing. So the
  newest `sync_completed` is still the partial one, and it still matches the rows.
- **When the flag clears:** only when a later poll writes the key's rows again.
  - A clean poll on the same day upserts the derivative rows, so its event is newest,
    and it is not partial.
  - A poll on a later day moves the rows' day.
- Every error path returns `partialReads: []`.
- `derivePhase07Fields` gets a defaulted trailing parameter and emits
  `partialPositionReads`. It is an optional payload field, following the precedent set
  by `asof`. Both `...phase07` spreads carry it. No payload whitelist exists; checked
  with a grep for `departedHistoryUnavailable`.
- `partialPositionReadNotes(partialReads, apiKeys, rows)` in `HoldingsTabPanel.tsx`
  renders the line. The CCXT venue gate stays: MT5 and sFOX warnings mean something else.

**Copy change.** "On its last sync" is no longer true once a later sync failed, so the
line now names the sync's day:
- Live key: "Open positions from the Binance key Main could not be read on its sync of
  2026-09-05. Any it holds are missing below until a sync reads them."
- A key that is not live: "... could not be read on its sync of 2026-09-05. Any it held
  then are missing below."

**Behaviour change, on purpose.** K1 gave departed keys no line, because a current
status means nothing for a key that is not polled. Now the line is bound to the rows, and
a departed key whose partial rows are still shown has its derivative positions missing
just the same. So it gets the line, without the promise of a sync. A departed key whose
rows a newer reading superseded contributes no rows and gets no line.

### SFH-R2-03: the age note never fired for a one-key book, or for equally stale keys

**Before:** a row was dated only when `asof < newest row in the book`.

**Now:** `openPositionReadDayNotes(..., today)` dates a row when its `asof` is older
than the later of two days: the newest read in the book, or yesterday (UTC).
- **Why yesterday and not today.** The daily poll runs at 04:00 UTC. Between midnight
  and that poll, a healthy key's latest read is yesterday's, so `asof < today` would
  date every healthy row for four hours a day. With one day of tolerance, a key is dated
  once it has missed a whole day's poll.
- **Why layered on the old rule rather than replacing it.** The book comparison still
  dates, on the same day, a key that missed today's poll while another key read today.
  Dropping that comparison would delay that note by a day. The sentence is true under
  both rules. So the change is a strict superset, and the round-1 arms stay as they were.
- **Why not the key's last poll attempt.** `api_keys.last_sync_at` is stamped only on
  success (`job_worker.py`, success arm), so for a failing key it equals the rows' day,
  and the note would never fire, which is the same defect. It also cannot date a
  disconnected key.
- **Why not the review's status-keyed alternative** (date rows whose key is not live or
  whose last sync failed): that is the class of bug WR-R2-03 removes.
- **Where `today` comes from:** a `useState` initializer in the panel,
  `new Date().toISOString().slice(0, 10)`. UTC, so it matches `asof`. This follows the
  precedent in `AllocatedForm.tsx`. The pure function takes it as a parameter.

**Tests:** `HoldingsTabPanel.key-read-notes.test.tsx`, with the clock pinned to
2026-09-29T12:00Z for that describe. Four new arms:
- a one-key book three weeks stale is dated;
- two equally stale keys are both dated;
- yesterday is not dated;
- two days ago is dated.

**Neuter record:**
- Ignoring `today` turned the 3 dating arms RED.
- Removing the tolerance (`yesterday = today`) turned the yesterday arm RED.

## Needs routing / known limits

1. **Hydration, narrow window.** `today` is fixed when the component mounts. Across UTC
   midnight, the server render and client hydration can disagree about one note's
   presence, which gives a React hydration warning, and the client render wins. The
   window is seconds wide and nothing breaks. It is recorded, not fixed. A
   server-supplied reference day on the payload would remove it.
   A related limit: the dashboard refreshes its payload every 30s without remounting, so
   a tab left open across UTC midnight keeps the old `today` until reload. It is then
   one day lenient: a key that crossed the threshold overnight is dated one reload late.
   The error runs toward fewer notes and never produces a false one.
   **Clock check done:** besides the pinned describe, no panel test puts an `asof` on
   `holdingsSummary`. `HoldingsTabPanel.exposure.test.tsx` uses `asof` only on the
   exposure prop, and its assertions are scoped to the Exposure section. So no other
   test depends on the clock.
2. **Spot rows are still undated.** The Exchange Positions table shows a stale key's
   spot rows with no day. This is the same class as SFH-R2-03, and K1's scope note
   already recorded it. The findings name Open Positions only. It is user-facing, so
   it is for the orchestrator to route.
3. **One more read per key.** The holdings read now makes three step-2 queries per key
   instead of two, all in parallel. It is bounded by the key count, which is capped at
   `HOLDINGS_ROW_CAP`.
4. **A legacy partial poll with no recorded `asof`** (from before C2 round 3) raises no
   line. Nothing binds it to the rows.
5. **Shared eslint cache.** `npm run lint` keeps its cache under `node_modules/.cache`,
   and `node_modules` is a symlink that sibling fixers' worktrees share. Cache entries
   are keyed by path and content, so this cannot produce a false green. It is noted in
   case a sibling fixer's run shows odd cache behaviour.
6. **SFH-R2-04 (LOW), seen, not fixed.** A same-day clean empty poll does not hide rows
   written earlier that day. It sits on the same `cleanPollAsof > latestAsof` comparison
   in `latest-holdings-per-key.ts`. It is not in this topic's scope and not changed.
