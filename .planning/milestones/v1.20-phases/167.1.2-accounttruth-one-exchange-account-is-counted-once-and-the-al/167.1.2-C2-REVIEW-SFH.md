`_counted_through_holder` (`equity_reconstruction.py:1818`, rule at `:1842`) both still use the

against the new rule. They are not.

Measured (holder A, key B marked `duplicate` of A, B healthy and eligible):

```

sign_in_failed refresh counted keys: ['A'] | derive treats B as duplicate (deletes curve): True
error          refresh counted keys: ['A'] | derive treats B as duplicate (deletes curve): True
```

This is already booked as `deferred-items.md` item 1 and plan 11 SUMMARY R1 ("belongs to plans 05

### SFH-01 — critical — the daily refresh counts an account through nobody, or through the stale key

**Location:** `analytics-service/services/equity_reconstruction.py:1818-1845`
(`_counted_through_holder`, `'duplicate'` branch at `:1842`); called from
`_fetch_latest_holdings_per_eligible_key` at `:1894`.

**Failure scenario, inactive holder.** Key A holds the account. Key B, healthy, is marked
`duplicate` of A. A is set `is_active = false` but is not disconnected. `eligible_key_predicate(A)`
is false, so A is not summed. `_counted_through_holder(B)` is true because A is "working" under the
old rule, so B is excluded too. **The account contributes $0.** If the allocator has any other
key, `breakdown` is non-empty and `persist_equity_snapshots` writes today's row with the account
missing, under `ON CONFLICT (allocator_id, asof) DO NOTHING`. That row is never rewritten (plan 10
rewrites no stored row). This is the same "$0 day" D-07 exists to remove, and the D-18 migration
COMMENT names it: "counted by the healthy key instead of by nobody". The only signal is
`excluded_shared_keys = 1` in `refresh_complete` metadata, which reads the same as a correct
exclusion.

**Failure scenario, `sign_in_failed` or `error` holder** (the realistic case: the owner rotated
the credential, the old key A starts failing, the new key B reads the same account). A stays
eligible, because `eligible_key_predicate` admits both statuses. The pre-D-18 rule excludes B. The
book is summed from A's **last** holdings, carried with no age limit (SFH-09), and B's fresh
holdings are thrown away every day. The persisted total freezes at A's last poll.

**Hidden errors:** a dropped account, frozen stale holdings, and a per-symbol `breakdown` that
loses or freezes the account's symbols. match.py reads `breakdown` (`routers/match.py:592-643`).

**User impact:** the D-02 hide keeps the curve off My Allocation. But the legacy store is the input
to per-symbol returns in match.py, and it is what `/compare` will read if D-13 ever flips. The
wrong rows are permanent.

**Recommendation.**
1. Add one D-18 predicate next to `eligible_key_predicate` in
   `services/allocator_equity_derive.py`, with the explicit NULL leg the migration comment requires
   (`is_active and disconnected_at is None and (sync_status is None or sync_status not in
   {"revoked","sign_in_failed","error"})`). Use it in both writers, and delete the two local copies.
2. Add a stronger invariant that does not depend on the rule staying in sync: **a marked key is
   excluded only when its holder is itself in the counted set.** An ineligible holder then can
   never take a marked key down with it.
3. When a marked key counts because its holder is not working, **the holder must leave the sum
   for that account**. Otherwise the failing holder's carried holdings and the healthy key's fresh
   holdings are both summed, which is a double count (D-18: "counted by the healthy key").
4. Add pytest cases for an inactive, `sign_in_failed`, `error` and NULL-status holder, mirroring
   the TS `isWorkingHolder` tests, plus a parity test that reads the status tuple from migration
   `20260927180000` the way `account-share-note.test.ts` does.

```python
# allocator_equity_derive.py
_NOT_WORKING_SYNC_STATUSES = frozenset({"revoked", "sign_in_failed", "error"})

def working_holder_predicate(row: Mapping[str, Any]) -> bool:
    status = row.get("sync_status")
    return (
        row.get("is_active") is True
        and row.get("disconnected_at") is None
        and (status is None or status not in _NOT_WORKING_SYNC_STATUSES)
    )

# equity_reconstruction.py — resolve pairs over the eligible set, never per key in isolation
def _counted_through_holder(key_row, key_rows_by_id, counted_ids) -> bool:
    holder = key_rows_by_id.get(key_row.get("account_shared_with_api_key_id"))
    if key_row.get("account_share_kind") not in ("duplicate", "composite_member") or holder is None:
        return False
    return working_holder_predicate(holder) and holder.get("id") in counted_ids
# ...and drop a NON-working holder from counted_ids when a working marked key reads its account.
```

### SFH-02 — high — the derive job deletes the curve on the old rule, and a naive fix double-counts

**Location:** `analytics-service/services/job_worker.py:10245-10252` (`_holder_is_working`) and
`:10348-10382` (the identity gate).

**Failure scenario (today).** With an inactive, `sign_in_failed` or `error` holder, B is put in
`duplicate_keys`, `_delete_equity_curve_row()` runs, the job logs at INFO and returns `DONE`. The
writer has decided "double-counted, refuse". The reader (`countsAsDuplicate`, D-18) has decided
"not a duplicate". Neither side tells the other, and no alert fires (SFH-07). The book is hidden
under a reason line that does not describe the cause (SFH-04, SFH-05).

**Failure scenario (after a one-line fix).** If `_holder_is_working` is switched to D-18 and
nothing else changes, a failing holder A is still **eligible**, so it stays in `counted_ids`. B is
no longer a duplicate, so it is counted too. `account_identity_collisions` cannot catch the pair,
because B's `venue_account_id` is NULL: `_mark_shared` (`account_identity.py:395-403`) leaves it
NULL until the holder is disconnected, and a NULL id never collides (by design, plan 05 deviation
2). **The compose then persists a trustworthy version-2 series that counts one account twice.**
Today the TS reader happens to hide it through SFH-04. Fix SFH-04 on its own and that
double-counted series renders as "ready".

**Recommendation:** fix SFH-01, SFH-02 and SFH-04 as one change, with the same pair resolution
in both writers: at most one key per marked pair in `counted_ids`, the working one. If neither key
is working, keep the holder, so the account's history is not lost. Add a derive test that fails if
a failing holder and its healthy duplicate are both composed.

### SFH-03 — high — a composite member with a failing holder: the stale key is counted and the book reads "ready"

**Location:** `job_worker.py:10326-10339` (`holder_id in eligible_ids`),
`equity_reconstruction.py:1843-1844` (`eligible_key_predicate(holder)`), and the reader exemption
at `src/lib/queries.ts:3732-3737` (`identityStillPending` returns false for `composite_member`).

**Failure scenario.** Two members of one composite read one account (a key rotation inside the
composite, D-04). The stamper names whichever key it met second as the member; its direction
follows stamp order, not seniority (C1 WR-03). When the holder is the OLD key, and its credential
is invalidated at the exchange (`sign_in_failed` or `error`, still `is_active`, not disconnected),
then:

- it is still in `eligible_ids`, so the healthy new member is dropped from the counted set;
- the compose runs on the holder's `csv_daily_returns`, which stopped on the day it started
  failing, plus its last `key_inputs` anchor. That anchor is kept, because a failed derive does not
  overwrite it. **This is an inference: no test covers it.** Per plan 05, a holder whose series
  has ended carries its last level with r = 0 while any other key continues;
- the payload gets the benign token `composite_shared_account_counted_once` and stays
  `is_trustworthy`;
- in the reader, `countsAsDuplicate` ignores composites, `identityStillPending` exempts them, and
  the holder has a venue id. **The result is `"ready"`.**

The allocator then sees a curve and KPIs (Sharpe, CAGR, drawdown) that leave out the healthy
member's P&L from the day the holder began failing. Those days read as flat 0% returns. That is a
wrong number, on screen, with no signal. The D-18 COMMENT's reader contract covers "a marked key"
of both kinds, so the member should count on its own once its holder is not working.

**Recommendation:** apply the D-18 predicate (SFH-01) to the `composite_member` branch in both
writers, not just `eligible_key_predicate`, with the same one-key-per-pair resolution. Add a derive
test: a failing holder plus a healthy member composes the member's series. Also add a reader
guard: a book is not "ready" while a composite pair's holder is not working and the member is
excluded.

### SFH-04 — high — the reader holds a marked duplicate in `account_identity_pending` forever

**Location:** `src/lib/queries.ts:3732-3737` (`identityStillPending`) and `:3745-3758`; copy at
`src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx:46-47`.

**Failure scenario.** B is marked `duplicate` of A, and A is live (`disconnected_at IS NULL`) but
not working under D-18: inactive, `sign_in_failed`, `error`, or even `revoked`. Because it is
live, A keeps the `(user, exchange, venue_account_id)` slot, so B's `venue_account_id` stays NULL
(`account_identity.py:399-403`: "succeeds once the holder has left"). In the reader:

1. `countsAsDuplicate(B)` is false, because the holder is not working.
2. `identityStillPending(B)` is true: B is eligible, on an identity venue, not a composite member,
   and has a NULL venue id.

So the reason is `account_identity_pending`, and the page promises "We are confirming which
exchange account each key reads. This happens on the next daily sync." **No sync can make that
true** while A stays live. The Exchanges page note (`accountShareNote`) returns null for a
non-working holder, so the allocator gets no instruction anywhere. The book is hidden with no end
date, and the one sentence shown is false.

This is exactly C1 review routing (b) in CONTEXT: "Its identity is known but blocked by the unique
index, not unknown, so the unknown-identity default-exclude must not be applied to it on that
ground." Plan 11 applies it anyway. It also means `deferred-items.md` item 1 names the wrong reason
line.

**Recommendation:** in `identityStillPending`, treat a key with `account_share_kind ===
"duplicate"` and a holder in the key list as identity KNOWN (blocked, not pending). Ship it only
together with SFH-02, so the writer never composes both keys. Name a reason that tells the owner
what to do (for example, reuse the `duplicate_account` action: disconnect one of the two keys).
Add a readiness test for a live, non-working holder with a NULL-id duplicate on okx.

### SFH-05 — high — "recomputed once a day" is shown for writer outcomes that will never recompute to ready

**Location:** `src/lib/queries.ts:3653-3680` (`extractTrustworthyDerivedSeries` returns `null`
for any rejection) and `:3757` (`!series` becomes `awaiting_derivation`); copy at
`EquityHistoryRebuilding.tsx:48-49`.

**Failure scenario.** Each of these ends in the same reader state, "Your history is recomputed from
each account's returns and cash flows once a day.":

- the writer refused on identity (row deleted, SFH-02 and SFH-07);
- a structural `NavReconstructionError` (`job_worker.py` step 4: row deleted, job FAILED
  **permanent**);
- a corrupt persisted input (`_permanent_corrupt_input`: row deleted, FAILED **permanent**);
- an empty compose (`:10597`: row deleted);
- a non-empty but **untrustworthy** compose (`:10608-10620`: upserted with
  `is_trustworthy: false` and `degrade_reasons` set). The reader throws the reasons away;
- a version-1 row or a malformed `returns` array (the reader rejects it and logs nothing);
- a failed read (SFH-06).

Several of these are permanent. The allocator is told to wait, and no log, Sentry event or audit
row records that a PRESENT row was rejected or why. The root cause is structural: the reader
re-derives the writer's decision from `api_keys` using its own copy of the rules, and the two
copies have already drifted (SFH-01 to SFH-04).

**Recommendation:**
1. The writer persists its outcome instead of deleting silently. Replace the deletes with a
   tombstone row, for example `{"version": 2, "refused": "account_duplicate" |
   "account_identity_collision" | "structural" | "corrupt_input" | "empty", "curve": [],
   "is_trustworthy": false}`. The reader maps `refused` and `degrade_reasons` to a reason, so it
   stops guessing.
2. The reader logs (`console.error` with an error id, so Sentry picks it up) whenever a row is
   PRESENT but `extractTrustworthyDerivedSeries` rejects it. Log the reason token only, never
   values.
3. Add a reason for "the recompute could not finish" that does not promise a daily fix.

### SFH-06 — medium — a failed read of the derived row is shown as a scheduled wait

**Location:** `src/lib/queries.ts:4200-4216`.

Any error on the `allocator_equity_derived` read returns `null`. The book then renders
`awaiting_derivation`. The log text says "falling back to legacy curve", but plan 11 removed that
fallback, so the message describes behaviour that no longer exists. `PGRST205` (table missing) is
swallowed with no log at all. The table exists on every environment now, so that branch can only
hide a real fault.

**Hidden errors:** RLS or grant regressions, PostgREST timeouts, schema-cache misses.

**Recommendation:** fix the log text ("rendering rebuilding"). Log PGRST205 too, or delete that
branch. Return a distinct sentinel so the reader can say "could not load your history, refresh to
retry" instead of promising a daily recompute. The stale block comment at `:4085-4091` ("degrades
to the legacy fallback") should go as well.

### SFH-07 — medium — the derive job's identity refusal leaves no durable trace

**Location:** `analytics-service/services/job_worker.py:10366-10382`; also the stale comments at
`:10592-10605` ("degrading to the legacy fallback").

The refusal deletes the allocator's curve, logs at INFO, and returns `DONE`. No `_emit_audit`, no
warning, and no FAILED job, while every branch of the refresh job is audited. With SFH-02 active,
this runs on every derive for the affected book, and nobody can find out from audit or Sentry why
the curve keeps disappearing. The empty-compose and missing-inputs deletes have the same shape.
Their comments still say "degrading to the legacy fallback (Option B)", which plan 11 made false:
there is no legacy render now, only the rebuilding panel.

**Recommendation:** emit an audit action (for example `allocator.equity.derive_refused`, counts and
reason token only, per T-167.1.2-22) and log at WARNING. Better, persist the reason as in SFH-05.
Fix the stale "legacy fallback" comments and log text.

### SFH-08 — medium — an eligible key that has never polled adds $0 and appears in no counter

**Location:** `analytics-service/services/equity_reconstruction.py:1915-1917`.

`if not asofs: continue` skips an eligible key with no `allocator_holdings` row. It is not in
`carried_keys` or `excluded_shared_keys`, and there is no `never_polled_keys`. Scenario: a book
that already has snapshots adds a key, and the daily fan-out refresh runs before that key's first
poll lands (or its poller is broken). Today's row is written without the key under first-writer-
wins, and the next day's row has it. The legacy store then shows a step equal to that key's whole
balance, and `breakdown` shows symbols appearing out of nowhere. The plan 12 hold covers only
books with ZERO snapshots.

**Recommendation:** count `never_polled_keys` in `_LatestHoldings`, the audit metadata and the
log line. For a book that has snapshots, either hold the write while any eligible key has never
polled (the same pattern as the plan 12 hold, audited) or state in the docstring that this is
accepted.

### SFH-09 — medium — carried holdings keep old prices, but the row claims today's

**Location:** `equity_reconstruction.py:1856-1860` ("There is no staleness horizon") and
`:3500-3506`, where the row is written as `source: "exchange_primary"` and
`pre_terminus_balance_unknown: False` under the comment "marks TODAY's live holdings against
current prices — this is the true, fully-known equity".

With D-07's carry, that comment is no longer true. A carried key contributes its `value_usd` from
its last poll, **priced at that day's marks**. A key that has been `sign_in_failed` for 60 days
feeds a 60-day-old BTC price into today's "fully-known" row, forever (D-07 sets no limit). Also,
the first refresh job of the day writes and wins, so a key that polls later that day keeps
yesterday's value for the whole day. The only trace is the aggregate `carried_keys` count in audit
metadata. It is not stored on the row, and the carry age is not recorded anywhere.

**Recommendation:** record the maximum carry age in days (and `carried_keys`) in the audit and on
the row (a `breakdown` meta key, or a column in a later migration). Log at WARNING once the carry
age passes a set number of days. Fix the comment. If a staleness limit is wanted, that is a
founder call. It is not a silent default for the code to pick.

### SFH-10 — low — a non-finite level is reported as benign, and missing returns become r = 0

**Location:** `analytics-service/services/allocator_equity_compose.py:171-195` and `:359-365`
(`poison` days count toward `skipped_days`, which raises the benign flag
`skipped_nonpositive_denominator` at INFO); `:150-158` (`_return_on` returns 0.0 for a missing
return row).

Upstream (`allocator_equity_derive.py:251-259`, `:607-612`) already refuses non-finite returns,
so the poison branch is mostly unreachable. But if a non-finite equity level ever gets through, it
is reported as a benign, trust-preserving skip with the wrong name. Separately, a day where a key
has a level but no `csv_daily_returns` row reads as r = 0, the same as a flow-only day. A missing
daily return inside coverage should not look like a flat day.

**Recommendation:** count poison days on their own and make them a degrade reason
(untrustworthy), not a benign flag. For `_return_on`, treat a missing return only as a flow day
when that key has a flow on that day. Otherwise count it and report it.

### SFH-11 — low — a stripped warning, and a silent filter

**Location:** `src/app/factsheet/[id]/v2/MetricsColumn.tsx:57-65,83`;
`src/app/(dashboard)/allocations/components/ScenarioComposer.tsx:3895-3898`.

- If `periodsPerYear` is missing (a stale cached payload; `buildFactsheetPayload` always sets it
  now), the "Only N observations" reliability warning is hidden. Before, it fell back to 252.
  Hiding a statistical caveat is the less safe of the two defaults. Keep the warning with a stated
  default basis, or log that the basis is missing.
- The own-book delta `.filter((r) => Number.isFinite(r))` would drop a non-finite return without a
  log. The producer guarantees finite values, so this is defensive only. If it ever fires, the
  Sharpe and Sortino are computed on fewer observations and nothing says so. Log it once, or treat
  it as "no book leg".

## What is done well

- `_fetch_latest_holdings_per_eligible_key` raises on every read failure instead of summing a
  partial book. The docstring explains why (first-writer-wins would keep the short total).
- The plan 12 hold probe raises into the job's FAILED path, never into a write, and it is audited
  as `refresh_held_for_reconstruct`.
- `extractTrustworthyDerivedSeries` fails closed on every malformed shape, and every consumer
  treats anything other than an explicit `"ready"` as rebuilding.
- `summarizeLiveHoldings` now puts every toggled-on dollar in exactly one part (`excludedTrusted`,
  `excludedManagerSide`). That closes a real vanishing-dollar path.
- `computeScenario` returns the honest empty shape on zero weight mass instead of a flat +0.00%
  curve.
