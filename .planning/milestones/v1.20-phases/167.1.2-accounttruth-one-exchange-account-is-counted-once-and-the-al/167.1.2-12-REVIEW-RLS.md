# 167.1.2 plan 12 — RLS / SECURITY DEFINER audit (rls-policy-auditor)

Scope: `supabase/migrations/20260927120000_refresh_fanout_bootstraps_zero_snapshot_books.sql`,
`supabase/migrations/down/20260927120000-rollback.sql`,
`supabase/tests/test_refresh_fanout_zero_snapshot_bootstrap.sql`,
`supabase/schema/functions/enqueue_refresh_allocator_equity_for_all.sql`.
Read-only review of the committed files on branch `feat/167.1.2-accounttruth`; no database command was run.

## What was checked

- **search_path.** `public.enqueue_refresh_allocator_equity_for_all()` keeps `SECURITY DEFINER` with
  `SET search_path = public, pg_catalog`, the project convention. The self-verify block checks the pin
  against `pg_proc.proconfig`. The search_path invariant belongs to migration-reviewer; this audit
  only covers whether an attacker can reach it (RLS-05).
- **EXECUTE ACL.** The migration runs `REVOKE ALL ... FROM PUBLIC, anon, authenticated` and
  `GRANT ALL ... TO service_role`. The self-verify block checks both with `has_function_privilege`, and
  gate arm `G` bites if a GRANT to authenticated is added. The gate's RED-UNDER-SETUP loads fixture
  `07-fixture-supabase-default-privileges.sql`, so arm `G` runs under Supabase's default grants.
- **Caller input.** The function has no parameters. Its only callers are pg_cron, where the job is
  owned by `postgres`, and service_role.
- **Tenant scoping.** Every enqueue is keyed on one `api_keys.id`. The idempotency keys embed that
  key's UUID. The strategy-link discriminator is owner-bound (`strategies.user_id = api_keys.user_id`)
  in all four copies.
- **Snapshot file.** The body in `supabase/schema/functions/enqueue_refresh_allocator_equity_for_all.sql`
  is byte-identical to the migration's CREATE (`diff` of the two CREATE ... `$$;` blocks is empty).
- **ACL drift vs 20260422101911 (075).** See RLS-01.

## Findings

### RLS-01 — INFO — The ACL matches migration 075 and baseline; no drift

Evidence: migration 075 re-creates the function with `CREATE OR REPLACE` and a COMMENT. It has no
GRANT or REVOKE, so it kept 070's ACL. 070 runs `REVOKE ALL ... FROM PUBLIC, anon, authenticated`,
and service_role's EXECUTE comes from Supabase default privileges. `supabase/schema/baseline.sql`
(the committed dump, standing in for PROD) shows exactly `REVOKE ALL ... FROM PUBLIC` +
`GRANT ALL ... TO "service_role"`, and the function is owned by `postgres`. The new migration
re-asserts the same set explicitly: owner postgres, service_role only. It widens nothing and
narrows nothing.
Residual note: service_role can call the function over PostgREST `/rpc`. ADR-0022's two-layer gate
is not needed here. The function takes no tenant argument, so a service_role caller can only trigger
the same fan-out the cron already runs. The advisory lock and idempotency keys make an extra call
harmless.
Fix: none.

### RLS-02 — INFO — The rollback revokes only FROM PUBLIC

Evidence: `down/20260927120000-rollback.sql` runs `REVOKE ALL ... FROM PUBLIC` and
`GRANT ALL ... TO service_role`, which mirrors baseline. It relies on the forward migration's explicit
anon/authenticated revoke surviving `CREATE OR REPLACE`, and it does survive, because CREATE OR
REPLACE keeps the existing ACL and does not re-apply default privileges. The rollback's
`$postverify$` block RAISEs if anon or authenticated can EXECUTE, so a gap would abort the rollback
rather than ship.
Fix: optional. Change the REVOKE to `FROM PUBLIC, anon, authenticated` so the rollback does not
depend on ACL history. It is not required.

### RLS-03 — INFO — BYPASSRLS cross-tenant reads are by design, and no tenant's rows can steer another tenant's enqueue

Evidence: the function is SECURITY DEFINER and owned by `postgres`. RLS therefore does not apply to
its reads of `api_keys`, `strategies`, `strategy_keys`, `compute_jobs` and
`allocator_equity_snapshots`, which it reads across all tenants. That is correct for a platform-wide
cron fan-out. It returns VOID and RAISEs no row data (the only NOTICE is a fixed literal), so nothing
read leaks to the caller.
One tenant-crossing input exists. The `strategy_keys_owner` policy lets `authenticated` write any
`strategy_keys` row whose `owner_id = auth.uid()`, and that WITH CHECK does not constrain
`api_key_id`, so user B can create a row pointing at user A's key. The discriminator neutralises
this in every copy (`bqks/rkks/akks/bkks.user_id = <key>.user_id`): B's strategy never counts as a
link for A's key. The `strategies.api_key_id` path is owner-bound the same way.
`api_keys.created_at`, `exchange`, `is_active` and `disconnected_at` cannot be written by
authenticated (baseline grants only DELETE and column SELECTs), so a user cannot forge a
key-creation time to jump the cap ordering. Archiving one's own strategy (`strategies_update`) only
changes the classification of one's own keys.
Fix: none. Keep the owner-equality term in every discriminator copy. Arms N3, N3b and N3c pin the
link halves, not the owner term. A future edit that drops `... .user_id = <key>.user_id` would
reopen the B-influences-A path, so consider an arm that seeds another owner's strategy_keys row
naming the key.

### RLS-04 — INFO — The bootstrap order can defer older stranded books (fairness/availability, not confidentiality)

Evidence: the book loop orders by `max(bq.created_at) DESC` and stops only before a new book once
`v_bootstrap_cap` (25) is reached. The cap is soft at book granularity: one book with N qualifying
keys enqueues all N in one run. On a day when new zero-snapshot books fill the cap, older stranded
books wait. A single owner with many unlinked keys is bounded only by that owner's key count, which
nothing in SQL limits. Key creation is server-side only (authenticated has no INSERT on `api_keys`),
so a tenant cannot trigger this at will. The plan's T-167.1.2-42 already accepts and states it.
No data crosses a tenant boundary.
Fix: none required. If the stranded population ever exceeds the cap on a sustained basis, order
oldest-first, or add a per-owner key ceiling to the per-key loop.

### RLS-05 — INFO — The search_path pin puts `public` ahead of `pg_catalog`, and no attacker can reach the gap

Evidence: the body calls `lower`, `hashtext`, `to_char`, `now`, `pg_try_advisory_lock` and
`pg_advisory_unlock` unqualified. Because `pg_catalog` is listed after `public`, an object of the same
name in `public` would shadow the built-in. Baseline grants only `USAGE` on schema `public` to anon,
authenticated and service_role, with no CREATE, so only the owner can plant such an object. This is
the repo-wide convention. Per the coordinator hand-off, migration-reviewer owns this invariant; it
is recorded here only as the reachability assessment.
Fix: none.

## Leak scope

None. The function takes no caller input, returns nothing, and only anon-less, authenticated-less
roles (postgres via pg_cron, and service_role) can execute it. Every job it enqueues is scoped to a
single `api_keys.id`, so each job's tenant is that key's owner.

RLS audit: 0 CRITICAL, 0 HIGH, 0 MEDIUM, 0 LOW (5 INFO). Leak scopes: [].
