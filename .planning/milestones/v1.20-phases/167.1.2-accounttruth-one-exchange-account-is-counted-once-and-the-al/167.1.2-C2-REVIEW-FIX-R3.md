## Fixed Issues

### SFH-R3-01 (high): one clean, empty poll zeroed the account, and the whole book, permanently

**Files modified:** `analytics-service/services/equity_reconstruction.py`, `analytics-service/tests/test_refresh_allocator_equity_carry_forward.py`
**Commit:** `43e2faeb1`
**Status:** fixed: requires human verification

**Applied fix, per the founder's decision.**
- **A clean, empty poll is not proof on its own.** `_polled_empty_since` now also reads the key's own live equity read. That is the `allocator_equity_derived` row `key_inputs:<api_key_id>`, which the key-mode derive persists from `fetch_account_equity_and_upnl_usd`.
  - The read takes `.eq("allocator_id").in_("kind", [...])`, one row per candidate key. It raises on a failure, like every other read in the refresh.
  - The function now takes `allocator_id`, and its one caller passes it.
  - The events read now also selects `entity_id`, so each clean, empty event is tied to its own key.
- **Proof:** a key has a clean, empty event (`final_status` `complete`, `row_count` 0), AND that key's read carries `anchor_null_reason` `dust` or `nonpositive`, stamped at an `anchor_asof` at or after that event.
- **No proof, so the account is carried:**
  - the read is missing;
  - the read failed (`balance_error`, `nonfinite`);
  - the read found capital: a present `anchor_usd`, or `flow_drop`, which the writer stamps only above the dust floor;
  - the read is older than every clean, empty event of its key;
  - either timestamp does not parse.
- **Contradiction.** Any candidate member whose read was taken at or after the group's first clean, empty poll, and found capital, cancels the proof. The refresh logs a WARNING with counts and the allocator only: no key id, no USD. This is the parse-empty defect itself, so it is logged loudly, not just carried.
- **Deribit never supplies the proof.** A local `_NO_EMPTINESS_PROOF_VENUES = NON_CCXT_VENUES | {"deribit"}` holds it. `NON_CCXT_VENUES` is left alone, because it means "not ccxt" elsewhere.
- **Sentry:** the `book_emptied` $0 write is now captured once with `sentry_sdk.capture_message(level="warning")`. It uses the pattern of the round-2 derive refusal:
  - `new_scope()`;
  - tags `compute_job_id` and `refresh_outcome=book_emptied`;
  - one static message, so Sentry groups the events;
  - no key id, no allocator id, no USD.
  - A module-level `import sentry_sdk` was added to `equity_reconstruction.py`.
- The docstrings of `_fetch_latest_holdings_per_eligible_key` and `_polled_empty_since`, and the comment block in the test file, now state the round-3 rule.

**Test evidence.**
- **RED, 8 failed.** On the first run, the 200,000 case and the Sentry arm failed on `AttributeError` (the module had no `sentry_sdk` yet), not on their values. Only the `import sentry_sdk` line was then added, and a second run gave the readings below:
  - the reviewer's case, `test_a_funded_account_whose_poll_reads_empty_keeps_its_carried_value`. A single bybit key held 200,000 USDT two days ago, yesterday's snapshot is 200,000, yesterday's poll was clean and empty, and the key's live read after it is 200,000. It measured **0.0 persisted where 200,000 is right**;
  - the Sentry arm of `test_a_book_whose_every_account_is_proven_empty_writes_a_zero_row`, with 0 captures;
  - six new carry arms: no live read, a failed read, `flow_drop`, a read that found capital, a read older than the poll, and Deribit.
- **GREEN:** the refresh and equity_reconstruction suites (163 passed), then the full suite above.
- **Existing proof tests** now seed both halves through `_seed_empty_proof`. None was weakened. The poll-side carry arms (a poll on the rows' day, warnings, a failed poll, a poll that wrote rows, a pre-round-2 event, MT5) now also get a live read that finds no capital. So each arm fails on its own rule, not on a missing read. MT5 now also gets a full proof, so the venue gate itself is what the arm tests.
- **Group veto**, `test_a_second_key_on_the_account_that_finds_capital_vetoes_the_proof`: a marked key's read finding capital cancels the holder's proof, and the account is carried at 500. With that read absent, the same setup is proven and zeroed, which shows the arm can fail.
- **Neuter:** with `contradicted = True` turned into a no-op, 2 tests failed: the funded case (its WARNING assertion) and the group-veto arm. The file was restored byte-for-byte.

**What it changes, stated plainly.**
- **The $0 lands one day later than before.** The crons run in this order: poll at 04:00, refresh at 05:00, key-mode derive at 05:30 (`20260717233529_allocator_equity_derived_surface.sql`). On the first empty day, the refresh sees the previous day's read, which is older than that day's poll. So the account is carried one more day, first-writer-wins, and the $0 lands the day after. That is the safe direction, and it is a permanent carried row for that one day.
- **R3-WR-02 (deploy day) was not in scope and is not fixed.** This change adds the same one-day lag there. After deploy, a proof needs both a new-shape poll event AND a key-mode read after it.
- **The dust floor is the materiality line.** `DUST_NAV_FLOOR` is $1000. A funded account under $1000 whose poll reads empty, and whose read says `dust`, is still zeroed. It is off by less than $1000, not by the whole balance.
- **A key whose read keeps failing never proves emptiness.** That covers a failing `balance_error` read, or a key the per-key derive never reaches. Such an account is carried for as long as the read fails. That is the carry D-07 already applies to any account without proof.
- **One read per key.** `key_inputs` is upserted per key, so only the latest read exists. A newer read that finds capital replaces an older dust read, and the proof then falls away. That is the intended direction.
- **Volume.** The contradiction WARNING fires on each refresh for as long as the parse-empty state lasts. It is a log line, not a Sentry event. The `book_emptied` capture fires once per $0 write, and that write is first-writer-wins per day, so at most about once per book per day.

### R3-WR-01 (warning): a poll across UTC midnight vetoed the emptiness proof for up to 200 later polls

**Files modified:** `analytics-service/services/job_worker.py`, `analytics-service/services/equity_reconstruction.py`, `analytics-service/tests/test_refresh_allocator_equity_carry_forward.py`, `analytics-service/tests/test_allocator_positions.py`
**Commits:** `d519a8f62` (fix); `7fcad08a4` (follow-up: an event without `asof` never proves)
**Status:** fixed: requires human verification

**Applied fix, per the founder's decision.**
- **Writer:** the `allocator.holdings.sync_completed` metadata now carries `"asof": today_str`. That is the day `run_poll_allocator_positions_job` stamps its rows with, fixed at handler start (`job_worker.py:9073`).
- **Reader:** in `_polled_empty_since`, an event whose `asof` is on or before the account's latest asof is skipped. It neither vetoes nor proves.
- **Prefilter:** the `created_at` filter stays as the index prefilter. An event whose `asof` is after the latest asof always has a `created_at` on or after that day, so the prefilter never drops it wrongly.
- **Pre-deploy events:** an event without `asof` was written before this deploy. It keeps round 2's `created_at` rule for the veto only: it still vetoes when `row_count > 0`, and it is never a candidate for the proof.
  - `d519a8f62` alone let a clean, empty event without `asof` still prove. That matched the founder's "(no proof)" in production only because no deployed event carries `final_status`.
  - `7fcad08a4` makes the code say what the decision says.
  - The poll-outcome fixture now defaults `asof` to the event's UTC day, which is the production shape. `without_asof=True` builds the old shape.

**Test evidence.**
- **RED, 2 failed:**
  - the reviewer's reproduction, `test_a_poll_that_ran_across_utc_midnight_does_not_veto_a_later_empty_proof`. Rows are at TODAY−3, and a `row_count=1` event with `asof` TODAY−3 was created at 00:00:04 on TODAY−2. Clean, empty polls follow on TODAY−2 and TODAY−1, with a live read after them that finds no capital. It measured **1500.0 where 1000 is right**;
  - the poll test, whose exact-metadata assertion now requires `asof`.
- **GREEN:** 1000, `emptied_accounts` 1. The poll test pins `asof` as equal to the day passed to `persist_allocator_holdings`.
- **Follow-up arm** (`7fcad08a4`), `clean-empty-event-without-asof`: RED 1000 (the event proved), GREEN 1500 (carried).
- **Legacy-rule arms,** `test_events_without_asof_keep_the_created_at_rule`:
  - a pre-deploy `row_count > 0` event without `asof` still vetoes;
  - an event with a later `asof` still vetoes.
- **Neuter:** treating a missing `asof` as "skip" failed the pre-deploy arm, and 13 other tests, which is the expected blast radius. The file was restored byte-for-byte.

**What it changes.**
- **Midnight crossing:** a poll that crosses midnight no longer blocks the proof. The account is emptied as soon as the proof's other half, the live read, is also in place.
- **Pre-deploy straddle events:** a straddle event written before this deploy has no `asof`, so it can still veto until 200 newer events push it out of the read window. That population is small: a manual sync near 00:00 UTC before deploy, on an account that emptied before its next poll that wrote rows. Recorded here rather than fixed, because the founder's decision keeps the old behaviour for pre-deploy events.
