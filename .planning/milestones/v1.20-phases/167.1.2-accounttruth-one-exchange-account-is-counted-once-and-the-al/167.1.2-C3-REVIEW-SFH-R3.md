## (1) Closures

### SFH-C3R2-01: CLOSED

- **The read.** `analytics-service/services/job_worker.py:10389` defines `_load_allocator_daily_returns`. It loops one key at a time (`:10440`, over sorted key ids) with `eq("allocator_id").eq("api_key_id", key)`. From the second page on it adds `gt("date", cursor)` (`:10450`), ordered by `date` with `.limit(size)`. It stops only on an EMPTY page (`:10455`).
- **Why that closes the finding.** No page's start depends on a count of rows that sort before it. So a sibling key's write cannot shift a page any more.
- **The key set.** The ids come from `key_rows` (`_load_returns`, `:10595`). `_load_keys` reads those before this read, so the set does not depend on this read. I checked every consumer against that set:
  - `first_return_day` is read only through ids in `key_rows`.
  - `counted_ids` and `stitch_sources` are both subsets of `key_rows`.
  - The coherence trigger keeps `csv_daily_returns.allocator_id` equal to the key owner at write time (`enforce_csv_daily_returns_owner_coherence`, `baseline.sql:3803`, read: it raises when `NEW.allocator_id IS DISTINCT FROM api_keys.user_id`). So filtering by `api_keys.user_id = allocator_id` drops no row the old whole-allocator read would have returned for a key in `key_rows`.
- **The truncation disposal is unchanged.** Past the hard cap the read raises `PaginatedSelectTruncated`, and the `except` arm at `:10602` still deletes the curve and ends the job permanent.
- **A server cap below 1000 is safe.** The empty-page stop is pinned by `test_c3r2_keyset_read_survives_a_server_cap_below_its_page_size`.
- **A retry starts clean.** `db_execute` can retry the whole callable. `_load_returns` builds a fresh generator and a fresh `out` list on every call, so a retry starts from nothing.

### Fix H: the writers' delete-then-upsert hole: CLOSED for the hole. The partial-failure shape changed; see SFH-C3R3-02.

**Order.** Both writers now upsert first.
- **Derive** (`job_worker.py:6030-6069`): the chunked `_upsert_dailies` runs first, then the `_reconcile_span_delete` batches.
- **Composite** (`:8571-8638`): the upsert runs first, then `_reconcile_full_delete` (`lt first` and `gt last`), then the `_reconcile_gap_delete` batches.

`ON CONFLICT … DO UPDATE` keeps each row present, so a day that exists both before and after a rewrite is never absent in between.

**Is every delete scoped exactly as before?** Yes. Each is the old scope or strictly narrower:
- **Derive.** The old filter was `eq(scope) + gte/lte(span)`. The new one is the same plus `in_("date", batch)`. Every date in a batch comes from `_calendar_days_absent_from(span_start, span_end, payload)` (`:3139`), so it lies inside the span. The scope is still `api_key_id` in key mode and `strategy_id` in strategy mode.
- **Composite.** The old statement deleted every row with `eq(strategy_id)`. The new statements are `eq(strategy_id)` with `lt first`, then `eq(strategy_id)` with `gt last`, then `eq(strategy_id)` with `gte first, lte last, in (gap days)`. Together they delete exactly the strategy's rows that the payload does not carry, which is the same end state.

**Can the UPDATE arm leave a stale column behind?** I checked this because a delete plus insert resets every column, while an UPDATE keeps any column the payload leaves out. The answer is no:
- The table has these columns: `strategy_id, date, daily_return, created_at, updated_at, id, api_key_id, allocator_id` (`baseline.sql:11548`).
- `csv_daily_returns_source_xor` forces exactly one owner column.
- The key-mode payload sets `api_key_id`, `allocator_id`, `strategy_id=None`, `date` and `daily_return`.
- The strategy and composite payloads set `strategy_id`, `date` and `daily_return`. The row they conflict with has `api_key_id` NULL by the xor check, so nothing is left behind.
- Only `created_at` and `updated_at` persist. See the sweep interaction below.

**Can a batch silently skip?** No, for four reasons:
- Each batch is bound through a default argument (`days: list[str] = _days`), so there is no late-binding closure bug.
- Each batch is awaited on its own, and an exception propagates out of the job.
- A zero-match delete is not an error, and it correctly deletes nothing.
- An empty complement sends no statement. That is correct, not a skip.

**Can a payload date miss the "keep" set and wipe the upserted rows?** This is the catastrophic case I looked for. It cannot happen:
- Both payloads build `date` as `ts.date().isoformat()` (`:5963` key mode, `:5974` strategy mode, `:8555` composite, each the `"date": ts.date().isoformat()` line of its `rows_payload`).
- `_calendar_days_absent_from` compares those strings against `date.isoformat()`.
- The formats are identical, so the keep set matches.

**The URL bound.** A 200-date batch was measured at 2,770 bytes. The PROD gateway limit was not measured, and fix H says so.

**The dropped-enqueue sweep interaction.** Fix H flagged that `MAX(csv_daily_returns.created_at)` no longer moves on a rewrite. I concur that this is safe. It is INFO SFH-C3R3-04, below.

## (2) New findings

### SFH-C3R3-01: LOW. The wizard's empty-series "recomputing" guards key on a state no Python writer produces any more, and five comments still describe the retired delete-first order

**Location.** `src/app/(dashboard)/strategies/new/wizard/steps/SyncPreviewStep.tsx`:
- `:257` (the in-flight doc: "the steps that perform the series delete→re-upsert");
- `:639` (the `seriesRecomputing` state: "the `csv_daily_returns` delete→re-upsert window");
- `:1556-1565` (R2-5: "the stitch_composite worker does a wholesale delete→re-upsert … can read a 'complete' status with 0 series rows");
- `:1947-1960` (TWIN-1: "`run_derive_broker_dailies_job` does the SAME wholesale delete→re-upsert … the 'series heal-delete'");
- `:3160-3166` (STALE-01b: "a red refusal computed from a mid-delete table").

**The issue.** Three wizard guards exist to detect one incoherent reading, "terminal status over a series that measures zero". The guards are R2-5 on the composite arm, TWIN-1 on the single-key arm, and the STALE-01b amber banner. The only thing that produced that reading was the writers' delete-first window. Fix H removed that window, so none of the Python writers now empties a series mid-rewrite. The guards are harmless, but they are dead against the writers they were built for. Their comments now state, as current fact, a writer order that fix H retired. This file sits outside fix H's scope, which is why fix H did not update it.

**What the wizard sees during a rewrite now.** A poll that lands mid-rewrite of an already-computed strategy reads:
- the PRIOR `strategy_analytics` status, still terminal (the bridge flips it only after a job finishes);
- a NON-empty series, part rewritten and part old, plus any refused day not yet deleted.

None of the three guards detects that. So the arm renders the prior verdict and metrics beside a partly new series, as current.

**Why it is only LOW.** The same "stale verdict over fresh rows" window already existed before fix H, from the moment the upsert finished until the chained analytics job flipped the status. Fix H extends that window across the upsert and the deletes, which takes milliseconds to seconds. It does not create a new class. The composite arm's R2-4 reconciliation caption still epsilon-checks the series against `cumulative_return`, so a torn composite does not reconcile silently.

**Failing scenario.**
1. An owner reopens the wizard for a composite whose `stitch_composite` re-derive is between its upsert and its `_reconcile_gap_delete`.
2. The status reads `complete`, from the prior run.
3. The series is 1,200 days, with stale rows still inside the new inter-member gap.
4. R2-5 does not fire, because the series is not empty. The attribution table and gantt render with the stale gap days, beside the prior headline.
5. The next poll is the same until the job flips the status. Then the arm re-reads.

**Recommendation.**
- Correct the five comments to say that the guards are defense in depth against a writer that empties a series, and that no current Python writer does so since C3 topic H.
- Optionally, key the "recomputing" state on a `derive_broker_dailies` or `stitch_composite` job being in flight for the strategy, rather than on an empty series. That would catch the torn-series window too. Do not delete the guards.

### SFH-C3R3-02: LOW. A reconcile delete that fails, or a worker death after the upsert, leaves a refused day's stale row present, and nothing marks it. "The retry heals it" is not guaranteed.

**Location.**
- `job_worker.py:6043-6069`: the derive's upsert, then the absent-day deletes.
- `job_worker.py:8582-8638`: the composite's upsert, then its `lt`/`gt` and gap deletes.
- Fix H's report, "Partial failure changes shape, stated honestly".

**What changed, and in which direction.**

| Failure point | Before fix H (delete first) | After fix H (upsert first) |
|---|---|---|
| The delete raises (all retries fail) | nothing written; the old series stays self-consistent | new values written; refused days keep their STALE values |
| Worker death mid-upsert | the span is partly EMPTY (a hole) | the span is partly rewritten; no hole |
| Worker death between upsert and delete | n/a | new values plus stale refused days, or, for a composite, stale out-of-span rows |

For deaths, fix H is a net improvement. A stale value is less wrong than a hole, and a hole also read as a trustworthy 0% day. The one row that got worse is the first: a delete that fails every retry.

**Why no retry may come.**
- A persistently failing delete reaches `failed_final`.
- For a recurring ledger refresh, D-15's protected path (`sync_strategy_analytics_status` branch b-prime) deliberately keeps the strategy `complete`, so nothing looks wrong.
- A worker death is terminalized by the orphan reaper as `orphaned_running_reaped`.
- The dropped-enqueue sweep readmits orphans only for strategies with NO `strategy_keys` rows. So keyed strategies and composites get no automatic retry.

In each case the heal waits for the next scheduled derive.

**The effect that the MEDIUM-HIGH reconcile exists to prevent.** The next `compute_analytics_from_csv` run reads the stale refused day as present. The NaN reinstatement does not fire, and `cumulative_twr_segmented` compounds across it: a headline bridged over a day the fresh derive refused. In key mode, the allocator compose reads the stale day as a trustworthy return.

**Failing scenario (strategy mode).**
1. A refresh derive refuses 2024-05-03, which has a stale legacy USD row.
2. The derive upserts its payload.
3. The `in.(…2024-05-03…)` delete hits a statement timeout on every retry, and the job ends `failed_final` under a protected refresh marker.
4. The strategy stays `complete`, and no Sentry signal names the stale day. `last_error` carries only the timeout.
5. A later analytics run publishes a headline that compounds the stale 2024-05-03 return.

**Why it is only LOW.**
- The statements are tiny and bounded, and a transient failure retries the whole derive idempotently, which heals it.
- The death window between the upsert and the delete lasts milliseconds.
- The failure is not swallowed: the exception propagates and is logged.

The silence is only that nothing records that the reconcile did not finish.

**Recommendation (any one).**
- Correct fix H's sentence "until the retry heals it" in the comment at `job_worker.py:5993-6007` and in the D5 block (`:8937-8945`) to "until the next successful derive heals it".
- Or, when the delete phase raises after the upsert has landed, log at ERROR with the count of absent days left unreconciled, so the Sentry event names the stale-day risk and not only the timeout.

## (3) INFO

### SFH-C3R3-03: INFO. The Python keyset helpers do not assert that the cursor advances, while the TypeScript drain does

**Where.** `job_worker.py:10440-10473` and `analytics_runner.py:1194-1256`. Both advance `cursor = str(chunk[-1]["date"])` and trust the server to honour `gt` and `order`.

**The asymmetry.** `drainById` refuses a non-increasing id as an ERROR (`drain-by-id.ts:129`). The Python helpers have no such check.

**What would happen.** If something between the worker and PostgREST ignored the `gt` filter, the Python loop would never see an empty page. After 1000 identical pages it would raise `PaginatedSelectTruncated`. In the allocator derive, that arm DELETES the equity curve and ends the job permanent, with the message "exceeds … 1,000,000 rows". That misnames the cause.

**Why INFO.** PostgREST honours `gt`, and no current proxy strips it. A two-line guard, `if cursor is not None and str(chunk[0]["date"]) <= cursor: raise …`, would make the helpers match the TypeScript discipline.

### SFH-C3R3-04: INFO. The dropped-enqueue sweep is not reachable through the rewrite; I concur with fix H

**The anchor.** The live body is in `supabase/migrations/20260819150000_reconcile_sweep_readmit_attempt_ceiling.sql:377-418`. It uses `MAX(dg.created_at) … < now() - interval '1 hour'` as its grace anchor, and it orders by that anchor.

**Why the rewrite cannot reach it.** The sweep admits a strategy only when all of these hold:
- no `strategy_keys` row, so every composite and keyed strategy is excluded;
- no `compute_jobs` row other than `orphaned_running_reaped` failures;
- no `strategy_analytics` row in `computing`, `complete`, `complete_with_warnings` or `failed`.

A strategy-mode derive that rewrites rows is itself a `compute_jobs` row for that strategy, so a live or finished derive excludes the strategy. Key-mode rows have `strategy_id` NULL, so the sweep never sees them.

**Other readers.** I found no other reader of `csv_daily_returns.created_at` or `updated_at` in `src/`, `analytics-service/services` or `routers`.

**Stale comment.** The migration comment fix H flagged (`20260816140000_reconcile_dropped_enqueue_sweep.sql`, about lines 153-167) is prose only. Leave it for a lineage doc, since migrations auto-apply to PROD.

### SFH-C3R3-05: INFO. The two surfaces fail closed differently on an unknown reason

**The difference.** For a reason this build does not know:
- the Scenario falls back to `rebuilding` ("being rebuilt"), a class the new doc defines as "a wait on a daily run";
- the Overview shows the no-reason panel.

**Why INFO.** The Overview's `<h2>` also says "Your equity history is being rebuilt" for every reason. So the two surfaces agree on the headline, and neither names an action.

**If it ever matters.** A future reason added server-side ahead of the client would be told "being rebuilt" on the Scenario. The alternative fail-closed target is `held_back`, which makes no wait claim. This is a copy decision, not a defect.
