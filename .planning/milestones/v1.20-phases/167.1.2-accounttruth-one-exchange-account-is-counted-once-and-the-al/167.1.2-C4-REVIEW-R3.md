### WR-R2-02 (unanchored key covers or bounds another): closed

- **Both twins filter the same way.** Each has the same one-clause filter:
  `k.id === key.id || k.anchored !== false` in `departed-history.ts`, and
  `other_id == key_id or …get("anchored", True) is not False` in `job_worker.py`.
- **The derive decides anchoring before the rule.**
  - It now reads `key_inputs` before the rule and sets
    `anchored = id in eligible_ids or id in departed_anchored`.
  - The anchored test is `anchor_usd is not None`. The old drop loop used the same
    test, so the late `float(departed_payload["anchor_usd"])` only ever sees anchored
    keys.
- **Unavailable keys are counted correctly.**
  - `departed_unavailable` is the set of included keys that are not anchored.
  - The WARNING's count split (`null_anchor_total`) is computed over that set only, so
    it cannot go negative.
- **Behaviour change, in the intended direction.** Unanchored keys have also left the B4
  collision input, because they were in `departed_end_by_key` before and are not now.
  An unanchored key is never counted, so it cannot collide.
- **Exactly-once holds.** Traced for both orders of an unanchored key U and an anchored
  key K on one account:
  - If K covers U, U is not included, and K carries the days.
  - If U would cover K, K is decided without U and counts its own window. U is flagged
    unavailable and disclosed.
- **The card agrees with the derive.** It waits for the anchor state of every departed
  key on the account before it renders (`AllocatorExchangeManager.tsx:570-572`). So a
  covering key with no anchor never reads as anchored for one render.

### WR-R2-03 / SFH-R2-02 (partial-read line) and SFH-R2-03 (age note): closed

- **The line is bound to the rows, not to the key's status.**
  - `partialReads` is set only for a contributing key, and only when the newest
    `sync_completed` of any outcome is `complete_with_warnings` with `asof` equal to
    the rows' day.
  - A failed poll emits a different action, and a running poll emits none, so neither
    removes the line.
- **The flag reaches the panel on every render.** Page load and the 30 s refresh both
  get it: `derivePhase07Fields` → `partialPositionReads` → `page.tsx` `{...payload}` →
  `AllocationsTabs` `{...props}` → `HoldingsTabPanel`, and the refresh is
  `router.refresh()`, a server re-render. No field whitelist sits on that path.
- **The age note uses an absolute reference.** It dates a row older than the later of
  the book's newest read and yesterday (UTC), so a one-key book and a book of equally
  stale keys are both dated now. The hydration window at UTC midnight is recorded by
  R2C, and it errs toward fewer notes, never a false one.

### WR-R3-01 (MEDIUM): the SQL fingerprint is a third copy of the reader's rule, and no gate compares the two

**Files:**
- `supabase/migrations/20260929120000_commit_scenario_batch_fingerprint_reader_set.sql:237-242` (the "⚠️ TWIN" note)
- `supabase/tests/test_commit_scenario_batch_fingerprint_precondition.sql` tests 10 to 14
- `src/lib/latest-holdings-per-key.ts`, and `accountIdentityTokens` in `src/lib/departed-history.ts`

**Issue:**
- **No test pairs the two sides.** The two sides agree today; the table above checks
  them clause by clause. But:
  - The migration's twin note says "The gate is … tests 10-14". Those tests compare
    the SQL with token sets written by hand in the SQL file.
  - No test runs the TypeScript reader and the SQL rule on the same fixture.
  - A grep for the migration's name outside `supabase/tests` finds nothing in `src`,
    `scripts` or `analytics-service/tests`.
- **A change to either TypeScript file would pass every gate.** Suppose someone edits
  `latest-holdings-per-key.ts` or `accountIdentityTokens`: a new supersede rule, a
  change from `>` to `>=`, a new marker kind, or a different venue normalisation.
  - Every vitest arm and all of tests 10 to 14 stay green.
  - Production then hits the SFH-R2-01 failure again: every book-mode commit of an
    affected allocator gets a 409, "Refresh to load the latest holdings", and no
    refresh clears it.
- **The shared file is the risky one.** `accountIdentityTokens` also drives the D-09
  rule. It has its own Python twin fixture, but that fixture does not cover the SQL.
  So a D-09 identity change made "correctly" in both of the pinned twins would still
  break scenario commits.
- **This round shows the coupling is live.** Topic C edited `latest-holdings-per-key.ts`
  in parallel with topic A's SQL. R2A's routing item 1 had to ask for a manual diff
  before merge. That change happened to leave the row set alone; nothing would have
  failed if it had not.
- **Why MEDIUM:** a divergence gives a user-facing dead end, and it would be silent in
  CI.

**Fix:**
1. **Pin the rule once and test both languages against it.** Add a shared fixture, for
   example `src/lib/__fixtures__/holdings-reader-set.json`, following the existing
   `departed_history_inclusion.json` pattern. Each case lists keys with identity
   columns, holdings rows `(key, asof, symbol, venue, holding_type)`, poll events
   `(key, created_at, metadata)`, and the expected token set.
2. **Run it in vitest.** Feed every case to `fetchLatestHoldingsPerKey` through a fake
   client, fingerprint the result, and assert the expected tokens.
3. **Run it on the SQL lane.** Load the same JSON in one extra DO block, via
   `pg_read_file`, or a generated `\set` literal checked by a freshness test. Seed the
   rows, call `commit_scenario_batch` with the expected fingerprint, and assert it is
   not `portfolio_fingerprint_stale`.
4. **Pin the marker kinds.** Add a static vitest that reads the migration text and
   asserts its `IN ('duplicate', 'composite_member')` list equals the kinds
   `MARKER_KIND_IS_SHARED` marks as shared. The shared-kind set is already written out
   by hand in the SQL, per R2A.
5. **Correct the twin note.** Change the note at `:240-242` to name the shared fixture
   as the gate.
