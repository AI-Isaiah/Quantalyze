#### SFH-R3-01: the fingerprint rule is now a TypeScript/SQL twin, and nothing fails when one side moves

- **Location:**
  - `supabase/migrations/20260929120000_commit_scenario_batch_fingerprint_reader_set.sql:237-242`.
    This is the twin warning. It says a change to `latest-holdings-per-key.ts` or
    `accountIdentityTokens` "that is not made here re-opens SFH-R2-01". The named gate
    is tests 10 to 14.
  - `:277` and `:283` hardcode `IN ('duplicate', 'composite_member')`. `:318` hardcodes
    the action string. `:321` hardcodes the `'complete'` literal.
  - The TypeScript sides of those same facts are `src/lib/latest-holdings-per-key.ts:76`
    (`POLL_COMPLETED_ACTION`), `:112-122` (`cleanPollDay`), `:281`, `:319-347`, and
    `src/lib/departed-history.ts:68-76` (`MARKER_KIND_IS_SHARED`) and `:120-171`
    (`accountIdentityTokens`).
- **What the gate covers.** Tests 10 to 14 are SQL fixtures run against the SQL body.
  They prove the SQL implements the rule as it stands today. They cannot fail when the
  TypeScript reader changes. Nothing in `src/` or `scripts/` reads the new migration
  (`grep -rl "20260929120000\|fingerprint_reader_set" src analytics-service/tests
  scripts` returns nothing). The departed-history twin has a shared fixture both
  languages run (`departed_history_inclusion.json`). This twin has no equivalent.
- **Scenario:** a later phase edits `fetchLatestHoldingsPerKey`. For example, it
  changes SFH-R2-04 (a same-day clean empty poll hides earlier rows, which R2C left on
  the same `>` comparison at `:281`), or it adds a third rule. The TypeScript tests
  pass, and the SQL gate passes, because it still tests the old rule. From then on,
  every book-mode commit of an affected allocator gets `portfolio_fingerprint_stale`.
- **Hidden errors:** a rule change in the reader, a renamed `POLL_COMPLETED_ACTION`, a
  change to the clean-poll predicate (for example, accepting `complete_with_warnings`
  with derivatives read), or a change to how `accountIdentityTokens` normalizes
  `exchange` or `venue_account_id`.
- **User impact:** this is SFH-R2-01's own failure mode. The route returns a handled 409
  with the copy "Your holdings were updated after you opened this scenario. Refresh…".
  A refresh rebuilds the same client set, so the commit is a dead end. No log line
  distinguishes a drifted rule from a real holdings change. The previous occurrence
  surfaced only through a review.
- **Recommendation (either option closes it):**
  1. Add a vitest source pin next to `latest-holdings-per-key.test.ts`. It reads the
     newest migration that defines `commit_scenario_batch` and asserts that step (3b)
     carries `POLL_COMPLETED_ACTION`, every kind in `SHARED_ACCOUNT_MARKER_KINDS`, and
     the literal `'complete'`. It also pins a hash of `fetchLatestHoldingsPerKey`'s
     rule block, so an edit there fails with a message that names the SQL twin. This
     is the repo's usual answer for a twin that cannot share runtime code.
  2. Alternatively, move the scenario rows of tests 10 to 14 into a shared JSON
     fixture. Run it through `fetchLatestHoldingsPerKey` with the existing fake client
     plus `computeHoldingsFingerprint`. Keep the SQL file's rows byte-equal to it, the
     way `departed_history_inclusion.json` binds the departed-history twins.

  Either way, the PR text should name the twin, because the migration auto-applies to
  PROD on merge.

**The derive's pre-rule `key_inputs` read (`job_worker.py` `run_derive_allocator_equity_job`, the `_load_key_inputs` block).**
- **Error path.** `db_execute` (`services/db.py:134`) propagates the exception, and the
  read sits outside any try. A read error therefore fails the job exactly as the old
  step-3 read did, one step earlier. It never falls through to "every key unanchored".
- **Empty result.** A supabase-py select raises on error. An empty `data` means no rows,
  which is the truthful "missing row" case.
- **Anchor test.** A departed key counts as anchored only on a non-null `anchor_usd`, the
  same test as the old drop. A key that cannot be levelled is disclosed under
  `departed_history_unavailable` with split counts. It never counts silently.
- **The late loop.** It reads `anchor_usd` only for keys in `departed_end_by_key`, which
  are anchored by construction.

**The third audit read (`partialReads`).**
- **Read error.** An error returns `error` with `partialReads: []`
  (`latest-holdings-per-key.ts:275-277`, `:297-300`), and `assertOk` fails the page
  loudly (`queries.ts:4771`). It is not silent. The blast radius of a failure grew by
  one parallel read per key (INFO-2's class).
- **Malformed metadata or a missing day.** `partialPollDay` returns null, so no line is
  shown. This is reachable only for a legacy event from before the poll recorded `asof`,
  which R2C recorded.
- **A key missing from `apiKeys`.** `keyPhrase` handles `undefined` ("a Binance key",
  `HoldingsTabPanel.tsx:76-80`), and the venue falls back to the row's venue
  (`:192`). It does not crash.
- **Threading.** `page.tsx` spreads the whole payload into `AllocationsTabs`, which
  spreads it into `HoldingsTabPanel`. No payload whitelist exists.

**The age note's yesterday-UTC reference (`HoldingsTabPanel.tsx:400-407`).**
- **Frozen `today`.** `today` is fixed when the panel mounts. The Holdings tab never
  polls, since `AllocationsTabs.tsx:484` polls only on Overview. The rows and
  `today` are therefore the same snapshot, and a long-open tab does not drift one
  against the other. Switching tabs remounts the panel.
- **Tolerance.** One day of tolerance matches the 04:00 UTC poll.
- **Device clock.** `today` comes from the device clock, so a device clock that is a
  whole day off can add or suppress a note. The sentence ("as last read on X") stays
  true either way. This is too exotic to rate above LOW.
