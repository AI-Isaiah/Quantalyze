**Commit:** `75926d1a1`
**Applied fix:**
- In `derivePhase07Fields`, `rejection` is computed with `derivedPayloadRejection`. Three outcomes read `awaiting_derivation`: no row, an accepted row whose readiness fails elsewhere, and a `not_version_2` row. A v2 row that is `untrustworthy` or `malformed` still reads `derivation_rejected`, and a failed read still reads `history_read_failed`.

**Correction to the round-1 record.** Fixer B's round-1 decision (`167.1.2-REVIEW-FIX-B.md`, "Recorded decision") said a pre-v2 row "reads `derivation_rejected` until the next key refresh", and that ledger books "never re-derive". That premise was wrong for allocator keys. `derive-allocator-key-dailies` (jobid 9, `30 5 * * *`) re-derives every eligible key every day, and each key-mode derive enqueues the compose. So "recomputed … once a day" is TRUE for a pre-v2 row. The round-1 fix replaced a true line with a false one, and this round reverts that for pre-v2 rows.

**Tests:**

The result is `awaiting_derivation`. `captureToSentry` is never called with `derived_row_rejected`. The warn line carries `not_version_2`, and it carries no curve value.
- New v2-untrustworthy arm, with the flag `shared_account_no_working_key`. The result is `derivation_rejected`, and the row is captured with `rejection: "untrustworthy"` at level `warning`.
- `queries.test.ts`: the "is_trustworthy=false" fixture now carries `version: 2`. Before, it had no version, so after the fix it would have tested the version check and not the writer's verdict. The version-1 case now expects `awaiting_derivation`. The outcomes table splits pre-v2 arms (`version: 1`, `version: undefined`, `version: 1` + untrustworthy) from v2 rejections.

**RED → GREEN:** 3 failures before the change, each `expected 'derivation_rejected' to be 'awaiting_derivation'`: the deploy-day arm, the version-1 case and the outcomes table. After the change: `queries.test.ts` + `queries.my-allocation.test.ts` + rebuilding test, 197/197.
**Status:** fixed: requires human verification (logic)

**Residual (recorded, not fixed).** Take a book whose compose never runs, for example because every key's `derive_broker_dailies` fails before the compose enqueue. It keeps its v1 row, and it now reads `awaiting_derivation` indefinitely. Its only trace is the `console.warn` line in the Vercel function log. The review offered a Sentry capture keyed on a stale `computed_at` (more than ~36 h) as the mechanism, and I did not add it. On deploy day many existing v1 rows may already be older than 36 h and will still be rewritten at the next 05:30. So a staleness capture risks the same deploy-day storm this finding removes, and the orchestrator's decision is flat: not sent per page load. If it is wanted, gate it on the deploy time and not on `computed_at` alone.

### SFH-R2-05: the derived-row Sentry captures were fire-and-forget inside a server read

**Files modified:** `src/lib/queries.ts`, `src/lib/queries.my-allocation.test.ts`
**Commit:** `2d86ed389`
**Docs read first:** `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md` (Next `16.2.11`). The docs list Server Components among the places `after` may be called, and state that on serverless it is backed by `waitUntil`. `getMyAllocationDashboard` runs from the allocations page Server Component. `queries.ts` is server-only: it imports `@/lib/supabase/server`, and every `"use client"` importer of `@/lib/queries` is `import type`. So importing `next/server` there does not reach a client bundle.
**Applied fix:**
- `import { after } from "next/server"`.
- A module-private `scheduleDerivedRowCapture(capture)` hands the capture to `after(() => capture.catch(() => {}))`. It has the same shape as `ratelimit.ts`'s `scheduleLimiterCapture`.
- The `queueMicrotask` fallback is kept, and it is required. I measured that `after()` throws synchronously outside a request scope (`` `after` was called outside a request scope ``). An observability call must never throw into the dashboard read.
- Both remaining captures, `derived_row_read_failed` and `derived_row_rejected`, go through the scheduler.

**Tests:** `next/server`'s `after` is mocked in `queries.my-allocation.test.ts` to record callbacks. The test runs with a failed read and with a v2 untrustworthy row. In both, the capture is called with its reason tag, at least one callback is scheduled, and the scheduled work stays pending until the capture's promise is released, then settles.
**Why the test is not vacuous:** `scheduled.length > 0` counts every `after` callback recorded during the call, not only the derived-row one. The check that bites is "pending until release". It ties the scheduled work to this test's capture promise. Any other callback that resolved at once would still leave the derived-row callback pending, but if NO callback waited on the capture, `settled` would already be true and the assertion would fail.
**RED → GREEN:** both arms failed with `expected 0 to be greater than 0` before the change, because no callback was scheduled. After the change: 181/181 across `queries.test.ts` and `queries.my-allocation.test.ts`.
**Status:** fixed

**Rate limiting: not added, recorded.** The `after` docs give no mechanism for it. `sentry-capture.ts` has `shouldCaptureNow`, a per-instance 60 s window. Keying it here would change alert semantics across allocators, because one allocator's window would mute another's. With R2-CR-03 in, `not_version_2` no longer captures at all. The steady-state per-load volume that remains:
- `untrustworthy` during an ordinary new-key backfill: a counted key with `key_inputs` but no returns yet makes the compose `DROPPED_KEY`.
- The `shared_account_no_working_key` outcome, once fixer A makes it non-benign.

Both fire once per dashboard load while the state lasts. Sentry groups them by message into one issue, so expect the `derived_row_rejected` issue to stay active in normal operation.

### IN-04: the key_not_syncing line did not name the key, although the round-1 report said it did

**Files modified:** `src/lib/queries.ts`, `src/lib/queries.test.ts`, `src/app/(dashboard)/allocations/AllocationDashboardV2.tsx`, `src/app/(dashboard)/allocations/components/EquityHistoryRebuilding.tsx`, `src/app/(dashboard)/allocations/AllocationDashboardV2.rebuilding.test.tsx`
**Commit:** `0b1565fdd`
**Applied fix:**
- **Producer.** `notSyncingIdentityPendingKeyIds(apiKeys)` lists the keys a `key_not_syncing` reason is about. A key is listed when `identityStillPending` is true AND `failingToSync` is true. `equityHistoryReadiness` now uses the same `failingToSync` helper, so the list and the reason cannot disagree. `derivePhase07Fields` exposes the list as the new optional payload field `equityHistoryNotSyncingKeyIds`, and it is `[]` under every other reason. It is optional so that a payload built without it renders the unnamed line and never a wrong name.
- **Renderer.** `AllocationDashboardV2` resolves the ids against the owner's own `apiKeys`. If any id does not resolve, the set is unknown (`null`). `EquityHistoryRebuilding` then renders one of three lines:
  - exactly one key: the key is named with `dataSourceLabel`, as `{Exchange} — {nickname}`, or the masked id tail when the key has no nickname. This is the same label shape as the Exchanges page key note (`account-share-note.ts`);
  - two or more keys: a plural line;
  - unknown: an unnamed line that is true for any count.
- The client re-derives no predicate. It only looks up ids the server chose.

**⚠️ T-167.1.2-22a amendment (flag for the verifier).** Plan 11's threat register accepts "fixed authored lines; no id, no number" for the reason copy. The named line breaks that in one case: a key with no nickname is shown by its masked tail, `••••` plus the last 4 characters of the key id. That is the owner's own label, already shown to the same owner on the Exchanges page key note and the Scenario data-source rows (T-37-03-01: the masked tail never reveals the full id). So it discloses nothing new. It is recorded in the component docblock as the one exception. It is a deliberate amendment, not an unrecorded regression.

**Schema check (the new payload key).** `AllocationDashboardV2` passes the whole payload to `EquityChartWidget` as `data={props}`. The new `equityHistoryNotSyncingKeyIds` key therefore cannot fail a parse.
