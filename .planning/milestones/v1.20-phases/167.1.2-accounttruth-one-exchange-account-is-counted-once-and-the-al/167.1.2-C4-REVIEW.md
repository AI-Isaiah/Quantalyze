# Phase 167.1.2 C4: Code Review Report

**Reviewed:** 2026-09-29
**Depth:** standard (C4's own hunks only; C3 is reviewed separately)
**Files Reviewed:** 19
**Status:** issues_found

## Summary

C4 ships plan 09 (a departed key's history stays in the rebuilt book up to its end
day, behind an include/exclude switch) and plan 15 (Open Positions keeps each key's
rows at that key's own latest `asof`, read in bounded steps).

The core math holds up. `compose_allocator_equity` replays a departed key on its full
series, clips it to its end day, and rotates it out. It rotates the key out through
the frozen core's own `prev_keys` rule (`_departure_seams`) and through
`portfolio_returns(departed_keys=...)`. So the exit is never read as a return and the
key's last level is never carried. The ledger books the exit as an outflow. The
Python and TS copies of the D-09 rule run against every row of one shared fixture
(17 cases), and the job-level test feeds those same rows through the job to the
compose. The B4 collision gate now works on the same identity token the rule uses,
so a departed key that the rule clipped cannot collide.

One BLOCKER: the rotate-secret reset added for plan 09 is unconditional. The owner
can reach it from a DISCONNECTED MT5 row ("Update password"), so it quietly wipes a
stored include/exclude choice on a key that stays departed. Four WARNINGs follow. Two
are about how D-16's per-key grain interacts with writers it does not control. One is
a gap between the derive's token-based gate and the TS reader. One is copy that is
false in a case the fixture pins.

### Verified as asked (not findings)

- **The RPC exists on main with the right auth.** `set_departed_key_history_inclusion(uuid, text)`
  was created by `20260925120000_api_keys_account_identity.sql` and re-based by
  `20260927180000_working_holder_rule_d18.sql`. It is SECURITY DEFINER with
  `search_path` pinned. It raises 42501 when `auth.uid()` is NULL or the caller does not
  own the key, and its row lookup is scoped `AND user_id = v_uid ... FOR UPDATE`. It
  has `REVOKE ALL` plus `GRANT EXECUTE ... TO authenticated` only. Every 55006 variant
  (IN_PROGRESS, REQUEUED, RACED) carries both DETAIL and HINT, so the component's
  `${details} ${hint}` branch always has text. C4 correctly wrote no migration.
- **The delete warning is true.** `delete_allocator_api_key(p_cascade_holdings => true)`
  runs `DELETE FROM allocator_holdings` and then `DELETE FROM api_keys`
  (baseline.sql:3474ff). `csv_daily_returns_api_key_id_fkey` is `ON DELETE CASCADE`
  (baseline.sql:14116). The warning is shown only on the checked (cascade) branch, and
  that branch is the only one that hard-deletes. The unchecked branch calls
  `disconnect_allocator_api_key`, a soft disconnect.
- **The C3 seam: the derive does read departed keys' returns.** `_load_returns` passes
  every `key_rows` id (live and departed) to `_load_allocator_daily_returns`. C3's
  keyset drain and its `PaginatedSelectTruncated` permanent disposal are unchanged
  by C4.
- **The new flag tokens are inert on the reader.** `departed_history_included` and
  `departed_history_unavailable` have no TS consumer. The reader gates only on
  `is_trustworthy` (queries.ts:3644, :3779).
- **The switch's state survives a refresh.** `history_inclusion` is in
  `API_KEY_USER_COLUMNS` (constants.ts:191), and the migration grants SELECT on it.
- **Plan 15's dashboard tests exercise the real helper.** The queries tests do not mock
  `latest-holdings-per-key`. `allocator_holdings.asof` is a `date`, so the
  `.eq("asof", latestAsof)` equality is exact.

## Critical Issues

### CR-01: rotate-secret erases the owner's history choice on a key that stays disconnected

**File:** `src/app/api/keys/[id]/rotate-secret/route.ts:492-498` (test pinning it: `route.test.ts:815-824`)
**Issue:** The update now writes `history_inclusion: null` unconditionally. The route
deliberately never clears `disconnected_at` (its WR-03 comment, lines 470-480). The
component renders "Update password" on DISCONNECTED MT5 rows
(`AllocatorExchangeManager.tsx:1422-1430`), and it calls this route. Trace:

1. MT5 key K is disconnected, and the owner sets 'exclude' through the switch. The RPC
   writes the value and enqueues a recompose.
2. The owner clicks "Update password" on K's disconnected row. The route writes
   `history_inclusion = NULL`, `sync_status = 'idle'` and leaves `disconnected_at` set.
3. K is still departed, and its choice has silently reverted to the default rule
   (included to its end day, for a known account). No recompose is enqueued. The book
   changes on the next unrelated derive, and the card flips from "you excluded it" to
   "History included until …" with no action from the owner that says so.

The same happens in reverse to an 'include' on an unknown-account key: its history
silently drops out.

The column COMMENT's contract is "reset on every path that returns a departed key
to LIVE". This path does not return a disconnected key to live. The key also bypasses
the RPC's recompose serialisation (the running-job refusal), so even the
revoked-to-live case writes the value outside the lock the RPC takes. The new test
asserts the unconditional reset, so it pins the defect.

**Fix:** Read the fields that decide liveness and reset only when this write makes the key live:
```ts
// pre-read
.select("id, user_id, exchange, venue_account_id, disconnected_at, is_active")
...
// in attemptPersist's update
...(keyRow.disconnected_at === null && keyRow.is_active !== false
  ? { history_inclusion: null }
  : {}),
```
Split the test into two arms. A revoked key (`disconnected_at` NULL) resets. A
disconnected key does NOT carry `history_inclusion` in the payload. Neuter the
condition and watch the second arm go red. Enqueue (or document) the recompose that
the reset implies for a revoked key that had a non-NULL choice.

## Warnings

### WR-01: a partial poll now hides all of that key's derivative positions

**File:** `src/lib/latest-holdings-per-key.ts:113-137`, `src/lib/queries.ts:4182-4190`
**Issue:** `persist_allocator_holdings` writes whatever the fetch returned at today's
`asof`. When the derivative-side read fails, `fetch_allocator_holdings` still returns
the spot rows ("spot rows persisted", `allocator_positions.py:1486-1500`). Before
D-16, the newest-per-symbol collapse kept yesterday's derivative rows. Now the key's
latest `asof` holds the spot rows alone, so every open derivative position of that
key drops out of Open Positions. The only disclosure is `DERIVATIVE_FETCH_FAILED_NOTE`
in `api_keys.sync_error`, which renders on the key card on the Exchanges page and
not beside Open Positions. D-16 swapped one staleness for a disappearance and says
nothing about partial polls.
**Fix:** Either (a) key the grain per `(api_key_id, holding_type)` so a failed
derivative leg keeps its previous day, or (b) when the key's `sync_error` carries the
derivative-failure note, surface a line on Open Positions naming the key. At minimum,
record the trade-off next to D-16 and in the PR description.

### WR-02: the holdings unique index lacks `api_key_id`, so a key's "latest asof" can fall back a day and bring back closed positions

**File:** `src/lib/latest-holdings-per-key.ts:38-49,113-121` (index: baseline.sql:13226)
**Issue:** `allocator_holdings_owner_venue_symbol_asof_key` is unique on
`(allocator_id, venue, symbol, asof)`, and the writer upserts on that conflict. Take
two keys on one venue that both hold symbol X on day D. The second upsert re-labels
the first key's row with its own `api_key_id`. If X was the first key's only row on D,
that key's latest `asof` becomes D-1, and every D-1 row of that key comes back,
including positions it closed on D. That is exactly the class D-16 says it closes.
This is a pre-existing index limit and not a C4 regression, but it bounds what plan 15
can claim.
**Fix:** Record it as a known limit of D-16 in the plan-15 SUMMARY and in the PR text.
The real fix is `api_key_id` in the unique index and in the writer's `on_conflict`
(a migration, so it is routed, not done here).

### WR-03: the token-based B4 gate can refuse a book the TS reader does not call a duplicate

**File:** `analytics-service/services/job_worker.py:10951-10983`, reader `src/lib/queries.ts:3894-3905,3974-3999`
**Issue:** The collision gate now keys on `account_identity_tokens`, which joins keys
through marker links AND venue ids, transitively. `account_groups` (which picks the
one counted key per group) joins through markers only. Reachable shape:

- Live A is marked `duplicate` against H, with A's own venue id NULL.
- H is disconnected, which frees the unique slot.
- Before A's next poll stamps it, live B connects to the same account and is stamped
  with the venue id V.

Now `account_groups` puts {H, A} and {B} in separate groups, so A and B are both
counted. The tokens join H–A (marker) and H–B (venue), so the gate refuses and deletes
the curve. `countsAsDuplicate` sees no duplicate behind a working holder, so the
reader says `awaiting_derivation`. That breaks the invariant `shared_account_resolution.json`
pins ("the reader says duplicate_account exactly when the derive refuses"). The window
is transient: A's next successful poll collides on V and is marked against B. But
if A is failing to sync (`sign_in_failed`), nothing re-stamps it and the book stays
"awaiting derivation" with a misleading reason. Before C4 the same shape composed
A+B and double-counted, so the refusal itself is the safer direction.
**Fix:** Make the counted-set resolution use the same tokens as the gate. Resolve
`account_groups` over `account_identity_tokens` among eligible keys, so A and B form
one group and one is counted. Then add this shape as a row in
`shared_account_resolution.json` so both runtimes pin it.

### WR-04: "a key you still have connected reads the same exchange account over these days" is false when that key has no returns yet

**File:** `src/lib/departed-history.ts:241-266`, rule at `:201-205` (Python twin `job_worker.py:10438-10461`)
**Issue:** A live key on the account with no returns yet bounds the departed key to
`0000-00-00` (fixture case 13). Its whole history is then left out, and the card
shows "History not included: a key you still have connected reads the same exchange
account over these days." That key reads none of those days: it has no daily returns
at all. This is the usual rotation case (disconnect the old key, connect a new one on
the same account). The owner sees their history vanish, and the stated reason is
wrong until the new key's reconstruction lands. The switch is disabled here, so the
owner cannot act on it.
**Fix:** Add a reason token (e.g. `same_account_as_connected_key_pending`), set in
both twins and in the fixture when the bounding live key has no `first_returns_day`,
with honest copy: "History not included yet: a key you connected on the same
exchange account has no history yet. It is counted once that key's history is
built."

## Info

### IN-01: a departed successor with no anchor still bounds its predecessor (recorded limit)

**File:** `analytics-service/services/job_worker.py:10915-10935,11230-11253`
**Issue:** `departed_history_inclusion` and the B4 gate run before the anchor check,
so a successor later dropped as `departed_history_unavailable` still clips the
earlier key. The account's days in the successor's window are counted by nobody,
under a benign flag on a "ready" curve. This is recorded in 167.1.2-09-SUMMARY
"Known limits" and errs toward under-counting, never double-counting.
**Fix:** None required for C4. Plan 08's census should count these.

### IN-02: the eligibility predicate now has a third and fourth copy

**File:** `analytics-service/services/job_worker.py:10492-10498`, `src/lib/departed-history.ts:62-68`
**Issue:** `_is_live_key` re-implements `eligible_key_predicate`, which is already
imported in the same module, with a different default for a missing `is_active`
(`True` vs `bool(None) == False`). In the job the column is always selected and is
`NOT NULL`, so they agree today, but `live_ids` and `eligible_ids` are two sets that
can drift. The TS `isLiveKey` has no parity test (recorded in the SUMMARY).
**Fix:** Use `eligible_key_predicate` in the job and default `is_active` only in the
fixture adapter. Add a parity row for `isLiveKey` vs `isPerKeyDailiesEligibleKey`.

### IN-03: `account_identity_tokens` duplicates `account_groups`' union-find and marker-kind set

**File:** `analytics-service/services/job_worker.py:10512-10569`
**Issue:** `_SHARED_ACCOUNT_MARKER_KINDS` restates `SHARED_ACCOUNT_KINDS`
(`allocator_equity_derive.py:233`), and the marker union repeats `account_groups`.
If a new marker kind is added, it will land in one and not the other. This is the
root of WR-03's divergence.
**Fix:** Import `SHARED_ACCOUNT_KINDS`. Longer term, derive one grouping from one
function (see WR-03).

### IN-04: plan 15's cap-and-fail and C3's keyset drain sit side by side

**File:** `src/lib/latest-holdings-per-key.ts:59,93-103,121-131`
**Issue:** The adjacent per-key dailies read (C3) drains past 1000 rows. The holdings
read fails the whole dashboard (`assertOk`) when one key has 1000 rows on one day.
The per-key, one-day scope makes the cap reasonable, and failing loud is what the
plan asked for. But the choice is not written down, and one pathological key blanks
the whole My Allocation page.
**Fix:** One sentence in the docblock on why the cap is used rather than the drain.
Consider scoping the failure to the holdings panel.

### IN-05: `_utc_day` can raise outside the job's corrupt-input disposal

**File:** `analytics-service/services/job_worker.py:10501-10508,10915-10927`
**Issue:** `datetime.fromisoformat` raises `ValueError` on a malformed
`disconnected_at`. The call sits outside the `(ValueError, TypeError, KeyError)` →
`_permanent_corrupt_input` block, so it would reach the catch-all as a retrying
`unknown`. The TS twin returns null instead, which is a twin divergence. PostgREST
always emits valid ISO text, so this cannot happen today.
**Fix:** Return None on `ValueError`, as the TS twin does, or move the call inside the
corrupt-input try.

### IN-06: the ledger books the exit but not a same-account successor's opening

**File:** `analytics-service/services/allocator_equity_compose.py:462-481`
**Issue:** When a third key overlaps both, a same-account rotation (departed D, then
live L) gets an exit outflow of D's last level but no matching inflow when L opens.
Dietz/MWR then count L's first level as P&L. The scalars are not rendered (F5 note,
:510-516), so nothing user-facing is wrong today.
**Fix:** Before any future display-wiring of the scalars, book a same-account
successor's opening as the matching inflow, or skip the exit outflow when the
successor shares the departed key's token.
