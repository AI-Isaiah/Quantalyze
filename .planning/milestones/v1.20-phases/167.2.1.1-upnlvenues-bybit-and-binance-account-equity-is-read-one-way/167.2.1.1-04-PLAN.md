Measured by the planner at the phase base (2026-10-22):
- Latest `enqueue_compute_job` (9 arguments: p_strategy_id, p_kind, p_idempotency_key, p_parent_job_ids,
  p_exchange, p_metadata, p_allocator_id, p_api_key_id, p_run_at) is the 20260515210300 body
  (supabase/schema/functions/enqueue_compute_job.sql). Its api-key branch (p_api_key_id set, strategy and
  allocator NULL) has no ownership check and passes p_metadata to the 10-argument `_enqueue_compute_job_internal`,
  whose latest body (migration 20261024120000) inserts it into `compute_jobs.metadata` ON CONFLICT DO NOTHING; the
  in-flight index allows one non-terminal job per (api_key_id, kind). When a non-terminal job of that kind already
  exists for the key, the internal function RETURNS THAT EXISTING JOB'S ID (it does not return NULL), and on a lost
  insert race it re-reads the winner; so a returned id never proves that a new job carrying this enqueue's metadata
  was created. Plan 06's handoff checks the job row's metadata for that reason. `claim_compute_jobs` and
  `claim_compute_jobs_with_priority` return SETOF compute_jobs, so the handler's `job` dict carries `metadata`.
  So the flag needs NO migration. EXECUTE on `enqueue_compute_job` is revoked from PUBLIC, anon and authenticated.
- `request_allocator_holdings_sync` (the authenticated user's RPC) enqueues `reconstruct_allocator_history` with
  p_kind and p_api_key_id only, no p_metadata. No TypeScript route enqueues this kind with metadata.
- `reconstruct_allocator_history` is api_key-scoped only (compute_jobs_kind_target_coherence).
- Handler metadata idiom: services/job_worker.py reads `_metadata = job.get("metadata")` then
  `_metadata.get("source") if isinstance(_metadata, dict) else None`, with the marker literal in one `Final`
  constant (`LEDGER_REFRESH_SINGLE_KEY_SOURCE`). Copy that guard.
- The reconstruct crawl has no Bybit-specific branch (OKX only), so the binance-shaped crawl fakes in
  tests/test_reconstruct_marker_writer.py work for venue "bybit" with `exchange.id = "bybit"`.
- Multi-key persist: `_allocator_has_other_api_keys` counts ANY other api_keys row of the same user_id (any
  status); with one present the reconstruct takes the DO-NOTHING upsert, never the atomic replace.

Planner decision PD-F (RESEARCH open question 1): a tested job-metadata flag, not a marker reset. A marker reset is
a hand SQL write, which D-02 rules out, and it would also make the key OWED to the daily fan-out. The flag is read
ONLY by `run_reconstruct_allocator_history_job`; the fan-out's OWED predicate and its SQL twin
(tests/test_fanout_owed_predicate_twins.py) are untouched.
