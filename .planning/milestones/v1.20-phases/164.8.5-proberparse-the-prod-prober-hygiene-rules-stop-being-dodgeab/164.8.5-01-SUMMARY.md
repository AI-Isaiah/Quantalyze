# Phase 164.8.5 Plan 01: Prober structure — hoist, mandatory marker, counted parse failures — Summary

The cron-drift arm's live credential scan now runs above every oracle-validation return in
`compareManifest` AND above the oracle read in `run()`, the live database marker is mandatory and
compared, and a `cron.job` record the parser cannot read is a counted `measure-fail` in the arm and
a refusal in the capture path — six new counted scenarios, each neuter-proved individually.

## What was built

**Task 1 — the hoist, and the mandatory compared marker** (`49a50d41`)

- `compareManifest(manifest, prodRows, opts)` opens with **section (0)**: the PROD-side hygiene loop,
  moved verbatim from section (2), guarded `Array.isArray(prodRows) ? prodRows : []`, above the
  `const invalid =` helper and every `return`. Its comment carries SR-01's measurement in prose and
  a `⛔ Do not move this below any return`.
- `opts.liveMarker` is **mandatory**: absent or empty is a `measure-fail` on subject
  `database marker` that returns **carrying section (0)'s findings with it**.
- After section (1)'s validation passes, `manifest.database_marker` is **compared** to the live
  marker; disagreement is a `measure-fail` naming BOTH markers and returning with no drift verdict.
- `opts.manifestReadError` + `opts.manifestPath` move `run()`'s old `manifest-invalid` sentence
  inside `compareManifest`, word for word.
- `run()` reordered: marker → `cron.job` → parse → **oracle read with NO return** → `compareManifest`.
  The old order returned on a manifest read error *before* `CRON_JOB_SQL` was ever issued, so the
  "no oracle at all" case would have stayed silent even with the hoist. The two surviving early
  returns are both "nothing has been read yet", and say so.
- New fixture `manifest-schema-bumped.json` (byte-copy of `manifest.json`, `schema_version: 2`;
  verified identical in every other key).
- Four counted scenarios: `HOIST … ABSENT`, `HOIST … STALE`, `HOIST … marker MISMATCHED`,
  `MARKER MANDATORY` (a direct `compareManifest` call plus a with-marker control proving the same
  two inputs otherwise produce zero defects).

**Task 2 — a record the parser cannot read is loud** (`05521515`)

- `parseCronJobRows` returns `{ rows, malformed }`; `malformed` carries `{ index, fields }` and
  **never the record text**. The `f.length < 7` `continue` became a push; **the empty-record skip
  stayed** (`fixtureSql` emits a trailing record separator by design, D6).
- The arm raises exactly one `measure-fail` on subject `cron.job` naming `1 of 4 record(s)` and its
  field counts, and **does not return** — the readable rows still reach section (0).
- `captureManifest` gained its **fourth refusal**: `malformed.length > 0` → `REFUSED:` line, **exit
  3** (not the hygiene refusal's 1), nothing written, placed BEFORE the hygiene loop. Docblock
  updated from "THREE REFUSALS" to "FOUR".
- The `CRON_JOB_SEPARATORS` docstring's claim that 0x1E/0x1F "cannot occur in SQL source text" is
  **corrected** — `E'\x1e'` is legal and a control byte can be pasted — and this plan ships the
  counter-example: `prod-malformed-record.json` (one literal U+001E inside jobid 1's `'{}'` body
  literal). Measured before the scenarios were written: `rows: 3, malformed: [{index:1, fields:1}]`.
- Two counted scenarios (WR-05 measure-fail, capture refusal) and two direct parser unit tests in
  the wiring test, the second a CALIBRATION whose mutated stdout is asserted to differ and whose
  predicate flips on it.

## Live-behaviour note the next reader needs

The marker comparison is **new production behaviour on the hourly prober**. The committed oracle
records `database_marker: "⛔ PRODUCTION — real customer data. …"`. If PROD's `COMMENT ON DATABASE`
is ever re-worded, the arm will now raise `measure-fail: database marker` and issue **no drift
verdict** until the manifest is re-captured. That is the intended semantics (CR-02 / SR-04) — a diff
between two databases is not drift — but it is a new way for the prober to go red, and re-wording
the marker is a thing a human might do casually.
