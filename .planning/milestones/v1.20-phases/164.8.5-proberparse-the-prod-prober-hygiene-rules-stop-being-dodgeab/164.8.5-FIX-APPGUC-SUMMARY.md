## ⚠️ WHERE THE GATES RAN, and why it is not a worktree

**Every figure below was measured in the MAIN CHECKOUT** at
the repo root, branch `phase-164.7-finalize`
— not in an isolated worktree, even though `workflow.use_worktrees` is `true`.

The reason is that the mandated gates include `npx vitest run` and
`npm run lint`, and a hand-rolled `git worktree add` has no `node_modules`, so
neither can run there. A worktree would therefore have traded a real,
reproducible verification for an unverifiable commit. The isolation that a
worktree would have bought was obtained the cheaper way instead: **path-scoped
commits**, which never stage the other fixer's files and never touch the shared
index for them. This is a deviation from the fixer role's default and is
recorded here rather than left implicit.

**Consequence for the reader:** every number below IS reproducible from the
tree you are looking at. Re-run the commands; do not trust the numbers.

Its CALIBRATION is the pre-existing first test in the block — the same corpus
with `later.sql` holding `SELECT 1;` — so the red is attributable to the
successor's content and not to the harness.

**The unnumbered `readFileSync(successorAbs)` catch had no surface either**, so

## Defect 3 — the symlink walk's empty `catch` re-opened "a skipped subtree reads like an empty one"

`scripts/lint-app-guc.mjs` `sqlFilesUnder()`. **Commit `5246529d`.**

**Reproduced before fixing:**

```
(a) DANGLING  -> filesScanned=1 findings=0 measureFails=0 ok=true
(b) LOOP      -> filesScanned=33 measureFails=0 ok=true     # walked OUT of the root
```

(a) is indistinguishable from an empty directory — the exact defect the
docstring directly above the catch claims to be FIXING. (b) confirms the
containment escape; at repo scale the same shape pulled in 66,034 files,
terminating only when `ENAMETOOLONG` hit that same swallowing catch.

**After, with the same three corpora:**

```
(a) DANGLING  ok=false filesScanned=1 measureFails=1
    -> cannot stat the symlink …/vendor (ENOENT). A link the walk cannot follow is NOT an empty directory: …
(b) ESCAPE    ok=false filesScanned=1 measureFails=1
    -> …/sub/loop resolves to …/loop, which is OUTSIDE the corpus root …/sub. …
(c) CYCLE     ok=false filesScanned=1 measureFails=1
    -> …/self resolves to …/cycle, a directory already on the descent path — a symlink cycle. …
```

**Three pairwise-distinct message-granularity fingerprints:**
`cannot stat the symlink` / `OUTSIDE the corpus root` / `already on the descent path`.

**The guard is a descent STACK, not a visited-set — deliberately.** Two
*different* links to the same sibling subtree are both legitimate corpus
entries and both still get walked. The pre-existing "descends into a SYMLINKED
directory" arm (3 files for 2 real ones) is this block's CALIBRATION and is
what stops the new guards being a walk that simply refuses everything. A
visited-set would have broken that arm — which is how the distinction was found.

`sqlFilesUnder` now returns `{ files, measureFails }`; `scanPaths` takes a
`measureFails` SEED that **survives the `requireNonEmpty` early return**, so a
walk that failed AND found nothing reports both reasons rather than only the
emptier one. That path has its own arm.

**Neuter matrix — one control per edit, DECLARED set matched exactly:**

| edit | failed | others | missing |
|---|---|---|---|
| swallow the stat throw | `["a DANGLING link…","a walk failure SURVIVES the empty-corpus early return…"]` | `[]` | `[]` |
| drop containment check | `["…OUTSIDE the corpus root…"]` | `[]` | `[]` |
| drop cycle guard | `["…already on the descent path…"]` | `[]` | `[]` |

The two-test set for the first edit is DECLARED, not a batch: both tests exist
specifically for that arm, and the second one exists because the seed path
through `requireNonEmpty` is a second way the same failure could be lost.

## ⚠️ NAMED LIMITS — what is NOT closed, and why

A named unclosed finding is worth more than a forced fix. These are declared,
not skipped.

1. **`arm 4 UNREADABLE` does not measure under root.** It builds the condition
   with `chmod 000` and PROBES it; a process running as root reads a 000 file
   anyway. On such a host the arm prints
   `SKIPPED (named): chmod 000 left the successor readable here (root?) …` and
   asserts the skip condition rather than reporting a green. GitHub's
   `ubuntu-latest` runs as non-root so it measures there, but a **container**
   job would not. The arm is honest about this; it is not universal coverage.
   Same class, and same idiom, as the pre-existing `symlinkSync` skip.

2. **The walk guards do not apply to `--files` mode**, which never calls
   `sqlFilesUnder`. That is correct — `--files` is ad-hoc and already announces
   that its allowlist enforcement is OFF — but it means the mode is not a gate
   in this respect either. CI uses corpus mode; nothing changed there.

3. **`report()` still prints `app-guc: files scanned 292` beside a walk
   MEASURE_FAIL.** The exit code is correct (`ok=false` → 1, plus the
   `lint-app-guc FAILED` banner), so CI cannot be fooled; but a human skimming
   the log sees a full-looking file count next to a subtree that was never
   entered. Cosmetic, real, and left alone rather than widened into a
   summary-format change outside this fix's fence.

4. **Containment is realpath-based.** A bind mount presenting the same inode
   under a second path inside the root would be walked twice rather than
   refused. Not reachable on this tree (0 symlinks, no bind mounts) and out of
   scope; recorded so the guarantee is not overstated.

5. **`DETECT_RE` was NOT touched**, per the fence. Its byte-identity with
   `scripts/prod-prober/arms/cron-drift.mjs` was verified READ-ONLY and holds
   (`byte-identical=true`) — note that probe read the other fixer's
   *working-tree* copy, which was dirty at the time and still agreed.

6. **The corpus stayed at exactly 0 findings throughout.** No fix here reddened
   it, so no allowlist entry and no `DETECT_RE` character was tuned. Counts
   `1/5/4/1/1`, sum 12, five entries — unmoved.
