## Critical Issues

### CR-R1-01: a credential ONE CALL-LEVEL DEEP inside a header argument list is reported by NO rule — and `captureManifest` commits it into the PUBLIC oracle

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1081` (the region exclusion),
`:644` and `:648-654` (`derivedLiteralLength`'s two deliberate refusals),
`:318` with the derivation at `:282-317` (the "loses nothing" claim);
consumed at `scripts/prod-prober/run.mjs:3605-3612` (the capture gate).
Pinned-but-unmeasured at `src/__tests__/prod-prober-wiring.test.ts:842-846` (test title).

**Issue.** `long-token-anywhere` excludes every literal overlapping a **parseable** header region
(`:1081`), on the stated ground that `long-literal-in-headers` already owns those regions and that
"the exclusion loses nothing ONLY while `TOKEN_MIN >= HEADERS_LITERAL_MAX`" (`:292-297`, restated
as the wiring test's title at `:842`).

**That condition is necessary and NOT sufficient, and the gap is exactly where
`derivedLiteralLength` deliberately under-counts.** It refuses to enter `(SELECT …)` (`:644`) and
skips whole any `(` whose callee is not in `BUILDERS` (`:648-654`). So a literal in a header region
that sits behind either one derives **0**, `long-literal-in-headers` does not fire, the three
anchored header rules measure 0 < `HEADER_LITERAL_MIN`, and `long-token-anywhere` — the only rule
left — has been switched off for that region.

The recorded residual beside `derivedLiteralLength` says this "needs an adversary who both splits
the key AND routes it through a function this list does not name." **Measured: no split is needed,
no adversary is needed, and one ordinary wrapper suffices.**

**Failure scenario — CONFIRMED BY EXECUTION.** `hygieneViolations(jobname, cmd)` at HEAD, with
`KEY = "FAKE-abcdef0123456789abcdef0123456789"` (37 chars, digit-bearing):

```
coalesce fallback key under X-Service-Key    []
nullif fallback                              []
DO block, coalesce fallback                  []
CONTROL: same key, plain                     ["[x-service-key-literal]","[long-literal-in-headers]"]
CONTROL: key outside any jsonb_build_object   ["[long-token-anywhere]"]
```

The first row is:

```sql
SELECT net.http_post(url := 'https://x.invalid/a',
  headers := jsonb_build_object('Content-Type','application/json',
                                'X-Service-Key', coalesce(nullif(v_key,''), '<37-char key>')));
```

Note the two CONTROLs: the identical key is caught when written plainly, and the identical
`coalesce(x, '<key>')` is caught when it sits **outside** a `jsonb_build_object`. **Moving the
credential INTO the header expression is what makes it invisible** — the precise inversion of what
the rule set is for. `(SELECT '<key>')`, `util_wrap('<key>')` and `trim_key('<key>')::text` all
behave identically (`[]`).

**And the capture path publishes it — CONFIRMED BY EXECUTION.** Driving the real
`captureManifest` with a stub seam returning one such row under a non-flagship jobname:

```
captureManifest exit code: 0 (0 = captured, 1 = refused on hygiene)
  log: captured 1 job(s) from database "OK — the marker names PROD." at 2026-09-11T00:00:00.000Z
  log:   audit_log_hot_to_cold 0 * * * * active=true sha 3cad51f279a4
WRITTEN FILE CONTAINS THE KEY: true
```

⚠️ **The flagship is incidentally covered and the other fourteen jobs are not.** Under the jobname
`match_engine_cron` the same row is refused — but by `[vault-absent]`, not by any credential rule,
because `vault-absent` is the only rule scoped to that one job (`:1215`). Every other cron job in
the plausibility list has no such backstop.

**This is not the accepted 16-31-character residual.** The value here is 37 characters and the
header name is one of the three anchored ones.

**Fix — WRITTEN AND EXECUTED.** Exclude a literal from `long-token-anywhere` only when the header
measurement actually **counted** it, instead of whenever it merely sits inside a region. Replace
`:1081`:

```js
      // ⛔ EXCLUDE ONLY WHAT `long-literal-in-headers` COULD ACTUALLY SEE. The
      // Q2 partition assumed a literal inside a header region is an argument of
      // at least its own derived length — false wherever `derivedLiteralLength`
      // refuses to descend (`(SELECT …)`, a non-BUILDERS callee), which is one
      // `coalesce(v, '<key>')` away from an ordinary cron command. MEASURED
      // 2026-09-11: a 37-character key under 'X-Service-Key' behind `coalesce`
      // reported ZERO violations and `captureManifest` wrote it into the oracle.
      if (
        regions.some(
          (r) =>
            !r.unparseable &&
            lit.start < r.to &&
            lit.end > r.from &&
            depth0Args(span, r.from, r.to).some(
              ([a, b]) =>
                lit.start >= a && lit.end <= b && derivedLiteralLength(span, a, b) >= lit.content.length,
            ),
        )
      )
        continue;
```

Measured with that patch applied, then reverted:

```

nullif fallback                              ["[long-token-anywhere]"]
DO block, coalesce fallback                  ["[long-token-anywhere]"]

=== SELF-TEST PASSED: 71/71 scenarios, every arm's kinds fired on their own fixtures and nowhere else ===
```

`71/71` includes the committed false-positive budget (`run.mjs:2548`), so the budget stays at **0 of
14**, and every red row keeps its one-rule isolation because in those rows the literal IS a counted
depth-0 operand. ⛔ No threshold moves — D4 is untouched.

Add a bypass row `(n) bypass_header_wrapped_literal_job` with

### WR-R1-01: a credential in a `--` comment inside a cron command is invisible to `long-token-anywhere`, and `captureManifest` publishes it verbatim into the public manifest

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1078` (`literalsIn(span)` — the token rule reads
LITERALS only) and `:546-564`; consumed at `scripts/prod-prober/run.mjs:3605-3612`.

**Issue.** `literalsIn` walks `masked`, in which `scanSql` has blanked comment bodies, so a comment
is never a literal and never reaches the token rule. The four text-shape rules (`:1150-1176`) DO read
`span.sql` raw, so a JWT, a `service_role` mention and a `'Bearer xxxxx` literal are still caught in a
comment — but an opaque non-JWT key is not.

This is the exact opposite of the call this repository already made for the sibling gate:
`scripts/lint-app-guc.mjs:10-21` (decision D-05) argues at length that *"a grep does not know a
comment from a statement. So neither may this gate."* Here the token rule quietly does.

**Failure scenario — CONFIRMED BY EXECUTION:**

```
comment-borne key             []
comment inside a DO body      []
key in a quoted IDENTIFIER    []
CONTROL: same key in literal  ["[long-token-anywhere]"]
```

The realistic path is an operator "removing" an inline key by commenting it out. The next capture
writes that comment, byte for byte, into `scripts/prod-prober/cron-manifest.json` in a **public**
repository, and the arm reports the row clean. Note that comments in these commands are not
hypothetical: the committed `retention_compute_jobs_orphaned_running` row opens with a
`-- CANARY_162_V1_PROSE_ONLY` block.

**Warning rather than Critical** only because the family this project has actually leaked — a
Supabase service-role JWT — is still caught from raw text by `jwt-shape` and `service-role`.

**Fix.** Run the token test over comment bodies as well as literals. `scanSql` already knows where
they are; the cheapest total version is to scan `span.sql` minus the masked-literal regions, or to
add a `commentsIn(span)` producer beside `literalsIn(span)` and feed both into the same token loop.
Give it its own bypass row so the arm is individually neuterable, and state the D-05 parallel in the
comment.

### WR-R1-02: `long-token-anywhere` fires on an ordinary UUID path segment — a foreseeable false positive introduced by CR-04's `isBareUrl`

**File:** `scripts/prod-prober/arms/cron-drift.mjs:363-367` (`isBareUrl`), threshold at `:318`.

**Issue.** `isBareUrl` now rejects a URL whose any `/`-delimited segment is `TOKEN_MIN`+ characters
and contains a digit. A UUID is 36 characters and contains digits, so any cron command posting to a
resource-scoped REST path fails the exemption and fires a rule whose remedy is *"treat the named
secret as EXPOSED and rotate it first"*.

**Failure scenario — CONFIRMED BY EXECUTION:**

```
isBareUrl("https://x.invalid/api/strategies/123e4567-e89b-12d3-a456-426614174000")  false
hygiene on that command  ["[long-token-anywhere]"]
```

The committed budget is still **0 of 14** (the self-test's budget scenario is green), so nothing is
live — but this is one ordinary cron job away, it fires hourly, and `TOKEN_MIN`'s own docstring
already warns the margin is one character wide. An arm that cries wolf on a UUID is how a true
positive gets ignored, which is the failure mode the zero-FP budget exists to prevent.

**Fix.** Narrow rather than raise (per the rule's own instruction at `:314-316`): exempt a segment
that matches a canonical UUID (`/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`),
and calibrate it in both directions in the wiring test beside the existing boundary assertions —
a UUID segment is exempt, a same-length opaque `FAKE-…` segment is not. Do **not** raise `TOKEN_MIN`:
per the derivation at `:289-297` that re-opens the region partition.

### WR-R1-03: the F3 residual is recorded as narrower than it measurably is — the per-row refusal loses a row's own credential finding for EVERY job, not only `match_engine_cron`

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1426-1451`; the understated record is in
`.planning/phases/164.8.5-…/164.8.5-FIX-PROBER-SUMMARY.md` under F3.

**Issue.** The fix summary names the residual and then bounds it: *"That is only ever
`match_engine_cron`, the one job the rule resolves callables for."* Measured at HEAD, that bound is

**Failure scenario — CONFIRMED BY EXECUTION** (same run as CR-R1-02 scenario B): a

The run still exits 1, so this is a downgrade and not a false green — hence Warning. But it is the

## Info

### IN-R1-01: the "the diff is exactly two lines" reasoning is stale under `ws-collapse-v2`

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1752-1757`

The comment says *"Normalization collapses each side to one line, so the diff is exactly two lines."*
`ws-collapse-v2` (`:232-239`) preserves line breaks by design, so a multi-line command produces two
array entries each containing embedded newlines. The `^[+-] ` prefix then applies only to the first
physical line of each side, and a reader of the Actions log cannot tell where the manifest text ends
and PROD's begins. The assertion at `run.mjs:2645` counts array entries, so it does not notice.
Prefix every physical line, and correct the comment.

### IN-R1-02: `captureManifest` has no guard around `hygieneViolations`, so a throw exits 3 — the code its own docstring assigns to three other refusals

**File:** `scripts/prod-prober/run.mjs:3605`, docstring at `:3540-3566`, top-level catch at `:3723-3729`

`hygieneViolations` throws on an absent `functionsDir` and on the `codeSpans` depth refusal. Neither
is wrapped here, so the throw unwinds to `main`'s catch, which leaves `code` at its initialiser `3` —
the value the docstring assigns to "no `--out` / unidentified database / unreadable record". Nothing
is written, so this is fail-safe, and the crash line is printed; but the exit code alone no longer
distinguishes a crash from a usage refusal. Wrap the loop the way `compareManifest`'s `judgeRow`
already does and give it its own exit code, or document 3 as also meaning "crashed".

### IN-R1-03 (pre-existing, not from this pass): `run.mjs`'s main-module guard is weaker than the idiom its sibling documents

**File:** `scripts/prod-prober/run.mjs:3722` — `if (process.argv[1] && process.argv[1].endsWith("run.mjs"))`

`scripts/lint-app-guc.mjs:1128-1141` documents the realpath-safe guard as *"the `[VAC04-C2]`
lesson"* — comparing `import.meta.url` to `file://${process.argv[1]}` "no-ops on symlinked or
space-bearing paths, silently turning the CLI into a library". The prober's guard has the opposite
failure: any process whose `argv[1]` merely *ends with* `run.mjs` — a future `scripts/<x>/run.mjs`
that imports this module — executes the CLI and calls `process.exit`. Introduced in `42868a9b`, not
by this pass. Adopt the `invokedDirectly()` idiom.
