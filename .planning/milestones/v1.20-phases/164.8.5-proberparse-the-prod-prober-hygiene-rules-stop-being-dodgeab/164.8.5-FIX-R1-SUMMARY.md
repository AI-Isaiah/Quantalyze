### CRITICAL 1 — a refused row's verdict coerced to "clean", raw PROD command printed to a PUBLIC log

Reproduced with the review's scenario B (**no operator mistake needed** — the throwing input is the
command TEXT itself, and it works for ANY jobname).

**AFTER**:

Three things moved: the key is gone from the log, the withholding SAYS WHY, and the credential

**The invariant, not the reproduction.** The refusal is now recorded **at the point of refusal** —

producer that forgets to record cannot re-open the hole. The file's own rule two lines above the
print was corrected: it now says the text is printed only when both sides were **JUDGED** and both
PASSED.

### CRITICAL 3 — a `0x1E` inside a command splits the record into two well-formed ones

**BEFORE** (at `96925a99` — both spellings reported `malformed: []`, i.e. the parser claiming it had
read every row):
```
(i) 0x1E + whitespace tail -> rows: 2 (real jobs: 2) malformed: []
     jobnames: a_job,b_job
(ii) 0x1E + 6x0x1F tail    -> rows: 3 (real jobs: 2) malformed: []
     jobnames: a_job,c_job,z_job
     rows failing hygiene: ["z_job"]  (the real command DOES: true )
```
In (ii) the REAL job `c_job` reports clean with a truncated command while the credential is
attributed to `z_job`, **a job that does not exist**.

**AFTER** (`CRON_JOB_COLUMNS.length = 8`):
```
(i)  0x1E + whitespace tail
      rows: 1 | real jobs: 2 | malformed: [{"index":1,"fields":7},{"index":2,"fields":2}] | total: 2
      countMismatch: CAUGHT — the database reported 2 cron.job row(s) but this reading yielded 3 record(s)
(ii) 0x1E + 6x0x1F tail (fab)
      rows: 2 | real jobs: 2 | malformed: [{"index":1,"fields":7}] | total: 2
      countMismatch: CAUGHT — the database reported 2 cron.job row(s) but this reading yielded 3 record(s)
(iii) stdout TRUNCATED at a record boundary — every surviving record WELL-FORMED
      rows: 1 | real jobs: 3 | malformed: [] | total: 3
      countMismatch: CAUGHT — the database reported 3 cron.job row(s) but this reading yielded 1 record(s)
```

**The invariant, not the reproduction.** `CRON_JOB_SQL` now carries `count(*) OVER () AS total`,
computed by Postgres over the real rows *before any separator was chosen*.

⭐ **`total` is the LAST column and the position is load-bearing, measured not assumed.** With it
LAST, the head fragment of a payload-`0x1E` split loses it and is therefore **SHORT**, so the width
guard bites too. **Measured with `total` FIRST instead: the head fragment had the full width, parsed
as a row, and the whitespace-tail spelling was caught by nothing at all.**

Case **(iii)** is the one that isolates the count guard: whole records are gone, nothing is a
fragment, `malformed` is EMPTY and every width is exactly right. The field-count guard is
*structurally incapable* of seeing it.

⚠️ **The brief's cheaper additional guard was considered and REJECTED as measurably VACUOUS.**
"Refuse any record whose `command` field contains either separator byte" cannot fire: `command` is
produced by splitting on both bytes, so it can never contain one. A guard that cannot fail is worse
than no guard because it reads as coverage. The rejection is recorded beside the parser so it is not
re-proposed.
