## Critical Issues

### CR-R2-01: the new `jobname` totality guard SILENCES every credential rule on a cron row created by pg_cron's two-argument `cron.schedule` — the credential is never named

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1132-1136`
**Introduced by:** `da382b45` (this fix pass), which replaced `const name = String(jobname ?? "")`.
**CONFIRMED by execution.**

`hygieneViolations` now *throws* when `jobname` is absent or blank. Both callers route a throw to
a per-row refusal, and on the PROD side that refusal is **substitutive**: `compareManifest`
pushes a `measure-fail` and `continue`s, so **no rule runs and no `cron-secret-in-command`
defect is produced for that row**.

`cron.job.jobname` is NULLable, and pg_cron's two-argument `cron.schedule(schedule, command)`
leaves it NULL. `psql -At` renders a NULL field as the empty string, and `parseCronJobRows`
takes `f[1].trim()` — so an unnamed PROD job reaches the rules as `""`.

**FAILURE SCENARIO (measured, not argued).** Command:
`SELECT net.http_post(url := 'https://x.invalid/a', headers := jsonb_build_object('X-Service-Key', '<37-char key>'));`

```
jobname "named_job"  -> ["x-service-key-literal","long-literal-in-headers"]
jobname ""           -> THROW: "…no usable jobname — refusing to judge it."
jobname "   "        -> THROW: same

compareManifest(null, [unnamed row, named row], {liveMarker:"TEST"}) defects:
   measure-fail           | prod:                | …no usable jobname…
   cron-secret-in-command | prod:named_job       | …fails 2 hygiene rule(s)…
```

The identical command is reported for the named row and **not reported at all** for the unnamed
one. I then disabled ONLY this guard (`if (typeof jobname !== "string" || …)` → `if (false)`,
grep-verified as landed, restored by `cmp`-proven `cp`) and re-ran the same probe:

```
jobname ""    -> ["x-service-key-literal","long-literal-in-headers"]
compareManifest defects now include:
   cron-secret-in-command | prod:  | the PROD cron.job row for  fails 2 hygiene rule(s)…
```

So the guard shipped this pass is precisely what suppresses the finding. Before `da382b45` the
row was judged normally.

**Why this is Critical and not a Warning.** The module headline names the measured outage as an
inline service key living in `cron.job.command` for months. This makes that exact finding
disappear for a row shape produced by an *ordinary pg_cron API call* — no obfuscation, no
adversary. The run does still exit 1 on the `measure-fail`, so it is not a green pass, but the
credential is never named, the rotation remedy is never attached, and the operator is sent to
fix a *jobname*. It is also a one-step off-switch: `cron.unschedule('x')` followed by the
two-arg `cron.schedule(…)` removes the jobname and takes all thirteen rules with it — the same
"off-switch an adversary holds with one character" class as F2 and WR-R1-03, both of which this
phase closed.

**The guard's own justification does not support its blast radius.** Its message says *"The
jobname SCOPES the vault-absent rule, so an unnamed row silently opts out of it."* That is true
of **one** rule — `vault-absent` is gated on `name === "match_engine_cron"` — and the refusal
disables **thirteen**.

**Fix** — apply WR-R1-03's own remedy (additive, not substitutive). Drop the throw, keep a
normalised name for the message text, and report the scoping loss as its own refusal id beside
whatever the rules found:

```js
// cron-drift.mjs — replace the jobname throw at :1132
const name = typeof jobname === "string" && jobname.trim().length > 0 ? jobname.trim() : null;
// …after `say` is defined, BEFORE the rule loops:
if (name === null) {
  say(
    "jobname-absent",
    "a cron.job row carries no jobname, so the vault-absent rule — which is SCOPED to a single " +
      "jobname — could not be applied to it. Every other rule below still ran, and any finding " +
      "they report is real.",
  );
}
// …and use `name ?? "an unnamed job"` in every violation sentence.
```

Add `"jobname-absent"` to `HYGIENE_RULE_IDS` and to `UNJUDGEABLE_RULE_IDS` (so it routes to
`measure-fail` and not to a rotation remedy), ship it a red row in `hygiene-red.json`, and add a
`run.mjs` scenario that drives an unnamed PROD row carrying an inline key and requires BOTH
`cron-secret-in-command:prod:` **and** the refusal. ⛔ The `typeof command !== "string"` guard at
`:1127` is fine as it stands and should NOT be changed — a non-string command really cannot be
scanned; a nameless one can.

### WR-R2-01: `isBareUrl` never examines the URL AUTHORITY — a credential in a host label is exempted by no-rule-at-all, and two docstrings claim the opposite

**File:** `scripts/prod-prober/arms/cron-drift.mjs:386` (`BARE_URL_RE`), `:445-451` (`isBareUrl`)
**CONFIRMED by execution.**

CR-04 closed the PATH-segment half of this exemption. The AUTHORITY half was never closed, and
both docstrings assert that it was:

- `:375-386` — *"`?`, `#` and `user:pw@` are all ABSENT from this pattern, so a 'URL' … carrying
  credentials in its authority … is NOT exempt."* True only of `user:pw@`.
- `:426-431` — *"A URL is exempt only while none of its segments would be a credential on its
  own, so **the exemption can never be the reason a credential goes unreported**."* Falsified
  below. `isBareUrl` strips the authority with `token.replace(/^https?:\/\/[^\/]*/, "")` and
  tests only the remaining path.

**FAILURE SCENARIO.**
```
isBareUrl('https://FAKE-01234567890123456789012345678901ab.invalid/a') -> true
hygieneViolations('j', "PERFORM net.http_post(url := 'https://<same 37-char key>.invalid/a');")
   -> []                                        (no rule fires at all)
hygieneViolations('j', "PERFORM foo('<same key>');")        -> ["long-token-anywhere"]
hygieneViolations('j', "…url := 'https://x.invalid/t/<same key>'…") -> ["long-token-anywhere"]
```
A host label matches `[A-Za-z0-9.-]+` in full, so every character of the key is inside the
pattern's own authority charset — byte-for-byte the CR-04 defect, moved left of the first `/`.
`captureManifest` would then write that command into the oracle committed to a PUBLIC repo.

I am filing this as Warning rather than Critical because no shape this project has recorded
puts a credential in a host label — unlike CR-04's path form, which the round-1 review correctly
called "the commonest webhook-token shape there is". The *mechanism* is identical.

**Fix** — ask the same question of the authority that CR-04 asks of each path segment, and
correct both docstrings:

```js
export function isBareUrl(token) {
  if (!BARE_URL_RE.test(token)) return false;
  const credentialish = (s) => s.length >= TOKEN_MIN && /\d/.test(s) && !CANONICAL_UUID_RE.test(s);
  const authority = token.replace(/^https?:\/\//, "").split("/")[0];
  // A host LABEL that would be a credential on its own is not "a URL carrying nothing".
  if (authority.split(".").some(credentialish)) return false;
  return !token.replace(/^https?:\/\/[^/]*/, "").split("/").some(credentialish);
}
```
Calibrate in both directions in `src/__tests__/prod-prober-wiring.test.ts` beside the existing
`BARE_URL_RE` block, and re-run the committed-manifest FP budget (the real 79-character
analytics URL's host labels are `quantalyze-analytics-production` (31), `up`, `railway`, `app`
— all under `TOKEN_MIN`, so the budget is unaffected; **re-measure rather than trust that**).

### WR-R2-05: WR-R1-03's additive refusal is ORDER-DEPENDENT — a deep-nesting throw blinds every structural rule for all LATER sibling spans, and the recorded residual is again narrower than measured

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1176-1184`
**CONFIRMED by execution.**

`codeSpans` throws from inside its recursion, so the parent's remaining `dollarRegions` loop AND
its entire single-quoted-body walk are abandoned. Everything not yet pushed into `spans` is lost
— not merely the too-deeply-nested body.

**FAILURE SCENARIO.** `deep` = six nested `DO` bodies with no credential. `sibling` = an ordinary
depth-1 `DO $y$ … $y$` carrying an inline `X-Service-Key` header literal.
```
SIBLING ALONE (control) -> ["x-service-key-literal","long-literal-in-headers"]
SIBLING then DEEP       -> ["command-unjudgeable","x-service-key-literal","long-literal-in-headers"]
DEEP then SIBLING       -> ["command-unjudgeable"]                 <-- credential NOT named
```
The only thing that changed is the ORDER of two independent statements in one command.
`command-unjudgeable` is in `UNJUDGEABLE_RULE_IDS`, so the row routes to `measure-fail` with no
rotation remedy: a real inline key in an ordinary shallow body is never named.

`164.8.5-FIX-R1-SUMMARY.md` residual 2 records this as *"A credential INSIDE a too-deeply-nested
`DO` body is still unreported … at its real width"*, and measured it only with the key in the
OUTER command — which is `spans[0]`, pushed before any recursion, so it can never be lost. That

first). The loud fallback keeps this a Warning, not a Critical.

  if (depth > MAX_DOLLAR_DEPTH) { refusals.push(`dollar nesting deeper than ${MAX_DOLLAR_DEPTH} at offset ${base}`); return out; }

and have `hygieneViolations` `say("command-unjudgeable", …)` when `refusals.length > 0` rather
than from a `catch`. Then re-measure the probe above: `DEEP then SIBLING` must report

### WR-R2-06: `DETECT_RE`'s block-comment groups BACKTRACK across statements and report a phantom app-GUC read

**File:** `scripts/lint-app-guc.mjs:142-143`; the byte-identical inline copy at
`scripts/prod-prober/arms/cron-drift.mjs:1407-1409`
**CONFIRMED by execution.** The AFTER-paren group is new this pass (`113f9783`, WR-05); the
BEFORE-paren group carries the same flaw and pre-dates it.

`\/\*[\s\S]*?\*\/` is lazy but still BACKTRACKS: when the shortest `*/` leads to a non-`app.`
literal the engine extends the "comment" to a LATER `*/` in the file and tries again.

**FAILURE SCENARIO.**
```
input : current_setting(/*a*/ 'other.x'); SELECT /*b*/ 'app.z';
DETECT_RE.test(...)  -> true
countReads(...)      -> [{ index: 0, line: 1,
                           text: "current_setting(/*a*/ 'other.x'); SELECT /*b*/ 'app." }]
control (no comments): current_setting('other.x'); SELECT 'app.z';  -> false
```
There is no app-GUC read in that text. The 51-character match spanning two statements is the
tell. Consequences: in `lint-app-guc` an unannotated file gets a phantom `unannotated-reader`
whose only D4-permitted remedies are "annotate" or "remove the reader"; an **annotated** file
gets `header-count-mismatch` whose message instructs *"A NEW read was added to an annotated
file — fix it, do not raise the count"*, sending a maintainer to hunt a reader that does not
exist. In the prober the same regex fires `app-guc` → `cron-secret-in-command` → a rotation
remedy. The corpus is at 0 today, so nothing fires now; this is a latent cry-wolf.

**Fix** — make the comment body incapable of crossing its own terminator, which also removes the
backtracking. Replace both occurrences of `\/\*[\s\S]*?\*\/` in BOTH copies (they must stay
byte-identical — `src/__tests__/lint-app-guc.test.ts` pins the identity by substring) with the
classic non-crossing form:
```
\/\*[^*]*\*+(?:[^/*][^*]*\*+)*\/
```
Then re-run `node scripts/lint-app-guc.mjs` and confirm `findings 0` / 292 files unchanged, and
add the two texts above to the DETECT_RE calibration block as a NEGATIVE cell.

### WR-R2-07: `long-token-anywhere` fires on an ordinary URL followed by a comma or wrapped in parentheses — a zero-budget false positive with a "rotate the exposed secret" remedy

**File:** `scripts/prod-prober/arms/cron-drift.mjs:1302` (`if (isBareUrl(token)) continue;`), `:386`
**CONFIRMED by execution.**

The exemption is applied to the whole whitespace-delimited token, and `BARE_URL_RE` is anchored
`^…$`, so ANY adjacent punctuation that is not in the path charset `[A-Za-z0-9._~/-]` destroys
it. `.` happens to be in the charset; `,` `)` `;` `'` are not.

**FAILURE SCENARIO** (ordinary prose, no credential anywhere):
```
DO $b$ BEGIN RAISE NOTICE 'see https://api.example.com/v1/ingest, then retry'; END $b$
   -> ["long-token-anywhere"]
SELECT 'endpoint (https://api.example.com/v1/ingest)';
   -> ["long-token-anywhere"]
… same URL with no trailing punctuation                     -> []
```
`long-token-anywhere` is a credential rule, so this becomes `cron-secret-in-command` whose remedy
is *"Treat the named secret as EXPOSED and rotate it first"* — hourly, on a real command, on no
evidence. The `TOKEN_MIN` docstring (3) already names this class as the thing the rule must never
do, and WR-R1-01's new comment producer widened the surface (a URL in a `--` comment is now token
-tested too). The committed corpus is at 0 today only because its one long URL carries no digit.

**Fix** — strip trailing/leading punctuation before the exemption test, not before the length
test (so the length still measures the real token):
```js
const TRIM_PUNCT = /^[('"`\[]+|[)'"`\].,;:!?]+$/g;
…
if (isBareUrl(token.replace(TRIM_PUNCT, ""))) continue;
```
Calibrate both directions in the wiring test: the three prose forms above must report `[]`, and
`https://hook.invalid/t/<37-char key>,` must still report `long-token-anywhere`.
