## Where the PG lane runs

| Option | Description | Selected |
|--------|-------------|----------|
| Both, one script | Same script local + a new CI job with its own throwaway cluster | ✓ |
| Local author-time only | Stays a pre-review oracle; CI keeps using shared TEST | |
| CI only | Runner is a CI job; no local path | |

**User's choice:** Both, one script.
**Notes:** The deciding constraint is that a mutation run deliberately breaks arms and restores
them, so it cannot use the shared TEST database — that database sits behind an advisory-lock mutex
shared with everyone else's CI. "Local only" was rejected because criterion 1 says the runner runs
IN CI, and a runner people are *supposed* to run is the same shape as `/gsd-pr-branch` (nothing
invokes it) and `SKIP-01` (skips forever, reads as PASS) — both on this phase's own defect list.
Two portability fixes came out of reading the existing script rather than assuming: `PGBIN`
defaults to a macOS-only homebrew path, and the fixed default port serialises concurrent agents.

## PROD access for criterion 4

| Option | Description | Selected |
|--------|-------------|----------|
| CI job, read-only role | Dedicated least-privilege PROD role in CI secrets; unskippable | ✓ |
| Local pre-merge step | No PROD creds in CI; run by whoever ships the migration | |
| Diff against TEST in CI | Reuse the DSN sql-tests already holds | |

**User's choice:** CI job with a read-only role.
**Notes:** "Diff against TEST" was rejected on correctness, not cost — that is DRIFT-01, a
different finding. TEST agreeing with the repo says nothing about PROD's body, which is where the
near-GDPR-regression (DRIFT-02) lived. The local option was rejected on the same ground as the
lane question: a manual gate is a claim that a human will remember, and the claim is never
compared to the thing.

## Failure blast radius

| Option | Description | Selected |
|--------|-------------|----------|
| Both hard-fail, exit 1 | Lying annotation AND coverage regression both fail the build | ✓ |
| Annotation fails, coverage warns | Coverage floor prints while 164.4 backfills | |
| Both advisory, report only | Runner reports; humans decide | |

**User's choice:** Both hard-fail, exit 1.
**Notes:** Branch protection is deliberately OFF on this repo, so a non-zero exit is the only
signal that exists — which argues for making it loud rather than soft. Advisory would reproduce
the status quo the phase exists to change: every mechanism the runner would catch was already
GREEN in CI. Clarified during write-up that the coverage floor is a RATCHET pinned at today's
measured 1/71 — it fails on regression, never "until 71/71".

## Fold in Phase 159's 2 items

| Option | Description | Selected |
|--------|-------------|----------|
| Fold in, one spec | Close both 159 items on the new lane, in this phase | ✓ |
| Follow-up, keep 164.3 narrow | Ship the lane; close 159 later | |

**User's choice:** Fold in.
**Notes:** Both 159 items were marked blocked earlier the same day on exactly the capability
criterion 2 builds. The argument that carried it was not the items themselves but the lane's
design: a lane that can run `supabase/tests/*.sql` is not automatically one that can drive two
concurrent HTTP POSTs against an app talking to it. Designing it without its first real consumer
in view is how a cheap addition becomes rework. Bounded to one spec, no production code changes.

**Notes:** Raised because creating a database role and setting a CI secret is a founder action —

and the runner (the highest-value item by a distance) has nothing to do with the PROD role.

`SKIP-01`, its own named defect.
