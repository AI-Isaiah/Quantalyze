  <behavior>
    - Parses `RED-UNDER-M` lines: single-line JSON in a SQL comment, adjacent to (immediately after) its prose RED-UNDER block. Required capabilities (fixed by the corpus, RESEARCH §Q3): `edit` (repo-relative file, byte-exact find/replace, nth occurrence), `insert-after` (file, byte-exact anchor, text), `sql` (statement executed on the throwaway DB after migrations, before the gate — the lane's --post-apply hook), `neuter` (names ANOTHER arm whose failure must be suppressed first), `waiver` (reason string; mutually exclusive with apply), and multi-step `apply` arrays for LAYERED mutations.
    - Prose markers and structured twins are matched ONLY at comment line start (leading whitespace, comment dashes, then the marker) — a fixture reproducing the header-prose shape (the marker mentioned mid-line inside a doc comment) is counted as ZERO annotations. This encodes the 30-vs-33 correction as a test.
    - Parity per file: count(prose markers) == count(structured twins), where a waiver counts as a twin. A prose annotation without a twin is a named parity defect.
    - Malformed JSON, unknown keys, or an apply+waiver combination are parse errors naming the line number — fail loud, never skip a bad annotation.
    - Reads files via node:fs only (grep is NUL-blind in this repo — measured precedent).
  </behavior>

Write `GRAMMAR.md` documenting every key with one real example per shape drawn from the corpus, the parity rule, the waiver rule, and an explicit note that 164.4 inherits this schema — plus the line-start anchoring rule and WHY (header prose inflated the recorded count).
