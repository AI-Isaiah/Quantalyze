## HIGH

### SFH-01 — C5's literal check admits quoted-identifier and schema-qualified calls, so a side-effecting call can replay inside the shared-TEST restore transaction

**File / symbol:** `scripts/extract-reference-inserts.mjs` → `updateLiteralCheck`

The call detector is `/([A-Za-z_][A-Za-z0-9_]*)[\t\n ]*\(/g` over masked text, with
`now` exempted by NAME ONLY. `maskSql` keeps quoted identifiers, as the WR-06 comment
above `quotedId` records. So:

- `"current_setting"('app.x')`: the identifier ends at the `"`, the `(` is not
  adjacent to a matched identifier, and **no call is seen**.
- `"pg_notify" ('c','p')::text`: **no call is seen**, for the same reason.
- `net.now()` or `anyschema.now()`: the regex matches `now(` and exempts it, so any
  function NAMED `now` in any schema passes.

Measured (offline, `matchUpdate` against `public.profiles`):

```
REPLAYED  [] :: UPDATE profiles SET manager_status = "current_setting"('app.x') WHERE id = 1;
REPLAYED  [] :: UPDATE profiles SET manager_status = net.now() WHERE id = 1;
REPLAYED  [] :: UPDATE profiles SET manager_status = "pg_notify" ('c','p')::text WHERE id = 1;
```

The INSERT side's `literalCheck` refuses both spellings: it names
`current_setting` and `net` as non-literal tokens, also measured. C5 is therefore
WEAKER than the C2 rule it sits beside. The function's own comment says it
"bans current_setting(), net.http_*(), pg_notify() and every other side effect",
and it does not ban the quoted spelling of any of them.

**Failure scenario.** An applied migration carries a top-level
`UPDATE public.profiles SET x = "net"."http_post"(…)` or an equivalent quoted call,
and a reviewer adds its `update:` line on the classifier's word. The restore then
fires that call inside the transaction on shared TEST. A pg_net request queued
there is sent on COMMIT, and a `current_setting` read computes the value from the
RESTORE's session rather than the migration's. `--audit` and the self-test both stay
green. Corpus today: 0 instances (the audit's 6 replayed statements are all
literal).

**Recommendation.** Invert it so it has the same shape as C2: a TOKEN ALLOWLIST over the SET and WHERE
region (identifiers that are column names or reserved words `AND/OR/NOT/IN/IS/NULL/
TRUE/FALSE/DEFAULT`, plus unqualified `now` followed by `(`), and refuse any `"`
immediately before a `(` and any `.` immediately before an identifier that is
followed by `(`. Add two red self-test kinds, `c5-update-quoted-call` and
`c5-update-qualified-now`. The floor moves 39 to 41.

## MEDIUM

### SFH-02 — "0 unaccounted" and "every UPDATE on a replayed table is accounted for" are stronger than the mechanism: writes inside a DO body, from a top-level function call, or via COPY are invisible

**File / symbol:** `scripts/extract-reference-inserts.mjs` → `modeAudit` C5 loop
(`if (!pair && m.ok.length === 0 && m.rejected.length === 0) continue;`),
`matchUpdate` (the `body` bucket), `matchOtherDml`. The claim is in
`scripts/restore-test-refdata-allowlist.txt`, where the C5 header says "every
UPDATE on a replayed table is accounted for", and in both workflows, which pin
`0 unaccounted`.

`matchUpdate` puts every UPDATE inside a dollar body into `body`. `c5Verdict` never
reads `body` except to word a count-mismatch refusal. With no pair, a body-only
hit falls through the `continue` in silence. That is right for a
`CREATE FUNCTION … AS $$ … $$` body, which the migration never executes. It is
wrong for a `DO $$ … $$` body, which the migration DOES execute. The lexer does
not tell those two apart. `matchOtherDml` also skips `inBody`. Top-level
`SELECT some_backfill()`, `CALL …` and `COPY … FROM` are not looked for at all.

Measured on the corpus: there are 20 UPDATE hits inside bodies on replayed tables,
across 14 files. I checked each against the nearest preceding opener, and **every
one is a `CREATE [OR REPLACE] FUNCTION` body** (`sanitize_user`,
`finalize_wizard_strategy`, `flip_capital_ownership_to_team_review`). A second probe
looked for top-level `DO` / `SELECT` / `CALL` spans whose text contains
`UPDATE`/`DELETE FROM` of a replayed table and found **0**. So this is latent. But
this repo's house style for a data backfill is exactly a `DO $$ … UPDATE … $$` block.

**Failure scenario.** A future migration backfills `profiles` inside a `DO` block.
The audit prints `audit C5 OK: … 0 unaccounted.` and both census steps pass. The
restore then COMMITS those rows in their pre-backfill state. The wrong-state leg
checks ONE pinned row, so it catches this only if the backfill happens to touch the
sentinel.

**Recommendation.** In `--audit`, for each replayed table, refuse by name any
UPDATE/DELETE of it inside a dollar body whose enclosing top-level statement starts
with `DO`. The enclosing span is the one whose `hasTag` range contains the hit.
Also refuse a top-level `SELECT`/`CALL` that invokes a function, and `COPY` into
the table: "classify by hand; C5 cannot see through it". If the team prefers to
keep the scope, reword the census line and the allowlist sentence to say
"top-level statements only" rather than "0 unaccounted". The honest form of the
current guarantee is: "0 unaccounted among top-level UPDATE/DELETE/TRUNCATE/MERGE".

### SFH-03 — the token check sends some LITERAL UPDATEs to `decline:`, which is the outcome D-02 forbids ("a decline must never hide a replayable effect")

**File / symbol:** `scripts/extract-reference-inserts.mjs` → `updateLiteralCheck`
(`/\b(FROM|USING|SELECT|RETURNING|WITH)\b/i`, and the `notCalls` set)

- `WHERE manager_status IS DISTINCT FROM 'verified'` is refused with
  `carries the token FROM — a joined … UPDATE` (measured).
- `WHERE id = ANY(ARRAY[1,2])` is refused as `the non-literal call ANY(` (measured).

Each refusal carries `nonLiteral: true`, so the documented remedy is a `decline:`
line. After that, `c5Verdict` accepts the decline and the census counts it as
"declined". The "a literal UPDATE is replayed, not declined" check never fires
again, because the classifier called the statement non-literal. The statement's
effect is dropped from every later restore, and nothing reports it.

**Failure scenario.** A migration writes the idiomatic
`UPDATE profiles SET role = 'both' WHERE role IS DISTINCT FROM 'both' AND is_admin`.
The author follows the refusal text and declines it. From then on, every restore
commits those rows in the wrong state, with a green census.

**Recommendation.** Exempt `IS [NOT] DISTINCT FROM` before the `FROM` test (strip
the phrase from the masked text first). Add `ANY`/`ALL`/`SOME` to `notCalls` when
their argument is `ARRAY[` or a parenthesised literal list. Add a green leg for
each to an existing C5 kind, so a regression that re-declines them turns red.

## LOW

### SFH-04 — the `0 unaccounted` the workflows "pin" is a string constant, so that part of the regex cannot fail

**File / symbol:** `modeAudit` final `io.out.push` (`… ; 0 unaccounted.`). Both
workflows' `Assert the allowlist audit PRINTED its census` step, `c5_line` regex, and
its comment "The regex pins `0 unaccounted`".

The line is printed only after `if (bad) return 1;`, and `0` is a literal in the
template. No run can print any other number there. The MEASURE_FAIL for an ABSENT
line is real and useful. The "pins 0 unaccounted" wording overclaims. Either
compute an `unaccounted` count and print it (then the pin can bite), or reword
the comment to "the line's presence is the check; the 0 is constant".

### SFH-05 — the restore never cross-checks `refdata_update_n` against the allowlist's `update:` pins

**File / symbol:** `scripts/restore-test-from-baseline.sh`, the `refdata_update_n`
awk and the C5 `note`.

The INSERT side takes two independent readings: the allowlist's bytes
(`REFDATA_ENTRY_N`) and the extractor's `-- refdata-expect:` trailers. The C5 side
takes one. `refdata_update_n` only goes into a `note`. Suppose the trailer
spelling drifts, or an extractor on the `REFDATA_EXTRACTOR` seam emits UPDATE SQL
without trailers. The restore then logs `refdata: 0 C5 update statement(s)
replayed` and proceeds. The SQL still runs, so no data is wrong, but the log stops
being evidence that C5 ran. Add the sum of the `update:<n>` pins, read by awk from
`$REFDATA_ALLOWLIST` the same way `REFDATA_ENTRY_N` is read, and `fail` when it
disagrees with `refdata_update_n`. Arm 33 already feeds the value 1.

### SFH-06 — declined statements are not named in the restore log

**File / symbol:** `scripts/restore-test-from-baseline.sh` C5 `note`. The extractor's
emit stderr line (`… decline: line(s) emit nothing.`) goes to `refdata.err` and is
printed only on failure.

A decline means the restore will COMMIT rows whose state differs from what
history produced. That is by design (D-02). But a successful restore log never says
it happened, or how often. Today there are 2 declines, both measured to reach no
replayed row. Print the extractor's second stderr line (or a decline count) in the
success `note`, so the log records what was deliberately NOT replayed.

## Checked and found sound (so a later round need not re-derive them)

- **Census steps under `bash -e`.** Both workflows bound every capture:
  `status`, `ok_rc`, `floor_rc`, `census_rc`, `scanned_rc`, `c5_rc`. Each grep
  distinguishes rc 1 (absent, which is MEASURE_FAIL) from rc >1 (not looked for).
  The `floor` read catches both a non-zero exit and a non-numeric value such as
  `undefined`. The data-dependence step is bounded the same way.
- **Ordering on the only path that writes to shared TEST.** In
  `test-restore-from-baseline.yml`, the `--audit` step and its census assertion run
  in the SAME job and checkout, BEFORE `Run the restore script`. The restore uses
  the default allowlist, extractor and migrations dir, and the workflow does not
  override them. So emit's deliberate skip of the membership check (kept for the
  lane's filtered allowlist) is covered by the audit on that path.
- **`REFDATA_ENTRY_N` awk against `parseAllowlist`.** Both split on TAB and both
  require field 3 to be exactly `^[1-9][0-9]*$` without trimming, so they agree on
  what an INSERT line is. The one divergence (a lone-CR line: awk skips it, parse
  calls it malformed) fails CLOSED through the extractor. An allowlist with only C5
  lines is refused by BOTH layers (arm 34 leg b, and the `c5-no-insert-line` kind).
- **C5 verdict completeness in emit.** An `update:` line whose file has 0 literal
  spans, or a count mismatch, or a `decline:` count mismatch, or a non-literal
  span with no `decline:` line is refused in both modes through one `c5Verdict`.
  `replay` is non-empty only when there are zero refusals.
- **Wrong-state RAISE.** The rewritten message has exactly one `%` for one argument,
  and its `''s` escaping survives the quoted heredoc. The lineage comment inside the
  plpgsql body has no apostrophe and no `$` tag. Arms 31 to 34 execute it.
- **Triggers the replayed UPDATEs fire on `profiles`/`strategies`**
  (`prevent_profile_privileged_change`, `reject_sentinel_writes`,
  `guard_strategies_publish_transition`, `guard_wizard_draft_updates`,
  `check_strategy_api_key_ownership`, `trg_strategies_team_review_mark_guard`). Each
  either RETURNs NEW or RAISEs. None silently reverts `NEW` to `OLD`, so a trigger
  refusal is a loud rollback, never a silently skipped row. If the restore ever
  connects as a role other than postgres, service_role or supabase_admin, the
  privileged-column trigger RAISEs loudly.
- **Emit sort.** `(basename, first)` is a total order over the blocks. INSERT order
  also moves to migration order, which is at least as safe for FK dependencies as
  allowlist order was.
- **Lane path** (`scripts/local-stack/run.sh` `load_reference_data`). It runs before
  `replay_migrations`, `filterRefdataAllowlist` drops C5 lines of replayed
  migrations by their first field, and extractor failure and empty output are both
  FATAL.
