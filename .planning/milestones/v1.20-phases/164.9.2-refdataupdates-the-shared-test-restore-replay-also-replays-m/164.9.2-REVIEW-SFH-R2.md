## MEDIUM

### R2-01 — a `decline:` over a DO-body write is never checked for literal-ness, so D-02's "a decline can never hide a replayable effect" is false for that half of the decline count

**Symbols:** `c5Verdict` (the `nonLit` array merges `m.doWrites` with
`nonLiteral: true` unconditionally), `matchDoBodyWrites`, and the allowlist header
sentence under "DECLINE, NEVER SKIP (decision D-02)": *"refused if the statement ever
turns literal … so a decline can never hide a replayable effect"*.

For a top-level UPDATE, the guarantee is real. If the statement is literal it goes
into `m.ok`, and `c5Verdict` refuses the decline with "a literal UPDATE is replayed,
not declined". A DO-body write takes a different path. Every hit becomes a
`nonLiteral: true` entry without its text ever reaching `updateLiteralCheck`, so a
**literal** backfill such as
`DO $$ BEGIN UPDATE profiles SET role = 'both' WHERE is_admin; END $$` is accepted
under a `decline:1` line. The unlisted-refusal text offers two remedies for a DO-body
write: decline it, or "move the write to a top-level literal UPDATE". An applied
migration is immutable (the file's own rule is "a pinned count moves ONLY when an
applied migration is edited"), so for an applied file the second remedy does not
exist, and decline is the only way through. The decline's reason is a human
assertion that no mechanism checks. The restore's wrong-state leg checks one pinned
row.

This is SFH-02's original failure scenario. It has moved from invisible to
visible-but-declinable. That is progress, but the census now reports it as
"declined", and the allowlist says declining such a write cannot happen.

**Measured.** There are 4 DO-body declines today. `20260407164606_perfect_match.sql:37`
reads `current_setting` and `auth.users`, so it is genuinely non-literal. The b5b
`:406`/`:408` DELETEs remove the block's own probe rows. The cleanup upsert at `:188`
sits inside a subtransaction that rolls back. None of the four is a literal write to
a replayed row. **Latent.**

**Recommendation.** For each DO-body UPDATE hit, slice the statement from the hit to
the next `;` in the masked body and run `updateLiteralCheck` on it. If it passes,
either:

- (a) print it on its own census term (`N DO-body declines over literal text`),
  which a workflow can pin to the measured value, or
- (b) require the decline reason to carry a fixed marker (for example `reaches-no-replayed-row:`).

At minimum, scope the header sentence to top-level statements and drop the "move the
write" remedy for applied files. Add a self-test kind: a DO-body literal UPDATE under
a decline must be visible on the census.

### R2-02 — `now()` and every admitted operator resolve under `SET LOCAL search_path = public, pg_catalog`, which is the shadowing argument the fixer used to exclude `lower()`

**Symbols:** `C5_ALLOWED_CALLS` (the `NOW` entry), `C5_ALLOWED_OPS`, the comment
above `C5_ALLOWED_CALLS` ("lower() / upper() are deliberately NOT here … a
`public.lower` would win"), and the `TXN_REFDATA_HEAD` heredoc in
`restore-test-from-baseline.sh`, which emits `SET LOCAL search_path = public, pg_catalog;`.

When `pg_catalog` is listed explicitly, PostgreSQL searches it at its listed position.
It is not searched first. So under `public, pg_catalog` a `public.now()` wins over
`pg_catalog.now()`. For operators, an exact-match `public.=(text,text)` or
`public.||` wins over the built-in. The reasoning that correctly kept `lower()` out
also covers `now()` and all 26 admitted operator spellings. Every replayed literal
UPDATE uses `=`. The C2 INSERT side (`now()`, `gen_random_uuid()`) sits in the same
bracket and carries the same exposure.

**Measured.** Offline, `updateLiteralCheck` classifies `SET x = now ( )` and
`SET x = y ->> 'k'` as literal. The corpus holds 0 definitions of a function named
`now` or `gen_random_uuid` in migrations and 0 `CREATE OPERATOR` in
`supabase/schema/baseline.sql`. **Latent.** The trigger would be a migration that
defines one, and that change would appear in review only as ordinary DDL.

**Recommendation.** Fix the root, not the list: bracket the replay with
`SET LOCAL search_path = pg_catalog, public`. The replayed tables still resolve,
because `pg_catalog` holds none of the 8. Built-in functions and operators then
always win. Measure it on the pg-lane through arms 22, 23, 33 and 34 before relying
on it. Also check that no replayed table name collides with a `pg_catalog` relation.
If the bracket must stay as it is, make `--audit` refuse any migration that creates a
`public` function named on `C5_ALLOWED_CALLS` or C2's `ALLOWED_CALLS`, or any operator
in `public`. In either case, fix the `lower()` comment so it no longer implies that
`now()` is immune.

## LOW

### R2-03 — the `C5 scope:` line lists what is NOT traced, and the list is incomplete

**Symbol:** `modeAudit`, the `C5 scope:` line ("NOT traced: a function called at top
level, and dynamic SQL built from a string").

Measured offline. Each shape below returns `ok 0, rejected 0, doWrites 0, otherDml 0`:

| Shape | Corpus count |
|---|---|
| a writer function called from INSIDE a DO body (`PERFORM fn()`) | **1**: `20260713120000_cleanup_abandoned_wizard_drafts.sql:149` calls `cleanup_abandoned_wizard_drafts()`, which DELETEs `strategies`. It sits inside the sentinel subtransaction, so nothing commits. |
| `EXPLAIN ANALYZE UPDATE/DELETE …` (executes the write) | 0 |
| `PREPARE p AS UPDATE …; EXECUTE p;` | 0 |
| SQL-standard `BEGIN ATOMIC` function bodies (no dollar quote) | 0 |

`BEGIN ATOMIC` is worse than untraced. The body's first statement is hidden inside
the `CREATE` span, and each later statement lexes as a TOP-LEVEL span. A literal
UPDATE in that position is reported as "add an update: line", and following that
advice would replay an UPDATE that the migration only defined and never executed.

Separately, a probe of the 11 corpus functions whose bodies write a replayed table
found exactly the 1 apply-time call site above. No top-level `SELECT fn()` or `CALL`
of any of them was found.

**Recommendation.** Add "a function called from a DO body, EXPLAIN ANALYZE, PREPARE /
EXECUTE" to the NOT-traced list. Either refuse `BEGIN ATOMIC` in `--audit` by name
("classify by hand") or teach `dollarBodyRanges` to treat it as a body.

### R2-04 — `c5Unaccounted` misses one C5 refusal site, and the FAILED line blames C5 for INSERT-side failures

**Symbol:** `modeAudit`. The "a C5 `<kind>`: line names …, which NO INSERT entry
fills" refusal sets `bad = 1` but does not increment `c5Unaccounted`. The
`audit C5 FAILED:` line is printed whenever `bad` is set. An INSERT-only failure
therefore prints `audit C5 FAILED: 0 unaccounted C5 refusal(s)`, and a C5 failure
caused only by an unfilled-table line prints the same `0`. The exit status is still
1, so nothing passes. But the number that SFH-04 made "computed" is wrong in both
cases, and the line points a reader at the wrong class. **Recommendation.** Increment
`c5Unaccounted` once per refused line at that site. Print the FAILED line only when
`c5Unaccounted > 0`, and give INSERT-side failures their own `audit FAILED` line.

### R2-05 — `DEFAULT` and qualified / domain casts are admitted, and both run code the statement text does not show

**Symbols:** `C5_ADMITTED_RESERVED` (`DEFAULT`) and `skipC5CastType`, which admits
`::schema.type`.

`SET x = DEFAULT` evaluates the column default in the RESTORE session. That is the
same concern that got the niladic session functions refused. `'x'::public.some_domain`
runs the domain's CHECK expression, which may call any function. Both classify as
literal (measured offline). **Measured today:** every column default on the 7 replayed
public tables is `now()`, `gen_random_uuid()` or a constant. No replayed UPDATE casts
to a non-`pg_catalog` type. **Recommendation.** Refuse any `::` whose type name is
qualified with a schema other than `pg_catalog`. Also note in the IN-03 paragraph
that `DEFAULT` is admitted on the premise that the replayed tables' defaults stay
free of session state. Alternatively, have `--audit` check that premise against
`baseline.sql`.

## Checked and found sound

- **DO-body detection** (`dollarBodyRanges` third element, `prepareFile.doBodies`).
  `stmtStart` moves only on a `;` outside comments, strings, quoted identifiers and
  dollar bodies. The `DO` test reads MASKED text, so a comment cannot forge or hide
  the keyword. Probes that were detected correctly:
  - `DO -- step; next\n$$…$$`
  - `DO LANGUAGE plpgsql $x$…$x$`
  - a nested `EXECUTE $q$UPDATE profiles…$q$`

  A `CREATE FUNCTION` body is not counted. The fixer's measured 4 public DO-body
  writes were re-derived independently: all 13 DO-body INSERTs into replayed tables
  are `profiles`/`strategies` self-test fixtures, and none targets a reference table.
- **Unlisted upsert refusal.** `ON CONFLICT … DO UPDATE` is flagged on multi-line,
  `ON CONSTRAINT` and `INSERT … SELECT` shapes, and refused with `bad = 1`.
- **Token allowlist.** Each of these is refused by name: a quoted call, a qualified
  call, `EXISTS(`, `CAST(`, `COLLATE`, `U&`, `CURRENT_SCHEMA`, `CURRENT_TIMESTAMP(0)`,
  `RETURNING`, and `ANY (SELECT`. A missing token class falls through to `bad` and
  is refused.
- **Restore trailer-vs-pin check.** Both awk sums print `s+0`, so the values are
  always numeric. A malformed pin (CR, whitespace, leading zero) is not summed, so
  the comparison fails CLOSED. It sits after the zero-trailer refusal and before any
  connection. Arm 24 legs (d) and (e) pin the named messages and the no-write check.
- **Declined-write notes.** The `while read` runs in the current shell (`< <(awk …)`),
  so its charset `fail` exits the script. It runs while `restore.sql` is being built,
  before `psql -f`, so a refusal there writes nothing.
- **Workflows.** The diff changes comments only. The `c5_line` regex still pins
  `0 unaccounted`, and the new comment states truthfully that the exit status is the
  gate.
- **No refusal path exits 0.** Every `refuse(` in `modeAudit`'s C5 section sets
  `bad = 1`, and `bad` returns 1 before any census line is printed.
