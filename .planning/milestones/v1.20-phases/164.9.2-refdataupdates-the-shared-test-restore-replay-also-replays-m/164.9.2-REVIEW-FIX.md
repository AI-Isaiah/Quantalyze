### ⚠️ Judgement call: DO-body DELETE / upsert are hard refusals UNLESS PROVEN, not hard refusals outright

The brief said a DO-body DELETE / TRUNCATE / MERGE / COPY / upsert on a replayed table is refused
and never declinable. Applied literally, `--audit` goes permanently red on three APPLIED migrations,
whose SQL cannot be edited: the b5b DELETEs at `20260602183000_b5b_api_key_delete_atomicity.sql:406`
and `:408`, and the cleanup self-test upsert at `20260713120000_cleanup_abandoned_wizard_drafts.sql:188`.
The reviewer said the same ("the b5b probe-row DELETEs need a way through"). So I did not add a
prose-declinable line kind. Instead, a way through that a MACHINE checks: `freshKeyProof`. A DO-body
DELETE or upsert may be declined only when it is keyed by a variable the block declares once as
`uuid := gen_random_uuid()` and never reassigns. "Reassigns" means `:=`, a statement-level `=`, a
FOR / INTO / GET DIAGNOSTICS target, a shadowing declaration, a quoted spelling or a block label. That
key means the write can reach only rows the block itself wrote. TRUNCATE, MERGE and COPY have no
such proof and are always hard. All three corpus writes pass it (each is keyed by `v_user`), so the
census is unchanged. ⛔ If the founder wants the literal rule instead, those three applied migrations
have no remedy and `sql-gate-lint` stays red, so that choice needs a decision, not a fixer.
