## Overview

v1.7 makes Deribit a first-class exchange with full OKX/Bybit parity on both onboarding paths,
lands the founder's 3 LTP Deribit accounts as live verified track records, and burns down the
accumulated carry-forward debt (v1.6 red-team set + planning ledger + stale TODOS.md). The journey:
clear the debt baseline first (no Deribit coupling), run a live harness from the worker to answer
the two design-driving empirical questions (funding-netting shape, inverse/linear/options mix) while
also reconciling Bybit against exchange ground truth, wire the Deribit boundary + key validation in
lockstep, surface the onboarding UX, build the high-risk ingestion/dailies core against the harness
answers, lift the allocator-position block, and finally onboard the 3 real accounts behind hard
acceptance gates (the v1.5/v1.6 canary pattern).

**Grounding correction (verified live 2026-07-04, supersedes the research SUMMARY's "Phase 67 Egress
Prerequisite"):** the Railway worker already egresses from Amsterdam NL (`152.55.184.110`), Deribit's
public API returns 200 from the worker, an LTP key authenticates read-only with `account:read`
present, and ALL FOUR exchanges (deribit/bybit/binance/okx) are reachable. There is NO
egress/proxy/region work in this milestone. The live harness (DRB-01) remains — but only to fetch
real trades/transaction-log data and answer the funding-netting + instrument-mix questions that
drive the dailies design.

### Phase 70: Trades Ingestion & Dailies (RISKY)

**Goal**: A real Deribit key's full trading history — perps, futures, options, inverse contracts, funding — produces honest per-key daily returns through the ONE existing path
**Depends on**: Phase 67 (funding-netting + instrument-mix answers drive this design) and Phase 68 (boundary accepts Deribit)
**Requirements**: DRB-04, DRB-05, DRB-06, DRB-07, DRB-08
**Success Criteria** (what must be TRUE):

  1. Full realized-cash history is crawled from the transaction-log ledger per scope × currency (currencies enumerated from the account, never hard-coded; count=250 + continuation to null, paced to the ~1 req/s limit) — verified by a LEDGER-COMPLETENESS gate that fails loud on any truncated/incomplete crawl (the known fill counts 18,778/21,014/61,248 are an advisory cross-check only; Wave-0 proved they reconcile to no API surface)
  2. Trades are classified by instrument kind (perp/future/option/combo); option premiums + deliveries enter dailies as realized cash flows via the transaction log — options never run through perp fill math
  3. Inverse-contract P&L converts coin→USD at event-time index price, sign-correct on shorts, unit-tested against hand-computed fixtures
  4. Funding is ingested as part of the ledger settlement cash delta (funding-inclusive per Wave-0 A3) and summed ONCE per UTC day — no separate funding stream, no funding_fees write, no double count against realized PnL
  5. A real Deribit key's per-key dailies flow through the ONE realized+funding → CSV → `compute_all_metrics` path, and Overview/Scenario/factsheet read the same honest source
