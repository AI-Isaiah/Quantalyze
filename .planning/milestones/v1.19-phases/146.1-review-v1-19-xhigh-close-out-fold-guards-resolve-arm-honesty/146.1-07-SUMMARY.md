## (5) What RT-3 actually does, and three things the plan did not anticipate

The plan said "persist the burned csv-submit signature in the signed envelope." Three facts
measured during execution changed the shape of that, and each is a deliberate deviation:

**(a) A fingerprint, not the raw signature [Rule 2 — missing critical functionality].**
`csvSubmissionSignature` serialises the ENTIRE daily-return series. `WizardClient.tsx:334-337`
states that series is not persisted because "the parsed dataset can be megabytes — too large
for localStorage". Since the burn rides in the envelope that every wizard save rewrites,
storing it raw would push hundreds of kilobytes through an HMAC sign on every debounced
keystroke and would eventually hit the storage quota — where `saveWizardState`'s catch
swallows the write and the wizard silently stops persisting its resume pointer at all. New
`csvSubmissionFingerprint` digests the signature to ~22 chars (a base36 length prefix plus a
64-bit two-lane FNV-1a-style hash). **Both sides of the comparison are fingerprinted**, so
in-session behaviour is unchanged except for collisions, and a collision fails in the safe
direction (no re-mint → the server's equality refusal catches it).

**(b) A sticky field, because eight callers would otherwise clobber it.** Stepping back from
`csv_submit` to change the file — the exact path RT-3 exists for — fires one of the eight CSV
step-transition saves, none of which knows about the burn. Omitted ⇒ carry forward, explicit
`null` ⇒ clear, string ⇒ set.

**(c) Saves are now SERIALIZED [Rule 1 — bug found during execution].** Sticky made write
ORDER matter, and the order was wrong. An omitting save does one extra async read before it
signs, so a LATER save supplying the field explicitly finished FIRST and was then overwritten
by the earlier save's stale carry-forward. That is deterministically the upload-changed-file
sequence, so a clear was silently resurrected. `saveWizardState` now chains onto a module-level
queue; the neuter **RT3-NOQUEUE** reds the clear case, which is how I know this was a real
defect and not a hypothetical.

**(d) The mint effect refuses to compare while the series is undefined.** Naive hydration
would have shipped a REGRESSION, not a fix: the series is not persisted, so immediately after
a reload the burn is restored while `csvDailyReturnsSeries` is `undefined`, and comparing then
finds a "change" the user never made. That would re-mint on every refresh — turning an honest
identical retry into a SECOND strategy, strictly worse than the pre-RT-3 behaviour. The guard
is inert in-session (the series is only ever set, never unset). The negative-control test
`does NOT mint when the identical submission is re-uploaded after a reload` is what pins it.

**RT-3 IS DEFENSE IN DEPTH.** Every comment written says so and names the operative fence —
the server-side equality refusal at `csv-finalize/route.ts:820-863`, shipped 2026-08-18.
Nothing in this plan weakened that arm.

## Deviations from Plan

**1. [Rule 2 — missing critical functionality] The persisted burn is a bounded fingerprint.**

**3. [Rule 1 — bug] Naive hydration would have re-minted on every refresh.**
Found during task 2. Added the `csvDailyReturnsSeries === undefined` guard plus its negative
control test. Without it, RT-3 would have been a regression that broke the idempotent-retry
path. Commit `8651be47`.

**4. [Measurement, not code] The plan's `CSV_FINALIZE_MOVED` grep fires on honest prose.**
Prose kept, intent measured with a comment-stripped scan. §6 above.
