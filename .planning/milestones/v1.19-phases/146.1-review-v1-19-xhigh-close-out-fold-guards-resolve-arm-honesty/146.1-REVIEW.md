## Summary

The phase's core mechanisms hold up under adversarial reading. Specifically **verified sound**,
not merely present:

- **A1 migration (20260819130000).** `CREATE OR REPLACE`, not a drop; the STEP 1 body is
  byte-identical to `supabase/schema/functions/finalize_csv_strategy_with_returns.sql` (diffed
  programmatically — 10098 bytes, identical). NULL-safety is genuinely closed: GUARD 3 (`p_rows IS
  NULL`), GUARD 4 (`p_fmt IS NULL OR …`), GUARD 8 (`IS DISTINCT FROM 'trades'`). `NOT (x BETWEEN
  -10 AND 10)` does catch NaN and ±Infinity under Postgres NaN ordering, and the NULL arms are
  listed separately because `NOT (NULL BETWEEN …)` is NULL. Every guard sits above the `strategies`
  INSERT, and STEP 4 check (p) proves the position (not just the presence) by comparing `strpos`
  of the first `jsonb_array_elements(p_rows) elem` against the INSERT anchor. The `\M` word bound
  on the `BETWEEN -10 AND 10` check does reject a widened `-10 AND 100`. The `REVOKE … FROM
  service_role` is safe: the only caller of this RPC anywhere in the repo is
  `csv-finalize/route.ts:611`, on the SSR user client.
- **B4 migration (20260819130500).** The predicate `NOT EXISTS (… AND NOT ((status='failed_final'
  AND last_error LIKE 'orphaned_running_reaped:%') IS TRUE))` admits exactly what the header
  claims: strategies whose *only* job rows are terminalizer-marked. The marker literal matches the
  terminalizer's own stamps (`20260817120000:622,641`). The `IS TRUE` wrapper is real NULL-safety
  and arm C2b is its behavioural half. C2/C4 are a genuinely discriminating pair, and Part 2
  executes the *deployed* body (`EXECUTE v_command`), not a re-typed copy. No re-enqueue loop: the
  healed `pending` row is unmarked, so the next tick excludes the strategy.
- **B1 limiter coverage gate.** Non-vacuous. `iter_route_contexts` + `.original_route` restores
  the full 20-route surface under the pinned `fastapi==0.139.0`; `MIN_API_ROUTES`/
  `MIN_LIMITED_ROUTES` fence the truncated-walk failure; the quarantine is compared by EQUALITY so
  both a new undecorated route and a stale exemption red by name. The named change that makes it
  RED is "add an `@app.post` handler without `@limiter.limit`".
- **B2 JWT drop.** Strictly a reduction, and it incidentally closed a real live leak: the client's
  transport catch was `scrubSeamError(message, [args.userAccessToken])`, which shipped
  `X-Tenant-Claim` verbatim to the Vercel log; it now derives via `credentialHeaderValues`.
- **C2 handler collapse.** Verified faithful — I diffed the deleted `contributionCsvFinalizeHandler`
  against the surviving body; the four differing tokens are exactly `terminalStatus` and
  `logPrefix`, both now passed verbatim from the two call sites.

The one thing that did **not** hold is A4. It is a real, new, silent data-integrity regression on
the exact recovery path that A3's new copy instructs the user to take. Details below.

## Critical Issues

### CR-01: A4's metadata skip permanently strands the classification — and the annualization clock — for every strategy whose first request committed but died before its metadata UPDATE

**Files:**
- `src/app/api/strategies/csv-finalize/route.ts:1923-1932` (the skip)
- `src/app/api/strategies/csv-finalize/route.ts:1938-1943` (the enqueue that still fires)
- `src/app/api/strategies/csv-finalize/route.ts:1165-1179` (`fresh: false` echo)
- `src/app/api/strategies/csv-finalize/route.ts:827-830` (the A3 copy that instructs the resubmit)

**Issue.** A4 changed `applyCsvMetadataUpdate` from unconditional to `outcome.fresh ? … : null`.
The stated rationale defends the case where the first request DID apply metadata and a retry
flips `asset_class`. But the reachable population is the opposite one, and this phase's own A3
work names it explicitly.

Concrete failure scenario, inputs → wrong outcome:

1. User submits a crypto CSV with `metadata.asset_class = "crypto"`, `category_id = <uuid>`,
   description, markets, aum.
2. The fold RPC **commits** (strategy + verification + dailies, one transaction). The connection
   then dies, or the lambda is killed, before `applyCsvMetadataUpdate` runs at `:1923`. This is
   exactly A3's CLASS 2 (`{error:{code:""}, status:0}`, POST never retried) and CLASS 3 (2xx with
   a lost id). The route answers 500 with the new commit-agnostic copy: *"…submit the same file
   again — an unchanged resubmit from this wizard resolves to the strategy you already started…"*
3. The user follows that instruction. Identical name, identical series.
4. 23505 → `resolveExistingStrategyOrRefuse` → status matches, name matches, count and boundaries
   match → **echo**, `fresh: false`, HTTP 200.
5. `:1923` now **skips the metadata UPDATE**. `:1938` **still enqueues** `compute_analytics_from_csv`.

Resulting committed state:
- `strategies.category_id = NULL` — the route's own WR-04 docblock (`:344-352`) states this
  "leaves the strategy invisible to discovery".
- `description`, `markets`, `strategy_types`, `subtypes`, `supported_exchanges`, `aum`,
  `max_capacity` — all absent.
- `strategies.asset_class` = the column default **`'traditional'`**
  (`20260709130000_strategies_asset_class.sql:26` — `NOT NULL DEFAULT 'traditional'`), not the
  user's `'crypto'`.
- The enqueue at `:1938` then actually runs the compute:
  `services/analytics_runner.py:1214,1399-1400` reads `strategies.asset_class` and calls
  `periods_per_year_for_asset_class(...)`, which returns **252** for anything that is not the
  literal `"crypto"` (`services/metrics.py:45`). So every persisted Sharpe / Sortino / Calmar /
  CAGR on a crypto track record is annualized on √252 and published as a "Verified" factsheet.
- The user is told **200 / "An earlier attempt in this wizard session had already saved this
  strategy, so nothing new was written."** Nothing anywhere says the classification was dropped.
- There is no repair surface: `asset_class` is written by the wizard only (grep over `src/app`
  finds no post-creation editor), so the wrong clock is permanent absent an operator UPDATE.

Before A4 the echo re-applied metadata, which **healed** exactly this case. A4 removed the heal
without adding a substitute. Note the phase already reasoned itself to the right conclusion for
the sibling side effect: the test at
`src/__tests__/csv-finalize-cross-submission-merge.test.ts:1163-1177` keeps the enqueue on the
echo precisely because *"a series-bearing echo whose first attempt lost its enqueue is exactly
the case that needs it"* — the identical argument applies to the metadata, and was not made.

The A4 test suite cannot catch this: every case arms the echo against a row that is assumed
already classified (`arm23505(... status:"pending_review")` + `armCommitted2024()`), and asserts
`updateCalls` is empty. There is no arm for "committed row has default/NULL classification".

**Forward fix** (route-only; no migration):

Extend the resolve arm's existing row read to carry the classification, and make the echo a
FILL, never an OVERWRITE:

```ts
// resolveExistingStrategyOrRefuse — the read already exists at :956-962
const { data: existing, error: refetchErr } = await supabase
  .from("strategies")
  .select("id, name, status, category_id, asset_class")   // + the two A4 cares about
  …

// carry them out on the echo
return { ok: true, strategyId: existingRow.id, status: …, fresh: false,
         committed: { categoryId: existingRow.category_id ?? null,
                      assetClass: existingRow.asset_class ?? null },
         humanMessage: … };
```

then at `:1923`:

```ts
// A4-corrected: an echo may FILL a classification the prior request never
// landed, but may never REWRITE one it did.
const requested = parseCsvMetadata(args.metadataRaw);
const echoNeedsFill =
  !outcome.fresh &&
  outcome.committed.categoryId === null;          // the first request died pre-UPDATE
const echoConflicts =
  !outcome.fresh &&
  outcome.committed.categoryId !== null &&
  requested.ok && requested.payload?.asset_class !== undefined &&
  requested.payload.asset_class !== outcome.committed.assetClass;

if (echoConflicts) return refuseResponse(...);      // a changed clock IS a changed submission
const metaErrResponse = (outcome.fresh || echoNeedsFill)
  ? await applyCsvMetadataUpdate(supabase, outcome.strategyId, args.userId,
                                 args.metadataRaw, { correlationId: args.correlationId })
  : null;
```

Add a regression arm to `csv-finalize-cross-submission-merge.test.ts`: echo against a committed
row with `category_id: null, asset_class: 'traditional'` and a request carrying
`asset_class: 'crypto'` → assert `updateCalls` has length 1 and carries `asset_class: 'crypto'`.
Neuter check: revert the `echoNeedsFill` clause and that arm must go RED.

If the fill-vs-refuse split is judged too much for a follow-up, the strictly-safer interim is to
re-enable the UPDATE on echoes **and** keep A4's protection by refusing (409, existing
`CSV_SESSION_REUSED`) when the requested `asset_class` differs from the committed one — that is
A2's own logic applied to the second identity field.

### WR-01: C1's honest copy is never shown to a user — the only consumer discards `human_message` on a 200

**Files:**
- `src/app/api/strategies/csv-finalize/route.ts:1173-1178` (the message), `:1958-1960` (envelope)
- `src/app/(dashboard)/strategies/new/wizard/steps/CsvSubmitStep.tsx:428`

**Issue.** C1 was a founder call: option (b), ship honest copy admitting the echo compared only
row count and boundary dates. The route now emits that sentence on the 200 echo. `CsvSubmitStep`
— the sole caller of this endpoint — reads `human_message` **only inside the `!res.ok` branch**
(`:332-333`). On any ok response it falls through to `onSubmitted(data.strategy_id)` at `:428` and
navigates away. The string is parsed and dropped.

So the user-visible behaviour after C1 is byte-identical to before it: an undifferentiated
success for an echo that did not verify interior values. The residual C1 documents as "accepted"
is accepted *without the mitigation that made accepting it defensible*. No gate asserts the
message reaches a rendered surface — the route tests assert it is in the JSON, which it is.

**Forward fix.** Either (a) render it — carry `human_message` through `onSubmitted` into the
post-submit / SyncPreview surface as an informational (not error) note, and add a component test
that a 200 body carrying `human_message` renders that text; or (b) if rendering is not wanted,
record in TODOS.md that C1 shipped a server-side-only statement with no user surface, so the
interior-values residual is not mistaken for mitigated. Do not leave it in the current state,
where the artifact says "honest copy ships" and the product shows nothing.

### WR-02: the RT-3 re-mint persists the RETIRED session id and never persists the newly minted one

**File:** `src/app/(dashboard)/strategies/new/wizard/WizardClient.tsx:595-603`

**Issue.** The burn-clear effect saves `{ wizardSessionId, failedCsvSubmitSig: null }` and *then*
calls `setWizardSessionId(newWizardSessionId())` at `:603`. `wizardSessionId` in that save is the
closure value — the **spent** id. The freshly minted id is not persisted by anything until the
next step-transition save (`:1268` … `:1401`).

Scenario: submit fails → user steps back to `csv_upload` → uploads a *different* file → the mint
effect fires → localStorage now holds `{spent session id, burn: null}` → user reloads (or the tab
is restored) before navigating forward. `deriveWizardResumeOverrides` restores the spent id with
the fence disarmed — the precise state RT-3 exists to prevent. Submitting the new file then hits
23505 on the spent session and the server fence answers 409 `CSV_SESSION_REUSED` ("Start a new
strategy to upload a different file"), a dead end inside the wizard.

This is not a regression (pre-RT-3 the burn was never persisted at all), but RT-3 touched exactly
this code and left the window open, so the fix belongs with it.

**Forward fix.** Mint first, then save the new id together with the cleared burn:

```ts
const nextSessionId = newWizardSessionId();
failedCsvSubmitSigRef.current = null;
void saveWizardState({
  strategyId: "", wizardSessionId: nextSessionId, step,
  source: "csv", strategyName, failedCsvSubmitSig: null,
});
setWizardSessionId(nextSessionId);
```

Regression arm for `WizardClient.csv-burn-persistence.test.tsx`: after a burn + a material series
change, `flushWizardStateSaves()` then `loadWizardState()` must return a `wizardSessionId` that is
NOT the one the failed submit used. Neuter check: restore the old ordering and it goes RED.

### WR-03: the fold now refuses pre-1900 dates that the route validator accepts — a client-fixable input answers 500 "safe to try again"

**Files:**
- `supabase/migrations/20260819130000_csv_finalize_fold_input_guards.sql:350` (`< DATE '1900-01-01'`)
- `src/app/api/strategies/csv-finalize/route.ts:179-239` (`parseDailyReturnsSeries` — no lower bound)

**Issue.** GUARD 9 adds a lower date fence at 1900-01-01. The route's parser has a regex, a
calendar round-trip and an upper (future) fence, but **no lower bound**: `"1899-12-31"` and even
`"0001-01-01"` pass `DAILY_RETURNS_DATE_REGEX`, `new Date(...)` and the `toISOString().slice(0,10)`
round-trip (JS pads years to 4 digits), and are not in the future.

So a payload the route accepts as valid raises 22023 inside the fold → the fold-failure arm →
`outcomeClass = "rolled-back"` → HTTP **500 `CSV_FINALIZE_FAIL`, "Nothing was saved … so it is
safe to try again"**. Retrying the same file fails identically forever, and the user gets no field
error naming the offending row — unlike every other value violation on this path, which is a 400
`CSV_INVALID_FORMAT` with `debug_context: {row, date}`.

Reachability is low (real track records do not carry pre-1900 dates) but the guard divergence is
new in this phase, and A1's own header states the design rule the other fences follow: "the two
must agree or a payload accepted at the route is refused here for a reason no error message would
explain."

**Forward fix.** Mirror the fence at the route boundary, next to the future-date check:

```ts
const MIN_DATE = "1900-01-01";
if (r.date < MIN_DATE) {
  return { ok: false, code: "CSV_INVALID_FORMAT",
    message: `daily_returns_series[${i}].date is before ${MIN_DATE}: ${r.date}.`,
    debug_context: { row: i, date: r.date } };
}
```

(Lexicographic comparison is correct for the already-validated `YYYY-MM-DD` shape, same
justification the resolve arm's min/max scan uses at `route.ts:1101-1104`.) Add a 400 case to
`csv-validate-route.test.ts` alongside the existing future-date case.
