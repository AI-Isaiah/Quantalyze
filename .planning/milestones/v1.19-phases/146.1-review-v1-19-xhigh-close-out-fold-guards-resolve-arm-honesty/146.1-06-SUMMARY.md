## 2. `credentialHeaderValues()` — read at `resilient-fetch.ts` and confirmed DERIVED

The plan required confirming, before removing the caller-declared array, that the core's class fix
did not depend on it. **Confirmed by reading the function body**, not by inference:

```ts
function credentialHeaderValues(init: RequestInit | undefined): string[] {
  const values: string[] = [];
  try {
    const headers = init?.headers;
    if (!headers) return values;
    const push = (name: string, value: unknown) => {
      if (typeof value === "string" && value.length > 0 &&
          CREDENTIAL_HEADER_NAMES.includes(name.toLowerCase())) {
        values.push(value);
      }
    };
    // …Headers | [string,string][] | Record<string,string>, all three shapes
```

Its **only** input is `init.headers` — the headers the core was actually asked to send — matched
against the module-level `CREDENTIAL_HEADER_NAMES`. It takes **no caller-declared secrets argument
at all**. Removing `args.userAccessToken` from `process-key-client` therefore cannot re-open the
core's leak. The call site is `scrubSeamError(err, credentialHeaderValues(requestInit))`
(`resilient-fetch.ts`, transport catch), unchanged by this plan.

This is also exactly why the header NAME stays in `CREDENTIAL_HEADER_NAMES` with no current
emitter: an emitter-less entry costs one array member and covers the next one automatically.

## 4. ⭐ UNPLANNED FINDING — a LIVE pre-existing credential leak at the client's log site

**Not in the plan. Found by execution, not by reading.** Deviation Rule 1 + 2.

When the two `ECONNREFUSED` scrub fixtures were re-pointed from the (now absent) JWT to
`X-Tenant-Claim`, they went RED — and the failure text showed the two log sites disagreeing:

```
+ [resilient-fetch] process-key-enqueue: network failure reaching the analytics service:
    Error: connect ECONNREFUSED … "X-Tenant-Claim":"<redacted>"
+ [keys/sync] /process-key upstream fetch threw: connect ECONNREFUSED …
    "X-Tenant-Claim":"00000000-0000-0000-0000-aaaaaaaaaaaa.1787060441.511262af9000ade4…"
```

The **core** redacted the claim; the **client** shipped it verbatim.

**Root cause, and it PREDATES this plan.** At HEAD the client called
`scrubSeamError(message, [args.userAccessToken])` — a caller-DECLARED list of one. `X-Tenant-Claim`
is the signed HMAC that **SELECTS the rate-limit bucket** (so documented in
`CREDENTIAL_HEADER_NAMES`), it is computed per request, and therefore no `SEAM_SECRET_ENV_NAMES`
member can reach it. So on **every** seam transport failure — both before and after B2 — that claim
went to the Vercel log in the clear. `git show HEAD:src/lib/process-key-client.ts` confirms the
declared array; this plan did not introduce it.

**Fix, at the root rather than by adding a second literal (Rule 6).** `credentialHeaderValues` is now
`export`ed from `resilient-fetch.ts`; the client hoists its outgoing headers into a named
`outgoingHeaders` const and calls
`scrubSeamError(message, credentialHeaderValues({ headers: outgoingHeaders }))`. Both seam log sites
now share **one** definition of "which outgoing headers are credentials". The scrub was **not**
weakened anywhere: no `scrubSeamError` call was deleted, and `CREDENTIAL_HEADER_NAMES` still contains
`x-user-access-token`.

## 6. ⚠️ Two comment-blind / regex-blind `<verify>` greps in this plan (measured, not deleted)

The prompt warned that four `<verify>` greps in this phase have already failed by matching prose.
**Two more did.** Neither was "fixed" by deleting honest prose.

**(a) Task 1's option grep is comment-blind, twice over.** The plan wrote:

```bash
grep -rn 'userAccessToken' <3 files> | grep -v '^\s*\*' | grep . && fail "the option or a caller survives"
```

`grep -rn` prefixes every output line with `<filename>:<lineno>:`, so `^\s*\*` can never match any
line of that output — the filter is a **no-op**. And `//` comments were never covered even in
principle. The B2 provenance comments (which are load-bearing: they are what stops a future author
re-adding the forward) would fail this grep forever.

**Measured the intent instead** with a comment-stripped scan (`verify-146.1-06.sh`, block-comment
and line-comment aware, line numbers preserved): **zero executable `userAccessToken` references** in
all three files. The honest prose stays.

**(b) Task 3's amendment loop has a REGEX false-PASS.** The loop is:

```bash
for f in $(git grep -l -- 'authenticated flow' .planning/); do grep -q '146.1' "$f" || echo "UNAMENDED: $f"; done
```

`146.1` is a regex, and `.` matches any character. `140.2-RESEARCH.md` contains
`permissions/route.ts:146,152` at `:577`, which matches `146.1` — so that file **passed the loop
while carrying the obligation unamended at `:1212`**. Found by inspecting the one file the loop did
not flag rather than trusting it. It is amended anyway (row 8 in §3). A correct check would be
`grep -qF '146.1'`.

**(c) The loop is also scope-blind**: it only walks `.planning/`, so it structurally cannot see the
two most consequential instances — `analytics-service/routers/process_key.py` (rows 13) and
`.planning/research/PITFALLS.md` (row 14, outside the `phases/` tree the plan enumerated). Both were
found by the repo-wide grep the plan's *action* text demanded, and `verify-146.1-06.sh` now asserts
