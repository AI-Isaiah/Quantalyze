technology, no new dependency, and no design question that the repo does not already answer
somewhere. What the phase actually needs is (a) precise NULL-safety and re-base discipline on

   that keeps both gates GREEN and is strictly more honest — key on the terminalizer's own

### 1.2 Exactly which guards are non-NULL-safe — MEASURED

I ran the fold's guard expressions against a throwaway `postgres:16-alpine` container
`[VERIFIED: docker probe, this session]`:

```
p_rows := NULL::jsonb ; p_fmt := 'daily_returns'
  IF jsonb_typeof(p_rows) <> 'array'      → typeof guard DID NOT FIRE
  IF jsonb_array_length(p_rows) > 5000    → cap DID NOT FIRE
  IF jsonb_array_length(p_rows) > 0       → dailies INSERT SKIPPED
p_fmt := NULL::text
  IF p_fmt NOT IN ('daily_returns','daily_nav','trades') → DID NOT FIRE
  IF p_fmt <> 'trades'                    → DID NOT FIRE
  IF p_fmt IS DISTINCT FROM 'trades'      → FIRED
jsonb_typeof(NULL::jsonb)                 → <NULL>
```

**Mechanism:** `jsonb_typeof` is STRICT, so `jsonb_typeof(NULL)` is NULL; `NULL <> 'array'` is
NULL; and plpgsql `IF NULL THEN` takes the ELSE branch. Same for `jsonb_array_length(NULL)`.

⇒ **With `p_rows := NULL` every rows-related guard is bypassed and the dailies INSERT is
skipped — the function commits a strategy + verification row with ZERO dailies and returns a
UUID.** This is A1's core claim and it is **confirmed**.

⇒ **`p_fmt := NULL` bypasses the fmt whitelist too.** This matters for the fix: a naive
`p_fmt <> 'trades'` scoping is *itself* NULL-unsafe. **Use `p_fmt IS DISTINCT FROM 'trades'`.**

**Guards that are already NULL-safe (do not "fix" them):**
- `p_strategy_name IS NULL OR length(p_strategy_name) = 0` — explicit (`:262`).
- `p_user_id` NULL → `v_auth_uid <> p_user_id` is NULL → passes the guard, but the strategies
  INSERT then violates `user_id UUID NOT NULL` `[VERIFIED: 20260405061911_initial_schema.sql:49]`
  → 23502, whole transaction rolls back. **Safe by table constraint, not by guard.** Worth a
  comment, not a raise.
- `p_terminal_status` NULL → whitelist passes, then `status TEXT NOT NULL`
  `[VERIFIED: 20260405061911_initial_schema.sql:63]` → 23502, rollback. **Safe by table
  constraint.**

### 1.3 STRICT vs explicit raises — recommendation

**Do NOT make the function `STRICT` (`RETURNS NULL ON NULL INPUT`).** Two reasons, both decisive:

1. A `STRICT` function **returns NULL silently** on any NULL argument. The route's success check
   is `if (!error && isUuid(newStrategyId))` (`route.ts:574`) — a NULL return with no error is
   the **TS-13 lost-id arm**, which routes into the same "Nothing was saved" 500 that A3 exists
   to fix. Trading a silent zero-dailies commit for a silent NULL return is a lateral move.
2. `p_terminal_status TEXT DEFAULT 'pending_review'` means the 6th argument is *routinely*
   omitted by no caller today but is a supported shape; `STRICT` interacts with defaults in a
   way that is easy to get wrong and impossible to test from the route.

**Recommendation: explicit `RAISE ... USING ERRCODE = '22023'` per argument**, in the fold's
existing sibling style. The ERRCODE is **22023** (`invalid_parameter_value`) — the fold already
uses it for all five input-shape guards `[VERIFIED: 20260819120000:224, 253, 264, 269, 274, 278]`
and it is the canonical value in the migration's own ERRCODE map at `:110-114`.

**Exact RAISE wording style used by siblings** (copy this shape byte-for-byte):

```sql
RAISE EXCEPTION 'finalize_csv_strategy_with_returns: p_rows is required (received NULL)'
  USING ERRCODE = '22023';
```

Sibling evidence, verbatim `[VERIFIED: supabase/schema/functions/finalize_csv_strategy_with_returns.sql:63-86]`:

```
'finalize_csv_strategy_with_returns: p_strategy_name is required'
'finalize_csv_strategy_with_returns: p_strategy_name exceeds 80 characters'
'finalize_csv_strategy_with_returns: p_rows must be a JSONB array, got %'
'finalize_csv_strategy_with_returns: p_rows exceeds 5000 rows (got %)'
'finalize_csv_strategy_with_returns: invalid fmt %'
```

Pattern: `<function name>: <subject> <verb phrase>`, one distinguishing substring per guard so a
gate can pin each separately (the migration says so explicitly at `:259-261`).

### 1.4 Scoping the empty-array allowance to `p_fmt='trades'` without breaking anything

**The route's legacy-client arm is NOT at risk.** `[VERIFIED: route.ts:1337-1352]` — the route
already refuses the exact combination:

```ts
if (
  (fmt === "daily_returns" || fmt === "daily_nav") &&
  dailyReturnsSeries.length === 0
) { ... 400 CSV_INVALID_FORMAT ... }
```

and `parseDailyReturnsSeries` maps `undefined`/`null` → `{ok: true, rows: []}` at `route.ts:144-146`,
so the legacy-client shape lands in that 400, not in the fold. **The `[]` + `daily_returns` arm
is therefore reachable ONLY by an authenticated direct-RPC caller**, and `auth.uid() = p_user_id`
confines the damage to that caller's own tenant. ⇒ **This is a CONTEXT correction; see the
Assumptions Log and §9.**

The `[]` + `trades` case **must keep working** — it is pinned by
`supabase/tests/test_csv_finalize_atomic_fold.sql` **Part 4** (`:248-290`), whose message reads
*"the trades-empty finalize returned NULL"* / *"the fold fabricated rows the user never
submitted"*. Any A1 change that 22023s an empty trades payload reds that gate.

**Recommended guard, NULL-safe on both arguments:**

```sql
IF p_rows IS NULL THEN
  RAISE EXCEPTION 'finalize_csv_strategy_with_returns: p_rows is required (received NULL)'
    USING ERRCODE = '22023';
END IF;
...
IF jsonb_array_length(p_rows) = 0 AND p_fmt IS DISTINCT FROM 'trades' THEN
  RAISE EXCEPTION 'finalize_csv_strategy_with_returns: p_rows is empty and fmt is % (an empty series is only legitimate for fmt=trades)', p_fmt
    USING ERRCODE = '22023';
END IF;
```

⚠️ **Ordering matters.** The `p_rows IS NULL` raise must sit BEFORE `jsonb_typeof(p_rows)` (so the
NULL case gets its own distinguishing message rather than falling into the typeof guard's
`got <NULL>` arm), and the empty+fmt raise must sit AFTER the fmt whitelist (so a bogus fmt gets
`invalid fmt` and not the empty-rows message). Also note the fmt whitelist itself is NULL-blind
(§1.2) — either add `p_fmt IS NULL` to that raise or accept that a NULL fmt now falls into the
empty-rows raise. **Recommend making the fmt guard explicit too:** `IF p_fmt IS NULL OR p_fmt NOT IN (...)`.

### 1.5 Value guards (absorbs TODOS "Fold value guards" + "fmt-blind empty-rows")

**The route's mirror values, read verbatim from source** `[VERIFIED: route.ts:183-232]`:
- `typeof r.daily_return !== "number" || !Number.isFinite(r.daily_return)` → 400 (`:183`)

**Recommended SQL mirror — ONE `EXISTS` scan, evaluated BEFORE the INSERT.** Verified predicate
behaviour `[VERIFIED: docker probe]`:

```
('NaN'::float8      BETWEEN -1e6 AND 1e6)  → false
('Infinity'::float8 BETWEEN -1e6 AND 1e6)  → false
NOT ('NaN'::float8  BETWEEN -1e6 AND 1e6)  → true
```

⇒ `NOT (x BETWEEN -10 AND 10)` catches **NaN, +Infinity, −Infinity and out-of-magnitude in a
single predicate**. ⚠️ It does **not** catch a NULL `daily_return` (an absent key) — `NOT (NULL
BETWEEN ...)` is NULL, so the `EXISTS` misses it. Guard that separately, or rely on
`csv_daily_returns.daily_return DOUBLE PRECISION NOT NULL`
`[VERIFIED: supabase/migrations/20260522111839_csv_daily_returns.sql:39]` which 23502s and rolls
back — safe but with a less legible SQLSTATE. **Recommend the explicit `IS NULL` arm** so the
error is 22023 like its siblings.

Also mirror the **duplicate-date** check (`SELECT count(*) <> count(DISTINCT (elem->>'date'))`).
This is not merely tidiness: it makes B3's "second 23505 source" **unreachable from the fold's
own INSERT**, which the fold's docblock at `route.ts:640-646` currently only *hopes* is true.
B3's constraint-name fence still ships (defense in depth against any future source), but A1
removes the one concrete path.

`CURRENT_DATE` is server-timezone-dependent; to mirror the route's **UTC** today, use
`(now() AT TIME ZONE 'UTC')::date`. `[CITED: PostgreSQL date/time functions]`

### 5.2 A4 — the fresh-vs-echoed discriminator

**The type, verbatim** `[VERIFIED: route.ts:534-536]`:

```ts
type FinalizeAtomicOutcome =
  | { ok: true; strategyId: string; status: string }
  | { ok: false; response: NextResponse };
```

**Recommended change:**
```ts
type FinalizeAtomicOutcome =
  | { ok: true; strategyId: string; status: string; fresh: boolean }
  | { ok: false; response: NextResponse };
```
- `fresh: true` at the create return (`route.ts:575`)
- `fresh: false` at the resolve echo return (`route.ts:871-876`)

⚠️ **Make it a required field, not optional.** A `fresh?: boolean` lets a future third return site
default to `undefined` → falsy → silently treated as an echo. Required forces the compiler to
name every construction site.

**Where the guards move** (both handlers, identically — see §7 on C2):

1. **`applyCsvMetadataUpdate`** (`route.ts:1512-1519` manager, `:1611-1618` contribution) — the
   defect. On an echo it runs THIS request's metadata against the **pre-existing committed row**.
   `buildMetadataUpdatePayload` copies `asset_class` verbatim when present
   `[VERIFIED: route.ts:505-507]`, and the docblock right above it (`:498-504`) states the
   downstream consequence: *"An absent field stays absent → column default null → 252 downstream."*
   ⇒ a same-series retry with a flipped `asset_class` rewrites the strategy's annualization clock
   (√252 vs √365) while the stored KPIs keep the OLD one. **This is the money-math half of A4 and
   it is real.**
   **Recommend: skip the metadata UPDATE entirely on `!fresh`.** The echo is by definition the
   *same* submission; honouring its metadata is honouring a mutation the user did not ask for on a
   row they already committed. Simpler and safer than "re-enqueue after".
2. **`enqueueCsvAnalyticsAfter`** (`:1526-1531`, `:1622-1627`) — currently gated on
   `args.dailyReturnsSeries.length > 0`. On an echo with a non-empty series, re-enqueueing is
   harmless-to-good (the sweep would do it anyway), so **leave it**. ⚠️ For `fmt='trades'` the
   series is empty on BOTH the fresh and the echo path, so no enqueue ever happens — that is
   pre-existing behaviour documented at `route.ts:1334-1337`, **not** an A4 regression. Do not
   "fix" it inside A4.

⚠️ If the planner instead chooses "re-enqueue after the metadata UPDATE", note that the enqueue is
`after()`-scheduled and non-blocking, so ordering between it and the UPDATE is **not** guaranteed —
which is why *skip* is the recommendation.

## Common Pitfalls

### Pitfall 1 — "The guard is there, so it holds"
`jsonb_typeof(NULL) <> 'array'` LOOKS like a guard and is not one. **Every** three-valued-logic
comparison against a possibly-NULL argument in plpgsql is a no-op guard. **Detection:** run the
predicate against NULL in a throwaway Postgres before believing it, as §1.2 did. **Prevention:**
`IS DISTINCT FROM` / explicit `IS NULL` arms.

### Pitfall 2 — Substring gates that cannot fail
This repo has already been bitten three times: `%5000%` matching `50000`; `LIMIT 25` matching
`LIMIT 2500`; a bare `%public.compute_jobs%` satisfied by the INSERT target alone
`[VERIFIED: 20260816140000:713-726, 866-878; 20260819120000:452-461]`. **Every new anchor in this
phase must be word-bounded or occurrence-counted, over a COMMENT-STRIPPED body.**

### Pitfall 3 — Re-basing on the wrong parent
Discharged here (§1.1: exactly one migration defines the fold). But the pattern that made this a
house rule — `20260728120000:186-195` — applies to any future re-base. **Always grep ALL
migrations first; never re-base on the file you happen to have open.**

### Pitfall 4 — Testing the helper instead of the wiring
An A4 test that asserts `fresh === false` on the resolve return proves nothing about whether the
metadata UPDATE is skipped. **The oracle must be "was the UPDATE issued?"**, driven through the
real handler.

### Pitfall 5 — Falsifying only in the safe direction
A widened-bound neuter for A1's value guard false-PASSES on NaN (NaN fails any `BETWEEN`). **Two
probes required** — one NaN, one large-finite. Same class as the `%5000%` failure.

### Pitfall 6 — Editing an applied migration's prose because it is now false
`20260819120000`'s 23505 attribution becomes false the moment B3 lands. It **must not be edited**.
The correction rides in the A1 migration's superseding `COMMENT ON FUNCTION`.
