## What changed

### B3 — enter the resolve arm only for a wizard-session fence (`534f0da5`)

The 23505 branch now computes `pgConstraintName(error)` once and enters
`resolveExistingStrategyOrRefuse` **iff** the result is `null` or a member of
`WIZARD_SESSION_CONSTRAINTS`. A `csv_daily_returns_strategy_date_key` violation
falls through to the fold-failure arm instead of being offered the resolve arm's
retryable 503 — a "try again shortly" for a payload defect that fails identically
forever.

`null` deliberately KEEPS entering the arm. The leaf's contract says `null` means
the name was UNPARSEABLE, not that no constraint was violated; the resolve arm
already fails closed, so a mis-routed 23505 answers 503 rather than fabricating an
echo. Tightening it to `constraint !== null && …` would convert a fail-closed 503
into a fail-open 500 with the wrong copy. That reason is written into the code.

A named-but-unrecognised constraint is fail-loud before falling through:
`console.error` with `scrubSeamError` plus a Sentry capture under the grep-unique
step tag `finalize-23505-unknown-constraint`, carrying `pg_code` and `constraint`.
`error.details` is read nowhere (verified by grep) — it carries client-supplied key
values and reading it would let a caller steer which arm answers them.

The CR-01 docblock previously called the dailies 23505 hypothetical ("in
principle"). It is not, and the docblock now says so and cites the migration.

### A2 — refuse a terminal-status mismatch (`04c074fb`)

`resolveExistingStrategyOrRefuse`'s `args` parameter type gained
`terminalStatus: "pending_review" | "private"`. **That one line was the actual
gate**: structural typing had let the caller pass the field while the function
could not see it, so there was nothing to compare against.

The comparison sits after the no-row fail-closed arm and before the name check,
guarded by `typeof existingRow.status === "string" &&` so an absent column is not
read as an observed mismatch. It refuses through the existing `refuse()` closure —
409 / `CSV_SESSION_REUSED` / `NO_STORE_HEADERS` / one `finalize-resolve-refused`
capture. Zero new error codes.

The real-world break this closes: `status` is not in the partial unique index the
23505 fires on, and `wizard_session_id` is restored unconditionally from one shared
localStorage key, so a manager-flow resubmit could resolve onto a row committed
`private` and be echoed 200 — a strategy the user is told was saved that never
enters the admin review queue — and in the other direction an owner-only
contribution's id reached the manager flow.

### C1 — honest echo copy (`f1165555`)

**Founder call: option (b) shipped. No hash, checksum or column exists in the diff.**

The 200 resolve echo now carries `human_message` naming its two reads (row count,
first and last dates) and stating that the individual daily values were not
compared. It rides the resolve echo ONLY — a fresh create's envelope is byte
identical to before, which is itself a discrimination: a caller can tell a save
from an echo.

A dated provenance comment records the removed claim verbatim ("this IS the
instructed retry of the same submission … presence is proven, not assumed"), why
two boundary reads cannot support it, which option was taken, and the pointer to
TODOS.md.

Behaviour is unchanged. Equal count and boundaries with different interior values
still echoes 200; every refusal threshold is untouched.

### C4 — fail-closed pins (`04c074fb`)

Both paths already existed and neither was asserted. Three cases now pin them to
503 `CSV_PERSIST_FAIL` **and** `updateCalls` empty: a failed `refetchErr`, a
re-fetch that finds no row, and a row whose id is not a UUID. Asserting only the
status code would miss a fail-closed path that still issued a metadata UPDATE.

### 4. [Scope judgement] C1's copy required a new envelope field

The plan says *"the copy is the envelope's own message field"*, but the 200 success
envelope carried **no prose at all** — only `{ok, strategy_id, status,
correlation_id}`. An absence assertion against an empty envelope is vacuous, and
the C1 truth (*"The 200 echo response … states what was actually compared"*)
is unsatisfiable without prose. I added `human_message` to the **resolve echo only**
(via an optional `humanMessage` on `FinalizeAtomicOutcome`), leaving fresh-create
envelopes unchanged. Safe for consumers: `CsvSubmitStep` branches on `!res.ok` /
`data.ok`, never on the presence of `human_message`, and the vocabulary invariant
derives `code: "…"` properties only — it does not move.

## Known residual (NOT closed, and not closable by A2)

When a resolved row's `status` column comes back **absent**, A2 correctly does not
refuse (absence is not a value), and the echo then falls back to
`existingRow.status ?? "pending_review"`. For a *contribution* request that fallback
reports `pending_review` while the request asked for `private`. The database row is
untouched — the resolve arm writes nothing, so the strategy does not actually enter
the review queue — but the **response misreports**. Refusing instead would violate
the absence rule that F-04-4 pins. Left open deliberately; the honest fix is to
echo `null`/omit the field when the status was not read, which is a contract change
for `CsvSubmitStep` and belongs in its own item.

## Threat Flags

None. No new network endpoint, auth path, file access pattern or schema change.
The `human_message` field carries no row data, no ids and no user input — it is a
fixed sentence. The Sentry `constraint` extra comes from Postgres `message`, which
is composed from catalog names only.
