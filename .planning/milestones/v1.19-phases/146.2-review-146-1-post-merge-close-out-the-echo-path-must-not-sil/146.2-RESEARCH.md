## R1 — the resolve/echo arm (BLOCKER)

### 1a. What the resolve arm's `.select()` returns today, and what extending it costs

`[VERIFIED: src/app/api/strategies/csv-finalize/route.ts:956-968]` — the re-fetch:

```ts

  .from("strategies")
  .select("id, name, status")
  .eq("user_id", args.userId)
  .eq("wizard_session_id", args.wizardSessionId)
  .eq("source", "csv")
  .maybeSingle();
...
const existingRow = existing as {
  id?: string;
  name?: string;
  status?: string;
} | null;
```

Cost of adding `category_id, asset_class`:
- The string select becomes `"id, name, status, category_id, asset_class"`; the cast type gains `category_id?: string | null; asset_class?: string;`. RLS: the owner-scoped user client already reads its own `strategies` row — no policy change (the same client's `applyCsvMetadataUpdate` already UPDATEs these columns under `strategies_update` RLS, `[VERIFIED: route.ts:1455-1459]`).
- **Test-fixture ripple (the real cost):** `src/__tests__/csv-finalize-c14-regression.test.ts:400-403` mocks the row as `{ id, name, status }` only, and `src/__tests__/csv-finalize-cross-submission-merge.test.ts` `arm23505({ id: EXISTING_ID, name: "Alpha", status: "pending_review" })` (used at `:1116,:1139,:1167`) does the same. Every fixture must declare `category_id`/`asset_class` explicitly once the arm reads them — an absent field must be handled as an **absent reading** (see 1b), so un-updated fixtures degrade to no-op, not to a spurious FILL.

### 1b. A2's existing identity-conflict mechanism — reuse it, don't parallel it

`[VERIFIED: route.ts:1042-1048]` — the A2 terminal-status check, the exact mechanism to extend:

```ts
if (
  typeof existingRow.status === "string" &&
  existingRow.status !== args.terminalStatus
) {
  return refuse(
    `terminal status mismatch (committed '${existingRow.status}', this submission asked for '${args.terminalStatus}')`,
  );
}
```

Three properties to preserve verbatim on the new field:
1. **`typeof === "string" &&` absence guard** — "a row whose `status` did not come back is an ABSENT reading, not an observed mismatch. Refusing on absence would render a read we could not make as a measurement" `[VERIFIED: route.ts:1032-1035, comment]`.
2. **Refusal goes through the existing `refuse()`** — 409 / `CSV_SESSION_REUSED` / no-store / one Sentry capture (`step: "finalize-resolve-refused"`, `[VERIFIED: route.ts:987-996]`). The docblock's own reasoning: "A new code would move KNOWN_CSV_FINALIZE_CODES, EXPECTED_TABLE_SIZE and the vocabulary invariant in the same commit, for a state the user cannot act on differently" `[VERIFIED: route.ts:1037-1041]`. ROADMAP SC#1 locks this.
3. **The reason string is specific** — `refuse(reason)` logs and captures the reason; a classification conflict gets its own reason string, greppable in ops.

**The discriminator design problem the planner must decide (this is the one genuinely open design point):**
`asset_class` is `NOT NULL DEFAULT 'traditional'` (`[CITED: 20260709130000_strategies_asset_class.sql:26, per CONTEXT — orchestrator-verified]`), so on the committed row "never classified" and "deliberately traditional" are the **same stored value**. `category_id` has no default and the fold's INSERT never writes it, so:

- **`category_id IS NULL` ⇔ the metadata UPDATE never ran on this row** — because `applyCsvMetadataUpdate` issues ONE atomic `.update(updatePayload)` carrying all fields together (`[VERIFIED: route.ts:1455-1459]`), and the wizard always sends `category_id` (WR-04: an explicit `category_id: null` is 400-refused pre-create, `[VERIFIED: route.ts:353-359]`; the wizard body always carries `category_id: metadata.categoryId`, `[VERIFIED: CsvSubmitStep.tsx:270-290]`).

Recommended rule (validate at plan time, it matches the review's FILL/REFUSE proposal):
- `category_id === null` (explicitly returned NULL) → **FILL**: run `applyCsvMetadataUpdate` with THIS request's metadata (the resubmit of the same submission — CsvSubmitStep sends the full metadata blob on every submit).
- `category_id` a string (classified row) → compare `asset_class`: present-and-different from this request's parsed `asset_class` → **REFUSE** via `refuse()`; equal or this-request-absent → no-op echo (unchanged today's behavior).
- Any field an **absent reading** (typeof guard fails) → no FILL, no REFUSE — mirror A2's absence rule.

Residual worth recording in the plan (not closing): a non-wizard direct caller that sent `asset_class` without `category_id` on attempt 1 would be re-FILLable on a retry. Only reachable off-wizard; the wizard cannot produce it.

## R3 — B4 readmit ceiling

### The attempt signal ALREADY EXISTS — no DDL

Two facts compose:
1. The terminalizer **UPDATEs the running row in place** to a persistent marker row — `[VERIFIED: supabase/migrations/20260817120000_retention_orphaned_running_terminalize.sql:618-622]`:
```sql
UPDATE public.compute_jobs cj
   SET status          = 'failed_final',
       next_attempt_at = now(),
       error_kind      = 'permanent',
       last_error      = 'orphaned_running_reaped: no worker completed this job within the 4h claim window'
```
(rows "survive as failed_final" — the migration's own NOTICE, `:650`).
2. The sweep **INSERTs a NEW row** each readmission — `[VERIFIED: 20260819130500…sql:368-373]` `INSERT INTO public.compute_jobs (strategy_id, kind, metadata) … jsonb_build_object('source','reconcile-sweep',…)`.

⇒ each reap-readmit cycle strictly increments the count of marker rows for that strategy. **The per-strategy count of `status='failed_final' AND last_error LIKE 'orphaned_running_reaped:%'` rows IS the attempt counter.** (`compute_jobs.attempts`/`max_attempts`/`reclaim_count` exist — `[VERIFIED: src/lib/database.types.ts, compute_jobs Row: "attempts: number … max_attempts: number … reclaim_count: number"]` — but they are per-JOB worker-retry counters reset to defaults on each sweep INSERT; they cannot carry the cross-row cycle count. Do not use them.)

### The fix shape

A new migration re-registering `reconcile_dropped_enqueue_sweep` (the body lives in `cron.job` on PROD — source edits alone change nothing; see Runtime State Inventory) with ONE added conjunct in the batch CTE, e.g.:

```sql
AND (SELECT count(*) FROM public.compute_jobs cj2
      WHERE cj2.strategy_id = s.id
        AND cj2.status = 'failed_final'
        AND cj2.last_error LIKE 'orphaned_running_reaped:%') < 3   -- ceiling; planner picks N
```

- **No table DDL.** But it IS a migration, auto-applied to PROD on merge ⇒ the 146.1-08 orchestrator-only rehearsal/verification pattern applies (TEST rehearsal, PROD post-merge census, one observed cron tick).
- C2/C3 stay satisfied: genuine `failed_final` (non-marker or NULL `last_error`) rows still exclude via the untouched `IS TRUE`-wrapped conjunct; the ceiling only STOPS readmission, never adds it. The refused blanket widening stays refused.
- Transcription discipline: 20260819130500 changed the 20260816140000 body by exactly one clause and preserved whitespace because gates anchor on exact spellings (`[VERIFIED: 20260819130500:290-296, comment]`). The new migration must do the same — one added conjunct, everything else byte-preserved, self-verify block re-issued (comment-stripped, word-bounded `\m…\M` on the count literal so a widening to e.g. 30 cannot pass as a prefix — the house rule the CONTEXT's "Verified sound" list records).
- **Known residual to state, not fix:** `failed_final` rows hit the 90-day retention wall (`[VERIFIED: 20260817120000:260-261, comment: "failed_final rows always hit the 90d wall on schedule"]`), after which the marker count resets and the strategy re-enters the zero-jobs arm ⇒ the loop is bounded at N cycles per ~90 days, not N forever. That is a ceiling, which is what R3 asks for; record it in the migration header.

## Common Pitfalls

### 1. FILL keyed on `asset_class` instead of `category_id`
`asset_class`'s column default makes "unclassified" unobservable on that column alone; keying FILL on it would overwrite deliberate `traditional` rows. Key on `category_id IS NULL` (§1b). **Warning sign:** a test where an echo against a deliberately-traditional classified row gets FILLed to crypto.

### 2. Treating an absent reading as NULL
`existingRow.category_id === null` (explicit NULL from a named-column select) ⇒ FILL; field **absent** (`typeof` guard fails — defective shape) ⇒ no-op. Collapsing the two re-creates the "render a read we could not make as a measurement" defect A2's comment forbids.

### 3. Editing the sweep body in place / free-hand
Gates anchor on exact spellings and TEST/PROD md5s already differ by whitespace (`[VERIFIED: 20260819130500:290-296]`). Transcribe byte-exact, change one clause, re-issue self-verify with word-bounded regexes.

### 4. CI Node 22 vs local Node 25
A vitest pass locally is not a CI pass — `PATH=/opt/homebrew/opt/node@22/bin` reproduces CI (memory: `reference_ci_node22_vs_local_node25`). Use `vi.spyOn` + `restoreAllMocks`, never leaked `vi.stubGlobal`.

### 5. Shared-TEST-DB gate arming
New SQL-gate arms that require the new migrations will red every open PR if the migration applies to TEST before the gates land (or SKIP silently if state-adaptive). Follow the Phase 156 state-adaptive precedent and RECORD that the armed-green run happens post-merge — or land gate+migration in one PR and accept the ordering. Never run python + e2e-seeded suites concurrently against TEST.

### 6. Self-referential oracles on the money path
R1's clock assertions must pin ECONOMICS (crypto ⇒ the √365 clock lands on the row AND a recompute is enqueued), not the implementation's own `fresh` flag. The existing "ECONOMIC ORACLE" test (`cross-submission-merge.test.ts:1133-1152`) is the template.

### 7. `$?` after a pipe
When observing neuters in shell, `$?` after a pipe is tee's status (memory: vacuity mechanisms). Capture vitest/pytest exit codes directly.
