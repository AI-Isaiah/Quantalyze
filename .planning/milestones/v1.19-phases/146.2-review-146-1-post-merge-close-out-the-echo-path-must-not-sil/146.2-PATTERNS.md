## 4. Attempt-ceiling / retry-bound pattern (R3) — repo HAS solved this once

**Analog:** `supabase/migrations/20260411144407_compute_jobs_queue.sql` —
`compute_jobs.max_attempts INTEGER NOT NULL DEFAULT 3` (`:122`) and the ceiling check in

```sql

  FROM compute_jobs WHERE id = p_job_id AND status = 'running' FOR UPDATE;

  v_new_status := 'failed_final'; ...
```

**Match is PARTIAL:** this bounds attempts of ONE job row. R3's cycle spans reap→readmit
cycles where each cycle mints a NEW job row, so a per-row counter cannot see it. However
the sweep's own predicate already counts the evidence: the reaped rows carry the marker
`last_error LIKE 'orphaned_running_reaped:%'` (`20260819130500:337-339`). The natural
conforming bound is a COUNT of marker-bearing `failed_final` rows per strategy in the
readmit predicate (e.g. `HAVING count(*) FILTER (...) < N`) — no exact analog exists for
"count prior terminal rows as the ceiling"; planner decides the N and shape deliberately.
Constraints from the migration's own text (`:98`, `:127`, `:442`): the `IS TRUE` NULL-safety
wrapper must survive, and C2/C3's "no retry loop over a settled failure" gates must stay
green. The `mark_compute_job_failed` ELSE-arm comment (`:738-743`) is the house philosophy:
prefer a conservative terminal state + monitoring signal over a RAISE that wedges the loop.

**Sweep predicate being bounded** (`20260819130500:325-340`):
