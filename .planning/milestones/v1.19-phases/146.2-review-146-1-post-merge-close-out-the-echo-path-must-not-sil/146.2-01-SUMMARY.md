## The ratified discriminator, and why it is not `asset_class`

FILL keys **exclusively** on `category_id IS NULL`. Verified at HEAD:

- `strategies.asset_class` is `NOT NULL DEFAULT 'traditional'` (`20260709130000_strategies_asset_class.sql:26-27`). On that column, "never classified" and "the user chose traditional" are the **same stored value** — so filling on `asset_class='traditional'` would overwrite a legitimate user choice, which is precisely what the economic oracle forbids.
- `category_id` has no default, the fold's INSERT never writes it, `applyCsvMetadataUpdate` writes both fields in ONE atomic UPDATE (`route.ts:1455-1459`), and the wizard always sends a `category_id` (an explicit null is 400-refused pre-create, `route.ts:353-359`).

⇒ A committed `category_id` of SQL NULL is observable proof the metadata UPDATE never ran. On the FILL arm the committed `asset_class` **will** read `'traditional'`; that is a default, not a conflict, and the code carries a comment forbidding an `asset_class`-present pre-check that would block the fill.

`undefined` (the column did not come back) is treated as an ABSENT reading throughout and licenses neither a fill nor a refusal — the same discipline as A2's `typeof === "string" &&` guard.

## FILL-safety, re-grounded (the pre-revision premise was REFUTED)

The 146.2 plan-check refuted the earlier claim that a trades strategy structurally cannot carry stored KPIs. That claim is false and is **not** relied on anywhere in this implementation, these tests, or this SUMMARY. What is true, and what the fix rests on:

1. **The route itself writes `strategy_analytics` rows with no job success.** `writeFailedStrategyAnalyticsPlaceholder` (`route.ts:1229-1305`, upsert `:1280-1293`) stamps `computation_status='failed'` placeholders. Measured on PROD 2026-08-19 (read-only): 18 of 22 csv strategies have zero dailies; **all 18 carry an analytics row**, and **7 carry non-null `sharpe` AND `cagr`** (all `computation_status='failed'`, computed 2026-05-27 under pre-A4 code).
2. **Those KPIs are surfaced** — per-surface, not systemically: `StrategyTable.tsx:1091` renders `analytics.sharpe` with no `computation_status` gate, and `getPercentiles` selects the KPI columns without that column at all, folding every published row into percentile ranks.
3. **Under current code, no KPI-VALUE writer runs without a completed compute job.** The finalize enqueue is gated on `dailyReturnsSeries.length > 0` (`route.ts:1938`); the only other enqueuer, the reconcile sweep, carries a dailies-existence conjunct whose self-verify RAISEs if the body stops reading `csv_daily_returns`; and the placeholder writer writes status/error/flags but **no KPI columns**.

⇒ Stored KPIs on a zero-dailies row are a **historical, per-row MEASURABLE fact** — not a structural impossibility. So the guard measures, per request, and never assumes. The historical failed-with-KPIs class is excluded by REFUSE.

The two arms are clock-safe in different ways:

- **Series-bearing echo → unconditional FILL.** The enqueue at `:1938` fires after the AWAITED update, so the stored KPIs recompute under the filled clock. Ordering is load-bearing and is now commented as such.
- **Empty-series echo → the clock-safety guard.** No recompute will fire, so the arm measures instead. On REFUSE it writes **nothing** — not even `category_id`, because a partial fill would promote a discovery-invisible row into the listing join and make KPIs computed under a different clock reachable in browse and in percentile ranks. Half-applying a classification is also the exact silent partial drop this phase exists to stop.

Governing principle, unchanged and extended: never change the annualization clock without guaranteeing the recompute that reconciles it — and never promote a row into a ranking surface whose stored KPIs were computed under a different clock.

**No backfill.** PROD re-measured at plan time: `suspect_and_visible = 0`, zero csv strategies created since A4. Forward fix only.

## Decisions Made

- **`refuse()` gained an optional second parameter** rather than a new error code. The vocabulary is closed (`route.ts:1037-1041`): a new code moves `KNOWN_CSV_FINALIZE_CODES`, `EXPECTED_TABLE_SIZE` and the vocabulary invariant in one commit, for a state the user cannot act on differently.
- **`fillClassification` is OPTIONAL on `FinalizeAtomicOutcome`, the opposite call from `fresh`.** `fresh` is required because omitting it defaults falsy ⇒ "treat as an echo" ⇒ skip a write the create needs. Omitting `fillClassification` defaults falsy ⇒ no write at all ⇒ the status quo ante. A future return site that forgets it can only decline a write, never cause one. Documented at the declaration.
- **The classification is threaded from the pre-create parse** (`route.ts:1679`) through `unifiedCsvFinalizeHandler` as two explicit values, not re-parsed in the resolve arm. Same reasoning T-19.1-10 gives for `dailyReturnsSeries`: a dependency the type system cannot see is one the next refactor drops. The pinned-signature gates (`csv-validate-route.test.ts` Tests 8b/8c) still pass — the change adds fields to the single typed args object and touches neither the name, the arity, nor the single-object-literal call sites.
- **`CLOCK_SAFETY_KPI_COLUMNS` is duplicated, not imported.** `PERCENTILE_ANALYTICS_COLUMNS` is a non-exported const in the client-reachable `queries.ts`. The duplication is commented with its provenance and the obligation to follow if that set changes.
- **The guard's presence test is `!== null`, not truthiness.** A stored `0` (a real cagr of zero) is a KPI. A column that came back `undefined` — schema drift — counts as PRESENT on purpose: the conservative direction, consistent with "absence of a measurement never licenses moving the clock".
- **The guard-read failure carries the allowlisted SQLSTATE** (`.code`, SEAMRIM-06) inside the synthetic Error's message so the fail-closed 503 is diagnosable in Sentry; nothing else from the read error is carried.

### BL-01 — a swallowed UPDATE failure answered 200 with "…so we applied them to it now"

**The mechanism, as shipped by this plan.** `applyCsvMetadataUpdate` returned
`NextResponse | null`. On `updateError` it did `console.error` +
`captureToSentry(...)` and then **`return null`** — the same value a success
returns. The call site only tested `if (metaErrResponse)`, so a FAILED UPDATE was
indistinguishable from a successful one, and the FILL arm answered **200** carrying
`fillHumanMessage`: *"…so we applied them to it now."*

The reviewer drove it against HEAD by returning `{code:'42501'}` from the merge
suite's UPDATE mock and got:

```
PROBE status= 200 ok= true msg= …so we applied them to it now. …
```

**Why this is worse than the bug it replaced.** The strategy keeps `category_id
NULL` (discovery-invisible) and `asset_class 'traditional'` (sqrt(252)) on a crypto
track record — **and the user has been told it was repaired, so they will not
retry.** There is no post-creation editor for either field anywhere in the product.
R1's original defect at least said nothing; a false receipt closes the one recovery
path the user had.

**The fix.** `applyCsvMetadataUpdate` now REPORTS its outcome instead of
swallowing it:

```
'applied' | 'noop' | 'invalid' (carries the 400) | 'update_failed'
```

⛔ **The failure semantics inside the helper are unchanged** — the same
`console.error` + `captureToSentry` fire on `updateError`, and the FRESH-create
path's long-standing non-fatal handling is untouched (the strategy row already
persisted must not be rolled back over a metadata write). What moved is the
DECISION, out of the helper and up to the call site, so it can differ per arm. Only
the arm this plan introduced answers differently:

- `outcome.fillClassification && kind !== "applied"` → **503 `CSV_PERSIST_FAIL`**,
  copy that states the fact ("that write did not land, so nothing was changed") and
  offers a non-destructive next step. **Refusing costs nothing here**: the strategy
  is already committed, this request wrote nothing, and the resubmit is idempotent —
  the discriminator still reads `category_id IS NULL`, so the next attempt takes the
  same arm and repairs it.
- `!== "applied"` rather than `=== "update_failed"` on purpose: `'noop'` means no
  UPDATE was issued at all, which is equally not a repair. The FILL arm now answers
  200 **only when an UPDATE actually ran and actually succeeded.**

**In-class extension found while fixing BL-01 (same call site, same false claim).**
`fillClassification` was set from the committed row alone, so an echo carrying **no
classification at all** still took the FILL arm. Two consequences, both closed:
the widened metadata gate handed `buildMetadataUpdatePayload` whatever else the blob
held — a `description`, an `aum` — and wrote it onto a row a PRIOR request committed,
which is exactly the **mutation-on-an-echo A4 forbids**; and the user was told their
category and asset class had been applied when neither was in the payload. The fill
exists to land a DROPPED classification, so it now requires one to land
(`requestedCategoryId !== null || requestedAssetClass !== null`). Otherwise: no fill,
no refusal, the plain echo — the status quo ante and the safe direction.

### BL-02 — the series-bearing FILL ASSUMED the recompute the empty-series arm MEASURES

**The asymmetry was the defect.** This plan shipped the clock-safety probe nested
inside `if (args.rows.length === 0)`. The empty-series arm read `strategy_analytics`
and REFUSED on stored KPIs; the series-bearing arm filled unguarded, on the premise
written into the code as *"the enqueue below fires after the awaited UPDATE… No
guard read is needed: the recompute is the reconciliation."*

That premise assumed the one side effect this file carries ~150 lines of fallback
machinery for. `enqueueCsvAnalyticsAfter` is `after()`-scheduled and non-blocking,
and **Phase 143 exists because it drops.** A drop *after* a fill is unhealable:
`writeFailedStrategyAnalyticsPlaceholder` returns early once the row is a terminal
success, and the Phase 143 sweep excludes `computation_status IN (…,'complete',…)`
