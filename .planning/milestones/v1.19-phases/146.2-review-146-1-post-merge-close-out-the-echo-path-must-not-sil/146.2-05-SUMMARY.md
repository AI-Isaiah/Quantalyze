### ⚠️ The review's stated reason for "regex, not equality" is not the reason — the measured one is

The finding said an equality test would red because `pg_get_functiondef` re-renders the SET clause.
**Measured, that is not the mechanism** — `proconfig` is not read through `pg_get_functiondef` at
all, and PostgreSQL normalises spacing and quoting before storing, so all three of
`= public, pg_catalog`, `= public,pg_catalog` and `= "public", pg_catalog` store the identical entry
and an equality test survives every one of them:

```
SET search_path = public, pg_catalog   | {"search_path=public, pg_catalog"} | equality t | regex t
SET search_path = public,pg_catalog    | {"search_path=public, pg_catalog"} | equality t | regex t
SET search_path = "public", pg_catalog | {"search_path=public, pg_catalog"} | equality t | regex t
```

The conclusion still holds, for a different and narrower reason: the **content** of the value
diverges on healthy databases.

```
SET search_path = pg_catalog, public          | {"search_path=pg_catalog, public"}          | equality f | regex t
SET search_path = public, pg_catalog, pg_temp | {"search_path=public, pg_catalog, pg_temp"} | equality f | regex t
```

A reorder and a hardening addition each leave the protected property fully intact — the body still
resolves through a FIXED list rather than the caller's — while the equality form reds. That is the
"fails on a healthy database" failure, and it is why Part 1b ships the regex form from
STEP 4(b2). The in-file comment states the measured mechanism, not the reviewer's.

The nearest in-repo precedent, `test_cutover_strategy_metrics_keys_atomic.sql:50-66`, uses the
**equality** form. Its *shape* is followed (read `proconfig` into a declared `TEXT[]`, assert, name
the observed value in the failure message); its *comparison* is not. Flagged rather than blended
(Rule 7). Not fixed here — different function, different plan, out of this closure's file scope.
