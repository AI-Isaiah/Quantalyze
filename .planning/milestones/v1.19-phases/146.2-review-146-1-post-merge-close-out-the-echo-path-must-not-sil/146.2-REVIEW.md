## Critical Issues

### CR-01 (BLOCKER): the FILL arm's 200 asserts a write that is best-effort and swallowed on failure

**File:** `src/app/api/strategies/csv-finalize/route.ts:1427-1434` (the sentence),
`src/app/api/strategies/csv-finalize/route.ts:1809-1826` (the swallow),
`src/app/api/strategies/csv-finalize/route.ts:2311-2320` (the caller)

**Issue:** On the FILL arm the route returns 200 with

> "…it was saved without the details you entered — including the category and
> the asset class that decides how its returns are annualized — **so we applied
> them to it now**."

`applyCsvMetadataUpdate` treats an UPDATE error as **non-fatal**: it logs,
captures to Sentry, and `return null` (`route.ts:1809-1826`). The caller's only
test is `if (metaErrResponse) return metaErrResponse;` — `null` falls straight
through to the 200 envelope that carries `fillHumanMessage`. So a 42501 (RLS,
e.g. an expired session mid-request), a 22P02, or a PostgREST transport fault on
that UPDATE produces a success response asserting a write that did not happen.

This is the exact harm R1 exists to close, surviving in R1's own failure branch:
the strategy stays `category_id = NULL` (invisible to discovery) with
`asset_class = 'traditional'` (√252) on a crypto track record, there is no
post-creation editor, **and the user is now told it was fixed**, so they have no
reason to retry. The previous behaviour at least left the user with a failure
they could act on.

**Failure scenario (measured, not argued):**

| step | input | outcome |
|---|---|---|
| 1 | fold commits; transport dies before the metadata UPDATE | strategy committed, `category_id NULL`, `asset_class 'traditional'` |
| 2 | user follows the A3 copy and resubmits the same file, `asset_class: crypto`, `category_id: <uuid>` | 23505 → resolve → FILL arm |
| 3 | the FILL `UPDATE strategies …` returns `{code:'42501'}` | logged + Sentry, `return null` |
| 4 | response | **200 `ok:true`**, `human_message` = "…so we applied them to it now" |

Executed against HEAD with the merge-suite mocks (`updateCalls` recorded the
call, the mock returned `{code:'42501'}`); observed:

```
PROBE status= 200 ok= true msg= An earlier attempt in this wizard session had already
saved this strategy, but it was saved without the details you entered — including the
category and the asset class that decides how its returns are annualized — so we
applied them to it now. …
```

**Fix:** on the fill arm the UPDATE is not a best-effort epilogue to a create —
it *is* the request's whole purpose, and refusing costs nothing (the strategy is
already committed and the resubmit is idempotent). Make it fatal on that arm
only:

```ts
// applyCsvMetadataUpdate — surface the failure to the caller instead of null.
if (updateError) {
  console.error(/* unchanged */);
  captureToSentry(updateError, { /* unchanged */ });
  if (opts.fatalOnFailure) {
    return NextResponse.json(
      { ok: false, code: "CSV_PERSIST_FAIL",
        human_message:
          "We could not apply the category and asset class to the strategy an " +
          "earlier attempt already saved, so nothing was changed. Try again shortly.",
        debug_context: {}, correlation_id: opts.correlationId },
      { status: 503, headers: NO_STORE_HEADERS },
    );
  }
}
```

…and pass `fatalOnFailure: outcome.fillClassification === true` at
`route.ts:2311`. (The `fresh` create path keeps today's non-fatal semantics —
rolling a committed strategy back over its metadata is the reason that swallow
exists.) A weaker but acceptable alternative: on UPDATE failure, drop
`fillHumanMessage` back to the neutral echo sentence, so the 200 never claims a
write it did not make. Add a regression case in
`csv-finalize-cross-submission-merge.test.ts` that drives the update mock to an
error on the FILL arm and asserts the envelope does not contain
"we applied them to it now".

### CR-02 (BLOCKER): the series-bearing FILL moves the annualization clock on an `after()` promise the same file documents as droppable — and the drop is unrepairable

**File:** `src/app/api/strategies/csv-finalize/route.ts:1421-1426` (the "no guard
read is needed" claim), `route.ts:2326-2331` (the enqueue),
`route.ts:1610-1624` (the placeholder guard that then skips),
`supabase/migrations/20260819150000_reconcile_sweep_readmit_attempt_ceiling.sql:397-402`
(the sweep exclusion)

**Issue:** The empty-series arm MEASURES clock safety by probing the seven ranked
KPI columns and refuses 409 if any is non-null. The series-bearing arm skips that
probe entirely, on the stated grounds that "the enqueue below fires after the
awaited UPDATE, so the stored KPIs recompute under the FILLED clock." That
enqueue is `after()`-scheduled and explicitly non-blocking — this very file
carries ~150 lines of machinery (`enqueueCsvAnalyticsAfter`,
`writeFailedStrategyAnalyticsPlaceholder`) because it *can* fail. When it does,
the fallback does not help here and the sweep cannot reach the row:

1. `writeFailedStrategyAnalyticsPlaceholder` pre-checks
   `isComputedAnalytics(existing.computation_status)` (`route.ts:1610-1624`;
   `src/lib/closed-sets.ts:715-719` → `'complete' | 'complete_with_warnings'`)
   and **returns without writing** when the row is already `complete`.
2. The Phase 143 sweep's candidate predicate excludes any strategy with a
   `strategy_analytics` row in `('computing','complete','complete_with_warnings','failed')`
   (`20260819150000:397-402`). A `complete` row is therefore never readmitted.

Result: `asset_class = 'crypto'` sitting over a `cagr`/`sharpe`/`sortino`/
`calmar`/`volatility` set computed under √252, `computation_status = 'complete'`,
permanently — the precise state the empty-series REFUSE arm was built to prevent,
reached from the arm that has no guard.

**Failure scenario (inputs → wrong outcome):**

| step | input | state |
|---|---|---|
| 1 | fold commits, response lost (A3 CLASS 2/3) | strategy + dailies committed; no metadata UPDATE, **no enqueue** (the route returned `ok:false`) |
| 2 | +1 h, `reconcile_dropped_enqueue_sweep` tick | job enqueued; worker computes KPIs under the DEFAULT `asset_class='traditional'` ⇒ √252; `strategy_analytics.computation_status = 'complete'` |
| 3 | user follows the A3 copy: resubmits the same file with `asset_class: crypto` | 23505 → resolve → `category_id IS NULL` → **series-bearing FILL**, no probe |
| 4 | `UPDATE strategies SET asset_class='crypto', category_id=…` (awaited, committed) | clock moved |
| 5 | the `after()` `enqueue_compute_job` errors (transient PostgREST 5xx / admin-client fault / lambda reaped before the callback settles) | placeholder pre-check reads `complete` ⇒ **skips**; sweep's `NOT EXISTS … computation_status IN (…,'complete',…)` ⇒ **never readmits** |
| 6 | steady state | crypto-labelled strategy, `category_id` now set (so it is discovery-visible), `complete` KPIs computed on √252, ranked by `getPercentiles` once published |

Note step 5 is *more* likely on exactly this request than on a fresh create: it
runs on a recovery path the user only reaches because something already failed.

**Fix:** make the series-bearing arm measure what the empty-series arm measures,
and let the recompute be a repair rather than the sole guarantee. Minimal shape —
hoist the probe out of the `rows.length === 0` branch and, when stored KPIs are
present on a series-bearing fill, invalidate them in the same request so a
dropped enqueue leaves a *healable* state rather than a false `complete`:

```ts
if (existingRow.category_id === null) {
  const storedKpiPresent = await probeStoredKpis(supabase, existingRow.id); // both arms
  if (storedKpiPresent) {
    if (args.rows.length === 0) return refuse(/* unchanged empty-series copy */);
    // Series-bearing: the fill is licensed ONLY because a recompute follows,
    // so make the recompute mandatory rather than best-effort — clear the
    // terminal status BEFORE the clock moves, so both the placeholder guard
    // and the Phase 143 sweep can still reach this row if the enqueue drops.
    needsKpiInvalidation = true;
  }
  fillClassification = true;
  …
}
```

…with the invalidation performed via the admin client, awaited, before
`applyCsvMetadataUpdate` (an owner cannot write `strategy_analytics` —
`analytics_update_deny`). If that is judged too large for this phase, the honest
alternative is to REFUSE the series-bearing fill when stored KPIs are present,
with the same copy the empty-series arm already ships. Either way the current
comment at `route.ts:1421-1423` ("No guard read is needed: the recompute is the
reconciliation") should not survive as written — the recompute is not guaranteed.

Add the missing case to `csv-finalize-cross-submission-merge.test.ts`: a
series-bearing FILL against `analyticsProbe.row = PROD_FAILED_WITH_KPIS` with
`enqueueRpcMock` rejecting, asserting the row does not end up
`complete`-with-old-KPIs under the new clock. That case does not exist today —
every FILL arm in the suite runs with `analyticsProbe.row = null`.

### WR-01: `createAdminClient()` on the request path, outside the fire-and-forget guard, immediately after an irreversible commit

**File:** `src/app/api/strategies/csv-finalize/route.ts:733`;
`src/lib/supabase/admin.ts:10-19`; `src/lib/api/withAuth.ts` (no `try`/`catch`
anywhere in the file)

**Issue:** `logAuditEventAsUser(createAdminClient(), …)` evaluates
`createAdminClient()` **before** the call, so it is outside
`logAuditEventAsUser`'s own `try` (`src/lib/audit.ts:922-930`).
`createAdminClient` throws synchronously when `NEXT_PUBLIC_SUPABASE_URL` or
`SUPABASE_SERVICE_ROLE_KEY` is unset (`admin.ts:14-16`). `withAuth` does not
catch, so the throw escapes to Next and becomes an opaque 500 with no `code`
and no `human_message` — on the branch where the fold has **already committed**.
The site's own docblock states the opposite contract three lines above
(`route.ts:725-728`: "a failed emission … must NOT change this response").

The two pre-existing admin usages in this file are both inside `after()`
epilogues wrapped in `try`/`catch` (`route.ts:1583-1585`, `route.ts:1699-1701`);
this new one is the first on the request path. The call-site *shape* matches
`preferences/route.ts:221` and `account/deletion-request/route.ts:141`, so this
is a class instance, not a novel pattern — but csv-finalize is the highest-stakes
member, because the throw lands after a committed track record.

**Failure scenario:** a preview/branch deployment (or any environment with a
rotated-out service-role key) → user submits a CSV → fold commits strategy +
verification + N dailies → `createAdminClient()` throws → 500 with a body the
wizard cannot parse → `CSV_SUBMIT_FAILED` copy → user believes nothing was
saved. (Recovery exists: the resubmit takes the 23505 arm, which never reaches
this line. The defect is the false failure report, not permanent loss.)

**Fix:**

```ts
try {
  logAuditEventAsUser(createAdminClient(), args.userId, { /* unchanged */ });
} catch (auditClientErr) {
  console.error(
    `${opts.logPrefix} audit emission could not be scheduled (non-blocking) [correlation_id=${opts.correlationId}]:`,
    scrubSeamError(auditClientErr),
  );
  captureToSentry(auditClientErr, {
    tags: { surface: "csv-finalize", step: "finalize-audit-schedule" },
    extra: { strategy_id: newStrategyId, correlation_id: opts.correlationId },
  });
}
```

### WR-02: the FILL discriminator's stated proof is not a proof — `category_id` is silently dropped when present-but-not-a-UUID

**File:** `src/app/api/strategies/csv-finalize/route.ts:409-418` (the parse),
`route.ts:1336-1339` and `route.ts:2298-2300` (the claim it invalidates)

**Issue:** R1 rests on "a committed NULL is observable proof that UPDATE never
ran". `parseCsvMetadata` refuses an *explicit null* `category_id` with a 400, but
a present-but-invalid string is neither accepted nor rejected — the `else if`
requires `isUuid()` and there is no else:

```ts
if (obj.category_id === null) { return { ok: false, … }; }
else if (typeof obj.category_id === "string" && isUuid(obj.category_id)) {
  out.category_id = obj.category_id;
}
// a non-UUID string, a number, an object → silently dropped
```

That directly contradicts the comment four lines above it
(`route.ts:397-398`: "Validate at the route boundary so the field either lands
cleanly or is rejected (**better UX than a silent drop**)"), and it is unlike
every sibling field — `asset_class` (`route.ts:495-503`) and `aum`
(`parseCsvMetadata`'s numeric arms) both 400 on present-but-invalid.

Pre-146.2 this only cost discovery visibility. This diff makes it **load-bearing
for a write decision**.

**Failure scenario:** an authenticated client (a stale wizard build, an
integration, a script) posts `metadata.category_id: "systematic-macro"` with
`asset_class: "traditional"`. → 200, strategy committed, `category_id NULL`,
metadata UPDATE **did** run. Later, a same-session resubmit with the same name
and series but `asset_class: "crypto"` → resolve arm reads `category_id === null`
→ FILL arm → `applyCsvMetadataUpdate` rewrites `asset_class`, `description`,
`aum`, `markets`, `strategy_types`… i.e. exactly the "honouring a mutation the
user never asked for" that A4 forbids and that `route.ts:2296-2305` claims
`fillClassification` cannot cause.

(The wizard itself cannot reach this: `MetadataStep` gates Submit on a non-null
`categoryId` sourced from `discovery_categories`. The API can.)

**Fix:** close the drop, in the same shape as `asset_class`:

```ts
if (obj.category_id === null) {
  return { ok: false, field: "metadata.category_id", message: "category_id is required — select a strategy category before submitting." };
} else if (obj.category_id !== undefined) {
  if (typeof obj.category_id !== "string" || !isUuid(obj.category_id)) {
    return { ok: false, field: "metadata.category_id",
      message: `category_id must be a UUID (got ${JSON.stringify(obj.category_id)}).` };
  }
  out.category_id = obj.category_id;
}
```

Then the "observable proof" claim becomes true, and a regression test should pin
it (`csv-finalize-c14-regression.test.ts`, beside the NEW-C14-03 arms).

### WR-03: R2 closes the route's capture sites; the two seam TRANSPORT log sites still derive their secret list from HEADERS only

**File:** `src/lib/process-key-client.ts:683-688`;
`src/lib/resilient-fetch.ts:2590-2593`; premise restated by this diff at
`src/app/api/verify-strategy/route.ts:224-227` and `:316-321`

**Issue:** This phase's justification for R2 is TRAP-1: "undici inlines that
**body** into `err.message`". The two places that actually render an undici fetch
error to the console scrub with `credentialHeaderValues(...)`, which walks
`CREDENTIAL_HEADER_NAMES` (`resilient-fetch.ts:1903-1909`:
`authorization`, `x-user-access-token`, `x-tenant-claim`, `x-service-key`,
`x-internal-token`) — a **headers-only** derivation. Nothing in either call
reaches the request body, and `postProcessKey` returns an envelope rather than
throwing, so the route's `perRequestSecrets` never reaches those frames.

So one of two things is true, and both are worth resolving before this ships as
"the passphrase is scrubbed":

- the TRAP-1 body premise is correct → `api_key` / `api_secret` / `passphrase`
  supplied by an anonymous caller on the **public, unauthenticated**
  `/api/verify-strategy` route land verbatim in the Vercel console on every seam
  transport failure, and R2 closed four sites while leaving the one that renders
  the raw undici message; or
- the premise is wrong → the phase's own rationale (and the `⛔` prohibitions
  built on it) overstates the mechanism, and the doc should say so.

This is a pre-existing site, not code this diff touched — flagged because this
diff is the one asserting completeness.

**Fix:** either (a) extend `postProcessKey` to derive body credentials the way it
derives header ones — e.g. accept an optional `secrets` on `PostProcessKeyArgs`
that the four seam callers already compute, and add it to the `scrubSeamError`
call at `process-key-client.ts:684-687`; or (b) measure undici's actual behaviour
once and, if the body is not inlined, correct the TRAP-1 wording at
`verify-strategy/route.ts:224-227` and in `seam-redaction`'s docblock so the next
reader is not defending a mechanism that does not exist.
