# Phase 153.1 Plan 02: VENUE_CAPABILITIES + MIN_DESCRIPTION_CHARS foundation Summary

Minted the two values the rest of the sub-phase consumes — a per-venue **capability
record** that makes venue-shaped behaviour a class rule, and a single-sourced
**description lower bound** — with nine new property assertions and four mutations
watched failing. Zero offered-set changes; zero production behaviour changes.

**Base commit:** `741b8b76` (wave-0's final commit). The plan measured at `0c4f01d8`;
every anchor below was re-derived from source at `741b8b76` per D-10 — see the drift
table.

**Exported names 153.1-03 / 153.2 / 153.4 import by name:**

| Kind | Name |
|---|---|
| interface | `VenueCapabilities` |
| record | `VENUE_CAPABILITIES` |
| predicate | `venueSupportsScopeProbe(venue: string \| null \| undefined): boolean` |
| predicate | `venueIsSubstitutable(venue: string \| null \| undefined): boolean` |
| predicate | `venueIsSerialized(venue: string \| null \| undefined): boolean` |
| constant | `MAGNITUDE_CAPS.MIN_DESCRIPTION_CHARS` (`= 10`) |

⛔ `venueCapabilities()` — the row lookup — is **module-private on purpose**. A consumer
that indexes `VENUE_CAPABILITIES` directly gets `undefined` for an unresolved venue and
must re-invent the default, which is exactly the drift the record exists to prevent. If a
later plan needs a fourth capability, add it to the interface **and** add a predicate;
never export the lookup.
