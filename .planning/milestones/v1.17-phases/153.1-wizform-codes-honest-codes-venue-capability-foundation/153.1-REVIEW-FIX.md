### WR-05: `venueCapabilities` indexed a `Record` with a wire-sourced key — **fixed (hardening; no test, deliberately)**

**File modified:** `src/lib/closed-sets.ts:159-166`
**Commit:** `a7c49ee9`

**Applied fix.** Gated the lookup behind `Object.hasOwn(VENUE_CAPABILITIES, key)`, so
`constructor` / `toString` / `__proto__` return `undefined` instead of a truthy inherited
member typed as a capability row. No behaviour change for any real venue.

**⚠️ NO TEST ADDED, AND THIS IS A DELIBERATE CALL — read before "completing" it.**

I checked whether a falsifiable test exists and it does not. All three predicates are:

```ts
return venueCapabilities(venue)?.scopeProbeSupported ?? true;
return venueCapabilities(venue)?.substitutable        ?? true;
return venueCapabilities(venue)?.serialized           ?? false;
```

`Object.prototype` carries none of those three property names, so under the **unfixed**
code a prototype-chain key returns an inherited object whose relevant property is
`undefined`, and `??` falls to exactly the same declared default as the fixed code
returning `undefined`. **Any test written at the predicate boundary would pass against
the unfixed code** — a guard that cannot fail, which is the exact defect class this phase
was convened to delete. Writing one would have been worse than writing none.

This matches the reviewer's own framing ("current impact is nil and the reason is
accidental"). The hardening is defence-in-depth for the day a **fourth** capability is
added whose safe default is the other polarity; the test becomes writable *and*
falsifiable at that point. Recorded in the commit message so it is not silently lost.

with two `it`s:

1. a non-vacuity/rename guard (`FIELD_LEVEL.length === 8`, every code present in the table);
2. the class sweep, reporting **offenders as a population** (`.toEqual([])`) rather than
   code-by-code — a per-code assertion stops at the first offender and hides the rest of
   the class.

The roster is **hand-typed** and deliberately *not* derived from `KNOWN_FINALIZE_CODES`
nor from a `startsWith("METADATA_")` filter: an oracle read off the structure under test
moves with it.

**Why a new describe rather than extending the existing sweep.** The existing sweep
(`wizardErrors.test.ts:3073`) is keyed on *"the ten members 153.1-04 **minted**"* — a
**provenance**, not a class. `METADATA_DESCRIPTION_REQUIRED` is answered by the same
`validatePayload` block against the same kind of rule but is a Phase-53 entry the route
was merely *pointed at*, so it fell outside that roster by construction. That is
mechanically why CR-01 shipped. The new sweep is keyed on **what the codes are**, which
closes the class rather than widening the instance list.

Falsification evidence is the CR-01 mutation above — the new sweep is the assertion that
reds, naming the offending code.

**Deferred, and flagged rather than silently dropped:** the reviewer also asked for one
`SubmitStep.test.tsx` render case. Not added. The behaviour it would assert
(`recoverable === false` ⇒ no Retry) is now covered at the derivation tier, where it is
decided; `SubmitStep.test.tsx` already carries three positive-control render cases
(`COMPOSITE_TOO_MANY_MEMBERS`, `SEAM_MISCONFIGURED`, `DRAFT_STATE_INVALID`) proving the
`recoverable → showRetry` wiring itself holds, so a fourth would re-test the wiring, not
the new codes. **Recommend a follow-up** adding one `METADATA_*` render case so the
