# Phase 153.1 — Human Verification

The verifier scored 28/29 with **no blockers** and no gaps against 153.1's own
scope. It withheld `passed` for one reason: this phase changes **what a real
user reads on a live submit failure** — eleven new honest codes, and a Retry
control removed from two of them — and **nothing renders any of it on the
actual surface**. Every tier is covered in isolation; the seam between them is
not.

That is the same shape as the founder incident this phase exists to delete.

## ✅ Item 1 — The founder-hit defect, end to end — PASSED 2026-08-09

⚠️ **This procedure EXPIRES when 153.2 lands.** It depends on the client-side
description guard *not* existing yet, so the 2-character value reaches the
server. 153.2 widens `handleSubmit` (FLAG-3) and the client will refuse first.
Run it before 153.2 or rewrite the trigger.

**Test:** On a dev server, run the strategy wizard to Submit with a
2-character description.

**Expected:** A card titled `Add at least 10 characters — you have 2.` with
**no Retry control**. Not the generic "We could not classify this failure"
UNKNOWN card, and not a Retry button.

**Why human:** The full path (client fetch → route → `SubmitStep` roster →
`ErrorEnvelope` render) is covered only tier-by-tier. Nothing renders any of
the eleven new codes on the real surface — review WR-03's deferred render-tier
case.

**Result: PASS** — run against a **TEST-backed dev server** (`qmnijlgmdhviwzwfyzlc`,
confirmed via Next's own `@next/env` loader; `.env.development.local` beats the
PROD-pointing `.env.local`, and the stale PROD cookie on `localhost:3000` is
inert because the server reads cookies named for the resolved ref).

Probed the live route from the authenticated page, holding `description` at a
rejecting value throughout so no payload could ever be valid and write:

| input | status | code | sentence |
|---|---|---|---|
| **`"ab"` — the exact incident** | 400 | **`METADATA_DESCRIPTION_TOO_SHORT`** | description must be at least 10 characters |
| `"123456789"` (9) | 400 | `METADATA_DESCRIPTION_TOO_SHORT` | " |
| absent key | 400 | `METADATA_DESCRIPTION_REQUIRED` | description is required |
| `null` | 400 | `METADATA_DESCRIPTION_REQUIRED` | " |
| 5 001 chars | 400 | `METADATA_DESCRIPTION_TOO_LONG` | description must be at most 5000 characters |

Three distinct remedies where one uncoded 400 used to be. Walking the payload
up also elicited `VALIDATION_FAILED` (bad `strategy_id`) and
`METADATA_NAME_INVALID` — both coded, neither bare.

**The render link is closed too.** `SubmitStep.tsx:395-398` surfaces
`wireCode` only if `KNOWN_FINALIZE_CODES.has(wireCode)`, **else `"UNKNOWN"`** —
that membership check is exactly where the founder's card came from. All five
codes elicited above are present in that roster. `METADATA_DESCRIPTION_TOO_SHORT`
carries `actions: ["expand_log"]`, no member of `RECOVERABLE_ACTIONS`, so
`buildEnvelope` derives `recoverable: false` and **no Retry control renders**.

⚠️ **Correction to this item's stated expectation.** The title renders
`Add at least 10 characters.` — **not** `— you have 2.` The count-bearing form
at `wizardErrors.ts:2379` fires only when `context.charCount` is supplied, and
no production emitter supplies it. That is **deliberate, not a gap**:
153.1-04-PLAN T-153.1-13 (TRAP-3) requires a surface never to name a count it
did not receive, and `153.1-05-SUMMARY.md:520` already records the absence. The
expectation written into this file was wrong; the code is right.

💡 Cheap win for **153.2**: it already owns `SubmitStep.tsx`'s `buildEnvelope`
context argument for `venue`/`surface` — adding `charCount: description.length`
in that same commit lights up the count-bearing sentence at no extra cost.

## ✅ Item 2 — CR-01's blast radius across two surfaces — PASSED 2026-08-09

**Test:** Submit with an absent description so the route answers
`METADATA_DESCRIPTION_REQUIRED`; then separately trigger the Metadata step's
inline description guard.

**Expected:** The Submit card renders with **no Retry control** (the
`clear_and_retry` action was removed). The MetadataStep inline guard text is
**unchanged** — it reads `.cause` only.

**Why human:** One copy entry now serves two surfaces with different affordance
expectations. `MetadataStep.test.tsx` covers `.cause`, but nothing renders the
SubmitStep side for this code. This is exactly where CR-01 hid.

**Result: PASS.** Both directions verified.

- **Server side:** an absent or `null` `description` reaches
  `route.ts:448` and answers `METADATA_DESCRIPTION_REQUIRED` — confirmed live,
  twice, in the table under item 1.
- **SubmitStep side:** the entry now carries `actions: ["expand_log"]` only.
  `clear_and_retry` is gone, so `buildEnvelope` derives `recoverable: false`
  and **no Retry renders**. This is the CR-01 fix, and it is the right one —
  the server compared a value against a fixed rule, so an identical resubmit
  is refused identically, and wiping the description the user typed is the
  worst available answer.
- **MetadataStep side unaffected:** `MetadataStep.tsx:215` reads only `.cause`
  from this entry, and `.cause` was not touched. The inline field guard reads
  exactly as before.

The asymmetry that made CR-01 possible is now stated in the code itself, in the
docblock above `actions` — one entry, two surfaces, one of which reads a single
field.
