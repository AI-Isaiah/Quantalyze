# Phase 153 — UI Design Contract

> Visual and interaction contract for WIZFORM-01/02/03/04/05 + MT5-14. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.
>
> **THE CONTRACT IN ONE SENTENCE: every message this wizard renders must be true about
> the thing the user is actually doing, and every control it offers must be able to
> work.**
>
> Three failures share one root and this contract closes all three the same way — by
> making the surface state what it *observed*, never what it *assumed*:
>
> | Live failure | What the UI asserted | What was true |
> |---|---|---|
> | 2-char description (3 lost submits) | a full-page envelope, field unnamed | one field, one rule, knowable before submit |
> | Retry × 5 on `KEY_NETWORK_TIMEOUT`, Retry on `SERVICE_UNREACHABLE` (2026-08-08) | "try again" | a deterministic condition that fails identically every attempt |
> | "switch to a different exchange" on a MetaTrader account | there is another venue | the account **is** the venue |
>
> **The acceptance bar is behavioural (D-13).** A prettier-but-still-ambiguous error
> does not pass. The test is: *did the user learn which field / which control / which
> action, without guessing?*

## Typography

Named fluid tiers from `DESIGN.md` §Fluid Type Spine. ⛔ No raw `text-[Npx]`
(`no-raw-font-px` is repo-wide `error`).

| Role | Token | px (min→max) | Weight | Line height |
|------|-------|--------------|--------|-------------|
| Field label / status label / chip | `text-caption` (labels, chips) · `text-body` (status label) | 12→13 · 14→16 | **500** `font-medium` | 1.5 |

**Two weights on every surface this phase authors: 400 regular + 500 medium.**

weight introduced here.

⛔ **No mono on a form label or an error message.** Mono is the data-annotation voice:
in this phase it is reserved for the elapsed counter, the character count, the
`code:`/`correlation_id:` values, and (MT5-14) the `DETECTED FROM YOUR KEY` eyebrow.
Putting DM Sans on that eyebrow, or mono on the "Add at least 10 characters" message,
is the documented failure mode.

## Surface 1 — The long-wait validate state (D-05, WIZFORM-05)

**Today's state is exactly what D-05 forbids:** `ConnectKeyStep.tsx:782` renders a
disabled button reading `Validating...` and nothing else. Against a ~90–120s MT5 budget
that is a two-minute silent spinner.

**Anatomy — lifted verbatim from the house long-wait card (`SyncPreviewStep.tsx:2309`),
placed directly above the submit row in `ConnectKeyStep` / `MultiKeyConnectStep`:**

```
<div class="mt-6 rounded-md border border-border bg-page px-4 py-3">
  <div class="flex items-center gap-3">
    <span aria-hidden class="inline-block h-2 w-2 animate-pulse rounded-full bg-accent" />
    <p class="text-body font-medium text-text-primary">{statusLabel}</p>
    <span aria-hidden class="ml-auto font-metric text-caption tabular-nums text-text-muted">{n}s</span>
  </div>
  {escalationLine}
  {cancelRow}
</div>
```

| Property | Contract |
|---|---|
| Render gate | Mounts 300ms after submit (a sub-300ms answer must never flash a card). One code path for **every** venue — no per-venue presentation branch |
| Motion | `animate-pulse` on the 8px dot **only**. ⛔ No spinner, no progress bar, no percentage, no indeterminate stripe. A progress bar implies a known completion fraction we do not have — that is a fabricated figure under the Numbers Contract |
| Elapsed counter | Whole seconds, 1s tick, `.font-metric tabular-nums` so it does not reflow. `aria-hidden="true"` — a per-second live update floods AT |
| Budget figure | Every copy string that names a duration reads it from the **configured venue budget constant**. ⛔ No literal seconds typed into copy — copy and budget cannot be allowed to drift |
| Submit button | Stays mounted, label `Validating…`, `disabled` **only** while in flight (double-submit guard). The form fields stay mounted and populated |
| `aria-busy` | `aria-busy="true"` on the `<form>` while in flight |

### Status labels — observed facts only

⚠️ **`validate-key` is ONE request/response. The client observes no server stages.** It
therefore MUST NOT render "Queued", "Signing in", "Probing" as *observed states* — that
would be the TRAP-3 class this repo already forbids ("a surface must NEVER invent a
duration it did not receive"). One label per venue, true for the whole span:

| Venue class | Status label |
|---|---|
| `serialized` venues (MT5) | `Signing in to your broker…` |
| ccxt venues | `Checking your key with {VenueName}…` |

If a future phase streams real stage events, these may become observed states. Until
then, one label.

### The escalation ladder

Thresholds are **fractions of the configured venue budget**, so a budget change moves
them automatically:

| Threshold | Line | Class |
|---|---|---|
| t = 0 | `We wait up to {budget}s for your broker to answer.` *(serialized venues)* — omitted for ccxt venues, whose budget is short enough to need no promise | `mt-2 text-caption text-text-muted` |
| t ≥ 40% | `Still signing in. MetaTrader allows one sign-in at a time, so your check may be waiting behind another.` — **rendered only when the venue capability `serialized` is true** | `mt-2 text-caption text-text-muted` |
| t ≥ 75% | `This is slower than usual. We will wait until {budget}s, then tell you what we found.` | `mt-2 text-caption text-warning` |

⛔ **No typical-duration range is stated for MT5.** No measured distribution of a
*successful* MT5 login exists; the only figures on record describe *failures*
(35–70s+). Naming a "usually 20–60s" would be an invented number. State only the budget,
which is a fact we control.

⛔ Copy vocabulary: `your broker`, `sign-in`, `one sign-in at a time`. Never `terminal`,
`gateway`, `rpyc`, `lock`, `MT5 client`, or any Python identifier.

### Cancel affordance

| Property | Contract |
|---|---|
| Appears | At t ≥ 40% of budget — the same moment as the first escalation line. Never before (it would flash on the ccxt fast path) |
| Control | `Button variant="ghost" size="sm"`, label **`Stop waiting`**. Full-opacity focus ring per the focus contract |
| Semantics | **Not destructive.** Cancelling costs the user nothing they can act on — the request finishes or fails on its own either way. ⛔ No confirmation dialog, no `variant="danger"`. ⚠️ **CORRECTED (153.4 review CR-02):** this row used to read *"`validate-key` is strictly pre-encrypt / pre-RPC … nothing is persisted server-side, so cancelling loses nothing"*. That is a fact about the SEAM CALL asserted about the ROUTE. The browser aborts `create-with-key` / `composite/add-key`, which run `validateKey` → `encryptKey` → an RPC and read no `request.signal`, so on any run where validate then succeeds the key IS stored |
| On click | Abort the in-flight request; unmount the card; keep every field value; move focus to the submit button |
| Resulting state | A **neutral** line where the card was — `text-caption text-text-secondary`, ⛔ not an `ErrorEnvelope`, ⛔ not red. ⛔ **It may not assert a server-side outcome this browser cannot know.** Single-key: `We stopped waiting for your broker. Your key details are still on this page — the check may still be finishing on our side, and connecting again picks up that key rather than storing a second one.` (true because `create-with-key` fences on `wizard_session_id`, at the route AND inside `create_wizard_strategy`'s advisory lock). Composite panel: `We stopped waiting for your broker. Your key details are still on this page — the check may still be finishing on our side, so give it a moment before validating this key again.` (the tail differs because `composite/add-key` has NO such fence by construction — a re-fire mints a second credential) |

### Accessibility

- `<LiveRegion message={statusLabel or escalationLine} />` (polite, non-assertive —
  a wait is a non-blocking state change per `DESIGN.md` DESIGN-05).
- Announce on: card mount, **each threshold crossing**, cancel, terminal. ⛔ Never on the
  1s tick.
- The pulse dot is `aria-hidden`. The wait is conveyed by **text**, never by motion alone.
- The elapsed counter is `aria-hidden`; a sighted user reads the figure, an AT user hears
  the label and the threshold sentences.

## Surface 2 — Inline field validation (D-11 / D-12 / D-13, WIZFORM-01)

**The precedent already exists and is correct:** `AllocateDialog.tsx` mirrors the
server's `parseAmount` client-side, refuses inline at the field, focuses it, and
**never disables the CTA for a validation reason**. This phase generalises that to the
wizard.

### The rule

> **Every server rule the client can evaluate is mirrored client-side and refuses at the
> field. The field is the ONLY place a field-level message appears.**

### Anatomy — through `Field`, always

| Property | Contract |
|---|---|
| Wrapper | `<Field label hint error>` — it already wires `aria-describedby="{id}-hint {id}-error"` and `aria-invalid="true"`. ⛔ No hand-wired label/error markup |
| Message position | Directly **below** the control, `text-caption text-negative`, 8px gap (Field's `gap-1.5`) |
| Invalid control | `aria-[invalid=true]:border-negative` — **the red border DERIVES from the aria state.** This is a hard invariant: it makes a red field without correct aria wiring structurally impossible |
| ⛔ Forbidden | red fill, coloured left border (AI-Slop Ban: "colored-left-border cards"), warning icon, emoji, tooltip-only error, `title=`-only error |
| Message voice | One declarative sentence. **State the threshold with its number** (`DESIGN.md` §Voice). No adjectives, no apology |
| Message source | The `title` field of a `WIZARD_ERROR_COPY` entry — a single sentence. ⛔ **Never `.cause`** (a paragraph). `MetadataStep.tsx:215` currently renders `.cause` inline; change it to `.title` |

### Reveal timing (this is where the actual defect lives)

| Event | Behaviour |
|---|---|
| Typing, field never blurred | **Silent.** Typing `S` into a 10-char-minimum field must not turn it red |
| Blur, field touched | Reveal that field's error |
| Change, **while an error is already shown** for that field | **Live re-evaluate** — the message and its count update on every keystroke, and the message and red border disappear the instant the value becomes valid |
| Submit attempted | Reveal **all** field errors at once |

⚠️ `AllocateDialog` sets `fieldError` on save and clears it only on the next save. The
live-clear rule above applies there too (D-12) — an amount the user has already fixed
must not still read red.

### Submit-with-errors

1. Reveal every field error.
2. If the first invalid control sits inside a collapsed `<details>` (the
   "More details (optional)" disclosure), **open the disclosure first** — otherwise
   focus lands on a control the user cannot see. This is a live hazard: the
   supported-exchanges chips live inside it.
3. `focus()` the first invalid control in DOM order and scroll it into view.
4. Announce once via `<LiveRegion assertive>`:
   `{n} fields need attention. The first is {Label}.`
   ⛔ Not an `ErrorEnvelope`. A field problem never renders a terminal envelope.

### The submit button is NEVER disabled for a validation reason

`MetadataStep.tsx:491` currently reads `disabled={!description.trim() || !categoryId}`.
**Delete that gate.** It is the precise mechanism that hid *which* field was wrong: a
dead button names nothing. `disabled` survives only as an in-flight double-submit guard.
(Consistent with the standing founder direction — no disabled buttons; a blocked action
must be clickable and must explain itself. `AllocateDialog.tsx:376` already states this
rule in its own comment.)

### Server-side rejections that are field-level

If the server still rejects a field-level rule (shape drift), the client **routes the
message back to the field by code** — it does not render a terminal envelope. Contract:
**each field-level 400 code maps to exactly one field id.** That map is the UI-side
consumer of WIZFORM-02's honest codes; a code with no field mapping is a planner bug, not
a runtime fallback to the envelope.

### The description field — the rule that cost 3 submits

Server bound: 10–5000 characters (`finalize-wizard/route.ts`, the `:396` arm). Today the
client checks only `!description.trim()`, so a 2-character description sails through and
dies at submit.

| State | Treatment |
|---|---|
| **Hint (always visible, pre-emptive)** | `Field hint`: `At least 10 characters.` — `text-caption text-text-muted`. This is the cheapest fix in the phase: it makes the error mostly unreachable |
| Empty | `Add a description.` (existing `METADATA_DESCRIPTION_REQUIRED.title`) |
| Under 10 | `Add at least 10 characters — you have {n}.` — `{n}` in `.font-metric tabular-nums`, live-updating |
| Over 5000 | `Keep this under 5,000 characters — you have {n}.` — thousands separator per the Numbers Contract |

**New copy-table members: `METADATA_DESCRIPTION_TOO_SHORT`, `METADATA_DESCRIPTION_TOO_LONG`.**
Both interpolate a new `WizardErrorContext.charCount?: number` through `formatKeyError`
(the existing seam — same shape as `trades` / `days` / `sizeMb`). `EXPECTED_TABLE_SIZE`
moves **64 → 66** at both sites in `wizardErrors.test.ts` (:1437, :1649), plus the
`SEAM_DEADLINE_EXCEEDED` member below ⇒ **final 67**.

## Surface 3 — Error-panel remedy affordances (D-17, WIZFORM-03/04, and the two live defects)

`ErrorEnvelope`'s visual contract does not change. What changes is **what it is handed.**
Three gates, each riding a mechanism this repo already uses.

### Gate A — Retry renders only when retrying can change the outcome

Mechanism: `buildEnvelope` derives `recoverable` from the entry's `actions`; the
envelope renders Retry iff `recoverable && onRetry`. **Absence of a recoverable action IS
the fix** — the exact mechanism `SEAM_MISCONFIGURED` and `VALIDATION_FAILED` already use,
and the one `AllocateDialog.tsx:283` applies at the call site.

**The 2026-08-08 panel offered Retry against a deadline inversion — a condition that
fails identically every attempt.** Same shape as the MT5-14 incident where the founder
clicked Retry five times.

New copy-table member **`SEAM_DEADLINE_EXCEEDED`** — the honest classification of "the
answer did not arrive inside the time *we* granted", which is distinguishable
client-side (our own abort fired; no transport error was observed):

| Field | Value |
|---|---|
| `title` | `This check ran out of the time we allow.` |
| `cause` | `We gave your broker {budget} seconds to answer and it did not. Nothing was saved — your key was not stored, and this is not a sign that your key is wrong.` |
| `fix[0]` | `Your key details are still on this page.` |
| `fix[1]` | `Some brokers are slower than the time we allow. Email security@quantalyze.com with the correlation id below and we will raise the limit for your broker.` |
| `actions` | `["request_call", "expand_log"]` — ⛔ **neither `clear_and_retry` nor `try_another_key`** ⇒ `recoverable: false` ⇒ **no Retry control renders** |
| `docsHref` | `/security#sync-timing` |

⛔ **Do not replace Retry with a second button.** The escalation path is the existing
`<details>` + "Copy diagnostics". Adding a control would re-create the false-affordance
class in a new costume.

### Gate B — surface-conditional bullets are gated on the surface

The live panel rendered, on the **connect** step:
> "If you were submitting a strategy, open /strategies before retrying — the request may
> have completed without answering." (`wizardErrors.ts:1448`)

Nothing was being submitted. The bullet sent the user on a pointless detour.

**Contract:** add `WizardErrorContext.surface?: "connect" | "submit" | "csv" | "allocate"`.
A `fix[]` entry that presupposes a surface renders **only** when the context names that
surface. **When the context is ABSENT, a surface-conditional bullet is SUPPRESSED** —
fail toward saying less, never toward advising a detour that may be pointless.
Every `buildEnvelope` call site passes its surface (`ConnectKeyStep.tsx:609` and its
siblings).

### Gate C — venue-shaped remedies are gated on a venue CAPABILITY, not on a venue name

Three bullets tell the user to change venue:

| Site | Code | Bullet |
|---|---|---|
| `wizardErrors.ts:484` | `KEY_PROBE_FAILED` | "If it keeps failing, switch to a different exchange or contact support." |
| `wizardErrors.ts:701` | `KEY_RATE_LIMIT` | "If it persists, try a different exchange account or contact support." |
| `wizardErrors.ts:713` | `KEY_NETWORK_TIMEOUT` | "If it keeps failing, switch to a different exchange or contact support." |

**Contract:** add `WizardErrorContext.venue` and a per-venue capability
**`substitutable: boolean`** — default `true` (every ccxt venue byte-unchanged), `false`
for `mt5`. A venue-substitution bullet renders iff `substitutable`.

⛔ **Not an `if (venue === "mt5")`.** That is the instance-not-class defect this repo has
paid for once. The capability-flag shape follows the established `passphraseSecret` /
`requiresSecret` per-venue precedent (`ConnectKeyStep.tsx:44-57`) that MT5-13 already
cites.

Replacement bullet when `substitutable === false` — states the truth and invents no
remedy:
> `This is your broker account, so there is no other venue to try. If it keeps failing, email security@quantalyze.com with the correlation id below.`

### Gate D — the form survives the envelope

On every error path the credential fields keep their values and stay mounted behind the
envelope. Retyping an API secret after a failure our own budget caused is a cost we
impose for no reason.

## Surface 4 — MT5 in the supported-exchanges step (MT5-14 / D-15)

The chips live in `InlineChipGroup label="Supported exchanges"` inside the collapsed
`<details>` "More details (optional)" (`MetadataStep.tsx:446`). The founder opened that
disclosure and toggled sFOX onto an MT5 account chasing an unrelated error — so the
group's honesty is load-bearing.

### The decision: a detected venue is a FACT, not a CHOICE

**Shape carries interactivity** — the same logic `DESIGN.md` uses to split rounded
interactive cards from square data panels.

| | Renders as | Can be toggled |
|---|---|---|
| The venue of the connected key | a **non-interactive `<span>`** carrying the *selected* chip tokens | **No** — there is no button, therefore no disabled button |
| Every other venue | a `<button>` chip, `aria-pressed` | Yes |

| Property | Contract |
|---|---|
| Pinned chip | `inline-flex items-center rounded-md border border-accent bg-accent/10 px-3 py-1.5 text-caption font-medium text-accent` — visually identical to a selected chip (it *is* selected), but it is a `<span>`, so it is not in the tab order and cannot be turned off |
| Provenance eyebrow | Beside the group label: `DETECTED FROM YOUR KEY` — Geist Mono, uppercase, `text-micro`, **eyebrow-std tracking `0.18em`**, `text-text-muted`. This is a data annotation, so it takes the mono voice, not DM Sans |
| Caption under the group | `MetaTrader 5 is included because it is the venue of the key you connected.` — `text-caption text-text-muted`. Venue name interpolated from the key |
| Payload | `supportedExchanges` **always contains the detected venue**; the pinned member is not user-removable, so the strategy can never declare a venue set that excludes its own key's venue |
| Never-asked-twice (D-15) | ⛔ No second venue question anywhere in the flow. The preselect is derived from `detectedExchange`, which `MetadataStep` already receives (`:64`, `:110-113`) |
| Disclosure state | **Stays collapsed** — this phase does not undo Phase 150's cull. The fact is re-stated on `ReviewStep` (`:178-179`, `:240-241`), which already recaps `supportedExchanges` |

## Checker findings folded in (non-blocking, but PLAN THESE)

The checker returned 9 FLAGs. Three change what the planner must build — they are recorded
here because the planner reads this file, not the checker's return.

### ⛔ FLAG-3 — deleting `disabled` WITHOUT widening the guard re-ships the original defect
`MetadataStep.tsx:491` is `disabled={!description.trim() || !categoryId}`. This spec deletes it
(a dead button names nothing — the mechanism that hid the failing field). **But the
`handleSubmit` early-return at `MetadataStep.tsx:222-233` is `.trim()`-ONLY**, and its comment
at `:225-229` justifies that narrowness with *"The Submit button stays disabled until both are
present."* Delete `:491` without widening `:230` and a 2-character description passes `.trim()`
and POSTs — **exactly the WIZFORM-01 defect this phase exists to delete** — with `categoryId`
unchecked entirely.
**Required:** the same client mirror (10 ≤ len ≤ 5000, `categoryId` present) becomes the
`handleSubmit` early-return predicate, and the stale comment at `:225-229` is rewritten in the
same edit.

### FLAG-1 — `AllocateDialog` is the BEHAVIOURAL precedent, not the styling one
D-12 puts the Phase-150 allocation form in scope, but its money input colours via a JS ternary
(`AllocateDialog.tsx:355` — `fieldError ? "border-negative" : "border-border"`), NOT
`aria-[invalid=true]:border-negative`. It is correct today only because `fieldError` also feeds
`Field`'s `error` prop, so this spec's "structurally impossible" invariant is not yet true
there. **Required:** convert that surface to the aria-derived mechanism, and cite the sites that
already work that way — `MetadataStep.tsx:334`, `CsvUploadStep.tsx:624`,
`RenameStrategyDialog.tsx:178`.

### FLAG-5 — character bounds must read from the constant, like durations do
This spec forbids literal seconds in copy because "copy and budget cannot be allowed to drift",
then hardcodes `10` and `5,000`. Apply the same rule: the server bound is `description.length < 10`
plus `MAGNITUDE_CAPS.MAX_DESCRIPTION_CHARS` (`closed-sets.ts:535`, pinned at
`closed-sets.test.ts:323`).
