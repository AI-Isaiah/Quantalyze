# Phase 153.2 Plan 03: The allocation amount's red derives from ARIA and clears live Summary

**The last JS-toggled invalid border in the repo is gone — `AllocateDialog`'s money field now
turns red only as a consequence of the ARIA state `Field` writes, and an amount the user has
already corrected stops reading red the moment it becomes valid instead of waiting for a
second click.**

## Accomplishments

### Task 1 — the border derives, and the error clears live (commit `af61c2fe`)

**(a) The border derives.** The template-literal ternary
(`fieldError ? "border-negative" : "border-border"`) is replaced by a static class string
ending `aria-[invalid=true]:border-negative`, with `border-border` folded back into the base.
The rendered result is unchanged; the *mechanism* is what changed. Previously the red was
correct only by coincidence — `fieldError` happens to also feed `Field`'s `error` prop, so the
two agreed without anything forcing them to. Now `Field` is the sole cause of both the ARIA
state and the colour, which makes a red control with broken a11y wiring **structurally
impossible** rather than merely unlikely (Shared Pattern A / UI-SPEC FLAG-1).

`aria-invalid` is **not** set on the `<input>`: `Field` spreads `...control.props` last, so a
hand-written child prop would win and re-open exactly the hazard being closed. That
prohibition is now recorded in the source comment so the next reader does not "helpfully" add
it.

**The focus-ring run is byte-identical.** `focus-visible:border-border-focus
focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-inset
focus-visible:ring-accent`, `min-h-[44px]`, the radius and the padding all survived untouched —
this file already carried the CORRECT full-opacity inset ring that `MetadataStep` lacked, and
the two files swapped fixes in opposite directions as the plan warned.

**(b) The error clears live.** `fieldError` was set in `handleSave` and cleared only on the
*next* save, so a corrected amount kept its red while the user stared at a value that was
already fine. The `onChange` handler now re-runs `parseAmount` on the new value and takes its
verdict — but **only when a message is already showing**. That single `!== null` guard delivers
both halves of the reveal-timing rule: live-clear after a refusal, and silence before one.

### Task 2 — the rows that can tell the two mechanisms apart (commit `bbdb22cc`)

The pre-existing assertion `expect(input.className).toMatch(/border-negative/)` was a guard
that could not fail in the way that mattered: it matched the hand-toggled ternary exactly as
happily as the derived class, so it could not have caught a revert — or a red field whose
a11y wiring had silently gone. It is now `toHaveAttribute("aria-invalid", "true")` plus
`toContain("aria-[invalid=true]:border-negative")`, with a comment recording why the old one
proved nothing.

Four rows added (three new claims plus the strengthened `it.each`):

| Row | What reds it |
|---|---|
| **Derivation** — `[153.2 FLAG-1] the red border DERIVES from the ARIA state, and points at the visible message` | any break in the chain: `Field` not writing the state, the class not deriving from it, the resting colour becoming conditional again, or `aria-describedby` resolving to a different node than the visible sentence |
| **Live-clear (D-12)** | a correction that does not clear message + red on `change` alone (no blur, no second click) — **and** a clear that swallows the write, since the row then clicks once and demands exactly one fetch carrying `25000` |
| **Swap** (`-5` → `1000000001`) | a blanket `setFieldError(null)` on every keystroke, which would satisfy the clear row while telling a user who typed $1B+1 that their amount is fine until they click again |
| **Silence** | a field that reddens mid-keystroke before any refusal — the reason the re-evaluation is gated at all |

The three claims are deliberately separate rows rather than one long one: the swap row is what
stops the fix degrading into "clear everything", and the silence row is what stops it
degrading into "validate on every keystroke". Neither is provable from the clear row alone.

## Deviations from Plan

**None.** The plan executed exactly as written. Two things it warned about were checked and
found not to apply here:

- **The `noValidate` trap 153.2-01 hit does not exist on this surface.** The plan's phase
  warning asked me to check explicitly rather than assume. `AllocateDialog` renders **no
  `<form>` element** — the CTA is a `type="button"` with an `onClick={handleSave}` inside
  `Modal`'s native `<dialog>`, and the amount input carries no `required` / `min` / `max`.
  Native constraint validation therefore has nothing to intercept, and no `noValidate` was
  needed.
- **`type="number"` input sanitisation** is real but pre-existing and harmless here: jsdom
  blanks a non-numeric value on a `type="number"` input, so the `it.each` `"abc"` row is in
  practice exercising the empty branch. Both branches yield `ERROR_NON_POSITIVE`, so the row
  still asserts a true fact. Every value the new rows use (`-5`, `0`, `25000`,
  `1000000001`) is legitimately typeable into a number input, so none of them depends on that
  behaviour. Left alone under the surgical-changes rule — widening that row is not this
  plan's scope.
