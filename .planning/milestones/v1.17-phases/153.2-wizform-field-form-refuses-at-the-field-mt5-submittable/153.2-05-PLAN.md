<objective>
Close the last path by which a field problem still reaches the user as a page-level envelope: a
server-side rejection of a rule the client mirrors (shape drift, a stale client, a rule that moves
server-first) is **routed back to the field by code**.

Purpose: UI-SPEC Surface 2 — *"each field-level 400 code maps to exactly one field id. A code with
no field mapping is a planner bug, not a runtime fallback to the envelope."* 153.1 made the route
honest (nine `validatePayload` arms now carry codes, seven of them field-level); 153.2-01/02 made
the client refuse first. This plan makes the two agree when they disagree — which is exactly the
state the founder was in: a message about the description, rendered where the description was not.

Output: a `ReadonlyMap<WizardErrorCode, MetadataFieldId>` in `SubmitStep` with a totality assertion,
the handoff through `WizardClient` back to the metadata step, and `MetadataStep` revealing and
focusing the named field on arrival.

⛔ **Prerequisites.** Phase 153.1 must be complete (the seven field-level codes and the route arms
that emit them) and 153.2-01/02 must be complete (the per-field message map and the
first-invalid-control focus this plan reuses). ⛔ `SubmitStep.tsx`'s roster
(`KNOWN_FINALIZE_CODES`) is 153.1-05's — this plan touches ROUTING only and must not add or remove
a roster member. ⛔ Nothing in `finalize-wizard/route.ts` is edited here.

⚠️ **Deliberate widening of the owned surface, recorded:** this plan edits `WizardClient.tsx`, which
the sub-phase's ownership list does not name. Routing a field-level code back to its field requires
a step change, and `WizardClient` is the only owner of `step`. No other 153.x plan touches this
file, so there is no collision — but the widening is stated here rather than discovered in review.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `finalize-wizard` response → wizard UI | a server-controlled `code` (and, today, a server-controlled `error` string) crosses here |
| `SubmitStep` → `WizardClient` → `MetadataStep` | a field id derived from that code drives a step change and a focus move |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-153.2-17 | Information disclosure | the message rendered at the field | mitigate | The field renders `formatKeyError(code).title` from the local copy table ONLY. ⛔ The response's `error` string is never rendered at a field — that is the path by which a raw exception, HTTP status, module path or env-var name would reach a user (UI-SPEC §Copywriting Contract). The diagnostics `code`/`correlation_id` stay inside the existing collapsed `<details>` on the envelope path, unchanged. |
| T-153.2-18 | Spoofing | an attacker-influenced `code` steering the UI | mitigate | Routing is keyed on `FIELD_BY_CODE`, a closed `ReadonlyMap` over `WizardErrorCode`; an unrecognised value cannot select a field and falls through the existing roster check to `UNKNOWN`. The blast radius of a forged code is at most "the user is shown one of our own copy sentences beside one of our own fields". |
| T-153.2-19 | Denial of service | a code the map does not carry silently rendering nothing | mitigate | The totality assertion plus its vacuity floor make an unmapped field-level code a RED test rather than a runtime fallback; and the runtime path still renders the envelope when `onFieldLevelError` is absent, so no failure is ever swallowed. |
| T-153.2-20 | Repudiation | telemetry lost on the new branch | mitigate | `wizard_error` fires with the surfaced `code` on BOTH branches, so the funnel cannot lose sight of field-level refusals — the exact blind spot the `UNKNOWN`-collapse class created. |
| T-153.2-SC | Tampering | npm/pip/cargo installs | mitigate | **This plan installs nothing.** Any install would require RESEARCH.md's Package Legitimacy Audit table and a blocking human checkpoint first. |
</threat_model>
