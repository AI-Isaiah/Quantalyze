# Phase 153.2 Plan 05: The form refuses at the field — even when the SERVER is the one refusing Summary

**A rejection `finalize-wizard` makes about one metadata field now takes the user back to
that field — revealed, red, focused, its disclosure opened and every value they typed
still on the form — instead of a full-page envelope that names no field; and an unmapped
field-level code is a RED test rather than a silent fallback to that envelope.**

## Performance

- **Completed:** 2026-08-09

- **Files modified:** 10

## Accomplishments

### Task 1 — `FIELD_BY_CODE`, and a totality assertion that reds by name (`e02bc8a6`)

`FIELD_BY_CODE` is a `ReadonlyMap<WizardErrorCode, MetadataFieldId>` with eight entries,
each naming the `validatePayload` arm it comes from in the roster's own "admitted in the
same commit" comment discipline. `SubmitStep` routes on it **after** `surfaced` is
computed, and **never on the status**: `validatePayload` answers 400 today, but a rule
that moves arms — or a route that starts answering 422 — must not silently revert a field
refusal to a full-page dead end.

Everything else on that path is byte-identical: the wire-code translation, the roster
membership check, `UNKNOWN` as the fallback, the correlation id and the `Retry-After`
read. `wizard_error` was **hoisted above the split** so it fires on both branches with the
same `code` dimension (T-153.2-20) — firing it only on the envelope branch would have made
every refusal the new routing handles invisible to the funnel the day it shipped.

`onFieldLevelError` is optional, and its absence falls through to today's envelope with a
comment saying why: a refusal shown in the wrong place is bad; a refusal shown nowhere is
worse.

**The field-id union was widened 4 → 6, and that is the load-bearing part.**
`METADATA_NAME_INVALID` and `METADATA_CAPITAL_OWNERSHIP_INVALID` belong to fields this
form has no client rule for — the codename is a `<select>` over a closed list and the
capital question is defaulted and uncleanable, so neither server arm is reachable by any
value the form can produce. But **"no client rule" and "no field" are different facts**,
and conflating them is exactly what sent a description refusal to an envelope that named
no field. Both arms still FIRE (a stale client, a payload shape drift, a constant that
moves server-first), and when they do the refusal now has somewhere to land. The union is
`export`ed and imported by `SubmitStep`, so the two sides cannot drift into different
spellings of the same field — a routing bug no type error would catch.

Two supporting conversions came with it: the codename moved off the `Select` primitive
onto `Field` + a bare `<select>` (the primitive colours its border from a JS expression
and never writes `aria-invalid` — the FLAG-1 shape 153.2-02 converted three other controls
for), and `CapitalOwnershipRadioGroup` gained an optional aria-wired `error` slot. The
group cannot be wrapped in `Field` — that primitive wires one `<label htmlFor>` to one
control `id`, and a radio group has neither — so the same contract is honoured on the
`role="radiogroup"` element instead. Absent `error` ⇒ byte-identical to before, and the
`MarkOwnershipDialog` mount passes nothing.

**The totality assertion** derives the field-level vocabulary from `WIZARD_ERROR_COPY` at
runtime (`startsWith("METADATA_")`) rather than hand-listing it, so a code minted without
a field reds **by name**. Beneath it sits an anti-vacuity floor (`>= 7`): a derivation that
matched nothing would satisfy "every field-level code is mapped" for the worst possible
reason and go on satisfying it forever. Three companion rows pin the converse (every key
is a real copy member), the field-id range (against a **hand-typed** array, deliberately
not imported from the module under test) and the two behaviour branches.

### Task 2 — the handoff: back to the step, into the field, values intact (`ac2cd539`)

`WizardClient` holds `metadataServerFieldError` and owns the step change, because it is
the only owner of `step`. The `persistPointer("metadata", …)` companion is not
decoration: without it the resume pointer still reads `submit`, so a reload would drop the
user back on a submit screen carrying a refusal they can neither see nor fix.

⛔ **`metadataDraft` is NOT reset** (Gate D). The user is returned to a populated form with
one field flagged — a form that loses its contents on a validation failure is a *worse*
outcome than the envelope being replaced. The refusal is cleared on completion of the step,
on `onBack`, and on any stepper navigation away from metadata, so it cannot outlive the
edit that fixed it.

In `MetadataStep` the server's code **merges into the existing `fieldErrors` map** rather
than rendering beside it. That is the whole design: the inline message, the aria-derived
red border, the submit predicate, the first-invalid-control focus and the summary line all
read one derivation, so a refusal that came from the server behaves in every one of those
respects exactly like one the client raised. A parallel rendering path is how a message
ends up somewhere its own field's border and its own submit gate do not agree with. The
client mirror wins via `??` — it judges the value on screen *now*; the server judged the
value that was submitted.

Arrival reveals through `markBlurred` (the same flag a blur sets, so there is no second
reveal mechanism) and calls `revealAndFocus` — 153.2-02's orchestration, **extracted so
both callers share it** rather than duplicated. A container ref resolves to its first
focusable descendant, stated as a general rule rather than a branch on the capital
question's name; a `<div>.focus()` would have been a silent no-op that every jsdom
`aria-invalid` assertion still passed.

The refusal is retired on the **first edit** of its field, unconditionally — not on the
edit becoming valid. A message the user cannot clear by acting on it is a dead end, and
the client mirror re-raises its own code in the same render when the new value is wrong
for a different reason (pinned by its own row, so "clears on edit" cannot become "goes
quiet on edit"). The effect's dependency list is the prop only, and the comment says why:
`revealAndFocus` is re-created every render, so including it would yank focus back to the
flagged field on every keystroke.

### Task 3 — the envelope names its venue, its surface and the count (`d853052c`)

⭐ **WIZFORM-03 has been shipped-and-inert since 153.1-03.** The `fixRequires` class filter
and all three venue-conditional entries were correct and live — but **zero of fourteen
`buildEnvelope` call sites passed a venue**, and venue-absence deliberately preserves
incumbent ccxt copy. So the mechanism worked perfectly and changed nothing: an MT5 user
went on reading *"switch to a different exchange"* for an account that **is** the venue.
`venue: snapshot.exchange` is what turns it on for this surface. `surface: "submit"`
restores `SERVICE_UNREACHABLE`'s `/strategies` bullet, which Gate B suppressed *everywhere*
until a call site named itself. `charCount` is passed for the fallback path, where a
description bound can still build an envelope.

Four rows pin it, including two controls that a one-sided implementation would fail: a
ccxt venue keeps the incumbent bullet **byte-for-byte**, and an *unresolved* venue keeps
it too (absence answers the predicate's default, which is what protects every pre-153.1
caller's copy).

### Task 4 — the limiter's two deny arms stop answering code-less, 5 → 3 (`d07b2a9e`)

Both sat on `KNOWN_CODELESS_FINALIZE_REJECTIONS`. A code-less rejection renders the UNKNOWN
card — *"We could not classify this failure"* — for a failure the route classified well
enough to pick a status and write a sentence about; and UNKNOWN's copy is **recoverable**,
so both arms handed the user a Retry button: correct for a throttle, a control that cannot
work for a misconfiguration.

⚠️ **The ledger named the wrong code for the 429.** It proposed `KEY_RATE_LIMIT` "because
that is what the key routes answer". That entry opens *"The exchange rate-limited this
request"* — false for `userActionLimiter` on our own per-user key, where the exchange is
never contacted. `RATE_LIMITED` is the member 140.3-01 wrote for our own cap (*"the cap is
ours, not your exchange's"*), and it needs **no roster edit**: `SEAM_CODE_TO_WIZARD_CODE`
maps it to itself and the translation runs before the roster check. `SEAM_MISCONFIGURED`
(the 503) is already a roster member and non-recoverable, so no Retry renders at all.

⚠️ **The tidy refactor was tried and rejected on evidence.** Routing both arms through the
`rateLimitDenyJson` chokepoint (the 140.4-13 idiom) was implemented first, and **measured**:
it drops `finalize-wizard`'s derived rejection-site count from **32 to 30**, because the
class scan finds sites by reading 4xx/5xx `NextResponse.json` literals out of source. A
helper call is invisible to it, so both arms would have left the population the guard
watches — and a guard that stops seeing an arm is exactly how the next code-less rejection
ships green. The explicit form was kept, with that measurement written at the site.

The arithmetic is the proof nothing was invented: `expectedSites` 27 → **29**, the ledger
5 → **3**, and `EXPECTED_FINALIZE_REJECTION_SITES` **unchanged at 32**. A plan that had
added two rejections to "fix" them would have moved the total too.
