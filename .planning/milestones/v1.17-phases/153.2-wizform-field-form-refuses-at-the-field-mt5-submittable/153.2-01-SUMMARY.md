# Phase 153.2 Plan 01: The form refuses at the field — description Summary

**A two-character description is now refused inline at the description field with the rule and the user's own count, and the dead submit button that hid which field was wrong is gone — both in the same commit, as FLAG-3 requires.**

## Accomplishments

### Task 1 — the indivisible edit (commit `75556898`)

The four edits FLAG-3 forbids splitting landed together:

- **`validateDescription(value)`** — a module-level pure function returning
  `WizardErrorCode | null`, reading `MIN_DESCRIPTION_CHARS` / `MAX_DESCRIPTION_CHARS`
  from `MAGNITUDE_CAPS`. Its docblock states that `finalize-wizard`'s `validatePayload`
  remains authoritative (T-153.2-01), so no later reader deletes the server arm as
  redundant.
- **`handleSubmit`'s predicate widened** to `validateDescription(description) !== null ||
  !categoryId`. `categoryId` is checked here for the first time — until now it was
  covered only by the `disabled` gate being deleted in the same commit.
- **The `disabled` prop deleted** and its WR-03 comment rewritten to state the new rule
  and why: a dead button names nothing, and naming nothing is the mechanism that sent the
  founder to change unrelated fields (D-13). No `aria-disabled` substitute.
- **The stale `handleSubmit` comment rewritten** — its premise ("The Submit button stays
  disabled until both are present") became false the moment the gate went, and leaving it
  would have invited the next reader to restore the gate.
- **The focus ring upgraded** on the description textarea to
  `focus-visible:border-border-focus focus-visible:outline-none focus-visible:ring-2
  focus-visible:ring-inset focus-visible:ring-accent`, keeping the trailing
  `aria-[invalid=true]:border-negative` so the red border still derives from ARIA
  (Shared Pattern A). `ui/Button.tsx` and `ui/Modal.tsx` were left alone as instructed.

### Task 2 — the message states (commit `2fc3850f`)

- The field renders `formatKeyError(code, { charCount }).title` — one sentence — through
  `Field`'s `error` prop. It previously rendered `.cause`, a multi-sentence paragraph
  containing "Nothing was saved, and everything you typed is still on the form", which is
  nonsense under a control the user is still typing into.
- `charCount` is the length the mirror itself measured, so the number in the sentence and
  the number the guard compared are the same number by construction.
- An always-visible hint (`At least {MIN} characters.`) composed from the constant per
  FLAG-5, wired into `aria-describedby` ahead of the error id by `Field`.
- All four reveal-timing events documented against the two existing flags; the derivation
  stays a render-time computation, which is precisely what makes the live-clear rule work.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] Native `required` intercepted the EMPTY refusal state before `handleSubmit` ran**

- **Found during:** Task 1, when the new "Submit is enabled but refuses when description
  and categoryId are both absent" row failed with `aria-invalid` never set.
- **Issue:** The description textarea carries `required`. Once the `disabled` prop was
  deleted, clicking submit with an empty description triggered **native constraint
  validation**, which blocks form submission entirely — so `handleSubmit` never ran, no
  inline message appeared, and the user got the browser's own bubble instead. This is not
  a test artefact: it is the shipped behaviour in every browser. It also meant the three
  refusal states would have behaved *differently from each other* — too-short and
  too-long would show the inline message, empty would show a native tooltip. A
  tooltip-only error is item 2 on the UI contract's forbidden list, and two gates
  disagreeing about one field is the exact drift class WIZFORM-01 exists to close.
- **Fix:** `noValidate` on the `<form>`, making `validateDescription` the single gate.
  `required` is kept on the control for AT semantics. Our predicate is strictly stronger
  than `required` — it also refuses whitespace-only and under-length text, both of which
  native validation accepts.
- **Files modified:** `MetadataStep.tsx`
- **Commit:** `75556898`

**2. [Rule 3 — Blocking] Four `toBeDisabled()` assertions, not the two the plan named**

- **Found during:** Task 1.
- **Issue:** The plan identified the two rows at `:153` and `:162`. Two more asserted the
  same dead-button behaviour: `[WR-04] surfaces an honest block when categories load to an
  empty (readable) set` (`:127`) and `[OWN-03] leaves the submit gate unchanged when the
  question renders` (`:656`). Both would have reddened.
- **Fix:** All four re-cut with their reasoning rewritten rather than deleted, each now
  asserting the behaviour the `disabled` prop stood for: the control is reachable,
  activating it does not reach `onComplete`, and the field says why. The OWN-03 row was
  renamed to `does not make the capital question a submit precondition`, which is the
  claim it was actually making.
- **Files modified:** `MetadataStep.test.tsx`
- **Commit:** `75556898`

**3. [Rule 3 — Blocking] Two acceptance greps matched the plan's own required prose**

- **Found during:** Task 1 verification.
- **Issue:** The plan's grep gates for `disabled=` and `ring-accent/20` do not filter
  comment lines (only the `MAGNITUDE_CAPS` gate does). The rewritten comments the plan
  *mandates* — which must name what was deleted and why — therefore matched their own
  gates.
- **Fix:** The prose was reworded to describe the removed code without quoting it
  verbatim, so both greps return nothing on source and on comments alike. This applies the
  same reasoning the plan states for gate B: "the file's own prose cannot satisfy or
  invalidate the gate". No behavioural content was lost from either comment.
- **Files modified:** `MetadataStep.tsx`
- **Commit:** `75556898`

**4. [Rule 2 — Missing coverage] Added two boundary-acceptance rows the plan did not list**

- **Found during:** Task 1 and Task 2.
- **Issue:** A refusal-only test suite is satisfied by a mirror that refuses
  *everything* — the "guard that cannot fail" shape inverted. The plan's rows prove
  `< MIN` and `> MAX` reject but nothing proved `= MIN` and `= MAX` pass, which is where
  the server's inclusive bounds actually sit and what the copy claims ("at least 10",
  "or fewer").
- **Fix:** Added `a description at exactly the minimum length is ACCEPTED` and
  `a description at exactly the upper bound is accepted`.
- **Files modified:** `MetadataStep.test.tsx`
- **Commits:** `75556898`, `2fc3850f`

**5. [Rule 3 — Blocking] `aria-describedby` became two ids once the hint landed**

- **Found during:** Task 2.
- **Issue:** The Phase-53 test did `document.getElementById(describedBy)` against the raw
  attribute. With a hint present, `Field` joins `{id}-hint {id}-error`, so that lookup
  returns `null`.
- **Fix:** A local `errorNodeFor(control)` helper that splits the attribute and selects
  the `-error` id. Used by every message assertion, and asserted to be `null` in the two
  silence rows — so the helper cannot mask a missing message.
- **Files modified:** `MetadataStep.test.tsx`
- **Commit:** `2fc3850f`
