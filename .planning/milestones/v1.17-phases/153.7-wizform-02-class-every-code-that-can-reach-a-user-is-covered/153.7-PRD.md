# Phase 153.7 — WIZFORM-02-CLASS: every code that can reach a user is covered

**Source:** `TODOS.md` FIX NOW #6 (boundary decision made 2026-08-13, autonomous, reversible)
**Raised by:** retroactive Phase 153 SPAN verification — `.planning/phases/153-wizform-form-errors-belong-on-the-form-mt5-declarable/153-VERIFICATION.md`, status `failed`, 5/6 requirements
**Requirement:** WIZFORM-02 — the ONE requirement the 153 span failed

---

## The defect, stated precisely

A server-classified failure reaches the user as `code: UNKNOWN`.

`analytics-service/routers/exchange.py:866` raises
`service_error(500, "MT5_GATEWAY_UNCONFIGURED", dependency="mt5-gateway", retryable=False, …)`
with operator-directed copy — fully classified — and the wizard renders
*"We could not classify this failure, so we cannot tell you what happened or whether your last
action took effect."*

**THIRD live instance.** Hit by the founder on PROD 2026-08-12 while dogfooding MT5, after the
whole 153 span had shipped. Reproduced from HEAD by direct measurement (`153-VERIFICATION.md`,
probes P1/P2).

⭐ **The derived-roster remedy was genuinely built and genuinely works.** Falsified: mutating an
emitted code literal in `finalize-wizard/route.ts` reds two assertions by name. The mechanism is
sound. Its **reach** is wrong.

It misses this code for **two structural reasons, either sufficient alone**:

| Guard | Directory root | Emission shape matched |
|---|---|---|
| `src/lib/wizardErrors.invariant.test.ts` (`ROUTES`, :204-272) | 3 Next route files | `NextResponse.json({code, error}, {status})` |
| `src/lib/seam-venue-vocabulary.invariant.test.ts` (`SERVICES_ROOT` :70, `ASSIGNMENT_RE` :94) | `analytics-service/services/**/*.py` | `error_code =` / `error_code=` / `result["error_code"] =` |

`routers/exchange.py` is in **neither** — wrong root (`routers/`, not `services/`) **AND** wrong
shape (a **positional** argument to `service_error(...)`, not an `error_code =` assignment).
Relocating the file alone would not make it visible. Teaching the shape alone would not either.

⭐ **The actual defect is an ASYMMETRY, above any individual missing code.** Measured from HEAD,
both `MT5_GATEWAY_UNCONFIGURED` and its retryable sibling `MT5_GATEWAY_UNREACHABLE` classify to
`{ code: "UNKNOWN", status: 500 }`, and both are absent from **both halves** of the coverage law
— no verdict row in `VENUE_WIRE_CODE_TO_VERDICT` (`wizardErrors.ts:2682-2730`) *and* no recorded
no-verdict in `VENUE_WIRE_CODES_WITHOUT_VERDICT` (`:2746-2795`). That double absence is the one
state the coverage law was built to make impossible, so their absence could never have been loud.

---

## Locked decision (reverse only with founder sign-off)

⭐ **The coverage law's boundary becomes "every code that can reach a user-facing surface"**, not
"codes emitted in a particular directory in a particular syntactic shape".

**Rationale:** the current boundary is an artifact of *how the scanners were written*, not of any
product rule. No one ever decided that a 500 from `routers/` deserves less honesty than a 400 from
a Next route, and the user cannot tell the difference. The requirement is written about *what the
user sees and what the server classified*. Both scanners already prove the mechanism works; only
their reach is wrong.

---

## Scope — the five steps

1. **Widen the Python scanner's root** from `analytics-service/services/**` to
   `analytics-service/**`.
2. **Teach it the positional shape** `service_error(<status>, "<CODE>", …)`, not just
   `error_code = "<CODE>"` assignments.
   ⚠️ Steps 1 and 2 are the two **independent** misses — doing either alone still leaves
   `routers/exchange.py` invisible.
3. **Re-cut the pinned code tables** (the 153.1 `EXPECTED_TABLE_SIZE` family) — **never delete
   them**. The re-cut is the deliberate act that records the widening.
4. **Add a coverage assertion that FAILS when a discovered code has neither a verdict row nor a
   recorded no-verdict.** ⭐ This is the headline fix: today's absence was silent precisely because
   the code was missing from *both* halves.
5. **Falsifiability:** add a new `service_error(...)` code in `routers/` with no verdict row and
   prove the gate reds. **A fix that cannot fail this way has not closed the class.**

Alongside the mechanism, the two known codes get a disposition — a wizard member, or an explicit
`VENUE_WIRE_CODES_WITHOUT_VERDICT` row with a measured reason:
- `MT5_GATEWAY_UNCONFIGURED` — permanent, operator-directed, not retryable
- `MT5_GATEWAY_UNREACHABLE` — transient, retryable

Emitters for reference: `MT5_GATEWAY_UNCONFIGURED` at `routers/exchange.py:465`, `:477`, `:620`,
`:868`; `MT5_GATEWAY_UNREACHABLE` at `:628`.

Also in scope, from the verification's `missing` list:
- The three code-less `finalize-wizard` rejections (D-153.2-D — 500 draft-load, 500 finalize-RPC,
  502 upstream-shape), each needing a copy member.
  `KNOWN_CODELESS_FINALIZE_REJECTIONS = 3` (`wizardErrors.invariant.test.ts:516`) moves accordingly.
- The terminal arm at `src/app/api/strategies/create-with-key/route.ts:1057`, `:1094`, which
  discards the honest machine code: `classifyKeyValidationError(err)` reads `err.seamCode` only
  through `VENUE_WIRE_CODE_TO_VERDICT`, falls through to a substring cascade over the human
  sentence, and answers `{ code: "UNKNOWN", status: 500 }`.

## Scope fence — what is explicitly OUT

⛔ **"Add two rows" is NOT the fix.** Landing `MT5_GATEWAY_UNCONFIGURED` and
`MT5_GATEWAY_UNREACHABLE` as verdict rows *without* steps 1/2/4 is **exactly the fourth instance**
of this defect. Do not bundle them as a shortcut.

⛔ **Do NOT re-open WIZFORM-05.** The 45,169 / 45,159 / 45,177 ms figures from the same incident
are `_MT5_VALIDATE_INITIALIZE_TIMEOUT_MS = 45000` (`routers/exchange.py:96`) — the innermost,
deliberately-first-firing layer of the D-02/D-03 nested chain, sized so the failure carries a real
MT5 code. The verdict arrived at ~45 s against a 120 s budget; the pre-153 30 s inversion is gone
(`worst_case_ms == 105_000 < 120_000`, 67 pytest green). What failed *after* arrival is WIZFORM-02.
**Lengthening the budget fixes nothing.**

⛔ **Do not re-verify 153.6.** It is `passed_with_concerns` (24/25) and is an INPUT here.

## Success criteria (what must be TRUE)

1. A code emitted anywhere under `analytics-service/**` — via **either** `error_code =` assignment
   **or** positional `service_error(<status>, "<CODE>", …)` — is in the derived population.
   Proven by both shapes appearing in the discovered set, not by inspection.
2. A discovered code with **neither** a verdict row **nor** a recorded no-verdict **fails CI, by
   name**. This is the assertion whose absence made the live defect silent.
3. A newly-added `service_error(...)` code in `routers/` with no disposition **reds the gate** —
   demonstrated, not asserted. (Step 5. The falsifier for this whole phase.)
4. `MT5_GATEWAY_UNCONFIGURED` and `MT5_GATEWAY_UNREACHABLE` each have a disposition, and the
   mt5-gateway fault family no longer renders `code: UNKNOWN` on a user-facing surface.
5. The pinned code tables are **re-cut, not deleted**, and the new sizes are recorded.
6. Phase 153's parent checkbox becomes tickable — WIZFORM-02 is the only thing holding it.

---

## Risk

⚠️ The 153.1 pinned-table family exists to make vocabulary changes deliberate. Widening the
scanner will discover codes beyond the two known ones. Each newly discovered code needs a real
disposition — **not** a blanket `WITHOUT_VERDICT` sweep to make CI green. A sweep would reproduce
the defect in its most general form: the law would cover everything and assert nothing.

⚠️ `analytics-service/**` is a wider root than `services/**` and may pull in test fixtures or
scripts that mint codes never reachable by a user. Excluding them is legitimate; excluding them
**silently** is not. Any exclusion is recorded with its reason.
