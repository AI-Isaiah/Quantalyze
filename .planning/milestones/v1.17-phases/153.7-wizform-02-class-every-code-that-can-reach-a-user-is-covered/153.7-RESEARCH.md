## Summary

The phase's headline mechanism — *"a discovered code with neither a verdict row nor a recorded
no-verdict fails CI by name"* — **already exists and is already correct in form**. It is
`seam-venue-vocabulary.invariant.test.ts`'s `it("EVERY derived code has an explicit disposition …")`,
which filters on `!VENUE_WIRE_CODE_TO_VERDICT.has(code) && !VENUE_WIRE_CODES_WITHOUT_VERDICT.has(code)`
and asserts the result is `[]`, naming the offenders. Nothing needs inventing. **The entire defect
is the population it runs over.** A plan that writes a new both-halves assertion beside the existing
one has added a duplicate and moved nothing.

The population is wrong along **one** axis, not two. Measured: widening the root from
`analytics-service/services/**` to `analytics-service/**` **adds zero codes** — every `error_code =`
assignment outside `services/` is literal-less. All 20 new codes arrive from the **shape** widening
(the `service_error(...)` call family). The CONTEXT's "two independent misses" framing is correct
about *why `routers/exchange.py` is invisible* (it fails both filters) but is **not** correct as a
description of where the population comes from: the root widening is necessary-but-empty, the shape
widening is where every discovery is. Both are still required — the shape scan has to be *rooted*
somewhere that includes `routers/` and `main.py`.

Size of the work, measured rather than estimated: the widened population is **37 distinct codes**
(up from 17). **20 are new and all 20 are currently undisposed** — zero verdict rows, zero recorded
no-verdicts. Eight of them were probed live through `classifyKeyValidationError` at HEAD and **all
eight answer `{ code: "UNKNOWN", status: 500 }`** — not two codes, an eight-code family, including
the 424 `EXCHANGE_PROBE_FAILED` which is the most ordinary venue failure the wizard has.

**Primary recommendation:** three plans. Plan A = scanner reach + pin re-cut + the falsifier
(mechanism only, zero user-visible change, must land first and must red before it greens). Plan B =
the 20 dispositions, split by *which classifier the code actually reaches* — a distinction that
decides verdict-row-vs-no-verdict-row per code and is the thing a blanket sweep would erase.
Plan C = the three code-less `finalize-wizard` rejections + the `create-with-key` terminal arm and
its byte-identical twin at `composite/add-key`.

## Q3 — What is the robust way to match the positional shape?

### The real call shapes, enumerated (not assumed)

| Property | Measured reality |
|---|---|
| Multi-line | **Yes, overwhelmingly.** 22 of 41 regex-matched sites carry an argument >60 chars; every `routers/*` site is written one-argument-per-line across 5–8 lines. |
| Status literal? | Yes at every **production** site (400/401/422/424/429/500/503). Non-literal only inside `error_contract.py` itself (`status_code: int` pass-through in the `def`). |
| Code literal? | Yes at every production site except `error_contract.py`'s own two internal `service_error_body(code, …)` forwards. |
| Argument **position** varies by callee | ⚠️ **`service_error_body(code, …)` takes the code FIRST** — there is no status argument. `service_error` / `service_error_response` take `(status, code, …)`. A single "second positional argument" rule is wrong for one of the three. |
| Keyword form | `VenueTransientHTTPException(code="X")` is keyword-only (`def __init__(self, *, …)`). |

### Regex vs AST — measured, not argued

Running an identical population through both:

| | sites found | false positives |
|---|---|---|
| Regex over `stripCommentsPreserveLines(src,"py")` | **41** | **9** |
| Python `ast` | **32** | **0** |

The nine regex false positives are three distinct classes, all live in this tree:

1. **Definition sites (3).** `def service_error(`, `def service_error_response(`,
   `def service_error_body(` in `services/error_contract.py:230/274/303` match a naive
   `service_error\s*\(` needle.
2. **Inside string literals (6).** `stripCommentsPreserveLines(src,"py")` blanks `#` comments and
   triple-quoted strings **but deliberately preserves ordinary string contents** (its docblock,
   semantics rule 2). So `"Use service_error() for 5xx. got {status_code!r}"`
   (`error_contract.py:435`) and five sentences in `tests/test_raw_5xx_census.py` (`:193 :412 :496
   :706 :793`) all match.
3. **Wrong argument slot** — not a false *positive* but a false *reading*: a `service_error_body`
   call scanned as `(status, code)` yields the code in the status slot.

### The repo already has BOTH conventions — and they are in different languages

- **TypeScript-side convention (what the two guards under change use):**
  `stripCommentsPreserveLines(src, "py"|"ts")` from `src/lib/source-scan.ts`, then a regex with a
  **depth-aware window** (`rhsWindow`, :115-128) so a multi-line parenthesised expression is one
  unit. Every TS guard that reads Python does this. `source-scan.ts` is COVERAGE-LAW ROW 1 for its
  importers and imposes a **vacuity-fence obligation** on every caller (a hand-typed floor).
- **Python-side convention:** `analytics-service/tests/test_raw_5xx_census.py` — a full `ast`-based
  census over `routers/**`, `services/**` and `main.py`, **"skipping any path containing a `tests`
  segment"**, keyed on `(module basename, enclosing function name, status)` and **never on a line
  number** ("this programme measured 19 line citations of which 5 were wrong"). Blind spots are
  pinned by hand-typed constants. It is a `collections.Counter`, not a `frozenset`, so multiplicity
  survives.

### Recommendation

**Stay in TypeScript, extend the existing depth-aware technique.** The disposition assertion must
compare against `VENUE_WIRE_CODE_TO_VERDICT` / `VENUE_WIRE_CODES_WITHOUT_VERDICT`, which are
TypeScript values. Emitting a manifest from a Python AST guard and reading it in TS would create the
second source of truth this whole coverage law exists to prevent, and would make the TS assertion
green whenever the manifest is stale.

The `rhsWindow` depth-tracker already in the file generalises to a **balanced-paren argument
extractor** in ~20 lines (demonstrated working in the harness), which handles multi-line calls by
construction and needs no character cap. Harden it against the three measured classes:

| Hazard | Guard, stated as an assertion not prose |
|---|---|
| `def` sites | Require the match not be preceded by `def\s+`. SELF-TEST both polarities. |
| Inside a string literal | Require the callee to be at statement/expression position — cheapest robust rule: the character before the identifier must not be inside an open quote on that logical line. **Or** simply exclude `error_contract.py` (the definition module) and `tests/**` and pin the exclusion; that alone removes all 6 measured cases. Prefer a SELF-TEST fixture containing `"… service_error() …"` inside a string, asserting it yields nothing. |
| Per-callee argument slot | A table `{service_error: 1, service_error_response: 1, service_error_body: 0, VenueTransientHTTPException: "kw:code"}`, not a constant `1`. SELF-TEST one fixture per callee. |
| Non-literal code arg | Must be **counted, not dropped** — into the same literal-less blind-spot pin the assignment scan already keeps. Otherwise a future dynamic router code silently shrinks the population. |

⛔ Do **not** add a `[\s\S]{0,N}?` character cap like `EMITTER_BODY_MAX_CHARS`. That cap exists
because the Next-route matcher has no bracket structure to lean on; the Python calls do. A cap here
would recreate the exact "one long detail string goes invisible" failure that
`wizardErrors.invariant.test.ts:1126-1173` documents.

## Q5 — The correct shape for the both-halves assertion

### It already exists, and it is already the right shape

`src/lib/seam-venue-vocabulary.invariant.test.ts:222-240`:

```ts
it("EVERY derived code has an explicit disposition — a verdict row or a reasoned exemption", () => {
  const undisposed = [...derived]
    .filter((code) => !VENUE_WIRE_CODE_TO_VERDICT.has(code)
                   && !VENUE_WIRE_CODES_WITHOUT_VERDICT.has(code))
    .sort();
  expect(undisposed, `These error_codes are EMITTED by analytics-service and TypeScript has
    no explicit answer for them …`).toEqual([]);
});
```

This is *exactly* "neither half ⇒ fail CI, by name" — sorted array, not a set, "so the failure
message NAMES what moved" (:217-218). **No existing assertion half-covers it; this one fully covers
it.** The reason it did not fire for `MT5_GATEWAY_UNCONFIGURED` is one identifier: `derived`, built
from `deriveEmitterSites()`, which is rooted at `SERVICES_ROOT` and matches only `ASSIGNMENT_RE`.

**⛔ The single most important instruction for the planner:** the work item is *"`derived` gets
bigger"*, **not** *"add a both-halves assertion"*. A plan that adds a second assertion beside this
one has produced a duplicate that will pass for the same reason the original does — and will look
like progress in a diff.

Three sibling assertions in the same file are load-bearing under the widening and must be re-reasoned,
not merely left alone:

| Assertion | Line | Interaction with the widening |
|---|---|---|
| "the derived population matches the hand-typed roster, member for member" | :216-220 | The oracle-independence assertion. Re-cut `EXPECTED_EMITTED_CODES` 17 → 37. ⛔ Never `[...derived]`. |
| "no exempt code is a fossil — every exemption names a code that is still EMITTED" | :263-270 | **Constrains Group B.** A `WITHOUT_VERDICT` row may only be written for a code the widened scan actually discovers. All 20 qualify. But it also means: if the shape scan is later narrowed, 12 rows become fossils and red. Good. |
| "every exemption reason is substantive" (`reason.length > 80`, no "todo") | :254-261 | Each of the ~12 Group-B reasons must be a real sentence >80 chars. This is the enforcement that makes a blanket sweep expensive by design. |
| "no code is BOTH mapped and exempt" | :242-252 | Unchanged; keeps A and B disjoint. |

### Where a genuinely NEW assertion is warranted

Not a second both-halves check — a **reach** check, so that the population itself cannot silently
shrink back:

- Pin the **set of roots and callees** the discovery uses (hand-typed), so removing `routers/` or
  dropping `service_error_response` from the callee table reds by name rather than shrinking the
  population quietly. This is the mirror of `dynamicishByFile`: today nothing asserts *where* the
  scanner looked.
- Assert **both shapes appear in the discovered set** (PRD success criterion 1, "proven by both
  shapes appearing in the discovered set, not by inspection"): e.g. `derived.has("MISSING_SCOPE")`
  (assignment shape) **and** `derived.has("MT5_GATEWAY_UNCONFIGURED")` (call shape). Two lines,
  and it makes "the shape matcher silently stopped matching" impossible to ship green.

## Q7 — The `create-with-key` terminal arm, and the twin

### How the honest `err.seamCode` is lost — the exact four steps

1. `analytics-client.ts:556-560` constructs `new AnalyticsUpstreamError(seamHumanMessage(error) ?? …,
   res.status, seamErrorCode(error), seamDependencyName(error))`. The wire code survives to
   TypeScript as `err.seamCode`. **Nothing is lost here.**
2. `wizardErrors.ts:2865-2874` — `classifyKeyValidationError` reads it:
   ```ts
   const seamCode = (error as { seamCode?: unknown } …)?.seamCode;
   if (typeof seamCode === "string") {
     const verdict = VENUE_WIRE_CODE_TO_VERDICT.get(seamCode);
     // No `??` fallback here BY DESIGN …
     if (verdict !== undefined) return verdict;
   }
   ```
   The table has no row → **no short-circuit, deliberately** (the comment says so). `seamCode` is
   never read again anywhere in the function.
3. `wizardErrors.ts:2930-2996` — the substring cascade runs over `err.message`, i.e. the *human
   sentence*. Measured: none of the eight real detail strings matches any needle (Q2). Terminal
   `return { code: "UNKNOWN", status: 500 }` at `:2997`.
4. `create-with-key/route.ts:1145` takes `{ code, status }`, fires `captureToSentry` at `:1169-1175`
   when `code === "UNKNOWN"`, and emits `NextResponse.json({ code }, { status, headers })` at
   `:1186`. **`err.seamCode` is not in the body.** `ConnectKeyStep` roster-checks `UNKNOWN` and
   renders "We could not classify this failure…".

The loss happens at **step 2/3**, in `wizardErrors.ts`, not in the route. The route is faithfully
forwarding a verdict that was already thrown away.

### What minimally preserves it

The `{ code }`-only body is a deliberate H-0305 property ("callers forward ONLY the returned
`code`") — widening it to carry the raw seam code would put a vocabulary on the wire that the
client's roster cannot admit, so it would render `UNKNOWN` anyway. **The minimal honest change is
therefore a verdict row per Group-A code**, mapping the wire code onto an existing `WizardErrorCode`
that is already in both key rosters. Measured roster membership, so the planner knows the cost:

```
KNOWN_CREATE_WITH_KEY_CODES (25) and KNOWN_ADD_KEY_CODES (24) both contain:
  SERVICE_UNREACHABLE ✓   SERVICE_UNAVAILABLE_RETRY ✓   KEY_VENUE_TRANSIENT ✓   KEY_PROBE_FAILED ✓
  SEAM_MISCONFIGURED ✗    ← present in KNOWN_FINALIZE_CODES only
```

So a verdict row pointing at `SERVICE_UNREACHABLE` / `SERVICE_UNAVAILABLE_RETRY` /
`KEY_VENUE_TRANSIENT` / `KEY_PROBE_FAILED` costs **zero roster edits and zero `EXPECTED_TABLE_SIZE`
movement**; pointing at `SEAM_MISCONFIGURED` costs two roster additions and still no copy; minting a
brand-new operator-directed member costs a copy entry + `EXPECTED_TABLE_SIZE` 76 → 77 + two roster
rows. ⚠️ `SERVICE_UNAVAILABLE_RETRY`'s copy asserts *"nothing was submitted"* — `wizardErrors.ts:2908-2912`
explicitly forbids reusing that claim for a request that WAS issued. `MT5_GATEWAY_UNREACHABLE` fires
after the request was issued, so it is `SERVICE_UNREACHABLE`, not `SERVICE_UNAVAILABLE_RETRY`. That
is a real trap and it is written down in the file already.

## Q8 — Falsifiability: how to prove the gate reds, permanently

### Today's state, measured

The current predicate cannot see a router code even after the root widens — reproduced over a
synthetic tree so the repository was never touched:

```
node_modules/.bin/tsx <scratch>/scan2.ts
=== FALSIFIER: synthetic tree, current predicate vs widened root ===
current predicate rooted at <root>/services  -> ["ASSIGNMENT_SHAPE_CODE"]
current predicate rooted at <root>           -> ["ASSIGNMENT_SHAPE_CODE"]
      ^ the routers/rtr.py `service_error(500, "ZZZ_FALSIFIER_ROUTER_CODE", …)` file is invisible
```

### The permanent falsifier — three layers, and only the third is real

| Layer | What it proves | Permanent? |
|---|---|---|
| 1. **Inline SELF-TEST fixture** (the file's established idiom, :313-364) — a synthetic `service_error(500, "X", …)` source string through the matcher | the *predicate* matches the shape | ✅ yes — but it tests the helper, not the wiring |
| 2. **Reach pin** — hand-typed roots + callee table, asserted | the discovery is pointed where we think | ✅ yes |
| 3. **Whole-pipeline falsifier over a synthetic directory tree** — `mkdtempSync` → write `<tmp>/routers/zzz.py` containing an undisposed `service_error(...)` code → run the **real** `deriveEmitterSites(root)` + the **real** disposition filter → assert the undisposed list is `["ZZZ_…"]` → `rmSync` | that the *composed* guard reds by name for a new router code | ✅ yes |

**Layer 3 is the one the PRD's criterion 3 asks for**, and it is what turns "the helper works" into
"the gate reds". It requires exactly one refactor: **make the root a parameter** of
`deriveEmitterSites()` (today it closes over the module-level `SERVICES_ROOT`). That is a two-line
change and it is what makes the falsifier permanent rather than a one-off manual mutation recorded in
a SUMMARY.

`mkdtempSync` / `os.tmpdir()` is established in this repo — `src/__tests__/gitleaks-allowlist.test.ts`,
`check-banned-packages.test.ts`, `check-route-contract.test.ts`, `check-admin-route-manifest.test.ts`,
`gdpr-export-coverage-hook.test.ts` all use it. No new technique.

⚠️ **Layer 3 is necessary but not sufficient on its own.** It proves the guard reds for a synthetic
tree; it does not prove the guard is *pointed at the real tree*. Layer 2's root pin is what closes
that, and the "both shapes appear in the discovered set" assertion from Q5 is what closes the
converse. All three, or the falsifier is theatre.

⛔ **Do not implement the falsifier by committing a real throwaway `.py` file under
`analytics-service/routers/`.** It would be discovered by the widened scan, by
`test_raw_5xx_census.py`, and by mypy/ruff, and removing it later re-opens the hole. The one-off
manual mutation (write, run, red, revert, `git status --short` → empty) is still worth doing **as a
receipt in the SUMMARY**, exactly as the 153 verification did with M1/M2 — but it is a receipt, not
a mechanism.

### The single highest-risk task

⭐ **Plan A task 2 — the call-shape matcher.**

Everything else in this phase is bookkeeping over a number that task produces. It is the highest-risk
task for four measured reasons:

1. **A too-narrow matcher passes every assertion in the file.** The disposition check, the fossil
   check and the exclusivity check are all *absence* assertions; a matcher that finds nothing
   satisfies all three. The vacuity floor is the only thing standing, and it is hand-typed — so it
   catches a *total* break and not a partial one. This is the file's own stated failure mode
   ("a guard born on an empty population is green forever while measuring nothing").
2. **The false-positive rate of the obvious implementation is 22 %** (9 of 41), across three distinct
   classes, all live in this tree today.
3. **The argument slot is not constant across callees.** `service_error_body` takes the code first.
   A single "second positional" rule silently mis-reads it.
4. **It is the one place where a wrong number becomes a locked pin.** `EXPECTED_EMITTED_CODES` is
   hand-typed against this matcher's output; a matcher bug is frozen into the roster in the same
   commit and thereafter looks like agreement.

**Mitigation the plan must name explicitly:** the matcher's output is cross-checked against the
**independent Python AST census** recorded in Q2 of this document — 32 sites, 21 literal codes, the
exact per-file/per-code table above. Two independent derivations agreeing is the oracle independence
this codebase already demands everywhere else; one derivation compared against its own roster is not.
