## ⭐ THREE ARMS, THREE DIFFERENT TRUTHS — why one member would have been a lie

The plan allowed "names at executor's judgment". The judgement that mattered was not naming; it was
noticing that the three arms are **not** three instances of one fact. Each was read at its own arm:

| Arm | Code | What it MAY claim, and why |
|---|---|---|
| 500 — the draft `.maybeSingle()` SELECT errored | **`DRAFT_LOOKUP_FAILED`** | "Nothing was submitted and nothing was changed." **Observable**: it is a read, and the handler contains no `.insert` / `.update` / `.upsert` / `.delete` / `.rpc` before it (measured). The strongest ground of the three, and the same ground 140.3-15's entry stands on. |
| 500 — the finalize RPC's **generic tail** | **`DRAFT_FINALIZE_FAILED`** | ⛔ May NOT say nothing was saved. The three specific SQLSTATEs are already split off above it, so the residue holds a SQL raise (transaction rolled back, nothing landed) **and** a transport failure reaching PostgREST (the write may have landed and the answer been lost). It says "we cannot confirm" — true in both worlds. |
| 502 — upstream answered **2xx** in an unreadable shape | **`SEAM_RESPONSE_UNREADABLE`** | ⛔ May claim NEITHER outcome. The submission was **accepted**; only its result is unreadable. "Nothing was saved" is false whenever the onboard landed; "it went through" is a guess about a body we could not parse. |

**`DRAFT_LOOKUP_FAILED` is not a new name.** `keys/sync`'s draft-read split already mints that exact
token for that exact fact, and its own comment records that it copied the template *from this arm*.
`verify-strategy` states the rule when it mints `VERIFY_PERSIST_FAILED` on that precedent: same fact
⇒ same token. So the vocabulary gained **two** names, not three, and the day `keys/sync`'s code is
routed through an envelope it already has honest copy waiting.

**Recoverability, decided per arm rather than per family:**

- `DRAFT_LOOKUP_FAILED` — **recoverable**. A transient read failure; the same condition
  `WIZARD_KEYS_LOAD_FAILED` is recoverable for.
- `DRAFT_FINALIZE_FAILED` — **recoverable**, and *both halves were checked*. A retry CAN win (the
  residue is dominated by transient database conditions) and a retry cannot HARM: a second finalize
  against a draft that already finalized raises 22023, which the arm one screen up answers as
  `DRAFT_STATE_INVALID` — an honest, non-recoverable card — rather than writing a duplicate.
- `SEAM_RESPONSE_UNREADABLE` — **non-recoverable, for a reason this milestone has not used before.**
  Retrying is not *futile* here, it is **unpredictable**: nobody, including us, knows what the first
  submission did. A one-click Retry on an unconfirmed submit is a control whose effect the person
  pressing it cannot foresee. The copy orders the remedy instead — open the strategies list, then
  decide — and `leave_and_return` carries the first step, the same control `WIZARD_DUPLICATE` uses.

⚠️ **The promise that was deliberately NOT written.** `CSV_SUBMIT_NO_STRATEGY_ID` can tell a user a
resubmit resolves to the strategy that already exists. This arm cannot: that promise rests on a
partial unique index predicated on a **non-null** wizard session id, and this route forwards the id
through a **conditional spread** — a draft carrying none sends no id at all. True for most users and
silently false for the rest is precisely the shape 140.4-03 recorded when the same guarantee was
published ahead of its mechanism.

## ⭐ THE TWIN — and why a route-local test exists for a fix that is not route-local

The loss was inside **shared** `wizardErrors.ts`, so Plan 02's verdict row reached both key routes
in one commit and **there was never a one-route half-fix to catch**. Zero production route files
were touched by this plan (`git diff` over the twin commit shows exactly two `.test.ts` files).

What a shared-table test **cannot** see is a future **route-local** change that re-opens one path
alone — and the `add-key` catch names the live example itself: pre-stringifying the caught value
before classification sends a breaker trip to the terminal UNKNOWN/500 instead of the retryable 503.
The two new tests are that alarm, written byte-identically on purpose: a divergence between them
would mean the two routes had stopped answering the same wire code the same way, which is the fact
worth failing on.

Each asserts four things, not one: the verdict code, `not UNKNOWN`, `not SERVICE_UNAVAILABLE_RETRY`
(whose "nothing was submitted" is knowable for a breaker that DECLINED to send and
false-by-construction for a connect that WAS attempted), and that the **unclassified-key-error
Sentry capture does NOT fire** — plus the fail-closed pair (`encryptKey` / RPC uncalled).
