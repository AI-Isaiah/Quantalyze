### Why `SERVICE_UNREACHABLE` takes 503 and not 502

The transport block one screen down answers 502 for `UPSTREAM_TIMEOUT` / `UPSTREAM_NETWORK_ERROR`
because 502 is the status the seam already used on that path. Here the producer's own status is
**503** and it stamps a `Retry-After` — a header defined for 503 — so forwarding 503 keeps the
wire answer the one the service chose, and keeps the wait coherent with the status carrying it.

## Decisions Made

- **Minted rather than stretched.** `SEAM_MISCONFIGURED` was the plan's default for the whole
  operator-fault family. Reading the emitters split it: three codes keep it because the emitter
  provably fires before any outbound request and before any state change, three take a new member
  because that clause is false at an emitter. The alternative — one member across all six — would
  have shipped a false sentence in exactly the class of defect this milestone exists to close.
- **Status 503 for `MT5_GATEWAY_UNREACHABLE`**, keeping the producer's own status and its
  `Retry-After` coherent, rather than mirroring the transport block's 502.
- **`SEAM_MISCONFIGURED` gets no roster row**, because the measurement says it does not need one
  (below). Adding it "for safety" would have contradicted `ConnectKeyStep.tsx`'s own docblock,
  which names that edit as the wrong fix.
- **Group-B rows state their residue.** Writing them as "renders elsewhere, all is well" would
  have been true and useless; naming the surfaces that still answer `UNKNOWN` is what makes them
  usable as the next plan's input.
