⛔⛔ **THE `REVOKE` IS ONE-SHOT — read `156-MEASUREMENTS.md` § A4 before Task 3.**
`pg_default_acl` for `public` functions granted by role `postgres` is
`postgres=X anon=X authenticated=X service_role=X`. Every function `postgres` creates in `public` is
**automatically** granted EXECUTE to `anon` and `authenticated`; the migrations' explicit
`REVOKE … FROM PUBLIC, anon` is what strips `anon`, and `service_role` is granted by **no migration
at all**. So Migration B's `REVOKE … FROM authenticated` holds only until the next `DROP`+`CREATE` —
which `20260812083206` performed on `create_wizard_strategy` three days before this phase, its
post-verify at `:867` existing *because the author hit this for `anon`*.

shipped, and the migration that reopens the door has not been written yet. Only a gate in
`supabase/tests/test_*.sql`, re-run on every PR, can. That gate is **5h** (Task 3), and it is why
this plan has three tasks instead of two.
