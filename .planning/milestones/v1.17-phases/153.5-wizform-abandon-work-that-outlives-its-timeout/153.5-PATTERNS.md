## The one-paragraph orientation the planner should read first

Every artifact below has a **direct, same-file-family analog** and the analog is usually
younger than three weeks. The three biggest ways a planner loses this phase are:

1. **Guarding the wrong roster.** D-35 spent a whole plan establishing that
   `close()`/`release()`/`_teardown_transport()` touch **our rpyc socket** and NOT the MT5
   session. Those must stay reachable *after* the lease releases or the Pitfall-6 session
   leak returns. The guard's roster is "touches `self._mt5`'s **MT5 surface**", not
   "is a method on `Mt5Client`". Get this wrong and the fix re-opens the exact leak
   `routers/exchange.py:899-948` exists to prevent.
2. **Naming the refusal with the word "terminal".** `_WRONG_SERVER_TOKENS`
   (`services/mt5_validation.py:66-73`) contains `"terminal"`, `"connect"`, `"ipc"`,
   `"network"`, `"server"`. A message carrying any of them, if it ever reaches
   `classify_mt5_login_error`, becomes a **400 telling the user their broker server is
   wrong**. That already happened once — the whole `exchange.py:678-704` short-circuit
   exists because of it.
3. **Believing an epoch stamped at construction fences finding #6.** #6a/#6b are cases
   where the **zombie thread constructs the client itself, after the release**. A
   construction-time snapshot read from the *registry* stamps the zombie's client with the
   *current* generation and it sails through. See §Artifact 1 → The trap. This is the
   single highest-risk design decision in the phase and CONTEXT explicitly leaves it to the
   planner's discretion.

## §0 — The fix-at-the-sink precedent (D-35, Phase 153.3 plan 06). THIS IS THE TEMPLATE.

**Commit:** `6990d37b` — *"feat(153.3-06): delete the MT5 teardown at the SINK — close() never calls shutdown()"*
**Follow-ups that are part of the template:** `a7e88c7d` (rationale re-cuts), `938159b6` (a review finding on the guard itself), `be358bc6` (phase-complete record).
**Diffstat:** 6 files, +408 / −105. **Production files changed: ONE** (`services/mt5_client.py`). The other five are tests.

### What moved

D-30 had removed `mt5.shutdown()` from the *request* path only, by introducing a second
verb (`release()`). Three callers still reached `shutdown()` from the worker side.
D-35's plan 06 did **not** add a fourth verb or edit those three callers. It:

1. **Extracted ONE private mechanism** — `Mt5Client._teardown_transport(mt5_obj, *, who, stage)`
   (`mt5_client.py:705-752`) — carrying the whole thing: the name-mangled
   `_MetaTrader5__conn` ponytail, the swallow-and-log, and the never-silently-no-op WARNING.
2. **Re-expressed the two public verbs as two names over that one implementation.**
   `close()` (`:754-797`) and `release()` (`:799-822`) now have *identical* three-line
   bodies (`if self._closed: return` → `self._closed = True` → `self._teardown_transport(...)`).
   The commit message states the reason exactly: *"so the two public names cannot drift
   apart and neither can regrow a shutdown()."*
3. **Deleted the offending call from the sink.** `close()` no longer calls `mt5.shutdown()`.

### What the callers did NOT have to do

**Nothing. Zero call-site edits.** The three fixed callers were:
- `services/exchange.py`'s `aclose_exchange` mt5 arm (the dispatch epilogue)
- `services/ingestion/mt5.py`'s adapter `finally`
- both operator scripts under `scripts/`

The `close()` docstring (`:770-775`) states *why* they could not have been fixed at their
own sites even if someone wanted to: *"both run in a `finally` outside the terminal lease,
so leasing them would mean queueing inside an error path to buy permission to do something
destructive."* **Finding #5 in this phase is the same argument in reverse** — the lease-held
premise that justifies the ONE surviving `shutdown()` is false on the timeout path.

### How the accompanying test was RE-CUT, never deleted

This is the half planners skip, and it is half the template.

Plan 153.3-03 had shipped `test_close_alone_still_calls_shutdown_exactly_once`, pinning
`shutdown_calls == 1`, with a docstring that said, in the test itself:

> ⚠️ KNOWINGLY TEMPORARY — owner **D-35** (153.3 wave 6). D-35 closes the
> shutdown-on-a-shared-session class AT THE SINK … at which point `shutdown_calls == 1`
> here becomes exactly the wrong pin. Wave 6 must RE-CUT this case deliberately rather
> than be surprised by it.

Wave 6 replaced it with `test_close_alone_never_reaches_shutdown`
(`tests/test_mt5_client_contract.py:998-1020`) pinning `== 0`, whose docstring **names its
predecessor by symbol and explains the flip**. The three disciplines to copy:

- **A test whose pin a future phase will invert is annotated with that phase's decision id
  at the time it is written.** If any pin this phase writes will be inverted by Phase 155
  (the two deferred findings #8/#10 are about the very timeouts around these `wait_for`s),
  annotate it now.
- **The re-cut test's docstring names the old test by symbol** and states the WHY (Rule 9),
  not just the WHAT.
- **The intent survives even when the observable moves.** `test_close_is_idempotent_and_swallows_teardown_errors:900`
  kept its name-minus-a-word and its intent ("a teardown failure must never mask the
  caller's error") while its observable moved from `fake.shutdown_calls` to
  `fake._MetaTrader5__conn.close_calls`. It says so in the docstring: *"The INTENT is
  unchanged and is what matters."*
- **New structural cases were ADDED alongside**, not instead: `test_close_and_release_are_observationally_identical:1039`
  drives each verb on its own client and compares observables — *"Asserted by driving each
  on its own client and comparing the observables, not by reading the source."*

### The one-liner for the planner

> D-35 = extract the mechanism into one private helper → express the public names over it →
> delete the offending behaviour at the sink → re-cut (never delete) the tests that pinned
> the old behaviour, naming the old symbol → derive the structural guarantee from source in
> a separate roster file → sweep every docblock whose *rationale* the change invalidated.
> **D-36 is the same five steps with `epoch` where `shutdown` was.**

## Pattern Assignments

### Artifact 1 — The epoch registry (`services/mt5_concurrency.py`, module level)

**Closest existing analog:** `services/mt5_concurrency.py:129-187` — the MT5CONC-02 docblock,
`_MT5_TERMINAL_LOCKS`, and `_mt5_terminal_lock_for`. Sibling: `services/position_reconstruction.py:299-318`.

**What to copy** — the shape, verbatim:

```python
# MT5CONC-02 (Phase 137 plan 02): module-level per-terminal asyncio.Lock registry,
# keyed by the process-wide terminal identity (host:port via Mt5Client.terminal_key),
# mirroring position_reconstruction.py:308-317. It MUST be module-level, NOT a
# Mt5Session attribute: _make_mt5_session builds a FRESH Mt5Session + Mt5Client per
# job, so a Session-attached lock would be a brand-new Lock object per job and
# serialize NOTHING (the Pitfall-1 anti-pattern). Keyed by terminal_key so every job
# hitting the ONE shared Wine terminal contends on the SAME Lock.
#
# The dict grows unboundedly BY DESIGN (same rationale as the reconstruct registry):
# evicting a Lock with waiters parked on it would silently break serialization, and
# terminal cardinality is bounded (v1 = ONE gateway terminal, O(1) keys).
_MT5_TERMINAL_LOCKS: dict[str, asyncio.Lock] = {}


def _mt5_terminal_lock_for(terminal_key: str) -> asyncio.Lock:
    # setdefault is atomic across coroutine resumption — there is no await between
    # the lookup and the insert, so within one event loop two simultaneous first-
    # callers for the same terminal cannot end up with two different Lock objects.
    return _MT5_TERMINAL_LOCKS.setdefault(terminal_key, asyncio.Lock())
```

Copy: (1) **module level**, in this exact leaf module — the module docstring's leaf-invariant
(`mt5_concurrency.py:20-24`) says its only in-tree import is one constant from
`services.mt5_client`; do not break that by importing anything else here; (2) **keyed by
`terminal_key`**; (3) a **plain mutable `dict`, deliberately NOT `Final`** (contrast the
five `Final[float]` timeout constants above it at `:59-101`); (4) an accessor function
using `setdefault` with the atomicity comment; (5) the unbounded-growth-by-design paragraph.

**The verified reason this must be module-level (do not paraphrase — this is the load-bearing
fact):** `services/job_worker.py:944-973` `_make_mt5_session` calls `Mt5Client(host, int(port_raw))`
**per job**. `routers/exchange.py:513-524` and `services/ingestion/mt5.py:207-210` each build
their own. There is no client cache anywhere. A per-instance counter that a fresh instance
resets fences **nothing across jobs** — MT5CONC-02's Pitfall-1 anti-pattern, which
`tests/test_mt5_derive_branch.py:988-996` already has a live negative control for
(`new=lambda _k: asyncio.Lock()` — "A FRESH Lock per call serializes NOTHING — this is
exactly what a Session-attached lock would do").

**What to change**

- A `dict[str, int]` (or `dict[str, object]` token) instead of `dict[str, asyncio.Lock]`.
- The bump belongs in `mt5_terminal_lease`'s **`finally`**, beside `lock.release()`
  (`mt5_concurrency.py:272-273`). That `finally` is the ONE release point for all five call
  sites, which is exactly why the bump lands there and nowhere else.
- **Ordering inside the `finally` matters and should be stated in a comment:** bump the
  generation **before** `lock.release()`. Releasing first hands the lock to a queued waiter
  who may begin touching the session in the window before the generation moves — the fence
  would be open for exactly the interval a real second caller uses.
- The bounded-acquisition arm (`:245-258`) **raises before ever holding the lock** and must
  therefore **not** bump. `test_lease_bound_expiry_raises_busy_and_never_acquires`
  (`tests/test_mt5_concurrency.py:266-295`) is the existing case that pins the analogous
  "release nothing you never acquired" half; the epoch needs its twin.

**The trap** — ⭐ **the single highest-risk decision in this phase.**

A generation counter keyed only by `terminal_key`, snapshotted by `Mt5Client.__init__` from
that registry, **fixes #5 and #7 but NOT #6a/#6b**:

| Finding | Zombie holds | Registry says | Guard verdict |
|---|---|---|---|
| #5, #7 | a client stamped at generation `G` (built under the old lease) | `G+1` | ✅ refuses |
| #6a, #6b | **nothing yet — it constructs the client itself, after the release** | `G+1`, and `__init__` stamps `G+1` | ❌ **passes; session leaks exactly as today** |

#6a/#6b are the *connect-stage* timeouts: the `wait_for` fires, `client` stays `None`, the
Pitfall-6 `if client is not None:` release at `exchange.py:935` releases **nothing**, and
the abandoned thread then runs `Mt5Client(...)` to completion. A registry-sourced
construction stamp cannot distinguish that zombie's `__init__` from a legitimate next
holder's.

**What distinguishes them is the lease OCCUPANCY the caller belongs to, not the terminal.**
The mechanism that carries occupancy identity into an abandoned thread already exists in
CPython and is **verified working in this environment** (measured 2026-08-11):

```
asyncio.to_thread    → copies the caller's contextvars.Context at spawn  ✅
asyncio.wait_for     → wraps in a Task, which inherits the context       ✅
@asynccontextmanager → a ContextVar.set() inside the CM IS visible to the caller,
                       and Token.reset() in its finally restores it       ✅
```

So a `ContextVar` set to a fresh occupancy token on lease acquire and `Token.reset()` on
release gives: the zombie thread's *frozen copy* still says `token-7`, while the registry
has moved to `token-8` (or to "unheld"). `Mt5Client.__init__` snapshots the **ContextVar**,
not the registry — and the zombie's fresh client is born already stale. That closes all four
findings at one sink with zero call-site edits.

In-repo ContextVar analogs to copy from (both carry the trap notes you want):
- `services/logging_config.py:40-45` — `correlation_id_var: ContextVar[str | None] = ContextVar("correlation_id", default=None)`, declared module-scope specifically *"so we can hold the Token and reset it precisely on request teardown"*. That is the exact `Token`/`reset` idiom the lease's `finally` needs.
- `services/exchange.py:56-69` — carries the ⚠️ **mutable-default** red-team note: a `default={}` literal is captured once at module load and **shared across every reader**. Use an immutable default (`None`) for the lease token, or inherit that whole hazard.
- `tests/test_correlation_middleware.py:44-136` — the existing test shape for "the ContextVar was reset to default after teardown" and "request N's value did not bleed into request N+1".

⚠️ The alternative — passing the token explicitly to `Mt5Client(...)` — costs **three
call-site edits** (`exchange.py:515`, `ingestion/mt5.py:208`, `job_worker.py:969`). That is
small, but it is *not* the D-35 shape, and the phase charter is explicitly "fix it at the
SINK, once — not three times." If the planner chooses it anyway, say so out loud and say why;
do not let it happen by drift.

⚠️ Second-order trap: **`Mt5Client.restart()` rebuilds the connection while the lease is
still held.** Whatever the stamp is, `restart()` must leave the client usable for the
remainder of the *current* occupancy (`job_worker.py:3594` and `allocator_positions.py:670,684`
all call it inside their `async with`, then return). A design that re-reads the registry on
restart is fine; one that invalidates the client is a self-inflicted regression on the
recovery path.

### Artifact 2 — The guard on session-touching methods (`services/mt5_client.py`)

**Closest existing analog:** `Mt5Client._guarded_read` (`:531-557`) and `Mt5Client._timed`
(`:460-497`) — the two existing *"one wrapper every read already passes through"* chokepoints.
Structural analog for the extraction itself: `_teardown_transport` (`:705-752`).

**What to copy**

`_guarded_read`'s docstring is the model for how this codebase justifies a chokepoint:

```python
    def _guarded_read(self, call: Callable[[], Any], *, stage: str | None = None) -> Any:
        """Run a raw transport read, converting ANY transport-RAISED exception
        into a scrubbed, typed `Mt5ClientError` (T-134-01). …
        `stage` (153.3 / D-32) composes the timing bracket INTO this one wrapper
        — the single place every non-login read already passes through — rather
        than wrapping it from outside."""
```

And `_timed`'s explains *why one helper and not ten brackets*:

```python
        ONE helper, not a bracket copy-pasted at ten call sites: a per-site
        bracket is how half the sites end up un-instrumented, and a population
        that silently excludes the failures is exactly the censored measurement
        this exists to replace.
```

`account_info`, `terminal_info`, `history_deals_get` and `order_check` (`:620-703`) are each
**a single `self._guarded_read(...)` line + a `None` check + `_materialize`**. A guard
composed into `_guarded_read` therefore covers four of the roster for free, with no
per-method edit — the same trick D-32 used to instrument every read in one line.

**What to change**

The roster is **not** "the methods on `Mt5Client`". Measured against source, it splits three ways:

| Method | Touches the MT5 session? | Guard? | Why |
|---|---|---|---|
| `login:559` | ✅ `initialize()` + `login()` | **YES** | it re-points the shared terminal — the single most destructive touch |
| `account_info:620` | ✅ | YES | via `_guarded_read` |
| `terminal_info:627` | ✅ | YES | via `_guarded_read` |
| `history_deals_get:659` | ✅ | YES | via `_guarded_read` |
| `order_check:682` | ✅ | YES | via `_guarded_read` |
| `_raise_last:499` | ✅ `last_error()` is a **full remote round-trip** (`:509-511`) | YES | easy to miss; it is not on the happy path |
| `restart:824` | ✅ **`stale.shutdown()` — finding #5 itself** | **YES** | ⭐ the whole reason the phase exists |
| `close:754` / `release:799` / `_teardown_transport:705` | ❌ **our rpyc socket only, since D-35** | ⛔ **NO — must stay reachable post-release** | `exchange.py:911-921` Pitfall 6: the release is *deliberately* outside the deadline so a fired deadline still releases the session. Guarding it re-opens the leak D-30/D-35 closed. |
| `_timed:460` / `_guarded_read:531` | wrappers | n/a | the guard composes *into* these, it is not guarded *by* them |
| `terminal_key:911` | ❌ pure `f"{host}:{port}"` | NO | — |

⛔ `close`/`release` being **exempt** is not an oversight to be tidied later — it is the
D-35 distinction ("release my connection" ≠ "shut down the terminal's IPC") load-bearing in
a second place. Write that sentence into the guard's docstring so the next author does not
"fix" it.

⚠️ `restart()`'s guard has a subtlety: its `shutdown()` is the ONE *permitted* teardown, and
its permission rests on lease-holding. The guard therefore replaces the belief with a check
— which is exactly what `restart()`'s own docstring (`:848-860`) currently claims
`test_mt5_shutdown_roster.py` provides, **and which that test cannot actually provide** (§4
below). That docstring is one of the three that must be re-cut.

**The trap**

1. **The guard must fire BEFORE the round-trip, not inside `_timed`.** The point is not to
   time a forbidden call, it is to not make it. Put the check ahead of the `_timed` bracket.

   ⛔ **SUPERSEDED 2026-08-11 — do NOT emit an `mt5.stage` event for a refusal.** This
   paragraph originally instructed emitting
   `emit_mt5_stage_event(stage, started, ok=False, …, outcome="abandoned")` at the refusal.
   **RESEARCH §Q-4 overrides it** on `duration_ms` population purity: a refusal makes no
   round-trip, so emitting one pollutes the stage histogram Phase 155 reads to set the real
   budget with rows whose duration measures nothing. Plan 153.5-01 implemented the
   RESEARCH ruling and executed accordingly; the fence LOGS (D-39) but emits no stage event.
   Kept rather than deleted so a reader who arrives at this section by search sees the
   ruling instead of the withdrawn instruction.

   The rest of the paragraph still holds *if* a stage event is ever emitted here: `outcome`
   is already a member of the **closed allow-list** (`:177-217`, hygiene rules at
   `:148-154`), so it would need **no new field** — and ⛔ adding one would violate the
   documented rule. Stage names are an **aggregation key across deploys** (`:141-146`);
   reuse the existing verbatim names, do not mint `abandoned_login`.
2. **Do not rely on the exception propagating.** By definition nobody is awaiting the
   abandoned thread — its `wait_for` already raised and its task was cancelled. A raise
   alone can end up as an unretrieved-future log line or nothing at all. **Log at the guard
   as well as raising**, using the `_teardown_transport` warning convention
   (`logger.warning("%s: …", who)` at `:738-743`). D-36 says "a zombie thread discovering it
   has been fenced is a real event" — make it an event, on our own logger, not a hope about
   asyncio's exception handler.
3. **Do not add a `__getattr__` passthrough** to route the guard generically. The module
   docstring (`:16-22`) makes the absence of that hook a load-bearing security property —
   it is what stops the trade surface being re-exposed and is what `api_verified` rests on.
4. `login()` (`:586-618`) does **not** go through `_guarded_read` — it has its own two
   hand-written try/excepts because it redacts credential literals by value (`:612-616`).
   It needs the guard added explicitly. Missing it is the most likely single omission in
   the whole phase, and it is the worst one.

### Artifact 3 — The new exception (`Mt5SessionAbandoned`)

**Closest existing analogs — there are THREE and they agree:**
- `services/mt5_concurrency.py:190-204` `Mt5TerminalBusyError`
- `services/mt5_concurrency.py:276-296` `_Mt5PostReadVerificationError`
- `services/mt5_client.py:291-315` `Mt5AccountMismatchError`

**What to copy** — the paragraph all three carry, near-verbatim:

```python
class Mt5TerminalBusyError(Exception):
    """D-29 — the terminal was still held when the INTERACTIVE acquisition bound
    expired. We never touched it; nothing about the caller's credentials is known.

    Deliberately a PLAIN ``Exception``, NOT an ``Mt5ClientError`` subclass —
    … the credential classify/stamp arms match on
    ``Mt5ClientError``, so a busy terminal that inherited from it could be absorbed
    into a USER-ATTRIBUTED verdict (``auth`` / ``wrong_server``) and blame a working
    key for our own queue. Plain ``Exception`` makes that structurally impossible.

    ⛔ It carries no host, port, terminal key, queue depth or account value. A busy
    terminal is OUR infrastructure, never the user's key, and nothing about it may
    reach a response body (WIZFORM-03).
    """
```

Copy all four elements: (1) the decision id in the first line; (2) **plain `Exception`**;
(3) the *structural-impossibility* argument spelled out (not "we are careful", but "the arm
cannot match it"); (4) the ⛔ no-infrastructure-in-the-message clause.

Its test is `tests/test_mt5_concurrency.py:343-357`, which is nine lines and copies directly:

```python
def test_busy_error_cannot_be_absorbed_into_a_credential_verdict() -> None:
    from services.mt5_client import Mt5ClientError
    assert issubclass(mt5_concurrency.Mt5TerminalBusyError, Exception)
    assert not issubclass(mt5_concurrency.Mt5TerminalBusyError, Mt5ClientError)
    message = str(mt5_concurrency.Mt5TerminalBusyError("the MT5 terminal was busy"))
    for leak in ("h:1", "18812", "localhost", "127.0.0.1"):
        assert leak not in message
```

**What to change**

Where it lives depends on where the epoch lives. If the registry is in `mt5_concurrency.py`,
the exception belongs there beside `Mt5TerminalBusyError` — but the **guard** that raises it
is in `mt5_client.py`, and `mt5_concurrency.py` imports *from* `mt5_client`, never the
reverse (leaf invariant, `:20-24`). ⭐ **Therefore the exception class must live in
`services/mt5_client.py`** (with `Mt5ClientError` / `Mt5AccountMismatchError`) and be
imported by `mt5_concurrency.py` if needed — the same direction the existing
`from services.mt5_client import MT5_REQUEST_TIMEOUT_S as _MT5_REQUEST_TIMEOUT_S` already
goes (`:36`). Putting it in `mt5_concurrency.py` creates an import cycle that
`test_importing_leaf_does_not_import_job_worker` (`tests/test_mt5_concurrency.py:122-144`)
is the in-repo precedent for caring about.

**The trap** — ⭐ **the `_WRONG_SERVER_TOKENS` history CONTEXT sent you to check.**

`services/mt5_validation.py:66-73`:

```python
_WRONG_SERVER_TOKENS: tuple[str, ...] = (
    "server", "connect", "ipc", "network", "terminal", "not found",
)
```

`classify_mt5_login_error` (`:256-278`) does a **substring match on `str(err).lower()`**.
