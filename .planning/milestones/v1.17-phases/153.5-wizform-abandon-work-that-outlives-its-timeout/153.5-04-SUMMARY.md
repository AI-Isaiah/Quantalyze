# Phase 153.5 Plan 04: Every surface classifies the refusal as TRANSIENT Summary

**Five `except Mt5SessionAbandoned` arms — router probe, ingestion adapter, derive job, holdings poll and `process_key`'s two previously-unguarded `adapter.validate` sites — each routing the abandoned-session refusal to its OWN existing transient disposition, so an operator-side fault can no longer be delivered as an unhandled bodyless 500 (R-1: "service-permanent, do not retry") or as a credential accusation against a working key.**

## Decisions Made

- **Both `process_key` sites answer the same 424 envelope, and that is not a unification.** The plan says "if the two sites' existing shapes differ, mirror each site's own". They do not differ in a usable way: `:1586` already emits `JSONResponse(424, _envelope_error(..., recoverable=True))` at its PYAPIFIX-02 venue-transient pre-gate, and `:774` (`_run_validate_only`) had **no** non-200 shape at all — every one of its returns is a bare dict. Each site therefore routes to the nearest existing shape it emits, which happens to be the same one.
- **The human copy is `exchange_svc.NETWORK_ERROR_DETAIL`**, not new prose. `exchange_svc` was already imported, the string is this service's single shared transient copy, and the wizard renders on `body.code` anyway (140.3-05). Zero new copy, zero new code.
- **`NETWORK_UNAVAILABLE` was verified to be an existing, non-permanent code** before it was reused: absent from `services/exchange.py`'s `PERMANENT_VALIDATION_ERROR_CODES` and from `process_key.py`'s own `_ROUTE_TERMINAL_ERROR_CODES`, and present in the frontend vocabulary (`src/lib/wizardErrors.ts` maps it to `KEY_NETWORK_TIMEOUT`). `recoverable` is nonetheless **stated**, not derived, matching the sibling 424 arm.
- **The sync-pipeline arm does not transition the verification row.** The scope-rejection arm beside it writes `status='draft'` with an `errors` array, because it has reached a verdict about the caller's key. This arm has not: the terminal was never read. Leaving the row alone is what lets an identical retry succeed.
- **The derive `error_message` was drafted against the LIVE token tables, not against intuition.** "terminal", "session", "connect", "login" and "account" are all substring members, so the phrase settled on is *"mt5 read was refused because the lease it began under had already ended — retrying"*. The class name lives in the WARNING log only; a log is never classified.
- **Tests drive the fence, they do not impersonate it.** Three small transport subclasses (`_EpochBumpingMt5`, and two `_EpochBumpingTransport`s) call the SHIPPED `bump_mt5_terminal_epoch` from inside `login()` — which is exactly what `mt5_terminal_lease`'s `finally` does — so the refusal that reaches each arm is produced by production `_assert_live`. The two `process_key` cases are the exception: they stub the adapter registry, because the property under test there is the call site's guard and no MT5 client is in play.
