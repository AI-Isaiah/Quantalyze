<domain>
## Phase Boundary

No `asyncio.to_thread` work can keep touching the MT5 terminal after its `wait_for` fired
and its caller released the lease.

ONE defect with three faces, all introduced in the Phase 153.3 diff and all deliberately
deferred by that phase's `/code-review high`. Work handed to `to_thread` outlives its
`asyncio.wait_for`; the `wait_for` raises, the caller unwinds and releases the terminal
lease, and the abandoned thread keeps driving the same process-global MT5 session.

Anchors below were RE-VERIFIED against source on 2026-08-11 (commit `bb29c712`). Each is
`file` › enclosing symbol › the specific expression. Line hints are as-of that date — **if a
hint ever disagrees with its symbol, the symbol wins.**

### Why this phase is load-bearing beyond its three findings

D-35 (Phase 153.3, plan 06) removed `mt5.shutdown()` from `Mt5Client.close()` and left
exactly ONE surviving teardown: `Mt5Client.restart()`'s, the deliberate heal of a wedged
pipe (MT5CONC-01). TODOS records that survivor as safe **"because every call site holds
the terminal lease."** Finding #5 is precisely the case where that premise is false. This
phase is therefore not three loose ends — it is the repair of the safety argument the
previous phase's fix rests on.

<decisions>
## Implementation Decisions

### D-36: The sink is a generation/epoch counter on `Mt5Client` (ACCEPTED)

- **`Mt5Client` carries a generation. The lease bumps it on release. Every method that
  touches the MT5 session checks it FIRST and refuses on a stale epoch.** Fixes #5, #6
  and #7 at one sink with zero call-site edits — the same fix-at-the-sink shape D-35
  already used successfully in this exact module.
- **The refusal must be LOUD** — raise a named error (e.g. `Mt5SessionAbandoned`), never a
  silent no-op. A zombie thread discovering it has been fenced is a real event; swallowing
  it reproduces the silent-UNKNOWN class this milestone has spent four phases closing.
- **An ast roster test is required, modelled on `tests/test_mt5_shutdown_roster.py`** —
  derive the set of session-touching methods from source, assert each carries the guard,
  with a vacuity floor and self-tests. Without it the guard is correct today and forgotten
  by the next method written. (This is the static complement to guard #16; it does NOT
  replace the runtime assertion.)
- ⛔ **REJECTED — "refuse to release the lease until the worker confirms it stopped."**
  Correct in isolation, wrong in system: it blocks the lease for as long as the hung
  thread, which is exactly the **WEDGE-01** class D-25 forbids (`mt5_client.py:79-81` — a
  hung terminal must not wedge the SEQUENTIAL worker past the ~90s healthz budget). This
  project has already paid for that class once (PR #632, heavy pandas on the shared loop
  froze healthz). The hang would propagate from one job to every subsequent lease waiter.
- ⛔ **REJECTED — "cancellation-aware wrapper" as a standalone remedy.** Python threads
  cannot be interrupted; `to_thread` offers no cancellation. Such a wrapper discards the
  RESULT while the thread keeps issuing rpyc calls against the same session — it makes the
  caller tidier and changes nothing about the defect. If the wrapper also gates the
  session, it *is* D-36 under a different name.

### D-37: Guard #16 is a deterministic barrier + fake-session spy (ACCEPTED)

- **The AST lease-roster CANNOT catch this class** — its enclosure proof is *lexical*, so
  it reads the `shutdown` as inside the `async with` and passes while the runtime escapes.
  Guard #16 must be a **runtime** assertion.
- **Shape:** a fake MT5 session records every touch as `(method, epoch, at_time)`. The test
  owns a `threading.Event` the worker thread blocks on, so the abandonment is *scheduled by
  the test*, not by the scheduler: worker blocks → `wait_for` fires → caller unwinds, lease
  releases, epoch bumps → test sets the Event → zombie proceeds → assert no post-release
  touch carries a live epoch and the zombie's calls raise.
- ⛔ **NO sleep-ordered concurrency test.** This repo already carries four documented flake
  mechanisms in its shared-DB suite and a `--no-file-parallelism` workaround for local
  vitest; a timing-ordered race would buy a fifth, and would pay the real bound on every
  run.
- The guard must be **falsifiable**: remove the epoch check, the post-release touch lands,
  the test reds. Observe that red, do not predict it.

### D-38: Scope stays ONE class (ACCEPTED)

- **IN:** findings #5, #6, #7 — the abandoned-`to_thread` mechanism, fixed at the sink.
- **OUT — the structlog processor-chain freeze** (8 module-level `get_logger` proxies bind
  before `configure_logging()` runs in the lifespan, bypassing the PII `_redact_processor`).
  A real defect and a real redaction bypass, but it shares only a *directory* with this
  phase, not a mechanism. It also carries its own unresolved decision in TODOS ("triage
  before fixing all eight — exposure is NOT uniform") plus a preferred class fix (drop
  `cache_logger_on_first_use`, or configure logging at import). That is a phase-sized
  decision, not a rider. Stays in TODOS with its own owner.
- **OUT — finding #8** (the 60s per-stage ceiling wraps SIX round-trips whose own ceilings
  are 45 000ms IPC / 55s rpyc, so "innermost fires first" holds per round-trip but not per
  stage) and **finding #10** (the 20s interactive lease wait is smaller than the worker's
  40s read + 10s restart hold, so an interactive validate can never wait out one in-flight
  derive). Both are **deferred to Phase 155** because both need the live latency data D-32
  made collectable. ⛔ Do NOT guess these numbers.
- **OUT — cross-replica serialization.** The terminal lease is an `asyncio.Lock`, which is
  single-event-loop and serializes nothing across replicas. That is why **D-33** pins the
  gateway to a SINGLE replica. Owner: D-33. A scale-up is a correctness change, not a
  capacity knob.

### D-36 AMENDED 2026-08-11 — the fence is TWO mechanisms, not one (post-research)

Research (`153.5-RESEARCH.md`) and pattern mapping (`153.5-PATTERNS.md`) independently found
that **a method-level epoch cannot fix finding #6**: in #6a/#6b the zombie sits inside
`Mt5Client.__init__`'s blocking connect and makes no subsequent session call, so there is no
method for a guard to sit in front of. D-36's original claim to fix "#5, #6 and #7 at one
sink" was false for #6. Amended, founder-approved:

- **(i) Registry epoch — fences METHOD CALLS (#5, #7).** Module-level, keyed by
  `terminal_key`. ⛔ It must live in **`mt5_client.py`**, NOT `mt5_concurrency.py`: the import
  edge is strictly one-way (`mt5_concurrency.py:36` imports from `mt5_client.py`, whose only
  in-tree import is `services.redact`), so the reverse is a circular import. Decisively,
  `mt5_terminal_lease(terminal_key: str, ...)` receives a *string and nothing else* — it holds
  no client reference and structurally cannot bump an instance attribute. The lease imports
  the bump.
- **(ii) Lease-occupancy `ContextVar` — fences CONSTRUCTION (#6a, #6b).** `asyncio.to_thread`
  copies the caller's `contextvars.Context` at spawn and `wait_for`'s task inherits it, so an
  abandoned thread carries the **old** occupancy token while the registry moves on. Verified
  empirically by the pattern-mapper. In-repo Token/reset precedent: `logging_config.py:43`.
- ⭐ **Why (ii) rather than a construction-time epoch snapshot (RESEARCH §Open Q-1).** A
  construction stamp false-positives: `job_worker._make_mt5_session:969` builds the client in
  **preflight, outside and before the lease** (`allocator_positions.py:601-606` says so), so
  an unrelated lease releasing in that window would refuse a legitimate derive read. Its
  mitigation was two opt-in call-site edits plus a hand-typed pin — i.e. exactly the per-site
  opt-out list this phase exists to avoid. The ContextVar removes the false positive
  *structurally*: a preflight build holds no lease, therefore carries **no token**, therefore
  is exempt — not as a special case someone maintains, but as the honest encoding of "this
  construction is not happening under anyone's lease."
- **Bind the epoch LAZILY on first touch, never at construction** (same preflight reason).
  Every zombie still fences: in every case its first touch happened under the lease that later
  released.
- **`restart()` needs TWO checks and the second is load-bearing.** An entry check passes
  trivially (the legitimate heal runs *before* the release that bumps). Finding #5 is closed
  only by a check immediately before `stale.shutdown()` (`mt5_client.py:892`). Three cleanup
  invariants interact on the fenced path and no existing test covers them together: skipping
  the shutdown must not skip the socket close; `self._closed = False` (set at `:886`) must be
  restored; and the fresh connection opened by the WR-01 reconnect must be disposed. Miss
  these and the fix introduces two new leaks.

### D-39: the refusal must LOG at the sink — raising is NOT loud

`asyncio.futures._copy_future_state` opens with `if dest.cancelled(): return`, so a fenced
zombie's exception is **silently discarded on three of the four sites** (reproduced
empirically during research). D-36's "loud refusal" is not delivered by `raise` alone. The
sink must log at the fence, or the event is invisible — which would reproduce the
silent-UNKNOWN class this milestone spent four phases closing.

### D-40: "zero call-site edits" describes the FENCE, not the CLASSIFICATION

🔴 Blast radius found in research: in `routers/exchange.py` a plain-`Exception`
`Mt5SessionAbandoned` falls through all three `except` arms and every outer handler, producing
an **unhandled bodyless 500** — which under R-1 means "service-permanent, do not retry", the
exact opposite of the truth. `routers/process_key.py:774` and `:1586` call `adapter.validate`
with **no enclosing try at all** (ast-verified). Four small `except` arms are required,
routing to each site's existing *transient* disposition. The plan must state this plainly
rather than repeating the zero-edits claim.

### D-41: the guard's roster is "touches the MT5 session", not "is a method on `Mt5Client`"

- **Exempt and MUST stay reachable after release: `__init__` (for the method fence — it is
  covered by (ii) instead), `close`, `release`, `_teardown_transport`.** Since D-35 these
  touch only our own rpyc socket. Fencing them reintroduces the **Pitfall-6 leak** that
  `routers/exchange.py:899-948` exists to prevent — the fix would cause the bug it is fixing.
- Two easy misses for the roster: `login()` does **not** go through `_guarded_read` (it has
  hand-written try/excepts that redact credential literals by value), and `_raise_last()`'s
  `last_error()` is a full remote round-trip.
- A working ast derivation (a `self._mt5` reference walk) is verified in RESEARCH §Q2.

### D-42: the exception must not be classifiable as a USER fault

- ⛔ **Its message must not contain the word "terminal"** — nor any other member of
  `_WRONG_SERVER_TOKENS` (`services/mt5_validation.py:66-73`, substring-matched) or
  `_AUTH_TOKENS`. This is the documented incident at `routers/exchange.py:678-684`, where an
  operator-side refusal became a 400 accusing the user their BROKER SERVER was wrong.
- It must be a **plain `Exception`, NOT an `Mt5ClientError` subclass** — three in-repo classes
  already carry this exact rationale paragraph, and
  `test_busy_error_cannot_be_absorbed_into_a_credential_verdict` is a nine-line copyable test.
- Add a cheap guard asserting no `_WRONG_SERVER_TOKENS`/`_AUTH_TOKENS` member appears in the
  message.

### D-43: rpyc reality — the epoch is necessary but honestly not sufficient

Verified against the pinned rpyc 5.2.3 wheel: `sync_request_timeout` is a purely *client-side*
TTL on `AsyncResult.wait()`; nothing cancels the remote handler, so an in-flight call
**completes server-side**. Closing the socket does raise `EOFError` on a parked thread, but
cannot help #6 (no socket exists yet), cannot help `restart()` (the fresh connection is already
swapped in), and cannot un-execute a dispatched `shutdown()`. State this limit in the plan
rather than implying the fence un-sends calls already on the wire.

## Test mechanics — traps found in research, do not rediscover

- ⚠️ **The E2 patch-target trap** (`test_mt5_derive_branch.py:869-877`): patching a
  *re-exported* constant is a **silent no-op**. RESEARCH §Q6 carries a per-constant table of
  the correct targets — use it.
- ⚠️ **CI-hang trap:** `asyncio.run` joins the default executor for
  `THREAD_JOIN_TIMEOUT = 300`s. An unbounded `Event.wait()` in a D-37 test stalls the whole
  suite for five minutes instead of redding. The existing analog
  (`test_mt5_derive_branch.py:917-1045`) is a real `threading.Event`-barriered, negative-
  controlled concurrency test using a bounded `.wait(0.25)` under the rule **"a broken lock
  reds, never hangs CI."** Copy that rule.
- ⚠️ **Registry isolation:** five modules already hand-clear `_MT5_TERMINAL_LOCKS`. The epoch
  registry needs the same reset or it buys a sixth flake mechanism — use ONE shared autouse
  reset helper rather than a sixth hand-rolled clear.
- ⚠️ **Existing roster pins are brittle by design:** `TEARDOWN_BARE_REFERENCE_SITES` is
  asserted with `==`, and `PERMITTED_SHUTDOWN_SITES` keys on the *outermost* enclosing def —
  so refactoring `_reconnect_then_dispose_stale` to module level reds it. Expect to re-cut,
  never delete, per the D-35 template.
- ⭐ **The existing `test_every_restart_call_site_holds_the_terminal_lease` is GREEN on
  finding #5 today** — concrete proof of the lexical blindness. The file already half-knows
  it: `_visit_function` resets lease depth at every function boundary because "a closure
  DEFINED inside a lease may be handed to `to_thread` and RUN long after the lease is
  released." That is the conservative half; the unconservative half is this defect. Two
  guards, two questions — do not try to make the ast test do the runtime test's job.
