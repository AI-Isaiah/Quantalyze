## Findings

### F-1 (WARNING) — the refuted category error survives verbatim in the shared card

`src/app/(dashboard)/strategies/new/wizard/ValidateWaitCard.tsx:153-155`, the `onStopWaiting` prop docblock:

> `Abort the in-flight validate. ⛔ NOT DESTRUCTIVE — `validate-key` is strictly pre-encrypt / pre-RPC and persists nothing server-side, so cancelling loses nothing.`

This is **the exact sentence CR-02 named as the load-bearing defect**, still standing, in the one component both corrected surfaces consume. Meanwhile `ConnectKeyStep.tsx:653-662` and `MultiKeyConnectStep.tsx:1094-1100` now carry docblocks that explicitly say this reasoning was the bug ("THAT WAS A FACT ABOUT `validate-key` ASSERTED ABOUT THE ROUTE"). The codebase contradicts itself across adjacent files.

Three test comments restate it as justification too:
- `ValidateWaitCard.test.tsx:276-277`
- `ConnectKeyStep.test.tsx:1424-1426`
- `MultiKeyConnectStep.test.tsx:2511-2513` (a third variant: "nothing is persisted until the key is accepted")

**Why it is not a BLOCKER.** No user-facing string carries the claim, and the *conclusion* (no confirmation dialog) survives on the independent ground `ConnectKeyStep.tsx:648-651` gives: "the request is going to finish or fail on its own either way". Under the project stopping rule this is prose, which never blocks.

**Why it still matters.** This premise is precisely how the false "Nothing was saved" copy got written the first time. Leaving it in the shared component is an invitation to restore it. `PATTERNS` Shared Pattern C and the phase's own audit method — "read the comment as a suspect, not a witness" — both point at this.

### F-2 (WARNING) — a docblock claims a property WR-03 shows is false, and WR-03 is UI-reachable

`MultiKeyConnectStep.tsx:1055-1056`: *"The browser gives up LAST — but it does give up, so no request can hold this tab open forever."*

`doRemove` (`:1001-1004`) still filters the panel out and does nothing else. I confirmed the precondition the review only asserted: **the Remove control is not disabled while a panel is validating** (`:1883-1891` has no `disabled` prop). So remove a validating panel → `anyValidating` recomputes false → the one interval clears → that request's client deadline is gone.

**Assessed as genuinely non-blocking, not quietly load-bearing:**
- No visual artifact: `updatePanelById` (`:982-987`) is a `.map` over ids and no-ops for a removed panel.
- No data-integrity delta: the abort WR-03 asks for would not prevent the server storing the key — CR-01/CR-02 established that neither route reads `request.signal`. The fix buys a bounded client wait, not a rollback.
- The residual is a browser fetch with no client bound, ended by the platform's 300 s `maxDuration`.

WR-05 (`validatePanel:1144` unguarded `panelsRef.current[idx]`) is likewise unfixed and likewise narrow — a one-commit ref-sync lag. Note `requestRemove:1008` has the same unguarded shape, so the asymmetry the review flagged is wider than it reported.

**What is blocking-adjacent is the sentence, not the code:** the docblock asserts closure the code does not have.
