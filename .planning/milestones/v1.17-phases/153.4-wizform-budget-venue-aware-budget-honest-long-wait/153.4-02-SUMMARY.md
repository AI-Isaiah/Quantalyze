## Accomplishments

- **The 120 s row stopped being inert.** One literal — `budgetKey: "validate-key"` at `analytics-client.ts` — became `budgetKeyFor(exchange)`, and that is the whole client-side fix D-01 asked for. `validateKey("mt5", …)` now hands `validate-key-serialized` to the core; every other venue, and every unknown, empty, null or undefined string, still hands it `validate-key` at 30 000 ms. Both directions are asserted at the CALL SITE by reading the first positional argument the core actually received, not only on the helper.
- **The selector reads the capability and nothing else.** No `switch` over venue codes, no `exchange === …`. Its body is scanned from disk for the six venue names and must match zero — a falsifier that reds by name under an instance fix, which the behavioural table alone would not (an `=== "mt5"` rewrite satisfies five of the six table rows).
- **It never throws, and the divergence is written down.** `process-key-client.ts`'s analog closes with a `never` assignment and a throw because `FlowType` is a closed union this codebase owns. `exchange` arrives in a wizard form body, so an unrecognised value is normal input; the fallback is the default row, byte-identical to pre-153.4 behaviour. The docblock states both divergences explicitly so a reviewer does not "fix" them back.
- **SC-4b now charges a MAX, not a phantom sum.** Three routes declare `default-venue` / `serialized-venue`; `encrypt-key` and the dormant leg stay unlabelled and are charged to BOTH branches, which is correct — the encrypt call runs whichever arm was taken. Without the labels the routes would be charged 150 000 ms of validation on a path no request takes.
- **Every number in the header headroom table was re-derived from a run**, not from RESEARCH Table B (which the plan correctly flagged as arithmetically inconsistent — its `validate-and-encrypt` mt5 rows are computed at 120 000 ms while its `create-with-key` rows are computed at 90 000 ms). The run agreed with the plan's cross-check table in all ten cells.
- **The tightest row did not change hands, and the summary says so.** The new worst case anywhere is 248 250 ms with **51 750 ms of headroom**; `finalize-wizard`'s composite remains the tightest at 277 500 ms with 22 500 ms. Stated explicitly in the header rather than left for a reader to re-derive six numbers to confirm.
- **Full suite green:** 770 files / **11 526 passed / 287 skipped / 0 failed**; `npx tsc --noEmit` clean; `npm run lint` 0 errors.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 — Blocking] `resilient-fetch.wiring.test.ts` — a hand-typed binding roster the plan did not enumerate, shrunk by this change**

- **Found during:** the post-Task-3 full-suite run (NOT by reading the plan's file list — 153.4-01 recorded the same lesson).
- **Issue:** the file maintains a 13/13 census of every place a budget key is BOUND to a seam call, discovered from source on disk and compared as a SET against a hand-typed roster. Family (i)'s discovery matched only `budgetKey: "<literal>"`. Replacing `validateKey`'s literal with `budgetKeyFor(exchange)` made the binding invisible: 13 sites discovered against 14 rostered. Three assertions red, including the vacuity fence whose own message says "this guard is now blind, not satisfied" — which was precisely true.
- **Why this matters more than a count:** the failure direction is *under*-discovery. The cheap way to green it is to delete B-01 and lower the fence, which would leave `validateKey` — now the ONLY wrapper that can land on two different deadlines — pinned by nothing.
- **Fix, as a CLASS:** family (i) discovery now reads both shapes, expanding `budgetKey: budgetKeyFor(…)` to every key the local selector can return. The return-literal extraction moved into a shared `returnedKeyLiterals` (family (ii)'s recipe, byte-unchanged) now that two modules carry a selector of that shape. B-14 was added to the roster and to `WRAPPER_PINS`, and the census went 13/13 → 14/14 with the fence 14 → 15 sites. A future third venue-aware wrapper is discovered automatically.
- **Files modified:** `src/lib/resilient-fetch.wiring.test.ts`

### Acceptance criteria met by rewrite rather than by deviation

**`grep -c 'validate-key-\${' src/lib/analytics-client.ts` returned 1 on first writing, not the 0 the criterion demands.** The single occurrence was the T-140-01 prohibition itself, which the same task's action text mandates writing verbatim ("⛔ never build it as `` `validate-key-${exchange}` ``"). The action and the criterion contradict each other, and 153.4-01 hit the same shape and resolved it by recording a deviation.

Here both were satisfiable, so neither was surrendered: the prohibition is written as `validate-key-<exchange>` and says in the same sentence why it avoids the template syntax. The security property the grep proxies for — no interpolated budget key in live code — now has a guard that can actually fail, instead of one permanently satisfied by the warning against the thing it looks for. `grep` returns 0 and the prohibition is, if anything, more legible.

The same reasoning drove the decision not to reprint the false `38 500 / 8 500 / 55 500` triple as a marked quotation. The file's own doctrine (lines ~169-174) keeps verbatim quotations of refuted text and admits nothing in the repo distinguishes a quotation from a claim; naming the defect precisely keeps the historical record and empties the scanner. `grep -c '38 500 / 8 500 / 55 500'` returns 0, as does `grep -c 'Hand-typed 1: exactly one row'`.
