# Phase 153.4: Code Review Report

**Reviewed:** 2026-08-11T06:54:04Z
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

The seam half of this phase (the `validate-key-serialized` row, `budgetKeyFor`, the
branch-aware SC-4b arithmetic, the retry-registry NO verdict, the runbook) is
internally consistent and its guards are mostly real rather than decorative. The
client half has a structural flaw that the phase's own prose asserts is impossible.

The load-bearing defect is a **category error about what an abort cancels**. Both
steps reason from the sentence *"`validate-key` is strictly pre-encrypt / pre-RPC, so
nothing is persisted"* — which is true of the **seam call** and false of the **route**
the browser actually aborts. `POST /api/strategies/create-with-key` and
`POST /api/strategies/composite/add-key` both run `validateKey → encryptKey → RPC
insert`, no route reads `request.signal`, and a Vercel invocation is not cancelled by
a client disconnect (the code says so itself at `ConnectKeyStep.tsx:610-614`, then
draws the opposite conclusion). Two user-facing consequences follow, and one of them
is arithmetically the *dominant* path into the new deadline verdict rather than an
edge case: the client's deadline is sized against the validate leg alone (120 000 +
15 000) while the route's worst case is validate **plus** encrypt (150 000+), so the
client gives up precisely in the window where the server has finished validating and
is storing the key. It then tells the user *"Nothing was saved — your key was not
stored."*

A second, independent user-facing defect: the composite step's `EXCHANGES` array has
no MT5 card, so the one path by which an MT5 key can reach a member panel (the
UAT/F-4 draft carry-over that plan 5's own tests drive) produces a panel that posts
`passphrase: null` — silently dropping the broker server — and renders no field to
put it back.

The A-25 coupling is tight to the point of being **one request-overhead term short**,
and its derived guard measures `timeoutMs` rather than the retried leg's wall clock,
so it constrains slightly less than its message claims.

Everything below cites lines at HEAD.

## Critical Issues

### CR-01: The client deadline is sized against ONE of the route's two seam legs, so `SEAM_DEADLINE_EXCEEDED` fires on requests that are succeeding — and then persisting

**Files:**
`src/app/(dashboard)/strategies/new/wizard/steps/ConnectKeyStep.tsx:497-503`,
`src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:961-982`,
`src/lib/wizard/validate-budget.ts:126-138`

**Issue:**
The browser aborts at `validateBudgetMsFor(venue) + WAIT_ABORT_GRACE_MS` — 135 000 ms
on the serialized arm, 45 000 ms on the default arm. That figure models the
`validate-key` budget only. The route it is aborting spends **two** sequential seam
budgets plus a Supabase RPC:

- `create-with-key/route.ts:303` `validateKey` (120 000 ms serialized) →
  `:341` `encryptKey` (30 000 ms) → `:409` `supabase.rpc("create_wizard_strategy")`
- `composite/add-key/route.ts:282 / :317 / :384`, same shape

The phase's own SC-4b table records the route's serialized branch at **150 000 ms of
request budget** (`seam-budgets.invariant.test.ts` header, `create-with-key /
composite/add-key | serialized-venue | 158 500`). The client gives up 15 000 ms *below*
that.

Trace the consequence. If validate itself over-runs, the seam's own 120 000 ms
deadline fires inside the route and the route answers at ≈120 s — comfortably inside
the client's 135 s, so no client abort occurs. The client deadline is therefore
reachable **almost exclusively** in the window where validate SUCCEEDED (say at
110 s) and the route has moved on to `encryptKey` + the RPC. At 135 s the browser
aborts, renders `SEAM_DEADLINE_EXCEEDED`, and emits the funnel event — while the
route runs to completion and writes the `api_keys` + `strategies` rows.

The user is then shown `DEADLINE_CAUSE_TAIL` (`src/lib/wizardErrors.ts:501-502`):
*"Nothing was saved — your key was not stored, and this is not a sign that your key
is wrong."* Both clauses are false on that path. Their next submit hits
`create-with-key/route.ts:429-437` → 409 `DRAFT_ALREADY_EXISTS` ("A wizard session
with this key is already in progress"), a dead end; on the composite arm they get a
second `api_keys` row for the same credentials.

No route reads `request.signal` (`grep -n signal` on both route files returns
nothing), so the abort has no server-side effect whatsoever.

**Fix:** the client deadline must cover the route's worst case, not one leg of it.
Introduce a route-level figure in `validate-budget.ts` and drive both steps from it,
keeping the *advertised* copy figure on the validate budget (the copy promise and the
abort deadline are already deliberately different numbers):

```ts
// src/lib/wizard/validate-budget.ts
/**
 * The ENCRYPT leg the connect routes spend AFTER validate. Hand-typed twin of
 * SEAM_BUDGETS["encrypt-key"].timeoutMs; pinned beside the other two in
 * seam-constants.pin.test.ts.
 */
export const ENCRYPT_KEY_BUDGET_MS = 30_000;

/**
 * When the BROWSER gives up on a connect route. The route spends validate THEN
 * encrypt THEN an RPC, and a client that abandons between them reports a
 * deadline for a request that is at that moment storing the key.
 */
export function connectAbortDeadlineMsFor(exchange: string | null | undefined): number {
  return validateBudgetMsFor(exchange) + ENCRYPT_KEY_BUDGET_MS + WAIT_ABORT_GRACE_MS;
}
```

then in `ConnectKeyStep.tsx:497-503` and `MultiKeyConnectStep.tsx:967-968` swap
`validateBudgetMsFor(...) + WAIT_ABORT_GRACE_MS` for
`connectAbortDeadlineMsFor(...)`. Add a regression case that fails without it: drive
the fake clock past `budget + grace` but below `budget + encrypt + grace` with the
fetch still pending, and assert **no** `SEAM_DEADLINE_EXCEEDED` and **no**
`wizard_error`. Separately, `DEADLINE_CAUSE_TAIL`'s "your key was not stored" must
stop being asserted unconditionally (see CR-02).

### CR-02: `Stop waiting` tells the user "Nothing was saved" while the server continues past validate and stores the key

**Files:**
`src/app/(dashboard)/strategies/new/wizard/steps/ConnectKeyStep.tsx:602-619, 1056-1064`,
`src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:984-1009, 2040-2048`

**Issue:**
The cancel affordance appears at `WAIT_QUEUE_FRACTION` — 48 s into a serialized wait,
12 s into a ccxt one — and its copy is an unconditional factual claim:

> "We stopped waiting. Nothing was saved and your key details are still on this page."

The justification is written twice (`ConnectKeyStep.tsx:605-608`,
`MultiKeyConnectStep.tsx:987-991`): *"`validate-key` is strictly pre-encrypt /
pre-RPC — nothing is persisted server-side."* That is a fact about the **seam call**.
The user is aborting the **route**, which continues (the same docblocks concede this
at `ConnectKeyStep.tsx:610-612` / `MultiKeyConnectStep.tsx:997-1000`) and which, on
any run where validate subsequently succeeds, encrypts the credential and inserts
`api_keys` + `strategies`. A user who cancels at 48 s of a 60 s MT5 validate is told
nothing was saved, and their key is stored.

On the composite arm the panel is left at `status: "editing"` with `apiKeyId: null`
while a member row exists server-side; re-validating produces a duplicate stored
credential, and the single-key arm produces a 409 `DRAFT_ALREADY_EXISTS` on retry.

This is the same root cause as CR-01 but a different surface and a different fix, so
it is listed separately: fixing the deadline arithmetic does not make this sentence
true.

**Fix:** state only what is known. The two facts a cancelling user needs are that the
form still holds their input and that we stopped listening — not a claim about server
state we do not have:

```tsx
{/* ⚠️ NO "nothing was saved" CLAIM. Aborting stops the BROWSER listening; the
    route runs on past validate into encryptKey and the create RPC, so the key
    may well be stored. Say what is known. */}
We stopped waiting for your broker. Your key details are still on this page —
if the check finished on our side, connecting again will pick it up.
```

and make the resubmit path reconcile rather than dead-end (the `DRAFT_ALREADY_EXISTS`
409 on `create-with-key` should resolve to the existing draft on the same
`wizard_session_id` rather than refusing). Both are user-facing; if the reconcile is
out of scope, the copy change is not.

### CR-03: An MT5 member panel silently drops the broker server and renders no field to re-enter it

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:94-140, 1041-1082, 1648-1651, 1904-1922`

**Issue:**
`MultiKeyConnectStep`'s private `EXCHANGES` array (`:94-140`) carries **no MT5 card** —
it spreads only `SFOX_UI_ENABLED`, and `MT5_UI_ENABLED` is not even imported into this
file. The only way an MT5 key reaches a member panel is the UAT/F-4 draft carry-over
(`enterMulti`, `:832-854`) — which is exactly the path plan 5's own tests drive
(`MultiKeyConnectStep.test.tsx`, `enterMultiFromMt5Draft`).

For such a panel `EXCHANGES.find((e) => e.id === "mt5")` is `undefined`, so:

- `validatePanel:1042` `requiresPassphrase = undefined?.requiresPassphrase ?? false` → **false**
- `validatePanel:1079` posts `passphrase: requiresPassphrase ? p.passphrase : null` → **`null`**

The broker server the user typed in State A is dropped from the request body. The
`add-key` route will reject it (`KEY_MISSING_REQUIRED_FIELD`) or probe against no
server at all — and `KeyPanel:1904` renders the passphrase input only when
`requiresPassphrase` is true, so **there is no field on screen to supply it**.
`canValidate:1716-1721` does not gate on it either, so the submit button is enabled
for a request that cannot succeed.

Same panel, same cause: `keyLabel`/`secretLabel` fall back to "API Key"/"API Secret"
(losing "MT5 login" / "Investor password" and the investor-vs-master steer), no
exchange card renders `aria-pressed="true"`, and the validated summary chip at
`:1806` renders `active?.name` → empty. `toRehydratedPanel:559-590` casts
`member.exchange as ExchangeId` and lands in the same state for a rehydrated MT5
composite member.

The missing card predates this phase, but plan 5 builds per-panel serialized-venue
budgets, copy and deadlines for a venue whose only route into a panel is this broken
one, and its tests assert the wait card on that panel while the request it produces is
malformed.

**Fix:** give the composite step the same MT5 card the single-key step has, gated on
the same flag, so the shared `activeOption` lookup resolves:

```ts
import { SFOX_UI_ENABLED, MT5_UI_ENABLED } from "@/lib/utils";
// …
  ...(MT5_UI_ENABLED
    ? [{
        id: "mt5" as const,
        name: "MT5",
        caption: "Live investor (read-only) login. Forex & CFD.",
        requiresPassphrase: true,
        credentialLabels: { key: "MT5 login", secret: "Investor password" },
        credentialPlaceholders: {
          key: "Your MT5 account number",
          secret: "Your read-only investor password",
        },
      }]
    : []),
```

and extend `ExchangeOption` here with the `passphraseLabel` / `passphraseSecret` /
`passphraseHelper` / `secretHelper` fields the panel needs, or lift the single-key
step's option table into a shared module. Add a case that asserts the POST body for a
draft-carried MT5 panel carries the broker server, not `null` — the existing mocks
never inspect the body.

### CR-04: Neither step aborts on unmount, so a completed validate can advance the wizard after the user has left the surface

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/ConnectKeyStep.tsx:432-439, 463-510, 746-751`

**Issue:**
`ConnectKeyStep` owns an `AbortController` (`abortRef`) but nothing aborts it on
unmount — the only cleanup (`:505-509`) clears the three timers. The reachable path:
the user selects MT5, submits (a 120 s wait), and clicks the `footerSlot` control
"+ Add another key window" — which is **not** disabled while `submitting` is true
(`MultiKeyConnectStep.tsx:1470-1479` renders it unconditionally). `enterMulti` flips
`mode` to `"multi"`, `ConnectKeyStep` unmounts, and its in-flight request keeps
running with no controller left holding it and no deadline timer (the effect cleanup
cleared it).

Up to two minutes later the request resolves and the still-live async closure calls
`onSuccess({ strategyId, apiKeyId, exchange })` (`:746-751`) — the prop threaded
straight through to `WizardClient`. The wizard advances past `connect_key` with a
single-key strategy, discarding the two member panels the user has been filling in
since. There is no mounted guard on that call.

The path predates the phase, but the phase quadrupled the window (30 s → 120 s) and
introduced the controller that makes the fix a two-line cleanup, so it is in scope
here.

**Fix:**

```tsx
// ConnectKeyStep.tsx — beside the other effects
useEffect(() => {
  return () => {
    // Unmounting is not a verdict: stop listening AND stop the outcome arms
    // firing into a component the user has navigated away from.
    abortReasonRef.current = "user";
    abortRef.current?.abort();
  };
}, []);
```

and belt-and-braces, gate the success arm on a `mountedRef` so `onSuccess` cannot
advance the wizard from a dead closure. The composite step needs the mirror of this
(see WR-03). A regression case: start a validate, unmount, resolve the fetch 200, and
assert `onSuccess` was not called.

## Warnings

### WR-01: The A-25 equality is one request-overhead term SHORT, and its derived guard measures the wrong quantity

**Files:** `src/lib/resilient-fetch.ts:268-288, 1573, 1578`, `src/lib/seam-constants.pin.test.ts:797-857`

**Issue:** two separate gaps in the same coupling.

**(a) The equality does not cover the interval it has to cover.** A-25's predicate
(`resilient-fetch.ts:1573`) needs the tombstoned key to still be READABLE when the
doomed request records its failure. Take a request admitted at `A − ε`, a lock armed
at `A` with `ttlS = 30 + 90 = 120 s` (`:1578`). That request's failure is recorded at
approximately `A − ε + (initial breaker check ≤ BREAKER_STORE_TIMEOUT_MS) + 120 000
(the fetch deadline) + (the read inside recordSeamFailure ≤ BREAKER_STORE_TIMEOUT_MS)`
— i.e. ≈ `A + 124 000`, against a key that vanishes at `A + 120 000`. The guard reads
`existing === null`, arms a fresh cooldown on stale evidence, and A-25 is violated at
exactly the boundary and exactly the row it was sized against. The quantity the
tombstone must span is the request's admission-to-record LIFETIME, not its `timeoutMs`.

**(b) The derived guard measures `timeoutMs`, not the retried leg's wall clock.**
`longestTimeoutMs` (`seam-constants.pin.test.ts:626-630`) takes `Math.max` over
`row.timeoutMs`. The real charge is `(1 + retries) × timeoutMs + SEAM_RETRY_BACKOFF_MS
+ SEAM_RETRY_JITTER_MAX_MS` — the same arithmetic SC-4b already performs one file
over. Today the two agree by luck (the longest row has `retries: 0`; the retried rows
are 15 000 ms). Grant `validate-key-serialized` a retry, or raise `process-key-enqueue`
past 60 000 ms, and A-25 breaks while the assertion whose message says it is "the ONLY
assertion in this file that can see it" stays green.

**Fix:** reduce over the lifetime, and give the ceiling the margin the overhead needs:

```ts
function longestRequestLifetimeMs(
  table: Readonly<Record<string, { readonly timeoutMs: number; readonly retries: number }>>,
): number {
  return Math.max(
    ...Object.values(table).map(
      // (1 + retries) attempts, plus the worst-case interval before the retried leg.
      (row) => (1 + row.retries) * row.timeoutMs + (row.retries > 0 ? 500 : 0),
    ),
  );
}
```

and either raise `BREAKER_LOCK_TOMBSTONE_S` so the ceiling exceeds the lifetime by at
least `2 × BREAKER_STORE_TIMEOUT_MS`, or lower the serialized budget. Both directions
are a same-commit change to the hand-typed seconds in the assertion, exactly as its
own message demands.

### WR-02: The derived A-25 assertion's vacuity floor is pinned to the current maximum, so a legitimate budget CUT reds with a message that sends the reader to the wrong fix

**File:** `src/lib/seam-constants.pin.test.ts:821-826` (with `:828-857`)

**Issue:** the floor asserts `longest >= 120_000` and the ceiling asserts
`longest <= 120_000`. Together they pin the longest budget to **exactly** 120 000 ms.
That is not what a vacuity guard is for. Phase 155 is explicitly chartered to *tighten*
this provisional number (`validate-budget.ts:35-40`, the row's own `notes`), and when it
does, the floor reds first with:

> "The longest seam budget derived below 120 000 ms. Either a real budget was cut (a
> separate question) or the rows no longer carry timeoutMs and the reducer is reading
> undefined."

— a message whose remedy ("fix the derivation, never the floor") is wrong for the
case that will actually trigger it. The floor exists to catch `-Infinity` from an empty
or mis-shaped table; it should be a small hand-typed number well below any real budget,
with the "is this table sane" question answered by the row-count check that already
sits above it.

**Fix:**

```ts
expect(
  longest,
  "The longest seam budget derived below 15 000 ms — no row in this table is that " +
    "short, so the reducer is reading an empty or mis-shaped table rather than a " +
    "real cut. Fix the derivation, never this floor.",
).toBeGreaterThanOrEqual(15_000);
```

A deliberate budget cut then reds only the assertions that should red (the literal
pins and the client-agreement pin), each with a message that names the right edit.

### WR-03: A panel removed — or the whole step unmounted — mid-validate leaks an unabortable credential-carrying POST with no deadline

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:910-913, 960-982`

**Issue:** `doRemove` (`:910-913`) filters the panel out of state and does nothing
else. The panel's controller stays in `abortControllersRef` until the request settles,
and — worse — `anyValidating` (`:960`) recomputes to `false`, so the step's one
interval is cleared and **the client deadline for that request is gone**. The POST runs
to whatever the platform allows with no client bound at all, which is the exact
property `:955-957` claims is closed ("it does give up, so no request can hold this tab
open forever").

The step's unmount has the same hole: the interval effect's cleanup clears the timer
but never walks `abortControllersRef`.

**Fix:**

```ts
const doRemove = useCallback((idx: number) => {
  const gone = panelsRef.current[idx];
  if (gone) {
    // A removed panel's check belongs to nobody. Abort it rather than letting it
    // run past the deadline this step no longer enforces for it.
    abortReasonsRef.current.set(gone.id, "user");
    abortControllersRef.current.get(gone.id)?.abort();
  }
  setAnnouncement(`Key ${idx + 1} removed`);
  setPanels((prev) => prev.filter((_, i) => i !== idx));
}, []);

// and, once, for unmount:
useEffect(() => {
  const controllers = abortControllersRef.current;
  return () => {
    for (const c of controllers.values()) c.abort();
  };
}, []);
```

### WR-04: `ConnectKeyStep`'s 300 ms mount gate can fire AFTER the request finished, leaving a ghost card whose only control does nothing

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/ConnectKeyStep.tsx:480-482, 505-509, 825-840`

**Issue:** the `mountGate` timeout is cleared **only** by the timer effect's cleanup,
which runs when React commits the `setWaitStartedAt(null)` from the `finally`. React
schedules passive-effect cleanup at normal Scheduler priority; the timeout is a
macrotask. For a request answering at, say, 250 ms on a loaded main thread, the
ordering `finally → setShowWaitCard(false)` … `mountGate → setShowWaitCard(true)` is
reachable, and nothing after it ever sets `showWaitCard` back to `false` until the next
submit. The result is a card mounted over a finished request with a frozen `0s`
counter, and (past the 40 % rung) a `Stop waiting` button that calls
`abortRef.current?.abort()` on a ref the `finally` already set to `null` — a control
that does nothing.

The composite step is immune by construction (its gate is derived from the ticked
`waitElapsedMs`), which is worth noting because the two surfaces disagree here.

**Fix:** make the timeout self-guard rather than depend on cleanup ordering:

```ts
const waitStartedAtRef = useRef<number | null>(null);
// …in handleSubmit, beside setWaitStartedAt: waitStartedAtRef.current = started;
// …in the finally, beside setWaitStartedAt(null): waitStartedAtRef.current = null;

const mountGate = setTimeout(() => {
  // The request may have finished between the schedule and the fire.
  if (waitStartedAtRef.current === waitStartedAt) setShowWaitCard(true);
}, WAIT_CARD_MOUNT_DELAY_MS);
```

### WR-05: `validatePanel` dereferences `panelsRef.current[idx]` with no guard, while its sibling handler has one

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:1034-1040` (cf. `:1003-1005`)

**Issue:** `handleStopWaiting` opens with `const p = panelsRef.current[idx]; if (!p) return;`.
`validatePanel` opens with `const p = panelsRef.current[idx]; if (p.status === …)` —
no guard. `panelsRef` is synced in an effect (`:643-645`), so it lags state by one
commit; a click landing between a removal and that sync throws
`TypeError: Cannot read properties of undefined` out of an unawaited async callback,
which surfaces as an unhandled rejection and leaves the panel wedged with no error
state. Cheap to close, and the asymmetry between two adjacent handlers reading the same
ref the same way is itself a maintenance trap.

**Fix:**

```ts
const p = panelsRef.current[idx];
if (!p || p.status === "validating") return;
```

## Info

### IN-01: The composite wait card mounts at ~1 s, not the UI-SPEC's 300 ms

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/MultiKeyConnectStep.tsx:1700-1714`

The gate is `p.waitElapsedMs >= WAIT_CARD_MOUNT_DELAY_MS`, and `waitElapsedMs` only
moves on the step's 1 s tick, so the first value that can satisfy it is ~1000. The
docblock records this as deliberate ("please do not 'fix' it by adding one"), and it
satisfies the *property* (never earlier than 300 ms) — but the two connect surfaces
now show the card ~700 ms apart for identical requests, and the constant's name
promises a mount delay it does not deliver here. Worth a one-line note on
`WAIT_CARD_MOUNT_DELAY_MS` that it is a FLOOR at this surface and an exact delay at the
other, so the next reader does not "reconcile" them in the wrong direction.

### IN-02: The abort-grace assertion is near-tautological

**File:** `src/lib/wizard/validate-budget.test.ts:149-152`

`expect(validateBudgetMsFor("mt5") + WAIT_ABORT_GRACE_MS).toBeGreaterThan(VALIDATE_KEY_SERIALIZED_BUDGET_MS)`
restates `WAIT_ABORT_GRACE_MS > 0` given the literal pin one line above and the fact
that both operands resolve to the same constant. It cannot fail for any value the line
above admits. The property actually worth pinning after CR-01 is that the client
deadline exceeds the ROUTE's worst case (validate + encrypt), not the validate leg.

### IN-03: A backward system-clock jump renders a negative elapsed figure

**File:** `src/app/(dashboard)/strategies/new/wizard/ValidateWaitCard.tsx:232`

`Math.floor(elapsedMs / 1000)` with `elapsedMs = Date.now() - waitStartedAt` renders
`-1s` (and worse) if the wall clock steps backward mid-wait — an NTP correction or a
laptop resume. `Math.max(0, …)` costs nothing and keeps the one visible number in the
card honest under the Numbers Contract.

### IN-04: Raising the tombstone widened the accepted breaker-lock span from 90 s to 120 s

**File:** `src/lib/resilient-fetch.ts:1095-1108`

`MAX_BREAKER_LOCK_SPAN_MS` is derived, so D-26 silently widened both the span check and
the one-sided absolute-expiry check by 33 %: a corrupt or mis-written lock value can
now hold every seam route open for 120 s instead of 90 s, and the clock-skew tolerance
recorded in the 141.2 review (`writerNow − readerNow > BREAKER_LOCK_TOMBSTONE_S`)
loosened by the same amount. Both are acceptable consequences of the coupling, but
neither is mentioned in the D-26 notes that otherwise enumerate what moves with this
constant.

### IN-05: `handleStopWaiting` can leave a stale `"user"` abort reason when nothing is in flight

**File:** `src/app/(dashboard)/strategies/new/wizard/steps/ConnectKeyStep.tsx:616-619`

`abortReasonRef.current = "user"` is written before the `abortRef.current?.abort()`
optional call, so pressing the control after the request settled (a race with the
`finally` at `:838`) records a reason with no controller to consume it. It is cleared
on the next submit (`:639`) so nothing reads it stale today, but the composite step
takes the stricter shape (delete-per-attempt at `:1256-1257`); matching it removes the
question.
