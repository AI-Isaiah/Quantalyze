`job_worker.py` (×2) and `allocator_positions.py` all took it — so two wizard submissions both

refusal routed to the existing transient 424 — and the serialization is proven by a test whose
observed pre-fix trace is `['login-start', 'login-start', …]`.

## Task 1 — `mt5_terminal_lease` (commit `65ba18cc`)

`analytics-service/services/mt5_concurrency.py`:

| Symbol | Anchor | What |
|---|---|---|
| `_MT5_LEASE_WAIT_S` | `:95` | `float(os.getenv("MT5_LEASE_WAIT_S", "20.0"))` — same `os.getenv(..., default)` convention as `_MT5_DERIVE_READ_TIMEOUT_S` (`:59`) and `_MT5_RESTART_TIMEOUT_S` (`:71`) |
| `_MT5_LEASE_WAIT_LOG_THRESHOLD_S` | `:101` | 0.5 s — log only a *non-trivial* queue wait, so the signal is not buried under uncontended acquires |
| `class Mt5TerminalBusyError` | `:179` | plain `Exception` |
| `@asynccontextmanager mt5_terminal_lease` | `:196-263` | the lease |
| the corrected SCOPE comment | `:147-167` | see (d) below |

**(a) The bound states D-29 in full** (`:75-94`): it bounds the **acquisition** of the terminal,
which is a different thing from the operation timeout; every other ceiling in this module and at
the three job call sites sits *inside* the lock, so a queued caller's own timer starts only once it
already holds the terminal and its wait for the terminal is unbounded. It applies to the
**interactive** path only — the batch passes `wait_s=None` and keeps patient unbounded queueing,
because bounding a sequential daily sync converts serialization into **failure**.

**(b) The typed refusal** (`:179-194`) is deliberately a plain `Exception`, not an
`Mt5ClientError` subclass, exactly as `_Mt5PostReadVerificationError` (`:265`) is and for the same
structural reason: the credential classify/stamp arms match on `Mt5ClientError`, so a busy terminal
that inherited from it could be absorbed into a **user-attributed** verdict and blame a working key
for our own queue. It carries no host, port, terminal key, queue depth or account value.

**(c) The lease** is built on `_mt5_terminal_lock_for(terminal_key)` — the ONE registry — and
declares no dict of its own:

```python
    lock = _mt5_terminal_lock_for(terminal_key)
    queued_at = time.monotonic()

    if wait_s is None:
        await lock.acquire()
    else:
        try:
            await asyncio.wait_for(lock.acquire(), timeout=wait_s)
        except asyncio.TimeoutError:
            logger.warning(...)          # names the BOUND only, never the key/host/port
            raise Mt5TerminalBusyError(...) from None

    waited_s = time.monotonic() - queued_at
    try:
        if waited_s >= _MT5_LEASE_WAIT_LOG_THRESHOLD_S:
            logger.info("mt5_terminal_lease: waited %.2fs for the terminal …", waited_s)
        yield
    finally:
        lock.release()
```

Both halves of the release discipline are structural, not conventional: the release is in a
`finally` (a caller's exception cannot strand the lock), and the timed-out branch raises **before**
the `try` is ever entered, so it cannot release a lock it never held.

**(d) The stale scope comment was corrected** (`:147-167`). It claimed the lock does not serialize
"the separate FastAPI validate process". `main.py`'s lifespan runs the dispatch/watchdog/enqueue
worker loops as background asyncio **tasks inside the API process**, so router and worker share one
event loop and the lock **does** serialize them today — which is what makes it correct for the
router to take this lease rather than race the worker. The honest remaining gap is now stated as
**replicas** (each with its own loop, registry and Lock objects), naming D-33's single-replica pin
and keeping the plan-02 login bracket as the cross-replica net. No cross-process claim is made.

**Placement, which is the whole point.** The lease is acquired *before* the `try:` whose body holds
the end-to-end deadline, so `_MT5_VALIDATE_DEADLINE_S` starts counting when we **hold** the
terminal. The release stays inside the `async with`, so the terminal is held until our transport is
given up (the Pitfall-6 `finally` at `:673` is byte-unchanged and still lexically outside the
deadline's `wait_for`). Lexically: lease `:595` → deadline `:600` → finally `:673` → release
`:705` → `except Mt5TerminalBusyError` `:717`.

**The key.** `f"{host}:{port}"`, byte-identical to `Mt5Client.terminal_key` (`mt5_client.py:638-651`,
`return f"{self._host}:{self._port}"`). It must be re-derived rather than read off a client because
the lease has to be held **before** construction — construction is what opens the racing rpyc
socket. A divergent format would yield a different `Lock` object and serialize nothing; a test
computes the expected key by **calling the shipped property** rather than retyping its format.

**The refusal.** `Mt5TerminalBusyError` → the pre-existing
`VenueTransientHTTPException(424, code="NETWORK_UNAVAILABLE", detail=NETWORK_ERROR_DETAIL,
recoverable=True)`, with its own distinct WARNING naming the bound only. Rationale written at the
site: genuinely recoverable (the terminal frees up), so "try again" is real advice — WIZFORM-04's
"copy names an action" for the server leg; and no terminal key, host, port, queue depth or wait
value reaches the body — WIZFORM-03. The comment records that the user-visible "waiting for the
connection" state, the long-wait card and `Stop waiting` are **Phase 153.4's** (D-05 / D-29's UI
clause) and that 153.4 may re-map this arm onto 153.1's `serialized` code — with an explicit ⛔
that nothing here depends on it. **No new user-facing code was minted. Zero TypeScript files.**

**`_assert_expected_login` is byte-unchanged** (`:457`); only its comment gained a paragraph
recording that the race it detects is now also *prevented* in-process by the lease, that the bracket
remains because an `asyncio.Lock` does not serialize across replicas, and that "a prevention is not
a licence to delete the detection".

## What stays UNVERIFIABLE offline — owner Phase 155 (MT5-VERIFY)

CI never installs `mt5linux`. Everything above runs on **real `asyncio.Lock`s** and the injected
`Mt5Client` double, so the lease logic itself — acquisition, ordering, the bound, the release
discipline — **is** genuinely covered offline. What is not:

1. **The real distribution of lease-wait durations under concurrent load.** Whether 20 s is the
   right bound is an empirical question this plan cannot answer: it installs a number and asserts
   its **placement and nesting**, not its **sufficiency**. Plan 153.3-05 instruments the wait
   (`stage` + `duration_ms`); **Phase 155** sets the final value (D-27 / D-32).
2. **Whether a real MT5 terminal's IPC region is fully covered by this lease.** The lease serializes
   every *in-process* caller that takes it. Two sites still reach `mt5.shutdown()` outside it —
   `services/exchange.py`'s `aclose_exchange` mt5 arm and `services/ingestion/mt5.py` — which is the
   residual **D-35 / wave 6** owns and which no offline test here can close.
3. **Cross-replica behaviour.** An `asyncio.Lock` serializes nothing across replicas; that this is
   safe rests entirely on D-33's ops pin (single replica) plus the `_assert_expected_login` bracket
   as the detector. Neither is observable from this suite.
