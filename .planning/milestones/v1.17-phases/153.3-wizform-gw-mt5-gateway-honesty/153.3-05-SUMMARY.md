# Phase 153.3 Plan 05: instrument before tuning Summary

**One-liner:** `mt5_client.py` and the validate router contained **zero** timing — no
`perf_counter`, no elapsed capture, no clock of any kind except the timeouts themselves —
which is precisely why every number this project has about MT5 latency is
**right-censored at a ceiling**; every MT5 round-trip now emits a structured
`mt5.stage` event carrying `stage` + `duration_ms` **on success and on failure alike**,
the terminal **queue wait is timed apart from the terminal work**, every validate
terminates in exactly **one** of ten categorical outcomes, no credential can structurally
reach any of it, **not one timeout was moved** (D-27), and the runbook now states the
single-replica invariant as a **correctness** constraint, the terminal option that
currently makes every validation fail, and the fact that the whole chain is a guess with
**Phase 155** named as the owner that replaces it with data.

**(a) The allow-list IS the hygiene mechanism.** `emit_mt5_stage_event` accepts six
fields and no others: `stage`, `duration_ms`, `ok`, `terminal_key`, `error_class`,
`outcome`. There is no `**kwargs`, no `extra`, no `context` — so "just add a bit of
context at the call site" is not expressible. `terminal_key` is `host:port`, our own lock
key, never a user value. ⛔ The exception **CLASS** is emitted, never its message:
`mt5linux` f-string-interpolates the investor password into the remotely-eval'd source,
so a remote traceback's text is a real credential.

**(b) The bracket sits INSIDE `_guarded_read`'s conversion, deliberately.** Two
consequences: the measured span is the raw round-trip rather than round-trip + our own
conversion, and `error_class` names the raw transport class (`RuntimeError`, an rpyc
`EOFError`, a socket timeout) instead of the uniform `Mt5ClientError` that every failure
would otherwise report — which is what makes a 30 s censor separable from a fast
rejection in a single Railway query.

**(c) `stage=None` is the byte-identical old path.** `_guarded_read`'s new parameter
defaults to `None`, and on that branch the code is `return call()` exactly as before.

**(d) ⭐ Root cause found by the FULL suite, not by `-k mt5`.** The five new telemetry
tests passed alone and **failed in a full run**. Not a flake:
`services/logging_config.py:233` configures structlog with
`cache_logger_on_first_use=True`, so a module-level `structlog.get_logger(...)` proxy
freezes whatever processor chain was installed at its **first use** and ignores every
later `structlog.configure`. That is a **production** defect, not merely a
test-visibility one — `main.py` configures logging inside the lifespan, long after this
module is imported, so a proxy bound before that point would emit through a chain
**without** the `_redact_processor` PII scrub. Fixed by binding per call (`_stage_logger()`),
which costs a proxy allocation next to a network round-trip and cannot go stale.
Documented at the function so the next reader does not "optimise" it back.

**(a) Why the outcome event lives at a function boundary, not in the release block.**
The plan said to *"put the emission where the release already lives so the runs-on-every-path
property is inherited."* That block sits **inside** `async with mt5_terminal_lease(...)`,
so it never runs for the two categories that never reach the terminal at all —
`lease_busy` (refused at the acquisition bound) and `gateway_unconfigured` (refused before
any client is built) — plus the two offline credential-shape refusals. Those are exactly
the outcomes an operator most needs counted. The property is therefore inherited from a
`try/finally` at a **new function boundary**: `_validate_mt5_key` became a thin bracket
over `_validate_mt5_key_probe`. Recorded as a deviation below.

**(b) `outcome` starts at `"unknown"`, not at a plausible default.** An arm that forgets
to set it produces a VISIBLE `outcome="unknown"` in the telemetry rather than silently
borrowing a neighbouring category and corrupting the counts a Phase-155 histogram is
built from.

**(c) The category map** — every one produced by a branch the code already took:

| Site | `outcome` |
|---|---|
| pre-probe parse: wrong/missing server | `wrong_server` |
| pre-probe parse: bad login/password shape | `auth` |
| `MT5_GATEWAY_HOST`/`PORT` unset or malformed | `gateway_unconfigured` |
| connect stage timeout / connect failure | `gateway_unreachable` |
| probe stage timeout · account mismatch · transient `Mt5ClientError` · undetermined-because-signal-unavailable | `transient` |
| `classify_mt5_login_error` → auth / wrong_server | `auth` / `wrong_server` |
| end-to-end deadline expiry | `deadline_exceeded` |
| verdict `trade_capable` | `master_rejected` |
| verdict `undetermined` + terminal trade permission off (D-31) | `undetermined` |
| investor success | `read_only` |
| `Mt5TerminalBusyError` at the acquisition bound | `lease_busy` |

`undetermined` is kept distinct from `gateway_unconfigured` even though both answer the
same HTTP code: the D-31 signal (the terminal ran and refused to classify) is what Phase
155 needs counted on its own.

**(d) `ok` is the SUCCESS predicate, not "no exception".** `ok = outcome == "read_only"`.
A master-password rejection is a *correct verdict* but not a successful validation, and
counting it as ok would put a fast 400 in the same bucket as a completed terminal read.

**(e) Hygiene.** Both new emissions pass only `stage`, `duration_ms`, `ok`,
`terminal_key`, `outcome` and (on the refusal) the literal string
