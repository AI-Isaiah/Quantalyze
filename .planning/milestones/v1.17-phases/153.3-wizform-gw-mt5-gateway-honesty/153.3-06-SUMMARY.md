**(a) One implementation, two names.** `_teardown_transport(mt5_obj, *, who, stage)`
carries the defensive `getattr` chain to `_MetaTrader5__conn` (the `_default_connect`
"ponytail" register, with the `mt5linux==0.1.9` pin named as what makes it stable),
its `close()`, the swallow-and-log-WARNING, and the ⛔ never-silently-no-op WARNING.
`close()` and `release()` are both: gate on `_closed` → set it → delegate.

Two design points worth stating:
- `mt5_obj` is a **parameter**, not `self._mt5`, because `restart()` disposes the
  **stale** connection after the fresh one is already swapped in (WR-01).
- `stage=None` runs the close **without** a `_timed` bracket — that is `restart()`,
  which is deliberately ONE timed stage end to end (wave 5's decision: recovery
  latency is the actionable number). A nested `close`/`release` event there would
  double-count and misreport.

**(b) ⭐ The telemetry stage set stayed at NINE, against wave 5's prediction.** Wave
5 flagged that if wave 6 deleted the teardown, `stage="close"` would disappear and
`test_every_mt5_round_trip_emits_its_stage_event`'s hand-typed nine would have to be
re-cut to eight. It did **not** — because the stage name is a parameter of the shared
teardown, `close` still emits, and it now measures **what `close()` actually does**
(the transport teardown) instead of a call that no longer exists. Recorded here
explicitly so this reads as a decision, not as the flagged surprise being missed.

**(c) `restart()` — keep the shutdown, stop leaking the socket.** `stale.shutdown()`
is untouched. Added after it, in its **own** `try`: the same transport teardown
against `stale`. Every restart previously leaked one socket against the gateway's
`ThreadedServer` — a slow resource bleed on the exact recovery path that runs when
the terminal is already unhealthy. Neither dispose step is bounded here; the
caller's `_MT5_RESTART_TIMEOUT_S` (`mt5_concurrency:68-70`) is what abandons a stale
socket an abandoned reader is parked on, exactly as it already did for the shutdown.

## Task 2 — the ast-DERIVED roster (commit `85e26f0c`)

`analytics-service/tests/test_mt5_shutdown_roster.py`, **new**, 12 cases.

**The scanner.** `ast.parse` by **path** over every `*.py` under
`analytics-service/` excluding any `tests` / `.venv` / `venv` / `site-packages` /
`__pycache__` path segment. `scripts/` IS included — an operator script that shuts
the shared terminal down is exactly as destructive as a service that does. ⛔ Never
`inspect.getsource` on an imported module (the `test_exchange.py:83-122` constraint:
importing `routers.exchange` pollutes `sys.modules` and breaks
`test_exchange_router_c0202`'s stub-reload fixture downstream). The module docstring
states why this must not be "simplified" into a grep: a grep would count the word
`shutdown` in `mt5_client.py`'s own D-35 rationale and in every
`# never call shutdown()` comment — the `EMITTER_RE` failure class, which an AST
makes structurally impossible.

**The hand-typed pins** (⛔ never a derivation compared against its own `len()`):

| Pin | Value | Measured |
|---|---|---|

⚠️ **Plan-text correction (measured, not assumed).** The plan expects the attribute-
reference set to be `{"services/mt5_client.py", "services/mt5_concurrency.py"}`. It
is **`{"services/mt5_concurrency.py"}` alone**: `mt5_client.py` *defines* `restart`
(an `ast.FunctionDef`) and never takes a reference to it, so no `ast.Attribute`
named `restart` exists in that file. Pinning the plan's set would have been a pin
that fails on day one. The definition is pinned **separately** (`RESTART_DEFINITION_FILE`),
so "a second definition appeared" is also caught.

⚠️ **Deviation — outermost, not innermost, enclosing def.** The plan's permitted
pin is `("services/mt5_client.py", "restart")`. The innermost enclosing def of the
surviving call is wave 5's `_reconnect_then_dispose_stale` **closure**, so an
innermost pin makes the plan's own literal fail. The scanner reports the
**outermost** def and carries the full dotted chain for the failure message.
Rationale beyond making the pin true: permission is granted to the *verb*
`restart`, not to whatever nested helper it uses this month — and an innermost pin
would report an unfamiliar name for a `shutdown()` added to a *new* closure inside
`close()`, exactly when a clear name matters most.

⚠️ **Deviation — a recursive visitor instead of `lineno`/`end_lineno` containment.**
The plan specifies containment arithmetic. A visitor computes the identical
enclosure exactly, cannot be fooled by a multi-line `with` item, and makes the
nested-function rule explicit: entering a nested `def` **RESETS** lease depth,
because a closure defined inside a lease is not executed inside it. Conservative
direction — it can only make the suite redder. Pinned by its own case
(`test_selftest_a_closure_defined_inside_a_lease_is_not_counted_as_held`).

**The assertions.** (1) derived shutdown set == permitted set, with the rule in one
sentence and both directions checked — a *missing* permitted site also reds, because
"nobody can heal a wedged pipe" is not an improvement. (2) every restart site is
lease-held. (3) the indirection pin + the definition pin. (4) anti-vacuity: file
floor, `shutdown_sites >= 1` (⭐ load-bearing — after Task 1 exactly one site
survives, so "matched nothing" is one silent breakage from "all clear"),
`restart_sites >= 4`, and "some module defines `restart`". Each message spells out
the PREDICATE, per PATTERNS §2.

**The self-tests — 8, in two groups.**

*Scanner (4):* a real `conn.shutdown()` inside a `def` is returned with the right
enclosing name; a source where `shutdown` appears **only** in a comment, a docstring
and a string literal returns **nothing** (what a grep cannot do); the known-present
REAL site is found in the real tree; and a `from mt5 import shutdown; shutdown()`
bare-`ast.Name` indirection is caught.

*Lease predicate (4):* ⭐ a **deliberately UNHELD** synthetic site next to a held one,
asserted as `{"held": True, "not_held": False}` — without this, "all sites held" is
indistinguishable from a predicate that always returns `True`; an unrelated
`async with some_other_lock(...)` reports **not** held (a predicate that merely asked
"inside *some* async with?" would pass every site holding an unrelated session);
wave 4's `mt5_terminal_lease` wrapper is honoured as well as `_mt5_terminal_lock_for`;
and the closure rule above.

## What stays UNVERIFIABLE offline — owner **Phase 155 (MT5-VERIFY)**

CI never installs `mt5linux`; every path above is exercised through the injected
`_connect` double and its stubbed `_MetaTrader5__conn`. What these tests prove is
that the teardown does exactly one thing and that no code path can reach the other.
They cannot prove:

1. **That "attach once, never tear down" is sustainable.** Nobody has observed an
   MT5 IPC pipe held open across days of daily syncs. This plan's central act is
   *not calling* something; its live consequence — pipe health, terminal
   file-handle growth, whether `mt5linux`'s `ThreadedServer` reclaims anything on
   its own — is unmeasured. ⭐ This is the single most important live check the
   phase leaves behind.
2. **That `restart()` actually heals a genuinely wedged Wine terminal.** With every
   other teardown gone, `restart()` is now the **only** recovery mechanism in the
   system. Offline it is proven to reconnect first, shut the stale connection down,

   whether `shutdown()` on a connection an abandoned reader is parked on is safe —

5. **Cross-replica behaviour.** Covered only by an ops control (D-33's runbook pin)
