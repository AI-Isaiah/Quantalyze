## Task 1 — `Mt5Client.release()` (commit `27ab644a`)

**`services/mt5_client.py:533-584`** — `def release(self) -> None`, placed immediately after
`close()` (`:521-531`, byte-unchanged) and before `restart()` (`:586`).

Behaviour, in the order that makes the guarantee structural rather than conventional:

1. `if self._closed: return`, then `self._closed = True` — **before** any teardown. After a
   `release()`, `close()` is a no-op and **cannot** reach `shutdown()` on that instance. This is why
   the D-30 property survives an "also call close() for safety" regression at any call site.
2. Best-effort close of the rpyc **transport** via `getattr(self._mt5, "_MetaTrader5__conn", None)`
   → `.close()`. mt5linux 0.1.9 exposes no transport close of its own (its `shutdown` forwards to
   MetaTrader5), so this reaches the same name-mangled private attribute `_default_connect` already
   sets `sync_request_timeout` on (`:167-193`), with a comment in the same "ponytail" register naming
   the `==0.1.9` pin as what makes it stable.
3. No reachable transport close → a **WARNING** naming that fact ("the connection is abandoned, not
   closed"). Never a silent no-op.
4. A raising teardown → swallowed with a WARNING, exactly as `close()` does at `:530-531`.

**Module docstring** (`:12-14`, `:59-72`) gained `release` to the surface list and a new **Teardown**
bullet stating the two verbs and why they are not the same statement.

`_FakeMt5` gained a shaped `_FakeRpycConn` at `_MetaTrader5__conn`
(`tests/test_mt5_client_contract.py:78-96`, `:118-122`), so the release path is genuinely EXERCISED
offline instead of always taking the fallback branch. (Single leading underscore ⇒ the test class does
not re-mangle the name; it is byte-identical to mt5linux's.)

## Deviations from Plan

**1. [Plan sequencing] Task 3's CODE landed in Task 2's commit (`b4ff7332`); Task 3's own commit
carries the recorded residual.**
- **Reason:** Task 2 mandates that the outer deadline live INSIDE the `try:` whose `finally:` tears
  down, and Task 3 mandates that the teardown be `release()` bounded by `_MT5_RELEASE_TIMEOUT_S`. An
  intermediate commit satisfying Task 2 alone would still have called `close()` in that `finally` —
  i.e. it would have shipped a tree that continues to `shutdown()` the shared IPC pipe on every
  validate, which is precisely the defect D-30 exists to delete. Wave 2 refused the same shape for the
  same reason (its deviation 1). Every Task-3 acceptance criterion was still run and evidenced
  independently above.

**2. [Rule 3 — blocking] `tests/test_status_contract_exchange_internal.py::test_s04…` was re-cut,
though it is outside the plan's `<files>`.**
- **Found during:** Task 2, the moment the outer deadline became the first `wait_for` invocation.
- **Issue:** S-04 fired the ceiling by timing out the **first** `wait_for` call, which used to be the
  connect stage and is now the end-to-end deadline. Left alone it walks into the transient 424 arm and
  fails its 503 assertion — and, worse in principle, a future stage could shift it into an arm whose
  assertions happen to match, silently re-pointing an S-row.
- **Fix:** same technique as the validate suite — monkeypatch `_MT5_VALIDATE_STAGE_TIMEOUT_S` to
  0.05 s and give `Mt5Client` a genuinely slow construction, so the **connect stage** fires by name.
  The docstring records the re-cut. `28 passed`.

**3. [Rule 3 — blocking] `tests/test_raw_5xx_census.py`'s subclass-site count 8 → 9.**
- **Found during:** the full-suite gate (it is invisible to `-k mt5`).

## What stays UNVERIFIABLE offline — owner Phase 155 (MT5-VERIFY)

CI never installs `mt5linux`; every assertion above runs through the injected `Mt5Client` /
`_connect` doubles and the env-overridable constants. Three claims are therefore **unproven against a
real terminal**:

1. **Whether 75 s is enough for a real login on a trading day.** This plan installs a number and
   asserts its NESTING; it cannot assert its SUFFICIENCY. Plan 153.3-05 instruments the real per-stage
   duration; **Phase 155** sets the final value (D-27). The honest claim here is *"the budget is now
   one number, bounded, and inside the client's ceiling"* — not *"validation now succeeds"*.
2. **Whether closing the rpyc connection via `_MetaTrader5__conn.close()` actually releases the
   server-side lease** without disturbing the shared `MetaTrader5` module instance. `mt5linux` 0.1.9's
   sdist exposes no other transport seam and rpyc's `close()` is stable across 5.x, so the wiring is
   sound; that the ThreadedServer reclaims the connection cleanly and that a concurrent caller's IPC
   survives is `[DOC]`/reasoned, not observed. The offline double proves we call the right method, not
   what the server does with it.
3. **Whether the end-to-end deadline's cancellation actually unblocks the abandoned rpyc thread.** As
   before this plan, a `to_thread` that times out is ABANDONED, not killed. The deadline bounds the
   *request*, not the thread. Under a genuinely wedged terminal the thread survives until the rpyc
   bound (55 s) expires beneath it — which is exactly why the stage ceiling must stay above the rpyc
   bound and below the deadline, and why that ordering is now asserted.
