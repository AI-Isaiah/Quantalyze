<objective>
⭐ **D-24 — the root cause.** `mt5_client.py:306` calls `self._mt5.initialize()` with **no
`timeout=`**, so MetaTrader5's vendor default of **60 000 ms** applies, *inside* an rpyc
`sync_request_timeout` of **30 s** (`MT5_REQUEST_TIMEOUT_S`, `:82`). The first MT5 call of every
login is therefore **structurally incapable** of returning an MT5-level answer before rpyc gives
up. That is why 9/9 correlated gateway↔worker failures on 2026-08-06/08 cluster at
**30.1–31.0 s** — a fixed ceiling, not a latency distribution
(`153-EVIDENCE-mt5-latency.md` §1a, §3). **No client-side budget can fix this**; it only moves
where the pile-up happens.

⚠️ This is the SAME defect class the codebase already knows about. The ordering guard at
`mt5_client.py:213-219` fails loud on `MT5_LOGIN_TIMEOUT_MS >= request_timeout_s * 1000` — it
covers `login()`, **the instance the author had in mind**, and not `initialize()`, the second
member of the class. **Fixing only `initialize()` re-ships the class defect.** The guard must
cover every MT5 call that carries its own timeout, and a third such call must be unable to land
unregistered.

⛔ **D-25 — `MT5_REQUEST_TIMEOUT_S` stays BYTE-UNCHANGED.** Its own comment (`:75-81`) records
why: a hung terminal must not wedge the SEQUENTIAL worker past the ~90 s healthz budget — the
v1.11 WEDGE-01 class. `Mt5Client.__init__` already accepts `request_timeout_s` (`:203`), so the
validate path constructs its **own longer chain** per instance. Any change to the module
constant has reopened WEDGE-01.

Purpose: make an honest verdict physically able to arrive.
Output: an explicit, registered, guarded timeout on every timeout-carrying MT5 call, and a
per-instance chain the validate path (plan 153.3-03) can lengthen.
</objective>
