# Phase 153.6 Plan 08: the suite stops building a DOM it never uses — Summary

**291 of the 791 test files never touch a DOM, and the suite was constructing a jsdom for every one of them — measured at 989s of the ~1173s of CPU a green parallel run burns; moving them to a `node` project takes 17.2% off the wall clock and 35.9% off the environment cost with the test count, the shard partition and the coverage gate all byte-identical — and the file that was blamed for forcing `--no-file-parallelism` turned out not to be a fetch leak at all but a `next/dynamic` import losing a race against Testing Library's 1000ms default.**

## Performance

- **Duration:** ~100 min (dominated by measurement: 13 full-suite runs)
- **Tasks:** 4/4
- **Commits:** 3 code + 1 docs
- **Files:** 1 created, 10 modified

## T1 — the order-dependent file, and why the stated cause was wrong

`src/app/(dashboard)/allocations/AllocationsTabs.scenario-state-preservation.test.tsx`

The brief's diagnosis: the file has no `fetch` of its own, so it free-rides on
a `globalThis.fetch` mock leaked by whichever file ran before it, and undici
rejects the relative URL when it runs first.

**Half of that is true and none of it is the cause.** The file really does have
no fetch mock, and the rejection really does happen — `[AllocationsTabs]
scenario_list_load_failed { error: 'TypeError: Failed to parse URL from
/api/allocator/scenario/saved' }` is in the isolated-run stderr. But
`ScenarioTabContent` catches that rejection by design (it must: an unloaded
list rendered as "No saved scenarios yet" would be a fabricated fact), so it
never reaches the assertion. **Installing the fetch mock first and re-running
produced a byte-identical failure at the same line.** The diagnosis was
falsified in one run, before any of it was built on.

The real cause, measured. `AllocationsTabs` reaches `ScenarioComposer` through
`next/dynamic` (`AllocationsTabs.tsx:129`). The first
`findByTestId("kpi-strip-mock")` is therefore not waiting on a render — it is
waiting on a **runtime module import** of a ~5,000-line component and its
transitive graph, paid once per worker process. Instrumented with
`performance.now()` around that await, cold in a fresh worker:

```
MEASURE kpi-strip visible after 1359.769 ms
```

against Testing Library's **1000ms** default. That is the whole story, and it
explains every observation the brief recorded: red in isolation under *both*
parallel and serial modes (cold worker either way), green only inside a full
**serial** run (by then the worker has been alive for minutes and the transform
and JIT caches are hot), and green-or-red at random in a parallel full run
depending on where the scheduler put the file. It is order-dependence, but on
**worker warmth**, not on a leaked global.

Fixed with an explicit budget — `findBy` at 10s, the test at 15s, both the
existing repo idiom (`ScenarioCommitDrawer.test.tsx:1219`,
`outcomes.test.tsx:189`) — carrying a comment that says what the wait is for.
The second `it` in the file needs no budget: by then the dynamic chunk is
resolved in the file's own module registry, which is exactly why it always
passed while the first one did not.

**No assertion was changed.** The H-0058 contract — add two strategies, toggle
Beta off, leave to Overview (unmount), return (remount → hydrate), Beta still
off and Alpha still on — is asserted exactly as before. The change is to the
wait budget, not to what is being waited for.

The fetch mock went in anyway, because inheriting the worker's ambient `fetch`
is a real defect even though it is not this one. It is URL-aware: the composer
treats a 200 whose body lacks a `daily_returns` **array** as a retryable
failure (WR-01), so `/returns` is answered in its own shape rather than with a
bare `[]`.

## T1 follow-up — the leak source, named and closed

**Eight sites across seven files assigned `globalThis.fetch = …` directly.**
That is the root cause the brief asked me to name, and it is a class, not a
file:

| file | site | what it leaked |
|---|---|---|
| `src/components/discovery/SimulateImpactButton.test.tsx` | 2 test bodies | `vi.fn(() => new Promise(() => {}))` — **never resolves** |
| `src/components/portfolio/PortfolioImpactPanel.test.tsx` | `mockFetch` helper | per-test impl |
| `src/components/portfolio/ReplacementCard.test.tsx` | `mockFetch` helper | per-test impl |
| `src/components/portfolio/ReplacementPanel.test.tsx` | `mockFetch` helper | per-test impl |
| `src/components/auth/ProfileTabs.test.tsx` | `beforeEach` | a bare `vi.fn()` |
| `src/components/exchanges/AllocatorExchangeManager.test.tsx` | `beforeEach` (the Reconnect describe, the only one of its seven with no `unstubAllGlobals`) | a 200 JSON responder |
| `tests/integration/process-key-thin-adapters.test.ts` | `beforeEach` + an in-test swap + its `finally` | an analytics-service responder |
| `tests/lib/process-key-client.test.ts` | `beforeEach` | a bare `vi.fn()` |

`unstubGlobals: true` and `vi.unstubAllGlobals()` both see **only** what
`vi.stubGlobal` recorded, so every one of those mocks outlived its file and
became the ambient `fetch` for whatever the worker ran next. This is the exact
global-scope twin of the direct-`process.env`-write leak that `vitest.config.ts`
already documents at lines 38-42 — the file said "`unstubEnvs` covers ONLY vars
set through `vi.stubEnv()`" and nobody had followed the same sentence one step
sideways to `globalThis`.

`PortfolioImpactPanel.test.tsx` is the clearest evidence that this was known
and mis-scoped. It carried an `afterEach` with `vi.unstubAllGlobals()` and a
comment conceding *"This file assigns `globalThis.fetch` directly rather than
via `vi.stubGlobal`, so the fence costs nothing today"*. The fence was prose.
It does real work now.

The worst of the eight is `SimulateImpactButton.test.tsx`, whose mock is a
promise that never settles: a later file inheriting it does not fail fast, it
**hangs to the test timeout**.

All eight converted to `vi.stubGlobal("fetch", …)`. Every call site is inside a
`beforeEach` or a test body, so the config's before-each restore cannot strip a
stub the file still needs — verified by running all nine affected files (230
tests, green) and then the full suite.
`src/app/(dashboard)/profile/components/AuditLogSubsection.test.tsx` still
assigns directly and was **left alone**: it captures the original into
`originalFetch` and puts it back in `afterEach`, so it does not leak.

### "Is this the only free-rider?"

No file was found that *fails* without the leaked mocks, and that is now
evidence rather than a hope: the leaks were removed **first**, and the full
suite has since been green nine times. Two of those were run with
`--sequence.shuffle.files`, i.e. two random file orders — 772 passed / 11,652
passed / **0 failed** in both. A file that depended on a neighbour's leaked
`fetch` would have to survive both permutations plus the seven natural-order
runs.

The claim that this proves is precise, and no more: **nothing in the suite
fails when the leaks are gone.** It does not prove no file *silently* changed
which code path it takes — a test that swallows a fetch rejection looks the
same either way. The merged-coverage comparison in T3 below is the only
instrument that would have caught that, and it moved by less than 0.2 points in
the positive direction.

## T2 — the flag was never committed

`--no-file-parallelism` appears **nowhere** in any executable path. Grepped the

- `.github/workflows/ci.yml` — the shards run `npx vitest run --shard=N/2

- Everything else is prose: `.planning/**` verification commands, and two

So there was nothing to edit, and the deliverable is the evidence. The full

## T3 — the environment split, and the CI-compat proof

`environmentMatchGlobs` is gone in vitest 4, so this is `test.projects`, as the
brief specified.

**`vitest.node-env.ts`** holds the opt-in list: 291 `*.test.ts` files that
reference no `window`, no `document.`, no `*Storage`, no `navigator`, no
`matchMedia`, no observer, no `HTML*Element`, no `@testing-library`, no
`react-dom`, no `renderHook`, and no `.tsx` import. Route handlers, pure lib
functions, schema and grep guards, RLS checks. jsdom stays the **default**:
every `.tsx` and every unlisted `.test.ts` keeps it, so the failure direction is
the safe one the brief asked for — a listed file that reaches for `window` dies
at the line that touched it, and an unlisted new file simply gets a DOM.

The list is per-file rather than per-glob because the population is genuinely
interleaved — `src/lib` is 65 node / 66 DOM, `src/__tests__` 64 / 42,
`src/app/api` 42 / 51. There is no directory to point at.

**The trap that cost a run, recorded in the config so it costs nobody else
one.** `extends: true` merges a project into the root with vite's
`mergeConfig`, which **concatenates** arrays rather than replacing them. With
the suite's `include` still at the root, the node project's include resolved to
`INCLUDE ∪ NODE_ENV_TEST_FILES` and it collected all 791 files: 285 failed
files, 2,736 red `ReferenceError: document is not defined`. Scalars (like
`environment`) *do* override, which is what makes the split work at all. The
root `include` is now `[]` with a comment saying why it must stay that way.

File sets are complementary by construction — the node list is the node
project's `include` and the jsdom project's `exclude` — and `vitest list`
confirms the partition: **291 node + 500 jsdom = 791**, no overlap, no gap.
`defaultExclude` is spread back into the jsdom project's exclude, because
setting `exclude` replaces vitest's default rather than adding to it.

The brief made this a hard gate. I ran the **actual CI command sequence**

| | control (before) | with projects | verdict |

`ci.yml`'s vitest transform-cache key now hashes `vitest.node-env.ts` alongside
`vitest.config.ts` — moving a file between projects changes how it is

## Deviations from plan

**1. [Rule 1 — Bug] The brief's root cause for T1 was wrong, and the fix it
implied does not work.** Found during T1. The stated cause (free-riding on a
leaked `globalThis.fetch`) was tested by installing a fetch mock and re-running
in isolation: identical failure. The measured cause is a 1360ms `next/dynamic`
import against a 1000ms `findBy` default. Both remedies shipped — the timeout
because it is the fix, the fetch mock because ambient-`fetch` dependence is a
genuine defect regardless. Commit `385fa00e`.

**2. [Rule 2 — Missing critical functionality] Closed the leak class rather
than the one file.** Found during T1's "is this the only free-rider?"
follow-up. Eight `globalThis.fetch =` sites were invisible to the config's
restore fence. Converting them is what makes the green-suite evidence mean
anything: with the leaks still in place, "no file fails" would only have said
that the leaks were holding. Commit `46efd53b`.

**3. [Rule 3 — Blocking] Root `include` had to move.** Not in the plan, but
`test.projects` cannot work without it — see the concatenation trap above.
Commit `95a9afbd`.

**4. [scope] `ci.yml` cache key.** One line, in the same commit as the config,
because a transform cache keyed on a config file that no longer decides the
environment alone is a stale-cache bug waiting to happen.

Nothing was deferred to `deferred-items.md`; nothing out of scope was touched.
`supabase/**` and `src/app/api/strategies/finalize-wizard/route.{ts,test.ts}`
were left alone for the concurrent sibling agent, as instructed.

## Residual risk

1. **The node list is a source-text classifier's opinion, not a proof.** It was
   built by scanning each file for DOM tokens and validated empirically — the
   node project ran green on the first attempt, 291 files / 3,941 tests — but a
   listed file could in principle import a module that touches `document` only
   on a path no current test takes. It would fail loudly the day that path is
   taken, which is the correct direction, and the fix is to delete one line.

2. **A silent branch shift is not fully excluded.** A test that passes under
   both environments while exercising a different branch would not fail. The
   coverage comparison is the instrument, and it moved by ≤0.17 points upward
   on all four metrics — but that is an aggregate over ~700 source files, so a
   single-file shift could hide inside it.

3. **Timing was measured on a machine under heavy foreign load** (load average
   64-72 on 10 cores, another agent's `tsx` and eight `zsh` children visible in
   `ps`). The interleaved design and the CPU-seconds column are what make the
   ~17% credible; a quiet-machine re-run would tighten the interval and would
   most likely move the number **up**, since contention compresses the
   difference between two runs that both saturate the box.

4. **New DOM-free files get no speedup until someone adds them to the list.**
   Deliberate — it is the price of jsdom-by-default — but it will drift. If it
   drifts far enough to matter, the regeneration rule is in the file header.

5. **The 15s per-test / 10s findBy budget on the scenario-preservation test
   makes a genuine hang slower to report** (15s instead of 1s, on one test).
   Accepted: it is one test, and the alternative is the coin-flip it replaced.
