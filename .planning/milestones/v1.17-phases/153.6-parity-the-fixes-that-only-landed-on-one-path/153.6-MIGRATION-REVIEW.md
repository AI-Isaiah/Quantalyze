## Findings

### MIG-01 (HIGH, confidence 8) — census pin uses strict equality on a live, user-mutable total

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:456`

The pin compares the **total** `api_keys` count with strict equality. That total is a
live, user-mutable number: any single key added or deleted between the 2026-08-11
measurement and the merge aborts the PROD auto-apply. The total carries no security
value.

**Recommended fix:** pin only the probe-exempt population, which is the pin's actual
security premise — abort when `v_mt5 <> c_pin_mt5 OR v_sig <> c_pin_mt5`, and demote
`v_total` to a NOTICE reporting the observed delta.

Verified in `src/lib/closed-sets.ts` `VENUE_CAPABILITIES` that `mt5` is the ONLY venue
with `scopeProbeSupported: false` — a backfilled deribit/okx/bybit/binance/sfox row gets
`attested_venue` = its own non-exempt venue and is PROBED regardless, so a change in
`v_total` cannot weaken the argument.

Alternative: re-measure and re-cut immediately before merge, and gate the merge on the
fresh count.

### MIG-02 (HIGH, confidence 7) — `$verify$` never asserts the RPC owner is inside the trigger's allowlist

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:368`

The `$verify$` block aborts on five things but not on the one behaviour the whole
migration rests on: that a privileged writer's `attested_venue` survives the scrub
trigger, i.e. that the two SECURITY DEFINER RPCs' OWNER is inside the trigger's
`current_user` allowlist.

Verify (b) only greps `pg_get_functiondef` for the literal `attested_venue`; verify (c)
only checks the trigger is attached. Neither can detect an owner outside the allowlist.

**Silent failure mode is total:** if the owner is outside the allowlist, every
wizard-minted key silently lands `attested_venue = NULL`, `venueSupportsScopeProbe(null)`
returns true, and every MT5 wizard submit gets a permanent `KEY_SCOPE_CHECK_UNAVAILABLE`
— precisely the regression the header's backfill section exists to prevent — while the
migration reports success.

Probability is low (`supabase db push` creates functions as `postgres`, and the RPCs
already need a privileged owner to bypass `api_keys` RLS), but the failure is silent, the
local PG16 fixture is structurally incapable of catching it (everything is `postgres`
there), and the SQL test's 5b anti-vacuity control also runs as `postgres` and never runs
against PROD.

**Recommended fix:**
```sql
IF pg_get_userbyid((SELECT proowner FROM pg_proc
   WHERE oid = 'public.create_wizard_strategy(uuid,text,text,text,text,text,text,text,integer,text,uuid)'::regprocedure))
   NOT IN ('postgres','service_role','supabase_admin') THEN
  RAISE EXCEPTION ...;
END IF;
```
…and the same for `add_wizard_composite_key`.

### MIG-03 (MEDIUM, confidence 8) — deploy-order race between Supabase auto-apply and Vercel

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:139`

The TS half already selects `attested_venue`, and `supabase-migrate.yml` and the Vercel
deploy both fire on the same push to main with no ordering between them.

During the window — or permanently if MIG-01's abort fires — PostgREST answers
PGRST204/42703 for `route.ts:1219` `.select("exchange, attested_venue")` and
`route.ts:1423` `api_keys ( exchange, attested_venue )`. The single-key arm degrades
safely (non-blocking warn, `attestedVenue` null, PROBE) but that makes every MT5 wizard
submit return `KEY_SCOPE_CHECK_UNAVAILABLE` for the duration, and the composite arm takes
the unreadable-shape refusal (`route.ts` ~1610) — a hard failure on composite submits.

**Recommended fix:** land the migration and confirm the Supabase Migrate run is green
BEFORE promoting the Vercel deployment (or add the ordering to the land checklist).

## Verified clean (the audit's numbered priorities)

**Priority 2 — the RPC re-bases (highest-risk item): CLEAN, independently confirmed.**
A repo-wide grep for `CREATE (OR REPLACE) FUNCTION ... create_wizard_strategy` returns
exactly four defining migrations (`20260411103316`, `20260513084844`, `20260515114310`,
`20260602190000`) with `20260602190000` latest, and `add_wizard_composite_key` exactly one
(`20260710180000`); the other mentions (`20260712120000`, `20260716130500`,
`20260728120000`) are prose/cross-references only, and there is no `ALTER FUNCTION` on
either. `diff -u` of the claimed source line ranges against the new bodies shows ONLY the
two documented additions in each — no intervening fix reverted, the `wizdraft:` /
`wizcomposite:` advisory-lock fences intact. The `supabase/schema/functions/` snapshots
match and will pass `dump-sql-functions.ts --check`.

**Priority 3 — SECDEF hardening: CLEAN.** All three functions pin
`SET search_path = public, pg_catalog` (project convention, not bare `public`).
`CREATE OR REPLACE FUNCTION` preserves owner, ACL and COMMENT; the last grants are
`20260602190000:161` and `20260710180000:149`, and verify (e) asserts both. The `anon`
negative also catches an accidental PUBLIC grant, since `anon` inherits PUBLIC.

**Priority 4 — the scrub trigger: CLEAN.** `SECURITY INVOKER` is correct (a DEFINER form
would make `current_user` the owner and the check a silent no-op). It cannot break the
wizard RPCs' inserts because it contains no `RAISE` at all — a wrong allowlist would
silently NULL, not fail (which is MIG-02). No allowlist bypass: PostgREST sets the role
from a signed JWT claim, and the only three `.insert()` sites into `api_keys` —
`ApiKeyManager.tsx:254`, `StrategyForm.tsx:140`, `AllocatorExchangeManager.tsx:591` — are
all anon-key/user-JWT clients running as `authenticated`. No service_role INSERT path
exists.

**Priority 5 — census discriminator: sound.** PROD carries `v_sig = 2`, so any realistic
drift lands on the ABORT branch, never the lenient one. `api_keys.created_at` is
`TIMESTAMPTZ` (`20260405061911:31`), so `(created_at AT TIME ZONE 'UTC')::date` is
session-timezone independent — no silent date shift. The only lenient-branch path is the
header's own documented "both censused mt5 rows deleted" state.

**Priority 6 — GDPR/sanitize: CLEAN, no exemption needed.** The trigger is
`BEFORE INSERT` only and has no `RAISE`; `sanitize_user` only DELETEs from `api_keys`
(`20260417110538:316`, `20260513073518:281`).

**Priority 7 and mechanical scans: CLEAN.** Filename is 14-digit conformant;
`20260811210000` > remote tip `20260810120000`, so not backdated and no allowlist entry
needed. Template-artifact grep returns 0 on all three files. The `RAISE`-format-string
scan (invariant 21) finds no `||` concatenation. Zero GRANT/REVOKE means no ACL-drift leak
window and no invariant-17 hazard — and the new trigger function correctly keeps default
PUBLIC EXECUTE, since revoking it would risk the 42501 class and a `RETURNS TRIGGER`
function cannot be invoked as an RPC anyway. No CONCURRENTLY, no NOT NULL, no
NUMERIC/INTEGER columns, no new policies, views or JSONB.

**Two other things checked because they would have been production breakage:** no
`select("*")` on `api_keys` from an authenticated client (`API_KEY_USER_COLUMNS` in
`src/lib/constants.ts:170` is an explicit list), so the ungranted new column breaks no
client read; and `analytics-service` reads `api_keys` with `select("*")` as service_role
(`routers/internal.py:276`, `routers/exchange.py:1255`) with no strict/forbid-extra model,
so the additive column is safe there.

**Locking.** `ADD COLUMN` on a nullable no-default column is metadata-only. ACCESS
EXCLUSIVE is held for the whole transaction, but the work is sub-second on 29 rows, and
`SET lock_timeout = '3s'` (line 135) makes a blocked ALTER abort cleanly rather than
queueing. That same lock also closes what would otherwise be a race between the backfill
and post-verify (a): a concurrent client INSERT cannot commit mid-migration and make
`v_unattested` nonzero.

**Two generic invariants deliberately overridden by project convention** (surfaced rather
than averaged): `BEGIN;`/`COMMIT;` appears in 155 of 240 migrations, and session-level
`SET lock_timeout = '3s'` is used throughout. Both are established house style here, so
neither is a finding.
