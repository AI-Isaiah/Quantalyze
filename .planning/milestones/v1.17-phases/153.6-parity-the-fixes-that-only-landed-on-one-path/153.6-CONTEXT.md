# Phase 153.6: PARITY — the fixes that only landed on one path - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Every fix the 153 span made on one path exists on its twin, no broad `except` re-absorbs a refusal
the fence was built to surface, and the venue label stops being a client-writable authority for
skipping a security probe.

⛔ **THE SHAPE OF THIS PHASE IS "the fix landed once, not twice."** Three of the four root causes are
the same failure: a correct fix applied to one path while its duplicate went untouched, with no
guard asserting the two agree. That is the instance-not-class mistake — found *inside the span whose
own charter said "fix it at the SINK, not three times."* No cluster closes as N point patches. Each
must answer: **what makes the two paths unable to diverge again?**

Source: `/code-review xhigh` over the whole 153→153.5 span (2026-08-11, 40 agents, 29 verified
findings → 13 distinct defects). Nine come here; two were fixed unplanned in the 153.5 PR (#673);
two are deliberately out.

</domain>

<decisions>
## Implementation Decisions

### D — the venue lock is bypassable (SECURITY, live on PROD)

- **D-01: The server-held venue becomes the probe gate's authority. The client-writable `exchange`
  column stops being load-bearing for the probe decision.** `/api/keys/validate-and-encrypt` already
  knows the venue at mint time — it just validated against it. Bind the venue to the minted
  ciphertext server-side and have `finalize-wizard`'s scope-broadening probe gate read *that*.
  DELETE-then-re-INSERT with a forged `exchange` then becomes irrelevant rather than merely harder.
- **D-02: Do NOT add a new REVOKE on `api_keys`.** Migration `20260810120000` line 181 warns in its
  own text that an over-broad REVOKE "would silently break the connect-a-key" flow. Revoking DELETE
  or INSERT is explicitly rejected for this phase. No new grant/revoke on `api_keys`.
- **D-03: The column may remain user-writable.** Once the probe no longer trusts it, a mislabelled
  row is a cosmetic lie, not a control bypass. Do not spend this phase making the column immutable.
- **D-04: The migration header of `20260810120000` currently asserts the opposite of the truth**
  ("the mislabelled row can never be corrected back"), and that false premise is what its
  "self-defeating forgery" residual argument rests on. The header must be corrected as part of this
  work — a security migration whose stated threat model is wrong is worse than one that says nothing.
- **D-05: `supabase/tests/test_api_keys_exchange_not_user_writable.sql` proves DELETE survives but
  never tests the round trip.** It must gain the DELETE + re-INSERT-under-a-different-exchange case,
  and that case must assert the *probe* outcome, not merely the row state.
- **D-01a (AMENDED 2026-08-11 by RESEARCH §1 — my premise was incomplete, and the correction makes
  this CHEAPER):** `/api/keys/validate-and-encrypt` persists nothing (`route.ts:326` returns the
  ciphertext and stores no row). But the **wizard — the only surface that can mint an MT5 key —
  never performs a client INSERT.** It POSTs `/api/strategies/create-with-key`, which calls the
  SECURITY DEFINER RPC `create_wizard_strategy(p_exchange, …)`, and that RPC does the `api_keys`
  INSERT itself (`20260602190000:130-138`; composite twin `20260710180000:125-137`). **A
  server-attested venue therefore already exists inside a privileged writer — it is simply not
  stored where the probe reads.** `ApiKeyManager.tsx:254` / `StrategyForm.tsx:140` remain genuine
  client INSERT paths, which is why the column stays client-writable (D-03) and why the probe must
  stop trusting it rather than the write being locked down.
- **D-01b: recommended shape — one nullable `api_keys.attested_venue`, written ONLY by those two
  SECURITY DEFINER RPCs, plus a `BEFORE INSERT` trigger that NULLs any client-supplied value.**
  Satisfies D-02 structurally (migration 027 already column-allowlists SELECT, so no new
  grant/revoke), needs no extra round trip, and adds no seam call.
- **D-01c: binding the venue INTO the ciphertext is arithmetically excluded, not merely awkward**
  (RESEARCH §2). The Next layer holds no KEK, so it would need a new seam leg, and
  `finalize-wizard`'s composite branch has only 22 500 ms of headroom against its 300 000 ceiling —
  ten per-member decrypt legs breach SC-4b outright. Do not re-propose it.
- **D-01d: OQ-1 RESOLVED 2026-08-11 — PROD census taken (read-only, counts only, no key material).**
  `api_keys` on `khslejtfbuezsmvmtsdn`: **deribit 13, okx 9, bybit 5, mt5 2 — 29 rows total.**
  The MT5 keys are **2** (one owner, both created 2026-08-04), ⚠️ **not the 3 RESEARCH assumed** —
  a count-pinned backfill must pin **29 total / 2 mt5**, and its self-verify block must abort on a
  mismatch. The population is small enough that backfill cost is a non-issue; what matters is that
  pure fail-toward-probing with NO backfill would hand every MT5 finalize a permanent
  `KEY_SCOPE_CHECK_UNAVAILABLE` — a self-inflicted regression on this milestone's headline venue.
- ⚠️ **Calibrate honestly in all prose:** this is a SELF-targeted control bypass, not a tenant leak.
  An owner mislabels their own key to dodge a probe on their own key. What is lost is the assurance
  that a key read-only at Connect was not broadened to trade. Serious for a product selling verified
  performance; not a 3am page. Do not write it up as a data breach.

### A — adapter parity (3 findings, ONE cause)

- **D-06: Extract the shared logic into one module both paths call, THEN add a parity guard over
  whatever genuinely resists extraction.** Not one or the other. Extraction removes today's
  duplicate; the guard catches the next duplicate someone adds. This span already shipped a fix "at
  the SINK" and still produced three one-path-only findings, so the structural fix alone has a
  demonstrated failure mode here.
- **D-07: Do NOT make `services/ingestion/mt5.py` import from `routers/exchange.py`.** That inverts
  the dependency direction (worker → HTTP layer) and is a circular-import hazard of exactly the kind
  that forced 153.5 to put the epoch registry in `mt5_client.py` rather than `mt5_concurrency.py`.
  The shared module is a third module both depend on.
- **D-08: The three missing twins are named and each must land:**
  - **A1** `_probe` — the terminal short-circuit that stops `order_check` running once the verdict is
    already `undetermined`. Without it, `_WRONG_SERVER_TOKENS` (which carry "terminal") turn an
    operator-side refusal into a 400 accusing the user their broker server is wrong. **This is the
    exact documented incident the router-side fix was written to prevent.**
  - **A2** `_read_terminal` — the broad `except Exception` around netref materialization. ⚠️
    `mt5linux` f-string-interpolates the password into remotely-eval'd source, so exception TEXT is a
    credential-disclosure surface (T-134-01 / T-153.3-23). **Only the exception CLASS is safe to
    surface.**
  - **A3** the D-31 arm — raises a bare `RuntimeError` documented PERMANENT, which escapes
    `Mt5Adapter.validate` into `job_worker.classify_exception`'s `("unknown", str(exc))`
    fall-through, so **the worker RETRIES a fault that can never clear**, re-running the whole
    serialized probe against the ONE shared terminal each time, queueing ahead of every other user's
    validate, and finally showing the user raw internal copy naming investor/master passwords.

### B — absorption: broad `except` re-swallowing the fence

- **D-09: D-42 made absorption structurally impossible for the classify arms; pre-existing catch-alls
  upstream reintroduced it. Close them at the same standard.** The fence type must reach its
  dedicated arm before any broad handler sees it.
  - **B1** `routers/exchange.py` › `_read_terminal`'s `except Exception` swallows
    `Mt5SessionAbandoned` → an operator triaging in Railway reads a gateway materialization fault
    **that never happened**, and the probe continues on a "terminal unreadable" premise that is false.
  - **B2** connect stage: the construction fence's `Mt5SessionAbandoned("connect")` is caught by the
    broad `except Exception as connect_err` **before** the dedicated D-40 arm, returning a 503 that
    **counts toward the mt5-gateway breaker** — our own abandoned thread driving the breaker toward
    opening against a healthy gateway.
  - **B3** `mt5_client.py` › `restart()` check 2 raises from INSIDE `_timed`, emitting an `mt5.stage`
    event whose `duration_ms` measures a round-trip never made — the exact event check 1 was
    deliberately placed outside `_timed` to avoid (RESEARCH §Q-4). The two checks must agree on the
    telemetry contract.

### C — the budget correction, and the oracle that cannot see it

- **D-10: Fix BOTH halves. The number alone is half the job.** `connectAbortDeadlineMsFor` was sized
  against the branch table's **closed**-breaker column (~158 500 ms) when the governing figure is the
  **failing** column (175 500 ms serialized / 85 500 ms default) — the failing state being exactly
  what a stalling seam is in when a client deadline fires. CR-01's "nothing was saved" lie is
  reachable again ~10.5 s before the route finishes writing the key.
- **D-10a (AMENDED 2026-08-11 by RESEARCH §4, arithmetic re-verified against the branch table):
  the defect is TWICE as wide as the finding says — BOTH arms are short, by the identical amount.**
  The shortfall is a per-route quantity, `failing_store − grace = 25 500 − 15 000 = 10 500 ms`, and
  it is independent of the validate budget. So the **default (ccxt) arm is short by the same
  10 500 ms** (75 000 against a governing 85 500), not just the serialized arm. Corrected targets:
  **190 500 serialized / 100 500 default**. A fix that corrects only the MT5 arm leaves the identical
  lie reachable on every ccxt venue — which would be this phase committing its own headline mistake,
  "the fix landed once, not twice."
- **D-11 (CORRECTED 2026-08-11 — my original named the WRONG FILE): the blind oracle is
  `src/lib/wizard/validate-budget.test.ts:226`**, which asserts
  `expect(connectAbortDeadlineMsFor("mt5")).toBeGreaterThan(158_500)` — the executable pin on the
  closed-breaker column. ⛔ **`src/lib/seam-budgets.invariant.test.ts` contains no `158_500` in code
  at all**; it carries `158 500` only inside a prose comment table (~`:118`). Verified by grep
  2026-08-11. Editing the file my first draft named would have left the real guard green — this
  phase's own defect class, committed inside the CONTEXT written to close it. Keep the branch table
  in `seam-budgets.invariant.test.ts` as a canonical reference to read, not as the thing to edit.
- **D-11a: the corrected oracle must be falsified by mutation** — restore the wrong column, observe
  the red, restore — not merely asserted. And it must pin the ECONOMICS (the governing failing-column
  figure and why the failing state is the one that matters), never `connectAbortDeadlineMsFor`'s own
  arithmetic, or it becomes self-referential and blind again.

### E — retry affordance

- **D-12: A probe parse miss must not be permanently classified.** It was moved off
  `KEY_NETWORK_TIMEOUT` onto `KEY_SCOPE_CHECK_UNAVAILABLE`, removing the Retry control for a
  condition that is **not** always permanent — a 2xx body the schema cannot read is also what a
  rolling analytics deploy produces.
- **D-13: Touching a wizard error code ripples into 153.1's pinned code tables.**
  `EXPECTED_TABLE_SIZE` and friends must be **re-cut, never deleted** — deleting a pin to make a
  change pass is the failure this milestone has guarded against throughout.

### Amendments from RESEARCH (2026-08-11) — read these before planning

- **D-14: A2 and B1 are the SAME EDIT, and doing them separately imports the bug.** Adding the
  router's broad `except Exception` to the worker's `_read_terminal` would carry B1 *onto* the
  worker path. The extracted `services/mt5_probe.py` must catch `Mt5SessionAbandoned` and re-raise
  **before** the broad arm — one implementation closes both findings. Plan them as one task, never
  two.
- **D-15: B2's bypass is NOT arm ordering.** `resilient-fetch.ts:519-525` confirms
  `MT5_GATEWAY_UNREACHABLE` "(×2: connect timeout, connect failure)" is one of exactly three
  breaker-counting sites, so the breaker claim holds. But the dedicated D-40 arm sits on a
  **different `try` block (stage 2)**, so reordering handlers inside one block will not fix it.
- **D-16: B3's remedy belongs in `_timed`, not `restart()`.** Restructuring `restart()` risks the
  three interacting cleanup invariants 153.5 warns about. One `except Mt5SessionAbandoned: raise`
  ahead of the emit makes 153.5 RESEARCH §Q-4's telemetry contract structural for *every* stage.
  ⚠️ The ROADMAP's phrasing "measures a round-trip never made" is imprecise — the reconnect *did*
  happen; the real defect is contaminating the **D-32 recovery-latency population**. Fix the
  ROADMAP wording as part of this phase.
- **D-17: A3's permanent-error convention already exists** — a `classify_exception` arm returning a
  **curated** message rather than `str(exc)`, which also closes the credential-vocabulary leak.
  Reuse it; do not invent a new marker.
- **D-18: E-cluster pin inventory (exact).** `EXPECTED_TABLE_SIZE` goes **74 → 75 at TWO sites**,
  and a meta-test counts its own declarations. `EXPECTED_FINALIZE_REJECTION_SITES` **stays 32** —
  and the fact that it does not move is the proof this is a fix rather than an addition. If a plan
  finds itself changing 32, it has mis-scoped E.
- **D-19: cluster-D migration hazards (the migration AUTO-APPLIES to PROD on merge).**
  (a) It must re-base **both** SECURITY DEFINER RPCs on their *latest* bodies
  (`20260602190000` / `20260710180000`) — re-basing an older body silently reverts the F6
  advisory-lock idempotency fence. (b) Any re-stamp of the `exchange` column comment **must preserve
  the `20260810120000` substring**, or `supabase/tests/test_api_keys_exchange_not_user_writable.sql`
  starts SKIPPING instead of failing — a guard that silently stops guarding, which is this phase's
  own defect class.
