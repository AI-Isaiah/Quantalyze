# Phase 153.6 Plan 04: the probe gate stops believing the client — Summary

**The finalize-wizard scope-broadening probe gate now reads the server-attested venue on both the single-key and composite arms, so a row that claims the MT5 exemption in the client-writable `exchange` column is probed anyway, and a row with no attestation at all is probed too — with no fallback between the two columns anywhere on the gate path.**

## Accomplishments

### Task 1 — the oracle, observed RED (`3e3597e4`)

`STATE` gained `adminApiKeysAttestedVenue` and the composite embed gained an
`attested_venue` field. Both are **separate from `exchange` on purpose**: a fixture where
the two agree cannot tell the two gates apart, and every pre-existing fixture in the file
is of that kind by construction.

Both CLASS SWEEPS were re-pointed at the attestation. The important half is how the
client-writable column is driven: it is pinned, for every iteration, to a non-probing code
**taken from the capability registry** (`nonProbing[0]`, never hand-named — naming a venue
is the instance-fix habit the sweep exists to catch). A gate that reads the wrong column
therefore skips the *entire* sweep, and every probing venue reds. The composite sweep
gained its own anti-vacuity floor, because it now performs a derivation of its own and a
floor living in the sibling `it` cannot fence it.

Seven new rows landed in a `[153.6-04 / PARITY-04]` block — forged label, NULL attestation,
and the **counterweight** (an attested non-probing venue still skips), each on both arms,
plus the "no attestation field at all" parse case.

### Task 2 — the gate, the flag, the guard, the falsification (`8eb4093e`)

- **Single-key:** `select("exchange")` → `select("exchange, attested_venue")`. One column,
  zero extra round trips. `attestedVenue` is its own binding and is the only thing passed
  to `runScopeBroadeningProbe`.
- **Composite:** embed → `api_keys ( exchange, attested_venue )`; the field joins
  `compositeMemberRowsSchema` (safeParse'd, never cast); the per-member gate reads it.
- **The leniency is not inherited.** The read's error arm is non-blocking *by design* for
  the asset_class stamp. The gate does not get that: a read that faulted attests nothing,
  so `attestedVenue` is null and the key is probed. Stated in-code.
- **OQ-2 flagged, not implemented** at the asset_class stamp, with why it is scoped out
  (self-targeted money-math residual) and why the follow-on is one identifier.
- **OQ-3 class guard** in `closed-sets.sfox-flag.test.ts`: `UI_EXCHANGE_CODES ∩
  {scopeProbeSupported:false} = ∅`, swept over both sFOX flag states, with **both**
  anti-vacuity halves — the offered set is non-empty, *and* an opt-out exists somewhere in
  the supported set (without the second, removing the capability entirely would leave the
  intersection empty forever and the guard asserting nothing).

## Cross-plan dependency — READ BEFORE MERGING

⚠️ **This plan reads a column that plan 153.6-03 creates.** The migration
(`api_keys.attested_venue` + the `BEFORE INSERT` scrub trigger + the two RPC re-bases +
the backfill) is **not in this worktree** and nothing under `supabase/` was touched here,
per the plan's instruction.

Consequences if the two are ever separated:

- **Single-key arm:** PostgREST answers `42703 undefined_column`, the read's error arm
  fires (non-blocking, already instrumented), `attestedVenue` stays null ⇒ **every key is
  probed**. Degraded but SAFE, and loud in Sentry.
- **Composite arm:** the member read errors ⇒ the existing fail-CLOSED arm returns
  `COMPOSITE_MEMBERSHIP_UNKNOWN`. Safe, but composites would not finalize.

So the two plans must land together. The `.optional()` on the schema field is the other
half of this: it means a member row that arrives *without* the attestation key (a schema
cache that has not caught up) still parses and is probed, rather than being refused as
shape drift.

**D-05 is half-discharged here.** This is the TS half — the probe OUTCOME. The SQL half —
the input's unforgeability — is plan 153.6-03. Neither alone discharges it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] The OQ-2 note un-instrumented an audited mutation**

- **Found during:** Task 2, full-suite run
- **Issue:** `src/__tests__/audit-coverage.test.ts` requires an `@audit-skip:` pragma
  within **8 lines above** a mutation chain. Inserting the 11-line OQ-2 note *between* the
  existing pragma and the `.update({}` pushed the pragma out of the scan window, and the
  asset_class stamp was reported as an uninstrumented mutation. Failure:
  `Found 1 uninstrumented mutation(s): route.ts:1267 > .update({`.
- **Fix:** the OQ-2 note moved **above** the pragma, and a `⛔` note now records the
  positional constraint at the site so the next person adding prose there does not repeat
  it. This is exactly the class of latent trap this phase is about, so it is written down
  rather than silently reordered.
- **Files modified:** `src/app/api/strategies/finalize-wizard/route.ts`
- **Commit:** `8eb4093e`

**2. [Rule 2 — Missing critical] The OQ-3 guard's second anti-vacuity half**

- **Found during:** Task 2
- **Issue:** The plan specified one anti-vacuity assertion (`UI_EXCHANGE_CODES` non-empty).
  That is insufficient on its own: if `scopeProbeSupported` were removed from every
  capability row — i.e. WIZFORM-04 reverted — `venueSupportsScopeProbe` answers `true` for
  everything, the intersection is empty forever, and the guard passes while asserting
  nothing.
- **Fix:** a second `it` asserts an opt-out **exists** somewhere in `SUPPORTED_EXCHANGES`,
  and that the offered set is a strict subset of the supported one.
- **Commit:** `8eb4093e`
