## Critical Issues

### CR-01: `attested_venue` is not server-attested — it is a client-supplied RPC parameter

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:219-231`, `:330-342`, `:577-589`
**Also asserts the false guarantee:** `src/app/api/strategies/finalize-wizard/route.ts:1203-1211`, `src/app/api/strategies/finalize-wizard/route.test.ts` (`[153.6-04 / PARITY-04]` docblock)

**Issue:**

The migration's own `COMMENT ON COLUMN` states the invariant the whole cluster
rests on:

> 'SERVER-ATTESTED venue … Written ONLY by the two SECURITY DEFINER wizard RPCs
> … **from the venue the server itself validated at mint time**.'

The first clause is true. The second is false, and it is the load-bearing one.
`create_wizard_strategy` and `add_wizard_composite_key` do not validate anything;
they write `p_exchange` — a caller-supplied parameter — verbatim into
`attested_venue`:

```sql
INSERT INTO api_keys (..., attested_venue)
VALUES (..., p_exchange)          -- p_exchange is whatever the caller passed
```

Both functions carry `GRANT EXECUTE … TO authenticated` (issued by
20260411103316 / 20260602190000 / 20260710180000, and **re-asserted as a required
post-condition by this very migration**, lines 557-563). Supabase exposes
`public`-schema functions over PostgREST, and the calling routes
(`create-with-key/route.ts:409`, `composite/add-key/route.ts:384`) use the
**user-scoped** client (`createClient()` from `@/lib/supabase/server`) precisely
because the RPC's `auth.uid()` guard requires it. So the browser can issue the
identical call itself:

```
POST /rest/v1/rpc/create_wizard_strategy
{ "p_user_id": "<own uid>", "p_exchange": "mt5", "p_api_key_encrypted": "<ciphertext>", ... }
```

and the ciphertext is available to the browser: `/api/keys/validate-and-encrypt`
returns the server-minted blobs to the client (`route.ts:326`) — that is exactly
what `ApiKeyManager.tsx:254` and `StrategyForm.tsx:140` consume.

The trigger + column-privilege story that the migration, the route comments, the
SQL test and `route.test.ts` all narrate ("only a privileged writer can attest")
therefore protects the *client INSERT* door while leaving the *RPC* door open.
The SQL test's assertion 5 exercises only the first door; nothing in this phase
exercises the second.

**Exploitability today — stated honestly.** I could not construct a live exploit,
and the reason is an accident rather than a control: the RPC derives **both**
`exchange` and `attested_venue` from the *same* parameter, so a forged
attestation also forges the label that drives ingestion. Since the only
probe-exempt venue today is `mt5`, a forged row is routed to the MT5 adapter and
never syncs. That coupling is:

1. nowhere stated as a security property,
2. nowhere tested,
3. broken by any of: adding a distinct `p_attested_venue` parameter, a
   service_role route that writes `attested_venue` independently (the trigger
   allows `service_role` — see IN-04), or a future writer that normalises
   `exchange` differently from `attested_venue`.

The phase's own RESEARCH names sFOX as the plausible next member of the opt-out
set, and the residual section of this migration enumerates three residuals —
none of them this one. A control whose actual guarantee is an undocumented
coincidence, shipped under a written claim of privilege, is the same defect class
this phase exists to close, one door over.

**Fix:** the guarantee must be made true or the claim must be corrected. Cheapest
correct option — bind the attestation to something the client cannot choose,
inside the DEFINER body, and pin the coupling:

```sql
-- inside create_wizard_strategy / add_wizard_composite_key, before the INSERT
IF p_exchange IS NULL OR p_exchange <> lower(p_exchange) THEN
  RAISE EXCEPTION 'attested venue must be a normalised venue code'
    USING ERRCODE = 'invalid_parameter_value';
END IF;
```

…which is not sufficient on its own. The real remedies, in order of strength:

- **(a)** Move the api_keys INSERT server-side behind a service-role writer that
  passes the venue *it* validated, and revoke `authenticated` EXECUTE on both
  RPCs. This is the "connect-flow refactor" both migrations defer; it is the only
  option that makes the shipped comment true.
- **(b)** If (a) stays deferred: **correct the comment and the route/test prose**
  to say what is actually guaranteed — "written only by the wizard RPCs, from the
  venue those RPCs were called with; `exchange` and `attested_venue` are written
  from ONE parameter and must never diverge" — and add a guard that keeps the
  coupling from drifting, e.g. a `CHECK (attested_venue IS NULL OR attested_venue
  = exchange)` table constraint plus a SQL-test assertion that the RPC path
  cannot produce a row where they differ. The CHECK is a one-line, zero-blast-
  radius way to convert the accident into an enforced invariant.

Either way, add the missing case to
`supabase/tests/test_api_keys_exchange_not_user_writable.sql`: call the RPC as
`authenticated` with a forged `p_exchange` and assert the outcome you intend.

## Warnings

### WR-01: the migration's "Safe to re-run" claim is false, and a re-run retro-attests scrubbed rows

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:124-130`, `:475-477`, `:492-499`

**Issue:** The header states *"the backfill is `WHERE attested_venue IS NULL`, so
a re-run writes nothing. Safe to re-run."* That is only true at the instant of
first apply. From that moment on, **every** non-privileged client INSERT
(ApiKeyManager, StrategyForm) deliberately lands `attested_venue = NULL` — that
is the fix working. A re-application of this file would sweep exactly those rows
and set `attested_venue = exchange`, i.e. bless the forgeable label on precisely
the population the trigger exists to keep unattested. The post-verify's assertion
(a) — `count(*) WHERE attested_venue IS NULL <> 0 → RAISE EXCEPTION` — makes this
worse rather than better: it encodes "no unattested rows may exist" as an
invariant, which directly contradicts the steady state the design intends, and it
would *force* the retro-attestation on any re-run rather than surface it.

**Fix:** scope the backfill and the post-verify to the migration's own snapshot,
and correct the header:

```sql
-- 6. the one-time backfill — BOUNDED to rows that predate this migration
UPDATE public.api_keys
   SET attested_venue = exchange
 WHERE attested_venue IS NULL
   AND created_at < timestamptz '2026-08-11 00:00:00+00';   -- the dated snapshot

-- 7(a) post-verify, scoped to the same population
SELECT count(*) INTO v_unattested
  FROM public.api_keys
 WHERE attested_venue IS NULL
   AND created_at < timestamptz '2026-08-11 00:00:00+00';
```

and replace "Safe to re-run" with "**Not** idempotent after the first apply — the
backfill is bounded by a dated cutoff so a re-run cannot attest rows the trigger
scrubbed."

### WR-02: nothing verifies that a SECURITY DEFINER RPC INSERT actually survives the scrub trigger

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:362-380` (allowlist), `:483-574` (post-verify)

**Issue:** The entire design depends on one unverified composition: that inside
`create_wizard_strategy` / `add_wizard_composite_key`, `current_user` resolves to
a member of `('postgres', 'service_role', 'supabase_admin')` — i.e. that the
function owner is in that allowlist. The post-verify block asserts five things
(zero unattested rows, both advisory-lock fences, the `attested_venue` substring
in both bodies, the trigger attachment, the EXECUTE grants) and **not** that one.
`supabase/tests/…:257-266` (assertion 5b) proves a privileged INSERT persists the
value, but as the *test session's* role, which is not the same fact.

If the assumption ever fails (a function re-created under a different owner, a
project where migrations apply as an unexpected role), the failure is silent and
total: every wizard-minted key is unattested → every key is probed → **every MT5
finalize returns a permanent `KEY_SCOPE_CHECK_UNAVAILABLE` with no remedy**,
which is exactly the self-inflicted regression the backfill section says it exists
to prevent.

**Fix:** add one assertion to the post-verify block — it is the cheapest possible
proof of the composition:

```sql
  -- (f) the DEFINER bodies run as a role the scrub trigger admits, or every
  --     wizard-minted key would be scrubbed to NULL and every MT5 finalize
  --     would answer a permanent KEY_SCOPE_CHECK_UNAVAILABLE.
  IF pg_get_userbyid(
       (SELECT proowner FROM pg_proc
         WHERE oid = 'public.create_wizard_strategy(uuid,text,text,text,text,text,text,text,integer,text,uuid)'::regprocedure)
     ) NOT IN ('postgres', 'service_role', 'supabase_admin')
     OR pg_get_userbyid(
       (SELECT proowner FROM pg_proc
         WHERE oid = 'public.add_wizard_composite_key(uuid,text,text,text,text,text,text,text,integer,text,uuid)'::regprocedure)
     ) NOT IN ('postgres', 'service_role', 'supabase_admin') THEN
    RAISE EXCEPTION
      'Migration 20260811210000 failed: a wizard RPC is owned by a role the api_keys_scrub_attested_venue trigger does not admit, so its attestation would be NULLed. Rolling back.';
  END IF;
```

(A stronger variant — INSERT via the RPC inside a `SAVEPOINT` and roll it back —
also works, but needs an `auth.uid()` stub.)

### WR-03: the migration and the code that depends on it land in one merge but apply concurrently — the composite path fails CLOSED in the window

**File:** `src/app/api/strategies/finalize-wizard/route.ts:1219`, `:1423`, `:1444-1447`

**Issue:** Merging to `main` triggers *both* the Supabase auto-apply and the
Vercel build; the ordering is not guaranteed. If the Vercel deployment goes live
first:

- Single-key arm: PostgREST answers `42703 undefined_column` → the non-blocking
  error arm fires → `attestedVenue` stays null → **every** key is probed. For an
  MT5 key that is a permanent `KEY_SCOPE_CHECK_UNAVAILABLE` — the wizard's last
  step, with no remedy, for this milestone's headline venue.
- Composite arm: the whole `select("api_key_id, api_keys ( exchange, attested_venue )")`
  errors → `membersErr` → the fail-CLOSED arm returns
  `COMPOSITE_MEMBERSHIP_UNKNOWN` (503). **No composite finalizes at all** during
  the window.

`153.6-04-SUMMARY.md` identifies this exactly and concludes "the two plans must
land together" — they do, in one branch, but "together" is not "ordered". No
mitigation shipped.

**Fix:** apply `20260811210000` to PROD (MCP `apply_migration`, or a manual apply)
**before** merging the branch, and record that in the land checklist — the
migration is idempotent on a fresh apply and its pre-flight census is already
written for exactly that run. Alternatively, make the composite read tolerant for
one release (`select("api_key_id, api_keys ( exchange )")` plus a second
tolerant read, or a `try/catch` narrowing to `42703`), then narrow it in a
follow-up once the column is live everywhere. The first option is far cheaper and
matches the `Manual-Only Verifications` row the VALIDATION file already carries.

### IN-02: a tautological parity assertion in the A1 test

**File:** `analytics-service/tests/test_mt5_validate_parity.py:441-444`
**Issue:**
```python
assert "order_check" not in router_client.calls
assert "order_check" not in adapter_client.calls
assert ("order_check" in router_client.calls) == ("order_check" in adapter_client.calls)
```
The third line cannot fail while the two above it pass — it is `False == False` by
construction. It reads as an independent parity claim and is not one. Harmless
(the two lines above carry the teeth) but it is the shape this phase is auditing
for.
**Fix:** delete it, or replace it with a claim the first two do not already make
(e.g. that both paths produced the *same* call sequence:
`assert router_client.calls == adapter_client.calls`).

### IN-03: the OQ-2 residual's "self-targeted" framing understates its audience

**File:** `src/app/api/strategies/finalize-wizard/route.ts:1264-1273`, `supabase/migrations/20260811210000_api_keys_attested_venue.sql:113-117`
**Issue:** The deferral reasons that a forged `exchange` on the asset_class stamp
"distorts the annualization clock (√365 vs √252) of the forger's OWN strategy". The
annualized figures are rendered on a **public** factsheet, so the party misled is
a prospective investor, not the forger — that is the opposite of self-targeted,
and it is the calibration that will decide whether the follow-on ships.
(In practice the residual is currently closed by the same coupling described in
CR-01: `isCryptoExchange` is false only for `mt5`, and an `mt5`-labelled row never
syncs. That is worth writing down, because it is the actual reason the residual is
tolerable — not the "self-targeted" one.)
**Fix:** restate the residual in both places as "misleads the factsheet's readers,
not the forger; currently unreachable because the only non-crypto label is `mt5`,
which cannot ingest a ccxt key."

### IN-04: `service_role` in the scrub-trigger allowlist is a standing exemption with no current beneficiary

**File:** `supabase/migrations/20260811210000_api_keys_attested_venue.sql:368`
**Issue:** `current_user IN ('postgres', 'service_role', 'supabase_admin')` admits
`service_role`, but I found no service-role `api_keys` INSERT anywhere in `src/`
(the only inserts are the two browser-side ones and the two RPCs). The exemption
therefore protects nothing today and silently pre-authorises the next server route
that inserts an `api_keys` row from a request body — which would persist a
client-chosen attestation without any code review flagging it.
**Fix:** either drop `service_role` from the allowlist (the RPCs run as the table
owner, so nothing regresses), or add a comment naming the intended future writer
and the obligation it carries.
