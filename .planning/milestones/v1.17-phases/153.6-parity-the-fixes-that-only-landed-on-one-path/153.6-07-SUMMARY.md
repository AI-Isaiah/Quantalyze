## What changed, per finding

### CR-01 (BLOCKER) — remedy (b), all four parts

The migration claimed `attested_venue` held *"the venue the server itself validated at mint time"*. It does not. Both wizard RPCs write the caller-supplied `p_exchange` verbatim, both hold `EXECUTE` for `authenticated`, and Supabase exposes them over PostgREST — with ciphertext the browser already holds from `/api/keys/validate-and-encrypt`. The claim was false in exactly the load-bearing clause.

- **(i)** `CHECK (attested_venue IS NULL OR attested_venue = exchange)`, named `api_keys_attested_venue_matches_exchange`, added directly (column is new and all-NULL at that point). Post-verify **(g)** asserts it exists *and* is `convalidated` — `NOT VALID` would police new writes while leaving existing rows unchecked.
- **(ii)** The column comment now states the guarantee that holds — written only by the two RPCs, both columns from ONE parameter, coupling pinned by the CHECK, client INSERTs scrubbed to NULL — and names what it is **not**.
- **(iii)** Same correction at every other site asserting it: the migration header, both RPC in-body comments, both `supabase/schema/functions/` snapshots (regenerated, `schema:functions:check` current), `route.ts` (3 sites incl. the composite embed), and the `[153.6-04 / PARITY-04]` docblock + `describe` title in `route.test.ts`. A repo grep for the claim now returns only the negated usage.
- **(iv)** SQL test **5d** calls the RPC as `authenticated` with a forged `p_exchange` and pins the honest outcome: the call **succeeds** — it validates nothing — but both columns come back forged, so the forgery cannot be selective. **5e** pins that the coupling is a constraint rather than a property of today's two function bodies.

### WR-01 — the re-run hazard

"Safe to re-run" was true only at first apply. Afterwards every client INSERT lands NULL *by design*, and an unbounded re-run would sweep exactly that population. Backfill and post-verify (a) are now bounded by one transaction-local GUC (`quantalyze.attest_backfill_cutoff`) — a second literal could drift earlier than the backfill's and pass vacuously.

### WR-02 / MIG-02 — the unverified composition

Post-verify **(f)** asserts both RPCs' `pg_get_userbyid(proowner)` is in the scrub trigger's allowlist, plus a loop asserting that allowlist actually appears in the trigger body (the array is a second copy; two copies that can disagree is this phase's own subject).

### MIG-01 — the census pin

Aborts on `v_mt5 <> c_pin_mt5 OR v_sig <> c_pin_mt5`; the total is reported as a delta. The signature is tested **first**, so the two-sided discriminator is preserved — a PROD apply still cannot reach the lenient branch.

### WR-03 / MIG-03 — deploy order

Documented in a ⛔ block at the top of the migration header and as a general rule in `CONTRIBUTING.md` §2 (the section that already documents auto-apply-on-merge). No land/deploy checklist file exists in the repo, so per instruction I did not invent one; `TODOS.md` was not used because CONTRIBUTING §2 is the procedural home for this behaviour.

**Should the composite arm be softened to match the single-key arm? My assessment: not as described — and the two arms are not actually inconsistent.** The single-key arm's degradation is safe *because it degrades toward the control*: a failed read leaves `attestedVenue` null and `venueSupportsScopeProbe(null)` answers PROBE. The composite arm cannot degrade toward the control, because when the embed read fails it cannot enumerate members at all — so it refuses. Softening it to proceed would skip the ASVS V4 probe for every member of every composite, i.e. fail **open** on a security control, which is a real regression rather than a parity fix. There is a narrower variant that *is* defensible — tolerate only `42703`/`PGRST204` for one release by re-reading without `attested_venue` and treating every member as unattested, so all members are PROBED — which removes the outage window while still failing toward the control. **Not implemented here:** it is route logic owned by another plan and needs its own oracle over the tolerated-vs-refused shapes. The shipped mitigation is the deploy ordering, which removes the window entirely.

### MIG-04 (LOW) — accepted, no action

The edit to the already-applied `20260810120000` is **comments-only**: a comment-stripped diff of the pre-change blob against the working tree is byte-identical, so zero statement bytes changed and no database is affected. The drift that invariant 11 protects against cannot occur. Recorded rather than remediated.

## Residual Risk — read this before treating CR-01 as closed

**Remedy (b) makes the invariant enforced. It does not make the venue server-validated.** Stated plainly, because the finding was precisely that a narrower guarantee had been written down as a broader one:

- `create_wizard_strategy` and `add_wizard_composite_key` still **validate nothing**. They write the `p_exchange` they were called with.
- Both still hold `EXECUTE` for `authenticated` and are still reachable directly over PostgREST. **The RPC door is still open** — assertion 5d asserts that it is, and asserts what the outcome is, rather than pretending otherwise.
- A caller *can* still mint a row attested `mt5` and skip the submit-time scope probe on their own key. What the CHECK guarantees is that this costs them `exchange = 'mt5'` too, so the key is routed to the MT5 adapter and never syncs. **The bypass is self-defeating, not impossible.**
- That defence is a property of the current venue set — `mt5` is the only member of the probe-exempt set. If a *syncable* venue is ever added to that set (RESEARCH names sFOX as the plausible next member), the coupling stops paying for the forgery and the bypass becomes free. **The CHECK does not protect against that; only remedy (a) does.**

The honest one-line status: *the probe gate can no longer be switched off by a client INSERT, and can no longer be switched off selectively by anyone — but it can still be switched off by a caller willing to break their own key's ingestion.*

Closing it properly is remedy **(a)**: move the `api_keys` INSERT behind a service-role writer that passes the venue *it* validated, and withdraw `authenticated` EXECUTE from both RPCs. That is the connect-flow refactor both migrations defer.
