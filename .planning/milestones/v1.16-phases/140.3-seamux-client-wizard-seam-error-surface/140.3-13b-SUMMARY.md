### THE CAPTURE POLICY — inherited, cited, never re-derived

Read from `140.3-13a`'s docblock in `src/app/api/admin/match/eval/route.ts` and applied verbatim:

> **Capture from a seam route's TERMINAL, UNCLASSIFIED error arm — the arm reached when the caught
> value matched no typed branch — and from any arm that detects an UPSTREAM CONTRACT VIOLATION (a 2xx
> whose body cannot be used). Capture from NOTHING ELSE: not a breaker short-circuit
> (`CircuitOpenError`), not an upstream timeout (`AnalyticsTimeoutError`), not a forwarded upstream
> 4xx, and not a CSRF / auth / rate-limit / validation rejection the route makes itself. Pass the
> caught value UNMODIFIED to `captureToSentry`, with `tags: { surface, step }` and a `secrets: [...]`
> array naming every per-request credential in scope.**

Each of the five routes' import comment **cites `admin/match/eval/route.ts`** rather than restating
the rule. The policy text appears in this repo exactly once.

### 🔴 AMBIGUITY-1 — `scenario/optimize` has no 4xx/5xx range split, and the policy answers differently depending on which half you read

The plan says: *"If the recorded policy is ambiguous at a site, record the ambiguity and the reading
you chose rather than substituting your own rule."* This is that site, and it is the only one.

The policy's **exclusion** list names *"a forwarded upstream 4xx"*; its **inclusion** list names the
terminal arm plus contract violations, then says *"Capture from NOTHING ELSE"*. At
`admin/match/eval` those two halves never collide, because `140.3-11` gave that route a **range
split** — only 4xx is answered in the typed arm, and a 5xx keeps falling through to the terminal arm.
That is why `13a` could write *"A 5xx keeps falling through to the terminal arm and **is** captured —
that is the policy's service-permanent outcome half."*

**`scenario/optimize` has no such split.** Every `AnalyticsUpstreamError`, 4xx or 5xx, is answered
with a flat 502 in one typed arm. So:

- a **literal** terminal-arm-only reading leaves an upstream **5xx unreported at this route** while
  the identical failure **is** reported at `eval` — an asymmetry that would be an accident of arm
  shape, not a decision;
- capturing the whole arm would violate the policy's one explicit exclusion.

**READING CHOSEN: apply the policy's own STATUS discrimination — the half it argues explicitly —
rather than the file shape it happened to be written against. 5xx captured, 4xx not.** Nothing about
the route's status, body or headers changes. The reasoning is written into the route so it is a
decision on the record, and **both directions are pinned** (a capture-everything and a
capture-nothing implementation each satisfy exactly one of the two cases). Ledger row **M79c**
falsifies the exclusion half.

**NOT done here, stated so it is not smuggled in:** adding the range split to the *response*, so a
deliberate upstream refusal survives with its own status the way `140.3-11` gave the admin/match
pair. That is a status-shape change (TS-34's family) and does not belong in an observability plan.

### The second reading, recorded at both key-connect routes

Neither `create-with-key` nor `composite/add-key` has a ladder of typed `catch` branches to fall off
the end of — the shared `classifyKeyValidationError` **is** the ladder, and its own terminal is
`{code:"UNKNOWN", status:500}`. So *"the arm reached when the caught value matched no typed branch"*
is expressed at those two routes as **`code === "UNKNOWN"`**. Reading the classifier's verdict is
what keeps the rule mechanical at those sites instead of re-implementing its cascade. Everything the
classifier **did** recognise is then excluded for free and for the policy's own reasons:
`SERVICE_UNAVAILABLE_RETRY` is the breaker, `KEY_NETWORK_TIMEOUT` the timeout, and the signature /
auth / MT5 verdicts are caller faults.

### ✅ `create-with-key`'s breaker cell — VERIFIED UNDISTURBED, by reading and by test

CONTEXT calls it *"the best in the audit"* and the plan forbids disturbing its three properties. The
capture was placed **after** `classifyKeyValidationError(err)` and **before** the `headers`
computation, and is gated on the classifier's verdict. Verified at source:

| Property | State |
|---|---|
| The caught **VALUE** (not `message`) reaches the shared classifier | ✅ unchanged — `classifyKeyValidationError(err)` |
| The status is **derived from** the classifier | ✅ unchanged — `const { code, status } = …`, returned as-is |
| The **conditional** `Retry-After` | ✅ unchanged — still `err instanceof CircuitOpenError ? {…, "Retry-After": String(err.retryAfterS)} : NO_STORE_HEADERS` |

All three are also **re-pinned by test**: the breaker negative case asserts `503` +
`SERVICE_UNAVAILABLE_RETRY` + `Retry-After: 42` alongside its zero-capture assertion. Only a **type
check** on the live value can yield `SERVICE_UNAVAILABLE_RETRY` — a stringified error would land on
`UNKNOWN`/500 — so that one case would redden if any of the three moved.

### The oracle: mock the TRANSPORT, not the helper

`@sentry/nextjs` is mocked at all five test files and `@/lib/sentry-capture` is **not**. None of the
five previously mocked the helper, so no `.seam.test.ts` split was needed (unlike `13a`'s
`verify-strategy`). The scrub therefore really runs, and **TRAP-1 is asserted in BOTH directions at
every route**: the secret is gone AND `ECONNREFUSED` / `ENOTFOUND` survives. Over-redaction destroys
the diagnosis, and a one-sided test ships that state green.

### 🔴 FINDING-F — a `vi.doMock` from a neighbouring block would have made all ten `create-with-key` cases pass VACUOUSLY

The first run of the new `create-with-key` block was **10 × 401**. The preceding
`unmocked withAuth boundary (H-0306)` describe registers `vi.doMock` for the REAL `@/lib/api/withAuth`
and for a Supabase client with **no authenticated user**, and a `doMock` registration **outlives the
`vi.resetModules()` in its own `afterEach`** — reset clears the *module* registry, not the *mock*
registry. Every new case re-imports `./route`, so all of them ran against a 401 short-circuit.

⚠️ **The dangerous half is what this does to the NEGATIVE cases.** "a breaker short-circuit is never
captured", "a caller fault is never captured", "a 400 never reaches the seam" — every one of them
would have gone **GREEN** on a 401, because nothing was captured for the trivial reason that the
handler never ran at all. Only the five POSITIVE cases reddened. A delivery that wrote only negatives
here would have shipped a fully vacuous policy oracle. Fixed by re-registering the file-top factories
in the block's own `beforeEach`, with the reason written in-file. **Found by measuring the first run,
not by reasoning about it.**
