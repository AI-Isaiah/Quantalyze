## Task 1 — `8e543e92` · a wait becomes representable

**This was plumbing, not copy — correction C-7's central point, confirmed at source.** Before this
commit `WizardErrorContext` had six fields and none was a wait; `ErrorEnvelope` had seven and none was
a wait. No amount of copy authoring could have produced a countdown.

| Layer | Field | Case | Why |
|---|---|---|---|
| `WizardErrorContext` | `retryAfterSeconds?: number` | camelCase | matches its six siblings (`draftId`, `sizeMb`, `issueCount`, …) |
| `ErrorEnvelope` | `retry_after_seconds?: number` | snake_case | matches every other multi-word field on the envelope (`human_message`, `debug_context`, `correlation_id`) |

**Units are SECONDS, end to end, and the decision is made exactly once** — at the context field, in
its docblock. `parseRetryAfterSeconds` returns seconds and `CircuitOpenError.retryAfterS` is seconds,
so nothing between the wire and the field converts. Conversion happens only at render. Mixing units
across this boundary is how the raw-`Number()` NaN bug reached this exact surface (B20).

**Additive by the `cause?` precedent, and proven so.** `buildEnvelope` carries the value verbatim —
no clamp, no default, no unit change. The additive-safety property is asserted against a **hand-typed
expected envelope** for `KEY_RATE_LIMIT`; nothing reads `WIZARD_ERROR_COPY[code]` on the expected side
of an `expect`. Zero `buildEnvelope` call sites changed.

**The renderer shows it only when a wait is PRESENT *and* the error is retryable**, in the existing
`font-metric tabular-nums` figures idiom the `correlation_id` line already uses. Two conditions,
tested independently so a regression in one cannot hide behind the other:

| Case | Result |
|---|---|
| present + recoverable + `onRetry` | renders `Try again in 90s.` |
| present, `recoverable: false` | **no wait line** — a countdown beside an unretryable error promises that waiting changes the outcome |
| present, no `onRetry` handler | **no wait line** — tested separately, so collapsing the two conditions reddens |
| **absent** | **no wait line at all** — not `0s`, not "shortly" (TRAP-3) |
| `0` or negative | no wait line — the ONE parser never emits these, so either arrived around it |
| `2520` (42 min) | renders `2520s` verbatim — advisory and **unclamped**, per the in-file B20 argument |

`wizardErrors.test.ts` additionally pins that the field is **inert with respect to copy**: supplying a
wait changes no `title`, `cause`, `fix` or `actions`, and `KEY_RATE_LIMIT`'s static *"Wait 60 seconds"*
fix line is **not** promoted into the wait slot — that sentence is copy, not a measurement.

## Task 3 — `4986584b` · TS-34's status half

**What was wrong.** The upstream's per-key 429 throttle (PYAPIFIX2-03) was flattened into an
`Error.message`, matched **none** of the catch's six substrings, and came out as `PROBE_FAILED` + a
hardcoded **502** with the upstream's `Retry-After` discarded. A one-minute throttle read to the user
as an indefinite fault on **our** side, with no wait and nothing to act on. 502 says *"the upstream is
broken"*; 429 says *"you are being throttled, and here is for how long"*. Those are different claims
about whose fault it is, and only one of them was true.

**Mechanism.** The upstream **status** and the upstream **`Retry-After`** now ride the thrown error's
`cause` alongside the machine code `140.3-01` already put there — the stringify-to-`message` hop
destroys both, and the cached callback can only reach the handler by throwing. The catch branches on
`status === 429` **below** the `CircuitOpenError` type check and **above** the substring cascade,
exactly as `classifyKeyValidationError` orders its own middle branch and for the same two reasons.

**The gate is the upstream STATUS, not the wire code.** This is the plan's `RATE_LIMITED` mapping,
implemented through the evidence that actually disambiguates it. `140.3-05` recorded the reason as an
open residual: `RATE_LIMITED` means **our limiter** (429) in the app-global vocabulary and **the venue
throttling us** (400) in the venue-transient one, and telling them apart needs the status. Gating on
429 settles it with no lookup table — and is also the only evidence available when the 429 comes from
an edge/WAF layer with no JSON body at all (a case with its own test).

**The wait is forwarded, never fabricated.** Read through the ONE parser (HTTP-date safe, never
`NaN`/`0`/`<0`) and re-published verbatim in seconds. **No header in ⇒ no header out, and the copy
names no duration.** The body asserts `error` contains no digit at all.

### Both 429 producers verified on the wire, at source

| Producer | Emits `Retry-After`? |
|---|---|
| `analytics-service/main.py:529` — app-global `RateLimitExceeded` handler | ✅ `headers={"Retry-After": str(retry_after)}` |

### 📌 THE RECORDED DECISION — this route's private codes stay a SEPARATE vocabulary

> **`PROBE_BACKEND_UNAVAILABLE` / `PROBE_TIMEOUT` / `PROBE_FAILED` (+ the new `PROBE_RATE_LIMITED`)
> do NOT join `WizardErrorCode`, and `classifyKeyValidationError` is NOT adopted at this route.**

Reasons, in order of weight — the first two are measurements, not preferences:

1. **5 of 6 real messages fall to `UNKNOWN`/500** through that classifier (table under FINDING-A).
   It classifies key-validation faults; every fault here is proxy-infrastructure.
2. **Its `RATE_LIMITED` verdict is 503**, so adopting it makes this plan's required 429 unreachable.
3. **The consumer renders the code to the user.** `KeyPermissionBadge` prints
   `` `${code}: ${message}` ``, so swapping vocabularies without swapping copy puts two vocabularies
   in one body and changes user-visible strings.
4. **`140.3-03` engineered its fail-CLOSED message to land on `PROBE_FAILED` 502** and pinned it;
   the classifier turns that security fail-closed into a terminal 500.
5. **The sharing that matters is already in place** — the breaker verdict comes from the shared typed
   `CircuitOpenError` and the ONE `CIRCUIT_OPEN_COPY` from `140.3-04`'s leaf. That is
   `create-with-key`'s genuinely valuable property, and it is a preserve here.

**The substring cascade is KEPT** — `.includes(` unchanged at **6**, zero branches replaced — as the
fallback for genuinely uncoded faults, per TS-35's reasoning.

**A copy note this plan will not resolve, stated so it is not lost.** The 429 body reuses the route's
own existing sentence `"Too many requests"` verbatim rather than authoring one — `140.3-12` owns new
sentences. It is distinguished from this route's **own** limiter arm (which returns the same sentence
with no code) by the `PROBE_RATE_LIMITED` code.

### ⚠️ Task 1's plumbing does NOT reach this route's consumer — an honest gap

`KeyPermissionBadge` is **not** an `ErrorEnvelope` consumer: it does not call `buildEnvelope` and
renders a flat string. So the envelope's `retry_after_seconds` slot does not currently produce a
countdown at this route; the wait lands in the **`Retry-After` header**, where a machine can read it.
**No countdown is claimed at the badge**, and nothing here asserts one. Wiring that surface onto the
envelope is a separate change with its own consumer, not something to smuggle in here.

### Residual, enumerated rather than absorbed

The seam envelope also carries the wait in its **body** as `retry_after_seconds`. Only the **header**
is forwarded. Reading the body field would require a **new export on the `seam-discriminator` leaf**,
whose `EXPECTED_EXPORTS` **set-equality** guard belongs to `140.3-01` — widening a shared leaf's public
surface to serve one route is exactly the bundling TRAP-8 warns against. Since both production
producers emit the header, the gap is a redundant second copy of the same number, not a missing wait.
Recorded in the TS-34 ledger row.
