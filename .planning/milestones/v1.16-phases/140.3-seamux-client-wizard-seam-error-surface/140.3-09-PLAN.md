<objective>
Make a recoverable seam error able to **name the real wait**, and honour `Retry-After` for the
breaker's 503 rather than only for a 429.

Purpose: obligation `TS-34` (its status half); requirement `SEAMUX-06` (the `Retry-After` clause;
the TRAP-4 clause is plan `140.3-10`).

## ⚠️ SC4 NEEDS PLUMBING, NOT COPY (correction C-7). Budget it as the first task.

The success criterion says a recoverable error should "name the real wait". **That is
*unrepresentable* today, not merely unimplemented:**

- `WizardErrorContext` (`src/lib/wizardErrors.ts`) has `trades`, `days`, `draftId`,
  `computationError`, `sizeMb`, `issueCount` — **no wait field**.
- `ErrorEnvelope` (`src/lib/envelope.ts`) is `{ ok, code, human_message, cause?, debug_context,
  correlation_id, recoverable }` — **no wait slot**.

So no amount of copy authoring can produce a countdown. The renderer already has the hook —
`ErrorEnvelope.tsx` computes `const showRetry = envelope.recoverable && Boolean(onRetry);` — but there
is nothing to render.

## ⚠️ B-11's mechanism claim is FALSE; its conclusion survives and gets stronger (correction C-7)

B-11 says *"`Retry-After` is honoured at 1 of 4 surfaces. Only `SyncPreviewStep` reads it."*
**ZERO of the four wizard surfaces read it.** `SyncPreviewStep`'s retry affordance is driven by
`const showRetry = elapsedMs >= RETRY_THRESHOLD_MS;` — a **client-side elapsed timer**, not a header.

The complete client reader class is **three sites**, exactly one of which is a seam route:

| # | Reader | Endpoint | Seam? | Gate |
|---|---|---|---|---|
| 1 | `PortfolioImpactPanel.tsx` — `const headerSec = parseRetryAfterSeconds(res.headers);` | `/api/simulator` | **YES** | ⚠️ inside `if (res.status === 429) {` — **the breaker's header-only 503 skips it entirely.** This is B-23. |
| 2 | `useMandateAutoSave.ts` | `/api/preferences` | no | 429 only |
| 3 | `StarToggle.tsx` | `/api/watchlist/*` | no | `!res.ok` |

B-11 and B-23 are the same finding attributed to two different files; **B-23 is the source-verified
one.** Only site 1 is in scope.

**The header is already on the wire at FOUR routes, not three.** `create-with-key`,
`composite/add-key` and `finalize-wizard` all mirror `err.retryAfterS` into a `Retry-After` header on
the `CircuitOpenError` path — **and so does `keys/[id]/permissions`.**

⚠️ **CORRECTED at the revision gate: this plan's original premise that `keys/[id]/permissions` "does
not publish it at all" was FALSE.** Measured on the tree, that file emits `Retry-After` at **three**
places, including a correct `CircuitOpenError` arm doing `"Retry-After": String(err.retryAfterS)`.

**TS-34 is therefore narrower and sharper than "add the header":** the route does not forward the
**UPSTREAM** `Retry-After` on the `/internal` **429 throttle** path. That body is flattened into an
`Error.message`, the substring cascade matches none of its six branches, and the result is
`PROBE_FAILED` + a hardcoded **502** with the upstream's wait discarded. **Its own breaker path is
already correct and is a PRESERVE, not a fix target.**

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Upstream `Retry-After` → client countdown | An upstream-controlled number drives a disabled control and a displayed duration |
| Typed breaker error → response header | `retryAfterS` becomes a public contract value |

| T-140.3-09-02 | Denial of service | A malformed `Retry-After` producing `NaN` and leaving the retry control enabled, so a re-click immediately re-fails | mitigate | The ONE parser (`parseRetryAfterSeconds`) is used; it handles the HTTP-date form and never returns `NaN`/`0`/`<0`.
