# Phase 140.3 Plan 08: Every seam call site observes the HTTP outcome — Summary

**One-liner:** All four SEAMUX-05 sites now read the status (and, on the sync path, the enqueue
evidence) before deciding anything, so a breaker 503 can no longer render as a completed recompute, an
unrecognised 200 can no longer start a poll for a job that was never enqueued, and no user-facing
string under `src/components/` names an internal environment variable.

## Task 1 — `ApiKeyManager`: both call sites, and the env-var lie

### 🔴 FINDING — the breaker sentence was reaching this consumer and being overwritten

The plan's instruction is to copy the file's own better `!res.ok` arm — the one that branches on
`content-type`. Measured, **that arm carries a defect of its own**, and copying it verbatim would have
propagated it:

```ts
const err = await res.json().catch(() => ({ error: "Sync failed" }));
throw new Error(err.error || "Trade sync failed");   // ← reads `error` ONLY
```

`/api/keys/sync` answers a breaker trip through `postProcessKey`, whose `CircuitOpenError` arm returns

```
{ ok:false, code:"CIRCUIT_OPEN", human_message: <the sentence>, correlation_id, recoverable:true }  503
```

— copy under **`human_message`**, not `error`. So the sentence `140.3-04` spent a whole plan
consolidating onto ONE production source **arrived at this consumer and was replaced with "Trade sync
failed"**. Both envelopes are live from the same route: the route's own arms (400 / 404 / 429 / the
composite-probe 503) use `{ error }`; every `postProcessKey` envelope uses `{ code, human_message }`.

`syncFailureMessage()` reads both, `error` first. This is the same class as `140.3-07`'s B-27 finding —
a failure path swallowing copy a route deliberately wrote — and it is fixed here rather than deferred
because it lives inside the exact arm this plan rewrites. Two tests pin it in both directions: the
breaker sentence renders, **and** an `{ error }` body still renders its own message.

### The enqueue evidence was already authored server-side

The route stamps `ok: true` on its three structured success branches and states in-file why its drift
fallback does not:

> *"Deliberately NOT stamped with ok:true — the structured success branches above own the
> discriminator, and marking an unrecognized shape ok:true would falsely signal success."*

So the client did not need a heuristic; it needed to **read the discriminator the server already
publishes**. `isSyncEnqueued(body)` is `body.ok === true`. The one response meaning "nothing was
enqueued" was precisely the one that used to start a 15-minute poll for it, ending in a timeout whose
copy blamed the computation.

**Not a wall-clock backstop.** That would have timed the symptom out while the poll still ran and the
user was still told their analytics were computing. The fix is not entering the state.

### The background sync stays non-blocking

`.catch()` became `.then(observe).catch(surface)`. Nothing is awaited on the render path — "don't block
the UI" is a real requirement and `handleAddKey` continues past it unchanged. The observation happens
inside the promise chain and routes to the **same `SyncProgress` surface** an explicit sync failure
uses. `lastAttemptedKeyId` is now set before the request so that surface's Retry button has a target;
without it the retry closure sees `null` and no-ops, a pre-existing bug the state's own comment
records.

The enqueue-evidence check was applied at the background member **as well as** the explicit one —
deliberately one shape at both members, because "3 of 5 sites" is this programme's signature failure
and a class fixed two ways cannot be audited.

### The replacement sentence, verbatim

> **We couldn't start the sync. Your key is saved — retry in a moment, and contact support if it keeps failing.**

Replacing: *"Analytics service unavailable. Ensure SUPABASE_SERVICE_ROLE_KEY is configured."*

Against DESIGN.md §Voice: declarative, sentence-case, active ("We couldn't start"), no exclamation, no
banned glyph, names nothing internal. **No number is given because none exists** — this component reads
no `Retry-After` (SEAMUX-06, plan `140.3-09`), so naming a wait would be the fabrication the rule
exists to prevent. *"Your key is saved"* is a **fact** at both call sites, not reassurance: the
background sync runs only inside `if (newKey)` (the insert returned a row) and the explicit sync only
after `handleLinkKey` resolved without error.

## Task 2 — `handleRecompute`, and the `WeightOptimizerSection` bare catch (ONE task, TRAP-8)

### `handleRecompute` copies its own sibling

`if (!res.ok)` now runs **before** the body is touched, matching `handleDecision` twenty lines below in
the same file. The JSON read on the failure path is guarded (`.catch(() => ({}))`) because a gateway
answers with HTML and an unguarded `res.json()` would throw a `SyntaxError` that replaces the real
failure — which M63 reproduced verbatim.

**The failure routes to `setError`, not to the pre-existing `alert()`.** This is a deliberate behaviour
change and the reasoning matters: an alert is dismissed in one click while the stale queue stays on
screen — the same "reads as a completed recompute" outcome wearing a different costume. `setError`
reaches the component's error-first card (`if (error || !data) return`), which is the guard that makes
this component immune to `140.3-07`'s stale-result class, and whose Retry button re-runs `load()` and
clears the error. The `disabled: true` branch keeps its alert: that is a **success** reply, not a
failure, and an anti-regression case pins it.

**The in-flight guard is a second ref, not a reuse of `loadIdRef`** — see D-2. `recomputing` is React
state, so two `r` presses inside one frame both observe `false` and both POST; the RED run measured
exactly that (`expected 2 to be 1`). A ref is written synchronously and is the guard that actually
holds.

### `WeightOptimizerSection` (B-13) — three named failures, not one

The old state said *"The optimizer is unavailable right now. Try again shortly."* for four different
facts. For two of them it is false, and the second half is **steering**: it instructs the allocator to
re-run a request that will be refused identically every time.

| Outcome | Named as | Why |
|---|---|---|
| 5xx, or a status we could not read | `unavailable` | availability IS the fact; unreadable status defaults to the *weaker* claim |
| 4xx | `refused` | the optimizer answered, immediately, and would not run it |
| `SyntaxError` from `res.json()` | `unreadable` | we cannot tell whether it ran; asserting availability claims something we cannot see |
| a rejected fetch / `TypeError` | `unavailable` | availability |

The caught value goes to `console.error` and **never** to the DOM (`140.3-07`'s B-27 discipline),
pinned by a case asserting neither `NetworkError` nor its embedded `localhost:8002` host reaches the
screen while the console call still happens.

**Nothing else in the file changed.** The 4xx/5xx split defaults an absent status to `unavailable`,
which is also why the pre-existing *"a non-ok HTTP response ⇒ the couldn't-reach empty state"* test
(whose mock supplies no `status`) stayed green **byte-unchanged**. No existing test in this plan was
edited or weakened.

### TRAP-8 held

`setResult(null)` — the locked shape `140.3-07` copied to both live B-26 members — is **byte-unchanged**:

```

grep -c "setResult(null)" "…/WeightOptimizerSection.tsx"                                →  1
```

behavioural oracle for it would be theatre.
