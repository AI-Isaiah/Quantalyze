## The finding in one paragraph

`DESIGN.md:329` states the Error Envelope authoring rule is *"Code-review block enforced by grep at
PR-time."* **No such grep exists.** And the deeper problem is not the missing grep: **the rule is
type-impossible for four of the five surfaces it names.** `buildEnvelope(code: WizardErrorCode, …)`
(`src/lib/envelope.ts:75`) accepts only a wizard code, while `DESIGN.md:312` names *"wizard, CSV
upload, factsheet load failure, admin status page, future `error.tsx` route boundaries."* Only the
wizard has `WizardErrorCode`s. **Three separate plans — `140.3-07`, `-11` and `-15` — hit that wall
independently, each reading the source fresh, and each declined and flagged rather than forcing it.**
That is not three failures of will. It is a correctly-specified codebase colliding with an
incorrectly-specified document.

**Nothing here is a user-visible defect.** Every surface renders error copy today. This is a
document describing a system we do not have.

## The options

### ⭐ Option A — Correct the doc *(recommended; `GAP-RESEARCH` Q5, HIGH confidence)*

Three edits to `DESIGN.md`, no code:

1. **`:328`** — scope the mandate to **wizard error paths**, where `buildEnvelope` is
   type-applicable and where all four wizard step components already comply. Write it as a scope
   statement, not a count, so it cannot go stale the way GC-4 just found five other counts had.
2. **`:329`** — delete the sentence claiming a PR-time grep enforces this. Replace with the truth:
   an authoring convention with **no automated enforcement today**, and name where enforcement
   would live if it is ever wanted (R10). *A documented gate that does not exist is worse than an
   undocumented one, because a reader stops checking.*
3. **`:311-314`** — record the tension where the five surfaces are named: four have no compliant
   path today and render error copy through other mechanisms (`csvErrorEnvelope()`; the admin
   error-first cards). **Widening `buildEnvelope`'s `code` parameter beyond `WizardErrorCode` is the
   enabling prerequisite** for any migration — unscheduled, needs a decision.

**Pros** — Root-cause obsession (Rule 6): fixes the specification defect rather than bandaging it.
Makes the document true today without pretending the tension is resolved. ~15 minutes.

**Cons** — The four non-wizard surfaces stay unenforced and inconsistent. Anyone wanting one
canonical envelope across the product must open that as its own work. Edit 3 exists precisely to
make that visible, but it is still a deferral, and deferrals are how this stayed open through three
plans.

### Option B — Build the grep gate as declared

**Pros** — Makes the document true in the other direction. The homes already exist and are wired
(R10).

**Cons** — **It would red-CI a tree with no compliant fix available.** The 10 `csvErrorEnvelope`
sites and the two CSV wizard steps have no `WizardErrorCode` to pass (R4/R7/R8). The only ways back
to green are to widen the guard until it catches nothing, or to invent wizard codes for non-wizard
surfaces — which `140.3-11` measured as breaking `140.3-12`'s pinned marker count. It also fails the
repo's own stated bar for a new structural gate (`tools/eslint-plugin-quantalyze/index.mjs:7-8`):
ship a rule only when its **runtime source of truth is already shipped**, and here it is not. And it
would be advisory at merge anyway. **If chosen, this needs its own plan** — a `scripts/` gate, a
`CONTRACT_GUARDS` entry, a CI wiring change, and its own falsification.

### Option C — Widen `buildEnvelope`'s `code` parameter first, then migrate, then enforce

**Pros** — The only option that eventually delivers what `DESIGN.md` currently promises: one
canonical envelope across all five surfaces. Removes the type impossibility at its root rather than
narrowing the promise.

**Cons** — Genuinely large. Touches `envelope.ts`'s public type, the copy table, `140.3-12`'s pinned
marker count, the CSV route's 10 sites and both CSV steps. **If chosen, this needs its own phase.**
Recommended companion: apply option A's three edits in the meantime, with edit 3 naming the widening
as scheduled work and a named owner, so the document is not left false while the migration is queued.

### Option D — Leave `DESIGN.md` exactly as it is

**Pros** — Zero change. The tension is already recorded in the verification report and in three plan
SUMMARYs, so nothing is lost from the record.

**Cons** — The document keeps asserting an enforcement mechanism that has never existed. That is the
same defect class as the inert poll pin one level up: **an unfalsified authoring rule that reads as
protection.** A fourth plan will hit the same wall and spend the same context re-deriving the same
finding. Three already have.

## Falsifiability note

This brief carries no Falsifiability Ledger row, and here is why — stated rather than left as an
unexplained absence, which is the same standard `140.3-G2` is held to for GC-4.

A documentation correction has no runtime behaviour to mutate. Its discriminator is a
before/after measurement on the untouched tree, and it is sound:

```
grep -c 'enforced by grep at PR-time' DESIGN.md
```

**Pre-value 1** (measured, `DESIGN.md:329`). Under options A, B or C it becomes **0**. Under option D
it stays **1**, and that is the recorded consequence of the decision rather than a failure.

Could an untouched or broken tree return the pass value? No — the pre-value is 1 today, so `0` is
reachable only by actually removing the sentence. That is the check the four GC-4 anchors are held
to, and one of those four failed it on first drafting (`'all 18 charts'`, pre-value already 0
because the sentence wrapped across two lines). This one was re-measured after that lesson.
