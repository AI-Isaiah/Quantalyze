## TS-37 — the split, and the three arms that were deliberately left alone

### The new code

`COMPOSITE_TOO_MANY_MEMBERS`, emitted **only** at `if ((members?.length ?? 0) > MAX_COMPOSITE_MEMBERS)`.

**Copy, verbatim:**

- **title:** *"This draft has more than 10 keys attached."*
- **cause:** *"A multi-key strategy can hold at most 10 keys, because we re-check every one of them against its exchange before submitting. This draft came back with more than 10, so we stopped rather than finalise a strategy whose extra keys were never re-checked. Nothing was submitted, and retrying will not change the count."*
- **fix[0]:** *"Go back to the keys step and remove keys until 10 or fewer remain, then submit again."*
- **fix[1]:** *"Splitting the extra keys into a second strategy also works — each strategy carries its own limit of 10."*
- **fix[2]:** *"If you need more than 10 keys in one strategy, email security@quantalyze.com with your draft ID. The limit is ours, not your exchange's."*
- **docsHref:** `/security` — a real anchor-less page section rather than a fabricated `#anchor`.
- **actions:** `["request_call", "expand_log"]`

**The `actions` choice IS the fix, not a side effect.** `RECOVERABLE_ACTIONS` (in `src/lib/envelope.ts`)
is `{clear_and_retry, try_another_key}`. The new entry carries **neither**, so
`buildEnvelope` derives **`recoverable: false`**, and `ErrorEnvelope`'s
`const showRetry = envelope.recoverable && Boolean(onRetry)` evaluates false — **the Retry control does
not render.** The whole defect was a permanent condition handing the user a button that could only
ever produce the identical 503.

`request_call` is kept deliberately: removing the wrong affordance is only half the fix, and a code
offering *nothing* would satisfy every negative assertion while being a worse dead end. A positive
case asserts `actions.length > 0` and that `request_call` is present, for exactly that reason.

**Honesty check against `140.3-12`'s FORBIDDEN list.** *"Nothing was submitted"* is knowable here and
is the same verdict `140.3-12`'s own audit table already recorded for this arm's family (*"probe
fail-CLOSED — we stopped before submitting"*): the refusal returns **before the probe loop and before
any enqueue**. The table-wide copy-honesty guard is green over 54 entries.

**DESIGN.md §Voice compliance:** declarative sentence-case, active voice, no adjectives where a number
exists, and the limitation stated **with its threshold attached** — which for a member cap is the
canonical case for that rule.

## TS-33 — one field, and 🔴 FINDING-A: the id was in scope, one column away

### The row's premise is false as a general statement (correction C-7 / F-2), and the row is corrected in place

TS-33 says *"no caller sent `wizard_session_id`"*, citing a grep returning ZERO hits. That grep was
scoped to two files and then generalised. **`csv-validate` and `csv-finalize` both send it today**,
inside the `postProcessKey` `context`, and `process_key.py` reads it from exactly there — so
`idempotent_by_session` has been **TRUE on the CSV path all along**. The true scope was **one call
site**. This matters operationally: an executor who believes the mechanism dead will not consult the
CSV path, and the CSV path is the working reference for the field's shape.

### 🔴 FINDING-A — where the id came from, and why it is NOT the request body

My first pass grepped `finalize-wizard/route.ts` for the identifier, found **zero** hits, and nearly
concluded the id was out of scope (which would have meant a STOP-and-report, or a client-side body
field). **That was wrong, and the correction is the finding.**

`strategies.wizard_session_id` is a **real, persisted, owner-scoped column** (migration
`20260602190000`, F6). `create-with-key` writes it at draft creation via `p_wizard_session_id`, the
composite RPC does the same (`20260710180000`, ONB-03), and `create-with-key` already *reads* it back
as *"the client's stable idempotency token"*. So the id is available in this handler **as one extra
column on a SELECT it already performs**:

```
.select("api_key_id, wizard_session_id")   // was: .select("api_key_id")
.eq("id", fields.strategy_id).eq("user_id", user.id)
```

**This is the CSV path's PLACEMENT copied verbatim with a strictly better SOURCE:**

| | CSV path | finalize-wizard (this plan) |
|---|---|---|
| Placement | `postProcessKey` → `context.wizard_session_id` | **identical** |
| Source | request body, validated `isUuid` at the edge | **the owner-scoped draft row** |
| Spoofable by the caller of this request | yes (validated, but caller-chosen) | **no** |
| Extra query | — | **none** |
| Client change required | — | **none** — zero deploy-skew 400 risk |

The non-spoofability matters concretely: migration `20260726000225` (140.1 / PYAPI-01) had to scope
the verification unique index to `(strategy_id, wizard_session_id)` precisely *because*
`wizard_session_id` is caller-supplied and a platform-global unique index let one tenant's id reject —
and then leak — another tenant's row. Reading the value server-side keeps this route out of that
surface entirely.

**`X-Correlation-Id` was considered and REJECTED as the source.** `getWizardCorrelationId()` is
**module-memoized per page load**, so a browser reload — the likeliest way a user double-submits —
mints a fresh one. That is `T-140.3-14-05` exactly: keying a dedupe on a value that changes per
request is **worse than absent**, and a field-presence test cannot tell the two apart. **M83 run A**
is the falsifier for it.

### Absence is forwarded as absence

The column is NULLABLE. A conditional spread (`...(x !== null ? {wizard_session_id: x} : {})`) is used
rather than `wizard_session_id: x ?? undefined`, so the **key is absent**, not present-and-undefined,
and the wire body on that path is byte-identical to the pre-change body. Python then mints its own
uuid4 and runs with the dedupe off — where this route already was. Asserted with
`hasOwnProperty`, because `JSON.stringify` would hide the difference.

### Shadowing

The field sits **after** `...args.payload` in the context literal, so a client-supplied
`wizard_session_id` in the request body cannot displace the server-derived one. Pinned by its own case.

### The ordering constraint held

`src/lib/process-key-onboard-contract.ts` is in **neither commit**;
`tests/lib/process-key-onboard-contract-parity.test.ts` is **green**; **zero** migrations added.
TS-01's do-NOT-re-widen warning is honoured and confirmed by name.

Incidentally, the predicate's teeth were exercised first-hand: my duplicate-resume test initially
returned **502** — the exact H-5 signature. Traced rather than assumed: it was a harness fault (a
`Response` body can be read only once, and `mockProbeReadOnly` uses `mockResolvedValue`, handing the
same object to both requests, so the second request's scope probe threw). The contract admits the
corrected envelope, as invariants 1 and 2 require. The fix and the reason are recorded in-file so the
next two-request case does not rediscover it.
