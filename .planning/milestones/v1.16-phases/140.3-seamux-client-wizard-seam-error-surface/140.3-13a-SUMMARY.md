### Why THREE membership sets and not one

`SubmitStep`'s set is per-route because a step should admit the codes **its** route emits. This step
calls **two different routes with different contracts**, so it gets two sets, and `ConnectKeyStep` gets
its own third:

| Set | Route | Members | Why separate |
|---|---|---|---|
| `KNOWN_CREATE_WITH_KEY_CODES` | `strategies/create-with-key` | 17 | 7 direct + the shared `classifyKeyValidationError`'s returns |
| `KNOWN_ADD_KEY_CODES` | `strategies/composite/add-key` | 17 | same classifier half **by construction**; direct emissions differ |
| `KNOWN_SET_MEMBERS_CODES` | `strategies/composite/set-members` | **4** | ⚠️ **performs NO key validation at all** |

**The set-separation case is the sharp one and it is pinned:** a body carrying `KEY_AUTH_FAILED` — a
genuine `WizardErrorCode` and a genuine add-key outcome — resolves to `UNKNOWN` at `set-members`. Had
the two sets been merged into one per-step set, or replaced by a totality check over the union, that
body would render *"the exchange rejected your credentials"* on a call that only ever persisted date
windows, and the funnel would record a credential failure that never happened. A
`MULTI_KEY_WINDOWS_INVALID` arriving at `ConnectKeyStep` is pinned the same way, in the other
direction.

### No wire→wizard translation hop, and the reason is measured

`SubmitStep` translates first because `finalize-wizard` answers a breaker trip with the WIRE code
`CIRCUIT_OPEN`. Measured on disk for all three of this plan's routes:

```
grep -c 'CIRCUIT_OPEN\|UPSTREAM_TIMEOUT\|UPSTREAM_NETWORK_ERROR'
  create-with-key/route.ts        → 0
  composite/add-key/route.ts      → 0
  composite/set-members/route.ts  → 0
```

All three route every caught value through the shared `classifyKeyValidationError`, which maps
`CircuitOpenError` to `SERVICE_UNAVAILABLE_RETRY` — a **member of both key-entry sets** — before
answering. A translation hop here would be machinery no reachable path can exercise. If one of those
routes ever starts emitting a wire code it falls to `UNKNOWN`, which is the safe direction and is what
the unrecognised-code cases pin. Recorded in-file so it is a decision, not an omission.

## Task 2 — the captures

### 📋 THE CAPTURE POLICY — one sentence, for `140.3-13b` to apply VERBATIM

> **Capture from a seam route's TERMINAL, UNCLASSIFIED error arm — the arm reached when the caught
> value matched no typed branch — and from any arm that detects an UPSTREAM CONTRACT VIOLATION (a 2xx
> whose body cannot be used). Capture from NOTHING ELSE: not a breaker short-circuit
> (`CircuitOpenError`), not an upstream timeout (`AnalyticsTimeoutError`), not a forwarded upstream
> 4xx, and not a CSRF / auth / rate-limit / validation rejection the route makes itself. Pass the
> caught value UNMODIFIED to `captureToSentry`, with `tags: { surface, step }` and a `secrets: [...]`
> array naming every per-request credential in scope.**

It is written out **in full, once**, in a docblock in `src/app/api/admin/match/eval/route.ts`, and the
other three routes' import comments **cite that file rather than restating it** — two copies of a
policy is how two policies start.

**Why the terminal arm and only the terminal arm.** Every typed branch above it is a condition we
already understand, already count and already answer with a specific status. The terminal arm is *by
construction* the one that means "we do not know what this is". This also makes the rule **mechanical
rather than a judgement call**, which is precisely what lets a second plan apply it to five more
routes without reinterpretation.

**Why a breaker trip is never captured (the plan asked for this to be argued, not assumed).** A trip
is an expected infrastructure fact, and during the exact correlated incident Sentry exists to surface,
**every** request to **every** seam route short-circuits. Capturing them emits one issue per
short-circuited request across all fifteen routes at once — burying the single signal that identifies
the cause under thousands of copies of its symptom. The breaker's own state is the correct alerting
source for a trip.

**Why a timeout is never captured.** `wizardErrors.ts` documents 60-second Railway cold starts as
normal, so `AnalyticsTimeoutError` is an expected outcome of a healthy system under a cold start; a
sustained one trips the breaker, which then takes over. It is already answered with a specific 504.

**Why a forwarded 4xx is never captured.** `140.3-11` gave these routes a 4xx arm precisely so a
deliberate upstream refusal survives with its own status. Alerting on correct behaviour is noise. A
5xx keeps falling through to the terminal arm and **is** captured — that is the policy's
"service-permanent outcome" half, and it is pinned by a POSITIVE case at every route so the 4xx
negative cannot silently become "never capture".

### This half's four routes, with every arm's disposition

| Route | Captured arm(s) | Deliberately NOT captured | Per-request secrets |
|---|---|---|---|
| `admin/match/eval` | terminal (`upstream-error`) | `CircuitOpenError`, `AnalyticsTimeoutError`, forwarded 4xx, 401/403 | **none** — forwards no JWT, touches no exchange material |
| `admin/match/recompute` | terminal (`upstream-error`) | same four | **none** |
| `keys/[id]/permissions` | terminal (`upstream-proxy`) | `CircuitOpenError`; the **429 upstream throttle** (`140.3-09`'s arm — the limiter working is not a fault); 401/403/404 | **none**, and it is a FACT about the route, recorded in-file: exchange material is decrypted inside Python, and the one credential the outgoing request carries is `INTERNAL_API_TOKEN`, already on the leaf's env list |
| `verify-strategy` | **four**: upstream-contract (502), admin-client-config (500, `fatal`), public-token-persist, public-token-persist-threw | the per-IP 429; all four 400 validation arms; **`!result.ok`** (postProcessKey's already-classified envelope, which is where the breaker 503 lives); the `getSession` catch (anonymous is this route's normal case) | 🔴 **three** — a LIVE end-user Supabase JWT + the caller's RAW `api_key` and `api_secret` |

**No route is an exception.** All four capture.

**The template scores 6 while scrubbing at zero call sites.** Its 6 come entirely from

Satisfying it would require calling `scrubSeamError(err)` at each site, which would:
1. **double-scrub** — `captureToSentry` already scrubs the input, the tags and the extra;
2. **hand Sentry a STRING instead of an Error**, destroying grouping and the stack (`scrubCaptureInput`
   rebuilds an Error precisely so that does not happen);
3. **restore the per-caller convention SEAMCORE-06 deliberately replaced** — its own docblock says
   *"Ten sites each remembering to scrub is the '3 of 5' shape this programme has already paid for"*;
4. **contradict the plan's own named template**, which passes the raw value at all eleven sites.

Per hard rule 9 — *a prescribed fix that would delete or overwrite a surface another plan just built
is a finding, not an instruction* — the criterion is **recorded as measured and not satisfied**. The
underlying requirement (*"every new capture passes a scrubbed value"*) is discharged **by construction
at the chokepoint** and **proven behaviourally, end to end, at all four routes** — which is strictly
stronger than any proximity grep. `140.3-13b` should apply the same reading; the grep, run on its five,
will report whatever its import ordering happens to produce.

### The oracle: mock the TRANSPORT, not the helper

The house pattern is `vi.mock("@/lib/sentry-capture", () => ({ captureToSentry: spy }))`. Used alone,
**every payload assertion becomes vacuous about scrubbing** — the scrub lives inside the helper, so a
mocked helper never runs it and "no secret in the payload" would pass with the scrubber deleted.

So `@sentry/nextjs` is mocked and `@/lib/sentry-capture` is **not**, in
`admin/match/eval/route.test.ts`, `admin/match/recompute/route.test.ts` and
`keys/[id]/permissions/route.test.ts`. `verify-strategy/route.test.ts` already mocked the helper
(pre-existing), so its cases prove the **call site** — including that every arm NAMES its per-request
credentials — and the end-to-end scrub proof lives in `verify-strategy/route.seam.test.ts`, the file
that already runs the REAL client over REAL wire bytes with only `fetch` faked. That split is stated
in both files so nobody later "simplifies" it back.

**TRAP-1 is asserted in BOTH directions at all four routes:** the secret is gone AND
`ECONNREFUSED` / `ENOTFOUND` survives. Over-redaction destroys the diagnosis, and a one-sided test
ships that state green.
