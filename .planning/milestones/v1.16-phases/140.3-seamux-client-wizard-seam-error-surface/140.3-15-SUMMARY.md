## TS-38 — the config fault, and the three constraints that had to hold at once

### The wire envelope, verbatim

```
500  { ok: false,
       code: "SEAM_MISCONFIGURED",
       human_message: "We could not send this request — our own configuration is wrong. Retrying will not clear it.",
       correlation_id: <the request's own>,
       recoverable: false }
```

**No `Retry-After` header.** There is no wait that helps, and naming one is TRAP-3.

### The status is a DECISION and the reason is the obligation

**500.** Every alternative was rejected first and the reasons are in the source:

| Status | Rejected because |
|---|---|
| **502** | asserts the UPSTREAM is bad. That is the precise lie TS-38 exists to stop — removing it from the sentence and leaving it in the status line is half a fix |
| **503 / 504** | both signal TRANSIENCE. The condition is permanent until an operator redeploys, so a transient status invites exactly the retry `recoverable:false` removes. (`140.3-14` recorded this same mismatch as a residual on the composite cap; this arm does not inherit it) |
| **500 ✅** | "the server that produced THIS response is at fault" — literally true, we are that server. It is also `STATUS_CONTRACT.md` §1's SERVICE-PERMANENT class: *"a deterministic fault can only be cleared by an operator"* |

### The teaser constraint, asserted rather than intended

Threat **T-140.3-15-02 / T-140-08**: the anonymous landing-page teaser renders `human_message`
directly. A case asserts the sentence contains no `http(s):`, no hostname or platform name
(`railway|upstash|vercel|supabase|localhost|.com|.app|.test`), no bare 3-digit number, and no env
variable name. Readable in the string above as well as asserted.

### Why a NEW `WizardErrorCode` and not an alias — the three near-misses, read at source first

This file's own convention (`140.3-05`'s `CIRCUIT_OPEN` reasoning) is that a second member with the
same meaning is how a vocabulary starts lying, so an alias was the default and each candidate was
read before it was rejected:

| Candidate | Asserts, falsely |
|---|---|
| `SERVICE_UNREACHABLE` | *"We sent the request and never got an answer."* Nothing was sent — `resilient-fetch.ts` states in its own docblock that `SeamConfigError` throws *"before any store or network I/O"*. It is also recoverable; this is not |
| `SERVICE_UNAVAILABLE_RETRY` | *"wait a moment, then try the same action again."* True of a breaker cooling down, false of a config typo |
| `VALIDATION_FAILED` | *"a request that failed its shape check."* Closest on BEHAVIOUR (non-recoverable, our software's fault) and wrong on the FACT: nothing was sent and nothing was shape-checked |

### The copy, verbatim

- **title:** *"We could not send this request — our own configuration is wrong."*
- **cause:** *"A setting on our side is wrong, so we stopped before sending the request. Nothing was submitted and nothing was changed. Retrying will not clear it: the setting stays wrong until we fix it and redeploy. This is not your key, your exchange or your data."*
- **fix[0]:** *"Email security@quantalyze.com with the correlation id below — a configuration fault is ours to fix, and running the same action again will not clear it."*
- **fix[1]:** *"Nothing needs undoing on your side. The request never left our servers, so no draft, key or strategy changed."*
- **docsHref:** `/security` · **actions:** `["request_call", "expand_log"]`

**The `actions` choice IS the fix.** `RECOVERABLE_ACTIONS` (`src/lib/envelope.ts`) is
`{clear_and_retry, try_another_key}`; the entry carries **neither**, so `buildEnvelope` derives
`recoverable: false` and `ErrorEnvelope`'s `showRetry` evaluates false — **no Retry control renders**.
`request_call` is kept deliberately: a code offering *nothing* would satisfy every negative assertion
while being a worse dead end, and a positive case asserts `actions.length > 0`.

**DESIGN.md §Voice:** declarative ✓ sentence-case ✓ active ✓ no exclamation ✓ no adjective where a
fact will do ✓ em dash is one of the five permitted glyphs ✓. **`fix[0]` deliberately points the user
at the correlation id** — which is the id TS-20 in the same plan makes worth quoting.

## TS-20 — the diagnostic, and 🔴 FINDING-A: the row's three named outcomes do not reach this renderer

### The row's premise is right about the diagnostic and wrong about the surface

TS-20 says `body.detail.correlation_id` exists on **`SCORING_FAILED`, `EVAL_FAILED`,
`SIMULATION_FAILED`** and points at `ErrorEnvelope`'s render slot. Verified at source: those three
are raised in `analytics-service/routers/match.py` and `simulator.py`, and their consumers are the
two admin match cards and `PortfolioImpactPanel` — **none of which renders `ErrorEnvelope`**
(`140.3-11`'s FINDING-C recorded exactly this for the admin cards, and it is the DESIGN.md tension
restated below).

**What DOES reach the canonical renderer** is the `/process-key` family, and it carries the id too —
`process_key.py`'s error envelopes and `main.py`'s 422/429 app-global handlers both emit
`correlation_id`, at the **TOP level**. Both `finalize-wizard` and `keys/sync` forward that envelope
verbatim (`if (!result.ok) return result.response`), and `process-key-client`'s own four envelopes
carry the id as well. So the obligation is closed against the surface that actually renders, and the
row's premise is corrected in place rather than quietly satisfied. **The three named outcomes remain
unrendered because their surfaces are bespoke cards — that is the unresolved DESIGN.md tension, not
this row.**

### 🔑 The leaf mechanism — `140.3-11`'s, reused by name

`140.3-11` faced the identical question for `dependency`, decided it, and wrote the decision in three
places so it would be found: its SUMMARY, the leaf's docblock, and the purity test's docblock. **It
was followed exactly.**

`seamCorrelationId` is the **FIFTH** narrow, purpose-named extractor over the same private
`nestedDetail`. **`EXPECTED_EXPORTS` went 4 → 5 in the SAME commit as the export** (`c07b9c39`) — the
hard gate, verified by `git show --name-only`. The leaf is still import-free (**0**). The two
alternatives `140.3-11` rejected stay rejected and were not re-litigated: exporting `nestedDetail`
itself hands every consumer the whole envelope, and a generic `seamDetailField(body, name)` getter
makes the export set unable to say WHICH fields are reachable, which is the only thing that file is
for.

It **mirrors `seamErrorCode`'s both-shape read**, exactly as routed: `correlation_id` is TOP-LEVEL on
the flat envelopes and NESTED inside `service_error`, and a nested-only reader answers `null` on every
body from the other family — an answer indistinguishable from a correctly-absent value. **M85 is the
falsifier** and it reddens at the leaf *and* at both consumers.

### 🔒 A SHAPE GUARD was added, and it is not decoration

The value is rendered **verbatim into the DOM** and copied to the user's clipboard in the
`QUANTALYZE_DIAG` block. On `main.py`'s app-global handlers it is
`request.headers.get("x-correlation-id")` — **caller-supplied and echoed straight back**. Unbounded,
that is an injection surface into a support artefact.

Bounded by `^[A-Za-z0-9._:-]{1,128}$`, **hand-typed in the leaf, duplicating `CORRELATION_ID_SHAPE`
in `src/lib/correlation-id.ts`**. The duplication is forced, not lazy: that module opens with
`import "server-only"` and `import { headers } from "next/headers"`, both of which the purity test's
first four assertions forbid here — and the duplication is also the falsifier, since two independent
literals can disagree and one shared literal cannot. Pinned in both directions: CR/LF, whitespace,
markup, path traversal, `@`, `;` and a 129-character value are all refused; a UUID, a
`wizard:<uuid>`, a 32-hex Sentry trace id and a value **at** 128 characters are all accepted, so the
bound is a bound and not a ban. **M85c is the falsifier.**

Deliberately **not trimmed first**, unlike `correlation-id.ts` — that module is normalising an
inbound header before re-broadcasting it; here the value is already a body field, and a surrounding
space is a sign the id is not what it claims to be, so falling back is more honest than repairing it.

### ⚠️ POSITIVE identity assertions — and why the shape is worse here than for `dependency`

`140.3-11` recorded the asymmetry for the next plan and it applies with extra force: for

`ErrorEnvelope.correlation_id` was already REQUIRED, the `<code className="font-metric tabular-nums">`
