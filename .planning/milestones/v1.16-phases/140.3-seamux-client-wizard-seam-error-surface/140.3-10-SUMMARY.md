### 🔴 FINDING-D — **neither of the plan's two 404-arm shapes could be applied as worded.** Recorded, not smuggled.

The plan requires the 404 arm's code to not present a destructive control as its only way forward, via

2. **`GATE_DRAFT_GONE` no longer renders a destructive control at all** at `SyncPreviewStep` — see

So changing `GATE_DRAFT_GONE.actions` would have altered a boolean and shipped zero user-visible
change, while both real paths to deletion stayed open.

## Task 1 — `11000b38` · the C-8 unit, indivisible

### (a) The transport split, first

`.maybeSingle()`, `strategyErr` → **500 `DRAFT_LOOKUP_FAILED`** with `scrubSeamError` on the log line,
then `!strategy` → **404 `GATE_DRAFT_GONE`**. Shape copied from `finalize-wizard`.

**P458 survives, and is pinned rather than asserted.** The anti-regression case compares the two
responses' **full body text** *and* their **sorted header-key sets** — a `Retry-After` or a differing
cache directive on one and not the other is an enumeration oracle exactly as usable as a body
difference.

The scrub pin is a two-sided assertion, not one: the log must **not** contain the service-role key
value, **and must still** contain `ECONNREFUSED`. A scrub that ate the syscall token would pass the
first assertion while leaving the operator an unusable line — the A-10 defect the preserve list exists
for.

### (b) A code on every arm

The eight arms and their codes are in FINDING-A. **Five separate per-arm cases, written out, not
parameterised** — the plan is right that a loop certifies arms it never exercises.

**Arms 3 and 4 needed a harness change to be independently reachable at all.** The suite's shared
`rateLimitResult` denies *every* bucket, so the per-user ceiling always short-circuits and the
per-strategy site was **structurally untestable**. A per-bucket override was added (absent override ⇒
byte-identical prior behaviour), and the two cases drive **different buckets with different waits**
(42 vs 9) plus a `checkLimitMock` call-count assertion — so neither case can be satisfied by the other
site answering.

### (c) The confirmation

`handleStartFresh` now opens the same `confirmDelete` dialog the chrome's Delete-draft button uses.

**One consequence had to be handled or the fix would have been a regression.** The old handler ran
`setShowResumeBanner(false)` **up front**, before the delete. Keeping that with a confirmation would
strand a user who cancels: the draft still exists and "Resume draft" would be gone. The banner is now
dismissed inside `handleDeleteDraft`'s three **confirmed-delete** branches instead, so its lifetime
tracks the draft's. Pinned by the cancel case.

**The intentional delete paths are intact.** `onTryAnotherKey`'s fire-and-forget `void
handleDeleteDraft()` (which regenerates the idempotency token first, per its own comment) and the
dialog's own danger button are untouched, and both the pre-existing `[94-03]` case and a new
anti-regression case pin that they still delete with no dialog interposed.
