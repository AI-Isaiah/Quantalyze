<objective>
Stop a failed recompute from leaving the previous result on screen as if it were current — **at every
live member of the class**.

Purpose: requirement `SEAMUX-09` (ROADMAP SC7). This is the phase's CRITICAL, money-bearing item.

`PortfolioOptimizer.tsx` sets `error` on a failed re-run but **never clears `suggestions`**. The error
card is gated on `computationStatus === "failed" && !suggestions` — and `computationStatus` is a
**server-rendered prop**, unchanged by a client-side re-run failure, so the card is unreachable twice
over. Execution falls through to the SUCCESS branch, which renders `suggestions.slice(0, 5)` as
`SuggestionRow`s with live, clickable "Add to portfolio" links, under one small red line.

## ⚠️ THE CLASS HAS ≥ 2 LIVE MEMBERS, NOT 1 (correction C-5)

The findings doc and PATTERNS both concluded "a class of ONE". **They enumerated by a syntax-shaped
candidate scan.** Enumerated by BEHAVIOUR — *"can this component render a fetched result while an
error is set?"* — there is a second live member:

**`src/components/connect/KeyPermissionBadge.tsx`.** Its `load` calls `setError(null)` and
`setPerms(data)` but **never `setPerms(null)`**, and `{loading && !perms && …}` / `{!loading && error
&& …}` / `{perms && …}` are **independent siblings** — no guard-order exclusivity. So "Re-check"
during a breaker trip renders the **previous Read / Trade / Withdraw verdict beside the error**. That
is a stale **security** claim about a money-bearing key, and it is arguably worse than the stale
allocation because the user reads it as a current fact about their key's scope.

**`ReplacementPanel.tsx` is a structural third member that is unreachable today** — its only refetch
trigger is a `[portfolioId, strategyId]` dep change, and its sole parent mounts it under `{open && …}`
from a single insight, so the props cannot change while mounted. **Pin it negatively. Do not "fix" it
into reachability.** Its real, live defects are different ones (B-27 member 3, and B-28) and this
plan closes those. ⚠️ **B-27 itself is a class of THREE** — see the table in Task 3; the other two
members are `PortfolioOptimizer` and `KeyPermissionBadge`, both fixed in Tasks 1 and 2.

## ⚠️ ONE pattern for the whole class

Three correct patterns exist in-tree (`setResult(null)` before refetch; guard-order exclusivity; a
discriminated `FetchState` union). CONTEXT **locks** the first. Apply the locked one to both live
members even where a guard-order fix would be smaller — *"3 of 5 log sites"* is this programme's
signature failure, and mixing patterns is how a reviewer loses track of a class.
