## Task 1 — TS-19, and the correction to B-12

### 🔴 FINDING-A — the flattening is broader than B-12 states, and it is not the shape B-12 implies

B-12 reads *"admin/match currently flattens all upstream 4xx to a generic 500"*, which describes a
mapping that exists and is wrong. There was **no mapping**. `grep -c "AnalyticsUpstreamError"` was
**0** in both route files: only `CircuitOpenError` (→ 503 + `Retry-After`) and
`AnalyticsTimeoutError` (→ 504) were branched, and the terminal arm was unconditional. So **every**
other upstream status — 4xx *and* 5xx — became `500 {"error":"Match recompute failed. Please try
again."}`.

**It was the common case, not a corner.** `analytics-service/routers/match.py` raises on these very
endpoints:

| Status | Site | What an admin saw before |
|---|---|---|
| 403 | `match.py:1668` | "Match recompute failed. Please try again." |
| 422 | `match.py:1697` | same |
| 429 | `match.py:1741` | same |
| 400 | `match.py:1783` | same |

Each is a deliberate, immediate refusal by the service, reported as our 500 with an invitation to
retry something that would be refused identically every time.

### The 4xx/5xx range split is a DECISION, and it defends a threat this file already closed

The plan says "forward the upstream status and the envelope". Forwarding **all** statuses would have
re-opened **T-140-11** at the two routes whose own docblock exists to close it:

> *"Until Phase 140 the generic arm echoed `err.message`, which on this seam carries Python
> contract-drift strings (the multi-line Zod issue list `parseResponse()` throws), FastAPI 5xx
> `detail`, and the analytics service's base URL."*

`AnalyticsUpstreamError.message` on a 5xx is exactly those things — it is `res.text()` of a
`text/plain` FastAPI unhandled exception, or `seamHumanMessage` of a 5xx envelope. A 4xx `detail` is
operator-curated copy. So the arm mirrors **`src/app/api/simulator/route.ts:201`**, the in-repo
template with tested precedent (its TC7/TC8 cases pin the same split), rather than inventing a fourth
shape. Anti-regression cases in **both** route test files re-pin the 5xx absence *through the new
arm*, so widening the range later reddens a test instead of shipping a leak.

**No header rides along.** `AnalyticsUpstreamError` carries none, so a forwarded upstream 429 reaches
the client **without** its `Retry-After`. Recorded rather than invented: naming a wait no upstream
stated is TRAP-3, and it is the rule `140.3-08` and `140.3-09` both applied. If that wait is wanted,
it is a `Retry-After`-on-the-error-type change and belongs with SEAMUX-06's plumbing.

### Proven against REAL WIRE BYTES, not only a double

The success criteria require TS-19 be established and proven *first*, and against real bytes. Both
route test files are mock-based — they replace `@/lib/analytics-client` and can therefore prove only
the route's mapping of a class to a status. `recompute/route.seam.test.ts` runs the **REAL** client
and the **REAL** resilience core with only `fetch` faked, and two cases were added there:

- a real `424` carrying the nested `service_error` envelope leaves the route as **424** with its
  sentence intact, and `fetch` **was** called (so it is a forward, not a short-circuit dressed as one);
- a real `502 text/plain` still leaves the route as the static **500**, with no `Traceback` and no
  base URL in the body.

TS-19 was committed GREEN (`7323c388`) with the full suite run **before** the commit, and only then
did any TS-18 work begin.

## Task 2 — TS-18

### The contract premise, verified at source rather than assumed

Read first-hand at `analytics-service/services/error_contract.py`, the `status_code == 424` arm
(2026-07-27, READ ONLY — this plan modified zero Python):

- a 424 **must** name a non-empty `dependency`;
- that name **may not** be a member of `SERVICE_DEPENDENCIES` — *"a 424 names the caller's venue, and
  a fault in our own dependency is 500/503"*;
- a 424 **must** be `retryable` — *"marking it non-retryable produces the B-01/B-22 dead-end render"*.

The two vocabularies therefore cannot collide on the emit side, and the venue name is safe to
display. The premise holds; no STOP was owed.

### 🔴 FINDING-B — `dependency` never survived the seam. `AnalyticsUpstreamError` carried three fields, and none of them was it

Read before writing, exactly as the plan instructed. What it carried:

| Field | Source |
|---|---|
| `message` | `seamHumanMessage(body) ?? "Analytics service error"`, or `res.text()` for a non-JSON body |
| `status` | `res.status`, range-guarded at construction (H-1144) |
| `seamCode` | `seamErrorCode(body)` — added by `140.3-01` |

**The body is discarded at that line.** Route handlers see only the thrown error, so `dependency` was
structurally unreachable to every consumer, in **both** 424 shapes — not only the flat one.

**This is not the "STOP and report" case the plan describes.** That instruction forbids *"a second
error type to work around it"*. What was done is the opposite: the SAME error type gained a fourth
**additive-optional readonly** field on exactly the contract `140.3-01` set for `seamCode` one plan
earlier, documented in-file as such. Every pre-existing construction site passes two or three
arguments and keeps `null`; zero call sites changed; zero behaviour changed anywhere else.

The rejected alternative is worth naming: `message` frequently *contains* the venue in prose
("Binance is not responding…"), and sniffing it back out would have been the substring cascade that
**correction C-6** caught rendering a venue WAF block as the user's own IP-allowlist problem.

### 🔑 The `dependency` reachability decision — the sentence `140.3-15` must read

`nestedDetail` in `src/lib/seam-discriminator.ts` is unexported by design, and its comment explains
why: everything exported from that leaf is browser-reachable and survives every wholesale seam mock,
so each member is a privilege.

**Decision: the leaf gained ONE narrow, purpose-named extractor, `seamDependencyName(body)`, built on
the same private `nestedDetail`.** `EXPECTED_EXPORTS` in `seam-discriminator.purity.test.ts` went
**3 → 4** in the SAME commit (`16244027`) — the hard gate, and the purity test is green.

Rejected, with reasons, so the next plan does not re-litigate:

| Rejected | Why |
|---|---|
| export `nestedDetail` itself | hands every consumer the whole envelope and makes the next hand-rolled `body.detail` branch a one-liner — the class `140.3-01` closed |
| a generic `seamDetailField(body, name)` getter | an export set that cannot say WHICH fields are reachable guards nothing, and set-equality is the only thing that file is for |
| reuse the private `serviceDependencyOf` | it answers the OPPOSITE question — it admits only OUR closed set because its output may become a breaker key (T-140-01). Collapsing the two would let a venue slug reach a key |

> ### ➡️ **`140.3-15` MUST add `seamCorrelationId` as a FIFTH narrow member on the same private
> `nestedDetail`, not a private reader of its own and not a widening of `seamDependencyName`.**
> Mirror `seamErrorCode`'s both-shape read, because `correlation_id` is at the TOP level on the
> app-global flat envelopes and nested on `service_error`. This is written in the purity test's own
> docblock as well as here, so it is found by whoever opens the file next.

### Safety: a shape guard, and a second refusal of our own vocabulary

`seamDependencyName` is not a bare read. Two guards, both because the value reaches a human as an
**attribution**:

1. **Slug shape, bounded** — `^[a-z0-9][a-z0-9._-]{0,39}$`, anchored at both ends. The value arrives
   over the wire and is rendered verbatim into an admin's screen; the case list pins rejection of
   markup, whitespace, a newline (a log/header-injection shape), uppercase, an empty string and a
   41-character value, and pins **acceptance** at 40 so the bound is a bound and not a ban.
   ⚠️ **It is a SHAPE guard, never a venue allow-list.** An allow-list would need every exchange
   added twice, and its failure mode is that a real outage renders as **no outage**.
2. **Every member of `SERVICE_DEPENDENCIES` is refused** — defence in depth over `_validate`, which
   already refuses them on emit. A body naming `supabase` here would tell an admin the caller's
   exchange broke when OUR datastore did: theme 2 in reverse, and the single lie SEAMUX-04 exists to
   make impossible. It degrades to the un-named state, which is truthful.

It does **not** warn on an unrecognised name (pinned by a case). `serviceDependencyOf` warns loudly
because there the value was supposed to be one of four; here the vocabulary is open, so a name we
have not seen is the normal case and a warning would fire on every venue we ever add.

### The 424 copy, verbatim

One production source, `src/components/admin/match/venueOutageCopy.ts`, imported by both consumers:

> **`Binance isn't responding right now. The fault is at the venue, not in the analytics service. Retry in a moment.`**

and when the wire named no venue:

> **`An exchange isn't responding right now. The fault is at the venue, not in the analytics service. Retry in a moment.`**

Against **DESIGN.md §Voice**: declarative ✓, sentence-case ✓, active ✓, no exclamation ✓, no banned
glyph ✓, no adjective where a number exists ✓. **No wait is named**, deliberately — neither route
forwards a `Retry-After`, so a duration would be the invented number TRAP-3 is about. It does not say
our service is degraded; it says the opposite, which is precisely what a 424 asserts.

The only transformation applied to the wire value is **capitalising one character**, so a sentence
does not open lowercase. Documented in-file as presentation-only, explicitly not a slug→display-name
lookup table (that would be the venue list this surface may not have).

### ⚠️ The `null` branch is the one that actually fires

`140.3-06`'s hand-off is right and it is load-bearing: the **flat** `VenueTransientHTTPException`
424 — the shape it actually put on the wire — carries **no `dependency` key at all**. Only the
nested `service_error(424, dependency=…)` form names a venue. So the un-named degrade is the common
path, and it is pinned at both consumers with an explicit assertion that **no literal `undefined` and
no literal `null` reaches the DOM**, plus a real-wire case proving the flat shape yields no venue
while still delivering its sentence.

**Reconciling the routed constraint.** The hand-off says the venue *"must come from wizard state, not
the response body"*. That is right for the wizard, and the wizard is out of scope here (see below).
The admin match surface has no wizard state and no venue of its own, so the nested envelope's
`dependency` is the only possible source — and it is contract-guaranteed to be a venue. Both are
honoured: the nested shape names the venue, the flat shape names none, and nothing is invented.

### Verified, not re-implemented: the wizard has no second 424 path

`grep -rn "424"` across `src/app/(dashboard)/strategies/new/wizard/` and `src/lib/wizardErrors.ts` →
**0**. `140.3-05`'s `body.code` branch routes `EXCHANGE_UNAVAILABLE` → `KEY_EXCHANGE_UNAVAILABLE` and
`DDOS_PROTECTION` → `KEY_VENUE_TRANSIENT` (`wizardErrors.ts:1148`), so the wizard-side venue-transient
render already exists and this plan created no rival. **`src/lib/wizardErrors.ts` was not opened, and
its marker count is UNCHANGED at 5** — `140.3-12`'s `toBe(5)` reconciliation is unaffected.

### 🔴 FINDING-C — the 424 renders through the EXISTING error card, not `ErrorEnvelope`. Stated because it deviates from the plan

The plan instructs: *"use the canonical `ErrorEnvelope` renderer rather than a bespoke card — that is
a DESIGN.md hard rule with a PR-time grep block."* Both options were read at source and both break
something:

- **`ErrorEnvelope` via `buildEnvelope`** requires a `WizardErrorCode`. Every member of that union is
  a key-connect or sync state; an admin match recompute has none. Adding one would put admin copy in
  the wizard copy table, open a file `140.3-08` deliberately left shut, and change the marker count
  `140.3-12` reconciles with `toBe(5)`.
- **`ErrorEnvelope` with a hand-built envelope literal** is, by DESIGN.md's own words in the same
  paragraph, *"an inline-string error envelope"* — the thing the authoring rule forbids. It would also
  need a `correlation_id` neither route forwards today.
- **Migrating both cards wholesale** is an architectural change (Rule 4) that would overwrite the
  error-first surface `140.3-08` built one wave ago — the "prescribed fix that would delete a surface
  another plan just built" case, which `-07`, `-08`, `-09` and `-10` each caught once.

**Picked: render through the existing error-first card**, which already supplies the shell and the
Retry control, so all three of TS-18's required properties hold (named / recoverable / not ours) and
every mechanical acceptance criterion is met — none of them greps for `ErrorEnvelope`.

**The DESIGN.md tension is UNCHANGED, not resolved**, and is restated verbatim from `140.3-08`'s
Known Stubs so it is not read as fixed: these components rendered inline error strings before this
plan and still do. This plan **narrowed** what those paths can render; it did not migrate them. The
migration is a real, separate piece of work and belongs to whoever owns the admin error surface.
