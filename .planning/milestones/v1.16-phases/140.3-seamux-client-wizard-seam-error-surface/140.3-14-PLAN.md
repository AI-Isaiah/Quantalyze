## TS-37 — a permanent condition rendered with transient copy, and only ONE of four arms is it

`COMPOSITE_MEMBERSHIP_UNKNOWN` is emitted at **four** sites in this file. **Only the
composite-member-cap arm is the permanent one**; the other three are genuine transient member-list
read failures and **must keep the code and the retry**. Fixing "the composite membership arms" as a
group would strip a correct retry from three real transient failures — the inverse of the defect.

The cap arm returns `503 { code: "COMPOSITE_MEMBERSHIP_UNKNOWN", error: "Could not load composite
members; please retry." }` — **byte-identical to the transient arm.** For an overflowing composite the
condition never clears, so the user gets a retry affordance that can only ever fail, with no
explanation and no path forward. The route's own in-file note hands the work over explicitly:
*"140.3 owns giving this arm its own code and copy; the retry affordance the shared envelope renders
is wrong for a permanent condition."*

The **operator** half is already distinct (`composite member list EXCEEDED the` in the log,
`step: "composite-member-cap"` in Sentry) — only the user half is missing.

⚠️ **A new finalize code is INVISIBLE unless `SubmitStep.tsx`'s `KNOWN_FINALIZE_CODES` gains it in the
SAME commit.** That set is the choke point every finalize code passes through; a code added to the
route alone falls straight through to `UNKNOWN` and the user sees the generic dead end instead of the
new copy. This is the single most likely way this obligation ships broken.

## TS-33 — ONE field, and its ordering constraint is already satisfied

`process_key.py` gates `idempotent_by_session` on a caller-supplied `wizard_session_id`. **The
mechanism exists and is unreachable from onboard/resync** because `finalize-wizard` sends no id.

⚠️ **TS-33 is NARROWER than its row states (correction C-7 / F-2).** The row's *"no caller sent
`wizard_session_id`"* is **false as a general statement** — `csv-validate` and `csv-finalize` both
send it inside the `postProcessKey` `context`, and Python reads it from exactly there, so
`idempotent_by_session` is **TRUE on the CSV path today**. The true scope is **one call site**:
`finalize-wizard`. A planner or executor who believes the mechanism is dead will not check the CSV
path when adding the field — and the CSV path is the working reference for how the field is shaped.

**Ordering:** strictly after TS-01, which is DONE-IN-140.1.1. The widened predicate is in place, so
the field is safe to add. Adding it before that would have converted H-5 from latent into a live
**502 + Sentry on every duplicate resume**.

**Scope fence, restated so it is not re-litigated: ONE field, not a new idempotency subsystem.**
Porting `Idempotency-Key` from `allocator/scenario/commit/route.ts` was **REJECTED** — it needs a
migration, and migrations auto-apply to PROD with no branch protection. Building a second mechanism
before wiring the first is the point-fix-a-class antipattern.

⚠️ **TS-33 must be scheduled in 140.3's own pass and NOT retrofitted into `140.3-02`.** This is that
pass. `140.3-02` has already run.
