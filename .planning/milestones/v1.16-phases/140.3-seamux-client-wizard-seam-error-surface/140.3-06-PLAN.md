## The blocker was mis-named, and the real one has landed

TS-32's row says `BLOCKED-BY: TS-05`. **That names the wrong row** (correction C-4, verified
first-hand). `VenueTransientHTTPException`'s guard admits any `400 ≤ status < 500`, and the single
`@app.exception_handler` in `main.py` serialises `{detail, code, recoverable}` **independent of
status** — so the remap is **body-neutral** and `"[object Object]"` is structurally impossible. TS-05
was never a prerequisite.

The real blocker is stated in the class's own docstring: *"changing the status alone buys nothing,
because the status is discarded"* — `classifyKeyValidationError` derived both the wizard code and the
returned status from the message string. **The row that fixes that is TS-35, and it landed in
`140.3-05`.** This plan is therefore unblocked and must not run before it.

## ⚠️ THE COUPLING NO SOURCE DOCUMENT NAMED — the sequencing trap of the phase

Three artifacts pin `400` and **all three redden on the remap**:

1. `analytics-service/tests/test_validate_key_venue_transient.py` → `EXPECTED_STATUS = 400`, asserted
   in **four** places, **with an argued failure message** that reasons *for* 400: *"status must stay
   400 — the TS classifier derives BOTH the wizard code and the returned status from the message
   string…"* **That rationale EXPIRED when TS-35 landed. Rewrite the argument, do not just flip the
   literal.** A message that still argues the old case beside a new number is how the branch grows
   back.
2. `analytics-service/tests/fixtures/validate_key_venue_transient_contract.json` → `"status": 400` in
   **all 14 cases**, plus an `invariants[]` entry asserting 400 at all seven sites.
3. `140.3-05`'s TypeScript parity test binds to those same bytes — **which is why that plan was
   required to read `status` FROM the fixture rather than pin it.** Verify that property first-hand
   before you flip anything (Task 1's first step). If the parity test contains a hard-coded `400`,
   **STOP and report**: `140.3-05` did not deliver its half of the split and flipping the fixture now
   would redden a test for the right reason at the wrong time.

⚠️ **TRAP-9 applies and is binding, in the direction that is easy to get wrong here.** The Python
wire tests are the regression fence for a genuine caller-fault contract. Their status expectations
changing IS the change — **do not "relax" them**, and do not delete any case. Update the expectation
and its argument; keep every case.
