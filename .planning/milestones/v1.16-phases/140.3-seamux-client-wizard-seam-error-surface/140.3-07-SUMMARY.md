# Phase 140.3 Plan 07: Stop a failed recompute from leaving stale money data on screen — Summary

**One-liner:** Both live members of the stale-result class now discard the invalidated result *before*
the refetch using one locked pattern, the client-side error state is reachable at the member where a
server-rendered prop made it unreachable, and no raw caught `Error.message` renders at any of the three
sites that did it — without swallowing the breaker sentence those routes legitimately send.

---

## Task 1 — live member 1: `PortfolioOptimizer`

### Two independent faults, both closed

1. **The invalidated result was never discarded.** `runOptimizer`'s catch set `error` but left
   `suggestions` intact, so execution fell through to the **success branch** and re-rendered the
   previous ranking with live, clickable "Add to portfolio" links under one small red line.
2. **The error card was unreachable.** It was gated on `computationStatus === "failed" && !suggestions`
   — and `computationStatus` is a **server-rendered prop** that a client-side re-run failure never
   updates. Even with `suggestions` correctly cleared, the user would have landed on the *"never run"*
   empty state saying **"Run the optimizer to see strategies…"** — a false statement about what had just
   happened. **M72b confirmed this empirically**, not by reading the code.

The fix applies the **locked** house shape — `setSuggestions(null)` at the top of the function
(line 211), **before** the fetch (line 213) — copied from `WeightOptimizerSection.tsx`'s
`requestWeights` and matching `admin/partner-import/page.tsx`. The render guard gains an `error`
disjunct; **the server conjunct is left byte-intact** so that path keeps working (TRAP-9), pinned by its
own anti-regression case.

### The guard shape was a real decision

`error || (computationStatus === "failed" && !suggestions)` was chosen over
`(error || computationStatus === "failed") && !suggestions`. The rejected form re-opens the hazard the
moment the invalidation regresses, and it misses the one path where `error` can coexist with a
**non-stale** result: `router.refresh()` throwing *after* a successful `setSuggestions`. The chosen form
returns the error card in every case.

### Three now-unreachable inline `{error && …}` paragraphs were removed

With the failed branch returning on any error, the inline error blocks in the empty state, the
empty-after-compute state and the success branch can no longer render. They were deleted rather than
left: **a second error surface that cannot render is how a reviewer loses track of which sites were
closed.** No affordance is lost — the failed card carries the same message plus a Retry control, where
those states offered only a Run/Re-run button. No test covered them.

### 🔴 The B-27 fix at this site was NOT what the plan described, and the difference is load-bearing

The plan says *"Replace the rendered string with a stable sentence."* Measured against the route, that
would have been a **regression**:

```
src/app/api/portfolio-optimizer/route.ts:185
  { status: "failed", suggestions: null, error: CIRCUIT_OPEN_COPY }
```

The route answers a breaker trip with the **single-source breaker sentence** that `140.3-04` spent a
whole plan consolidating precisely so it reaches users. A component that replaced every caught message
with its own fallback would have **deleted the breaker surface at a seam consumer while appearing to fix
B-27** — undoing plan 04 silently. The same route also documents (M-0333) that it deliberately never
puts `err.message` in its body, so its `error` field is already scrubbed, reviewed copy.

So the fix is **not "render less", it is "render only what a route wrote"** — see the deviation below.
A dedicated test pins the non-over-firing direction: *"renders the route's breaker sentence rather than
swallowing it (B-27 must not over-fire)"*, asserted against a **hand-typed** literal, never imported
from `seam-copy.ts` (lesson C-1).

### 🔴 FINDING-A — the plan's "in-flight window" case is PRE-SATISFIED, and its stated rationale is wrong for this component

The plan asks for a case proving *"after the re-run starts and before it resolves, the stale ranking is
already gone"*, and justifies invalidating at the top rather than in the catch because *"doing it in the
catch leaves the stale list rendered for the whole in-flight window."*

**Measured, that is false here.** `runOptimizer` calls `setLoading(true)` first, and the `loading`
branch returns the shimmer **before any success branch**, so no ranking rendered during the in-flight
window even on the untouched tree. The case is written and kept — a future edit that reorders the
loading branch below the success branch would re-open that half — but it is **labelled a PIN in the test
body and counted as no part of this plan's evidence.** The real reasons to invalidate at the top are
uniformity with the locked pattern and the `router.refresh()` throw path, and those are what the code
comment says.

## Task 2 — live member 2: `KeyPermissionBadge`

**ONE pattern, deliberately.** `setPerms(null)` at the top of `load` (line 97), before the fetch (line
99) — byte-for-byte the same idiom as member 1's `setSuggestions(null)` (line 211, before its fetch at
213), both descended from `WeightOptimizerSection.tsx`'s `setResult(null)`.

> **The identical idiom at both live members, in one sentence, as the plan asked:** each component
> discards its own fetched-result state by calling its setter with `null` as the first statement after
> `setError(null)` at the top of its refetch function, before the request is issued — `setSuggestions(null)`
> at `PortfolioOptimizer.tsx:211` and `setPerms(null)` at `KeyPermissionBadge.tsx:97`.

A **guard-order fix would have worked here and been smaller** — the three render blocks are independent
siblings, so reordering them into exclusivity would also have hidden the chips. It was not used: a class
fixed two different ways is a class a reviewer cannot audit, and *"3 of 5 log sites"* is this
programme's signature failure.

The `mountedRef` unmount guard is intact (non-comment count holds at its pre-task **6**). The
invalidation is a **synchronous set before any await**, so it needs no guard of its own and cannot
introduce a set-after-unmount — pinned by an anti-regression case that unmounts mid-flight and asserts
no React warning.

### B-27 here preserved three existing tests rather than breaking them

Three existing cases assert that this component renders the route's `{ error, code }` body —
`PROBE_BACKEND_UNAVAILABLE: …`, `HTTP 504 (Gateway Timeout)`. That copy is **deliberate, greppable
support-ticket text**, not a raw caught value. The discriminator preserved all three: the two throws
built from the response are `RouteResponseError`, so they still render. Only genuinely raw values —
a rejected fetch, a `SyntaxError` from a proxy's HTML page — are replaced.

### Agreement with `140.3-03`

That plan made `keys/[id]/permissions` fail **CLOSED** on an unreadable 2xx (502 `PROBE_FAILED`, never
cached). This component is that route's **only** consumer, so a dedicated case drives the route's real
fail-closed shape and asserts no verdict survives it. **A fail-closed route in front of a component that
keeps showing the old verdict closes nothing** — the two halves had to be checked together.

## Task 3 — `ReplacementPanel`: B-28, B-27 member 3, and the negative pin

### B-28 — the array guard

`setCandidates(data.candidates ?? [])` turned every malformed body into an **empty-but-successful**
panel, and the empty branch says *"No replacement candidates found that would improve this portfolio"* —
**a claim about the USER'S PORTFOLIO made on the strength of our own failed parse.** That is the second
half of SEAMUX-09's own wording. `?? []` also admitted a non-array truthy value straight into `.map()`.

The guard copies `OutcomesWidget`'s in-tree shape (`!Array.isArray(data?.original)`) rather than
inventing one. Five malformed shapes are covered (absent, `null`, object, string, non-object body), plus
an anti-regression case proving a **genuine `[]` is still the empty state**, plus a case proving the
parse failure is logged.

### ⚠️ B-27 was a class of THREE, and two existing tests asserted the defect

The identical `setError(err instanceof Error ? err.message : …)` shape sat at **all three** components
this plan touches — each reading `1` on the untouched tree, **all three now `0`**. No site was left, so
no waiver is claimed.

**Two existing `ReplacementPanel` tests pinned the defect** and were changed deliberately, stated here
rather than buried: both drove `throw new Error("network down")` and asserted that raw message reached
the DOM. Their intent survives and is strengthened —

- *"renders an error message when the fetch rejects"* → now *"renders the stable sentence — not the raw
  caught message — when the fetch rejects"*, and it additionally asserts the raw message **and its
  embedded host** do not reach the DOM.
- The M-0905 breadcrumb case keeps its console assertions **untouched**; only its `waitFor` anchor moved.
  That case is now what proves debuggability was not traded for the copy fix.

The caught value still reaches `console` at all three sites (verified by reading, not by grep).

### The negative pin — the latent member stays latent

`ReplacementPanel` **structurally qualifies** for the class: fetched result and error in independent
state, independent sibling render blocks — exactly `KeyPermissionBadge`'s shape. It is unreachable only
because of two facts, and the pin asserts **both**:

1. its only refetch trigger is a single mount-effect keyed `[portfolioId, strategyId]`; and
2. its **sole** parent, `BridgeTrigger.tsx`, mounts it under `{open && …}` from one insight, so those
   props cannot change while it is mounted.

The parent enumeration scans **all of `src/`**, not just the known parent — a pin that checked only
`BridgeTrigger.tsx` could not detect a second parent being added, which is the mutation it exists to
catch. A behavioural half asserts a re-render with unchanged props does not refetch.

**It was deliberately NOT fixed.** Adding an invalidation would convert a pinned-latent member into a
live one with no way to exercise the new code, and an untested path is worse than a structurally
unreachable one. If the pin ever reddens, that is the moment to apply the locked shape.

## Deviations from Plan

### 1. [Rule 2 — the plan's prescribed B-27 fix would have caused a regression] `src/lib/route-response-error.ts` is a new file outside `files_modified`

The plan says to replace the rendered string with a stable sentence at each of the three sites. Measured
against `src/app/api/portfolio-optimizer/route.ts:185`, that would have **swallowed `CIRCUIT_OPEN_COPY`**
— deleting the breaker surface `140.3-04` consolidated, at a seam consumer, while every acceptance grep
still read 0. The fix therefore discriminates **route-authored copy** (rendered) from **raw caught
values** (replaced, logged).

That discrimination needs one shared marker. Declaring it locally in three files would have been the
duplication drift class this programme exists to close, so it lives in **one** module with its own test
pinning the predicate (a plain `Error`, `TypeError` and `SyntaxError` must all fail `instanceof`). This
