- **Verdict:** CONFIRMED · **Category:** correctness

**What:** The new distinct-request denominator dedupes on `metadata.correlation_id`, which is the inbound client-supplied `X-Correlation-Id` header, so an unauthenticated caller can collapse the denominator and silence (or falsely fire) the error-rate alert. [same root cause also at: src/app/api/cron/flag-monitor/route.ts:236, src/app/api/cron/flag-monitor/route.ts:234]

**Failure scenario:**

Inputs: anonymous traffic submits 200 teaser verifications inside one 15-minute window, every request carrying `X-Correlation-Id: aaaa`. State: `audit_log` holds 200 `entity_type='process_key'` rows all sharing one correlation_id, plus, say, 5 genuine onboard requests. Wrong outcome: `getDenominator` returns 6 instead of 205. `total = 6 < MIN_SAMPLE (20)`, so `handle()` skips BOTH the `errorRate > ALERT_THRESHOLD` and the `errorRate > WARN_THRESHOLD` branches (route.ts:380, 390) and answers `{ok:true}` — the founder is never paged no matter how high the real error rate is. In the other direction, if the collapse leaves `total` at 25 while Sentry reports 1 error, `errorRate` computes to 4% and a false `[ALERT]` email is sent claiming "1/25". The replaced `.select("id", {count:"exact", head:true})` counted rows and could not be influenced from the wire at all; this is a monitoring-integrity regression introduced by D-16, and it re-opens the exact "monitor goes silent with no signal" class D-16 was written to close.

- **Verdict:** CONFIRMED · **Category:** correctness

**What:** The new denominator dedups on `metadata->>correlation_id`, but the analytics service re-mints a fresh uuid4 whenever the inbound `X-Correlation-Id` is not a bare UUID — which is true for 100% of retry-eligible traffic, so the dedup collapses nothing on exactly the population it was written for. [same root cause also at: src/app/api/cron/flag-monitor/route.ts:204]

**Failure scenario:**

`wizardFetch` (src/lib/wizard/wizard-correlation.ts) stamps `X-Correlation-Id: wizard:<uuid-v4>` on every wizard request, including SubmitStep.tsx → /api/strategies/finalize-wizard (flow_type=onboard) and SyncPreviewStep.tsx → /api/keys/sync (flow_type=resync) — the ONLY two flows in RETRY_SAFE_FLOW_TYPES. `getCorrelationId()` (src/lib/correlation-id.ts) accepts that value verbatim (its allowlist explicitly permits the colon) and `postProcessKey` forwards it unchanged on both attempts. In analytics-service/routers/process_key.py the handler does `correlation_id = str(uuid.UUID(str(_raw_cid)))` and falls back to `str(uuid.uuid4())` on ValueError — `wizard:abc…` is not a UUID, so each of the two HTTP attempts derives a DIFFERENT server-minted uuid4, and `_write_audit_sync` writes that server value into `metadata.correlation_id`. Concrete run: during a Railway blip, 200 wizard onboard finalizes each retry once and each fails; audit_log holds 400 rows with 400 distinct correlation_ids; getDenominator returns 400 rather than the intended 200; errorRate = errors/400 is exactly half the true per-request rate, so a real 0.6% incident computes as 0.3% and stays under ALERT_THRESHOLD — the founder is not paged during precisely the retry-heavy degradation this repair was written to stop hiding. ## Finding 5

- **Location:** `src/lib/resilient-fetch.ts:2099`
- **Verdict:** CONFIRMED · **Category:** correctness

**What:** `admittedAtMs` is captured once before the retry loop, so attempt 2's failure is judged by the A-25 guard as pre-dating a lock armed after admission, and the retried wave can never re-arm the breaker on the 30s `optimize-weights` budget.

**Failure scenario:**

`optimize-weights` is `timeoutMs: 30_000, retries: 1` and `BREAKER_COOLDOWN_S` is 30, so the attempt-1 deadline exactly equals the cooldown and the retry backoff (250-500 ms) pushes the re-check past lock expiry. Sequence, with Railway hard-down: a wave of Scenario Composer requests is admitted at t=0 past a closed circuit (`admittedAtMs = 0`); a concurrent caller's failures arm the global lock at t=0.2s (`armedAtMs=200`, `expiresAtMs=30200`). Each request's attempt 1 times out at t=30.0s; `recordSeamFailure` reaches the trip path, sees `existing.expiresAtMs (30200) > now (30000)` and returns without writing. The loop sleeps 250-500 ms and re-checks at t=30.4s, where the lock has just expired, so `isBreakerOpen` reports CLOSED and attempt 2 fires a fresh 30s request at the still-dead upstream. Attempt 2 times out at t=60.4s and calls `recordOnce`, which passes the ORIGINAL `admittedAtMs = 0`; the A-25 guard `if (admittedAtMs <= existing.armedAtMs) return;` is true (0 <= 200) so the trip path returns WITHOUT arming, even though attempt 2 was admitted at t=30.4s — 30s AFTER that lock was armed — and its failure is genuinely new evidence. Every request in the wave is suppressed identically. Result: `/api/scenario/optimize` keeps issuing full 60s+ double attempts against a dead upstream instead of short-circuiting, and allocators wait 60s per click for a 502/504 rather than receiving an immediate CIRCUIT_OPEN 503 with Retry-After.

- **Verdict:** PLAUSIBLE · **Category:** correctness

**What:** A retried onboard/resync consumes TWO tokens of the platform-wide `500/hour` /process-key ceiling that all flows share, and 429 is classified non-counting so the breaker cannot contain the amplification — draining the ceiling refuses the anonymous public teaser and CSV flows that never retry. [same root cause also at: src/lib/seam-retry-registry.ts:349]

**Failure scenario:**

`resilientFetch` re-issues the whole HTTP request on attempt 2, and the Python side stacks TWO slowapi limiters on `/process-key` (analytics-service/routers/process_key.py:820-821): a per-identity window (`_PROCESS_KEY_TENANT_LIMIT = "100/hour"`, `_PROCESS_KEY_ANON_LIMIT = "30/hour"`) and `_PROCESS_KEY_CEILING_LIMIT = "500/hour"` keyed on the credential hash — which, post-PYAPI-04, is ONE platform-wide bucket because every admitted caller presents the same `INTERNAL_API_TOKEN`. Each retried attempt spends one token of BOTH. The breaker cannot see this: `seamBreakerVerdict` classifies 429 as `counts: false` (stated at resilient-fetch.ts:2337), so a 429 storm neither records a failure nor trips the circuit. The D-03 cost note in seam-retry-registry.ts records the doubled concurrent COMPUTE but nothing in this phase records the doubled limiter consumption or the fact that the breaker structurally cannot contain it.

## Finding 9

- **Location:** `src/lib/resilient-fetch.ts:1938`
- **Verdict:** PLAUSIBLE · **Category:** correctness

**What:** hasContractualWait tests only for the presence of Retry-After, so an empty, zero, or non-numeric value on any 503 disables the retry — including a `Retry-After: 0` that literally means "retry now".

**Failure scenario:**

`return res.headers.get("Retry-After") !== null` treats every non-null header value as a contractual wait, including `""`, `"0"`, and unparseable garbage. The docblock's safety argument is that "a malformed or hostile value cannot influence timing", but presence alone gates the whole retry: the value is never validated, so a value that is not a wait at all still routes attempt 1 down the fail-fast fall-through. Inputs: an `onboard` flow (retriesOverride=1, budget `process-key-enqueue`) whose attempt 1 receives a 503 from anything other than `error_contract.service_error` — a Railway edge/proxy response during a container restart, or a service_error whose header renders empty — carrying `Retry-After: 0` or `Retry-After: `. Expected: `hasContractualWait` is false, the loop logs, sleeps ~250-500 ms and retries; attempt 2 hits the restarted container and succeeds, and the user's key-connect completes transparently. Actual: `"0" !== null` and `"" !== null` are both true, the retry is skipped, and `instrumentBody` returns attempt 1's 503 to `postProcessKey`, which maps it to the SEAM-04 503 envelope — the wizard shows the user a connection failure for exactly the transient blip the retry was added to absorb, and it does so on the strength of a header value that said to retry immediately. The 503-only scoping does not save this: the check asserts the header's contract without checking that the response actually came from the emitter bound by that contract.

## Finding 10 — ⚠️ PRE-EXISTING, confirm attribution

- **Location:** `src/lib/resilient-fetch.ts:1053`
- **Verdict:** PLAUSIBLE · **Category:** correctness

**What:** The new span bound makes `decodeBreakerLock` return null for a stored value that is still PRESENT in Redis, which routes `recordSeamFailure`'s trip path into the `nx: true` branch — and `SET NX` cannot write over an existing key, so the circuit can never arm for the remaining TTL of that key.

**Failure scenario:**

Inputs/state: `breaker:railway` holds `open:0:100000000000000000` (the exact corrupt value the new G2 case in resilient-fetch.test.ts seeds) with a live key TTL, and Railway is degraded so every seam call fails. Path: `recordSeamFailure` reaches the trip path and does `const existing = decodeBreakerLock(await redis.get(breakerKey))`. Before 141.1 that decoded to `{armedAtMs: 0, expiresAtMs: 1e17}`, so `existing !== null` and the trip took the `get: true` overwrite branch at line ~1471, which unconditionally replaces the corrupt value with a fresh valid lock and arms the circuit. The key still exists, so Redis answers `null`, `written` is falsy, NO lock is written and the `if (written)` guard skips `emitBreakerTransition("open", …)`. ## Finding 11 — ⚠️ PRE-EXISTING, confirm attribution

- **Location:** `src/lib/resilient-fetch.ts:1053`
- **Verdict:** PLAUSIBLE · **Category:** correctness

**What:** decodeBreakerLock's new bound validates only the span between the two timestamps, so a lock with absurd absolute epochs but a legal 30 000 ms span still decodes and still mints the implausible Retry-After the docblock claims it closed. [same root cause also at: src/lib/resilient-fetch.ts:1012]

**Failure scenario:**

The guard is `spanMs <= 0 || spanMs > MAX_BREAKER_LOCK_SPAN_MS`, a purely relative check; neither `armedAtMs` nor `expiresAtMs` is compared against `Date.now()` or any absolute plausibility bound. Every legitimate lock has span exactly `BREAKER_COOLDOWN_S * 1000` = 30 000 (see `encodeBreakerLock` at the `recordSeamFailure` write site), so any pair sharing that delta passes regardless of where it sits on the timeline. Inputs: the stored value `open:100000000000000000:100000000000030000` (both magnitudes are exactly representable as doubles; 30000 is a multiple of the 16 ms ulp at 1e17, so `spanMs` computes to exactly 30000). Expected, per the docblock: rejected as not-plausible, decoder returns null, circuit reads CLOSED. Actual: it decodes, `isBreakerOpen` sees `lock.expiresAtMs > now` and returns `{ open: true, retryAfterS: Math.ceil((1e17 - now) / 1000) }` ≈ 1e14; `CircuitOpenError`'s A-15 guard passes it (`Number.isInteger(1e14)` is true, non-negative), and both seam clients emit it as `Retry-After: 100000000000000` — including on the anonymous verify-strategy teaser — which is the precise on-the-wire outcome the docblock says this parse now prevents. The reachable production variant is milder but the same shape: a writer instance whose clock is skewed an hour ahead arms a span-30 000 lock, and every reader tells users to retry in ~3,600 seconds instead of 30.
