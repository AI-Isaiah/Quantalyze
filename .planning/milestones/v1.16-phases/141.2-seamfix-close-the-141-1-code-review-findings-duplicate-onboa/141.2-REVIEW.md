## Summary

Six probe areas were traced against the tree at `a8084078`, not against the plans
or summaries. All six hold.

Independent verification run during the review: `npx tsc --noEmit` clean;
`vitest run` over the seven touched seam/cron suites — 394 tests, all passing.
(Branch protection is deferred, so CI is advisory at merge: these gates *would
have caught* a regression, they did not *stop* anything.)

**What was traced, and what was found:**

1. **Breaker trip path branching on RAW presence.** Correct in both directions.
   `rawLock === null` → `SET NX`, which still makes concurrent absent-key trips
   idempotent (loser gets `null` from `nx`, `written` falsy, no event). The
   displacement arm cannot double-emit: with `SET … GET`, exactly one racer
   displaces a non-live value (`displaced === null || expiresAtMs <= now`) and
   every other racer displaces the winner's live lock and returns silently. The
   corrupt-value case now self-heals instead of jamming `SET NX` for the key's
   whole TTL. Verified for corrupt-value races, tombstone races, and the
   mixed-deploy case (old instance jams, new instance heals — same direction).
2. **`decodeBreakerLock` one-sided bound.** The past side is open: a tombstone
   (`expiresAtMs` in the past) still decodes, so `isBreakerOpen`'s
   `announceBreakerClosed` path is intact. No production caller passes `nowMs`
   (`resilient-fetch.ts:1328`, `:1483`, `:1581` all take the `Date.now()`
   default); the only two non-default callers are tests. A live lock is rejected
   only if the writing instance's clock leads the reading instance's by more than
   `BREAKER_LOCK_TOMBSTONE_S` (60 s), and the rejection direction is fail-open.
3. **Per-attempt `admittedAtMs`.** The re-stamp at `:2341` sits *after* the
   `CircuitOpenError` throw at `:2329`, so a refused attempt is never stamped.
   Every admitted attempt is stamped exactly once: attempt 0 at `:2219` after the
   entry gate, attempt 1 at `:2341` after the re-check. `recordOnce` and the
   post-loop `instrumentBody` closure read the live binding, so both carry the
   last *admitted* attempt's instant — which is the attempt that produced what
   they record. No path stamps an unadmitted attempt; no admitted attempt goes
   unstamped.
4. **`hasContractualWait` parses instead of testing presence.** No new throw
   class: `parseRetryAfterSeconds` reaches the header through `headers?.get?.()`
   and `Date.parse` cannot throw; the local `typeof res.headers?.get !==
   "function"` belt still stands in front. Behaviour changes only for values our
   own `error_contract.service_error` cannot emit (`0`, empty, negative,
   unparseable, date-form without a `Date` header), and the change is toward
   retrying rather than surrendering — the safe direction.
5. **TS/Python predicate agreement on the empty string.** `retriesForFlow` uses
   `Boolean(context?.wizard_session_id)`; `process_key.py:1033` uses
   `bool(body.context.get("wizard_session_id"))`. Both read the same JSON field
   (`process-key-client.ts:498` sends `context: args.context` verbatim). Traced
   the only onboard producer that can populate the field:
   `finalize-wizard/route.ts:1585` spreads it conditionally from the DB column,
   and `payload` (`:1089`) is an explicit field allowlist that cannot smuggle a
   `wizard_session_id` of a non-string type — so the JS/Python truthiness
   divergence on `[]`/`{}` is unreachable. Empty string agrees on both sides.
   The other onboard producer (`keys/validate-and-encrypt`) is refused by the
   same predicate *and* by an explicit `retriesOverride: 0`.
6. **Flag-monitor denominator.** `audit_log.id` exists (migration
   `20260407075303_portfolio_intelligence.sql:68`), the `head: true` count shape
   matches the in-repo precedent (`src/lib/observability.ts:18`), and a
   PostgREST-reported error now terminates on its own reason instead of
   collapsing into `handleZeroDenominator`. **One residual path can still
   misreport a non-error as zero traffic** — see WR-02.

Two warnings below are real and provable, but both are operator-facing
(alerting) rather than user-facing or data-integrity, so under the stopping rule

## Warnings

### WR-01: a persistent denominator read failure now pages nobody, and reports HTTP 200

**File:** `src/app/api/cron/flag-monitor/route.ts:306-312`, `:430-441`

**Issue:** The fail-loud change routes a PostgREST error to
`{ kind: "terminal", res: NextResponse.json({ ok: false, reason:
"denominator_read_failed" }) }`. That response carries the default **200**
status, and the handler returns *before* both the H-2 streak increment
(`:439`) and the streak reset (`:445`).

Concrete scenario — Supabase REST degraded for four consecutive windows (~1 h):

- every run: one `console.warn` into the Vercel function log, then `200 {ok:false}`;
- `flag_monitor_zero_denominator_streak` is neither incremented nor reset, so
  the H-2 guard can never fire;
- Vercel's cron-failure alerting keys on non-2xx, so each run is recorded as a
  **success**;
- no email is ever sent.

This is a net regression against the pre-141.2 behaviour, which reached
`handleZeroDenominator` and sent a SEV-2 after three windows. The old alert
carried a *wrong diagnosis* ("no traffic OR the audit-write is failing"), which
is what D-05 correctly objected to — but the remedy replaced a wrong page with
**no page**. The docblock at `:281` claims "FAIL LOUD"; the response body is
louder and the paging is silent.

Not blocking: this is monitor-of-a-monitor territory, no user request is
affected, and the sibling `sentry_unreachable` / `sentry_not_configured` arms
have always had the same shape.

**Fix:** give the terminal response a non-2xx status so the platform's own cron
alerting fires, and/or give the read failure its own streak so it can escalate:

```ts
return {
  kind: "terminal",
  res: NextResponse.json(
    { ok: false, reason: "denominator_read_failed" },
    { status: 500 },
  ),
};
```

If a non-2xx is undesirable for the other arms' sake, the alternative is a
second streak row (`flag_monitor_denominator_error_streak`) with its own email
body naming Supabase rather than the audit-write.

### WR-02: `count ?? 0` reinstates the exact conflation D-05 removed, on a narrower path

**File:** `src/app/api/cron/flag-monitor/route.ts:314`

**Issue:** `return { kind: "ok", total: count ?? 0 };` treats "PostgREST answered
without an error but supabase-js could not derive a count" as **zero traffic**.
`postgrest-js` only populates `count` when the response carries a parseable
`content-range` (`node_modules/@supabase/postgrest-js/src/PostgrestBuilder.ts:512-516`):

```ts
const contentRange = res.headers.get('content-range')?.split('/')
if (countHeader && contentRange && contentRange.length > 1) {
  count = parseInt(contentRange[1])
}
```

Two reachable-in-principle outcomes, neither of which sets `error`:

- **header absent or unsplittable** (a gateway/proxy that drops `Content-Range`
  on a `HEAD`) → `count === null` → `total = 0` → `handleZeroDenominator` →
  after three windows the founder receives the H-2 SEV-2 asserting *"Either no
  traffic is reaching /process-key OR the audit-write at /process-key entry is
  failing"* — a false diagnosis pointing at the wrong system. That is precisely
  the failure D-05 set out to remove, still live behind the `??`.
- **`Content-Range: 0-24/*`** → `parseInt('*')` is `NaN`, and `NaN ?? 0` is
  `NaN` (not nullish) → `total = NaN` → `total === 0` false → `errorRate = NaN`
  → both threshold comparisons false → the route answers
  `{ok: true, errorRate: null, errorCount: N, total: null}` and **alerting is
  silently disabled for that window** with an `ok: true` envelope.

Low reachability (`count: "exact"` should always produce a numeric second
segment), which is why this is a warning rather than a blocker — but the
`?? 0` is the specific construct the docblock at `:286-288` calls out as having
had "finding 12 SILENTLY", kept verbatim one line below that sentence.

**Fix:** make a missing/non-finite count terminal, alongside the error arm:

```ts
if (error || typeof count !== "number" || !Number.isFinite(count)) {
  console.warn("[cron/flag-monitor] denominator read failed:", error ?? { count });
  return {
    kind: "terminal",
    res: NextResponse.json({ ok: false, reason: "denominator_read_failed" }, { status: 500 }),
  };
}
return { kind: "ok", total: count };
```

## Info

### IN-01: `hasContractualWait`'s docblock misstates where its throw would land

**File:** `src/lib/resilient-fetch.ts:2016-2020` (and the same claim on
`readDependencyBody`, `:1978-1980`)

Both docblocks say *"a throw here lands inside the classification window and
would replace the real upstream error with a bookkeeping one"*. Both call sites
are **outside** the `try`/`catch` — the catch closes at `:2440` and the calls are
at `:2465` and `:2486`. A throw would not be swallowed and re-reported; it would
escape `resilientFetch` entirely, past every client's typed error mapping. The
prose understates the consequence, in a file whose whole discipline is that its
comments are load-bearing. (The misleading dedent of the `try` body at
`:2356-2386` is what makes this easy to misread.) Behaviourally inert today —
both helpers are hardened not to throw — so this is a comment correction, not a
code change.

### IN-02: `decodeBreakerLock` is called with a fresh `Date.now()` while the caller already holds `now`

**File:** `src/lib/resilient-fetch.ts:1472` vs `:1483` and `:1581`

`recordSeamFailure` captures `const now = Date.now()` and then makes three
time-sensitive decisions, two of which (`decodeBreakerLock`) take their own,
later `Date.now()` via the new default parameter. Adding `nowMs` was justified as
"deterministically testable"; the one caller that could pass a consistent instant
does not. Benign in the current direction (a later `nowMs` only widens the future
bound, i.e. admits more), so no defect follows — but passing `now` explicitly
would make the trip path decide from one clock.

### IN-03: `Boolean(x) ? 1 : 0` is a double conversion

**File:** `src/lib/seam-retry-registry.ts:398`

`return Boolean(context?.wizard_session_id) ? 1 : 0;` — the ternary already
coerces. `return context?.wizard_session_id ? 1 : 0;` is identical. The explicit
`Boolean()` is defensible as documentation of the Python-agreeing predicate (the
docblock at `:312` makes that the point), so this is noted rather than
recommended for change.

### IN-04: the one-sided absolute bound is sensitive to inter-instance clock skew > 60 s

**File:** `src/lib/resilient-fetch.ts:1119`

A legitimate lock is rejected iff `writerNow − readerNow > BREAKER_LOCK_TOMBSTONE_S`
(60 s). On NTP-synced Vercel instances this is not a live risk, and the rejection
direction is fail-open (circuit reads CLOSED), which is this module's doctrine.
Recorded so the coupling between `BREAKER_LOCK_TOMBSTONE_S` and the skew
tolerance is written down somewhere other than a reviewer's head: retuning the
tombstone down retunes the skew tolerance with it.

### IN-05: `SEAM_BUDGETS["process-key-enqueue"].retries` now over-charges SC-4b

**File:** `src/lib/resilient-fetch.ts:639`

After D-03 withdrew `resync` and D-01 conditioned `onboard` on key presence, the
row still declares `retries: 1` while the traffic that can actually spend a
second attempt on it is `onboard`-carrying-a-`wizard_session_id` only. The row is
accounting-only (D-08) and over-charging headroom is the safe direction, and
`seam-constants.pin.test.ts:352-360` records the decision explicitly. Noted as a
known, deliberate imprecision rather than a defect.
