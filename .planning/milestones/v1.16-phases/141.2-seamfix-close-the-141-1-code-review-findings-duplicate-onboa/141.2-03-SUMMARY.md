# Phase 141.2 Plan 03: Flag-Monitor Denominator Summary

Rebuilt `getDenominator` as an uncapped, attempt-grained, wire-uninfluenceable
server-side COUNT with a fail-loud read path — closing findings 2, 3, 4, 7 and
12 as one coherent rewrite, with `getNumerator` byte-for-byte untouched.

---

## ⚠️ Operational reality — read before any claim about impact

**This monitor has never computed a denominator in production.** The
`flag_monitor_zero_denominator_streak` feature-flag row — which `handle()`
writes on *both* exits past the denominator — does not exist in prod. The only
consistent explanation is that `handle()` has never progressed past the Sentry
gate.

The suspected cause (`SENTRY_ORG_SLUG` / `SENTRY_AUTH_TOKEN` unset in Vercel
prod, returning `{ok:false, reason:"sentry_not_configured"}`) is **[ASSUMED]**
— it was not verified against Vercel's environment, and confirming it is an
**operator task, not a phase task**.

Consequently, every claim in this summary is framed as **"would have caught"**.
These are genuine correctness defects, not live-firing incidents. Nothing here
"did stop" a bad page, because nothing here has ever run to completion.

## What changed

### The three defects, and why they were one rewrite

The 141.1 D-16 denominator shipped three monitoring-integrity regressions at
once, and all three dissolve in the same move — removing the dedup:

| # | Finding | Defect | Why the COUNT removes it |
|---|---------|--------|--------------------------|
| 3 | Truncation | unbounded `.select()` vs PostgREST `max_rows=1000`, HTTP 200, `error: null` | `head: true` materialises no rows; no cap at any volume |
| 2, 4 | Wire control | dedup keyed on inbound `X-Correlation-Id`, reachable via the **unauthenticated** `/api/verify-strategy` | the computation reads no caller-supplied value at all |
| 7 | Grain | denominator at request grain vs a per-attempt numerator | audit rows are per-attempt, so attempt/attempt is consistent with no dedup |
| 12 | Error-as-zero | a PostgREST error became literal `0`, i.e. `handleZeroDenominator`'s meaning | distinct `denominator_read_failed` terminal outcome |

**The dedup's premise was false on the wire, not merely fragile.** Production
evidence over every `entity_type='process_key'` row: 42/42 carry bare
server-minted UUIDs, 0/42 carry a `wizard:` prefix, and the distinct-id count
equals the row count *exactly*. The Set could never collapse anything.

### NOT a literal revert

Per research §0.4, the pre-141.1 body destructured only `count` and returned
`?? 0` — finding 12 in its **silent** form. A literal revert would have
reintroduced the bug this same plan was ordered to fix. The shipped form is
counting form **plus** explicit error capture, using the
`{kind:"ok"} | {kind:"terminal"}` union `getNumerator` already uses in the same
file.

### Prose moved with the code

The false seam-crossing sentence was **named and corrected, not deleted** (§7a
idiom): stated as true in TypeScript, false end-to-end, with the mechanism
(Python re-mints `uuid4()` on any non-bare-UUID inbound id; `wizardFetch` sends
a prefixed id on both retry-eligible flows) and the production evidence. The
true per-attempt-write sentence was **retained and re-purposed** as the
load-bearing half of the new rationale.

The known limitation is stated rather than engineered around: **retries inflate
the denominator, so the rate biases DOWNWARD (quieter) when the seam retries.**
That is the safe direction versus a fabricated denominator that pages falsely
and a wire-controlled one that can be silenced on demand. A true per-request
rate needs a server-minted request id the retry reuses — deferred, out of scope.
Two further caveats recorded: 429/401 attempts refused above the audit write
produce no row, and the write is fire-and-forget (a lost row biases the rate
upward — also the safe direction).

## The doubles — shape-distinguishing, with different per-test payloads

Both the unit and integration `audit_log` doubles now **inspect the select they
receive**:

- the COUNT chain (`{ count: "exact", head: true }`) resolves the scenario's
  true total, uncapped;
- any row-materialising select resolves a **per-test configurable** payload,
  defaulting to a `max_rows`-capped page (what deployed PostgREST actually
  returns, with no truncation signal).

The two payloads genuinely differ, and each is required by exactly one mutation:

| Test | Row payload | Mutation it reddens |
|------|-------------|---------------------|
| (D3) | 1000-row `max_rows` page, true count 3000 | SC-F |
| (D4) | 200 rows, all one shared wire-supplied id | SC-G |
| (D5) | 20 rows, retried pair sharing one id | SC-H |

Verified empirically, not just by inspection: SC-F reddens (D3) and **not**
(D4); SC-G reddens (D4). Different payloads, different mutations.

**2. [Plan-conformance] SC-H pin reordered so the RATIO fails first**

- **Found during:** Task 2 mutation proof
- **Issue:** As first written the pin asserted `body.total` before
  `body.errorRate`, so SC-H reddened on the count — violating the plan's
  explicit requirement that it "REDs **via the RATIO**" and its warning that
  the pin "does not merely re-assert the count the double returned".
- **Fix:** Ratio asserted first; component values retained afterwards as
  diagnostics, with a comment recording why the order is load-bearing.
- **Commit:** `5ad5efce`

**3. [Scope] TDD gate on Task 2 is a mutation proof, not a RED-before-GREEN**

Task 2 is marked `tdd="true"`, but the behaviour it pins (attempt grain) landed
in Task 1, so the SC-H pin passed on first run. Its falsifiability is
established by the SC-H mutation rather than by a prior RED. Stated rather than
papered over — claiming a RED that did not happen is the defect class this
