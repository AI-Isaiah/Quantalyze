## Summary

The phase's core claims hold up under adversarial tracing. I verified independently, and
found no defect in:

- **All eight `X-Tenant-Claim` call sites are server-derived.** `create-with-key`,
  `composite/add-key`, `validate-and-encrypt` (threaded `user.id` rather than re-derived),
  `scenario/optimize` (`supabase.auth.getUser()` after the approval gate),
  `admin/match/eval`, `bridge`, `simulator`, `admin/match/recompute` — every one takes the
  authenticated session id, and the five `postProcessKey` callers pass `user.id` or the
  literal `"public"`. No caller can influence the claimed tenant. The `TenantIdentity`
  object-wrapper genuinely converts the `passphrase`-transposition threat into a type error.
- **The `recordOnce` latch is correct.** A counting 503 whose body then aborts records once,
  not twice; a second body read records nothing; a `SyntaxError` parse failure records
  nothing. I traced every arm.
- **`redirect: "error"` outranks the caller** (placed after the `...requestInit` spread).
- **Path construction is safe.** Both `/internal/keys/…` sites use `encodeURIComponent`;
  `evalMatch` builds its query with `URLSearchParams`. No SSRF or traversal found.
- **The A-09 fix is right.** `verdict.reason === "timeout"` correctly separates the library's
  fail-open sentinel from the `cacheBlock` denial that must still trip.
- **The harness de-self-referencing is real.** `fakeRatelimitFor` no longer harvests
  production's `slidingWindow` argument; `FAKE_THRESHOLD`/`FAKE_WINDOW_MS`/`FAKE_LOCK_TOMBSTONE_MS`
  are hand-typed and pinned literal-against-literal. The residual
  `mod.BREAKER_FAILURE_THRESHOLD` loop bounds are now a genuine two-source falsifier, not the
  old mirror. The real-Redis lane's anti-vacuity fence (7 hand-typed `casesExecuted++`) is
  wired, gated as a required check, and consumes no secret so it cannot skip on a fork.
- `npx tsc --noEmit` clean; `npx eslint --no-cache` on every changed seam file clean
  (one pre-existing `import/no-anonymous-default-export` warning); the six seam unit suites
  pass 334/334.

What it did **not** get right is concentrated in two places: the redaction leaf **destroys**
the diagnosis for every non-`Error` object — which is the over-redaction half of TRAP-1
shipping inside the fix meant to prevent it, across six log sites this phase converted — and

## Critical

### CR-01 (BLOCKER): the redaction leaf renders every non-`Error` object as `[object Object]`, destroying six Supabase diagnostics this phase converted

**File:** `src/lib/seam-redaction.ts:272-299` (`describeThrown`)
**Downstream sites:** `src/app/api/strategies/finalize-wizard/route.ts:598, 671, 714, 811, 948, 1125`

`describeThrown` has exactly three shapes: `undefined`, `null`, `Error`, and a
`String(err)` fallback. It has **no branch for a plain object**. `String({code, message, …})`
is `"[object Object]"` — confirmed by execution.

Supabase/PostgREST errors on the **non-throwing** path are plain parsed JSON objects, not
`PostgrestError` instances. Read at source in the installed dependency
(`node_modules/@supabase/postgrest-js/dist/index.mjs:373-436`): `new PostgrestError(error)`
is constructed **only** when `shouldThrowOnError` is set; otherwise `processResponse` returns
the raw `JSON.parse(body)` result as `error`. Every `const { data, error } = await supabase…`
in this repo takes that path.

This phase converted six log sites from `err.message` / `scrubInternalToken(err.message)` to
`scrubSeamError(err)`, driven by the new `seam-log-coverage.test.ts` guard. All six now emit
`[object Object]`:

| line | site | was | is now |
|---|---|---|---|
| 598 | strategy lookup failed | `strategyErr.message` | `[object Object]` |
| 671 | asset_class venue resolve | `scrubInternalToken(keyVenueErr.message)` | `[object Object]` |
| 714 | asset_class persist | `scrubInternalToken(assetClassErr.message)` | `[object Object]` |
| 811 | composite member list read | `scrubInternalToken(membersErr.message)` | `[object Object]` |
| 948 | api_keys.exchange lookup | `scrubInternalToken(keyRowErr.message)` | `[object Object]` |
| 1125 | api_key_id lookup in `after()` | `scrubInternalToken(keyLinkErr.message)` | `[object Object]` |

**Concrete failure scenario.** A composite draft fails to finalize because the member-list
read errors (RLS change, connection pool exhaustion, a `PGRST` code). The route fails closed
and returns 503 `COMPOSITE_MEMBERSHIP_UNKNOWN`; the user retries and it keeps failing. The
only operator artefact is
`[strategies/finalize-wizard] composite member list read failed: [object Object]`.
The SQLSTATE, the message, the hint and the details are all gone. This is exactly the A-10
harm the phase's own CONTEXT names ("the operator could see THAT the seam failed and never
WHY") reintroduced by the mechanism that was supposed to close it, and the TRAP-1
over-redaction warning realised.

**Why no test caught it.** `src/lib/seam-redaction.test.ts:297-318` is the case that covers
non-`Error` inputs. It seeds a plain object literally containing `code: "ECONNREFUSED"` — a
preserve token — and then asserts only:

```ts
expect(typeof out).toBe("string");
expect(out.length).toBeGreaterThan(0);
```

`"[object Object]"` satisfies both. The assertion cannot redden for any rendering whatsoever.
This is a toothless oracle inside the phase whose subject is toothless oracles.

**Fix:**

```ts
// src/lib/seam-redaction.ts — inside describeThrown, before `return String(err)`
if (typeof err === "object" && !Array.isArray(err)) {
  // A Supabase/PostgREST error is a PLAIN object on the non-throwing path
  // (postgrest-js constructs PostgrestError only under shouldThrowOnError), so
  // String() renders it "[object Object]" and the whole diagnosis is lost.
  const rec = err as Record<string, unknown>;
  const parts: string[] = [];
  for (const key of ["name", "code", "message", "details", "hint", "errno", "syscall"]) {
    const v = rec[key];
    if (typeof v === "string" || typeof v === "number") parts.push(`${key}=${v}`);
  }
  if (parts.length > 0) return parts.join(" ");
  try { return JSON.stringify(err) ?? "[unserialisable object]"; }
  catch { return "[unserialisable object]"; }
}
```

and make the oracle two-sided, so it can fail:

```ts
const out = scrubSeamError({ code: "ECONNREFUSED", message: "connect ECONNREFUSED 10.0.0.1:8002" });
expect(out).toContain("ECONNREFUSED");           // the preserve side, on a PLAIN OBJECT
expect(out).not.toBe("[object Object]");
```

Add a corresponding case for a PostgREST-shaped object (`{code:"42501", message, details, hint}`)
asserting the SQLSTATE and message survive.

## High

### HI-01: `nx: true` is provably untested, and the branch that actually races does not use it

**File:** `src/lib/resilient-fetch.ts:1129-1158`

Two writes exist on the trip path:

```ts
if (existing === null) {
  written = await redis.set(breakerKey, value, { ex: ttlS, nx: true });   // :1134
} else {
  written = await redis.set(breakerKey, value, { ex: ttlS });             // :1139  ← no nx
}
if (written) { emitBreakerTransition("open", …); }                        // :1150
```

The comment at `:1141-1149` states: *"`nx` answers `null` when a concurrent instance won the
race, and that instance is emitting its own event; claiming a transition here would
double-count every trip across a Fluid Compute fleet."* That is true only of the first branch.

**Failure scenario.** A lock armed at `t=0` expires at `t=30`; the key survives to `t=90` as a
tombstone. At `t=31` Railway is still degraded, so N Fluid Compute instances each hit the trip
path within the same few milliseconds. Each reads the tombstone (`expiresAtMs <= now`, so the
`:1107` guard does not fire), each passes the A-25 guard (`admittedAtMs > armedAtMs`), and each
takes the `else` branch, which has **no `nx`**. Every one of them writes and every one of them
gets a truthy reply, so `emitBreakerTransition("open", …)` fires **N times for one trip** — the
exact double-count the comment claims is prevented — and each later write extends
`expiresAtMs` by its own write-time delta, a small ratchet of the same class R-3 exists to
forbid.

**Why nothing sees it.** Every test that claims to cover this reaches
`if (existing.expiresAtMs > now) return;` (`:1107`) and returns before any `set`:

- `src/lib/resilient-fetch.test.ts:889-905` — comment says *"`nx: true` makes the trip
  idempotent"*; it drives 5 failures (lock live), then 2 more. Both extra calls return at `:1107`.
- `src/lib/resilient-fetch.test.ts:2014-2027` — comment says *"`nx: true` refuses the write"*;
  identical shape, identical early return.
- `tests/redis/seam-breaker.redis.test.ts:430-473` (R-3) — sleeps 4s of a 30s cooldown, so the
  lock is still live; also returns at `:1107`.

`src/lib/resilient-fetch.test.ts:664` (the A-25 negative control) is the only case that reaches
a `set` with a non-null `existing`, and it exercises the `else` branch — the one without `nx`.
Every case that reaches the `nx` branch does so with an **empty** store, where `nx` and no-`nx`
behave identically.

**Deleting `nx: true` from line 1134 leaves the entire suite green**, including the real-Redis
lane. A live production behaviour has no falsifier at all, and two test comments actively
assert a mechanism their case never touches.

**Fix (both halves):**

1. Make the write compare-and-set rather than blind on the tombstone branch, so exactly one
   instance claims the transition:

```ts
// Overwriting a TOMBSTONE. `nx` would refuse, so claim the slot by asserting the
// value we read is still there; anything else means another instance re-armed it
// first and IT owns the event.
written = await redis.eval(
  "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3]) end return nil",
  [breakerKey],
  [encodeBreakerLock(existing.armedAtMs, existing.expiresAtMs), value, String(ttlS)],
);
```
   (or, if Lua is unwanted here: `del` + `set … {nx:true}` and treat a `null` reply as "another
   instance won", accepting the sub-millisecond window in which the key is absent.)

2. Add a case that stubs the store's `set` to return `null` and asserts **zero**
   `seam.breaker.open` events and no second write — the only shape that can redden if `nx` is
   removed. Correct the two misattributing comments at `:890` and `:2015` in the same change.

### HI-03: the minimum-length refusal leaves short USER-OWNED credentials unredacted, and prints a remedy the user cannot apply

**File:** `src/lib/seam-redaction.ts:129, 210-216`
**Call site:** `src/app/api/keys/validate-and-encrypt/route.ts:342-348`

`MIN_REDACTABLE_SECRET_LENGTH = 12`. A candidate shorter than that is **not** redacted; the
line goes out verbatim with a notice appended:

```
[seam-redaction: refused to redact 1 value(s) shorter than 12 chars (a per-request secret) —
 this line may be under-redacted; lengthen the secret rather than the leaf]
```

The floor is correct for *env* secrets (all are ≥32 chars) and the reasoning about eating
`ENOTFOUND`/`ETIMEDOUT`/`EAI_AGAIN` is sound in the abstract. It is wrong for **per-request**
secrets, which are user-owned and not length-controlled by us:

- MT5's `api_key` is the **account login number** — 8 digits (`26547876`). Below the floor.
- OKX / Coinbase passphrases are **user-chosen**. `validate-and-encrypt/route.ts:125` validates
  only `passphrase.trim().length !== 0`; `create-with-key/route.ts:167,188` validates non-empty
  and `<= 512`. A 6-character passphrase is accepted.

`validate-and-encrypt/route.ts:342` passes `[api_key, api_secret, passphrase]` to **both**
`console.error` and `captureToSentry(..., { secrets })`. Sentry is a third party — the leaf's
own docblock says *"anything captured leaves our infrastructure, so 'the caller will remember'
is not an acceptable control."* For a short passphrase the leaf itself is the one that stops
remembering.

The stated justification for the floor is already served **independently** by the preserve-token
collision check at `:217-222`, which detects and reports a secret whose value contains a
diagnostic token regardless of length.

**Fix:** apply the floor only to env-derived candidates. An explicitly-passed per-request secret
is an assertion by the call site that this exact byte string is a credential; honour it at any
length and let the existing collision check report the (rare) case where it eats a token.

```ts
interface SecretCandidate { label: string; value: string; perRequest: boolean }
// …
if (!candidate.perRequest && candidate.value.length < MIN_REDACTABLE_SECRET_LENGTH) {
  refused.push(candidate.label);
  continue;
}
```

### ME-02: the composite member cap creates a permanent dead end rendered to the user as a transient retry

**File:** `src/app/api/strategies/finalize-wizard/route.ts:123, 806, 845-889`

`.limit(MAX_COMPOSITE_MEMBERS)` fetches at most 10 rows, and `:845` refuses at
`>= MAX_COMPOSITE_MEMBERS`. The usable maximum is therefore **nine**, and the constant named
`MAX_COMPOSITE_MEMBERS = 10` is off by one from the thing it names.

**Failure scenario.** A user with a genuine 10-member composite draft submits. The read returns
exactly 10, `:845` fires, and they get `503` with
`code: "COMPOSITE_MEMBERSHIP_UNKNOWN"` and `error: "Could not load composite members; please
retry."` — forever. The condition is permanent, the copy says retry, the client renders a retry
affordance, and the user has no path forward and no explanation. Any existing composite with
≥10 members becomes un-finalizable the moment this ships.

The route's own comment at `:873-878` acknowledges this: *"the retry affordance the shared
envelope renders is wrong for a permanent condition"*, deferring the copy to 140.3. The
behaviour ships now regardless.

**Fix:** distinguish "exactly at the cap" from "possibly truncated" by fetching one extra row,
so a legitimate 10-member composite finalizes and only 11+ refuses:

```ts
.limit(MAX_COMPOSITE_MEMBERS + 1);
// …
if ((members?.length ?? 0) > MAX_COMPOSITE_MEMBERS) { /* refuse */ }
const probeList = members ?? [];   // now provably complete and <= MAX_COMPOSITE_MEMBERS
```
`SEAM_ROUTE_BUDGETS`'s `calls: 10` and SC-4e stay correct because the probed count is still
capped at 10. Give the refusal its own `code` so 140.3 can render a permanent condition rather
than a retry.

### ME-03: `{ timeoutMsOverride: undefined }` passed explicitly throws `SeamConfigError`

**File:** `src/lib/resilient-fetch.ts:1472-1483`

The guard is `if ("timeoutMsOverride" in init)`, not `if (timeoutMsOverride !== undefined)`. The
declared type is `timeoutMsOverride?: number`, which under this repo's tsconfig admits an
explicit `undefined`. The ordinary JS shape for forwarding an optional value —

```ts
resilientFetch(key, path, { ...base, timeoutMsOverride: maybeOverride });
```

— therefore becomes a hard `SeamConfigError` whenever `maybeOverride` is `undefined`, which is
the common case. `analytics-client.ts:295-297` dodges it with a conditional spread, but that is
a convention held at one call site, not a mechanism, and nothing stops the other four call sites
(or a new one) from writing the natural form. Property-key presence deciding validity is
invisible at the type level.

**Fix:**

```ts
if (timeoutMsOverride !== undefined) {
  if (typeof timeoutMsOverride !== "number" || !Number.isFinite(timeoutMsOverride) || …) { throw … }
}
```
If the intent really is "presence is the contract", encode it: `exactOptionalPropertyTypes`, or a
discriminated `{ timeoutMsOverride: number } | Record<string, never>`.

### ME-04: the unauthenticated teaser records onto the GLOBAL breaker key, which every call site checks

**File:** `src/lib/resilient-fetch.ts:473-483` (`process-key-sync` row)

`process-key-sync` declares `dependencies: []`, and the comment reasons that *"Declaring nothing
keeps an unauthenticated caller's blast radius at the global key alone."* The global key is not a
containment: `breakerKeysFor` (`:778-780`) appends `BREAKER_KEY` to **every** call site's check,
so a lock on `breaker:railway` blocks all fifteen routes.

The anonymous `verify-strategy` teaser reaches this row with a **60 000 ms** budget and runs the
full inline pipeline. Five deadline expiries or transport failures inside the 30 s window open
the global circuit for every authenticated user for 30-60 s. Vercel's 10 req/60 s per-IP cap is
not a defence against a distributed caller. This phase **widens** the surface: SEAMCORE-02 moved
the body read inside the classification window, so an aborted body read on the teaser path is a
new way for an anonymous caller to record a global failure.

Fail-open is doctrine and I am not asking to change it. What is missing is that the widest key in
the system is reachable by the least-authenticated path, and the row's comment reads as if that
were the safe choice.

**Fix (pick one and record it):** give anonymous budgets a dedicated key
(`breaker:teaser`) added to the anonymous rows' `dependencies` and to nothing else; or exclude
anonymous flows from recording entirely (they are lead-generation, not a health signal); or
document explicitly that the global key is deliberately reachable anonymously and why the
resulting DoS is accepted.

### LO-01: `501` and `505` count toward the breaker, re-creating the self-sustaining outage the `500` arm exists to prevent

**File:** `src/lib/seam-discriminator.ts:294-312`

Only `500` is `service-permanent`. `501 Not Implemented` and `505 HTTP Version Not Supported`
fall into the `other 5xx → SERVICE-TRANSIENT → COUNTS` arm. Both are deterministic: retrying
cannot help, so five of them in 30 s open the global circuit, which then blocks its own recovery
— verbatim the R-1 / A-02 reasoning the `500` arm cites. A route deployed against a Python
version that does not implement a method would trip the seam for everyone, permanently, one
cooldown at a time.

The docblock justifies the arm for 502/504 (platform edge) and notes it is pre-phase behaviour,
which is true — but the phase re-derived this table from the status contract and could close it.

**Fix:** `if (status === 500 || status === 501 || status === 505) return SERVICE_PERMANENT;`, or
state in the table why 501/505 are considered transient on this seam.

### LO-02: `decodeBreakerLock` accepts a reversed or unbounded span, defeating the A-15 guard downstream

**File:** `src/lib/resilient-fetch.ts:828-835`

The regex `^open:(\d+):(\d+)$` accepts any digit strings. A corrupt-but-matching value such as
`open:0:99999999999999999999` decodes to `expiresAtMs ≈ 1e20`, `isBreakerOpen` returns
`retryAfterS ≈ 1e17`, `Number.isInteger` accepts it, and `Retry-After: 100000000000000000` goes
on the wire — including to the anonymous teaser. A reversed pair (`expiresAtMs < armedAtMs`)
makes `emitBreakerTransition`'s `cooldownS` negative.

The value is only writable by us today, so this is bookkeeping corruption rather than an attack
path. But `CircuitOpenError`'s A-15 guard was added specifically to stop implausible values
reaching a header, and this is the one remaining path that can produce one that passes it.

**Fix:**

```ts
const armedAtMs = Number(parsed[1]);
const expiresAtMs = Number(parsed[2]);
const span = expiresAtMs - armedAtMs;
// A lock this module wrote spans exactly BREAKER_COOLDOWN_S; anything outside the
// key's own maximum life is corruption, and corruption reads CLOSED (locked decision 4).
if (span <= 0 || span > (BREAKER_COOLDOWN_S + BREAKER_LOCK_TOMBSTONE_S) * 1_000) return null;
return { armedAtMs, expiresAtMs };
```

### LO-03: two test comments assert a mechanism their case never reaches

**File:** `src/lib/resilient-fetch.test.ts:890-892, 2015-2016`

*"`nx: true` makes the trip idempotent"* and *"`nx: true` refuses the write"*. Neither case

### LO-04: `resilient-fetch.ts:1560-1567` describes `X-User-Id` as "UNSIGNED client input" — it is server-derived at the only site that sends it

**File:** `src/lib/resilient-fetch.ts:1560-1567`

### LO-05: `sentryCaptureDeps()` resolves one hop and re-arms the trap it disarmed

### LO-06: `scrubSeamError(error.message)` passes a string into the error renderer
