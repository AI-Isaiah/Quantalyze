<objective>
Fail loud on malformed values, and give ambiguous transports exactly one defined outcome across both
clients.

Purpose: the remainder of `SEAMCORE-11` (A-15, A-27). The redirect and timeout-override halves
landed in plan 140.2-05; this plan closes the two that touch the clients rather than the core.

Three defects, all verified by execution on Node this session:

  **A-27 — a null-body status crashes the route.** `Response.json(body, { status })` THROWS
  `TypeError: Response constructor: Invalid response status code` for 204, 205 and 304. The
  `/process-key` client's `!res.ok` arm does `NextResponse.json(err, { status: res.status })`, so a
  304 pass-through crashes the handler. 204 also DIVERGES between the two clients today — one throws
  untyped, the other returns a success envelope with an empty body.

  **A-27's first half — a non-JSON 2xx is invisible to the breaker and lies to the operator.** A
  Railway edge or maintenance page served as `200 text/html` produces
  `"Analytics service returned an unexpected response. Is it running on the correct port?"` — a
  local-dev message, during a production incident.

  **A-15 — `CircuitOpenError` has no constructor validation**, while `AnalyticsUpstreamError` sixty
  lines away fail-loudly raises on a bad status. A `retryAfterS` of NaN produces `Retry-After: NaN`
  on the wire.

SEAMCORE-11 requires ONE defined outcome across both clients. Pick it, document it, pin it — the
requirement is not satisfied by two clients each having a reasonable but different answer.
</objective>

<interfaces>
The defined outcome to implement, identically in both clients — state it in a comment in both files
so the next reader does not have to diff them:

  Non-JSON 2xx (any 2xx whose content-type is not JSON, including a `text/html` maintenance page):
    a typed upstream error carrying the observed status and content-type, with a static operator-
    facing message that names the SEAM, not a local dev port.

  Null-body statuses 204 / 205 / 304: the same typed outcome, constructed WITHOUT attempting a
  JSON-bodied response at that status — the construction itself is what throws. Neither client may
  pass one of those three statuses to a JSON response constructor.

  In `process-key-client` the outcome must be delivered as a `{ ok: false, response }` envelope
  rather than a throw, preserving the never-throws contract plan 140.2-05 established.

Verified by execution on Node this session, so these are behaviours, not guesses:
  `Response.json(body, { status: 204 | 205 | 304 })` throws `TypeError: Response constructor:
  Invalid response status code`.
  `AbortSignal.timeout(NaN)` and `(-1)` and `(1e15)` throw `RangeError`; `(undefined)` and `("x")`
  throw `TypeError`.
  `fetch("notaurl/x")` REJECTS with `TypeError: Failed to parse URL` — a rejection, not a
  synchronous throw.
</interfaces>
