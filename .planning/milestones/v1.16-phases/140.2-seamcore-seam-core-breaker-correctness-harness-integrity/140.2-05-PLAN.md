<objective>
Move the classification window so it covers the whole request lifecycle, and move the caller/config
faults out of it — in ONE pass over the same `try` block.

Purpose: `SEAMCORE-02` / ROADMAP SC1, plus the first half of `SEAMCORE-11`.

Today the `try` closes before every body read. `AbortSignal.timeout` aborts the RESPONSE STREAM, not
just the header exchange, so for the modal Railway degradation — headers fast, body slow — `fetch`
RESOLVES, the try closes, the response is returned, and the rejection happens later inside the
caller's `res.json()`. `recordSeamFailure()` is therefore **never called** on that path, and the
core's own docblock ("breaker check → budgeted fetch → classified failure recording") is FALSE about
it. On the success arm of `analytics-client` there is no catch at all, so the raw `DOMException`
escapes and misses every `instanceof` arm.

In the opposite direction, the URL template and `AbortSignal.timeout()` are constructed INSIDE the
try, so a malformed `ANALYTICS_SERVICE_URL` rejects before a packet leaves, is logged as "network
failure reaching the analytics service", and after five requests opens the global breaker
permanently — from a config typo, with the log pointing ops at Railway.

⚠️ **A-21 and A-22 MUST be one task and one commit.** One moves the body read INTO the try; the
other moves URL and signal construction OUT of it. They pull in opposite directions on the same
block. TRAP-8 is receipted: two fixes touching the same file in one pass reintroduced each other's
bugs (C5 undid C6). Splitting them here is the receipted failure mode. They live in Task 1's SECOND
commit, together with A-23 and A-28.

⚠️ **RED comes first, and it is the same task.** This is the phase's highest-value fix, so its test
must exist and FAIL before the implementation exists. Task 1 writes the failing cases, observes them
RED, and only then makes them green. A `tdd="true"` task whose tests are written two tasks later is
TDD in frontmatter only.

<error_leaf_decision>
## The `SeamBodyReadError` importer class — DECIDED here, not left to the executor

The plan-checker was right that this was undecided, and an undecided error class is how a new throw
type reaches a route handler nobody updated. Three decisions, binding:

**1. Re-export symmetry: YES.** `src/lib/resilient-fetch.ts` currently carries
`export { CircuitOpenError };` with a docblock explaining it is an ergonomics re-export while
`@/lib/seam-errors` stays the CANONICAL path. Add `SeamBodyReadError` to that same re-export.
Reason: both classes are thrown BY the core, so a caller importing the core reasonably expects both
there. An asymmetry would read as meaningful and would invite a future reader to "fix" it in the
wrong direction — importing the leaf's class from the core inside a `"use client"`-reachable module
and dragging `@upstash/redis` into the browser bundle. One line, and it removes a trap.
**The canonical import path stays `@/lib/seam-errors`** — say so in the same comment, and import it
from there in every new production site.

**2. The fifteen `CircuitOpenError` importers do NOT need a new catch arm.** Enumerated this session
by `grep -rn "seam-errors" src/`: nine seam-touching route files, `process-key-client.ts`,
`analytics-client.ts`, `resilient-fetch.ts`, `wizardErrors.ts`, plus two more route files — fifteen
production importers. They import that class for the BREAKER arm. `SeamBodyReadError` can only reach
a catch arm that sits DOWNSTREAM of a body read, which is a strictly smaller set.

**3. `SeamBodyReadError` must NOT escape `postProcessKey` — extend its `try`, do not let it
propagate.** This is the substantive decision and it reverses an implication in this plan's earlier
form. `postProcessKey`'s `try` wraps only the `resilientFetch` call; both body reads sit after the
catch. Letting the new error propagate from those reads would make a function whose declared type is
`Promise<PostProcessKeyResult>` — and which today NEVER throws — start throwing, at five caller
routes (`strategies/csv-validate`, `strategies/csv-finalize`, `strategies/finalize-wizard`,
`keys/sync`, `verify-strategy`), none of which has a catch for it. That is five new unhandled-throw
paths delivered as a side effect of a body-read fix.

Instead: **extend `process-key-client`'s existing `try` to cover both body reads**, and add a
`SeamBodyReadError` arm to its existing catch that maps onto the taxonomy ALREADY THERE —
`deadlineExceeded: true` → the existing `UPSTREAM_TIMEOUT` 504 envelope, `deadlineExceeded: false` →
the existing `UPSTREAM_NETWORK_ERROR` 502 envelope. Both envelopes exist today with their copy
already written, so this authors **zero new user-facing copy** (140.3's fence holds) and preserves
the never-throws contract. Keep `CircuitOpenError` FIRST in the catch order — that ordering comment
is load-bearing.

Consequently the sites that DO need attention are exactly: `analytics-client.ts` (maps it internally
onto `AnalyticsTimeoutError` / the not-reachable arm, so its nine wrapper consumers see no new type),
`process-key-client.ts` (per above), and the three route files that call `resilientFetch` directly
and read the body themselves — `keys/[id]/permissions`, `finalize-wizard`, `keys/validate-and-encrypt`.
At those three the throw is the DESIRED behaviour (`keys/[id]/permissions` depends on it so the
`unstable_cache` boundary writes no entry), so they need no new arm either — only a comment recording
that the propagation is deliberate.

**Net: zero new catch arms outside the two clients.** Record the enumeration and this reasoning in
the SUMMARY; if the executor finds a sixth direct body-read site, that is a finding and the count
must be re-derived, not assumed.
</error_leaf_decision>
