## The completeness mechanism, in detail

The plan's charge was to deliver *the other half* of `src/lib/api/limiter-ordering.test.ts` — walk,
classify, **fail on unclassified**. Implementation:

1. **DISCOVER from disk, three families**, every read comment-stripped before matching:
   - (i) each `export async function` in `analytics-client.ts` scanned for `budgetKey: "…"`
     occurrences, each paired with the nearest preceding `analyticsRequest(` path literal;
   - (ii) `budgetKeyFor`'s body with the `=== "flowType"` comparisons removed first, so the only
     literals left are the keys it can return; the path taken from that module's core call;
   - (iii) a walk of every non-test `.ts`/`.tsx` under `src/`, matching a string literal in first
     argument position of a core call.
2. **NORMALISE paths** by replacing `${…}` with `{}` rather than truncating — truncating would have
   collapsed B-12's two copies (which differ only by `?force_refresh=true`) into one
   indistinguishable entry.
3. **COMPARE AS A SET**, not a count: `family | key | path | site` encodings, sorted, deep-equal
   against the flattened hand-typed roster. A count passes a rename and passes swapping one binding
   for another — measured in 140.2-02, where a key rename left the count at 13.
4. **A vacuity fence:** `discovered.length >= 14`, so a moved file or a pattern that stops matching
   fails loudly instead of leaving the guard blind-but-satisfied.
5. **A non-literal sentinel:** a call whose path argument is not a literal is recorded as
   `<NON-LITERAL PATH>`, which cannot match the roster — it fails rather than being skipped.

**Failure-mode direction is deliberate.** Trailing `//` comments are NOT stripped, so hiding a
binding behind one produces a false POSITIVE (an extra discovered site). A guard that fails when it
should not is recoverable; one that silently misses a binding is the defect.
