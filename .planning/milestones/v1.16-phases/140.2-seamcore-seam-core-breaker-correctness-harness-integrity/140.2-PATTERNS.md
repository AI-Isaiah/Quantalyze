## PART 6 — Structural/architectural test idioms this repo already uses

**Enumeration method.** `grep -rln "typescript-estree\|ts.createSourceFile\|@typescript-eslint/parser\|espree\|acorn" src tests tools scripts` → **EMPTY**. There is **no AST-based structural test on the
TypeScript side** (the AST fences in this programme are all Python `ast` in `analytics-service/tests/`).
The four idioms that DO exist:

### Idiom A — eslint-plugin-quantalyze AST rule + RuleTester + resolved-severity assertion ⭐
*This is the repo's answer to "you may not do X in file Y".* Three artifacts per rule:
1. `tools/eslint-plugin-quantalyze/rules/<name>.mjs` — the rule. Best analog:
   `no-raw-analytics-fetch.mjs`. Its detection strategy is **init-tracking, not name-matching**
   (a `VariableDeclarator` whose initializer references `process.env.ANALYTICS_SERVICE_URL` binds a
   TAINTED name; a `fetch()` whose first arg references a tainted name is reported), resolved at
   `Program:exit` so declaration order cannot hide a violation. It documents its own ceiling honestly:
   *"tainting is ONE hop"*.
2. `tools/eslint-plugin-quantalyze/tests/<name>.test.ts` — `RuleTester` with valid/invalid fixtures,
   run by the normal vitest suite (`vitest.config.ts` includes `tools/eslint-plugin-quantalyze/tests/**`).
   The header names its **discriminator fixture** ("renamed binding") explicitly.
3. `src/__tests__/contracts/contracts-registry.test.ts` — asserts (a) the plugin exports **exactly**
   the expected rule set, (b) `ESLint.calculateConfigForFile` **RESOLVES** the rule to `"error"` for a
   representative src file (not a config substring — an over-broad later `"off"` would defeat that),
   and (c) each allowlisted path resolves to NON-error, with the allowlist **frozen at 4**.

**Known gaps in `no-raw-analytics-fetch` (A-18 / D-14), confirmed by reading the rule:**
`const url = \`${base}/x\`; fetch(url)` — the template is not the fetch ARG, so the one-hop taint
misses it. `new URL("/x", base)` — `isFetchCallee` only matches `fetch`/`globalThis.fetch`, and the
first arg is a `NewExpression`, not a tainted identifier. Also unmatched: `fetch(url.replace(/\/+$/,"") + "/health")`
where `url` is one hop removed. **Both warmers use `${url.replace(...)}` inside a template — legal
today only because they are allowlisted.**

### Idiom B — registry-completeness by directory walk ⭐
`src/lib/api/limiter-ordering.test.ts`. Walks `src/app/api`, regex-detects every route that consumes
a limiter, and requires each to be classified into **exactly one** named bucket (`WRAPPER`,
`CANONICAL`, `NO_INPUT`, `PUBLIC_IP_EXCEPTION`, `WRAPPER_ADMIN`). *"A NEW limiter route that nobody
classified fails this test, forcing a conscious decision."* **This is the closest existing analog for
"every call site's budget key is pinned" and for "a health warmer provably cannot enter the core".**

### Idiom C — anchored grep gate over `readFileSync`d source
`src/__tests__/critical-regressions.test.ts` `[SD-CRITICAL-01]`: for each of the two clients, assert
`/resilientFetch\s*\(/` is present AND `/(^|[^a-zA-Z0-9_])fetch\s*\(/m` is absent, with a named
failure message. `seam-budgets.invariant.test.ts` documents the hygiene rule: the regex is
`/^export const maxDuration = (\d+)/m` — **`^` under `m` so a comment line cannot satisfy it**
(*"this phase hit prose-defeats-the-guard twice"*).

### Idiom D — committed-fixture cross-process parity with a literal roster ⭐⭐
`tests/lib/process-key-onboard-contract-parity.test.ts` + `analytics-service/tests/fixtures/*.json`.
