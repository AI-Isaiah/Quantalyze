## The cross-tenant proof — and why it is not `toBeDefined()`

`expect(headers["X-Tenant-Claim"]).toBeDefined()` is green against a mint that returns a constant, one keyed on the wrong secret, and one minting over an empty payload — that last being 140.1's mutation #3 shape, which shipped GREEN against an identity assertion.

**Worse: asserting "the two claim strings differ" is also insufficient.** Two claims that BOTH fail `compare_digest` also differ — and both land in the *same* `platform:<path>` bucket, which is the exact regression under test.

So the oracle is **the decision the other side actually makes**. `analytics-client.test.ts` contains `pythonBucketKey()` — a hand transcription of `verify_tenant_claim` + `tenant_or_platform_key` from `analytics-service/services/rate_limit.py`, imported from nothing on the TS side: `rsplit(".", 2)` via `lastIndexOf`, the 512-char cap, the empty-payload rejection, the `exp` check, `timingSafeEqual` for `compare_digest`, the `"public" → <scope>:anon` arm, and the `platform:<path>` fallback.

Five cases:

1. **Two tenants → two buckets** on `/api/optimize-weights`: `optimize_weights:t:tenant-a` vs `optimize_weights:t:tenant-b`, hand-typed, and explicitly `not.toBe("platform:/api/optimize-weights")`.
2. **The forgery is refused.** Splicing `tenant-b`'s payload onto `tenant-a`'s MAC — the attack of a caller holding a captured claim who wants B's window — degrades to `platform:/api/optimize-weights`. It does **not** become `optimize_weights:t:tenant-b`.
3. **All five live routes**, each driven twice, each asserted to its own `<scope>:t:<tenant>` with a named failure message.
4. **The wrong secret degrades silently** — verifying against `ANALYTICS_SERVICE_KEY` yields the platform bucket with no error on the Python side. This is why M44 must redden.
5. **An expired claim degrades** rather than being a permanent window credential.

## Fail-loud behaviour on a missing secret

`INTERNAL_API_TOKEN` is read at **call** time (`process.env.INTERNAL_API_TOKEN ?? ""`), never captured at module scope like the sibling `SERVICE_KEY` — which is the env-before-import ordering hazard `resilient-fetch.wiring.test.ts` documents. Here the failure mode is worse than an empty header: **an empty secret produces a syntactically perfect claim that simply fails `compare_digest`**, so every route silently reverts to `platform:<path>`, with no error, no warning (the Python arm deliberately does not WARN), and a fully green test suite.

`mintTenantClaim` therefore **throws**. Two consequences were designed for:

- **In `analytics-client`**, the mint is called **before** the transport `try`. Inside it, the `TenantClaimError` would have been caught and rewritten as `"Analytics service is not reachable"` — a config fault wearing a dying-Railway costume. Pinned by *"does not misreport a mint refusal as a dead upstream"*.
- **In `process-key-client`**, throwing was not an option: that function is typed `Promise<PostProcessKeyResult>` and has never thrown at any of its five caller routes, none of which has a catch. The refusal therefore takes the **same shape as the existing missing-token branch** — `console.error` + a clean 503, with `fetch` never called. Pinned by a new regression case asserting 503-not-502, zero fetches, and no secret in the log.

**Blast radius, stated honestly:** if `INTERNAL_API_TOKEN` is absent in production, every `analytics-client` route now **500s** and every `/process-key` route **503s**, instead of quietly degrading. That is the intended trade — see the ops question below.

## Decisions Made

Beyond the frontmatter list, two worth stating in full:

**The claim is NOT added to `seam-redaction`'s secret list — considered and rejected.** Plan 140.2-08's leaf reads secret VALUES at call time from a hand-typed NAME list that already includes `INTERNAL_API_TOKEN`. The claim is a **derived MAC** over a public user id with a 300-second life — a short-lived public credential, not a secret. Adding it would also be impossible to do correctly: the leaf redacts by env-var NAME, and the claim is per-request. Recorded here so a later reviewer does not read the omission as an oversight. (Threat register `T-140.2-09-04`, disposition `accept`.)

**The three inert routes mint anyway.** `/api/match/recompute` and `/api/match/eval` have no Python limiter at all (TS-21) and `/api/simulator` is the tenth, still-IP-keyed route (TS-30). A comment in `analyticsRequest` says so explicitly and says *do not optimise it away* — eight of nine is the instance-not-class defect this programme exists to close, and those routes become per-tenant for free the moment 146 adds their limiters.

### Auto-fixed / scope corrections

**1. [Rule 1 — plan's done-criterion is factually unsatisfiable] `grep -rn "createHmac" src/` cannot return one site**

- **Found during:** Task 1 verification
- **Issue:** The plan's done clause reads *"One mint implementation repo-wide (`grep -rn "createHmac" src/` shows it only in the new module)"*. That grep returns **eight** lines even at a correct end state: `src/lib/alert-ack-token.ts`, `src/lib/demo-pdf-token.ts` and `src/lib/pdf-render-token.ts` are three pre-existing, unrelated HMAC token systems (alert acknowledgement, demo PDF access, PDF render), plus the two test-side oracles this plan's discipline *requires*.
- **Fix:** Satisfied the honest criterion instead — exactly one **tenant-claim** mint. `grep -rn 'createHmac("sha256", secret).update(signed)' src/` → 1 line. Nothing was deleted or merged; touching the three unrelated token modules would have been scope creep.
- **Verification:** greps recorded above.

**2. [Rule 2 — class completeness] An eighth route call site: `admin/match/eval`**

- **Found during:** Task 2
- **Issue:** The plan enumerates **seven** call sites for the three wrappers needing identity. But making `tenantId` **required** on `analyticsRequest` — which is what stops a future tenth wrapper landing identity-less — forces *every* wrapper to supply one, and `evalMatch` had **no identity parameter of any kind**. Leaving it optional to avoid an eighth call site would have re-opened exactly the hole the requirement closes.
- **Fix:** `evalMatch(params, tenant)`; `src/app/api/admin/match/eval/route.ts` passes `user.id` from its already-present admin-gated session. The claim is inert there (no Python limiter) and the code says so.
- **Files:** `src/lib/analytics-client.ts`, `src/app/api/admin/match/eval/route.ts`

**3. [Rule 2 — security] `TenantIdentity` is an object, not a bare string**

- **Found during:** Task 2 design
- **Issue:** `validateKey(exchange, apiKey, apiSecret, passphrase?)` — adding `userId: string` puts two adjacent `string` parameters where a transposition **compiles cleanly** and mints the tenant claim over a **user-chosen OKX passphrase**: a credential in an outbound header, and every caller collapsed into one bucket keyed on it. That is threat `T-140.2-09-02` with the compiler unable to help.
- **Fix:** A one-field `TenantIdentity` interface for the four newly-threaded wrappers. Used on `optimizeScenarioWeights`/`evalMatch` too, for uniformity across the changed set. The five wrappers that already carried `actorId`/`userId` keep their existing string parameters — no adjacent secret, and churning them would be scope creep.

**4. [Rule 3 — blocking] `process-key-client`'s mint moved out of its transport `try`**

- **Found during:** Task 1
- **Issue:** Extraction added refusals to a call that previously **could not throw**, and the call sat inline in the headers object *inside* the classification window. A refusal would have been caught and returned as `UPSTREAM_NETWORK_ERROR` **502** — a config fault reported as a dead Railway.
