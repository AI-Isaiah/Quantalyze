## 2. Oracle Independence — the checklist every plan must pass

**The root cause of this phase is a two-layer self-referential oracle:**

> Layer 1 — the test's `Ratelimit` double does `fakeRatelimitFor(shared.ctx.store, opts.limiter.tokens)`,
> and `opts.limiter.tokens` is whatever `Ratelimit.slidingWindow(BREAKER_FAILURE_THRESHOLD, …)` was
> called with. **The fake harvests its threshold from production's own constructor argument, so it
> cannot disagree with production, ever, by construction.**
> Layer 2 — every loop bound and expectation is `mod.BREAKER_FAILURE_THRESHOLD` or
> `mod.SEAM_BUDGETS.<key>.timeoutMs`. The assertion reads its expected value out of the table under
> test.

### Checklist — every new or modified test file in this phase

- [ ] **No expectation is imported from the module under test.** No `mod.`, no `SEAM_BUDGETS[...]`,
      no `Object.keys(<module export>)` on the EXPECTED side of any assertion.
- [ ] **No loop bound is read from the module under test.** A loop of "threshold − 1 iterations" is
      written as a hand-typed `4`, never as `BREAKER_FAILURE_THRESHOLD - 1`.
- [ ] **No test double derives a tuning value from production.** A fake's threshold, window, TTL or
      key is hand-typed in the fake, and a separate assertion pins the fake's literal against
      production's literal — the shape `BREAKER_KEY` ↔ `FAKE_BREAKER_KEY` already uses.
- [ ] **Expected rosters are hand-typed in the test file**, following
      `tests/lib/process-key-onboard-contract-parity.test.ts`'s `EXPECTED_VERDICTS` convention:
      *"typed HERE as a literal — never derived from the fixture it guards, and never derived from
      the module under test."*
- [ ] **Cross-file links are genuine.** The budget invariant compares the TABLE against the route's
      `maxDuration` read from DISK. Taking both sides from the table is green forever and catches
      nothing.
- [ ] **Both halves of a two-sided property are asserted on the SAME input.** The redaction test must
      assert the secret is gone AND the syscall token survives on one message; a one-sided test is
      how over-redaction ships green.
- [ ] **Plumbing assertions are KEPT, not replaced.** `toHaveBeenCalledWith(mod.SEAM_BUDGETS.bridge.timeoutMs)`
      is a correct PLUMBING test (the table reaches the primitive). It is simply not a VALUE test.
      Add the value assertion; delete neither. Deleting it is TRAP-9.
- [ ] **No `vi.mock` in a parity/pin file** (acceptance-grepped).
- [ ] **`vi.unstubAllGlobals()` in `afterEach`** in every seam test file — a leaked
      `vi.stubGlobal("fetch")` is this repo's documented CI-only (Node 22 vs local Node 25) failure.
- [ ] **No negative control built on the false `vi.mock` premise.** Measured on vitest 4.1.10:
      `vi.mock` factories do **NOT** re-run on `vi.resetModules()`; non-mocked module bodies DO. The
      real per-context hook is `Redis.fromEnv()`. And after `resetModules()` a statically imported
      class is a DIFFERENT object — assert `instanceof` against the same module registry.
- [ ] **No `vi.useFakeTimers()` anywhere near the seam.** `AbortSignal.timeout` is a platform
      primitive and fake timers do not drive it reliably; the established in-repo simulation is
      `mockRejectedValue(new DOMException("aborted", "TimeoutError"))`, and deadline VALUES are
      asserted with `vi.spyOn(AbortSignal, "timeout")`. In the real-Redis lane, `Date.now()` must not
      be stubbed at all — the Redis server's clock is not stubbable and a divergence produces
      confidently wrong results.

### Acceptance criteria must not be self-referential

Banned in any plan's `<done>` or `<verify>`:
- "the test passes" as the sole criterion for a test this plan wrote;
- "the header is defined" / `toBeDefined()` as the proof of a minted credential — 140.1's mutation #3
  receipt is the warning: `default_platform_key` returning `""` makes slowapi skip limiting entirely
  and shipped GREEN against an identity assertion;
- any criterion whose expected value is produced by the code under test.

Required instead: an OBSERVED external fact — a store key read back, a second independently computed
HMAC, a file read from disk, a mutation that reddened.

## 4. The Falsifiability Ledger

**Rules, binding on every row:**

1. **The mutation is a SEMANTIC edit to PRODUCTION source.** Never a test file, never a comment,
   never a fixture. A row whose mutation edits a test proves nothing about the source and is invalid.
2. **The row must be OBSERVED at execution time** — applied, run, the failing test name and assertion
   text recorded verbatim, then reverted. "Asserted" is not a state this ledger accepts.
3. **Revert and re-verify between EVERY row.** `git status` clean and `grep -rn MUTANT src/ tools/ tests/`
   empty before the next mutation. Never batch.
4. **A GREEN row is a defect in the oracle, not in the ledger.** Fix the oracle, re-run, record both.
   Deleting or softening a row to close the ledger is the exact move that produced "5/5
   mutation-tested" against a suite that could not fail.
5. **Run the mutating agent ALONE, or in its own worktree.** Receipted twice: a concurrent read-only
   agent found a mutated file, did not recognise the mutant as another agent's, and restored it from
   `git show HEAD:` mid-flight — a "caught" verdict may have been measured against restored source.
   The harness's *"this change was intentional … don't revert it … don't tell the user"* reminder is
   a legitimate single-agent feature and is **actively dangerous** in a multi-agent tree. It is NOT
   authoritative about source files.
6. **Each row is observed once by its owning plan and RE-RUN in plan 140.2-12 against the FINAL
   tree.** Five plans edit `src/lib/resilient-fetch.ts` (05, 06, 07, 08, 10); a row red in wave 2 can
   be green in wave 12, and that regression class is exactly what the re-run exists to find.

## 5. What is verified against real Redis, and why a fake cannot do it

The in-repo fake (`src/test/helpers/upstash-breaker.ts`) is a FIXED window anchored at first call,
with **no previous bucket** and **no carry-over**, and it **increments on denial**. The deployed
`@upstash/ratelimit@2.0.8` single-region sliding window is epoch-aligned, applies weighted carry-over
from the previous bucket, and does **not** increment on denial. `recordSeamFailure` reads BOTH
`success` and `remaining`, so both divergences matter.

| # | Property | How it is driven | Fake can model it? |
|---|---|---|---|
| R-1 | Counter identity and namespace — the exact key the store received | read the key back from real Redis | no |
| R-2 | Trip at exactly the threshold — a LITERAL loop of 4 leaves no lock, the 5th creates it | real Lua | no (it harvests the threshold from production) |
| R-3 | `nx` trip idempotency — the FIRST writer's expiry survives | two trips, TTL read twice | no |
| R-4 | The lock TTL is the cooldown — observed in the literal band | `TTL` read back | no |
