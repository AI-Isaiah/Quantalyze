## The cap: 10, and the two independent bounds that fix it

Both are stated in the constant's docblock in the route, not only here.

- **PRODUCT.** Real composites are small — the largest receipted book is a
  three-key venue stitch, and the wizard's multi-key connect step exists to
  combine a handful of accounts. **Nine usable** members (see below) is ~3x the
  largest composite anyone has built. There was **no pre-existing product cap
  anywhere** — grepped `src/`, `supabase/`: no `MAX_KEYS`, no member-count
  constraint on `strategy_keys`, nothing in `composite/add-key`. The number is
  therefore chosen here, not inherited.
- **THE FUNCTION CEILING.** In the breaker's FAILING state each member costs
  `15 000` request + `3 × 4 250` store = **27 750 ms**. Eleven members is
  **305 250 ms** and BREACHES the declared 300 000 ms; ten is **277 500 ms** and
  fits. So 10 is the largest cap that keeps SC-4b true in every breaker state,
  and the invariant recomputes exactly that arithmetic.

**The usable maximum is 9, not 10, and that is deliberate.** `.limit(10)` cannot
distinguish "exactly ten members" from "more than ten, truncated", so the tenth
is spent as a tripwire. Refusing a genuine ten-member draft is recoverable;
finalising a composite whose eleventh member key was never re-probed is not — it
is the connect→submit scope-broadening hole the O-1 loop exists to close,
reintroduced by a silently short list.

`>=` rather than `===` on purpose: if the `.limit()` were ever dropped, the arm
still refuses an oversized list rather than fanning out over it.

## How the cap interacts with wave 7's budget invariant

Wave 7 established, per route:

```
worstCase(state) = Σ ( timeoutMs × calls × (1 + row.retries) )
                 + storeCommands(state) × 4 250 ms × seamCalls
storeCommands: closed 1 · open 1 · failing 3     (hand-counted from the core)
```

**That formula is UNCHANGED. It is now evaluated per BRANCH and maximised**, and
the row's `budgets` legs carry an optional `branch` label:

```
worstCase(state) = MAX over branches of [ the wave-7 formula over that branch's legs ]
```

An **unlabelled** row is one implicit branch — literally the wave-7 sum — so
fourteen of the fifteen rows are byte-unchanged in both declaration and computed
value. An unlabelled leg on a *labelled* row is shared and charged to every
branch (no row uses that today; the semantics are defined rather than left open).

**Why a MAX and not a bigger sum.** Summing both branches at the cap gives
`165 000` request over `11` seam calls = **305 250 ms failing** — a false breach
describing a request that cannot exist (a composite has `api_key_id IS NULL` by
construction; the fan-out hoist is scoped to exactly that, and the single-key
enqueue arm is unreachable from it). Modelling the max is what makes a cap of 10
both true and provable. RESEARCH §11 named "a per-branch shape **or** a
worst-case row that names the composite fan-out"; the per-branch shape was taken
because it keeps the single-key legs declared — which is what keeps **ledger row
M24** ("drop the `process-key-enqueue` leg from the finalize-wizard row")
reachable for plan 140.2-12's re-run.

### RECOMPUTED SC-4b headroom (07's numbers were written with `calls: 1`)

The honesty docblock in `seam-budgets.invariant.test.ts` was **updated, not left
standing**. Before/after, against the on-disk 300 000 ms ceiling:

| state | validate-and-encrypt (3 calls) | finalize-wizard — 07's row | finalize-wizard — this plan (composite) |
|---|---|---|---|
| closed | 132 750 ms | 38 500 ms | **192 500 ms** |
| open | 12 750 ms | 8 500 ms | **42 500 ms** |

- `finalize-wizard`'s single-key branch is unchanged (38 500 / 8 500 / 55 500)

- **No assertion was widened and no ceiling was raised.** The corrected worst

## Deviations from Plan

**1. [Rule 2 — Missing critical] The invariant needed a branch MECHANISM, not a hand-computed max**

- **Found during:** Task 2
- **Issue:** The plan says "the declared worst case is the MAXIMUM over the two mutually exclusive branches". `SEAM_ROUTE_BUDGETS`' shape is a flat array the invariant SUMS, so the only way to express a max in that shape is to declare the dominating branch alone and delete the other's legs — a max computed by hand at authoring time. Two problems: (a) the dominance silently inverts if the cap is ever lowered below 3, and nothing would notice; (b) deleting the `process-key-enqueue` leg makes **ledger row M24** unreachable, and an unreachable row silently skipped is an asserted row wearing a different hat (VALIDATION §4).
- **Fix:** Added an optional `branch` label to the leg shape and made the invariant group-then-maximise. Fourteen rows are unlabelled and byte-unchanged.
- **Verification:** SC-4d deep compare green against the hand-typed roster; a dedicated anti-vacuity case pins that exactly ONE row is multi-branch and that its labels are `["composite","single-key"]` (deleting the labels turns MAX back into SUM, the over-stating direction no headroom assertion would notice on its own).
- **Committed in:** `ce229318` / `402714df`

**2. [Rule 3 — Blocking] The cap constant cannot be `export`ed from a Next route module**

- **Found during:** Task 1
- **Issue:** The plan's behaviour note says "exported or otherwise readable". A `route.ts` export surface is validated against the route-segment contract, so an extra export is a build error.
- **Fix:** Took the "otherwise readable" arm — the invariant reads `^const MAX_COMPOSITE_MEMBERS = (\d+)` from disk with the same anchored-regex idiom the file already uses for `maxDuration`. Stated as the reason in both files.
- **Verification:** M47 reddens the binding; the reader throws a named error if the declaration disappears.
- **Committed in:** `0a73a959` / `402714df`

**3. [Rule 2 — Missing critical] The route's `maxDuration` docblock named only the single-key branch**

- **Found during:** Task 2
- **Issue:** It said "this route spends TWO budgets — the keys-permissions probe, then the process-key enqueue". That is the branch this plan proved the table was wrongly modelling; leaving it is the stale-comment-beside-a-corrected-branch shape this programme has receipted.
- **Fix:** Rewritten to name both branches and which one can reach the ceiling.
- **Committed in:** `ce229318`

**4. [Rule 2 — Missing critical] Registry text updated for the changed guard**

- **Found during:** Task 2
- **Issue:** `CONTRACT_GUARDS` and `REGISTRY.md` described the invariant as a plain sum. A registry that describes a guard it no longer matches is worse than no registry.
- **Fix:** Both entries now describe the branch MAX and SC-4e, and name ledger rows M24/M32/M41/M47.

## Found but NOT fixed

1. **The cap arm's user-facing copy is wrong for a permanent condition, and
   deliberately so.** It returns the EXISTING `COMPOSITE_MEMBERSHIP_UNKNOWN`
   envelope verbatim — "A transient check couldn't determine whether this draft
   is a multi-key composite… try again" — because this phase authors no
   user-facing copy and a new `code` would require a new entry in
   `wizardErrors.ts`'s copy registry (title/cause/fix), which is 140.3's fence.
   A user with an oversized composite will be told to retry, and retrying will
   loop. **Recommend 140.3 give this arm its own code and copy**; the operator
   half is already distinct (`step: "composite-member-cap"` + a dedicated log
   line naming the cap).
2. **The count probe and the list read are two separate reads and can disagree.**
   `compositeMemberCount` (a `head+count` query) is uncapped by design — a count
   is one row of wire regardless — and the cap is enforced on the LIST read. A
   draft with 50 members passes the count gate and is refused at the list gate,
   which is the correct order (the refusal is cheaper than the fan-out) but means
   the count is not itself a bound. Recorded, not changed: capping the count
   query would make `>0` unanswerable.
3. **There is still no product-side cap on composite membership.**
   `POST /api/strategies/composite/add-key` will happily add an eleventh member;
   the user only discovers the wall at submit. The seam-side tripwire is the
   correct place for a *budget* bound, but a wizard-side "you can combine up to
   9 keys" gate is missing and would be a better user experience.
4. **`EquityChart.tsx` `react-hooks/exhaustive-deps` warning** — pre-existing,
   unrelated file, out of scope. Not touched.
