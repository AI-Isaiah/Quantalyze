# Phase 140.2 Plan 07: Bounded Breaker Store, the A-09 Sentinel, Single-Read State and No-Re-Arm — Summary

Closed four live breaker defects at once: an unbounded Upstash client (A-04), a
fail-open timeout sentinel that **was tripping the breaker on one failure**
(A-09), a two-read state check that could deny a healed circuit or discard a
known-open one (A-24), and an expired lock that a doomed in-flight request could
re-arm (A-25) — then put the store's own wall clock into the route budget
invariant in all three breaker states.

## The A-09 proof — failing without the fix

The RED run at `fe30c4f8`, before any core change:

```
FAIL src/lib/resilient-fetch.test.ts > recordSeamFailure
     > [SEAMCORE-04 / A-09] a SLOW store does not trip the breaker
AssertionError: A slow Upstash tripped the breaker. […]
  expected { value: 'open', …(1) } to be undefined
```

`{ value: 'open' }` **is the lock, written by HEAD.** With `@upstash/ratelimit`
resolving its own fail-open sentinel — `{ success: true, limit: 0, remaining: 0,
reset: 0, reason: "timeout" }`, read at source in `dist/index.mjs` `applyTimeout`,
fired by a `timeout` that defaults to 5 000 ms — the core's
`if (success && remaining > 0) return;` fell through and armed the circuit. One
recorded failure plus one slow Upstash was a full trip. This was live, not
hypothetical.

Two controls keep the fix honest:

- **Negative control** — "genuine exhaustion still trips on the threshold-th
  failure" (hand-typed 4 then the 5th). A guard that returned early on *every*
  result would satisfy the sentinel case while disabling the breaker; this
  refuses that.
- **M27** — deleting the guard reddens the sentinel case and nothing else.

**Discriminator chosen: `reason === "timeout"`, not `limit === 0`.** Both identify
the sentinel today, but `reason` says *which* fail-open the library took, and
that distinction is load-bearing: `"cacheBlock"` is the other path that answers
without touching Redis, and it is a **genuine denial that must still trip**. A
`limit === 0` test is correct today only because the cacheBlock path happens to
carry a real limit.

## The signal-form choice, with its abort-semantics rationale

**FACTORY (`signal: () => AbortSignal.timeout(…)`).** Two independent reasons,
both read at source in `node_modules/@upstash/redis/chunk-2X4SLXT7.mjs`:

1. `signal: isSignalFunction ? signal() : signal` is evaluated once per
   `request()`. A single `AbortSignal` **instance** is therefore already-aborted
   on the second store command.
2. The abort branch differs:
   `if (requestOptions.signal?.aborted && isSignalFunction) throw error_;` —
   the factory form **RETHROWS**. The plain form takes the `else` and fabricates
   `new Response(blob, { status: 200 })` whose body is `signal.reason ?? "Aborted"`.
   That fabricated 200 would make an aborted `mget` look like a *successful* read
   of values that are not locks (harmlessly fail-open) and an aborted `set` look
   like a lock that **was written** — an unarmed breaker reported as armed.
   The read direction's wrong answer is this module's doctrine; the write
   direction's is a lie. Recorded in the client's docblock naming the
   fabricated-200 behaviour, as the plan required.

**⚠️ Correction to the plan's premise, recorded rather than smoothed.** The plan
and `<interfaces>` describe "a per-attempt store timeout". The SDK builds
`requestOptions` **before** the retry loop, so the factory is evaluated once per
**command** and all of that command's attempts share one deadline; the true worst
case per command is nearer `TIMEOUT + one backoff` than `attempts × TIMEOUT`.
SC-4b nonetheless charges `attempts × TIMEOUT + retries × BACKOFF`, which
**over-states** the cost — the safe direction for a headroom assertion. Stated in
both the constant's docblock and the invariant test rather than implied.

## The A-25 mechanism, and why the plan's alternative does not work

The plan offered two: *"skip the trip WRITE when the breaker is already open, or
record only when the request STARTED after the current lock was armed. Pick
one."*

**The first does not close A-25.** Re-read the scenario: a call admitted at t=0
under a 60 s budget fails at t≈60; the lock armed at t≈0 **expired at t=30**. At
t=60 the breaker is *not* open, so an is-open guard passes — and `nx` succeeds,
which is exactly today's behaviour. An is-open guard is a restatement of `nx`,
not a fix. Implemented the second, and recorded the rejection in source.

**It required making the question answerable.** With `ex: BREAKER_COOLDOWN_S` the
expired lock is simply *gone* at t=60. So the lock KEY now outlives the lock it
carries by `BREAKER_LOCK_TOMBSTONE_S = 60` (key TTL 90 s), and the value stores
`armedAt` explicitly rather than deriving it from `expiresAt − cooldown`.

**This is not gold-plating — it is what makes the encoding load-bearing at all.**
Under `ex: cooldown`, the encoded expiry could *never* be in the past while the
key still existed, so `now < expiresAt` would be true whenever the key was
readable and the whole encoding would be decorative. M30 is only falsifiable
because the tombstone exists.

Tombstone sized from evidence: the guard must span the longest budget in
`SEAM_BUDGETS` (`process-key-sync`, 60 000 ms) measured from a lock's arming, and
`cooldown + tombstone = 90 s ≥ 60 s`. Pinned both as a literal and as that
inequality.

**Wiring.** `resilientFetch` captures `admittedAtMs` immediately after the
open-check and passes it through `recordOnce`. `recordSeamFailure`'s parameter
defaults to `Date.now()` (i.e. "admitted now" = guard off), which is the
fail-open degradation and keeps the real-Redis lane's ~20 call sites compiling.
That default is a risk, so the wiring is pinned by its own case — and by M40b.

## The budget invariant, in all three states

```
worstCaseMs(state) = Σ over the row's budgets of ( timeoutMs × calls × (1 + row.retries) )   [request]
                   + storeCommands(state) × STORE_COMMAND_WORST_CASE_MS × (total seam calls)  [store]

STORE_COMMAND_WORST_CASE_MS = (1 + 1) × 2 000 + 1 × 250 = 4 250 ms
```

Store commands per seam call, hand-counted from the core:

| state | commands | what they are | request budget spent? |
|---|---|---|---|
| **closed** | 1 | the pre-fetch `mget` (ONE since this plan collapsed the `ttl`) | yes |
| **open** | 1 | the same `mget`; the call then throws `CircuitOpenError` before `fetch` | **no** |
| **failing** | 3 | that `mget` + the trip path's `get` (the A-25 guard) + its `set` | yes |

Headroom against the 300 000 ms ceiling:

| state | worst route (validate-and-encrypt, 3 calls) | 2-call route (finalize-wizard / create-with-key) |
|---|---|---|
| closed | 120 000 + 12 750 = **132 750 ms** | 30 000 / 60 000 + 8 500 = **38 500 / 68 500 ms** |
| open | 0 + 12 750 = **12 750 ms** (headroom 287 250) | 0 + 8 500 = **8 500 ms** (**headroom 291 500 ms**) |
| failing | 120 000 + 38 250 = **158 250 ms** (headroom 141 750) | +25 500 = **55 500 / 85 500 ms** |

The ceiling side stays `readFileSync` of each route's own `export const
maxDuration` — that disk read is now the *only* independent side, since the store
terms are read from the core (they must be, or M41 could not redden). The
honesty docblock was **updated, not deleted**: it still says this is not a tight
guard, now with the post-store numbers and a third stated job — "to fail if the
store's own bounding is loosened, which previously changed a route's real worst
case while changing nothing this file could see".

The `failing` figure is deliberately pessimistic: the trip path runs once per
threshold failures, not per failure, and the limiter's default in-memory
`ephemeralCache` can short-circuit recordings without reaching Redis at all
(wave 1's finding, wave 6's decision). Charging every seam call the full three is
the safe direction, and nothing added here assumes a guaranteed Redis round trip
per `recordSeamFailure` — the extra `get` sits on the **trip path only**, which
is why the ephemeralCache decision is untouched.

**BEFORE** (`resilient-fetch.ts`, false):

> …and because TTL expiry IS the half-open transition, this value is **the
> entire recovery latency of the system.**

> ⚠️ THIS IS **NOT** THE RECOVERY LATENCY OF THE SYSTEM, AND THIS DOCBLOCK USED
> TO SAY IT WAS. […] The counter is never cleared on a trip […] so whether ONE
> failure immediately re-trips depends on WHERE in that bucket the original trip
> landed.
>
> | trip at position p | carry-over floor((1−p′)·5) | one failure at +32 s |
> | 0.05 | 4 ⇒ remaining 0 | RE-TRIPS instantly |
> | 0.50 | 2 ⇒ remaining 2 | does NOT re-trip |

> ACCEPTED, not a defect to fix here. The obvious remedy — clearing the counter

**Source of the number:** `140.2-01-SUMMARY.md` § "The OBSERVED R-7 recovery band

32 s** and reached opposite outcomes. Taken verbatim; **not re-derived and not
guessed** (`140.2-VALIDATION.md` §5: correct the docblock to match the

**`DEFAULT_RETRY_AFTER_S`**: its docblock named "the key expired between the

   call shape became a type error and every site had to state its meaning. The
   same argument applies here, and I did not follow it: making it required would
   have forced edits to ~20 real-Redis-lane call sites and ~15 unit-test calls,
   beyond this plan's V-6 mandate. The default (`Date.now()` = "admitted now" =
   guard off) is the fail-open degradation, and M40b pins the one production
   path — but a *future* call site can silently lose the guard. **Recommend a
   follow-up making it required.**

   pre-plan code write the bare `"open"`, which new instances read as CLOSED.
   Bounded (at most one cooldown, fail-open direction) and documented in
   `decodeBreakerLock`, but it is a real transient.
