### OB-8, and why it needed three controls

The positive case alone is indistinguishable from "the seed never opened anything at all" — the
seeded-key-nobody-reads failure (TRAP-9) this plan's casualty list exists to prevent. So:

1. `with breaker:mt5-gateway open, a call declaring only supabase still reaches Railway` — the criterion.
2. `NEGATIVE CONTROL: the SAME seeded key DOES block a call site that declares it` — `validate-key`

3. `NEGATIVE CONTROL: the declared dependency's own key DOES block the call` — seeded at TTL **21**,

   *something* was open).
4. `the residual global key still blocks EVERY call site, declared set or not` — narrowing the blast
   radius must not remove the Railway-wide stop.

## 6. R-1: the re-expression judgement (and it is not a relaxation)

| | Counter key shape |
|---|---|
| **Old (wave 1)** | `breaker:breaker:railway:failures:<epoch window index>` |
| **New** | `breaker:<breaker key>:failures:<epoch window index>`, where `<breaker key>` is `breaker:railway` for a failure naming no dependency and `breaker:<dependency>` for a counting 503 that does |

*(The doubled `breaker:` is the limiter's `prefix` meeting the key, not a typo.)*

**Judgement: RE-EXPRESSION, and additionally a STRENGTHENING.**

- The property pinned is **unchanged**: "the store received exactly the key we think it did."
- The assertion form is **unchanged**: an EXACT key-set equality (`toEqual`), never a prefix match and
  never a `contains`. That distinction is load-bearing — a substring check would pass a key built from
  a caller-influenced value, which is precisely threat T-140-01.
- **Strengthened** because the new shape admits a failure the old could not express: R-1 now drives
  **two** keys in one case with **two different counts** (4 global, 3 mt5-gateway) and asserts both
  identities and both values. Equal counts would still have passed had the identifiers collapsed and
  the reads lined up; unequal counts cannot.
- The rest of the lane was re-expressed mechanically (`recordSeamFailure(LOCK_KEY)`,
  `isBreakerOpen(LANE_BUDGET_KEY)`), which **tightens** the lane's own oracle rule: the key and budget
  key are now hand-typed literals at every call site rather than defaults.

**M20 → M20R naming.** M20's original identifier `` `${BREAKER_KEY}:failures` `` ceased to exist at
this wave, so the row was not skipped — M20R (already in `140.2-VALIDATION.md`) targets the same
property under the new shape and was observed below. An unreachable mutation silently skipped is an
asserted row wearing a different hat.

## 7. The ephemeralCache decision

`@upstash/ratelimit@2.0.8` defaults `ephemeralCache` to a **live in-memory `Map`**
(`dist/index.mjs:757-761`, verified at source) and `resilient-fetch.ts` omits the option. After a
DENIED `limit()` the limiter calls `ctx.cache.blockUntil(identifier, reset)` and every later call for
that identifier short-circuits in memory, never reaching Redis until the bucket ends.

**DECISION: leave it at the default.** Three reasons, all now written into the limiter's docblock:

1. **The block is keyed by IDENTIFIER, and identifiers are now per-dependency.** So the in-process
   suppression became per-dependency at the same moment the counters did — it now **agrees** with
   OB-8 instead of cutting across it. Under the old single global identifier, one denial muted that
   instance's counting for *everything*.
2. **It cannot cause an under-trip.** It only engages after a denial, and a denial only happens once
   the threshold is already exceeded — i.e. after that key's circuit has tripped. The trip itself is a
   direct `redis.set` **outside** the limiter, so it still lands.
3. **`ephemeralCache: false` is a semantic change to the deployed breaker** — it re-arms a Redis round
   trip per failure during precisely the correlated incident the breaker exists for, and it would
   invalidate the drain machinery R-3/R-6/R-7 are built on. That belongs to a plan that owns the
   breaker's timing behaviour.

**The binding consequence, recorded for 140.2-07:** nothing in this module may assume
`recordSeamFailure` performs a Redis round trip. The implementation shipped here does not.

## 8. The double-record closure (wave 5's deferred interaction)

**Closed with a per-request latch**, not an ordering rule — the arms cannot be ordered, because the
body read happens whenever the CALLER chooses to read it, arbitrarily later:

```
let recorded = false;
async function recordOnce(breakerKey) { if (recorded) return; recorded = true; await recordSeamFailure(breakerKey); }
```

All three counting arms (transport catch, status verdict, body-read) go through it; `recordOnce` is
passed into `instrumentBody`. **Why it matters:** a counting status AND a body that then aborts are
two arms observing ONE degraded request. Recording both halves the failures needed to trip, so five
genuinely-distinct incidents' worth of protection would fire after two or three — a breaker that opens
early is still an outage it created itself.

Receipt: `a counting status whose body then aborts records EXACTLY ONE, not two` — asserts
`limitCalls === 1` after the status arm, then `=== 1` again after the body read throws
`SeamBodyReadError`. Wave 5's existing "exactly ONE" SC1 case (headers OK, body aborts, status 200)
still passes unchanged.

The body-read arm's key comes from `seamBreakerVerdict(null)` — the same ONE definition of "no status
line, therefore global" the transport arm uses, rather than a second hardcoded literal.

## 9. The 503 dependency peek — a design point worth flagging

The core cannot read the caller's body (status interpretation is the caller's contract), so the peek
goes through `res.clone()` and **only on a 503**. Properties, all documented at
`readDependencyBody`:

- An absent, `text/plain`, truncated or aborting body degrades to the global key and **still counts**.
  The peek can only ever make a key MORE specific; it can never decide whether to record. That is what
  keeps TRAP-2 closed with the refinement in place.
- The read is bounded by the same `AbortSignal.timeout` deadline (the clone shares the stream), so a
  503 whose body never arrives costs the remaining budget here instead of at the caller — the same
  wall clock, moved earlier. **This is a real behaviour change on that path** and is called out rather
  than buried.
- The `typeof res.clone === "function"` check is not decoration: `SeamResponse` is deliberately
  structural so route tests can stub the core with `Response`-shaped objects, and several existing
  fixtures are bare `{ ok, status }` literals. A missing `clone` degrades to the global key rather than
  throwing inside the classification window.
