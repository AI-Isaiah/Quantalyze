## TRAP-9 assertion swaps — recorded verbatim

Two existing cases in `strategyGate.test.ts` **pinned the fall-through this plan closes**. Both were replaced by strictly stronger assertions in the same commit (`d1e4521a`), and the replacement block carries a comment naming both originals so the swap is visible at the source.

**Removed #1 (verbatim):**
```ts
  it("skips the day-span check when latest < earliest (computeSpanDays returns null on negative delta)", () => {
    // M-0572: a corrupt trades table where latestTradeAt < earliestTradeAt
    // yields a negative delta → computeSpanDays returns null → the
    // `spanDays !== null` guard SKIPS the day check entirely. With analytics
    // complete + enough trades, the gate currently PASSES (no temporal
    // validation). This pins the documented current behavior so a future
    // change (e.g. a new code that rejects corrupt timestamps) is a
    // deliberate, test-visible decision rather than a silent drift.
    ...
    expect(result.passed).toBe(true);
    expect(result.code).toBeNull();
```
**Replacement:** `it("REFUSES (throws) when latest < earliest — a corrupt span is unrepresentable, not a pass")` — same input, `expect(...).toThrow(/unreadable/i)`. Strictly stronger: `passed:true` is admitted by exactly one behaviour, the throw by exactly one, and the new one is the safe direction. The removed case's own comment asked for precisely this ("a deliberate, test-visible decision rather than a silent drift") — this is that decision.

**Removed #2 (verbatim):**
```ts
  it("skips day-span check when trade timestamps are missing", () => {
    // A strategy with >= 5 trades reported by count but no timestamps
    // should still pass if analytics are complete. This handles the
    // edge case where the trades count is fetched from a head query
    // but the timestamp query returned no rows due to an ordering bug.
    ...
    expect(result.passed).toBe(true);
```
**Replacement:** `it("REFUSES (throws) when trades exist but the timestamps are missing — the C-3 publish-side fail-open")`. Note the removed case's stated premise — *"the timestamp query returned no rows due to an ordering bug"* — **is the defect**: it documents a failed read and then asserts the gate should pass anyway.

**Route test file: zero `it(` removed** (`git diff -U0 ... | grep -c '^-.*it("'` → 0). The clean-approve and both genuine-rejection cases are byte-unchanged.

## Why a throw rather than a new `GateFailureCode`

Recorded because the alternative is **not wrong** — it is out of scope for this wave.

1. A new code forces a `gateFailureToWizardError` arm and a `WIZARD_ERROR_COPY` entry in `src/lib/wizardErrors.ts`. Plan `140.4-03` owns that file in this wave, and two plans editing one file in one pass is TRAP-8 verbatim.
2. It would require **inventing user-facing copy**, which is founder-owned (CONTEXT §7.1). A throw authors no sentence.
3. Both consumers already have a fail-loud path for a throw: the wizard's heavy arm catches and escalates through `heavyFetchErrorsRef`; the admin route gained an explicit narrowed catch here.
4. A code is a *verdict about the strategy*. The whole finding is that we were answering about the strategy when the failure was ours. A refusal is the honest type.

## Decisions Made

1. **Throw, not a new `GateFailureCode`** — full reasoning above.
2. **PGRST116 is an absence, not a failure.** `.single()` reports "0 rows" as an error object.
