## What changed

### Task 1 — the chokepoint stops detaching (`c05da8d5`)

`captureToSentry`'s return type went `void` → `Promise<void>` and the `void import(...)`
became `return import(...)`, copying `audit.ts`'s `reportToSentry` exactly. Everything else
is preserved: the unconditional chokepoint scrub before the import, both swallowing
catches, the outer `try`/`catch`, the default level. The outer catch now returns
`Promise.resolve()` so `await` and `after(...)` are total on every path.

Source-compatible, as designed: **no call site outside this plan changed** and
`npx tsc --noEmit` exits 0 across all 109.

Five behaviour cases added. They deliberately do **not** use the file's existing
`nextCapture()` helper — that helper polls with `vi.waitFor`, which observes the capture
whether the chain was returned or detached. Polling is precisely what a reaped lambda
cannot do, so the only valid oracle is awaiting the return value and nothing else.

### Task 2 — the three sinks and the third posture (`67b2c01a`)

`resilient-fetch.ts` gained a module-local `scheduleSeamCapture(capture, event)` carrying
`audit.ts`'s `try { after(...) } catch { console.warn(…); queueMicrotask(…) }` shape
verbatim, called from the three enumerated sinks:

| Sink | Level | Posture (unchanged) |
|---|---|---|
| `emitBreakerTransition` (open **and** close) | `warning` | — |
| `isBreakerOpen`'s catch | `error` | still returns `{ open: false }` — fails OPEN |
| `recordSeamFailure`'s catch | `error` | still swallows |

`ratelimit.ts`'s `checkLimit` now destructures `reason` alongside `success`/`reset`. On the
timeout sentinel it logs a structured warn, captures at `warning`, and returns
`{ success: true }` **unchanged**. The identifier is deliberately neither logged nor
captured: it is a user id or client IP, and the event says nothing about *who* was let
through, only that the cap went unenforced.

Diff confined to `checkLimit` and its imports, so plan `140.4-13`'s later-wave change to
this file does not collide.

#### The rewritten `emitBreakerTransition` docblock, verbatim

```
/**
 * Emit one transition.
 *
 * ⚠️ THIS DOCBLOCK USED TO SAY *"A PLAIN STRUCTURED LOG, deliberately — it
 * performs no I/O, so there is nothing to await and TRAP-7 … cannot apply. If
 * this ever gains a network sink it must become an awaited call at both sites."*

 * itself is live: the capture is SCHEDULED with `after()` rather than fired and
 * forgotten. A bare fire-and-forget promise is orphaned by the Fluid Compute

 * incident the alert exists for (TRAP-7). `after()` hands it to `waitUntil`,
 * which holds the instance alive until the capture settles; that only works
 * because `captureToSentry` returns its import chain rather than detaching it
 * (`audit.ts`'s NEW-C10-03, re-created in `sentry-capture.ts` and fixed in plan
 * 140.4-06).

 * the Vercel function log without a Sentry round trip — and the capture is the
 * remote one. Replacing either with the other is a regression, so both are
 * asserted.
 *

 * same reason: a breaker transition is an operational fact, and the OPEN half is
 * a mitigation working. Routing it to `error` would make every recovery look
 * like a fault.

```

#### The three limiter postures, as commented in `checkLimit`

1. **FAIL-CLOSED** — an HTTP-5xx (or any rejection) from the store. `@upstash/redis` does
   not retry a non-ok HTTP response, so the rejection arrives promptly and production
   answers `ratelimit_misconfigured` → 503.
2. **FAIL-OPEN, plus up to 5 s of the user's latency** — a hanging store. The SDK never
   rejects; `applyTimeout`'s sentinel wins the race and says *let it through*. The cap is
   **not** enforced for that request.
3. **NON-DETERMINISTIC** — a refused socket, where the SDK's ~4.29 s retry ladder races the
   5 s sentinel and either of the above can win.

**None of the three is changed by this plan.** Posture 2 was *silent*; it is now recorded.
