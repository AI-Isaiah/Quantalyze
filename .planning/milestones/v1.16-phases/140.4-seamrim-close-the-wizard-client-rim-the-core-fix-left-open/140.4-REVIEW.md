## Critical Issues

### CR-01: The CSV double-submit fence silently merges a *different* submission into an existing strategy, and reports 200

**Files:**
`analytics-service/routers/process_key.py:1121-1176`
`src/app/api/strategies/csv-finalize/route.ts:1280-1307`
`supabase/schema/functions/persist_csv_daily_returns.sql:87-93`
`src/lib/wizardErrors.ts:887,933`

**Issue.** The 23505 arm re-fetches the existing `strategies` row by
`(user_id, wizard_session_id, source='csv')` and echoes its id at 200 — **without comparing the
request to the row it resolves to**. The route then runs `applyCsvMetadataUpdate` and
`persistDailyReturnsOrErrorResponse` against that id with *this* request's payload
(`route.ts:1283-1303`), and `persist_csv_daily_returns` is an
`INSERT … ON CONFLICT (strategy_id, date) DO UPDATE` with **no delete of rows outside the new
range**. `strategies.name` is set only by the RPC's `INSERT`; it is not in the metadata update
payload (`route.ts:451-499`), so a changed name is silently dropped.

The wizard cannot distinguish a *repeat* from a *changed resubmit*, because
`wizardSessionId` is stable across both: `clearWizardState` fires only on success /
delete-draft / start-fresh, which is stated verbatim as load-bearing at
`localStorage.ts:390-393`. Pre-140.4 a changed resubmit minted its own strategy (that was
C-2, correctly closed); post-140.4 it lands on the first one.

**Concrete failure scenario.**

1. User names the strategy *"Alpha 2024"*, uploads `2024.csv` (Jan–Dec 2024) and submits.
   `finalize_csv_strategy` creates strategy **S** and its `strategy_verifications` row.
2. `applyCsvMetadataUpdate` rejects the metadata (`NEW-C14-03/04/05`, a 400) **or**
   `persistDailyReturnsOrErrorResponse` hits a PostgREST 5xx (a 500) **or** the browser times
   out (`CSV_NETWORK_TIMEOUT`). **S exists.** The user sees `CSV_SUBMIT_FAILED`, whose fix line
   (`wizardErrors.ts:887`) reads: *"If it is not listed, submit again. Submitting again from this
   same wizard cannot create a second copy — a repeat submit resolves to the strategy that
   already exists."*
3. The user steps back in the wizard, renames to *"Alpha 2025"*, uploads `2025.csv`
   (Jan–Dec 2025), and submits.
4. `finalize_csv_strategy` raises 23505. `process_key.py:1168-1175` answers
   `{ok: true, strategy_id: S, status: …}`. The route upserts 2025's rows onto **S**.

**Result:** strategy **S** is named *"Alpha 2024"*, carries **2024 ∪ 2025** returns (2024's rows
survive — the upsert only touches conflicting dates), carries 2025's metadata, and the wizard
navigates the user to `/strategies` reporting success. On a product whose core value is a
trustworthy verified track record, that is a fabricated series presented as verified, with no
signal to the user or the operator (`process_key.csv_finalize_idempotent_hit` logs only the id).

**Grading.** BLOCKER: data integrity on the published artefact, silent, and newly reachable
*because of* this phase's fence. The idempotency decision itself is correct — the defect is that
the arm asserts idempotency without establishing the precondition.

**Fix.** Make the arm idempotent *for the request it was given*, or refuse. Minimum viable:
compare the echoed row to the request before answering 200, and answer the existing
`WIZARD_DUPLICATE` vocabulary otherwise.

```python
# analytics-service/routers/process_key.py — inside the 23505 arm
existing = one(
    user_sb.table("strategies")
    .select("id, status, name")           # + name
    .eq("user_id", user_id)
    .eq("wizard_session_id", wsid)
    .eq("source", "csv")
    .maybe_single()
    .execute()
)
if existing and existing.get("name") != strategy_name:
    # NOT a repeat — a DIFFERENT submission wearing the same session id. Echoing
    # the old row would attach this file to that strategy and drop this name.
    log.warning(
        "process_key.csv_finalize_session_reused_with_new_payload",
        strategy_id=str(existing["id"]),
    )
    return JSONResponse(
        status_code=409,
        content=_envelope_error(
            "CSV_SESSION_REUSED",
            "This wizard session already created a strategy under a different "
            "name. Start a new strategy to upload a different track record.",
            correlation_id,
            None,
        ),
    )
```

The name check is a floor, not the whole fix — the file can change while the name does not.
The durable shape is to mint a fresh `wizardSessionId` whenever the CSV wizard's
`strategyName` or `dailyReturnsSeries` changes after a failed submit, so a changed submission
is a *new* submission by construction. Either way, `wizardErrors.ts:887` and `:933` must stop
promising an unconditional "resolves to the strategy that already exists" until the
precondition is enforced — as written they instruct the action that triggers this.

### CR-02: `csv-validate`'s 502 terminal arm tells the user their CSV failed validation, when by construction the fault is ours

**File:** `src/app/api/strategies/csv-validate/route.ts:346`
**Rendered at:** `src/app/(dashboard)/strategies/new/wizard/steps/CsvValidationEnvelope.tsx:56,69`
**Pinned by:** `src/__tests__/csv-validate-route.test.ts:443,477`

**Issue.** Plan `140.4-09` replaced the leaky `err.message` echo with a static sentence — correct
in intent, wrong in content:

```ts
return csvErrorEnvelope(
  "CSV_UPSTREAM_FAIL",
  "CSV validation failed. Try again shortly.",
  {},
  502,
);
```

The arm's own docblock (`route.ts:311-315`) states what reaches it: *"a transport failure, a
missing-config throw from the client, a contract-drift parse throw, or any untyped throw"* —
i.e. **never** the user's data. `CSV_UPSTREAM_FAIL`'s authored copy is honest
(`wizardErrors.ts`: *"Validation service returned an unexpected response. Retry shortly."*), but
it is unreachable at this surface: `CsvUploadStep.tsx:277-280` takes `data.human_message` when
present, and `CsvValidationEnvelope` renders `human_message` as **both** the bold heading
(`:69`, because `errors.length === 0` on this path — `debug_context` is `{}`) **and** the cause
line (`:56`). The user reads *"CSV validation failed."* twice, for our outage.

**Concrete failure scenario.** `ANALYTICS_SERVICE_URL` is unroutable (exactly the §7.3 preview
condition this phase asks the founder to create). `postProcessKey` throws `fetch failed`. The
user, who uploaded a perfectly valid file, is told their CSV failed validation and is given no
indication the fault is on our side.

**Regression direction.** Before this change the sentence *"CSV validation failed"* applied only
to the **non-Error** throw branch (`const message = err instanceof Error ? err.message :
"CSV validation failed"`). The change widened a rare misattribution to **every** 502 on this arm
— and then pinned it with two `toBe` assertions.

**Grading.** BLOCKER: this is the phase goal clause *"stop attributing our own faults to the user
or their venue"* violated by the phase's own new code, on the wizard's highest-traffic error
surface, and guarded into place.

**Fix.** Use the sentence the code already owns and stop shadowing it.

```ts
return csvErrorEnvelope(
  "CSV_UPSTREAM_FAIL",
  // The code's OWN authored copy, not a sentence about the user's file. This arm
  // is the unclassified residue — transport, missing config, contract drift — so
  // naming the user's data is a misattribution by construction.
  WIZARD_ERROR_COPY.CSV_UPSTREAM_FAIL.title,
  {},
  502,
);
```

…and update `src/__tests__/csv-validate-route.test.ts:443,477` in the same commit, since they
currently hold the wrong sentence in place.

### WR-06: Sentry capture is unbounded per-request on exactly the incidents it observes

**Files:** `src/lib/ratelimit.ts:466-481` · `src/lib/resilient-fetch.ts:1098-1110,1321-1329`

**Issue.** Three new capture sites fire **once per request**, not once per state transition:

- `checkLimit`'s posture-2 arm captures on every request that wins the 5 s fail-open race.
- `isBreakerOpen`'s catch captures on every request whose breaker probe rejects.
- `recordSeamFailure`'s catch captures on every failure whose bookkeeping write fails.

`emitBreakerTransition` is correctly bounded (open/close edges only); these three are not, and
they are reached from the seam's highest-volume paths. During a sustained Upstash outage — the
incident the instrumentation exists for — every request in the window emits an
`import("@sentry/nextjs")` + `captureException`, held alive by `after()`. The predictable outcome
is Sentry rate-limit/quota exhaustion, which drops **other** alerts during the same incident, and
`after()` keeps the function instance alive for each capture.

**Fix.** Gate the three on an edge or a coarse time window, in the shape
`emitBreakerTransition` already uses — e.g. a module-level `lastCapturedAtMs` per
`(surface, stage)` with a 60 s floor — and keep the `console.warn`/`console.error` unconditional
so the local trace stays complete.

**Files:** `src/lib/seam-ratelimit-posture.invariant.test.ts` (whole file) · `ConnectKeyStep.tsx:225-235` · `MultiKeyConnectStep.tsx:185-201`

**Issue and judgement.** The fixer's stated residual is *"no guard asserts that every wizard
client consuming a `rateLimitDenyJson` route consults the shared table"*. I enumerated the class
rather than accepting the framing. Six sites emit a `code` in a `misconfiguredBody`

the wire code cannot collapse), and `ApiKeyManager.tsx:80-92` (renders `fields.error`, no roster).

**So the class is closed in fact today** — every membership-checking client has the hop, and no
seventh client exists. My judgement: the residual is **acceptable as a coverage claim** and
**not acceptable as a documentation claim**, for two specific reasons:

1. Both docblocks rest the safety of the reordering on *"the table's key set and this set
   intersect in NOTHING"* — a measured fact with **no assertion behind it**. Adding
   `RATE_LIMITED` or `VALIDATION_FAILED` to either roster (a plausible future edit; the routes
   already mint sibling codes) is a one-line change nothing reddens. As it happens the two
   overlapping entries are identity mappings, so today the consequence is nil — but *that* is
   also asserted nowhere.
2. The structural guard is one line away from being able to hold the class it needs. It already
   walks `src/app/api` and derives seam routes; a second scan for `misconfiguredBody:` with a
   `code:` field, cross-checked against the wizard clients that membership-check, would be
   coverage-law row 1. The 3-of-3 state was reached by two hand-fixes after the fact, which is
   the mechanism the Coverage Law says produces 9/37.

**Fix (cheap, and it holds the class rather than the instances).** Add to

it("no roster shadows the ONE wire→wizard table", () => {
  // The reordering at ConnectKeyStep/MultiKeyConnectStep/SyncPreviewStep is safe

  const wire = new Set(SEAM_CODE_TO_WIZARD_CODE.keys());
