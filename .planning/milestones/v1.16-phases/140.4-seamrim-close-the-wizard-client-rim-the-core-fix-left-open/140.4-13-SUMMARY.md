## The four preserved 429 contracts, named individually — plus two the plan did not name

Blanket adoption of `rateLimitDenyJson`'s **fixed** body would have regressed these. Each body
is quoted **before → after**; every one is **byte-identical**.

### 1. `strategies/create-with-key:223` — `KEY_RATE_LIMIT`

```js
// BEFORE
{ code: "KEY_RATE_LIMIT", error: "Too many requests" }
// headers: { ...NO_STORE_HEADERS, "Retry-After": String(rl.retryAfter) }

// AFTER — passed as throttledBody, verbatim, key order included
{ code: "KEY_RATE_LIMIT", error: "Too many requests" }
// headers: NO_STORE_HEADERS + Retry-After (stamped by the artefact)
```
**Why it matters:** `ConnectKeyStep`'s `KNOWN_CREATE_WITH_KEY_CODES` admits `KEY_RATE_LIMIT`,
and its copy reads *"a transient, exchange-side throttle and not a problem with your key"*.
Dropping the code blanks the rendered sentence. **This is the sharpest site in the class** —
it is where we blamed the user's exchange for our own outage, on their first click, on the step
where they hand us a credential.

### 2 & 3. `keys/sync:116` and `keys/sync:123` — `RATE_LIMITED`, ×2

```js
// BEFORE (both arms, identical)
{ error: "Too many requests", code: "RATE_LIMITED" }
// headers: { ...NO_STORE_HEADERS, "Retry-After": String(<that arm's> retryAfter) }

// AFTER (both arms) — throttledBody, verbatim
{ error: "Too many requests", code: "RATE_LIMITED" }
```
⚠️ **Note the key order is `{error, code}` here and `{code, error}` at create-with-key.** A
builder that *rebuilt* the object would have silently normalised one into the other; the
options bag passes the literal through untouched, and `ratelimit.test.ts` asserts that with a
`JSON.stringify` byte comparison, not just a deep equality.
**Why it matters:** `SyncPreviewStep`'s `KNOWN_KICKOFF_CODES` maps `RATE_LIMITED`.

### 4. `strategies/csv-validate:180` — the CSV v0 envelope

## Task 1 — the extended builder

```ts
export type RateLimitDenyOptions = {
  headers?: Readonly<Record<string, string>>;
  throttledBody?: unknown;
  misconfiguredBody?: unknown;
  retryAfterHeader?: "always" | "misconfigured-only";
};

export function rateLimitDenyJson(rl: DenyResult, options?: RateLimitDenyOptions): NextResponse
export function rateLimitDenyText(rl: DenyResult): NextResponse   // signature UNCHANGED
```

**What the artefact keeps, exclusively:** the status (`denyStatus()` = the sole computation of
503-vs-429 in the repo) and the `Retry-After` **value**. `denyHeaders()` spreads the caller's
bag **first** and stamps `Retry-After` **last**, so a caller cannot clobber it — asserted.

**What the route keeps:** its body and its extra headers.

**`rateLimitDenyText` was deliberately NOT given the options bag.** It has zero call sites
today (measured: the P1 predicate finds only its own definition), so an options argument would
be speculative surface. What it *did* gain is the shared `denyStatus` / `denyHeaders`, so the
two twins can no longer drift apart on the decision.

**The docblock's old justification was replaced, and recorded as the defect it was.** It read:

> *"Routes whose tests `vi.mock("@/lib/ratelimit")` still inline the branch to keep their
> existing mocks intact — this helper is for the admin surface where the real ratelimit module
> loads."*

That sentence is the **fix's own justification for leaving the class open** — a P6-shaped fact.
Test-mock convenience is why eleven seam routes stayed off the artefact for two years. The
replacement states what is now true and names why the old reason was a defect.

### The negative cases, which are the point

A criterion that only checked *"the override is honoured"* would be satisfied by an
implementation that let a route answer 429 on a misconfiguration — **the exact defect, at
twelve sites**. Three named cases close that:

- `a misconfiguration answers 503 even when the options bag says otherwise` — an options object
  carrying `{status, statusCode, code, misconfigured, reason, throttledStatus,
  misconfiguredStatus}`, cast in, still yields **503**. The cast is deliberate: the assertion is
  about **runtime** behaviour, which a type signature cannot guarantee against a caller who
  casts.
- `a genuine throttle answers 429 even when the options bag says otherwise`.
- `a body override does not carry a status with it` — passing the 429 body on a misconfigured
  result still yields **503**.

**RED evidence (Task 1, before the implementation):** `5 failed | 37 passed (42)`. The
**no-options** cases were already **green** on the untouched implementation — which is the
byte-identity baseline doing its job, not a weak test.

## Task 2 — the twelve conversions

### The `csv-validate` envelope decision, and why it is neither of the two shapes offered

The plan allowed *either* passing the envelope as a body override *or* keeping
`csvErrorEnvelope` and branching on `isRateLimitMisconfigured` locally. **Neither verbatim.**

- Re-typing the five v0 fields into the options bag would have given this route a **second
  definition of the envelope** — the precise opposite of M-14's stated reason for
  `csvErrorEnvelope` existing (*"one edit, not seven"*), and the shape a future `correlation_id`
  thread would miss.
- Branching locally would have left the status decision in a twelfth inlined copy and failed
  the plan's own `≥ 1 rateLimitDenyJson` acceptance.

**What was done:** `csvErrorBody(code, human_message, debug_context)` was split out of
`csvErrorEnvelope`, which now calls it. The deny arm hands **that same builder's output** to
`rateLimitDenyJson`. ⇒ the envelope keeps **one** definition, and the status comes from the
**artefact**. `csvErrorEnvelope`'s own behaviour is unchanged (it is the only caller of the new
helper besides the deny arm).
