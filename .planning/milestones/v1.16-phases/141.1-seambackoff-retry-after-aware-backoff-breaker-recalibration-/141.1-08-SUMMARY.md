## Evidence that the alert actually fires

The plan's pins are all *query-shape* assertions. On their own they do not prove the alert fires, and every pre-existing test in this suite mocks `fetch` **URL-blind** — returning the same count whatever is asked — so they stay green against a query that matches nothing in production. That is precisely the defect this phase exists to close, so it could not be the only evidence.

Added `SC-N end-to-end` (deviation, Rule 2 — see below): the fetch double is an **index simulator** that answers the way the real Sentry backend does given this repo's instrumentation:

| Query shape asked | Simulated `count()` | Why |
|---|---|---|
| contains any `path:` term | `0` | unindexed field — matches no event, ever (the observed production reality) |
| the repaired indexed query | `10` | the process-key errors in the window |
| unscoped (scoping term dropped) | `682` | the whole error population — cron-recompute |

With a 1000-request denominator, the repaired path yields `10/1000 = 1%` > `ALERT_THRESHOLD` 0.5% with `total >= MIN_SAMPLE`, and the test asserts the full chain: `errorCount === 10`, `errorRate ≈ 0.01`, `action === "alerted"`, **exactly one email sent**, subject matching `[ALERT]` and containing `1.00%`, addressed to the founder. Asserting `errorCount === 10` separates all three arms, so the test fails if the query is dead (`0`), if it is unscoped (`682`), or if the numerator is not wired (mutation 4).
