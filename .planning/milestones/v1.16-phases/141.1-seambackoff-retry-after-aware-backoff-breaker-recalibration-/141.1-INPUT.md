# Phase 141.1 — Planning Input

**Source of scope:** `.planning/phases/141-seam-retry-with-backoff-gated-on-the-idempotency-audit/141-REVIEW-CONSOLIDATED.md`

Read that file first. It is the deduped output of an 8-agent review campaign over
phase 141 (3 specialist reviewers, 2 analysis lenses, 5 adversarial red teams,
1 completeness critic), and it contains both the surviving work and — importantly —
a **RULED OUT** table of claims that were killed by evidence.

## Why this phase exists

Phase 141 shipped a bounded seam retry gated on a committed idempotency audit.
The review campaign found **zero user-facing defects and zero data-integrity
defects** — every blocking claim was refuted under adversarial scrutiny. The
mechanism is sound and should NOT be redesigned.

What survived is three different things, none of which is a bug fix:

1. **A design input that was built and never consumed.** Phase 140.5 shipped
   `Retry-After` propagation as an explicit hard prerequisite for 141. The retry
   loop ignores it: the contract mandates `Retry-After` on every SERVICE-TRANSIENT
   503 (15s supabase / 30s mt5-gateway) and the loop waits 250–500ms and re-attacks.
   The retry is near-certain to fail AND spends a second breaker failure learning that.

2. **An uncalibrated threshold.** `BREAKER_FAILURE_THRESHOLD = 5` predates
   per-attempt counting. A doubly-failing request now records 2 failures, so the
   GLOBAL `breaker:railway` key — which gates all 15 routes including the anonymous
   teaser — trips in ~2.5 user requests instead of 5. Possibly the right direction;
   definitely an undecided one.

3. **A defective deliverable.** SEAM-05's requirement is a committed retry-safety
   audit whose evidence and enforcement cannot drift. The enforcement is correct,
   but the evidence is wrong in four places (three analytics verdicts claim "no
   persisted write" and all three write; resync claims a class is "closed" that is
   ~40% open within a blip; onboard states a conditional as fact; a migration id
   points at the wrong index). No verdict changes and no user is harmed — but a
   future engineer extends the allowlist by reasoning from these strings, which is
   precisely the failure the registry was built to prevent.

## Standing constraints

- **Do not re-litigate the RULED OUT table.** Each entry died on specific evidence.
  Re-opening them burns the campaign's main value.
- **Do not change any retry verdict or un-flip any `SEAM_BUDGETS` row.** The red
  teams established the verdicts are correct; only the justifying prose is wrong.
- **Every fix gets a regression test that fails without it.** Two of the biggest
  findings (C3, D1) are cases where deleting production code left the suite green.
- **Run the pattern-mapper.** The last remedy in this area introduced the very
  incompleteness this campaign spent its time investigating; C2 is explicitly an
  instance-not-class finding where the correct guard pattern already exists in-repo
  (`resilient-fetch.wiring.test.ts` `EXPECTED_BINDINGS`) and was not extended to
  the new axis.

## Nothing is live

`origin/main` has no `seam-retry-registry.ts` and no `retriesOverride` — production
performs zero seam retries today. Branch `feat/v1.16-141-jobs-rate-retry` is ahead
with no open PR, so 141.1 can land alongside 141 in the same PR rather than shipping
a knowingly-imprecise audit artifact and correcting it afterwards.
