# Phase 141.1 Plan 01: Retry-After fail-fast + breaker-threshold ratification Summary

**A retry-eligible 503 that carries the upstream's own mandatory `Retry-After` now fails fast — one fetch, body intact, one breaker failure instead of two — and `BREAKER_FAILURE_THRESHOLD = 5` is ratified as a decided number under per-attempt counting rather than left resting on a premise the retry loop invalidated.**

## Accomplishments

- **D-01 landed.** `hasContractualWait` + a one-conjunct change to the counting-status retry guard. A 503 advertising a 15 s (supabase) or 30 s (mt5-gateway) wait is no longer retried ~375 ms later into a near-certain second failure; attempt 1's response is returned with `dependency` / `human_message` intact so the client contract still renders its own copy.
- **The 503 retry arm was NOT disabled.** SC-C′ proves a 503 without the header still retries, and a stray header on a counting 502 still retries — the rule is narrow by construction and both halves are mutation-proven.
- **The capability guard is real, not theoretical.** The repo's existing `statusSequenceFetch` doubles are bare `{ ok, status }` literals with no `headers` at all; that pre-existing test is now also the anti-regression for the guard, with a comment forbidding its conversion to a real `Response`.
- **D-02 landed.** The threshold docblock no longer reasons as if attempt == request. It carries the arithmetic table, the global-key blast radius (all fifteen routes, including the anonymous teaser), and an explicit dated acceptance — plus a derived pin so neither half can move in silence.
- **Zero Python changes**, zero package installs, zero constant-value changes.
