## Summary

This is a **zero-new-dependency, in-repo repair phase**. Nothing here is a library-selection or ecosystem question: every artifact under repair is a file in this repo, and every "standard stack" answer is "the pattern this repo already established, extended to the axis it was not extended to." I therefore spent the research budget on *literal source tracing* rather than on external lookup, per the phase brief.

Three findings dominate what the planner needs to know, and each of them **changes the shape of the work** relative to what CONTEXT.md assumes:

1. **The citation guard cannot see the registry's evidence strings.** `seam-citations.invariant.test.ts` extracts **comments** (`extractComments`) and it has an explicit negative self-test — `"-1: the SAME token inside a STRING literal is NOT caught"` at `:369-375` — proving string-literal citations are out of reach *by design*. Every rotted citation D-06 names (`20260418194206`, `resilient-fetch.ts:502`, `keys/sync/route.ts:563-599`, `process_key.py:1351`) lives inside the `evidence:` **string literals** of `seam-retry-registry.ts`. Adding that file to `SEAM_CITATION_SURFACE` produces **zero offences today** — a vacuous addition. `TODOS.md:483` already records this exact residual ("string-literal citations invisible to the comment-scoped census"). D-06 needs a **second predicate**, not a roster append. See §"D-06 — the guard gap".

2. **The `Retry-After` read must be capability-guarded or it will throw inside the classification window.** `statusSequenceFetch` in `resilient-fetch.retry.test.ts:210-219` returns bare `{ ok, status } as Response` doubles with **no `headers`**. `res.headers.get(...)` on those is a `TypeError` raised *inside* the try — exactly the failure `readDependencyBody` guards against with its `typeof res.clone !== "function"` check (`resilient-fetch.ts:1798`, whose docblock at `:1789-1795` says a throw here "would replace the real upstream error with a bookkeeping one"). Copy that guard shape.

3. **The SC-4b arithmetic must be corrected PER LEG, not per route.** `storeMs` is currently computed from `seamCalls` (the branch's total call count) outside the leg reduce (`seam-budgets.invariant.test.ts:653-657`). A flat `× (1 + retries)` has no well-defined `retries` for a multi-leg branch. Move the store term into the leg reduce. I verified the resulting numbers: the worst retried route becomes **keys/sync at 56,000 ms** — which is exactly the "~56,000ms" figure D-15 cites, confirming the finding's arithmetic — while the true tightest route in the table, `finalize-wizard` composite at **277,500 ms** (22,500 ms headroom), is **unchanged** because all its legs are `retries: 0`.

**Primary recommendation:** Wave 2 (D-04 – D-07) is the phase's highest-value work and is fully pre-traced below — the executor should be copying findings, not re-deriving them. Wave 1's D-01 is a **three-line change at one insertion point** with one hard constraint (the capability guard). Wave 3's D-08/D-09 both have exact in-repo precedents that are quoted below. Do not let Wave 4 (D-16) expand: the flag-monitor numerator may already be structurally dead — see the OPEN QUESTION.

### Locked Decisions

**A. Design (founder-decided 2026-07-31)**

- **D-01 — `Retry-After` ⇒ fail fast, do not sleep.** When a retry-eligible 503 carries a `Retry-After` header, the loop must **not** retry: it surfaces attempt 1's response immediately (preserving the 503 body — `dependency`, `human_message`) and does not spend a second breaker failure. Rationale: `analytics-service/services/error_contract.py:131-152` makes `Retry-After` mandatory on every SERVICE-TRANSIENT 503 from `RETRY_AFTER_SECONDS = {"mt5-gateway": 30, "supabase": 15}`; no route budget is worth burning billed Vercel wall-clock sleeping for 15–30s, and retrying in 375ms is near-certain to fail. The existing jittered `SEAM_RETRY_BACKOFF_MS + jitter` backoff **stays unchanged** for the transport/timeout class, which is the dominant Railway-blip class. 429 is already correctly excluded (`attributability: "caller"`, `counts: false`) and stays excluded. Covers A1.
- **D-02 — `BREAKER_FAILURE_THRESHOLD` stays 5; the decision gets recorded.** Faster containment under per-attempt counting is ratified as *intentional*, not accidental: a Railway blip reaching 5 counted failures is a real outage, and tripping the global `breaker:railway` key in ~2.5 user requests instead of 5 is the right direction. No numeric change to `BREAKER_FAILURE_THRESHOLD`, `BREAKER_WINDOW`, or `BREAKER_COOLDOWN_S`. The reasoning must be pinned in a comment **and** a test so it stops being an undecided tradeoff. Covers A2.
- **D-03 — Server-side cancellation is out of scope; the cost is recorded.** No `request.is_disconnected()` work in the analytics service. The doubled-compute consequence (a retry adds a second concurrent full compute on the 4 heavy budgets while attempt 1 still burns CPU) is documented in the registry/runbook as a known accepted consequence and booked to `TODOS.md`. Covers A3.

### D-01 — the exact insertion point

**Where the retry-eligibility decision lives.** There are exactly **two** retry-eligible arms inside the loop:

| Arm | Lines | Decision |
|---|---|---|

| Counting-status (503 / other-5xx) | `resilient-fetch.ts:2154-2163` | **THE INSERTION POINT.** |

Current code at `:2154-2163`:

```ts
const verdict = seamBreakerVerdict(res.status, await readDependencyBody(res));
if (verdict.counts) {
  await recordOnce(verdict.breakerKey);
  // A counting status is retry-eligible too. Not the last attempt → discard
```

**The smallest correct change** is to add one conjunct to the `!lastAttempt` guard. Falling through to `:2176`'s `return instrumentBody(res, …)` gives D-01 everything it asks for *for free*:

- attempt 1's response is surfaced immediately, body intact (`readDependencyBody` uses `res.clone()` at `:1800`, so the caller's branch is untouched — [VERIFIED: `:1770-1773` docblock + `res.clone().json()`);
- attempt 2 never fires, so no second breaker failure is spent;

**⚠️ THE CAPABILITY-GUARD PITFALL — this is the single most likely way D-01 breaks the suite.**

`SeamResponse.headers` is typed `Response["headers"]` (`resilient-fetch.ts:1541-1548`), i.e. **required**. But at runtime the test doubles are bare literals:

```ts
// resilient-fetch.retry.test.ts:213-217
mock.mockImplementation(() => {
  const status = statuses[Math.min(i, statuses.length - 1)];
  i += 1;
  return Promise.resolve({ ok: status < 400, status } as Response);   // ← no `headers`
});
```

A bare `res.headers.get("Retry-After")` on that double throws `TypeError: Cannot read properties of undefined`, **inside the classification window**, where it becomes an unrelated transport failure. The repo already solved this exact problem once — `readDependencyBody:1789-1795`:

> *"The `clone` capability check is not defensive decoration: `SeamResponse` is deliberately structural so route tests can stub the core with a `Response`-shaped object, and several existing fixtures are bare `{ ok, status }` literals. A missing `clone` must degrade to the global key, never throw — a throw here lands inside the classification window and would replace the real upstream error with a bookkeeping one."*

**Copy that shape verbatim.** Recommended helper, sited next to `readDependencyBody`:

```ts
/** Does this counting response carry the upstream's own contractual wait hint? */
function hasRetryAfterHint(res: Response): boolean {
  if (typeof res.headers?.get !== "function") return false;   // bare-literal stub — degrade, never throw
  return res.headers.get("Retry-After") !== null;
}
```

**Scope note the planner must decide explicitly:** the contract makes `Retry-After` mandatory **only on 503** (`error_contract.py:120-152`). Other counting 5xx cannot carry one from our service. Gating on `res.status === 503 && hasRetryAfterHint(res)` mirrors `readDependencyBody`'s "only 503" discipline exactly and is the narrower, more defensible rule. Gating on the header alone is equivalent in practice today (nothing else emits it) but is broader. **Recommend: mirror `readDependencyBody` and gate on 503.**

**What must NOT change:**
- A 503 with **no** `Retry-After` — e.g. from Railway's own edge, or Vercel's proxy, i.e. not from our FastAPI at all — **still retries**. That is the correct behaviour and the existing test at `:338-350` (`statusSequenceFetch(503, 200)` → 2 fetches) pins it. Because that double has no `headers`, the capability guard makes it fall to `false` and the test stays green. [VERIFIED by reading the double's shape]
- 429 is already `counts: false` at the discriminator, so it never reaches this arm. Nothing to do. [CITED: `141-REVIEW-CONSOLIDATED.md` A1; consistent with `seamBreakerVerdict` usage at `:2154`]

**The contract D-01 consumes** — [VERIFIED: `analytics-service/services/error_contract.py:88-94, 120-152`]:

```python
RETRY_AFTER_SECONDS: Final[dict[str, int]] = {

    "supabase": 15,      # PostgREST/Supabase blips are seconds, not minutes
```

### D-15 — SC-4b, the corrected arithmetic (numbers verified)

**Current code**, `seam-budgets.invariant.test.ts:650-657`:

```ts
const seamCalls = branch.legs.reduce((acc, b) => acc + b.calls, 0);
const storeMs =
  STORE_COMMANDS_PER_SEAM_CALL[state] *
  STORE_COMMAND_WORST_CASE_MS *
  seamCalls;
```

`STORE_COMMANDS_PER_SEAM_CALL = { closed: 1, open: 1, failing: 3 }` (`:308-312`). `STORE_COMMAND_WORST_CASE_MS = (1+1)×2000 + 1×250 = 4250` (`:278-280`, pinned to the literal at `:704`).

**The defect:** `requestMs` is multiplied by `(1 + retries)` per leg (`:638-640`) but `storeMs` is not multiplied at all. A retried call issues a **second** breaker-store round: the pre-attempt-2 `mget` at `resilient-fetch.ts:2025` (`isBreakerOpen`) plus attempt 2's own trip `get`/`set` if it also fails.

**Per-attempt command count, hand-counted from the loop:**

| State | Attempt 1 | Attempt 2 (when it runs) | Total at retries=1 |
|---|---|---|---|
| `closed` | entry `mget` = 1 | pre-attempt-2 `mget` = 1 | **2** |
| `failing` | entry `mget` + trip `get` + trip `set` = 3 | pre-attempt-2 `mget` + trip `get` + trip `set` = 3 | **6** ✓ matches D-15 |
| `open` | entry `mget` = 1, then `CircuitOpenError` before `fetch` | never runs | **1** |

**The correct fix is PER LEG**, because `retries` is a property of a leg's budget row, not of a branch. Move the store term inside the same reduce as `requestMs`:

```ts
const storeMs = branch.legs.reduce(
  (acc, b) =>
    acc +
    STORE_COMMANDS_PER_SEAM_CALL[state] *
      // Phase 141.1 / D-15 — a RETRIED leg issues the store round a SECOND
      // time (pre-attempt-2 isBreakerOpen, plus attempt 2's own trip path).
      // Zero-extra when retries=0, so every non-flipped leg is unchanged.
      (1 + (STATE_SPENDS_REQUEST_BUDGET[state] ? SEAM_BUDGETS[b.key].retries : 0)) *
      STORE_COMMAND_WORST_CASE_MS *
      b.calls,
  0,
);
```

The `STATE_SPENDS_REQUEST_BUDGET` conjunct is load-bearing: in the `open` state the call throws before entering the loop, so there is no second round.

## Common Pitfalls

### Pitfall 1: `res.headers` is undefined on the repo's test doubles
**What goes wrong:** D-01's `Retry-After` read throws `TypeError` inside the classification window; the real upstream error is replaced by a bookkeeping one and gets counted as Railway degradation.
**Why:** `statusSequenceFetch` / `throwThenOkFetch` return `{ ok, status } as Response`; `SeamResponse` is deliberately structural so route tests can stub the core with bare literals.
**Avoid:** `typeof res.headers?.get !== "function"` → return `false`.
**Warning sign:** existing 503 retry tests at `resilient-fetch.retry.test.ts:338-350` go red for a reason unrelated to their subject.

### Pitfall 2: the citation guard is comment-scoped
**What goes wrong:** D-06 is marked done after a roster append; the rotted evidence strings stay unguarded and rot again.
**Why:** `extractComments` + an explicit `-1` negative self-test proving string literals are excluded by design.
**Avoid:** add the registry-local evidence-string guard **and** the roster append; treat them as two tasks.
**Warning sign:** the new guard finds 0 offences on a file that demonstrably contains rotted citations today.

### Pitfall 3: making `retriesOverride` required breaks every test that calls the core
**What goes wrong:** D-08 lands as a two-line prod change and reddens dozens of tests.
**Why:** the field becomes non-optional on `ResilientFetchInit`, so *every* `resilientFetch(...)` in tests must pass it too.
**Avoid:** budget a mechanical task for the test population; run `npx tsc --noEmit` first to enumerate it exactly.
**Warning sign:** `npm run typecheck` produces a long list — that list *is* the task.

### Pitfall 4: sequencing D-07 site #4 before D-08
**What goes wrong:** the corrected comment at `:553-558` describes a world that does not exist yet, and becomes false a second time when D-08 lands.
**Avoid:** land D-08 first, then write that comment against the post-D-08 state. Same for D-10's comment.

### Pitfall 5: `CircuitOpenError` swallowed by the retry loop
**What goes wrong:** SC4 breaks silently.
**Why:** it is thrown from `:2027`, **above** the fetch `try` at `:2045` — the current structure is correct. Any refactor that moves the re-check inside the try re-opens this.
**Avoid:** keep the throw above the try. The existing SC4b test at `:463-496` pins it.

### Pitfall 6: D-15's arithmetic applied per-route
**What goes wrong:** `finalize-wizard` composite appears to breach.
**Avoid:** per-leg, gated on `STATE_SPENDS_REQUEST_BUDGET`.

### Pitfall 7: "shared test DB" scoping in SQL gates
**What goes wrong:** a global count in `test_resync_retry_single_job.sql` flakes under concurrent CI.
**Why:** the test Supabase project is shared [MEMORY: `project_shared_testdb_concurrent_ci_flake`].
**Avoid:** the file already scopes every count to the literal fixture strategy id `6d6d6d6d-0000-4000-8000-000000000041`. D-07 only edits a **comment** at `:40` — do not touch the assertions.

### Pitfall 8: a Python edit sneaking in
**What goes wrong:** D-03's fence breaks; `mypy --strict` exposure appears; the phase's scope statement becomes false.
**Avoid:** D-04/D-05/D-16 *read* Python and *write* TypeScript/markdown. Zero `.py` files change.

## Code Examples

### D-01 — the fail-fast arm (verified insertion point)

```ts
// resilient-fetch.ts — beside readDependencyBody
/**
 * Does this counting response carry the upstream's OWN contractual wait hint?
 *
 * ⚠️ CAPABILITY-CHECKED, for the same reason readDependencyBody checks `clone`:
 * SeamResponse is deliberately structural and several fixtures are bare
 * `{ ok, status }` literals with no `headers` at all. A throw here lands INSIDE
 * the classification window and would replace the real upstream error with a
 * bookkeeping one.
 */
function hasContractualWait(res: Response): boolean {
  if (res.status !== 503) return false;          // the ONLY status the contract
  if (typeof res.headers?.get !== "function") return false;   // mandates it on
  return res.headers.get("Retry-After") !== null;
}

// …inside the loop, at the counting-status arm (was `:2155-2163`):
const verdict = seamBreakerVerdict(res.status, await readDependencyBody(res));
if (verdict.counts) {
  await recordOnce(verdict.breakerKey);
  // Phase 141.1 / D-01 — HONOUR THE UPSTREAM'S OWN CONTRACT. Every
  // SERVICE-TRANSIENT 503 this service emits carries a mandatory Retry-After
  // (15s supabase / 30s mt5-gateway). Retrying in ~375ms is near-certain to
  // fail AND spends a second breaker failure learning that. So a 503 that
  // names a wait FAILS FAST: fall through and RETURN attempt 1's response
  // with its body (`dependency`, `human_message`) intact. The jittered
  // backoff above is UNCHANGED for the transport/timeout class, which is the
  // dominant Railway-blip class and carries no header to honour.
  if (!lastAttempt && !hasContractualWait(res)) {
    continue;
  }
}
```
