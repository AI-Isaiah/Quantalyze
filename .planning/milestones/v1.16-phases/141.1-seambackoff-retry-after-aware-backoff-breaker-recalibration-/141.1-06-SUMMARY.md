### 2. [Rule 3 — blocking] SC-B's fresh-budget case needed a signal-honouring fetch double and an `AbortSignal.timeout` spy

- **Plan text:** *"using the existing harness only (no new doubles; `statusSequenceFetch` for SC-B, fake timers + Math.random spy for determinism)"*.
- **Blocker:** the plan's own behaviour spec for the same case requires *"attempt 1 times out at its full `timeoutMsOverride`"*. `statusSequenceFetch` answers immediately and ignores the signal, so it **cannot express a timeout**. Two facts had to be established before the case could be written at all:
  - **MEASURED:** vitest 4.1.10 fake timers do **not** drive `AbortSignal.timeout` (install fake timers, create a 1000 ms signal, advance 1500 ms → still not aborted). The repo's existing fake-timer cases pass `timeoutMsOverride: 300_000` for exactly this reason — they are keeping a *real* deadline from firing, not asserting on it.
  - A `setTimeout`-backed `AbortSignal.timeout` spy **is** drivable (verified: not aborted at 999, aborted at 1000).
- **Resolution:** the case uses (a) `vi.spyOn(AbortSignal, "timeout")` — a pattern already established in `resilient-fetch.test.ts`'s budget-wiring tests — with a `setTimeout`+`AbortController` implementation, and (b) a local signal-honouring fetch double. Both are confined to that one `it`; the other three D-12/D-13 cases use `statusSequenceFetch` as the plan specifies. The substitution preserves exactly the property under test — one signal per call — so a hoisted deadline still reddens it, which is the point and was verified (§5).
- Both measured facts are written into the test's own comment so the next author does not assume the primitive works and write a vacuous case.

### 3. [Acceptance-criterion intent] SC-O's case ALREADY EXISTED; upgraded in place rather than duplicated

- **Criterion:** *"Add a `bridge` case at production configuration… written through `findReplacementCandidates`."*
- **Actual:** that case already existed — `SC2 — findReplacementCandidates (bridge) + a single transient then 200 → exactly TWO fetches`, landed in an earlier plan. **Measured:** deleting the `bridge` registry entry already reddened it. So SC-O's *substance* was discharged before this plan started.
- **The real defect, which was worth fixing:** it reddened by **throwing**. With the entry gone the wrapper makes one attempt, the transient propagates, and `findReplacementCandidates` throws — so the `await` aborted the test before the count assertion ran, and the CI failure read `Error: Analytics service is not reachable`, naming neither the registry nor the retry.
- **Resolution:** upgraded in place with a settle-capture so the **count** reddens first, carrying a message that names the registry, the chokepoint and the consequence (§10). Renamed to `SC2 / SC-O` and anchored to D-14d. **A twin test was deliberately NOT added** — duplicating an existing passing case to satisfy the word "add" would be scope creep with no coverage gain.

### 4. [Deviation from RESEARCH mechanics] SC-D could not use `shared.mode.staleReadOnce`

- **Plan/VALIDATION text:** SC-D *"via `shared.mode.staleReadOnce`"*, described as *"already built and currently unused — it is D-13's tool"*.
- **Issue:** `staleReadOnce` is wired into the fake Redis's **`get`** only. `isBreakerOpen` reads via **`mget`**, which does not consult it. The hook could not have driven this case.
- **Resolution:** used the plan's own sanctioned alternative (*"direct store write scheduled with setTimeout"*): a fake-timer `setTimeout` seeds the lock 100 ms into the 250 ms backoff. The case additionally asserts the circuit is **still closed** at the instant attempt 1 returns, so it cannot pass vacuously under either ordering — and the swap mutation was verified RED (§6). `staleReadOnce` remains unused; **not** fixed here, since wiring it into `mget` would change a shared harness for no remaining consumer.
