# Phase 142.1 Plan 08: SQL gate Part 6 — the G1 trigger sentinel — Summary

Gave the silently-coercing stamp trigger a gate that CAN fail, one assertion arm per
trigger arm, with every state seeded at INSERT because the trigger is bound to UPDATE
only — turning the honest cost plan 142.1-05 accepted (silence on a live money path)
into an observable one.

## What Was Built

### Part 6 — ungated, seeded at INSERT, three arms

Appended to `supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql`, copying
the retrofitted Part 4's framing verbatim: its own `BEGIN;`, `SET LOCAL lock_timeout =
'5s'`, one `DO` block, `ROLLBACK;`, the `auth.users → profiles → strategies` FK seed
chain with fresh uuids, and a `DELETE FROM auth.users` teardown. **No pg_cron gate and no
early-exit arm** — Part 6 needs only the trigger, so an unapplied `20260803120000` must
be a RED, never a skip. Parts 2 and 3 remain the file's only legitimate skips.

**Two strategies under one seeded user**, because `strategy_analytics` is one row per
strategy and the two states cannot coexist on one row:

| Row | Seeded at INSERT | Used by |
|-----|------------------|---------|
| `v_strat_a` | `('computing', FALSE, now() - interval '3 hours')` | 6a, then 6c |
| `v_strat_b` | `('computing', FALSE, NULL)` | 6b |

Row B's state is seeded **directly**. The "intermediate transition-out" dance an earlier
draft carried is gone (D-18 resolved the old W7): it existed only because the superseded
insert-firing sketch made that state unreachable, and the shipped trigger is `BEFORE
UPDATE` only.

**Both S-2 seed-integrity controls run before any driver** — row A at computing with the
stamp equal to the sentinel, row B at computing with no stamp — so a broken fixture
cannot green the part vacuously.

**The three arms**, each with a distinct `RAISE EXCEPTION` naming Part 6 / G1 / its
D-number, and each preceded by a status vacuity guard (the Part 4 convention):

- **6a NEVER-ADVANCE** (arm (a), D-01, ledger row SC-17/01). Driver is shaped like the
  Python writer's upsert conflict path — it names the status the row is already at *and*
  supplies its own clock — and the sentinel must survive. `now()` is transaction-constant,
  so without the three-hour offset this assertion could never fail.
- **6b CLOCK-START CLOSURE** (arm (b), the UPDATE-path half of D-11). No clock key
  supplied, row carries none, so it enters the trigger unclocked; the stamp must come back
  non-NULL **and** not back-dated.
- **6c EXIT-CLEAR** (arm (d)). The driver deliberately does the wrong thing — supplies a
  non-NULL clock on a terminal transition — and the stamp must come back NULL.

Row A is reused by 6c while still carrying its sentinel, so the clear is visible against a
real prior value rather than against NULL-to-NULL.

**Two header lines** were also corrected: the file now states that Part 2 arm D and the
trigger-sentinel part additionally guard migration `20260803120000`, and the `Run order`
line requires **both** migrations. Plan 142.1-07 applies this file to TEST; running it
with only the Phase 142 migration applied would have produced a RED with a misleading
cause.

### Behavioural, against a throwaway PostgreSQL 16 (the Pass-C technique)

Local `postgresql@16` cluster, TCP-only, a minimal `auth.users` / `profiles` /
`strategies` / `strategy_analytics` fixture. **Both the trigger DDL and the Part 6 block
were EXTRACTED programmatically from their source files, never re-typed** — a re-typed
oracle passes when the shipped artifact is wrong. The extractor confirmed 3 driver
`UPDATE`s in the extracted block, matching the pin.

**Baseline, real trigger:**

```
NOTICE:  Part 6 OK: the stamp trigger never advances the clock on an already-clocked
         computing row (6a), starts the clock when a write leaves a computing row
         unclocked (6b), and clears it on exit even when the writer supplies one (6c).
EXIT=0
```

That green is itself the D-18 part-2 proof: both seed-integrity controls passed, so
`(computing, sentinel)` and `(computing, NULL)` really do land verbatim at INSERT under
the shipped trigger.

**Six mutations, each derived from the real function text by deleting exactly one thing.
Every one reddens exactly the expected arm:**

| Mutation | Result |
|----------|--------|
| arm (a) coercion deleted | **6a RED** — `expected the sentinel 19:44:46, got 22:44:46` (the three-hour offset is what made it visible) |
| arm (b) clock-start deleted | **6b RED** — stamp still NULL |
| arm (d) exit-clear deleted | **6c RED** — the writer's supplied clock survived the terminal transition |
| the load-bearing `OLD.computing_started_at IS NOT NULL` conjunct deleted | **6b RED** — arm (a) reverts the clock-start write to NULL. This is the mutation plan 142.1-05 called its most valuable result; Part 6 now guards it too |
| arm (b) back-dates the clock (`now() - interval '100 years'`) | **6b RED** on the second assertion — `got 1926-08-02…, transaction now() is 2026-08-02…` |
| **the migration entirely unapplied** (trigger dropped) | **6a RED**, exit 3 — Part 6 REDDENS, it does not skip. This is the ungated requirement, observed |

Each mutation was run against a freshly rebuilt database, so no result leaks into the next.

⚠️ **What the local cluster does NOT prove.** The fixture is a minimal stand-in: no RLS,
no pg_cron, no bridge RPCs, no real constraints, single-connection. It proves the Part 6
SQL compiles, that its DML drives the trigger arms as designed, and that each arm is
falsifiable. It proves nothing about behaviour under the real schema on the shared TEST
project. That is D-16, owed by plan 142.1-07.

**2. [Rule 1 — Bug in my own edit] My header line pulled the whole file into Part 6's own acceptance gate**
- **Found during:** first acceptance sweep.
- **Issue:** I added a header line reading "Part 2 arm D and Part 6 additionally guard…".
  The criterion is `awk '/Part 6/,0' <file> | grep -c 'RETURN;'` → 0. Because `awk`'s
  range starts at the FIRST match, that header mention moved the range start from Part 4's
  prose (line ~590) to line 7 — swallowing Parts 2 and 3, whose legitimate pg_cron skip
  arms contain that literal. Measured **2**, expected **0**.
- **Fix:** Named the part descriptively in the header ("the trigger-sentinel part at the
  END of this file") instead of by number, and wrote the reason beside it so the next
  author does not re-add the number. The substance — that a second migration is required
  before this file is run — is unchanged. Re-measured **0**.
- **Files modified:** `supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql`
- **Commit:** `585376e7`
- **Note:** this is the phase's recurring hazard (plans 01–05 each shipped an instance),
  and it is the first one where the *range operator*, not a bare grep count, was the
  amplifier — a single prose mention 800 lines away changed what the gate measured.

**3. [Rule 2 — Missing critical] 6b asserts the started clock is not BACK-DATED**
- **Found during:** drafting 6b.
- **Issue:** The plan specifies "assert the stamp comes back NON-NULL". A trigger arm that
  stamped a time in the past would satisfy that and be strictly worse than leaving the row
  unclocked: the 16-hour staleness threshold could already be exceeded the instant the
  clock starts, so the next reaper tick terminalizes a healthy in-flight chain — user-
  visible data loss on a money surface, which clears the founder bar.
- **Fix:** Added a second `IF` in 6b, `v_stamp < now()`, with its own message. Written as a
  strict `<` against the frozen `now()` deliberately: a future arm using `clock_timestamp()`
  would land marginally AFTER `now()` inside the transaction and must not false-red.
  Falsifiability observed (mutation table above).
- **Files modified:** `supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql`
- **Commit:** `585376e7`

**4. [Rule 1 — Design correction] The three-hour literal is written twice, deliberately**
- **Found during:** reconciling the plan's acceptance criterion with Part 4's own header.
- **Issue:** Seeding with `VALUES (…, v_sentinel)` would (i) fail the criterion that
  `interval '3 hours'` sit INSIDE the seed INSERT's value list, and (ii) reproduce exactly
  the weakness Part 4's header documents about 4a — an S-2 control that "cannot fail on any
  behaviour of the code under test" because it compares a value against the variable that
  wrote it.
- **Fix:** The seed INSERT carries `now() - interval '3 hours'` and `v_sentinel` is
  initialised to the same expression independently. `now()` is transaction-constant, so
  they are exactly equal by construction, and the S-2 control becomes a genuine comparison
  of two independently written expressions. The reason is written into the Part 6 header.
- **Files modified:** `supabase/tests/test_strategy_analytics_stuck_computing_reaper.sql`
- **Commit:** `585376e7`
