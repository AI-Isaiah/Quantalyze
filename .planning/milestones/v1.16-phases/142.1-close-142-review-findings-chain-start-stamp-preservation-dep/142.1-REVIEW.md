## Warnings

### WR-01: the D-19 anti-regression guard cannot match the shape it exists to catch

**File:** `supabase/migrations/20260803130000_reaper_limit_bound_materialized_cte.sql:188`

**Issue:** The guard

```sql
IF v_command ~* 'IN\s*\(\s*SELECT[^)]*LIMIT' THEN
  RAISE EXCEPTION 'D-19 verification failed: the deployed body still binds a bounded batch through an IN (SELECT ... LIMIT ...) subquery. …';
```

`[^)]*` cannot cross a `)`. Both reverted arms carry
`AND NOT EXISTS ( SELECT 1 … cj.status IN ('pending', …) )` **between**
`IN (SELECT` and `LIMIT`, so the character class terminates long before it
reaches the `LIMIT` token. Measured against the exact superseded body from
`20260803120000`:

```
guard matches the reverted shape?              False
guard matches a NOT-EXISTS-free variant?       True
```

So the one assertion that names the defect by name provably cannot fire on the
defect. This is not a hole in the *fix* — the `v_mat <> 2` check immediately
above it does catch a revert of either or both arms (it counts `AS
MATERIALIZED` occurrences and demands exactly 2), so the bound is guarded. But a
guard that cannot fail is the exact class this phase exists to close, and its
`RAISE` text is what a future engineer will read as proof the shape is banned.

**Fix (one line):**

```sql
  -- POSIX ARE: `.` matches newline by default, and `[^)]*` cannot cross the
  -- NOT EXISTS subquery's closing paren — which is why the original form
  -- silently never matched.
  IF v_command ~* 'IN\s*\(\s*SELECT.*?LIMIT' THEN
```

Verify the change with the header's own measured shape (paste the superseded
arm into a scratch `SELECT 'x' ~* '…'`) before trusting it — the whole point of
this finding is that the un-executed form was accepted on its face.

**File:** `.github/workflows/ci.yml:902-904`

**Issue:** GitHub keeps at most **one** pending job per concurrency group; a
newly-queued job **cancels the previously-pending one**. With `python`,
`e2e-seeded` and now `sql-tests` all on `shared-test-db` (multiplied across
concurrent runs), `sql-tests` can be evicted-and-cancelled rather than queued —
a gate that silently does not execute. `cancel-in-progress: false` does not
address this; it only protects the *in-progress* job, which is what the new
vitest pin's message correctly describes.

Impact is bounded and this is a pre-existing property of the group (it already
held two jobs) rather than something the phase introduced: branch protection is
deferred on this project, `sql-tests` feeds no aggregator, and a cancel is
visible in the run summary. The correct decision — accept the eviction risk in
exchange for serialization, or split into a chained `needs:` — belongs to
whoever un-defers branch protection.

**Fix:** route to `TODOS.md` under the v1.16 CI residuals; no code change now.

### IN-04: `v_mat` mixes a raw length with an upper-cased one

**File:** `supabase/migrations/20260803130000_reaper_limit_bound_materialized_cte.sql:182`

```sql
v_mat := (length(v_command) - length(replace(upper(v_command), 'AS MATERIALIZED', ''))) / length('AS MATERIALIZED');
```

**Issue:** The minuend is `length(v_command)`; the subtrahend is derived from
`upper(v_command)`. These are only guaranteed equal for input where `upper()`
preserves length. The deployed body is ASCII and generated by this same file, so
the arithmetic is correct today and the check is doing real work (it is the
guard that actually catches a D-19 revert — see WR-01).

**Fix:** make both sides consistent, e.g.
`length(upper(v_command)) - length(replace(upper(v_command), 'AS MATERIALIZED', ''))`.
Cosmetic; route to `TODOS.md` or fold into the WR-01 edit since it is two lines
away.
