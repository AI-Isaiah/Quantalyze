# Phase 142.1 Plan 02: Test-hygiene cluster (D-10, D-06, D-09, D-15) — Summary

Closed the four test-hygiene findings. The load-bearing one is **D-10**: three
copies of `_py_scan_files` carried three different file lists, so the JOB-07
structural gate and the dark-path gate had both silently narrowed to a five-file
hand list while claiming full coverage — a green gate that had stopped looking.
They now share one `rglob`-walked union. D-06 removed a wall-clock flake, D-09
removed a misleading load parameter, and D-15 (TDD) made a thrice-refuted latent
finding falsifiable for the first time and then contained it.

## What Was Built

### Task 1 — D-10: `analytics-service/tests/_scan_helpers.py`, four consumers re-pointed

One plain module (not `conftest.py` — `tests/conftest.py` is reserved for pytest
hooks and imports pandas/numpy, so every collection would pay for path helpers)
exporting `_repo_root`, `_rel`, `_is_pure_comment`, `_count_in_text`, `_count`
and `_py_scan_files`.

**The divergence that mattered.** Before this commit:

| Site | `services/` coverage |
|---|---|
| `test_computing_started_at_stamp` | full `rglob` walk |
| `test_job07_reaper_off_worker_loop` | 2 files, hand-listed |
| `test_dark_path_deleted` | 2 files, hand-listed |

`test_job07`'s docstring claimed *"same file list as
`test_dark_path_deleted._py_scan_files`"* (true) **and** that it covered *"any
wiring of reaper work"* (false — `services/` was cherry-picked). Both claims were
deleted and replaced with a statement of the actual surface plus the history of

The shared `_py_scan_files` is the union
`{main_worker.py, main.py} ∪ services/** ∪ routers/** ∪ scripts/**`, a strict
superset of both narrow copies. No file is named by hand.

**Naming conflict surfaced, not averaged.** Four copies of the comment detector
existed under two names. `_strip_comment` is a lie — it returns `bool` and strips
nothing. `test_computing_started_at_stamp` had already renamed it
`_is_pure_comment`; that name won and the other three call sites were re-pointed.

**Deliberately NOT folded** (verified as genuinely different, not merely
similar-looking): `_strip_comments` (plural, whole-text → `str`) at
`test_job_worker_flipretry.py:278`, and the `Path(__file__).resolve().parents[2]`
repo-root mechanism in `test_main_worker.py` / `test_f4_sweep_fixture_parity.py`.

**Widening safety was checked before relying on it**, not assumed: greps for
`run_strategy_analytics`, `run_compute_analytics_job`, `BROKER_DAILIES_VIA_FUNDING`,
`"compute_analytics"`, `reap_strategy_analytics_stuck_computing` and
`reset_stuck_computing_rows` across the newly-added `services/**` surface return
zero non-comment hits, so no gate reddens on correct code. (The one hit,

### Task 2 — D-06 + D-09 in `test_job07_reaper_off_worker_loop.py`

**D-06:** the yielding control arm's sub-100 ms probe-latency assertion is
**deleted, not loosened**. It pinned real elapsed time against a real asyncio
server while pytest shards run in parallel on a shared CI runner, and its message
("a yielding reap must not delay healthz") pointed the next engineer at the
reaper instead of runner contention. The surviving
`tick_after_work > tick_before_work` and `probe_landed_mid_dispatch` assertions
are the deterministic proof — see SC-06 below, where exactly one test flips.

**D-09:** the janitor-sim driver now builds `backlog_rows=0`. Nothing it
exercises reads the backlog (`dispatch` is patched out; the reaper lives in
pg_cron), and the `5_000` implied that backlog size was load-bearing for the
healthz outcome. This one call site accounts for 10,000 of the 15,000 dicts the
finding counted, because the driver runs twice (blocking + yielding arms).

### Task 3 — D-15 (TDD): arity containment in `long_fetch.py`

The late import, the fixed-arity unpack and the dependent `tail_kind` selection
now sit **inside** the `try:` at `long_fetch.py:598` whose own comment already
promised the block must never crash the handler. Indentation confirms it: `try:`
at column 8, the import at column 12.

New `analytics-service/tests/test_long_fetch_follow_on_guard.py` — two tests:

1. **The protection.** `monkeypatch.setitem(_jw.JOB_CHAIN_FOLLOW_ON,
   "process_key_long", (…3-tuple…))`, driven through the deribit ledger-backed
   path, asserts the handler does not raise, returns `DONE`, **and logs
   `process_key_long.enqueue_tail_failed`** — containment without a log would be
   an invisible dropped chain, strictly worse than the crash it replaces.
2. **Negative control.** With the real 2-tuple, the ledger tail is still selected
   from element 0 and still enqueued. Without this, a hoist that swallowed every
   follow-on enqueue would satisfy test 1 while silently killing the feature.

Assertions route by RPC **name** (`c.args[0] == "enqueue_compute_job"`), never by
call-counter position (PATTERNS S-8).

⚠️ **Provenance recorded honestly, in the test file's own docstring:** D-15 is
latent, not live. Pass A raised it three times and verifiers refuted it three
times — correctly, since the map is a module-level literal 2-tuple. This plan is
what makes it falsifiable; it is **not** evidence that Pass A missed anything.

## Deviations from Plan

### 1. [Rule 2 — Missing critical] The "two-line hoist" needed a third line

- **Found during:** Task 3, reading the `except` arm before editing.
- **Issue:** The `except` block logs `tail_kind=tail_kind`. Moving the unpack
  inside the `try:` means `tail_kind` is **unbound** when the unpack is what
  failed — the handler would raise `NameError` from inside its own containment
  handler. The plan (and CONTEXT D-15) describe this as a two-line hoist; that
  literal change would have replaced one escaping exception with another.
- **Fix:** `tail_kind: str | None = None` immediately before the `try:`.
- **Files modified:** `analytics-service/services/ingestion/long_fetch.py`
- **Commit:** `d868714f`

### 2. [Rule 3 — Blocking] Worktree base correction at startup

- **Issue:** The worktree spawned on merge commit `34127316` (default-branch
  fork), **3 commits behind** the plan's `EXPECTED_BASE` — the same misfire the
  wave-1 worktree hit. `git merge-base HEAD c1cc3e29` returned HEAD itself,
  i.e. HEAD was an ancestor of the expected base.
- **Fix:** `git reset --hard c1cc3e29` per `<worktree_branch_check>`, only after
  the HEAD/namespace assertions passed (`worktree-agent-a69e826b41f8b9e7e`, not a
  protected ref). Working tree was clean; nothing was discarded.
- **Commit:** n/a (pre-execution)

### 3. ⚠️ OPEN — Task 2 acceptance criterion 3 does NOT reach 0, deliberately

`grep -cF 'backlog_rows=5_000' analytics-service/tests/test_job07_reaper_off_worker_loop.py`
returns **1**, not 0.

The surviving site is line 399, inside
`test_healthz_stays_200_with_large_stranded_backlog` — a **different** test from
the janitor-sim driver the plan's `<action>` names, and one where the number is
genuinely the premise: the test asserts `len(stranded) == 5_000` as a
fixture-honesty guard (its comment cites the SEAMUX-08 "docstring that lies about
its own setup" class) and the test's own **name** states it. Zeroing it would
make the name false and gut the guard.

CONTEXT D-09 and PATTERNS §11 both cite only `:346` — the janitor-sim call — so
the action is single-site and the acceptance grep appears to have been written
assuming only one call site existed. **I fixed the site the action names and did
not game the grep** (e.g. by hiding the literal behind a constant). Flagging for
the verifier rather than reporting a clean sweep.

### 4. [Judgment] `_rel` moved into `_scan_helpers.py`

The plan's artifact `provides` names five helpers and omits `_rel`; PATTERNS
§7(d) explicitly lists it as moving. `_rel` exists in only one file (it is not a
duplication problem), but it is a one-line consumer of `_repo_root`, so keeping
them together avoids splitting the path helpers across two modules. Exported
alongside the five; no criterion is affected.

### 5. [Rule 1 — Bug in my own edits, twice] Prose tripped my own gates

Both caught by running the acceptance greps before committing, not after:

- My replacement comment for the deleted D-06 assertion **quoted the literal
  string** the acceptance grep searches for, so `grep -cF 'obs["latency"] < 0.1'`
  returned 1 on my own documentation. Reworded to "under a 100 ms ceiling".
- My `_scan_helpers.py` module docstring named `services/basis_series.py` as the
  concrete example of a newly-covered file, tripping
  `grep -c 'basis_series' … == 0`. Reworded to "any `services/` module the two
  narrow copies did not name by hand", plus an explicit note that no list here is
  hand-written.

This is the same defect class plan 01 hit (its deviation #3): documentation that
quotes the token a gate greps for. Worth noting as a recurring hazard in this
phase — every gate here is a string search, so prose about the gate is inside the
gate's blast radius.
