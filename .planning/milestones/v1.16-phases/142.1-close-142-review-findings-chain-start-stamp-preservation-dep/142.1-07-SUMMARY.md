## D-19 — the defect the gate caught on its first real run

Part 3 arm E went **RED**: 26 seeded stranded rows, zero foreign competitors, one
tick terminalized **26 of 26**. Expected 25.

Both arms bound their batch through
`UPDATE ... WHERE strategy_id IN (SELECT ... LIMIT 25 FOR UPDATE SKIP LOCKED)`.
`FOR UPDATE` makes the subplan un-hashable, so the planner attaches it as the
**inner side of a nested-loop semi-join and re-executes it per outer row**, each
re-execution applying a fresh `LIMIT`. The cap was per-rescan, never global.

Every static gate in two phases passed over it, because they all assert the
*presence* of the bound's tokens — and the tokens are there. Only executing the
body against real rows falsifies it. **This is the D-16 argument, vindicated on
its first exercise.**

Impact, stated precisely: the bound is a blast-radius control. Unbounded, one
`*/15` tick against a backlog of N stranded rows terminalizes all N in a single
statement and holds row locks on all N, on a table every live analytics write
touches. The rows are genuinely stranded (>16h, no active job), so this is a
**lock-duration and blast-radius defect, not data corruption**.

Fix: `20260803130000_reaper_limit_bound_materialized_cte.sql` — `WITH batch AS
MATERIALIZED (...)` on both arms, verified on TEST *before* the migration was
written (failed=25, still_computing=1, youngest survives). A `FROM`-clause
subquery form was also measured and **also reaps 26 of 26**, so single evaluation
is load-bearing, not stylistic. Class census: of 8 registered cron jobs, only
this one puts a `LIMIT` inside an `IN (...)`; the other seven carry no `LIMIT`.
