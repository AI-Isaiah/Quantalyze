# Phase 142.1 Plan 05: BEFORE UPDATE stamp trigger + NULL-stamp clock-start arm — Summary

Moved the `computing_started_at` invariant off every individual writer and onto the
table, as a self-contained `BEFORE UPDATE` trigger, and gave the reaper a second,
non-destructive cron arm that starts the clock on rows the reap arm can never see —
closing D-01 for writers that do not exist yet and D-11 with the only tier that can
see rows at all.

## What Was Built

### Task 1 — migration 20260803120000 and every coupling it forces

**The trigger (D-17 in its settled D-18 shape).**
`public.strategy_analytics_stamp_computing_started()` is bound `BEFORE UPDATE`, row
level, and nothing else. Four arms:

| Arm | Condition | Action | Why |
|-----|-----------|--------|-----|
| (a) | already `computing` AND already stamped | restore `OLD` stamp | never advance — D-01 |
| (b) | `computing`, update left it unstamped | `now()` | no computing row sits unstamped after an update |
| (c) | genuine transition in with its own stamp | respect it | the backfill anchor and the bridge's transition-in both need this |
| (d) | leaving `computing` | `NULL` | every exit clears the reaper key |

It coerces **silently** — a `RAISE` would kill the live `_mark_computing` call, burn
its three retries and strand the strategy. That is the accepted cost of Option A, and
it is only acceptable because plan 142.1-08's Part 6 makes the coercion observable.

The body reads only `NEW` / `OLD` / `TG_OP` and calls only `now()`. That is what makes
the `20260516170000:3-11` production-breaker structurally unreachable: the ACL is
re-checked at fire time for functions the body *calls*, and a body that calls nothing
has no ACL to lose. STEP 4 re-asserts it against the **deployed** `pg_get_functiondef`,
not against this file's text.

**Event scope is UPDATE-only on purpose, and the migration proves it at apply time.**
STEP 3 reads `pg_trigger.tgtype` and asserts the row bit, the before bit and the
update bit are set while the insert and delete bits are clear. Bits rather than text,
so the assertion does not depend on how Postgres formats a trigger definition.

**The companion arm (D-11).** The cron job keeps its name, its `*/15` cadence and its
reap statement — that statement is carried over **byte-identically** from
`20260802120000:505-526` (verified by `diff`, below). What is new is a statement
*before* it that sets `computing_started_at = now()` on `(computing, NULL, no active
job)` rows, bounded `LIMIT 25 FOR UPDATE SKIP LOCKED`, carrying **no interval literal
of its own** (C-11). Clock-start-first ordering is load-bearing: a row stamped by this
tick cannot be reaped by the same tick, so it gets a full threshold.

**Cadence honesty, two bounds not one.** The header states the main arm's ~16h15m
(restored to TRUE by the trigger) and the companion arm's own ~32.5 h worst case
(≤15 min to notice + 16 h threshold + ≤15 min to reap) as **separate** numbers, with
an explicit instruction not to quote the first for a NULL-stamp row.

**Same-commit couplings, all in `bafad3cf`:**

- `_REAPER_MIGRATION_NAME` **and** the prose comment above it in `test_main_worker.py`
  now name 20260803120000 (C-10). Without this the drift gate would have kept reading
  the superseded body and reporting green over something pg_cron no longer runs.
- `job_worker.py`'s `STRATEGY_ANALYTICS_REAP_THRESHOLD` comment likewise (W-a) —
  comment-only, verified by reading the diff.
- SQL-gate **arm D inverted** (C-6): a `(computing, NULL, no active job)` row must now
  end the tick still `computing` **and** stamped. Both halves assert, because
  non-destructiveness is half the property.
- SQL-gate **Part 4 retrofit** (D-18 part 2): the sentinel is seeded in the part's
  `INSERT` at `computing`, the mid-test `UPDATE` is gone, and the 4b assertion is
  byte-unchanged.
- The D-05 anti-vacuity pin moved for the deleted UPDATE site.

**Part 4's honesty note.** The header now says in as many words that (i) 4a's
`IF v_stamp IS NULL` is an S-2 **seed-integrity control** which after the retrofit
cannot fail on any behaviour of the code under test, (ii) the behavioural proof that a
transition *into* computing stamps has **left** Part 4 and lives in Part 1's structural
anchors, the migration's STEP 7 anchors, and Part 6/6b, and (iii) 4b is
**double-mutation defence-in-depth** — trigger arm (a) and the bridge's own Arm 3 each

with a ⛔ instruction not to credit 4b as the SC-2b proof in any evidence ledger, and
not to "restore" the transition-in proof by re-seeding at `'pending'`.

## Deviations from Plan

**1. [Rule 3 — Blocking] Worktree base was wrong on spawn**
- **Issue:** `git merge-base HEAD b086aad6` returned `34127316` — the same
  default-branch merge commit all three prior spawns in this phase landed on, and an
  ancestor of the required base. Without correction the plan's `depends_on: [142.1-03]`
  commits would not have been present.
- **Fix:** `git reset --hard b086aad6…` per `<worktree_branch_check>`, after the HEAD
  and `worktree-agent-*` namespace assertions passed.
- **Commit:** n/a (pre-execution). **This is now 4 for 4 in this phase.**

**2. [Rule 1 — Bug] The pin cannot express `reaper: 0` as an explicit entry**
- **Found during:** Task 1, step 11.
- **Issue:** The plan (and the plan's success criteria) say the per-file pin should
  "read reaper: 0". It cannot. `test_sql_gate_scoped_updates.py:156` builds `actual`
  with `{name: count for name, count in actual.items() if count}` — a file with zero
  matches never appears in `actual`, so an explicit `"…reaper.sql": 0` in
  `_EXPECTED_MATCH_COUNTS` would make the comparison fail. The two instructions
  (`pin reads 0` and `the gate is green`) are mutually exclusive as written.
- **Fix:** Removed the entry and replaced it with a ⚠️ note above the map stating that
  a count of zero is expressed by **absence**, explaining why, and confirming the gate
  is unweakened (a file that regains an UPDATE adds a key `_EXPECTED_MATCH_COUNTS` does
  not have, and the assertion still fires). A comment placeholder line records
  `reaper.sql: 0` and that plan 142.1-08 restores it at 3. **The gate's logic was not
  changed** — only the data and the documentation.
- **Files modified:** `analytics-service/tests/test_sql_gate_scoped_updates.py`
- **Commit:** `bafad3cf`

**3. [Rule 3 — Blocking] `PERFORM cron.unschedule` omitted**
- **Found during:** Task 1, step 6.
- **Issue:** `20260802120000:448-450` does unschedule-then-schedule. Mirroring that
  would put a second `PERFORM` in the file and break the plan's own criterion that
  every `PERFORM` be `PERFORM cron.schedule`.
- **Fix:** Relied on `cron.schedule` upserting by job name (which the plan itself
  asserts), and closed the risk that removes — a duplicate job still running the
  superseded one-arm body — **harder than the unschedule closed it**, with a
  `count(*) = 1` assertion in STEP 6 that names exactly that failure mode. A comment
  beside the call explains the reasoning.
- **Files modified:** the migration.
- **Commit:** `bafad3cf`

**4. [Rule 2 — Missing critical] Both self-verify regexes written lower-case**
- **Found during:** Task 1, drafting STEP 4.
- **Issue:** The natural spelling of the self-containment check (`v_fn ~* '\mPERFORM\M'`
  and `~* 'SECURITY DEFINER'`) would have tripped two acceptance criteria — the
  PERFORM-parity count and the whole-file definer-literal count, the latter of which
  does not strip comments at all. This is the phase's recurring hazard: prose or code
  *about* a gate sits inside that gate's blast radius.
- **Fix:** Wrote both literals lower-case. `~*` is case-insensitive by definition, so
  the checks are **identical in strength**, and a comment beside them states why the
  case was chosen. Everywhere else the migration cites `20260516170000:3-11` and uses
  descriptive phrasing instead of quoting the literals.
- **Files modified:** the migration.
- **Commit:** `bafad3cf`

**5. [Reported, not worked around] One acceptance criterion is unmeetable as written**
- **Criterion:** ``awk '/\$cron\$/,/\$cron\$/' <migration> | grep -o "interval '[^']*'" | sort -u`` should print only `interval '16 hours'`.
- **Evidence:** awk's range operator ends a range on the **same** line when the start
  pattern also matches the end pattern, so this expression selects each `$cron$`
  delimiter line as its own one-line range. Its actual output is the two delimiter
  lines and nothing else — **for the Phase 142 migration too**, so the command was
  broken before this plan existed, not by anything here.
- **Action:** Did **not** contort the file to make the command produce output. Verified
  the underlying property with the drift gate's own extraction
  (`re.search(r"\$cron\$(.*?)\$cron\$", …, DOTALL)`), which is also what CI actually
  uses: interval set is `['16 hours']` for the new migration and `['16 hours']` for the
  Phase 142 one. The property holds; the criterion's command does not measure it.

**6. [Scope note] `sync_strategy_analytics_status.sql` was not modified**
- The plan lists it in `files_modified` for Task 2. Regenerating produced no change to
  it — plan 01's D-12 run 1 had already brought it current, and this migration does not
  redefine that function. Only the new trigger-function snapshot was written.
