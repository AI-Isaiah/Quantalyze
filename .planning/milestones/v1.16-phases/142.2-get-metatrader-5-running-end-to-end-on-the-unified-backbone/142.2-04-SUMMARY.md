### A1 — CONFIRMED via the REAL PostgREST path, not the SQL fallback

The plan permitted a SQL `INSERT ... ON CONFLICT DO UPDATE` fallback, recorded honestly as partial.
**It was not needed, and would have proved little**: `ON CONFLICT DO UPDATE SET one_column`
trivially preserves every other column — that is plain SQL semantics. The actual question in A1 is
whether **PostgREST projects only the payload's keys**. That was tested directly.

Credentials: `.env.test.local`, verified to point at `https://qmnijlgmdhviwzwfyzlc.supabase.co`
(the script aborts if the host is not TEST). Target row chosen with `computation_status='complete'`
and `computing_started_at IS NULL`, deliberately **not** `computing`, to avoid the
`BEFORE UPDATE` stamp trigger from `20260803120000`.

| Step | Action | Result |
|---|---|---|
| 1 | `UPDATE ... SET series_completeness='ledger_complete'` | stamped; `computing_started_at` still NULL |
| 2 | `POST /rest/v1/strategy_analytics?on_conflict=strategy_id`, `Prefer: resolution=merge-duplicates`, payload **only** `{strategy_id, computation_status}` | **HTTP 200** — `series_completeness = 'ledger_complete'` **INTACT**; `sharpe = 1.4` intact |
| 3 (non-vacuity) | same upsert **including** `series_completeness: "sampled_gapped"` | value changed to `'sampled_gapped'` — so the path *can* write the column; step 2 is genuine preservation, not a no-op |
| 4 (cleanup) | upsert `series_completeness: null` | restored to `NULL`; `computation_status='complete'`, `sharpe=1.4` unchanged |

**Survival-by-omission is executed evidence.** The carrier design holds; plan 05's
`analytics_runner` task proceeds as written.

⚠️ **Incidental finding worth carrying forward:** the first attempt returned **HTTP 409 / 23505**
(`duplicate key ... strategy_analytics_strategy_id_key`) because `merge-duplicates` alone does not
resolve against a **UNIQUE constraint that is not the primary key**. The conflict target must be
named — `?on_conflict=strategy_id`. The production code already does this
(`.upsert(..., on_conflict="strategy_id")`), so this is not a defect; but any new upsert against
this table that omits the parameter will 409 rather than merge.

Post-test state confirmed clean: `series_completeness = NULL`, `computing_started_at = NULL` — the
stamp trigger produced no side effect.

### A2 — CONFIRMED, via a corrected check

**The plan's check was mis-specified.** It expected
`select count(*) from information_schema.column_privileges` to be **zero**, reading non-zero as
"column-level carve-outs exist". That view **expands table-level grants to every column**, so it is
never zero when table grants exist. The observed count was **512** = 32 columns × 4 roles × 4
privilege types — the signature of *uniform* grants, i.e. exactly the desired answer.

The meaningful test is whether the new column's privilege set **differs from its peers**:

```
total_columns                  32
distinct_priv_counts            1      <- every column identical
new_col_privs                  16
min_privs / max_privs       16 / 16
new_col SELECT (anon/auth/svc)  1/1/1
columns_differing_from_sharpe   0      <- zero carve-outs
```

**Zero columns differ.** The new column is covered by the existing table-level grants with **no
policy change**. Policy set unchanged and intact: `analytics_read` (SELECT), `analytics_insert_deny`
(INSERT), `analytics_update_deny` (UPDATE), all `{public}`.

⚠️ This also **empirically confirms** the migration review's anon-readability finding: `anon` holds
`SELECT` on `series_completeness`. That is not special to this column — every column on the table is
anon-selectable for published rows via `analytics_read`, and two `withPublishedOnly` code paths
embed `strategy_analytics (*)`. Logged to `TODOS.md` (commit `d935fa61`) as its own item rather than
special-cased here; protecting one enum while the splat stands would secure nothing.
