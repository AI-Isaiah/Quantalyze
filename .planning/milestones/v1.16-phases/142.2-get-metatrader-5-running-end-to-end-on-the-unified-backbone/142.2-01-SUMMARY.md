## Decisions Made

- **Used `information_schema.columns` (not `pg_attribute`) for the migration's self-verification.** The named analog (`20260802120000:546-560`) uses `pg_attribute`, but the plan's acceptance criteria are phrased literally in `is_nullable = 'YES'` / `column_default IS NULL` terms. Semantically identical; this also makes the migration's self-check and the CI gate read as the same assertion, which is the point of both.
- **Exactly three RAISE arms, no fourth type check.** The analog also asserts the column's type, but the acceptance criterion enumerates three arms. Type is asserted by the SQL gate (assertion 1) instead, so the property is not lost.
- **Kept `SET lock_timeout = '5s'` from the analog's transaction preamble.** `ADD COLUMN` nullable-with-no-default is metadata-only in modern Postgres, but it still takes a brief ACCESS EXCLUSIVE lock; the bounded wait is the production-safe form and is what the analog does.
- **No down-migration written.** `supabase/migrations/down/` stops at `20260714090000`; none of the recent migrations (including both 20260803 ones) carry a rollback file, and the plan does not ask for one.
