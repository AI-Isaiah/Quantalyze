## What shipped

### Task 1 — Producer 1: fail-loud at the derive persist seam (prior run)

`run_derive_broker_dailies_job` now reads `meta["series_completeness"]` and, when it is not a member
of `SERIES_COMPLETENESS_VALUES`, disposes the job as a **permanent FAILED** via the
`_dispose_broker_nav_error` idiom — `error_kind="permanent"`, and in strategy mode a terminal
`strategy_analytics` stamp carrying all four companion fields (`computation_warned` False,
`computing_started_at` None, `metrics_json_by_basis` None, csv_source flags). Key-mode refuses
without stamping, because an allocator key owns no `strategy_analytics` row.

The load-bearing detail is **placement**. The reconcile-span DELETE fires before the upsert; a check
placed between them would refuse to write the new series *after* destroying the old one. The test
asserts the DELETE **was never executed** on refusal, which is a stronger claim than "the job
failed".

T-142.2-14 is honoured: the refusal message carries the scrubbed, length-bounded verdict repr and
nothing else — no venue, no identifiers, no magnitudes.

### Task 2 — Producer 2: composites stamp `composite_stitched` (prior run)

`run_stitch_composite_job` carries `series_completeness="composite_stitched"` on its
`headline_payload`, as a **sibling** of `"data_quality_flags": merged_flags`, upserted by
`_write_headline_and_by_basis`. The diff touches zero lines of the `merged_flags` construction.

Why it is not optional: composites carry `api_key_id` NULL and zero fills, so once the gate drops
its `!apiKeyId` term in favour of a positive allow-list, an unstamped composite reads NULL → trade
branch → `INSUFFICIENT_TRADES` → **no composite could ever be approved again**. The terminal
`failed` arm deliberately omits the column so a prior verdict survives a failed re-stitch.

### Task 3 — Producer 3: keyless CSV stamps `user_supplied` (this run)

`run_csv_strategy_analytics` stamps `series_completeness="user_supplied"` on its `_mark_complete`
payload for genuinely keyless uploads, and writes the column **nowhere else in the file**
(`grep -c series_completeness analytics-service/services/analytics_runner.py` → **1**).

Two exclusions, both deliberate:

1. **Keyed** (`_is_broker_sourced`) — the column is absent from this and every other payload, so the
   derive-stamped verdict survives the analytics round trip by **omission** (A1, executed against
   TEST in plan 04: a PostgREST upsert projects only the payload's keys).
2. **Former composite** (`_was_composite`) — this run **verified the premise the stalled run
   asserted** rather than accepting it. Composites do carry `api_key_id` NULL
   (`src/app/api/admin/strategy-review/route.test.ts:1073`, a pre-existing test, independent of this
   phase), so a naive "keyless ⇒ user_supplied" would relabel a machine stitch as a human upload and
   erase producer 2's verdict. This run also established the *scope* of the guard, which the diff's
   comment did not: a **current** composite cannot reach this function at all, because
   `stitch_composite` is **chain-terminal** in `JOB_CHAIN_FOLLOW_ON` (`job_worker.py:516`) and the
   `derive_broker_dailies → compute_analytics_from_csv` chain requires a key. So the guard fires only
   across a composite→keyless transition, and it **self-heals**: this upsert rebuilds
   `data_quality_flags` wholesale, so the next run sees no `composite` flag and stamps
   `user_supplied`. Both values are allow-listed, so the one-run lag costs approvability nothing,
   while the wrong stamp would be a permanent lie.

⛔ The discriminator is **provenance, never current column state**. Stamping because the verdict
reads NULL would promote a keyed funding-only perp — whose combiner deliberately declined to certify
it — into the gate's allow-list, which is exactly the publication D-15 exists to refuse. The tests
assert on `api_key_id` shape, never on a NULL read.

Six new tests: keyless, keyed, former-composite, and all four terminal arms (insufficient-history,
truncation, config-error, catch-all). The keyed and former-composite tests **scan every captured
`strategy_analytics` upsert of the run**, not just the completion one — because
`_clear_stale_by_basis` is the standing counter-example in this very function that omission is a
*mechanism*, not a *guarantee*.

## Deploy window — in-flight jobs

Deploy order is **migration → worker → frontend**.

A derive job claimed under the old code that finishes after the new assert deploys simply carries no
verdict → the column stays NULL → the gate refuses on the next preview → it **self-heals on
re-derive**. Nothing already published changes: the gate runs at exactly two moments (wizard
`SyncPreviewStep`, admin approve).

The plan-04 PROD census sized the population at **6 unpublished strategies** (1 keyed, 4 keyless CSV,
1 composite) and **0 published composites**. The 4 keyless CSV strategies are the group this task
serves, and their remedy is re-running `compute_analytics_from_csv` — i.e. exactly this code path.
No backfill UPDATE is warranted for any group: it would fabricate a trust claim about series whose
inputs no longer exist.
