## Summary

The central change is sound. I attacked the new error path from every angle the
brief named and could not break it:

- **Handler precedence.** `main.py:597` registers on the `VenueTransientHTTPException`
  subclass; Starlette 0.52 `_lookup_exception_handler` walks `type(exc).__mro__`, so
  the subclass wins over FastAPI's default `HTTPException` handler. Registration happens
  at import time (line 597) before router inclusion (line 798+), and Starlette builds the
  middleware stack lazily in `__call__`, so ordering is irrelevant. **Verified empirically**,
  not by reading: deleting the registration reddens 14 of 19 cases in the new suite.
- **No swallow path.** Every `except HTTPException` in production code
  (`cron.py:970`, `debug_key_flow.py:147/190/239`, `portfolio.py:1174/2532`,
  `analytics_runner.py:1570`) either re-raises the object unchanged or is on an unrelated
  route. None of the seven raise sites sits inside an `except Exception` that could turn a
  400 into a 500. The routers are mounted on `main.app` only.
- **`detail` byte-identity holds at all 7 sites.** C1/C2 reuse `RATE_LIMITED_DETAIL` /
  `NETWORK_ERROR_DETAIL`, C3–C5 reuse `NETWORK_ERROR_DETAIL`, C6/C7 pass `result["error"]`
  through untouched. Serialization is identical too: FastAPI's default handler and the new
  handler both use `starlette.responses.JSONResponse`, so the em-dash in `RATE_LIMITED_DETAIL`
  encodes the same bytes (`ensure_ascii=False`) before and after.
- **The `error ⇒ error_code` producer invariant holds.** I read every branch of
  `validate_key_permissions` (`services/exchange.py:1035-1262`): all nine sites that assign
  `result["error"]` assign `result["error_code"]` in the same branch, and the dict is
  initialised with `"error_code": None` so `result["error_code"]` can never `KeyError`.
  The invariant is mechanised by an AST test at the producer.
- **`internal.py` authn ordering.** `_verify_internal_token(request)` runs at `:224`,
  `_consume_rate_limit(key_id)` at `:226`. Pinned by a test that empties the bucket with
  unauthenticated calls and then proves an authenticated call is still admitted.
- **`permanent` fall-through is fail-safe.** `val.permanent is True` (identity, not
  truthiness) means `None` — every non-MT5 adapter — falls through to the byte-unchanged
  list. `_probe_error` still short-circuits transient *before* the permanence check, so a
  fail-closed probe cannot be turned permanent.

**Mutation testing (5 mutations, 5 killed):** unregister the handler → 14 fail; force
`recoverable=True` at C6 → the AUTH_FAILED control fails; drop the `val.permanent is True`
consult → 2 fail; drop `permanent=True` from `_wrong_server()` → 1 fail; reword
`NETWORK_ERROR_DETAIL` → 5 fail including the cross-artifact pin. Deleting a `_SHAPES` row
now reddens the new one-to-one corpus fence (it did not before).

**Hygiene:** full analytics-service suite green (4772 passed, 96 skipped). `mypy --strict
--follow-imports=silent services/ routers/ models/` shows only pre-existing
missing-stub/untyped-call errors from the local env — zero new. Zero new `# type: ignore`,
zero debug artifacts.

**Test quality is genuinely good** — this is not the usual "tests that pass regardless".
The oracles are cross-artifact (test literal vs production constant vs committed fixture vs
router AST), both polarities of `recoverable` are pinned, the exact key set is asserted so a
fall-through to the default handler cannot pass, and the `inspect.unwrap(route.endpoint).__globals__`
workaround is **sound**: `evict_module("routers.exchange")` really is called by five sibling
suites (`test_sfox_validate.py:87/92`, `test_create_exchange_attribution.py:126/131/364/371`,
`test_mt5_validate.py:97/102`), and `main.app`'s routes genuinely hold the *first* module's
function objects, so patching the re-imported module would not reach the executed code. It is
a correct fix for a real hazard, not a way to make tests pass.

The findings below are all real but none of them changes behaviour a user sees today.

## Medium

### M-01: `internal.py`'s 429 becomes `[object Object]` in the live TS consumer's error log

**File:** `analytics-service/routers/internal.py:246-252` →
`src/app/api/keys/[id]/permissions/route.ts:144-145,275`

**Issue:** PYAPIFIX2-03 replaced a scalar body
`{"detail": "Too many permission probes for this key. Try again in a moment."}`
with the nested envelope `{"detail": {code, dependency, retryable, detail}}`.
The live consumer does:

```ts
const err = await res.json().catch(() => ({ detail: res.statusText }));
throw new Error(err.detail ?? `Upstream ${res.status}`);   // route.ts:145
...
console.error(`[keys/permissions] proxy failed for ${keyId}:`, err);  // route.ts:275
```

`new Error(<object>)` produces `message === "[object Object]"`. This is verbatim the failure
mode the *same phase* forbids at the sibling seam — `routers/exchange.py:150-160` and the
`VenueTransientHTTPException` docstring both name "[object Object]" as the reason the flat
shape is mandatory — and it was committed on the other side of the service in the same phase.

I traced the blast radius: the downstream classifier (`route.ts:257-268`) keys on
`startsWith("Upstream 5")` / `includes("not configured")` / `includes("timeout")`, none of which
matched the old sentence either, so **both before and after this change the reply is
`PROBE_FAILED` / 502**. The regression is therefore **diagnostics only** — an operator reading
the Vercel log for a throttled probe now sees `Error: [object Object]` instead of the human
sentence. That, plus the fact that five *pre-existing* `service_error` sites on the same endpoint
(`internal.py:300/316/330/471/495`) already do this and `STATUS_CONTRACT.md:113-127` records it as
accepted debt pending 140.2, is why this is Medium and not High.

**Fix:** either (a) add the 429 to `STATUS_CONTRACT.md`'s §2 "Obligation this creates for 140.2"
list so 140.3 knows the 429 is now in the object-detail set, or (b) keep the header/`code` win but
leave the body scalar the way `main.py`'s app-global 429 does. (a) is the smaller change and matches
the phase's own recorded reasoning.

### M-02: `ValidationResult.permanent` is documented as tri-state but implemented as bi-state

**File:** `analytics-service/services/ingestion/adapter.py:133-153`,
`analytics-service/services/ingestion/long_fetch.py:410-418`

**Issue:** The field's docstring states three distinct meanings:

```
True  -> "this rejection can never clear by retrying"
False -> "retrying may succeed" (an explicit transient verdict)
None  -> "this adapter states no verdict"
```

But the only consumer is:

```python
_is_permanent = (
    val.permanent is True
    or _reject_code in permanent_codes
    or (_reject_code == "VALIDATION_UNEXPECTED" and _is_unexpected_fallback)
)
```

`False` short-circuits nothing. An adapter that explicitly states "retrying may succeed" on a
result carrying `error_code="AUTH_FAILED"` is still classified **permanent**, because the `or`
falls through to the list. The documented third state does not exist in behaviour, and there is
no test for it (the new suite tests `True` and `None` only).

**Failure scenario:** a future exchange adapter that can distinguish a genuine bad key from a
venue-side auth blip sets `permanent=False` on the blip, still tagging it `AUTH_FAILED` for copy
reuse. The worker marks it permanent, the key is failed_final, and the author's explicit
statement was silently ignored.

**Fix:** make the stated verdict authoritative in both directions:

```python
if val.permanent is not None:
    _is_permanent = val.permanent
else:
    _is_permanent = (
        _reject_code in permanent_codes
        or (_reject_code == "VALIDATION_UNEXPECTED" and _is_unexpected_fallback)
    )
```

…or narrow the docstring to `True | None` and drop the `False` sentence. Add a test for whichever
is chosen.

### M-03: the provenance channel has one consumer; the two sibling classifiers still key on strings

**File:** `analytics-service/routers/process_key.py:398-412` (`_envelope_error` derivation) and
`:1425-1428` (the 424 venue-transient pre-gate)

**Issue:** The phase's stated root cause is that "the consumers' permanent-code sets are
structurally uncompletable" (`adapter.py:145-149`). It then wires the provenance channel into
**one** of three classifiers. `_envelope_error`'s `recoverable` derivation and the sync-arm 424
pre-gate both still key on `_ROUTE_TERMINAL_ERROR_CODES` ∪ `PERMANENT_VALIDATION_ERROR_CODES`,
neither of which knows `MT5_WRONG_SERVER` / `MT5_MASTER_PASSWORD` or any pandera-minted CSV code.

This is currently **unreachable** for MT5 — `process_key.py:216-225` admits `mt5` to
`onboard`/`resync` only, and `_is_long_fetch` routes both to the worker — so I verified the
CONTEXT's claim and it holds today. But the phase closed the class at one of three sites while
naming partial closure as the defect it exists to prevent, and the next adapter that states
permanence (or any change to `_is_long_fetch`) gets two contradictory verdicts on two paths for
one rejection.

**Fix:** thread `val.permanent` into `_envelope_error` (it already accepts an explicit
`recoverable: bool | None`, so the plumbing exists: `recoverable=None if val.permanent is None
else not val.permanent`) and into the 424 pre-gate's condition. If deferring, record it in
`TODOS.md` beside the four-vocabulary-unification item rather than only in a phase SUMMARY.

### M-04: `VenueTransientHTTPException` guards `detail`, `code` and `recoverable` — but not `status_code`

**File:** `analytics-service/services/error_contract.py:399-428`

**Issue:** The class refuses a non-scalar `detail`, an empty `code` and a non-`bool`
`recoverable`, but accepts any `status_code` ≥ nothing at all. `super().__init__` passes it
straight through. A future site copying the C3 block and writing `status_code=503` would emit a
**flat 5xx with no `dependency` and no `Retry-After`** — a direct R-2 violation that
`service_error`'s `_validate` would have refused, and which 140.2 (SEAMCORE-01) keys its
per-dependency breaker on. Nothing in the class, the handler or the tests pins the status to 4xx;
the wire tests pin 400 at the seven sites but not the class's admissible range.

**Fix:** add to `__init__`, matching the module's ValueError posture:

```python
if not 400 <= status_code < 500:
    raise ValueError(
        "VenueTransientHTTPException is a CALLER-class 4xx shape: it carries no "
        "`dependency` and no Retry-After, so a 5xx here would violate R-2 and "
        f"mis-key 140.2's breaker. Use service_error() for 5xx. got {status_code!r}"
    )
```

### M-06: `venue_transient_exception_handler` silently drops `exc.headers`

**File:** `analytics-service/main.py:584-594`

**Issue:** `VenueTransientHTTPException` inherits `HTTPException`, which carries a `headers`
attribute (`None` at all seven current sites, because `__init__` never forwards one). The handler
constructs `JSONResponse(status_code=..., content={...})` with no `headers=` argument, so any
header a future site sets is dropped without a trace. FastAPI's default handler — the one this
replaced — *does* forward `exc.headers`. Given the sibling handler two blocks above
(`rate_limit_exceeded_handler`, `main.py:529`) exists precisely to emit `Retry-After`, a future
venue-transient site wanting a `Retry-After` is a plausible next step.

**Fix:** `return JSONResponse(..., headers=verdict.headers)` — one word, and it restores parity
with the handler this one shadows.

### M-07: one route, two body shapes for the same user-visible condition

**File:** `analytics-service/routers/exchange.py:111`, `:141`, `:196`, `:256`, `:257`, `:399`,
`:401`, `:419-421` (bare `{detail}`) vs `:598-603` (C6, `{detail, code, recoverable}`)

MT5 bad-password yields `{"detail": AUTH_FAILED_DETAIL}` with no `code` at all — same route, same
status, byte-identical `detail`. Same for `MT5_WRONG_SERVER_DETAIL` and
`MT5_MASTER_PASSWORD_DETAIL`, which carry no machine code anywhere on the HTTP path even though
the *worker* path now knows they are permanent (PYAPIFIX2-02).

The phase acknowledges this in a test docstring

permanent-only arms … carry no machine code either") but it is not in `TODOS.md`, so it lives only

differently per venue for an identical condition.

**Fix:** record it in `TODOS.md` under the v1.16 routed findings (the phase already routed two
other items there, so the mechanism exists), or close it by giving the permanent 400 arms the same
flat shape with `recoverable=false`.

## Low

### L-01: three new `Retry-After` values advertise the full window when the true remainder is known

**File:** `analytics-service/routers/simulator.py:260`,
`analytics-service/routers/portfolio.py:1971`, `:2263`

All three throttles are **sliding windows** (`_check_simulator_user_rate`,
`simulator.py:117-150`, keeps a per-user list of timestamps), so the true wait is
`bucket[0] + WINDOW - now`, which can be a second. The new header always advertises `3600`.
That is safe (never under-advertises) but it can tell a user one second from a free slot to come
back in an hour. The service already has the better pattern:
`main.py:_retry_after_seconds` (`:461-490`) reads the real remainder and falls back to the window
only when it cannot. The bodies interpolate no number here, so there is no header/body
contradiction — hence Low.

**Fix (optional):** have `_check_*_rate` return `(ok, retry_after)` and pass the remainder through,
mirroring `main.py:_retry_after_seconds`.

### L-03: `type(x) is not str` vs the module's own `isinstance` convention

**File:** `analytics-service/services/error_contract.py:406`, `:413`

`service_error_body:252` — the analogous scalar guard in the same module, written in the same
programme — uses `not isinstance(detail, str)`. The new class uses `type(detail) is not str`,
which additionally rejects `str` subclasses. No caller passes one today. Not a bug; an
inconsistency in a module whose whole point is that one rule lives in one place.

### L-04: the producer-invariant AST test has both a false-positive and a false-negative mode

**File:** `analytics-service/tests/test_validate_key_venue_transient.py:944-995`

The pairing walk requires `result['error']` to be assigned **before** `result['error_code']` in the
same statement list. A future branch that assigns the code first is reported as unpaired (false
red), and a branch that sets the error via anything other than a bare `ast.Assign` — e.g.
`result.update({...})` or `result["error"] = f"..."` (an `ast.JoinedStr`, not an `ast.Constant`,
which the *copy* test at `:925` silently skips) — escapes the check entirely (false green).

**Fix:** treat any `result['error_code']` assignment anywhere in the enclosing branch as closing
the obligation, and assert that the number of `result['error']` assignments found is non-zero so a
walker that stops matching reddens instead of vacuously passing.

### L-05: the cross-language fixture can grow uncovered cases silently

**File:** `analytics-service/tests/fixtures/validate_key_venue_transient_contract.json`,
consumed at `test_validate_key_venue_transient.py:153`, `:380`

Deleting a case reddens (`_BY_TRIGGER[trigger]` → `KeyError`). **Adding** one does not: nothing
asserts that every `cases[]` entry is driven by a test. The file is 140.3's TS input, so a case
added there and never exercised in Python would hand the other language a contract nobody emits —
the exact drift the `spec["body"] == body` assertion exists to prevent, from the other direction.

**Fix:** collect the triggers exercised during the session and assert
`set(exercised) == set(_BY_TRIGGER)` in a session-scoped teardown, or add a simple
`test_every_fixture_case_is_driven` listing the trigger names.

### L-06: `recoverable: true` for `UNSUPPORTED_EXCHANGE`

**File:** `analytics-service/routers/exchange.py:601`
(`recoverable=result["error_code"] not in PERMANENT_VALIDATION_ERROR_CODES`)

`UNSUPPORTED_EXCHANGE` (`services/exchange.py:1219`) can never clear by retrying, but it is not in
`PERMANENT_VALIDATION_ERROR_CODES`, so the new field advertises a retry affordance for it. The arm
is effectively unreachable — `create_exchange` already gates on `EXCHANGE_CLASSES` and raises
`ValueError` for unknown ids — and `UNSUPPORTED_EXCHANGE` was explicitly REFUTED and fenced out of
this phase's scope, so the *classification* is inherited. What is new is that this phase put the
derived boolean on the wire. Worth one line in `TODOS.md` beside the four-vocabulary item.
