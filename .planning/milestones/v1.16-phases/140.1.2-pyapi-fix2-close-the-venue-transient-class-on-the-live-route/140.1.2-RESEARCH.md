## Summary

The phase is correctly scoped small, and the evidence that produced it is **mostly** right. Reading
the source resolved the two disputes it was told to resolve, and found **seven** places where the
review evidence, the CONTEXT or REQUIREMENTS is wrong at source. Two of those are load-bearing enough
to change what the plans must do:

1. **PYAPIFIX2-01 cannot achieve its stated success criterion in Python alone.** The criterion says a
   test must prove a Binance-maintenance failure "no longer renders as `UNKNOWN`/500". At source,
   `src/app/api/strategies/create-with-key/route.ts:483` returns `{ code }` with the status that
   `classifyKeyValidationError` *computed from the message string* — **the upstream HTTP status is
   discarded entirely**. So changing Python's `400` to `424` changes nothing a user sees; and turning
   `body.detail` into an object (the `service_error` envelope) makes it **strictly worse** at three of
   five codes, because `src/lib/analytics-client.ts:177-181` does `error.detail ?? …` and would feed
   `"[object Object]"` into the cascade. This is exactly the hazard TS-32 already recorded as
   `BLOCKED-BY: TS-05` — and PYAPIFIX2-01 inherits it. A zero-regression, Python-only design exists
   (the PYAPI-08 flat shape, §PYAPIFIX2-01 below); the *render* half must be recorded as a 140.3
   obligation, not attempted here.

2. **PYAPIFIX2-02 reproduces on exactly one half, and both red teams were right for reasons neither
   stated.** The `long_fetch` half is **LIVE** (`services/ingestion/long_fetch.py:391-402` — proved by
   reading the code path end to end). The sync-424 half is **UNREACHABLE**, but *not* because "MT5
   never calls `validate_key_permissions`" — that gate keys on the **adapter's** `val.error_code`, not
   on `validate_key_permissions` at all. It is unreachable because `routers/process_key.py:221-233`
   admits `source="mt5"` **only** to `flow_type ∈ {onboard, resync}`, and `_is_long_fetch`
   (`:600-606`) routes both to the worker before the sync path at `:1335-1339` is ever reached.

Everything else is small, precise and confirmed at source. `mypy --strict`, `pytest`, `pandera
0.32.1` and `slowapi 0.1.10` (the CI pin) are all present and working in this environment.

**Primary recommendation:** three plans. Wave 1 = PYAPIFIX2-02 (reproduce-first gate, may exit early)
+ PYAPIFIX2-03/04 (429 hygiene, mechanical). Wave 2 = PYAPIFIX2-01 (behaviour-enumerated, additive
flat shape only — **never** an object `detail`) + PYAPIFIX2-05. Wave 3 = PYAPIFIX2-06 (artifact truth,
four named items, each re-derived at source, never arithmetically).

### C-1 ⭐⭐ (BLOCKING) — PYAPIFIX2-01's stated success criterion is **not satisfiable in Python alone**, and the obvious Python fix makes three of five codes WORSE

**What the evidence says.** ROADMAP criterion 1 / REQUIREMENTS PYAPIFIX2-01: *"A test must prove that
a Binance-maintenance-shaped failure during key-connect no longer renders as `UNKNOWN`/500 'our team
has been notified' with no retry affordance."*

**What the source says.**

```
src/lib/analytics-client.ts:174-181
    if (!res.ok) {
      const contentType = res.headers.get("content-type") ?? "";
      if (contentType.includes("application/json")) {
        const error = await res.json().catch(() => ({ detail: res.statusText }));
        throw new AnalyticsUpstreamError(
          error.detail ?? "Analytics service error",
          res.status,
        );
```
```
src/app/api/strategies/create-with-key/route.ts:472,483
    const { code, status } = classifyKeyValidationError(err);
    …
    return NextResponse.json({ code }, { status, headers });
```

`classifyKeyValidationError` (`src/lib/wizardErrors.ts:936-1035`) derives BOTH the `code` and the
`status` from `err.message` — i.e. from `error.detail`. **The upstream HTTP status is read at
`analytics-client.ts:180` and then never used to decide anything.** `composite/add-key/route.ts:427`
is byte-identical in this respect.

Two consequences:

1. **Changing Python's `400` → `424` changes nothing a user sees.** The status is discarded.
2. **Changing `body.detail` from a scalar string to the `service_error` object makes it strictly
   worse.** `error.detail ?? …` would then hand a JS object to `new AnalyticsUpstreamError(message,…)`;
   `message` becomes `"[object Object]"`; `lower` matches no branch; every code lands on
   `UNKNOWN`/500. Today three of the five codes route correctly — verified by running the literal
   strings through the cascade by hand:

   | `error_code` | `result["error"]` literal (source) | Cascade branch | Today's verdict |
   |---|---|---|---|
   | `RATE_LIMITED` | `services/exchange.py:35-39` "Exchange **rate**-limited the validation request…" | `:1011` `"rate"` | `KEY_RATE_LIMIT` / 503 ✓ |
   | `PROBE_FAILED` | `services/exchange.py:1250-1253` "**Could not verify** the key's permission scopes…" | `:1024` | `KEY_PROBE_FAILED` / 503 ✓ |
   | `DDOS_PROTECTION` | `services/exchange.py:1155-1158` "…Check region / **IP** **allow**list." | `:1007` | `KEY_IP_ALLOWLIST` / 502 (wrong code, right flavour) |
   | `EXCHANGE_UNAVAILABLE` | `services/exchange.py:1179-1181` "Exchange is currently unavailable. Try again in a few minutes." | none | **`UNKNOWN` / 500** ✗ |
   | `NETWORK_UNAVAILABLE` | `services/exchange.py:40-43` "**Network** error reaching the exchange…" | none (branch tests `timeout`/`etimedout`) | **`UNKNOWN` / 500** ✗ |
   | `PERMISSION_DENIED` | `services/exchange.py:1131-1134` "…your **IP** **allow**list includes our service." | `:1007` | `KEY_IP_ALLOWLIST` / 502 — *a permanent caller fault rendered as an upstream 502; noted, out of scope* |

   ⇒ a naive Python-side remap to `service_error(424, …)` would take `RATE_LIMITED`, `PROBE_FAILED`
   and `DDOS_PROTECTION` from correct-or-nearly to the terminal dead end. **This is exactly the
   hazard `140.1-TS-OBLIGATIONS.md` TS-32 recorded as `BLOCKED-BY: TS-05`** — and PYAPIFIX2-01
   inherits it verbatim, because it names the same seam.

**What this means for the plan.** PYAPIFIX2-01 must be re-scoped to what Python can actually make
true, with the render half recorded as a 140.3 obligation. See §PYAPIFIX2-01 for the recommended
zero-regression design (the **PYAPI-08 flat shape**: top-level `detail` stays a scalar, `code` /
`recoverable` ride alongside it).

## PYAPIFIX2-05 — the 200-discriminator corpus cannot silently shrink

### Source of the gap

`analytics-service/tests/test_process_key_200_discriminator.py`:

green — observed as `141→140 passed` by the review.

### Recommended oracle (non-self-referential, cross-artifact)

The banned shape is *literal vs. literal in the same file*. The sanctioned shape is *a pinned contract
confronted with the code's real behaviour* (the file's own comment at `:434-437` says exactly this).
So bind `_SHAPES` to the **router's AST**, with the two sides derived from two different artifacts:

1. **ACTUAL side A** — the AST-derived fingerprint set already computed at `:572-589`, filtered to its
   `dict:` entries (the reachable wire shapes; `call:` entries are delegation edges).
2. **ACTUAL side B** — for each `_SHAPES` row, drive `reach(client)` and fingerprint the **real
   response body** as `"dict:" + ",".join(sorted(body))`.
3. **Assertion** — every `dict:` fingerprint from side A is covered by side B.

Deleting a `_SHAPES` row leaves a router-declared 200 shape with no reaching case ⇒ **RED**, with a
message naming the uncovered fingerprint. Neither side is a literal typed beside the other.

**Known wrinkle the planner must resolve empirically, not by assumption:** shape 6
(`6-envelope-error-at-200`) returns through `_envelope_error`, which is **not** in
`_SHAPE_BEARING_FUNCTIONS`, so its dict has no AST fingerprint — its wire fingerprint would be
"extra". Two clean resolutions:
- **(a)** add `_envelope_error` to `_SHAPE_BEARING_FUNCTIONS` and pin its dict fingerprint, then assert
  **set equality** (tighter — also catches a junk row being added); or
- **(b)** keep `_SHAPE_BEARING_FUNCTIONS` as-is and assert **coverage (⊇)** only.

Recommend (a). Either way the planner must verify empirically that a wire body's sorted top-level keys
equal the AST dict fingerprint at every shape — they can diverge if a return dict is post-processed by
FastAPI's `response_model`. **Check before pinning.**
