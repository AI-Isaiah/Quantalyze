## ⭐ HALF A (the sync `/process-key` 424 gate) — RECORDED **UNREACHABLE**, ZERO CODE

**No defensive membership was added.** An unreachable-by-construction guard is dead code; the
wire-boundary validator is the real fence. `git diff` for this plan contains **no**
`routers/process_key.py` change.

The proof (C-2), re-verified at source this session — note that **neither red team's stated reason is
the reason**. The 424 pre-gate does *not* consult `validate_key_permissions`; it reads the adapter's
own `ValidationResult.error_code`, and `get_adapter("mt5")` really does mint the two codes. If that
line were reachable with `source="mt5"`, the claim would hold. It is unreachable for a different
reason — **the wire-boundary whitelist plus the long-fetch routing**:

## Decisions Made

1. **Provenance, not enumeration.** CONTEXT-locked: `csv_adapter.py` mints `error_code` from a
   pandera rule name (`first_rule.upper()`), an open code space no list can close, so any fix keyed
   on a string list is wrong by construction. The adapter that minted the code is the only component
   that knows whether it can clear, so it states the verdict.
2. **Tri-state with a `None` default, consulted via `is True`.** Anything else would restate every
   existing adapter's retry verdict by accident. `None` is what all six other adapters return today.
3. **`long_fetch`'s local set left byte-unchanged.** Re-pointing it at
   `PERMANENT_VALIDATION_ERROR_CODES` would flip `MISSING_SCOPE` transient→permanent on the worker
   path — a production behaviour change named in no requirement, and the divergence is documented as
   deliberate at `services/exchange.py`.
4. **No four-vocabulary unification proposed.** It is backlogged (OB-11/OB-12). The new field is its
   seed only; `CREDENTIAL_REJECTION_CODES` (`routers/cron.py`) remains the fail-SAFE polarity to
   unify toward if it is ever picked up.
5. **Cross-language note (recorded, no action):** `wizardErrors.ts:1001-1006` already classifies both
   codes as 400 client faults. Before this plan Python and TypeScript held **opposite** verdicts on
   the same two codes; they now agree. No TypeScript was touched.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in the plan's test shape] Tasks 1A/1B rewritten to drive the REAL `Mt5Adapter`**

- **Found during:** Task 2 (the fix went in and the tests stayed RED).
- **Issue:** The plan's Task 1 `<behavior>` specifies a stub adapter returning a **hand-built**
  `ValidationResult(error_code="MT5_WRONG_SERVER", ...)`. That shape is only satisfiable by a fix
  that keys on the **string** — exactly the design Task 2 forbids ("any fix keyed on a string list is
  wrong by construction"). Under the mandated provenance design a fabricated `ValidationResult`
  carries `permanent=None` and stays transient, so the two specs are mutually incompatible. Making
  the test pass by adding `permanent=True` to the *test's own* object would have been a pure
  tautology: the test would assert what the test itself decided.
- **Fix:** Both tests now drive production end-to-end. Test A instantiates the real `Mt5Adapter` with
  a blank broker server → its **offline** wrong-server rejection (a spy on `_build_client` asserts no
  RPyC client is constructed). Test B instantiates the real `Mt5Adapter` against the canonical
  offline terminal double reused from `tests/test_ingestion_mt5.py` (`_install_client` +
  `_FakeNamedTuple(trade_allowed=True, login=123456)`) → the real `MT5_MASTER_PASSWORD` mint. Both
  then assert on `error_kind`. Cross-test-module imports are an established convention in this suite
  (`tests/test_cash_basis_series_sc4.py`, `tests/limiter_stub`, etc.), and reusing the double is what
  stops this test drifting from the adapter suite's notion of a trade-capable account.
- **Oracle integrity:** unaffected and arguably improved. The **expected** side is still a literal
  typed in the test (`"permanent"`); only the **actual** side is now derived from production
  behaviour end-to-end — the sanctioned direction (PATTERNS S-3), and the opposite of a
  self-referential oracle. Grep of the new test block for
  `MT5_WRONG_SERVER_DETAIL|MT5_MASTER_PASSWORD_DETAIL|permanent_codes|PERMANENT_VALIDATION` → **0**.
- **Verification:** RED re-observed first-hand against pre-fix production (3 failed / 29 passed),
  then GREEN (32 passed). Both pasted above.
- **Committed in:** `c3819c2d` (test) — the fix itself in `861b7315`.
