`CSV_PERSIST_FAIL`, `CSV_FINALIZE_FAIL` — and RESEARCH §12.2's `!res.ok` measurement was scoped to
*"bodies with NO top-level `code`"*, the upstream-forwarded population only.

**The three-way arm on `!res.ok`:**
1. top-level `data.code` ∈ the client's hand-typed `KNOWN_CSV_*` roster → **keep today's path**:
   `CsvValidationEnvelope` with the route's own `human_message` (the route's copy — including its
   CORRECTED sentences — wins; this plan must not touch that copy).
2. else `recogniseSeamErrorCode(seamErrorCode(data)) !== "UNKNOWN"` → the seam hop: shared
   `ErrorEnvelope` with the advertised wait (reads flat AND nested `service_error` shapes).
3. else (unrecognised or codeless) → §4a: `CSV_UPSTREAM_FAIL` founder copy via shared envelope.

**Why roster-FIRST is load-bearing (checker B-7 — a hop-first draft of this plan was rejected):**
both CSV routes emit `SEAM_MISCONFIGURED` with a ROUTE-CORRECTED `human_message`
(`csv-validate/route.ts:224-236` — the 140.4-16/WR-07 fix: `req.formData()` runs ~50 lines above
the deny, so the file has ALREADY crossed the wire and the generic
`WIZARD_ERROR_COPY.SEAM_MISCONFIGURED` clauses *"Nothing was submitted"* / *"The request never
left our servers"* are FALSE there; `csv-finalize/route.ts:1183` likewise). `SEAM_MISCONFIGURED`
has been in `SEAM_CODE_TO_WIZARD_CODE` since 140.3-15, so a hop-first order would route it to the
generic entry and regress WR-07. Under roster-first it stays on the route's corrected copy.
`CSV_RATE_LIMIT` gets the opposite treatment BY EXCLUSION: it is deliberately NOT in the rosters,
so it falls past branch 1, hops via 140.5-02's `["CSV_RATE_LIMIT","RATE_LIMITED"]` table row, and
renders rate-limit copy WITH its stamped wait (`CsvValidationEnvelope` cannot carry a wait —
PATTERNS §5). The overlap set {CSV_RATE_LIMIT, SEAM_MISCONFIGURED} is thus split deliberately:
roster membership decides which copy wins, and both memberships are asserted by negative controls.

Coverage-law rows, stated per CONTEXT §2: the hop + shared envelope are **row 1**; the
`KNOWN_CSV_*` rosters are **row 2 — hand-typed, partial by construction in those words** (the same
shape as the four existing clients' rosters), fail-louded by the guard's roster-completeness
assertion, whose population is DERIVED from the route source.
