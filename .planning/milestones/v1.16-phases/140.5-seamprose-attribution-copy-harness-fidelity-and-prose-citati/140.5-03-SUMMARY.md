# Phase 140.5 Plan 03: `Retry-After` Arrival + Honest Transport Attribution — Summary

`Retry-After` now survives from the Python service to the browser on all five `postProcessKey`
routes and renders a wait on every actionable non-CSV wizard surface — including the sixth
thread nobody had named, which is the exact path phase 141 builds on — while all five wizard
transport catches stopped blaming the exchange for a fault on our own hop.

## Coverage-law rows, stated (CONTEXT §2)

| Remedy | Row | Reach |
|---|---|---|
| the `Retry-After` relay at `process-key-client.ts`'s non-2xx arm | **1** | all five callers (`csv-validate`, `csv-finalize`, `finalize-wizard`, `keys/sync`, `verify-strategy`) inherit it with no edit |
| the client wait-threads at 4 handlers / 5 `buildEnvelope` sites | **3 — PER-SITE, PARTIAL BY CONSTRUCTION** | see below |
| `SERVICE_UNREACHABLE` at the five catches | **3 for the edits, 1 for the property** | the edits are per-site; the derived-population guard is what makes the state HELD |
| `seam-transport-attribution.invariant.test.ts` | **1 over the steps directory** | a seventh step file added next month is scanned without an edit |

⚠️ **The client threads are coverage-law row 3 and are PARTIAL BY CONSTRUCTION, in those
words.** There is no shared artefact behind them: each handler reads the header itself, and a
sixth wizard surface added tomorrow gets no wait and nothing notices. The compensating
artefacts are the per-surface arrival tests and the derived-population attribution guard — and
the guard covers the *attribution* half only, not the *wait-threading* half. **Nothing in this
plan would detect a NEW `buildEnvelope` surface that forgets to thread the wait.** Making that
row 1 would mean routing every wizard failure through one shared hook that owns both the code
and the wait; that is not done here and is named in `## OPEN`.

⚠️ **BOTH HALVES WERE REQUIRED AND NEITHER IS USEFUL ALONE** (RESEARCH §4.4, restated because
it is the finding most likely to be lost): the choke-point relay reaches **zero wizard
surfaces**, because no client read the header; the client threads reach **zero `/process-key`
429s**, because the header never arrived. Landing one without the other would have produced a
green plan and no behaviour change.

## What shipped

### Task 1 — the choke point (`process-key-client.ts`)

`/process-key` is rate-limited on the Python side (stacked `@limiter.limit` decorators;
`main.py`'s `RateLimitExceeded` handler answers 429 with
`headers={"Retry-After": str(retry_after)}`). The forwarded non-2xx arm reconstructed the
response from the **body and status only**, so every upstream header died silently — a Python
429 reached the browser with `retry_after_seconds` in the body and no header at all.

The relay copies the raw string when present and does nothing when absent. It does **not**
parse: `parseRetryAfterSeconds` is the ONE parser and lives on the read side, and the body's
`retry_after_seconds` field is deliberately not consulted, because two extraction paths for one
fact is the substring-cascade shape this milestone removes.

**The docblock reconciliation, written in-file as the plan required.** `:598-642` carries a
45-line prohibition on branching by status. That contract is about **behaviour selection**, and
it is untouched: the relay is unconditional on status — 429, 403 and 503 all take the identical
path — and `res.status` is still used for exactly the one thing it was always used for,
forwarding itself. The header is metadata the contract never governed. The prohibition was
**extended**, never weakened. A dedicated test (*"relays the header on a 503 too — the relay is
not keyed to 429"*) asserts the non-branching rather than narrating it, and a positive control
pins the PYAPI-10b 403 verdict passing through body-and-status verbatim.

### Task 2 — the four actionable threads + four of five catches

| surface | route | wait state | catch |
|---|---|---|---|
| `ConnectKeyStep` | `create-with-key` | step-level | ✅ 2 occurrences replaced |
| `SubmitStep` | `finalize-wizard` | step-level | ✅ 1 occurrence replaced |
| `MultiKeyConnectStep` add-key | `composite/add-key` | **PER-PANEL** | ✅ 2 occurrences replaced |
| `MultiKeyConnectStep` continue | `composite/set-members` | step-level, both envelope arms | ✅ 2 occurrences replaced |

The add-key wait is **per-panel and not per-step** because that route is rate-limited per
identity: panel 3 hitting the limiter says nothing about panel 1, and one step-level value
would render panel 3's duration under panel 1's error.

Every thread clears the wait on a **fresh attempt**, which is the half a copy-paste of the
working `SyncPreviewStep` thread drops (TRAP-3), and every arrival is asserted with its
absence case and its stale-value case.

⚠️ **`MultiKeyConnectStep` held TWO of the five catches and every prior census missed the file
entirely** — `140-SYNTHESIS.md` named three catches and all three of its line numbers had
drifted. Its `set-members` catch was the worst of the five: that route performs **no key
validation on any path** (`KNOWN_SET_MEMBERS_CODES` is four codes, none a venue verdict), so
*"We could not reach the exchange"* named a venue provably not involved in a request that only
persists date windows.

### Task 3 — the sixth thread and the class guard

**⭐ `handleRetrySync` was `if (res.ok && mountedRef.current) { … }` with no else.** A non-2xx
retry discarded the `Retry-After` the route had just stamped **and rendered nothing** — the
banner stayed up, the button re-enabled, and a user throttled at 60 s could hammer it with no
feedback. The one surface that honours the wait on its first attempt discarded it on every
retry, and that is what 141 was about to build on.

It now classifies through the **same** wire→wizard hop as the kickoff (one route, one
classifier — a second path for the identical request is how two vocabularies drift apart),
reads the header into the **same** state the first attempt uses, and renders the envelope.
**No automatic retry was added**; the test file asserts exactly one request per click, and says
so in its docblock.

The class guard derives its population from disk, comment-strips via `source-scan.ts`, extracts
catch bodies by balanced-brace walk (strings and template interpolation walked, so a `}` in a
string cannot close a body early) and asserts **no** catch body contains the venue-fault code —
any occurrence, so the telemetry second-occurrences are in scope.

## Deviations from plan

### 1. [Rule 1 — bug] The class guard's catch-walk DOUBLE-COUNTED its own population

- **Found during:** Task 3, cross-checking the published count against an independent one.
- **Issue:** the walk rejected a `catch` adjoined to identifier characters, but `.` is not an
  identifier character, so `res.json().catch(() => ({}))` — a shape this directory uses
  constantly — was read as a catch clause and its `({})` consumed as a body. The population
  measured **22** against an independently counted **11**.
- **Why it mattered more than a wrong number:** a double-counted population **inflates what the
  vacuity fence measures**, so a walk that had lost HALF the real catch bodies would still have
  cleared the ≥8 floor. The count and the guard would have gone wrong together and agreed with
  each other — the exact failure mode the fence exists to prevent.
- **Fix:** reject a `catch` whose preceding non-whitespace character is `.`, plus a regression
  case pinning the brace-carrying arrow-body shape.
- **Caught only because the plan required the predicate to be published.** An unpublished count
  would have shipped.
- **Commit:** `919a7aa1`.

### 2. [Rule 3 — blocking] `SyncPreviewStep.render.test.tsx`'s distinct-code vacuity floor

- **Found during:** the Task-3 full-suite run.
- **Issue:** the floor pins ≥14 DISTINCT codes reaching `gate_failed`. Replacing the kickoff
  catch's `KEY_NETWORK_TIMEOUT` with `SERVICE_UNREACHABLE` collapsed two scenarios onto one
  code, so the honest count is 13. A floor of 14 would have pinned the pin to a false
  attribution.
- **Fix:** lowered to 13 **with the reason recorded in-file**, and — because lowering a vacuity
  floor is exactly what the guard idiom forbids — a **second, stronger** assertion added:
  `driven`, the number of scenarios that actually rendered an envelope, pinned at the full 14.
  A shrinking reachable set is now distinguishable from a loop going blind, which it was not
  before. **Net: the fence is stronger than it was.**
- **Commit:** `919a7aa1`.

### 3. [Rule 3 — blocking] The new guard's debug census violated the env manifest

- `process.env.SEAM_ATTRIBUTION_CENSUS` reddened `env-manifest.test.ts`, which enforces that
  every literal `process.env` read in `src/` is declared. **Removed rather than declared**: a
  debug flag is a new row in an enforced manifest, for a convenience the floor already provides
  (raise it, read the count out of the assertion message — which is how the figures here were
  taken). The reasoning is recorded in the file, not only here.

### 4. [reporting] Three pre-existing tests PINNED the false attribution and were re-pointed

`ConnectKeyStep.test.tsx`, `SubmitStep.test.tsx`, `MultiKeyConnectStep.test.tsx` (×2) asserted
`KEY_NETWORK_TIMEOUT` by name on the catch paths. Each was re-pointed **with a negative
assertion**, so a revert cannot pass. One of them (`SubmitStep`'s) asserted only that *some*
Retry button rendered, so it was green for any recoverable code — including the wrong one it was
named after; it now names the code and the copy.

### 5. [naming] The sixth thread's test file

The plan's `files_modified` names `SyncPreviewStep.test.tsx`. **That file does not exist**, and
its near-namesake `SyncPreviewStep.test.ts` is a pure-helper unit suite that cannot render.
