# Phase 140.5 Plan 05: the CSV upstream arm — three-way, roster-first, on BOTH clients Summary

Closed DEF-140.4-C and the §6 hand-off-hole class as the one defect they are: both CSV wizard
clients now discriminate a forwarded upstream failure from a caller fault from a validation verdict,
and a derived-population guard holds "both clients" as a property rather than a claim — while six
replayed negative controls prove the obvious two-way fix would have been worse than the defect.

---

| remedy | row | in the required words |
|---|---|---|
| the shared `SEAM_CODE_TO_WIZARD_CODE` hop + shared `ErrorEnvelope` (branches 2 and 3) | **row 1** | one chokepoint; a new wire code or a new upstream status is covered at both clients without an edit here |

⚠️ **No "effective row 1" claim is made for the row-2 halves.** What the guard adds is strictly
**fail-loud arrival**: the roster's population is derived from the route's own source, so a

miss a new member is still a roster.**

## What shipped

### Task 1 — `CsvUploadStep`, the three-way arm

`if (!res.ok || data.ok === false)` is **split**. `!res.ok` now runs: roster → hop → §4a; a genuine
verdict (`200 + ok:false`) keeps the per-row path untouched. Branches 2 and 3 read through
`seamErrorCode` / `seamCorrelationId`, which handle the flat **and** nested `service_error` shapes —
the top-level read is exactly how the defect was built.

Two panels now exist on this surface, so mutual exclusion was made **structural** rather than left
to discipline: `showCsvEnvelope` and `showSeamEnvelope` are the only writers, each clears the other,
and every pre-existing call site goes through them. That also closes TRAP-3 by construction — the
wait is rebuilt from the current response on every attempt and both panels are cleared at the start
of each one, so there is no stale-wait state to forget to reset.

### Task 2 — `CsvSubmitStep`, the second client

Same arm, same order, against `csv-finalize`. The `NEW-C14-01` / `RED-TEAM-L2` retry fence moved
**onto branch 1 with the read it depends on**: both codes it names are route-minted, so no other
branch can carry them, and leaving it below the arm would have made it read as if it governed
branches where it can never fire. A regression test pins that `CSV_PERSIST_FAIL` still leaves Submit
disabled.

### Task 3 — the class guard

`src/lib/seam-wire-vocabulary.invariant.test.ts`, 15 cases:

- **hop coverage** over the derived client population; the failure message NAMES the file.
- **agreement** over **all seven** `KNOWN_*` rosters, from a **derived** file list. The pre-existing
  140.4 guard scans a **hand-typed three-file list** and pins that exactly four rosters exist — so
  `KNOWN_FINALIZE_CODES` (in `SubmitStep.tsx`) had **never been inside any agreement check**. That
  gap closes by construction here.
- **the overlap oracle**, hand-typed at four rows: `KNOWN_KICKOFF_CODES.RATE_LIMITED` (pre-existing),
  `KNOWN_FINALIZE_CODES.SEAM_MISCONFIGURED` (previously uncovered), and the two CSV rosters'
  `SEAM_MISCONFIGURED`.
- **`CSV_RATE_LIMIT` roster-absence**, asserted directly — the other half of 140.5-02's pin.
- **roster completeness** per CSV route, with a vacuity fence (≥4 codes) and the exemption BY NAME.
- **the cause partition** (below).
- **both-polarity needle self-tests** for all three needles, each demonstrating the unstripped
  counter-example as well as the stripped one.

⚠️ The plan predicted the guard would be **green on arrival** because the fix lands first

## Deviations from plan

### 1. [Rule 1 — bug] The negative control found a LIVE defect on the untouched tree

`CsvValidationEnvelope` renders the route's per-**emission** `human_message` as its heading and the
code's per-**code** authored `cause` beneath it. For `SEAM_MISCONFIGURED` those two **contradict**,
and the panel printed both. Verbatim from the DOM, before the fix:

> Our rate limiter is unavailable, so we stopped before checking your file. This is a fault on our
> side, not your data. Nothing was saved and nothing was validated — **try again in a minute.**
> A setting on our side is wrong, so we stopped before sending the request. **Nothing was submitted**
> and nothing was changed. **Retrying will not clear it:** the setting stays wrong until we fix it
> and redeploy.

Line 1 says try again in a minute; line 2 says retrying will not clear it. Line 1 is true; line 2 is
false in three clauses. **This is the sentence WR-07 removed from the route four days ago, silently
re-imported by CR-02's cause lookup two commits later.** Neither change was wrong on its own.

**Fix:** an explicit suppression set in the panel, with the partition asserted by the guard. **Not**
in the copy table — that entry is true at its other emitters (a pre-I/O `SeamConfigError`), and
weakening it there would trade a false sentence here for a vaguer one everywhere; minting a second
code for one fact is the drift 140.5-02 refused by name.

⭐ **This is the plan's own thesis demonstrated: the defect was reachable only by a person uploading
a file, no test failed on it, and the negative control is what found it.**

### 2. [Rule 2 — correctness] `correlation_id` falls back to the wizard session id, not `null`

The plan's action said `seamCorrelationId(data) ?? data.correlation_id ?? null`, but `buildEnvelope`
takes `correlation_id: string` and §4a's first stated requirement is that an id **must render** —
`correlation_id: —` was half the reported defect. The fallback is the id `wizardFetch` already
stamped on the request header, so it is joinable to the server's log rather than decorative.
SC-CSV-3 falsifies both halves independently.

### 3. [reporting] `CSV_UPSTREAM_FAIL` is IN the validate roster

It follows mechanically from the plan's own enumeration predicate and the roster-completeness guard
requires it. Worth stating because it is not obvious: the route's 502 arm sends
`WIZARD_ERROR_COPY.CSV_UPSTREAM_FAIL.title` verbatim, so branch 1 renders the §4a title **and** its
authored cause — the same words the fallback would produce. The 503 config-missing arm sends
`"Service unavailable."`, which now renders with no second line.

### 4. [reporting] The `!data.preview` defensive arm was left alone

A `200` with no preview still renders `CSV_UPSTREAM_FAIL` through `CsvValidationEnvelope` rather
than the shared envelope. It produces the same §4a title and cause, it is outside the `!res.ok`
population this plan scopes, and moving it would have widened the blast radius for no user-visible
change. Recorded so the next reader does not think it was missed.

### 5. [reporting] Two one-off `.mjs` probes were written and then DELETED

They measured the roster enumeration and the two guard populations while drafting. Both derivations
now live in the guard, in TypeScript, run on every CI run. Leaving the probes would have added two
more unowned scanners to the 17 `stripComments` copies `source-scan.ts` exists to stop multiplying.
Their outputs are published above.
