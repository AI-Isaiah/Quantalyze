# Phase 140.5 — SEAMPROSE · CONTEXT (locked decisions)

**Goal:** what the codebase SAYS about itself is true — in user copy, in comments, in citations,
and in the tests that stand in for the contract — so phase 141 can trust what it reads.

**Depends on:** 140.4 (SEAMRIM closed the behavioural rim; this closes the descriptive one).

---

## 1. Why this phase exists

v1.16's recurring defect, found eight separate times, is **our fault rendered as the user's**.
140.1–140.4 closed the behavioural half: the seam now emits machine-readable, correctly-attributed
codes. What it does **not** yet guarantee is that the *words* — user copy, comments, citations, and
the tests standing in for contracts — are true.

Three concrete proofs that the descriptive half is still open:

- A **live browser QA pass** on 2026-07-29, uploading a real founder CSV, was told
  *"Validation failed. See per-row breakdown below."* for an **auth failure**, with **no breakdown
  below**, the sentence printed twice. 140.4's fix round closed the 502 arm and the duplication;
  **the forwarded-4xx arm is still live** (DEF-140.4-C).
- `sentry-capture.ts` claims *"the seam captures nothing to Sentry"* — it is **41 sites across all
  15 routes**. The contract registry says *"exactly three predicates"* (five) and *"the six seam
  files"* (eight — and the guard's own docblock says eight).
- **7 of 17 comment findings were 140.2 comments falsified by 140.3 commits in the same range.**
  No phase re-measures what its predecessor wrote down. 140.4 produced two more instances of exactly
  this (see §5).

⭐ **`Retry-After` is honoured at 1 of 4 surfaces. This is a HARD PREREQUISITE FOR PHASE 141** —
141's retry-with-backoff consumes `Retry-After`, so it must not land on plumbing that reaches one
surface in four.

## 4. LOCKED FOUNDER DECISIONS (2026-07-29)

### 4a. DEF-140.4-C — one sentence for every non-validation upstream status

**Decision: ONE message for all of 401 / 403 / 404 / 409 / 5xx** — every non-2xx from the CSV
validator that is **not** row-level validation failure. **Coverage-law row 1: a single chokepoint**,
so a future upstream status is covered without an edit.

**Rationale as stated:** the user cannot act differently on a 403 than a 404 — both mean *"not your
fault, try again or contact us."* Per-status copy was explicitly rejected as a hand-typed roster,
row 2, *"the shape 140.4 spent 14 plans undoing."*

**Approved copy — this is founder-authored, use it verbatim:**

> **We couldn't check your file just now.**
>
> This is on our side, not your data. Nothing was saved. Try again in a moment — if it keeps
> happening, send us this reference.
>
> `correlation_id: <id>`

Requirements this carries:
- `correlation_id` **must render** (it was absent on the 401 arm — that is part of the defect).
- **Nothing was saved** must be TRUE at this arm — verify it, do not assert it in copy alone.
- The sentence must **not** be rendered twice. `CsvValidationEnvelope.tsx:56,69` printed
  `human_message` as **both** heading and cause whenever `errors.length === 0`; 140.4 fixed that
  instance — pin it so it cannot return.
- The copy must **not** promise a per-row breakdown when none will render.

### 4b. Citation rot — fix repo-wide, guard the seam surface

**Decision: correct all known-bad citations repo-wide; build the CI guard SCOPED to the seam files
this milestone owns.** Repo-wide guarding of all 881 citations was rejected as too large a build
inside a phase already carrying 8 scope items, and because it would surface hundreds of pre-existing
stale citations needing triage by someone.

**This is coverage-law row 1 *on the seam surface* and explicitly NOT a repo-wide closure.** Say so
in those words. The guard must be a ratchet: widening its glob later must be a one-line change, and
the plan must name what it would take to widen it.

### 6c. STRUCTURAL FINDING — §4a and §6 are ONE defect, and the fix is row 1

Both agents reached this independently:

**`CsvUploadStep.tsx` and `CsvSubmitStep.tsx` are the ONLY two wizard clients that never call
`seamErrorCode` / `recogniseSeamErrorCode`** (measured: 0 references; the other four have the hop).
Both consume `rateLimitDenyJson` routes. That missing hop is *mechanically why* a forwarded 401
renders *"Validation failed. See per-row breakdown below."* — `CsvUploadStep.tsx:277` reads
`data.code`, a **top-level** read, so `withAuth`'s `{error:"Unauthorized"}`, FastAPI's
`{"detail":"Forbidden"}`, and **every nested `service_error` envelope** (code at `detail.code`) all
fall through to `CSV_VALIDATION_FAILED` with `correlation_id: —`.

⇒ **ONE artefact closes DEF-140.4-C and the §6 class together, at row 1.** A plan that edits only
`CsvUploadStep` closes **1 of 2** — the exact 5-of-7 shape this milestone exists to stop.

**The discriminator §4a needs is already on the wire:** validation verdicts arrive **200 with
`ok:false`**; the *forwarded-upstream* population is `!res.ok` **with no top-level `code`**.

> ⛔ **CORRECTION (2026-07-29, plan-checker B-1) — THE SENTENCE THAT USED TO SIT HERE WAS WRONG.**
> It read *"everything else is `!res.ok`. No new protocol is required."* That over-generalised
> RESEARCH §12.2, which measured the discriminator against the **upstream-forwarded** population
> only — its own table heading says *"bodies with NO top-level `code`."* **`!res.ok` is NOT the
> upstream population.** The route emits its own caller-fault non-2xx with real top-level codes:
> `CSV_FILE_TOO_LARGE` (`csv-validate/route.ts:144,164`), `CSV_INVALID_FORMAT` (`:155,160,176,191`
> and **×20** in `csv-finalize`), `CSV_RATE_LIMIT` (429, `Retry-After` stamped, `:218`),
> `CSV_SESSION_REUSED`, `CSV_PERSIST_FAIL`, `CSV_FINALIZE_FAIL`. None is in
> `SEAM_CODE_TO_WIZARD_CODE` (**exactly 6 members**, `wizardErrors.ts:1637-1652`), so all of them
> would resolve `"UNKNOWN"` and fall to §4a's copy.
>
> **The concrete regression that would have shipped:** a user uploads an 11 MB file. Today they read
> *"Maximum file size is 10 MB. Your file is 11.3 MB."* Under a two-way `!res.ok` arm they would read
> ***"We couldn't check your file just now. This is on our side, not your data."*** — **the user's
> fault rendered as ours, across ~30 sites, inside the plan written to close that exact defect.**
> Worse: `CSV_PERSIST_FAIL` would assert *"Nothing was saved"* where that may be affirmatively
> **false**, and `CSV_RATE_LIMIT` would drop the one CSV wait `rateLimitDenyJson` actually stamps.
>
> ⇒ **THE ARM MUST BE THREE-WAY, NOT TWO-WAY:**
> 1. `data.code` is already a known `WizardErrorCode` **or** route CSV vocabulary → **keep today's
>    copy and `human_message`**;
> 2. a seam wire code via `seamErrorCode` → **hop through the shared table**;
> 3. genuinely unrecognised **or codeless** → **§4a's founder copy**.
>
> Branch (1) needs **negative controls** — `CSV_FILE_TOO_LARGE` (400), `CSV_INVALID_FORMAT` (400),
> `CSV_RATE_LIMIT` (429 + `Retry-After`), `CSV_SESSION_REUSED`, `CSV_PERSIST_FAIL` — replayed as
> tests. Without them, branch (3) swallowing branch (1) is invisible to the suite and reachable only
> by a live QA pass, which is how the original defect survived.

**Related, and larger than §7 describes:** `CsvValidationEnvelope` has **no `retry_after_seconds`
prop and no `cause` field at all**. Routing the CSV surface onto the shared `ErrorEnvelope` is
**row 1 and closes the `Retry-After` gap in the same edit**; extending the CSV props is row 2.
