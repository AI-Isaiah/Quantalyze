<objective>
Build the bounded retry loop inside `resilientFetch` — the ONE transport both seam clients share — behind a new `retriesOverride` escape hatch, with the SC4 breaker-open guarantee (zero attempts open; re-check before attempt 2) and fixed-backoff-plus-jitter. All `SEAM_BUDGETS` rows stay 0 and no caller passes the override yet, so production behavior is byte-equivalent until plan 04 activates it.

Purpose: SEAM-06's mechanics half. The loop lives here (not in the clients) because `resilientFetch` owns the three things a retry must respect — the deadline, the breaker check, and the failure classification. Putting it anywhere else risks an SC4 bypass (RESEARCH Q1).

Design decision (locked by CONTEXT, corrected post-research): **Design A** — each attempt gets its own fresh `timeoutMs` deadline; total worst case = timeoutMs × (1+retries) + backoff. Allowlisting is restricted to headroom-safe routes (plan 04 enforces via SC-4b). Do NOT build a shared-deadline (Design B) variant.

Output: the dormant retry mechanism + `resilient-fetch.retry.test.ts` with the SC-4 falsifiability-ledger row OBSERVED.
</objective>
