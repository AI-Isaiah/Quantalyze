The one that is not simple is **PYAPIFIX-01**. `_wizard_duplicate_reply`

**The obvious fix is insufficient by construction.** Pinning the Python shape in a pytest and the TS
shape in a vitest is two mocks agreeing with each other — the precise state that shipped this
defect. The fix must be ONE artifact both runtimes read, where the **Python side proves the artifact
equals what the real route actually emits** and the **TS side runs the real guard predicate** over
it. Anything less leaves the boundary uncrossed.

That plumbing already exists here and needs no new infrastructure:
`tests/lib/composite/window-overlap-convention-parity.test.ts:29` and
`src/lib/scenario-optimizer-parity.test.ts:20` each `readFileSync` a JSON fixture out of
`analytics-service/tests/fixtures/`, and `vitest.config.ts:30-33` documents the TS↔Python parity
idiom as a deliberate, already-configured include glob.

**Primary recommendation:** a **committed shared JSON fixture under
`analytics-service/tests/fixtures/`**, asserted equal to a real `TestClient` response on the pytest
side and fed through the **extracted, exported** TS guard predicate on the vitest side. **The
TypeScript consumer is the side that changes** — and after re-deriving that with the rollout
argument removed, the answer is unchanged, for a stronger reason: `queued` (a fact about the job)
and `duplicate` (a fact about the submission) are **orthogonal**, `_resume_duplicate_job` exists

## PYAPIFIX-01 — Crossing the Process Boundary

> **Framing (round 2):** this is **contract coherence plus latent-trap removal**, NOT an emergency.
> No live caller can reach the 502 today (C-3, re-confirmed: zero `wizard_session_id` occurrences in
> `finalize-wizard/route.ts` or `keys/sync/route.ts`). Still a merge blocker — 140.2/140.3 plan
> against this shape and M-11's remedy is literally "add that field" — but urgency must not buy a
> rushed shape.

### The exact break, verified at HEAD

**Producer** — `analytics-service/routers/process_key.py:680-690` (`_wizard_duplicate_reply`):

```python
return {"ok": True, "code": "WIZARD_DUPLICATE", "idempotent": True,
        "verification_id": existing["id"], "status": existing["status"],
        "trust_tier": existing.get("trust_tier"), "correlation_id": correlation_id,
        "queued": queued,        # <-- a FACT now, no longer a discriminant
        "job_state": job_state}
```
**One shared builder, two call sites** (`:1173`, `:1250`) — so a Python-side change is one edit, and
its docstring argues *for* emitting `code` on success (*"the contract is `code` MUST be a non-empty
string when `ok` is false, not that it is absent when `ok` is true"*). Reasonable in isolation, and
contradicted by a guard in another language nobody read. That is the finding.

`queued`/`job_state` come from `_resume_duplicate_job` (`process_key.py:587-660`), which returns
`(False, "not_applicable")` for non-long-fetch or non-`draft` rows and `(True, "enqueued"|"running")`
after a real `enqueue_compute_job` RPC. So `queued: True` **is true** when it appears.

**Consumer** — `src/app/api/strategies/finalize-wizard/route.ts:1433-1462`:

```ts
if (typeof r.queued !== "boolean") return false;
if (r.queued) {
  if (typeof r.verification_id !== "string") return false;
  if ("code" in r || "idempotent" in r) return false;   // mixed envelope = bug
  return true;
}
```

A guard miss lands at `route.ts:1371-1402`: `console.error` + `captureToSentry(new
Error("process-key onboard contract violation"), {tags:{step:"unified-response-parse"}})` +
`NextResponse.json({error:"Upstream service returned unexpected response"}, {status: 502})`.
The TS test pinning the rejection is `finalize-wizard/route.test.ts:1474-1500`
("rejects mixed envelope (queued=true with code field) with 502").

**Why both suites are green:** `route.test.ts` sets `STATE.processKeyResult` by hand — a mock of the
Python side. `analytics-service/tests/test_process_key.py` mounts the router in a bare `FastAPI()`
(`tests/test_process_key.py:88-111`) and asserts the dict it built — a mock of the TS side. Neither
runtime ever observes the other.

### WHICH SIDE CHANGES — re-derived on contract quality alone

> **Round-1's argument is withdrawn.** It recommended TypeScript because consumer-first is the only
> rollout ordering that keeps two independent deploy pipelines consistent. **That argument is void:**
> the guard is unmerged (Phase 140's `57b11813`, this branch), `43449cc6` is not on `origin/main`,
> and Phase 140.1 never touched `finalize-wizard/route.ts`. Both sides land together. The rollout
> table that stood here has been deleted rather than left beside its replacement.
>
> **Re-derived without it, the recommendation is unchanged — and the reason is better.**

**The modelling error.** Post-PYAPI-09 the reply carries two *independent* facts:

| Field | What it asserts | Produced by |
|---|---|---|
| `queued` / `job_state` | a compute job is now enqueued or running for this verification | `_resume_duplicate_job` (`process_key.py:587-660`) |
| `code:"WIZARD_DUPLICATE"` + `idempotent:true` | this submission was a duplicate; no new verification was created | the duplicate pre-check (`:1173`, `:1250`) |

Neither implies the other, and `_resume_duplicate_job` **exists to produce the state where both are
true** — a duplicate submission whose wedged job we re-enqueued. The guard encodes those two
independent booleans as **one discriminant**, so it asserts a mutual exclusion the domain does not
have. Its comment (`route.ts:1416-1418`) calls the combination "a backbone bug"; it is a supported
recovery outcome. **That is a defect in the consumer's model, not in the producer.**

**Every Python-side option, and why each loses on the merits:**

| Option | What it does | Why it loses |
|---|---|---|
| **P1** — omit `code`/`idempotent` when `queued:true` | the guard's `queued:true` arm accepts it as-is | **Destroys information.** A duplicate-resume becomes byte-indistinguishable from a fresh queue. `route.ts:1355-1367` forwards `code`/`idempotent` to the wizard *precisely* so it can say "already submitted"; under P1 it cannot. Lower contract fidelity, not higher. |
| **P2** — carry the duplicate signal in a field the `queued:true` arm permits | that arm rejects only `code`/`idempotent`, so `job_state` or a new `duplicate:true` passes today | **Invents a second spelling of one fact.** "Duplicate" would be named `code:"WIZARD_DUPLICATE"` on one arm and something else on the other, and the consumer must branch on `queued` to know which. Strictly worse. And `route.ts:1355-1367` **drops `job_state`**, so it needs a TS edit anyway. |
| **P3** — revert to a hardcoded `queued:false` | restores the pre-140.1 shape the guard accepts | **Restores a documented lie.** `process_key.py:1159-1164` verbatim: the pre-fix path *"returned a hardcoded `queued: False` without ever reaching the enqueue below, so a session whose draft INSERT committed but whose enqueue never ran was told 'duplicate, not queued' on every subsequent retry — forever, with no state from which it could recover."* Also needs a TS edit for the same `job_state` reason. |

**Round-1's C-4 is decisive, and generalises:** *no* Python-side option is TypeScript-free.
`finalize-wizard/route.ts:1355-1367` forwards exactly
`ok`/`strategy_id`/`status`/`verification_id`/`queued`/`code`/`idempotent` and **drops `job_state`**,
so any Python shape that preserves the duplicate signal without using `code`/`idempotent` requires a
forwarding change. "Change Python, touch no TypeScript" was never on the table. With the rollout
tiebreak gone, the choice is decided purely by which model is true — and the two-orthogonal-facts
model is.

**Widening the guard is a narrowing of falsehood, not of teeth.** The objection to touching a
deliberately-strict guard is answered at source: the guard is **not** uniformly strict. Its
`queued:true` arm silently permits `ok`, `job_state`, `status`, `trust_tier` and `correlation_id` —
every other extra key the Python reply actually carries. It singles out exactly `code` and
`idempotent`, i.e. exactly the falsified premise. Removing that one line removes an untrue
assertion and nothing else.

**And the plan must buy the teeth back in the same edit** (otherwise this *is* convenience):

| Add | Why |
|---|---|
| `verification_id` must remain a `string` on the `queued:true` arm | the one real invariant the arm has; keep it |
| `code`, when present, must be a **non-empty string** | today the `queued:false` arm requires it; the widened union must not let `code:""` through |
| `idempotent`, when present, must be `true` **iff** `code === "WIZARD_DUPLICATE"` | pins the pairing the emitter actually guarantees (`process_key.py:680-690`) — a *new* invariant the current guard does not assert |
| a negative fixture case the widened predicate must still **reject** | proves the extraction did not degrade into `() => true` |

Net: one false assertion deleted, three true ones added. **Recommendation stands: the TypeScript
consumer changes**, exactly as `140.1-TS-OBLIGATIONS.md` TS-01 already prescribes (see
§TS-OBLIGATIONS Reconciliation — TS-01 is therefore **not** stale, which removes the reconciliation
risk the CONTEXT flagged).

**Scope-fence reconciliation the planner must state explicitly:** `140.1.1-CONTEXT.md:70` puts
"everything TypeScript beyond the one contract test" out of scope, while `:99-108` instructs
"choose it on which contract is better". These reconcile — the fence is about the **140.2/140.3 TS

## PYAPIFIX-02 — The Behavioural Predicate

### Why a syntactic search fails here

The review names two line ranges in one file. Grepping for `read_only is False` finds **two** sites
repo-wide; grepping for the venue-transient codes finds a **third and fourth** concern in functions
that mention neither. The class is not "lines containing `read_only is False`."

### The predicate the pattern-mapper must resolve

> **Any code path that takes a `ValidationResult` produced by `services/exchange.py`'s permission

## PYAPIFIX-04 — Enforcing the scalar guarantee

### Current state, verified

- The guarantee is asserted three times: module docstring (`services/error_contract.py:30`),
  `docs/STATUS_CONTRACT.md` §2, and R-2.
- `_validate` (`services/error_contract.py:82-155`) **never inspects `detail`**. Read in full: it
  checks status membership, `dependency` against `SERVICE_DEPENDENCIES` on the 503 arm, `retryable`
  polarity, and `Retry-After` presence/absence. `detail` is untouched.
- `service_error_body` (`:158-181`) passes it straight through:
  `"detail": detail if detail else _FALLBACK_DETAIL`.
- The only protection is the `detail: str | None = None` annotation — in a module whose callers
  routinely hand it `Any` (`key_data.get(...)`, `exc.args`, `err.detail`), which `mypy --strict`
  cannot narrow at the call boundary.
- Proven by execution in the review: `detail=['a','b']` and `detail={'k':'v'}` both emit verbatim.

### Where the guard goes

**In `service_error_body`, before the dict is built.** *(Round-2 correction — round 1 justified this
with a claim that is false; the conclusion survives, the reasoning does not. See C-16.)*

The caller set is now **enumerated, not assumed**: `grep -rn "service_error_body" --include='*.py' .`
returns exactly three hits, all inside `error_contract.py` — the definition (`:158`) and two calls,
`service_error` (`:208`) and `service_error_response` (`:243`). **Both** of those also call
`_validate` first (`:206`, `:239`). So round 1's stated reason — *"guarding `_validate` covers only
one entry point"* — is **wrong**: both entry points pass through both functions, and either location
gives complete coverage. **Open Question 3 is RESOLVED; no pattern-mapper input is needed.**

The tiebreak is now mechanical, not architectural: `_validate` does not receive `detail`, so putting
the guard there means widening a private signature and threading a sixth argument through two call
sites. `service_error_body` already has the parameter. **Choose `service_error_body`** — zero
signature churn, provably complete coverage. Note the consequence for PYAPIFIX-06: 06(a) and 06(b)
land in `_validate`, 04 lands in `service_error_body`, so the two requirements do **not** collide in
the same hunk even though the CONTEXT describes them as "the same function".

### What it does with a list/dict

Match the file's existing style exactly: **raise `ValueError` at construction**, same as the eleven
out-of-class constructions `_validate` already forbids. Do **not** coerce with `str()` — coercion
would emit `"['a', 'b']"` to a user, which is the same defect wearing a string costume, and it would
hide the calling bug that produced a non-scalar.

```python
if detail is not None and not isinstance(detail, str):
    raise ValueError(
        "body.detail.detail must be a scalar string; "
        f"got {type(detail).__name__}"
    )
```

Guard on `not isinstance(detail, str)`, **not** on `isinstance(detail, (list, dict))` — the latter
is a syntactic enumeration that misses `int`, `bytes`, a pydantic model, or `None`-like sentinels.
This is the same lesson as PYAPIFIX-02.

### mypy implications and the oracle

The `isinstance` narrowing is **statically dead** under `detail: str | None`. `mypy --strict` accepts
always-false narrowing, but verify: if it complains, widen the parameter at the boundary and `cast()`
after the guard — **never** `# type: ignore` (locked). The runtime guard is the point precisely
*because* mypy passes `Any` through silently; tightening the annotation alone closes nothing.
Baseline to preserve: `Success: no issues found in 89 source files`, confirmed at HEAD.

The test must build the non-scalar **outside** the module under test and assert the raise; it must
**not** import `_FALLBACK_DETAIL` or any other `error_contract` constant.

## PYAPIFIX-06 — error_contract's Unreachable Gaps (M-1, M-2)

Both live in `_validate` (`services/error_contract.py:82-155`). Neither is reachable by any

### (a) M-1 — a 429 carrying `Retry-After` is unconstructable

Confirmed at source. Two rules collide:

| Line | Rule | Effect on a 429 |
|---|---|---|
| `:100-101` | `retry_after is not None and not retryable` → raise | `Retry-After` **requires** `retryable=True` |
| `:152-155` | generic CALLER arm: `if retryable:` → raise | any non-424 4xx **forbids** `retryable=True` |

A 429 reaches the generic arm (not 503, not `>=500`, not 424), so both fire. No argument tuple
produces one. Meanwhile `docs/STATUS_CONTRACT.md:34` promises `Retry-After` "on `429` only" and
`:276` documents the live handler emitting it **always**.

**The decisive structural fact: the 424 arm already REQUIRES `retryable=True` on a 4xx**
(`:139-143`, *"a 424 is recoverable — the venue may come back"*). So "4xx ⇒ not retryable" is **not**
an invariant of the contract — it is the *default* arm's rule, and the file already carries a
precedent for a 4xx that opts out. A 429 arm is consistent with the existing structure, not a
special case bolted on.

**Recommended arm — insert after the 424 block, before the generic CALLER checks:**

```python
if status_code == 429:
    # CALLER, throttled. Unlike every other CALLER fault an identical retry DOES
    # succeed — after the advertised wait — so the generic arm's "a retry cannot
    # help" rule must not reach here. Still breaker-inert by construction (4xx).
    if dependency is not None:
        raise ValueError("a 429 is a CALLER fault and must not name a dependency")
    if not retryable:
        raise ValueError(
            "a 429 is recoverable after the advertised wait; retryable:false "
            "beside a Retry-After is the self-contradicting body R-1 forbids"
        )
    if retry_after is None:
        raise ValueError("a 429 must carry Retry-After (STATUS_CONTRACT.md 2)")
```
