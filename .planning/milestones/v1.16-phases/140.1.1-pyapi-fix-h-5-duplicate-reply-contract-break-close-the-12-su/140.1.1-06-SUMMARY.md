## Why each oracle could not fail before

### #1/#2 — a class pinned by ONE member

The old S-06a oracle raised exactly `ccxt.ExchangeNotAvailable`. In ccxt 4.5.49
that is a `NetworkError`, so **both** narrowings kept it inside the 424 arm and
both mutations shipped green. Under either narrowing `ccxt.RateLimitExceeded`
and `ccxt.PermissionDenied` fall to the generic arm and answer **500** — A-01 /
C-12 verbatim, the exact defect this programme exists to fix, with a green suite.

The fix is the hierarchy, not more cases. The family deliberately **straddles
both ccxt roots**, so no single narrowing can satisfy it:

| Row | ccxt MRO root | Killed by mutation A (`NetworkError`) | Killed by mutation B (`ExchangeNotAvailable`) |
|---|---|---|---|
| `RateLimitExceeded` | `NetworkError` | — | ✅ |
| `RequestTimeout` | `NetworkError` | — | ✅ |
| `DDoSProtection` | `NetworkError` | — | ✅ |
| `ExchangeNotAvailable` | `NetworkError` | — | — |
| `PermissionDenied` | `ExchangeError` | ✅ | ✅ |
| `AuthenticationError` | `ExchangeError` | ✅ | ✅ |
| `ExchangeError` | `ExchangeError` | ✅ | ✅ |
| `RuntimeError` (control) | *not ccxt* | — | — |

The **`RuntimeError` control is inside the parametrisation on purpose**: a
"fix" that widened the arm to `except Exception` would satisfy all seven venue
rows and fail that one. The split is what is being pinned, not the 424.

### #6 — `int(retry_after) > 0` accepts 900

`900` is `> 0`. A fifteen-minute advertised wait for a Supabase blip shipped
green at four sites. The mt5-gateway control two hundred lines away had the
correct idiom (`== "30"` with `# Literal, NOT imported from
RETRY_AFTER_SECONDS`) and **caught its own mutation** — the pattern existed and
simply was not applied. It is now applied verbatim at all four sites, with `15`
substituted.

`grep -rn "int(retry_after) > 0"` across both files → **0**.
`grep -c "Literal, NOT imported"` → 1 (`test_match_router.py`) + 3
(`test_status_contract_match_sim_portfolio.py`) = **4**.

### #7 — suppression is only half the contract

The old test fired four probes against a **free-running** clock and asserted
`capture_message.call_count == 1`. That assertion is satisfied by **any** window
at least as long as the test's own runtime, so `300.0 → 1e18` — a window that
never expires, i.e. exactly one Sentry alert per process lifetime for a fault
that persists until an operator acts — shipped green.

The rewrite drives the clock in three phases with **`300` as a literal typed
into the test**:

| Phase | Clock | Expectation | Teeth |
|---|---|---|---|
| 1 | t = 0 | 1 capture | the first fault must reach the operator |
| 2 | t = 299 s (**inside**) | still 1 | five badges per dashboard render must not flood |
| 3 | t = 301 s (**past**) | **2** | *this is the half a never-expiring window silences* |

Phase 3 is the assertion the mutation reddens. The secret-leak assertions
(neither tag nor message may carry a credential substring) are **retained**, and
the tag-count assertion moved 1 → 2 to track the second capture.

The clock is injected by substituting `routers.internal`'s **`time` module
attribute** with a `_FakeClock`, not by patching stdlib `time.monotonic`
globally. `internal.py` uses `time.monotonic` and nothing else (its two
`datetime.now` sites import `datetime` separately), so the stand-in is complete
and scoped to that module.

### #12 — an inequality against a *different* constant

`assert detail != AUTH_FAILED_DETAIL` is satisfied by junk copy, by `""`, and by
a stack trace. The copy IS the contract on that arm — 140.3 renders it verbatim
and it is the only thing telling the operator that no retry can clear the fault
— so it is now pinned by **equality against a string literal typed into the
test**, never imported from `routers.exchange`. The inequality is **kept** as a
second guard: whatever else the copy says, it must never become the credential
accusation.

Only the **first** of the two identical `detail=` occurrences was mutated (the
unset-host/port arm this test drives); the occurrence count was asserted at 2
before replacing 1.

### Why the fence never counts

RESEARCH **C-20**: the "six" was a **coincidence**. Two of the handler's returns
**collapse** onto one shape (both `_wizard_duplicate_reply` call sites, `:1226`
and `:1303`) while one **expands** into two (`_run_validate_only` has two
returns). One collapse cancelling one expansion is what made six look
meaningful. A count-based replacement would have looked right and meant
something else — so the fence compares **SETS**, and is never keyed on a line
number or an ordinal.

### The fingerprint set (8 entries, the pinned contract)

| Fingerprint | Source | Wire meaning |
|---|---|---|
| `dict:code,correlation_id,idempotent,job_state,ok,queued,status,trust_tier,verification_id` | `_wizard_duplicate_reply` return | shape 1 — idempotent hit |
| `dict:correlation_id,ok,queued,verification_id` | `process_key` queued-fresh return | shape 2 |
| `dict:correlation_id,daily_returns_series,ok,preview,read_only,step,valid` | `_run_validate_only` success (Name → local keys) | shape 3 |
| `dict:correlation_id,ok,status,step,strategy_id` | `process_key` csv-finalize return | shape 4 |
| `dict:code,correlation_id,encrypted_credentials,errors,fingerprint,matched_strategy_id,metrics_snapshot,ok,status,trust_tier,verification_id` | `process_key` synchronous success | shape 5 |
| `call:_envelope_error` | `_run_validate_only` failure return | shape 6 (200 + `ok:false`) |
| `call:_wizard_duplicate_reply` | `process_key` × 2 — **collapse** | delegation edge |
| `call:_run_validate_only` | `process_key` × 1 — **expands** into 2 above | delegation edge |

Renderings, per the plan: sorted top-level key names for a dict literal, callee
name for a delegation. A bare-`Name` return (`_run_validate_only`'s
`return envelope`) resolves to **every key ever assigned to that local** — the
dict literal **plus** the conditional `envelope["preview"] = …` /
`envelope["daily_returns_series"] = …` subscript adds — so the optional half of
that shape is inside the fingerprint rather than invisible to it.

### The 200-capable predicate, and why it is load-bearing (checker W-4)

A return is 200-capable iff it has **no** `status_code=` keyword, **or** a
`status_code=` whose literal value is `200`. Applied **before** fingerprinting.

The same handler returns `JSONResponse(status_code=…)` at six error sites, all
correctly excluded:

| Line | Status | Arm |
|---|---|---|
| 1081 | 401 | csv-finalize requires an authenticated session |
| 1108 | 422 | `finalize_csv_strategy` RPC failed |
| 1131 | 422 | `MISSING_STRATEGY_ID` |
| 1160 | **403** | `STRATEGY_NOT_OWNED` |
| 1439 | **424** | plan 140.1.1-02's venue-transient arm |
| 1467 | **403** | scope/validation refusal |

A naive walk would sweep those in — either reddening on a legitimate error arm
or **silently widening** the pinned set, reintroducing the exact defect class the
fence exists to catch. `test_pyapi_10a_non_200_returns_are_excluded_from_the_shape_fence`
asserts the filter from the other side and **names 403 and 424 explicitly**
(membership, not equality — so probe (c)'s added 418 does not redden it), plus
fails loud on a computed `status_code=`.

Nested `def`s are skipped: `process_key` defines `_write_audit_sync` inline, and
a closure's return never reaches the wire.

### Oracle direction

The **actual** side is derived from `routers/process_key.py`'s AST (via
`pathlib.Path(process_key_router.__file__)` — the module's own import location,
never a hand-built path). The **expected** side is a literal `frozenset` typed
into the test. That is the sanctioned direction — a pinned contract confronted
with the code's real shape — and it is the opposite of the literal-vs-literal
form that was deleted.
