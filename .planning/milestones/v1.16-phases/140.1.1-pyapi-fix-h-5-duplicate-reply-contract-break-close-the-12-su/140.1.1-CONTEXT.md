## Implementation Decisions (LOCKED)

### PYAPIFIX-01 — the mock-boundary blind spot
`routers/process_key.py:680-690` emits `queued:true` **with** `code`/`idempotent`. The guard at
`src/app/api/strategies/finalize-wizard/route.ts:1433-1450` rejects exactly that shape —
`if ("code" in r || "idempotent" in r) return false;`, commented "mixed envelope = bug" — and the
miss arm at `:1369-1400` emits `console.error` + `captureToSentry("process-key onboard contract
violation")` + **HTTP 502**. PYAPI-09 inverted the discriminant without touching the consumer.

**Both suites are green because each mocks the other.** That is the root cause, and it is why a
fix verified only on the Python side would not close it. **The test must exercise the REAL Python
reply shape against the REAL TS guard logic** — a shared fixture, a contract test, or a golden
response file consumed by both. A second pair of mocks agreeing with each other is not a fix.

> ⚠️ **CORRECTION (verified at source 2026-07-26 — an earlier draft of this file, the ROADMAP
> criterion, the requirement text AND the code review all said the guard was "already deployed"/
> "shipped". IT IS NOT.** The guard was added by **Phase 140** (commit `57b11813`, "feat(140-06)")
> on this same branch; `43449cc6` is **NOT on `origin/main`** (`git merge-base --is-ancestor` says no;
> `git branch --contains` lists only `feat/v1.16-production-resilience` and the wip archive).
> Phase 140.1 did **not touch that file at all** (`git diff --stat 43449cc6..HEAD` on it is empty).
>
> **What this changes:** there is **NO rollout-ordering constraint** — both sides are unmerged and
> land together. Do not choose the fix direction on a deployment argument; choose it on which
> contract is better. **What it does NOT change:** the defect is real and still a merge blocker.
> Before 140.1 the duplicate arms hardcoded `"queued": False` (base `:754`, `:917`), which the
> guard's `queued=false` branch **accepts** — that branch permits `code` and `idempotent`. The
> regression is purely that PYAPI-09 made `queued` sometimes `true` while keeping those two fields.
>
> **Therefore the minimal correct fix is likely Python-side** (do not emit `code`/`idempotent` when
> `queued:true`, or carry the duplicate signal in a field the `queued=true` branch permits) — but
> the planner should weigh that against widening the guard, on contract-quality grounds alone. Note
> the guard is deliberately strict and its comment explains why; widening it needs a real argument.
