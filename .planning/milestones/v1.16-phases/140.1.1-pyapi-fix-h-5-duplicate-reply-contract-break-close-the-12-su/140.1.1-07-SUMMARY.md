## Why each oracle could not fail before

### #3 / #4 — a key function pinned by IDENTITY

`test_shared_limiter_default_key_is_not_ip_derived` asserted
`rl.limiter._key_func is rl.default_platform_key`. That is object identity: it
holds for **any body whatsoever**. Both mutations therefore shipped green
through the whole of Phase 140.1, and the more dangerous one is silent —
`return ""` does not throw, does not log at WARN, does not change a status
code. slowapi takes the `else` branch, emits one `logger.error("Skipping
limit…")` line, and the route is unlimited **forever**. `services/rate_limit.py`
documents this hazard in prose at `:152-154` and again at `:164-166`; nothing
enforced it.

The new gate does both halves:

| Assertion | Kills | Why the other assertion is not enough |
|---|---|---|
| `key != ""` and `key == "platform:/pyapifix05-default-key-probe"` (a literal) | #3 | a string check cannot see #4's per-request key being *unique* |
| the same key from two DISTINCT `_FakeRequest` objects | #4 | equality-to-literal alone would pass a constant-per-process mutant, so both are asserted |
| **a driven trip: real HTTP requests through a route declaring NO `key_func`, the (N+1)th must be 429** | **#3 and #4** | this is the only assertion that observes the *consequence*. Under #3 no 429 ever arrives because the limit is skipped; under #4 no 429 ever arrives because every request has its own bucket. Both reddened here, first-hand. |

Two structural choices, both load-bearing:

- **The probe app is a throwaway `FastAPI()`, not `main.app`.** Every production
  route declares an explicit `key_func`, so **no production route exercises the
  singleton's default at all**. Driving `main.app` would have proved nothing
  about `default_platform_key`.
- **The probe is decorated exactly ONCE, at module scope.** slowapi APPENDS to
  `_route_limits[name]` on every decoration and all copies share one bucket, so
  decorating inside a test body would make one request cost N tokens on the Nth
  run. The 140.1-08 lesson (bounded-and-driven loops, never a fixed call count)
  is applied on top of that anyway.
- Two further tests pin the probe itself — its registered limit value
  (`{"3 per 1 minute"}`) and that its `key_func is rl.default_platform_key`. A
  probe that silently acquired an explicit `key_func` would throttle happily
  while the default was broken, which is the same proves-nothing shape as the
  identity assertion it exists to reinforce.

The `:483` identity assertion is **retained**, per the plan: augment, don't
replace.

### #5 — a bound satisfied by the degenerate value

`assert 0 < seconds <= _ROUTE_A_WINDOW_S` is satisfied by `1`, because
`0 < 1 <= 3600`. The header existed, was present, was parseable, was positive,
and was **wrong** — and that is not a cosmetic wrongness: a wrong-but-small
Retry-After is the retry-storm shape. Every throttled client is told to come
back in one second, so the header that exists to *prevent* a stampede *causes*
one.

The band is `seconds > window * 0.9`. Its arithmetic comes from
`_ROUTE_A_WINDOW_S = 3600` / `_ROUTE_B_WINDOW_S = 3600`, the seconds in each
route's own **declared limit string** (`"5 per 1 hour"`, `"30 per 1 hour"`),
typed into the test file — never read back from `_retry_after_seconds`, the
function under test. `fresh_limiter` empties the bucket and the driver spends it
in milliseconds, so the true remaining wait is essentially the full window; 0.9
leaves six minutes of slack, orders of magnitude more than the suite's runtime
and orders of magnitude less than the mutation.

Also per §9-M8: the **mutation targets the computation** (`main.py:458-487`)
while the **oracle reads the header** the handler mints (`main.py:526`). Those
are different lines on purpose — the oracle observes the wire, not the function.

Applied at **both** sites carrying the weak oracle (route A `/api/verify-strategy`
in `routers/portfolio.py`, route B `/api/csv/validate` in `routers/csv.py` — two
different routers). The review named one; closing one of two is the
instances-not-classes failure mode the repair programme exists to shut. The
pre-existing upper bound is retained as a second guard.

### #8-#11 — four guards with NO test at all

These did not survive because the tests were weak. They survived because **there
were no tests**. `tests/test_tenant_claim_parsing.py` is the first.

**#8's fixture is the subtle one, and getting it wrong would have produced a
false "closed".** The obvious fixture is 513 characters of junk — and it does
*not* work: drop the length bound and `raw.rsplit(".", 2)` raises `ValueError`
on an unparseable string, the never-raise `except` swallows it, and
`verify_tenant_claim(...) is None` holds **with or without the guard**. The
mutation would not have reddened, and the survivor would have been recorded as
closed on a test that could never fail for it.

The fixture used is therefore a **correctly minted, fully valid, merely
oversized** claim: a 437-char payload + `.` + a 10-digit exp + `.` + a 64-hex MAC
= exactly **513** chars, one past the documented 512 bound. With the guard it is
refused without the MAC ever being computed; without the guard it verifies and is
**accepted**. Both assertions then redden, for two independent reasons — which
is what row 12 shows.

The second assertion is the point of the guard: `:274` is a refusal to
**compute**, not a refusal to trust. The spy substitutes `services.rate_limit`'s
`hmac` MODULE attribute (plan 06's `_FakeClock` idiom) rather than patching
stdlib `hmac.new` globally — complete, because `rate_limit` uses exactly
`hmac.new` and `hmac.compare_digest`; scoped, so this file's own minter is
unaffected. A negative control inside the same class asserts an ordinary claim
reaches the MAC **exactly once**, so the zero above is a decision rather than an
accident.

| Survivor | What the mutant actually produced | Consequence in production terms |
|---|---|---|
| #9 `split` | a dotted-payload claim landed in `claimtest:unverified:b654…` | every dotted tenant shares ONE bucket; and `verify` returned `None`, i.e. `"a.b.c"` truncated out of existence |
| #10 no empty guard | **`claimtest:t:`** | a real, shared, tenant-*shaped* bucket belonging to no tenant, that every empty-payload caller collides in |
| #11 `startswith` | `claimtest:anon` for payload `public-enemy` | every `public*` tenant merged into the bucket the public teaser shares with the whole internet — a cross-tenant DoS where the tenant's own identity is what put them there |

Each class carries its control **inside** it: #11's positive control asserts the
exact payload `"public"` still buckets to `:anon` at both functions, so a "fix"
that deleted the anonymous arm entirely (giving every teaser visitor a private
bucket, i.e. no anonymous ceiling at all) still reddens.

### Oracle direction — zero self-referential assertions

`grep`ped and confirmed: the only symbols referenced from the module under test
are the **three functions under test** (`verify_tenant_claim`,
`tenant_rate_limit_key`, `tenant_or_platform_key`). Not `ANON_PAYLOAD`, not
`_CLAIM_MAX_CHARS`, not `_NO_CREDENTIAL`, not `credential_hash`, not
`_platform_bucket`.

Every expected value is a literal or a stdlib re-implementation typed into the
test file: the bucket strings, the 512/513 boundary, `"public"`, and
`_NO_CREDENTIAL_HASH = "b6545eef9260416b"` (= `sha256("unauthenticated")[:16]`,

`verify_tenant_claim`'s **docstring** — the same idiom as
`tests/test_process_key.py:3065-3099` and `test_limiter_identity._mint_claim` —
so no claim is ever built by calling the verifier's own helpers. A claim signed
by the code under test would prove only that the code agrees with itself
(programme non-negotiable #3).
