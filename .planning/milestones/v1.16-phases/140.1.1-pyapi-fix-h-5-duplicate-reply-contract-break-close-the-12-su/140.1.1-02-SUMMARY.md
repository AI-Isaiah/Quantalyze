# Phase 140.1.1 Plan 02: PYAPIFIX-02 — venue faults answer 424, not 403 — Summary

When the caller's exchange blips, `/process-key` now answers **424 + `recoverable: true`**
instead of **403 + `recoverable: false`** — so the caller retries and succeeds rather than
being sent to rotate credentials that were never broken. The fix is a **permanent-code
ALLOW-LIST defaulting to transient**, so a venue code nobody remembered to list fails SAFE.

**PYAPIFIX-02 closed by enumeration:** 2 in-fence sites fixed (A1 status, A2 `recoverable`),
3 members (A3/A4/A5) enumerated and blocker-named `BLOCKED-BY: TS-05`.

## Decisions Recorded

### 1. `MISSING_SCOPE` is in the allow-list, and it is load-bearing

`services/exchange.py:1043-1059` (the deribit `scope_detail` arm) sets `read_only=False` +
`error_code="MISSING_SCOPE"` and **returns early without ever setting `valid=True`** — so
`_scope_rejected` fires with `_reject_code == "MISSING_SCOPE"`. It is reachable.

Because the new default is *transient*, omitting it would have dropped a **permanently
missing read scope** onto the 424 retry path: an infinitely retried key, a NEW bug of exactly
the class this requirement closes. The negative-control parametrisation pins
`MISSING_SCOPE → 403 / recoverable:false`, so a future "just reuse long_fetch's set" refactor
reddens rather than silently regressing.

### 2. `long_fetch.py` is deliberately BYTE-UNCHANGED — divergence recorded, not unified

Verbatim, as the plan requires:

> long_fetch's local `permanent_codes` omits MISSING_SCOPE and therefore retries a
> permanently-missing read scope; unifying it with the shared constant is a correct fix but
> changes worker retry semantics — deferred, not overlooked.

`git diff 56fb7167..HEAD --name-only -- services/ingestion/long_fetch.py` → **empty**. All 30
long_fetch tests green, unedited. The divergence is also recorded in the constant's own
docstring in `services/exchange.py`, so a reader at the definition site cannot miss it.

PATTERNS §8's "all three consumers read it or none is added" constraint was **overridden by
the checker W-3 ruling** and that override is exercised here: re-pointing long_fetch would
flip its `MISSING_SCOPE` handling transient→permanent on the worker retry path — a production
behaviour change named in no requirement and no success criterion.

### 3. `_envelope_error` gained a `recoverable` parameter — the callee cannot always derive it

`_envelope_error` serves **seven** call sites (`:726` validate-only failure, `:1030`/`:1057`
CSV finalize, `:1080` missing strategy_id, `:1109` strategy-not-owned, the new 424 arm, and
the `:1362` 403 arm). Two code universes flow through it and they **fail safe in opposite
directions**:

| Universe | Unknown code should default to | Why |
|---|---|---|
| Venue probe codes (unbounded, adapter-set) | **recoverable** | a forgotten venue code must not become a permanent credential accusation |
| The route's own vocabulary (closed, in-file) | **terminal** | no retry makes a caller the owner of someone else's strategy |

A blanket `not in PERMANENT_VALIDATION_ERROR_CODES` would therefore have marked
`STRATEGY_NOT_OWNED` recoverable — the exact failure the plan's A2 constraint names. Both
universes are enumerated instead (`PERMANENT_VALIDATION_ERROR_CODES` +
`_ROUTE_TERMINAL_ERROR_CODES`), and the caller may **state** the verdict outright.

The decisive case the parameter exists for: **`VALIDATION_UNEXPECTED` is not a function of
the code string.** Our own fallback (`val.error_code is None`) is permanent — that is what
fence test `:2568` pins — while an ADAPTER-set `VALIDATION_UNEXPECTED` may be a transient
exchange error and escapes to 424. Same string, two verdicts. The derivation defaults it
terminal (the safe half) and the 424 arm — the only place an adapter-set one can land —
passes `recoverable=True`.

### 4. `_run_validate_only`'s failure arm improved for free, and stayed 200

`:726` passes `val.error_code` straight through, so `PROBE_FAILED` and `DDOS_PROTECTION` now
answer `recoverable: true` there as well. The **status is unchanged at 200 + `ok:false`** —
the 140.1-05 scope fence — and its pinned tests stay green. No test anywhere in the repo
asserted `body["recoverable"]` on this route before this plan, so nothing was silently
re-baselined.

## Oracle Discipline (programme non-negotiable #3)

Zero self-referential oracles, verified by construction:

- **`PERMANENT_VALIDATION_ERROR_CODES` is never imported by any test.** Both parametrisations
  type their own literal code lists. An oracle that iterated the set under test could not fail
  when a member is added to or removed from it — the exact shape that let the review's
  mutation survivors ship green.
- **The human copy is quoted, not imported.** `test_process_key_sync_probe_failed_body_does_not_contradict_itself`
  types `"Try again in a moment."` as a literal rather than reading it out of
  `services/exchange.py:1203-1206`. An oracle that read the string back from the module that
  produces it could not fail if the copy and the flag drifted apart again — which is the
  precise defect being closed.
- **Statuses are literals** (`424`, `403`, `200`), never `getattr`-ed from the route.
- **The envelope key set is a literal set**, so adding a wizard-facing field is a deliberate
  act with a failing test rather than a silent information-disclosure surface (T-140.1.1-06).
