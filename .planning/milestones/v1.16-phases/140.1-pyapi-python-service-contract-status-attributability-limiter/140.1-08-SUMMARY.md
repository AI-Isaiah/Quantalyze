## PYAPI-07 — the canary, and its proof

**Design.** `_CANARY = "CANARY_SECRET_98d1"` is placed at
`context.api_secret` in a body that fails
`_ProcessKeyBody._validate_per_flow_required_keys` — the
`model_validator(mode="after")` whose `loc` is `["body"]` and whose `input` is
the **entire** payload. The oracle is:

```python
haystack = resp.text + "\n" + "\n".join(f"{k}: {v}" for k, v in resp.headers.items())
assert haystack.count(_CANARY) == 0
```

**Whole serialised response, body AND headers, counted to zero** — not
`assert "input" not in body`. A field probe passes for any handler that moves
the echo to a differently-named key or into a header; the count does not.

**Proven leaking before the fix** (run against the pre-fix service):

```json
{"detail":[{"type":"value_error","loc":["body"],
  "msg":"Value error, flow_type='onboard' requires context keys ['api_key']",
  "input":{"flow_type":"onboard","source":"okx",
           "context":{"strategy_id":"s1","wizard_session_id":"wiz",
                      "api_secret":"CANARY_SECRET_98d1"}},
  "ctx":{"error":{}}}]}
```

**After:**

```json
{"ok":false,"code":"VALIDATION_FAILED",
 "human_message":"Some of the values sent with this request are not valid.",
 "detail":"body: value_error","correlation_id":"...","recoverable":false}
```

**Mutation M4 — re-add `input` to the handler's error dicts.** Applied
(`... MUTANT_M4={err.get('input')!r}`), ran, **5 tests RED including both
canary oracles**, reverted, re-ran **11 passed**, `grep -c MUTANT main.py` → 0.

**App-global proof:** the canary case is repeated on `/api/match/recompute` — a
different router, no limiter — with the canary in `allocator_id`. Zero
occurrences there too, and `detail == "body.allocator_id: uuid_parsing"`.

**Anti-vacuity:** a handler returning a fixed `"invalid"` string would pass
07a/07b/07c. Two tests pin the detail as a *derived literal* —
`"body.allocator_id: uuid_parsing"` and `"body: value_error"` — and a third
pins two simultaneous failures naming both paths.

### `msg` is dropped too — stated because the plan lists only input/ctx/url

The plan's action is "build detail from `type`+`loc` **only**", and RESEARCH's
handler table says the same. `msg` therefore goes as well, and that is
load-bearing rather than incidental: `ctx.error` is called out as re-embedding
"the validator's message" — which means `msg` **is** that message. For a
generic pydantic error `msg` can carry the input (`union_tag_invalid` embeds
the tag value), and for our own validators it names server-side feature flags
verbatim. The cost is debuggability: `body: value_error` says less than
`Value error, flow_type='onboard' requires context keys ['api_key']`. That is
mitigated server-side — the handler logs the **same** type+loc summary with the
`correlation_id`, deliberately not the full errors, because a log line is a
second copy of the credential and the copy that survives longest.

## PYAPI-08 — the 429 literals

**Body** (key set asserted as an **equality**, so an added debug key fails):

```json
{"ok":false,"code":"RATE_LIMITED",
 "human_message":"Too many requests. Please wait a moment and try again.",
 "detail":"Rate limit exceeded: 5 per 1 hour",
 "correlation_id":"<uuid>","recoverable":true,"retry_after_seconds":3600}
```

**Header:** `Retry-After: 3600` — `int()`-parseable, asserted `0 < n <= window`,
and asserted **equal to** `body.retry_after_seconds` so a header-reading and a
body-reading consumer cannot disagree.

**Retry-After derivation:** the true remaining window from
`limiter.limiter.get_window_stats(*request.state.view_rate_limit)` (slowapi
stashes that tuple at `extension.py:525`, immediately before it raises), falling
back to the **full** window length on any failure. Never shorter — a short wait
is a retry storm, which is the failure mode the header exists to prevent.

**Mutation M5 — change the `code` literal.** Applied
(`"MUTANT_M5_THROTTLED"`), ran, **08a and 08c RED**, reverted, **7 passed**,
`grep -c MUTANT` → 0.

**Second route:** `/api/csv/validate` (a different router, L-4 in plan 07's
table) returns the identical envelope with `"Rate limit exceeded: 30 per 1 hour"`.
All 10 statically decorated routes inherit the registration.

## Deviations from Plan

### Rule 2 — auto-added, correctness

1. **`msg` is dropped from the 422 alongside `input`/`ctx`/`url`.** The plan's
   critical warning 1 names only three keys but its action says "type + loc
   ONLY"; RESEARCH's own rationale for dropping `ctx` is that `ctx.error`
   re-embeds the message, which makes `msg` the same carrier. Documented in the
   handler and in the rewritten TRAP-9 test.
2. **The `X-Service-Key` MISMATCH arm captures.** The plan says "wire the same
   capture into the middleware's unset/mismatch arms"; the mismatch arm is
   C-11's **headline** seen from the receiving end (a stale Vercel
   `ANALYTICS_SERVICE_KEY` is a 401 storm the breaker never sees). Guarded to
   non-empty headers so it cannot fire on prober noise.
3. **`retry_after_seconds` is carried in the 429 body as well as the header.**
   Same reasoning as `retryable` in the 5xx envelope — a body-reading consumer
   must not be able to disagree with a header-reading one. Pinned by a test.
4. **Bounded output.** The 422 detail summarises at most 5 errors (the error
   count is caller-controlled) with each `loc` part capped at 60 chars.

### Rule 3 — cleaning up my own mess

5. **`docs/STATUS_CONTRACT.md` §7 extended** (commit `1baf01e8`) — a 6th file
   beyond the plan's four-file `files_modified`. Mirrors plan 06's precedent of
   adding its own block. §2 already *promised* the scalar-`detail` behaviour for
   422/429; this records where it now lives, so 140.2 reads the doc as spec
   rather than re-deriving it. Doc-only, no code effect. Checked plan 09's
   frontmatter first: it touches only a `.planning/` artifact, so there is no
   wave conflict.
6. **The test harnesses are bounded-and-driven, not fixed-call-count.** The
   first version of `test_rate_limit_contract.py` spent exactly `LIMIT` calls.
   It passed in isolation and **failed in the full suite**: slowapi *appends* to
   `limiter._route_limits[endpoint]` on every decoration, sibling suites reload
   `routers.portfolio`, and all N duplicate limits share one bucket key — so one
   request costs N tokens. Verified directly (`len(_route_limits[...]) == 2`
   after one reload). Root-caused rather than papered over, and the reason is in
   the helper's docstring.
