### How the enumeration was done (reproducible)

Enumerated by **behaviour** — "every arm of these four files that can answer
with a status the breaker would count, or that mis-blames the caller" — not by
the syntax of a known instance, which is this programme's documented under-count
root cause.

```bash
# 1. every 5xx-capable HTTPException in the four files, whatever its shape
grep -n "status_code=5" routers/match.py routers/simulator.py routers/portfolio.py main.py
# 2. the 502 arms a 503-only grep would miss (there are none in these files —
#    stating the null result is the point; step 2 is not optional just because
#    step 1 looked complete)
grep -n "status_code=502" routers/match.py routers/simulator.py routers/portfolio.py main.py
# 3. every JSONResponse literal — the mechanism that appears in NEITHER of the
#    above greps, and the reason the class gate had an off-by-one in itself
grep -n "JSONResponse" routers/match.py routers/simulator.py routers/portfolio.py main.py
# 4. read the enclosing handlers end-to-end (match.py:1619-1900,
#    simulator.py:405-465, portfolio.py:605-1185, main.py:198-300) so an arm
#    that answers a countable status WITHOUT a status_code= literal cannot hide
```

Step 1 found 12 lines; two of them (`portfolio.py:2242`, `:2446`) are the
Python `/api/verify-strategy` route the contract's §7 explicitly excludes as
not seam-reachable, and `main.py:279` is S-24. Step 3 is what surfaces
**S-23 and S-24 at all** — both are `JSONResponse` literals inside
`BaseHTTPMiddleware` / a route body, invisible to steps 1's `HTTPException`
reading. Result: exactly the S-13..S-20 + S-23 rows of RESEARCH's table, at the
documented lines, no drift, no additional site, no spurious site.

## The two raw-exception leaks (T-140.1-10)

`f"Scoring failed: {err}"` (S-15) and `f"Eval failed: {err}"` (S-17) rendered
whatever a pandas/Supabase/PostgREST exception happened to carry — table names,
row payloads, DSNs — into a response body. Both are gone:

```
$ grep -nE 'f"(Scoring|Eval) failed: \{' analytics-service/routers/match.py
$ echo $?
1        # zero matching lines
```

The diagnostic was **moved, not deleted**. Each site mints a `uuid4()`
correlation_id, logs `logger.error(..., correlation_id, err, exc_info=True)`,
and returns that same correlation_id in the envelope — so an operator joins a
user's report to the full traceback without the leak. Both canary tests assert
`resp.text.count("CANARY_ERR") == 0` **and** `"CANARY_ERR" in <the log>` **and**
that the body's correlation_id appears in the log; a fix that simply deleted the
logging would turn them red too.

## Deviations from Plan

**One, and it is a documentation-truth fix, not a behavioural deviation.**

**1. `analytics-service/services/db.py` docstring updated (not in the plan's
`files_modified`).** `PaginatedSelectTruncated`'s docstring stated *"The hint
flows into the client-visible **503** detail in `routers/match.py`, so callers
must not embed multi-tenant or PII payloads."* S-16 changes that status to 400,
so the sentence became false the moment the remap landed — and it is the
sentence that tells future `paginated_select` callers why they must not put PII
in a hint. Changed `503` → `400 EVAL_WINDOW_TOO_LARGE` (with the former status
noted); the PII constraint is preserved verbatim. **1 line of prose, 0 lines of
logic**, and the file is not in any other 140.1 plan's `files_modified`, so
there is no cross-plan diff collision. Precedent: 140.1-03 updated a module
docstring in the same commit as the behaviour it described, for the same reason.

Two points where the plan left a choice and it was resolved (not deviations):

2. **The `correlation_id` at S-15/S-17 is minted, not inherited.** The plan says
   "structured log with correlation_id at the same site"; `routers/match.py`'s
   routes take no `Request` and have no correlation-id concept (unlike
   `simulator.py`, which reads `x-correlation-id`). Minting a `uuid4()` avoids a
   route-signature change and still satisfies the requirement, because the same
   id is in the log **and** in the response body — which is what makes the join
   possible.
3. **S-16 keeps the truncation hint in the client copy.** The plan only requires
   stripping `{err}` at S-15/S-17. The hint is our own structured, curated,
   explicitly-non-PII field (per its own docstring), the route is admin-only,
   and dropping it would have made the db.py docstring stale in a *different*
   direction. The actionable "narrow lookback_days (or scope with partner_tag)
   and retry" instruction is appended — the test pins `"lookback_days" in
   envelope["detail"]`.

## Obligations handed forward

**To Phase 140.2 (SEAMCORE)** — in addition to O-1…O-9 already written into
`docs/STATUS_CONTRACT.md` §6:
- **The emit side is now COMPLETE.** Every deliberate error from the 11 seam
  endpoints is one of `4xx` / `424` / `503`+Retry-After+dependency / `500`
  `retryable:false`, or a bodyless `500` (S-21/S-22). The discriminator needs no
  Python-side follow-up.
- **`400` joins the CALLER bucket from a NEW source.** S-16 is the first case
  where a `400` arrives from a condition that used to be a `503`; if 140.2's
  discriminator special-cases "was this previously an outage?", it will be wrong.
- **`body.detail.correlation_id` now exists on S-15, S-17 and S-18.** Surfacing
  it in the UI's error copy is the cheapest possible support channel; 140.3's
  call.

**To Phase 146 (RATE-03):** `/api/match/recompute` and `/api/match/eval` carry
no rate limiter at all (see Scope fences). Both are SERVICE_KEY-gated, so the
exposure is an authenticated-caller loop rather than an anonymous one, but
`/eval` in particular is an unbounded aggregation over `lookback_days` and now
answers `400` rather than `503` when it is driven past the paginator cap — i.e.
the accidental back-pressure the old 503 provided (via the breaker) is gone by
design. A limiter there is now load-bearing, not merely hygienic.

**Hygiene flag (recorded, no code change):** the pre-existing
`resp.status_code not in (401, 503)` assertion in
`test_verify_service_key_middleware.py::test_correct_service_key_passes_middleware`
still names `503` as "a middleware rejection". That is now vestigial — the
middleware's two rejection statuses are `401` and `500`. It was deliberately not
touched: adding `500` to the tuple would make the test flaky (the admitted
request reaches a route that legitimately 500s with no DB env), and removing
`503` changes nothing. Flagged so a reader does not mistake it for a live claim.
