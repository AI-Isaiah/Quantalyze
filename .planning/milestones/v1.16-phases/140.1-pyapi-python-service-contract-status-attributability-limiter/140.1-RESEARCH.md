### Q1.2 RECOMMENDATION — (a) + (c) + (d) as ONE mechanism

**Bucket on an HMAC-verified tenant claim, with a dedicated anonymous bucket and a stacked global ceiling.**

The replacement for `routers/process_key.py:75-105` returns, in order:

| Condition | Bucket | Rationale |
|---|---|---|
| `X-Tenant-Claim` present, HMAC valid (`hmac.compare_digest`), unexpired, payload != `public` | `process_key:t:<user_id>` | forgery-resistant per-tenant window |
| HMAC valid, payload == `public` | `process_key:anon` | the whole public teaser shares ONE allowance — this is what closes C-09 |
| header absent / malformed / bad HMAC / expired | `process_key:unverified:<sha256(bearer)[:16]>` | **never raise** (G-8); degrade to today's behaviour and WARN, so a caller that stops sending the header is visible before it starves anyone |

Plus a second stacked decorator carrying a platform ceiling keyed on the bearer hash.

**Why (a) not (b):** (a) reuses the secret the endpoint *already* authenticates with (G-15) — zero new
trust assumptions, zero new production secrets. (b) needs a new secret AND a TS change on four routes
AND still cannot serve the teaser, which has no JWT by construction (G-13).

**Why a header, not a body field:** G-7. Not a style choice.

**Why `key_func` must never raise:** G-8 — a raising key function converts a throttling concern into an
unhandled 500 `text/plain`, which then feeds the TS breaker. That is the exact A-02/C-12 class this
programme exists to close.

**Ordering interaction with PYAPI-04:** G-6 shows auth is gate 3 today. Once PYAPI-04 moves
`_verify_internal_token` ahead of the limiter, the `unverified` bucket becomes reachable only by holders
of `INTERNAL_API_TOKEN` — i.e. "a trusted caller forgot the header", exactly the WARN case.
**Plan PYAPI-02 and PYAPI-04 in the same wave.** Shipping PYAPI-02 alone leaves an unauthenticated
caller able to allocate `unverified` buckets.

**Rollout order (no flag day):** ship the Python key function FIRST (it tolerates a missing header by
falling back), then the TS minting. This keeps the TS half genuinely mechanical and additive, satisfying
the CONTEXT boundary rule rather than straining it.

## Q2 — The status attributability contract (PYAPI-05)

### Q2.0 The contract (this is what 140.2 builds its discriminator on)

**The status code answers exactly one question: *should this response count against the analytics
service's own health?*** Everything else — user copy, remedy, retry affordance — is carried in the body
and is 140.3's concern.

Four classes. Every 5xx-capable site must be assignable to exactly one, **at the site**, without
downstream inference:

| Class | Decision question | Status | `Retry-After` | 140.2 obligation |
|---|---|---|---|---|
| **CALLER** | Is the caller's request, credentials, or authorization at fault? | `400` / `401` / `403` / `404` / `422` / `429` | on 429 only | never counts |
| **CALLER'S EXCHANGE** | Is the third party *the caller named* at fault (venue down, throttling us, key revoked at the venue, IP-allowlist change)? | **`424 Failed Dependency`** | optional | **never counts** |
| **SERVICE-TRANSIENT** | Is one of *our* dependencies temporarily unavailable such that an identical retry could succeed? | `503` | **required** | counts — but keyed on the named `dependency`, not globally |
| **SERVICE-PERMANENT** | Is this a misconfiguration or a bug that an identical retry cannot fix? | `500` | **never** | **never counts** — a deterministic fault can only be cleared by an operator, so counting it guarantees a self-sustaining outage (A-12 / C-17 class) |

Two rules follow, and they are the load-bearing ones:

- **R-1 — `500` means "do not retry".** Today `500` is used for both bugs and transient failures, which is
  why A-02's undecryptable key can re-trip the breaker forever. Splitting `500` (permanent) from `503`
  (transient) makes the breaker's input set decidable without body parsing — which matters because
  **TRAP-2**: an unhandled exception is `500` `text/plain` (verified: `starlette.middleware.errors`
  `ServerErrorMiddleware.__call__` → `PlainTextResponse("Internal Server Error", status_code=500)`), so
  `500` *must* be safe to classify with no body at all.
- **R-2 — every deliberate 5xx body carries `{code, dependency, retryable}`.** `code` is the stable
  machine discriminator PYAPI-10 asks for; `dependency` names *which* of our dependencies failed
  (`mt5-gateway`, `kek`, `supabase`, `egress-proxy`) so 140.2 can key a breaker per dependency instead of
  the single global `breaker:railway` that A-01 shows is false. An unhandled `500` has no body — that is
  the signal that it is unclassified, and R-1 makes it safe.

### Q2.2 The hard case, stated explicitly

> *A 502 for "the user's exchange is down" must not trip our breaker, but it is genuinely not the user's
> fault either. What status does it get, and why?*

**`424 Failed Dependency`, with `code: EXCHANGE_PROBE_FAILED` and the venue name in the body.**

Reasoning, in the order it must survive review:

1. **It cannot be 5xx.** Status is the breaker's input (R-1) and the analytics service is provably
   healthy in this scenario — it successfully reached the venue and received a refusal. Emitting 5xx
   makes C-12 true: one dashboard render with five keys during a Binance outage = five 502s = a global
   trip that denies Deribit users, the optimizer, admin match and CSV finalize.
2. **It should not be `400`.** `400` already means "your request was malformed" across
   `exchange.py:96,114,123,130,143,203,204,385,393,412`. Overloading it destroys the distinction between
   "fix your input" and "wait for your venue", which is the single most important thing to tell this user.
3. **`424` is exact and free.** It is a registered IANA status (RFC 4918 §11.4), it is a 4xx so it is
   breaker-inert by construction, and it is distinguishable **from the status line alone** — which matters
   because TRAP-2 means the body may be absent.
4. **"Not the user's fault" is a copy problem, not a status problem.** The 4xx/5xx axis answers
   *"is our service degraded?"*, not *"who is to blame?"*. Conflating those two questions is the root
   cause of both A-01 and C-12. 140.3 renders `424` as *"Binance is not responding right now — your key
   is fine, try again shortly"*, which is neither an accusation nor a false claim about our uptime.

**Inter-phase obligation this creates for 140.2:** the discriminator must treat `424` as *recoverable,
non-counting*. If 140.2 collapses all 4xx into "caller error, not recoverable", `424` renders as an
un-retryable dead end — the B-01/B-22 failure shape. Record this in the phase contract explicitly.
