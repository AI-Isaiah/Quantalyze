### The correct shape — both halves

**`strategy_verifications` has NO `user_id` column.** Columns are
`id, strategy_id, wizard_session_id, status, trust_tier, flow_type, source, metrics_snapshot, errors,
correlation_id, created_at, updated_at` — `migrations/20260501055202_strategy_verifications.sql:77-98`.

So `UNIQUE (user_id, wizard_session_id)` is **not available without a schema addition**. Two options:

| Option | Shape | Pros | Cons |
|--------|-------|------|------|
| **A (RECOMMEND)** | `UNIQUE (strategy_id, wizard_session_id)` | No new column, no backfill. `strategy_id` is `NOT NULL` + FK'd. Tenancy inherits from `strategies.user_id`. ### Migration-ordering hazard

`supabase/migrations/**` merged to `main` **auto-applies to PROD**. The `sql-tests` CI job runs
against the **live TEST project** (`qmnijlgmdhviwzwfyzlc`) — so a test asserting the new shape is RED
in CI until the migration is applied *there*. Safe order:

1. Author the migration. Apply to **TEST** via Supabase MCP `apply_migration` **before opening the PR**.
   Then fix the `schema_migrations` stamp — MCP stamps `now()`, not the filename timestamp.
2. One PR carries: migration + SQL test + Python change. CI `sql-tests` then runs green against the
   already-migrated TEST project.
3. Merge → auto-apply to PROD → **watch the run and verify**, do not assume.

**Do-not-drop-first:** CREATE the new composite unique index, verify valid, **then** DROP the old
single-column one. Reversing the order opens a window with no uniqueness at all — a double-submit
storm writes duplicate SV rows that then block the new index build.

**Duplicate pre-flight:** mirror the M-1 block at `20260510173005:55-67`, retargeted at
`(strategy_id, wizard_session_id)`. Without it a `CREATE UNIQUE INDEX` failure inside `BEGIN/COMMIT`
leaves a partially-applied migration.

**⚠️ `IF NOT EXISTS` name-reuse trap:** do **not** reuse the name
`strategy_verifications_wizard_session_id_unique_idx` for the new composite index. `CREATE UNIQUE
INDEX IF NOT EXISTS <existing name>` is a **silent no-op** against the old definition — the migration
reports success, the index is unchanged, and A4/A5 would be the only things that catch it. Use a new
name (e.g. `strategy_verifications_strategy_wizard_session_uniq`). `[VERIFIED: Postgres semantics + the existing migration uses IF NOT EXISTS at :83]`

### CONCURRENTLY — needed, and the trap

**Needed?** Undecided from source alone; **it depends on the PROD row count, which must be measured
first.** The existing migration reasoned about exactly this at `:75-82`: *"At current row counts the
build completes in <1s; if the table grows past 1M rows, split this STEP into a standalone
non-transactional migration."* That precedent, plus `SET lock_timeout = '3s'` at `:46`, is the
decision rule. **Plan a `checkpoint:human-verify` that runs `SELECT count(*) FROM
strategy_verifications` against PROD before choosing.** `[VERIFIED: migration comment]` `[ASSUMED: current row count]`

**The trap, if CONCURRENTLY is chosen:**

| Trap | Consequence |
|------|-------------|
| `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY` **cannot run inside a transaction block** | Supabase CLI wraps each migration file in a transaction → `25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. The file must contain **no** `BEGIN`/`COMMIT` and must be its own migration. The existing file is wrapped (`:44 BEGIN;`) — do not add CONCURRENTLY to it. |
| A failed CONCURRENTLY build leaves an **INVALID** index behind | It still enforces nothing but does consume writes. Must be dropped manually. The plan needs an explicit cleanup step + a `pg_index.indisvalid` assertion. |
| `CREATE UNIQUE INDEX CONCURRENTLY` fails at the **second** pass on duplicates | Same INVALID-index residue, and the pre-flight DO block cannot be in the same transaction to protect it. Run the duplicate check as its own prior migration. |
| Self-verify DO blocks | The existing file's self-verify pattern (`:289-348`) assumes a transaction. A non-transactional CONCURRENTLY file can still `DO $$`, but cannot `ROLLBACK TO SAVEPOINT` — drop the smoke-test pattern from that file. |

**Recommendation:** if the count is under ~100k, use the plain transactional form with
`SET lock_timeout='3s'` and keep the self-verify + pre-flight blocks. Reach for CONCURRENTLY only if
the measurement says otherwise, and then split into three files: (1) duplicate pre-flight +
abort, (2) non-transactional `CREATE UNIQUE INDEX CONCURRENTLY` + validity assertion, (3) `DROP INDEX`
of the old name + self-verify.

### Load-bearing new fact: the enqueue RPC already dedupes

`enqueue_compute_job` → `_enqueue_compute_job_internal`
(`migrations/20260716090000_retire_compute_analytics_kind_rpc_guard.sql:181+`) performs a
select-existing on `(target, kind)` restricted to `status IN ('pending','running',
'done_pending_children')` and **returns the existing id** rather than inserting; the INSERT itself is
`ON CONFLICT DO NOTHING` with a post-conflict re-select. `[VERIFIED: source read]`

⇒ **Re-calling `enqueue_compute_job` on the duplicate path is safe.** It cannot double-enqueue while a
job is live, and it *will* create one when none exists. This removes the main objection to the
recommended shape and means **no new SQL is required for PYAPI-09**.

Residual: if the prior job reached a **terminal** status (`done` / `failed_final`), the dedupe misses
and a new job is created. Gate the re-enqueue on the SV row's `status` being non-terminal (`draft`) —
precisely the wedged state — so a legitimately-completed session does not silently re-sync.

⚠️ `process_key.py:923-935` passes **no** `p_idempotency_key`, though the RPC accepts one
(`migrations/20260515210300_scoring_weight_overrides_high_hardening.sql:258`). Dedupe is therefore
purely `(strategy_id, kind, non-terminal status)`-based today. Passing `verification_id` as the
idempotency key is a cheap tightening but is **not required** by PYAPI-09 — flag, do not scope-creep.

### The three candidate mechanisms

| # | Mechanism | Fixes C-19? | Fixes C-20? | New migration? | Verdict |
|---|-----------|-------------|-------------|----------------|---------|
| **1** | **Enqueue-aware pre-check** — move the pre-check below the `strategy_id` branch; on an idempotent hit for a long-fetch flow whose SV row is non-terminal, call `enqueue_compute_job` (idempotent per above) and return the **true** `queued` value | **YES** | **YES** (the move alone un-shadows the csv-finalize branch) | **No** | ✅ **RECOMMEND** |
| 2 | Make INSERT+enqueue atomic in one SECURITY DEFINER RPC | YES | **NO** — a double-submit still short-circuits at the pre-check *before* reaching the atomic RPC | Yes — a production event | ❌ Reject as primary. Also collides with Phase 145's ownership of finalize's transaction shape. |
| 3 | Reconciliation sweeper (cron finds SV rows with no compute_job, enqueues) | eventually | no | Yes — new job kind + cron | ⚠️ Follow-up only. The caller still receives a false `queued:false` at the moment of the call. |

**Minimal correct shape = #1.** Trade-offs, stated honestly:

- **Cost:** one extra RPC round trip, on the duplicate path only. Negligible.
- **Risk:** depends on `_enqueue_compute_job_internal`'s dedupe staying as it is. That is a *shared*
  RPC with many callers, so the plan must **pin** its dedupe behaviour with an assertion (V-09b
  below) rather than assume it.
- **Does not** add `Idempotency-Key` header support — explicitly deferred (OPS-03, per CONTEXT.md).

### The reply contract itself — the part PYAPI-09 actually owns

`queued` today means *"this call enqueued a job"*. That is unobservable to the caller and, on the
duplicate path, false by construction. Redefine it:

> **`queued` means: a non-terminal `compute_job` exists for this verification at the moment of reply.**

That predicate is checkable, and mechanism #1 makes it *true* rather than merely asserting it. Add an
explicit `job_state` so a caller can distinguish the three cases `queued:false` collapses today:

| Case | Today | Proposed |
|------|-------|----------|
| synchronous flow, work already done inline | `queued:false` | `queued:false, job_state:"not_applicable"` |
| duplicate, job live | `queued:false` ❌ lie | `queued:true, job_state:"running"` |
| duplicate, wedged (no job, SV still `draft`) | `queued:false` ❌ wedge presented as success | after #1: `queued:true, job_state:"enqueued"` |

Fold `job_state` under PYAPI-10's single discriminator rather than bolting on a fourth ad-hoc key.

**Both WIZARD_DUPLICATE emitters must change** — `:747-755` **and** `:910-918`. TRAP-5.

### Scope fence — exactly where the 140.1 / 145 line falls

**IN 140.1 (this phase):** everything inside `analytics-service/routers/process_key.py` and the reply
body it emits. Specifically: the pre-check's **position** in the handler, its enqueue-awareness, and

**OUT — Phase 145 (JOB-06) owns:** (a) whether `finalize_csv_strategy` + persist-daily-returns +

**The boundary case, resolved:** moving the pre-check below the csv-finalize branch **is 140.1 work**.
It is control flow inside `/process-key`'s own handler, not finalize's transaction shape. It must

  token gets its own bucket too, and a caller who replays the *right* token shape burns the real one.

#### What the regression test asserts

Three assertions, each falsifiable without reading the implementation:
