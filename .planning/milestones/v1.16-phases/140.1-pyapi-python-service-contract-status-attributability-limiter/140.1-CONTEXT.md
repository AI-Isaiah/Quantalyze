<domain>
## Phase Boundary

**This phase changes `analytics-service/` (Python/FastAPI) and the SQL schema it depends on.**
It owns **what the service EMITS**: HTTP status codes, response body shapes, limiter identity, and
idempotency semantics.

It is the FIRST of three repair phases inserted after Phase 140:

| Phase | Owns | Language |
|-------|------|----------|
| **140.1 (this)** | what the service EMITS — status codes, body shapes, limiter identity | Python + SQL |
| 140.2 SEAMCORE | the error TYPES the TS core derives from those emissions | TypeScript |
| 140.3 SEAMUX | how those types RENDER to users | TypeScript/React |

**Why this phase is first:** PYAPI-01 is the programme's only CRITICAL (a cross-tenant leak) and is
independent of the breaker entirely. PYAPI-05 settles the 4xx-vs-5xx contract that 140.2's
`SEAMCORE-01` discriminator consumes — planning 140.2 first would build a discriminator against a
contract this phase is about to change.

**Out of this phase:** anything in `src/` (TypeScript). If a finding requires a coordinated
TS-side change, this phase ships the Python/SQL half and records the TS obligation for 140.2/140.3
rather than reaching across the boundary. The one exception is a TS change that is *purely
mechanical* and required for the Python change not to break production (e.g. accepting a new field);
call it out explicitly in the plan.
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Scope — the 10 requirements
`PYAPI-01` … `PYAPI-10` in `.planning/REQUIREMENTS.md`. Every one must appear in some plan's
`requirements` field. Their evidence is Cluster C of the findings doc (C-01, C-04, C-08..C-23).

### Severity ordering
1. **PYAPI-01 (C-08) is CRITICAL and lands first.** `strategy_verifications_wizard_session_id_unique_idx`
   is a single-column, non-partial, non-tenant-scoped unique index, and the duplicate pre-check runs
   on the **service-role** client (not RLS-scoped). A colliding UUID returns another tenant's
   `verification_id`, `status` and `trust_tier`.
2. Then the availability/security cluster: PYAPI-02 (anonymous platform DoS), PYAPI-04 (auth ordering),
   PYAPI-05 (status attributability).
3. Then contract hygiene: PYAPI-03, 06, 07, 08, 09, 10.

### Locked technical decisions
- **Verification of PYAPI-01 is an RLS/SQL gate under `supabase/tests/test_*.sql`.** Per this repo's
  standing rule, `*_live.py` and `skipIf(!HAS_LIVE_DB)` vitest **never run in CI** — a test in those
  forms is not a gate. A migration alone is not proof.
- **Attributability (PYAPI-05) is decided at the source, not inferred downstream.** A fault in the
  caller's request, credentials, or the caller's *exchange* answers **4xx**. Only a genuine
  service-side fault answers 5xx. This is what makes 140.2's discriminator possible at all.
- **Throttle identity must be per-tenant.** Today `/process-key` is one global bucket keyed on
  `sha256(INTERNAL_API_TOKEN)`, which every lambda sends. `X-User-Id` was deliberately removed as
  spoofable and only WARN-logs — so the per-tenant identity must be derived from something the
  caller cannot forge. **This is the phase's main open design question; the researcher must resolve
  it before the planner commits to a mechanism.**
- **No new limiter library.** `services/rate_limit.py` already exists and is the pattern the three
  offending routers bypass.
- **`mypy --strict` must pass** — `cd analytics-service && python3 -m mypy --strict
  --follow-imports=silent services/ routers/ models/`. CI's `python` job runs it; a milestone pytest
  run does NOT, so mypy errors stay latent until PR CI. Narrow unions with `cast()`, never
  `# type: ignore`.
- **Migrations auto-apply to PROD on merge to `main`.** Any migration here is a production event.
  Follow the repo's timestamped-migration convention and re-base any `CREATE OR REPLACE` on the
  LATEST definition (grep ALL migrations first).

<specifics>
## Specific Ideas

- **PYAPI-01** almost certainly needs a partial + tenant-scoped unique index AND a pre-check that is
  either RLS-scoped or explicitly filtered by the calling tenant. Fixing only the index leaves the
  service-role read able to see foreign rows; fixing only the query leaves the constraint able to
  reject a legitimate insert with a foreign collision. **Both halves, or the class is not closed.**
- **PYAPI-04**: auth is currently the LAST of three gates on `/process-key` (validation → slowapi →
  token check) because the `X-Service-Key` middleware skips that path. Reordering is the fix; the
  regression test must prove an unauthenticated request cannot reach validation (no flag
  enumeration) and cannot consume throttle budget.
- **PYAPI-09**: the duplicate pre-check returns ~175 lines *before* `enqueue_compute_job`, while the
  `strategy_verifications` draft INSERT commits *before* that. Dying between them yields
  `WIZARD_DUPLICATE, queued:false` forever — surfaced to the user as `200 {ok:true, accepted:true}`.
  Note C-20: this needs **no timeout** to trigger; a plain double-submit does it.
- **PYAPI-07**: FastAPI's 422 echoes the request body — including raw exchange `api_secret` — and the
  PUBLIC teaser forwards it verbatim to an anonymous browser.
</specifics>
