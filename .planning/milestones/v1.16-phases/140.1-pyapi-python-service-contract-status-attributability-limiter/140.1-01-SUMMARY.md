20 rows is ~5,000× under the ~100k threshold the RESEARCH decision rule sets (itself derived
from `20260510173005:75-82`, which built the original index in <1s and said to split into a
non-transactional `CONCURRENTLY` migration only past ~1M rows). **Single transactional
migration** is therefore correct; `CONCURRENTLY` was deliberately not used (cannot run inside a
transaction block — `25001` — and a failed build leaves an INVALID index that enforces nothing
while still costing every write). `SET lock_timeout = '3s'` bounds the worst case.

Zero duplicates on both projects means the pre-flight `DO` block will not abort at PROD apply.
It is retained anyway as the guard against drift between authoring and merge.

## PROD-Apply Watch Obligation

**This migration auto-applies to PROD on merge to `main`. It is a production event.** Two things
to watch, both stated with their rationale rather than left as "keep an eye on it":

**1. Migration apply itself.** Watch the Supabase migration run and verify afterwards that
`strategy_verifications_strategy_wizard_session_uniq` exists over
`{strategy_id, wizard_session_id}` and that
`strategy_verifications_wizard_session_id_unique_idx` is gone. The in-file self-verify `DO`
block asserts exactly this and will abort the transaction if either is false, so a green apply
is already meaningful — but confirm, do not assume.

**2. Deploy-skew window (ACCEPTED, with rationale).** The index swap lands on PROD at merge;
Railway redeploys the Python service on its own schedule. In the gap, the OLD code's unscoped
pre-check (`process_key.py:722-728`, `.eq("wizard_session_id", …).maybe_single()`) runs against
the NEW composite index. `maybe_single()` raises if it sees more than one row — which requires
two tenants to hold the *same* `wizard_session_id` on *different* strategies. Under the old
index that state was impossible to create, so it can only arise from writes made after the swap,
and only if two independently minted `uuid4` values collide (~2^122). **Accepted:** the window
is bounded by one Railway redeploy and the trigger requires a cross-tenant uuid4 collision.
The window closes entirely when Plan 140.1-02 lands the `.eq("strategy_id", …)` filter on both
read sites.

**3. Read-path note (not a risk, recorded so it is not rediscovered as a bug).** After the drop
there is no index on `wizard_session_id` alone, so the pre-140.1-02 unscoped query seq-scans.
At 20 PROD rows this is immaterial, and 140.1-02's `strategy_id` filter is served by the new
index's leading column. `strategy_verifications_strategy_id_idx` still covers the factsheet /
marketplace / admin join paths.

## Decisions Made

1. **Option A over Option B.** `UNIQUE (strategy_id, wizard_session_id)`, not a new `user_id`
   column. Verified from the catalog (not just the migration source) that
   `strategy_verifications` has no `user_id`: its 16 columns are
   `id, strategy_id, wizard_session_id, status, trust_tier, flow_type, source,
   metrics_snapshot, errors, correlation_id, created_at, updated_at, transitioned_at,
   encrypted_credentials, public_token, expires_at`. Tenancy derives through
   `strategy_id → strategies.user_id`, exactly as the table's own owner RLS policy does.

2. **A4 asserts catalog columns, not an `indexdef` `LIKE`.** The plan suggested qualifying with
   `indexdef LIKE '%wizard_session_id%'`. Implemented as a stronger form: read `pg_index.indkey`
   → `pg_attribute.attname` ordered array and compare to the literal
   `ARRAY['strategy_id','wizard_session_id']`, after asserting exactly one such unique index
   exists. This satisfies the plan's intent (disambiguate from
   `strategy_verifications_public_token_unique_idx`) and additionally removes the
   substring-false-positive surface a `LIKE` on the index *name* would carry, and closes the
   PL/pgSQL `SELECT INTO` multi-row silent-first-row hazard the plan warns about.

3. **No `down/` rollback file.** Only 26 of 229 migrations carry one and the plan did not list
   it in `files_modified`. The exact rollback SQL is recorded in the migration header comment
   instead — same information, no unplanned file.

4. **Migration timestamp `20260726000225`** (current UTC at authoring), which sorts after the
   repo's latest `20260723172032`.
