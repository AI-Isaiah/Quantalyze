### How the enumeration was done (reproducible)

Enumerated by **behaviour** — "every arm of these two routers that can answer with a
status the breaker would count" — not by the syntax of a known instance, which is this
programme's documented under-count root cause.

```bash
# 1. every 5xx-capable raise in the two files, whatever its literal shape
grep -n "status_code=5" analytics-service/routers/exchange.py analytics-service/routers/internal.py
# 2. the 502 arms a "5xx" grep alone would still find, but a "503" grep would not
grep -n "status_code=502" analytics-service/routers/internal.py
# 3. read both handlers end-to-end (exchange.py:90-450, internal.py:120-360) so an arm
#    that answers a countable status WITHOUT a status_code= literal cannot hide
```

Result: exactly the S-01..S-12 rows of RESEARCH's table, at exactly the documented
lines — no drift, no additional site, no spurious site. Steps 1 and 2 alone would have
found all 12 here, but step 3 is the one that generalises: it is the step that catches
S-23-shaped sites (`main.py:230` is a `JSONResponse` literal and appears in **neither**
grep). S-23 is plan 140.1-04's; the helper deliberately ships
`service_error_response()` so 04 is not forced to hand-roll a divergent body.

## Design decisions (these are the contract; 140.1-04 and 140.2 inherit them)

**1. The R-2 envelope always lives at `body.detail`.** FastAPI's default `HTTPException`
handler serialises to `{"detail": <detail>}`, so `service_error()` puts the whole
envelope there. `service_error_response()` (for `BaseHTTPMiddleware` sites that must
RETURN, per the `main.py:221-228` never-raise trap) nests it **identically**, so a
consumer never has to know which mechanism produced the response. Precedent, not
invention: `routers/simulator.py:453` already raises `HTTPException(500, detail={...})`,
and RESEARCH names it "the closest existing envelope; the helper must be a superset".

⚠️ **Consequence, deliberate and recorded:** `body.detail` is now an object on these
responses, so the three TS sites doing `err.detail ?? "..."` (Class 5) will render
`"[object Object]"` until 140.2 reads `body.detail.detail`. This is **not** a
reintroduction of C-14 in the 422/429 path — plans 140.1-08's handlers keep those
`detail`s scalar at the top level, which is why they need no TS change. It is invisible
to users because `feat/v1.16-production-resilience` is never merged mid-programme.
Recorded as obligation **O-5** in the contract.

**2. On a `424`, `dependency` names the caller's VENUE.** Q2.2 requires the venue name in
the body; the envelope's key set is fixed at `{code, dependency, retryable, detail}`, so
adding an `exchange` key was not available. `424` never counts toward the breaker, so the
two vocabularies cannot collide in practice — and `_validate` **refuses** a `424` whose
`dependency` is one of our own service dependencies, so they cannot collide by accident
either. Documented in §4 of the contract with the "never use a 424's dependency as a
breaker key" warning.

**3. `RETRY_AFTER_SECONDS` holds only dependencies with a genuinely transient arm**
(`mt5-gateway: 30`, `supabase: 15`). `kek` and `egress-proxy` are absent on purpose:
every fault of theirs in the current site set is permanent, and advertising a wait for
them invites exactly the retry loop R-1 exists to stop. `supabase` is pre-seeded for
140.1-04's S-13/S-14/S-19.

**4. `service_error` raises `ValueError` on a contradictory combination** (a `500` that
claims `retryable`, a `503` with no `Retry-After` or a foreign dependency, a `424` marked
non-retryable or naming one of ours, a `4xx` naming a dependency). These are programming
errors at raise sites whose arguments are literals, so the failure is deterministic and
caught by tests; an escaping `ValueError` becomes a bodyless `500`, which R-1 makes safe
and loud.

## Deviations from Plan

**None in substance.** Three points where the plan left a choice and it was resolved:

1. **Helper surface is slightly wider than the plan's sketch** — `service_error()`,
   `service_error_response()` and `service_error_body()` rather than one function. The
   plan itself anticipated this ("returning an HTTPException *or JSONResponse where the
   caller needs one*"); `service_error_response()` exists specifically so 140.1-04's S-23
   middleware fix is not forced to hand-roll a divergent body, which the plan's own
   Task-3 note warned about. No behavioural deviation.
2. **`dependency` is always present, `null` when nothing of ours failed** — the plan says
   "body key set is exactly `{code, dependency, retryable, detail}`". A stable key set
   (rather than omitting `dependency`) means a consumer never probes for key existence.
3. **`RETRY_AFTER_SECONDS` is not keyed for all four dependencies** — see decision 3
   above. The plan said "a single dict of per-dependency integer literals"; seeding
   permanent-only dependencies with a wait would contradict R-1, which is the stronger
   constraint.

## PYAPI-06 (partial — the S-08 site only)

`_alert_kek_unavailable()` in `internal.py` follows `services/audit.py:428-467`: `set_tag`
before `capture_message` so events are greppable per-cause, the whole capture wrapped in
`try/except: pass` so a Sentry transport failure cannot mask the path it reports on, and
a structured `logger.error` alongside.

**Bounded at one capture per 300 s** (`_KEK_ALERT_WINDOW_S`, with a test-only
`_reset_kek_alert()` mirroring the existing `_reset_rate_limit()`). A stale KEK fires on
*every* permission probe and the dashboard renders five badges per page, so an unbounded
capture is a flood that gets muted — indistinguishable from no signal at all. The
**log** is deliberately emitted on every occurrence: the rate of rejection is itself the
operator's evidence, and logs do not page.

Pinned by `test_s08_kek_failure_captures_exactly_one_sentry_alert_per_window`: four
consecutive KEK failures ⇒ exactly one `capture_message` and one `set_tag`, and neither
the tag nor the message contains any secret substring (nothing in the function reads the
KEK value or the caller's token).

The plan's fence was honoured: `internal.py`'s hand-rolled per-`key_id` limiter
(`:67-91`, now `:125-154` after the alert block was inserted above it) is **untouched** —
it is correctly keyed and not part of any class here.
