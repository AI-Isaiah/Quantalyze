## PYAPI-10b: the verdict moves to 403 — and which envelope it uses

`routers/process_key.py:1313` (was `:1004` in the plan's numbering — the plan-02 restructure moved
it; I located it by behaviour, as the bare `_envelope_error` return under the `_scope_rejected`
gate, and confirmed it is the site RESEARCH's table calls site 2).

**Envelope: the route's own top-level Phase-17 DESIGN-05 envelope** (`ok`, `code`, `human_message`,
`debug_context`, `correlation_id`, `recoverable`), **not** `services/error_contract.py`'s
`service_error_response`, which nests under `body.detail`. Three reasons, in the order they must
survive review:

1. **The plan forbids a parallel envelope** (critical warning 4: "extend `_envelope_error`'s key
   vocabulary, never invent a parallel envelope"). Every other deliberate 4xx *on this route* —
   the 401 at :981, the 422s at :1008/:1031, plan 02's 403 at :1060 — already uses `_envelope_error`
   wrapped in a `JSONResponse`. Introducing a second body shape for one of five sibling refusals is
   exactly the drift the warning names.
2. **`error_contract` is the 5xx-capable seam's contract, and `/process-key` is not on it.**
   `STATUS_CONTRACT.md` §7 records `/process-key` as **S-22**: *"`routers/process_key.py` contains
   ZERO explicit 5xx sites"* — it has no row in the S-01…S-24 site map because it has no site to
   remap. Its consumer is the wizard's error renderer, which reads `ok`/`code`/`human_message`
   directly off the body.
3. **The status-line semantics still obey PYAPI-05.** 403 is the CALLER class: the caller's
   credentials are at fault, nothing of ours failed (`dependency` would be `null`), an identical
   retry cannot succeed (`retryable` would be `false`), and a 4xx is breaker-inert by construction.
   The two envelopes disagree about *where the keys live*, never about *what the status means*.

`_envelope_error` now carries a comment stating this so the next reader does not re-litigate it.

## ⚠️ Finding: the rejection gate is UNIFIED, so more than the scope arms moved

**Stated loudly because it is the one consequence a reviewer must actively accept.**

`_scope_rejected` (`process_key.py:1245-1249`) is a **three-arm** predicate:

```python
_scope_rejected = (
    not val.valid                                          # ordinary validation failure
    or val.read_only is False                              # write-capable key
    or val.error_code in {"TRADE_SCOPE", "WITHDRAW_SCOPE"}  # scope violation
)
```

There is **one** return site behind all three. Moving it to 403 therefore also moves ordinary
`not val.valid` failures — `AUTH_FAILED`, `PERMISSION_DENIED`, a malformed CSV on the synchronous
path — off 200.

**I executed the plan literally rather than splitting the arms.** The reasoning, since this is the
kind of judgement the programme's non-negotiables exist to constrain:

- The plan **saw** this predicate: its `read_first` cites `_scope_rejected` at the pre-restructure
  `:956-961`, which is exactly this three-arm OR. This is not a premise that fails against source.
- The plan's own acceptance criterion — *"every `_envelope_error` call site is either
  JSONResponse-wrapped with an explicit 4xx or the `:488` validate-only arm"* — is **only
  satisfiable** if the whole return moves. Splitting the gate would leave a second bare
  `_envelope_error` at 200 inside the handler and fail the criterion.
- RESEARCH's stated mechanism generalises: *"a fault in the caller's credentials answers 4xx"*.
  All three arms are caller credential/input faults, so all three are CALLER-class.
- One return site is also the *safer* long-run shape: the security arm cannot silently drift back to
  a success status while the sibling arms stay 4xx.

**Residual imprecision, recorded not fixed:** a malformed CSV now answers **403** where **422**
would be the more precise CALLER status. `403` is not *wrong* (it is CALLER-class and
breaker-inert), but it is coarse. Splitting the gate into `403` (scope/authorization) + `422`
(malformed input) is a clean follow-up and is **out of this plan's scope fence**. Handing it to the
phase's consolidation plan rather than acting on it unilaterally.
