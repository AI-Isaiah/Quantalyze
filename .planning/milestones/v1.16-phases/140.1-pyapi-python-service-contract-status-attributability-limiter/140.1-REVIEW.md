## HIGH (5)

### H-1 · Transient venue faults now answer a permanent CALLER 403 — REGRESSION
- **Severity:** High · **Confidence:** High (reproduced end-to-end against the real route)
- **Location:** `analytics-service/routers/process_key.py:1295-1299` (gate), `:1360-1365` (return site)

PYAPI-10b moved the unified `_scope_rejected` verdict from 200 to **403**. That one gate covers
`not val.valid` **and** `read_only is False`, and `services/exchange.py` sets those for the
venue-*transient* codes `PROBE_FAILED`, `EXCHANGE_UNAVAILABLE`, `NETWORK_UNAVAILABLE`,
`RATE_LIMITED`, `DDOS_PROTECTION` (`services/exchange.py:1112,1123,1135,1145,1207`). Under the
contract these are CALLER'S EXCHANGE → **424, retryable:true, dependency=venue**. They now
answer 403: CALLER fault, non-retryable, terminal.

**Why it matters:** the status line alone must be decidable, and it now decides *wrongly*. When
OKX blips, 140.2 reads 403 and tells the user to fix their credentials; the retry that would
have succeeded never happens. The **same semantic condition on `/exchange/validate-key`
correctly answers 424 retryable:true** (`routers/exchange.py:473-479`) — so this is an
**incomplete class**: venue-fault classification applied to one route, not the other. The body
contradicts itself: `recoverable:false` beside human copy reading *"Try again in a moment."*

This is **distinct from known issue #3**. Known #3 is 422-vs-403 *sharpness* on `not val.valid`.
This is a wrong *class* reached via the `read_only is False` arm, with a retryability
consequence — a materially more severe axis. **No test exercises it**: the parametrised 403
test covers only `TRADE_SCOPE`/`WITHDRAW_SCOPE` (`tests/test_process_key.py:2435-2444`), both
genuine caller faults.

```
>>> STATUS: 403
>>> BODY: {"ok":false,"code":"PROBE_FAILED","human_message":"Could not verify the key's
    permission scopes — the permission probe failed. Try again in a moment.",
    ...,"recoverable":false}
```

### H-2 · `create_exchange` failures classified 424 — a venue blamed for our own bugs
- **Severity:** High · **Confidence:** High
- **Location:** `analytics-service/routers/internal.py:416-431` (S-11)

S-11 classifies any non-`ValueError` out of `create_exchange()` as **424 CALLER'S EXCHANGE**
with copy *"We could not open a connection to your exchange. This is a problem at the venue."*
`create_exchange` **opens no connection and never contacts the venue** — it is
`EXCHANGE_CLASSES.get()`, a dict build, `cls(config)`, two attribute sets
(`services/exchange.py:817-861`). There is no network I/O in it at all.

Every remaining failure mode there is *ours*: a ccxt constructor `TypeError`, an `AttributeError`
on `exchange.has`, an `ImportError`, an OOM. Under the contract those are SERVICE-PERMANENT
**500**. As a 424 they are breaker-inert **and** 4xx — no one is ever paged, the bug hides
behind a tidy classified response, and the user waits on a venue that is fine. The identical
call at `routers/exchange.py:447-454` answers 400 — same function, same failure, two classes in
one phase. S-06 (`exchange.py:467`) did the correct `ccxt.BaseError`-vs-everything-else split;
that split was available here and was not applied.

### H-3 · The helper does not enforce the scalar-`detail` guarantee it documents
- **Severity:** High · **Confidence:** High (proven by execution)
- **Location:** `analytics-service/services/error_contract.py:158-181`, guard at `:82-155`

The contract states three times that `body.detail.detail` is "**always** a scalar string"
(module docstring `:30`, `STATUS_CONTRACT.md` §2, R-2). `_validate()` never inspects `detail`;
`service_error_body` passes it through. A list or dict is emitted verbatim:

```
OK  detail=list -> status=500 detail={'code':'X',...,'detail':['a','b']}
OK  detail=dict -> status=500 detail={'code':'X',...,'detail':{'k':'v'}}
```

This is the one guarantee 140.2's `SEAMCORE-01` renders from. It is enforced only by a
`str | None` annotation, in a codebase full of `Any` (`key_data.get(...)`, `exc.args`,
`err.detail`) that mypy passes through silently. Every *other* class rule in the file is a hard
constructor guard; this one is a suggestion. No test covers it — the new files only assert
`isinstance(env["detail"], str)` on responses those same tests built from string literals.

**PYAPI-01 / the CRITICAL path**

- **No DROP-then-CREATE gap** — STEP 1 creates before STEP 2 drops; uniqueness is never absent.
- **NULL-safe by schema:** `strategy_id UUID NOT NULL`, so the "NULL tenant bypasses the unique
  index" hazard does not exist. `strategy_id` is the correct tenant key (the table has no
  `user_id`; it matches the owner RLS policy's own subquery).
- Both directions proven at the DB: different strategies + same session → both succeed; same
  strategy + same session → `23505`.
- Timestamp ordering correct (latest existing `20260723172032`), no collision among 231 migrations.

**PYAPI-04 / auth ordering**

  it is the **outermost** middleware — ahead of CORS, routing and body validation. A dependency
