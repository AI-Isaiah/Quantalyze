## v1 Requirements

Requirements for the v1.2.1 milestone. Each maps to exactly one roadmap phase. Phases continue from v1.2's Phase 33 — this milestone is Phases 34–38.

### Explicit unified annualization — 252 (Phase 34)

> **Redefined 2026-06-24 (user decision).** ANNUAL-02/03/04/05 originally targeted asset-class-divergent
> annualization (crypto 365). The user chose to keep **252 as the universal basis** for all displayed/ranking
> metrics (comparability), with the `periods_per_year` param shipping so the basis is explicit and a future
> per-asset divergence is a call-site change. The ×1.20 mismatch is fixed by converging `equity_reconstruction`
> down to 252. Wording below reflects the redefinition.

- [x] **ANNUAL-01**: `compute_all_metrics` accepts a `periods_per_year` parameter (default 252 preserves today's behavior) so the annualization basis is explicit at the call site rather than hardcoded to 252 inside the function — threaded through every annualization site (the explicit `np.sqrt(252)`/`*252` sites AND the quantstats sharpe/sortino/volatility/cagr calls).
- [x] **ANNUAL-02**: The basis is resolved at the call site. Every current production caller (CSV analytics runner, crypto trades path, the coming per-key derive path) resolves **252** — the unified comparability basis. The param makes a future per-asset divergence (e.g. crypto 365) a one-line call-site change, not a function rewrite; no production caller diverges from 252 today.
- [x] **ANNUAL-03**: All displayed/ranking metrics remain on the unified 252 basis — crypto and TradFi strategies stay apples-to-apples on the ranking page (preserving the deliberate convention documented in `test_mt5_golden_fixtures.py`), rather than crypto inflating ~1.204× on a 365 basis.
- [x] **ANNUAL-04**: Golden-parity fixtures pin the unified 252 basis (existing fixture unchanged) AND add a parametrized `periods_per_year=365` proof case asserting the output rescales by ≈√(365/252), so a silent regression in the param threading (or a convention flip) fails CI loudly.
- [x] **ANNUAL-05**: The known `equity_reconstruction`@365 vs `compute_all_metrics`@252 ×1.20 mismatch is resolved by converging `equity_reconstruction` down to the 252 basis — the two paths agree at 252 with no residual scale factor.

### Per-key dailies foundation (Phase 35)

- [x] **DAILIES-01**: The per-key dailies store carries an `api_key_id` axis (a dedicated per-key store or an added `api_key_id` axis), resolving the `csv_daily_returns.strategy_id NOT NULL FK→strategies` blocker without inventing synthetic strategy rows.
- [x] **DAILIES-02**: The default-ON broker-dailies derive job (`run_derive_broker_dailies_job`) is generalized from strategy-scoped to allocator-key-scoped, deriving realized+funding dailies per crypto exchange key at the 365 basis.
- [x] **DAILIES-03**: Existing allocator exchange keys are backfilled into the per-key dailies store so historical keys produce a per-key series, not only keys onboarded after this milestone.
- [x] **DAILIES-04**: The new/changed storage ships a migration with an RLS review that scopes per-key dailies to the owning allocator (no cross-tenant read of another allocator's per-key series).

### Repoint stats reads (Phase 36)

- [x] **UNIFY-01**: `src/lib/queries.ts` reads persisted per-key dailies for an allocator's stats instead of reconstructing them from the blended `allocator_equity_snapshots`.
- [x] **UNIFY-02**: The portfolio equity curve is computed as a blend of the per-key dailies through the compute path, so Overview equity/KPIs converge to the realized+funding @365 basis (the same honest source the Scenario tab and factsheets read).
- [x] **UNIFY-03**: Live HOLDINGS (the positions table) continue to read the poll/snapshot path — the holdings-vs-stats split is preserved, so repointing stats does not stale or break the live positions view.

### Honest per-data-source toggle (Phase 37)

- [x] **DSRC-01**: The scenario adapter (`scenario-adapter.ts`) keys its projection units per `api_key` (per data source) rather than per blended book.
- [x] **DSRC-02**: The composer surfaces a per-data-source toggle UI letting an allocator include/exclude each API key from the projection.
- [x] **DSRC-03**: Excluding a key honestly recomputes the curve and KPIs from the remaining per-key series (now possible because per-key series exist) — never a cosmetic hide over an unchanged blended number.

### Composer factsheet parity + blank-mode fix (Phase 38)

- [x] **PARITY-01**: The composer's equity chart reuses the factsheet `TimeSeriesChart` + `MasterBrush`, so wheel-zoom, drag-pan, brush, and keyboard navigation work in the composer exactly as on the factsheet.
- [x] **PARITY-02**: The composer's max width is relaxed from `max-w-[1100px]` to `1440px` so the factsheet-grade chart has room to render.
- [x] **PARITY-03**: In blank-slate mode (empty baseline) the equity-projection renders the scenario overlay — the `EquityChart` projection guard no longer bails on an empty baseline before considering `scenarioSeries`/`composite`, matching how `DrawdownChart`'s `hasScenario` guard already renders the overlay.

## v2 Requirements

Deferred to a future release. Tracked, not in this roadmap.

### Per-key analytics depth

- **DSRC-V2-01**: Per-trade / per-instrument attribution within a single API key's contribution to the blend.
- **UNIFY-V2-01**: Per-key factsheet surface (a standalone factsheet rendered for an individual exchange key, not just the blended book).
- **ANNUAL-V2-01**: Per-strategy custom trading-calendar annualization (beyond the binary crypto-365 / TradFi-252 split) — only if a venue's true trading calendar diverges from both bases by test.

## Out of Scope

Explicitly excluded.

| Feature | Reason |
|---------|--------|
| Non-crypto venue expansion (new exchange/broker adapters) | This milestone hardens the existing crypto-exchange + CSV/MT5 paths onto one honest source; adding venues is separate scope. |
| Per-trade attribution / decomposing a key's return into individual trades | The dailies axis is per-key daily returns; per-trade attribution is a v2 analytics-depth feature, not required to unify the stats source. |
| Recomputing peer/percentile panels on the per-key or scenario blend | The v1.1/v1.2 honesty invariant stays LOCKED — you cannot peer-rank a hypothetical or per-source-filtered blend (`ingestSource` gate). |
| A second annualization convention beyond crypto-365 / TradFi-252 | The product is already 252-or-365; introducing a third per-venue calendar is deferred (ANNUAL-V2-01) to avoid convention sprawl. |
