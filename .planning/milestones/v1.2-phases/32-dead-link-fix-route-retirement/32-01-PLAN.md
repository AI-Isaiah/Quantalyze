<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser query string → AddToPortfolio (client) | `?portfolio=<id>` is fully user-controlled; an attacker can craft any uuid. |
| AddToPortfolio (client) → portfolio_strategies (DB) | the attach write crosses into the user's tenant data under Supabase RLS. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Tampering / Elevation | `?portfolio=<id>` → `AddToPortfolio` insert | mitigate | The default id is matched ONLY against the RLS-scoped owned-portfolio fetch (`.eq("user_id", user.id)`); an id the user does not own never appears in that set, so it can never become the `portfolio_id` of an insert. The `portfolio_strategies.insert` is itself RLS-scoped (write rejected for non-owned portfolios). This is an EXISTING RLS guarantee — no new write path, no new server endpoint. Task 1's unowned-id no-op test pins it. Block-on: none. |
| T-32-02 | Information disclosure | the portfolio uuid in the URL | accept | A portfolio uuid in a query string is not a secret (it is already in the path `/portfolios/{id}`); knowing it grants no access without ownership (RLS). |
</threat_model>
