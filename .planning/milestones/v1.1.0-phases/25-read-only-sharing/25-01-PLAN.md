<objective>
Build the security foundation of Phase 25: the `scenario_shares` table (owner RLS + REVOKE anon + a partial unique index enforcing one active share per scenario), the token-scoped `get_shared_scenario` SECURITY DEFINER read RPC that is the SOLE anon data path, the `down/` rollback, the hand-patched `database.types.ts` block, and the load-bearing two-tenant + anon CONTENT-leak + revoke-immediacy SQL test.

This is the phase's reason to exist: a single trusted, self-verifying read function that resolves a snapshot (the saved `draft` JSONB) plus a strictly-scoped re-resolution of ONLY the `addedStrategies[].id` published-strategy series — and nothing else (never holdings/AUM/api_keys, never another tenant's content).

Purpose: RLS and SECURITY DEFINER scoping fail SILENTLY — a loosened predicate ships green unless a test inspects CONTENT by field. The SQL test is the only honest proof of the boundary.
Output: one migration + rollback + SQL content test + the database.types hand-patch + its guard test.

DECISION (Claude's discretion per CONTEXT Area 2, RESEARCH A1/Open-Question-1): **hash in Node, not in SQL.** The repo enables no `pgcrypto digest` extension anywhere (verified: zero `digest(` / `CREATE EXTENSION pgcrypto` in `supabase/migrations/`; only `gen_random_uuid()` is used, which is core pg13+). So the RPC takes `p_token_hash TEXT` (a precomputed sha256 hex), NOT a raw token — `scenario-share-token.ts` (Plan 25-02) is the single digest source-of-truth and the route/page hash before calling. This avoids the unverified pgcrypto landmine and keeps ONE digest site. Where RESEARCH §Pattern 1 shows `get_shared_scenario(p_token TEXT)` hashing internally with `digest()`, build `get_shared_scenario(p_token_hash TEXT)` instead and skip the in-SQL hash line.
</objective>
