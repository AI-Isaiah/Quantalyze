# Phase 19.1: Code Review Report

**Reviewed:** 2026-05-22
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Phase 19.1 re-derives the CSV → analytics → factsheet pipeline through the GSD
workflow. The pre-hardened invariants from PRs #272–#275 (collapsed 42501
probe-oracle, no redundant index, GRANT TO authenticated, jsonb_typeof guard,
PR #273 `_mark_unrecoverable` warning, PR #274 duplicate-date guard, PR #275
audit-skip pragmas, explicit `dailyReturnsSeries` param) are all preserved in
this branch.

The `complete_with_warnings` status is a first-class DB status; the
`run_csv_strategy_analytics` runner writes plain `complete`, while
`run_strategy_analytics` is the only writer of `complete_with_warnings`. The
status type union in `src/lib/types.ts` has been updated and the
`toSyncStatus()` discriminated converter is exhaustive.

No BLOCKER-class defects were identified. Six WARNING-class issues and seven
INFO-class observations are listed below — none of them block the production
deploy, but most should be folded into a follow-up sweep before the next CSV
slice ships.

The finalize_csv_strategy + persist_csv_daily_returns non-atomic gap is
explicitly out of scope per BACKBONE-07 / R4 and is NOT flagged.

## Warnings

### WR-01: CSV runner mis-classifies missing-strategy as an unrecoverable HTTP 500

**File:** `analytics-service/services/analytics_runner.py:1467-1585`
**Issue:** `run_csv_strategy_analytics` calls `_mark_computing` (unconditional
upsert) BEFORE any check that the strategy row actually exists. The
exchange-backed sibling `run_strategy_analytics` (line 748-757) performs a
`SELECT id FROM strategies` first and raises `HTTPException(404)` when the row
is absent, which `classify_exception` maps to `permanent` (no retry). The CSV
path skips that probe — if `compute_analytics_from_csv` is enqueued for a
strategy_id that was deleted between enqueue and dispatch (e.g. wizard race,
admin delete-and-recreate), the unconditional `_mark_computing` upsert on
`strategy_analytics` succeeds (it just creates the row), but then the
`csv_daily_returns` SELECT returns 0 rows, hitting the `len(data) < 2` branch
and writing a misleading `"Insufficient CSV history. At least 2 data points
required."` error. The 400 raised after that gets classified by
`classify_exception` as `permanent`, so the job fails terminally with an
incorrect operator-facing message — a deleted-strategy condition is reported
as a data-quality problem, hampering triage.

**Fix:** Mirror the exchange runner — probe `strategies` first:
```python
strategy_row = await db_execute(
    lambda: supabase.table("strategies")
    .select("id, user_id")
    .eq("id", strategy_id)
    .single()
    .execute()
)
if not strategy_row.data:
    raise HTTPException(status_code=404, detail="Strategy not found")
```
This also avoids a spurious `strategy_analytics` row being upserted for a
nonexistent strategy (the FK on `strategy_analytics.strategy_id` would normally
prevent this, but the upsert may still succeed depending on cascade timing —
worth probing explicitly).

### WR-02: `_load_series` truncates silently at PostgREST default 1000-row cap

**File:** `analytics-service/services/analytics_runner.py:1479-1488`
**Issue:** The CSV daily-returns SELECT uses a bare `.select(...).eq(...).order(...).execute()` with no pagination wrapper. The persistence RPC caps the
series at 5000 rows (migration 20260522120000, line 160), but PostgREST's
default response limit on hosted Supabase is 1000 rows. A strategy uploaded
with 1001–5000 rows persists fine via `persist_csv_daily_returns` but reads
back ONLY the first 1000 rows here, silently truncating the input to
`compute_all_metrics`. Note that `run_strategy_analytics` uses the
`paginated_select` helper (line 212, line 1006) for exactly this reason —
the CSV path inherits the same hazard but skips the protection.

**Fix:** Use `paginated_select` here as well, e.g.:
```python
def _load_series():
    return paginated_select(
        supabase.table("csv_daily_returns")
        .select("date, daily_return")
        .eq("strategy_id", strategy_id),
        order_by=(("date", False),),
        truncation_hint=f"csv_daily_returns strategy_id={strategy_id}",
    )
rows = await db_execute(_load_series)
data = rows  # paginated_select returns the rows list directly
```
The persisted cap is 5000 rows; a single page of 1000 will quietly skip up to
4000. Use the same `PaginatedSelectTruncated` exception handling pattern the
exchange runner uses (line 973-979).

### WR-03: CSV runner does not catch `PaginatedSelectTruncated` like the exchange runner does

**File:** `analytics-service/services/analytics_runner.py:1557-1559`
**Issue:** Companion to WR-02. The catch-all `except Exception as exc` in the
CSV runner would swallow a `PaginatedSelectTruncated` exception if pagination
were added (per WR-02 fix), classifying it as the generic `CSV analytics
computation failed.` instead of preserving the typed signal. The exchange
runner has a dedicated `except PaginatedSelectTruncated` branch (line 1399-1428)
that re-raises after writing a specific `computation_error`. If the WR-02 fix
lands, this handler must mirror that pattern.

**Fix:** When adopting `paginated_select` per WR-02, add:
```python
except PaginatedSelectTruncated as trunc:
    logger.error(
        "csv analytics: pagination truncation for %s (page_count=%d, page_size=%d)",
        strategy_id, trunc.page_count, trunc.page_size,
    )
    def _mark_truncated():
        supabase.table("strategy_analytics").upsert(
            {
                "strategy_id": strategy_id,
                "computation_status": "failed",
                "computation_error": (
                    f"CSV analytics aborted: series exceeds "
                    f"{trunc.page_count * trunc.page_size:,} rows."
                ),
            },
            on_conflict="strategy_id",
        ).execute()
    await db_execute(_mark_truncated)
    raise
```

### WR-04: `dailyReturnsSeries` length-zero short-circuit skips persist + enqueue silently

**File:** `src/app/api/strategies/csv-finalize/route.ts:570-635`
**Issue:** The legacy path gates BOTH `persist_csv_daily_returns` AND the
`after(...)` enqueue of `compute_analytics_from_csv` on `dailyReturnsSeries.length > 0`. For `fmt = "daily_returns"` or `fmt = "daily_nav"` the validator
emits a non-empty series whenever `ok=true`, so this is safe in the wizard
happy path. BUT — when `fmt = "trades"` (currently producing no series per
csv_validator.py:541-561) or when a malformed-but-passing-zod payload happens
to hit `daily_returns_series: []`, the strategy row is created (status =
`pending_review`) but no series is persisted and no compute job is enqueued.
The wizard polls `strategy_analytics.computation_status` and will hang
indefinitely (no row, no terminal state). Operators will see the strategy
exists with no analytics row at all — no signal to investigate.

Worse: the `parseDailyReturnsSeries` helper (line 105-107) treats `undefined`
AND `null` AND empty `[]` identically as `{ok: true, rows: []}`. The
`raw.length > MAX_DAILY_RETURNS_ROWS` guard catches oversized arrays; there is
no `raw.length === 0` guard. A `daily_returns_series: []` body silently lands
a half-baked strategy.

**Fix:** Either (a) require `daily_returns_series.length >= 2` for daily_returns
and daily_nav `fmt`s, OR (b) when persistence is skipped because the series is
empty, write `strategy_analytics` with `computation_status='failed'` +
`computation_error='No CSV series provided'` so the wizard's poller breaks
out. Otherwise the user sees an indefinite spinner. The cleaner option is (a)
— reject at the validator boundary so the strategy is never created.

### WR-05: `csv_source` flag is initialized to `True` regardless of failure path

**File:** `analytics-service/services/analytics_runner.py:1523-1542`
**Issue:** The CSV runner sets `data_quality_flags = {"csv_source": True}`
inside the success branch only, then writes the flags on `_mark_complete`.
On the insufficient-history path (line 1490-1501) and on the
`_mark_unrecoverable` path (line 1562-1570), the `computation_error` row is
written WITHOUT the `csv_source` flag. Downstream consumers reading
`data_quality_flags?.csv_source` to gate the "CSV-uploaded" provenance pill
(per `src/lib/types.ts:335` JSDoc) will see `null` flags on the failed row and
fall through to "missing data" copy instead of "CSV upload failed", losing
provenance information for the user.

**Fix:** Stamp `csv_source: True` in both the failed and complete branches.
The simplest approach is to write the flag inside `_mark_failed` (line 1491)
and `_mark_unrecoverable` (line 1562) too:
```python
def _mark_failed():
    supabase.table("strategy_analytics").upsert(
        {
            "strategy_id": strategy_id,
            "computation_status": "failed",
            "computation_error": "Insufficient CSV history. ...",
            "data_quality_flags": {"csv_source": True},
        },
        on_conflict="strategy_id",
    ).execute()
```
Mirror in `_mark_unrecoverable`. This preserves the provenance signal across
all terminal states.

### WR-06: Test `test_mark_unrecoverable_logs_warning_before_reraise` over-fits the call sequence

**File:** `analytics-service/tests/test_csv_analytics_runner.py:196-247`
**Issue:** The test side-effects on `db_execute` call number (1=mark_computing,
2=load_series, 3=mark_unrecoverable) hard-code the ordering of the runner's
DB calls. If a future refactor inserts a new `db_execute` call between
mark_computing and load_series (e.g. the WR-01 strategy-existence probe), the
3rd call becomes load_series instead of mark_unrecoverable, the side-effect
returns `MagicMock(data=rows)` instead of raising, and the test silently
starts asserting the WRONG thing — the warning would no longer fire because
mark_unrecoverable would now be call #4 which falls through to `return None`.
The test would still pass (because `compute_all_metrics` is patched to raise
and the runner has its own retry logic), but it would no longer regress
test PR #273's mitigation.

**Fix:** Patch `analytics_runner._mark_unrecoverable` (or a named helper) so
the test asserts on the SPECIFIC failing call, not on call-counter position.
Alternatively: route side-effects by inspecting the lambda's enclosing
fn body — but the cleaner approach is to extract `_mark_unrecoverable` as a
testable module-level function and patch it directly. Right now the test
documents intent in a comment ("So make the third call raise") but the
mechanism cannot detect drift.

## Info

### IN-01: `csv-finalize` route's `dailyReturnsSeries.length > 0` gate is duplicated

**File:** `src/app/api/strategies/csv-finalize/route.ts:570, 606, 712, 746`
**Issue:** The `if (... && dailyReturnsSeries.length > 0)` guard is repeated
four times across the legacy and unified paths. A future refactor that adjusts
the gate semantics (e.g. minimum-rows threshold per WR-04) requires touching
all four sites. Extract a single `shouldPersistAndEnqueueSeries(rows)` helper.

### IN-02: `compute_analytics_from_csv` watchdog headroom is only 5 minutes (50% slack)

**File:** `analytics-service/main_worker.py:99-102`, `analytics-service/services/job_worker.py:188`
**Issue:** Other long-running kinds get >=30% slack (compute_portfolio: 10→15min,
sync_trades: 15→30min, reconstruct_allocator_history: 30→35min). The new
`compute_analytics_from_csv` has 10min handler timeout, 15min watchdog — 50%
slack, generous, but tightly above the test invariant of "strictly greater".
The asymmetry is fine for v1, but consider widening to 20min as a future
hardening pass — the handler is pure math + 1 DB SELECT, so 10 minutes is
already huge; the 5-minute headroom matches realistic worst-case (cold cache,
slow benchmark fetch).

### IN-03: `parseDailyReturnsSeries` does not validate the date is a valid calendar date

**File:** `src/app/api/strategies/csv-finalize/route.ts:136-143`
**Issue:** The regex `/^\d{4}-\d{2}-\d{2}$/` accepts `"2024-13-45"` and
`"9999-99-99"`. The persist RPC casts via `(elem->>'date')::DATE` which throws
on invalid dates (SQLSTATE 22008) — a 22008 surfaces as a 500 rather than the
clean 400 the route otherwise promises. Tighten with a `new Date(r.date)` +
`isFinite(d.getTime())` check, or use a date library. Low frequency; the CSV
validator on the upstream multipart route catches most cases.

### IN-04: `_redact_preview` masks-then-projects ordering may leak data on validation-failure path

**File:** `analytics-service/services/csv_validator.py:519-532`
**Issue:** The fallback path (`df_validated = df` after SchemaErrors) routes
through `present_declared = [c for c in df.columns if c in declared_cols]`
before `_redact_preview`. The projection itself is safe (drops undeclared
columns), but in the un-coerced fallback `df`, schema-failing values could
still be present in the declared columns (e.g. a `date` column with malformed
strings). The preview ships them verbatim. Not a privacy leak per se — these
are values the user just uploaded — but the `_redact_preview` regex pattern
might match column NAMES across both branches differently. The current
`_PII_COLUMN_PATTERN` does not match `date`, `daily_return`, `nav`, etc., so
this is safe today; if future schemas declare a column matching the regex
(e.g. `customer_balance`), the behavior diverges between the success and
SchemaErrors branches. Document the assumption.

### IN-05: `SyncProgress.tsx` polls `strategy_analytics` from a browser-side Supabase client

**File:** `src/components/strategy/SyncProgress.tsx:178-205`
**Issue:** The `pollStatus` callback uses `createClient()` from
`@/lib/supabase/client` (browser anon role) and reads
`strategy_analytics.computation_status, computation_error, computed_at` every
3 seconds. The strategy_analytics RLS policies (not in the reviewed migrations
but inherited) gate by strategy owner. If a wizard user navigates away during
sync, the interval keeps polling until unmount. For a >90s `compute_analytics_from_csv`
job, that's ~30 round-trips per user per job. Not a bug per se — but consider
exponential backoff or visibility-API gating to reduce DB load on the
free-tier Supabase project. Not in scope for Phase 19.1, but worth noting.

### IN-06: Test 8b uses regex on file contents to enforce the explicit-param contract

**File:** `src/__tests__/csv-validate-route.test.ts:808-855`
**Issue:** Tests 8b and 8c read `src/app/api/strategies/csv-finalize/route.ts`
via `fs.readFileSync` and run regexes against the source string. This is a
brittle contract-shape check — any refactor that uses a type alias for the
args object, splits the signature across multiple files, or applies
prettier/eslint formatting changes risks breaking these tests for non-
semantic reasons. Consider replacing with a TypeScript AST query (e.g.
`ts-morph`) or by exporting the handler signature for direct
`Parameters<typeof unifiedCsvFinalizeHandler>` introspection.

### IN-07: Migration assertion (e) uses `count < 1` instead of `count = 1` for the GRANT check

**File:** `supabase/migrations/20260522120000_csv_daily_returns.sql:269-278`
**Issue:** The DO-block assertion accepts ANY count >= 1 of GRANT EXECUTE TO
authenticated rows. If a future migration adds a duplicate GRANT (no-op for
PG but signals duplication), this assertion passes silently. Use `= 1` to
catch drift. Cosmetic; impact is observability only.
