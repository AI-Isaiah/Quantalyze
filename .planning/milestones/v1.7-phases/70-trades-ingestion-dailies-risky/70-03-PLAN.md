<objective>
Build the NEW backbone of the reworked phase: the transaction-log **cash-delta ledger** that is
the authoritative realized-cash source for Deribit daily returns (per the LOCKED design —
`analytics-service/docs/deribit-ingestion-design.md`). The ledger crawl (`private/get_transaction_log`,
count=250, continuation→null) captures settlement PnL (funding-inclusive) + fees + delivery in one
pass, paced to the endpoint's harsh ~1 req/s rate limit with backoff on 10028, and FAILS LOUD if the
crawl is truncated. This plan also ships the re-anchored D-02 honesty gate: **ledger completeness
over the date range**, not reconciliation to the fill counts (which the Wave-0 probe proved do not
reconcile to any API surface).

Purpose: a silently-partial ledger is THE corruption risk of this phase — an under-fetched crawl
that renders as a complete track record. The completeness gate + truncation-fail-loud paginator make
that impossible. Subaccount-scoped auth (exchange_token) is supported because subaccount_id is refused
on the read-only LTP keys.
Output: services/deribit_ingest.py (ledger paginator + producer + completeness gate + scope auth) +
CI-runnable synthetic fixtures (no live creds, injected clock).
</objective>

- The ledger = `private/get_transaction_log`. Params: `currency` (req), `start_timestamp`+
  `end_timestamp` (req), `count` MAX 250 (1000 is over the documented max and truncates), `continuation`
  (integer, null when done), and a per-scope auth (`subaccount_id` OR an exchange_token subject).
- Rate limit: get_transaction_log is SPECIAL — cost 10,000, pool 80,000, ~1 req/s, burst 8. The crawl
  MUST pace ≤1 req/s and exponential-backoff on 10028. Skip ccxt for the ledger (no ledger / paging
  issues) — call the raw private endpoint.
- Subaccounts: get_subaccounts returns `id` as a STRING. subaccount_id is REFUSED (-32602
  {"reason":"Not allowed","param":"subaccount_id"}) on the read-only LTP keys → use public/exchange_token
  (param `subject_id`) to mint a read-scoped token per subaccount, OR a per-subaccount key. Per-scope
  auth is a Phase-72 key-provisioning consideration — this plan builds the CAPABILITY (per-scope auth
  in the fetch loop); provisioning of real per-sub keys is deferred.
- D-02 RE-ANCHOR: the honesty gate is LEDGER COMPLETENESS over the date range (continuation→null, no
  rate-limit truncation, every currency × scope covered), NOT reconciliation to 18,778/21,014/61,248.
  Wave-0 BLOCKING_FINDING: those totals are fill-level and reconcile to NO API surface — they become an
  OPTIONAL advisory fill-count cross-check on the trades axis (70-04), never the gate.
