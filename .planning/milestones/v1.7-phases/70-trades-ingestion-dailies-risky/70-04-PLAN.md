<objective>
Land the SECONDARY trades axis (DRB-04 execution detail): a `deribit` branch in `fetch_raw_trades` +
`_fetch_raw_trades_deribit` that fetches fills per scope × currency using the **id-cursor**
`private/get_user_trades_by_currency` endpoint (`historical=true`, `sorting=asc`, advance
`start_id`=last trade_id, continue while `has_more` OR the page is full), per the LOCKED design
(`analytics-service/docs/deribit-ingestion-design.md` — the time endpoint one-page-stalls). Each fill
maps to the existing `FillRow` with `exchange_fill_id = trade_id` for idempotent dedup, and lands in
the `trades` table via the existing upsert.

Purpose/SCOPE: the trades endpoint is NOT the return source — realized returns come from the
transaction-log ledger (70-03/70-05). This axis provides execution detail and an OPTIONAL advisory
fill-count cross-check. The Wave-0 probe proved the known fill totals (18,778/21,014/61,248) do NOT
reconcile to any API surface, so `reconcile_fill_count` is ADVISORY only — the honesty gate is ledger
completeness (70-03's assert_ledger_complete), never this count.
Output: services/deribit_ingest.py id-cursor fill fetch + FillRow mapping + fetch_raw_trades branch +
CI-runnable synthetic fixtures.
</objective>

- The trade fetch = id-cursor `private/get_user_trades_by_currency` with `historical=true`,
  `sorting=asc`, `count`, advancing `start_id`=last trade_id EXCLUSIVE; continue while `has_more` OR
  the page is full (`len==count`) — `has_more` has no documented reliability guarantee. Do NOT use the
  time endpoint `_and_time` (passing both bounds one-page-stalls; Wave-0 root-cause bug #2).

  bug #1: without it the endpoint returns only the last 24h → 674 vs 2,962 for acct3).
- This is the SECONDARY axis. Wave-0 BLOCKING_FINDING: known fill totals reconcile to NO API surface →
  reconcile_fill_count is ADVISORY; the D-02 honesty gate is the ledger completeness gate (70-03).

- `services.deribit_txn.classify_instrument` (70-02) — for kind tagging if needed.
