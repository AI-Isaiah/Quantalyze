<objective>
Land the D-13 Source-widening half of DRB-08: make the ingestion registry deribit-capable — widen
`SUPPORTED_SOURCES` + `_FACTORIES` + `get_adapter` and add a `DeribitAdapter` wrapping the Phase-70
fetch (`deribit_ingest.fetch_deribit_fills`) behind the existing 5-method `IngestionAdapter` Protocol,
mirroring `BybitAdapter`. Phase 68 explicitly parked this widening for Phase 70 (adapter.py comment).

CRITICAL correctness guard (net-new vs the prior plan): `long_fetch.process_key` calls
`adapter.compute_metrics(trades)` and PERSISTS the result. For Deribit, fills carry ZERO realized
cashflow (Wave-0 A3 — realized crystallizes at settlement, captured only in the ledger), so
fill-based metrics would be a silently-empty/wrong track record (BYB-02 class). Therefore
`DeribitAdapter.compute_metrics` must FAIL LOUD: Deribit returns come from the transaction-log ledger
via the broker-dailies ONE-path (70-05), never from fills.

Purpose/SCOPE GUARD: this plan builds the ingestion CAPABILITY only. Live onboarding of the 3 LTP
accounts as verified strategies + secret rotation + per-subaccount key provisioning is Phase 72
(CONTEXT Deferred) — do NOT wire that orchestration here. The read-only scope gate stays enforced.
Output: ingestion/deribit.py DeribitAdapter + registry widening + adapter.py comment update + tests.
</objective>
