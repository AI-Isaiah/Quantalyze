## Milestone Goal

Every surface an allocator touches works end-to-end with real data. A brand-new institutional LP can sign up, connect a read-only exchange API key, see Performance populate, and use a Scenario tab to run what-if analyses that commit through the Bridge outcome-recording flow. No seed fallback anywhere.

## Success Gate

Fresh signup → connect API key → Performance tab populates → open Scenario tab → toggle a holding off → add a Bridge-recommended strategy → commit scenario → outcome recorded — within 10 minutes.

## Decisions and Outcomes

- **Phase 09.1 inserted mid-milestone** to land the designer-provided dashboard vision before Phase 10 built on top of it. Cost: ~6 sessions; benefit: cohesive 6-tab shell for Phase 10 instead of grafting onto the legacy 2-tab dashboard.
- **Phase 11 spun out as v0.16.0.0** because the onboarding/security work landed independently and the v0.15.x line had already been shipping incrementally on `main`.
- **`allocator_holdings` schema (Phase 06):** 4-way XOR on `compute_jobs.target` (strategy_id / portfolio_id / allocator_id / api_key_id) instead of the prior 3-way; idempotent diff-upsert keyed on `(allocator_id, venue, symbol, asof)`.
- **Notes multi-scope reshape (Phase 08):** `user_notes` keyed by `(user_id, scope_kind, scope_ref)` with text scope_ref instead of typed FKs — same precedent as Phase 09's `match_decisions.original_holding_ref`.
- **Bridge over real holdings (Phase 09):** Pseudo-strategy IDs use `holding:{venue}:{symbol}:{holding_type}` text format; ENGINE_VERSION bumped to v2.1.0 to invalidate cached v2.0.0 batches on first cron run after ship.
- **Scenario projection (Phase 10):** Reuses frozen `src/lib/scenario.ts::computeScenario` via `scenario-adapter.ts` cast, zero engine changes; `commit_scenario_batch` RPC for atomic single-tx commit.
