## ▶ v1.5 — Scenario Coverage-Window Blend (Active)

## Overview

v1.5 deliberately rewrites the FROZEN `scenario.ts` blend engine so the modeled "mean
strategy" is an *honest* average of strategies actually co-live over the shown window —
not one diluted toward zero by members that have already ended. It replaces the
"all-started / no-end-bound / 0-fill-the-tail / divisor = every started strategy"
convention with a **coverage-window membership model** (a strategy is a member iff
`enabled AND its data span ⊇ the window`; the divisor counts members only), then plumbs
that window through the allocator UI (steer + auto-toggle), coverage legibility,
persistence (saved / shared / compared), a deliberate golden & e2e re-bake, and a live
authed QA canary.

**Safety ordering** (all four researchers converged): compute core → factsheet-parity
re-verify → UI/state & auto-toggle → coverage legibility → persistence → golden re-bake
→ authed QA canary. The golden/e2e re-bake (Phase 60) is its own phase AFTER compute +
parity are green — never in the same commit that changes the math.

**LOCKED invariants:** `no-invented-data`, 252-day annualization, factsheet
parity-by-construction, WCAG-AA floor, no share-link / cross-tenant leak.
**Zero new runtime dependencies.**

## Phase Details

### Phase 55: Coverage-Window Compute Core
**Goal**: `computeScenario` blends over an explicit coverage window with a constant, honest divisor — an ended strategy no longer dilutes the tail — and every downstream consumer + the frozen-spine guards are reconciled to the new series.
**Depends on**: Nothing (first phase of v1.5; builds on the frozen v1.4 engine baseline)
**Requirements**: BLEND-01, BLEND-02, BLEND-03, BLEND-04, BLEND-05, BLEND-06, BLEND-07, PARITY-02, PARITY-03
**Success Criteria** (what must be TRUE):
  1. `computeScenario` accepts an explicit `[winStart, winEnd]` window (new optional `ScenarioState.window`, positional signature unchanged), and a strategy is a blend member iff `enabled AND its data span ⊇ the window` — the divisor counts members only, so an ended strategy contributes nothing and no longer divides the mean (BLEND-01, BLEND-02).
  2. Interior mid-window gaps stay 0-filled (constant divisor, documented), weighted blends renormalize surviving members to sum-to-1 after a coverage drop (typed weights preserved as source of truth), and a zero-member window returns an honest empty-state — no divide-by-zero, no fabricated zeros (BLEND-03, BLEND-04, BLEND-05).
  3. The output exposes `member_count`, the effective `[winStart, winEnd]`, and `N` so consumers and the UI read the divisor rather than infer it (BLEND-06).
  4. The blend matches an independent from-scratch numpy computation to floating-point precision over the max-overlap window on the 6-strategy golden dataset (mm/neon1/pokeokx/uc244 + OKX/Bybit), with the divisor == live-member count — recorded as an artifact *before* any golden re-bake (BLEND-07).
  5. stress/VaR, benchmark, Monte-Carlo, compare, and the KPI strip produce correct results on the coverage-window series with honest sample-floor behavior on the shorter window, and the latent union-window assumptions in `scenario-benchmark.ts` / `scenario-compare.ts` (and stale header comments) are cleared (PARITY-02).
  6. SCENARIO-05 zero-diff + the `phase-{29,30,31,32,52}-frozen-spine-guards` are **re-baselined as a reviewed act** — never deleted, never blind `--update-snapshots` — while `no-invented-data`, 252-annualization, and the WCAG-AA floor stay green (PARITY-03).
**Plans**: 4 (55-01…55-04) — ✅ COMPLETE (verified 2026-07-01)

### Phase 56: Factsheet Parity Re-Verify
**Goal**: Confirm the real factsheet on the blend stays parity-by-construction after the engine change — it consumes `computeScenario`'s emitted member-windowed series and never re-derives the blend.
**Depends on**: Phase 55
**Requirements**: PARITY-01
**Success Criteria** (what must be TRUE):
  1. The factsheet path (`ScenarioFactsheetChart` / `scenario-factsheet-payload.ts`) is traced and confirmed to consume `computeScenario`'s emitted series — it never re-derives the blend on its own (PARITY-01).
  2. A single-source-of-truth guard asserts parity-by-construction (the factsheet metrics equal `computeScenario`'s metrics on the identical member-windowed series) — parity is proven, not assumed.
  3. The v1.2.2 factsheet-parity specs are extended/re-run and stay green on the coverage-window series; the WCAG-AA + no-invented-data invariants hold.
**Plans**: 1 plan

### Phase 57: Window Control & Auto-Toggle State Machine
**Goal**: The allocator can steer the coverage window and watch membership auto-adjust honestly — the intersection is the default and snap target, widening drops non-covering members, narrowing restores them (within the selected subset only), and an empty intersection is a guided fix, not a dead end.
**Depends on**: Phase 56
**Requirements**: WINDOW-01, WINDOW-02, WINDOW-03, WINDOW-04, WINDOW-05, WINDOW-06, POLISH-01, POLISH-02
**Success Criteria** (what must be TRUE):
  1. The scenario defaults its timeline to the max-overlap (intersection) window of the selected+on strategies — default + snap target, not a hard cap (WINDOW-01).
  2. Widening the window past a strategy's coverage auto-toggles it OFF (removed from blend + divisor); narrowing until it regains full coverage auto-toggles it back ON, operating ONLY within the user's selected subset, never adding an unselected strategy (WINDOW-02, WINDOW-03).
  3. A "Common period (all in)" preset snaps to the selected set's common overlap with all members ON; a "Full range (some drop out)" preset widens to the union, auto-dropping non-covering members (WINDOW-04, WINDOW-05).
  4. When the selected set shares no common window, the app names the outlier(s) and offers a one-click deselect — a guided empty-intersection fix, not a dead-end (WINDOW-06).
  5. The chart brush-zoom stays a **view** control, visually distinct from the analytical window — never merged (POLISH-01); the auto-toggle transition animates so a dropped strategy visibly moves to the excluded state (POLISH-02).
**Plans**: 3 plans (3 waves)
  - [x] 57-01-PLAN.md — unionOf + outlier-detection pure helpers in scenario-window.ts (WINDOW-05/06 targets)
  - [x] 57-02-PLAN.md — window state + post-collapse engine injection + CustomRangePicker control + two presets + POLISH-01 guard (WINDOW-01/04/05, POLISH-01)
  - [x] 57-03-PLAN.md — coverageEligible auto-toggle + animated auto-excluded group + empty-intersection banner (WINDOW-02/03/06, POLISH-02)

### Phase 58: Coverage Legibility & Disclosure
**Goal**: The allocator can see, at a glance, which strategies are in the blend and why — coverage spans, per-row state with reasons, the honest blend header, the cost of including a dropped strategy, and a one-time note that the default changed from the full range to the common period.
**Depends on**: Phase 57
**Requirements**: COVERAGE-01, COVERAGE-02, COVERAGE-03, COVERAGE-04, POLISH-03
**Success Criteria** (what must be TRUE):
  1. A coverage timeline (mini-gantt) shows each selected strategy's data span against the active window, so "why did X drop?" and "how much history to keep it?" are visible (COVERAGE-01).
  2. Each strategy row shows one of three states — in-blend / manually excluded / auto-excluded (outside window) — the third visually distinct and carrying an inline reason (COVERAGE-02).
  3. An always-visible blend header states member count · effective window · N, degrading honestly ("1 strategy — not a blend", "window truncated from full range") (COVERAGE-03).
  4. An auto-excluded row offers a one-click "include → shortens window to [date] (−N months)" affordance that shows the cost before applying (COVERAGE-04).
  5. A one-time union→intersection default-change note ("Now showing the common period where all N overlap · show full range") with an escape hatch is shown so returning users aren't surprised (POLISH-03).
**Plans**: 3 plans (3 waves)
  - [x] 58-01-PLAN.md — BlendHeader (COVERAGE-03) + CoverageStateChip in-blend/manual states (COVERAGE-02) + register POLISH-03 storage prefix
  - [x] 58-02-PLAN.md — AutoExcludedRow amber chip (COVERAGE-02) + include-cost affordance (COVERAGE-04)
  - [x] 58-03-PLAN.md — CoverageTimeline mini-gantt (COVERAGE-01) + one-time DefaultChangeNote (POLISH-03) + composer-axe anchors

### Phase 59: Saved / Shared / Compared Windows
**Goal**: The coverage window is durable — a saved scenario reopens at the owner's window, a shared link recomputes at that same window with no leak, and compare works across each scenario's own window.
**Depends on**: Phase 58
**Requirements**: PERSIST-01, PERSIST-02, PERSIST-03
**Success Criteria** (what must be TRUE):
  1. The coverage window is saved as part of a scenario (`ScenarioDraft` schema_version bump + migration); reopening a saved scenario recomputes today's numbers at the owner's saved window; pre-v1.5 windowless drafts default to intersection with a provenance note (PERSIST-01).
  2. A shared link recomputes-on-open at the owner's window under the new rule, with no live-book / cross-tenant leak, and the recipient's view matches the owner's (identical window derivation via the one shared helper) (PERSIST-02).
  3. Compare (2+ scenarios side-by-side) works with each scenario's own persisted window (PERSIST-03).
**Plans**: 3 plans (2 waves)

  - [x] 59-03-PLAN.md — compare per-scenario window POST-collapse (live-book stays windowless) + per-column {start}–{end} label (PERSIST-03) [wave 2]
