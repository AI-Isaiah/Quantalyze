## Pattern Assignments

### 1. The derive-swap — `process_key.py:863-948` (route, compute-only transform)

**Analog (primary):** `analytics-service/services/analytics_runner.py:2299-2347` — the CSV single-key seam,
the closest structural twin (single strategy, asset-class annualization, reads `.metrics_json`).

**Confirmed signature answer (the task's Q1):** `derive_basis_series` is **compute-only by construction** —
it NEVER persists. Persistence is a *separate* function `persist_basis_series` (`basis_series.py:275`).
So "compute-only (no-persist)" use = **call `derive_basis_series`, read `result.metrics_json`, and simply
never call `persist_basis_series`.** No flag, no special mode. This is exactly what Option c needs.

Signature (`basis_series.py:162-172`):
```python
def derive_basis_series(
    returns: pd.Series,
    benchmark_rets: pd.Series | None,
    *,
    periods_per_year: int,
    cumulative_method: str,
    day_basis: str,
    benchmark_symbol: str | None = None,   # omit — teaser needs no benchmark identity
    scalar_returns: pd.Series | None = None,   # omit — pass None (no byte-identity, D2/Pitfall 4)
    densify_policy: str | None = None,          # omit — default byte-invisible
) -> BasisSeriesResult
```

`BasisSeriesResult.metrics_json` (`basis_series.py:153`, `:265`) IS `MetricsResult.metrics_json` — the
JSON-safe top-level scalar dict. It is populated with **no** `persist_basis_series` call. Confirmed.

**Call-shape to copy** (from `analytics_runner.py:2313-2347`):
```python
_periods_per_year = periods_per_year_for_asset_class(asset_class)  # #597: crypto 365 / traditional 252
_cumulative_method = "geometric"   # teaser default (no denominator_config)
_day_basis = "calendar"            # teaser default
result = derive_basis_series(
    returns,
    None,                          # benchmark_rets — teaser passes None
    periods_per_year=_periods_per_year,
    cumulative_method=_cumulative_method,
    day_basis=_day_basis,
)
scalars = result.metrics_json      # read-only; NO persist_basis_series call
```
`periods_per_year_for_asset_class` lives at `services/metrics.py:43` (imported by analytics_runner at
`:59`). Defaults `geometric`/`calendar` match the analytics_runner defaults at `:2316-2317` (before the
denominator-config override the teaser does not have).

**Input series (D3):** `returns = trades_to_daily_returns(trades_as_dicts, account_balance=None)` is
ALREADY computed at `process_key.py:896-898` — reuse that same call's output; feed it straight into
`derive_basis_series` instead of the current `(1+returns).cumprod()` scalar path.

**Degrade arm (D6) — analog:** `services/job_worker.py:4354-4385` (composite) and
`analytics_runner.py:2355` region wrap the derive in `try/except ValueError`. `derive_basis_series` raises
`ValueError` on `<2 finite rows` (`basis_series.py:206-209`). Map that onto the teaser's EXISTING
degrade-to-nulls arm (`process_key.py:916-928`): on `ValueError`, null the four return-based scalars
(trade-level `total_pnl/trade_count/win_rate` still render). The teaser already has a `len(returns) >= 2`
pre-check at `:899` — the derive's ValueError is the same boundary; keep one guard, not two.

**FLAG C (no clean analog — asset_class source):** every existing `derive_basis_series` caller reads
`asset_class` off a persisted `strategy_row` (`analytics_runner.py:2313-2314`, `:2162` select). The teaser
is **pre-strategy** — there is no `strategy_row` and the sentinel anchor is `status='archived'` with no
meaningful `asset_class`. The planner must decide where the teaser's asset_class comes from (exchange/venue
of the adapter, or per-instrument off the trades, or a hardcoded default). This is the one genuinely-new
decision with no drop-in analog. `periods_per_year_for_asset_class(None)` has a defined fallback — confirm
which branch it returns and whether that is acceptable for a crypto-venue teaser (D2 wants √365 for crypto).

### 2. The 4-key map (`metrics_json` → `MetricsSnapshot`)

**Answer (task Q2): there is NO existing helper that maps `result.metrics_json` → the four
`MetricsSnapshot` fields. This is a NEW inline map.** The existing `to_metrics_snapshot`
(`equity_reconstruction.py:3065-3087`) builds the snapshot from `EquityCurveBuilder` *methods*
(`compute_sharpe()/compute_twr()/compute_ytd()/compute_max_drawdown()`), not from a metrics_json dict —
so it is the **construction-site analog** (shows the exact target field names + that `total_pnl/trade_count/
win_rate` are trade-level, D5), but not a reusable mapper.

`MetricsSnapshot` shape (`services/ingestion/adapter.py:150-164`):
```python
sharpe: float | None
twr: float | None
ytd: float | None            # NOTE: field is `ytd`, NOT `return_ytd` (CONTEXT label is imprecise)
max_drawdown: float | None
total_pnl: float | None      # trade-level — KEEP from EquityCurveBuilder (D5)
trade_count: int             # trade-level — KEEP
win_rate: float | None       # trade-level — KEEP
```

Current teaser build site: `process_key.py:867` `metrics = adapter.compute_metrics(trades)` →
`okx.py:84-89` → `EquityCurveBuilder(trades).to_metrics_snapshot()`. Then `:888`
`_metrics_to_jsonb(metrics)` (aliased import at `process_key.py:49` = `services.ingestion.serde.metrics_to_jsonb`)
serializes it into the JSONB written at `:946`.

**The 4-key map to write** — override the four return-based fields on the builder-produced snapshot with
the derived values, keep the three trade-level fields:
```python
snap = adapter.compute_metrics(trades)            # keeps total_pnl/trade_count/win_rate (D5)
scalars = result.metrics_json
snap = replace(snap,                              # dataclasses.replace on the frozen-ish MetricsSnapshot
    twr=scalars["cumulative_return"],             # top-level  (metrics.py:1178)
    sharpe=scalars["sharpe"],                     # top-level  (metrics.py:1181)
    max_drawdown=scalars["max_drawdown"],         # top-level  (metrics.py:1184)
    ytd=scalars["metrics_json"]["ytd"],           # NESTED — see FLAG A
)
```

**FLAG A (depth gotcha — load-bearing):** the four source keys are NOT at a uniform depth on
`result.metrics_json`. `cumulative_return`, `sharpe`, `max_drawdown` are **top-level** keys of the
sanitized dict (`metrics.py:1177-1195`). But `ytd` is **nested one level deeper**, inside the inner
`metrics_json["metrics_json"]` sub-dict (`metrics.py:846` writes `metrics_json["ytd"]` into the inner
dict that becomes the `"metrics_json"` key at `:1189`). Accessing `scalars["ytd"]` at top level will
`KeyError`. The map must read `scalars["metrics_json"]["ytd"]`. Planner: confirm at plan time by grepping
the emitted dict; do not assume flat.

**FLAG B (do NOT wholesale-spread — D5):** map exactly these four keys. A `dict.update(result.metrics_json)`
spread pushes ~50 keys through the public H-04 sanitizer (`src/app/api/verify-strategy/route.ts:264-278`)
to unauthenticated browsers — avoidable public-surface growth. The map is 4 keys, hard-listed.
`MetricsSnapshot.twr` maps from `cumulative_return` (twr and cumulative_return are the teaser's synonym —
the same convention `to_metrics_snapshot` uses: `twr=self.compute_twr()`).
