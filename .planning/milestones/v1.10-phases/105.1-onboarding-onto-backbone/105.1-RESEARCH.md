## Summary

Collapse #4 ("unify onboarding — kill the scalar-without-series window") is **two arms wearing one
name**, and the research's first job is to separate them:

1. **The async onboard arm** (`services/ingestion/long_fetch.py`) — the in-wizard path. It writes
   `strategy_verifications.metrics_snapshot` (scalars) during onboarding, then **enqueues a proven
   tail job** (`sync_trades` → `compute_analytics`, or `derive_broker_dailies` for Deribit) that
   **already routes through `derive_basis_series` and persists a real MTM series + `strategy_analytics`**
   under the *real* `strategy_id` created at finalize (`long_fetch.py:474-489`). Its
   scalar-without-series window is **transient** and already closes via the backbone. This arm is
   *mostly done* — the residual is that `metrics_snapshot` is written before the series exists.

2. **The sync teaser arm** (`routers/process_key.py:854-948`) — the unauthenticated landing-page
   "probe your keys" preview. It computes scalars via `adapter.compute_metrics` + an ad-hoc
   `trades_to_daily_returns(account_balance=None)` heuristic-capital pass (`:896-898`), writes them
   to `strategy_verifications.metrics_snapshot`, and **never persists any daily series, ever**. It
   runs against a **shared sentinel anchor strategy** (`TEASER_ANCHOR_STRATEGY_ID =
   00000000-0000-0000-0000-000000000001`, `status='archived'`, owned by a system pseudo-user). **This
   is the real unsolved arm.**

The carve rationale in 105-CONTEXT §D2 ("teaser may have NO strategy_id") is **slightly imprecise vs
the code**: the teaser *always* has a `strategy_id` — but it is a **shared, non-unique, archived
sentinel**, which is *worse* than "missing" for reuse of `persist_basis_series`'s `(strategy_id, kind)`
primary key: every concurrent teaser submission would collide on the single
`(00000…0001, mtm_daily_returns)` row, and because the anchor is `status='archived'` and owned by no
real user, any persisted row is **unreadable** through the visibility-gated `fetch_strategy_lazy_metrics`
RPC anyway. So "reuse the shared persist as-is" is a non-starter for a positive reason, not just the
key-shape reason.

**The decisive framing question (Q2/Q5):** the teaser is an **explicitly-throwaway preview** whose
numbers are *already allowed to differ* from the eventual factsheet (it uses heuristic capital that the
code itself documents as degrading "5–10× on volatile strategies", `:884`; the finalize path uses real
capital/`denominator_config`). There is **no SC-4 byte-identity gate on the teaser** — it is
pre-strategy, pre-publish, `trust_tier='self_reported'`, 90-day-expiring. So "route through the
backbone" here means **structural unification** (compute dailies first via `derive_basis_series`, derive
the preview scalars *from* that series), **not numeric parity** and **not necessarily persistence**.

**Primary recommendation:** Option (c) — **compute-through-`derive_basis_series` at teaser, persist no
series row** — as the spine, with the `metrics_snapshot` scalars becoming a cache of the derived
series *within the same call*. This closes the "bypasses the backbone" invariant violation with **zero
DDL, zero new SECDEF, zero RLS surface**, and leaves the `metrics_snapshot` delete-tail cleanly to 106.
The discuss-phase should pressure-test whether the invariant demands a *persisted* series (pushing
toward Option a/b + DDL) or whether *derived-from-a-computed-series* satisfies it.

## Research Questions — Answered with Evidence

### Q1. Map the teaser arm end-to-end. What does it compute/persist? When does `strategy_id` exist? Handoff to finalize? Is `metrics_snapshot` read?

**The teaser sync pipeline** (`process_key.py:789-1026`), entered when `flow_type='teaser'` (also
`csv`/`internal_report`). For `teaser` specifically:

- **`strategy_id` is forced to the shared anchor unconditionally** at `:479-480`:
  `body.context["strategy_id"] = TEASER_ANCHOR_STRATEGY_ID`. This is a **security override** (the
  comment at `:460-470` explains it closes an attacker-supplied-`strategy_id` hole by making teaser
  anchor-less by definition). So the teaser **always has a `strategy_id`, but it is the single shared
  sentinel `00000000-0000-0000-0000-000000000001`** (`teaser_anchor.py:13`), provisioned by migration
  `20260515095804_teaser_anchor_strategy.sql` as `status='archived'`, owned by an all-zeros system
  pseudo-user.
- **What it computes** (`:863-948`): `adapter.fetch_raw` → `adapter.compute_metrics(trades)` →
  `metrics_snapshot = _metrics_to_jsonb(metrics)`, then an **enrichment block** (`:890-939`) that runs
  `trades_to_daily_returns(trades_as_dicts, account_balance=None)` (`:896-898`), `compute_period_returns`,
  builds a **cumulative** `equity_curve` (`(1+returns).cumprod()`, `:901-905` — a `{date,value}` array,
  *not* daily returns and *not* the persisted-series shape), and `find_matched_strategy`. All of this
  is folded into `enriched_metrics_snapshot`.
- **What it persists** (`:941-948`): a single `transition_strategy_verification` RPC to status
  `metrics_captured` with `p_metadata={"metrics_snapshot": enriched_metrics_snapshot}`. It then walks
  the SV state machine to `published` (`:991-998`). It **touches neither `strategy_analytics` nor
  `strategy_analytics_series` nor `derive_basis_series`** — confirmed: `process_key.py` and
  `long_fetch.py` never import `basis_series` (grep: NONE).
- **The landing-page (unauthenticated) entry** additionally has a *TS-side* twin at
  `src/app/api/verify-strategy/route.ts:434-448`, which upserts the SV row directly with
  `strategy_id: TEASER_ANCHOR_STRATEGY_ID`, `trust_tier: 'self_reported'`, `status: 'published'`,
  `public_token`, `expires_at = now+24h`, `metrics_snapshot`. This is the **kill-switch-OFF / legacy**
  path; `process_key.py` is the flag-ON unified path (`route.ts:417-420`). **Both write the same
  `metrics_snapshot` shape** — 105.1 must account for both, or scope to the Python arm and leave the TS
  twin to 106's repoint.
- **Handoff / when the real derive happens:** for the **in-wizard onboard** (not teaser),
  `long_fetch.py:474-489` documents it exactly: the handler advances the SV machine + captures
  `metrics_snapshot` but **does NOT write `strategy_analytics`**; it then **enqueues the tail job**
  (`sync_trades` for fill sources, `derive_broker_dailies` for Deribit) which "persists the return
  series and auto-chains to the analytics compute, which writes `strategy_analytics`" — i.e. **through
  `derive_basis_series`** (the single-key broker derive at `job_worker.py:~3112` per
  `basis_series.py:60-67`). The wizard's `SyncPreviewStep` polls `computation_status='complete'`. **The
  teaser has no such tail job** — it terminates at `published` with only `metrics_snapshot`.
- **Who reads `metrics_snapshot`** (shape = **scalar bundle** + cumulative `equity_curve` array, NOT a
  daily-return series):
  1. **Landing card** — `verify-strategy` returns `results` (= `metrics_snapshot`), consumed by
     `src/components/landing/VerificationSection.tsx:24-29,83-86` (`return_24h`, `equity_curve`,
     `matched_strategy_id`).
  2. **90-day public teaser status route** — `src/app/api/verify-strategy/[id]/status/route.ts:44-62`
     selects `metrics_snapshot` and returns it as `results` (gated on `public_token` + status).
  3. It is the **only home** for `matched_strategy_id` / `return_24h` / `equity_curve`
     (BACKBONE-BYPASS-INVENTORY:52). These are the 3 repoints 106 must land before the store is retired.

### Q2. The capital-basis question (SC-4-like). Must the teaser scalar MATCH finalize, or is it throwaway?

**It is explicitly throwaway; numbers are already allowed to differ — and do.**

- The teaser computes on `trades_to_daily_returns(account_balance=None)` = **heuristic capital**. The
  code documents this at `:880-887`: "`account_balance` is None here… falls back to the heuristic-capital
  path… (degrades 5–10× on volatile strategies)." The finalize/tail path uses **real
  capital/`denominator_config`** (collapse #6, `job_worker.py:2149`). So the teaser preview scalar and
  the eventual factsheet scalar are **already numerically different by design**.
- The teaser SV row is `trust_tier='self_reported'` (`route.ts:442`), `public_token`-gated, 24h/90-day
  expiring — a preview, not a published factsheet.
- **There is no SC-4 byte-identity gate on onboarding.** SC-4 (105) protects *existing cash factsheets*
  (single-key CSV/broker, published composite) — all *post-strategy, post-publish*. The teaser is
  *pre-strategy, pre-publish*: **nothing to preserve byte-for-byte.**

**Consequence for scope:** "route through the backbone" for the teaser means **structural unification**
(compute the daily series first, derive the preview scalars from it via the shared helper) — **not**
reproducing the finalize scalar byte-for-byte, and **not** the `scalar_returns`/`densify_policy`
byte-identity machinery 105 needed for cash. The teaser can pass `scalar_returns=None` (default
`gap_fill(sparse)`) and accept whatever derive produces; the numbers may shift slightly vs today's
ad-hoc `compute_metrics`, and **that is acceptable** because the teaser was never a byte-identity
surface. (Discuss-phase should still confirm the landing card tolerates a small shift — see Open
Decisions.)

### Q3. Persistence-design options vs the `(strategy_id, kind)` key problem.

Ground truth on the persist target (`migration 20260428120919` + `basis_series.py:275-337`):
`strategy_analytics_series` — **PK `(strategy_id, kind)`**, **FK `strategy_id → strategies(id) ON DELETE
CASCADE`**, **RLS deny-all**, written **only** via the service-role-only SECDEF
`upsert_strategy_analytics_series_batch`, read only via the visibility-gated SECDEF
`fetch_strategy_lazy_metrics` (requires `status='published' OR user_id=auth.uid()`). The teaser anchor
is `status='archived'` and user-less → **any row persisted under it is unreadable by design.**

| Option | Shape | DDL? | New SECDEF? | Preserves no-scalar-without-series? | Fits existing RPC? | Verdict |
|--------|-------|------|-------------|-------------------------------------|--------------------|---------|
| **(a) Verification-scoped persistence** — new key/table keyed on `verification_id` | New table `strategy_verification_series(verification_id, kind, payload)` OR a new nullable `verification_id` axis | **YES (new table or column + index + RLS + SECDEF)** | **YES** (write RPC; likely a gated read RPC too) | Yes — a real persisted series per verification | **No** — `upsert_strategy_analytics_series_batch` is keyed on `strategy_id` | **Heaviest.** Full prod-DDL + hardening + migration-reviewer + rls-policy-auditor + test-project catch-up. Buys a *persisted* teaser series that today has **no reader** (readers key on `strategy_id`/publish-visibility). Speculative. |
| **(b) Defer series-persist to finalize** — compute dailies at teaser for preview only; persist the authoritative series only once a real `strategy_id` exists (already true for the onboard arm via the tail job) | No teaser persist; rely on finalize's existing backbone persist | **No** | No | Yes for onboard (already). For **teaser specifically there is no finalize** (it terminates at `published` with no strategy) → the teaser window stays open unless combined with (c) | Yes (finalize already uses it) | **Correct for the onboard arm** (it *already is* this). **Insufficient alone for the teaser** — the teaser never reaches a finalize, so nothing ever persists. Must pair with (c) for teaser. |
| **(c) Compute-only, no persist at teaser + authoritative re-derive at finalize** — route the teaser *compute* through `derive_basis_series` (dailies first → scalars derived from that series), persist **no** series row; the `metrics_snapshot` scalars become a cache of the just-computed series | Teaser calls `derive_basis_series(returns, …)` and reads `result.metrics_json`; discards `series_rows` (or keeps in-memory only) | **No** | No | **Structurally yes** — no scalar is produced except as a derivation of a computed daily series; "nothing bypasses the backbone" holds *within the call*. Does **not** persist a series row (none is needed — no reader) | Uses `derive_basis_series` (not the persist half) | **Lightest, zero-DDL, zero-RLS.** Closes the *bypass* (teaser no longer computes scalars via a second path). Leaves `metrics_snapshot` store + its repoints cleanly to 106. **Recommended spine.** Open question: does the invariant demand a *persisted* series or only a *derived-from-series* scalar? |
| **(d) Reuse the anchor `strategy_id` for a shared teaser row** | `persist_basis_series(TEASER_ANCHOR_STRATEGY_ID, kind='teaser_preview')` | No (kind is free TEXT) | No | Superficially — but **all teaser users collide on one row** (last-writer-wins), and the row is **unreadable** (`status='archived'`, user-less) via the fetch RPC | Yes | **Rejected.** Concurrent-teaser collision on `(00000…0001, kind)` + unreadable-by-construction. A persisted series no one can read and everyone overwrites is worse than none. |

**Key structural fact:** the "backbone invariant" as implemented (`basis_series.py:9-14`) is *"scalars
are a cache of the rows, derived from the one series"* — it does **not** independently mandate that the
rows be **persisted to `strategy_analytics_series`** for every compute. For MTM/composite the rows *are*
persisted because there is a reader (the factsheet). For the teaser there is **no series reader** — the
landing card reads scalars + a cumulative equity curve, not a daily-return series. So Option (c)
satisfies the invariant's intent (no independent scalar path) without persistence. The discuss-phase's
core call is whether SC1's "no scalar-without-series *window*" is read as (c)-satisfiable or demands
(a).

### Q4. The `metrics_snapshot` legacy delete-tail — 105.1-vs-106 boundary.

**Confirmed deferred to 106.** What still writes/reads `metrics_snapshot`:

- **Writes (Python):** `process_key.py:941-948` (teaser sync), `long_fetch.py:396` (onboard async).
- **Writes (TS):** `verify-strategy/route.ts:434-448` (kill-switch-OFF legacy teaser).
- **Reads (TS):** landing card (`VerificationSection.tsx`), 90-day public status route
  (`verify-strategy/[id]/status/route.ts:44-62`), and it is the **sole home** for
  `matched_strategy_id` / `return_24h` / `equity_curve` (BYPASS-INVENTORY:52 — a ZOMBIE-RISK store).

**Boundary recommendation:** **105.1 = unify the *compute*** (teaser scalars derived via the shared
route). **106 = retire the *store*** and its 3 repoints (landing card, 90-day teaser,
`matched_strategy_id`/`return_24h`/`equity_curve` new home). Do **not** delete `metrics_snapshot` in
105.1 — the 3 repoints are frontend + public-URL surface changes that belong with 106's cutover, and
the store still backs live public teaser URLs (up to 90 days out). 105.1 keeps writing
`metrics_snapshot` (now sourced from the derived series) so nothing user-visible changes.

### Q5. Blast radius + SC-4.

- **No existing factsheet at risk.** The teaser is pre-strategy/pre-publish; it produces a preview card
  + a public teaser URL, not a factsheet. The published/single-key/composite factsheets (the SC-4
  surfaces) are downstream of finalize and untouched by the teaser compute.
- **No byte-identity gate here.** There is nothing to preserve byte-for-byte; today's teaser numbers
  are already heuristic-capital approximations that differ from the eventual factsheet. The only
  regression risk is a *visible* preview-number shift on the landing card / public teaser if we swap the
  ad-hoc `compute_metrics` for `derive_basis_series`-derived scalars. That shift is bounded (both feed
  `compute_all_metrics`; the difference is the conditioning of the input series) and is **not** an SC-4
  violation — but the discuss-phase should decide whether a golden-snapshot advisory on the teaser
  scalars is worth adding to catch *unintended* large shifts.
- **Concurrency safety** improves under (c): no shared-anchor row is written, so no cross-teaser
  last-writer-wins hazard is introduced.

## Common Pitfalls

### Pitfall 1: Treating "no `strategy_id`" as the blocker (it's the *shared archived* anchor)
**What goes wrong:** designing a "create a scratch strategy_id" or "handle the null strategy_id" fix.
**Reality:** `strategy_id` is always present but is the shared `00000…0001` sentinel (`:479-480`).
**Avoid:** design around "this id is shared + archived + unreadable," not "this id is missing."

### Pitfall 2: Persisting a teaser series that no reader can read
**What goes wrong:** Option (a)/(d) ships a table/row, but `fetch_strategy_lazy_metrics` requires
`published OR owner` — the archived anchor fails both, and a `verification_id` table has no wired reader.
**Avoid:** don't persist unless a concrete reader is defined in-scope. The landing card reads scalars,
not a daily series.

### Pitfall 3: Conflating the async onboard arm with the teaser arm
**What goes wrong:** re-plumbing `long_fetch.py` when its window already closes via the tail job
(`:474-489`).
**Avoid:** scope 105.1 to the sync teaser arm; treat the onboard arm as already-on-backbone (verify the
tail job's `derive_basis_series` persist, don't rebuild it).

### Pitfall 4: Assuming the teaser needs SC-4 byte-identity
**What goes wrong:** importing 105's `scalar_returns`/`densify_policy`/`nan_dates` byte-identity
machinery into a surface that has no factsheet to preserve — over-engineering.
**Avoid:** teaser passes `scalar_returns=None`; accept the derive's default scalar. Only add a golden
*advisory* if the discuss-phase wants a shift-detector.

### Pitfall 5: Forgetting the TS flag-OFF teaser twin
**What goes wrong:** unifying only `process_key.py` and leaving `verify-strategy/route.ts:434-448`
computing scalars the old way when the kill-switch is OFF.
**Avoid:** decide explicitly whether 105.1 covers only the flag-ON Python arm (with the TS twin's
repoint deferred to 106) or both.

## Open Questions / Decisions for the Fable discuss-phase to pressure-test

1. **Does SC1 ("no scalar-without-series window") require a *persisted* series, or is a scalar *derived
   from a computed series within the same call* (Option c) sufficient?** This is the load-bearing
   decision. (c) is zero-DDL and closes the bypass; (a) persists a series with no current reader at full
   DDL/RLS/SECDEF cost. Recommendation leans (c); the invariant's author (user, "nothing bypasses the
   backbone") should confirm whether "bypass" means the *compute path* (satisfied by c) or *durable
   evidence* (forces a).
2. **Scope: Python flag-ON arm only, or also the TS flag-OFF teaser twin (`verify-strategy/route.ts`)?**
   If 106 is going to repoint/retire `metrics_snapshot` anyway, is it cleaner to leave the TS twin alone
   until then, or unify both now to avoid a mixed state?
3. **Do we add a golden *advisory* snapshot on teaser scalars** to catch unintended shifts from the
   compute swap, given there is no SC-4 gate? (Cheap insurance vs. noise on an intentionally-approximate
   preview.)

## Recommendation

**Adopt Option (c) as the spine, scoped to the sync teaser arm:**

- Route the teaser's return computation through `derive_basis_series(returns, benchmark_rets=None,
  periods_per_year=…, cumulative_method=…, day_basis=…)` and source the `metrics_snapshot` scalars from
  `result.metrics_json` (+ keep the existing `period_returns`/`equity_curve`/`matched_strategy_id`
  enrichment, which are landing-card-specific and not part of the backbone). Pass `scalar_returns=None`
  — no byte-identity requirement.
- **Persist no new series row.** The invariant holds structurally (scalars are a cache of the just-
  derived series); there is no reader for a persisted teaser series.
- **Treat the async onboard arm as already on-backbone** — verify (A1) rather than rebuild.
- **Zero DDL, zero new SECDEF, zero RLS surface** → no migration-reviewer / rls-policy-auditor /
  test-project-catch-up burden, honoring the LOCKED "NO DDL in 105.1" preference.
- **Leave `metrics_snapshot` writing in place** (now derived), deferring the store's retirement + 3
  repoints to Phase 106.

**Fallback if the discuss-phase rules SC1 requires a persisted series (A2 resolves toward "durable"):**
Option (a) verification-scoped table — but this **forces prod DDL** (new table + index + RLS deny-all +
a hardened service-role write SECDEF + a visibility-gated read SECDEF) with migration-reviewer +
rls-policy-auditor + test-project MCP catch-up, and ships a table with **no in-scope reader**. Prefer to
push any such persistence into 106's fold migration (which already carries DDL + catch-up) rather than
make 105.1 prod-DDL-affecting.
