## Medium

### MD-01: Third silent source-of-truth for "which venues are crypto" — annualization drift risk

**File:** `analytics-service/routers/process_key.py:295` &nbsp;↔&nbsp; `analytics-service/services/job_worker.py:3291`
**Issue:** This diff introduces `_CRYPTO_VENUES = frozenset({"okx","binance","bybit","deribit"})`
to pick the √365 vs √252 clock for the sync preview. `job_worker.py:3291` already
owns `_COMPOSITE_CRYPTO_VENUES = frozenset({"deribit","binance","okx","bybit"})`
for the *same* semantic decision (composite blend annualization, #597). The two sets
are byte-identical **today** but are independent literals with no shared anchor. The
in-file comment instructs a maintainer admitting a new sync venue to "grep the H-11
whitelist above" — it does **not** point at the `job_worker` set. The failure mode is
silent and cross-surface: admit a new crypto venue (say `hyperliquid`) to
`_CRYPTO_VENUES` only, and the onboarding **preview** annualizes it √365 while the
**composite** blend still treats it √252 (or vice-versa) — the exact "second
derivation diverges" class the v1.10 backbone-unification program exists to kill,
re-introduced one layer up. `job_worker` even documents that it derives
`_COMPOSITE_DEGRADE_VENUES` from `_COMPOSITE_CRYPTO_VENUES` precisely "so the two sets
can never drift" — that discipline is broken the moment a third set exists.
**Fix:** Hoist a single canonical crypto-venue set (e.g. `CRYPTO_VENUES` in
`services/metrics.py` next to `periods_per_year_for_asset_class`, the module both
callers already import) and have both `process_key._CRYPTO_VENUES` and
`job_worker._COMPOSITE_CRYPTO_VENUES` reference it:
```python
# services/metrics.py
CRYPTO_VENUES: frozenset[str] = frozenset({"okx", "binance", "bybit", "deribit"})
# routers/process_key.py
from services.metrics import CRYPTO_VENUES as _CRYPTO_VENUES
```
If a shared constant is out of scope for this slice, at minimum add a cross-reference
comment on each set naming the other and a test asserting `_CRYPTO_VENUES ==
_COMPOSITE_CRYPTO_VENUES` so drift reddens CI.

## Low

### LW-01: Generic `except` (and the post-`four_keys` success window) leaves the 5 legacy landing keys ABSENT, not nulled — inconsistent with the two degrade arms

**File:** `analytics-service/routers/process_key.py:1067-1101`
**Issue:** The `len<2` arm (`:1088`) and the derive-`ValueError` arm (`:1064`) both
apply `_LEGACY_NULL_ENRICHMENT`, so the landing card renders explicit dashes. The
outer `except Exception` (`:1092`) does **not**. Because the swap now writes
`four_keys` **first** and *then* runs `compute_period_returns` + `find_matched_strategy`
(`:1069-1081`), a transient DB error in `find_matched_strategy` (a live SELECT) now
persists a **new partial shape**: derived `twr/sharpe/ytd/max_drawdown` present, but
`return_24h/return_mtd/return_ytd/equity_curve/matched_strategy_id` **absent** (never
set). The public card would show scalar values with no supporting curve, and — unlike
the degrade arms — the keys are omitted rather than dashed. The four scalar keys
staying `None` is correctly protected by the pre-null, so no *wrong* number is shown;
this is a shape-consistency defect, and the failure window is genuinely reachable
(any transient failure of the matching SELECT). Pre-swap the whole legacy block was a
single trailing `.update()`, so this "scalars-present, curve-absent" state is new.
**Fix:** Null the legacy keys in the outer handler so all failure shapes converge:
```python
except Exception as exc:  # noqa: BLE001
    enriched_metrics_snapshot.update(_LEGACY_NULL_ENRICHMENT)
    log.warning("process_key.enrichment_failed", error=str(exc)[:200],
                verification_id=verification_id)
```
(The four scalar keys are already pre-nulled, so this only harmonizes the 5 legacy keys.)

### LW-02: Direct `scalars[...]` indexing in `_derive_return_scalars` is brittle to a metrics.py shape change and escapes the specific degrade arm

**File:** `analytics-service/routers/process_key.py:400-408`
**Issue:** `_derive_return_scalars` reads `scalars["cumulative_return"]`,
`scalars["sharpe"]`, `scalars["metrics_json"]["ytd"]`, `scalars["max_drawdown"]` with
bare `[]`. The caller's degrade contract only catches `ValueError` (`:1053`). If
`metrics.py` ever renames/flattens any of those keys (the nested-`ytd` at
`metrics.py:846` is exactly the kind of thing that moves — the code comments admit it
is a FLAG), a `KeyError` propagates past the `except ValueError` arm into the generic
`except Exception`, which logs the *less-specific* `enrichment_failed` (not
`derive_return_scalars_degraded`) and — per LW-01 — leaves the legacy keys absent. No
wrong number results (pre-null holds), but the failure is harder to triage than the
purpose-built degrade path. The `test_derive_return_scalars_reads_nested_ytd` pin
does guard the current shape, so this is robustness, not a live bug.
**Fix:** Either broaden the caller to `except (ValueError, KeyError)`, or have the
helper convert a missing key into the same `ValueError` degrade signal, e.g.
`try: four_keys = {...} except KeyError as e: raise ValueError(f"derive metrics_json
missing key {e}") from e`.

### LW-03: No end-to-end route test for the traditional / √252 path

**File:** `analytics-service/tests/test_process_key.py:150-441`
**Issue:** Every *route-level* derive test drives a crypto venue (`okx`/`binance` →
√365). `test_resolve_asset_class_venue_and_csv` unit-checks that `csv` resolves to
`"traditional"`, and the golden checks the √365-vs-√252 *ratio* in isolation, but no
test drives a `source="csv"` / traditional strategy **through the pipeline** and
asserts the persisted `sharpe` equals the √252 derive. A regression that hard-wired
`periods_per_year=365` at the `_derive_return_scalars` call site would pass the entire
suite. Given this is the annualization seam (#597), the traditional clock deserves a
route-level pin symmetric to `test_teaser_derive_crypto_uses_365_not_252`.
**Fix:** Add a `flow_type="csv"`, `source="csv"` run with a mocked
`strategies.asset_class="traditional"` and assert the captured `sharpe` == the
`periods_per_year=252` derive and `!=` the 365 derive.

### LW-04: Advisory golden's absolute-Sharpe assertion is coupled to quantstats' internal convention

**File:** `analytics-service/tests/test_teaser_derive_golden.py:79-84`
**Issue:** `test_teaser_derive_golden_crypto_365` pins `four["sharpe"] ==
approx(oracle["sharpe"], rel=1e-6)` where the paper oracle hard-codes
`mean/std(ddof=1)×√N, rf=0`. That equals quantstats' *current* `qs.stats.sharpe`
only by convention; a future quantstats upgrade that changes the estimator (or a
periods/rf default) reddens this golden with **no** Quantalyze regression, and the
1e-6 band leaves no room. The companion `test_teaser_derive_golden_365_not_252`
`sharpe == sharpe_252 * √365/√252` (rel=1e-9) is convention-independent and robust —
the fragility is confined to the absolute pin. This is acceptable under the file's
REGEN CONTRACT, but a reviewer re-running after a `requirements.txt` qs bump should
know a red here may be a *library* drift, not a backbone drift.
**Fix:** Optional — keep the absolute pin (it is the shift-detector's point) but add
a comment naming the qs version the oracle was reconciled against, so a future qs bump
is triaged as library drift rather than a backbone regression.

## Cleared (checked per brief — NOT defects)

- **`_LEGACY_NULL_ENRICHMENT` shared-mutable-default (`:303`):** SAFE. Module-level
  dict consumed only via `enriched_metrics_snapshot.update(...)` (which *copies*
  key/values), never aliased, never mutated; all values are immutable `None`. No
  cross-request bleed. Verified no other reader/writer (`grep`).
- **Pre-null ordering vs every write path (`:1027`):** CORRECT. `{"twr":None,
  "sharpe":None,"ytd":None,"max_drawdown":None}` is applied before the `try`; success
  overrides with backbone values, all three failure arms leave them `None`. D1 (no
  off-backbone builder scalar can persist) holds on every path. This is the crux of
  the phase and it is sound.
- **Exception-scope variable leak (`as exc`):** none — Python 3 auto-`del`s the bound
  name at block exit.
- **4-key map vs `MetricsSnapshot` field names:** match (`twr/sharpe/ytd/max_drawdown`);
  the nested `scalars["metrics_json"]["ytd"]` read matches `metrics.py:846`; top-level
  `cumulative_return/sharpe/max_drawdown` match `metrics.py:1178-1189`. Confirmed by
  the passing wiring test's independent re-derive.
- **Public-surface growth / PII:** none. Only 4 scalar keys + a locally-built
  `equity_curve` are pulled from the derive result; `scalars` is a discarded local —
  no wholesale spread of the ~40-key `metrics_json` into the unauthenticated response,
  no new fields, no new exposure. `_resolve_asset_class` reads *only* `asset_class` and
  echoes nothing to the caller; the teaser (public) path never reaches the DB read
  (crypto branch returns before any query), so no unauthenticated enumeration vector.
- **Injection / authz:** `strategy_id` flows through parameterized `.eq("id", ...)`;
  no string interpolation, `eval`, or path handling introduced. Compute-only —
  `persist_basis_series` is never called (proven by `test_teaser_persists_no_series_row`).
- **`TYPE_CHECKING`/`"pd.Series"` forward-ref:** correct — no runtime import cost, no
  `NameError`.
- **Equity-curve ↔ `twr` coherence:** the sparse-rows cumprod endpoint equals
  `1+cumulative_return` because densified gap days are the multiplicative identity
  (`gap_fill` 0.0). Coherent by construction, as claimed.
