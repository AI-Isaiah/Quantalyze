<objective>
Add the per-key (allocator_id) axis to the GDPR export manifest so Art.15/20 bundles include an allocator's per-key `csv_daily_returns` rows (D4). This is the load-bearing compliance fix and MUST land in the same phase as the repoint, BEFORE the post-deploy backfill (D6) populates per-key rows — otherwise the bundle silently omits them.

Why it is silently broken today: `csv_daily_returns` is in `USER_EXPORT_TABLES` only as an INDIRECT entry (`strategy_id → strategies.user_id`). Per-key rows have `strategy_id NULL` + `allocator_id` set, so the indirect sub-select (`strategy_id IN (...)`) never matches them. The CI coverage hook stays GREEN regardless because the table NAME is present — so this is a correctness/compliance gap the hook cannot catch, not a CI failure. The fix is additive (a second axis); the existing indirect strategy entry stays untouched.

Purpose: per-key dailies become exportable before any exist; the two-axis ownership is pinned by a unit test.
Output: a `projected` manifest spec + allowlist entry + a new unit test; the coverage hook still exits 0.
</objective>
