<parity_contract_clarification>
CRITICAL — read before writing the runtime assertion. CONTEXT's shorthand says "the
factsheet payload's headline metrics equal computeScenario's ComputedMetrics on the
identical series." That shorthand is IMPRECISE and MUST NOT be implemented literally,
because the two compute paths use DIFFERENT numerical conventions (verified in source):

  - `computeScenario` (src/lib/scenario.ts:497-527): SAMPLE stdev (÷ n−1),
    CAGR uses a 252-TRADING-DAY year (`years = n / 252`), Sortino ÷ n.
  - `compute.ts` (src/lib/factsheet/compute.ts:15-41): POPULATION stdev (÷ n),
    CAGR uses a 365.25-CALENDAR-day year (`years = days / 365.25`).

So `computeScenario.ComputedMetrics.volatility/sharpe/cagr` do NOT equal the factsheet
`strategyMetrics.ann_vol/sharpe/cagr` field-for-field, by design. Asserting that would be
a doomed, wrong test.

The LOCKED parity invariant (ADR-001 § "Parity with compute.ts (v1.2.2)", line ~100-101,
and the payload-builder header comment) is **single-source-of-truth of the SERIES**: the
factsheet is computed on THE SAME blended series `computeScenario` emits, via the SAME
`compute()` the real strategy factsheet runs. "The change is to how the series is built,
not the metric formulas, so parity holds iff the factsheet path consumes computeScenario's
output rather than re-deriving the blend."

Therefore the runtime parity assertion (Task 2) proves: the factsheet payload's
returns-derived body (metrics + equity + drawdowns) equals
`compute(rets, dates)` / `cumEq(rets)` / `drawdowns(cumEq(rets))` applied to THE IDENTICAL
member-windowed `portfolio_daily_returns` the engine emits on the present-`window` path.
This is exactly what the existing Phase 39 union-path spec asserts (`strategyMetrics equals
compute(rets,dates) field-by-field`), extended to the coverage-window path where `rets`
comes from a windowed `computeScenario` run. (CLAUDE.md Rule 7: conflict surfaced, more-
tested/more-correct pattern chosen.)
</parity_contract_clarification>
