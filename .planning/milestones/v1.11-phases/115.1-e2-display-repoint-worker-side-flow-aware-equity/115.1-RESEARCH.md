## Summary

All six research questions resolve with codebase evidence. The worker machinery 115.1 needs **already exists and is proven**: key-mode `run_derive_broker_dailies_job` decrypts allocator keys worker-side, crawls real deposits/withdrawals into the exact `ExternalFlow` list the P115 core consumes, fetches the terminal equity anchor, and writes per-key `csv_daily_returns` (pinned mutation-falsifiably in P115 plan-04). 115.1 is therefore a **composition problem, not a crawl-invention problem**: get per-key returns + flows + anchors to one allocator-scoped compose step, run the frozen core, persist to a new surface, and read that surface in `getMyAllocationDashboard`.

The recommended architecture: **a new table `allocator_equity_derived` (one row per `(allocator_id, kind)`, JSONB payload — the exact `strategy_analytics_series` precedent)** written by a **new allocator-scoped compute-job kind `derive_allocator_equity`**, enqueued as an epilogue of each key-mode derive (dedup-safe via the existing one-inflight index pattern) plus a new daily pg_cron key-mode fan-out that simultaneously closes the P115-flagged recurring-enqueue gap. The frontend repoint swaps the producer of `equityDailyPoints` at ONE site (`queries.ts:2409`) — but research found the repoint is NOT purely chart-only as scoped: `equityDailyPoints` also feeds the V2 Overview factsheet metrics via `buildAllocatorPortfolioFactsheetPayload` and the ScenarioComposer baseline, and **prod allocator keys currently have ZERO per-key `csv_daily_returns` rows** (A1 census) — a hard repoint without a fallback would blank every allocator's chart in prod. Both are flagged as residual founder/planner decisions with recommended dispositions.

**Primary recommendation:** new `(allocator_id, kind)` JSONB series table + new `derive_allocator_equity` compute-job kind (crawl-free compose that reuses the flows/anchor already fetched by the key-mode derive via a per-key persist epilogue), segment-wise blend wiring per §Q5 (dense per-key series make it exact), and a legacy-fallback repoint in `queries.ts` gated on the derived row's `is_trustworthy`.

### Options evaluated

| Option | Verdict | Why |
|--------|---------|-----|
| (a) **New table, one JSONB row per `(allocator_id, kind)`** | **RECOMMENDED** | Exact `strategy_analytics_series` precedent. Atomic replace-on-upsert (no per-day delete-reconcile, no partial-curve read race — the legacy store needed a `replace_allocator_equity_snapshots` SECDEF fn to fix exactly that, equity_reconstruction.py:1500-1541). | (a′) New table, one row per `(allocator_id, date)` | Rejected | Mirrors the legacy store's shape and its worst property: non-atomic multi-row replace (the two-writers/partial-read class P115 explicitly avoided). More rows, no benefit — the frontend consumes the whole curve at once. |
| (b) Keyed compute-job output (`compute_jobs.metadata`) | Rejected | `compute_jobs` is RLS deny-all service-role-only operational infra (20260411144407:242-247); rows are terminal-state queue entries, not a durable read surface; the SSR read would need a SECDEF helper into the queue table. Wrong layer. |
| (c) Materialized read/view keyed allocator+key | Rejected | The derivation needs worker-only decryption + exchange I/O (flows) — structurally impossible in SQL. A matview over persisted inputs would still need the inputs persisted first (= option a anyway) and adds refresh scheduling. |

### Recommended shape (planner fills exact DDL)

`allocator_equity_derived`:
- `allocator_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE`

- `payload JSONB NOT NULL` — `{ curve: [{date:'YYYY-MM-DD', equity_usd}], flags: {...}, degrade_reasons: [...], is_trustworthy: bool, scalars: {mwr, dietz, computable}, inputs: {n_keys, anchor_asof, ...} }` (no raw secrets; USD magnitudes in STORAGE are fine — the legacy store already stores USD; the T-115-05 no-USD rule is for logs/exceptions only, allocator_equity_derive.py:68-69)

## Q3 — Real-flow crawl reuse (reuse, don't re-invent — CONFIRMED)

Everything needed already exists inside the dual-mode `run_derive_broker_dailies_job` (job_worker.py:1869+), which **runs in key-mode for allocator keys today** (P115-04 proved the deribit key-mode path end-to-end):

- **Worker-side decryption for allocator keys:** `_allocator_key_preflight` (job_worker.py:736-830) loads the api_key row directly (no strategy hop), runs the circuit breaker, decrypts, creates the exchange. Multi-key precedent inside ONE job: `run_stitch_composite_job` iterates members and calls `_allocator_key_preflight` per member (job_worker.py:3971), with per-venue branches `_reconstruct_deribit` (:3609) / `_reconstruct_ccxt_member` (:3630).
- **ccxt venues (binance/okx/bybit) flow crawl:** `fetch_ccxt_transfers(exchange, "deposits"/"withdrawals", since, now)` bounded by the venue retention floor (`flow_retention_floor` — OKX 90d / Bybit 365d / Binance full), then the PURE valuer `ccxt_rows_to_dated_flows(rows, venue, price_index)` → `list[ExternalFlow]`; same-UTC-day price index via `_resolve_ccxt_flow_price_index` (job_worker.py:2582-2624, :1761). Fail-loud on unpriceable/schema-drifted flows (NavReconstructionError → permanent, scrubbed).
- **Deribit flow source:** the native ledger crawl inside `combine_native_ledger`; dated flows surfaced as `_completeness.dated_external_flows` (job_worker.py:2518) — already `ExternalFlow`-shaped.
- **The ONE ledger shape:** `services/external_flows.ExternalFlow(utc_day_iso: 'YYYY-MM-DD', usd_signed, currency='USD', quantity=None)` — deposit +, withdrawal −; unpacks positionally `(day, usd)` which is exactly what the core's `_flows_by_day` reads (allocator_equity_derive.py:630-649) `[VERIFIED: external_flows.py:45-75]`.
- **Terminal anchor at crawl time:** ccxt branch fetches `equity` via `fetch_account_equity_and_upnl_usd(exchange, venue)` (job_worker.py:2529-2532) = the key's current total equity (NAV incl. uPnL); deribit's native core reconstructs to the account's current state.

### How the worker assembles the ONE dated ledger for the core

Per allocator: `real_flows_by_key = {api_key_id: list[ExternalFlow]}` (one crawl per key), `returns_by_key = {api_key_id: pd.Series}` from `csv_daily_returns` per-key rows, `anchors = {api_key_id: float}`. Then, per the core's contract: `seg = segment_coverage(returns_by_key)` → `per_key_equity = {k: replay_key_equity(returns_by_key[k], real_flows_by_key[k], anchors[k])}` → `ledger = build_allocator_ledger(real_flows_by_key, seg.seams, per_key_equity, returns_by_key)` → `curve = allocator_equity_curve(per_key_equity, seams=seg.seams)` → `scalars = mwr_and_dietz_from_ledger(ledger, …)` (allocator_equity_derive.py:1004-1083, :790-951, :1192-1279).

### Avoid double-crawling — the compose-job input options

The key-mode derive **already crawls flows and fetches the anchor** on every run, then discards them (only `csv_daily_returns` is persisted; grep confirms no flow persistence anywhere). Two viable designs:

- **Option B (RECOMMENDED): persist per-key `{flows, anchor, anchor_asof}` from the key-mode derive epilogue** onto the new surface (e.g. `allocator_equity_derived (allocator_id, kind='key_inputs:'||api_key_id)` rows, or a sibling per-key kind), then `derive_allocator_equity` is a **crawl-free, decryption-free DB-only compose** (cheap, 5-min timeout class, trivially retryable, no added 429 exposure). Cost: a new stored per-key flow-USD surface (owner-RLS + GDPR-manifested — same sensitivity class as `allocator_equity_snapshots.value_usd`, already stored today).
- **Option A: the compose job re-crawls per key** (mirroring `run_stitch_composite_job`'s member machinery). Self-contained but doubles exchange I/O + rate-limit exposure per day, needs decryption + venue branching in a second handler (~the stitch job's member complexity), and a 20-30 min timeout + watchdog override.

Recommendation: **Option B** — it reuses work already done in the same daily cycle and keeps the new handler pure-compose. Surface the new flow store to the founder (Residual Decision RD-3).

### Anchor source for STITCH-04 (Q6 folded in — anchor availability CONFIRMED, with a trap)

- **Available paths:** (1) live `fetch_account_equity_and_upnl_usd` during the key-mode derive (same-session as the flow crawl — same-day-consistent with the series' last day); (2) persisted `allocator_holdings` per `api_key_id` (refreshed daily 04:00 UTC by `poll_allocator_positions` + first-connect `request_allocator_holdings_sync`, 20260420073003:692, 20260422101911:279-334). The P115 ground-truth harness uses (2): "the persisted per-key anchor is that key's terminal equity as persisted at the last sync (`allocator_holdings.value_usd`)" `[VERIFIED: scripts/e2_allocator_ground_truth.py:63-73]`.
- ⚠️ **Derivative-notional trap:** for a derivative holding, `value_usd` is NOTIONAL, not equity — the equity contribution is `unrealized_pnl_usd` (the NEW-C03-01 rule, queries.ts:2046-2056, and the holdingsSummary doc at :1666). Any worker-side anchor summed from `allocator_holdings` MUST mirror `holdingEquityContribution` (spot → `value_usd`; derivative → `unrealized_pnl_usd`), or a levered key's anchor inflates by the leverage factor. **Recommendation: use (1), the live equity read captured in the derive epilogue** — it is the venue's own total-equity number (no per-holding reassembly, no notional trap, no 04:00-vs-derive-time asof skew). The harness's tolerance band (±2% same-trading-day drift, e2_allocator_ground_truth.py:100-102) remains the acceptance check.
- `anchor=None` (a key with no persisted/live equity) is handled honestly by the core (`REASON_NO_ANCHOR` → key dropped → `DROPPED_KEY` blocking flag at the curve level) — no fabrication path exists.

**Confidence: HIGH** on mechanism; MEDIUM on Option B's exact persist shape (planner's discretion within the locked surface).

## Q5 — Segment-wise blend + exclusive-only EXCLUSIVE_FILL (carry-ins #1 + #4)

### The decisive simplifying fact (verified)

Per-key `csv_daily_returns` series are **DENSE calendar-daily**: the derive path reindexes to EVERY calendar day in `[first, last]`, 0-filling no-activity days `[VERIFIED: services/broker_dailies.py:124-137]`, and structural failures refuse loudly rather than emit gapped series (P115-04 fail-loud pin). Therefore a key can only be missing on a union day **outside its own [first, last] window** — genuine interior PRESENT-window holes do not occur on this input population. Consequence: `segment_coverage`'s coverage-set segments coincide with active-window segments, and per-Segment feeding is exact (no interior-gap semantic fork to resolve).

### The concrete wiring (implementation-ready)

Current state: `blend_concurrent_returns` receives the RAW union and 0-fills any missing key at CONSTANT full weight-mass; `exclusive_fill_days` counts ANY union day where any key lacks a row and sets BLOCKING `EXCLUSIVE_FILL` (allocator_equity_derive.py:308-353, F4 comment :325-339). For a normal multi-key allocator with different start dates this is ALWAYS nonzero → `is_trustworthy=False` forever (the never-green gate). The structural fix, in the 115.1 worker (do NOT edit the frozen core's blend internals):

1. `seg = segment_coverage(returns_by_key)` — computed ONCE (ISO-index asserted at its boundary, :446-449).
2. For each `Segment s` in `seg.segments`: slice `series_by_key_s = {k: returns_by_key[k].loc[list(s.days)] for k in s.keys}`; weights = the SAME static current-equity shares restricted to `s.keys` (the core renormalizes internally, :294-306 — this reproduces the TS ABSENT-window renorm, scenario.ts L407-409, which the module docstring identifies as the exact HIGH-1 divergence source, :26-49).
3. `blend_concurrent_returns(series_by_key_s, weights_s)` — within a segment every key covers every day by construction ⇒ `exclusive_fill_days == 0` ⇒ `EXCLUSIVE_FILL` can NEVER fire on correct wiring. It becomes a structural canary: if it fires, the wiring regressed — assert on it in tests.
4. Concatenate segment outputs in day order (seam gap-days stay ABSENT — no-invented-data, matching `Seam.gap_days` semantics :378-396); union the `degrade_reasons` across segments; a single-key segment flows through the sole-key passthrough (weight-1.0) which is exactly the honest sequential-leg semantic.
5. Trustworthiness for display = union of: per-segment blend reasons + per-key `KeyEquity.degrade_reasons` + `AllocatorEquity.degrade_reasons` (`_is_trustworthy` over the union, :122-135). NOTE: the $-curve itself (`allocator_equity_curve`) does not consume the blend — the blend output is what a future KPI/factsheet unification reads (see RD-1) and what the ground-truth gate's `is_trustworthy` verdict incorporates. If the plan gates display ONLY on curve+key reasons, F4 is still MANDATORY before any blend reason joins the gate (the CONTEXT lock).

Falsifiable pins the plan should demand: (i) two keys with offset windows → segment-wise blend has NO `EXCLUSIVE_FILL` and the late key's lead days blend over the covering set only; (ii) neutering the segment slice (feeding the raw union) reddens the pin; (iii) a rotation fixture's seam list is byte-identical between the ledger call and the curve call (carry-in #2).

**Confidence: HIGH** — the density fact removes the one semantic ambiguity; everything else is the core's documented contract.

## Carry-in #2 — Shared seam list: wiring points the planner must not miss

- Compute `seg = segment_coverage(...)` ONCE and pass `seg.seams` to BOTH `build_allocator_ledger(real_flows, seg.seams, per_key_equity, returns_by_key)` AND `allocator_equity_curve(per_key_equity, seams=seg.seams)` — the `seams=` param exists exactly for this (allocator_equity_derive.py:792,814-816).
- ⚠️ **Stray-key guard:** the curve's MEDIUM-6 guard RAISES if a passed seam references a key absent from the ANCHORED set (:857-878). Since `segment_coverage` runs over the RETURNS key-set but the curve runs over ANCHORED keys only (unanchored keys are dropped, :831-834), **drop unanchored keys BEFORE segmentation** (or re-segment over the anchored subset) so the shared list passes the guard. An anchored-set/returns-set mismatch is the one way carry-in #2 can throw at runtime.
- Pass `returns_by_key` to `build_allocator_ledger` — without it every seam is `known=False` → `LedgerScalars(computable=False)` (:1026-1029, :1229-1230).

## Carry-in #3 — ISO-string day-index: wiring points

- `csv_daily_returns.date` is a Postgres `DATE`; PostgREST returns `'YYYY-MM-DD'` strings — build `pd.Series(values, index=[row["date"] ...])` DIRECTLY from the string column. Never `pd.to_datetime` / `parse_dates` / `DatetimeIndex` anywhere on the path — the core hard-fails via `_assert_iso_day_index` (allocator_equity_derive.py:170-184) at `segment_coverage` (:446-449) and `replay_key_equity` (:698-699), and a DatetimeIndex that slipped through would stringify to `'YYYY-MM-DD 00:00:00'` and silently misalign flow vs return days.
- `ExternalFlow.utc_day_iso` is already the ISO string (external_flows.py:12-14) — no conversion.
- Anchor `asof`: `allocator_holdings.asof` is timestamptz — if the persisted-holdings anchor path is used anywhere, slice to `[:10]`/`.date().isoformat()` before comparing to series days.
- The persisted `payload.curve[].date` and the frontend `DailyPoint.date` are the same ISO string end-to-end — no `new Date()` re-parsing server-side (the chart's own `parseISO` handles display).

## Common Pitfalls

1. **Prod-blank repoint** — per-key rows are 0 for ALL allocator keys until the approval-gated backfill runs. Hard repoint = blank charts fleet-wide. Ship fallback-to-legacy gated on `is_trustworthy` (see Q2).
2. **Two-writers race** — any write/upsert to `allocator_equity_snapshots` from the new path. Grep-gate the diff (the P115 additive-only pattern).
3. **Notional-as-anchor** — summing `allocator_holdings.value_usd` for derivative rows inflates the anchor by leverage. Mirror `holdingEquityContribution` or use the live equity read (Q3/Q6).
4. **Seam-list stray-key raise** — segmenting over the returns key-set but passing seams to a curve over the anchored subset raises MEDIUM-6. Drop unanchored keys before segmentation.
5. **Headline return off the curve** — WR-02 pin: the perf/$-curves deliberately exclude day-0; `(1+backbone_cumret) == (1+r_0)×curve_terminal` EXACTLY (allocator_equity_derive.py:592-604, oracle-pinned). No 115.1 consumer may derive a headline cumulative return from the curve — relevant if RD-1 keeps the factsheet on curve-derived returns.
6. **Migration re-base** — the kind CHECKs must be re-based on 20260710130000 (which carries the api_key arm); copying an older def silently drops allocator derives (that migration's own header warns exactly this).
7. **Watchdog headroom** — any handler timeout > 10 min without a `WATCHDOG_PER_KIND_OVERRIDES` entry fails `test_every_kind_has_watchdog_headroom` (main_worker.py:123-131).
8. **CI Node-gap** — new vitest tests around queries/dashboard must pass under Node 22 (`PATH=/opt/homebrew/opt/node@22/bin` repro; leaked `vi.stubGlobal` class — memory `reference_ci_node22_vs_local_node25`).
9. **`.planning` discipline** — subagents Edit (not Write) existing ledgers; never `git add .planning` (memory).
