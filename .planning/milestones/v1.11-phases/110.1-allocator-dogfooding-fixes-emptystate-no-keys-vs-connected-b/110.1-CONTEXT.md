## Phase Boundary

Three self-contained allocator-surface honesty fixes surfaced during live founder
dogfooding (2026-07-16), captured in `.planning/DOGFOODING-FINDINGS-2026-07-16.md`.
All three are **copy / data-honesty** fixes — no engine, no reconstruction, no new
data path.

1. **EmptyState conflation** — the allocator "No positions to analyze yet" empty
   state tells a user with 5 connected+synced keys to "Connect a read-only exchange
   API key," because `EmptyState` only knows `hasSyncing`, not whether any key is
   connected.
2. **Balance↔holdings mislabel** — the Exchanges/connections surface presents a real
   `api_keys.account_balance_usdt` as an "Active Allocation auto-synced" when
   `allocator_holdings` is empty, implying an allocation the holdings/reconstruction
   can't back.
3. **Latent validate-and-encrypt mislabel** — the legacy validate handler returns the
   blanket "This key has trading or withdrawal permissions" whenever the validator
   reports `read_only:false`, which also fires when the Python probe fail-closes
   (`_FAIL_CLOSED` sets `trade=True` on ANY probe error), mislabeling an
   auth/probe failure as a permissions problem.

<decisions>
## Implementation Decisions

### Finding 1 — EmptyState no-keys vs connected-but-empty
- **Signal:** thread a `hasConnectedKeys` boolean into the payload and down to
  `EmptyState`. Derive it from the already-computed
  `activeKeys = apiKeys.filter(k => k.is_active)` in `getMyAllocationDashboard`
  (`src/lib/queries.ts:2348`) — `activeKeys.length > 0`. No new query.
- **Branching:** `EmptyState` gains a three-way copy:
  - `hasSyncing` → existing first-sync InfoBanner (unchanged).
  - `!hasSyncing && !hasConnectedKeys` → existing "Connect a read-only exchange API
    key…" Card + "Connect Exchange →" CTA (unchanged copy).
  - `!hasSyncing && hasConnectedKeys` → NEW honest state: your exchange is connected;
    we have no open positions to show yet (either none are open, or the position sync
    hasn't landed). Link to **Manage exchanges** (`/profile?tab=exchanges`), NOT a
    "Connect" CTA that reads as "you have no keys."
- **Copy is intent, not final polish** — planner picks the exact strings following
  DESIGN.md Numbers/Copy discipline; the locked semantic is: connected-but-empty must
  NOT tell the user to connect a key.
- Caller gate stays `holdingsEmpty && !hasSyncing` (`AllocationDashboardV2.tsx:82`);
  only the `EmptyState` props + copy branch change.

### Finding 2 — balance implies an allocation holdings can't back
- **No invented data.** Do NOT seed fake `allocator_holdings` for the demo allocator
  to match the balance (violates the project's no-invented-data principle). The
  `account_balance_usdt` is real per-key exchange data and may legitimately show while
  positions are still syncing or genuinely flat.
- **Fix the label, not the data:** the misleading element is the affirmative
  "Active Allocation auto-synced" (or equivalent) shown on the connections/Exchanges
  surface when `allocator_holdings` for that allocator is empty. When there are no
  holdings, that surface must not assert an active allocation — show the real balance
  with an honest state ("connected · no open positions yet" / "syncing"), consistent
  with Finding 1's empty-state copy.
- Planner to locate the exact "Active Allocation auto-synced" render site on the
  Exchanges/connections surface and gate the affirmative on holdings presence.

### Finding 3 — validate-and-encrypt honest error cause
- **Root-cause, not bandaid:** the blanket message at
  `src/app/api/keys/validate-and-encrypt/route.ts:123-127` must distinguish a genuine
  trade/withdrawal-permission rejection from an auth/probe fail-closed.
- **Approach (planner verifies the exact plumbing):** inspect `ValidateKeyResponseSchema`
  (`src/lib/analytics-client.ts:164`, `/api/validate-key`) and the Python
  `key_permissions.py` `_FAIL_CLOSED` path. Prefer surfacing the validator's actual
  cause (auth-failed / missing-scope / probe-error vs. real trade-permission) so the
  user sees why. If the schema does not currently carry a distinguishing
  `error_code`/`detail`, the honest minimum is to have the analytics fail-closed path
  set an `error`/reason the route can forward, rather than asserting "trading or
  withdrawal permissions" on an unknown-cause fail-closed.
- ZAV33's real case (deribit `invalid_credentials` → analytics 400 → route already
  forwards "Authentication failed…") is CORRECT and is not the bug; the bug is the
  fail-closed mislabel path.

### Regression tests (all three)
- Per stored feedback (regression-first): each fix gets a test that FAILS without it.
  - Finding 1: `EmptyState` renders connected-but-empty copy (no "Connect a … key")
    when `hasConnectedKeys` and not syncing; still renders connect CTA when no keys.
  - Finding 2: the connections/Exchanges affirmative is suppressed when holdings empty.
  - Finding 3: a fail-closed / auth-probe error does NOT return the blanket
    "trading or withdrawal permissions" message.

### Claude's Discretion

  whether `hasConnectedKeys` is a new payload field vs. derived in the component from
  an existing signal (`activeVenues.length`), provided it does not re-query.
