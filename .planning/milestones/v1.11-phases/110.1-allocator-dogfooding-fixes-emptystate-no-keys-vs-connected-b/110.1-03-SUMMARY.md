# Phase 110.1 Plan 03: Allocator Dogfooding Red-Team Gap-Closure Summary

Closes the Phase 110.1 red-team findings: the allocator connected-keys and holdings
signals now fail honest/loud instead of asserting states they can't back, and the
wizard key-validation routes stop mislabeling unobserved/transient causes as trade
permissions. Two HIGH/MEDIUM behavior fixes and three copy/docstring fixes, each with
regression coverage where behavior changed.

## What Changed (per fix)

### FIX 1 (HIGH) — connected-keys signal uses the canonical predicate
`getMyAllocationDashboard` now derives a dedicated `hasConnectedKeys` payload field via
`apiKeys.some(isPerKeyDailiesEligibleKey)` (`is_active && sync_status !== "revoked" &&
disconnected_at == null`). `AllocationDashboardV2` threads it into `EmptyState` in place
of the old `activeVenues.length > 0` (is_active-only) derivation. An allocator who
disconnected/revoked their only key now sees the "Connect a key" CTA, not the
connected-but-empty copy. `activeVenues` stays is_active-scoped (factsheet "markets" line
unchanged). `derivePhase07Fields` was exported `@internal` so the regression test
exercises the real wiring, not just the predicate.
- Commit: `9d619c07`

### FIX 2 (MEDIUM) — fail-loud on holdings-count error
`profile/page.tsx` now surfaces the `allocator_holdings` head-count `error` (mirror of
H-0499): it no longer discards it into `count=null → false → "no open positions yet"` on
a money path. `hasHoldings` is tri-state (`boolean | null`); `null` (count failed) →
`AllocatorExchangeManager` shows a neutral `"N connected"` subtitle that asserts nothing
about the book. Threaded through `ExchangesTabContent`. Logs, does not throw.
- Commit: `7a1e81fc`

### FIX 3 (MEDIUM) — honest key-validation reasons on the wizard create routes
`create-with-key/route.ts` (and, to close the class, `composite/add-key/route.ts`) no
longer assert `KEY_HAS_TRADING_PERMS` from `validation.permissions` — a field
`/api/validate-key` never returns. A bare `read_only:false` now maps to the honest
`KEY_NOT_READ_ONLY`; scope-specific codes fire only when a scope was actually observed.
Facet (b): the Python probe fail-closed detail ("could not verify … permission scopes")
now maps in the catch classifier to a retryable `503` + `KEY_PROBE_FAILED` instead of
falling through to `500 UNKNOWN`. Two new `wizardErrors` copy entries added.
Fail-closed acceptance is unchanged — every unverifiable key is still rejected (still
400/5xx, never encrypted/inserted); only the user-facing reason changed.
- Commit: `cd1fdc15`

### FIX 4 (LOW) — marketing copy quotes the real rejection message
`for-quants/page.tsx` TRUST_ATOMS no longer quotes the now-nonexistent
"This key has trading or withdrawal permissions…" string. It quotes the actual curated
message ("Key has trading permissions. Please use a read-only key.") as an example and
notes the read-only backstop, describing the behavior truthfully.
- Commit: `ea910287`

### FIX 5 (LOW) — adapter docstring drift
`adapter.py` `ValidationResult.error_code` enumeration now includes `PROBE_FAILED` and
`MISSING_SCOPE`. Comment-only.
- Commit: `9a3dc2eb`

### FIX 6 (LOW) — count-neutral EmptyState copy
The connected-but-empty copy changed from "Your exchange is connected" (singular, wrong
for the 5-venue repro) to "You're connected — …", which reads correctly for one key or
many. Existing DOGFOOD-1 test unaffected (asserts headline + absence of connect copy).
- Commit: `fdb05277`
