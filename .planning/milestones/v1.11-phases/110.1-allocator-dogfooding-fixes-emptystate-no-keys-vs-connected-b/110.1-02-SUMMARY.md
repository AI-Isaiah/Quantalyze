# Phase 110.1 Plan 02: Validate-and-encrypt fail-closed mislabel (DOGFOOD-3) Summary

Root-caused DOGFOOD-3 at the Python layer: a transient permission-probe
fail-close (network blip / WAF / exchange 5xx) set the `_FAIL_CLOSED` default
`{read:T, trade:T, withdraw:T, probe_error:T}` and flowed into
`validate_key_permissions`'s `if has_withdraw` branch, so ANY probe failure was
labeled "Key has withdrawal permissions. Please use a read-only key." A new
`probe_error`-first branch derives an honest `PROBE_FAILED` code + could-not-verify
copy while keeping `read_only=False` so the key is still REJECTED. The legacy
Next backstop's blanket "trading or withdrawal permissions" claim (fired on any
`read_only:false` 200) is replaced with an honest could-not-verify-as-read-only
message that asserts no scope it never observed.

## What Was Built

**Task 1 — Python root cause (`exchange.py`).** After `read_only` and
`probe_error` are derived (:1111-1114), a new `if probe_error:` branch runs
BEFORE the `has_withdraw` / `has_trade` scope assertions. On a fail-closed probe
it sets `error_code="PROBE_FAILED"` and the exact copy "Could not verify the
key's permission scopes — the permission probe failed. Try again in a moment.",
citing `key_permissions.py:56-59` in the code comment (the fail-closed scopes are
not evidence). `read_only` stays False and `valid` stays True. The stale
`long_fetch.py:253-257` comment that documented the old
"derives WITHDRAW_SCOPE" behavior was updated to "PROBE_FAILED" (comment-only —
its `probe_error` transient bail already runs before any error_code gate, so its
logic diff is empty).

**Task 2 — TS backstop (`route.ts`).** The `!validation.read_only` blanket at
:123-127 now returns "This key could not be verified as read-only. Only
read-only keys are accepted." (status 400, `NO_STORE_HEADERS` unchanged) with a
comment noting genuine scope + probe rejections now arrive as curated 4xx
details via the F5b forward (:137-143), so this unknown-cause branch must not
assert scopes it never observed. The F5b forward, 504, 500, encrypt call,
rate-limit, and dormant unified handler are byte-identical.
