## Summary

Phase 09.1 ships the designer-provided Allocator Dashboard refresh: tab shell rewrite, V2 widget grid with DnD + resize, Tweaks panel lifted out of QA-mode, hero Bridge widget + drawer, holdings adapter, custom range picker, KPI strip rewrite, OutcomesWidget restyle, and a cross-tree flagged-count store for the sidebar badge. Implementation quality is high overall — the cross-tree useSyncExternalStore bridge (AllocationContext.tsx) is sound, the Tweaks panel contains no postMessage handlers (verified by source-level invariant test), there is zero dangerouslySetInnerHTML / eval usage, and font-mono tabular-nums is correctly applied to numeric KPI cells per DESIGN.md.

The review surfaces no critical (security-grade or data-loss) issues. Five warnings cluster around React lifecycle correctness:

1. The "Widget" chip dispatches its open-picker CustomEvent BEFORE the target listener mounts when fired from a non-Overview tab, producing a silent no-op (the visible-bug concern called out in the brief).
2. The AllocationProvider cleanup race that briefly publishes 0 to the cross-tree store on every value-change render — flicker risk for the sidebar badge.
3. The MobileSidebarDrawer focus-restoration effect fires on initial mount with `open === false`, stealing focus into the hamburger button on every (dashboard) route entry on mobile.
4. The OutcomesWidget ExpandedPanel stale-fetch race — the `aborted` ref is reset to false in the new effect before the previous effect's catch handler has cleared.
5. The MyAllocationClient fallback max_drawdown formula divides by `(1 + peak)` where peak can be near -1 for early-loss timeframes (extreme edge case, but renders Infinity).

Info findings include hardcoded amber Bridge surface hex colors (not in DESIGN.md but consistent with the warning palette), a couple of noise-level patterns, and DESIGN.md-adjacent observations.

The work has shipped via v0.15.x release tags and is in production. None of the warnings are regressions of shipped behavior — they're latent edge cases or polish items for a follow-up pass.

## Warnings

### WR-01: Widget chip click from non-Overview tab silently fails

**File:** `src/app/(dashboard)/allocations/AllocationsTabs.tsx:420-431`
**Issue:** Clicking the Widget chip while the user is on Holdings/Outcomes/Mandate/Risk/Scenario calls `changeTab("overview")` (which is async — it uses `router.replace`) and then fires `window.dispatchEvent(new CustomEvent("allocations:open-widget-picker"))` synchronously. AllocationDashboardV2 is mounted lazily (line 489 — `{activeTab === "overview" && <AllocationDashboardV2 ... />}`), so when the user is on a non-Overview tab the listener registered inside AllocationDashboardV2's mount-time useEffect (lines 86-92) does not yet exist. Result: the dispatched event has no listener, gets dropped, the picker never opens, and the user sees the tab change but nothing else.

**Fix:** Defer the dispatch to after the tab actually mounts. Two cheap options:

```tsx
// Option A — fire after a microtask so the new tab's effect has registered.
onClick={() => {
  changeTab("overview");
  if (typeof window !== "undefined") {
    // Wait until React has flushed the new render + effects.
    queueMicrotask(() => {
      window.dispatchEvent(new CustomEvent("allocations:open-widget-picker"));
    });
  }
}}

// Option B — read a deferred flag from a query param so the picker opens
// from inside the new render's effect deterministically.
onClick={() => {
  const params = new URLSearchParams(searchParams.toString());
  params.set("openPicker", "1");
  router.replace(`${pathname}?${params.toString()}`, { scroll: false });
}}
// Then in AllocationDashboardV2:
//   useEffect(() => {
//     if (searchParams.get("openPicker") === "1") {
//       setPickerOpen(true);
//       const next = new URLSearchParams(searchParams.toString());
//       next.delete("openPicker");
//       router.replace(`${pathname}?${next.toString()}`, { scroll: false });
//     }
//   }, [searchParams, ...]);
```

Option B is more robust (queueMicrotask still races with the suspense boundary on initial dynamic-import, since AllocationDashboardV2 is direct-imported but its child widgets are lazy). Add a regression test that asserts the picker opens after the chip is clicked from each tab.

### WR-02: AllocationProvider cleanup races publish 0 between count updates

**File:** `src/app/(dashboard)/allocations/AllocationContext.tsx:94-99`
**Issue:** The effect cleanup fires on every `value.flaggedCount` change (not just unmount):

```tsx
useEffect(() => {
  setFlaggedCount(value.flaggedCount);
  return () => setFlaggedCount(0);   // also runs when value.flaggedCount changes!
}, [value.flaggedCount]);
```

When the parent re-renders with a new count (e.g., after a `router.refresh()` polls the dashboard payload — see AllocationsTabs.tsx:264-270), React's effect lifecycle is: previous-cleanup runs, new-effect runs. So subscribers see `count -> 0 -> newCount` in two sequential commits. The Sidebar useSyncExternalStore will re-render twice, and the badge briefly disappears for one paint cycle before re-appearing. The intended semantic ("clear on unmount") is conflated with the value-change path.

The condition is also fragile under React 18 strict mode (dev) where every effect runs twice (mount, cleanup, mount), so the badge rapidly toggles `count -> 0 -> count` on initial render.

**Fix:** Split the publish-on-change effect from the cleanup-on-unmount effect:

```tsx
// Publish on change.
useEffect(() => {
  setFlaggedCount(value.flaggedCount);
}, [value.flaggedCount]);

// Clear ONLY on unmount.
useEffect(() => {
  return () => setFlaggedCount(0);
}, []);
```

This preserves the "no stale leak across routes" guarantee while removing the per-update flicker. Add a test that asserts the store value never drops to 0 between two non-zero commits with the same provider mounted.

### WR-03: MobileSidebarDrawer focus-restore effect steals focus on initial mount

**File:** `src/components/layout/MobileSidebarDrawer.tsx:63-67`
**Issue:** The effect runs unconditionally on mount because the deps array contains `open` and the body of the effect treats `!open` as "drawer just closed -> restore focus to trigger":

```tsx
useEffect(() => {
  if (!open) {
    triggerRef.current?.focus();   // fires on initial mount with open=false!
    return;
  }
  // ... open === true branch installs listeners + locks scroll
}, [open, onClose, triggerRef]);
```

On every (dashboard) route entry on mobile, the hamburger receives focus before the user has interacted with the drawer at all. This pulls focus away from whatever the route's natural tab-stop should be (e.g., the page heading after route transitions, or a focused input persisted by the page).

**Fix:** Track whether the drawer was previously open, restore focus only on the close transition:

```tsx
const prevOpenRef = useRef(open);
useEffect(() => {
  const wasOpen = prevOpenRef.current;
  prevOpenRef.current = open;
  if (!open) {
    if (wasOpen) triggerRef.current?.focus();   // only on actual close
    return;
  }
  // ... open===true path unchanged
}, [open, onClose, triggerRef]);
```

Add a test that asserts the trigger does NOT receive focus on initial mount with `open={false}`.

### WR-04: OutcomesWidget ExpandedPanel `aborted` ref reset races with previous fetch's catch handler

**File:** `src/app/(dashboard)/allocations/widgets/outcomes/OutcomesWidget.tsx:358-395`
**Issue:** The effect both creates a new AbortController and mutates the shared `aborted` ref:

```tsx
useEffect(() => {
  aborted.current = false;                       // (1) reset
  const controller = new AbortController();
  // ...
  return () => {
    aborted.current = true;
    controller.abort();
  };
}, [outcome.id, curvesCache]);
```

When `outcome.id` changes:
- Previous cleanup runs: `aborted.current = true; controller.abort();`
- New effect body runs: `aborted.current = false; const controller = new AbortController();`

If the OLD fetch's catch handler is still queued in the microtask queue (the `try { ... } catch (err) { ... if (!aborted.current) setError("Failed to load curves"); }` block at line 384-386), it now reads `aborted.current === false` (the new effect's reset) and sets error state for the wrong outcome. In practice the AbortController short-circuits via the `if (err instanceof DOMException && err.name === "AbortError") return;` guard at line 385, so the most likely path is fine — but a non-Abort failure (network error, JSON parse error) racing with the new effect's reset will paint the wrong error onto the new panel.

**Fix:** Capture a per-effect cancelled flag instead of mutating a shared ref:

```tsx
useEffect(() => {
  let cancelled = false;
  const controller = new AbortController();

  if (curvesCache.current.has(outcome.id)) {
    setCurve(curvesCache.current.get(outcome.id)!);
    return () => {
      cancelled = true;
      controller.abort();
    };
  }

  async function fetchCurves() {
    try {
      const res = await fetch(
        `/api/bridge/outcome/${outcome.id}/curves`,
        { signal: controller.signal, credentials: "same-origin" },
      );
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const data = (await res.json()) as CurveData;
      if (!cancelled) {
        curvesCache.current.set(outcome.id, data);
        setCurve(data);
      }
    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") return;
      if (!cancelled) setError("Failed to load curves");
    }
  }
  void fetchCurves();

  return () => {
    cancelled = true;
    controller.abort();
  };
}, [outcome.id, curvesCache]);
```

Drop `const aborted = useRef(false);` (line 358) entirely — it's the pattern that introduces the race. The closure-captured `cancelled` is both clearer and per-effect-instance-scoped.

### WR-05: MyAllocationClient fallback Max DD division-by-near-zero on early-loss timeframes

**File:** `src/app/(dashboard)/allocations/MyAllocationClient.tsx:265-274`
**Issue:** The fallback drawdown computation is:

```tsx
let peak = compositeCurve[0].value;
let maxDD = 0;
for (const p of compositeCurve) {
  if (p.value > peak) peak = p.value;
  const dd = (p.value - peak) / (1 + peak);    // divides by (1 + peak)
  if (dd < maxDD) maxDD = dd;
}
```

`compositeCurve[i].value = wealth - 1` (line 259 — return-form, not wealth-form). If the first day is a heavy loss (wealth = 0.5 -> value = -0.5), peak = -0.5. Then 1 + peak = 0.5, denominator is fine. But if the strategy is in a wealth <= 0 state (catastrophic loss for the visible window — possible for highly-leveraged short-window slices on 1D / 1W timeframes), peak ~= -1 and 1 + peak ~= 0, producing Infinity or huge negative maxDD values that then thread into displayMaxDD and render as "-Infinity%" in the KPI card.

This is a latent edge case — the live data is unlikely to hit `wealth <= -1` for real allocators — but the math is dangerous. The legitimate scenario engine in lib/scenario.ts uses cumulative-return form too but with different drawdown math.

**Fix:** Compute the drawdown on cumulative-wealth (1 + return), not return-relative:

```tsx
// compositeCurve[i].value is cumulative return; convert to wealth for DD math.
let peakWealth = 1 + compositeCurve[0].value;   // >= 0 by construction (wealth)
let maxDD = 0;
for (const p of compositeCurve) {
  const wealth = 1 + p.value;
  if (wealth > peakWealth) peakWealth = wealth;
  if (peakWealth > 0) {
    const dd = (wealth - peakWealth) / peakWealth;
    if (dd < maxDD) maxDD = dd;
  }
}
```

Or guard with `if (Math.abs(1 + peak) < 1e-9) continue;` if you'd rather minimize the diff. Add a regression test feeding a curve with a leading-day -95% return to assert displayMaxDD is finite.

### IN-02: WidgetGrid drag handler reads stale `draggingK` via closure

**File:** `src/app/(dashboard)/allocations/components/WidgetGrid.tsx:201-205`
**Issue:** The onDrop handler reads draggingK from the React closure:

```tsx
onDrop={(e) => {
  e.preventDefault();
  if (draggingK && draggingK !== k) onMove(draggingK, k);
  setDraggingK(null);
  setDragOverK(null);
}}
```

For HTML5 DnD, the dragstart sets draggingK, then dragend / drop fires later — between renders. Because each WidgetCell re-renders when draggingK changes, the closure should be fresh. Confirmed not a bug. However, the canonical idiom for drag id propagation is `e.dataTransfer.getData("text/plain")` which is set in onDragStart (line 189). Using the dataTransfer payload would let the drop handler work even across iframes / detached drag operations and would survive future state-management refactors.

**Fix (optional polish):**

```tsx
onDrop={(e) => {
  e.preventDefault();
  const fromK = e.dataTransfer.getData("text/plain") || draggingK;
  if (fromK && fromK !== k) onMove(fromK, k);
  setDraggingK(null);
  setDragOverK(null);
}}
```

### IN-03: WidgetChrome announce() comment is misleading

**File:** `src/app/(dashboard)/allocations/components/WidgetChrome.tsx:79-85`
**Issue:** The polite live region uses a clever trick to force re-announcement of duplicate strings:

```tsx
function announce(message: string) {
  // Setting the same string twice would be deduped by aria-atomic
  // re-render, so append a zero-width space to force a fresh
  // announcement when the same action fires repeatedly...
  setAnnouncement((prev) => (prev === message ? `${message} ` : message));

```

The comment claims "append a zero-width space" but the actual code appends a regular space. The behavior works (screen readers strip trailing whitespace on a fresh announce), but the comment is wrong — and a future reader trying to debug duplicate announcements may go looking for ZWSP that isn't there.

**Fix:** Update the comment to match the code, or use a counter increment to make the dedup-defeat explicit. Cosmetic only.

### IN-05: Outside-click handlers swap mousedown/click semantics inconsistently

**Files:**
- `src/app/(dashboard)/allocations/components/CustomRangePicker.tsx:124-136` (mousedown)
- `src/app/(dashboard)/allocations/components/Tweaks.tsx:32-48` (mousedown)
- `src/app/(dashboard)/allocations/components/WidgetPicker.tsx:46-62` (click)
- `src/app/(dashboard)/allocations/components/WidgetChrome.tsx:141-149` (click)

**Issue:** Three popovers in the same surface use click for outside-click dismissal, two use mousedown. The behaviors are subtly different: mousedown fires before click and dismisses the popover before the click can reach the target the user is dragging from (e.g., a date input). For a date picker this is fine because the date input is INSIDE the picker. For widget chrome it's also fine because the menu items are inside the menu. But the inconsistency makes the surface feel non-uniform under heavy interaction, and a future edit that copy-pastes the wrong idiom will silently regress.

**Fix:** Pick one and standardize. If outside-click is meant to fire BEFORE the click reaches the underlying element (the more common popover idiom — "clicking through" the backdrop), use mousedown everywhere. Document the choice in tasks/lessons.md and link from each call site comment.

### IN-06: KpiStrip uses `analytics: any` — type erosion at the public component boundary

**File:** `src/app/(dashboard)/allocations/components/KpiStrip.tsx:36-37`
**Issue:** The analytics prop is typed as any with an eslint-disable comment:

```ts
interface KpiStripProps {
  // eslint-disable-next-line @typescript-eslint/no-explicit-any
  analytics: any;
  // ...
}
```

The component reads `analytics?.total_aum`, `analytics?.ytd_twr`, `analytics?.sharpe`, `analytics?.max_drawdown_12m`, `analytics?.avg_correlation`. Each of these is a known field on PortfolioAnalytics (`@/lib/types`) — a TS type already exists. Erasing it loses the regression-protection: a future field rename on PortfolioAnalytics would pass type-check but render null at runtime.

**Fix:**

```ts
import type { PortfolioAnalytics } from "@/lib/types";

interface KpiStripProps {
  analytics: PortfolioAnalytics | null;
  // ...
}
```

Then drop the `?.` chains on fields that are non-optional (verify against the actual PortfolioAnalytics shape). Same applies to `BridgeHeroWidget.tsx:22` (`{ data }: WidgetProps` where data is also any per WidgetProps.data's definition in lib/types.ts:80). The widget contract is intentionally loose (different widgets read different shapes), but call sites that funnel a known payload (e.g., OutcomesTabPanel, RiskTabPanel, BridgeHeroWidget) can narrow at the boundary.
