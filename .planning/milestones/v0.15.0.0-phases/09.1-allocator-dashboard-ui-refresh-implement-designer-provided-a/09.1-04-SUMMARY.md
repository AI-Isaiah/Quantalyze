# Phase 09.1 Plan 04: holdings-adapter (D-18) Summary

Pure read-side transform `toDesignHoldings` joining `holdingsSummary` + `flaggedHoldings` + `matchDecisionsByHoldingRef` + `strategies[]` (+ optional analytics) into the designer's HoldingsTable row shape — no server payload widening, no synthetic strategy joins, fully unit-tested.

## Context

D-18 calls for a thin read-side adapter that lets Plan 08's full-width HoldingsTable (and the Overview Holdings widget) consume the designer's row shape (Strategy / Weight / Allocation / MTD / Sharpe / DD / Age / Status / BridgeCandidate) without widening `MyAllocationDashboardPayload`. The plan additionally locks a critical safety property: the adapter MUST NOT invent a holding→strategy correspondence (T-09.1-04-04 — fabricated joins would silently mis-attribute analytics). Instead, the caller passes a `holdingToStrategyId` map keyed by `buildHoldingRef`; absent or missing entries fall through to `strategy=null`.

Pre-implementation grep of `AllocationDashboard.tsx` lines 697-724 confirmed the legacy `enrichedHoldings` block joins `apiKeys` for `sync_status` only — there is currently NO holding→strategy join in the legacy body. Defaulting `strategy=null` therefore matches the current UI behavior exactly. Plan 08 is responsible for introducing whatever correspondence the new HoldingsTable surfaces (if any) by constructing the `holdingToStrategyId` map.

### Task 2 — toDesignHoldings implementation (GREEN, commit `315f340`)

Created `src/app/(dashboard)/allocations/lib/holdings-adapter.ts` (218 LOC). The implementation:

- Imports `buildHoldingRef` from `./holding-outcome-adapter` to share the exact ref format with Phase 09 (`holding:{venue}:{symbol}:{holding_type}`).
- Exports `FLAG_COMPOSITE_THRESHOLD = 50` and `WATCH_COMPOSITE_THRESHOLD = 40` as `const` literals; documents alignment with `flag-threshold.ts`.
- `HoldingsAdapterInputs` declares its own minimal shapes for `holdingsSummary` / `flaggedHoldings` / `strategies[]` / `analyticsByStrategyId` rather than importing live payload types — this is the D-18 narrow-boundary design (no implicit coupling to future server changes).
- O(n) build: one Map over flagged-by-ref, one Map over strategies-by-id, one pass over `holdingsSummary`. Σ value_usd computed once via reduce; non-finite values treated as 0.
- Strategy resolution via internal `findStrategy(ref)` helper that consults `holdingToStrategyId?.[ref]` and looks up the resulting id in the strategies map. NEVER falls back to symbol matching or any other heuristic.
- Status: `flag.composite_score >= 50 → underperform`; `>= 40 → watch`; `< 40 OR no flag → ok`.
- Age in whole days via `(nowMs - allocatedMs) / 86_400_000`; null-safe and future-date-safe.

JSDoc comment carefully avoids the literal tokens `fetch(`, `localStorage`, `document.` in any prose so the side-effect grep verification (which is a pattern check, not a behavior check) reports a clean 0.
