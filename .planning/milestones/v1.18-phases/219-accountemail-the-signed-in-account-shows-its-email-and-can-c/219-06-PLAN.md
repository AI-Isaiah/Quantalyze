Request: `POST /api/account/email`, `Content-Type: application/json`, body `{ "email": string, "password": string }`, same-origin (the browser's fetch sends Origin).

| Case | Status | Body |
|------|--------|------|
| success | 200 | `{ "ok": true, "pending_email": <data.user.new_email, or null when Auth applied it at once> }` |
| no session | 401 | wrapper's `{ "error": "Unauthorized" }` |
| bad origin / not approved | 403 | wrapper's responses |
| malformed body | 400 | wrapper's `{ "error": "Invalid request body", "issues": [...] }` (limiter NOT consumed) |
| rate limited / limiter unconfigured | 429 / 503 | `rateLimitDenyJson` |
| same address (trim, case-insensitive) | 400 | `{ "code": "same_address", "error": "That is already your sign-in email." }` |
| wrong password | 400 | `{ "code": "wrong_password", "error": "That password is not right. Nothing was sent." }` |
| account has no password | 409 | `{ "code": "password_not_set", "error": "This account has no password yet. Set a password first, then change your email." }` |
| sign-in errored for another reason, or the has-password RPC errored or answered a non-boolean | 502 | `{ "code": "verify_unavailable", "error": "Could not check your password. Please try again." }` |
| updateUser returned an error | 400 | `{ "code": "update_failed", "error": <Supabase error.message, or "Could not send the confirmation link. Please try again." when it is empty or whitespace> }` |

Database function: `public.auth_user_has_password(p_user_id uuid) RETURNS boolean`, called as `admin.rpc("auth_user_has_password", { p_user_id: user.id })` with `createAdminClient()`, `user.id` from the wrapper's getUser().

Redirect: `emailRedirectTo = <origin>/auth/callback?next=` + `encodeURIComponent("/profile?tab=account&email_change=confirmed")`.

<planner_decisions>
1. **Location `src/app/api/account/email/route.ts`**, beside `account/deletion-request` and `account/export` (the existing self-service account routes).
2. **`withAuthLimited`, not an inline limiter.** It runs `assertSameOrigin` for a POST, `getUser()` on the cookie-bound server client, the approval gate, zod validation, then `checkLimit(userActionLimiter, key(user))`, then the handler: exactly GD-01's getUser and GD-02's limiter-before-password order, guaranteed by construction (B15). The route goes in the WRAPPER bucket of src/lib/api/limiter-ordering.test.ts. `requireApproval` keeps its default (true): src/app/(dashboard)/layout.tsx redirects an unapproved user to /pending-approval, so such a user cannot reach the Account tab. Limiter key `email_change:${user.id}` (GD-02, keyed by user id; a bucket of its own so other sensitive POSTs do not share it).
3. **Origin for emailRedirectTo:** the repo's trusted pattern, `resolveAppUrl` in src/app/api/strategies/[id]/share/route.ts (D-16): the origin of `Origin ?? Referer`, which the wrapper's `assertSameOrigin` already validated against the allow-list, then `NEXT_PUBLIC_APP_URL`, then `http://localhost:3000`. Never `Host`, `x-forwarded-host` or `req.nextUrl`. Written as a local function in the new route with a comment naming the share route as its source (two copies already exist; extracting a shared helper is outside this gap).
4. **Only `invalid_credentials` reaches the has-password check.** supabase-js 2.x exposes `error.code` on AuthApiError; `invalid_credentials` is the code GoTrue returns for a bad password. Any other code (`over_request_rate_limit`, `email_not_confirmed`, a network failure) is a 502, never "wrong password". When `user.email` is null there is nothing to sign in with: skip signInWithPassword and go straight to the has-password branch.
5. **Close the verifier session with `signOut({ scope: "local" })`, best effort.** A successful signInWithPassword creates a real GoTrue session; the local scope revokes only that session. Its error is logged by message only and does not change the response. The default scope is global and would sign the user out of the browser too, hence the prohibition.
6. **Password set-up destination for a 409 (used by plan 219-07):** `/reset-password`. Measured in src/proxy.ts: it is in PUBLIC_ROUTES AND in isAuthBounceExempt, so a signed-in user of any role stays on it and ResetPasswordForm's `updateUser({ password })` runs with their session. `/forgot-password` is NOT bounce-exempt, so a signed-in user there is bounced to the role home, and the Security tab is allocator-only (`allocatorOnly: true` in ProfileTabs.tsx). Recorded limit: ResetPasswordForm pushes to `/login?reset=1` on success, which the proxy bounces to the role home for a signed-in user; the user returns to the Account tab by hand.
</planner_decisions>
