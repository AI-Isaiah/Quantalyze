### 1.3 Disconnect trigger

```tsx
<div className="flex flex-nowrap items-center justify-end gap-3 whitespace-nowrap">
  {/* existing Finish setup → button, unchanged, only on eligible rows */}
  <button
    type="button"
    aria-label={`Disconnect ${p.exchangeLabel} · ${p.keyLabel}`}
    className={`${GHOST_ROW_ACTION} inline-flex items-center pointer-coarse:min-h-[44px]`}
    onClick={() => onDisconnect?.(p.id)}
  >
    Disconnect
  </button>
</div>
```

- The visible label is exactly `Disconnect`. The accessible name names the row, so several keys on one venue stay distinguishable.
- `onDisconnect` is a client-to-client function prop minted in `StrategiesSection`, for the same RSC-boundary reason `onFinishSetup` already gives. The public pages pass neither prop, so the control is dead code there.
- Any role that renders the row gets the control. It is never disabled; a control that cannot work is not rendered (repo UAT direction, "no disabled buttons").

### 1.4 The confirm: Disconnect-only variant of the existing feeds-aware confirm

This variant reuses the `AllocatorExchangeManager` confirm (CONTEXT (b)) and narrows it. **For every role it offers exactly two buttons, Cancel and Disconnect.** It has no `Delete key` button and no "Also delete N historical holdings" cascade checkbox. Both exist in the source confirm, and both would break "disconnect, never delete". A manager gets Disconnect here even though the source confirm offers a manager Delete only.

| Slot | Contract |
|------|----------|
| Title (`Modal` `title`) | `Disconnect {Exchange} · {label}?` (the row's own text, then `?`). **Claude's discretion — founder review**: the source confirm's title names the venue only, and this one adds the label because the row lists keys, not venues. |
| Body, allocator and `both` | `We'll stop syncing this key. Your historical holdings stay available for audit and are reflected in past performance.` (verbatim from the source confirm) |
| Body, manager-only | `We'll stop using this key. It stays on your account, marked disconnected, and you can connect this exchange account again.` **Claude's discretion — founder review**: the source confirm has no manager Disconnect string. This one names only facts the phase guarantees: the row is kept, and connecting again is not refused as `KEY_ORPHANED` (CONTEXT (b) test). |
| Feeds note | `deleteFeedsNote(check, false)`, verbatim and in its existing `data-testid="allocator-delete-feeds"` paragraph: `Checking which strategies this key feeds…` (muted) → `This key feeds no strategy.` / `This key feeds: {names}.` (muted), or `Could not check which strategies this key feeds.` (`text-warning`) |
| Retry | The existing `Button variant="secondary" size="sm"` `Retry`, shown only while the feeds read is `unchecked`. It re-runs the feeds read. |
| Holdings | Not read and not shown. The holdings read exists in the source confirm only to decide whether to offer the cascade box, and this variant has no cascade. |
| Error | The existing `role="alert"` line: `Could not disconnect this key. Please try again.` |
| Buttons | `Cancel` (`variant="secondary"`). `Disconnect` (`variant="danger"`, which is the source confirm's variant when no Delete key is offered). The in-flight label is `Disconnecting…`. Disconnect is disabled while the feeds read is open (at most `FEEDS_READ_BOUND_MS`) and while the request is in flight. | Close | Esc and the Modal close button are ignored while the request is in flight (source confirm behaviour). |

The action is the existing owner-scoped RPC `disconnect_allocator_api_key` (CONTEXT (b)). Nothing is deleted.

### 1.5 After a successful Disconnect

1. The confirm closes and the page refreshes (`router.refresh()`). The disconnected key's row is gone from the list, and the comparison-set note's `kSentence` count drops by one.
2. `LiveRegion` (polite) announces exactly: `{Exchange} · {label} is disconnected. You can connect this account again.`
3. Focus moves to the next remaining placeholder row's `Disconnect` control. When none remains, focus moves to the page heading `Strategies` (`tabIndex={-1}` on the heading if `PageHeader` does not already allow it). Focus never drops to `<body>`, which is where the native `<dialog>` would send it once the trigger row is removed. **Claude's discretion — founder review.**

### 1.6 Legend line (`PIPELINE_DEFINITIONS.no_strategy_yet`)

Replace `A connected key with no strategy. Finish setup creates one.` with exactly:

`A stored key with no strategy. Finish setup, when offered, builds one from it. Disconnect stops using the key and keeps it on record, so the account can be connected again.`

`StrategiesLegend.test.tsx` pins the old string, and the planner updates that pin in the same task.

## Surface 4 — Scenario composer holds basis-dependent figures while a leg is pending (decision (d))

File: `src/app/(dashboard)/allocations/components/ScenarioComposer.tsx`.

### 4.1 Definitions

- **Leg**: **every** constituent in the composer's engine set, selected or not. This is the literal reading of locked decision (d), "until every leg's asset class resolves". Pending always ends (below), so the literal reading costs at most the seconds a probe takes. The narrower reading, which counts only the selected legs `blendBasis` reads, is listed as an alternative in § Founder Review and is **not** the contract.
- **Resolved**: the leg's asset class is known, or its probe has **settled**: answered with a class, answered null, or failed. A settled null or failure keeps the existing nullish ⇒ 365 rule (CONTEXT (d), RANK-06 unchanged). Book legs arrive resolved from the SSR payload. So pending always ends.
- **Pending**: at least one leg is unresolved. In practice this means a drawer-added leg whose `/returns` probe has not answered yet.

### 4.2 Visual treatment: the composer's existing pending treatment, nothing new

While pending, each held figure renders the **existing pending state of the constituent rows (UI-SPEC C-4): an em-dash `—`, colourless (`text-text-muted`), with silence.** No caption, no spinner, no skeleton, no new copy, and no tone, under DESIGN.md's Numbers Contract and semantic gates. When the last leg resolves, every held figure renders once, on the final basis. A figure never shows a number first and then changes because the basis flipped.

**Silence is binding: a held consumer never shows its "unavailable" or empty-state reason while pending.** Several consumers print a cause in their absent state. `ScenarioBenchmarkSection`, for example, renders `EmptyStateCard` "Benchmark comparison unavailable" with a reason body. While pending, that would claim a cause that is not true. So a consumer is held by blanking its basis-dependent figure slots to `—` inside its normal populated layout, never by sending it into its own empty or unavailable branch. Where a consumer has no way to do that today, the planner adds a hold input to it. That adds state, not a visual primitive.

### 4.3 What is held and what is not

Held, because each consumes `blendBasis`, directly or through a figure or gate computed with it:

| Consumer | While pending |
|----------|---------------|
| "Scenario blend" strip: Sharpe (`gatedBlendMetrics`). Corrected at plan-check round 1: `KpiStrip` paints YTD TWR, Sharpe, Max DD 12m and Avg \|ρ\| only, so the blend's Volatility, Sortino and CAGR have no strip cell; `gatedBlendMetrics` still nulls all four while pending | `—` in the Sharpe slot |

| Rolling Sharpe chart (`<RollingMetrics data={blendPanels.rollingSharpe}>`; `deriveBlendPanels` computes it with `periodsPerYear = blendBasis`). **CAGR: show it when the gate gives the same verdict on both bases.** CAGR's value runs on the calendar clock, so it is basis-invariant (CONTEXT's own example). Its display, though, goes through `gatedValue(cagr, blendGateState)`, and the gate is basis-dependent (see the gate caption row above). The planner enumerates every `blendBasis` consumer with `grep -n 'blendBasis'`, and every consumer of `blendGateState`, and adds any consumer missing from this table under the same rule.

### 4.4 Save, commit and share

Today `postNewScenario` and `putUpdateScenario` persist the draft only, with no figures. **By default no control is disabled for pending, and none gets new copy.** If the planner's enumeration finds a save, commit or share path that persists a basis-dependent figure, that path either recomputes the figure after resolution or reuses its control's existing `disabled` state while pending. It never persists an interim-basis number (CONTEXT (d)).

## Founder Review

These are open choices CONTEXT left to Claude, plus one truthfulness caveat. Each one is cheap to reverse.

1. **Dedup notice on the session-fence arm (CONTEXT discretion; default kept: it shows).** Caveat: the session fence returns the existing draft **before validating or comparing keys**. So the notice's first sentence, "These credentials are already connected.", is not measured on that arm, and it would be false if the user had typed a different key into the same session. The arm also answers an ordinary double-click or browser retry, which is silent today and would show the notice after this phase. Options: (a) keep the notice as is (the CONTEXT default, implemented here); (b) show it on the venue-fence arm only (one condition); (c) a separate session-arm sentence, which would need the response to say which arm answered.
2. **`KEY_ORPHANED` rewritten fix lines** (Surface 2), and the **new MT5 composite refusal copy and code name** (Surface 3.3).
3. **Disconnect confirm**: the manager-only body sentence and the title carrying the key label (Surface 1.4). Focus after success (Surface 1.5).
4. **MT5 limitation note** shown in place of `+ Add another key window` rather than a silent hide (Surface 3.2).
5. **"Every leg" is implemented literally** (Surface 4.1): any unresolved constituent, selected or not, holds the figures. The narrower alternative counts only selected legs, since an unselected leg cannot move `blendBasis` and selecting it while unresolved would start the hold then. It would hide fewer figures for a few seconds, and it departs from the locked wording, so it is offered here and not implemented.
6. **CAGR while pending** (Surface 4.3). Its value is basis-invariant, but its D-15 gate reads the basis (`crypto` switches between the 90-day and 60-observation bounds). The rule shows CAGR when the gate verdict is the same at 365 and 252, and `—` otherwise. CONTEXT names CAGR as an example of a figure that is not held. This holds it only in the narrow case where its own visibility would flip with the basis.
7. **Legend line** for `No strategy yet` (Surface 1.6).
