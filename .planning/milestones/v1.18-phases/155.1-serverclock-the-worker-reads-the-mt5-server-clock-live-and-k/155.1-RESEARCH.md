### The reading and its assertion
- D-08 Measured offset = newest tick wall time minus the worker's UTC now, rounded to 900 s (C3).
  The rounding residual and the newest tick's age are recorded with the reading.
- D-09 Expected offset = the configured clock's offset at that wall instant
  (`Mt5ServerClock.instant_offset_s`). In a repeated or skipped broker hour, where that is `None`,
  the reading is recorded as unassertable and is not a mismatch.
- D-10 Three verdicts: `match`, `mismatch`, `unmeasured`. `unmeasured` covers no fresh tick (a
  closed market, a session break, the weekend) and a residual past the refusal bound. An
  `unmeasured` reading is persisted with its reason and does NOT refuse the persist: refusing on a
  closed market would fail every weekend derive. Only `mismatch` refuses (D-01). The freshness and
  residual bounds come from the spike, never picked to make a run green.
- D-11 Mismatch error: a named error (working name `Mt5ServerClockMismatchError`). The derive fails
  before any `nav_marks` / dailies persist for that key, with an `ops_alert`, and the message carries
  the rule id and the two offsets only. Error kind follows 175 / D-04: `transient`, so retries are
  bounded and a corrected rule heals on the next derive.
- D-12 The reading is never written back as configuration (Anti-Pattern 3); `MT5_SERVER_TIME_RULE`
  stays the only carrier.

## Summary

The phase adds one narrow tick-time read to `Mt5Client`, one pure assessment function beside `Mt5ServerClock`, one write-once table, one `ops_alert` source and the wiring inside `run_derive_broker_dailies_job`. Every ingredient has a close in-repo precedent: `session_snapshot` (a committed remote expression read in ONE rpyc crossing with an AST pin on its allowed calls) for the method, `api_key_flow_prices` (RLS on, no policy, INSERT-only grant, eight-arm gate) for the table, the Phase 175 config-fault arm for the transient refusal, and `ops_alert.page` for the alert.

Three findings reshape the plan and are surfaced as decisions, not smoothed over. (1) D-04 and D-07 conflict as worded: `_materialize` copies every field of a tick, prices included. (2) D-18's premise does not match the schema: no PROD table stores a deal's broker wall time, so a "PROD read through the Supabase MCP" cannot preselect the deal. (3) The spike mirrored per-symbol netref iteration (4.7 to 7.3 s for the listing); the house pattern is one crossing, which is unmeasured live for these calls. The D-10 bounds are derived from the three readings below: the residual bound rests on the 0.292 s maximum (Run 3), the freshness side has NO observed stale case, and a stale newest tick is indistinguishable from an offset shift by the data alone, so the verdict order and a plausibility class carry the weight.

**Primary recommendation:** Build `Mt5Client.server_tick_times` as a committed one-expression remote constant modelled on `_REMOTE_SESSION_SNAPSHOT_SRC` (returns by-value ints only; AST-pinned allowed calls and attributes), call it in a separate `to_thread` inside the existing lease after `read_mt5_deal_ledger`, assess with a pure function (residual bound 5 s as a ratified margin over the 0.292 s maximum, plus a rule-offset plausibility class), insert the reading before deciding, then refuse only on `mismatch`. Keep tick read failures out of the `Mt5ClientError` classify arm.

### Pattern 1: The method is a committed one-crossing remote expression (session_snapshot precedent)

**What:** `server_tick_times` evaluates ONE committed expression on the far side with `conn.eval`; the expression enumerates `mt5.symbols_get()`, keeps `visible`, reads `mt5.symbol_info_tick(name)` per visible symbol and returns a by-value tuple of ints. Names never cross the wire. The client parses with `type(raw) is tuple` first (a netref would cost a crossing per index) and raises a typed scrubbed `Mt5ClientError` on a malformed shape.

**Why not `_materialize`:** D-07 names `_materialize`, but `_materialize` calls `asdict()` and copies every field [VERIFIED: mt5_client.py:1284-1290, `return {str(k): _coerce(v) for k, v in asdict().items()}`], which includes bid, ask, last and volume. That violates D-04 ("never materialised or returned"). The remote expression reads only `.time_msc`; the rest of the D-07 discipline (`_assert_live` first statement, `_guarded_read(..., stage=...)`, `None`/unanswered mapped through `_raise_last`) is kept. Surface this to the planner as a reconciled reading of D-04/D-07.

**Precedent for the pin (the D-D "exception is pinned by a test"):** `test_SESSION_SNAPSHOT_the_remote_source_is_a_committed_literal_that_can_only_read` asserts the source is an AST string constant, carries no `{`, `}`, `%`, `__` or `import`, and that its only calls on `mt5` equal `_SNAPSHOT_ALLOWED_MT5_CALLS` [VERIFIED: tests/test_mt5_client_contract.py:5513 `_SNAPSHOT_ALLOWED_MT5_CALLS = frozenset({"terminal_info", "account_info", "last_error"})` and the test body that follows it, read at 5515-5568]. The new pin: allowed `mt5` calls `{"symbols_get", "symbol_info_tick", "last_error"}`; attribute reads allowed `{"visible", "name", "time_msc"}` plus the `getattr` string constants; and an offline double whose tick raises on any other attribute (reuse `_Tick.__getattr__` from `tests/test_mt5_spike_tick.py`).

**Mechanism evidence:** `mt5linux` runs every call as `conn.eval(code)` in the namespace where `mt5` was bound by `execute('import MetaTrader5 as mt5')` [VERIFIED: wheel `__init__.py:364-365`], so a committed expression referencing `mt5` uses the library's own seam. `[ASSUMED]` whether a multi-call expression with lambdas and a comprehension runs on the Wine-side Python: `_REMOTE_SESSION_SNAPSHOT_SRC` carries the same shape and its own comment says "Never exercised against the live bridge" [VERIFIED: mt5_client.py:2164]. The spike runs 1-3 exercised only the client-side route.

**Example (executed offline this session against a far-side double, NOT against the live bridge):**
```python
# Source: written for this phase; shape follows _REMOTE_SESSION_SNAPSHOT_SRC (mt5_client.py:2165-2183)
_REMOTE_SERVER_TICK_TIMES_SRC = """
(lambda scalar: (lambda symbols:
    ("listing_unanswered", scalar(mt5.last_error()[0]))
    if symbols is None
    else (lambda ticks: (
        "answered",
        len(symbols),
        len(ticks),
        len([t for t in ticks if t is not None]),
        max([scalar(getattr(t, "time_msc", None)) for t in ticks
             if t is not None and isinstance(getattr(t, "time_msc", None), int)] or [-1]),
    ))([mt5.symbol_info_tick(s.name) for s in symbols if s.visible])
)(mt5.symbols_get()))(
    lambda value: value
    if value is None or isinstance(value, (bool, int, float, str))
    else str(value)
)
"""
# offline result for 4 symbols (3 visible, one with no tick): ('answered', 4, 3, 2, 1700000005000)
# a None listing -> ('listing_unanswered', -1); an empty listing -> ('answered', 0, 0, 0, -1)
```

`Mt5ServerClock.instant_offset_s(wall_epoch_s)` raises `ValueError` for a year outside 2007-2099 and the conversion can raise `OverflowError`/`OSError` for an undatable epoch [VERIFIED: mt5_server_clock.py `_wall_year` and docstring; `_FIRST_RULE_YEAR = 2007`, `_LAST_RULE_YEAR = 2099`, mt5_server_clock.py:67-68]. A garbage tick must become `unmeasured`, never an unhandled raise. A fixed clock returns its offset at every instant.

**Example (executed offline this session against the real `Mt5ServerClock`; not yet in the repo):**
```python
ROUND_S = 900                 # CONTEXT D-08 / spike _TICK_ROUND_S
RESIDUAL_BOUND_S = 5.0        # see "D-10 bounds": a ratified margin, [ASSUMED]
MAX_PLAUSIBLE_S = 13 * 3600   # spike _MAX_PLAUSIBLE_OFFSET_S; clock _MAX_FIXED_OFFSET_S
RULE_OFFSETS = frozenset({7200, 10800})   # clock _STANDARD_OFFSET_S / _DAYLIGHT_OFFSET_S

def assess(clock, *, newest_tick_ms, utc_now_ms):
    if newest_tick_ms is None:
        return Assessment("unmeasured", "no_tick")
    raw = (newest_tick_ms - utc_now_ms) / 1000.0
    rounded = int(round(raw / ROUND_S) * ROUND_S)
    residual = rounded - raw
    if abs(rounded) > MAX_PLAUSIBLE_S:
        return Assessment("unmeasured", "offset_implausible", ...)
    if abs(residual) > RESIDUAL_BOUND_S:
        return Assessment("unmeasured", "residual_over_bound", ...)
    if clock.rule != "fixed" and rounded not in RULE_OFFSETS:      # plausibility class, see below
        return Assessment("unmeasured", "offset_not_a_rule_offset", ...)
    try:
        expected = clock.instant_offset_s(newest_tick_ms // 1000)
    except (ValueError, OverflowError, OSError):
        return Assessment("unmeasured", "tick_time_out_of_range", ...)
    if expected is None:                                           # D-09: repeated/skipped hour
        return Assessment("unmeasured", "expected_unassertable", ...)
    return Assessment("match" if rounded == expected else "mismatch", None, ...)
```
Offline checks that came out as the three recorded runs (hand-built inputs reproducing Run 2's raw 7199.836 s and Run 3's raw 7199.708 s under rule `us`: both `match`, residuals 0.164 and 0.292); a `us`-true broker at 2026-10-28 12:00Z under rule `eu` is `mismatch`; under `us` it is `match`; a Saturday stale tick (2.75 h old) is `unmeasured/offset_not_a_rule_offset`; a fixed 10800 against a true 7200 is `mismatch`.

### Pattern 5: Keep a tick read failure out of the credential classify arm

In the derive, `except Mt5ClientError as exc:` runs `classify_mt5_login_error(exc)` and on `"auth"` stamps `"MT5 login was rejected (bad credentials)."` PERMANENT [VERIFIED: job_worker.py:7571-7600]. The scrubbed text of a terminal error from the tick read could match an auth phrase and permanently fail a working key; D-42 states the same hazard for abandonment. Therefore: inside the thread function that does the tick read, catch `Mt5ClientError` and return an `unmeasured` outcome with reason `tick_read_failed` (exception CLASS name only, never the text); let `Mt5SessionAbandoned`, `asyncio.TimeoutError` and `Mt5AccountMismatchError` propagate to their existing arms. This is a planner decision (D-10 does not say what a raising read means); the alternative (letting it reach the classify arm) can fail every derive on a gateway blip after the deals were already read.

### Anti-Patterns to Avoid
- **Reading via `_materialize` on a tick:** copies prices (D-04).
- **Per-symbol netref iteration in production:** O(1416) round trips (spike listing 4.731 to 7.337 s).
- **Writing the reading back as configuration (D-12)** or resolving the clock a second time.
- **Asserting freshness from an age computed against the rule:** the spike's `age_vs_rule` is `expected - raw` and presupposes the rule (see bounds).
- **A DELETE-refusing trigger on a table with a key FK that cascades** (Migration section).

## Common Pitfalls

### Pitfall 1: A stale newest tick passes as an offset shift
**What goes wrong:** at a closed market with no 24/7 symbol visible, `raw = offset - age`; an age near a multiple of 900 s with a clean residual reads as a `mismatch`, refusing a healthy derive and paging the founder.
**Why:** age is unobservable apart from the rule (bounds item 1).
**How to avoid:** residual bound plus the rule-offset plausibility class; only `mismatch` refuses; persist `unmeasured` with its reason.
**Warning signs:** `mismatch` rows with `measured_offset_s` not in `{7200, 10800}`; mismatches clustered at weekend derive times.

### Pitfall 2: The new round trip breaks ~54 existing derive tests
**What goes wrong:** the real `Mt5Client` over the existing doubles hits a missing attribute; `_guarded_read` turns it into `Mt5ClientError`; the derive ends `FAILED transient` and any test expecting `DONE` goes red. The conftest comment above the 175 clock default records "At least 54 tests drove the MT5 branch" (read via `sed`, not `Read`, so cited as context); the fixture itself sets `monkeypatch.setenv("MT5_SERVER_UTC_OFFSET_S", "0")` [VERIFIED: tests/conftest.py:447-450].
**How to avoid:** give the shared doubles an `eval` answering the new expression with a default "no ticks" answer (`unmeasured/no_tick`, never refuses), and update the three call-sequence pins. Doubles to update: `_FakeMt5Transport` and its `_FakeRpycConn` in `tests/test_mt5_derive_branch.py` (they have `execute` but no `eval`), the `_FakeMt5` and `_FakeRpycConn` in `tests/test_mt5_client_contract.py`, and the other suites that import `run_derive_broker_dailies_job` with an MT5 session (by Mt5Client/session mention count: `test_mt5_read.py`, `test_mt5_concurrency.py`, `test_mt5_sync_path.py`, `test_mt5_handover.py`, `test_allocator_positions_non_ccxt.py`, `test_mt5_relogin.py`, plus the nav-marks and allocator-equity derive tests that carry a session).

### Pitfall 3: Alert detail is scrubbed of 5-digit offsets
`10800` becomes `<digits>` in `ops_alert` detail. Render hours or minutes. (Pattern 4.)

### Pitfall 4: A tick read failure classified as a credential verdict
See Pattern 5. Convert inside the thread; never let the scrubbed text reach `classify_mt5_login_error`.

### Pitfall 5: A DELETE-refusing trigger blocks key deletion and account erasure
See Migration. Prove both erasure paths in the gate.

### Pitfall 6: `_materialize` on a tick leaks prices into the client
The D-04/D-07 conflict. Time-only far-side expression plus an AST pin.

### Pitfall 7: The mismatch refusal repeats on every retry
Each attempt writes a new reading row and the alert window (1 h per source/cause/event) collapses the pages. A corrected rule heals the next attempt or derive (175/D-04). Do not add a unique key on `job_id` alone.

### Pitfall 8: Putting hashing or JSON inside the clock leaf
`mt5_server_clock.py` is pinned to a stdlib allow-list without `hashlib` or `json`. Hash in a worker module.

### Pitfall 9: Weekday row means `match`, not just a row
Criterion 3 needs a weekday PROD row per key. A Saturday 00:40Z derive after a Friday close is `unmeasured` for an account with no weekend-quoting symbol. Check the Tue-Fri derive's `match`, not row existence.

|---------|--------|---------------------|
