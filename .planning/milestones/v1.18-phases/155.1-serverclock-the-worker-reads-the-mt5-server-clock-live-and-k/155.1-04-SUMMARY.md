# Phase 155.1 Plan 04: write-once trigger, keep-data rollback and the 24-arm SQL gate Summary

**`mt5_server_clock_readings` is now write-once against every role, owner and BYPASSRLS included, through a BEFORE UPDATE OR DELETE row trigger that admits the `api_keys` cascade by trigger depth, with BIGINT offsets, a keep-data rollback, and a SQL gate whose 24 arms were each shown to bite on a private lane.**

## Accomplishments

- **Migration (`20261117120000_mt5_server_clock_readings.sql`).**
  - `enforce_mt5_server_clock_readings_write_once()` is SECURITY INVOKER with `search_path = public, pg_temp`. It raises `check_violation` (23514) with a single-literal message on every UPDATE, and on a DELETE unless the trigger depth is greater than one. EXECUTE is revoked from PUBLIC, anon and authenticated.
  - Trigger `mt5_server_clock_readings_write_once` is BEFORE UPDATE OR DELETE, FOR EACH ROW.
  - The depth literal appears once in the file (code only; every comment paraphrases it).
  - The `DO $verify$` block now also checks the function (`pg_proc`) and the trigger (`pg_trigger`, `NOT tgisinternal`). It is catalogue-only and asserts no grant, RLS flag, CHECK body or FK action.
  - Header paragraphs rewritten for the trigger (D-14), plus SC-6 and a new SC-7 for the BIGINT widening.
- **BIGINT offsets (orchestrator note, Rule 1).** `measured_offset_s` and `expected_offset_s` are BIGINT. Every CHECK, including the `offsets_chk` equality, is unchanged and still coherent. The parity pin `test_mt5_server_clock_readings_parity.py` does not pin column types and stayed green (2 passed). Plan 01's `tick_time_out_of_range` all-None behaviour is untouched.
- **Rollback (`down/20261117120000-rollback.sql`).**
  - Marker-query header, `psql --single-transaction -v ON_ERROR_STOP=1`, ledger row left in place.
  - Catalogue-only precondition: refuses when the table is absent, or when the table or function is already set aside.
  - Revokes every privilege, then renames the table, pkey, fkey, the seven CHECKs, the index, the identity sequence and the function aside. No `DROP TABLE`. Data kept.
  - The trigger stays on the renamed table, so the kept rows stay write-once and still erase with their key. The header says so.
  - Catalogue-only verify, including that the trigger is attached to the kept table.
- **SQL gate (`test_mt5_server_clock_readings.sql`).** 24 identities, each with prose `RED-UNDER:` and machine `RED-UNDER-M:`; `RED-UNDER-SETUP` is flow_prices' list ending with this migration. `pg_temp` helpers use the `sc_` prefix. Arms:

  - 3a-3j: each value rule refuses with 23514 naming its own constraint.
  - 4a, 4b, 4c: service_role UPDATE, DELETE and TRUNCATE refused 42501.
  - 5: owner-role UPDATE refused by the trigger.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] BIGINT offsets (directed by the orchestrator, from plan 01's finding)**
- **Issue:** INTEGER offsets overflow on an absurd tick (about 68 years or more off), failing the insert on every retry, while D-19 forbids a plausibility bound.
- **Fix:** both columns BIGINT in the CREATE TABLE; a SC-7 note in the header. No CHECK changed.
- **Commit:** ef5740171

**2. [Rule 1 - Bug] Rollback names past the 63-character identifier limit**
- **Found during:** Task 1, apply/rollback/re-apply on the lane (PostgreSQL printed `identifier ... will be truncated` for two renames).
- **Issue:** with the plan's `_rolled_back_20261117` suffix, `mt5_server_clock_readings_reason_verdict_chk_rolled_back_20261117` and `enforce_mt5_server_clock_readings_write_once_rolled_back_20261117` are 65 characters and were silently truncated. The file's own precondition and verify still passed only because they were truncated identically.
- **Fix:** those two names use `_rb_20261117`. Every other renamed object keeps `_rolled_back_20261117`. The header says why.
- **Commit:** ef5740171

**3. [Rule 3 - Blocking] Arms 7a and 7b need different mutations**
- **Found during:** Task 2 design (depth probe).
- **Issue:** the plan gave both arms the same twin (the depth test changed to greater than 99). The runner credits an arm only when the FIRST `TEST FAILED (N)` names that arm, so 7b's twin would have read 7a's identity. A threshold edit cannot separate them either, because both paths reach the trigger at depth 2.
- **Fix:** 7a keeps the plan's edit (refuse every cascade); 7b's edit admits the cascade only when `auth.uid()` is set, so 7a (signed-in) passes and 7b (claims cleared, an operator-style erasure) is refused. The gate header explains it. Both bite.
- **Commit:** ee6a0e56d

**4. [Rule 3 - Blocking] The plan's arms were split into more identities**
- The same first-failure rule needs one identity per independent defect. Arm 4 became 4a, 4b, 4c (each grant widening is a different mutation). Arm 3's offsets rule became 3e, 3f, 3g, and the counts rule 3i, 3j. Arm 9 became 9a-9d (9b makes the trigger FOR EACH STATEMENT, which no behaviour arm can see; 9c SECURITY DEFINER; 9d the function's EXECUTE revoke). The sentinel is `ALL 24 ARMS EXECUTED` with all 24 identities named in its roster, rather than one count of arms. The plan allows sub-identities.
- 3f/3g and the helper `sc_row` also had to avoid an `END ... CASE` token sequence that `lint-sql-gates.mjs` mis-parsed (a MEASURE_FAIL on first run); `sc_row` is plpgsql with IF blocks.
- **Commit:** ee6a0e56d

**Total deviations:** 4 (2 Rule 1, 2 Rule 3). **Impact:** the contract is the plan's; the gate is larger (24 arms, not about 16).
