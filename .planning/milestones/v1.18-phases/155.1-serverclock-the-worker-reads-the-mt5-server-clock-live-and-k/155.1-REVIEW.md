## Warnings

### WR-01: A slow or hung tick crossing fails the derive and restarts the terminal; the D-20(b) "unmeasured" arm cannot catch it

**File:** `analytics-service/services/mt5_read.py:313-325`, `analytics-service/services/mt5_concurrency.py:119-145` (bound not widened), `analytics-service/services/mt5_concurrency.py:91-93` (`_MT5_DERIVE_READ_TIMEOUT_S` = `MT5_REQUEST_TIMEOUT_S + 10` = 40 s by default)
**Issue:** The new crossing runs inside the same outer `asyncio.wait_for` bound as login, PRE `account_info`, the full-history `history_deals_get` and POST `account_info`. On a cached read that bound is 40 s. The tick crossing's own ceiling is the rpyc `sync_request_timeout` of 30 s (`mt5_client.py` `MT5_REQUEST_TIMEOUT_S`).

If the far-side `symbols_get` (about 1416 symbols on MM2) plus the tick loop stalls, two things go wrong:
- The tick crossing reaches its 30 s rpyc timeout, which `_guarded_read` turns into `Mt5ClientError`. By then the outer 40 s bound has almost certainly fired, because login and the deal read already used part of it.
- The derive then takes the `asyncio.TimeoutError` arm. That arm calls `_mt5_bounded_restart` (a terminal restart) and returns FAILED.

So the D-20(b) path (`tick_read_failed`, derive proceeds) only covers a crossing that raises quickly. A crossing that is merely slow now fails every MT5 derive and restarts the terminal. Before this phase, that core path carried one fewer crossing of unmeasured cost.

The far-side cost of the production expression is UNMEASURED, as the docstring at `mt5_concurrency.py:133-145` admits. The spike figures timed a 14-symbol client-side loop and do not measure this expression. The only evidence would be the founder-run `--leg clock` `crossing_elapsed_s` after deploy. That makes an evidence-only reading a new way to fail the core derive, which is the coupling D-20(b) exists to prevent.

**Fix:** Give the tick crossing its own short rpyc ceiling, well inside the remaining outer budget. Then a slow listing becomes `Mt5ClientError` and lands in `tick_read_failed`, and the outer timeout never sees it. Use the existing per-connection knob (`_MetaTrader5__conn._config["sync_request_timeout"]`, `mt5_client.py:1257`), saved and restored around the one call:
```python
def server_tick_times(self, *, timeout_s: float = 5.0) -> Mt5ServerTickTimes:
    ...
    cfg = conn._config
    prev = cfg.get("sync_request_timeout")
    cfg["sync_request_timeout"] = timeout_s
    try:
        raw = self._guarded_read(_remote_call, stage="server_tick_times")
    finally:
        cfg["sync_request_timeout"] = prev
    return _parse_server_tick_times(raw)
```
A timed-out eval can leave the far side busy, so the POST `account_info` may then queue behind it. If that matters, reserve the tick crossing's ceiling explicitly in `mt5_derive_read_bound_s` (add `timeout_s` to `read_s`) so the outer bound is never what fires first. Either way, record the founder's `crossing_elapsed_s` reading against this ceiling.

**Issue:** The exemption admits a DELETE issued from inside any trigger context. That includes a future trigger on any table whose function deletes readings, not only the RI cascade. Today no such trigger exists, and only the owner holds DELETE (service_role has none), so this is not exploitable now. The header's "admits exactly the cascades" is true of today's catalogue, not of the rule itself.
**Fix:** If the guarantee needs to outlive catalogue changes, also require that the parent row is gone. The RI cascade runs after the api_keys row is deleted, so the row is invisible at that point:
```sql
IF pg_trigger_depth() > 1
   AND NOT EXISTS (SELECT 1 FROM public.api_keys WHERE id = OLD.api_key_id) THEN
  RETURN OLD;
END IF;
```
This needs SELECT on api_keys in the trigger's execution context, so check which role the RI action runs as before adopting it.

### IN-06: No reading is recorded when the settle loop raises `Mt5HistoryUnsettledError`

The gap is small, because those derives write nothing else either and they retry.
**Fix:** Accept and document this, or move the tick read before the settle loop. It would still sit inside the PRE/POST bracket, because the POST re-assertion follows the settle loop.

### IN-07: The band leg reads deals without asserting the logged-in account
