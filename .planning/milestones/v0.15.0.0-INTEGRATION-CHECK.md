## G-1 fix verification

The prior integration check flagged G-1: `outcomes: []` was hardcoded at `src/lib/queries.ts:1351` in the `!portfolio` branch of `getMyAllocationDashboard`, even though `bridge_outcomes` is keyed only by `allocator_id` (not `portfolio_id`). A fresh allocator with flagged holdings could record outcomes via the bridge UI but the dashboard payload would always show `outcomes: []`, hiding the outcomes lane until they had a `portfolio_strategies` row.

**Fix landed in commit `2161a94`.** Re-verification of all invariants the prior check identified as load-bearing:

### Single source of truth for `outcomes`

`src/lib/queries.ts:1221-1228` — the `bridge_outcomes` query is now part of Step 1's `Promise.all` array, named `outcomesFullRes`:

```typescript
admin
  .from("bridge_outcomes")
  .select("id, strategy_id, match_decision_id, kind, ...
    replacement_strategy:strategies!bridge_outcomes_strategy_id_fkey(id, name),
    match_decision:match_decisions!bridge_outcomes_match_decision_id_fkey(
      original_strategy:strategies!match_decisions_original_strategy_id_fkey(id, name)
    )")
  .eq("allocator_id", userId)
  .order("created_at", { ascending: false })
  .limit(200),
```

### Ownership gate preserved inline

`.eq("allocator_id", userId)` at line 1226 — kept inline with the query per Voice-D4 regression assertion (TC outcomes-05). No reviewer can accidentally drop it. Same defense-in-depth pattern as the older bridge_outcomes query at lines 1490-1495.

### Normalization runs once

`src/lib/queries.ts:1231-1260` — the `normalizeEmbed` + `outcomes: OutcomeRow[]` derivation is single-pass at module top-level, before the `if (!portfolio)` branch.

### Both branches return the same `outcomes` variable

- `!portfolio` branch — `src/lib/queries.ts:1398` returns `outcomes` (was `[] as OutcomeRow[]` before fix).
- portfolio branch — `src/lib/queries.ts:1595` returns `outcomes` (was a duplicate normalization block before fix; now uses the hoisted derivation).

### Step 2 cleanup

`src/lib/queries.ts:1430-1506` — Step 2's `Promise.all` no longer fetches `outcomesFullRes` (the duplicate query/comment block at the old lines 1465-1480 is now a single comment-only stub at 1503-1505). Step 2 still fetches the orthogonal `existingOutcomesRes` (smaller projection, no joins) for the per-strategy eligibility filter — those are different queries with different purposes.

### Type/shape parity

Both branches return `outcomes: OutcomeRow[]` (line 605 type def). `OutcomesWidget.tsx:208,762` reads `payload?.outcomes` with no branch-aware logic — the consumer was always ready for non-empty `outcomes` in the `!portfolio` branch; the producer is now ready too.

### Net diff

53 insertions / 44 deletions = ~9 net new lines (per commit `git show 2161a94 --stat`); reflects a single hoist + dedupe, not an architectural change.

**G-1 verdict:** RESOLVED. Re-verifying the four invariants the prior check called out (single fetch, ownership gate inline, single normalization pass, identical return shape across branches) shows all four hold. No regression risk identified.
