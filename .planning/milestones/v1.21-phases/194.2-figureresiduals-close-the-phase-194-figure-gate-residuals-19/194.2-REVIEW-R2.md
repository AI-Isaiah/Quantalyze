## Warnings

### WR-01: [MEDIUM] The USD view of a native-unit strategy shows annualised figures that its native view withholds for an unreadable date

**File:** `src/lib/factsheet/fetch-and-build-payload.ts:1130-1166` (`buildUsdView`), with
`src/lib/factsheet/native-to-usd.ts:53-63` and `src/lib/factsheet/build-payload.ts:946-952`.
The view is selected at `src/app/factsheet/[id]/v2/unit-view.tsx:66`.
**User-facing and data-integrity. Round 1 missed it. It is in phase scope:
`194-MALFORMED-DATES-ABSENT`, "every date axis ... read a malformed date as unreadable, never as
absent".**

**Issue:** `buildUsdView` converts the native series with `convertNativeReturnsToUsd`. That
function keeps only days that `alignCoveredReturns` pairs with a BTC close, and a malformed date
never pairs. The USD series therefore has every malformed interior or last date stripped out. The
USD payload then goes through `buildFactsheetPayload`, which re-judges readability with
`firstUnreadableDate` over the USD dates. Those dates are now all readable, and the only extra
input is `recordSeriesStart`. Plan 05 deliberately carries `recordSeriesStart` and
`recordObservations` to the USD build, because "the record is a fact about the record, not its
unit". The unreadable verdict is the same kind of fact, and it is not carried. `unit-view.tsx:66`
renders `usdView.payload` in the USD view, and that payload has its own `figureRecord`.

**Measured** (probe through the real chain: a curve with `daily_returns` null,
`resolveDailyReturnSeries(null, curve, "geometric", true)`, then `convertNativeReturnsToUsd`, then
both builds with `curveRecordStart`, on a 200-point crypto curve):

| malformed curve point | native view | USD view |
|---|---|---|
| `2024-02-30` at index 60 | withheld | **short**, Sharpe 1.688 shown |
| `2024-1-5` at index 60 | withheld | **short**, Sharpe 1.728 shown |
| `garbage` at index 199 | withheld | **short**, Sharpe 1.570 shown |
| `2024-13-01` at index 199 | withheld | **short**, Sharpe 1.570 shown |
| `2024-13-01` at index 0 | withheld | withheld (carried by `recordSeriesStart`) |

**Failure scenario:** a BTC-denominated (native-unit) strategy whose stored curve holds one
malformed date after its first point. On `/factsheet/<id>` the native view withholds CAGR, Sharpe
and Sortino under the unreadable reason, and the Sentry report fires. The viewer clicks the USD
segment, and the same factsheet now prints those annualised figures with only a `<1y` marker. One
record gets two verdicts on one page, which is the split this phase exists to remove. When the
malformed date is the last one, the list also withholds through the `->-1->>date` alias, so only
the USD view shows the figures.

**Fix:** carry the native record's readability into the USD build, before the build, because every
bundle gates on the one `totalRecord`. Add an opt that `firstUnreadableDate` scans as one more axis,
and pass the native dates:

```ts
// build-payload.ts, BuildFactsheetOpts
/** 194.2: dates of the series this one was converted from; their readability is the record's. */
recordSourceDates?: readonly string[];

// build-payload.ts:946
const firstBad = firstUnreadableDate(
  dates, mtmDates, smoothedDates,
  opts?.recordSeriesStart ? [opts.recordSeriesStart] : [],
  opts?.recordSourceDates ?? [],
);

// fetch-and-build-payload.ts, buildUsdView usdOpts
recordSourceDates: nativeSeries.map((p) => p.date),
```

Add the axis name to the report's `firstBadAxis` list. Add a parity case through
`fetchAndBuildPayload` for a native-unit curve with `2024-02-30` at an interior index. It should
assert that `usdView.payload.figureRecord.unreadable === true` and that the gate is `withheld`.
Then neuter it by dropping `recordSourceDates` and see it go RED as `short`.

### WR-02: [MEDIUM] Carried from round 1, unnumbered there and still open: any signed-in user can insert an intro row directly, bypassing `/api/intro`'s attestation check

**File:** `supabase/schema/baseline.sql:16605`
(`CREATE POLICY "contact_requests_insert" ... FOR INSERT WITH CHECK (("allocator_id" = "auth"."uid"()))`).
The policy was first created at `supabase/migrations/20260405061912_rls_policies.sql:47`. No later
migration in the tree replaces it (re-checked with `grep -rn contact_requests_insert supabase/migrations`).
**Security and compliance. Not a fix-round regression. The fix round neither fixed nor booked it.**

**Issue:** plan 04 makes `/api/intro` refuse an unattested allocator (D-03). The table's INSERT
policy checks only `allocator_id = auth.uid()`, and `authenticated` holds INSERT. So the
accredited-investor gate exists only in the route, not in the data. D-03's sentence, "a direct POST
no longer bypasses the gate", holds for the route and not for the table.

**Failure scenario:** an unattested signed-in user, or a non-allocator, sends
`POST /rest/v1/contact_requests` with their own `allocator_id` and a target `strategy_id`, using
the anon key and their session JWT. The row lands, and it appears in the manager's and admin's
intro views as a request from someone who never attested.

**Fix:** a migration that tightens the policy's `WITH CHECK` to require an attested allocator
(for example an `EXISTS` on the attestation row with `attested_at IS NOT NULL`, through a
SECURITY DEFINER helper that has anon EXECUTE if a `{public}` policy calls it). The other option is
to revoke direct INSERT from `authenticated` and insert only through the route's service-role
client. Either way it needs migration-reviewer and rls-policy-auditor clean before merge. If it is
not fixed in this phase, book it in `TODOS.md` with an owner, so it does not survive a third round
as prose.
