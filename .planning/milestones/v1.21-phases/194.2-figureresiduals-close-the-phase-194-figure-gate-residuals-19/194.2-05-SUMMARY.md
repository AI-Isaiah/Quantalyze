## What changed

- **Task 1 (item 8, D-02).** The cause is the curve inversion, as the RESEARCH addendum found on PROD: `equityCurveToDailyReturns` never emits day 0, so for a curve-derived series (`daily_returns` null) the factsheet's dates start at the second curve date and its record read one day short (193 against 194).
  - `BuildFactsheetOpts.recordSeriesStart` carries the stored curve's first date. `buildFactsheetPayload` starts `endsRecord` at `recordSeriesStart ?? dates[0]`. The equity and metric series are untouched (`payload.dates` still starts at the second curve date).
  - `fetchAndBuildPayload` computes it with a new private `curveRecordStart(dailyRaw, returnsSeriesRaw)`: null when `daily_returns` normalizes to an entry (the predicate `resolveDailyReturnSeries` applies), otherwise the first stored element's `date`, verbatim, no earliest-valid scan. It is passed on the native build and the USD build, not on the composite arm.
  - The record start is a fourth `firstUnreadableDate` axis, appended last so the cash, mark-to-market and smoothed axis numbers keep their meaning. `figureRecord` already flags a malformed `seriesStart` unreadable on its own, so the axis exists to NAME the cause: the Sentry report now carries `firstBadAxis: "record_start"` and the verbatim date, and its `seriesStart` is the record start.
  - Cache key `factsheet-v2-payload-v21` to `v22` with a dated comment (the v17 to v18 precedent: values change, shape does not). The four v21 pins (page.tsx, the doc comment in fetch-and-build-payload.ts, and two test files) follow. `grep -arl payload-v21 src` now prints nothing; the whole repo outside `.planning` is also clear.
- **Task 2 (item 7).** Re-measure at code level: no `Sparkline`, and no intrinsic-pixel chart root, is reachable from `src/app/factsheet/[id]/tearsheet` or `.../v2` (the only `Sparkline` hits are two comments in `MasterBrush.tsx`; the only `width={N}` literals are `<rect>` and handle internals). The premise was closed by Phase 196 (`f4a2ab4ce`), which replaced the 620px `Sparkline` with `FactsheetView printView` and `ResponsiveChartFrame`. No overflow was found at code level, so no fix was made to the print-view width chain.
  - New `test.describe("194.2 item 7: print-view equity figure fits its card at 1470px")` in `e2e/layout-narrow.spec.ts`: seeds one strategy under the spec's per-worker prefix, 1470x900, opens `/factsheet/<id>/tearsheet`, waits for the first equity SVG, lets layout settle (networkidle plus two animation frames), then asserts every measurable SVG in `#tearsheet-main [data-census-section="equity"]` has right <= card right + 0.5 and left >= card left - 0.5, and the card lies inside `.tearsheet`.
  - Never vacuous (code reviewed here): it fails when the section has no `.tearsheet` ancestor, when no SVG has a layout box, and when the widest SVG is under 300px (a collapsed figure would pass the fit by being tiny). It skips without seed env (`HAS_SEED_ENV`, the describe's own `test.skip`) and cleans its prefix in `afterAll`. `ci.yml` is not edited: the file is already in the `e2e-seeded` list.
