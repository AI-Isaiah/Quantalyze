# Phase 194.2 Plan 06: Zoomed benchmark span and the wizard's one short-record statement Summary

On a selected range the factsheet rail now says which span the benchmark was compared over when its data starts after the window start or ends before its end (D-05), judged on the benchmark's own calendar, and the wizard no longer prints a second, hard-coded short-record sentence from the server's raw flag: `figureNote` (D-15) is the one statement (D-01).

## What changed

- `benchCoverageNote(name, from, through, { startsAfter, endsBefore })` sits beside `shortTrackNote`. It takes already formatted dates (the formatter lives in `MetricsColumn`, which imports `figure-gate`), prints the spaced en dash, and returns null when neither side is short. One covered day reads `compared on {from} only (...)`.
- `startsAfterCoverage(firstCovered, windowStart, calendar)` in `align.ts`: true when a day of the benchmark's own calendar lies in `[windowStart, firstCovered)`. A null or absent first covered day is false (no span, no note).
- `buildComparatorBlock` sets `coveredFrom` / `coveredThrough` from the same `coveredDates` the summary is computed on; absent when no day is covered.
- `MetricsColumn` `benchNote` precedence: unreadable sentence, else a selected range with a shortfall (strategy gate not `withheld`, comparator shown, a covered day exists, covered dates readable) prints the helper's sentence, else the full-history short note, else nothing. Both render sites print the identical string with the unchanged class. No figure is withheld or dashed by the note.
- Wizard: deleted the amber "Short track record" paragraph, took the raw flag out of `hasDqCaveat` (so `hasWarnings` follows), and removed the now-dead `insufficientWindow` field from the composite snapshot type and its parse line. The server flag and its other readers are untouched.

## Windowed view recomputes the fields client-side (confirmed, no cache bump)

`windowView` re-derives the slice through `deriveSeriesBundle`, which calls `buildComparatorBlock`, so a zoomed block always carries `coveredFrom` / `coveredThrough`. Proven by a test: a payload whose stored blocks have the two fields stripped (a stale cached payload) still prints the starts-after sentence on a zoom. The note never reads them at full history, and the server payload is unchanged apart from the two additive keys, so the factsheet cache key was NOT bumped. The `unstable_cache` payload shape gains two optional strings per comparator block; an old cached payload simply lacks them and the zoom path does not need them.

## Known limits (recorded, not fixed)

- The start side shares the end side's Monday-to-Friday calendar, which is not an exchange-holiday table. A weekday benchmark window that opens on a weekday market holiday reads one weekday "short" and prints the note. This mirrors `isPastCoverage` as the plan and UI-SPEC require, and the note only qualifies figures. Documented in the `startsAfterCoverage` docblock.
- `jointCmp.through` (the last close on or before the window end) drives the ends-before side, while the sentence names the last covered strategy date; they can differ by days where the benchmark has an interior gap. The sentence stays truthful (it names where figures were actually computed).
