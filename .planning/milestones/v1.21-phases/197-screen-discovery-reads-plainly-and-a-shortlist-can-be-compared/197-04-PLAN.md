Decisions taken in this plan:
- The search and the Remove links build URLs from the RESOLVED items' ids (strategy ids and validated holding refs, in display order), not from the raw `ids` query value. A raw id the page could not resolve is dropped instead of being echoed back, and the cap counts what the page shows, so an added id is never sliced off as a fifth. UI-SPEC's "existing ids in order" holds for every id the page renders.
- One tiny module `src/lib/compare-href.ts` owns `COMPARE_MAX_ITEMS = 4` and `compareHref(ids)` because three call sites need it (this page, the search, plan 05's bar). `compareHref([])` is `/compare`; otherwise `/compare?ids=` plus each id through `encodeURIComponent`, joined by commas. It does not slice: callers enforce the cap, and a unit test pins that.
- The search reuses `GET /api/strategies/browse` (allocator auth, per-user rate limit, `displayStrategyName` pseudonymity; RESEARCH Pattern 5). No new API route, so no route-contract or admin-route-manifest entry.
- `e2e/layout-narrow.spec.ts` compare block: only the one-item copy assertion changes; the "Compare strategies" heading anchor stays.
</context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query `ids` → page | attacker-controlled; already parsed and validated server-side |
| browser → `GET /api/strategies/browse` | allocator-authenticated, rate-limited catalogue read |
| client state → `router.push` | navigation target built in the browser |

| T-197-11 | Tampering (open redirect / script URL) | `router.push`, Remove hrefs | medium | mitigate | Path fixed to `/compare`; ids percent-encoded by `compareHref`; built from resolved item ids only, never from a URL in data |
| T-197-12 | Information disclosure (catalogue enumeration) | search fetch | low | accept | Existing per-user `userActionLimiter` on the route and one fetch per mount; the catalogue is what the allocator may already browse |
| T-197-SC | Tampering | npm installs | low | mitigate | No package is added; `npm ci` installs only the lockfile already on main |
</threat_model>
