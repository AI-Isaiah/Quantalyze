## Summary

All seven residuals are small, local changes. Two of them (D-01 and D-06) share one mechanism: a `flex-1`/`basis-0` item inside a `flex-wrap` row is counted as 0px by the line-breaker, so its siblings win the line and it gets the leftover; both take the same fix shape (give the flexible item a real basis). D-07 is a different defect that looks like an artifact but, from the code, is almost certainly real: `FactsheetProvider` seeds the brush range once with `useState(fullRange)`, and the composer mounts the factsheet chart while the scenario's return series is still empty (lazy `/returns` fetch), so the seed is `[0, 0]` and never follows the series when it grows. That produces exactly "Selected range: d – d", `n = 1`, KPI dashes, and a Reset button that fixes it. No user gesture can create a one-day range (`MIN_VISIBLE_SAMPLES = 5` clamps), and a genuinely one-day common window collapses to an empty payload and reads "Full history", so the "seed artifact" outcome cannot explain the UAT observation. This is `[ASSUMED]` until a jsdom test (render with `[]`, rerender with N points) is shown RED.

The two expensive parts of the phase are not the code. (1) D-04 changes the output of three helpers used by 69 non-test files; roughly 174 exact-comparison test lines across about 50 vitest files are the grep upper bound for what must be rewritten, and D-03 + D-04 rewrite the same ~24 assertion lines in two ScenarioComposer test files, so they must be one plan. (2) D-05's golden re-bake is dispatch-only, runs on the Linux runner, and, because Playwright's bare `--update-snapshots` means mode `changed`, rewrites only goldens that FAIL the comparison. The measured re-bake set is therefore "the PNGs in the bake artifact whose sha differs from the committed one". For the mobile `LABEL_W` change the 320 matrix golden always fails (its element width changes 758 → 766 user units, a size mismatch always fails); the desktop and 2560 matrix goldens will probably stay inside `maxDiffPixelRatio: 0.02` and not be rewritten (the UI-SPEC O-3 premise is a maximum, not a fact).

**Primary recommendation:** six plans (A to F in the table below): five parallel in wave 1 (D-04 + D-03 helper-and-assertion sweep; D-01 key row; D-06 sticky bar; D-05 matrix; D-07 range seed) and D-02 (CoverageTimeline, compare ticks, census form) in wave 2, because it edits `src/lib/utils.ts`'s docstring and the `CoverageTimeline.test.tsx` / `CompareEquityOverlay.test.tsx` expectations that the D-04 sweep also rewrites. ### Pattern 1: give the flexible item of a `flex-wrap` row a real basis (D-01, D-06)
**What:** In a `flex-wrap` container each item's *hypothetical main size* (its flex-basis, clamped) decides line breaking. `flex-1` is `flex: 1 1 0%`, so the item counts as 0px, every sibling whose max-content fits joins line one, and the flexible item receives only the leftover. A basis equal to the smallest acceptable width makes the line-breaker reserve that width first.
**When to use:** any `flex-1` text column beside content of unknown width in a wrapping row.
**Example (current code, then the recommended edit):**
```tsx
// Source: src/components/exchanges/AllocatorExchangeManager.tsx, active key row label column [VERIFIED: Read, line range 1817]
// at HEAD: <div className="flex-1 min-w-0 basis-[calc(100%_-_3.5rem)] @4xl:basis-0">
// edit:    <div className="flex-1 min-w-0 basis-[calc(100%_-_3.5rem)] @4xl:basis-[12.5rem]">
// (same edit on the disconnected row's label column; both carry the identical class string at HEAD)
```
```tsx
// Source: src/app/(dashboard)/allocations/components/ScenarioFooter.tsx, the summary group [VERIFIED: Read, line range 128]
// at HEAD: <div className="flex min-w-0 flex-1 flex-wrap items-center gap-x-3 gap-y-1">
// edit:    <div className="flex min-w-0 flex-1 basis-56 flex-wrap items-center gap-x-3 gap-y-1">   /* 14rem */
```
Note: Tailwind v4 generates `basis-56` from the spacing scale (0.25rem steps; 56 = 14rem) and `basis-50` = 12.5rem; the arbitrary `basis-[12.5rem]` form is equally valid and matches the reviewer's hint. `[ASSUMED]` that `basis-56` is generated without a safelist (v4 dynamic spacing); the arbitrary-value form removes the doubt.

- **Blessing a desktop golden "because the label changed".** The snapshot README rule says a desktop diff means the frozen boundary was crossed. ## Common Pitfalls

### Pitfall 1: the D-07 stale seed hides behind "it only happens on first add"
**What goes wrong:** the composer's composed branch mounts `ScenarioFactsheetChart` the moment `addedStrategies.length` is 1, before the lazy `/returns` fetch lands, so the first `portfolioDaily` is `[]`. `buildReturnsBody` treats `< 2` points (and the engine pre-collapses below n < 10) as degenerate and returns `dates: []`, so `fullRange = [0, 0]`.
**Why it happens:** `const [xRange, setXRangeRaw] = useState(fullRange)` seeds once and no effect re-seeds when `payload.dates.length` changes (only `resetXRange` re-reads `fullRange`).
**How to avoid:** write the RED rerender test first (Pattern 2). The fix belongs where the contract is broken (the provider re-follows `fullRange` until the user sets a range, e.g. store the user's range as nullable and derive `xRange = userRange ?? fullRange`), and touches `factsheet-context.tsx`, which the public factsheet and `AllocationDashboardV2` share. Run `factsheet-context.provider.test.tsx`, `basis-context.window*.test.tsx`, `MasterBrush.basis.test.tsx` and the window-kpis tests after.
**Warning signs:** the eyebrow reads "Selected range" with `start === end`, KPIs `—`, and `range-reset-*` present, with no gesture ever made.

### Pitfall 2: D-03 and D-04 edit the same assertion lines
**What goes wrong:** ~24 assertions in `ScenarioComposer.test.tsx` and `ScenarioComposer.save.test.tsx` read `...textContent).toContain("Jan 1, 2026 → Jan 6, 2026")`. Both the arrow and the spaces change. Two plans editing them in parallel conflict.
**How to avoid:** one plan owns both criteria and those two files. Keep expected strings as literals (an independent oracle), written with `\u00a0` escapes or a one-line test-local `nb()` that converts spaces inside a date literal; do not build the expected value with `formatDay` (a tautology).

### Pitfall 3: `--update-snapshots` "changed" mode proves nothing about freshness
**What goes wrong:** a bake that leaves a golden byte-identical proves it passed within tolerance, not that it matches the current render. A branch bake rewrote exactly the four goldens whose element size changed in the 169.1 incident (`.planning/debug/zoomkpis-corr-matrix-moved.md`).
**How to avoid:** treat the sha-compare of the artifact as the re-bake set; accept that desktop/2560 matrix goldens may stay "stale but passing" and say so; never `--update-snapshots=all` unreviewed.

### Pitfall 4: the portrait golden's failure is a SIZE failure
**What goes wrong:** the matrix SVG is `width:100%; minWidth: W`, so at 320px it renders 1:1 at `W = LABEL_W + N*CELL_W + 6`. With `N = 6`, mobile `CELL_W = 104`: W goes 758 → 766 when `LABEL_W` goes 128 → 136 (arithmetic from the Read values, and the committed 320 PNG is 758 pixels wide, which confirms the 1:1 rendering). A dimension mismatch always fails `toHaveScreenshot` regardless of `maxDiffPixelRatio` `[ASSUMED: Playwright behaviour as recorded in the 169.1 debug note]`, so the 320 golden needs a re-bake.
**Warning signs:** a CI failure naming `correlations-matrix-portrait-320` with a size mismatch (758 wide expected, 766 received; the committed height is 323).

### Pitfall 5: removing break opportunities can create overflow
**What goes wrong:** after D-04 a date can no longer wrap at its internal spaces. A 12-character `Oct 9, 2026` is short, but `formatDayTime` (22 chars) and range strings in narrow table cells, `truncate` rows and 320px layouts change behaviour.
**How to avoid:** run the reflow gates that already exist in the seeded job (`reflow-sweep-authed`, `no-clip-sweep`, `layout-narrow`, `axe-app-wide`) after the helper change; they are in `e2e-seeded`'s spec list and the phase's CI run is the proof.

### Pitfall 6: the cap fix alone clips the mobile label
**What goes wrong:** cap 13 with `LABEL_W = 128` puts a 124.8px end-anchored label at x = -4.8 (UI-SPEC arithmetic; CONTEXT measured 4.81px at V390). The NARROWCHARTS V390 "overview: no svg text clipped" case is the gate that sees it.

### Pitfall 7: a failed-state e2e row can pass vacuously
**What goes wrong:** if the seeded key does not actually render the helper (wrong `sync_status` value, or the page hides it), the "label column >= 199px" assertion passes against a healthy row.
**How to avoid:** assert the helper element is visible and its text length is ~150 before measuring (`[data-testid="allocator-sync-helper"]`, `data-sync-status="error"` on the pill).
