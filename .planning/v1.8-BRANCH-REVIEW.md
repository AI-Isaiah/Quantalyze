# v1.8 Flow-Aware TWR — Consolidated Integration Review

**Reviewed:** 2026-07-07
**Depth:** deep / cross-phase seam analysis
**Verdict:** The six phases compose correctly on the numeric happy paths — count-once
holds across both flow sources, the DQ-flag bridges are symmetric, the backward-NAV /
chain-linked-TWR core is disciplined and fail-loud, and the SC-4 byte-identity claim for
flow-less `estimated_start>0` accounts is intact. **One real seam defect** breaks the
milestone's own error-disposition invariant at the ccxt flow-valuation boundary (HIGH-1).
Everything else is drift/quality.

## Summary of what was verified clean

- **Count-once (Q3):** Deribit `_EXTERNAL_FLOW_TYPES ⊆ INFORMATIONAL_TYPES` are structurally
  excluded from `txn_rows_to_daily_records`' realized sum and fed to `F_t` exactly once via
  `deribit_dated_external_flows_usd`; the disjointness of CASH_BEARING/INFORMATIONAL is
  asserted at import. ccxt transfers are never in `fetch_all_trades` (fills), so no
  double-count on that seam. Same-UTC-day bucketing uses the single shared `_row_utc_day`
  on both flow and pnl (Pitfall #11 respected). Boundary-overlap dedup by `id` in
  `fetch_ccxt_transfers` closes the paginated double-count.
- **DQ-flag bridges (Q2):** All five warn flags (`negative_nav_guard`, `dust_nav_guard`,
  `flow_dominated_guard`, `flow_coverage_incomplete`, `unrealized_pnl_in_anchor`) are present
  in all four registries — the `DataQualityFlags` TypedDict, the `run_strategy_analytics`
  lift loop, the `consumer_specific_flags` promotion predicate, and the broker
  pre-stamp/CSV-lift `_BROKER_WARN_FLAGS` tuples. MED-3 clear-on-clean-rederive works: the
  pre-stamp is unconditional and replaces `data_quality_flags` wholesale, so a healed
  account returns to `complete`.
- **Fail-loud discipline:** `_coerce_float` rejects NaN/Inf at the single input choke;
  null/blank `change`/`amount` rejected as schema drift (HIGH-2 across both producers);
  the DQ-02 construction residual is honestly documented as a roll-vs-Σ self-check that does
  NOT catch wrong-scope anchors (that is deferred to the P78 parity gate). No silent-except
  was found swallowing a `NavReconstructionError`/`LedgerValuationError` on the numeric path.

## Narrative Findings (AI reviewer)

### HIGH-1 — ccxt flow-valuation `NavReconstructionError` escapes the typed catch → infinite `unknown` retry + stuck wizard + unscrubbed USD leak

**File:** `analytics-service/services/job_worker.py:2168` (raise site reachable), guarded only by
`except ccxt.RateLimitExceeded` at `:2171`; the typed `except NavReconstructionError` is at `:2205`
(around the *combine* call, a **separate** later try).

**Issue:** In `run_derive_broker_dailies_job`, the ccxt else-branch calls
`ccxt_rows_to_dated_flows(_flow_rows, venue=venue, price_index=_price_index)` (`:2168`) **inside
the first try block, which only catches `ccxt.RateLimitExceeded`**. `ccxt_rows_to_dated_flows`
raises `NavReconstructionError` (permanent, structural) for: an unknown venue, an unsignable
`type`, a missing/null/blank/non-numeric/non-finite `amount`, an undatable row, and — the
realistically-common case in production — **a non-stable coin flow with no resolvable
same-UTC-day price** (`ccxt_flows.py:207-214`). That error is NOT caught here. It propagates
out of the handler to `dispatch` (`:3524 except Exception`) → `classify_exception` → it is a
`ValueError` subclass, not an `HTTPException`, so it falls through to the terminal **`unknown`**
bucket → the job is **retried** (until `max_attempts`, then `failed_final` DB-side) instead of
being disposed permanent.

This is the exact T-74-02/T-74-03 harm class the milestone deliberately closed at the *other*
two new flow seams:
- the combine-site catch (`:2205`) stamps a **scrubbed terminal `failed`** on
  `strategy_analytics` (so the wizard poller reaches a gate) and returns
  `error_kind="permanent"`;
- the deribit producer's `LedgerValuationError` is caught at `:2040`.

At the ccxt valuation seam the account gets **none** of that: no permanent classification (retry
budget burned on an input that can never re-price), **no scrubbed `failed` stamp** (the wizard
spins on `computing` until retries exhaust), and the raw `NavReconstructionError` message — which
for the schema-drift variants contains `amount={raw_amount!r}` — reaches
`compute_jobs.error_message` **without `scrub_freeform_string`** (account-size-leak discipline
T-74-03 bypassed). No test covers a valuation-`NavReconstructionError` propagating through
`run_derive_broker_dailies_job` (the nearest test, `test_open_position_account_reconciles...`,
asserts the happy path).

**Fix:** Wrap the ccxt flow fetch+value block (or specifically `ccxt_rows_to_dated_flows`) in the
same typed disposition as the combine site — catch `NavReconstructionError`, scrub, stamp a
terminal `failed` (strategy-mode), and return `error_kind="permanent"`. Note the WR-04 comment at
`:2147` is only correct for the *fetch* (transient network → bubble retryable); the **pure
valuation** call must be split out and disposed permanent:
```python
try:
    external_flows = ccxt_rows_to_dated_flows(_flow_rows, venue=venue, price_index=_price_index)
except NavReconstructionError as exc:
    # mirror the :2205 disposition — scrub, terminal 'failed' stamp, permanent
    ...
```

### MEDIUM-1 — uPnL materiality test duplicated with divergent guards; core's flag silently dropped at the transforms boundary

**File:** `analytics-service/services/nav_twr.py:569` vs `analytics-service/services/job_worker.py:2257-2262`
(and the drop at `transforms.py:276-309` `_merge_status_meta`).

**Issue (Q4):** The `unrealized_pnl_in_anchor` materiality test is computed in two places with
**different guards**. Core: `anchor > DUST_NAV_FLOOR and abs(upnl)/anchor > ratio` (divides by
signed `anchor`). job_worker: `abs(equity) > DUST_NAV_FLOOR and abs(open_unrealized_usd)/abs(equity)
> ratio` (divides by `abs(equity)`). For a negative anchor these disagree (core suppresses, worker
flags). More structurally: the core sets the flag inside `NavTWRMeta`, but `_merge_status_meta`
carries through **only the three `_GUARD_KEYS`** — `unrealized_pnl_in_anchor` (and the core-side
`complete_with_warnings` hint it would imply) is **silently dropped** at the transforms boundary,
forcing job_worker to recompute it. Any future caller that threads `open_unrealized_usd` through
`trades_to_daily_returns_with_status` and reads the returned meta will get a `complete` hint even
when the core judged the wedge material — the flag vanishes at the seam.

**Fix:** Make `_merge_status_meta` carry `unrealized_pnl_in_anchor` (and `flow_coverage_incomplete`
if/when threaded) through additively like the three guard keys, and delete the job_worker recompute
so the ratio/guard lives in exactly one place. If the recompute must stay for the P74 byte-identity
pins, at minimum align the two conditions (both should use signed `anchor`) and add a comment
pinning them as a known duplicate.

### MEDIUM-2 — `len(returns) < 2` gate counts NaN'd (guarded / terminus-segmented) rows

**File:** `analytics-service/services/job_worker.py` — the `if len(returns) < 2:` gate runs after
`apply_flow_coverage_terminus` and after the DQ-01 guards, but `returns` still *contains* the NaN
rows (they are NaN, not dropped; the NaN-skip only happens later at csv payload build).

**Issue:** A series whose interpretable rows are almost all NaN'd (a dominating-flow account, or one
segmented back to a 1-day trustworthy tail) can pass the `>= 2` gate on NaN-inclusive length, then
write `< 2` real rows to `csv_daily_returns`. The downstream CSV run then fails "insufficient
history" — a safe permanent failure, but a confusing two-step one instead of the intended
brand-new-account short-circuit. Not wrong numbers, but the guard does not mean what it reads as.

**Fix:** Gate on `returns.notna().sum() < 2` (or `returns.dropna()`) so the "not enough history"
short-circuit reflects the rows that will actually be written.

### LOW-1 — dead function `deribit_linear_external_flow_usd`

**File:** `analytics-service/services/deribit_txn.py:350-375`.

**Issue:** The F1 scalar anchor-correction was deleted (job_worker no longer subtracts a net flow),
and `deribit_dated_external_flows_usd` superseded this linear-only scalar producer. Grep confirms
zero callers in `services/` and `tests/` — the only remaining references are its own docstring and a
"supersedes" comment. Its `CompletenessReport` fields (`net_external_flow_usd`,
`saw_unvalued_inverse_flow`) were correctly removed, but the function itself was left behind.

**Fix:** Delete `deribit_linear_external_flow_usd` (per the project dead-code gate, confirm before
removal). `_row_is_linear` is still live (used by `txn_change_to_usd`) — keep it.

### LOW-2 — ccxt flow-fetch window boundary vs terminus boundary misalignment (≤1 day)

**File:** `analytics-service/services/job_worker.py:2140-2146` (`_flow_since_ms = now_ms - retention*86400000`,
unnormalized) vs `nav_twr.py:457` (`flow_coverage_terminus_day` normalizes `now_utc` to midnight
before subtracting retention).

**Issue:** The flow-fetch lower bound is wall-clock `now`, while the terminus is `midnight(now) -
retention`. They can differ by up to one day, so a flow on the boundary day may be fetched-but-then-
NaN'd or vice-versa. Benign today (the `_union_flow_days` inclusion + guards keep it correct and the
pre-terminus region is refused anyway), but the two "retention" definitions should share one helper
to stay honest as the constants get tuned at P78.

**Fix:** Derive `_flow_since_ms` from the same normalized terminus used by the DQ-02 gate.

### LOW-3 — CAGR/Calmar basis change (TWR-05) moves EVERY existing factsheet, not just flow accounts

**File:** `analytics-service/services/metrics.py:466-511`.

**Issue (Q6):** Switching CAGR/Calmar from `len/252` to `calendar-days/365` is correct and
founder-approved, but it means the P78 "flow-less account should not MOVE" parity check will see
CAGR/Calmar **legitimately move on every account** (the golden bake `golden_252d_expected.json` was
updated to match). The SC-4 "byte-identity" guarantee is about the **returns series**, not the
headline metrics — make sure the P78 parity panel diffs the returns series (which is stable) rather
than CAGR (which is expected to shift), or it will red on clean accounts. The short-window
over-annualization (`elapsed_days==1`, exponent 365) is documented as a pre-existing, deferred DQ
class — acceptable, but it will exaggerate a days-old account's CAGR.

**Fix:** No code change required; ensure the P78 gate compares the returns series for the
no-move invariant and treats CAGR/Calmar movement as expected.

### NIT-1 — Deribit `session_upl` is an unverified assumption `[ASSUMED A1]`

**File:** `analytics-service/services/deribit_ingest.py:706-750`.

**Issue:** The open-uPnL wedge sums `session_upl` from `get_account_summaries` under an explicit
`[ASSUMED A1]` that this field is the open-unrealized component. The fallback is conservative (absent/
non-numeric/unvaluable → 0.0, never fabricated), so a wrong assumption degrades to "no wedge" rather
than a bad number — acceptable — but the assumption should be confirmed against a live Deribit
response before the wedge is trusted at P78, since a mislabeled field would silently under-flag
`unrealized_pnl_in_anchor`.
